Enterprise Database & Cloud-Native Guide

In 2027, senior backend engineers are expected to own their systems end-to-end under the "You Build It, You Run It" paradigm. This guide delineates the exact database and cloud proficiencies covered across Stages 1–3 that separate senior engineers from junior CRUD developers.

Section 1: Production Database Engineering (Stages 1 & 2)

PostgreSQL 17 Redis 7+ HikariCP Flyway

Beyond Basic CRUD: What Senior Backend Engineers Master

Junior developers only write repository.save(entity). Senior backend engineers understand what happens on disk pages, in MVCC buffers, and across connection pools:

1. Indexing & Query Plans (EXPLAIN ANALYZE)

  • B-Tree Indexes: Default for equality (=) and range (<, >) queries.
  • Leftmost Prefix Rule: A composite index (tenant_id, status, created_at) only works if your query filters by tenant_id first!
  • GIN Indexes: Used for indexing semi-structured JSONB payloads and full-text search.
  • Reading Query Plans: Identifying red flags like Sequential Scans (Seq Scan) on million-row tables versus clean Index Cond scans.

2. Connection Pooling (HikariCP) & Sizing

  • PostgreSQL Process Model: Each connection spawns a separate OS process consuming ~10–20MB RAM.
  • Pool Sizing Formula: pool_size = (cpu_cores * 2) + disk_spindles. Setting a pool to 100 on an 8-core database server degrades performance due to context-switching thrash!
  • Avoiding Pool Starvation: Keep transaction scope small; never hold a database connection while performing slow external HTTP or LLM calls.

3. Concurrency & Locking

  • Optimistic Locking (@Version): Checks a version number at commit time. High throughput, perfect for low-contention operations.
  • Pessimistic Locking (SELECT FOR UPDATE): Locks database rows immediately. Necessary for high-contention financial balance transfers.
  • Deadlock Prevention: Always acquire locks across multiple rows in consistent ascending ID order and set bounded lock_timeout.

4. Distributed Caching with Redis

  • Data Structures: Hashes for objects, Sorted Sets for ranking/leaderboards, Streams for consumer-group logs.
  • Cache Invalidation Patterns: Cache-Aside (@Cacheable), L1 Caffeine + L2 Redis, and avoiding Cache Stampedes via jittered TTLs or locks.
  • Distributed Idempotency: Storing unique request keys (X-Idempotency-Key) with TTL to prevent duplicate order submissions from mobile retries.

The Cloud Developer Mindset: "You Build It, You Run It"

1. Production Container Standards

  • Distroless / Minimal Base: No curl, no bash, no package manager in production containers (minimizes attack surface).
  • Run as Non-Root User: Prevent container escape exploits by running under a dedicated user (e.g. UID 10001).
  • JVM Container Memory: Configure -XX:MaxRAMPercentage=75.0 -XX:+UseZGC so the JVM respects Linux cgroup v2 memory limits and avoids OOMKilled crashes.

2. Kubernetes Developer Primitives

  • Liveness vs Readiness: Liveness restarts the JVM if it deadlocks. Readiness temporarily removes the pod from the Service load balancer during shutdown or DB blips.
  • Externalized Config & Secrets: Injecting database credentials from Kubernetes Secrets or AWS Secrets Manager into Spring environment variables (SPRING_DATASOURCE_PASSWORD).
  • Stateless Horizontal Autoscaling: Pods scale from 2 to 20 based on traffic because zero session state lives in JVM memory.
📱 Crucial Mobile-to-Backend Pattern: AWS S3 Presigned URLs

Junior backend devs often accept 20MB image file uploads directly into a Spring Boot controller (MultipartFile) and then upload them to S3. Senior backend engineers never do this because it chokes backend heap and socket buffers. Instead, the client asks the backend for a Presigned S3 PUT URL with a 5-minute expiration, and the Android client uploads the file directly to S3! The backend only stores the final object key in PostgreSQL.
