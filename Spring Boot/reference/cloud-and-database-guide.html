Enterprise Database & Cloud-Native Guide

In 2027, mid-level backend developers are expected to own their systems end-to-end under the "You Build It, You Run It" paradigm. This guide delineates the exact database and cloud proficiencies that separate mid-level engineers from junior developers.

Part 1: Production Database Engineering

Beyond Basic CRUD: What Mid-Level Devs Must Know

Junior developers only write repository.save(entity). Mid-level developers understand what happens on the disk, in memory buffers, and across network connections:

1. Indexing & Query Plans (`EXPLAIN ANALYZE`)

  • B-Tree Indexes: Default for equality (`=`) and range (`<, >`) queries.
  • Leftmost Prefix Rule: A composite index (tenant_id, status, created_at) only works if your query filters by tenant_id first!
  • GIN Indexes: Used for indexing semi-structured JSONB payloads and full-text search.
  • Reading Query Plans: Identifying red flags like Sequential Scans (Seq Scan) on million-row tables versus clean Index Cond scans.

2. Connection Pooling (HikariCP) & Sizing

  • PostgreSQL Process Model: Each connection spawns a separate OS process consuming 10-20MB RAM.
  • Pool Sizing Formula: pool_size = (cpu_cores * 2) + disk_spindles. Setting a pool to 100 on an 8-core database server actually degrades performance due to context-switching thrash!
  • Avoiding Pool Starvation: Keep transaction scope small; never hold a database connection while performing slow external HTTP/network calls.

3. Concurrency & Locking

  • Optimistic Locking (`@Version`): Checks a version number at commit time. High throughput, perfect for low-contention operations.
  • Pessimistic Locking (`SELECT FOR UPDATE`): Locks database rows immediately. Necessary for high-contention financial balance transfers.
  • Deadlock Prevention: Always acquire locks across multiple rows in consistent alphabetical/numerical order.

4. Distributed Caching with Redis

  • Data Structures: Hashes for objects, Sorted Sets for ranking/leaderboards, Streams for audit logs.
  • Cache Invalidation Patterns: Cache-Aside (`@Cacheable`), Write-Through, and avoiding Cache Stampedes via probabilistic early expiration or distributed locks.
  • Distributed Idempotency: Storing unique request keys (`X-Idempotency-Key`) with TTL to prevent duplicate order submissions from mobile retries.

The Cloud Developer Mindset: "You Build It, You Run It"

In 2027, you are not expected to be a cloud sysadmin configuring raw BGP routing or provisioning VPC peering. But you must know how your application packages, scales, authenticates with cloud services, and deploys.

1. Production Container Standards

  • Distroless / Minimal Base: No curl, no bash, no package manager in production containers (minimizes attack surface).
  • Run as Non-Root User: Prevent container escape exploits by running under dedicated user (e.g. `UID 10001`).
  • JVM Container Memory: Configure `-XX:MaxRAMPercentage=75.0` so the JVM respects Docker cgroup memory limits and avoids Linux OOM (Out Of Memory) killer kills.

2. Kubernetes Developer Primitives

  • Liveness vs Readiness: Liveness restarts the JVM if it deadlocks. Readiness temporarily removes the pod from the load balancer if the database connection drops.
  • Externalized Config & Secrets: Injecting database credentials from Kubernetes Secrets or AWS Secrets Manager into Spring environment variables (`SPRING_DATASOURCE_PASSWORD`).
  • Stateless Horizontal Autoscaling: Pods scale from 2 to 20 based on CPU/traffic because zero session state lives in JVM memory.
📱 Crucial Mobile-to-Backend Pattern: AWS S3 Presigned URLs

Junior backend devs often accept 20MB image file uploads directly into a Spring Boot controller (`MultipartFile`) and then upload it to S3. Mid-level backend devs don't do this because it chokes backend memory and threads. Instead, the client asks the backend for a Presigned S3 URL with a 5-minute expiration, and the Android client uploads the file directly to S3/Cloud Storage! The backend only stores the final image URL in PostgreSQL.
