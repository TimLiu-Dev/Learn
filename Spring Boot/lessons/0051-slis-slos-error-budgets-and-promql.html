SLIs, SLOs, Error Budgets & PromQL Burn-Rate Alerts

Target: Exposing /actuator/prometheus is easy; turning raw numbers into reliable operational decisions is what distinguishes senior observability. Teams routinely fall into two traps: measuring average latency (which hides 5-second tail timeouts affecting 2% of mobile users) and paging engineers on CPU spikes that don't affect customers. In this lesson, we configure Spring Boot native Micrometer histogram buckets & SLO boundaries, write accurate PromQL P99 queries, and apply Error Budgets to page only when user reliability is actually burning.

📖 Primary Source Recommendation

Study the official authorities: Google SRE Workbook: Alerting on SLOs and Spring Boot Actuator: Per-Meter Histogram & SLO Properties.

💡 Why This Matters in Production

If 99 requests take 10ms and 1 checkout request takes 10,000ms, the average is ~110ms—looks totally fine on a naive dashboard, while real customers see timeouts. Histograms (http_server_requests_seconds_bucket) + histogram_quantile(0.99, ...) expose the true P99 experience across multiple pods.

Key Architectural Takeaways

  • SLI vs. SLO vs. Error Budget: An SLI is the measurement (e.g., % of HTTP requests under 250ms and non-5xx); an SLO is the target (e.g., 99.9% over 30 days); the Error Budget is the remaining 0.1% (~43.2 minutes of bad behavior per month).
  • Why Client-Side Percentiles Fail Across Pods: Never average publishPercentiles across 10 Kubernetes pods—averages of percentiles are mathematically invalid. Always publish Prometheus histograms (management.metrics.distribution.percentiles-histogram) and compute quantiles server-side in PromQL.
  • Spring Boot Native SLO Buckets: Configure management.metrics.distribution.slo.http.server.requests=100ms,250ms,500ms so Prometheus gets exact bucket boundaries aligned with your SLO without wasting buckets.
  • RED Method for Services: Every Spring Boot endpoint needs Rate (RPS), Errors (5xx ratio), and Duration (P95/P99 latency).
  • Burn-Rate Alerting: Alert when the error budget is burning fast (e.g., 14.4× normal burn over 1 hour = 2% monthly budget lost in 1 hour), eliminating noisy CPU/memory wakeups.

Production Implementation (Spring Boot Config & PromQL vs Custom Timer)

Histograms, SLO Buckets & PromQL Queries 
# application.yml — Publish exact Prometheus histogram buckets for SLOs
management:
  metrics:
    distribution:
      percentiles-histogram:
        http.server.requests: true
      slo:
        http.server.requests: 50ms,100ms,250ms,500ms,1s

---
# PromQL Queries for Grafana & Alertmanager
# 1. P99 Request Latency over 5m window (valid across all pods)
histogram_quantile(0.99, sum by (le, uri) (
  rate(http_server_requests_seconds_bucket{application="order-service"}[5m])
))

# 2. 5xx Error Ratio (SLI)
sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
/
sum(rate(http_server_requests_seconds_count[5m]))

---
// Java: Recording a custom Timer with explicit SLO buckets
Timer.builder("nexus.checkout.duration")
     .publishPercentileHistogram()
     .serviceLevelObjectives(Duration.ofMillis(100), Duration.ofMillis(250), Duration.ofMillis(500))
     .register(meterRegistry);

💡 Complete Production Reference Solution
Java 21/25 Implementation:
// PromQL: histogram_quantile(0.99, sum by (le) (rate(nexus_payment_duration_seconds_bucket[5m])))
public Timer checkoutTimer(MeterRegistry registry) {
    return Timer.builder("nexus.payment.duration")
        .publishPercentileHistogram()
        .serviceLevelObjectives(Duration.ofMillis(100), Duration.ofMillis(250))
        .register(registry);
}
Kotlin 2.x Implementation:
// PromQL: histogram_quantile(0.99, sum by (le) (rate(nexus_payment_duration_seconds_bucket[5m])))
fun checkoutTimer(registry: MeterRegistry): Timer =
    Timer.builder("nexus.payment.duration")
        .publishPercentileHistogram()
        .serviceLevelObjectives(Duration.ofMillis(100), Duration.ofMillis(250))
        .register(registry)
Architectural Breakdown:

Explicit SLO boundaries ensure exact bucket counts right at your 100ms/250ms thresholds, while sum by (le) (rate(..._bucket[5m])) aggregates accurately across any number of Kubernetes replicas.
