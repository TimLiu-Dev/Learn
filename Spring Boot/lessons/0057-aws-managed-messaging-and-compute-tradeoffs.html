AWS Managed Messaging (SQS/SNS/EventBridge) & Compute Tradeoffs

Target: Running a 3-node Apache Kafka cluster (or Amazon MSK) costs thousands of dollars and nontrivial ops effort when all you really needed was reliable async job queuing or fan-out notifications. On AWS, senior architects match the tool to the workload: SQS + SNS + EventBridge for serverless pay-per-message queues vs. Kafka for high-throughput event replay, and ECS Fargate vs. EKS for running Spring Boot containers. In this lesson, we master those architectural tradeoffs and implement an idempotent Spring Cloud AWS @SqsListener with Dead-Letter Queues.

📖 Primary Source Recommendation

Study the official authority: Spring Cloud AWS Reference: SQS & SNS Integration.

💡 Why This Matters in Production

Choosing Kafka when you need a simple work queue (like sending receipts or thumbnailing S3 uploads) creates unnecessary partition rebalancing headaches; choosing SQS when you need multi-consumer event replay across 7-day history won't work because SQS deletes messages upon acknowledgement. Knowing when to pick each is a staple Senior System Design question.

Key Architectural Takeaways

  • SQS vs. SNS vs. EventBridge vs. Kafka:
    • Amazon SQS: Competing-consumer point-to-point queue; messages deleted after ack; visibility timeout + automatic DLQ after maxReceiveCount. Standard = at-least-once; FIFO = strict ordering per MessageGroupId.
    • SNS + SQS Fan-Out: Publish one event to SNS, fan out into independent SQS queues per microservice for isolated retries and DLQs.
    • EventBridge: Content-based JSON event router across AWS services and SaaS webhooks.
    • Apache Kafka / MSK: Append-only log with consumer-offset replay, stream joins, and high sustained throughput.
  • Spring Boot Compute on AWS (App Runner vs. ECS Fargate vs. EKS): Small/medium teams ship Spring Boot faster on ECS Fargate (zero node OS patching, native ALB/IAM); large multi-team orgs standardize on EKS for Kubernetes ecosystem portability.
  • SQS Visibility Timeout Rule: Always configure SQS visibility timeout > max processing time + Spring retry backoff, or a second worker picks up the same in-flight message (requiring idempotency!).

Production Implementation (Java 21/25 vs Kotlin 2.x — Spring Cloud AWS SQS Listener)

Idempotent @SqsListener with Explicit Ack Mode 
package com.nexus.worker;

import io.awspring.cloud.sqs.annotation.SqsListener;
import io.awspring.cloud.sqs.listener.acknowledgement.Acknowledgement;
import org.springframework.stereotype.Component;

@Component
public class S3UploadEventConsumer {

    // ON_SUCCESS (default) acks only when method returns cleanly;
    // MANUAL gives explicit control after idempotent DB/Redis commit.
    @SqsListener(value = "${nexus.sqs.upload-queue}", acknowledgementMode = "MANUAL")
    public void onFileUploaded(UploadEvent event, Acknowledgement ack) {
        if (alreadyProcessed(event.eventId())) {
            ack.acknowledge(); // Deduplicate at-least-once redelivery safely
            return;
        }
        processInvoiceThumbnail(event);
        ack.acknowledge(); // Delete from SQS; exceptions leave message for DLQ redrive
    }
}

Hint 2: Deduplication Guard

💡 Complete Production Reference Solution
Java 21/25 Implementation:
@Component
public class OrderSqsConsumer {
    @SqsListener(value = "nexus-orders-queue", acknowledgementMode = "MANUAL")
    public void onOrderEvent(String eventId, Acknowledgement ack) {
        if (isDuplicate(eventId)) {
            ack.acknowledge();
            return;
        }
        process(eventId);
        ack.acknowledge();
    }
}
Kotlin 2.x Implementation:

Architectural Breakdown:

Manual acknowledgement plus idempotency ensures SQS at-least-once redeliveries never double-charge or double-emit, while unhandled exceptions leave messages un-acked until SQS moves them to the DLQ.
