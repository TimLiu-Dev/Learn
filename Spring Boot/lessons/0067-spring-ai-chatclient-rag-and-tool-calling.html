Spring AI: ChatClient, Structured Output, Tool Calling & pgvector RAG

Target: In 2027, backend engineers aren't expected to train foundation models—they ARE expected to integrate LLMs cleanly into existing Java/Kotlin services with strict type safety, guardrails, and observability. Spring AI gives Spring Boot developers a familiar fluent API (ChatClient, similar to RestClient!), typed Structured Output mapped directly into Java Records / Kotlin data classes, RAG powered by PostgreSQL pgvector, and Tool Calling into real domain services.

📖 Primary Source Recommendation

Study the official authority: Spring AI Reference Documentation (ChatClient, Advisors & Tool Calling).

💡 Why This Matters in Production

LLM calls take 1–10 seconds over external HTTPS—never hold a PostgreSQL connection or @Transactional lock open while waiting on an AI model! Run ChatClient calls outside transaction boundaries on Virtual Threads, enforce timeouts + Resilience4j fallbacks, and use Structured Output (entity(OrderTriage.class)) so downstream code never crashes parsing free-form markdown.

Key Architectural Takeaways

  • Fluent ChatClient API: Built via ChatClient.Builder—supports system prompts, user prompts, .entity(MyRecord.class) for JSON-schema-enforced structured output, and streaming (.stream()) compatible with SSE (Lesson 0060).
  • RAG via Advisors + pgvector: Attach QuestionAnswerAdvisor backed by a PostgreSQL pgvector VectorStore so prompts retrieve grounded company docs without spinning up a separate vector database.
  • Tool Calling (@Tool): Expose strictly read-scoped or RBAC-checked Spring methods with @Tool so the model can look up live order status safely instead of hallucinating.
  • Production Guardrails: Keep LLM calls outside @Transactional (prevent HikariCP starvation!), set strict HTTP timeouts, and track token usage via Micrometer observability built into Spring AI.

Production Implementation (Java 21/25 vs Kotlin 2.x)

Typed Structured Output + @Tool Calling with ChatClient 
public record SupportTriage(String category, boolean urgent, String summary) {}

@Component
public class OrderLookupTools {
    @Tool(description = "Fetch current fulfillment status for an order ID")
    public String getOrderStatus(String orderId) {
        return "SHIPPED"; // Read-only lookup; enforce tenant authorization!
    }
}

@Service
public class SupportAssistantService {
    private final ChatClient chatClient;

    public SupportAssistantService(ChatClient.Builder builder, VectorStore vectorStore, OrderLookupTools tools) {
        this.chatClient = builder
            .defaultAdvisors(new QuestionAnswerAdvisor(vectorStore))
            .defaultTools(tools)
            .build();
    }

    // NEVER annotate with @Transactional: LLM latency would exhaust HikariCP connections!
    public SupportTriage triageTicket(String customerMessage) {
        return chatClient.prompt()
            .system("Classify e-commerce support tickets concisely.")
            .user(customerMessage)
            .call()
            .entity(SupportTriage.class);
    }
}

Java 21/25 Implementation:
public class AiRiskService {
    private final ChatClient chatClient;

    public AiRiskService(ChatClient.Builder builder, VectorStore vectorStore) {
        this.chatClient = builder.defaultAdvisors(new QuestionAnswerAdvisor(vectorStore)).build();
    }

    @Tool(description = "Check SKU stock count")
    public int stockCount(String sku) { return 42; }

    public RiskAssessment assess(String promptText) {
        return chatClient.prompt().user(promptText).call().entity(RiskAssessment.class);
    }
}

Architectural Breakdown:

Spring AI treats LLM calls like structured typed HTTP integrations, while keeping them outside @Transactional protects your PostgreSQL connection pool.
