Kubernetes Sizing: CPU Throttling, HPA & PodDisruptionBudgets

Target: Why does a Spring Boot pod showing only 35% average CPU suddenly stall for 200–400ms on every P99 request inside Kubernetes? The culprit is almost always Linux CFS CPU throttling triggered by overly tight limits.cpu. In this lesson, we distinguish Kubernetes requests from limits for JVM workloads, configure Horizontal Pod Autoscalers (HPA) that scale cleanly ahead of traffic spikes, and add PodDisruptionBudgets (PDB) so cluster upgrades never kill all your replicas at once.

📖 Primary Source Recommendation

Study the official authorities: Kubernetes Resource Management and Kubernetes PodDisruptionBudget (PDB) Guide.

💡 Why This Matters in Production

The JVM is multi-threaded by nature: GC threads, JIT C2 compiler threads, Netty/Tomcat workers, and Virtual Thread carrier pools burst briefly for 10–30ms. A limits.cpu: "500m" quota gives you only 50ms of CPU time per 100ms CFS period—causing the Linux kernel to freeze all JVM threads for the remaining 50ms, crushing P99 latency even when the host node has plenty of idle CPU!

Key Architectural Takeaways

  • Memory vs. CPU Limits Are Fundamentally Different: Always set requests.memory == limits.memory (Guaranteed memory avoids unpredictable OOM eviction), paired with -XX:MaxRAMPercentage=75.0.
  • Beware Tight limits.cpu: Set realistic requests.cpu (used for scheduler placement & HPA percentage math), and either omit limits.cpu or leave generous burst headroom so JVM JIT & GC bursts aren't CFS-throttled.
  • Horizontal Pod Autoscaler (HPA): Scale pods automatically between minReplicas (at least 2 for HA) and maxReplicas using CPU, memory, or custom Prometheus metrics (e.g., Kafka consumer lag or HTTP RPS).
  • PodDisruptionBudget (PDB): Guarantees Kubernetes voluntary evictions (node upgrades, Spot node drains) keep at least minAvailable pods healthy—never leaving an endpoint with zero ready pods.

Production Implementation (Kubernetes Sizing, HPA & PDB vs Spring Probe Alignment)

Hardened Deployment Sizing, HPA & PodDisruptionBudget 
# 1. Container Resource Sizing (JVM-Friendly, No CPU Throttling Trap)
resources:
  requests:
    cpu: "1000m"
    memory: "1Gi"
  limits:
    memory: "1Gi"   # Equal to requests.memory; omit tight limits.cpu on bursty JVM workloads!
env:
  - name: JAVA_TOOL_OPTIONS
    value: "-XX:MaxRAMPercentage=75.0 -XX:+UseZGC"

---
# 2. HorizontalPodAutoscaler (HPA)
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: order-service-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: order-service
  minReplicas: 2
  maxReplicas: 12
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 65

---
# 3. PodDisruptionBudget (PDB)
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: order-service-pdb
spec:
  minAvailable: 1
  selector:
    matchLabels:
      app: order-service
# Kotlin Spring Boot pods share identical JVM + cgroups v2 ergonomics
# Add Kotlin-specific startup optimization:
#   - Spring AOT / CDS reduces startup CPU burst during HPA scale-out
resources:
  requests:
    cpu: "1000m"
    memory: "1Gi"
  limits:
    memory: "1Gi"
env:
  - name: JAVA_TOOL_OPTIONS
    value: "-XX:MaxRAMPercentage=75.0 -XX:+UseZGC -Dspring.threads.virtual.enabled=true"

---
# Startup Probe protects slow JVM JIT warm-up during HPA scale-out:
startupProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8080
  failureThreshold: 12
  periodSeconds: 5   # Up to 60s for cold JVM boot before liveness checks begin

Equal memory requests/limits lock in predictable cgroups heap math, omitting tight CPU limits eliminates CFS stalls, HPA scales dynamically, and PDB protects availability during node maintenance.
