Kafka Production Operations: Manual Offsets, Cooperative Rebalancing, Consumer Lag & Log Compaction

Target: The most common Kafka outage in Spring Boot production is not a crashed broker—it is an infinite Consumer Rebalance Storm triggered when a batch takes longer than max.poll.interval.ms, or silent data loss from enable-auto-commit=true! Master AckMode.MANUAL_IMMEDIATE, CooperativeStickyAssignor incremental rebalancing, tuning max.poll.records, monitoring Consumer Lag, and Log Compaction + Tombstones.

📖 Primary Source Recommendation

Study the official authorities: Spring for Apache Kafka: Committing Offsets & AckMode and Apache Kafka Docs: Log Compaction & Cooperative Rebalancing.

💡 Android Mental Model Bridge

Think of Kafka consumer offsets like a bookmark in an audiobook: with enable-auto-commit=true, a timer advances the bookmark every 5 seconds even if your code hasn't finished saving the chapter! With AckMode.MANUAL_IMMEDIATE, you only call ack.acknowledge() *after* PostgreSQL commits cleanly.

1. Four Kafka Operational Rules That Prevent 2 AM Pager Storms

  • Disable Auto-Commit & Use AckMode.MANUAL_IMMEDIATE: Set spring.kafka.consumer.enable-auto-commit=false and spring.kafka.listener.ack-mode=MANUAL_IMMEDIATE (or Spring Kafka's default BATCH), calling Acknowledgment.acknowledge() only after durable DB writes succeed. Know auto-offset-reset=earliest vs. latest for brand-new consumer groups!
  • Stop Infinite Rebalance Loops (max.poll.interval.ms & max.poll.records): If poll() fetches 500 records and each record takes 1 second to call a slow API (500s total > default 300s max.poll.interval.ms), the broker declares the pod dead, kicks it out of the group, reassigns the partitions to another pod—which then also times out in an endless loop! Fix: lower max.poll.records (e.g. 50) and size max.poll.interval.ms realistically.
  • CooperativeStickyAssignor Incremental Rebalancing: Legacy eager rebalancers stop *every* pod across the whole consumer group whenever one pod deploys. Setting partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor moves only affected partitions while healthy pods keep consuming uninterrupted.
  • Log Compaction (cleanup.policy=compact) & Tombstones: Time-based retention deletes old events after 7 days. Compacted topics keep the *latest* value per message key forever (ideal for reference data replication like products.catalog), and publishing a record with a null payload (Tombstone) deletes that key cleanly.

1. Anatomy of a max.poll.interval.ms Rebalance Death Spiral

1. Pod A polls 500 records (default max.poll.records=500) 2. Downstream HTTP call slows to 800ms/msg ==> Batch takes 400s (> 300s max.poll.interval.ms!) 3. Broker declares Pod A dead, revokes partitions, rejects Pod A's offset commit! 4. Pod B receives the exact same 500 unacked records ==> Takes 400s ==> INFINITE REBALANCE STORM! FIX: Set max.poll.records=50 + CooperativeStickyAssignor + bounded HTTP timeouts!

2. Topic Retention Policy Matrix: Delete vs. Log Compaction

Cleanup Policy What Kafka Retains Ideal Domain Use Case
cleanup.policy=delete All immutable events within time/size window (e.g., 7 days) Fact streams: orders.placed, payments.captured, audit trails
cleanup.policy=compact Latest record value per message key (null value = Tombstone delete) Entity state snapshots: fx.exchange-rates, catalog.products

Always monitor kafka_consumergroup_lag (latest broker offset minus committed consumer offset) in Prometheus—rising lag is your earliest warning that consumers cannot keep pace with producer throughput.

package com.nexus.kafka;

import org.springframework.kafka.annotation.KafkaListener;
import org.springframework.kafka.support.Acknowledgment;
import org.springframework.stereotype.Component;

@Component
public class SettlementConsumer {
    private final SettlementService service;

    public SettlementConsumer(SettlementService service) { this.service = service; }

    @KafkaListener(topics = "payments.settled", groupId = "ledger-writers")
    public void onMessage(String payload, Acknowledgment ack) {
        service.applyIdempotently(payload); // Durable DB commit first!
        ack.acknowledge();                  // Commit Kafka offset only AFTER DB succeeds
    }
}

Architectural Breakdown:

Manual offset commits guarantee at-least-once processing only after durable persistence succeeds, while CooperativeStickyAssignor eliminates stop-the-world pauses during rolling deployments.
