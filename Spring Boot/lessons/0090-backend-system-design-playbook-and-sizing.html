Senior Backend System Design Playbook: Back-of-the-Envelope Capacity Math, Bottlenecks & Tradeoffs

Target: In Senior Spring Boot interviews, knowing individual tools (`Redis`, `Kafka`, `PostgreSQL`, `Virtual Threads`) is only half the battle—the System Design round tests whether you can **combine them under constraints**. Master the repeatable 4-step Senior System Design framework: back-of-the-envelope QPS/storage/bandwidth math, identifying the real bottleneck (read vs. write vs. fan-out), sizing HikariCP/Redis/Kafka partitions from numbers, and defending failure-mode tradeoffs.

📖 Primary Source Recommendation

Study the official authority: Designing Data-Intensive Applications (Martin Kleppmann) and High Scalability Architecture Case Studies.

💡 Android Mental Model Bridge

In Android interviews, you design for battery, memory, and flaky offline networks on 1 device. In Senior Backend System Design, you translate product requirements ("10M daily active users") into requests per second (RPS), peak bursts (3×–5× average), PostgreSQL IOPS vs. Redis hit rate, and Kafka consumer parallelism!

1. Cheat Sheet: Numbers Every Senior Engineer Calculates in 60 Seconds

  • The 86,400 Rule: $1\text{ day} \approx 10^5\text{ seconds}$ (`86,400s`). So $10\text{M requests/day} \approx 115\text{ RPS average}$ and $\sim 400\text{–}600\text{ RPS peak}$.
  • Read vs. Write Ratio Dictates Architecture: A 100:1 read-heavy feed (`50,000 read RPS`, `500 write RPS`) needs **L1 Caffeine + L2 Redis + Read Replicas + CDN/ETag**. A write-heavy ingestion pipeline (`50,000 write RPS`) needs **Kafka partitioning + batch/async DB writes + Redis counters** rather than synchronous JPA writes!
  • Storage Math: $1\text{ KB/row} \times 1\text{M rows} = 1\text{ GB}$. $1\text{B rows} \approx 1\text{ TB}$ (requires PostgreSQL range partitioning or sharding!).
  • Latency Math (Little's Law & Concurrency): Concurrent in-flight requests $= \text{RPS} \times \text{Latency (sec)}$. At $2,000\text{ RPS}$ and $50\text{ms}$ DB time, you need $2,000 \times 0.05 = 100$ concurrent DB operations—exceeding a single 20-connection HikariCP pool unless you scale replicas, cache hot reads, or shorten transactions!

2. Production Implementation (Capacity Estimator in Java 21/25 & Kotlin 2.x)

Little's Law Concurrency & Kafka Partition Sizer 
package com.nexus.sysdesign;

public class CapacityCalculator {
    // Little's Law: L = lambda * W (concurrent in-flight operations = RPS * latencySeconds)
    public static int requiredConcurrency(double peakRps, double avgLatencyMs) {
        return (int) Math.ceil(peakRps * (avgLatencyMs / 1000.0));
    }

    // Minimum Kafka partitions = ceil(peakEventsPerSec / singleConsumerThroughputPerSec)
    public static int minKafkaPartitions(double peakEventsPerSec, double singlePodThroughput) {
        return (int) Math.ceil(peakEventsPerSec / singlePodThroughput);
    }

    // Daily storage in GB: (eventsPerDay * bytesPerEvent) / 10^9
    public static double dailyStorageGb(long eventsPerDay, int bytesPerEvent) {
        return (eventsPerDay * (double) bytesPerEvent) / 1_000_000_000.0;
    }
}
package com.nexus.sysdesign

import kotlin.math.ceil

object CapacityCalculator {
    fun requiredConcurrency(peakRps: Double, avgLatencyMs: Double): Int =
        ceil(peakRps * (avgLatencyMs / 1000.0)).toInt()

    fun minKafkaPartitions(peakEventsPerSec: Double, singlePodThroughput: Double): Int =
        ceil(peakEventsPerSec / singlePodThroughput).toInt()

    fun dailyStorageGb(eventsPerDay: Long, bytesPerEvent: Int): Double =
        (eventsPerDay * bytesPerEvent.toDouble()) / 1_000_000_000.0
}
