Keyset (Cursor) Pagination & Dynamic Read-Replica Routing

Target: Solve high-scale database bottlenecks. Learn why OFFSET pagination kills database performance, implement Keyset (cursor) pagination (mirroring Android Paging 3), and route read queries dynamically to PostgreSQL read-replicas.

📖 Primary Source Recommendation

Study the official authority: High-Performance Java Persistence: Keyset Pagination (Vlad Mihalcea). Ground your learning in primary architecture rather than secondary summaries.

1. Why `OFFSET 100000` Kills Database Performance

Junior developers use offset pagination: SELECT * FROM orders ORDER BY id LIMIT 20 OFFSET 100000;. To return those 20 rows, PostgreSQL must fetch and scan all 100,020 rows from disk, sort them, and discard the first 100,000!

As pages increase, query latency spikes from 2ms to 4,000ms, causing database CPU saturation.

🤖 Android Mental Model: Paging 3 & Keyset Cursors

In Android, Jetpack Paging 3 uses PagingSource<Key, Value> where the key is a cursor ID. Keyset pagination is the exact backend implementation! Instead of OFFSET, the client passes ?after_id=8921, and the backend queries WHERE id > 8921 ORDER BY id ASC LIMIT 20. This uses an index scan and executes in 0.05ms regardless of whether you are on page 1 or page 50,000!

2. Keyset (Cursor) Pagination Pattern

Keyset Pagination Repository 
package com.example.ecommerce.order;

import org.springframework.data.jpa.repository.*;
import org.springframework.data.repository.query.Param;
import java.util.List;

public interface OrderKeysetRepository extends JpaRepository<OrderEntity, Long> {

    // First page: where afterId is null
    @Query("SELECT o FROM OrderEntity o ORDER BY o.id ASC LIMIT :limit")
    List<OrderEntity> findFirstPage(@Param("limit") int limit);

    // Subsequent pages: O(1) index seek!
    @Query("SELECT o FROM OrderEntity o WHERE o.id > :afterId ORDER BY o.id ASC LIMIT :limit")
    List<OrderEntity> findNextPage(@Param("afterId") Long afterId, @Param("limit") int limit);
}
package com.example.ecommerce.order

import org.springframework.data.repository.query.Param

    @Query("SELECT o FROM OrderEntity o ORDER BY o.id ASC LIMIT :limit")
    fun findFirstPage(@Param("limit") limit: Int): List<OrderEntity>

    @Query("SELECT o FROM OrderEntity o WHERE o.id > :afterId ORDER BY o.id ASC LIMIT :limit")
    fun findNextPage(@Param("afterId") afterId: Long, @Param("limit") limit: Int): List<OrderEntity>
}

3. Dynamic Read-Replica Routing (`AbstractRoutingDataSource`)

In high-traffic systems, 90% of database traffic is read-only. Using Spring's AbstractRoutingDataSource, you can automatically route @Transactional(readOnly = true) queries to AWS RDS Read-Replicas, while write operations hit the Primary DB:

Read/Write Dynamic Routing DataSource 
package com.example.ecommerce.database;

import org.springframework.jdbc.datasource.lookup.AbstractRoutingDataSource;
import org.springframework.transaction.support.TransactionSynchronizationManager;

public class ReplicaRoutingDataSource extends AbstractRoutingDataSource {

    @Override
    protected Object determineCurrentLookupKey() {
        // If current transaction is readOnly, route to REPLICA!
        boolean isReadOnly = TransactionSynchronizationManager.isCurrentTransactionReadOnly();
        return isReadOnly ? DatabaseType.REPLICA : DatabaseType.PRIMARY;
    }

    public enum DatabaseType { PRIMARY, REPLICA }
}
package com.example.ecommerce.database

import org.springframework.jdbc.datasource.lookup.AbstractRoutingDataSource
import org.springframework.transaction.support.TransactionSynchronizationManager

class ReplicaRoutingDataSource : AbstractRoutingDataSource() {

    override fun determineCurrentLookupKey(): Any {
        val isReadOnly = TransactionSynchronizationManager.isCurrentTransactionReadOnly()
        return if (isReadOnly) DatabaseType.REPLICA else DatabaseType.PRIMARY
    }

    enum class DatabaseType { PRIMARY, REPLICA }
}

Lab 0014 Implement Keyset Cursor Query Builder
To Do

Goal: Implement buildKeysetQuery(Long afterId, int limit):

  • If afterId == null: return "SELECT * FROM orders ORDER BY id ASC LIMIT " + limit
  • If afterId != null: return "SELECT * FROM orders WHERE id > " + afterId + " ORDER BY id ASC LIMIT " + limit
Hint 1: Architectural Nudge
Check if afterId is null.
Hint 2: Syntax Signature
Use WHERE id > afterId when afterId is provided.
Hint 3: Concrete Snippet
if (afterId == null) return "SELECT * FROM orders ORDER BY id ASC LIMIT " + limit; else return "SELECT * FROM orders WHERE id > " + afterId + " ORDER BY id ASC LIMIT " + limit;
💡 Complete Production Reference Solution
Java 21 Implementation:
package com.example.pagination;

public class KeysetQueryBuilder {
    public static String buildKeysetQuery(Long afterId, int limit) {
        if (afterId == null) {
            return "SELECT * FROM orders ORDER BY id ASC LIMIT " + limit;
        }
        return "SELECT * FROM orders WHERE id > " + afterId + " ORDER BY id ASC LIMIT " + limit;
    }
}
Kotlin 2.x Implementation:
package com.example.pagination

object KeysetQueryBuilder {
    fun buildKeysetQuery(afterId: Long?, limit: Int): String {
        return if (afterId == null) {
            "SELECT * FROM orders ORDER BY id ASC LIMIT $limit"
        } else {
            "SELECT * FROM orders WHERE id > $afterId ORDER BY id ASC LIMIT $limit"
        }
    }
}
Architectural Breakdown:

Keyset pagination ensures that querying page 10,000 is just as fast as page 1, because PostgreSQL seeks the B-Tree primary key index directly without scanning and discarding prior records.
