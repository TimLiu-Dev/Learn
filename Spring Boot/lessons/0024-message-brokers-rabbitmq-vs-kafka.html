Demystifying Message Brokers: RabbitMQ (Queues) vs Apache Kafka (Streams)

Target: Demystify message brokers. Understand point-to-point queues vs distributed append-only commit logs, smart broker vs dumb broker architectures, and when to pick RabbitMQ vs Kafka.

📖 Primary Source Recommendation

Study the official authority: Martin Fowler: What is an Event-Driven Architecture?. Ground your learning in primary architecture rather than secondary summaries.

1. Why Not Just Use HTTP REST Between Services?

When an order is placed, 5 things must happen: charge credit card, reserve inventory, send push notification, generate invoice PDF, update analytics.

  • Synchronous HTTP Chain: If you call 5 REST APIs in sequence, the HTTP request takes 4 seconds. If the notification service is down, the whole order fails!
  • Asynchronous Event-Driven: The order service writes an event OrderPlaced to a broker in 2ms and returns 201 Created to the Android app. Downstream services consume the event at their own pace!

2. RabbitMQ vs Apache Kafka: The Architectural Divide

Feature RabbitMQ (AMQP) Apache Kafka (Distributed Log)
Core Model Queue (Traditional Message Broker) Distributed Append-Only Commit Log
Message Lifecycle Deleted from broker once consumed & acknowledged Retained on disk for days/months; replayable!
Broker Intelligence Smart broker, dumb consumer (broker tracks delivery) Dumb broker, smart consumer (consumer tracks offset)
Ideal Use Case Complex routing, task workers, immediate processing High-throughput event streaming, event sourcing, replay

3. Dual Java & Kotlin Publisher Comparison

Publishing Events (Kafka vs RabbitMQ) 
package com.example.ecommerce.event;

import org.springframework.kafka.core.KafkaTemplate;
import org.springframework.stereotype.Service;

@Service
public class OrderEventPublisher {
    private final KafkaTemplate<String, String> kafkaTemplate;

    public OrderEventPublisher(KafkaTemplate<String, String> kafkaTemplate) {
        this.kafkaTemplate = kafkaTemplate;
    }

    public void publishOrderPlaced(String orderId, String payloadJson) {
        // Partition key is orderId: guarantees partition ordering!
        kafkaTemplate.send("orders.v1", orderId, payloadJson);
    }
}

    private val kafkaTemplate: KafkaTemplate<String, String>

    fun publishOrderPlaced(orderId: String, payloadJson: String) {
        kafkaTemplate.send("orders.v1", orderId, payloadJson)
    }

💡 Complete Production Reference Solution
Java 21 Implementation:
package com.example.broker;

public class BrokerSelector {
    public static String recommendBroker(boolean needsReplay, boolean complexAmqpRouting) {
        if (needsReplay) return "KAFKA";
        if (complexAmqpRouting) return "RABBITMQ";
        return "KAFKA";
    }
}
Kotlin 2.x Implementation:
package com.example.broker

object BrokerSelector {
    fun recommendBroker(needsReplay: Boolean, complexAmqpRouting: Boolean): String =
        when {
            needsReplay -> "KAFKA"
            complexAmqpRouting -> "RABBITMQ"
            else -> "KAFKA"
        }
}
Architectural Breakdown:

Selecting between Kafka and RabbitMQ depends on architectural needs: log retention and event replay mandate Kafka, while granular routing exchanges favor RabbitMQ.
