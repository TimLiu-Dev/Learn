Distributed Rate Limiting: Token Bucket with Redis & Bucket4j

Target: Protect your APIs from credential stuffing, scraping, and runaway mobile retry loops. Implement the Token Bucket algorithm using Bucket4j and Redis, inspect ConsumptionProbe remaining tokens, and emit RFC-compliant HTTP 429 Too Many Requests with exact Retry-After headers.

📖 Primary Source Recommendation

Study the official authority: Bucket4j: Distributed Token-Bucket Rate Limiting Reference.

1. Why Rate Limiting Is Essential for Mobile Backends

A single mobile app release with a buggy retry loop—or an automated credential-stuffing botnet—can fire 50,000 requests per minute at your login or checkout endpoints. Without distributed rate limiting shared in Redis across all Kubernetes pods, HikariCP starves and every legitimate user suffers timeouts.

2. The Token Bucket Algorithm & ConsumptionProbe

Bucket Concept: - Capacity: 50 tokens max (allows short mobile bursts) - Refill Rate: 50 tokens replenished greedily over 60 seconds - Request Check: ConsumptionProbe probe = bucket.tryConsumeAndReturnRemaining(1); ├─ probe.isConsumed() == true ──► 200 OK (X-Rate-Limit-Remaining: probe.getRemainingTokens()) └─ probe.isConsumed() == false ──► 429 Too Many Requests (Retry-After: nanosToWait / 1_000_000_000)

Single-Node vs. Multi-Pod Production: In local tests, a ConcurrentHashMap<String, Bucket> demonstrates token mechanics; in multi-pod production, back Bucket4j with LettuceBasedProxyManager on Redis so a client hitting 5 pods shares one atomic Redis bucket!

3. Production Dual Rate Limiter with Bucket4j & Retry-After

Bucket4j Bandwidth + ConsumptionProbe + Retry-After Calculation 
package com.example.ecommerce.ratelimit;

import io.github.bucket4j.*;
import org.springframework.stereotype.Service;
import java.time.Duration;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.TimeUnit;

@Service
public class RateLimiterService {

    public record RateDecision(boolean allowed, long remainingTokens, long retryAfterSeconds) {}

    // In multi-pod production, swap ConcurrentHashMap for Bucket4j LettuceBasedProxyManager (Redis)!
    private final Map<String, Bucket> buckets = new ConcurrentHashMap<>();

    public RateDecision evaluate(String clientKey) {
        Bucket bucket = buckets.computeIfAbsent(clientKey, this::createBucket);
        ConsumptionProbe probe = bucket.tryConsumeAndReturnRemaining(1);
        if (probe.isConsumed()) {
            return new RateDecision(true, probe.getRemainingTokens(), 0L);
        }
        long waitSeconds = Math.max(1L, TimeUnit.NANOSECONDS.toSeconds(probe.getNanosToWaitForRefill()));
        return new RateDecision(false, 0L, waitSeconds);
    }

    private Bucket createBucket(String key) {
        Bandwidth limit = Bandwidth.builder()
            .capacity(50)
            .refillGreedy(50, Duration.ofMinutes(1))
            .build();
        return Bucket.builder().addLimit(limit).build();
    }
}

Java 25 Implementation:
package com.example.ratelimit;

import io.github.bucket4j.*;
import java.time.Duration;
import java.util.concurrent.TimeUnit;

public class ApiRateLimiter {
    public static Bucket buildBucket(long capacity) {
        Bandwidth limit = Bandwidth.builder()
            .capacity(capacity)
            .refillGreedy(capacity, Duration.ofMinutes(1))
            .build();
        return Bucket.builder().addLimit(limit).build();
    }

    public static long checkRetryAfterSeconds(Bucket bucket) {
        ConsumptionProbe probe = bucket.tryConsumeAndReturnRemaining(1);
        if (probe.isConsumed()) {
            return 0L;
        }
        return TimeUnit.NANOSECONDS.toSeconds(probe.getNanosToWaitForRefill());
    }
}
Kotlin 2.2+ Implementation:
package com.example.ratelimit

import io.github.bucket4j.*
import java.time.Duration
import java.util.concurrent.TimeUnit

object ApiRateLimiter {
    fun buildBucket(capacity: Long): Bucket {
        val limit = Bandwidth.builder()
            .capacity(capacity)
            .refillGreedy(capacity, Duration.ofMinutes(1))
            .build()
        return Bucket.builder().addLimit(limit).build()
    }

    fun checkRetryAfterSeconds(bucket: Bucket): Long {
        val probe = bucket.tryConsumeAndReturnRemaining(1)
        return if (probe.isConsumed) {
            0L
        } else {
            TimeUnit.NANOSECONDS.toSeconds(probe.nanosToWaitForRefill)
        }
    }
}
Architectural Breakdown:

Using tryConsumeAndReturnRemaining(1) instead of a bare boolean check gives you both remaining token quota headers and exact nanosecond refill wait times for Retry-After.
