Zero-Downtime Releases: Expand-and-Contract Migrations & Canary Rollouts

Target: Even with Kubernetes rolling updates and graceful shutdown, a single Flyway migration like ALTER TABLE orders RENAME COLUMN total TO amount_cents will crash your old v1 pods mid-rollout while v1 and v2 share the same database! True zero-downtime deployment requires N-1 backward compatibility. In this lesson, we master the Expand-and-Contract database migration pattern, decouple deployment from release with Feature Flags, and compare Canary vs. Blue-Green traffic shifting.

📖 Primary Source Recommendation

Study the official authorities: Martin Fowler: Parallel Change (Expand & Contract) and Flyway Documentation: Zero-Downtime Migrations.

💡 Why This Matters in Production

Just as a backend API must support old Android app versions that users haven't updated yet, a shared PostgreSQL schema during a rolling or canary deploy must simultaneously satisfy both v1 and v2 backend pods. Breaking schema changes cannot happen in one release.

Key Architectural Takeaways

  • The Expand-and-Contract (Parallel Change) 3-Deploy Rule:
    1. Expand: Add the new nullable column (ADD COLUMN amount_cents BIGINT); deploy app v2 writing to both old and new columns (reading old or coalescing).
    2. Backfill & Switch: Batch-backfill historical rows safely without locking the table; deploy v3 reading solely from amount_cents.
    3. Contract: Only after 100% of v1/v2 pods are gone, drop the legacy column and enforce NOT NULL (using NOT VALID + VALIDATE CONSTRAINT in PostgreSQL to avoid table-wide write locks).
  • Canary vs. Blue-Green Deployments: Blue-Green swaps 100% traffic instantly (fast rollback, 2× compute cost); Canary shifts 5% → 25% → 100% traffic while automated SLO checks abort on error-rate spikes.
  • Deploy ≠ Release (Feature Flags): Ship dark code behind a runtime flag so turning off a broken feature takes 1 second without rolling back containers or Flyway schemas.

-- V12__expand_add_amount_cents.sql (Safe: nullable, metadata-only instant in Postgres)
ALTER TABLE orders ADD COLUMN amount_cents BIGINT;

-- Later in Contract phase (avoids AccessExclusiveLock scan on million-row table):
-- ALTER TABLE orders ADD CONSTRAINT chk_amount_not_null CHECK (amount_cents IS NOT NULL) NOT VALID;
-- ALTER TABLE orders VALIDATE CONSTRAINT chk_amount_not_null;

---
// OrderEntity.java — Expand Phase: Dual-write to old & new columns so v1 and v2 coexist
@Entity
@Table(name = "orders")
public class OrderEntity {
    @Id
    private UUID id;

    @Column(name = "total")
    private BigDecimal legacyTotal;   // Still read by running v1 pods

    @Column(name = "amount_cents")
    private Long amountCents;         // Read by v2+ pods

    public void setOrderAmount(long cents) {
        this.amountCents = cents;
        this.legacyTotal = BigDecimal.valueOf(cents, 2); // Dual-write keeps v1 safe!
    }

    public long effectiveAmountCents() {
        return amountCents != null ? amountCents : legacyTotal.movePointRight(2).longValueExact();
    }
}
-- V12__expand_add_amount_cents.sql
ALTER TABLE orders ADD COLUMN amount_cents BIGINT;

// OrderEntity.kt — Expand Phase: Dual-write to old & new columns
@Entity
@Table(name = "orders")
class OrderEntity(
    @Id
    val id: UUID,
    @Column(name = "total")
    var legacyTotal: BigDecimal,
    @Column(name = "amount_cents")
    var amountCents: Long? = null
) {
    fun setOrderAmount(cents: Long) {
        this.amountCents = cents
        this.legacyTotal = BigDecimal.valueOf(cents, 2)
    }

    fun effectiveAmountCents(): Long =
        amountCents ?: legacyTotal.movePointRight(2).longValueExact()
}

// ALTER TABLE orders ADD COLUMN amount_cents BIGINT;
public class OrderMigrationHelper {
    private BigDecimal legacyTotal;
    private Long amountCents;

    public void updateAmount(long cents) {
        this.amountCents = cents;
        this.legacyTotal = BigDecimal.valueOf(cents, 2);
    }

    public long readAmountCents() {
        return amountCents != null ? amountCents : legacyTotal.movePointRight(2).longValueExact();
    }
}
Kotlin 2.x Implementation:
// ALTER TABLE orders ADD COLUMN amount_cents BIGINT;
class OrderMigrationHelper(
    var legacyTotal: BigDecimal,
    var amountCents: Long? = null
) {
    fun updateAmount(cents: Long) {
        this.amountCents = cents
        this.legacyTotal = BigDecimal.valueOf(cents, 2)
    }

    fun readAmountCents(): Long =
        amountCents ?: legacyTotal.movePointRight(2).longValueExact()
}
Architectural Breakdown:

Dual-writing keeps v1 readers intact while v2+ pods populate the new column and tolerate un-backfilled rows cleanly until the Contract release.
