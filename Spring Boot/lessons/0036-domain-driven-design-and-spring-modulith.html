Domain-Driven Design & Modular Monoliths with Spring Modulith

Target: Over the past decade, countless engineering organizations prematurely split simple backends into dozens of microservices, creating crushing operational overhead: distributed transactions, network latency, broken CI/CD pipelines, and duplicated data models. The industry has rediscovered that a well-structured Modular Monolith delivers the architectural clarity and domain boundaries of microservices with the deployment simplicity, zero-network latency, and ACID consistency of a single binary. Spring Modulith (first-class Spring ecosystem project in Spring Boot 3) enforces strict Domain-Driven Design (DDD) module boundaries at compile and test time using ArchUnit, and provides built-in transactional event publication outboxes.

📖 Primary Source Recommendation

Study the official authority: Spring Modulith Official Reference Documentation by Oliver Drotbohm & Domain-Driven Design: Tackling Complexity in the Heart of Software by Eric Evans.. Ground your learning in primary architecture rather than secondary summaries.

💡 Why This Matters in Production

Without architectural guardrails, monoliths inevitably rot into 'Big Balls of Mud' where circular dependencies between packages prevent refactoring, testing, and independent scaling. Spring Modulith prevents this rot automatically: if package 'order' attempts to import an internal private class from package 'inventory', your build fails immediately in unit tests.

Key Architectural Takeaways

  • A Modular Monolith organizes code by business domain modules (e.g. 'order', 'payment', 'inventory') rather than technical layers ('controllers', 'services', 'repositories').
  • In Spring Modulith, top-level subpackages under the application root represent distinct modules. Internal classes are kept package-private (Java) or 'internal' (Kotlin); only explicitly exposed API classes and records are public.
  • Architectural verification: A single test calling 'ApplicationModules.of(Application.class).verify()' detects circular module dependencies and illegal package access using ArchUnit.
  • Module decoupling via Events: Instead of directly autowiring foreign service beans, modules publish domain events ('ApplicationEventPublisher').
  • Transactional Event Publication: Spring Modulith includes a transactional event publication log (built-in Outbox table) that guarantees events are published reliably even if downstream listeners fail.
  • Generates Living Documentation: Spring Modulith automatically produces UML component diagrams, C4 architecture diagrams, and application module Canvas docs.

1. Package Structure and Encapsulation

Consider an application root com.example.app. Spring Modulith treats each direct subpackage as an architectural module: 

com.example.app
├── order               <-- Order Module Boundary
│   ├── OrderPlacedEvent.java   (public - Exposed API)
│   ├── OrderService.java       (public - Exposed API)
│   └── internal                <-- Hidden Module Internals
│       ├── OrderEntity.java    (package-private)
│       └── OrderRepository.java(package-private)
├── inventory           <-- Inventory Module Boundary
│   ├── InventoryListener.java  (listens to OrderPlacedEvent)
│   └── internal
│       └── StockEntity.java
└── Application.java

If a developer in inventory writes import com.example.app.order.internal.OrderRepository;, Java allows it if public, but Spring Modulith's architectural test fails immediately with an IllegalModuleDependencyException.

2. Architectural Verification in CI

You enforce architecture with a single JUnit 5 test: 

@Test
void verifyModularArchitecture() {
    ApplicationModules modules = ApplicationModules.of(Application.class);
    modules.verify(); // Fails on cyclic dependencies or illegal package imports!
}

3. Transactional Event Publication (The Monolith Outbox)

When an order is created, the order module should not directly call InventoryService.deductStock()—that creates tight coupling and risks partial failures. Instead, it emits an event: 

eventPublisher.publishEvent(new OrderPlacedEvent(orderId, items));

The inventory module listens asynchronously: 

@ApplicationModuleListener
public void on(OrderPlacedEvent event) {
    inventoryService.reserve(event.items());
}

@ApplicationModuleListener combines @Async, @Transactional(propagation = REQUIRES_NEW), and Spring Modulith's event publication registry. If the inventory pod crashes mid-execution, the uncompleted event remains in the DB publication log and is replayed automatically upon reboot!

Domain-Driven Design & Modular Monoliths with Spring Modulith 
package com.example.modulith;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.ApplicationEventPublisher;
import org.springframework.modulith.ApplicationModule;
import org.springframework.modulith.ApplicationModuleListener;
import org.springframework.modulith.core.ApplicationModules;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.util.UUID;

// 1. Root Application
@SpringBootApplication
public class ModulithApplication {
    public static void main(String[] args) {
        SpringApplication.run(ModulithApplication.class, args);
    }
}

// 2. Order Module: Public Domain Event (Contract)
record OrderPlacedEvent(UUID orderId, String customerId, long totalAmountCents) {}

// Order Module Service
@Service
class OrderPlacementService {
    private final ApplicationEventPublisher eventPublisher;

    public OrderPlacementService(ApplicationEventPublisher eventPublisher) {
        this.eventPublisher = eventPublisher;
    }

    @Transactional
    public void createOrder(String customerId, long amountCents) {
        UUID orderId = UUID.randomUUID();
        // Persist order in DB...
        
        // Decoupled communication: publish domain event into Modulith outbox
        eventPublisher.publishEvent(new OrderPlacedEvent(orderId, customerId, amountCents));
    }
}

// 3. Billing Module: Event Listener
@Service
class BillingModuleListener {

    // @ApplicationModuleListener wraps @Async + @Transactional(REQUIRES_NEW)
    // + Spring Modulith persistent event publication registry
    @ApplicationModuleListener
    public void on(OrderPlacedEvent event) {
        // Charges the customer credit card
        // If this throws an exception, Modulith marks the event as pending in DB
        // and retries according to configured backoff policy!
        System.out.println("Processing billing for order: " + event.orderId());
    }
}

package com.example.modulith;

import org.junit.jupiter.api.Test;
import org.springframework.modulith.core.ApplicationModules;

class ArchitectureTest {

    @Test
    void verifyModularBoundaries() {
        ApplicationModules modules = ApplicationModules.of(ModulithApplication.class);
        modules.verify();
        modules.forEach(System.out::println);
    }
}
