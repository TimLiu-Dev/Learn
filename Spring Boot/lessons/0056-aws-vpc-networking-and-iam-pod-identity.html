AWS VPC Networking & Zero-Trust IAM (EKS Pod Identity / IRSA)

Target: Two real-world failures stall backend teams moving to AWS: 1) *"My Spring Boot pod times out connecting to RDS PostgreSQL!"* (almost always a VPC subnet route or Security Group rule), and 2) hardcoded long-lived AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY credentials leaked in Secrets or CI logs. In this lesson, we build the developer mental model for AWS VPC public vs. private subnets, NAT Gateways, and Security Group chaining, and eliminate static AWS keys with least-privilege IAM Roles via EKS Pod Identity / IRSA.

📖 Primary Source Recommendation

Study the official authorities: AWS EKS Pod Identity Documentation and Amazon VPC Subnets, NAT & Security Groups Guide.

💡 Why This Matters in Production

Think of VPC Security Groups like stateful firewall allow-lists referenced by group ID rather than brittle IP addresses: your RDS PostgreSQL Security Group only accepts TCP 5432 from the order-service Security Group, never 0.0.0.0/0. Meanwhile, AWS SDK v2's DefaultCredentialsProvider automatically obtains short-lived STS tokens injected by EKS Pod Identity—zero static keys anywhere.

Key Architectural Takeaways

  • Public vs. Private Subnets: Only the Application Load Balancer (ALB) sits in public subnets (with an Internet Gateway route). Your Spring Boot pods and RDS PostgreSQL instances live in private subnets with zero public IPs.
  • NAT Gateway & VPC Endpoints: Pods in private subnets reach external APIs outbound through a NAT Gateway—or hit S3/Secrets Manager privately at zero NAT bandwidth cost using VPC Gateway/Interface Endpoints.
  • Security Group Chaining (Not CIDR IPs): Reference the App Security Group ID inside the RDS Security Group inbound rule on port 5432. Pods scale freely across new IPs without firewall edits.
  • Zero Static AWS Keys: Bind an IAM Role directly to a Kubernetes ServiceAccount via EKS Pod Identity (or IRSA), scoped strictly to exact S3 prefixes / SQS queues (never "Action": "*" or "Resource": "*").

Production Implementation (Least-Privilege IAM Policy & AWS SDK v2 Credential Chain)

Least-Privilege IAM Policy + Zero-Key Spring Cloud AWS / SDK v2 
// Least-Privilege IAM Policy for order-service (EKS Pod Identity Role)
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:PutObject", "s3:GetObject"],
      "Resource": "arn:aws:s3:::nexus-invoices-prod/orders/*"
    },
    {
      "Effect": "Allow",
      "Action": ["sqs:SendMessage"],
      "Resource": "arn:aws:sqs:us-east-1:123456789012:nexus-orders-queue"
    }
  ]
}

---
// AwsClientConfig.java — Use DefaultCredentialsProvider (Pod Identity / IRSA automatic!)
@Configuration
public class AwsClientConfig {
    @Bean
    S3Client s3Client() {
        return S3Client.builder()
            .region(Region.US_EAST_1)
            .credentialsProvider(DefaultCredentialsProvider.create())
            .build();
    }
}

💡 Complete Production Reference Solution
Java 21/25 Implementation:
// IAM Policy: {"Action": ["s3:PutObject"], "Resource": "arn:aws:s3:::nexus-uploads-prod/invoices/*"}
@Configuration
public class SecureAwsConfig {
    @Bean
    S3Client s3Client() {
        return S3Client.builder()
            .region(Region.US_EAST_1)
            .credentialsProvider(DefaultCredentialsProvider.create())
            .build();
    }
}
