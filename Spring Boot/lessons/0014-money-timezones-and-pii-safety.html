Production Correctness: Money (BigDecimal & Minor Units), UTC Time (Instant) & PII Log Masking

Target: Some of the most expensive bugs in production Java/Kotlin backends are silent data-corruption defects that pass unit tests: losing pennies with double, failing equality checks on BigDecimal("10.0").equals(new BigDecimal("10.00")), storing LocalDateTime without a timezone (breaking during Daylight Saving Time), and leaking raw customer emails, tokens, or card numbers into JSON logs!

📖 Primary Source Recommendation

Study the official authorities: Java 21 Javadoc: BigDecimal (Scale vs. compareTo) and Java 21 Javadoc: java.time.Instant (UTC Epoch Timeline).

💡 Android Mental Model Bridge

On Android, you format prices and dates for one user's device locale and timezone. On a global backend serving Tokyo, Berlin, and New York simultaneously, the server must store integer minor units (long amountCents) or BigDecimal + ISO-4217 currency code, store timestamps strictly as UTC Instant (TIMESTAMPTZ in PostgreSQL), and let the mobile client convert to local display time!

1. The Three Iron Laws of Backend Data Correctness

  • Money: Ban double/float & Beware BigDecimal.equals(): Binary floating-point cannot represent 0.1 exactly (0.1 + 0.2 == 0.30000000000000004). Store integer minor units (long cents + Currency) or BigDecimal with explicit RoundingMode.HALF_EVEN (Banker's Rounding). Crucially, BigDecimal.equals() checks scale as well as value (10.0 != 10.00), so always compare monetary amounts with a.compareTo(b) == 0!
  • Time: Store Instant (UTC) + TIMESTAMPTZ, Never LocalDateTime: LocalDateTime has zero timezone offset—if a server's OS timezone changes or Daylight Saving Time springs forward, 2:30 AM vanishes or duplicates! Store java.time.Instant in Java/Kotlin, serialize as ISO-8601 UTC (2027-03-14T08:30:00Z), and save in PostgreSQL TIMESTAMPTZ. (Save ZoneId separately only for recurring human calendar rules like "every Monday at 9 AM Berlin time".)
  • PII & Secret Hygiene in Logs: Never dump raw request DTOs containing passwords, JWTs, SSNs, or emails into log.info(...). Override toString() on sensitive records/classes or apply a Logback masking converter so logs stay GDPR/PCI-compliant.

1. Financial Representation Matrix: Why double & BigDecimal.equals() Break Ledgers

Representation PostgreSQL Column Precision & Pitfalls
double / float DOUBLE PRECISION FORBIDDEN: IEEE-754 binary fractions drift (0.1 + 0.2 = 0.30000000000000004)
long amountMinor + Currency BIGINT + CHAR(3) Fast exact integer math (watch 0-decimal JPY vs. 2-decimal USD vs. 3-decimal KWD!)
BigDecimal + Currency NUMERIC(19, 4) Exact decimal math with RoundingMode.HALF_EVEN; always compare via compareTo() == 0!

2. Global Temporal Flow: UTC Instant on the Server, ZoneId at the Edge

[ Tokyo Android App (JST +09:00) ] ──("2027-03-14T08:30:00Z")──► [ Spring Boot: java.time.Instant ] ──► [ Postgres TIMESTAMPTZ ] │ [ New York Web App (EDT -04:00) ] ◄─("2027-03-14T08:30:00Z")─────────────┘ (Client formats locally; zero DST ambiguity!)

Only store an explicit IANA ZoneId string (e.g., "America/New_York") alongside a LocalTime when modeling future human calendar rules (such as "send digest at 09:00 local time"), because governments occasionally change Daylight Saving Time laws between when a schedule is created and when it fires!

Safe Money Value Object, UTC Instant Audit & Masked PII toString() 
package com.nexus.correctness;

import java.math.BigDecimal;
import java.math.RoundingMode;
import java.time.Instant;
import java.util.Currency;
import java.util.Objects;

public record Money(BigDecimal amount, Currency currency) {
    public Money {
        Objects.requireNonNull(amount);
        Objects.requireNonNull(currency);
        amount = amount.setScale(currency.getDefaultFractionDigits(), RoundingMode.HALF_EVEN);
    }

    public boolean sameValueAs(Money other) {
        // NEVER use BigDecimal.equals() — 10.0 vs 10.00 returns false!
        return currency.equals(other.currency) && amount.compareTo(other.amount) == 0;
    }
}

public record CustomerReceipt(String orderId, Money total, Instant createdAtUtc, String email) {
    @Override
    public String toString() {
        String masked = (email == null || !email.contains("@")) ? "***"
            : email.charAt(0) + "***@" + email.substring(email.indexOf('@') + 1);
        return "CustomerReceipt[orderId=" + orderId + ", total=" + total + ", at=" + createdAtUtc + ", email=" + masked + "]";
    }
}
package com.nexus.correctness

import java.math.BigDecimal
import java.math.RoundingMode
import java.time.Instant
import java.util.Currency

data class Money(val rawAmount: BigDecimal, val currency: Currency) {
    val amount: BigDecimal = rawAmount.setScale(currency.defaultFractionDigits, RoundingMode.HALF_EVEN)

    fun sameValueAs(other: Money): Boolean =
        currency == other.currency && amount.compareTo(other.amount) == 0
}

data class CustomerReceipt(
    val orderId: String,
    val total: Money,
    val createdAtUtc: Instant,
    val email: String
) {
    override fun toString(): String {
        val masked = if ('@' !in email) "***" else "${email.first()}***@${email.substringAfter('@')}"
        return "CustomerReceipt(orderId=$orderId, total=$total, at=$createdAtUtc, email=$masked)"
    }
}

💡 Complete Production Reference Solution
Java 25 Implementation:
package com.nexus.correctness;

import java.math.BigDecimal;
import java.math.RoundingMode;
import java.time.Instant;

public class PaymentMath {
    public static boolean amountsMatch(BigDecimal a, BigDecimal b) {
        return a.compareTo(b) == 0;
    }

    public static BigDecimal roundUsd(BigDecimal raw) {
        return raw.setScale(2, RoundingMode.HALF_EVEN);
    }

    public static Instant nowUtc() {
        return Instant.now();
    }
}
Kotlin 2.x Implementation:
