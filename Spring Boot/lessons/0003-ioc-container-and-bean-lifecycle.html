Lesson 0003 • Phase 1

IoC Container, Bean Lifecycle & Constructor Injection

Target: Understand how Spring builds runtime object dependency trees, why field injection is strictly prohibited in senior codebases, and how Spring IoC mirrors Android Hilt.

📖 Primary Source Recommendation

Study the official authority: Spring Framework Reference: The IoC Container. Ground your learning in primary architecture rather than secondary summaries.

1. What Actually Happens in the IoC Container

In raw Java, you manually assemble objects: new OrderService(new OrderRepository()). Inversion of Control (IoC) flips this responsibility to the Spring ApplicationContext.

🤖 Android Mental Model: Hilt vs. Spring IoC

If you know Hilt (@Inject constructor(...) and @Singleton), Spring does the exact same thing! But while Hilt generates code at compile time with annotation processors, Spring builds its dependency graph dynamically at startup.

2. Why Senior Engineers Ban Field Injection

  • @Autowired private OrderRepo repo; prevents fields from being declared final (breaking immutability).
  • It makes pure unit testing impossible without starting heavy reflection or the entire Spring context.
  • It hides code smells: a class with 10 injected fields is violating Single Responsibility, but field injection disguises the problem.

3. The Modern Standard: Constructor Injection

Since Spring 4.3+, single constructors do not require @Autowired at all.

Immutable Service with Constructor Injection 
package com.example.ecommerce.order;

import org.springframework.stereotype.Service;
import java.util.Objects;

@Service
public class OrderService {
    private final OrderRepository orderRepository;
    private final PaymentClient paymentClient;

    public OrderService(OrderRepository orderRepository, PaymentClient paymentClient) {
        this.orderRepository = Objects.requireNonNull(orderRepository, "orderRepository must not be null");
        this.paymentClient = Objects.requireNonNull(paymentClient, "paymentClient must not be null");
    }
}
package com.example.ecommerce.order

import org.springframework.stereotype.Service

@Service
class OrderService(
    private val orderRepository: OrderRepository,
    private val paymentClient: PaymentClient
)

Add @Service above the class declaration.
Hint 2: Syntax Signature
In Java, use 'private final EmailClient emailClient;'. In Kotlin, use a primary constructor with 'val'.
Hint 3: Concrete Snippet
public NotificationService(EmailClient emailClient, SmsClient smsClient) { this.emailClient = emailClient; this.smsClient = smsClient; }
💡 Complete Production Reference Solution
Java 21 Implementation:
package com.example.service;

import org.springframework.stereotype.Service;

@Service
public class NotificationService {
    private final EmailClient emailClient;
    private final SmsClient smsClient;

    public NotificationService(EmailClient emailClient, SmsClient smsClient) {
        this.emailClient = emailClient;
        this.smsClient = smsClient;
    }
}
Kotlin 2.x Implementation:
package com.example.service

import org.springframework.stereotype.Service

@Service
class NotificationService(
    private val emailClient: EmailClient,
    private val smsClient: SmsClient
)
Architectural Breakdown:

Notice how Kotlin eliminates all constructor assignment boilerplate into a single primary constructor with `val` properties, while Java 21 enforces immutability via `private final`.
