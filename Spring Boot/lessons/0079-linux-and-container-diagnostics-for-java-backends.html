Linux & Container Shell Essentials for Java Spring Boot Engineers

Target: Every production Spring Boot service runs inside a Linux environment (containers, CI runners, EC2/EKS nodes). You do not need to be a Linux kernel sysadmin, but you must be fluent in the Linux diagnostics that solve real Java incidents: POSIX signals (SIGTERM exit 143 vs SIGKILL 137), file descriptors (ulimit -n / "Too many open files"), socket & port debugging (ss -tulpn, lsof -i), non-root UID/permissions (chmod, chown), and triaging ECS JSON logs with jq & rg.

📖 Primary Source Recommendation

Study the official authorities: Brendan Gregg: Linux Performance Observability Tools and jq Official Manual (JSON Log Triage).

💡 Android Mental Model Bridge

You already use adb shell and logcat to inspect Android processes and permissions. Production backend debugging is the same concept on a Linux host/container: instead of logcat, you slice structured JSON stdout with jq and rg; instead of Android app sandbox UIDs, you verify non-root container UIDs, open TCP sockets (ss), and POSIX shutdown signals (SIGTERM).

1. The 5 Linux Survival Skills Every Java Backend Engineer Needs

  • PID 1 & Exit Codes (143 vs 137): Always use Docker exec-form (ENTRYPOINT ["java", "-jar", "app.jar"]), never shell-form (java -jar ... wrapped in /bin/sh -c), so Java runs as PID 1 and receives SIGTERM directly! Clean shutdown exits with 128 + 15 = 143 (or 0); Linux OOM Killer or timeout SIGKILL exits with 128 + 9 = 137.
  • File Descriptors (ulimit -n): On Linux, every TCP socket, open JAR, log file, and DB connection is a file descriptor. If a container defaults to 1024 FDs, 900 concurrent clients crash Tomcat with java.io.IOException: Too many open files. Check limits via ulimit -n and inspect active process FDs via ls /proc/<pid>/fd | wc -l.
  • Port, Socket & Process Triage: Quickly answer "who owns port 8080?" or "how many connections are stuck in CLOSE_WAIT/TIME_WAIT?" with ss -tulnp, lsof -i :8080, and ps -ef | grep java.
  • Filesystem Permissions & Non-Root Containers: When mounting volumes (logs, TLS certs, `/tmp` heap dumps) into a non-root container (`USER 1001`), mismatched ownership causes silent startup crashes (`AccessDeniedException`). Fix in Dockerfiles with chown -R 1001:1001 /app and restrict private keys with chmod 600.
  • Piping & JSON Log Triage (jq + rg): Pipe container logs through jq to isolate slow or failing requests in seconds: kubectl logs pod-1 | jq 'select(.log_level == "ERROR" and .trace_id != null)'.

2. Production Implementation: Safe Exec-Form Container + Linux Diagnostics

Exec-Form PID 1 Signal Safety & Everyday Linux Triage Commands 
# 1. Dockerfile PID 1 Signal Hygiene (Java 21/25)
FROM eclipse-temurin:21-jre-alpine
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
WORKDIR /app
COPY --chown=appuser:appgroup target/order-service.jar app.jar
USER appuser
# MUST use JSON exec-form so Java is PID 1 and receives SIGTERM (graceful shutdown)!
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75.0", "-jar", "/app/app.jar"]

# 2. Essential Linux Triage One-Liners:
# ss -tulnp | grep 8080                # Check which PID is bound to port 8080
# ss -tan state time-wait | wc -l      # Count sockets stuck in TIME_WAIT
# ulimit -n                            # Inspect max open file descriptors (sockets + files)
# docker logs api | jq -c 'select(.level=="ERROR") | {ts:.["@timestamp"], msg:.message, trace:.traceId}'
# 1. Dockerfile PID 1 Signal Hygiene (Kotlin 2.x Spring Boot)
FROM eclipse-temurin:21-jre-alpine
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
WORKDIR /app
COPY --chown=appuser:appgroup build/libs/order-service.jar app.jar
USER appuser
# Exec-form ensures PID 1 forwards SIGTERM directly to the JVM
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75.0", "-jar", "/app/app.jar"]

# 2. Essential Linux Triage One-Liners:
# lsof -i :8080                        # Identify process holding port 8080
# cat /sys/fs/cgroup/memory.current    # Check live container cgroup v2 memory usage
# docker logs worker | jq -c 'select(.level=="ERROR") | {msg:.message, trace:.traceId}'
