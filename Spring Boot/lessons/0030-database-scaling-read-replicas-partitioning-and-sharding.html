Database Scaling: Read Replicas, Partitioning, Sharding & CAP/PACELC

Target: A single PostgreSQL 17 primary scales surprisingly far once you apply B-Tree indexes, keyset pagination, and @Transactional discipline from Stage 1. When traffic outgrows one box, senior backend engineers climb the scaling ladder in strict order: Read-Replica Routing (AbstractRoutingDataSource), PostgreSQL declarative partitioning, and finally horizontal sharding or purpose-built NoSQL stores guided by CAP & PACELC.

📖 Primary Source Recommendation

Study the official authorities: PostgreSQL Table Partitioning Reference and Designing Data-Intensive Applications (Martin Kleppmann).

💡 Why This Matters in Production

Sharding prematurely turns simple SQL joins and ACID transactions into a distributed nightmare. The senior scaling ladder is strictly ordered: 1) Query/Index optimization & Caching → 2) Read Replicas (@Transactional(readOnly = true)) → 3) Table Partitioning (single node) → 4) Functional splitting / Horizontal Sharding as a last resort.

Key Architectural Takeaways

  • Read-Replica Routing & Replication Lag: Extend Spring's AbstractRoutingDataSource wrapped inside LazyConnectionDataSourceProxy so @Transactional(readOnly = true) queries automatically route to async read replicas while writes hit the primary—watching out for 5–200ms Read-Your-Own-Writes lag!
  • CAP & PACELC in Plain English: Network partitions (P) are unavoidable in distributed systems, forcing a choice between Consistency (C: reject writes or risk stale reads—e.g., ledgers/inventory) and Availability (A: accept writes everywhere and reconcile—e.g., shopping carts). Even without partitions (E), you trade off Latency (L) vs. Consistency (C) on synchronous vs. async replication.
  • Partitioning vs. Sharding: Partitioning splits a giant table into smaller physical chunks (e.g., monthly orders_2026_11) on the same PostgreSQL server (instant drops for archiving, smaller B-Tree indexes). Sharding splits rows across independent database servers by a shard key (e.g., tenant_id or user_id).
  • Choosing a Shard Key: Pick high-cardinality keys present on every hot query (tenant_id, customer_id) via consistent hashing—never shard by monotonically increasing created_at (all today's writes hit one hot shard!).

1. Read-Replica Routing with AbstractRoutingDataSource & Replication Lag

Most e-commerce and SaaS workloads are 80–95% reads. By adding streaming WAL read replicas in AWS RDS / Cloud SQL, you can offload catalog searches and analytics from the primary writer. Two subtle bugs trip up mid-level engineers when wiring Spring's AbstractRoutingDataSource:

  • Wrap in LazyConnectionDataSourceProxy: By default, Spring opens a JDBC connection before entering the @Transactional interceptor—meaning isCurrentTransactionReadOnly() is still false when routing runs! Wrapping the routing datasource in LazyConnectionDataSourceProxy defers physical HikariCP checkout until the first SQL statement executes, after the readOnly flag is active.
  • Read-Your-Own-Writes Lag: Asynchronous WAL streaming typically lags 5–200ms behind the primary. If a mobile app calls POST /orders (routed to Primary) and 15ms later calls GET /orders/{id} (routed to Replica), the replica may return 404 Not Found! Either return the created DTO directly in the 201 Created response, cache recent writes in Redis, or route immediate post-write fetches to Primary.

2. Single-Node Partitioning vs. Multi-Server Horizontal Sharding

SINGLE-NODE PARTITIONING (1 Postgres Host — Keeps Local ACID & Instant Archive Drops) [ audit_events (Parent) ] ──┬──► [ audit_events_2026_11 ] (DROP TABLE = 5ms, zero VACUUM bloat!) └──► [ audit_events_2026_12 ] (Hot index fits in RAM!) MULTI-SERVER HORIZONTAL SHARDING (N Independent Hosts — Scales Write IOPS & Storage) [ App Router: hash(tenant_id) ] ──┬──► [ Shard 0: Postgres Primary A ] ├──► [ Shard 1: Postgres Primary B ] └──► [ Shard 2: Postgres Primary C ] (Cross-shard JOINs forbidden!)

3. Consistent Hashing & CAP / PACELC Storage Selection Matrix

Naive modulo routing (hash % N) remaps ~80%+ of all keys when scaling from 4 shards to 5. Production sharded routers (Citus, Vitess, DynamoDB, Cassandra) place virtual nodes on a Consistent Hash Ring so adding a shard moves only 1 / N of keys. When evaluating SQL vs. NoSQL engines, apply the PACELC matrix:

Storage Engine PACELC Profile Ideal Backend Workload
PostgreSQL 17 (Primary + Replicas) PC / EC (Primary) • PA / EL (Async Replica) Default choice: ACID financial ledgers, orders, inventory, relational joins + JSONB
DynamoDB / Cassandra PA / EL (Tunable Quorum) Massive predictable single-key write throughput (carts, session state, IoT ingest)
MongoDB PC / EC (Replica Set Primary) Polymorphic product catalogs with rapidly evolving nested attributes
TimescaleDB / ClickHouse Append-Optimized Columnar / Hypertables High-ingest time-series telemetry, billing usage events, analytical rollups

// 3. TenantShardRouter.java — Deterministic non-negative shard lookup
public final class TenantShardRouter {
    public int resolveShard(UUID tenantId, int totalShards) {
        // Unsigned modulo avoids negative index bug when hashCode() == Integer.MIN_VALUE!
        return Integer.remainderUnsigned(tenantId.hashCode(), totalShards);
    }
}

💡 Complete Production Reference Solution
Java 25 Implementation:
// CREATE TABLE ledger_entries (id UUID, created_at TIMESTAMPTZ, PRIMARY KEY (id, created_at)) PARTITION BY RANGE (created_at);
public class ScalingRouter extends AbstractRoutingDataSource {
    @Override
    protected Object determineCurrentLookupKey() {
        return TransactionSynchronizationManager.isCurrentTransactionReadOnly() ? "REPLICA" : "PRIMARY";
    }

    public int shardForTenant(UUID tenantId, int shardCount) {
        return Integer.remainderUnsigned(tenantId.hashCode(), shardCount);
    }
}
Kotlin 2.2+ Implementation:
// CREATE TABLE ledger_entries (id UUID, created_at TIMESTAMPTZ, PRIMARY KEY (id, created_at)) PARTITION BY RANGE (created_at);
class ScalingRouter : AbstractRoutingDataSource() {
    override fun determineCurrentLookupKey(): Any =
        if (TransactionSynchronizationManager.isCurrentTransactionReadOnly()) "REPLICA" else "PRIMARY"

    fun shardForTenant(tenantId: UUID, shardCount: Int): Int =
        Integer.remainderUnsigned(tenantId.hashCode(), shardCount)
}
Architectural Breakdown:

Read-replica routing offloads @Transactional(readOnly = true) traffic, range partitioning keeps hot B-Trees compact on one server, and Integer.remainderUnsigned prevents negative modulo shard bugs.
