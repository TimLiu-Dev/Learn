Redis Data Structures & Distributed Locks (Redlock vs Fencing Tokens)

Target: Understand why Java's synchronized keyword fails in the cloud. Master Redis atomic operations (SETNX), distributed locks with Redisson, and the critical Martin Kleppmann fencing token caveat.

📖 Primary Source Recommendation

Study the official authority: Martin Kleppmann: How to do distributed locking. Ground your learning in primary architecture rather than secondary summaries.

1. Why Java `synchronized` Fails in Cloud Microservices

On a single Android phone or single JVM, synchronized or ReentrantLock prevents race conditions.

In cloud backends, you run multiple container pods (e.g. 5 pods in AWS ECS or Kubernetes behind an Application Load Balancer):

Pod #1 (Instance A) ──► synchronized(lock) { executes checkout } Pod #2 (Instance B) ──► synchronized(lock) { ALSO executes checkout! RACE CONDITION! }

JVM locks only exist in the RAM of one single operating system process! Instance B has no idea Instance A is holding a lock.

2. Distributed Locks with Redisson

Because all 5 server instances connect to the same shared Redis cluster, we coordinate locks centrally using atomic SETNX operations via Redisson:

Distributed Lock with Redisson 
package com.example.ecommerce.inventory;

import org.redisson.api.RLock;
import org.redisson.api.RedissonClient;
import org.springframework.stereotype.Service;
import java.util.concurrent.TimeUnit;

@Service
public class FlashSaleService {

    private final RedissonClient redisson;

    public FlashSaleService(RedissonClient redisson) {
        this.redisson = redisson;
    }

    public void purchaseLimitedItem(String itemId, String userId) {
        RLock lock = redisson.getLock("lock:item:" + itemId);

        try {
            // Wait up to 2 seconds to acquire; hold lock for at most 5 seconds
            boolean acquired = lock.tryLock(2, 5, TimeUnit.SECONDS);
            if (!acquired) {
                throw new IllegalStateException("High traffic! Please retry.");
            }

            try {
                // CRITICAL SECTION: Execute sensitive inventory deduction
                System.out.println("Processing purchase for item: " + itemId);
            } finally {
                // Always unlock inside inner finally block!
                if (lock.isHeldByCurrentThread()) {
                    lock.unlock();
                }
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}

3. The Martin Kleppmann Critique: Why Fencing Tokens Matter

🧠 Senior Distributed Systems Insight: Lock Lease Expiration

What happens if Instance A acquires the lock for 5 seconds, but encounters a 6-second GC pause or network stall? The Redis lock expires while Instance A is frozen! Instance B acquires the lock. Instance A unfreezes and both write to the DB simultaneously! The Solution: In addition to distributed locks, use Fencing Tokens (monotonic version numbers) or database-level constraints (optimistic locking) to reject out-of-order writes at the storage layer!

💡 Complete Production Reference Solution
Java 21 Implementation:
package com.example.lock;

import org.redisson.api.RLock;

public class LockHelper {
    public static void safeUnlock(RLock lock) {
        if (lock != null && lock.isHeldByCurrentThread()) {
            lock.unlock();
        }
    }
}
Kotlin 2.x Implementation:
package com.example.lock

import org.redisson.api.RLock

object LockHelper {
    fun safeUnlock(lock: RLock?) {
        if (lock != null && lock.isHeldByCurrentThread) {
            lock.unlock()
        }
    }
}
Architectural Breakdown:

Guarding unlock with isHeldByCurrentThread prevents crashing with IllegalMonitorStateException if the lease timed out while processing.
