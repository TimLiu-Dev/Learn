Indexing Mechanics & Query Analysis with EXPLAIN ANALYZE

Target: Understand why queries slow down as tables grow to millions of rows. Master B-Tree indexes, the composite index leftmost prefix rule, and reading PostgreSQL execution plans.

📖 Primary Source Recommendation

Study the official authority: Use The Index, Luke! (Markus Winand). Ground your learning in primary architecture rather than secondary summaries.

1. What Is an Index Physically?

Without an index, finding one order in 5,000,000 rows requires scanning every single disk block: a Sequential Scan (Seq Scan). A B-Tree Index is a self-balancing sorted tree stored on disk that lets PostgreSQL locate rows in O(log N) disk reads (typically 3–4 reads among millions of rows!).

2. The Leftmost Prefix Rule for Composite Indexes

When you create an index across multiple columns:

CREATE INDEX idx_orders_tenant_status ON orders (tenant_id, status, created_at);
  • WHERE tenant_id = 'acme' AND status = 'PENDING': Uses the index!
  • WHERE tenant_id = 'acme': Uses the index!
  • WHERE status = 'PENDING': Fails to use index! (Because tenant_id was omitted, PostgreSQL falls back to a slow full Seq Scan!).

3. Executing and Reading `EXPLAIN (ANALYZE, BUFFERS)` in Java & Kotlin

Running EXPLAIN ANALYZE via JdbcTemplate 
package com.example.ecommerce.database;

import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.stereotype.Repository;
import java.util.List;

@Repository
public class QueryPlanAnalyzer {
    private final JdbcTemplate jdbcTemplate;

    public QueryPlanAnalyzer(JdbcTemplate jdbcTemplate) {
        this.jdbcTemplate = jdbcTemplate;
    }

    public List<String> explainOrderQuery(String customerEmail) {
        String sql = "EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE customer_email = ?";
        return jdbcTemplate.query(sql, (rs, rowNum) -> rs.getString(1), customerEmail);
    }
}
