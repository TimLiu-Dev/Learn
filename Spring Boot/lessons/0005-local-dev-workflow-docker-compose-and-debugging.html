Local Backend Dev Workflow: start.spring.io, spring-boot-docker-compose & Virtual Thread Debugging

Target: On Android, clicking Run ▶ in Android Studio boots an Emulator and installs your APK. On a backend team, your service cannot boot alone—it needs a real PostgreSQL 17 database, Redis 7 cache, or Kafka broker running locally. Learn the 2027 zero-friction backend inner loop: bootstrapping projects on start.spring.io (Spring Boot 4.2 + Java 25), auto-starting local containers via spring-boot-docker-compose, committing reproducible .http API tests in Git, and debugging Virtual Threads without freezing carrier pools.

1. Bootstrapping Cleanly on start.spring.io (2027 Greenfield Defaults)

When initializing a new backend service at start.spring.io (or IntelliJ IDEA's Spring Initializr wizard), senior engineers select a lean, production-aligned baseline:

  • Spring Boot 4.2.x + Java 25 LTS + Packaging Jar: Never select legacy War packaging for containerized microservices.
  • Essential Stage 1 Starters: Spring Web (spring-boot-starter-webmvc in Boot 4), Validation, Spring Data JPA, Flyway Migration, PostgreSQL Driver, Docker Compose Support, Spring Boot Actuator, and Testcontainers.
  • Skip Over-Eager Starters: Do not add Spring Security, Kafka, or OAuth2 on Day 1 until you are ready to configure them—adding Spring Security locks every endpoint behind a generated password immediately, and adding JPA without a database or compose.yaml fails startup until a DataSource exists.

2. Zero-Config Local Infrastructure with spring-boot-docker-compose

Historically, backend developers had to remember to run docker compose up -d in a terminal and copy-paste matching ports, usernames, and passwords into application-local.yml. Spring Boot's spring-boot-docker-compose module eliminates all of that friction:

Click Run ▶ in IntelliJ / ./gradlew bootRun │ ├─► 1. Spring Boot finds compose.yaml in project root ├─► 2. Runs docker compose up & waits for Postgres/Redis healthchecks ├─► 3. Inspects container env/ports and registers JdbcConnectionDetails + RedisConnectionDetails └─► 4. Flyway runs V1__init.sql and Tomcat starts on :8080 (Zero manual YAML URLs needed!)

Because the dependency is scoped as developmentOnly (Gradle) or <optional>true</optional> + runtime (Maven), Spring Boot automatically excludes it from your production fat JAR and skips it during JUnit Testcontainers runs!

3. Reproducible .http Files & Debugging Virtual Threads Safely

  • Git-Tracked .http Requests: Create a requests/orders.http file (supported natively by IntelliJ HTTP Client, VS Code REST Client, and CLI runners like JetBrains ijhttp). You can chain requests—capturing a 201 Created order ID or JWT token from one response into the next request automatically.
  • Virtual Thread Breakpoint Hygiene: In IntelliJ IDEA, standard breakpoints default to Suspend: All (which freezes every JVM thread, causing HikariCP heartbeats and Kafka consumers to time out while you inspect a variable) or Suspend: Thread. Always set breakpoints to Suspend: Thread—or even better, use Non-Suspending Tracepoints (Shift+Click gutter in IntelliJ) to log evaluated expressions without pausing concurrent traffic!

4. Production-Grade Local Setup (Java 25 Maven vs. Kotlin 2.2 Gradle)

# 1. compose.yaml — Auto-started & auto-wired by Spring Boot on local run!
services:
  postgres:
    image: postgres:17-alpine
    environment:
      POSTGRES_DB: nexus_orders
      POSTGRES_USER: nexus
      POSTGRES_PASSWORD: secret_dev_password
    ports:
      - "5432"   # Ephemeral host port avoids "port 5432 already in use" conflicts!

  redis:
    image: redis:7-alpine
    ports:
      - "6379"

---
<!-- 2. pom.xml — Scoped to runtime + optional so it never ships inside prod bootJar -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-docker-compose</artifactId>
    <scope>runtime</scope>
    <optional>true</optional>
</dependency>
