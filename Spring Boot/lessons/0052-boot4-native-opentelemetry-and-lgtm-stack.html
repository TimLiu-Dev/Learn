Spring Boot 4 Native OpenTelemetry & The Grafana LGTM Stack

Target: In Spring Boot 3.x, enabling full OpenTelemetry required juggling multiple Micrometer bridge dependencies and exporters. Spring Boot 4.0 unifies observability around a first-class official starter — spring-boot-starter-opentelemetry — and pairs seamlessly with Docker Compose's Grafana LGTM stack (Loki for logs, Grafana for dashboards, Tempo for traces, Mimir/Prometheus for metrics). In this lesson, we wire unified OTLP export, instrument critical business paths with @Observed, and design tail-based sampling.

📖 Primary Source Recommendation

Study the official authorities: Spring Boot Reference: Tracing & OpenTelemetry and OpenTelemetry Official Docs: Head vs. Tail-Based Sampling.

💡 Why This Matters in Production

Head-based sampling (e.g., sampling 5% at the API gateway) drops 95% of your errors and slow P99 requests before you even know they failed. Using an OpenTelemetry Collector with tail-based sampling keeps 100% of error and high-latency traces while sampling healthy 200 OK traffic down to 1–5%.

Key Architectural Takeaways

  • spring-boot-starter-opentelemetry (Boot 4.0): Replaces fragmented Micrometer-to-OTel bridge wiring with a single cohesive starter that exports traces, metrics, and logs over OTLP—even without pulling the full Actuator web layer.
  • Unified @Observed Annotation: Annotating a critical service method with @Observed(name = "nexus.ledger.post") automatically produces both a Micrometer Timer metric and an OpenTelemetry Span from one instrumentation point.
  • OTel Collector + Tail-Based Sampling: Services emit OTLP to an OpenTelemetry Collector sidecar/gateway; the Collector buffers each trace briefly and retains 100% of ERROR or >500ms traces while discarding routine noise.
  • Local LGTM Productivity: Pair Spring Boot Docker Compose support with grafana/otel-lgtm to test correlated logs (Loki), traces (Tempo), and metrics (Mimir) locally before deploying.

Production Implementation (Java 21/25 vs Kotlin 2.x)

Boot 4 OpenTelemetry Starter, @Observed & OTLP Configuration 
# pom.xml (Spring Boot 4.0)
# <dependency>
#   <groupId>org.springframework.boot</groupId>
#   <artifactId>spring-boot-starter-opentelemetry</artifactId>
# </dependency>

# application.yml — Push OTLP signals to local/cluster OTel Collector
management:
  otlp:
    tracing:
      endpoint: http://otel-collector:4318/v1/traces
    metrics:
      export:
        url: http://otel-collector:4318/v1/metrics
  tracing:
    sampling:
      probability: 1.0  # Emit 100% to OTel Collector so Collector performs tail-based sampling

---
// LedgerPostingService.java — Single @Observed produces BOTH metric Timer + OTel Span
package com.nexus.ledger;

import io.micrometer.observation.annotation.Observed;
import org.springframework.stereotype.Service;

@Service
public class LedgerPostingService {

    @Observed(name = "nexus.ledger.post", contextualName = "post-ledger-entry")
    public void postDoubleEntry(String accountId, long amountCents) {
        // Business logic automatically timed AND traced with correlated traceId
    }
}

    }

Architectural Breakdown:

Sending 100% of traces to an OTel Collector enables tail-based sampling at the edge so every error and slow P99 request reaches Grafana Tempo without flooding storage.
