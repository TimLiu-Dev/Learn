Spring Batch: Chunk Processing, JobRepository & Fault-Tolerant Retries

Target: Suppose your fintech or e-commerce system must reconcile 5,000,000 nightly settlement rows from a CSV/S3 file into PostgreSQL. Loading 5M rows into a List causes instant OutOfMemoryError, and if row #4,200,000 crashes, restarting from row #1 wastes hours or duplicates ledger entries! Spring Batch solves massive offline processing cleanly using chunk-oriented streaming (ItemReader → ItemProcessor → ItemWriter), persistent JobRepository checkpoints for restartability, and declarative fault-tolerant skip/retry policies.

📖 Primary Source Recommendation

Study the official authority: Spring Batch Reference: Chunk-Oriented Processing & Fault Tolerance.

💡 Why This Matters in Production

A @Scheduled method processing 5M records in one @Transactional block holds locks for 30 minutes and blows heap. Spring Batch's chunk model reads 1 record at a time, commits every chunk(500, txManager) cleanly, saves the exact offset inside BATCH_STEP_EXECUTION_CONTEXT, and resumes from record #4,200,001 after a pod crash!

Key Architectural Takeaways

  • Job → Step → Chunk Pipeline: A Job contains one or more Steps; each chunk step streams items through ItemReader → optional ItemProcessor → bulk ItemWriter, committing one database transaction per chunk size (e.g., 500 items).
  • Restartability via JobRepository: Spring Batch persists execution state & reader cursors in PostgreSQL metadata tables so re-launching a failed job resumes right where it stopped rather than reprocessing 4 million rows.
  • Fault-Tolerant Skip & Retry: Configure .faultTolerant().retryLimit(3).retry(TransientDataAccessException.class).skipLimit(50).skip(FlatFileParseException.class) so one malformed CSV line doesn't abort a 5M-row nightly settlement.
  • Spring Batch vs. Kafka Consumers: Use Kafka/SQS for continuous real-time event streams; use Spring Batch for bounded finite datasets (nightly bank settlements, monthly billing PDFs, S3 CSV imports).

Production Implementation (Java 21/25 vs Kotlin 2.x — Spring Batch 5+ StepBuilder)

Chunk-Oriented Fault-Tolerant Step & Job Configuration 
@Configuration
public class SettlementBatchConfig {

    @Bean
    public Step reconcileStep(JobRepository jobRepository,
                              PlatformTransactionManager txManager,
                              ItemReader<SettlementRow> reader,
                              ItemProcessor<SettlementRow, LedgerEntry> processor,
                              ItemWriter<LedgerEntry> writer) {
        return new StepBuilder("reconcileStep", jobRepository)
            .<SettlementRow, LedgerEntry>chunk(500, txManager)
            .reader(reader)
            .processor(processor)
            .writer(writer)
            .faultTolerant()
            .retryLimit(3)
            .retry(TransientDataAccessException.class)
            .skipLimit(50)
            .skip(FlatFileParseException.class)
            .build();
    }

    @Bean
    public Job settlementJob(JobRepository jobRepository, Step reconcileStep) {
        return new JobBuilder("settlementJob", jobRepository)
            .start(reconcileStep)
            .build();
    }
}
@Configuration
class SettlementBatchConfig {

    @Bean
    fun reconcileStep(
        jobRepository: JobRepository,
        txManager: PlatformTransactionManager,
        reader: ItemReader<SettlementRow>,
        processor: ItemProcessor<SettlementRow, LedgerEntry>,
        writer: ItemWriter<LedgerEntry>
    ): Step = StepBuilder("reconcileStep", jobRepository)
        .chunk<SettlementRow, LedgerEntry>(500, txManager)
        .reader(reader)
        .processor(processor)
        .writer(writer)

            .start(reconcileStep)
            .build()
}

Architectural Breakdown:

Bounded chunks protect heap & database locks, JobRepository enables safe restarts, and skip/retry separates transient DB blips from bad input records.
