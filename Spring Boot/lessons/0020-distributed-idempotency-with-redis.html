Mobile-Friendly Distributed Idempotency with Redis

Target: Solve the mobile elevator retry problem. Use unique Idempotency Keys (X-Idempotency-Key), atomic SETNX in Redis, and caching response envelopes to guarantee safe request deduplication.

📖 Primary Source Recommendation

Study the official authority: IETF Draft: The Idempotency-Key HTTP Header Field. Ground your learning in primary architecture rather than secondary summaries.

1. The Mobile Flaky Network Retry Trap

1. Android App sends: POST /api/v1/orders { amount: $100 } 2. Server processes transaction and charges customer card! 3. User enters an elevator; TCP connection drops before 200 OK arrives! 4. OkHttp sees timeout and RETRIES: POST /api/v1/orders { amount: $100 } 5. ❌ RESULT: Customer is charged $200!

2. The Architecture: Distributed Idempotency

The mobile client generates a UUID X-Idempotency-Key: e82f-41a9... before sending.

  • The server performs an atomic SETNX (Set if Not eXists) in Redis with a 24-hour TTL: SET key "IN_PROGRESS" NX EX 86400.
  • If SETNX returns true: First time seeing this request! Process order, save final response in Redis, and return 200 OK.
  • If SETNX returns false: This is a duplicate retry! Do not re-charge the card! Return the cached response from Redis immediately.

3. Production Dual Java & Kotlin Idempotency Filter

Redis Idempotency Service 
package com.example.ecommerce.idempotency;

import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Service;
import java.time.Duration;

@Service
public class IdempotencyService {

    private final StringRedisTemplate redis;

    public IdempotencyService(StringRedisTemplate redis) {
        this.redis = redis;
    }

    public boolean claimKey(String idempotencyKey) {
        // Atomic SETNX in Redis!
        Boolean success = redis.opsForValue().setIfAbsent(
            "idemp:" + idempotencyKey,
            "IN_PROGRESS",
            Duration.ofHours(24)
        );
        return Boolean.TRUE.equals(success);
    }
}

Architectural Breakdown:

Atomic setIfAbsent in Redis guarantees that only the very first request claims the key, protecting financial transactions from duplicate double-spend charges.
