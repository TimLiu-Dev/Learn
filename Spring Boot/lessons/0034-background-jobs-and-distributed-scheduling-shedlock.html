Background Jobs & Distributed Scheduling with ShedLock

Target: Every production backend needs scheduled background work: dispatching daily billing invoices, purging expired user sessions, or compiling analytics rollups. Spring's built-in '@Scheduled' annotation makes cron scheduling trivial in a local environment. However, the moment your application is deployed to Kubernetes with 5 replica pods, each pod executes that cron job simultaneously! Unless protected by distributed locking, your users receive 5 duplicate billing charges, or database tables suffer violent write collisions. In this lesson, we master ShedLock—the industry standard for distributed task scheduling—and explore how to protect cron executions across multi-replica cloud clusters.

📖 Primary Source Recommendation

Study the official authority: ShedLock Official GitHub Documentation & Guide (net.javacrumbs.shedlock) by Lukáš Křístek.. Ground your learning in primary architecture rather than secondary summaries.

💡 Why This Matters in Production

A duplicate scheduled job in production can double-charge thousands of credit cards, send spam notification blasts, or corrupt audit ledgers. Senior engineers never use bare '@Scheduled' without distributed mutex guarantees. Understanding clock drift, 'lockAtLeastFor', and 'lockAtMostFor' is critical to ensuring jobs execute exactly once across distributed instances.

Key Architectural Takeaways

  • Spring's '@Scheduled' has zero cluster awareness; every active pod in a Kubernetes ReplicaSet executes the scheduled method independently.
  • ShedLock coordinates scheduled tasks across multiple nodes using an external shared store (e.g. PostgreSQL, MySQL, Redis, DynamoDB).
  • The ShedLock database table ('shedlock') tracks 'name', 'lock_until', 'locked_at', and 'locked_by'. It uses database conditional updates to guarantee mutual exclusion without requiring heavy leader election.
  • 'lockAtMostFor' protects against deadlocks if a pod crashes mid-execution (ensures the lock auto-expires).
  • 'lockAtLeastFor' protects against clock skew and fast tasks completing before other nodes evaluate their cron trigger (preventing duplicate runs in short intervals).
  • Enable ShedLock with '@EnableSchedulerLock(defaultLockAtMostFor = "10m")' and annotate individual jobs with '@SchedulerLock(name = "...")'.

1. The Kubernetes Multi-Replica Cron Problem

Suppose you configure a job: 

@Scheduled(cron = "0 0 2 * * ?") // 2:00 AM daily
public void generateDailyInvoices() { ... }

If Kubernetes runs 4 replicas of your service, at 02:00:00 UTC, all 4 pods trigger the invoice generator simultaneously. Each pod queries unbilled accounts and processes payments. Customers get billed 4 times.

2. The Architecture of ShedLock

ShedLock does not replace Spring's scheduler; it wraps scheduled method invocations in an AOP proxy that attempts to acquire a row in a dedicated database table: 

CREATE TABLE shedlock (
    name VARCHAR(64) NOT NULL PRIMARY KEY,
    lock_until TIMESTAMP WITH TIME ZONE NOT NULL,
    locked_at TIMESTAMP WITH TIME ZONE NOT NULL,
    locked_by VARCHAR(255) NOT NULL
);

When Pod A triggers at 02:00:00.002, it issues an atomic SQL statement: 

UPDATE shedlock 
SET lock_until = :now + :lockAtMostFor, locked_at = :now, locked_by = :podName 
WHERE name = :lockName AND lock_until <= :now;

If Pod A updates 1 row, it acquired the lock and executes the task. When Pod B fires at 02:00:00.005, its update statement affects 0 rows because lock_until is in the future. Pod B immediately skips execution without error.

3. The Critical Role of 'lockAtLeastFor'

Consider a task that takes only 100 milliseconds to complete. Pod A acquires the lock, completes the work in 100ms, and releases the lock at 02:00:00.100.

Pod B's system clock happens to be 200 milliseconds behind Pod A's clock. When Pod B hits 02:00:00, Pod A has already released the lock! Pod B acquires the lock and runs the job a second time!

The Fix: Specify lockAtLeastFor = "30s". Even if the task finishes in 100ms, ShedLock holds the lock until 02:00:30 UTC, preventing any clock-skewed peer node from executing during that schedule window.

Background Jobs & Distributed Scheduling with ShedLock 
package com.example.scheduling;

import net.javacrumbs.shedlock.core.LockProvider;
import net.javacrumbs.shedlock.provider.jdbctemplate.JdbcTemplateLockProvider;
import net.javacrumbs.shedlock.spring.annotation.EnableSchedulerLock;
import net.javacrumbs.shedlock.spring.annotation.SchedulerLock;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.scheduling.annotation.EnableScheduling;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;

import javax.sql.DataSource;

@Configuration
@EnableScheduling
@EnableSchedulerLock(defaultLockAtMostFor = "15m")
class SchedulingConfig {
    @Bean
    public LockProvider lockProvider(DataSource dataSource) {
        return new JdbcTemplateLockProvider(
            JdbcTemplateLockProvider.Configuration.builder()
                .withJdbcTemplate(new org.springframework.jdbc.core.JdbcTemplate(dataSource))
                .usingDbTime() // Crucial: rely on DB server clock to eliminate app pod clock drift
                .build()
        );
    }
}

@Component
class InvoicingScheduledJob {
    private static final Logger log = LoggerFactory.getLogger(InvoicingScheduledJob.class);

    @Scheduled(cron = "0 0 2 * * ?") // 2:00 AM every night
    @SchedulerLock(
        name = "InvoicingJob_generateNightlyInvoices",
        lockAtMostFor = "30m",   // Auto-unlock if pod crashes or is killed by OOM
        lockAtLeastFor = "2m"    // Keep locked for 2 mins even if task finishes in 5 secs
    )
    public void generateNightlyInvoices() {
        log.info("Acquired distributed ShedLock! Processing nightly invoices...");
        // Heavy processing logic here
        simulateWork();
        log.info("Nightly invoices generated successfully.");
    }

    private void simulateWork() {
        try {
            Thread.sleep(1000);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}
