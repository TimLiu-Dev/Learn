Demystifying Kubernetes: Pods, Deployments & Services

Target: Modern Spring Boot applications are almost universally deployed onto Kubernetes (EKS, GKE, AKS, or on-premise clusters). Yet many backend developers view Kubernetes as an intimidating black box managed solely by DevOps. When a deployment fails, pods crash loop, or service-to-service calls return 503 errors, relying on DevOps creates crippling delays. A senior backend engineer must understand the core Kubernetes primitives: Pods (ephemeral units of compute), Deployments (declarative state, rolling updates, and self-healing), and Services (internal L4 load balancing and CoreDNS discovery).

📖 Primary Source Recommendation

Study the official authority: Kubernetes Official Documentation: Pods, Deployments & Services Networking Reference.. Ground your learning in primary architecture rather than secondary summaries.

💡 Why This Matters in Production

Understanding Kubernetes networking and lifecycle management transforms how you design Spring Boot applications. Knowing how CoreDNS resolves 'http://payment-service:8080' within the cluster, how rolling updates replace old pods without dropped packets, and how ConfigMaps inject environment properties enables you to architect resilient, cloud-native services.

Key Architectural Takeaways

  • A Pod is the smallest deployable compute unit in Kubernetes, wrapping one or more tightly coupled containers sharing network namespace (localhost) and storage volumes.
  • Pods are strictly ephemeral: their IP addresses change every time they are rescheduled, restarted, or scaled. Never hardcode Pod IP addresses!
  • Deployments manage ReplicaSets declaratively: they orchestrate zero-downtime Rolling Updates, rollback failed releases, and automatically replace crashed pods.
  • A Kubernetes Service (ClusterIP) provides a stable virtual IP and DNS name that load-balances traffic across all ready pods matching its 'spec.selector' labels.
  • Internal DNS: CoreDNS allows services to reach each other via simple hostnames: 'http://<service-name>.<namespace>.svc.cluster.local:<port>'.
  • ConfigMaps store non-sensitive configuration keys, while Secrets store base64-encoded credentials injected as environment variables or mounted files.

2. Declarative Rolling Updates

When you push a new container image tag, Kubernetes does not kill all old pods at once. It follows a Rolling Update Strategy configured by maxSurge and maxUnavailable:

  1. Kubernetes creates 1 new pod running the new image version (surging to 4 total pods).
  2. It waits for the new pod's Readiness probe to return HTTP 200.
  3. Once ready, traffic is routed to the new pod, and 1 old pod is gracefully terminated.
  4. The process repeats until all 3 pods run the new version without a single millisecond of downtime.

# Production Kubernetes Deployment & Service Manifest
# ====================================================
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
  namespace: production
  labels:
    app.kubernetes.io/name: order-service
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1        # Allow 1 extra pod during rollout
      maxUnavailable: 0  # Never take down an old pod until the new pod is fully ready!
  selector:
    matchLabels:
      app: order-service
  template:
    metadata:
      labels:
        app: order-service
    spec:
      containers:
        - name: order-service
          image: ghcr.io/myorg/order-service:1.2.0
          imagePullPolicy: IfNotPresent
          ports:
            - containerPort: 8080
              name: http
          env:
            - name: SPRING_PROFILES_ACTIVE
              value: "production"
            - name: SPRING_DATASOURCE_URL
              valueFrom:
                configMapKeyRef:
                  name: order-service-config
                  key: DB_URL
            - name: SPRING_DATASOURCE_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: order-service-secrets
                  key: DB_PASSWORD
          resources:
            requests:
              cpu: "500m"
              memory: "1024Mi"
            limits:
              cpu: "1500m"
              memory: "1536Mi"
---
# Stable ClusterIP Service for Internal DNS Load Balancing
apiVersion: v1
kind: Service
metadata:
  name: order-service
  namespace: production
spec:
  type: ClusterIP
  selector:
    app: order-service
  ports:
    - name: http
      port: 8080
      targetPort: 8080
# Kotlin Spring Boot Client invoking Kubernetes Service via CoreDNS
package com.example.k8s

import org.springframework.context.annotation.Bean
import org.springframework.context.annotation.Configuration
import org.springframework.stereotype.Service
import org.springframework.web.client.RestClient

@Configuration
class ServiceMeshConfig {
    @Bean
    fun orderServiceRestClient(builder: RestClient.Builder): RestClient {
        // CoreDNS resolves "order-service.production.svc.cluster.local"
        // directly to the ClusterIP virtual load-balancer!
        return builder
            .baseUrl("http://order-service.production.svc.cluster.local:8080")
            .build()
    }
}

@Service
class OrderGatewayClient(private val orderServiceRestClient: RestClient) {
    fun fetchOrderStatus(orderId: String): String? {
        return orderServiceRestClient.get()
            .uri("/api/orders/{id}", orderId)
            .retrieve()
            .body(String::class.java)
    }
}
