Transaction Management, AOP Proxies & ACID Boundaries

Target: Master database ACID guarantees. Understand how @Transactional operates via Spring AOP proxies, avoid the infamous self-invocation trap, and use readOnly optimizations.

📖 Primary Source Recommendation

Study the official authority: Spring Framework Reference: Transaction Management. Ground your learning in primary architecture rather than secondary summaries.

1. What Is a Database Transaction (ACID)?

  • Atomicity: All SQL statements succeed together, or ALL rollback on exception. No partial writes.
  • Consistency: The database transitions from one valid state to another, obeying all constraints.
  • Isolation: Concurrent transactions cannot see each other's uncommitted modifications.
  • Durability: Once committed, data is written to PostgreSQL's Write-Ahead Log (WAL) and survives power loss.

2. How `@Transactional` Works via Spring AOP Dynamic Proxies

When you annotate a method with @Transactional, Spring wraps your bean in a CGLIB Dynamic Proxy:

Caller ──► [ Spring AOP Proxy ] ├─ 1. Check out connection from HikariCP ├─ 2. connection.setAutoCommit(false); ├─ 3. Delegate to your actual Service method! ├─ 4a. If SUCCESS: connection.commit(); └─ 4b. If RuntimeException: connection.rollback();

3. The Infamous Self-Invocation Trap

⚠️ The Trap: Calling `@Transactional` from Within the Same Class!

If method A calls this.methodB() where method B is @Transactional, THE TRANSACTION IS COMPLETELY IGNORED! Why? Because internal calls bypass the Spring AOP Proxy! Method B runs without an active transaction, and exceptions will NOT roll back data!

4. Production Pattern: Bank Transfer Service

Atomic Bank Transfer Service 
package com.example.ecommerce.billing;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import java.math.BigDecimal;

@Service
public class TransferService {

    private final AccountRepository accountRepo;

    public TransferService(AccountRepository accountRepo) {
        this.accountRepo = accountRepo;
    }

    @Transactional
    public void transferMoney(Long fromId, Long toId, BigDecimal amount) {
        Account from = accountRepo.findById(fromId).orElseThrow();
        Account to = accountRepo.findById(toId).orElseThrow();

        from.debit(amount);
        to.credit(amount);

        accountRepo.save(from);
        accountRepo.save(to);
        // If an exception occurs anywhere, BOTH changes roll back!
    }

    @Transactional(readOnly = true) // Disables dirty-checking; routes to read replica!
    public BigDecimal getBalance(Long accountId) {
        return accountRepo.findById(accountId).orElseThrow().getBalance();
    }
}
package com.example.ecommerce.billing

import org.springframework.stereotype.Service
import org.springframework.transaction.annotation.Transactional
import java.math.BigDecimal

@Service
class TransferService(
    private val accountRepo: AccountRepository
) {
    @Transactional
    fun transferMoney(fromId: Long, toId: Long, amount: BigDecimal) {
        val from = accountRepo.findById(fromId).orElseThrow()
        val to = accountRepo.findById(toId).orElseThrow()

        from.debit(amount)
        to.credit(amount)

        accountRepo.save(from)
        accountRepo.save(to)
    }

    @Transactional(readOnly = true)
    fun getBalance(accountId: Long): BigDecimal =
        accountRepo.findById(accountId).orElseThrow().balance
}

    }

Kotlin 2.x Implementation:
package com.example.payment

import org.springframework.stereotype.Service
import org.springframework.transaction.annotation.Transactional

@Service
class PaymentService {

    @Transactional(rollbackFor = [Exception::class])
    fun executePayment(accountId: String, amount: Double) {
        // Business logic...
    }

    @Transactional(readOnly = true)
    fun getPaymentHistory(accountId: String): Double = 0.0
}
Architectural Breakdown:

Specifying rollbackFor = Exception.class guarantees rollbacks even on checked exceptions, while readOnly = true optimizes query performance and allows read-replica routing.
