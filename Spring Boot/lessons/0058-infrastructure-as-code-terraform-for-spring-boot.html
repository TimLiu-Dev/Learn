Infrastructure as Code (Terraform / OpenTofu) for Spring Boot

Target: Just as Flyway replaced manual SQL console edits for database tables, Infrastructure as Code (Terraform / OpenTofu) replaces fragile AWS Console "ClickOps" for your S3 buckets, SQS queues + DLQs, RDS databases, and IAM roles. In this final Part 2 lesson, we understand Terraform's plan → apply workflow, remote encrypted state locking, and write declarative HCL resources wired cleanly into Spring Boot via environment outputs.

📖 Primary Source Recommendation

Study the official authority: Terraform HCL Language & State Reference (also compatible with OpenTofu).

💡 Why This Matters in Production

If staging works and production breaks because someone unchecked "Block Public Access" or forgot a Dead-Letter Queue in the AWS Console six months ago, ClickOps failed you. With Terraform in Git, every S3 policy, SQS redrive rule, and RDS Multi-AZ flag goes through a peer-reviewed terraform plan on Pull Requests.

Key Architectural Takeaways

  • Declarative Desired State + Plan Diff: You declare the end state in HCL (.tf); terraform plan computes the exact create/update/destroy diff before changing a single live resource.
  • Remote State & Locking (Never Local terraform.tfstate): Store state in an encrypted S3 bucket with locking (S3 native lockfile or DynamoDB) so two engineers or CI jobs never corrupt infrastructure state simultaneously.
  • App-Adjacent IaC Pattern: Keep service-owned resources (S3 upload bucket, SQS queue + DLQ, least-privilege IAM policy) modularized cleanly alongside the Spring Boot service repo, consuming shared VPC/EKS outputs via remote data sources.
  • prevent_destroy Lifecycle Guard: Protect stateful resources (production RDS PostgreSQL, S3 buckets) with lifecycle { prevent_destroy = true } so an accidental refactor cannot wipe customer data.

Production Implementation (Terraform HCL for NexusCommerce S3 + SQS + DLQ)

Terraform HCL Module + Spring Boot Environment Wiring 
# infra/main.tf — Remote State + Encrypted S3 + SQS with Dead-Letter Queue
terraform {
  backend "s3" {
    bucket       = "nexus-terraform-state-prod"
    key          = "services/order-service/terraform.tfstate"
    region       = "us-east-1"
    encrypt      = true
    use_lockfile = true
  }
}

resource "aws_s3_bucket" "invoices" {
  bucket = "nexus-invoices-${var.env}"
  lifecycle {
    prevent_destroy = true
  }
}

resource "aws_s3_bucket_public_access_block" "invoices" {
  bucket                  = aws_s3_bucket.invoices.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

resource "aws_sqs_queue" "orders_dlq" {
  name = "nexus-orders-dlq-${var.env}"
}

resource "aws_sqs_queue" "orders" {
  name                       = "nexus-orders-${var.env}"
  visibility_timeout_seconds = 60
  redrive_policy = jsonencode({
    deadLetterTargetArn = aws_sqs_queue.orders_dlq.arn
    maxReceiveCount     = 5
  })
}
# Terraform outputs feed Kubernetes ConfigMaps / application.yml cleanly:
# output "orders_queue_url" { value = aws_sqs_queue.orders.url }
# output "invoices_bucket"  { value = aws_s3_bucket.invoices.bucket }

# application-prod.yml (Consumed identically by Java 21/25 or Kotlin 2.x Spring Boot)
nexus:
  s3:
    invoices-bucket: ${NEXUS_INVOICES_BUCKET}
  sqs:
    orders-queue-url: ${NEXUS_ORDERS_QUEUE_URL}

spring:
  cloud:
    aws:
      region:
        static: us-east-1
