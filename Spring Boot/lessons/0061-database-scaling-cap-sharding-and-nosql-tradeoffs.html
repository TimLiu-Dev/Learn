Database Scaling: CAP/PACELC, Partitioning, Sharding & NoSQL Tradeoffs

Target: A single PostgreSQL primary scales surprisingly far—especially with indexes, keyset pagination, L1/L2 caching, and read replicas (Lessons 0012–0021). But in Senior System Design interviews, you will be asked: "What happens when your orders table hits 2 billion rows or writes saturate one primary?" In this lesson, we master CAP vs. PACELC, PostgreSQL declarative partitioning vs. horizontal sharding, consistent hashing, and when Document/Key-Value/Time-Series stores beat relational SQL.

📖 Primary Source Recommendation

Study the official authorities: PostgreSQL Table Partitioning Reference and Designing Data-Intensive Applications (Martin Kleppmann).

💡 Why This Matters in Production

Sharding prematurely turns simple SQL joins and ACID transactions into a distributed nightmare. The senior scaling ladder is strictly ordered: 1) Query/Index optimization & Caching → 2) Read Replicas → 3) Table Partitioning (single node) → 4) Functional splitting / Horizontal Sharding as a last resort.

Key Architectural Takeaways

  • CAP & PACELC in Plain English: Network partitions (P) are unavoidable in distributed systems, forcing a choice between Consistency (C: reject writes or risk stale reads—e.g., ledgers/inventory) and Availability (A: accept writes everywhere and reconcile—e.g., shopping carts). Even without partitions (E), you trade off Latency (L) vs. Consistency (C) on synchronous vs. async replication.
  • Partitioning vs. Sharding: Partitioning splits a giant table into smaller physical chunks (e.g., monthly orders_2026_11) on the same PostgreSQL server (instant drops for archiving, smaller B-Tree indexes). Sharding splits rows across independent database servers by a shard key (e.g., tenant_id or user_id).
  • Choosing a Shard Key: Pick high-cardinality keys present on every hot query (tenant_id, customer_id) via consistent hashing—never shard by monotonically increasing created_at (all today's writes hit one hot shard!).
  • NoSQL Selection Matrix: PostgreSQL (ACID ledgers, relational integrity, JSONB); DynamoDB / Cassandra (predictable key-value / wide-column write scale); MongoDB (rapidly evolving document catalogs); TimescaleDB / InfluxDB (high-ingest metrics/IoT telemetry).

-- V20__partition_audit_events.sql (Single-Node PostgreSQL Partitioning)
CREATE TABLE audit_events (
    id          UUID NOT NULL,
    tenant_id   UUID NOT NULL,
    occurred_at TIMESTAMPTZ NOT NULL,
    payload     JSONB NOT NULL,
    PRIMARY KEY (id, occurred_at) -- Partition key MUST be part of primary/unique keys!
) PARTITION BY RANGE (occurred_at);

CREATE TABLE audit_events_2026_11 PARTITION OF audit_events
    FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');

// TenantShardRouter.java — Deterministic consistent-hash shard lookup
public final class TenantShardRouter {
    public int resolveShard(UUID tenantId, int totalShards) {
        // Unsigned modulo on Murmur/SHA/hash avoids negative index bug in Java %!
        return Integer.remainderUnsigned(tenantId.hashCode(), totalShards);
    }
}

💡 Complete Production Reference Solution
Java 21/25 Implementation:
// CREATE TABLE ledger_entries (id UUID, created_at TIMESTAMPTZ, PRIMARY KEY (id, created_at)) PARTITION BY RANGE (created_at);
public class ShardResolver {
    public int shardForTenant(UUID tenantId, int shardCount) {
        return Integer.remainderUnsigned(tenantId.hashCode(), shardCount);
    }
}
Kotlin 2.x Implementation:
// CREATE TABLE ledger_entries (id UUID, created_at TIMESTAMPTZ, PRIMARY KEY (id, created_at)) PARTITION BY RANGE (created_at);
class ShardResolver {
    fun shardForTenant(tenantId: UUID, shardCount: Int): Int =
        Integer.remainderUnsigned(tenantId.hashCode(), shardCount)
}
Architectural Breakdown:

Standard hashCode() % shardCount can return negative numbers (crashing array lookups!), whereas Integer.remainderUnsigned guarantees 0 .. shardCount - 1.
