Modern Java 21/25 for Kotlin Developers: Records, Sealed Types, Pattern Matching & JSpecify

Target: If your daily language on Android is Kotlin, your mental picture of Java might still be verbose Java 8 boilerplate. Modern server-side Java (JDK 21 and 25 LTS) has evolved into an algebraic, expressive language with Records, Sealed Interfaces, Exhaustive Pattern Matching for switch, Record Deconstruction, and JSpecify (@NullMarked) compile-time nullability contracts adopted across Spring Boot 4. Master the exact 1-to-1 translation between modern Kotlin and modern Java so you can write both fluently in senior interviews and production systems.

📖 Primary Source Recommendation

Study the official specifications: OpenJDK JEP 440 (Record Patterns) & JEP 441 (Pattern Matching for switch) and JSpecify User Guide (Spring Framework 7 / Boot 4 Nullability Standard).

💡 Android Kotlin → Modern Java 21/25 Rosetta Stone

Every construct you love in Android Kotlin now has a direct first-class counterpart in Java 21/25:
• Kotlin data class Payment(val id: UUID, val amount: Long) ↔ Java public record Payment(UUID id, long amount) {}
• Kotlin sealed interface PaymentResult ↔ Java public sealed interface PaymentResult permits Approved, Declined {}
• Kotlin when (result) { is Approved -> ... } ↔ Java switch (result) { case Approved(var id, var authCode) -> ... }
• Kotlin String vs String? ↔ Java package-level @NullMarked + explicit @Nullable String

1. Algebraic Data Types: Records + Sealed Interfaces + Exhaustive Switch

In modern backend domain modeling, returning vague boolean flags or throwing exceptions for expected business outcomes (like an expired card or insufficient funds) leads to fragile control flow. Just as you use a sealed interface UiState on Android, senior Java 21/25 engineers combine sealed interface with record implementations and exhaustive switch expressions. Because the compiler knows every permitted subtype via permits, no default branch is required—and adding a new subtype immediately flags every unhandled switch at compile time!

2. Java Streams & Optional vs. Kotlin Collection Pipelines

Where Kotlin provides eager collection extensions (list.filter { ... }.map { ... }) and lazy asSequence(), Java uses lazy .stream() pipelines terminated by .toList() (which returns an unmodifiable list in Java 16+, replacing verbose Collectors.toList()). For nullable lookups, Spring Data repositories in Java return Optional<T>; senior Java engineers chain .map(...) and .orElseThrow(...) rather than calling .get() without checking, and never use Optional for class fields or method parameters.

3. JSpecify (@NullMarked): Zero-Ambiguity Java ↔ Kotlin Interop

Historically, calling Java APIs from Kotlin produced risky "platform types" (String!) that could explode with a NullPointerException. Spring Framework 7 and Spring Boot 4 annotate packages with JSpecify's @NullMarked (inside package-info.java), making every unannotated Java type non-null by default—just like Kotlin! Only parameters or return values explicitly marked @Nullable permit null, and the Kotlin 2.x compiler enforces these annotations as strict compile errors.

Exhaustive Sealed Domain Results & Record Pattern Deconstruction 
package com.example.checkout;

import org.jspecify.annotations.NullMarked;
import org.jspecify.annotations.Nullable;
import java.math.BigDecimal;

@NullMarked // All types in this class are non-null unless marked @Nullable!
public class CheckoutDecisionEngine {

    public sealed interface ChargeOutcome
            permits ChargeOutcome.Authorized, ChargeOutcome.Declined, ChargeOutcome.FraudReview {
        record Authorized(String transactionId, BigDecimal capturedAmount) implements ChargeOutcome {}
        record Declined(String reasonCode, boolean retryable) implements ChargeOutcome {}
        record FraudReview(String caseId, @Nullable String reviewerNote) implements ChargeOutcome {}
    }

    // Record pattern deconstruction + guarded pattern ('when') inside exhaustive switch expression
    public static String toClientStatus(ChargeOutcome outcome) {
        return switch (outcome) {
            case ChargeOutcome.Authorized(var txId, var amt) ->
                "APPROVED:" + txId + ":" + amt;
            case ChargeOutcome.Declined(var code, var retry) when retry ->
                "RETRY_LATER:" + code;
            case ChargeOutcome.Declined(var code, var retry) ->
                "HARD_DECLINE:" + code;
            case ChargeOutcome.FraudReview(var caseId, var note) ->
                "HELD:" + caseId + ":" + (note != null ? note : "PENDING");
        };
    }
}
package com.example.checkout

import java.math.BigDecimal

sealed interface ChargeOutcome {
    data class Authorized(val transactionId: String, val capturedAmount: BigDecimal) : ChargeOutcome
    data class Declined(val reasonCode: String, val retryable: Boolean) : ChargeOutcome
    data class FraudReview(val caseId: String, val reviewerNote: String?) : ChargeOutcome
}

object CheckoutDecisionEngine {
    fun toClientStatus(outcome: ChargeOutcome): String =
        when (outcome) {
            is ChargeOutcome.Authorized ->
                "APPROVED:${outcome.transactionId}:${outcome.capturedAmount}"
            is ChargeOutcome.Declined ->
                if (outcome.retryable) "RETRY_LATER:${outcome.reasonCode}"
                else "HARD_DECLINE:${outcome.reasonCode}"
            is ChargeOutcome.FraudReview ->
                "HELD:${outcome.caseId}:${outcome.reviewerNote ?: "PENDING"}"
        }
}

Hint 1: Exhaustive Dispatch Expression
In Java, return switch (event) { ... };. In Kotlin, return when (event) { ... }.
Hint 2: Deconstructing Captured
In Java: case Captured(var txId, var cents) -> "OK:" + txId;. In Kotlin: is PaymentEvent.Captured -> "OK:${event.txId}".
Hint 3: Guarding Retryable Failures
In Java: use case Failed(var code, var retryable) when retryable -> "RETRY:" + code; followed by case Failed(var code, var retryable) -> "FAIL:" + code;.
💡 Complete Production Reference Solution
Java 21/25 Implementation:
package com.example.modern;

public class PaymentStatusMapper {
    public sealed interface PaymentEvent permits Captured, Failed {}
    public record Captured(String txId, long cents) implements PaymentEvent {}
    public record Failed(String code, boolean retryable) implements PaymentEvent {}

    public static String describe(PaymentEvent event) {
        return switch (event) {
            case Captured(var txId, var cents) -> "OK:" + txId;
            case Failed(var code, var retryable) when retryable -> "RETRY:" + code;
            case Failed(var code, var retryable) -> "FAIL:" + code;
        };
    }
}
Kotlin 2.x Implementation:
package com.example.modern

sealed interface PaymentEvent {
    data class Captured(val txId: String, val cents: Long) : PaymentEvent
    data class Failed(val code: String, val retryable: Boolean) : PaymentEvent
}

object PaymentStatusMapper {
    fun describe(event: PaymentEvent): String =
        when (event) {
            is PaymentEvent.Captured -> "OK:${event.txId}"
            is PaymentEvent.Failed ->
                if (event.retryable) "RETRY:${event.code}" else "FAIL:${event.code}"
        }
}
Architectural Breakdown:

Sealed interfaces paired with immutable records (or Kotlin data classes) turn illegal domain states into compile-time errors, giving Java 21/25 the exact same algebraic safety you rely on in Kotlin.
