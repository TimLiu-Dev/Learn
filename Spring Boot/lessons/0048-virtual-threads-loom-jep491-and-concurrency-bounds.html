Virtual Threads in Java 25 LTS: Project Loom, JEP 491 & Concurrency Bounding

Target: Project Loom (JEP 444 in Java 21, supercharged by JEP 491 in Java 25 LTS) decouples Java threads from OS kernel threads—restoring clean, readable thread-per-request imperative code while scaling to hundreds of thousands of concurrent I/O requests without reactive WebFlux complexity. Master how carrier-thread mounting works, what changed between Java 21 and Java 25 around synchronized pinning, why you must never pool Virtual Threads, and how to bound scarce downstream resources with Semaphore and ReentrantLock.

📖 Primary Source Recommendation

Study the official authorities: JEP 444: Virtual Threads and JEP 491: Synchronize Virtual Threads without Pinning (Java 24/25 LTS).

1. Platform Threads vs. Virtual Threads (Carrier Mounting)

Classic Java platform threads wrap OS kernel threads 1:1 (~1MB stack memory each; context switches trap into the OS kernel). When a platform thread blocks for 40ms waiting on PostgreSQL or Stripe, that 1MB OS thread sits completely idle.

Virtual Threads are lightweight JVM-managed continuations (~few hundred bytes) scheduled onto a small ForkJoinPool of OS carrier threads (sized to CPU core count). The moment your code hits blocking socket/JDBC I/O, the JVM unmounts the virtual thread's stack frames onto the heap and immediately runs another virtual thread on that CPU core! Enable them globally in Spring Boot with one line: spring.threads.virtual.enabled=true.

2. Carrier Pinning in 2027: Java 25 LTS (JEP 491) vs. Java 21 LTS

A virtual thread is pinned if it blocks on I/O while unable to unmount from its OS carrier thread. Knowing the exact Java 21 vs. Java 25 distinction is a top 2027 senior interview differentiator:

  • In Java 25 LTS (JEP 491 — Current Greenfield Baseline): The JVM re-implemented object monitors so virtual threads unmount cleanly even inside synchronized blocks and methods! In Java 25, carrier pinning now happens only when blocking inside native JNI / Foreign Function (FFM) frames or inside a class initializer (static {} / <clinit>).
  • In Existing Java 21 LTS Codebases: Blocking I/O inside synchronized does pin the carrier thread! On Java 21 services, diagnose pinning with -Djdk.tracePinnedThreads=full and replace blocking synchronized monitors with ReentrantLock.
  • Why Senior Engineers Still Use ReentrantLock in Java 25: Unlike synchronized, ReentrantLock provides bounded acquisition timeouts (tryLock(500, TimeUnit.MILLISECONDS)), interruptible lock waits, and explicit fairness policies—plus full safety across mixed Java 21/25 libraries!

3. Never Pool Virtual Threads — Bound Resources with Semaphore

Never create a fixed pool of 50 virtual threads—virtual threads are disposable per-task objects! However, because Tomcat can now spawn 20,000 concurrent virtual threads during a traffic spike, you can no longer rely on Tomcat's old 200-thread ceiling to protect a 20-connection HikariCP pool or fragile partner API. Bound concurrency explicitly with a Semaphore (or Spring Framework 7's @ConcurrencyLimit): waiting virtual threads park cheaply on the heap without holding carrier threads!

package com.example.loom;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.core.task.support.TaskExecutorAdapter;
import org.springframework.stereotype.Service;
import org.springframework.web.client.RestClient;

import java.util.concurrent.Executors;
import java.util.concurrent.Semaphore;
import java.util.concurrent.locks.ReentrantLock;

@Configuration
class VirtualThreadConfig {
    // Also set `spring.threads.virtual.enabled=true` in application.yml
    @Bean
    public TaskExecutorAdapter virtualTaskExecutor() {
        return new TaskExecutorAdapter(Executors.newVirtualThreadPerTaskExecutor());
    }
}

@Service
class ExternalPartnerGateway {
    private final RestClient restClient;
    private final Semaphore partnerSemaphore = new Semaphore(15); // Max 15 in-flight calls
    private final ReentrantLock stateLock = new ReentrantLock();
    private long totalRequestsServed = 0;

    public ExternalPartnerGateway(RestClient.Builder builder) {
        this.restClient = builder.baseUrl("https://api.partner.com").build();
    }

    public String fetchPartnerData() throws InterruptedException {
        partnerSemaphore.acquire(); // Virtual thread suspends cheaply on heap if 15 permits busy
        try {
            String result = restClient.get().uri("/data").retrieve().body(String.class);
            stateLock.lock();
            try {
                totalRequestsServed++;
            } finally {
                stateLock.unlock();
            }
            return result;
        } finally {
            partnerSemaphore.release();
        }
    }
}

💡 Complete Production Reference Solution
Java 25 Implementation:
package com.example.loom;

import java.util.concurrent.Semaphore;
import java.util.concurrent.locks.ReentrantLock;

public class VirtualThreadThrottler {
    private final Semaphore semaphore = new Semaphore(10);
    private final ReentrantLock lock = new ReentrantLock();
    private int counter = 0;

    public String executeThrottled(Runnable task) throws InterruptedException {
        semaphore.acquire();
        try {
            task.run();
            lock.lock();
            try {
                counter++;
            } finally {
                lock.unlock();
            }
            return "executed: " + counter;
        } finally {
            semaphore.release();
        }
    }

    public boolean isRunningOnVirtualThread() {
        return Thread.currentThread().isVirtual();
    }
}
Kotlin 2.2+ Implementation:
package com.example.loom

import java.util.concurrent.Semaphore
import java.util.concurrent.locks.ReentrantLock
import kotlin.concurrent.withLock

class VirtualThreadThrottler {
    val semaphore = Semaphore(10)
    val lock = ReentrantLock()
    var counter = 0

    fun executeThrottled(task: Runnable): String {
        semaphore.acquire()
        try {
            task.run()
            lock.withLock {
                counter++
            }
            return "executed: $counter"
        } finally {
            semaphore.release()
        }
    }

    fun isRunningOnVirtualThread(): Boolean =
        Thread.currentThread().isVirtual
}
Architectural Breakdown:

Using a Semaphore bounds downstream database/HTTP concurrency so bursts of virtual threads never overwhelm connection pools, while ReentrantLock works safely across both Java 21 and Java 25 runtimes.
