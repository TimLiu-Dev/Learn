Keyset (Cursor) Pagination & Composite Tie-Breaker Indexes

Target: Solve the #1 pagination bottleneck in mobile feeds and order histories. Learn why OFFSET 100000 saturates PostgreSQL CPU, implement O(log N) Keyset (Cursor) Pagination (the server-side engine behind Android Jetpack Paging 3), and avoid duplicate/skipped rows on timestamp-sorted feeds using composite (created_at, id) tie-breaker cursors.

📖 Primary Source Recommendation

Study the official authorities: Use The Index, Luke: We Need Tool Support for Keyset Pagination (No Offset!) and Vlad Mihalcea: High-Performance Keyset Pagination.

1. Why OFFSET 100000 Kills Database Performance

Junior developers reach for offset pagination: SELECT * FROM orders ORDER BY id ASC LIMIT 20 OFFSET 100000;. To return just 20 rows, PostgreSQL must still scan, fetch, and count through all 100,020 rows from disk/index and throw the first 100,000 in the trash! Worse yet, if a new row is inserted on Page 1 while a user scrolls to Page 2, OFFSET shifts every row down and returns a duplicate item to the mobile RecyclerView/LazyColumn.

🤖 Android Mental Model: Jetpack Paging 3 & Opaque Cursors

In Android Jetpack Paging 3, your PagingSource<String, OrderItem> passes nextCursor from the previous JSON page into the next Retrofit request (GET /api/v1/orders?cursor=...&limit=20). On the backend, Keyset Pagination seeks directly into the B-Tree index via WHERE id > :afterId ORDER BY id ASC LIMIT 20—executing in ~0.1ms whether the user is on Page 1 or Page 50,000!

2. Simple Primary-Key Cursor Pagination

Keyset Pagination Repository (O(log N) B-Tree Seek) 
package com.example.ecommerce.order;

import org.springframework.jdbc.core.simple.JdbcClient;
import org.springframework.stereotype.Repository;
import java.util.List;

@Repository
public class OrderKeysetRepository {
    private final JdbcClient jdbcClient;

    public OrderKeysetRepository(JdbcClient jdbcClient) {
        this.jdbcClient = jdbcClient;
    }

    public List<OrderSummary> fetchPage(Long afterId, int limit) {
        int safeLimit = Math.min(Math.max(limit, 1), 100); // Always cap page size!
        if (afterId == null) {
            return jdbcClient.sql("SELECT id, status, total FROM orders ORDER BY id ASC LIMIT :limit")
                .param("limit", safeLimit)
                .query(OrderSummary.class)
                .list();
        }
        return jdbcClient.sql("SELECT id, status, total FROM orders WHERE id > :afterId ORDER BY id ASC LIMIT :limit")
            .param("afterId", afterId)
            .param("limit", safeLimit)
            .query(OrderSummary.class)
            .list();
    }
}
package com.example.ecommerce.order

import org.springframework.stereotype.Repository

@Repository
class OrderKeysetRepository(private val jdbcClient: JdbcClient) {

        val safeLimit = limit.coerceIn(1, 100)
        return if (afterId == null) {
            jdbcClient.sql("SELECT id, status, total FROM orders ORDER BY id ASC LIMIT :limit")
                .param("limit", safeLimit)
                .query(OrderSummary::class.java)
                .list()
        } else {
            jdbcClient.sql("SELECT id, status, total FROM orders WHERE id > :afterId ORDER BY id ASC LIMIT :limit")
                .param("afterId", afterId)
                .param("limit", safeLimit)
                .query(OrderSummary::class.java)
                .list()
        }
    }
}

3. Senior Trap: Sorting by Non-Unique Columns (created_at Tie-Breakers)

Real mobile feeds almost always sort newest-first by created_at DESC. What happens if two orders arrive in the exact same microsecond (2027-03-10T12:00:00.125Z), and the page boundary cuts right between them? Filtering with WHERE created_at < :lastCreatedAt permanently skips the second order!

The Production Fix — Composite Tuple Comparison + Matching Index: Pair the timestamp with a unique tie-breaker column (id) in both the Flyway index and PostgreSQL's row-value tuple predicate:

Deterministic Composite Cursor: (created_at DESC, id DESC) 
-- 1. Flyway Index MUST match exact sort direction of both columns:
CREATE INDEX CONCURRENTLY idx_orders_created_id_desc
    ON orders (created_at DESC, id DESC);

-- 2. SQL Row-Value Comparison handles timestamp ties deterministically:
SELECT id, created_at, total
FROM orders
WHERE (created_at, id) < (:afterCreatedAt, :afterId)
ORDER BY created_at DESC, id DESC
LIMIT :limit;
// Encode composite cursor as Base64URL("2027-03-10T12:00:00.125Z|8921") for mobile clients
data class OrderCursor(val createdAt: Instant, val id: Long)

fun findNewestOrders(cursor: OrderCursor, limit: Int): List<OrderSummary> =
    jdbcClient.sql("""
        SELECT id, created_at, total
        FROM orders
        WHERE (created_at, id) < (:afterCreatedAt, :afterId)
        ORDER BY created_at DESC, id DESC
        LIMIT :limit
    """.trimIndent())
        .param("afterCreatedAt", cursor.createdAt)
        .param("afterId", cursor.id)
        .param("limit", limit.coerceIn(1, 100))
        .query(OrderSummary::class.java)
        .list()

Hint 1: Page Size Cap

Hint 2: First Page vs. Subsequent Page
Check if (cursorId == null) for the initial page, and include WHERE id > when cursorId is present.
Hint 3: Concrete Snippet

💡 Complete Production Reference Solution
Java 25 Implementation:
package com.example.pagination;

public class KeysetQueryBuilder {
    public static String buildKeysetQuery(Long cursorId, int requestedLimit) {
        int safeLimit = Math.min(requestedLimit, 100);
        if (cursorId == null) {
            return "SELECT * FROM orders ORDER BY id ASC LIMIT " + safeLimit;
        }
        return "SELECT * FROM orders WHERE id > " + cursorId + " ORDER BY id ASC LIMIT " + safeLimit;
    }
}
Kotlin 2.2+ Implementation:
package com.example.pagination

import kotlin.math.min

object KeysetQueryBuilder {
    fun buildKeysetQuery(cursorId: Long?, requestedLimit: Int): String {
        val safeLimit = min(requestedLimit, 100)
        return if (cursorId == null) {
            "SELECT * FROM orders ORDER BY id ASC LIMIT $safeLimit"
        } else {
            "SELECT * FROM orders WHERE id > $cursorId ORDER BY id ASC LIMIT $safeLimit"
        }
    }
}
Architectural Breakdown:

Keyset pagination seeks the B-Tree index in constant logarithmic time while clamping LIMIT protects JVM heap memory against unbounded client page requests.
