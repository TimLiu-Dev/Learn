Integration Testing with Testcontainers & Spring Boot 3.1+ @ServiceConnection

Target: For years, Java teams tested against in-memory databases like H2 or embedded Kafka. In production, however, applications crashed because H2 does not support PostgreSQL JSONB operators, Flyway migrations containing Postgres-specific dialect fail, and embedded in-memory brokers hide network partition bugs. Testcontainers revolutionized Java integration testing by spinning up genuine, throwaway Docker containers for PostgreSQL, Redis, Kafka, and RabbitMQ during test runs. With Spring Boot 3.1+, the revolutionary '@ServiceConnection' annotation eliminates all dynamic property boilerplate, binding Spring Datasource and Kafka configurations to containers automatically.

📖 Primary Source Recommendation

Study the official authority: Spring Boot 3.1 Release Notes (ConnectionDetails & @ServiceConnection) & Testcontainers Official Documentation.. Ground your learning in primary architecture rather than secondary summaries.

💡 Why This Matters in Production

Testing against an in-memory substitute provides false confidence. If your Flyway migrations use PostgreSQL-specific features like 'CREATE INDEX CONCURRENTLY' or 'uuid_generate_v4()', H2 fails to compile them. Testcontainers guarantees tests run against the exact same engine and version deployed in production AWS.

Key Architectural Takeaways

  • Never use H2 for integration tests if production runs PostgreSQL or MySQL: dialect discrepancies create false test passes that break in production.
  • Testcontainers runs real Docker containers (PostgreSQL, Redis, Kafka) directly from JUnit 5 tests via the Docker daemon.
  • Spring Boot 3.1+ introduced '@ServiceConnection': placing it on a container automatically configures 'spring.datasource.url', username, password, or Kafka bootstrap servers.
  • Eliminates messy legacy '@DynamicPropertySource' methods and hardcoded port mapping.
  • Use Singleton Container Pattern across test classes to reuse the same running Docker container throughout the entire test suite, speeding up runs by 80%.
  • Testcontainers Desktop allows developers to pause and inspect test container databases locally with GUI tools like DBeaver or psql.

1. The Evolution: From @DynamicPropertySource to @ServiceConnection

Prior to Spring Boot 3.1, connecting a Testcontainer required repetitive boilerplate: 

// The Old Clunky Way (Pre-3.1):
@Container
static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16-alpine");

@DynamicPropertySource
static void configureProperties(DynamicPropertyRegistry registry) {
    registry.add("spring.datasource.url", postgres::getJdbcUrl);
    registry.add("spring.datasource.username", postgres::getUsername);
    registry.add("spring.datasource.password", postgres::getPassword);
}

With Spring Boot 3.1+, @ServiceConnection does everything in one annotation: 

// The Modern Spring Boot 3.1+ Way:
@Container
@ServiceConnection
static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16-alpine");

Spring Boot detects the container type and automatically injects all relevant configuration properties into the Spring Environment!

2. The Singleton Container Pattern

Starting a new Docker container for every single test class wastes 5–10 seconds per class. In a project with 30 test classes, that adds 3–5 minutes of startup overhead.

Instead, define an abstract base class or reusable configuration that starts the container once: 

public abstract class BaseIntegrationTest {
    static final PostgreSQLContainer<?> postgres = 
        new PostgreSQLContainer<>("postgres:16-alpine")
            .withReuse(true); // Reuses container across local runs!

    static {
        postgres.start();
    }
}

Integration Testing with Testcontainers & Spring Boot 3.1+ @ServiceConnection 
package com.example.testcontainers;

import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.testcontainers.service.connection.ServiceConnection;
import org.testcontainers.containers.PostgreSQLContainer;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;

import java.util.Optional;
import java.util.UUID;

import static org.assertj.core.api.Assertions.assertThat;

@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@Testcontainers
class CustomerRepositoryIntegrationTest {

    // Spring Boot 3.1+ @ServiceConnection auto-wires datasource properties!
    @Container
    @ServiceConnection
    static PostgreSQLContainer<?> postgres = 
        new PostgreSQLContainer<>("postgres:16-alpine")
            .withDatabaseName("testdb")
            .withUsername("testuser")
            .withPassword("testpass");

    @Autowired
    private CustomerRepository customerRepository;

    @Test
    @DisplayName("Persist customer in real PostgreSQL container and verify JSONB/UUID handling")
    void saveAndFindCustomer_worksWithRealPostgres() {
        Customer customer = new Customer(UUID.randomUUID(), "jane.doe@example.com", "Jane Doe");
        customerRepository.save(customer);

        Optional<Customer> found = customerRepository.findById(customer.getId());

        assertThat(found).isPresent();
        assertThat(found.get().getEmail()).isEqualTo("jane.doe@example.com");
    }
}
