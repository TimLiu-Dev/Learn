PostgreSQL Internals: MVCC, AUTOVACUUM, DDL lock_timeout & Deadlock Triage

Target: A shocking number of Spring Boot production outages happen during a tiny 2-second Flyway migration: an ALTER TABLE asks for an AccessExclusiveLock, waits behind one slow analytical SELECT query, and queues every subsequent SELECT, INSERT, and UPDATE behind it until HikariCP exhausts and the entire API goes down! Master PostgreSQL's MVCC (dead tuples & AUTOVACUUM), SET lock_timeout + statement_timeout, CREATE INDEX CONCURRENTLY, and live lock triage via pg_stat_activity.

📖 Primary Source Recommendation

Study the official authorities: PostgreSQL Docs: MVCC & Explicit Locking and PostgreSQL Docs: Routine Vacuuming & Table Bloat.

💡 Android Mental Model Bridge

SQLite on Android uses a simple single-writer lock. PostgreSQL uses MVCC (Multi-Version Concurrency Control) so readers never block writers and writers never block readers—instead, every UPDATE/DELETE writes a new row version and marks the old tuple dead (xmax) for AUTOVACUUM to reclaim later!

1. Four PostgreSQL Production Laws Every Backend Engineer Must Know

  • MVCC & Table Bloat (AUTOVACUUM): In PostgreSQL, an UPDATE is internally an INSERT + dead old row. High-churn tables (like `outbox_events` or `sessions`) accumulate dead tuples fast; if AUTOVACUUM falls behind (or long-running idle-in-transaction connections block cleanup), table size balloons 10× and query latency degrades!
  • The AccessExclusiveLock Queue Pile-Up: Running ALTER TABLE orders ADD COLUMN ... requires AccessExclusiveLock. Even if the DDL itself takes 5ms, if it waits behind a 20-second report query, every new application query queues behind the DDL! Always prefix Flyway DDL scripts with SET lock_timeout = '2s'; so the migration fails safely instead of taking down production, and use CREATE INDEX CONCURRENTLY outside transactions (`-- flyway:executeInTransaction=false`).
  • Guard Application Queries with statement_timeout: Set a HikariCP connection init / session statement_timeout (e.g. 5000ms) so runaway queries never hold DB CPU and connections forever.
  • Live Lock & Deadlock Triage (pg_stat_activity): Spot blocked queries and their blocker PIDs immediately in psql using pg_blocking_pids(pid) and wait_event_type = 'Lock'.
