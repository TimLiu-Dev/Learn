Hands-On NoSQL in Spring Boot: Spring Data MongoDB (@Document, TTL, @Version) & AWS DynamoDB

Target: In Lesson 0061 you learned when to pick NoSQL over PostgreSQL. When your team actually runs MongoDB (for schema-evolving product catalogs, session histories, or audit documents) or AWS DynamoDB (for single-digit-millisecond key-value workloads at massive scale), you need practical modeling discipline: embedding vs. referencing, TTL auto-expiring indexes, @Version optimistic concurrency, and avoiding full-table Scan anti-patterns in DynamoDB.

📖 Primary Source Recommendation

Study the official authorities: Spring Data MongoDB Reference Documentation and AWS SDK v2: DynamoDB Enhanced Client Guide.

💡 Android Mental Model Bridge

If you have used Cloud Firestore on Android, MongoDB and DynamoDB share the same core rule: model around your exact read access patterns, not relational normalization. Unlike Room/SQLite joins, joining 5 collections in NoSQL destroys latency—embed bounded child items together inside one document or DynamoDB item collection!

1. MongoDB vs. DynamoDB Production Rules in Spring Boot

  • Embed Bounded Data, Reference Unbounded Arrays: Never embed an unbounded array (like 500,000 comments inside one blog document) because MongoDB caps documents at 16MB (and DynamoDB items at 400KB). Embed small value lists (order shipping address, line items), reference unbounded logs.
  • TTL Indexes (@Indexed(expireAfter = "30d")): Let MongoDB or DynamoDB automatically purge expired audit tokens, OTP codes, or cart drafts in the background without cron jobs! (Remember in Spring Boot to enable spring.data.mongodb.auto-index-creation=true or create indexes via Mongock migrations.)
  • Optimistic Concurrency (@Version) & Conditional Writes: Both Spring Data MongoDB (@Version) and DynamoDB Enhanced Client (@DynamoDbVersionAttribute / ConditionExpression) prevent lost updates without multi-row locks.
  • Ban DynamoDB scan() in Request Paths: Always fetch via partition key + sort key (GetItem / Query) or a Global Secondary Index (GSI)—never scan() millions of items on an API endpoint.

Spring Data MongoDB Document with TTL Expiry, Compound Index & @Version 
package com.nexus.nosql;

import org.springframework.data.annotation.Id;
import org.springframework.data.annotation.Version;
import org.springframework.data.mongodb.core.index.CompoundIndex;
import org.springframework.data.mongodb.core.index.Indexed;
import org.springframework.data.mongodb.core.mapping.Document;
import org.springframework.data.mongodb.repository.MongoRepository;

import java.time.Instant;
import java.util.List;

@Document(collection = "shopping_carts")
@CompoundIndex(name = "idx_tenant_user", def = "{'tenantId': 1, 'userId': 1}", unique = true)
public record ShoppingCartDoc(
    @Id String id,
    String tenantId,
    String userId,
    List<CartLine> items,
    @Indexed(expireAfter = "7d") Instant expiresAt,
    @Version Long version
) {
    public record CartLine(String sku, int qty, long unitCents) {}
}

public interface ShoppingCartRepository extends MongoRepository<ShoppingCartDoc, String> {
    ShoppingCartDoc findByTenantIdAndUserId(String tenantId, String userId);
}
package com.nexus.nosql

    fun findByTenantIdAndUserId(tenantId: String, userId: String): ShoppingCartDoc?
