Concurrency Defense: Optimistic (@Version) vs Pessimistic Locking

Target: When multiple concurrent transactions update the same database record simultaneously, without defensive concurrency control you guarantee data corruption via the 'Lost Update' anomaly. Consider an e-commerce flash sale: two threads read inventory count = 5. Thread A sells 2 units and writes 3. Thread B sells 1 unit and writes 4, overwriting Thread A's update. Two fundamental paradigms exist to prevent this: Optimistic Locking (assume collisions are rare, detect at commit via version columns) and Pessimistic Locking (assume collisions are frequent, lock the physical row via SELECT FOR UPDATE). Choosing the wrong strategy causes either catastrophic deadlock storms or unacceptable abort/retry latency under load.

📖 Primary Source Recommendation

Study the official authority: PostgreSQL Documentation: Explicit Locking (Row-Level Locks) & Vlad Mihalcea's High-Performance Java Persistence: Chapter on Locking.. Ground your learning in primary architecture rather than secondary summaries.

💡 Why This Matters in Production

A senior engineer must know precisely when to use optimistic locking versus pessimistic locking. Using optimistic locking on a hot flash-sale SKU results in 99% of requests throwing OptimisticLockException and failing. Conversely, using pessimistic locks on low-contention user profiles degrades database throughput by turning multi-core relational databases into sequential single-threaded bottlenecks.

Key Architectural Takeaways

  • Lost updates occur when concurrent transactions read the same initial state and subsequently overwrite each other without collision detection.
  • Optimistic Locking uses JPA '@Version' (integer or timestamp). Hibernate appends 'WHERE id = ? AND version = ?' on update. If row count is 0, it throws 'OptimisticLockException'.
  • Optimistic locking requires an explicit retry loop (e.g. Spring Retry or Resilience4j Retry) to reload the latest entity state and re-apply business logic.
  • Pessimistic Locking uses database row-level locks via 'SELECT ... FOR UPDATE' (in JPA: '@Lock(LockModeType.PESSIMISTIC_WRITE)'). Other transactions block until the holding transaction commits or rolls back.
  • Pessimistic locks risk database deadlocks if two transactions acquire rows in different orders. Always enforce deterministic ordering (e.g., sorting IDs ascending before locking).
  • Set query timeout ('jakarta.persistence.lock.timeout') on pessimistic locks to prevent indefinite thread blocking when downstreams stall.

1. The Mechanics of Optimistic Locking (@Version)

Optimistic locking places zero database-level locks on read. The table contains a version INT NOT NULL DEFAULT 0 column. When Hibernate updates the entity: 

UPDATE inventory_item 
SET quantity = ?, version = version + 1 
WHERE id = ? AND version = ?;

If another transaction updated the row first, the version has already incremented, so the UPDATE statement affects 0 rows. Hibernate detects this and immediately throws ObjectOptimisticLockingFailureException.

Crucial Architecture Rule: Optimistic locking alone does not fix the collision—it only detects it. The application must catch the exception and execute a Retry Loop that re-fetches the record with its new version and recalculates the balance.

2. The Mechanics of Pessimistic Locking (SELECT FOR UPDATE)

When write contention is extremely high (e.g., a ticket reservation system with 5,000 users attempting to buy 10 remaining tickets), optimistic locking causes excessive retry storms and CPU waste. Here, Pessimistic Locking is superior: 

@Lock(LockModeType.PESSIMISTIC_WRITE)
@QueryHints({@QueryHint(name = "jakarta.persistence.lock.timeout", value = "3000")})
@Query("SELECT i FROM InventoryItem i WHERE i.id = :id")
Optional<InventoryItem> findByIdForUpdate(@Param("id") UUID id);

The database engine (PostgreSQL/MySQL) acquires an exclusive row-level lock on the tuple. All subsequent transactions attempting to read or write with FOR UPDATE are suspended by the database until the first transaction completes.

3. Deadlock Prevention Strategy

If Transaction 1 locks Account A and wants Account B, while Transaction 2 locks Account B and wants Account A, a classic Deadlock occurs. PostgreSQL will detect the cycle after deadlock_timeout (typically 1s) and violently abort one transaction with SQLState 40P01.

Rule: When locking multiple rows in a single transaction, always sort the identifiers in ascending order before executing queries: 

List<UUID> sortedIds = ids.stream().sorted().toList();
List<Account> accounts = repo.findAllByIdInOrderByIdAscForUpdate(sortedIds);

Concurrency Defense: Optimistic (@Version) vs Pessimistic Locking 
package com.example.concurrency;

import jakarta.persistence.*;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Lock;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.jpa.repository.QueryHints;
import org.springframework.data.repository.query.Param;
import org.springframework.retry.annotation.Backoff;
import org.springframework.retry.annotation.Retryable;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Isolation;
import org.springframework.transaction.annotation.Transactional;

import java.util.Optional;
import java.util.UUID;

@Entity
@Table(name = "product_inventory")
class ProductInventory {
    @Id
    @GeneratedValue(strategy = GenerationType.UUID)
    private UUID id;

    @Column(nullable = false)
    private String sku;

    @Column(nullable = false)
    private int availableQuantity;

    // Optimistic lock version: incremented automatically by Hibernate
    @Version
    private Long version;

    public void deduct(int quantity) {
        if (this.availableQuantity < quantity) {
            throw new IllegalStateException("Insufficient stock for SKU: " + sku);
        }
        this.availableQuantity -= quantity;
    }

    public UUID getId() { return id; }
    public int getAvailableQuantity() { return availableQuantity; }
    public Long getVersion() { return version; }
}

interface ProductInventoryRepository extends JpaRepository<ProductInventory, UUID> {
    // Pessimistic Write Lock with 3-second timeout
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @QueryHints({@QueryHint(name = "jakarta.persistence.lock.timeout", value = "3000")})
    @Query("SELECT p FROM ProductInventory p WHERE p.sku = :sku")
    Optional<ProductInventory> findBySkuForUpdate(@Param("sku") String sku);

    Optional<ProductInventory> findBySku(String sku);
}

@Service
class InventoryService {
    private final ProductInventoryRepository repository;

    public InventoryService(ProductInventoryRepository repository) {
        this.repository = repository;
    }

    // Pattern A: Optimistic Locking with Automatic Retry on collision
    @Retryable(
        retryFor = { OptimisticLockException.class },
        maxAttempts = 3,
        backoff = @Backoff(delay = 50, multiplier = 2.0)
    )
    @Transactional
    public void deductStockOptimistic(String sku, int amount) {
        ProductInventory item = repository.findBySku(sku)
            .orElseThrow(() -> new IllegalArgumentException("SKU not found"));
        item.deduct(amount);
        // Hibernate issues: UPDATE ... WHERE id = ? AND version = ?
    }

    // Pattern B: Pessimistic Locking for Ultra-High Contention (Flash Sale)
    @Transactional(isolation = Isolation.READ_COMMITTED)
    public void deductStockPessimistic(String sku, int amount) {
        // Blocks at database level until lock acquired or timeout expires
        ProductInventory item = repository.findBySkuForUpdate(sku)
            .orElseThrow(() -> new IllegalArgumentException("SKU not found"));
        item.deduct(amount);
        // Lock released when transaction commits
    }
}
package com.example.concurrency

import jakarta.persistence.*
import org.springframework.data.jpa.repository.JpaRepository
import org.springframework.data.jpa.repository.Lock
import org.springframework.data.jpa.repository.Query
import org.springframework.data.jpa.repository.QueryHints
import org.springframework.data.repository.query.Param
import org.springframework.retry.annotation.Backoff
import org.springframework.retry.annotation.Retryable
import org.springframework.stereotype.Service
import org.springframework.transaction.annotation.Isolation
import org.springframework.transaction.annotation.Transactional
import java.util.UUID

@Entity
@Table(name = "product_inventory")
class ProductInventory(
    @Id
    @GeneratedValue(strategy = GenerationType.UUID)
    val id: UUID? = null,

    @Column(nullable = false)
    val sku: String = "",

    @Column(nullable = false)
    var availableQuantity: Int = 0
) {
    @Version
    var version: Long? = null

    fun deduct(quantity: Int) {
        check(availableQuantity >= quantity) { "Insufficient stock for SKU: $sku" }
        availableQuantity -= quantity
    }
}

interface ProductInventoryRepository : JpaRepository<ProductInventory, UUID> {
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @QueryHints(QueryHint(name = "jakarta.persistence.lock.timeout", value = "3000"))
    @Query("SELECT p FROM ProductInventory p WHERE p.sku = :sku")
    fun findBySkuForUpdate(@Param("sku") sku: String): ProductInventory?

    fun findBySku(sku: String): ProductInventory?
}

@Service
class InventoryService(private val repository: ProductInventoryRepository) {

    @Retryable(
        retryFor = [OptimisticLockException::class],
        maxAttempts = 3,
        backoff = Backoff(delay = 50, multiplier = 2.0)
    )
    @Transactional
    fun deductStockOptimistic(sku: String, amount: Int) {
        val item = repository.findBySku(sku)
            ?: throw IllegalArgumentException("SKU not found")
        item.deduct(amount)
    }

    @Transactional(isolation = Isolation.READ_COMMITTED)
    fun deductStockPessimistic(sku: String, amount: Int) {
        val item = repository.findBySkuForUpdate(sku)
            ?: throw IllegalArgumentException("SKU not found")
        item.deduct(amount)
    }
}

package com.example.concurrency;

import jakarta.persistence.*;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Lock;
import org.springframework.data.jpa.repository.Query;

import java.util.Optional;
import java.util.UUID;

@Entity
public class Wallet {
    @Id
    private UUID id;
    private long balance;

    @Version
    private Long version;

    public void debit(long amount) {
        if (balance < amount) throw new IllegalStateException("Insufficient funds");
        this.balance -= amount;
    }

    public UUID getId() { return id; }
    public long getBalance() { return balance; }
}

}
