Search Engines & CQRS: PostgreSQL FTS / pgvector vs. Elasticsearch

Target: Every e-commerce catalog eventually faces a brutal bottleneck: WHERE title LIKE '%wireless%' ignores standard B-Tree indexes and triggers full table scans across millions of products. In this final Part 2 lesson, we understand inverted indexes, compare PostgreSQL Full-Text Search (GIN + tsvector) & pgvector against dedicated Elasticsearch / OpenSearch clusters, and apply CQRS (separating transactional PostgreSQL writes from asynchronous search-index read projections via Kafka/Outbox).

📖 Primary Source Recommendation

Study the official authorities: PostgreSQL Full-Text Search (tsvector & GIN) and Elasticsearch Inverted Index Reference.

💡 Why This Matters in Production

Never spin up a 3-node Elasticsearch cluster if your catalog has 200,000 products—PostgreSQL's built-in GIN(to_tsvector(...)) gives sub-10ms stem-aware search with zero sync lag! Save Elasticsearch/OpenSearch for massive scale (10M+ docs, complex faceted aggregations, custom BM25 relevance tuning, and typo-tolerant fuzzy search) synced via CQRS + Outbox.

Key Architectural Takeaways

  • Why Leading-Wildcard LIKE '%term%' Dies: Standard B-Tree indexes sort left-to-right; a leading % forces PostgreSQL into a Seq Scan over every row on disk.
  • Inverted Indexes (Postgres GIN vs. Elasticsearch): Maps tokenized stems (e.g., "running" → "run") directly to matching document IDs. Add pg_trgm for substring/typo matching or pgvector (HNSW index) for AI semantic similarity directly inside PostgreSQL.
  • CQRS (Command Query Responsibility Segregation): Commands (POST /orders, catalog updates) write transactionally to PostgreSQL + Outbox; an async Kafka consumer updates Elasticsearch/OpenSearch read models—avoiding dual-write inconsistencies and accepting brief eventual consistency on search results.

-- V25__add_product_fts_gin_index.sql (Zero extra infra up to ~1M products!)
ALTER TABLE products
  ADD COLUMN search_vector tsvector
  GENERATED ALWAYS AS (to_tsvector('english', coalesce(title, '') || ' ' || coalesce(description, ''))) STORED;

CREATE INDEX CONCURRENTLY idx_products_search_gin ON products USING GIN (search_vector);

-- Query via: WHERE search_vector @@ websearch_to_tsquery('english', :query)

---
// ProductSearchProjector.java — CQRS Read-Side Sync via Kafka Outbox Event
@Component
public class ProductSearchProjector {
    private final ElasticsearchOperations elasticOps;

    public ProductSearchProjector(ElasticsearchOperations elasticOps) {
        this.elasticOps = elasticOps;
    }

    @KafkaListener(topics = "catalog.products.updated", groupId = "search-indexer")
    public void onProductUpdated(ProductChangedEvent event) {
        // Idempotent upsert by document ID prevents duplicate entries on Kafka replay
        elasticOps.save(new ProductSearchDoc(event.productId(), event.title(), event.priceCents()));
    }
}

Architectural Breakdown:

PostgreSQL GIN handles moderate full-text search with zero extra infrastructure, while CQRS + Kafka idempotent projection cleanly scales out to Elasticsearch when catalog volume demands it.
