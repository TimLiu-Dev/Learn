Fault Tolerance: Resilience4j Circuit Breakers, Retries & Bulkheads

Target: Prevent cascading distributed failures. Master Resilience4j Circuit Breakers (CLOSED, OPEN, HALF_OPEN), Exponential Backoff Retries with Jitter, and ThreadPool Bulkheads.

📖 Primary Source Recommendation

Study the official authority: Resilience4j Official User Guide: CircuitBreaker & Retry. Ground your learning in primary architecture rather than secondary summaries.

1. The Cascading Failure Nightmare

In microservices, Service A calls Service B, which calls Payment Gateway C. If Payment Gateway C slows down and takes 15 seconds per call:

  • All Service B threads block waiting for C. Service B crashes!
  • All Service A threads block waiting for B. Service A crashes!
  • Result: One slow third-party API knocks down your entire company's infrastructure!

2. The Circuit Breaker States (Like an Electrical Fuse)

CLOSED (Normal): Calls pass through normally. Tracks failure percentage. │ ▼ (If failure rate > 50% in last 100 calls) OPEN (Tripped!): Fails FAST immediately without calling downstream! Executes Fallback method. │ ▼ (After wait duration, e.g. 30 seconds) HALF_OPEN (Testing): Allows 10 probe calls to test if downstream recovered. ├─ If successful ──► Returns to CLOSED! └─ If fails ───────► Trips back to OPEN!

3. Production Dual Resilience4j Implementation

CircuitBreaker & Fallback Service 
package com.example.ecommerce.payment;

import io.github.resilience4j.circuitbreaker.annotation.CircuitBreaker;
import io.github.resilience4j.retry.annotation.Retry;
import org.springframework.stereotype.Service;

@Service
public class ResilientPaymentService {

    @CircuitBreaker(name = "paymentService", fallbackMethod = "paymentFallback")
    @Retry(name = "paymentService")
    public PaymentResponse processPayment(PaymentRequest request) {
        // Calls external payment gateway API over HTTP:
        return callExternalGateway(request);
    }

    // Fallback executed when Circuit is OPEN or call fails!
    public PaymentResponse paymentFallback(PaymentRequest request, Throwable ex) {
        System.err.println("Circuit OPEN! Fallback invoked due to: " + ex.getMessage());
        return new PaymentResponse(request.orderId(), "QUEUED_FOR_OFFLINE_PROCESSING");
    }

    private PaymentResponse callExternalGateway(PaymentRequest req) {
        // Real HTTP call...
        return new PaymentResponse(req.orderId(), "SUCCESS");
    }
}
package com.example.ecommerce.payment

import io.github.resilience4j.circuitbreaker.annotation.CircuitBreaker
import io.github.resilience4j.retry.annotation.Retry
import org.springframework.stereotype.Service

@Service
class ResilientPaymentService {

    @CircuitBreaker(name = "paymentService", fallbackMethod = "paymentFallback")
    @Retry(name = "paymentService")
    fun processPayment(request: PaymentRequest): PaymentResponse =
        callExternalGateway(request)

    fun paymentFallback(request: PaymentRequest, ex: Throwable): PaymentResponse {
        System.err.println("Circuit OPEN! Fallback invoked due to: ${ex.message}")
        return PaymentResponse(request.orderId, "QUEUED_FOR_OFFLINE_PROCESSING")
    }

    private fun callExternalGateway(req: PaymentRequest): PaymentResponse =
        PaymentResponse(req.orderId, "SUCCESS")
}

Lab 0023 Configure Resilience4j Fallback Handler
To Do

Goal: Implement the standard fallback signature in OrderResilienceHelper:

  • Method name: fallback(String orderId, Throwable ex)
  • Must return "FALLBACK_ORDER_" + orderId
Hint 1: Architectural Nudge
The fallback method must match the target method arguments PLUS a trailing Throwable parameter.
Hint 2: Syntax Signature
Signature: public static String fallback(String orderId, Throwable ex)
Hint 3: Concrete Snippet
public static String fallback(String orderId, Throwable ex) { return "FALLBACK_ORDER_" + orderId; }
💡 Complete Production Reference Solution
Java 21 Implementation:
package com.example.resilience;

public class OrderResilienceHelper {
    public static String fallback(String orderId, Throwable ex) {
        return "FALLBACK_ORDER_" + orderId;
    }
}
Kotlin 2.x Implementation:
package com.example.resilience

object OrderResilienceHelper {
    fun fallback(orderId: String, ex: Throwable): String =
        "FALLBACK_ORDER_$orderId"
}
Architectural Breakdown:

Resilience4j matches fallback methods by parameter types: they must accept the original method parameters followed by the Throwable exception.
