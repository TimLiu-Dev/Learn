Lesson 19: Accessibility Testing (Android & Web)

Over 1 billion people rely on screen readers, switch access, or large fonts — and accessibility regressions carry legal WCAG / EAA compliance risk. Senior SDETs automate 48dp touch targets, content descriptions, 4.5:1 contrast, and axe-core checks right in CI.

00 Automated A11y vs Manual Screen-Reader Reality

Automated Scanners Catch ~30–40% of A11y Bugs (Important!)
Tools like Android AccessibilityChecks and Web axe-core catch missing labels, low contrast, and tiny touch targets in CI. However, only human/TalkBack traversal checks catch illogical focus order or meaningless labels like "icon_1". Senior SDETs combine both!

01 Android Compose & Espresso AccessibilityChecks

Note the API distinction: for Jetpack Compose UI tests, use composeRule.enableAccessibilityChecks() (from androidx.compose.ui.test.junit4.accessibility) so Compose's semantics tree is audited directly. For XML Views / hybrid screens, enable Espresso's AccessibilityChecks.enable().setRunChecksFromRootView(true). 

@get:Rule val composeRule = createComposeRule()

@Before fun enableComposeA11y() {
  // Automatically checks touch targets (>=48dp), contrast, and speakable labels on Compose nodes!
  composeRule.enableAccessibilityChecks()
}
@Before fun enableViewA11y() {
  AccessibilityChecks.enable().setRunChecksFromRootView(true)
}
import AxeBuilder from "@axe-core/playwright";
test("checkout page has zero critical WCAG violations", async ({ page }) => {
  await page.goto("/checkout");
  const results = await new AxeBuilder({ page }).withTags(["wcag2a", "wcag2aa"]).analyze();
  expect(results.violations).toEqual([]);
});

02 The 4 Core Automated A11y Rules

(1) Every interactive icon/button has a meaningful speakable label; (2) Touch targets are ≥ 48dp × 48dp; (3) Normal text contrast ratio ≥ 4.5:1 (3.0:1 for large text); (4) Decorative icons are hidden from screen readers (contentDescription = null / aria-hidden) so TalkBack doesn't announce noise.
