1 · The six-step script

Interviewers grade your process as well as your final code. Use these steps on every problem in this course, easy ones included, so they become automatic. They are adapted from the Tech Interview Handbook cheatsheet.

  1. Clarify. Restate the problem in your own words. Ask at least two questions. How big can the input be? Can it be empty? Can it contain duplicates or negative numbers? Which output format do they want?
  2. Examples. Work through one normal example and one edge case by hand.
  3. Approach. Describe the brute-force solution and its complexity, then improve it. Get the interviewer to agree before you write any code.
  4. Code. Narrate as you type. Use clear names. If you take a shortcut, say so.
  5. Test. Don't say "done." Trace your example through the code line by line, then check the edge cases.
  6. Complexity. State the time and space complexity and explain why.

In this course, steps 1–3 are what you send me before you start coding. Steps 4–6 come with your code.

2 · Big-O in six rules

Big-O describes how the work grows as the input size n grows. Constant factors are ignored.

RuleExample
Drop constants and smaller terms3n + 10 → O(n). n² + n → O(n²)
Nested loops over the input multiplyfor i … for j … → O(n²)
Loops one after another add, so the biggest winsan O(n) pass, then an O(n log n) sort → O(n log n)
Halving the problem each step gives log nbinary search → O(log n)
Hash map and set operations are O(1) on averagemap[key], set.contains(x)
Space counts the extra memory you allocate, including the recursion stacka map of n entries → O(n). A recursion n deep → O(n)

Use the constraints to guess the target complexity

A rough guide is about 108 simple operations per second (USACO Guide). The input-size limit on a problem tells you which complexities are fast enough:

If n is up to……this is usually fast enough
~20O(2ⁿ) — try every subset (backtracking)
~5,000O(n²) — a double loop
~10⁵ to 10⁶O(n log n) or O(n) — sort, hash, pointers, window
huge (10⁹+)O(log n) or O(1) — binary search, math

Most LeetCode Mediums have n ≤ 10⁵. That's a strong hint that O(n²) will be too slow and you need something better.

3 · The Kotlin you'll use every day

This is the minimum set. The full list is in the Kotlin toolkit reference.

// Arrays: LeetCode gives you IntArray, a primitive int[] with no boxing
val nums = intArrayOf(3, 1, 2)
val zeros = IntArray(5)                 // [0, 0, 0, 0, 0]
for (i in nums.indices) { }             // 0 until nums.size
for (i in nums.size - 1 downTo 0) { }   // backwards

// Hash map and set
val count = HashMap<Int, Int>()
count[3] = count.getOrDefault(3, 0) + 1
val seen = HashSet<Int>()
if (!seen.add(7)) { /* add() returns false if 7 was already present */ }

// Stack and queue: use ArrayDeque for both
val stack = ArrayDeque<Int>()
stack.addLast(1); stack.removeLast()    // push / pop
val queue = ArrayDeque<Int>()
queue.addLast(1); queue.removeFirst()   // enqueue / dequeue

// Strings
val sb = StringBuilder()
sb.append('a').append("bc")             // build strings in O(total length)
val c = 'x'; c.isLetterOrDigit(); c - 'a'   // Char arithmetic gives an Int

Overflow trap. Int holds values up to about 2.1 × 10⁹. Sums or products of large values can overflow without any error. Use Long when that might happen, for example val total = 0L.

Quick check

A loop runs over the array, and inside it you call set.contains(x) on a HashSet. What is the total time?

  1. O(n²) total time
  2. O(log n) total time
  3. O(n) total time
  4. O(n log n) total time

n iterations, each doing O(1) average work, gives O(n). Replacing the HashSet with a List would make each lookup O(n) and the total O(n²).

A problem says 1 ≤ n ≤ 10⁵. Which approach is probably too slow?

  1. Compare all item pairs
  2. Sort, then scan once
  3. One pass, hash map
  4. Binary search each item

All pairs is about n²/2 ≈ 5 × 10⁹ operations, which is far more than the roughly 10⁸ per second rule allows. The other three are O(n log n) or better.

Which Kotlin type should you use as a stack?

  1. LinkedList<Int>()
  2. IntArray(n) only
  3. listOf<Int>()
  4. ArrayDeque<Int>()

ArrayDeque gives O(1) addLast and removeLast, and it also works as a queue. listOf is read-only, and LinkedList is slower in practice.

A recursive function calls itself once per level, n levels deep, and allocates nothing else. What is its space complexity?

  1. O(1) since no data
  2. O(n) for the stack
  3. O(log n) for calls
  4. O(n²) for the frames

Each pending call keeps a frame on the call stack, so n levels deep means O(n) space.

Running Sum of 1d Array Easy

  1. Each output value is the previous output value plus the current input value.
  2. Allocate the result with IntArray(nums.size), or think about whether you could reuse nums itself.
  3. If you overwrite nums in place, what does that do to the space complexity? Is changing the input acceptable? Asking that is a good clarifying question.

Concatenation of Array Easy

  1. The output has length 2n. Where does input index i appear in it?
  2. It appears twice: at i and at i + n.
  3. Try writing it with the IntArray(size) { index -> … } constructor in a single line.

Fizz Buzz Easy
