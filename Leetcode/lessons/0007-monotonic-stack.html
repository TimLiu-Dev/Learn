The idea

Many problems ask, for every element, "what is the next element to the right that is bigger (or smaller)?" The brute force scans forward from each index, which is O(n²).

Instead, walk left to right and keep a stack of indices that are still waiting for their answer. Their values are always in sorted order, which is why the stack is called monotonic. When a new element is bigger than the top, it is the answer for the top. Pop it, record the answer, and repeat. Then push the new index.

Every index is pushed once and popped at most once. So the whole loop does O(n) work, even though there is a while inside a for.

Reach for it when you see…

  • "next greater," "next smaller," "previous greater," or "previous smaller"
  • "how many days until," "how far until a warmer, taller, or cheaper one"
  • "largest rectangle," or how far each bar can extend left and right

Template: next greater element

val nextGreater = IntArray(nums.size) { -1 }  // -1 means "none to the right"
val stack = ArrayDeque<Int>()                // indices; their values decrease bottom to top
for (i in nums.indices) {
    while (stack.isNotEmpty() && nums[stack.last()] < nums[i]) {
        nextGreater[stack.removeLast()] = nums[i] // nums[i] answers the popped index
    }
    stack.addLast(i)                          // i now waits for its own answer
}

For the next smaller element, flip the comparison to >. The stack then holds increasing values.

Walkthrough: Daily Temperatures

Given daily temperatures, return for each day how many days you have to wait for a warmer one. Use 0 if no warmer day comes.

1 · Clarify

"Does 'warmer' mean strictly warmer? What do I return if no warmer day comes? How long is the input?" It means strictly warmer, the answer is 0 in that case, and there are up to 10⁵ days.

2 · Examples

[73, 74, 75, 71, 69, 72, 76, 73] → [1, 1, 4, 2, 1, 1, 0, 0]. Edge cases: [30, 30, 30] → [0, 0, 0] (equal is not warmer), and a single day → [0].

3 · Approach

Brute force: for each day, scan forward until you find a warmer one. That's O(n²). With n = 10⁵, that's too slow.

Key question: which days are still waiting? Exactly the ones that no later day has beaten yet. Keep them on a stack. When today is warmer than the top, today is the top's answer. Pop and record it, and keep going while today still beats the new top.

Why store indices, not temperatures? The answer is a distance, i − j, so you need the position. From an index you can always read the value with temperatures[j]. From a value you can't get the index back, especially when values repeat.

4 · Code 
class Solution {
    fun dailyTemperatures(temperatures: IntArray): IntArray {
        val answer = IntArray(temperatures.size)       // default 0 = no warmer day
        val waiting = ArrayDeque<Int>()                 // indices; temps decrease bottom to top
        for ((i, t) in temperatures.withIndex()) {
            while (waiting.isNotEmpty() && temperatures[waiting.last()] < t) {
                val j = waiting.removeLast()            // day j's warmer day is today
                answer[j] = i - j
            }
            waiting.addLast(i)
        }
        return answer
    }
}
5 · Test

Trace [30, 30, 30]. Each 30 is not strictly greater than the top, so nothing ever pops, and every answer stays 0. ✓ This is why the comparison is < and not <=.

Trace [30, 40, 50, 60]. Each day pops the one before it, so the answer is [1, 1, 1, 0]. ✓

6 · Complexity

Time O(n): each index is pushed once and popped at most once, so the while loop runs at most n times in total, not n times per day. Space O(n): a strictly decreasing input keeps every index on the stack.

Quick check

In Daily Temperatures, why does the stack hold indices instead of temperatures?

  1. Indices take less memory
  2. The answer is a distance
  3. Values could be negative
  4. Indices keep it sorted

The answer is i − j, so you need positions. You can always look up the value from an index, but not the other way around.

There's a while loop inside the for loop. What is the total time?

  1. O(n²) worst case total
  2. O(n log n) total time
  3. O(n) total, amortized
  4. O(k·n) for k pops each

Each index is pushed once and popped at most once, so across the whole run there are at most n pops. Counting total work instead of the worst single iteration is called amortized analysis.

To find the next smaller element for each index, the stack's values from bottom to top are…

  1. decreasing; pop while top < x
  2. increasing; pop while top < x
  3. decreasing; pop while top > x
  4. increasing; pop while top > x

A smaller x answers every larger value on top, so you pop while top > x. What remains below is smaller, so the stack increases from bottom to top.

Next Greater Element I Easy

  1. Start with the brute force: for each value in nums1, find it in nums2 and scan right. What does that cost?
  2. Run the template once over nums2. That gives every value in nums2 its next greater element.
  3. The values are distinct, so you can store those answers in a map from value to next greater. Then each nums1 query is one lookup.

Car Fleet Medium

  1. For each car, how long would it take to reach the target if it drove alone? Use Double for that time.
  2. A car can never pass the car ahead of it. Process cars from the one closest to the target to the one farthest away.
  3. A car that would arrive no later than the fleet just ahead of it catches up and joins that fleet. Otherwise it leads a new fleet. Keep the arrival times of the fleets on a stack.

Largest Rectangle in Histogram Hard Stretch

  1. Take one bar and use its full height. How far left and right can the rectangle stretch?
  2. It stretches until it hits a shorter bar on each side. So for every bar you need the previous smaller and the next smaller index.
  3. Use an increasing stack. When a bar gets popped because a shorter bar arrived at i, its right boundary is i and its left boundary is the new top of the stack. Think about how to flush the bars still on the stack at the end.
