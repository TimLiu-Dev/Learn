Container Internals From Scratch: Namespaces, cgroups v2 & OverlayFS

Demystify Docker and Kubernetes: there is no 'container' object in the Linux kernel—only Namespaces (visibility), cgroups v2 (resource caps), chroot/pivot_root, and OverlayFS (copy-on-write layers).

1. Android Developer → Linux Mental Bridge

Transferring Prior Knowledge

On Android, Linux cgroups throttle background app CPU/I/O, and mount namespaces isolate app storage views. Docker and rootless Podman simply orchestrate those exact same three Linux kernel primitives—which you can invoke manually via unshare!

2. Namespaces + cgroups v2 + OverlayFS = Container

Container Anatomy

A container is just a normal Linux process visible on the host's process table! Run unshare --pid --fork --uts --mount-proc bash to spawn an isolated namespace without Docker. Remember: namespaces isolate visibility, NOT resource usage—without cgroups v2 limits (like --memory/MemoryMax), one container fork bomb or memory leak starves the whole host!

example-01: Spawning a Namespace Manually & Inspecting Containers 
sudo unshare --pid --fork --uts /bin/bash   # Container from scratch!
podman ps                                    # Rootless OCI runtime view

3. Running Rootless OCI Containers Under systemd Quadlets

Modern 2027 Runtime

Modern Linux fleets favor rootless Podman (mapping container UID 0 to an unprivileged host user namespace) paired with minimal non-root Containerfiles (multi-stage builds, USER 10001) and systemd Quadlets (.container files under ~/.config/containers/systemd/ or /etc/containers/systemd/) that compile into native systemd units with cgroups v2 quotas.

example-02: Inspecting Rootless Containers & Host Processes Together 
podman ps   # OCI container inventory
ps aux      # Host kernel process view showing containers are normal processes

Real Outage Pattern: Container Escape via Shared Host `/var/run/docker.sock` Mount

A CI runner container wasn't marked --privileged, yet had -v /var/run/docker.sock:/var/run/docker.sock mounted to build images. Any build script could spawn a new sibling container mounting host /:/host as root! Use rootless Podman or BuildKit/Kaniko instead of exposing the root Docker socket.

Interview Q1

If asked 'what IS a Linux container under the hood?', how do you answer in 30 seconds?

Model Answer: A normal Linux process isolated by Namespaces (PID, NET, MNT, UTS, IPC, USER) for visibility, bounded by cgroups v2 for CPU/RAM/I/O limits, packaged on a copy-on-write OverlayFS rootfs, and restricted by seccomp + Capabilities + AppArmor/SELinux.

Interview Q2

What is the difference between `chroot` and `pivot_root`?

Model Answer: chroot changes the root path for a process without unmounting the old root (which privileged processes can escape); pivot_root swaps the mount namespace's root filesystem cleanly so containers can unmount the host root completely.
