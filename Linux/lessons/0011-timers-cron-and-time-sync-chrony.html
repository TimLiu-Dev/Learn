2. Scheduling with cron vs Modern systemd Timers

Periodic Jobs

A crontab line has 5 time fields: minute hour day-of-month month day-of-week (e.g., 0 2 * * * = 02:00 daily). Modern Linux favors paired foo.timer + foo.service units because timers capture logs in journald, support randomized jitter (RandomizedDelaySec=) to avoid thundering herds, and run missed jobs after downtime (Persistent=true).

example-01: Listing Crontabs & Active systemd Timers 
crontab -l              # Inspect user crontab entries
systemctl list-timers  # Inspect systemd timer schedules

3. Server Time Hygiene with timedatectl & chronyc

Clock Accuracy

Keep every production server timezone on UTC so logs across regions align without daylight-saving jumps. Verify NTP lock with timedatectl and offset precision with chronyc tracking.

example-02: Checking System Clock & NTP Stratum 
timedatectl        # Verify NTP service active & synchronized
chronyc tracking   # Check exact millisecond drift vs upstream NTP

Real Outage Pattern: Thundering Herd at Midnight Crushed the Artifact Server

500 build nodes all had 0 0 * * * /usr/local/bin/sync-sdk.sh in cron. Every night at 00:00:00 sharp, 500 concurrent downloads saturated the artifact server's NIC. Moving to a systemd timer with RandomizedDelaySec=15m smoothed the load spike completely.

Interview Q1

What happens to a `cron` job scheduled at 02:00 if the server is powered off at 01:55 and booted at 02:30?

Model Answer: Standard cron skips it completely. A systemd timer with Persistent=true records last run time and triggers the missed job upon boot.

Interview Q2

What breaks first when a Linux server's clock drifts by 10 minutes?

Model Answer: TLS/mTLS certificate validation, short-lived JWT/OIDC tokens, TOTP MFA codes, S3 signed URLs, and distributed trace ordering.
