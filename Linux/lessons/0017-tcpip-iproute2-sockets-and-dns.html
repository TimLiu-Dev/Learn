1. Android Developer → Linux Mental Bridge

Transferring Prior Knowledge

In Android you debug Retrofit HTTP failures on client networks. On Linux servers, you verify L3 routing tables (ip route), inspect L4 kernel socket states (ss -tulnp), and isolate DNS failures (dig + /etc/resolv.conf).

2. Modern Network Inspection with ip & ss -tulnp

L3/L4 Diagnostics

ss -tulnp (TCP, UDP, Listening, Numeric ports, Processes) queries kernel netlink directly and is orders of magnitude faster than deprecated netstat. Always inspect the Local Address column: 127.0.0.1:8443 accepts local loopback traffic ONLY (e.g., from Nginx reverse proxy), while 0.0.0.0:443 accepts traffic on all interfaces.

example-01: Inspecting Interfaces, Routes & Listening Sockets 
ip addr      # Network interfaces & CIDR IPs (10.20.0.45/24)
ip route     # Kernel routing table & default gateway
ss -tulnp    # Listening TCP/UDP sockets + owning PIDs

3. Tracing DNS (nsswitch.conf, dig) & Probing APIs (curl)

Name Resolution & L7

Linux checks /etc/nsswitch.conf (hosts: files dns) to decide order: first /etc/hosts, then DNS servers in /etc/resolv.conf (on Ubuntu, 127.0.0.53 is the local systemd-resolved stub). Test raw DNS directly with dig and HTTP endpoints with curl -I.

example-02: Checking DNS Config, Querying dig & Probing Local API 
cat /etc/nsswitch.conf
dig aegis.internal
curl -I http://127.0.0.1:8443/healthz

4. Inspecting Stub Resolvers with resolvectl & Split-DNS Domains

Modern Linux DNS

Seeing nameserver 127.0.0.53 in /etc/resolv.conf does NOT tell you which upstream DNS server actually answers queries! Modern Linux uses resolvectl status to reveal per-interface DNS servers, search domains (e.g. corporate VPN vs public internet), and cache hit rates, plus resolvectl query to trace what the stub resolver sees.

example-03: Tracing systemd-resolved & Upstream DNS Servers 
cat /etc/resolv.conf
resolvectl status
resolvectl query aegis.internal

Real Outage Pattern: App Container Bound to 127.0.0.1 Passed Local Healthchecks While Load Balancer Failed

A newly deployed telemetry service passed local curl 127.0.0.1:8443 checks inside the VM, yet the cloud load balancer marked the node unhealthy. Running ss -tulnp showed it listening on 127.0.0.1:8443 instead of behind Nginx or 0.0.0.0.

Interview Q1

How do you troubleshoot 'I cannot reach service X on port 8443 from host B to host A' step by step?

Model Answer: 1) On host A, run ss -tulnp | grep 8443 (is it listening, and on 0.0.0.0 vs 127.0.0.1?). 2) Test local curl on A. 3) Check host A firewall (nft list ruleset). 4) Check routing/DNS from B (dig, ip route, ping, nc -vz). 5) Capture packets via tcpdump.

Interview Q2

Which file controls whether Linux checks `/etc/hosts` before DNS?

Model Answer: /etc/nsswitch.conf (specifically the hosts: files dns line).
