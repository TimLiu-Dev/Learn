1. Android Developer → Linux Mental Bridge

Transferring Prior Knowledge

When you delete a file on Android/Linux while a running app still holds an open FileDescriptor, the directory name disappears—but the kernel keeps the disk blocks allocated until that process closes the FD! lsof exposes those invisible space hogs.

2. Why Deleting a 20 GB Log Didn't Free Any Space (lsof +L1)

Classic Senior Outage

If df -h reports 95% full while du -sh accounts for only 1 GB, a process is holding an open file descriptor to a deleted file! Also, trying to umount a busy volume triggers target is busy—use lsof +f -- /mount or fuser -vm /mount to find which PID holds it open.

example-01: Catching Deleted Open Files & Busy Mounts 
df -h                  # /var/lib/aegis shows 95% full
umount /var/lib/aegis  # Fails: target is busy
lsof +L1               # Reveals PID 1120 (aegis-api) holding 18GB deleted log!
fuser /var/lib/aegis   # Lists PIDs locking the mountpoint

3. LVM Layers (pvs/vgs/lvs) & Online Extension

Enterprise Storage

LVM adds a virtual abstraction layer: Physical Volumes (pvs) pool into Volume Groups (vgs), which carve out Logical Volumes (lvs). Adding -r to lvextend -r -L +5G /dev/vg0/data resizes both the block LV AND the filesystem cleanly online with zero downtime.

example-02: Inspecting LVM Hierarchy & Disk Latency 
pvs      # Physical disks/partitions
vgs      # Available free pool space
lvs      # Logical volumes
iostat   # Check await latency & %util

4. Automated Log Rotation (logrotate: postrotate vs copytruncate)

Outage Prevention

Why did PID 1120 end up holding an 18 GB deleted file? Because an external script removed/renamed the log without telling the daemon to reopen its FD! Proper /etc/logrotate.d/* rules rotate, compress, keep rotate 7 generations, and run a postrotate script signaling systemctl reload/SIGHUP (or use copytruncate carefully when daemons cannot reopen logs).

example-03: Dry-Running logrotate Configs Safely 
cat /etc/logrotate.d/aegis
logrotate -d /etc/logrotate.d/aegis   # Dry-run catches missing rotate/postrotate handlers!

Real Outage Pattern: Running rm on an Active 90 GB Log Made Debugging Worse

During a disk-full alert, an on-call dev ran rm /var/log/java/app.log. Disk usage stayed at 100%, and now ls couldn't even find the file anymore! Using lsof +L1 revealed the JVM PID holding the deleted inode; gracefully restarting the JVM (or next time using truncate -s 0 instead of rm) restored 90 GB instantly.

Interview Q1

How do you safely reclaim space from an actively written 50 GB log file without restarting the service?

Model Answer: Use truncate -s 0 /path/to/app.log (or : > /path/to/app.log) rather than rm, then configure logrotate with copytruncate or postrotate signal reload.

Interview Q2

Explain PV, VG, and LV in LVM.

Model Answer: Physical Volumes (PVs) are raw disks/partitions; Volume Groups (VGs) pool PVs into combined storage capacity; Logical Volumes (LVs) are virtual block partitions carved from a VG.
