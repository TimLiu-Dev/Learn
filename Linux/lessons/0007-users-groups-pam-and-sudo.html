1. Android Developer → Linux Mental Bridge

Transferring Prior Knowledge

On Android, the Linux kernel assigns each installed app its own unique UID (like u0_a142) so apps cannot read each other's files. Server Linux uses the exact same UID/GID kernel isolation for humans and system daemons.

Android / App Concept GNU/Linux Server Equivalent Why Senior Linux Engineers Care
Per-App Android UID (u0_a142)Dedicated service UID (aegis, www-data)Every service gets its own locked account with /usr/sbin/nologin.

2. Anatomy of /etc/passwd, /etc/shadow & Service Users

Identity Model

The kernel knows only numeric UIDs and GIDs—/etc/passwd maps UIDs to names, home directories, and login shells, while hashed passwords live in root-only /etc/shadow (mode 0640). Production services use useradd -r -s /usr/sbin/nologin svcuser so nobody can SSH into them interactively.

example-01: Inspecting UIDs, Groups & Passwd Entries 
id              # Current UID, primary GID, and supplementary groups
groups          # Quick list of group memberships
cat /etc/passwd # Account definitions (notice nologin on system accounts)
cat /etc/group

3. Safe Delegation with sudo & visudo

Privilege Escalation

Never edit /etc/sudoers with a raw editor—a syntax typo locks everyone out of sudo! Always use visudo or drop validated snippets into /etc/sudoers.d/. Check what commands your user is permitted to run with sudo -l.

example-02: Auditing sudo Privileges & Creating a Locked Service Account 
sudo -l
sudo useradd -r -s /usr/sbin/nologin metrics-agent
tail -n 2 /etc/passwd
Group Membership Pitfall: Missing -a in usermod -aG
Running usermod -G docker alice without -a (append) strips Alice from all her other supplementary groups—including sudo! Always pass usermod -aG.

Real Outage Pattern: Locked Out of Production via Raw Edit to /etc/sudoers

On a cloud VM with SSH root login disabled, an engineer edited /etc/sudoers with vim directly, left a trailing typo, and logged out. Every subsequent sudo command failed with a parse error, forcing an emergency single-user rescue mount via the cloud serial console.

Interview Q1

What is the difference between `su`, `su -`, and `sudo -i`?

Model Answer: su switches user while keeping the caller's environment and directory; su - simulates a full login shell with target user's env/HOME; sudo -i authenticates with your password (audited) and opens a root login shell.

Interview Q2

Why are password hashes stored in `/etc/shadow` instead of `/etc/passwd`?

Model Answer: Tools like ls -l and ps must read /etc/passwd to map UIDs to usernames, so it must be world-readable (0644). Moving hashes to root-only /etc/shadow stops local users from offline brute-forcing hashes.
