1. Android Developer → Linux Mental Bridge

Transferring Prior Knowledge

On Android you use Android Studio's CPU Profiler / Perfetto traces to spot hot functions. On Linux servers, perf builds CPU FlameGraphs, sar tracks historical CPU/memory/I/O, and eBPF lets you run sandboxed, verifier-checked bytecode probes right inside the Linux kernel!

2. Systematic Triage: Utilization, Saturation & Errors (USE)

Methodology

Instead of random guessing when a box feels slow, check Utilization (% busy), Saturation (queue depth/runqueue wait), and Errors for every resource (CPU, Memory, Disk, Network). Check historical spikes with sar.

example-01: Sampling CPU Hotspots with perf, sar & bpftrace 
sar -u           # Historical CPU utilization
sudo perf top    # Live CPU cycle hotspots (user + kernel functions)
sudo bpftrace -e 'tracepoint:raw_syscalls:sys_enter { @[comm] = count(); }'

Real Outage Pattern: High CPU Traced to Uncached Regex Re-Compilation in 60 Seconds via perf

API latency tripled after a minor release while DB and network looked idle. Running perf record -F 99 -g -p <pid> -- sleep 15 showed 68% of CPU cycles inside regcomp()—a request handler was compiling a complex regex on every HTTP request instead of once at startup.

Interview Q1

Walk through Brendan Gregg's USE Method for troubleshooting a slow Linux server.

Model Answer: For every primary resource (CPU, Memory, Storage I/O, Network), check Utilization (% busy), Saturation (queued work like CPU runqueue or disk await), and Errors (dmesg disk errors, NIC drops, OOMs).

Interview Q2

Why does `load average` of `8.0` mean healthy capacity on one host and total overload on another?

Model Answer: Load average counts runnable + uninterruptible (D) tasks. On a 32-core host, load 8.0 is 25% utilized; on a 2-core host, load 8.0 means severe saturation (or blocked disk I/O!).
