2. Isolating SYN Drops & Resets with tcpdump

Packet Capture

tcpdump -nn -i any host 10.20.0.14 and port 443 settles 'is it the network or the app?' debates permanently. Three flags matter immediately: [S] = TCP SYN, [S.] = SYN-ACK, [R] = RST (immediate refusal). Only seeing [S] repeated with zero [S.] means a firewall or route is silently dropping packets!

example-01: Capturing Handshakes & Checking WireGuard 
sudo tcpdump -nn -i eth0 port 443   # -nn skips slow DNS/port name lookups
sudo wg show                        # Inspect WireGuard peers & endpoints

3. WireGuard Peers & Safe NFSv4 Mount Options

Tunnels & Network FS

Unlike legacy IPSec/OpenVPN, WireGuard uses ~4,000 lines of kernel code over UDP (default 51820/udp) with simple public-key peering. For NFSv4 shared storage (2049/tcp), remember: a hard NFS mount retries forever if the NFS server dies—putting reading processes into unkillable state D!

example-02: Tracing Network Hops with traceroute 
traceroute 10.20.0.10   # Identify L3 hop latencies

Real Outage Pattern: Dead NFS Mount Froze Every Monitoring Check & SSH Login

An NFS backup server went offline. Every node with a hard NFS mount inside /etc/fstab hung whenever any monitoring agent ran df -h, stacking dozens of unkillable D-state processes. Using umount -lf (lazy unmount) and moving backups to asynchronous rsync/object storage prevented cascade hangs.

Interview Q1

How do you distinguish a firewall `DROP` from a closed port (`REJECT` or stopped daemon) using `tcpdump`?

Model Answer: With DROP, you see outgoing [S] retries and zero response. With a closed port or REJECT, you see an immediate [R] (RST) or ICMP unreachable packet back.

Interview Q2

Why does `df -h` sometimes hang indefinitely on a Linux box?

Model Answer: df calls statfs() on every mounted filesystem—if an NFS or CIFS mount is dead and mounted hard, df blocks in state D.
