1. Android Developer → Linux Mental Bridge

Transferring Prior Knowledge

On Android, init.rc files start core daemons and logcat streams structured logs. On modern Linux distributions, systemd (PID 1) manages service dependency graphs, auto-restarts, cgroups v2 quotas, and journald binary logs.

2. Operating Services via systemctl & Anatomy of a .service Unit

Service Control

A .service unit has three sections: [Unit] (description & ordering like After=network-online.target), [Service] (how to run, restart, and sandbox), and [Install] (which boot target enables it, usually multi-user.target). Remember: start runs now; enable starts on boot; enable --now does both!

example-01: Inspecting Units, Unit Files & Reloading systemd 
systemctl status aegis-api.service
cat /etc/systemd/system/aegis-api.service
systemctl list-units

3. Filtering Service Logs with journalctl

Structured Logs

Instead of hunting across dozens of text files, journalctl queries indexed logs across boot boundaries: -u <unit> scopes to one service, -p err filters errors and above, -f tails live, and --since "10 minutes ago" narrows incident windows.

example-02: Querying journald by Unit & Priority 
journalctl -u nginx   # Logs for nginx.service only
journalctl -p err     # Error-severity logs across all units

Real Outage Pattern: Silent Failure Because systemd Unit Used After=network.target

A startup database client bound to a DHCP IP failed on reboot even though After=network.target was set. On Linux, network.target only means the network stack initialized—not that an IP address is assigned! Switching to After=network-online.target + Wants=network-online.target fixed boot race conditions permanently.

Interview Q1

How do you override one setting in a vendor-installed systemd service without touching its package file?

Model Answer: Run systemctl edit <service>, which creates an override drop-in at /etc/systemd/system/<service>.d/override.conf and survives package upgrades.

Interview Q2

What does `systemd-analyze blame` show you?

Model Answer: It ranks every unit by initialization time during boot, letting you pinpoint slow startup bottlenecks.
