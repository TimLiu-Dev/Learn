MVI Core Loop

The compressed version of Lesson 1. Re-read this before an interview, not the lesson.

The loop

View --Intent--> StateHolder --(reducer)--> State --> View

Events flow up as Intent; state flows down as one State object. Same direction as Google's unidirectional data flow (UDF), tightened to a single channel each way.

Vocabulary

TermMeans
IntentA sealed type describing one thing the user/system wants to happen. Not an Android Intent — unfortunate name collision.
StateOne immutable data class describing the entire screen at an instant.
ReducerThe function (oldState, Intent) -> newState. Close to pure — easy to unit test.
State holderGoogle's general term for whatever owns the state (usually still a ViewModel in MVI-on-Android).
SSOTSingle Source of Truth — exactly one object is authoritative for the screen's state.
UDFUnidirectional Data Flow — events up, state down, never the reverse.

MVVM → MVI, at a glance

MVVMMVI
State shapeSeveral independent flowsOne StateFlow<State>
InputSeveral public methodsOne onIntent(Intent) entry point
Disagreeing statePossibleReduced with one State object; fully prevented once State is a sealed hierarchy
TestingAssert multiple flows post-callAssert one state transition

sealed interface Intent { /* ... */ }
data class State(/* ... */)

class Store : ViewModel() {
    private val _state = MutableStateFlow(State())
    val state: StateFlow<State> = _state.asStateFlow()

    fun onIntent(intent: Intent) { /* reduce -> _state.update { ... } */ }
}

Why it matters (interview framing)

  • SSOT — no reasoning about combinations of flows.
  • Testability — reducer ≈ pure function.
  • Predictability — every change goes through one funnel; replayable for debugging.
