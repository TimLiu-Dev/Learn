One-Off Events

Compressed version of Lesson 3.

The problem in one line

StateFlow replays its latest value to every new collector, so an event stored there (toast, navigation) fires again after rotation. State is what is true now. An event is something that happened.

Two fixes

A: Reduce to StateB: Effect Channel
ShapeuserMessage: String? in State + MessageShown IntentChannel<Effect>(BUFFERED).receiveAsFlow()
Can it be lost?NoRarely, between receive and handle
Reducer-testable?YesNo
Main costA reset/acknowledge for every eventA second stream and lifecycle-aware collection
Backed byGoogle's UI events guideCommon practice; Orbit postSideEffect

A: skeleton

// State carries the fact; UI acknowledges via an Intent
state.userMessage?.let { msg ->
    LaunchedEffect(msg) {
        snackbarHost.showSnackbar(msg)
        viewModel.onIntent(Intent.MessageShown)
    }
}

B: skeleton

private val _effects = Channel<Effect>(Channel.BUFFERED)
val effects = _effects.receiveAsFlow()

LaunchedEffect(viewModel, lifecycleOwner) {
    lifecycleOwner.repeatOnLifecycle(Lifecycle.State.STARTED) {
        withContext(Dispatchers.Main.immediate) {
            viewModel.effects.collect { /* handle */ }
        }
    }
}

Rules of thumb

  • Never use SharedFlow(replay = 0) for events. It drops them silently when nothing is collecting.
  • Use receiveAsFlow(), not consumeAsFlow(). The latter is meant for a single collection, and it cancels the channel when that collector is cancelled.
  • If losing the event would be a bug, make it State. If it's cosmetic, a Channel is defensible. This is a synthesis, not official guidance.
  • Present it in interviews as a trade-off, and mention both approaches.
