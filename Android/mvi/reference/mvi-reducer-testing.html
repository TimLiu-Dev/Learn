Reducer & Testing

Compressed version of Lesson 2 and Lesson 4.

The full pipeline

View --Intent--> ViewModel --(side effect)--> Result --reduce()--> State --> View

Intent triggers a side effect (not a state change). The side effect's outcome becomes a Result. reduce(Result): State is a pure function — the only place State is actually computed.

Vocabulary addition

TermMeans
ResultA sealed type describing the outcome of a side effect (e.g. network call) — what happened, not what should happen.
Reducer(Result) -> State (or (State, Result) -> State for screens where the new state depends on the old one too). Pure — no coroutines, no I/O.

Minimal shape

sealed interface Result { /* Loading / Loaded / Failed */ }
sealed interface State { /* Loading / Success / Error */ }

fun reduce(result: Result): State = when (result) {
    is Result.Loading -> State.Loading
    is Result.Loaded  -> State.Success(result.data)
    is Result.Failed  -> State.Error(result.message)
}

With memory: (State, Result) -> State

From Lesson 4. The same Result can mean different things depending on what's on screen, so real reducers take the current state too:

fun reduce(state: State, result: Result): State = when (result) {
    Result.Loading -> when (state) {
        is State.Success -> state.copy(isRefreshing = true)   // keep data
        else -> State.Loading
    }
    is Result.Failed -> when (state) {
        is State.Success -> state.copy(isRefreshing = false, userMessage = result.message)
        else -> State.Error(result.message)
    }
    ...
}

private fun dispatch(result: Result) = _state.update { reduce(it, result) }
  • update { } is atomic but may retry the lambda, which is one more reason the reducer must be pure.
  • Put fields where they make sense (isRefreshing inside Success) so impossible combinations can't be represented.
  • Racing loads: cancel the previous Job (or use flatMapLatest). The reducer can't fix ordering.
  • Process death: save small inputs (IDs) in SavedStateHandle and reload. Don't persist the whole State.

Testing template

@Test
fun `result maps to expected state`() {
    assertEquals(State.Success(data), reduce(Result.Loaded(data)))
}

No runTest, no fake dispatcher, no mocked repository — the reducer has no dependencies to fake.

Why it matters (interview framing)

  • Separation of effect from transition — side effects (network, DB) stay in the ViewModel; the pure reducer is the only thing that decides the next State.
  • Trivial unit tests — every branch is a one-line assertion.
  • Compiler-enforced UI coverage — a sealed State forces every consuming when to handle every case, at compile time.
