One-Off Events: Toasts, Snackbars & Navigation

MVI says the screen is one State. But "show a toast" and "go to Home" aren't facts about the screen. They're things that happen. Where do they go?

Interviewers ask this a lot, because it's where MVI's "single state" promise meets messy UI. There are two defensible answers. A strong answer names both and explains the trade-off.

The bug, in MVVM you've probably written

private val _toast = MutableStateFlow<String?>(null)
val toast: StateFlow<String?> = _toast

fun save() = viewModelScope.launch {
    repo.save(profile)
    _toast.value = "Saved!"
}

// UI
val toast by viewModel.toast.collectAsStateWithLifecycle()
toast?.let { msg -> LaunchedEffect(msg) { snackbarHost.showSnackbar(msg) } }

Rotate the phone after saving and "Saved!" shows again. The composition is rebuilt, the new collector gets the current value (still "Saved!"), and the effect runs again. StateFlow is working as designed: it holds the latest value. That's correct for state and wrong for an event.

In the LiveData era the usual workaround was a SingleLiveEvent subclass that delivers each value only once. If an interviewer mentions it, this is the same problem.

Answer A: reduce the event to State (Google's official guidance)

Google's guide says it plainly: "ViewModel events should always result in a UI state update." Rephrase the event as a fact: "a message is currently on screen." When the UI has shown it, the UI says so, and in MVI that acknowledgement is just another Intent.

data class Success(
    val user: User,
    val userMessage: String? = null      // "a message is on screen" is a fact
) : ProfileState

sealed interface ProfileIntent {
    data class Load(val id: String) : ProfileIntent
    object Save : ProfileIntent
    object MessageShown : ProfileIntent  // UI: "I showed it"
}

// UI
(state as? ProfileState.Success)?.userMessage?.let { msg ->
    LaunchedEffect(msg) {
        snackbarHost.showSnackbar(msg)
        viewModel.onIntent(ProfileIntent.MessageShown)
    }
}

Now rotation is correct. If the user rotates mid-snackbar, the LaunchedEffect is cancelled before MessageShown goes out, so the message is still in State and shows again. The user hadn't finished seeing it, so that's the right outcome. Because the event's whole lifecycle goes through the reducer, you can test it with plain JUnit, just like in Lesson 2:

@Test
fun `message is cleared once shown`() {
    val before = ProfileState.Success(ada, userMessage = "Saved!")
    assertEquals(
        ProfileState.Success(ada),
        reduce(before, ProfileResult.MessageCleared)
    )
}

Notice that reduce now takes the current state as well. You can't clear one field without knowing the others. Lesson 2 skipped this on purpose, and Lesson 4 covers it properly.

The cost: every event needs a reset. If you forget MessageShown, the toast repeats. If you forget to reset a "navigate to Home" flag, the user can get bounced back to Home every time they return. Critics call this flag bloat (Nek.12's rebuttal).

Answer B: a separate effect stream (a Channel)

Many teams and libraries keep events out of State and send them down a second, one-shot pipe. Orbit MVI calls these side effects (postSideEffect / collectSideEffect).

sealed interface ProfileEffect {
    data class ShowMessage(val text: String) : ProfileEffect
    object NavigateHome : ProfileEffect
}

private val _effects = Channel<ProfileEffect>(Channel.BUFFERED)
val effects: Flow<ProfileEffect> = _effects.receiveAsFlow()
// in save():  _effects.send(ProfileEffect.ShowMessage("Saved!"))

// UI
LaunchedEffect(viewModel, lifecycleOwner) {
    lifecycleOwner.repeatOnLifecycle(Lifecycle.State.STARTED) {
        withContext(Dispatchers.Main.immediate) {
            viewModel.effects.collect { effect -> /* show / navigate */ }
        }
    }
}

Why a Channel and not a SharedFlow? A channel buffers an event until someone receives it, and each event goes to exactly one collector. A SharedFlow(replay = 0) with no subscriber (say, the app is in the background) drops the event silently.

The cost: it isn't airtight. The UI can receive an event and get cancelled (by a configuration change) before it handles it, and then the event is gone. Collecting on Dispatchers.Main.immediate makes that window very small, which is Roman Elizarov's suggested workaround. Manuel Vivo (Google) asked for a real guarantee in kotlinx.coroutines #2886 in 2021, and that issue is still open. These events also bypass the reducer, so reducer tests can't cover them.

The interview answer

A: Reduce to StateB: Effect Channel
Can it be lost?No. It sits in State until acknowledged.Rarely, in the receive→handle window.
Reducer-testable?YesNo, it lives outside the reducer
Main costAn acknowledge Intent for every eventA second stream and lifecycle-aware collection
Who backs itGoogle's official architecture guideCommon in practice; Orbit's side effects

A useful rule of thumb (my synthesis, not an official rule): if losing the event would be a bug, make it State. A payment result or a "your session expired" redirect belongs in State. If losing it would only be cosmetic, like a "Copied!" toast, a Channel is a defensible choice. Present this as a trade-off, not as dogma. Interviewers are checking whether you can see both sides.

After this lesson, you can explain why a StateFlow toast replays on rotation, show both fixes in MVI shape (acknowledge-Intent and effect Channel), and pick between them using the "would losing it be a bug?" test.

Drill: say it out loud

Close the code above. Out loud, in under 60 seconds, answer: "In an MVI app, how do you handle one-off events like navigation or a snackbar?" Then compare your answer with the model answer.

Reveal model answer

"A one-off event can't be plain state on a StateFlow, because the latest value replays to every new collector and the toast shows again after rotation. There are two standard fixes. Google's guidance is to reduce the event to state: something like userMessage in the State, with the UI sending a MessageShown intent once it's displayed. It can't be lost and it's testable in the reducer, but every event needs a reset. The alternative is a separate effect stream, usually a buffered Channel collected on Main.immediate. That's what Orbit's side effects look like. It's more ergonomic, but there's a small window where an event can be lost. I use state for anything where losing it would be a bug, like a payment result, and I'm fine with a Channel for cosmetic toasts."
