Build a Login Screen, MVI-Style, From Scratch

No new theory. You'll put Lessons 1–4 together in Android Studio on a different screen, so you have to use the pattern rather than recognise it. The JUnit tests tell you when you've got it right.

A login form is a common take-home and whiteboard exercise in Android interviews. If you can build this one cold, you can build the one they give you.

How to use this lesson: do each step yourself before opening "Reveal". If the reveal doesn't match your version, that's fine as long as the tests pass. If you want a code review, paste your version to me.

The spec

  • Email and password fields. "Log in" is enabled only when the email contains @ and the password has at least 8 characters.
  • While the request is in flight, the button shows a spinner and a double-tap must not send two requests.
  • On failure, show the error and keep what the user typed. Typing again clears the error.
  • On success, navigate away. Per Lesson 3's rule, losing this event would be a bug, so it goes in State.

Use this fake repository so you don't need a backend:

class AuthException(message: String) : Exception(message)

interface AuthRepository {
    suspend fun login(email: String, password: String)  // throws AuthException
}

class FakeAuthRepository : AuthRepository {

        println("login() called")          // count these when you double-tap

Step 1: the contract (State, Intent, Result)

Write the three types. Decide which parts are a data class and which are sealed. Rule of thumb: use sealed for states that exclude each other and a data class for fields that exist together.

Reveal step 1 
data class LoginState(
    val email: String = "",
    val password: String = "",
    val submit: SubmitStatus = SubmitStatus.Idle,
) {
    val canSubmit: Boolean
        get() = "@" in email && password.length >= 8 &&
                submit != SubmitStatus.InFlight
}

sealed interface SubmitStatus {
    object Idle : SubmitStatus
    object InFlight : SubmitStatus
    data class Failed(val message: String) : SubmitStatus
    object LoggedIn : SubmitStatus
}

sealed interface LoginIntent {
    data class EmailChanged(val value: String) : LoginIntent
    data class PasswordChanged(val value: String) : LoginIntent
    object Submit : LoginIntent
}

sealed interface LoginResult {
    data class EmailUpdated(val value: String) : LoginResult
    data class PasswordUpdated(val value: String) : LoginResult
    object SubmitStarted : LoginResult
    object SubmitSucceeded : LoginResult
    data class SubmitFailed(val message: String) : LoginResult
}

The email and password exist in every status, so LoginState is a data class. Idle, in flight, failed and logged in exclude each other, so SubmitStatus is sealed and sits inside it. Like isRefreshing in Lesson 4, the sealed part lives where it makes sense. canSubmit is a derived property, the same idea as canBookmarkNews in Google's UI layer guide. Because it's computed from the other fields, it can't get out of sync with them.

Step 2: the reducer (test first)

Paste these tests into src/test and run them. They should fail. Then write reduce(state: LoginState, result: LoginResult): LoginState until they all pass.

class LoginReducerTest {
    private val filled = LoginState(email = "ada@x.io", password = "correct-horse")

    @Test fun `typing email updates only the email`() =
        assertEquals(LoginState(email = "a"), reduce(LoginState(), LoginResult.EmailUpdated("a")))

    @Test fun `submit started puts the form in flight`() =
        assertEquals(SubmitStatus.InFlight, reduce(filled, LoginResult.SubmitStarted).submit)

    @Test fun `cannot submit while in flight`() =
        assertFalse(reduce(filled, LoginResult.SubmitStarted).canSubmit)

    @Test fun `failure keeps what the user typed`() = assertEquals(
        filled.copy(submit = SubmitStatus.Failed("Wrong password")),
        reduce(filled.copy(submit = SubmitStatus.InFlight), LoginResult.SubmitFailed("Wrong password"))
    )

    @Test fun `typing after a failure clears the error`() = assertEquals(
        SubmitStatus.Idle,
        reduce(filled.copy(submit = SubmitStatus.Failed("x")), LoginResult.PasswordUpdated("y")).submit
    )

    @Test fun `success marks the user logged in`() =
        assertEquals(SubmitStatus.LoggedIn, reduce(filled, LoginResult.SubmitSucceeded).submit)
}
Reveal step 2 
fun reduce(state: LoginState, result: LoginResult): LoginState = when (result) {
    is LoginResult.EmailUpdated ->
        state.copy(email = result.value, submit = clearFailure(state.submit))
    is LoginResult.PasswordUpdated ->
        state.copy(password = result.value, submit = clearFailure(state.submit))
    LoginResult.SubmitStarted   -> state.copy(submit = SubmitStatus.InFlight)
    LoginResult.SubmitSucceeded -> state.copy(submit = SubmitStatus.LoggedIn)
    is LoginResult.SubmitFailed -> state.copy(submit = SubmitStatus.Failed(result.message))
}

private fun clearFailure(status: SubmitStatus): SubmitStatus =
    if (status is SubmitStatus.Failed) SubmitStatus.Idle else status

These are six behaviours of the screen, tested without a ViewModel, coroutines or mocks. That's the pay-off from Lesson 2.

Step 3: the ViewModel

Write LoginViewModel(auth: AuthRepository) with one onIntent entry point. Typing Intents have no side effect, so they go straight to a Result. Submit runs the network call. Make sure a double-tap can't send two requests.

Reveal step 3 
class LoginViewModel(private val auth: AuthRepository) : ViewModel() {

    private val _state = MutableStateFlow(LoginState())
    val state: StateFlow<LoginState> = _state.asStateFlow()

    fun onIntent(intent: LoginIntent) {
        when (intent) {
            is LoginIntent.EmailChanged    -> dispatch(LoginResult.EmailUpdated(intent.value))
            is LoginIntent.PasswordChanged -> dispatch(LoginResult.PasswordUpdated(intent.value))
            LoginIntent.Submit             -> submit()
        }
    }

    private fun submit() {
        val current = _state.value
        if (!current.canSubmit) return             // double-tap guard
        dispatch(LoginResult.SubmitStarted)        // synchronous: the 2nd tap sees InFlight
        viewModelScope.launch {
            val result = try {
                auth.login(current.email, current.password)
                LoginResult.SubmitSucceeded
            } catch (e: AuthException) {
                LoginResult.SubmitFailed(e.message ?: "Login failed")
            }
            dispatch(result)
        }
    }

    private fun dispatch(result: LoginResult) = _state.update { reduce(it, result) }
}

The double-tap guard works because update runs synchronously on the main thread before launch. The second tap reads canSubmit == false and returns. It catches AuthException specifically, not Exception: a broad catch would also swallow the CancellationException that coroutines use to stop work.

Step 4: the Compose UI

Split it in two. One composable connects to the ViewModel. The other is stateless and takes only (state, onIntent). This is state hoisting taken to its MVI conclusion: the whole screen depends on one value plus one callback.

Reveal step 4 
@Composable
fun LoginRoute(viewModel: LoginViewModel, onLoggedIn: () -> Unit) {
    val state by viewModel.state.collectAsStateWithLifecycle()
    val currentOnLoggedIn by rememberUpdatedState(onLoggedIn)

    LaunchedEffect(state.submit) {
        if (state.submit == SubmitStatus.LoggedIn) currentOnLoggedIn()
    }
    LoginScreen(state = state, onIntent = viewModel::onIntent)
}

@Composable
fun LoginScreen(state: LoginState, onIntent: (LoginIntent) -> Unit) {
    Column(Modifier.padding(24.dp), verticalArrangement = Arrangement.spacedBy(12.dp)) {
        OutlinedTextField(
            value = state.email,
            onValueChange = { onIntent(LoginIntent.EmailChanged(it)) },
            label = { Text("Email") }
        )
        OutlinedTextField(
            value = state.password,
            onValueChange = { onIntent(LoginIntent.PasswordChanged(it)) },
            label = { Text("Password") },
            visualTransformation = PasswordVisualTransformation()
        )
        (state.submit as? SubmitStatus.Failed)?.let {
            Text(it.message, color = MaterialTheme.colorScheme.error)
        }
        Button(onClick = { onIntent(LoginIntent.Submit) }, enabled = state.canSubmit) {
            if (state.submit == SubmitStatus.InFlight)
                CircularProgressIndicator(Modifier.size(18.dp), strokeWidth = 2.dp)
            else Text("Log in")
        }
    }
}

Look at that preview: every screen state is just a value, so you can preview or screenshot-test any state without a ViewModel. That's a strong point to raise in an interview. Navigation uses state, as in Lesson 3. The login screen is normally popped off the back stack after success, so Google's back-stack caveat doesn't apply here.

Step 5: check it in the emulator

  1. Rotate after typing. Both fields should survive, because the ViewModel outlives rotation.
  2. Double-tap "Log in" quickly. Logcat should show exactly one login() called.
  3. Enter a wrong password. The error should appear and the email should stay. Type one character and the error should disappear.
  4. Enter correct-horse. The app should navigate once, not repeatedly.
  5. Stretch goal (Lesson 4): put the app in the background, kill the process (adb shell am kill <your.package>) and reopen it. The email is gone. Make it survive using SavedStateHandle. Save the email only, and think about why you shouldn't save the password.
After this lesson, you have a working MVI screen you built yourself. It has a contract, a reducer with six passing tests, a ViewModel with one entry point and a double-tap guard, and a stateless Compose UI with previews. This is the shape you'd draw at a whiteboard.
