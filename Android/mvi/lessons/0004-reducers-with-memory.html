Reducers With Memory: (State, Result) → State

Lesson 2's reducer only looked at the new Result, so it forgot everything that was already on screen. Real screens need the old state, and this lesson shows how to give it to the reducer.

The bug: pull-to-refresh wipes the screen

Recall Lesson 2's reducer:

fun reduce(result: ProfileResult): ProfileState = when (result) {
    is ProfileResult.Loading -> ProfileState.Loading
    ...
}

The user is looking at their profile and pulls to refresh. The ViewModel reduces ProfileResult.Loading, and the profile is replaced by a full-screen spinner. If the refresh then fails, they get a full-screen error in place of data they could see a second ago. The reducer had no way to know there was a profile on screen, because it was never given the current state.

The fix: pass the current state in

This is the reducer shape Hannes Dorfmann used in 2017: viewStateReducer(previousState, changes). It works out the new state from the old state plus one change. First, change the State so that "refreshing" can only exist when there is data:

sealed interface ProfileState {
    object Loading : ProfileState
    data class Error(val message: String) : ProfileState
    data class Success(
        val user: User,
        val isRefreshing: Boolean = false,
        val userMessage: String? = null    // from Lesson 3
    ) : ProfileState
}

Why put isRefreshing inside Success? It only makes sense when a user is on screen. If it were a top-level field, "refreshing with nothing loaded" would be possible again. That's the same kind of bug as Lesson 1's three independent fields.

fun reduce(state: ProfileState, result: ProfileResult): ProfileState =
    when (result) {
        ProfileResult.Loading -> when (state) {
            is ProfileState.Success -> state.copy(isRefreshing = true)  // keep the user
            else -> ProfileState.Loading
        }
        is ProfileResult.Loaded -> ProfileState.Success(result.user)
        is ProfileResult.Failed -> when (state) {
            is ProfileState.Success ->
                state.copy(isRefreshing = false, userMessage = result.message)
            else -> ProfileState.Error(result.message)
        }
        ProfileResult.MessageCleared ->
            (state as? ProfileState.Success)?.copy(userMessage = null) ?: state
    }

Now the same Failed Result has two meanings depending on the state. On first load it's a full-screen error. During a refresh, the data stays and a snackbar appears, using Lesson 3's pattern. The reducer is still pure, and the tests are still one line each:

@Test
fun `failed refresh keeps the user and shows a message`() {
    val refreshing = ProfileState.Success(ada, isRefreshing = true)
    assertEquals(
        ProfileState.Success(ada, userMessage = "Network down"),
        reduce(refreshing, ProfileResult.Failed("Network down"))
    )
}

Wiring it in: update { }

private fun dispatch(result: ProfileResult) {
    _state.update { current -> reduce(current, result) }
}

MutableStateFlow.update "updates the value atomically", but the docs warn that the function "may be evaluated multiple times, if value is being concurrently updated." So the lambda has to be pure. A reducer that logged analytics or called the network could do it twice. Lesson 2 made the reducer pure for testability, and update is a second reason. This line is the Kotlin version of Dorfmann's scan(initialState, this::viewStateReducer).

Two follow-ups interviewers often ask

1. "What if the user refreshes twice?"

Two loads run at the same time, and the older response can come back last and overwrite the newer one. The reducer can't fix this, because it only sees Results in the order they arrive. Ordering is the ViewModel's job, so cancel the previous load before starting a new one:

private var loadJob: Job? = null

private fun load(id: String) {
    loadJob?.cancel()
    loadJob = viewModelScope.launch { /* Loading → Loaded / Failed */ }
}

In a Flow pipeline the same idea is flatMapLatest. When a new value arrives, it cancels the work for the previous one.

2. "What happens after process death?"

The ViewModel survives rotation, but it does not survive the OS killing your process. Don't try to save the whole State. Google's guidance is that saved state "must be simple and lightweight". Its examples are things like "the ID of the item the user wants more detail about" (SavedStateHandle docs). So save the input (the user id) in SavedStateHandle, and rebuild the State by loading again. The Mavericks library makes the same choice: its @PersistState refuses to persist loading values, because "persisting and restoring loading states would lead to a broken user experience."

After this lesson, you can write a (State, Result) → State reducer that keeps data on screen during a refresh, wire it in with update { }, and explain why it has to be pure. You can also answer the "double refresh" and "process death" follow-up questions.

Drill: say it out loud

In under 60 seconds: "Why does your reducer take the previous state, and what does it mean that it's pure?"

Reveal model answer

"The same Result can mean different things depending on what's on screen. A failed load with no data is a full-screen error. A failed refresh with data should keep the data and show a message. So the reducer is (State, Result) -> State, the way Dorfmann defined it. It's pure: no I/O and no side effects, only data in and data out. That makes every transition a one-line unit test, and it also has to be pure because I apply it with MutableStateFlow.update, which can retry the lambda when there's contention. Side effects like the network call stay in the ViewModel, and that's also where I handle ordering, by cancelling a stale load before starting a new one."
