Orbit, Mavericks, MVIKotlin, and When Not to Use MVI

All three libraries implement the loop you built in Lesson 5, under different names. Once you can translate the names, you can talk about any of them, and you can explain when the pattern isn't worth it.

This lesson is a survey, as agreed in MISSION.md. If a job posting names one of these libraries, ask me for a dedicated lesson on it.

One structural difference stands out. Orbit and Mavericks drop the separate Result type: you call a reducer lambda right where the outcome happens. MVIKotlin keeps it as Message, which is the closest match to Dorfmann's original pattern and to Lesson 2.

Orbit: side effects and testing built in

class CalculatorViewModel :
    OrbitContainerHost<CalculatorState, CalculatorState, CalculatorSideEffect>, ViewModel() {

    override val container = orbitContainer<CalculatorState, CalculatorSideEffect>(CalculatorState())

    fun add(number: Int) = intent {
        postSideEffect(CalculatorSideEffect.Toast("Adding $number to ${state.total}!"))
        reduce { state.copy(total = state.total + number) }
    }
}

// Compose
val state = viewModel.collectAsState().value
viewModel.collectSideEffect { handleSideEffect(it) }
  • reduce "atomically updates" state. It isn't suspend, so async work has to happen before it, which matches your pure reducer (Core docs).
  • This answers Lesson 3's problem: side effects are cached when nobody is observing and delivered on re-subscription. By default each effect goes to one collector.
  • Testing is a DSL. After viewModel.test(this) { … } you call expectState { copy(count = 1) } and expectSideEffect(Toast(1)), and any item you don't check fails the test (Test docs).
  • Kotlin Multiplatform. The API was renamed recently (OrbitContainerHost, orbitContainer), so older posts may show ContainerHost and container.

Mavericks (Airbnb): State plus Async<T>

data class WeatherState(
    val currentTemperature: Async<Int> = Uninitialized
) : MavericksState

class WeatherViewModel(initial: WeatherState) : MavericksViewModel<WeatherState>(initial) {
    fun refresh() = suspend { weatherApi.fetchTemperature() }
        .execute { copy(currentTemperature = it) }   // Loading → Success / Fail
}
  • Async<T> is a sealed class with Uninitialized, Loading, Success and Fail. It's Lesson 2's sealed State, packaged per property. Loading and Fail can keep the previous value, which solves the same problem as Lesson 4's refresh fix.
  • It enforces immutable state with default values for every property, so the screen can always render immediately.
  • Interview gotcha: setState is queued and runs on a background thread, so state hasn't changed yet on the next line. Their threading doc shows one example printing [A, C, E, B, D].
  • @PersistState handles process death (see Lesson 4). Compose support comes from mavericks-compose (collectAsState()).

MVIKotlin: the textbook version

internal interface CalculatorStore : Store<Intent, State, Nothing> {
    sealed interface Intent {
        object Increment : Intent
        object Decrement : Intent
    }
    data class State(val value: Long = 0L)
}

private object ReducerImpl : Reducer<State, Intent> {
    override fun State.reduce(msg: Intent): State = when (msg) {
        is Intent.Increment -> copy(value = value + 1L)
        is Intent.Decrement -> copy(value = value - 1L)
    }
}
  • Store is "the place for business logic". The Executor is where "all asynchronous operations" happen, and it emits Messages to the Reducer and Labels ("one-time events"). A Bootstrapper starts the Store.
  • It's Kotlin Multiplatform (Android, iOS, JVM, JS and more) and includes logging and time-travel debugging. Time travel is only possible because every change goes through one pure reducer. That's a good point to mention in an interview.
  • The example above passes Intent straight to the Reducer for a trivial counter. Real Stores go Intent → Executor → Msg → Reducer.

When MVI isn't worth it

Be honest about how much Google's recommended MVVM already overlaps with MVI. The UI layer guide already recommends events up, state down, and usually one UiState stream, because "consumers of state always have the latest information available." On top of that, MVI adds a sealed Intent type, a single pure reducer and a strict rule about where side effects go. The question is whether those additions earn their boilerplate. (This is my synthesis; no official source settles it.)

MVI is worth it whenMVI is too much when
A screen has many interacting transitions (forms, refresh plus paging, multi-step flows)A screen has one or two independent values, like a settings toggle or a static detail page
You want every transition unit-tested, replayable or time-travel debuggableThe Intent, Result and State types would outnumber the logic
A team needs one consistent shape across many screensParts of the state are unrelated and update at different rates. Google lists this as a reason for separate streams
After this lesson, you can map any of the three libraries onto the plain loop, name what each one adds (Orbit: side effects and a test DSL; Mavericks: Async and queued setState; MVIKotlin: an explicit Executor and Msg, multiplatform support and time travel), and argue when MVI is overkill.

Drill: say it out loud

In under 60 seconds: "Have you used an MVI library? How is it different from writing MVI yourself, and when wouldn't you use MVI at all?"

Reveal model answer

"They're all the same loop. Orbit wraps each intent in an intent { } block with an atomic reduce, and gives you first-class side effects that are cached while nobody is observing, plus a test DSL. Mavericks centres on setState { copy() } and Async for loading states. One gotcha is that setState is queued, not immediate. MVIKotlin is the most literal version: Intent, Executor, Message, Reducer, plus Labels for one-off events, and because of that it can do time-travel debugging. Orbit and Mavericks drop the separate Result type, while MVIKotlin keeps it. I wouldn't use full MVI on a trivial screen. Google's single-UiState MVVM gives you most of the benefit, and the sealed Intent plus reducer only pays off when the transitions are complex enough to need testing on their own."
