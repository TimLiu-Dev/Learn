The Reducer: Testable State Transitions

Lesson 1 ended with a sealed ProfileState — but never actually finished wiring it up, and never tested it. That's today.

Quick recap, not a re-teach: Lesson 1 showed that one State object only prevents disagreement once it's a sealed hierarchy (Loading / Success / Error), because a sealed case simply has no slot for a field that shouldn't exist on it.

The piece that was still missing

Here's the gap: ProfileIntent.LoadProfile(id) fires the moment the user asks to load a profile — before the network call resolves. At that instant, nobody knows yet whether it'll succeed or fail. An Intent describes a request, not an outcome. So a function that takes an Intent and returns a new State can't actually do its job — it doesn't have the information yet.

What does have that information is the outcome of the side effect, once it finishes. MVI usually gives that outcome its own type — call it a Result (Hannes Dorfmann, who defined this pattern for Android, calls it PartialState or Result depending on the post):

sealed interface ProfileIntent {
    data class Load(val id: String) : ProfileIntent
}

sealed interface ProfileResult {
    object Loading : ProfileResult
    data class Loaded(val user: User) : ProfileResult
    data class Failed(val message: String) : ProfileResult
}

sealed interface ProfileState {
    object Loading : ProfileState
    data class Success(val user: User) : ProfileState
    data class Error(val message: String) : ProfileState
}

Now the reducer can be a plain function: given a Result, it returns a State. No ViewModel, no coroutines, no repository — just data in, data out.

fun reduce(result: ProfileResult): ProfileState = when (result) {
    is ProfileResult.Loading -> ProfileState.Loading
    is ProfileResult.Loaded  -> ProfileState.Success(result.user)
    is ProfileResult.Failed  -> ProfileState.Error(result.message)
}

The ViewModel's job shrinks to: turn an Intent into a side effect, turn the side effect's outcome into a Result, hand the Result to reduce.

class ProfileViewModel(
    private val repo: ProfileRepository
) : ViewModel() {

    private val _state = MutableStateFlow<ProfileState>(ProfileState.Loading)
    val state: StateFlow<ProfileState> = _state.asStateFlow()

    fun onIntent(intent: ProfileIntent) {
        when (intent) {
            is ProfileIntent.Load -> load(intent.id)
        }
    }

    private fun load(id: String) {
        viewModelScope.launch {
            _state.value = reduce(ProfileResult.Loading)
            val result = try {
                ProfileResult.Loaded(repo.getUser(id))
            } catch (e: Exception) {
                ProfileResult.Failed(e.message ?: "Unknown error")
            }
            _state.value = reduce(result)
        }
    }
}

The viewModelScope.launch block still exists — MVI doesn't remove side effects, it just refuses to let them leak into the function that decides what the new state looks like.

Why this is worth the extra type

reduce() has zero dependencies: no coroutine, no mock, no repository. You can test every branch with plain JUnit:

class ProfileReducerTest {

    @Test
    fun `loading result produces loading state`() {
        assertEquals(ProfileState.Loading, reduce(ProfileResult.Loading))
    }

    @Test
    fun `loaded result produces success state with the user`() {
        val user = User(id = "1", name = "Ada")
        assertEquals(
            ProfileState.Success(user),
            reduce(ProfileResult.Loaded(user))
        )
    }

    @Test
    fun `failed result produces error state with the message`() {
        assertEquals(
            ProfileState.Error("Network down"),
            reduce(ProfileResult.Failed("Network down"))
        )
    }
}

Compare that to testing the MVVM version from Lesson 1: you'd need runTest, a fake repository, control over coroutine dispatchers, and three separate assertions per case — and you'd still be testing the side effect and the state update together, because they were never separated.

Wiring it into Compose

@Composable
fun ProfileScreen(viewModel: ProfileViewModel, userId: String) {
    val state by viewModel.state.collectAsStateWithLifecycle()

    when (val s = state) {
        is ProfileState.Loading -> CircularProgressIndicator()
        is ProfileState.Success -> ProfileContent(s.user)
        is ProfileState.Error -> ErrorMessage(
            message = s.message,
            onRetry = { viewModel.onIntent(ProfileIntent.Load(userId)) }
        )
    }
}

Because ProfileState is sealed, this when needs no else branch — and if a teammate adds a fourth case (say, ProfileState.Empty) next quarter, this function fails to compile until someone handles it here. That's a compiler-enforced guarantee that MVVM's independent-flows version can't give you: there, adding a new piece of state is just adding a new flow, and nothing forces any View to react to it.

After this lesson: given a screen's sealed State and Intent, you can introduce a Result type, write a pure reduce() function, and unit test every branch of it with zero mocks and zero coroutines.
