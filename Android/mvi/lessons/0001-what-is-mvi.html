MVI, By Contrast With the MVVM You Already Know

You've shipped MVVM apps. The fastest way into MVI is to see exactly what it changes — not to start from zero.

This lesson exists because interviewers expect you to explain MVI crisply, not just name-drop it. By the end you'll be able to take any MVVM ViewModel's public surface and redraw it in MVI shape.

The loop you already know

A typical MVVM screen you've built probably looks like this: several independent streams, one per piece of UI state.

class ProfileViewModel(
    private val repo: ProfileRepository
) : ViewModel() {

    private val _isLoading = MutableStateFlow(false)
    val isLoading: StateFlow<Boolean> = _isLoading

    private val _user = MutableStateFlow<User?>(null)
    val user: StateFlow<User?> = _user

    private val _error = MutableStateFlow<String?>(null)
    val error: StateFlow<String?> = _error

    fun loadProfile(id: String) {
        viewModelScope.launch {
            _isLoading.value = true
            try {
                _user.value = repo.getUser(id)
                _error.value = null
            } catch (e: Exception) {
                _error.value = e.message
            } finally {
                _isLoading.value = false
            }
        }
    }
}

This already follows Google's unidirectional data flow principle loosely — events flow up (loadProfile), state flows down (the three flows). The View calls whichever public method it needs, and observes whichever flows it cares about.

The crack: nothing stops isLoading = true, error = "Network down", and a stale user from all being true at the same instant. The three streams can disagree, and the View has to reason about every combination of them.

What MVI changes

MVI keeps the same up/down direction, but tightens two things:

  1. One State, not many streams. All the screen's state lives in a single immutable object, exposed through a single StateFlow.
  2. One entry point, not many methods. The View never calls arbitrary methods on the state holder. It sends a single kind of message — an Intent — through one function.
sealed interface ProfileIntent {
    data class LoadProfile(val id: String) : ProfileIntent
}

data class ProfileState(
    val isLoading: Boolean = false,
    val user: User? = null,
    val error: String? = null
)

class ProfileViewModel(
    private val repo: ProfileRepository
) : ViewModel() {

    private val _state = MutableStateFlow(ProfileState())
    val state: StateFlow<ProfileState> = _state.asStateFlow()

    fun onIntent(intent: ProfileIntent) {
        when (intent) {
            is ProfileIntent.LoadProfile -> loadProfile(intent.id)
        }
    }

    private fun loadProfile(id: String) {
        viewModelScope.launch {
            _state.update { it.copy(isLoading = true, error = null) }
            try {
                val user = repo.getUser(id)
                _state.update { it.copy(isLoading = false, user = user) }
            } catch (e: Exception) {
                _state.update { it.copy(isLoading = false, error = e.message) }
            }
        }
    }
}

Note what did not change: it's still a ViewModel, still StateFlow, still coroutines. MVI on Android is usually a disciplined shape layered on the same tools you already use — not a new runtime.

Side by side

MVVM (as you've built it)MVI
State shape Several independent flows/LiveData One immutable State object, one StateFlow
Input from View Call whichever public method applies Send one sealed Intent through one entry point
Can parts of state disagree? Yes — streams update independently Reduced, not eliminated — one copy() updates every field together, but a forgotten field is still possible until State is a sealed hierarchy (see below)
Testing the logic Assert on several flows after calling a method Assert on one state transition: old state + Intent → new state
After this lesson: given any MVVM ViewModel's public surface, you can redraw it as one sealed Intent interface in, one State data class out — and explain precisely what that does and does not fix on its own.

Does merging into one object actually prevent disagreement?

Be skeptical here — the ProfileState data class above is a smaller win than it looks. It groups the three fields together and updates them atomically via copy(), but nothing stops someone from writing this six months from now:

fun retry(id: String) {
    viewModelScope.launch {
        _state.update { it.copy(isLoading = true) } // forgot: error = null
        try {
            val user = repo.getUser(id)
            _state.update { it.copy(isLoading = false, user = user) }
        } catch (e: Exception) {
            _state.update { it.copy(isLoading = false, error = e.message) }
        }
    }
}

This compiles. It ships. And the screen can now show a spinner next to a stale error message, because isLoading, user, and error are still three independent fields on the same object — grouping them didn't connect them.

The fix that actually makes the bad combination unrepresentable is modeling State as a sealed hierarchy instead of one data class with optional fields:

sealed interface ProfileState {
    object Loading : ProfileState
    data class Success(val user: User) : ProfileState
    data class Error(val message: String) : ProfileState
}

There is no error field on Loading. You cannot construct "loading with a stale error" — not because you remembered not to, but because the type doesn't have the slot for it. This is the real engine behind "MVI prevents impossible states": not the single object by itself, but combining it with Kotlin's sealed types so the compiler rejects the invalid combination outright, and an exhaustive when forces the View to handle every case.

The plain data-class version still isn't wasted effort — it's what makes one entry point and one atomic update possible in the first place. The sealed hierarchy is the next layer on top, not a replacement. We'll build and test a full sealed State in the next lesson.

Why interviewers care

Three things come up constantly:

  • Single source of truth. One object describes the screen completely at any instant — no reasoning about flow combinations.
  • Testability. The state-update step (oldState + Intent → newState) is close to a pure function. You can unit test it without touching coroutines or mocking flows.
  • Predictability. Because every change goes through one funnel, you can log every (State, Intent) pair and replay a bug exactly — a debugging property Hannes Dorfmann highlights as one of MVI's original motivations.
