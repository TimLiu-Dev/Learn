Offline-First Repository Pattern (Single Source of Truth)

Architect resilient offline-first data engines where the local database is the Single Source of Truth (SSOT).

Recommended Primary Source
Google Android: Guide to App Architecture - Data Layer & Offline-First
Official Documentation →

In a 2027 production Android architecture, network connectivity is an asynchronous background synchronization detail, never a prerequisite for rendering UI. Whether a user opens your application inside an elevator, on a subway tunnel, or over a high-jitter 5G handoff, cached domain models must render within a single 16ms frame budget from local storage.

Under the Hood: Room InvalidationTracker & Reactive SSOT

The Single Source of Truth (SSOT) pattern mandates that the UI and Domain layers observe an immutable Flow<List<DomainModel>> backed exclusively by Room's SQLite database. Under the hood, when Room executes a @Query returning a Flow, it registers a table observer on its internal InvalidationTracker using SQLite triggers on a hidden shadow table (room_table_modification_log). When your repository's sync() coroutine fetches fresh DTOs from Ktor/Retrofit and writes them into SQLite inside an atomic @Upsert transaction, SQLite increments the table modification counter. Room's tracker detects the dirty table and automatically re-executes the read query on Dispatchers.IO, pushing the updated domain models downstream to any active StateFlow collector.

🌱 Junior Android Dev Mental Model: Unidirectional Data Sync

The Golden Rule: Read streams flow strictly Upward (Room SQLite → Repository mapping → ViewModel StateFlow → Compose UI). Network responses never return data directly to the ViewModel; instead, network DTOs flow strictly into the local database, which then triggers the reactive read stream.

Optimistic Mutations, Tombstones & Conflict Resolution

What happens when the user modifies data while offline (e.g., bookmarking an asset or rebalancing a portfolio)? A senior offline-first repository applies an optimistic local write immediately to Room with a syncState = PENDING_UPLOAD flag or records a tombstone row (isDeleted = true) for deletions rather than executing a hard DELETE before the server acknowledges it. A background synchronization engine (WorkManager) later drains dirty rows using exponential backoff and resolves server conflicts using vector clocks or updatedAtEpochMillis Last-Write-Wins (LWW) timestamps.

✅ 2027 Senior Production Standard: Reactive SSOT

class OfflineFirstPortfolioRepository(
    private val dao: AssetDao,
    private val api: PortfolioNetworkDataSource
) {
    // UI strictly observes local SQLite SSOT
    val portfolio: Flow<List<Asset>> = dao.observeActiveAssets()
        .map { entities -> entities.map(AssetEntity::asExternalModel) }
        .distinctUntilChanged()

    // Sync writes only to Room; never returns data to UI
    suspend fun syncWith(synchronizer: ChangeListSynchronizer): Boolean =
        suspendRunCatching {
            val changeList = api.getChangeList(afterVersion = synchronizer.ChangeVersion)
            dao.deleteAssets(changeList.deletedIds)
            val updated = api.getAssets(changeList.updatedIds)
            dao.upsertAssets(updated.map(NetworkAsset::asEntity))
        }.isSuccess
}

⚠️ Senior Interview Trap: Structured Cancellation & CancellationException

When wrapping network synchronization inside a generic helper like runCatching { ... }, catching Throwable swallows kotlinx.coroutines.CancellationException! If the coroutine scope is cancelled, swallowing CancellationException breaks structured concurrency and allows subsequent suspension points in the parent coroutine to execute zombie writes. Always define a dedicated suspendRunCatching helper that explicitly rethrows CancellationException.

import kotlinx.coroutines.CancellationException

data class AssetDto(val symbol: String, val priceUsd: Double, val serverVersion: Long)
data class AssetEntity(val symbol: String, val priceUsd: Double, val version: Long, val pendingSync: Boolean)
data class Asset(val symbol: String, val priceUsd: Double, val isSynced: Boolean)

class InMemoryAssetDao {
    private val table = linkedMapOf(
        "BTC" to AssetEntity("BTC", 91200.0, version = 10L, pendingSync = false),
        "ETH" to AssetEntity("ETH", 3150.0, version = 10L, pendingSync = false)
    )

    fun queryActiveAssets(): List<AssetEntity> = table.values.toList()

    fun upsertWithLwwResolution(incoming: List<AssetEntity>) {
        for (entity in incoming) {
            val current = table[entity.symbol]
            if (current == null || (!current.pendingSync && entity.version >= current.version)) {
                table[entity.symbol] = entity
            }
        }
    }

    fun markOptimisticPriceAlert(symbol: String, targetPrice: Double) {
        val cur = table[symbol] ?: return
        table[symbol] = cur.copy(priceUsd = targetPrice, pendingSync = true)
    }
}

class OfflineFirstAssetRepository(private val dao: InMemoryAssetDao) {
    fun readSsotSnapshot(): List<Asset> =
        dao.queryActiveAssets().map { Asset(it.symbol, it.priceUsd, !it.pendingSync) }

    fun syncFromRemote(remoteDtos: List<AssetDto>): Result<Int> = try {
        val entities = remoteDtos.map { AssetEntity(it.symbol, it.priceUsd, it.serverVersion, pendingSync = false) }
        dao.upsertWithLwwResolution(entities)
        Result.success(entities.size)
    } catch (c: CancellationException) {
        throw c
    } catch (t: Throwable) {
        Result.failure(t)
    }
}

fun main() {
    val dao = InMemoryAssetDao()
    val repo = OfflineFirstAssetRepository(dao)

    println("[LAUNCH] Instant SSOT emission from SQLite: ${repo.readSsotSnapshot()}")
    dao.markOptimisticPriceAlert("ETH", 3200.0)
    println("[OPTIMISTIC] Local dirty write applied:     ${repo.readSsotSnapshot()}")

    val remotePayload = listOf(
        AssetDto("BTC", 94500.0, serverVersion = 11L),
        AssetDto("ETH", 3180.0, serverVersion = 11L), // Blocked by local pendingSync!
        AssetDto("SOL", 210.0, serverVersion = 11L)
    )
    val synced = repo.syncFromRemote(remotePayload)
    println("[SYNC] Remote delta reconciled (result=$synced)")
    println("[SSOT] Post-sync emission (ETH protected):  ${repo.readSsotSnapshot()}")
}

import kotlinx.coroutines.CancellationException
import kotlinx.coroutines.flow.Flow
import kotlinx.coroutines.flow.distinctUntilChanged
import kotlinx.coroutines.flow.map

data class TickerDto(val id: String, val price: Double)
data class TickerEntity(val id: String, val price: Double)
data class Ticker(val id: String, val price: Double)

interface TickerDao {
    fun observeTickers(): Flow<List<TickerEntity>>
    suspend fun upsertAll(entities: List<TickerEntity>)
}

interface TickerNetworkDataSource {
    suspend fun fetchTickers(): List<TickerDto>
}

class OfflineFirstTickerRepository(
    private val dao: TickerDao,
    private val api: TickerNetworkDataSource
) {
    val tickers: Flow<List<Ticker>> = dao.observeTickers()
        .map { entities -> entities.map { Ticker(it.id, it.price) } }
        .distinctUntilChanged()

    suspend fun synchronize(): Boolean = try {
        val networkItems = api.fetchTickers()
        dao.upsertAll(networkItems.map { TickerEntity(it.id, it.price) })
        true
    } catch (e: CancellationException) {
        throw e
    } catch (e: Exception) {
        false
    }
}

Why this works: Exposing a mapped Flow from Room with distinctUntilChanged() ensures UI collectors only recompose when domain-visible columns change, while synchronize() updates the database without breaking coroutine cancellation.

Room @Upsert methods cannot execute inside runCatching lambdas because inline functions strip the transaction CoroutineContext.
runCatching intercepts CancellationException via Throwable, logging normal scope cancellation as an error without rethrowing it.
Mapping network responses to entities on the invoking dispatcher throws a Room IllegalStateException without Dispatchers.Default.
Kotlin inline Result wrappers cannot be returned from suspend functions because continuation state-machines forbid boxing.

Quiz 2: Production Architectural Reasoning

In an enterprise offline-first app where users can delete items while offline, why must the Repository record a local 'tombstone' row (isDeleted = true) rather than immediately executing a SQL DELETE on the Room table?

SQLite cannot execute physical DELETE statements while in Airplane Mode due to write-ahead lock constraints.
Room InvalidationTracker only triggers reactive Flow emissions on INSERT and UPDATE queries, ignoring physical DELETEs.
Deleting rows immediately loses local deletion tracking, causing the undeleted server item to resurrect later.
Physical DELETE statements immediately trigger a blocking SQLite VACUUM operation on the main UI thread.
