Production Rollouts: Feature Flags, Remote Config & Analytics Architecture

Design multi-module feature flag evaluation, QA debug override panels, staged rollout hydration, and decoupled analytics pipelines.

Recommended Primary Source
Android Developers: Modularization & Production Architecture
Official Documentation →

In elite mobile engineering organizations, deployment (shipping binary code in an AAB to the Play Store) is completely decoupled from release (turning a feature on for users). Every non-trivial feature, migration, or risky SDK upgrade is wrapped behind a strongly typed Feature Flag backed by Remote Config (Firebase Remote Config, LaunchDarkly, Statsig, or an in-house experimentation service). To keep a 20+ module codebase clean and testable, a Senior Android Architect designs a Layered Feature Flag Evaluation Pipeline that resolves values in strict priority order: (1) Local QA / Debug Override (persisted in a debug-only DataStore so QA and developers can toggle any flag via an in-app Debug Drawer without changing server configs), (2) Fetched & Activated Remote Config, and (3) Compile-Time Safe Default (<code>false</code> for unfinished features, <code>true</code> for operational kill switches that disable a feature on outage).

A critical production subtlety is Session Consistency (Activate-on-Next-Start vs. Mid-Session Mutation). Imagine the user is halfway through a 3-step Checkout flow using the Legacy Checkout UI (<code>new_checkout_enabled = false</code>), and a background Remote Config fetch completes and flips <code>new_checkout_enabled = true</code> mid-session! If your UI reacts live to the raw network fetch, Step 1 renders in the old UI and Step 2 suddenly morphs into the new UI with incompatible state—causing crashes and corrupt analytics! Therefore, senior teams snapshot/activate feature flags once at session startup (writing newly fetched network configs to disk to take effect on the next cold start), while reserving real-time mid-session reactive <code>Flow<Boolean></code> updates strictly for emergency operational kill switches. Pair this with a vendor-agnostic <code>AnalyticsTracker</code> interface in <code>:core:analytics</code> combined with a batched offline event queue so feature modules never import Firebase, Amplitude, or Mixpanel SDKs directly.

🌱 Junior Android Dev Mental Model: Never Pass Raw String Flag Keys Across Feature Modules

Scattering remoteConfig.getBoolean("enable_new_chart_v2") across 15 files leads to typos ("enable_new_charts_v2"), untestable static singletons, and stale dead flags that haunt the codebase for years. Define a sealed or enum FeatureFlag<T>(val key: String, val defaultValue: T, val ownerTeam: String, val expiresOn: String) in :core:config so every flag is strongly typed, discoverable by your Debug Menu, and audited for expiration in CI!

Senior Interview Trap & Production Edge Case

Trap: Blocking the main thread or holding the Android <code>SplashScreen</code> for 5 seconds on cold start waiting for <code>remoteConfig.fetchAndActivate().await()</code> over a slow 3G elevator connection! Never block cold startup on a network flag fetch: read the last-activated disk cache snapshot immediately in <code><2ms</code> from local storage (<code>DataStore</code> / cached Remote Config) to render the first frame, and fetch fresh remote flags asynchronously in the background for the next session.
Edge Case: When running an A/B experiment, logging the <strong>Experiment Exposure Event</strong> (<code>experiment_viewed</code>) on app startup instead of at the exact moment the user actually reaches the gated screen dilutes your experiment statistics with 80% of users who never even opened that tab! Always fire exposure analytics lazily when the flag is evaluated at the feature entry point.

✅ 2027 Senior Standard: Priority Chain + Session Snapshot + Decoupled Analytics

// :core:config — Strongly typed flag with priority: DebugOverride > SessionSnapshot > Default
enum class BooleanFlag(val key: String, val default: Boolean) {
    NEW_ORDER_BOOK("new_order_book_v3", default = false),
    LIVE_PRICE_WEBSOCKET_KILLSWITCH("ws_enabled", default = true)
}

class LayeredFeatureFlagManager(
    private val debugOverrides: Map<String, Boolean>,
    private val sessionSnapshot: Map<String, Boolean>
) {
    fun isEnabled(flag: BooleanFlag, recordExposure: (String, Boolean) -> Unit): Boolean {
        val value = debugOverrides[flag.key] ?: sessionSnapshot[flag.key] ?: flag.default
        recordExposure(flag.key, value) // Lazy exposure tracking at point of use!
        return value
    }
}

enum class FeatureFlag(val key: String, val defaultValue: Boolean, val isKillSwitch: Boolean = false) {
    NEW_KMP_CHECKOUT("new_kmp_checkout", defaultValue = false),
    GEMINI_NANO_SUMMARY("gemini_nano_summary", defaultValue = false),
    WEBSOCKET_STREAM_ACTIVE("websocket_stream_active", defaultValue = true, isKillSwitch = true)
}

class ProductionFlagEvaluator(
    private val isDebugBuild: Boolean,
    private val qaOverrides: Map<String, Boolean>,
    private val activatedSessionSnapshot: Map<String, Boolean>,
    private val liveRemoteKillSwitches: Map<String, Boolean>
) {
    val exposureLog = mutableListOf<String>()

    fun evaluate(flag: FeatureFlag): Boolean {
        // 1. QA Override wins in debug builds
        if (isDebugBuild && qaOverrides.containsKey(flag.key)) {
            val v = qaOverrides.getValue(flag.key)
            exposureLog.add("EXPOSURE(${flag.key}=$v, source=QA_DEBUG_OVERRIDE)")
            return v
        }
        // 2. Emergency kill switches react immediately mid-session
        if (flag.isKillSwitch && liveRemoteKillSwitches.containsKey(flag.key)) {
            val v = liveRemoteKillSwitches.getValue(flag.key)
            exposureLog.add("EXPOSURE(${flag.key}=$v, source=LIVE_KILLSWITCH)")
            return v
        }
        // 3. Frozen session snapshot guarantees UI consistency during user flow
        val v = activatedSessionSnapshot[flag.key] ?: flag.defaultValue
        val src = if (activatedSessionSnapshot.containsKey(flag.key)) "SESSION_SNAPSHOT" else "COMPILE_DEFAULT"
        exposureLog.add("EXPOSURE(${flag.key}=$v, source=$src)")
        return v
    }
}

fun main() {
    val evaluator = ProductionFlagEvaluator(
        isDebugBuild = true,
        qaOverrides = mapOf("new_kmp_checkout" to true),
        activatedSessionSnapshot = mapOf("new_kmp_checkout" to false, "gemini_nano_summary" to true),
        liveRemoteKillSwitches = mapOf("websocket_stream_active" to false)
    )

    FeatureFlag.entries.forEach { flag ->
        println("[FLAG-EVAL] ${flag.name.padEnd(24)} -> enabled=${evaluator.evaluate(flag)}")
    }
    println("[ANALYTICS-EXPOSURES] ${evaluator.exposureLog}")
}

fun resolveFlagWithSource(
    flagKey: String,
    defaultVal: Boolean,
    isDebugBuild: Boolean,
    debugOverrides: Map<String, Boolean>,
    sessionRemoteValues: Map<String, Boolean>
): Pair<Boolean, String> {
    if (isDebugBuild && debugOverrides.containsKey(flagKey)) {
        return Pair(debugOverrides.getValue(flagKey), "DEBUG_OVERRIDE")
    }
    if (sessionRemoteValues.containsKey(flagKey)) {
        return Pair(sessionRemoteValues.getValue(flagKey), "REMOTE_SESSION")
    }
    return Pair(defaultVal, "DEFAULT")
}

Why this works: Gating local QA overrides behind <code>isDebugBuild</code> ensures production builds cannot be spoofed locally while allowing QA engineers to test unreleased branches without altering production Remote Config rules.

Invoking the Kotlin forEach collection extension inside Application.onCreate resets all evaluated boolean flags to false.
Statistical A/B experiments only succeed when one hundred million concurrent active users open screens simultaneously.
Calling Boolean.toString on remote feature configuration flags generates randomized alphanumeric strings inside optimized release builds.
Premature exposure logging in Application.onCreate enrolls unexposed users; fire exposure events lazily at feature boundaries.

Quiz 2: Production Architectural Reasoning

Why should regular UI/navigation feature flags use a 'Fetch-in-Background, Activate-on-Next-Session' strategy rather than flipping <code>StateFlow<Boolean></code> values immediately in the middle of an active user session?

Flipping navigation flags mid-session breaks active flows and backstacks; per-session snapshots guarantee consistent UI state.
Android platform storage policies strictly forbid reading local persistent disk storage more than once daily.
Kotlin coroutines MutableStateFlow streams can emit only one configuration boolean value throughout application process lifetimes.
Google Play automated review systems immediately unpublish applications that fetch Remote Config payloads over Wi-Fi.
