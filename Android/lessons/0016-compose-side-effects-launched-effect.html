Compose Side-Effects: LaunchedEffect & Lifecycle

Master LaunchedEffect, rememberCoroutineScope, DisposableEffect, and rememberUpdatedState.

Recommended Primary Source
Google Android: Side-effects in Compose
Official Documentation →

Because a @Composable function can re-execute on any frame, execute in parallel on background threads in future Compose runtimes, or have its composition discarded before being committed to the Applier, executing side-effects directly inside a Composable body is a critical bug. Jetpack Compose provides a suite of Lifecycle- and Slot-Table-bound Effect Handlers that guarantee effects run only after a composition is successfully committed by the Applier and clean up deterministically when leaving the tree.

  • LaunchedEffect(key1, ...) { ... }: Stores a LaunchedEffectImpl (RememberObserver) in the Slot Table. When the slot enters the composition, it launches a coroutine in the Composition's CoroutineContext (typically AndroidUiDispatcher.Main). If any key changes on a subsequent recomposition, the existing coroutine is cancelled and relaunched; when the Composable leaves the tree, the coroutine is cancelled automatically. Use this for Compose-initiated suspending work (collecting one-off UI effects, triggering initial animations, or running snapshotFlow).
  • rememberCoroutineScope(): Returns a CoroutineScope bound to the current point in the Slot Table, used to launch coroutines from non-composable event callbacks (onClick = { scope.launch { pagerState.animateScrollToPage(2) } }). Never call scope.launch directly in the Composable body!
  • DisposableEffect(key1, ...) { onDispose { ... } }: For non-suspending setup/teardown pairs (registering a LifecycleEventObserver, binding a hardware sensor, or locking screen orientation). Guarantees onDispose runs whenever a key changes or the node leaves composition.
  • SideEffect { ... }: Runs synchronously after every successful composition to publish Compose state to non-Compose imperative objects (e.g., updating a Firebase Analytics user property or syncing status bar icon tint).
🌱 Junior Android Dev Mental Model: LaunchedEffect vs. rememberCoroutineScope

Ask one simple question: Who triggers the coroutine?
• If the coroutine should start automatically because the UI entered a state or mounted → use LaunchedEffect(key).
• If the coroutine should start because the user tapped a button or performed a gesture → use val scope = rememberCoroutineScope() inside the onClick lambda.

🔥 Senior Interview Trap: Lambda Capture Staleness & Why rememberUpdatedState Exists!

Suppose you build a SplashTimeout(onTimeout: () -> Unit) Composable that waits 3 seconds inside LaunchedEffect(Unit) { delay(3_000L); onTimeout() }. Why is keying on Unit while calling onTimeout() directly a subtle production bug? Because if the parent screen recomposes during those 3 seconds and passes a new onTimeout lambda capturing updated state, LaunchedEffect(Unit) will NOT restart (its key is still Unit!), so after 3 seconds it invokes the stale onTimeout closure captured from the very first composition! Conversely, if you pass LaunchedEffect(onTimeout), the 3-second timer resets from 0 every time onTimeout changes! The Solution: val currentOnTimeout by rememberUpdatedState(onTimeout) writes the latest lambda into a MutableState box on every recomposition so LaunchedEffect(Unit) reads currentOnTimeout() at the end of the 3-second delay without restarting the timer!

❌ Junior Anti-Pattern: Stale Closure Capture & Uncleaned Listeners

@Composable
fun AutoSaveEditor(
    draftText: String,
    onAutoSave: (String) -> Unit
) {
    // BUG: Key is Unit, so this coroutine captures the INITIAL draftText ("")
    // and INITIAL onAutoSave lambda forever! Every 10s it saves ""!
    LaunchedEffect(Unit) {
        while (true) {
            delay(10_000L)
            onAutoSave(draftText)
        }
    }
}

✅ 2027 Senior Standard: rememberUpdatedState + DisposableEffect

@Composable
fun AutoSaveEditor(
    draftText: String,
    onAutoSave: (String) -> Unit,
    lifecycleOwner: LifecycleOwner = LocalLifecycleOwner.current
) {
    // Always holds the latest value without restarting the 10s timer!
    val currentDraft by rememberUpdatedState(draftText)
    val currentOnSave by rememberUpdatedState(onAutoSave)

    LaunchedEffect(Unit) {
        while (true) {
            delay(10_000L)
            currentOnSave(currentDraft)
        }
    }

    DisposableEffect(lifecycleOwner) {
        val observer = LifecycleEventObserver { _, event ->
            if (event == Lifecycle.Event.ON_STOP) currentOnSave(currentDraft)
        }
        lifecycleOwner.lifecycle.addObserver(observer)
        onDispose { lifecycleOwner.lifecycle.removeObserver(observer) }
    }
}

import kotlinx.coroutines.*

// Demonstrates how rememberUpdatedState solves stale closure capture in long-running LaunchedEffects
class MutableStateBox<T>(var value: T)

fun main() = runBlocking {
    var parentRecompositionCount = 1
    val staleCapturedCallback: () -> String = { "Callback from Composition #1 (STALE!)" }

    // rememberUpdatedState box updated on every recomposition without restarting the effect
    val updatedStateBox = MutableStateBox<() -> String>({ "Callback from Composition #1" })

    val effectJob = launch {
        println("[LAUNCHED_EFFECT(Unit)] Started 100ms countdown timer (key=Unit)...")
        delay(100L)
        println("[BUGGY DIRECT CAPTURE] Invoked: ${staleCapturedCallback()}")
        println("[REMEMBER_UPDATED_STATE] Invoked: ${updatedStateBox.value()}")
    }

    // Simulate parent recomposing at t=40ms and t=70ms with fresh state in its lambda
    delay(40L)
    parentRecompositionCount = 2
    updatedStateBox.value = { "Callback from Composition #$parentRecompositionCount" }
    println("[RECOMPOSE #2 at 40ms] Updated rememberUpdatedState box without restarting timer")

    delay(30L)
    parentRecompositionCount = 3
    updatedStateBox.value = { "Callback from Composition #$parentRecompositionCount (LATEST!)" }
    println("[RECOMPOSE #3 at 70ms] Updated rememberUpdatedState box without restarting timer")

    effectJob.join()
}

Implement @Composable fun InactivityWatchdog(sessionId: String, timeoutMs: Long, onTimeout: () -> Unit). First, capture the latest callback with val currentOnTimeout by rememberUpdatedState(onTimeout) so lambda updates don't reset the timer. Next, launch a LaunchedEffect(sessionId, timeoutMs) that calls delay(timeoutMs) and invokes currentOnTimeout(). Finally, add a DisposableEffect(sessionId) that calls WatchdogRegistry.register(sessionId) and cleans up with onDispose { WatchdogRegistry.unregister(sessionId) }.

🎯 Reference Production Solution 
import androidx.compose.runtime.*
import kotlinx.coroutines.delay

object WatchdogRegistry {
    fun register(id: String) {}
    fun unregister(id: String) {}
}

@Composable
fun InactivityWatchdog(
    sessionId: String,
    timeoutMs: Long,
    onTimeout: () -> Unit
) {
    val currentOnTimeout by rememberUpdatedState(onTimeout)

    LaunchedEffect(sessionId, timeoutMs) {
        delay(timeoutMs)
        currentOnTimeout()
    }

    DisposableEffect(sessionId) {
        WatchdogRegistry.register(sessionId)
        onDispose {
            WatchdogRegistry.unregister(sessionId)
        }
    }
}

Why this works: rememberUpdatedState keeps currentOnTimeout pointing to the latest lambda without restarting the timer on unrelated recompositions, LaunchedEffect(sessionId, timeoutMs) restarts the timer only when sessionId or timeoutMs changes, and DisposableEffect guarantees WatchdogRegistry.unregister(sessionId) runs on key change or disposal.

rememberCoroutineScope() creates an unmanaged GlobalScope job that leaks the hosting Activity instance after configuration changes.
