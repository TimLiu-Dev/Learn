Google Play Billing 7+, Subscriptions & Entitlement Architecture

Engineer tamper-proof in-app subscriptions with BillingClient coroutines, backend purchaseToken verification, RTDN webhooks, and 3-day acknowledgment.

Recommended Primary Source
Android Developers: Google Play Billing Library Overview
Official Documentation →

In consumer subscription and freemium Android apps (like an "Aether Pro" real-time institutional market tier), revenue security depends on a strict separation of duties between the Google Play Billing Library (v7+) on the client and your Entitlement Verification Service on the backend. On Android, your repository manages a single BillingClient connection (configured with enablePendingPurchases(PendingPurchasesParams.newBuilder().enableOneTimeProducts().build())), queries localized pricing via queryProductDetails(), and launches the system purchase sheet via launchBillingFlow(activity, params)—passing an encrypted/hashed user identifier in setObfuscatedAccountId(userHash) so renewals and fraud checks map deterministically to the right account.

However, a Senior Android Engineer never unlocks premium entitlements solely because PurchasesUpdatedListener returned PurchaseState.PURCHASED on the device! Rooted hooks and proxy tools can spoof local client callbacks. Instead, when onPurchasesUpdated delivers a Purchase, the client sends its opaque purchaseToken to your backend server. Your backend calls the Google Play Developer API (purchases.subscriptionsv2.get) using a service account to cryptographically verify validity, grants the entitlement in your database, calls acknowledgePurchase (either server-side or via client after server confirmation), and listens to Real-Time Developer Notifications (RTDN) over Google Cloud Pub/Sub to handle renewals, cancellations, Grace Periods, and Account Hold states automatically even when the user never opens the app!

🌱 Junior Android Dev Mental Model: The Fatal 3-Day Unacknowledged Auto-Refund Rule!

Google Play enforces an unforgiving transactional safeguard: every non-consumable purchase and initial subscription MUST be acknowledged within 3 days (72 hours) via acknowledgePurchase() (or consumeAsync() for consumables like game coins). If your app crashes after payment or forgets to acknowledge, Google Play automatically refunds the transaction and revokes the user's subscription after 72 hours! Always call queryPurchasesAsync() on every app startup/resume to retry sending any unacknowledged PURCHASED tokens to your backend!

⚠️ Senior Interview Trap: Pending Purchases & Subscription Lifecycle States

Trap: Treating Purchase.PurchaseState.PENDING the same as PURCHASED! In markets supporting cash/voucher or slow bank-transfer payments (like OXXO in Mexico or Boleto in Brazil), a user starts checkout in your app and pays hours later at a convenience store. Granting Pro access while purchaseState == PENDING gives away free subscriptions; instead, show an "Awaiting Payment Confirmation" banner until RTDN / onPurchasesUpdated transitions the state to PURCHASED.
Edge Case: When a recurring renewal card fails, a subscription enters Grace Period (keep Pro access enabled while nudging the user with Play's showInAppMessages billing fix dialog!) and then Account Hold (suspend Pro access without deleting user settings until payment recovers).

❌ Junior Anti-Pattern: Client-Only Unlock, Ignored Pending & No Acknowledge

override fun onPurchasesUpdated(result: BillingResult, purchases: List<Purchase>?) {
    if (result.responseCode == BillingResponseCode.OK && purchases != null) {
        // BUG 1: Grants Pro locally without verifying purchaseToken on backend!
        // BUG 2: Grants Pro even when purchaseState == PENDING!
        // BUG 3: Never acknowledges -> Play auto-refunds in 72 hours!
        prefs.setProUnlocked(true)
    }
}

✅ 2027 Senior Standard: Pending Guard + Server Token Verify + Startup Reconcile

suspend fun processPurchases(purchases: List<Purchase>) {
    for (purchase in purchases) {
        when (purchase.purchaseState) {
            Purchase.PurchaseState.PURCHASED -> {
                // Backend verifies token with Play Developer API & acknowledges idempotently!
                val verified = entitlementApi.verifyAndAcknowledge(purchase.purchaseToken)
                if (verified) localEntitlementDao.upsertActivePro()
            }
            Purchase.PurchaseState.PENDING -> localEntitlementDao.markPendingPayment()
            else -> Unit
        }
    }
}

enum class ClientPurchaseState { PURCHASED, PENDING, UNSPECIFIED }
enum class RtdnWebhookType { SUBSCRIPTION_RENEWED, SUBSCRIPTION_IN_GRACE_PERIOD, SUBSCRIPTION_ON_HOLD }

data class PlayPurchaseRecord(
    val purchaseToken: String,
    val state: ClientPurchaseState,
    val isAcknowledged: Boolean,
    val serverVerifiedValid: Boolean
)

object SubscriptionEntitlementMachine {
    fun evaluatePurchase(record: PlayPurchaseRecord): String = when {
        record.state == ClientPurchaseState.PENDING ->
            "AWAITING_PAYMENT_SETTLEMENT (Pro locked)"
        record.state == ClientPurchaseState.PURCHASED && !record.serverVerifiedValid ->
            "REJECTED_INVALID_SIGNATURE"
        record.state == ClientPurchaseState.PURCHASED && record.serverVerifiedValid ->
            "PRO_ACTIVE_ACKNOWLEDGED (72h refund prevented!)"
        else -> "NO_ENTITLEMENT"
    }

    fun applyRtdnEvent(event: RtdnWebhookType): String = when (event) {
        RtdnWebhookType.SUBSCRIPTION_RENEWED -> "PRO_ACTIVE_RENEWED"
        RtdnWebhookType.SUBSCRIPTION_IN_GRACE_PERIOD -> "PRO_GRACE_BANNER_SHOWN"
        RtdnWebhookType.SUBSCRIPTION_ON_HOLD -> "PRO_SUSPENDED_ACCOUNT_HOLD"
    }
}

fun main() {
    val cashPending = PlayPurchaseRecord("tok_mx_01", ClientPurchaseState.PENDING, isAcknowledged = false, serverVerifiedValid = false)
    val cardValid = PlayPurchaseRecord("tok_us_99", ClientPurchaseState.PURCHASED, isAcknowledged = false, serverVerifiedValid = true)

    println("[CHECKOUT-CASH]  State=PENDING   -> Entitlement=${SubscriptionEntitlementMachine.evaluatePurchase(cashPending)}")
    println("[CHECKOUT-CARD]  State=PURCHASED -> Entitlement=${SubscriptionEntitlementMachine.evaluatePurchase(cardValid)}")
    println("[RENEWAL-FAILED] RTDN=SUBSCRIPTION_IN_GRACE_PERIOD -> Entitlement=${SubscriptionEntitlementMachine.applyRtdnEvent(RtdnWebhookType.SUBSCRIPTION_IN_GRACE_PERIOD)}")
    println("[RENEWAL-EXPIRED] RTDN=SUBSCRIPTION_ON_HOLD        -> Entitlement=${SubscriptionEntitlementMachine.applyRtdnEvent(RtdnWebhookType.SUBSCRIPTION_ON_HOLD)}")
}

fun reconcilePlayPurchase(
    purchaseState: String,
    serverVerified: Boolean,
    alreadyAcknowledged: Boolean
): String {
    if (purchaseState == "PENDING") {
        return "SHOW_PENDING_PAYMENT"
    }
    if (purchaseState != "PURCHASED" || !serverVerified) {
        return "DENY_ENTITLEMENT"
    }
    return if (!alreadyAcknowledged) {
        "GRANT_AND_ACKNOWLEDGE_NOW"
    } else {
        "GRANT_ALREADY_ACKNOWLEDGED"
    }
}

Why this works: Isolating PENDING transactions, requiring cryptographic backend verification before unlocking entitlements, and explicitly acknowledging unacknowledged purchases prevents piracy and 72-hour automatic Play Store refunds.

Quiz 2: Production Architectural Reasoning

Why do production subscription apps pair startup BillingClient.queryPurchasesAsync() reconciliation with backend Real-Time Developer Notifications (RTDN) over Cloud Pub/Sub?

RTDN updates renewals, cancellations, and account holds server-side while startup queries recover interrupted client purchase sessions.
Google Play blocks BillingClient from returning product prices unless a Cloud Pub/Sub socket runs inside Compose.
Calling queryPurchasesAsync charges the customer's saved credit card an extra verification fee on every cold start.
Real-Time Developer Notifications replace HTTPS TLS encryption so purchase tokens can travel safely in unencrypted plaintext.
