Background Processing with Jetpack WorkManager

Schedule battery-conscious offline synchronization tasks using WorkManager and CoroutineWorker.

Recommended Primary Source
Google Android: Schedule tasks with WorkManager
Official Documentation →

Android aggressively restricts background execution to preserve battery life and RAM through Doze Mode, App Standby Buckets, and strict foreground service quotas introduced across Android 14–16. When a task must be guaranteed to execute eventually—even if the user swipes the app away from Recents or reboots the device—WorkManager is the canonical deferrable background execution engine.

Under the Hood: WorkManager's Persistence & JobScheduler Bridge

When you enqueue a WorkRequest, WorkManager does not immediately spawn a thread. First, it writes the work specification, constraints, input Data payload (capped at 10KB), and backoff policy into an internal Room database (androidx.work.workdb). Next, it registers a system-level alarm with Android's JobScheduler (API 23+). Because the OS kernel and system_server own JobScheduler, your work survives process death and device reboots (via WorkManager's internal RescheduleReceiver). When constraints (e.g., NetworkType.CONNECTED, requiresBatteryNotLow) are met, JobScheduler wakes your app process and invokes your CoroutineWorker.doWork() on Dispatchers.Default.

🌱 Junior Android Dev Mental Model: CoroutineScope vs. WorkManager

Use viewModelScope for in-memory work tied to the screen lifecycle (cancels when the user backs out). Use WorkManager for persistent, deferrable work that must survive process death (e.g., syncing offline database tombstones, uploading encrypted logs, periodic cache refresh).

Expedited Work, Unique Work Policies & Hilt Injection

For time-sensitive background tasks (such as sending a chat message or executing a trade order right before the user backgrounds the app), use setExpedited(OutOfQuotaPolicy.RUN_AS_NON_EXPEDITED_WORK_REQUEST). On Android 12+, this leverages JobScheduler's expedited job quota without requiring a visible notification unless the app's quota is exhausted. Furthermore, always enqueue periodic or sync tasks using enqueueUniqueWork or enqueueUniquePeriodicWork with an explicit ExistingWorkPolicy (such as KEEP or APPEND_OR_REPLACE) to prevent duplicate sync workers from stampeding your backend.

❌ Junior Anti-Pattern: GlobalScope & Duplicate Enqueues

// 1. GlobalScope dies immediately when the OS kills the process!

✅ 2027 Senior Production Standard: Hilt + Unique Constrained Work

@HiltWorker
class PortfolioSyncWorker @AssistedInject constructor(
    @Assisted appContext: Context,
    @Assisted params: WorkerParameters,
    private val repository: PortfolioRepository
) : CoroutineWorker(appContext, params) {

    override suspend fun doWork(): Result {
        if (runAttemptCount >= 4) return Result.failure()
        return if (repository.synchronize()) Result.success()
        else Result.retry()
    }

    companion object {
        fun enqueueUniqueSync(workManager: WorkManager) {
            val constraints = Constraints.Builder()
                .setRequiredNetworkType(NetworkType.CONNECTED)
                .setRequiresBatteryNotLow(true)
                .build()
            val request = OneTimeWorkRequestBuilder<PortfolioSyncWorker>()
                .setConstraints(constraints)
                .setExpedited(OutOfQuotaPolicy.RUN_AS_NON_EXPEDITED_WORK_REQUEST)
                .setBackoffCriteria(BackoffPolicy.EXPONENTIAL, 15, TimeUnit.SECONDS)
                .build()
            workManager.enqueueUniqueWork("PortfolioSync", ExistingWorkPolicy.KEEP, request)
        }
    }
}

⚠️ Senior Interview Trap: Android 14+ Foreground Service Types & 10-Minute Execution Cap

Standard JobScheduler jobs are strictly capped at a 10-minute execution window by the Android OS. If a worker promotes itself to long-running foreground execution via setForeground(ForegroundInfo(...)), Android 14+ (API 34+) strictly enforces declaring a matching android:foregroundServiceType (such as dataSync or mediaProcessing) in AndroidManifest.xml and passing that exact constant into the ForegroundInfo constructor. Note that in Android 15+, dataSync foreground services are limited to a maximum of 6 hours within a 24-hour window!

enum class NetworkType { NOT_REQUIRED, CONNECTED, UNMETERED }
enum class ExistingWorkPolicy { KEEP, REPLACE, APPEND_OR_REPLACE }
sealed interface WorkerResult {
    data object Success : WorkerResult
    data object Retry : WorkerResult
    data object Failure : WorkerResult
}

data class WorkConstraints(val network: NetworkType, val requiresBatteryNotLow: Boolean)
data class WorkSpec(val uniqueName: String, val constraints: WorkConstraints, val maxRetries: Int = 3)

class SimulatedWorkManager {
    private val workDb = linkedMapOf<String, WorkSpec>()

    fun enqueueUniqueWork(name: String, policy: ExistingWorkPolicy, spec: WorkSpec): String {
        if (policy == ExistingWorkPolicy.KEEP && workDb.containsKey(name)) {
            return "SKIPPED_DUPLICATE(KEEP)"
        }
        workDb[name] = spec
        return "ENQUEUED_IN_WORKDB"
    }

    fun triggerJobScheduler(name: String, networkOnline: Boolean, batteryLow: Boolean, syncBlock: (attempt: Int) -> WorkerResult) {
        val spec = workDb[name] ?: return
        if (spec.constraints.network == NetworkType.CONNECTED && !networkOnline) {
            println("[JOB-SCHEDULER] Deferring '$name': waiting for NetworkType.CONNECTED")
            return
        }
        if (spec.constraints.requiresBatteryNotLow && batteryLow) {
            println("[JOB-SCHEDULER] Deferring '$name': battery is low")
            return
        }
        var attempt = 0
        while (attempt <= spec.maxRetries) {
            val res = syncBlock(attempt)
            println("[WORKER] '$name' attempt #$attempt -> $res")
            if (res == WorkerResult.Success || res == WorkerResult.Failure) {
                workDb.remove(name)
                return
            }
            attempt++
        }
    }
}

fun main() {
    val wm = SimulatedWorkManager()
    val spec = WorkSpec("AetherDeltaSync", WorkConstraints(NetworkType.CONNECTED, requiresBatteryNotLow = true))

    println("[ENQUEUE 1] ${wm.enqueueUniqueWork(spec.uniqueName, ExistingWorkPolicy.KEEP, spec)}")
    println("[ENQUEUE 2] ${wm.enqueueUniqueWork(spec.uniqueName, ExistingWorkPolicy.KEEP, spec)}")

    wm.triggerJobScheduler("AetherDeltaSync", networkOnline = false, batteryLow = false) { WorkerResult.Success }
    wm.triggerJobScheduler("AetherDeltaSync", networkOnline = true, batteryLow = false) { attempt ->
        if (attempt < 2) WorkerResult.Retry else WorkerResult.Success
    }
}

enum class NetworkType { NOT_REQUIRED, CONNECTED, UNMETERED }
sealed interface WorkOutcome {
    data object Success : WorkOutcome
    data object Retry : WorkOutcome
    data object Failure : WorkOutcome
}

data class ConstraintsSpec(
    val requiredNetworkType: NetworkType,
    val requiresBatteryNotLow: Boolean
)

fun interface TelemetryBatchUploader {
    suspend fun uploadPendingBatch(): Boolean
}

class TelemetryUploadWorker(private val uploader: TelemetryBatchUploader) {
    suspend fun doWork(runAttemptCount: Int): WorkOutcome {
        if (runAttemptCount >= 3) {
            return WorkOutcome.Failure
        }
        return if (uploader.uploadPendingBatch()) {
            WorkOutcome.Success
        } else {
            WorkOutcome.Retry
        }
    }

    fun buildSyncConstraints(): ConstraintsSpec {
        return ConstraintsSpec(
            requiredNetworkType = NetworkType.CONNECTED,
            requiresBatteryNotLow = true
        )
    }
}

Why this works: Bounding runAttemptCount prevents poisoned payloads from draining user battery in an infinite exponential retry loop, while NetworkType.CONNECTED and requiresBatteryNotLow defer execution until OS health conditions are met.

Quiz 1: Code Analysis & Bug Hunt

A developer integrates Hilt with WorkManager using @HiltWorker as shown below, but every time JobScheduler triggers the worker in production, it crashes with a NoSuchMethodException: SyncWorker.<init>(Context, WorkerParameters). Why?

@HiltWorker
class SyncWorker @AssistedInject constructor(
    @Assisted context: Context,
    @Assisted params: WorkerParameters,
    private val syncRepository: SyncRepository
) : CoroutineWorker(context, params) {
    override suspend fun doWork(): Result = Result.success()
}
@AssistedInject is only supported on ListenableWorker subclasses in Java, not Kotlin CoroutineWorker subclasses.
The Context and WorkerParameters parameters must be annotated with @ApplicationContext instead of @Assisted.
SyncRepository must be passed inside WorkerParameters.inputData instead of constructor injection.
The Application class did not disable WorkManager's default ContentProvider initializer in AndroidManifest.xml and implement Configuration.Provider supplying HiltWorkerFactory, so WorkManager fell back to default reflection.

Quiz 2: Production Architectural Reasoning

Why does WorkManager strictly enforce a 10KB serialized size limit on input/output Data objects, and what is the senior architectural pattern when a worker needs to upload a 25MB video or a 5,000-row JSON payload?

WorkManager persists Data blobs directly inside SQLite rows in androidx.work.workdb and passes metadata across Binder IPC to JobScheduler; large payloads must be written to disk or Room first, passing only a lightweight primary key or file URI in Data.
Kotlin's ByteArray serializer overflows 16-bit integer indices if a Data bundle exceeds 10,240 bytes.
You should compress the 25MB payload using Base64 and split it across 2,500 chained OneTimeWorkRequests.
You should hold the 25MB byte array in a companion object static variable and read it inside doWork().
