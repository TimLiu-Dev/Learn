Compile-Time Dependency Injection with Dagger Hilt & KSP

In 2027 Android engineering, legacy annotation processing via kapt (which generated stub Java classes and doubled Gradle build times) is completely extinct. Dagger Hilt on KSP (Kotlin Symbol Processing) analyzes Kotlin AST symbols directly at compile time to generate a zero-reflection, type-safe dependency graph (Dagger*Component). If a dependency is missing or has a circular cycle, your build fails at compile time with an exact dependency trace rather than crashing in production with a runtime NoSuchElementException (a common hazard of service-locator libraries).

Understanding Hilt at a senior level requires mastering two mechanics: the Component Scope Hierarchy and @Binds vs @Provides generated bytecode. Every Hilt component has a strict lifetime: SingletonComponent lives as long as the Application process; ActivityRetainedComponent and ViewModelComponent survive configuration changes and die when the navigation entry/Activity finishes; ActivityComponent is destroyed and recreated on every screen rotation. When binding an interface (MarketRepository) to a constructor-injected implementation (OfflineFirstMarketRepository), always use an abstract fun annotated with @Binds rather than @Provides. @Provides forces Dagger to instantiate the module or call a static factory wrapper method, whereas @Binds is a zero-cost compile-time type alias that emits ~40% less generated factory bytecode!

🌱 Junior Android Dev Mental Model: Over-Scoping with @Singleton

Do NOT slap @Singleton on every Repository or UseCase out of habit! Any object annotated with @Singleton stays pinned in RAM for the entire lifetime of the app process—even after the user logs out or leaves that feature. Only use @Singleton for genuinely stateful process-wide resources (OkHttpClient, RoomDatabase, DataStore) or when caching in memory across features is intentional. Unscoped bindings create a fresh lightweight instance on demand and allow the GC to reclaim memory immediately!

Senior Interview Trap: Scoping Mismatches & Captive Dependencies

A component can only inject dependencies from its own scope or an ancestor scope—never a narrower child scope! For example, injecting an @ActivityScoped tracker or an Activity Context into a @Singleton repository (or @HiltViewModel) fails at compile time (or causes a massive Activity memory leak if forced via a provider), because the Singleton / ViewModel outlives the Activity on rotation.

❌ Junior Anti-Pattern: @Provides for Interface Binding & Over-Scoped UseCase

@Module
@InstallIn(SingletonComponent::class)
object BadDataModule {
    // BUG 1: @Provides generates extra Factory classes when @Binds requires zero runtime code!
    @Provides
    @Singleton
    fun provideMarketRepository(
        api: MarketApi,
        dao: MarketDao
    ): MarketRepository = OfflineFirstMarketRepository(api, dao)

    // BUG 2: Stateless UseCase pinned in RAM forever as @Singleton!
    @Provides
    @Singleton
    fun provideFormatPriceUseCase(): FormatPriceUseCase = FormatPriceUseCase()
}

✅ 2027 Senior Production Standard: Zero-Overhead @Binds + Constructor Injection

// 1. Implementation uses @Inject constructor directly
class OfflineFirstMarketRepository @Inject constructor(
    private val api: MarketApi,
    private val dao: MarketDao
) : MarketRepository

// 2. Interface bound via abstract @Binds in an interface or abstract class
@Module
@InstallIn(SingletonComponent::class)
abstract class DataModule {
    @Binds
    @Singleton
    abstract fun bindMarketRepository(
        impl: OfflineFirstMarketRepository
    ): MarketRepository
}

// 3. Stateless UseCase needs NO module and NO @Singleton — just @Inject constructor!
class FormatPriceUseCase @Inject constructor()

enum class HiltScope { SINGLETON, VIEW_MODEL_SCOPED, UNSCOPED }

class GeneratedComponentGraph {
    private val singletonCache = mutableMapOf<String, String>()
    private val viewModelCache = mutableMapOf<String, String>()
    private var allocationCounter = 0

    fun resolve(typeName: String, scope: HiltScope): String = when (scope) {
        HiltScope.SINGLETON -> singletonCache.getOrPut(typeName) {
            "$typeName@${++allocationCounter}"
        }
        HiltScope.VIEW_MODEL_SCOPED -> viewModelCache.getOrPut(typeName) {
            "$typeName@${++allocationCounter}"
        }
        HiltScope.UNSCOPED -> "$typeName@${++allocationCounter}"
    }

    fun onNavigationEntryCleared() {
        viewModelCache.clear()
        println("[HILT-LIFECYCLE] NavEntry popped -> ViewModelComponent cleared! SingletonComponent retained.")
    }
}

fun main() {
    val graph = GeneratedComponentGraph()
    println("1. Screen A Launch:")
    println("   OkHttpClient (SINGLETON)      -> ${graph.resolve("OkHttpClient", HiltScope.SINGLETON)}")
    println("   TradeStateHolder (VM_SCOPED)  -> ${graph.resolve("TradeStateHolder", HiltScope.VIEW_MODEL_SCOPED)}")
    println("   ValidateUseCase (UNSCOPED)    -> ${graph.resolve("ValidateUseCase", HiltScope.UNSCOPED)}")
    println("2. Screen A Rotation (Config Change):")
    println("   TradeStateHolder (VM_SCOPED)  -> ${graph.resolve("TradeStateHolder", HiltScope.VIEW_MODEL_SCOPED)} (Same instance!)")
    graph.onNavigationEntryCleared()
    println("3. Re-entering Screen A:")
    println("   OkHttpClient (SINGLETON)      -> ${graph.resolve("OkHttpClient", HiltScope.SINGLETON)} (Still same!)")
    println("   TradeStateHolder (VM_SCOPED)  -> ${graph.resolve("TradeStateHolder", HiltScope.VIEW_MODEL_SCOPED)} (Fresh instance!)")
}

import dagger.Binds
import dagger.Module
import dagger.hilt.InstallIn
import dagger.hilt.components.SingletonComponent
import javax.inject.Inject
import javax.inject.Singleton

interface PortfolioRepository {
    fun getAccountId(): String
}

class DefaultPortfolioRepository @Inject constructor() : PortfolioRepository {
    override fun getAccountId(): String = "ACC-2027"
}

@Module
@InstallIn(SingletonComponent::class)
abstract class PortfolioDataModule {
    @Binds
    @Singleton
    abstract fun bindPortfolioRepository(
        impl: DefaultPortfolioRepository
    ): PortfolioRepository
}

Why this works: Using @Inject constructor() teaches Dagger how to construct DefaultPortfolioRepository, while @Binds on an abstract function maps the interface to the implementation at compile time without generating intermediate @Provides factory objects.

Quiz 1: Code Analysis & Bug Hunt

Why does this Hilt module fail to compile under KSP with [Dagger/MissingBinding] MainActivity cannot be provided or a scope incompatibility error?

@Singleton
class BiometricSessionManager @Inject constructor(
    @ActivityContext private val context: Context
) {
    fun promptBiometrics() { /* ... */ }
}
The @ActivityContext qualifier was removed in Hilt 2.51 and replaced by Compose LocalContext.current composition locals.
Classes annotated with @Singleton cannot use @Inject constructors and require explicit @Provides module factory methods.
Dagger KSP processors no longer support javax.inject.Singleton and require migrating all annotations to jakarta.inject.Singleton exclusively.
A @Singleton inside SingletonComponent lives process-wide and cannot depend on narrower @ActivityContext bindings from ActivityComponent.

Quiz 2: Production Architectural Reasoning

In Dagger Hilt, when must you use @Provides instead of @Binds?

Use @Provides for third-party classes or builders without @Inject constructors, and @Binds for interface implementations.
Use @Provides exclusively for abstract project interfaces and @Binds when configuring external third-party builder instances.
The @Binds annotation relies on slow runtime classpath reflection whereas @Provides generates compile-time factory classes.
Abstract @Binds declarations are restricted to ActivityComponent modules and cannot be installed inside SingletonComponent containers.
