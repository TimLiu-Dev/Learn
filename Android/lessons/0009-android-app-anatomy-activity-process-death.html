Android App Anatomy, ComponentActivity & Process Death

Master the Android application lifecycle, ComponentActivity, SavedStateHandle, and surviving system process death.

Recommended Primary Source
Google Android: Understanding the Activity Lifecycle & Process Death
Official Documentation →

Every Android application runs inside an isolated Linux process (with its own unique UID and SELinux sandbox) forked from the Zygote process, which preloads framework classes and Android Runtime (ART) resources into shared copy-on-write memory pages. When the user switches to a camera or heavy game while your app is in the background (STOPPED state), the Linux kernel's Low Memory Killer Daemon (lmkd) can kill your app's OS process silently without calling onDestroy().

Understanding the three distinct survival mechanisms in Android is a foundational requirement for every Senior Android Engineer:

  • Recomposition (remember): Survives UI recompositions in memory, but is wiped on configuration changes (rotation, foldable posture change) AND system process death.
  • Configuration Changes (ViewModel): Retained in memory across Activity recreation via NonConfigurationInstances, but completely wiped on system-initiated process death because the entire Linux heap is destroyed!
  • System Process Death (SavedStateHandle / rememberSaveable / Persistent Storage): Prior to stopping, Android serializes the state registry into an in-memory Binder parcel held by system_server. When the user returns to your app from Recents after process death, the OS spawns a fresh process, recreates the Activity back stack, and restores the saved Bundle into SavedStateHandle and rememberSaveable.
🌱 Junior Android Dev Mental Model: The 500KB–1MB Binder Transaction Limit

Never store full network responses, large lists of domain objects, or Bitmaps inside SavedStateHandle or rememberSaveable! The saved instance state Bundle crosses process boundaries to system_server over Android's Binder IPC buffer, which has a shared 1MB ceiling across all in-flight transactions (throwing TransactionTooLargeException at ~500KB). Store only minimal navigation/filter keys and transient user input (e.g., selectedOrderId, searchQuery, draftComment) in SavedStateHandle, and let your Repository reload the full data from Room/SQLite!

2027 Production Pattern: Reactive SavedStateHandle.getStateFlow()

In a modern ViewModel, you should not manually read and write Bundle keys in Activity.onSaveInstanceState(). Hilt automatically injects SavedStateHandle directly into your ViewModel constructor. By binding filter keys via savedStateHandle.getStateFlow("selected_tab", "ALL") and combining them with your Room database Flow, your screen automatically restores its exact state after process death with zero lifecycle boilerplate.

⚠️ Senior Interview Trap: Why In-Memory Singletons & Static Caches Cause Post-Death NPEs!

A classic production crash happens when a developer stores var currentUser: User? = null in an object SessionCache singleton (initialized on Screen A) and reads SessionCache.currentUser!! on Screen C. During normal navigation, this works. When the user backgrounds the app on Screen C, the OS kills the process, and the user reopens the app from Recents: Android recreates Screen C directly (NOT Screen A!) in a brand-new OS process. SessionCache.currentUser is now null, crashing Screen C immediately on startup! Always back session and screen data with persistent storage (DataStore / Room) + SavedStateHandle IDs.

❌ Junior Anti-Pattern: Volatile Memory State & Bloated Bundles

class OrderDetailViewModel(
    private val savedState: SavedStateHandle
) : ViewModel() {
    // BUG 1: Wiped to null after background process death!
    var orderId: String? = null

    fun cacheFullList(orders: List<OrderDto>) {
        // BUG 2: Storing 2,000 objects in SavedStateHandle crashes
        // with TransactionTooLargeException over Binder IPC!
        savedState["all_orders_dump"] = ArrayList(orders)
    }
}

✅ 2027 Senior Standard: Lightweight ID in SavedStateHandle + Room

class OrderDetailViewModel(
    private val savedState: SavedStateHandle,
    private val repository: OrderRepository
) : ViewModel() {
    // Survives both rotation AND system process death (< 100 bytes in Binder)
    val selectedOrderId: StateFlow<String?> =
        savedState.getStateFlow(KEY_ORDER_ID, null)

    val orderDetails: StateFlow<OrderUiState> = selectedOrderId
        .flatMapLatest { id ->
            if (id == null) flowOf(OrderUiState.Empty)
            else repository.observeOrderFromRoom(id)
        }
        .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), OrderUiState.Loading)

    fun selectOrder(id: String) { savedState[KEY_ORDER_ID] = id }
    companion object { private const val KEY_ORDER_ID = "selected_order_id" }
}

Cold Start Hygiene: installSplashScreen() & Readiness Gate

In ComponentActivity.onCreate(), always invoke val splashScreen = installSplashScreen() (androidx.core:core-splashscreen) before super.onCreate(savedInstanceState) and enableEdgeToEdge(). Use splashScreen.setKeepOnScreenCondition { viewModel.uiState.value is UiState.Loading } to hold the OS icon transition cleanly for a few milliseconds while asynchronous DataStore/Room auth state hydrates—never block onCreate() with runBlocking!

// Simulates Android's SavedStateHandle + system_server Binder state restoration across Process Death
class SimulatedSavedStateHandle(initialSnapshot: Map<String, Any?> = emptyMap()) {
    private val stateMap = initialSnapshot.toMutableMap()

    operator fun <T> set(key: String, value: T) {
        // Guard against TransactionTooLargeException (> 512KB limit simulation)
        val estimatedBytes = value.toString().length * 2
        require(estimatedBytes < 10_000) { "TransactionTooLargeException: payload too large for Binder!" }
        stateMap[key] = value
    }

    @Suppress("UNCHECKED_CAST")
    fun <T> getOrDefault(key: String, default: T): T = (stateMap[key] as? T) ?: default

    fun serializeToSystemServerBundle(): Map<String, Any?> = stateMap.toMap()
}

class FilterViewModel(private val savedState: SimulatedSavedStateHandle) {
    // Volatile field: lost on process death!
    var volatileScrollOffsetPx: Int = 0

    // Process-death resilient properties backed by SavedStateHandle
    var activeCategory: String
        get() = savedState.getOrDefault("key_category", "ALL")
        set(value) { savedState["key_category"] = value }

    var searchQuery: String
        get() = savedState.getOrDefault("key_query", "")
        set(value) { savedState["key_query"] = value }
}

fun main() {
    val initialHandle = SimulatedSavedStateHandle()
    val vmBeforeDeath = FilterViewModel(initialHandle).apply {
        activeCategory = "KOTLIN_2_2"
        searchQuery = "SavedStateHandle"
        volatileScrollOffsetPx = 1480
    }
    println("[ACTIVE PROCESS] category=${vmBeforeDeath.activeCategory}, query='${vmBeforeDeath.searchQuery}', volatileScroll=${vmBeforeDeath.volatileScrollOffsetPx}")

    // OS kills background process; system_server retains serialized Bundle
    val binderSnapshot = initialHandle.serializeToSystemServerBundle()
    println("[OS LMKD] Process killed in background! Recreating fresh process from Binder bundle...")

    val vmAfterDeath = FilterViewModel(SimulatedSavedStateHandle(binderSnapshot))
    println("[RESTORED PROCESS] category=${vmAfterDeath.activeCategory}, query='${vmAfterDeath.searchQuery}', volatileScroll=${vmAfterDeath.volatileScrollOffsetPx}")
}

interface SavedStateStore {
    operator fun set(key: String, value: String)
    operator fun get(key: String): String?
}

class TicketDraftManager(private val savedState: SavedStateStore) {
    fun saveDraft(ticketId: String, draftComment: String) {
        require(draftComment.length <= 2000) {
            "Draft exceeds safe Binder IPC threshold"
        }
        savedState["ticket_id"] = ticketId
        savedState["draft_comment"] = draftComment
    }

    fun restoreDraft(): Pair<String, String>? {
        val id = savedState["ticket_id"] ?: return null
        val comment = savedState["draft_comment"] ?: ""
        return Pair(id, comment)
    }
}

Why this works: Enforcing size bounds protects the 1MB Binder transaction buffer from TransactionTooLargeException, while persisting lightweight keys and draft inputs in SavedStateStore guarantees seamless restoration after LMKD kills the background process.

A user navigates from LoginActivity -> HomeActivity -> CheckoutActivity. The user switches to the Camera app to scan a QR code, and the Android OS kills the app's background process to free RAM. When the user switches back to the app via Recents, what happens?

Android cold-starts the entire application task stack from LoginActivity, ensuring CheckoutViewModel is never instantiated automatically.
Android recreates CheckoutActivity with its restored SavedStateHandle, but InMemorySession.authUserId is null, throwing a fatal NullPointerException.
Both savedStateHandle['cart_id'] and InMemorySession.authUserId survive process termination because Kotlin object singletons utilize Zygote shared memory.
CheckoutViewModel survives in RAM across background process termination because ViewModelStore instances reside inside system_server memory.

Quiz 2: Production Architectural Reasoning

Why is saving a 600KB JSON response or a large List<ProductParcelable> into SavedStateHandle / onSaveInstanceState an architectural anti-pattern on Android?

SavedStateHandle encrypts all entries using Android Keystore RSA keys, restricting main-thread payloads below 256 bytes.
Android 15+ automatically wipes the application Room SQLite database whenever SavedStateHandle serializes any Parcelable objects.
Saved state Bundles cross Binder IPC to system_server, where exceeding the 1MB buffer throws TransactionTooLargeException.
SavedStateHandle only supports primitive Int and Boolean values under Kotlin 2.x multiplatform serialization compiler rules.
