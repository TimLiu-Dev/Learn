Reactive Room Queries (`InvalidationTracker`) & Zero-Data-Loss Schema Migrations

When a Room `@Dao` method returns a Flow<List<AlertEntity>>, how does it know when to re-emit? Under the hood, Room registers an observer in its InvalidationTracker linked to the specific table names referenced by your `@Query` (`alerts`). Whenever any `INSERT`, `UPDATE`, `UPSERT`, or `DELETE` commits to the `alerts` table, SQLite triggers a table modification flag, and `InvalidationTracker` asynchronously re-executes your `SELECT` query on Room's background query executor—pushing the fresh `List<AlertEntity>` downstream!

However, there is a crucial nuance: `InvalidationTracker` tracks at the table level, not the row level! If you observe `observeAssetById("BTC"): Flow<AssetEntity>`, and a background sync updates the `"ETH"` row in the `assets` table, Room re-runs the `"BTC"` query and emits an identical `AssetEntity("BTC", ...)` instance. Always append .distinctUntilChanged() to single-row or filtered Room `Flow`s so downstream ViewModels and Composables ignore redundant table-level invalidations!

Equally critical in production is Database Schema Migration. When you bump `@Database(version = 2)` in an app update:

  • AutoMigration(from = 1, to = 2): Handles simple additions (`ADD COLUMN`), table creations, or renames/deletions (when paired with an `@RenameColumn` / `@DeleteColumn` `AutoMigrationSpec`) automatically at compile time using exported Room schema JSON files (`room.schemaLocation`).
  • Manual Migration(1, 2): Required for complex data transformations (e.g., splitting a full name column, migrating data across tables, or recreating a table with altered constraints). Every migration must be verified in CI using MigrationTestHelper against exported `1.json`, `2.json` schema files!

🌱 Junior Android Dev Mental Model: Why `fallbackToDestructiveMigration()` is a Career-Limiting Bug

Calling .fallbackToDestructiveMigration() on `Room.databaseBuilder` tells Room: "If I forgot to write a migration when bumping the version, silently DROP ALL TABLES and wipe the user's local database!" Never ship `fallbackToDestructiveMigration()` in production if any table holds unsynced user drafts, encrypted keys, or offline history!

Senior Interview Trap: SQLite's Exact Column Type Affinity in Manual `Migration`

When writing a manual `Migration(1, 2)` with `db.execSQL("ALTER TABLE alerts ADD COLUMN is_active INTEGER NOT NULL DEFAULT 1")`, Room inspects the table's `PRAGMA table_info(alerts)` immediately after your migration runs and compares every column's name, type affinity (`TEXT`, `INTEGER`, `REAL`), `notNull` constraint, and `defaultValue` against what the `@Entity` class expects. Even a single mismatch (like omitting `NOT NULL` for a non-nullable Kotlin `Boolean` or `Int` property) crashes on startup with `IllegalStateException: Migration didn't properly handle...`!

❌ Junior Anti-Pattern: Destructive Migration & Unfiltered Table Invalidation

// BUG 1: Wipes user's entire SQLite database on version bump!
Room.databaseBuilder(context, AppDb::class.java, "aether.db")
    .fallbackToDestructiveMigration()
    .build()

// BUG 2: Re-emits BTC every time ETH or SOL updates in the 'assets' table!
fun observeBtc(dao: AssetDao): Flow<AssetEntity> =
    dao.observeAssetById("BTC")

✅ 2027 Senior Production Standard: Verified Migration + distinctUntilChanged()

val MIGRATION_1_2 = object : Migration(1, 2) {
    override fun migrate(db: SupportSQLiteDatabase) {
        db.execSQL(
            "ALTER TABLE price_alerts ADD COLUMN trigger_count INTEGER NOT NULL DEFAULT 0"
        )
    }
}

Room.databaseBuilder(context, AppDb::class.java, "aether.db")
    .addMigrations(MIGRATION_1_2)
    .build()

// Suppresses false-positive table-level InvalidationTracker emissions:
fun observeAsset(dao: AssetDao, symbol: String): Flow<AssetEntity?> =
    dao.observeAssetById(symbol).distinctUntilChanged()

import androidx.room.migration.Migration
import androidx.sqlite.db.SupportSQLiteDatabase
import kotlinx.coroutines.flow.Flow
import kotlinx.coroutines.flow.distinctUntilChanged

interface AlertDao {
    fun observeAlert(id: String): Flow<String>
}

val MIGRATION_1_2 = object : Migration(1, 2) {
    override fun migrate(db: SupportSQLiteDatabase) {
        db.execSQL("ALTER TABLE alerts ADD COLUMN is_enabled INTEGER NOT NULL DEFAULT 1")
    }
}

fun observeDistinctAlert(dao: AlertDao, id: String): Flow<String> {
    return dao.observeAlert(id).distinctUntilChanged()
}

Why this works: Migration(1, 2) alters the existing alerts table with an explicit NOT NULL DEFAULT 1 constraint matching Kotlin's non-null Boolean mapping, while .distinctUntilChanged() filters out redundant emissions triggered when unrelated rows in the alerts table are modified.

Quiz 1: Code Analysis & Bug Hunt

A developer added `val priority: Int = 0` to `AlertEntity`, bumped `@Database(version = 2)`, and wrote the manual migration below. Why does the app crash on startup for upgrading users with `IllegalStateException: Migration didn't properly handle: alerts`?

@Entity(tableName = "alerts")
data class AlertEntity(
    @PrimaryKey val id: String,
    val priority: Int = 0 // Non-nullable Kotlin Int!
)

val MIGRATION_1_2 = object : Migration(1, 2) {
    override fun migrate(db: SupportSQLiteDatabase) {
        db.execSQL("ALTER TABLE alerts ADD COLUMN priority INTEGER DEFAULT 0")
    }
}
SQLite does not support `ALTER TABLE ... ADD COLUMN` and requires dropping the table.
In Kotlin, a non-nullable `val priority: Int` maps to a SQLite column with `notNull = true`, but the SQL statement omitted `NOT NULL` (`INTEGER DEFAULT 0` instead of `INTEGER NOT NULL DEFAULT 0`), causing Room's post-migration schema verification to fail.
Kotlin `Int` maps to `LONG` in SQLite, not `INTEGER`.
`Migration(1, 2)` only runs on fresh installs, not upgrades from version 1.

Quiz 2: Production Architectural Reasoning

If a database transitions across versions `1 -> 2 -> 3` over two months, and a user who hasn't updated their app since version `1` installs version `3` from the Play Store, how does Room execute migrations if you registered `MIGRATION_1_2` and `MIGRATION_2_3`?

Room crashes unless you manually write an `N * (N - 1)` matrix of migrations for every possible historical version pair.
Room skips `MIGRATION_1_2` and only runs `MIGRATION_2_3` directly on the v1 schema.
Room's migration path resolver automatically chains `MIGRATION_1_2` followed by `MIGRATION_2_3` sequentially inside a transaction (unless a direct shortcut `MIGRATION_1_3` is also provided), bringing the user from v1 to v3 with zero data loss.
Google Play forces the user to install version 2 before downloading version 3.
