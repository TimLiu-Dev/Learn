Reactive Room Queries (<code>InvalidationTracker</code>) & Zero-Data-Loss Schema Migrations

When a Room <code>@Dao</code> method returns a Flow<List<AlertEntity>>, how does it know when to re-emit? Under the hood, Room registers an observer in its InvalidationTracker linked to the specific table names referenced by your <code>@Query</code> (<code>alerts</code>). Whenever any <code>INSERT</code>, <code>UPDATE</code>, <code>UPSERT</code>, or <code>DELETE</code> commits to the <code>alerts</code> table, SQLite triggers a table modification flag, and <code>InvalidationTracker</code> asynchronously re-executes your <code>SELECT</code> query on Room's background query executor—pushing the fresh <code>List<AlertEntity></code> downstream!

However, there is a crucial nuance: <code>InvalidationTracker</code> tracks at the table level, not the row level! If you observe <code>observeAssetById("BTC"): Flow<AssetEntity></code>, and a background sync updates the <code>"ETH"</code> row in the <code>assets</code> table, Room re-runs the <code>"BTC"</code> query and emits an identical <code>AssetEntity("BTC", ...)</code> instance. Always append .distinctUntilChanged() to single-row or filtered Room <code>Flow</code>s so downstream ViewModels and Composables ignore redundant table-level invalidations!

Equally critical in production is Database Schema Migration. When you bump <code>@Database(version = 2)</code> in an app update:

  • AutoMigration(from = 1, to = 2): Handles simple additions (<code>ADD COLUMN</code>), table creations, or renames/deletions (when paired with an <code>@RenameColumn</code> / <code>@DeleteColumn</code> <code>AutoMigrationSpec</code>) automatically at compile time using exported Room schema JSON files (<code>room.schemaLocation</code>).
  • Manual Migration(1, 2): Required for complex data transformations (e.g., splitting a full name column, migrating data across tables, or recreating a table with altered constraints). Every migration must be verified in CI using MigrationTestHelper against exported <code>1.json</code>, <code>2.json</code> schema files!

🌱 Junior Android Dev Mental Model: Why <code>fallbackToDestructiveMigration()</code> is a Career-Limiting Bug

Calling .fallbackToDestructiveMigration() on <code>Room.databaseBuilder</code> tells Room: "If I forgot to write a migration when bumping the version, silently DROP ALL TABLES and wipe the user's local database!" Never ship <code>fallbackToDestructiveMigration()</code> in production if any table holds unsynced user drafts, encrypted keys, or offline history!

Senior Interview Trap: SQLite's Exact Column Type Affinity in Manual <code>Migration</code>

When writing a manual <code>Migration(1, 2)</code> with <code>db.execSQL("ALTER TABLE alerts ADD COLUMN is_active INTEGER NOT NULL DEFAULT 1")</code>, Room inspects the table's <code>PRAGMA table_info(alerts)</code> immediately after your migration runs and compares every column's name, type affinity (<code>TEXT</code>, <code>INTEGER</code>, <code>REAL</code>), <code>notNull</code> constraint, and <code>defaultValue</code> against what the <code>@Entity</code> class expects. Even a single mismatch (like omitting <code>NOT NULL</code> for a non-nullable Kotlin <code>Boolean</code> or <code>Int</code> property) crashes on startup with <code>IllegalStateException: Migration didn't properly handle...</code>!

❌ Junior Anti-Pattern: Destructive Migration & Unfiltered Table Invalidation

// BUG 1: Wipes user's entire SQLite database on version bump!
Room.databaseBuilder(context, AppDb::class.java, "aether.db")
    .fallbackToDestructiveMigration()
    .build()

// BUG 2: Re-emits BTC every time ETH or SOL updates in the 'assets' table!
fun observeBtc(dao: AssetDao): Flow<AssetEntity> =
    dao.observeAssetById("BTC")

✅ 2027 Senior Production Standard: Verified Migration + distinctUntilChanged()

val MIGRATION_1_2 = object : Migration(1, 2) {
    override fun migrate(db: SupportSQLiteDatabase) {
        db.execSQL(
            "ALTER TABLE price_alerts ADD COLUMN trigger_count INTEGER NOT NULL DEFAULT 0"
        )
    }
}

Room.databaseBuilder(context, AppDb::class.java, "aether.db")
    .addMigrations(MIGRATION_1_2)
    .build()

// Suppresses false-positive table-level InvalidationTracker emissions:
fun observeAsset(dao: AssetDao, symbol: String): Flow<AssetEntity?> =
    dao.observeAssetById(symbol).distinctUntilChanged()

data class ColumnSchema(val name: String, val type: String, val notNull: Boolean, val defaultVal: String?)

class RoomSchemaValidator(val version: Int, val columns: MutableMap<String, ColumnSchema>) {
    fun execAlterAddColumn(name: String, type: String, notNull: Boolean, defaultVal: String?) {

        columns[name] = ColumnSchema(name, type, notNull, defaultVal)

    fun verifyMatchesEntity(expected: Map<String, ColumnSchema>) {
        check(columns == expected) {
            "IllegalStateException: Migration didn't properly handle table!

Found:    $columns"
        }

    }
}

import androidx.room.migration.Migration
import androidx.sqlite.db.SupportSQLiteDatabase
import kotlinx.coroutines.flow.Flow
import kotlinx.coroutines.flow.distinctUntilChanged

interface AlertDao {
    fun observeAlert(id: String): Flow<String>
}

val MIGRATION_1_2 = object : Migration(1, 2) {
    override fun migrate(db: SupportSQLiteDatabase) {
        db.execSQL("ALTER TABLE alerts ADD COLUMN is_enabled INTEGER NOT NULL DEFAULT 1")
    }
}

fun observeDistinctAlert(dao: AlertDao, id: String): Flow<String> {
    return dao.observeAlert(id).distinctUntilChanged()
}

Why this works: Migration(1, 2) alters the existing alerts table with an explicit NOT NULL DEFAULT 1 constraint matching Kotlin's non-null Boolean mapping, while .distinctUntilChanged() filters out redundant emissions triggered when unrelated rows in the alerts table are modified.

Quiz 1: Code Analysis & Bug Hunt

A developer added <code>val priority: Int = 0</code> to <code>AlertEntity</code>, bumped <code>@Database(version = 2)</code>, and wrote the manual migration below. Why does the app crash on startup for upgrading users with <code>IllegalStateException: Migration didn't properly handle: alerts</code>?

@Entity(tableName = "alerts")
data class AlertEntity(
    @PrimaryKey val id: String,
    val priority: Int = 0 // Non-nullable Kotlin Int!
)

val MIGRATION_1_2 = object : Migration(1, 2) {
    override fun migrate(db: SupportSQLiteDatabase) {
        db.execSQL("ALTER TABLE alerts ADD COLUMN priority INTEGER DEFAULT 0")
    }
}
Android SQLite engines forbid ALTER TABLE ADD COLUMN statements and require dropping existing database tables.
Non-nullable Kotlin properties require NOT NULL constraints, so omitting NOT NULL fails Room schema verification.
Kotlin primitive Int entity properties require LONG storage affinity inside SQLite schemas rather than INTEGER.
The registered Migration instance only executes during fresh application installs rather than database version upgrades.

Quiz 2: Production Architectural Reasoning

If a database transitions across versions <code>1 -> 2 -> 3</code> over two months, and a user who hasn't updated their app since version <code>1</code> installs version <code>3</code> from the Play Store, how does Room execute migrations if you registered <code>MIGRATION_1_2</code> and <code>MIGRATION_2_3</code>?

Room crashes unless developers register a complete matrix of migrations covering every historical version pair.
Room skips MIGRATION_1_2 completely and executes only MIGRATION_2_3 directly against the existing version 1 database.
Room chains MIGRATION_1_2 and MIGRATION_2_3 sequentially in one transaction, upgrading version 1 without data loss.
Google Play forces outdated devices to install intermediate release version two before downloading version three.
