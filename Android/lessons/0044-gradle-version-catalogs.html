Gradle Version Catalogs (libs.versions.toml)

Centralize and standardize dependencies across 30+ modules with Gradle Version Catalogs and bundles.

Recommended Primary Source
Google Android: Migrate your build to version catalogs
Official Documentation →

In a 20-module enterprise Android project, managing library versions via hardcoded strings or legacy buildSrc/Versions.kt constants causes painful maintenance and build cache invalidations. Whenever you bumped a single version number inside buildSrc, Gradle invalidated the entire buildscript classpath across every module in the project! Gradle Version Catalogs (gradle/libs.versions.toml) solve this cleanly with type-safe accessors and native IDE Renovate/Dependabot integration.

Under the Hood: The 4 Sections of libs.versions.toml

Gradle parses gradle/libs.versions.toml during configuration and generates type-safe Kotlin DSL accessors where dashes (-) and underscores (_) become dot-separated camelCase properties (e.g., androidx-lifecycle-runtime-compose becomes libs.androidx.lifecycle.runtime.compose). The TOML catalog is structured into four canonical sections:

  • [versions]: Declares reusable version variables and version constraints (e.g., kotlin = "2.1.10", composeBom = "2026.02.00").
  • [libraries]: Maps logical aliases to Maven coordinates using group, name, and version.ref (or versionless BOM-managed artifacts).
  • [bundles]: Groups related libraries that are always added together via implementation(libs.bundles.ktor).
  • [plugins]: Declares Gradle plugin IDs and versions applied via alias(libs.plugins.android.application).
🌱 Junior Android Dev Mental Model: BOMs + Version Catalogs

When using the Jetpack Compose BOM (Bill of Materials) in libs.versions.toml, only the BOM entry itself specifies a version.ref! Individual Compose libraries (androidx.compose.ui, androidx.compose.material3) omit the version field entirely in the TOML file because the BOM pins their exact compatible versions automatically.

❌ Junior Anti-Pattern: Hardcoded Strings & Version Drift

// :feature:market/build.gradle.kts
dependencies {
    // Version drift across modules causes runtime NoSuchMethodError!
    implementation("androidx.compose.material3:material3:1.2.0")
    implementation("io.ktor:ktor-client-core:2.3.4")
    implementation("io.ktor:ktor-client-okhttp:2.3.1") // Mismatched!
}

✅ 2027 Senior Production Standard: Type-Safe TOML Catalog

# gradle/libs.versions.toml
[versions]
composeBom = "2026.02.00"
ktor = "3.0.3"

[libraries]
androidx-compose-bom = { group = "androidx.compose", name = "compose-bom", version.ref = "composeBom" }
androidx-compose-material3 = { group = "androidx.compose.material3", name = "material3" }
ktor-client-core = { group = "io.ktor", name = "ktor-client-core", version.ref = "ktor" }
ktor-client-okhttp = { group = "io.ktor", name = "ktor-client-okhttp", version.ref = "ktor" }

[bundles]
ktor-client = ["ktor-client-core", "ktor-client-okhttp"]

⚠️ Senior Interview Trap: Overusing [bundles] & Unused Transitive Bloat

A common anti-pattern is creating a massive [bundles] entry like core-all = ["room", "ktor", "coil", "biometric", "workmanager"] and adding implementation(libs.bundles.core.all) to every module. This forces every module to resolve and configure dependencies it never uses, slowing down Gradle dependency resolution and violating principle-of-least-privilege module encapsulation. Only bundle libraries that genuinely form a single logical unit (like Ktor client core + serialization + content negotiation).

KOTLIN 2.X VersionCatalogParser.kt 
data class LibraryAlias(val aliasKey: String, val group: String, val name: String, val versionRef: String?)

class VersionCatalogSimulator(
    private val versions: Map<String, String>,
    private val libraries: List<LibraryAlias>
) {
    fun toKotlinDslAccessor(aliasKey: String): String =
        "libs." + aliasKey.replace("-", ".").replace("_", ".")

    fun resolveCoordinates(aliasKey: String, activeBomVersionMap: Map<String, String> = emptyMap()): String {
        val lib = libraries.first { it.aliasKey == aliasKey }
        val resolvedVersion = lib.versionRef?.let { versions[it] }
            ?: activeBomVersionMap["${lib.group}:${lib.name}"]
            ?: "BOM_MANAGED"
        return "${lib.group}:${lib.name}:$resolvedVersion"
    }
}

fun main() {
    val versions = mapOf("kotlin" to "2.1.10", "composeBom" to "2026.02.00", "room" to "2.7.0")
    val libraries = listOf(
        LibraryAlias("androidx-compose-bom", "androidx.compose", "compose-bom", "composeBom"),
        LibraryAlias("androidx-compose-material3", "androidx.compose.material3", "material3", null),
        LibraryAlias("androidx-room-runtime", "androidx.room", "room-runtime", "room")
    )
    val bomLocks = mapOf("androidx.compose.material3:material3" to "1.4.0-bom")
    val catalog = VersionCatalogSimulator(versions, libraries)

    for (lib in libraries) {
        val dsl = catalog.toKotlinDslAccessor(lib.aliasKey)
        val coord = catalog.resolveCoordinates(lib.aliasKey, bomLocks)
        println("$dsl -> $coord")
    }
}

class VersionCatalogFormatter {
    fun toAccessor(tomlKey: String): String {
        return "libs." + tomlKey.trim().replace("-", ".")
    }

    fun formatLibraryEntry(
        alias: String,
        group: String,
        name: String,
        versionRef: String
    ): String {
        return "$alias = { group = \"$group\", name = \"$name\", version.ref = \"$versionRef\" }"
    }
}

Why this works: Gradle's TOML catalog parser maps hyphenated keys directly to nested type-safe property accessors under libs, while version.ref links multiple artifacts to a single source-of-truth version string.

Quiz 1: Code Analysis & Bug Hunt

Examine this root build.gradle.kts and module build.gradle.kts setup. Why is apply false required on plugins in the root build.gradle.kts?

// Root build.gradle.kts
plugins {
    alias(libs.plugins.android.application) apply false
    alias(libs.plugins.android.library) apply false
    alias(libs.plugins.kotlin.compose) apply false
    alias(libs.plugins.hilt) apply false
}
Declaring apply false disables Gradle configuration caching so plugins can mutate subproject configurations at runtime.
Without apply false, Gradle downloads every declared library inside libs.versions.toml twice during project synchronization runs.
Specifying apply false instructs the R8 shrinker to strip plugin metadata annotations from release builds.
apply false loads versioned plugin jars onto the root buildscript classpath without applying them here.

Quiz 2: Production Architectural Reasoning

When declaring Jetpack Compose libraries in gradle/libs.versions.toml alongside androidx-compose-bom, what happens if you accidentally hardcode an older version.ref on androidx-compose-material3 while also importing the Compose BOM?

The explicit material3 version overrides BOM constraints, risking binary incompatibility and NoSuchMethodError with Compose UI.
Gradle refuses to parse libs.versions.toml catalogs whenever any library entry omits an explicit version.ref property.
The Compose BOM dependency resolver automatically deletes the conflicting version.ref line inside libs.versions.toml during sync.
Android Studio disables interactive @Preview rendering whenever a Compose BOM is imported inside multi-module projects.
