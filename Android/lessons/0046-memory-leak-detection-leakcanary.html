Memory Leak Detection with LeakCanary

Track GC roots, detect retained Activity/Context instances, and eliminate memory leaks with LeakCanary.

Recommended Primary Source
Square LeakCanary: Fundamentals of Memory Leaks
Official Documentation →

A memory leak occurs when an object is no longer needed by the app, but a static reference or uncancelled coroutine retains a reference to it, preventing the Java Garbage Collector (GC) from freeing its memory. In Android, leaking an Activity or Context also leaks the entire window hierarchy, view tree, and bitmaps (often 50MB+ per leak)!

🌱 Junior Android Dev Mental Model: Top 3 Memory Leak Causes
  1. Static Fields: Storing a Context or Activity in a singleton or companion object.
  2. Uncancelled Coroutines: Launching a coroutine in GlobalScope that references an Activity or ViewModel.
  3. Listeners: Registering a sensor or location callback without unregistering in onDispose.

Interactive Code Practice

Write a safe context holder class ContextHolder that stores 'val applicationContext: Any' passed in its constructor, preventing retention of short-lived Activity contexts.

LeakCanaryFix.kt
Test Runner Output
💡 Guided Progressive Hint
🎯 Reference Production Solution 
class ContextHolder(context: Any) {
    val applicationContext: Any = context
}

Why this works: Holding applicationContext rather than an Activity context avoids leaking the Activity and its associated UI resources when the Activity is destroyed.
