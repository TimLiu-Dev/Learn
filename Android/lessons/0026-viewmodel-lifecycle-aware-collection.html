Lifecycle-Aware Flow Collection: `collectAsStateWithLifecycle`, `stateIn` & `SavedStateHandle`

Connecting a reactive Kotlin `Flow` to an Android UI requires bridging two different lifecycles: the ViewModel lifecycle (which survives configuration changes and lives until the navigation destination is popped or the Activity finishes) and the UI View/Composition lifecycle (which stops whenever the user sends the app to the background, locks their phone, or opens another Activity on top).

If your Composable collects an upstream database, sensor, or WebSocket flow using raw collectAsState(), collection stays active at `Lifecycle.State.CREATED` while the app is in the background—wasting CPU, draining battery, and burning cellular data for invisible screens! The 2027 Android standard is two-fold:

  1. In the UI (`@Composable`): Always collect with collectAsStateWithLifecycle() (`androidx.lifecycle:lifecycle-runtime-compose`), which uses `repeatOnLifecycle(Lifecycle.State.STARTED)` under the hood to cancel upstream collection when the app goes to background (`ON_STOP`) and restart it when foregrounded (`ON_START`).
  2. In the ViewModel: Convert cold upstream flows into hot `StateFlow`s using .stateIn(scope = viewModelScope, started = SharingStarted.WhileSubscribed(5_000), initialValue = ...). The 5,000ms grace timeout is critical: during a screen rotation, the Activity is destroyed and recreated in ~150ms. The 5-second window keeps the upstream flow alive across configuration changes without restarting expensive queries, yet cancels upstream work 5 seconds after the user actually leaves the app!
🌱 Junior Android Dev Mental Model: ViewModel != Process Death Survival!

A ViewModel survives Configuration Changes (rotation, dark mode toggle, foldable posture change) in RAM. It does NOT survive System-Initiated Process Death (when the OS kills your backgrounded app to reclaim memory). Any user input or transient filter ID that must survive process death must be stored in SavedStateHandle (via savedStateHandle.getStateFlow("key", default))!

Senior Interview Trap: Initializing Network Calls in `init {}` vs Cold Flow `stateIn`

When you trigger an imperative load inside `ViewModel.init { loadData() }`, the data is fetched once when the ViewModel is created, and never refreshes after the app returns from a long background session—or worse, runs side effects during unit test instantiation before test dispatchers or mocks are configured. Driving state reactively from a cold flow (`combine(savedStateHandle.getStateFlow(...), repository.observeStream()).stateIn(viewModelScope, WhileSubscribed(5_000), Loading)`) starts lazily on first subscription and automatically pauses/resumes with the lifecycle.

❌ Junior Anti-Pattern: SharingStarted.Eagerly + Raw collectAsState()

class BadTickerViewModel(repo: TickerRepo) : ViewModel() {
    // BUG 1: Eagerly keeps WebSocket open 24/7 even when app is backgrounded!
    val uiState = repo.streamLivePrices()
        .stateIn(viewModelScope, SharingStarted.Eagerly, TickerUiState.Loading)
}

@Composable
fun BadTickerScreen(vm: TickerViewModel) {
    // BUG 2: collectAsState() never stops collecting on ON_STOP!
    val state by vm.uiState.collectAsState()
    Text(state.toString())
}

✅ 2027 Senior Production Standard: WhileSubscribed(5_000) + collectAsStateWithLifecycle

class TickerViewModel(
    savedStateHandle: SavedStateHandle,
    repo: TickerRepo
) : ViewModel() {
    val selectedTimeframe: StateFlow<String> =
        savedStateHandle.getStateFlow(key = "timeframe", initialValue = "24H")

    val uiState: StateFlow<TickerUiState> = selectedTimeframe
        .flatMapLatest { tf -> repo.streamLivePrices(tf) }
        .stateIn(
            scope = viewModelScope,
            started = SharingStarted.WhileSubscribed(stopTimeoutMillis = 5_000),
            initialValue = TickerUiState.Loading
        )
}

@Composable
fun TickerScreen(vm: TickerViewModel) {
    val state by vm.uiState.collectAsStateWithLifecycle()
    Text(state.toString())
}

class WhileSubscribedSimulator(private val stopTimeoutMs: Long = 5_000L) {
    var subscriberCount = 0
        private set
    var isUpstreamActive = false
        private set
    private var lastUnsubscribedAtMs: Long? = null

    fun onUiStarted(nowMs: Long, reason: String) {
        subscriberCount++
        lastUnsubscribedAtMs = null
        if (!isUpstreamActive) {
            isUpstreamActive = true
            println("[t=${nowMs}ms] ($reason) Subscriber=1 -> STARTED upstream WebSocket/DB flow")
        } else {
            println("[t=${nowMs}ms] ($reason) Subscriber=1 -> REUSED active upstream (0 restarts!)")
        }
    }

    fun onUiStopped(nowMs: Long, reason: String) {
        subscriberCount = (subscriberCount - 1).coerceAtLeast(0)
        if (subscriberCount == 0) {
            lastUnsubscribedAtMs = nowMs
            println("[t=${nowMs}ms] ($reason) Subscriber=0 -> Grace timer started (${stopTimeoutMs}ms)")
        }
    }

    fun advanceClockTo(nowMs: Long) {
        val unsubTime = lastUnsubscribedAtMs ?: return
        if (subscriberCount == 0 && nowMs - unsubTime >= stopTimeoutMs && isUpstreamActive) {
            isUpstreamActive = false
            println("[t=${nowMs}ms] (Grace timeout expired) -> CANCELLED upstream WebSocket/DB flow to save battery!")
        }
    }
}

fun main() {
    val sim = WhileSubscribedSimulator(stopTimeoutMs = 5_000L)
    sim.onUiStarted(nowMs = 0L, reason = "Initial Activity Launch")
    sim.onUiStopped(nowMs = 1000L, reason = "Screen Rotation Destroy")
    sim.onUiStarted(nowMs = 1150L, reason = "Screen Rotation Recreate (150ms later)")
    sim.onUiStopped(nowMs = 3000L, reason = "User Pressed Home Button")
    sim.advanceClockTo(nowMs = 8000L)
}

import androidx.compose.runtime.Composable
import androidx.compose.runtime.getValue
import androidx.lifecycle.ViewModel
import androidx.lifecycle.compose.collectAsStateWithLifecycle
import androidx.lifecycle.viewModelScope
import kotlinx.coroutines.flow.Flow
import kotlinx.coroutines.flow.SharingStarted
import kotlinx.coroutines.flow.StateFlow
import kotlinx.coroutines.flow.stateIn

sealed interface MarketUiState {
    data object Loading : MarketUiState
    data class Success(val price: Double) : MarketUiState
}

class MarketFeedViewModel(priceFlow: Flow<MarketUiState>) : ViewModel() {
    val uiState: StateFlow<MarketUiState> = priceFlow.stateIn(
        scope = viewModelScope,
        started = SharingStarted.WhileSubscribed(5_000),
        initialValue = MarketUiState.Loading
    )
}

@Composable
fun MarketFeedRoute(viewModel: MarketFeedViewModel) {
    val state by viewModel.uiState.collectAsStateWithLifecycle()
}

Why this works: collectAsStateWithLifecycle unsubscribes when the UI drops below Lifecycle.State.STARTED, which drops the StateFlow's subscriberCount to 0. SharingStarted.WhileSubscribed(5_000) waits 5 seconds before cancelling the upstream cold flow, surviving 150ms configuration changes seamlessly while halting background battery drain.

Quiz 1: Code Analysis & Bug Hunt

A developer configured `SharingStarted.WhileSubscribed(5_000)` in the ViewModel, yet the upstream GPS location flow never stops when the user presses the Home button to background the app. Look at the Composable below—why is the upstream flow still running?

@Composable
fun LiveMapScreen(viewModel: LiveMapViewModel) {
    // Inside ViewModel: locationFlow.stateIn(viewModelScope, WhileSubscribed(5_000), Idle)
    val mapState by viewModel.mapState.collectAsState()
    MapCanvas(state = mapState)
}
5,000ms is too long and prevents Android from entering background state.
StateFlow does not track subscriber counts unless replay is set to 0.
viewModelScope ignores cancellation signals from SharingStarted.
`collectAsState()` is lifecycle-agnostic and stays subscribed as long as the Composable remains in the Composition tree (which persists in the background when the Activity is STOPPED), so `subscriptionCount` never drops to 0. Switching to `collectAsStateWithLifecycle()` fixes the leak.

Quiz 2: Production Architectural Reasoning

A user types a search filter `'Ethereum'` into a screen, puts the app in the background to answer a phone call, and the Android OS kills the app process under low memory. When the user switches back via the Recents screen, what is required so the `'Ethereum'` filter is still intact?

Store and observe the search query via `SavedStateHandle` (`savedStateHandle.getStateFlow("query", "")` and `savedStateHandle["query"] = newQuery`), which Android persists across system-initiated process death.
Mark the ViewModel with `@Singleton` in Hilt so it survives process death.
Use `remember { mutableStateOf("") }` inside the Composable.
