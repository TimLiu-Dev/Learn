Brownfield Compose & View Interop (AndroidView, ComposeView & Migration)

Lead incremental legacy-to-Compose migrations safely with ViewCompositionStrategy, AndroidView pooling, and shared ViewModels.

Recommended Primary Source
Android Developers: Interoperability APIs in Jetpack Compose
Official Documentation →

In real-world enterprise companies, you rarely start from File -> New Project. Instead, you inherit a 500,000-line brownfield codebase mixing legacy Fragments, XML layouts, custom Canvas views, and RecyclerView adapters—and as a Senior Android Engineer, you are expected to lead an incremental, zero-regression migration to Jetpack Compose. Bidirectional interoperability rests on two bridge APIs: ComposeView (hosting @Composable trees inside legacy XML layouts, Fragments, or RecyclerView ViewHolders) and AndroidView / AndroidViewBinding (hosting legacy or hardware-backed android.view.Views like MapView, WebView, or PlayerView inside Compose).

Under the hood, a ComposeView manages an internal Compose Composition holding slot-table state and active LaunchedEffect coroutines. By default (DisposeOnDetachedFromWindowOrReleasedFromPool), a ComposeView disposes its composition whenever the View detaches from the window. However, inside a Fragment, when the user navigates forward from FragmentA to FragmentB, FragmentA's *View* (onDestroyView) is destroyed while FragmentA itself stays alive on the backstack! If you don't align disposal with the Fragment's view lifecycle using setViewCompositionStrategy(ViewCompositionStrategy.DisposeOnViewTreeLifecycleDestroyed), or if you create a brand-new ComposeView improperly, you either leak compositions or lose state across transitions. Conversely, when embedding a legacy View inside a LazyColumn via AndroidView(factory = ..., update = ..., onReset = ..., onRelease = ...), supplying the onReset callback enables View instance reuse and pooling across lazy scroll items without re-inflating expensive View hierarchies on every scroll tick!

🌱 Junior Android Dev Mental Model: Never Mutate the Legacy View Inside AndroidView's factory = {} Block

The factory = { context -> CustomChartView(context) } lambda in AndroidView executes only once when the View is initially allocated (or pulled cold). It does not re-run when your Compose state changes! Always apply state-driven updates inside the update = { view -> view.setData(uiState.points) } lambda, which is snapshot-aware and automatically re-executes whenever any State<T> read inside update changes.

Senior Interview Trap & Production Edge Case

Trap: Calling findViewTreeLifecycleOwner() or setting content on a ComposeView inside a Fragment using the obsolete DisposeOnDetachedFromWindow strategy. In a RecyclerView or ViewPager2, views detach and reattach constantly as the user scrolls; DisposeOnDetachedFromWindow destroys and recreates the entire Compose slot table on every scroll detach unless DisposeOnDetachedFromWindowOrReleasedFromPool (the modern default for pooling containers) or DisposeOnViewTreeLifecycleDestroyed (for Fragments) is used.
Edge Case: How do you migrate a legacy 10,000-line app incrementally without breaking navigation or theming? Use the Bottom-Up Leaf-First Strategy: (1) Unify theme tokens with Mdc3Theme / shared color-typography tokens so XML and Compose match visually, (2) Replace leaf components/cards via ComposeView, (3) Convert whole screen bodies inside Fragments while sharing the same activity/fragment-scoped ViewModel, and (4) Finally replace the Fragment container with Compose Navigation once all child screens are @Composable.

❌ Junior Anti-Pattern: State Read in factory & Missing onReset

// 1. State read inside 'factory' NEVER updates when 'tickerPrice' changes!
// 2. No 'onReset' forces LazyColumn to destroy & recreate WebView/ChartView on scroll!
LazyColumn {
    items(tickers, key = { it.id }) { item ->
        AndroidView(
            factory = { ctx ->
                LegacySparklineView(ctx).apply {
                    renderPoints(item.points) // BUG: Stuck on initial item forever!
                }
            }
        )
    }
}

✅ 2027 Senior Standard: Snapshot-Driven update + Pooled onReset

// 1. 'factory' only allocates; 'update' reacts to Compose State changes!
// 2. 'onReset' enables AndroidView recycling across LazyColumn scroll items!
LazyColumn {
    items(tickers, key = { it.id }) { item ->
        AndroidView(
            factory = { ctx -> LegacySparklineView(ctx) },
            update = { view -> view.renderPoints(item.points) },
            onReset = { view -> view.clearPointsForReuse() },
            onRelease = { view -> view.releaseHardwareBuffers() }
        )
    }
}

class SimulatedLegacyChartView(val instanceId: Int) {
    var boundSymbol: String? = null
    var hardwareReleased: Boolean = false
    fun bindData(symbol: String) { boundSymbol = symbol }
    fun resetForPool() { boundSymbol = null }
    fun release() { hardwareReleased = true }
}

class AndroidViewPoolCoordinator {
    private var nextId = 1
    private val pool = ArrayDeque<SimulatedLegacyChartView>()

    fun acquireOrAllocate(symbol: String): Pair<SimulatedLegacyChartView, String> {
        val reused = pool.removeFirstOrNull()
        return if (reused != null) {
            reused.bindData(symbol) // update = {} block
            reused to "REUSED_FROM_POOL(view#${reused.instanceId} -> $symbol)"
        } else {
            val fresh = SimulatedLegacyChartView(nextId++).also { it.bindData(symbol) } // factory + update
            fresh to "ALLOCATED_FRESH(view#${fresh.instanceId} -> $symbol)"
        }
    }

    fun recycleToPool(view: SimulatedLegacyChartView) {
        view.resetForPool() // onReset = {} block enables reuse!
        pool.addLast(view)
    }
}

fun main() {
    val coordinator = AndroidViewPoolCoordinator()
    val (v1, log1) = coordinator.acquireOrAllocate("BTC-USD")
    val (v2, log2) = coordinator.acquireOrAllocate("ETH-USD")
    println("[LAZY-SCROLL] $log1")
    println("[LAZY-SCROLL] $log2")

    // User scrolls BTC-USD off screen -> onReset recycles View#1 into pool
    coordinator.recycleToPool(v1)
    val (_, log3) = coordinator.acquireOrAllocate("SOL-USD")
    println("[LAZY-SCROLL] $log3 (Zero new View inflation!)")
}

Implement selectViewCompositionStrategy(hostContainer: String): String and planAndroidViewLifecycle(hasOnReset: Boolean, itemScrolledOffScreen: Boolean, compositionDisposed: Boolean): String. In selectViewCompositionStrategy, return "DisposeOnViewTreeLifecycleDestroyed" when hostContainer == "Fragment", and "DisposeOnDetachedFromWindowOrReleasedFromPool" when hostContainer == "RecyclerView" (or any other host). In planAndroidViewLifecycle, return "ON_RELEASE" if compositionDisposed is true; otherwise if itemScrolledOffScreen && hasOnReset return "ON_RESET_REUSE"; otherwise if itemScrolledOffScreen return "DISCARD_VIEW"; else return "ON_UPDATE".

fun selectViewCompositionStrategy(hostContainer: String): String {
    return if (hostContainer == "Fragment") {
        "DisposeOnViewTreeLifecycleDestroyed"
    } else {
        "DisposeOnDetachedFromWindowOrReleasedFromPool"
    }
}

fun planAndroidViewLifecycle(
    hasOnReset: Boolean,
    itemScrolledOffScreen: Boolean,
    compositionDisposed: Boolean
): String {
    return when {
        compositionDisposed -> "ON_RELEASE"
        itemScrolledOffScreen && hasOnReset -> "ON_RESET_REUSE"
        itemScrolledOffScreen -> "DISCARD_VIEW"
        else -> "ON_UPDATE"
    }
}

Why this works: Matching ViewCompositionStrategy to the host lifecycle (Fragment view vs RecyclerView pool) prevents memory leaks and lost UI state, while supplying onReset unlocks AndroidView instance pooling inside lazy layouts.

Quiz 1: Code Analysis & Bug Hunt

A developer embeds a legacy CustomMapView inside a Compose screen using AndroidView. When uiState.selectedPin updates in the ViewModel, the Compose top bar updates immediately, but the map marker on CustomMapView never moves! Why?

@Composable
fun StoreLocatorScreen(uiState: LocatorUiState) {
    Column {
        Text("Selected: ${uiState.selectedPin.title}")
        AndroidView(
            factory = { context ->
                CustomMapView(context).apply {
                    centerOnPin(uiState.selectedPin) // <-- Look closely!
                }
            }
        )
    }

Embedding AndroidView inside a layout permanently blocks Column from recomposing any sibling Compose Text nodes.
AndroidView executes factory only once on creation, so view.centerOnPin must run inside the update callback.
Jetpack Compose automatically destroys all embedded android.view.View instances immediately after rendering the initial layout frame.
Calling the Kotlin apply scope function resets uiState.selectedPin references to null during initial bytecode compilation.
