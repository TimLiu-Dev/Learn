Advanced Modeling with Sealed Hierarchies & Value Classes

Eliminate invalid UI states with exhaustive sealed interfaces and zero-allocation @JvmInline value classes.

Recommended Primary Source
Kotlin Official Documentation: Sealed Interfaces & Inline Value Classes
Official Documentation →

In legacy Android, developers frequently represented states using sets of booleans (e.g. isLoading = true, isError = false). This causes the dreaded impossible state bug (e.g., both isLoading == true AND data != null).

🌱 Junior Android Dev Mental Model: Make Invalid States Unrepresentable

A screen can only be in exactly ONE state at a given instant: Loading, Empty, Success, or Error. In Modern Android, we represent state as a sealed interface. The Kotlin compiler forces any when expression evaluating a sealed hierarchy to be exhaustive without needing a fragile else -> fallback.

Zero-Allocation Type Safety: @JvmInline value class

Passing primitive Strings or Longs for IDs (like userId: String, orderId: String) invites parameter-swap bugs. By declaring @JvmInline value class UserId(val value: String), you gain strict compile-time type safety. At runtime, the Kotlin compiler boxes or unboxes it to a raw primitive JVM String with zero heap allocation overhead!

KOTLIN 2.X DomainModeling.kt 
@JvmInline
value class TransactionId(val value: String)

sealed interface PaymentUiState {
    data object Idle : PaymentUiState
    data object Processing : PaymentUiState
    data class Success(val txId: TransactionId, val amountUsd: Double) : PaymentUiState
    data class Failed(val reason: String) : PaymentUiState
}

fun renderState(state: PaymentUiState): String = when (state) {
    PaymentUiState.Idle -> "[STATE] Awaiting user checkout action."
    PaymentUiState.Processing -> "[STATE] Communicating with bank gateway..."
    is PaymentUiState.Success -> "[SUCCESS] Payment confirmed! TxID: ${state.txId.value}, Paid: $${state.amountUsd}"
    is PaymentUiState.Failed -> "[ERROR] Transaction declined: ${state.reason}"
}

fun main() {
    val tx = TransactionId("tx_live_884910")
    println(renderState(PaymentUiState.Processing))
    println(renderState(PaymentUiState.Success(tx, 49.99)))
}

@JvmInline
value class AccountId(val id: String)

sealed interface AccountState {
    data object Loading : AccountState
    data class Active(val id: AccountId, val balance: Double) : AccountState
}

fun describeAccount(state: AccountState): String = when (state) {
    AccountState.Loading -> "Loading account..."
    is AccountState.Active -> "Account ${state.id.id} has balance $${state.balance}"
}

Why this works: Sealed interfaces prevent any external module from subclassing states, giving compiler-enforced exhaustiveness without an 'else' branch, while value classes eliminate object allocation overhead on the JVM heap.
