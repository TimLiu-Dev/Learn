Advanced Modeling with Sealed Hierarchies & Value Classes

Eliminate invalid UI states with exhaustive sealed interfaces and zero-allocation @JvmInline value classes.

Recommended Primary Source
Kotlin Official Documentation: Sealed Interfaces & Inline Value Classes
Official Documentation →

Modelling UI and domain state with independent nullable fields and boolean flags (isLoading, isError, data) creates 2<sup>N</sup> state combinations, most of which are illegal or contradictory (e.g., simultaneously showing a loading spinner and an error retry screen while stale data renders underneath). In 2027 Android engineering, we enforce Algebraic Data Types (ADTs) using sealed interface hierarchies and zero-cost domain primitives via @JvmInline value class.

Under the hood, a sealed interface restricts all direct implementations to the same compilation module and package, enabling the Kotlin K2 compiler to verify exhaustiveness in when expressions without a catch-all else branch. Unlike sealed class, a sealed interface carries no constructor state or superclass vtable overhead, allowing a single domain event or state node to belong to multiple sealed hierarchies simultaneously (diamond-safe sum types).

🌱 Junior Android Dev Mental Model: Make Illegal States Unrepresentable

Instead of writing defensive if (state.isLoading && state.data == null) checks across 15 Composables, design your types so an invalid combination cannot even be constructed. Use data object (not legacy object) for singleton sealed branches so toString(), equals(), and debugging logs print clean human-readable names instead of raw memory hashes like Loading@4f023edb.

@JvmInline value class: Bytecode Erasure & Boxing Rules

Passing raw String or Long parameters (e.g., fun transfer(fromUserId: String, toAccountId: String, assetId: String)) invites catastrophic argument-swapping bugs. Wrapping them in a regular data class allocates an extra 16–24 byte object header on the Android ART heap per instance, increasing GC pressure during 120Hz scrolling. A @JvmInline value class wraps a single immutable property at compile time for strict type safety, while the compiler erases the wrapper to the underlying primitive or reference in JVM bytecode.

⚠️ Senior Interview Trap: When Do Value Classes Box on the Heap?

A common Senior interview question is: "Does a @JvmInline value class ALWAYS have zero heap allocations?" The answer is No. The compiler must allocate a boxed wrapper object on the heap in three specific scenarios:

  • Nullable Type Usage: Declaring val id: UserId? (especially when wrapping a primitive like Long) or passing it where nullability requires distinguishing null from the underlying value.
  • Generic Type Arguments: Storing UserId in a List<UserId>, Map<UserId, User>, or passing it to a generic function fun <T> log(item: T) boxes every element because JVM generics erase to Object.
  • Interface Delegation / Supertype Upcasting: If value class UserId(val raw: String) : Identifiable is assigned to a variable of type Identifiable or Any, it boxes immediately.

💰 Financial & Precision Rule: Never Use IEEE-754 Double for Money!

In fintech and e-commerce apps (including our Capstone Aether), binary floating-point Double cannot represent base-10 decimals exactly (0.1 + 0.2 == 0.30000000000000004). Always wrap integer minor units—such as cents, micros (10^-6 USD), or satoshis—inside a zero-allocation @JvmInline value class UsdMicros(val micros: Long) (or java.math.BigDecimal for arbitrary-precision FX rates)!

@JvmInline
value class AccountId(val raw: String) {
    init {
        require(raw.startsWith("acc_") && raw.length >= 8) {
            "Malformed AccountId: $raw"
        }
    }

@JvmInline
value class MinorUnitsCents(val amount: Long) {
    operator fun plus(other: MinorUnitsCents) = MinorUnitsCents(amount + other.amount)
}

sealed interface TransferResult {
    data object PendingVerification : TransferResult
    data class Settled(
        val from: AccountId,
        val to: AccountId,
        val totalSettled: MinorUnitsCents
    ) : TransferResult
    data class Rejected(val code: Int, val reason: String) : TransferResult
}

fun renderBanner(result: TransferResult): String = when (result) {
    TransferResult.PendingVerification -> "[BANNER] Awaiting biometric confirmation..."
    is TransferResult.Settled ->
        "[BANNER] Sent ${result.totalSettled.amount} cents from ${result.from.raw} to ${result.to.raw}"
    is TransferResult.Rejected ->
        "[BANNER] Transfer failed (${result.code}): ${result.reason}"
}

fun main() {
    val sender = AccountId("acc_9001")
    val receiver = AccountId("acc_4420")
    val transfer = TransferResult.Settled(
        from = sender,
        to = receiver,
        totalSettled = MinorUnitsCents(12_500L) + MinorUnitsCents(250L)
    )

    println(renderBanner(TransferResult.PendingVerification))
    println(renderBanner(transfer))
    println(renderBanner(TransferResult.Rejected(403, "Daily velocity limit exceeded")))
}

@JvmInline
value class InvoiceId(val id: String) {
    init {
        require(id.startsWith("inv_")) { "InvoiceId must start with inv_" }
    }
}

sealed interface PaymentState {
    data object Loading : PaymentState
    data class Paid(val invoiceId: InvoiceId, val amountCents: Long) : PaymentState
    data class Error(val reason: String) : PaymentState
}

fun describePayment(state: PaymentState): String = when (state) {
    PaymentState.Loading -> "Processing payment..."
    is PaymentState.Paid -> "Paid ${state.amountCents} cents for ${state.invoiceId.id}"
    is PaymentState.Error -> "Failed: ${state.reason}"
}

Why this works: @JvmInline erases InvoiceId to a raw String at runtime while enforcing prefix validation at construction time, and sealed interface + data object allows the compiler to verify exhaustive handling of every PaymentState without an else branch.

Quiz 2: Production Architectural Reasoning

Why should senior Android engineers prefer 'sealed interface' over 'sealed class' and 'data object' over 'object' when modeling UI state and MVI intents?

Sealed interfaces avoid constructor overhead and allow multi-hierarchy types, while data objects generate clean toString/equals methods
Abstract sealed classes are deprecated throughout Kotlin and trigger compilation diagnostics whenever collected inside Compose StateFlow
Generated data-object instances allocate directly on thread stacks instead of heap, whereas standard singletons retain ActivityContext
Sealed interfaces automatically generate Android Parcelable creator code for all child subclasses without requiring Parcelize annotations
