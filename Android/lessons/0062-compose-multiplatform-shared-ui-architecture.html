Compose Multiplatform (CMP): Shared UI, Resources & Native Interop

Architect shared @Composable screens across Android and iOS using composeResources, ComposeUIViewController, and UIKitView interop.

Recommended Primary Source
JetBrains Official Docs: Compose Multiplatform UI Framework
Official Documentation →

While Kotlin Multiplatform (Lessons 0060–0061) shares pure domain and data logic beneath platform-native UIs, JetBrains Compose Multiplatform (CMP) lets your team share the entire declarative UI layer (@Composable screens, Material 3 design systems, animations, ViewModels, and Jetpack Navigation) across Android, iOS, Desktop (JVM), and Web (Kotlin/Wasm). On Android, CMP compiles directly to standard Jetpack Compose bytecode; on iOS, CMP renders at 120Hz ProMotion frame rates via Skia backed by Apple's Metal GPU pipeline hosted inside a native ComposeUIViewController that plugs directly into SwiftUI or UIKit.

Shipping a senior-grade CMP app in 2027 requires mastering three multiplatform boundaries: (1) Multiplatform Resources (org.jetbrains.compose.components:components-resources)—replacing Android-only R.drawable and R.string with compile-time generated Res.drawable.* and Res.string.* accessors inside commonMain/composeResources; (2) Bidirectional Native View Interop—embedding platform-specific views like Apple's MKMapView, WKWebView, or AVPlayerLayer inside iosMain Composables via UIKitView / UIKitViewController while androidMain delegates to AndroidView behind a clean @Composable expect fun PlatformMap(...) boundary; and (3) Platform Feel & Accessibility—bridging Compose's Semantics Tree automatically to iOS VoiceOver alongside native Cupertino overscroll physics and system text selection.

🌱 Junior Android Dev Mental Model: When to Choose CMP vs. KMP + Native SwiftUI

Choose CMP (Shared UI) when you want 90%+ code reuse with a unified brand design system (like Aether's custom financial charts, dashboards, and forms) and rapid feature velocity across Android and iOS. Choose KMP Shared Logic + Native SwiftUI when an app relies predominantly on OS-exclusive UI chrome (such as WatchKit/WidgetKit extensions, RealityKit AR, or deeply idiomatic Apple Cupertino controls) where fighting platform conventions would cost more than building thin SwiftUI views.

⚠️ Senior Interview Trap: Android-Only Imports in commonMain & Heavy UIKitView Re-Allocation

Trap: Importing androidx.compose.ui.res.painterResource or android.content.Context inside composeApp/src/commonMain! Even a single android.* import breaks iOS compilation. Always import org.jetbrains.compose.resources.painterResource and org.jetbrains.compose.resources.stringResource paired with the generated Res object, and use multiplatform androidx.lifecycle.ViewModel (supported natively in commonMain since Lifecycle 2.8+!).
Edge Case: Just like AndroidView on Android, UIKitView(factory = { MKMapView() }, update = { mapView -> ... }) on iOS allocates an expensive native Objective-C UIView in factory. Never read reactive Compose State inside factory—perform all state-driven coordinate updates inside update so panning or adding map pins never destroys and recreates the underlying Metal/UIKit surface!

❌ Junior Anti-Pattern: Android R.* Imports & Stateful UIKitView Factory

// 1. Fails iosArm64 build: R.drawable is Android-only!
import androidx.compose.ui.res.painterResource
import com.aether.R

// 2. Inside iosMain: Reading 'pinLocation' only in factory never updates MKMapView!
@Composable
actual fun NativeVenueMap(pinLocation: LatLng) {
    UIKitView(factory = {
        MKMapView().apply { setCenter(pinLocation) } // Stale after first frame!
    })
}

✅ 2027 Senior Standard: Multiplatform Res + Clean expect/actual UIKitView

// commonMain: Multiplatform generated Res + platform-agnostic expect Composable
import org.jetbrains.compose.resources.painterResource
import aether.composeapp.generated.resources.Res
import aether.composeapp.generated.resources.ic_vault_shield

@Composable
expect fun NativeVenueMap(pinLocation: LatLng, modifier: Modifier = Modifier)

// iosMain: Allocate once in factory, react to Compose Snapshot State in update!
@Composable
actual fun NativeVenueMap(pinLocation: LatLng, modifier: Modifier) {
    UIKitView(
        factory = { MKMapView() },
        modifier = modifier,
        update = { mapView -> mapView.setCenterCoordinate(pinLocation.toCLLocation(), animated = true) }
    )
}

enum class HostTarget { ANDROID_APK, IOS_METAL }
enum class UiStrategy { SHARE_UI_WITH_CMP, KMP_LOGIC_NATIVE_SWIFTUI }

data class CmpPlatformBinding(val target: HostTarget, val renderer: String, val nativeViewBridge: String)

object CmpArchitecturePlanner {
    fun resolveBinding(target: HostTarget): CmpPlatformBinding = when (target) {
        HostTarget.ANDROID_APK -> CmpPlatformBinding(target, "Android Canvas/Skia", "AndroidView(MapView)")
        HostTarget.IOS_METAL -> CmpPlatformBinding(target, "ComposeUIViewController(Metal)", "UIKitView(MKMapView)")
    }

    fun recommendUiStrategy(customBrandDesignPct: Int, requiresWatchKitOrRealityKit: Boolean): Pair<UiStrategy, Int> {
        return if (requiresWatchKitOrRealityKit || customBrandDesignPct < 40) {
            UiStrategy.KMP_LOGIC_NATIVE_SWIFTUI to 62
        } else {
            UiStrategy.SHARE_UI_WITH_CMP to 94
        }
    }
}

fun auditCmpModuleImports(
    imports: List<String>,
    usesHeavyOsExclusiveChrome: Boolean
): Result<String> {
    val hasLeak = imports.any { it.startsWith("android.") || it.startsWith("platform.UIKit.") }
    if (hasLeak) {
        return Result.failure(IllegalArgumentException("PLATFORM_LEAK_IN_COMMON_MAIN"))
    }
    val verdict = if (usesHeavyOsExclusiveChrome) "NATIVE_UI_RECOMMENDED" else "CMP_SHARED_UI_READY"
    return Result.success(verdict)
}

Why this works: Keeping commonMain strictly free of android.* and Objective-C platform.UIKit.* imports ensures every shared Composable compiles cleanly to both Android DEX and iOS Metal frameworks.

Compose Multiplatform disables all Kotlin StateFlow emissions whenever an Objective-C UIView subclass mounts inside native ComposeUIViewController.
The UIKitView factory block executes only once upon allocation; reactive state updates belong inside update callbacks.
Apple App Store review guidelines prohibit calling MKMapView camera methods from Kotlin/Native compiled ARM64 machine binaries.
Every UIKitView instance must be recreated from scratch on every rendered frame using randomized Compose keys.
