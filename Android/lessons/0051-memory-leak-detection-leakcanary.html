Memory Leak Detection with LeakCanary

Track GC roots, detect retained Activity/Context instances, and eliminate memory leaks with LeakCanary.

Recommended Primary Source
Square LeakCanary: Fundamentals of Memory Leaks
Official Documentation →

Every Android application runs inside an ART heap ceiling (typically 256MB to 512MB depending on device RAM class). When a destroyed Activity, ViewModel, or detached View tree is accidentally retained by a long-lived reference, the Garbage Collector (GC) cannot reclaim its memory. Within a few configuration changes or screen navigations, heap fragmentation triggers frequent Stop-The-World GC pauses (jank) and ultimately crashes the process with java.lang.OutOfMemoryError (OOM).

Under the Hood: GC Roots, WeakReference, ReferenceQueue & Shark

How does LeakCanary detect memory leaks automatically without slowing down production builds? First, it is included strictly via debugImplementation(libs.leakcanary.android) so zero bytes ship in your release APK. At runtime, LeakCanary's ObjectWatcher hooks into Android lifecycle callbacks (Activity.onDestroy(), Fragment.onDestroyView(), ViewModel.onCleared()). When an object reaches the end of its lifecycle, LeakCanary wraps it in a KeyedWeakReference paired with a JVM ReferenceQueue. If the object is properly garbage-collected, the JVM enqueues its WeakReference into the ReferenceQueue. If the reference is still missing from the queue 5 seconds after destruction and an explicit GC trigger, LeakCanary dumps the heap (Debug.dumpHprofData) and invokes Shark—its low-memory HPROF graph analyzer—to compute the shortest strong reference path from a GC Root (static fields, active threads, JNI globals, window manager roots) down to the leaked instance!

🌱 Junior Android Dev Mental Model: Reading a Shark Leak Trace

In a LeakCanary trace, the top node is the GC Root (always alive) and the bottom node is the Leaked Object (definitely dead, e.g., Activity.mDestroyed = true). Don't look at the top or bottom—look for the exact link marked with a wavy underline ~~~ where Leaking: NO transitions to Leaking: YES. Breaking that single reference fixes the entire leak!

❌ Junior Anti-Pattern: Singleton Retaining Activity Context & Unregistered Listener

object MarketTickerBus {
    private val listeners = mutableListOf<(Double) -> Unit>()
    var activeContext: Context? = null // GC Root static field!

    fun register(context: Context, listener: (Double) -> Unit) {
        activeContext = context // Leaks entire Activity + View hierarchy!
        listeners.add(listener) // Implicitly captures 'this@MainActivity'
    }
}

✅ 2027 Senior Production Standard: ApplicationContext + Auto-Cancelling callbackFlow

class MarketTickerManager @Inject constructor(
    @ApplicationContext private val appContext: Context,
    private val sensorService: LegacyTickerSdk
) {
    val priceTicks: Flow<Double> = callbackFlow {
        val listener = LegacyTickerSdk.Listener { price -> trySend(price) }
        sensorService.register(listener)
        // Automatically unregisters when the UI collector leaves the screen!
        awaitClose { sensorService.unregister(listener) }
    }
}

⚠️ Senior Interview Trap: Automated CI Leak Assertions (LeakAssertions)

Many teams install debugImplementation(libs.leakcanary.android) but ignore the notification icon on developers' test phones. In 2027, senior teams wire leakcanary-android-instrumentation directly into their UI and Robolectric/Espresso test suites using DetectLeaksAfterTestSuccess() JUnit rule or LeakAssertions.assertNoLeaks(), failing the CI build immediately if a PR introduces a single retained Activity or ViewModel!

data class HeapNode(val name: String, val isGcRoot: Boolean, val lifecycleDestroyed: Boolean, val pointsTo: HeapNode? = null)

class SharkLeakAnalyzer {
    fun analyzeShortestPath(root: HeapNode): String {
        val chain = mutableListOf<HeapNode>()
        var curr: HeapNode? = root
        while (curr != null) {
            chain += curr
            curr = curr.pointsTo
        }
        val leakedTarget = chain.last()
        if (!leakedTarget.lifecycleDestroyed) return "NO_LEAK"

        val report = StringBuilder("┬───\n")
        for (i in chain.indices) {
            val node = chain[i]
            val leakingState = when {
                node.isGcRoot -> "Leaking: NO (GC Root: Static Field)"
                node.lifecycleDestroyed -> "Leaking: YES (${node.name}.mDestroyed = true)"
                else -> "Leaking: NO (Singleton alive in application scope)"
            }
            val pointer = if (i < chain.lastIndex && chain[i + 1].lifecycleDestroyed) " ~~~> [SUSPECT REFERENCE]" else ""
            report.append("│ ${node.name} ($leakingState)$pointer\n")
        }
        report.append("╰→ ${leakedTarget.name} retained in heap!")
        return report.toString()
    }
}

fun main() {
    val leakedActivity = HeapNode("MainActivity", isGcRoot = false, lifecycleDestroyed = true)
    val lambdaCapture = HeapNode("MarketScreen\$onStart\$1 (capture this@MainActivity)", isGcRoot = false, lifecycleDestroyed = false, pointsTo = leakedActivity)
    val staticSingleton = HeapNode("MarketTickerBus.INSTANCE.listeners", isGcRoot = true, lifecycleDestroyed = false, pointsTo = lambdaCapture)

    println("[OBJECT-WATCHER] KeyedWeakReference(MainActivity) still missing from ReferenceQueue after 5000ms + GC!")
    println(SharkLeakAnalyzer().analyzeShortestPath(staticSingleton))
}

class RetainedObjectTracker {
    private val watchedKeys = mutableSetOf<String>()
    private val collectedKeys = mutableSetOf<String>()

    fun watchDestroyed(key: String) {
        watchedKeys.add(key)
    }

    fun onGarbageCollected(key: String) {
        collectedKeys.add(key)
    }

    fun findRetainedLeaks(): Set<String> {
        return watchedKeys - collectedKeys
    }
}

Why this works: LeakCanary's ObjectWatcher records a unique UUID key when an Activity/ViewModel is destroyed and removes keys dequeued from its ReferenceQueue; any remaining keys after GC represent retained heap leaks.

Quiz 2: Production Architectural Reasoning

Why must LeakCanary be added using debugImplementation(libs.leakcanary.android) rather than implementation(libs.leakcanary.android)?

Dumping .hprof heaps freezes the process and exposes sensitive memory; debugImplementation excludes LeakCanary from release builds.
Google Play Console automatically suspends developer accounts uploading APK artifacts containing Canary inside Maven group identifiers.
LeakCanary's Shark memory analyzer requires legacy Dalvik bytecode verification and cannot analyze AOT-compiled ART release snapshots.
Using implementation causes LeakCanary to automatically wipe the application's persistent Room database whenever memory leaks occur.
