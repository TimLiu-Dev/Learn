State in Compose: remember, rememberSaveable & Hoisting

Master mutableStateOf, state survival across recomposition and configuration changes, and state hoisting.

Recommended Primary Source
Google Android: State and Jetpack Compose
Official Documentation →

Jetpack Compose's reactivity is powered by the Snapshot State System (androidx.compose.runtime.snapshots), an implementation of Software Transactional Memory (STM) and Multiversion Concurrency Control (MVCC). When you create a state holder with mutableStateOf(initialValue, policy), Compose allocates a SnapshotMutableStateImpl containing a linked list of StateRecord versions. Whenever a @Composable function (or a Layout/Draw phase block) reads state.value, Compose's thread-local read observer registers a dependency between that StateObject and the current RecomposeScope. When state.value is mutated, Compose marks only the subscribed RecomposeScopes as invalid for the next frame tick.

To prevent a local state variable from resetting on every recomposition, you cache it in the Slot Table using remember { mutableStateOf(...) }. However, the Slot Table lives entirely in the Activity's heap memory—meaning a screen rotation, dark-mode toggle, or background process death wipes all remember slots. To survive both configuration changes and OS process death, use rememberSaveable, which hooks into Android's SaveableStateRegistry Bundle.

🌱 Junior Android Dev Mental Model: Unidirectional Data Flow (UDF) & State Hoisting

State goes down; Events go up. A stateless, reusable Composable should never own its own business state or take a ViewModel as a parameter! Instead, hoist state to the caller by accepting immutable values (value: String) and exposing event lambdas (onValueChange: (String) -> Unit). This makes your Composable 100% deterministic, previewable with @Preview, and trivially testable in isolation.

Custom Savers (<code>listSaver</code> / <code>mapSaver</code>) & Snapshot Mutation Policies

  • Custom Saver<Original, Saveable>: When a UI state object cannot or should not be annotated with @Parcelize (e.g., third-party classes or complex UI scroll/selection controllers), pass a Saver via listSaver(save = { listOf(it.x, it.y) }, restore = { Point(it[0], it[1]) }) to pack only essential primitives into the saved Bundle.
  • Snapshot Mutation Policies: mutableStateOf accepts three policies: structuralEqualityPolicy() (default, uses equals()), referentialEqualityPolicy() (uses ===), and neverEqualPolicy() (always triggers recomposition on write).

⚠️ Senior Interview Trap: Forgetting <code>remember</code> Keys (<code>remember(key1)</code>) & Collecting Flows Without Lifecycle Awareness!

Two pervasive bugs appear in Senior Compose code reviews:

  1. Stale <code>remember</code> State When Inputs Change: Writing val formatted = remember { expensiveFormat(user.name) } inside <code>UserProfileCard(user: User)</code> caches the initial <code>user.name</code> in the Slot Table on first composition. When a new <code>user</code> is passed into the same slot later, <code>remember</code> returns the <strong>stale cached result from the first user</strong> because <code>user.name</code> was not passed as a key: <code>remember(user.name) { expensiveFormat(user.name) }</code>!
  2. <code>collectAsState()</code> vs <code>collectAsStateWithLifecycle()</code>: Using standard <code>flow.collectAsState()</code> keeps the upstream Flow collection active even when the Android app is in the background (<code>STOPPED</code>), wasting battery and CPU on background location/sensor/network updates. On Android, always use <code>collectAsStateWithLifecycle()</code> (from <code>androidx.lifecycle:lifecycle-runtime-compose</code>), which automatically cancels collection when the Lifecycle drops below <code>Lifecycle.State.STARTED</code>.

❌ Junior Anti-Pattern: Unkeyed remember & Unhoisted Stateful Widget

@Composable
fun PriceEditor(product: Product, viewModel: CartViewModel) {
    // BUG 1: Missing key! If 'product' changes, initialPrice stays stuck on old product!
    // BUG 2: Lost on screen rotation because rememberSaveable wasn't used!
    var draftPrice by remember { mutableStateOf(product.defaultPrice) }

    // BUG 3: Passing ViewModel into leaf component breaks @Preview and reuse!
    TextField(value = draftPrice, onValueChange = {
        draftPrice = it
        viewModel.updatePrice(it)
    })
}

✅ 2027 Senior Standard: Keyed rememberSaveable + Stateless Hoisting

@Composable
fun PriceEditorRoute(product: Product, onPriceCommitted: (String) -> Unit) {
    // Keyed on product.id AND survives rotation + process death!
    var draftPrice by rememberSaveable(product.id) {
        mutableStateOf(product.defaultPrice)
    }
    PriceEditorContent(
        price = draftPrice,
        onPriceChange = { draftPrice = it },
        onCommit = { onPriceCommitted(draftPrice) }
    )
}

// Demonstrates Compose Custom Saver serialization & keyed remember invalidation mechanics
data class CanvasViewportState(val panX: Float, val panY: Float, val zoomLevel: Float)

interface CustomSaver<Original, Saveable : Any> {
    fun save(value: Original): Saveable
    fun restore(saved: Saveable): Original
}

val ViewportListSaver = object : CustomSaver<CanvasViewportState, List<Float>> {
    override fun save(value: CanvasViewportState): List<Float> =
        listOf(value.panX, value.panY, value.zoomLevel)

    override fun restore(saved: List<Float>): CanvasViewportState =
        CanvasViewportState(panX = saved[0], panY = saved[1], zoomLevel = saved[2])
}

class KeyedSlotSimulator<K, V>(private val saver: CustomSaver<V, List<Float>>) {
    private var lastKey: K? = null
    private var currentValue: V? = null

    fun rememberSaveableWithKey(key: K, init: () -> V): V {
        if (lastKey != key || currentValue == null) {
            lastKey = key
            currentValue = init()
            println("[SLOT] Key changed to '$key' -> initialized state: $currentValue")
        } else {
            println("[SLOT] Key '$key' unchanged -> retained state: $currentValue")
        }
        return currentValue!!
    }

    fun simulateRotationRestore(): V {
        val bundlePayload = saver.save(currentValue!!)
        println("[SAVER] Serialized to Bundle list: $bundlePayload")
        currentValue = saver.restore(bundlePayload)
        println("[SAVER] Restored after rotation: $currentValue")
        return currentValue!!
    }
}

fun main() {
    val slot = KeyedSlotSimulator<String, CanvasViewportState>(ViewportListSaver)
    slot.rememberSaveableWithKey("doc_1") { CanvasViewportState(12.5f, -40.0f, 2.0f) }
    slot.simulateRotationRestore()
    slot.rememberSaveableWithKey("doc_2") { CanvasViewportState(0f, 0f, 1.0f) }
}

import androidx.compose.runtime.*
import androidx.compose.runtime.saveable.rememberSaveable

@Composable
fun QuantitySelectorStateful(itemId: String, initialQty: Int) {
    var qty by rememberSaveable(itemId) {
        mutableStateOf(initialQty)
    }

    QuantitySelectorStateless(
        quantity = qty,
        onIncrement = { qty += 1 },
        onDecrement = { if (qty > 0) qty -= 1 }
    )
}

@Composable
fun QuantitySelectorStateless(
    quantity: Int,
    onIncrement: () -> Unit,
    onDecrement: () -> Unit
) {
    // Stateless UI representation
}

Why this works: Passing itemId as the key to rememberSaveable(itemId) ensures the state survives screen rotation and process death for the current item, yet cleanly re-initializes to initialQty whenever the parent passes a different itemId.

Quiz 1: Code Analysis & Bug Hunt

A developer builds a detail screen that displays a user's bio and allows editing it locally before saving. When the parent screen switches from 'userA' to 'userB', the TextField still displays 'userA's bio! Why?

@Composable
fun EditableBioCard(user: UserProfile) {
    var draftBio by rememberSaveable {
        mutableStateOf(user.initialBio)
    }
    TextField(
        value = draftBio,
        onValueChange = { draftBio = it }
    )
}
Material TextField caches its initial String value inside a static companion object across all compositions.
Because rememberSaveable omits user.id from its input keys, Composition state storage preserves the initial value.
Because mutableStateOf uses referentialEqualityPolicy by default for String values, Compose skips updating the internal state.
Because UserProfile lacks the @Parcelize annotation, rememberSaveable silently falls back to the previous cached instance.

Quiz 2: Production Architectural Reasoning

Why should Android Compose engineers always prefer 'flow.collectAsStateWithLifecycle()' over standard 'flow.collectAsState()' when observing ViewModel StateFlows in UI?

collectAsState() throws an uncaught IllegalStateException whenever an Android configuration change recreates the hosting Activity instance.
collectAsStateWithLifecycle() automatically persists the entire upstream StateFlow emission history inside encrypted SQLite across process death.
collectAsStateWithLifecycle() cancels collection below STARTED, letting upstream WhileSubscribed producers halt background CPU and network work.
collectAsState() collects emissions exclusively on background Dispatchers.IO threads and cannot trigger main-thread Compose UI recomposition.
