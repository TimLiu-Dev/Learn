Android Hardware Security & Biometrics

Protect sensitive cryptographic keys using Android Keystore (StrongBox/TEE) and BiometricPrompt authentication.

Recommended Primary Source
Google Android: Show a biometric authentication dialog
Official Documentation →

Storing bearer tokens, private wallet keys, or sensitive health records in plaintext <code>SharedPreferences</code>, Room, or DataStore leaves your users vulnerable on rooted devices or via physical backup extraction. Even encrypting data with an AES key hardcoded in Kotlin or C++ JNI (<code>libnative.so</code>) is security theater—any attacker with <code>jadx</code> or <code>Ghidra</code> can extract a static key in minutes! True mobile cryptography relies on the Android Hardware-Backed Keystore (<code>AndroidKeyStore</code>) and StrongBox Keymaster.

Under the Hood: TEE (TrustZone) vs. StrongBox Secure Element

When you generate an <code>AES/GCM/NoPadding</code> secret key using <code>KeyGenerator.getInstance(KeyProperties.KEY_ALGORITHM_AES, "AndroidKeyStore")</code>, the raw key bytes never enter the Android Linux kernel or your app's RAM. Instead, the key is generated and sealed inside hardware:

  • TEE (Trusted Execution Environment / ARM TrustZone): An isolated secure world on the main SoC processor with its own cryptographic memory boundary.
  • StrongBox (<code>setIsStrongBoxBacked(true)</code>): Available on modern flagships (e.g., Google Tensor Titan M2, Samsung Knox Vault)—a physically discrete tamper-resistant Secure Element microprocessor with its own CPU, RNG, and storage!

When your app calls <code>cipher.doFinal(plaintext)</code>, the Android framework sends the plaintext across a hardware bus into the TEE/StrongBox, which performs the AES-GCM encryption inside the secure enclave and returns only the ciphertext and 128-bit authentication tag!

🌱 Junior Android Dev Mental Model: Boolean Callback vs. <code>CryptoObject</code>

Crucial Security Distinction: Calling <code>biometricPrompt.authenticate(promptInfo)</code> without a <code>CryptoObject</code> simply runs an <code>if (authenticated)</code> boolean check in Kotlin memory—which an attacker using Frida on a rooted device can hook and bypass in 3 lines of JavaScript! Passing <code>BiometricPrompt.CryptoObject(cipher)</code> binds a Keystore key configured with <code>setUserAuthenticationRequired(true)</code>: the hardware enclave itself refuses to unlock the <code>Cipher</code> until the fingerprint/face sensor sends a cryptographic hardware auth token (HAT) directly to the TEE!

❌ Junior Anti-Pattern: Frida-Bypassable Boolean Biometrics

// Attacker hooks onAuthenticationSucceeded() via Frida -> Instant bypass!
// Key is not cryptographically bound to biometric hardware unlock!
override fun onAuthenticationSucceeded(result: AuthenticationResult) {
    val secretKey = prefs.getString("plaintext_wallet_seed", "")
    unlockVaultUi(secretKey)
}

✅ 2027 Senior Production Standard: Hardware <code>CryptoObject</code> + AES-GCM

val keyGenSpec = KeyGenParameterSpec.Builder(
    "aether_vault_master_key",
    KeyProperties.PURPOSE_ENCRYPT or KeyProperties.PURPOSE_DECRYPT
)
    .setBlockModes(KeyProperties.BLOCK_MODE_GCM)
    .setEncryptionPaddings(KeyProperties.ENCRYPTION_PADDING_NONE)
    .setUserAuthenticationRequired(true)
    .setInvalidatedByBiometricEnrollment(true)
    .build()

// Cipher stays locked by TEE until biometric sensor issues Hardware Auth Token:
biometricPrompt.authenticate(promptInfo, BiometricPrompt.CryptoObject(cipher))

⚠️ Senior Interview Trap: <code>KeyPermanentlyInvalidatedException</code> & IV Reuse

Two critical production edge cases every senior Android engineer must handle:

  1. <code>RandomizedEncryptionRequired</code>: In <code>AES/GCM/NoPadding</code>, reusing the same Initialization Vector (IV) with the same key catastrophically compromises GCM confidentiality. <code>AndroidKeyStore</code> enforces <code>setRandomizedEncryptionRequired(true)</code> by default—generating a fresh random 12-byte IV inside the TEE on every <code>ENCRYPT_MODE</code> call. You must read <code>cipher.iv</code> after encrypting and store <code>[iv + ciphertext]</code> together so you can pass <code>GCMParameterSpec(128, iv)</code> when decrypting!
  2. <code>KeyPermanentlyInvalidatedException</code>: When <code>setInvalidatedByBiometricEnrollment(true)</code> is active and the user enrolls a *new* fingerprint in Android Settings (e.g., an attacker who knew the device PIN added their own thumbprint), <code>cipher.init()</code> throws <code>KeyPermanentlyInvalidatedException</code>. Your app must catch this, delete the invalidated Keystore entry, wipe the encrypted vault blob, and prompt the user to re-authenticate with their account credentials.

class KeyPermanentlyInvalidatedException(message: String) : Exception(message)

data class EncryptedVaultPayload(val ivHex: String, val ciphertextHex: String, val gcmTagBits: Int = 128)

class SimulatedTeeKeystore(
    private val keyAlias: String,
    private var enrolledFingerprintsHash: Int = 1001
) {
    private var keyCreationFingerprintHash: Int = enrolledFingerprintsHash
    private var hardwareAuthTokenPresent: Boolean = false

    fun enrollNewDeviceFingerprint(newHash: Int) {
        enrolledFingerprintsHash = newHash
    }

    fun grantBiometricHardwareAuthToken() {
        hardwareAuthTokenPresent = true
    }

    fun initGcmCipherAndEncrypt(plaintext: String): EncryptedVaultPayload {
        if (enrolledFingerprintsHash != keyCreationFingerprintHash) {
            throw KeyPermanentlyInvalidatedException("Key '$keyAlias' invalidated by new biometric enrollment!")
        }
        check(hardwareAuthTokenPresent) { "android.security.KeyStoreException: Key user not authenticated" }
        hardwareAuthTokenPresent = false // Consumed per operation
        val hex = plaintext.encodeToByteArray().joinToString("") { "%02x".format(it.toInt() xor 0x5A) }
        return EncryptedVaultPayload(ivHex = "9f8e7d6c5b4a3f2e1d0c9b8a", ciphertextHex = hex)
    }
}

fun main() {
    val tee = SimulatedTeeKeystore("aether_vault_aes256_key")
    tee.grantBiometricHardwareAuthToken()
    val payload = tee.initGcmCipherAndEncrypt("seed:witch-collapse-practice-feed")
    println("[TEE-GCM] Encrypted with CryptoObject: iv=${payload.ivHex} cipher=${payload.ciphertextHex} tag=${payload.gcmTagBits}b")

    println("[SETTINGS] User enrolls a new fingerprint in Android OS Settings...")
    tee.enrollNewDeviceFingerprint(newHash = 2002)
    try {
        tee.grantBiometricHardwareAuthToken()
        tee.initGcmCipherAndEncrypt("transfer:10_BTC")
    } catch (e: KeyPermanentlyInvalidatedException) {
        println("[SECURITY-TRAP] Caught ${e::class.simpleName}: ${e.message}")
        println("[RECOVERY] Purging invalidated alias & requiring full account re-verification.")
    }
}

When encrypting with AES/GCM/NoPadding in AndroidKeyStore, you must store the 12-byte random IV alongside the ciphertext. Implement AesGcmPayloadSerializer with fun pack(iv: ByteArray, ciphertext: ByteArray): ByteArray (which requires iv.size == 12 and returns iv + ciphertext) and fun unpack(combined: ByteArray): Pair<ByteArray, ByteArray> (which extracts the first 12 bytes as the IV and the remaining bytes as the ciphertext).

class AesGcmPayloadSerializer {
    companion object {
        const val GCM_IV_LENGTH_BYTES = 12
    }

    fun pack(iv: ByteArray, ciphertext: ByteArray): ByteArray {
        require(iv.size == GCM_IV_LENGTH_BYTES) { "GCM IV must be 12 bytes" }
        return iv + ciphertext
    }

    fun unpack(combined: ByteArray): Pair<ByteArray, ByteArray> {
        require(combined.size > GCM_IV_LENGTH_BYTES) { "Payload too short" }
        val iv = combined.copyOfRange(0, GCM_IV_LENGTH_BYTES)
        val ciphertext = combined.copyOfRange(GCM_IV_LENGTH_BYTES, combined.size)
        return iv to ciphertext
    }
}

Why this works: Prepending the 12-byte (96-bit) NIST-recommended GCM IV directly to the ciphertext guarantees atomic persistence in DataStore/Room and enables exact extraction via copyOfRange during decryption.

AES/GCM/NoPadding cipher transformations strictly require passing 64-byte initialization vectors rather than 12-byte vectors on Android 14+.
AndroidKeyStore enables setRandomizedEncryptionRequired to prevent IV reuse; call cipher.init without an IV and read cipher.iv afterward.
GCMParameterSpec parameter specifications are exclusively compatible with asymmetric RSA keypairs rather than symmetric AES block-cipher keys.
Authentication integrity-tag lengths inside GCMParameterSpec constructors must be configured representing bytes (16) instead of bits (128).
