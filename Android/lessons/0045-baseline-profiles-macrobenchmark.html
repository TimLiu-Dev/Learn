Baseline Profiles & Jetpack Macrobenchmark

Slash cold app startup times by 40%+ using ahead-of-time (AOT) Baseline Profiles and Macrobenchmark tests.

Recommended Primary Source
Google Android: Baseline Profiles Overview
Official Documentation →

When a user downloads your app from Google Play and launches it for the very first time, the Android Runtime (ART) faces a cold-start dilemma. Without ahead-of-time compilation guidance, ART must interpret DEX bytecode instructions or wait for its Just-In-Time (JIT) compiler to warm up—Slowing down cold start (<code>Time To Initial Display</code> / <code>Time To Full Display</code>) and causing jank during the first scroll of your Jetpack Compose screens! Baseline Profiles and Jetpack Macrobenchmark solve this by pre-compiling your critical execution paths at install time.

Under the Hood: ART Compilation Modes (<code>interpret-only</code>, <code>speed-profile</code>, <code>speed</code>)

Because Jetpack Compose is shipped as an unbundled Jetpack library inside your APK (rather than burned into the Android OS system image), every Composable function, <code>Modifier</code> node, and slot-table operation is regular DEX bytecode. A Baseline Profile (<code>baseline-prof.txt</code>) is a human-readable list of hot classes and methods (prefixed with <code>H</code> for Hot, <code>S</code> for Startup, <code>P</code> for Post-Startup) generated by <code>BaselineProfileRule</code>. During APK/AAB build packaging, AGP compiles <code>baseline-prof.txt</code> into a compact binary format (<code>assets/dexopt/baseline.prof</code>). When a user installs your app from the Play Store, <code>installd</code> invokes <code>dex2oat</code> with <code>--compiler-filter=speed-profile</code>, compiling every <code>H</code>/<code>S</code> method directly into native ARM64 machine code (<code>.odex</code>) before the user ever taps your launcher icon—delivering 25% to 40% faster cold startups and Compose frame rendering!

🌱 Junior Android Dev Mental Model: Macrobenchmark vs. Microbenchmark

Macrobenchmark drives your full app process externally via <code>UiAutomator</code> to measure real startup (<code>StartupTimingMetric</code>) and scrolling jank (<code>FrameTimingMetric</code>) and generate Baseline Profiles. Microbenchmark runs a tight in-process loop 1,000+ times to measure a pure CPU algorithm (like a custom order-book sorting function).

ReportDrawnWhen, Time To Full Display (TTFD) & App Startup Initializers

Android automatically records Time To Initial Display (TTID) when the first frame of your Activity is drawn. However, in an offline-first app, the first frame might just be a skeleton shimmer before Room emits cached data! Calling ReportDrawnWhen { uiState.isPortfolioLoaded } in Compose (which invokes ComponentActivity.reportFullyDrawn() under the hood) notifies the OS and Macrobenchmark when Time To Full Display (TTFD) is reached—and tells BaselineProfileRule to keep recording hot methods until your asynchronous data actually renders.

Equally important during cold start is eliminating ContentProvider initialization bloat before Application.onCreate(). Many third-party SDKs (WorkManager, Crashlytics, Analytics) historically registered their own manifest <provider> just to auto-initialize on cold start—adding 10–30ms per provider on the main thread before your first Activity even starts! In 2027 production apps, you consolidate startup work using Jetpack App Startup (androidx.startup.Initializer<T>) behind a single shared InitializationProvider, or strip automatic initialization entirely for non-critical SDKs (like WorkManager via Configuration.Provider on-demand initialization) and defer heavy disk/network warmups onto a background coroutine after the first frame renders.

✅ 2027 Senior Production Standard: <code>BaselineProfileRule</code> + <code>ReportDrawnWhen</code>

@RunWith(AndroidJUnit4::class)
class AetherBaselineProfileGenerator {
    @get:Rule
    val rule = BaselineProfileRule()

    @Test
    fun generateStartupAndScrollProfile() = rule.collect(
        packageName = "com.aether.portfolio",
        includeInStartupProfile = true
    ) {
        pressHome()
        startActivityAndWait() // Waits for Activity + ReportDrawnWhen!
        val list = device.findObject(By.res("portfolio_lazy_column"))
        list.setGestureMargin(device.displayWidth / 5)
        list.fling(Direction.DOWN)
    }
}

⚠️ Senior Interview Trap: Startup Profiles & Multi-DEX Layout Optimization

What is the difference between a standard <strong>Baseline Profile</strong> (<code>includeInStartupProfile = false</code>) and a <strong>Startup Profile</strong> (<code>includeInStartupProfile = true</code>)? A Baseline Profile guides ART's <code>dex2oat</code> install-time AOT compilation on the user's device. A <strong>Startup Profile</strong> is additionally consumed *at build time* by R8/D8 to partition your APK's DEX files—packing all startup classes into the primary <code>classes.dex</code> so the OS kernel doesn't incur page-fault I/O loading <code>classes2.dex</code> and <code>classes3.dex</code> during cold start!

enum class ArtCompilationFilter { INTERPRET_ONLY, SPEED_PROFILE }

data class ProfileRuleEntry(val flags: String, val classDescriptor: String, val methodSignature: String?)

class ArtDex2OatSimulator(private val baselineRules: List<ProfileRuleEntry>) {
    fun simulateColdStart(filter: ArtCompilationFilter): String {
        val hotMethods = baselineRules.count { "H" in it.flags && "S" in it.flags }
        val startupClasses = baselineRules.count { it.methodSignature == null }
        return when (filter) {
            ArtCompilationFilter.INTERPRET_ONLY ->
                "[COLD START: JIT/INTERPRET] 0 methods AOT-compiled. TTID=640ms, TTFD=890ms, JankyFrames=14%"
            ArtCompilationFilter.SPEED_PROFILE ->
                "[COLD START: SPEED-PROFILE] AOT-compiled $hotMethods hot startup methods & packed $startupClasses classes into classes.dex. TTID=395ms (-38%), TTFD=510ms (-43%), JankyFrames=1.2%"
        }
    }
}

fun main() {
    val rules = listOf(
        ProfileRuleEntry("HS", "Lcom/aether/MainActivity;", "onCreate(Landroid/os/Bundle;)V"),
        ProfileRuleEntry("HSPL", "Lcom/aether/feature/portfolio/PortfolioScreenKt;", "PortfolioRoute(Lcom/aether/PortfolioState;)V"),
        ProfileRuleEntry("HS", "Lcom/aether/core/database/AssetDao_Impl;", "observeActiveAssets()Lkotlinx/coroutines/flow/Flow;"),
        ProfileRuleEntry("", "Lcom/aether/MainActivity;", null),
        ProfileRuleEntry("", "Lcom/aether/feature/portfolio/PortfolioScreenKt;", null)
    )

    val simulator = ArtDex2OatSimulator(rules)
    println(simulator.simulateColdStart(ArtCompilationFilter.INTERPRET_ONLY))
    println(simulator.simulateColdStart(ArtCompilationFilter.SPEED_PROFILE))

class BaselineProfileParser {
    fun filterHotStartupMethods(rawLines: List<String>): List<String> {
        return rawLines.filter { line ->
            val flags = line.substringBefore("L")
            line.contains("->") && flags.contains("H") && flags.contains("S")
        }
    }
}

Why this works: In ART's human-readable baseline-prof.txt syntax, method rules include '->' and begin with flag characters ('H' for hot, 'S' for startup, 'P' for post-startup) immediately preceding the 'L' JVM class descriptor.

StartupTimingMetric() only captures telemetry during iOS XCUITest instrumentation executions and malfunctions inside Android Macrobenchmark suites.

Quiz 2: Production Architectural Reasoning

In Jetpack Compose, why should you place <code>ReportDrawnWhen { uiState is PortfolioUiState.Success }</code> on your main landing screen?

It blocks the main Looper thread until PortfolioUiState.Success materializes, preventing loading indicators from briefly rendering visually.
ReportDrawnWhen automatically invalidates and purges persistent Room SQLite database caches once initial composition frames finish rendering.
It delays reportFullyDrawn() until async data renders, producing accurate timeToFullDisplayMs metrics and complete Baseline Profile traces.
ReportDrawnWhen permanently disables Jetpack Compose snapshot state observation and recomposition once the boolean predicate evaluates true.
