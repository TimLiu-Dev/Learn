Advanced Hilt: Custom `@Qualifier` Annotations, `@AssistedInject` ViewModels & `@TestInstallIn`

As your dependency graph grows across dozens of feature modules, three advanced DI patterns become mandatory:

  1. Type Disambiguation via `@Qualifier`: You should never hardcode `Dispatchers.IO` or `Dispatchers.Default` inside a Repository or UseCase, because doing so makes deterministic unit testing with `StandardTestDispatcher` impossible. However, since `Dispatchers.IO`, `Dispatchers.Default`, and `Dispatchers.Main` all share the exact same Kotlin type (`CoroutineDispatcher`), Hilt cannot tell them apart by type alone. Defining custom `@Qualifier` annotations (`@IoDispatcher`, `@DefaultDispatcher`) lets Hilt bind and inject distinct instances of the same type cleanly.
  2. Runtime Arguments in ViewModels via `@AssistedInject`: Since Dagger Hilt 2.49+, `@HiltViewModel(assistedFactory = ...)` supports `@AssistedInject`! When a `ViewModel` needs a dynamic runtime parameter passed from a composable (such as a Navigation 3 `MarketDetailKey` or a bottom-sheet widget config that isn't inside a legacy `SavedStateHandle`), you annotate that parameter with `@Assisted` and create it via `hiltViewModel<OrderViewModel, OrderViewModel.Factory> { factory -> factory.create(runtimeTicker) }`.
  3. Hermetic Integration Testing via `@TestInstallIn`: In instrumentation or Robolectric integration tests (`@HiltAndroidTest`), @TestInstallIn(components = [SingletonComponent::class], replaces = [ProdNetworkModule::class]) swaps out production network/database modules for deterministic in-memory fakes across the entire test suite without touching production source code.
🌱 Junior Android Dev Mental Model: Never Use `@Named("io")` Strings in Production!

While JSR-330 offers string-based @Named("io"), a typo like @Named("iO") is Easy to make and harder to refactor across modules. Always define dedicated strongly-typed @Qualifier @Retention(AnnotationRetention.BINARY) annotation class IoDispatcher annotations instead!

Senior Interview Trap: Application-Scoped CoroutineScope for Work That Must Outlive ViewModel

What happens if a user taps "Submit Trade" and immediately presses the Back button while the HTTP POST is in flight? If the repository launched the POST inside `viewModelScope`, popping the screen cancels `viewModelScope` mid-flight, leaving the user unsure whether their order executed! Senior engineers inject an `@ApplicationScope CoroutineScope(SupervisorJob() + defaultDispatcher)` into repositories for critical fire-and-complete mutations that must finish syncing to the local DB even if the originating screen closes.

❌ Junior Anti-Pattern: Hardcoded Dispatchers.IO & Mutable `lateinit` Setter on ViewModel

@HiltViewModel
class BadChartViewModel @Inject constructor(
    private val api: ChartApi
) : ViewModel() {
    // BUG 1: Requiring UI to call vm.initTicker("BTC") after creation causes race conditions!
    lateinit var ticker: String

    fun load() {
        // BUG 2: Hardcoded Dispatchers.IO cannot be controlled by TestScope!
        viewModelScope.launch(Dispatchers.IO) { api.fetch(ticker) }
    }
}

✅ 2027 Senior Production Standard: @Qualifier Dispatcher + @AssistedInject ViewModel

@Qualifier
@Retention(AnnotationRetention.BINARY)
annotation class IoDispatcher

@HiltViewModel(assistedFactory = ChartViewModel.Factory::class)
class ChartViewModel @AssistedInject constructor(
    @Assisted private val ticker: String,
    @IoDispatcher private val ioDispatcher: CoroutineDispatcher,
    private val api: ChartApi
) : ViewModel() {

    @AssistedFactory
    interface Factory {
        fun create(ticker: String): ChartViewModel
    }
}

// In Composable (e.g. Navigation 3 entry):
val vm = hiltViewModel<ChartViewModel, ChartViewModel.Factory> { factory ->
    factory.create(key.ticker)
}

enum class DispatcherQualifier { IO, DEFAULT, MAIN_IMMEDIATE }

class DispatcherRegistry(private val isTestMode: Boolean) {
    fun resolve(qualifier: DispatcherQualifier): String {
        if (isTestMode) return "StandardTestDispatcher(virtualClock)"
        return when (qualifier) {
            DispatcherQualifier.IO -> "Dispatchers.IO(64-thread-pool)"
            DispatcherQualifier.DEFAULT -> "Dispatchers.Default(CPU-cores)"
            DispatcherQualifier.MAIN_IMMEDIATE -> "Dispatchers.Main.immediate"
        }
    }
}

class AssistedOrderViewModel(
    val assistedSymbol: String,
    val injectedIoDispatcher: String,
    val injectedRepoName: String
) {
    fun interface Factory {
        fun create(symbol: String): AssistedOrderViewModel
    }
}

fun main() {
    for (testMode in listOf(false, true)) {
        val registry = DispatcherRegistry(isTestMode = testMode)
        val repoName = if (testMode) "FakeInMemoryOrderRepo (@TestInstallIn)" else "ProdNetworkOrderRepo"
        val factory = AssistedOrderViewModel.Factory { symbol ->
            AssistedOrderViewModel(
                assistedSymbol = symbol,
                injectedIoDispatcher = registry.resolve(DispatcherQualifier.IO),
                injectedRepoName = repoName
            )
        }
        val vm = factory.create("SOL-USD")
        println("[MODE=${if (testMode) "TEST" else "PROD"}] Created VM(symbol=${vm.assistedSymbol}) | Dispatcher=${vm.injectedIoDispatcher} | Repo=${vm.injectedRepoName}")
    }
}

import dagger.assisted.Assisted
import dagger.assisted.AssistedFactory
import dagger.assisted.AssistedInject
import dagger.hilt.android.lifecycle.HiltViewModel
import kotlinx.coroutines.CoroutineDispatcher
import javax.inject.Qualifier

@Qualifier
@Retention(AnnotationRetention.BINARY)
annotation class IoDispatcher

@HiltViewModel(assistedFactory = OrderBookViewModel.Factory::class)
class OrderBookViewModel @AssistedInject constructor(
    @Assisted val symbol: String,
    @IoDispatcher val dispatcher: CoroutineDispatcher
) {
    @AssistedFactory
    interface Factory {
        fun create(symbol: String): OrderBookViewModel
    }
}

Why this works: @Qualifier disambiguates multiple CoroutineDispatcher bindings at compile time, while @AssistedInject and @AssistedFactory let Hilt inject graph dependencies (dispatcher) alongside caller-supplied runtime arguments (symbol).

Quiz 1: Code Analysis & Bug Hunt

Examine this Hilt module providing two `OkHttpClient` instances (one authenticated, one public). Why does the KSP build fail with `[Dagger/DuplicateBindings] okhttp3.OkHttpClient is bound multiple times`?

@Module
@InstallIn(SingletonComponent::class)
object HttpModule {
    @Provides @Singleton
    fun providePublicOkHttpClient(): OkHttpClient = OkHttpClient.Builder().build()

    @Provides @Singleton
    fun provideAuthOkHttpClient(authInterceptor: AuthInterceptor): OkHttpClient =
        OkHttpClient.Builder().addInterceptor(authInterceptor).build()
}
A single `@Module` object cannot contain more than one `@Provides` function.
Dagger Hilt resolves bindings by their return type and qualifiers, ignoring `@Provides` function names (`providePublicOkHttpClient` vs `provideAuthOkHttpClient`). Both functions must be annotated with distinct `@Qualifier` annotations (e.g., `@PublicClient` and `@AuthenticatedClient`).
`OkHttpClient` is a final class and must be bound with `@Binds` instead of `@Provides`.
`@Singleton` can only be applied once per module.
