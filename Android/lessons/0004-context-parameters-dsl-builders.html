Kotlin 2.x Context Parameters & Type-Safe DSLs

Eliminate dependency plumbing using Kotlin 2.x context parameters and build expressive UI DSLs with @DslMarker.

Recommended Primary Source
Kotlin Evolution: Context Parameters Specification
Official Documentation →

Large-scale Android codebases constantly thread cross-cutting capabilities—such as AnalyticsLogger, FeatureFlagGate, TransactionScope, or LocaleFormatter—through deep call hierarchies. Passing them as explicit parameters clutters domain logic, while hiding them in global singletons breaks testability. Kotlin 2.2+ Context Parameters (context(logger: AnalyticsLogger, tx: DatabaseTransaction), which replaced experimental context receivers from Kotlin 1.6–2.0) solve this cleanly at the language level.

Unlike legacy context receivers—which introduced implicit multiple-this ambiguity because every context was unnamed—Kotlin 2.x Context Parameters give each ambient dependency an explicit parameter name (or underscore _ when only used for implicit resolution of downstream calls). At the JVM bytecode level, the compiler lowers context(logger: Logger) fun trackCheckout() into standard leading method parameters on the generated static/member function, meaning zero runtime reflection and zero ThreadLocal overhead.

🌱 Junior Android Dev Mental Model: How @DslMarker Prevents Scope Leakage

When you build a nested declarative DSL in Kotlin (like Compose's LazyColumn { item { ... } }, Navigation graphs, or Gradle's android { defaultConfig { ... } }), each lambda uses a Lambda with Receiver (BlockScope.() -> Unit). Without @DslMarker, an inner lambda can accidentally call methods on an outer receiver! Annotating all builder classes with the same @DslMarker meta-annotation forces the compiler to disallow implicit calls to outer receivers.

Type-Safe Builders & @DslMarker Mechanics

A type-safe DSL combines three Kotlin features:

  1. Function Types with Receiver (Receiver.() -> Unit): Inside the block, this is bound to the builder instance, exposing builder methods directly.
  2. @DslMarker Scope Control: Applying a custom marker annotation (e.g., @NavGraphDsl) to every builder class in the hierarchy restricts implicit this lookup strictly to the innermost receiver.
  3. Explicit Immutable Seal on Build: The builder mutates private state only during construction and returns a deeply immutable domain object when the lambda exits.

⚠️ Senior Interview Trap: Context Parameters vs. Dependency Injection (Hilt/Metro)

Senior candidates are often asked: "Should we replace Hilt/Dagger constructor injection with Kotlin 2.x Context Parameters everywhere?" No! Constructor injection manages long-lived object graphs and component lifecycles (Repositories, ViewModels, OkHttpClients). Context parameters are designed for lexical, call-scoped ambient capabilities—such as a short-lived database TransactionContext, a parser's ErrorCollector, or a UI DSL's SemanticsScope—that only exist for the duration of a lexical block (introduced via context(tx) { ... } or with(tx) { ... }).

❌ Junior Anti-Pattern: Unscoped Receiver Leakage in Nested DSLs

// Missing @DslMarker! Inner 'step' block can accidentally
// call 'step { ... }' on the outer WorkflowBuilder!
class WorkflowBuilder {
    fun step(name: String, block: StepBuilder.() -> Unit) { ... }
}
class StepBuilder {
    var retryCount: Int = 0
}

workflow {
    step("Upload") {
        retryCount = 3
        // BUG: Compiles! Calls outer WorkflowBuilder.step() by mistake!
        step("AccidentalNestedStep") { }
    }
}

✅ 2027 Senior Standard: @DslMarker + Context Parameter

@DslMarker
annotation class TelemetryDsl

@TelemetryDsl
class EventPacketBuilder(val name: String) {
    private val attrs = mutableMapOf<String, String>()
    fun attr(k: String, v: String) { attrs[k] = v }
    fun build(): Map<String, String> = attrs.toMap()
}

// Kotlin 2.2+ Named Context Parameter
context(sink: TelemetrySink)
fun emitEvent(name: String, block: EventPacketBuilder.() -> Unit) {
    val packet = EventPacketBuilder(name).apply(block).build()
    sink.record(name, packet)
}

@DslMarker
annotation class NavigationDsl

data class DeepLinkSpec(val uriPattern: String, val requireAuth: Boolean)
data class RouteDestination(val route: String, val deepLinks: List<DeepLinkSpec>)

@NavigationDsl
class RouteBuilder(private val route: String) {
    private val links = mutableListOf<DeepLinkSpec>()

    fun deepLink(uriPattern: String, requireAuth: Boolean = true) {
        links.add(DeepLinkSpec(uriPattern, requireAuth))
    }

    fun build(): RouteDestination = RouteDestination(route, links.toList())
}

@NavigationDsl
class NavGraphBuilder {
    private val destinations = mutableListOf<RouteDestination>()

    fun composableRoute(route: String, block: RouteBuilder.() -> Unit) {
        destinations.add(RouteBuilder(route).apply(block).build())
    }

    fun build(): List<RouteDestination> = destinations.toList()
}

fun navGraph(block: NavGraphBuilder.() -> Unit): List<RouteDestination> =
    NavGraphBuilder().apply(block).build()

fun main() {
    val graph = navGraph {
        composableRoute("profile/{userId}") {
            deepLink("app://android2027/profile/{userId}", requireAuth = true)
            deepLink("https://android2027.dev/u/{userId}", requireAuth = false)
        }
        composableRoute("settings/security") {
            deepLink("app://android2027/security", requireAuth = true)
        }
    }

    graph.forEach { dest ->
        println("[ROUTE] ${dest.route} -> ${dest.deepLinks.size} deepLink(s): ${dest.deepLinks}")
    }
}

@DslMarker
annotation class RolloutDsl

@RolloutDsl
class RolloutConfigBuilder {
    private val flags = mutableMapOf<String, Boolean>()

    fun flag(key: String, enabled: Boolean) {
        flags[key] = enabled
    }

    fun build(): Map<String, Boolean> = flags.toMap()
}

fun rolloutConfig(block: RolloutConfigBuilder.() -> Unit): Map<String, Boolean> {
    return RolloutConfigBuilder().apply(block).build()
}

Why this works: @DslMarker prevents nested DSL blocks from implicitly accessing outer receivers, while RolloutConfigBuilder.() -> Unit provides a clean receiver-scoped configuration block that seals into an immutable Map via .toMap().

Why did Kotlin 2.2+ replace the experimental 'context receivers' design (context(Logger)) with explicit 'context parameters' (context(logger: Logger))?

Unnamed receivers caused method shadowing, whereas named context parameters provide explicit disambiguation with implicit downstream forwarding
Context receivers required expensive runtime reflection across Android runtimes, whereas context parameters utilize ThreadLocal storage variables
Named context parameters automatically generate Dagger and Hilt @Provides dependency injection component bindings during annotation processing
