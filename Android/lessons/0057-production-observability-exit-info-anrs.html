Production Observability: ApplicationExitInfo, ANRs & Staged Rollouts

Diagnose silent OOM/LMK kills and ANRs via ApplicationExitInfo, and ship safely using staged rollouts and remote kill switches.

Recommended Primary Source
Android Developers: Android Vitals & ApplicationExitInfo
Official Documentation →

A common blind spot among junior and mid-level developers is trusting Firebase Crashlytics' "99.9% Crash-Free Users" badge as complete truth. Crashlytics installs an uncaught JVM Thread.UncaughtExceptionHandler and a native signal handler (SIGSEGV, SIGABRT). However, when the Linux kernel's Low Memory Killer (LMK / lmkd) terminates your process via SIGKILL (kill -9), or when the OS kills your app due to an ANR (Application Not Responding), excessive CPU/battery drain, or an OS permission change, user-space handlers cannot run or flush network telemetry before death! To eliminate this blind spot, Android 11+ (with richer traces in Android 15/16/17) provides ActivityManager.getHistoricalProcessExitReasons() (ApplicationExitInfo).

On the next cold start, querying getHistoricalProcessExitReasons(packageName, pid = 0, maxNum = 5) returns kernel-recorded forensics for why previous process instances died: reason (REASON_ANR, REASON_LOW_MEMORY, REASON_CRASH_NATIVE, REASON_Crash, REASON_EXCESSIVE_RESOURCE_USAGE, REASON_DEPENDENCY_DIED), process importance at the moment of death (IMPORTANCE_FOREGROUND vs IMPORTANCE_CACHED), peak physical memory (rss and pss in kilobytes), and—for REASON_ANR and native tombstones—an openable traceInputStream containing the full system thread dump at the exact moment of the freeze! Senior teams combine ApplicationExitInfo ingestion with custom breadcrumbs (ActivityManager.setProcessStateSummary(byteArray)—up to 128 bytes persisted by the OS kernel across SIGKILL!) and disciplined staged Play Console rollouts (1% → 5% → 20% → 50% → 100%).

🌱 Junior Android Dev Mental Model: Foreground LMK vs. Normal Background LMK

Do not page the on-call engineer every time ApplicationExitInfo.reason == REASON_LOW_MEMORY! When a user switches to a heavy 3D game, Android normally reclaims background apps whose importance == IMPORTANCE_CACHED. You should only fire a high-severity Out-Of-Memory alert when reason == REASON_LOW_MEMORY AND importance <= IMPORTANCE_VISIBLE (or IMPORTANCE_FOREGROUND)—which means the OS killed your app while the user was actively looking at it!

Senior Interview Trap & Production Edge Case

Trap: Uploading every historical ApplicationExitInfo record on every app launch without deduplicating by exitInfo.timestamp or exitInfo.pid. Because getHistoricalProcessExitReasons returns a rolling ring buffer of recent exits, failing to store the lastReportedExitTimestamp in DataStore will re-report the same ANR 50 times for the same user, wildly skewing your observability dashboards.
Edge Case: How do you know which screen was open when a foreground SIGKILL (REASON_LOW_MEMORY) occurred if user-space handlers can't write to disk during kill -9? Call activityManager.setProcessStateSummary("screen=TradeChart|tier=PRO".toByteArray()) on navigation transitions; the kernel stores those bytes in system_server RAM and attaches them to exitInfo.processStateSummary on the next launch!

❌ Junior Anti-Pattern: Duplicate Reporting & Cached LMK Panic

// 1. Re-uploads the entire historical buffer on every launch (no timestamp cursor!)
// 2. Alerts on normal background IMPORTANCE_CACHED memory reclamation!
val exits = activityManager.getHistoricalProcessExitReasons(null, 0, 10)
exits.forEach { info ->
    if (info.reason == ApplicationExitInfo.REASON_LOW_MEMORY) {
        analytics.logFatalOom(info.rss) // 99% false positives from backgrounded apps!
    }
}

✅ 2027 Senior Standard: Deduplicated Foreground Exit Forensics

val lastSeenTs = prefsDataStore.getLastExitTimestamp()
val newExits = activityManager.getHistoricalProcessExitReasons(null, 0, 5)
    .filter { it.timestamp > lastSeenTs }

newExits.forEach { info ->
    val breadcrumb = info.processStateSummary?.decodeToString() ?: "unknown"
    val isForeground = info.importance <= ActivityManager.RunningAppProcessInfo.IMPORTANCE_VISIBLE
    if (info.reason == REASON_ANR || (info.reason == REASON_LOW_MEMORY && isForeground)) {
        telemetry.uploadExitForensics(info, breadcrumb, info.traceInputStream)
    }
}
newExits.maxOfOrNull { it.timestamp }?.let { prefsDataStore.saveLastExitTimestamp(it) }

data class SimulatedExitInfo(
    val pid: Int,
    val timestampMs: Long,
    val reason: String,
    val importance: Int, // 100 = FOREGROUND, 200 = VISIBLE, 400 = CACHED
    val rssKb: Long,
    val stateSummary: String
)

object ExitTelemetryProcessor {
    private const val IMPORTANCE_VISIBLE = 200

    fun classifyNewExits(exits: List<SimulatedExitInfo>, lastReportedTs: Long): List<String> =
        exits.filter { it.timestampMs > lastReportedTs }
            .map { info ->
                val isUserVisible = info.importance <= IMPORTANCE_VISIBLE
                when {
                    info.reason == "REASON_ANR" ->
                        "CRITICAL_ANR(pid=${info.pid}, state=${info.stateSummary}, attachTrace=true)"
                    info.reason == "REASON_LOW_MEMORY" && isUserVisible ->
                        "CRITICAL_FOREGROUND_OOM(pid=${info.pid}, rssMb=${info.rssKb / 1024}, state=${info.stateSummary})"
                    info.reason == "REASON_LOW_MEMORY" && !isUserVisible ->
                        "BENIGN_CACHED_LMK_RECLAIM(pid=${info.pid}, ignored=true)"
                    else ->
                        "INFO_EXIT(reason=${info.reason}, pid=${info.pid})"
                }
            }
}

fun main() {
    val historicalBuffer = listOf(
        SimulatedExitInfo(4100, 1740000100L, "REASON_ANR", 100, 310_000L, "screen=OrderBook"),
        SimulatedExitInfo(4205, 1740000500L, "REASON_LOW_MEMORY", 400, 180_000L, "screen=HomeBg"),
        SimulatedExitInfo(4312, 1740000900L, "REASON_LOW_MEMORY", 100, 940_000L, "screen=4KVideoEditor")
    )

    // First cold start after pid 4100 was already reported at t=1740000100L
    val alerts = ExitTelemetryProcessor.classifyNewExits(historicalBuffer, lastReportedTs = 1740000100L)
    println("[EXIT-FORENSICS] Deduplicated new exits since t=1740000100:")
    alerts.forEach { println("  -> $it") }
}

fun triageExitRecord(
    timestampMs: Long,
    lastSeenTimestampMs: Long,
    reason: String,
    importance: Int
): String {
    if (timestampMs <= lastSeenTimestampMs) {
        return "SKIP_ALREADY_REPORTED"
    }
    return when {
        reason == "REASON_ANR" -> "UPLOAD_ANR_TRACE"
        reason == "REASON_LOW_MEMORY" && importance <= 200 -> "ALERT_FOREGROUND_LMK"
        else -> "IGNORE_BENIGN_EXIT"
    }
}

Why this works: Filtering out already-processed timestamps and distinguishing foreground/visible LMK kills (importance <= 200) from background cached process eviction keeps production alerting high-signal and actionable.

Concept Retrieval & Code Quizzes

Quiz 1: Code Analysis & Bug Hunt

You want to know which screen and feature flag state were active right before the OS Low Memory Killer (SIGKILL) terminated your app in the foreground. Why does the first approach below fail, and why does setProcessStateSummary succeed?

// Approach A: Trying to save breadcrumb on process death inside Runtime shutdown hook
Runtime.getRuntime().addShutdownHook(Thread {
    File(filesDir, "last_screen.txt").writeText(currentScreenName)
})

// Approach B: Updating kernel process state summary on screen navigation
activityManager.setProcessStateSummary("screen=$currentScreenName".encodeToByteArray())
Standard JVM shutdown hooks execute exclusively on iOS devices and always throw UnsupportedOperationException on Android.
SIGKILL skips JVM shutdown hooks, while setProcessStateSummary stores bytes in system_server memory for ApplicationExitInfo reads.
Calling setProcessStateSummary prevents the Linux kernel from terminating your foreground application regardless of memory pressure.
Invoking File.writeText automatically deletes the local Room SQLite database file whenever executed inside background threads.
