Gradle Convention Plugins with build-logic

Eliminate 500+ lines of duplicate build.gradle.kts boilerplate using custom Kotlin DSL convention plugins in build-logic.

Recommended Primary Source
Now in Android: Convention Plugins Guide (Google GitHub)
Official Documentation →

In a 20-module app, every feature module needs identical Gradle setup: compileSdk 35, Java 21 toolchains, Compose compiler flags, and Hilt plugins. The Google Now in Android standard solves this using Convention Plugins inside an included build named build-logic.

🌱 Junior Android Dev Mental Model: Custom Plugins as Presets

Instead of 50 lines of boilerplate, each feature module's build.gradle.kts becomes just 3 lines: 

plugins {
    alias(libs.plugins.aether.android.feature)
}
The custom plugin configures Android, Compose, Hilt, and testing automatically!

🎯 Reference Production Solution 
open class MockPlugin<T> { open fun apply(target: T) {} }
class MockProject { fun applyPlugin(id: String) {} }

class AndroidFeatureConventionPlugin : MockPlugin<MockProject> {
    override fun apply(target: MockProject) {
        target.applyPlugin("com.android.library")
    }
}

Why this works: Convention plugins encapsulate shared build logic into reusable Kotlin classes, ensuring consistent compiler flags and dependencies across all modules.
