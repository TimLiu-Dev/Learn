Gradle Convention Plugins with build-logic

Eliminate 500+ lines of duplicate build.gradle.kts boilerplate using custom Kotlin DSL convention plugins in build-logic.

Recommended Primary Source
Now in Android: Convention Plugins Guide (Google GitHub)
Official Documentation →

In a 25-module Android repository, copy-pasting compileSdk = 36, minSdk = 26, JavaVersion.VERSION_17, Compose compiler options, and Hilt KSP wiring across 25 build.gradle.kts files is an architectural anti-pattern. If you need to enable a new Kotlin compiler flag or update compileSdk, editing 25 build files creates merge conflicts and subtle configuration drift. The 2027 standard (championed by Google's Now in Android architecture) is an Included Build named build-logic housing Custom Gradle Convention Plugins.

Under the Hood: Why includeBuild("build-logic") Beat Legacy buildSrc

Historically, teams used Gradle's implicit buildSrc directory. However, prior to Gradle 8+ isolated classloaders—and even today when sharing build logic across composite builds—any edit inside buildSrc invalidates the root buildscript classpath for the entire project, busting task caches across every module. By contrast, declaring includeBuild("build-logic") inside settings.gradle.kts treats your convention plugins as a standalone composite Gradle build with fine-grained plugin IDs (e.g., aether.android.library, aether.android.feature, aether.android.hilt). Changes to the aether.android.feature plugin only invalidate modules that actually apply that plugin!

🌱 Junior Android Dev Mental Model: Composable Build Plugins

Think of a Convention Plugin like a Jetpack Composable function for your build scripts! Instead of repeating 60 lines of Android + Kotlin + Hilt + Compose setup in every feature module, a feature module's build.gradle.kts simply declares alias(libs.plugins.aether.android.feature) in 4 lines.

Accessing the Version Catalog Inside build-logic

Inside a binary convention plugin class (implementing Plugin<Project>), Gradle's generated libs.* Kotlin DSL accessors are not automatically in scope for the target project. Instead, you retrieve the shared catalog via the VersionCatalogsExtension: val libs = extensions.getByType<VersionCatalogsExtension>().named("libs"), allowing your convention plugin to wire libs.findLibrary("hilt.android").get() and libs.findLibrary("hilt.compiler").get() centrally.

✅ 2027 Senior Production Standard: build-logic Convention Plugin

// build-logic/convention/src/main/kotlin/AndroidFeatureConventionPlugin.kt
class AndroidFeatureConventionPlugin : Plugin<Project> {
    override fun apply(target: Project) = with(target) {
        pluginManager.apply {
            apply("aether.android.library")
            apply("aether.android.hilt")
        }
        val libs = extensions.getByType<VersionCatalogsExtension>().named("libs")
        dependencies {
            add("implementation", project(":core:model"))
            add("implementation", project(":core:data"))
            add("implementation", project(":core:designsystem"))
            add("implementation", libs.findLibrary("androidx.lifecycle.runtime.compose").get())
        }
    }
}

⚠️ Senior Interview Trap: Legacy subprojects { ... } & Gradle Project Isolation

Never configure subprojects by placing a subprojects { ... } or allprojects { ... } block in your root build.gradle.kts! Cross-project configuration couples every module's configuration phase together and directly breaks Gradle Project Isolation (which configures all modules in parallel across CPU threads). Convention plugins in build-logic configure each Project in complete isolation.

class SimulatedGradleProject(val path: String) {
    val appliedPlugins = mutableSetOf<String>()
    val dependencies = mutableListOf<Pair<String, String>>()
    var compileSdk: Int = 0
    var minSdk: Int = 0
}

fun interface ConventionPlugin {
    fun apply(target: SimulatedGradleProject)
}

class AndroidLibraryConventionPlugin : ConventionPlugin {
    override fun apply(target: SimulatedGradleProject) {
        target.appliedPlugins += "com.android.library"
        target.appliedPlugins += "org.jetbrains.kotlin.android"
        target.compileSdk = 36
        target.minSdk = 26
    }
}

class AndroidHiltConventionPlugin : ConventionPlugin {
    override fun apply(target: SimulatedGradleProject) {
        target.appliedPlugins += "com.google.devtools.ksp"
        target.appliedPlugins += "dagger.hilt.android.plugin"
        target.dependencies += "implementation" to "com.google.dagger:hilt-android:2.55"
        target.dependencies += "ksp" to "com.google.dagger:hilt-compiler:2.55"
    }
}

class AndroidFeatureConventionPlugin(
    private val libraryPlugin: AndroidLibraryConventionPlugin,
    private val hiltPlugin: AndroidHiltConventionPlugin
) : ConventionPlugin {
    override fun apply(target: SimulatedGradleProject) {
        libraryPlugin.apply(target)
        hiltPlugin.apply(target)
        target.dependencies += "implementation" to "project(:core:model)"
        target.dependencies += "implementation" to "project(:core:data)"
        target.dependencies += "implementation" to "project(:core:designsystem)"
    }
}

fun main() {
    val featureProject = SimulatedGradleProject(":feature:portfolio")
    val featureConvention = AndroidFeatureConventionPlugin(
        AndroidLibraryConventionPlugin(),
        AndroidHiltConventionPlugin()
    )
    featureConvention.apply(featureProject)

    println("[PROJECT] ${featureProject.path} (compileSdk=${featureProject.compileSdk}, minSdk=${featureProject.minSdk})")
    println("[PLUGINS] ${featureProject.appliedPlugins}")
    featureProject.dependencies.forEach { (cfg, notation) ->
        println("  + $cfg("$notation")")
    }
}

interface TargetProject {
    fun applyPlugin(pluginId: String)
    fun addCatalogDependency(configuration: String, catalogAlias: String)
}

class AndroidHiltConventionPlugin {
    fun apply(target: TargetProject) {
        target.applyPlugin("com.google.devtools.ksp")
        target.applyPlugin("dagger.hilt.android.plugin")
        target.addCatalogDependency("implementation", "hilt.android")
        target.addCatalogDependency("ksp", "hilt.compiler")
    }
}

Why this works: Centralizing KSP and Hilt plugin application plus compiler processor wiring inside a single convention plugin guarantees every module uses KSP instead of legacy KAPT and stays locked to the catalog version.
