Clean Architecture Domain Layer (When & How to Use Cases)

Encapsulate complex business rules with single-responsibility Use Cases and avoid 1:1 pass-through over-engineering.

Recommended Primary Source
Google Android: Guide to App Architecture - Domain Layer
Official Documentation →

Pragmatic Clean Architecture: Pure Kotlin Domain Layer & operator fun invoke UseCases

In a multi-module 2027 Android codebase, Clean Architecture enforces the Dependency Rule: source code dependencies point strictly inward toward business policy. Your UI Layer (:feature:*) depends on the Domain Layer (:core:domain), and the Data Layer (:core:data) also depends on and implements the repository interfaces defined in :core:domain (Dependency Inversion). Crucially, :core:domain is a pure Kotlin/JVM module (kotlin("jvm")) with zero dependencies on android.*, Retrofit, Room, or Compose—meaning your domain unit tests compile and execute in milliseconds on the raw JVM!

However, a major trap in over-engineered codebases is creating 100 "pass-through" UseCases that literally do nothing except forward a single line (override suspend fun invoke() = repo.getItems()). In 2027 pragmatic Android architecture (aligned with Google's official architecture guidance), a UseCase (Interactor) earns its existence when it:

  1. Combines data from 2+ repositories (e.g., merging a live MarketRepository price stream with PortfolioRepository holdings and UserPreferencesRepository currency settings).
  2. Encapsulates complex, reusable business rules (e.g., validating margin requirements, tick-size rounding, and fee tiers before placing an order) shared across multiple ViewModels.
🌱 Junior Android Dev Mental Model: Why operator fun invoke?

Declaring operator fun invoke(...) on a single-responsibility UseCase lets callers invoke the injected instance like a function: calculatePortfolioValuationUseCase(baseCurrency = "USD")! Also, make your UseCases stateless—never store mutable caches inside a UseCase; state belongs in the Repository (single source of truth) or the ViewModel (UI state).

Senior Interview Trap: Domain Error Modeling vs Throwing Unchecked Exceptions

When a domain rule fails (e.g., InsufficientBuyingPower or MarketClosed), throwing raw runtime exceptions across coroutine boundaries forces callers to guess what can fail. In 2027 Kotlin, model expected domain outcomes explicitly as a sealed hierarchy (sealed interface PlaceOrderResult or typed error union) so the compiler forces the ViewModel to handle every business failure path exhaustively in a when expression.

✅ 2027 Senior Production Standard: Pure Kotlin UseCase Combining Repositories

// Pure Kotlin module (:core:domain) — zero Android dependencies!
class ObserveNetPortfolioValueUseCase @Inject constructor(
    private val holdingsRepository: HoldingsRepository,
    private val marketPriceRepository: MarketPriceRepository,
    private val feePolicyRepository: FeePolicyRepository
) {
    operator fun invoke(accountId: String): Flow<PortfolioValuation> = combine(
        holdingsRepository.observeHoldings(accountId),
        marketPriceRepository.observeSpotPrices(),
        feePolicyRepository.observeTierFeeRate(accountId)
    ) { holdings, prices, feeRate ->
        val gross = holdings.sumOf { pos -> (prices[pos.symbol] ?: 0.0) * pos.quantity }
        val netAfterLiquidationFee = gross * (1.0 - feeRate)
        PortfolioValuation(grossUsd = gross, netUsd = netAfterLiquidationFee)
    }.distinctUntilChanged()
}

data class Holding(val symbol: String, val quantity: Double)

sealed interface OrderValidationResult {
    data class Approved(val symbol: String, val notionalUsd: Double, val feeUsd: Double) : OrderValidationResult
    data class RejectedInsufficientFunds(val requiredUsd: Double, val availableUsd: Double) : OrderValidationResult
    data object RejectedBelowMinimumLot : OrderValidationResult
}

class ValidateSpotOrderUseCase(private val feeRate: Double = 0.001) {
    operator fun invoke(
        symbol: String,
        quantity: Double,
        spotPriceUsd: Double,
        availableCashUsd: Double
    ): OrderValidationResult {
        val grossUsd = quantity * spotPriceUsd
        if (grossUsd < 10.0) return OrderValidationResult.RejectedBelowMinimumLot
        val feeUsd = grossUsd * feeRate
        val totalRequired = grossUsd + feeUsd
        return if (totalRequired <= availableCashUsd) {
            OrderValidationResult.Approved(symbol, grossUsd, feeUsd)
        } else {
            OrderValidationResult.RejectedInsufficientFunds(totalRequired, availableCashUsd)
        }
    }
}

fun main() {
    val validateOrder = ValidateSpotOrderUseCase(feeRate = 0.001)
    val scenarios = listOf(
        Triple(0.00005, 94000.0, 5000.0),
        Triple(0.05, 94000.0, 3000.0),
        Triple(0.02, 94000.0, 5000.0)
    )
    for ((qty, price, cash) in scenarios) {
        val result = validateOrder(symbol = "BTC", quantity = qty, spotPriceUsd = price, availableCashUsd = cash)
        println("[USE-CASE invoke(qty=$qty)] -> $result")
    }
}

import kotlinx.coroutines.flow.Flow
import kotlinx.coroutines.flow.combine

interface CashRepository { fun observeCashUsd(): Flow<Double> }
interface MarginRepository { fun observePendingHoldsUsd(): Flow<Double> }

class ObserveBuyingPowerUseCase(
    private val cashRepo: CashRepository,
    private val marginRepo: MarginRepository
) {
    operator fun invoke(): Flow<Double> = combine(
        cashRepo.observeCashUsd(),
        marginRepo.observePendingHoldsUsd()
    ) { cash, holds ->
        (cash - holds).coerceAtLeast(0.0)
    }
}

Why this works: ObserveBuyingPowerUseCase is a pure Kotlin class with zero Android dependencies, uses operator fun invoke() for ergonomic invocation in ViewModels, and encapsulates multi-repository domain rules in a single testable location.

class CalculateTaxLiabilityUseCase @Inject constructor(

Kotlin 2.x coroutines strictly forbid combining the operator keyword with suspend functions inside domain classes.
It violates Dependency Inversion by importing concrete Room DAO and Context while holding thread-unsafe state.
Domain UseCase classes cannot use @Inject constructors and must be instantiated manually inside ViewModel.init blocks.
Calling collection sumOf operations inside a suspend function directly blocks the Android Choreographer rendering thread.
