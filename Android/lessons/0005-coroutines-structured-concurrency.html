Kotlin Coroutines Fundamentals & Structured Concurrency

Harness structured concurrency, CPS state machines, coroutine cancellation, and error isolation.

Recommended Primary Source

Official Documentation →

Under the hood, a Kotlin suspend fun does not block OS threads or allocate heavy thread stacks. The K2 compiler transforms every suspending function into a Continuation-Passing Style (CPS) finite state machine via an added final parameter: Continuation<T>. Each suspension point is compiled into a state label in a when (this.label) switch table. When a coroutine suspends (e.g., awaiting network I/O), it saves local variables into fields on its heap-allocated Continuation object and returns COROUTINE_SUSPENDED, freeing the underlying OS thread immediately.

Structured Concurrency organizes every coroutine into a strict parent-child Job tree via its CoroutineContext:
1. A parent Job cannot complete until all of its children have completed.
2. Cancelling a parent Job recursively cancels all of its children.
3. An uncaught exception (other than CancellationException) in a child propagates upward, cancelling the parent and all sibling coroutines unless isolated by a SupervisorJob.

🌱 Junior Android Dev Mental Model: Cooperative Cancellation

Calling job.cancel() does NOT forcefully kill a running CPU loop like Thread.stop(). Coroutine cancellation is cooperative: a tight CPU loop on Dispatchers.Default (e.g., parsing 50,000 JSON nodes or encrypting files) will keep running after the user closes the screen unless you call ensureActive(), yield(), or check isActive inside the loop!

🔥 Senior Interview Trap #1: Why scope.launch(SupervisorJob()) Breaks Structured Concurrency!

One of the most common bugs in production Android code is writing viewModelScope.launch(SupervisorJob()) { ... } thinking it isolates child failures. Look closely at what happens to the Job hierarchy:

  • When you pass a brand-new SupervisorJob() into launch(...), that new SupervisorJob replaces the parent scope's Job in the coroutine context with a root SupervisorJob(parent = null)!
  • You have completely severed the parent-child link to viewModelScope! When the user exits the screen and ViewModel.onCleared() cancels viewModelScope, this detached coroutine is never cancelled and leaks indefinitely.
  • The Fix: Either use supervisorScope { launch { ... }; launch { ... } } inside an existing coroutine, or if you must pass a supervisor job explicitly, bind it to the parent job: SupervisorJob(parent = coroutineContext.job).

🔥 Senior Interview Trap #2: runCatching / catch (e: Throwable) Swallowing CancellationException!

Coroutines signal normal cancellation by throwing kotlinx.coroutines.CancellationException at suspension points. When you wrap a suspending call inside runCatching { api.fetchUser() } or try { ... } catch (e: Exception) without rethrowing CancellationException, you swallow the cancellation signal! The coroutine treats the cancelled call as a normal business error, stays alive as a "zombie coroutine," and continues executing subsequent lines (such as writing corrupted state to Room or calling subsequent APIs) even though its scope was cancelled! Always add if (e is CancellationException) throw e (or call currentCoroutineContext().ensureActive() in your failure handler).

❌ Junior Anti-Pattern: Severed Job & Swallowed Cancellation

// BUG 1: SupervisorJob() has NO parent! Leaks past viewModelScope!
viewModelScope.launch(SupervisorJob()) {
    // BUG 2: runCatching catches CancellationException!
    val result = runCatching {
        remoteApi.syncHeavyData() // suspends
    }
    result.onFailure { error ->
        // Executes even when user leaves screen & scope cancels!
        saveSyncFailureToDatabase(error)
    }
}

✅ 2027 Senior Standard: supervisorScope & Cancellation Rethrow

viewModelScope.launch {
    // Preserves parent-child link to viewModelScope while isolating children
    supervisorScope {
        launch {
            try {
                remoteApi.syncHeavyData()
            } catch (e: CancellationException) {
                throw e // ALWAYS rethrow CancellationException!
            } catch (e: Exception) {
                saveSyncFailureToDatabase(e)
            }
        }
    }
}

import kotlinx.coroutines.*

suspend fun runCatchingSuspendSafe(block: suspend () -> String): Result<String> =
    try {
        Result.success(block())
    } catch (e: CancellationException) {
        println("[CANCEL] Rethrowing CancellationException to preserve structured concurrency!")
        throw e
    } catch (e: Exception) {
        Result.failure(e)
    }

fun main() = runBlocking {
    println("[START] Launching supervisorScope with two isolated children...")
    supervisorScope {
        val failingChild = launch {
            delay(40L)
            throw IllegalStateException("Analytics upload 503")
        }

        val resilientSibling = launch {
            val outcome = runCatchingSuspendSafe {
                delay(80L)
                "Primary Dashboard Loaded"
            }
            println("[SIBLING] Completed intact despite sibling failure: ${outcome.getOrNull()}")
        }

        runCatching { failingChild.join() }
        resilientSibling.join()
    }
    println("[DONE] supervisorScope completed cleanly with parent-child hierarchy intact.")
}

import kotlinx.coroutines.*

suspend fun <T> executeCancellable(block: suspend () -> T): Result<T> {
    return try {
        Result.success(block())
    } catch (e: CancellationException) {
        throw e
    } catch (e: Exception) {
        Result.failure(e)
    }
}

suspend fun syncDashboardIndependent(
    taskA: suspend () -> String,
    taskB: suspend () -> String
): List<Result<String>> = supervisorScope {
    val deferredA = async { executeCancellable(taskA) }
    val deferredB = async { executeCancellable(taskB) }
    listOf(deferredA.await(), deferredB.await())
}

Why this works: Explicitly catching and rethrowing CancellationException prevents runCatching/catch(Exception) from breaking cooperative cancellation, while supervisorScope maintains the parent Job link to the caller's scope yet isolates child failures.
