Room Database with KSP: Entities, Foreign Key Indexes & N+1 Relation Queries

In 2027 Android apps, local persistence is built on Jetpack Room (with KSP) backed by SQLite in WAL (Write-Ahead Logging) mode, enabling concurrent reads while a write transaction is in progress. At compile time, Room's KSP processor validates every SQL query in your @Dao interfaces against your @Entity schemas—catching SQL syntax typos or missing columns during compilation rather than crashing in production!

Two database modeling mistakes frequently surface in Senior Android interviews and production performance traces:

  1. Missing @Index on @ForeignKey child columns: When you declare a @ForeignKey(entity = PortfolioAccountEntity::class, parentColumns = ["id"], childColumns = ["account_id"], onDelete = ForeignKey.CASCADE) on PositionEntity, SQLite automatically indexes the parent primary key (id), not the child column (account_id). Whenever a parent row is deleted or updated, SQLite must check PositionEntity for matching account_id rows—without an index on account_id, SQLite performs a full table scan while holding a write lock! Thankfully, Room emits a compile-time warning unless you add indices = [Index(value = ["account_id"])].
  2. Non-Atomic @Relation Queries without @Transaction: When modeling a 1-to-Many relationship using a POJO with @Embedded val account: AccountEntity and @Relation(parentColumn = "id", entityColumn = "account_id") val positions: List<PositionEntity>, Room executes two separate SQL SELECT queries under the hood. You must annotate the @Dao method with @Transaction so both queries run inside a single atomic SQLite snapshot—preventing inconsistent partial reads if a background sync updates PositionEntity between the two queries!
🌱 Junior Android Dev Mental Model: Why @Upsert Replaced Insert + Update

Instead of writing boilerplate @Insert(onConflict = OnConflictStrategy.REPLACE) (which actually deletes the existing row and inserts a new one—triggering ON DELETE CASCADE and wiping child foreign-key rows by accident!), use Room's @Upsert annotation! @Upsert executes SQLite's native INSERT ... ON CONFLICT DO UPDATE, updating existing rows in-place without triggering cascade deletions.

Senior Interview Trap: OnConflictStrategy.REPLACE Wiping Child Tables

This is a classic production data-loss post-mortem question: if AccountEntity has child PositionEntity rows linked with onDelete = ForeignKey.CASCADE, and you sync accounts from the server using @Insert(onConflict = OnConflictStrategy.REPLACE), SQLite implements INSERT OR REPLACE by deleting the existing AccountEntity row first and then inserting the replacement—which triggers ON DELETE CASCADE and silently deletes all of the user's local PositionEntity rows! Always use @Upsert instead of REPLACE when foreign key cascades exist.

        entity = AccountEntity::class,

✅ 2027 Senior Production Standard: Indexed Foreign Key + @Upsert + @Transaction

@Entity(
    tableName = "positions",
    indices = [Index(value = ["account_id"])], // Fast B-Tree lookup on joins & cascades!
    foreignKeys = [ForeignKey(
        entity = AccountEntity::class,
        parentColumns = ["id"],
        childColumns = ["account_id"],
        onDelete = ForeignKey.CASCADE
    )]
)
data class PositionEntity(
    @PrimaryKey val id: String,
    @ColumnInfo(name = "account_id") val accountId: String,
    val symbol: String
)

data class AccountWithPositions(
    @Embedded val account: AccountEntity,
    @Relation(parentColumn = "id", entityColumn = "account_id")
    val positions: List<PositionEntity>
)

@Dao
interface PortfolioDao {
    @Upsert // Updates in-place without triggering ON DELETE CASCADE!
    suspend fun upsertAccount(account: AccountEntity)

    @Transaction // Ensures parent & child @Relation SELECTs read the exact same snapshot!
    @Query("SELECT * FROM accounts WHERE id = :id")
    fun observeAccountWithPositions(id: String): Flow<AccountWithPositions>
}

data class AccountRow(val id: String, val name: String)
data class PositionRow(val id: String, val accountId: String, val symbol: String)

class SimulatedSqliteEngine {
    val accounts = mutableMapOf<String, AccountRow>()
    val positions = mutableListOf<PositionRow>()

    fun insertWithReplace(account: AccountRow) {
        if (accounts.containsKey(account.id)) {
            positions.removeAll { it.accountId == account.id }
            println("[SQLITE-REPLACE] Deleted existing Account '${account.id}' -> ON DELETE CASCADE wiped child positions!")
        }
        accounts[account.id] = account
    }

    fun upsert(account: AccountRow) {
        accounts[account.id] = account
        println("[SQLITE-UPSERT] Updated Account '${account.id}' in-place -> Child positions preserved (${positions.size} rows)!")
    }
}

fun main() {
    val db = SimulatedSqliteEngine()
    db.upsert(AccountRow("ACC-1", "Main Margin Account"))
    db.positions.add(PositionRow("POS-1", "ACC-1", "BTC"))
    db.positions.add(PositionRow("POS-2", "ACC-1", "ETH"))

    db.upsert(AccountRow("ACC-1", "Renamed Margin Account"))
    println("Positions after @Upsert: ${db.positions.map { it.symbol }}")

    db.insertWithReplace(AccountRow("ACC-1", "Replaced Margin Account"))
    println("Positions after @Insert(REPLACE): ${db.positions.map { it.symbol }} (DATA LOSS!)")
}

import androidx.room.Dao
import androidx.room.Embedded
import androidx.room.Entity
import androidx.room.PrimaryKey
import androidx.room.Query
import androidx.room.Relation
import androidx.room.Transaction
import androidx.room.Upsert
import kotlinx.coroutines.flow.Flow

@Entity(tableName = "watchlists")
data class WatchlistEntity(@PrimaryKey val id: String, val title: String)

@Entity(tableName = "watchlist_items")
data class WatchlistItemEntity(@PrimaryKey val itemId: String, val watchlist_id: String, val symbol: String)

data class WatchlistWithItems(
    @Embedded
    val watchlist: WatchlistEntity,
    @Relation(parentColumn = "id", entityColumn = "watchlist_id")
    val items: List<WatchlistItemEntity>
)

@Dao
interface WatchlistDao {
    @Upsert
    suspend fun upsertWatchlist(watchlist: WatchlistEntity)

    @Transaction
    @Query("SELECT * FROM watchlists WHERE id = :id")
    fun observeWatchlist(id: String): Flow<WatchlistWithItems>
}

Why this works: @Embedded and @Relation allow Room to join parent and child entities without manual cursor boilerplate, @Upsert updates existing parent rows in-place without triggering cascade deletes, and @Transaction ensures both SELECT queries read from a consistent database snapshot.

Quiz 1: Code Analysis & Bug Hunt

Examine this Room DAO method that fetches 500 OrderEntity rows and their associated FillEntity child rows using @Relation. Why does Room emit a compile-time warning Method return type contains a relation, so it should be annotated with @Transaction?

data class OrderWithFills(
    @Embedded val order: OrderEntity,
    @Relation(parentColumn = "orderId", entityColumn = "parentOrderId")
    val fills: List<FillEntity>
)

@Dao
interface OrderDao {
    @Query("SELECT * FROM orders")
    suspend fun getAllOrdersWithFills(): List<OrderWithFills>
}
Generated suspend DAO methods remain strictly read-only at runtime unless explicitly annotated with Room @Transaction.
Room @Relation queries execute on the main UI thread unless @Transaction switches execution onto Dispatchers.IO.
The Android SQLite driver cannot return Kotlin List collections without first acquiring an exclusive transaction.
Room runs separate parent and child queries, so @Transaction prevents inconsistent results from concurrent writes.

Quiz 2: Production Architectural Reasoning

Why should every @Entity inside a Room database represent only database persistence concerns, rather than doubling as both the Retrofit @Serializable network DTO and the Compose UI model?

Coupling DTOs, entities, and UI models makes JSON changes break SQLite migrations and Compose stability.
The Kotlin symbol processor strictly forbids placing Room @Entity and kotlinx @Serializable on one class.
Room @Entity classes require mutable var properties, which cannot be rendered inside Jetpack Compose functions.
Room @Entity instances are automatically cleared from local SQLite tables whenever network connectivity is lost.
