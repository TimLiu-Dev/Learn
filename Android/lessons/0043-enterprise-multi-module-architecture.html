Enterprise Multi-Module Architecture (Feature vs Core)

Scale Android codebases to 50+ engineers with strict module isolation and parallel Gradle compilation.

Recommended Primary Source
Google Android: Guide to multi-module app architecture
Official Documentation →

As an Android codebase scales beyond 50,000 lines of Kotlin and multiple feature squads, a monolithic :app module becomes an engineering bottleneck. Changing a single line in a shared helper invalidates the entire module's compilation cache, driving incremental build times from seconds to minutes and allowing circular spaghetti dependencies between unrelated screens.

Under the Hood: Directed Acyclic Graph (DAG) & Gradle Parallelism

Gradle models a multi-module project as a Directed Acyclic Graph (DAG) of tasks. When you partition your codebase horizontally by layer (:core:model, :core:network, :core:database, :core:data, :core:designsystem) and vertically by feature (:feature:market, :feature:portfolio, :feature:vault), Gradle can compile independent feature modules in parallel across all CPU cores (org.gradle.parallel=true). Better yet, with Gradle's Compile Avoidance and remote Build Cache, if you modify a private implementation inside :core:network without changing its public ABI, downstream modules that depend on it via implementation do not even need to recompile!

🌱 Junior Android Dev Mental Model: The 3 Golden Module Rules
  1. :feature:* modules NEVER depend on other :feature:* modules. Feature-to-feature navigation is wired up at the top-level :app assembly module (or via pure navigation route contracts).
  2. :core:model is a pure JVM/Kotlin module (kotlin("jvm")) with zero Android SDK dependencies, so domain models compile in milliseconds and run in pure JVM tests.
  3. Prefer implementation over api in build.gradle.kts to prevent leaking transitive dependencies across module boundaries.

api vs. implementation, ABI Compilation Avoidance & KSP Speed

When Module A declares implementation(project(":core:database")), Module A can use Room entities internally, but Module B (which depends on Module A) cannot see :core:database on its compile classpath. Under the hood, Gradle computes an ABI (Application Binary Interface) fingerprint containing only the public/internal signatures of a module (stripping private methods and method bodies). If :core:database changes a query body or private mapper without altering its public ABI, only :core:database recompiles—downstream modules using implementation stay UP-TO-DATE via Compilation Avoidance. By contrast, declaring api(...) exposes that module transitively on every consumer's compile classpath; only :core:model (whose domain classes appear in public repository method signatures) should ever be exposed via api(projects.core.model) when appropriate, while :core:network and :core:database remain strictly encapsulated behind implementation.

❌ Junior Anti-Pattern: Lateral Feature Coupling & api Leak

// :feature:portfolio/build.gradle.kts
dependencies {
    // BAD 1: Lateral dependency on another feature creates tight coupling
    // and flattens the build graph into a sequential chain!
    implementation(project(":feature:market"))

    // BAD 2: Leaking Room & Retrofit transitively to consumers!
    api(project(":core:database"))
    api(project(":core:network"))
}

✅ 2027 Senior Production Standard: Strict Layered DAG

// :feature:portfolio/build.gradle.kts
plugins {
    alias(libs.plugins.aether.android.feature)
    alias(libs.plugins.aether.android.library.compose)
}

dependencies {
    // Feature only sees domain models, UI design tokens, and data interfaces
    implementation(project(":core:model"))
    implementation(project(":core:data"))
    implementation(project(":core:designsystem"))
}

⚠️ Senior Interview Trap: Circular Dependencies & Graph Depth

What happens when :feature:market needs to navigate to :feature:asset-detail, and :feature:asset-detail can navigate back or open a related market sector? If they depend on each other, Gradle immediately fails configuration with a Circular dependency between the following tasks error. The senior solution is to expose a lightweight onAssetClick: (assetId: String) -> Unit lambda from MarketRoute (or place type-safe @Serializable route objects in a tiny contract module) and bind the destination inside :app's root NavHost.

data class GradleModule(val path: String, val dependencies: List<String>)

class ArchitectureDagValidator(private val modules: Map<String, GradleModule>) {
    fun validateRules(): List<String> {
        val violations = mutableListOf<String>()
        for ((name, mod) in modules) {
            if (name.startsWith(":feature:")) {
                val illegalFeatureDeps = mod.dependencies.filter { it.startsWith(":feature:") }
                illegalFeatureDeps.forEach { target ->
                    violations += "VIOLATION [Horizontal Feature Coupling]: $name -> $target"
                }
                val illegalLowLevelDeps = mod.dependencies.filter { it == ":core:database" || it == ":core:network" }
                illegalLowLevelDeps.forEach { target ->
                    violations += "VIOLATION [Encapsulation Bypass]: $name directly depends on $target (use :core:data)"
                }
            }
            if (name == ":core:model" && mod.dependencies.isNotEmpty()) {
                violations += "VIOLATION [Impure Domain Model]: :core:model must have zero module dependencies"
            }
        }
        return violations
    }
}

fun main() {
    val aetherGraph = listOf(
        GradleModule(":app", listOf(":feature:market", ":feature:portfolio", ":core:designsystem")),
        GradleModule(":feature:market", listOf(":core:data", ":core:designsystem", ":core:model")),
        GradleModule(":feature:portfolio", listOf(":core:data", ":core:designsystem", ":core:model", ":feature:market")),
        GradleModule(":core:data", listOf(":core:database", ":core:network", ":core:model")),
        GradleModule(":core:database", listOf(":core:model")),
        GradleModule(":core:network", listOf(":core:model")),
        GradleModule(":core:model", emptyList())
    ).associateBy { it.path }

    val validator = ArchitectureDagValidator(aetherGraph)
    val issues = validator.validateRules()
    println("[DAG CHECK] Scanned ${aetherGraph.size} Gradle modules.")
    issues.forEach { println("  ❌ $it") }
}

class ModuleDependencyAuditor {
    fun findIllegalFeatureDependencies(
        modulePath: String,
        deps: List<String>
    ): List<String> {
        if (!modulePath.startsWith(":feature:")) {
            return emptyList()
        }
        return deps.filter { dep ->
            dep.startsWith(":feature:") || dep == ":app" || dep == ":core:database"
        }
    }
}

Why this works: Enforcing module graph boundaries automatically in CI prevents feature modules from coupling to sibling features, the root :app module, or low-level persistence internals like :core:database.

Quiz 1: Code Analysis & Bug Hunt

Examine this :core:data/build.gradle.kts configuration. What is the build performance impact of declaring :core:network with api instead of implementation?

// :core:data/build.gradle.kts
dependencies {
    implementation(project(":core:model"))
    api(project(":core:network"))
    implementation(project(":core:database"))
}
Declaring api instructs R8 to disable dead-code elimination for every class inside :core:network during release.
Feature modules inherit :core:network on their compile classpath, so :core:network ABI changes force feature recompilation.
Gradle duplicates the compiled :core:network DEX bytecode inside every dependent feature module archive, doubling binaries.
Hilt cannot resolve dependency bindings from implementation modules, requiring api declarations whenever modules contain @Module.

Quiz 2: Production Architectural Reasoning

Why should :core:model be configured as a pure Kotlin/JVM module (id("org.jetbrains.kotlin.jvm")) rather than an Android Library module (id("com.android.library"))?

Automatic Kotlin data class equals and hashCode bytecode generation is only supported inside Kotlin/JVM modules.
Jetpack Compose stability inference only treats domain classes as @Immutable when compiled without an AndroidManifest.xml.
Pure JVM modules skip Android resource, manifest, and AAR tasks, compiling faster without Android coupling.
Room @Entity and @PrimaryKey database annotations can only be processed inside pure Kotlin/JVM library modules.
