Jetpack DataStore (Proto / Typed Kotlinx Serialization vs Preferences) & Why `SharedPreferences` is Extinct

In 2027 Android engineering, legacy SharedPreferences is strictly banned in production codebases. Why? Even though developers thought `SharedPreferences.Editor.apply()` was "safe and asynchronous" compared to `.commit()`, `apply()` queues an in-memory runnable in Android's `QueuedWork`. Whenever any `Activity.onStop()`, `Service.onDestroy()`, or broadcast finishes on the Main UI Thread, `ActivityThread` calls `QueuedWork.waitToFinish()`, blocking the Main Thread until the pending `SharedPreferences` `fsync` disk write completes—causing systemic `Application Not Responding` (ANR) crashes in Play Console vitals! Furthermore, `SharedPreferences` parses the entire XML file synchronously on first read, provides zero type safety, and cannot signal I/O errors.

Jetpack DataStore eliminates every one of these flaws by running all file reads and atomic write-rename operations asynchronously on `Dispatchers.IO`, exposing state as a cold Flow<T>, and updating values inside a transactional, coroutine-safe dataStore.updateData { current -> ... } block. DataStore comes in two flavors:

  1. Preferences DataStore (`DataStore<Preferences>`): Stores untyped key-value pairs (`booleanPreferencesKey("biometric_lock")`) similar to a map, without defining a schema upfront.
  2. Typed DataStore (`DataStore<UserSettings>` via Proto or Kotlinx Serialization `Serializer<T>`): The 2027 Senior Production Standard! Instead of nullable dictionary lookups, you persist a strongly-typed, immutable `@Serializable data class UserSettings` (or Protocol Buffer message) validated by a custom `Serializer<UserSettings>` paired with a ReplaceFileCorruptionHandler that recovers gracefully if disk blocks corrupt.
🌱 Junior Android Dev Mental Model: The Singleton File Rule for DataStore

Never instantiate two DataStore objects pointing to the same physical file (`"user_settings.pb"`) in the same process! Doing so throws an immediate IllegalStateException: There are multiple DataStores active for the same file. Always provide your `DataStore` instance as an @Singleton in Hilt's SingletonComponent!

Senior Interview Trap: Reading DataStore Synchronously with `runBlocking` at Startup

A common anti-pattern when migrating away from `SharedPreferences` is wrapping `runBlocking { dataStore.data.first() }` on the Main thread inside `Activity.onCreate()`. That re-introduces the exact disk-I/O main-thread stall DataStore was built to prevent! Instead, hold the Android 12+ `SplashScreen` open via `splashScreen.setKeepOnScreenCondition { viewModel.uiState.value is Loading }` while `viewModelScope` asynchronously collects the initial theme/auth state from `DataStore` on `Dispatchers.IO`.

✅ 2027 Senior Production Standard: Typed DataStore<UserSettings> + CorruptionHandler

@Serializable
data class UserSettings(
    val displayCurrency: String = "USD",
    val biometricEnabled: Boolean = false,
    val chartCandlesCount: Int = 120
)

@Provides @Singleton
fun provideUserSettingsDataStore(
    @ApplicationContext context: Context,
    @IoDispatcher ioDispatcher: CoroutineDispatcher
): DataStore<UserSettings> = DataStoreFactory.create(
    serializer = UserSettingsSerializer,
    scope = CoroutineScope(ioDispatcher + SupervisorJob()),
    corruptionHandler = ReplaceFileCorruptionHandler { UserSettings() },
    produceFile = { context.dataStoreFile("user_settings.json") }
)

// Transactional atomic read-modify-write:
suspend fun setCurrency(currency: String) {
    dataStore.updateData { current -> current.copy(displayCurrency = currency) }
}

class SimulatedTypedDataStore(
    initial: UserSettings = UserSettings(),
    private val onCorruptFallback: () -> UserSettings = { UserSettings() }
) {
    var currentData: UserSettings = initial
        private set

    fun updateData(transform: (UserSettings) -> UserSettings): UserSettings {
        val updated = transform(currentData)
        currentData = updated
        println("[DATASTORE-IO] Atomic write-and-rename committed -> $currentData")
        return currentData
    }

    fun simulateCorruptedDiskRead(): UserSettings {
        println("[DATASTORE-ERROR] CorruptionException detected on disk read! Invoking ReplaceFileCorruptionHandler...")
        currentData = onCorruptFallback()
        println("[DATASTORE-RECOVERED] Restored default settings -> $currentData")
        return currentData
    }
}

import androidx.datastore.core.DataStore
import java.io.IOException
import kotlinx.coroutines.flow.Flow
import kotlinx.coroutines.flow.catch

data class AppSettings(val biometrics: Boolean = false, val currency: String = "USD")

class UserPreferencesRepository(
    private val dataStore: DataStore<AppSettings>
) {
    val settingsFlow: Flow<AppSettings> = dataStore.data.catch { exception ->
        if (exception is IOException) {
            emit(AppSettings())
        } else {
            throw exception
        }
    }

    suspend fun enableBiometrics(enabled: Boolean) {
        dataStore.updateData { current ->
            current.copy(biometrics = enabled)
        }
    }
}

Why this works: Chaining .catch on dataStore.data handles disk read IOExceptions gracefully by emitting default settings instead of crashing the collector, while dataStore.updateData performs an atomic, serialized read-modify-write transaction on Dispatchers.IO.

Quiz 1: Code Analysis & Bug Hunt

Why does this repository crash at runtime with `IllegalStateException: There are multiple DataStores active for the same file` when two different screens call `ThemeRepository(context)`?

class ThemeRepository @Inject constructor(
    @ApplicationContext private val context: Context
) {
    private val dataStore = PreferenceDataStoreFactory.create {
        context.preferencesDataStoreFile("theme_prefs")
    }
    val isDarkFlow = dataStore.data.map { it[DARK_KEY] ?: false }
}
`preferencesDataStoreFile` can only be called inside an `Activity`, not with `@ApplicationContext`.
`PreferenceDataStoreFactory` does not support `.map` operators on `dataStore.data`.
File names passed to `preferencesDataStoreFile` cannot contain underscores.
`ThemeRepository` is unscoped, so every injection creates a new `ThemeRepository` instance that calls `PreferenceDataStoreFactory.create` for the same `theme_prefs.preferences_pb` file. `DataStore` strictly enforces a single process-wide instance per file to guarantee transactional consistency, so `DataStore` must be provided as an `@Singleton` in Hilt.

Quiz 2: Production Architectural Reasoning

Why does `SharedPreferences.edit().putBoolean("key", true).apply()` still cause Main-Thread ANRs (Application Not Responding) in production Android apps even though `.apply()` updates memory immediately and writes to disk on a background thread?

Android's `ActivityThread` calls `QueuedWork.waitToFinish()` on the Main UI Thread during `Activity.onStop()` and `Service` lifecycle transitions, which blocks the Main Thread until all pending `.apply()` disk `fsync` writes complete.
`apply()` secretly calls `commit()` on the main thread on Android 14+.
`SharedPreferences` encrypts every boolean with RSA-4096 on the UI thread.
`putBoolean` triggers a full SQLite `VACUUM` command.
