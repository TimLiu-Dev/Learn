Jetpack DataStore (Proto / Typed Kotlinx Serialization vs Preferences) & Why <code>SharedPreferences</code> is Extinct

In 2027 Android engineering, legacy SharedPreferences is strictly banned in production codebases. Why? Even though developers thought <code>SharedPreferences.Editor.apply()</code> was "safe and asynchronous" compared to <code>.commit()</code>, <code>apply()</code> queues an in-memory runnable in Android's <code>QueuedWork</code>. Whenever any <code>Activity.onStop()</code>, <code>Service.onDestroy()</code>, or broadcast finishes on the Main UI Thread, <code>ActivityThread</code> calls <code>QueuedWork.waitToFinish()</code>, blocking the Main Thread until the pending <code>SharedPreferences</code> <code>fsync</code> disk write completes—causing systemic <code>Application Not Responding</code> (ANR) crashes in Play Console vitals! Furthermore, <code>SharedPreferences</code> parses the entire XML file synchronously on first read, provides zero type safety, and cannot signal I/O errors.

Jetpack DataStore eliminates every one of these flaws by running all file reads and atomic write-rename operations asynchronously on <code>Dispatchers.IO</code>, exposing state as a cold Flow<T>, and updating values inside a transactional, coroutine-safe dataStore.updateData { current -> ... } block. DataStore comes in two flavors:

  1. Preferences DataStore (<code>DataStore<Preferences></code>): Stores untyped key-value pairs (<code>booleanPreferencesKey("biometric_lock")</code>) similar to a map, without defining a schema upfront.
  2. Typed DataStore (<code>DataStore<UserSettings></code> via Proto or Kotlinx Serialization <code>Serializer<T></code>): The 2027 Senior Production Standard! Instead of nullable dictionary lookups, you persist a strongly-typed, immutable <code>@Serializable data class UserSettings</code> (or Protocol Buffer message) validated by a custom <code>Serializer<UserSettings></code> paired with a ReplaceFileCorruptionHandler that recovers gracefully if disk blocks corrupt.
🌱 Junior Android Dev Mental Model: The Singleton File Rule for DataStore

Never instantiate two DataStore objects pointing to the same physical file (<code>"user_settings.pb"</code>) in the same process! Doing so throws an immediate IllegalStateException: There are multiple DataStores active for the same file. Always provide your <code>DataStore</code> instance as an @Singleton in Hilt's SingletonComponent!

Senior Interview Trap: Reading DataStore Synchronously with <code>runBlocking</code> at Startup

A common anti-pattern when migrating away from <code>SharedPreferences</code> is wrapping <code>runBlocking { dataStore.data.first() }</code> on the Main thread inside <code>Activity.onCreate()</code>. That re-introduces the exact disk-I/O main-thread stall DataStore was built to prevent! Instead, hold the Android 12+ <code>SplashScreen</code> open via <code>splashScreen.setKeepOnScreenCondition { viewModel.uiState.value is Loading }</code> while <code>viewModelScope</code> asynchronously collects the initial theme/auth state from <code>DataStore</code> on <code>Dispatchers.IO</code>.

❌ Legacy Anti-Pattern: SharedPreferences ANR & runBlocking DataStore Read

// BUG 1: SharedPreferences.apply() blocks Activity.onStop() on QueuedWork fsync -> ANR!
context.getSharedPreferences("prefs", MODE_PRIVATE)
    .edit()
    .putString("currency", "EUR")
    .apply()

// BUG 2: Calling runBlocking on Main Thread stalls frame rendering on disk I/O!

✅ 2027 Senior Production Standard: Typed DataStore<UserSettings> + CorruptionHandler

@Serializable
data class UserSettings(
    val displayCurrency: String = "USD",
    val biometricEnabled: Boolean = false,
    val chartCandlesCount: Int = 120
)

@Provides @Singleton
fun provideUserSettingsDataStore(
    @ApplicationContext context: Context,
    @IoDispatcher ioDispatcher: CoroutineDispatcher
): DataStore<UserSettings> = DataStoreFactory.create(
    serializer = UserSettingsSerializer,
    scope = CoroutineScope(ioDispatcher + SupervisorJob()),
    corruptionHandler = ReplaceFileCorruptionHandler { UserSettings() },
    produceFile = { context.dataStoreFile("user_settings.json") }
)

// Transactional atomic read-modify-write:
suspend fun setCurrency(currency: String) {
    dataStore.updateData { current -> current.copy(displayCurrency = currency) }
}

class SimulatedTypedDataStore(
    initial: UserSettings = UserSettings(),
    private val onCorruptFallback: () -> UserSettings = { UserSettings() }
) {
    var currentData: UserSettings = initial
        private set

    fun updateData(transform: (UserSettings) -> UserSettings): UserSettings {
        val updated = transform(currentData)
        currentData = updated
        println("[DATASTORE-IO] Atomic write-and-rename committed -> $currentData")
        return currentData
    }

    fun simulateCorruptedDiskRead(): UserSettings {
        println("[DATASTORE-ERROR] CorruptionException detected on disk read! Invoking ReplaceFileCorruptionHandler...")
        currentData = onCorruptFallback()
        println("[DATASTORE-RECOVERED] Restored default settings -> $currentData")
        return currentData
    }
}

import androidx.datastore.core.DataStore
import java.io.IOException
import kotlinx.coroutines.flow.Flow
import kotlinx.coroutines.flow.catch

data class AppSettings(val biometrics: Boolean = false, val currency: String = "USD")

class UserPreferencesRepository(
    private val dataStore: DataStore<AppSettings>
) {
    val settingsFlow: Flow<AppSettings> = dataStore.data.catch { exception ->
        if (exception is IOException) {
            emit(AppSettings())
        } else {
            throw exception
        }
    }

    suspend fun enableBiometrics(enabled: Boolean) {
        dataStore.updateData { current ->
            current.copy(biometrics = enabled)
        }
    }
}

Why this works: Chaining .catch on dataStore.data handles disk read IOExceptions gracefully by emitting default settings instead of crashing the collector, while dataStore.updateData performs an atomic, serialized read-modify-write transaction on Dispatchers.IO.

Quiz 1: Code Analysis & Bug Hunt

Why does this repository crash at runtime with <code>IllegalStateException: There are multiple DataStores active for the same file</code> when two different screens call <code>ThemeRepository(context)</code>?

class ThemeRepository @Inject constructor(
    @ApplicationContext private val context: Context
) {
    private val dataStore = PreferenceDataStoreFactory.create {
        context.preferencesDataStoreFile("theme_prefs")
    }
    val isDarkFlow = dataStore.data.map { it[DARK_KEY] ?: false }
}
The preferencesDataStoreFile helper can only be invoked inside an Activity context rather than with @ApplicationContext.
PreferenceDataStoreFactory does not allow chaining Flow map operators directly onto the exposed dataStore.data preference stream.
Preference file names passed into preferencesDataStoreFile cannot contain underscore characters on modern Android file systems.
Unscoped ThemeRepository creates duplicate DataStore instances for one file; DataStore requires a single @Singleton instance.

Quiz 2: Production Architectural Reasoning

Why does <code>SharedPreferences.edit().putBoolean("key", true).apply()</code> still cause Main-Thread ANRs (Application Not Responding) in production Android apps even though <code>.apply()</code> updates memory immediately and writes to disk on a background thread?

ActivityThread calls QueuedWork.waitToFinish on the main thread during onStop, blocking until pending apply writes finish.
The SharedPreferences apply implementation delegates directly to synchronous commit execution on the main application thread.
SharedPreferences synchronously encrypts every boolean preference value using RSA-4096 hardware keys on the UI thread.
Calling putBoolean on an Editor instance triggers a blocking SQLite VACUUM command across application databases.
