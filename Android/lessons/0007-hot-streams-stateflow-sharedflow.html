Hot Streams & State Management: StateFlow vs SharedFlow

Model production UI state with StateFlow and one-off navigation/toast events with SharedFlow.

Recommended Primary Source
Kotlin Docs: StateFlow and SharedFlow
Official Documentation →

Unlike cold Flows, Hot Streams (StateFlow and SharedFlow) remain active in memory independently of individual collectors and multicast emissions to multiple subscribers. In fact, StateFlow<T> is a specialized implementation of SharedFlow<T> configured with replay = 1, onBufferOverflow = BufferOverflow.DROP_OLDEST, a mandatory initial value, and structural equality conflation (Any.equals).

In 2027 Android architecture, we avoid creating separate coroutines in <code>init { ... }</code> to manually copy upstream repository Flows into a <code>MutableStateFlow</code>. Instead, we transform cold upstream Flows into a hot <code>StateFlow</code> declaratively using stateIn(scope = viewModelScope, started = SharingStarted.WhileSubscribed(5_000), initialValue = ...).

🌱 Junior Android Dev Mental Model: Why WhileSubscribed(5_000) & .update { }?

1. The 5-Second Grace Period: When a user rotates their device, the Activity is destroyed and recreated (~150–400ms), temporarily dropping the UI collector count to 0. WhileSubscribed(5_000) keeps the upstream database/network Flow alive for 5 seconds so configuration changes don't restart expensive queries, yet cancels upstream work 5 seconds after the user minimizes the app to the background!
2. Atomic CAS Updates: Never write _state.value = _state.value.copy(...) when multiple coroutines can update state concurrently; two threads reading the same <code>.value</code> will overwrite each other's changes (Lost Update Race). Always use _state.update { current -> current.copy(...) }, which runs a lock-free Compare-And-Swap (CAS) loop.

🔥 Senior Architectural Tradeoff: One-Off UI Events (Channel vs. SharedFlow vs. State Consumption)

How to handle "one-off" effects (navigation triggers, Snackbar messages, Toast alerts) is one of the deepest architectural debates in Senior/Staff Android interviews. Understand the exact tradeoffs of all three patterns:

  1. MutableSharedFlow(replay = 0, extraBufferCapacity = 1) (Broadcast Trap!): Because SharedFlow is a multicast broadcast stream with replay = 0, if an event is emitted while the UI lifecycle is temporarily below STARTED (e.g., mid-rotation or while a permission dialog pauses the Activity), there are 0 active collectors and the event is permanently lost! Do NOT use <code>SharedFlow(replay = 0)</code> for critical navigation or payment confirmation events.
  2. Channel<UiEffect>(Channel.BUFFERED).receiveAsFlow() (Single-Consumer Queue): Unlike <code>SharedFlow</code>, a <code>Channel</code> is a unicast queue: if no collector is currently subscribed, events wait safely in the buffer until the UI collector resumes after rotation. However, if the collector cancels mid-processing between receiving the item and completing the UI side-effect, an event can still be dropped in rare edge cases.
  3. Modeling Events as UI State + Idempotent Consumption Callback (Google Official Recommendation): Whenever an event affects what the user sees on screen (e.g., val userMessage: UserMessage? = null inside <code>UiState</code>), model it directly inside <code>StateFlow</code>! Once the UI displays the Snackbar, it invokes <code>viewModel.onUserMessageShown(messageId)</code> which clears it via <code>_uiState.update { it.copy(userMessage = null) }</code>. This guarantees zero lost events across process recreation and configuration changes.

❌ Junior Anti-Pattern: Race-Prone .value = & Dropped SharedFlow Events

class CheckoutViewModel : ViewModel() {
    val uiState = MutableStateFlow(CheckoutState())
    // BUG 1: replay=0 drops navigation events emitted during screen rotation!
    val navEvents = MutableSharedFlow<String>(replay = 0)

    fun onPayClicked() {
        // BUG 2: Non-atomic read-modify-write race condition!
        uiState.value = uiState.value.copy(isSubmitting = true)
    }
}

✅ 2027 Senior Standard: CAS .update {} & State-Modeled / Buffered Effects

class CheckoutViewModel : ViewModel() {
    private val _uiState = MutableStateFlow(CheckoutState())
    val uiState: StateFlow<CheckoutState> = _uiState.asStateFlow()

    // Unicast buffered queue for ephemeral side-effects (or model inside CheckoutState)
    private val _effects = Channel<CheckoutEffect>(Channel.BUFFERED)
    val effects: Flow<CheckoutEffect> = _effects.receiveAsFlow()

    fun onPayClicked() {
        _uiState.update { it.copy(isSubmitting = true) } // Atomic CAS loop
    }

    fun onReceiptBannerConsumed() {
        _uiState.update { it.copy(pendingBanner = null) }
    }
}

KOTLIN 2.X StateFlowAtomicStore.kt 
import kotlinx.coroutines.*
import kotlinx.coroutines.channels.Channel
import kotlinx.coroutines.flow.*

data class BannerMessage(val id: Long, val text: String)

data class WalletUiState(
    val balanceCents: Long = 10_000L,
    val txCount: Int = 0,
    val activeBanner: BannerMessage? = null
)

class WalletStateHolder {
    private val _uiState = MutableStateFlow(WalletUiState())
    val uiState: StateFlow<WalletUiState> = _uiState.asStateFlow()

    private val _navigationChannel = Channel<String>(Channel.BUFFERED)
    val navigationFlow: Flow<String> = _navigationChannel.receiveAsFlow()

    fun applyConcurrentDeposit(cents: Long, bannerId: Long) {
        // Atomic Compare-And-Swap loop: safe across concurrent threads
        _uiState.update { current ->
            current.copy(
                balanceCents = current.balanceCents + cents,
                txCount = current.txCount + 1,
                activeBanner = BannerMessage(bannerId, "Deposited $cents cents")
            )
        }
    }

    fun onBannerShown(bannerId: Long) {
        _uiState.update { current ->
            if (current.activeBanner?.id == bannerId) current.copy(activeBanner = null)
            else current
        }
    }
}

fun main() = runBlocking {
    val holder = WalletStateHolder()
    // Launch 50 concurrent deposits on Default dispatcher to verify CAS atomicity
    coroutineScope {
        repeat(50) { idx ->
            launch(Dispatchers.Default) {
                holder.applyConcurrentDeposit(cents = 100L, bannerId = idx.toLong())
            }
        }
    }
    println("[STATE] After 50 concurrent deposits: balance=${holder.uiState.value.balanceCents}, txCount=${holder.uiState.value.txCount}")
    val lastBannerId = holder.uiState.value.activeBanner?.id ?: -1L
    holder.onBannerShown(lastBannerId)
    println("[STATE] After consuming banner #$lastBannerId: activeBanner=${holder.uiState.value.activeBanner}")
}

import kotlinx.coroutines.flow.*

data class CartUiState(
    val itemCount: Int = 0,
    val totalCents: Long = 0L,
    val toastMessage: String? = null
)

class CartStateHolder {
    private val _uiState = MutableStateFlow(CartUiState())
    val uiState: StateFlow<CartUiState> = _uiState.asStateFlow()

    fun addItemAtomically(itemPriceCents: Long) {
        _uiState.update { current ->
            current.copy(
                itemCount = current.itemCount + 1,
                totalCents = current.totalCents + itemPriceCents,
                toastMessage = "Item added"
            )
        }
    }

    fun onToastShown() {
        _uiState.update { current ->
            current.copy(toastMessage = null)
        }
    }
}

Why this works: Exposing asStateFlow() prevents external callers from downcasting to MutableStateFlow, while _uiState.update { ... } performs a lock-free Compare-And-Swap loop and models the one-off toast message as consumable state so it cannot be lost during rotation.
