SOLID, Coupling & Composition — 2027 Android Cheat Sheet

Compressed essence of Lesson 01. Print or pin during PR reviews.

1. Root Forces

Low Coupling

Hide volatile details (3rd-party SDKs, Room SQL, HTTP DTOs) behind pure Kotlin interfaces so changing one module never cascades across screens.

High Cohesion

Keep each class focused on one job. If a class has both fee math and SQL queries, split it before adding features.

2. Composition vs. Inheritance Decision Rule

Question Use Inheritance / Sealed Use Composition (Has-A)
Can behaviors mix & match (Logging + Retry + Fee)? No (causes 2N subclass explosion) Yes — pass small collaborators via constructor
Can a subtype break a parent method (throws UnsupportedOperationException)? Never — violates LSP Yes — split capability interfaces (ISP)
Closed set of domain states (Loading, Success, Error)? Yes — Kotlin sealed interface N/A

3. SOLID PR-Review Checklist (2027 Android)

Letter 1-Line Senior Rule Red Flag in Android PR
SRP One reason to change per class/UseCase. ViewModel formats currencies, calls Retrofit, and builds Room entities.
OCP Add new variants without editing existing callers. Duplicated when (paymentType) scattered across 4 files.
LSP Subtypes honor every contract of the base interface. Subclass overrides a method just to throw UnsupportedOperationException.
ISP Depend only on the methods you actually call. Unit tests write 12 dummy overrides for a bloated Repository interface.
DIP Domain owns interfaces; Data implements them. :core:domain imports Retrofit, Room, or Android Context.

4. When NOT to Abstract (Anti-Over-Engineering Rule)

Skip interfaces for pure, deterministic helpers with zero I/O and zero competing implementations (e.g., MoneyFormatter). Place interfaces at volatile boundaries: network, DB, 3rd-party SDKs, OS APIs, and product policies. See Android Architecture Guide • Refactoring.Guru.
