Virtual Threads, Carrier Pinning & Concurrency Bulkheads

Turning on spring.threads.virtual.enabled=true lets Spring Boot handle 50,000 concurrent blocking HTTP requests without WebFlux complexity—but juniors immediately crash production by pooling Virtual Threads, blowing HikariCP database limits, or pinning carrier threads!

Java 21–25 LoomVirtual ThreadsSemaphore BulkheadHikariCP Limits

1. Never Pool Virtual Threads — Limit Downstream Resources Instead

Per Oracle Java 21+ Docs and Spring Boot Reference: Platform threads were scarce, so we pooled them (FixedThreadPool(200)). Virtual threads are cheap (1 task = 1 virtual thread). To throttle concurrent calls to a fragile bank partner or DB, use a Semaphore (Bulkhead) — never a fixed thread pool!

2. Carrier Pinning & The HikariCP Connection Trap

  • Pinning: On Java 21–23, holding a synchronized monitor across blocking I/O pinned the OS carrier thread (prefer ReentrantLock on 21–23; Java 24+ JEP 491 unpins synchronized!).
  • DB Bottleneck: 10,000 Virtual Threads calling `@Transactional` simultaneously still fight for 20 HikariCP DB connections—keep transactions tiny and never call external HTTP APIs while holding a DB connection!

5. 2027 Senior Backend Interview Corner

Q1: "Why is calling an external Stripe HTTP API inside a `@Transactional` Spring method catastrophic under Virtual Threads?"
Senior Answer: `@Transactional` holds a scarce HikariCP PostgreSQL connection for the entire method duration. If 500 Virtual Threads wait 2 seconds on Stripe HTTP calls inside `@Transactional`, your 20-connection DB pool saturates instantly and the whole backend stalls (`Connection is not available`). Do HTTP calls outside the DB transaction!
