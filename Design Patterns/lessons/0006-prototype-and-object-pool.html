Prototype & Object Pool: Safe Cloning & Zero-Churn Reuse

Two opposite problems in mobile systems: Prototype solves safe cloning without corrupting shared nested lists (crucial in Compose state), while Object Pool reuses expensive buffers to prevent GC stutter on low-RAM Android phones.

Creational data class.copy() Trap Compose Snapshots Buffer Pooling

1. Prototype & The data class.copy() Shallow Trap

Kotlin's copy() is a built-in Prototype—but it is shallow! If your TransferDraft holds a MutableList<Split>, cloning the draft shares the exact same list reference. Modifying Draft B silently corrupts Draft A (and breaks Jetpack Compose equality checks!). Fix: use immutable lists (List / kotlinx.collections.immutable) or explicit deep cloning.

2. Object Pool: Controlling Allocations Under Load

Allocating 4MB crypto/PDF buffers repeatedly on scroll or batch receipt export triggers GC pauses (jank). An Object Pool checks out a pre-allocated buffer, resets its state on release, and caps max pool size.

5. 2027 Senior Android Interview Corner

Q1: "When does an Object Pool actually hurt performance instead of helping?"
Senior Answer: Modern ART generational GC allocates and collects tiny short-lived objects in nanoseconds. Pooling small objects adds lock contention, memory leaks (if never released), and stale-data security bugs! Only pool genuinely expensive/large objects (Bitmaps, ByteBuffers, DB connections).
