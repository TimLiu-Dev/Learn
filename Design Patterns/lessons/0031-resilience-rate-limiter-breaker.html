Resilience4j: Token Bucket Rate Limiter, Aspect Order & DLQs

Stacking @Retry, @CircuitBreaker, and @RateLimiter blindly in Spring Boot causes subtle disasters—like retrying against an OPEN circuit or burning a bank partner's rate limit inside tight retry loops! Master the exact Resilience4j Decorator order and Token Bucket throttling.

1. Token Bucket Rate Limiter (`429 Too Many Requests`)

Protect PayVault's public API and outbound partner quotas with a Token Bucket: a bucket holds up to `capacity` tokens, refilling at `refillPerSec` based on elapsed clock time—allowing short bursts while bounding sustained throughput!

2. Resilience4j Default Aspect Order (And Why Order Matters!)

Per the Resilience4j User Guide, the default Spring AOP wrapper order is:

Retry ( CircuitBreaker ( RateLimiter ( TimeLimiter ( Bulkhead ( Target ) ) ) ) )
Wait—look closely! With default order, Retry sits outside CircuitBreaker (so 3 failed retries register as 1 outer failure—or if CB opens mid-retry, next attempt throws CallNotPermittedException!). If you want CircuitBreaker to count every individual HTTP failure (or fail fast immediately without retrying an OPEN circuit), configure circuitBreakerAspectOrder higher than retryAspectOrder!

5. 2027 Senior Backend Interview Corner

Q1: "Why add a Retry Budget and Dead Letter Queue (DLQ) instead of retrying Kafka messages forever?"
Senior Answer: A poison-pill message (e.g., malformed JSON or permanently closed bank account) retried infinitely blocks the Kafka partition and burns CPU forever. Cap retries (or enforce a Retry Budget like max 10% extra traffic) and route exhausted failures to a DLQ for alerting and manual/automated replay!
