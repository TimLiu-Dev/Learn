Offline-First Sync, Transactional Outbox & Idempotency

The #1 Fintech production disaster: User sends \$200 on a shaky subway connection. The server charges \$200, the HTTP response drops before reaching the phone, and WorkManager retries—charging the user \$400! Combining the Transactional Outbox (Command + Room `@Transaction`) with deterministic Idempotency Keys + Full Jitter Backoff guarantees at-least-once delivery with effectively-once financial effect.

2027 ArchitectureTransactional OutboxIdempotency KeyBackoff + Jitter

1. Transactional Outbox Pattern

When the user clicks "Send", do NOT fire Retrofit first! Inside a single atomic local SQLite @Transaction: 1) Insert a `PENDING` ledger row into Room (so UI updates immediately); 2) Insert an Outbox row containing a stable idempotencyKey = UUID. Then schedule WorkManager (`NetworkType.CONNECTED`) to drain the Outbox.

2. Idempotency Keys & Exponential Backoff with Jitter

Generate the `idempotencyKey` once at transfer creation and persist it in the Outbox row—NEVER generate a new UUID inside the retry loop! Add random jitter (`0 .. cap`) so 100,000 phones coming out of a subway outage don't DDoS your bank backend simultaneously (thundering herd).

5. 2027 Senior Android Interview Corner

Q1: "Why must the Ledger insert and Outbox insert happen inside the SAME Room `@Transaction`?"
Senior Answer: If the app crashes or battery dies between two separate inserts, you either show a transfer in UI that never syncs (lost money intent) or sync a payment with no local record. An atomic SQLite transaction guarantees both commit or neither commits.
