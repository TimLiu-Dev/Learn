Optimistic / Pessimistic Locking & Double-Entry Ledgers

Two threads read balance = \$100 at the same millisecond. Both pass `if (balance >= 80)`, both write `balance = 20`—and the user just withdrew \$160 from a \$100 wallet! Senior Fintech Engineers eliminate lost-update overdrafts with Optimistic (`@Version`) / Pessimistic (`FOR UPDATE`) Locking and replace mutable balance columns with an immutable Double-Entry Ledger.

Fintech Integrity@Version LockingFOR UPDATEDouble-Entry Ledger

1. Optimistic (`@Version`) vs. Pessimistic (`SELECT ... FOR UPDATE`)

  • Optimistic Locking (`@Version`): Read `version = 5`, update `WHERE id = ? AND version = 5`. If another thread bumped `version` to `6`, 0 rows update → `OptimisticLockException` → retry! Best for low/medium contention.
  • Pessimistic Locking (`@Lock(PESSIMISTIC_WRITE)`): Acquires a DB row lock (`FOR UPDATE`). Best for hot merchant accounts with massive contention (always lock account IDs in sorted order to prevent deadlocks!).

2. Double-Entry Accounting (Zero-Sum Invariant)

Never just `UPDATE wallets SET balance = balance - 50` without an audit trail! Every movement creates two balanced immutable entries: `DEBIT -5000` on `sender_acct` and `CREDIT +5000` on `receiver_acct`. The sum across the ledger is ALWAYS zero—making silent money creation or loss mathematically detectable!

5. 2027 Senior Backend Interview Corner

Q1: "How do you prevent database deadlocks when locking two accounts (`fromId` and `toId`) pessimistically?"
Senior Answer: Lock ordering! If Thread 1 transfers A → B and Thread 2 transfers B → A concurrently, acquiring `FOR UPDATE` in arbitrary order deadlocks. Always sort `[fromId, toId]` lexicographically first (`minId` then `maxId`) so all threads acquire locks in identical global order!
