Lesson 0005 • Phase 1: Creational Patterns

Singleton, Scopes & Dependency Injection (DI)

The Gang of Four Singleton is the most abused pattern in mobile history. In Fintech, a careless global object AuthSession can leak User A's wallet token to User B after logout—and make parallel unit tests fail randomly.

Creational Hilt / Metro / Koin Session Scoping Security Boundary

1. The 3 Fatal Flaws of Naive Global Singletons (`object`)

  • Hidden Dependencies: Calling AuthSession.token inside a UseCase hides what that class actually needs to run.
  • Test Pollution: Test 1 sets AuthSession.userId = "u1"; Test 2 runs in the same JVM and reads stale state!
  • Wrong Lifetime: Process lifetime != User-Session lifetime != Screen lifetime. Logout MUST destroy session-scoped caches.

2. Scoped Lifetimes via Dependency Injection

Per the Android Guide to App Architecture, let a DI container (Hilt, Kotlin-inject, Metro) own how many instances exist and when they die—while your domain classes stay plain constructors.

Kotlin — Plain Class Scoped by DI (Not `object`)
// ✅ Plain class: pure constructor, 100% isolated in unit tests!
class InMemorySessionStore : SessionStore {
    private var token: String? = null
    override fun saveToken(t: String) { token = t }
    override fun currentToken() = token
    override fun clear() { token = null }
}

5. 2027 Senior Android Interview Corner

Q1: "Why is `ServiceLocator.get<Repo>()` inside a ViewModel considered an anti-pattern compared to Constructor DI?"
Senior Answer: Service Locator hides a class's dependencies behind a global lookup, so you only discover missing bindings at runtime (crash!) instead of compile time, and unit tests must mutate global locator state instead of passing arguments to a constructor.
