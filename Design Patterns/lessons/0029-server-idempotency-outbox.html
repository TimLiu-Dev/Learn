Server Idempotency Keys & Transactional Outbox-to-Kafka

In Part 1 (L0021), the Android app promised to send a stable Idempotency-Key. Now build the server half! Plus, solve the Dual-Write Problem: why calling ledgerRepo.save() followed by kafkaTemplate.send() breaks consistency—and how the Server Transactional Outbox fixes it.

Server IntegrityIdempotency-KeyPayload Hash 422Outbox -> Kafka

1. Server Idempotency Store Contract

  • Step 1: Atomically claim `(userId, idempotencyKey, payloadHash)` using a PostgreSQL `UNIQUE` constraint (`INSERT ... ON CONFLICT DO NOTHING`).
  • Step 2: If the key already exists with a different `payloadHash` (client reused a key for a different amount!), reject with `422 Unprocessable Entity`!
  • Step 3: If already `COMPLETED` with matching hash, immediately replay the stored HTTP status + JSON body—never re-running the ledger debit.

2. Solving the DB + Kafka Dual-Write Problem

You cannot share one atomic ACID transaction between PostgreSQL and Apache Kafka! If DB commits and the pod crashes before `kafka.send()`, downstream Fraud/Notification services never hear about the transfer. Write the `OutboxEvent` row inside the same PostgreSQL `@Transactional` commit, then have an Outbox Poller (or Debezium CDC) relay unpublished rows to Kafka idempotently.

5. 2027 Senior Backend Interview Corner

Q1: "Why use PostgreSQL Outbox instead of wrapping `kafka.send()` inside `@Transactional` with Kafka transactions?"
Senior Answer: Chaining separate DB + Kafka transaction managers does not give true atomic 2PC—the DB can commit while Kafka times out, leaving partial state. Transactional Outbox guarantees atomicity inside PostgreSQL's single WAL, and works identically with Debezium CDC or a simple `@Scheduled` relay!
