Lesson 0032 • Part 2: Scale & Production Operations

CQRS, Event-Driven Projections & Fintech Observability

Summing 200,000 Double-Entry ledger rows on every mobile home-screen refresh will crush PostgreSQL—and logging raw user emails/card numbers violates PCI/GDPR! CQRS separates Write invariants from pre-aggregated Read projections, while OpenTelemetry + PII Redaction makes distributed bugs traceable in seconds.

CQRS & ProjectionsRead/Write SplitOpenTelemetryPII Redaction

1. CQRS: Write-Side Integrity vs. Read-Side Speed

Command side: Validates KYC, enforces `@Version` locking, appends immutable Double-Entry postings, and emits `LedgerPostedEvent`. Query side: Listens to events and updates a fast, denormalized `WalletSummaryView` (`balanceCents`, `monthlySpentCents`, `lastTxAt`)—turning O(N) ledger scans into O(1) indexed reads!

2. Distributed Tracing (`traceparent`) & PII-Safe Logging

Propagate W3C `traceId` from Android HTTP headers → Spring Filter (`MDC`) → Kafka event headers → Saga workers. Wrap log formatters/Decorators to mask emails, IBANs, and card PANs before anything hits Datadog/Cloud Logging.

5. 2027 Senior Backend Interview Corner

Q1: "When is CQRS overkill—and when does it become essential in Spring Boot?"
Senior Answer: Skip separate Read/Write databases for simple CRUD screens (`UserProfile`)—that's premature complexity. Introduce CQRS projections when write models are normalized/append-only (Double-Entry Ledger, Event Sourcing) while dashboards need fast pre-aggregated O(1) summaries!
