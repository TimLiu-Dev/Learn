Why Design Patterns Exist: Coupling, Composition & SOLID

Design patterns are not academic trivia to memorize for whiteboards. They are battle-tested blueprints for stopping one small product change from breaking ten unrelated screens. Before learning your first GoF pattern, you must master the two forces every pattern manipulates: Coupling and Composition.

The Junior → Senior Mental Shift: PayVault Day 1 vs. Month 6

Imagine you are hired to build PayVault, a Fintech Wallet Android app. On Day 1, the Product Manager says: "Just let users pay with a credit card via Stripe."

A junior developer opens CheckoutViewModel.kt, instantiates StripeApiClient("pk_live_...") directly inside the ViewModel, writes fee math inline, logs to Android Log.d(), and ships in 2 hours. It works!

Six months later, the business grows. PM asks for:

  • ACH Bank Transfers (0.5% fee capped at \$5) and Brazil Pix (instant, 0% fee).
  • Offline Queueing when users tap Pay in a subway tunnel.
  • Fast CI Unit Tests without hitting Stripe servers or booting an Android emulator.

Because everything is glued directly into CheckoutViewModel, changing one rule breaks three screens, unit tests require Robolectric + network mocks, and KMP iOS sharing is impossible. That pain is why design patterns exist.

1. Coupling & Cohesion: The Root Metric of Software Design

Low Coupling (Goal)

Coupling is how much Module A knows about Module B's internal details. If changing Stripe's JSON response or Android's Context forces you to edit your business logic, coupling is too high.

High Cohesion (Goal)

Cohesion means everything inside a class belongs together for one focused purpose. A FeeCalculator that only calculates fees has high cohesion; a WalletManager that formats dates, signs JWTs, and runs SQL has low cohesion.

2027 Android Reality Check: Why Coupling Hurts Build Times In a modern multi-module Android / KMP project, if :feature:checkout depends directly on :core:stripe-sdk, any edit to the Stripe wrapper forces Gradle to recompile every feature module using it. Introducing a pure Kotlin interface in :core:domain (per the Android Guide to App Architecture) cuts compile graphs and lets unit tests run on the JVM in <50ms.

2. Composition over Inheritance (Avoiding Subclass Explosion)

Juniors reach for inheritance (class B : A()) to share code. Seniors ask: "Is this an is-a permanent identity, or a has-a swappable capability?" As documented in Refactoring.Guru, most structural and behavioral patterns rely on replacing rigid inheritance with delegation.

Suppose PaymentProcessor can optionally have Logging, Retry, and FraudCheck. With inheritance, you end up writing LoggingStripeProcessor, RetryStripeProcessor, LoggingRetryStripeProcessor, LoggingRetryFraudStripeProcessor... That is 2N classes! With Composition, you pass small collaborators via constructor parameters:

Kotlin — Composition vs. Inheritance Trap 
// ❌ INHERITANCE TRAP: Subclass explosion + rigid parent coupling
open class StripeProcessor { open fun pay(cents: Long) { ... } }
class LoggingStripeProcessor : StripeProcessor() { ... }
class LoggingRetryStripeProcessor : LoggingStripeProcessor() { ... } // Fragile!

// ✅ COMPOSITION: Small, single-purpose pieces snapped together
fun interface FeePolicy { fun feeFor(cents: Long): Long }
fun interface AuditLogger { fun record(event: String) }
interface PaymentRail { fun charge(totalCents: Long): String }

class CheckoutService(
    private val rail: PaymentRail,
    private val feePolicy: FeePolicy,
    private val logger: AuditLogger
) {
    fun checkout(amountCents: Long): String {
        val total = amountCents + feePolicy.feeFor(amountCents)
        val receipt = rail.charge(total)
        logger.record("Charged $total cents -> $receipt")
        return receipt
    }
}

3. The 5 SOLID Principles (2027 Android Edition)

Forget textbook definitions—here is how each letter prevents real Android production bugs.

S — Single Responsibility Principle (SRP)

"A class should have one, and only one, reason to change." Separate UI state management (ViewModel), business rules (UseCase), and persistence/network (Repository). If a designer changes a button label and your payment validation file gets modified in Git, SRP was violated.

O — Open/Closed Principle (OCP)

"Open for extension, closed for modification." When PayVault adds Apple Pay or Pix, you should create a new class implementing PaymentRail—not hunt down five when (method) statements across the codebase.

L — Liskov Substitution Principle (LSP)

"Subtypes must be safely substitutable for their base types without surprising callers."

Kotlin — Classic Android/Fintech LSP Violation & Fix 
// ❌ VIOLATES LSP: Callers of WalletAccount assume withdraw() works!
open class WalletAccount(var balanceCents: Long) {
    open fun withdraw(cents: Long) { balanceCents -= cents }
}
class LockedVaultAccount(balance: Long) : WalletAccount(balance) {
    override fun withdraw(cents: Long) {
        throw UnsupportedOperationException("Vault is locked!") // 💥 Runtime crash!
    }
}

// ✅ FIX: Separate capabilities so illegal calls fail at COMPILE TIME
interface BalanceReadable { val balanceCents: Long }
interface Withdrawable : BalanceReadable { fun withdraw(cents: Long) }

class LockedVault(override val balanceCents: Long) : BalanceReadable
class CheckingWallet(override var balanceCents: Long) : Withdrawable {
    override fun withdraw(cents: Long) { balanceCents -= cents }
}

I — Interface Segregation Principle (ISP)

"Clients should not be forced to depend on interfaces they do not use." A 12-method WalletRepository forces your Compose BalanceCard ViewModel (and its unit test fakes!) to stub out KYC upload, PDF export, and card freezing methods it never calls. Split into small role interfaces: BalanceReader, TransferExecutor, KycUploader.

D — Dependency Inversion Principle (DIP)

"High-level policy (:domain) must not depend on low-level details (:network / :room). Both depend on abstractions." Notice that :core:domain defines interface PaymentGateway, and :core:network imports :core:domain to implement StripeGatewayAdapter. Domain never imports Retrofit, OkHttp, or Room! See Kotlin Interface Delegation for zero-boilerplate forwarding.

6. 2027 Senior Android Interview Corner

How Staff/Principal interviewers test whether you actually understand these principles vs. memorizing acronyms.

Q1: "Isn't creating interfaces and separating classes over-engineering for a small Android feature?"
Senior Answer: Yes, if you wrap a 20-line pure calculation in 4 interfaces for no reason—that is speculative abstraction. We introduce an interface boundary specifically at volatile seams: 3rd-party SDKs (Stripe, Firebase), I/O boundaries (Network/Room), platform APIs (Biometrics, Keystore), and policies that vary by product/region (Fees, Fraud Rules). A pure helper like formatCentsToUsd() needs no interface.
Q2: "How does Dependency Inversion actually speed up Android CI & enable Kotlin Multiplatform?"
Senior Answer: Because :core:domain only defines pure Kotlin interfaces (PaymentGateway, Clock, VaultStorage) with zero Android framework imports, domain logic compiles as pure JVM/KMP code. Unit tests run in milliseconds without Robolectric or emulators, and iOS can share the exact same domain rules by plugging in an iOS Keychain implementation of VaultStorage.
Q3: "Your teammate created a BaseViewModel that handles analytics, error dialogs, and retry logic via inheritance. Why should we push back in PR review?"
Senior Answer: God-class BaseViewModel inheritance couples every screen to dependencies it might not need (violating ISP), hides control flow in super calls, and breaks as soon as one screen needs custom retry or no dialog. Prefer small injected collaborators (ErrorMapper, AnalyticsTracker) or Kotlin delegation so each ViewModel stays explicit and independently testable.
