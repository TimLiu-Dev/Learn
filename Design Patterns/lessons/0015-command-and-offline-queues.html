Command Pattern & Durable Offline Queues

If a user sends \$50 in an elevator with zero signal, a direct function call api.send(5000) fails and disappears into thin air. The Command Pattern turns a request into a standalone object—letting you queue, serialize to Room, retry via WorkManager, audit-log, and undo/compensate!

BehavioralOffline QueueWorkManagerUndo / Compensation

1. Turning a Method Call into Data

Per Refactoring.Guru, Command decouples the sender (UI button) from the receiver (Ledger/API) by wrapping parameters + action into a `Command` object with `execute()` (and optionally `undo()`).

2. Fintech Note: Undo vs. Compensating Transaction

In local UI drafts (e.g., adjusting split-bill amounts), `undo()` reverses memory state. On settled financial ledgers, you never delete history—you execute a compensating command (refund/reversal entry) so the audit log stays append-only!

5. 2027 Senior Android Interview Corner

Q1: "Why store serialized Command data in Room instead of keeping `() -> Unit` lambdas in memory for offline sync?"
Senior Answer: In-memory lambdas vanish the instant Android kills the app process in the background (or the phone reboots). A serializable `TransferCommand` persisted in Room survives process death and executes reliably later via WorkManager.
