Decorator & Interceptor Chains

Want to layer Idempotency Keys, Auth Token Refresh, Retry, and Metrics around your PaymentGateway without touching the core gateway or writing 2N subclasses? That is the exact superpower of Decorator—the pattern powering OkHttp Interceptors and Compose Modifier!

StructuralOkHttp InterceptorsKotlin byIdempotency

1. Wrapping Objects Implementing the Same Interface

A Decorator implements the exact same interface as the object it wraps (PaymentGateway), runs logic before and/or after delegating to the inner instance, and stays completely transparent to callers.

2. Zero-Boilerplate Decorators with Kotlin by

Kotlin — Stacking Decorators Over PaymentGateway
interface PaymentGateway {
    fun charge(idempotencyKey: String, cents: Long): String
    fun name(): String
}

// `by inner` forwards name() automatically; we only override charge()!
class IdempotentCacheDecorator(
    private val inner: PaymentGateway
) : PaymentGateway by inner {
    private val cache = mutableMapOf<String, String>()
    override fun charge(idempotencyKey: String, cents: Long): String =
        cache.getOrPut(idempotencyKey) { inner.charge(idempotencyKey, cents) }
}

5. 2027 Senior Android Interview Corner

Q1: "Does decorator wrapping order matter? Give a concrete Fintech bug when order is flipped."
Senior Answer: Yes! If `LoggingDecorator` wraps `RetryDecorator`, you see 1 outer log for the operation; if `RetryDecorator` wraps `LoggingDecorator`, every retry attempt logs. Worse: if `CachingDecorator` sits *inside* `AuthHeaderDecorator`, it might cache an unauthenticated failure or miss auth checks!
