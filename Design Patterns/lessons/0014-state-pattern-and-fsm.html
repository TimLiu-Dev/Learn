Lesson 0014 • Phase 3: Behavioral Patterns

State Pattern & Finite State Machines (FSM)

Junior UI/Domain code models status with 5 independent booleans: isLoading, is3dsRequired, isSettled, isFailed, isCancelled. That allows 25 = 32 combinations—meaning 27 impossible bug states (like showing a Spinner AND "Transfer Settled" simultaneously!). The State Pattern / FSM makes invalid states and illegal transitions impossible.

1. Modeling a PayVault Transfer State Machine

In PayVault, a transfer moves strictly through: Draft → Authorizing → Challenge3DS | Settled | Failed (and Challenge3DS → Settled | Failed). Once Settled or Failed, clicking "Submit" again must be rejected—never double-charging the user!

2. Pure Reducer Transition Function

Kotlin — Deterministic Sealed State Machine
sealed interface TxState {
    data object Draft : TxState
    data object Authorizing : TxState
    data class Challenge3DS(val url: String) : TxState
    data class Settled(val txId: String) : TxState
    data class Failed(val reason: String) : TxState
}

5. 2027 Senior Android Interview Corner

Q1: "When is a pure `reduce(state, event) -> state` FSM better than classic GoF State subclasses mutating a Context?"
Senior Answer: In Jetpack Compose and Kotlin Coroutines, immutable `reduce(state, event)` functions over `sealed interface` states are thread-safe, replayable, serialize cleanly across process death, and pair natively with `StateFlow`. Classic mutable `state.handle(ctx)` classes still shine when each state owns heavy stateful resources (like a BLE socket or MediaPlayer).
