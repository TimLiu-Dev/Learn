Lesson 0035 • Part 3: Java & Kotlin Spring Boot Side-by-Side

Spring Boot Core: Java vs. Kotlin (`allopen`, Entities & Bean DSL)

Android Kotlin devs moving to Spring Boot routinely hit two silent traps: Kotlin classes are final by default (breaking Spring CGLIB proxies unless `kotlin-spring` is configured), and Kotlin `data class` breaks JPA `@Entity` `equals/hashCode` & Hibernate lazy proxies!

Java vs. Kotlinkotlin-spring / allopenJPA Entity RulesBean DSL

1. Why Kotlin Needs `kotlin("plugin.spring")` & `kotlin("plugin.jpa")`

Per Official Spring Kotlin Docs: Java classes are non-final by default so CGLIB proxies (`@Transactional`, `@Configuration`, `@Service`) subclass them freely. Kotlin classes are `final` by default—so add `kotlin("plugin.spring")` (`allopen`) to open Spring-annotated beans and `kotlin("plugin.jpa")` (`noarg`) to generate Hibernate's hidden no-arg constructor!

2. `record` vs. `data class` vs. JPA `@Entity`

  • DTOs / Commands / Events: Java `record` ↔ Kotlin `data class` (or `@JvmInline value class` for typed IDs!).
  • JPA `@Entity`: NEVER use Java `record` OR Kotlin `data class`! `data class` generates `equals`/`hashCode`/`toString` over all mutable fields (causing `StackOverflowError` on bidirectional `@OneToMany` and broken `Set` membership before DB persist assigns `@Id`)! Use a regular `class` with ID-based equality.
