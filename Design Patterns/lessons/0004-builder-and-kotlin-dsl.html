Builder Pattern & Kotlin Type-Safe DSLs

In Java, every object with 6 optional fields needed a 70-line Builder class. In Kotlin, default & named arguments replace basic Builders—so when do 2027 Senior Android Engineers still build Builders and DSLs?

Creational @DslMarker Immutable Specs Java SDK Interop

1. Named Arguments vs. Classic Builder

For a simple flat data class, use Kotlin default arguments. Reach for a Builder when: 1) Construction requires multi-step accumulation (adding line items, headers, or compliance tags sequentially), 2) Cross-field validation must run before producing an immutable object, or 3) You ship a public Android SDK consumed by Java callers (like PayVaultRequest.Builder, similar to OkHttp's Request.Builder).

2. Kotlin Type-Safe DSLs with @DslMarker

Kotlin — PayVault TransferIntent DSL
@DslMarker annotation class PayVaultDsl

@PayVaultDsl class TransferSpecBuilder {
    var amountCents: Long = 0
    var recipientId: String = ""
    private val tags = mutableListOf<String>()
    fun tag(name: String) { tags += name }
    fun build(): TransferSpec {
        require(amountCents > 0 && recipientId.isNotBlank())
        return TransferSpec(amountCents, recipientId, tags.toList())
    }
}
fun transferSpec(block: TransferSpecBuilder.() -> Unit) =
    TransferSpecBuilder().apply(block).build()

5. 2027 Senior Android Interview Corner

Q1: "Why does Jetpack Compose / Navigation use `@DslMarker` on builder scopes?"
Senior Answer: Without `@DslMarker`, nested lambda receivers (`navGraph { screen { ... } }`) allow calling outer-scope methods inside inner blocks by accident (scope leakage). `@DslMarker` restricts implicit `this` to the innermost receiver, catching nesting bugs at compile time.
