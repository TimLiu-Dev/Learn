Lesson 0026 • Part 2: Architecture & Modularity

Hexagonal Architecture (Ports & Adapters) & Spring Modulith

In a typical junior Spring Boot app, `@Service` classes import JPA `@Entity` objects, Jackson annotations, and Kafka templates directly—turning business rules into an untestable framework soup. Hexagonal Architecture keeps your PayVault Domain Core 100% framework-free, while Spring Modulith verifies module boundaries automatically in unit tests!

HexagonalPorts & AdaptersSpring ModulithZero-Spring Domain

1. Inbound Ports (Use Cases) & Outbound Ports (SPI)

  • Inbound Port (`SendTransferUseCase`): What the REST Controller or Kafka Consumer calls.
  • Domain Core: Pure Java classes/records (`Money`, `Wallet`, `FeePolicy`) with zero `@Entity` or Spring imports.
  • Outbound Port (`LoadWalletPort`, `SaveLedgerPort`): Interfaces owned by Domain, implemented by Adapters (`JpaWalletAdapter`, `StripeBankAdapter`).

2. Spring Modulith: Modular Monolith Before Microservices

Per Spring Boot / Spring Modulith docs, `ApplicationModules.of(PayVaultApp.class).verify()` fails CI if the `notifications` module reaches directly into `ledger.internal.*` JPA repositories instead of listening to published domain events!

5. 2027 Senior Backend Interview Corner

Q1: "Why start with a Spring Modulith modular monolith instead of splitting into 8 microservices on Day 1?"
Senior Answer: Microservices pay immediate distributed-systems taxes (network latency, partial failures, distributed tracing, deployment orchestration). A Spring Modulith gives you strong package encapsulation, event-driven module decoupling, and `@ApplicationModuleTest` isolation in one deployable—and lets you extract a hot module into a microservice later cleanly because boundaries already exist.
