Proxy Pattern: Lazy Init, Security Gates & Remote Stubs

In Fintech, transfers above \$500 must trigger a BiometricPrompt gate, and heavy PDF/Crypto engines shouldn't initialize on app cold-start (ruining Android TTID metrics). A Proxy stands in place of the real object to control access, lifecycle, or location.

StructuralBiometric GateLazy Cold-StartAIDL / Retrofit

1. The 3 Flavors of Proxy in 2027 Android

  • Protection Proxy: Checks authorization/biometrics before forwarding to the real vault (BiometricVaultProxy).
  • Virtual (Lazy) Proxy: Defers instantiating an expensive PDF renderer or ML fraud model until the first actual call (like Kotlin's by lazy).
  • Remote Proxy: Local Kotlin interface representing an RPC/REST/AIDL endpoint (what Retrofit's create(PayApi::class.java) generates!).

2. Proxy vs. Decorator (Favorite Interview Question)

Structurally they look almost identical—both wrap an object with the same interface. The difference is intent & ownership: a Decorator lets the caller stack extra behaviors dynamically; a Proxy controls access or lazy creation of a specific subject (often managing its lifecycle or blocking calls).

5. 2027 Senior Android Interview Corner

Q1: "How does a Virtual Proxy improve Android Cold Start (TTID)?"
Senior Answer: Heavy SDKs (analytics, ML fraud models, crypto keystores) initialized eagerly inside `Application.onCreate()` inflate cold-start latency. Wrapping them in a Virtual Proxy defers heavy disk/classloader initialization until the first feature actually invokes a method.
