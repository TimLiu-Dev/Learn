Part 01 · First Principles

Why "Happened Earlier in Time" ≠ "Visible to Another Core"

Most engineers picture shared memory as one blackboard that every OS Thread reads and writes directly. In reality, reading Main RAM costs ~100ns (~300 CPU cycles), so modern CPUs sit behind private caches, Store Buffers, and Invalidation Queues—while compilers and CPUs reorder independent instructions. The JSR-133 Java Memory Model (JMM) defines the exact contract that bridges this hardware gap.

1. Store Buffers & Stale L1 Caches

When Core 0 writes a non-volatile field stop = true, it does not stall waiting for other cores to invalidate their L1 caches. Instead, Core 0 pushes the write into its private Store Buffer and continues executing immediately.

Meanwhile, Core 1 keeps reading stop = false from its own L1 cache (or the JIT hoists !stop into a CPU register), creating an infinite loop even seconds after Core 0 wrote true.

2. Instruction Reordering & Store-Load

Compilers, the JVM JIT, and out-of-order CPU pipelines may reorder operations that have no single-thread data dependency.

On x86/ARM hardware, a core can execute a later LOAD (reading from L1) while its earlier STORE is still sitting in its Store Buffer—producing outcomes like (r1 = 0, r2 = 0) that are impossible under any simple interleaving of lines of code.

JMM Happens-Before Edges & Memory Synchronization Primitives

Mechanism Hardware Effect Visibility Guarantee Atomicity?
Plain var (No Sync) Writes sit in Store Buffer; reads use L1/register; JIT may hoist None across OS Threads (stale reads & reordering allowed) No (64-bit word tearing also possible on 32-bit JVMs without @Volatile)
@Volatile Read / Write Release fence drains Store Buffer; Acquire fence invalidates stale L1 Happens-before edge from volatile write to subsequent volatile read (transitive!) Single read/write only — NOT compound x++
Mutex / synchronized Acquire barrier on lock entry; Release barrier + Store Buffer flush on unlock Unlock happens-before every subsequent lock of the same monitor Yes (Mutual Exclusion over entire critical section)
val (JVM final) Store-Store freeze fence at end of constructor before reference escapes Safe Publication: any thread seeing the object observes frozen val fields Immutable post-construction (provided this never leaked in init)
Thread.start() / join() Memory barrier across thread spawn and termination handoff Pre-start() writes visible to new thread; thread writes visible after join() Only at the spawn / join boundary
Happens-Before Transitivity (Piggybacking): Per JSR-133, if Thread A writes plain fields payload = 42; config = "prod" and then writes @Volatile ready = true, any Thread B that reads ready == true is guaranteed to observe payload == 42 and config == "prod" too—because program order + volatile write→read compose transitively!

Part 03 · Production Kotlin & Android

Junior Traps vs. Senior Patterns in Kotlin

These three visibility and reordering bugs pass unit tests on your laptop and fail silently on multi-core ARM Android devices.

Pattern 1: Stop-Flag Infinite Loop Without @Volatile

✗ JUNIOR TRAP: Plain Boolean Hoisted / Stale L1
class Worker {
    private var stopped = false // No happens-before!

    fun start() = Thread {
        // JIT may hoist !stopped -> if (!stopped) while (true)
        while (!stopped) { processNextBatch() }
    }.start()

    fun stop() { stopped = true } // May never become visible
}
✓ SENIOR PATTERN: @Volatile / AtomicBoolean
class Worker {
    @Volatile
    private var stopped = false // Release on write, Acquire on read

    fun start() = Thread {
        while (!stopped) { processNextBatch() }
    }.start()

    fun stop() { stopped = true } // Drains Store Buffer -> visible
}

Pattern 2: Unsafe Publication of Mutable Fields vs. Immutable val

✗ JUNIOR TRAP: Publishing Non-Final Fields
class EndpointConfig {
    var baseUrl: String = "" // Mutable, NOT final!
    var timeoutMs: Int = 0
}
var activeConfig: EndpointConfig? = null

// Writer on IO thread:
val cfg = EndpointConfig()
cfg.baseUrl = "https://api.prod"
cfg.timeoutMs = 5000
activeConfig = cfg // Reader can see baseUrl == "" / timeoutMs == 0!
✓ SENIOR PATTERN: Immutable val + Safe Publication
data class EndpointConfig(
    val baseUrl: String, // JVM final: frozen before ctor returns
    val timeoutMs: Int
)
@Volatile var activeConfig: EndpointConfig? = null

// Writer on IO thread:
activeConfig = EndpointConfig("https://api.prod", 5000)
// Any reader observing non-null activeConfig sees frozen vals

Pattern 3: Double-Checked Locking (DCL) Missing @Volatile

✗ JUNIOR TRAP: DCL Without @Volatile
class AnalyticsClient private constructor() {
    private val queue = ArrayDeque<Event>()
    companion object {
        private var instance: AnalyticsClient? = null // BUG!
        fun get(): AnalyticsClient {
            return instance ?: synchronized(this) {
                // Reordering can publish non-null ref BEFORE queue init!
                instance ?: AnalyticsClient().also { instance = it }
            }
        }
    }
}
✓ SENIOR PATTERN: @Volatile DCL (or Kotlin lazy)
class AnalyticsClient private constructor() {
    private val queue = ArrayDeque<Event>()
    companion object {
        @Volatile private var instance: AnalyticsClient? = null
        fun get(): AnalyticsClient {
            return instance ?: synchronized(this) {
                instance ?: AnalyticsClient().also { instance = it }
            }
        }
        // Or idiomatic Kotlin: val instance by lazy { AnalyticsClient() }
    }
}
