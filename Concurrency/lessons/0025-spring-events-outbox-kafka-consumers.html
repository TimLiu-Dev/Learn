@TransactionalEventListener, Outbox Pattern & Spring Kafka Concurrency

Raw @EventListener executes synchronously before your JDBC transaction commits—emitting ghost events to downstream services whenever an exception rolls back the database. Part 01 · First-Principles Mental Model

Transaction Timing, Dual Writes & Partition-Bounded Scaling

Database ACID commits and message-broker sends happen across two separate systems without two-phase commit (2PC). Spring's Transaction-bound Events and Spring for Apache Kafka give you the building blocks—only if you respect commit phases, crash windows, and partition ownership.

1. Why @EventListener Emits Ghost Events

ApplicationEventPublisher.publishEvent() dispatches synchronously on the calling thread by default.

Inside @Transactional, a raw @EventListener runs while the DB transaction is still uncommitted. If a later check throws or Hibernate fails on flush/constraint at commit, the DB rolls back—while billing, email, or Kafka already acted on a ghost order.

@TransactionalEventListener(phase = AFTER_COMMIT) registers a TransactionSynchronization hook so the listener only fires after COMMIT succeeds.

2. Outbox Reliability & Kafka Partition Bounds

Even with AFTER_COMMIT, calling kafkaTemplate.send() after DB commit is a dual write: a pod crash or broker outage between DB commit and Kafka ack silently loses the event.

The Transactional Outbox Pattern writes the domain row and outbox_events row in the same local ACID transaction, then relays asynchronously.

On the consumer side, Kafka assigns at most one consumer thread per partition in a group. Setting concurrency > partitionCount leaves extra threads idle, while keyed routing (hash(key) % P) preserves per-entity ordering.

[TRAP 1: @EventListener] BEGIN TX ─► INSERT order ─► publishEvent() ─► Kafka/Billing CHARGED! ─► ROLLBACK! (Ghost Order!) [TRAP 2: AFTER_COMMIT] BEGIN TX ─► INSERT order ─► COMMIT ✓ ─► [JVM CRASH / Kafka down!] ─► Event LOST forever! [SENIOR: Outbox + Kafka] BEGIN TX ─► INSERT order + INSERT outbox_events ─► COMMIT ✓ (Atomic!) └─► Outbox Relay (SKIP LOCKED / CDC) ─► Kafka key=orderId (P0..P3) └─► @KafkaListener(concurrency="4") + Idempotent eventId dedup ─► ACK ✓

Event Publishing & Consumption Guarantees

Mechanism Commit Timing Crash / Rollback Safety Concurrency & Ordering Rule
Raw @EventListener Pre-commit (inline in caller TX) Fires even if TX later rolls back (ghost events). Synchronous on caller thread; unsafe for external side effects.
@TransactionalEventListener(AFTER_COMMIT) Post-commit (TransactionSynchronization) Never fires on rollback; still loses events on post-commit crash. Follow-up DB writes need Propagation.REQUIRES_NEW to commit.
Transactional Outbox + Relay / CDC Persisted atomically inside domain TX Zero ghost events AND zero lost events across crashes. Relay uses FOR UPDATE SKIP LOCKED or Debezium WAL tailing.
@KafkaListener(concurrency = "N") At-least-once broker delivery Rebalances & un-acked crashes redeliver records. N <= partitions; key with orderId; deduplicate eventId in DB TX.
The AFTER_COMMIT + REQUIRES_NEW Trap: When an AFTER_COMMIT listener executes, the original JDBC transaction has already committed. Calling a repository method with default Propagation.REQUIRED joins a completed synchronization lifecycle and fails to commit new writes! You must annotate follow-up DB writes with @Transactional(propagation = Propagation.REQUIRES_NEW)—or write to an Outbox table before commit instead.

Part 03 · Production Java 21–25+ & Spring Boot

Junior Traps vs. Senior Patterns in Spring Boot

Eliminate pre-commit ghost events, close dual-write crash windows with an atomic Outbox table, and scale Kafka consumers safely within partition limits.

Pattern 1: @EventListener Pre-Commit vs. @TransactionalEventListener(AFTER_COMMIT) + REQUIRES_NEW

✗ JUNIOR TRAP: Pre-Commit @EventListener & Missing REQUIRES_NEW
@Component
public class OrderEventTrap {
    // BUG 1: Fires BEFORE DB commit! If reserveInventory() throws,
    // email/Kafka already ran for a rolled-back ghost order.
    @EventListener
    public void onCreated(OrderCreatedEvent ev) {
        kafkaTemplate.send("orders", ev.orderId(), ev);
    }

    // BUG 2: Writing to DB inside AFTER_COMMIT with default REQUIRED
    // never commits because the outer TX already committed!
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    @Transactional // Missing propagation = REQUIRES_NEW!
    public void saveAuditBroken(OrderCreatedEvent ev) {
        auditRepo.save(AuditLog.forOrder(ev.orderId()));
    }
}
✓ SENIOR PATTERN: AFTER_COMMIT + REQUIRES_NEW
@Component
public class OrderAuditListener {
    // Fires ONLY after outer JDBC transaction commits cleanly.
    // Opens a brand-new transaction for follow-up persistence.
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void recordAudit(OrderCreatedEvent ev) {
        auditRepo.save(AuditLog.forOrder(ev.orderId()));
    }

    // Optional compensation hook when outer TX rolls back:
    @TransactionalEventListener(phase = TransactionPhase.AFTER_ROLLBACK)
    public void onOrderFailed(OrderCreatedEvent ev) {
        metrics.counter("orders.rolled_back").increment();
    }
}

Pattern 2: Dual-Write Failure vs. Atomic Transactional Outbox

✗ JUNIOR TRAP: Dual Write (DB Commit + Kafka Send)
@Service
public class CheckoutService {
    @Transactional
    public Order placeOrder(OrderCmd cmd) {
        var order = orderRepo.save(Order.from(cmd));
        // Even with AFTER_COMMIT, a pod crash or broker blip
        // right after DB commit silently loses this Kafka event!
        publisher.publishEvent(new OrderCreatedEvent(order.id()));
        return order;
    }
}
✓ SENIOR PATTERN: Same-TX Outbox + SKIP LOCKED Relay
@Service
public class CheckoutService {
    @Transactional
    public Order placeOrder(OrderCmd cmd) {
        var order = orderRepo.save(Order.from(cmd));
        // Persisted in the EXACT SAME ACID commit as orders!
        outboxRepo.save(OutboxEvent.pending(
            order.id().toString(), "OrderCreated", json(order)
        ));
        return order;
    }
}
// Relay worker claims rows with FOR UPDATE SKIP LOCKED (or CDC),
// sends to Kafka with key = aggregateId, and marks status = SENT.

Pattern 3: @KafkaListener(concurrency) Partition Ordering & Idempotent Deduplication

✗ JUNIOR TRAP: Over-Provisioned Threads & Unkeyed Non-Idempotent Reads
// BUG 1: Topic has 4 partitions -> 4 of 8 threads sit idle!
// BUG 2: Producer sent null key -> events for order-42 race!
// BUG 3: Rebalance redelivery charges customer twice!
@KafkaListener(topics = "orders.events", concurrency = "8")
public void onEvent(OrderEvent ev) {
    ledgerService.debit(ev.accountId(), ev.amountCents());
}
✓ SENIOR PATTERN: concurrency <= Partitions + Same-TX Dedup
// Producer: kafkaTemplate.send("orders.events", ev.orderId(), ev);
@KafkaListener(topics = "orders.events", concurrency = "4")
public void onEvent(OrderEvent ev, Acknowledgment ack) {
    txTemplate.executeWithoutResult(status -> {
        // Unique constraint on processed_events(event_id)
        int inserted = dedupRepo.insertIgnore(ev.eventId());
        if (inserted == 0) return; // Safe duplicate skip!
        ledgerService.debit(ev.accountId(), ev.amountCents());
    });
    ack.acknowledge(); // AckMode.MANUAL_IMMEDIATE AFTER DB commit!
}

LAB 25.1 · TRANSACTIONAL EVENT BUS

@EventListener vs. @TransactionalEventListener(AFTER_COMMIT)

Implement TransactionalEventBus supporting 'IMMEDIATE' and 'AFTER_COMMIT' phase hooks so rolled-back transactions never leak ghost events.

Not Run
• subscribe(phase, handler) registers callbacks for 'IMMEDIATE' or 'AFTER_COMMIT'.
• publish(event) fires 'IMMEDIATE' handlers right away, but buffers 'AFTER_COMMIT' delivery until commit() if inside an active transaction (if outside a transaction, 'AFTER_COMMIT' does not fire).
• commit() exits the transaction state before firing queued 'AFTER_COMMIT' handlers (enabling REQUIRES_NEW transactions inside listeners); rollback() discards queued events without firing 'AFTER_COMMIT'.

LAB 25.2 · KAFKA PARTITION CONCURRENCY

Partition Key Routing & Consumer Group Assignment

Implement KafkaPartitionAssigner(numPartitions, hashFn) so keyed events preserve FIFO order per partition, distinct partitions run in parallel, and extra consumers sit idle.

Not Run
• partitionFor(key): return deterministic Math.abs(hashFn(String(key))) % numPartitions.
• assignPartitions(consumerIds): map every consumer ID to an array of assigned partitions so each partition 0..numPartitions-1 belongs to exactly one consumer (round-robin consumerIds[p % consumerIds.length]); extra consumers get [].
• async consumeBatch(records, consumerIds, handler): group records by partition preserving FIFO order, run active consumers concurrently via Promise.all where each consumer drains its assigned partitions sequentially, and return { assignment, idleConsumers, processedCount }.

LAB 25.3 · IDEMPOTENT KAFKA CONSUMER

Atomic eventId Deduplication Under At-Least-Once Delivery

Implement IdempotentKafkaConsumer(store, handler) so redeliveries skip safely and transient failures roll back cleanly for retry.

Not Run
Store API: await store.runInTx(async (tx) => { ... }) provides await tx.hasProcessed(eventId), await tx.markProcessed(eventId), await tx.getState(k), and await tx.setState(k, v).
• Wrap duplicate check, await handler(record, tx), and await tx.markProcessed(record.eventId) inside the same store.runInTx.
• Return { status: 'DUPLICATE_SKIPPED', eventId } if already processed; otherwise return { status: 'PROCESSED', eventId }.
