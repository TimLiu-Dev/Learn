Part 01 · First Principles

Synchronization Primitives, Deadlocks & Lock-Free Hardware

Mutual Exclusion guarantees that at most one OS thread or coroutine holds a lock and executes a critical section at any instant. Choosing the wrong primitive—or acquiring two locks in inconsistent order—turns a race condition into a permanent freeze (JSR-133 JMM Spec; Kotlin Shared Mutable State Guide).

Lock-Based Mutual Exclusion

1. Intrinsic Monitors (synchronized): Every JVM object has a built-in monitor lock. Reentrant per OS thread, automatically released on exit/exception, and establishes a happens-before edge on unlock → lock (JSR-133). Hazard: blocks the underlying OS thread and pins Java 21+ virtual threads (JEP 444).

2. ReentrantLock: Explicit JVM lock supporting tryLock(timeout), interruptible acquisition, and optional fair FIFO queuing—still blocks OS threads.

3. Coroutine Mutex: Cooperative suspending lock (mutex.withLock { ... }). Parks only the coroutine Continuation without blocking the carrier OS thread, but is strictly non-reentrant!

Deadlocks, Priority Inversion & CAS

Coffman's 4 Deadlock Conditions (all 4 must hold simultaneously):
1. Mutual Exclusion — resource cannot be shared concurrently.
2. Hold and Wait — holder keeps one lock while waiting for another.
3. No Preemption — locks cannot be forcibly revoked.
4. Circular Wait — closed cycle T1 → T2 → ... → T1.

Priority Inversion: A high-priority thread (e.g., UI/audio) blocks waiting on a lock held by a low-priority thread that gets preempted by medium-priority CPU work. Solved via Priority Inheritance or lock-free state.

Lock-Free CAS (AtomicInteger): Uses CPU instructions (LOCK CMPXCHG / LDREX-STREX) to atomically swap expected → next in a retry loop—immune to deadlocks, though exposed to the ABA problem if values recycle A → B → A.

Synchronization Primitives Comparison

Primitive Wait Behavior Reentrancy Deadlock / Pinning Risk Best Production Use Case
synchronized Blocks OS thread Reentrant (same thread) Circular wait; pins virtual threads (JEP 444); forbids suspend Tiny in-memory invariants with zero I/O or suspend calls
ReentrantLock Blocks OS thread (supports tryLock) Reentrant (hold count) Manual unlock() leak if omitted from finally Thread-pool code needing timed tryLock, interruptibility, or conditions
Coroutine Mutex Suspends coroutine (frees thread) Non-reentrant! Self-deadlocks if same coroutine calls withLock nested Multi-step critical sections containing suspend calls
Atomic* (CAS) Non-blocking retry loop N/A (lock-free) Zero deadlock; vulnerable to ABA without version stamp Counters, flags, StateFlow.update, single-reference state
The ABA Trap in Lock-Free Code: Suppose Thread 1 reads node head A and gets preempted before calling compareAndSet(A, next). Thread 2 pops A, pops B, frees/reuses memory, and pushes A back as the head. When Thread 1 resumes, CAS(A, next) sees address A still matches and succeeds—even though the list structure changed underneath! Fix ABA with a monotonic version stamp (AtomicStampedReference or packed Long tag + pointer).

Part 03 · Production Kotlin & Android

Junior Traps vs. Senior Patterns in Kotlin

Apply the Kotlin Shared Mutable State Guide to avoid compiler rejections, carrier thread starvation, and self-deadlocks.

Pattern 1: Calling suspend Inside synchronized {} vs. Mutex.withLock

✗ JUNIOR TRAP: Blocking Monitor / Compiler Error
private val lock = Any()

suspend fun fetchAndCache(id: String): User {
    synchronized(lock) {
        // 1. Compiler forbids suspend calls directly inside synchronized!
        // 2. Wrapping runBlocking {} inside synchronized parks the OS thread
        //    AND causes deadlocks / Virtual Thread pinning under load.
        return runBlocking { api.fetchUser(id) }
    }
}
✓ SENIOR PATTERN: Cooperative Mutex.withLock
private val mutex = Mutex()

suspend fun fetchAndCache(id: String): User = mutex.withLock {
    // Suspends the coroutine Continuation cleanly while api.fetchUser runs;
    // the underlying Dispatcher OS thread stays free for other coroutines!
    cache[id] ?: api.fetchUser(id).also { cache[id] = it }
}

Pattern 2: Non-Reentrant Coroutine Mutex Self-Deadlock Trap

✗ JUNIOR TRAP: Nested Mutex.withLock Self-Deadlock
private val mutex = Mutex()

suspend fun updateProfile(user: User) = mutex.withLock {
    saveUser(user) // Holds mutex, calls saveUser()...
}

suspend fun saveUser(user: User) = mutex.withLock {
    // HANGS FOREVER! Coroutine Mutex is NOT reentrant.
    // Waiting on itself never wakes up.
    db.upsert(user)
}
✓ SENIOR PATTERN: Private *Locked() Helper Separation
private val mutex = Mutex()

suspend fun updateProfile(user: User) = mutex.withLock {
    saveUserLocked(user) // Caller already holds mutex
}

suspend fun saveUser(user: User) = mutex.withLock {
    saveUserLocked(user)
}

private suspend fun saveUserLocked(user: User) {
    db.upsert(user) // Never re-acquires mutex
}

Pattern 3: Canonical Lock Ordering + Lock-Free AtomicInteger.update

✗ JUNIOR TRAP: Caller-Order Locking Deadlocks
fun transfer(from: Account, to: Account, amount: Long) {
    synchronized(from) {      // T1 locks A, T2 locks B
        synchronized(to) {    // T1 waits B, T2 waits A -> DEADLOCK!
            from.balance -= amount
            to.balance += amount
        }
    }
}
✓ SENIOR PATTERN: Canonical Order + CAS Update
fun transfer(from: Account, to: Account, amount: Long) {
    if (from.id == to.id) return
    val (first, second) = if (from.id < to.id) from to to else to to from
    synchronized(first) {
        synchronized(second) {
            from.balance -= amount
            to.balance += amount
        }
    }
}
// For single-value transitions, skip locks entirely with CAS:
val nextSeq = seqCounter.updateAndGet { cur -> cur + 1 }
