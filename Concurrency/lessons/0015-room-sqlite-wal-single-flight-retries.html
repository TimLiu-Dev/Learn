Part 01 · First Principles

Database Contention, Coalescing & Jittered Recovery

Most mobile engineers treat SQLite as a multi-writer server and HTTP retries as harmless loops. Senior engineers model file-level lock contention (SQLite WAL Specification), Room's single-writer transaction discipline (Android Room Guide), and distributed retry amplification (AWS Exponential Backoff & Jitter).

1. SQLite WAL: N Readers + 1 Writer

In legacy Rollback Journal mode, writers acquire an EXCLUSIVE lock on the database file and stall every reader; readers hold SHARED locks and stall writers.

With Write-Ahead Logging (WAL) (Room's default on API 16+), writes append committed pages to -wal instead of mutating the main database file in place. Readers resolve a snapshot mark via the -shm index, so multiple readers run concurrently alongside one writer. However, SQLite still allows only one active writer at a time—a second concurrent writer hits SQLITE_BUSY once busy_timeout expires.

2. Room withTransaction & Deadlock Hazards

Room's withTransaction { ... } acquires a dedicated transaction thread/connection and stores a TransactionElement in the coroutine's CoroutineContext (Kotlin Coroutines Guide).

The trap: Switching to an unrelated dispatcher (withContext(Dispatchers.IO)) or launching a blocking runBlocking DAO query onto another thread while holding the single write connection causes self-deadlock: the inner query waits for the write connection already held by the outer transaction! Mixing a coroutine Mutex with withTransaction in inconsistent lock order produces classic AB-BA deadlocks.

3. Single-Flight Request Deduplication

During screen rotation, feed scrolling, or cold start, multiple view models or Flow collectors often request the same resource (GET /users/42) at the exact same millisecond.

A single-flight cache maps each active key to one shared in-flight Deferred. Concurrent callers await the same network call instead of issuing N redundant requests. Crucially, the key must be evicted in a finally block on both success and failure—otherwise one transient timeout permanently poisons future callers with a failed Deferred.

4. Full Jitter + Idempotency Keys

Deterministic exponential backoff (base * 2^attempt) fails under correlated outages: clients that failed together at t = 0 wake up together in synchronized waves at 100ms, 200ms, and 400ms (a thundering herd).

Full Jitter draws random(0, min(cap, base * 2^attempt)) to spread retries smoothly across the window. For state-mutating endpoints (POST /payments), attach a single UUID Idempotency-Key generated before the retry loop so the server deduplicates retries if an earlier response was lost in transit.

Part 03 · Production Kotlin & Android

Junior Traps vs. Senior Patterns in Room & Networking

Production Android repositories combine Room transactions, in-memory request coalescing, and resilient HTTP retries. Compare the common failure traps against hardened senior implementations.

Pattern 1: Single-Flight Request Deduplication (With Error Cleanup)

✗ JUNIOR TRAP: Races or Caches Failed Deferred
private val cache = ConcurrentHashMap<String, Deferred<User>>()

suspend fun getUser(id: String): User = coroutineScope {
    // Trap A: check-then-put races two callers!
    // Trap B: failed Deferred stays in map forever!
    cache[id]?.await() ?: async { api.fetchUser(id) }
        .also { cache[id] = it }
        .await()
}
✓ SENIOR PATTERN: Atomic Map + finally Eviction
private val mutex = Mutex()
private val inFlight = HashMap<String, Deferred<User>>()

suspend fun getUser(id: String): User = coroutineScope {
    val (deferred, isOwner) = mutex.withLock {
        inFlight[id]?.let { it to false } ?: async {
            try { api.fetchUser(id) } finally {
                mutex.withLock { inFlight.remove(id) }
            }
        }.let { inFlight[id] = it; it to true }
    }
    deferred.await()
}

Pattern 2: Room withTransaction & Dispatcher/Mutex Deadlock Avoidance

✗ JUNIOR TRAP: Dispatcher Hop / Lock Inversion
suspend fun syncOrder(order: Order) {
    // Trap A: External mutex acquired BEFORE transaction,
    // while another path calls withTransaction then mutex -> AB-BA deadlock!
    syncMutex.withLock {
        db.withTransaction {
            // Trap B: Hopping out of transaction context or calling
            // runBlocking { dao.insert(...) } deadlocks the 1 write slot!
            withContext(Dispatchers.IO) { blockingLegacyWrite(order) }
        }
    }
}
✓ SENIOR PATTERN: Network Outside, Pure Suspend Inside
suspend fun syncOrder(orderId: String) {
    // 1. Perform network I/O outside SQLite locks
    val remote = api.fetchOrder(orderId)

    // 2. Keep transaction short, single-context, no external Mutex inversion
    db.withTransaction {
        orderDao.upsert(remote.toEntity())
        auditDao.recordSync(orderId, clock.now())
    }
}

Pattern 3: Exponential Backoff with Full Jitter + Idempotency-Key

✗ JUNIOR TRAP: Lockstep Retries & Duplicate Charges
suspend fun submitPayment(req: PaymentReq): Receipt {
    repeat(3) { attempt ->
        try {
            // Missing Idempotency-Key -> timeout retry double-charges!
            return api.charge(req)
        } catch (e: Exception) { // Even retries 400 Bad Request!
            delay(200L * (1L shl attempt)) // Deterministic spike!
        }
    }
    return api.charge(req)
}
✓ SENIOR PATTERN: Full Jitter + One Key Per Operation
suspend fun submitPayment(req: PaymentReq): Receipt {
    val idempotencyKey = UUID.randomUUID().toString()
    var attempt = 0
    while (true) {
        try {
            return api.charge(idempotencyKey, req)
        } catch (e: HttpException) {
            if (e.code() in 400..499 && e.code() != 429) throw e
            if (attempt >= 3) throw e
            val cap = minOf(4_000L, 200L * (1L shl attempt++))
            delay(Random.nextLong(0L, cap + 1L)) // Full Jitter
        }
    }
}
