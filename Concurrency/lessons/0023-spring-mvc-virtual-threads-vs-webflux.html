Part 01 · First-Principles Mental Model

Why Netty Uses ~CPU-Core Threads — and How One .block() Destroys It

Spring WebFlux runs on Reactor Netty's non-blocking event loop, whereas Spring MVC with Java 21–25+ Virtual Threads runs imperative code on cheap mountable user-space threads (Spring WebFlux Reference, JEP 444).

Spring WebFlux (Reactor Netty Event Loop)

1 thread per CPU core (e.g. 4 or 8 reactor-http-nio-* threads). Each thread runs an OS epoll/kqueue selector loop handling hundreds of concurrent sockets via non-blocking callbacks.

Golden Rule: Never block an event-loop thread. Because one thread multiplexes hundreds of connections, a single 50ms JDBC call or .block() freezes every request pinned to that thread—causing cascading latency spikes and health-check timeouts.

Superpower: End-to-end Reactive Streams backpressure (Subscription.request(n)) lets a slow downstream consumer regulate a fast upstream producer without buffering gigabytes into heap.

Spring MVC + Virtual Threads (Java 21–25+)

One virtual thread per HTTP request (spring.threads.virtual.enabled=true). Virtual threads mount onto a small ForkJoinPool of ~CPU-core carrier threads.

Unmounting on I/O: When imperative code calls jdbcTemplate.query(...) or restClient.get(), the JVM parks the virtual thread's heap stack continuation and frees the carrier thread for another request. With JEP 491 (Java 24+), even synchronized blocks unmount cleanly.

New Bottleneck: You no longer run out of Tomcat threads—you saturate downstream pools (HikariCP, external APIs) unless bounded with Semaphores or Bulkheads.

2027 Senior Decision Matrix: Spring MVC + VT vs. Spring WebFlux

Dimension Spring MVC + Virtual Threads Spring WebFlux (Reactor Netty)
Thread / Execution Model Thread-per-request on lightweight JVM virtual threads; unmounts automatically on blocking JDK I/O. ~CPU-core event-loop threads; non-blocking Mono/Flux state machines + Schedulers.boundedElastic() for legacy blocking calls.
Database & Drivers Native JDBC, JPA/Hibernate, Flyway, Spring Data JPA work out of the box with readable stack traces. Requires R2DBC or non-blocking drivers; mixing JPA/JDBC forces boundedElastic thread-hopping.
Backpressure Semantics Implicit TCP / Servlet backpressure; bounded via Tomcat queue + Semaphore/Resilience4j Bulkheads. Explicit Reactive Streams request(n) pull demand across operators (limitRate, onBackpressureDrop/Latest/Buffer).
Failure / Debugging UX Linear stack traces, standard ThreadLocal / Java 25 ScopedValue, simple breakpoints. Async operator-assembly stack traces (needs Hooks.onOperatorDebug() or Reactor Context propagation).
2027 Senior Default Pick Default choice for CRUD APIs, JPA/JDBC microservices, and high-concurrency REST aggregation. Specialized choice for API gateways, SSE/WebSocket streaming fan-out, and reactive Kafka/R2DBC backpressure pipelines.
How Reactive Streams request(n) works: Unlike push-only callbacks that flood slow consumers until OutOfMemoryError, Reactive Streams (Project Reactor Reference) uses hybrid push-pull: downstream calls subscription.request(n) to grant credit, and upstream is strictly forbidden from calling onNext more than n times until new demand arrives.

Part 03 · Production Java & Spring Boot Patterns

Junior Traps vs. Senior Patterns (Java 21–25+ & Spring Boot)

Follow Spring Reactive Core Guidance and keep blocking calls off Netty event loops while enforcing explicit backpressure.

Pattern 1: Blocking JDBC / .block() on Netty vs. subscribeOn(boundedElastic())

✗ JUNIOR TRAP: Calling JDBC or .block() on Netty
@GetMapping("/orders/{id}")
public Mono<OrderDto> getOrder(@PathVariable String id) {
    // Runs on reactor-http-nio-*!
    Order entity = jdbcRepo.findById(id).orElseThrow();
    Profile p = webClient.get().uri("/p/" + id)
        .retrieve().bodyToMono(Profile.class)
        .block(); // IllegalStateException / stalls event loop!
    return Mono.just(OrderDto.of(entity, p));
}
✓ SENIOR PATTERN: Offload Source + Non-Blocking Zip
@GetMapping("/orders/{id}")
public Mono<OrderDto> getOrder(@PathVariable String id) {
    Mono<Order> dbMono = Mono.fromCallable(() ->
            jdbcRepo.findById(id).orElseThrow())
        .subscribeOn(Schedulers.boundedElastic());

    Mono<Profile> profileMono = webClient.get().uri("/p/" + id)
        .retrieve().bodyToMono(Profile.class);

    return Mono.zip(dbMono, profileMono, OrderDto::of);
}
subscribeOn vs. publishOn: subscribeOn dictates where the upstream source (Mono.fromCallable) executes regardless of chain position, while publishOn switches the thread for all downstream operators after it (e.g., .publishOn(Schedulers.parallel()).map(this::heavyCpu)).

Pattern 2: Unbounded Push vs. Reactive request(n) Backpressure

✗ JUNIOR TRAP: Unbounded Buffer / Ignored Demand
Flux<MetricEvent> hotStream = sensorSink.asFlux();
// Fast producer emits 100k events/sec; slow DB sinks 500/sec.
// Unbounded onBackpressureBuffer() grows heap until OOM!
hotStream
    .onBackpressureBuffer()
    .flatMap(ev -> slowDbWriter.save(ev), 1024)
    .subscribe();
✓ SENIOR PATTERN: Bounded Buffer / Drop / Latest + limitRate
hotStream
    .onBackpressureBuffer(
        1024,
        dropped -> metrics.increment("stream.dropped"),
        BufferOverflowStrategy.DROP_OLDEST // or onBackpressureLatest()
    )
    .limitRate(64) // requests 64 at a time, replenishing at 75%
    .concatMap(ev -> slowDbWriter.save(ev))
    .subscribe();

Pattern 3: Choosing Spring MVC + Virtual Threads Cleanly Over WebFlux

✗ JUNIOR TRAP: Forcing WebFlux Around JPA + ThreadLocal
// Unnecessary complexity: JPA is blocking, MDC breaks across hops,
// and developers accidentally call .block() in helper methods.
public Mono<Invoice> createInvoice(Req req) {
    return Mono.fromCallable(() -> jpaService.create(req))
        .subscribeOn(Schedulers.boundedElastic());
}
✓ SENIOR PATTERN: Spring MVC + Virtual Threads + Bulkhead
// application.properties: spring.threads.virtual.enabled=true
@RestController
public class InvoiceController {
    private final Semaphore downstreamCap = new Semaphore(64);

    @PostMapping("/invoices")
    public Invoice createInvoice(@RequestBody Req req) throws Exception {
        // Imperative JPA + RestClient unmounts virtual thread cleanly!
        downstreamCap.acquire();
        try { return jpaService.createAndNotify(req); }
        finally { downstreamCap.release(); }
    }
}

LAB 23.2 · REACTIVE STREAMS REQUEST(N)

Honor Pull-Based subscription.request(n) Demand

Implement createReactivePullStream(items) returning a Reactive Streams Publisher with subscribe(subscriber).

Not Run
• On subscribe(subscriber), invoke subscriber.onSubscribe({ request(n), cancel() }) without emitting any items yet.
• In request(n): if cancelled/completed, return; if !Number.isFinite(n) || n <= 0, cancel and call subscriber.onError(new Error('3.9: request(n) must be > 0')).
• Otherwise add n to demand and drain in a re-entrancy-safe loop: emit up to demand items via onNext(item), then call onComplete() once when all items are delivered (never emit after cancel()).

LAB 23.3 · BACKPRESSURE OVERFLOW STRATEGIES

Implement 'BUFFER', 'DROP', and 'LATEST' Overflow Adapters

Implement createBackpressureFluxAdapter(strategy, bufferCapacity) to handle fast hot producers when downstream demand === 0.

Not Run
• API: { subscribe(sub), emit(val), complete(), getStats() } where getStats() returns { delivered, dropped, buffered }.
• If demand > 0 and nothing is buffered, deliver directly via sub.onNext(val) (demand--).
• If demand === 0: 'BUFFER' queues up to bufferCapacity (if full, calls sub.onError(new Error('Buffer overflow'))); 'DROP' discards val and increments dropped; 'LATEST' retains only the newest value (incrementing dropped whenever an older buffered item is overwritten).
• On request(n), drain buffered/latest items up to demand; when complete() was called and no buffered items remain, call sub.onComplete() once.
