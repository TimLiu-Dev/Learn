Part 01 · First-Principles Mental Model

Stackful Virtual Threads vs. Stackless Coroutines & Resilience Primitives

Scaling to 100,000+ concurrent I/O operations requires decoupling logical tasks from kernel-scheduled OS Threads—either via JVM-managed stackful virtual threads (OpenJDK JEP 444: Virtual Threads) or compiler-generated stackless continuations (Kotlin Coroutines Guide). High concurrency then demands admission control and fault isolation so a slow dependency cannot cascade into a total outage.

Java 21+ Virtual Threads (Project Loom)

Stackful user-mode threads mounted on ForkJoinPool carrier OS threads.

Each virtual thread owns a dynamically resized heap-stored call stack chunk. When it hits a JDK blocking I/O operation (e.g., Socket.read(), Thread.sleep(), LockSupport.park()), the JVM unmounts the virtual thread's stack frames to the heap, freeing the carrier OS thread to run another virtual thread.

Pinning Hazard (Java 21): Entering a synchronized monitor block or a JNI native frame pins the virtual thread to its carrier OS thread, preventing unmounting during blocking I/O and starving the carrier pool!

Kotlin Coroutines (CPS State Machines)

Stackless cooperative computations compiled into Continuation objects.

The Kotlin compiler rewrites every suspend function into a finite state machine stored in a heap Continuation. Suspension is explicit in the type system: a coroutine only yields its dispatcher OS thread at suspend calls.

Structured Concurrency & Pinning: Kotlin prevents calling suspend functions inside synchronized at compile time. Using Mutex.withLock suspends cooperatively without pinning any carrier thread, and Job trees enforce cancellation propagation.

Traffic Shaping & Fault Isolation Primitives

Primitive Core Mechanism Failure Mode Prevented Key Production Invariant
Token Bucket Bucket holds up to capacity tokens; refills at steady refillPerSec Sustained overload while permitting bounded bursts Use monotonic clock (System.nanoTime()); never allow negative tokens
Sliding Window Tracks timestamps/weighted sub-windows over rolling interval W 2× boundary burst spike seen in naive Fixed Window counters Bounded memory via sub-bucket counters or pruned ring buffer
Bulkhead Partitions concurrency permits/pools per downstream service Slow Service B exhausting all threads/slots and starving Service A Independent semaphores per dependency; release permit in finally
Circuit Breaker State machine: CLOSED → OPEN → HALF_OPEN Cascading timeouts & retry storms against an already failing peer Fail fast when OPEN; cap concurrent probes (halfOpenMaxCalls)
Monotonic Clock Rule: Never compute token refill elapsed time or circuit-breaker cooldowns using wall-clock time (System.currentTimeMillis() or Date.now()). NTP clock adjustments can jump backwards or forwards, causing token starvation, negative durations, or premature circuit transitions. Always use a monotonic clock source (System.nanoTime() on JVM, TimeSource.Monotonic in Kotlin, performance.now() in browsers).

Part 03 · Production Kotlin & JVM Patterns

Junior Traps vs. Senior Patterns

Avoiding carrier-thread pinning in Loom, clock-drift bugs in Token Buckets, and thundering-herd probes in Circuit Breakers.

Pattern 1: Virtual Thread Pinning (synchronized) vs. ReentrantLock / Kotlin Mutex

✗ JUNIOR TRAP: synchronized + Blocking I/O
// Java 21 Virtual Thread Pool
synchronized (lock) {
    // Pins virtual thread to carrier OS thread!
    // All 8 carrier threads block on HTTP/DB I/O.
    String body = httpClient.send(req, BodyHandlers.ofString()).body();
    cache.put(key, body);
}
✓ SENIOR PATTERN: ReentrantLock or Kotlin Mutex
// Option A (Java 21 Loom): ReentrantLock unmounts cleanly
lock.lock();
try {
    String body = httpClient.send(req, BodyHandlers.ofString()).body();
    cache.put(key, body);
} finally { lock.unlock(); }

// Option B (Kotlin Coroutines): non-blocking Mutex
mutex.withLock { cache[key] = api.fetchSuspended(key) }

Pattern 2: Wall-Clock Rate Limiter vs. Monotonic Token Bucket

✗ JUNIOR TRAP: System.currentTimeMillis() + Unbounded Tokens
fun tryAcquire(): Boolean {
    val now = System.currentTimeMillis() // NTP can jump!
    val elapsedSec = (now - lastMs) / 1000.0
    tokens += elapsedSec * refillPerSec // Exceeds capacity!
    lastMs = now
    tokens -= 1.0 // Goes negative on rejection!
    return tokens >= 0.0
}
✓ SENIOR PATTERN: Monotonic Clock + Clamped Atomic/Locked Refill
private val lock = ReentrantLock()
fun tryAcquire(permits: Int = 1): Boolean = lock.withLock {
    val nowNs = System.nanoTime()
    val elapsedNs = (nowNs - lastNs).coerceAtLeast(0L)
    milliTokens = minOf(capacity * 1000L,
        milliTokens + (elapsedNs * refillPerSec) / 1_000_000L)
    lastNs = nowNs
    val cost = permits * 1000L
    if (milliTokens < cost) return false
    milliTokens -= cost
    return true
}

Pattern 3: Racy Circuit Breaker vs. Probe-Capped State Machine

✗ JUNIOR TRAP: Unsynchronized Check-Then-Act & Probe Herd
if (state == OPEN && elapsed >= resetMs) {
    state = HALF_OPEN // 1,000 threads see HALF_OPEN!
}
if (state == OPEN) throw OpenException()
// All 1,000 threads stampede the recovering backend!
return callBackend()
✓ SENIOR PATTERN: Guarded Transitions + halfOpenMaxCalls Cap
mutex.withLock {
    if (state == OPEN && nowMs() - openedAtMs >= resetTimeoutMs) {
        state = HALF_OPEN; halfOpenUsed = 0; halfOpenOk = 0
    }
    when (state) {
        OPEN -> throw CircuitOpenException()
        HALF_OPEN -> if (halfOpenUsed >= halfOpenMaxCalls)
            throw ProbeLimitException() else halfOpenUsed++
        CLOSED -> Unit
    }
}

LAB 17.2 · CIRCUIT BREAKER STATE MACHINE

CircuitBreaker

Implement class CircuitBreaker accepting { failureThreshold, resetTimeoutMs, halfOpenMaxCalls, nowMs } with getState() and async execute(fn).

Not Run
• CLOSED: tracks consecutive failures; any success resets failure count; reaching failureThreshold transitions to OPEN.
• OPEN: rejects calls immediately without invoking fn until nowMs() - openedAtMs >= resetTimeoutMs, then transitions to HALF_OPEN.
• HALF_OPEN: permits at most halfOpenMaxCalls concurrent/sequential probes (preventing a probe herd). If all succeed, transitions to CLOSED; any probe failure immediately trips back to OPEN.
