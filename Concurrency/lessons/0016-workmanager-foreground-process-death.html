Part 01 · First Principles

Designing for Crash-Recoverable Background Execution

Junior Android engineers assume an active coroutine inside viewModelScope or GlobalScope will run to completion. Senior engineers treat OS process death (Low Memory Killer SIGKILL), Doze Mode maintenance windows, and network drops as normal control-flow events—anchoring state in SQLite and scheduling deferrable work through Android Developers: WorkManager & CoroutineWorker.

In-Memory Scopes vs. Persistent WorkManager

Process death wipes all heap memory without running finally blocks.

When Android reclaims a backgrounded app via LMK SIGKILL, viewModelScope, GlobalScope, and in-memory Channel queues vanish instantly.

WorkManager writes each WorkRequest, input Data, backoff policy, and Constraints into its internal SQLite WorkDatabase and delegates wakeups to JobScheduler, surviving process kills and device reboots.

CoroutineWorker & Foreground Service Rules

CoroutineWorker.doWork() executes on Dispatchers.Default by default—NOT Dispatchers.IO.

Each worker gets ~10 minutes of execution budget unless promoted via setForeground(ForegroundInfo(...)) (or short expedited quotas via setExpedited()).

Since Android 14 (API 34), foreground services require an explicit foregroundServiceType (such as dataSync), and Android 15 (API 35) enforces a 6-hour rolling runtime cap on dataSync services (Foreground Service Types).

Part 03 · Production Kotlin & Android

Junior Traps vs. Senior Patterns in WorkManager

Follow Android Coroutines Best Practices and persistent worker contracts so mutations survive kills without duplicate side effects.

Pattern 1: Fire-and-Forget viewModelScope vs. Persistent Outbox + CoroutineWorker

✗ JUNIOR TRAP: In-Memory Upload Lost on LMK Kill
class CheckoutViewModel(private val api: OrderApi) : ViewModel() {
    fun submitOrder(order: Order) {
        viewModelScope.launch {
            // If user leaves screen or OS kills process mid-call,
            // coroutine dies silently; order is lost forever!
            api.postOrder(order)
        }
    }
}
✓ SENIOR PATTERN: Room Outbox + Constrained Worker
suspend fun enqueueOrder(order: Order) {
    outboxDao.insertPending(order.toOutboxEntity(idempotencyKey = uuid()))
    val req = OneTimeWorkRequestBuilder<OutboxSyncWorker>()
        .setConstraints(Constraints(requiredNetworkType = NetworkType.CONNECTED))
        .setBackoffCriteria(BackoffPolicy.EXPONENTIAL, 15, TimeUnit.SECONDS)
        .build()
    workManager.enqueueUniqueWork("outbox_sync", ExistingWorkPolicy.KEEP, req)
}

class OutboxSyncWorker(ctx: Context, params: WorkerParameters) : CoroutineWorker(ctx, params) {
    override suspend fun doWork(): Result = withContext(Dispatchers.IO) {
        outboxRepo.recoverStaleInFlightAndFlush() // Reuses stored idempotencyKey
    }
}

Pattern 2: ExistingWorkPolicy.KEEP vs. REPLACE vs. APPEND_OR_REPLACE

✗ JUNIOR TRAP: Blindly Using REPLACE for Sync
// Called from Pull-to-Refresh AND Push Notification simultaneously:
workManager.enqueueUniqueWork(
    "sync_inbox",
    ExistingWorkPolicy.REPLACE, // Cancels in-flight HTTP upload mid-mutation!
    syncRequest
)
// Worker #1 gets CancellationException AFTER server committed,
// Worker #2 starts from scratch and causes duplicate mutations.
✓ SENIOR PATTERN: Match Policy to State Semantics
// 1) KEEP: Ignore duplicate triggers while sync is ENQUEUED/RUNNING
workManager.enqueueUniqueWork("sync_inbox", ExistingWorkPolicy.KEEP, syncReq)

// 2) APPEND_OR_REPLACE: Chain next upload after active chain,
//    OR wipe a stuck FAILED chain cleanly without cancelling new work
workManager.enqueueUniqueWork(
    "upload_chain",
    ExistingWorkPolicy.APPEND_OR_REPLACE,
    nextChunkReq
)

Pattern 3: Distinguishing Result.success(), Result.retry() & Result.failure()

✗ JUNIOR TRAP: Catch-All Swallows Cancellation & Retries 4xx
override suspend fun doWork(): Result {
    return try {
        api.upload(inputData.getString("id")!!)
        Result.success()
    } catch (e: Exception) {
        // BUG 1: Swallows CancellationException when OS stops worker!
        // BUG 2: Retries permanent HTTP 400 Bad Request 20 times!
        Result.retry()
    }
}
✓ SENIOR PATTERN: Rethrow Cancellation, Classify HTTP Errors
override suspend fun doWork(): Result = withContext(Dispatchers.IO) {
    try {
        api.upload(idempotencyKey)
        Result.success()
    } catch (ce: CancellationException) {
        throw ce // Mandatory: cooperative cancellation for WorkManager stop/constraints!
    } catch (e: HttpException) {
        if (e.code() in 400..499 && e.code() != 429) Result.failure()
        else Result.retry() // 429 Too Many Requests / 5xx transient
    } catch (e: IOException) {
        Result.retry() // Network drop / Doze socket interruption
    }
}

LAB 16.1 · CRASH-RECOVERABLE OUTBOX WORKER

Implement DurableOutboxWorker (Stale Lease Recovery + Idempotency)

Recover stale IN_FLIGHT rows left behind by OS process death and flush PENDING mutations using persisted idempotency keys.

Not Run
• outboxStore.getRows() returns [{ id, payload, idempotencyKey, status, leaseExpiresAt, attempts }]; outboxStore.update(id, patch) patches a row.
• In async doWork(): first reset any stale 'IN_FLIGHT' row where leaseExpiresAt <= this.clock() back to { status: 'PENDING', leaseExpiresAt: null } (leave active non-stale leases untouched!).
• For each 'PENDING' row: claim { status: 'IN_FLIGHT', leaseExpiresAt: now + this.leaseMs, attempts: (row.attempts || 0) + 1 }, then call await this.apiClient.send(row.payload, row.idempotencyKey).
• On success mark 'SENT'; on error with err.permanent === true mark 'FAILED'; on transient error reset to 'PENDING' (leaseExpiresAt: null). Return 'RETRY' if any transient failure occurred, else 'FAILURE' if any permanent failure occurred, else 'SUCCESS'.

LAB 16.2 · EXISTING WORK POLICY

Implement WorkQueuePolicyManager (KEEP / REPLACE / APPEND)

Implement WorkManager's enqueueUniqueWork(name, policy, workItem) semantics over active vs. completed work items.

Not Run
• Work item states: 'ENQUEUED' | 'RUNNING' | 'SUCCEEDED' | 'FAILED' | 'CANCELLED'. Active items are 'ENQUEUED' or 'RUNNING'.
• 'KEEP': If any active item exists for name, do nothing and return 'KEPT'; otherwise enqueue { ...workItem, state: 'ENQUEUED' } and return 'ENQUEUED'.
• 'REPLACE': Mark all active items for name as 'CANCELLED', enqueue the new item, and return 'REPLACED'.
• 'APPEND': Keep existing items intact, append the new item to the queue, and return 'APPENDED'. Throw an Error on unknown policy.

LAB 16.3 · DOZE-RESILIENT CHUNK CHECKPOINTING

Implement ResumableChunkUploader (Byte-Offset Checkpoints)

Checkpoint acknowledged offsets after each chunk so resuming after Doze or a network drop skips already-uploaded chunks.

Not Run
• Read initial offset via this.checkpointStore.getOffset(fileId) || 0. Loop while offset < data.length.
• Send const chunk = data.slice(offset, Math.min(offset + this.chunkSize, data.length)) via await this.transport.uploadChunk(fileId, offset, chunk).
• Immediately persist const nextOffset = (res && typeof res.ackOffset === 'number') ? res.ackOffset : end; with this.checkpointStore.saveOffset(fileId, nextOffset).
• Catch errors: return { status: err.permanent ? 'FAILURE' : 'RETRY', finalOffset: offset, chunksSent, uploadedBytes }; on full completion return { status: 'SUCCESS', finalOffset: offset, chunksSent, uploadedBytes }.
