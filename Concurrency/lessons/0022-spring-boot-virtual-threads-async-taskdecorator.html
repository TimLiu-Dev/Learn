Part 01 · First Principles

What spring.threads.virtual.enabled=true Actually Changes

Turning on virtual threads in Spring Boot is a two-line property change, yet four separate runtime layers interact under the hood: auto-configured executors, Spring AOP proxies, ThreadLocal propagation, and exception routing (Spring Boot Task Execution Reference).

1. Auto-Configured Virtual Executors

With spring.threads.virtual.enabled=true (Spring Boot 3.2+ on Java 21+), Boot configures:

• Servlet container (Tomcat/Jetty): spawns one virtual thread per incoming HTTP request instead of blocking a fixed 200-thread platform pool.
• applicationTaskExecutor (@Async): switches from ThreadPoolTaskExecutor (pooled platform threads) to SimpleAsyncTaskExecutor with virtualThreads = true (one fresh virtual thread per task; never pooled).

Trap: Defining your own @Bean Executor taskExecutor() disables Boot's auto-configuration via @ConditionalOnMissingBean(Executor.class)!

2. AOP Proxy Boundary & Context Loss

@Async works through a Spring AOP proxy wrapped around your bean at startup. External callers hold the proxy reference, so AsyncExecutionInterceptor submits the method to the Executor.

• Self-invocation bypass: Inside the bean, this.sendEmailAsync() calls the raw target instance directly, skipping the proxy and running synchronously on the HTTP request thread.
• Context loss: Neither virtual threads nor platform pools copy SLF4J MDC or Spring SecurityContextHolder automatically. You must bridge them via a TaskDecorator that restores/clears in finally.

SimpleAsyncTaskExecutor (Virtual) vs. ThreadPoolTaskExecutor (Platform)

Dimension SimpleAsyncTaskExecutor (Virtual Enabled) ThreadPoolTaskExecutor (Default / Custom)
Thread Lifecycle Spawns a new lightweight virtual thread per task; never pools (JEP 444) Reuses bounded platform OS threads (corePoolSize, maxPoolSize, queueCapacity)
Blocking I/O Cost Unmounts from carrier OS thread during socket/JDBC wait (cheap) Parks the OS thread (~1 MB stack); pool saturates quickly on slow I/O
Concurrency Bounding Unbounded by default; apply setConcurrencyLimit(n) or Resilience4j Bulkhead / Semaphore Bounded by maxPoolSize + queue (can hit TaskRejectedException)
ThreadLocal / MDC Risk Starts empty on every new virtual thread (silent context loss; avoid heavyweight caches in ThreadLocal) Reused workers keep stale ThreadLocal values across tasks (context bleed if finally cleanup is omitted)

@Async Call Paths & Error Propagation Rules

Call Pattern & Return Type Who Executes It? Where Do Exceptions Go?
External call → @Async CompletableFuture<T> AOP proxy → applicationTaskExecutor worker Wrapped in failed future; caller observes via .join() / .get() / .exceptionally()
External call → @Async void AOP proxy → applicationTaskExecutor worker Swallowed by default unless AsyncConfigurer.getAsyncUncaughtExceptionHandler() handles it (Spring Async Docs)
Internal this.methodAsync() Caller thread synchronously (proxy bypassed!) Thrown straight into the caller's synchronous stack frame
Tomcat vs. Downstream Reality: Even when spring.threads.virtual.enabled=true lets Tomcat accept 10,000 concurrent requests on virtual threads, your database still has a finite HikariCP pool (e.g., maximum-pool-size=20) and downstream APIs have rate limits. Virtual threads prevent Tomcat thread starvation, not connection pool exhaustion.

Part 03 · Production Java 21–25+ & Spring Boot

Junior Traps vs. Senior Patterns in Spring Boot

Compare real production failure modes against clean Spring Boot 3.2+/4.x patterns built for virtual threads, observability, and error isolation.

Pattern 1: this.sendEmailAsync() Proxy Bypass vs. Collaborator Bean

✗ JUNIOR TRAP: Same-Bean Self-Invocation
@Service
public class OrderService {
  public Receipt placeOrder(OrderCmd cmd) {
    var order = saveOrder(cmd);
    // Bypasses Spring AOP proxy! Runs synchronously
    // on the Tomcat request thread and blocks HTTP!
    this.sendEmailAsync(order.id());
    return Receipt.from(order);
  }

  @Async
  public void sendEmailAsync(String orderId) {
    smtpClient.sendBlocking(orderId);
  }
}
✓ SENIOR PATTERN: Inject Collaborator Bean
@Service
public class OrderService {
  private final NotificationService notifications;

  public OrderService(NotificationService notifications) {
    this.notifications = notifications; // Spring AOP proxy
  }

  public Receipt placeOrder(OrderCmd cmd) {
    var order = saveOrder(cmd);
    // Crosses proxy boundary -> runs on virtual @Async thread
    notifications.sendEmailAsync(order.id());
    return Receipt.from(order);
  }
}

Pattern 2: Custom applicationTaskExecutor Accidentally Disabling Virtual Threads

✗ JUNIOR TRAP: Replacing Boot's Executor Bean
// application.properties has spring.threads.virtual.enabled=true
@Configuration
@EnableAsync
public class AsyncConfig {
  // Defining ANY Executor bean triggers
  // @ConditionalOnMissingBean(Executor.class) -> Boot's
  // virtual-thread SimpleAsyncTaskExecutor is disabled!
  @Bean
  public Executor applicationTaskExecutor() {
    var pool = new ThreadPoolTaskExecutor();
    pool.setCorePoolSize(8);
    pool.initialize();
    return pool; // Reverts @Async to platform threads!
  }
}
✓ SENIOR PATTERN: Keep Boot Auto-Config or Customize Builder
@Configuration
@EnableAsync
public class AsyncConfig {
  // Option A: Let Boot wire SimpleAsyncTaskExecutor and only
  // register a TaskDecorator + SimpleAsyncTaskExecutorCustomizer:
  @Bean
  SimpleAsyncTaskExecutorCustomizer vtCustomizer() {
    return exec -> {
      exec.setVirtualThreads(true); // explicit safeguard
      exec.setConcurrencyLimit(250); // optional backpressure
    };
  }
  // Option B: If registering AsyncConfigurer, also wire
  // AsyncUncaughtExceptionHandler for void @Async methods!
}

Pattern 3: TaskDecorator Copying MDC & SecurityContext + finally Cleanup

✗ JUNIOR TRAP: InheritableThreadLocal or Missing Cleanup
@Bean
TaskDecorator brokenDecorator() {
  return runnable -> {
    // BUG 1: Captures MDC inside the lambda on the WORKER thread!
    // BUG 2: No try/finally -> leaks MDC & SecurityContext
    // onto pooled workers across unrelated user requests!
    return () -> {
      MDC.setContextMap(MDC.getCopyOfContextMap());
      runnable.run();
    };
  };
}
✓ SENIOR PATTERN: Capture on Caller, Restore in finally
@Bean
TaskDecorator contextPropagatingDecorator() {
  return runnable -> {
    Map<String, String> callerMdc = MDC.getCopyOfContextMap();
    SecurityContext callerSec = SecurityContextHolder.getContext();
    return () -> {
      Map<String, String> prevMdc = MDC.getCopyOfContextMap();
      SecurityContext prevSec = SecurityContextHolder.getContext();
      try {
        if (callerMdc != null) MDC.setContextMap(callerMdc); else MDC.clear();
        SecurityContextHolder.setContext(callerSec);
        runnable.run();
      } finally {
        if (prevMdc != null) MDC.setContextMap(prevMdc); else MDC.clear();
        SecurityContextHolder.setContext(prevSec);
      }
    };
  };
}
Do Not Forget AsyncUncaughtExceptionHandler: Whenever an @Async method returns void instead of CompletableFuture<T>, uncaught exceptions never reach the caller. Register an AsyncConfigurer bean overriding getAsyncUncaughtExceptionHandler() to log structured alerts and increment error metrics.

SpringProxyDispatcher: External Interception vs. this Self-Invocation

Implement SpringProxyDispatcher(targetBean, asyncMethods, executor) to model Spring's AsyncExecutionInterceptor.

Not Run
• asyncMethods is an Array (or Set) of method names annotated with @Async.
• Return a proxy object exposing every method of targetBean.
• When an external caller calls an @Async method on the proxy, dispatch () => targetBean[name](...args) via executor.submit(fn) and return its Promise.
• Non-async methods must run synchronously with this === targetBean so internal this.asyncMethod() calls bypass the proxy just like real Spring beans!

LAB 22.2 · TASKDECORATOR CONTEXT PROPAGATION

MdcTaskDecorator: Submission Capture & finally Restoration

Implement MdcTaskDecorator(mdcStore) returning { decorate(task) } with leak-free cleanup.

Not Run
APIs on mdcStore: getCopyOfContextMap() (returns shallow copy or null), setContextMap(map), and clear().
• Capture caller MDC when decorate(task) is called (submission time), not when the worker runs.
• Before calling task(), save worker's previous MDC and install caller MDC (or clear() if null).
• In finally, restore previous MDC (or clear() if null) even when task() throws!

LAB 22.3 · VOID VS FUTURE ERROR HANDLING

AsyncBatchAggregator: Capturing Void @Async Exceptions

Implement AsyncBatchAggregator(executor, uncaughtHandler) with invokeVoid, invokeFuture, and runBatch.

Not Run
• invokeVoid(methodName, fn, ...params): submits to executor.submit(() => fn(...params)), returns undefined immediately, and routes any sync/async error to uncaughtHandler.handleUncaughtException(err, methodName, params).
• invokeFuture(methodName, fn, ...params): returns the Promise from executor.submit directly to the caller (do not call uncaughtHandler for future failures).
• async runBatch(tasks): dispatches all { type: 'void'|'future', methodName, fn, params } tasks concurrently, awaits all pending void + future executions, and returns an array of settled future entries { methodName, status, value/reason }.
