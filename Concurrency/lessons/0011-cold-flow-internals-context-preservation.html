Part 01 · First Principles

Why Cold Flow Is Just Sequential suspend Lambdas

Most developers imagine a Flow as an active pipeline pushing values through background queues. In reality, an unbuffered cold Flow has zero concurrency of its own: it is a lazy, unicast CPS callback chain (Kotlin Asynchronous Flow Guide).

1. Two Interfaces, Zero Threads

The entire cold stream abstraction compiles down to two tiny interfaces: 

interface Flow<out T> {
    suspend fun collect(collector: FlowCollector<T>)
}

fun interface FlowCollector<in T> {
    suspend fun emit(value: T)
}

When you write flow { emit(1); emit(2) }.map { it * 10 }.collect { render(it) }, nothing runs until collect is invoked. Every emit(1) directly suspends and invokes map's lambda, which directly invokes render(10) before emit(1) returns to produce 2.

2. Context Preservation & flowOn

Because emit() directly calls the downstream FlowCollector, Kotlin enforces Context Preservation: emit() must be called from the same CoroutineContext as collect(). 

// Upstream runs in channel coroutine on IO;
// Downstream stays on collector's Main context!
flow { emit(queryDb()) }    // runs on Dispatchers.IO
    .map { toDomain(it) }   // runs on Dispatchers.IO
    .flowOn(Dispatchers.IO) // <-- Channel boundary
    .map { toUiModel(it) }  // runs on Main
    .collect { render(it) } // runs on Main

flowOn inserts a coroutine + buffered channel boundary so upstream runs on its own dispatcher while downstream stays untouched (Flow Context & flowOn).

Operator Architecture Diagram: Sequential Fusion vs. Channel Boundary

COLD SEQUENTIAL (default — 1 coroutine, 0 channels, sequential CPS calls):
  [Collector Coroutine]
     └─ collect() ─▶ map.collect() ─▶ flow.collect()
                         ▲                 │
                         └─── emit(v) ◀────┘   (must stay on same CoroutineContext!)

WITH flowOn / buffer / conflate (2 coroutines decoupled by Channel):
  [Upstream Coroutine (e.g. IO)] ──emit──▶ [ Channel / Buffer ] ──receive──▶ [Collector Coroutine (Main)]
     ▲ flowOn(IO) affects ONLY stages left of the channel!                      ▲ downstream stays on Main

EARLY TERMINATION (take(n) / first()):
  Collector throws internal AbortFlowException(owner) inside emit() ──▶ unwinds upstream immediately!

Backpressure & Flattening Operators Compared

Operator Coroutines When Collector Is Slower Than Producer Production Use Case
Default (Sequential) 1 coroutine Producer suspends inside emit() until collector finishes item. Deterministic step-by-step transforms with natural backpressure.
buffer(capacity) 2 coroutines + Channel Producer runs ahead up to capacity items; total time shrinks from sum to overlap. Decoupling fast I/O/DB reads from moderately slow UI/disk writes.
conflate() 2 coroutines + 1-slot DROP_OLDEST Producer never waits; intermediate uncollected items are overwritten by newest value. UI state ticks, download progress %, sensor frames where only latest matters.
collectLatest / flatMapLatest Cancels previous inner job Immediately cancels in-flight collector/inner flow and starts fresh on latest emission. Search-as-you-type autocomplete, filter switches, reactive reload triggers.
flatMapConcat Sequential inner flows Waits for inner flow N to complete completely before collecting inner flow N+1. Strict ordered multi-step uploads or paginated fetches.
flatMapMerge(concurrency) Bounded concurrent inner flows Collects up to concurrency (default 16) inner flows concurrently, interleaving results. Parallel enrichment of independent IDs when output order does not matter.
Exception Transparency Invariant: A downstream collector must always be able to catch exceptions thrown by upstream or by itself. Wrapping emit() inside a try { emit(v) } catch (e: Throwable) { ... } inside flow { ... } accidentally swallows downstream collector errors (and breaks CancellationException!). Always use the declarative .catch { ... } operator, which inspects the thrower and catches upstream errors only (Exception Transparency).

Part 03 · Production Kotlin & Android

Junior Traps vs. Senior Patterns in Kotlin Flow

Apply Android Coroutines Best Practices and Kotlin Flow Context & Exception Rules to avoid silent bugs and crashes.

Pattern 1: Context Preservation — Why withContext Inside flow {} Throws

✗ JUNIOR TRAP: withContext Around emit()
fun fetchReadings(): Flow<Reading> = flow {
    // CRASH: IllegalStateException!
    // Flow invariant is violated: collected on Main,
    // but emit() called from Dispatchers.IO!
    withContext(Dispatchers.IO) {
        val row = db.queryLatest()
        emit(row)
    }
}
✓ SENIOR PATTERN: flowOn(Dispatchers.IO)
fun fetchReadings(): Flow<Reading> = flow {
    val row = db.queryLatest() // runs on IO
    emit(row)
}
    .map { mapToDomain(it) }   // also runs on IO
    .flowOn(Dispatchers.IO)    // affects UPSTREAM only
// Collector in ViewModel/UI stays safely on Main!

Pattern 2: Search-as-You-Type with debounce + flatMapLatest

✗ JUNIOR TRAP: flatMapMerge Out-of-Order Race
queryFlow
    .debounce(300)
    // Stale "ko" (500ms) can finish AFTER "kot" (80ms)
    // and overwrite newer search results on screen!
    .flatMapMerge { q -> repo.searchUsers(q) }
    .collect { render(it) }
✓ SENIOR PATTERN: distinctUntilChanged + flatMapLatest
queryFlow
    .debounce(300)
    .map { it.trim() }
    .distinctUntilChanged()
    .flatMapLatest { q ->
        if (q.isEmpty()) flowOf(emptyList())
        else repo.searchUsers(q).flowOn(Dispatchers.IO)
    } // Cancels obsolete "ko" HTTP request immediately!
    .collect { render(it) }

Pattern 3: catch {} Scope & onCompletion Ordering

✗ JUNIOR TRAP: try/catch in flow{} + Wrong Order
flow {
    try { emit(api.load()) }
    catch (e: Exception) { emit(Fallback) }
    // Trap 1: Catches collector crashes AND CancellationException!
}
    .onCompletion { cause -> log(cause) } // Trap 2: Sees cause == null
    .catch { emit(Fallback) }             // if catch runs AFTER onCompletion!
✓ SENIOR PATTERN: Declarative catch Before Downstream
flow { emit(api.load()) }
    .catch { cause ->
        // Upstream errors ONLY; CancellationException is never caught.
        emit(cachedFallback())
    }
    .onCompletion { cause ->
        // Runs on normal finish, upstream failure, or cancellation.
        // Positioned AFTER catch: cause == null if catch handled it.
        hideLoadingSpinner(failed = cause != null)
    }
    .collect { render(it) } // Downstream crashes still propagate!

LAB 11.3 · CONTEXT PRESERVATION & EXCEPTION TRANSPARENCY

Implement flowContextAndCatch(pipeline)

Enforce flowOn upstream-only context assignment, reject direct withContext emissions, and restrict catch to upstream errors.

Not Run
Input: { source, ops = [], collector, collectorContext = 'Main' }.
• ops contains { type: 'map', fn }, { type: 'flowOn', context }, and { type: 'catch', handler }.
• flowOn assigns context to stages upstream of itself only; downstream stages and collector(val, collectorContext) retain downstream context.
• source({ emit, withContext, context }): if emit() is called while withContext(otherCtx, ...) changed the active context away from context, throw new Error('Flow invariant is violated...').
