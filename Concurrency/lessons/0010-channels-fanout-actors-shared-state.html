Channels, Fan-Out/Fan-In Pipelines & Shared State Patterns

A Deferred<T> returns a single value; a Channel<T> transfers a hot stream of values across coroutines with cooperative backpressure. Master channel capacities (RENDEZVOUS, BUFFERED, CONFLATED, UNLIMITED), produce pipelines, worker-pool fan-out, select expressions, and choosing cleanly between Mutex, Actors, and confinement.

Part 01 · First Principles

Share Memory by Communicating (CSP) vs. Synchronized Memory

In Lesson 03 and Lesson 05 we built locks and bounded queues from scratch. Kotlin Coroutines formalize that producer-consumer transfer as a Channel: a hot, thread-safe, non-blocking FIFO pipe where send() and receive() suspend cooperatively instead of parking OS threads (Kotlin Coroutines Channels Guide).

Channel Semantics (Hot & Unicast)

Ownership transfer: Each item sent into a Channel is delivered to at most one receiver (fan-out load balancing), never broadcast to all listeners.

Hot lifetime: A Channel exists and buffers independently of whether a receiver is listening right now. If nobody calls close() or receive(), producers can stay suspended forever.

produce, Fan-Out & select

produce { ... }: Coroutine builder returning a ReceiveChannel that automatically closes when its builder block completes or fails—eliminating orphan suspended receivers.

select { ... }: Multiplexes multiple suspending clauses (e.g., chanA.onReceive vs. chanB.onReceive or onSend), executing whichever becomes ready first with bias toward earlier clauses (Kotlin Select Expression).

Pipeline Architecture: Producer → Fan-Out Workers → Fan-In Collector

                   ┌──▶ Worker 0 (suspends on jobs.receive()) ──┐
Producer (produce) ├──▶ Worker 1 (suspends on jobs.receive()) ──┼──▶ results Channel ──▶ Fan-In Collector
  jobs.send(item)  └──▶ Worker 2 (suspends on jobs.receive()) ──┘     (closed ONLY after all workers join)

Closing invariant: Calling close() on a Channel sends a special close token after all previously buffered elements. A consumer draining via for (x in channel) or receive() continues receiving every buffered item before seeing the channel closed (Closing and iteration over channels).

Shared Mutable State: Choosing Your Tool

When multiple coroutines on multi-threaded dispatchers (Dispatchers.Default / Dispatchers.IO) touch shared state, you have four primary solutions (Kotlin Shared Mutable State & Concurrency):

MechanismHow It Serializes AccessSupports suspend Inside?Best FitPrimary Hazard
Thread Confinement
limitedParallelism(1)		 All mutations hop onto one dedicated single-threaded dispatcher Yes (careful: interleaving occurs at inner awaits!) Fast in-memory state machines, UI/canvas state, single-writer caches Multi-step suspend calls still interleave unless queued
Mutex.withLock Suspending mutual exclusion lock (non-reentrant!) Yes, preserves lock across suspend points Short critical sections guarding multi-field invariants Holding lock during slow network I/O; re-entrant self-deadlock
Atomic* / StateFlow.update Hardware CAS retry loop (lock-free) No (lambda must be pure & fast) Counters, flags, immutable MVI state snapshots Side effects inside CAS retry loop run multiple times!
Actor Mailbox
(Coroutine + Channel)		 Single coroutine dequeues & runs one message at a time Yes, safely! Next message waits until current completes Stateful services owning caches, sockets, or ordered disk writes Unbounded mailbox growth under overload; request-reply boilerplate
Subtle distinction (Confinement vs. Actor): Simply running mutations inside withContext(singleThreadDispatcher) does not make a read-suspend-write atomic! If the block suspends midway for disk I/O, another coroutine dispatched to that same single thread can enter and read stale state. An Actor loop or Mutex keeps the entire multi-step operation serialized.

Part 03 · Production Kotlin & Android

Junior Traps vs. Senior Patterns in Kotlin

Apply Kotlin Channels and Android Coroutines Best Practices to eliminate resource leaks, premature channel closes, and lock contention.

Pattern 1: Hot Channel Leaks vs. Structured produce / Cold Flow

✗ JUNIOR TRAP: Raw Unclosed Channel Leaks Coroutines
fun streamEvents(): ReceiveChannel<Event> {
    val ch = Channel<Event>(Channel.BUFFERED)
    GlobalScope.launch { // Unstructured! Leaks forever
        while (true) ch.send(pollNextEvent())
    }
    return ch // Consumer cancels -> producer hangs forever!
}
✓ SENIOR PATTERN: Structured produce or Cold Flow
// Option A: Scoped produce auto-closes & cancels on failure
fun CoroutineScope.produceEvents(): ReceiveChannel<Event> = produce {
    while (isActive) send(pollNextEvent())
}
// Option B: Cold Flow cleans up automatically when collector cancels
fun observeEvents(): Flow<Event> = flow {
    while (currentCoroutineContext().isActive) emit(pollNextEvent())
}

Pattern 2: Fan-Out Worker Pool + Fan-In Result Merge

✗ JUNIOR TRAP: Worker Closes Shared Results Channel
repeat(4) {
    launch {
        for (job in jobsChannel) {
            resultsChannel.send(process(job))
        }
        resultsChannel.close() // CRASH! Faster worker closes
        // while slower workers still call send()!
    }
}
✓ SENIOR PATTERN: Coordinator Closes Results After Join
suspend fun processAll(items: List<Job>): List<Result> = coroutineScope {
    val jobs = produce(capacity = 8) { items.forEach { send(it) } }
    val results = Channel<Result>(capacity = 8)
    val workers = List(4) {
        launch { for (job in jobs) results.send(process(job)) }
    }
    launch { workers.joinAll(); results.close() }
    buildList { for (r in results) add(r) }
}

Pattern 3: Actor Mailbox vs. Broad Mutex Around I/O

✗ JUNIOR TRAP: Holding Mutex Across Slow Network/Disk I/O
val mutex = Mutex()
suspend fun updateToken(newToken: String) {
    mutex.withLock {
        val prev = diskStore.read()   // 40ms
        networkApi.syncToken(newToken) // 800ms! Every reader stalls!
        diskStore.write(newToken)
    }
}
✓ SENIOR PATTERN: Actor Mailbox + Explicit Reply Deferred
sealed interface TokenMsg {
    data class Update(val token: String, val ack: CompletableDeferred<Unit>) : TokenMsg
    data class Get(val reply: CompletableDeferred<String>) : TokenMsg
}
// Single coroutine owns state sequentially via mailbox:
fun CoroutineScope.tokenActor() = Channel<TokenMsg>(64).also { box ->
    launch {
        var cached = diskStore.read()
        for (msg in box) when (msg) {
            is TokenMsg.Update -> { diskStore.write(msg.token); cached = msg.token; msg.ack.complete(Unit) }
            is TokenMsg.Get -> msg.reply.complete(cached)
        }
    }
}

LAB 10.1 · CHANNEL MODES

Implement AsyncChannel(capacity, mode)

Support RENDEZVOUS (capacity = 0), BUFFERED (capacity > 0), and 'CONFLATED' modes with send(val), receive(), and close().

Not Run
Contract:
• await ch.send(val): throws if already closed; delivers immediately to a waiting receiver if present; in Rendezvous (capacity === 0 && mode !== 'CONFLATED') suspends until matched; in Buffered enqueues up to capacity then suspends when full; in 'CONFLATED' overwrites any unconsumed item and never suspends.
• await ch.receive(): resolves to { value, done: false }, or { value: undefined, done: true } only after close() AND all buffered/pending sends are drained.
• ch.close(): prevents new send() calls while letting unread buffered/waiting items drain; resolves any waiting receivers on an empty channel with { value: undefined, done: true }.

LAB 10.2 · FAN-OUT / FAN-IN PIPELINE

Implement fanOutFanIn(jobs, workerCount, processFn, createChannel)

Wire a producer into a bounded jobs channel, launch workerCount concurrent workers, and fan-in all results until closed.

Not Run
API: createChannel(capacity) returns a channel with await send(v), await receive() ({ value, done }), and close().
• Producer sends all jobs into jobsCh = createChannel(2) and calls jobsCh.close().
• Spawn Math.max(1, workerCount) concurrent workers reading jobsCh, calling await processFn(job, workerId), and sending outputs to resultsCh = createChannel(workerCount).
• Call resultsCh.close() only after all workers complete, and drain resultsCh concurrently to return all collected results.

LAB 10.3 · ACTOR MAILBOX

Implement ActorStateBox(store)

Process { type: 'INC' | 'DEC' | 'GET', amount, resolve } messages sequentially through a mailbox so concurrent async callers never race.

Not Run
Contract:
• store exposes await store.read() and await store.write(nextVal) with interleaved async latencies.
• actor.send(msg) enqueues { type, amount, resolve } into an internal FIFO mailbox and triggers a single sequential processor loop (never running two messages concurrently).
• 'INC' adds amount and writes; 'DEC' subtracts amount and writes; 'GET' reads current value; each resolves msg.resolve(value) upon completion.
