Part 01 · First-Principles Mental Model

Why Cancellation Is Cooperative—and Why Generic catch Breaks It

Kotlin coroutines follow cooperative scheduling: calling job.cancel() never preempts or kills the underlying OS thread. Instead, it transitions the Job state machine and relies on the coroutine to observe cancellation at suspension points or explicit checkpoints (Kotlin Coroutines Cancellation and Timeouts; Android Coroutines Best Practices).

1. The Job Cancellation State Machine

Active → Cancelling → Cancelled:

When job.cancel() is invoked on an Active job, isActive becomes false and isCancelled becomes true immediately, placing the job in Cancelling state. It stays Cancelling while unwinding stack frames, running finally blocks, and waiting for child jobs. Only after all cleanup finishes does it reach Cancelled (isCompleted == true).

2. The CancellationException Sentinel

Normal termination signal, not a crash:

All cancellable kotlinx.coroutines suspend functions (delay, yield, await, Ktor/Retrofit calls) check the job and throw CancellationException to unwind the call stack. The parent Job treats CancellationException as expected teardown. If your catch (e: Exception) or runCatching swallows it, the stack never unwinds and the coroutine keeps running as a zombie!

Cancellation Checkpoints, Cleanup & Timeout Semantics

MechanismBehavior When Job Is CancelledUse CaseCommon Trap
isActive Boolean property (false once cancelling); never throws. Loop guard (while (isActive)) where cleanup follows the loop. Does not explain why cancelled; easy to skip checking inside nested helpers.
ensureActive() Immediately throws the exact CancellationException cause if !isActive. Top of tight CPU-bound loops or before expensive steps without suspend points. Calling yield() when you only need a cancellation check (extra dispatch overhead).
yield() Checks cancellation and yields dispatcher thread to queued peers. Fairness in long CPU coroutines sharing a bounded dispatcher. Using it on an already-cancelled coroutine without expecting CancellationException.
withContext(NonCancellable) Suspends safely even while enclosing Job is Cancelling. Suspending resource cleanup inside a finally block (DB flush, file close). Passing NonCancellable to launch(...)—breaks structured parent-child links!
withTimeout vs withTimeoutOrNull withTimeout throws TimeoutCancellationException (a CancellationException subclass); withTimeoutOrNull returns null. Use withTimeoutOrNull when caller wants a fallback value without aborting the outer coroutine. Catching Exception inside withTimeout swallows TimeoutCancellationException.
Resource safety rule: Synchronous cleanup (cursor.close(), mutex.unlock()) runs normally inside finally { ... } even after cancellation. However, calling any suspending function inside finally while the job is Cancelling immediately throws CancellationException—skipping the rest of finally unless wrapped in withContext(NonCancellable) { ... }.

Part 03 · Production Kotlin & Android

Junior Traps vs. Senior Patterns in Kotlin

Apply Kotlin Cancellation Guidelines to keep ViewModels, repositories, and resource wrappers leak-free.

Pattern 1: Swallowing CancellationException in catch(Exception) & runCatching

✗ JUNIOR TRAP: catch(Exception) & stdlib runCatching
// Trap A: catch(Exception) eats CancellationException!
suspend fun syncLoop() {
    while (true) {
        try { api.pushAnalytics() }
        catch (e: Exception) { logWarn(e) } // Zombie loop!
    }
}

// Trap B: runCatching catches Throwable (including cancel)!
suspend fun loadUser(): Result<User> = runCatching {
    api.fetchUser() // Cancelling returns Result.failure!
}
✓ SENIOR PATTERN: Rethrow CancellationException
suspend fun syncLoop() {
    while (currentCoroutineContext().isActive) {
        try { api.pushAnalytics() }
        catch (e: CancellationException) { throw e } // Rethrow!
        catch (e: IOException) { logWarn(e) }
    }
}

// Safe suspend wrapper for Result<T>:
suspend inline fun <R> suspendRunCatching(block: () -> R): Result<R> =
    try { Result.success(block()) }
    catch (c: CancellationException) { throw c }
    catch (t: Throwable) { Result.failure(t) }

Pattern 2: Suspending Cleanup Inside finally Needs withContext(NonCancellable)

✗ JUNIOR TRAP: Suspend in finally (or launch(NonCancellable))
val job = scope.launch {
    val session = db.openSession()
    try {
        streamEvents(session)
    } finally {
        // THROWS CancellationException immediately!
        session.flushPendingAsync()
        session.close() // NEVER REACHED — resource leaked!
    }
}
// ALSO WRONG: scope.launch(NonCancellable) { ... }
// Severs structured parent Job so scope.cancel() ignores it!
✓ SENIOR PATTERN: withContext(NonCancellable) in finally
val job = scope.launch {
    val session = db.openSession()
    try {
        streamEvents(session)
    } finally {
        withContext(NonCancellable) {
            // Runs even though enclosing job is Cancelling!
            try { session.flushPendingAsync() }
            finally { session.close() }
        }
    }
}

Pattern 3: withTimeout (Throws!) vs. withTimeoutOrNull

✗ JUNIOR TRAP: Expecting withTimeout to Return or Recover
viewModelScope.launch {
    // Throws TimeoutCancellationException!
    val cached = withTimeout(500) { fetchRemoteConfig() }
    // Next line NEVER executes on timeout!
    applyFallbackConfig()
}
// Worse: wrapping withTimeout in try/catch(Exception)
// can accidentally swallow outer coroutine cancellation too!
✓ SENIOR PATTERN: withTimeoutOrNull for Optional Deadlines
viewModelScope.launch {
    // Returns null on timeout without cancelling launch;
    // still rethrows real IOExceptions / outer cancellation!
    val remote = withTimeoutOrNull(500) {
        fetchRemoteConfig()
    }
    _uiState.value = remote ?: loadCachedConfig()
}

LAB 8.1 · COOPERATIVE WORKER LOOP

Implement cancellableWorker(items, processFn, token)

Check cancellation cooperatively via token.throwIfCancelled(), rethrow CancellationError, and recover only from domain errors.

Not Run
• Call token.throwIfCancelled() before starting and before processing each item.
• For each item, run await processFn(item). On success, push { item, status: 'ok', value }.
• In catch (err): if err instanceof CancellationError || err?.isCancellation, rethrow err immediately. For domain errors, push { item, status: 'error', error: err.message } and continue.
• Return the collected array of item results in input order.

LAB 8.2 · NONCANCELLABLE CLEANUP

Implement withManagedResource(openFn, useFn, closeFn, token)

Guarantee closeFn(resource) completes inside a non-cancellable cleanup phase even when useFn fails or token is cancelled.

Not Run
• Call token.throwIfCancelled() before opening, then const resource = await openFn().
• Execute return await useFn(resource) inside a try { ... } finally { ... } block.
• In finally, run await token.runNonCancellable(() => closeFn(resource)) so async cleanup never aborts on cancellation.
• If openFn() throws before acquiring a resource, do not call closeFn.

LAB 8.3 · STRUCTURED TIMEOUTS

Implement withTimeoutOrNull(ms, taskFn)

Cancel the task's AbortToken when ms expires and return null, while rethrowing genuine task errors.

Not Run
• Provided global helper: new AbortToken() with isCancelled, cancel(reason), throwIfCancelled(), and onCancel(cb).
• If ms <= 0, return null immediately.
• Race taskFn(token) against a setTimeout of ms. On timeout, call token.cancel('Timeout') and return null.
• Always clearTimeout in finally; rethrow genuine non-timeout task errors!
