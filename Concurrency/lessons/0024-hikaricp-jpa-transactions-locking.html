HikariCP Pool Saturation, @Transactional Boundaries & JPA Locking

Part 01 · First-Principles Mental Model

Little's Law, Connection Starvation & Row Contention

Before Virtual Threads, Tomcat's 200-thread pool accidentally throttled traffic before it reached PostgreSQL. With spring.threads.virtual.enabled=true (Spring Boot Virtual Threads Reference), thousands of virtual threads arrive simultaneously at a 10-connection HikariCP pool (HikariCP Pool Sizing Guide).

1. Why 10,000 Virtual Threads + Pool=10 Crashes

By Little's Law, max throughput is PoolSize / HoldTime. HikariCP defaults to maximum-pool-size=10 and connection-timeout=30000ms.

If a transaction runs 5ms of SQL, 10 connections sustain 10 / 0.005s = 2,000 tx/s. If a developer puts a 500ms HTTP call inside @Transactional, each connection stays checked out for 505ms—collapsing throughput to ~19.8 tx/s. The remaining 9,990 virtual threads block in HikariCP's waiter queue until they throw SQLTransientConnectionException.

2. ThreadLocal Transactions & @Async Traps

Spring binds the active JDBC Connection to the calling thread via ThreadLocal inside TransactionSynchronizationManager.

Calling an @Async method from inside @Transactional hops to a different thread with no transaction context—it cannot join or roll back with the parent. Conversely, calling PROPAGATION_REQUIRES_NEW on the same thread checks out a second HikariCP connection while holding the first—causing instant self-deadlock if activeParents >= poolSize.

10,000 Virtual Threads (Tomcat / @Async) │ ├─[TRAP: RestClient inside @Transactional]──▶ Acquires HikariCP conn BEFORE 500ms HTTP │ └─► 10 conns pinned idle for 500ms ─► Waiter queue explodes ─► SQLTransientConnectionException! │ └─[SENIOR: Pre-Fetch HTTP, then TransactionTemplate] 1) Virtual thread runs 500ms HTTP (0 DB connections held) 2) TransactionTemplate acquires HikariCP conn for 5ms SQL commit ─► 100× pool capacity!

JPA Concurrency & Locking Spectrum (Spring Data JPA Locking)

Strategy SQL / JPA Mechanism Contention & Lock Behavior Production Fit
No Lock (READ COMMITTED) Plain SELECT then UPDATE Two transactions read balance=100 and both write 80; silent lost update / double-spend. Never for read-modify-write state transitions.
@Version Optimistic UPDATE ... SET version=v+1 WHERE id=? AND version=v Zero DB row locks during read/think time; 0 affected rows throws OptimisticLockingFailureException. Low/moderate contention edits (user profiles, order status, normal accounts).
@Lock(PESSIMISTIC_WRITE) SELECT ... FOR UPDATE Acquires exclusive DB row lock immediately; concurrent writers queue until commit/rollback. Hot rows (flash-sale inventory, central settlement ledgers) where retries thrash.
FOR UPDATE SKIP LOCKED Native query with SKIP LOCKED (PostgreSQL Docs) Skips rows currently locked by other workers instead of blocking; zero head-of-line pileup. Concurrent job queues, transactional outbox workers, batch task claiming.
Disable Open Session in View in production: Set spring.jpa.open-in-view=false. With OSIV enabled (Spring Boot's default), Hibernate keeps a database connection or persistence context tied to the entire HTTP request lifecycle—masking N+1 queries and extending HikariCP pressure into controller JSON serialization.

Part 03 · Production Java 21–25+ & Spring Boot

Junior Traps vs. Senior Patterns in Spring Boot

Keep transactions microsecond-short, isolate external HTTP calls outside JDBC boundaries, and choose the right locking primitive for your contention profile.

Pattern 1: External HTTP Inside @Transactional vs. Split Boundary (TransactionTemplate)

✗ JUNIOR TRAP: Holding JDBC Conn During RestClient
@Service
public class CheckoutService {
    @Transactional // Acquires HikariCP conn BEFORE HTTP!
    public Order placeOrder(OrderCmd cmd) {
        var auth = restClient.post()
            .uri("https://psp.example/authorize")
            .body(cmd.payment())
            .retrieve()
            .body(AuthResult.class); // 500ms network wait!
        return orderRepo.save(Order.create(cmd, auth));
    }
}
✓ SENIOR PATTERN: Pre-Fetch Outside + TransactionTemplate
@Service
public class CheckoutService {
    private final TransactionTemplate txTemplate;

    public Order placeOrder(OrderCmd cmd) {
        // 1. Virtual thread parks on HTTP; 0 DB conns held!
        var auth = restClient.post()
            .uri("https://psp.example/authorize")
            .body(cmd.payment())
            .retrieve()
            .body(AuthResult.class);

        // 2. Short, deterministic ~5ms DB transaction
        return txTemplate.execute(status ->
            orderRepo.save(Order.create(cmd, auth))
        );
    }
}

Pattern 2: @Version Optimistic Retry Loop vs. @Lock(PESSIMISTIC_WRITE)

✗ JUNIOR TRAP: Retrying Inside Same @Transactional
// BUG 1: No @Version -> silent lost update!
// BUG 2: Catching OptimisticLockingFailureException INSIDE
// @Transactional reuses a stale persistence context & rolled-back TX!
@Transactional
public void debit(UUID id, long amount) {
    for (int i = 0; i < 3; i++) {
        try {
            var acct = repo.findById(id).orElseThrow();
            acct.debit(amount);
            repo.saveAndFlush(acct);
            return;
        } catch (OptimisticLockingFailureException ignored) {}
    }
}
✓ SENIOR PATTERN: Fresh TX Per Retry OR Pessimistic Lock
// Option A: @Version with fresh TransactionTemplate per attempt
public void debitOptimistic(UUID id, long amount) {
    for (int attempt = 0; attempt < 5; attempt++) {
        try {
            txTemplate.executeWithoutResult(s -> {
                var acct = repo.findById(id).orElseThrow();
                acct.debit(amount); // checks balance >= amount
            }); // commit executes UPDATE ... WHERE version = ?
            return;
        } catch (OptimisticLockingFailureException ex) {
            if (attempt == 4) throw ex;
        }
    }
}
// Option B (Hot SKU): @Lock(LockModeType.PESSIMISTIC_WRITE)
// SELECT ... FOR UPDATE serializes writers without retry storms.

Pattern 3: Concurrent Worker Job Claiming with FOR UPDATE SKIP LOCKED

✗ JUNIOR TRAP: Plain SELECT or Blocking FOR UPDATE
// Trap A: Plain SELECT lets 10 pods read the SAME row!
// Trap B: Plain FOR UPDATE makes 49 workers block on worker 1's lock!
@Query(value = """
    SELECT * FROM outbox_jobs
    WHERE status = 'PENDING'
    ORDER BY created_at LIMIT 1
    FOR UPDATE
    """, nativeQuery = true)
Optional<OutboxJob> findNextBlocking();
✓ SENIOR PATTERN: SKIP LOCKED Claim in Short TX
@Query(value = """
    SELECT * FROM outbox_jobs
    WHERE status = 'PENDING'
    ORDER BY created_at
    FOR UPDATE SKIP LOCKED
    LIMIT 1
    """, nativeQuery = true)
Optional<OutboxJob> lockNextPendingSkipLocked();

// Inside TransactionTemplate:
// 1. lockNextPendingSkipLocked() -> skips rows locked by peers
// 2. mark status = 'CLAIMED', worker_id = :podId
// 3. commit in <5ms, then run slow external HTTP outside TX!
