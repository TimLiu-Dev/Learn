Observability: Structured Logs & OpenTelemetry GenAI Traces

Pinpointing whether a 7-second AI response stalled in SQL auth, vector search, or model output tokens—using OpenTelemetry distributed trace waterfalls and GenAI semantic conventions.

Estimated Time: 25 min Prerequisites: 0012, 0028 Tangible Win: Build a Trace Waterfall Bottleneck Finder & GenAI Cost/SLO Analyzer

1. From Mobile Crashlytics to Distributed AI Waterfalls

On Android, Crashlytics shows one stack trace on one device. In an FDE AI system, a single user query hops from API Gateway → OIDC Auth → Hybrid Retrieval → Reranker → LLM Synthesis → MCP Tool Call. When the customer complains "Your copilot feels sluggish today", plain print() logs are useless.

Industry observability teams converge on OpenTelemetry and the OTel GenAI Semantic Conventions (consumed by Datadog, Honeycomb, Grafana, and Langfuse):

  1. Structured JSON Logs + trace_id: Every log line emits machine-parseable JSON carrying trace_id, tenant_id, and span_id—never unredacted PII!
  2. Parent-Child Span Waterfalls: Isolates exact latency shares (e.g., Reranker took 4,200ms of a 4,800ms request, not the LLM).
  3. GenAI Span Attributes: Attach gen_ai.request.model, gen_ai.usage.input_tokens, gen_ai.usage.cached_tokens, gen_ai.usage.output_tokens, and ttft_ms so cost spikes trace straight back to the guilty tenant or prompt version.
SLO Hygiene:
Averages lie! One 9-second cold-start outlier hidden inside a 900ms mean still frustrates operators—always measure P95 / P99 latency.
