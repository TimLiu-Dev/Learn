PostgreSQL Internals, API Design & Operator UI Foundations

Closing the full-stack gap from mobile dev: choosing Postgres B-tree, GIN, and HNSW indexes, avoiding OFFSET pagination collapse, designing idempotent REST/GraphQL APIs, and wiring React operator tables.

Estimated Time: 25 min Prerequisites: 0003, 0008 Tangible Win: Build a Keyset Pagination API Builder & Postgres Index Advisor

1. Why Android Room Habits Break on Multi-Tenant Postgres & Operator UIs

On Android, SQLite/Room holds a few thousand rows for one user. On an FDE deployment, PostgreSQL holds millions of rows across dozens of enterprise tenants, serving both your Python/TypeScript API and your pgvector hybrid search (PostgreSQL Index Docs).

  1. Composite Tenant-First Indexes: Filtering WHERE tenant_id = $1 AND status = $2 needs a composite B-tree index (tenant_id, status, updated_at DESC)—and use GIN for JSONB/tsvector and HNSW for embeddings (Postgres Indexing).
  2. Keyset (Cursor) Pagination Beats OFFSET: Deep OFFSET 50000 scans and discards 50,000 rows while drifting if new webhooks insert mid-scroll. Cursor pagination ((created_at, id) < ($1, $2)) stays O(log N) forever.
  3. Zero-Downtime Migrations & Locks: Creating an index without CONCURRENTLY locks writes on live customer tables!
  4. Operator React/TS UI State: Enterprise users don't just chat—they triage 5,000 rows in filterable tables with server-driven pagination, URL-synced filters, and explicit mutation rollback.
Android Bridge:
Keyset pagination in REST/GraphQL mirrors Jetpack Paging 3 remote keys—except you must tie-break timestamps with id so two orders created in the same millisecond never get skipped!
Mobile / Naive Default

Local SQLite + Page Numbers

  • Uses LIMIT 25 OFFSET 2500 page-number queries.
  • Runs schema migrations on app restart with zero lock concerns.
  • Single index on primary key feels fast on 2,000 local rows.
Senior FDE Production

Multi-Tenant Postgres + Keyset APIs

  • Uses opaque base64 cursors (sortKey, id) for deterministic O(log N) paging.
  • Deploys additive migrations + CREATE INDEX CONCURRENTLY.
  • Runs EXPLAIN ANALYZE to verify index scans inside every tenant query.

2. Annotated Code: Postgres Index & Keyset Pagination Pattern

SQL / PostgreSQL Tenant-Scoped Composite B-Tree + Deterministic Keyset Cursor 
-- Composite index matches tenant filter + deterministic keyset sort:
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_orders_tenant_cursor
  ON orders (tenant_id, created_at DESC, id DESC);

-- Keyset page fetch (fast at row #1 and row #1,000,000 alike):
SELECT id, order_ref, amount, created_at
FROM orders
WHERE tenant_id = $1
  AND (created_at, id) < ($2::timestamptz, $3::text)
ORDER BY created_at DESC, id DESC
LIMIT 26; -- Fetch limit+1 to compute hasMore without running expensive COUNT(*)!
