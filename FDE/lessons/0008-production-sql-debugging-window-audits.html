Production SQL Debugging & Window Drift Audits

When a VP says "Your dashboard revenue is 18% higher than SAP!", you don't guess. Use SQL CTEs and window functions (ROW_NUMBER()) to isolate duplicate ingestion and many-to-many join fan-out in 60 seconds.

Estimated Time: 25 min Prerequisites: 0007 Tangible Win: Build a Window-Dedup Drift Auditor & Join Fan-Out Detector

1. Two SQL Bugs That Ruin Customer Trust Every Week

Almost every data discrepancy in a customer pilot comes from one of two SQL/pipeline bugs (DuckDB Window Functions):

  1. Duplicate Staging Ingestion: Retried batches land twice in raw_orders_staging. Summing the staging table directly overcounts revenue until you partition by (tenant_id, order_id) and keep only rn = 1 ordered by ingested_at DESC.
  2. 1-to-N Join Fan-Out: Joining orders (1 row) directly to shipments (3 partial deliveries) repeats orders.amount three times before SUM()! Always aggregate child tables in a CTE before joining onto parent financial tables.

2. Annotated Code: CTE + Window Deduplication & Pre-Aggregated Join

SQL / Postgres & DuckDB Isolating Duplicates and Preventing Join Fan-Out 
WITH deduped_orders AS (
  SELECT tenant_id, order_id, amount,
    ROW_NUMBER() OVER (PARTITION BY tenant_id, order_id ORDER BY ingested_at DESC) AS rn
  FROM raw_orders_staging
),
shipment_counts AS (
  SELECT tenant_id, order_id, COUNT(*) AS shipment_count
  FROM shipments
  GROUP BY tenant_id, order_id
)
SELECT o.order_id, o.amount, COALESCE(s.shipment_count, 0) AS shipments
FROM deduped_orders o
LEFT JOIN shipment_counts s ON o.tenant_id = s.tenant_id AND o.order_id = s.order_id
WHERE o.rn = 1;
