AWS Lambda Internals: Firecracker MicroVMs, Cold Starts, Concurrency & Power Tuning

Serverless does not mean server-free. Every Lambda invocation executes inside a single-concurrency Firecracker microVM where static initialization, Hyperplane VPC attachment, Little's Law concurrency limits, and memory-to-vCPU coupling decide whether your p99 latency and AWS bill look senior-engineered or catastrophic.

Your Android Bridge

On Android, a cold app start forks a fresh process from the Zygote, loads DEX bytecode, builds your Hilt/Dagger dependency graph in Application.onCreate(), and finally renders the first Activity—whereas a warm start skips process creation and reuses objects already alive in memory. AWS Lambda works the same way: a cold start boots a Firecracker microVM and runs your module-level INIT code once before calling your handler, while warm invocations freeze and unfreeze that exact sandbox—keeping SDK clients, HTTP connection pools, and parsed configs intact across requests.

1. Firecracker MicroVMs & The INIT / INVOKE Lifecycle

Earlier multi-tenant serverless platforms had an ugly tradeoff: running containers on shared hosts risked kernel escapes, while dedicating one EC2 VM per customer wasted gigabytes of RAM and took tens of seconds to boot. AWS built Firecracker—a minimalist KVM-based Virtual Machine Monitor written in Rust—to get hardware-virtualized isolation at container speed (~125 ms VM boot, ~5 MiB memory overhead per microVM).

Each microVM hosts exactly one execution environment, and each execution environment processes strictly one synchronous invocation at a time. Unlike an ECS or EKS container that multiplexes 200 concurrent HTTP requests onto one event loop or thread pool, Lambda scales out horizontally by launching one microVM per concurrent request.

  1. INIT Phase (Cold Start Only): Lambda downloads your deployment artifact (zip or container image up to 10 GB), starts the microVM, boots the language runtime (Node.js, Python, JVM, custom Rust/Go binary), runs any Lambda Extensions' init hooks, and executes everything outside your handler function (module-level SDK clients, DI containers, TLS cert loading). Standard on-demand runtime init is capped at 10 seconds.
  2. INVOKE Phase (Every Request): Lambda unfreezes the vCPU, passes the event payload to your handler, and waits up to your configured timeout (maximum 15 minutes / 900 seconds). Once the handler returns, Lambda immediately freezes the microVM CPU—meaning background coroutines or async flushes left running after return pause mid-flight until the next invocation (or die silently!).
  3. SHUTDOWN Phase (Idle Reclamation): After roughly 5–15 minutes of inactivity (exact timing is non-deterministic), Lambda reclaims the sandbox, giving registered Lambda Extensions up to 2 seconds to flush telemetry before terminating the microVM.
Figure 1: Cold starts pay MicroVM bootstrap plus INIT duration once per sandbox. Warm requests unfreeze the existing microVM and reuse module-level clients and connection pools.

2. VPC Cold Starts & AWS Hyperplane ENIs

Older AWS blog posts often warn: "Never put Lambda in a VPC unless you can tolerate 10–15 second cold starts." That advice became obsolete when AWS introduced AWS Hyperplane for VPC-connected Lambdas.

Before Hyperplane, every new concurrent microVM triggered CreateNetworkInterface in your VPC subnet at cold-start time, causing massive latency spikes and rapidly exhausting private subnet IP addresses. Today, AWS provisions shared Hyperplane ENIs asynchronously when you create or update your function—one ENI per unique (Subnet, SecurityGroupSet) combination across all functions sharing that tuple. At runtime, Firecracker microVMs open an internal tunnel to that pre-warmed Hyperplane ENI, bringing VPC cold starts down to parity with non-VPC Lambdas.

Three VPC Lambda Traps That Still Break Production
  • Missing NAT Gateway or VPC Endpoints: Attaching a Lambda to private subnets removes its default AWS-managed internet route. Calls to DynamoDB, S3, Secrets Manager, or Stripe will hang until function timeout unless you route through a NAT Gateway or attach VPC Gateway/Interface Endpoints.
  • Over-Permissive Security Group Churn: Hyperplane ENIs are shared per unique (Subnet, SecurityGroupSet). Giving 40 Lambdas 40 distinct security groups across 3 subnets still consumes 120 subnet IPs.
  • Frozen TCP Sockets: When a microVM freezes between invocations, an idle RDS or HTTP connection cannot respond to TCP keep-alives or server-side FIN packets—causing stale-socket timeouts on the next warm invoke. Use Amazon RDS Proxy for relational databases behind Lambda.

3. Concurrency Math, Throttling & Reserved vs. Provisioned Concurrency

Lambda capacity planning starts with Little's Law:

Concurrent Executions = Requests per Second (RPS) × Average Duration (seconds)

Suppose your checkout API serves 100 RPS and normally finishes in 200 ms (0.2 s): it needs 100 × 0.2 = 20 concurrent microVMs. If a downstream PostgreSQL lock slows your handler from 200 ms to 1.0 s at the same 100 RPS, required concurrency jumps 5× to 100. By default, every AWS account starts with a soft quota of 1,000 concurrent executions per Region shared across all functions, and individual functions scale up at 1,000 concurrent executions every 10 seconds until hitting the account quota or a configured cap.

Senior engineers confuse Reserved Concurrency and Provisioned Concurrency constantly, yet they solve opposite problems:

  • Reserved Concurrency (Ceiling + Guarantee, \$0 extra): Carves a dedicated slice out of your 1,000-execution regional pool. It simultaneously guarantees those slots are never stolen by noisy neighbors and acts as a hard ceiling—any request exceeding the reserved cap fails immediately with 429 TooManyRequestsException (synchronous) or retries/DLQs (asynchronous). Setting Reserved Concurrency to 0 is an instant emergency kill switch.
  • Provisioned Concurrency (Pre-Warmed Sandboxes, Continuous Cost): Tells Lambda to keep N microVMs booted with INIT already completed, eliminating cold starts for those N slots. You pay continuous GB-hour charges while idle plus execution fees. Traffic beyond N overflows into standard on-demand cold-start scaling unless capped by Reserved Concurrency.

4. Memory, vCPU Coupling & Power Tuning

Lambda exposes no CPU slider. You configure memory from 128 MB to 10,240 MB (in 1 MB steps), and AWS allocates vCPU, network bandwidth, and disk I/O proportionally—granting 1 full vCPU at 1,769 MB and up to 6 vCPUs at 10,240 MB.

Lambda bills duration rounded up to the nearest 1 ms in GB-seconds: $0.0000166667 per GB-second on x86_64, or ~20% cheaper at $0.0000133334 per GB-second on AWS Graviton2 (arm64), plus $0.20 per 1 million requests. Because doubling memory doubles vCPU:

  • CPU-bound workloads (JSON/Protobuf parsing, JWT verification, PDF/image transforms, JVM/Kotlin cold starts) often finish in less than half the time at 1,024 MB vs. 512 MB—delivering faster p99 latency at the same or lower monthly bill.
  • I/O-bound workloads (waiting 200 ms on DynamoDB or a third-party REST API) leave extra vCPU idle, so raising memory linearly increases cost with near-zero speedup.

Production Code Example: Static INIT Reuse & CDK Sizing

Notice how the handler keeps the AWS SDK v3 client and HTTP keep-alive agent outside handler() so INIT runs once per sandbox, while CDK pins arm64, memory sizing, Hyperplane VPC subnets, and concurrency controls: 

// 1. handler.mjs — Static INIT runs ONCE per Firecracker microVM
import { DynamoDBClient } from "@aws-sdk/client-dynamodb";
import { DynamoDBDocumentClient, GetCommand } from "@aws-sdk/lib-dynamodb";

// Reused across all warm invocations in this execution environment
const ddb = DynamoDBDocumentClient.from(new DynamoDBClient({}), {
  marshallOptions: { removeUndefinedValues: true },
});

export const handler = async (event) => {
  const orderId = event.pathParameters?.id;
  const { Item } = await ddb.send(new GetCommand({
    TableName: process.env.ORDERS_TABLE,
    Key: { orderId },
  }));
  return { statusCode: Item ? 200 : 404, body: JSON.stringify(Item ?? { error: "Not found" }) };
};

// 2. lambda-stack.ts (AWS CDK) — Graviton2, Hyperplane VPC, Reserved + Provisioned
const ordersFn = new lambda.Function(this, "OrdersReaderFn", {
  runtime: lambda.Runtime.NODEJS_20_X,
  architecture: lambda.Architecture.ARM_64,   // ~20% cheaper per GB-sec
  memorySize: 1024,                           // Tuned via Power Tuning (sweet spot)
  timeout: cdk.Duration.seconds(5),
  reservedConcurrentExecutions: 100,          // Protect downstream DB & isolate quota
  vpc,
  vpcSubnets: { subnetType: ec2.SubnetType.PRIVATE_WITH_EGRESS },
  securityGroups: [sharedLambdaSg],           // Reuse SG across functions to save ENIs
  code: lambda.Code.fromAsset("dist/orders"),
  handler: "handler.handler",
});

// Optional: keep 10 pre-initialized sandboxes warm for latency-critical mobile traffic
const prodAlias = ordersFn.addAlias("live", { provisionedConcurrentExecutions: 10 });
