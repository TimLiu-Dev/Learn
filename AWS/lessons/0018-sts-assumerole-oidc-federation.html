STS AssumeRole, Cross-Account Delegation & OIDC Federation

Shipping static AWS access keys (AKIA...) in mobile builds, containers, or CI secrets is a junior anti-pattern that turns a single leak into a full account compromise. Production AWS architectures run on short-lived credentials minted dynamically by AWS Security Token Service (STS)—via role assumption, cross-account ExternalId delegation, and OIDC token exchange.

Your Android Bridge

In Android, you never embed a privileged backend database secret inside your APK because anyone can run apktool and extract it. Instead, your app uses OAuth 2.0 / OIDC (via AppAuth or Credential Manager) to obtain a short-lived signed JWT, then exchanges it for scoped access tokens. AWS STS is the exact cloud counterpart: AssumeRole and AssumeRoleWithWebIdentity verify a caller's identity or signed OIDC JWT and return short-lived credentials (AccessKeyId starting with ASIA, SecretAccessKey, and a mandatory SessionToken) that automatically expire.

1. How STS Temporary Credentials Work (ASIA vs. AKIA)

Long-lived IAM User access keys begin with AKIA and remain valid forever until manually rotated or deactivated. By contrast, every credential issued by AWS STS begins with ASIA and bundles three values:

  • AccessKeyId (ASIA...) & SecretAccessKey: Used to compute the SigV4 HMAC signature on every AWS SDK request.
  • SessionToken (X-Amz-Security-Token): An encrypted, signed blob encoding the assumed role, session name, inline session policy, and exact expiration timestamp. Omitting it causes InvalidClientTokenId.
  • Bounded Lifetime (DurationSeconds): For sts:AssumeRole, sessions run from 900 seconds (15 minutes) up to the role's configured MaxSessionDuration (default 3,600 seconds / 1 hour, max 43,200 seconds / 12 hours).
Senior Gotcha: The 1-Hour Role Chaining Ceiling

When an already-assumed role (such as a Lambda execution role, ECS task role, or SSO session) calls sts:AssumeRole to assume a second role, AWS classifies this as role chaining. Role chaining hard-caps DurationSeconds at 3,600 seconds (1 hour)—even if the target role's MaxSessionDuration is 12 hours. Requesting DurationSeconds: 7200 in a chained call fails immediately with ValidationError.

Always configure SDKs to call regional STS endpoints (e.g., https://sts.us-east-1.amazonaws.com via AWS_STS_REGIONAL_ENDPOINTS=regional) rather than the legacy global endpoint sts.amazonaws.com. Regional endpoints reduce cross-continent RTT, provide regional fault isolation, and are mandatory for opt-in AWS Regions.

2. Cross-Account Delegation & The Confused Deputy Problem

Every IAM Role has two distinct policy halves: a Trust Policy (a resource-based policy answering who may assume the role) and Permissions Policies (answering what the assumed session may do). In cross-account delegation, access requires a two-way handshake:

  1. Account A (Caller): The caller's identity policy must explicitly allow sts:AssumeRole on Account B's Role ARN.
  2. Account B (Target): The target role's trust policy must explicitly allow Account A's principal (plus any required conditions).

Now consider the classic Confused Deputy vulnerability when delegating access to a multi-tenant third-party SaaS vendor (e.g., Datadog, CloudHealth, or a cost-auditing SaaS):

  1. Victim Co (Account 444455556666) creates an IAM Role trusting Vendor X's AWS account (111122223333) with no sts:ExternalId condition.
  2. Attacker Mallory creates a separate paid/trial account on Vendor X, guesses or discovers Victim Co's Role ARN (e.g., arn:aws:iam::444455556666:role/VendorReadOnly), and pastes it into Mallory's Vendor X integration form.
  3. Vendor X calls sts:AssumeRole on Victim Co's role. Because Victim Co's trust policy only checks "Is the caller Account 111122223333?", STS says Allow—tricking Vendor X into acting as a confused deputy and displaying Victim Co's AWS data inside Mallory's dashboard.

The Defense (sts:ExternalId): Vendor X must generate a unique, high-entropy ExternalId per tenant (never chosen by the user!) and store it server-side tied to that tenant's organization. When Victim Co creates its IAM Role, it adds "StringEquals": { "sts:ExternalId": "<vendor-issued-secret>" } to the trust policy. When Mallory triggers Vendor X to call Victim Co's Role ARN, Vendor X passes Mallory's ExternalId—which fails the trust condition with AccessDenied.

AWS Service Equivalent: When AWS services themselves (S3, SNS, EventBridge) invoke your Lambda or write to your SQS queue cross-service, they use aws:SourceAccount and aws:SourceArn instead of sts:ExternalId to prevent the exact same confused-deputy attack.

3. OIDC Federation & GitHub Actions (Zero Static Secrets)

Just as your Android app exchanges an OIDC ID token for temporary credentials (e.g., via Amazon Cognito Identity Pools calling AssumeRoleWithWebIdentity under the hood), your CI/CD runners should never hold static IAM keys. Instead, you register GitHub's OIDC Identity Provider (https://token.actions.githubusercontent.com) once per AWS account with audience sts.amazonaws.com.

At deploy time, the GitHub runner requests a short-lived signed JWT (valid ~5 minutes) containing claims such as iss, aud, and sub (for example, repo:acme-corp/orders-api:environment:production). The runner calls sts:AssumeRoleWithWebIdentity unauthenticated; STS fetches GitHub's public JWKS, validates the signature and expiration, and evaluates the role's trust policy conditions against the JWT claims.

Two Deadly OIDC Misconfigurations:

  • Omitting or wildcarding sub: Writing "StringLike": { "token.actions.githubusercontent.com:sub": "*" } lets any GitHub repository on the public internet assume your AWS role. Even "repo:acme-corp/*" lets a compromised or experimental repo in the org deploy to production, and failing to lock to :ref:refs/heads/main or :environment:production lets feature branches or pull-request workflows hijack production roles.
  • Omitting aud validation: Always pair sub with "StringEquals": { "token.actions.githubusercontent.com:aud": "sts.amazonaws.com" } so tokens minted for another relying party cannot be replayed against AWS STS.

4. Production Policies & GitHub Actions Workflow

Below are the two production trust policies—cross-account SaaS delegation with sts:ExternalId and tightly scoped GitHub Actions OIDC—alongside the workflow step that exchanges the JWT for ASIA... credentials: 

// 1. Cross-Account Vendor Role Trust Policy (Customer Account 444455556666)
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::111122223333:role/VendorCollectorRole" },
      "Action": "sts:AssumeRole",
      "Condition": {
        "StringEquals": {
          "sts:ExternalId": "ext-9f3c7a12-4b8e-4d19-92ab-710c8841e0f2"
        }
      }
    }
  ]
}

// 2. GitHub Actions OIDC Trust Policy (Production Deploy Role)
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::444455556666:oidc-provider/token.actions.githubusercontent.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
          "token.actions.githubusercontent.com:sub": "repo:acme-corp/orders-api:environment:production"
        }
      }
    }
  ]
}

# 3. GitHub Actions Workflow (.github/workflows/deploy-prod.yml)
permissions:
  id-token: write   # Required so runner can mint the signed OIDC JWT
  contents: read
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::444455556666:role/OrdersProdDeployRole
          aws-region: us-east-1
