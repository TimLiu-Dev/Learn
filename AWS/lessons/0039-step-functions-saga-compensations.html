AWS Step Functions: Standard vs. Express, Saga Pattern & Callback Tokens

A single checkout request touches inventory, fraud scoring, payment authorization, 3D Secure mobile verification, and shipping—yet distributed services cannot share an ACID database transaction. Learn when to orchestrate with Step Functions instead of choreographing events, how Standard and Express workflows differ on durability and cost, and how to build crash-proof Sagas and zero-polling .waitForTaskToken callbacks.

Your Android Bridge

In Android, a multi-screen checkout wizard pairs Jetpack Navigation with SavedStateHandle and WorkManager so that if the OS kills your app process while the user approves 3D Secure in their banking app, the flow resumes cleanly at the exact step where it paused. On AWS, an API Gateway + Lambda invocation dies after at most 29 seconds (or 15 minutes async) and loses all local stack memory. AWS Step Functions is your cloud-side durable state machine—persisting every transition so multi-step workflows and external callbacks survive process restarts, transient outages, and hours of waiting.

1. Orchestration vs. Choreography: Where Control Belongs

After learning EventBridge event buses, it is tempting to wire every multi-step workflow as a chain of loosely coupled events (choreography): OrderPlaced triggers Inventory, which emits InventoryReserved, which triggers Payment, and so on. Choreography shines across independent bounded contexts because adding a new consumer (like Analytics or Loyalty) requires zero edits to the producer.

Inside a single transactional business flow like checkout, however, pure choreography hides the workflow across half a dozen EventBridge rules and SQS queues. Answering "Which step failed for order #8492, and did we void the card authorization?" requires stitching distributed traces manually.

  • Orchestration (Step Functions): A central Amazon States Language (ASL) state machine explicitly defines step order, Retry policies, Catch rollback branches, parallel fan-out, and timeouts in one inspectable graph.
  • Choreography (EventBridge / SNS): Producers publish domain facts without knowing downstream subscribers. Best for decoupling separate teams and domains.
  • Senior Architecture Rule: Orchestrate inside a bounded context (e.g., an Order Checkout Saga), and choreograph across bounded contexts (the workflow's final state emits OrderConfirmed to EventBridge for shipping analytics, email, and warehouse projection).

2. Standard vs. Express Workflows (Semantics, Quotas & Cost)

Step Functions offers two distinct execution engines behind the same ASL syntax. Choosing the wrong one either blows up your AWS bill by 10× on high-throughput traffic or silently breaks long-running human callbacks and auditability.

Dimension Standard Workflows Express Workflows (Async / Sync)
Max Duration Up to 1 year (365 days) Up to 5 minutes
Execution Semantics Exactly-once workflow execution (each state transition persisted durably) Async: At-least-once (can duplicate on internal retry)
Sync: At-most-once (StartSyncExecution)
Pricing Model Per state transition ($0.025 per 1,000 transitions after 4,000/mo free) Executions + duration + memory ($1.00 per 1M requests + GB-second)
Service Integrations Supports all patterns, including .waitForTaskToken and .sync Fire-and-forget / Request-Response only (no .waitForTaskToken or .sync)
Audit & History 90-day visual & API execution history (GetExecutionHistory) No Step Functions history API; must ship logs to CloudWatch Logs

Two hard quotas govern real production designs according to the AWS Step Functions Service Quotas:

  • 256 KB State Payload Cap: Every state input and output is capped at 256 KB (262,144 bytes of UTF-8 JSON). Returning a large catalog list or PDF bytes triggers States.DataLimitExceeded and aborts the execution—use the Claim Check pattern (write payload to S3, pass { bucket, key } through states).
  • 25,000 Execution History Events (Standard): Every Standard state entry/exit appends history events up to a hard limit of 25,000 events per execution. Unbounded polling loops eventually crash; use .waitForTaskToken or restart via an outer workflow when processing massive batches.

3. The Saga Pattern: Forward Execution & Reverse Compensation

When your Android user taps Place Order, you cannot wrap DynamoDB inventory updates, Stripe card charges, and a third-party carrier API inside a database BEGIN ... COMMIT. Two-Phase Commit (2PC) locks external services indefinitely and collapses under partial network partitions. Instead, distributed systems use the Saga Pattern: a sequence of local transactions T1, T2, …, Tn, each paired with a semantic compensating action Ck.

Figure 1: When Step 3 fails, Step Functions catches the error and unwinds only previously completed compensatable steps in strict reverse (LIFO) order—never touching unexecuted Step 4.

Three production rules separate toy Sagas from battle-tested ones:

  1. Retry transient faults before compensating: Configure Retry with exponential backoff and JitterStrategy: "FULL" on transient errors (States.Timeout, HTTP 503, DynamoDB throttling), while immediately falling through to Catch on business errors like CardDeclined.
  2. Respect the Pivot Transaction: Steps before the irreversible pivot (e.g., ReserveStock, AuthorizeCard) are compensatable. Once the pivot transaction commits (e.g., CapturePayment or printing a non-voidable customs manifest), subsequent steps (e.g., SendReceipt) are retriable—you retry forward rather than trying to un-ring the bell.
  3. Never abort rollback if one compensation fails: If VoidCardAuth fails permanently, still execute ReleaseStock so inventory does not leak, and route the failed compensation metadata to an SQS Dead Letter Queue (DLQ) for operator reconciliation.
Critical Rule: Every Compensating Action Must Be Idempotent

Compensations can run twice—for example, when Step Functions retries a ReleaseStock Lambda after a response timeout, or when an operator replays a DLQ record. Key every compensation with a deterministic token (such as orderId + "#" + stepName) using a DynamoDB conditional write (attribute_not_exists(compensationKey)) so a duplicate invocation never double-increments inventory or double-refunds a customer.

4. Callback Pattern (.waitForTaskToken) & Production Code

Mobile checkouts frequently pause for asynchronous human or third-party events: 3D Secure banking verification, Stripe webhook confirmation, or warehouse pick-and-pack scans. Polling a database inside a Lambda every 10 seconds wastes compute and burns Step Functions state transitions.

Instead, append .waitForTaskToken to an integrated service ARN (such as arn:aws:states:::sqs:sendMessage.waitForTaskToken). Step Functions injects the opaque $$.Task.Token from the Context Object and freezes the Standard execution at zero compute cost until an external worker calls SendTaskSuccess or SendTaskFailure.

Always set TimeoutSeconds (and HeartbeatSeconds for active workers). Without TimeoutSeconds, a dropped webhook leaves the workflow dangling in RUNNING state for up to a full year before timing out. 

// 1. ASL State Machine Excerpt (Standard Workflow — Saga + Callback Token)
{
  "StartAt": "ReserveInventory",
  "States": {
    "ReserveInventory": {
      "Type": "Task",
      "Resource": "arn:aws:states:::lambda:invoke",
      "Parameters": { "FunctionName": "ReserveInventoryFn", "Payload.$": "$" },
      "ResultPath": "$.inventoryResult",
      "Retry": [{
        "ErrorEquals": ["States.Timeout", "Lambda.TooManyRequestsException"],
        "IntervalSeconds": 1, "MaxAttempts": 3, "BackoffRate": 2.0, "JitterStrategy": "FULL"
      }],
      "Catch": [{ "ErrorEquals": ["States.ALL"], "ResultPath": "$.errorInfo", "Next": "OrderFailed" }],
      "Next": "WaitFor3DSCallback"
    },
    "WaitFor3DSCallback": {
      "Type": "Task",
      "Resource": "arn:aws:states:::sqs:sendMessage.waitForTaskToken",
      "TimeoutSeconds": 900,
      "Parameters": {
        "QueueUrl": "https://sqs.us-east-1.amazonaws.com/123456789012/payment-3ds-requests",
        "MessageBody": { "orderId.$": "$.orderId", "taskToken.$": "$$.Task.Token" }
      },
      "ResultPath": "$.paymentResult",
      "Catch": [{
        "ErrorEquals": ["States.Timeout", "PaymentDeclined", "States.ALL"],
        "ResultPath": "$.errorInfo",
        "Next": "ReleaseInventory"
      }],
      "Next": "CreateShipment"
    },
    "ReleaseInventory": {
      "Type": "Task",
      "Resource": "arn:aws:states:::lambda:invoke",
      "Parameters": { "FunctionName": "ReleaseInventoryIdempotentFn", "Payload.$": "$" },
      "ResultPath": "$.compensationResult",
      "Next": "OrderFailed"
    },
    "OrderFailed": { "Type": "Fail", "Error": "CheckoutSagaRolledBack" }
  }
}

// 2. Webhook Handler (Node.js / AWS SDK v3) completing the paused Task Token
import { SFNClient, SendTaskSuccessCommand, SendTaskFailureCommand } from "@aws-sdk/client-sfn";
const sfn = new SFNClient({});

export async function handle3DSWebhook({ taskToken, approved, authId, declineReason }) {
  try {
    if (approved) {
      await sfn.send(new SendTaskSuccessCommand({
        taskToken,
        output: JSON.stringify({ authId, verifiedAt: new Date().toISOString() })
      }));
    } else {
      await sfn.send(new SendTaskFailureCommand({
        taskToken,
        error: "PaymentDeclined",
        cause: declineReason || "3DS challenge rejected by issuer"
      }));
    }
  } catch (err) {
    // TaskTimedOut or TaskDoesNotExist means TimeoutSeconds already triggered Saga rollback
    if (err.name === "TaskTimedOut" || err.name === "TaskDoesNotExist") return { ignored: true };
    throw err;
  }
}
