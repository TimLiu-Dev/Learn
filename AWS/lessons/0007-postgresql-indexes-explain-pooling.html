PostgreSQL Internals: B-Tree Indexes, EXPLAIN Plans & Connection Pooling

Adding an index in SQLite on Android masks slow queries on 5,000 local rows. On multi-tenant Amazon RDS PostgreSQL with 50 million rows and autoscaling ECS/Lambda callers, misunderstanding composite B-tree ordering, Visibility Map heap fetches, or process-per-connection memory turns a 4 ms lookup into an outage.

Your Android Bridge

In Android Room, you annotate @Entity(indices = [Index(value = ["userId", "createdAt"])]) on a local SQLite file opened by a single app process with zero network hops. In production AWS backends, Amazon RDS / Aurora PostgreSQL stores table rows (heap) and B-tree indexes in 8 KB pages across network-attached EBS volumes, verifies MVCC row visibility on every tuple, and forks an OS process (~5–10 MB RAM) for every open client connection.

1. Composite B-Tree Indexes & the Leftmost Prefix Rule

A PostgreSQL B-tree index stores sorted keys in a balanced tree of 8 KB pages (typically 3–4 levels deep even for 50 million rows). Leaf pages hold the indexed column values plus a physical tuple pointer called a ctid ((page_number, slot_index)) pointing to the row in the table heap.

When you create a composite index ON orders (tenant_id, status, created_at), entries are sorted lexicographically: first by tenant_id, ties broken by status, and ties broken by created_at. That sort order creates the leftmost prefix rule:

  1. Equality prefixes stay contiguous: WHERE tenant_id = 42 AND status = 'PAID' narrows directly to one contiguous slice of leaf pages, keeping created_at sorted inside that slice.
  2. The first range predicate stops prefix narrowing: In WHERE tenant_id = 42 AND created_at >= '2026-11-01' on (tenant_id, created_at, status), tenant_id = 42 and created_at >= ... use the tree, but any trailing column (status) is no longer sorted globally across the matched range—it can only be filtered row-by-row after scanning the range.
  3. Skipping a leading column breaks the tree lookup: WHERE status = 'PAID' (without tenant_id) cannot jump to one subtree because 'PAID' rows live inside every tenant_id subtree, forcing PostgreSQL toward a Seq Scan.
Figure 1: Put high-selectivity equality columns (tenant_id, status) first and range/sort columns (created_at) last in a composite B-tree index.

2. Reading EXPLAIN (ANALYZE, BUFFERS): Seq Scan vs. Index-Only Scan

Never optimize a PostgreSQL query from EXPLAIN alone—EXPLAIN only prints the planner's estimates, which drift badly if table statistics from ANALYZE are stale. Always run EXPLAIN (ANALYZE, BUFFERS) in staging or read replicas to see real execution times, actual row counts, and 8 KB page hits/reads:

  • Seq Scan (Sequential Scan): Reads every heap page in physical order (seq_page_cost = 1.0). Counterintuitively, a Seq Scan is faster than an Index Scan on tiny tables (<~50 pages) or when a query matches more than ~15%–20% of the table (low selectivity), because sequential I/O avoids bouncing across random heap pages (random_page_cost = 4.0 by default, often tuned to 1.1 on AWS GP3/io2 NVMe EBS).
  • Index Scan: Traverses the B-tree and follows each ctid to the table heap to check MVCC visibility (xmin/xmax) and fetch non-indexed columns. At 1%–10% selectivity, PostgreSQL often switches to Bitmap Index Scan + Bitmap Heap Scan to sort ctids and read each heap page once.
  • Index Only Scan & the Visibility Map: Using INCLUDE (total_cents) stores extra payload columns inside leaf pages so queries never need heap data. However, PostgreSQL B-tree leaves contain no MVCC visibility info. It skips the heap fetch only if the page's bit in the Visibility Map is marked all-visible (maintained by VACUUM / autovacuum). Watch Heap Fetches: 0 vs Heap Fetches: 184200 in your plan!

3. Connection Pooling Math: Process-Per-Connection vs. RDS Proxy

In Android, a single app uses one SQLite handle. In PostgreSQL, every client connection forks a dedicated OS backend process consuming roughly 5–10 MB of base RAM (plus per-query work_mem allocations for sorts/hashes). Accepting 2,000 direct connections from ECS tasks or AWS Lambda functions triggers two distinct failure modes:

  1. max_connections exhaustion & OOM: Connections fail with FATAL: remaining connection slots are reserved or exhaust instance memory before CPU even hits 100%.
  2. CPU & lock thrashing: Even if RAM holds out, having far more actively executing queries than roughly 2x to 4x the instance's vCPUs causes heavy context switching and kernel/lightweight lock contention (such as ProcArrayLock).
Figure 2: A transaction pooler shields PostgreSQL from thousands of idle app sockets, but cannot fix CPU saturation if too many queries run concurrently.
Golden Rule for Pool Sizing & Proxy Limits

Never set application pool size blindly to 100 per container. Calculate instances × pool_per_instance before deploying: if it exceeds ~80% of max_connections, insert Amazon RDS Proxy or PgBouncer (transaction mode), and cap active concurrent queries near 2–4 × db_vcpus with queue timeouts.

4. Code Example: Production Index DDL & Pool Sizing

Compare the Android Room index you write locally with the zero-blocking DDL, query diagnostic, and pool sizing required in production on AWS: 

-- 1. Production PostgreSQL: build covering composite index WITHOUT locking writes
CREATE INDEX CONCURRENTLY idx_orders_tenant_status_created_cov
  ON orders (tenant_id, status, created_at DESC)
  INCLUDE (total_cents);

-- 2. Verify Index-Only Scan + zero heap fetches + shared buffer cache hits
EXPLAIN (ANALYZE, BUFFERS)
SELECT tenant_id, created_at, total_cents
FROM orders
WHERE tenant_id = 42 AND status = 'PAID' AND created_at >= NOW() - INTERVAL '7 days'
ORDER BY created_at DESC
LIMIT 50;

// 3. Backend Pool Sizing (Node.js pg / ECS behind RDS Proxy on 8-vCPU RDS)
// 40 ECS tasks * max 5 = 200 client sockets -> multiplexed by RDS Proxy to ~32 PG backends
const pool = new Pool({
  host: process.env.RDS_PROXY_ENDPOINT,
  max: 5,                       // Keep per-task pool small; avoid connection storms
  connectionTimeoutMillis: 2000 // Fail fast instead of piling up blocked requests
});

Why CONCURRENTLY Matters A plain CREATE INDEX holds a SHARE lock that blocks all INSERT, UPDATE, and DELETE writes until finished. CREATE INDEX CONCURRENTLY takes two passes without blocking writes.
Pinning in RDS Proxy If your ORM runs session-level SET search_path or creates temporary tables, RDS Proxy pins that client to one backend process for the session—defeating multiplexing!
Tune random_page_cost PostgreSQL's default random_page_cost = 4.0 assumes spinning HDDs. On AWS GP3/io2 SSDs, lowering it toward 1.1–1.5 helps the planner pick indexes accurately.
