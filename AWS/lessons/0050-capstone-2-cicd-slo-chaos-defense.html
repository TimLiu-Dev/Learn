1. Zero-Secret CI/CD with GitHub Actions OIDC & Canary Rollbacks

Junior cloud setups paste long-lived IAM user access keys (AKIA...) into GitHub Repository Secrets. If a secret leaks in a build log or third-party GitHub Action, an attacker holds permanent credentials until someone manually rotates them. Senior AWS teams ban static CI/CD keys entirely and federate via IAM OIDC Identity Providers + sts:AssumeRoleWithWebIdentity.

  1. Signed Short-Lived Assertion: When a workflow runs with id-token: write, GitHub’s OIDC provider signs a JWT containing claims for aud (sts.amazonaws.com) and sub (exact repo, branch, or protected environment).
  2. Split-Privilege Roles: Pull requests assume a read-only ci-plan-role (runs tfsec / cdk-nag and terraform plan). Only protected main merges approved for the production environment may assume ci-deploy-prod-role.
  3. Failure Mode — Unscoped sub Trust: If your IAM trust policy checks only aud and omits a strict sub condition, any GitHub repository on the public internet can request an OIDC token and assume your AWS deploy role.
  4. Canary Deploy + Auto-Rollback: Once Terraform/CDK updates infrastructure, CodeDeploy shifts ECS Fargate traffic via Canary10Percent5Minutes (or Linear10PercentEvery1Minute) behind the ALB, rolling back in under 60 seconds if the CloudWatch 5xx rollback alarm fires.

2. SLO Dashboards, Multi-Window Burn Rates & FinOps Guardrails

Alerting on CPU > 80% wakes engineers up at 3:00 AM when traffic is completely healthy, yet stays silent when a bad IAM policy or Aurora connection leak returns HTTP 500 at 2% CPU. Instead, define symptom-based SLIs tied to user pain on your checkout API:

  • Availability SLI: 1 - (5xx_count / valid_request_count) targeting a 99.9% monthly SLO. Over a 30-day (43,200-minute) window, your total error budget is exactly 43.2 minutes of full downtime (or 0.1% of all requests).
  • Latency SLI: Percentage of POST /orders requests completing with ALB TargetResponseTime ≤ 250 ms (p99 target 99.0%).
  • Multi-Window Burn-Rate Alerting: Following the Google SRE Workbook multi-burn-rate pattern, a single 5-minute spike pages on transient flaps, while a slow 1-hour window lingers long after mitigation. Pair a 1-hour window with a 5-minute confirmation window, both exceeding a 14.4× burn rate (1.44% error rate for a 99.9% SLO, burning 2% of the 30-day budget in 1 hour). Only page on-call when both windows breach simultaneously; route slower 3× (6-hour) burns to a Slack/Jira ticket.
  • FinOps Guardrails: Attach AWS Budgets forecasted-spend alarms at 80% and 100% of monthly baseline, enforce mandatory tags (env, service, owner, cost-center) via Terraform default tags and AWS Organizations Tag Policies, and expire old CloudWatch logs + S3 artifacts via lifecycle rules.

3. Production Code: GitHub OIDC Trust Policy, Workflow & SLO Burn-Rate Alarm

Review how the three core guardrails lock together in production: the IAM trust policy scoped to your exact GitHub environment, the split plan/apply workflow, and the CloudWatch Metric Math expression enforcing the 14.4× burn-rate gate. 

// 1. IAM Role Trust Policy (Terraform/JSON) — strictly scoped by aud + sub
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com" },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
        "token.actions.githubusercontent.com:sub": "repo:acme/cloud-saas-platform:environment:production"
      }
    }
  }]
}

# 2. .github/workflows/deploy-prod.yml (OIDC deploy, zero long-lived keys)
permissions:
  id-token: write
  contents: read
jobs:
  deploy:
    environment: production
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/ci-deploy-prod-role
          aws-region: us-east-1
      - run: terraform apply -auto-approve -input=false

4. Chaos Drill: Proving Multi-AZ Failover with AWS FIS

An architecture diagram showing two Availability Zones is a hypothesis until you break one in staging or controlled production. AWS Fault Injection Service (FIS) injects real infrastructure faults—network ACL blackholes, ECS task stops, and Aurora DB cluster failovers—while enforcing automated Stop Conditions tied to CloudWatch alarms.

Three Failure Modes Caught Only by Chaos Drills
  • Single-AZ Capacity Cliff: Running 2 ECS tasks total at 75% CPU looks fine in normal traffic. Killing AZ-A shifts 100% of traffic onto the lone AZ-B task (150% CPU load), triggering OOM kills and 503s before Auto Scaling spins up replacement containers (60–90s). Fix: maintain N + 1 headroom (~50% baseline CPU across ≥ 2–3 AZs).
  • Stale Aurora Writer DNS Caching: Aurora Multi-AZ failover typically takes 35–60 seconds to promote a reader. Services caching DNS forever keep writing to the old read-only primary IP. Fix: route ECS through RDS Proxy (failover cutover < 5–15s) or bound client DNS TTL + pool max-lifetime.
  • Missing FIS Stop Conditions: Always attach a CloudWatch Alarm stop condition (e.g., 5xx > 5% for 2 minutes or p99 > 1,500 ms) so an experiment aborts automatically if blast radius exceeds your hypothesis.
