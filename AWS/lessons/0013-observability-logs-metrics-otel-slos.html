Observability: Structured Logs, RED/USE Metrics, OpenTelemetry & SLOs

Logging plain-text lines to stdout and watching average CPU graphs leaves you blind during real cloud incidents. Senior engineers connect distributed requests across Android clients, load balancers, and containers using structured JSON logs, RED/USE histogram metrics, W3C Trace Context, and SLO burn-rate alerts.

Your Android Bridge

In Android, you use Timber.d("Checkout failed for %s", orderId) in Logcat and attach FirebaseCrashlytics.setCustomKey("userTier", tier) so every crash report carries breadcrumbs from that single phone. In AWS, one user tap fans out across an ALB, multiple ECS containers, SQS queues, and PostgreSQL—interleaving logs from thousands of concurrent callers. Structured JSON logs are Timber with a strict machine-readable schema, and an OpenTelemetry traceId is the distributed Crashlytics custom key that stitches every hop back into one timeline.

1. Structured JSON Logs & CloudWatch Logs Insights

Plain-text log lines like 2026-11-15 ERROR Checkout failed for user=8821 timeout=2000ms fail in production for two reasons: multi-line stack traces split into separate log events, and every team invents slightly different spacing that breaks regex parsers.

Instead, emit one single-line JSON object per log event to stdout/stderr (which the AWS ECS awslogs driver or Fluent Bit ships to CloudWatch Logs). Every line carries fixed correlation fields:

  • timestamp (ISO-8601 UTC), level (INFO/WARN/ERROR), and service (orders-api).
  • traceId and spanId so you can jump from a single failing request to all logs emitted across every microservice.
  • route (parameterized template like /v1/orders/:id), statusCode, and durationMs.
  • Redacted context only: never log Authorization headers, JWTs, passwords, or raw credit card numbers—scrub them in the logger middleware before serialization.

At $0.50 per GB ingested in CloudWatch Logs Standard (us-east-1), verbose DEBUG dumps on every 200 OK silently blow up your AWS bill. Emit one canonical log line per request at INFO (or ERROR on failure) instead of 15 scattered debug prints. Then query billions of events in seconds using CloudWatch Logs Insights: 

fields @timestamp, traceId, route, statusCode, durationMs, err.code
| filter service = "orders-api" and statusCode >= 500
| sort @timestamp desc
| limit 50

2. RED vs. USE Metrics & Why Averages Lie (p50, p95, p99)

Logs tell you what happened on a specific request; metrics tell you how much and how fast across the whole fleet at low cost. Use two complementary frameworks:

  • RED Method (Request-Driven Services): Track Rate (requests/sec), Errors (5xx/sec), and Duration (latency distribution) for every HTTP endpoint or RPC handler.
  • USE Method (Infrastructure Resources): For CPUs, memory, DB connection pools, and EBS volumes, track Utilization (% busy), Saturation (queue depth or thread waits), and Errors (dropped packets, OOM kills).

Why mean latency hides outages: Suppose 99 requests complete in 15 ms, while 1 request hits a PostgreSQL lock wait and stalls for 2,015 ms. The arithmetic mean is 35 ms—your dashboard looks green—yet p99 is >2,000 ms. At 1,000 req/s, 10 users every second experience a multi-second freeze (and if a mobile screen triggers 5 API calls on launch, roughly 1 - 0.99^5 ≈ 4.9% of app opens hit that p99 tail!).

The Percentile Aggregation Trap

You cannot average percentiles across containers (avg(p99) across 10 ECS tasks is mathematically invalid—1 busy task having a 3-second spike gets diluted by 9 idle tasks). Always export histograms (bucket counts such as ≤25ms, ≤100ms, ≤500ms, +Inf) so your metrics backend merges bucket counts first and computes true fleet-wide p95 and p99.

3. OpenTelemetry & W3C traceparent Propagation

OpenTelemetry (OTel) gives you vendor-neutral SDKs and a Collector so you can export to AWS X-Ray, CloudWatch, Honeycomb, or Grafana Tempo without rewriting application code.

Cross-service correlation relies on the W3C Trace Context HTTP header traceparent: 

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  └────────── 32-hex traceId ─────────┘ └─ 16-hex spanId ─┘ │
             version (00)                                           flags (01 = sampled)

Sampling tradeoffs (Head vs. Tail): Tracing 100% of requests at 10,000 req/s costs more than your database. Two strategies exist:

  • Head-based sampling: Decided at the first hop (e.g., keep 5% via bit 01 in traceFlags). Cheap and stateless, but discards 95% of rare 500 errors before you even know they failed.
  • Tail-based sampling: Your ECS apps export all spans to an OTel Collector, which buffers each trace for a few seconds and keeps 100% of error or slow (>p95) traces while keeping only 1–5% of healthy fast traces.

4. SLIs, SLOs, Error Budgets & Multi-Window Burn-Rate Alerts

Paging an on-call engineer at 3:00 AM because "CPU hit 82%" or "two requests returned 500" causes alert fatigue. Google SRE SLO alerting replaces arbitrary thresholds with user-impact math:

  • SLI (Indicator): Measured ratio of good events to total valid events (e.g., non-5xx responses under 300 ms / all requests).
  • SLO (Objective): Target over a rolling window, such as 99.9% over 30 days (43,200 minutes).
  • Error Budget: 1 - SLO = 0.1% (0.001). At 100 req/s (259.2M requests/month), your budget is 259,200 failed requests (equivalent to 43.2 minutes of total outage).

Burn Rate measures how fast you consume that budget relative to a steady 30-day pace: burnRate = observedErrorRate / (1 - sloTarget).

  • 1x burn rate: 0.1% errors consumes 100% of the budget in exactly 30 days.
  • 14.4x burn rate (1.44% errors on a 99.9% SLO): Consumes 2% of your 30-day budget in 1 hour (exhausts the entire month's budget in 50 hours) → PAGE immediately.
  • 6x burn rate (0.6% errors): Consumes 5% of your 30-day budget in 6 hours → create an urgent TICKET.

Always pair a long window with a short confirmation window (e.g., 1 hour AND 5 minutes both ≥ 14.4x). Without the short window, an alert stays firing for 55 minutes after you already rolled back a bad deploy; without the long window, a 30-second deploy blip wakes up the team.

5. Production Code Example: Trace-Correlated Logger + CloudWatch EMF

Here is how a Node.js/TypeScript backend binds the incoming W3C traceparent into AsyncLocalStorage so every log line automatically carries traceId, while emitting zero-overhead CloudWatch Embedded Metric Format (EMF) metrics to stdout: 

import { AsyncLocalStorage } from "node:async_hooks";

interface TraceCtx { traceId: string; spanId: string; }
const traceStore = new AsyncLocalStorage<TraceCtx>();

export function logJson(level: "INFO" | "WARN" | "ERROR", msg: string, fields: Record<string, unknown> = {}) {
  const ctx = traceStore.getStore();
  // Redact sensitive keys before writing to stdout
  const safeFields = { ...fields };
  delete safeFields.authorization;
  delete safeFields.password;

  console.log(JSON.stringify({
    timestamp: new Date().toISOString(),
    level,
    service: "orders-api",
    traceId: ctx?.traceId ?? "untraced",
    spanId: ctx?.spanId ?? "none",
    msg,
    ...safeFields,
  }));
}

// CloudWatch EMF line: parsed asynchronously by CloudWatch into RED metrics (no network call on hot path)
export function emitRedEmf(route: string, statusCode: number, durationMs: number) {
  console.log(JSON.stringify({
    _aws: {
      Timestamp: Date.now(),
      CloudWatchMetrics: [{
        Namespace: "OrdersService/Prod",
        Dimensions: [["Route"]], // Keep Route bounded (e.g. "/v1/orders/:id"), NEVER raw orderId!
        Metrics: [
          { Name: "LatencyMs", Unit: "Milliseconds" },
          { Name: "ServerErrors", Unit: "Count" },
        ],
      }],
    },
    Route: route,
    LatencyMs: durationMs,
    ServerErrors: statusCode >= 500 ? 1 : 0,
  }));
}

High-Cardinality Trap Never put unbounded IDs (userId, orderId, traceId) into metric dimensions. Each unique combination creates a new paid time series. Put bounded routes (/orders/:id) in metrics, and put high-cardinality IDs in structured logs and trace attributes.
Why CloudWatch EMF? Pushing metrics synchronously via PutMetricData API calls adds latency and rate-limit risk to every request. Writing EMF JSON to stdout lets the CloudWatch agent aggregate and ship metrics out-of-band.
