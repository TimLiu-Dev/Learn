Production CI/CD: GitHub Actions + AWS OIDC, Canary Deployments & Rollbacks

Shipping cloud services safely requires two orthogonal defenses: eliminating static long-lived AWS credentials from CI runners via OIDC federation, and replacing all-or-nothing deploys with automated canary traffic shifting wired to CloudWatch rollback alarms.

Your Android Bridge

In Google Play Console, you never push a risky release straight to 100% of devices—you run a staged rollout (5% → 20% → 100%), watch Android Vitals crash rates, and click Halt if crashes spike. On AWS, CodeDeploy (with ALB target-group weights or Lambda aliases) automates that exact staged rollout via configurations like Canary10Percent5Minutes, while CloudWatch Alarms act as your automated Vitals watchdog—rolling back to 100% Blue in seconds if 5xx errors breach threshold. Meanwhile, GitHub Actions OIDC replaces static IAM access keys with short-lived STS tokens, just as Play App Signing separates your upload key from the production signing key.

1. Killing Static IAM Keys with GitHub Actions OIDC

Legacy CI/CD pipelines stored an IAM user's AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY in GitHub repository secrets. Those keys never expire unless manually rotated; if leaked through a debug print, compromised third-party Action, or misconfigured pull-request workflow, an attacker keeps persistent access to your AWS account.

With IAM OpenID Connect (OIDC) federation, GitHub acts as an identity provider and AWS Security Token Service (STS) issues short-lived session credentials (default 1 hour, configurable down to 15 minutes / 900 seconds) on every job run:

  1. Workflow JWT Request: Because the job declares permissions: { id-token: write }, the GitHub runner requests a signed OIDC JSON Web Token from https://token.actions.githubusercontent.com.
  2. Verifiable Claims: The JWT embeds signed claims including aud: "sts.amazonaws.com" and sub: "repo:acme/orders-api:environment:production" (or ref:refs/heads/main).
  3. STS Exchange: aws-actions/configure-aws-credentials calls sts:AssumeRoleWithWebIdentity with that JWT and your target Role ARN—zero static secrets stored anywhere.
  4. Trust Policy Verification: AWS verifies the JWT signature against GitHub's JWKS endpoint and evaluates your IAM Role's Condition block before returning temporary credentials.
Critical OIDC Failure Mode: Over-Broad sub Conditions

Never trust "token.actions.githubusercontent.com:sub": "repo:acme/*" or omit the sub condition on a production deploy role. Without strict pinning, any branch, sandbox repo, or pull_request_target workflow in your org can mint a valid JWT and assume production admin privileges. Pin production roles to a GitHub Environment claim (repo:acme/orders-api:environment:production) backed by required human reviewers and branch protection rules.

2. Canary Traffic Shifting & CodeDeploy Mechanics

Once CI builds and pushes an artifact (a container image to ECR or a Lambda zip), AWS CodeDeploy controls how production traffic moves from the incumbent Blue (v1) revision to the new Green (v2) revision:

  • Canary10Percent5Minutes: Shifts 10% of requests to Green for a 5-minute bake window while 90% stays on Blue. If zero rollback alarms fire after 5 minutes, CodeDeploy shifts the remaining 90% at once. (Variants include 10Percent10Minutes, 10Percent15Minutes, and 10Percent30Minutes.)
  • Linear10PercentEvery1Minute: Advances traffic in equal increments (+10% every 1 minute, finishing in 10 minutes). Prefer Linear when Green needs gradual cache warming or autoscaling; prefer Canary when you want a fixed low blast radius (10%) to catch startup crashes or bad configuration quickly.
  • AllAtOnce: Cuts 100% of traffic over immediately—appropriate only for dev/staging environments where speed outweighs blast-radius isolation.

3. CloudWatch Alarm Rollbacks & Production Traps

As detailed in the Amazon Builders' Library guide to safe hands-off deployments, a canary pipeline is only as trustworthy as the signals gating promotion. Three operational failure modes bite teams in production:

  1. Low-Traffic Blindness & TreatMissingData: At 3:00 AM, a 10% canary may receive only 2 requests per minute. If your alarm sets TreatMissingData: breaching, quiet minutes trigger false rollbacks; if it uses a raw error count (5xx > 0) without a minimum request floor, 1 transient error causes 100% rollback, whereas missing with zero traffic lets broken code promote blindly. Fix: Use a CloudWatch Metric Math error-rate expression (100 * m_5xx / m_requests), require DatapointsToAlarm: 2 of 3 1-minute periods, and keep synthetic canary traffic (Route 53 / CloudWatch Synthetics) hitting critical paths continuously.
  2. Premature Blue Termination: If CodeDeploy terminates Blue ECS tasks immediately when Green reaches 100%, a slow-burn bug discovered 15 minutes later (such as a connection-pool leak or deadlock) forces ECS to cold-boot Blue tasks from scratch. Fix: Set TerminationWaitTimeInMinutes (e.g., 30–60 minutes for stateless ECS services) so reverting to Blue is an instant ALB listener weight change.
  3. Absolute Count vs. Percentage Alarms: An absolute alarm like HTTPCode_Target_5XX_Count > 5 breaks both ways—too sensitive at peak traffic (50,000 req/min) and blind at off-peak (20 req/min). Always alarm on percentage error rate and p99 latency together.

4. Production Code: IAM OIDC Trust Policy & GitHub Workflow

Below is a production-hardened IAM Role Trust Policy paired with a GitHub Actions workflow that exchanges an OIDC JWT for 15-minute STS credentials and triggers a CodeDeploy deployment: 

// 1. IAM Role Trust Policy (Terraform/JSON) — pinned to ONE repo + production environment
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
          "token.actions.githubusercontent.com:sub": "repo:acme/orders-api:environment:production"
        }
      }
    }
  ]
}

# 2. .github/workflows/deploy-prod.yml
permissions:
  id-token: write   # Required to mint GitHub OIDC JWT
  contents: read    # Least-privilege checkout only

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production   # Enforces required reviewers + matches IAM sub claim
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/gha-orders-prod-deploy
          aws-region: us-east-1
          role-duration-seconds: 900   # 15-minute short-lived STS session
      - name: Trigger CodeDeploy Canary10Percent5Minutes
        run: |
          aws deploy create-deployment \
            --application-name orders-api-ecs \
            --deployment-group-name orders-prod-dg \
            --deployment-config-name CodeDeployDefault.ECSCanary10Percent5Minutes \
            --revision file://appspec-revision.json

Why id-token: write Matters GitHub Actions scopes GITHUB_TOKEN permissions per workflow. Explicitly granting id-token: write while keeping contents: read ensures the job can mint an OIDC JWT without accidentally getting write access to your repository code.
Canary vs. Linear Tradeoff Use Canary10Percent5Minutes when fast failure detection with bounded 10% blast radius matters most. Use Linear10PercentEvery1Minute when cold JVMs, connection pools, or auto-scaling targets need a gradual traffic ramp.
