Caching Patterns: Cache-Aside, Write-Through, TTL Jitter & Stampedes

A cache turns 30 ms database queries into 1 ms memory reads—until a single expired hot key sends 5,000 concurrent requests straight into PostgreSQL at once. Learn how distributed caching on AWS differs from Android's device-local OkHttp and Coil caches, and how to engineer stampede-proof cache-aside layers.

Your Android Bridge

In Android, you rely on OkHttp's disk Cache (respecting Cache-Control: max-age) and Coil's two-tier MemoryCache + DiskCache. Those caches live inside one user's phone: if an entry expires, only that single device hits the network. In AWS, an Amazon ElastiCache (Redis / Valkey) cluster sits in front of your database for every user simultaneously. One expired key or cold cache node exposes RDS PostgreSQL or DynamoDB to the combined concurrency of your entire fleet—a failure mode called a cache stampede (or thundering herd).

1. Cache-Aside vs. Write-Through vs. Write-Behind

In the AWS Database Caching Strategies Using Redis whitepaper, three canonical topologies govern how application servers coordinate Redis and the primary database:

  • Cache-Aside (Lazy Loading): Your API checks Redis first (~0.5–1.5 ms inside a VPC). On a hit, it returns immediately. On a miss, the API queries the database (~10–50 ms), writes the result to Redis with a TTL, and returns it.
    Tradeoff: Only actively read keys consume expensive RAM, and a Redis outage degrades latency instead of blocking writes. However, cold misses pay full DB latency, and if a write updates the DB and fails to DEL the stale cache key, readers see stale data until the TTL expires.
  • Write-Through: Every application write updates the cache and the primary database synchronously in the write path (e.g., via your repository layer or Amazon DynamoDB Accelerator (DAX)).
    Tradeoff: Cache entries stay warm and consistent with recent writes, eliminating cold misses on newly created items. The cost is higher write latency (two network hops) and wasted Redis memory storing keys that may never be read unless paired with TTLs and eviction.
  • Write-Behind (Write-Back): Writes land in the cache immediately and acknowledge to the client, while a background worker batches and flushes dirty entries to the database asynchronously.
    Tradeoff: Blazing write throughput (coalescing 1,000 counter increments into 1 SQL UPDATE), but if a cache node crashes before flushing, acknowledged writes are permanently lost. Never use write-behind for financial balances or orders.

2. Thundering Herds & Why TTL Jitter Is Mandatory

Suppose a cron job warms 200,000 user feed keys in ElastiCache at 08:00:00 with an exact 15-minute TTL (900 s). At 08:15:00, all 200,000 keys expire in the same second. Thousands of mobile clients suddenly experience simultaneous cache misses, slamming RDS PostgreSQL with identical queries. As DB connections saturate, query latency climbs from 15 ms to 5,000 ms, mobile clients time out and retry, and the database enters a death spiral.

TTL Jitter solves synchronized multi-key expiration waves by adding bounded randomness to every TTL at write time:

ttlMs = baseTtlMs + Math.round(Math.random() * jitterMs)

Instead of 200,000 keys expiring at second 900, adding 0–180 s of jitter spreads those refreshes smoothly across a 3-minute window, keeping RDS CPU flat. As documented in the Amazon Builders' Library: Caching challenges and strategies, jitter decouples batch populations from synchronized load spikes—just like jittered backoff prevents retry storms.

3. Single-Flight, Negative Caching & Hot-Key Traps

A common senior interview mistake is claiming that TTL jitter alone stops all stampedes. Jitter staggers different keys—it does nothing when 4,000 requests hit the exact same hot key (product:999) within the 20 ms window while it is missing! To stop single-key stampedes, combine three defenses:

  1. Single-Flight Request Coalescing: Maintain an in-process map of active loads keyed by cache key (inFlight.get(key)). When 500 concurrent requests inside an ECS container miss on product:999, only the first request queries Redis/RDS; the other 499 attach to the same in-flight promise/waiter list and share the result. Across 20 ECS containers, 10,000 concurrent misses collapse to at most 20 DB queries.
  2. Negative Caching (Stopping Cache Penetration): If a buggy client or attacker floods GET /users/-1 (an ID that does not exist in PostgreSQL), naive cache-aside skips writing to Redis because the DB returned null. Every request pierces straight through to RDS. Fix this by validating IDs upfront and caching explicit null sentinel values with a short TTL (e.g., 30–60 s).
  3. L1 Micro-Cache & Redis Eviction Policy: Even at a 99.9% hit rate, one viral celebrity key routed to a single Redis shard can saturate that shard's network interface. Adding a 1–5 second in-process L1 LRU map on ECS absorb viral bursts. Meanwhile, configure ElastiCache maxmemory-policy intentionally: use volatile-lru if Redis holds both session tokens (no TTL) and cache keys (with TTL), or allkeys-lru when Redis is dedicated purely to caching.
Always Clean Up the In-Flight Map on Failure

If the single-flight leader's DB query throws an error and you forget to remove key from inFlight inside a finally block (or before invoking error callbacks), every future request for that key hangs onto the dead promise forever. Never cache transient DB errors, and always delete the in-flight entry before resolving or rejecting waiters.

4. Production Code: Android Device Cache vs. Cloud Single-Flight

Notice how Android caches per-device HTTP responses cleanly via OkHttp/Coil, while the cloud API must coalesce concurrent misses across thousands of users and add TTL jitter on Redis writes: 

// 1. Android Client (Kotlin) — OkHttp + Coil cache per device
val httpCache = Cache(File(context.cacheDir, "http_cache"), maxSize = 50L * 1024 * 1024)
val okHttp = OkHttpClient.Builder().cache(httpCache).build()

val imageLoader = ImageLoader.Builder(context)
    .okHttpClient(okHttp) // Honors Cache-Control: max-age + ETag per device
    .build()

// 2. Cloud Backend (TypeScript / Redis) — Cache-Aside + Single-Flight + TTL Jitter
const inFlight = new Map<string, Promise<Product | null>>();

export async function getProduct(id: string): Promise<Product | null> {
  const key = `product:${id}`;
  const cached = await redis.get(key);
  if (cached !== null) {
    return cached === "__NULL__" ? null : JSON.parse(cached);
  }

  let pending = inFlight.get(key);
  if (!pending) {
    pending = (async () => {
      const row = await db.queryProduct(id);
      if (!row) {
        await redis.set(key, "__NULL__", "EX", 30); // Short negative cache
        return null;
      }
      const jitterSec = Math.floor(Math.random() * 120); // 0-120s jitter
      await redis.set(key, JSON.stringify(row), "EX", 600 + jitterSec);
      return row;
    })().finally(() => {
      inFlight.delete(key); // Critical: always release even on DB error
    });
    inFlight.set(key, pending);
  }
  return pending;
}
