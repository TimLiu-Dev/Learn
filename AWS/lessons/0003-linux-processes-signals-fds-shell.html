Linux Processes, Signals (SIGTERM), File Descriptors & DNS Tools

On Android, the OS manages your app lifecycle via callbacks and kills background processes silently. In the cloud, your backend container is Linux PID 1: mishandling SIGTERM causes 30-second deploy stalls and 502 errors, leaking sockets triggers EMFILE outages at low CPU, and blind DNS lookups double latency.

Your Android Bridge

On Android, ProcessLifecycleOwner and Service.onDestroy() notify you to flush state before Android's Zygote / ActivityManager terminates your process—and if you forget to close a Cursor or ParcelFileDescriptor, Android StrictMode warns about leaked file descriptors. On AWS ECS and EKS, Linux signals (SIGTERM → SIGKILL) play the role of onDestroy(), your container entrypoint runs as PID 1, and every open socket shares a hard kernel budget enforced by ulimit -n.

1. Container PID 1 & Graceful Shutdown (SIGTERM vs. SIGKILL)

When AWS ECS or Kubernetes replaces a container during a rolling deploy or scale-in event, it does not magically wait for user requests to finish. Instead, the orchestrator follows a strict two-stage POSIX signal contract:

  1. Step 1 — SIGTERM (Signal 15, catchable): Sent immediately when termination begins. A healthy backend catches SIGTERM, flips its health/readiness endpoint to 503 so the ALB stops routing new traffic, stops accepting new sockets, waits for active in-flight requests to finish, closes database pools, and exits with code 0.
  2. Step 2 — Grace Period Expiration → SIGKILL (Signal 9, uncatchable): If the process is still alive after stopTimeout on AWS ECS (default 30 seconds, configurable up to 120 seconds) or terminationGracePeriodSeconds on EKS (default 30 seconds), the kernel destroys it instantly with exit code 137 (128 + 9). Any in-flight HTTP call is severed with TCP RST, producing HTTP 502 Bad Gateway errors for clients.
The Dockerfile Shell-Form CMD Trap (PID 1 Swallows SIGTERM)

In Linux, PID 1 ignores default signal actions unless it explicitly registers a signal handler. If your Dockerfile uses shell form (CMD node dist/server.js), Docker spawns /bin/sh -c "node dist/server.js" as PID 1 and node as PID 7. Because /bin/sh does not forward SIGTERM to child processes, your Node server never hears the shutdown signal. Every deployment stalls for the full 30-second stopTimeout before ECS fires SIGKILL. Always use exec form (CMD ["node", "dist/server.js"]) or an init shim such as tini.

Figure 1: Exec-form containers receive SIGTERM directly and exit cleanly before stopTimeout. Shell-form containers trap SIGTERM in /bin/sh until the kernel issues SIGKILL.

2. Everything Is a File Descriptor (ulimit -n & EMFILE Outages)

In Linux, almost every I/O resource is tracked in a per-process file descriptor (FD) table: standard streams (0 stdin, 1 stdout, 2 stderr), loaded shared libraries, open log files, epoll event loops, and every single TCP or UDP socket (both inbound client connections from the ALB and outbound connections to RDS, Redis, or DynamoDB).

The kernel caps how many FDs a process can hold open concurrently via RLIMIT_NOFILE (inspected in the shell with ulimit -Sn for the soft limit and ulimit -Hn for the hard limit). On many base Linux distributions and older Docker daemon defaults, the soft limit is just 1,024 file descriptors.

Consider a microservice with a seemingly modest footprint:

  • 60 baseline FDs (runtime libraries, log files, epoll, pipes)
  • 450 concurrent client TCP sockets behind an ALB
  • 450 outbound upstream/database sockets (1:1 fan-out during a slow downstream call)
  • 100 leaked sockets stuck in CLOSE_WAIT because an exception path skipped socket.close()

Total = 1,060 FDs. The moment the process crosses 1,024, the next accept() or socket() system call fails immediately with EMFILE: Too many open files. Your metrics dashboard shows CPU at 18% and RAM at 35%, yet the service refuses every new connection and fails ALB health checks.

3. Production Shell Diagnostics: DNS (dig) & Sockets (ss, lsof)

When an ECS task or EC2 instance misbehaves in production, senior engineers skip guesswork and inspect the kernel and resolver directly from the shell:

  • ss -tanp and ss -s (Socket Statistics): Modern replacement for netstat. Shows every TCP socket state and owning PID. A surge of sockets in CLOSE_WAIT means the remote peer already closed its side (sent FIN), but your application code forgot to call close()—a classic FD leak. (By contrast, many TIME_WAIT sockets indicate rapid short-lived outbound connections without pooling.)
  • lsof -p <pid> | wc -l and cat /proc/<pid>/limits: Counts live open file descriptors for a running process and confirms its active soft/hard Max open files limit.
  • dig +noall +answer +stats api.internal.corp: Queries DNS directly and prints the resolved IP, remaining TTL, CNAME chain, and query time in milliseconds. Inside an AWS VPC, AmazonProvidedDNS lives at 169.254.169.253 (and VPC CIDR base + 2, e.g., 10.0.0.2).
  • Checking /etc/resolv.conf (ndots:5 in EKS): Kubernetes sets options ndots:5 by default. Any hostname with fewer than 5 dots (like rds.us-east-1.amazonaws.com, which has 3 dots) is first queried against 3–4 cluster search suffixes (.svc.cluster.local, .cluster.local, etc.) before trying the absolute domain—multiplying DNS traffic and latency by 4–8× unless you append a trailing dot or set ndots:2.

4. Production Configuration: Dockerfile, ECS Ulimits & Signal Handler

Below is the complete production triad: exec-form container startup, ECS Task Definition ulimits and stopTimeout, and a non-leaking Node.js SIGTERM drain handler. 

# 1. Dockerfile — Exec form ensures Node runs as PID 1 (receives SIGTERM directly)
FROM node:22-alpine
WORKDIR /app
COPY dist/ ./dist/
CMD ["node", "dist/server.js"]

// 2. ECS Task Definition snippet — Raise NOFILE above 1024 default & set drain window
{
  "name": "orders-api",
  "stopTimeout": 30,
  "ulimits": [
    { "name": "nofile", "softLimit": 65536, "hardLimit": 65536 }
  ]
}

// 3. Backend Graceful Shutdown (Node.js / TypeScript)
let isShuttingDown = false;
app.get("/health", (_req, res) => {
  res.status(isShuttingDown ? 503 : 200).send(isShuttingDown ? "draining" : "ok");
});

process.on("SIGTERM", () => {
  isShuttingDown = true;                 // Fail ALB readiness checks immediately
  server.close(async () => {             // Stop new connections; drain in-flight
    await dbPool.end();                  // Close outbound DB sockets cleanly
    process.exit(0);                     // Exit cleanly before ECS fires SIGKILL
  });
  setTimeout(() => process.exit(1), 25_000).unref(); // Failsafe before 30s SIGKILL
});

# 4. On-host shell triage commands
$ ulimit -Sn && ulimit -Hn              # Inspect soft/hard FD limits
$ ss -tanp | grep CLOSE-WAIT | wc -l    # Detect app-side leaked sockets
$ dig @169.254.169.253 api.myapp.com +noall +answer +stats

Why Exit Code 137? Unix shells encode a signal kill as 128 + signal_number. Since SIGKILL is signal 9, any container killed by SIGKILL (or Linux OOM killer) reports exit code 137. A clean SIGTERM handler exits with 0.
ALB Deregistration Race On ECS/EKS, SIGTERM is sent to the container at the same moment the ALB begins target deregistration. Add a short pre-stop pause (or ensure ALB deregistration finishes) before closing the listening socket.
TIME_WAIT vs. CLOSE_WAIT TIME_WAIT is normal after your side closes first (waiting 2×MSL for stray packets). CLOSE_WAIT means the remote peer closed, and your code forgot to close its FD.
