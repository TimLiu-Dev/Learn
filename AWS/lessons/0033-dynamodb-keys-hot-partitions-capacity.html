DynamoDB Fundamentals: Partition & Sort Keys, Hot Partitions, Capacity & GSIs

Amazon DynamoDB delivers single-digit millisecond latency at petabyte scale because it forbids cross-node joins and routes every item to an exact SSD storage partition via a hash of its Partition Key. A senior engineer understands the physical per-partition limits (1,000 WCU, 3,000 RCU, 10 GB), why On-Demand mode cannot save a hot partition key, and how an under-provisioned Global Secondary Index silently throttles your base table.

Your Android Bridge

On Android, you reach for DataStore / SharedPreferences when you need fast key-value persistence, and Room (SQLite) when you want flexible WHERE clauses, secondary indexes added in a later migration, and joins on a single flash chip. DynamoDB feels like a key-value store at the API level (GetItem, PutItem), but it shards data across hundreds of independent storage servers across three Availability Zones. Unlike Room, you cannot casually query arbitrary columns later: every query must target a Partition Key (or a Global Secondary Index) designed upfront, and routing 50% of your app's writes to one shared key overwhelms a single storage node—even if the rest of the cluster sits idle.

1. Primary Keys, Partition Routing & Item Collections

Every item stored in a DynamoDB table is uniquely identified by its Primary Key, which comes in two shapes:

  • Simple Primary Key (Partition Key only): A single attribute (PK, e.g., userId). DynamoDB behaves like a distributed HashMap<PK, Item>, supporting O(1) point lookups (GetItem, PutItem, DeleteItem).
  • Composite Primary Key (Partition Key + Sort Key): Two attributes (PK + SK, e.g., PK = "USER#42", SK = "ORDER#2026-11-15#901"). All items sharing the same PK form an Item Collection stored together in sorted SK order inside a B-tree.

When your backend calls PutItem or Query, a DynamoDB Request Router feeds the raw PK value into an internal hash function (conceptually an unordered MurmurHash-style hash) to produce a hash space coordinate. That coordinate maps directly to one physical storage partition (replicated across three Availability Zones via Paxos/consensus leaders). Because SK values inside that partition are sorted in UTF-8 binary (or numeric) order, Query executes a fast B-tree range scan (begins_with, BETWEEN, >=), returning up to 1 MB of data per page (using LastEvaluatedKey for cursor pagination).

By contrast, Scan ignores the hash router and sequentially reads every partition in the table—consuming massive Read Capacity Units and degrading latency linearly as the table grows. Meanwhile, every individual item is hard-capped at 400 KB (attribute names plus values); larger binary payloads (avatars, receipts, videos) belong in S3 with only the S3 key stored in DynamoDB.

2. Capacity Math (RCU & WCU), On-Demand vs. Provisioned & Hot Partitions

Understanding DynamoDB Read and Write Capacity Units prevents unexpected 10x AWS bills and silent throttling:

Operation / Mode Unit Size Consumption Formula Senior Production Rule
Write (WCU) 1 KB blocks Math.ceil(bytes / 1024) A 1,025-byte write consumes 2 WCU. TransactWriteItems costs 2x (prepare + commit).
Strongly Consistent Read (RCU) 4 KB blocks Math.ceil(bytes / 4096) × 1 Reads the latest committed leader state; required for read-after-write guarantees.
Eventually Consistent Read (RCU) 4 KB blocks Math.ceil(bytes / 4096) × 0.5 Default on GetItem / Query; halves RCU cost (2 reads/sec per RCU up to 4 KB).
Single Partition Hardware Ceiling Per Partition 1,000 WCU & 3,000 RCU max Hard physical limit per storage node across both Provisioned and On-Demand tables.

Provisioned vs. On-Demand Capacity Modes

  • Provisioned Mode: You set explicit RCU/WCU targets (typically backed by Application Auto Scaling at ~70% utilization). Up to 5×–7× cheaper for steady, predictable traffic. DynamoDB retains up to 300 seconds (5 minutes) of unused capacity per partition as burst capacity for brief micro-spikes—never rely on burst capacity for sustained load.
  • On-Demand Mode (PAY_PER_REQUEST): Zero capacity planning; you pay per Read/Write Request Unit (RRU/WRU). New On-Demand tables start ready for thousands of requests/sec and automatically scale up to double their previous peak within 30 minutes (or faster with pre-warming). Best for spiky, unpredictable mobile launch traffic or low-traffic microservices.
Hot Partition Trap & Write Sharding

Even with Adaptive Capacity (which instantaneously shifts unused table WCU/RCU to busy partitions) and Split for Capacity (which splits partitions when throughput stays high), DynamoDB cannot split a single exact PK across multiple partitions for writes if the workload hits one partition's 1,000 WCU / 3,000 RCU ceiling. When an Android telemetry stream or flash-sale counter must write >1,000 WCU/s under one logical key, use Write Sharding: append a deterministic or random suffix (e.g., PK = "TELEMETRY#2026-11-15#shard_" + (rand % 10)) to fan writes across 10 partitions (10,000 WCU/s aggregate), accepting scatter-gather reads across those 10 shards.

3. Secondary Indexes: GSI vs. LSI & Backpressure Failure Modes

When your Android app needs to look up an order by orderId and list a user's orders by status, a single primary key is not enough. DynamoDB provides two index types with sharply different operational tradeoffs:

  • Local Secondary Index (LSI): Shares the exact same PK as the base table with an alternate SK. Must be defined at table creation time (cannot be added or deleted later), shares the base table's provisioned RCU/WCU, supports strongly consistent reads, and enforces a strict 10 GB maximum item collection size per PK (base items + all LSIs combined). Rarely used in new architectures unless strong consistency on a second sort key is mandatory.
  • Global Secondary Index (GSI): Defines a brand-new PK (and optional SK) across the whole table. Can be created or dropped anytime, supports eventually consistent reads only, and maintains its own independent partitions and provisioned RCU/WCU (or scales under On-Demand).

The Silent Production Outage: GSI Write Backpressure

Because a GSI replicates writes asynchronously from the base table into its own partition set, an under-provisioned or hot-keyed GSI becomes a toxic bottleneck. If your base table accepts 2,000 WCU/s, but GSI1 only has 300 WCU (or uses a low-cardinality GSI1PK = "ACTIVE" that exceeds 1,000 WCU on one GSI partition), DynamoDB's internal replication queue fills up. Once full, DynamoDB throttles writes on the base table itself—causing every PutItem, UpdateItem, and DeleteItem to fail with ProvisionedThroughputExceededException even though base table WCU metrics look healthy!

Two design rules prevent GSI surprises: (1) choose narrow projections (KEYS_ONLY or INCLUDE specific attributes rather than ALL) to minimize storage and write amplification, and (2) leverage Sparse Indexes—items that omit the GSI key attribute are automatically excluded from the GSI, keeping index size and WCU tiny (for example, setting PendingCheckAt only while an order is PENDING and removing it once shipped).

4. Production Example: CDK Table + Sparse GSI & SDK v3 Query

Below is a realistic AWS CDK (TypeScript) table definition with a sparse GSI and an AWS SDK v3 query inspecting consumed capacity and pagination cursors: 

// 1. AWS CDK (TypeScript) — Orders Table with On-Demand Billing & Sparse GSI
import * as dynamodb from "aws-cdk-lib/aws-dynamodb";

const ordersTable = new dynamodb.Table(this, "OrdersTable", {
  partitionKey: { name: "PK", type: dynamodb.AttributeType.STRING },
  sortKey: { name: "SK", type: dynamodb.AttributeType.STRING },
  billingMode: dynamodb.BillingMode.PAY_PER_REQUEST,
  pointInTimeRecoverySpecification: { pointInTimeRecoveryEnabled: true },
});

// Sparse GSI: only items with PendingShardPK + CreatedAt appear in this index
ordersTable.addGlobalSecondaryIndex({
  indexName: "GSI_PendingOrders",
  partitionKey: { name: "PendingShardPK", type: dynamodb.AttributeType.STRING }, // e.g. "PENDING#shard_3"
  sortKey: { name: "CreatedAt", type: dynamodb.AttributeType.STRING },
  projectionType: dynamodb.ProjectionType.INCLUDE,
  nonKeyAttributes: ["OrderId", "UserId", "TotalCents"],
});

// 2. Backend Service (Node.js / AWS SDK v3) — Paginated Query + Capacity Telemetry
import { DynamoDBClient } from "@aws-sdk/client-dynamodb";
import { DynamoDBDocumentClient, QueryCommand } from "@aws-sdk/lib-dynamodb";

const ddb = DynamoDBDocumentClient.from(new DynamoDBClient({}));

async function listUserOrders(userId: string, cursor?: Record<string, unknown>) {
  const res = await ddb.send(new QueryCommand({
    TableName: process.env.ORDERS_TABLE,
    KeyConditionExpression: "PK = :pk AND begins_with(SK, :prefix)",
    ExpressionAttributeValues: { ":pk": `USER#${userId}`, ":prefix": "ORDER#" },
    ConsistentRead: false, // 0.5 RCU per 4 KB block (half the cost of strong consistency)
    Limit: 25,
    ExclusiveStartKey: cursor,
    ReturnConsumedCapacity: "TOTAL",
  }));
  return { items: res.Items ?? [], nextCursor: res.LastEvaluatedKey, rcu: res.ConsumedCapacity?.CapacityUnits };
}
