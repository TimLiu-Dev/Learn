SQS (Standard vs FIFO, Visibility Timeout, DLQ) & SNS Fan-Out Filtering

Synchronous REST calls tie your availability to your slowest downstream dependency. Senior cloud architectures break that coupling with SNS fan-out and SQS queues—but misconfigured visibility timeouts, global FIFO group keys, or unfiltered subscriptions silently cause duplicate charges, global stalls, and runaway Lambda bills.

Your Android Bridge

On Android, you already separate broadcasting events from durable background work. You use Kotlin SharedFlow or EventBus to fan out an event to multiple in-app listeners, and you use WorkManager to persist a job to SQLite with ExistingWorkPolicy, exponential BackoffPolicy, and a bounded runAttemptCount so a crash doesn't lose the task. On AWS, Amazon SNS is the distributed push fan-out bus, Amazon SQS is the durable pull queue, Visibility Timeout is the lease preventing two workers from running the same job simultaneously, and a Dead-Letter Queue (DLQ) isolates poison pills once maxReceiveCount expires.

1. SNS + SQS Fan-Out & Subscription Filter Policies

Never push directly from one microservice to three downstream HTTP endpoints when an order completes: if the Analytics service goes down, Checkout shouldn't fail or block. Instead, the producer publishes a single event to an Amazon SNS topic, and each downstream service owns its own Amazon SQS queue subscribed to that topic.

By default, SNS delivers every published message to every subscriber. If 50 million events hit your topic daily and the Fraud service only inspects high-value refunds (1% of traffic), letting Fraud's Lambda poll and discard 99% of messages wastes 49.5M SQS receives, 49.5M deletes, and 49.5M Lambda invocations.

Attach an SNS Subscription Filter Policy so SNS drops non-matching messages before they ever enter the subscriber's SQS queue:

  • FilterPolicyScope: "MessageAttributes" (Default): Evaluates up to 10 structured attributes attached alongside the payload. Zero JSON body parsing overhead.
  • FilterPolicyScope: "MessageBody": Evaluates JSON fields directly inside the message body—handy when legacy producers don't populate MessageAttributes, though payload-based filtering carries per-GB evaluation pricing.
  • Boolean Logic & Operators: Multiple keys in a filter policy are combined with AND; values inside a key's array are combined with OR. Supported operators include exact match, {"numeric": [">=", 500]}, {"prefix": "eu-"}, {"anything-but": ["TEST"]}, and {"exists": true}.
  • RawMessageDelivery = true: Strips the outer SNS JSON envelope (TopicArn, Signature) when writing to SQS so your consumer receives the clean domain JSON directly.
Figure 1: SNS evaluates filter policies before enqueueing into isolated SQS queues. Failed messages move to a matching DLQ after maxReceiveCount and can be safely rate-limited during redrive.

2. SQS Standard vs. FIFO: Throughput, Ordering & Head-of-Line Blocking

Choosing between SQS Standard and SQS FIFO is an architectural tradeoff between horizontal scale and strict ordering/deduplication guarantees:

Dimension SQS Standard Queue SQS FIFO Queue (.fifo)
Throughput Nearly unlimited transactions per second (TPS) across distributed partitions. 300 TPS (3,000 TPS batched by 10); High Throughput mode scales to 3,000+ TPS (30,000+ batched).
Ordering Best-effort; messages can arrive out of order. Strict FIFO order within each MessageGroupId.
Delivery At-least-once (occasional duplicate deliveries possible; consumers must be idempotent). Exactly-once processing via 5-minute deduplication window (MessageDeduplicationId).
SNS Compatibility Standard SNS topics fan out to Standard or FIFO queues. FIFO SQS queues can only subscribe to FIFO SNS topics.

The Senior FIFO Trap (Head-of-Line Blocking): In a FIFO queue, SQS locks a MessageGroupId while any message in that group is in-flight. If you hardcode a single global MessageGroupId = "orders" for your entire platform, you serialize your whole fleet to one single active message at a time—and one stuck message blocks every customer behind it. Always partition MessageGroupId by the finest entity that requires ordering (e.g., customerId or orderId), and enable DeduplicationScope = messageGroup + FifoThroughputLimit = perMessageGroupId for high-throughput workloads.

3. Visibility Timeout, Long Polling & The Lambda 6× Rule

SQS does not delete a message when a worker calls ReceiveMessage. Instead, SQS marks the message invisible to other consumers for the duration of the Visibility Timeout (default 30 seconds, configurable from 0s to 12 hours). The worker must explicitly call DeleteMessage before that lease expires.

Always set ReceiveMessageWaitTimeSeconds = 20 (Long Polling) on your queues. Short polling (0s) returns empty responses immediately from a random subset of SQS servers, burning API dollars and missing messages in low-traffic queues until subsequent polls.

Golden AWS Rule: VisibilityTimeout ≥ 6× Lambda Timeout

Per the AWS Lambda SQS Event Source Mapping documentation, set your SQS queue's VisibilityTimeout to at least 6 times your Lambda function's Timeout (plus MaximumBatchingWindowInSeconds if configured). Why 6×? When Lambda hits a concurrency throttle, the Event Source Mapping backs off and retries before your handler even executes—eating into the visibility timer. If VisibilityTimeout ≤ Lambda Timeout, a slow invocation still running at second 30 becomes visible to a second Lambda worker concurrently, causing duplicate side effects and burning maxReceiveCount prematurely.

Furthermore, always enable FunctionResponseTypes: ["ReportBatchItemFailures"] on Lambda-SQS integrations. Without partial batch failure reporting, a single bad message in a 10-message batch causes Lambda to throw and forces SQS to retry all 10 messages—re-executing 9 records that already succeeded.

4. Dead-Letter Queues (DLQ), Poison Pills & Safe Redrive

A RedrivePolicy binds a source queue to a Dead-Letter Queue (DLQ) using maxReceiveCount (commonly 3–5). Once a message's ApproximateReceiveCount hits maxReceiveCount without being deleted, SQS moves it to the DLQ—stopping infinite retry loops and unblocking any FIFO MessageGroupId stuck behind a poison pill.

  • Type Parity: Standard queues must target Standard DLQs; FIFO queues must target FIFO DLQs.
  • Retention Clock Trap: SQS calculates MessageRetentionPeriod (default 4 days, max 14 days) from when the message was originally enqueued in the source queue, NOT when it entered the DLQ. Always set DLQ retention to 14 days (1,209,600s) so weekend poison pills don't silently expire before Monday triage.
  • Rate-Limited Redrive: After deploying a fix, use StartMessageMoveTask (DLQ Redrive) with a bounded MaxNumberOfMessagesPerSecond (e.g., 50 msg/s) to replay failed messages back to the source queue without overwhelming your database connection pool.

5. Production Example: Terraform SNS Filter + SQS + Lambda Batch Handler

Notice how the infrastructure aligns the 6× visibility timeout, 14-day DLQ retention, raw delivery, and partial-batch failure handler: 

# 1. Terraform: Source SQS Queue + 14-Day DLQ + Filtered SNS Subscription
resource "aws_sqs_queue" "orders_dlq" {
  name                      = "orders-billing-dlq.fifo"
  fifo_queue                = true
  message_retention_seconds = 1209600 # 14 days (clock starts at original enqueue!)
}

resource "aws_sqs_queue" "orders_queue" {
  name                        = "orders-billing.fifo"
  fifo_queue                  = true
  content_based_deduplication = false   # Producer supplies deterministic MessageDeduplicationId
  deduplication_scope         = "messageGroup"
  fifo_throughput_limit       = "perMessageGroupId"
  receive_wait_time_seconds   = 20      # Long polling
  visibility_timeout_seconds  = 180     # >= 6x Lambda timeout (30s * 6 = 180s)
  redrive_policy = jsonencode({
    deadLetterTargetArn = aws_sqs_queue.orders_dlq.arn
    maxReceiveCount     = 3
  })
}

resource "aws_sns_topic_subscription" "billing_sub" {
  topic_arn            = aws_sns_topic.orders_events.arn
  protocol             = "sqs"
  endpoint             = aws_sqs_queue.orders_queue.arn
  raw_message_delivery = true
  filter_policy_scope  = "MessageAttributes"
  filter_policy = jsonencode({
    eventType   = ["ORDER_PAID", "ORDER_REFUNDED"]
    totalCents  = [{ numeric = [">=", 100] }]
  })
}

// 2. TypeScript Lambda Handler with ReportBatchItemFailures (partial batch retries)
export const handler = async (event: SQSEvent): Promise<SQSBatchResponse> => {
  const batchItemFailures: SQSBatchItemFailure[] = [];
  for (const record of event.Records) {
    try {
      await processIdempotently(JSON.parse(record.body), record.messageId);
    } catch (err) {
      batchItemFailures.push({ itemIdentifier: record.messageId });
    }
  }
  return { batchItemFailures };
};
