Part 2 Capstone (2/3): ECS Fargate, Aurora, DynamoDB Streams & Step Functions Saga

With the VPC, PrivateLink, KMS, Cognito, and CloudFront + WAF perimeter built in Lesson 0048, it is time to wire the application core. In this second Capstone 2 installment, you connect an ECS Fargate API behind an ALB to Aurora PostgreSQL + RDS Proxy, capture state mutations via DynamoDB Streams & EventBridge Pipes, orchestrate distributed rollbacks in a Step Functions Standard Saga, and isolate poison events with EventBridge + SQS DLQs.

Your Android Bridge

On Android, a resilient checkout uses OkHttp + Retrofit with a Cognito JWT and attaches a UUID Idempotency-Key persisted in Room so WorkManager can retry safely across tunnel dropouts. On AWS, no single database transaction spans inventory, payment gateways, ledger postings, and push notifications. Your cloud backend splits that work across ECS Fargate (stateless API), Aurora + RDS Proxy (ACID ledger), DynamoDB Streams + EventBridge Pipes (zero-dual-write event capture), and a Step Functions Saga (durable state + compensating rollbacks).

1. End-to-End Application Flow Inside the Capstone 2 VPC

Every component below runs inside the private subnets provisioned in Lesson 0048, using VPC Interface/Gateway Endpoints instead of public internet hops:

  1. ALB → ECS Fargate API: CloudFront + WAF forwards authenticated API calls to an ALB in front of stateless Fargate tasks spread across two Availability Zones. Containers run non-root, enforce keepAliveTimeout = 65s (> ALB 60s), and drain gracefully on SIGTERM.
  2. Aurora PostgreSQL Multi-AZ + RDS Proxy: Fargate writes strongly consistent financial and ledger records through RDS Proxy, which multiplexes bursty container connections onto a bounded Aurora pool and shields tasks from 30–60s DNS failover delays.
  3. DynamoDB + Streams + EventBridge Pipe: Order intake state and idempotency records land in DynamoDB with NEW_AND_OLD_IMAGES streaming enabled. An EventBridge Pipe filters for ORDER_PLACED transitions and triggers the Saga—eliminating dual-write failure windows without custom poller fleets.
  4. Step Functions Standard Workflow Saga: Orchestrates ReserveInventory → AuthorizePayment → CommitLedger with exponential retries and deterministic Catch compensations (VoidPayment, ReleaseInventory) in reverse order.
  5. EventBridge Bus → SQS + Dead Letter Queue (DLQ): Once the Saga reaches a terminal state (OrderConfirmed or OrderFailed), it publishes domain facts to an EventBridge custom bus that fans out to decoupled SQS subscriber queues, each guarded by a DLQ after maxReceiveCount failures.
Figure 1: Capstone 2 runtime flow. Synchronous writes stay fast at the edge; DynamoDB Streams + EventBridge Pipes hand off asynchronously to a durable Step Functions Saga and fan-out queues.

2. Compute & Relational Data: ECS Fargate Drain & RDS Proxy Math

Two subtle production failures hit Fargate + Aurora stacks long before CPU hits 80%: deployment 502s and connection-slot exhaustion.

Failure Mode Why It Happens Capstone 2 Production Fix
Blue/Green or Rolling 502s ECS sends SIGTERM to an old task while the ALB still holds it in-service until deregistration finishes, or the app exits before closing keep-alive sockets. Set ALB deregistration_delay = 30s, ECS task stopTimeout = 45s, and stop accepting new requests only after ALB health checks or drain wait completes.
Aurora max_connections Exhaustion Suppose Fargate scales from 6 to 60 tasks during a push campaign, each holding a 20-connection pool = 1,200 open TCP sessions on an instance capped below that limit. Route Fargate through Amazon RDS Proxy. Idle app connections share a warm server-side pool, and Aurora failover drops from ~45s DNS TTL wait to ~1–5s.
Cross-AZ Latency Tax Aurora writes always hit the single Writer AZ. Cross-AZ round trips cost ~0.5–1.5 ms per query, multiplying rapidly across N+1 loops. Batch ledger inserts in one transaction and route read-only catalog queries to the Aurora Reader endpoint (or local-AZ reader via RDS Proxy).

3. Streams, EventBridge Pipes & Saga Consistency Rules

Why use DynamoDB Streams + EventBridge Pipes instead of calling stepfunctions.startExecution() directly from Fargate? Because network partitions between Fargate and Step Functions create the classic dual-write bug: DynamoDB commits the order, the API call to Step Functions times out, and the order is orphaned forever.

  • Pipe Filtering Cuts Cost & Noise: DynamoDB Streams emit every INSERT, MODIFY, and REMOVE. Configuring an EventBridge Pipe filter (e.g., eventName = INSERT/MODIFY and dynamodb.NewImage.status.S = "ORDER_PLACED") drops irrelevant heartbeats inside the managed Pipe service at zero Lambda/Step Functions invocation cost.
  • Standard vs. Express Choice: A Checkout Saga requires Standard Workflows because Standard guarantees exactly-once workflow execution, persists every state transition for 90 days of audit history, and supports up to 1 year of runtime (for 3DS or human approvals). Standard bills per state transition ($0.025 per 1,000 transitions), whereas Express bills per execution + duration and is at-least-once asynchronously.
  • Idempotent Forward & Compensating Steps: If VoidPayment times out after the payment processor already voided the charge, Step Functions retries VoidPayment. Every task handler MUST pass a deterministic idempotency token (such as $$.Execution.Id + "-void") so retries return 200 OK instead of failing compensation.
  • SQS Visibility & DLQ Quarantine: Downstream EventBridge targets write to SQS queues rather than invoking brittle Lambdas directly. Set VisibilityTimeout ≥ 6 × LambdaTimeout and attach a DLQ with maxReceiveCount = 3 (14-day retention) so one malformed payload cannot stall healthy subscribers.
No Dead-End Compensation!

Forward steps are allowed to fail with business errors (e.g., CardDeclined). Compensating steps must never silently give up: wrap VoidPayment and ReleaseInventory in aggressive exponential retries (MaxAttempts: 5+), and add a fallback Catch that routes unrecoverable compensation failures to an operations SQS DLQ + PagerDuty alert.

4. Production Blueprint: CDK Wiring + ASL Saga Definition

Below is the core Capstone 2 infrastructure-as-code pattern pairing an RDS Proxy, an EventBridge Pipe over DynamoDB Streams, and the Step Functions Standard Saga state machine: 

// 1. AWS CDK (TypeScript) — RDS Proxy + EventBridge Pipe Filter (DynamoDB Stream -> Step Functions)
const dbProxy = auroraCluster.addProxy("CapstoneRdsProxy", {
  secrets: [auroraSecret],
  vpc,
  vpcSubnets: { subnetType: ec2.SubnetType.PRIVATE_ISOLATED },
  requireTLS: true,
  maxConnectionsPercent: 80, // Leave 20% headroom for admin / migrations
});

const ordersPipe = new pipes.CfnPipe(this, "OrdersToSagaPipe", {
  roleArn: pipeRole.roleArn,
  source: ordersTable.tableStreamArn!,
  sourceParameters: {
    dynamoDbStreamParameters: {
      startingPosition: "LATEST",
      batchSize: 10,
      maximumRetryAttempts: 3,
      deadLetterConfig: { arn: streamDlq.queueArn }, // Never block shard forever
    },
    filterCriteria: {
      filters: [{
        pattern: JSON.stringify({
          eventName: ["INSERT", "MODIFY"],
          dynamodb: { NewImage: { status: { S: ["ORDER_PLACED"] } } },
        }),
      }],
    },
  },
  target: checkoutSaga.stateMachineArn,
  targetParameters: { stepFunctionStateMachineParameters: { invocationType: "FIRE_AND_FORGET" } },
});

RDS Proxy Pinning Gotcha If your Fargate code runs session-level SET TIME ZONE or unnamed prepared statements over a connection, RDS Proxy pins that backend Aurora session until the client disconnects—reducing pooling efficiency. Keep transactions stateless and short.
Stream Shard Poison Pill DynamoDB Streams guarantee strict ordering per partition key inside a shard. Without maximumRetryAttempts and a deadLetterConfig on the EventBridge Pipe, one malformed item can stall an entire shard for up to 24 hours.
Saga Execution Naming Pass idempotencyKey as the Step Functions Standard execution name. AWS rejects a second StartExecution with the same name within 90 days—giving you free, API-level deduplication.
