S3 Deep Dive: Strong Consistency, Block Public Access, Pre-Signed URLs & Lifecycle

Proxying user photos and videos through your API servers wastes compute, trips Lambda 6 MB and API Gateway 10 MB payload limits, and doubles egress costs. A senior cloud engineer keeps S3 buckets locked behind Block Public Access, issues constrained SigV4 pre-signed URLs so Android clients stream straight to S3, relies on strong read-after-write consistency for immediate post-upload processing, and avoids 128 KB and early-deletion traps in storage lifecycle policies.

Your Android Bridge

In Android, uploading a 40 MB video via Retrofit @Multipart to your REST backend ties up an OkHttp socket and forces your ECS/Lambda server to buffer or stream the file twice (Mobile → Backend → S3). Instead, your app calls a tiny JSON endpoint (POST /uploads/presign) to obtain a short-lived S3 pre-signed PUT URL, then uses a custom streaming OkHttp RequestBody backed by ContentResolver.openInputStream(uri) to upload bytes directly to S3 without loading the file into the JVM heap—while the bucket itself stays 100% private.

1. Strong Read-After-Write Consistency & Partition Scaling

Before December 2020, Amazon S3 had eventual consistency for overwrite PUTs and DELETEs, forcing mobile backends into awkward DynamoDB metadata hacks or retry loops. Today, per the Amazon S3 Data Consistency Model, S3 delivers strong read-after-write consistency automatically across all Regions at zero extra cost or latency penalty:

  • Immediate Visibility After 200 OK: Once a PUT (new key or overwrite), POST (multipart complete), or DELETE returns 200 OK, every subsequent GET, HEAD, or LIST sees the new object version or deletion immediately. When Android finishes uploading uploads/u42/avatar.jpg and calls POST /profile/confirm, your Lambda thumbnailer never hits a stale 404 NoSuchKey race.
  • No Partial Reads, Last-Writer-Wins on Races: In-flight uploads are atomic—concurrent readers see either the previous committed object or the new one, never half-written bytes. If two devices overwrite the exact same key simultaneously, the write with the later S3 commit timestamp wins unless you enforce optimistic locking with S3 conditional writes (If-None-Match: * to fail if the key exists, or If-Match: <ETag> for compare-and-swap).
  • Automatic Partition Throughput: S3 scales horizontally to at least 3,500 PUT/COPY/POST/DELETE and 5,500 GET/HEAD requests per second per partitioned prefix. You no longer need random hex prefixes for normal workloads.
  • Single PUT vs. Multipart Upload Limits: A single PUT Object supports up to 5 GiB. Any upload above 5 GiB (max object size 5 TiB) requires Multipart Upload (up to 10,000 parts, minimum 5 MiB per part except the final part). AWS recommends switching to Multipart Upload at 100 MiB+ so mobile network drops only retry a 5–10 MiB chunk instead of restarting from byte zero.

2. Block Public Access & Bucket Owner Enforced

Historical S3 data leaks rarely came from broken cryptography; they came from a stray bucket policy or legacy object ACL granting anonymous s3:GetObject to *. Since April 2023, every newly created S3 bucket enables two defaults that should never be weakened for user-upload buckets:

  1. S3 Block Public Access (4 Guardrails): BlockPublicAcls, IgnorePublicAcls, BlockPublicPolicy, and RestrictPublicBuckets. Enable all four at both the Bucket level and the AWS Account level (enforced org-wide via SCPs).
  2. ObjectOwnership: BucketOwnerEnforced (ACLs Disabled): Disables legacy S3 ACLs completely. Access is governed strictly by IAM policies, Bucket policies, and VPC Endpoint policies, guaranteeing the bucket owner always owns every uploaded object.
Key Distinction: Private Bucket ≠ Broken Pre-Signed URLs

Turning on all four Block Public Access settings does not break pre-signed URLs. Block Public Access only blocks anonymous (unauthenticated) policies and ACLs. A pre-signed URL carries your backend IAM role's SigV4 signature (X-Amz-Credential + X-Amz-Signature), so S3 evaluates it as an authenticated IAM request—while direct unauthenticated requests to https://bucket.s3.amazonaws.com/key still fail with 403 AccessDenied.

3. Pre-Signed URLs: SigV4 Mechanics & Three Production Traps

A SigV4 pre-signed URL computes an HMAC-SHA256 signature over the HTTP method, object key, query parameters, and exact headers listed in X-Amz-SignedHeaders. Note that signing happens 100% locally in your backend CPU—your Lambda does not make a network round-trip to S3 to generate the URL.

Watch out for three classic senior-level production failures:

  1. The STS Credential Expiration Trap: While SigV4 allows X-Amz-Expires up to 604,800 seconds (7 days) for long-lived IAM user access keys, production backends run on IAM Roles (Lambda, ECS, EC2 IMDSv2) backed by temporary STS credentials. Per AWS docs, a pre-signed URL expires when either X-Amz-Expires elapses or the underlying STS token expires—whichever comes first. If an assumed role session lasts 1 hour (3600s) and you set ExpiresIn = 86400, S3 rejects uploads with 403 ExpiredToken after 1 hour.
  2. Unconstrained Signed Headers (Abuse Vector): If your backend only signs host and omits ContentType and ContentLength, any authenticated user who requests a pre-signed URL for a 2 MB avatar can use curl to upload a 5 GiB archive or an executable text/html phishing page into your bucket. Always bind ContentType, exact ContentLength (or use a Pre-Signed POST Policy with ["content-length-range", 1, 10485760] when exact byte length isn't known upfront), and prefix-scope the IAM role to uploads/${userId}/*.
  3. 403 SignatureDoesNotMatch on Android: If your backend signs content-type: image/jpeg, OkHttp must transmit Content-Type: image/jpeg verbatim—not image/jpg and not application/octet-stream. Even an auto-appended ; charset=utf-8 breaks the HMAC signature.
Security Rule: Never Trust Client-Supplied Object Keys

Never let the Android client choose the S3 object key directly (key = req.body.key), or a user could overwrite uploads/victim-id/avatar.jpg. Generate a server-side UUID key scoped to the verified JWT subject: uploads/${jwtSub}/${uuid}.jpg.

4. Storage Classes & Lifecycle Cost Traps

Mobile user-generated media is read heavily in the first days and rarely touched after 90 days. Keeping everything in S3 Standard ($0.023/GB-month in us-east-1) wastes up to 80% of storage spend—yet naive S3 Lifecycle rules can actually increase your bill if you ignore minimums and request fees:

  • S3 Standard ($0.023/GB-mo): 0-day minimum duration, 0 minimum billable size, $0 retrieval fee. Best for active media (<30 days) or tiny objects (<128 KB).
  • S3 Standard-IA ($0.0125/GB-mo): 30-day minimum storage duration, 128 KB minimum billable object size, $0.01/GB retrieval fee. A 16 KB thumbnail is still billed as 128 KB (8× storage inflation!).
  • S3 Glacier Instant Retrieval ($0.004/GB-mo): Millisecond latency via normal GET, 90-day minimum duration, 128 KB minimum billable size, $0.03/GB retrieval fee. Ideal for archived user photos and videos that must still open instantly in-app.
  • S3 Glacier Flexible Retrieval ($0.0036/GB-mo) & Deep Archive ($0.00099/GB-mo): Asynchronous restore (minutes to 48 hours via RestoreObject), 90-day / 180-day minimums, plus 40 KB per-object metadata overhead. Do not use for interactive mobile reads.
  • S3 Intelligent-Tiering: Automatically moves objects ≥128 KB across tiers with zero retrieval fees, charging $0.0025 per 1,000 objects/month for monitoring. Objects <128 KB never tier down and pay monitoring fees for nothing.
  • Abort Incomplete Multipart Uploads: Always include AbortIncompleteMultipartUpload (e.g., 7 days). When an Android phone loses LTE halfway through a 500 MB multipart upload, orphaned parts sit in S3 Standard accruing silent monthly charges until aborted.

5. Production Code: Backend Presigner + Android OkHttp Streamer

Notice how the backend constrains ContentType, ContentLength, and encryption in the signature, while the Android client streams straight from a ContentResolver descriptor with zero byte-array buffering: 

// 1. Backend (TypeScript / AWS SDK v3) — Generate constrained 5-minute pre-signed PUT
import { S3Client, PutObjectCommand } from "@aws-sdk/client-s3";
import { getSignedUrl } from "@aws-sdk/s3-request-presigner";

const s3 = new S3Client({ region: "us-east-1" });

export async function createPhotoUploadUrl(userId: string, bytes: number, mime: string) {
  if (!["image/jpeg", "image/webp", "video/mp4"].includes(mime)) throw new Error("Unsupported MIME");
  if (bytes <= 0 || bytes > 50 * 1024 * 1024) throw new Error("Exceeds 50 MiB limit");

  const key = `uploads/${userId}/${crypto.randomUUID()}`;
  const cmd = new PutObjectCommand({
    Bucket: process.env.MEDIA_BUCKET!,
    Key: key,
    ContentType: mime,       // Included in X-Amz-SignedHeaders -> locked by SigV4
    ContentLength: bytes,    // Prevents client from uploading larger payload
    ServerSideEncryption: "AES256"
  });

  const url = await getSignedUrl(s3, cmd, { expiresIn: 300 }); // 5 min (< STS role expiry)
  return { url, key, requiredHeaders: { "Content-Type": mime, "Content-Length": String(bytes), "x-amz-server-side-encryption": "AES256" } };
}

// 2. Android Client (Kotlin / OkHttp) — Stream Uri directly without loading into RAM
class UriStreamingRequestBody(
  private val resolver: ContentResolver,
  private val uri: Uri,
  private val mimeType: String,
  private val exactBytes: Long
) : RequestBody() {
  // Exact match required: OkHttp must NOT append "; charset=utf-8"
  override fun contentType(): MediaType = mimeType.toMediaType()
  override fun contentLength(): Long = exactBytes
  override fun writeTo(sink: BufferedSink) {
    resolver.openInputStream(uri)?.source()?.use { source -> sink.writeAll(source) }
      ?: error("Unable to open upload stream for $uri")
  }
}
