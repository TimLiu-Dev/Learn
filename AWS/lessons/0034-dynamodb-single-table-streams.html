DynamoDB Production Patterns: Single-Table Design, Optimistic Locking & Streams

DynamoDB has no server-side JOIN and no interactive row locks. To hit consistent single-digit millisecond p99 latency at scale, senior engineers pack related entities into one partition using overloaded PK/SK keys, invert relationships with sparse Global Secondary Indexes, guard mutations with ConditionExpression versions, and react to state transitions via DynamoDB Streams.

Your Android Bridge

In Android Room, you normalize entities into separate tables and write @Transaction @Relation queries so SQLite joins User, Order, and LineItem on the device. That works locally on one phone, but distributed joins across storage nodes wreck tail latency at cloud scale. Instead, Single-Table Design pre-joins those entities inside one DynamoDB item collection (PK + SK prefixing), GSI inverted indexes replace reverse foreign-key lookups, ConditionExpression plays the role of Room's OnConflictStrategy.ABORT plus a version check, and DynamoDB Streams + Lambda acts like a server-side Flow<List<Event>> observer for async side effects.

1. Single-Table Design & PK/SK Overloading (Pre-Joined Item Collections)

In DynamoDB, a Query hits one storage partition via an O(1) hash of the partition key (PK), then reads a contiguous B-tree range sorted by the sort key (SK). Because all items sharing a PK live together in the same item collection, fetching a heterogeneous group of entities in one Query replaces multi-table SQL joins with a single network round trip.

To store different entity types side-by-side, name your table keys generically (PK, SK) and prefix values with entity namespaces:

  • Customer Profile: PK = "USER#u_42", SK = "PROFILE"
  • Customer Orders (time-ordered): PK = "USER#u_42", SK = "ORDER#2026-11-15T08:10:00Z#ord_9"
  • Saved Addresses: PK = "USER#u_42", SK = "ADDR#home"
  • Order Line Items: PK = "ORDER#ord_9", SK = "ITEM#sku_7"

With one Query(PK = "USER#u_42", SK begins_with "ORDER#"), you read the customer's chronological orders. With Query(PK = "USER#u_42") (no SK filter), you read their profile, addresses, and recent orders in one call—bounded only by DynamoDB's 1 MB per-page response limit and 400 KB max item size (attributes plus values combined).

Figure 1: Overloaded PK/SK values co-locate user profile and order headers in one partition, while GSI1PK/GSI1SK invert the key graph for reverse lookups without duplicating tables.
When NOT to Use Single-Table Design

Single-table design optimizes for known, high-throughput OLTP access patterns. Skip it—or keep separate tables—when product requirements change weekly, when teams need ad-hoc BI/SQL analytics (Athena/Glue exports become painful when every row has a different schema), or when fine-grained IAM row/table isolation per microservice is required. Also avoid unbounded item collections: storing millions of audit events under one hot PK can exceed the single-partition limit (1,000 WCU / 3,000 RCU), and if any Local Secondary Index (LSI) exists, caps that item collection at 10 GB.

2. Inverted Indexes, Adjacency Lists & Sparse GSIs

Base tables only query forward from PK. To query the reverse direction—for example, looking up an order by orderId without knowing userId, or finding every order containing SKU#sku_7—add a Global Secondary Index (GSI) with generic attributes GSI1PK and GSI1SK.

  • Adjacency List Pattern: Many-to-many graphs (Users ↔ Groups, Orders ↔ SKUs) live cleanly in one table. Put PK = "ORDER#ord_9", SK = "ITEM#sku_7" on the base table, and mirror GSI1PK = "SKU#sku_7", GSI1SK = "ORDER#ord_9". Querying the base table returns an order's items; querying GSI1 returns all orders for a SKU.
  • Sparse Indexes: DynamoDB only projects an item into a GSI if both the GSI partition key and sort key attributes exist on that item. Setting GSI2PK = "STATUS#OPEN" only while an order is open—and deleting GSI2PK on completion—creates a tiny, fast work-queue index over active orders without scanning millions of archived rows.

Senior Failure Mode — GSI Write Backpressure: GSIs replicate asynchronously (typically under 10 ms; strong consistency is not supported on GSIs). Every GSI maintains its own provisioned or on-demand capacity. If a GSI has a low-cardinality key like GSI2PK = "STATUS#OPEN" under heavy write load, or its provisioned WCU is too low, GSI throttling propagates backward and stalls writes on the base table. Choose projection carefully (KEYS_ONLY, INCLUDE, or ALL) because projecting large attributes doubles storage and WCU cost.

3. Optimistic Locking with ConditionExpression & Transactions

Consider two concurrent Lambda invocations (or an Android client retrying a flaky cellular request) both reading ORDER#ord_9 at stock = 5 and decrementing it by 1. Without a concurrency guard, the second writer blindly overwrites the first, leaving stock = 4 instead of 3.

Instead of holding pessimistic row locks across network calls, DynamoDB enforces Optimistic Concurrency Control (OCC) via ConditionExpression:

  1. Store a monotonically increasing version attribute on every mutable item (starting at 1 on insert).
  2. On create (idempotent insert), pass ConditionExpression: "attribute_not_exists(PK)" so duplicate mobile retries fail safely instead of clobbering existing orders.
  3. On update, read the item's current version (say 7), then send UpdateItem with ConditionExpression: "version = :expectedVersion" and UpdateExpression: "SET #s = :status, version = version + :one".

DynamoDB evaluates the condition atomically on the storage leader node. If another writer bumped version to 8 first, DynamoDB rejects the stale write with ConditionalCheckFailedException (HTTP 400). Note the billing trap: a failed conditional write still consumes normal WCU based on the item's size (minimum 1 WCU).

When a business invariant spans multiple items—such as deducting inventory from SKU#sku_7 and creating ORDER#ord_9 together—use TransactWriteItems. It executes all-or-nothing across up to 100 items or 4 MB total within one AWS Region, at 2× WCU cost (prepare + commit phases), returning TransactionCanceledException with per-item CancellationReasons if any condition fails.

4. DynamoDB Streams + Lambda (CDC, Poison Pills & Loop Prevention)

Once an order commits, downstream systems need to charge cards, push FCM notifications to Android, or update OpenSearch—without slowing down the checkout API. Enabling DynamoDB Streams emits a time-ordered sequence of item mutations (INSERT, MODIFY, REMOVE) per partition shard, retained for 24 hours, with strict per-item ordering and no duplicate stream records per write.

Choose your StreamViewType intentionally: KEYS_ONLY minimizes payload size, NEW_IMAGE shows the post-write item, and NEW_AND_OLD_IMAGES lets your Lambda compute exact attribute diffs (e.g., triggering only when status changed from OPEN to PAID).

Watch out for three classic DynamoDB Streams production outages:

  • The Infinite Self-Trigger Loop: Your Stream Lambda reads an INSERT/MODIFY event and writes an enrichedAt attribute back to the same table, emitting another MODIFY event forever until your AWS bill explodes. Fix: attach an Event Source Mapping (ESM) filter matching only eventName: ["INSERT"] or specific status transitions, and avoid redundant writes.
  • The Poison-Pill Shard Block: By default, a Lambda ESM retries an unhandled exception on the same batch until the 24-hour stream retention expires—freezing every newer item on that shard. Fix: set BisectBatchOnFunctionError: true, MaximumRetryAttempts: 3, and an OnFailure SQS/SNS dead-letter destination, or return batchItemFailures with ReportBatchItemFailures.
  • Consumer Fan-Out Limits: At most 2 concurrent consumers should poll a DynamoDB Stream shard before LimitExceededException throttling occurs. If 5+ microservices need the stream, route events through EventBridge Pipes or enable Kinesis Data Streams for DynamoDB (up to 365-day retention, though without DynamoDB Streams' strict single-record deduplication guarantee on shard splits).

5. Code Example: AWS SDK v3 Optimistic Lock & Stream Handler

Below is a production TypeScript pattern using @aws-sdk/lib-dynamodb for conditional versioned updates and a hardened Lambda Stream consumer with ESM filtering and partial batch failure reporting: 

// 1. Optimistic Lock Update (AWS SDK v3 DocumentClient)
import { UpdateCommand } from "@aws-sdk/lib-dynamodb";

export async function markOrderPaid(userId: string, orderSk: string, expectedVersion: number) {
  try {
    const res = await docClient.send(
      new UpdateCommand({
        TableName: process.env.TABLE_NAME,
        Key: { PK: `USER#${userId}`, SK: orderSk },
        UpdateExpression: "SET #st = :paid, version = version + :one REMOVE GSI2PK, GSI2SK",
        ConditionExpression: "attribute_exists(PK) AND version = :expectedVersion",
        ExpressionAttributeNames: { "#st": "status" },
        ExpressionAttributeValues: {
          ":paid": "PAID",
          ":expectedVersion": expectedVersion,
          ":one": 1
        },
        ReturnValues: "ALL_NEW"
      })
    );
    return res.Attributes;
  } catch (err: any) {
    if (err.name === "ConditionalCheckFailedException") {
      // Stale read: re-fetch item and retry with jitter, or return HTTP 409 Conflict
      throw new ConflictError("Order modified concurrently; reload and retry.");
    }
    throw err;
  }
}

// 2. ESM Filter Criteria (CDK / SAM) — prevents infinite loop on enrichments
// Only triggers Lambda when an Order transitions into status = "PAID"
const streamFilter = {
  Filters: [
    {
      Pattern: JSON.stringify({
        eventName: ["INSERT", "MODIFY"],
        dynamodb: {
          NewImage: {
            entityType: { S: ["Order"] },
            status: { S: ["PAID"] }
          }
        }
      })
    }
  ]
};
