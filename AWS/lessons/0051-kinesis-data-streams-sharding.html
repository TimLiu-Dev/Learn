High-Throughput Streaming: Amazon Kinesis Data Streams, Shards, Checkpointing & SQS Comparison

SQS deletes a message once a consumer processes it. When you need ordered per-device telemetry, multiple independent consumer groups reading the same stream, and 24-hour to 365-day replay, you move from queues to partitioned append-only logs: Amazon Kinesis Data Streams.

Your Android Bridge

In Android, a Channel delivers each event to a single collector (like SQS), whereas a SharedFlow(replay = N) broadcasts the same ordered stream to multiple independent collectors that each track their own position (like Kinesis Data Streams). If 100,000 Android devices flush telemetry via WorkManager, Kinesis shards partition that firehose cleanly while keeping every single device's events strictly ordered.

1. Shard Mechanics, Capacity Math & Hot-Shard Skew

A Kinesis Data Stream is composed of one or more shards. Every shard has hard physical throughput ceilings:

  • Write (Ingress) Limit: 1 MB/sec OR 1,000 records/sec per shard (whichever hits first).
  • Read (Egress) Limit (Standard Polling): 2 MB/sec per shard shared across all consumers reading that shard.
  • Read Limit (Enhanced Fan-Out): Each registered HTTP/2 push consumer gets a dedicated 2 MB/sec pipe per shard.

Producers supply a PartitionKey; Kinesis hashes it (MD5 → 128-bit keyspace) to pick a shard. Just like DynamoDB hot partitions, passing a constant key like "global" or a single mega-tenant ID sends 100% of writes to one shard—causing ProvisionedThroughputExceededException even when 9 other shards sit idle.

Figure 1: Each Kinesis shard guarantees ordering within its PartitionKey hash bucket and retains records so multiple consumers can checkpoint independently.

2. Checkpointing, Poison Pills & SQS vs. Kinesis

Because Kinesis does not delete records after reading, consumers (AWS Lambda, KCL apps on ECS, or EventBridge Pipes) advance a per-shard sequence-number checkpoint. That creates a notorious production trap: a poison-pill record in a shard blocks every later record in that shard if your Lambda keeps retrying indefinitely!

Senior Lambda + Kinesis configurations always set bisectBatchOnFunctionError: true, bounded maximumRetryAttempts, and an onFailure SQS/SNS destination so bad records get quarantined while healthy records continue flowing. 

// AWS CDK v2: Hardened Kinesis Data Stream + Lambda Event Source Mapping
const stream = new kinesis.Stream(this, "TelemetryStream", {
  streamMode: kinesis.StreamMode.ON_DEMAND, // Auto-scales shards up to 200 MB/s+
  retentionPeriod: Duration.days(7),        // Full 7-day replay window
  encryption: kinesis.StreamEncryption.KMS,
  encryptionKey: platformKmsKey,
});

consumerFn.addEventSource(new sources.KinesisEventSource(stream, {
  startingPosition: lambda.StartingPosition.LATEST,
  batchSize: 100,
  maxBatchingWindow: Duration.seconds(2),
  parallelizationFactor: 5,                 // Up to 10 concurrent batches/shard by PartitionKey
  bisectBatchOnFunctionError: true,         // Binary-search isolate poison pills
  retryAttempts: 3,                         // Bounded retries so shard never stalls forever
  onFailure: new destinations.SqsDestination(poisonDlq),
}));
