EKS (Kubernetes on AWS): Control Plane, IRSA/Pod Identity & When NOT to Use EKS

Amazon EKS gives you upstream Kubernetes on AWS, but it is never "free Kubernetes": you inherit VPC CNI IP-address planning, Pod-level IAM credential plumbing, ALB Ingress readiness mechanics, and a continuous version-upgrade treadmill. Senior cloud architects know both how EKS works under the hood and when ECS on Fargate ships the same product at a fraction of the operational cost.

Your Android Bridge

Think about Android teams that wire up multi-component Dagger graphs, custom KSP code generators, and five Gradle convention plugins for a 4-screen app—when simple constructor injection or a single Hilt @Singleton module would have shipped in an afternoon. Adopting Amazon EKS for a small set of standard HTTP APIs is the exact cloud equivalent: you pay a $73/month control-plane tax per cluster, maintain Kubernetes API upgrades, tune VPC ENI IP pools, and manage cluster add-ons before deploying a single line of business logic.

1. EKS Control Plane vs. Data Plane (And the Hidden VPC CNI Trap)

In Amazon EKS, AWS splits responsibility cleanly at the Kubernetes API boundary:

  • Managed Control Plane ($0.10/hour ≈ $73/month per cluster): AWS runs a dedicated, single-tenant Kubernetes control plane (kube-apiserver, kube-scheduler, kube-controller-manager, and a 3-AZ etcd cluster) behind a managed endpoint. Unlike ECS—where the cluster control plane costs $0—every EKS cluster starts with a fixed $73/month bill under Standard Support, jumping to $0.60/hour (≈ $438/month) per cluster if you fall behind Kubernetes releases (~14 months per minor version) and enter EKS Extended Support.
  • Customer Data Plane (EC2 Managed Node Groups, Karpenter, or Fargate): Your Pods still execute on compute you pay for and size. With Managed Node Groups or Karpenter, EC2 instances join the cluster in your VPC subnets and run kubelet, kube-proxy, and the Amazon VPC CNI plugin (aws-node).

Here is the #1 EKS networking failure mode that surprises engineers coming from overlay CNI clusters (like Calico/Flannel on-prem): by default, the Amazon VPC CNI assigns real VPC secondary IPv4 addresses directly to Pods from your subnet CIDR.

Consider an m5.large worker node. Per AWS EC2 ENI limits, an m5.large supports at most 3 ENIs and 10 IPv4 addresses per ENI (one primary IP + 9 secondary IPs). Excluding the node's own primary IP, that caps a single m5.large at 29 Pods unless you enable Prefix Delegation (assigning /28 blocks of 16 IPs per slot). Worse, by default aws-node pre-allocates a full ENI's worth of warm IPs (WARM_ENI_TARGET=1) on every node. Twenty nodes in a /24 subnet (251 usable AWS IPs) can exhaust the subnet's free IPs before CPU hits 30%, causing new Pods to stick in ContainerCreating with FailedCreatePodSandBox: no available IP addresses.

2. Pod IAM: Node Profiles vs. IRSA vs. EKS Pod Identity

Containers inside Pods frequently call DynamoDB, S3, or SQS. How does a Pod obtain short-lived AWS STS credentials without hardcoding static access keys?

  1. Anti-Pattern — EC2 Node Instance Profile (IMDSv2): Every Pod on a worker node shares the node's IAM role via 169.254.169.254. That violates least privilege: a compromised static-asset Pod on the same node as your Payments Pod inherits Payments' database permissions. (Setting IMDS hop limit to 1 blocks Pods from reaching IMDSv2 entirely; setting it to 2 exposes the node role to every container.)
  2. IRSA (IAM Roles for Service Accounts): Introduced in 2019. You register an IAM OIDC Identity Provider tied to your cluster's unique issuer URL (oidc.eks.<region>.amazonaws.com/id/<cluster-id>), annotate a Kubernetes ServiceAccount with eks.amazonaws.com/role-arn, and a mutating webhook injects AWS_WEB_IDENTITY_TOKEN_FILE + AWS_ROLE_ARN into new Pods. The AWS SDK calls sts:AssumeRoleWithWebIdentity. Operational friction: every IAM trust policy hardcodes the cluster's OIDC ID, so rebuilding a cluster or sharing one IAM role across 10 clusters requires editing IAM trust policies for every cluster.
  3. EKS Pod Identity (Modern Standard): Launched in late 2023 to fix IRSA's OIDC coupling. You run the eks-pod-identity-agent DaemonSet on nodes, which exposes a node-local credential endpoint at 169.254.170.23 (link-local, reachable by Pods with an injected AWS_CONTAINER_CREDENTIALS_FULL_URI + AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE). You bind a ServiceAccount to an IAM Role using the EKS API (aws eks create-pod-identity-association), and the IAM trust policy simply trusts the universal service principal pods.eks.amazonaws.com with sts:AssumeRole and sts:TagSession.
Figure 1: EKS Pod Identity removes per-cluster OIDC providers from IAM trust policies and attaches session tags (cluster, namespace, service account) automatically.
Confused Deputy Guard for Pod Identity

Because pods.eks.amazonaws.com is a shared AWS service principal rather than a cluster-specific OIDC URL, always include an aws:SourceAccount (and optionally aws:SourceArn) condition in your IAM role's trust policy so no external AWS account could ever reference your role via the EKS Pod Identity service.

3. ALB Ingress: target-type: ip vs. instance & Readiness Gates

Kubernetes Ingress objects do nothing on AWS until you install the AWS Load Balancer Controller inside kube-system (itself authenticated via Pod Identity or IRSA). When you create an Ingress, the controller provisions a real Application Load Balancer and reconciles Target Groups automatically.

Two annotations determine whether rolling deployments are zero-downtime or drop live traffic:

  • alb.ingress.kubernetes.io/target-type: ip (Recommended with VPC CNI): Registers each Pod's VPC IP directly into the ALB Target Group. Traffic flows ALB → Pod ENI directly, skipping an extra NodePort hop through kube-proxy iptables/IPVS, preserving true client source IP, and avoiding cross-AZ node bounces. (Required if you run Pods on EKS Fargate.)
  • alb.ingress.kubernetes.io/target-type: instance: Routes ALB → NodePort (30000–32767) → kube-proxy → Pod. If the Pod sits on a different node than the NodePort target, traffic makes an extra cross-node/cross-AZ hop and gets SNATed.
  • Pod Readiness Gates: Without labeling your namespace with elbv2.k8s.aws/pod-readiness-gate-inject: enabled, Kubernetes considers a new Pod "Ready" the instant its local readinessProbe passes—before the ALB registers the Pod IP and completes its target-group health checks (often 10–30 seconds later). During a rolling update, Kubernetes may terminate old Pods while new Pods are still initial in the ALB Target Group, producing bursts of HTTP 502/503. Readiness gates block old Pod termination until the ALB itself reports the new Pod as healthy.

4. Production Config: Pod Identity Trust Policy & ALB Ingress

Below is a production-safe EKS Pod Identity trust policy, CLI association, and zero-downtime ALB Ingress manifest: 

// 1. IAM Role Trust Policy for EKS Pod Identity (reusable across clusters in this account)
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "Service": "pods.eks.amazonaws.com" },
      "Action": ["sts:AssumeRole", "sts:TagSession"],
      "Condition": {
        "StringEquals": { "aws:SourceAccount": "111122223333" }
      }
    }
  ]
}

# 2. Associate Kubernetes ServiceAccount to the IAM Role (no OIDC provider needed)
aws eks create-pod-identity-association \
  --cluster-name prod-orders-eks \
  --namespace orders \
  --service-account orders-api-sa \
  --role-arn arn:aws:iam::111122223333:role/OrdersApiPodRole

# 3. Namespace label + Ingress with target-type: ip for Pod Readiness Gates
# kubectl label namespace orders elbv2.k8s.aws/pod-readiness-gate-inject=enabled
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: orders-api-ingress
  namespace: orders
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
    alb.ingress.kubernetes.io/healthcheck-path: /healthz
    alb.ingress.kubernetes.io/listen-ports: '[{"HTTPS":443}]'
spec:
  ingressClassName: alb
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: orders-api-svc
                port:
                  number: 8080

5. When NOT to Use EKS: ECS Fargate vs. EKS Decision Matrix

In Lesson 0026, you saw how ECS on Fargate abstracts hosts, assigns an ENI per Task, and attaches IAM roles natively via taskRoleArn. Before proposing EKS in an Architecture Decision Record (ADR), benchmark your team against this matrix:

Dimension ECS on Fargate Amazon EKS
Control Plane Cost $0 / month (pay only per vCPU/GB-sec of running tasks) $73 / month per cluster ($438/mo in Extended Support) + add-on overhead
IAM per Workload Native taskRoleArn on Task Definition; zero agents Requires Pod Identity Agent DaemonSet (or cluster OIDC + IRSA webhook)
Upgrade Treadmill AWS patches Fargate platform versions transparently ~3 Kubernetes minor versions/year; must test deprecated APIs, CNI & CSI drivers
Networking & IPs 1 ENI / 1 private IP per Fargate Task automatically VPC CNI secondary IPs + warm pool tuning; prefix delegation needed for density
When It Wins Teams < 25 devs, < 30 services, standard APIs/workers, zero platform SREs Custom GPU/ML bin-packing (Karpenter), CNCF/Helm/CRD platforms, strict multi-cloud

Rule of thumb: If you do not have a dedicated platform team to own Kubernetes upgrades, CoreDNS, Metrics Server, Cluster Autoscaler/Karpenter, and Ingress controller lifecycles—and you do not strictly need Kubernetes CRDs or specialized EC2 GPU scheduling—choose ECS on Fargate.
