AWS CDK (TypeScript): L1/L2/L3 Constructs, Aspects, cdk-nag & Assertions

Hand-writing thousands of lines of raw CloudFormation YAML does not scale across microservices. AWS CDK lets you compose typed infrastructure trees in TypeScript, apply cross-cutting security policies with Aspects and cdk-nag, and assert synthesized templates in CI before touching a live AWS account—while hiding one notorious Logical ID trap when refactoring stateful resources.

Your Android Bridge

In Jetpack Compose, you build UI out of a hierarchical tree of reusable @Composable functions, pass cross-cutting styling via Modifier chains and CompositionLocal, and verify behavior in unit tests using ComposeTestRule without booting a full device every time. In AWS CDK, your TypeScript classes build an in-memory Construct Tree (App → Stack → Construct → CfnResource), apply cross-cutting governance across every node with Aspects (just like a tree visitor), and verify the compiled output in milliseconds using aws-cdk-lib/assertions.

1. The Construct Tree & Synthesis Lifecycle

A critical mental model shift for CDK beginners: AWS never executes your TypeScript code at deploy time. Instead, running cdk synth executes your TypeScript locally (or in CI) to build an in-memory Construct tree and compile it into deterministic CloudFormation JSON templates inside cdk.out/ (capped at CloudFormation's 500 resources per stack and 1 MB S3-staged template limit).

Every Construct constructor takes three canonical parameters—(scope, id, props)—which form a tree path such as OrdersApp/ProdStack/OrderStorage/OrdersBucket. According to the AWS CDK Identifiers specification, CDK computes each CloudFormation Logical ID by stripping non-alphanumerics from the path and appending an 8-hex-character MD5 hash of the construct's full path (e.g., OrderStorageOrdersBucket8F3A12B9).

The Production Refactoring Trap: Renaming Stateful Construct IDs

If you wrap an existing dynamodb.Table or s3.Bucket inside a new parent Construct—or rename its id string—its construct path changes, so its CloudFormation Logical ID hash changes. CloudFormation treats a new Logical ID as an entirely new resource: if the physical name is auto-generated, CloudFormation creates a brand-new empty table/bucket and removes the old one from the stack (leaving the old resource orphaned under RemovalPolicy.RETAIN, or permanently deleting production data if RemovalPolicy.DESTROY was set). If the physical name was hardcoded, deployment fails immediately with AlreadyExists.

During cdk synth, the Construct tree passes through four deterministic phases:

  1. Construction: Constructors instantiate child constructs, register L1 CfnResource nodes, and wire IAM permissions (grantRead) and environment variables.
  2. Prepare (Aspects): Every IAspect attached to a node invokes visit(node) top-down across that subtree—mutating properties, adding tags, or registering compliance checks.
  3. Validate: CDK runs every node's validate() hook. Any error added via Annotations.of(node).addError(...) aborts synthesis with a non-zero exit code before deployment begins.
  4. Synthesize: Emits CloudFormation JSON templates, asset manifests (Docker images, Lambda ZIPs), and tree.json metadata to cdk.out/.

2. L1, L2, and L3 Constructs — Plus Escape Hatches

AWS CDK organizes abstractions into three tiers, matching the AWS CDK Constructs Guide:

  • L1 (Cfn* Resources): Auto-generated 1:1 from the CloudFormation Resource Specification (e.g., s3.CfnBucket, iam.CfnRole). Zero defaults, zero helper methods, raw CloudFormation PascalCase or typed property shapes. Use L1 directly only when AWS launches a brand-new CloudFormation property before an L2 wrapper supports it.
  • L2 (Curated Intent-Based Constructs): Resource classes like s3.Bucket, lambda.Function, and ec2.Vpc. They supply sane defaults, type-safe enums, automatic cross-stack exports, and least-privilege IAM helpers such as bucket.grantRead(fn)—which inspects the bucket ARN, KMS key ARN (if encrypted), and Lambda execution role to emit exact scoped actions rather than s3:*.
  • L3 (Patterns): Multi-resource architectures bundled behind a narrow domain interface, either from AWS (ecs_patterns.ApplicationLoadBalancedFargateService) or your own platform team (e.g., CompliantApiService wiring API Gateway + Lambda + KMS + CloudWatch Alarms).

Escape Hatches bridge the gap when an L2 omits a newly released CloudFormation property: access the underlying L1 node via bucket.node.defaultChild as s3.CfnBucket and set typed properties or call cfnBucket.addPropertyOverride("VersioningConfiguration.Status", "Enabled"). You keep L2 grant* ergonomics without rewriting the resource in raw L1.

Tradeoff & Feature Flags: L2 defaults can evolve over time. CDK pins potentially breaking default changes behind feature flags in cdk.json (e.g., @aws-cdk/aws-s3:createDefaultLoggingPolicy). Never blindly run cdk init flags into an existing production repo without running cdk diff first—a flipped feature flag can silently alter IAM policies or Logical IDs across dozens of stacks.

3. Governance at Scale: Aspects & cdk-nag

In Jetpack Compose, you do not ask every developer to remember accessibility contrast or font scaling inside every screen; you enforce defaults centrally at the theme/modifier boundary. In CDK, Aspects implement the Visitor pattern (IAspect with visit(node: IConstruct): void) to enforce invariants across every stack in an organization.

  • Validating vs. Mutating Aspects: A validating aspect checks nodes and calls Annotations.of(node).addError("...") when a policy fails. A mutating aspect modifies the tree—for example, calling Tags.of(app).add("CostCenter", "checkout") or forcing CfnBucket encryption overrides.
  • Why Aspects Must Target L1 CfnResource Nodes: Aspects run after construct constructors finish. Because L2 constructs instantiate their underlying L1 CfnResource children inside their constructors, mutating an L2 helper property inside an Aspect frequently has no effect on the emitted JSON. Always inspect or mutate the underlying L1 node (if (node instanceof s3.CfnBucket)).
  • cdk-nag Compliance Packs: Maintained by AWS Labs, cdk-nag ships built-in Aspect packs such as AwsSolutionsChecks, HIPAASecurityChecks, and NIST80053R5Checks. It flags violations like AwsSolutions-S1 (missing S3 server access logs), AwsSolutions-S10 (missing TLS-only bucket policy), and AwsSolutions-IAM5 (wildcard IAM actions or resources).
  • Granular Suppressions: When an exception is legitimately required (for example, CloudWatch Logs or KMS permissions on a wildcard log group prefix), use NagSuppressions.addResourceSuppressions(role, [{ id: "AwsSolutions-IAM5", reason: "...", appliesTo: ["Action::s3:GetObject*", "Resource::*"] }]). Always include appliesTo so a blanket suppression does not silently hide future over-privileged wildcards added to the same role.

4. Production TypeScript Example: L3 Construct, Aspect, cdk-nag & Assertions

Notice how the L3 construct encapsulates compliant defaults, the custom IAspect enforces KMS encryption and private VPC placement across all stacks, AwsSolutionsChecks audits synthesized L1 nodes, and aws-cdk-lib/assertions verifies the final CloudFormation JSON in Jest without hitting AWS. 

import { Aspects, CfnResource, IAspect, RemovalPolicy, Stack, StackProps, Annotations } from "aws-cdk-lib";
import { Match, Template } from "aws-cdk-lib/assertions";
import * as ec2 from "aws-cdk-lib/aws-ec2";
import * as kms from "aws-cdk-lib/aws-kms";
import * as lambda from "aws-cdk-lib/aws-lambda";
import * as s3 from "aws-cdk-lib/aws-s3";
import { AwsSolutionsChecks, NagSuppressions } from "cdk-nag";
import { Construct, IConstruct } from "constructs";

// 1. L3 Construct: opinionated company pattern bundling KMS + S3 + least-privilege grant
export class EncryptedArtifactStore extends Construct {
  public readonly bucket: s3.Bucket;
  constructor(scope: Construct, id: string, key: kms.IKey) {
    super(scope, id);
    this.bucket = new s3.Bucket(this, "Bucket", {
      encryption: s3.BucketEncryption.KMS,
      encryptionKey: key,
      enforceSSL: true,
      blockPublicAccess: s3.BlockPublicAccess.BLOCK_ALL,
      removalPolicy: RemovalPolicy.RETAIN,
    });
  }
}

// 2. Custom Validating Aspect: runs during Prepare phase on L1 CfnResource nodes
export class OrgSecurityAspect implements IAspect {
  public visit(node: IConstruct): void {
    if (node instanceof s3.CfnBucket) {
      if (!node.bucketEncryption) {
        Annotations.of(node).addError("OrgPolicy: All S3 buckets must declare BucketEncryption.");
      }
    }
    if (node instanceof lambda.CfnFunction && !node.vpcConfig) {
      Annotations.of(node).addWarning("OrgPolicy: Lambda function has no VpcConfig attached.");
    }
  }
}

// 3. Stack wiring + cdk-nag + granular suppression
export class OrdersStack extends Stack {
  constructor(scope: Construct, id: string, props?: StackProps) {
    super(scope, id, props);
    const vpc = new ec2.Vpc(this, "Vpc", { maxAzs: 2, natGateways: 1 });
    const key = new kms.Key(this, "DataKey", { enableKeyRotation: true });
    const store = new EncryptedArtifactStore(this, "Artifacts", key);

    const fn = new lambda.Function(this, "Processor", {
      runtime: lambda.Runtime.NODEJS_20_X,
      handler: "index.handler",
      code: lambda.Code.fromInline("exports.handler = async () => ({ ok: true });"),
      vpc,
      vpcSubnets: { subnetType: ec2.SubnetType.PRIVATE_WITH_EGRESS },
    });
    store.bucket.grantRead(fn); // Generates scoped IAM policy + KMS Decrypt permissions

    // Escape hatch example: override an L1 property directly
    const cfnBucket = store.bucket.node.defaultChild as s3.CfnBucket;
    cfnBucket.addPropertyOverride("VersioningConfiguration.Status", "Enabled");

    NagSuppressions.addResourceSuppressions(
      fn,
      [{ id: "AwsSolutions-IAM5", reason: "grantRead uses s3:GetObject* on the artifact bucket only", appliesTo: ["Action::s3:GetObject*"] }],
      true
    );
    Aspects.of(this).add(new OrgSecurityAspect());
    Aspects.of(this).add(new AwsSolutionsChecks({ verbose: true }));
  }
}

// 4. Fine-grained CloudFormation template assertions (Jest)
test("OrdersStack enforces KMS encryption, SSL, and private VPC Lambda placement", () => {
  const stack = new OrdersStack(new (require("aws-cdk-lib").App)(), "TestOrders");
  const template = Template.fromStack(stack);

  template.hasResourceProperties("AWS::S3::Bucket", {
    BucketEncryption: Match.objectLike({
      ServerSideEncryptionConfiguration: Match.arrayWith([
        Match.objectLike({ ServerSideEncryptionByDefault: { SSEAlgorithm: "aws:kms" } }),
      ]),
    }),
    VersioningConfiguration: { Status: "Enabled" },
  });

  template.hasResourceProperties("AWS::Lambda::Function", {
    VpcConfig: Match.objectLike({
      SubnetIds: Match.anyValue(),
      SecurityGroupIds: Match.anyValue(),
    }),
  });
});

Why prefer fine-grained assertions (hasResourceProperties, Match.objectLike, resourceCountIs) over giant Jest toMatchSnapshot() files? Snapshot tests break on every benign Lambda ZIP hash or CDK metadata bump—training engineers to blindly run jest -u and approve accidental IAM wildcards or deleted KMS keys. Reserve snapshot tests only for small, stable core-networking stacks, and pair fine-grained assertions with Annotations.fromStack(stack).hasNoError(...) in CI.
