CloudFormation Internals: Change Sets, Rollbacks, Drift & StackSets

Before adopting AWS CDK or Terraform, you must understand the declarative control-plane engine underneath AWS itself: how CloudFormation compiles templates into a resource DAG, why a single property edit triggers destructive replacement, how DeletionPolicy and UpdateReplacePolicy protect stateful databases, why out-of-band console edits poison rollbacks, and how StackSets roll out organization-wide guardrails safely.

Your Android Bridge

In Android, your build.gradle.kts and Hilt modules declare what dependencies and components exist—not imperative shell commands telling kotlinc which file to compile first. Gradle builds a Directed Acyclic Graph (DAG), resolves edges, and only rebuilds dirty nodes. AWS CloudFormation does the exact same thing for cloud infrastructure: you declare VPCs, IAM roles, and RDS databases with !Ref, !GetAtt, and DependsOn edges, and CloudFormation computes a plan (a Change Set) against live stack state. The critical difference: when Gradle decides a build cache key changed, wiping build/ is harmless; when CloudFormation decides a property change requires Replacement: True on a database, wiping the old node destroys production user data unless you explicitly guard it.

1. The Declarative Engine: DAG Resolution, Stacks & Quotas

Imperative provisioning scripts (aws rds create-db-instance ...) break the moment step 4 of 12 fails: you are left with half-created subnets, orphaned security groups, and no automatic rollback or diffing. A CloudFormation Stack solves this by storing a declarative template, parameter values, and the mapping from Logical IDs (names inside your template) to Physical IDs (real ARNs/names in AWS).

At deploy time, CloudFormation constructs a Directed Acyclic Graph (DAG):

  • Implicit edges: Using !Ref Vpc or !GetAtt OrdersDB.Endpoint.Address forces CloudFormation to finish provisioning the referenced resource (or wait until the attribute is available) before creating the dependent resource.
  • Explicit edges: DependsOn: [GatewayAttachment] enforces ordering when no direct property reference exists (such as waiting for an Internet Gateway attachment before creating a default route).
  • Parallel execution: Independent branches of the DAG execute concurrently up to service throttling limits, while deletions run in exact reverse topological order.

Per the AWS CloudFormation Quotas specification, every stack faces hard structural boundaries you must design around early:

  • 500 resources maximum per template (pushing teams toward modular multi-stack architectures rather than one giant monolith).
  • 51,200 bytes max template size via direct API body upload, or 1,048,576 bytes (1 MB) when staged in S3.
  • 200 parameters, 200 mappings, and 200 outputs per template; 2,000 stacks default limit per account per region.

2. Change Sets & Replacement Blast Radius

Running aws cloudformation deploy blindly applies changes immediately. In production, senior teams separate planning from execution using a Change Set (create-change-set → inspect → execute-change-set). Note that a stack can hold up to 100 unexecuted Change Sets, and creating a Change Set executes zero infrastructure mutations.

Every entry in describe-change-set reports an Action (Add, Modify, Remove, Import, or Dynamic) and—for modifications—a Replacement field with three possible values:

  • Replacement: False: In-place update (e.g., changing a Lambda memory size, adding a DynamoDB GSI, or editing tags). Minimal blast radius.
  • Replacement: True: CloudFormation cannot mutate the property in place (e.g., changing a DynamoDB partition key, an RDS DBName/AvailabilityZone, or an S3 bucket name). It creates a brand-new physical resource, updates downstream references, and then deletes the old resource.
  • Replacement: Conditional: Replacement depends on runtime parameter values or conditions (treat this as True during code review unless proven otherwise).
Figure 1: CloudFormation builds a replacement before deleting the original resource. Hardcoded physical names block creation of the replacement, causing immediate rollback.
The Hardcoded Physical Name Anti-Pattern

Never hardcode physical names like TableName: orders-prod, BucketName: myapp-assets, or DBInstanceIdentifier: primary-db on resources that might ever be replaced. Because CloudFormation performs create-before-delete during Replacement: True, two resources with the exact same physical name cannot coexist in AWS—so the replacement immediately fails with AlreadyExistsException! Let CloudFormation auto-generate unique physical names (or include a version suffix) and pass them around via !Ref and !GetAtt.

3. Stateful Protection (DeletionPolicy, UpdateReplacePolicy) & Rollback Traps

Two separate attributes govern what happens to physical data when CloudFormation lets go of a resource, and confusing them is a classic senior production incident:

  • DeletionPolicy (Delete [default], Retain, Snapshot): Fires when you remove the resource from the template or delete the entire stack.
  • UpdateReplacePolicy (Delete [default], Retain, Snapshot): Fires when a stack update triggers Replacement: True and CloudFormation disposes of the old physical resource after creating the new one.

If you put DeletionPolicy: Retain on an AWS::RDS::DBInstance but forget UpdateReplacePolicy, a Change Set that replaces the DB instance will spin up an empty database and delete your original production database once the swap finishes! Furthermore, per the CloudFormation DeletionPolicy documentation, Snapshot is supported only on select resource types (such as AWS::RDS::DBInstance, AWS::RDS::DBCluster, AWS::EC2::Volume, and AWS::ElastiCache::ReplicationGroup). Setting Snapshot on AWS::DynamoDB::Table or AWS::S3::Bucket is invalid and fails stack validation/deletion.

As a second line of defense, attach a Stack Policy (a resource-based JSON policy on the stack itself) that explicitly denies Update:Replace and Update:Delete on critical logical IDs like OrdersDB and OrdersTable. Even if an engineer accidentally approves a destructive Change Set, CloudFormation rejects the update at execution time unless a separate overriding stack policy is explicitly supplied.

Rollback Mechanics & UPDATE_ROLLBACK_FAILED: By default, any failed resource step during an update puts the stack into UPDATE_ROLLBACK_IN_PROGRESS, reverting modified resources to the prior template. If that rollback itself hits an unrecoverable error—for instance, an out-of-band edit deleted a referenced security group, IAM permissions were revoked, or an S3 bucket is non-empty—the stack freezes in UPDATE_ROLLBACK_FAILED. No further updates or deletes can run until you manually reconcile the broken resource and call aws cloudformation continue-update-rollback --resources-to-skip <LogicalId>.

4. Drift Detection & Out-of-Band Console Edits

ClickOps—editing a Lambda timeout, opening a Security Group port, or deleting an IAM policy directly in the AWS Console during an incident—creates configuration drift. CloudFormation stores the template it last deployed, not live AWS state, so routine updates do not automatically detect console changes.

Running Stack Drift Detection (detect-stack-drift) inspects live resource properties against the stack's expected template state and classifies each supported resource as:

  • IN_SYNC: Live properties match the template definition.
  • MODIFIED: Property-level diff shows ADD, REMOVE, or NOT_EQUAL between expected and actual JSON.
  • DELETED: The physical resource no longer exists in AWS (a ticking time bomb for UPDATE_ROLLBACK_FAILED).
  • NOT_CHECKED: Resource type does not support drift detection yet.

Critically, CloudFormation drift detection is read-only—it alerts you, but never auto-remediates. To bring a drifted resource back under IaC control cleanly, either update the template to match the desired live configuration (or revert the console edit), or use Resource Import when adopting unmanaged resources into a stack.

5. Multi-Account & Multi-Region Rollouts with StackSets

A single CloudFormation stack deploys into one account and one region. When your organization runs 50+ accounts across dev, staging, production, and security OUs, deploying baseline IAM roles, AWS Config rules, or CloudTrail trails stack-by-stack breaks down. AWS CloudFormation StackSets manage a single template from an administrator (or delegated admin) account and stamp out Stack Instances across any matrix of target accounts and regions.

  • SELF_MANAGED permissions: You manually create AWSCloudFormationStackSetAdministrationRole in the hub account and AWSCloudFormationStackSetExecutionRole trust roles in every spoke account.
  • SERVICE_MANAGED permissions: Integrates directly with AWS Organizations and Organizational Units (OUs). Enabling AutoDeployment automatically provisions baseline stacks whenever a new AWS account joins an OU—and automatically retains or deletes them if an account leaves.

To prevent a broken template change from taking down every production account simultaneously, always configure OperationPreferences as a deployment circuit breaker:

  • MaxConcurrentCount / MaxConcurrentPercentage: Limits simultaneous account-region deployments (e.g., roll out to 1 canary account or 10% first).
  • FailureToleranceCount / FailureTolerancePercentage: Stops the entire StackSet rollout once failures exceed your threshold (set FailureToleranceCount: 0 for zero-tolerance security/network baselines).
  • RegionConcurrencyType: Choose SEQUENTIAL (region-by-region blast containment) or PARALLEL (faster rollouts for low-risk updates), alongside STRICT_FAILURE_TOLERANCE so later regions never start after an earlier failure threshold trips.

6. Production Code Example: Stateful Guardrails & CLI Workflow

Below is a production-safe CloudFormation snippet protecting stateful databases during both deletion and replacement, paired with the exact CLI Change Set and StackSet rollout commands: 

# 1. template.yaml — Stateful Resources with Full Protection & Auto-Generated Physical Names
AWSTemplateFormatVersion: "2010-09-09"
Resources:
  OrdersTable:
    Type: AWS::DynamoDB::Table
    DeletionPolicy: Retain         # Survives stack delete / resource removal
    UpdateReplacePolicy: Retain    # Survives key-schema replacement (Snapshot unsupported on DynamoDB!)
    Properties:
      # Omit TableName so CloudFormation generates a unique name (avoids create-before-delete collision)
      BillingMode: PAY_PER_REQUEST
      AttributeDefinitions:
        - AttributeName: orderId
          AttributeType: S
      KeySchema:
        - AttributeName: orderId
          KeyType: HASH

  OrdersDatabase:
    Type: AWS::RDS::DBInstance
    DeletionPolicy: Snapshot       # RDS supports Snapshot on delete AND on UpdateReplacePolicy
    UpdateReplacePolicy: Snapshot
    Properties:
      Engine: postgres
      EngineVersion: "16.3"
      DBInstanceClass: db.t4g.medium
      AllocatedStorage: 100

# 2. stack-policy.json — Block accidental Replacement or Delete on stateful databases
# {
#   "Statement": [
#     { "Effect": "Allow", "Action": "Update:*", "Principal": "*", "Resource": "*" },
#     { "Effect": "Deny", "Action": ["Update:Replace", "Update:Delete"],
#       "Principal": "*", "Resource": ["LogicalResourceId/OrdersTable", "LogicalResourceId/OrdersDatabase"] }
#   ]
# }

# 3. Safe Production CLI Workflow (Change Set + Drift Check + StackSet Canary)
aws cloudformation detect-stack-drift --stack-name orders-prod
aws cloudformation create-change-set --stack-name orders-prod --template-body file://template.yaml --change-set-name v42-rollout
aws cloudformation describe-change-set --stack-name orders-prod --change-set-name v42-rollout --query 'Changes[*].[ResourceChange.LogicalResourceId,ResourceChange.Action,ResourceChange.Replacement]'
aws cloudformation execute-change-set --stack-name orders-prod --change-set-name v42-rollout

aws cloudformation update-stack-instances \
  --stack-set-name org-security-baselines \
  --deployment-targets OrganizationalUnitIds=ou-prod-12345 \
  --regions us-east-1 us-west-2 \
  --operation-preferences RegionConcurrencyType=SEQUENTIAL,MaxConcurrentPercentage=10,FailureToleranceCount=0,ConcurrencyMode=STRICT_FAILURE_TOLERANCE

7. Interactive Code Practice (Runs Live & Checks)

Implement auditChangeSet(templateResources, changes, stackPolicy) to catch destructive replacement blast-radius traps before calling execute-change-set: hardcoded physical name collisions, missing UpdateReplacePolicy or DeletionPolicy on stateful resources, invalid Snapshot policies on DynamoDB/S3, and changes blocked by a Stack Policy.
