Part 1 Capstone: Distributed Order & Ledger Backend

Every concept from Part 1—Android OkHttp pooling, HTTP timeouts, JWT auth, Redis caching, PostgreSQL ACID transactions, the Transactional Outbox, idempotent workers, OpenTelemetry traces, Testcontainers CI, and load testing—converges here into one cloud-portable backend ready for AWS in Part 2.

Your Android Bridge

Think about how a resilient Android checkout feature works offline-first: Retrofit + OkHttp reuses a pooled TLS socket and attaches an Idempotency-Key UUID, while WorkManager persists pending mutations in Room so a subway tunnel dropout triggers a safe retry instead of charging the user twice. Now build the server side that honors that contract end-to-end—without losing an event, overselling stock, or double-posting a ledger entry.

1. Full-Stack Target Architecture: Android Client to Ledger Commit

In Part 1, you studied individual failure modes in isolation. In production, those layers interact under concurrency and partial network failures. Our capstone target pairs a mobile checkout client with a five-component cloud-portable backend:

  1. Reverse Proxy / Edge Gateway: Terminates TLS 1.3, validates JWT signatures (Lesson 0005), enforces token-bucket rate limits (Lesson 0004), and maintains keep-alive timeouts strictly shorter than the upstream API server’s keepAliveTimeout (Lesson 0001: e.g., Proxy 60s → API 65s).
  2. Order API Service: Runs as a non-root container (Lesson 0012), parses incoming W3C traceparent headers (Lesson 0013), checks Redis/Postgres for Idempotency-Key replay or payload mismatch, and executes a single atomic PostgreSQL transaction.
  3. Redis Cache Layer: Serves read-heavy SKU catalog and stock-level views via cache-aside with TTL jitter (e.g., 30s + random(0, 6s)) and singleflight coalescing to prevent cache stampedes during flash sales (Lesson 0006).
  4. PostgreSQL Primary (Source of Truth): Holds orders, inventory, ledger_entries, idempotency_keys, and outbox_events behind a bounded connection pool (e.g., 20 connections per instance, Lesson 0007).
  5. Async Outbox Relay & Worker: Polls or tails outbox_events, dispatches fulfillment/receipt work with exponential backoff + full jitter (Lesson 0010), deduplicates via processed_events, and quarantines poison messages into a Dead Letter Queue (DLQ, Lesson 0011).

2. Five System Invariants & How They Fail Under Load

A senior backend engineer defines correctness by invariants—properties that must remain true even when mobile clients retry, containers crash mid-request, or concurrent buyers race for the last unit in stock:

  • Invariant 1 — No Dual-Write Split-Brain: Writing to PostgreSQL and then calling a message broker outside the transaction leaves a crash window (often 0.1%–0.5% during deploys or network blips). At 500,000 orders/day, a 0.2% gap orphans 1,000 paid orders every day. Inserting into outbox_events inside the same COMMIT guarantees atomicity.
  • Invariant 2 — Strict Idempotency Semantics: When Android WorkManager retries a timed-out POST /v1/orders with the same Idempotency-Key and identical canonical payload hash, the API must return the exact stored status and orderId without deducting stock twice. If the same key arrives with a different payload hash, reject with 422 Unprocessable Entity (IDEMPOTENCY_CONFLICT) so a buggy client cannot silently mutate an old order.
  • Invariant 3 — Zero Oversell Under Contention: Reading SELECT available FROM inventory in application code and updating later fails under concurrent transactions at PostgreSQL’s default READ COMMITTED isolation level. Instead, use a single atomic conditional update: UPDATE inventory SET available = available - $1 WHERE sku = $2 AND available >= $1. Zero rows updated means insufficient stock; roll back cleanly.
  • Invariant 4 — At-Least-Once Worker Deduplication & Bounded DLQ: A worker can crash after sending a receipt or posting a downstream ledger credit but before marking the outbox row done. Every worker must insert event_id into processed_events (unique primary key) inside its completion transaction. Poison-pill events that fail past maxAttempts (e.g., 5 retries with exponential backoff + full jitter) must transition to DLQ rather than starving healthy orders.
  • Invariant 5 — Graceful Shutdown & Load Verification: On SIGTERM, the API stops accepting new sockets, drains in-flight requests inside the container grace window (e.g., 25s before Docker/ECS sends SIGKILL at 30s), and closes DB pools cleanly. Integration tests with Testcontainers and k6/Locust load runs verify p99 latency < 150 ms, zero negative inventory, and 100% outbox-to-ledger reconciliation.
Golden Capstone Rule: Prove Conservation, Don’t Assume It

Never judge a load test solely by HTTP 200/201 rates. Always run an end-of-test reconciliation query asserting: initial_stock == remaining_stock + SUM(committed_order_qty) and confirmed_orders == processed_ledger_events. If either equation drifts by even 1 unit, you have a concurrency or idempotency bug.

3. Production Blueprint: Atomic Checkout SQL + Outbox Relay

Below is the core PostgreSQL schema and atomic transaction boundary that enforces idempotency, conditional stock reservation, double-entry ledger intent, and outbox creation in a single round-trip block: 

-- 1. Core tables with database-enforced invariants
CREATE TABLE inventory (
  sku        TEXT PRIMARY KEY,
  available  INTEGER NOT NULL CHECK (available >= 0)
);

CREATE TABLE idempotency_keys (
  key           TEXT PRIMARY KEY,
  payload_hash  TEXT NOT NULL,
  response_code INTEGER NOT NULL,
  order_id      UUID,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE outbox_events (
  event_id    UUID PRIMARY KEY,
  order_id    UUID NOT NULL,
  payload     JSONB NOT NULL,
  attempts    INTEGER NOT NULL DEFAULT 0,
  status      TEXT NOT NULL CHECK (status IN ('PENDING', 'PROCESSED', 'DLQ')),
  next_run_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 2. Atomic checkout inside ONE ACID transaction (Order API)
BEGIN;
  -- Guard 1: Lock/check idempotency record first (ON CONFLICT DO NOTHING pattern in app)
  -- Guard 2: Conditional atomic stock reservation (zero oversells under READ COMMITTED)
  UPDATE inventory
     SET available = available - $1
   WHERE sku = $2 AND available >= $1
  RETURNING available; -- 0 rows => ROLLBACK and return 409 INSUFFICIENT_STOCK

  INSERT INTO orders (order_id, sku, qty, status) VALUES ($3, $2, $1, 'PENDING');
  INSERT INTO outbox_events (event_id, order_id, payload, status)
  VALUES ($4, $3, jsonb_build_object('sku', $2, 'qty', $1, 'traceparent', $5), 'PENDING');
COMMIT;

-- 3. Concurrent worker lease using SKIP LOCKED (prevents head-of-line blocking)
SELECT event_id, order_id, payload, attempts
  FROM outbox_events
 WHERE status = 'PENDING' AND next_run_at <= now()
 ORDER BY next_run_at ASC
 FOR UPDATE SKIP LOCKED
 LIMIT 25;
