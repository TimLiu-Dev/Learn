CloudFront CDN: Origin Access Control (OAC), Cache Keys & Edge Functions

Putting a CDN in front of S3 or an ALB is trivial; operating it at senior scale without leaking private origins, tanking your cache hit ratio with fragmented cache keys, or overpaying for Lambda@Edge when a sub-millisecond CloudFront Function suffices is where production mastery lives.

Your Android Bridge

In Android, you pass a Cache(context.cacheDir, 50L * 1024 * 1024) to OkHttpClient so repeated image or catalog fetches hit disk instead of traversing the cellular network. Amazon CloudFront is that exact HTTP cache moved onto 600+ global Edge Points of Presence (POPs)—with one critical distinction: OkHttp is a private cache for one device (governed by max-age), whereas CloudFront is a shared cache serving millions of devices (governed by s-maxage and strict cache-key normalization).

1. From OkHttp Cache-Control to CloudFront Edge POPs

When an Android app in Sao Paulo requests https://cdn.myapp.com/catalog/v2/items.json, the packet terminates TLS at the nearest CloudFront Edge POP (often 10–25 ms away) rather than crossing the ocean to us-east-1 (130+ ms).

Under RFC 9111 (HTTP Caching), the origin's Cache-Control header speaks separately to shared CDN caches and private device caches:

  • s-maxage=3600: Applies only to shared caches (CloudFront). It overrides max-age inside the Edge POP, provided it falls inside your Cache Policy's [MinTTL, MaxTTL] bounds.
  • max-age=60: Governs OkHttp's on-device cache (and acts as the fallback for CloudFront if s-maxage is omitted). This pattern lets you push fresh catalog updates to phones within 60 seconds while shielding your origin for a full hour—invalidating CloudFront once on deploy.
  • private or no-store: Instructs CloudFront never to store the response in shared POP memory. Returning private is mandatory for user-specific payloads so User B never receives User A's cached JSON.
  • stale-while-revalidate=30: Allows CloudFront to serve a slightly expired object instantaneously while asynchronously refreshing it from the origin in the background, keeping p99 tail latency flat.
Figure 1: CloudFront separates client caching (max-age) from edge caching (s-maxage) and signs origin misses to a completely private S3 bucket using OAC SigV4.

2. Securing Private S3 Origins: Origin Access Control (OAC) vs. Legacy OAI

A classic beginner mistake is enabling S3 Static Website Hosting or toggling off Block Public Access so CloudFront can read files. That exposes the raw bucket.s3.amazonaws.com endpoint to the internet—allowing attackers to bypass your AWS WAF, geo-restrictions, and CloudFront Signed URLs while billing you uncached S3 data transfer rates.

Instead, you keep S3 100% private (all four Block Public Access toggles enabled) and attach a CloudFront Origin Access Control (OAC). On every cache miss, CloudFront dynamically signs the upstream request using AWS Signature Version 4 (SigV4) under the cloudfront.amazonaws.com service principal, and your S3 bucket policy restricts access to your exact distribution via aws:SourceArn.

Two OAC Traps That Cause 403 Errors in Production

1. SSE-KMS Key Policy Missing CloudFront: Unlike legacy Origin Access Identity (OAI), OAC supports customer-managed SSE-KMS keys—provided your KMS key policy explicitly grants kms:Decrypt, kms:Encrypt, and kms:GenerateDataKey* to cloudfront.amazonaws.com scoped by aws:SourceArn. Without it, S3 returns 403 AccessDenied even when the S3 bucket policy is perfect.
2. Omitting aws:SourceArn (Confused Deputy): Allowing cloudfront.amazonaws.com without a condition lets any AWS customer's CloudFront distribution point at your bucket and read your objects.

3. Cache Policies, Cache Keys & Why Fragmentation Kills Hit Ratio

When a request reaches a CloudFront POP, CloudFront constructs a Cache Key—the unique lookup string inside its distributed cache. By default, a managed policy like CachingOptimized hashes only the host and URI path (plus gzip/brotli encoding), ignoring query strings, cookies, and arbitrary headers.

Every extra dimension you add to the Cache Key multiplies cardinality and crushes your Cache Hit Ratio (CHR):

  • Marketing & Tracking Parameters: If your policy caches on all query strings, links containing ?fbclid=... or ?utm_source=... generate millions of distinct cache keys for the identical JPEG, dropping CHR from 95% to under 20%.
  • User-Agent or Accept-Language Fragmentation: Android devices send hundreds of distinct User-Agent strings (Dalvik/2.1.0 (Linux; U; Android 14; Pixel 8...)). Including User-Agent in the cache key creates a separate cached copy per phone model and OS patch!
  • Cache Policy vs. Origin Request Policy: Never add a header or query string to a Cache Policy just because your backend wants to log or read it. Put cache-varying inputs (e.g., v, region) in the Cache Policy, and put non-varying metadata (e.g., X-Request-Id, CloudFront-Viewer-Country) in an Origin Request Policy so they reach your origin without splitting the cache key.

4. Edge Compute: CloudFront Functions vs. Lambda@Edge

Before a request hits the cache lookup—or right before a response leaves the POP—you can execute code at the edge. Choosing the wrong runtime blows up latency and bills by an order of magnitude:

Dimension CloudFront Functions Lambda@Edge
Execution Location 600+ Edge Locations (POPs) Regional Edge Caches (RECs)
Triggers Viewer Request, Viewer Response only All 4 (Viewer & Origin Request/Response)
Runtime & Limits JS (cloudfront-js-2.0), <1 ms, 2 MB RAM, 10 KB max code Node.js / Python, 5s–30s timeout, 128 MB–10 GB RAM, 1–50 MB pkg
Network / Body Access None (no external HTTP, no DynamoDB, no request body) Full network I/O, AWS SDK calls, and request/response body access
Typical Use Cases Strip utm_* params, URL rewrites, security headers, cache-key normalization Dynamic origin routing via DynamoDB, image resizing, S3 auth token exchange

5. Production Config: S3 OAC Policy & Cache-Normalizing Edge Function

Below are the two production artifacts you deploy together: the least-privilege S3 bucket policy locked to your CloudFront distribution ARN, and a sub-millisecond cloudfront-js-2.0 viewer-request function that strips tracking parameters before cache key lookup. 

// 1. S3 Bucket Policy (Block Public Access = ALL ON, OAC SigV4 Only)
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowCloudFrontServicePrincipalReadOnly",
      "Effect": "Allow",
      "Principal": { "Service": "cloudfront.amazonaws.com" },
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::myapp-private-media/*",
      "Condition": {
        "StringEquals": {
          "AWS:SourceArn": "arn:aws:cloudfront::123456789012:distribution/E1ABC2DEF3GHIJ"
        }
      }
    }
  ]
}

// 2. CloudFront Function (cloudfront-js-2.0, Viewer Request, < 1 ms)
// Strips marketing query params before cache lookup so hit ratio stays > 95%.
function handler(event) {
  var request = event.request;
  var qs = request.querystring;
  var dropKeys = ["utm_source", "utm_medium", "utm_campaign", "fbclid", "gclid"];

  for (var i = 0; i < dropKeys.length; i++) {
    delete qs[dropKeys[i]];
  }
  return request;
}

Why OAC Replaced OAI Legacy Origin Access Identity (OAI) used a static CloudFront user identity that failed on SSE-KMS encrypted S3 objects, newer opt-in AWS regions, and PUT/POST requests. OAC uses standard SigV4 signing and works everywhere.
Invalidation vs. Versioned Keys Running CreateInvalidation for /* flushes every POP globally (first 1,000 paths/month free, then billed per path). Senior teams avoid invalidations for assets by embedding a content hash in the URL (app.9f3a2.js) and setting max-age=31536000, immutable.
Origin Shield Bonus Layer Enabling CloudFront Origin Shield places one centralized caching tier in front of your origin, collapsing misses from multiple Regional Edge Caches into a single upstream request—ideal for protecting an ALB or high-egress S3 bucket.
