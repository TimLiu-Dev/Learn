API Design at Scale: REST Semantics, Pagination & Rate Limiting

An API that feels instant with 50 rows and 5 test devices breaks violently at 50 million rows and 100,000 mobile clients. Here is how senior backend engineers design idempotent writes for flaky cellular links, replace O(N) offset queries with O(log N) cursor pagination, and protect databases with token-bucket rate limiters and HTTP 429 Retry-After.

Your Android Bridge

In Android, Jetpack Paging 3 asks your PagingSource<String, Item> for an opaque LoadParams.Append(key) and passes it through Retrofit as @Query("cursor"). If the backend implements that parameter with SQL OFFSET, users see duplicate feed items whenever new rows arrive—and page 5,000 takes hundreds of milliseconds to scan. Worse, if Retrofit retries a timed-out POST /orders or ignores HTTP 429 Retry-After, your mobile app causes duplicate charges and synchronized retry storms.

1. REST Semantics & Idempotency Over Flaky Mobile Networks

Per RFC 9110 (HTTP Semantics, §9.2), HTTP methods carry strict contracts that load balancers, OkHttp caches, and retry interceptors rely on:

  • Safe & Idempotent (GET, HEAD): Read-only. Calling them 1 time or 10 times changes zero server state, so clients and CDNs may retry safely.
  • Unsafe & Idempotent (PUT, DELETE): Mutates state, but repeating the exact same request yields the same resource state (e.g., PUT /users/42/preferences replaces the document; DELETE /sessions/abc leaves the session absent whether called once or twice).
  • Unsafe & Non-Idempotent (POST): Creates a new side effect every time it executes (e.g., POST /v1/charges or POST /v1/orders).

Here is the mobile failure mode: an Android user taps "Confirm Order ($49)" in an elevator. Your backend behind an ALB commits the order and sends 201 Created, but the cellular tunnel drops before Android reads the bytes. The user taps again—or an automatic retry fires—and your server processes a second POST /v1/orders, charging the customer twice.

As documented in the Amazon Builders' Library ("Making retries safe with idempotent APIs"), the production fix is an explicit Idempotency-Key header (a UUIDv4 generated once per user action on Android):

  1. Android generates idempotencyKey = UUID.randomUUID() when the checkout sheet opens and sends Idempotency-Key: <uuid> on every retry of that attempt.
  2. The backend performs an atomic insert/conditional write (e.g., PostgreSQL INSERT ... ON CONFLICT DO NOTHING or DynamoDB attribute_not_exists(idempotency_key)) keyed by (tenant_id, idempotency_key) with a 24-hour TTL.
  3. If the key already exists with the same payload hash, the server returns the stored 201 response without re-running business logic. If the payload hash differs, it rejects with 409 Conflict or 422 Unprocessable Content to expose client bugs.

For partial updates, prefer PATCH with explicit semantics (JSON Merge Patch, RFC 7396) and evolve response schemas additively: add optional fields, never change a field's type in place, and version breaking contracts via URI (/v2/orders) or media-type versioning with deprecation headers.

2. Offset vs. Cursor (Keyset) Pagination at 10M+ Rows

Small admin dashboards often use LIMIT 20 OFFSET 40. At consumer scale (10 million orders or social posts), offset pagination fails in two ways:

  1. Linear O(offset + limit) Database Cost: To serve LIMIT 20 OFFSET 100000, PostgreSQL must still walk and discard 100,000 index entries (and often heap pages) before returning rows 100,001–100,020. Latency climbs from 2 ms on page 1 to 350–800 ms at deep pages, burning RDS IOPS.
  2. Page Drift (Duplicates & Skips): If 2 new orders arrive while a user scrolls from page 1 to page 2, every row shifts down by 2 positions. Items #19 and #20 from page 1 reappear at the top of page 2—breaking Jetpack Paging 3's DiffUtil list integrity.

Cursor (Keyset) Pagination solves both problems by encoding the deterministic sort boundary of the last item returned—for example {"v":1,"ts":1731648000000,"id":"ord_987"} as an opaque Base64URL string—and seeking directly in the B-Tree index:

WHERE (created_at, id) < ($1, $2) ORDER BY created_at DESC, id DESC LIMIT 21

Notice two senior details: first, the unique tie-breaker id guarantees rows sharing the exact same millisecond timestamp are never skipped; second, requesting limit + 1 (21 rows when the client asked for 20) reveals hasMore = rows.length > 20 in a single ~2 ms query, eliminating expensive SELECT COUNT(*) scans.

Figure 1: Keyset cursor pagination keeps page 5,000 nearly as fast as page 1 (~2 ms) and eliminates insert-induced duplicates in Android Paging 3 feeds.

3. Rate Limiting: Token Bucket Math & HTTP 429 Retry-After

Without rate limiting, a single buggy mobile release or credential-stuffing botnet can exhaust your RDS connection pool and take down every customer. Naive Fixed Window Counters (e.g., "100 req/min per user") suffer from a classic 2x boundary spike: a client sends 100 requests at 12:00:59 and another 100 at 12:01:01, pushing 200 requests in 2 seconds.

Production cloud gateways—including AWS API Gateway and AWS WAF—use the Token Bucket algorithm, defined by two numbers:

  • Capacity / Burst Limit (B): Maximum tokens the bucket can hold (e.g., API Gateway's account-level default is 5,000 concurrent burst requests). Allows legitimate short mobile bursts (app launch fetching 5 screens in parallel).
  • Refill Rate (R tokens/sec): Steady-state sustained throughput (e.g., API Gateway's default is 10,000 req/s; per-tenant plans are often 10–100 req/s).

On each request at timestamp nowMs, the limiter refills lazily without background timers:

tokens = Math.min(capacity, tokens + ((nowMs - lastRefillMs) / 1000) * refillPerSec)

If tokens >= cost (normally 1), deduct cost and allow the request (200). Otherwise reject with HTTP 429 Too Many Requests and include Retry-After (RFC 9110 §10.2.3), computed as Math.ceil((cost - tokens) / refillPerSec) seconds.

Figure 2: Lazy token-bucket evaluation computes elapsed refill on demand—no background timer per user required—and emits exact Retry-After seconds when exhausted.
Beware the Synchronized Retry Herd on Retry-After

If 5,000 Android devices receive HTTP 429 with Retry-After: 5 at 12:00:00 and every device schedules a coroutine delay(5_000), all 5,000 devices slam your API again at 12:00:05.000. Always teach mobile clients to add random jitter (e.g., retryAfterMs + Random.nextLong(0, 1500)) and cap retry attempts.

4. Production Code: Android Paging 3 + Postgres Keyset + AWS CDK Throttle

Notice how cleanly the mobile client, database index, and AWS API Gateway configuration align: 

// 1. Android Client (Kotlin — Paging 3 PagingSource + 429 Retry-After with jitter)
override suspend fun load(params: LoadParams<String>): LoadResult<String, OrderDto> {
    return try {
        val resp = api.listOrders(cursor = params.key, limit = params.loadSize)
        LoadResult.Page(data = resp.items, prevKey = null, nextKey = resp.nextCursor)
    } catch (e: HttpException) {
        if (e.code() == 429) {
            val retrySec = e.response()?.headers()?.get("Retry-After")?.toLongOrNull() ?: 2L
            delay(retrySec * 1000L + Random.nextLong(250L, 1250L)) // Honor + jitter
        }
        LoadResult.Error(e)
    }
}

-- 2. PostgreSQL / Amazon RDS Schema & Keyset Query (O(log N) regardless of depth)
CREATE INDEX CONCURRENTLY idx_orders_created_id
  ON orders (created_at DESC, id DESC);

SELECT id, created_at, total_cents
FROM orders
WHERE (created_at, id) < ($1, $2) -- Decoded & validated from Base64URL cursor
ORDER BY created_at DESC, id DESC
LIMIT $3; -- Pass limit + 1 to detect nextCursor without SELECT COUNT(*)
