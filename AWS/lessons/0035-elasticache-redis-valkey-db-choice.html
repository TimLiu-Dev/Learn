ElastiCache (Redis/Valkey) Cluster Mode & Choosing RDS vs DynamoDB vs ElastiCache

Sub-millisecond caching can drop p99 API latency by 10x—or take down production with CROSSSLOT errors, silent cache evictions, and thundering-herd database meltdowns. A senior engineer knows how Redis/Valkey partitions keys across 16,384 hash slots, how Multi-AZ failover breaks naive connection pools, and when a workload belongs in RDS/Aurora, DynamoDB, or ElastiCache.

Your Android Bridge

In Android, you separate ephemeral RAM caches from durable disk storage: an in-memory LruCache or StateFlow inside a ViewModel delivers instant UI reads but disappears when the OS kills your process, whereas Room (SQLite) persists structured records across restarts. On AWS, Amazon ElastiCache (Valkey or Redis OSS) is your fleet-wide shared RAM layer—delivering sub-millisecond reads across stateless ECS containers and Lambda functions—while RDS/Aurora and DynamoDB serve as your durable sources of truth. Treating ElastiCache like Room is the fastest way to lose production data during a failover or memory eviction.

1. Valkey vs. Redis OSS, Memory Headroom & Eviction Traps

Amazon ElastiCache manages two wire-compatible in-memory engines—Valkey (the Linux Foundation open-source fork of Redis 7.2, offered at lower AWS node and serverless pricing) and Redis OSS (up to 7.1 in ElastiCache)—alongside simpler multi-threaded Memcached. Because Valkey and Redis OSS speak the same RESP protocol, standard clients such as Lettuce, Jedis, ioredis, and redis-py work identically against both.

Unlike Memcached, Valkey/Redis provides rich atomic data structures (Strings, Hashes, Lists, Sets, Sorted Sets for leaderboards, HyperLogLog, and Streams) and executes commands on a single main thread per shard. That single-threaded command loop eliminates lock contention and guarantees atomic operations like INCR or Lua scripts, but it also means one slow KEYS * scan or a 2 MB big-key read stalls every other client queued on that shard.

Three production configuration details determine whether your cache stays healthy under memory pressure:

  • Reserved Memory (reserved-memory-percent): ElastiCache defaults to reserving 25% of node RAM (leaving 75% for user keys) so background BGSAVE copy-on-write forks and replication output buffers do not trigger the Linux OOM killer.
  • Eviction Policy (maxmemory-policy): ElastiCache defaults to volatile-lru, which evicts least-recently-used keys only among keys that have an explicit EXPIRE TTL. If your team writes keys without TTLs and memory hits max, volatile-lru refuses writes with OOM command not allowed when used memory > 'maxmemory'! Use allkeys-lru (or allkeys-lfu) for pure caches, and reserve noeviction strictly for queues or locks where silent eviction would corrupt state.
  • Stampede & Penetration Protection: When a hot key expires at peak mobile traffic, thousands of concurrent cache misses slam RDS/DynamoDB simultaneously (a cache stampede). Mitigate with jittered TTLs (e.g., 300s + random(0..60s)) and singleflight/mutex locks. For queries targeting missing IDs (cache penetration), store a short-lived NULL sentinel (e.g., 30s TTL) so attackers cannot bypass the cache on every request.

2. Cluster Mode Disabled vs. Enabled & the 16,384 Hash Slots

ElastiCache for Valkey/Redis deploys in two distinct topologies (plus ElastiCache Serverless, which abstracts shards behind a single VPC endpoint and scales storage and ECPUs automatically):

  • Cluster Mode Disabled (CMD): One shard total (1 primary write node + up to 5 async read replicas). You scale writes and memory vertically (larger cache.r7g node) and scale reads horizontally via replicas. Because every key lives on the single primary, multi-key commands (MGET, SUNION, Lua scripts) work across any keys.
  • Cluster Mode Enabled (CME): Data is horizontally sharded across up to 500 shards (each with 1 primary and 0–5 replicas). CME scales both memory and write throughput linearly, capped only by per-shard single-thread CPU on hot keys.

According to the Valkey / Redis Cluster Specification, CME divides the entire keyspace into exactly 16,384 hash slots (0 through 16383). Every key maps deterministically to a slot via:

slot = CRC16(hash_key) mod 16384

Crucially, CME supports hash tags: if a key contains a non-empty substring inside its first {...} pair (for example, user:{42}:profile and user:{42}:cart), only 42 is passed to CRC16. If the braces are empty (user:{}:profile) or missing, the entire key is hashed. Because CME nodes do not proxy multi-key commands across shards, calling MGET user:42:profile user:42:cart without hash tags throws CROSSSLOT Keys in request don't hash to the same slot whenever those two keys land on different shards.

Figure 1: Cluster Mode Enabled partitions 16,384 slots across shards. Cluster-aware clients fetch the slot map via CLUSTER SLOTS, route in 1 network hop, and refresh on -MOVED or -ASK redirects.

3. Multi-AZ Auto-Failover & Stale Client Traps

Enabling Multi-AZ with Automatic Failover places replicas in separate Availability Zones from each primary. Writes acknowledge as soon as the primary commits to RAM, and commands replicate asynchronously to replicas. That async gap gives ElastiCache sub-millisecond writes, at the cost of a small window of potential data loss if a primary dies before its replication buffer drains.

When a primary fails, ElastiCache detects the outage, promotes the replica with the least replication lag (typically within 15–60 seconds), and updates cluster state. Two failure modes catch teams off guard during failover:

  1. JVM / Client DNS Caching (CMD): In Cluster Mode Disabled, ElastiCache flips the Primary Endpoint DNS CNAME (low 5-second TTL) to the newly promoted replica. If your Java/Kotlin backend caches DNS for too long or holds open pooled TCP sockets to the old primary (which restarts as a read-only replica), writes fail with READONLY You can't write against a read only replica until connections recycle and DNS refreshes.
  2. Non-Cluster Clients Against CME: Using a standard non-cluster Redis client against a CME Configuration Endpoint fails immediately with MOVED <slot> <ip:port> because CME nodes return redirect responses instead of proxying traffic. Always enable cluster topology refresh in your client (and enable TLS in-transit + KMS at-rest encryption + RBAC/IAM Auth in private subnets).
Never Over-Tag Keys in CME

Hash tags solve CROSSSLOT, but putting the same coarse tag on millions of keys (for example, tenant:{acme}:* for your largest enterprise customer) pins every key for that tenant onto a single shard, destroying horizontal scaling and creating a hot-shard bottleneck.

4. Choosing RDS/Aurora vs. DynamoDB vs. ElastiCache

Senior cloud architects rarely ask "Which database is best?" Instead, they match workload invariants to the storage engine—and frequently pair a durable database with ElastiCache in front.

Dimension Amazon RDS / Aurora Amazon DynamoDB ElastiCache (Valkey / Redis)
Data Model & Queries Relational tables, foreign keys, ad-hoc SQL joins, aggregations, window functions. Key-value & wide-column; fast PK/SK lookups + GSIs for pre-known access patterns. In-memory key-value plus Sorted Sets, Hashes, Bitmaps, HyperLogLog, Streams.
Typical Latency Low milliseconds to tens of ms (query & index dependent). Consistent single-digit ms at any table size (sub-ms with DAX). Sub-millisecond (<1 ms inside VPC).
Durability & ACID Full ACID; Multi-AZ sync standby (RDS) or 6-copy quorum storage (Aurora). 3-AZ durable storage; TransactWriteItems ACID across up to 100 items. In-memory with async replication & snapshots; not a sole ACID source of truth.
Scaling Ceiling Vertical primary + read replicas (Aurora Serverless v2 auto-scales ACUs). Serverless auto-partitioning to millions of RPS with zero cluster ops. Vertical (CMD) or up to 500 shards (CME) / ElastiCache Serverless.
Sweet-Spot Workloads Financial ledgers, orders, ERP, complex reporting & ad-hoc analytics. Mobile user profiles, session/cart state, IoT telemetry, high-scale APIs. DB query caching, sliding-window rate limiters, real-time leaderboards, pub/sub.

5. Production Code: Multi-AZ Valkey Cluster & Jittered Cache-Aside

Below is a production AWS CDK definition for a Cluster Mode Enabled, Multi-AZ Valkey replication group alongside a Kotlin/TypeScript-style backend cache-aside helper using hash tags and TTL jitter: 

// 1. AWS CDK (TypeScript) — Multi-AZ, Encrypted, Cluster Mode Enabled Valkey Group
const cacheSubnetGroup = new elasticache.CfnSubnetGroup(this, "ValkeySubnets", {
  description: "Private isolated subnets for Valkey",
  subnetIds: vpc.isolatedSubnets.map((s) => s.subnetId),
});

const valkeyCluster = new elasticache.CfnReplicationGroup(this, "AppValkey", {
  replicationGroupDescription: "Production CME Valkey cache",
  engine: "valkey",
  engineVersion: "8.0",
  cacheNodeType: "cache.r7g.large",
  numNodeGroups: 3,                 // 3 shards across 16,384 slots
  replicasPerNodeGroup: 1,          // 1 replica per shard in a different AZ
  multiAzEnabled: true,
  automaticFailoverEnabled: true,   // Requires Multi-AZ + replicasPerNodeGroup >= 1
  transitEncryptionEnabled: true,   // TLS between ECS/Lambda and Valkey
  atRestEncryptionEnabled: true,
  cacheParameterGroupName: "default.valkey8.cluster.on",
  cacheSubnetGroupName: cacheSubnetGroup.ref,
  securityGroupIds: [valkeySg.securityGroupId],
});

// 2. Application Cache-Aside Pattern (Hash Tags + Jittered TTL + Negative Caching)
async function getUserBundle(userId: string) {
  const profileKey = `user:{${userId}}:profile`; // Co-located on same shard
  const cartKey    = `user:{${userId}}:cart`;    // Safe for MGET & Lua scripts

  const cached = await valkeyCluster.mget(profileKey, cartKey);
  if (cached[0] === "__NULL__") return null;     // Penetration guard
  if (cached[0] && cached[1]) return { profile: JSON.parse(cached[0]), cart: JSON.parse(cached[1]) };

  const dbBundle = await rdsRepo.loadUserBundle(userId);
  const jitter = Math.floor(Math.random() * 60); // Stampede guard: 300s..359s
  if (!dbBundle) {
    await valkeyCluster.set(profileKey, "__NULL__", "EX", 30);
    return null;
  }
  await valkeyCluster
    .multi()
    .set(profileKey, JSON.stringify(dbBundle.profile), "EX", 300 + jitter)
    .set(cartKey, JSON.stringify(dbBundle.cart), "EX", 300 + jitter)
    .exec();
  return dbBundle;
}

Why 16,384 Slots? Redis Cluster nodes gossip slot ownership bitmaps in every heartbeat packet. At 16,384 bits (2 KB per heartbeat), cluster gossip stays compact while easily partitioning up to ~1,000 nodes; 65,536 slots would bloat every heartbeat to 8 KB.
Why Not Memcached? Memcached scales across threads on a single node and fits dead-simple string caching, but it lacks Multi-AZ replication, automatic failover, Lua scripts, Sorted Sets, and persistence snapshots—making Valkey/Redis the default choice on AWS.
