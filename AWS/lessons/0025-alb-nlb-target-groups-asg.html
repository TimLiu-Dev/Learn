ALB vs NLB, Target Groups, Health Checks, Deregistration Delay & Auto Scaling

Scaling compute behind a single static endpoint requires mastering two halves of AWS traffic management: choosing between Layer 7 (ALB) and Layer 4 (NLB) load balancing, and orchestrating health checks, connection draining, target-tracking math, and warm pools so deploys and traffic spikes never drop a single user request.

Your Android Bridge

In Android, when a DNS lookup returns multiple A records, OkHttp automatically loops through them on connection failure (client-side failover), and a gRPC channel uses a client-side picker to spread RPCs across subchannels. On AWS, you cannot rely on millions of mobile clients to detect dead EC2 instances or rebalance hot nodes. Instead, an Application Load Balancer (ALB) or Network Load Balancer (NLB) acts as the server-side router: polling backend health, draining in-flight sockets before shutdown, and feeding per-target metrics to an EC2 Auto Scaling Group (ASG).

1. L7 ALB vs. L4 NLB: Choosing the Right Edge

AWS Elastic Load Balancing offers two primary workhorses that solve fundamentally different networking problems. Picking the wrong one forces painful workarounds later (such as proxying TCP streams through HTTP or losing AWS WAF protection).

Dimension Application Load Balancer (ALB) Network Load Balancer (NLB)
OSI Layer & Protocols Layer 7: HTTP/1.1, HTTP/2, gRPC, WebSockets. Layer 4: TCP, UDP, TCP_UDP, TLS passthrough/termination.
Proxy Behavior Full reverse proxy: terminates client TCP+TLS, parses HTTP, opens pooled backend connections, adds X-Forwarded-For. Flow-based Hyperplane forwarding: routes 5-tuple flows at ultra-low latency (~microseconds) without buffering HTTP payloads.
Static IPs & DNS Dynamic public IPs (DNS-only); use Global Accelerator or NLB-in-front-of-ALB if partners require static IPs. Native static Elastic IP (EIP) per Availability Zone; required for AWS PrivateLink providers.
Client Source IP Hidden at TCP level (backend sees ALB ENI IP); read HTTP X-Forwarded-For header instead. Preserved automatically for instance targets (and optionally ip targets, or via Proxy Protocol v2).
Idle Timeout Default 60s (configurable 1–4,000s). Watch out for the 502 keep-alive close race. Fixed 350s for TCP flows and 120s for UDP flows.
Cross-Zone LB Default Always ON (cannot disable) at $0 extra cross-AZ data transfer charge. OFF by default; turning it on bills inter-AZ data transfer ($0.01/GB each way) but prevents zonal hot spots.
Security & Routing Security Groups, AWS WAF, host/path/header/query routing, OIDC/Cognito auth. Security Groups (added for NLB in 2023), zero HTTP inspection, handles millions of RPS and instant flash spikes.
Senior Pattern: NLB → ALB Chaining

Need static Elastic IPs for a banking partner's firewall allowlist and AWS WAF + path-based HTTP routing? AWS supports placing an ALB as a target (target type alb) behind an NLB. The NLB gives you static EIPs per AZ and passes TCP packets straight to the ALB for L7 inspection.

2. Target Groups, Target Types & The Health Check Trap

Both ALB and NLB route traffic to Target Groups. Every target group picks an immutable target_type at creation time:

  • instance: Routes to EC2 instance IDs on a host port. Even if containers run on the instance, traffic hits the instance's primary ENI first (an extra hop).
  • ip: Routes directly to private IPv4/IPv6 addresses—mandatory for ECS Fargate (awsvpc mode), EKS pod IPs, and on-premises targets across Direct Connect/VPN.
  • alb / lambda: Routes NLB to an ALB (alb), or ALB to serverless functions (lambda).

Shallow vs. Deep Health Checks & ALB "Fail Open"

An ALB polls every target on a configured path (e.g., GET /healthz) every interval (default 30s, timeout 5s), requiring healthy_threshold (default 5) consecutive 2xx responses to restore a target and unhealthy_threshold (default 2) consecutive failures to pull it out of rotation.

Here is the classic production outage: a developer makes /healthz run SELECT 1 against RDS PostgreSQL. When RDS undergoes a 15-second failover:

  1. Every backend instance in every AZ fails /healthz twice in a row.
  2. All targets transition to unhealthy simultaneously.
  3. ALB Fail-Open (Panic Mode): When 100% of targets in a target group are unhealthy, the ALB assumes the health check itself may be broken and routes traffic to all targets anyway.
  4. ASG Cascading Termination: Worse, if your Auto Scaling group uses health_check_type = "ELB", ASG sees every instance past its health_check_grace_period marked unhealthy and begins terminating your entire healthy compute fleet at the exact moment the database recovers.
Rule: Liveness Is Shallow; Readiness Is Careful

Keep load-balancer health checks local to the process (e.g., verify the event loop, worker threads, and local configuration are alive—return 200 OK in <5 ms). Never fail an ELB health check because a shared downstream database or third-party API blipped. Report downstream dependency degradation through metrics, alarms, and circuit breakers instead.

3. Deregistration Delay & Zero-Downtime Draining

When you deploy a new AMI, scale in an ASG, or roll an ECS task, the load balancer starts deregistration. The Target Group attribute deregistration_delay.timeout_seconds defaults to 300 seconds (5 minutes)—which guarantees safe draining for slow monoliths, but needlessly stalls CI/CD rollouts when your API requests finish in 200 ms.

Conversely, engineers who get impatient and set deregistration_delay = 0 trigger instant 502 Bad Gateway errors: the load balancer stops waiting immediately and severs in-flight responses. Safe zero-downtime shutdown requires synchronizing two clocks:

Figure 1: Both deregistration_delay and compute stopTimeout must strictly exceed propagationBuffer + maxInFlightRequest.

For Network Load Balancers with long-lived TCP/WebSocket connections, AWS also exposes deregistration_delay.connection_termination.enabled (default false). When disabled, existing TCP flows keep running past the delay; when enabled, NLB forcefully sends TCP RST at the end of the delay so old tasks actually vacate.

4. EC2 Auto Scaling: Target Tracking, Warmup & Warm Pools

Manual step-scaling rules ("add 2 instances when CPU > 75%") constantly fight oscillation. AWS recommends Target Tracking Scaling Policies, which act like a thermostat around a single utilization metric such as ASGAverageCPUUtilization or ALBRequestCountPerTarget:

desiredCapacity = clamp(ceil(currentCapacity * (currentMetricPerTarget / targetValue)), minSize, maxSize)

  • Asymmetric Reaction Speed: Target tracking scales out rapidly (typically after 3 consecutive 1-minute datapoints above target) and scales in conservatively (typically 15 consecutive 1-minute datapoints ~10–20% below target) to avoid capacity flapping.
  • The Instance Warmup Trap (default_instance_warmup): Suppose an EC2 instance needs 240 seconds to boot, pull containers, and warm JIT/in-memory caches while burning 95% CPU. If you leave default_instance_warmup too low (e.g., 30s), target tracking folds that booting instance's 95% CPU into the group average and assumes the previous scale-out already failed—triggering a runaway launch storm. Setting an accurate warmup excludes warming instances from scale-out calculations and prevents double-counting unmet capacity.
  • EC2 Warm Pools: Even with perfect target tracking, cold-booting a fresh EC2 instance takes 3–5 minutes. A Warm Pool keeps pre-booted, pre-configured instances in the Stopped state (paying only EBS volume storage, $0 EC2 compute) or Running/Hibernated state. During a sudden traffic spike, ASG pulls from the Warm Pool in ~20–30 seconds instead of 4 minutes.

5. Production Example: Terraform Target Group, Drain & ASG

Notice how every timeout and threshold below aligns across the ALB Target Group, the Auto Scaling Group, and the Warm Pool: 

resource "aws_lb_target_group" "orders_api" {
  name                 = "orders-api-tg"
  port                 = 8080
  protocol             = "HTTP"
  vpc_id               = aws_vpc.prod.id
  target_type          = "ip"
  deregistration_delay = 45 # > propagationBuffer (2s) + maxInFlightRequest (25s)

  health_check {
    path                = "/healthz" # Shallow process check ONLY (no RDS query!)
    interval            = 15
    timeout             = 5
    healthy_threshold   = 3
    unhealthy_threshold = 2
    matcher             = "200"
  }
}

resource "aws_autoscaling_group" "orders_api" {
  name                      = "orders-api-asg"
  min_size                  = 4
  max_size                  = 40
  vpc_zone_identifier       = aws_subnet.private[*].id
  target_group_arns         = [aws_lb_target_group.orders_api.arn]
  health_check_type         = "ELB"
  health_check_grace_period = 240 # Must cover boot + app startup
  default_instance_warmup   = 240 # Prevents double-scaling during cold boot

  warm_pool {
    pool_state                  = "Stopped" # Pay EBS only; ~25s resume on spike
    min_size                    = 2
    max_group_prepared_capacity = 10
  }
}

resource "aws_autoscaling_policy" "req_per_target" {
  name                   = "orders-alb-req-tracking"
  autoscaling_group_name = aws_autoscaling_group.orders_api.name
  policy_type            = "TargetTrackingScaling"

  target_tracking_configuration {
    predefined_metric_specification {
      predefined_metric_type = "ALBRequestCountPerTarget"
      resource_label         = "${aws_lb.public.arn_suffix}/${aws_lb_target_group.orders_api.arn_suffix}"
    }
    target_value = 800
  }
}
