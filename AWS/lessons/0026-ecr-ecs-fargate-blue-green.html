ECR & ECS on Fargate: Task Definitions, IAM Roles, Service Connect & Blue/Green

Deploying containers on AWS without managing EC2 hosts comes down to four contracts: immutable artifact identity in ECR, strict Fargate CPU/memory sizing, clean separation between the Execution Role and Task Role, and zero-downtime traffic shifting via Service Connect and CodeDeploy Blue/Green.

Your Android Bridge

In Android releases, Google Play enforces two ironclad rules: you can never upload a second AAB with the same versionCode, and a staged rollout (10% → 50% → 100%) lets you halt a crash regression before most users see it. On AWS, ECR immutable tags play the role of versionCode, ARM64 Graviton mirrors your native arm64-v8a builds (~20% cheaper than x86_64), and CodeDeploy Blue/Green behind an ALB lets you shift 10% canary traffic and snap 100% back in seconds when 5xx alarms fire.

1. ECR Immutable Tags, Digest Pinning & Private Subnet Pulls

Amazon Elastic Container Registry (ECR) is your private Docker/OCI registry. If you leave tag mutability at its default (MUTABLE) and push api:latest or overwrite api:v1.4.2, two Fargate tasks launched 10 minutes apart can silently run different binaries under the exact same tag—destroying rollback determinism during an outage.

  • Enable IMMUTABLE tags: Setting imageTagMutability = "IMMUTABLE" causes ECR to reject any docker push reusing an existing tag with ImageTagAlreadyExistsException. Always tag builds with a unique CI identifier (e.g., v2.4.1-g8f3a19) or pin the task definition to the immutable SHA-256 digest (repo@sha256:9c4e...).
  • Scan & expire old artifacts: Enable scanOnPush (or Inspector Enhanced Scanning) for OS/library CVEs, and attach an ECR Lifecycle Policy (for example, expire untagged layers after 7 days and retain only the last 25 release tags). Without lifecycle rules, daily CI builds accumulate toward the 10,000-image repository quota and bill \$0.10/GB-month indefinitely.
  • The Private-Subnet Pull Trap: Fargate tasks belong in private subnets. If those subnets have no NAT Gateway, pulling a single image from ECR requires three VPC endpoints: ecr.api (Interface), ecr.dkr (Interface), and the S3 Gateway endpoint (because ECR stores image layers in Amazon S3, not inside the registry control plane), plus a logs Interface endpoint if you ship stdout to CloudWatch Logs.

2. Task Definitions: Fargate Sizing, IAM Roles & Health Checks

An ECS Task Definition is the immutable blueprint for your container group (analogous to a Kubernetes Pod spec). Unlike EC2-backed ECS, where you manage instance capacity yourself, Fargate launches each task inside an isolated Firecracker microVM and enforces discrete CPU-to-memory pairs. Requesting an invalid combination—such as 1024 CPU units (1 vCPU) with 1024 MiB RAM—fails immediately at registration.

Task CPU (cpu) vCPU Allowed Task Memory (memory in MiB)
256 0.25 vCPU 512, 1024, 2048
512 0.5 vCPU 1024 to 4096 (1024 MiB increments)
1024 1 vCPU 2048 to 8192 (1024 MiB increments)
2048 2 vCPU 4096 to 16384 (1024 MiB increments)
4096 4 vCPU 8192 to 30720 (1024 MiB increments)
8192 / 16384 8 / 16 vCPU 16384–61440 (4 GiB steps) / 32768–122880 (8 GiB steps)

Every Fargate task gets 20 GiB of ephemeral storage by default (expandable up to 200 GiB via ephemeralStorage; container images unpack into this quota), and must declare networkMode: "awsvpc" so ECS attaches a dedicated Elastic Network Interface (ENI) per task.

The #1 ECS IAM Trap: Execution Role vs. Task Role

Senior engineers cleanly split the two IAM ARNs on every Task Definition:

  1. Execution Role (executionRoleArn): Assumed by the ECS / Fargate infrastructure agent before your process starts. It needs permissions to pull from ECR (ecr:GetAuthorizationToken, ecr:BatchGetImage, ecr:GetDownloadUrlForLayer), write logs (logs:CreateLogStream, logs:PutLogEvents), and resolve secrets from Secrets Manager or SSM Parameter Store into container environment variables.
  2. Task Role (taskRoleArn): Assumed by your application code at runtime via the local task credentials endpoint (169.254.170.2, exposed via AWS_CONTAINER_CREDENTIALS_RELATIVE_URI). Grant it only runtime business permissions (e.g., dynamodb:PutItem, sqs:SendMessage, s3:GetObject). Never reuse the same ARN for both roles.
Health Check & Shutdown Alignment

Two timers race during deploys: (1) On startup, if your JVM/Ktor/Spring app takes 40s to listen and either the container healthCheck.startPeriod or the ECS service healthCheckGracePeriodSeconds is shorter than 40s, ECS kills the task in an infinite crash loop. (2) On shutdown, ECS sends SIGTERM and waits stopTimeout (default 30s, Fargate hard maximum 120s) before sending SIGKILL. Keep stopTimeout at least equal to your ALB target group deregistration_delay so in-flight requests finish cleanly.

3. Service Connect vs. ALB & CodeDeploy Blue/Green

How should services find each other once running on Fargate? Avoid routing internal service-to-service traffic back out through a public ALB or relying on raw Cloud Map DNS alone (clients cache DNS TTLs and keep hitting dead task IPs after a scale-in).

  • ECS Service Connect (East-West): When enabled on a service, ECS automatically injects a lightweight Envoy sidecar proxy into each task. Callers dial a clean logical name like http://orders-api:8080; Envoy maintains live endpoint health lists, pools HTTP/gRPC connections, retries transient 503s, and emits per-route latency metrics—with zero Kubernetes or Istio control-plane overhead.
  • Rolling Update vs. CodeDeploy Blue/Green (North-South): ECS's default ECS rolling controller replaces tasks in place inside one Target Group (e.g., minimumHealthyPercent: 100, maximumPercent: 200). Rollback requires launching old containers all over again. By contrast, setting deploymentController.type = "CODE_DEPLOY" wires two ALB Target Groups (Blue and Green) plus an optional test listener (:8443) and BeforeAllowTraffic Lambda smoke test. Using CodeDeployDefault.ECSCanary10Percent5Minutes, 10% of production traffic hits Green for 5 minutes while Blue stays warm; if a CloudWatch 5xx alarm triggers, CodeDeploy shifts 100% back to Blue in seconds.

4. Production Example: Immutable ECR + Fargate Task Definition

Below is a production-hardened task definition pattern (with Terraform ECR policy + ECS JSON structure) demonstrating ARM64 Graviton sizing, separate roles, startup grace alignment, and Service Connect readiness: 

# 1. ECR Repository with Immutable Tags & Cleanup (Terraform HCL)
resource "aws_ecr_repository" "orders_api" {
  name                 = "orders-api"
  image_tag_mutability = "IMMUTABLE"
  image_scanning_configuration { scan_on_push = true }
}

# 2. ECS Fargate Task Definition (JSON excerpt)
{
  "family": "orders-api",
  "requiresCompatibilities": ["FARGATE"],
  "networkMode": "awsvpc",
  "runtimePlatform": { "cpuArchitecture": "ARM64", "operatingSystemFamily": "LINUX" },
  "cpu": "1024",
  "memory": "2048",
  "executionRoleArn": "arn:aws:iam::111122223333:role/orders-ecs-execution-role",
  "taskRoleArn":      "arn:aws:iam::111122223333:role/orders-app-task-role",
  "containerDefinitions": [{
    "name": "orders-api",
    "image": "111122223333.dkr.ecr.us-east-1.amazonaws.com/orders-api:v2.4.1-g8f3a19",
    "portMappings": [{ "name": "http", "containerPort": 8080, "appProtocol": "http" }],
    "stopTimeout": 60,
    "healthCheck": {
      "command": ["CMD-SHELL", "curl -fsS http://localhost:8080/health || exit 1"],
      "interval": 15,
      "timeout": 5,
      "retries": 3,
      "startPeriod": 45
    }
  }]
}

Why S3 Gateway for ECR? ECR's control plane handles auth and manifests via ecr.api/ecr.dkr, while actual compressed image tarballs stream directly from S3—so private subnets without NAT fail pulls unless an S3 Gateway Endpoint exists.
Distroless healthCheck Trap Minimal images like gcr.io/distroless ship without sh or curl. Using CMD-SHELL with curl on distroless causes every container health check to fail—use a tiny static health binary with CMD instead.
