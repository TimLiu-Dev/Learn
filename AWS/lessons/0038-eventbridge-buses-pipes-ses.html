EventBridge Event Buses, Schema Registry, Pipes & Transactional SES Integration

Point-to-point queues and fan-out topics solve transport, not domain choreography. A senior AWS engineer routes decoupled microservices through EventBridge content-based event patterns, replaces brittle glue Lambdas with EventBridge Pipes, guards against payload drift via the Schema Registry, and wires Amazon SES bounces and complaints straight back into an automated suppression loop.

Your Android Bridge

In Android, a BroadcastReceiver declares an IntentFilter specifying the action, category, and data scheme it cares about—so senders fire an Intent without importing or knowing any receiver class. Amazon EventBridge is your cloud-scale Intent router: producers emit structured JSON events via PutEvents onto an Event Bus, and Rules evaluate deep JSON fields (prefixes, numeric ranges, missing keys, exclusions) to route events to up to five targets per rule. Meanwhile, EventBridge Pipes acts like a Kotlin Flow pipeline (source.filter { ... }.map { ... }.collect) over DynamoDB Streams or SQS without writing boilerplate polling code, and Amazon SES emits delivery, bounce, and spam-complaint broadcasts back to EventBridge so your sender reputation stays healthy.

1. Event Buses & Content-Based Event Pattern Matching

Every event entering Amazon EventBridge shares a canonical JSON envelope of up to 256 KB per entry (with PutEvents accepting up to 10 entries and 256 KB total request size):

  • Envelope Metadata: version, id (UUID generated by EventBridge for idempotency), source (e.g., "com.myapp.orders"), detail-type (e.g., "OrderConfirmed"), account, region, time, and resources.
  • Domain Payload (detail): Arbitrary JSON containing your business state—orderId, totalCents, currency, customerEmail.

EventBridge separates traffic across three bus types: the Default Bus (receives AWS-native service events from S3, ECS, IAM, and SES), Custom Buses (isolated per bounded context or environment, such as orders-prod-bus), and Partner Buses (ingesting SaaS webhooks natively from Stripe, Auth0, or Datadog without public API Gateway endpoints).

Unlike classic SNS attribute filtering—which forced producers to duplicate payload fields into MessageAttributes—EventBridge Rules match directly on any nested property inside the envelope or detail:

  • AND across keys, OR within arrays: Listing both source and detail-type requires both to match; listing ["OrderPlaced", "OrderConfirmed"] matches either value.
  • Rich Content Operators: prefix, suffix, equals-ignore-case, anything-but, exists (true/false for schema presence), cidr (IP matching), numeric (e.g., [">=", 5000, "<", 100000]), and $or across multiple fields.
  • Input Transformers & Archives: Before invoking a target (Lambda, Step Functions, SQS, or an HTTP API Destination), a Rule can reshape the JSON payload with an Input Transformer—and an Event Archive lets you replay historical events onto a bus after deploying a consumer bug fix.

2. Schema Registry & Preventing Silent Event Drift

In an Android codebase, changing a Kotlin @Serializable field name fails immediately at compile time. Across distributed AWS microservices, renaming customerEmail to email in the Orders service causes downstream EventBridge rules and consumers to silently drop or misread events.

The EventBridge Schema Registry stores OpenAPI 3 and JSON Schema Draft-04 definitions for every event type on a bus. Enabling Schema Discovery inspects live bus traffic and automatically registers new schemas and incremental versions whenever shapes evolve, letting teams download generated code bindings (TypeScript, Java, Python, Go) directly into their IDE or CI pipeline.

Senior Trap: Schema Discovery Observes — It Does Not Reject

EventBridge does not validate or reject malformed payloads at PutEvents ingestion time. If a producer ships a breaking field rename, EventBridge accepts the event, registers a new schema version in Discovery, and routes the unmatchable payload nowhere (or breaks consumers). Enforce schema contracts in CI tests, producer TypeScript/Kotlin types, or Pipe validation—and always attach an SQS Dead-Letter Queue (DLQ) to every Rule target because EventBridge stops retrying after 24 hours / 185 attempts.

3. EventBridge Pipes: Eliminating Glue Lambdas

Before EventBridge Pipes, connecting a poll-based stream (DynamoDB Streams, Kinesis, SQS, MSK, or Kafka) to an Event Bus or Step Functions required writing, IAM-scoping, and paying for a custom "glue Lambda" just to filter records and call PutEvents.

A Pipe is a strictly ordered, 1-to-1 managed integration with four stages:

  1. Source: Polls SQS, DynamoDB Streams, Kinesis, or Kafka in configurable batches, preserving shard/group ordering.
  2. Filter (Optional, Crucial for Cost): Evaluates standard EventBridge pattern syntax against source records. Filtered-out events are dropped at the poller—you pay zero enrichment or target invocation charges for noise like DynamoDB REMOVE events or health-check heartbeats.
  3. Enrichment (Optional): Invokes a Lambda, Step Functions Express workflow, API Gateway, or HTTP API Destination to hydrate sparse records (for example, fetching customer preferences from an internal service before publishing).
  4. Target: Delivers the final payload to a Custom Event Bus, Step Functions, SQS, SNS, or an API Destination, with support for partial batch failure reporting and a Pipe-level DLQ.

4. Transactional Email via Amazon SES & Bounce/Complaint Loops

Mobile backends rely on Amazon SES for transactional emails—order receipts, password resets, security alerts. New AWS accounts start inside the SES Sandbox (capped at 200 emails per 24 hours, 1 email/second, and verified recipient addresses only) until you request production access and verify domain identity via SPF, Easy DKIM (2048-bit RSA), DMARC, and a custom MAIL FROM subdomain.

The single biggest operational failure with SES is ignoring feedback loops until AWS suspends your sending privileges. AWS enforces strict account-level reputation thresholds:

  • Bounce Rate: Exceeding 5% triggers an account review warning; reaching 10% can automatically pause sending across the region.
  • Complaint Rate: Exceeding 0.1% (1 spam report per 1,000 emails) triggers a warning; reaching 0.5% risks immediate sending suspension.

Attach a Configuration Set with an EventBridge event destination to every SendEmail call. Your guard must distinguish between bounce severities using the SES Suppression Model:

  • Permanent Bounce (bounceType: "Permanent"): The mailbox does not exist or domain is invalid (SMTP 5xx). Suppress immediately—every retry hurts reputation.
  • Transient Bounce (bounceType: "Transient"): Mailbox full or temporary throttling (SMTP 4xx). SES automatically retries transient bounces for up to 12 hours; do not permanently blacklist the user on a single soft bounce.
  • Complaint (eventType: "Complaint"): The recipient clicked "Report Spam". Suppress immediately and audit opt-out preferences.

5. Production Code Example: Pipe + Pattern Rules + SES Guard

Below is how a production TypeScript stack wires a DynamoDB CDC Pipe into a Custom Bus, defines a content-matched Rule with an SQS DLQ, and checks a DynamoDB suppression table before calling SESv2: 

// 1. EventBridge Rule Pattern (CDK / JSON) — High-value confirmed orders only
const highValueOrderRule = new events.Rule(this, "HighValueReceiptRule", {
  eventBus: ordersBus,
  eventPattern: {
    source: ["com.myapp.orders"],
    detailType: ["OrderConfirmed"],
    detail: {
      status: ["CONFIRMED"],
      currency: [{ "anything-but": ["TEST"] }],
      totalCents: [{ numeric: [">=", 5000] }],
      customerEmail: [{ exists: true }]
    }
  }
});
highValueOrderRule.addTarget(new targets.LambdaFunction(receiptWorker, {
  deadLetterQueue: receiptDlq, // Catch events failing after 24h / 185 retries
  retryAttempts: 5
}));

// 2. Transactional SES Send with Defense-in-Depth Suppression Guard
async function sendTransactionalReceipt(email: string, htmlBody: string) {
  const normalized = email.trim().toLowerCase();
  const suppressed = await ddb.get({ TableName: "EmailSuppressions", Key: { email: normalized } });
  if (suppressed.Item) {
    return { sent: false, status: "SUPPRESSED", reason: suppressed.Item.reason };
  }

  return sesv2.send(new SendEmailCommand({
    FromEmailAddress: "receipts@mail.myapp.com",
    ConfigurationSetName: "transactional-prod-events", // Streams Bounce/Complaint to EventBridge
    Destination: { ToAddresses: [normalized] },
    Content: { Simple: { Subject: { Data: "Your Order Receipt" }, Body: { Html: { Data: htmlBody } } } }
  }));
}

EventBridge vs. SNS Choose SNS when you need ultra-high throughput (tens of thousands of TPS) or millions of mobile/SQS subscribers. Choose EventBridge for deep JSON payload matching, SaaS partner events, Input Transformers, Schema Registry, and Archive/Replay (default quota: 300 rules/bus, 5 targets/rule).
At-Least-Once Delivery EventBridge guarantees at-least-once delivery and retries target errors for up to 24 hours (185 attempts). Always key consumer idempotency on the envelope id or business key so rare duplicate deliveries stay harmless.
Account-Level SES Suppression AWS SES also provides a managed account-level suppression list that silently drops future sends to previously hard-bounced addresses—though keeping your own DynamoDB guard gives your app explicit UX feedback (like prompting users to update a bad email).
