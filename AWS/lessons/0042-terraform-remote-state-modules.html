Terraform on AWS: Remote S3 State, Locking, Modules & CDK vs Terraform

In AWS CDK, CloudFormation tracks what exists in your AWS account for you. In Terraform, you own the state file. Understanding how S3 remote state, state locking, plan vs apply, reusable modules, and moved refactors work separates engineers who safely ship multi-account infrastructure from engineers who accidentally destroy production databases.

Your Android Bridge

In Android/Gradle projects, you commit gradle.lockfile (and libs.versions.toml) so every developer and CI runner resolves the exact same dependency graph, while Gradle acquires a file lock on .gradle/ caches so two builds do not corrupt artifacts concurrently. Terraform uses that exact same discipline at cloud scale: .terraform.lock.hcl pins provider binaries and SHA-256 checksums, remote S3 state replaces your local build/ folder as the single source of truth, and state locking prevents two CI pipelines from mutating the same VPC or RDS instance at the exact same second.

1. Remote S3 State & Locking (Preventing Split-Brain Infrastructure)

Terraform maps every resource block in your .tf files (e.g., aws_rds_cluster.orders) to its real AWS identifier (ARN, VPC ID, DB endpoint) inside a JSON file called state (terraform.tfstate). Leaving state on a laptop breaks immediately in teams:

  • No shared truth: Teammate B runs terraform apply without Teammate A's local state and Terraform tries to recreate resources that already exist—or overwrites them.
  • Secrets exposure: State JSON stores attributes in plaintext (including initial DB passwords or TLS private keys if generated in HCL), so it must never be committed to Git.
  • Concurrent corruption: Two CI jobs running apply simultaneously read the same old state, write conflicting AWS changes, and overwrite each other's state JSON—orphaning live AWS resources.

The production AWS solution is an encrypted, versioned Amazon S3 backend paired with atomic state locking:

  1. S3 Bucket Hardening: Enable S3 Versioning (so a corrupted state file can be rolled back to a prior version ID), enforce server-side encryption (SSE-S3 or KMS CMK), and enable S3 Block Public Access.
  2. State Locking Evolution (DynamoDB vs. Native S3 Lockfile): Historically, AWS teams paired S3 with a DynamoDB table (partition key LockID) because S3 lacked atomic compare-and-swap writes. Since Terraform 1.10+ (GA in 1.11, per the HashiCorp S3 Backend Documentation), Terraform supports use_lockfile = true using S3 Conditional Writes (If-None-Match: *) to create a .tflock object atomically—eliminating the DynamoDB table while preserving legacy dynamodb_table support in older codebases.
Figure 1: Atomic locking serializes writes to the state file. Run 2 aborts safely with zero infrastructure corruption and retries only after Run 1 releases the lock.
Two State-Locking Mistakes That Cause Outages

1. Passing -lock=false: Disabling locks forces concurrent applies to race on state writes, leaving real AWS resources untracked.
2. Blindly running terraform force-unlock <LOCK_ID>: If another engineer or GitHub Actions job is still mid-apply, breaking their lock causes split-brain state corruption. Always inspect the lock's Who and Created timestamp first.

2. plan vs. apply & Destructive Replacement Traps

Terraform splits every deployment into two distinct phases:

  1. terraform plan -out=tfplan: Reads state, refreshes live AWS APIs, constructs the resource dependency graph (DAG), and outputs an exact diff showing + create, ~ update in-place, - destroy, or -/+ destroy and then create replacement. Saving tfplan freezes the exact execution graph.
  2. terraform apply tfplan: Executes only the approved plan artifact without re-calculating against changes merged by someone else minutes later.

The deadliest Terraform failure mode for newcomers is missing a forced replacement (-/+) in a noisy plan diff. Changing an immutable AWS property—such as an aws_db_instance identifier, an aws_s3_bucket bucket name, an aws_subnet cidr_block, or an aws_kms_key policy/key spec—cannot be updated in place. Terraform destroys the live resource and creates a brand-new empty one.

Mechanism What It Does Production Rule
prevent_destroy = true Fails the plan/apply with an error if any change would delete the resource. Mandatory on stateful data stores (RDS, DynamoDB, KMS keys, S3 state buckets).
create_before_destroy = true Reorders replacement from ["delete", "create"] to ["create", "delete"]. Use on stateless/edge resources (Launch Templates, ACM certs, SGs)—requires unique or name_prefix names.
moved { from = ... to = ... } Rewrites the resource address in state without touching the live AWS resource. Use whenever renaming blocks or extracting root resources into reusable modules (zero downtime).

3. Reusable Modules, Version Pinning & Environment Isolation

A Terraform module is any directory containing .tf files with explicit variables.tf inputs and outputs.tf exports—identical to extracting an Android Gradle library module with a clean public API. Senior platform teams enforce three module rules:

  • Pin module versions strictly: Pin registry modules with semantic constraints (version = "~> 5.8") or Git modules to an immutable 40-character commit SHA (?ref=8f3c...), never floating main branches.
  • Validate inputs at plan time: Use Terraform validation { condition = ... } blocks on variables (e.g., enforcing private-only RDS snapshots or valid CIDR blocks) so bad configs fail before AWS API calls run.
  • Directories over Terraform Workspaces for prod isolation: While terraform workspace select prod swaps state keys inside one backend, every workspace shares the same code branch, variable defaults, and backend IAM permissions. Separate root directories (envs/dev/, envs/prod/) give each environment its own AWS account role, S3 state key, and blast radius—calling the same pinned module.

4. Production HCL Example: Remote State, Pinned Module & Lifecycle Guardrails

Notice how the root environment configuration combines S3 native locking, a committed .terraform.lock.hcl workflow, a version-pinned module, and zero-downtime moved refactoring: 

# envs/prod/backend.tf — Terraform 1.11+ with native S3 conditional locking
terraform {
  required_version = "~> 1.11.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.80" # Exact checksums locked in .terraform.lock.hcl
    }
  }

  backend "s3" {
    bucket       = "acme-tfstate-prod-123456789012"
    key          = "orders-service/terraform.tfstate"
    region       = "us-east-1"
    encrypt      = true
    use_lockfile = true # Atomic S3 conditional write (.tflock); replaces legacy dynamodb_table
  }
}

# envs/prod/main.tf — Pin module version & refactor safely with moved {}
module "orders_db" {
  source  = "git::https://github.com/acme/tf-modules.git//rds-postgres?ref=a4b92d18e7c2f3b91c0a"
  env     = "prod"
  db_name = "orders"
  multi_az = true
}

# Migrating a live DB into the module without destroying & recreating it:
moved {
  from = aws_db_instance.orders
  to   = module.orders_db.aws_db_instance.this
}

# Inside modules/rds-postgres/main.tf — Guardrail against accidental replacement
resource "aws_db_instance" "this" {
  identifier     = "${var.env}-${var.db_name}"
  engine         = "postgres"
  multi_az       = var.multi_az
  lifecycle {
    prevent_destroy = true
  }
}

5. AWS CDK vs. Terraform: Senior Architectural Tradeoffs

In Lesson 0041, you built infrastructure with AWS CDK in TypeScript. In senior interviews, never say one tool is universally better—frame the tradeoff around state ownership, provider scope, and team ergonomics:

Dimension AWS CDK (CloudFormation Engine) Terraform (HCL + Provider Graph)
State & Rollback AWS manages state inside CloudFormation; failed deploys auto-roll back, but stack drift or stuck rollbacks are painful. You manage S3 state + locks; no automatic rollback on partial failure, but state commands give surgical control.
Provider Scope AWS-only (plus limited CloudFormation registry types). Unified DAG across AWS, Cloudflare, GitHub, Datadog, Auth0, and Kubernetes in one apply.
Abstractions Full TypeScript/Java/Python loops, L2/L3 constructs, and .grantRead() least-privilege IAM helpers. Declarative HCL + versioned modules; explicit IAM policies (clearer auditability, more boilerplate).
Scale & Speed Subject to CloudFormation 500-resource stack limit and slower stack change-set previews. Parallel API graph execution; fast local plan diffs across thousands of resources.
