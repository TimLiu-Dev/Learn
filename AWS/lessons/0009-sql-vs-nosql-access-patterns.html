SQL vs NoSQL Access-Pattern Modeling: From Room Tables to DynamoDB Partitions

In relational databases, you model entities and relationships first and figure out queries later with JOINs. In distributed key-value/document stores like Amazon DynamoDB, you do the exact opposite: list every query upfront, pre-join data into partition-keyed item collections, and avoid the hot-partition and Scan traps that wreck production latency and AWS bills.

Your Android Bridge

On Android, you already choose between two storage models every week: Room (SQLite) when you have normalized @Entity tables, foreign keys, and @Relation joins across arbitrary filters—and Preferences DataStore / SharedPreferences when you know the exact key upfront and want a single fast read without running a query planner. In AWS, Amazon RDS / Aurora (PostgreSQL) is your cloud-scale Room database, while Amazon DynamoDB is a distributed, partitioned key-value and document engine where every access pattern must resolve directly to a Partition Key (PK) and optional Sort Key (SK).

1. Entity-First Normalization vs. Access-Pattern-First Modeling

Relational databases (RDS PostgreSQL, Aurora) optimize for storage efficiency and query flexibility. You normalize into 3rd Normal Form (3NF)—separating users, orders, and order_items—so an email update touches one row. The cost is paid at read time: the database engine traverses B-tree indexes and executes JOINs across tables. Up to tens of millions of rows with proper indexing, PostgreSQL handles flexible, ad-hoc queries effortlessly.

Distributed NoSQL databases like Amazon DynamoDB optimize for predictable single-digit-millisecond latency at virtually infinite scale. To guarantee that a lookup at 100 TB runs just as fast as at 10 MB, DynamoDB removes ad-hoc cross-table JOINs altogether. Instead, you design your primary key and item layout around the exact queries your API executes:

  • Partition Key (PK): Hashed internally by DynamoDB's request routers to pick the exact physical storage partition (each SSD-backed partition holds up to 10 GB of data).
  • Sort Key (SK): Stores all items sharing the same PK in sorted B-tree order inside that partition—forming an item collection that supports fast range queries (begins_with, BETWEEN, >=) in a single network call.
  • 400 KB Item Ceiling: Every DynamoDB item (attribute names + values) must stay at or below 400 KB; larger payloads (images, PDFs, verbose logs) belong in Amazon S3 with a pointer stored in the item.
Figure 1: Relational schemas separate entities and join at read time. DynamoDB co-locates related items under a shared Partition Key (PK) and embeds tightly coupled child objects (like order line items) so one Query returns everything in a single round trip.

2. Partition Key Physics: Hot Partitions, GSIs, and the Scan Trap

Even when your application has known access patterns, DynamoDB has hard physical partition limits documented in the AWS DynamoDB Service Quotas and Partition Key Best Practices:

  • Per-Partition Throughput Ceiling: A single storage partition delivers at most 1,000 Write Capacity Units (WCUs) (1 WCU = 1 write/sec up to 1 KB) and 3,000 Read Capacity Units (RCUs) (1 RCU = 1 strongly consistent read/sec up to 4 KB, or 2 eventually consistent reads/sec).
  • Hot Partition Failures: Suppose your table provisions 50,000 WCUs, but you set PK = orderStatus (only 4 distinct values) or PK = "2026-11-15" (today's date). Every write hashes to the same single partition! Once that partition crosses 1,000 WCUs, DynamoDB throws ProvisionedThroughputExceededException even though 98% of your table capacity sits idle.
  • Why Scan + FilterExpression Fails: A common mistake by SQL developers is running Scan with a FilterExpression (e.g., status = 'ACTIVE'). DynamoDB applies FilterExpression after reading every item off SSD—so scanning a 50 GB table to return 1% of matching rows still bills you RCUs for all 50 GB and stalls your API for seconds.
  • Global Secondary Indexes (GSIs) & Backpressure: A GSI projects a subset of attributes under a different PK/SK (for example, looking up an order by orderId when the base table is keyed by userId). GSIs replicate asynchronously (always eventually consistent) and enforce a silent failure mode: if a GSI has low-cardinality keys and throttles, it exerts backpressure that stalls writes to your base table.
When NOT to Choose NoSQL / DynamoDB

Do not force DynamoDB onto workloads with unplanned ad-hoc queries, heavy multi-dimensional filtering (dashboards, BI reporting, GROUP BY), or complex multi-entity ACID invariants. On AWS, choosing Amazon RDS / Aurora PostgreSQL for relational or evolving queries is often faster to build, cheaper to operate, and avoids painful data migrations later.

3. Code Example: Android Room (SQL) vs. AWS DynamoDB Access-Pattern Query

Compare how you fetch a user's recent orders in Android Room (relational join) versus an AWS TypeScript service querying a DynamoDB single-table collection in one round trip: 

// 1. Android Room (Normalized SQLite) — flexible relational query
@Dao
interface OrderDao {
    @Transaction
    @Query("""
        SELECT * FROM orders
        WHERE user_id = :userId AND created_at >= :sinceIso
        ORDER BY created_at DESC
    """)
    suspend fun getRecentOrdersWithItems(userId: String, sinceIso: String): List<OrderWithItems>
}

// 2. AWS DynamoDB (AWS SDK v3 TypeScript) — pre-joined item collection Query
import { DynamoDBClient } from "@aws-sdk/client-dynamodb";
import { DynamoDBDocumentClient, QueryCommand } from "@aws-sdk/lib-dynamodb";

const ddb = DynamoDBDocumentClient.from(new DynamoDBClient({}));

async function getRecentUserOrders(userId: string, sinceIso: string) {
  // Hits ONE storage partition directly; line items are embedded inside each order item
  const res = await ddb.send(new QueryCommand({
    TableName: "AppCoreTable",
    KeyConditionExpression: "PK = :pk AND SK >= :minSk",
    ExpressionAttributeValues: {
      ":pk": `USER#${userId}`,          // High-cardinality PK distributes load evenly
      ":minSk": `ORD#${sinceIso}`,      // Composite SK enables sorted range scan
    },
    ScanIndexForward: false,            // Descending order without in-memory sort
    Limit: 25,
  }));
  return res.Items ?? [];
}
