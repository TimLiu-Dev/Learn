How a Request Travels: From Android OkHttp to Cloud Load Balancers

Before touching AWS IAM or VPCs, a senior engineer must see what happens on the wire when a mobile client calls GET /orders—why cold connections burn hundreds of milliseconds, how connection pooling saves them, and why a 5-second timeout mismatch causes mysterious 502 Bad Gateway outages.

Your Android Bridge

In Android, you configure a singleton OkHttpClient with Retrofit and rarely think about sockets again. Why do senior Android devs say "never instantiate a new OkHttpClient per API call"? Because each new client builds a separate connection pool—throwing away TCP and TLS state and paying full handshake latency on every request. On AWS, the Application Load Balancer (ALB) sits on the opposite side of that exact same pool.

1. The Anatomy of One HTTPS Call (Cold vs. Pooled)

Suppose a user in Dallas taps "Checkout" on your Android app, talking to an API behind an AWS Application Load Balancer in us-east-1 with a 40 ms Round-Trip Time (RTT).

On a cold connection (no cached DNS, no pooled socket), four sequential phases must finish before your server even reads the HTTP request:

  1. DNS Resolution (~1+ RTT): Android asks the OS resolver for the IP of api.myapp.com (managed in AWS by Route 53).
  2. TCP 3-Way Handshake (1 RTT): SYN → SYN-ACK → ACK establishes a reliable byte stream to the ALB.
  3. TLS 1.3 Handshake (1 RTT): The client verifies the server certificate (issued via AWS Certificate Manager) and negotiates symmetric session keys.
  4. HTTP Request / Response (1 RTT + server work): Finally, GET /orders crosses the wire and returns JSON.
Figure 1: Connection pooling eliminates DNS, TCP, and TLS handshakes on subsequent requests. Note: TLS 1.2 costs 2 RTTs instead of 1 RTT for TLS 1.3.

2. The Senior Production Trap: Keep-Alive Close Races (HTTP 502)

Connection pooling happens in two places: between your Android app and the AWS ALB, and between the AWS ALB and your backend servers (e.g., Node.js/Kotlin/Go containers on ECS).

According to the AWS Application Load Balancer specification, the ALB default connection idle timeout is 60 seconds. Meanwhile, Node.js's built-in http.Server defaults to a 5-second keepAliveTimeout!

Here is the race condition that breaks production systems under light traffic:

  1. The ALB keeps a pooled TCP connection open to your backend container, expecting up to 60 seconds of idle reuse.
  2. At second 5.000, your backend container silently closes that idle TCP socket (sending a TCP FIN).
  3. At that exact millisecond, the ALB forwards a new user request down the socket it still thinks is open.
  4. The backend rejects the write with TCP RST, and the ALB returns HTTP 502 Bad Gateway to your Android app—even though your server never crashed.
Golden AWS Rule for Upstream Timeouts

Always set your backend server's keepAliveTimeout strictly greater than the load balancer's idle timeout (e.g., ALB = 60s → Backend keepAliveTimeout = 65s, and headersTimeout = 66s). That way, the ALB always initiates the close cleanly first, eliminating the 502 close race.

3. Code Example: Aligning Client & Server Pools

Compare the Android client configuration you already recognize with the backend server configuration required in production behind an AWS ALB: 

// 1. Android Client (Kotlin / OkHttp) — reuse ONE singleton instance app-wide
val okHttpClient = OkHttpClient.Builder()
    .connectionPool(ConnectionPool(maxIdleConnections = 5, keepAliveDuration = 5, TimeUnit.MINUTES))
    .connectTimeout(5, TimeUnit.SECONDS)   // Bound TCP + TLS handshake wait
    .readTimeout(10, TimeUnit.SECONDS)     // Bound waiting for server response bytes
    .build()

// 2. Cloud Backend (Node.js HTTP Server behind AWS ALB with 60s idle_timeout)
const server = http.createServer(app);
server.keepAliveTimeout = 65_000; // MUST exceed ALB idle_timeout (60,000 ms)
server.headersTimeout   = 66_000; // MUST exceed keepAliveTimeout to avoid header race
