KMS Envelope Encryption, CMKs, Secrets Manager Rotation & SSM Parameter Store

Hardcoded API keys and naive whole-file KMS calls both fail in production—one fails security audits, the other hits a hard 4 KB API wall and drains your KMS quota. Senior cloud engineers combine KMS envelope encryption, strict Key Policies with Encryption Context, and overlapping 30-day secret rotation so credentials roll automatically with zero dropped requests.

Your Android Bridge

In Android, EncryptedSharedPreferences and EncryptedFile (Jetpack Security / Tink) do not ask the hardware AndroidKeyStore to encrypt every megabyte directly. The hardware keystore holds a non-exportable Master Key that wraps a fast symmetric Data Encryption Key (DEK); AES-GCM encrypts your preferences or file locally in RAM. AWS KMS works identically: the HSM-backed Customer Managed Key (CMK) never leaves AWS, while kms:GenerateDataKey mints a 256-bit DEK so your app encrypts payloads locally at memory speed.

1. Envelope Encryption & kms:GenerateDataKey (Why You Never Encrypt Payloads Directly)

AWS KMS enforces a strict 4,096-byte (4 KB) payload ceiling on direct kms:Encrypt calls. Sending a 2 MB PDF or a 50 KB JSON blob directly to KMS fails immediately with ValidationException. Even for tiny 500-byte records, calling KMS over HTTPS on every read/write adds 5–20 ms of network latency, costs $0.03 per 10,000 requests, and consumes your regional KMS request quota (typically 5,500–50,000 requests/sec depending on region and key type).

Envelope encryption splits the job in two:

  1. Generate the Data Key: Your backend calls kms:GenerateDataKey (passing KeySpec: "AES_256" and an EncryptionContext). KMS returns two artifacts: a 32-byte Plaintext DEK and an HSM-encrypted CiphertextBlob (the same DEK wrapped by your CMK).
  2. Encrypt Locally & Zero the Plaintext DEK: Your application encrypts arbitrarily large data (megabytes or gigabytes) in memory using AES-256-GCM with a fresh random 96-bit nonce/IV, then immediately overwrites/zeros the plaintext DEK buffer in RAM.
  3. Store Together: Persist the CiphertextBlob (wrapped DEK) alongside the nonce, GCM authentication tag, and encrypted payload (as S3 SSE-KMS object metadata or a DynamoDB binary attribute).
  4. Decrypt Later: To read the payload, pass only the small CiphertextBlob + matching EncryptionContext to kms:Decrypt, retrieve the plaintext DEK, decrypt the payload locally, and zero the DEK again.
Figure 1: Envelope encryption keeps large payloads off the KMS control plane while retaining HSM-backed auditability (every GenerateDataKey and Decrypt call is logged in CloudTrail).

2. Customer Managed Keys (CMKs), Key Policies & Encryption Context

KMS organizes symmetric keys into three ownership tiers, and picking the wrong tier blocks cross-account sharing or compliance audits later:

KMS Key Tier Monthly Fee Policy Control Rotation & Cross-Account
AWS Owned Key $0 / month None (invisible to you) Managed transparently by AWS (e.g., default DynamoDB encryption). No cross-account sharing.
AWS Managed Key (aws/s3, aws/rds) $0 / month Read-only default policy Rotates automatically every 1 year (365 days). Cannot be shared with another AWS account.
Customer Managed Key (CMK) $1.00 / month (+ $0.03 / 10k API calls) Full Key Policy + Grants Configurable auto-rotation (90–2,560 days, default 365). Supports cross-account sharing and scheduled deletion.
The KMS IAM Trap: Why AdministratorAccess Still Gets AccessDenied

In S3 or DynamoDB, an IAM policy granting * inside the same account works immediately. In KMS, IAM policies cannot grant access to a CMK unless the CMK's resource-based Key Policy explicitly delegates trust to the account root ("Principal": { "AWS": "arn:aws:iam::111122223333:root" } with kms:*). If you remove that root delegation statement to restrict access and forget to list your admin role, even account root cannot manage the key—requiring AWS Support recovery.

Two senior features separate toy KMS setups from production security:

  • Encryption Context (AAD): An optional map of non-secret key-value strings (e.g., { "tenant_id": "acct-89", "table": "invoices" }) passed to both GenerateDataKey and Decrypt. KMS mixes this map into AES-GCM Additional Authenticated Data (AAD) and logs it in CloudTrail. If a compromised microservice swaps Tenant A's encrypted blob into Tenant B's row, decryption cryptographically fails with InvalidCiphertextException—and you can enforce "Condition": { "StringEquals": { "kms:EncryptionContext:tenant_id": "${aws:PrincipalTag/tenant_id}" } } in IAM.
  • Automatic Key Rotation vs. Re-Encryption: Enabling rotation on a symmetric CMK generates new backing key material every 365 days (or 90–2,560 days custom). AWS keeps all previous backing key versions forever so existing ciphertexts still decrypt seamlessly via a key-version header embedded in CiphertextBlob; new encryptions automatically use the latest key material.

3. Secrets Manager vs. SSM Parameter Store

Both services store encrypted strings backed by KMS, yet teams routinely burn hundreds of dollars a month putting static feature flags in Secrets Manager—or fail SOC 2 audits by building fragile cron jobs to rotate RDS passwords in SSM Parameter Store.

Dimension AWS Secrets Manager SSM Parameter Store (Standard / Advanced)
Pricing $0.40 / secret / month + $0.05 per 10,000 API calls Standard: $0 / parameter (10k limit). Advanced: $0.05 / param / month (100k limit).
Max Value Size 64 KB Standard: 4 KB · Advanced: 8 KB
Built-in Rotation Yes (native Lambda rotation state machine + RDS/Redshift/DocDB templates) No native rotation engine (must build EventBridge + Lambda yourself)
Staging Labels Yes (AWSCURRENT, AWSPREVIOUS, AWSPENDING) Numeric versions only (:1, :2); no built-in dual-label rollover
Best For DB passwords, OAuth client secrets, webhook signing keys with 30-day rotation Non-rotating app config, service URLs, API endpoints, static low-risk tokens

4. Zero-Downtime 30-Day Secret Rotation (AWSPENDING → AWSCURRENT → AWSPREVIOUS)

If your Lambda rotator simply overwrites the single PostgreSQL password in place every 30 days, every Fargate container or Lambda instance holding an active connection pool or a cached secret immediately starts failing with 28P01: password authentication failed until its cache expires.

AWS Secrets Manager prevents rotation downtime through a 4-step Lambda state machine paired with alternating dual database users (or multi-key API issuers):

  1. createSecret: Generates a new random password and stores it under staging label AWSPENDING. Production traffic is completely untouched.
  2. setSecret: Connects to RDS as the master/admin user and updates the alternating user (e.g., if AWSCURRENT is app_user_a, update app_user_b) with the AWSPENDING password.
  3. testSecret: Opens a real connection to RDS using the AWSPENDING credentials to prove network reachability, permissions, and password validity before flipping traffic.
  4. finishSecret: Atomically moves the AWSCURRENT label to the new version and demotes the prior version to AWSPREVIOUS. Because app_user_a stays valid for another full rotation cycle (30 days)—far longer than your app's 5–15 minute in-memory cache TTL—existing connection pools drain cleanly with zero errors.
Client Caching Rule: Cache with TTL + Refresh on Auth Failure

Never call secretsmanager:GetSecretValue on every incoming HTTP request—at 2,000 RPS that costs ~$260/month in API charges alone and couples your p99 latency to Secrets Manager. Cache the secret in memory (or use the AWS Parameters and Secrets Lambda Extension / Secrets Manager Caching Client) with a 5–15 minute TTL plus jitter, and force a single cooldown-protected cache refresh if a downstream DB/API rejects the cached credential.

5. Production Code: KMS Key Policy & Envelope Encryption with Context

Notice two critical guards in the production configuration below: the CMK Key Policy enables IAM delegation while scoping application decryption strictly to the expected EncryptionContext, and the TypeScript helper wipes the plaintext DEK buffer in a finally block even if AES-GCM throws. 

// 1. KMS Key Policy (JSON) — Root IAM delegation + Condition-guarded Decrypt
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "EnableAccountIAMPolicies",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::111122223333:root" },
      "Action": "kms:*",
      "Resource": "*"
    },
    {
      "Sid": "AllowOrdersServiceWithTenantContext",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::111122223333:role/orders-ecs-task" },
      "Action": ["kms:GenerateDataKey", "kms:Decrypt"],
      "Resource": "*",
      "Condition": {
        "StringEquals": {
          "kms:EncryptionContext:service": "orders-api"
        }
      }
    }
  ]
}

// 2. Node.js / TypeScript — Envelope Encryption + Zeroing Plaintext DEK
import crypto from "node:crypto";
import { KMSClient, GenerateDataKeyCommand } from "@aws-sdk/client-kms";

const kms = new KMSClient({});

export async function envelopeEncrypt(payload: Buffer, keyId: string, tenantId: string) {
  const { Plaintext, CiphertextBlob } = await kms.send(new GenerateDataKeyCommand({
    KeyId: keyId,
    KeySpec: "AES_256",
    EncryptionContext: { service: "orders-api", tenant_id: tenantId }
  }));

  const dek = Buffer.from(Plaintext!);
  try {
    const iv = crypto.randomBytes(12); // 96-bit GCM nonce
    const cipher = crypto.createCipheriv("aes-256-gcm", dek, iv);
    const ciphertext = Buffer.concat([cipher.update(payload), cipher.final()]);
    return {
      encryptedDek: Buffer.from(CiphertextBlob!).toString("base64"),
      iv: iv.toString("base64"),
      authTag: cipher.getAuthTag().toString("base64"),
      ciphertext: ciphertext.toString("base64")
    };
  } finally {
    dek.fill(0); // Wipe plaintext DEK from process memory immediately
  }
}
