Multi-Account Landing Zones: Organizations, Control Tower, SCPs & Identity Center

Putting dev, staging, and prod inside a single AWS account is the cloud equivalent of shipping debug and release builds under one Play Store package name. Senior AWS architectures treat each AWS account as a hard blast-radius boundary, unified by AWS Organizations, Guardrail SCPs, Control Tower, and IAM Identity Center.

Your Android Bridge

In Android Gradle builds, you separate productFlavors and buildTypes (dev, stage, prod) with distinct applicationIds (com.myapp.dev vs com.myapp), separate Firebase projects, and an isolated release signing keystore that developers never hold on their laptops. On AWS, IAM roles and VPCs inside one account are not strong enough for environment isolation: a noisy dev load test can still exhaust account-wide Lambda concurrency quotas, and a misconfigured wildcard IAM policy can delete production data. An AWS Organizations landing zone gives every environment its own account, enforces unbreakable ceilings via Service Control Policies (SCPs), and federates engineers through IAM Identity Center without static keys.

1. Why One Account Breaks in Production (Blast Radius & Quotas)

Teams often start with one AWS account and separate environments with resource prefixes (dev-orders vs prod-orders) or tags. That pattern fails along four dimensions as soon as traffic and headcount grow:

  • Shared Service Quotas (Noisy Neighbors): Many AWS limits are enforced per account, per Region. By default, an account gets 1,000 concurrent Lambda executions and 5 VPCs per Region, plus shared control-plane API rate limits (e.g., EC2 DescribeInstances and CloudFormation throttling). A runaway dev load test or CI loop can throttle prod APIs in the same account.
  • IAM Policy & Lateral-Movement Blast Radius: Inside one account, an overly permissive CI role or S3 bucket policy with a missing resource restriction can reach production buckets or RDS snapshots. Cross-account access, by contrast, requires an explicit two-way handshake (trust policy + identity policy via sts:AssumeRole).
  • Cost & Compliance Isolation: Separate accounts generate clean per-account billing lines in AWS Cost Explorer without relying on 100% tag compliance, and isolate PCI/HIPAA/SOC2 audit scopes from experimental developer sandboxes.
  • Operational Limits: Single accounts hit hard ceilings such as 5,000 IAM users and 1,000–5,000 IAM roles, making large microservice fleets fragile.

According to the AWS Multi-Account Strategy whitepaper, a production landing zone groups accounts into purpose-built Organizational Units (OUs) under a single Organization Root:

2. Service Control Policies (SCPs): How Guardrail Math Works

A Service Control Policy (SCP) is an organization-wide JSON policy attached to the Root, an OU, or a specific Account. Understanding SCP evaluation prevents the most common multi-account lockouts:

  1. SCPs Filter—They Never Grant Permissions: An SCP with "Effect": "Allow" does not give any IAM user or role permission to do anything. Effective permission is the intersection of the account's IAM identity/resource policies and every SCP in its ancestor chain: Effective = (IAM Allow) ∩ (Root SCP Allow) ∩ (Parent OU SCP Allow) ∩ (Account SCP Allow) − (Any Explicit Deny).
  2. Every Level in the Path Must Allow: For an API call to pass the SCP layer, every single node from Root down through every intermediate OU to the target Account must have at least one matching Allow statement (usually AWS's default managed FullAWSAccess policy), and zero nodes may have a matching Deny statement. Detaching FullAWSAccess from an OU without replacing it with another Allow policy immediately blocks all API calls for every account in that OU.
  3. Explicit Deny Beats Everything: An explicit Deny inside an SCP overrides AdministratorAccess ("*") inside a member account—and even blocks the member account's root user.
  4. Two Critical Exemptions: SCPs never apply to principals in the Management Account, and SCPs never restrict AWS Service-Linked Roles (e.g., AWSServiceRoleForAutoScaling).
Senior Trap: Region-Restriction SCPs Breaking Global Control Planes

If you attach an SCP that denies every action when aws:RequestedRegion is outside eu-west-1 or eu-central-1, you will accidentally break IAM, STS (global endpoint), CloudFront, Route 53, Organizations, Budgets, and AWS Support—because those global control-plane APIs evaluate aws:RequestedRegion as us-east-1. Always pair a Region-lock SCP with a NotAction block exempting global services, and check AWS's hard SCP quotas: 5,120 bytes max per SCP document and max 5 SCPs attached directly per Root, per OU, and per Account.

In practice, teams choose between two SCP design patterns:

Strategy How It Works Production Tradeoff
Deny-List (Recommended Default) Keep FullAWSAccess attached at every node; attach targeted Deny SCPs for invariants (root user, CloudTrail tampering, unapproved Regions, public S3). Low friction when AWS launches new services; developers keep velocity inside approved guardrails.
Allow-List (Strict Regulated) Detach FullAWSAccess and attach explicit Allow lists naming only approved services/actions at each OU. Zero new services work until security updates the SCP; easy to break hidden dependencies (e.g., KMS, STS, CloudWatch Logs) across 5,120-byte limits.

3. Control Tower & IAM Identity Center (Zero Static Keys)

Building an Organization by hand—wiring CloudTrail into a central S3 bucket, enabling AWS Config aggregators across 15 Regions, writing baseline SCPs, and vending new accounts—is error-prone. AWS Control Tower automates that Landing Zone baseline and exposes Account Factory to vend new accounts with pre-attached guardrails:

  • Preventive Controls (SCPs): Block forbidden actions before they execute (e.g., disallow disabling CloudTrail or creating public S3 buckets).
  • Detective Controls (AWS Config Rules): Continuously evaluate resource configurations and surface non-compliance alerts (e.g., an EBS volume created without encryption or an IAM user created with console access).
  • Proactive Controls (CloudFormation Hooks): Inspect CloudFormation templates before provisioning starts and reject non-compliant infrastructure in CI/CD.

For human access across dozens of accounts, AWS IAM Identity Center (formerly AWS SSO) eliminates per-account IAM users and long-lived AKIA... access keys. You connect your corporate IdP (Google Workspace, Okta, or Microsoft Entra ID via SAML 2.0 + SCIM group sync) once in the Management Account (or a delegated admin account), then map IdP groups to Permission Sets per OU/account. Each login or CLI session (aws sso login) mints short-lived STS credentials—for example, 8–12 hours in NonProd and 1 hour (PT1H) read-only or break-glass admin in Prod. Removing an engineer from your corporate IdP revokes access to every AWS account immediately.

4. Production Code: Multi-Guardrail SCP & Terraform Identity Center Assignment

Because each OU accepts at most 5 attached SCPs (5,120 bytes each), production landing zones pack cohesive invariants into one well-structured policy and manage attachments plus Identity Center Permission Sets via IaC: 

// 1. Production Guardrail SCP (JSON) — packs Root Lock + Region Lock + Public S3 Lock
//    Must stay <= 5,120 bytes; keep FullAWSAccess attached alongside this Deny policy.
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyMemberRootUserActions",
      "Effect": "Deny",
      "Action": "*",
      "Resource": "*",
      "Condition": {
        "StringLike": { "aws:PrincipalArn": ["arn:aws:iam::*:root"] }
      }
    },
    {
      "Sid": "DenyUnapprovedRegionsExceptGlobalControlPlanes",
      "Effect": "Deny",
      "NotAction": [
        "iam:*", "sts:*", "organizations:*", "cloudfront:*", "route53:*", "support:*"
      ],
      "Resource": "*",
      "Condition": {
        "StringNotEquals": { "aws:RequestedRegion": ["us-east-1", "us-west-2"] }
      }
    },
    {
      "Sid": "DenyDisablingS3PublicAccessBlockOrCloudTrail",
      "Effect": "Deny",
      "Action": [
        "s3:PutAccountPublicAccessBlock",
        "s3:PutBucketPublicAccessBlock",
        "cloudtrail:StopLogging",
        "cloudtrail:DeleteTrail"
      ],
      "Resource": "*"
    }
  ]
}

# 2. Terraform — Attach SCP to Prod OU & bind 1-hour Identity Center Permission Set
resource "aws_organizations_policy_attachment" "prod_guardrails" {
  policy_id = aws_organizations_policy.prod_guardrails.id
  target_id = aws_organizations_organizational_unit.prod.id
}

resource "aws_ssoadmin_permission_set" "prod_readonly" {
  name             = "ProdReadOnly"
  instance_arn     = tolist(data.aws_ssoadmin_instances.main.arns)[0]
  session_duration = "PT1H" # Short STS lease in Prod; PT8H in NonProd
}
