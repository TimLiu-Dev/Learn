Authentication & Authorization: OAuth 2.0, OIDC, JWT & RBAC/ABAC

Getting a user logged in on Android with AppAuth or Credential Manager is only half the contract. A senior backend engineer must verify cryptographic tokens without falling into alg=none or confused-deputy traps, separate 401 authentication from 403 authorization, and stop cross-tenant IDOR bugs with RBAC + ABAC policy checks.

Your Android Bridge

On Android, you integrate AppAuth (Custom Tabs + PKCE) or Credential Manager, store tokens inside EncryptedSharedPreferences backed by the Android Keystore, and attach Authorization: Bearer <token> in an OkHttp interceptor. Crucially, an Android APK is a public client: anyone can decompile it with jadx in seconds, so you can never embed a client_secret or trust client-decoded claims. Every trust decision happens on the server after cryptographic signature and policy verification.

1. OAuth 2.0 vs. OIDC: PKCE & the Three-Token Split

Junior developers frequently conflate OAuth 2.0 (RFC 6749) with login. OAuth 2.0 is strictly an authorization delegation protocol ("grant this app permission to call my API"); it does not define how the user logged in or what a token looks like. OpenID Connect (OIDC) 1.0 layers identity on top of OAuth 2.0 (triggered by scope=openid profile email) and returns three distinct artifacts with different audiences and lifetimes:

  1. ID Token (always a JWT): Proof of authentication intended solely for the client app (aud = android_client_id). Android reads name, email, and sub for UI display. Never send an ID token as a bearer token to backend resource APIs.
  2. Access Token (JWT or opaque): Authorization credential sent to your backend API (aud = https://api.myapp.com, scope = orders:read orders:write). Keep lifetimes short—typically 5 to 15 minutes (60 minutes max)—because stateless JWTs cannot be cheaply revoked before exp.
  3. Refresh Token (opaque string): Long-lived credential (7 to 90 days) sent only to the Identity Provider's /oauth/token endpoint. Production systems enforce Refresh Token Rotation: every refresh invalidates the old refresh token and issues a new pair; if a stolen old token is replayed, the server revokes the entire token family.

Because mobile apps cannot keep a static secret confidential, RFC 7636 (PKCE) replaces static client_secret strings with a per-login cryptographic proof. Android generates a 43–128 character random code_verifier, hashes it with SHA-256 into code_challenge on /authorize, and sends the raw code_verifier when redeeming the authorization code at /token.

Figure 1: Mobile OIDC login uses PKCE with the IdP, then sends only the short-lived Access Token to backend APIs, which verify JWKS signatures locally and enforce two separate gates (401 vs. 403).

2. JWT Verification Internals & Senior Failure Modes

A JSON Web Token (RFC 7519) is three Base64URL-encoded segments: header.payload.signature. By default, a signed JWT (JWS) is integrity-protected, not encrypted—anyone holding the token can decode the JSON payload. Never store passwords, API secrets, or sensitive PII inside standard JWT claims.

In production, Identity Providers sign tokens using asymmetric cryptography (RS256 or ES256) and publish their public keys at a discovery endpoint (/.well-known/jwks.json). Your backend caches the JWKS keys in memory (for example, 5–15 minutes), looks up the signing key by the header's kid (Key ID), and refreshes the cache (with rate-limiting) if an unrecognized kid arrives during key rotation.

Signature verification alone is not enough. Senior engineers explicitly guard against four production failures:

  • alg=none & Key-Confusion Attacks: Never let the unverified token header pick the verification algorithm. Pin an explicit allowlist (e.g., ["RS256", "ES256"]) in your JWT library so an attacker cannot pass "alg": "none" or trick an HMAC verifier into using your public RSA key as a shared secret.
  • Missing aud (Audience) Check (Confused Deputy): Suppose your Billing API and Marketing Portal share one AWS Cognito User Pool or Auth0 tenant. A token issued for Marketing has a valid signature and valid iss. Only checking aud === "https://billing.myapp.com" prevents cross-service token replay.
  • Clock Skew vs. Replay Window: Server clocks across containers drift by a few seconds. Standard verifiers allow 30 to 60 seconds of clock skew on exp and nbf, while keeping access token TTLs short.
  • The Stateless Revocation Gap: When a user changes their password or an employee is offboarded, already-minted JWTs stay valid until exp. For high-risk endpoints (transfers, role edits), combine short JWT TTLs with a lightweight cache check (e.g., Redis min_token_iat per user, covered in Lesson 0006).
401 Unauthorized vs. 403 Forbidden (Contract Matters for Android)

Return 401 Unauthorized only when authentication failed (missing header, invalid signature, bad iss/aud, expired exp)—this signals Android's OkHttp Authenticator to silently exchange the refresh token once and retry. Return 403 Forbidden when the token is valid, but the caller lacks the required scope, role, or resource ownership; retrying with a refreshed token will never succeed.

3. Authorization: Scopes, RBAC, and ABAC (IDOR Defense)

Once Gate 1 proves who the caller is (sub, tenantId, role, scopes), Gate 2 answers what they may touch:

  • OAuth Scopes (Delegation Boundary): Coarse capability strings like invoices:read or invoices:write restricting what the client application is authorized to invoke on the user's behalf.
  • RBAC (Role-Based Access Control): Maps users to roles (VIEWER, SUPPORT, ADMIN) checked against route permissions. RBAC is fast and auditable, but breaks down on multi-tenant ownership rules—you cannot create a separate role per customer tenant without causing role explosion.
  • ABAC (Attribute-Based Access Control): Evaluates attributes of the Subject (claims.tenantId, claims.sub), Resource (invoice.tenantId, invoice.status), and Environment (time, IP).

In multi-tenant SaaS backends, the #1 authorization vulnerability (OWASP API1:2023 Broken Object Level Authorization / IDOR) happens when RBAC passes, but ABAC is omitted: an "ADMIN" of Tenant A sends DELETE /invoices/inv_999 (owned by Tenant B) and succeeds because the handler never verified claims.tenantId === invoice.tenantId. Never read tenantId from request headers or JSON bodies—always derive it from the verified JWT and enforce it in both your policy evaluator and database WHERE tenant_id = $1 predicates.

4. Code Example: Android OkHttp Refresh + Backend Policy Guard

Notice how the Android client and the cloud backend form two halves of one contract: Android handles 401 via a synchronized Authenticator, while the backend enforces cryptographic JWT claims before running RBAC/ABAC checks (on AWS, API Gateway HTTP API JWT Authorizers can offload Gate 1 at the edge). 

// 1. Android Client (Kotlin / OkHttp) — handle 401 by refreshing ONCE, never retry 403
class TokenAuthenticator(private val authRepo: AuthRepository) : Authenticator {
    override fun authenticate(route: Route?, response: Response): Request? {
        if (response.priorResponse != null) return null // Prevent infinite 401 retry loop
        val freshAccessToken = authRepo.refreshAccessTokenBlocking() ?: return null
        return response.request.newBuilder()
            .header("Authorization", "Bearer $freshAccessToken")
            .build()
    }
}

// 2. Cloud Backend Middleware (TypeScript) — pinned alg, JWKS verify, then RBAC + ABAC
async function requireAccess(req: Request, requiredScope: string, allowedRoles: string[]) {
  const token = req.headers.authorization?.replace(/^Bearer\s+/i, "");
  if (!token) throw new HttpError(401, "MISSING_BEARER_TOKEN");

  // jose jwtVerify pins algorithms, verifies signature via cached JWKS, and checks iss/aud/exp
  const { payload } = await jwtVerify(token, jwksClient, {
    issuer: "https://cognito-idp.us-east-1.amazonaws.com/us-east-1_ProdPool",
    audience: "https://api.myapp.com",
    algorithms: ["RS256"],
    clockTolerance: 30,
  }); // throws -> map to HTTP 401

  const scopes = String(payload.scope || "").split(" ");
  if (!scopes.includes(requiredScope)) throw new HttpError(403, "INSUFFICIENT_SCOPE");
  if (!allowedRoles.includes(String(payload["custom:role"]))) throw new HttpError(403, "ROLE_DENIED");

  // ABAC tenant boundary: derived strictly from verified JWT, never from req.body
  const resource = await db.invoices.findById(req.params.id);
  if (!resource || resource.tenantId !== payload["custom:tenantId"]) {
    throw new HttpError(403, "TENANT_MISMATCH");
  }
  return payload;
}
