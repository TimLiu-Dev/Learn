Stateful Security Groups vs Stateless NACLs & VPC Flow Logs Debugging

In production AWS VPCs, two firewall layers protect every workload: Security Groups (SGs) attached to elastic network interfaces and Network ACLs (NACLs) attached to subnets. Mixing up stateful connection tracking with stateless ephemeral return rules causes silent timeouts that only VPC Flow Logs expose.

Your Android Bridge

In Android, res/xml/network_security_config.xml declares an explicit trust boundary for outbound traffic—blocking cleartext HTTP by default and pinning trusted CAs per domain so individual OkHttp calls cannot bypass policy. In AWS, Security Groups enforce that same declarative allow-list mindset at the ENI boundary—except instead of pinning hostnames, you chain SG-to-SG references (sg-alb → sg-ecs → sg-rds), while NACLs act like a raw stateless packet filter at the subnet edge that forgets every connection the moment a packet leaves.

1. Two Firewalls on Every Packet Path (Stateful vs. Stateless)

Every packet entering or leaving an EC2 instance, ECS task ENI, RDS instance, or Application Load Balancer crosses two independent enforcement boundaries in strict order:

  • Ingress path (into the workload): Subnet Route Table → NACL Inbound → Security Group Inbound → Target ENI.
  • Egress path (out of the workload): Source ENI → Security Group Outbound → NACL Outbound → Subnet Route Table.
Dimension Security Group (SG) Network ACL (NACL)
Attachment Scope Elastic Network Interface (ENI) — per instance, ECS task, or RDS endpoint. Subnet boundary — affects every ENI in associated subnets (1 NACL per subnet).
Statefulness Stateful: Return traffic for an allowed flow is automatically permitted regardless of opposite-direction rules. Stateless: Inbound and outbound are evaluated independently; return packets must match explicit ephemeral port rules.
Rule Semantics Allow-only (no explicit DENY rules). Implicit deny if no allow rule matches. Allow and Deny rules, evaluated in ascending rule number (1–32766); first match wins; default rule * denies.
Source / Dest Targets CIDR blocks, prefix lists, or other Security Group IDs (including self-referencing). IPv4/IPv6 CIDR blocks only — NACLs have no awareness of Security Group IDs.
Default Quotas 60 inbound + 60 outbound rules per SG; up to 5 SGs per ENI (adjustable). 20 rules per direction per NACL (hard limit up to 40; AWS recommends numbering by 100s).
Figure 1: Security Groups remember the inbound 5-tuple and automatically allow the return response, whereas stateless NACLs require explicit outbound ephemeral port rules (1024–65535) or the return SYN-ACK dies silently.

2. SG-to-SG Chaining & Self-Referencing Patterns

Junior engineers often copy subnet CIDRs into Security Group rules (for example, allowing 10.0.10.0/24 onto RDS port 5432). In an autoscaling, multi-AZ architecture, CIDR-based SG rules create two operational hazards:

  1. Overly broad blast radius: Any compromised container or bastion that happens to land in 10.0.10.0/24 inherits database access even if its role does not need it.
  2. Brittle IP churn: When ECS tasks scale out or replace across multiple subnets, or when an ALB scales its node IPs dynamically, CIDR rules silently go stale.

Instead, reference the caller's Security Group ID directly. According to the AWS Security Group Rules specification, VPC resolves the membership of every ENI carrying that source SG ID dynamically in the control plane:

  • Tier chaining: sg-alb allows 0.0.0.0/0:443 → sg-api allows source: sg-alb on 8080 → sg-rds allows source: sg-api on 5432.
  • Self-referencing SGs: Distributed caches (Redis clusters) or worker meshes attach sg-cache to every node and add an inbound rule with source: sg-cache so peers talk freely without hardcoding cluster IPs.
  • Peered-VPC limitation: SG-to-SG referencing works across subnets and AZs in one VPC, and across same-region VPC Peering, but not across Transit Gateway or AWS PrivateLink endpoints—where you fall back to CIDR or prefix-list rules.

3. The Classic Stateless NACL Outage: Ephemeral Return Ports

Every VPC ships with a default NACL that allows all inbound and outbound traffic (Rule #100 ALLOW ALL 0.0.0.0/0). When teams create a custom NACL for compliance, AWS initializes it with only the catch-all deny rule (* DENY ALL) in both directions.

Consider what happens if you allow inbound HTTPS (443) and outbound PostgreSQL (5432) on a custom NACL, forgetting return traffic:

  • An ALB opens an ephemeral source port (AWS ELB/ALB, NAT Gateway, and IANA clients use 1024–65535; Linux kernels typically allocate 32768–60999) to connect to your backend on port 443.
  • Your backend sends a TCP SYN-ACK back to <ALB_IP>:52100.
  • Because the NACL is stateless, it evaluates Outbound rules against destination port 52100—finds no match—hits * DENY, and silently drops the packet.
Two Production Traps with NACLs & Connection Tracking

1. Asymmetric Ephemeral Failure: Any custom NACL protecting TCP workloads must allow 1024–65535 on the return direction (outbound for servers accepting requests, inbound for clients initiating outbound HTTPS/DB calls).
2. Untracked SG Connections: Per the AWS Connection Tracking rules, if a Security Group allows 0.0.0.0/0 on all protocols and ports in both directions (or matches an identical broad rule in both directions), AWS treats the flow as untracked. Never mix a wide-open SG rule with a narrower opposite-direction change without expecting connection tracking state to reset.

4. Debugging Packet Drops with VPC Flow Logs

When a service times out, you cannot run tcpdump on a managed ALB, NAT Gateway, or RDS endpoint. VPC Flow Logs capture IP traffic metadata directly at the Nitro hypervisor boundary of a VPC, subnet, or individual ENI and publish records to CloudWatch Logs, S3, or Kinesis Data Firehose.

Each flow record aggregates packets over a 1-minute or 10-minute capture window (with roughly 1–5 minutes of delivery delay to CloudWatch/S3). A default Version 2 record contains 14 space-delimited fields: 

# Default VPC Flow Log v2 format:
# version account-id interface-id srcaddr dstaddr srcport dstport protocol packets bytes start end action log-status

2 123456789012 eni-0a1b2c3d4e5f 10.0.1.10 10.0.10.25 52100 443 6 4 240 1731650400 1731650460 ACCEPT OK
2 123456789012 eni-0a1b2c3d4e5f 10.0.10.25 10.0.1.10 443 52100 6 3 180 1731650400 1731650460 REJECT OK

Read those two lines like a senior incident responder:

  • protocol 6 = TCP (17 = UDP, 1 = ICMP).
  • Line 1 shows 10.0.1.10:52100 → 10.0.10.25:443 marked ACCEPT OK: both the NACL inbound rule and the SG inbound rule allowed the request in.
  • Line 2 shows the return flow 10.0.10.25:443 → 10.0.1.10:52100 marked REJECT OK. Because the Security Group automatically tracks established inbound TCP flows, an outbound REJECT on an ephemeral destination port (52100) immediately proves a stateless NACL outbound rule dropped the return packet!
  • Note what Flow Logs omit: traffic to Amazon DNS (+2), instance metadata (169.254.169.254), DHCP, and VPC router ARP. And remember: Flow Logs record REJECT for both SG and NACL drops, without labeling which one—you infer the layer from direction, port, and rule state.

5. Production Code: Android Policy vs. AWS CDK SG Chain & Custom NACL

Notice the architectural symmetry between Android's declarative network policy and an AWS CDK TypeScript stack enforcing SG-to-SG chaining, stateless NACL ephemeral ranges, and VPC Flow Logs: 

<!-- 1. Android: res/xml/network_security_config.xml (declarative outbound trust boundary) -->
<network-security-config>
  <base-config cleartextTrafficPermitted="false" />
  <domain-config cleartextTrafficPermitted="false">
    <domain includeSubdomains="true">api.myapp.com</domain>
    <pin-set expiration="2027-06-01">
      <pin digest="SHA-256">7HIpactkIAq2Y49orFOOQKurWxmmSFZhBCoQYcRhJ3Y=</pin>
    </pin-set>
  </domain-config>
</network-security-config>
// 2. AWS CDK (TypeScript): SG-to-SG chaining + Custom NACL + VPC Flow Logs
const albSg = new ec2.SecurityGroup(this, "AlbSg", { vpc, allowAllOutbound: false });
const apiSg = new ec2.SecurityGroup(this, "ApiSg", { vpc, allowAllOutbound: false });
const rdsSg = new ec2.SecurityGroup(this, "RdsSg", { vpc, allowAllOutbound: false });

albSg.addIngressRule(ec2.Peer.anyIpv4(), ec2.Port.tcp(443), "HTTPS from Android clients");
albSg.addEgressRule(apiSg, ec2.Port.tcp(8080), "Forward only to API SG");

apiSg.addIngressRule(albSg, ec2.Port.tcp(8080), "Accept only from ALB SG");
apiSg.addEgressRule(rdsSg, ec2.Port.tcp(5432), "Query only RDS SG");

rdsSg.addIngressRule(apiSg, ec2.Port.tcp(5432), "Postgres only from API SG");

// Stateless NACL for private API subnet — MUST include ephemeral ports 1024-65535
const apiNacl = new ec2.NetworkAcl(this, "ApiNacl", {
  vpc,
  subnetSelection: { subnetType: ec2.SubnetType.PRIVATE_WITH_EGRESS },
});
apiNacl.addEntry("AllowAlbInbound", {
  ruleNumber: 100,
  cidr: ec2.AclCidr.ipv4("10.0.0.0/16"),
  traffic: ec2.AclTraffic.tcpPort(8080),
  direction: ec2.TrafficDirection.INGRESS,
  ruleAction: ec2.Action.ALLOW,
});
apiNacl.addEntry("AllowEphemeralOutbound", {
  ruleNumber: 100,
  cidr: ec2.AclCidr.ipv4("10.0.0.0/16"),
  traffic: ec2.AclTraffic.tcpPortRange(1024, 65535),
  direction: ec2.TrafficDirection.EGRESS,
  ruleAction: ec2.Action.ALLOW,
});

// Enable 1-minute VPC Flow Logs for SG/NACL debugging
vpc.addFlowLog("VpcFlowLogs", {
  trafficType: ec2.FlowLogTrafficType.ALL,
  maxAggregationInterval: ec2.FlowLogMaxAggregationInterval.ONE_MINUTE,
});

Why Rule Numbers in Multiples of 100? NACL rules evaluate from lowest number to highest. Leaving gaps (100, 200, 300) lets you insert an emergency #50 DENY block during an incident without renumbering existing rules.
Ephemeral Range Differences AWS ELB/ALB, NAT Gateways, and IANA use ports 1024–65535, whereas modern Linux kernels default to 32768–60999. Always use 1024–65535 on NACL return rules unless every caller is strictly pinned.
