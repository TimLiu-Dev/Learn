Queues, At-Least-Once Delivery, Idempotency Keys, Outbox Pattern & DLQs

In Android, WorkManager.enqueueUniqueWork() relies on a single device's SQLite database to guarantee a background job runs once. Across distributed cloud producers, Amazon SQS queues, and auto-scaling worker fleets, exactly-once delivery is a trap—so senior systems combine at-least-once delivery, idempotency key stores, the transactional outbox, and Dead-Letter Queues (DLQs) to stay consistent under crashes and retries.

Your Android Bridge

On Android, when you schedule an offline upload with WorkManager.getInstance(ctx).enqueueUniqueWork("order-42", ExistingWorkPolicy.KEEP, request), WorkManager stores the work row inside its local Room/SQLite table and enforces uniqueness on one CPU. In AWS, your API servers, message broker (Amazon SQS), and consumer containers run on separate machines across Availability Zones. If a worker crashes after charging a credit card—or simply pauses longer than the queue's visibility timeout—SQS assumes the job failed and hands the exact same message to another container.

1. At-Least-Once Delivery & the Visibility Timeout Trap

In distributed messaging, brokers make a deliberate CAP/latency tradeoff: at-least-once delivery guarantees no acknowledged message is lost, at the cost of occasionally delivering the same message two or more times.

In Amazon SQS, messages stay in the queue until a consumer explicitly calls DeleteMessage:

  1. Receive & Lease: Worker A calls ReceiveMessage. SQS hands out the message and hides it from other workers for the VisibilityTimeout (default 30 seconds, configurable from 0s to 12 hours).
  2. The Slow-Consumer Duplicate: Suppose Worker A hits a GC pause or slow third-party API call and takes 38 seconds. At second 30.000, the visibility lease expires. SQS makes the message visible again, increments ApproximateReceiveCount, and delivers it to Worker B.
  3. Concurrent Execution: Worker A and Worker B now process the same order simultaneously unless your consumer enforces idempotency at the data layer.
Standard vs. FIFO SQS Throughput & Guarantees

SQS Standard offers nearly unlimited transactions per second (TPS), best-effort ordering, and occasional duplicates by design. SQS FIFO preserves strict ordering per MessageGroupId and deduplicates identical MessageDeduplicationId sends within a 5-minute window (up to 300 TPS unbatched, 3,000 TPS with 10-message batches, or higher with High Throughput FIFO). Crucially, FIFO still redelivers on visibility timeout expiry—so neither queue type excuses non-idempotent consumers.

2. Idempotency Keys & Atomic Deduplication Stores

An operation is idempotent when executing it multiple times with the same key produces the same final state as executing it once. As detailed in the Amazon Builders' Library guide on idempotent APIs, a naive if (!seen) { chargeCard(); markSeen(); } check fails under concurrency because two workers can both pass !seen before either writes markSeen() (a TOCTOU race).

Production idempotency stores use a two-phase atomic claim backed by a unique constraint (PostgreSQL PRIMARY KEY or DynamoDB ConditionExpression: "attribute_not_exists(idempotency_key)"):

  • Phase 1 — Atomic Claim (IN_PROGRESS): Before running side effects, insert (key, status='IN_PROGRESS', payload_hash, locked_until) with ON CONFLICT DO NOTHING. If 0 rows are inserted, another worker already owns or finished the key.
  • Payload Hash Guard: Always store a SHA-256 hash of the canonical payload. If a client or bug reuses key = "order-42" with amount = $99 after previously sending amount = $49, fail loudly with a non-retryable PAYLOAD_MISMATCH error rather than returning stale success.
  • Phase 2 — Finalize or Release: On success, update the row to status = 'SUCCEEDED' along with the serialized result (same transaction as your DB business mutation if both live in PostgreSQL). On transient failure, delete the IN_PROGRESS lock so the next SQS retry can claim and succeed.
  • Retention Horizon: Keep idempotency records longer than your maximum retry + DLQ redrive window. Because SQS retention maxes out at 14 days, retain idempotency keys for at least 14–30 days before DynamoDB TTL or Postgres partition cleanup reclaims them.

3. The Transactional Outbox Pattern

Suppose your Checkout service needs to record an order in PostgreSQL and notify a fulfillment queue in SQS. Calling SQS inside the database transaction blocks a precious PostgreSQL connection and holds row locks for 20–500 ms of remote network I/O (or full timeout failures). Calling SQS after COMMIT creates the dual-write gap: if the container is OOM-killed or loses network connectivity in the 2 milliseconds between COMMIT and sqs.sendMessage(), the order exists with no event.

The Transactional Outbox solves both problems using the database's own ACID atomicity:

  1. Inside one local transaction, insert into orders and insert an event row into outbox_events(id, aggregate_id, payload, created_at, published_at). Either both commit or both roll back.
  2. A separate Outbox Relay worker (polling via SELECT ... FOR UPDATE SKIP LOCKED LIMIT 100 every 200 ms, or streaming PostgreSQL WAL changes via Debezium / AWS DMS) reads unpublished rows, calls sqs.sendMessageBatch(), and updates published_at = NOW().
  3. If the relay crashes after sendMessageBatch() but before updating published_at, it republishes that row on restart—which is completely safe because your downstream consumer uses the event's id as its idempotency key.

4. Dead-Letter Queues (DLQs), Poison Pills & Redrive

What happens when a message is structurally broken—a poison pill such as invalid JSON, a missing required field, or a bug in consumer code? Without a boundary, SQS delivers that message endlessly until retention expires, burning worker concurrency and starving healthy traffic (and in FIFO queues, blocking every later message in the same MessageGroupId).

Attach an SQS Redrive Policy (deadLetterTargetArn + maxReceiveCount, typically 3 to 5 for event-driven workloads):

  • How maxReceiveCount Works: Each time SQS hands a message to a consumer, ApproximateReceiveCount increments. When a message exceeds maxReceiveCount (i.e., fails or expires visibility again), SQS automatically moves it to the DLQ.
  • Fail Fast on Non-Retryable Errors: If your consumer catches a deterministic schema/validation error (retryable: false), don't waste 4 more visibility cycles—explicitly send or route it to the DLQ and delete it from the source queue immediately.
  • Retention Clock Gotcha: SQS preserves the message's original enqueue timestamp when moving it to a DLQ. If your source queue has a 4-day retention and your DLQ also has 4-day retention, a message moved on day 3.9 expires in 2 hours! Always configure DLQ MessageRetentionPeriod to 14 days (1209600 seconds) and set a CloudWatch alarm on ApproximateNumberOfMessagesVisible > 0.
  • Safe Replay (DLQ Redrive): Once a fix is deployed, use SQS StartMessageMoveTask to drain the DLQ back into the source queue at a controlled rate (e.g., 50 msg/sec) so replay doesn't trigger a thundering herd.

5. Production Code: Outbox Schema, Idempotent Consumer & SQS Redrive

Notice how three short pieces fit together: an atomic PostgreSQL transaction writes both order and outbox event, the consumer claims the idempotency key with ON CONFLICT DO NOTHING, and Terraform enforces a 14-day DLQ with maxReceiveCount = 5. 

-- 1. PostgreSQL Transactional Outbox + Idempotency Key Store
BEGIN;
  INSERT INTO orders (id, user_id, total_cents, status)
  VALUES ($1, $2, $3, 'CONFIRMED');

  INSERT INTO outbox_events (id, aggregate_id, event_type, payload)
  VALUES ($4, $1, 'ORDER_CONFIRMED', $5::jsonb);
COMMIT;

-- Consumer-side atomic claim (prevents TOCTOU race across ECS tasks)
INSERT INTO idempotency_keys (key, payload_hash, status, expires_at)
VALUES ($1, $2, 'IN_PROGRESS', NOW() + INTERVAL '30 days')
ON CONFLICT (key) DO NOTHING
RETURNING key;

# 2. Terraform SQS Source Queue + 14-Day DLQ Redrive Policy
resource "aws_sqs_queue" "orders_dlq" {
  name                      = "orders-events-dlq"
  message_retention_seconds = 1209600 # 14 days (exceeds source retention)
}

resource "aws_sqs_queue" "orders" {
  name                       = "orders-events"
  visibility_timeout_seconds = 180     # >= 6x max 30s worker runtime
  message_retention_seconds  = 345600  # 4 days
  redrive_policy = jsonencode({
    deadLetterTargetArn = aws_sqs_queue.orders_dlq.arn
    maxReceiveCount     = 5
  })
}

FIFO Deduplication Scope SQS FIFO's 5-minute MessageDeduplicationId only drops duplicate producer SendMessage calls. It does not prevent consumer-side duplicates caused by slow processing or worker crashes.
