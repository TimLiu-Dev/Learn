EC2 Deep Dive: AMIs, Graviton/ARM64, IMDSv2 & SSM Session Manager

Running modern workloads on Amazon EC2 is no longer about SSHing into mutable Ubuntu boxes and running apt-get by hand. A senior AWS engineer builds immutable Golden AMIs, cuts compute bills by ~20%+ on ARM64 AWS Graviton processors, defeats SSRF credential theft with IMDSv2, and eliminates SSH bastions entirely using AWS Systems Manager (SSM) Session Manager.

Your Android Bridge

Every Android engineer already ships for ARM64: your production APK/AAB splits native .so libraries into arm64-v8a vs x86_64 because ARM64 dominates mobile performance-per-watt. On AWS, Graviton (ARM64) brings that exact silicon shift to the data center — and shares the exact same JNI/native-binary compatibility trap if an x86_64 library sneaks in. Meanwhile, Golden AMIs work like a pre-compiled Android system image rather than downloading dependencies on first boot, IMDSv2 guards instance credentials like Android Keystore guards tokens against untrusted inputs, and SSM Session Manager replaces open TCP port 22 SSH bastions the way an authenticated adb shell debug bridge replaces exposing an unencrypted telnet port on a phone.

1. Graviton (ARM64) vs. x86_64: Silicon, Cost-Performance & Traps

For decades, cloud servers meant Intel or AMD x86_64. Today, AWS's custom 64-bit Arm Neoverse processors — Graviton2 (m6g/c6g/r6g), Graviton3 (m7g/c7g/r7g), and Graviton4 (r8g/m8g/c8g) — are the default cost-performance choice for general-purpose Linux, JVM/Kotlin, Go, Python, Node.js, and containerized microservices.

Two architectural facts explain why Graviton wins benchmarks and lowers bills:

  • ~20% lower On-Demand hourly rate: Comparing equivalent-generation Linux instances in us-east-1, an m7g.large (2 vCPU, 8 GiB RAM, Graviton3) runs around $0.0816/hr (~$59.57/mo) versus $0.1008/hr (~$73.58/mo) for m7i.large (Intel) — roughly 19% cheaper before Savings Plans, with up to 40% better price-performance on CPU-bound APIs.
  • No Simultaneous Multithreading (SMT / Hyper-Threading): On x86 instances, 2 vCPUs are typically 2 hardware threads sharing one physical core's execution pipelines and L1/L2 caches. On Graviton, 1 vCPU = 1 full physical core, eliminating sibling-thread noisy-neighbor contention under high tail concurrency.

Real Graviton Migration Traps

Moving a fleet from x86_64 to arm64 is trivial for pure bytecode/interpreted code (JVM, Go, Python, Node) until native machine code enters the picture:

  1. QEMU silent emulation cliff: If you deploy a single-arch linux/amd64 Docker image onto an ARM64 node with binfmt_misc/QEMU enabled, the service may actually boot — and suffer a 5× to 10× throughput collapse as every x86 instruction is translated in software. Always publish multi-arch OCI manifests via docker buildx build --platform linux/amd64,linux/arm64 and verify uname -m reports aarch64.
  2. JNI, C/C++ extensions & hardcoded CLI downloads: Just as an Android APK crashes with UnsatisfiedLinkError if arm64-v8a lacks a compiled .so, backend dependencies like grpc, sharp, sqlite3, bcrypt, or a UserData script running curl .../kubectl-amd64 will fail or segfault on Graviton.
  3. Nitro NVMe & ENA drivers: All Graviton instances run on the AWS Nitro System, which exposes EBS volumes as NVMe block devices (/dev/nvme0n1 instead of /dev/xvda) and requires the Elastic Network Adapter (ENA) driver. Old pre-Nitro x86 AMIs cannot be booted on Graviton.

2. Golden AMIs vs. Runtime UserData Bootstrapping

An Amazon Machine Image (AMI) packages the root EBS snapshot (OS + software), block device mappings, and architecture flag (x86_64 or arm64). When an Auto Scaling Group scales out during a traffic spike, you face a fundamental design split:

  • Mutable / UserData bootstrapping: Launch a bare base OS AMI and run a shell script via EC2 UserData (processed by cloud-init) to install Java, Node, Docker, the CloudWatch Agent, and your app artifact on every boot.
  • Immutable Golden AMI pipeline: Pre-bake OS security patches, CIS hardening, SSM Agent, CloudWatch Agent, runtime libraries, and base tooling into a versioned AMI using EC2 Image Builder or HashiCorp Packer in CI/CD. UserData shrinks to 5 lines that inject runtime environment tags or fetch config from SSM Parameter Store.
Four Production Rules for UserData & AMIs

1. Size limit: EC2 UserData is hard-capped at 16 KB (prior to base64 encoding; use gzip or pull scripts from S3 if larger). 2. Never store secrets in UserData: Anyone with ec2:DescribeInstanceAttribute or local access to IMDS can read UserData in plaintext — pass a KMS-encrypted Secrets Manager ARN or SSM parameter path instead. 3. First-boot only: By default, cloud-init executes UserData once per instance ID, not on stop/start reboots. 4. Encrypt AMI snapshots: Always enable EBS encryption with a KMS CMK so cross-account AMI sharing never leaks unencrypted root disks.

3. IMDSv2: Defeating SSRF & The Docker Hop-Limit Trap

Every EC2 instance reaches the Instance Metadata Service (IMDS) at the link-local IPv4 address http://169.254.169.254 (or IPv6 [fd00:ec2::254]) to discover its AZ, instance ID, and — critically — short-lived IAM credentials from its attached IAM Instance Profile.

Under legacy IMDSv1, any process or attacker who tricks your app into issuing an HTTP GET (via Server-Side Request Forgery / SSRF, an open HTTP proxy, or a leaky reverse proxy header) can immediately read /latest/meta-data/iam/security-credentials/<role-name> and exfiltrate valid AWS STS temporary keys.

According to the AWS EC2 Instance Metadata Service documentation, IMDSv2 defeats SSRF and open proxies with four defense-in-depth controls:

  1. Session-oriented PUT handshake: Clients must first send PUT /latest/api/token with header X-aws-ec2-metadata-token-ttl-seconds (1 to 21,600 seconds / 6 hours) to obtain a secret token, then supply X-aws-ec2-metadata-token: $TOKEN on every subsequent GET. Most SSRF vulnerabilities only allow GET requests without arbitrary custom headers.
  2. Rejects forwarded requests: IMDSv2 explicitly rejects any PUT /latest/api/token request containing an X-Forwarded-For header, blocking misconfigured Nginx/Envoy reverse proxies from minting tokens on behalf of external callers.
  3. Enforce HttpTokens = required: Leaving HttpTokens = optional allows IMDSv1 fallback, meaning an attacker simply skips the PUT step and still steals credentials via GET! Always enforce required via Launch Templates and an IAM/SCP guard rail checking ec2:MetadataHttpTokens.
  4. The Container Hop-Limit Trap (HttpPutResponseHopLimit): IMDSv2 enforces an IP Time-To-Live (TTL) on the token PUT response, defaulting to 1 hop. On a bare EC2 Linux host, host ↔ IMDS is 1 hop, so HopLimit = 1 works. Inside a Docker bridge container (docker0 / ECS bridge mode), packets traverse two L3 hops (container → host bridge → IMDS), causing the PUT response to drop before reaching the container! For Docker bridge workloads, set HttpPutResponseHopLimit = 2 (or use awsvpc / host networking where the container shares the ENI directly and HopLimit = 1 holds).

4. SSM Session Manager vs. SSH Bastions

Traditional cloud setups exposed a hardened "jump box" (SSH bastion) in a public subnet with TCP port 22 open, distributed static PEM keys across laptops, and hoped nobody leaked a private key or forgot to revoke access when an engineer left.

AWS Systems Manager (SSM) Session Manager flips the network direction and replaces static SSH keys with IAM:

  • Zero inbound ports: The amazon-ssm-agent running inside the EC2 instance initiates an outbound HTTPS (TCP 443) WebSocket connection to AWS SSM endpoints. Your EC2 Security Group requires zero inbound rules — no port 22, no public IP, and no bastion host to patch.
  • Private subnet reachability: Instances in completely air-gapped private subnets (no IGW, no NAT Gateway) connect to SSM through three VPC Interface Endpoints (Lesson 0022): com.amazonaws.<region>.ssm, ssmmessages, and ec2messages.
  • IAM-gated & fully audited: Access is authorized via IAM policies (ssm:StartSession, optionally scoped by resource tag aws:ResourceTag/Env), encrypted with KMS, recorded in CloudTrail, and streamed keystroke-by-keystroke to S3 or CloudWatch Logs. You can even tunnel local ports (e.g., RDS PostgreSQL port 5432) over SSM using AWS-StartPortForwardingSessionToRemoteHost.

5. Production IaC & Guardrails: Launch Template, SCP & SSM CLI

In production, you never rely on engineers remembering security flags in the EC2 Console. You bake Graviton + IMDSv2 + SSM directly into your Terraform Launch Template and enforce IMDSv2 organization-wide with an IAM/SCP guardrail: 

# 1. Terraform: Hardened Graviton3 Launch Template (No SSH, IMDSv2 Required, Encrypted gp3)
resource "aws_launch_template" "api_arm64" {
  name_prefix   = "orders-api-arm64-"
  image_id      = data.aws_ami.golden_al2023_arm64.id # Built via EC2 Image Builder
  instance_type = "m7g.large"                         # Graviton3 ARM64 (~20% cheaper than m7i)

  iam_instance_profile {
    arn = aws_iam_instance_profile.ec2_ssm_profile.arn # Attaches AmazonSSMManagedInstanceCore
  }

  vpc_security_group_ids = [aws_security_group.private_api.id] # Zero port 22 ingress rules!

  metadata_options {
    http_endpoint               = "enabled"
    http_tokens                 = "required" # Disables IMDSv1 completely
    http_put_response_hop_limit = 2          # Set 2 if running Docker bridge containers; 1 for host-only
  }

  block_device_mappings {
    device_name = "/dev/xvda"
    ebs {
      volume_size           = 30
      volume_type           = "gp3"
      encrypted             = true
      kms_key_id            = aws_kms_key.ebs_cmk.arn
      delete_on_termination = true
    }
  }
}
