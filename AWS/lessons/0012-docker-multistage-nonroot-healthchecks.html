Docker Multi-Stage Builds, Non-Root Security & Health Checks

A naive container ships a 950 MB compiler toolchain running as UID 0 (root) with a health probe that DDoSes your own database during failover. Learn how multi-stage builds mirror Android R8 release shrinking, why unprivileged USER and pinned image digests harden runtime blast radius, and how to separate liveness from readiness probes on AWS.

Your Android Bridge

In Android, your CI machine needs 2+ GB of Gradle, kotlinc, and the Android SDK to compile, yet R8 / ProGuard strips unused code and ships only a ~20 MB release APK/AAB to users. Moreover, Android OS isolates every app under its own unprivileged Linux UID—never root. In cloud containers (ECS Fargate, EKS, App Runner), a multi-stage Dockerfile is your R8 release step, distroless + non-root USER is your Android app sandbox, and readiness vs. liveness probes act like Activity lifecycle callbacks telling the load balancer when you are ready for traffic.

1. Multi-Stage Builds & Layer Caching (10x Smaller, Faster, Safer)

A single-stage Dockerfile leaves the compiler, package managers (apt, npm, gradle), source tree, and build caches inside the production image. On AWS ECS Fargate or EKS, pulling a bloated 950 MB image from Amazon ECR during an auto-scaling spike wastes tens of seconds per task—while bundling hundreds of unnecessary OS binaries with CVEs.

With a multi-stage build, Stage 1 (AS builder) compiles and tests your artifact using the full SDK, and Stage 2 starts from a minimal runtime base (such as Google's Distroless or a slim Alpine image) and runs COPY --from=builder to pull in only the compiled output:

  • JVM / Kotlin services: Drop from ~920 MB (gradle:8-jdk21) to ~195 MB (distroless/java21-debian12).
  • Node.js / TypeScript APIs: Drop from ~1.05 GB (node:20 + devDependencies) to ~140 MB (distroless/nodejs20-debian12).
  • Go / Rust binaries: Drop from ~850 MB to ~15–25 MB on gcr.io/distroless/static-debian12 or scratch.

Layer caching rule: Docker caches each instruction layer top-down. Always copy dependency manifests (package.json + package-lock.json, or build.gradle.kts + gradle/libs.versions.toml) and install dependencies before running COPY src/ .. Otherwise, every 1-line application edit invalidates the dependency layer and forces CI to re-download the internet. Always pair this with a strict .dockerignore excluding .git, node_modules, build/, .gradle, and local .env secrets.

Figure 1: Multi-stage builds discard compilers, source code, and shells—shipping only the runtime and compiled artifact, just as R8 strips unused code into a release APK.

2. Pinned Tags, Digests & Non-Root USER Security

Two silent security failures plague beginner Dockerfiles:

  1. Mutable Tags (:latest or untagged FROM node): Docker tags are mutable pointers. node:20-alpine today can silently pull a different OpenSSL or musl patch tomorrow, breaking reproducible builds or introducing an unvetted upstream change. Pin every stage—including builder—to an explicit version tag and, ideally, an immutable @sha256:<digest> (managed automatically by Dependabot or Renovate).
  2. Running as UID 0 (root): Unless you declare a non-root USER in your final stage, the container process runs as root. Note that USER does not carry across FROM boundaries—setting USER 10001 in Stage 1 leaves Stage 2 running as root unless you declare USER again in Stage 2! If an attacker exploits an application RCE (e.g., SSRF, template injection, or deserialization bug), running as non-root prevents writing to system binaries, binding raw sockets, or escalating against misconfigured host mounts.
Unprivileged Ports & Read-Only Filesystems

Non-root users cannot bind ports below 1024 without extra Linux capabilities (CAP_NET_BIND_SERVICE). Configure your container server to listen on an unprivileged port such as 8080 (the AWS ALB / ECS Target Group handles external TLS on 443 and forwards to 8080). In ECS/EKS, combine USER 10001:10001 with readonlyRootFilesystem: true and mount only /tmp if temporary scratch space is needed.

3. Health Checks: Liveness vs. Readiness vs. Startup

Cloud orchestrators need to know two completely different facts about your container, and mixing them up causes fleet-wide outages:

  • Readiness Probe (ALB Target Group check on ECS, readinessProbe on EKS): Asks "Should the load balancer send user traffic to this instance right now?" When a container boots, warms an in-memory cache, or receives SIGTERM to drain active requests during deployment, readiness flips to 503 Service Unavailable so the ALB stops sending new requests without killing the process.
  • Liveness Probe (Dockerfile HEALTHCHECK / ECS container healthCheck, or EKS livenessProbe): Asks "Is the process event-loop or thread pool permanently deadlocked and in need of a hard SIGKILL restart?"
  • Startup Probe (HEALTHCHECK --start-period=30s on Docker/ECS, startupProbe on EKS): Gives slow-booting runtimes (like JVM/Spring Boot taking 15–25s) grace time before liveness failures begin counting toward a restart.

The Cascading-Outage Trap: Never put a dependency check like SELECT 1 against RDS inside your liveness probe (or ECS container HEALTHCHECK). If RDS has a 10-second primary failover, every healthy API container simultaneously fails its liveness check, ECS/EKS kills and restarts your entire fleet at once, and the resulting boot + connection storm prevents RDS from recovering. Keep liveness checks strictly local (process responsive + HTTP 200 on /health/live).

Distroless Gotcha: Because distroless images remove /bin/sh and curl, HEALTHCHECK CMD curl -f ... fails inside distroless! In distroless containers, either invoke your runtime directly in exec form (e.g., HEALTHCHECK CMD ["node", "healthcheck.js"]) or rely on ECS ALB / Kubernetes HTTP kubelet probes (which make TCP/HTTP requests from outside the container without needing curl inside).

4. Production Code Example: Hardened Multi-Stage Dockerfile & Probes

Notice how every stage uses pinned tags + digests, dependencies are cached separately from src/, the final stage runs as non-root UID 10001, and CMD uses exec JSON-array form so Node receives SIGTERM directly as PID 1: 

# syntax=docker/dockerfile:1.7
# Stage 1: Builder (toolchain stays here, never shipped)
FROM node:20.18.0-bookworm-slim@sha256:6b2a1f4c... AS builder
WORKDIR /build

# 1. Cache dependency install independently of source code edits
COPY package.json package-lock.json ./
RUN npm ci

# 2. Copy source & compile TypeScript
COPY tsconfig.json ./
COPY src/ ./src/
RUN npm run build && npm prune --omit=dev

# Stage 2: Hardened Runtime
FROM node:20.18.0-alpine3.20@sha256:9c8a2d1e... AS runtime
ENV NODE_ENV=production
WORKDIR /app

# Create explicit unprivileged user/group (UID/GID 10001)
RUN addgroup -g 10001 -S appgroup && adduser -u 10001 -S appuser -G appgroup

# Copy ONLY compiled JS + prod dependencies with explicit ownership
COPY --from=builder --chown=10001:10001 /build/dist ./dist
COPY --from=builder --chown=10001:10001 /build/node_modules ./node_modules
COPY --from=builder --chown=10001:10001 /build/healthcheck.js ./healthcheck.js

USER 10001:10001
EXPOSE 8080

# Shallow local liveness probe using exec form (no /bin/sh wrapper)
HEALTHCHECK --interval=15s --timeout=3s --start-period=20s --retries=3 \
  CMD ["node", "healthcheck.js"]

# Exec form ensures Node is PID 1 and receives SIGTERM for graceful ALB draining
CMD ["node", "dist/server.js"]
// healthcheck.js — zero-dependency local probe (works without curl)
import http from "node:http";
const req = http.get("http://127.0.0.1:8080/health/live", { timeout: 2000 }, (res) => {
  process.exit(res.statusCode === 200 ? 0 : 1);
});
req.on("error", () => process.exit(1));

// server.js — separate /health/live (process alive) vs /health/ready (ALB draining)
let isShuttingDown = false;
process.on("SIGTERM", () => { isShuttingDown = true; /* drain in-flight sockets */ });

app.get("/health/live",  (_req, res) => res.status(200).json({ status: "alive" }));
app.get("/health/ready", (_req, res) => {
  if (isShuttingDown) return res.status(503).json({ status: "draining" });
  return res.status(200).json({ status: "ready" });
});

Distroless vs. Alpine Alpine uses musl libc rather than glibc. While tiny (~7 MB base), musl has subtle differences in DNS resolution and thread stack sizes that can bite JVM, Python native wheels, and Go Cgo binaries. Prefer glibc-based distroless when compatibility matters.
ECS vs. EKS Health Checks Amazon ECS honors Dockerfile HEALTHCHECK (or task-definition healthCheck) for container liveness alongside ALB Target Group checks for readiness. Kubernetes/EKS ignores Dockerfile HEALTHCHECK completely and uses livenessProbe, readinessProbe, and startupProbe.
PID 1 & Signal Handling Always use JSON exec form (CMD ["node", "server.js"]) rather than shell form (CMD node server.js). Shell form spawns /bin/sh -c as PID 1, which often swallows SIGTERM during ECS/EKS task draining and causes slow 30-second forced SIGKILL shutdowns.
