ACID Transactions, Isolation Levels, Optimistic Locking & Zero-Downtime Migrations

In Android Room, @Transaction protects a single-device SQLite file where only one writer runs at a time. On AWS RDS PostgreSQL, dozens of stateless API containers compete over pooled connections—turning subtle isolation defaults, long-held row locks, and careless ALTER TABLE statements into silent data corruption or full production outages.

Your Android Bridge

In Android Jetpack Room, annotating a DAO method with @Transaction wraps multiple queries inside SQLite's BEGIN IMMEDIATE ... COMMIT. Because SQLite allows only one active writer on the local device, you rarely see two concurrent transactions collide on different snapshots. In cloud PostgreSQL, Multi-Version Concurrency Control (MVCC) lets readers and writers run concurrently without blocking—which shifts the burden onto you to choose the right isolation level, detect stale writes with optimistic locking, and evolve schemas via expand-and-contract without queuing behind an ACCESS EXCLUSIVE lock.

1. ACID & PostgreSQL MVCC Isolation Levels

Every relational database promises ACID (Atomicity, Consistency, Isolation, Durability), yet most engineers assume Isolation automatically prevents concurrent race conditions. By default, PostgreSQL (and Amazon RDS / Aurora PostgreSQL) runs at READ COMMITTED—the weakest of PostgreSQL's three distinct isolation behaviors:

  • READ COMMITTED (PostgreSQL default): Each individual SQL statement sees a fresh snapshot taken at the start of that statement. Two identical SELECT queries inside the same BEGIN ... COMMIT block can return different numbers if another transaction commits in between (a non-repeatable read). Read-compute-write in application memory causes lost updates.
  • REPEATABLE READ (Snapshot Isolation): One frozen snapshot is taken at the first non-control statement of the transaction. If two concurrent transactions try to update or delete the same row, the second waits for the first; if the first commits, PostgreSQL aborts the second with SQLSTATE 40001 (could not serialize access due to concurrent update). However, Snapshot Isolation still permits write skew when two transactions read overlapping rows and update disjoint rows.
  • SERIALIZABLE (Serializable Snapshot Isolation / SSI): Tracks predicate read locks (SIREAD) across transactions to detect dependency cycles even across disjoint rows. If two concurrent on-call doctors both check SELECT count(*) > 1 and each sets only their own row to active = false, SSI aborts one with SQLSTATE 40001 so your invariant holds. You pay slightly higher memory/CPU tracking overhead and must implement bounded retries with jitter.
Figure 1: Under READ COMMITTED, read-modify-write in app code loses updates unless guarded by an atomic WHERE version = $expected check or pessimistic row locking.

2. Optimistic Locking vs. Pessimistic Locking (FOR UPDATE)

Two concurrency patterns prevent lost updates in production backends, and picking the wrong one directly impacts connection pool availability:

  • Pessimistic Locking (SELECT ... FOR UPDATE): Acquires an exclusive row-level lock immediately on read and holds it until COMMIT or ROLLBACK. Ideal for high-contention single rows (e.g., decrementing the last 5 concert tickets) when the entire transaction finishes inside the database in < 5 ms.
  • Optimistic Concurrency Control (version CAS): Reads the row with no lock (balance_cents = 10000, version = 4), performs validation or user confirmation, and executes UPDATE accounts SET balance_cents = $1, version = version + 1 WHERE id = $2 AND version = $3. If rowCount === 0, someone else modified the row first—return 409 Conflict or retry from a fresh read.
Never Hold DB Transactions Open Across Network Calls

A classic outage occurs when a service opens a PostgreSQL transaction, executes SELECT ... FOR UPDATE, and then calls Stripe or a fraud API (500 ms–5,000 ms). Every waiting request pins both a row lock and a precious database connection from your RDS Proxy / PgBouncer pool. Move external HTTP calls outside the transaction, track state with an idempotency key, and use optimistic version checks when committing the result.

3. Zero-Downtime Migrations: The Expand-and-Contract Pattern

In Room on Android, a schema migration runs locally while the app is upgrading and no old version of your code is running. In AWS ECS or Lambda, old code (v1) and new code (v2) run side-by-side during rolling deploys and blue/green cutovers.

Even worse, PostgreSQL DDL commands like ALTER TABLE ... RENAME COLUMN or adding an unguarded NOT NULL constraint acquire an ACCESS EXCLUSIVE lock—which conflicts with every lock mode, including SELECT. If a 30-second reporting query holds an ACCESS SHARE lock on payments, your waiting ALTER TABLE stalls behind it and blocks every subsequent SELECT and INSERT in the lock queue, exhausting your connection pool within seconds.

Figure 2: Expand-and-contract decouples schema changes from application deployments so v1 and v2 containers remain compatible at every step.

Follow four non-negotiable rules for RDS PostgreSQL migrations:

  1. Bound DDL waits: Always run SET lock_timeout = '2s'; so a blocked migration aborts cleanly instead of queuing production traffic behind an ACCESS EXCLUSIVE request.
  2. Build indexes online: Use CREATE INDEX CONCURRENTLY (outside a transaction block). Standard CREATE INDEX takes a SHARE lock that blocks all INSERT/UPDATE/DELETE writes for the entire table scan.
  3. Validate constraints without blocking writes: Add ALTER TABLE ... ADD CONSTRAINT chk_not_null CHECK (amount_cents IS NOT NULL) NOT VALID; (metadata-only instant lock), then run VALIDATE CONSTRAINT chk_not_null; which uses SHARE UPDATE EXCLUSIVE so normal reads and writes continue uninterrupted. On PostgreSQL 12+, SET NOT NULL then completes instantly by reading the validated check constraint.
  4. Never rename or drop columns with active readers: Expand with a new nullable column, dual-write, backfill in small batches (1,000–5,000 rows per commit), switch reads to the new column, and contract only after zero old application containers remain.
