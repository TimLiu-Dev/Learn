CloudWatch Logs Insights, Alarms, X-Ray/ADOT Tracing & Operational Runbooks

When an incident hits production at 2:00 AM, senior engineers do not SSH into containers to tail text files. They query structured JSON logs with CloudWatch Logs Insights, trust composite alarms tuned against missing-data false positives, isolate tail latency using distributed X-Ray/ADOT flame graphs, and execute pre-written runbooks.

Your Android Bridge

In Android Studio, you filter one device's Logcat stream by tag and inspect CPU/network flame charts in Android Profiler or Perfetto. In AWS, millions of concurrent requests interleave across API Gateway, Lambda/ECS, DynamoDB, and SQS. CloudWatch Logs Insights is your distributed, SQL-like Logcat; Composite Alarms replace noisy single-threshold alerts; AWS X-Ray / ADOT is your cross-service Profiler tied together by trace headers; and Runbooks + Synthetics Canaries ensure the on-call engineer mitigates failures in minutes rather than guessing under pressure.

1. Structured Logging, EMF & CloudWatch Logs Insights

Plain-text console.log strings ("Order 991 failed in 420ms") break down at cloud scale because regex parsing is slow and fragile. Senior AWS services emit single-line JSON containing stable correlation fields: timestamp, level, service, route, statusCode, durationMs, requestId, and traceId.

According to the CloudWatch Logs Insights query syntax, CloudWatch automatically discovers JSON fields in log events, letting you run interactive aggregations in seconds:

  • fields & filter: Project only needed columns and prune early (e.g., filter statusCode >= 500).
  • stats pct(durationMs, 99) as p99: Compute p50/p95/p99 latency per route instead of misleading averages.
  • bin(1m): Bucket counts and percentiles into time series to pinpoint the exact deployment minute a regression started.
  • Cost & Speed Trap: Logs Insights bills per GB of log data scanned. Always narrow your time window, query specific log groups (never wildcard every service), and avoid dumping multi-kilobyte request/response bodies into standard logs.
Embedded Metric Format (EMF) vs. Synchronous PutMetricData

Never call the CloudWatch PutMetricData API synchronously inside an API request path—it adds network latency and hits API throttling quotas during traffic spikes. Instead, print CloudWatch Embedded Metric Format (EMF) JSON to stdout. The Lambda runtime or CloudWatch Agent extracts custom metrics asynchronously with zero request latency, while retaining full-resolution JSON logs. Also keep metric dimensions low-cardinality (e.g., route and tenantTier, never userId or orderId), because each unique dimension combination creates a separate billable custom metric.

2. CloudWatch Alarms, M-of-N Evaluation & Composite Alarms

Naive alarms trigger false pages whenever one container restarts or traffic drops overnight. Production alarming relies on four tuning levers documented in the CloudWatch Alarms configuration guide:

  1. Percentile Statistics (p99 / p95) over Average: An endpoint serving 99% of requests in 40 ms and 1% in 8,000 ms reports an Average of ~120 ms—hiding a severe tail-latency outage.
  2. M-of-N Evaluation (DatapointsToAlarm / EvaluationPeriods): Requiring 3 out of 5 consecutive 1-minute periods absorbs transient 60-second blips (such as rolling ECS task replacements) while still paging within 3 minutes of a sustained outage.
  3. TreatMissingData Semantics: Sparse metrics (like Lambda Errors or ALB HTTPCode_Target_5XX_Count) emit nothing when zero errors occur. Setting notBreaching treats silent minutes as 0 errors; leaving missing can stall in INSUFFICIENT_DATA, while breaching will page you at 3:00 AM simply because traffic stopped. Conversely, use breaching for heartbeat / Synthetics canary metrics where silence means the probe died.
  4. Composite Alarms: Combine multiple underlying metric alarms using boolean expressions (ALARM(High5xxRate) AND ALARM(HighRequestVolume)) via CloudWatch Composite Alarms. That stops an isolated single-user retry loop (100% error rate on 2 requests/min) from waking the primary on-call engineer.

3. Distributed Tracing: X-Ray, ADOT & Context Propagation

When an Android request takes 1,450 ms across five microservices, logs alone only show isolated timestamps. Distributed tracing links every hop into a single causal tree using a trace header—either AWS X-Ray's X-Amzn-Trace-Id (e.g., Root=1-6736a1b2-...;Parent=53995c3f...;Sampled=1) or the W3C standard traceparent supported by AWS Distro for OpenTelemetry (ADOT).

Figure 1: Inclusive vs. exclusive time in an AWS X-Ray trace. Even though Lambda Checkout reports 1,350 ms total duration, 1,230 ms belongs to child subsegments; DynamoDB's 1,030 ms exclusive self-time is the true bottleneck.

Two architectural rules govern distributed tracing in production:

  • Inclusive vs. Exclusive (Self) Time: A parent segment's duration includes its own CPU work plus every synchronous child subsegment. Always rank bottlenecks by exclusive time (segment.durationMs - sum(directChild.durationMs)) so you fix the slow DynamoDB query rather than blindly bumping Lambda memory.
  • Sampling & Async Propagation: X-Ray's default sampling rule records 1 request per second plus 5% of additional requests to control cost. Use ADOT Collector tail-sampling (or explicit error/slow-path rules) to capture 100% of 5xx errors, and propagate trace headers into SQS message attributes or EventBridge metadata so asynchronous consumers attach as linked spans.

4. Production Examples: Logs Insights, CDK Composite Alarm & ADOT

Below is a real operational pair: (1) a CloudWatch Logs Insights query that surfaces slow p99 endpoints alongside sample traceIds for immediate X-Ray lookup, and (2) an AWS CDK TypeScript definition combining an error-rate alarm and a minimum-traffic gate into one composite pager alarm with a direct runbook link. 

# 1. CloudWatch Logs Insights — Find slow p99 routes & grab a sample traceId for X-Ray
fields @timestamp, route, statusCode, durationMs, traceId
| filter service = "checkout-api" and statusCode >= 200
| stats count() as reqs,
        pct(durationMs, 95) as p95Ms,
        pct(durationMs, 99) as p99Ms,
        earliest(traceId) as sampleTrace
  by route, bin(5m)
| filter p99Ms > 800
| sort p99Ms desc
| limit 20
// 2. AWS CDK (TypeScript) — Composite Alarm eliminating 3 AM low-traffic false pages
import * as cw from "aws-cdk-lib/aws-cloudwatch";
import * as actions from "aws-cdk-lib/aws-cloudwatch-actions";
import { Duration } from "aws-cdk-lib";

const high5xxAlarm = new cw.Alarm(this, "CheckoutHigh5xx", {
  metric: apiErrorRateMetric, // 5xx / TotalRequests * 100
  threshold: 2.0,
  comparisonOperator: cw.ComparisonOperator.GREATER_THAN_THRESHOLD,
  evaluationPeriods: 5,
  datapointsToAlarm: 3, // 3-of-5 M-of-N dampens single-minute spikes
  treatMissingData: cw.TreatMissingData.NOT_BREACHING,
});

const meaningfulTrafficAlarm = new cw.Alarm(this, "CheckoutActiveTraffic", {
  metric: apiRequestCountMetric.with({ statistic: "Sum", period: Duration.minutes(1) }),
  threshold: 50,
  comparisonOperator: cw.ComparisonOperator.GREATER_THAN_OR_EQUAL_TO_THRESHOLD,
  evaluationPeriods: 5,
  datapointsToAlarm: 3,
  treatMissingData: cw.TreatMissingData.NOT_BREACHING,
});

const pagerComposite = new cw.CompositeAlarm(this, "CheckoutUserImpactPager", {
  compositeAlarmName: "PROD-Checkout-UserImpact-Sev2",
  alarmDescription: "Runbook: https://internal.example.com/runbooks/checkout-5xx-sev2",
  alarmRule: cw.AlarmRule.allOf(
    cw.AlarmRule.fromAlarm(high5xxAlarm, cw.AlarmState.ALARM),
    cw.AlarmRule.fromAlarm(meaningfulTrafficAlarm, cw.AlarmState.ALARM)
  ),
});
pagerComposite.addAlarmAction(new actions.SnsAction(onCallPagerTopic));

5. Actionable On-Call Runbooks & CloudWatch Synthetics

An alarm without a runbook is just noise. Following the Amazon Builders' Library guidance on operational visibility, every paging composite alarm must embed a direct URL to a version-controlled runbook containing four sections:

Runbook Section Required Operational Content Anti-Pattern to Avoid
1. Impact & Severity User-facing symptom (e.g., Android checkout fails with 503), SLO burn rate, and customer communication threshold. Vague CPU/memory metrics with no explanation of user impact.
2. Triage Queries Copy-paste Logs Insights query, CloudWatch dashboard deep-link, and X-Ray service map filter. Forcing a sleepy engineer to recall log group names and JSON field keys.
3. Safe Mitigations Pre-approved levers: CodeDeploy rollback, AppConfig feature flag off, Route 53 weight shift, or ASG scale-out. Ad-hoc database edits or unreviewed manual EC2/container mutations.
4. Verify & Escalate Exact recovery criteria (e.g., canary passes 3 consecutive runs + p99 < 400 ms) and secondary escalation path. Closing an incident before synthetic probes and error budgets stabilize.

Pair real-user metrics with CloudWatch Synthetics Canaries (scheduled Node.js/Python scripts hitting critical login and checkout paths every 1–5 minutes). Because canaries run even at 4:00 AM with zero organic mobile users, set their alarm TreatMissingData to breaching so a broken deployment or expired TLS cert is caught before morning commuters open the app.
