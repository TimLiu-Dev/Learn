Designing Production Multi-AZ VPCs: Subnets, Route Tables, IGW & NAT Gateways

In Lesson 0002 you mastered CIDR bitmasks and longest-prefix matching. Now you will assemble those primitives into a resilient, multi-Availability-Zone Amazon VPC—separating ingress, compute, and databases across public, private, and isolated tiers while avoiding single-AZ NAT outages and silent cross-AZ data transfer taxes.

Your Android Bridge

Compare your home Wi-Fi router and your mobile carrier's NAT (CGNAT) to an AWS VPC. If you configure port forwarding and a public IP on your router, external traffic can reach a home server directly (a Public Subnet backed by an Internet Gateway). On 5G behind carrier NAT, your Android phone can open outbound HTTPS sockets via OkHttp, yet random internet hosts cannot initiate inbound TCP connections to your phone's 10.x IP (a Private Subnet behind a NAT Gateway). Finally, a smart-home VLAN with no default gateway at all can only talk locally on your LAN (an Isolated Data Subnet).

1. The Three Production Subnet Tiers & CIDR Sizing

An Amazon VPC spans an entire AWS Region (e.g., us-east-1) and typically claims a non-overlapping RFC 1918 /16 block such as 10.20.0.0/16 (65,536 addresses). Because AWS subnets are bound to a single Availability Zone, high availability requires mirroring your subnet tiers across at least two (ideally three) AZs.

According to the AWS VPC Subnet Architecture guide, a subnet's tier is determined entirely by its associated Route Table—never by its name tag:

Tier Typical Mask Default Route (0.0.0.0/0) Production Workloads
Public /24 (251 IPs) 0.0.0.0/0 → igw-xxxx Application Load Balancers, Network Load Balancers, NAT Gateways. Never run application containers or databases here.
Private /22 (1,019 IPs) 0.0.0.0/0 → nat-az (same AZ) ECS Fargate tasks, EKS pods, EC2 Auto Scaling groups, VPC-attached Lambda ENIs that call external APIs (Stripe, FCM, APNs).
Isolated /24 (251 IPs) None (local + VPC endpoints only) RDS PostgreSQL, Aurora, ElastiCache Redis, MSK Kafka—zero internet egress path even if compromised.

Notice the asymmetric sizing: private compute tiers exhaust IPs fastest (especially EKS pods with VPC CNI or rolling blue/green ECS deployments), so allocating /22 or /21 blocks to private subnets while keeping public and isolated subnets at /24 prevents premature IP exhaustion. Leave half your /16 unallocated for future tiers or secondary CIDR expansions.

2. IGW vs. NAT Gateway: Wire Mechanics & Multi-AZ HA

The Internet Gateway (IGW) is a horizontally scaled, redundant, regional AWS construct—it is never a single-AZ bottleneck and incurs zero hourly cost. On the wire, an IGW performs stateless 1:1 NAT between an instance's private IP and its assigned public IPv4 (or Elastic IP). Two crucial rules trip up engineers:

  • No public IP, no IGW egress: Placing an EC2 instance without a public IPv4 address in a public subnet with 0.0.0.0/0 → igw-xxxx causes every outbound internet packet to be silently dropped at the IGW, because the IGW has no public source address to map.
  • IGW works bi-directionally: Once a public IPv4 is mapped and security groups allow it, both inbound and outbound flows traverse the IGW.

By contrast, an AWS NAT Gateway is a zonal, stateful SNAT appliance that lives inside a specific public subnet in one AZ, binds to an Elastic IP, and auto-scales from 5 Gbps up to 100 Gbps (supporting ~55,000 simultaneous connections per destination IP/port tuple per Elastic IP, expandable up to 8 EIPs).

Figure 1: Each AZ pairs its own private route table with a local NAT Gateway inside that AZ's public subnet, isolating AZ failures and avoiding cross-AZ egress charges.
Three Cost & Reliability Traps in NAT Gateway Design

1. Single-AZ NAT SPOF: Deploying one NAT Gateway in us-east-1a ($32.40/mo) and pointing us-east-1b private subnets to it saves $32/month—but destroys AZ fault isolation and adds $0.02/GB cross-AZ transfer ($0.01 out + $0.01 in) on top of the $0.045/GB NAT processing fee.
2. NAT in a Private Subnet: A NAT Gateway must sit in a public subnet with 0.0.0.0/0 → igw. Putting a NAT Gateway inside a private subnet creates a routing blackhole.
3. Missing Gateway Endpoints: S3 and DynamoDB have public endpoints. Without free Gateway VPC Endpoints in your private route tables, S3 uploads/downloads traverse your NAT Gateway at $0.045/GB.

3. Production Code Example: Multi-AZ VPC in AWS CDK (TypeScript)

In production Infrastructure as Code, explicitly declare subnet masks, per-AZ NAT Gateways (natGateways: 2 or 3), and free Gateway VPC Endpoints so S3 and DynamoDB never touch NAT billing: 

import * as ec2 from "aws-cdk-lib/aws-ec2";

// Production 3-Tier, 2-AZ VPC with Per-AZ NAT Gateways & Free Gateway Endpoints
const vpc = new ec2.Vpc(this, "ProdVpc", {
  ipAddresses: ec2.IpAddresses.cidr("10.20.0.0/16"),
  maxAzs: 2,
  natGateways: 2, // CRITICAL: 1 NAT Gateway per AZ eliminates cross-AZ SPOF & $0.02/GB tax
  subnetConfiguration: [
    {
      name: "PublicIngress",
      subnetType: ec2.SubnetType.PUBLIC,
      cidrMask: 24, // 251 usable IPs per AZ for ALBs & NAT Gateways
    },
    {
      name: "PrivateCompute",
      subnetType: ec2.SubnetType.PRIVATE_WITH_EGRESS,
      cidrMask: 22, // 1,019 usable IPs per AZ for ECS/EKS & Lambda ENIs
    },
    {
      name: "IsolatedData",
      subnetType: ec2.SubnetType.PRIVATE_ISOLATED,
      cidrMask: 24, // 251 usable IPs per AZ; local routes only (RDS/Redis)
    },
  ],
  gatewayEndpoints: {
    S3: { service: ec2.GatewayVpcEndpointAwsService.S3 },
    DynamoDB: { service: ec2.GatewayVpcEndpointAwsService.DYNAMODB },
  },
});
