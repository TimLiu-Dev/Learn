API Gateway (HTTP API vs REST API): Authorizers, Throttling & ALB Tradeoffs

Every Retrofit baseUrl in your Android app terminates at an AWS Layer-7 front door. Choosing blindly between API Gateway HTTP API, REST API, and an Application Load Balancer (ALB) can inflate your monthly bill by 10×, strip away AWS WAF protection, or trigger mysterious 403 and 429 failures under mobile traffic bursts.

Your Android Bridge

In Android, Retrofit defines your HTTP routes while an OkHttp Interceptor attaches Authorization: Bearer <jwt> and an OkHttp Authenticator refreshes expired tokens on HTTP 401. On AWS, API Gateway or an ALB sits directly on the receiving end of that baseUrl: validating JWT signatures before your Lambda or ECS task even wakes up, enforcing token-bucket rate limits (HTTP 429), and metering every request or load-balancer capacity unit.

1. HTTP API vs. REST API vs. ALB: Capabilities, Latency & Cost

AWS offers three primary Layer-7 HTTP ingress services. Although they all accept HTTPS from OkHttpClient and forward requests to compute targets, they sit at completely different points on the pay-per-request vs. baseline-hourly curve and offer sharply different edge features (see Choosing between HTTP APIs and REST APIs).

The Cost Crossover Math: At low or spiky mobile traffic (say 2M requests/month at 16 KB each), HTTP API costs $2.00/mo while an ALB starts at $16.43/mo + LCUs (~$22/mo total). Flip that to sustained high volume (150M requests/month, ~58 RPS average): HTTP API climbs to $150/mo and REST API hits $525/mo, whereas an ALB handling 4 LCUs/hr costs roughly $16.425 + $23.36 = $39.78/mo—over 13× cheaper than REST API.

2. Authorizers: JWT Validation vs. Lambda Authorizer Caching Traps

Push authentication to the gateway whenever possible so unauthenticated traffic is rejected before burning backend CPU or Lambda concurrency. Each authorizer mechanism has distinct cost and failure characteristics (HTTP API JWT Authorizers):

  • Native JWT Authorizer (HTTP API only): API Gateway automatically fetches your IdP's JWKS public keys via issuer/.well-known/openid-configuration, verifies the cryptographic signature (RS256/ES256), checks expiration (exp), issuer (iss), audience (aud), and optional OAuth scopes—at $0 extra cost and zero Lambda cold starts.
  • Cognito User Pools Authorizer (REST API only): Validates Cognito tokens natively on REST APIs, including Cognito Access Tokens that lack an aud claim.
  • Lambda Authorizer (HTTP & REST): Invokes a custom Lambda function when you need opaque tokens, database/Redis revocation checks, or custom HMAC headers. To avoid paying a Lambda invocation on every API call, API Gateway caches the authorizer's decision for up to 3,600 seconds (default 300s), keyed by the identity source (usually $request.header.Authorization).
Two Production Authorizer Traps That Break Mobile Apps

Trap 1 — The REST API Cached methodArn 403 Bug: When a REST API Lambda Authorizer caches an IAM Allow policy using Resource: event.methodArn (e.g., .../prod/GET/orders) keyed on the Bearer token, the first call to GET /orders succeeds and populates the 300-second cache. When the Android user taps "Place Order" (POST /orders) 2 seconds later with the same JWT, API Gateway reads the cached policy, sees only GET /orders allowed, and immediately returns HTTP 403 Forbidden without even calling your Lambda! Fix: Return a wildcard stage/method ARN (arn:aws:execute-api:region:acct:apiId/stage/*/*) and enforce fine-grained RBAC in your backend, or use HTTP API's Simple boolean response ({ isAuthorized: true, context: {...} }).

Trap 2 — Cognito Access Token vs. HTTP API JWT Authorizer: Cognito ID tokens contain an aud claim matching your App Client ID, whereas Cognito Access tokens use client_id instead of aud. Pointing an HTTP API JWT Authorizer (which strictly enforces aud) at a Cognito Access Token fails every request with 401 Unauthorized unless you configure a Lambda authorizer or validate ID tokens/scopes appropriately.

3. Token-Bucket Throttling, Usage Plans & Mobile Retries

To protect downstream databases and prevent runaway bills during client retry storms, API Gateway enforces rate limiting using a token bucket algorithm (Throttle API requests for better throughput).

Think of a bucket that holds at most burstLimit tokens and refills continuously at rateLimit tokens per second:

  1. Each incoming HTTP request attempts to take 1 token from the bucket.
  2. If tokens ≥ 1, the request proceeds to your Lambda/ALB/ECS backend and decrements the bucket by 1.
  3. If tokens < 1, API Gateway does not queue the request—it immediately rejects it at the edge with HTTP 429 Too Many Requests.

API Gateway evaluates limits hierarchically from broadest to narrowest: Account-level regional limit (default 10,000 RPS steady-state and 5,000 concurrent burst shared across every API in your account/region) → Stage/Route throttling → REST API Usage Plans & API Keys (per-client rate/burst plus daily or monthly request quotas).

Notice a subtle consequence when burstLimit < rateLimit: suppose a stage sets rateLimit = 500 RPS and burstLimit = 100. If 250 Android devices fire simultaneously at the exact same millisecond after a push notification, only 100 requests fit in the bucket at that instant; the remaining 150 receive HTTP 429 even though 250 < 500! Smoothly spaced traffic at 500 RPS succeeds, while spiky traffic hits the burst ceiling.

4. Production Code: Terraform HTTP API & Android OkHttp 429 Handling

Below is a minimal production Terraform setup for an HTTP API with a native JWT Authorizer and stage throttling, paired with an Android OkHttp interceptor that respects 429 backoff with jitter instead of amplifying a spike: 

# 1. Terraform: API Gateway HTTP API + Cognito/OIDC JWT Authorizer + Stage Throttling
resource "aws_apigatewayv2_api" "mobile" {
  name          = "mobile-orders-http-api"
  protocol_type = "HTTP"
}

resource "aws_apigatewayv2_authorizer" "jwt" {
  api_id           = aws_apigatewayv2_api.mobile.id
  authorizer_type  = "JWT"
  identity_sources = ["$request.header.Authorization"]
  name             = "oidc-jwt-auth"
  jwt_configuration {
    audience = [var.mobile_app_client_id]
    issuer   = "https://cognito-idp.us-east-1.amazonaws.com/${var.user_pool_id}"
  }
}

resource "aws_apigatewayv2_stage" "prod" {
  api_id      = aws_apigatewayv2_api.mobile.id
  name        = "prod"
  auto_deploy = true
  default_route_settings {
    throttling_burst_limit = 500   # Max simultaneous token capacity
    throttling_rate_limit  = 1000  # Steady-state tokens refilled per second
  }
}
// 2. Android (Kotlin / OkHttp): Honor HTTP 429 with Retry-After or Full Jitter Backoff
class RateLimitRetryInterceptor(private val maxRetries: Int = 3) : Interceptor {
  override fun intercept(chain: Interceptor.Chain): Response {
    val request = chain.request()
    var response = chain.proceed(request)
    var attempt = 0
    while (response.code == 429 && attempt < maxRetries) {
      response.close()
      val retryAfterSec = response.header("Retry-After")?.toLongOrNull()
      val backoffMs = if (retryAfterSec != null) {
        retryAfterSec * 1000L
      } else {
        val capMs = minOf(8000L, 250L * (1L shl attempt))
        kotlin.random.Random.nextLong(0L, capMs + 1) // Full jitter prevents synchronized waves
      }
      Thread.sleep(backoffMs)
      attempt++
      response = chain.proceed(request)
    }
    return response
  }
}
