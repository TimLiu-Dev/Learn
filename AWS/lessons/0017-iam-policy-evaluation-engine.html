IAM Policy Evaluation Engine: Explicit Deny, Boundaries & Conditions

Every AWS API call—whether from an Android backend on ECS, a Lambda function, or your own CLI—is statelessly evaluated by the IAM decision engine before a single byte of data moves. Understanding how default deny, explicit deny overrides, identity vs. resource policies, permissions boundaries, and condition keys combine prevents both silent outages and catastrophic privilege escalation.

Your Android Bridge

In Android, dangerous permissions (like CAMERA or ACCESS_FINE_LOCATION) start denied by default: calling ContextCompat.checkSelfPermission() returns PERMISSION_DENIED until explicitly granted, and no SDK library inside your APK can grant itself a permission absent from AndroidManifest.xml. Meanwhile, an exported ContentProvider can enforce its own component-level permission check on top of the caller's grants. AWS IAM scales this exact zero-trust model to cloud APIs: Implicit Deny is the baseline, an Explicit Deny acts like an OS-level revocation that overrides every grant, Permissions Boundaries act like the manifest ceiling that caps delegated roles, and Resource Policies act like the provider's own access gate.

1. Implicit Deny, Explicit Deny & the Evaluation Funnel

Every request arriving at an AWS endpoint is cryptographically signed with SigV4, carrying a Principal (who is calling), an Action (such as s3:PutObject), a Resource (an ARN), and a bag of Request Context attributes (source IP, VPC endpoint ID, TLS status, tags, MFA state).

According to the AWS IAM Policy Evaluation Logic specification, the engine initializes every request at Implicit Deny and walks a strict deterministic funnel across all applicable policies:

  1. Explicit Deny Check (Global Circuit Breaker): The engine inspects every matching policy attached to the request—identity-based policies, resource-based policies, permissions boundaries, STS session policies, and AWS Organizations SCPs/RCPs. If any single statement has "Effect": "Deny" and its Action, Resource, and Condition all match, evaluation stops immediately with Explicit Deny. No Allow anywhere in AWS can override an explicit Deny.
  2. Organization Guardrails (SCPs & RCPs): If the account belongs to AWS Organizations, applicable Service Control Policies (SCPs) and Resource Control Policies (RCPs) must explicitly allow the action (covered in depth in Lesson 0019).
  3. Permissions Boundary & Session Policy Caps: If a Permissions Boundary is attached to the IAM user or role—or a Session Policy was passed during sts:AssumeRole—it defines a hard ceiling. An identity-based Allow only counts if the boundary (and session policy) also contains a matching Allow.
  4. Identity-Based & Resource-Based Allow Evaluation: Within the same account, an Allow from an identity policy (within its boundary) OR a direct Allow in a resource-based policy permits the call (with notable exceptions for KMS key policies and IAM role trust policies). Across accounts, BOTH the caller's identity side and the target resource policy must allow the request.
  5. Fallback to Implicit Deny: If no explicit Deny fired and the required Allow path was not satisfied, the request terminates as an Implicit Deny (typically surfaced as HTTP 403 AccessDenied).
Figure 1: Explicit Deny short-circuits all layers immediately. Without an explicit Deny, Permissions Boundaries intersect (∩) with Identity policies, while Cross-Account requests require an Allow from both accounts.

Keep real IAM service quotas in mind when designing production policies: a customer-managed policy is capped at 6,144 characters (excluding whitespace), an inline policy on an IAM role is capped at 10,240 characters (2,048 for IAM users, 5,120 for groups), and an IAM role defaults to at most 10 attached managed policies (adjustable up to 20). Pushing fine-grained authorization into too many tiny managed policies hits that 10-policy ceiling surprisingly fast.

2. Identity vs. Resource Policies, Boundaries & Condition Keys

Senior engineers distinguish four policy mechanisms by who they attach to and whether they grant or only bound permissions:

  • Identity-Based Policies (Grant): Attached to IAM Users, Groups, or Roles. They specify Action and Resource, and omit Principal (because the principal is implicitly the attached identity). Multiple identity policies on one role combine as a union (OR).
  • Resource-Based Policies (Grant + Cross-Account Gate): Attached directly to resources like S3 buckets, SQS queues, SNS topics, KMS keys, and IAM role trust policies. They must include a Principal element. Cross-account access is impossible without a matching Allow on both the caller's identity policy and the target's resource policy.
  • Permissions Boundaries (Cap Only — Never Grant): Attached to an IAM User or Role to set the maximum permissions ceiling that identity-based policies can grant to that entity (Effective = Identity ∩ Boundary). According to the IAM Permissions Boundaries documentation, a boundary alone grants zero permissions—if you attach an AdministratorAccess boundary to a role with no identity policy, the role can do nothing.
  • Condition Keys (Zero-Trust Context): Every statement can carry a Condition block comparing context keys against expected values using operators like StringEquals, StringNotEquals, StringLike (wildcards * and ?), IpAddress, and Bool. Multiple operators and multiple keys inside one Condition block combine with AND logic, while multiple values in a single key's array combine with OR logic.
Two Classic Production IAM Traps

1. The Delegated Role Privilege-Escalation Trap: If you grant a developer iam:CreateRole and iam:AttachRolePolicy without enforcing Condition: { "StringEquals": { "iam:PermissionsBoundary": "arn:aws:iam::111122223333:policy/AppBoundary" } }, that developer can create a brand-new role, attach AdministratorAccess, call sts:AssumeRole, and take over the entire AWS account.

2. The Deny + StringNotEquals Missing-Key Trap: Writing an S3 bucket policy that says "Deny everything if StringNotEquals: { "aws:SourceVpce": "vpce-0abc123" }" will evaluate to true (triggering Deny) when an AWS service like CloudTrail or Athena accesses the bucket without setting aws:SourceVpce at all—because undefined !== "vpce-0abc123"! Always guard negative Deny conditions with Bool: { "aws:PrincipalIsAWSService": "false" } or ...IfExists operators when AWS services must still reach the resource.

3. Code Example: Guardrail Boundary & TLS-Only S3 Policy

Notice how production IAM JSON pairs delegated Allow statements with explicit Deny guardrails so engineers can self-serve Lambda/ECS roles without ever escaping their sandbox: 

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowTeamToCreateBoundedAppRoles",
      "Effect": "Allow",
      "Action": [
        "iam:CreateRole",
        "iam:AttachRolePolicy",
        "iam:PutRolePermissionsBoundary"
      ],
      "Resource": "arn:aws:iam::111122223333:role/app-*",
      "Condition": {
        "StringEquals": {
          "iam:PermissionsBoundary": "arn:aws:iam::111122223333:policy/AppDeveloperBoundary"
        }
      }
    },
    {
      "Sid": "DenyTamperingWithTheBoundaryItself",
      "Effect": "Deny",
      "Action": [
        "iam:DeleteRolePermissionsBoundary",
        "iam:DeletePolicy",
        "iam:CreatePolicyVersion"
      ],
      "Resource": [
        "arn:aws:iam::111122223333:policy/AppDeveloperBoundary",
        "arn:aws:iam::111122223333:role/app-*"
      ]
    },
    {
      "Sid": "DenyUnencryptedTransportOnS3",
      "Effect": "Deny",
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::prod-mobile-uploads",
        "arn:aws:s3:::prod-mobile-uploads/*"
      ],
      "Condition": {
        "Bool": {
          "aws:SecureTransport": "false"
        }
      }
    }
  ]
}
