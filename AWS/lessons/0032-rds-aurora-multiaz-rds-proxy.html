RDS PostgreSQL & Aurora: Multi-AZ Failover, Read Replicas & RDS Proxy

In Android, Room talks to a local SQLite file with zero network hops and one process. On AWS, relational databases sit across a VPC boundary where PostgreSQL forks an expensive OS process per socket, Multi-AZ failover flips DNS underneath idle pools, Read Replicas introduce replication lag, and bursty Lambda traffic exhausts max_connections in milliseconds unless RDS Proxy sits in front.

Your Android Bridge

In Android, RoomDatabase wraps a single local SQLite file through SupportSQLiteOpenHelper. Enabling Write-Ahead Logging (WAL) lets coroutines run concurrent reads alongside one writer inside your app process—with 0 ms network RTT, no TLS handshakes, and no connection limits beyond local file locks. Cloud PostgreSQL on Amazon RDS or Amazon Aurora breaks every piece of that intuition: every new client connection costs TCP + TLS + authentication RTTs plus ~5–10 MB of database RAM, writes must survive whole Availability Zone outages, and read scaling shifts from local threads to distributed replicas.

1. RDS PostgreSQL: Multi-AZ (High Availability) vs. Read Replicas (Scale)

Junior engineers frequently confuse Multi-AZ deployments with Read Replicas because both maintain a second database instance. In Amazon RDS, they solve completely different problems using opposite replication models:

  • Multi-AZ DB Instance (1 Standby — High Availability & Durability): AWS provisions a primary instance in AZ-a and a passive standby in AZ-b. Every storage write is replicated synchronously at the physical block level to the standby before the commit returns. Result: zero data loss (RPO = 0) if an AZ fails, and automatic failover by updating the instance's DNS CNAME record (typically a 5-second DNS TTL, completing failover in 60–120 seconds). Crucially, the standby cannot serve read queries—its endpoint is closed until promoted.
  • Multi-AZ DB Cluster (2 Readable Standbys — HA + Read Scaling): A newer RDS option spanning 3 AZs (1 writer + 2 readable standbys) using semi-synchronous transaction log replication (at least 1 standby acknowledges before commit). It supports read traffic on the standbys and typically fails over in ~35 seconds.
  • RDS Read Replicas (Asynchronous — Read Scale & Cross-Region DR): Read Replicas use PostgreSQL's asynchronous WAL streaming replication from the primary to up to 15 read replicas (same region or cross-region). Because replication is asynchronous, the primary does not wait for replicas to apply WAL records before returning COMMIT to your backend.
Production Trap: Read-After-Write Consistency & Stale JVM DNS

Two failures bite mobile backends immediately in production: (1) Replication Lag: An Android client posts POST /orders to the primary and immediately calls GET /orders/{id} routed to a Read Replica—getting HTTP 404 because the WAL record hasn't arrived yet (ReplicaLag > 0). Route read-your-own-writes queries strictly to the primary writer. (2) Client DNS Caching: During an RDS Multi-AZ failover, AWS updates the DNS record to the promoted standby IP, but runtimes with aggressive DNS caching (older JVMs or unconfigured connection pools) keep sending packets to the dead IP until restarted.

2. Amazon Aurora: Decoupled Storage & the 6-Copy Quorum

Classic RDS PostgreSQL couples compute and storage: the database engine writes 8 KB dirty pages, full-page images, and WAL over EBS, and EBS replicates blocks synchronously across AZs. Amazon Aurora eliminates EBS page writes from the critical path by separating compute head nodes from a shared, multi-tenant cluster storage volume spanning 3 Availability Zones:

  1. 6 Storage Copies Across 3 AZs: Every 10 GB protection group in the cluster volume is replicated 6 times—2 copies in AZ-1, 2 copies in AZ-2, and 2 copies in AZ-3. The primary compute node sends only compact redo log records (not full 8 KB data pages) to the storage fleet.
  2. 4-of-6 Write Quorum & 3-of-6 Read Quorum: A write is durable once 4 of 6 storage nodes acknowledge the redo log record. Reads and peer-to-peer storage repair query at least 3 of 6 nodes. Because $4 + 3 = 7 > 6$, every read quorum is mathematically guaranteed to intersect with at least one copy holding the latest write.
  3. AZ + 1 Fault Tolerance: Losing an entire Availability Zone destroys 2 copies, leaving 4 copies healthy—so both reads and writes continue uninterrupted. Losing an entire AZ plus 1 additional storage node (3 copies lost) leaves 3 surviving copies: writes pause because the 4/6 write quorum is lost, while reads and automated storage repair continue from the 3/6 read quorum.
  4. Fast Failover & Shared-Storage Replicas: Up to 15 Aurora Replicas mount the exact same 6-copy storage volume. The writer only ships lightweight log metadata to invalidate replica buffer caches—keeping replica lag typically in the 10–20 ms range and enabling automatic failover in under 30 seconds without replaying gigabytes of WAL.

3. RDS Proxy: Multiplexing Lambda Bursts & Avoiding Connection Pinning

PostgreSQL uses a process-per-connection model: each client socket spawns a separate OS backend process consuming roughly 5–10 MB of RAM even while idle. A traditional ECS service with 4 containers holding a pool of 20 connections each opens 80 DB connections. By contrast, if an Android push notification triggers 600 concurrent AWS Lambda invocations, each warm container opens its own pool—instantly exceeding max_connections on a db.t3.medium (~450 max) and burning CPU on TLS + SCRAM-SHA-256 handshakes.

Amazon RDS Proxy solves this by placing a managed, highly available proxy fleet inside your VPC:

  • Transaction-Level Multiplexing: RDS Proxy holds a warm pool of persistent DB connections (capped via MaxConnectionsPercent of max_connections). After a Lambda finishes a SQL transaction (COMMIT or ROLLBACK), the proxy immediately reuses that underlying database connection for another Lambda's transaction.
  • Failover Acceleration (Up to 66% Faster): Because RDS Proxy directly monitors the underlying cluster topology, it preserves client TCP connections during a failover, pauses incoming queries briefly, and routes them straight to the promoted writer without waiting for client DNS caches to expire.
  • IAM & Secrets Manager Integration: Lambda functions authenticate to RDS Proxy using short-lived IAM tokens while the proxy retrieves the actual DB credentials from AWS Secrets Manager.
The RDS Proxy Anti-Pattern: Connection Pinning

Multiplexing only works when the backend connection carries zero leftover session state between transactions. If your Lambda executes session-wide SET statements (e.g., SET TIME ZONE 'UTC' or Prisma/TypeORM startup session config), creates TEMP tables, uses advisory locks, or triggers unsupported prepared statement state, RDS Proxy pins the client socket 1:1 to a physical database connection for the rest of the session. Watch the CloudWatch metric DatabaseConnectionsCurrentlySessionPinned: if pinning climbs during a burst, multiplexing collapses and your database still hits max_connections! Fix it by keeping transactions short, replacing session SET with transaction-scoped SET LOCAL, or enabling EXCLUDE_VARIABLE_SETS in your proxy target group's SessionPinningFilters when safe.

4. Production Code Example: Aurora + RDS Proxy (CDK) & Safe Lambda Pooling

Notice how the CDK configuration caps backend pool usage at 80% (leaving 20% headroom for migrations and DBA consoles) and enables EXCLUDE_VARIABLE_SETS, while the Lambda initializes its PostgreSQL client outside the handler and uses SET LOCAL inside transactions to prevent connection pinning: 

// 1. Infrastructure (AWS CDK TypeScript) — Aurora PostgreSQL + RDS Proxy
const cluster = new rds.DatabaseCluster(this, "OrdersAurora", {
  engine: rds.DatabaseClusterEngine.auroraPostgres({
    version: rds.AuroraPostgresEngineVersion.VER_16_2,
  }),
  writer: rds.ClusterInstance.provisioned("Writer", {
    instanceType: ec2.InstanceType.of(ec2.InstanceClass.R6G, ec2.InstanceSize.LARGE),
  }),
  readers: [
    rds.ClusterInstance.provisioned("Reader", {
      instanceType: ec2.InstanceType.of(ec2.InstanceClass.R6G, ec2.InstanceSize.LARGE),
    }),
  ],
  vpc,
});

const proxy = cluster.addProxy("OrdersProxy", {
  secrets: [cluster.secret!],
  vpc,
  iamAuth: true,
  requireTLS: true,
  maxConnectionsPercent: 80,           // Leave 20% of max_connections for admin/migrations
  idleClientTimeout: Duration.minutes(30),
  sessionPinningFilters: [rds.SessionPinningFilter.EXCLUDE_VARIABLE_SETS],
});

// 2. Lambda Handler (Node.js / pg) — Global pool + transaction-scoped SET LOCAL
const { Pool } = require("pg");
// Global scope: reused across warm Lambda invocations (max: 1 or 2 per container)
const pool = new Pool({ host: process.env.PROXY_ENDPOINT, max: 2, ssl: { rejectUnauthorized: true } });

exports.handler = async (event) => {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    await client.query("SET LOCAL statement_timeout = '3000ms'"); // Transaction-scoped: NO pinning!
    const res = await client.query("SELECT id, status FROM orders WHERE user_id = $1", [event.userId]);
    await client.query("COMMIT");
    return { statusCode: 200, body: JSON.stringify(res.rows) };
  } catch (err) {
    await client.query("ROLLBACK");
    throw err;
  } finally {
    client.release(); // Returns socket to container pool; Proxy detaches backend DB conn
  }
};
