Route 53: Hosted Zones, Alias vs CNAME, Health Checks & Routing Policies

Every cold mobile connection begins with a DNS lookup. A senior engineer knows why you cannot put a CNAME at your domain apex, how Split-Horizon Private Hosted Zones keep internal services invisible from the internet, and why DNS TTLs and mobile socket pools govern your real failover recovery time.

Your Android Bridge

In Android, OkHttpClient delegates hostname lookup to Dns.SYSTEM (which invokes Android's netd / bionic getaddrinfo resolver and respects Private DNS over TLS), then opens a TCP+TLS socket to the first reachable IP and stores it in ConnectionPool. Two crucial mobile realities collide with AWS DNS here: (1) while a socket stays pooled, OkHttp does not re-query DNS even after the record's TTL expires, and (2) mobile carrier resolvers strictly cache records for up to the record's TTL. Amazon Route 53 sits on the authoritative side of that lookup—controlling which regional IP Android sees, failing over around dead ALBs, and keeping internal microservice hostnames private inside your VPC.

1. Authoritative Anycast DNS, Public vs. Private Hosted Zones & Split-Horizon

Amazon Route 53 is an authoritative DNS service backed by a 100% availability SLA for the DNS query data plane. When your domain registrar delegates myapp.com to Route 53, it assigns four authoritative name servers spread across four distinct top-level domains (.com, .net, .org, .co.uk) so even an entire TLD outage cannot take your domain offline.

Inside Route 53, records live inside Hosted Zones—containers that answer queries for a domain and its subdomains:

  • Public Hosted Zones: Route internet traffic (from Android devices, browsers, and partners) to public entry points such as CloudFront distributions, Application Load Balancers, or API Gateways.
  • Private Hosted Zones (PHZs): Associated with one or more VPCs (requiring both enableDnsSupport = true and enableDnsHostnames = true on the VPC). Queries from EC2/ECS/Lambda workloads go to the VPC's Route 53 Resolver at VPC_CIDR + 2 (for example, 10.0.0.2) or 169.254.169.253 and never cross the public internet.
  • Split-Horizon (Split-View) DNS: You create both a Public Hosted Zone and a Private Hosted Zone for the exact same domain (myapp.com). External Android clients resolve api.myapp.com to a public CloudFront/ALB IP, while internal services resolve api.myapp.com or orders-db.myapp.com to private 10.0.x.x Interface Endpoints or ALB IPs.
Split-Horizon Trap: No Fallback From Private to Public

When a VPC is associated with a Private Hosted Zone for myapp.com, Route 53 Resolver considers that PHZ authoritative for the entire namespace inside that VPC. If an ECS task queries status.myapp.com and that record exists only in your Public Hosted Zone (not in the PHZ), Route 53 Resolver returns NXDOMAIN—it does not fall back to the Public Hosted Zone. Always mirror any public records needed by internal workloads inside the PHZ.

2. Zone Apex, Alias Records vs. CNAME

Suppose you want users to reach https://myapp.com (the zone apex, or naked/root domain) backed by an AWS ALB or CloudFront distribution. AWS load balancers scale horizontally behind the scenes and rotate their IP addresses constantly, so you cannot hardcode static A record IPs. Why not point myapp.com to my-alb-123.us-east-1.elb.amazonaws.com using a standard CNAME?

Because RFC 1034 Section 3.6.2 and RFC 1912 Section 2.4 forbid a CNAME from coexisting with any other DNS record type at the same name. The zone apex must carry NS (Name Server) and SOA (Start of Authority) records—so placing a CNAME at myapp.com breaks DNS compliance and causes resolvers to fail NS, SOA, and MX lookups.

Route 53 solves this with Alias records—an AWS-specific extension on standard A (IPv4) and AAAA (IPv6) records:

  • Zone Apex Support: Because an Alias record presents externally as an A or AAAA record, it legally coexists with NS, SOA, and MX records at myapp.com.
  • Zero Extra RTT & Zero Query Cost: Route 53 internally resolves the target AWS resource (CloudFront, ALB, NLB, API Gateway, S3 website, Global Accelerator, or VPC Interface Endpoint) and returns the target's IP addresses directly—saving one recursive DNS lookup and eliminating Route 53 per-query charges (standard CNAME queries are billed at \$0.40 per million queries, whereas Alias queries to AWS resources are free).
  • Automatic Target Health & Managed TTL: Setting EvaluateTargetHealth = true lets Route 53 check the ALB/NLB's own target group health without creating a separate HTTP health check. Note the tradeoff: you cannot set a custom TTL on an Alias record; Route 53 inherits the target AWS service's TTL (typically 60 seconds for ALBs).

3. Routing Policies, Health Checks & TTL Failover Tradeoffs

Choosing the right Route 53 routing policy determines both normal-state latency and blast radius during regional incidents:

  • Simple: Returns one or more IPs in random order. Does not support per-record health checks. Use only for single-region static endpoints.
  • Failover (Active-Passive): Routes 100% of traffic to PRIMARY while its health check passes, switching to SECONDARY when PRIMARY fails. Important Route 53 behavior: if both Primary and Secondary health checks fail, Route 53 fails open and returns Primary anyway (assuming the health-checker network might be partitioned rather than blackholing all traffic).
  • Weighted (0–255): Splits traffic proportionally across records (for example, 95 to v1 and 5 to canary v2). Setting weight to 0 stops traffic to that record unless every record has weight 0 (in which case all receive equal weight). Unhealthy records are removed before normalizing remaining weights.
  • Latency-Based Routing (LBR): Routes each user to the AWS Region with the lowest measured network latency (using us-east-1, eu-west-1, etc.). If the closest region fails its health check, Route 53 automatically selects the next-lowest-latency healthy region.
  • Geolocation vs. Geoproximity: Geolocation maps strictly by country, continent, or US state (ideal for GDPR/data-residency compliance, with an optional * default fallback). Geoproximity routes by physical distance and supports a numeric Bias (-99 to +99) to expand or shrink a region's catchment area.
  • Multivalue Answer: Returns up to 8 healthy records selected randomly—essentially Simple routing upgraded with health checks for client-side redundancy.

Health Checks & Real-World Failover Math

Route 53 supports three health check modes: (1) Endpoint checks (HTTP/HTTPS/TCP probes sent from distributed AWS checkers every 30s standard or 10s fast, requiring 3 consecutive failures by default to flip unhealthy), (2) Calculated health checks (aggregating up to 256 child checks with AND/OR/M-of-N logic to prevent noisy single-host flaps), and (3) CloudWatch Alarm-backed health checks—essential when monitoring private VPC resources like Aurora or internal ALBs that public Route 53 health checkers cannot reach directly.

Total failover time for an Android user is not just the health check speed:

Worst-Case Failover = Health Check Detection (e.g., 3 × 10s = 30s) + DNS Record TTL (e.g., 60s) + Client Connection Pool Lifetime

A 300s or 3600s TTL lowers DNS billings and keeps carrier caches warm, but traps new sessions on a dead region for 5–60 minutes. Conversely, setting TTL to 0s forces fresh lookups on every cold connection, hurting Android P95 startup latency and increasing query costs. In production, 60 seconds (matching ALB Alias TTL) is the standard sweet spot for dynamic APIs—and on Android, configuring reasonable OkHttp pool eviction or retry-on-connection-failure ensures active clients rotate off dead sockets promptly.

4. Production Code Example: Terraform Route 53 Failover & Private Zone

Notice how the Terraform configuration below separates the public apex Alias, the 10-second fast health check for active-passive regional failover, and the split-horizon Private Hosted Zone: 

# 1. Public Hosted Zone + Fast 10s Health Check for Primary Region
resource "aws_route53_zone" "public" {
  name = "myapp.com"
}

resource "aws_route53_health_check" "primary_api" {
  fqdn              = "primary-origin.myapp.com"
  port              = 443
  type              = "HTTPS"
  resource_path     = "/healthz"
  request_interval  = 10   # Fast health check (10s vs 30s default)
  failure_threshold = 3    # 3 consecutive failures = ~30s detection
}

# 2. Zone Apex Active-Passive Failover using Alias (free queries, legal at apex)
resource "aws_route53_record" "apex_primary" {
  zone_id        = aws_route53_zone.public.zone_id
  name           = "myapp.com"
  type           = "A"
  set_identifier = "us-east-1-primary"

  failover_routing_policy { type = "PRIMARY" }
  health_check_id = aws_route53_health_check.primary_api.id

  alias {
    name                   = aws_lb.us_east_1.dns_name
    zone_id                = aws_lb.us_east_1.zone_id
    evaluate_target_health = true
  }
}

resource "aws_route53_record" "apex_secondary" {
  zone_id        = aws_route53_zone.public.zone_id
  name           = "myapp.com"
  type           = "A"
  set_identifier = "us-west-2-secondary"

  failover_routing_policy { type = "SECONDARY" }

  alias {
    name                   = aws_lb.us_west_2.dns_name
    zone_id                = aws_lb.us_west_2.zone_id
    evaluate_target_health = true
  }
}

# 3. Split-Horizon Private Hosted Zone (internal VPCs only)
resource "aws_route53_zone" "private" {
  name = "myapp.com"
  vpc { vpc_id = aws_vpc.prod.id } # Requires enable_dns_support & enable_dns_hostnames
}
