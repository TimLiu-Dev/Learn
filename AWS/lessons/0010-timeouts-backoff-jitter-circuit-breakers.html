Timeouts, Exponential Backoff with Jitter & Circuit Breakers

In distributed cloud systems, partial failures and transient brownouts are normal—not rare exceptions. Left unchecked, generous timeouts and naive retries turn a 5-second database hiccup into a self-inflicted retry storm that keeps your AWS stack down for an hour. Here is how to bound wait times, spread retries with Marc Brooker's Full Jitter, enforce retry budgets, and fail fast with a 3-state circuit breaker.

Your Android Bridge

On Android, WorkManager gives you BackoffPolicy.EXPONENTIAL (defaulting to a 30s initial delay, floored at 10s), and OkHttp gives you connectTimeout, readTimeout, writeTimeout, and callTimeout. On a single device, a deterministic 2s → 4s → 8s retry loop feels harmless. When 200,000 phones and dozens of backend ECS containers hit the same AWS ALB and RDS primary during a brief brownout, unjittered retries synchronize into periodic hammer waves that crush recovery.

1. Bounded Timeouts & Metastable Retry Amplification

Every network call consumes a finite resource while waiting: a thread or coroutine, memory buffers, a file descriptor, or a precious PostgreSQL connection slot. If you omit a strict timeout—or set it to 60 seconds on a service whose normal p99 latency is 40 ms—slow failures become far worse than fast errors.

Consider an ECS service with 100 worker slots handling 2,500 req/s at 40 ms average latency. If a downstream dependency hangs and your timeout is 30,000 ms, all 100 workers saturate at just 3.3 req/s (100 / 30s). Even after the dependency recovers, queued retries keep workers pinned at 100% saturation—a classic metastable failure.

  • Per-attempt timeout vs. total call deadline: Separate the time allowed for one attempt (e.g., 800 ms) from the total wall-clock budget including retries (OkHttp's callTimeout = 2,500 ms).
  • Only retry transient failures: Retry 429 Too Many Requests, 500, 502, 503, 504, and socket/connect timeouts. Never retry deterministic client errors (400, 401, 403, 404)—they will fail identically every time.
  • Respect idempotency: Retrying a timed-out GET is safe; retrying a timed-out POST /charges without an idempotency key risks double-charging the user (covered in Lesson 0011).

2. Exponential Backoff & Marc Brooker's Full Jitter

Suppose an Availability Zone network blip drops 10,000 requests at t = 0.00s. With plain deterministic exponential backoff (sleep = min(cap, base * 2^attempt)), all 10,000 callers sleep 1s, wake up together at t = 1.00s, overload the server, sleep 2s, and collide again at t = 3.00s.

In the AWS Architecture Blog classic Exponential Backoff And Jitter, Marc Brooker simulated competing clients under contention and compared four formulas:

  • No Jitter: sleep = min(cap, base * 2^attempt) — terrible under concurrency; creates sharp thundering-herd spikes.
  • Full Jitter (Recommended Default): sleep = random(0, min(cap, base * 2^attempt)) — uniformly spreads retries across the entire window from 0 up to the exponential cap, minimizing both total server work and client completion time.
  • Equal Jitter: temp = min(cap, base * 2^attempt); sleep = temp / 2 + random(0, temp / 2) — guarantees at least half the backoff wait, avoiding immediate 0 ms retries at the cost of slightly higher contention than Full Jitter.
  • Decorrelated Jitter: sleep = min(cap, random(base, prevSleep * 3)) — stateful across attempts; performs nearly as well as Full Jitter.
Figure 1: Deterministic backoff synchronizes clients into periodic load spikes. Full Jitter flattens contention by sampling uniformly over [0, min(cap, base * 2^attempt)].

3. Retry Budgets & Avoiding Multi-Layer Amplification

Jitter fixes timing collisions, but it does not cap total volume. If a database goes completely dark for 60 seconds and every caller performs 3 retries, total traffic quadruples (4x) right when capacity is zero.

As detailed in the Amazon Builders' Library and the AWS SDK Retry Behavior Specification, production SDKs protect downstream services using a token bucket retry budget:

  • A client starts with a bucket of e.g. 500 retry tokens.
  • Each retry attempt spends 5 tokens (a 1:5 ratio, capping retries at roughly 20% overhead during sustained outages).
  • Each successful first-try response refunds 1 token up to the bucket capacity.
  • When the bucket hits 0 tokens, retries are suppressed immediately—turning cascading amplification into fast failure until healthy responses return.
Never Stack Retries Across Every Tier

If your Android app retries 3x, your API Gateway/BFF retries 3x, and your Order Service retries 3x against RDS, one user tap can generate (1 + 3) × (1 + 3) × (1 + 3) = 64 database attempts! Retry at one well-chosen layer (typically the immediate caller of a flaky network boundary, or the client edge for transient mobile connectivity) and propagate remaining request deadlines downstream.

4. The 3-State Circuit Breaker (Closed, Open, Half-Open)

Retries assume the failure is brief. When a downstream dependency is hard-down or timing out for minutes, retrying—even with Full Jitter—still forces callers to wait for timeouts and ties up worker pools. A circuit breaker wraps downstream calls in a 3-state finite state machine that stops calling a broken dependency altogether:

  1. CLOSED (Healthy): Traffic flows normally. Every failure increments a failure counter (or sliding-window error rate); a success resets consecutive failures to 0. When failures reach failureThreshold, the breaker trips to OPEN and records openedAt.
  2. OPEN (Fail Fast): Calls are rejected immediately in <1 ms without opening a socket—returning a cached fallback, degraded UI state, or fast 503. This protects both caller threads and the struggling downstream service for openDurationMs (cooldown).
  3. HALF_OPEN (Recovery Probe): Once now - openedAt ≥ openDurationMs, the breaker lets limited probe traffic through. If halfOpenSuccessThreshold probes succeed, it resets to CLOSED. If any probe fails, it trips immediately back to OPEN and restarts the cooldown timer.
Figure 2: A 3-state circuit breaker isolates unhealthy dependencies in OPEN, then cautiously tests recovery in HALF_OPEN before restoring full traffic.

Serverless & Fleet Caveat: In-memory circuit breakers live per container or AWS Lambda execution environment. If you run 100 ECS tasks, each task opens and probes independently (sending 100 probes instead of 1). Never share breaker state in a database that sits on the same failing path—keep per-instance breakers lightweight, or read coarse feature flags from an out-of-band control plane like AWS AppConfig.

5. Production Code: Android + AWS SDK v3 Resilience

Notice how both sides of the stack enforce bounded deadlines and backoff—while letting the AWS SDK handle jittered token-bucket retries rather than writing raw for loops: 

// 1. Android Client (Kotlin — WorkManager + OkHttp bounded callTimeout)
val syncWork = OneTimeWorkRequestBuilder<SyncOrdersWorker>()
    .setBackoffCriteria(
        BackoffPolicy.EXPONENTIAL,
        WorkRequest.MIN_BACKOFF_MILLIS, // 10,000 ms floor enforced by WorkManager
        TimeUnit.MILLISECONDS
    )
    .build()

val okHttp = OkHttpClient.Builder()
    .connectTimeout(2, TimeUnit.SECONDS)
    .readTimeout(3, TimeUnit.SECONDS)
    .callTimeout(6, TimeUnit.SECONDS) // Hard ceiling across redirects + retries
    .build()

// 2. Cloud Service (TypeScript — AWS SDK v3 Adaptive Retry + Attempt Timeout)
import { DynamoDBClient } from "@aws-sdk/client-dynamodb";
import { NodeHttpHandler } from "@smithy/node-http-handler";

const ddb = new DynamoDBClient({
  maxAttempts: 3,               // Total attempts (1 initial + up to 2 retries)
  retryMode: "adaptive",        // Full jitter + client-side token bucket rate limiter
  requestHandler: new NodeHttpHandler({
    connectionTimeout: 500,     // Fail fast on TCP/TLS stall
    requestTimeout: 1500,       // Bound each individual DynamoDB attempt
  }),
});
