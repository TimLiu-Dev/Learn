Problem Statement & Boundary Checks

LeetCode #933 ↗

Verbatim Problem Statement

You have a RecentCounter class which counts the number of recent requests within a certain time frame.

Implement the RecentCounter class:

  • RecentCounter() Initializes the counter with zero recent requests.
  • int ping(int t) Adds a new request at time t, where t represents some time in milliseconds, and returns the number of requests that has happened in the past 3000 milliseconds (including the new request). Specifically, return the number of requests that have happened in the inclusive range [t - 3000, t].

It is guaranteed that every call to ping uses a strictly larger value of t than the previous call.

Plain-English Translation

Design a sliding-window rate limiter. Because timestamps arrive in strictly ascending chronological order (t_1 < t_2 < \dots), older events always expire before newer events. Add the new timestamp to the back of a FIFO queue, discard all expired timestamps from the front that are smaller than t - 3000, and return the remaining count of elements in the queue.

Example Call Sequence
rc = RecentCounter();
rc.ping(1); // returns 1 (range [-2999, 1])
rc.ping(100); // returns 2 (range [-2900, 100])
rc.ping(3001); // returns 3 (range [1, 3001])
rc.ping(3002); // returns 3 (range [2, 3002], 1 is evicted!)
Eviction Analysis on ping(3002)
• Range window: [3002 - 3000, 3002] = [2, 3002]
• Timestamp 1 in queue is < 2 → EVICTED from front!
• Queue remaining: [100, 3001, 3002]
• Queue size = 3 ✓

Constraints

  • 1 ≤ t ≤ 109 (Monotonically strictly increasing)
  • At most 104 calls will be made to ping.

3 Canonical Boundary Check Shapes

1. First Call Ever: ping(1) → Queue starts empty, pushes 1, returns exactly 1.
2. Massive Time Gap: ping(1), ping(10000) → All previous elements expire, queue holds only [10000], returns 1.
3. Tight Clustered Burst: Hundreds of calls within a 500ms span → No elements evicted, queue size grows to count every call in the burst.

The Mental Model & "Explain Like I'm 12"

Why monotonic timestamps convert rate limiting into an amortized O(1) queue eviction.

The Airport Baggage Conveyor Belt

Imagine an airport baggage conveyor belt. Luggage boxes are loaded onto the back of the belt stamped with their arrival time t.

Because time moves forward, every new piece of luggage has a timestamp larger than the luggage before it.

At the front of the conveyor belt, a mechanical arm sweeps off any luggage that is older than 3000 milliseconds:

while (!queue.isEmpty() && queue.peek() < t - 3000) {
  queue.poll() // Evict stale timestamp from front
}

Amortized O(1) Guarantee: Every timestamp is added to the queue exactly once and evicted from the queue at most once. Over M total pings, the loop runs at most M times total across the entire lifetime of the program!

The "A-Ha!" Architectural Trigger

When items arrive in strictly ascending order and you need to query a sliding expiration window ($[t - W, t]$), choose a FIFO Queue. Elements are pushed to the back; expired elements are peeled off the front. Memory never exceeds the maximum burst count in window W.

The Naive Trap (Red) vs. Optimal Breakthrough (Green)

Why unbounded memory lists fail production rate limiter requirements.

The Naive Trap: Unbounded List + Linear Count Memory Leak • O(M) Space

Appending every timestamp into a persistent list without eviction: 

val history = mutableListOf<Int>()
fun ping(t: Int): Int {
    history.add(t)
    var count = 0
    for (time in history) {
        if (time >= t - 3000) count++
    }
    return count
}
  • Memory Leak: In a production web server receiving 10,000 pings/sec, storing historical pings forever will crash the JVM with OutOfMemoryError.
  • Degrading Latency: Scanning an ever-growing list makes each subsequent request slower (O(M) per ping).
Interview Verdict: Critical memory leak in production
Optimal Breakthrough: FIFO Queue Eviction O(1) Amortized Time • O(W) Bounded Space

Evict expired timestamps immediately from the head of an ArrayDeque: 

val queue = ArrayDeque<Int>()
fun ping(t: Int): Int {
    queue.addLast(t)
    while (queue.first() < t - 3000) {
        queue.removeFirst()
    }
    return queue.size
}
  • Bounded Memory: The queue size can never exceed the maximum number of requests in a 3000ms window (W ≤ 3001). Memory is fixed and safe.
  • Amortized O(1): Each timestamp enters once and exits once. Peak efficiency.
Interview Verdict: Production-grade rate limiter

From Brute Force to Optimal & Interactive Sandbox

Evolution from unbounded historical lists to sliding FIFO queue eviction.

Approach 1: Unbounded List Linear Scan (O(M) Time, O(M) Space)

Store every call to ping(t) in a dynamic array. To return the count, linearly count how many timestamps satisfy time ≥ t - 3000. Memory grows indefinitely and request latency degrades over time. 

class RecentCounter() {
    private val list = mutableListOf<Int>()

    fun ping(t: Int): Int {
        list.add(t)
        var count = 0
        for (time in list) {
            if (time >= t - 3000) count++
        }
        return count
    }
}
class RecentCounter:
    def __init__(self):
        self.history = []

    def ping(self, t: int) -> int:
        self.history.append(t)
        threshold = t - 3000
        return sum(1 for time in self.history if time >= threshold)
import java.util.*;

class RecentCounter {
    private List<Integer> history = new ArrayList<>();

    public int ping(int t) {
        history.add(t);
        int count = 0;
        for (int time : history) {
            if (time >= t - 3000) count++;
        }
        return count;
    }
}
Approach 2: Binary Search (Bisect) on Sorted List (O(log M) Time, O(M) Space)

Since timestamps are strictly increasing, use binary search to locate the first timestamp ≥ t - 3000. Faster query time (O(\log M)), but still fails the space constraint by holding all M items forever. 

class RecentCounter() {
    private val list = mutableListOf<Int>()

    fun ping(t: Int): Int {
        list.add(t)
        val threshold = t - 3000
        var idx = list.binarySearch(threshold)
        if (idx < 0) idx = -(idx + 1)
        return list.size - idx
    }
}
import bisect

class RecentCounter:
    def __init__(self):
        self.history = []

    def ping(self, t: int) -> int:
        self.history.append(t)
        idx = bisect.bisect_left(self.history, t - 3000)
        return len(self.history) - idx
import java.util.*;

class RecentCounter {
    private List<Integer> history = new ArrayList<>();

    public int ping(int t) {
        history.add(t);
        int idx = Collections.binarySearch(history, t - 3000);
        if (idx < 0) idx = -(idx + 1);
        return history.size() - idx;
    }
}
Approach 3: FIFO Queue Eviction (O(1) Amortized Time, O(W) Bounded Space)

Store active timestamps in a FIFO queue. Whenever a new ping arrives, enqueue it at the back, then discard timestamps from the front as long as they are strictly less than t - 3000. Maximum queue size is bounded by $\min(M, 3001)$. 

class RecentCounter() {
    // ArrayDeque offers O(1) amortized append and pop operations
    private val queue = ArrayDeque<Int>()

    fun ping(t: Int): Int {
        // 1. Enqueue new request timestamp
        queue.addLast(t)

        // 2. Evict any timestamps older than the 3000ms sliding window
        while (queue.first() < t - 3000) {
            queue.removeFirst()
        }

        // 3. Number of elements remaining in queue is the active request count
        return queue.size
    }
}
from collections import deque

class RecentCounter:
    def __init__(self):
        self.queue = deque()

    def ping(self, t: int) -> int:
        self.queue.append(t)
        threshold = t - 3000
        while self.queue[0] < threshold:
            self.queue.popleft()
        return len(self.queue)
import java.util.ArrayDeque;
import java.util.Deque;

class RecentCounter {
    private final Deque<Integer> queue;

    public RecentCounter() {
        queue = new ArrayDeque<>();
    }

    public int ping(int t) {
        queue.addLast(t);
        while (queue.peekFirst() < t - 3000) {
            queue.pollFirst();
        }
        return queue.size();
    }
}
★ Senior Engineering Guardrails

1. Amortized Cost vs Worst Case: Even if a single call evicts 3,000 items in its while loop, every element is inserted into the queue exactly once and deleted at most once. Therefore, across M calls, total operations are bounded by 2M. The average cost per call is strictly O(1).

2. Bounded Memory Invariant: The memory consumption of this counter does NOT depend on the total lifespan of the process (M). It depends solely on the maximum arrival rate within any 3-second window! This makes it suitable for long-running production server daemons.

You: "Because timestamps are strictly increasing, the oldest timestamps are always at the front of the queue. We use an ArrayDeque. When ping(t) is called, we append t to the back. Then, in a while loop, we pop elements from the front as long as queue.first() < t - 3000. Finally, we return queue.size. Because each element enters and exits the queue at most once, the amortized runtime per call is strictly O(1), and the space is capped at ≤ 3001 integers."
