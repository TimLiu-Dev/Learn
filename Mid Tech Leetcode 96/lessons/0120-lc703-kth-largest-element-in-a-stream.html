Problem #703: Kth Largest Element in a Stream

External Judge ↗

Official Problem Statement

Design a class to find the kth largest element in a stream. Note that it is the kth largest element in the sorted order, not the kth distinct element.

Implement KthLargest:
• KthLargest(int k, int[] nums) Initializes the object with the integer k and initial stream nums.
• int add(int val) Appends val to the stream and returns the current kth largest element.

Example 1: KthLargest(3, [4, 5, 8, 2]); add(3); add(5); add(10); add(9); add(4) → Output: 4, 5, 5, 8, 8

Plain-English Translation & Core Nuance

Maintain a VIP club with capacity k storing the k largest numbers seen so far. Keep a Min-Heap of size k so the *weakest* VIP (k-th largest overall!) always stands right at the door (peek()): any newcomer smaller than the weakest VIP bounces off; any larger newcomer evicts the weakest VIP in O(log k).

Official Constraints:
  • 1 <= k <= 10^4
  • 0 <= nums.length <= 10^4 (initial array may have k - 1 elements!)
  • It is guaranteed at least k elements exist when add() is called.

Canonical Input Shapes (Mental Boundary Checks)

Minimum Base Case
k = 1, nums = [] -> Constructor starts with empty heap; first add(5) pushes 5 and returns 5.
Best-Case Early Exit
Heap already has k items and val <= minHeap.peek() -> can skip or push+pop, root stays unchanged.
Worst-Case Full Scan
10^4 calls with k = 10^4 -> Each add() runs in O(log k) time and O(k) total memory.

Section 01 • Cognitive Anchor

The Mental Model & "Explain Like I'm 12"

💡 The K-Seat VIP Lounge Bouncer (Min-Heap, Not Max-Heap!)

Instinct screams 'Largest -> Max-Heap!'—that's the classic trap. If you keep only the top K champions in a lounge, who gets kicked out when a stronger challenger arrives? The *weakest* of those K champions! And which champion is the K-th largest overall? Also the *weakest* of those K champions! A Min-Heap capped at size K keeps that exact threshold element at O(1) peek() and evicts it in O(log K).

The Mental "A-Ha!" Switch:

To track the K largest elements, use a MIN-Heap capped at size K: its minimum root IS the K-th largest element!

Section 02 • Algorithmic Trade-off Analysis

The Naive Trap (Red) vs. Optimal Breakthrough (Green)

The Naive Trap O(M · N log N) or O(M · N) Time

Append every incoming val to an ArrayList and re-sort (or binary-insert shift) on every add().

Wasted Work: Elements smaller than the K-th largest can NEVER become the K-th largest later because the stream only grows—storing and shifting them is pure waste.
The Optimal Breakthrough O(N log K) Init, O(log K) per add(), O(K) Space

Maintain a PriorityQueue (Min-Heap) of size <= K: offer(val), if (pq.size > k) pq.poll(), return pq.peek().

Core Invariant: After every operation with >= k stream items, minHeap contains the exact k largest values seen so far, and minHeap.peek() is the k-th largest.
Approach Time Complexity Space Complexity Practical Trade-off / Bottleneck
Naive: Append + Sort Every add() O(N log N) per add O(N) TLE across 10^4 stream events.
Better: Max-Heap of All Elements O(K log N) per add O(N) Must pop K-1 items and push them back on every read!
Optimal: Size-K Min-Heap O(log K) per add O(K) ★ Bounded O(K) memory even on infinite streams.

From Naive to Optimal & Runnable Practice Arena

Strict ordering: Kotlin (Default) → Python → Java across all approaches.

Naive: Append & Re-Sort List on Every Add

Stores all stream values and sorts on every add() in O(N log N) per query.

Time: O(N log N) per add Space: O(N) 
class KthLargest(private val k: Int, nums: IntArray) {
    private val list = nums.toMutableList()

    fun add(v: Int): Int {
        list.add(v)
        list.sort()
        return list[list.size - k]
    }
}

In Naive: Append & Re-Sort List on Every Add, Kotlin uses unboxed JVM primitive arrays (IntArray / BooleanArray) to eliminate object header overhead.

Optimal: Bounded Size-K Min-Heap

Maintains only the k largest elements in a Min-Heap; only mutates the heap when size < k or val > peek().

Time: O(log K) per add Space: O(K) 
import java.util.PriorityQueue

class KthLargest(private val k: Int, nums: IntArray) {
    private val minHeap = PriorityQueue<Int>()

    init {
        for (x in nums) {
            add(x)
        }
    }

    fun add(v: Int): Int {
        if (minHeap.size < k) {
            minHeap.offer(v)
        } else if (v > minHeap.peek()) {
            minHeap.poll()
            minHeap.offer(v)
        }
        return minHeap.peek()
    }
}
Kotlin Runtime & Memory Nuance:

In Optimal: Bounded Size-K Min-Heap, Kotlin uses unboxed JVM primitive arrays (IntArray / BooleanArray) to eliminate object header overhead; and maintains heap ordering in O(log K) via PriorityQueue.

import heapq

class KthLargest:
    def __init__(self, k: int, nums: list[int]):
        self.k = k
        self.heap = []
        for x in nums:
            self.add(x)

    def add(self, val: int) -> int:
        if len(self.heap) < self.k:
            heapq.heappush(self.heap, val)
        elif val > self.heap[0]:
            heapq.heappop(self.heap)
            heapq.heappush(self.heap, val)
        return self.heap[0]

In Optimal: Bounded Size-K Min-Heap, Python uses C-backed heapq binary heap operations on flat lists.

import java.util.PriorityQueue;

class KthLargest {
    private final int k;
    private final PriorityQueue<Integer> minHeap = new PriorityQueue<>();

    public KthLargest(int k, int[] nums) {
        this.k = k;
        for (int x : nums) {
            add(x);
        }
    }

    public int add(int val) {
        if (minHeap.size() < k) {
            minHeap.offer(val);
        } else if (val > minHeap.peek()) {
            minHeap.poll();
            minHeap.offer(val);
        }
        return minHeap.peek();
    }
}

Live Interview Spoken Script & Mid-Level (L4) Follow-Ups

        
4-phase spoken communication script for Karat, pair-programming screens, and onsite loops.

      


      

        

          Phase 1: Clarifying Constraints
          
Notice two key details in the spec: first, we want the k-th largest in sorted order including duplicates; second, initial nums can have k - 1 elements (even empty when k = 1), only guaranteeing >= k elements once add() is called.

        

        

          Phase 2: Space-Time Trade-Off Pitch
          
Since the stream is append-only, any number smaller than the current k-th largest can never enter the top k later. Keeping a Min-Heap capped at size k bounds space at O(k) and exposes the k-th largest at the root in O(1).

        

        

          Phase 3: Clean Implementation Narration
          
In init, I route every element through add(x)—or guarded offer—and inside add(val), if size < k I offer(val); else if val > peek(), I poll and offer(val), avoiding unnecessary heap sifts when val <= peek().

        

        

          Phase 4: Boundary Dry-Run Verification
          
Tracing k=1, nums=[]: constructor leaves minHeap empty without calling peek() prematurely; add(-3) pushes -3 and returns -3.

        

      


      

        ⚡ Mid-Level (L4) Production & Requirement-Pivot Follow-Up:
        
If elements can ALSO expire or be deleted (sliding window K-th largest), a single Min-Heap isn't enough because shrunk top-K needs promotion from the rank-(K+1) runner-up; pair two heaps (or two TreeMaps / Order-Statistic Tree) like #295/#480 with lazy deletion.
