Modern OOD Foundations: Rich Domain Models vs. Anemic Traps & Value Objects

Why traditional 1990s class hierarchies get candidates immediately downleveled, how to eliminate primitive obsession using immutable Value Objects, and how to construct Rich Domain Entities that defend business invariants under concurrent production traffic.

1. The 2027 Senior Reality: Why Inheritance and Anemic Models Fail

In mid-tech and big-tech interviews today, interviewers deliberately listen for signs of "Junior OOP" vs "Senior Production OOD".

Junior candidates immediately reach for deep class inheritance (e.g., class SavingsAccount extends CheckingAccount extends Account) and build Anemic Domain Models—classes that are mere passive data bags filled with public getters and setters, while business rules are haphazardly spread across an unbounded AccountService.

The Senior Interview Red Flag: The Anemic Data Bag

If your domain entity allows external callers to execute account.setBalance(account.getBalance() - 100), you have leaked state mutation and destroyed encapsulation. Any caller can bypass business validation, insert negative balances, create floating-point rounding errors, and trigger race conditions.

2. Anemic Domain Model vs. Rich Domain Model

Examine how a junior candidate implements a monetary transfer compared to how a Senior Engineer structures it:

Anemic Model (Anti-Pattern) Rich Domain Model (Senior Standard)
AnemicAccount.ts (Fragile)
// ❌ Primitive obsession: raw number for money
class AnemicAccount {
  public id: string;
  public balance: number; // Floating point bugs!
  public currency: string;
  
  // Public setters leak state mutation
  public setBalance(amt: number) {
    this.balance = amt;
  }
}

// Logic leaked outside the domain entity
class AccountService {
  transfer(from: AnemicAccount, to: AnemicAccount, amt: number) {
    if (from.balance >= amt) { // Non-atomic check-then-act!
      from.setBalance(from.balance - amt);
      to.setBalance(to.balance + amt);
    }
  }
}
RichAccount.ts (Production Grade)
// ✅ Value Object: Self-validating, immutable
class Money {
  constructor(
    public readonly amountInCents: bigint,
    public readonly currency: Currency
  ) {
    Object.freeze(this);
  }

  add(other: Money): Money {
    this.assertSameCurrency(other);
    return new Money(this.amountInCents + other.amountInCents, this.currency);
  }
}

// ✅ Rich Entity: Encapsulates business invariants
class BankAccount {
  private balance: Money;
  private readonly history: Transaction[] = [];

  withdraw(amount: Money): void {
    if (this.balance.isLessThan(amount)) {
      throw new InsufficientFundsError(this.id, amount);
    }
    this.balance = this.balance.subtract(amount);
    this.history.push(new Transaction(TransactionType.DEBIT, amount));
  }
}

3. Core Pillars of Value Objects in Senior OOD

In modern Domain-Driven Design (DDD) and Senior OOD, domain concepts that represent a descriptor or measurement rather than an individual lifecycle entity must be modeled as Value Objects:

  • Structural Equality over Identity: Two Money objects with 1000 USD are completely interchangeable. They do not have an entity ID (unlike a User or Account).
  • Strict Immutability: Once instantiated, a Value Object can never have its properties mutated. Any operation (e.g. add(), subtract(), format()) yields a fresh instance. Call Object.freeze(this) in JavaScript/TypeScript or use Java record / Python @dataclass(frozen=True).
  • Self-Validating Invariants at Instantiation: A Value Object is impossible to construct in an invalid state. A Money object cannot have a null currency, an invalid ISO-4217 code, or a fractional cent.
  • Elimination of Primitive Obsession: Passing raw numbers, strings, and booleans across methods introduces subtle bugs (e.g. accidentally passing EUR amount into a USD calculation). Value Objects make illegal states unrepresentable.

4. The 2027 Precision Rule: Never Use Floating-Point for Currency

In modern interviews, using JavaScript number (IEEE 754 float) or Java double for currency calculations will trigger immediate scrutiny from interviewers. Why? Because 0.1 + 0.2 === 0.30000000000000004. In financial ledger systems, this rounding drift causes reconciliation failures.

Senior Solution: Store currency amounts in minor units (integers/cents) using integers, BigInt, or fixed-point decimal structures.

  • Money(amountInCents, currency): Must reject fractional amounts (must be integer), reject empty/invalid currency, freeze itself, and provide add(), subtract(), and equals() with currency mismatch checks.
  • BankAccount(id, initialBalance): Must enforce initial non-negative balance, guard deposit(), guard withdraw() against overdraft (throw InsufficientFundsError), and return defensive copies for transaction history.

How to Ace this Topic in a 45-Minute Interview

Verbal phrasing, timing, and defensive techniques when asked to design financial models or transactions.

Say This to the Interviewer

"Before modeling the service layer, I'm isolating Money as an immutable Value Object with structural equality. This eliminates primitive obsession, guarantees zero floating-point drift by operating strictly in integer cents, and rejects currency mismatches at compile/runtime."

Instant Disqualification Trap

Storing balance as a raw double or number on the account class, providing public setters like setBalance(), and checking for overdraft in the UI controller or a generic service helper.
