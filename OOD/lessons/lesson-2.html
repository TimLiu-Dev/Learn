The S.O.L.I.D. Audit: Senior Refactoring under Constraints

Beyond textbook acronyms: how Staff engineers apply Open-Closed extensibility without abstraction bloat, avoid fatal Liskov Substitution violations in domain inheritance, and use Strategy Registries to eliminate branching switch statements.

1. The 2027 Senior Reality: Why Textbook SOLID Fails Interviews

In senior interviews, reciting what S.O.L.I.D. stands for is a junior signal. Interviewers want to see how you balance extensibility against over-engineering. The #1 mistake senior candidates make is creating an interface and abstract factory for every single class before requirement changes even exist.

In production systems, Open-Closed Principle (OCP) means: "Core workflow logic should remain unmodified when adding new business rules, payment gateways, or pricing tiers."

The Switch Statement Anti-Pattern

Whenever you write switch(pricingType) { case 'VIP': ... case 'HOLIDAY': ... } inside a central billing service, you violate OCP. Every new pricing tier requires editing, re-testing, and redeploying the core engine. A Senior Engineer replaces this with a Strategy Registry pattern.

2. Concrete Architecture: The Strategy Registry Pattern

Instead of hardcoded conditionals, the engine depends on a generic strategy interface. Concrete strategies register themselves into an in-memory registry or DI container. The engine delegates calculation polymorphically:

StrategyRegistryPattern.ts
// 1. Unified Strategy Contract
interface DiscountStrategy {
  readonly id: string;
  isApplicable(context: OrderContext): boolean;
  calculateDiscount(subtotalInCents: number, context: OrderContext): number;
}

// 2. Extensible Registry
class DiscountStrategyRegistry {
  private strategies = new Map<string, DiscountStrategy>();

  register(strategy: DiscountStrategy): void {
    if (this.strategies.has(strategy.id)) {
      throw new Error(`Strategy with ID ${strategy.id} already registered.`);
    }
    this.strategies.set(strategy.id, strategy);
  }

  resolveApplicable(context: OrderContext): DiscountStrategy[] {
    return Array.from(this.strategies.values()).filter(s => s.isApplicable(context));
  }
}

3. Liskov Substitution Principle (LSP) in Domain Modeling

The classic textbook violation is Square extends Rectangle. In modern enterprise design, LSP violations look like:

  • Subtypes throwing NotSupportedException for methods inherited from base classes (e.g. ReadOnlyRepository extends Repository throwing on save()).
  • Subtypes strengthening preconditions (e.g. base requires amount > 0, but subclass silently requires amount >= 100).
  • Subtypes weakening postconditions (e.g. base promises to return a non-null, immutable array, but subclass returns null on empty).

Senior Fix: Segregate contracts with the Interface Segregation Principle (ISP). Separate ReadableRepository from WritableRepository rather than forcing a dummy implementation.

How to Ace S.O.L.I.D. in a 45-Minute Senior Interview

Key talking points when interviewers ask to extend system capabilities.

Senior Phrasing to Use

"To adhere to Open-Closed principles without premature abstraction, I'll extract a Strategy interface for discount calculation and register instances into a strategy registry. When new discount rules emerge tomorrow, we add new classes without touching the core billing loop."

Instant Rejection Trap

Creating an interface for every single class regardless of whether polymorphism is needed, or modifying a 200-line switch statement in a shared God service.
