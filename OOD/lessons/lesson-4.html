Concurrency-Safe In-Memory Object Design

Eliminating check-then-act race conditions, implementing Reader-Writer locking semantics, preventing deadlocks via lock hierarchies, and designing leak-free concurrent collections.

1. The #1 Senior Disqualification: The Check-Then-Act Race Condition

In an interview, if you write code like this without synchronization or atomic primitives, your interview ends immediately:

CheckThenActRace.ts
// ❌ Fatal Race Condition: Two concurrent requests check availableSpots === 1 simultaneously!
class ParkingFloor {
  private availableSpots: number = 1;

  public parkCar(car: Car): boolean {
    if (this.availableSpots > 0) {  // THREAD A & B BOTH SEE 1!
      // Context switch occurs here...
      this.availableSpots--;        // Both decrement -> availableSpots becomes -1!
      return true;                  // Both cars parked in the same physical spot!
    }
    return false;
  }
}
Non-Atomic Operations in In-Memory State

Checking a condition in one statement and modifying state in the next without an atomic lock or compare-and-swap (CAS) guarantees corruption in production multi-threaded environments.

2. Reader-Writer Lock (RWLock) Semantics

In high-throughput systems (such as cache lookups or seat availability checks), 95% of operations are read-only, while 5% are writes.

  • Coarse-grained Mutex: Serializes every read. Read latency spikes under load.
  • Reader-Writer Lock: Allows infinite concurrent readers when no write is active. When a write occurs, it acquires exclusive access.

3. Deadlock Prevention via Global Lock Ordering

When transferring resources between two entities (e.g. transferring money from Account A to Account B, or moving inventory between Warehouse 1 and Warehouse 2):

DeadlockHierarchy.ts
// Thread 1: transfer(Account_A, Account_B) -> locks A, waits for B
// Thread 2: transfer(Account_B, Account_A) -> locks B, waits for A
// DEADLOCK!

// ✅ Senior Solution: Enforce global lock acquisition ordering by ID
function transferFunds(from: Account, to: Account, amount: Money) {
  const [firstLock, secondLock] = from.id < to.id ? [from, to] : [to, from];
  
  firstLock.lock();
  try {
    secondLock.lock();
    try {
      // Execute atomic transfer safely
    } finally {
      secondLock.unlock();
    }
  } finally {
    firstLock.unlock();
  }
}
Interactive Practice Studio: Concurrency-Safe Resource Registry
Senior Challenge: Implement ConcurrentResourceRegistry with atomic operations and simulated read-write locking:
  • putIfAbsent(key, value): Atomic check-then-act. If key exists, return { success: false, existingValue }. If absent, set and return { success: true, value }.
  • acquireResource(key, consumerId): Grants exclusive lease. Returns false if already leased by someone else.
  • releaseResource(key, consumerId): Releases lease only if leased by matching consumerId.
  • atomicTransfer(fromKey, toKey, amount): Safe transfer preventing negative balances and ordering lock evaluations by key to avoid deadlocks.

How to Ace Concurrency in a 45-Minute Senior Interview

Proactive techniques that guarantee top marks on the technical rubric.

Proactive Senior Move

Do not wait for the interviewer to ask "Is this thread-safe?". Immediately after writing your core domain method, say: "Under concurrent traffic, this check-then-act section is susceptible to race conditions. I'm introducing an atomic lock or compare-and-swap check with lock ordering based on ID to avoid deadlock."

Instant Disqualification Trap

Saying "Node.js is single-threaded so race conditions don't exist in JavaScript." Async I/O interleaves asynchronous promises and creates severe asynchronous race conditions!
