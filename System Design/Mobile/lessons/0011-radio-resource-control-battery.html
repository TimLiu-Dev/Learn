Lesson 0011: Radio Resource Control (RRC) & Battery-Aware Mobile State Machines

Uncover how cellular modems actually consume battery. Understand the Radio Resource Control (RRC) state machine, eliminate disastrous tail energy waste, and architect packet coalescing and piggybacking pipelines.

1. The Cellular Radio Resource Control (RRC) State Machine

The cellular modem (baseband chip) in an Android phone is the single most power-hungry component next to the screen. To balance latency and battery, telecom networks use the 3GPP RRC state machine:

IDLE State (~5 mA)

The radio receiver is asleep. It cannot transmit data. Minimal power consumption.

FACH State (~120 mA)

Intermediate power state with low transmission bandwidth.

DCH State (~450 mA)

Full dedicated high-speed channel. Maximum power drain.

The Fatal "Tail Energy" Trap

When an app transmits even a single 1 KB packet, the radio ramps up from IDLE to DCH. When the transfer finishes, the radio does not drop back to IDLE immediately. It lingers in DCH for ~5 seconds, then FACH for ~10 seconds waiting for more packets (the tail state).

The Staff Math: If your app sends a tiny heartbeat every 15 seconds, the modem stays trapped in DCH/FACH 100% of the time, draining a 5000mAh battery in just a few hours!

2. Packet Coalescing & Request Piggybacking

To preserve battery life in FAANG applications (e.g. Uber driver tracking or Instagram telemetry), apply three patterns:

  • Burst Transmission: Rather than sending 10 packets spaced 10 seconds apart, buffer them in RAM and transmit all 10 in a single 2-second burst, allowing the radio to sleep for 98 seconds.
  • Piggybacking: When the user taps a button that triggers a network request (e.g. liking a post), wake up the telemetry buffer and attach queued logs to that same connection.
  • Motion-Adaptive Polling: When accelerometer/fused location detects the phone is stationary on a desk, reduce GPS and network polling frequency from 5s down to 15 minutes.

3. Interactive Practice: Simulate Radio Energy Consumption

Task: Implement calculateRadioEnergy(requests, tailDchSeconds = 5, tailFachSeconds = 10). Each request at time $t$ keeps the radio in DCH ($400\text{ mA}$) from $t$ until $t + \text{tailDchSeconds}$, followed by FACH ($100\text{ mA}$) for $\text{tailFachSeconds}$. Calculate the total milliampere-seconds ($\text{mA}\cdot\text{s}$) consumed across all intervals without double-counting overlapping times!

Radio Energy Simulator Sandbox
Hint 1: For a single request at $t=0$, DCH is active for $[0, 5)$ seconds ($5 \times 400 = 2000$), and FACH is active for $[5, 15)$ seconds ($10 \times 100 = 1000$). Total = $3000\text{ mA}\cdot\text{s}$.
Hint 2: For multiple requests, merge overlapping DCH intervals $[t_i, t_i + 5]$ and adjust FACH intervals accordingly.
Canonical Solution: 
function calculateRadioEnergy(requestTimestamps, tailDch = 5, tailFach = 10) {
  if (requestTimestamps.length === 0) return 0;
  
  // Track state second by second for up to the max window
  const maxTime = Math.max(...requestTimestamps) + tailDch + tailFach;
  const states = new Array(maxTime).fill(0); // 0=IDLE, 1=FACH, 2=DCH

  for (const t of requestTimestamps) {
    for (let s = t; s < t + tailDch; s++) {
      states[s] = 2; // DCH
    }
    for (let s = t + tailDch; s < t + tailDch + tailFach; s++) {
      if (states[s] < 2) states[s] = 1; // FACH
    }
  }

  let energy = 0;
  for (let s = 0; s < maxTime; s++) {
    if (states[s] === 2) energy += 400;
    else if (states[s] === 1) energy += 100;
  }
  return energy;
}
