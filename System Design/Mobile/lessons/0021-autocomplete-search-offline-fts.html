Lesson 0021: Typeahead Autocomplete Search, Prefix Tries & Offline SQLite FTS5

Architect lightning-fast search systems (Amazon, YouTube, Slack). Eliminate out-of-order search race conditions using debounce and flatMapLatest, build in-memory prefix tries for instant suggestions, and power offline search with SQLite FTS5.

1. The Out-Of-Order Search Race Condition

In an interview prompt like "Design Typeahead Autocomplete Search", the most common trap is firing un-throttled network requests on text changes.

The Inverted Query Race Hazard

User types "app", pauses briefly, then types "apple".

  • Request 1 ("app") routes through a slow cell tower and takes 400ms.
  • Request 2 ("apple") routes fast through edge cache and returns in 80ms.
  • Request 2 renders results for "apple" first. 300ms later, Request 1 resolves and overwrites the screen with results for "app"!

The Solution: Debounce + flatMapLatest

Production search view models pipe text emissions through two critical Coroutine operators: 

[User Types in Compose TextField]
        │
        ▼ (Flow of Raw Strings: "a", "ap", "app", "appl", "apple")
[debounce(300.milliseconds)] ── (Drops rapid keystrokes; waits for 300ms typing pause)
        │
        ▼
[distinctUntilChanged()] ────── (Ignores duplicate triggers)
        │
        ▼
[flatMapLatest { query ->       (AUTOMATICALLY CANCELS the prior in-flight search coroutine!)
    repository.search(query)
}]
        │
        ▼
[StateFlow<SearchUiState>] ──► [Instant, Causal UI Render]

2. In-Memory Prefix Trie vs. SQLite FTS5 Full-Text Search

To deliver sub-10ms suggestion rendering while offline, clients maintain a dual-layer search cache:

1. In-Memory Prefix Trie (Suggestions)

Stores recent searches and popular keywords in an in-memory Trie (Prefix Tree). Traversing the Trie takes $O(L)$ time where $L$ is the length of the prefix (independent of catalog size), returning top 5 suggestions instantly with zero disk I/O.

2. SQLite FTS5 (Offline Document Search)

For full text search across thousands of offline messages or notes, standard SQLite LIKE '%query%' performs full table scans ($O(N)$). SQLite FTS5 builds inverted indexes with BM25 ranking, tokenizing words and supporting prefix queries: SELECT * FROM fts_messages WHERE fts_messages MATCH 'andr*' ORDER BY rank in $O(\log N)$.

4. Production Kotlin 2.x Search ViewModel

package com.systemdesign.search.presentation

import androidx.lifecycle.ViewModel
import androidx.lifecycle.viewModelScope
import kotlinx.coroutines.FlowPreview
import kotlinx.coroutines.ExperimentalCoroutinesApi
import kotlinx.coroutines.flow.*
import kotlin.time.Duration.Companion.milliseconds

data class SearchUiState(
    val query: String = "",
    val suggestions: List<String> = emptyList(),
    val results: List<SearchResultItem> = emptyList(),
    val isLoading: Boolean = false
)

class SearchViewModel(
    private val localTrie: PrefixTrie,
    private val ftsDao: MessageFtsDao,
    private val searchApi: SearchApiService
) : ViewModel() {

    private val _searchQuery = MutableStateFlow("")

    @OptIn(FlowPreview::class, ExperimentalCoroutinesApi::class)
    val uiState: StateFlow<SearchUiState> = _searchQuery
        .debounce(300.milliseconds)
        .distinctUntilChanged()
        .flatMapLatest { query ->
            if (query.isBlank()) {
                flowOf(SearchUiState())
            } else {
                flow {
                    // 1. Instant local suggestions (< 5ms)
                    val localSuggestions = localTrie.searchPrefix(query, limit = 5)
                    emit(SearchUiState(query = query, suggestions = localSuggestions, isLoading = true))

                    // 2. Fetch remote authoritative results (cancels automatically if user types)
                    val remoteResults = try {
                        searchApi.queryCatalog(query)
                    } catch (e: Exception) {
                        // Fallback to offline SQLite FTS5 database on network failure
                        ftsDao.searchMessagesFts("$query*")
                    }

                    emit(SearchUiState(
                        query = query,
                        suggestions = localSuggestions,
                        results = remoteResults,
                        isLoading = false
                    ))
                }
            }
        }
        .stateIn(
            scope = viewModelScope,
            started = SharingStarted.WhileSubscribed(5000),
            initialValue = SearchUiState()
        )

    fun onQueryChanged(newQuery: String) {
        _searchQuery.value = newQuery
    }
}

5. Interactive Practice: In-Memory Prefix Trie Search

Task: Implement PrefixTrie.
• insert(word, frequency): Inserts word into the trie with a search frequency weight.
• search(prefix, limit = 3): Returns array of words matching the prefix, sorted by descending frequency (highest frequency first).

Prefix Trie Sandbox
Hint 1: In insert, iterate chars: if (!curr.children[c]) curr.children[c] = new TrieNode(); curr = curr.children[c];. At end, set curr.isWord = true; curr.word = word; curr.frequency = frequency;.
Hint 2: In search, find prefix node. Use DFS helper collect(node, list) to collect all { word, frequency } objects. Sort by b.frequency - a.frequency and slice 0, limit.
Canonical Staff-Level Solution: 
class TrieNode {
  constructor() {
    this.children = {};
    this.isWord = false;
    this.word = null;
    this.frequency = 0;
  }
}

class PrefixTrie {
  constructor() {
    this.root = new TrieNode();
  }

  insert(word, frequency = 1) {
    let curr = this.root;
    for (const char of word) {
      if (!curr.children[char]) {
        curr.children[char] = new TrieNode();
      }
      curr = curr.children[char];
    }
    curr.isWord = true;
    curr.word = word;
    curr.frequency = frequency;
  }

  search(prefix, limit = 3) {
    let curr = this.root;
    for (const char of prefix) {
      if (!curr.children[char]) return [];
      curr = curr.children[char];
    }

    const matches = [];
    function collect(node) {
      if (node.isWord) {
        matches.push({ word: node.word, frequency: node.frequency });
      }
      for (const char in node.children) {
        collect(node.children[char]);
      }
    }
    collect(curr);

    matches.sort((a, b) => b.frequency - a.frequency);
    return matches.slice(0, limit).map(m => m.word);
  }
}

6. Senior Architecture Calibration Quizzes

Question 1: In a mobile search autocomplete pipeline, what is the crucial architectural purpose of using flatMapLatest over flatMapMerge?
A flatMapLatest allocates native C++ memory buffers to bypass Android Dalvik heap limits.
B It cancels in-flight queries when new text is typed, preventing stale result overwrites.
C It automatically encrypts search query strings using AES-256 before transmission.
D It converts the database schema to read-only mode to prevent SQLite table locks.
Comprehensive Option Breakdown:
  • Option A (Wrong): Coroutine operators operate within the JVM coroutine runtime, not native C++ allocators.
  • Option B (Correct): When the user types a new character, flatMapLatest immediately cancels the coroutine running the search for the previous character. This eliminates race conditions.
  • Option C (Wrong): Stream operators do not perform TLS cryptographic encryption.
  • Option D (Wrong): Coroutine operators have no direct coupling with database table locking.
Question 2: Why do Big-Tech messaging applications (e.g. Slack, WhatsApp) utilize SQLite FTS5 virtual tables rather than standard SQL LIKE '%query%' queries for local message search?
A Android OS has deprecated standard SQL SELECT statements in Room SQLite database.
B SQLite FTS5 reduces database file storage size on disk by compressing text using GZIP.
C LIKE '%query%' forces O(N) table scans; FTS5 uses inverted indexes with BM25 ranking.
D Room ORM does not support Kotlin Coroutine Flow observation on regular tables.
Comprehensive Option Breakdown:
  • Option A (Wrong): Standard SQL statements remain fully supported in SQLite.
  • Option B (Wrong): FTS indexes increase disk usage slightly due to auxiliary postings lists.
  • Option C (Correct): Leading wildcards (%query%) cannot use B-tree indices, causing linear full-disk scans that freeze the device on large databases. FTS5 builds an inverted index with $O(\log N)$ token lookups.
  • Option D (Wrong): Room Flow works on both standard and FTS tables.
