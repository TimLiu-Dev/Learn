Lesson 0023: Background Audio Streaming, MediaSessionService & Offline Downloader

Architect mission-critical background audio playback and offline download systems (Spotify, Apple Music, Podcasts). Master AndroidX MediaSessionService, Audio Focus state machines (ducking vs pausing), lock-screen controls, and HTTP Range downloads.

1. Background Playback: MediaSessionService Architecture

In an interview prompt like "Design Spotify Mobile App", junior candidates create an audio player inside an Activity or ViewModel. When the user locks the phone or switches apps, the OS pauses the process and audio halts!

The Decoupled Media3 Session Pattern

To ensure playback continues indefinitely with the screen locked while meeting Android 14/15/16 Foreground Service restrictions:

The audio player runs inside an androidx.media3.session.MediaSessionService running a Foreground Service with type FOREGROUND_SERVICE_MEDIA_PLAYBACK. The UI connects via a lightweight MediaController, enabling the Activity to be created and destroyed without touching the audio engine!

2. Audio Focus State Machine: Ducking vs. Pausing

Android and iOS are multi-application operating systems. When competing audio events occur (e.g. navigation prompts, phone calls, or video ads), the app must respond to Audio Focus changes:

Audio Focus Event Real-World Trigger Required Mobile Action
AUDIOFOCUS_LOSS User starts a YouTube video or another music app Stop playback immediately and release audio focus. Do not resume automatically.
AUDIOFOCUS_LOSS_TRANSIENT Incoming phone call or alarm ring Pause playback temporarily. Save state and resume automatically when focus returns.
AUDIOFOCUS_LOSS_TRANSIENT_CAN_DUCK Turn-by-turn navigation voice or text notification chime Lower music volume by 80% (Duck). Restore full volume once navigation finishes speaking.
AUDIOFOCUS_GAIN Phone call ended or transient interruption finished Restore volume to 100% or unpause playback if previously playing.

4. Production Kotlin 2.x MediaSessionService

package com.systemdesign.audio.playback

import android.app.PendingIntent
import android.content.Intent
import androidx.media3.common.AudioAttributes
import androidx.media3.common.C
import androidx.media3.exoplayer.ExoPlayer
import androidx.media3.session.MediaSession
import androidx.media3.session.MediaSessionService

class BackgroundAudioService : MediaSessionService() {

    private var mediaSession: MediaSession? = null
    private lateinit var player: ExoPlayer

    override fun onCreate() {
        super.onCreate()

        // 1. Configure audio attributes for automatic audio focus handling
        val audioAttributes = AudioAttributes.Builder()
            .setUsage(C.USAGE_MEDIA)
            .setContentType(C.AUDIO_CONTENT_TYPE_MUSIC)
            .build()

        player = ExoPlayer.Builder(this)
            .setAudioAttributes(audioAttributes, /* handleAudioFocus = */ true)
            .setHandleAudioBecomingNoisy(true) // Automatically pauses when headphones unplugged!
            .build()

        // 2. Open MainActivity on notification tap
        val sessionActivityPendingIntent = PendingIntent.getActivity(
            this, 0,
            Intent(this, Class.forName("com.systemdesign.MainActivity")),
            PendingIntent.FLAG_IMMUTABLE
        )

        mediaSession = MediaSession.Builder(this, player)
            .setSessionActivity(sessionActivityPendingIntent)
            .build()
    }

    override fun onGetSession(controllerInfo: MediaSession.ControllerInfo): MediaSession? {
        return mediaSession
    }

    override fun onDestroy() {
        mediaSession?.run {
            player.release()
            release()
            mediaSession = null
        }
        super.onDestroy()
    }
}

5. Interactive Practice: Audio Focus State Machine

Task: Implement AudioFocusStateMachine.
• Initial state: state = 'STOPPED', volume = 1.0.
• play(): Sets state = 'PLAYING', volume = 1.0.
• onFocusChange(event):
  • 'LOSS': Sets state = 'STOPPED', volume = 1.0.
  • 'LOSS_TRANSIENT': If was PLAYING, sets state = 'PAUSED_TRANSIENT'.
  • 'LOSS_TRANSIENT_CAN_DUCK': If was PLAYING, sets state = 'DUCKED', volume = 0.2.
  • 'GAIN': If was PAUSED_TRANSIENT, resumes PLAYING. If was DUCKED, restores volume = 1.0, sets PLAYING.
Return { state: this.state, volume: this.volume }.

Audio Focus State Machine Sandbox
Hint 1: Handle LOSS by setting this.state = 'STOPPED'; this.volume = 1.0;. Handle LOSS_TRANSIENT only if state was PLAYING.
Hint 2: In LOSS_TRANSIENT_CAN_DUCK, set this.state = 'DUCKED'; this.volume = 0.2;. In GAIN, restore volume to 1.0 and state to PLAYING.
Canonical Staff-Level Solution: 
class AudioFocusStateMachine {
  constructor() {
    this.state = 'STOPPED';
    this.volume = 1.0;
  }

  play() {
    this.state = 'PLAYING';
    this.volume = 1.0;
    return { state: this.state, volume: this.volume };
  }

  onFocusChange(event) {
    switch (event) {
      case 'LOSS':
        this.state = 'STOPPED';
        this.volume = 1.0;
        break;
      case 'LOSS_TRANSIENT':
        if (this.state === 'PLAYING') {
          this.state = 'PAUSED_TRANSIENT';
        }
        break;
      case 'LOSS_TRANSIENT_CAN_DUCK':
        if (this.state === 'PLAYING') {
          this.state = 'DUCKED';
          this.volume = 0.2;
        }
        break;
      case 'GAIN':
        if (this.state === 'PAUSED_TRANSIENT' || this.state === 'DUCKED') {
          this.state = 'PLAYING';
          this.volume = 1.0;
        }
        break;
    }
    return { state: this.state, volume: this.volume };
  }
}

6. Senior Architecture Calibration Quizzes

Question 1: In audio streaming systems like Spotify, why must player playback be hosted inside a MediaSessionService rather than an Activity or ViewModel?
A OkHttp network sockets cannot download MP3 audio bytes outside of MediaSessionService.
B It runs a Foreground Service that survives screen-off and UI Activity destruction.
C Room SQLite databases lock in read-only mode whenever an Activity is paused.
D MediaSessionService completely eliminates all JVM garbage collection pauses.
Comprehensive Option Breakdown:
  • Option A (Wrong): OkHttp operates in any background coroutine.
  • Option B (Correct): When the user locks their screen or switches apps, Activities are stopped and can be destroyed. A Foreground Service with FOREGROUND_SERVICE_MEDIA_PLAYBACK informs the Android OS that active audio is playing, preventing the system from freezing the audio pipeline.
  • Option C (Wrong): Room has no such restriction.
  • Option D (Wrong): MediaSessionService does not eliminate GC pauses.
Question 2: When an audio app receives AUDIOFOCUS_LOSS_TRANSIENT_CAN_DUCK during playback, what is the expected Staff-level architectural response?
A Terminate the background player service and release all hardware decoders.
B Throw an IllegalStateException to notify Android OS of audio channel conflict.
C Temporarily duck (lower) music volume to ~20%, restoring full volume on GAIN.
D Ignore the event and continue playing music at 100% volume through the speakers.
Comprehensive Option Breakdown:
  • Option A (Wrong): Stopping playback completely creates an annoying abrupt cut for transient sounds like navigation prompts.
  • Option B (Wrong): Focus changes are normal events, not fatal error conditions.
  • Option C (Correct): "Ducking" reduces the player volume by ~80% so the user clearly hears the navigation prompt ("In 200 feet, turn left"), and smoothly fades the music back to 100% when AUDIOFOCUS_GAIN arrives.
  • Option D (Wrong): Playing full volume over navigation instructions ruins the user experience.
