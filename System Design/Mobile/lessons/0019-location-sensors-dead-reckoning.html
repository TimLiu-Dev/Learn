Lesson 0019: Continuous Location Tracking, Sensor Fusion & Dead Reckoning

Architect mission-critical real-time navigation and delivery tracking (Uber, Google Maps, DoorDash). Master the ActivityTransition API for battery savings, Kalman filtering for urban canyon GPS jitter, and IMU-driven Dead Reckoning during tunnel signal loss.

1. The Power-Accuracy Trade-Off & Activity Gating

Running continuous GPS hardware (GNSS chip) drains 15% to 25% battery per hour and rapidly overheats mobile devices. Staff Mobile Engineers never query raw GPS at a fixed 1Hz rate indefinitely.

1. ActivityTransition API Gating

Uses low-power on-chip hardware coprocessors (pedometer and accelerometer) to detect activity states: STILL, WALKING, IN_VEHICLE. When a driver is parked or waiting at a light (STILL), GPS tracking is completely put to sleep, reducing idle battery draw by up to 85%!

2. Speed-Adaptive Polling

Instead of time-based polling (e.g. every 1 second), the client adjusts displacement intervals:
• Speed > 60 km/h: Poll every 25 meters ($1.5\text{s}$)
• Speed < 20 km/h: Poll every 10 meters ($2.0\text{s}$)
• Stationary: Sleep until motion transition fires.

2. Kalman Filtering for Urban Canyons & Dead Reckoning in Tunnels

In real-world mobile deployments, two severe physical phenomena distort GPS:

Urban Canyons & Multipath Distortion

In cities with glass skyscrapers (Manhattan, Tokyo, San Francisco), satellite signals reflect off glass facades before reaching the phone antenna (multipath reflection). This causes raw GPS coordinates to jitter wildly across adjacent streets ($\pm 80\text{ meters}$).

The Staff Solution: A Kalman Filter fuses noisy GPS coordinates with a physical motion model (velocity and heading). It assigns higher weight to the physics model when GPS horizontal accuracy estimates ($\sigma$) degrade.

Dead Reckoning During Tunnel Blackouts

When entering an underground tunnel, satellite SNR drops to zero. The client activates Dead Reckoning: 

[GPS Satellite Signal Drops to 0]
      │
      ▼
[Activate IMU Sensor Fusion at 60 FPS]
      │
      ├── Gyroscope ────────► Heading change (Δθ)
      ├── Accelerometer ────► Linear forward acceleration (a)
      └── Speedometer ──────► Estimated velocity (v = v₀ + a · Δt)
      │
      ▼
[Compute New Lat/Lng: (lat + Δlat, lng + Δlng)] ──► Smooth vehicle movement on map!

4. Production Kotlin 2.x Fused Location Engine

package com.systemdesign.location.engine

import android.annotation.SuppressLint
import android.content.Context
import android.location.Location
import com.google.android.gms.location.*
import kotlinx.coroutines.channels.awaitClose
import kotlinx.coroutines.flow.Flow
import kotlinx.coroutines.flow.callbackFlow

class BatteryAwareLocationEngine(private val context: Context) {
    private val fusedClient: FusedLocationProviderClient = 
        LocationServices.getFusedLocationProviderClient(context)

    @SuppressLint("MissingPermission")
    fun observeDriverLocation(isHighSpeedMode: Boolean): Flow<Location> = callbackFlow {
        val intervalMs = if (isHighSpeedMode) 1500L else 4000L
        val minDistanceMeters = if (isHighSpeedMode) 20f else 5f

        val request = LocationRequest.Builder(Priority.PRIORITY_HIGH_ACCURACY, intervalMs)
            .setMinUpdateIntervalMillis(1000L)
            .setMinUpdateDistanceMeters(minDistanceMeters)
            .setGranularity(Granularity.GRANULARITY_FINE)
            .build()

        val callback = object : LocationCallback() {
            override fun onLocationResult(result: LocationResult) {
                result.lastLocation?.let { rawLocation ->
                    // Filter out readings with unacceptable horizontal accuracy (> 30 meters)
                    if (rawLocation.hasAccuracy() && rawLocation.accuracy <= 30f) {
                        trySend(rawLocation)
                    }
                }
            }
        }

        fusedClient.requestLocationUpdates(request, callback, context.mainLooper)

        awaitClose {
            fusedClient.removeLocationUpdates(callback)
        }
    }
}

5. Interactive Practice: 1D Kalman Filter for GPS Smoothing

Task: Implement KalmanCoordinateFilter.
• constructor(processNoiseQ = 1.0, measurementNoiseR = 4.0): Initializes noise parameters.
• filter(measurement): Updates estimated position ($x$) and variance ($p$) using the 1D Kalman equations:
  1. Predict: $p = p + Q$
  2. Kalman Gain: $K = p / (p + R)$
  3. Update estimate: $x = x + K \times (\text{measurement} - x)$
  4. Update variance: $p = (1 - K) \times p$
Return the smoothed estimate $x$ rounded to 2 decimal places.

Kalman Filter Sandbox
Hint 1: On first call when this.x === null, set this.x = measurement and return measurement.
Hint 2: Follow the 4 formulas: this.p += this.Q, const K = this.p / (this.p + this.R), this.x += K * (measurement - this.x), this.p = (1 - K) * this.p.
Canonical Staff-Level Solution: 
class KalmanCoordinateFilter {
  constructor(processNoiseQ = 1.0, measurementNoiseR = 4.0) {
    this.Q = processNoiseQ;
    this.R = measurementNoiseR;
    this.x = null;
    this.p = 1.0;
  }

  filter(measurement) {
    if (this.x === null) {
      this.x = measurement;
      return measurement;
    }

    // 1. Predict
    this.p += this.Q;

    // 2. Compute Kalman Gain
    const K = this.p / (this.p + this.R);

    // 3. Update estimate
    this.x = this.x + K * (measurement - this.x);

    // 4. Update variance
    this.p = (1 - K) * this.p;

    return Math.round(this.x * 100) / 100;
  }
}

6. Senior Architecture Calibration Quizzes

Question 1: In a real-time driver delivery application (e.g. Uber Driver), what is the most battery-efficient technique to handle prolonged stationary parking periods?
A Continue polling FusedLocationProviderClient at 1-second intervals continuously.
B Gate GPS polling behind ActivityTransitionClient STILL motion events to sleep GNSS.
C Programmatically disable device Wi-Fi and Bluetooth antennas via root Linux shell.
D Set an inexact repeating AlarmManager alarm to ping GPS hardware every 60 seconds.
Comprehensive Option Breakdown:
  • Option A (Wrong): Continuous GNSS polling rapidly depletes battery and overheats phone silicon.
  • Option B (Correct): ActivityTransitionClient relies on the dedicated sensor hub chip (consuming micro-amps). When the user is stationary (STILL), the app suspends GPS entirely.
  • Option C (Wrong): Third-party apps cannot toggle device Wi-Fi/Bluetooth hardware.
  • Option D (Wrong): Waking the CPU every 60s prevents device deep sleep without providing real-time accuracy.
Question 2: If an enterprise retail app needs to trigger push notifications across 10,000 store locations worldwide, how must geofencing be architected given Android OS hardware constraints?
A Register all 10,000 geofence coordinates directly with Google GeofencingClient.
B Launch a permanent foreground service to calculate Euclidean distances to all 10,000 stores.
C Store stores in SQLite R-Tree/Geohashes; register only the ~20 nearest to current location.
D Intercept raw cellular baseband satellite packets via a custom BroadcastReceiver.
Comprehensive Option Breakdown:
  • Option A (Wrong): Android limits apps to 100 active geofences in hardware memory. Registering 10,000 fails immediately.
  • Option B (Wrong): Calculating 10,000 Euclidean distances every second on the main CPU drains battery and triggers system throttling.
  • Option C (Correct): Maintain the full list of stores in a local SQLite spatial index (R-Tree or Geohash). As the user travels, dynamically query and register only the 20 to 50 nearest locations with the OS Geofencing API.
  • Option D (Wrong): Third-party applications have no access to baseband radio packets.
