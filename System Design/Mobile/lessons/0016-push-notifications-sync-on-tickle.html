Lesson 0016: Real-Time Push Notifications, Sync-on-Tickle & Background Constraints

Architect mission-critical real-time message delivery (WhatsApp, Slack, Uber). Master the battle-tested Sync-on-Tickle pattern, navigate Android 15/16 Foreground Service restrictions, eliminate duplicate push deliveries, and maintain reliable sync under aggressive OS battery throttling.

1. The Anti-Pattern of Full-Payload Push: Why "Sync-on-Tickle" Wins

In messaging system design interviews (e.g. "Design Slack or WhatsApp Mobile"), junior candidates frequently suggest transmitting the entire chat message (sender, text, media metadata, reactions) directly inside the Firebase Cloud Messaging (FCM) or Apple Push Notification service (APNs) payload.

Why Full-Payload Push Fails at Scale
  • Payload Size Limits: FCM caps payload data at 4 KB; APNs caps notification payloads at 4 KB. Group chats with thread metadata, mention entities, or media attachments immediately exceed this budget.
  • Unreliable & Out-of-Order Delivery: Neither Google nor Apple guarantees FIFO ordering for push deliveries. If a user receives message #5 before message #4, the local database becomes causally corrupt.
  • OS Packet Dropping & Throttling: When a device is in Doze mode or has poor network connectivity, mobile operating systems drop or aggregate background data pushes.

The Staff-Level Solution: The Sync-on-Tickle (Push-to-Sync) Pattern 

[App Server] ── (1. High-Priority Push Notification) ──► [Google FCM / Apple APNs]
      │                                                               │
      │                                                               ▼
      │                                                  [Device OS Push Daemon]
      │                                                               │
      │                                                               ▼
      │                                                [FCM Service: onMessageReceived]
      │                                                               │ (Extracts: { seq: 4028 })
      │                                                               ▼
      │                                            [WorkManager / Network Coroutine]
      │                                                               │
      │ ◄── (2. Pull Missing Delta: GET /v1/messages?since=4027) ────┘
      │
      ▼
(3. Deterministic Batch of Ordered Messages) ──► [Room SQLite WAL DB] ──► [Compose UI Flow]

Instead of carrying message content, the push packet acts strictly as a lightweight "Tickle" containing only a sequence pointer (e.g., { "channel_id": "c_99", "latest_seq": 4028 }). The client then connects to its trusted API or WebSocket endpoint to pull ordered, authenticated, and compressed deltas.

2. OS Background Execution Quotas & iOS Parity

Modern mobile operating systems strictly restrict what client apps can do upon receiving a push notification when the app is in the background or killed:

Android (2027 Standards) WorkManager
  • Data Push vs Notification Push: High-priority data messages grant ~10–30 seconds of CPU execution to invoke WorkManager.enqueue(Expedited).
  • Foreground Service Restrictions: Starting in Android 14/15/16, apps cannot launch background Foreground Services unless categorized under strict system types (e.g. FOREGROUND_SERVICE_REMOTE_MESSAGING) and granted runtime notification permissions.
  • Doze Quotas: Apps receive a limited budget of high-priority messages per day. Overusing push causes the OS to silently downgrade pushes to normal priority.
iOS Counterpart (Cross-Platform Parity) APNs & Extensions
  • Notification Service Extension (NSE): iOS launches a separate lightweight process for exactly 30 seconds before displaying the notification banner. This is where media is downloaded and encrypted payloads are decrypted.
  • Silent Push (content-available: 1): Wakes the app in the background for max 30s. Throttled heavily by iOS if battery is low or if the app is infrequently opened.
  • Background Tasks: Uses BGAppRefreshTask to batch periodic reconciliations when the user connects to power.

3. Production Kotlin 2.x Push-to-Sync Service

package com.systemdesign.messaging.push

import android.content.Context
import androidx.work.*
import com.google.firebase.messaging.FirebaseMessagingService
import com.google.firebase.messaging.RemoteMessage
import java.util.concurrent.TimeUnit

class PushNotificationReceiverService : FirebaseMessagingService() {

    override fun onMessageReceived(remoteMessage: RemoteMessage) {
        val data = remoteMessage.data
        val channelId = data["channel_id"] ?: return
        val latestSequence = data["latest_seq"]?.toLongOrNull() ?: return

        // Check if app is in active foreground session
        if (AppLifecycleTracker.isForeground) {
            // Hot stream update via existing WebSocket or active CoroutineScope
            ActiveSocketSyncManager.triggerImmediateDeltaSync(channelId, latestSequence)
        } else {
            // App is in background or killed: Schedule Expedited WorkRequest
            scheduleExpeditedDeltaSync(applicationContext, channelId, latestSequence)
        }
    }

    private fun scheduleExpeditedDeltaSync(context: Context, channelId: String, sequence: Long) {
        val constraints = Constraints.Builder()
            .setRequiredNetworkType(NetworkType.CONNECTED)
            .build()

        val syncWork = OneTimeWorkRequestBuilder<MessageDeltaSyncWorker>()
            .setExpedited(OutOfQuotaPolicy.RUN_AS_NON_EXPEDITED_WORK_REQUEST)
            .setConstraints(constraints)
            .setInputData(workDataOf(
                "channel_id" to channelId,
                "target_seq" to sequence
            ))
            .setBackoffCriteria(BackoffPolicy.EXPONENTIAL, 10, TimeUnit.SECONDS)
            .build()

        WorkManager.getInstance(context)
            .enqueueUniqueWork("sync_$channelId", ExistingWorkPolicy.KEEP, syncWork)
    }

    override fun onNewToken(token: String) {
        // Upload token to auth user registration backend with hardware device ID
        DeviceTokenRepository.registerPushToken(token)
    }
}

4. Interactive Practice: Push Notification Deduplication & Ordering Buffer

Task: In mobile messaging, push notifications may arrive out-of-order or duplicate due to network re-transmissions. Implement PushOrderingBuffer:
• processPush(msgId, seqNum, payload): Ignores duplicate msgId. Stores messages. If the sequence number is the immediate next expected sequence (currentSeq + 1), advances the stream and returns all continuous queued messages in order.
• If a gap exists (e.g., receives seq 4 when expecting seq 2), buffers seq 4 and returns an empty list [] until the missing messages arrive.

Push Deduplication & Reordering Sandbox
Hint 1: First check if (this.seenIds.has(msgId)) return []; and this.seenIds.add(msgId);. Also ignore if seqNum <= this.currentSeq.
Hint 2: Store into this.buffer.set(seqNum, payload). Then run a while (this.buffer.has(this.currentSeq + 1)) loop, advancing this.currentSeq++, deleting from the map, and pushing the payload into the results array.
Canonical Staff-Level Solution: 
class PushOrderingBuffer {
  constructor(initialSeq = 0) {
    this.currentSeq = initialSeq;
    this.seenIds = new Set();
    this.buffer = new Map(); // seq -> payload
  }

  processPush(msgId, seqNum, payload) {
    if (this.seenIds.has(msgId) || seqNum <= this.currentSeq) {
      return [];
    }
    this.seenIds.add(msgId);
    this.buffer.set(seqNum, payload);

    const readyMessages = [];
    while (this.buffer.has(this.currentSeq + 1)) {
      this.currentSeq++;
      readyMessages.push(this.buffer.get(this.currentSeq));
      this.buffer.delete(this.currentSeq);
    }
    return readyMessages;
  }
}

5. Senior Architecture Calibration Quizzes

Question 1: You are designing a mobile chat application (e.g. Slack or WhatsApp). Why is sending full message payloads directly via FCM data messages considered an anti-pattern at Big-Tech scale?
A Push notification gateways do not support modern TLS 1.3 socket encryption protocols.
B Gateways have strict 4KB limits, lack FIFO ordering, and may drop packets in Doze.
C Android Play Services crashes with OutOfMemoryError if receiving JSON strings above 1KB.
D Room SQLite database drivers refuse to persist text payloads received via push broadcasts.
Comprehensive Option Breakdown:
  • Option A (Wrong): Push gateways use standard TLS 1.3; encryption is not the bottleneck.
  • Option B (Correct): Both FCM and APNs enforce a hard 4KB payload cap, do not guarantee delivery order, and throttle delivery when the device enters low-power Doze states. The Sync-on-Tickle pattern completely circumvents these issues.
  • Option C (Wrong): Google Play Services runs in its own process and easily handles payloads without memory issues.
  • Option D (Wrong): SQLite has no restriction on inserting data from push receivers.
Question 2: When an Android app receives a high-priority data push while killed in the background, what is the correct 2027 mechanism to perform an immediate network delta sync?
A Launch a standard Foreground Service with a sticky persistent notification from the receiver.
B Block the main thread inside onMessageReceived() using Thread.sleep() until sync completes.
C Dispatch an Expedited WorkRequest via WorkManager to run within system background quotas.
D Schedule an inexact AlarmManager alarm with setAndAllowWhileIdle() for 15 minutes later.
Comprehensive Option Breakdown:
  • Option A (Wrong): Calling startForegroundService() from the background triggers ForegroundServiceStartNotAllowedException on Android 14, 15, and 16.
  • Option B (Wrong): Blocking the broadcast receiver thread triggers an immediate Application Not Responding (ANR) crash.
  • Option C (Correct): WorkManager.enqueue(Expedited) allows the OS to immediately execute the task within an allocated high-priority quota without violating background service restrictions.
  • Option D (Wrong): Inexact alarms introduce a 15-minute latency delay, destroying the real-time chat experience.
