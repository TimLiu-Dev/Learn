Lesson 0022: Resumable Chunked Media Upload Pipeline & On-Device Transcoding

Architect bulletproof large media upload pipelines (YouTube, WhatsApp, Instagram). Master S3 Multipart / TUS resumable chunking, survive OS process termination using WorkManager, generate SHA-256 checksums, and transcode video with AndroidX Media3 Transformer.

1. Why Monolithic File Uploads Fail on Mobile

In an interview prompt like "Design YouTube Video Upload" or "Design WhatsApp Media Sharing", naive candidates upload video files via a single monolithic POST /v1/videos/upload HTTP multipart request.

The 99% Upload Failure Trap

Uploading a 500 MB video on a 4G/5G connection takes 60–120 seconds. On mobile:

  • A subway tunnel or cellular cell handover causes a temporary TCP socket timeout.
  • The user switches apps to answer a phone call, and Android kills the app process to free RAM.
  • With a monolithic upload, the connection resets at 95% completion (475 MB uploaded). All 475 MB are lost, forcing the user to restart from 0 MB!

The Solution: S3 Multipart / TUS Chunked Resumption

The client slices the file into uniform 5 MB chunks, uploading each chunk independently with an idempotency sequence: 

[Raw 50MB Video File]
        │
        ├── Split into [Part 1 (5MB)] ──► PUT /upload?part=1 ──► 200 OK (ETag: "abc") ──► [Save in Room DB]
        ├── Split into [Part 2 (5MB)] ──► PUT /upload?part=2 ──► 200 OK (ETag: "def") ──► [Save in Room DB]
        ├── Split into [Part 3 (5MB)] ──► Network Drops! (Socket Reset)
        │
[App Process Dies / Phone Reconnects to Wi-Fi]
        │
        ▼ (WorkManager queries Room DB: Parts 1 & 2 Completed!)
Resumes upload strictly starting from [Part 3] ──► Zero wasted bytes!

2. On-Device Transcoding (AndroidX Media3 Transformer)

Modern phone cameras record 4K at 60 FPS in ProRes or uncompressed H.264, generating files larger than 2 GB for a 3-minute clip.

1. Pre-Upload Compression

Using androidx.media3.transformer.Transformer, the client leverages on-device hardware encoders (HEVC / H.265) to transcode 4K video to 1080p with a target bitrate of 6 Mbps. This shrinks a 2 GB video down to 150 MB before touching the network, reducing upload time by 90%!

2. SHA-256 Chunk Verification

To prevent bit-rot and corrupted frame uploads, the client computes an SHA-256 or MD5 hash for each 5 MB slice. The hash is sent in the Content-MD5 header so the storage CDN validates byte integrity before accepting each part.

4. Production Kotlin 2.x Chunked Upload Worker

package com.systemdesign.upload.pipeline

import android.content.Context
import androidx.work.CoroutineWorker
import androidx.work.WorkerParameters
import java.io.File
import java.io.RandomAccessFile

class ChunkedMediaUploadWorker(
    context: Context,
    params: WorkerParameters,
    private val uploadDao: UploadPartDao,
    private val s3Api: StorageUploadApi
) : CoroutineWorker(context, params) {

    companion object {
        const val CHUNK_SIZE_BYTES = 5L * 1024L * 1024L // 5 MB chunks
    }

    override suspend fun doWork(): Result {
        val fileUri = inputData.getString("file_path") ?: return Result.failure()
        val uploadSessionId = inputData.getString("session_id") ?: return Result.failure()
        val file = File(fileUri)
        val totalBytes = file.length()
        val totalChunks = ((totalBytes + CHUNK_SIZE_BYTES - 1) / CHUNK_SIZE_BYTES).toInt()

        val completedParts = uploadDao.getCompletedParts(uploadSessionId).associateBy { it.partNumber }

        RandomAccessFile(file, "r").use { raf ->
            for (partNumber in 1..totalChunks) {
                // If part already uploaded in previous session, skip!
                if (completedParts.containsKey(partNumber)) continue

                val startOffset = (partNumber - 1) * CHUNK_SIZE_BYTES
                val currentChunkSize = minOf(CHUNK_SIZE_BYTES, totalBytes - startOffset)
                val buffer = ByteArray(currentChunkSize.toInt())

                raf.seek(startOffset)
                raf.readFully(buffer)

                // Upload individual 5MB part
                val etag = try {
                    s3Api.uploadPart(uploadSessionId, partNumber, buffer)
                } catch (e: Exception) {
                    return Result.retry() // Triggers WorkManager exponential backoff
                }

                // Persist part completion in local database
                uploadDao.insertPart(UploadPartEntity(uploadSessionId, partNumber, etag))
            }
        }

        // Finalize multi-part upload session on server
        s3Api.completeMultipartUpload(uploadSessionId, uploadDao.getAllParts(uploadSessionId))
        return Result.success()
    }
}

5. Interactive Practice: Chunked Upload Resumption Tracker

Task: Implement ChunkedUploadTracker.
• constructor(totalSizeBytes, chunkSize = 5000000): Calculates total chunk count.
• markPartCompleted(partNum): Records part as finished.
• getPendingPartNumbers(): Returns array of part numbers (1-indexed) that still need uploading.
• getProgressPercentage(): Returns integer 0–100 representing upload progress percentage based on completed parts.

Upload Resumption Tracker Sandbox
Hint 1: In markPartCompleted, check if (partNum >= 1 && partNum <= this.totalParts) this.completedParts.add(partNum);.
Hint 2: In getProgressPercentage, compute Math.floor((this.completedParts.size / this.totalParts) * 100).
Canonical Staff-Level Solution: 
class ChunkedUploadTracker {
  constructor(totalSizeBytes, chunkSize = 5000000) {
    this.totalSizeBytes = totalSizeBytes;
    this.chunkSize = chunkSize;
    this.totalParts = Math.ceil(totalSizeBytes / chunkSize);
    this.completedParts = new Set();
  }

  markPartCompleted(partNum) {
    if (partNum >= 1 && partNum <= this.totalParts) {
      this.completedParts.add(partNum);
    }
  }

  getPendingPartNumbers() {
    const pending = [];
    for (let i = 1; i <= this.totalParts; i++) {
      if (!this.completedParts.has(i)) {
        pending.push(i);
      }
    }
    return pending;
  }

  getProgressPercentage() {
    if (this.totalParts === 0) return 100;
    return Math.floor((this.completedParts.size / this.totalParts) * 100);
  }
}

6. Senior Architecture Calibration Quizzes

Question 1: In video sharing applications like YouTube or Instagram, why do client architectures transcode video files on-device with Media3 Transformer before uploading?
A Cloud storage object stores reject videos that have not been encoded with MP4 metadata.
B It downscales 4K videos to 1080p, reducing payload size by ~80% before network upload.
C Transcoding video files on client mobile devices consumes zero battery power.
D Google Play Developer Policies ban Android apps that transmit raw 4K video frames.
Comprehensive Option Breakdown:
  • Option A (Wrong): Cloud servers accept any binary format; transcoding is an optimization, not a protocol mandate.
  • Option B (Correct): Camera recordings produce huge raw files (often 1–3 GB). Transcoding to an optimized 1080p H.265 stream on-device shrinks the file down to ~150 MB, dramatically reducing upload time and preventing timeouts.
  • Option C (Wrong): Transcoding uses hardware silicon and does consume battery.
  • Option D (Wrong): Play Store policies do not mandate video resolutions.
Question 2: How does a production WorkManager chunked upload pipeline survive Android OS process termination midway through uploading a 1 GB file?
A The ViewModel retains the upload stream in JVM memory across process termination.
B The app recovers by reading Linux kernel memory dumps from the Android system partition.
C It records completed part ETags in SQLite; resumed workers skip already finished chunks.
D WorkManager requires the device to be rooted to persist background task progress.
Comprehensive Option Breakdown:
  • Option A (Wrong): ViewModels only survive configuration changes, not OS process death.
  • Option B (Wrong): Sandboxed apps have zero access to raw Linux kernel memory dumps.
  • Option C (Correct): Every successful chunk response returns an ETag from the server. The worker writes this to Room SQLite immediately. When WorkManager restarts the task, it queries Room, sees that parts 1 to 5 are complete, and resumes directly at part 6!
  • Option D (Wrong): WorkManager is a standard Jetpack library and requires no root access.
