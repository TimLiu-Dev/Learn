Lesson 0003: Offline-First Repository Architecture, Room DB & Cache Eviction

Architect a production-grade Single Source of Truth (SSOT). Learn SQLite Write-Ahead Logging (WAL) concurrency, optimistic UI updates with mutation tracking, and memory-safe cache invalidation policies.

1. The Single Source of Truth (SSOT) Flow

The gold standard for Mid-Tech and Big-Tech mobile apps is Offline-First SSOT: The UI observes the local database via reactive Kotlin Flow. Network requests never feed the UI directly; they update the database, which automatically emits fresh data to observers.

Why SQLite WAL (Write-Ahead Logging) is Mandatory

In traditional rollback journaling, SQLite locks the entire database file during writes, blocking UI read queries and causing frame drops (jank). In WAL mode (default in modern Room), writes append to a separate .wal file. Readers never block writers, and writers never block readers, enabling high-throughput background sync while the user scrolls at 120 FPS.

2. Optimistic UI Mutations & Reconciliation

When a user posts a comment or likes a photo, waiting for the HTTP roundtrip creates a sluggish user experience. Staff architects implement Optimistic Updates with mutation flags: 

@Entity(tableName = "comments")
data class CommentEntity(
    @PrimaryKey val id: String,
    val feedItemId: String,
    val text: String,
    val timestamp: Long,
    val syncStatus: SyncStatus // SYNCED, PENDING_INSERT, PENDING_DELETE
)

enum class SyncStatus { SYNCED, PENDING_INSERT, PENDING_DELETE }

1. When user taps Send, write to Room with syncStatus = PENDING_INSERT and temporary UUID.
2. Room Flow emits to UI immediately (render with subtle spinner or checkmark).
3. Background worker sends payload to server with idempotency key.
4. Server returns real ID → Room transaction updates status to SYNCED.
5. If network aborts or HTTP 4xx occurs → Rollback or mark FAILED with retry option.

3. Interactive Practice: Implement an Optimistic Mutation Sync Store

Task: Implement SyncStore. It maintains local items. When addItem(item) is called, it adds the item with status 'PENDING'. When onServerAck(localId, serverId) is called, it updates the item's ID and sets status to 'SYNCED'. If onServerReject(localId) is called, it removes the pending item (rollback).

Optimistic Store Sandbox
Hint 1: Use this.items.find() to locate the record by localId.
Hint 2: When rejecting, use filter(i => i.id !== localId) to perform clean deletion.
Canonical Solution: 
class SyncStore {
  constructor() {
    this.items = [];
  }

  addItem(localId, text) {
    this.items.push({ id: localId, text, status: 'PENDING' });
  }

  onServerAck(localId, serverId) {
    const item = this.items.find(i => i.id === localId);
    if (item) {
      item.id = serverId;
      item.status = 'SYNCED';
    }
  }

  onServerReject(localId) {
    this.items = this.items.filter(i => i.id !== localId);
  }

  getItems() {
    return this.items;
  }
}
