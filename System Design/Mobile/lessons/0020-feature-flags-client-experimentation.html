Lesson 0020: Client-Side Feature Flagging, Dynamic Configuration & Experimentation at Scale

Architect high-scale experimentation and continuous delivery frameworks (Meta, Netflix, Google). Master local rule evaluation, sticky bucketing via consistent hashing, eliminating startup UI flashes, and zero-bias exposure telemetry logging.

1. Local vs. Remote Evaluation: The Microsecond Imperative

In Big-Tech applications with hundreds of simultaneous experiments (e.g. checkout button color, new ranking algorithms, redesigned nav bars), naive architectures query the server on demand: GET /v1/flags/checkout_button?user=123.

Why Remote Flag Evaluation Fails on Mobile
  • UI Freezes & Flash of Content: Waiting for a 150ms network round-trip before rendering a button causes noticeable layout shifts (CLS) and UI jank.
  • Zero Offline Support: If the user is on an airplane or subway tunnel, remote flag evaluations fail, causing UI features to revert or crash.
  • Server Thundering Herd: 500 million daily active users opening the app at 8 AM would DDOS the feature flag backend with billions of synchronous queries.

The Solution: Local Evaluation via Compiled Config Manifests

The client downloads a compressed JSON/Protobuf manifest of flag definitions in the background. The mobile app evaluates flag targeting rules locally in memory in <10 microseconds: 

[Client Cold Start] ──► Reads [Local Disk Manifest] (Cached from previous session)
                              │
                              ▼ (Local In-Memory Evaluation: 5 microseconds!)
                      [Render UI with Deterministic Variant]
                              │
[Background Worker] ──► (Fetches Latest Manifest from CDN) ──► Saves for Next Session

2. Sticky Bucketing & Zero-Bias Exposure Telemetry

Two core distributed systems problems govern mobile A/B testing:

1. Consistent Hashing (Sticky Bucketing)

To ensure a user always sees the same variant without storing centralized server state, the client computes:
bucket = Hash(userId + experimentSalt) % 100
If bucket < 50 $\rightarrow$ Control; otherwise $\rightarrow$ Treatment. The experimentSalt isolates experiments so users in Test for Experiment A are randomly distributed for Experiment B.

2. Zero-Bias Exposure Logging

Common Interview Blunder: Logging an "Exposure Event" during app launch. If only 5% of users ever visit the Settings screen, logging an exposure on startup for a Settings A/B test dilutes your data with 95% inactive users, ruining statistical power! Rule: Emit the exposure log strictly when the composable renders on screen.

4. Production Kotlin 2.x Feature Flag & Experiment Engine

package com.systemdesign.experimentation

import java.nio.charset.StandardCharsets
import java.security.MessageDigest

data class ExperimentConfig(
    val salt: String,
    val controlWeight: Int, // e.g. 50
    val treatmentWeight: Int // e.g. 50
)

enum class Variant { CONTROL, TREATMENT }

class LocalExperimentEvaluator(
    private val activeExperiments: Map<String, ExperimentConfig>,
    private val telemetryLogger: TelemetryExposureLogger
) {
    fun getVariant(experimentKey: String, userId: String): Variant {
        val config = activeExperiments[experimentKey] ?: return Variant.CONTROL

        // Deterministic Consistent Hashing (MD5 or MurmurHash3)
        val input = "${userId}_${config.salt}"
        val md5Bytes = MessageDigest.getInstance("MD5").digest(input.toByteArray(StandardCharsets.UTF_8))
        val bucket = (md5Bytes[0].toInt() and 0xFF) % 100 // Bucket 0 to 99

        return if (bucket < config.controlWeight) Variant.CONTROL else Variant.TREATMENT
    }

    // Called strictly when the UI Composable actually appears in viewport!
    fun logExposure(experimentKey: String, variant: Variant, userId: String) {
        telemetryLogger.logEvent(
            eventName = "EXPERIMENT_EXPOSURE",
            attributes = mapOf(
                "experiment_key" to experimentKey,
                "variant" to variant.name,
                "user_id" to userId
            )
        )
    }
}

5. Interactive Practice: Consistent Hashing Experiment Allocator

Task: Implement ConsistentHashExperimentAllocator.
• constructor(experiments): Takes an object of experiments (e.g. { exp_1: { salt: "s1", controlPercent: 50 } }).
• getVariant(expKey, userId): Computes a deterministic integer hash from userId + "_" + salt.
  Computes bucket = Math.abs(hash) % 100.
  Returns "CONTROL" if bucket < controlPercent, else "TREATMENT".
  Must produce identical results for the same user, and distributed results across different users.

Sticky Bucketing Sandbox
Hint 1: Look up const exp = this.experiments[expKey]. If not found, return "CONTROL".
Hint 2: Compute const hash = this.hashString(userId + '_' + exp.salt). const bucket = Math.abs(hash) % 100. Return bucket < exp.controlPercent ? 'CONTROL' : 'TREATMENT'.
Canonical Staff-Level Solution: 
class ConsistentHashExperimentAllocator {
  constructor(experiments = {}) {
    this.experiments = experiments;
  }

  hashString(str) {
    let hash = 0;
    for (let i = 0; i < str.length; i++) {
      hash = ((hash << 5) - hash) + str.charCodeAt(i);
      hash |= 0;
    }
    return hash;
  }

  getVariant(expKey, userId) {
    const exp = this.experiments[expKey];
    if (!exp) return 'CONTROL';

    const hash = this.hashString(userId + '_' + exp.salt);
    const bucket = Math.abs(hash) % 100;

    return bucket < exp.controlPercent ? 'CONTROL' : 'TREATMENT';
  }
}

6. Senior Architecture Calibration Quizzes

Question 1: In mobile experimentation architecture, why is emitting an experiment exposure telemetry event during Application.onCreate() considered a critical flaw?
A It blocks the Android Application class main thread and causes an immediate ANR crash.
B It dilutes statistical power by recording exposures for users who never saw the feature.
C It requires cryptographic hardware StrongBox keys that are unavailable at startup.
D Google Play Services flags the application as spyware and blocks future installs.
Comprehensive Option Breakdown:
  • Option A (Wrong): Telemetry logging is asynchronous; it does not block the main thread.
  • Option B (Correct): If a feature flag controls a checkout button, but you log exposure on app launch, 90% of users who never reached checkout will be counted as exposed. This washes out the true metric delta, invalidating the A/B test.
  • Option C (Wrong): Feature flags use standard hash functions, not StrongBox keys.
  • Option D (Wrong): Standard telemetry logging does not trigger Play Store spyware flags.
Question 2: How do Big-Tech applications prevent UI layout flash while avoiding blocking cold app startup for dynamic remote configuration?
A Block the main thread on the splash screen until the CDN returns the latest flag JSON.
B Hardcode all feature flags inside the compiled Kotlin binary, releasing a new APK daily.
C Render immediately using disk-cached flags; fetch latest config in background for next session.
D Generate a random boolean on every screen recomposition to alternate between variants.
Comprehensive Option Breakdown:
  • Option A (Wrong): Holding the splash screen destroys cold startup performance (TTID) and triggers ANRs on slow connections.
  • Option B (Wrong): Hardcoding flags requires full app store releases to change any variable.
  • Option C (Correct): Using the cached manifest from the previous session allows sub-millisecond cold start rendering with zero UI flash. An asynchronous background task fetches the new manifest, which applies cleanly on the next app restart.
  • Option D (Wrong): Random variants per recomposition cause chaotic flickering and unusable UI.
