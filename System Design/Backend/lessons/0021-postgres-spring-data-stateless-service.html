Postgres + Spring Data: Making the Service Stateless

In 0019's quiz, two instances with in-memory maps disagreed: a POST to A followed by a GET from B returned 404. The fix is to move state out of the app and into a shared database. The skill in this lesson: evolve a schema safely with versioned migrations, then prove two instances now agree.

1. Stateless app, stateful database

Before → after
 BEFORE (0019)                         AFTER (this lesson)
 LB ─┬─> app A  {map: note 1}          LB ─┬─> app A ─┐
     └─> app B  {map: empty}  → 404        └─> app B ─┴─> [ Postgres: notes ]  → 200 from both

Room on Android is SQLite with a migrations system. On the server it's the same idea at a larger scale: one shared Postgres, and a migration tool that applies schema changes in order on every environment (your laptop, CI, production).

2. How Flyway thinks

  • Each schema change is a SQL file named V<version>__<description>.sql (two underscores), e.g. V1__create_notes.sql, under src/main/resources/db/migration (Flyway docs: Migrations).
  • On startup, Flyway reads the flyway_schema_history table, then applies only the pending versions, in ascending order, recording each one with a checksum.
  • Applied migrations are immutable. If you edit a migration that has already run, its checksum no longer matches the history and validation fails at startup. To change something, write a new migration (V2, V3…).
-- V1__create_notes.sql
CREATE TABLE notes (
    id         BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title      TEXT        NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

PRIMARY KEY means unique and not null. GENERATED … AS IDENTITY makes Postgres assign the id, which replaces 0019's AtomicLong (PostgreSQL: CREATE TABLE). An id handed out by the database is unique across all instances. A counter in memory never could be.

3. Spring Data JDBC: the repository is an interface

Like a Room @Dao, you declare an interface and Spring generates the implementation. This course uses Spring Data JDBC because it works directly with immutable Kotlin data classes. Spring Data JPA (Hibernate) is common in job posts, but in Kotlin it needs extra compiler plugins (kotlin("plugin.jpa")) and regular classes instead of data classes (Kotlin docs: JPA support).

@Table("notes")
data class Note(@Id val id: Long? = null, val title: String)   // id = null → INSERT, DB assigns it

interface NoteRepository : CrudRepository<Note, Long>

@RestController
@RequestMapping("/notes")
class NoteController(private val repo: NoteRepository) {          // constructor injection

    @GetMapping("/{id}")
    fun get(@PathVariable id: Long): ResponseEntity<Note> =
        repo.findByIdOrNull(id)?.let { ResponseEntity.ok(it) } ?: ResponseEntity.notFound().build()

    @PostMapping
    fun create(@RequestBody body: CreateNote): ResponseEntity<Note> {
        if (body.title.isBlank()) return ResponseEntity.badRequest().build()
        val saved = repo.save(Note(title = body.title.trim()))
        return ResponseEntity.created(URI.create("/notes/${saved.id}")).body(saved)
    }
}
☕ Java on the side: entity and repository 
@Table("notes")
public record Note(@Id Long id, String title) {}

public interface NoteRepository extends CrudRepository<Note, Long> {}

// in the controller:
return repo.findById(id).map(ResponseEntity::ok).orElse(ResponseEntity.notFound().build());

The 201/400/404 behaviour from 0019 is unchanged. Only where the state lives moved.

4. Practice: build a mini Flyway

Implement migrate(db, migrations):

  • db.history holds the applied {version, checksum} entries. Every SQL you run goes into db.executed.
  • Validate first: if an applied migration's checksum changed, throw Error('CHECKSUM_MISMATCH'). If a migration that hasn't run has a version lower than the latest applied one, throw Error('OUT_OF_ORDER').
  • Only then apply the pending migrations in ascending version order, and return the list of versions you applied.

5. Check yourself

6. Do it for real (on your machine)

  1. Run Postgres in Docker. The official image needs POSTGRES_PASSWORD; POSTGRES_USER and POSTGRES_DB are optional (Docker Hub: postgres): 
    docker run --name notes-db -e POSTGRES_PASSWORD=dev -e POSTGRES_DB=notes -p 5432:5432 -d postgres
  2. Add dependencies with Initializr (or "Add starters" in IntelliJ): Spring Data JDBC, Flyway Migration, PostgreSQL Driver. Then check your build file contains org.flywaydb:flyway-database-postgresql. Since Flyway 10, database support ships as separate modules, and Flyway fails at startup without it.
  3. In application.properties: 
    spring.datasource.url=jdbc:postgresql://localhost:5432/notes
spring.datasource.username=postgres
spring.datasource.password=dev
  4. Add V1__create_notes.sql, the Note entity, the repository, and the updated controller. Start the app and check the log line saying Flyway applied V1. Then run docker exec -it notes-db psql -U postgres -d notes -c 'select version, description, checksum from flyway_schema_history;'
  5. Prove statelessness: start a second instance with ./gradlew bootRun --args='--server.port=8081', then: 
    curl -i -X POST localhost:8080/notes -H 'Content-Type: application/json' -d '{"title":"shared!"}'
curl -i localhost:8081/notes/1     # 200: same note, different instance
  6. Break it on purpose: add a comment to V1__create_notes.sql and restart. Read the validation error, then revert the change. To change the schema, add V2__add_done_flag.sql with ALTER TABLE notes ADD COLUMN done BOOLEAN NOT NULL DEFAULT false;
  7. Java on the side: port the entity and repository to Java (record + interface) in your Java project and run the same curls.
✓ Win condition

A note created on :8080 is returned by :8081, and you've seen Flyway refuse to start after an applied migration was edited.
