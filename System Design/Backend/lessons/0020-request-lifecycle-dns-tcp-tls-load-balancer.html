From Tap to Controller: DNS, TCP, TLS & the Load Balancer

Between api.getNote(1) in your app and @GetMapping("/{id}") on the server, the request makes several network round trips before your code runs. The skill in this lesson: count the round trips, so you can estimate latency and explain why the first request is slow and later ones are fast.

1. The journey of one request

Cold request: nothing cached, no open connection
 Android app          DNS resolver       Load balancer            app #1 / app #2
     |  where is api.x.com? |                   |                          |
     |--------------------->|  (1 RTT, unless cached until its TTL expires) |
     |<---- 203.0.113.7 ----|                   |                          |
     |  SYN / SYN-ACK / ACK  (TCP: 1 RTT)       |                          |
     |----------------------------------------->|                          |
     |  TLS handshake  (TLS 1.3: 1 RTT · TLS 1.2: 2 RTT)                  |
     |----------------------------------------->|                          |
     |  GET /notes/1 ... response (1 RTT + server time)                    |
     |----------------------------------------->|--- picks an instance --->|
     |<-----------------------------------------|<---- 200 {note} --------|
  • DNS turns a hostname into an IP address. Answers are cached for their TTL (time to live), so later lookups are usually free.
  • TCP needs a three-way handshake (SYN, SYN-ACK, ACK) before any data flows, which costs about one round trip (HPBN: Building Blocks of TCP).
  • TLS sets up encryption. A full TLS 1.3 handshake takes 1 RTT, half of TLS 1.2's 2 RTT (RFC 8446, HPBN: TLS).
  • The HTTP request itself costs one more round trip, plus the time your server spends working.
Keep-alive is the big win

Once a connection is open, later requests reuse it and skip DNS, TCP, and TLS entirely. This is why OkHttp's docs say OkHttpClient instances should be shared: each client has its own connection pool and thread pools, and creating new clients throws that reuse away (OkHttpClient docs).

2. Round-trip math

The model used in the sandbox below, with one RTT meaning one trip there and back between phone and server:

PhaseCostSkipped when…
DNS lookup1 RTT (a simplification: the resolver may be closer than the server)Answer is cached, or the connection is reused
TCP handshake1 RTTConnection reused
TLS handshake1.3 → 1 RTT · 1.2 → 2 RTT · plain HTTP → 0Connection reused
Request + response1 RTT + server timeNever

Example: on mobile with RTT = 100 ms, server time = 20 ms, TLS 1.2, and cold DNS: (1 + 1 + 2 + 1) × 100 + 20 = 520 ms. The same request on a reused connection: 1 × 100 + 20 = 120 ms. Most of a cold request is spent on the network, not in your code.

3. Load balancers: L4 vs L7

In 0019's quiz you put two app instances behind a load balancer. There are two kinds (System Design Primer: load balancer):

Layer 4 (transport)Layer 7 (application)
SeesIP addresses and portsThe full HTTP request: path, headers, cookies
Can route /api/* and /static/* differently?NoYes
Terminates TLS?Usually passes it throughUsually yes: it decrypts, then routes
CostCheaper, fasterMore CPU, much more flexible

A reverse proxy (such as nginx) sits in front of servers and forwards requests to them. A load balancer is a reverse proxy that spreads traffic across several servers. Both run health checks and stop sending traffic to instances that fail them, which you'll wire up in 0024.

4. Practice: estimate and route

Implement two functions:

  • estimateRequestMs(opts) uses the table in §2.
  • routeL7(path, rules, defaultBackend) picks a backend the way an L7 load balancer does. The longest matching path prefix wins, and anything unmatched goes to the default.

5. Check yourself

6. Do it for real (on your machine)

  1. Start your 0019 service (./gradlew bootRun) and time one request. The -w timings are cumulative from the start of the request (everything.curl.dev: --write-out): 
    curl -s -o /dev/null -w 'dns %{time_namelookup}  tcp %{time_connect}  tls %{time_appconnect}  ttfb %{time_starttransfer}  total %{time_total}\n' http://localhost:8080/notes/1
    On localhost, DNS, TCP, and TLS are close to zero. That's why your laptop hides the real cost.
  2. Run the same command against a public HTTPS site, e.g. https://www.google.com/. Work out TCP time as time_connect − time_namelookup and TLS time as time_appconnect − time_connect. Compare the TLS time with the TCP time (roughly one RTT). Is TLS about one RTT (TLS 1.3) or two?
  3. Look up a DNS answer and its TTL: dig www.google.com. The number before IN A is the TTL in seconds. Run it twice and watch it count down while your resolver serves it from cache.
  4. Android bonus: check your app creates exactly one OkHttpClient (e.g. a Hilt @Singleton) and that Retrofit reuses it. If you need a different timeout somewhere, use client.newBuilder(), which shares the same pools.
☕ Java on the side: a shared client in plain Java 
public final class Http {
    public static final OkHttpClient CLIENT = new OkHttpClient();   // one per app
    private Http() {}
}
// Per-call tweak that shares the same connection pool:
OkHttpClient slow = Http.CLIENT.newBuilder().readTimeout(Duration.ofSeconds(30)).build();
✓ Win condition

You can point at a curl timing line and say which part was DNS, TCP, TLS, and server time, and why a reused connection skips the first three.
