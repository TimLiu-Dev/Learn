Idempotent API Design & Distributed Locking

In unreliable distributed networks, packets drop, connections time out, and clients retry aggressively. Designing idempotent APIs guarantees that retried requests never cause duplicate financial charges or conflicting side effects.

1. The Distributed Network Retry Dilemma

Consider a mobile client initiating a \$100 money transfer:

  1. Client sends POST /v1/charges { amount: 10000, recipient: 'acct_42' }.
  2. Backend server receives request, deducts money, and issues charge.
  3. Cell tower loses connection right before sending 200 OK back to client.
  4. Client library hits timeout and automatically retries the identical POST request.
Without Idempotency: Duplicate Financial Charge

The backend treats the retry as a brand-new request and charges the user a second time! An API is idempotent if making the identical request $N$ times produces the exact same system state as making it once: $f(f(x)) = f(x)$.

2. Distributed Locking & The Fencing Token Problem

When coordinating concurrent operations across microservices, developers often use Redis distributed locks (e.g. Redlock). However, distributed systems expert Martin Kleppmann demonstrated a critical failure mode:

The Stop-the-World GC Pause Hazard

Client 1 acquires a distributed lock for 10 seconds. Client 1 experiences a 15-second Java GC pause. The lock expires in Redis. Client 2 acquires the lock. Client 1 wakes up, unaware time has passed, and writes to storage concurrently with Client 2!

The Solution: Fencing Tokens. Every time a lock is granted, the lock manager returns a monotonically increasing integer token ($1, 2, 3\dots$). Storage engines reject any write carrying a fencing token lower than the highest token already accepted.
