Server-Side Auth: The Other Half of Your Login Screen

On Android you've built login screens, saved tokens in EncryptedSharedPreferences or DataStore, and attached Authorization: Bearer <token> in an OkHttp interceptor. In this lesson you build the server side: store passwords safely, issue short-lived JWT access tokens + rotating refresh tokens, and tell 401 apart from 403.

1. Four decisions every backend makes

QuestionWrong answerRight answer & standard
1. How do we store passwords?Plaintext, encrypted, or a fast hash like SHA-256 (GPUs try billions/sec)A slow, salted, adaptive hash: Argon2id (OWASP's primary pick) or bcrypt with cost ≥ 10 (OWASP Password Storage Cheat Sheet).
2. Session ID or JWT?Long-lived JWTs that never expireServer session (random ID in DB/Redis: easy to revoke, one lookup per request) or a short-lived JWT (5–15 min, verified by signature with zero DB lookups) paired with a revocable refresh token (RFC 7519).
3. How do we protect refresh tokens on a phone?One permanent refresh token foreverRefresh token rotation (RFC 9700 §4.14): each refresh issues a new token and invalidates the old one. If an already-used token arrives again, revoke the whole token family.
4. How does a third-party or SSO login work on Android?Embedded WebView or sending raw passwordsAuthorization Code + PKCE in the system browser / Custom Tabs (RFC 8252, RFC 7636). OpenID Connect (OIDC) layers an ID token on top.
401 Unauthorized vs 403 Forbidden (RFC 9110)

401 means "I don't know who you are" (missing, malformed, or expired token — triggers your OkHttp Authenticator to refresh). 403 means "I know who you are, and you aren't allowed" (customer #7 asking for customer #8's order, or a customer calling a /staff/* route). Refreshing the token won't fix a 403 (RFC 9110 §15.5).

2. Inside a JWT: never read the payload before verifying the signature

A JWT is three Base64URL strings joined by dots: header.payload.signature (RFC 7519 §3).

// header                              // payload
{"alg":"HS256","typ":"JWT"}            {"sub":"42","role":"CUSTOMER","aud":"pulseorder","exp":1795000900}

Anyone can decode the middle part — it's encoded, not encrypted. What stops an attacker from changing "sub":"42" to "sub":"1" is the signature across header + "." + payload. Your verifier must check, in order:

  1. The token has three parts and valid JSON in header and payload.
  2. header.alg matches the algorithm you expect (never trust "alg":"none").
  3. The signature computed with your server's key equals the token's signature.
  4. payload.exp is in the future and payload.aud matches your service.

3. Spring Security in 25 lines

With spring-boot-starter-oauth2-resource-server, Spring validates the Authorization: Bearer JWT before your controller runs and injects the verified token:

@Configuration
class SecurityConfig(@Value("\${app.jwt.secret}") private val secret: String) {

    @Bean fun passwordEncoder(): PasswordEncoder = BCryptPasswordEncoder()   // or Argon2PasswordEncoder

    @Bean fun jwtDecoder(): JwtDecoder =
        NimbusJwtDecoder.withSecretKey(SecretKeySpec(secret.toByteArray(), "HmacSHA256"))
            .macAlgorithm(MacAlgorithm.HS256).build()

    @Bean fun filterChain(http: HttpSecurity): SecurityFilterChain = http
        .csrf { it.disable() }
        .sessionManagement { it.sessionCreationPolicy(SessionCreationPolicy.STATELESS) }
        .authorizeHttpRequests {
            it.requestMatchers("/auth/**", "/menu").permitAll()
              .anyRequest().authenticated()
        }
        .oauth2ResourceServer { it.jwt {} }
        .build()
}

// Inside OrderController — check ownership so user 7 cannot read user 8's order:
@GetMapping("/orders/{id}")
fun get(@PathVariable id: Long, @AuthenticationPrincipal jwt: Jwt): ResponseEntity<Order> {
    val order = repo.findByIdOrNull(id) ?: return ResponseEntity.notFound().build()
    if (order.userId != jwt.subject.toLong()) return ResponseEntity.status(403).build()
    return ResponseEntity.ok(order)
}
☕ Java on the side: ownership check in the controller 
@GetMapping("/orders/{id}")
public ResponseEntity<Order> get(@PathVariable long id, @AuthenticationPrincipal Jwt jwt) {
    Order order = repo.findById(id).orElse(null);
    if (order == null) return ResponseEntity.notFound().build();
    if (order.userId() != Long.parseLong(jwt.getSubject())) return ResponseEntity.status(403).build();
    return ResponseEntity.ok(order);
}

4. Practice: write a JWT verifier

Implement verifyToken(token, opts) using the starter's toy sign(input, secret) helper (real systems use HMAC-SHA256 or RSA/ECDSA). Return either { valid: true, sub, role } or { valid: false, reason } with one of the exact reasons listed in the starter.

5. Check yourself

6. Do it for real (on your machine)

  1. Add org.springframework.boot:spring-boot-starter-oauth2-resource-server to build.gradle.kts, and add a users table migration: id, email UNIQUE, password_hash, role.
  2. Add SecurityConfig above and a small /auth/signup + /auth/login controller that hashes passwords with passwordEncoder.encode(raw), verifies with passwordEncoder.matches(raw, hash), and signs a 15-minute HS256 JWT with NimbusJwtEncoder.
  3. Test all three status codes with curl: 
    curl -i localhost:8080/orders/1                                    # 401 (no token)
curl -i localhost:8080/orders/1 -H "Authorization: Bearer $USER2"  # 403 (belongs to user 1)
curl -i localhost:8080/orders/1 -H "Authorization: Bearer $USER1"  # 200
  4. Android bonus: in your app, attach the access token in an OkHttp Interceptor, and implement OkHttp's Authenticator interface so a 401 automatically calls POST /auth/refresh and retries the request once (OkHttp: Handling Authentication).
  5. Java on the side: write the SecurityConfig class in your Java project and verify the same three curls.
✓ Win condition

select password_hash from users; shows a $2a$... bcrypt hash (never a raw password), and the three curls return 401, 403, and 200.
