Zero-Downtime Database Migrations: The Expand-Contract Pattern

In enterprise systems with 500 million records, running a naive ALTER TABLE statement acquires an exclusive metadata lock that queues queries, exhausts connection pools, and takes the entire production site offline.

1. The Lock Avalanche: Why Naive DDL Takes Sites Down

In an interview, candidates are frequently asked: "We need to rename a column or split a table with 200 million rows in Postgres/MySQL. How do you do it without downtime?"

⚠️ The Metadata Lock Trap

In PostgreSQL, an ALTER TABLE requires an ACCESS EXCLUSIVE lock. Even if the alter takes 20ms, it must wait behind any active in-flight SELECT queries. While it waits, every incoming query queues behind the lock request. Within seconds:

  • All application server connection pool slots are exhausted waiting for table access.
  • Load balancers fail health check probes due to HTTP request timeout cascades.
  • The entire cluster collapses into an outage while waiting for a single DDL statement.

2. The 5-Phase Expand-Contract (Parallel Run) Architecture

Senior engineers decouple database schema changes from application deployments using the 5-phase Expand-Contract pattern:

Expand-Contract Migration Lifecycle
Phase 1: EXPAND           Phase 2: DUAL-WRITE       Phase 3: BACKFILL         Phase 4: CUTOVER          Phase 5: CONTRACT
+--------------------+   +--------------------+   +--------------------+   +--------------------+   +--------------------+
| App writes: OLD    |   | App writes: BOTH   |   | App writes: BOTH   |   | App writes: BOTH   |   | App writes: NEW    |
| App reads:  OLD    |   | App reads:  OLD    |   | App reads:  OLD    |   | App reads:  NEW    |   | App reads:  NEW    |
| Schema: OLD + NEW* |   | Schema: OLD + NEW  |   | [Worker backfills  |   | [Verify telemetry  |   | Schema: NEW only   |
| (*new is NULLABLE) |   |                    |   |  historical rows]  |   |  & consistency]    |   | (Drop OLD column)  |
+--------------------+   +--------------------+   +--------------------+   +--------------------+   +--------------------+
Phase Application Deployment State Database Operations & Safety Guards
1. Expand Deploy schema migration first. Application code remains untouched. Add the new column/table as NULLABLE or with a safe default. In Postgres, NOT NULL without a default requires rewriting the entire table disk space.
2. Dual-Write Deploy code version 2. Writes write to both Old and New fields inside a single transaction. Reads still read from Old. Guarantees that any new row created from this point forward contains valid data in both schemas.
3. Backfill Background asynchronous worker runs independently of user traffic. Iterates through historical records in bounded primary key chunks (e.g. 1,000 rows at a time). Throttles execution if database replication lag exceeds 100ms.
4. Cutover Deploy code version 3. Reads switch to New schema. Writes still write to both. Shadow reads or async reconciliation jobs compare Old vs New values to verify 100% data parity. If a bug is detected, rollback requires zero database downtime.
5. Contract Deploy code version 4. Writes write only to New schema. Old code is deleted. Drop old column asynchronously using online schema tools (e.g., gh-ost or pg_repack).
