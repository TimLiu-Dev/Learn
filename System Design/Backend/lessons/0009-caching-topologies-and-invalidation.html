Caching Topologies, Cache Stampede & Invalidation

Caching is the universal lever for reducing latency and shielding databases from traffic spikes. In senior system design interviews, the focus shifts to cache invalidation races, thundering herds, and dual-write consistency.

1. The Four Fundamental Caching Patterns

Pattern Data Flow Mechanics Production Trade-Off
Cache-Aside (Lazy) App reads cache. On miss, reads DB and writes to cache. On mutation, app writes to DB then deletes cache key. Industry Standard: Resilient to cache crashes; lazy population saves memory. Must handle cold start misses.
Write-Through App writes to cache; cache synchronously writes to DB before acknowledging. Guarantees data in cache is always warm and synchronized; adds write latency for two sequential writes.
Write-Behind (Write-Back) App writes directly to cache; cache asynchronously batches writes to DB. Maximum write throughput; risk of data loss if cache crashes before async flush to persistent storage.
Refresh-Ahead Cache automatically refreshes hot keys before configured TTL expires. Reduces read latency spikes on hot keys; requires accurate prediction of access frequency.
⚠️ The Golden Rule: DELETE the Cache Key, Never UPDATE It

When updating the database in Cache-Aside, always delete the cache key rather than updating it with the new value. If two concurrent database writes occur ($W_1$ followed by $W_2$), network jitter can cause $W_2$'s cache update to arrive before $W_1$'s cache update, leaving stale data in the cache permanently until TTL expiration!

2. The Cache Stampede (Thundering Herd) Disaster

Imagine a celebrity account's profile cached in Redis with a 1-hour TTL, receiving 20,000 queries per second:

The Thundering Herd Effect
t = 00:59:59 -> Redis has cached data. 20,000 QPS served in 0.5ms. Database CPU at 3%.
t = 01:00:00 -> KEY EXPIRES IN REDIS!
t = 01:00:00.001 -> 20,000 concurrent requests miss the cache simultaneously!
                    All 20,000 requests execute expensive SQL queries against Postgres!
                    Database connection pool exhausted -> Latency spikes to 30s -> Database crashes!

How Senior Engineers Prevent Cache Stampedes

  1. Mutex / Single-Flight Locking: When a cache miss occurs, the first request acquires an in-memory lock or mutex. It alone queries the database and populates the cache. The other 19,999 requests wait on that single promise and read the populated result.
  2. Probabilistic Early Expiration (XFetch Algorithm): Requests pre-emptively recompute the key before it expires based on a probabilistic formula $-\beta \cdot \delta \cdot \ln(\text{rand}())$, where $\delta$ is the compute time and $\beta > 0$. As expiration approaches, probability of background refresh increases smoothly.
  3. Logical vs. Physical TTL: Physical Redis TTL is set to 2 hours; a logical timestamp embedded in the JSON payload indicates expiration after 30 minutes. The first client observing logical expiration triggers an asynchronous background worker to refresh while returning the slightly stale value immediately.
