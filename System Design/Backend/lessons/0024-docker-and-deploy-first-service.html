Ship It: Docker, Config & Your First Deploy

An APK packages your compiled Kotlin code and resources so any Android phone can run it. A container image packages your compiled Spring Boot app plus the exact Java runtime and OS libraries it needs, so your laptop, CI, and production all run the exact same bytes.

1. Image vs container, and two ways to build

  • An image is an immutable snapshot (like an APK). A container is one running process started from that image. If a container crashes or you deploy a new version, the platform throws the container away and starts a fresh one — its local filesystem is ephemeral.
  • Option A — Cloud Native Buildpacks (zero Dockerfile): Spring Boot's Gradle plugin builds an OCI image directly with ./gradlew bootBuildImage (Spring Boot Gradle Plugin: Packaging OCI Images).
  • Option B — Multi-stage Dockerfile: stage 1 compiles with a full JDK; stage 2 copies only the jar into a slim JRE image so build caches and source code never ship to production.
# Dockerfile (multi-stage)
FROM eclipse-temurin:21-jdk AS build
WORKDIR /workspace
COPY gradlew settings.gradle.kts build.gradle.kts ./
COPY gradle ./gradle
COPY src ./src
RUN ./gradlew bootJar --no-daemon

FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /workspace/build/libs/*.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "/app/app.jar"]

2. Twelve-Factor config & Spring Boot relaxed binding

The Twelve-Factor App rule for config is simple: store config that varies between deploys (database URLs, credentials, secrets) in environment variables, never baked into the image. That way the exact same image runs locally, in staging, and in production.

Spring Boot maps environment variables to property names automatically through relaxed binding, and OS environment variables override application.properties (Spring Boot: Externalized Configuration):

Property in application.propertiesCanonical OS environment variableRule
spring.datasource.urlSPRING_DATASOURCE_URLReplace dots (.) with underscores (_), remove dashes (-), uppercase
spring.datasource.passwordSPRING_DATASOURCE_PASSWORDEnv var overrides the file default
app.jwt.secretAPP_JWT_SECRETMatches @Value("\${app.jwt.secret}") from 0023

3. Health probes: liveness vs readiness

Add org.springframework.boot:spring-boot-starter-actuator and expose health probes (Spring Boot Actuator: Kubernetes Probes):

# application.properties
management.endpoints.web.exposure.include=health
management.endpoint.health.probes.enabled=true
Probe endpointQuestion it answersWhat the platform does when it fails
/actuator/health/liveness"Is this process wedged beyond repair?"Restarts the container
/actuator/health/readiness"Is this instance ready to take requests right now?"Stops sending traffic from the load balancer without killing the container
Don't wire liveness to external dependencies

If a 2-second Postgres hiccup makes liveness fail, the platform restarts every app container at once, turning a blip into a full outage. Liveness checks the process itself; readiness gates traffic.

4. Practice: Spring config resolver & probe router

Implement three functions that mirror how Spring Boot and a container platform work together:

  • toEnvName(propertyKey): replace every dot (.) with _, remove every dash (-), and uppercase (Spring's canonical rule: spring.datasource.driver-class-name → SPRING_DATASOURCE_DRIVERCLASSNAME).
  • resolveProperty(propertyKey, sources): return the value from sources.env[toEnvName(propertyKey)] if defined, else sources.applicationProperties[propertyKey] if defined, else sources.defaults[propertyKey], else null.
  • probeDecision({ liveness, readiness }): if liveness !== 'UP' return 'RESTART'; else if readiness !== 'UP' return 'DRAIN' (remove from load balancer, don't restart); else return 'SERVE'.

5. Check yourself

6. Do it for real (on your machine & in the cloud)

  1. Add spring-boot-starter-actuator and the two management.* properties from §3. Write a docker-compose.yml that runs two app instances and one Postgres container: 
    services:
  db:
    image: postgres:16
    environment:
      POSTGRES_DB: pulseorder
      POSTGRES_PASSWORD: dev
    ports: ["5432:5432"]
  app:
    build: .
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://db:5432/pulseorder
      SPRING_DATASOURCE_USERNAME: postgres
      SPRING_DATASOURCE_PASSWORD: dev
      APP_JWT_SECRET: local-dev-secret-at-least-32-bytes-long
    ports: ["8080:8080"]
    depends_on: [db]
  2. Run docker compose up --build and verify: 
    curl -i localhost:8080/actuator/health/liveness    # 200 {"status":"UP"}
curl -i localhost:8080/actuator/health/readiness   # 200 {"status":"UP"}
  3. Deploy to a managed container platform (for example Render, Railway, Fly.io, or Google Cloud Run — pick one that runs a Dockerfile and offers managed Postgres):
    • Provision a managed Postgres instance and copy its internal connection URL.
    • Set SPRING_DATASOURCE_URL, SPRING_DATASOURCE_USERNAME, SPRING_DATASOURCE_PASSWORD, and APP_JWT_SECRET in the platform's environment variables UI.
    • Point the platform's health check path at /actuator/health/readiness and scale the service to 2 instances.
  4. Android bonus: switch your Retrofit baseUrl from http://10.0.2.2:8080/ to your deployed https://... URL (real TLS, no cleartext flag needed!). Create an order from your phone, kill one container instance in the dashboard, and confirm fetching the order still returns 200.
  5. Java on the side: the exact same Dockerfile and docker-compose.yml package your Java Spring Boot project without changing a line.
