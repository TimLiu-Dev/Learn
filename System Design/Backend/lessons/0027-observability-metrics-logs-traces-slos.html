Observability Basics: Metrics, Logs, Traces & SLOs

roadmap.sh splits monitoring across eight separate nodes (Health, Availability, Performance, Usage, Security Monitoring, Instrumentation, Visualization & Alerts). In interviews and in production, those eight nodes boil down to two skills: picking the right signal (metrics, logs, or traces) and measuring reliability with an SLO and an error budget.

1. The three signals: metrics vs logs vs traces

SignalWhat it isQuestion it answersSpring Boot tool
MetricsNumeric time series (counters, gauges, histograms)"Is there a problem right now?" (e.g. POST /orders 5xx rate or p99 latency just spiked)Micrometer + Prometheus (/actuator/prometheus, http.server.requests)
LogsTimestamped structured event records (JSON with a traceId)"What exact error happened inside this service?"SLF4J / Logback with MDC traceId & spanId
TracesA tree of timed spans sharing one traceId across services"Which hop in the chain (gateway → orders → Postgres → payment) was slow?"Micrometer Tracing + OpenTelemetry (micrometer-tracing-bridge-otel)
Why p95 / p99 instead of average latency?

If 99 requests take 10 ms and 1 request takes 5,000 ms, the average is 60 ms — everything looks fine while 1 in 100 checkouts hangs for 5 seconds. The 99th percentile (p99) is the value below which 99% of requests fall (here, 5,000 ms). Always state latency targets as p95 and p99 (Google SRE Book: Service Level Objectives).

2. SLI, SLO, Error Budget, and Burn Rate

From the Google SRE Book and SRE Workbook: Alerting on SLOs:

  • SLI (Service Level Indicator): the ratio you measure, e.g. good_requests / total_requests.
  • SLO (Service Level Objective): the target for that SLI over a window, e.g. SLI ≥ 99.9% over 30 days. (An SLA is a legal contract with penalties — usually looser than your internal SLO.)
  • Error budget: the allowed unreliability, $\text{Error Budget} = 1 - \text{SLO Target}$. For a 99.9% SLO, the error budget is 0.1% (0.001) — out of 1,000,000 requests, 1,000 can fail before you breach the SLO.
  • Burn rate: how fast you are consuming that budget relative to the window: $$\text{Burn Rate} = \frac{\text{Observed Error Rate}}{1 - \text{SLO Target}}$$ A burn rate of 1.0 uses the budget at the exact end of the 30-day window. A burn rate of 10.0 (e.g. a 1% error rate against a 99.9% SLO) exhausts a 30-day budget in 3 days; a burn rate of 14.4 exhausts it in 50 hours (a common paging threshold in the SRE Workbook).

3. Spring Boot instrumentation in 15 lines

With Actuator, Micrometer Prometheus, and the OpenTelemetry bridge on the classpath, Spring Boot automatically records http.server.requests histograms and injects traceId into your logs (Spring Boot Actuator: Metrics, Tracing):

# application.properties
management.endpoints.web.exposure.include=health,prometheus
management.metrics.distribution.percentiles-histogram.http.server.requests=true
management.tracing.sampling.probability=1.0
// Adding a custom business counter in Kotlin
@Service
class OrderMetrics(registry: MeterRegistry) {
    private val placedCounter = Counter.builder("pulseorder.orders.placed")
        .description("Total orders placed").register(registry)

    fun recordOrderPlaced() = placedCounter.increment()
}

}

4. Practice: nearest-rank percentile & SLO burn-rate calculator

Implement two functions:

  • percentile(values, p) using the nearest-rank method: sort a copy of values ascending, compute index Math.ceil((p / 100) * sorted.length) - 1 (clamped to ≥ 0), and return sorted[idx] (or 0 if values is empty).
  • sloReport({ total, failed, sloTarget }):
    • sli = (total - failed) / total
    • errorBudget = 1 - sloTarget
    • allowedFailures = Math.floor(total * errorBudget)
    • budgetConsumed = (failed / total) / errorBudget (fraction of budget spent, e.g. 0.5 means 50% spent)
    • burnRate = (failed / total) / errorBudget (round sli, errorBudget, budgetConsumed, and burnRate to 4 decimal places with Number(x.toFixed(4))).

5. Check yourself

6. Do it for real (on your machine)

  1. Add io.micrometer:micrometer-registry-prometheus and io.micrometer:micrometer-tracing-bridge-otel to build.gradle.kts, plus the three properties from §3.
  2. Start your service, fire a few requests at /menu and /orders, and inspect the Prometheus scrape output: 
    curl -s localhost:8080/actuator/prometheus | grep http_server_requests_seconds
    You'll see count, sum, max, and histogram buckets labelled by method, uri, and status.
  3. Check your application console logs: every log line written during a request now carries a [traceId,spanId] correlation prefix automatically.
  4. Capstone SLO doc: create docs/slo.md in your PulseOrder repo defining two SLOs: availability (e.g. 99.5% of POST /orders return non-5xx over 28 days) and latency (e.g. 95% of GET /menu complete in < 100 ms).
