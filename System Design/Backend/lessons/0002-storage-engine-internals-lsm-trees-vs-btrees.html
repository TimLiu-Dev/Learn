Storage Engine Internals: LSM-Trees vs. B-Trees, Write-Ahead Logs & Compaction

All distributed systems—from Raft consensus logs and Kafka partitions to Cassandra, RocksDB, and Spanner—are constrained by the physical mechanics of persistent disk storage. To pass as a Senior or Staff Engineer in 2027, you must demonstrate mechanical sympathy: knowing exactly when to choose B-Trees versus LSM-Trees based on read, write, and space amplification.

1. Hardware Physics: The Tyranny of Random Disk I/O

Regardless of whether storage is a spinning hard drive or a modern NVMe SSD, sequential writes are 100x to 1,000x faster than random in-place overwrites:

  • On NVMe SSDs: Flash memory cannot overwrite data in-place without erasing an entire 2MB–8MB flash block. Random updates trigger massive background Flash Translation Layer (FTL) garbage collection, causing high write amplification and SSD wear.
  • Sequential Append: Appending bytes sequentially to an open file stream operates at the physical line-rate of PCIe buses (3,000 to 7,000 MB/s).
B-Tree In-Place Updates vs. LSM-Tree Sequential Append
B-TREE (In-Place Mutation - Postgres / MySQL InnoDB):
Write Key "user:99" -> Search Page -> Lock Page -> Mutate Page in-place on Disk
[ Page 0x01 ] ---> [ Page 0x4B (Random Seek) ] ---> [ Page 0x9F (Random Seek) ]
Result: Slow random disk writes; requires WAL + Double-Write Buffer to prevent torn pages.

LSM-TREE (Append-Only Sequential Writes - RocksDB / Cassandra / ScyllaDB):
Write Key "user:99" -> (1) Append to WAL on disk (Sequential)
                    -> (2) Insert into In-Memory MemTable (SkipList/Red-Black Tree)
                    -> (3) Background flush to Immutable SSTables on Disk
Result: Maximum write throughput; zero random disk writes during write path.

2. Detailed Architectural Comparison: B-Tree vs. LSM-Tree

Dimension B-Tree (PostgreSQL, MySQL, Oracle) LSM-Tree (RocksDB, Cassandra, LevelDB, TiKV)
Primary Design Goal Fast random reads ($O(\log_B N)$) via balanced fixed-size pages (4KB–16KB). Maximum write throughput by eliminating random in-place updates.
Write Path Mechanics Appends to WAL, updates buffer pool page, periodically flushes dirty pages in-place. Appends to WAL, updates in-memory MemTable, sequentially flushes immutable SSTables.
Read Path Mechanics Traverses tree index directly to target page ($1\text{ to }3$ page reads). Checks MemTable $\rightarrow$ queries Bloom filters $\rightarrow$ reads SSTables.
Deletion Semantics Marks slot deleted inside page; immediately reclaims or fragments page. Appends a Tombstone marker; space is reclaimed later during background compaction.
The RUM Trade-Off Optimizes Read latency at expense of Update write speed. Optimizes Update throughput at expense of Read latency & Memory.

3. The Four Core Components of an LSM-Tree

  1. Write-Ahead Log (WAL): An append-only file on disk. Every write (insert, update, delete) is appended to the WAL before being acknowledged. If the server loses power, the WAL is replayed on restart to restore in-memory state.
  2. MemTable: An in-memory, concurrent sorted data structure (typically a SkipList or Red-Black Tree). Because keys are held in sorted order in RAM, range scans and lookups are instantaneous.
  3. Immutable SSTables (Sorted String Tables): When the MemTable exceeds a configured size threshold (e.g. 64MB), it is frozen into a read-only MemTable and flushed sequentially to disk as an SSTable. Once written, an SSTable file is never modified.
  4. Bloom Filters: A space-efficient probabilistic data structure stored in RAM alongside each SSTable. It answers: "Is this key definitely not in this SSTable, or might it be?" If the Bloom filter returns false, the storage engine completely avoids reading that SSTable from disk!
Compaction Strategies: Leveled vs. Size-Tiered

As SSTables accumulate, multiple versions of the same key exist across files, degrading read performance. Compaction merges multiple sorted SSTables into new sorted runs, discarding overwritten versions and tombstones.

  • Size-Tiered Compaction (STCS): Merges SSTables of similar sizes. Great for high write throughput, but requires up to 50% free disk headroom.
  • Leveled Compaction (LCS): Divides storage into Levels (L0, L1, L2, each 10x larger). Key ranges do not overlap in L1+. Guarantees bounded read latency and lower space amplification, at the cost of higher write amplification.
