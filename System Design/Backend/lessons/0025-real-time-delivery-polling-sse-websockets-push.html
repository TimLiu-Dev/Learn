Real-Time Delivery: Polling, SSE, WebSockets & FCM

A customer places a coffee order and watches the status change from received → preparing → ready. How does that update reach their phone? This topic is missing from roadmap.sh, yet it decides the architecture of every chat, live-feed, ride-status, and notification question — and your Android background gives you an unfair advantage.

1. Five ways to push data to a phone

TransportDirectionHow it worksPick it when…
1. Short pollingClient pullsGET /orders/42 every N secondsUpdates are slow (>30 s) and traffic is tiny. Wastes battery and QPS at scale.
2. Long pollingClient pulls, server holdsServer holds the GET open until an event arrives or a timeout expiresFallback when proxies block streaming (historical chat systems).
3. Server-Sent Events (SSE)Server → client streamOne long-lived HTTP response (text/event-stream) with id: and data: frames + automatic reconnect via Last-Event-ID (WHATWG SSE Spec)One-way live updates while the app is open: order status, live scores, LLM token streaming.
4. WebSocketsFull-duplex (both ways)HTTP Upgrade: websocket handshake (RFC 6455), then persistent two-way framesBoth sides send at high rate: 1:1 chat, collaborative docs, multiplayer games.
5. Mobile Push (FCM / APNs)OS-level wakeupYour server calls Firebase Cloud Messaging; Google Play Services wakes the device (FCM Architectural Overview)The app is backgrounded or killed. Best-effort delivery; not guaranteed or strictly ordered.
Your Android edge in interviews

Many backend candidates say "we'll hold a WebSocket to the phone in the background." You know Android's Doze mode and background execution limits kill open sockets when the user locks the screen. The real production answer is SSE (or WebSockets) while foregrounded + FCM push when backgrounded + a fresh GET on app resume as the source of truth.

2. Why two server instances break naive SSE/WebSockets

Multi-instance fan-out via Redis Pub/Sub
 Customer phone ─── SSE (open socket) ───> [ app #1 ] <── SUBSCRIBE order-events ──┐
                                                                                   ├── [ Redis Pub/Sub ]
 Barista tablet ─── PATCH /orders/42 ────> [ app #2 ] ─── PUBLISH order-events ────┘

An open SSE or WebSocket connection is an in-memory socket held by one specific app instance (say, app #1). When the barista taps "Ready", the load balancer can send their PATCH to app #2. App #2 has no reference to app #1's socket! To bridge instances, app #2 writes the new status to Postgres and publishes the event to a shared bus (like Redis Pub/Sub); every app instance subscribes and forwards matching events to its local sockets.

3. Spring SseEmitter + Last-Event-ID replay

When a phone rides through a subway tunnel, its SSE connection drops. On reconnect, SSE clients automatically send the Last-Event-ID header so the server can replay missed events (Spring MVC: Server-Sent Events):

@RestController
class OrderEventsController(private val hub: OrderEventHub) {

    @GetMapping("/orders/{id}/events", produces = [MediaType.TEXT_EVENT_STREAM_VALUE])
    fun stream(
        @PathVariable id: Long,
        @RequestHeader("Last-Event-ID", required = false) lastId: Long?
    ): SseEmitter {
        val emitter = SseEmitter(0L)
        hub.subscribe(orderId = id, lastEventId = lastId) { evt ->
            emitter.send(SseEmitter.event().id(evt.id.toString()).name("status").data(evt.data))
        }
        return emitter
    }
}
☕ Java on the side: the same SSE endpoint 
@GetMapping(value = "/orders/{id}/events", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter stream(@PathVariable long id,
                         @RequestHeader(value = "Last-Event-ID", required = false) Long lastId) {
    SseEmitter emitter = new SseEmitter(0L);
    hub.subscribe(id, lastId, evt ->
        emitter.send(SseEmitter.event().id(String.valueOf(evt.id())).name("status").data(evt.data()))
    );
    return emitter;
}

4. Practice: bounded replay hub + multi-instance fan-out

Implement createEventHub(bufferSize):

  • publish(data) assigns an incrementing numeric id (starting at 1), keeps only the last bufferSize events in a ring/sliding buffer, notifies all active subscribers, and returns the created { id, data }.
  • subscribe(lastEventId, onEvent):
    • If lastEventId is provided and is older than the oldest buffered event (meaning some events were evicted, i.e. buffer.length > 0 && lastEventId < buffer[0].id - 1), immediately deliver { id: null, data: 'RESYNC' } so the client knows to do a full HTTP GET.
    • Otherwise, if lastEventId is provided, immediately replay every buffered event with event.id > lastEventId in order.
    • Register onEvent so future publish() calls deliver to it, and return an unsubscribe() function.

5. Check yourself

6. Do it for real (on your machine)

  1. Add the /orders/{id}/events endpoint above to your service and watch it in one terminal with curl -N http://localhost:8080/orders/1/events (-N disables output buffering).
  2. In a second terminal, call curl -X PATCH http://localhost:8080/staff/orders/1/status -H 'Content-Type: application/json' -d '{"status":"PREPARING"}' and watch the SSE frame (id: 1, event: status, data: ...) appear immediately in terminal 1.
  3. Stop curl -N, publish two more status updates, then reconnect with curl -N -H 'Last-Event-ID: 1' http://localhost:8080/orders/1/events and watch events 2 and 3 replay on connect.
  4. Android bonus: add com.squareup.okhttp3:okhttp-sse to your Android app and connect an EventSource while the Order Status screen is visible (`Lifecycle.State.STARTED`). When the status becomes READY and the user isn't connected, trigger an FCM notification message via the Firebase Admin SDK.
  5. Java on the side: run the Java controller snippet in your Java project and test with the same two curl -N commands.
✓ Win condition

Live status frames stream to curl -N, reconnecting with Last-Event-ID replays missed frames, and publishing through Redis Pub/Sub reaches a client connected to a different instance.
