Distributed Rate Limiting: Algorithms, Redis Clusters & Edge Coordination

Rate limiting is the archetypal system design interview question: it deceptively appears simple, yet exposes whether a candidate grasps concurrency race conditions, memory sizing, distributed state coordination, and failover topologies.

1. The Four Core Rate Limiting Algorithms

In an interview, you must instantly contrast algorithms based on memory overhead, burst tolerance, and accuracy:

Algorithm Memory Complexity Burst Handling Production Trade-off
Token Bucket O(1) (Tokens count + Last timestamp) Permits bursts up to bucket capacity. Industry Standard (Stripe/AWS): Highly memory efficient; allows natural traffic bursts while maintaining average throughput.
Leaky Bucket (FIFO) O(Queue Size) or O(1) Smooths bursts into constant rate. Ideal for packet egress or queuing background jobs; drops or delays traffic if queue overflows.
Fixed Window Counter O(1) (1 integer per window) Vulnerable to 2x burst at boundary. Dangerous edge flaw: A burst at 00:59 and 01:01 doubles permitted quota across that 2-second span.
Sliding Window Log O(N) (Stores timestamp per request) 100% Mathematically accurate. Memory prohibitive: 100k requests = 100k stored timestamps in Redis sorted set. Unviable at scale.
Sliding Window Counter O(1) (Current count + Previous count) Smooth rolling approximation. Gold Standard for Distributed Redis: Combines low O(1) memory of fixed windows with 99.9% rolling accuracy.
Sliding Window Counter Calculation Logic
+------------------------------+------------------------------+
| Previous Window (Count: 80)  |  Current Window (Count: 30)  |
+------------------------------+------------------------------+
[00:00                 01:00]  [01:00        * (01:18)  02:00]
                                             |
                                             v 30% through window (elapsed = 0.3)
Formula:
  Weight of Previous Window = 1.0 - 0.3 = 0.70
  Estimated Requests In Rolling 60s = (80 * 0.70) + 30 = 56 + 30 = 86 requests
  If Limit = 100 -> 86 < 100 -> REQUEST ALLOWED (Increment current to 31)

2. Mid Tech vs. Big Tech Architecture

The Mid Tech Approach: Centralized Redis Cluster with Atomic Lua Scripts

In a mid-sized architecture (1,000 to 50,000 QPS), API instances route requests through a shared Redis cluster. The fatal mistake junior engineers make is executing a GET count, incrementing in application memory, and calling SET count. Under concurrent load, this creates a catastrophic Read-Modify-Write Race Condition.

⚠️ The Atomicity Requirement

To eliminate race conditions without distributed locks (which introduce severe latency), Redis executes an embedded Lua Script. Because Redis executes scripts in a single-threaded event loop, the entire check-and-increment runs atomically in a single network roundtrip. 

-- Production Redis Lua Script for Sliding Window Counter
local key = KEYS[1]
local current_bucket = ARGV[1]
local prev_bucket = ARGV[2]
local weight = tonumber(ARGV[3])
local limit = tonumber(ARGV[4])

local prev_count = tonumber(redis.call('HGET', key, prev_bucket) or '0')
local curr_count = tonumber(redis.call('HGET', key, current_bucket) or '0')

local estimated = math.floor(prev_count * weight + curr_count)

if estimated < limit then
    redis.call('HINCRBY', key, current_bucket, 1)
    redis.call('EXPIRE', key, 120) -- TTL safety cleanup
    return {1, limit - estimated - 1} -- {Allowed: true, Remaining}
else
    return {0, 0} -- {Allowed: false, Remaining: 0}
end

The Big Tech Approach (10,000,000+ QPS): Local Batching & Edge Synchronization

At Google or Cloudflare scale, sending 10M requests/second to a centralized Redis cluster will saturate network interfaces and blow past CPU limits.

  • Local In-Memory Token Batching: Each microservice instance requests a quota chunk (e.g., 100 tokens) from the cluster once every few seconds. Local worker threads decrement their in-memory quota with sub-microsecond latency.
  • Edge Rate Limiting (Cloudflare / Envoy / eBPF): Rate limiting is enforced at regional Point-of-Presence (PoP) edge servers via Anycast DNS, stopping DDoS attacks before traffic hits the core cloud infrastructure.
  • Failure Mode (Fail-Open vs. Fail-Closed): Always state your failure strategy in an interview: "If Redis fails or partitions, critical business APIs (e.g. Checkout) fail open to local fallback heuristics, whereas unauthenticated public endpoints fail closed."
