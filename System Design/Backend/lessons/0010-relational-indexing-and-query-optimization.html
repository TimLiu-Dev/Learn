Mid Tech Core Database Internals Composite Indexes & PgBouncer

Relational Data Modeling, B-Tree Indexes & Partitioning

Relational databases power financial ledgers, identity stores, and e-commerce transactions. Senior developers must know how B+ Tree leaf pages organize data, how composite indexes enforce the leftmost prefix rule, and how to size connection pools without crashing PostgreSQL.

1. The Mechanics of B+ Tree Indexes

In modern relational engines (Postgres, MySQL InnoDB), indexes are structured as B+ Trees:

  • Branch / Root Pages: Contain routing keys and child page pointers. Highly cached in RAM buffer pools.
  • Leaf Pages: Contain actual index keys paired with row pointers (or the clustered row data itself in InnoDB). Leaf pages are linked bidirectionally as a doubly linked list, enabling ultra-fast range scans without re-traversing the tree root.
  • Height of the Tree: With a branching factor of ~100–300 per 16KB page, a 3-level B+ Tree indexes over 10,000,000 rows in only 3 page lookups!
Composite Index Leftmost Prefix Rule: INDEX(status, created_at)
Index sorted primarily by "status", then secondarily by "created_at":
[ ('ACTIVE', 100) ] -> [ ('ACTIVE', 150) ] -> [ ('PENDING', 90) ] -> [ ('PENDING', 120) ]

Query 1: WHERE status = 'ACTIVE' AND created_at > 120
-> USES INDEX EFFICIENTLY: Jumps straight to ('ACTIVE', 150) in O(log N).

Query 2: WHERE status = 'ACTIVE'
-> USES INDEX EFFICIENTLY: Reads all 'ACTIVE' entries sequentially.

Query 3: WHERE created_at > 120 (OMITTING 'status')
-> CANNOT USE INDEX! Full Table Scan required, because created_at is only sorted
   within individual status groups!

2. Covering Indexes and Connection Pool Sizing

The Power of the Covering Index (Index-Only Scan)

If your query only requests columns present in the index (e.g. SELECT user_id, created_at FROM orders WHERE status = 'PAID' with INDEX(status, created_at, user_id)), the database engine performs an Index-Only Scan. It completely skips reading the heap table pages from disk, cutting I/O by up to 90%!

Why 10,000 Database Connections Crash Postgres: Pool Sizing Math

Junior engineers often set their connection pool max size to 5,000 connections during high load. This causes server collapse:

  • PostgreSQL forks an independent OS process per connection, consuming 5MB–10MB of private RAM and thrashing the OS kernel with CPU context switching.
  • The Optimal Pool Sizing Formula (Postgres & HikariCP): $$\text{Pool Size} = (\text{CPU Cores} \times 2) + \text{Disk Spindles}$$ On an 8-core NVMe server, the optimal pool size is 17 to 20 connections. Use PgBouncer as an external connection pooler to multiplex 10,000 client sockets into 20 database backend processes!
