Transactions & Isolation: Don't Sell the Last Croissant Twice

Two customers tap "Order" on the last croissant at the same moment. Both requests read stock = 1, both see "in stock", and both write stock = 0. You've sold two croissants and own one. The skill in this lesson: spot the read-modify-write race and fix it three ways. roadmap.sh doesn't cover this at all, yet it comes up in almost every order, booking, or payment design question.

1. ACID in four lines

LetterPromiseCroissant meaning
AtomicityAll of the transaction's writes happen, or none doOrder row and stock decrement commit together
ConsistencyYour invariants hold (enforced partly by constraints)CHECK (stock_qty >= 0)
IsolationConcurrent transactions don't see each other's half-finished work……to a degree that depends on the isolation level
DurabilityOnce committed, it survives a crashThe order isn't lost on restart

The "I" is where bugs hide. PostgreSQL's default isolation level is Read Committed: each statement sees data committed before that statement began (PostgreSQL: Transaction Isolation). That prevents dirty reads, but it does not protect a read-then-write sequence done in your application code.

2. The bug: a lost update

// ❌ Broken under concurrency, even inside @Transactional at Read Committed
val item = repo.findById(id)                 // both requests read qty = 1
if (item.qty > 0) {
    repo.save(item.copy(qty = item.qty - 1)) // both write qty = 0 → two orders, one croissant
}

Kleppmann calls this the lost update problem: two read-modify-write cycles interleave and one overwrites the other (DDIA ch. 7). There are three standard fixes:

FixHowBest when
1. Atomic conditional updateUPDATE items SET qty = qty - 1 WHERE id = :id AND qty > 0, then check rows affected (1 = sold, 0 = sold out)The change fits in one statement. Simplest and fastest. Default choice.
2. Pessimistic lockSELECT … FOR UPDATE locks the row, so other transactions wait until you commitComplex logic between read and write, with conflicts expected to be common
3. Optimistic lockA version column: UPDATE … SET qty = ?, version = version + 1 WHERE id = ? AND version = ?. Zero rows means someone else got there first, so retryConflicts are rare and you don't want to hold locks (e.g. editing a menu item)

Postgres makes fix 1 safe: a concurrent UPDATE on the same row waits for the first transaction, then re-checks the WHERE clause against the newly committed row (Read Committed details). Spring Data JDBC implements fix 3 for you. Add a @Version property and a conflicting save() throws OptimisticLockingFailureException (Spring Data JDBC: optimistic locking).

3. @Transactional in one paragraph

Put @Transactional on a service method and Spring wraps the call in a proxy: begin, run your method, then commit. If a RuntimeException or Error escapes, it rolls back instead. Checked exceptions do not trigger a rollback by default, so use rollbackFor if you throw one (Spring: rolling back). Kotlin doesn't distinguish checked exceptions, but Spring still does: an IOException thrown from Kotlin won't roll back. Because it works through a proxy, calling a @Transactional method from inside the same class skips the proxy, and no transaction starts.

@Service
class OrderService(private val items: ItemRepository, private val orders: OrderRepository) {

    @Transactional
    fun placeOrder(userId: Long, itemId: Long, qty: Int): Order {
        val updated = items.decrementIfAvailable(itemId, qty)   // fix 1: atomic + conditional
        if (updated == 0) throw OutOfStockException(itemId)     // RuntimeException → rollback → 409
        return orders.save(Order(userId = userId, itemId = itemId, qty = qty))
    }
}

interface ItemRepository : CrudRepository<Item, Long> {
    @Modifying
    @Query("UPDATE items SET stock_qty = stock_qty - :qty WHERE id = :id AND stock_qty >= :qty")
    fun decrementIfAvailable(id: Long, qty: Int): Int
}
☕ Java on the side: the same service 
@Service
public class OrderService {
    private final ItemRepository items; private final OrderRepository orders;
    public OrderService(ItemRepository items, OrderRepository orders) { this.items = items; this.orders = orders; }

    @Transactional
    public Order placeOrder(long userId, long itemId, int qty) {
        if (items.decrementIfAvailable(itemId, qty) == 0) throw new OutOfStockException(itemId);
        return orders.save(new Order(null, userId, itemId, qty));
    }
}

4. Practice: optimistic locking with retry

The simulated database lets another buyer sneak in between your read and your write. Implement:

  • buyOptimistic(db, id, maxRetries): read {qty, version}. If qty === 0, return 'SOLD_OUT'. Otherwise call db.compareAndSet(id, version, qty - 1). If that returns false, someone else won, so re-read and retry. Make at most maxRetries retries after the first attempt, then return 'CONFLICT'. Return 'OK' on success.
  • buyAtomic(db, id): one call to db.decrementIfPositive(id), which returns the number of rows affected (1 or 0).

6. Do it for real (on your machine)

  1. Reproduce the race in two psql sessions. Add migration V3__items.sql: CREATE TABLE items (id BIGINT PRIMARY KEY, name TEXT NOT NULL, stock_qty INT NOT NULL CHECK (stock_qty >= 0)); INSERT INTO items VALUES (1, 'croissant', 1); Then open two terminals with docker exec -it notes-db psql -U postgres -d notes: 
    -- A: BEGIN; SELECT stock_qty FROM items WHERE id = 1;    -- 1
-- B: BEGIN; SELECT stock_qty FROM items WHERE id = 1;    -- 1
-- A: UPDATE items SET stock_qty = 0 WHERE id = 1; COMMIT;   -- "app" computed 1 - 1
-- B: UPDATE items SET stock_qty = 0 WHERE id = 1; COMMIT;   -- succeeds too → two sales
  2. Now the fix. Reset the stock to 1 and have both sessions run UPDATE items SET stock_qty = stock_qty - 1 WHERE id = 1 AND stock_qty > 0;. B blocks until A commits, then reports UPDATE 0. That 0 is your 409 Out of Stock.
  3. In Spring: add ItemRepository.decrementIfAvailable and a @Transactional OrderService.placeOrder like §3. Map OutOfStockException to 409 Conflict (e.g. with @ResponseStatus(HttpStatus.CONFLICT) on the exception class).
  4. Hammer it: set the stock to 5 and fire 20 concurrent orders: 
    seq 20 | xargs -P 20 -I{} curl -s -o /dev/null -w '%{http_code}\n' -X POST localhost:8080/orders \
  -H 'Content-Type: application/json' -d '{"itemId":1,"qty":1}' | sort | uniq -c
#   5 201
#  15 409
    Then swap in the broken "read, check, save" version and run it again. You'll often see more than 5 × 201, which means overselling.
  5. Java on the side: write the same service in Java and repeat step 4.
✓ Win condition

Exactly 5 × 201 and 15 × 409 on every run, and stock never goes negative (the CHECK constraint is your safety net).
