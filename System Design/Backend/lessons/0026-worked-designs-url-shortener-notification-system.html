2. Worked Design A: URL Shortener (TinyURL / bit.ly)

  • 1. Requirements: POST a long URL → get a short URL like https://sho.rt/2Bi; GET /{code} redirects to the long URL. Non-functional: 100:1 read:write ratio, low redirect latency (<20 ms p95 at server), links persist for 10 years.
  • 2. Estimation (10M DAU, 1 new link per 10 users/day = 1M writes/day):
    • Write QPS = 1,000,000 / 86,400 ≈ 12 writes/s. Read QPS (100:1) ≈ 1,200 reads/s.
    • 10-year rows = 1M × 365 × 10 = 3.65B rows. At ~500 bytes/row ≈ 1.83 TB — fits on one primary Postgres with read replicas plus Redis for the hot 20%.
    • Code length: Base62 (0-9a-zA-Z) with 7 chars gives $62^7 = 3{,}521{,}614{,}606{,}208$ (≈3.52 trillion) codes — 960× headroom over 3.65B.
  • 3. API & schema:
    • POST /urls {"longUrl":"https://..."} → 201 Created {"code":"2Bi","shortUrl":"https://sho.rt/2Bi"} (400 if invalid URL).
    • GET /{code} → 301 or 302 with header Location: https://... (404 if unknown).
    • Table: urls(id BIGINT PRIMARY KEY, code VARCHAR(10) UNIQUE NOT NULL, long_url TEXT NOT NULL, created_at TIMESTAMPTZ).

 Client ── GET /2Bi ──> [ L7 LB ] ──> [ Shortener Service ] ──(1) cache-aside ──> [ Redis (code -> longUrl) ]
                                              │                                         │ (miss)
                                              └──(2) write / fallback ──────────> [ Postgres + sequence ]
  • 5. Two deep dives interviewers always ask:
    1. Base62 counter vs hash truncation: truncating SHA-256 to 7 chars risks collisions and forces a DB lookup-and-retry loop. Converting a unique 64-bit integer ID (from a DB sequence or range-allocated ID generator) to Base62 is collision-free by construction (System Design Primer: Pastebin / URL shortener).
    2. 301 Moved Permanently vs 302 Found (RFC 9110 §15.4): browsers cache a 301 indefinitely, so repeat clicks bypass your server — lowest server load, but you lose repeat-click analytics and cannot update the destination URL. A 302 hits your server every time, giving accurate click analytics and mutable links at the cost of higher read QPS (which Redis absorbs). State both and let the interviewer pick the product priority!
☕ Kotlin & Java: Base62 encoding a database ID 
// Kotlin
private const val ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"
fun encodeBase62(num: Long): String {
    if (num == 0L) return "0"
    var n = num; val sb = StringBuilder()
    while (n > 0) { sb.append(ALPHABET[(n % 62).toInt()]); n /= 62 }
    return sb.reverse().toString()
}

3. Worked Design B: Multi-Channel Notification System (FCM, APNs, Email, SMS)

  • 1. Requirements: Internal services (like PulseOrder's order service) trigger notifications across mobile push (FCM/APNs), email, and SMS. Must respect user opt-outs, prevent duplicate sends on retry, and survive third-party provider slowdowns.
  • 2. API & schema:
    • POST /notifications with header Idempotency-Key and body {"userId":42,"template":"ORDER_READY","channels":["PUSH","SMS"],"vars":{"orderId":108}} → 202 Accepted (queued asynchronously).
    • Tables: device_tokens(user_id, platform, token), user_prefs(user_id, channel, enabled), notification_log(idempotency_key PRIMARY KEY, user_id, status, created_at).

  • Deep dives (Alex Xu, System Design Interview Vol. 1: Notification System):
    1. Never call providers synchronously in the caller's request: if Twilio takes 3 seconds or is down, checkout fails. Return 202 Accepted (or write to an Outbox table, 0011) and fan out through isolated per-channel queues so an SMS outage never delays FCM pushes (0012 Bulkheads).
    2. At-least-once delivery + deduplication: workers retry on timeout with exponential backoff + jitter and move poison messages to a Dead Letter Queue (0017); the notification_log unique key prevents sending the same alert twice (0008).

4. Practice: Base62 codec & capacity estimator

Implement the two calculators you'll run in your head during design rounds:

  • encodeBase62(n) and decodeBase62(str) using the alphabet "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ" (0 → "0", 61 → "Z", 62 → "10").
  • estimateCapacity({ dau, writesPerUserPerDay, readWriteRatio, bytesPerRecord, years }) using 86400 seconds/day and 365 days/year, rounding writeQps and readQps with Math.ceil, and returning { writeQps, readQps, totalRecords, storageBytes }.
