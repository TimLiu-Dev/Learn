Global Distributed Transactions: 2PC vs. Spanner TrueTime

Executing multi-shard ACID transactions across distributed databases requires solving the blocking coordinator trap of Two-Phase Commit (2PC) and establishing global serializability without cross-continent coordination locks.

1. The Two-Phase Commit (2PC) Blocking Dilemma

Two-Phase Commit coordinates atomic transactions across multiple autonomous database shards:

  • Phase 1 (Prepare): The Coordinator sends a PREPARE message to all participants (cohorts). Each cohort acquires exclusive row locks, writes the intent to its local WAL, and replies with VOTE_COMMIT or VOTE_ABORT.
  • Phase 2 (Commit): If all cohorts voted commit, the coordinator persists GLOBAL_COMMIT and broadcasts commit to all cohorts. If any cohort voted abort, the coordinator broadcasts GLOBAL_ABORT.
The Fundamental Flaw: 2PC is a Blocking Protocol

If the Coordinator crashes after cohorts have voted commit but before sending the commit message, cohorts are left in a state of indefinite uncertainty. They cannot abort (the coordinator might have committed), nor can they commit (it might have aborted). They must hold row locks indefinitely, blocking all subsequent reads and writes across the entire database cluster!

Modern Fix: Paxos-Replicated Coordinators (Spanner / CockroachDB)
Instead of a single coordinator node that can crash:
The Coordinator is a FAULT-TOLERANT PAXOS GROUP (3 or 5 replicas across datacenters)!
                    +------------------------------------+
                    |  Paxos-Replicated Transaction Group|
                    |  (Leader commits intent via Raft)  |
                    +------------------------------------+
                                 /          \
                Phase 1: PREPARE/            \Phase 1: PREPARE
                               v              v
               +--------------------+    +--------------------+
               | Paxos Group Shard A|    | Paxos Group Shard B|
               | (Lock rows in WAL) |    | (Lock rows in WAL) |
               +--------------------+    +--------------------+
If the active coordinator leader crashes, the Paxos group immediately elects a new leader,
reads the committed transaction state from the replicated log, and resumes Phase 2 seamlessly!

2. Google Spanner's Breakthrough: The TrueTime API & Commit Wait

How does Google Spanner execute globally distributed transactions with External Consistency (Linearizability) without acquiring global locks across datacenters?

The TrueTime Uncertainty Bound: [earliest, latest]

Google equipped every datacenter with GPS receivers and atomic rubidium clocks. The TrueTime.now() API does not return a single float timestamp; it returns an interval $[t_{\text{earliest}}, t_{\text{latest}}]$ where the clock uncertainty $\epsilon$ is bounded between 1ms and 7ms.

Spanner Mechanism How It Operates Guaranteed Invariant
Commit Timestamp ($s$) Leader sets commit timestamp $s = \text{TrueTime.now().latest}$. Guarantees $s$ is strictly $\ge$ absolute real wall-clock time at invocation.
Commit Wait Rule Leader refuses to release locks or return success to client until $\text{TrueTime.now().earliest} > s$ (waiting $2\epsilon$). Guarantees that any future transaction starting after this commit will be assigned a timestamp strictly greater than $s$.
Lock-Free Snapshot Reads Read-only transactions specify timestamp $T_{\text{read}}$ and read historical MVCC versions without locks. Reads never block writes, and writes never block reads across global regions.
