PulseOrder: A Mobile Order-Ahead Backend

A coffee-shop style "order ahead" system. Customers browse a menu, place orders, and watch the status change live. Staff move orders from received → preparing → ready. You build the backend and the Android client. That is your edge: few backend juniors can show both ends of a production-style system.

1. Why this project

  • Every Part 1 topic has a natural home. Orders need transactions, retries need idempotency, the menu needs caching, status updates need real-time delivery, and a lunch rush needs rate limiting.
  • It's a classic interview shape. You can defend it in the same format as "design a food-delivery or ticketing system".
  • It grows into Part 2. The senior capstone, NexusPulse, turns PulseOrder into a multi-tenant payments and event platform. You won't throw anything away.

10. Interview defense (L3/L4)

"How do you stop a flaky mobile network from creating two orders?"

The app generates an Idempotency-Key once per checkout and reuses it on every retry. The server inserts (user_id, key) under a unique constraint in the same transaction as the order and stores the response. A replay returns the stored response instead of creating a new order (0008).

"How do you stop overselling the last item?"

Decrement with a conditional update (… SET stock_qty = stock_qty - :n WHERE id = :id AND stock_qty >= :n) and check the affected row count inside the order transaction. Zero rows means 409 and a rollback (0022).

"Why cache the menu but not orders?"

The menu is read-heavy, shared by everyone, changes rarely, and can tolerate a few seconds of staleness: use a TTL and invalidate on staff edits. Orders are per-user and must be read-your-writes consistent.

"An instance dies while my app holds an SSE connection. What happens?"

The client reconnects through the load balancer to another instance and sends Last-Event-ID. Any instance can serve it, because events are fanned out through Redis pub/sub and the current status is in Postgres. FCM covers the backgrounded case.

"Traffic grows 10×. What breaks first, and what do you do?"

The app tier scales out because it's stateless. The database is usually the bottleneck, so: cache hot reads, add a read replica for history, cap connection pools, and absorb notification spikes with the queue. Partitioning by shop is a Part 2 conversation (0006).

"Why Postgres and not a NoSQL store?"

Orders, line items, and inventory need multi-row transactions and joins, and the scale is modest. Write the reasoning down as ADR-0001.
