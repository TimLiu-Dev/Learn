3. Core Technical Innovations to Defend in Senior Rounds

Key Architectural Pillars
  • Zero-Loss Transactional Outbox + WAL CDC: Replaces vulnerable dual-writes with Postgres WAL Change Data Capture into Kafka, guaranteeing at-least-once event publication with idempotent consumers and zero Two-Phase Commit lock contention (0011, 0005).
  • Double-Entry Ledger Integrity: Append-only double-entry accounting where every payment writes balanced debit and credit rows in integer cents (SUM(amount_cents) = 0 per transaction ID), eliminating floating-point drift and silent balance mutations.
  • Two-Tier Rate Limiting & Idempotency: Combines local token-bucket pre-allocation with Redis Lua scripts (0001), and pairs short-lived Redis SET NX locks with a Postgres unique constraint fallback (0008).
  • Zero-Downtime Schema Evolution: Executes a 5-phase Expand-Contract migration on the live ledger table under load test without metadata-lock stalls (0016).

7. Live Senior Interview Defense Guide

Q1: "Why not use Two-Phase Commit (2PC) between Postgres and Kafka instead of the Outbox pattern?"

Senior Answer: 2PC is a blocking protocol (0007). If the coordinator crashes or Kafka experiences a temporary network partition, Postgres holds row locks and blocks checkout commits, coupling database availability to broker availability. The Transactional Outbox pattern (0011) commits the ledger entries and the outbox row in a single local ACID transaction, and CDC streams from the Write-Ahead Log asynchronously without holding transactional locks.

Q2: "How do you handle a Redis cluster partition or failure in your rate limiter?"

Senior Answer: We set explicit fail-open vs fail-closed policies per endpoint tier (0001). For authenticated payment endpoints (protected downstream by idempotency keys and database constraints), we fail open to a conservative local in-memory token bucket on each Spring Boot instance and fire a burn-rate alert (0027) rather than dropping revenue. For unauthenticated public endpoints, we fail closed or shed load at the edge.

Q3: "Why keep the ledger in a B-Tree relational engine (Postgres) instead of an LSM-Tree wide-column store?"

Senior Answer: Double-entry ledger transfers require multi-row ACID transactions, conditional balance checks, and immediate read-your-writes consistency on secondary indexes (0002, 0010). B+ Trees excel at predictable point reads and row-level locking, whereas high-fan-out immutable event logs and audit streams fit append-optimized log/LSM storage (Kafka + cold object storage).
