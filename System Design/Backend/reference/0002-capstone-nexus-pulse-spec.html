2. Core Technical Innovations (What Sets This Apart)

Key Architectural Features to Highlight on Resume
  • Zero-Loss Transactional Outbox: Replaced vulnerable dual-write operations with Postgres WAL-level Change Data Capture (CDC via Debezium), guaranteeing exactly-once event publication to Kafka without 2-phase commit overhead.
  • Double-Entry Ledger Integrity: Engineered append-only double-entry financial accounting. Debits and credits are validated via Postgres constraints (sum(balance) = 0 invariant), preventing negative balances and currency floating errors.
  • High-Performance Distributed Rate Limiting: Deployed a local token-bucket batching layer in Go/Node.js microservices combined with Redis Cluster Lua scripts, slashing Redis network roundtrips by 94% under heavy spikes.
  • Lock-Free Idempotent Key Resolution: Used two-tier caching with Redis NX locks for in-flight requests and Postgres unique constraint fallback, ensuring absolute protection against network retries without thread blocking.

5. Live Interview Defense Guide

Q1: "Why not use Two-Phase Commit (2PC) between Postgres and Kafka instead of the Outbox pattern?"

Senior Answer: 2PC is a blocking protocol. If the coordinator crashes or Kafka experiences temporary network partition, the relational database locks rows and halts transaction commit, degrading overall database availability. The Transactional Outbox pattern couples the business update and the event table within a single local ACID transaction. Decoupled CDC asynchronously streams from the Write-Ahead Log without holding transactional locks.

Q2: "How do you handle Redis cluster partition or failure in your rate limiter?"

Senior Answer: We configure fail-open vs fail-closed policies based on client tier. For critical payment endpoints, we fail open to a degraded local in-memory token bucket on each app server instance to avoid blocking revenue, accompanied by an immediate alerting event. For untrusted public endpoints, we fail closed to prevent DDoS attacks.
