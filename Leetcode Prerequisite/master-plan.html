Technical Coding Interview Protocol (Industry Standard)

Consensus Rubric

The Core Question: "Do I verbally present brute force and then only write code of the optimal solution?"

The Absolute Consensus
Yes. In 95% of technical coding interviews, you verbally walk through brute force (30–60s) and write code only for the optimal solution. Writing optimal code immediately within 10 seconds is considered an active red flag: it signals rote memorization rather than systematic engineering reasoning.
1
Clarify & Validate Inputs (Minutes 0 – 5)

Ask about bounds, empty inputs, duplicate elements, negative values, and whether memory or execution speed is the primary optimization target.

2
State the Brute-Force Baseline (Minutes 5 – 6)

"The naive baseline is an exhaustive nested scan comparing all pairs in O(n²) time and O(1) auxiliary space."

3
Isolate the Bottleneck & Propose Optimal (Minutes 6 – 9)

"The bottleneck is repeatedly scanning the array to find the complement. We can trade O(n) auxiliary memory in a hash map to get O(1) lookups, dropping overall time to O(n)."

4
Secure Consensus (Minute 9 – 10)

Ask: "Does this approach sound good to you, or would you like me to start coding this up?"

5
Implement Only the Optimal Solution (Minutes 10 – 30)

Write idiomatic, modular code. (Only code brute force if the interviewer explicitly asks or if you are stuck).

6
Dry-Run Line-by-Line with a State Table (Minutes 30 – 45)

Trace sample inputs and edge cases manually using a tabular walkthrough without relying on a compiler, debugger, or print statements.
