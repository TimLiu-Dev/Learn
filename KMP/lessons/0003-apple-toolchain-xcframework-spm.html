The Apple Toolchain: CocoaPods vs. SPM vs. Direct XCFrameworks

Master Kotlin/Native Apple compilation targets, XCFramework generation, and modern Swift Package Manager (SPM) distribution.

1. The Why & Architectural Mental Model

To run on iOS, Kotlin code must be compiled by Kotlin/Native into an Apple-compatible binary artifact. Historically, CocoaPods was used. Today, the industry has migrated heavily toward XCFrameworks and Swift Package Manager (SPM).

An XCFramework is an Apple binary package containing multiple architecture slices (e.g. ios-arm64 for real devices and ios-arm64_x86_64-simulator for Xcode simulators) in a single bundle.

2. Production Code Examples

Exporting an XCFramework in build.gradle.kts

import org.jetbrains.kotlin.gradle.plugin.mpp.apple.XCFramework

kotlin {
    val xcf = XCFramework("SharedKit")
    
    listOf(
        iosArm64(),
        iosSimulatorArm64()
    ).forEach { iosTarget ->
        iosTarget.binaries.framework {
            baseName = "SharedKit"
            isStatic = true
            xcf.add(this)
        }
    }
}

Running ./gradlew assembleSharedKitXCFramework produces the complete bundle inside build/XCFrameworks/release/SharedKit.xcframework.

3. Production Pitfalls & Anti-Patterns

Pitfall: Missing Simulator Arm64 Slice
On Apple Silicon Macs (M1/M2/M3/M4), Xcode runs simulators in arm64. If your build only includes iosX64() (Intel simulator), Xcode will fail to link on Apple Silicon hardware. Always include iosSimulatorArm64()!
