Mocking in Multiplatform: Fakes vs. Mockative

Discover why senior architects prefer Test Fakes over mocks, and explore Ktor MockEngine for network testing.

1. The Why & Architectural Mental Model

In multiplatform engineering, Test Fakes are vastly superior to runtime mocks:

  • Fakes are lightweight, in-memory implementations of your interfaces (e.g. FakeIncidentRepository). They have zero third-party dependencies, compile in 0ms on all targets, and are 100% type-safe.
  • Ktor MockEngine: For networking, instead of mocking the HttpClient class, Ktor provides a native MockEngine where you configure simulated HTTP status codes, headers, and JSON responses.

2. Production Code Examples

Mocking Network Responses with Ktor MockEngine

package com.pulsesync.network

import io.ktor.client.*
import io.ktor.client.engine.mock.*
import io.ktor.http.*
import kotlin.test.*
import kotlinx.coroutines.test.runTest

class IncidentApiClientTest {

    @Test
    fun shouldParseIncidentsJsonCorrectly() = runTest {
        val mockEngine = MockEngine { request ->
            respond(
                content = """[{"id":"1","title":"Database Lag","timestamp":1700000000}]""",
                status = HttpStatusCode.OK,
                headers = headersOf(HttpHeaders.ContentType, "application/json")
            )
        }

        val client = createKtorClient(mockEngine)
        val incidents = IncidentApiClient(client).fetchIncidents()

        assertEquals(1, incidents.size)
        assertEquals("Database Lag", incidents[0].title)
    }
}

3. Production Pitfalls & Anti-Patterns

Pitfall: Mocking What You Don't Own
Never mock third-party library classes (e.g. trying to mock RoomDatabase or OkHttpClient). Mocking external classes creates brittle tests that break on library upgrades. Always mock your own repository interfaces or use Ktor's official MockEngine.
