Anatomy of a Modern KMP Project & Gradle Kotlin DSL

Master the multiplatform project layout, Gradle Version Catalogs (libs.versions.toml), and hierarchical source sets in Kotlin 2.x.

1. The Why & Architectural Mental Model

In single-platform Android development, Gradle compiles Kotlin source files directly into JVM bytecode (`.class` → `.dex`). In Kotlin Multiplatform (KMP), Gradle orchestrates multiple distinct compiler backends simultaneously:

  • Kotlin/JVM compiles code for Android and JVM runtimes.
  • Kotlin/Native compiles code using an LLVM backend directly into ARM64/x86_64 machine code for Apple Silicon and iOS runtimes.

To prevent code duplication, modern KMP uses a Hierarchical Source Set Structure. Code written in commonMain is compiled by both backends. Platform-specialized code resides in androidMain and iosMain: 

                     [ commonMain ]
              (Shared logic, Domain, Models)
                     /            \
                    /              \
           [ androidMain ]      [ iosMain ]
           (OkHttp, Keystore)   (Darwin, Keychain)
                                 /      \
                                /        \
                        [ iosArm64 ]   [ iosSimulatorArm64 ]
Kotlin 2.x Default Hierarchy Template
In modern Kotlin (2.x+), the Kotlin Multiplatform Gradle plugin automatically configures intermediate source sets like iosMain when you declare iosArm64() and iosSimulatorArm64(). You no longer need manual dependsOn calls for standard Apple targets.

2. Production Gradle Configuration

Modern industry standards mandate Gradle Version Catalogs (gradle/libs.versions.toml) for type-safe, centralized dependency management.

Part A: gradle/libs.versions.toml

[versions]
kotlin = "2.1.0"
agp = "8.7.2"
coroutines = "1.9.0"
ktor = "3.0.1"

[libraries]
coroutines-core = { module = "org.jetbrains.kotlinx:kotlinx-coroutines-core", version.ref = "coroutines" }
ktor-client-core = { module = "io.ktor:ktor-client-core", version.ref = "ktor" }
ktor-client-okhttp = { module = "io.ktor:ktor-client-okhttp", version.ref = "ktor" }
ktor-client-darwin = { module = "io.ktor:ktor-client-darwin", version.ref = "ktor" }

[plugins]
kotlin-multiplatform = { id = "org.jetbrains.kotlin.multiplatform", version.ref = "kotlin" }
android-library = { id = "com.android.library", version.ref = "agp" }

Part B: shared/build.gradle.kts

plugins {
    alias(libs.plugins.kotlin.multiplatform)
    alias(libs.plugins.android.library)
}

kotlin {
    // 1. Android Target Configuration
    androidTarget {
        compilerOptions {
            jvmTarget.set(org.jetbrains.kotlin.gradle.dsl.JvmTarget.JVM_17)
        }
    }

    // 2. iOS Targets with Static XCFramework Export
    listOf(
        iosArm64(),
        iosSimulatorArm64()
    ).forEach { iosTarget ->
        iosTarget.binaries.framework {
            baseName = "SharedCore"
            isStatic = true // Static framework avoids dynamic iOS runtime lookup overhead
        }
    }

    // 3. Hierarchical Source Sets
    sourceSets {
        commonMain.dependencies {
            implementation(libs.coroutines.core)
            implementation(libs.ktor.client.core)
        }
        androidMain.dependencies {
            implementation(libs.ktor.client.okhttp)
        }
        iosMain.dependencies {
            implementation(libs.ktor.client.darwin)
        }
    }
}

android {
    namespace = "com.pulsesync.shared"
    compileSdk = 35
    defaultConfig {
        minSdk = 26
    }
}

3. Common Production Pitfalls

Anti-Pattern 1: Putting Platform-Specific Libraries in commonMain
Declaring implementation("io.ktor:ktor-client-okhttp") inside commonMain will break the iOS compilation target immediately. commonMain must only consume multiplatform libraries (libraries that publish metadata artifacts for all declared targets).
Anti-Pattern 2: Dynamic vs. Static iOS Frameworks
Omitting isStatic = true defaults to dynamic frameworks on Apple targets. In modular iOS applications, dynamic frameworks significantly increase cold app startup time (pre-main dylib loading) and can trigger code-signing issues in nested bundles.
