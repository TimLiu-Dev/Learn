The expect/actual Mechanism & Anti-Patterns

Learn the mechanics of expected declarations and why senior engineers favor polymorphism and DI over expect/actual.

1. The Why & Architectural Mental Model

The expect/actual mechanism is Kotlin's language-level feature for declaring a contract in commonMain and fulfilling it in platform source sets (androidMain, iosMain).

However, overusing expect/actual is one of the most common anti-patterns in KMP:

  • It tightly couples common code to compile-time platform branches.
  • It makes unit testing difficult because you cannot easily swap in a mock or fake implementation.
  • Best Practice: Use expect/actual for low-level foundational primitives (e.g. platform dispatchers, UUID generation, timestamps). For business services and hardware APIs, use polymorphic interfaces injected via Dependency Injection.

2. Production Code Examples

Idiomatic expect/actual: Generating UUIDs

commonMain:

package com.pulsesync.core

expect fun generateUuid(): String

androidMain:

package com.pulsesync.core

actual fun generateUuid(): String = java.util.UUID.randomUUID().toString()

iosMain:

package com.pulsesync.core
import platform.Foundation.NSUUID

actual fun generateUuid(): String = NSUUID().UUIDString()

3. Production Pitfalls & Anti-Patterns

Anti-Pattern: Expecting Entire Classes with State
Avoid expect class LocationTracker. Instead, declare interface LocationTracker in commonMain, implement AndroidLocationTracker in androidMain, IosLocationTracker in iosMain, and bind them with Koin or Kotlin-Inject.
