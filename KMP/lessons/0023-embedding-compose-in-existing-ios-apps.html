Embedding Compose Multiplatform into Existing iOS Apps

Export Compose screens as native UIViewController instances via ComposeUIViewController for incremental migration.

1. The Why & Architectural Mental Model

Enterprise mobile teams rarely rewrite an existing iOS app from scratch. Instead, they migrate screen-by-screen. Compose Multiplatform provides ComposeUIViewController to facilitate this:

  • In iosMain, we declare a top-level factory function: fun MainViewController(): UIViewController = ComposeUIViewController { MainApp() }.
  • In Swift/SwiftUI, we wrap this inside a UIViewControllerRepresentable struct.
  • The existing iOS app can present, push, or embed the Compose screen into any native navigation controller or SwiftUI tab view seamlessly.

2. Production Code Examples

1. Kotlin Entry Point in iosMain

package com.pulsesync

import androidx.compose.ui.window.ComposeUIViewController
import platform.UIKit.UIViewController

fun MainViewController(): UIViewController = ComposeUIViewController {
    App() // Root Composable in commonMain
}

2. Embedding in SwiftUI (Xcode)

import SwiftUI
import SharedKit

struct ComposeView: UIViewControllerRepresentable {
    func makeUIViewController(context: Context) -> UIViewController {
        return MainViewControllerKt.MainViewController()
    }
    func updateUIViewController(_ uiViewController: UIViewController, context: Context) {}
}

struct ContentView: View {
    var body: some View {
        ComposeView()
            .ignoresSafeArea() // Allow Compose to manage insets
    }
}

3. Production Pitfalls & Anti-Patterns

Pitfall: SwiftUI Safe Area Double-Padding
If your SwiftUI container applies .padding() or respects safe areas, and your Compose screen *also* applies WindowInsets.safeDrawing, your UI will be double-padded on iOS. Use .ignoresSafeArea() in SwiftUI so Compose has full control over edge-to-edge drawing.
