The Dual-UI Architecture: Shared KMP Logic + Native SwiftUI

Master the enterprise hybrid architecture: sharing 100% of Data, Domain, and ViewModels while building 100% native SwiftUI and Jetpack Compose.

1. The Why & Architectural Mental Model

Many top tech companies (e.g. Netflix, Cash App, Philips, 9GAG) do not share UI code with Compose. Instead, they choose the Dual-UI Architecture:

  • Shared in KMP (commonMain): 100% of Networking (Ktor), Database (Room/SQLDelight), Domain Business Rules, and ViewModels (StateFlow / MVI state machines).
  • Native Frontends:
    • Android: Built with Jetpack Compose.
    • iOS: Built with 100% Native SwiftUI consuming shared Kotlin ViewModels via SKIE.

This gives iOS developers 100% native Apple UX, Cupertino animations, and immediate Day-1 iOS SDK support, while eliminating 70% of business logic duplication.

2. Production Code Examples

1. Shared ViewModel in commonMain

package com.pulsesync.presentation

import kotlinx.coroutines.flow.*

class SharedIncidentViewModel(private val repository: IncidentRepository) {
    val uiState: StateFlow = repository.observeIncidents()
        .map { list -> IncidentListState(incidents = list) }
        .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5000), IncidentListState())
}

2. Pure SwiftUI View Consuming Shared ViewModel via SKIE

import SwiftUI
import SharedKit

struct NativeIncidentListView: View {
    @StateObject var viewModel = ObservableSharedIncidentViewModel()

    var body: some View {
        NavigationStack {
            List(viewModel.uiState.incidents, id: \.id) { incident in
                VStack(alignment: .leading) {
                    Text(incident.title).font(.headline)
                    Text("Severity: \(incident.severity)").font(.subheadline).foregroundStyle(.secondary)
                }
            }
            .navigationTitle("Incidents")
        }
    }
}

3. Production Pitfalls & Anti-Patterns

Pitfall: Re-implementing Business Validation in SwiftUI
In the Dual-UI pattern, the SwiftUI layer must be a passive rendering shell. Never write business calculations or validation logic in Swift. All validation, state transformations, and caching must remain inside the shared Kotlin ViewModel.
