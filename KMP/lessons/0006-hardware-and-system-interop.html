Hardware & Native System Interop: Secure Key Storage

Bridge secure hardware enclaves using Android Keystore and Apple Keychain through clean dependency-injected interfaces.

1. The Why & Architectural Mental Model

Production mobile applications must securely persist sensitive session tokens (OAuth refresh tokens, encryption keys, biometrics). Storing these in plaintext preferences or databases is a major security vulnerability.

Both mobile platforms provide hardware-backed security enclaves:

  • Android: EncryptedSharedPreferences backed by the Android Keystore hardware-backed master key.
  • iOS: The Apple Keychain service (SecItemAdd, SecItemCopyMatching) backed by the Secure Enclave processor.

In KMP, we model this with a pure Kotlin interface SecureStorage in commonMain, implemented independently in androidMain and iosMain.

2. Production Code Examples

1. Common Interface in commonMain

package com.pulsesync.security

interface SecureStorage {
    suspend fun saveToken(key: String, token: String)
    suspend fun getToken(key: String): String?
    suspend fun clearToken(key: String)
}

3. Production Pitfalls & Anti-Patterns

Pitfall: Main-Thread Keychain / Keystore I/O
Accessing Apple Keychain or Android EncryptedSharedPreferences performs disk I/O and cryptographic hardware operations. Always dispatch secure storage operations onto background dispatchers (Dispatchers.Default or Dispatchers.IO) to avoid UI frame drops.
