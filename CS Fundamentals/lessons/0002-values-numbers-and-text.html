Part 1

How to start from a blank file

~15 min

Coding without AI mostly means not freezing in front of an empty editor. The fix is a routine that turns "write a program" into small steps you already know how to do. Use the same four steps for every exercise in this course:

StepWhat you doWhy
1 · ExamplesWrite 2–4 concrete inputs with the outputs you expect, including at least one edge case: zero, empty, negative, or huge.You can't code what you can't do by hand. These examples become your tests.
2 · PlanWrite the steps in plain words, as comments, before any code.It separates what to do from how to say it in Kotlin or Java.
3 · CodeTurn one comment into code at a time, and run after each small step.A small step that fails is easy to find.
4 · CheckRun all your examples, and especially the edge case. Read any error from the top."It compiled" is not the same as "it works".

Default to val, and switch to var only when the value really has to change. Fewer moving parts means fewer bugs. Note that Java's var means "infer the type", not "variable". A Java var can still be reassigned, so its closest Kotlin equivalent is var too, and final var is Java's val (dev.java: Using var).

val means the variable can't be pointed at something else. It doesn't freeze the object it points to. L5 covers that distinction properly.

Primitives and boxes

Java has two kinds of value. Primitives (int, double, …) are raw values: fast, never null, and not objects. Wrapper classes (Integer, Double, …) are objects that each hold one primitive. Collections can only hold objects, so you write List<Integer> and Java autoboxes each int into an Integer for you. A wrapper can be null, and unboxing a null crashes:

Java compiles happily, then crashes at runtime:

7
Exception in thread "main" java.lang.NullPointerException: Cannot invoke "java.lang.Integer.intValue()" because "<local3>" is null
	at Boxing.main(Boxing.java:12)

Kotlin won't even compile it:

Boxing.kt:7:16: error: initializer type mismatch: expected 'Int', actual 'Int?'.
    val n: Int = maybe            // refused at COMPILE time
What Kotlin does for you. There's only one Int, and the compiler decides how to store it. In the docs' words: "on the JVM, non-nullable numeric values are usually stored using primitive types… However, when you use generic types or nullable numeric types like Int?, the value is boxed" (Kotlin docs: Numbers). You get primitive speed where possible, and the compiler stops you from unboxing a null. L3 covers nullable types like Int? in depth.

The <local3> placeholder appears because java File.java compiles without debug info. Compiled with javac -g, the message names the variable (JEP 358).

Converting between types

2000000000 2000000001 705032704 3

Notice 705032704: five billion doesn't fit in 32 bits, so the conversion keeps only the low 32 bits, without any error. 3.99 becomes 3, which is truncated, not rounded. Here's what each compiler says when you skip the explicit step:

Widen.kt:3:20: error: initializer type mismatch: expected 'Long', actual 'Int'.
    val wide: Long = small
Widen.kt:4:19: error: initializer type mismatch: expected 'Double', actual 'Int'.
    val d: Double = 1
Narrow.java:4: error: incompatible types: possible lossy conversion from long to int
        int small = big;
What Kotlin makes explicit that Java doesn't. This one goes the other way round. Java silently widens int to long and int to double. Kotlin refuses all implicit conversions, so you write .toLong() or .toDouble() (Kotlin docs: "Kotlin does not support implicit conversion"). Mixed arithmetic such as Int + Long is still allowed in both languages, and the result is the wider type.

Check

Kotlin: val wide: Long = small, where small is an Int. What happens?

Kotlin has no implicit numeric conversions. A Long can certainly hold any Int value, but you have to ask for the conversion.

Java: System.out.println(010); prints…

A leading zero makes it an octal literal: 1×8 + 0 = 8. Kotlin doesn't support octal literals at all.

Why can't Java write List<int>?

Type parameters must be reference (object) types, so you use the wrapper Integer and let autoboxing convert. L13 explains why generics work this way.

Kotlin's val is closest to which Java declaration?

Both prevent reassignment. Java's var only infers the type and can still be reassigned.

Part 3

How numbers really work

~25 min

Binary, bit by bit

Memory stores everything as bits, 0s and 1s. A binary number works like decimal, but each place is worth twice the one to its right: 1011 is 8 + 0 + 2 + 1 = 11. With 8 bits you can make 2⁸ = 256 patterns.

To represent negative numbers, the JVM uses two's complement: the leftmost bit is worth a negative amount, −128 in an 8-bit byte. The JVM's integer types are all "signed two's-complement integers" (JLS §4.2), so the same idea applies to Kotlin's Int.

Try it: click the bits. Then press signed max followed by +1, and watch what happens.

Going from 127 to −128 isn't a bug in the widget. It's what hardware addition does: 0111_1111 + 1 = 1000_0000, and that pattern means −128. An Int is the same with 32 bits, so Int.MAX_VALUE + 1 wraps round to Int.MIN_VALUE. The JLS says plainly that "the integer operators do not indicate overflow or underflow in any way" (JLS §4.2.2).

That also explains Part 1's bug. The range is lopsided: −2,147,483,648 to +2,147,483,647. There's no +2147483648 Int, so abs(Int.MIN_VALUE) has nowhere to go and comes back negative.

Floating point: why 0.1 + 0.2 ≠ 0.3

A Double stores a number as a binary fraction. Just as 1/3 can't be written exactly in decimal (0.333…), 1/10 can't be written exactly in binary. So 0.1 is stored as the nearest representable value, and those tiny errors add up (The Floating-Point Guide). Two practical rules follow:

  • Never compare doubles with ==. Check whether they're close: abs(a - b) < 1e-9.
  • Never store money in a Double. Use whole cents in a Long, or BigDecimal, and build a BigDecimal from a String. The JDK docs warn that new BigDecimal(0.1) is "actually equal to 0.1000000000000000055511151231257827021181583404541015625" (BigDecimal docs).

Part 4

Text: strings, Unicode and regex

~25 min

Strings are immutable

Once a String exists, its contents never change. Methods like uppercase() or replace() return a new string (Kotlin docs: Strings; Java's String docs say "Strings are constant"). This is why name.uppercase() on its own line does nothing useful. You have to keep the result.

Characters and Unicode

Unicode gives every character in every writing system a number, called a code point. On the JVM, a String is stored as UTF-16: most characters take one 16-bit Char, but characters beyond the first 65,536, such as most emoji, take two, called a surrogate pair. So length counts 16-bit units, not "characters" (String docs: "the number of Unicode code units"). For the background, read Joel Spolsky's classic "The Absolute Minimum Every Software Developer Must Know About Unicode".

Four things to notice in that output:

  • 'a' + 1: Kotlin gives the next Char, b. Java promotes char to int and gives 98. In Kotlin a Char isn't a number, so you ask for its code explicitly with .code (Kotlin docs: Characters).
  • Emoji length: one emoji has length 2 in both languages, because it's two UTF-16 units but one code point.
  • substring(1, 4): the start index is included and the end index is excluded. That rule shows up all over both languages.
  • String equality: Java's == on objects asks "is this the same object?", so two equal texts built separately give false. In Java, always compare strings with .equals(). Kotlin's == calls equals for you. L5 explains the full story, including Kotlin's ===.
What Kotlin does for you. String templates ("$name", "${expr}") replace Java's chains of +. Kotlin's raw strings ("""…""") with trimIndent() predate Java's text blocks, which arrived in JDK 15 (JEP 378). Both strip the indentation. Kotlin's == compares contents, so the Java == trap doesn't exist (Kotlin docs: Strings).

Check

Java: "hi" == new StringBuilder("h").append("i").toString()

Two different objects with the same text. In Java, == compares references, so it's false. Use .equals().

What do Kotlin and Java print for 'a' + 1?

Kotlin defines Char + Int → Char. Java promotes the char to an int before adding.

What's the length of a string holding one 😀 emoji?

😀 lies outside the 16-bit range, so UTF-16 stores it as a surrogate pair: two code units, one code point.

Which substrings does \d+ find in "a1b22"?

+ grabs as many digits in a row as it can, so 22 is a single match.

Wrap-up

Exit quiz, recall card, sources

~5 min

You need to store 3 billion as a whole number. Which type?

An Int tops out at about 2.1 billion. A Double would hold it, but it's the wrong tool for exact whole numbers.

Why is it """\d+""" in Kotlin but "\\d+" in Java?

It's the same regex engine. The only difference is how the string literal treats backslashes.

Your build fails with "initializer type mismatch". What's your first move?

Error messages start with File.kt:line:column. Go there first. L3 practises reading errors properly.
