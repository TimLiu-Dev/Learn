Design Patterns

A pattern is a named, reusable answer to a design problem that keeps coming back. The names matter as much as the code: "put a caching decorator in front of the catalog" is a whole design in one sentence. This lesson covers seven classic patterns, each built in Java the Gang of Four way and then in idiomatic Kotlin, where several of them shrink to one line or vanish.

Part 1

Strategy and Observer

~25 min

The 1994 book Design Patterns: Elements of Reusable Object-Oriented Software by Gamma, Helm, Johnson and Vlissides (the "Gang of Four", GoF) catalogued 23 patterns, written for C++ and Smalltalk. Refactoring.Guru's pattern catalogue is a free, well-illustrated companion. Two years later, Peter Norvig's talk Design Patterns in Dynamic Languages pointed out that "16 of 23 patterns are either invisible or simpler" in languages with features like first-class functions. Strategy and Observer were both on his list. Kotlin has first-class functions, so watch for patterns shrinking.

Every pattern below follows the same steps: the problem, the Java (GoF) version, the Kotlin version, real output, when not to use it, and where it already appears in code you use. The diagram shows the shape of each pattern in both languages:

Strategy: interchangeable algorithms

The problem. The library charges late fees, and the rule changes: a flat fee, a per-day fee, a per-day fee with a cap, "students pay nothing". If the rule lives in an if/when inside Library, every new rule means editing Library (L38's open-closed principle). Strategy pulls each rule out behind one interface, so Library knows when to charge and the strategy knows how much (Refactoring.Guru: Strategy).

flat: 1500 cents
per-day: 1225 cents
capped: 825 cents
students free: 1075 cents
most late first: [Ulysses, Emma, Dune]

Both print exactly this. The Java version is the textbook shape: an interface and one class per algorithm. Look at the fourth policy, though: since Java 8 a lambda can implement LateFeePolicy, because it's a functional interface with one abstract method (L14). Kotlin goes all the way: the "interface" is the function type (Loan) -> Int, and perDay(25) and capped(…) are functions that return strategies. CappedFee wraps another policy, which is already a hint of Decorator in Part 3.

If you want a named type in Kotlin, for clearer error messages or Java callers, declare a fun interface LateFeePolicy { fun feeCents(loan: Loan): Int } and you can still pass lambdas to it (Kotlin docs: Functional (SAM) interfaces).

In the wild. You've used a strategy since L14: Comparator. sort is the context, and the comparator decides the order.

When not to use it. When there's one algorithm and no sign of a second. An interface plus a single implementation is ceremony with no payoff, and you can extract a strategy later, when the second rule actually arrives.

Observer: tell everyone who cares

The problem. When a book is lent, the screen at the desk should update, an audit log should record it, and next month maybe a mobile notification goes out. The LoanDesk shouldn't know about any of them. Observer lets interested objects subscribe, and the subject notifies every subscriber without knowing what they are (Refactoring.Guru: Observer).

screen: Dune lent
screen: Dune returned
listeners while screen open: 2
listeners after close: 1
audit: [lent:Dune, returned:Dune, lent:Emma]
fee 0 -> 250
fee 250 -> 250
screen: Dune lent
screen: Dune returned
listeners while screen open: 2
listeners after close: 1
audit: [lent:Dune, returned:Dune, lent:Emma]
fee 0 -> 250

Three details carry over from earlier lessons:

  1. The leak. A listener the subject still holds can never be garbage-collected. That was L24's listener leak. So subscribe returns an AutoCloseable, and the screen subscribes inside try-with-resources / use (L10). After the block, the screen is gone and Emma only reaches the audit.
  2. Changing the list mid-notification. A listener might unsubscribe while publish is looping. CopyOnWriteArrayList iterates over a snapshot, so that's safe (L27).
  3. The last line differs. The JDK's ready-made single-property observer, PropertyChangeSupport, follows its documented rule: "No event is fired if old and new values are equal and non-null." Kotlin's Delegates.observable (L15) calls its callback after every assignment, so it printed 250 -> 250. Same pattern, different contract: read the docs of the observer you use.

The modern Kotlin observer: SharedFlow. In L29 you met flows. A SharedFlow is "a hot Flow that shares emitted values among all its collectors in a broadcast fashion, so that all collectors get all emitted values" (API docs). It is the listener list, written and tested for you. A StateFlow adds "and here is the current value".

screen: Dune lent
audit:  lent:Dune
screen: Emma lent
audit:  lent:Emma
screen: Dune returned
audit:  returned:Dune
on loan now: 1
subscribers while open: 2
subscribers after cancel: 0

Subscribing is collecting, and unsubscribing is cancelling the collecting coroutine. Structured concurrency (L29) means a cancelled scope cleans up its subscribers, so the L24 leak is much harder to write. Java has no coroutines. Its closest standard type is java.util.concurrent.Flow with SubmissionPublisher, which you saw in L29.

Bridge. On Android, LiveData "is an observable data holder class" that's also lifecycle-aware, and modern Android UI state is usually a StateFlow. Spring has application events with listener beans. Both are this pattern, packaged.

When not to use it. Observer hides control flow. "Who runs when a book is lent?" has no answer you can find by reading lend(), and a chain of events triggering events is hard to debug. If there's exactly one interested party, just call it.

What Kotlin does for you.
  • Function types like (Loan) -> Int replace one-method strategy interfaces. Java needs the interface declared first, even when every implementation is a lambda.
  • Strategy factories like perDay(25) are one-line functions returning lambdas. In Java, each needs a class with a constructor and a field.
  • Delegates.observable gives a single observable property in one line.
  • SharedFlow/StateFlow replace the hand-written listener list. Cancelling a coroutine unsubscribes.
  • use { } works on any AutoCloseable, so subscription handles are tidy in both languages.

Check

In Fees, what does the capped(perDay(25), 600) policy total for the three loans (3, 6 and 40 days late)?

75 + 150 + min(1000, 600) = 825. The cap applies per loan, because capped wraps the per-loan policy.

How many classes did Fees.kt declare to implement its four late-fee policies?

None. The policies are values of the function type (Loan) -> Int. That's Norvig's "first-class functions" point in practice.

Kotlin: feeCents uses Delegates.observable, and you assign 250 twice in a row. How many callback lines print?

observable runs its callback after every assignment. Java's PropertyChangeSupport skips equal values, so it printed only one line.

Why does subscribe return an AutoCloseable instead of nothing?

A subscriber the subject still references can't be garbage-collected (L24). Handing back the "off switch" makes unsubscribing easy, and works with use / try-with-resources.

When is the Strategy pattern overkill?

One algorithm and no second one in sight: an interface with a single implementation adds indirection for nothing. Extract the strategy when the second rule appears.

Part 2

Factory and Builder

~25 min

Factory: creating objects without naming their class

The problem. Constructors have three limits. They must be called by their class's name, they always create a new object, and they can only return that exact class. Effective Java Item 1, "Consider static factory methods instead of constructors", lists what a static factory method gains: a descriptive name, the freedom to reuse instances, and the freedom to return any subtype.

$12.50 $0.99 $5.00
zero reused: true
email desk@library.test -> ada: Dune is due
sms -> ada: Dune is due
unknown notifier: pigeon
Ok(isbn=9780441172719)
Bad(reason=need 13 digits, got 3)
$12.50 $0.99
zero reused: true
email desk@library.test -> ada: Dune is due
sms -> ada: Dune is due
unknown notifier: pigeon
valueOf(127) == valueOf(127): true
valueOf(128) == valueOf(128): false
List.of(...).add -> UnsupportedOperationException

All three advantages are visible:

  • Names. Money.parse("12.50") says what it does. A second constructor taking a String wouldn't.
  • Reuse. ofCents(0) hands back the same cached ZERO every time. You met this in L5: Integer.valueOf "will always cache values in the range -128 to 127, inclusive" (API docs), which is why 127 compared equal with == and 128 didn't.
  • Subtypes. notifierFrom("sms") returns a Notifier. The caller never names SmsNotifier, so you can add PushNotifier later without touching any caller. List.of does the same: it returns some unmodifiable implementation you never name, so add throws.

That last one is the GoF Factory Method idea in its everyday form: creation goes through a method, so the concrete class can vary (Refactoring.Guru: Factory Method). The full GoF version puts that method in a superclass and lets subclasses override it. Abstract Factory goes one step further: a factory object that creates a whole family of related products, like "all the Material widgets" vs "all the Cupertino widgets" (Refactoring.Guru: Abstract Factory). You'll meet it in UI toolkits; you rarely write it.

Kotlin's versions. Kotlin has no static, so factories live in a companion object (L6), or as top-level functions like listOf. Two more Kotlin options are shown above:

  • operator fun invoke on the companion makes Money(5) call a factory while looking like a constructor call (Kotlin docs: invoke operator). It's a debated idiom: neat, but readers may think they're calling a constructor and be surprised by caching or validation. Prefer a named factory unless the type really feels like a value.
  • A factory that returns a sealed result (L7, L10): isbnOf returns Ok or Bad instead of throwing, and the caller's when must handle both.

Bridge. In Spring, a method annotated with @Bean is a factory method: "@Bean is a method-level annotation" whose return value the container manages (Spring docs). The container calls your factory so callers never call new.

When not to use it. A plain data holder with one obvious constructor doesn't need a factory. Don't hide Point(x, y) behind Point.of(x, y) just because the pattern exists.

Builder: many parameters, most optional

The problem. A book search has seven settings: title, author, year range, sort, page size, offset. Most have sensible defaults. In Java, the options are a "telescoping" set of constructors, one per combination, where new BookSearch("dune", null, 1960, 1970, "year", 20, 0) gives no hint which int is which. Or you make the object mutable with setters. Effective Java Item 2, "Consider a builder when faced with many constructor parameters", recommends a third way: a mutable builder object that collects settings, then a build() that validates and creates an immutable result (Refactoring.Guru: Builder).

BookSearch(title=dune, author=null, yearFrom=1960, yearTo=1970, sort=year, limit=20, offset=0)
BookSearch(title=dune, author=null, yearFrom=1960, yearTo=1970, sort=year, limit=20, offset=20)
rejected: yearFrom 2000 > yearTo 1990
copy rejected: limit must be 1..100, was 500
due: Dune (3 days)
[Dune, Emma, Ulysses]
apply configures in place
BookSearch(title=dune, author=null, yearFrom=1960, yearTo=1970, sort=year, limit=20, offset=0)
rejected: yearFrom 2000 > yearTo 1990
GET http://127.0.0.1:8080/books?q=dune {Accept=[application/json]}
due: Dune (3 days)

Count the Java: every field appears in the class, again in the builder, again in a setter method, and once more in the private constructor that copies it across. The Kotlin data class does the same job in its constructor:

  • Named arguments make BookSearch(title = "dune", yearFrom = 1960, …) as readable as a builder chain.
  • Default values make every field optional. The Kotlin coding conventions say it directly: "Prefer declaring functions with default parameter values to declaring overloaded functions" (Kotlin coding conventions).
  • init { check(…) } is the build() validation. Note the fourth output line: copy calls the constructor, so q.copy(limit = 500) is validated too (L7). An invalid BookSearch can't exist.

Where Kotlin still uses builders. Building something step by step, with loops and conditions, still suits a builder. Kotlin's version is a function taking a lambda with a receiver (L15): buildString, buildList, or apply on a mutable object. And if Java code must call your Kotlin constructor, Java can't use named or default arguments: add @JvmOverloads (L9), or give Java callers a real builder.

In the wild. HttpRequest.newBuilder(…)…build() from L31 and StringBuilder. The JDK uses builders where Java has no named arguments.

When not to use it. Two or three required parameters: a constructor is clearer. In Kotlin, almost never write a Builder class for your own types. Named and default arguments already do it.

What Kotlin does for you.
  • Named arguments and defaults replace the whole Builder class, and telescoping constructors.
  • copy(field = …) gives "a modified copy" with validation still enforced by init.
  • Top-level functions and companion objects give factories a home without a utility class.
  • buildString/buildList/apply cover step-by-step building, where Java needs a builder object.
  • Sealed results let a factory report failure in the type system, where Java usually throws.

Check

Money has a private constructor and a companion operator fun invoke(dollars: Int). What does println(Money(5)) do?

Money(5) resolves to Money.Companion.invoke(5), not the private constructor. It looks like a constructor call, which is exactly why the idiom is debated.

Which advantage does a static factory method have that a constructor never can?

A constructor always has the class's name. Money.parse and Money.ofCents say what they do (Effective Java Item 1). Factories can also cache, and return subtypes.

BookSearch's init checks limit in 1..100. What does q.copy(limit = 500) do?

copy calls the primary constructor, so init runs and check throws IllegalStateException: "copy rejected: limit must be 1..100, was 500".

Which of these is a builder-style API in the Kotlin standard library?

buildString hands you a StringBuilder as the lambda's receiver and returns the result: step-by-step building, the part of Builder Kotlin keeps.

Why does the Java builder validate in build() rather than in each setter?

yearFrom <= yearTo involves two fields, and they can be set in either order. Only build() sees the complete object.

Part 3

Adapter, Decorator, Singleton

~30 min

Adapter: make a foreign API fit your interface

The problem. The rest of your app depends on a BookCatalog interface (L38: depend on abstractions). Then the library buys a legacy system that only offers XmlBookFeed.fetchXml(). You can't change that class, and you don't want XML parsing spread through your code. An Adapter implements your interface and translates each call into the foreign API (Refactoring.Guru: Adapter).

[Book(isbn=9780441172719, title=Dune), Book(isbn=9780141439587, title=Emma)]
Emma
view after shelf[0] = ...: [Ulysses, Emma]
[Book[isbn=9780441172719, title=Dune], Book[isbn=9780141439587, title=Emma]]
Emma
array after view.set: [Ulysses, Emma]
view.add -> UnsupportedOperationException
5 bytes in, 4 chars out

The adapter is also the one place that knows the legacy API's quirks. Notice that the XML parser's checked exceptions stop inside it (L10), and the rest of the app never sees them. It parses with the JDK's real XML parser, never with string tricks.

In the wild. Two JDK adapters you've used:

  • Arrays.asList "Returns a fixed-size list backed by the specified array". The array is adapted to the List interface, so a write through the list changes the array, and add throws. Kotlin's shelf.asList() is a read-only view of the array.
  • InputStreamReader "is a bridge from byte streams to character streams" (L22). It adapts the InputStream interface to the Reader interface: 5 UTF-8 bytes in, 4 characters out.

Kotlin's extra. The adapter class is the same in both languages. An extension function, fun XmlBookFeed.asCatalog(), just makes the conversion read naturally at the call site (L9).

When not to use it. When you control both sides, change one of them so the interfaces match, instead of adding a translation layer.

Decorator: add behaviour by wrapping

The problem. Catalog lookups are slow, so you want caching. You also want logging, sometimes. Subclassing gives you CachingSlowCatalog, LoggingCachingSlowCatalog and so on: one class per combination (L8's argument for composition). A Decorator implements the same interface as the object it wraps, adds one behaviour, and passes the rest through. Decorators stack in any combination at runtime (Refactoring.Guru: Decorator). L8's UrgentNotifier(LoggingNotifier(email)) was exactly this.

plain:  273 ms
  find(9780441172719)
  find(9780141439587)
  find(9780441172719)
  find(9780441172719)
  find(9780000000000)
cached: 157 ms, misses=3
size still forwards: 2
plain:  271 ms
  find(9780441172719)
  find(9780141439587)
  find(9780441172719)
  find(9780441172719)
  find(9780000000000)
cached: 158 ms, misses=3
size still forwards: 2

Times are from my machine; yours will differ. Five lookups at 50 ms each take about 270 ms. With the cache, only the three distinct ISBNs (including the one that doesn't exist) reach the slow catalog, so about 157 ms. The logging decorator sits outside the cache, so it logs all five calls. Put it inside, and it would log only the three misses. Exercise 3 makes you predict that.

The difference between the languages is inside the decorator classes. Java's CachingCatalog must forward all() and size() by hand, even though it changes nothing about them. A real interface might have twenty methods. Kotlin's : BookCatalog by inner generates every forwarding method (L15), so each decorator contains only the one method it changes. The Kotlin docs call delegation "a good alternative to implementation inheritance", supported "natively requiring zero boilerplate code" (Kotlin docs: Delegation).

A real trap in the Kotlin cache. The obvious one-liner is cache.getOrPut(isbn) { inner.find(isbn) }. But getOrPut "returns the value for the given key if the value is present and not null" (API docs). A cached null, meaning "no such book", counts as missing, so every lookup of a missing ISBN hits the slow catalog again:

getOrPut: 3 calls, 3 slow lookups

That's why CachingCatalog checks isbn in cache first. Java's computeIfAbsent with Optional values avoids the problem, because Optional.empty() isn't null.

In the wild. Java I/O is built from decorators. In new BufferedReader(new InputStreamReader(new FileInputStream(f))), each layer wraps the one inside it. A BufferedInputStream "adds functionality to another input stream-namely, the ability to buffer the input". In L22, that one wrapper took a read from 2.6 s down to 41 ms.

Bridge. Spring wraps your beans in proxies to add transactions, security or caching around your methods: "Spring AOP uses either JDK dynamic proxies or CGLIB to create the proxy for a given target object" (Spring docs). Those proxies are decorators the framework writes for you.

When not to use it. Deep stacks of decorators are hard to debug, because a stack trace shows six layers of forwarding. And order matters, as you just saw. If a behaviour always applies, put it in the class itself.

Singleton: exactly one instance

The problem. Some things really should exist once per process: an ID generator, the application's configuration. GoF Singleton guarantees one instance and gives global access to it (Refactoring.Guru: Singleton).

1 2
before first use
  (Config loading...)
loan days: 21
same instance: true
loaned Oct 1, overdue on Nov 1? true
loaned Oct 20, overdue on Nov 1? false

Both print exactly this. Java has two good ways to write a singleton:

  • An enum with one constant. Effective Java Item 3, "Enforce the singleton property with a private constructor or an enum type", says a single-element enum is often the best way, because the JVM guarantees exactly one instance, even through serialization or reflection tricks.
  • The lazy holder. From L27: the nested Holder class is initialised on first use, and class initialisation is thread-safe. (Config loading...) appears only after "before first use".

Kotlin needs one keyword. "The initialization of an object declaration is thread-safe and done on first access" (Kotlin docs: Object declarations).

Why it's dangerous anyway. Look at isOverdueHidden. Its signature promises "give me a date, I'll tell you if it's overdue", but it secretly reads global config and the real clock. A test can't control either, so its answer changes from day to day. That's the testability problem from L38: singletons are hidden dependencies. isOverdue takes the loan period and a Clock as parameters, so the output above is the same today and next year. Spring makes the same choice: its beans are singletons by default, "a single object instance for each Spring IoC container" (Spring docs: Bean scopes), but they're injected, not fetched from a global.

When it's acceptable. Stateless things like an object holding pure functions or constants, and genuinely process-wide resources, as long as you inject them where they're used. Never use a singleton just to avoid passing a parameter.

Pattern-itis. Patterns are tools, not goals. The famous warning sign is a real Spring class, AbstractSingletonProxyFactoryBean, described as a "Convenient superclass for FactoryBean types that produce singleton-scoped proxy objects". Four pattern words in one name. It makes sense inside a framework. In your app, if a class name reads like a pattern catalogue, ask whether a function would do.

What Kotlin does for you.
  • by inner writes every forwarding method of a decorator. Java forwards each method by hand.
  • object is a complete, lazy, thread-safe singleton. Java needs an enum or a holder class.
  • Extension functions like feed.asCatalog() make adapters pleasant to call.
  • Nullable types make "no such book" a Book? instead of an Optional. That's the source of the getOrPut trap.

Why use decorators instead of subclasses like LoggingCachingSlowCatalog?

With subclasses you need one class per combination. Decorators are wrapped in any order and combination when the objects are built.

CountingCatalog(CachingCatalog(fake)), then find for a, b, a, a, b. What is the count?

The counter is outside the cache, so it sees every call, hits included. Swap the order and it counts only the 2 misses.

Kotlin: cache.getOrPut(k) { slowFind(k) } runs 3 times, and slowFind returns null. How many slow lookups?

getOrPut treats a stored null as absent, so it calls the lambda every time. Check k in cache first when null is a real answer.

Why do singletons make code hard to test?

Code that reaches for a global gets the real thing every time: real config, real clock. Inject the dependency instead (L38) and a test passes a fake or a fixed clock.

Final exercise

An order system with five patterns

~20 min

From a blank Gradle project in each language (gradle init as in L11), build a small order system. Use each pattern deliberately, and write a one-line comment explaining why it's there. Test-first where it makes sense (L11).

  1. Builder / named arguments. An Order with an id, a customer, one or more lines (sku, quantity, unit price in cents), and optional member, coupon and notifyBy (default "email:orders@shop.test"). Java: a Builder whose required fields go to builder(id, customer). Kotlin: a data class. Reject an order with no lines.
  2. Strategy. Pricing rules, each a function from (order, running total) to a new total: members get 10% off; 10 or more items take $5 off; coupon SAVE5 takes $5 off but never below zero. price(order, rules) applies them in order.
  3. Factory. notifierFrom("email:…") / notifierFrom("sms:2") returns a Notifier. sms:N creates a simulated SMS gateway that times out on its first N calls.
  4. Decorator. RetryingNotifier(inner, attempts) retries on IllegalStateException and rethrows after the last attempt. LoggingNotifier(inner, log) records each send.
  5. Observer. Order events (Placed, Notified). Kotlin: a SharedFlow. Java: a listener list whose subscribe returns an AutoCloseable.
  6. A Shop that gets the rules, the events and a notifier factory injected (L38), and a main composition root that places the two orders below.

Reflect: which patterns did Kotlin make disappear?

PatternJavaKotlinVerdict
Strategyan interface + lambdas or classesa function type (typealias)shrinks to values
Buildera nested Builder class, every field 3 more timesnamed arguments + defaults + copydisappears
Singletonan enum or a holder classobjectone keyword (still use sparingly)
Decoratorforward every method by handby innersame shape, no boilerplate
Observera listener list + subscribe/unsubscribeSharedFlow / StateFlowmoves into a library
Factorya static methoda top-level or companion functionbarely changes
Adapteran adapter classthe same class (+ an extension)unchanged

The patterns that survive unchanged are about structure: which object talks to which. The ones that disappear were working around missing language features: functions as values, named arguments, delegation. That's Norvig's 1996 point, restated for Kotlin.

Wrap-up

Exit quiz, recall card, sources

~5 min

Java: Integer.valueOf(128) == Integer.valueOf(128) (L5)

valueOf is a caching static factory, but the cache covers only -128 to 127. Two separate Integer objects compared with == are different references. Use equals.

Why is the lazy holder idiom thread-safe without any synchronized? (L27)

The JVM runs a class's static initialiser exactly once, with its own locking, the first time the class is used. The holder class exploits that rule.

In new BufferedReader(new InputStreamReader(in, UTF_8)), which class is the adapter (bytes to chars)? (L22)

InputStreamReader converts one interface (InputStream) into another (Reader): an adapter. BufferedReader keeps the Reader interface and adds buffering: a decorator.

Which Kotlin type is a pricing rule that takes an order and a running total and returns a new total? (L14)

Two parameters, one result. With that function type, Strategy needs no interface at all, and fold applies a list of rules in order.
