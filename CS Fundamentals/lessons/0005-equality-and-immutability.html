Recall from L4

From memory: no peeking

After val b = a, where a holds an object, how many objects are there?

Assignment copies the arrow.

  1. Assignment never creates an object. Only a constructor call, like Counter(1), does.
  2. b = a copies the reference, so both variables point at the single object.
  3. a already holds an object, and copying its arrow doesn't destroy it.
  4. Nothing here builds two more objects. Only a constructor call creates one.

A Java method assigns a brand-new object to its parameter. Afterwards, the caller's variable…

Pass-by-value: the method only re-pointed its own copy of the reference.

  1. Only the method's own copy of the reference was re-pointed. The caller's variable never left the caller.
  2. Nothing assigns null to the caller's variable. Parameter assignment can't touch it at all.
  3. Java passes the reference by value, so re-pointing the parameter can't reach the caller's variable.
  4. Assigning to a parameter is ordinary, legal code. Returning from the method throws nothing.
Part 1

Identity vs equality

~28 min

Given two references, you can ask two different questions:

QuestionNameKotlinJava
Do both arrows point at the same object?identity (referential equality)a === ba == b
Do the objects have the same contents?equality (structural equality)a == ba.equals(b)

Look at the operators. The same symbol, ==, asks different questions in the two languages. Kotlin's == is translated to a?.equals(b) ?: (b === null), so it calls equals and is null-safe. Its === is true "if and only if a and b point to the same object" (Kotlin docs: Equality). On objects, Java's == compares references. For primitives like int, both languages simply compare the values.

Who decides what "same contents" means?

The class does, by overriding equals. If it doesn't, it inherits Object.equals, which returns true "if and only if x and y refer to the same object" (Object.equals docs). In other words, the default equality is identity. String, List, Set, Map and the number wrappers all override equals. Your own classes don't, until L7 shows you how, or until you use a Kotlin data class or a Java record.

Three things stand out:

  • Arrays don't override equals, in either language. Two arrays with equal contents are never == (Kotlin) or .equals() (Java). Use contentEquals / Arrays.equals (Kotlin docs). Kotlin warns you at compile time: 
    Equality.kt:19:19: warning: '==' on arrays compares only references. Replace '==' with 'contentEquals' to compare the arrays' contents or use '===' to remove the warning.
  • Why Java's == on strings seems to work. The last Java line prints true: identical string literals are "interned" so they share one object (JLS §3.10.5). Strings built at runtime aren't. So == passes your quick test with literals and then fails on real input. That's why the bug is so sneaky.
  • Equality needs a matching hashCode. If you override equals, you must also override hashCode, because "equal objects must have equal hash codes" (Object docs). L7 shows how, and L19 shows what breaks if you don't.
What Kotlin does for you. Kotlin's == means what you almost always want, content equality, and it's null-safe: a == b with a null a doesn't throw. Identity is the rarer question, so it gets the rarer operator, ===. Java makes you remember .equals() every time, and guard against null on the left (Objects.equals(a, b) does that for you).

Check

Kotlin: Box(1) == Box(1), where Box doesn't override equals.

== calls equals, and the inherited equals is identity. Two separate objects aren't identical.

  1. Equal contents don't matter here: Box inherits equals from Any, which only checks identity.
  2. == calls the inherited equals, and two separate objects are never identical.
  3. == works on any two objects, because every class inherits an equals to call.
  4. == always gives a Boolean, never null, even when one side is null.

Kotlin's === asks…

Referential equality: are both arrows pointing at one object?

  1. That's structural equality, which == asks by calling equals.
  2. Hash codes aren't compared. Two distinct objects can even share a hash code.
  3. Two objects of the same class are still two objects, so === is false for them.
  4. === is true only when both references point at the one object.

Kotlin: arrayOf(1, 2) == arrayOf(1, 2)

It's false, with a compiler warning. Arrays use identity for equals. Use contentEquals.

  1. Arrays don't override equals, so equal contents don't count. contentEquals would say true.
  2. It compiles. Kotlin only warns that == on arrays compares references.
  3. == calls the array's inherited identity equals, and these are two arrays.
  4. Comparing two non-null arrays can't throw. It just returns a Boolean.

Java: after String a = "hi", b = "hi";, why is a == b true?

String literals are interned (JLS §3.10.5). Runtime-built strings aren't, so never rely on it.

  1. String literals are interned, so both "hi" literals refer to one String object.
  2. Java's == on objects compares references. A "hi" built at runtime would give false.
  3. Java doesn't cache strings by length. Literals of any length are interned, and runtime-built strings aren't.
  4. The comparison really runs. It's true because both variables hold the same interned object.

Kotlin: a list of lists, and a list of arrays. What does this print?

fun main() {

A list's equals compares its elements using their equals. The inner lists are equal by contents, so the first comparison is true. Arrays don't override equals, so the two IntArrays are unequal, and that makes the outer lists unequal too. Kotlin can't warn you here, because the arrays are hidden inside lists.

  1. List equality isn't a deep content check. It calls each element's equals, and an array's equals is identity.
  2. The inner lists are equal by contents, but the two IntArrays are separate objects.
  3. That's a Java habit. Kotlin's == calls List.equals, which compares the elements.
  4. Backwards: lists compare by contents, and arrays are the ones that fall back to identity.

Stretch, Java: Point overrides equals but not hashCode. What does this print?

import java.util.HashSet;
import java.util.Set;

public class NoHash {
    static class Point {
        final int x;
        Point(int x) { this.x = x; }

        @Override
        public boolean equals(Object o) {
            if (!(o instanceof Point)) return false;
            return ((Point) o).x == x;
        }
        // no hashCode() override
    }

    public static void main(String[] args) {
        Set<Point> seen = new HashSet<>();
        seen.add(new Point(1));
        System.out.println(seen.contains(new Point(1)));
    }
}

A HashSet uses hashCode to decide where to look, and compares hash codes before it ever calls equals. The inherited hashCode almost certainly gives two separate Points different codes, so equals is never asked. That's why the contract says equal objects must have equal hash codes. L7 writes both methods properly, and L19 shows the buckets.

  1. The new Point's inherited hash code differs from the stored one's, so the set never reaches equals.
  2. equals alone isn't enough. The set compares hash codes first, and these two differ.
  3. The compiler doesn't make you override both methods. That's exactly what makes this bug sneaky.
  4. A failed lookup isn't an error: contains simply returns false.
Part 2

The boxing trap: 127 == 127, but 128 != 128

~23 min

In L2 you met Java's wrapper classes, such as Integer, which put a primitive in an object. Since they're objects, == compares their references. Here's the twist: to save memory, Integer.valueOf (which autoboxing uses) "will always cache values in the range -128 to 127" (Integer.valueOf docs; also JLS §5.1.7). Small boxed values come back as the same shared object, and bigger ones don't:

Code that compares Integers with == passes every test with small numbers, then breaks in production the day an ID or a count goes past 127. Two more details from the Java run:

  • If one side is a primitive int, Java unboxes the other and compares values, which is why c == plain is true.
  • If the wrapper is null, unboxing it throws an NPE. That's the L2 trap again.

The rule is the same as for strings: compare wrappers with .equals(), never ==.

Kotlin's Int? is boxed on the JVM too (L2), so === shows the same cache effect. The Kotlin compiler flags it:

Cache.kt:6:13: warning: identity equality for arguments of types 'Int?' and 'Int?' is prohibited.
What Kotlin does for you. The trap needs == to mean identity, and in Kotlin it doesn't. c == d compares the values whether they're boxed or not, so the bug can only appear if you reach for === on numbers, and the compiler warns you when you do. Kotlin also stops you from unboxing a null at compile time (L2, L3).
Practice · Only the real changes

// Which items changed between two snapshots? A missing key counts as null.
fun changedKeys(before: Map<String, Int?>, after: Map<String, Int?>): List<String> =
    (before.keys + after.keys)
        .filter { before[it] !== after[it] }
        .sorted()

!== asks "different objects?" A boxed 500 in one map and a boxed 500 in the other are two objects. You want "different values?", and Kotlin's != asks exactly that, even for Int?.

The fix is one character: before[it] != after[it]. It also treats two nulls as equal, and a null and a number as different, with no !! needed. In Java, != on Integer is the same bug. Use !Objects.equals(a, b), because a.equals(b) throws when a is null.

Final answer

Why it works. != calls equals, so it compares the numbers inside the boxes. The starter's !== compared the boxes themselves. It seemed to work for small counts only because Integer.valueOf hands out shared objects from −128 to 127. Kotlin's != is also null-safe, so unknown and missing counts need no special case. Java's Objects.equals gives you the same thing.

Common mistake. Unboxing by force to "compare the real numbers": before[it]!! != after[it]!!, or .intValue() in Java. It fixes the 500s, then throws a NullPointerException on the first missing or unknown count.

Two separate Integer objects. Only −128 to 127 are guaranteed to be shared.

What's the safe way to compare two Integer objects in Java?

equals compares the values. If either side could be null, Objects.equals(c, d) is safer still.

  1. On two Integers, == compares references, so it fails above 127.
  2. Java has no === operator. That's Kotlin's identity check, and identity is the wrong question anyway.
  3. Integer.equals compares the wrapped int values.

The int on the right forces Java to unbox missing, and there's nothing to unbox.

  1. Java never gets to compare: the int side forces missing to be unboxed first.
  2. null holds no number at all, so it can't equal 128.
  3. Comparing an Integer with an int is legal. The compiler inserts the unboxing.
  4. Unboxing calls missing.intValue(), and calling a method on null throws.

Java: two cached Integers, each incremented once. What does this print?

public class Bump {
    public static void main(String[] args) {
        Integer a = 127, b = 127;
        System.out.print((a == b) + " ");
        a++;
        b++;
        System.out.println((a == b) + " " + (a == 128));
    }
}

a++ on an Integer unboxes, adds 1, and boxes the result again with Integer.valueOf(128). 127 came from the cache, so the first a == b is true. 128 doesn't, so after the increments each variable holds its own new object. a == 128 has an int on one side, so Java unboxes and compares values.

  1. a++ can't change the shared 127 object, because an Integer is immutable. It boxes a new 128, outside the cache.
  2. With an int on one side, == unboxes and compares values, and a really holds 128.
  3. 127 is cached and shared, the reboxed 128s are two objects, and the mixed comparison unboxes.
  4. Values from −128 to 127 always come back as the same cached object, so the first a == b is true.

~33 min

The view saw "Grace" arrive, because it's just another arrow to, or a thin wrapper around, the same list. The JDK says query operations on an unmodifiable view "read through" to the original (Collections.unmodifiableList docs). The snapshot didn't see "Alan", because it's a separate object. A Kotlin List works the same way: the type only removes the mutating methods from your reference (Kotlin docs: Collections overview).

Why bother? Aliasing bugs

Every bug in L4's aliasing examples needs two things: shared references and mutation. Take away either one and that whole class of bug disappears. You can't always avoid sharing, but you can often avoid mutation. That's why experienced engineers default to val, read-only types and immutable data, and only reach for mutation on purpose. It pays off even more once threads appear in L26.

Defensive copies

Here's the classic real-world version of the bug. A class keeps the list you gave it, and you keep using that same list:

The fix is a defensive copy: copy on the way in, and never hand out your mutable internals on the way out. What Kotlin does for you. Exposing the property as List<String> means outside code can't even write team.players.add(…). It's a compile error, where Java waits until runtime. Copying costs a little time and memory. For small collections it's almost always worth it. You will measure costs like this properly in L24 (profiling).

Practice · Seal the grade book

GradeBook leaks: the caller's list is its list, and all hands out that same list behind a read-only type. Make it safe:

  • Changes to the caller's list after construction must not reach the book.
  • A list you got from all earlier must not change when the book does.
  • No outside code may change the book's scores, even by casting. add must still work.
class GradeBook(private val scores: MutableList<Int>) {
    fun add(score: Int) {
        scores.add(score)
    }

    // A read-only type... but which list does it point at?
    val all: List<Int>
        get() = scores
}

    @Test fun `casting back to MutableList can't change the book`() {
        val book = GradeBook(mutableListOf(70, 80))
        runCatching { (book.all as MutableList<Int>).add(0) }   // a read-only type is only a type
        assertEquals(listOf(70, 80), book.all)
    }
}

Hint 1 of 3

There are two leaks: one on the way in (the constructor keeps the caller's list) and one on the way out (all returns the book's own list). Each needs a copy.

Hint 2 of 3

On the way in, the book still needs a list it can add to, so a plain toList() copy won't do. toMutableList() makes a mutable copy that only the book holds. Take the constructor parameter as a plain List<Int> while you're at it.

Hint 3 of 3

On the way out, get() = scores.toList() returns a fresh snapshot each time, so a list someone got earlier stays as it was, and a cast reaches only the copy. In Java: new ArrayList<>(scores) in the constructor, and List.copyOf(scores) in all().

Final answer

Why it works. After the fix, no reference to the book's list ever leaves the class. The constructor copies the caller's list into one only the book holds, and all hands out a new snapshot each time. A List<Int> type alone only hides add from your reference. The object behind it is still the book's MutableList, which is why the cast in the last check could change it. Java's List.copyOf goes one step further: the snapshot itself refuses writes.

Common mistake. Copying on the way in but returning scores on the way out, trusting the read-only type. Callers then hold a live view: it changes under them when the book changes, and a cast lets them change the book.

Check

val names = mutableListOf("Ada"). Does names.add("Linus") compile?

val forbids names = …, but not changes to the object.

  1. val forbids re-pointing names. The list object itself stays mutable.
  2. val freezes the variable, not the object. Mutability comes from the list's type.
  3. var only adds the ability to re-point the variable. add needs neither.
  4. toList() returns a read-only List, which has no add at all.

val view: List<String> = names, then names.add("X"). What's "X" in view?

It's the same object reached through a read-only reference, so it sees every change.

  1. view and names point at one list, so the new element is visible through both.
  2. Assigning to a List variable copies the reference, not the list. No snapshot was taken.
  3. in calls contains, a read operation that a read-only List allows.
  4. Reading through a read-only type is fine. Only mutating calls like view.add won't compile.

Java: Collections.unmodifiableList(list) vs List.copyOf(list)?

A view reads through to the original. A copy is a separate, unmodifiable object.

  1. List.copyOf copies the elements once, so later changes to the original don't reach it.
  2. Backwards: the view reads through to the original, and the copy is a separate object.
  3. The view wraps the original list, while the copy holds its own elements.
  4. Both allow every read operation. They refuse only writes.

Where should a class make its defensive copy of a list argument?

Copy as soon as you receive it, before the caller can change it under you, and never hand out the mutable original.

  1. Callers keep their reference and can change your list later, as TeamBug showed.
  2. Copying in the constructor cuts the link to the caller's list before anything can change it.
  3. toString only reads. Copying there protects nothing about the stored state.
  4. var lets the field be re-pointed. That adds a way to change it, not a protection.

Kotlin: an alias of a string, then two "changes". What does this print?

fun main() {
    var a = "hi"
    val b = a
    a.uppercase()
    a += "!"
    println("$a $b")
}

String is immutable (L2). uppercase() returns a new string, which this code throws away. a += "!" means a = a + "!": it builds another string and re-points a. b still points at the original "hi". That's Part 3's point in miniature: sharing an immutable object is harmless, because nobody can change it under you.

  1. uppercase() can't change a String. It returns a new one, which is ignored here.
  2. On a var string, += builds a new string and re-points a only. b keeps the old one.
  3. uppercase() returned "HI", but nothing stored it, so a was still "hi".
  4. Neither line changed the shared "hi": one result was discarded, and += re-pointed only a.

Puzzles, then fixes

~20 min

Step 1: predict, without running

Kotlin P1: x == y, both Int? holding 1000

Kotlin == compares values, even for boxed numbers.

  1. Kotlin's == calls equals, which compares the boxed values.
  2. That's Java's ==. Only Kotlin's === would compare the two boxes.
  3. Neither side is null, and == is null-safe anyway, so nothing throws.
  4. == on two Int? values is legal. Only === earns a warning.

Java P1: x == y, both Integer holding 1000

1000 is outside the −128 to 127 cache, so these are two different objects.

  1. Only −128 to 127 come from the shared cache. 1000 is boxed into two objects.
  2. == compares two different Integer references.
  3. No null and no unboxing are involved, so nothing throws.
  4. Comparing two Integer references with == is legal Java.

P2, both languages: what does first print?

second is an alias of first. One list, two arrows.

  1. second = first copied the arrow, not the list, so the add changed first's list too.
  2. add appends to the existing list. It doesn't replace the contents.
  3. Nothing duplicated the list. There's one list, holding 1, 2 and then 3.
  4. first and second point at one list, and it gained a 3.

Java P3: new int[]{1, 2}.equals(new int[]{1, 2})

Arrays inherit identity equals. (Kotlin's P3 uses contentEquals, so it prints true.)

  1. Arrays don't override equals, so equal contents don't count. Arrays.equals would say true.
  2. Calling equals on a non-null array is ordinary. It just returns false.
  3. Arrays inherit Object.equals, and these are two separate array objects.
  4. Every array is an Object, so it has an equals method to call.

Kotlin P4: frozen.size after first.clear()

frozen is a read-only view of the same list. "Frozen" was a lie.

  1. P2's second += 3 already added to first, and a view follows clear() anyway.
  2. frozen is a read-only view of first's list, so it sees the clear.
  3. That's the size before clear(). Only a copy, like toList(), would keep it.
  4. Reading size through a read-only view is allowed, and clearing doesn't break the view.

Java P4: t == "hello", where t = s + "lo" and s is a variable

t is built at runtime, so it isn't the interned literal. P5's equals correctly says true.

  1. t is built at runtime, so it's a different object from the interned literal.
  2. Only literals and constant expressions are interned. s + "lo" with a non-final variable s isn't constant.
  3. Both sides are non-null strings, and == on references never throws.
  4. Comparing two String references with == is legal, just usually wrong.

Wrap-up

Exit quiz, recall card, sources

~5 min

Kotlin: a == b when a is null

a?.equals(b) ?: (b === null): it's true only if b is null too.

  1. Kotlin's == becomes a?.equals(b) ?: (b === null), which never calls a method on null.
  2. == is allowed on nullable types. Null safety is built into it.
  3. The safe call skips equals when a is null, then checks whether b is null too.
  4. == always gives a Boolean: true if both are null, false otherwise.

Which Kotlin expression makes an independent copy of a list?

A cast just changes the type of the same reference, and asReversed() returns a view. toList() copies.

  1. A cast changes only the static type of the same reference. No new list is made.
  2. !! only asserts non-null and returns the same reference.
  3. asReversed() returns a reversed view that follows changes to the original.
  4. toList() copies the elements into a new list.

Java's Map.of(…) iteration order is…

"Unspecified and is subject to change" (L3).

  1. Map.of doesn't sort. A sorted map is a TreeMap.
  2. Keeping insertion order is a LinkedHashMap promise. Map.of makes none.
  3. The JDK docs say the order is unspecified and subject to change, so don't depend on it.
  4. No order is promised at all, reversed or otherwise.
