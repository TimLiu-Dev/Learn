Part 1

Eager vs lazy: List, Sequence, Stream

~30 min

In L14 you chained filter and map on lists. Each of those calls is eager: it runs over the whole list and returns a new list, and only then does the next step start. The Kotlin docs: "each processing step completes and returns its result – an intermediate collection". A Sequence is lazy. It "performs all the processing steps one-by-one for every single element", and "actual computing happens only when the result of the whole processing chain is requested" (Kotlin docs: Sequences). A Java Stream works the same way: its intermediate operations "are always lazy" (java.util.stream docs).

Put a println inside each lambda and the difference becomes visible:

Short-circuiting: stopping early

Operations like first, any and take can finish without seeing every element. The stream docs call them short-circuiting, and they "can allow computations on infinite streams to complete in finite time" (java.util.stream). Count how many source elements are actually pulled:

take(3): [10, 20, 30], visited 3
no terminal op, visited 0
eager chain: 8, visited 1000
first square > 50: 8, visited 8
any even: true, visited 2
limit(3): [10, 20, 30], visited 3
no terminal op, visited 0
  • Out of a thousand elements, the lazy versions pulled only 8, 2 and 3.
  • No terminal operation means nothing runs at all, not even once. A sequence or stream that you build and never consume is a silent no-op, and that includes any println you were relying on.
  • The last Kotlin line uses an eager chain. onEach on a range walked all 1000 elements before first even started.
  • The Java side shows L14's rule again: a lambda can't change a captured local, so the count lives in an AtomicInteger. Kotlin just captures var visited.
  • peek is the stream version of onEach. Its docs say it "exists mainly to support debugging" (Stream.peek), so don't build program logic on it.

Infinite sequences

Because nothing is computed until it's asked for, a lazy source can be endless, as long as something downstream stops it. Kotlin gives you generateSequence(seed) { next }, which ends when the function returns null, and the sequence { … yield(x) … } builder, which suspends at each yield "until the next element is requested by the consumer" (Kotlin docs).   • A Java stream is single-use. "A stream should be operated on … only once", and an implementation "may throw IllegalStateException if it detects that the stream is being reused" (Stream docs). The fix is a Supplier<Stream<…>>, or a method that builds a fresh stream each time.

Each terminal operation re-runs the whole recipe, so the lambdas run again. constrainOnce() opts into Java-style one-shot behaviour, and "IllegalStateException is thrown on iterating the returned sequence for the second time" (constrainOnce).

Stateless vs stateful operations

map and filter look at one element at a time. sorted can't: it can't emit the smallest element until it has seen all of them. The stream docs call it stateful ("such as distinct and sorted"), operations that "may need to process the entire input before producing a result" (java.util.stream). Kotlin's API docs label Sequence.sorted() "intermediate and stateful" (sorted).

The sorted step acts as a wall. Everything upstream of it runs to completion first, so laziness can't save you work there, and it can never finish on an infinite sequence.

Laziness isn't free. The Kotlin docs warn that it "adds some overhead which may be significant when processing smaller collections or doing simpler computations", and suggest you "consider both Sequence and Iterable and decide which one is better for your case" (Kotlin docs). Don't sprinkle asSequence() everywhere. Reach for it when you have many steps, a lot of data, or an early exit.

Boxing (L5) again. A Stream<Integer> or a Sequence<Int> holds boxed Integer objects, because a generic type argument must be a reference type on the JVM (L13). Java offers IntStream, LongStream and DoubleStream to stay with primitives. Kotlin gets the same effect from ranges, IntArray and functions like sumOf:

338350 338350
min=4 max=42 avg=18.0

One more method you'll meet: parallel() splits a stream across CPU cores (Parallelism). Leave it alone until the concurrency phase, because the rules about shared state matter there.

What Kotlin does for you.
  • The same filter/map/take names work on both List and Sequence, so switching to lazy is one call: asSequence(). Java collections have no map/filter of their own: you either loop or use a stream.
  • You can finish with toList(), first { } or sum(), with no Collectors needed for the common cases.
  • sequence { yield(…) } lets you write a generator as a normal loop, where Java has to carry the state along inside the elements.
  • Sequences can be re-iterated, so there's no "already operated upon" crash unless you ask for it with constrainOnce().
  • Lambdas can update a captured var.

Part 2

Scope functions

~25 min

Kotlin's standard library has five functions "whose sole purpose is to execute a block of code within the context of an object": let, run, with, apply and also. They "don't introduce any new technical capabilities, but they can make your code more concise and readable" (Kotlin docs: Scope functions). All five do the same basic thing. They differ along just two axes:

  1. How the block sees the object: as this (a receiver, so you can call its members without a prefix), or as it (an ordinary lambda argument).
  2. What the call returns: the lambda's result, or the object itself, which lets you keep chaining.

Line by line, here's what Java does instead:

  • ?.let → Optional.map or an explicit if (x != null) (L3).
  • apply → a builder. Effective Java Item 2 recommends one when a constructor has many parameters, and it's the most boilerplate on the page: a nested class, a method per field, a build(). Kotlin gets most of the way with named and default arguments (L3) plus apply.
  • also, with → a temporary variable, then separate statements.
  • run → repeat the variable name: server.tls, server.host, server.port.
  • takeIf / takeUnless → a conditional expression. takeIf "returns this object if it satisfies the given predicate. Otherwise, it returns null", so it's "a filtering function for a single object" (docs). The port was 443, which is odd, so takeIf { even } gave null.

Bridge: the Java builder pattern is everywhere in Spring and Android Java APIs. Kotlin code that calls them often swaps the builder for SomeObject().apply { … }, or for a DSL built from the trick explained below.

When scope functions hurt

The docs warn: "avoid nesting scope functions and be careful when chaining them because it's easy to get confused about the current context object and value of this or it" (docs). Here's the problem in real code:

1: domain example.com | domain example.com
2: no contact | no contact
3: no contact | no contact

In domainNested the name it means three different things: a User, then a String email, then a domain. kotlinc compiled it without a single warning. The flat version with names and ?: return is longer by one line, and you can read it top to bottom. Java's Optional chain has the same trade-off. Rule of thumb: one scope function per expression, and if you need a name, write a val.

How apply works: lambdas with a receiver

None of these are keywords. They're ordinary inline generic functions (L13, L14), and here is the real signature from the standard library (apply):

inline fun <T> T.apply(block: T.() -> Unit): T

The new piece is T.() -> Unit, a function type with receiver. Inside such a lambda "the receiver object passed to a call becomes an implicit this, so that you can access the members of that receiver object without any additional qualifiers" (Kotlin docs: Function literals with receiver). It's an extension function (L9) written as a lambda. Write your own:

built with myApply

That's the whole trick behind Kotlin DSLs (domain-specific languages). buildString is declared as inline fun buildString(builderAction: StringBuilder.() -> Unit): String (buildString), and htmlList { item("eggs") } works the same way. Java can pass the object as a Consumer<T> parameter, but it can't make it an implicit this, so every call inside needs a prefix like l.item(…).

Bridge: Gradle's build.gradle.kts (L1, L11), Jetpack Compose on Android and Spring's Kotlin DSLs are all built from lambdas with receivers. Now you know what dependencies { … } really is: a function call whose last argument is a lambda with a receiver.

What Kotlin does for you.
  • Function types with receivers (T.() -> R) let a library hand you an implicit this. That's how apply, run, with and buildString work, and every Kotlin DSL too. Java has no equivalent.
  • All five scope functions are inline (L14), so they cost nothing at runtime.
  • In Java you write the alternatives yourself: Optional, temporary variables, a builder class.

Part 3

Delegation

~25 min

Some property patterns come up again and again: compute the value on first use, notify someone when it changes, clamp it to a range. Java makes you write each one by hand in every getter and setter. Kotlin's delegated properties let you write the logic once in a delegate object, then attach it with by: "the get() (and set()) that correspond to the property will be delegated to its getValue() and setValue() methods" (Kotlin docs: Delegated properties).

by lazy: compute on first access

catalog created
  (loading products...)
first access: 3
second access: mat
before config
  (loading config...)
mode = dev
mode again = dev
  • Creating the object doesn't run the initializer. The first read does, and later reads return the cached value. That's how this differs from L6's custom getter, which recomputes on every read, and from lateinit, where you must assign the value before anyone reads it.
  • It's thread-safe by default. lazy { } uses LazyThreadSafetyMode.SYNCHRONIZED (lazy): "the value is computed only in one thread, but all threads will see the same value" (docs). You can pass PUBLICATION or NONE to trade safety for speed (LazyThreadSafetyMode).
  • Java's if (field == null) check is not thread-safe. Two threads can both see null and both load. The concurrency phase shows why. For a static field, the safe idiom is the holder class (Effective Java Item 83). The JVM initializes a class the first time it's used, and only once (JLS §12.4.1), so Holder.VALUES loads on the first call to values().

Observable, vetoable, and map-backed properties

  target 20 -> 22
  target 22 -> 19

  • Delegates.observable(initial) { prop, old, new -> } runs its handler "every time you assign to the property (after the assignment has been performed)" (docs).
  • vetoable's handler runs "before the assignment". Returning false silently rejects the new value, which is why limit stayed 28 after you tried 45.
  • by map reads each property from a map entry with the same name (docs). It's handy for parsed JSON or config, as long as you trust the keys. A missing key throws when you read it.

Your own delegate

A delegate is any object with getValue (and, for a var, setValue). The easiest way to write one is to implement the standard ReadWriteProperty interface (docs):

  volume: 42 clamped to 10
  balance: -9 clamped to -5
volume=10 balance=-5

What does by compile to? The docs say that for a property prop the compiler "generates the hidden property prop$delegate, and the code of the accessors simply delegates to this additional property" (Translation rules). javap confirms it:

Class delegation: composition without the boilerplate

Back to L8. The fix for InstrumentedHashSet was composition plus forwarding, and Effective Java Item 18 writes a ForwardingSet that forwards every one of Set's methods by hand. Kotlin's : MutableSet<E> by inner means "b will be stored internally in objects of Derived and the compiler will generate all the methods of Base that forward to b" (Kotlin docs: Delegation):

Two gotchas, both verified:

  1. The delegate never calls your overrides. AddOnlyCountingSet overrides only add, so addAll forwards straight to the inner HashSet, whose internal add calls are its own. The count is 1, not 3. The docs: "members overridden in this way do not get called from the members of the delegate object, which can only access its own implementations". This is the mirror image of L8. Inheritance counted too much because the superclass called back into you, and delegation counts too little if you forget a method, because it never calls back. Either way, override every entry point you care about. Java's forwarding class behaves the same.
  2. toString, equals and hashCode are not forwarded. They come from Any, not from the Set interface, and they're missing from the javap list. A delegating wrapper prints as CountingSet@1b6d3586-style output and compares by identity unless you override them. Bloch's ForwardingSet forwards them explicitly, as the Java column does.
What Kotlin does for you.
  • by lazy gives you thread-safe, cached lazy initialization in one line. Java needs a null check (unsafe across threads) or a holder class.
  • by Delegates.observable/vetoable and by map replace hand-written setter logic and casts.
  • Your own delegate is written once and attached with one line per property. The compiler generates the hidden $delegate field and the accessors, and hands you the property's name.
  • : Interface by inner generates every forwarding method. That's composition at the price of inheritance, and it's why Kotlin can make classes final by default (L8) without making reuse painful.

Debuggingbreakpoint on any line (L12)harder to step through. Use onEach/peek or split into named vals

Neither is "the right one". Pipelines win for standard transformations. Loops win when the logic has lots of state or early exits with side effects. You should be able to write both from a blank file, and now you can.

Java: Stream.of("x").map(Integer::parseInt) is assigned to a variable, then the program prints done. No terminal op. What happens? (L10 + L15)

parseInt("x") would throw a NumberFormatException, but it never runs, because without a terminal operation the lambda isn't called. Verified: the output is just done.

val name: String? = null, then name?.let { it.length } ?: 0 (L3)

?. skips let on null, so the whole left side is null, and ?: supplies 0.

generateSequence(1) { it + 1 }.toList() on a JVM with -Xmx32m (L4)…

The sequence never returns null, so toList() keeps growing a list. Int overflows (L2) and keeps going, until the run ends with java.lang.OutOfMemoryError: Java heap space. An infinite source needs a short-circuiting step like take.

L8 said "favour composition over inheritance". What does Kotlin's by add?

The compiler generates the forwarding methods at compile time. The delegate never calls back into you, which was the gotcha in Part 3.
