When does the garbage collector consider an object collectable? (L24)

Reachability is the rule: an object stays alive while a chain of references leads to it from a GC root (a local variable in a live frame, a static field, and so on). Setting one reference to null only helps if it was the last path.

  1. An object outlives a call whenever something still references it, such as a field or a list.
  2. Heap fullness decides when the GC runs, not which objects it may collect.
  3. Reachability from roots, like live local variables and static fields, is the only test.
  4. Nulling one reference helps only if it was the last path from a root.

By itself, what does putting @Test on a method do? (L11)

An annotation is metadata. JUnit's engine scans your test classes, finds methods carrying @Test and calls them. Part 2 shows exactly how code does that.

  1. An annotation is inert metadata: JUnit's engine finds @Test by reflection and calls the method.
  2. The method compiles exactly the same way with or without the annotation.
  3. JUnit doesn't promise an order between test methods unless you ask for one.
  4. Visibility comes from modifiers like private, never from annotations.

Who acts on @JvmOverloads? (L9)

kotlinc reads it and generates the extra overloads in the bytecode. Some annotations are for the compiler, some for build-time tools, and some for code running later. Part 1 sorts them out.

  1. The JVM just runs the overloads kotlinc already wrote. It never acts on the annotation.
  2. kotlinc reads it while compiling and writes the extra Java-callable overloads into the class file.
  3. The jar task only packs compiled classes. It never reads annotations.
  4. No reflection is involved: the overloads exist before the program ever runs.

Why does a compiled Kotlin program need kotlin-stdlib.jar on its classpath at runtime? (L23)

kotlinc emits calls into the stdlib, for example the Intrinsics.checkNotNullParameter null checks you saw with javap. Part 3 shows what happens when that jar is missing.

  1. The JVM runs unsigned class files all the time. Signing jars is optional.
  2. Your classes live in your own output folder or jar, not inside the stdlib.
  3. The bytecode verifier is part of the JVM itself, not of any library.
  4. kotlinc emits calls into stdlib classes like Intrinsics, so they must be loadable.

Annotations

The Java spec is blunt about it: "An annotation is a marker which associates information with a program element, but has no effect at run time" (JLS §9.7). An annotation is a label stuck on a class, method, field or parameter. Nothing happens until some tool reads the label. There are exactly three kinds of reader, and every annotation you'll ever meet is aimed at one of them:

Declaring your own

Java declares an annotation with @interface. Its elements look like methods and can have defaults. Kotlin uses annotation class, and the elements are constructor parameters. Both get two meta-annotations, which are annotations on annotations. @Target says what the annotation may be attached to. @Retention says how long it survives:

KotlinJavaKept until
SOURCESOURCEcompilation. Not in the .class file at all.

Kotlin use-site targets

One Kotlin line, class User(val email: String), produces three JVM things: a constructor parameter, a private field, and a getEmail() getter (L6). So when you annotate email, which one gets the annotation? Kotlin lets you say exactly, with a use-site target: @field:, @get:, @set:, @param:, @property:, @file:, and since 2.4 @all: (Kotlin docs: use-site targets). The Java comparison is a record, whose components produce the same three things:

a: param=[] field=[field] getter=[]
b: param=[] field=[] getter=[get]
c: param=[param] field=[] getter=[]
d: param=[none] field=[none] getter=[]
e: param=[all] field=[all] getter=[all]
a: param=[component] field=[component] getter=[component]
  • Explicit targets (a, b, c) land exactly where you say.
  • No target (d): "the compiler chooses one or more" of them. The constructor parameter if applicable, then the property if applicable, then the field "if it's applicable and the property target isn't" (Kotlin docs). Tag can't target a Kotlin property, so d gets param and field. That's what a Java framework reading fields expects.
  • This rule is new. Before Kotlin 2.2, an annotation went to "only one of param, property, or field" (What's new in 2.2), usually just the parameter. The new defaults and @all: became Stable in Kotlin 2.4.0. Older Stack Overflow answers about "my @Email annotation is ignored" describe the old rule.
  • Java records do this automatically: a component annotation "is propagated to the declarations of members and constructors of the record class if their annotation interfaces are applicable" (JLS §8.10.1). That's why the Java side shows it in all three places.
  • @property: annotations are "not visible to Java" at all. Only Kotlin's own reflection sees them (Part 2).

Annotation processing: code that writes code

The middle reader in the first table runs during the build. An annotation processor sees your annotated declarations and generates new source files that get compiled with the rest. No reflection is needed at runtime, so it's fast and errors appear at compile time. Kotlin has two ways to run one:

What Kotlin does for you.
  • override and fun interface are keywords, so you can't forget them the way you can forget @Override.
  • Custom annotations default to RUNTIME, so they're readable by reflection with no extra line. A Java annotation without @Retention(RUNTIME) is silently invisible.
  • @Deprecated can carry a ReplaceWith that the IDE applies for you, and a level that escalates a warning to an error.
  • Annotation elements are ordinary constructor parameters with defaults, and arguments can be named: @Timed(warnAbove = 50).
  • The cost: one property is three JVM elements, so you sometimes have to say which one with @field: or @get:. Java records spread annotations to all three automatically.

// The "framework": it reads annotations through Java reflection. Don't change it.
fun columns(type: Class<*>): Map<String, String> =
    type.declaredFields
        .mapNotNull { f -> f.getAnnotation(Column::class.java)?.let { f.name to it.name } }
        .sortedBy { it.first }
        .toMap()

fun auditedMethods(type: Class<*>): List<String> =
    type.declaredMethods.filter { it.isAnnotationPresent(Audited::class.java) }.map { it.name }.sorted()

Hint 1 of 3

Three separate bugs. BINARY keeps an annotation in the class file but hides it from reflection, and RUNTIME is the opposite of what @Secret wants.

Hint 2 of 3

For @Column: with no @Target, Kotlin 2.4 puts an annotation on a constructor val as param + property, and Java reflection on fields sees neither. Restrict the annotation to one target with @Target(AnnotationTarget.…).

Hint 3 of 3

@Target(AnnotationTarget.FIELD) on Column; delete the @Retention line on Audited (the default is RUNTIME); @Retention(AnnotationRetention.SOURCE) on Secret. In Java, you'd also have to add @Retention(RUNTIME) to Column and Audited, because Java's default is CLASS.

Final answer

Why it works. Retention decides whether reflection can see an annotation at all: RUNTIME (Kotlin's default) yes, BINARY no, SOURCE not even in the file. @Target(FIELD) leaves the default use-site rule only one place to put @Column: the backing field, which is exactly where the framework looks.

Common mistake. Writing @field:Column at each use instead. The framework then works, but nothing stops the next person from putting @Column on a function, where it would be silently ignored. A @Target makes the compiler refuse that.

Java: @interface Audit {} has no @Retention. A method carries @Audit. What does method.getAnnotation(Audit.class) return?

Java's default retention is CLASS: the annotation is in the class file but invisible to reflection, so you get null. The Audited line in RetentionDemo's javap output showed it as RuntimeInvisibleAnnotations.

  1. Default CLASS retention keeps it in the file but hidden from reflection, so the lookup finds nothing.
  2. Only RUNTIME retention lets reflection return an instance, and Java's default is CLASS.
  3. A missing annotation isn't an error: getAnnotation simply returns null.
  4. The call is legal for any annotation type. javac doesn't check retention here.

Kotlin: annotation class Audit has no @Retention. Same call, getAnnotation(Audit::class.java)?

Kotlin's default is "stored in the compiled class files and … visible through reflection at runtime" (Kotlin docs), the same as Java's RUNTIME. Timed in RetentionDemo.kt had no @Retention and was found.

  1. That's Java's CLASS default. Kotlin's default retention is RUNTIME.
  2. Kotlin annotations are RUNTIME by default, so reflection finds and returns one.
  3. Nothing fails: the annotation is present and visible.
  4. Audit::class.java is exactly the Java class object getAnnotation expects.

Kotlin 2.4: class User(@Email val email: String), where Java's @Email targets FIELD, METHOD and PARAMETER. Where does it end up?

The 2.4 default: param if applicable, property if applicable (not here, it's a Java annotation), otherwise field. That's the d row of UseSite.kt. Before 2.2 it would have been the parameter only.

  1. A getter gets an annotation only with @get: or @all:, never by default.
  2. The constructor parameter is applicable and comes first in the rule, so it gets one too.
  3. param applies; property doesn't, since it's a Java annotation; so field is added.
  4. That was the rule before Kotlin 2.2. The current default adds the field as well.

In a current Android project, what turns Room's @Dao interface into working database code?

Room's processor runs during the build, through KSP or older kapt, and generates the implementation as source. Android recommends KSP, because kapt "is now in maintenance mode".

  1. Room generates its code at build time, so no reflection scan happens at app start.
  2. The class loader only loads classes. It never writes new code from annotations.
  3. R8 shrinks and renames code. It doesn't generate Room's implementation.
  4. Room's annotation processor runs through KSP and generates the DAO implementation as source.

You call a function marked @Deprecated("…", level = DeprecationLevel.ERROR).

ERROR makes every use a compile error with your message, as err/DeprecatedError.kt showed. WARNING, the default level, only warns.

  1. Level ERROR turns every use into a compile error carrying your message.
  2. A warning is the default level, WARNING. ERROR goes one step further.
  3. Deprecation is checked by the compiler. Nothing extra happens at runtime.
  4. It never gets to run, because the calling code no longer compiles.

Java: a runtime-visible @Tag, with no @Target, on a record component. What does this print?

import java.lang.annotation.*;

public class Spread {
    @Retention(RetentionPolicy.RUNTIME)
    @interface Tag {}

    record User(@Tag String email) {}

    public static void main(String[] args) throws Exception {
        boolean onField = User.class.getDeclaredField("email").isAnnotationPresent(Tag.class);
        boolean onAccessor = User.class.getMethod("email").isAnnotationPresent(Tag.class);
        System.out.println(onField + " " + onAccessor);
    }
}

A record component's annotation "is propagated to the declarations of members and constructors of the record class if their annotation interfaces are applicable" (JLS §8.10.1). With no @Target, @Tag is applicable to every declaration, so the private field, the email() accessor and the constructor parameter all carry it. Compare Kotlin, where you pick the place with @field:, @get: or @all:.

  1. Record components aren't plain parameters: their annotations spread to the generated members too.
  2. The accessor email() is a method, an applicable target, so it gets @Tag as well.
  3. The private field is applicable too, so it carries @Tag like the accessor.
  4. @Tag has no @Target, so it's applicable everywhere and lands on both.

Reflection

~33 min

Reflection is code inspecting and using other code at runtime: listing a class's methods, calling one by name, reading its annotations, creating instances. dev.java: "Reflection is commonly used by programs which require the ability to examine or modify the runtime behavior of applications running in the Java virtual machine" (dev.java: The Reflection API). It's how a framework can call your methods without ever having been compiled against them.

Getting hold of a class

Everything starts from a class object. Java has Class<T>. Kotlin has its own KClass<T>, which knows Kotlin-only things like properties and nullability, plus a bridge to the Java one:

There's exactly one Class object per loaded class (per class loader, L23), so === is true however you got it. Class.forName("Point") is the interesting one: the name is just a string, so it could come from a config file. That's how plugin systems and JDBC drivers get loaded.

Hint 1 of 3

Start from type.declaredMethods, keep the ones where isAnnotationPresent(Check::class.java), and sort by name: the array comes back in no particular order.

Hint 2 of 3

Hint 3 of 3

Anything the method throws arrives wrapped in InvocationTargetException. Catch that and report e.cause: "FAIL ${method.name}: ${real.javaClass.simpleName}: ${real.message}". Java is the same, with getCause(), getSimpleName() and getMessage().

Final answer

Why it works. This is JUnit's core loop: scan for an annotation, sort, create a new instance per test (L11), invoke, and turn exceptions into reports. A fresh instance keeps checks independent, so counts passes whatever ran before it. Unwrapping InvocationTargetException reports what really went wrong.

Common mistake. Catching Exception and reporting e itself. You get FAIL divides: InvocationTargetException: null: the wrapper has no message, and the real ArithmeticException is hidden in e.cause.

Why do frameworks scan for annotations once at startup and keep the Method objects?

Scanning and lookups are the slow part, and a mistake like a duplicate route or a bad signature should crash at startup, not on the first request. Your router's constructor does all its checks for exactly this reason.

  1. A Method object can be invoked any number of times.
  2. Lookups done once make later calls cheap, and mistakes crash at startup instead of mid-request.
  3. The JVM allows repeated lookups. They're just slower than reusing the result.
  4. RUNTIME annotations stay readable for as long as the class is loaded.

public class Lookup {
    static class Calc {
        public int twice(int x) { return 2 * x; }
    }

    public static void main(String[] args) throws Exception {
        String first;
        try {
            first = String.valueOf(Calc.class.getMethod("twice", Integer.class).invoke(new Calc(), 21));
        } catch (NoSuchMethodException e) {
            first = "missing";
        }
        Object second = Calc.class.getMethod("twice", int.class).invoke(new Calc(), 21);
        System.out.println(first + " " + second);
    }
}

A method is found by its name plus its exact parameter types. twice takes the primitive int, and int.class and Integer.class are different class objects, so the first lookup throws NoSuchMethodException. Once you have the right Method, invoke unboxes the Integer 21 for you. In Kotlin, Int::class.javaPrimitiveType gives int.class.

  1. The lookup needs exact parameter types: Integer.class misses, int.class finds twice.
  2. getMethod doesn't autobox: Integer.class and int.class are different class objects.
  3. It's the other way round: the Integer.class lookup fails, and the int.class one works.
  4. The second lookup matches exactly, and invoke unboxes 21 for the int parameter.

  • A closed-source Android app. Every install is a distribution of your APK, and everything in it. Beyond one module: version numbers that mean something

Version conflicts are only manageable if version numbers carry meaning. Semantic Versioning 2.0.0 (SemVer) gives them one: "Given a version number MAJOR.MINOR.PATCH, increment the: MAJOR version when you make incompatible API changes, MINOR version when you add functionality in a backward compatible manner, PATCH version when you make backward compatible bug fixes."

  • What counts as breaking is anything that can stop a caller's code from compiling, or already-compiled code from running: removing or renaming a public class or method, changing a parameter or return type, adding an abstract method to an interface callers implement, making an open class final. A subtle Kotlin one: adding a parameter with a default value keeps source compatibility but changes the JVM signature, so old compiled callers fail with NoSuchMethodError. That's what @JvmOverloads (L9) helps with. Changing behaviour callers rely on is breaking too, even when every signature stays the same.
  • Compare numerically. "Each element MUST increase numerically. For instance: 1.9.0 -> 1.10.0 -> 1.11.0." As text, "1.9.0" > "1.10.0".
  • Before 1.0.0, no promises: "Major version zero (0.y.z) is for initial development. Anything MAY change at any time."
  • SemVer is a promise, not a guarantee. Libraries make mistakes, and not every project follows SemVer. Under SemVer, Guava's 33.5.0-jre would be a pre-release, because a hyphen marks one; for Guava, -jre just names the Java flavour (there's an -android one too). That's why Gradle's resolution rule is simply "highest wins", and why you still run your tests after upgrading.

Avoid dynamic versions. Gradle accepts 1.+, meaning "Only versions exactly matching the portion before the + are included", and then picks the newest (Gradle: Declaring Versions and Ranges). I tried two in the build below:

implementation("com.google.guava:guava:33.+")   // a dynamic version
implementation("org.slf4j:slf4j-api:2.+")
$ ./gradlew -q :app:dependencies --configuration runtimeClasspath   # excerpt
+--- com.google.guava:guava:33.+ -> 33.8.0-jre
\--- org.slf4j:slf4j-api:2.+ -> 2.1.0-alpha1

Guava silently moved to 33.8.0-jre, past the 33.5.0-jre the catalog pins, so a teammate building next month may get yet another version. And 2.+ picked an alpha: by Gradle's version ordering, 2.1.0-alpha1 is higher than any 2.0.x, because the second part, 1, beats 0. Gradle's docs warn that "Using dynamic versions and changing modules can lead to unreproducible builds." Pin exact versions in the catalog, upgrade on purpose, and use dependency locking if you really need ranges.

BOMs and platform(): one version for a family

Some libraries come in families whose versions must match: Jackson's core, databind and annotations, or Spring's dozens of modules. Fix 2: one "fat" jar

Gradle's docs note that it has no built-in way to create uber JARs. They point to the third-party Shadow plugin, or show a Jar task that unzips every runtime jar into yours (Gradle: Creating "uber" or "fat" JARs). I pasted their example and it failed:

Execution failed for task ':app:uberJar' (registered in build file 'app/build.gradle.kts').
> Entry META-INF/versions/9/module-info.class is a duplicate but no duplicate handling strategy has been set. Please refer to https://docs.gradle.org/9.7.1/dsl/org.gradle.api.tasks.Copy.html#org.gradle.api.tasks.Copy:duplicatesStrategy for details.

Six of the runtime jars (Guava, failureaccess, JSpecify, the Kotlin stdlib and two more) each contain META-INF/versions/9/module-info.class, and a zip can hold only one file per path. With the DuplicatesStrategy line added, it works:

// From Gradle's docs, "Creating uber or fat JARs": copy every runtime jar inside.
tasks.register<Jar>("uberJar") {
    archiveClassifier = "uber"
    duplicatesStrategy = DuplicatesStrategy.EXCLUDE   // keep the first copy of clashing files
    manifest { attributes("Main-Class" to "demo.AppKt") }
    from(sourceSets.main.get().output)
    dependsOn(configurations.runtimeClasspath)
    from({
        configurations.runtimeClasspath.get().filter { it.name.endsWith("jar") }.map { zipTree(it) }
    })
}

"1.10.0" < "1.9.0" as strings, because '1' < '9'. Split each version on ".", turn the parts into Ints, and let the first part that differs decide.

Hint 2 of 3

For resolve, the module is everything before the last colon: groupBy({ it.substringBeforeLast(":") }, { it.substringAfterLast(":") }) gives module → versions. Then take maxWith(::compareVersions) of each list.

Hint 3 of 3

SemVer item 4: "Major version zero (0.y.z) is for initial development. Anything MAY change at any time." So any change from a 0. version counts as breaking; otherwise only a different MAJOR does. In Java, a TreeMap with merge(module, version, …) keeps the higher of the old and new version in one pass.

Final answer

Why it works. SemVer says "Major, minor, and patch versions are always compared numerically", so compareVersions compares integers left to right. resolve is Gradle's default rule in miniature: group by module, keep the highest. And isBreaking reads the version the way SemVer intends: only MAJOR announces incompatible changes, and 0.y.z promises nothing.

Common mistake. Comparing versions as strings. "1.9.0" > "1.10.0" in text order, so the resolver silently picks the older library. Real Gradle's ordering is richer still (it also orders qualifiers like -rc1 and -jre), but it never compares the whole string as text.

    val requested = listOf("1.9.0", "1.10.0", "1.2.0")
    val numerically = compareBy<String>(
        { it.split(".")[0].toInt() },
        { it.split(".")[1].toInt() },
        { it.split(".")[2].toInt() },
    )

}

max() on strings compares text character by character. At the third character, '9' beats '1', so "1.9.0" wins. The comparator compares the parts as numbers, which is what SemVer requires: "Major, minor, and patch versions are always compared numerically." A resolver that compares text would pick the older library.

  1. The comparator compares the minor parts as Ints, and 10 is greater than 9.
  2. max() on strings uses text order, where "1.9.0" beats "1.10.0".
  3. Text order picks 1.9.0, and the numeric comparator picks 1.10.0.
  4. Text order doesn't favour 1.2.0: '9' beats '2' at the third character.

Your router stores commands in a HashMap<String, Method>. Average cost of looking up one command by name? (L19)

A hash table gives average O(1) get. That's why the router builds the map once at startup and never scans the methods again per call.

  1. O(n) is a linear scan, which hashing avoids by jumping straight to a bucket.
  2. Hashing the name finds its bucket directly: average constant time.
  3. O(log n) is a sorted tree such as TreeMap, not a HashMap.
  4. O(n log n) is the cost of sorting, not of one lookup.

  1. The ArithmeticException arrives wrapped, so this catch never matches.
  2. It doesn't end quietly: the uncaught wrapper stops the program with a stack trace.
  3. InvocationTargetException isn't an ArithmeticException, so it escapes the catch.
  4. Kotlin has no checked exceptions, so this compiles fine.

Why can't Java reflection tell whether a parameter is List<String> or List<Integer> through getParameterTypes()? (L13)

getParameterTypes() returns the erased class, List.class. Generic signatures are kept as metadata for getGenericParameterTypes(), but the runtime type of a list never knows its element type.

  1. Generics are checked at compile time. At runtime, the parameter's class is just List.
  2. List is a real interface with a class object, List.class.
  3. Reflection handles generic methods fine, and getGenericParameterTypes() even shows type arguments.
  4. Every parameter is visible. Only its type arguments are erased.

kotlinc writes @kotlin.Metadata as a runtime-visible annotation on every class. It "is read by the compiler and reflection".

  1. @JvmStatic changes the bytecode shape for Java callers. It carries no metadata.
  2. @Retention is a meta-annotation saying how long annotations live.
  3. @Target is a meta-annotation saying where annotations may go.
  4. kotlinc writes @kotlin.Metadata on every class, and kotlin-reflect decodes it.
