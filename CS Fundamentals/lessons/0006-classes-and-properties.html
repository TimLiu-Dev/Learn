In Java, which expression asks "are these the same object?"

On references, Java's == compares identity. Kotlin spells that ===.

  1. equals asks "same contents?" in classes that override it. Only Object's default falls back to identity.
  2. On references, Java's == compares the references themselves, so it's true only for one object.
  3. === is Kotlin's identity operator. Java has no ===, so this doesn't compile.
  4. Object has no same method, so this doesn't compile.

Kotlin: listOf(1, 2) == listOf(1, 2)

Kotlin's == calls equals, and lists compare their contents.

  1. Both lists hold 1 and 2 in the same order, and == calls equals, which compares contents.
  2. That would be identity, which Kotlin spells ===. == compares contents.
  3. == is null-safe and calls equals. Nothing here can throw.
  4. Comparing two List<Int> values with == is perfectly legal.

A method sets c.count = 0 on an object it was passed. Does the caller see the change?

The parameter is a copy of the reference, so it points at the caller's object (L4).

  1. Only the reference is copied. Both copies point at the same object, so the change shows.
  2. val/var controls reassigning a variable, not changing the object's fields.
  3. The parameter holds a copy of the caller's reference, so both reach the same heap object.
  4. The field's type doesn't matter. The object itself is shared, whatever its fields hold.
Part 1

Classes and constructors

~28 min

A class is a blueprint. It describes what data each object holds and what it can do. Each object made from it is an instance, living on the heap with its own copy of the fields (L4). A constructor is the special code that runs once, when an instance is created. Its job is to put the new object into a valid starting state.

A few rules from the docs:

  • Constructor parameters marked val or var become properties. Parameters without them are only visible during initialisation.
  • init blocks "run in the order in which they appear in the class body, along with property initializers".
  • Secondary constructors "must delegate to the primary constructor".
  • Kotlin needs no new keyword.

(Kotlin docs: Classes.) In Java, a constructor that starts with this(…) is making "an explicit constructor invocation" of another constructor in the same class (dev.java: Using this with a constructor).

What happens during new

Step through the first object being built. The JVM creates the object with every field set to a default value first. The JLS says each "instance variable… is initialized with a default value when it is created", which is 0 for numbers and null for references (JLS §4.12.5). Then your constructor fills the fields in, using this to refer to the object under construction.

Validate in the constructor

A constructor that checks its inputs means no broken object can ever exist. That's a far stronger guarantee than checking later. Both versions above reject pages <= 0:

Exception in thread "main" java.lang.IllegalArgumentException: pages must be positive
	at Book.<init>(BadBook.kt:3)

<init> in a stack trace is the JVM's internal name for a constructor (L23).

What Kotlin does for you. The Kotlin header class Book(val title: String, val author: String = "Unknown", var pages: Int = 100) declares three fields and a constructor, and writes all three this.x = x assignments. With its defaults, it also stands in for Java's whole family of chained constructors. In Java you type each piece by hand: field declarations, the constructor, the assignments, and one overload per combination of optional arguments.

Hint 1 of 3

Declare val num: Int and val den: Int without values, then assign both inside an init block. Divide each by gcd(numerator, denominator).

Hint 2 of 3

If denominator is negative, flip the sign of both numbers before dividing. Put require(denominator != 0) at the very top of the init: gcd(0, 0) is 0, and dividing by it throws ArithmeticException first.

Hint 3 of 3

For the text constructor, write : this(text.substringBefore('/').trim().toInt(), text.substringAfter('/').trim().toInt()). In Java, a constructor's first statement must be the this(…) call, so parse with a small static helper inside the arguments.

Final answer

Why it works. All the work happens in the primary constructor, so no unsimplified or zero-denominator Fraction can ever exist. The secondary constructor only converts its argument and delegates with this(…), so it gets every check for free. numerator and denominator have no val: they're needed only while the object is being built.

Common mistake. Computing gcd in property initialisers and putting require in an init block below them. Initialisers and init blocks run in the order they're written, so Fraction(0, 0) divides by zero before the check is reached.

In class P(val x: Int), what does the val do?

val in the header declares a read-only property, initialised from the argument (Kotlin docs).

  1. That's a parameter without val. Adding val stores it as a property.
  2. val in the header declares a property with a getter and no setter, set from the argument.
  3. val affects only x. Other var properties could still change.
  4. Constants are const val, fixed at compile time. Here each object gets its own x at runtime.

A primary-constructor parameter without val or var is…

It isn't stored. It can only be used while initialising, in property initialisers and init blocks. BankAccount's openingDeposit in the final uses exactly this.

  1. Only val makes a property. Without it, nothing is stored.
  2. Without val or var, nothing is stored at all, private or otherwise.
  3. Constants need const val. A parameter can get a different value on every call.
  4. It's a plain constructor parameter, in scope only for property initialisers and init blocks.

Java: this(title, author, 100); as the first line of a constructor…

That's an explicit constructor invocation, and it's how Java constructors share code.

  1. this(…) runs the matching constructor of the same class, on the same object.
  2. No new object: this(…) keeps working on the object already being built.
  3. That's super(…). this(…) stays in the same class.
  4. It passes values on to another constructor. The copy constructor is the one taking a Book.

In Kotlin, init blocks run…

Top to bottom, together with the property initialisers, as part of the primary constructor.

  1. The reverse: init blocks are part of the primary constructor, so they run before any secondary constructor's body.
  2. Class loading runs once per class. init runs for every new instance.
  3. Top to bottom, mixed with property initialisers, every time an object is built.
  4. init blocks can read the primary constructor's parameters, so those already exist.

Stretch: which runs first, the init block or the secondary constructor's body? What does this print?

class Box(val size: Int) {
    init {
        print("init$size ")
    }

    constructor() : this(1) {
        print("secondary ")
    }
}

fun main() {
    Box()
    Box(2)
    println("done")
}

Box() delegates with this(1) before its own body runs, so the primary constructor, init block included, goes first. Box(2) calls the primary directly. The docs: delegation "ensures that all primary constructor initialization logic is executed before any secondary constructor logic runs" (Kotlin docs: Classes).

  1. The secondary body can't go first: its this(1) call runs before it, and that runs init.
  2. this(1) runs the primary constructor and its init block, then the secondary body runs.
  3. A secondary constructor never skips init: it must delegate to the primary constructor, which runs it.
  4. The secondary body does run, right after the delegated call returns.
Gotcha: defaults and overloads don't mix well. If a secondary constructor's parameters exactly match a call that the primary constructor could also handle using defaults, Kotlin picks the one that needs fewer default values filled in. In the Kotlin spec's words, "the candidate with the least number of non-specified default parameters is a more specific candidate" (Kotlin spec: overload resolution). 
class Book(val title: String, val author: String = "Unknown", val pages: Int = 100) {
    // A secondary constructor whose parameters exactly match the call below
    constructor(title: String, author: String) : this(title, author, 1)
}

fun main() {
    val b = Book("Emma", "Austen")   // which constructor runs?
    println(b.pages)
}
1
The call silently used the secondary constructor, so pages is 1, not the default 100. The fix is to use default parameters or overloads for a given call shape, never both.
Part 2

Properties vs fields with getters and setters

~33 min

A class's data has rules, which programmers call invariants: a thermostat's target must stay between 5 and 30, and a balance can't go negative. If any code anywhere can write the field directly, nothing enforces those rules. Encapsulation means hiding the field and letting the outside world in only through methods that check the rules.

In Java, that means a private field plus hand-written getter and setter methods, the getX/setX convention. Effective Java Item 16 says it outright: "In public classes, use accessor methods, not public fields" (Bloch).

Kotlin bakes the idea into the language. A property is a field plus a generated getter, and a setter too for var. You can replace either accessor with your own code without changing how callers use it (Kotlin docs: Properties).

The Java version keeps main in a separate top-level class, ThermostatDemo. A class's own code, nested classes included, can always touch its private members, so to see encapsulation enforced, the caller has to live outside the class.

lateinit: "I'll set this before I use it"

Sometimes a non-null property can't be given a value in the constructor, for example when a framework fills it in later (Android and Spring both do this). lateinit var promises to assign it before any read. Break the promise and you get a clear exception, not a silent null. It only works on non-null vars of non-primitive types (Kotlin docs: lateinit).

The same docs page names one more null-safety exception, UninitializedPropertyAccessException, which "typically happens with lateinit properties" (Kotlin docs: Null safety). It's still better than Java's behaviour: Java's field silently starts as null, and the bug surfaces wherever that null is eventually used.

What Kotlin does for you. For every property, Kotlin generates the private field, the getX(), and the setX() for a var, so you write one line. You start with the plain version and add a custom get()/set() later without changing a single caller, because t.target = 19 was already calling a setter. In Java, switching from a public field to getters and setters means rewriting every call site, which is why Java style says to write getters and setters from day one. In L9 you'll see Java call these generated getTarget()/setTarget() methods by name.

Hint 1 of 3

A custom setter goes on the line right under the property: set(value) { field = … }. value.coerceIn(0, capacity) does the clamping. For recharges, one line under the property is enough: private set.

Hint 2 of 3

"A custom setter runs every time you assign a value to the property, except during initialization." So Battery(100, 250) skips your setter: clamp initialLevel in the initialiser too. percent is level * 100 / capacity.

Hint 3 of 3

use is one line, level -= amount, because assigning level inside the class still calls the setter. In Java, the constructor calls setLevel(initialLevel), as Thermostat did, and setRecharges simply doesn't exist.

Final answer

Why it works. Every write to level goes through one setter, even level -= amount inside the class, so the rule lives in exactly one place. percent has no backing field, so it can never go stale. private set keeps the generated getter public and gives Java callers no setRecharges at all.

Common mistake. Writing var level: Int = initialLevel and trusting the setter. The initialiser writes the backing field directly, so Battery(100, 250) starts at 250%, the same trap as Thermostat(99).

The incoming value is value. field is the stored slot. Writing the property's own name inside its setter would call the setter again, forever.

  2. Reading the property by name calls the getter. field goes straight to the storage.
  3. That's this. field is one stored slot, not the object.
  4. The hidden storage behind this one property, usable only inside its accessors.

Only the setter is private. The getter keeps the property's (public) visibility.

  1. The getter stays public, and only the class's own code can call the setter.
  2. private set restricts the setter only. Reading stays public.
  3. Only the setter is restricted. Reading is still allowed everywhere.

A Kotlin property with a custom setter and an initialiser. During construction, the setter…

The initialiser writes the backing field directly, so validate it separately.

  1. The setter doesn't run at all for the initialiser, which writes the field directly.
  2. The initialiser stores straight into the backing field, bypassing the setter's code.
  3. It runs zero times during construction, then once per later assignment.
  4. The setter's validation is skipped, so a bad initial value gets in silently. That's the trap.

One property is stored, one is computed. What does this print?

class Rect(var width: Int, var height: Int) {
    val storedArea = width * height
    val computedArea: Int
        get() = width * height
}

fun main() {
    val r = Rect(2, 3)
    r.width = 10
    println("${r.storedArea} ${r.computedArea}")
}

storedArea has an initialiser, so it's calculated once, during construction, and kept in a backing field. computedArea has a getter and no field, so every read multiplies again, using the new width.

  1. Only storedArea is frozen. computedArea's getter runs on each read and sees width = 10.
  2. An initialiser runs once, at construction, so storedArea doesn't follow later changes to width.

Hint 1 of 3

Start with one word: private in front of val items. Run the checks again. Two still fail, and they're the interesting ones.

Hint 2 of 3

get() = items hands out the very same ArrayList, just typed as List. That's L5's "view": the type hides add, but the object still has it. Return a copy instead.

Hint 3 of 3

get() = items.toList() builds a new list on every read. In Java, make the field private and return List.copyOf(items), which is also unmodifiable. Collections.unmodifiableList(items) isn't enough: it's still a live view, so the snapshot check fails.

Final answer

Why it works. private hides the field, but a getter can still leak the object it points to. Returning items.toList() gives every caller their own list, so the only way to change the playlist is add, which keeps the trim and size rules. This is the defensive copy from L5, applied to a getter.

Common mistake. Keeping get() = items because the type is List. A read-only type isn't an immutable object. A Java caller sees a plain java.util.List and can call add, and every earlier "snapshot" changes as the playlist grows.

Java. takeAll reaches into another account's private field. What happens?

public class Steal {
    public static void main(String[] args) {
        Account a = new Account(100);
        Account b = new Account(50);
        a.takeAll(b);
        System.out.println(a.balance() + " " + b.balance());
    }
}

class Account {
    private int balance;

    Account(int balance) { this.balance = balance; }

    int balance() { return balance; }

    void takeAll(Account other) {
        balance += other.balance;   // another object's private field
        other.balance = 0;
    }
}

private is checked per class, not per object: a private member "can only be accessed in its own class" (dev.java), and takeAll is code in Account. Kotlin's private works the same way. Steal, a different class, has to use balance().

  1. takeAll is code inside Account, so it may read and write any Account's private balance.
  2. The transfer does happen: nothing blocks it, so b's 50 moves to a.
  3. Access is checked per class. other.balance is used inside Account, so it compiles.
  4. Access rules are checked by the compiler, and this code passes them, so nothing fails later.
Part 4

object and companion vs static

~28 min

Some things belong to the class as a whole, not to any one instance: a counter of how many tickets were issued, a maximum price, a factory method that decides how instances get made. Java marks these static. A static field "is associated with the class, rather than with any object… in one fixed location in memory" (dev.java: Class variables).

Kotlin has no static keyword. It uses objects instead:

  • object Name { … } declares a singleton: a class and its only instance in one go. "The initialization of an object declaration is thread-safe and done on first access."
  • companion object { … } inside a class holds the class-level members, called through the class name, as in Ticket.vip(…).

The companion object gathers all class-level members in one clearly marked block, instead of scattering static keywords through the class. One difference to remember: companion members "look like static members… [but] are actually instance members of the companion object" (Kotlin docs). When Java code needs a true static, you add @JvmStatic (L9).
