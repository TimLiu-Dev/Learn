How do you tell, just by reading it, that a piece of code will be fine for 1,000 items and hopeless for 1,000,000? This lesson covers Big O, how to check it with a stopwatch, and the data structure you've used in every lesson so far without ever seeing inside: the growable array behind ArrayList.

Part 1

Reasoning about Big O

~30 min

An AI assistant will happily write code that is correct, readable, passes every test, and falls over the first time real data arrives. The tests used 10 items; production has 10 million. The skill that catches this in a code review is reading a function and asking how does the work grow when the input grows? That's all Big O is.

Count steps, not seconds

Seconds depend on your laptop. Steps depend only on the input size, n. Here are the four loop shapes you'll see most often, each counting its own steps:

       n   O(1) O(log n)       O(n)         O(n^2)
      10      1        3         10            100
     100      1        6        100          10000
    1000      1        9       1000        1000000
   10000      1       13      10000      100000000
  100000      1       16     100000    10000000000
  • O(1), constant: the same work whatever n is. Reading array[i] is the classic case.
  • O(log n), logarithmic: the loop halves what's left each time, so multiplying n by 10 adds only about 3 steps. That's how binary search (L18) finds one item among a billion in about 30 looks.
  • O(n), linear: one pass. Ten times the data, ten times the work.
  • O(n²), quadratic: a loop inside a loop over the same data. Ten times the data, a hundred times the work. At n = 100,000 that's ten billion steps.

What "O(n²)" means, and what it throws away

Sedgewick & Wayne describe running time with tilde approximations, "where we throw away low-order terms that complicate formulas", and call the dominant function the order of growth (Algorithms §1.4). Big O goes one step further and also drops the constant factor. Formally, f(n) is O(g(n)) if there are constants c and n₀ with f(n) ≤ c·g(n) for every n ≥ n₀ (CLRS, ch. 3). In plain words: eventually, f grows no faster than g, up to a constant factor. So:

  • 3n² + 100n + 7 is O(n²). For large n, the n² term swamps the others, and the 3 is a constant factor.
  • Two loops one after the other (n + n = 2n) are still O(n). Only nesting multiplies.
  • Big O is an upper bound on growth, not a stopwatch. An O(n) function with a huge constant can lose to an O(n²) one for small n. That's why Part 2 measures as well.

How long would it take?

A rough rule: a modern machine does somewhere around 10⁸ to 10⁹ simple steps per second. The table assumes 10⁹ and ignores everything else (memory, caches, the JIT), so treat it as an estimate of scale, not a prediction:

nlog nnn log nn²2ⁿ
1,00010 ns1 µs10 µs1 msnever finishes
1,000,00020 ns1 ms20 ms~17 minnever finishes
1,000,000,00030 ns1 s30 s~32 yearsnever finishes

Exponential is in a different league: at 10⁹ steps per second, 2ⁿ takes about 1 second at n = 30, 18 minutes at n = 40, and 36 years at n = 60. The jump from O(n log n) to O(n²) at a million items, 20 ms vs 17 minutes, is the one you'll actually meet at work.

Best, worst and average case

Many functions don't take the same time for every input of size n. A linear search that returns as soon as it finds the target does 1 step if the target is first (best case), n steps if it's last or missing (worst case), and about n/2 on random inputs (average case). When people say "linear search is O(n)" they mean the worst case, because that's the guarantee you can rely on. Sedgewick & Wayne put it as a promise that holds "no matter what the input" (§1.4, Worst-case performance guarantees). There's also a fourth kind, amortised, the average cost per operation over a long sequence of operations. Part 3 is built around it.

Space complexity

The same notation counts memory: how much extra space a function needs as n grows. Summing an array needs O(1) extra space (one accumulator). Copying it, or building a HashSet of its elements, needs O(n). Speed often costs memory, and the next example trades one for the other on purpose.

The hidden loop

Most real O(n²) bugs don't look like two nested fors. One of the loops is hidden inside a library call. This is a very natural way to "remove duplicates, keep the order":

Inside a loop of n, that's O(n²). HashSet "offers constant time performance for the basic operations (add, remove, contains and size)" on average (HashSet), so the fast version is O(n), at the price of O(n) extra memory for seen. What Kotlin does for you.
  • x in list reads beautifully, which is exactly why it's easy to miss that it's a loop. It's the same contains call as Java's; Kotlin only changes the spelling.
  • distinct(), toSet() and toHashSet() are one call each, so the O(n) version is as short to write as the O(n²) one. Java needs a new LinkedHashSet<>(…) copy, or a stream with .distinct().
  • for (i in 0 until n) and indices make the loop bounds explicit, so counting steps is easy. Big O itself is the same in both languages: it's about the algorithm, not the syntax.

for (w in words) if (w !in result) result.add(w), where result is a MutableList.

A linear search finds its target at index 0. Which case is that?

One step: the luckiest possible input. Guarantees are usually quoted for the worst case, a missing target, which takes n steps.

Roughly how long do 10¹² simple steps (O(n²) at n = 10⁶) take at 10⁹ steps per second?

10¹² ÷ 10⁹ = 1,000 seconds, about 17 minutes. The O(n log n) version takes about 20 ms.

Part 2

Measuring it

~25 min

Big O is a hypothesis. A stopwatch tests it. Sedgewick & Wayne frame performance work as the scientific method: observe, hypothesise, predict, verify (§1.4). You'll do exactly that.

The stopwatch

Java's tool is System.nanoTime(). Its docs say it "can only be used to measure elapsed time and is not related to any other notion of system or wall-clock time", and that it "provides nanosecond precision, but not necessarily nanosecond resolution" (System.nanoTime). Take a reading before and after, and subtract. Kotlin wraps that in measureTime { … } from kotlin.time, available since Kotlin 1.9, which returns a typed Duration (API). On the JVM it uses System.nanoTime() underneath (Kotlin docs: Time measurement). The older measureTimeMillis and measureNanoTime from kotlin.system still compile on the JVM without warnings, but return a bare Long, and their docs point you to measureTime.

A doubling experiment

The cleanest test of a Big O hypothesis is to double n and look at the ratio of the times. Sedgewick & Wayne's DoublingRatio.java does this. The maths is one line: if T(n) ≈ a·nᵇ, then T(2n) / T(n) ≈ 2ᵇ. A ratio near 2 means b = 1, linear. Near 4 means quadratic, and near 8 cubic. Rules for honest timing

  1. Warm up before measuring, so the JIT has compiled the code you're timing.
  2. Repeat and report the best or the median, not one lucky or unlucky run. The garbage collector can pause your program at any moment and add noise.
  3. Use the result. If the compiler can prove a result is never used, it may delete the computation entirely. That's what sink is for. JMH's own sample calls dead-code elimination "the downfall of many benchmarks" (JMHSample_08_DeadCode).
  4. Compare ratios, not absolutes, and only on the same machine.
  5. For real measurements, use JMH, the OpenJDK benchmark harness, which handles warm-up, forking and dead code for you. It comes with profiling in L24. A hand-rolled harness like this one is good enough to check a Big O claim, not to settle a 10% argument.

Part 3

Inside a dynamic array

~30 min

A JVM array has a fixed length, set when it's created. Yet you've been calling list.add since L3 without ever saying how big the list would get. A dynamic array (ArrayList, Kotlin's mutableListOf()) fakes growth with three things: a backing array, a size (how many slots are in use), and a rule for what to do when size reaches the capacity (the array's length).

Watch one resize

size=3 capacity=4 [a, b, c, null]
size=3 capacity=4 [a, b, c, null]

Most adds are one write. The add that finds the array full pays for a new array plus copying every element: O(n) for that one add. So is add O(1) or O(n)? Both, depending on how you count.

Amortised O(1): why doubling works

Count the copies over a whole sequence of adds instead of a single one. With doubling from capacity 4, the resizes copy 4, then 8, then 16 elements, and so on. That sum is always less than twice the final size, because each term is bigger than all the earlier ones put together. So n adds cost fewer than n writes plus 2n copies: O(n) in total, which is O(1) amortised per add. Sedgewick & Wayne state it for their resizing-array stack: "any sequence of N operations takes time proportional to N in the worst case (amortized constant time per operation)" (§1.4, Amortized analysis). A useful way to picture it is to charge every add 3 units: 1 pays for its own write, and 2 go into a savings account that pays for copying when the next resize comes. CLRS calls this the accounting method (ch. 16 or 17, depending on edition).

Now the experiment. Simulate n adds under three growth rules and count the copies:

   n adds    x2 copies (per add)  x1.5 copies (per add)   +10 copies (per add)
    1,000            1,020 (1.0)            2,131 (2.1)          49,900 (49.9)
   10,000           16,380 (1.6)           24,278 (2.4)      4,999,000 (499.9)
  100,000          131,068 (1.3)          276,515 (2.8)   499,990,000 (4999.9)
1,000,000        1,048,572 (1.0)        2,099,747 (2.1) 49,999,900,000 (49999.9)
  • ×2: copies per add stay between 1 and 2, whatever n is. Constant: amortised O(1).
  • ×1.5: about twice as many copies, still a constant per add. Any constant growth factor greater than 1 gives amortised O(1). The factor only trades wasted space against copying.
  • +10: copies per add grow with n: 50 per add at a thousand, 50,000 per add at a million. Total work is about n²/20, so O(n²). Growing by a constant amount is the bug. A million adds copy fifty billion elements.

Feel it. Add elements one at a time and watch the cost of each add. Then switch policy:

Shifting is one call, not a hand-written loop. Kotlin's copyInto explicitly allows overlap: "It's allowed to pass the same array in the destination and even specify the subrange so that it overlaps with the destination range" (copyInto). Java's System.arraycopy behaves "as if the components … were first copied to a temporary array" when source and destination are the same array (System.arraycopy). To insert at i, copy [i, size) one slot right, then write the new element at i.

Don't leak removed elements

After removeAt shifts everything left, the last used slot still holds a reference to an element that's no longer in the list. The garbage collector (L4, L24) can't reclaim an object while anything still points at it, so a long-lived list that never clears those slots slowly leaks memory. Effective Java Item 7, "Eliminate obsolete object references", uses exactly this example, a hand-written stack. The fix is one line: write null into the vacated slot. OpenJDK's ArrayList does the same in its remove path, es[size = newSize] = null (OpenJDK source).

The real thing: java.util.ArrayList

  • What's promised: "The size, isEmpty, get, set, … iterator, listIterator, and reversed operations run in constant time. The add, and addLast operations runs in amortized constant time, that is, adding n elements requires O(n) time. All of the other operations run in linear time (roughly speaking)." And: "The details of the growth policy are not specified beyond the fact that adding an element has constant amortized time cost." (ArrayList docs)
  • What OpenJDK actually does (an implementation detail, not a guarantee): an empty ArrayList() allocates its first array of DEFAULT_CAPACITY = 10 lazily, on the first add, and then grows by half: oldCapacity >> 1 as the "preferred growth", so ×1.5 (ArrayList.grow). Your ×2 version is equally valid. Both are constant factors.
  • Knobs: if you know you'll add a million items, ArrayList(1_000_000) or ensureCapacity skips every resize. trimToSize() shrinks the backing array to the current size when you're done growing.

  • operator fun get / set let your own class use list[i] and list[i] = x syntax, the same as built-in lists. Java callers write get(i) / set(i, x).
  • var size = 0; private set gives a public read-only property in two lines. Java needs a private field plus a size() method.
  • data.copyOf(n) and copyInto are methods on arrays. Java spells the same operations Arrays.copyOf and System.arraycopy(src, srcPos, dest, destPos, length), five positional ints that are easy to mix up.
  • index !in 0 until size reads like the bounds check it is. Java's nearest equivalent is Objects.checkIndex(index, size), which throws IndexOutOfBoundsException with a ready-made message (API).
  • joinToString(", ", "[", "]") writes toString in one line once your class is Iterable. Java uses a StringJoiner and a loop.

Check

list.add(0, x) on a dynamic array holding n elements, with spare capacity.

All n elements shift one slot right. Only adding at the end is cheap.

Capacity starts at 4 and doubles. How many element copies do the first 17 adds cause in total?

Resizes happen at adds #5, #9 and #17, copying 4 + 8 + 16 = 28 elements. That's under 2 per add, as the argument promised.

Inside class MyList<T>, Kotlin code says val data = arrayOfNulls<T>(4).

cannot use 'T' as reified type parameter. arrayOfNulls needs a reified type, and a class's T is erased. Use arrayOfNulls<Any?>(4) and cast on the way out.

Why does removeAt finish with data[--size] = null?

The vacated slot still points at the removed object, which keeps it alive. Effective Java Item 7: eliminate obsolete object references.

A dynamic array that grows by +10 slots each time. Total cost of n adds:

A resize every 10 adds, each copying everything so far: about n²/20 copies. CopyCount showed 50 billion for a million adds.

Reference race, and what the numbers mean 
1000000 adds, best of 3, on my machine:
java.util.ArrayList  size 1,000,000        4.9 ms

1000000 adds, best of 3, on my machine:
java.util.ArrayList  size 1,000,000        4.9 ms
MyArrayList (x2)     size 1,000,000        2.5 ms
PlusTenList (+10)    size 1,000,000     4240.6 ms
  • +10 is about 1,700 times slower than doubling at a million items, and the gap grows with n. That's O(n²) vs amortised O(1) per add, measured.
  • Yours beat ArrayList? Don't celebrate yet. Both are a few milliseconds and both are linear. The JDK class does more work per add: it grows by ×1.5, so roughly twice as many copies (see CopyCount), and it maintains a modCount so its iterators can detect modification during iteration (AbstractList.modCount). A hand-rolled harness can't separate those effects from noise, and JMH (L24) can. In real code, use ArrayList. It's tested by millions of programs, and yours by twelve tests.
  • Gradle runs these on the project's JDK 21 toolchain (L11), not the JDK 26 you use for single files. The ratios come out the same.
Wrap-up

Exit quiz, recall card, sources

~5 min

TDD: you've just written a test and watched it fail. What's the next step? (L11)

Red, green, refactor: make it pass with the simplest code that works, and only then tidy up with the tests as a safety net.

MyArrayList<Int>(0) hits require(initialCapacity >= 1). What is thrown? (L10)

require is for bad arguments, so IllegalArgumentException. check is for bad state, so IllegalStateException.

val xs = MyArrayList<Int>(), then xs.add(7) and println(xs[0]). (L5)

val fixes the reference, not the object it points at. Adding to the list mutates the object; xs still points at the same one.

What does implementing Iterable<T> give MyArrayList? (L8)

An interface is a contract. Iterable's single method, iterator(), is what for loops call. In Kotlin it also unlocks joinToString, map, filter and the rest of L14's extension functions.
