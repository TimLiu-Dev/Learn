(1..5).toList().map { it * 10 }.take(2). How many times does the map lambda run? (L15)

A List is eager: map runs over all 5 elements and builds a new list before take starts. Counting work like this is exactly what Big O formalises today.

  1. That's what a lazy Sequence would do. A List's map is eager and finishes before take starts.
  2. List.map transforms all 5 elements into a new list, and only then does take(2) keep two of them.
  3. take never calls the lambda. It copies two finished results, so nothing adds 5 + 2.
  4. On a List, nothing is deferred: map runs right away, over every element.

listOf(3, 4).fold(1) { acc, n -> acc * n } (L14)

Start at 1, then 1 × 3 × 4 = 12.

  1. That's 3 + 4: it ignores the start value and adds instead of multiplying.
  2. That's 1 + 3 + 4. The lambda multiplies the accumulator by each element.
  3. The accumulator starts at 1, becomes 1 × 3 = 3, then 3 × 4 = 12.
  4. 1 is only the starting value. fold applies the lambda once per element after that.

Part 1

Reasoning about Big O

~38 min

An AI assistant will happily write code that is correct, readable, passes every test, and falls over the first time real data arrives. The tests used 10 items; production has 10 million. The skill that catches this in a code review is reading a function and asking how does the work grow when the input grows? That's all Big O is.

Count steps, not seconds

Seconds depend on your laptop. Steps depend only on the input size, n. Here are the four loop shapes you'll see most often, each counting its own steps:

       n   O(1) O(log n)       O(n)         O(n^2)
      10      1        3         10            100
     100      1        6        100          10000
    1000      1        9       1000        1000000
   10000      1       13      10000      100000000
  100000      1       16     100000    10000000000
  • O(1), constant: the same work whatever n is. Reading array[i] is the classic case.
  • O(log n), logarithmic: the loop halves what's left each time, so multiplying n by 10 adds only about 3 steps. That's how binary search (L18) finds one item among a billion in about 30 looks.
  • O(n), linear: one pass. Ten times the data, ten times the work.
  • O(n²), quadratic: a loop inside a loop over the same data. Ten times the data, a hundred times the work. At n = 100,000 that's ten billion steps.

What "O(n²)" means, and what it throws away

Sedgewick & Wayne describe running time with tilde approximations, "where we throw away low-order terms that complicate formulas", and call the dominant function the order of growth (Algorithms §1.4). Big O goes one step further and also drops the constant factor. Formally, f(n) is O(g(n)) if there are constants c and n₀ with f(n) ≤ c·g(n) for every n ≥ n₀ (CLRS, ch. 3). In plain words: eventually, f grows no faster than g, up to a constant factor. So:

  • 3n² + 100n + 7 is O(n²). For large n, the n² term swamps the others, and the 3 is a constant factor.
  • Two loops one after the other (n + n = 2n) are still O(n). Only nesting multiplies.
  • Big O is an upper bound on growth, not a stopwatch. An O(n) function with a huge constant can lose to an O(n²) one for small n. That's why Part 2 measures as well.

Best, worst and average case

Many functions don't take the same time for every input of size n. A linear search that returns as soon as it finds the target does 1 step if the target is first (best case), n steps if it's last or missing (worst case), and about n/2 on random inputs (average case). When people say "linear search is O(n)" they mean the worst case, because that's the guarantee you can rely on. Sedgewick & Wayne put it as a promise that holds "no matter what the input" (§1.4, Worst-case performance guarantees). There's also a fourth kind, amortised, the average cost per operation over a long sequence of operations. Part 3 is built around it.

Space complexity

The same notation counts memory: how much extra space a function needs as n grows. Summing an array needs O(1) extra space (one accumulator). Copying it, or building a HashSet of its elements, needs O(n). Speed often costs memory, and the next example trades one for the other on purpose.

Most real O(n²) bugs don't look like two nested fors. One of the loops is hidden inside a library call. This is a very natural way to "remove duplicates, keep the order":

Practice · Find the pair in one pass

hasPairSum answers correctly, but it checks every pair: O(n²). Make it O(n), with one pass and a HashSet.

  • Two different positions must add up to target: [5] with target 10 is false, and [5, 1, 5] is true.
  • The checks don't time anything. They pass in a list that counts how often its elements are read, and allow a few reads per element, not one per pair.
// Correct, but O(n²): every pair (i, j) gets checked.
fun hasPairSum(xs: List<Int>, target: Int): Boolean {
    for (i in xs.indices)
        for (j in i + 1 until xs.size)
            if (xs[i] + xs[j] == target) return true
    return false
}

Hint 1 of 3

Walk the list once. When you reach x, the partner it needs is target - x. Has that partner already gone by?

Hint 2 of 3

Keep a HashSet<Int> of the elements you've passed. For each x: if target - x is in the set, return true; otherwise add x and move on. A set lookup is O(1) on average, so the loop is O(n).

Hint 3 of 3

Order matters: check before you add. If you put every element in the set first, [5] with target 10 finds its own 5 and wrongly returns true. In Java, use Set<Integer> seen = new HashSet<>() and seen.contains(target - x).

Final answer

Why it works. When the loop reaches x, the set holds exactly the elements before it, so a hit means two different positions add up to target. Every pair is still covered: the later element of the pair finds the earlier one. That's n set operations at O(1) on average, so O(n) time for O(n) extra memory, the same trade as uniqueFast.

Common mistake. Building the whole set first with xs.toHashSet(), then checking target - it in all. It's still O(n), but each element can find itself, so [5] with target 10 says true.

A linear search finds its target at index 0. Which case is that?

One step: the luckiest possible input. Guarantees are usually quoted for the worst case, a missing target, which takes n steps.

  1. The worst case is a target that's last or missing: n steps, not 1.
  2. The average over random positions is about n/2 steps, not one specific input.
  3. Amortised averages over a sequence of operations, like many adds. This is one search.
  4. Index 0 is the luckiest input: the search stops after one comparison.

Measuring it

~33 min

Big O is a hypothesis. A stopwatch tests it. Sedgewick & Wayne frame performance work as the scientific method: observe, hypothesise, predict, verify (§1.4). You'll do exactly that.

The stopwatch

Java's tool is System.nanoTime(). Its docs say it "can only be used to measure elapsed time and is not related to any other notion of system or wall-clock time", and that it "provides nanosecond precision, but not necessarily nanosecond resolution" (System.nanoTime). Take a reading before and after, and subtract. Kotlin wraps that in measureTime { … } from kotlin.time, available since Kotlin 1.9, which returns a typed Duration (API). On the JVM it uses System.nanoTime() underneath (Kotlin docs: Time measurement). The older measureTimeMillis and measureNanoTime from kotlin.system still compile on the JVM without warnings, but return a bare Long, and their docs point you to measureTime.

A doubling experiment

The cleanest test of a Big O hypothesis is to double n and look at the ratio of the times. Sedgewick & Wayne's DoublingRatio.java does this. Rules for honest timing

  1. Warm up before measuring, so the JIT has compiled the code you're timing.
  2. Repeat and report the best or the median, not one lucky or unlucky run. The garbage collector can pause your program at any moment and add noise.
  3. Use the result. If the compiler can prove a result is never used, it may delete the computation entirely. That's what sink is for. JMH's own sample calls dead-code elimination "the downfall of many benchmarks" (JMHSample_08_DeadCode).
  4. Compare ratios, not absolutes, and only on the same machine.
  5. For real measurements, use JMH, the OpenJDK benchmark harness, which handles warm-up, forking and dead code for you. It comes with profiling in L24. A hand-rolled harness like this one is good enough to check a Big O claim, not to settle a 10% argument.

Inside a dynamic array

A JVM array has a fixed length, set when it's created. Yet you've been calling list.add since L3 without ever saying how big the list would get. A dynamic array (ArrayList, Kotlin's mutableListOf()) fakes growth with three things: a backing array, a size (how many slots are in use), and a rule for what to do when size reaches the capacity (the array's length).

Most adds are one write. The add that finds the array full pays for a new array plus copying every element: O(n) for that one add. So is add O(1) or O(n)? Both, depending on how you count.

Amortised O(1): why doubling works

Count the copies over a whole sequence of adds instead of a single one. With doubling from capacity 4, the resizes copy 4, then 8, then 16 elements, and so on. That sum is always less than twice the final size, because each term is bigger than all the earlier ones put together. So n adds cost fewer than n writes plus 2n copies: O(n) in total, which is O(1) amortised per add. Sedgewick & Wayne state it for their resizing-array stack: "any sequence of N operations takes time proportional to N in the worst case (amortized constant time per operation)" (§1.4, Amortized analysis). A useful way to picture it is to charge every add 3 units: 1 pays for its own write, and 2 go into a savings account that pays for copying when the next resize comes. CLRS calls this the accounting method (ch. 16 or 17, depending on edition).

            s.pop();
            return List.of(full, atThree, s.capacity());
        });
        check("elements survive a shrink", List.of(8, 4, 3, 2, 1), () -> {
            ResizingStack<Integer> s = stackOf(16);
            for (int i = 0; i < 12; i++) s.pop();
            return List.of(s.capacity(), s.pop(), s.pop(), s.pop(), s.pop());
        });
        check("push and pop at a boundary don't thrash", true, () -> {
            ResizingStack<Integer> s = stackOf(8);
            long before = s.copies;
            for (int i = 0; i < 1_000; i++) { s.push(0); s.pop(); }
            return s.copies - before < 100;
        });
        check("a long run copies fewer than 3 elements per operation", true, () -> {
            ResizingStack<Integer> s = stackOf(10_000);
            for (int i = 0; i < 10_000; i++) s.pop();
            return s.copies < 3 * 20_000;
        });
    }

    interface Check { Object get() throws Exception; }

    static void check(String name, Object expected, Check actual) {
        try {
            Object got = actual.get();
            System.out.println(Objects.equals(expected, got) ? "PASS " + name : "FAIL " + name + ": expected <" + expected + "> but was <" + got + ">");
        } catch (Exception e) {
            System.out.println("FAIL " + name + ": threw " + e);
        }
    }
    // END CHECKS
}
Hint 1 of 3

Popping is the reverse of push: decrement size, then read data[size]. It's stored as Any?, so cast it with as T, as GrowList.get did.

Hint 2 of 3

After reading the element, write null into its slot. Then: if size > 0 && size == data.size / 4, call resize(data.size / 2). Throw NoSuchElementException first if size == 0.

Hint 3 of 3

Why a quarter, not a half? Right after the halving, the array is half full, so it can take many pushes before it grows again. Shrink at half full and one push/pop pair at the boundary copies everything twice. In Java, the array is an Object[] and the cast is (T) data[size] with @SuppressWarnings("unchecked").

Final answer

Why it works. Growing at full and shrinking at a quarter leaves a gap: after either resize, the array is exactly half full. The next resize needs at least a quarter of the capacity in pushes or pops, and those operations pay for its copies, so every operation is amortised O(1). This is Sedgewick & Wayne's ResizingArrayStack (§1.3).

Common mistake. Halving at half full. A full array of 8 grows to 16 on a push, then halves back to 8 on the pop, and every pair after that copies 16 elements. The boundary check counts about 16,000 copies, against 8 for the quarter rule.

Why does removeAt finish with data[--size] = null?

The vacated slot still points at the removed object, which keeps it alive. Effective Java Item 7: eliminate obsolete object references.

  1. get already rejects any index ≥ size with its bounds check. The null isn't what stops it.
  2. Without the null, the array still references the removed object, so the GC can't free it.
  3. A dynamic array isn't sorted. Removal keeps the existing order with or without the null.
  4. Writing null changes one slot. The array's length stays the same until a resize.

A dynamic array that grows by +10 slots each time. Total cost of n adds:

A resize every 10 adds, each copying everything so far: about n²/20 copies. CopyCount showed 50 billion for a million adds.

  1. That needs a constant growth factor, like ×2. +10 resizes n/10 times, each copying up to n.
  2. n adds need at least n writes, so the total can't be below O(n).
  3. The copies sum to about n²/20, which grows faster than n log n.
  4. n/10 resizes copy 10, 20, 30, … elements: about n²/20 in total.

Java: OpenJDK's growth rule, simulated for 40 adds. What does this print?

public class Growth {
    public static void main(String[] args) {
        int capacity = 10, size = 0;                    // OpenJDK's first capacity
        StringBuilder log = new StringBuilder("" + capacity);
        for (int i = 0; i < 40; i++) {                  // 40 adds
            if (size == capacity) {
                capacity = capacity + (capacity >> 1);  // OpenJDK's "preferred growth"
                log.append(" ").append(capacity);
            }
            size++;
        }
        System.out.println(log);
    }
}

capacity >> 1 is half the capacity, rounded down, so 10 → 15 → 22 → 33. At add #34 the array of 33 is full again, and it grows to 49. ×1.5 is a constant factor, so adds stay amortised O(1).

  1. Each resize adds half the capacity, rounded down: 15 + 7 = 22, and 33 + 16 = 49.
  2. That's doubling. OpenJDK adds capacity >> 1, half the old capacity, so it grows ×1.5.
  3. >> 1 rounds down: 15 >> 1 is 7, so 15 becomes 22, not 23.
  4. That's a fixed +5. The shift uses the current capacity, so each step is bigger than the last.

Kotlin: a reference saved before a resize. What does this print?

fun main() {
    var data: Array<Int?> = arrayOf(1, 2)
    val old = data
    data = data.copyOf(4)          // "grow" to capacity 4
    data[0] = 99
    println("${old[0]} ${old.size} ${data.size}")
}

copyOf allocates a new array of 4 and copies into it, and data is re-pointed at it. old still points at the original 2-slot array, which nothing changed. Growing is always "allocate, copy, re-point", never "stretch in place".

  1. copyOf makes a separate array, so writing data[0] doesn't touch the one old points at.
  2. Arrays never grow in place. old still sees the original two-element array.
  3. old[0] is right, but old's array keeps length 2. Only the new array has 4 slots.
  4. old keeps the original array, untouched, and data points at the new 4-slot copy.

Exit quiz, recall card, sources

~5 min

TDD: you've just written a test and watched it fail. What's the next step? (L11)

Red, green, refactor: make it pass with the simplest code that works, and only then tidy up with the tests as a safety net.

  1. Refactoring comes after green: tidy up only once the tests pass and can protect you.
  2. A second failing test gives you two reasons to be red. Make this one pass first.
  3. Red, then green: write the simplest code that makes the failing test pass.
  4. Failing is the point of red: it proves the test can catch the missing behaviour.

MyArrayList<Int>(0) hits require(initialCapacity >= 1). What is thrown? (L10)

require is for bad arguments, so IllegalArgumentException. check is for bad state, so IllegalStateException.

  1. IllegalStateException comes from check, for bad object state, not bad arguments.
  2. require checks arguments and throws IllegalArgumentException when its condition is false.
  3. That's for bad indexes in get or set, not for constructor arguments.
  4. Nothing is null here. require fails on the value 0, not on a missing reference.

val xs = MyArrayList<Int>(), then xs.add(7) and println(xs[0]). (L5)

val fixes the reference, not the object it points at. Adding to the list mutates the object; xs still points at the same one.

  1. val stops xs being reassigned, not the object being changed, so add works.
  2. Only xs = … would fail to compile. Calling methods that mutate the object is fine.
  3. After one add, index 0 exists, so xs[0] is within bounds.
  4. Slot 0 holds 7, written by add. Only unused slots hold null.

What does implementing Iterable<T> give MyArrayList? (L8)

An interface is a contract. Iterable's single method, iterator(), is what for loops call. In Kotlin it also unlocks joinToString, map, filter and the rest of L14's extension functions.

  1. It's still not a List: List extends Iterable and adds size, get and more.
  2. Implementing an interface adds no speed. get is already O(1) on the backing array.
  3. equals still compares identity unless you override it. Iterable doesn't declare it.
  4. A for loop calls iterator(), which is exactly what Iterable promises.
