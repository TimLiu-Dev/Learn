  2. What does SQLite write before it changes a page of the database file, and why? (L36)

Before SQLite changes a database page in its default mode, its rollback journal saves… (L36)

"Prior to making any changes to the database file, SQLite first creates a separate rollback journal file and writes into the rollback journal the original content of the database pages that are to be altered" (SQLite: Atomic Commit). After a crash, the old pages go back. Part 2 builds the same idea, all-or-nothing records, into a log.

Why do databases default to B-tree indexes rather than hash tables? (L35)

A hash sends neighbouring keys to unrelated buckets, so "everything between A and B" means checking every key. A B-tree keeps keys sorted and chains its leaves. Part 1's store has exactly this weakness, and Part 3 fixes it by sorting.

A JVM receives kill -9. Its shutdown hooks… (L53)

SIGKILL can't be caught: the kernel ends the process with no warning, so nothing in the JVM runs and the exit code is 128 + 9 = 137. Whatever a storage engine hasn't handed to the operating system by then is gone. Part 2 measures exactly how much.

Two independent checks each wrongly answer "yes" with probability 0.1. The chance that both do is… (L48)

Independent events multiply: 0.1 × 0.1 = 0.01. A Bloom filter (Part 3) is built on this: it checks k bits per key, and a false "yes" needs all k of them to be set by chance.

Part 1

A log with a hash index

~25 min

Here is a complete database, in the shell from L53. Writing appends a line; reading takes the last line for the key, because later lines overrule earlier ones:

$ echo 'dune,Herbert' >> db.txt
$ echo 'emma,Austen' >> db.txt
$ echo 'dune,Frank Herbert' >> db.txt
$ grep '^dune,' db.txt | tail -n 1
dune,Frank Herbert
$ cat db.txt
dune,Herbert
emma,Austen
dune,Frank Herbert

Writes are as fast as a file can grow: nothing is ever looked up or rewritten, just appended. But grep reads the whole file on every lookup, which is O(n) in the number of writes ever made (L16), and the file grows forever, because an overwrite leaves the old line behind. Every storage engine in this lesson is an answer to those two problems that keeps the fast append.

Bitcask: keep the log, add an index

The first answer is to keep a hash map in memory from each key to where its latest value sits in the file. That's the design of Bitcask, the storage engine Basho wrote for the Riak database. Its paper is six readable pages (Sheehy & Smith, "Bitcask: A Log-Structured Hash Table for Fast Key/Value Data", 2010):

  • Writes append. "The active file is only written by appending, which means that sequential writes do not require disk seeking." A delete "is simply a write of a special tombstone value, which will be removed on the next merge."
  • An index in memory. "After the append completes, an in-memory structure called a "keydir" is updated. A keydir is simply a hash table that maps every key in a Bitcask to a fixed-size structure giving the file, offset, and size of the most recently written entry for that key."
  • Reads seek once. Reading "doesn't ever require more than a single disk seek. We look up the key in our keydir, and from there we read the data."
  • Merging removes garbage. "The merge process iterates over all non-active (i.e. immutable) files in a Bitcask and produces as output a set of data files containing only the "live" or latest versions of each present key."

The paper's figure shows each entry as crc · tstamp · ksz · value_sz · key · value: a checksum, a timestamp, the two lengths, then the bytes. Ours drops the timestamp:

offset  0     4         8         12        12+keyLen
        [crc ][keyLen  ][valLen  ][key bytes][value bytes]
        CRC-32 of everything after it         valLen = -1 means "deleted" (a tombstone)

Fixed-size lengths in front let a reader find where each record ends without any separators, so keys and values can contain any bytes at all. The checksum is for Part 2. java.util.zip.CRC32 is in the JDK: "A class that can be used to compute the CRC-32 of a data stream" (CRC32).

  • Positional I/O. ch.write(buf, pos) and ch.read(buf, pos) take an explicit file position, so reads anywhere in the file never disturb where the next append goes. One FileChannel does both. The loops around write exist because a single call may write fewer bytes than asked.
  • ByteBuffer packs ints and bytes into one array. Its integers are big-endian unless you change it: "The initial order of a byte buffer is always BIG_ENDIAN" (ByteBuffer). L30's length prefixes were big-endian too.
  • Recovery is a scan. Opening the file reads every record from the start and replays it into the index. Bitcask calls this out as a cost, and its fix is the hint file: "like the data files but instead of the values they contain the position and size of the values," so startup reads less.

Step through it. Each box is a record in the file, with its offset and size. Struck-through records are garbage, and ✝ marks a tombstone. The orange outline is the record the operation touched.

Compaction is crash-safe because of the rename. It writes the live records to a new file, forces them to disk, and only then renames the new file over the old one. If the process dies before the rename, the old file is untouched and the half-written new one is just a stray file to delete next time. If it dies after, the new file is complete. There's no moment when the store is half old and half new. ATOMIC_MOVE asks for exactly that: "The move is performed as an atomic file system operation", and if it can't be, "then AtomicMoveNotSupportedException is thrown" (Files.move). The same docs warn that if the target exists, "it is implementation specific if the existing file is replaced". On macOS and Linux the JDK implements it with the rename system call (UnixFileSystem.java, an implementation detail), and macOS's man page promises: "If new exists, it is first removed" and "The rename() system call guarantees that an instance of new will always exist, even if the system should crash in the middle of the operation" (rename(2)).

The price of the hash index. Bitcask's authors are upfront about it: "the keydir structure grows by a small amount with the number of keys and must fit entirely in RAM". Every key must fit in memory, and a hash map can't answer "every key between m and p" without visiting them all. Part 3 removes both limits by keeping the data sorted.

Exercise: compaction that runs itself

From a blank file, in both languages. Wrap LogKV in an AutoKV that compacts automatically after a write once garbage is more than half the file, but never while the file is under 64 KB (compacting a tiny file is pure overhead). Run the same 100,000 writes over 1,000 keys and print how many compactions ran and the largest the file ever got. Then answer: why a ratio rather than "every 10,000 writes"?

Solution 
compactions 77, largest file 64 KB, now 47 KB, get(key7) = value-99007

Java prints the same line. The file never passed 64 KB, against 2.8 MB without compaction. Why a ratio: it bounds the space directly. Garbage can never be more than about the live data again, however the writes are spread. It also keeps the cost fair: each compaction copies the live data, and it only runs after at least that much garbage has been written, so the copying amortises to a constant per write. That's L16's doubling-array argument again. A fixed count would compact too often for a small store and not often enough for a busy one.

Check

Nothing is ever changed in place. A new record is appended and the index moves to it; the old one stays until compaction copies only live records. The widget's third step shows it.

One hash lookup in memory (L19) gives the offset, then one read at that offset. Bitcask: reading "doesn't ever require more than a single disk seek". The shell version's grep was O(n).

Why is a delete written as a tombstone instead of just removing the key from the index?

The index lives in memory and is rebuilt by replaying the file. Without a tombstone on disk, the replay would find the old value and bring it back.

The old file isn't touched until the atomic rename, so it's complete. The final exercise also deletes the leftover .compact file on startup.

Part 2

What survives which crash

~25 min

"The write returned" doesn't mean "the write is safe". A byte you write passes through several places, and each kind of crash wipes out different ones:

Where the bytes areProcess crash
(kill -9, exception)		OS crash or
power loss		How they get to the next layer
Your JVM's bufferlostlostflush(), or a direct write
The OS page cachesurvivelostfsync / FileChannel.force
The drive's own cachesurvivemay be losta drive flush (F_FULLFSYNC on macOS)
Stable storagesurvivesurvive—

The page cache belongs to the kernel, not to your process (L22), which is why it outlives a kill -9. Let's prove the top two rows. The program starts a copy of itself as a child process. The child writes 20,000 records, prints acked 20000, and goes to sleep. The parent kills it the moment it reads that line, then counts what's in the file:

$ java -cp killdemo.jar KillDemoKt parent
buffered child said "acked 20000", exit 137 | file 556,185 bytes, torn tail 0 bytes | recovered 19,945 of 20,000
direct   child said "acked 20000", exit 137 | file 557,780 bytes, torn tail 0 bytes | recovered 20,000 of 20,000

Java (java KillDemo.java parent) prints identical numbers. validPrefix comes from today's second exercise; it measures how many bytes at the start of the file are whole, valid records.

  • Buffered: 55 acknowledged writes vanished. The child's write calls returned, so it said "acked", but the last 1,595 bytes were still in the BufferedOutputStream's 8 KB array inside the JVM. SIGKILL gave nothing a chance to flush (L53: exit 137, 128 + 9).
  • Direct: every acknowledged write survived, with no fsync at all. Each LogKV.put is a write system call, which hands the bytes to the kernel's page cache before it returns. A dead process can't take them back.
  • No torn record, even in buffered mode. That's an implementation detail. When a write doesn't fit in the buffer, JDK 26's BufferedOutputStream flushes the buffer first and then copies the whole write: if (len > buf.length - count) { flushBuffer(); } (BufferedOutputStream.java). So records never straddle a flush. Nothing promises that, and an OS crash or power cut can tear a record anyway, which is next.

Torn writes and garbage tails

If the power goes off in the middle of a write, the end of the file can hold part of a record, or worse. SQLite's designers assume the worst: "SQLite assumes that when a file grows in length that the new file space originally contains garbage and then later is filled in with the data actually written. In other words, SQLite assumes that the file size is updated before the file content" (SQLite: Atomic Commit). The lengths and the CRC are how LogKV notices. Simulate every kind of damage on a file of three 16-byte records:

length 32..47 -> [k1, k2]
length 48..48 -> [k1, k2, k3]
full + 16 junk bytes -> [k1, k2, k3]
bit flip in record 2 -> [k1]
wrote k4, get(k4) = v4
reopen: keys = [k1, k2], get(k4) = null

Both languages print the same thing (their Random(56) junk bytes differ, with the same outcome).

  1. A cut anywhere inside the last record (lengths 32 to 47) loses exactly that record. The length check stops at a record that runs past the end of the file.
  2. Random garbage after the records is rejected. The junk bytes parse as some header, but the CRC of what follows doesn't match. A random match would be a 1 in 232 chance (L48).
  3. One flipped bit fails record 2's CRC. LogKV stops scanning there, so record 3 is lost too, even though it's intact. For a crash at the end of a log, stopping is right. Corruption in the middle is a different failure (a bad disk, not a crash), and real systems report it rather than silently dropping data.
  4. The bug. After reopening the torn file, put("k4") works and get returns it. But the record was appended at offset 40, after the 8 torn bytes. On the next open the scan stops at the torn bytes and never reaches it. An acknowledged write is gone. The exercise fixes it.

SQLite's own write-ahead log uses the same defence: "Checksums and counters attached to each frame are used to determine which frames within the WAL are valid and which are leftovers from prior checkpoints" (SQLite file format, §4).

What a durable write costs

To survive power loss, the bytes have to leave the page cache. FileChannel.force is how: "If this channel's file resides on a local storage device then when this method returns it is guaranteed that all changes made to the file since this channel was created, or since this method was last invoked, will have been written to that device. This is useful for ensuring that critical information is not lost in the event of a system crash" (FileChannel.force). Bitcask offers it as a "sync on put" option, for a writer that "would prefer to sync the write file after every write operation". What does that cost?

sync every put    3556.0 µs per put         281 puts/s
sync every 10      386.7 µs per put       2,586 puts/s
sync every 100      42.6 µs per put      23,476 puts/s
never sync           1.6 µs per put     617,474 puts/s
sync every put    3534.3 µs per put         282 puts/s
sync every 10      379.7 µs per put       2,633 puts/s
sync every 100      39.8 µs per put      25,116 puts/s
never sync           2.0 µs per put     490,140 puts/s

Kotlin on the left, Java on the right. A forced write costs about 3.5 ms, roughly 2,000 times a write that stops in the page cache. That's the latency ladder from L22: memory is nanoseconds, a real trip to the drive is milliseconds. The middle rows show the standard escape, group commit. Write several records, force once, and only then acknowledge all of them. Ten writes per force cost a tenth as much each. The trade-off is that nothing is acknowledged until the batch's force returns, so each caller waits a little longer while the system as a whole does far more.

Databases expose exactly this dial. SQLite's PRAGMA synchronous: "When synchronous is FULL (2), the SQLite database engine will use the xSync method of the VFS to ensure that all content is safely written to the disk surface prior to continuing" (SQLite pragmas). And L36's batching measurement, where 10,000 inserts ran far faster inside one transaction than as 10,000 auto-commits, was group commit: one forced journal write instead of ten thousand.

Two kinds of sync on macOS Optional deep dive

Apple's fsync man page has an unusual warning: "while fsync() will flush all data from the host to the drive (i.e. the "permanent storage device"), the drive itself may not physically write the data to the platters for quite some time and it may be written in an out-of-order sequence." It goes on: "This is not a theoretical edge case. This scenario is easily reproduced with real world workloads and drive power failures," and the fix is that "Mac OS X provides the F_FULLFSYNC fcntl. The F_FULLFSYNC fcntl asks the drive to flush all buffered data to permanent storage" (fsync(2)).

The JDK has both. On macOS, FileChannel.force calls fcntl(fd, F_FULLFSYNC) (FileDispatcherImpl.c), while the older FileDescriptor.sync() is a plain fsync (#define IO_Sync fsync in io_util_md.h). Both are implementation details, not guarantees. Measuring them:

FileDescriptor.sync()     22.0 µs per write
FileChannel.force()     3757.5 µs per write
FileDescriptor.sync()     35.6 µs per write
FileChannel.force()     3600.4 µs per write

A plain fsync on this Mac is 100 to 170 times cheaper, because it doesn't wait for the drive. It survives a kernel crash but, per Apple, not necessarily a power cut. SQLite makes the same choice by default: its fullfsync flag "determines whether or not the F_FULLFSYNC syncing method is used on systems that support it. The default value of the fullfsync flag is off" (SQLite pragmas). "Durable" always means "durable against which failure?"

  • if (args.firstOrNull() == "child") return child(…) returns Unit from main in one line, without crashing on empty args.
  • full.copyOf(40), full + junk and .also { it[29] = … } are standard-library array helpers; Java writes Arrays.copyOf and System.arraycopy.

Check

A program calls FileChannel.write (no force), then gets kill -9. The bytes it wrote…

They're in the kernel's page cache, which doesn't belong to the process. KillDemo's direct mode recovered 20,000 of 20,000. A power cut is a different story.

Why must recovery truncate a torn tail instead of just stopping the scan there?

New records go at the end of the file. With the garbage still there, the next scan stops at it and never reaches them: TornDemo step 4 lost k4 that way.

One forced write costs 3.5 ms. Roughly how many writes per second does "force after every write" allow?

1 s ÷ 3.5 ms ≈ 285, and the measurement said 281. That ceiling is why databases batch commits: 100 writes per force reached about 23,000 per second.

With group commit, when may the store tell a caller "your write is durable"?

The acknowledgement has to wait for the force that covers the record; otherwise it's the buffered child's promise again. Batching delays each caller slightly and multiplies throughput.

Part 3

LSM-trees, Bloom filters and B-trees

~25 min

Bitcask's two limits, every key in memory and no ranges, both come from the hash index. Keep the data sorted and they go away, without giving up sequential writes. The trick is to sort in memory and write sorted files in one go:

  • Memtable. Writes go into a sorted map in memory. RocksDB: "new writes are inserted into the memtable and are optionally written to the logfile (aka. Write Ahead Log(WAL))" and "The default implementation of the memtable for RocksDB is a skiplist" (RocksDB Overview). A skip list is a sorted map like L20's trees; the JDK has one, ConcurrentSkipListMap, "providing expected average log(n) time cost for the containsKey, get, put and remove operations" (ConcurrentSkipListMap). Ours is a TreeMap.
  • SSTable. When the memtable fills, it's written out in key order as an immutable sorted string table: "When the memtable fills up, it is flushed to a sstfile on storage and the corresponding logfile can be safely deleted. The data in an sstfile is sorted to facilitate easy lookup of keys."
  • Tombstones and merging. LevelDB's design notes: each entry "is either a value for the key, or a deletion marker for the key. (Deletion markers are kept around to hide obsolete values present in older sorted tables)" (LevelDB implementation notes). Merging sorted files, keeping the newest version of each key, is merge sort's merge step (L18).

The design is the log-structured merge tree, published by O'Neil, Cheng, Gawlick and O'Neil as "The Log-Structured Merge-Tree (LSM-Tree)" (1996). LevelDB, RocksDB and Cassandra use it: "The Cassandra storage engine is optimized for high performance, write-oriented workloads. The architecture is based on Log Structured Merge (LSM) trees, which utilize an append-only approach instead of the traditional relational database design with B-trees" (Cassandra: Storage Engine).

Bloom filters: skip the files that can't have it

Reading a key that's in an old table, or in none, means checking table after table. A Bloom filter per table answers "definitely not here" without touching the disk. Broder and Mitzenmacher's survey defines it: "A Bloom filter for representing a set S = {x1, x2, …, xn} of n elements is described by an array of m bits, initially all set to 0. A Bloom filter uses k independent hash functions." Adding a key sets k bits; to check a key, "If not, then clearly y is not a member of S. If all hi(y) are set to 1, we assume that y is in S, although we are wrong with some probability" ("Network Applications of Bloom Filters: A Survey", Internet Mathematics, 2004). "No" is always right; "maybe" is sometimes wrong. The same survey derives the false-positive rate, f = (1 − e−kn/m)k, and that it's smallest when k = ln 2 · (m/n).

You don't need k separate hash functions. Kirsch and Mitzenmacher showed that two are enough, combined "to simulate additional hash functions of the form gi(x) = h1(x) + ih2(x)" ("Less Hashing, Same Performance", 2008). Ours takes both halves of one 64-bit hash: FNV-1a over the bytes, which loops "hash = hash xor octet_of_data; hash = hash * FNV_prime" (FNV hash), then MurmurHash3's fmix64 finaliser (MurmurHash3.cpp) to spread the bits, as L19's HashMap spreads hashCode.

bits/key   k   memory    measured   predicted
       4   3     48 KB    14.722%    14.689%
       8   6     97 KB     2.131%     2.158%
      10   7    122 KB     0.826%     0.819%
      10   1    122 KB     9.513%     9.516%
      16  11    195 KB     0.044%     0.046%

Both languages print exactly this table, because the hash is the same bit for bit. The measurements land within a few hundredths of a percent of the formula. Ten bits per key, about 1.2 bytes, rules out 99.2% of absent keys, and the check confirms there's never a false "no". The fourth row is the same memory with k = 1: 9.5% wrong instead of 0.8%. Choosing k matters as much as choosing m.

The whole LSM tree

Each SSTable keeps two small things in memory: the Bloom filter, and a sparse index holding the first key of every 16-record block. A lookup checks the filter, finds the block with TreeMap.floorEntry (the entry version of the floorKey you met in L20), and reads at most 16 records. The records use Part 1's format, so LogKV.encode writes them.

compact is a k-way merge: a min-heap (L20) holds the head record of every table, ordered by key and then by age, so for equal keys the newest comes out first and the older copies are skipped. Then 100,000 random writes over 50,000 possible keys, a memtable of 10,000, and lookups checked against a plain HashMap of the truth:

100,000 puts to 43107 keys -> 9 SSTables, write amplification 0.90
present keys                 blocks read per get  1.02  bloom skips per get  2.59  wrong 0
absent keys, Bloom on        blocks read per get  0.08  bloom skips per get  8.92  wrong 0
absent keys, Bloom off       blocks read per get  9.00  bloom skips per get  0.00  wrong 0
range(user01000, user01004) = [(user01001, v66031), (user01002, v12661), (user01003, v36833)]
after compact: 1 SSTable, write amplification 1.33
present keys, compacted      blocks read per get  1.00  bloom skips per get  0.00  wrong 0

That's Kotlin. Java's numbers agree to within a few hundredths, but it draws different random keys (kotlin.random.Random and java.util.Random are different generators), so its range lists other values.

  • Every answer is right (wrong 0), including the deleted user00042: its tombstone in a newer table hides the older value.
  • Present keys cost about one block read, because the Bloom filters skip on average 2.6 of the tables in front of the right one.
  • Absent keys: 0.08 block reads with filters, 9.00 without. Every one of the 9 tables would otherwise be read. With filters, the only reads are false positives: 9 tables × about 0.8% ≈ 0.07.
  • Range queries work, which Bitcask couldn't do: the tables are sorted, so range reads from the right block of each and stops at the end key.
  • Write amplification is bytes written to SSTables divided by the bytes Part 1's plain log would have written. Flushing alone gave 0.90, because overwrites inside one memtable never reach the disk. Compaction rewrote everything once more: 1.33 in total. Real engines compact again and again as data moves down levels. Cassandra's docs call it out: "Every write of data in Cassandra is re-written multiple times, known as write amplification, and this adds background I/O to the database workload."

B-trees write pages, not records

For comparison, a B-tree database (L35) updates a page in place. With SQLite's write-ahead log, every changed page is appended to the WAL first: "Each frame consists of a 24-byte frame-header followed by a page-size bytes of page data" (SQLite file format), and "the default page size increased to 4096" (PRAGMA page_size). So a commit costs at least 4,120 bytes per changed page, however small the change. Measure it by switching off automatic checkpoints so the WAL keeps every frame:

1 row per commit      WAL  9,167,032 bytes =  4,583 per row,  180.1× a plain log
100 rows per commit   WAL    572,712 bytes =    286 per row,   11.3× a plain log
all rows in 1 commit  WAL     57,712 bytes =     28 per row,    1.1× a plain log

Java's run matches to within 1%. A one-row commit writes about 4.6 KB to the WAL for a row that takes about 25 bytes in Part 1's log: 180 times what a plain log writes, and that's before a checkpoint copies the same pages into the database file again. Batch 100 rows per commit and many of them share pages, and the ratio falls to 11. All 2,000 in one commit is barely more than a log. So "B-trees write more than LSM-trees" is true per small transaction, and mostly a statement about how you batch. The honest summary is a table of trade-offs:

RocksDB lets you tune the LSM side of this. Its leveled compaction optimises "disk footprint vs. logical database size (space amplification)", while universal compaction optimises "total bytes written to disk vs. logical database size (write amplification)" and "typically results in lower write-amplification but higher space- and read-amplification" (RocksDB Overview). Read, write and space amplification trade against each other: no engine minimises all three.

Bridge to Android. "The Room persistence library provides an abstraction layer over SQLite to allow fluent database access while harnessing the full power of SQLite" (Android: Room). And SQLite commits every statement that isn't already inside a transaction: "Any command that accesses the database (basically, any SQL command, except a few PRAGMA statements) will automatically start a transaction if one is not already in effect. Automatically started transactions are committed when the last SQL statement finishes" (SQLite: Transaction). So an app that saves rows one at a time in a loop pays the 180× row above on every one. Wrapping the loop in one transaction is the fix you just measured.

Exercise: size a Bloom filter for a target error rate

From a blank file, in both languages. Using the survey's two results, k = ln 2 · (m/n) and, at that k, a false-positive rate of (1/2)k, derive how many bits per key a filter needs for a target rate p. Write bitsPerKey(p), build filters for 10%, 1% and 0.1% over 100,000 keys, and measure them on 1,000,000 absent keys.

Solution

(1/2)k = p gives k = −log2 p. Substituting k = ln 2 · (m/n): m/n = −log2 p / ln 2 = −ln p / (ln 2)2. That's about 1.44 · log2(1/p) bits per key, and every tenfold improvement costs another 4.8 bits.

target  10.0%:  4.79 bits/key, k =  3, measured 10.093%
target   1.0%:  9.59 bits/key, k =  7, measured  0.991%
target   0.1%: 14.38 bits/key, k = 10, measured  0.103%

Java prints the same. 9.59 bits per key and k = 7 is the "about 1%" filter the SSTables use (they round up to 10 bits).

Check

A Bloom filter says a key is not in a table. The key is…

A key that was added set all its k bits, and bits are never cleared, so a 0 among them proves absence. Only "maybe" can be wrong.

An LSM tree reads a key. Why must it check the SSTables newest first?

A key can be in several tables. The newest copy, value or tombstone, is the truth, so the search stops at the first table that has the key.

Compacting all SSTables into one, a key's newest entry is a tombstone. The merge…

When every table takes part, nothing older remains for the tombstone to hide, so both go. A partial merge has to keep it, which is why LevelDB keeps "deletion markers … around to hide obsolete values present in older sorted tables".

Why did one-row commits write about 4.6 KB of WAL per small row?

The WAL records whole changed pages, 24 bytes of frame header plus 4,096 bytes of page, sometimes two pages when a leaf splits. Batching lets many rows share each logged page.

A storage engine decides how bytes sit on disk. A data model decides what shape your data has when you think about it. Documents: one record holds the whole thing

MongoDB stores JSON-like documents: "Embedded documents store related data in a single document structure. A document can contain arrays and sub-documents with related data. These denormalized data models allow applications to retrieve related data in a single database operation" (MongoDB: Embedded Data). The first query is that win: a book and its authors come back together, with no join. SQLite's ->> operator pulls a field out, and it "returns an SQL TEXT, INTEGER, REAL, or NULL value that represents the selected subcomponent, or NULL if the subcomponent does not exist" (SQLite JSON functions).

Two prices show up in the output:

  • Schema-on-read. The Lathe of Heaven has no year, and nothing complained: the query just got NULL. MongoDB calls this a feature: "Documents within a single collection are not required to have the same set of fields or data types" (MongoDB: Data Modeling). The relational table refused the same insert: NOT NULL constraint failed. That's schema-on-write. A document store moves the check into every program that reads the data.
  • Duplicated relationships. "Ursula K. Le Guin" is spelled out inside two documents. Counting her books meant unpacking every document's array with json_each, and renaming her means rewriting every document that mentions her. One-to-many data that's read together suits documents; many-to-many data (authors ↔ books, students ↔ courses) is what joins and normalisation (L35) are for.

Key-value and wide-column

Parts 1 and 3 built key-value stores: get, put and delete by key, with the value opaque to the database. That's the whole model, and it scales well because a key says exactly where its data lives (L42's sharding). Wide-column stores such as Cassandra add structure on top: rows grouped into partitions by a key, sorted inside each partition, all of it stored in an LSM tree. You design the tables backwards from the questions: "In Cassandra, data modeling is query-driven" (Cassandra: Data Modeling).

Graphs: when the relationships are the data

"A Neo4j graph database stores data as nodes, relationships, and properties instead of in tables or documents" (Neo4j: Graph database concepts). Its strength is questions that follow edges an unknown number of times: friends of friends, the shortest route, everything a package depends on. SQL can do it too, with a recursive common table expression, and SQLite's docs describe how it runs: "Run the initial-select and add the results to a queue. While the queue is not empty: Extract a single row from the queue. Insert that single row into the recursive table. Pretend that the single row just extracted is the only row in the recursive table and run the recursive-select, adding all results to the queue" (SQLite: WITH). A queue of frontier rows, expanded one at a time: that's L21's breadth-first search. Check it against a BFS written by hand:

within 1: {ana=0, ben=1, eve=1}  same as SQL: true
within 2: {ana=0, ben=1, cai=2, eve=1}  same as SQL: true
within 3: {ana=0, ben=1, cai=2, dee=3, eve=1}  same as SQL: true
within 4: {ana=0, ben=1, cai=2, dee=3, eve=1, fay=4}  same as SQL: true

Both languages print the same, and SQL agrees with BFS at every depth. UNION rather than UNION ALL drops repeated rows ("only add rows to the queue if no identical row has been previously added"), and the hops < ? limit is what stops a cycle from looping forever. cai is reachable two ways, through ben and through eve; min(hops) keeps the shorter.

Check

A document store accepts a book with no year field. Reading year later gives…

Schema-on-read: nothing checked the shape on the way in, so a missing field reads as absent, NULL in SQLite's ->>. The relational table rejected the same row at insert time.

SQLite runs a recursive CTE by repeatedly taking rows from a queue. That makes it…

A FIFO queue of frontier rows, each expanded once: BFS (L21). The Friends program confirms it against a hand-written BFS at every depth.

Which data most needs a relational model with joins?

Students ↔ courses is many-to-many: embedding either side in the other duplicates data and makes updates touch many documents. The other three are self-contained, read whole by one key.

Final exercise

A store that survives kill -9

~25 min

Do this in a fresh Gradle project (L11), from blank files, test-first. Kotlin first, then Java. No peeking at the parts above until you've rated your attempt.

The spec. A LogStore in package katas, opened with LogStore.open(dir, sync), where sync is Sync.EVERY_WRITE (the default) or Sync.NEVER:

  • put(key, value), get(key) (null if absent), delete(key), size, fileBytes, compact() and close(). An empty key is an IllegalArgumentException.
  • One file, data.log, in Part 1's record format, CRC included. With EVERY_WRITE, put returns only after force.
  • On open: delete any leftover data.log.compact, rebuild the index, and truncate anything after the last valid record.
  • compact() writes the live records to data.log.compact, forces it, and renames it over data.log with ATOMIC_MOVE.

Tests to write, in this order: an empty store has nothing → put then get → an overwrite keeps the latest → a delete survives reopening → reopening recovers 100 keys → a torn tail is cut at every length inside the last record, and a write after repair survives a second reopen → garbage after the last record is truncated → compaction shrinks the file and keeps the latest values → a leftover compaction file is ignored → an empty key is rejected → finally, kill -9 loses no acknowledged write.

The kill test. Put a main in the test sources that opens a store and loops forever: put("k$i", "v$i"), then print acked $i. The test starts it as a separate JVM with the same java and classpath (ProcessHandle.current().info().command() and the java.class.path system property), reads lines until about 2,000 writes are acked, kills it with SIGKILL, and reads any acks still in the pipe. It asserts exit code 137, then reopens the store and checks every acked key. Sync.NEVER is enough here, because Part 2 showed the page cache survives a process crash. Power loss is the one failure a test can't produce.

The DURABILITY row: without looking, explain to yourself, or write in your katas repo, which of your store's guarantees hold after (a) an exception, (b) kill -9, (c) a kernel panic, (d) a power cut, for both Sync settings, and which line of code provides each one. Then open the model answer.

Model answer: what survives which crash
  • (a) An exception, and (b) kill -9: every completed put survives with either setting, because ch.write has handed the bytes to the kernel. A crash in the middle of compact() leaves the old file intact (the rename hasn't happened), and the next open deletes the leftover file.
  • (c) A kernel panic: with NEVER, writes still in the page cache are lost, possibly leaving a torn tail. Startup's CRC check and truncate remove it, so the store opens with a clean prefix of the writes. With EVERY_WRITE, every acknowledged write was forced, so nothing acknowledged is lost.
  • (d) A power cut: the same as (c) on this Mac, because JDK 26's force uses F_FULLFSYNC and flushes the drive's cache too. With a plain fsync, Apple warns the drive may still lose or reorder recent writes.
  • One gap: the rename itself is a change to the directory. A fully careful store also forces the directory after the rename, which is what SQLite's synchronous=EXTRA adds for its journal ("the directory containing a rollback journal is synced after that journal is unlinked").
Reference solution: LogStore

Wrap-up

Exit quiz, recall card, sources

~5 min

Merging k sorted SSTables with a min-heap of their heads costs, for n records in total… (L18, L20)

Each record is pushed and popped once, and each heap operation is O(log k) for a heap of k cursors. Merge sort's two-way merge is the case k = 2.

L36 found 10,000 inserts far faster inside one transaction than as 10,000 auto-commits. Today's name for that is… (L36)

One forced write covers many changes. FsyncCost showed the same thing with 1, 10 and 100 writes per force, and WalAmp with rows per commit.

A CRC-32 check passes on 4 random garbage bytes by chance with probability about… (L48)

Random bytes produce a random 32-bit value, so the chance it equals the stored CRC is 1 in 232, about 1 in 4.3 billion. Rare, which is why it's good enough to tell a torn tail from a real record.

A child JVM was killed with SIGKILL. waitFor() returns… (L53)

128 + 9. The final's kill test asserts exactly this, so it fails loudly if the child died some other way, such as a crash at startup.
