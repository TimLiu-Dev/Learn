Part 1

Why clocks lie

~25 min

Every computer keeps time with a quartz crystal, and no two crystals tick at exactly the same rate. Martin Kleppmann's Cambridge lecture notes (free, and this lesson's best companion) put it plainly: "The rate by which a clock runs fast or slow is called drift", measured in parts per million, where "1 ppm = 1 microsecond/second = 86 ms/day = 32 s/year" (Kleppmann, Distributed Systems notes, §3.1). The difference between two clocks at one moment is clock skew. To keep skew small, machines regularly ask a time server for the correct time. "The Network Time Protocol (NTP) is widely used to synchronize computer clocks in the Internet" (RFC 5905).

Correcting a clock means changing it, sometimes by a jump. That's why the JVM gives you two different clocks. L32's time part showed them inside one program; here's why the difference matters across machines:

MonotonicTimeSource.Monotonic · System.nanoTime()Durations, timeouts, benchmarks (L16).Meaningless across machines: nanoTime "can only be used to measure elapsed time and is not related to any other notion of system or wall-clock time" (System.nanoTime).

Java prints the same, except that it has no TimeSource line. The two sleep timings are real and came out at 60–62 ms, not 50. Thread.sleep promises at least the time you ask for, and this machine was busy.

  • The user's latest edit vanished. B's clock was 300 ms slow, so its later write carried an earlier timestamp, and last write wins kept the older value on both replicas. No error, no log line. Kleppmann describes the rule exactly: "the update with the greatest timestamp takes effect, and any concurrent updates with lower timestamps to the same key are discarded" (§5.1). With skewed clocks, "greatest timestamp" no longer means "latest".
  • The table is the real rule. Last write wins is only safe when two writes are further apart than the clocks' skew. Two edits 10 ms apart lose one as soon as the skew passes 10 ms. L43 avoided this by sharing one counter between both replicas, a luxury that machines in different buildings don't have.
  • The timeout fired at 7 s or 3 s, never 5 s. When NTP stepped the clock back 2 s, the elapsed time measured by the time-of-day clock shrank by 2 s. Stepping forward made it fire early. A lease, a lock expiry or a rate limiter (L43) built on currentTimeMillis inherits exactly this bug. Measure durations with a monotonic clock, always.

Bridge: on Android the user can set the phone's clock to anything they like. Never let a client's timestamp decide which write wins on your server: the server assigns the order, or you use Part 2's logical clocks.

  • Data class vs record. data class Versioned(…) and record Versioned(…) both generate equals, hashCode and toString (L7).
  • !! says "I know it's set". a.current!!.value throws if current is null. Java's a.current.value() throws the same NullPointerException, but the type never warned you it could be null (L3).

Both languages print this table. The simulation matches the formula exactly, because the worst moment is always just before a sync, when one clock has gained ppm × T and the other has lost the same. Syncing every 16 s keeps two good clocks within about 1.6 ms of each other; a machine that syncs every 17 minutes can be 100 ms out. That's only drift: real NTP adds its own error, and "the exact accuracy achieved in a particular system depends on the timing properties of the network between client and server" (Kleppmann, §3.2). So last write wins is safe only for writes further apart than drift plus NTP error, a number you rarely know. Two clicks a user makes 50 ms apart can easily fall inside it.

A rate limiter refills tokens based on elapsed time. Which clock should measure that time?

Elapsed time needs a monotonic clock, and nanoTime is the JVM's. The other three are time-of-day clocks that NTP can step, so a backwards step would stall the refill and a forward one would grant a burst. (L43's token bucket used an injected clock for testing; in production it should sit on a monotonic source.)

Two replicas use last write wins. B's clock is 100 ms slow, and a user edits on A, then on B 50 ms later. Which value survives?

B stamps its write 50 − 100 = 50 ms earlier than A's, so last write wins keeps A's older value and drops the user's latest edit. That's the "100ms / 50ms" cell of the table: LOST.

Part 2

Logical clocks

~25 min

If physical clocks can't tell you what happened first, what can? In 1978 Leslie Lamport answered with one of the most cited papers in computing, "Time, Clocks, and the Ordering of Events in a Distributed System". Its abstract: "The concept of one event happening before another in a distributed system is examined, and is shown to define a partial ordering of the events" (Lamport, 1978). He defines the happened-before relation, written →, as the smallest relation where:

  1. "If a and b are events in the same process, and a comes before b, then a → b."
  2. "If a is the sending of a message by one process and b is the receipt of the same message by another process, then a → b."
  3. "If a → b and b → c then a → c."

Two events where neither happened before the other are concurrent. This is the shape you met in L27. The Java memory model's happens-before is also built from program order plus extra edges (unlocks before locks, volatile writes before reads), closed under transitivity. There the edges are synchronization between threads; here they are messages between machines. Both say the same thing: a could have influenced b only if there is a chain of edges from a to b.

Lamport clocks

Lamport then gives every process a counter and two rules that make timestamps respect →:

  • IR1. "Each process Pi increments Ci between any two successive events."
  • IR2. "(a) If event a is the sending of a message m by process Pi, then the message m contains a timestamp Tm = Ci(a). (b) Upon receiving a message m, [the receiver] sets [its clock] greater than or equal to its present value and greater than Tm."

Together they guarantee his Clock Condition: "For any events a, b: if a → b then C(a) < C(b)." A vector clock goes further, and Part 2's program runs both over the same script. Kleppmann explains why you'd want the second one: "If we do want to detect when events are concurrent, we need a different type of logical time: a vector clock" (§3.4). Each node keeps one counter per node; "Whenever an event occurs at node Ni, it increments the i th entry (its own entry) in its vector clock", and a receiver takes the element-wise maximum of its vector and the message's before incrementing its own entry.

Both print exactly this (checked with diff):

  • Lamport clocks respect causality. The send of m1 (2) comes before its receipt (3), and the chain a → send m1 → recv m1 → send m2 → recv m2 gives 1 < 5.
  • They can't detect concurrency. P2's b (1) and P1's d (3) never exchanged a message, yet Lamport gives them an order, 1 < 3. Lamport says so himself: "Note that we cannot expect the converse condition to hold as well, since that would imply that any two concurrent events must occur at the same time." A smaller Lamport time means "maybe before", never "definitely before".
  • Vector clocks can. compare returns BEFORE only when every entry is ≤ and one is <; if each vector is ahead somewhere, the events are CONCURRENT. b's [0,1,0] and d's [3,0,0] are concurrent, which is the truth.
  • A total order is still useful. Sorting by (Lamport time, process number) gives every node the same order of all events, consistent with causality. It's arbitrary for concurrent events, but it's the same arbitrary choice everywhere. Lamport's paper uses exactly this to build a distributed lock.
  • Version vectors fix L43's cart. A vector per replica counts each replica's writes. [2,0] vs [1,1] is CONCURRENT, so instead of silently dropping one cart, the replica keeps both and merges. A merge written later dominates both parents, and a stale write is recognised as old. L43's exercise did this with parent pointers; Amazon's Dynamo paper, cited there, used vectors.

Event x has Lamport time 4 and event y has Lamport time 9. What do you know for certain?

The Clock Condition says if y → x then C(y) < C(x). Here C(y) > C(x), so y → x is impossible. But x → y isn't guaranteed either: they could be concurrent. Only a vector clock can tell those apart.

Compare the vector clocks [2,1,0] and [1,1,3]. What's the relation?

The first is ahead in entry 0 (2 > 1), and the second is ahead in entry 2 (3 > 0). Neither dominates, so neither event could have seen the other: concurrent.

Part 3

Leader election and consensus: Raft

~35 min

L42's leader database had a weak spot you may have noticed: if the leader dies, someone has to promote a follower. If two followers both decide they're the new leader, both accept writes and the data splits into two histories. Kleppmann: "If there were multiple leaders, they could make inconsistent decisions … (a situation known as split brain)" (§7.1). Picking exactly one leader, even while machines crash and messages vanish, is an instance of consensus. The Raft site defines it: "Consensus involves multiple servers agreeing on values. Once they reach a decision on a value, that decision is final" (raft.github.io).

Raft, by Diego Ongaro and John Ousterhout, "is a consensus algorithm for managing a replicated log", designed to be easier to understand than Paxos, which came before it ("In Search of an Understandable Consensus Algorithm (Extended Version)"). Its leader election rests on five rules, each quoted from §5.1–5.2 of the paper:

  1. Terms number the leaderships. Time is divided into terms, each starting with an election. "Terms act as a logical clock in Raft, and they allow servers to detect obsolete information such as stale leaders": Part 2's idea, used to order leaders.
  2. A newer term always wins. "If a candidate or leader discovers that its term is out of date, it immediately reverts to follower state. If a server receives a request with a stale term number, it rejects the request."
  3. Leaders send heartbeats. "Leaders send periodic heartbeats (AppendEntries RPCs that carry no log entries) to all followers in order to maintain their authority." A follower that hears nothing for an election timeout becomes a candidate: it increments its term, votes for itself, and sends RequestVote to everyone.
  4. One vote per term. "Each server will vote for at most one candidate in a given term, on a first-come-first-served basis … The majority rule ensures that at most one candidate can win the election for a particular term."
  5. Random timeouts break ties. "To prevent split votes in the first place, election timeouts are chosen randomly from a fixed interval (e.g., 150–300ms)."

The program below implements exactly those five rules on five simulated nodes. Each message takes 2–10 ms of virtual time, a crashed node drops everything, and a partition cuts links. It replays one run with a crash, then attacks rule 4 with 2,000 random runs, once with correct voters and once with a voter that "forgets" its vote.

  • The first election took 14 ms. n1's random timeout (154 ms) expired first, so it asked before anyone else and got every vote. It became leader as soon as the third vote arrived: 3 of 5 is a majority, and it doesn't wait for the rest.
  • Failover is automatic. 600 ms after start the leader crashed. Followers stopped hearing heartbeats, n3's timeout expired first at 775 ms, and it won term 2 within 9 ms. No operator promoted anyone.
  • The old leader rejoined safely. n1 restarted "still in term 1" because Raft stores the term and the vote on disk ("Raft's RPCs typically require the recipient to persist information to stable storage", §5.6; L56's fsync is exactly that). The first heartbeat it received carried term 2, so it simply became a follower.
  • Rule 4 is the whole safety argument. Across 2,000 chaotic runs, not one term had two leaders. Let a voter forget its vote and 464 terms did; in seed 4, three nodes all believed they led term 1. With honest voters it can't happen: two majorities of 5 always share a server (the warm-up's pigeonhole), and that server would have had to vote twice.
  • Most terms had no leader (9,181 vs 4,696). Each partition leaves a minority that keeps timing out and starting elections it can never win, so its term number climbs. That's harmless for safety, but when such a node rejoins, its high term forces a needless new election. Production systems add extensions for exactly this.

From one leader to one log

A leader by itself isn't the goal. The goal is a replicated log: the same commands, in the same order, on every node, so each node's copy of the data (its state machine) ends up identical. Raft's leader appends each client command to its log and ships missing entries to each follower in the next AppendEntries, so a heartbeat doubles as replication. Three more rules from §5.3–5.4 make it safe:

  • Commit by majority. "A log entry is committed once the leader that created the entry has replicated it on a majority of the servers." Only then is it applied, and only then may a client be told "done".
  • The consistency check. "When sending an AppendEntries RPC, the leader includes the index and term of the entry in its log that immediately precedes the new entries. If the follower does not find an entry in its log with the same index and term, then it refuses the new entries." The paper calls this "an induction step" (L48's induction, holding a whole log in shape). On a refusal the leader steps back one entry and tries again; followers' conflicting, uncommitted entries get overwritten.
  • The election restriction. A candidate can't win unless its log holds every committed entry: "the voter denies its vote if its own log is more up-to-date than that of the candidate", where "If the logs have last entries with different terms, then the log with the later term is more up-to-date. If the logs end with the same term, then whichever log is longer is more up-to-date."

Together they give the two guarantees the final will test, both from the paper's Figure 3: Election Safety, "at most one leader can be elected in a given term", and State Machine Safety, "if a server has applied a log entry at a given index to its state machine, no other server will ever apply a different log entry for the same index." The widget below steps through the final's real run, event by event. Leave the box unticked to watch a healthy cluster, then tick it to split the network at 700 ms and compare.

Look for three moments in the partitioned run. At 750 ms the old leader n5 accepts x=3 and copies it to n1, but with only 2 of 5 it can never commit. At 881 ms the majority side elects n4 in term 2 and commits x=4. After the heal, n5 sees term 2, steps down, and both n5 and n1 drop the uncommitted x=3. A client that was told "accepted" for x=3 learns the hard way that only "committed" counts.

The paper also states when this works at all: "broadcastTime ≪ electionTimeout ≪ MTBF". Messages must arrive well within a timeout, or followers start elections while the leader is still alive. And timeouts must be far shorter than the mean time between failures, because "When the leader crashes, the system will be unavailable for roughly the election timeout" (§5.6).

Bridge: you will almost never write Raft yourself, but you will depend on it. etcd is "Properly distributed via Raft protocol" (etcd.io), and Kubernetes uses etcd as its "Consistent and highly-available key value store used as Kubernetes' backing store for all cluster data" (Kubernetes architecture). When a Spring Boot service runs on Kubernetes, every deployment and config change you make is a Raft log entry somewhere.

With no randomness, all 1,000 runs failed to elect a first leader within 10 s: every follower times out at the same moment, everyone votes for themselves, and the split repeats forever. Wider ranges mainly shrink the worst case. The paper recommends "a conservative election timeout such as 150–300ms".

A 5-node Raft cluster is split into groups of 2 and 3. Where can a leader be elected?

Winning needs votes from a majority of the whole cluster: 3 of 5. The group of 2 can never collect 3 votes, so it keeps timing out with rising terms. The group of 3 elects a leader and keeps working.

An old leader in the minority accepts a client's write after the partition. What happens to that entry?

It can't reach a majority, so the old leader never commits it. After the heal the old leader sees a higher term, steps down, and the consistency check makes it (and any follower it copied the entry to) drop the conflicting entry. The widget shows x=3 going exactly this way.

Why does each candidate pick a random election timeout?

If every follower timed out together, they'd all vote for themselves and split the vote, over and over. Randomness spreads them out, so one candidate usually asks first and wins before the others wake up. The exercise measured it.

Part 4

Two-phase commit vs sagas

~20 min

L36's transactions were all-or-nothing inside one database. Now an order must be saved in orders-db and stock reserved in stock-db, two separate systems, and you want both or neither. "The most common algorithm to ensure atomic commitment across multiple nodes is the two-phase commit (2PC) protocol [Gray, 1978]" (Kleppmann, §6.1). A coordinator runs it in two phases:

  1. Prepare. The coordinator asks each participant "can you commit?". A participant that answers yes must make sure it can commit later, even after a crash, and keeps its locks until told the outcome.
  2. Commit or abort. If every vote was yes, the coordinator writes COMMIT to its own log and tells everyone; any no means ABORT.

The catch is what happens between the phases. A prepared participant has given up the right to decide alone. Kleppmann: "The problem with two-phase commit is that the coordinator is a single point of failure", and the slide beside it adds, "Algorithm is blocked until coordinator recovers."

Both print exactly this:

== 1. Both participants can commit
  votes orders-db=yes, stock-db=yes -> coordinator logs COMMIT
  orders-db=COMMITTED  stock-db=COMMITTED
== 2. stock-db can't (out of stock)
  votes orders-db=yes, stock-db=no -> coordinator logs ABORT
  orders-db=ABORTED  stock-db=ABORTED
== 3. Both vote yes, then the coordinator crashes
  votes orders-db=yes, stock-db=yes -> coordinator logs COMMIT
  coordinator CRASHES before phase 2
  orders-db=PREPARED  stock-db=PREPARED
  after 1s, a reader on orders-db: BLOCKED: row locked by an in-doubt transaction
  after 60s, a reader on orders-db: BLOCKED: row locked by an in-doubt transaction
  after 3600s, a reader on orders-db: BLOCKED: row locked by an in-doubt transaction
  orders-db asks stock-db what to do: it is PREPARED too, so neither knows the decision
  coordinator restarts, reads its log: COMMIT, tells everyone
  orders-db=COMMITTED  stock-db=COMMITTED   reader: ok

Cases 1 and 2 are what 2PC is for: both databases committed, or both aborted. Case 3 is its price. Both participants voted yes, so neither may abort, and neither knows the decision, so neither may commit. The row stays locked for as long as the coordinator is down, an hour in this run, and every reader of that row waits. Real databases document this honestly. PostgreSQL's PREPARE TRANSACTION "prepares the current transaction for two-phase commit", and the manual warns: "It is unwise to leave transactions in the prepared state for a long time", because "the transaction continues to hold whatever locks it held". Its advice for applications is blunt: "Unless you're writing a transaction manager, you probably shouldn't be using PREPARE TRANSACTION". The feature is meant for external transaction managers, "some of which are covered by standards (such as X/Open XA)" (PostgreSQL docs).

The cure for a coordinator that can crash is Part 3. If the votes go through a consensus log instead of one coordinator, any node can learn the outcome. Kleppmann's notes show "a fault-tolerant two-phase commit algorithm based on Paxos Commit [Gray and Lamport, 2006]" (§6.1). That's powerful and heavyweight, and most microservice systems choose something weaker.

Sagas: give up isolation, keep going

The saga pattern drops the global lock altogether: "Implement each business transaction that spans multiple services as a saga. A saga is a reliably coordinated sequence of local transactions" (microservices.io: Saga). Each step commits for real in its own service. If a later step fails, "the changes made by the completed steps are undone by compensating transactions": not a rollback, but a new action that cancels the old one.

== Ana's trip: every step succeeds
  reserve flight: ok
  reserve hotel: ok
  charge card: ok
  committed: true, seats=0 rooms=0 charged=450
== Ben's trip: the card is declined, so earlier steps are compensated
  reserve flight: ok
  reserve hotel: ok
  charge card: FAILED
  compensate reserve hotel
  compensate reserve flight
  committed: false, seats=1 rooms=1 charged=0
  meanwhile Cleo searched hotels between Ben's steps and saw: sold out
  (no isolation: she saw a reservation that was later undone)

Ben's card was declined, so the hotel and flight reservations were cancelled in reverse order, and the books balance again. Nothing ever blocked. But look at Cleo: between Ben's steps she searched for a room and was told "sold out", because Ben's reservation was real for a moment. The pattern's own page lists this as the main drawback: "Lack of isolation (the "I" in ACID)", with a risk that concurrent sagas cause data anomalies. You design around it, for example by marking rows pending until the saga finishes.

The outbox: one local transaction, then a queue

Every saga step has the same problem in miniature: save to my database and send a message to the next service. If you commit and then crash before sending, the message is lost. If you send and then the commit fails, you've announced something that never happened. The transactional outbox asks "How to atomically update the database and send messages to a message broker?" and answers: "The solution is for the service that sends the message to first store the message in the database as part of the transaction that updates the business entities" (microservices.io: Transactional outbox). A separate relay then publishes the stored messages. Its honest caveat: "The Message relay might publish a message more than once. It might, for example, crash after publishing a message but before recording the fact that it has done so." That's L42's at-least-once delivery again, and the answer is the same: an idempotent consumer.

What Kotlin does for you.
  • Function types. A step's action is (Inventory) -> Boolean and its compensation (Inventory) -> Unit. Java needs two different interfaces, Predicate<Inventory> and Consumer<Inventory>, and calls them with .test(…) and .accept(…) (L14).
  • Default arguments. Coordinator(crashBeforePhase2 = true) and runSaga(…, afterEach = {}) replace Java's extra constructor and the explicit name -> {}.
  • Capturing a var. Kotlin's lambda can assign seenByCleo directly. Java's lambda can't assign a local, hence the String[] seenByCleo = {""} one-element-array trick (L14).
  • use { } closes each JDBC statement in the exercise, like Java's try-with-resources (L10).

In two-phase commit, a participant has voted yes and then loses contact with the coordinator. What may it do?

A yes vote is a promise to commit if told to, so aborting alone could break atomicity. But the coordinator might have decided ABORT, so committing alone could break it too. It must wait, and its locks block everyone who needs those rows.

An outbox relay crashes after publishing a message but before marking it sent. What does the consumer see?

On restart the relay finds the row still unsent and publishes it again. The outbox guarantees at-least-once delivery, never exactly-once, so the consumer must be idempotent (L42).

SAFETY, a model answer. (1) A node becomes leader of term T only after votes from a majority, more than n/2 nodes, all in term T. (2) Each node votes at most once per term, and stores that vote durably, so even a crash and restart can't make it vote again in T. (3) Any two majorities of the same n nodes overlap in at least one node, because together they have more than n members (pigeonhole, L48). So if two candidates both won term T, the shared node voted twice in T, contradicting (2). The buggy-voter sweep in Part 3 broke rule (2), and two leaders appeared at once.

Wrap-up

Exit quiz, recall card, sources

~5 min

L24 + L57: a Raft leader stops for a 2-second garbage-collection pause, with a 150–300 ms election timeout. What happens?

No heartbeats for 2 s means followers time out and elect a new leader in a higher term. When the paused leader wakes, its first contact carries the newer term and it steps down. A stop-the-world pause (L24) looks exactly like a crash from outside, which is why long GC pauses matter in clustered systems.

L56 + L57: why must a Raft node save its term and vote to disk, with fsync, before replying to a RequestVote?

If the vote lived only in memory, a node could vote, crash, restart with no memory of it, and vote for a second candidate in the same term. That breaks the one-vote rule the whole safety argument rests on. L56 showed that only fsync makes a write survive a crash.

L32 + L57: a client's write to the leader times out. The leader may or may not have committed it. What makes a retry safe?

A timeout tells you nothing about whether the write committed. With an idempotency key (L32), the service recognises the retry and returns the first result instead of applying it twice. The final's x=3 shows the other half: "accepted" was never a promise.

L27 + L57: what do the Java memory model's happens-before and Lamport's happened-before have in common?

Both start from program order, add edges (synchronization in the JMM, messages here), and close under transitivity. Neither orders every pair: events with no chain between them are concurrent, and neither uses physical time.
