L43's replicas resolved a conflict with last write wins. What happened to the other concurrent write? (L43)

Last write wins keeps the version with the bigger timestamp and discards the rest, with no error anywhere. L43 got its timestamps from one shared counter. Part 1 shows what happens when each machine uses its own clock instead.

  1. Last write wins never merges: it keeps one whole version. Merging needs more information, such as Part 2's version vectors.
  2. Nothing failed, so nothing was retried. Both writes succeeded locally; the loss happened later, when the replicas synced.
  3. The version with the smaller timestamp is discarded, with no error or log line anywhere.
  4. A 409 Conflict would at least tell someone. Last write wins resolves the conflict silently, so no client ever hears.

Two groups of 3 are chosen from the same 5 servers. What must be true? (L48)

3 + 3 = 6 slots but only 5 servers, so by the pigeonhole principle (L48) some server is in both. That overlap is the whole reason a majority vote can't elect two leaders. Part 3 builds on it.

  1. 3 + 3 = 6 slots but only 5 servers, so some server must fill two slots: the pigeonhole principle.
  2. They can share just one: {1,2,3} and {3,4,5} overlap only in server 3.
  3. Two groups with no server in common would need 6 different servers, and there are only 5.
  4. Each group has only 3 servers, and even together {1,2,3} and {1,2,4} cover just four.

Which signal can a JVM's shutdown hook never react to? (L53)

SIGKILL "cannot be caught or ignored" (L53): the process just stops. That's the crash model in this lesson's simulations. A node vanishes mid-step, and only what it had already saved survives.

  1. SIGTERM is the polite stop request. The JVM catches it and runs its shutdown hooks before exiting.
  2. Ctrl+C sends SIGINT, and the JVM runs its shutdown hooks for it too.
  3. SIGHUP (the terminal closed) also starts an orderly JVM shutdown, hooks included.
  4. The kernel ends the process directly. SIGKILL can't be caught, so no Java code runs at all.

Inside one database, what does a transaction's atomicity promise? (L36)

One database can promise all-or-nothing because it controls every write. Part 5 asks how to get the same promise across two databases or services, and why that's much harder.

  1. Atomicity is about all-or-nothing, not CPU scheduling. A transaction may run on any thread or core.
  2. If any statement fails or the transaction rolls back, none of its changes remain.
  3. Whether readers wait is a question of isolation and concurrency control (MVCC can avoid it), not atomicity.
  4. How finely rows are locked is an isolation detail that varies by database. Atomicity doesn't promise it.
Part 1

Why clocks lie

~23 min (+10 min optional)

Every computer keeps time with a quartz crystal, and no two crystals tick at exactly the same rate. Martin Kleppmann's Cambridge lecture notes (free, and this lesson's best companion) put it plainly: "The rate by which a clock runs fast or slow is called drift", measured in parts per million, where "1 ppm = 1 microsecond/second = 86 ms/day = 32 s/year" (Kleppmann, Distributed Systems notes, §3.1). The difference between two clocks at one moment is clock skew. To keep skew small, machines regularly ask a time server for the correct time. "The Network Time Protocol (NTP) is widely used to synchronize computer clocks in the Internet" (RFC 5905).

Correcting a clock means changing it, sometimes by a jump. That's why the JVM gives you two different clocks. L32's time part showed them inside one program; here's why the difference matters across machines:

  • The user's latest edit vanished. B's clock was 300 ms slow, so its later write carried an earlier timestamp, and last write wins kept the older value on both replicas. No error, no log line. Kleppmann describes the rule exactly: "the update with the greatest timestamp takes effect, and any concurrent updates with lower timestamps to the same key are discarded" (§5.1). With skewed clocks, "greatest timestamp" no longer means "latest".
  • The table is the real rule. Last write wins is only safe when two writes are further apart than the clocks' skew. Two edits 10 ms apart lose one as soon as the skew passes 10 ms. L43 avoided this by sharing one counter between both replicas, a luxury that machines in different buildings don't have.
  • The timeout fired at 7 s or 3 s, never 5 s. When NTP stepped the clock back 2 s, the elapsed time measured by the time-of-day clock shrank by 2 s. Stepping forward made it fire early. A lease, a lock expiry or a rate limiter (L43) built on currentTimeMillis inherits exactly this bug. Measure durations with a monotonic clock, always.

Bridge: on Android the user can set the phone's clock to anything they like. Never let a client's timestamp decide which write wins on your server: the server assigns the order, or you use Part 2's logical clocks.

What Kotlin does for you.
  • Typed durations. TimeSource.Monotonic.markNow() returns a mark, and mark.elapsedNow() returns a Duration. Java's System.nanoTime() returns a bare long of nanoseconds, so subtracting and dividing by 1,000,000 is your job, and so is remembering the unit.
  • Data class vs record. data class Versioned(…) and record Versioned(…) both generate equals, hashCode and toString (L7).
  • !! says "I know it's set". a.current!!.value throws if current is null. Java's a.current.value() throws the same NullPointerException, but the type never warned you it could be null (L3).

Practice · A lease that NTP can't stretch

A leader holds a lease: "I may act as leader for the next 10 s." This one measures its time with the time-of-day clock, so an NTP step stretches or shortens it, just like Part 1's 5 s timeout.

  • Make remainingMs() and isValid() use the monotonic clock. It counts in nanoseconds; the lease works in milliseconds.
  • Fill in expiresAtWall(), the time of day printed in a log line: the wall clock's current reading plus the time left.
// A leader lease: "I may act as leader for the next durationMs milliseconds."
// Both clocks are passed in, so the checks can control them:
//   wallMillis() works like System.currentTimeMillis(): NTP may step it, even backwards.

Hint 1 of 3

Which clock does startedAt read? Every duration in this class should start and end on the same clock, and only one of the two clocks never jumps.

Hint 2 of 3

Record monoNanos() when the lease starts. Elapsed time is monoNanos() - start, in nanoseconds, so divide by 1_000_000 before subtracting it from durationMs.

Hint 3 of 3

expiresAtWall() is wallMillis() + remainingMs(): the time of day comes from the wall clock, the amount left from the monotonic one. In Java, the clocks are LongSuppliers, read with getAsLong().

Final answer

Why it works. Each clock does the one job it's good at. The monotonic clock measures how long the lease has run, so an NTP step can't touch that. The wall clock answers "what time is it?" for the log line, which is why expiresAtWall() reads it now, after any step, instead of adding 10 s to the start time. Passing the clocks in as functions is the same trick as L43's injected clock: the checks control time, so nothing sleeps.

Common mistake. Switching to monoNanos() but forgetting the unit: durationMs - (monoNanos() - start) subtracts nanoseconds from milliseconds, so the lease runs out a million times too early. Kotlin's TimeSource.Monotonic returns a typed Duration and avoids this.

A rate limiter refills tokens based on elapsed time. Which clock should measure that time?

Elapsed time needs a monotonic clock, and nanoTime is the JVM's. The other three are time-of-day clocks that NTP can step, so a backwards step would stall the refill and a forward one would grant a burst. (L43's token bucket used an injected clock for testing; in production it should sit on a monotonic source.)

  1. It's a time-of-day clock: an NTP step back stalls the refill, and a step forward grants a burst.
  2. It's monotonic: it only moves forward, so the difference between two readings is the real elapsed time.
  3. Instant.now() reads the same time-of-day clock as currentTimeMillis, so NTP steps hit it too.
  4. It's a time-of-day clock too, and local time also jumps at daylight-saving changes.

Two replicas use last write wins. B's clock is 100 ms slow, and a user edits on A, then on B 50 ms later. Which value survives?

B's clock is 100 ms behind, so its write, made 50 ms after A's, carries a timestamp 50 ms earlier than A's. Last write wins keeps A's older value and drops the user's latest edit. That's the "100ms / 50ms" cell of the table: LOST.

  1. B's write really is the latest, but its timestamp is 50 ms earlier, and last write wins trusts timestamps.
  2. Last write wins keeps exactly one value per key. It never merges.
  3. Last write wins never rejects a write. It accepts both and silently discards one when the replicas sync.
  4. A's write carries the larger timestamp even though it happened first, so last write wins keeps it.

Part 2

Logical clocks

~31 min (+10 min optional)

If physical clocks can't tell you what happened first, what can? In 1978 Leslie Lamport answered with one of the most cited papers in computing, "Time, Clocks, and the Ordering of Events in a Distributed System". Its abstract: "The concept of one event happening before another in a distributed system is examined, and is shown to define a partial ordering of the events" (Lamport, 1978). He defines the happened-before relation, written →, as the smallest relation where:

  1. "If a and b are events in the same process, and a comes before b, then a → b."
  2. "If a is the sending of a message by one process and b is the receipt of the same message by another process, then a → b."
  3. "If a → b and b → c then a → c."

Two events where neither happened before the other are concurrent. This is the shape you met in L27. The Java memory model's happens-before is also built from program order plus extra edges (unlocks before locks, volatile writes before reads), closed under transitivity. There the edges are synchronization between threads; here they are messages between machines. Both say the same thing: a could have influenced b only if there is a chain of edges from a to b.

Lamport clocks

Lamport then gives every process a counter and two rules that make timestamps respect →:

  • IR1. "Each process Pi increments Ci between any two successive events."
  • IR2. "(a) If event a is the sending of a message m by process Pi, then the message m contains a timestamp Tm = Ci(a). (b) Upon receiving a message m, [the receiver] sets [its clock] greater than or equal to its present value and greater than Tm."

Together they guarantee his Clock Condition: "For any events a, b: if a → b then C(a) < C(b)." A vector clock goes further, and the program below runs both over the same script. Kleppmann explains why you'd want the second one: "If we do want to detect when events are concurrent, we need a different type of logical time: a vector clock" (§3.4). Each node keeps one counter per node; "Whenever an event occurs at node Ni, it increments the i th entry (its own entry) in its vector clock", and a receiver takes the element-wise maximum of its vector and the message's before incrementing its own entry.

Both print exactly this (checked with diff):

  • Lamport clocks respect causality. The send of m1 (2) comes before its receipt (3), and the chain a → send m1 → recv m1 → send m2 → recv m2 gives 1 < 5.
  • They can't detect concurrency. P2's b (1) and P1's d (3) never exchanged a message, yet Lamport gives them an order, 1 < 3. Lamport says so himself: "Note that we cannot expect the converse condition to hold as well, since that would imply that any two concurrent events must occur at the same time." A smaller Lamport time means "maybe before", never "definitely before".
  • Vector clocks can. compare returns BEFORE only when every entry is ≤ and one is <; if each vector is ahead somewhere, the events are CONCURRENT. b's [0,1,0] and d's [3,0,0] are concurrent, which is the truth.
  • A total order is still useful. Sorting by (Lamport time, process number) gives every node the same order of all events, consistent with causality. It's arbitrary for concurrent events, but it's the same arbitrary choice everywhere. Lamport's paper uses exactly this to build a distributed lock.
  • Version vectors fix L43's cart. A vector per replica counts each replica's writes. [2,0] vs [1,1] is CONCURRENT, so instead of silently dropping one cart, the replica keeps both and merges. A merge written later dominates both parents, and a stale write is recognised as old. L43's exercise did this with parent pointers; Amazon's Dynamo paper, cited there, used vectors.

Offline-first sync: every phone is a replica

An offline-first Android app has exactly this problem, in your pocket. Android's architecture guide makes the on-device database "the canonical source of truth for the app", and when a device has written data offline that no longer matches the server, "you must resolve the conflict before synchronization can happen." Its suggestion: "For mobile apps, a common approach is 'last write wins.'" In that scheme "devices attach timestamp metadata to the data they write to the network. When the network data source receives them, it discards any data older than its current state" (Android Developers: Build an offline-first app). Hint 1 of 3

Keep one counter per process and a map from message name to the stamp it carries. A when (s) over the sealed Step (L7) needs exactly three branches.

Hint 2 of 3

A Local or Send adds 1 to its process's counter; a Send also stores that new value under its message. A Recv sets the counter to maxOf(own counter, message stamp) + 1.

Hint 3 of 3

For compare, compute two booleans: is every entry of a ≤ b's, and is every entry ≥? Both means EQUAL, only the first BEFORE, only the second AFTER, neither CONCURRENT. In Java, Java 21's switch with type patterns replaces when.

Final answer

Why it works. Lamport's two rules are the whole algorithm: count every event (IR1), and on a receive jump past both your own clock and the message's stamp (IR2). So every edge of happened-before, program order or a message, goes to a bigger number. A vector keeps one count per process, so it can say "neither saw the other", which one Lamport number can't.

Common mistake. A receive of stamp + 1 that forgets maxOf with the receiver's own clock. When P2 is already at 4 and a message stamped 1 arrives, its clock falls back to 2, below its own earlier events. A second trap is comparing vectors by their sums: [2,1,0] and [1,1,3] would look "before" when they're concurrent.

Event x has Lamport time 4 and event y has Lamport time 9. What do you know for certain?

The Clock Condition says if y → x then C(y) < C(x). Here C(y) > C(x), so y → x is impossible. But x → y isn't guaranteed either: they could be concurrent. Only a vector clock can tell those apart.

  1. A smaller Lamport time allows x → y, but doesn't prove it: the two events may be concurrent.
  2. They may be concurrent, but x → y is also possible. Lamport times alone can't tell which.
  3. If y → x, the Clock Condition would force C(y) < C(x), and 9 > 4 rules that out.
  4. Lamport times say nothing about where events ran. Any two processes can produce 4 and 9.

Compare the vector clocks [2,1,0] and [1,1,3]. What's the relation?

The first is ahead in entry 0 (2 > 1), and the second is ahead in entry 2 (3 > 0). Neither dominates, so neither event could have seen the other: concurrent.

  1. Each vector is ahead in one entry, so neither event could have seen the other.
  2. "Before" needs every entry ≤ the other's, but entry 0 is 2 vs 1.
  3. The second is ahead in entry 2 (3 vs 0) but behind in entry 0, so it can't have come first.
  4. Equal vectors need every entry to match, and these differ in entries 0 and 2.

An offline-first notes app syncs through one server. Which design never silently drops a concurrent edit?

If the phone says which version it edited, the server can tell a stale edit from a fresh one and refuse it, like L36's version column or L32's If-Match. The app then shows the conflict. Any form of last write wins keeps one edit and drops the other without telling anyone.

  1. Phone clocks drift and users can change them, and even correct timestamps still mean one edit is discarded.
  2. Arrival order at the server isn't edit order, and one of the two concurrent edits is still thrown away silently.
  3. A mismatched base version proves the edit was made on stale data, so the conflict is reported, not hidden.
  4. Syncing more often only narrows the window. Two phones offline at the same time still edit concurrently.

Leader election and consensus: Raft

~33 min (+15 min optional)

L42's leader database had a weak spot you may have noticed: if the leader dies, someone has to promote a follower. If two followers both decide they're the new leader, both accept writes and the data splits into two histories. Kleppmann: "If there were multiple leaders, they could make inconsistent decisions … (a situation known as split brain)" (§7.1). Picking exactly one leader, even while machines crash and messages vanish, is an instance of consensus. The Raft site defines it: "Consensus involves multiple servers agreeing on values. Once they reach a decision on a value, that decision is final" (raft.github.io).

Raft, by Diego Ongaro and John Ousterhout, "is a consensus algorithm for managing a replicated log", designed to be easier to understand than Paxos, which came before it ("In Search of an Understandable Consensus Algorithm (Extended Version)"). Its leader election rests on five rules, each quoted from §5.1–5.2 of the paper:

  1. Terms number the leaderships. Time is divided into terms, each starting with an election. "Terms act as a logical clock in Raft, and they allow servers to detect obsolete information such as stale leaders": Part 2's idea, used to order leaders.
  2. A newer term always wins. "If a candidate or leader discovers that its term is out of date, it immediately reverts to follower state. If a server receives a request with a stale term number, it rejects the request."
  3. Leaders send heartbeats. "Leaders send periodic heartbeats (AppendEntries RPCs that carry no log entries) to all followers in order to maintain their authority." A follower that hears nothing for an election timeout becomes a candidate: it increments its term, votes for itself, and sends RequestVote to everyone.
  4. One vote per term. "Each server will vote for at most one candidate in a given term, on a first-come-first-served basis … The majority rule ensures that at most one candidate can win the election for a particular term."
  5. Random timeouts break ties. "To prevent split votes in the first place, election timeouts are chosen randomly from a fixed interval (e.g., 150–300ms)."

The program below implements exactly those five rules on five simulated nodes. Each message takes 2–10 ms of virtual time, a crashed node drops everything, and a partition cuts links. It replays one run with a crash, then attacks rule 4 with 2,000 random runs, once with correct voters and once with a voter that "forgets" its vote.

From one leader to one log

A leader by itself isn't the goal. The goal is a replicated log: the same commands, in the same order, on every node, so each node's copy of the data (its state machine) ends up identical. Raft's leader appends each client command to its log and ships missing entries to each follower in the next AppendEntries, so a heartbeat doubles as replication. Three more rules from §5.3–5.4 make it safe:

  • Commit by majority. "A log entry is committed once the leader that created the entry has replicated it on a majority of the servers." Only then is it applied, and only then may a client be told "done".
  • The consistency check. "When sending an AppendEntries RPC, the leader includes the index and term of the entry in its log that immediately precedes the new entries. If the follower does not find an entry in its log with the same index and term, then it refuses the new entries." The paper calls this "an induction step" (L48's induction, holding a whole log in shape). On a refusal the leader steps back one entry and tries again; followers' conflicting, uncommitted entries get overwritten.
  • The election restriction. A candidate can't win unless its log holds every committed entry: "the voter denies its vote if its own log is more up-to-date than that of the candidate", where "If the logs have last entries with different terms, then the log with the later term is more up-to-date. If the logs end with the same term, then whichever log is longer is more up-to-date."

Together they give the two guarantees the final's tests check, both from the paper's Figure 3: Election Safety, "at most one leader can be elected in a given term", and State Machine Safety, "if a server has applied a log entry at a given index to its state machine, no other server will ever apply a different log entry for the same index." And timeouts must be far shorter than the mean time between failures, because "When the leader crashes, the system will be unavailable for roughly the election timeout" (§5.6).

Final answer

Why it works. Each line is one of Raft's rules. A stale term is refused, and a newer one is adopted first, whatever the vote turns out to be: that's how a node with a stale log still learns that the cluster has moved on. votedFor gives one vote per term, and a repeat request from the same candidate gets the same answer. The up-to-date check is the election restriction: a log whose last entry has a later term has heard from a newer leader, however short it is.

Common mistake. Comparing lengths first. A long log full of entries from an old term, which a minority leader accepted but never committed, would then win votes over a shorter log that holds a newer committed entry. That's the final's x=3 trying to come back.

A 5-node Raft cluster is split into groups of 2 and 3. Where can a leader be elected?

Winning needs votes from a majority of the whole cluster: 3 of 5. The group of 2 can never collect 3 votes, so it keeps timing out with rising terms. The group of 3 elects a leader and keeps working.

  1. 2 votes out of 5 isn't a majority, so the group of 2 can only time out and try again.
  2. 3 of 5 is a majority of the whole cluster, so a candidate there can collect enough votes.
  3. Both groups would need a majority of the same 5 nodes, and two majorities need at least 6.
  4. The group of 3 holds a majority of the whole cluster, so it can elect a leader.

An old leader in the minority accepts a client's write after the partition. What happens to that entry?

It can't reach a majority, so the old leader never commits it. After the heal the old leader sees a higher term, steps down, and the consistency check makes it (and any follower it copied the entry to) drop the conflicting entry. The widget shows x=3 going exactly this way.

  1. Committing needs a majority of the whole cluster: 3 of 5. Two copies aren't enough.
  2. Raft never merges logs. The leader's log wins, and conflicting entries are overwritten.
  3. No node applies an entry before it's committed, and this one never is.
  4. It never reaches a majority, and after the heal the consistency check replaces it with the new leader's entry.

Why does each candidate pick a random election timeout?

If every follower timed out together, they'd all vote for themselves and split the vote, over and over. Randomness spreads them out, so one candidate usually asks first and wins before the others wake up. The optional exercise measures how little randomness it takes.

  1. Spread-out timeouts mean one follower usually times out first and collects votes before the others start.
  2. Heartbeats come from the leader on a fixed schedule. Election timeouts don't change their cost.
  3. Terms still number every election. Randomness only changes who starts one first.
  4. Each server still votes at most once per term. Randomness never changes how votes count.

Part 4

Leases and fencing tokens

~25 min

Raft protects itself from a leader that was paused and wakes up stale: its term is out of date, so everyone rejects it. Your own services meet the same problem in a far more ordinary place, the distributed lock. A Spring Boot app runs on three instances, and a row in a database table or a key in Redis makes sure only one of them runs the nightly invoice job or rewrites a shared file. Martin Kleppmann's essay on the subject starts by asking what the lock is for ("How to do distributed locking", 2016):

  • Efficiency: "If the lock fails and two nodes end up doing the same piece of work, the result is a minor increase in cost … or a minor inconvenience (e.g. a user ends up getting the same email notification twice)."
  • Correctness: "If the lock fails and two nodes concurrently work on the same piece of data, the result is a corrupted file, data loss, permanent inconsistency, the wrong dose of a drug administered to a patient, or some other serious problem."

Every distributed lock is a lease, like the one Part 1's practice built: it expires on its own, so a crashed holder can't keep it forever. That's also the trap: "if the GC pause lasts longer than the lease expiry period, and the client doesn't realise that it has expired, it may go ahead and make some unsafe change." Kleppmann notes that "This bug is not theoretical: HBase used to have this problem." And checking the lease first doesn't save you: "You cannot fix this problem by inserting a check on the lock expiry just before writing back to storage. Remember that GC can pause a running thread at any point, including the point that is maximally inconvenient for you (between the last check and the write operation)." A GC pause (L24) isn't the only cause. The essay also lists page faults, a SIGSTOP (L53), and plain network delay: in one GitHub incident "packets were delayed in the network for approximately 90 seconds".

The fix: a number that only goes up

The fix, in Kleppmann's words: "you need to include a fencing token with every write request to the storage service. In this context, a fencing token is simply a number that increases (e.g. incremented by the lock service) every time a client acquires the lock." Client 1 gets token 33 and pauses; its lease expires; client 2 gets 34 and writes. When client 1 wakes up and writes with 33, "the storage server remembers that it has already processed a write with a higher token number (34), and so it rejects the request with token 33."   • Without tokens, the stale write wins silently. Client 2's report is overwritten by one prepared before client 2 even started. That's the same silent loss as last write wins, and no lock service, however good, can prevent it alone.
  • With tokens, the storage says no. The storage is the one place every write passes through, so it's the only place that can notice a token going backwards. As Kleppmann puts it, "this requires the storage server to take an active role in checking tokens". Client 1 learns its lease is gone from the rejection.
  • You've seen this before: Raft's term is a fencing token. "If a server receives a request with a stale term number, it rejects the request" (Raft §5.1): the follower is the storage and the term is the token. The essay makes the same link for lock services built on consensus: with ZooKeeper "you can use the zxid or the znode version number as fencing token".
  • The token must be ordered, not just unique. A random lock value tells you who holds the lock, not who came later. Of Redis's Redlock, Kleppmann writes: "The unique random value it uses does not provide the required monotonicity."

Bridge: ShedLock, a common way to stop a Spring @Scheduled job running on several instances at once, is honest about being an efficiency lock. Its README says it "is designed to be used in situations where you have scheduled tasks that are not ready to be executed in parallel, but can be safely executed repeatedly", and that if a task outlives lockAtMostFor "the resulting behavior may be unpredictable (more than one process will effectively hold the lock)" (ShedLock). So whenever a Redis or database lock in a Spring service protects correctness (money, a file, a row two jobs must never both rewrite), hand out a token with the lock and make the database check it, as in the exercise below, or make the work idempotent (L42). Kleppmann's rule: "please enforce use of fencing tokens on all resource accesses under the lock."

Final answer

Why it works. Tokens only grow, because the lock service hands out the next number on every grant. So a token smaller than one the store has already accepted can only come from a holder whose lease ran out while someone newer took over. The storage is the one place every write passes through, which is why the check lives there and not in the client: a paused client can't know it was paused. @Synchronized makes the check and the write one step, the same idea as the exercise's single conditional UPDATE (and L26's check-then-act race).

Common mistake. Rejecting equal tokens too (token <= seen). The current holder then can't write twice under one lease. Another one: keeping a single highest token for the whole store, so a job holding token 50 for one key blocks every other lock's lower tokens on unrelated keys.

A job checks that its lease is still valid, then writes to storage. Why can it still corrupt data?

The check is true when it runs. A GC pause, a page fault or a slow network can come right after it, and by the time the write arrives the lease has expired and someone else holds it. Kleppmann: GC can pause a thread "between the last check and the write operation".

  1. The lock service never grants overlapping leases by its own clock. The danger is a holder that doesn't know its lease ended.
  2. Part 1's monotonic clock fixes NTP steps, but even a perfect clock can't help a thread that is paused after reading it.
  3. Nothing stops a pause landing after the check, so the write can arrive long after the lease expired.
  4. Even with writes applied in arrival order, the stale write arrives last and overwrites the newer one.

With fencing tokens, which component must compare the tokens?

Every write passes through the storage, so it alone can see a token go backwards after a newer one was accepted. The lock service doesn't see the writes, and the paused client doesn't know it was paused.

  1. It sees every write and remembers the highest token accepted, so it can reject one that went backwards.
  2. It hands out the tokens but never sees the writes, so it can't stop a late one.
  3. It can't know it was paused. From its own point of view, the lease check just passed.
  4. A load balancer forwards requests without understanding tokens or knowing which writes came first.

Two-phase commit vs sagas

~28 min

L36's transactions were all-or-nothing inside one database. Now an order must be saved in orders-db and stock reserved in stock-db, two separate systems, and you want both or neither. "The most common algorithm to ensure atomic commitment across multiple nodes is the two-phase commit (2PC) protocol [Gray, 1978]" (Kleppmann, §6.1). A coordinator runs it in two phases:

  1. Prepare. The coordinator asks each participant "can you commit?". A participant that answers yes must make sure it can commit later, even after a crash, and keeps its locks until told the outcome.
  2. Commit or abort. If every vote was yes, the coordinator writes COMMIT to its own log and tells everyone; any no means ABORT.

The catch is what happens between the phases. A prepared participant has given up the right to decide alone. Kleppmann: "The problem with two-phase commit is that the coordinator is a single point of failure", and the slide beside it adds, "Algorithm is blocked until coordinator recovers."

Both print exactly this:

== 1. Both participants can commit
  votes orders-db=yes, stock-db=yes -> coordinator logs COMMIT
  orders-db=COMMITTED  stock-db=COMMITTED
== 2. stock-db can't (out of stock)
  votes orders-db=yes, stock-db=no -> coordinator logs ABORT
  orders-db=ABORTED  stock-db=ABORTED
== 3. Both vote yes, then the coordinator crashes
  votes orders-db=yes, stock-db=yes -> coordinator logs COMMIT
  coordinator CRASHES before phase 2
  orders-db=PREPARED  stock-db=PREPARED
  after 1s, a reader on orders-db: BLOCKED: row locked by an in-doubt transaction
  after 60s, a reader on orders-db: BLOCKED: row locked by an in-doubt transaction
  after 3600s, a reader on orders-db: BLOCKED: row locked by an in-doubt transaction
  orders-db asks stock-db what to do: it is PREPARED too, so neither knows the decision
  coordinator restarts, reads its log: COMMIT, tells everyone
  orders-db=COMMITTED  stock-db=COMMITTED   reader: ok

Cases 1 and 2 are what 2PC is for: both databases committed, or both aborted. Case 3 is its price. Both participants voted yes, so neither may abort, and neither knows the decision, so neither may commit. The row stays locked for as long as the coordinator is down, an hour in this run, and every reader of that row waits. Real databases document this honestly. PostgreSQL's PREPARE TRANSACTION "prepares the current transaction for two-phase commit", and the manual warns: "It is unwise to leave transactions in the prepared state for a long time", because "the transaction continues to hold whatever locks it held". Its advice for applications is blunt: "Unless you're writing a transaction manager, you probably shouldn't be using PREPARE TRANSACTION". The feature is meant for external transaction managers, "some of which are covered by standards (such as X/Open XA)" (PostgreSQL docs).

The cure for a coordinator that can crash is Part 3. If the votes go through a consensus log instead of one coordinator, any node can learn the outcome. Kleppmann's notes show "a fault-tolerant two-phase commit algorithm based on Paxos Commit [Gray and Lamport, 2006]" (§6.1). That's powerful and heavyweight, and most microservice systems choose something weaker.

Sagas: give up isolation, keep going

The saga pattern drops the global lock altogether: "Implement each business transaction that spans multiple services as a saga. A saga is a reliably coordinated sequence of local transactions" (microservices.io: Saga). Each step commits for real in its own service. If a later step fails, "the changes made by the completed steps are undone by compensating transactions": not a rollback, but a new action that cancels the old one.

The outbox: one local transaction, then a queue

Every saga step has the same problem in miniature: save to my database and send a message to the next service. If you commit and then crash before sending, the message is lost. If you send and then the commit fails, you've announced something that never happened. The transactional outbox asks "How to atomically update the database and send messages to a message broker?" and answers: "The solution is for the service that sends the message to first store the message in the database as part of the transaction that updates the business entities" (microservices.io: Transactional outbox). A separate relay then publishes the stored messages. Its honest caveat: "The Message relay might publish a message more than once. It might, for example, crash after publishing a message but before recording the fact that it has done so." That's L42's at-least-once delivery again, and the answer is the same: an idempotent consumer.

  • Default arguments. Coordinator(crashBeforePhase2 = true) and runSaga(…, afterEach = {}) replace Java's extra constructor and the explicit name -> {}.

Final answer

Why it works. The coordinator may abort on its own any time before it decides, because no participant can have been told COMMIT yet. A timeout is therefore a safe reason to abort. Once it has logged a decision, though, it must stick to it: participants may already be acting on it. Counting participants in a set, not messages, makes a duplicated vote harmless, the same idea as L42's idempotent consumer.

Common mistake. A counter, if (++yesCount == participants.size). When orders-db's yes arrives twice, the counter reaches 2 and the coordinator commits while stock-db has never voted, and might be about to say no.

In two-phase commit, a participant has voted yes and then loses contact with the coordinator. What may it do?

A yes vote is a promise to commit if told to, so aborting alone could break atomicity. But the coordinator might have decided ABORT, so committing alone could break it too. It must wait, and its locks block everyone who needs those rows.

  1. The coordinator might have decided ABORT, for example because another participant voted no.
  2. It promised to commit if asked, and the coordinator may already have decided COMMIT and told the others.
  3. Only the coordinator's decision can release it, so it keeps its locks and waits.
  4. Clients don't know the votes or the decision either, so letting them decide could break atomicity just as easily.

An outbox relay crashes after publishing a message but before marking it sent. What does the consumer see?

On restart the relay finds the row still unsent and publishes it again. The outbox guarantees at-least-once delivery, never exactly-once, so the consumer must be idempotent (L42).

  1. The row is still unsent in the outbox, so the restarted relay publishes it again. Nothing is lost.
  2. The relay can't know it already published, so it publishes again: at-least-once delivery.
  3. The relay reads unsent rows in order, so the repeat arrives before any later message, not out of order.
  4. The broker just receives a second publish. It can't tell it's a duplicate, so it reports no error.

A coordinator that decides from the votes it has received so far. What does this print?

fun decide(votes: Map<String, Boolean>) = if (votes.values.all { it }) "COMMIT" else "ABORT"

all on an empty collection is true, because no element fails the test (vacuous truth, L48). So decide says COMMIT before anyone has voted, and again with only one yes. It never asks who should vote. The practice above fixes this by waiting for every participant's yes.

  1. all over no votes is true, not false: there is no vote that fails the test.
  2. decide sees only the votes received, so it can't know that stock-db hasn't voted yet.
  3. The empty map and the one-yes map both pass all { it }. Only stock-db's no fails it.
  4. decide runs afresh each time, so stock-db's no turns the last result into ABORT.

SAFETY, a model answer. (a) A node becomes leader of term T only after votes from a majority, more than n/2 nodes, all in term T. Each node votes at most once per term, and stores that vote durably, so even a crash and restart can't make it vote again in T. Any two majorities of the same n nodes overlap in at least one node, because together they have more than n members (pigeonhole, L48). So if two candidates both won term T, the shared node voted twice in T, a contradiction. The buggy-voter sweep in Part 3 broke the one-vote rule, and two leaders appeared at once.

(b) An entry is committed only once a majority stores it. Any later candidate needs votes from a majority, so at least one of its voters holds the entry, and the up-to-date check makes that voter refuse a candidate whose log is less up-to-date than its own. What remains is to show that a log at least as up-to-date as the voter's must also contain the entry. That step is the subtle one: the paper's proof in §5.4.3 needs the rule that a leader only counts entries from its current term when committing, which is why deleting that rule breaks safety too (the stretch above). Together they give what the paper calls the Leader Completeness Property: "if a log entry is committed in a given term, then that entry will be present in the logs of the leaders for all higher-numbered terms" (Figure 3). This is a sketch, not the full proof. The red run is (b) failing in practice.

Wrap-up

Exit quiz, recall card, sources

~5 min

L24 + L57: a Raft leader stops for a 2-second garbage-collection pause, with a 150–300 ms election timeout. What happens?

No heartbeats for 2 s means followers time out and elect a new leader in a higher term. When the paused leader wakes, its first contact carries the newer term and it steps down. A stop-the-world pause (L24) looks exactly like a crash from outside, which is why long GC pauses matter in clustered systems.

  1. Followers wait only one election timeout, 150–300 ms, far less than 2 s.
  2. Only briefly: a new leader is elected within a timeout or two and accepts writes again.
  3. Missing heartbeats start an election, and the winner leads a higher term.
  4. The paused leader can't commit anything new, and when it wakes it sees the higher term and steps down.

L56 + L57: why must a Raft node save its term and vote to disk, with fsync, before replying to a RequestVote?

If the vote lived only in memory, a node could vote, crash, restart with no memory of it, and vote for a second candidate in the same term. That breaks the one-vote rule the whole safety argument rests on. L56 showed that only fsync makes a write survive a crash.

  1. A vote saved before replying survives the crash, so the restarted node can't vote again in that term.
  2. fsync makes a reply slower, not faster: it waits for the disk.
  3. Heartbeats are the leader's job. A voter's disk has nothing to do with them.
  4. The leader never reads another node's disk. Nodes share state only through messages.

L32 + L57: a client's write to the leader times out. The leader may or may not have committed it. What makes a retry safe?

A timeout tells you nothing about whether the write committed. With an idempotency key (L32), the service recognises the retry and returns the first result instead of applying it twice. The final's x=3 shows the other half: "accepted" was never a promise.

  1. A longer timeout makes a lost answer rarer, but a retry could still apply the write twice.
  2. A follower doesn't take client writes, and the write still reaches the leader, where it could apply twice.
  3. An election doesn't tell the client whether its write committed, so the retry could still apply it twice.
  4. The service remembers each key's first result, so a repeated request gets that result without being applied again.

L27 + L57: what do the Java memory model's happens-before and Lamport's happened-before have in common?

Both start from program order, add edges (synchronization in the JMM, messages here), and close under transitivity. Neither orders every pair: events with no chain between them are concurrent, and neither uses physical time.

  1. Neither uses physical time. Both are defined by edges between events, not by clocks.
  2. Both start from program order, add edges, and close under transitivity, which gives a partial order.
  3. Neither needs one. Lamport's whole point is ordering events without a shared clock.
  4. Both are partial: events with no chain of edges between them stay unordered, or concurrent.
