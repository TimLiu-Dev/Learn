Executors & Virtual Threads

In L26 you started threads by hand and joined them one by one. Real programs almost never do that. They hand tasks to an executor and get futures back, and since JDK 21 they can give every task its own virtual thread. This lesson covers pools, futures, CompletableFuture pipelines and virtual threads, all measured.

Warm-up

Recall from L10, L14, L26 and L27

~10 min
From memory: no peeking
  1. Write a producer and a consumer that share a BlockingQueue<String> of capacity 2. Which call blocks when the queue is full, and which when it's empty? (L27)
  2. In L26 you started 10,000 platform threads. Each one is a real OS thread. Name two things the OS has to give every one of them. (L26, L22)
  3. Write the Java functional interface for "takes nothing, returns a value, may throw". What is the Kotlin function type for the same shape? (L14)

Thread A writes x = 42, then calls queue.put(x). Thread B calls queue.take(). Is B guaranteed to see 42? (L27)

The java.util.concurrent docs promise that actions before putting an object into a concurrent collection happen-before actions after another thread removes it (Memory Consistency Properties). Executors make the same promise for submitting a task, which this lesson relies on.

Two threads each need locks A and B. Which rule prevents the classic deadlock? (L27)

Deadlock needs a cycle of waiting. If every thread takes A before B, no cycle can form.

Java: future.get() fails because the task threw IllegalStateException. What does get() actually throw? (L10)

The task's exception is wrapped. You read the original with getCause(), the same "Caused by" chain you learned to read in L10. Part 1 shows it.

Why can't a Runnable lambda call Thread.sleep(100) in Java without extra code? (L10, L14)

Thread.sleep throws the checked InterruptedException, and Runnable.run() declares none. You either catch it or use a Callable, whose call() is declared throws Exception. Kotlin has no checked exceptions, so its lambdas don't care.

Part 1

Thread pools and executors

~30 min

A platform thread is an OS thread with its own stack, so creating thousands of them costs real time and memory (L26, L22). Creating one per task also means nothing limits how many run at once. A thread pool fixes both problems: a few long-lived worker threads take tasks from a queue, one after another. In Java the pool hides behind the ExecutorService interface. You submit work and get a Future back, a handle to a result that may not exist yet.

Six 100 ms tasks on three threads take about 200 ms: two "waves". Only three threads ever existed, and each ran two tasks. Executors.newFixedThreadPool(n) "creates a thread pool that reuses a fixed number of threads operating off a shared unbounded queue" (Executors). Notice the word unbounded; it comes back below.

Shutting down: shutdown, shutdownNow, close

The default thread factory creates each thread "as a non-daemon thread" (Executors.defaultThreadFactory), and non-daemon threads keep the JVM running (L26). So a pool you forget to shut down keeps the JVM alive after main returns:

$ perl -e 'alarm 5; exec @ARGV' java ForgotShutdown.java; echo "exit=$?"
main is done
task ran on pool-1-thread-1
exit=142

macOS has no timeout command, so I used Perl's alarm to kill the process after 5 seconds; exit code 142 means "killed by the alarm signal". Both versions were still running when the alarm fired. The pool's idle worker threads were waiting for work that never came. The three ways out, from the ExecutorService docs:

CallRunning tasksQueued tasksWaits?
shutdown()finishstill runno: "does not wait for previously submitted tasks to complete"; use awaitTermination
shutdownNow()interrupted ("best-effort")returned to you, never runno
close() (JDK 19+)finishstill runyes: "waits until all tasks have completed execution and the executor has terminated"

ExecutorService has extended AutoCloseable since JDK 19, so try-with-resources and Kotlin's use both call close() for you. That's why PoolBasics needed no shutdown line. The docs' own example is try (ExecutorService e = Executors.newWorkStealingPool()) { … }.

Inside the pool: ThreadPoolExecutor

The Executors factory methods are shortcuts for ThreadPoolExecutor, whose full constructor shows every decision a pool makes: corePoolSize, maximumPoolSize, keepAliveTime and its unit, the workQueue, a ThreadFactory and a RejectedExecutionHandler. The class docs describe three queuing strategies: a direct hand-off (SynchronousQueue), an unbounded queue, which "admits the possibility of unbounded work queue growth when commands continue to arrive on average faster than they can be processed", and a bounded queue, which "helps prevent resource exhaustion … but can be more difficult to tune and control" (ThreadPoolExecutor). A fixed pool's unbounded queue is why a flood of requests can quietly eat all your memory.

With a bounded queue, a full pool must reject work. Two workers, room for two waiting tasks, six tasks submitted:

With the default AbortPolicy, execute throws RejectedExecutionException, and its message is a snapshot of the pool: 2 threads, 2 active, 2 queued. With CallerRunsPolicy, "the thread that invokes execute itself runs the task. This provides a simple feedback control mechanism that will slow down the rate that new tasks are submitted." You can see [main] finished task 5: while main was busy running task 5 it couldn't submit anything, which is backpressure. The two CallerRuns runs differ. In Java, the pool was still full when task 6 arrived, so main ran that one too. In Kotlin the workers had freed up first. That's a race you can't control, and it's fine, because both outcomes are correct. The other two policies silently drop work: DiscardPolicy is "designed only for those rare cases in which task completion is never relied upon", and of DiscardOldestPolicy the docs say "This policy is rarely acceptable".

How big should a pool be?

For CPU-bound work, more threads than cores just take turns on the same cores. Same 144 prime-counting tasks, different pool sizes:

availableProcessors = 18
  1 threads:   3023 ms   (1365511 primes)
  4 threads:    806 ms   (1365511 primes)
 18 threads:    221 ms   (1365511 primes)
 72 threads:    216 ms   (1365511 primes)
availableProcessors = 18
  1 threads:   3208 ms   (1365511 primes)
  4 threads:    815 ms   (1365511 primes)
 18 threads:    232 ms   (1365511 primes)
 72 threads:    215 ms   (1365511 primes)

4 threads are about 3.8× faster than 1. 18 threads are about 14× faster, not 18×, because 12 of this machine's cores are slower efficiency cores. 72 threads buy nothing over 18. Java Concurrency in Practice §8.2 ("Sizing thread pools") gives the rule: for compute-intensive tasks, about Ncpu + 1 threads. For tasks that also wait, size for the wait: Nthreads = Ncpu × Ucpu × (1 + W/C), where Ucpu is the target CPU use (0 to 1) and W/C is the ratio of wait time to compute time. A task that waits 90 ms for every 10 ms of work (W/C = 9) on 18 cores at full use wants about 18 × 1 × 10 = 180 threads. Hold that number for Part 3.

Three tasks threw, but only two left any trace. "boom in submit" vanished completely. submit catches whatever the task throws and stores it in the Future, and nobody ever called get() on that future. execute returns no future, so the exception escapes to the worker thread's uncaught-exception handler, which prints the trace (and the pool replaces the dead worker). The rule: if you submit, you must eventually get(), or the failure is silently lost. In production this is a classic "the job just stopped and nothing was logged" bug.

Bridge: a classic Spring MVC app is the "thread per request" model on a pool. The embedded Tomcat server runs each HTTP request on one of its worker threads, and Spring Boot's server.tomcat.threads.max property, "Maximum amount of worker threads", defaults to 200 (Spring Boot application properties). That's a ThreadPoolExecutor under another name: when all 200 are blocked waiting on a slow database, request 201 waits in the queue.

What Kotlin does for you.
  • No checked exceptions. Thread.sleep inside a Runnable lambda just works. Java's Bounded.java needs a try/catch around every sleep, or a Callable instead.
  • No "effectively final" copy. Java needs int taskId = id; before the lambda (L14). Kotlin's for (id in 1..6) creates a fresh val each iteration, which the lambda can capture directly.
  • use works on any AutoCloseable, including an ExecutorService: inline fun <T : AutoCloseable?, R> T.use(block: (T) -> R): R, available on the JVM since Kotlin 1.2 (API). It also returns the block's value, which Sizing.kt uses to return the total straight out of the pool.
  • Property syntax for Java getters: pool.queue.size, pool.largestPoolSize (L9).

The surprise is that tasks 5 and 6 start before 3 and 4. The order of decisions comes straight from the class docs: below the core size, create a thread (tasks 1, 2). Otherwise queue the task (3, 4). Only when the queue is full, create extra threads up to the max (5, 6 get brand-new worker-3 and worker-4 and run at once). When that's exhausted too, reject (7–10). So the queued tasks 3 and 4 wait while later arrivals run first. Most people expect the pool to grow to its max before queuing; it doesn't. That's also why a max size does nothing at all with an unbounded queue.

Check

Your program's main finishes, but the process never exits. The most likely cause?

Pool worker threads are non-daemon, so they keep the JVM alive. Virtual threads are daemon threads and don't (Thread docs). Use try-with-resources / use.

You submit a task that throws, and never call get() on its future. What appears on the console?

submit stores the exception in the Future. With no get(), it's silently lost, as "boom in submit" was in LostException.

A pool has core 2, max 10 and an unbounded LinkedBlockingQueue. Under heavy load, how many threads will it create?

Extra threads are only created when the queue is full, and an unbounded queue is never full. The docs: "no more than corePoolSize threads will ever be created. (And the value of the maximumPoolSize therefore doesn't have any effect.)"

Pure CPU work on a machine with 8 identical cores. Which pool size is the sensible starting point?

CPU-bound work wants about one thread per core (JCiP §8.2 says Ncpu + 1). More threads only take turns, as 72 vs 18 showed in Sizing.

Part 2

Futures and CompletableFuture

~25 min

A Future<T> lets you wait for one result. get() blocks with no limit, get(timeout, unit) gives up with a TimeoutException, and cancel(true) interrupts the task. To wait on a batch, invokeAll "executes the given tasks, returning a list of Futures holding their status and results when all complete", and invokeAny returns "the result of one that has completed successfully" (ExecutorService).

gave up waiting after 100 ms; cancel = true
invokeAll: [a after 300 ms, b after 100 ms, c after 200 ms] in 306 ms
invokeAny: mirror-2 after 100 ms in 105 ms
gave up waiting after 100 ms; cancel = true
invokeAll: [a after 300 ms, b after 100 ms, c after 200 ms] in 304 ms
invokeAny: mirror-2 after 100 ms in 103 ms

invokeAll took as long as the slowest task (300 ms, not 600), and its results come back in submission order, not finishing order. invokeAny returned the fastest mirror after about 100 ms and cancelled the rest.

CompletableFuture: futures you can chain

A plain Future only lets you wait. CompletableFuture lets you say what should happen next, without blocking a thread to wait for it. Each method returns a new stage:

MethodDoesLike (L14)
supplyAsync(s, ex)run s on executor exstart a task
thenApply(f)transform the result with fmap
thenCompose(f)f returns another future: flatten itflatMap
thenCombine(other, f)when both are done, combine themzip

Async methods without an executor argument run on ForkJoinPool.commonPool(): "All async methods without an explicit Executor argument … are performed using the ForkJoinPool.commonPool()" (CompletableFuture). The common pool is shared by everything in the JVM and sized for CPU work, so blocking I/O belongs on your own executor, as below.

The classic shape is "fetch the user, then the user's orders, and meanwhile the price list, then price the order":

Sequential: 200 + 300 + 250 ≈ 780 ms. Async: about 506 ms, because the prices (250 ms) are fetched while user → orders (500 ms) runs, so the total is the length of the longest path, not the sum. Building the pipeline took 3 ms and blocked nothing. Only join() waits. The orders call depends on the user, so it must come after it: thenCompose expresses that dependency.

Why thenCompose and not thenApply? If the function returns a future, thenApply wraps it in another one:

nested.join()        = java.util.concurrent.CompletableFuture@7f31245a[Completed normally]
nested.join().join() = user-42
flat.join()          = user-42

That's exactly map vs flatMap on a list of lists (L14). Both languages print the same three lines; only the hash differs.

When stages fail

exceptionally saw: java.util.concurrent.CompletionException: java.lang.NumberFormatException: For input string: "80x0"
port = 8080
handle -> ok 443
whenComplete logged: NumberFormatException
join threw CompletionException, cause NumberFormatException
get threw ExecutionException, cause NumberFormatException
completeOnTimeout -> cached answer
orTimeout -> java.util.concurrent.TimeoutException
done

Both languages printed exactly these lines. In order:

  • A failed stage skips every later thenApply: "never printed" never printed. The failure flows down the chain until something handles it, like an exception unwinding the stack (L10).
  • The exception arrives wrapped in CompletionException. join() throws that unchecked wrapper, while get() throws the checked ExecutionException. Either way, the real problem is getCause().
  • completeOnTimeout and orTimeout give a stage a deadline. They complete the future, but they don't stop the work behind it, as the exercise below shows.
  • The last runAsync threw, and nothing was printed: no handler, no join, no trace. It's the same silent loss as submit without get.

Pitfalls to avoid: calling a blocking get()/join() inside a stage (that thread sits idle and the pool can run out of threads); doing blocking I/O on the common pool; and ending a chain without exceptionally/handle or a final join.

What Kotlin does for you.

Part 3

Virtual threads

~30 min

The JCiP formula from Part 1 said a task that mostly waits wants hundreds of threads, and a server with 10,000 waiting connections would want 10,000. Platform threads are too expensive for that, which is why pools and async callbacks exist. Virtual threads, final since JDK 21 (JEP 444), change the trade-off. From the Thread docs: "Virtual threads are typically user-mode threads scheduled by the Java runtime rather than the operating system. Virtual threads will typically require few resources and a single Java virtual machine may support millions of virtual threads. Virtual threads are suitable for executing tasks that spend most of the time blocked, often waiting for I/O operations to complete. Virtual threads are not intended for long running CPU intensive operations."

The mechanism is the third tab of the diagram above. JEP 444: "The platform thread to which the scheduler assigns a virtual thread is called the virtual thread's carrier." When a virtual thread blocks, it unmounts: its stack frames move to the heap and the carrier is free to run another one. You write plain blocking code (Thread.sleep, a socket read), and the JDK does the juggling. The API is the same Thread class in both languages:

  • Virtual threads: 10,000 one-second sleeps take 1.04 s, and so do 100,000, near enough. A million take 5.2 s, mostly spent creating and scheduling them, and the JVM never had more than 26 platform threads: 18 carriers plus the JVM's own housekeeping threads.

  • A platform thread per task works at 10,000, but it needed 735 MB of RAM and 8,863 OS threads at peak (some tasks had already finished). A million of them isn't something to try on your laptop. I didn't.

Pinning: when a virtual thread can't let go

JEP 444 listed two cases where a blocked virtual thread stays stuck to its carrier, called pinning: "When it executes code inside a synchronized block or method" and "When it executes a native method or a foreign function." JDK 24 removed the first case. JEP 491, "Synchronize Virtual Threads without Pinning", lets a virtual thread unmount even while it holds a monitor. Some cases remain. JEP 491 lists "When blocking inside a class initializer. This is also a case where the virtual thread pins the carrier due to a native frame on the stack." Here's a test with one carrier thread, so pinning shows up directly as lost time:

-Djdk.virtualThreadScheduler.parallelism=1 limits the scheduler to one carrier. On JDK 26 (both languages), and then on the JDK 21 that Gradle keeps in ~/.gradle/jdks for comparison (the same Pinning.java):

$ java -Djdk.virtualThreadScheduler.parallelism=1 Pinning.java
java 26

1 class init + 3 plain sleeps (300 each)  603 ms
$ ~/.gradle/jdks/…21…/bin/java -Djdk.virtualThreadScheduler.parallelism=1 Pinning.java
java 21
4 x sleep(300) inside synchronized       1216 ms
1 class init + 3 plain sleeps (300 each)  610 ms
  • synchronized on JDK 21: 4 × 300 = 1,216 ms. Each virtual thread held the only carrier while it slept, so they ran one after another.
  • synchronized on JDK 26: 305 ms. All four slept at the same time, monitors and all. That's JEP 491. Kotlin's synchronized(lock) { } is an inline stdlib function that compiles to the same monitorenter/monitorexit bytecodes (I checked with javap, L23), so it behaves identically.
  • Class initializer, on both JDKs: about 600 ms instead of 300. While SlowInit's initializer slept, the carrier was pinned and the three plain sleepers couldn't even start until it let go.

Rules for using virtual threads

  • Don't pool them. JEP 444 says it directly: "Do not pool virtual threads". They're cheap enough to create one per task and throw away. A pool exists to ration expensive threads, and these aren't expensive.
  • To limit access to something scarce, use a semaphore, "constructs specifically designed for that purpose, such as semaphores" (JEP 444). A database with 10 connections, 1,000 virtual threads:
1000 queries, at most 10 at once, 2345 ms
1000 queries, at most 10 at once, 2351 ms

1,000 queries of 20 ms through 10 permits is 100 rounds, about 2 s plus overhead. Waiting on acquire() parks the virtual thread, which costs no carrier.

  • Be careful with ThreadLocal. With a pool, a thread-local is one object per worker. With a virtual thread per task, it's one per task, possibly a million. The JDK itself "removed many uses of thread locals from the JDK's java.base module in preparation for virtual threads … in order to reduce memory footprint when running with millions of threads" (JEP 444). The replacement for passing context down a call chain is scoped values, final in JDK 25 (JEP 506), which offer "lower space and time costs, especially when used together with virtual threads".
  • CPU-bound work gains nothing, as shown above. Use a fixed pool sized to your cores.

Structured concurrency (PREVIEW in JDK 26)

With virtual threads, "fork a thread for each subtask" becomes cheap, which raises the question who waits for them, and what happens when one fails? Structured concurrency answers it: subtasks live inside a scope, the scope waits for all of them, and a failure cancels the rest. In JDK 26 the API is a preview, its sixth (JEP 525), so it may still change, and you must opt in with --enable-preview. The JEP's own example shape:

$ java Structured.java
Structured.java:1: error: StructuredTaskScope is a preview API and is disabled by default.
import java.util.concurrent.StructuredTaskScope;
                           ^
  (use --enable-preview to enable preview APIs)
$ java --enable-preview Structured.java
Ada has order #7 (208 ms)
failed after 105 ms: java.lang.IllegalStateException: order service down

The success case takes 208 ms, the slower of the two subtasks. In the failure case the scope gave up after 105 ms: when fetchOrder failed at 100 ms, the scope cancelled findUser instead of waiting out its 200 ms. The JEP: "if any subtask fails then the join method throws an exception and the scope is cancelled", and close "always waits for threads executing subtasks to finish". No subtask can outlive the block that started it. Kotlin coroutines are built on exactly this model, and it's the heart of L29.

Calling it from Kotlin works, with two surprises I hit:

$ java --enable-preview -jar structured.jar
Ada has order #7 (211 ms)
failed after 110 ms: java.lang.IllegalStateException: order service down
  1. My first version wrote scope.fork<String> { findUser() } and printed null has order #null. fork is overloaded for Callable and Runnable, and Kotlin resolved the bare lambda to fork(Runnable), which throws the result away. That version is saved as err/StructuredRunnable.kt. Wrapping the lambda in Callable { … } fixes it. Watch for this with every Java API that overloads Callable/Runnable.
  2. kotlinc doesn't know about Java preview features, so it compiled this with no flag, and the jar even ran without --enable-preview. Don't rely on that. A preview API can change or disappear in the next JDK, which is exactly what "preview" means.

Bridge: Spring Boot can switch to virtual threads with one property, spring.threads.virtual.enabled, "Whether to use virtual threads", defaulting to false. The server.tomcat.threads.max entry quoted in Part 1 notes: "Doesn't have an effect if virtual threads are enabled." (application properties). Thread-per-request without the 200-thread ceiling is exactly the trade-off measured above.

What Kotlin does for you.
  • Nothing special for virtual threads themselves: Kotlin uses the same Thread and Executors API, and every number above matched between the languages.
  • Lambdas convert to Runnable, so builder.start { … } and Thread.startVirtualThread(job) take Kotlin lambdas or function values directly. The flip side is the fork overload trap: when a Java method takes either a Runnable or a Callable, say which you mean.
  • object SlowInit { init { … } } is Kotlin's version of a static { } initializer (L6, L23), and it pins in the same way.
  • Coroutines (L29) are Kotlin's own answer to the same problem: lightweight tasks that suspend instead of blocking, with structured concurrency built into the library rather than in preview.

Fetch 1,000 URLs four ways

No real network: a "fetch" sleeps for a fixed but random-looking 50–200 ms, and about 2% fail with an IOException. Build it from a blank file, Kotlin first and then Java, without looking at the parts above until you've rated yourself.

Reading the numbers (on my machine):

  • Sequential pays every delay in turn: 13.3 s for 100 pages, 125.8 s for all 1,000.
  • 16 threads divide that by about 16: 125.8 / 16 ≈ 7.9 s, measured 8.1 s. The pool is the bottleneck, because 984 tasks are always waiting in its queue.
  • 100 threads divide it by about 100: ≈ 1.3 s, measured 1.4 s. That's the JCiP sizing formula in action: these tasks are almost all waiting, so more threads keep helping.
  • Virtual threads run all 1,000 waits at once. The run takes about as long as the slowest single page (200 ms), plus overhead: 209 ms. That's 600× faster than sequential, with no thread count to tune.
  • Every concurrent version reports exactly 976 ok, 24 failed and the same first failure, because the "network" is seeded. If one of your versions reports fewer failures, it's swallowing exceptions. Typical causes are a submit with no get, or an allOf(...).join() that throws on the first failure before you've collected the rest.

Two details in the solutions. First, allOf(...).join() would itself throw if any future failed, which is why each future gets a handle first, turning every outcome into a value. Second, the Java supplyAsync lambda must catch IOException and rethrow it as CompletionException, because Supplier can't throw checked exceptions. Kotlin doesn't have that problem.

Wrap-up

Exit quiz, recall card, sources

~5 min

L22 + L28: why can a JVM hold a million virtual threads but not a million platform threads?

Every platform thread is a real OS thread with a fixed native stack and kernel bookkeeping (L22). A virtual thread is a heap object whose stack is only as big as it needs to be.

L16 + L28: a fixed pool of k threads runs n independent tasks of 1 s each (n much larger than k). The wall time grows like…

The tasks run in waves of k: 2,000 tasks / 200 threads = 10 s, and 10,000 / 200 = 50 s. Doubling n doubles the time.

L24 + L28: which JFR event tells you a virtual thread blocked while stuck to its carrier?

"jdk.VirtualThreadPinned indicates that a virtual thread was parked while pinned" (JEP 444). On JDK 26 it also reports the reason, here SlowInit.<clinit>.

L26 + L28: 1,000 virtual threads each do count++ on a shared Int field. The final value is…

Virtual threads are still threads running in parallel on many carriers. count++ is still a read-modify-write race (L26), so use an atomic, a LongAdder or a lock.
