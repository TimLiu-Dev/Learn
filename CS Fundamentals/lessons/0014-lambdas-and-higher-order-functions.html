Part 1

Functions as values

~30 min

A higher-order function takes a function as a parameter, or returns one (Kotlin docs). To do that, a language needs a way to treat a function as a value: store it in a variable, pass it, call it later. A lambda is a function written inline, with no name. Here's the same program in both languages:

Kotlin has function types. Java has functional interfaces.

  • Kotlin has real function types: (Int) -> Int means "takes an Int, returns an Int". () -> Unit takes nothing and returns nothing useful. The Unit "cannot be omitted", and a nullable function type needs parentheses: ((String) -> Unit)? (Kotlin docs: Function types). You call a function value like a function, f(x), or as f.invoke(x), which is handy with ?..
  • Java has no function types. A lambda must target a functional interface, "an interface that has only one abstract method" (dev.java: Your first lambda). The lambda becomes an object implementing that interface, and you call it by the interface's method name: apply, test, run, accept… You have to remember which.
  • Lambda syntax. Kotlin: { x -> x * 2 }, always in braces. A single parameter can be left unnamed and called it (docs). The value of the last expression is the result, with no return. Java: x -> x * 2, or x -> { …; return …; } for a block.
  • Trailing lambdas. "If the last parameter of a function is a function, then a lambda expression passed as the corresponding argument can be placed outside the parentheses" (docs). That's why retry(3) { … } looks like a built-in control structure. And it answers the warm-up: require(ok) { "msg" } passes a lambda that builds the message only when it's needed.

The JDK supplies standard functional interfaces in java.util.function. dev.java groups them into "4 categories": suppliers, consumers, predicates and functions (dev.java: Using lambdas).

Why do the primitive versions exist? Generics only work with objects (L13), so a Function<Integer, Integer> boxes every int into an Integer and unboxes it again (L5). dev.java says plainly that "this boxing / unboxing does not come for free". IntPredicate takes a real int, "in that way, no boxing is made". That's why retry uses IntPredicate.

Under the hood: what a lambda compiles to

A lambda doesn't get its own .class file. The compiler moves the body into a private method and creates the object at runtime with an invokedynamic instruction, which calls the JDK's LambdaMetafactory. Part 2

Closures and capture

~20 min

A lambda can use variables from the scope around it. Together with the variables it captures, it's called a closure. The two languages disagree about one thing: can the lambda change what it captured?

Capture.java:6: error: local variables referenced from a lambda expression must be final or effectively final
        List.of(3, 4, 5).forEach(n -> total += n);   // modify a captured local
                                      ^

The Kotlin version compiles and prints 12.

  • Java: "Any local variable, formal parameter, or exception parameter used but not declared in a lambda expression must either be final or effectively final" (JLS §15.27.2). Effectively final means you never reassign it after initialisation, even without writing final (JLS §4.12.4). The lambda gets a copy of the value, and the rule makes sure that copy can never go stale.
  • Kotlin: "The variables captured in the closure can be modified in the lambda" (Kotlin docs: Closures). The visualiser below shows how.

Java programmers work around the rule by capturing a mutable object. The reference is effectively final, but the object it points to isn't (L5's "val is not immutable" again):

The loop-capture puzzle

A classic bug in many languages: build a list of lambdas inside a loop, call them afterwards, and every one returns the last value. Predict both lines before reading the output:

[1, 2, 3]
[4, 4, 4]
[1, 2, 3]
[1, 2, 3]
  • Kotlin for (i in 1..3): each iteration gets a fresh, read-only i, so each lambda captures a different one: 1, 2, 3.
  • Kotlin, capturing a var: all three lambdas share one heap box for j. By the time they run, the loop has pushed it to 4. Kotlin's freedom to capture a var brings back the trap.
  • Java enhanced for: like Kotlin's for, a fresh i per iteration, so it compiles.
  • Java C-style for: j++ reassigns j, so it isn't effectively final, and Java refuses to let you write the bug:
LoopCapture.java:9: error: local variables referenced from a lambda expression must be final or effectively final
            actions.add(() -> j);      // j changes every iteration
                              ^

The fix in Java (and the habit worth keeping in Kotlin) is to copy into a fresh local each time round: int copy = j;.

A lambda is not a shorthand for an anonymous class. What Kotlin does for you. Capturing and changing a var just works, because the compiler builds the Ref box that Java makes you build by hand with int[] or AtomicInteger. Part 3

Collection operations vs Java Streams

~25 min

Most loops you write over a collection do one of a few jobs: transform each item, keep some items, combine them into one answer, or group them. The standard library has a named higher-order function for each job. Kotlin puts them directly on collections (Kotlin docs: Collection transformations). Java puts them on streams: call .stream(), chain operations, then finish with a terminal operation such as toList() or collect(…) (dev.java: Terminal operations). One workout log, nine questions:

The details that bite:

  • Ordering of groups. Kotlin's groupBy "preserves the entry iteration order of the keys produced from the original" collection (API). Java's groupingBy makes "no guarantees on the type" of the map (Collectors), so the Java version asks for a LinkedHashMap to match.
  • Counting. Kotlin's groupingBy { }.eachCount() gives Ints. Java's counting() gives Longs.
  • "Maybe no answer". Kotlin returns null (maxByOrNull, firstOrNull), which works with ?. and ?: (L3). Java's max and findFirst return an Optional, "an empty Optional if the stream is empty" (Stream docs).
  • Sums. Kotlin's sumOf { } works directly. In Java you convert with mapToInt to an IntStream, which has sum(), the primitive-stream version of the boxing story from Part 1.
  • Comparators. compareByDescending { }.thenBy { } vs Comparator.comparingInt(…).reversed().thenComparing(…). Same idea: build a comparator out of key-extracting functions.
  • Java inference has limits. Passing log.stream().collect(groupingBy(Workout::sport, LinkedHashMap::new, …)) straight into println fails to compile: inference variable R "has incompatible bounds", because println is overloaded. Assigning the result to a typed variable first fixes it, and it reads better anyway.

When a loop is clearer

Effective Java Item 45 is titled Use streams judiciously. Chains are great for "transform, filter, group, summarise". Loops are often clearer when you need to break out early with complex conditions, update several things at once, or when the chain would need comments to follow. Two firm rules:

  • No side effects inside map/filter. They should compute values, not print, add to outside lists, or bump counters (Item 46). Use forEach at the end of a chain for the one effect you want.
  • Name things. A chain that groups, then sums, then sorts reads better split into val totals = … and val ranked = ….

Bridge: frameworks are built on these interfaces. Android's click handler, View.OnClickListener, has one method, onClick(View), so Kotlin code passes it a lambda. Spring's RowMapper is documented as "a functional interface and can therefore be used as the assignment target for a lambda expression or method reference".

What Kotlin does for you.
  • Operations live on the collection itself: no .stream() at the start, no .toList()/collect(…) at the end.
  • Results are ordinary Lists and Maps, with read-only types, and groupBy keeps insertion order.
  • null instead of Optional, so the L3 tools ?., ?: and let apply.
  • sumOf, partition, zip, mapNotNull, chunked, windowed and associateWith are built in, and destructuring makes val (long, short) = … one line.

Part 4

Write your own: map, filter, fold, and inline

~20 min

None of these operations is magic. Each is a short loop that takes a function. Writing them yourself is the best way to be able to use them without thinking, and it puts L13's generics to work:

fold is the general one. map is a fold that appends f(item) to the accumulator, and filter is a fold that appends only some items. The Kotlin acc + item version builds a new list on every step, which is fine for learning but slow for big lists. L16 (Big O) explains why the real map uses a loop and one ArrayList.

Why the JDK's signatures are full of ? super and ? extends

The real Stream.map is declared <R> Stream<R> map(Function<? super T, ? extends R> mapper) (Stream docs). That's PECS from L13. The function consumes Ts, so ? super T, and produces Rs, so ? extends R. Without the wildcards, the last call in MyOps fails, even though a function that accepts any Object can obviously accept a String:

StrictMap.java:15: error: method strictMap in class StrictMap cannot be applied to given types;
        List<CharSequence> tags = strictMap(words, describe);
                                  ^
  required: List<T>,Function<T,R>
  found:    List<String>,Function<Object,String>
  reason: inference variable T has incompatible equality constraints Object,String

Kotlin's myMap has no wildcards, yet words.myMap(describe) compiled. Kotlin's function types already carry the variance: the spec defines (A) -> R as Function1<in P1, out R>, "please note the variance of type parameters" (Kotlin spec: Function types). So an (Any) -> String is an (String) -> CharSequence. That's declaration-site variance (L13), declared once in the library instead of at every use.

inline: why map and forEach cost nothing

The Kotlin docs are frank: "Using higher-order functions imposes certain runtime penalties: each function is an object, and it captures a closure" (Kotlin docs: Inline functions). Part 1's javap showed the boxing too. Marking a function inline fixes this: "the inline modifier affects both the function itself and the lambdas passed to it: all of those will be inlined into the call site". The compiler pastes the loop and your lambda body into the caller, so no function object is created. The stdlib's map, filter, forEach and fold are all declared inline fun (API: map).

Remove inline from timesDo, and the lambda becomes a real object that could be called later, after firstOver has returned. So a bare return is no longer allowed:

    timesDo(10) { i -> if (i * i > limit) return i }
                                          ^^^^^^

Two modifiers, briefly. noinline keeps one lambda parameter as a real object, so you can store it. "noinline lambdas, however, can be manipulated in any way you like, including being stored in fields" (docs). crossinline marks a lambda that is inlined but runs "from another execution context, such as a local object", so it "cannot use non-local returns":

Without crossinline, the compiler refuses:

Crossinline.kt:1:59: error: cannot inline 'task: () -> Unit' here: it might contain non-local returns. Add 'crossinline' modifier to parameter declaration 'task: () -> Unit'.

When should you write inline? Mostly for small, general-purpose functions that take lambdas, like your own myCount in the exercise below. And always for reified (L13). Don't inline big functions: their body is copied into every call site.

What Kotlin does for you.
  • inline removes the cost of lambdas for the standard operations: no object, no boxing, no virtual call.
  • It also lets a lambda return from the enclosing function, so forEach behaves like a real loop.
  • Function types carry in/out variance, so myMap needs no wildcards. Java makes you write Function<? super T, ? extends R> on every parameter, or your API is needlessly rigid.

Exit quiz, recall card, sources

~5 min

A lambda stored as val f: (Int) -> Int is called a million times. Where do the extra Integer objects come from? (L5, L13)

Function1<P1, R> is generic, and generics work on objects, so Ints are boxed (Part 1's Integer.valueOf). The Integer cache from L5 covers only −128…127.

Kotlin's require(x > 0) { "bad: $x" } builds the message string… (L10)

The braces are a trailing lambda, called only on failure. That's the warm-up answer.

Where is the lambda object returned by makeCounter() stored? (L4)

Every object lives on the heap. main's frame holds a reference to it in a, and the lambda in turn references its captured box.

Which declaration makes Kotlin's (Any) -> String usable where (String) -> CharSequence is expected? (L13)

Parameters are consumed (in), and results are produced (out). It's PECS, declared once in the library.
