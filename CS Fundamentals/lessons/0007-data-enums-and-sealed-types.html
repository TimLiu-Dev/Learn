Part 1

Value classes three ways

~30 min

Some classes are things with identity: a bank account, a user session, where two separate ones are different even if their fields match. Others are just values: a point, an amount of money, a date. Two Money(12.50, EUR)s should be interchangeable, just as two 5s are. In L5 you saw that plain classes compare by identity. A value class has to override equals, and once it does, also hashCode and, to be readable, toString. Effective Java devotes Items 10, 11 and 12 to exactly these three methods (Bloch, 3rd ed.).

Every equals follows the same three steps: same object? Right type? Then compare the fields that define the value. hashCode must combine the same fields, because "if two objects are equal according to the equals method, then calling the hashCode method on each… must produce the same integer result". The reverse isn't required: unequal objects may share a hash code (Object.hashCode docs). Java's Objects.hash(x, y) does the combining for you. Without toString, you.d see something like Hand$Point@1b6d3586, which is the class name, an @, and the hash in hex (Object.toString docs).

What breaks if you forget hashCode

Hash-based collections (HashSet, HashMap, and Kotlin's default setOf/mapOf) use the hash code to decide where to look first, and only then call equals. If equal objects have different hash codes, the collection looks in the wrong place:

2
null

equals says the points are equal, yet the set can't find one, accepts a "duplicate", and the map can't look up its own key. Neither compiler warns you. That's why the rule is "override both or neither". In L19 you'll build a hash table yourself and see exactly where the lookup goes wrong.

Way 2: Java record

Since JDK 16, a one-line record declares a "transparent carrier for immutable data" (JEP 395). For each component, Java generates a private final field and a public accessor with the same name (cents(), not getCents()), plus a canonical constructor and equals, hashCode and toString. A compact constructor lets you validate the arguments; the fields are assigned automatically afterwards. Records are implicitly final and can't extend another class, but they can implement interfaces (JEP 395; dev.java: Using records).

Way 3: Kotlin data class

Kotlin's data class derives these members "from the properties in the primary constructor": equals()/hashCode(), toString() in the form User(name=John, age=42), componentN() functions, and copy() (Kotlin docs: Data classes). Validation goes in an init block with require.

Four details to notice:

  • copy builds a new object with some properties changed: price.copy(cents = …). That's how you "update" immutable data. Java records have no copy, so you call the constructor again, or write a small withX method yourself (you'll do this in the final).
  • Destructuring: val (cents, currency) = price calls component1() and component2(), in constructor order (Kotlin docs). Java 21 has its own version, record patterns, which you'll meet in Part 3.
  • Only the primary constructor counts. Tagged's note is declared in the class body, so equals and toString ignore it, and two Taggeds with different notes are "equal". The docs put it plainly: "The compiler only uses the properties defined inside the primary constructor for the automatically generated functions."
  • It's only shallow immutability. Look at Order: its fields are final, but the list it points to changed anyway. That's L5's "final reference isn't an immutable object", all over again.

Step through the shallow-copy trap below. copy() "creates a shallow copy of the instance… references to other objects are shared" (Kotlin docs):

The fix is the same as in L5: use read-only List components with a defensive copy (toList() / List.copyOf in the compact constructor), so nothing mutable is shared.

What Kotlin does for you. Compare the Point class in Hand.java (about 30 lines) with data class Point(val x: Int, val y: Int) (one line). The compiler writes equals, hashCode and toString, plus two things a Java record doesn't give you: copy() with named arguments, and componentN() for destructuring. And because the methods are generated, they can never drift out of sync when you add a field, which is the classic hand-written bug.

Part 2

Enums

~15 min

An enum is a type with a fixed set of named instances, created once and shared. Unlike plain constants, an enum constant is a real object. It can carry properties, have methods, and implement interfaces (Kotlin docs: Enum classes; dev.java: Enums).

Because there's exactly one object per constant, comparing enums with == is safe in both languages: identity and equality coincide. And because the set of constants is closed, a when or a switch expression that covers every constant needs no else/default.

Why not just use strings or ints?

Code like shippingDays("express") compiles even when someone types "Express" or "exprss". The typo only shows up as wrong behaviour at runtime, if you're lucky. With an enum, Shipping.EXPRSS is a compile error, your IDE can list every valid option, and each option can carry its own data. Effective Java Item 34 is titled exactly this: "Use enums instead of int constants".

What Kotlin does for you. The constant's data lives right in the header, as in enum class Size(val ml: Int), while Java needs a field, a constructor and an accessor. entries gives you an immutable list rather than a fresh array on every call. And an exhaustive when works as both a statement and an expression.

Part 3

Sealed types

~25 min

Enums give you a fixed set of instances. Sometimes you need a fixed set of kinds, each carrying different data. A payment can succeed (with a transaction id), be declined (with a reason), or fail (retryable or not). A sealed interface or class declares that closed family: "all direct subclasses of a sealed class are known at compile time" (Kotlin docs: Sealed classes). In Kotlin, they "must be declared in the same package", and none can appear outside the module. In Java, the permits clause lists them, and each permitted subclass must be final, sealed or non-sealed. Records are implicitly final, so they fit perfectly (JEP 409, JDK 17).

paid, id tx-42
declined: insufficient funds
failed, try again
  • Kotlin: when with is Success -> checks the type, then smart-casts, so result.transactionId works with no cast. "In such cases, you don't need to add an else clause" (Kotlin docs).
  • Java 21: switch can match patterns (JEP 441). case Success s is a type pattern, which binds s already cast. case Declined(String reason) is a record pattern, which pulls the component straight out (JEP 440). When the cases cover every permitted subtype, "this switch block is exhaustive. As a result, no default label is needed" (JEP 441). See also dev.java: Using pattern matching.

The real payoff: adding a case

Six months later, someone adds Pending. Every when/switch that doesn't handle it now fails to compile. The compiler hands you a to-do list:

PaymentsNew.kt:8:47: error: 'when' expression must be exhaustive. Add the 'is Pending' branch or an 'else' branch.
PaymentsNew.java:12: error: the switch expression does not cover all possible input values

Now compare a version written "defensively" with else/default:

failed

It compiles cleanly and reports a pending payment as failed. The catch-all threw away the exact check the sealed type existed to give you. Rule: when switching over a sealed type or an enum, list every case and leave out else/default. (If a class compiled against the old version meets a new subtype at runtime, Java's compiler-inserted fallback throws a MatchException rather than guessing, according to JEP 441.)

Kotlin needs no permits list, since the compiler finds the subclasses in the package. You also don't name a variable in each branch: after is Success ->, result simply is a Success. Java gets the same benefit through type and record patterns.

Exit quiz, recall card, sources

~5 min

Two data class instances with equal properties: a == b is…

Kotlin == calls equals (L5), and a data class's equals compares the constructor properties.

After val b = a.copy() on a data class, how many objects of that class exist?

copy() creates a new object, unlike val b = a, which copies only the arrow (L4). Its fields' objects are still shared, though.

Does a Kotlin when expression over an enum that covers every constant need an else?

Enums and sealed types are closed, so the compiler can check coverage (L3, Part 1).
