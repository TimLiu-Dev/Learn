With no override, Java's a.equals(b) checks…

The inherited Object.equals is identity (L5).

  1. Object.equals is this == obj: true only when both references point to one object.
  2. Comparing fields is what an override does. Without one, Java never looks at the fields.
  3. Two different objects of the same class are still unequal under the inherited identity check.
  4. equals never consults hashCode. Hash codes are for hash tables, and unequal objects may share one.

If a.equals(b) is true, then a.hashCode() and b.hashCode() must…

"If two objects are equal according to the equals method, then calling the hashCode method on each of the two objects must produce the same integer result" (Object.hashCode docs).

  1. Backwards: equal objects must share a hash code. Different codes are allowed only for unequal objects.
  2. Zero for every object is legal but makes hash tables slow. The rule only demands equal values.
  3. Equal objects must give the same integer, or hash tables look for them in the wrong bucket.
  4. There's no "nearly equal" rule. The contract asks for exactly the same integer.

Kotlin var balance = 0L followed by private set means…

The getter stays public and the setter becomes private (L6).

  1. Backwards: private set hides the setter, and the getter stays public.
  2. Only the setter is private, so outside code can read balance but not assign it.
  3. That would be a private var. Here only the setter is hidden.
  4. That's a plain var, with no private set.

In Kotlin, a factory that Java would write as a static method usually lives in…

Kotlin has no static keyword. Members of a companion object are called on the class name (L6).

  1. An init block runs while each object is built. You can't call it on the class.
  2. A constructor can't have a descriptive name like eco(); a factory function can.
  3. lateinit only delays initialising a property. It has nothing to do with factories.
  4. Companion members are called on the class name, like Thermostat.eco(), just as Java calls statics.
Part 1

Value classes three ways

~38 min

Some classes are things with identity: a bank account, a user session, where two separate ones are different even if their fields match. Others are just values: a point, an amount of money, a date. Two Money(12.50, EUR)s should be interchangeable, just as two 5s are. In L5 you saw that plain classes compare by identity. A value class has to override equals, and once it does, also hashCode and, to be readable, toString. Effective Java devotes Items 10, 11 and 12 to exactly these three methods (Bloch, 3rd ed.).

Way 1: by hand

Every equals follows the same three steps: same object? Right type? Then compare the fields that define the value. hashCode must combine the same fields, because "if two objects are equal according to the equals method, then calling the hashCode method on each… must produce the same integer result". The reverse isn't required: unequal objects may share a hash code (Object.hashCode docs). Java's Objects.hash(x, y) does the combining for you. Without toString, you'd see something like Hand$Point@1b6d3586, which is the class name, an @, and the hash in hex (Object.toString docs).

What breaks if you forget hashCode

Hash-based collections (HashSet, HashMap, and Kotlin's default setOf/mapOf) use the hash code to decide where to look first, and only then call equals. If equal objects have different hash codes, the collection looks in the wrong place:

false
2
null

equals says the points are equal, yet the set can't find one, accepts a "duplicate", and the map can't look up its own key. Neither compiler warns you. That's why the rule is "override both or neither". In L19 you'll build a hash table yourself and see exactly where the lookup goes wrong.

Way 2: Java record

Since JDK 16, a one-line record declares one of Java's "transparent carriers for immutable data" (JEP 395). For each component, Java generates a private final field and a public accessor with the same name (cents(), not getCents()), plus a canonical constructor and equals, hashCode and toString. A compact constructor lets you validate the arguments; the fields are assigned automatically afterwards. Records are implicitly final and can't extend another class, but they can implement interfaces (JEP 395; dev.java: Using records).

Way 3: Kotlin data class

Kotlin's data class derives these members "from all properties declared in the primary constructor": equals()/hashCode(), toString() in the form User(name=John, age=42), componentN() functions, and copy() (Kotlin docs: Data classes). Validation goes in an init block with require.

Four details to notice:

  • copy builds a new object with some properties changed: price.copy(cents = …). That's how you "update" immutable data. Java records have no copy, so you call the constructor again, or write a small withX method yourself (you'll do this in the final).
  • Destructuring: val (cents, currency) = price calls component1() and component2(), in constructor order (Kotlin docs). Java 21 has its own version, record patterns, which you'll meet in Part 3.
  • Only the primary constructor counts. Tagged's note is declared in the class body, so equals and toString ignore it, and two Taggeds with different notes are "equal". The docs put it plainly: "The compiler only uses the properties defined inside the primary constructor for the automatically generated functions."
  • It's only shallow immutability. Look at Order: its fields are final, but the list it points to changed anyway. That's L5's "final reference isn't an immutable object", all over again.

The fix is the same as in L5: use read-only List components with a defensive copy (toList() / List.copyOf in the compact constructor), so nothing mutable is shared.

What Kotlin does for you. Compare the Point class in Hand.java (about 30 lines) with data class Point(val x: Int, val y: Int) (one line). The compiler writes equals, hashCode and toString, plus two things a Java record doesn't give you: copy() with named arguments, and componentN() for destructuring. Hint 2 of 3

Hint 3 of 3

Final answer

Why it works. equals and hashCode now look at the same thing: the address with case ignored. Equal emails therefore get equal hash codes, the set looks in the right bucket, and finds them. That's the contract from the Object.hashCode docs, and it's why a data class couldn't help here: its generated methods compare the property exactly.

Common mistake. Ignoring case in equals but returning address.hashCode(). Every equality check passes, yet the set lets "duplicates" in and the map lookup usually returns null: the Broken.kt bug in a new disguise.

Check

You override equals but not hashCode, then call set.contains(equalCopy) on a HashSet. Typically it…

The set looks in the bucket for the copy's (different) hash code and never finds the original.

  1. Only if the two identity-based hash codes happened to match, which almost never happens.
  2. Nothing is thrown: the set quietly searches the wrong bucket and reports a miss.
  3. The copy's identity-based hash sends the set to look in the wrong place, so it reports a miss.
  4. Overriding only equals compiles in both languages. Neither compiler checks the contract.

Which of these does a Kotlin data class not generate?

The generated set is equals/hashCode, toString, componentN and copy (Kotlin docs). Ordering is up to you.

  1. copy() is generated, with a named parameter for each constructor property.
  2. toString() is generated, in the form Point(x=1, y=2).
  3. component1() is generated for destructuring: one componentN per constructor property.
  4. Ordering isn't generated. Implement Comparable yourself if you need it.

The accessor that a Java record Money(long cents, …) generates is…

Records use the component name itself (JEP 395).

  1. That's the JavaBeans getter convention. Records deliberately drop the get prefix.
  2. A record's accessor is a method named exactly after its component.
  3. No such convention exists. Java names are case-sensitive, and records add no prefix.
  4. The field is private, so outside code can't read cents directly. It calls cents().

A data class's copy() handles a MutableList property…

It's a shallow copy, so the new object gets the same reference.

  1. copy passes the same reference along, so both objects point to one list.
  2. The docs say copy "doesn't copy components recursively". Deep copies are your job.
  3. copy never wraps or converts a property. The MutableList stays mutable.
  4. Properties you don't name keep their values. Nothing is reset to null.

A property declared in a data class's body, not its constructor, is…

Only primary-constructor properties feed the generated functions.

  1. Only primary-constructor properties feed the generated methods, which is why Tagged's note was left out.
  2. The generated methods use only primary-constructor properties, so t1 == t2 despite different notes.
  3. Body properties are allowed. Tagged declares one and compiles fine.
  4. copy doesn't carry it over either: the new object's body property starts from its initializer again.

Two records, one holding an array and one holding a List. What does this print?

import java.util.List;

public class Scores {
    record Team(String name, int[] points) {}
    record Squad(String name, List<Integer> points) {}

    public static void main(String[] args) {
        Team a = new Team("red", new int[] {1, 2});
        Team b = new Team("red", new int[] {1, 2});
        Squad c = new Squad("red", List.of(1, 2));
        Squad d = new Squad("red", List.of(1, 2));
        System.out.println(a.equals(b) + " " + c.equals(d));
    }
}

A record's generated equals compares each component with that component's equals. Arrays don't override it (L5), so two separate arrays are unequal, and so are the Teams. List.equals compares elements, so the Squads are equal. Prefer a List component, or override equals using Arrays.equals.

  1. Records don't look inside arrays: each component's own equals is used, and for arrays that's identity.
  2. The two arrays are different objects, so they're unequal; the two lists hold equal elements, so they're equal.
  3. List.equals compares elements, so two lists holding 1 and 2 are equal.
  4. Backwards: the array component causes the problem, and the lists compare fine.

Stretch: a data class goes into a set and is changed afterwards. What prints?

data class Box(var size: Int)

fun main() {
    val box = Box(1)
    val set = hashSetOf(box)
    box.size = 2                 // changed after it went into the set
    println("${set.contains(box)} ${set.size}")
}

The set filed box under the hash code of Box(1). Changing size changes the generated hashCode, so contains looks where a Box(2) would be, and misses, though the object is still inside. That's why things you put in a set or use as map keys should be immutable: make the property a val.

  1. The object is still in the set, but the lookup uses its new hash code, not the one it was stored under.
  2. Changing a field adds nothing to the set. It still holds one object, which contains can't find.
  3. The size stays 1: mutating the element doesn't insert a second entry.
  4. The entry sits under the old hash code, so the lookup misses while the size stays 1.

Enums

~23 min

An enum is a type with a fixed set of named instances, created once and shared. Unlike plain constants, an enum constant is a real object. It can carry properties, have methods, and implement interfaces (Kotlin docs: Enum classes; dev.java: Enums).

Because there's exactly one object per constant, comparing enums with == is safe in both languages: identity and equality coincide. And because the set of constants is closed, a when or a switch expression that covers every constant needs no else/default.

Why not just use strings or ints?

Code like shippingDays("express") compiles even when someone types "Express" or "exprss". The typo only shows up as wrong behaviour at runtime, if you're lucky. With an enum, Shipping.EXPRSS is a compile error, your IDE can list every valid option, and each option can carry its own data. Effective Java Item 34 is titled exactly this: "Use enums instead of int constants".

What Kotlin does for you. The constant's data lives right in the header, as in enum class Size(val ml: Int), while Java needs a field, a constructor and an accessor. entries gives you an immutable list rather than a fresh array on every call. And an exhaustive when works as both a statement and an expression.

Hint 1 of 3

total is one call: sumOf with each coin's cents. For change, think like a cashier: hand over the biggest coin that still fits, and repeat until nothing is left.

Hint 2 of 3

Coin.entries lists the constants in declaration order: penny first. Looping over it as it is hands out 41 pennies. Sort it by cents, largest first, then use a while loop per coin.

Hint 3 of 3

for (coin in Coin.entries.sortedByDescending { it.cents }), and inside it while (left >= coin.cents) { coins += coin; left -= coin.cents }. Java's Coin.values() returns a fresh array; sort a copy with Comparator.comparingInt.

Final answer

Why it works. Each constant is an object carrying its own data, so the code asks a coin what it's worth instead of keeping a separate table of values. Sorting by cents uses that data too, so the result doesn't depend on where a constant sits in the list. (Taking the biggest coin first gives the fewest coins for these US coins, though not for every coin system.)

Common mistake. Looping over Coin.entries unsorted: the penny comes first and swallows the whole amount, so change(41) is 41 pennies. .reversed() passes the checks, but breaks the day someone reorders the constants.

Check

Kotlin: Size.valueOf("medium"), when the constant is MEDIUM

The name must match exactly, including case.

  1. valueOf is case-sensitive, and "medium" isn't the name MEDIUM.
  2. valueOf never returns null. To get null, catch the exception, as parseShipping does.
  3. No constant is named exactly medium, so valueOf throws, as Sizes.kt shows.
  4. The compiler doesn't check a string's contents, so the mistake only shows up at runtime.

What's the recommended way to get all the constants in modern Kotlin?

values() still works, but entries is recommended since 1.9.0.

  1. values() still works, but builds a new array on every call. entries is now recommended.
  2. entries is a ready-made immutable list, recommended since Kotlin 1.9.0.
  3. Enums have no all() function.
  4. There's no list property. The list of constants is called entries.

Why prefer an enum over String constants like "express"?

The compiler knows the full set of valid values, so it catches mistakes for you.

  1. Memory isn't the reason, and the difference is tiny. Safety is.
  2. when works on strings: the fragile shippingDays does exactly that, and falls into else.
  3. Printing speed doesn't matter here, and printing an enum just prints its name.
  4. Shipping.EXPRSS doesn't compile, while "exprss" compiles and fails silently.

MEDIUM was added later, at the end. What does this print?

enum class Size { SMALL, LARGE, MEDIUM }    // MEDIUM was added later, at the end

fun main() {
    val sorted = listOf(Size.MEDIUM, Size.LARGE, Size.SMALL).sorted()

Enums compare by declaration order (their ordinal), not by name or meaning. MEDIUM was declared last, so it sorts last and counts as "greater" than LARGE. That's the table's warning about building logic on order: to sort by size, sort by a property such as ml.

  1. sorted() and > both use declaration order, and MEDIUM was declared after LARGE.
  2. The compiler doesn't know what the names mean. Only the position in the declaration counts.
  3. Enums don't compare by name. Alphabetical order happens to agree on >, but not on the sort.
  4. > uses the same declaration order as sorted(), so MEDIUM > LARGE is true.
Part 3

Sealed types

~33 min

Enums give you a fixed set of instances. Sometimes you need a fixed set of kinds, each carrying different data. A payment can succeed (with a transaction id), be declined (with a reason), or fail (retryable or not). A sealed interface or class declares that closed family: "all direct subclasses of a sealed class are known at compile time" (Kotlin docs: Sealed classes). In Kotlin, they "must be declared in the same package", and none can appear outside the module. In Java, the permits clause lists them, and each permitted subclass must be final, sealed or non-sealed. Records are implicitly final, so they fit perfectly (JEP 409, JDK 17).

paid, id tx-42
declined: insufficient funds
failed, try again
  • Kotlin: when with is Success -> checks the type, then smart-casts, so result.transactionId works with no cast. "In such cases, you don't need to add an else clause" (Kotlin docs).
  • Java 21: switch can match patterns (JEP 441). case Success s is a type pattern, which binds s already cast. case Declined(String reason) is a record pattern, which pulls the component straight out (JEP 440). When the cases cover every permitted subtype, "this switch block is exhaustive. As a result, no default label is needed" (JEP 441). See also dev.java: Using pattern matching.

The real payoff: adding a case

Six months later, someone adds Pending. Every when/switch that doesn't handle it now fails to compile. The compiler hands you a to-do list:

PaymentsNew.kt:8:47: error: 'when' expression must be exhaustive. Add the 'is Pending' branch or an 'else' branch.
PaymentsNew.java:12: error: the switch expression does not cover all possible input values

Now compare a version written "defensively" with else/default:

failed

It compiles cleanly and reports a pending payment as failed. The catch-all threw away the exact check the sealed type existed to give you. Rule: when switching over a sealed type or an enum, list every case and leave out else/default. (If a class compiled against the old version meets a new subtype at runtime, Java's compiler-inserted fallback throws a MatchException rather than guessing, according to JEP 441.)

Check

You add Pending to a sealed interface. A when expression with no else that doesn't handle it…

"'when' expression must be exhaustive. Add the 'is Pending' branch or an 'else' branch."

  1. A when expression must produce a value for every input. Kotlin never fills a gap with null.
  2. Without else, every subtype needs a branch, so the missing Pending is a compile error.
  3. The check happens at compile time, so this code never gets to run.
  4. Nothing is silent here. Silently mishandling Pending is what the else version in the next question does.

…and a when that does have else -> and doesn't handle it?

The catch-all absorbs the new case, which is exactly how PaymentsElse mislabels a pending payment.

  1. else covers every remaining case, so the when is exhaustive and compiles.
  2. MatchException is Java's, for code compiled against an older version. Here else simply runs.
  3. Pending matches else, so it gets the catch-all answer, with no warning.
  4. There's no warning, and nothing refuses to run: the code runs and is quietly wrong.

In Java, case Declined(String reason) -> is a…

It deconstructs the record into its components (JEP 440).

  1. It matches a Declined and pulls its reason component into a new variable.
  2. There's no cast syntax here. The pattern checks the type and binds the component safely.
  3. Declined is a record type with a component, not an enum constant.
  4. A default branch is default -> …. This case matches only Declined values.

Where must the direct subclasses of a Kotlin sealed type be declared?

"Direct subclasses of sealed classes and interfaces must be declared in the same package", and none can appear outside the module (Kotlin docs).

  1. That would make the family open. Sealed means outside code can't add subclasses.
  2. Nesting is allowed but not required: Payments.kt declares them at top level.
  3. There's no file rule: any file in the same package works, including the sealed type's own.
  4. The compiler must see every direct subclass, so they all live in its package and module.

A log of commands, turned into a set. What does this print?

sealed interface Command
data class Add(val item: String) : Command
data object Clear : Command

fun main() {
    val log: List<Command> = listOf(Add("tea"), Clear, Add("tea"), Clear)
    println(log.toSet())
}

toSet() drops every element that equals an earlier one, and keeps the original order. The two Add("tea")s are equal because a data class compares contents, and both Clears are the same single object. A data object prints just its name; a plain object would print something like Clear@1b6d3586.

  1. A set keeps one of each equal element, and both repeats here equal earlier elements.
  2. That's how a plain object prints. A data object gets a generated toString that shows just its name.
  3. The equal Adds collapse into one, the single Clear appears once, and insertion order is kept.
  4. The two Add("tea") objects are separate but equal, because data classes compare contents. So one is dropped.

Wrap-up

Exit quiz, recall card, sources

~5 min

Two data class instances with equal properties: a == b is…

Kotlin == calls equals (L5), and a data class's equals compares the constructor properties.

  1. That's identity, which is ===. Kotlin's == calls equals.
  2. == calls the generated equals, which compares every constructor property.
  3. Comparing two values of the same type with == always compiles.
  4. The generated equals accepts any argument, even null, without throwing.

After val b = a.copy() on a data class, how many objects of that class exist?

copy() creates a new object, unlike val b = a, which copies only the arrow (L4). Its fields' objects are still shared, though.

  1. a already existed, and copy() adds another. Neither disappears.
  2. That's val b = a, which copies only the reference. copy() builds a new object.
  3. copy() makes exactly one new object, not two.
  4. The original a, plus the new object copy() returned.

Does a Kotlin when expression over an enum that covers every constant need an else?

Enums and sealed types are closed, so the compiler can check coverage (L3, Part 1).

  1. Only a when that can't be proven exhaustive needs else. Closed types can be covered completely.
  2. Statements don't need else either: listing every constant is enough.
  3. The compiler knows every constant, so covering all of them makes else unnecessary.
  4. Methods don't change the set of constants, and that set is all the compiler checks.
