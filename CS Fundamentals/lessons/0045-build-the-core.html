Why did L44's URL shortener redirect with 302 instead of 301? (L44)

A 301 is cacheable by default, so a browser stops asking after the first visit and the click counter never sees the rest. 302 keeps every click coming back to the server (RFC 9110 §15.4).

What is a composition root? (L38)

Everything else depends on interfaces and receives its dependencies through constructors; only the composition root says SqliteBookStore(db). Today that's the Shelf class.

L36 put a partial unique index on loans(book_id) WHERE returned IS NULL. What does it do? (L36)

Only open loans are in the index, and it's unique on book_id, so a second open loan for the same book is a constraint violation, whatever the application code does. Shelf keeps it as its last line of defence.

A POST /books that creates a book should answer with… (L32)

RFC 9110 §9.3.3: the origin server "SHOULD send a 201 (Created) response containing a Location header field that provides an identifier for the primary resource created". Shelf does exactly that.

The layers, and where they live

Shelf has the layering from L38, with one package per layer. Arrows point from a layer to what it depends on: http knows about services, services know about store interfaces, and only Shelf (the composition root) names the SQLite classes.

shelf/
├── App.kt            Shelf: the composition root, plus main()        (Java: Shelf.java + App.java)
├── domain/           Book, Member, Loan: plain data, no JSON, no SQL
├── http/             Router, Request, Response, ApiError, DTOs, JSON helpers, Routes
├── service/          BookService, LendingService: the rules
└── store/            BookStore, MemberStore, LoanStore interfaces
                      SqliteBookStore … (Db helper)  and  MemoryBookStore … (fakes)

     └──────────── Shelf (composition root) ────────┘

Three details carry over from earlier phases. The server binds to InetAddress.getLoopbackAddress(), so nothing outside this machine can reach it (L30). Each request runs on its own virtual thread (L28), so a request waiting on SQLite costs almost nothing. And the clock is a constructor parameter (L38): main passes Clock.systemUTC(), tests pass a fixed clock.

The router

HttpServer routes by context. Its docs: "the appropriate HttpContext (and handler) is located by finding the context whose path is the longest matching prefix of the request URI's path." Shelf registers a single context, "/", which is a prefix of every path, so every request reaches one handler: Router.handle. From there, routing is yours. A route is a method plus a path template such as /books/{id}. Matching a request has three outcomes, which is why Match is a sealed type:

  • Found: a template and the method both match. The router binds the {id}-style segments into a map and calls the handler.
  • WrongMethod: some template matches the path, but not for this method. That's a 405, and RFC 9110 §10.2.1 says "An origin server MUST generate an Allow header field in a 405 (Method Not Allowed) response", so the router collects the methods that would have worked.
  • NoRoute: nothing matches the path at all. That's a 404.
Java's Request and Response (Kotlin keeps them in Router.kt)

Read handle as the whole "framework" in twenty lines: match, run the handler, turn every failure into a Problem Details response, send. Handlers never write to the exchange themselves; they return a Response. That keeps them small, and it means status codes and headers are decided in exactly one place. Errors flow the other way: a handler that can't answer throws an ApiError (404, 409, 400…), and handle renders it. Anything unexpected becomes a 500 whose body says only "Something went wrong"; the details go to the log, never to the client (L33).

Because match is a pure function of the method and the path, you can test it without a server, a socket or a database:

What Kotlin does for you.

  • val (route, params) = hits.firstOrNull { … } ?: return Match.WrongMethod(…): destructuring plus an early return in one line. Java loops and collects by hand.

Check

HttpServer has one context, "/". Which requests reach Router.handle?

Contexts match by longest prefix, and "/" is a prefix of every path, so it catches everything. Routing by template and method happens inside Router.

A path matches a template, but only for other methods. Shelf answers…

The resource exists but doesn't support this method: WrongMethod becomes 405, with the Allow header RFC 9110 requires. In the capture, PATCH /books/1 got Allow: DELETE, GET, PUT.

Why is match() kept separate from handle()?

match takes two strings and returns a value, so RouterTest runs in a few milliseconds with no socket. Push the logic you want to test into pure functions, and keep the I/O at the edges.

What does GET /books/abc return?

The template binds id = "abc", and req.id() can't parse it, so it throws ApiError.notFound. No book can have that name; the integration test checks exactly this.

With first-match routing, /books/{id} registered before /books/count, what does GET /books/count bind? (Exercise 1)

The template comes first and fits, so "count" becomes the id, and the literal route is never reached. Register specific routes first, or rank by specificity as Spring does.

Part 2

JSON endpoints

~30 min

DTOs are not the domain

The domain classes (Book, Member, Loan) are plain data: no JSON annotations, no SQL. The http package has its own DTOs (data transfer objects), shaped like the JSON. Keeping them apart costs a few mapping functions, and buys three things you'll use today:

  • Input DTOs have nullable fields, even for required data, so a missing title becomes the message "title is required" instead of a parser exception. Validation happens here, at the boundary, and produces a clean command (NewBook) that the service can trust (L10: parse, don't trust).
  • Output DTOs choose the wire format. Loan.loaned is a LocalDate in the domain and an ISO-8601 string in the JSON (L32).
  • The API can change without touching the domain, and the reverse.

Errors as Problem Details

RFC 9457 defines "a 'problem detail' to carry machine-readable details of errors in HTTP response content" (RFC 9457). Shelf uses the about:blank type everywhere, which "indicates that the problem has no additional semantics beyond that of the HTTP status code", and the RFC adds that the title "SHOULD be the same as the recommended HTTP status phrase for that code". So a validation failure is titled Bad Request, and the specific messages go in an errors extension member. (My first version titled it "Invalid request"; rereading §4.2.1 made me fix it in both languages.)

Java's ApiError (Kotlin keeps it in Json.kt) 
package shelf.http;

import java.util.List;

public final class ApiError extends RuntimeException {
    final int status;
    final String title;
    final List<String> errors;                               // null unless it's a validation error

    public ApiError(int status, String title, String detail) {
        this(status, title, detail, null);
    }

    ApiError(int status, String title, String detail, List<String> errors) {
        super(detail);
        this.status = status;
        this.title = title;
        this.errors = errors;
    }

    static ApiError notFound(String path) {
        return new ApiError(404, "Not Found", "No resource at " + path);
    }

    static ApiError conflict(String detail) {
        return new ApiError(409, "Conflict", detail);
    }

    static ApiError invalid(List<String> errors) {
        return new ApiError(400, "Bad Request", errors.size() + " problem(s) with the request", errors);
    }
}

The two JSON libraries start from opposite defaults (you saw this in L32). kotlinx.serialization rejects unknown keys unless you set ignoreUnknownKeys, and by default "all null values are encoded into JSON output" unless you set explicitNulls = false (Kotlin docs: Customize the Json instance). Jackson 3 ignores unknown keys by default. Shelf configures both the same way: strict about unknown keys, and silent about nulls. That's why the two servers give byte-identical responses.

The handlers

Each handler does three things: read the request (path parameters, query, body), call one service method, and map the result to a response. There's no SQL here and no business rule. When the service returns a sealed result such as BookOnLoan, the handler chooses the status code.

Here's the code that caused it:

@Serializable
data class MemberIn(val name: String? = null, val email: String? = null) {
    fun validate(): Pair<String, String> {
        val errors = buildList {
            if (name.isNullOrBlank()) add("name is required")
            if (email == null || !EMAIL.matches(email)) add("email must look like name@example.com")
        }
        if (errors.isNotEmpty()) throw ApiError.invalid(errors)
        return name!!.trim() to email!!.lowercase()
    }

    private companion object {
        val EMAIL = Regex("[^@\\s]+@[^@\\s]+\\.[^@\\s]+")
    }
}

The serialization plugin works through MemberIn's companion object: bodyAs<MemberIn>() compiles into a call that reads MemberIn.Companion (the trace's RoutesKt tried to access private field shelf.http.MemberIn.Companion). I'd made that companion private, so the JVM refused at runtime. Moving the regex to a top-level private val fixed it. That's an observation from this run, not a documented rule. Two lessons from it:

  • Integration tests catch what unit tests can't: serialization, wiring, the real HTTP path.
  • IllegalAccessError is an Error, not an Exception, so the router's catch (e: Exception) didn't see it, and the client got silence instead of a 500. Catching only Exception is the usual advice; the price is that a JVM-level error kills that one response. (Spring's DispatcherServlet catches any Throwable from a handler and wraps an Error in a ServletException, so error handlers still see it; L47 shows this.)
What Kotlin does for you.
  • @Serializable data classes generate their serializers at compile time (L32). Jackson finds record components by reflection at runtime (L25).
  • inline fun <reified T> Request.bodyAs(): T lets a handler write req.bodyAs<BookIn>(). Java passes BookIn.class, because generics are erased (L13).
  • title.isNullOrBlank() smart-casts title to non-null in the else branch; Java repeats the null check.
  • val (name, email) = …validate() destructures a Pair. Java returns a cleaned-up MemberIn and calls its accessors.
  • buildList { if (…) add(…) } collects errors in one expression; Java creates an ArrayList and returns it.
  • Exhaustive when over sealed results means a new result type won't compile until every handler maps it. Java's pattern switch gives the same guarantee.

Check

Why are BookIn's fields nullable when a book's title is required?

With a non-null title, a missing key fails inside the parser with a generic error. Nullable fields let the request parse, and validate() then reports every problem in words the client can act on.

§4.2.1: the title "SHOULD be the same as the recommended HTTP status phrase for that code". Specifics belong in detail and extension members such as errors.

The key is left out, which is why an open loan prints {"id":1,…,"loaned":"2026-10-28"} with no returned. The Java side matches with JsonInclude.Include.NON_NULL.

Part 3

JDBC with SQLite; unit vs integration tests

~30 min

The schema and a tiny JDBC helper

The schema is L34's library (with authors in their own table, L35), plus L36's partial unique index. Db opens a fresh connection per operation, switches on foreign keys every time (they're off by default in SQLite, L34), and asks for transaction_mode=IMMEDIATE so concurrent writers queue instead of failing halfway (L36). Three helpers, query, update and insert, bind every value through a ? placeholder, so SQL injection (L33) can't happen here.

The services depend on three small interfaces (BookStore, MemberStore, LoanStore; listed in the final). The SQLite implementations translate between rows and domain objects. One transaction per write, and a read uses a plain connection:

The rules

A known race, kept on purpose. lend checks openForBook and then calls add: two store calls, two transactions. Two requests for the same book at the same instant can both pass the check (L26's check-then-act, L38 flagged it). In v1 the partial unique index still refuses the second insert, so the data stays correct, but that request gets a 500 instead of a 409. L46 load-tests Shelf, reproduces this for real, and fixes it.

Three kinds of test

Martin Fowler's Test Pyramid: "you should have many more low-level UnitTests than high level BroadStackTests". Ham Vocke's longer Practical Test Pyramid puts it as "Write lots of small and fast unit tests. Write some more coarse-grained tests and very few high-level tests". Shelf has all three levels:

  • Unit tests run one class with fakes: RouterTest, BookServiceTest and LendingServiceTest (the real service, in-memory stores, a fixed clock).
  • Contract tests run one suite against both store implementations (L38), so the fakes the unit tests rely on can't drift away from SQLite.
  • Integration tests start the whole app on port 0 (the OS picks a free port) with a temporary SQLite file, and talk to it over real HTTP with HttpClient (L31).

    private static Book book(ResultSet rs) throws SQLException {
        int year = rs.getInt(4);
        return new Book(rs.getLong(1), rs.getString(2), rs.getString(3), rs.wasNull() ? null : year);
    }

getInt returns 0 for SQL NULL, and the ResultSet docs say wasNull() "Reports whether the last column read had a value of SQL NULL" (java.sql.ResultSet). Java evaluates constructor arguments left to right, so by the time wasNull() ran, the last column read was column 3, the author, which is never null. The fix reads the columns in order and asks wasNull() straight after getInt(4). The Kotlin version never had the bug, by luck of argument order: rs.getInt(4).takeUnless { rs.wasNull() } is the fourth argument, so wasNull runs right after getInt. Same contract, same test, both stores now green: this is what contract tests are for.

What Kotlin does for you.
  • inline fun <T> transaction(block: (Connection) -> T) takes a lambda, and since SQLException isn't checked in Kotlin, there's no wrapper type. Java defines a Work<T> interface whose method throws SQLException, and wraps failures in DbException (L10).
  • c.query(sql, id) { book(it) }: an extension function with a trailing lambda. Java's varargs must come last, so the row mapper goes in the middle: query(c, sql, mapper, id).
  • One file, SqliteStores.kt, holds three classes. Java needs one public class per file.
  • rs.getString(5)?.let(LocalDate::parse) handles a nullable column in one expression.
  • A nullable Book? return replaces Java's Optional<Book>.
  • @Synchronized on the fakes compiles to the same monitor as Java's synchronized methods (L26).

Reference answer

Add CREATE INDEX IF NOT EXISTS books_by_author ON books(author_id) to the schema list; it's in the reference Db above. The new plan:

$ /usr/bin/sqlite3 shelf.db < plans_after.sql
QUERY PLAN
|--SEARCH a USING COVERING INDEX sqlite_autoindex_authors_1 (name=?)
`--SEARCH b USING INDEX books_by_author (author_id=?)

Now SQLite finds the author by name with the UNIQUE index it creates for authors.name, then finds that author's books with books_by_author. There's no TEMP B-TREE for ORDER BY b.id, because entries for one author come out of the index already in rowid order. The contract test list is ordered by id, paged and filtered by author still passes against SQLite, which is your proof.

Check

Java's rs.wasNull() reports on…

It takes no argument; it reports on the most recent getter. Read a nullable primitive column, then ask wasNull() immediately.

Which test caught the Java wasNull bug?

The bug lived in the SQLite store, which unit tests never touch. The same contract suite passed for the memory store and failed for SQLite, which pinpointed the culprit.

Two requests lend book 1 at the same instant. In v1, what stops a double loan?

Both requests can pass the service's check, because it's a separate transaction from the insert. The database index refuses the second open loan. L46 turns that refusal into a proper 409.

According to the test pyramid, which tests should you have the most of?

Many low-level unit tests, fewer broad tests (Fowler's TestPyramid). Shelf has 13 unit tests, 12 contract runs (6 per store) and 8 integration tests.

EXPLAIN QUERY PLAN shows SCAN b for the ?author= query. The fix?

The join looks up books by author_id, which had no index, so SQLite scanned the whole table. With books_by_author, the plan becomes SEARCH b USING INDEX.

Wrap-up

Exit quiz, recall card, sources

~5 min

Which executor does Shelf give its HttpServer? (L28)

One cheap virtual thread per request. A request blocked on SQLite parks its virtual thread and frees the carrier. Without setExecutor, HttpServer would handle requests on its own dispatcher thread, one at a time.

The 500 handler logs the exception but sends only "Something went wrong". Why? (L33)

Error details reveal libraries, versions and sometimes SQL: the security-misconfiguration category of L33's OWASP list. Log them for yourself; send a generic problem to the client.

The contract test compares domain objects with assertEquals. What makes that work? (L7)

data class and record generate value-based equals and hashCode, so a book read back from SQLite equals the one you added, field by field.

What does ./gradlew installDist produce? (L25)

The Application plugin's docs: "You can run gradle installDist to create an image of the application in build/install/projectName". That image has bin/app plus every jar in lib/; the session above ran bin/app.
