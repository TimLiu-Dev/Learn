Warm-up

Recall from L4, L22, L23 and L25

~10 min
From memory: no peeking
  1. Draw one process with two threads. Which parts of memory does each thread get for itself, and which part do they share? (L4, L22)
  2. Write the bytecode javap -c shows for count++ on a field, as best you remember. How many instructions? (L23)
  3. An annotation does nothing until some tool reads it. Name the three kinds of reader. (L25)

Two threads in one JVM both use a local variable i in the same method. Where does each i live? (L4)

Each thread has its own stack, and local variables live in that thread's frames. That's why locals are never shared between threads, and why the trouble in this lesson always comes from fields on the heap.

What do two threads of the same process share that two separate processes don't? (L22)

Threads of one process live in one virtual address space, so they see the same heap. Each still has its own program counter, registers and stack. Separate processes get separate address spaces.

In javap -c output, which instruction stores a value back into an object's field? (L23)

getfield pushes a field's value onto the operand stack, and putfield pops a value and writes it into the field. istore_1 writes a local variable. Keep getfield/putfield in mind for Part 2.

Kotlin's @Synchronized is an annotation. Who acts on it? (L25)

kotlinc reads it and sets the JVM's ACC_SYNCHRONIZED flag on the generated method. You'll see that flag with javap in Part 3.

Part 1

Starting threads; how the OS schedules them

~25 min

A thread is a separate path of execution inside one process. OSTEP puts it like this: each thread "is very much like a separate process, except for one difference: they share the same address space and thus can access the same data" (OSTEP ch. 26). Every Java or Kotlin program already has one: main runs on a thread called main. You add more by giving a Thread a piece of work and calling start().

start() vs run()

The work is a Runnable, an interface with one method, run() (L14's functional interfaces). The classic beginner bug is calling run() yourself. That's an ordinary method call on the current thread. Only start() asks the JVM for a new thread: "Starting a thread schedules it to execute its run method. The newly started thread executes concurrently with the thread that caused it to start" (Thread API docs). join() makes the caller wait until that thread has finished.

task runs on: main
task runs on: worker
block runs on: kotlin-worker
main done on: main
task runs on: main
task runs on: worker
builder runs on: builder-worker
main done on: main

The first line says main, even though the thread object is called worker: run() never started anything. Kotlin's thread { } from kotlin.concurrent creates and starts a thread in one call. Its full signature is thread(start = true, isDaemon = false, contextClassLoader = null, name = null, priority = -1, block) (Kotlin API: thread). Those are named parameters with defaults (L3), so you only write the ones you change. Java's closest equivalent is the Thread.ofPlatform() builder added in JDK 21.

Same code, five different orders, in both languages. You didn't choose the order, and neither did the JVM. On this machine a Java thread is a platform thread, which is "typically mapped 1:1 to kernel threads scheduled by the operating system" (Thread API docs). You saw those kernel threads in L22, when ps -M listed 26 of them for one JVM. The OS scheduler decides which thread runs on which core, for how long, and when to preempt it. Switching threads on a core is a context switch: "the register state of T1 must be saved and the register state of T2 restored before running T2" (OSTEP ch. 26). With several cores, two threads also run at literally the same time. Here's what this machine has:

$ sysctl hw.ncpu hw.perflevel0.name hw.perflevel0.physicalcpu hw.perflevel1.name hw.perflevel1.physicalcpu
hw.ncpu: 18
hw.perflevel0.name: Super
hw.perflevel0.physicalcpu: 6
hw.perflevel1.name: Performance
hw.perflevel1.physicalcpu: 12

That's 18 cores in two tiers: Apple names the faster six "Super" and the other twelve "Performance". Runtime.getRuntime().availableProcessors() reports 18 to the JVM. Even with 18 cores, the order of the two threads' output isn't fixed, because each print is a separate call, and the threads race each other for System.out between calls. Never write code that depends on one thread "probably" running first.

Thread states

A thread is always in one of six states, the Thread.State enum: NEW ("has not yet started"), RUNNABLE ("executing in the Java virtual machine"), BLOCKED ("blocked waiting for a monitor lock"), WAITING ("waiting indefinitely for another thread"), TIMED_WAITING (waiting "for up to a specified waiting time") and TERMINATED ("has exited") (Thread.State API docs). This program catches a thread in each one:

before start: NEW
sleeping:     TIMED_WAITING
joining:      WAITING
needs lock:   BLOCKED
computing:    RUNNABLE
all finished: TERMINATED
before start: NEW
sleeping:     TIMED_WAITING
joining:      WAITING
needs lock:   BLOCKED
computing:    RUNNABLE
all finished: TERMINATED

The Thread.sleep(50) calls in main are only there so the other thread has time to reach the state being printed. Using sleep to coordinate threads is a bug in real code; you'll use proper tools like join and latches instead. Notice the Java version is longer: every lambda that calls sleep or join needs a try/catch. More on that below. The docs add that these "are virtual machine states which do not reflect any operating system thread states". RUNNABLE means "ready to run", not necessarily "on a core right now".

Daemon threads

When does the JVM exit? "The shutdown sequence begins when all started non-daemon threads have terminated" (Thread API docs). A daemon thread is a background helper that doesn't keep the JVM alive:

  heartbeat
main ends; only a daemon thread is left, so the JVM exits
  heartbeat
  heartbeat
  heartbeat

main ends; only a daemon thread is left, so the JVM exits

The heartbeat loop never ends, yet the program does. Drop isDaemon = true (or setDaemon(true)) and it would print heartbeats forever, because a live non-daemon thread holds the JVM open. That's also the classic reason a "finished" program doesn't exit: some thread you forgot about is still running.

Threads aren't free

A platform thread is an OS thread with its own stack. The docs warn they "will usually have a large stack and other resources that are maintained by the operating system" and "may be a limited resource". Time how long it takes to start and join 10,000 threads that do nothing:

round 1: 10000 threads started and joined in 232 ms (23 µs each)
round 2: 10000 threads started and joined in 221 ms (22 µs each)
round 3: 10000 threads started and joined in 217 ms (21 µs each)
round 1: 10000 threads started and joined in 228 ms (22 µs each)
round 2: 10000 threads started and joined in 218 ms (21 µs each)
round 3: 10000 threads started and joined in 221 ms (22 µs each)

About 22 µs per thread on my machine, the same in both languages because it's the same OS call underneath. That's thousands of times the cost of a method call, which is why real servers reuse threads in a pool (L28) and why Java added much cheaper virtual threads (also L28).

Sleeping, interrupting, and crashing

You can't safely kill a thread from outside. Instead you interrupt it: a polite request that the thread checks for. If the thread is blocked in sleep, join or wait, the request arrives as an InterruptedException. And if a thread throws an exception nobody catches, only that thread dies:

sleeper: interrupted (sleep interrupted), cleaning up and stopping
Exception in thread "crasher" java.lang.IllegalStateException: boom
	at InterruptsKt.main$lambda$1(Interrupts.kt:16)
	at kotlin.concurrent.ThreadsKt$thread$thread$1.run(Thread.kt:30)
main is still alive; crasher.isAlive = false
handler: Thread-2 died with bang
sleeper: interrupted (sleep interrupted), cleaning up and stopping
Exception in thread "crasher" java.lang.IllegalStateException: boom
	at Interrupts.lambda$main$1(Interrupts.java:16)
	at java.base/java.lang.Thread.run(Thread.java:1516)
main is still alive; crasher.isAlive = false
handler: Thread-0 died with bang

The default behaviour for an uncaught exception is to print the stack trace with the thread's name (Exception in thread "crasher") and end that thread. main carries on. That's dangerous in a server, where a worker can die silently while the rest looks healthy, so set an UncaughtExceptionHandler to log it. The unnamed threads got default names, Thread-0 and Thread-2.

In Java, InterruptedException is a checked exception (L10), and Runnable.run() declares no exceptions. So a lambda that sleeps without a try doesn't compile:

SleepNoCatch.java:4: error: unreported exception InterruptedException; must be caught or declared to be thrown
            Thread.sleep(100);          // Runnable.run() declares no exceptions
                        ^
1 error

Kotlin "treats all exceptions as unchecked" (Kotlin docs: Exceptions), so thread { Thread.sleep(100) } just compiles. That's convenient, but it means nothing reminds you to handle the interruption. A good habit in both languages: catch it, clean up, and stop, as sleeper does above. If you can't stop right there, restore the flag with Thread.currentThread().interrupt() so code further up can see it.

What Kotlin does for you.
  • thread(name = "w", isDaemon = true) { … } creates, configures and starts a thread in one call, using named parameters with defaults. Java needs new Thread(…), setDaemon and start(), or the JDK 21 builder.
  • No checked exceptions, so lambdas that call sleep or join need no try/catch. Compare the lengths of States.kt and States.java.
  • Trailing-lambda syntax (L14) makes thread { … } read like a built-in block.
  • What it doesn't do: anything about thread safety. Kotlin threads are the same JVM platform threads as Java's, with the same scheduler and the same costs.
Exercise: a parallel sum with nothing shared
  1. From a blank file, fill an IntArray/int[] of 40,000,000 elements with i % 7.
  2. Start 4 threads named summer-0 to summer-3. Each sums one quarter of the array into a local variable, then writes the result into its own slot of a 4-element LongArray/long[].
  3. join all four, add up the slots, and compare the answer and the time with a single-threaded loop. Print each worker's name and state at the end.
  4. Predict: will 4 threads be 4× faster? Then run it.
Reference solutions 
4 threads: 119999995 in 12 ms; 1 thread: 119999995 in 10 ms
summer-0=TERMINATED, summer-1=TERMINATED, summer-2=TERMINATED, summer-3=TERMINATED
4 threads: 119999995 in 5 ms; 1 thread: 119999995 in 10 ms
summer-0=TERMINATED, summer-1=TERMINATED, summer-2=TERMINATED, summer-3=TERMINATED

The answers are always right, because no two threads ever write the same memory. This is thread confinement, the simplest kind of thread safety. Each sum is a local on its own thread's stack, and each slot has exactly one writer. join also guarantees that main sees the slot values the workers wrote (L27 explains why that guarantee matters).

The speed-up is not 4×. Java went from 10 ms to 5 ms; Kotlin was slower with threads in this run. Starting threads costs time, the loop code is still cold (not yet JIT-compiled, L23) when the workers start, and summing an array is limited by memory bandwidth, not by the CPU. Measure before you assume threads make something faster.

Check

val t = Thread { println(Thread.currentThread().name) }, then t.run() called from main. What's printed?

run() is an ordinary method call, so the lambda runs on the calling thread, main. Only start() creates a new thread. StartRun's first line showed exactly this.

A thread is waiting to enter a synchronized block that another thread holds. Its state?

"A thread that is blocked waiting for a monitor lock is in this state." WAITING is for join()-style waits with no timeout, and TIMED_WAITING is for sleep or waits with one.

main returns while a non-daemon thread is still looping forever. What happens?

Shutdown begins only "when all started non-daemon threads have terminated". A forgotten non-daemon thread keeps the program alive. Daemon threads don't.

A worker thread throws an exception that nobody catches. What happens to the rest of the program?

The default handler prints Exception in thread "…" and the trace, then that thread terminates. main kept going in Interrupts. In a server, add an UncaughtExceptionHandler so the failure isn't silent.

Cause a race condition on purpose

~25 min

The exercise above was safe because nothing was shared. Now share one thing: a counter. Two threads each add 1 to it a million times, so the answer should be 2,000,000. Run it five times:

The early runs lose hundreds of thousands of increments. Each lost increment is a lost update: one thread's write overwrote another's. Then something odd happens. Later runs print exactly 2,000,000, or exactly 1,000,000. Did the bug fix itself?

No. Here is the same Java program run with -Xint, which turns the JIT compiler off (L23):

$ java -XX:+PrintCompilation LostUpdate 2>&1 | grep -E 'work|run [0-9]'
     …

19   65 %     4       LostUpdate::work @ 2 (23 bytes)
19   66       4       LostUpdate::work (23 bytes)

Because count has no synchronization, the JIT is allowed to keep it in a CPU register for the whole loop: read it once, add 1,000,000, and write it once at the end. The JLS says exactly this about a similar loop: "The compiler is free to read the field this.done just once, and reuse the cached value in each execution of the loop" (JLS §17.3). Now each thread does one big read and one big write. If the threads don't overlap, you get 2,000,000. If they overlap, one big write erases the other, and you get exactly 1,000,000. The race is still there; it just got coarser. That is my reading of the evidence above (I can't show you the machine code without extra tools), but the conclusion doesn't depend on it: a racy program can print the right answer, and that proves nothing.

Why count++ isn't one step

To see the collision, look at what count++ compiles to. Here is a tiny Counter class with an increment() method, through javap -c (L23):

public final void increment();
  Code:
     0: aload_0
     1: getfield      #16   // Field count:I
     4: istore_1
     5: aload_0
     6: iload_1
     7: iconst_1
     8: iadd
     9: putfield      #16   // Field count:I
    12: return
void increment();
  Code:
     0: aload_0
     1: dup
     2: getfield      #7    // Field count:I
     5: iconst_1
     6: iadd
     7: putfield      #7    // Field count:I

Both are read (getfield), add (iconst_1, iadd), write (putfield). kotlinc even parks the old value in local variable 1 on the way. The scheduler can switch threads between any two instructions, and on a multicore machine the two threads run these steps at the same time. The Java tutorial calls this thread interference: it "happens when two operations, running in different threads, but acting on the same data, interleave. This means that the two operations consist of multiple steps, and the sequences of steps overlap" (Java Tutorials: Thread Interference).

Check-then-act

Lost updates come from read-modify-write: read a value, compute from it, write it back. The other classic shape is check-then-act: check a condition, then act on it, while another thread changes the world in between. Lazy initialisation is the textbook case. Eight threads call getConfig() at the same moment, held at a start line by a CountDownLatch, "a synchronization aid that allows one or more threads to wait until a set of operations being performed in other threads completes" (CountDownLatch API docs):

run 1: Config created 8 times by getConfig()
run 2: Config created 8 times by getConfig()
run 3: Config created 8 times by getConfig()
run 4: Config created 8 times by getConfig()
run 5: Config created 8 times by getConfig()
by lazy: Config created 1 time
run 1: Config created 8 times by getConfig()
run 2: Config created 8 times by getConfig()
run 3: Config created 8 times by getConfig()
run 4: Config created 8 times by getConfig()
run 5: Config created 8 times by getConfig()

All eight threads saw null, all eight built a Config, and each overwrote the last one. The 5 ms "expensive setup" widens the window between check and act, which is realistic: real initialisation reads files or opens connections. Kotlin's by lazy (L15) created exactly one, because "by default, the evaluation of lazy properties is synchronized: the value is computed only in one thread, but all threads will see the same value" (Kotlin docs: Delegated properties). The created counter is an AtomicInteger, Part 3's tool, so the measuring code isn't racy itself.

Why races are so hard to find

  • They depend on timing. The same program printed 1,809,603, then 2,000,000. On a different machine, JDK or load, the odds change.
  • They hide when you look. A breakpoint (L12) or a println changes the timing, and the bug may vanish while you watch. People call this a Heisenbug.
  • The code looks right. count++ and if (instance == null) are correct in single-threaded code. Nothing in the source says "shared".
  • The failure shows up far away, as a wrong balance or a missing map entry, long after the racing lines ran.

Data race vs race condition

The two terms are related but different. A data race is defined by the JLS: two accesses to the same variable are "conflicting if at least one of the accesses is a write", and "when a program contains two conflicting accesses that are not ordered by a happens-before relationship, it is said to contain a data race" (JLS §17.4.5). A race condition is any bug where the result depends on the timing between threads. You can have one without the other. The JLS itself warns that "freedom from data races still allows errors arising from groups of operations that need to be perceived atomically and are not" (§17.4.3). Part 3's exercise shows exactly that: an AtomicInteger account has no data race, but it still overdraws. L27 explains "happens-before".

Kotlin note. LostUpdate.kt used a top-level var count. There's no magic there: it compiles to a static field of the LostUpdateKt class (L9), shared by every thread exactly like Java's static int count. The same goes for properties of an object and of a companion object. "Global" in Kotlin means "shared between all threads".

Bridge: Spring creates one instance of a singleton bean, and "all requests for beans with an ID or IDs that match that bean definition result in that one specific bean instance being returned". Its advice is "use the prototype scope for all stateful beans and the singleton scope for stateless beans" (Spring: Bean Scopes). A web server handles requests on many threads at once, so a mutable field in a singleton controller is this lesson's shared counter. Android takes the opposite approach: "the Android UI toolkit is not thread-safe", so its rule is "Don't access the Android UI toolkit from outside the UI thread" (Android: Processes and threads). Confining all UI work to one thread removes the races by design.

What Kotlin does for you.
  • by lazy { } is synchronized by default, so the check-then-act race in getConfig() can't happen. In Java you write the locking yourself (L27 shows the correct way).
  • object declarations are initialised safely: "The initialization of an object declaration is thread-safe and done on first access" (Kotlin docs).
  • What it doesn't do: protect any var. A Kotlin property is a field plus getter and setter, and count++ on it is the same read, add, write as Java's, as javap showed. Read-only List types don't help either: HashMap under a MutableMap races exactly as in Java.

Check

Two threads each run count++ once on a shared count that starts at 5. Which final values are possible?

If the read-add-write sequences don't overlap, you get 7. If both threads read 5 before either writes, both write 6. Both threads always write something at least 6, so 5 is impossible. Try both orders in the widget.

A racy counter printed the right total on runs 4 and 5. What does that prove?

if (cache[key] == null) cache[key] = load(key) on a shared map is an example of which race shape?

The check (== null) and the act (the put) are separate steps, and another thread can pass the same check in between, so load runs twice. It's the same shape as getConfig().

Part 3

synchronized, locks, atomics

~30 min

Every fix in this part does the same job: it makes the read-modify-write behave as one indivisible step, an atomic action, one that "effectively happens all at once. An atomic action cannot stop in the middle: it either happens completely, or it doesn't happen at all" (Java Tutorials: Atomic Access). There are three tools, and you'll measure all three.

Tool 1: the built-in lock

"Each object in Java is associated with a monitor, which a thread can lock or unlock. Only one thread at a time may hold a lock on a monitor. Any other threads attempting to lock that monitor are blocked until they can obtain a lock on that monitor" (JLS §17.1). Java uses it through the synchronized keyword, on a whole method (the lock is this) or on a block (you choose the lock object). Kotlin has no such keyword. It has the @Synchronized annotation, which "marks the JVM method generated from the annotated function as synchronized" (Kotlin API), and a stdlib function synchronized(lock) { } that "executes the given function block while holding the monitor of the given object lock" (Kotlin API).

run 1: @Synchronized = 2000000, synchronized(lock) = 2000000
run 2: @Synchronized = 2000000, synchronized(lock) = 2000000
run 3: @Synchronized = 2000000, synchronized(lock) = 2000000
reentrant: addTwice() -> 2
run 1: synchronized method = 2000000, synchronized (lock) = 2000000
run 2: synchronized method = 2000000, synchronized (lock) = 2000000
run 3: synchronized method = 2000000, synchronized (lock) = 2000000
reentrant: addTwice() -> 2

Correct every time. Notice that get() is synchronized too. Reading under the same lock is what guarantees you see the latest value; L27 explains why. addTwice() already holds the lock when it calls increment(), which needs the same lock, and that works because monitors are reentrant: "A thread t may lock a particular monitor multiple times; each unlock reverses the effect of one lock operation" (JLS §17.1).

What did each form compile to? A synchronized method is just a flag; a synchronized block is real instructions (L23):

$ javap -v -p SyncCounter        # Kotlin's @Synchronized fun increment()

A new Any()/new Object() per call means every thread holds its own private lock, so no thread ever waits. Locking on the boxed counter is sneakier. boxed++ creates a new Integer (L5: wrappers are immutable), so the next thread locks a different object. For values from −128 to 127 it might even share a cached box with unrelated code that locks on the same number. javac warns about it: Integer is a value-based class, and the docs say "synchronization on instances of value-based classes is strongly discouraged, because the programmer cannot guarantee exclusive ownership of the associated monitor" (Value-based Classes). Kotlin goes further and refuses to compile it:

The safe pattern is the one in BlockCounter: a private val lock = Any() / private final Object lock = new Object() field, created once, used for every access to the data it guards, and invisible to outside code. Never lock on a String literal either: identical literals are the same interned object (L5), so unrelated code could end up sharing your lock.

Tool 2: ReentrantLock

java.util.concurrent.locks.ReentrantLock is "a reentrant mutual exclusion Lock with the same basic behavior and semantics as the implicit monitor lock accessed using synchronized methods and statements, but with extended capabilities" (ReentrantLock API docs). Being explicit, it doesn't release itself. The docs: "It is recommended practice to always immediately follow a call to lock with a try block, and to always immediately call unlock as the first statement in the finally block" (L10's finally). Kotlin wraps that pattern in the withLock extension, which "executes the given action under this lock" (Kotlin API).

The extended capabilities are why you'd choose it over synchronized:

  • tryLock, with or without a timeout. As above, a thread can give up and do something else instead of waiting forever. That becomes a deadlock defence in L27.
  • Interruptible waiting with lockInterruptibly(). A thread stuck entering a synchronized block can't be interrupted.
  • Fairness. ReentrantLock(true) makes the lock "favor granting access to the longest-waiting thread", but the docs warn that fair locks "may display lower overall throughput (i.e., are slower; often much slower)".
  • Conditions (newCondition()), for more than one wait queue. You'll meet them with blocking queues in L27.

If you need none of these, synchronized is shorter and can't be left locked by mistake.

Tool 3: atomics and compare-and-set

The third option needs no lock at all. AtomicInteger.incrementAndGet() does the read-modify-write as one atomic hardware operation. Underneath is compare-and-set (CAS): compareAndSet(expected, new) "atomically sets the value to newValue if the current value == expectedValue" (AtomicInteger API docs), and returns false if another thread got there first. So you can build any atomic update yourself: read, compute, try to swap, and retry if you lost. The program below does exactly that and counts the retries:

incrementAndGet: 4000000
my CAS loop:     4000000 after 8119671 retries
LongAdder:       4000000
incrementAndGet: 4000000
my CAS loop:     4000000 after 9067867 retries
LongAdder:       4000000

All correct, but look at the retries. With 4 threads hammering one value, my CAS loop failed about twice for every success, and each failure is wasted work. CAS is optimistic: it assumes no conflict and pays when there is one. LongAdder solves heavy contention differently. It spreads the count over several internal cells and only adds them up when you call sum(). The docs: "under high contention, expected throughput of this class is significantly higher, at the expense of higher space consumption" (LongAdder API docs). It's perfect for statistics, and wrong when you need the exact current value in the middle of updates.

Kotlin 2.4 has its own atomics in kotlin.concurrent.atomics; on the JVM, AtomicInt "instances … are represented by java.util.concurrent.atomic.AtomicInteger" (Kotlin API). They're still experimental, though:

On my machine, and only for this extreme case of threads doing nothing but fighting over one counter:

  • Unsafe is fastest and wrong. Speed means nothing if the answer is wrong.
  • synchronized was the slowest under this heavy contention, and got slower as threads were added.
  • ReentrantLock beat synchronized by 2–18× here. A likely reason is the non-fair default: a thread that just released the lock can grab it again straight away, so one thread often does long runs of increments without a hand-off. That's an inference from the docs' description of non-fair locking, not something this program proves. The 2-thread row being slower than the 4-thread row shows how noisy single runs are.
  • AtomicInteger sits in between, paying for the CAS retries you counted earlier.
  • LongAdder barely notices the contention, as its docs promise.

Treat these numbers as a rough sketch: one run each, a crude timer, and a workload no real program has. For decisions that matter, use JMH (L24) on a workload that looks like yours. In real code a lock is usually held around a few microseconds of actual work, and uncontended locking is far cheaper than this table suggests.

Which one?

SituationReach for
Several fields that must change together, or check-then-actsynchronized / @Synchronized / synchronized(lock) { }
The same, but you need tryLock, timeouts, interruptible waits or fairnessReentrantLock + withLock / try-finally
A single number or reference updated on its ownAtomicInteger, AtomicLong, AtomicReference
A heavily contended counter you only read occasionallyLongAdder
Data that never changes after constructionnothing: share immutable objects freely (L5, L7)

Java Concurrency in Practice (ch. 2) sums the whole topic up in three options, paraphrased here: if several threads access the same mutable state without synchronization, the program is broken, and you can fix it by not sharing the state, by making it immutable, or by synchronizing every access to it. Confinement (Part 1's exercise), immutability, or locking. "Every access" includes reads.

What Kotlin does for you.
  • lock.withLock { … } writes the lock()/try/finally/unlock() dance for you, so you can't forget the unlock. It's inline, so there's no lambda object (L14).
  • synchronized(lock) { … } is an inline function that returns the block's value: fun get() = synchronized(lock) { count }.
  • It refuses to compile synchronized on an Int, where javac only warns.
  • The price: synchronized isn't a keyword. For a synchronized method you need the @Synchronized annotation, and for a synchronized getter @Synchronized get, which are easy to miss when you read Java examples.

Check

Two threads call increment(), where each call runs synchronized (new Object()) { count++; }. Is count safe?

A lock only excludes threads that lock the same object. A fresh object per call means nobody ever waits. WrongLock lost about 40,000–106,000 updates per run this way.

Kotlin: var n: Int? = 0 and then synchronized(n!!) { n = n!! + 1 }. What happens?

Kotlin 2.4 reports synchronizing on 'Int' is forbidden. javac only issues an [identity] warning for the Java equivalent, which then lost updates at runtime.

Why must lock.unlock() go in a finally block when you use ReentrantLock in Java?

An explicit lock isn't released automatically. If the body throws and unlock() is skipped, every other thread waits forever. synchronized gets this for free (the extra monitorexit in javap), and Kotlin's withLock writes the finally for you.

What does compareAndSet(5, 6) do if another thread already changed the value to 7?

CAS only writes when the current value equals the expected one. Otherwise it leaves the value alone and returns false, and your loop re-reads and tries again. Those were the millions of retries in Atomics.

A request counter is incremented by 200 threads and read once a minute by a dashboard. Best fit?

Heavy contention with rare reads is exactly LongAdder's job: "significantly higher" throughput under contention. A fair lock would be the slowest choice. A plain @Volatile var would still lose updates, since ++ isn't atomic (L27).

  • The reads are guarded too: @Synchronized get, withLock { count }, synchronized int value(). In this test join() would already make the final value visible, but a counter class can't know how callers will use it.

Exit quiz, recall card, sources

~5 min

Two threads add words to one plain HashMap with no locking. What should you expect? (L19)

HashMap is "not synchronized". In MapRace entries vanished and size() stopped matching the real contents, with no exception at all. Silent corruption is the dangerous outcome.

Which L10 construct guarantees that unlock() runs even when the locked code throws?

finally runs whether the try body completes or throws. The ReentrantLock docs make unlock() "the first statement in the finally block"; withLock and synchronized do it for you.

Why is locking on an Integer especially risky for small values like 42? (L5)

Integer.valueOf caches −128 to 127 (L5's Integer cache), so unrelated code using the same value can hold the very same object, and therefore the same monitor. Larger values get fresh boxes, so the lock changes on every ++.

Several threads read val config by lazy { load() } at the same time. How many times does load() run? (L15)

by lazy is synchronized by default: "the value is computed only in one thread, but all threads will see the same value". CheckThenAct printed created 1 time.
