Garbage Collection & Profiling

The JVM frees memory for you, so how can a Java or Kotlin program still run out of it? This lesson covers what the garbage collector actually does, how leaks happen anyway, and how to find where the time and memory really go, using only tools that ship with the JDK.

Recall from L4, L19, L22 and L23

From memory: no peeking

  2. Two variables a and b refer to the same object. You set a = null. Is the object garbage now? Why or why not? (L4, L5: aliasing)

Objects made with new, and the local variables of a running method: where does each live? (L4, L23)

Objects live on the heap. Each running method gets a stack frame holding its locals, and a local that refers to an object holds a reference into the heap (L4). Those locals are where the garbage collector starts looking, as Part 1 shows.

A method's first few thousand calls are slower than later ones. The main reason? (L23)

HotSpot interprets bytecode first and compiles hot methods later (L23). Any timing you take must allow for that warm-up, which is a big part of why Part 3 uses JMH.

A JVM started with -Xmx64m shows more than 64 MB of resident memory in ps. Why? (L22)

-Xmx caps the heap only. The process also needs memory for metaspace, thread stacks, compiled code and the JVM itself. Today we stay inside the heap.

Which call creates a LinkedHashMap in access order, the basis of L19's LRU cache?

The third argument, accessOrder = true, moves an entry to the end on every access. Override removeEldestEntry and the map evicts the least recently used entry. You'll use that to fix a leak in the final.

Part 1

Reachability, GC roots, generations

~30 min

You never call free on the JVM. So how does the garbage collector decide which objects to throw away? It never asks "is this object still needed?", because it can't know that. It asks a question it can answer: can the program still reach it? The Java API puts it like this: "A reachable object is any object that can be accessed in any potential continuing computation from any live thread" (java.lang.ref: Reachability, quoting JLS §12.6.1). Everything else is garbage, and "its memory can be reused by the VM when it can no longer be reached from any reference of any other live object in the running program" (HotSpot GC Tuning Guide, ch. 3).

Reaching has to start somewhere. Collectors start from GC roots: references the program can use without going through any other object. The ones you'll meet every day are:

  • Local variables and parameters in every active stack frame, on every thread (L4).
  • Static fields of loaded classes. In Kotlin, that includes every object declaration and top-level property.
  • Live Thread objects themselves, plus references held by native code (JNI), which you won't see in this course.

Mark, then sweep

The simplest tracing collector works in two phases. Mark starts at the roots and follows every reference, marking each object it reaches. Sweep then reclaims everything left unmarked. Step through it, because two of the results surprise most people:

Two takeaways:

  • Cycles don't keep anything alive. Unreachable objects that point at each other are still unreachable. Reachability is decided by tracing from the roots, never by counting references.
  • Only incoming references from live objects count. A dead object can point at a live one. That doesn't help the dead object.

Sweeping leaves holes between the survivors. Real collectors therefore also compact, sliding the survivors together, or they copy the survivors into a fresh area and treat the whole old area as free. Copying does mark-sweep-compact in one pass, and its cost depends on how many objects survive, not on how much garbage there is. That fact drives the next idea.

Generations: most objects die young

Tracing the entire heap on every collection would be slow for a big application. The tuning guide says "the time this approach takes is proportional to the number of live objects, which is prohibitive for large applications". HotSpot relies on an observation called the weak generational hypothesis, "which states that most objects survive for only a short period of time" (GC Tuning Guide, ch. 3). Think of every iterator, every temporary String and every StringBuilder you've written. So the heap is split up:

  • "The vast majority of objects are allocated in a pool dedicated to young objects (the young generation), and most objects die there. When the young generation fills up, it causes a minor collection in which only the young generation is collected."
  • "The young generation consists of eden and two survivor spaces. Most objects are initially allocated in eden." Live objects are copied between the survivor spaces until "they've been copied a certain number of times", and then they move to the old generation. "This process is also called aging."
  • "Eventually, the old generation fills up and must be collected, resulting in a major collection, in which the entire heap is collected."

How to read a line. The guide spells out the format: after the timestamp, the GC number, and the type and cause, comes "used before GC" -> "used after GC" ("heap size"), then the pause length (ch. 3). So 154M->25M(246M) 1.103ms means 154 MB in use, 25 MB left after the collection, a 246 MB heap, and the program stopped for about a millisecond.

The story the log tells:

  1. GC(16)–GC(27), young collections. Each one frees most of eden. But the "after" figure creeps up from 64M to 108M. Some orders survived long enough to be promoted, and died later, in the old generation, where young collections never look. This is the last step of the generations diagram.
  2. GC(28), a concurrent mark cycle. G1 traces the whole heap while the program keeps running, then stops it briefly for Remark. Usage drops from 123M to 35M, because completely empty old regions are reclaimed right away.
  3. GC(29)–GC(30), mixed collections. These are young collections that also clean up some old regions G1 now knows are mostly garbage.
  4. From GC(31) on, steady state. Every collection takes about 154M down to 25M in about 1.1 ms. The 25 MB that survives is the live window of 100,000 orders.
  5. The last line is the System.gc() call, a full collection. Only 1M survived because recent is no longer used after the loop, so the compiled code doesn't keep it alive. The JLS allows exactly that: "a Java compiler or code generator may choose to set a variable or parameter that will no longer be used to null" (JLS §12.6.1).

Same program, four collectors

Swap the collector with one flag and measure two things: how long the program took, and how long it was stopped. -Xlog:safepoint logs every stop-the-world pause the same way for all collectors, and a 6-line script adds them up:

# Summarise -Xlog:safepoint output: number of stop-the-world pauses, their total and the longest.
import re, sys

totals = [int(m.group(1)) / 1e6 for line in sys.stdin
          if (m := re.search(r"Total: (\d+) ns", line))]
print(f"pauses={len(totals)} total={sum(totals):.1f}ms max={max(totals):.2f}ms")

Serial stops the program for half its run time on one thread. ZGC pauses more often than any other, but every pause is tens of microseconds, because it does almost all its work concurrently. This is one toy program, though. A real service's best choice depends on its heap size, its live data and whether it cares more about throughput or latency. The guide's own advice is to "first run your application and allow the VM to select a collector" and to change it only when you have a measured reason (Selecting a Collector).

System.gc() is a request

The API docs: calling it "suggests that the Java Virtual Machine expend effort toward recycling unused objects", and "there is no guarantee that this effort will recycle any particular number of unused objects, reclaim any particular amount of space, or complete at any particular time, if at all" (System.gc). Operators can switch it off entirely with -XX:+DisableExplicitGC. I ran Churn with that flag, and the final Pause Full (System.gc()) line simply wasn't there. Don't sprinkle it into code to "help". G1 already decides when to collect better than you can.

And not finalize() either. Finalizers, which run "some time" before an object is reclaimed, were deprecated for removal in JDK 18 (JEP 421). The replacement for releasing files and sockets is try-with-resources / use (L10). For long-lived resources, use the java.lang.ref.Cleaner API, which "allows a program to register a cleaning action for an object that is run some time after the object becomes unreachable". Garbage collection manages memory. It isn't a resource-closing mechanism.

What Kotlin does for you.
  • Nothing different at runtime: Kotlin on the JVM runs on exactly the same heap and collectors, so everything in this part applies to both languages unchanged.
  • But Kotlin hides some roots. An object declaration and a top-level val both compile to static fields. In Part 2, javap shows object Sessions becoming public static final Sessions INSTANCE. A static field is a GC root for as long as its class is loaded, so anything it refers to lives that long.
  • Kotlin's use { }, like Java's try-with-resources, closes files and sockets deterministically. Neither relies on the GC.

"There is no guarantee …", and with -XX:+DisableExplicitGC it does nothing at all.

Part 2

Memory leaks in a garbage-collected language

~30 min

If the GC frees everything unreachable, how can memory leak? Because the GC can only free what's unreachable, not what's unneeded. LeakCanary's documentation defines it well: "In a Java based runtime, a memory leak is a programming error that causes an application to keep a reference to an object that is no longer needed. As a result, the memory allocated for that object cannot be reclaimed" (LeakCanary: Fundamentals). Effective Java Item 7 makes the same point: eliminate obsolete object references. Every leak below is a reference somebody forgot about.

Leak 1: the collection that only grows

The classic case: a static map, used as a cache or a registry, that things are added to and never removed from. Every login adds about 100 KB, and nobody ever logs out:

$ java -Xmx64m SessionLeak
sessions: 1
sessions: 101
sessions: 201
sessions: 301
sessions: 401
sessions: 501
sessions: 601

Exception: java.lang.OutOfMemoryError thrown from the UncaughtExceptionHandler in thread "main"

Both languages print exactly this. Look at the last line: the heap was so full that the JVM couldn't even allocate the memory to print the usual stack trace, so the error was thrown again while handling the error. Leaks often end this messily. The GC log shows what happened in the final moments, and it's the signature of a leak worth memorising:

$ java -Xmx64m -Xlog:gc SessionLeak
…
[7.412s][info][gc] GC(92) Pause Full (G1 Compaction Pause) 61M->61M(64M) 1.578ms
[7.412s][info][gc] GC(93) Pause Young (Normal) (G1 Evacuation Pause) 61M->61M(64M) 0.308ms
[7.414s][info][gc] GC(94) Pause Full (G1 Compaction Pause) 61M->61M(64M) 1.925ms
[7.416s][info][gc] GC(95) Pause Full (G1 Compaction Pause) 61M->61M(64M) 1.877ms

Full collections back to back that free nothing (61M->61M). Everything in the heap is reachable. The GC is doing its job perfectly, and the program is keeping everything.

The heap dump: a photo of every object

A histogram counts objects. A heap dump records every object and every reference, so a tool can show you the path from a GC root to the thing that's leaking. You can ask for one on demand with jcmd <pid> GC.heap_dump file.hprof, or have the JVM write one automatically at the moment it dies (-XX:+HeapDumpOnOutOfMemoryError):

A heap dump contains everything in memory, passwords and personal data included. Treat a production dump as sensitive.

Leak 2: listeners nobody removes

An object registers a callback with something long-lived, an event bus, a timer, a system service, and never unregisters. The long-lived object holds the callback, and the callback holds the object that created it.

$ java -Xmx64m Listeners
opened 20, listeners 20
opened 40, listeners 40
opened 60, listeners 60
Exception in thread "main" java.lang.OutOfMemoryError: Java heap space
	at java.base/jdk.internal.misc.Unsafe.allocateInstance(Native Method)
	…
	at Listeners$Screen.<init>(Listeners.java:19)
	at Listeners.main(Listeners.java:30)
$ java -Xmx64m Listeners fix
opened 20, listeners 0
opened 40, listeners 0
…
opened 480, listeners 0
opened 500, listeners 0

Every screen was "closed", but each one stayed reachable through the bus's listener list, holding its 1 MB bitmap: BUS (static, a root) → listeners → the lambda → its Screen → bitmap. The Kotlin version fails at the same point, with Screen.<init>(Listeners.kt:13) in the trace. One forgotten line, unsubscribe, is the whole difference.

Bridge: this is the classic Android leak. LeakCanary's docs: "an Android Activity instance is no longer needed after its onDestroy() method is called, and storing a reference to that instance in a static field prevents it from being garbage collected" (LeakCanary). An Activity holds its whole screen of views and bitmaps, so leaking one leaks megabytes, and rotating the phone creates a new Activity every time. LeakCanary is a library that detects exactly this and shows the reference path.

Leak 3: a key you can never find again

From L19: if a key's hashCode changes while it's in a HashMap or HashSet, lookups go to the wrong bucket. That makes it a leak too, because something you can't find, you can't remove:

removed? false, size 1
removed? false, size 2
removed? false, size 3

Every remove fails and the set only grows. In Kotlin, one keyword causes this: data class Cell(var row: Int) generates equals/hashCode from a mutable property. Use val for anything that goes into a hash key.

Leak 4: callbacks that capture their creator

L17 said to make nested node classes static in Java, because a non-static inner class holds a hidden reference to its outer instance. Does a callback keep its creator alive? Test it instead of guessing. Each check keeps only the callback, drops the screen, requests a GC and looks through a WeakReference (more on those below):

object, ignores screen: collected
object, uses bitmap:    STILL ALIVE
lambda, ignores screen: collected
lambda, uses bitmap:    STILL ALIVE
anonymous, ignores screen: collected
anonymous, uses bitmap:    STILL ALIVE
lambda, ignores screen:    collected
lambda, uses bitmap:       STILL ALIVE

javap shows why. Only the class that uses the screen gets a field pointing to it:

$ javap -p 'Capture$Screen$1.class' 'Capture$Screen$2.class'
class Capture$Screen$1 implements java.lang.Runnable {
  Capture$Screen$1(Capture$Screen);
  public void run();
}
class Capture$Screen$2 implements java.lang.Runnable {
  final Capture$Screen this$0;
  Capture$Screen$2(Capture$Screen);
  public void run();
}
$ javap -p 'Screen$objectIgnoringScreen$1.class' 'Screen$objectUsingScreen$1.class'
public final class Screen$objectIgnoringScreen$1 implements java.lang.Runnable {
  Screen$objectIgnoringScreen$1();
  public void run();
}
public final class Screen$objectUsingScreen$1 implements java.lang.Runnable {
  final Screen this$0;
  Screen$objectUsingScreen$1(Screen);
  public void run();
}

Older Java tutorials say every anonymous or inner class captures its outer instance. That was true until JDK 17. The JDK 18 release notes: "Prior to JDK 18, when javac compiles an inner class it always generates a private synthetic field with a name starting with this$ … Starting in JDK 18, unused this$ fields are omitted", which "avoids a source of potential memory leaks" (JDK 18 release notes: Enclosing Instance Fields Omitted). Serializable classes are not affected. The rule that matters today is the same in both languages: a callback that touches anything of its creator's, even one field, keeps the whole creator alive. If it needs only one value, copy it into a local first. I checked that val size = bitmap.size; Runnable { println(size) } lets the screen be collected, in both languages.

Leak 5, briefly: ThreadLocal in a thread pool

"Each thread holds an implicit reference to its copy of a thread-local variable as long as the thread is alive" (ThreadLocal). In a thread pool, threads live as long as the application, so anything you put in a ThreadLocal and forget to remove() lives that long too. It's a common leak in servers. Thread pools come in Phase 8.

The fixes

  1. Bound what grows. Caches get a maximum size and an eviction policy, like L19's LRU. The final exercise does exactly this.
  2. Pair every register with an unregister. Tie the unregister to the end of the object's life: close(), onDestroy(), a use { } block.
  3. Hold references weakly when the holder shouldn't keep things alive. A WeakReference is a reference the GC ignores when deciding reachability. Weak references "do not prevent their referents from being made finalizable, finalized, and then reclaimed" (WeakReference). A WeakHashMap holds its keys weakly:
before: entries=2 ref=settings
after:  entries=2 ref=null
later:  entries=1
home still there: row 12

Both languages print this, every time I ran it. Look closely at the after line. The GC had already cleared the weak reference (ref=null), but the map still reported 2 entries. A WeakHashMap removes stale entries only after the JVM has queued the cleared references for it, and that happens on another thread shortly afterwards. The docs warn that a WeakHashMap "may behave as though an unknown thread is silently removing entries" (WeakHashMap). Two more cautions from the same page: it's "intended primarily for use with key objects whose equals methods test for object identity", and the values are held strongly, so "care should be taken to ensure that value objects do not strongly refer to their own keys". Weak references are a precise tool. They aren't a general fix for forgetting to clean up.

What Kotlin does for you, and what it doesn't.
  • Kotlin makes Leak 1 easy to write without noticing: object Sessions { val all = HashMap… } looks harmless, but javap shows private static final java.util.HashMap<…> all and public static final Sessions INSTANCE. That's a GC root forever.
  • It nudges you away from Leak 3: prefer val in data classes, because var properties feed straight into the generated hashCode.
  • On Leak 4 the two languages now agree: Kotlin lambdas and object expressions, like Java 18+ lambdas and anonymous classes, capture their creator only if they use it.
  • WeakReference, WeakHashMap and ThreadLocal are the same java.* classes in both languages. Kotlin adds no wrappers on the JVM.

Check

A GC log ends with several Pause Full … 61M->61M(64M) lines in a row. The most likely cause?

A full collection that frees nothing means every object is reachable. Either the heap is too small for genuinely live data, or something is holding references it no longer needs.

The top line of a GC.class_histogram is [B. What's your next step?

byte[] is the payload in almost every program. Look for the count of your own classes that only grows, then find what holds them, which is where a heap dump helps.

JDK 26: an anonymous Runnable inside a method of Screen prints only "tick". Does it keep the screen alive?

Since JDK 18, javac omits the unused this$0 field, and Capture.java showed the screen collected. Touch one field and it's captured.

Right after System.gc(), a WeakReference returns null but its WeakHashMap still reports the entry. Why?

The cleared references are queued on another thread, and the map drops stale entries when it next looks at that queue. 100 ms later, entries=1.

Kotlin: object Registry { val items = mutableListOf<Item>() }. When can the list's items be collected?

An object compiles to a static field, which is a GC root for the life of the class, effectively the whole program. Its contents live until you remove them.

Part 3

Profiling: where do the time and memory go?

~30 min

When a program is slow, everyone has a theory. Theories about performance are usually wrong. In L16 and L21 the culprits were things nobody suspects by reading the code: a contains inside a loop, a list that grew by +10. A profiler replaces the theory with a measurement. It samples what the program is actually doing and tells you where the time goes. The JDK has one built in.

JDK Flight Recorder

JDK Flight Recorder (JFR) is "a low-overhead data collection framework for troubleshooting Java applications and the HotSpot JVM" (JEP 328). You switch it on with one JVM flag, and read the recording with the jfr tool (the jfr command).

Microbenchmarks: JMH

A profiler finds the slow part of a whole program. Sometimes you want to compare two small pieces of code in isolation, like + versus StringBuilder, or ArrayList versus LinkedList. In L16 you timed things with nanoTime and warm-up loops, and you saw how noisy that was. The professional tool is JMH, "a Java harness for building, running, and analysing nano/micro/milli/macro benchmarks", written by the JDK's own performance engineers. It handles warm-up, forking a fresh JVM, statistics, and the problem that silently ruins hand-written benchmarks: the JIT deleting the code you're timing.

JMH's README recommends a Maven archetype. Most Gradle users use the community plugin me.champeau.jmh, and I checked that its current version, 0.7.3, works with Gradle 9.7.1 (Gradle plugin portal, plugin README). Leave out warmup and timeOnIteration and JMH uses 10-second iterations. My first run with the defaults took 5 minutes and 20 seconds for four benchmarks.

  • @Benchmark marks a method to measure. @State marks a class whose fields hold the benchmark's data. @Param runs everything once per value. @BenchmarkMode(Mode.AverageTime) reports time per call (JMH samples).

Why JMH: the JIT deletes unused work

The JIT compiler (L23) removes code whose result is never used. That's great for your program and fatal for a benchmark. JMH's own sample says "the downfall of many benchmarks is Dead-Code Elimination (DCE)" (JMHSample_08_DeadCode). Watch it happen:

Benchmark                         (n)  Mode  Cnt    Score    Error  Units
DeadCodeBench.baseline            N/A  avgt    5    0.241 ±  0.001  ns/op
DeadCodeBench.resultIgnored       N/A  avgt    5    0.241 ±  0.001  ns/op
DeadCodeBench.resultReturned      N/A  avgt    5  430.442 ±  0.873  ns/op
DeadCodeBench.resultToBlackhole   N/A  avgt    5  426.886 ±  0.583  ns/op

A 1,000-step loop "taking" 0.241 ns, exactly as long as an empty method, didn't run at all. The JIT proved sum was unused and deleted the loop. Return the value, or pass it to a Blackhole, and the real cost appears: about 430 ns. Returned results "are implicitly consumed by Blackholes" (JMHSample_09). A hand-rolled nanoTime loop has the same problem, and nothing warns you. The other traps JMH handles are constant folding (sample 10), which is why x and n are fields and not constants, and JIT warm-up.

A detail that shows how slippery this is: my first version of resultIgnored computed Math.log(x) and threw the result away. On the JDK 21 that Gradle used, it took 3.1 ns (not deleted). Running the same benchmark jar directly on JDK 26, it took 0.26 ns (deleted). What the JIT removes changes between JDK versions, which is exactly why you let JMH guard against it rather than reasoning it out yourself.

A profiling checklist

  1. Reproduce the problem with realistic data, and measure the baseline: total time, or memory over time.
  2. Record, don't guess. JFR (-XX:StartFlightRecording) for time and allocation, a GC log and jstat for memory, GC.class_histogram and heap dumps for leaks.
  3. Find the biggest single cost in hot-methods or a flame graph, and follow its stack down to your code.
  4. Fix that one thing, then measure again with the same data. A fix you didn't measure is a guess.
  5. Use JMH only to compare small alternatives in isolation, never to judge a whole program.
What Kotlin does for you, and what it costs.
  • Kotlin's String.matches on the JVM takes a Regex, not a String. Passing a string fails with argument type mismatch: actual type is 'String', but 'Regex' was expected. That nudges you toward building a Regex object. Keeping it in a val outside the function, so it's compiled once, is still on you.
  • JFR, jcmd and the IntelliJ Profiler work on Kotlin unchanged. Stacks show Kotlin's generated names, like EmailsKt.isValid for a top-level function in Emails.kt.
  • JMH needs open (or all-open) in Kotlin, the price of final-by-default classes. In Java nothing is final unless you say so.
  • For quick, rough timings Kotlin has measureTime { } (L16). For anything you'll make decisions on, use JMH.

Wrap-up

Exit quiz, recall card, sources

~5 min

L10: a FileInputStream is never closed, but the stream object becomes unreachable. Is the file descriptor released at once?

The GC manages memory, not files, and it runs whenever it likes. Close resources deterministically with try-with-resources / use. Finalizers are deprecated for removal.

L16 + L24: a JMH benchmark shows a method taking about 4× longer every time n doubles. Its complexity?

The L16 doubling rule: a ratio of 4 means quadratic. plusInLoop behaved similarly, about 38× for 10× more input.

L19 + L24: why is a data class Key(var id: Int) risky as a HashMap key?

The generated hashCode uses id. Change it and the entry sits in the wrong bucket. You can't find it and can't remove it, which is a leak (LostKey).

L23 + L24: why does JMH run warm-up iterations before measuring?

Early calls run in the interpreter or lower JIT tiers (L23). Measuring them would mix up warm-up cost with steady-state speed.
