Part 1

suspend, launch/async, structured concurrency

~30 min

A function that can pause without blocking

The Kotlin docs: "Coroutines can suspend their execution instead of blocking a thread", and "when a coroutine suspends, the thread isn't blocked and remains free to run other tasks" (Coroutines basics). The building block is the suspending function, marked suspend. "You can only call a suspending function from another suspending function", or from a coroutine builder like runBlocking, which "blocks the current thread until the coroutines launched in that scope finish".

Here is the difference, measured on one thread. Ten thousand coroutines each delay(100), and then twenty each call Thread.sleep(100):

10,000 x delay(100):     134.079417ms
20 x Thread.sleep(100):  2.125183625s
all on thread: main
10,000 callbacks after 100ms: 118ms
20 x Thread.sleep(100):       2143ms
  • 10,000 delays took about 0.13 s on a single thread. Each delay hands the thread back, and a timer resumes the coroutine 100 ms later.
  • 20 sleeps took 2.1 s: 20 × 100 ms, one after another. Thread.sleep blocks the only thread, so nothing else can run. Never call blocking code from a coroutine on a thread you care about. Part 2 shows the fix.
  • Java can do the fast version too, but only by turning the work inside out into callbacks scheduled on a timer. You'll see that shape again in a moment, and it's exactly what the Kotlin compiler builds for you.

What the compiler does with suspend

There's no magic in the JVM: a suspending function is still an ordinary method. The coroutines design document says "suspending functions are implemented via Continuation-Passing-Style (CPS)", and "a suspending function is compiled to a state machine, where states correspond to suspension points" (KEEP: coroutines). A continuation "is a state of the suspended coroutine at suspension point". In other words, it is "the rest of the function", plus the local variables it needs.

  • A state machine. The label field and the tableswitch (L23) choose where to resume. There are three states for two suspension points.
  • Locals move to the heap. Before each suspension, id and name are copied into fields of the continuation object (I$0, L$0). The thread's stack frame (L4) is thrown away when the function returns COROUTINE_SUSPENDED, so a suspended coroutine costs a small heap object, not a whole thread stack.

CpsByHand.java is the same program, with the continuation written as a lambda. Two suspension points already means two nested callbacks. The compiler's state machine is that callback chain, flattened, with loops and try/catch still working.

Builders: launch, async, runBlocking

A coroutine builder starts a coroutine. launch is fire-and-forget and returns a Job. async returns a Deferred<T>, a Job with a result you get with await(). The guide puts it simply: "Conceptually, async is just like launch", except that it returns a value (Composing suspending functions).

launch done
sequential total 90
  took ~613 ms
concurrent total 90
  took ~313 ms
submit done
sequential total 90
  took ~620 ms
concurrent total 90
  took ~302 ms

Sequential by default. Two plain calls to a suspending function run one after another, 300 + 300 ms. That's deliberate: code that looks sequential is sequential. You opt into concurrency explicitly with async, and the guide says it's "twice as fast, because the two coroutines execute concurrently". On the Java side, the same opt-in is supplyAsync plus join.

Structured concurrency

The most important idea in this lesson. The docs: "coroutines form a tree hierarchy of parent and child tasks with linked lifecycles. A parent coroutine waits for its children to complete before it finishes. If the parent coroutine fails or gets canceled, all its child coroutines are recursively canceled too." And to keep that true, "new coroutines can only be launched in a CoroutineScope that defines and manages their lifecycle" (Coroutines basics).

1. coroutineScope waits for every child
  A finished
  B finished
   scope returned after both
2. one child fails: siblings cancelled, error rethrown
  C cancelled
   caught: D failed
3. supervisorScope: a failure stays local
  E finished
   E -> E
   F -> F failed

Both programs print exactly this. (The Java one needs java --enable-preview --source 26 Structured.java.)

  1. coroutineScope doesn't return until every child has finished. No coroutine can leak out and keep running after the function that started it has returned.
  2. One failure cancels the siblings. D throws at 100 ms. The scope cancels C, which is still in delay, then rethrows D's exception to the caller. This is the right default for "I need all of these results".
  3. supervisorScope keeps failures local. "A failure or cancellation of a child does not propagate to the supervisor job or its other children" (Exception handling). E finishes. F's exception waits inside its Deferred until you await() it. This is the right choice for "show whatever succeeded", and it's what the final uses.

Without the flag, javac really says error: StructuredTaskScope is a preview API and is disabled by default. Its default policy matches coroutineScope, failing and cancelling the rest, and Joiner.awaitAll() matches the supervisor. Note that cancellation there is interruption: C saw an InterruptedException from sleep.

Cancellation is cooperative

"In Kotlin, coroutine cancellation is cooperative" (Cancellation and timeouts). Cancelling only asks. Suspending functions like delay check for it and throw CancellationException, but a busy CPU loop never asks, so it never stops:

stubborn: loop ran to the end anyway
stubborn: cancelAndJoin took 439 ms
polite: cancelAndJoin took 1 ms
withTimeoutOrNull -> null
cleanup ran after cancellation
caught TimeoutCancellationException: Timed out waiting for 200 ms
stubborn: loop ran to the end anyway
stubborn: interrupt+join took 440 ms
polite: interrupt+join took 0 ms
completeOnTimeout -> null
  • Stubborn ignored cancel() and ran its full 500 ms. Polite calls ensureActive() on every iteration, which throws as soon as the job is cancelled, so it stopped in 1 ms. isActive (check a flag yourself) and yield() (suspend briefly) work too.
  • Java's interruption works the same way: interrupt() only sets a flag, and the loop has to check isInterrupted(). The difference is that every delay, await and withContext in coroutine code checks for you.
  • withTimeout cancels its block and throws TimeoutCancellationException. withTimeoutOrNull returns null instead.
  • Suspending cleanup needs NonCancellable. Inside a cancelled coroutine, any suspending call in finally would itself throw CancellationException. The docs: "pass NonCancellable as an argument to the withContext() coroutine builder function", for example to close resources with a suspending close().
  • Java's completeOnTimeout gives up waiting but doesn't stop the work. The sleeping task is still running. In coroutines, timing out a block cancels the block.

Never swallow CancellationException. It's how cancellation travels. A catch (e: Exception) around a suspending call catches it too (it's an IllegalStateException subclass), and if you don't rethrow it, the coroutine keeps going as if nothing happened. That's why Structured.kt catches it, prints, and rethrows. L10's rule about broad catches matters even more here.

Exceptions: launch vs async

The guide: builders come "in two flavors: propagating exceptions automatically (launch) or exposing them to users (async …)". At the root, launch treats exceptions "as uncaught exceptions, similar to Java's Thread.uncaughtExceptionHandler", while async relies "on the user to consume the final exception, for example via await" (Exception handling).

async failed quietly so far: isCompleted=true
await threw: bad input
handler got: launch blew up
main still running
future failed quietly so far: isDone=true
join threw: bad input
handler got: thread blew up
main still running

The mapping is clean: async behaves like a CompletableFuture, where the exception waits for whoever reads the result. launch behaves like a Thread, where nobody reads a result, so the exception goes to a handler. A CoroutineExceptionHandler "is invoked only on uncaught exceptions — exceptions that were not handled in any other way". It's a last-resort logger, not a way to recover.

What about GlobalScope? You'll see GlobalScope.launch { … } in old tutorials. Its API docs warn: "This is a delicate API. GlobalScope is easy to use to create new coroutines, avoiding all bureaucracy of structured concurrency, but it also means losing all its benefits" (GlobalScope). Nobody waits for those coroutines and nobody cancels them: they're L24's leaks waiting to happen. Use coroutineScope, or a scope tied to a lifecycle.

What Kotlin does for you.
  • suspend makes the compiler write the continuation, the state machine and the saved locals that CpsByHand.java writes by hand. Your code keeps its shape: loops, try/catch and early return all work across suspension points.
  • Structured concurrency is the default. A scope waits for its children and cancels them on failure, with no executor to close and no futures to track. Java's version, StructuredTaskScope, is still a preview in JDK 26.
  • Every suspending call is a cancellation check, so most coroutine code is cancellable without you writing any checks. Java code has to check the interrupt flag itself, and orTimeout/completeOnTimeout don't stop the underlying work.
  • withTimeout, NonCancellable and supervisorScope are one-liners for policies you'd assemble by hand in Java.

Check

Why did 10,000 × delay(100) finish in about 0.13 s on one thread?

A suspended coroutine holds no thread, so the one thread was free to start all 10,000. A timer resumed them about 100 ms later. Thread names in the output prove it: everything ran on main.

javap shows fetchUser(int, Continuation) returning Object, not String. Why?

A suspend function returns either its real result or COROUTINE_SUSPENDED. The KEEP calls that a union "that cannot be expressed in Kotlin's type system", so the JVM signature uses Object.

Inside coroutineScope, child D throws at 100 ms while sibling C is in delay(300). What happens to C?

D's failure cancels the parent, which cancels every other child. C's delay throws CancellationException, and Structured.kt printed C cancelled. With supervisorScope, C would have kept running.

val j = launch(Dispatchers.Default) { while (true) { x++ } }, then j.cancelAndJoin(). What happens?

Cancellation is cooperative. The loop never suspends or checks isActive, so it never notices it was cancelled, and cancelAndJoin waits forever. Add ensureActive() inside the loop.

Which builder returns a Deferred whose exception waits until someone calls await()?

async exposes its exception to whoever awaits, like a CompletableFuture. launch propagates it up the Job tree at once, like an uncaught exception in a thread.

Part 2

Dispatchers and the "main thread"

~20 min

A coroutine needs some thread to run on whenever it isn't suspended. The dispatcher chooses which one: it "can confine coroutine execution to a specific thread, dispatch it to a thread pool, or let it run unconfined" (Coroutine context and dispatchers). There are three built-in ones you'll use:

DispatcherForThreads (from the API docs)
Dispatchers.DefaultCPU work"equal to the number of CPU cores, but is at least two" (Default): 18 on this machine
Dispatchers.IOblocking I/O"the limit of 64 threads or the number of cores (whichever is larger)"; it "and its views share threads with the Default dispatcher" (IO)
Dispatchers.MainUI updatesthe single UI thread. It only exists if you add a UI artifact such as kotlinx-coroutines-android, -javafx or -swing (Main)

withContext(dispatcher) { … } runs a block on another dispatcher and then comes back, which "may suspend the current coroutine and switch to a new context". Print thread names to see who runs what:

  • IO and Default printed the same thread. They share one pool, as the docs say. A switch from Default to IO often doesn't change threads at all; it only changes which limit applies.
  • Unconfined starts in the caller's thread and resumes in whatever thread did the resuming. Here that was the timer thread behind delay. The guide calls it "a different mechanism", so leave it for special cases.
  • Java makes you pick an executor for each task. The virtual-thread line shows something similar to a coroutine: a virtual thread runs on a carrier thread (@ForkJoinPool-1-worker-1), and after blocking it may resume on a different one.

The "main thread" idea

UI toolkits use a single thread that draws the screen and handles input. Android calls it the main thread. If you block it, the app freezes. Android's docs list "slow operations involving I/O on the main thread" and "a long calculation on the main thread" as causes of ANRs ("Application Not Responding"). One trigger is an app that hasn't "responded to an input event (such as a key press or screen touch) within 5 seconds" (Android: ANRs). Servers have the same issue in a different form: when every request thread in a pool is blocked, new requests wait in a queue (L28).

Bridge. Android's coroutine guide asks for main-safe functions, which move their own slow work off the main thread with withContext, and for injected dispatchers so tests can swap them (Best practices for coroutines in Android). That's exactly the shape of screen(), minus the real UI.

Shared mutable state, again

Coroutines on Dispatchers.Default run in parallel on many threads, so everything from L26 and L27 still applies: count++ is a read, an add and a write. 1,000 coroutines × 1,000 increments:

plain var, run 1: 347852
plain var, run 2: 841839
plain var, run 3: 680244
Mutex:           1000000  (177 ms)
AtomicInteger:   1000000  (31 ms)
confined:        1000000  (6 ms)
Channel owner:   1000000  (121 ms)
plain field, run 1: 255130
plain field, run 2: 569672
plain field, run 3: 876000
ReentrantLock:     1000000  (12 ms)
AtomicInteger:     1000000  (7 ms)

  • Lost updates, and a different number every run. Yours will differ. Being "lightweight" doesn't make coroutines safe.
  • Mutex is the coroutine lock. "The key difference is that Mutex.lock() is a suspending function" (Shared mutable state): a waiting coroutine suspends instead of blocking its thread. withLock is the try/finally version. It was the slowest here, because this loop does nothing but fight over the lock.
  • Atomics work unchanged, because they're JVM classes (L26).
  • Confinement was the fastest. Dispatchers.Default.limitedParallelism(1) runs at most one of these coroutines at a time, so the plain var is safe. The API docs: it "only guarantees that at most parallelism coroutines are executed at the same time" (limitedParallelism). The guide calls this thread confinement.
  • An owner coroutine plus a Channel is the message-passing style: only one coroutine touches the counter, and everyone else sends it messages. (The older actor builder does the same thing.)

Never block a Default thread

Default has exactly as many threads as cores. Fill them all with blocking calls and every other coroutine waits, even a trivial one:

blocking: quick job ran at 1007 ms
IO fix:   quick job ran at 52 ms
blocking:    quick job ran at 1004 ms
io pool fix: quick job ran at 57 ms

Eighteen Thread.sleep(1000) calls occupied all 18 Default threads, so the quick job waited a full second. With the blocking calls wrapped in withContext(Dispatchers.IO), it ran at 52 ms. This is the same thread-pool starvation as L28's fixed pool. Rule: Default for computing, IO for blocking calls you can't avoid, and suspending APIs when they exist.

Testing with virtual time

A function that waits 10 seconds shouldn't make its test wait 10 seconds. The test library kotlinx-coroutines-test provides runTest, which "behaves similarly to runBlocking, with the difference that the code that it runs will skip delays", and "delay-skipping is achieved by using virtual time" (runTest). Add testImplementation("org.jetbrains.kotlinx:kotlinx-coroutines-test:1.11.0"):

$ ./gradlew test
VirtualTimeTest > advanceTimeBy moves the virtual clock() PASSED
VirtualTimeTest > a ten second delay takes no real time() STANDARD_OUT
    virtual 10000 ms took 0 ms of real time
VirtualTimeTest > a ten second delay takes no real time() PASSED

Ten virtual seconds took 0 ms of real time. currentTime and advanceTimeBy are marked experimental, so without the @OptIn line the compiler warns: This declaration needs opt-in. Its usage should be marked with '@kotlinx.coroutines.ExperimentalCoroutinesApi' or '@OptIn(kotlinx.coroutines.ExperimentalCoroutinesApi::class)'. Java has nothing like this built in. A Java test of a 10-second timeout really waits 10 seconds, unless you design your code to take an injectable clock or scheduler.

What Kotlin does for you.
  • withContext(Dispatchers.IO) { … } hops threads and comes back to the original dispatcher by itself. The Java version chains supplyAsync(…, io).thenAcceptAsync(…, ui) and loses the ordinary flow of the method.
  • Ready-made, sensibly sized pools: Default (cores) and IO (64, elastic, sharing the same threads), instead of choosing and closing executors yourself.
  • Mutex waits by suspending, not blocking, and limitedParallelism(1) gives confinement without a dedicated thread.
  • runTest gives you a virtual clock, so time-based code is testable in milliseconds.

Part 3

Flow: streams of values over time

~20 min

A suspend function returns one value, later. A Flow delivers many values, over time: sensor readings, search results as you type, the current state of a screen. The docs: "Cold flows start producing values when collected", and "Like sequences, cold flows are lazy. The code block of a cold flow builder doesn't run until a collector collects it" (Flows). It's L15's sequence { yield() }, except that the body may suspend: it can call delay, a network API, or anything else that suspends.

  • Lazy and cold. Nothing ran until collect. Collecting a second time ran the whole block again ("flow block starts" twice), the same way L15's sequences re-run.
  • Sequence vs Flow. A Sequence is pulled synchronously: the consumer asks, and the producer runs on the same thread right then. A Flow is suspend-based: emit suspends until the collector has processed the value, so producer and collector take turns without blocking threads.
  • Java's nearest equivalent is java.util.concurrent.Flow: four interfaces that "correspond to the reactive-streams specification", with flow control through Subscription.request(n) (Flow). The JDK's only implementation, SubmissionPublisher, "asynchronously issues submitted (non-null) items to current subscribers" (SubmissionPublisher). That makes it hot: items submitted before you subscribe are simply missed. For operators like map and filter, Java developers use libraries such as Reactor or RxJava. The JDK has none built in.

Operators

Flows have the operators you know from L14 and L15, and they're lazy and run element by element, like a sequence:

  • take(3) stopped the source at 6, so values 7–10 were never produced (L15's short-circuiting).
  • onCompletion runs when the flow ends for any reason, like finally. transform can emit zero or more values per input. catch handles exceptions from upstream and can emit a fallback value.
  • flowOn(Dispatchers.IO) changes the dispatcher of everything above it. The emitting ran on a worker thread and the collecting stayed on main. The docs: "By default, a cold flow runs in the same coroutine context as the collector." That's how an Android screen collects on the main thread while the data loads in the background.

Slow collectors: buffer and conflate

By default the producer waits for the collector at every emit. When the collector is slower, you choose what happens:

1 2 3   <- no buffer: 1232 ms
1 2 3   <- buffer(): 1022 ms
1 3   <- conflate(): 715 ms
1 2 3 4 5 6  <- submit (waits): 1926 ms
1 2 4  <- offer (drops):  1010 ms
  • No buffer: each value costs 100 + 300 ms in turn. 3 × 400 ≈ 1.2 s.
  • buffer() lets the producer run ahead while the collector works. The making and the using overlap: 100 + 3 × 300 ≈ 1.0 s.
  • conflate() keeps only the newest value. The collector "always gets the most recent value emitted", and values it was too slow for are dropped (conflate). Value 2 was never seen: right for a temperature display, wrong for a bank ledger.
  • Java has the same two choices on SubmissionPublisher's bounded buffer: submit blocks the producer until there's room, and offer with a drop handler throws values away. Three runs printed the same 1 2 4 each time.

Combining flows

zip     20C  at 414 ms

combine 20C  at 411 ms
combine 21C  at 613 ms
combine 21F  at 816 ms
combine 22F  at 913 ms

zip pairs values one-to-one and stops when the shorter flow ends. combine emits the latest of each whenever either side changes, which is what you want for "filter text + sort order → results".

  • StateFlow always has a value (it started at 0), and you can read it any time with .value. "Updates to the value are always conflated", and equal values are skipped "using Any.equals comparison in a similar way to distinctUntilChanged" (StateFlow). So the collector never saw 1, which was overwritten before it ran, or the second 2.
  • Bridge. Android's docs: "StateFlow is a great fit for classes that need to maintain an observable mutable state", for example a ViewModel exposing UI state (StateFlow and SharedFlow). On the server side, Spring supports suspend controller methods and Flow return values in Spring MVC and WebFlux (Spring: Coroutines).
  • SharedFlow has no current value and broadcasts each event to every active collector: good for one-off events like "saved". Java's SubmissionPublisher is the nearest thing. Its run printed B before A for "saved", and that order varies between runs. The JDK has no equivalent of StateFlow.
What Kotlin does for you.
  • flow { emit(x) } is a normal loop that can suspend. Backpressure is automatic, because emit suspends until the collector is ready. Java's Flow makes you implement Subscriber, call request(n) yourself, and handle every signal by hand.
  • A full operator set ships with the library (map, filter, take, catch, buffer, conflate, combine, flowOn). The JDK has none, so Java needs Reactor or RxJava.
  • Cancellation and structured concurrency apply to flows too: when the collecting coroutine is cancelled, the producer stops.
  • StateFlow gives you an observable "current value" with conflation and de-duplication built in.

Part 4

Coroutines vs virtual threads

~10 min

L28's virtual threads and today's coroutines solve the same problem: huge numbers of tasks that spend most of their time waiting. Same workload, both ways. 100,000 tasks each wait one second:

100000 coroutines x delay(1000): 1352 ms, peak heap ~49 MB
100000 coroutines x delay(1000): 1354 ms, peak heap ~49 MB
100000 coroutines x delay(1000): 1343 ms, peak heap ~49 MB
100000 virtual threads x sleep(1000): 1433 ms, peak heap ~118 MB
100000 virtual threads x sleep(1000): 1434 ms, peak heap ~119 MB
100000 virtual threads x sleep(1000): 1393 ms, peak heap ~152 MB

Both finished in about 1.4 s, so 100,000 waits ran concurrently either way. Coroutines used less heap here: a suspended coroutine is a small continuation object (Part 1), while "the stacks of virtual threads are stored in Java's garbage-collected heap as stack chunk objects" (JEP 444). Treat these numbers as rough. The peak is sampled every 5 ms and depends on when the GC runs (L24), so it isn't a benchmark. JMH (L24) is the tool for careful numbers. With the same code at 10,000 and 1,000,000 tasks, the trend held. That's the exercise below.

They work together

Coroutine code sometimes has to call a blocking library, like an old JDBC driver. Dispatchers.IO caps it at 64 threads, but a virtual-thread executor can be turned into a dispatcher:

1000 blocking calls on Dispatchers.IO:   1652 ms
1000 blocking calls on virtual threads:   114 ms

On IO, 1,000 blocking calls of 100 ms each ran 64 at a time: about 16 rounds, or 1.65 s. On virtual threads they all overlapped: 114 ms.

When to choose which. On Android or in any Kotlin codebase, use coroutines: virtual threads aren't available on Android, and Flow and StateFlow are how modern Android UIs work. In a Java server, especially one that already uses blocking libraries, use virtual threads: Spring Boot switches to them with one property, spring.threads.virtual.enabled=true on Java 21+ (Spring Boot: Task Execution). In Kotlin on a server, coroutines for your own code and a virtual-thread dispatcher for unavoidable blocking calls is a sound combination.

What Kotlin does for you.
  • Coroutines are a library, so the same code runs on the JVM, on Android (where there are no virtual threads), and on Kotlin's other targets.
  • asCoroutineDispatcher() turns any Java Executor, including a virtual-thread one, into a dispatcher, so you get both worlds in one line.

You're writing an Android app. Which of the two can you actually use there?

Android's Thread.isVirtual() "always returns false because virtual thread isn't implemented on Android yet". Coroutines are a library and run anywhere Kotlin runs.

Coroutine code must call a blocking driver 1,000 times at once. Fastest option from Interop.kt?

What is the main cost of coroutines compared with virtual threads?

A suspending function can only be called from a coroutine or another suspending function, so suspend spreads up the call chain. Virtual threads keep plain blocking code. In exchange, coroutines give you structure, cancellation, Flow and Android support.

Wrap-up

Exit quiz, recall card, sources

~5 min

Why did 1,000 coroutines doing plain++ on Dispatchers.Default lose updates? (L26 + L29)

count++ is three steps (L23's bytecode showed it), and Default runs coroutines in parallel on 18 threads. Lightweight doesn't mean safe.

A suspending call is wrapped in try { … } catch (e: Exception) { log(e) }, and the coroutine gets cancelled. What's the problem? (L10 + L29)

CancellationException is an Exception. Catching it without rethrowing stops cancellation from travelling, so the coroutine keeps running. Catch specific exceptions, or rethrow CancellationException.

Where do a suspended coroutine's local variables live? (L4 + L29)

javap showed fields like I$0 and L$0 on CpsKt$fetchUser$1: the locals are copied into a heap object before suspending, and the thread's stack frame is discarded.

In the fetchUser bytecode, what is the tableswitch on label for? (L23 + L29)

Each suspension point is a state. On resume, label says where to continue: 0 is the start, 1 is after the first delay, 2 is after the second.
