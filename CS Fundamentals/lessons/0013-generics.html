A bug appears only on iteration 733 of a loop. Fastest debugger tool? (L12)

A conditional breakpoint pauses only when its Boolean expression is true, so you land straight on the bad iteration.

  1. Stepping over 733 iterations by hand is the slowest way to get there.
  2. Prints work, but you rerun and reread output; a breakpoint stops right at the bad state.
  3. It pauses only when its condition, like i == 733, is true.
  4. Restarting changes nothing: you'd still have to reach iteration 733 somehow.

You run git merge fix, and main hasn't moved since fix branched off. What happens? (L12)

That's a fast-forward: there's nothing to combine, so Git just moves the pointer (Pro Git §3.2).

  1. A merge commit is needed only when both branches have new commits.
  2. main is an ancestor of fix, so Git just moves the pointer forward.
  3. Conflicts need changes on both sides. Here only fix has new commits.
  4. Merging never deletes a branch. You delete fix yourself with git branch -d.

val s: Shape = Circle(), where Circle overrides area(). Which area() runs for s.area()? (L8)

Overrides are chosen at runtime from the object's real class. A Circle can stand in wherever a Shape is expected: that's subtype polymorphism, and Part 2 asks whether it carries over to lists of shapes.

  1. Dispatch uses the object's runtime class, which is Circle.
  2. The declared type Shape only decides which methods you may call, not which version runs.
  3. A Circle is a Shape, so the assignment and the call both compile.
  4. An override replaces the parent's version. The parent's runs only through super.area().

Java: Integer a = 1000, b = 1000; then System.out.println(a == b); (L5)

== compares references, and 1000 is outside the Integer cache (−128 to 127), so these are two different objects. Generics in Java only work with boxed types, so this trap follows you into every List<Integer>.

  1. true would need the same object. Only −128 to 127 are cached.
  2. == on two Integer objects compares references, and 1000 gives two different boxes.
  3. Comparing two references never throws. It just answers whether they're the same object.
  4. Comparing two Integer references with == is legal Java, just usually wrong.

Kotlin: val xs: List<Int> = listOf(1) then xs.add(2). What happens? (L3)

List is the read-only interface and has no add. That read-only design is also what lets a List<Int> be used as a List<Number>, as Part 2 shows.

  1. The call never runs: Kotlin rejects it before the program starts.
  2. Read-only List has no add method, so there's nothing to call.
  3. No add exists to return anything. That's a compile-time fact.
  4. List is read-only, so add is an unresolved reference.

Generic classes and functions

~38 min

You don't want IntBox, StringBox and PointBox. The old-fashioned fix is one box that holds Any / Object. It works, until it doesn't:

Every read needs a cast, and every cast is a promise the compiler can't check. When the promise breaks, you find out at runtime, possibly in production. This is how Java collections worked before Java 5.

Type parameters move the check to compile time

A generic class declares a type parameter, here T, which stands for "some type, chosen by whoever uses the class". When you write Box<String>, String is the type argument. The compiler substitutes it everywhere T appears, so it knows item is a String (Kotlin docs: Generics, dev.java: Introducing Generics):

TypedBox.java:10: error: incompatible types: int cannot be converted to String
        box.item = 42;                               // caught at COMPILE time
                   ^

Same bug, but now it's a red line in your editor instead of a crash for your users. No casts either: box.item.uppercase() just works. Effective Java Items 29 and 30 say it plainly: favour generic types, and favour generic methods.

Upper bounds: "any type, as long as it can…"

Inside firstOrNull, T could be anything, so you can't call anything on it beyond what every object has. To compare items you need to promise that T is comparable. That promise is an upper bound:

pear

  • T : Comparable<T> (Kotlin) and T extends Comparable<T> (Java) both read as "T can be compared with other Ts". In Java, extends here means "is a subtype of", even when the bound is an interface.
  • Two or more bounds: Java joins them with &. Kotlin allows only one bound inside the angle brackets, and "if the same type parameter needs more than one upper bound, you need a separate where-clause" (Kotlin docs: Upper bounds).

What Kotlin does for you.
  • Type arguments are inferred almost everywhere, with no diamond and no repeated types.
  • There are no raw types at all, so the legacy back door is closed.
  • You write List<Int>; the boxing to Integer happens silently, and == compares values, so the L5 cache trap can't bite.
  • Nullability is part of the type: Box<String> vs Box<String?>, and T : Any makes the compiler reject null, where Java needs Objects.requireNonNull at runtime.
What's the same: bounds (: vs extends), and the idea that the compiler, not a cast, guarantees the type.

Practice · A span of anything comparable

Finish Span, a closed range from lo to hi that works for Int, String or any other comparable type:

  • Creating a span with lo greater than hi throws IllegalArgumentException (L10's require). A single-point span like Span(3, 3) is fine.
  • x in span is true when lo ≤ x ≤ hi, and clamp(x) moves x to the nearest end if it's outside.
  • spanOf(items) returns the span from the smallest to the largest item, or null for an empty list.

Hint 1 of 3

Try writing lo <= hi in the init block first. The compiler refuses, because a plain T could be any type at all, and not every type can be compared. Which bound from Part 1 promises "T can be compared with other Ts"?

Hint 2 of 3

Change the header to class Span<T : Comparable<T>>, and give spanOf the same bound: fun <T : Comparable<T>> spanOf. Now <, <= and > work on T. Use require(lo <= hi) { … } in init.

Hint 3 of 3

contains is lo <= x && x <= hi. clamp is a when with x < lo -> lo, x > hi -> hi, else -> x. For spanOf, return null when the list is empty, then track the smallest and largest in one loop. In Java the bound is T extends Comparable<T>, and every comparison is spelled a.compareTo(b) <= 0.

Final answer

Why it works. The upper bound T : Comparable<T> is a promise the compiler checks at every use: Span(1, 5) and Span("b", "d") compile, while Span(Point(0, 0), Point(1, 1)) wouldn't. Inside the class, that promise is what makes <= legal on T, which Kotlin turns into compareTo calls.

Common mistake. Writing require(lo < hi). It looks the same, but it rejects Span(3, 3), and spanOf(listOf(7)) then throws instead of returning 7..7. A closed range needs <=.

What is the main thing generics give you over a box of Any/Object?

The compiler substitutes the type argument and rejects the wrong types, so the ClassCastException becomes a compile error. Part 3 shows that the runtime code is the same either way.

  1. The bytecode is the same either way, as Part 3's javap output shows.
  2. The compiler knows each type argument, so a wrong type is an error before the program runs.
  3. Erasure produces the same class files, so they aren't smaller.
  4. Null safety comes from Kotlin's ? types, not from generics.

In Java, where does a generic method's <T> go?

static <T> T firstOrNull(List<T> items). In Kotlin it goes right after fun.

  1. After the name is where you put a type argument when calling: Generics.<Integer>firstOrNull(…).
  2. Java has no slot for type parameters after the parameter list.
  3. A type parameter must be declared in the signature, before anything uses it.
  4. static <T> T firstOrNull(…): declared first, then used as the return type.

Java: List<int> xs = List.of(1, 2);

Type arguments must be reference types: "unexpected type, required: reference, found: int". Use List<Integer>.

  1. Type arguments must be reference types, and int is primitive.
  2. It never compiles, so nothing can throw.
  3. Nothing runs: the compiler stops at List<int>.
  4. Java generics accept only reference types. Write List<Integer> instead.

Why is passing a List<String> to a method that takes a raw List dangerous?

The raw method added 42 with only a warning, and the crash came later, far from the cause (JLS §4.8, Effective Java Item 26).

  1. Speed isn't the issue: raw and generic lists are the same class at runtime.
  2. Raw types compile, with at most a warning. That's exactly why they're risky.
  3. The raw parameter turns off the checks, so add(42) goes into a list of strings.
  4. A raw List holds any object, strings included.

Kotlin: class Box<T>(val item: T), then Box<String?>(null).

The default bound is Any?, so T can be String?. Only T : Any rules nullable types out.

  1. Only a T : Any bound would reject String?.
  2. A plain T has the bound Any?, so String? and null fit.
  3. Nothing here fails at runtime. item simply holds null.
  4. There's nothing to warn about: a nullable type argument is completely normal Kotlin.

Java picks between a generic overload and a String overload. What does this print?

public class Relay {
    static <T> String what(T x) { return "T"; }
    static String what(String s) { return "String"; }

    static <T> String relay(T x) { return what(x); }

    public static void main(String[] args) {
        System.out.println(what("hi") + " " + relay("hi"));
    }
}

Overloads are chosen at compile time from static types (L8). In main, "hi" is a String, so the more specific what(String) wins. Inside relay, x is just a T with the bound Object, so only what(T) fits, and that choice is compiled once for every caller.

  1. relay was compiled once, when x was only a T. The caller's String doesn't change that choice.
  2. The direct call sees a String; inside relay, x is an unbounded T, so only what(T) applies.
  3. That's backwards: the direct call has the more specific static type, String.
  4. When both overloads apply, Java picks the most specific one, and what(String) is more specific.

Variance: out/in vs ? extends/? super

~38 min

A String is an Object, so surely a list of strings is a list of objects? L8's substitution rule suggests yes. Java's arrays agreed, and that turned out to be a mistake:

Ada
Exception in thread "main" java.lang.ArrayStoreException: java.lang.Integer
	at ArrayStore.main(ArrayStore.java:6)

Step through it to see why the JVM has to check every array store:

Java arrays are covariant: if String is a subtype of Object, then String[] is a subtype of Object[]. That makes writes unsafe, so the JVM checks every store into an array at runtime and throws ArrayStoreException on a mismatch (JLS §10.5). Kotlin decided otherwise: "In Kotlin, arrays are invariant. This means that Array<String> is not a subtype of Array<Any>" (Kotlin docs: Arrays):

err/ArrayInvariant.kt:3:28: error: initializer type mismatch: expected 'Array<Any>', actual 'Array<String>'.
    val things: Array<Any> = names            // Kotlin arrays are invariant
                           ^

Generics are invariant

Generics learned from the array mistake. Box<String> and Box<Object> are simply unrelated types. That's called invariant. "Generic types in Java are invariant, meaning that List<String> is not a subtype of List<Object>" (Kotlin docs: Variance and wildcards in Java):

err/Invariant.kt:3:34: error: initializer type mismatch: expected 'MutableList<Any>', actual 'MutableList<String>'.
    val things: MutableList<Any> = names      // would let you add an Int to names
                                 ^
Invariant.java:7: error: incompatible types: List<String> cannot be converted to List<Object>
        List<Object> things = names;              // would let you add an Integer to names
                              ^

If line 3/7 were allowed, line 4/8 would put an Integer into a list of strings, and this time there would be no runtime store check to save you, because of erasure (Part 3). Effective Java Item 28: prefer lists to arrays. But invariance is too strict for code that only reads. A sum function should accept a list of Ints and a list of Doubles. The fix is to tell the compiler what the code does with the type: only takes things out, or only puts things in.

Producers and consumers in both languages

Java marks variance at every use with wildcards (dev.java: Wildcards):

  • List<? extends Number> means "a list of some subtype of Number". You can read Numbers out, but you can't add anything, because you don't know which subtype it really is.
  • List<? super Integer> means "a list of some supertype of Integer". You can add Integers, but reading gives you only Object.
  • The rule of thumb is Bloch's PECS: Producer-Extends, Consumer-Super (Effective Java Item 31, quoted in the Kotlin docs). The JDK's own Collections.copy is declared exactly like copyInto: public static <T> void copy(List<? super T> dest, List<? extends T> src) (JDK docs).

Kotlin needed far less. sum(nums: List<Number>) accepts a List<Int> with no wildcard, because the standard library declares interface List<out E> (Kotlin API: List). A read-only list only produces Es, so it's covariant once, for everyone. MutableList<E> can't be, since it has add, so at that use site you write MutableList<in Int>. That's Kotlin's version of ? super Integer.

Declaration-site variance: Kotlin's out and in

For your own types, Kotlin lets you mark a type parameter once, where the class is declared. out T promises that T is "only returned (produced) from members… and never consumed", and in T is the reverse. The docs call this declaration-site variance, in contrast with Java's use-site wildcards (Kotlin docs: Declaration-site variance):

10
printing hello
0

The standard library uses this too: Comparable<in T> and Iterable<out T> (Kotlin API). Something that can compare any Number can certainly compare Doubles. Java has no declaration-site variance, so every use repeats the wildcard. The compiler enforces your promise, and these are real errors:

Use-site projections and star projections

  • Use-site projection. When a class can't be covariant, like Array or MutableList, Kotlin still lets you restrict one use of it. Array<out Any> "corresponds to Java's Array<? extends Object>", and Array<in String> to ? super String (Kotlin docs: Type projections). describeAll above uses it. Java's version gets away with plain Object[] only because Java arrays are covariant.
  • Star projection. List<*> means "a list of some type I don't know". Reading gives Any?, and writing is forbidden (that's the third error above). Java writes it List<?>. The docs: "Star-projections are very much like Java's raw types, but safe" (Kotlin docs: Star-projections).

Why design it this way? Generics arrived in Java 5, after a decade of code using raw collections. Erasure let old and new code share the same classes, which is the "concession to compatibility" JLS §4.8 mentions. Kotlin runs on the same JVM, so it inherits erasure.

        check("a type with nothing stored gives null", null, () -> new Favorites().get(Boolean.class));
        check("putting the same type again replaces the old value", 2, () -> {
            Favorites f = new Favorites();
            f.put(Integer.class, 1);
            f.put(Integer.class, 2);
            return f.get(Integer.class);
        });
        check("the slot is chosen by the token, not the runtime class", "hi null", () -> {
            Favorites f = new Favorites();
            f.put(CharSequence.class, "hi");
            return f.get(CharSequence.class) + " " + f.get(String.class);
        });
    }

    interface Check { Object get() throws Exception; }

    static void check(String name, Object expected, Check actual) {
        try {
            Object got = actual.get();
            System.out.println(Objects.equals(expected, got) ? "PASS " + name : "FAIL " + name + ": expected <" + expected + "> but was <" + got + ">");
        } catch (Exception e) {
            System.out.println("FAIL " + name + ": threw " + e);
        }
    }
    // END CHECKS
}
Hint 1 of 3

The map is keyed by KClass. Inside a function with a reified T, you can write T::class to get the class object for the type argument the caller used.

Hint 2 of 3

put is one line: slots[T::class] = value. For get, look up slots[T::class]. You get an Any? back, and you need a T?.

Hint 3 of 3

Use as? T: because T is reified, it's a real runtime check, not an unchecked cast, so there's no warning. In Java, the token does the same jobs: slots.put(type, type.cast(value)) and return type.cast(slots.get(type)). Class.cast(null) returns null.

Final answer

Why it works. Erasure removes T from the compiled function, but an inline function's body is pasted into each call site, where T is known. So T::class becomes String::class or Int::class there, and as? T becomes a real instanceof check. Java gets the same safety by asking the caller for a Class<T> token and using type.cast.

Common mistake. Keying the slot with value::class. That's the runtime class, so put<CharSequence>("hi") lands in the String slot, and get<CharSequence>() finds nothing. The caller's type argument is the key.

Kotlin: println(ArrayList<String>().javaClass == ArrayList<Int>().javaClass)

Erasure: at runtime both are plain java.util.ArrayList.

  1. Type arguments are erased, so both objects have the same runtime class.
  2. There's one ArrayList class, not one per type argument.
  3. Comparing class objects never throws.
  4. Comparing two class references is legal, and Erasure.kt does exactly this.

After erasure, what does an unbounded T become in the bytecode?

The javap descriptor read ()Ljava/lang/Object;. A bounded T erases to its first bound instead.

  1. String appears only when a bound or a cast says so.
  2. Void is the type of no value. It has nothing to do with erasure.
  3. Comparable is the erasure of T extends Comparable<T>, a bounded T.
  4. With no bound, the erasure is Object, as the descriptor shows.

Why can an inline fun <reified T> use x is T when a normal generic function can't?

The call site knows T, and inlining pastes the body there. javap showed instanceof java/lang/Integer right inside main.

  1. The JVM still erases everything. Inlining just puts the real type into the caller's code.
  2. The body is pasted into each call site, where the compiler knows the real T.
  3. No hidden field exists. The type is fixed in the inlined bytecode.
  4. Erasure is a JVM rule that Kotlin can't switch off.

Java overloads f(List<String>) and f(List<Integer>) in one class.

"name clash: … have the same erasure". Both become f(List).

  1. This is a compile-time question; nothing runs or prints.
  2. The class is rejected before anything can run.
  3. Both erase to f(List), and one class can't have two methods with that signature.
  4. After erasure both signatures are identical, so javac reports a name clash.

An unchecked cast xs as List<String> was wrong. Where does the exception appear?

The cast itself is just List to List. The hidden checkcast on the first element read is what fails, which is why the stack trace points at the wrong line.

  1. The hidden checkcast on the first read of an element is what fails.
  2. At runtime the cast is only List to List, which always succeeds.
  3. The JVM never converts an Integer into a String; reading one as a String fails.
  4. It's only a warning: the compiler can't check it, so it trusts you.

Stretch: filterIsInstance is reified. What does this print?

fun main() {
    val mixed: List<Any> = listOf(listOf("a"), listOf(1, 2), "b")
    val lists = mixed.filterIsInstance<List<String>>()
    println(lists)
}

reified brings back the class, List, but not the erased type argument, which no list object carries at runtime. The inlined check is just instanceof List, so listOf(1, 2) passes too. lists is typed List<List<String>> while holding a list of Ints: reading lists[1][0] as a String would throw ClassCastException. kotlinc doesn't even warn here, so filter by List<*> and check the elements.

  1. The check can only test instanceof List, so both lists pass and the string doesn't.
  2. That needs the list objects to know their element types. Erasure removed that, and reified can't restore it.
  3. Both elements really are lists, so the List check passes for them.
  4. "b" isn't a List at all, so the class check drops it.

Which JUnit assertion would test that pop() on an empty stack fails? (L11)

assertThrows(IllegalStateException.class, () -> stack.pop()), or assertFailsWith<IllegalStateException> { … } in kotlin.test, which is itself a reified inline function.

  1. assertEquals compares values. It can't catch an exception.
  2. assertNull checks for null. The test would crash on the exception instead.
  3. It runs the code and passes only if the expected exception is thrown.
  4. assertTrue checks a condition. A thrown exception would just fail the test.

Two Kotlin overloads clash after erasure. Which annotation fixes it? (L9)

@JvmName("labelStrings") gives one of them a different JVM name, while Kotlin callers still use the original name.

  1. It gives one overload a different JVM name, which ends the clash.
  2. @JvmStatic exposes companion members as static methods. It doesn't rename anything.
  3. @JvmField exposes a property as a plain field. Functions are untouched.
  4. @JvmOverloads adds overloads for default arguments. That would add clashes, not remove them.

Kotlin: data class Box<T>(val item: T), then println(Box(1) == Box(1)). (L7)

A data class's generated equals compares properties, and it works the same whatever T is.

  1. The generated equals compares item, not references.
  2. Both have item == 1, and data-class equals compares properties.
  3. Comparing two data-class objects never throws.
  4. == works on any two objects of the same type.

Java: List<Integer> xs = List.of(127, 127); then System.out.println(xs.get(0) == xs.get(1)); (L5)

127 is inside the Integer cache, so both elements are the same boxed object. With 1000 it prints false, which is exactly why == on boxed generics is a trap.

  1. false needs two different boxes; 127 comes from the cache both times.
  2. Comparing references never throws.
  3. == on two Integers compiles. It's legal, just risky.
  4. List.of boxes through Integer.valueOf, which returns the cached 127 both times.
