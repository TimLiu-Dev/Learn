Part 1

Generic classes and functions

~30 min

You don't want IntBox, StringBox and PointBox. The old-fashioned fix is one box that holds Any / Object. It works, until it doesn't:

HELLO
Exception in thread "main" java.lang.ClassCastException: class java.lang.Integer cannot be cast to class java.lang.String (java.lang.Integer and java.lang.String are in module java.base of loader 'bootstrap')
	at AnyBoxKt.main(AnyBox.kt:9)
	at AnyBoxKt.main(AnyBox.kt)

Every read needs a cast, and every cast is a promise the compiler can't check. When the promise breaks, you find out at runtime, possibly in production. This is how Java collections worked before Java 5.

Type parameters move the check to compile time

A generic class declares a type parameter, here T, which stands for "some type, chosen by whoever uses the class". When you write Box<String>, String is the type argument. The compiler substitutes it everywhere T appears, so it knows item is a String (Kotlin docs: Generics, dev.java: Introducing Generics):

err/TypedBox.kt:6:14: error: assignment type mismatch: actual type is 'Int', but 'String' was expected.
    box.item = 42                    // caught at COMPILE time
             ^
TypedBox.java:10: error: incompatible types: int cannot be converted to String
        box.item = 42;                               // caught at COMPILE time
                   ^

Same bug, but now it's a red line in your editor instead of a crash for your users. No casts either: box.item.uppercase() just works. Effective Java Items 29 and 30 say it plainly: favour generic types, and favour generic methods.

For compatibility with pre-generics code, Java still lets you write a generic type without its type argument. List instead of List<String> is called a raw type. Upper bounds: "any type, as long as it can…"

Inside firstOrNull, T could be anything, so you can't call anything on it beyond what every object has. To compare items you need to promise that T is comparable. That promise is an upper bound:

What Kotlin does for you.
  • Type arguments are inferred almost everywhere, with no diamond and no repeated types.
  • There are no raw types at all, so the legacy back door is closed.

  • Nullability is part of the type: Box<String> vs Box<String?>, and T : Any makes the compiler reject null, where Java needs Objects.requireNonNull at runtime.

Part 2

Variance: out/in vs ? extends/? super

~30 min

A String is an Object, so surely a list of strings is a list of objects? L8's substitution rule suggests yes. Java's arrays agreed, and that turned out to be a mistake:

Ada
Exception in thread "main" java.lang.ArrayStoreException: java.lang.Integer
	at ArrayStore.main(ArrayStore.java:6)

Step through it to see why the JVM has to check every array store:

Java arrays are covariant: if String is a subtype of Object, then String[] is a subtype of Object[]. That makes writes unsafe, so the JVM checks every store into an array at runtime and throws ArrayStoreException on a mismatch (JLS §10.5). Kotlin decided otherwise: "In Kotlin, arrays are invariant. This means that Array<String> is not a subtype of Array<Any>" (Kotlin docs: Arrays):

err/ArrayInvariant.kt:3:28: error: initializer type mismatch: expected 'Array<Any>', actual 'Array<String>'.
    val things: Array<Any> = names            // Kotlin arrays are invariant
                           ^

Generics are invariant

Generics learned from the array mistake. Box<String> and Box<Object> are simply unrelated types. That's called invariant. "Generic types in Java are invariant, meaning that List<String> is not a subtype of List<Object>" (Kotlin docs: Variance and wildcards in Java):

err/Invariant.kt:3:34: error: initializer type mismatch: expected 'MutableList<Any>', actual 'MutableList<String>'.
    val things: MutableList<Any> = names      // would let you add an Int to names
                                 ^
Invariant.java:7: error: incompatible types: List<String> cannot be converted to List<Object>
        List<Object> things = names;              // would let you add an Integer to names
                              ^

If line 3/7 were allowed, line 4/8 would put an Integer into a list of strings, and this time there would be no runtime store check to save you, because of erasure (Part 3). Effective Java Item 28: prefer lists to arrays. But invariance is too strict for code that only reads. A sum function should accept a list of Ints and a list of Doubles. The fix is to tell the compiler what the code does with the type: only takes things out, or only puts things in.

Java marks variance at every use with wildcards (dev.java: Wildcards):

  • List<? extends Number> means "a list of some subtype of Number". You can read Numbers out, but you can't add anything, because you don't know which subtype it really is.
  • List<? super Integer> means "a list of some supertype of Integer". You can add Integers, but reading gives you only Object.
  • The rule of thumb is Bloch's PECS: Producer-Extends, Consumer-Super (Effective Java Item 31, quoted in the Kotlin docs). The JDK's own Collections.copy is declared exactly like copyInto: public static <T> void copy(List<? super T> dest, List<? extends T> src) (JDK docs).

Kotlin needed far less. sum(nums: List<Number>) accepts a List<Int> with no wildcard, because the standard library declares interface List<out E> (Kotlin API: List). A read-only list only produces Es, so it's covariant once, for everyone. MutableList<E> can't be, since it has add, so at that use site you write MutableList<in Int>. That's Kotlin's version of ? super Integer.

CAP#1 is javac's name for "the specific, unknown type behind this wildcard". You can't add an int to a list of unknown-subtype-of-Number: it might be a List<Double>.

Declaration-site variance: Kotlin's out and in

For your own types, Kotlin lets you mark a type parameter once, where the class is declared. out T promises that T is "only returned (produced) from members… and never consumed", and in T is the reverse. The docs call this declaration-site variance, in contrast with Java's use-site wildcards (Kotlin docs: Declaration-site variance):

10
printing hello
0

The standard library uses this too: Comparable<in T> and Iterable<out T> (Kotlin API). Something that can compare any Number can certainly compare Doubles. Java has no declaration-site variance, so every use repeats the wildcard. The compiler enforces your promise, and these are real errors:

err/BadVariance.kt:3:19: error: type parameter 'T' is declared as 'out' but occurs in 'in' position in type 'T (of interface Source<out T>)'.
    fun put(item: T)                    // T in an "in" position
                  ^
err/BadVariance.kt:8:17: error: type parameter 'T' is declared as 'in' but occurs in 'out' position in type 'T (of interface Sink<in T>)'.
    fun peek(): T                       // T in an "out" position
                ^
err/BadVariance.kt:12:15: error: receiver type 'MutableList<*>' contains star projection which prohibits the use of 'fun add(element: E): Boolean'.
    items.add(1)                        // star projection: can't write
              ^

Rule of thumb: a parameter type is an in position and a return type is an out position. The docs' mnemonic is "Consumer in, Producer out!"

Use-site projections and star projections

  • Use-site projection. When a class can't be covariant, like Array or MutableList, Kotlin still lets you restrict one use of it. Array<out Any> "corresponds to Java's Array<? extends Object>", and Array<in String> to ? super String (Kotlin docs: Type projections). describeAll above uses it. Java's version gets away with plain Object[] only because Java arrays are covariant.
  • Star projection. List<*> means "a list of some type I don't know". Reading gives Any?, and writing is forbidden (that's the third error above). Java writes it List<?>. The docs: "Star-projections are very much like Java's raw types, but safe" (Kotlin docs: Star-projections).

Part 3

Type erasure and reified

~25 min

Here's the surprise: all that type checking happens only at compile time. "At runtime, the instances of generic types do not hold any information about their actual type arguments. The type information is said to be erased" (Kotlin docs: Type erasure).

true

There is one ArrayList class, not one per type argument. To see what the compiler really generated, use javap, the JDK's class-file disassembler:

$ javac Erasure.java && javap -s 'Erasure$Box'

     105: checkcast     #54                 // class java/lang/String

The Ts survive only as metadata for the compiler and for reflection. The descriptor, which is what the JVM actually runs, says Object. At the call site the compiler quietly inserts the cast you used to write by hand (checkcast … String). That's exactly what dev.java describes: the compiler replaces type parameters "with their bounds or Object if the type parameters are unbounded" and inserts "type casts if necessary to preserve type safety", so "generics incur no runtime overhead" (dev.java: Type Erasure, JLS §4.6). With a bound, T erases to the bound instead: javap shows <T extends Comparable<T>> T largest(…) from Part 1 as returning Ljava/lang/Comparable;.

Why design it this way? Generics arrived in Java 5, after a decade of code using raw collections. Erasure let old and new code share the same classes, which is the "concession to compatibility" JLS §4.8 mentions. Kotlin runs on the same JVM, so it inherits erasure.

The cast "succeeds" because at runtime it's just List to List. The list then sits there polluted until someone reads an element, and only that line's hidden checkcast fails. Notice that javac warned about castListLoud but said nothing about castList, because @SuppressWarnings("unchecked") silenced it. Effective Java Item 27: eliminate every unchecked warning you can. If you're sure a cast is safe, suppress it on the smallest possible scope and add a comment saying why.

Bridge to Spring. Erasure is why some framework APIs ask you to create an odd-looking anonymous subclass: new ParameterizedTypeReference<List<String>>() {}. Its docs say its purpose "is to enable capturing and passing a generic Type… and retain it at runtime" (Spring docs). A subclass records its superclass's type arguments in the class file, where reflection can read them. When an HTTP client needs to turn JSON into a List<User>, a plain List.class token can't say "of User". Kotlin-first libraries tend to use reified functions for the same job.
What Kotlin does for you. Erasure is a JVM fact, so Kotlin can't remove it, but it softens it in three ways:
  • inline fun <reified T> lets a function use is T, as T and T::class, so callers write only<Int>() instead of passing Integer.class.
  • @JvmName resolves overload clashes, so Kotlin callers keep one function name.
  • The compiler always shows unchecked-cast warnings, where javac hides them behind a "Note" unless you pass -Xlint:unchecked.

After erasure, what does an unbounded T become in the bytecode?

The javap descriptor read ()Ljava/lang/Object;. A bounded T erases to its first bound instead.

Why can an inline fun <reified T> use x is T when a normal generic function can't?

The call site knows T, and inlining pastes the body there. javap showed instanceof java/lang/Integer right inside main.

Java overloads f(List<String>) and f(List<Integer>) in one class.

"name clash: … have the same erasure". Both become f(List).

An unchecked cast xs as List<String> was wrong. Where does the exception appear?

The cast itself is just List to List. The hidden checkcast on the first element read is what fails, which is why the stack trace points at the wrong line.

Why it's shaped this way: pushAll is a producer and popAllInto is a consumer, so this is PECS in its natural habitat (it's close to Bloch's own example in Item 31). In Kotlin you may have written Iterable<out T>. That works, but the compiler says it's unnecessary, because Iterable is already declared out:

Stack.kt:16:31: warning: projection is redundant: the corresponding type parameter of 'Iterable<out T (of class Stack<T>)>' has the same variance.
    fun pushAll(src: Iterable<out T>) { for (item in src) push(item) }

MutableCollection is invariant, so in T is needed there. In Java, both wildcards have to be spelled out. One more design note: peek(): T? is ambiguous for a Stack<String?>, since null could mean "empty" or "the top item is null". Real stacks often throw instead, or you'd bound it with T : Any. Exit quiz, recall card, sources

~5 min

Which JUnit assertion would test that pop() on an empty stack fails? (L11)

assertThrows(IllegalStateException.class, () -> stack.pop()), or assertFailsWith<IllegalStateException> { … } in kotlin.test, which is itself a reified inline function.

Two Kotlin overloads clash after erasure. Which annotation fixes it? (L9)

@JvmName("labelStrings") gives one of them a different JVM name, while Kotlin callers still use the original name.

Kotlin: data class Box<T>(val item: T), then println(Box(1) == Box(1)). (L7)

A data class's generated equals compares properties, and it works the same whatever T is.

Java: List<Integer> xs = List.of(127, 127); then xs.get(0) == xs.get(1). (L5)

127 is inside the Integer cache, so both elements are the same boxed object. With 1000 it prints false, which is exactly why == on boxed generics is a trap.
