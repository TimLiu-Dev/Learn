Part 1

Bytecode and javap

~30 min

Neither javac nor kotlinc produces machine code. Both produce class files: one .class per class, in a format the JVM specification defines byte by byte (JVMS ch. 4: The class File Format). The JVM doesn't know or care which language produced them. That's the whole reason Kotlin can call Java and back (L9).

$ javac -d out Calc.java
$ kotlinc Calc.kt -d out
$ ls out
Calc.class
CalcKt.class
META-INF
$ java -cp out Calc
5 10
$ kotlin -cp out CalcKt
5 10

Kotlin's top-level functions had to live in some class, so kotlinc made one named after the file: CalcKt (L9).

Every class file starts with CAFEBABE

$ xxd -l 16 out/Calc.class
00000000: cafe babe 0000 0046 0037 0a00 0200 0307  .......F.7......
$ xxd -l 16 out/CalcKt.class
00000000: cafe babe 0000 0034 0049 0100 0643 616c  .......4.I...Cal
$ javap -v -cp out Calc | grep version
  minor version: 0
  major version: 70
  • Bytes 0–3 are the magic number: "it has the value 0xCAFEBABE" (JVMS §4.1). If those four bytes are wrong, the JVM refuses to load the file.
  • Bytes 4–7 are the minor and major version. 0x46 is 70, which is Java SE 26: a JVM "which conforms to Java SE 26 supports precisely" major versions 45 through 70. Run a version-70 class on an older JVM and you get an UnsupportedClassVersionError.
  • Kotlin wrote 0x34 = 52, which is Java 8's version. That's deliberate: kotlinc's -jvm-target option says "Possible values are 1.8, 9, 10, ..., 26. The default value is 1.8" (Kotlin compiler options), so a plain kotlinc build runs on any JVM from Java 8 up. In a Gradle project the toolchain sets the target instead; your L1 projects use 21.

The JVM is a stack machine

javap -c disassembles the bytecode of each method:

static int add(int, int);
  Code:
     0: iload_0
     1: iload_1
     2: iadd
     3: ireturn
public static final int add(int, int);
  Code:
     0: iload_0
     1: iload_1
     2: iadd
     3: ireturn

Left is javap -c -cp out Calc, right is javap -c -cp out CalcKt: identical instructions. To read them you need the frame from L4, opened up. The spec says each frame "has its own array of local variables, its own operand stack, and a reference to the run-time constant pool" (JVMS §2.6):

  • The local-variable array holds the parameters and locals, numbered from 0. For a static method, slot 0 is the first parameter. For an instance method, slot 0 is this.
  • The operand stack is a scratchpad. Instructions pop their inputs off it and push their results back. iadd has no operands of its own: it pops two ints and pushes their sum.
  • The letter prefix is the type: i for int, l for long, d for double, a for a reference. iload_0 means "push the int in local slot 0".

The comments are mine; javap prints only the instructions. Loops are just a conditional jump plus a goto back. There's no "for" in bytecode. But look at the shapes. Kotlin checks the range once up front, then tests i == n before incrementing. Why? Because Java's version has a bug at the edge of the int range. If n is Int.MAX_VALUE, i <= n is always true and i++ overflows to a negative number (L2):

Decompiling a data class and a record

Now check your warm-up list. javap -p lists every member, including private ones:

public final class Point {
  private final int x;
  private final int y;
  public Point(int, int);
  public final int getX();
  public final int getY();
  public final int component1();
  public final int component2();
  public final Point copy(int, int);
  public static Point copy$default(Point, int, int, int, java.lang.Object);
  public java.lang.String toString();
  public int hashCode();
  public boolean equals(java.lang.Object);
}
final class Point extends java.lang.Record {
  private final int x;
  private final int y;
  Point(int, int);
  public static void main(java.lang.String[]);
  public final java.lang.String toString();
  public final int hashCode();
  public final boolean equals(java.lang.Object);
  public int x();
  public int y();
}
  • Kotlin wrote getters (getX), componentN for destructuring, copy, and a hidden static copy$default. The extra int parameter in copy$default is a bitmask saying which arguments were left out, so their defaults (the current values) get used. That's how default arguments work on a JVM that has no such feature.
  • Java wrote accessors named after the components (x(), not getX()), and the class extends java.lang.Record. No copy, no destructuring methods: records do destructuring through pattern matching instead (L7).

The bodies differ even more. Kotlin's equals is 49 bytes of ordinary bytecode: an identity check, instanceof, then a field-by-field compare. The record's equals is four instructions:

// Kotlin Point.equals (start)
 0: aload_0
 1: aload_1
 2: if_acmpne     7     // same object?
 5: iconst_1
 6: ireturn
 7: aload_1
 8: instanceof    #2    // class Point
   …
22: getfield      #13   // Field x:I
   …
// Java record Point.equals
0: aload_0
1: aload_1
2: invokedynamic #53,  0  // InvokeDynamic #1:equals:(LPoint;Ljava/lang/Object;)Z
7: ireturn

// javap -v, BootstrapMethods:
1: #79 REF_invokeStatic java/lang/runtime/ObjectMethods.bootstrap:(…)
  Method arguments:
    #8 Point
    #69 x;y
    #71 REF_getField Point.x:I
    #72 REF_getField Point.y:I

The record hands the job to invokedynamic, the same instruction as L14's lambdas. On first call the JVM asks ObjectMethods.bootstrap to build an implementation from the list of components (x;y) and their getters. The API docs describe it as "bootstrap methods for state-driven implementations of core methods, including Object.equals(Object), Object.hashCode(), and Object.toString()" (ObjectMethods; see also JEP 395). The class file stays tiny, and the JDK can improve the implementation without you recompiling.

1 · Null checks on every public parameter. Here's javap -c for greet:

Your Kotlin said name: String, never null. But a Java caller can pass null anyway, so "Kotlin generates runtime checks for all public functions that expect non-nulls. This way we get a NullPointerException in the Java code immediately" (Calling Kotlin from Java). The parameter's name is passed along, so the error message can say which parameter was null. Java's greet has no such check.

tableswitch uses the value as an index into a table of jump targets, so it costs one step no matter how many cases there are. For sparse values like 1, 100, 5000, both compilers emit lookupswitch instead (I checked with javap on a three-case version): a table of key/target pairs that "are sorted to support lookup routines that are quicker than linear search" (JVMS: lookupswitch), such as L18's binary search. That's why a when on an int is not a chain of ifs.

There's no call to twice at all: kotlinc pasted its body, and the lambda's body, straight into main, twice. Because the lambda is gone, count stays a plain local int. L14 showed that a captured var in a non-inline lambda gets boxed in a Ref$IntRef. The non-inline twiceNoInline call still builds a Function0 object via invokedynamic, just as Java's version builds a Runnable. Java has no inline, so it needs the int[] trick from L14.

One more thing in every Kotlin class file: a @kotlin.Metadata annotation (visible in javap -v). It "is present on any class file produced by the Kotlin compiler and is read by the compiler and reflection" (Metadata API). It records the Kotlin-only facts the JVM format can't express, like which types are nullable.

What Kotlin does for you (and you can now prove it in the bytecode).
  • A runtime Intrinsics.checkNotNullParameter guards every non-null parameter of a public function, so null from Java fails fast, at the boundary.
  • Data classes get componentN, copy and copy$default on top of equals/hashCode/toString, all as plain bytecode.
  • inline pastes lambdas into the call site, so there's no lambda object and no boxing of captured vars.
  • Range loops are compiled overflow-safe at Int.MAX_VALUE.
  • Top-level functions get a FileKt class, and companions become a nested class plus a static field: things Java makes you write by hand.
What's the same: it's all ordinary JVM bytecode in an ordinary class file. A when and a switch compile to the same tableswitch.

Check

What does iadd do?

It's a stack instruction with no operands: its inputs are whatever is on top of the operand stack (JVMS §2.6.2). Adding a constant to a local is iinc.

A plain kotlinc File.kt writes class-file major version 52. Why?

kotlinc's -jvm-target defaults to 1.8 (major version 52), so the output runs on Java 8 and up. Gradle toolchains raise it, and higher targets unlock things like invokedynamic string concatenation.

Why does kotlinc insert Intrinsics.checkNotNullParameter at the start of public functions?

Kotlin's type system can't stop Java code passing null, so the check makes it fail immediately at the boundary, with the parameter's name in the message, instead of deep inside your code.

How does a Java record implement equals in its class file?

The record's equals is just aload_0, aload_1, invokedynamic, ireturn. The real implementation is built at runtime by java.lang.runtime.ObjectMethods from the component list. Kotlin's data class instead contains the full compare as ordinary bytecode.

After twice { count++ }, where twice is inline, what does main's bytecode contain?

kotlinc copies the function body and the lambda body into the caller, so count++ appears twice as plain iload/iadd/istore, with no object and no call.

Part 2

Class loading and runtime data areas

~20 min

A class file on disk does nothing. Before your code runs, the JVM goes through three steps, which JVMS chapter 5 defines (JVMS ch. 5: Loading, Linking, and Initializing):

  1. Loading: find the bytes for a class (a .class file, a jar entry, the JDK's own modules) and create the class from them.
  2. Linking: verify that the bytecode is well-formed and type-safe, so a hand-crafted class file can't corrupt memory; prepare the static fields with default values; and resolve symbolic references like java/lang/StringBuilder to the real classes.
  3. Initialization: "consists of executing the class or interface initialization method <clinit>". That's your Java static {} blocks and static field initializers, or the Kotlin object/companion init blocks.

The important word is lazy. A class is initialized only on first active use: "Upon execution of a new, getstatic, putstatic, or invokestatic instruction" that refers to it (JVMS §5.5).

Nothing is initialized up front. Each class wakes up exactly when first touched, and only once. A Kotlin object is a thread-safe lazy singleton for exactly this reason: its init runs in the class initializer, which the JVM guarantees runs once. Class loaders

Classes are loaded by class loaders, and the JDK has three built in (ClassLoader API):

  • Bootstrap: "the virtual machine's built-in class loader, typically represented as null". It loads core classes like String.
  • Platform: the rest of the Java SE APIs, like java.sql.
  • System, also called application: "used to define classes on the application class path". That's your code, and any jar on -cp, including kotlin-stdlib.

Parent delegation: "When requested to find a class or resource, a ClassLoader instance will usually delegate the search for the class or resource to its parent class loader before attempting to find the class or resource itself." So when your code asks for java.lang.String, the app loader asks the platform loader, which asks bootstrap, which finds the real one. You can't accidentally replace String by putting your own String.class on the classpath. Notice that kotlin.Unit comes from the app loader: to the JVM, the Kotlin standard library is just another jar. (Run java Loaders.java in source mode and Mine shows a different loader, com.sun.tools.javac.launcher.MemoryClassLoader: the source launcher compiles into memory and loads from there. Frameworks use custom loaders like this all the time.)

The runtime data areas

Once loaded, where does everything live? JVMS §2.5 names the areas (Run-Time Data Areas). L4's stack-and-heap picture was the simplified version:

AreaPer thread?HoldsFails with

The spec leaves the layout to each JVM. HotSpot keeps class metadata in an area called Metaspace, outside the heap. You can see all of it inside your process's address space (L22) with Native Memory Tracking, which you turn on with -XX:NativeMemoryTracking=summary; it "tracks memory usage only by JVM subsystems, such as Java heap, class, code, and thread" (the java command, jcmd):

  • Reserved vs committed is L22's virtual memory in action. The JVM reserves 512 MB of address space for the heap (our -Xmx), but only commits (backs with real memory) the 105 MB it uses, which is mostly our 100 MB array.

  • Code: where the JIT compiler puts the machine code it generates (Part 3). GC: the collector's own bookkeeping, which is L24's topic. Shared class space: that archive again.

  • object gives you a lazy, thread-safe singleton by riding on the JVM's once-only class initialization. Java's equivalent is the holder-class idiom from L15, written by hand.
  • The kotlin runner puts the stdlib on the classpath for you.
What it costs: Kotlin programs need kotlin-stdlib at runtime (about 1.8 MB) and load a few dozen extra classes. Class loading, linking and initialization rules are identical for both languages. The JVM never knows which one you wrote.

Check

When does a class's static {} block (or Kotlin object init) run?

Initialization is lazy: the first new, getstatic, putstatic or invokestatic that refers to the class triggers <clinit>, exactly once (JVMS §5.5).

What does String.class.getClassLoader() return?

The bootstrap loader is built into the JVM and "typically represented as null" (ClassLoader API). Core classes like String come from it.

A Kotlin program compiles, then crashes at runtime with NoClassDefFoundError: kotlin/jvm/internal/Intrinsics. Most likely cause?

The class was there at compile time but not at runtime. Run with kotlin -cp …, add the stdlib jar to -cp, or build a fat jar.

Which runtime data area is shared by all threads?

The heap and the method area are shared. The pc register and the JVM stack, with its frames and their operand stacks, are per thread (JVMS §2.5). That sharing is exactly why Phase 8 (concurrency) is hard.

Part 3

The interpreter and the JIT

~25 min

So who runs the bytecode? At first, an interpreter: a loop that reads one instruction, does it, and moves to the next, exactly like the widget in Part 1. That's simple and starts instantly, but it's slow. So HotSpot counts how often each method runs and how many times its loops go round. Hot code gets handed to a just-in-time (JIT) compiler, which turns it into real machine code for this CPU while the program keeps running. java -version says "mixed mode" because both run together.

HotSpot has two JIT compilers: C1, which compiles fast with basic optimizations, and C2, which compiles slowly with aggressive ones. Tiered compilation uses both (HotSpot performance enhancements: Tiered Compilation). The HotSpot source names five levels (compilationPolicy.hpp, implementation detail):

LevelWhoWhat
0interpreterruns bytecode and collects a profile
1–3C1quick machine code; level 3 also keeps profiling
4C2"full profile guided optimization"

The columns, as printed by HotSpot's CompileTask::print (implementation detail; the format isn't a documented contract):

  • 10: milliseconds since the JVM started. 8, 9, 10, 105: compile IDs.
  • %: an on-stack replacement (OSR) compile. The loop in work was hot while still running, so HotSpot compiled the loop and switched to it mid-loop. @ 4 is the bytecode offset it jumps in at: offset 4 is the loop's iload_3, the target of its goto 4.
  • 3 or 4: the tier. C1 with profiling, then C2.
  • (29 bytes): the method's bytecode size. The Kotlin version also says HotKt::work (29 bytes): same bytecode, same JIT story.
  • made not entrant: old compiled code that's retired once the better version arrives.

Three things the JIT does that javac doesn't

javac and kotlinc barely optimize; you saw them translate almost line by line. The real optimizing happens at runtime, where C2 can see which code is actually hot and which types actually show up.

1 · Inlining. Calling a tiny method costs more than the method body. C2 copies small, hot callees into the caller, like inline but done automatically at runtime and only where it pays off. Watch it with -XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining (the java command) on the next program:

$ java -XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining -XX:+PrintCompilation -cp out Escape   # excerpt
32  143 %     4       Escape::sumPoints @ 4 (45 bytes)
                              @ 17   Escape$Point::<init> (15 bytes)   inline (hot)
                                @ 1   java.lang.Record::<init> (5 bytes)   inline (hot)
                                  @ 1   java.lang.Object::<init> (1 bytes)   inline (hot)
                              @ 25   Escape$Point::x (5 bytes)   accessor
                              @ 30   Escape$Point::y (5 bytes)   accessor

The constructor chain and both accessors were pasted into sumPoints. Once the code is hot, a getter costs essentially nothing, so don't avoid them for speed.

2 · Escape analysis. Once everything is inlined, C2 can see that each Point never leaves the method. "Escape analysis is a technique by which the Java HotSpot Server Compiler can analyze the scope of a new object's uses and decide whether to allocate the object on the Java heap." An object that doesn't escape is "scalar replaceable": C2 keeps its fields in registers and never allocates it. Note that it "does not replace a heap allocation with a stack allocation" (HotSpot performance enhancements: Escape Analysis). We can measure it, because the JDK can report how many bytes the current thread has allocated:

$ java -cp out Escape
round 1: 6,403,912 bytes allocated
round 2: 4,521,960 bytes allocated
round 3: 196,584 bytes allocated
round 4: 196,584 bytes allocated
round 5: 0 bytes allocated
sink=5000000000000
$ java -XX:-DoEscapeAnalysis -cp out Escape
round 1: 24,005,056 bytes allocated
round 2: 24,000,000 bytes allocated
round 3: 24,000,000 bytes allocated
round 4: 24,000,000 bytes allocated
round 5: 24,000,000 bytes allocated
sink=5000000000000

With escape analysis turned off (-XX:-DoEscapeAnalysis; it's "enabled by default"), every round allocates exactly 24,000,000 bytes: one million Points at 24 bytes each on this JVM. With it on, allocation falls as the method moves up the tiers, and reaches zero once C2's version runs. A million new Point(…) calls in your source, and not one object on the heap. The Kotlin data class version gives the same pattern (6.2 MB, 4.9 MB, 196,584, 196,584, 0). Less allocation means less garbage for L24's collector.

3 · Dead-code elimination. If a result is never used, C2 may not compute it at all. That's great for your program, and a trap for your benchmarks:

round 1: discarded  1571 µs, used  30558 µs
round 2: discarded  4389 µs, used  29697 µs
round 3: discarded     0 µs, used  29815 µs
round 4: discarded     0 µs, used  29832 µs
round 5: discarded     0 µs, used  30440 µs
round 1: discarded  1385 µs, used  31332 µs
round 2: discarded  2999 µs, used  30039 µs
round 3: discarded     0 µs, used  29846 µs
round 4: discarded  3205 µs, used  29819 µs
round 5: discarded     0 µs, used  29782 µs

Ten million Math.log calls in 0 µs? Of course not. Once wrong() is inlined, C2 sees that its result goes nowhere and deletes the loop. A naive benchmark of wrong() would "prove" that log is free. This is the example from JMH's own samples (JMHSample_08_DeadCode). JMH, the benchmark harness you'll run for real in L24, exists to defeat exactly this, plus the warm-up problem above.

I also tried to show dead-code elimination with a plain arithmetic loop (s += i, result discarded). On JDK 26, C2 did not remove it: discarded and used took the same time. The JIT is free to optimize or not, which is another reason to measure instead of guessing.

Startup vs peak: AOT caches

The JIT's price is warm-up: every run starts slow, loading and linking classes and interpreting code. Recent JDKs attack this with ahead-of-time (AOT) caches from Project Leyden. You do a training run once, the JVM saves the work it did, and later runs start from that snapshot:

  • JEP 483 (JDK 24): Ahead-of-Time Class Loading & Linking.
  • JEP 514 (JDK 25): a one-step -XX:AOTCacheOutput.
  • JEP 515 (JDK 25): method profiles in the cache, so the JIT warms up faster.
  • JEP 516 (JDK 26): AOT object caching with any GC.

What Kotlin does for you (here, mostly nothing, and that's the lesson).
  • At runtime there's no "Kotlin JIT". HotKt::work and Hot::work were both 29 bytes and got the same tiers at the same moments. Escape analysis removed the data class allocations exactly as it removed the record's.
  • The one Kotlin-specific runtime tool you saw is compile-time inline (Part 1), which guarantees inlining for lambdas instead of hoping C2 does it.

Check

In -XX:+PrintCompilation output, what does % mark?

OSR: a hot loop compiled while its method is still running, and entered at the bytecode offset after @. (s marks synchronized, ! exception handlers, n native.)

Why did -XX:-DoEscapeAnalysis make every round allocate 24 MB?

Escape analysis is what lets C2 scalar-replace non-escaping objects, keeping their fields in registers. Without it, all one million Points are allocated on the heap each round. HotSpot never moves them to the stack.

A loop calls Math.log(x) ten million times, ignores the result, and takes 0 µs. Why?

Dead-code elimination: after inlining, the result is provably unused, so the work is deleted. JMH's Blackhole and returned values exist to stop this (L24).

What does a JDK 25+ AOT cache (-XX:AOTCache) mainly speed up?

It stores classes already loaded and linked, plus profiles, from a training run, so later runs skip that work (JEPs 483, 514, 515). Peak speed still comes from the JIT.

Part 4

Android's ART vs the JVM

~10 min

This part is docs only. I didn't build or run any Android code for it, and every claim links to the Android docs.

Your Android app is written in the same Kotlin and compiled by the same kotlinc into the same JVM class files. But a phone doesn't run HotSpot. Here's the pipeline:

  1. .class → DEX. "d8 is a command-line tool that Android Studio and the Android Gradle plugin use to compile your project's Java bytecode into DEX bytecode that runs on Android devices" (d8).
  2. Shrinking. In release builds, R8 removes unused code and renames things. "Obfuscation (also known as minification): To reduce the size of the DEX file, R8 shortens the names of classes, fields, and methods (for example, com.example.MyActivity could become a.b.a)" (Enable app optimization with R8). This is why release stack traces need a mapping file.
  3. ART runs the DEX. "Android runtime (ART) is the managed runtime used by apps and some system services on Android… ART as the runtime executes the Dalvik executable (DEX) format and DEX bytecode specification" (ART and Dalvik).

A different instruction set. JVM bytecode is stack-based, as you saw in Part 1. DEX is register-based: "The machine is register-based, and frames are fixed in size upon creation. Each frame consists of a particular number of registers" (Dalvik bytecode format). So a + b is one instruction naming its registers, something like "add v0, v1, v2", instead of iload, iload, iadd, istore: fewer instructions, but each one is bigger.

A different compilation strategy. ART mixes interpreting, JIT and ahead-of-time compilation:

  • AOT: "ART compiles apps using the on-device dex2oat tool. This utility accepts DEX files as input and generates a compiled app executable for the target device."
  • JIT with profiling: "The JIT compiler complements ART's current ahead-of-time (AOT) compiler… JIT makes use of runtime type information, can do better inlining, and makes on stack replacement (OSR) compilation possible" (Implement ART JIT). The profile it records is later used by dex2oat to AOT-compile the hot methods while the phone is idle.
  • Baseline Profiles: ship that profile with your app, so even the first launch is precompiled. They "improve code execution speed by about 30% from the first launch by avoiding interpretation and just-in-time (JIT) compilation steps for included code paths" (Baseline Profiles). It's the same idea as Part 3's AOT cache, arrived at from the phone side.

What this means for you: almost everything in this lesson's Parts 1–2 carries over. Kotlin compiles to JVM bytecode first, so inline, the null checks, data class members and lazy object init are all still there in your Android app, just translated to DEX. What changes is the runtime: the JIT details, the flags and the GC. L24's leak hunting applies directly, though, because a leaked Activity is the classic Android memory bug.

What Kotlin does for you on Android.
  • The same compiler output (null checks, inline, data classes) reaches the phone, because d8 translates the class files kotlinc wrote.
  • R8 "identifies and removes unreachable code from your application and its library dependencies", and kotlin-stdlib is one of those dependencies, so the extra jar from Part 2 shrinks in release builds.
(Both points follow from the d8 and R8 docs linked above. I didn't build an APK to check them.)

Reference answer
  • a + b: HotSpot uses stack bytecode, iload_0, iload_1, iadd. ART uses one register instruction naming source and destination registers.
