A JVM running your program shows up in ps as one process. What does that process get from the OS? (L22)

Each process sees its own virtual address space, which the OS maps onto physical memory. The JVM's heap, thread stacks and compiled code are all regions inside that space, as Part 2 shows with jcmd.

  1. User programs never touch physical RAM directly: the OS maps their virtual addresses onto it.
  2. Processes are isolated from each other. No process gets a piece of another's memory.
  3. The OS gives every process its own private address space, mapped onto physical memory page by page.
  4. A process can run many threads. The JVM alone starts about twenty, as Part 2's NMT summary shows.

In the JVM's model, where does a method's local int variable live while the method runs? (L4)

Each call gets a frame on its thread's stack, holding its local variables. Part 1 opens up that frame: a local-variable array plus a small operand stack.

  1. Each call's frame has a local-variable array, and the int sits in one of its slots.
  2. The heap holds objects. A primitive local isn't an object, so it stays in the frame.
  3. The class file holds the method's code, not the values its variables have while it runs.
  4. JIT-compiled code may keep it in a register, but that's an optimisation. The JVM's model puts it in the frame.

From Java, what do you call a Kotlin companion object function that has no @JvmStatic? (L9)

The companion is a real nested class called Companion, held in a static field. You'll see both in javap output today.

  1. That works only with @JvmStatic, which adds a real static method to Config.
  2. INSTANCE is the field of an object declaration, not of a companion.
  3. ConfigKt would hold the top-level functions of Config.kt, not companion members.
  4. The companion is an instance of a nested class, held in the static field Companion, so calls go through it.

A Java lambda like x -> x * 2 compiles to which bytecode instruction at the call site? (L14)

L14's javap peek showed invokedynamic: the JVM links the lambda at runtime on first use. Records use the same trick for equals, as Part 1 shows.

  1. new is what an anonymous class compiles to. A lambda names no class at compile time.
  2. The JVM links the lambda at runtime, on first use, and then reuses that call site.
  3. The lambda's body does become a private static method, but creating the lambda object needs invokedynamic.
  4. checkcast checks a type, for example after erasure (L13). It never creates a lambda.
Part 1

Bytecode and javap

~38 min

Neither javac nor kotlinc produces machine code. Both produce class files: one .class per class, in a format the JVM specification defines byte by byte (JVMS ch. 4: The class File Format). The JVM doesn't know or care which language produced them. That's the whole reason Kotlin can call Java and back (L9).

$ kotlinc Calc.kt -d out
$ ls out

META-INF
$ java -cp out Calc

$ kotlin -cp out CalcKt

Kotlin's top-level functions had to live in some class, so kotlinc made one named after the file: CalcKt (L9).

Every class file starts with CAFEBABE

$ xxd -l 16 out/Calc.class
00000000: cafe babe 0000 0046 0037 0a00 0200 0307  .......F.7......
$ xxd -l 16 out/CalcKt.class
00000000: cafe babe 0000 0034 0049 0100 0643 616c  .......4.I...Cal
$ javap -v -cp out Calc | grep version
  minor version: 0
  major version: 70
  • Bytes 0–3 are the magic number: "it has the value 0xCAFEBABE" (JVMS §4.1). If those four bytes are wrong, the JVM refuses to load the file.
  • Bytes 4–7 are the minor and major version. 0x46 is 70, which is Java SE 26: a JVM "which conforms to Java SE 26 supports precisely" major versions 45 through 70. Run a version-70 class on an older JVM and you get an UnsupportedClassVersionError.
  • Kotlin wrote 0x34 = 52, which is Java 8's version. That's deliberate: kotlinc's -jvm-target option says "Possible values are 1.8, 9, 10, ..., 26. The default value is 1.8" (Kotlin compiler options), so a plain kotlinc build runs on any JVM from Java 8 up. In a Gradle project the toolchain sets the target instead; your L1 projects use 21.

The JVM is a stack machine

javap -c disassembles the bytecode of each method:

static int add(int, int);
  Code:
     0: iload_0
     1: iload_1
     2: iadd
     3: ireturn
public static final int add(int, int);
  Code:
     0: iload_0
     1: iload_1
     2: iadd
     3: ireturn

Left is javap -c -cp out Calc, right is javap -c -cp out CalcKt: identical instructions. To read them you need the frame from L4, opened up. The spec says each frame "has its own array of local variables, its own operand stack, and a reference to the run-time constant pool" (JVMS §2.6):

  • The local-variable array holds the parameters and locals, numbered from 0. For a static method, slot 0 is the first parameter. For an instance method, slot 0 is this.
  • The operand stack is a scratchpad. Instructions pop their inputs off it and push their results back. iadd has no operands of its own: it pops two ints and pushes their sum.
  • The letter prefix is the type: i for int, l for long, d for double, a for a reference. iload_0 means "push the int in local slot 0".

  private final int x;
  private final int y;
  Point(int, int);
  public static void main(java.lang.String[]);
  public final java.lang.String toString();
  public final int hashCode();
  public final boolean equals(java.lang.Object);
  public int x();
  public int y();
}
  • Kotlin wrote getters (getX), componentN for destructuring, copy, and a hidden static copy$default. The extra int parameter in copy$default is a bitmask saying which arguments were left out, so their defaults (the current values) get used. That's how default arguments work on a JVM that has no such feature.
  • Java wrote accessors named after the components (x(), not getX()), and the class extends java.lang.Record. No copy, no destructuring methods: records do destructuring through pattern matching instead (L7).

The bodies differ even more. Kotlin's equals is 49 bytes of ordinary bytecode: an identity check, instanceof, then a field-by-field compare. The record's equals is four instructions:

The record hands the job to invokedynamic, the same instruction as L14's lambdas. On first call the JVM asks ObjectMethods.bootstrap to build an implementation from the list of components (x;y) and their getters. The API docs describe it as "bootstrap methods for state-driven implementations of core methods, including Object.equals(Object), Object.hashCode(), and Object.toString()" (ObjectMethods; see also JEP 395). The class file stays tiny, and the JDK can improve the implementation without you recompiling.

One more thing in every Kotlin class file: a @kotlin.Metadata annotation (visible in javap -v). It "is present on any class file produced by the Kotlin compiler and is read by the compiler and reflection" (Metadata API). It records the Kotlin-only facts the JVM format can't express, like which types are nullable.

What Kotlin does for you (and you can now prove it in the bytecode).
  • A runtime Intrinsics.checkNotNullParameter guards every non-null parameter of a public function, so null from Java fails fast, at the boundary.
  • Data classes get componentN, copy and copy$default on top of equals/hashCode/toString, all as plain bytecode.
  • inline pastes lambdas into the call site, so there's no lambda object and no boxing of captured vars.
  • Range loops are compiled overflow-safe at Int.MAX_VALUE.
  • Top-level functions get a FileKt class, and companions become a nested class plus a static field: things Java makes you write by hand.
What's the same: it's all ordinary JVM bytecode in an ordinary class file. A when and a switch compile to the same tableswitch.

Hint 1 of 3

Locals and the stack are both already there. iload reads locals[k] and pushes it with addLast; istore does the reverse with removeLast. parts[1].toInt() gives you k.

Hint 2 of 3

For the arithmetic, pop twice, compute, push once. The first value you pop is the one pushed last: for a - b, that's b. Name them right and left so the order is obvious.

Hint 3 of 3

val right = stack.removeLast(); val left = stack.removeLast(); stack.addLast(left - right). ireturn is return stack.removeLast(). In Java, use an ArrayDeque<Integer> with push/pop, and a switch on the opcode string.

Final answer

Why it works. Every instruction is "pop my inputs, push my result", so the loop never needs to know what came before. That's why bytecode is easy to interpret, and why iadd needs no operands: its inputs are whatever sits on top of the stack. Kotlin's Int wraps on overflow exactly like the JVM's iadd, because it is iadd.

Common mistake. stack.removeLast() - stack.removeLast(). Kotlin evaluates left to right, so the first pop is b, and you compute b - a. Addition and multiplication hide the bug; isub exposes it.

What does iadd do?

It's a stack instruction with no operands: its inputs are whatever is on top of the operand stack (JVMS §2.6.2). Adding a constant to a local is iinc.

  1. iadd never names locals. iload instructions must copy them onto the stack first.
  2. The JVM's model has no registers, and adding a constant to a local is iinc.
  3. Its inputs are the top two values on the operand stack, and its result goes back there.
  4. That's iinc 2, 1, which changes a local slot directly without touching the stack.

Kotlin's type system can't stop Java code passing null, so the check makes it fail immediately at the boundary, with the parameter's name in the message, instead of deep inside your code.

  1. It's an extra call, so it costs a little. It's there for safety, not speed.
  2. The JVM has no such rule: Java's greet has no check at all.
  3. Smart casts are checked at compile time and need no runtime helper.
  4. Java doesn't know Kotlin's non-null types, so the check catches a null at the boundary and names the parameter.

How does a Java record implement equals in its class file?

The record's equals is just aload_0, aload_1, invokedynamic, ireturn. The real implementation is built at runtime by java.lang.runtime.ObjectMethods from the component list. Kotlin's data class instead contains the full compare as ordinary bytecode.

  1. That's what Kotlin's data class does. The record's equals is only four instructions.
  2. On first call, the bootstrap method builds the implementation from the component list and their getters.
  3. Object.equals compares identity, but records compare components, so javac writes an override.
  4. No reflection: the bootstrap receives direct method handles (REF_getField), as javap -v showed.

  2. A Function0 is built only for the non-inline twiceNoInline call.

  1. The increment does happen, but the assignment then overwrites i with the value pushed before it.
  2. Postfix stores back the old 5 it pushed; prefix increments first, so 6 is stored.
  3. Prefix ++j increments before its value is read, so j ends up 6.

Class loading and runtime data areas

~28 min

A class file on disk does nothing. Before your code runs, the JVM goes through three steps, which JVMS chapter 5 defines (JVMS ch. 5: Loading, Linking, and Initializing):

  1. Loading: find the bytes for a class (a .class file, a jar entry, the JDK's own modules) and create the class from them.
  2. Linking: verify that the bytecode is well-formed and type-safe, so a hand-crafted class file can't corrupt memory; prepare the static fields with default values; and resolve symbolic references like java/lang/StringBuilder to the real classes.
  3. Initialization: "consists of executing the class or interface initialization method <clinit>". That's your Java static {} blocks and static field initializers, or the Kotlin object/companion init blocks.

The important word is lazy. A class is initialized only on first active use: "Upon execution of a new, getstatic, putstatic, or invokestatic instruction" that refers to it (JVMS §5.5).

Hint 1 of 3

Start with "once only": if name is already in started, return straight away. started.add(name) returns false in exactly that case.

Hint 2 of 3

Order matters: mark the class as started, then use the superclass (if superName isn't null), then record the event, then use each class in initUses. It's recursion (L18): use calls itself.

Hint 3 of 3

Mark it as started before recursing, not after. If you mark it when it's finished, A uses B, B uses A, A isn't marked yet, and the recursion never ends: that's the cycle check. In Java, the same shape works with a HashSet<String> and if (!started.add(name)) return;.

Final answer

Why it works. started.add(name) is both the "once only" rule and the cycle breaker: the JVM records that a class is being initialised before running anything else, and when the same thread asks again, it just returns (JVMS §5.5, step 3). The real Base/Child/Helper classes log the same order your simulation predicts.

Common mistake. Marking the class only after its initialiser finishes. Everything else still passes, but A → B → A recurses until the stack overflows (L4). The real JVM's early mark has a price, though: during a cycle, B sees A half-initialised, with static fields still at their defaults.

Which runtime data area is shared by all threads?

The heap and the method area are shared. The pc register and the JVM stack, with its frames and their operand stacks, are per thread (JVMS §2.5). That sharing is exactly why Phase 8 (concurrency) is hard.

  1. Each thread has its own pc register, because each runs its own instruction.
  2. Each thread has its own JVM stack of frames.
  3. All threads allocate objects in one heap and can share references to them.
  4. An operand stack lives inside one frame, so it belongs to one call on one thread.

The columns, as printed by HotSpot's CompileTask::print (implementation detail; the format isn't a documented contract):

Three things the JIT does that javac doesn't

javac and kotlinc barely optimize; you saw them translate almost line by line. The real optimizing happens at runtime, where C2 can see which code is actually hot and which types actually show up.

Items 1 and 2 are an optional deep dive into JIT internals; if you skip them, skip the Check question on -XX:-DoEscapeAnalysis too. Item 3, dead-code elimination, is core: L24 and L41 rely on it.

1 · Inlining. Optional deep dive Calling a tiny method costs more than the method body. C2 copies small, hot callees into the caller, like inline but done automatically at runtime and only where it pays off. Watch it with -XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining (the java command) on the next program:

                              @ 30   Escape$Point::y (5 bytes)   accessor

The constructor chain and both accessors were pasted into sumPoints. Once the code is hot, a getter costs essentially nothing, so don't avoid them for speed.

2 · Escape analysis. Optional deep dive Once everything is inlined, C2 can see that each Point never leaves the method. "Escape analysis is a technique by which the Java HotSpot Server Compiler can analyze the scope of a new object's uses and decide whether to allocate the object on the Java heap." An object that doesn't escape is "scalar replaceable": C2 keeps its fields in registers and never allocates it. Note that it "does not replace a heap allocation with a stack allocation" (HotSpot performance enhancements: Escape Analysis). The other road: GraalVM Native Image

The AOT cache keeps the JVM and makes it start from a snapshot. GraalVM Native Image goes much further: it compiles your program and the parts of the JDK it uses "ahead-of-time to a binary—a native executable", with no JVM underneath (GraalVM: Native Image). To do that, it makes a closed-world assumption. At build time, a static analysis starts from main and keeps only the classes, methods and fields it can prove are reachable. Everything else is left out, and "once a native image is built, no new elements can be added at run time, for example, through class loading" (Native Image Basics).

That buys a lot. The executable "starts in milliseconds", "delivers peak performance immediately, with no warmup" and "uses a fraction of the resources required by the Java Virtual Machine", because there's no class loading, bytecode interpreter or warm-up left to do. It also costs a lot:

  • No JIT at runtime. Everything you saw in this part (profiles, C2, deoptimizing when a guess turns out wrong) is gone. The code was optimized once, before it shipped, from "a static view of the code". Oracle GraalVM can feed it a profile recorded on an instrumented build instead (profile-guided optimization).
  • Dynamic features must be declared up front. The analysis can't see what reflection, resource loading, serialization, dynamic proxies or JNI will touch, so you list those classes in reachability-metadata.json. Forget one, and a reflective call throws MissingReflectionRegistrationError, an Error you aren't meant to catch (Reachability Metadata).
  • Frameworks must change how they start. A container that scans annotations by reflection at startup, like the one you'll build in L25, breaks this model. Spring Boot's answer is Spring AOT: "rather than parsing @Configuration classes and generating bean definitions at runtime, it does it at build-time", writing Java source code plus the JSON hint files. The price is that the classpath is fixed and beans can't change at runtime, so @ConditionalOnProperty isn't supported (Spring Boot: Introducing GraalVM Native Images).

Project Leyden's stated aim is "to improve the startup time, time to peak performance, and footprint of Java programs" (Project Leyden), while keeping Java dynamic. In September 2025, Oracle announced it was detaching GraalVM from the Java SE release train (summary on inside.java). GraalVM for JDK 24 was the last release supported as part of Oracle's Java SE products, Native Image is no longer offered to Java SE customers, and Oracle points them to Leyden for startup and footprint. GraalVM itself carries on as its own project with its own releases. So, in practice: for a server on the JVM, try the AOT cache first, because it costs one training run and no code changes. Reach for a native executable when millisecond startup and a small footprint matter more than peak throughput (a command-line tool, or a function that scales to zero), and accept the closed world. Hint 1 of 3

Split on whitespace, as the starter does. tokens[0] is the time and tokens[1] the ID. The method is the token containing ::, and the size is the token starting with (.

Hint 2 of 3

Everything between the ID and the method is the "middle": flag characters such as %, then the tier if there is one. middle.any { '%' in it } gives osr; middle.lastOrNull()?.toIntOrNull() gives the tier, or null when the last token isn't a number (L3's safe call).

Hint 3 of 3

c2Landed is lines.map(::parse).firstOrNull { it.method == method && it.tier == 4 && !it.osr && !it.retired }?.ms. In Java, make Compile a record, use Integer for the nullable tier, and loop instead of firstOrNull.

Final answer

Why it works. The only reliable anchors in the line are the first two numbers, the :: in the method name and the (N bytes) size; everything else is optional. Ignoring OSR lines matters: a % compile only gives the running loop a way in, at the @ offset. The method's normal entry point gets C2 code only when the full-method compile lands.

Common mistake. Taking the first tier-4 line. In Hot's log that's the OSR compile at 10 ms, nine milliseconds before C2's whole-method version. (This format is a HotSpot implementation detail, so a parser like this is for your own logs, not production.)

In -XX:+PrintCompilation output, what does % mark?

OSR: a hot loop compiled while its method is still running, and entered at the bytecode offset after @. (s marks synchronized, ! exception handlers, n native.)

  1. % marks a loop compiled while its method was running, entered at the @ offset.
  2. Thrown exceptions aren't logged here. ! marks a method that has exception handlers.
  3. Synchronized methods are marked s, not %.
  4. % says nothing about success. It only marks an on-stack replacement compile.

Why did -XX:-DoEscapeAnalysis make every round allocate 24 MB?

Escape analysis is what lets C2 scalar-replace non-escaping objects, keeping their fields in registers. Without it, all one million Points are allocated on the heap each round. HotSpot never moves them to the stack.

  1. HotSpot never stack-allocates. With escape analysis on it scalar-replaces; off, every object goes on the heap.
  2. The GC kept running. The 24 MB counts what was allocated, which collection doesn't change.
  3. Without escape analysis, C2 can't prove a Point stays local, so every one is allocated.
  4. C2 still compiled the method. Only its escape-analysis pass was switched off.

A loop calls Math.log(x) ten million times, ignores the result, and takes 0 µs. Why?

Dead-code elimination: after inlining, the result is provably unused, so the work is deleted. JMH's Blackhole and returned values exist to stop this (L24).

  1. The JDK doesn't cache log results, and the "used" loop still took about 30 ms.
  2. nanoTime resolves far below a millisecond, and the same timer measured the used loop fine.
  3. Branch prediction guesses jumps, not results. Ten million logarithms still take real time.
  4. After inlining, C2 saw that the result was never used, so it deleted the work.

What does a JDK 25+ AOT cache (-XX:AOTCache) mainly speed up?

It stores classes already loaded and linked, plus profiles, from a training run, so later runs skip that work (JEPs 483, 514, 515). Peak speed still comes from the JIT.

  1. The cache holds loaded classes and profiles. The garbage collector works exactly as before.
  2. Later runs skip loading and linking, and the JIT starts from recorded profiles.
  3. Peak speed still comes from C2 compiling at runtime. The cache only gets you there sooner.
  4. Class files are untouched. The cache is a separate file next to your jar.

A native executable reads a class name from a config file, then calls Class.forName(name). It worked on the JVM. What happens now?

The closed-world analysis can't know which name the file will hold, so the class must be listed in the reachability metadata. Otherwise the reflective lookup fails at runtime (GraalVM: Reachability Metadata).

  1. A native executable has no JIT and can't load new classes at runtime. Everything was compiled at build time.
  2. On the JVM the class is loaded on demand. A closed world has nothing left to load it from.
  3. Only classes declared in reachability-metadata.json are kept for reflection. An undeclared one fails at runtime.
  4. The build can't see the file's contents, so it succeeds. The failure shows up only when the lookup runs.

Your Spring Boot service on the JVM starts too slowly. Which option speeds up startup with no code changes and keeps the JIT?

An AOT cache is a training run plus a flag on the normal JVM; JEP 483 lists "do not require any change to the code" as a goal. Native Image and Spring AOT trade dynamism for startup.

  1. One training run makes the cache, later runs use it, and C1/C2 still compile hot code using the cached profiles.
  2. A native executable has no JIT, and it often needs reflection metadata and framework AOT processing first.
  3. -XX:-TieredCompilation removes C1, which usually makes a large app start slower, not faster.
  4. Spring AOT moves bean setup to build time for native images, and it fixes the classpath and beans in place.

Android's ART vs the JVM

~18 min

This part is docs only. I didn't build or run any Android code for it, and every claim links to the Android docs.

Your Android app is written in the same Kotlin and compiled by the same kotlinc into the same JVM class files. But a phone doesn't run HotSpot. Here's the pipeline:

  1. .class → DEX. "d8 is a command-line tool that Android Studio and the Android Gradle plugin use to compile your project's Java bytecode into DEX bytecode that runs on Android devices" (d8).
  2. Shrinking. In release builds, R8 removes unused code and renames things. "Obfuscation (also known as minification): To reduce the size of the DEX file, R8 shortens the names of classes, fields, and methods (for example, com.example.MyActivity could become a.b.a)" (Enable app optimization with R8). This is why release stack traces need a mapping file.
  3. ART runs the DEX. "Android runtime (ART) is the managed runtime used by apps and some system services on Android… ART as the runtime executes the Dalvik executable (DEX) format and DEX bytecode specification" (ART and Dalvik).

A different instruction set. JVM bytecode is stack-based, as you saw in Part 1. DEX is register-based: "The machine is register-based, and frames are fixed in size upon creation. Each frame consists of a particular number of registers" (Dalvik bytecode format). So a + b is one instruction naming its registers, something like "add v0, v1, v2", instead of iload, iload, iadd, istore: fewer instructions, but each one is bigger.

A different compilation strategy. ART mixes interpreting, JIT and ahead-of-time compilation:

  • AOT: "ART compiles apps using the on-device dex2oat tool. This utility accepts DEX files as input and generates a compiled app executable for the target device."
  • JIT with profiling: "The JIT compiler complements ART's current ahead-of-time (AOT) compiler… JIT makes use of runtime type information, can do better inlining, and makes on stack replacement (OSR) compilation possible" (Implement ART JIT). The profile it records is later used by dex2oat to AOT-compile the hot methods while the phone is idle.
  • Baseline Profiles: ship that profile with your app, so even the first launch is precompiled. They "improve code execution speed by about 30% from the first launch by avoiding interpretation and just-in-time (JIT) compilation steps for included code paths" (Baseline Profiles). It's the same idea as Part 3's AOT cache, arrived at from the phone side.

Hint 1 of 3

Walk the mapping one line at a time. row.trim().split(" -> ") gives the original and the obfuscated side. A row that doesn't start with a space is a class line: drop the trailing : and compare it with obfClass.

Hint 2 of 3

Keep a flag, "am I inside the right class?". Inside it, a row whose right side equals obfMethod and whose left side contains ( is a candidate method. The original name is the word just before (: left.substringBefore('(').substringAfterLast(' ').

Hint 3 of 3

For the line range, match ^(\d+):(\d+): at the start of left. Accept the candidate when there's no range, or when line.toInt() is in first..last. If no class line matched, return frame. In Java, use Pattern/Matcher for both regexes and split(" -> ") the same way.

Final answer

Why it works. The mapping file is a two-level map, class then members, and only line numbers can tell apart two methods that R8 renamed to the same a. That's why release builds should keep line-number information. This is a toy: Android's real retrace tool also maps the line numbers back to the source, and handles methods R8 inlined into others (R8 retrace, mapping format).

Common mistake. Taking the first method whose short name matches. a.b.a.a then always says lend, and you'd debug the wrong method. ProGuard's ReTrace, given no line numbers, lists every candidate instead of guessing.

Which tool turns your app's .class files into DEX?

d8 compiles Java bytecode to DEX at build time. dex2oat runs later, on the device, turning DEX into machine code.

  1. dex2oat runs later, on the device, and turns DEX into machine code.
  2. d8 is the build-time tool that compiles Java bytecode into DEX.
  3. javap only prints class files. It never converts anything.
  4. kotlinc writes ordinary .class files. Turning them into DEX is d8's job.

How does DEX bytecode differ from JVM bytecode?

"The machine is register-based, and frames are fixed in size upon creation" (Dalvik bytecode format). JVM bytecode is stack-based.

  1. DEX has invoke instructions, just as JVM bytecode has invokevirtual and friends.
  2. It's still bytecode: ART interprets it, JIT-compiles it, or compiles it ahead of time with dex2oat.
  3. Loops are just jumps, and DEX has branch instructions like any bytecode.
  4. Each instruction names registers in a fixed-size frame instead of using an operand stack.

What do Baseline Profiles give an Android app?

ART uses the shipped profile to AOT-compile the listed code paths at install, avoiding interpretation and JIT for them: "about 30%" faster from the first launch.

  1. ART compiles the listed paths ahead of time, so even the first launch skips interpreting them.
  2. Shrinking the DEX is R8's job. Profiles don't make it smaller.
  3. Profiles guide compilation. They don't change the garbage collector.
  4. Readable traces come from R8's mapping file and retrace, not from profiles.

L16 said to run warm-up iterations before timing. Which part of today explains why?

Early runs measure the interpreter and C1, and include compile time. Only after C2 takes over (the ~90 µs batches in Hot) are you timing the steady state.

  1. The version decides whether a class loads at all, not how fast it runs.
  2. Early runs measure the interpreter, C1 and compile time before C2 code takes over.
  3. Delegation decides which loader finds a class. Once loaded, it doesn't affect speed.
  4. DEX is Android's format. Warm-up on HotSpot comes from the JIT tiers.

L13 said generics are erased. Where would you look to see that for yourself?

javap -c shows descriptors like (Ljava/lang/Object;)… plus checkcast where a type parameter was used. L13 showed exactly that with javap -s.

  1. GC logs show heap collections. They know nothing about type parameters.
  2. NMT reports memory per JVM subsystem, not method signatures.
  3. PrintInlining shows which calls C2 inlined, not declared types.
  4. Descriptors show Object where the type parameter was, plus checkcast where it's used.

Kotlin: data class Money(val cents: Long, val currency: String) used as a HashMap key. Is it safe? (L19)

You saw the generated equals and hashCode in javap -p. With immutable val properties, the key can't change while it's in the map.

  1. The data class generates both from its properties, and vals mean the key can't change.
  2. javap -p showed hashCode() right there in the class.
  3. A generated equals already exists. A hand-written one risks breaking its pairing with hashCode.
  4. TreeMap needs an ordering, not hashing. A HashMap is fine here.

A JUnit test calls a Kotlin function with null from Java code. When does it fail? (L11)

Intrinsics.checkNotNullParameter is the very first call in the method, so the NPE names the parameter at the boundary. That's handy in an assertThrows.

  1. javac doesn't enforce Kotlin's non-null types, so passing null compiles.
  2. The check at the top fails first, before the body can touch the null.
  3. checkNotNullParameter is the first call in the method, so the NPE names the parameter at once.
  4. Kotlin never substitutes values. It fails fast with a NullPointerException.
