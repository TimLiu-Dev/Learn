Part 1

Recursion and the call stack

~30 min

A function is recursive when it calls itself. It sounds circular, but it isn't, as long as every call works on a smaller version of the problem and there's a version small enough to answer directly. Every recursive function has two parts:

  • Base case: an input you can answer without recursing. Without one, the function never stops.
  • Recursive case: shrink the problem, call yourself on the smaller piece, and combine the answer.

The classic first example is n! = n × (n−1)!, with 1! = 1 as the base case:

24

Step through it. This is the L4 stack visualizer again, now with the same function on the stack four times. Watch each frame pause, waiting for the one above it:

Three things to notice. Every call gets its own frame with its own n; nothing is shared. The calls go down until the base case, and the multiplications happen on the way back up. And the deepest moment, five frames, is exactly the depth of the recursion. That depth is what runs out later in this part.

Trust the recursion

Don't try to trace every call in your head when you write a recursive function. Instead, assume the recursive call already works for the smaller input (the "leap of faith"), and ask only: given the answer for the rest, how do I build the answer for the whole?

desserts
  • sum: if I already knew the sum of everything after the first element, I'd just add the first element. The base case is the empty list, whose sum is 0.
  • reverse: if I already had the rest reversed ("tressed" → "dessert"), I'd stick the first char on the end. The base case is a string of length 0 or 1, which is its own reverse.
  • The checklist for every recursive function: is there a base case, does every call get closer to it, and does the combining step use the smaller answer correctly?

These are teaching examples, not good code: subList and substring make the recursion pleasant to read, but substring copies characters, so reverse is O(n²). In real code you'd use a loop, or s.reversed() / new StringBuilder(s).reverse().

When recursion explodes: naive Fibonacci

Each Fibonacci number is the sum of the two before it: fib(n) = fib(n−1) + fib(n−2). Translated literally, each call makes two more calls. Count them:

fib(10) = 55   calls = 177   0 ms
fib(20) = 6,765   calls = 21,891   0 ms
fib(30) = 832,040   calls = 2,692,537   2 ms
fib(40) = 102,334,155   calls = 331,160,281   331 ms
fib(45) = 1,134,903,170   calls = 3,672,623,805   3540 ms

Five more in n, about 11 times the work (the Java run printed the same counts and near-identical times). The calls grow like 1.618n: exponential, the 2n-family row of L16's table. The waste is that the same values are computed over and over: fib(45) calls fib(2) hundreds of millions of times. Remembering answers you've already computed (memoisation) makes this linear, and it's the first idea of dynamic programming in L21.

When recursion runs out of stack

Every call that hasn't returned yet holds a frame, and a thread's stack has a fixed size. So recursion depth is limited, no matter how simple each call is:

sumTo(10_000) = 50005000
sumTo(1_000_000): StackOverflowError

dive(): StackOverflowError after 47342 frames

On my machine the default thread stack is 2 MB, which fits roughly 40,000–50,000 of these small frames. The exact number changes from run to run (three more Java runs gave 43,514, 45,844 and 44,305), because the JIT compiler changes frame sizes as it optimises code mid-run. -Xss from L4 moves the limit, but only moves it:

A bigger stack buys depth, but a million-deep recursion still fails. With a 512 KB stack even sumTo(10_000) dies. The robust fix is the boring one: sumToLoop uses one frame however big n is. Rule of thumb: recursion is great when the depth is small, like log n for binary search and merge sort, or a tree's height. It's risky when the depth grows with n, like walking a long list one element per call.

Catching StackOverflowError is only here so one program can show several results. It's an Error, not an Exception (L10), and real code shouldn't catch it.

Kotlin's tailrec: recursion that compiles to a loop

A call is a tail call when it's the very last thing a function does, with nothing left to compute afterwards. n + sumTo(n - 1) is not a tail call, because the addition still has to happen when the call returns. Carry the running total in a parameter instead (an accumulator), and the call becomes the last step. Kotlin can then reuse the same frame: "When a function is marked with the tailrec modifier and meets the required formal conditions, the compiler optimizes out the recursion, leaving behind a fast and efficient loop based version instead" (Kotlin docs: Tail recursive functions).

Mark a function tailrec when its recursive call isn't in tail position, and you get no optimisation, just a warning:

err/NotTail.kt:2:1: warning: a function is marked as tail-recursive but no tail calls are found.
tailrec fun sumTo(n: Long): Long = if (n == 0L) 0 else n + sumTo(n - 1)
^^^^^^^
err/NotTail.kt:2:60: warning: recursive call is not a tail call.
tailrec fun sumTo(n: Long): Long = if (n == 0L) 0 else n + sumTo(n - 1)

It's only a warning, so the code still compiles and still overflows on deep input. Read your warnings. The docs list the rules: "You can apply the tailrec modifier to a function only when it calls itself as its final operation. You cannot use tail recursion when there is more code after the recursive call, within try/catch/finally blocks, or when the function is open."

Recursion fits recursive data

Recursion is most natural when the data is defined recursively. A linked list (L17) is "empty, or a node followed by a smaller list". A tree, coming in L20, is "empty, or a node with two smaller trees". The function's shape copies the data's shape:

length=3 sum=8
size=6 height=3

null is the base case: an empty list has length 0, and an empty tree has size 0. size makes two recursive calls, one per subtree, like fib. But each node is visited exactly once, so it's O(n), not exponential: fib's problem was repeating the same sub-problems, not the branching itself. The recursion depth is the tree's height, which is why L20 cares so much about keeping trees balanced.

What Kotlin does for you.
  • tailrec turns tail recursion into a loop at compile time, and warns when it can't. Java has no equivalent, so in Java a deep recursion has to be rewritten as a loop by hand.
  • if is an expression, so many recursive definitions are one line that reads like the maths: = if (n <= 1) 1 else n * factorial(n - 1). Java needs ? : or a block with returns.
  • Node? in the type says "a list may end here", and the compiler won't let you forget the null base case. In Java, a missing null check is a NullPointerException at runtime.
  • Default parameters (acc: Long = 0) hide the accumulator from callers. In Java you'd add a public one-argument overload that calls the two-argument version.
What's the same: one frame per call, the same stack limit, the same StackOverflowError.

Reference solutions

fastPow halves n on every call (62 → 31 → 15 → 7 → 3 → 1 → 0), so it makes about log₂ n + 1 calls: L16's halving idea, and the same idea as binary search, coming next. Check

What makes a recursive function stop calling itself?

The base case answers directly without recursing. If it's missing or never reached, the calls continue until StackOverflowError.

Naive fib(n) makes how many calls compared with fib(n - 1)?

Calls grow like the golden ratio, 1.618n: 21,891 for fib(20) and 2,692,537 for fib(30). Exponential, but with base 1.6 rather than 2.

Which body can Kotlin's tailrec turn into a loop?

Only there is the recursive call the last operation. In the other three, a multiplication or addition still has to happen after the call returns, so the frame must stay alive.

Which change reliably makes Java's sumTo(1_000_000) work?

Java doesn't eliminate tail calls, so an accumulator alone still overflows (that's Tailrec.java). -Xss only moves the limit. A loop uses one frame.

Part 2

Binary search

~25 min

Finding a value in an unsorted array means checking every element: O(n). If the array is sorted, you can do much better. Look at the middle element. If it's too small, the target can only be to its right, so throw away the left half; if it's too big, throw away the right half. Every comparison halves what's left. Sorted input is the precondition: binary search on unsorted data gives wrong answers without any error.

search 23:
  lo=0 mid=5 hi=10  a[mid]=13
  lo=6 mid=8 hi=10  a[mid]=23
-> 8
search 4:
  lo=0 mid=5 hi=10  a[mid]=13
  lo=0 mid=2 hi=4  a[mid]=5
  lo=0 mid=0 hi=1  a[mid]=2
  lo=1 mid=1 hi=1  a[mid]=3
-> -1
recursive: 8 -1

The comment on lo and hi is the most important line. A loop invariant is a statement that's true before every iteration: here, "if the target is anywhere, it's in a[lo..hi]". Each branch keeps it true (a[mid] < target means nothing at or left of mid can match, so lo = mid + 1 is safe). When lo > hi the range is empty, so the invariant says the target isn't there. This is exactly how Sedgewick and Wayne describe it: the method works by "maintaining variables lo and hi such that the key is in a[lo..hi] if it is in the array" (Algorithms §1.1). Most binary-search bugs, like hi = mid instead of mid - 1, or < instead of <=, break the invariant or the termination. The recursive version is the same algorithm. Its depth is only log₂ n, so the stack is never a worry.

Why it's O(log n)

n =         1,000   steps = 10
n =     1,000,000   steps = 20
n = 1,000,000,000   steps = 30

A thousand times more data costs ten more steps. After k steps, n/2k items remain, and the loop ends when that reaches 1, so k ≈ log₂ n. (This simulates an array where a[i] == i, so it can count steps for a billion elements without allocating 4 GB.)

The bug that hid in the JDK for nine years

In 2006 Joshua Bloch, who wrote java.util.Arrays.binarySearch (and Effective Java), published "Extra, Extra – Read All About It: Nearly All Binary Searches and Mergesorts are Broken". The JDK's version "contained the same bug. It was reported to Sun recently when it broke someone's program, after lying in wait for nine years or so." The bug is the line almost everyone writes:

int mid = (low + high) / 2;

It "fails if the sum of low and high is greater than the maximum positive int value (231 − 1). The sum overflows to a negative value, and the value stays negative when divided by two." That's L2's overflow, inside the most famous algorithm there is. A real array needs about a billion elements (230) to trigger it, so this demo searches a pretend array with the same index arithmetic:

As the target is near the top, lo climbs past a billion and lo + hi wraps negative. Two standard fixes:

  • lo + (hi - lo) / 2: hi - lo is never bigger than the array size, so nothing overflows. This lesson uses it everywhere.
  • (lo + hi) >>> 1 (Kotlin: ushr 1): the sum still overflows, but the unsigned shift treats its 32 bits as a positive number, so the halving comes out right. It's the line the JDK uses today, in OpenJDK's Arrays.java: int mid = (low + high) >>> 1;

Bloch's conclusion is the real lesson: "It is hard to write even the smallest piece of code correctly." The bug also "applies equally to mergesort", which is why your merge sort in the final computes its midpoint the same safe way.

Use the JDK's version, and read its return value

In real code you don't write binary search. You call Arrays.binarySearch or Collections.binarySearch, or Kotlin's List.binarySearch. When the key is missing, they don't just return −1; they tell you where it would go. The API docs say they return the "index of the search key, if it is contained in the array; otherwise, (-(insertion point) - 1). The insertion point is defined as the point at which the key would be inserted into the array: the index of the first element greater than the key, or a.length if all elements in the array are less than the specified key" (Arrays.binarySearch). Kotlin uses the same convention, which it calls "the inverted insertion point" (Kotlin API: binarySearch).

30 -> 2  (found at 2)
35 -> -4  (missing, insert at 3)
5 -> -1  (missing, insert at 0)

kiwi -> 2, grape -> -3
unsorted, 10 -> -1
  • Why -(insertion point) - 1 and not just -(insertion point)? Because an insertion point of 0 would give -0 == 0, which looks like "found at 0". The extra −1 "guarantees that the return value will be >= 0 if and only if the key is found."
  • The last line is the trap. 10 is in that array, at index 1, but the search says missing. The docs: "If it is not sorted, the results are undefined." No exception, just a wrong answer.
  • With duplicates, "there is no guarantee which one will be found". If you need the first one, you need a lower bound, which is the exercise.
What Kotlin does for you.
  • binarySearch is a method on every List, with optional fromIndex/toIndex, so there's no separate Collections utility class to remember.
  • when with conditions lays out the three-way branch (less, greater, found) as a table.
  • A plain Int overflows exactly like Java's int, silently. Kotlin does not protect you from the midpoint bug; you still have to write lo + (hi - lo) / 2. And >>> is spelled ushr.
What's the same: the algorithm, the invariant, the return-value convention, and the sorted precondition.
Exercise: lower bound, upper bound, count

A lower bound is the first index whose element is ≥ the target. It's the insertion point when the target is missing, and the first occurrence when it's present. The trick is a half-open range [lo, hi) that starts with hi = a.size, because "after the last element" is a valid answer.

  1. lowerBound(a, target): the first i with a[i] >= target, or a.size.
  2. upperBound(a, target): the first i with a[i] > target, or a.size. Exactly one character differs from lowerBound.
  3. countOf(a, x) in O(log n), using the two functions.
lower(2)=1 upper(2)=4 count(2)=3
lower(4)=5 count(4)=0
lower(0)=0 lower(9)=7
empty: 0

Test on [1, 2, 2, 2, 3, 5, 8]. For every loop, say the invariant out loud before you write the body.

Reference solutions

The invariant: everything left of lo is < target, and everything at or right of hi is ≥ target. When a[mid] >= target, mid itself might be the answer, so it's hi = mid, not mid - 1. The loop condition is lo < hi because [lo, hi) is empty when they're equal, and they meet at the answer. You'll write this generic version again in the final, test-first.

Check

What happens when you binary-search an array that isn't sorted?

"If it is not sorted, the results are undefined." The demo's 10 was present but reported missing. There's no exception and no warning, just a wrong answer.

What is wrong with mid = (lo + hi) / 2 on huge arrays?

When lo + hi passes 231 − 1 it wraps negative, giving a negative index. Use lo + (hi - lo) / 2 or (lo + hi) >>> 1.

Arrays.binarySearch(new int[]{10, 20, 30}, 25) returns what?

25 would be inserted at index 2 (before 30), so the result is -(2) - 1 = -3. Decode it with -r - 1.

When does lowerBound(a, target) return a.size?

No element is ≥ target, so the insertion point is after the end. It's the same as the JDK's "a.length if all elements in the array are less than the specified key".

Part 3

Sorting: insertion, merge, quick

~35 min

Binary search needs sorted data, so sorting comes next. This part builds three classic sorts, each with a different idea, and then measures them. Every comparison goes through a tiny less() function so we can count comparisons. Sedgewick and Wayne use the same trick (Algorithms §2.1).

Watch them work first. This is the same 8-element array sorted by the three algorithms below. The traces were recorded from instrumented copies of this code, and the comparison counts match the real less() counter: 21, 17 and 16. Use the tabs, and press Step ▶ or the arrow keys:

Insertion sort: like sorting a hand of cards

The left part of the array is always sorted. Take the next element (the key), slide bigger elements one step right until you find its spot, and drop it in. On random data each key slides about halfway, so it's O(n²). On data that's already nearly sorted each key barely moves, so it's close to O(n). Sedgewick: "Insertion sort works well for certain types of nonrandom arrays that often arise in practice, even if they are huge." The number of moves equals the number of inversions, pairs that are out of order (§2.1). It sorts in place, and it's stable, a word explained below.

Merge sort: divide, recurse, merge

Recursion from Part 1 doing real work. The base case is "0 or 1 items are already sorted". The recursive case is "sort each half, then merge": walk both sorted halves with one finger each, and always take the smaller front item. Merging is O(n). Halving gives log₂ n levels, and each level merges n items in total, so merge sort is O(n log n) every time. "Its prime disadvantage is that it uses extra space proportional to N" (Algorithms §2.2): those copyOfRange arrays. The recursion depth is only log₂ n, so the stack is safe. Taking from the right only when strictly smaller keeps equal items in their original order, which makes it stable.

Quicksort: partition around a pivot

Merge sort does its work after recursing (the merge). Quicksort does it before. Choose a pivot, then partition: move everything smaller to its left, and the pivot lands in its final position. Then sort the two sides recursively; there's nothing to merge. If the pivot splits the range roughly in half, that's log n levels of O(n) work: O(n log n) on average, in place, with no extra array. If the pivot is always the smallest or largest item, one side is empty and the other has n − 1 items: n levels, O(n²), and recursion depth n. Choosing the last element as pivot does exactly that on input that's already sorted. "Quicksort uses ~N²/2 compares in the worst case, but random shuffling protects against this case" (Algorithms §2.3).

Stability: why "ties keep their order" matters

A sort is stable if items that compare as equal stay in the order they had before. That matters when you sort by one key and want an earlier order preserved. Here the students start in alphabetical order and are sorted by grade:

input     B:Ada A:Ben B:Cy A:Di C:Eve A:Flo
stable    A:Ben A:Di A:Flo B:Ada B:Cy C:Eve
quick     A:Flo A:Di A:Ben B:Ada B:Cy C:Eve

The JDK's sort keeps the A students alphabetical; our quicksort reversed them, because partitioning swaps items over long distances. So "sort by name, then stably by grade" gives "by grade, alphabetical within each grade" for free, but only with a stable sort. Insertion and merge sort are stable as written (the strict < is what makes them so); quicksort is not.

What the JDK actually uses

The API docs say it in their implementation notes:

  • Primitives, e.g. Arrays.sort(int[]): "The sorting algorithm is a Dual-Pivot Quicksort by Vladimir Yaroslavskiy, Jon Bentley, and Joshua Bloch. This algorithm offers O(n log(n)) performance on all data sets" (Arrays.sort(int[])). Stability doesn't matter for primitives: two equal ints are indistinguishable.
  • Objects, e.g. Arrays.sort(Object[]) and List.sort: "This sort is guaranteed to be stable" and "This implementation is a stable, adaptive, iterative mergesort … If the input array is nearly sorted, the implementation requires approximately n comparisons … adapted from Tim Peters's list sort for Python (TimSort)" (Arrays.sort(Object[]), List.sort). TimSort is a merge sort that handles short stretches with "a binary insertion sort" (OpenJDK TimSort.java, an implementation detail rather than a guarantee): your two stable sorts, combined.
  • Kotlin doesn't have its own algorithm on the JVM. Its docs promise "The sort is stable" (sorted, sortWith), and a stack trace shows who's really doing the work:

Comparable vs Comparator: sorting anything

The sorts above only handle Int. To sort any type, you need a way to compare two items. There are two (L13, L14):

[apple, date, fig, kiwi, pear]
[fig, pear, kiwi, date, apple]
[Run, Hey, Go]
  • Comparable is the type's own natural order: String, Int and dates implement it. A generic sort bounds T by it: Kotlin <T : Comparable<T>>, Java <T extends Comparable<? super T>>. The Java wildcard is L13's PECS: a T compared by a supertype's compareTo still qualifies.
  • Comparator is an order passed in from outside, so one type can be sorted many ways. Kotlin's Comparator<in T> and Java's Comparator<? super T> mean the same thing.
  • The natural-order version just calls the comparator version with naturalOrder(), so one algorithm serves both.
  • The songs show stability again: Hey and Go are both 210 seconds, and they keep their original order.
Bridge to Android and Spring. Every sorted list on screen, like a RecyclerView of messages by date or a REST endpoint returning products by price, ends in one of these library sorts with a comparator. Stability is why "sort by date, then by unread" works the way users expect. And when you see Sort.by("firstname").ascending().and(Sort.by("lastname").descending()) in Spring Data (Spring Data docs: Paging and Sorting), the "then by" idea is the same one as thenBy.
What Kotlin does for you.
  • compareBy { it.length }.thenByDescending { it } builds comparators from lambdas. Java's Comparator.comparing(...).thenComparing(...) is the same idea, but you often need a type witness like Comparator.<String>reverseOrder().
  • sorted(), sortedBy and sortedWith return a new list; sort() and sortWith sort a mutable list in place. The name tells you whether the original changes. In Java, list.sort mutates, and stream().sorted() copies.
  • Extension functions like IntArray.swap and a.copyOfRange(…) read naturally. Java needs a static helper and Arrays.copyOfRange(a, …).
  • Function references like ::insertionSort make a list of algorithms easy to loop over (L14). Java needs Consumer<int[]> and method references.
What's the same: the algorithms, their Big O, and the library underneath, which is java.util's TimSort and Dual-Pivot Quicksort in both languages.

[b, d]

Reference solutions

Reversed means every pair is out of order: 1,000 × 999 / 2 = 499,500 inversions, so 499,500 shifts. In the nearly sorted array, the 500 at index 10 is bigger than the 490 values after it up to index 500 (the 489 values in between, plus the 10). The 10 at index 500 is smaller than those 489 values in between. That's 490 + 489 = 979 inversions. Shifts equal inversions, exactly as Sedgewick's proposition says, so one swapped pair costs a few hundred moves, not hundreds of thousands. That's why TimSort uses insertion sort on short, nearly ordered runs.

Check

Which sort is fastest on a large array that is already almost sorted?

Its cost is proportional to n plus the number of inversions: 999 compares on sorted input of 1,000. Naive quicksort is at its worst there.

Quicksort with the last element as pivot, on already-sorted input, costs what?

Each partition peels off just the pivot, so there are n levels of up to n comparisons: about n²/2 (7,979,992 for n = 4,000), plus a recursion n deep.

What does it mean for a sort to be stable?

Items that compare as equal keep their original relative order. Merge sort uses O(n) extra memory and is still stable. Stability is about order, not space.

Which algorithm does Arrays.sort(int[]) use?

Primitives use Dual-Pivot Quicksort, where stability is irrelevant. Objects use the stable TimSort.

On the JVM, Kotlin's list.sortedWith(cmp) ends up running which class?

The stack trace showed sortedWith → Arrays.sort → TimSort.sort. Kotlin reuses the JDK's stable object sort.

Wrap-up

Exit quiz, recall card, sources

~5 min

In the red-green-refactor loop, what do you write first? (L11)

Red first: a test that fails for the right reason. Then the smallest code that turns it green, then tidy up.

Which method decides the order when you call sorted() on a list of your own class? (L7)

sorted() needs T : Comparable<T> and calls compareTo. A data class or record generates equals/hashCode, but not an ordering.

Kotlin's require(lo <= hi) fails. What is thrown? (L10)

require checks arguments (IllegalArgumentException); check checks state (IllegalStateException).

Why does Java's sort signature use Comparable<? super T> rather than Comparable<T>? (L13)

If Fruit implements Comparable<Fruit>, then Apple is comparable only as a Fruit. ? super T (PECS: a consumer) still accepts it.

Kotlin: println(Int.MAX_VALUE + 1). What happens? (L2)

Two's complement wraps silently to Int.MIN_VALUE. That's exactly the binary-search midpoint bug.
