You push 1, 2 and 3 onto a stack, then pop once. What comes out? (L17)

Last in, first out. Keep that picture: the JVM's call stack works exactly the same way, and Part 1 is all about it.

  1. A stack is last in, first out, so the most recent push, 3, comes off first.
  2. 1 was pushed first, so it comes out last. First in, first out is a queue.
  3. 2 sits in the middle: it comes out second, after 3.
  4. The stack holds three values, so one pop can't come back empty.

What does each frame on a thread's call stack hold? (L4)

One frame per active call, holding that call's parameters and locals. Objects live on the heap, and frames hold references to them (JVM spec §2.6).

  1. Objects live on the heap. A frame holds only references to them.
  2. Bytecode is stored once with the loaded class and shared by every call.
  3. Each call gets its own frame for its parameters and locals, popped when it returns.
  4. The garbage collector's bookkeeping belongs to the JVM, not to your method's frames.

What does the -Xss flag change? (L4)

-Xss sets the thread stack size; -Xmx is the heap. Part 1 uses it to make a recursion survive deeper.

  1. That's -Xmx. Objects go on the heap; frames don't.
  2. Collectors are chosen with flags like -XX:+UseG1GC, not -Xss.
  3. JIT tuning uses -XX options. -Xss doesn't touch compilation.
  4. -Xss sets the stack size per thread, which limits how deep recursion can go.

You halve a range of 1,000,000 items until one is left. About how many halvings? (L16)

220 ≈ 1,048,576, so about 20. That's what O(log n) means in practice, and it's binary search's whole trick.

  1. 1,000 is the square root of a million. Halving shrinks much faster than that.
  2. 220 ≈ 1,000,000, so twenty halvings get down to one item.
  3. 500,000 is what's left after one halving, not the number of halvings.
  4. 100 halvings would handle 2100 items, vastly more than a million.

In a doubling experiment the time goes ×4 every time n doubles. Which growth rate? (L16)

(2n)² = 4n². You'll see exactly ×4.0 for insertion sort in Part 3, and about ×2.1 for the O(n log n) sorts.

  1. Linear time doubles when n doubles: ×2, not ×4.
  2. n log n grows a little more than ×2 per doubling, about ×2.1.
  3. (2n)² = 4n², so doubling n multiplies the time by exactly 4.
  4. Exponential time squares when n doubles, which is far worse than ×4.

compareBy<String> { it.length }.thenBy { it } orders words how? (L14)

The first key wins; thenBy only breaks ties. Part 3 hands comparators like this to your own sort.

  1. compareBy sets the main key, and thenBy only breaks ties between equal lengths.
  2. That would be compareBy { it }.thenBy { it.length }. The first key wins.
  3. Longest first needs compareByDescending. compareBy is ascending.
  4. A comparator defines a real order, and sorting with it does reorder the words.
Part 1

Recursion and the call stack

~38 min

A function is recursive when it calls itself. It sounds circular, but it isn't, as long as every call works on a smaller version of the problem and there's a version small enough to answer directly. Every recursive function has two parts:

  • Base case: an input you can answer without recursing. Without one, the function never stops.
  • Recursive case: shrink the problem, call yourself on the smaller piece, and combine the answer.

The classic first example is n! = n × (n−1)!, with 1! = 1 as the base case:

Three things to notice. Every call gets its own frame with its own n; nothing is shared. The calls go down until the base case, and the multiplications happen on the way back up. And the deepest moment, five frames, is exactly the depth of the recursion. That depth is what runs out later in this part.

Trust the recursion

Don't try to trace every call in your head when you write a recursive function. Instead, assume the recursive call already works for the smaller input (the "leap of faith"), and ask only: given the answer for the rest, how do I build the answer for the whole?

When recursion explodes: naive Fibonacci

Each Fibonacci number is the sum of the two before it: fib(n) = fib(n−1) + fib(n−2). Translated literally, each call makes two more calls. Count them:

fib(10) = 55   calls = 177   0 ms
fib(20) = 6,765   calls = 21,891   0 ms
fib(30) = 832,040   calls = 2,692,537   2 ms
fib(40) = 102,334,155   calls = 331,160,281   331 ms
fib(45) = 1,134,903,170   calls = 3,672,623,805   3540 ms

Five more in n, about 11 times the work (the Java run printed the same counts and near-identical times). The calls grow like 1.618n: exponential, the 2n-family row of L16's table. The waste is that the same values are computed over and over: fib(45) calls fib(2) hundreds of millions of times. Remembering answers you've already computed (memoisation) makes this linear, and it's the first idea of dynamic programming in L21.

Kotlin's tailrec: recursion that compiles to a loop

A call is a tail call when it's the very last thing a function does, with nothing left to compute afterwards. n + sumTo(n - 1) is not a tail call, because the addition still has to happen when the call returns. Carry the running total in a parameter instead (an accumulator), and the call becomes the last step. Kotlin can then reuse the same frame: "When a function is marked with the tailrec modifier and meets the required formal conditions, the compiler optimizes out the recursion, leaving behind a fast and efficient loop based version instead" (Kotlin docs: Tail recursive functions).

Recursion fits recursive data

Recursion is most natural when the data is defined recursively. A linked list (L17) is "empty, or a node followed by a smaller list". A tree, coming in L20, is "empty, or a node with two smaller trees". The function's shape copies the data's shape:

length=3 sum=8
size=6 height=3

null is the base case: an empty list has length 0, and an empty tree has size 0. size makes two recursive calls, one per subtree, like fib. But each node is visited exactly once, so it's O(n), not exponential: fib's problem was repeating the same sub-problems, not the branching itself. The recursion depth is the tree's height, which is why L20 cares so much about keeping trees balanced.

What Kotlin does for you.
  • tailrec turns tail recursion into a loop at compile time, and warns when it can't. Java has no equivalent, so in Java a deep recursion has to be rewritten as a loop by hand.
  • if is an expression, so many recursive definitions are one line that reads like the maths: = if (n <= 1) 1 else n * factorial(n - 1). Java needs ? : or a block with returns.
  • Node? in the type says "a list may end here", and the compiler won't let you forget the null base case. In Java, a missing null check is a NullPointerException at runtime.
  • Default parameters (acc: Long = 0) hide the accumulator from callers. In Java you'd add a public one-argument overload that calls the two-argument version.
What's the same: one frame per call, the same stack limit, the same StackOverflowError.

Hint 1 of 3

Both base cases are the empty list, node == null. For maxValue the answer there is null, not 0: a list of negative numbers has a max below 0.

Hint 2 of 3

Trust the recursion: maxValue(node.next) is the max of the rest, or null if the rest is empty. In that case node.value is the answer; otherwise take the bigger of the two. For without, first get without(node.next, x), then either drop node or put a new Node(node.value, rest) in front.

Hint 3 of 3

val rest = maxValue(node.next) ?: return node.value handles the one-element case in one line. In Java, the return type is Integer so it can be null; compare with rest == null before unboxing.

Final answer

Why it works. Each function copies the shape of the data: an empty list is the base case, and a node is "one value plus a smaller list". The leap of faith gives you the answer for the rest, and you only decide how the first node changes it. without builds new nodes on the way back up, so the old list is never touched.

Common mistake. if (node == null) return 0 for the max. It passes for positive numbers, but for -5, -1, -9 it returns 0, a value that isn't in the list. A base case must be a true answer for the empty input, and an empty list has no max.

What makes a recursive function stop calling itself?

The base case answers directly without recursing. If it's missing or never reached, the calls continue until StackOverflowError.

  1. The JVM never spots repetition. Without a base case, the calls continue until the stack overflows.
  2. The base case returns an answer directly, so the chain of calls stops there.
  3. Arguments don't run out by themselves. The base case has to test for the smallest input.
  4. tailrec only reuses the frame. Without a base case, a tailrec function loops forever.

Naive fib(n) makes how many calls compared with fib(n - 1)?

Calls grow like the golden ratio, 1.618n: 21,891 for fib(20) and 2,692,537 for fib(30). Exponential, but with base 1.6 rather than 2.

  1. One more call per step would be linear. Each call makes two more, so the work compounds.
  2. fib(n-1) and fib(n-2) differ in size, so the count grows by less than ×2.
  3. The extra fib(n-1) call makes the total strictly bigger every step.
  4. calls(n) = calls(n−1) + calls(n−2) + 1, so the ratio approaches the golden ratio, 1.618.

Which body can Kotlin's tailrec turn into a loop?

Only there is the recursive call the last operation. In the other three, a multiplication or addition still has to happen after the call returns, so the frame must stay alive.

  1. The multiplication by n waits for the call to return, so it isn't a tail call.
  2. acc * n is computed before the call, as an argument, so the call is the last step.
  3. The + 1 runs after the call returns, so the frame must stay alive.
  4. Writing the 1 first changes nothing: the addition still waits for the call.

Which change reliably makes Java's sumTo(1_000_000) work?

Java doesn't eliminate tail calls, so an accumulator alone still overflows (that's Tailrec.java). -Xss only moves the limit. A loop uses one frame.

  1. Java has no tail-call elimination, so Tailrec.java still overflowed at one million.
  2. A retry runs the same million-deep recursion and overflows again.
  3. A loop keeps one frame no matter how big n is.
  4. final stops overriding. It doesn't change how many frames the calls need.

Each call adds its n before and after the recursive call. What prints?

fun countdown(n: Int): String {

  1. The second half is added as frames return, deepest first, so it counts up, not down.
  2. Down the stack builds 3 2 1; coming back up adds 1 2 3.
  3. Each frame's two copies of n are separated by everything the deeper calls produce.
  4. The outermost call, n = 3, adds its first part before any deeper call runs.

Binary search

~33 min

Finding a value in an unsorted array means checking every element: O(n). If the array is sorted, you can do much better. Look at the middle element. If it's too small, the target can only be to its right, so throw away the left half; if it's too big, throw away the right half. Every comparison halves what's left. Sorted input is the precondition: binary search on unsorted data gives wrong answers without any error.

search 23:
  lo=0 mid=5 hi=10  a[mid]=13
  lo=6 mid=8 hi=10  a[mid]=23
-> 8
search 4:
  lo=0 mid=5 hi=10  a[mid]=13
  lo=0 mid=2 hi=4  a[mid]=5
  lo=0 mid=0 hi=1  a[mid]=2
  lo=1 mid=1 hi=1  a[mid]=3
-> -1
recursive: 8 -1

The comment on lo and hi is the most important line. A loop invariant is a statement that's true before every iteration: here, "if the target is anywhere, it's in a[lo..hi]". Each branch keeps it true (a[mid] < target means nothing at or left of mid can match, so lo = mid + 1 is safe). When lo > hi the range is empty, so the invariant says the target isn't there. This is exactly how Sedgewick and Wayne describe it: the method works by "maintaining variables lo and hi such that the key is in a[lo..hi] if it is in the array" (Algorithms §1.1). Most binary-search bugs, like hi = mid instead of mid - 1, or < instead of <=, break the invariant or the termination. The recursive version is the same algorithm. Its depth is only log₂ n, so the stack is never a worry.

Why it's O(log n)

n =         1,000   steps = 10
n =     1,000,000   steps = 20
n = 1,000,000,000   steps = 30

A thousand times more data costs ten more steps. After k steps, n/2k items remain, and the loop ends when that reaches 1, so k ≈ log₂ n. (This simulates an array where a[i] == i, so it can count steps for a billion elements without allocating 4 GB.)

The bug that hid in the JDK for nine years

In 2006 Joshua Bloch, who wrote java.util.Arrays.binarySearch (and Effective Java), published "Extra, Extra – Read All About It: Nearly All Binary Searches and Mergesorts are Broken". The JDK's version "contained the same bug. It was reported to Sun recently when it broke someone's program, after lying in wait for nine years or so." The bug is the line almost everyone writes:

int mid = (low + high) / 2;

It "fails if the sum of low and high is greater than the maximum positive int value (231 − 1). The sum overflows to a negative value, and the value stays negative when divided by two." That's L2's overflow, inside the most famous algorithm there is. Use the JDK's version, and read its return value

In real code you don't write binary search. You call Arrays.binarySearch or Collections.binarySearch, or Kotlin's List.binarySearch. When the key is missing, they don't just return −1; they tell you where it would go. The API docs say they return the "index of the search key, if it is contained in the array; otherwise, (-(insertion point) - 1). The insertion point is defined as the point at which the key would be inserted into the array: the index of the first element greater than the key, or a.length if all elements in the array are less than the specified key" (Arrays.binarySearch). Kotlin uses the same convention, which it calls "the inverted insertion point" (Kotlin API: binarySearch).

Both are the Part 2 exercise's lower bound and upper bound with a half-open range [lo, hi) and hi = xs.size. Never return from inside the loop; let lo and hi meet.

Hint 2 of 3

For firstIndexOf, loop while lo < hi: if xs[mid] < target then lo = mid + 1, else hi = mid. After the loop, lo is the first index with xs[lo] >= target, but it might be xs.size or a bigger value, so check before you return it.

Hint 3 of 3

insertSorted is the same loop with <= instead of <, so lo lands after the last equal value; then xs.add(lo, x). In Java, the list is a List<Integer>: compare with xs.get(mid), which unboxes, and insert with xs.add(lo, x).

Final answer

Why it works. The invariant is "everything left of lo is too small, everything from hi on is big enough". Each step halves [lo, hi) and keeps it true, so the loop ends with lo == hi at the boundary: the first copy if target is present. The comparison decides which boundary: < finds the first value ≥ target, <= the first value > x.

Common mistake. Finding any copy with the usual binary search, then walking left while the values are equal. The answer is right, but on a million equal values the walk reads the list about 500,000 times: O(n), not O(log n). The counting check catches it.

What happens when you binary-search an array that isn't sorted?

"If it is not sorted, the results are undefined." The demo's 10 was present but reported missing. There's no exception and no warning, just a wrong answer.

  1. Sorting would cost O(n log n) and change your data. Binary search never does that.
  2. It halves using comparisons that assume order, so it can skip right past the target.
  3. Checking the order would cost O(n), so the JDK doesn't check, and throws nothing.
  4. It never falls back to a scan. It just trusts the precondition.

What is wrong with mid = (lo + hi) / 2 on huge arrays?

When lo + hi passes 231 − 1 it wraps negative, giving a negative index. Use lo + (hi - lo) / 2 or (lo + hi) >>> 1.

  1. For non-negative indices, rounding down is exactly what a midpoint needs.
  2. (lo + hi) / 2 does land in the middle, as long as the sum doesn't overflow.
  3. Past 231 − 1 the int sum wraps negative, giving a negative index.
  4. One addition and one division are cheap. The problem is correctness, not speed.

Arrays.binarySearch(new int[]{10, 20, 30}, 25) returns what?

25 would be inserted at index 2 (before 30), so the result is -(2) - 1 = -3. Decode it with -r - 1.

  1. 25 isn't in the array, so the result must be negative. 2 is only its insertion point.
  2. That's -(insertion point) without the extra −1.
  3. Index 1 holds 20. A missing key never gets a non-negative result.
  4. Insertion point 2 gives -(2) - 1 = -3, and -r - 1 decodes it back to 2.

When does lowerBound(a, target) return a.size?

No element is ≥ target, so the insertion point is after the end. It's the same as the JDK's "a.length if all elements in the array are less than the specified key".

  1. No element is ≥ target, so the first such index is just past the end.
  2. Unsorted input gives undefined results, not a guaranteed a.size.
  3. With duplicates it returns the first copy's index, which is inside the array.
  4. If the target is at index 0, the lower bound is 0.

        int lo = 0, hi = a.length;
        while (lo < hi) {
            int mid = lo + (hi - lo) / 2;
            if (a[mid] <= target) lo = mid + 1;

Insertion sort: like sorting a hand of cards

The left part of the array is always sorted. Take the next element (the key), slide bigger elements one step right until you find its spot, and drop it in. On random data each key slides about halfway, so it's O(n²). On data that's already nearly sorted each key barely moves, so it's close to O(n). Sedgewick: "Insertion sort works well for certain types of nonrandom arrays that often arise in practice, even if they are huge." The number of moves equals the number of inversions, pairs that are out of order (§2.1). It sorts in place, and it's stable, a word explained below.

Merge sort: divide, recurse, merge

Recursion from Part 1 doing real work. The base case is "0 or 1 items are already sorted". The recursive case is "sort each half, then merge": walk both sorted halves with one finger each, and always take the smaller front item. Merging is O(n). Halving gives log₂ n levels, and each level merges n items in total, so merge sort is O(n log n) every time. "Its prime disadvantage is that it uses extra space proportional to N" (Algorithms §2.2): those copyOfRange arrays. The recursion depth is only log₂ n, so the stack is safe. Taking from the right only when strictly smaller keeps equal items in their original order, which makes it stable.

Quicksort: partition around a pivot

Merge sort does its work after recursing (the merge). Quicksort does it before. Choose a pivot, then partition: move everything smaller to its left, and the pivot lands in its final position. Then sort the two sides recursively; there's nothing to merge. If the pivot splits the range roughly in half, that's log n levels of O(n) work: O(n log n) on average, in place, with no extra array. If the pivot is always the smallest or largest item, one side is empty and the other has n − 1 items: n levels, O(n²), and recursion depth n. Choosing the last element as pivot does exactly that on input that's already sorted. "Quicksort uses ~N²/2 compares in the worst case, but random shuffling protects against this case" (Algorithms §2.3).

Hint 1 of 3

Start from MergeSort.kt: same base case, same split, same merge. Inversions come in three kinds: both items in the left half, both in the right half, or one in each. The two recursive calls count the first two kinds.

Hint 2 of 3

The crossing pairs show up during the merge. When you take right[j] because it's smaller than left[i], it's also smaller than everything after left[i], since the left half is sorted. That's left.size - i inversions in one step.

Hint 3 of 3

Take from the right only when right[j] < left[i], strictly. On a tie, take from the left and count nothing. Use a Long for the count: 100,000 reversed items already have about 5 billion inversions. Java: long count = sortAndCount(left) + sortAndCount(right); and Arrays.copyOfRange.

Final answer

Why it works. Every inversion is either inside one half, which the recursion counts, or crosses the middle, which the merge counts. When right[j] goes first, the left.size - i items still waiting on the left are all bigger, so each makes one crossing inversion. Counting them in one addition, instead of one by one, keeps the whole thing O(n log n).

Common mistake. Taking from the right on a tie, right[j] <= left[i]. The array still ends up sorted, but every pair of equal values gets counted: [2, 2, 2] gives 3 instead of 0. It's the same < that makes merge sort stable.

Which sort is fastest on a large array that is already almost sorted?

Its cost is proportional to n plus the number of inversions: 999 compares on sorted input of 1,000. Naive quicksort is at its worst there.

  1. A last-element pivot on sorted data splits off one item at a time: about n²/2 compares.
  2. Merge sort stays O(n log n) on sorted input: 4,932 compares for 1,000 items, against insertion's 999.
  3. Each key moves only past its inversions, so nearly sorted input costs close to n.
  4. Selection sort always scans the whole unsorted rest: about n²/2 compares, whatever the order.

Quicksort with the last element as pivot, on already-sorted input, costs what?

Each partition peels off just the pivot, so there are n levels of up to n comparisons: about n²/2 (7,979,992 for n = 4,000), plus a recursion n deep.

  1. That needs balanced splits. A last-element pivot on sorted data splits off only one item.
  2. n levels of partitioning, each scanning nearly the whole range: about n²/2 compares.
  3. One partition pass is already O(n), and there are n of them here.
  4. A sort has to look at every item at least once, so it can't be O(log n).

Java: insertion sort by rank, with >= in the inner loop. What prints?

import java.util.*;

public class TieShift {
    record Card(int rank, char suit) {
        public String toString() { return "" + rank + suit; }
    }

    // Insertion sort by rank, but the loop shifts while a[j] >= key.
    static void sort(List<Card> a) {
        for (int i = 1; i < a.size(); i++) {
            Card key = a.get(i);
            int j = i - 1;
            while (j >= 0 && a.get(j).rank() >= key.rank()) {
                a.set(j + 1, a.get(j));
                j--;
            }
            a.set(j + 1, key);
        }
    }

    public static void main(String[] args) {
        List<Card> hand = new ArrayList<>(List.of(
            new Card(5, 'h'), new Card(2, 's'), new Card(5, 'c'), new Card(2, 'd')));
        sort(hand);
        System.out.println(hand);
    }
}

The ranks come out sorted, but >= also shifts cards of the same rank, so each key jumps ahead of its equals and every tie group is reversed: 2s was before 2d, and 5h before 5c. With > the loop stops at an equal card, and the sort is stable. One character decides stability, like merge sort's strict <.

  1. That's the stable result, which needs >. >= moves each card past its equals.
  2. It still sorts ascending. >= only changes what happens to ties.
  3. The 5s flip too: when 5c is inserted, it shifts past 5h because 5 ≥ 5.
  4. Sorted by rank, and each later card jumped ahead of its equal, so both tie groups are reversed.

In the red-green-refactor loop, what do you write first? (L11)

Red first: a test that fails for the right reason. Then the smallest code that turns it green, then tidy up.

  1. Code written first leaves no proof that the test can fail.
  2. Refactoring comes last, once a green test protects you.
  3. Red first: a test that fails for the right reason proves it checks something.
  4. A test that passes before any code exists can't catch a missing feature.

Which method decides the order when you call sorted() on a list of your own class? (L7)

sorted() needs T : Comparable<T> and calls compareTo. A data class or record generates equals/hashCode, but not an ordering.

  1. equals only says same or different, not which comes first.
  2. sorted() requires Comparable and asks compareTo for less, equal or greater.
  3. hashCode picks hash buckets (L19). It says nothing about order.
  4. toString is for display. Sorting never calls it, unless your comparator does.

Kotlin's require(lo <= hi) fails. What is thrown? (L10)

require checks arguments (IllegalArgumentException); check checks state (IllegalStateException).

  1. That's what check throws, for bad state.
  2. require doesn't index anything. It reports a bad argument.
  3. Nothing here is null. require throws its own exception type.
  4. require checks preconditions on arguments, so it throws IllegalArgumentException.

Why does Java's sort signature use Comparable<? super T> rather than Comparable<T>? (L13)

If Fruit implements Comparable<Fruit>, then Apple is comparable only as a Fruit. ? super T (PECS: a consumer) still accepts it.

  1. An Apple compares as a Fruit, and ? super T accepts Comparable<Fruit>.
  2. Generics are erased at compile time, so wildcards never change speed.
  3. Primitives can't be type arguments at all. int[] has its own overloads.
  4. Stability comes from the algorithm, not from the type bound.

Kotlin: println(Int.MAX_VALUE + 1). What happens? (L2)

Two's complement wraps silently to Int.MIN_VALUE. That's exactly the binary-search midpoint bug.

  1. JVM Int arithmetic doesn't check for overflow, so nothing is thrown.
  2. An Int expression stays Int. Kotlin never widens it to Long by itself.
  3. Two's complement wraps past the top to Int.MIN_VALUE, -2147483648.
  4. Stopping at the maximum is saturating arithmetic, which the JVM doesn't do.
