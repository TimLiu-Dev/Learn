The Relational Model & SQL

Every app you'll build keeps its data somewhere, and most of the time that somewhere speaks SQL. This lesson builds a small library database, then teaches you to ask it questions: filter, sort, join and group, with every answer checked against a real sqlite3 run. Along the way you'll meet the traps that fool AI-written queries most often: NULL logic and the LEFT JOIN that quietly turns into an inner one.

Part 1

Tables, primary keys, foreign keys

~25 min

The relational model comes from E. F. Codd's 1970 paper "A Relational Model of Data for Large Shared Data Banks". Its idea is simple: keep all data in relations, which SQL calls tables. Each table holds rows (tuples) with the same named, typed columns (attributes). You never follow pointers from row to row, as you did with L17's linked nodes; instead, rows refer to each other by value, through keys. The PostgreSQL manual's Data Definition chapter is a clear, free walk through tables, constraints and keys.

This phase uses one small database for all three lessons: a library with authors, books, members and loans.

Types, and SQLite's flexible typing

Most databases enforce column types strictly. SQLite doesn't, by design: "the datatype of a value is associated with the value itself, not with its container", and "Flexible typing is a feature of SQLite, not a bug" (Datatypes In SQLite). A column's declared type only sets its affinity, a preference SQLite applies when it can:

$ /usr/bin/sqlite3 -echo -header -column -nullvalue NULL :memory: < affinity.sql
CREATE TABLE t (n INTEGER);
INSERT INTO t VALUES (42), ('42'), ('forty-two'), (4.5);
SELECT n, typeof(n) FROM t;
n          typeof(n)
---------  ---------
42         integer
42         integer
forty-two  text
4.5        real
CREATE TABLE s (n INTEGER) STRICT;
INSERT INTO s VALUES ('42');
INSERT INTO s VALUES ('forty-two');
Runtime error near line 6: cannot store TEXT value in INTEGER column s.n (19)

The string '42' looked like a number, so INTEGER affinity converted it. 'forty-two' couldn't be converted, so SQLite stored text in an INTEGER column without complaint. PostgreSQL would reject that insert. If you want rigid types in SQLite, add STRICT after the closing parenthesis: "As of version 3.37.0 (2021-11-27), SQLite provides STRICT tables that do rigid type enforcement" (STRICT Tables). The '42' insert still worked there: a STRICT table still "attempts to coerce the data into the appropriate type", and only "If the value cannot be losslessly converted" does it raise an error, as the second insert did (same page).

Primary keys

A primary key identifies one row: unique, and never NULL. A natural key is real-world data that happens to be unique, such as an email address or an ISBN. A surrogate key is a meaningless number the database hands out. Our tables use surrogate ids, because real-world "unique" data changes: people change their email, and some books have no ISBN.

In SQLite, a column declared exactly INTEGER PRIMARY KEY "becomes an alias for the rowid", the hidden 64-bit integer every ordinary table already has. The docs warn that the name must be exactly INTEGER: "Other integer type names like "INT" or "BIGINT" … causes the primary key column to behave as an ordinary table column" (CREATE TABLE: ROWIDs). Leave the id out of an INSERT and SQLite picks the next one:

$ cp library.db scratch.db
$ /usr/bin/sqlite3 -echo -header -column -nullvalue NULL scratch.db < rowid.sql
SELECT rowid, id, title FROM books LIMIT 2;
id  id  title
--  --  -------------------------
1   1   A Wizard of Earthsea
2   2   The Left Hand of Darkness
INSERT INTO books (title, author_id, year, price_cents) VALUES ('Piranesi', NULL, 2020, 1399);
SELECT id, title FROM books WHERE title = 'Piranesi';
id  title
--  --------
21  Piranesi

Notice the header of the first result: id id. Asking for rowid gave back a column labelled id, because they're the same column.

Foreign keys and referential integrity

A foreign key says "this column's value must exist as a key in that table": every loans.book_id must be a real books.id. That guarantee is called referential integrity. Here's SQLite's biggest surprise: foreign-key enforcement "is disabled by default", and every connection must turn it on with PRAGMA foreign_keys = ON (SQLite Foreign Key Support, section 2). The Quirks page explains it's for backward compatibility, because enforcement only arrived in 2009.

$ cp library.db scratch.db
$ /usr/bin/sqlite3 -echo -header -column -nullvalue NULL scratch.db < fk.sql
PRAGMA foreign_keys;
foreign_keys
------------
0
INSERT INTO loans (book_id, member_id, loaned) VALUES (999, 1, '2026-10-01');
PRAGMA foreign_key_check;
table  rowid  parent  fkid
-----  -----  ------  ----
loans  31     books   1
PRAGMA foreign_keys = ON;
INSERT INTO loans (book_id, member_id, loaned) VALUES (998, 1, '2026-10-01');
Runtime error near line 5: FOREIGN KEY constraint failed (19)
DELETE FROM authors WHERE id = 5;
Runtime error near line 6: FOREIGN KEY constraint failed (19)

With enforcement off, a loan for book 999 went straight in. PRAGMA foreign_key_check finds the orphan afterwards (row 31 of loans points at a missing books row). Once enforcement was on, the same kind of insert failed, and so did deleting an author who still has books. Run the PRAGMA every time you open a connection; L36 does it in JDBC.

That delete failed because books.author_id has no ON DELETE clause, so the default is to refuse. The PostgreSQL docs list the other choices: "CASCADE specifies that when a referenced row is deleted, row(s) referencing it should be automatically deleted as well", and SET NULL sets the referencing column to NULL instead (Constraints, §5.5.5). SQLite supports the same actions. A cascade, on a scratch copy:

$ cp library.db scratch.db
$ /usr/bin/sqlite3 -echo -header -column -nullvalue NULL scratch.db < ondelete.sql
PRAGMA foreign_keys = ON;
CREATE TABLE reviews (
  id      INTEGER PRIMARY KEY,
  book_id INTEGER NOT NULL REFERENCES books(id) ON DELETE CASCADE,
  stars   INTEGER CHECK (stars BETWEEN 1 AND 5)
);
INSERT INTO reviews (book_id, stars) VALUES (19, 5), (19, 4), (20, 3);
DELETE FROM books WHERE id = 19;
SELECT * FROM reviews;
id  book_id  stars
--  -------  -----
3   20       3

Deleting Beowulf (book 19) took its two reviews with it. Cascades are right when the child can't exist without the parent; a review of a deleted book is meaningless. For loans you'd want the refusal instead: you don't silently erase lending history.

NOT NULL, UNIQUE and CHECK

Three more constraints make the database itself reject bad data, whichever program writes it:

$ cp library.db scratch.db
$ /usr/bin/sqlite3 -echo -header -column -nullvalue NULL scratch.db < constraints.sql
INSERT INTO books (author_id, year, price_cents) VALUES (5, 1990, 999);
Runtime error near line 1: NOT NULL constraint failed: books.title (19)
INSERT INTO members (name, email) VALUES ('Ada Again', 'ada@example.com');
Runtime error near line 2: UNIQUE constraint failed: members.email (19)
INSERT INTO books (title, author_id, year, price_cents) VALUES ('Future Book', 3, 3000, 999);
Runtime error near line 3: CHECK constraint failed: year BETWEEN 1400 AND 2100 (19)

Each error names the rule that was broken. This is the database version of L10's require: fail loudly at the boundary rather than store nonsense.

Create, update, delete

INSERT adds rows, UPDATE … SET … WHERE changes them, and DELETE … WHERE removes them. The CLI's changes() function reports how many rows the last statement touched. The last two statements are the classic disaster, on a scratch copy:

$ cp library.db scratch.db
$ /usr/bin/sqlite3 -echo -header -column -nullvalue NULL scratch.db < crud.sql
INSERT INTO members (name, email, joined) VALUES ('Linus Torvalds', 'linus@example.com', '2026-10-01');
UPDATE members SET email = 'linus@kernel.example' WHERE name = 'Linus Torvalds';
SELECT id, name, email FROM members WHERE id = 9;
id  name            email
--  --------------  --------------------
9   Linus Torvalds  linus@kernel.example
DELETE FROM members WHERE id = 9;
SELECT changes();
changes()
---------
1
UPDATE books SET price_cents = 0;
SELECT changes();
changes()
---------
20
SELECT count(*) AS free_books FROM books WHERE price_cents = 0;
free_books
----------
20

One missing WHERE, and all 20 books became free. There's no undo. Two habits help: write the WHERE first and run it as a SELECT to see exactly which rows match, and use transactions (L36) so a mistake can be rolled back.

From table to type

When code reads a row, each column becomes a field, and the column's nullability should become the field's nullability. Here's the books row as a Kotlin data class and a Java record:

Book(id=19, title=Beowulf, authorId=7, year=null, priceCents=799)
age: unknown

Get the mapping wrong, and both compilers catch it. Declare year as a non-null type and pass Beowulf's NULL:

err/RowTypesBad.kt:4:33: error: null cannot be a value of a non-null type 'Int'.
    println(Book(19, "Beowulf", null))
                                ^^^^
err/RowTypesBad.java:5: error: constructor Book in record Book cannot be applied to given types;
        System.out.println(new Book(19, "Beowulf", null));
                           ^
  required: int,String,int
  found:    int,String,<null>
  reason: argument mismatch; <null> cannot be converted to int

The Java error only happened because int is a primitive. Java's String title would accept null without a word, even though the column is NOT NULL.

What Kotlin does for you.
  • Nullability matches the schema. String means NOT NULL and Int? means nullable, checked at compile time. In Java every reference type, String included, can be null, so a NOT NULL column has no type-level guarantee.
  • One nullable type for every column. Int? works for a nullable INTEGER. Java needs the boxed Integer, because int can't hold null (L5's boxing).
  • Safe access. year?.let { 2026 - it } ?: "unknown" (L3) is one expression. Java needs an explicit null check or a ternary.
  • Both languages generate equals, hashCode and toString for the row type (L7), which makes rows easy to compare in tests.

Check

In a fresh sqlite3 session, with no PRAGMA, you insert a loan whose book_id is 999 (no such book). What happens?

Foreign-key enforcement "is disabled by default" in SQLite (docs, section 2). Only PRAGMA foreign_keys = ON, on that connection, makes it an error.

CREATE TABLE t (n INTEGER); INSERT INTO t VALUES ('forty-two'); then SELECT typeof(n) FROM t;

INTEGER affinity converts text only when it looks like a number. Otherwise the value keeps its own type, text. A STRICT table would have refused it.

Which column declaration becomes an alias for SQLite's rowid?

The declared type must be exactly INTEGER. "INT" or "BIGINT" make an ordinary column with a unique index (CREATE TABLE).

Foreign keys are on. You delete an author whose books still reference them, and books.author_id has no ON DELETE clause.

The default action refuses the delete: "FOREIGN KEY constraint failed". You'd only get a cascade or NULLs by asking for ON DELETE CASCADE or ON DELETE SET NULL.

Part 2

SELECT, WHERE, ORDER BY

~25 min

A SELECT describes the result you want. It doesn't say how to get it; the database decides that, much as L15's pipelines leave the "how" to Sequence. Pick columns (and expressions over them), give them names with AS, and remove duplicate rows with DISTINCT:

price_cents / 100.0 is computed per row. Dividing by 100.0 rather than 100 matters, because integer division drops the fraction (Part 3 shows it). Prices are stored in cents for the same reason L32 sent money as integers: no floating-point rounding (L2).

WHERE: filtering rows

WHERE keeps the rows for which its condition is true. Comparisons (= <> < <= > >=) combine with AND, OR and NOT, and here's the first trap: AND binds tighter than OR, just like && and || in Kotlin and Java. "Pratchett or Le Guin books under $10", two ways:

$ /usr/bin/sqlite3 -echo -header -column -nullvalue NULL library.db < precedence.sql
SELECT title, author_id, price_cents FROM books
WHERE author_id = 5 OR author_id = 1 AND price_cents < 1000;
title            author_id  price_cents
---------------  ---------  -----------
Guards! Guards!  5          999
Small Gods       5          999
Going Postal     5          1099
Mort             5          899
SELECT title, author_id, price_cents FROM books
WHERE (author_id = 5 OR author_id = 1) AND price_cents < 1000;
title            author_id  price_cents
---------------  ---------  -----------
Guards! Guards!  5          999
Small Gods       5          999
Mort             5          899

The first query means "any Pratchett book, or a Le Guin book under $10", so Going Postal ($10.99) sneaks in. Parentheses say what you meant. When AND and OR mix, always add them.

  • IN (…) is shorthand for a chain of = … OR.
  • BETWEEN a AND b includes both ends.
  • LIKE matches a pattern: % is any run of characters, and _ is exactly one. 'the %' matched "The…": in SQLite, LIKE is case-insensitive for ASCII letters only. The docs warn that "'a' LIKE 'A' is TRUE but 'æ' LIKE 'Æ' is FALSE" (SQL Language Expressions: LIKE). PostgreSQL's LIKE is case-sensitive; it offers ILIKE "to make the match case-insensitive" (Pattern Matching), so the same query behaves differently there.

NULL and three-valued logic

NULL means "unknown", and SQL takes that literally. Any comparison with NULL gives NULL (unknown), not true or false, and WHERE keeps only rows where the condition is true. The PostgreSQL docs put it bluntly: "Do not write expression = NULL because NULL is not “equal to” NULL" (Comparison Functions and Operators).

$ /usr/bin/sqlite3 -echo -header -column -nullvalue NULL library.db < nulls.sql
SELECT title FROM books WHERE year = NULL;
SELECT title FROM books WHERE year IS NULL;
title
-------
Beowulf
SELECT NULL = NULL AS eq, NULL IS NULL AS is_null, 1 + NULL AS sum;
eq    is_null  sum
----  -------  ----
NULL  1        NULL
SELECT title, COALESCE(year, 'unknown') AS year FROM books WHERE author_id = 7;
title                            year
-------------------------------  -------
Beowulf                          unknown
Sir Gawain and the Green Knight  1400

year = NULL returned nothing at all, not even Beowulf. IS NULL is the test you want. Arithmetic with NULL gives NULL, and COALESCE(a, b) picks the first non-NULL value, much like Kotlin's ?:.

The nastiest NULL trap hides in NOT IN. "Authors with no books" works, until one book has an unknown author:

$ /usr/bin/sqlite3 -echo -header -column -nullvalue NULL scratch.db < notin.sql
SELECT name FROM authors WHERE id NOT IN (SELECT author_id FROM books);
name
--------------

INSERT INTO books (title, author_id, year, price_cents) VALUES ('Piranesi', NULL, 2020, 1399);

One NULL author_id made NOT IN return nothing. To SQL, "is 8 not in (1, 2, …, NULL)?" is unknown, because the NULL might be 8.   • NULL becomes 0. The ResultSet docs say getInt returns "if the value is SQL NULL, the value returned is 0". Beowulf didn't come from the year 0. What Kotlin does for you.
  • use { } closes everything. Connection, statement and result set each get a use block, closed in reverse order even if an exception escapes, just like Java's try-with-resources (L10). The difference: use is an ordinary extension function, so it also returns a value.

JOIN and GROUP BY

~35 min

A loans row says "member 3 borrowed book 7". To print "Grace Hopper borrowed Stories of Your Life", you join tables on their keys. Conceptually, a join starts from every combination of rows (the cross product) and keeps the combinations that satisfy the ON condition. The database doesn't really build all the pairs; L35 shows how indexes avoid that.

  • CROSS JOIN: 8 authors × 20 books = 160 pairs, nearly all meaningless.
  • JOIN (inner join): only pairs where a.id = b.author_id, one per book: 20 rows. Becky Chambers has no books, so she isn't in any of them.
  • LEFT JOIN: every row of the left table, matched or not. Unmatched rows get NULLs for the right-hand columns: 21 rows. WHERE b.id IS NULL then finds exactly the unmatched ones.

The missing-rows puzzle

"How many books has each author published since 2000?" Here are two queries that look almost the same:

$ /usr/bin/sqlite3 -echo -header -column -nullvalue NULL library.db < puzzle.sql
SELECT a.name, count(b.id) AS recent_books
FROM authors a LEFT JOIN books b ON b.author_id = a.id
WHERE b.year > 2000
GROUP BY a.id ORDER BY a.id;
name             recent_books
---------------  ------------
Ted Chiang       2
N. K. Jemisin    3
Terry Pratchett  1
Liu Cixin        3
SELECT a.name, count(b.id) AS recent_books
FROM authors a LEFT JOIN books b ON b.author_id = a.id AND b.year > 2000
GROUP BY a.id ORDER BY a.id;
name               recent_books
-----------------  ------------
Ursula K. Le Guin  0
Octavia E. Butler  0
Ted Chiang         2
N. K. Jemisin      3
Terry Pratchett    1
Liu Cixin          3
Anonymous          0
Becky Chambers     0

The first query dropped four authors, even though it says LEFT JOIN. WHERE runs after the join (the widget's last step). For Le Guin, every joined row has b.year < 2000; for Becky Chambers, the only row has b.year NULL. Either way the test isn't true, so WHERE removes the rows, and the LEFT JOIN has become an inner join. Move the condition into ON, and it decides which books match while every author still survives, with a count of 0. This is one of the most common bugs in hand-written and AI-written SQL alike. Conditions on the right-hand table of a LEFT JOIN belong in ON.

Aggregates

An aggregate function turns many rows into one value. The details matter: "The count(X) function returns a count of the number of times that X is not NULL in a group. The count(*) function (with no arguments) returns the total number of rows in the group" (Built-in Aggregate Functions).

$ /usr/bin/sqlite3 -echo -header -column -nullvalue NULL library.db < aggregates.sql
SELECT count(*), count(year), count(DISTINCT author_id) FROM books;
count(*)  count(year)  count(DISTINCT author_id)
--------  -----------  -------------------------
20        19           7
SELECT sum(price_cents), avg(price_cents), min(year), max(year) FROM books;
sum(price_cents)  avg(price_cents)  min(year)  max(year)
----------------  ----------------  ---------  ---------
27480             1374.0            1400       2019
SELECT 7 / 2 AS int_div, 7 / 2.0 AS real_div;
int_div  real_div
-------  --------
3        3.5

count(year) is 19 because Beowulf's year is NULL, and min/max skip NULLs too. SQLite's avg "is always a floating point value … even if all inputs are integers" (same page), but plain / between two integers is integer division: 7 / 2 is 3, exactly as in Kotlin and Java.

GROUP BY and HAVING

GROUP BY splits rows into groups with equal values, and aggregates then work per group. HAVING filters groups, the way WHERE filters rows. Loans per author, keeping only authors with at least four:

$ /usr/bin/sqlite3 -echo -header -column -nullvalue NULL library.db < groupby.sql
SELECT a.name, count(*) AS loans
FROM loans l JOIN books b ON b.id = l.book_id JOIN authors a ON a.id = b.author_id
GROUP BY a.id
HAVING count(*) >= 4
ORDER BY loans DESC;
name               loans
-----------------  -----
Terry Pratchett    12
Ted Chiang         5
Octavia E. Butler  4
SELECT a.name, count(*) AS loans_2026
FROM loans l JOIN books b ON b.id = l.book_id JOIN authors a ON a.id = b.author_id
WHERE l.loaned >= '2026-01-01'
GROUP BY a.id
ORDER BY loans_2026 DESC, a.name;
name               loans_2026
-----------------  ----------
Terry Pratchett    5
Liu Cixin          2
Octavia E. Butler  2
N. K. Jemisin      1
Ursula K. Le Guin  1

The first query's HAVING test uses count(*), which only exists after grouping. The second query's WHERE runs before grouping, so only 2026 loans are counted at all. Rule of thumb: test individual rows in WHERE (cheaper, and it happens first), and test aggregates in HAVING.

One SQLite quirk to know about, because AI tools trained on SQLite and MySQL code reproduce it. Standard SQL rejects a selected column that's neither grouped nor aggregated. PostgreSQL's SELECT docs say it "is not valid for the SELECT list expressions to refer to ungrouped columns except within aggregate functions" (SELECT). SQLite allows these "bare" columns:

$ /usr/bin/sqlite3 -echo -header -column -nullvalue NULL library.db < bare.sql
SELECT author_id, title, max(price_cents) FROM books GROUP BY author_id HAVING author_id <= 3;
author_id  title                 max(price_cents)
---------  --------------------  ----------------
1          The Dispossessed      1599
2          Parable of the Sower  1499
3          Exhalation            1899
SELECT author_id, title, count(*) FROM books GROUP BY author_id HAVING author_id <= 3;
author_id  title                            count(*)
---------  -------------------------------  --------
1          A Wizard of Earthsea             3
2          Kindred                          3
3          Stories of Your Life and Others  2

With max(), SQLite documents a special case: "all bare columns in the result set take values from an input row which also contains the minimum or maximum" (SELECT, §2.5), so title really is each author's most expensive book. With count(), the title is just one row from the group: "in many cases the value for "b" is undefined". "A Wizard of Earthsea" next to a count of 3 means nothing. Don't rely on bare columns; the query won't even run on PostgreSQL.

Subqueries and CTEs

A query can contain another query: a scalar subquery that returns one value, IN (subquery), or EXISTS (subquery). A common table expression (WITH name AS (…)) names a subquery so the main query reads top to bottom, like extracting a local variable:

The Obelisk Gate  1599
The Stone Sky     1699

Edsger Dijkstra
Barbara Liskov

WHERE NOT EXISTS (SELECT 1 FROM loans l WHERE l.member_id = m.id);

  SELECT l.member_id FROM loans l JOIN books b ON b.id = l.book_id WHERE b.author_id = 5

The second query nests two subqueries ("members whose loans include a book by author 5"). The CTE version names that intermediate result pratchett_loans and also counts. As queries grow, CTEs are how you keep them readable.

Window functions

Sometimes you want an aggregate-like calculation without collapsing the rows: "each member's most recent loan". A window function computes a value per row over a set of related rows. ROW_NUMBER() OVER (PARTITION BY member ORDER BY loaned DESC) numbers each member's loans newest first, and then you keep number 1. SQLite has supported them since "release version 3.25.0 (2018-09-15)", modelled on PostgreSQL (Window Functions):

$ /usr/bin/sqlite3 -echo -header -column -nullvalue NULL library.db < window.sql
WITH ranked AS (
  SELECT m.name, b.title, l.loaned,
         ROW_NUMBER() OVER (PARTITION BY l.member_id ORDER BY l.loaned DESC) AS rn
  FROM loans l JOIN members m ON m.id = l.member_id JOIN books b ON b.id = l.book_id
)
SELECT name, title, loaned FROM ranked WHERE rn = 1 ORDER BY loaned DESC;
name               title                   loaned
-----------------  ----------------------  ----------
Margaret Hamilton  The Fifth Season        2026-09-25
Donald Knuth       Small Gods              2026-09-20
Ada Lovelace       Guards! Guards!         2026-09-01
Barbara Liskov     The Three-Body Problem  2026-08-15
Edsger Dijkstra    Kindred                 2026-07-01
Grace Hopper       A Wizard of Earthsea    2026-06-01
Alan Turing        Going Postal            2026-05-10

Ken Thompson has no loans, so he has no rows to number. You'd need a LEFT JOIN from members to include him.

The order SQL really runs in

You write a query SELECT-first, but it's evaluated in a different order. PostgreSQL's SELECT reference lists it: FROM (including joins), then WHERE, then GROUP BY and HAVING, then the SELECT list computes the output columns, then DISTINCT, ORDER BY and LIMIT. Step through it on one query in the widget's Logical order tab above. Real engines rearrange the work for speed, but the result always matches this order.

The order explains a classic error: a SELECT alias doesn't exist yet when WHERE runs. PostgreSQL says an output column's name can be used "in ORDER BY and GROUP BY clauses, but not in the WHERE or HAVING clauses; there you must write out the expression instead" (SELECT). SQLite is more lenient, and that leniency is worth seeing:

$ /usr/bin/sqlite3 -echo -header -column -nullvalue NULL library.db < alias.sql
SELECT title, price_cents / 100.0 AS price FROM books WHERE price > 17 ORDER BY price DESC;
title       price
----------  -----
Exhalation  18.99
SELECT title, price_cents / 100.0 AS price, count(*) OVER () AS n FROM books WHERE n > 1;
Parse error near line 2: misuse of aliased window function n

SQLite accepted WHERE price > 17 by quietly substituting the expression, an extension PostgreSQL would reject. But it refused the window-function alias n, because window functions are computed after WHERE, so there's nothing to substitute yet. Write the expression out in WHERE, and your SQL runs on every database.

Preview: the N+1 problem

Joins and GROUP BY let the database do in one query what code might do in many. Here's the same report built both ways, counting the queries sent:

N+1 : 9 queries -> [(Ursula K. Le Guin, 3), (Octavia E. Butler, 3), (Ted Chiang, 2), (N. K. Jemisin, 3), (Terry Pratchett, 4), (Liu Cixin, 3), (Anonymous, 2), (Becky Chambers, 0)]
JOIN: 1 query   -> [(Ursula K. Le Guin, 3), (Octavia E. Butler, 3), (Ted Chiang, 2), (N. K. Jemisin, 3), (Terry Pratchett, 4), (Liu Cixin, 3), (Anonymous, 2), (Becky Chambers, 0)]
same answer: true

Java prints the same counts as Ursula K. Le Guin=3, … and same answer: true. One query for the list, plus one per item, is the N+1 problem. With 8 authors and an in-process database, it's harmless. With 10,000 authors and a database across a network (L30's round trips), it's 10,001 round trips instead of one. A cross join pairs every row with every row: 8 × 20 = 160.

-- 7. Top 3 books per author by number of loans
WITH counts AS (
  SELECT a.name AS author, b.title, count(l.id) AS loans
  FROM books b
  JOIN authors a     ON a.id = b.author_id
  LEFT JOIN loans l  ON l.book_id = b.id
  GROUP BY b.id
), ranked AS (
  SELECT author, title, loans,
         ROW_NUMBER() OVER (PARTITION BY author ORDER BY loans DESC, title) AS rank
  FROM counts
)
SELECT author, rank, title, loans FROM ranked
WHERE rank <= 3 AND author IN ('Terry Pratchett', 'Octavia E. Butler')

  • Q1 could also be a LEFT JOIN with WHERE l.id IS NULL. NOT EXISTS states the question most directly.
  • Q2 is the LEFT JOIN + count(l.id) pattern from the exercise; count(*) would give Ken 1.
  • Q3 compares ISO date strings directly, which works because ISO dates sort as text. date(…, '-21 days') and julianday() are SQLite's date functions. Other databases spell date arithmetic differently.
  • Q4 uses ORDER BY … LIMIT 1. If two authors tied, it would silently pick one; a window function with RANK() would show both.
  • Q5: year / 10 * 10 is integer division, so 1987 becomes 1980. NULL years make a NULL decade, placed last by NULLS LAST. Grouping by the alias decade is allowed in both SQLite and PostgreSQL.
  • Q6 is called relational division. Read it as "members for whom there's no Chiang book without a matching loan".
  • Q7 counts loans per book with a LEFT JOIN (so unloaned books count 0), then numbers them per author. Going Postal and Mort both have 2 loans; the title tiebreak picks Going Postal.

Exit quiz, recall card, sources

~5 min

Two threads each read a book's price with SELECT, add 100 in Kotlin, and UPDATE it back, at the same moment. What can go wrong? (L26)

It's L26's count++ race, moved into the database: both read the old price, both write old + 100, and one increase vanishes. Transactions and isolation levels (L36) are the database's answer.

Which clause does SQL evaluate first, logically? (L15 + Part 3)

FROM (and its joins) builds the rows that everything else works on. Like a lazy Sequence (L15), you describe the steps and the engine decides how to run them, but the result must match FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT.

The year column allows NULL. What Kotlin property type should a row class use for it? (L3)

Nullable column, nullable type. With Int, Beowulf's row couldn't even be constructed, as Part 1's compile error showed.

Why use a PreparedStatement with ? even when the value comes from your own code? (L33)

A placeholder sends the value separately from the SQL, so no value can change the query's meaning. Code changes over time; today's constant is tomorrow's user input.
