Part 1

ACID and transactions

~25 min

A transaction is a group of statements the database treats as one unit. PostgreSQL's tutorial puts it well: "The essential point of a transaction is that it bundles multiple steps into a single, all-or-nothing operation. The intermediate states between the steps are not visible to other concurrent transactions, and if some failure occurs that prevents the transaction from completing, then none of the steps affect the database at all" (PostgreSQL: Transactions). The guarantees go by the acronym ACID. Kleppmann's Designing Data-Intensive Applications, chapter 7 "Transactions", is the best long treatment.

LetterMeansIn this lesson
AtomicityAll of the statements happen, or none of them do.The transfer below: either both balances change, or neither does.
ConsistencyRules you declared (CHECK, UNIQUE, foreign keys) hold before and after.The CHECK (balance_cents >= 0). DDIA ch. 7 points out that most of "consistency" is really your application's job; the database only enforces what you declare.
IsolationConcurrent transactions don't see each other's half-finished work. How strictly is configurable.All of Part 2.
DurabilityOnce COMMIT returns, the data survives a crash or power cut.The journal below, and why Part 3's batched inserts are so much faster.

Atomicity in sqlite3

Move 150.00 from Ada (100.00) to Bob. The first UPDATE succeeds and the second breaks the CHECK:

Look at the middle SELECT: inside the transaction, Bob already has 200.00. ROLLBACK undoes everything since BEGIN. Now the trap. Same start, but COMMIT instead of ROLLBACK after the error:

BEGIN;
UPDATE accounts SET balance_cents = balance_cents + 15000 WHERE id = 2;
UPDATE accounts SET balance_cents = balance_cents - 15000 WHERE id = 1;
Runtime error near line 4: CHECK constraint failed: balance_cents >= 0 (19)
COMMIT;
SELECT * FROM accounts;
┌────┬───────┬───────────────┐
│ id │ owner │ balance_cents │
├────┼───────┼───────────────┤
│ 1  │ Ada   │ 10000         │
│ 2  │ Bob   │ 20000         │
└────┴───────┴───────────────┘

150.00 appeared from nowhere. A failing statement does not roll back the whole transaction. SQLite's default conflict rule, ABORT, "backs out any changes made by the current SQL statement; but changes caused by prior SQL statements within the same transaction are preserved and the transaction remains active. This is the default behavior and the behavior specified by the SQL standard" (SQLite: ON CONFLICT). Deciding to roll back is your job, which is why every JDBC transaction below has a catch that calls rollback().

Durability: the journal

How can a database promise all-or-nothing if the power fails halfway through writing a page? "Prior to making any changes to the database file, SQLite first creates a separate rollback journal file and writes into the rollback journal the original content of the database pages that are to be altered" (SQLite: Atomic Commit). After a crash, SQLite finds the journal and puts the old pages back. PRAGMA journal_mode; on our file prints delete, the default: the journal is deleted on commit. The other common mode, WAL (write-ahead log), appends changes to a log instead and lets readers keep going while one connection writes. Every commit has to wait until the data really is on disk. Remember that cost; you'll measure it in Part 3.

Transactions from JDBC: autocommit is on

JDBC hides BEGIN. "By default, new connections are in auto-commit mode. The commit occurs when the statement completes" (Connection). So, by default, every statement is its own transaction. Here's what that means for a transfer interrupted by a crash, simulated with an exception between the two UPDATEs:

autocommit by default: true
1. crashed: power cut between the two UPDATEs
   autocommit:  Ada=10000 Bob=7500
2. crashed: power cut between the two UPDATEs
   transaction: Ada=10000 Bob=5000
3. [SQLITE_CONSTRAINT_CHECK] A CHECK constraint failed (CHECK constraint failed: balance_cents >= 0)
   transaction: Ada=10000 Bob=5000
4. committed:   Ada=7500 Bob=7500

Both languages print exactly this. Run 1 is the bug: Bob's credit was committed the moment its statement finished, and Ada's debit never ran. Runs 2 and 3 use the helper: setAutoCommit(false), run the work, commit() if it returns, rollback() if it throws, and switch autocommit back on in finally. That's the whole pattern, and the same one frameworks automate.

Savepoints: rolling back part of a transaction

A Savepoint is "a point within the current transaction that can be referenced from the Connection.rollback method. When a transaction is rolled back to a savepoint all changes made after that savepoint are undone" (Savepoint). Here, a bulk sign-up skips the one bad row instead of throwing away the whole batch:

skipped Ada again: [SQLITE_CONSTRAINT_UNIQUE] A UNIQUE constraint failed (UNIQUE constraint failed: members.email)
1 Ada
2 Alan
3 Grace
What Kotlin does for you.
  • inline fun <T> Connection.transaction(block) reads like a language feature: c.transaction { … }. Because it's inline (L14), there's no lambda object, and the block can even return from the enclosing function.
  • No checked exceptions (L10). The block may throw SQLException freely. Java's java.util.function interfaces can't throw checked exceptions, so the Java version declares its own SqlWork<T>, and the transfer has to return Void/null to fit it.
  • use { } closes statements and connections like try-with-resources, but as an ordinary extension function you can nest anywhere, including inside an expression.
  • c.autoCommit = false: JDBC's getAutoCommit/setAutoCommit pair becomes a property (L9).
Exercise: a transfer that can't lose money

From a blank file, in both languages. The transfer above has a silent bug: UPDATE … WHERE id = 99 changes zero rows without any error, so money sent to a non-existent account just vanishes. executeUpdate returns "the row count for SQL Data Manipulation Language (DML) statements" (Statement.executeUpdate). Use it.

  1. Write transfer(c, from, to, cents) returning a sealed result (L7, L10): Done, or Rejected(reason).
  2. Reject non-positive amounts before touching the database. Reject unknown accounts by checking that each UPDATE changed exactly one row. Turn the CHECK failure into Rejected("overdraft").
  3. Every rejection must leave both balances untouched.

The Kotlin version leans on require and check (L10) inside the transaction: they throw, the helper rolls back, and the outer catch turns the exception into a result. Check

A brand-new JDBC connection runs two UPDATEs. When does each one commit?

"By default, new connections are in auto-commit mode." Each statement is its own transaction, which is exactly how run 1 above lost Ada's debit.

BEGIN; Bob +15000 (works); Ada −15000 (fails the CHECK); COMMIT; Bob started at 5000. His balance now?

The failed statement is undone, but the earlier one isn't, and the transaction stays open. COMMIT keeps Bob's +15000. You must ROLLBACK yourself (SQLite: ABORT).

Why does the Java version declare its own SqlWork<T> instead of using Function<Connection, T>?

Function.apply declares no checked exceptions, and SQLException is checked (L10). Kotlin has no checked exceptions, so its helper takes a plain function type.

Inside one transaction you insert rows 1, 2 and 3, roll back to a savepoint taken before row 3, then commit. What is saved?

Rolling back to a savepoint undoes only what came after it. The transaction stays open, and commit() keeps everything before the savepoint.

Part 2

Isolation levels and anomalies

~35 min

Atomicity protects you from crashes. Isolation protects you from other users. A server handles many requests at once (L28), each with its own connection, and they all touch the same rows. This is L26's race condition again, except the shared memory is now a table. Perfect isolation would mean every transaction behaves as if it ran alone, which is slow. So databases offer isolation levels: weaker levels allow certain anomalies in exchange for speed.

The SQL standard names three anomalies. In PostgreSQL's wording (PostgreSQL: Transaction Isolation):

  • Dirty read: "A transaction reads data written by a concurrent uncommitted transaction."
  • Non-repeatable read: "A transaction re-reads data it has previously read and finds that data has been modified by another transaction (that committed since the initial read)."
  • Phantom read: "A transaction re-executes a query returning a set of rows that satisfy a search condition and finds that the set of rows satisfying the condition has changed due to another recently-committed transaction."

DDIA ch. 7 adds two that bite real applications more often:

  • Lost update: two transactions read a value, both compute a new one from what they read, and both write. The second write silently overwrites the first. It's count++ from L26, in SQL.
  • Write skew: two transactions read the same rows, then each updates a different row based on what it read. Each write is fine alone; together they break a rule. The classic example is two doctors who both check "is someone else on call?" and both go home.

The standard's table, as PostgreSQL's docs reproduce it (Table 13.1):

LevelDirty readNon-repeatablePhantom
READ UNCOMMITTEDpossiblepossiblepossible
READ COMMITTEDnot possiblepossiblepossible
REPEATABLE READnot possiblenot possiblepossible
SERIALIZABLEnot possiblenot possiblenot possible

That table says what a level must prevent. A real database may prevent more, and the details vary a lot between products. So instead of trusting the table, we'll measure one. H2's docs: it "supports read uncommitted, read committed, repeatable read, snapshot, and serializable (partially, see below) isolation levels". Read committed "is the default level", and serializable "currently doesn't ensure equivalence of concurrent and serializable execution of transactions that perform write operations" (H2: Transaction Isolation). Keep that last sentence in mind.

Every anomaly, for real

The trick for a reproducible demo: open two connections, T1 and T2, and drive them step by step from one thread. No real concurrency, so no luck involved; the interleaving is exactly the one written in the code. If a step has to wait for a lock, H2 gives up after SET LOCK_TIMEOUT 300 milliseconds instead of hanging the thread.

Kotlin and Java print the same 24 lines. What the measurement says that the textbook table doesn't:

  • READ COMMITTED, the default, allows lost updates. Two deposits of 10.00 on a balance of 100.00 left 110.00. Your code has to handle this; Part 2's next section shows how.
  • H2's REPEATABLE READ blocked the phantom, although its own docs say phantoms "are possible" at that level. H2 reads from a snapshot (MVCC), so the re-run count still saw 2. The docs describe what's allowed; this run shows what one version actually did. Don't rely on behaviour the docs don't promise.
  • The lost update is caught by an error, not prevented by waiting. At REPEATABLE READ, T2's UPDATE of a row T1 had changed since T2's snapshot fails with SQLState 40001. The message is misleading. The real one reads Deadlock detected. The current transaction was rolled back. Details: "ACCOUNTS", although there was no deadlock, only a conflicting update. T2 was rolled back, and the application must retry it.
  • Write skew happens even at SERIALIZABLE, which is exactly the caveat in H2's docs. On PostgreSQL, SERIALIZABLE would abort one of the two doctors (see below). Here, you have to prevent it yourself; the exercise shows how.

Fixing the lost update

Now the realistic version of the problem: four threads, each making 250 deposits of one cent, at the default READ COMMITTED level. The balance should end at 1000. Four ways to write "add one cent":

read, then write    balance  311 of 1000  (43 ms)
read, then write    balance  271 of 1000  (20 ms)
read, then write    balance  281 of 1000  (18 ms)
atomic UPDATE       balance 1000 of 1000  (13 ms)
SELECT FOR UPDATE   balance 1000 of 1000  (24 ms)
optimistic version  balance 1000 of 1000  (24 ms, 1871 retries)
read, then write    balance  280 of 1000  (39 ms)
read, then write    balance  294 of 1000  (17 ms)
read, then write    balance  299 of 1000  (14 ms)
atomic UPDATE       balance 1000 of 1000  (13 ms)
SELECT FOR UPDATE   balance 1000 of 1000  (26 ms)
optimistic version  balance 1000 of 1000  (24 ms, 1995 retries)

Real concurrency, so your numbers will differ from run to run. That's the point: "read, then write" lost about 70% of the deposits, and differently every time.

  • Atomic UPDATE … SET balance = balance + 1: the read and the write are one statement, and the row lock is held between them. Use this whenever the new value can be computed in SQL. It's the AtomicInteger.incrementAndGet() of databases (L26).
  • SELECT … FOR UPDATE: pessimistic locking. The read takes the row lock, so the next transaction's SELECT … FOR UPDATE waits until this one commits. Use it when the new value needs Kotlin or Java code to compute. H2 supports it; the waiting shows up as slightly more time.
  • Optimistic locking with a version column: no locks while you think. Write with WHERE id = ? AND version = ?. If the update count is 0, someone else got there first, so read again and retry. It's L26's compare-and-set loop in SQL, and it's how JPA's @Version works. It shines when conflicts are rare. Here, with four threads fighting over one row, it needed nearly 2,000 retries for 1,000 deposits.

A bug I wrote first, and what it shows. My first optimistic version read the balance and the version with two separate SELECTs. At READ COMMITTED, another transaction can commit between them. I'd pair an old balance with a new version, the version check would pass, and a deposit would vanish. That run printed optimistic version balance 727 of 1000 (25 ms, 1599 retries): wrong, despite all the retrying. Reading both columns in one statement fixed it. A version check only protects the values you read with that version.

Deadlock in the database

L27's deadlock, with rows instead of locks. Two transfers lock the two account rows in opposite orders; a barrier makes sure each holds its first row before reaching for the second:

== lock in argument order
  1->2 committed
  2->1 [40001] Deadlock detected. The current transaction was rolled back.
  took 13 ms
== lock in id order
  1->2 committed
  2->1 committed
  took 0 ms
== lock in argument order
  1->2 committed
  2->1 [40001] Deadlock detected. The current transaction was rolled back.
  took 8 ms
== lock in id order
  1->2 committed
  2->1 committed
  took 0 ms

Unlike L27's JVM deadlock, which hung until your watchdog noticed, H2 found the cycle in about 10 ms and rolled one transaction back. Which one is the victim varies; in an earlier run it was 1->2. Databases detect deadlocks because applications can't, but the victim's work is lost, so the cure is the same as in L27: lock in one global order, here by id. When a lock is merely held too long rather than deadlocked, H2 waits for the lock timeout and then fails with SQLState HYT00, "Timeout trying to lock table". With the 300 ms setting, that took 313 ms in a separate run.

SQLite: one writer at a time

SQLite takes a much simpler approach. "All transactions in SQLite show 'serializable' isolation. SQLite implements serializable transactions by actually serializing the writes. There can only be a single writer at a time to an SQLite database" (SQLite: Isolation). A second writer waits up to its busy timeout, then gets SQLITE_BUSY:

b reads while a writes: 10000
b writes after 259 ms: [SQLITE_BUSY] The database file is locked (database is locked)
after a commits, b's write works: 8000

Readers aren't blocked; they see the last committed value. Writers queue. The SQLite JDBC driver's default busy timeout is 3000 ms (its SQLiteConfig source); this demo lowers it to 200 so you don't wait. One subtlety matters in the final: SQLite's default transaction is DEFERRED, which "does not actually start until the database is first accessed". A transaction that reads first and writes later may be unable to upgrade: "If some other database connection has already modified the database … the write statement will fail with SQLITE_BUSY". IMMEDIATE instead "causes the database connection to start a new write immediately" (SQLite: BEGIN TRANSACTION). You'll see the difference in a failing test.

PostgreSQL, for comparison (from its docs; not run here)

PostgreSQL isn't installed for this course, but you'll meet it in Spring projects, so know how it differs. Its REPEATABLE READ "only sees data committed before the transaction began" and "prevents all of the phenomena described in Table 13.1 except for serialization anomalies". When a repeatable-read transaction tries to change a row someone else changed, it fails with ERROR: could not serialize access due to concurrent update, and "the application … should abort the current transaction and retry the whole transaction from the beginning". Its SERIALIZABLE uses Serializable Snapshot Isolation, which does detect write skew and aborts one transaction (PostgreSQL: Transaction Isolation). The lesson carries over: stronger isolation turns silent bugs into errors, and errors mean retries.

What Kotlin does for you.
  • Function types for strategies. Map<String, (Connection) -> Unit> holds the four deposit strategies directly. Java needs its own Deposit interface again, because a lambda passed as Consumer<Connection> can't throw SQLException.
  • Destructuring. val (b, v) = … it.getInt(1) to it.getInt(2) returns the balance and version as a Pair from one read. Java declares two variables and assigns them inside the try block.
  • Executors.newFixedThreadPool(4).use { }: since JDK 19, ExecutorService is AutoCloseable (L28), and Kotlin's use works on it as on any closeable.
  • Nothing new at runtime. Isolation is a database property. Both languages send identical SQL, which is why they print identical tables.
Exercise: stop the write skew

From a blank file, in both languages. Write skew happened at every H2 level, so isolation alone won't save the doctors. Make the conflict concrete instead: if both transactions lock the rows they read, the second checker has to wait for the first one's decision.

  1. Create doctors(name, on_call) with Alice and Bob on call. Write goOffCall(name, lock): count the doctors on call, and if there are at least 2, set yourself off call, then commit.
  2. Run Alice and Bob on two real threads. With a plain SELECT, use a latch so both check before either writes. Show that 0 doctors are left.
  3. Change the check to SELECT name FROM doctors WHERE on_call FOR UPDATE and count the rows in code. Show that exactly 1 doctor is left, on every run.
== plain SELECT
  alice saw 2 on call, went off
  bob saw 2 on call, went off
  on call now: 0
== with FOR UPDATE
  alice saw 1 on call, stayed
  bob saw 2 on call, went off
  on call now: 1
Reference solutions

Which doctor wins the race varies; in this run Bob locked the rows first, so Alice waited, then saw only 1 doctor on call and stayed. I ran both versions three times each and always got 0 without the lock and 1 with it. Why FOR UPDATE and not COUNT(*) … FOR UPDATE? You need to lock the actual rows. An aggregate returns one computed row, not the rows you're relying on. Note what this fix needs: the rows you read must exist. If the rule were "at most 3 bookings for a time slot", there might be no row to lock yet. DDIA ch. 7 calls the fix for that case "materializing conflicts".

Check

H2, READ COMMITTED: T1 reads 10000, T2 updates the row to 9000 and commits, T1 reads again.

A non-repeatable read. At READ COMMITTED, each statement sees whatever is committed when it runs. At REPEATABLE READ, the second read gave 10000.

H2, REPEATABLE READ: T1 and T2 both read 10000, T1 writes 11000 and commits, then T2 writes 11000. What happens to T2?

SQLState 40001 ("Deadlock detected…"), and T2 is rolled back. The lost update is caught, not prevented, so the application must retry T2. At READ COMMITTED, the same steps silently ended at 11000.

H2, SERIALIZABLE: both doctors count 2 on call, each takes only themselves off call, both commit. How many on call?

Write skew got through even at SERIALIZABLE, as H2's docs warn ("doesn't ensure equivalence … for transactions that perform write operations"). Locking the rows you read with FOR UPDATE fixed it.

UPDATE accounts SET balance_cents = ?, version = version + 1 WHERE id = 1 AND version = 7 returns 0. What does that mean?

The row's version is no longer 7, so someone committed a change after you read it. Optimistic locking says: read again, recompute, retry. (A deleted row would also give 0, which a real app should check for.)

SQLite: connection A holds the write lock in an open transaction. Connection B, with busy_timeout = 200, runs an UPDATE.

After waiting about 200 ms, B gets [SQLITE_BUSY] The database file is locked. SQLite allows one writer at a time. Readers still see the last committed value.

Part 3

JDBC by hand

~25 min

JDBC (Java Database Connectivity, package java.sql) is the standard API every JVM database library is built on. Spring's JdbcTemplate, Hibernate and Android's Room (which uses Android's own SQLite API rather than JDBC, but the same ideas) all end up sending SQL like yours. There are four types to know:

  • The cursor. "Initially the cursor is positioned before the first row. The next method moves the cursor to the next row, and because it returns false when there are no more rows … it can be used in a while loop" (ResultSet). Columns are numbered from 1, not 0.
  • NULL hides as 0. getInt returns "the column value; if the value is SQL NULL, the value returned is 0". Beowulf's unknown year would quietly become the year 0. wasNull() "reports whether the last column read had a value of SQL NULL", and the intOrNull helper turns that into a proper Int? / Integer. Going the other way, setNull(index, Types.VARCHAR) writes a NULL.
  • Generated keys. Pass Statement.RETURN_GENERATED_KEYS, then getGeneratedKeys() "retrieves any auto-generated keys created as a result of executing this Statement object". That's how you learn the new member got id 9.
  • Update counts. executeUpdate returned 1 for the INSERT and 1 for the UPDATE, the number of rows changed. Exercise 1 used this to catch the missing account.
  • The rollback at the end leaves library.db exactly as L34 left it: 8 members, not 9.

A lazy trap (Kotlin). The tour reads three titles through a Sequence (L15) while the ResultSet is open. Return that sequence from inside use { } and iterate it later, and the rows are gone:

[]
Failure(org.h2.jdbc.JdbcSQLNonTransientException: The object is already closed [90007-252])

Same code, two drivers, two behaviours. The JDBC spec says next() throws SQLException "if a database access error occurs or this method is called on a closed result set". H2 obeys it. The SQLite driver just returns false, so your query silently returns nothing. That's the worst kind of bug: no error, wrong answer. The rule: finish reading (toList()) before the use block ends. Java's ResultSet has no built-in lazy wrapper, so you'd only hit this there if you built your own Iterator or Stream over one.

Batching and transactions: the cost of a commit

Insert 10,000 loans into a fresh file database, four ways. addBatch() queues a row; executeBatch() sends the whole queue:

one by one, autocommit           2399 ms  (10000 rows)
addBatch, autocommit             1669 ms  (10000 rows)
one by one, one transaction        18 ms  (10000 rows)
addBatch, one transaction           4 ms  (10000 rows)
one by one, autocommit           1761 ms  (10000 rows)
addBatch, autocommit             1687 ms  (10000 rows)
one by one, one transaction        16 ms  (10000 rows)
addBatch, one transaction           4 ms  (10000 rows)

One transaction made it about 100 times faster. Batching on its own barely helped. With autocommit on, each row is still its own transaction, and each commit has to wait for the disk (Part 1's durability, L22's latency ladder). Group work into transactions; batch on top of that for the last bit. In memory you wouldn't see the gap, which is why this runs on a temp file.

SQL injection, once more: the column-name hole

L33's rule was "bind every value". But a sort column isn't a value, and you can't bind it:

1. bound   ORDER BY ?  ('year'):  Guards! Guards! | Small Gods | Going Postal | Mort
2. glued   ORDER BY year:         Mort | Guards! Guards! | Small Gods | Going Postal
3. glued   ORDER BY <guess 'a'>: Going Postal | Guards! Guards! | Mort | Small Gods
3. glued   ORDER BY <guess 'b'>: Mort | Guards! Guards! | Small Gods | Going Postal
4. allowlist 'year': Going Postal | Small Gods | Guards! Guards! | Mort
4. allowlist 'price': Going Postal | Guards! Guards! | Small Gods | Mort
4. allowlist rejected: can't sort by 'email'
4. allowlist rejected: can't sort by '(SELECT email FROM members WHERE id = 1)'
  1. Binding doesn't sort. ORDER BY ? with 'year' sorts by the string 'year', the same constant for every row. No error; the rows simply come back in storage order.
  2. Gluing works for honest input.
  3. Gluing leaks data. The attacker can't see the members table, but a CASE expression turns a yes/no question into a sort order. Guess "a": sorted by title, so Ada's email starts with "a". Guess "b": sorted by year, so no. Twenty-odd requests per character spell out the whole email. This is "blind" SQL injection.
  4. The fix is an allowlist. OWASP: for "parts of SQL queries that can't use bind variables, such as table names, column names, or sort order indicators (ASC or DESC), input validation or query redesign is the most appropriate defense", and developers "should map the parameter values to the legal/expected table or column names" (OWASP SQL Injection Prevention). The user picks a key; only your code's strings reach the SQL.

The N+1 query problem

List all 20 books with their authors. The innocent-looking version loads the books, then asks for each author separately:

N+1  20 rows, 21 queries,  9.58 ms   first: Row(title=A Wizard of Earthsea, author=Ursula K. Le Guin)
JOIN 20 rows,  1 queries,  0.36 ms   first: Row(title=A Wizard of Earthsea, author=Ursula K. Le Guin)
N+1  20 rows, 21 queries,  4.41 ms   first: Row[title=A Wizard of Earthsea, author=Ursula K. Le Guin]
JOIN 20 rows,  1 queries,  0.22 ms   first: Row[title=A Wizard of Earthsea, author=Ursula K. Le Guin]

Same answer, 21 queries instead of 1. The timings flatter the JOIN, because N+1 ran first and paid for the JIT warming up (L23), so trust the query count. Here SQLite is a file on the same machine. With a database server across a network, each query is a round trip of maybe a millisecond (L30), and N+1 over 1,000 rows means a second of pure waiting. This is the classic ORM trap: with JPA or Room, book.author looks like a field access but can quietly run a query each time. When a page is slow, count its queries first.

Connections are expensive: pools

round 1: 500 queries, new connection each 293.0 ms, one reused connection 2.9 ms
round 2: 500 queries, new connection each 28.3 ms, one reused connection 2.4 ms
round 1: 500 queries, new connection each 264.2 ms, one reused connection 2.7 ms

Even warmed up (round 2), opening a fresh connection per query cost about ten times more, and that's for a local file. A networked database adds a TCP handshake (L30), TLS (L31) and authentication on top. So servers keep a connection pool: a fixed set of open connections that requests borrow and return, much like L28's thread pools. You won't write one; in the JVM world that's HikariCP's job, and Spring Boot uses it by default. When a pool is involved, "closing" a connection returns it to the pool, so still always close.

Bridge: Spring's @Transactional is the transaction { } helper from Part 1, applied by a proxy around your method. JdbcTemplate is the query/toList helpers. Spring Data JPA writes the SQL from method names, and N+1 is its best-known pitfall. Android's Room generates DAOs over SQLite and refuses database calls on the main thread (L29). After this lesson, none of these are magic: they're the code you just wrote.

What Kotlin does for you.
  • Extension functions tidy JDBC. fun <T> ResultSet.toList(map: (ResultSet) -> T) and ResultSet.intOrNull(column) read like methods JDBC should have had. Java needs static helpers and its own RowMapper interface, again because of SQLException.
  • Int? models SQL NULL. A nullable type makes "this column can be NULL" part of the row type. Java records need a boxed Integer, and nothing stops you reading it as int.
  • buildList { while (rs.next()) add(…) } is one expression. Java declares a list, loops and returns.
  • vararg args: Any + setObject gives a tiny query helper that takes any parameters, which Java matches with Object... args.
  • The flip side: generateSequence makes lazy reading so easy that the closed-ResultSet trap is easier to fall into in Kotlin.

The library's data layer

~30 min (more if you test-drive it)

Design a schema and a repository for lending books, from a blank Gradle project, Kotlin first and then Java. This is the data layer the capstone (L45–L47) will put behind an HTTP API.

The schema (SQLite, a file in a temp directory):

  • books(id, title, year), with a CHECK on year. members(id, name, email UNIQUE). loans(id, book_id → books, member_id → members, loaned, returned), with dates as ISO text.
  • The database itself must refuse a double loan. A partial unique index allows at most one open loan per book: CREATE UNIQUE INDEX … ON loans(book_id) WHERE returned IS NULL. Code can have bugs; the index can't be bypassed.
  • Run PRAGMA foreign_keys = ON on every connection. It's off by default in SQLite (L34).

The LibraryRepository:

  • addMember(name, email) and addBook(title, year) return the generated id.
  • lend(bookId, memberId, today) returns a sealed LendResult (L7, L10): Lent(loanId), AlreadyOnLoan, NoSuchBook or NoSuchMember. The checks and the insert run in one transaction.
  • returnBook(bookId, today) returns whether an open loan was closed (check the update count).
  • overdueLoans(today): open loans older than 14 days, oldest first.
  • topBorrowers(limit): a JOIN + GROUP BY from L34, ordered by count descending, then name.

Test-first, in this order (L11), each test on a fresh database file:

  1. Lending an already-lent book returns AlreadyOnLoan and leaves exactly one loan row: no partial writes.
  2. An unknown book or member is reported as a result, not thrown.
  3. Returning a book makes it available again, and returning it twice reports false.
  4. Overdue means open and older than 14 days; a returned book never counts.
  5. Top borrowers break ties by name.
  6. A member named Robert'); DROP TABLE members; -- is stored as plain text, and the table survives (L33).
  7. The database refuses a second open loan even when you bypass the repository with raw SQL.
  8. Eight threads lend the same book at once (L26's latch start gate): exactly one Lent, seven AlreadyOnLoan.

Wrap-up

Exit quiz, recall card, sources

~5 min

Why does "read the balance, then write balance + 1" lose deposits under concurrency? (L26)

The same interleaving as count++ in L26: two transactions read the same old value, each adds one, and the second write overwrites the first. An atomic UPDATE … = balance + 1 removes the gap.

lend returns AlreadyOnLoan instead of throwing when the book is out. Why? (L10)

L10's rule: exceptions for bugs and broken environments, return values for outcomes the caller should handle. "Someone else has it" is an everyday answer, and a sealed type makes the caller handle every case.

A request handler opens a Connection and never closes it. After thousands of requests? (L24)

Each open connection holds memory and a file handle (L22), and the code keeps it reachable. Like L24's listener leak, the GC can't help. Close with use/try-with-resources, or return it to the pool.

Kotlin: a function returns generateSequence { if (rs.next()) … } from inside use { }, and the caller does .toList(). On SQLite? (L15)

The sequence is lazy (L15), so it runs after use has closed the ResultSet. The SQLite driver's next() then returns false: [], silently. H2 throws "The object is already closed", as the JDBC spec requires.
