Part 1

JUnit in both languages

~25 min

So far, every exercise ended with an "expected output" box that you compared with your output by eye. That works once. It doesn't work after you change the code next week, or for fifty functions at once. A unit test is a small piece of code that calls one unit (usually a function or a class) with a known input and asserts what must come back. The computer does the comparing, every time, in milliseconds.

On the JVM, the standard tool is JUnit, now at version 6 (JUnit User Guide). Kotlin adds a thin layer, kotlin.test, whose @Test on JUnit 5+ is JUnit's org.junit.jupiter.api.Test and whose assertions call JUnit's (kotlin.test docs). Both languages end up running on the same JUnit engine.

The setup Gradle already gave you

The projects gradle init generated in L1 already had testing wired in. Here is the relevant part of each generated app/build.gradle.kts (Gradle 9.7.1), plus two lines added for this lesson:

  • Versions: both projects' gradle/libs.versions.toml pin JUnit 6.0.1. The generated comment still says "JUnit 5". JUnit 6 kept the same org.junit.jupiter programming model, so the comment is just stale.
  • useJUnitPlatform() tells Gradle to run tests through JUnit (Gradle docs: Testing in Java & JVM projects). It also makes the Kotlin plugin pick the JUnit 5+ flavour of kotlin-test. Without it, the plugin defaults to JUnit 4 (Kotlin docs: test library dependencies).
  • testLogging is my addition. By default a passing run prints nothing per test, just BUILD SUCCESSFUL. events(…) prints one line per test, and exceptionFormat = FULL shows the full "expected … but was …" message in the console (Gradle docs: test logging; TestLogging API).
  • Tests live in a separate source tree, app/src/test/kotlin/… or app/src/test/java/…, next to src/main. They're compiled and run by Gradle but never shipped with your app.

Anatomy of a test

Here's L3's formatPrice moved into src/main, and its first tests in src/test:

  • @Test "denotes that a method is a test method" (JUnit: Annotations). JUnit finds and runs every one. Test classes and methods "are not required to be public, but they must not be private" (JUnit: Test classes and methods).
  • Arrange, act, assert. Set up the input, call the code under test, and check the result. The first test labels the three steps. Short tests often fold them into one line.
  • assertEquals(expected, actual): the expected value comes first. Swap them and the failure message will lie to you ("expected: <wrong thing>").
  • Names describe behaviour. In tests (and only in tests), Kotlin lets you write method names with spaces in backticks. The Kotlin conventions note that Android supports these only from API level 30 (Kotlin coding conventions). Java uses camelCase, or @DisplayName("…") for a human-readable label.

A fresh object for every test

For tests that need setup, use a lifecycle method. @BeforeEach runs "before each" test method (JUnit: Annotations). Kotlin's @BeforeTest is literally a type alias for it on JUnit 5+ (kotlin.test: BeforeTest). JUnit goes further still: it "creates a new instance of each test class before executing each test method", precisely "to avoid unexpected side effects due to mutable test instance state" (JUnit: Test instance lifecycle). That's L4's aliasing lesson, applied to tests.

WalletTest > withdrawing too much is rejected() PASSED
WalletTest > zero deposit is rejected() PASSED
WalletTest > deposit increases the balance() PASSED
WalletTest > a new wallet is empty() PASSED

a new wallet is empty passes even though another test deposited 500, because each test got its own Wallet. Part 2 explains the assertFailsWith / assertThrows lines.

What Kotlin does for you. kotlin.test gives you assertEquals and friends as plain top-level functions, so Java's import static org.junit.jupiter.api.Assertions.* isn't needed. Test names can be full sentences in backticks. assertFailsWith<IllegalArgumentException> { … } takes the exception type as a type parameter and the code as a trailing lambda, so you get no .class and no () ->. Under the hood it's all the same JUnit engine, and the Kotlin plugin picks the matching kotlin-test variant when it sees useJUnitPlatform().

Two habits from the Wallet tests are worth keeping:

  • Capture the exception and check its message. A test that only checks the exception type would pass even if the code threw for the wrong reason.
  • Check that nothing changed after a rejected operation. In the Wallet tests, that's balance still being 100.

Parameterised tests: one test, many inputs

Copy-pasting the same test with different numbers gets old fast. A @ParameterizedTest runs one method once per row of data. @ValueSource supplies single values, and @CsvSource supplies comma-separated rows (JUnit: Parameterized tests).

A dependency gotcha. The generated Java project depends on the junit-jupiter aggregator, which "transitively pulls in" junit-jupiter-api, junit-jupiter-params and junit-jupiter-engine (JUnit: Dependency metadata). The generated Kotlin project only depends on junit-jupiter-engine, and JUnit says plainly that "to use parameterized classes or tests you need to add a dependency on the junit-jupiter-params artifact". That's why the Kotlin build file above has one extra line. Without it:

What makes a good test

PropertyMeansBreaks when…
Fastmilliseconds, so you run them constantlyit hits the network, a real database or sleep
Independentpasses alone or in any orderit relies on state left by another test
Repeatablesame result every run, on every machineit depends on the clock, randomness or a HashMap's order (L3)
One reason to faila failure points at one behaviourone test checks ten unrelated things
Covers the edges0, empty, negative, max, boundariesit only tests the "happy path"

Most of your tests should be fast unit tests like these, with only a few slow, broad end-to-end tests. Fowler calls this the test pyramid: "many more low-level UnitTests than high level BroadStackTests". You'll meet integration tests in L45.

What Kotlin does for you. The tolerance is a named argument, absoluteTolerance = 0.0001, so you can't mix it up with the expected value. Java's third positional double is easy to misread. Annotation arrays are written [1996, 2000] instead of {1996, 2000}. And assertFailsWith returns the exception already typed, so e.message just works.

Part 3

The TDD loop: red, green, refactor

~25 min

So far you wrote code, then tests. Test-driven development (TDD) flips the order. Martin Fowler's summary (bliki: TestDrivenDevelopment), which follows Kent Beck's Test-Driven Development: By Example:

  1. First, "write out a list of test cases".
  2. Red: "Write a test for the next bit of functionality you want to add." Run it and watch it fail.
  3. Green: "Write the functional code until the test passes." The simplest code is fine.
  4. Refactor: "Refactor both new and old code to make it well structured." The tests keep you safe.

Fowler calls these three steps, "often summarized as Red - Green - Refactor, … the heart of the process." It's the L2 blank-file routine (examples → plan → code → check), with the examples turned into code that checks itself.

Why bother, especially if you code with AI?

  • Tests are the spec. A failing test is a precise, executable statement of "correct". Whoever writes the implementation, you or an AI, either passes it or doesn't. Without tests, "it looks right" is the only check you have.
  • Small steps keep you un-stuck. Each step was a few lines, and you always knew what to do next: make the red test green.
  • Refactoring stops being scary. Step 4 replaced the entire algorithm, and seven tests confirmed it in a second.

A preview of fakes. Real code talks to databases, clocks and networks, which are slow and unrepeatable in a unit test. The usual answer is a test double, "a generic term for any case where you replace a production object for testing purposes". The most useful kind is a fake, which "actually [has a] working implementation, but usually take[s] some shortcut", like an in-memory list instead of a database (Fowler: TestDouble). You need L8's interfaces to swap one in, and L38 builds this properly with dependency injection.

What Kotlin does for you. The Kotlin NUMERALS table is a single list of pairs (1000 to "M") that you destructure in the loop with for ((value, symbol) in NUMERALS). Java keeps two parallel arrays in step by index, which is easy to misalign. require(number in 1..3999) states the valid range in one readable line, where Java needs an explicit if and throw.
Exercise: TDD FizzBuzz, strictly

Rules: fizzBuzz(n) returns "Fizz" for multiples of 3, "Buzz" for multiples of 5, "FizzBuzz" for both, and otherwise the number as a string. Commit after every green (git commit -m "green: 15 is FizzBuzz"). Your Git log will tell the story.

Where it usually ends up

Kotlin: fun fizzBuzz(n: Int) = when { n % 15 == 0 -> "FizzBuzz"; n % 3 == 0 -> "Fizz"; n % 5 == 0 -> "Buzz"; else -> n.toString() }. Java uses the same chain with if/return. If your tests for 3 and 5 went green before 15 existed, your 15 test should have gone red first. If it didn't, check whether your earlier code accidentally already handled it.

How do tests help when an AI writes the implementation?

Tests turn "looks plausible" into "passes the spec you wrote". You still read the code (L40), but now you have a precise check.

Final exercise

Test-drive a password validator

~25 min

From an empty test file and an empty main file, in both languages. Every rule gets its test first. Watch it go red, then make it green.

Rules: a password needs at least 8 characters, at least one digit, at least one uppercase letter, and no spaces. The validator returns a result, not a boolean: either Ok, or Rejected with the list of every broken rule, in the order listed. That's L10's sealed-result idea, so the caller can tell the user exactly what to fix.

Suggested shape: an enum Rule { TOO_SHORT, NO_DIGIT, NO_UPPERCASE, HAS_SPACE }, and a sealed PasswordResult with Ok and Rejected(failures: List<Rule>) as a data object/class in Kotlin and records in Java.

Write these tests in this order, one red-green cycle each:

  1. "Abcdef1" (7 chars) → Rejected([TOO_SHORT]). Start with a stub that always returns Ok, so you see a real red.
  2. "Abcdefg1" (8 chars) → Ok. This is the boundary.
  3. "Abcdefgh" → Rejected([NO_DIGIT])
  4. "abcdefg1" → Rejected([NO_UPPERCASE])
  5. "Abc defg1" → Rejected([HAS_SPACE])
  6. "abc" → Rejected([TOO_SHORT, NO_DIGIT, NO_UPPERCASE]): every failure, in rule order
  7. "" → the same three failures. This is the edge case.

Wrap-up

Exit quiz, recall card, sources

~5 min

Why does assertEquals work on two separately built data class or record values?

assertEquals just calls equals, and data classes and records generate a content-based one (L7). JUnit itself never looks at fields.

Which input is most likely to expose an overflow bug?

Extremes break fixed-width arithmetic (L2). That's exactly how the average bug surfaced.

In what order do the tests in a class run?

The output above shows tests running in neither written nor alphabetical order. Independent tests don't care.
