A failed require(x > 0) throws…

require checks arguments and throws IllegalArgumentException. check checks state and throws IllegalStateException (L10).

  1. check throws that, because it tests the object's state, not an argument.
  2. require validates arguments, so a false condition becomes an IllegalArgumentException.
  3. Dereferencing null or !! on null throws that. require only reports a false condition.
  4. That's for maths errors such as integer division by zero (L2).

Which exceptions does Kotlin force you to catch?

Kotlin has no checked exceptions (L10). That's one reason tests matter: the compiler won't remind you that a failure path exists.

  1. That's Java's rule. Kotlin dropped checked exceptions entirely, so nothing forces a catch.
  2. IOException is checked in Java, but in Kotlin catching it is optional, like any exception.
  3. Kotlin has no checked exceptions, so the compiler never forces a try/catch.
  4. Not even Java forces you to catch runtime exceptions: they're unchecked in both languages.

Why did L3 tell you to prefer functions that return values over functions that print?

A test can only check something it can get its hands on. Today is where that habit pays off.

  1. Speed wasn't the reason. Printed text simply can't be checked by other code.
  2. println works fine inside any function. Returning is a design choice, not a rule.
  3. Memory doesn't come into it. The point is that a caller, such as a test, can use the value.
  4. A test can assert on a returned value. Printed text goes to the console, out of its reach.
Part 1

JUnit in both languages

~33 min

So far, every exercise ended with an "expected output" box that you compared with your output by eye. That works once. It doesn't work after you change the code next week, or for fifty functions at once. A unit test is a small piece of code that calls one unit (usually a function or a class) with a known input and asserts what must come back. The computer does the comparing, every time, in milliseconds.

On the JVM, the standard tool is JUnit, now at version 6 (JUnit User Guide). Kotlin adds a thin layer, kotlin.test, whose @Test on JUnit 5+ is JUnit's org.junit.jupiter.api.Test and whose assertions call JUnit's (kotlin.test docs). Both languages end up running on the same JUnit engine.

The setup Gradle already gave you

The projects gradle init generated in L1 already had testing wired in. Here is the relevant part of each generated app/build.gradle.kts, plus two lines added for this lesson. We generated and ran everything with Gradle 9.7.1; the current release is 9.9.2 (Gradle release notes), and nothing in this lesson depends on the difference:

  • Versions: both projects' gradle/libs.versions.toml pin JUnit 6.0.1, because that's what every run in this lesson used. For your own projects, use the newest 6.x: JUnit 6.1 or newer, which adds the time-zone and locale annotations you'll meet in Part 2 (JUnit release notes). The generated comment still says "JUnit 5". JUnit 6 kept the same org.junit.jupiter programming model, so the comment is just stale.
  • useJUnitPlatform() tells Gradle to run tests through JUnit (Gradle docs: Testing in Java & JVM projects). It also makes the Kotlin plugin pick the JUnit 5+ flavour of kotlin-test. Without it, the plugin defaults to JUnit 4 (Kotlin docs: test library dependencies).
  • testLogging is my addition. By default a passing run prints nothing per test, just BUILD SUCCESSFUL. events(…) prints one line per test, and exceptionFormat = FULL shows the full "expected … but was …" message in the console (Gradle docs: test logging; TestLogging API).
  • Tests live in a separate source tree, app/src/test/kotlin/… or app/src/test/java/…, next to src/main. They're compiled and run by Gradle but never shipped with your app.

Anatomy of a test

Here's L3's formatPrice moved into src/main, and its first tests in src/test:

  • @Test "denotes that a method is a test method" (JUnit: Annotations). JUnit finds and runs every one. Test classes and methods "are not required to be public, but they must not be private" (JUnit: Test classes and methods).
  • Arrange, act, assert. Set up the input, call the code under test, and check the result. The first test labels the three steps. Short tests often fold them into one line.
  • assertEquals(expected, actual): the expected value comes first. Swap them and the failure message will lie to you ("expected: <wrong thing>").
  • Names describe behaviour. In tests (and only in tests), Kotlin lets you write method names with spaces in backticks. The Kotlin conventions note that Android supports these only from API level 30 (Kotlin coding conventions). Java uses camelCase, or @DisplayName("…") for a human-readable label.

A fresh object for every test

For tests that need setup, use a lifecycle method. @BeforeEach runs "before each" test method (JUnit: Annotations). Kotlin's @BeforeTest is literally a type alias for it on JUnit 5+ (kotlin.test: BeforeTest). JUnit goes further still: it "creates a new instance of each test class before executing each test method", precisely "to avoid unexpected side effects due to mutable test instance state" (JUnit: Test instance lifecycle). That's L4's aliasing lesson, applied to tests.

What Kotlin does for you. kotlin.test gives you assertEquals and friends as plain top-level functions, so Java's import static org.junit.jupiter.api.Assertions.* isn't needed. Test names can be full sentences in backticks. assertFailsWith<IllegalArgumentException> { … } takes the exception type as a type parameter and the code as a trailing lambda, so you get no .class and no () ->. Under the hood it's all the same JUnit engine, and the Kotlin plugin picks the matching kotlin-test variant when it sees useJUnitPlatform().

Practice · Build a tiny JUnit

A test framework is less magic than it looks. Write its two halves:

  • expectEqual(expected, actual) returns quietly when the two are equal (by ==). Otherwise it throws an AssertionError whose message is exactly expected: <X> but was: <Y>.
  • runAll(tests) runs every test body in order and returns one line per test: "PASS name", or "FAIL name: MESSAGE". One failing test must not stop the rest.

The hidden checks are JUnit 4, so they import org.junit.Test. Your Gradle projects use JUnit 5+, where it's org.junit.jupiter.api.Test (or kotlin.test.Test). The idea is the same.

import org.junit.Assert.assertEquals
import org.junit.Assert.fail
import org.junit.Test

class TinyJUnitTest {
    private fun messageOf(block: () -> Unit): String? {
        try {
            block()
        } catch (e: AssertionError) {
            return e.message
        }
        fail("expected an AssertionError, but nothing was thrown")
        return null
    }

    @Test fun `equal values pass quietly`() {
        expectEqual(4, 2 + 2)
        expectEqual("$12.05", "$" + "12.05")
        expectEqual(listOf(1, 2), listOf(1, 2))   // == means equals, so contents count
        expectEqual(null, null)
    }

    @Test fun `a mismatch throws an AssertionError with expected first`() {
        assertEquals("expected: <\$12.05> but was: <\$12.5>", messageOf { expectEqual("$12.05", "$12.5") })
    }

    @Test fun `a passing test is reported as PASS`() {
        assertEquals(listOf("PASS adds"), runAll(mapOf("adds" to { expectEqual(4, 2 + 2) })))
    }

    @Test fun `a failing test is reported with its message`() {
        val report = runAll(mapOf("pads cents" to { expectEqual("$12.05", "$12.5") }))
        assertEquals(listOf("FAIL pads cents: expected: <\$12.05> but was: <\$12.5>"), report)
    }

    @Test fun `one failure does not stop the tests after it`() {
        val report = runAll(mapOf(
            "first" to { expectEqual(1, 1) },
            "second" to { expectEqual(1, 2) },
            "third" to { expectEqual("a", "a") },
        ))
        assertEquals(listOf("PASS first", "FAIL second: expected: <1> but was: <2>", "PASS third"), report)
    }
}

        check("equal values pass quietly", "quiet", () -> {

            expectEqual(List.of(1, 2), List.of(1, 2));
            expectEqual(null, null);
            return "quiet";
        });
        check("a mismatch throws an AssertionError with expected first", "expected: <$12.05> but was: <$12.5>", () -> {
            try { expectEqual("$12.05", "$12.5"); } catch (AssertionError e) { return e.getMessage(); }
            return "nothing was thrown";
        });
        check("a passing test is reported as PASS", List.of("PASS adds"),
                () -> runAll(tests("adds", () -> expectEqual(4, 2 + 2))));
        check("a failing test is reported with its message", List.of("FAIL pads cents: expected: <$12.05> but was: <$12.5>"),
                () -> runAll(tests("pads cents", () -> expectEqual("$12.05", "$12.5"))));
        check("one failure does not stop the tests after it", List.of("PASS first", "FAIL second: expected: <1> but was: <2>", "PASS third"),
                () -> runAll(tests("first", () -> expectEqual(1, 1), "second", () -> expectEqual(1, 2), "third", () -> expectEqual("a", "a"))));
    }

    // Ordered maps of test name -> body, like a test class's methods.
    static Map<String, Runnable> tests(String n1, Runnable b1) {
        Map<String, Runnable> m = new LinkedHashMap<>();
        m.put(n1, b1);
        return m;
    }

    static Map<String, Runnable> tests(String n1, Runnable b1, String n2, Runnable b2, String n3, Runnable b3) {
        Map<String, Runnable> m = tests(n1, b1);
        m.put(n2, b2);
        m.put(n3, b3);
        return m;
    }

    interface Check { Object get() throws Exception; }

    static void check(String name, Object expected, Check actual) {
        try {
            Object got = actual.get();
            System.out.println(Objects.equals(expected, got) ? "PASS " + name : "FAIL " + name + ": expected <" + expected + "> but was <" + got + ">");
        } catch (Exception | AssertionError e) {
            System.out.println("FAIL " + name + ": threw " + e);
        }
    }
    // END CHECKS
}
Hint 1 of 3

expectEqual is one line: if (expected != actual) throw AssertionError("…"). Use a string template for the message, with expected first.

Hint 2 of 3

In runAll, loop with for ((name, body) in tests). Call body() inside a try. If it returns, the test passed. If it throws, it failed.

Hint 3 of 3

Catch AssertionError, not Exception. L10's family tree puts it under Error, so catch (e: Exception) lets it escape and crash the whole run. Add "PASS $name" after body() and "FAIL $name: ${e.message}" in the catch. In Java, the test bodies are Runnables, so you call run().

Final answer

Why it works. A test is just a function that either returns (pass) or throws (fail). An assertion is an if plus a throw, and a runner is a loop with a try/catch around each test. JUnit adds discovery, reports and much more, but its core is this. That's also why the order of expected and actual matters: the message is built from it.

Common mistake. catch (e: Exception). AssertionError is an Error, not an Exception, so the first failing test escapes the runner and the rest never run. (Real JUnit also catches other exceptions and reports them as failures.)

Check

In assertEquals(a, b), which argument comes first?

Expected first, actual second. The failure message is built from that order, so swapping them makes it misleading.

  1. JUnit's signature is assertEquals(expected, actual), and the failure message labels them in that order.
  2. Actual comes second. Swap them and the message puts "expected" next to the wrong value.
  3. The optional message is the last parameter, in both JUnit 5+ and kotlin.test.
  4. assertEquals takes no test name. The name comes from the test method itself.

Without a testLogging block, what does a passing ./gradlew test print about each test?

Silence means success. testLogging { events(…) } asks Gradle to print one line per test.

  1. Names appear only when testLogging { events(…) } asks for them.
  2. A passing run doesn't print counts either, just BUILD SUCCESSFUL. Counts appear when something fails.
  3. By default Gradle is silent about passing tests and reports only the build result.
  4. Stack traces appear only for failures, and nothing failed here.

On JUnit 5+, Kotlin's @BeforeTest is the same as…

actual typealias BeforeTest = BeforeEach (kotlin.test docs).

  1. @BeforeAll runs once for the whole class. @BeforeTest runs before every test.
  2. @Test marks a test method. Kotlin's alias for it is kotlin.test.Test.
  3. @AfterEach runs after each test. Its Kotlin alias is @AfterTest.
  4. kotlin.test declares BeforeTest as a type alias for JUnit's BeforeEach.

By default, JUnit creates a new instance of your test class…

A new instance per test method keeps tests isolated from each other's mutable state.

  1. That's the opt-in @TestInstance(PER_CLASS) mode, not the default.
  2. A new instance per test method gives each test fresh fields, so no test sees another's changes.
  3. Instances are created to run tests, whether they pass or fail.
  4. The instance must exist before the test, because the test method runs on it.

Java. A hand-written assertEquals, called with its arguments swapped. What does this print?

public class Swapped {
    static String formatPrice(long cents) {
        return String.format("$%d.%d", cents / 100, cents % 100);   // forgot the zero-padding
    }

    static void assertEquals(Object expected, Object actual) {
        if (!expected.equals(actual)) {
            throw new AssertionError("expected: <" + expected + "> but was: <" + actual + ">");
        }
    }

    public static void main(String[] args) {
        String result = formatPrice(1205);
        try {
            assertEquals(result, "$12.05");      // arguments in the wrong order
            System.out.println("PASS");
        } catch (AssertionError e) {
            System.out.println("FAIL " + e.getMessage());
        }
    }
}

%d doesn't pad, so 5 cents prints as 5 and the test fails. An assertion can't know which value is right: it calls its first argument "expected". Here that's the buggy result, so the message claims the code was supposed to return $12.5.

  1. %d doesn't zero-pad, so the result is $12.5 and the strings differ.
  2. That's the message with the arguments in the right order. The assertion only knows positions.
  3. The first argument is labelled "expected", and here that's the buggy result.
  4. %d prints 5 as 5, not 50. $12.5 just reads like 12.50, which is how the bug hides.

Kotlin. The same test class, run two ways. What does this print?

class CounterTest {
    var count = 0

    fun first(): String { count++; return "first=$count" }
    fun second(): String { count++; return "second=$count" }
}

fun main() {
    // JUnit's default: a new instance for every test method
    val fresh = CounterTest().first() + " " + CounterTest().second()

    // A hand-made runner that reuses one instance
    val shared = CounterTest()
    val reused = shared.first() + " " + shared.second()

    println("$fresh | $reused")
}

Each CounterTest() is a new object with its own count, starting at 0. The shared instance carries count from the first call into the second. JUnit's new-instance-per-method default exists so that tests behave like the first half.

  1. Two separate CounterTest() calls make two objects, each with its own count.
  2. Fresh objects start at 0 every time, while the shared one remembers the first call.
  3. Both calls on shared change the same object's count, so the second sees 2.
  4. count belongs to each object, not to the class: a new object starts again at 0.

Parameterised tests: one test, many inputs

Copy-pasting the same test with different numbers gets old fast. A @ParameterizedTest runs one method once per row of data. @ValueSource supplies single values, and @CsvSource supplies comma-separated rows (JUnit: Parameterized tests).

Flaky tests, and how to make them repeatable

A test that breaks the "repeatable" row above is called flaky. Google's testing team defines a flaky result as "a test that exhibits both a passing and a failing result with the same code", and found that "about 84% of the transitions we observe from pass to fail involve a flaky test" (Google Testing Blog: Flaky Tests at Google). That's the real cost: once a suite cries wolf, people rerun it until it's green and start ignoring red, including the red that's real. Here's the most common cause, the clock:

I ran the same code twice, a few seconds apart, changing only the time zone the JVM started in (TZ=UTC, where it was 02:08, then TZ=America/Los_Angeles, where it was 18:08). That's what happens when a CI server in UTC and a teammate in California run your suite:

TZ=UTC

The Java project gave the same PASSED and FAILED pair. The fix is to stop reading the real clock inside the logic. The JDK's own advice: "Best practice for applications is to pass a Clock into any method that requires the current instant and time-zone" (Clock API docs). Production code passes Clock.systemDefaultZone(). A test passes Clock.fixed(…), which never moves, so it can pin the time to the edges that matter:

import org.junit.Assert.assertEquals
import org.junit.Assert.assertTrue
import org.junit.Test

// The real grade(), and a maker for buggy copies of it ("mutants").
fun grade(score: Int, valid: IntRange = 0..100, a: Int = 90, b: Int = 80, c: Int = 70): String = when {
    score !in valid -> "invalid"
    score >= a -> "A"
    score >= b -> "B"
    score >= c -> "C"
    else -> "F"
}

// Caught: some correct row gets a different answer from the mutant.
fun caught(mutant: (Int) -> String): Boolean =
    gradeCases.any { (score, want) -> want == grade(score) && mutant(score) != want }

class GradeCasesTest {
    @Test fun `every row agrees with the spec`() {
        for ((score, want) in gradeCases) assertEquals("the row for $score", grade(score), want)
    }

    @Test fun `at most 10 rows`() {
        assertTrue("${gradeCases.size} rows: pick sharper ones", gradeCases.size <= 10)
    }

    @Test fun `catches an A that starts at 91, or at 89`() {
        assertTrue("no row catches an A that starts at 91", caught { grade(it, a = 91) })
        assertTrue("no row catches an A that starts at 89", caught { grade(it, a = 89) })
    }

    @Test fun `catches a B that starts at 81, and a C that starts at 71`() {
        assertTrue("no row catches a B that starts at 81", caught { grade(it, b = 81) })
        assertTrue("no row catches a C that starts at 71", caught { grade(it, c = 71) })
    }

    @Test fun `catches a validator that rejects 0 or 100`() {
        assertTrue("no row catches a validator that rejects 0", caught { grade(it, valid = 1..100) })
        assertTrue("no row catches a validator that rejects 100", caught { grade(it, valid = 0..99) })
    }

    @Test fun `catches a validator that accepts 101`() {
        assertTrue("no row catches a validator that accepts 101", caught { grade(it, valid = 0..101) })

import java.util.*;
import java.util.function.IntFunction;

public class Practice {
    record Case(int score, String expected) {}

    // One row per test case: a score, and the grade the spec demands.
    // The spec: 90..100 "A", 80..89 "B", 70..79 "C", 0..69 "F", anything else "invalid".
    static List<Case> gradeCases() {
        return List.of(
            new Case(95, "A"),
            new Case(50, "F")
        );
    }

    // CHECKS
    // The real grade(), and buggy copies of it ("mutants"): valid range lo..hi, and where A, B and C start.
    static String grade(int score, int lo, int hi, int a, int b, int c) {
        if (score < lo || score > hi) return "invalid";
        if (score >= a) return "A";
        if (score >= b) return "B";
        if (score >= c) return "C";
        return "F";
    }

    static String grade(int score) { return grade(score, 0, 100, 90, 80, 70); }

    // Caught: some correct row gets a different answer from the mutant.
    static boolean caught(IntFunction<String> mutant) {
        for (Case row : gradeCases()) {
            if (row.expected().equals(grade(row.score())) && !mutant.apply(row.score()).equals(row.expected())) return true;
        }
        return false;
    }

    public static void main(String[] args) {
        check("every row agrees with the spec", List.of(), () -> {
            List<String> wrong = new ArrayList<>();
            for (Case row : gradeCases()) if (!row.expected().equals(grade(row.score()))) wrong.add(row.toString());
            return wrong;
        });
        check("at most 10 rows", true, () -> gradeCases().size() <= 10);
        check("catches an A that starts at 91", true, () -> caught(s -> grade(s, 0, 100, 91, 80, 70)));
        check("catches an A that starts at 89", true, () -> caught(s -> grade(s, 0, 100, 89, 80, 70)));
        check("catches a B that starts at 81", true, () -> caught(s -> grade(s, 0, 100, 90, 81, 70)));
        check("catches a C that starts at 71", true, () -> caught(s -> grade(s, 0, 100, 90, 80, 71)));
        check("catches a validator that rejects 0", true, () -> caught(s -> grade(s, 1, 100, 90, 80, 70)));
        check("catches a validator that rejects 100", true, () -> caught(s -> grade(s, 0, 99, 90, 80, 70)));
        check("catches a validator that accepts 101", true, () -> caught(s -> grade(s, 0, 101, 90, 80, 70)));
    }

    interface Check { Object get() throws Exception; }

    static void check(String name, Object expected, Check actual) {
        try {
            Object got = actual.get();
            System.out.println(Objects.equals(expected, got) ? "PASS " + name : "FAIL " + name + ": expected <" + expected + "> but was <" + got + ">");
        } catch (Exception e) {
            System.out.println("FAIL " + name + ": threw " + e);
        }
    }
    // END CHECKS
}
Hint 1 of 3

Middle-of-the-band scores like 95 or 50 get the same grade from every buggy copy. Bugs hide where the answer changes: at the edges between bands.

Hint 2 of 3

An off-by-one can push an edge either way, so test both sides of it. For the A/B edge, that's 89 and 90. The same goes for the edges of the valid range, 0 and 100, and just outside them.

Hint 3 of 3

Eight rows are enough: -1, 0, 70, 80, 89, 90, 100 and 101, each with the grade the spec gives. Work out each expected value from the spec, not from code. In Java, each row is a new Case(score, "grade").

Final answer

Why it works. This is boundary-value testing: off-by-one bugs (> instead of >=, 1..100 instead of 0..100) live at edges, so the sharpest rows sit right on and right next to them. Running tests against deliberately broken copies is called mutation testing. Tools such as PIT make the mutants for you and report the ones your suite misses.

Common mistake. Picking typical values, one from the middle of each band. Every row is correct and the suite is green, yet it catches none of the seven bugs. Green tests only prove what they actually check.

Check

assertEquals(PlainPoint(1, 2), PlainPoint(1, 2)), where PlainPoint doesn't override equals…

assertEquals calls equals, and the inherited version is identity (L5).

  1. That needs content equality. PlainPoint inherits identity equals, and these are two objects.
  2. Two separate objects, compared by the inherited identity equals, are never equal.
  3. assertEquals accepts any two objects, so this compiles fine.
  4. JUnit never skips a test because an assertion fails. It reports the failure.

Why did average(Int.MAX_VALUE, Int.MAX_VALUE) return -1.0?

The two maximums wrapped round to −2 in an Int before the division. A Long accumulator fixes it.

  1. A Double holds about 4.3 billion easily. The damage happened earlier, in the Int sum.
  2. It divided by 2, the number of values. The empty case returns early, before any division.
  3. Two Int.MAX_VALUEs wrap round to −2 in an Int, and −2 / 2 is −1.0.
  4. JUnit only compares values. The −1.0 came from the code under test.

In the generated Kotlin project, @ParameterizedTest gives "Unresolved reference 'params'". The fix?

Parameterized tests live in a separate artifact, which the Java template gets through the junit-jupiter aggregator.

  1. @ParameterizedTest lives in the junit-jupiter-params artifact, which the Kotlin template doesn't include.
  2. The error is an unresolved package, params. File names don't decide which libraries exist.
  3. open controls inheritance (L8). It has nothing to do with resolving an import.
  4. Unnecessary: one dependency line fixes Kotlin. The Java template just happens to include it.

Two doubles in a test should be compared using…

Floating point is approximate (L2), so assert "within a tolerance", not "exactly equal".

  1. 0.1 + 0.2 == 0.3 is false, so exact equality fails on rounding noise.
  2. The strings carry the same noise, 0.30000000000000004 against 0.3, and hide the intent.
  3. Casting throws the fraction away, so 1.2 and 1.9 would both "equal" 1.
  4. "Within 0.0001" ignores rounding noise but still catches real errors.

Kotlin. Each comparison is the one assertEquals would make. What does this print?

Kotlin's == calls equals, just like assertEquals. The data class compares contents, the plain class falls back to identity, and a list compares element by element using each element's equals. 0.1 + 0.2 is 0.30000000000000004, so the last needs a tolerance.

  1. Data class and list compare contents, the plain class compares identity, and the double sum isn't exactly 0.3.
  2. A list's equals compares its elements with their equals, and DataPoint's compares contents.
  3. PlainPoint doesn't override equals, so two separate objects are never equal (L5).
  4. 0.1 + 0.2 is 0.30000000000000004 in binary floating point, so exact == is false (L2).

A test passes on your laptop every morning but fails on CI every evening. The best fix?

The result depends on the real time of day, a hidden input. Passing a Clock in makes it explicit, and Clock.fixed pins it in the test.

  1. A green rerun only means it happened to be morning somewhere. The test still can't be trusted.
  2. Waiting changes nothing about the hour, and sleeps slow the suite while adding a new timing dependency.
  3. The code reads time from the injected Clock, and Clock.fixed gives the test the same instant on every run.
  4. That hides the symptom and throws away the check. The behaviour itself still needs testing.

Kotlin, on a machine whose default locale is German. What does this print?

import java.util.Locale

fun price(cents: Long) = "%.2f".format(cents / 100.0)                    // uses the default locale
fun pricePinned(cents: Long) = "%.2f".format(Locale.ROOT, cents / 100.0)  // locale chosen explicitly

fun main() {
    Locale.setDefault(Locale.GERMANY)    // what a teammate's laptop in Berlin starts with
    println(price(1234) + " " + pricePinned(1234))
}

format without a locale uses the default one, and German writes the decimal separator as a comma. Passing Locale.ROOT pins the output, so a test of pricePinned passes on every machine, while a test of price is flaky across countries.

  1. The first call has no locale argument, so it follows the German default and prints a comma.
  2. The default-locale call gives a German comma, and the Locale.ROOT call gives a neutral dot.
  3. An explicit Locale.ROOT argument overrides the default, so the second number keeps its dot.
  4. This swaps the two calls. The explicit locale is the one that ignores setDefault.

The TDD loop: red, green, refactor

~33 min

So far you wrote code, then tests. Test-driven development (TDD) flips the order. Martin Fowler's summary (bliki: TestDrivenDevelopment), which follows Kent Beck's Test-Driven Development: By Example:

  1. First, "write out a list of test cases".
  2. Red: "Write a test for the next bit of functionality you want to add." Run it and watch it fail.
  3. Green: "Write the functional code until the test passes." The simplest code is fine.
  4. Refactor: "Refactor both new and old code to make it well structured." The tests keep you safe.

Fowler calls these three steps, "often summarized as Red - Green - Refactor, … the heart of the process." It's the L2 blank-file routine (examples → plan → code → check), with the examples turned into code that checks itself.

Why bother, especially if you code with AI?

  • Tests are the spec. A failing test is a precise, executable statement of "correct". Whoever writes the implementation, you or an AI, either passes it or doesn't. Without tests, "it looks right" is the only check you have.
  • Small steps keep you un-stuck. Each step was a few lines, and you always knew what to do next: make the red test green.
  • Refactoring stops being scary. Step 4 replaced the entire algorithm, and seven tests confirmed it in a second.

A preview of fakes. Real code talks to databases, clocks and networks, which are slow and unrepeatable in a unit test. The usual answer is a test double, "a generic term for any case where you replace a production object for testing purposes". In TDD, what do you write first?

Red first. Seeing the test fail proves it can detect the missing behaviour.

  1. That's test-after. TDD writes the test first, then just enough code to pass it.
  2. A test that passes before the code exists proves nothing: it can't detect the missing behaviour.
  3. Red first shows the test can fail, so its later pass means something.
  4. Review needs finished code (L40). It isn't a step of the TDD loop.

Step 3's if (number == 4) return "IV" is…

The simplest code that passes is legitimate. The next tests and the refactor step clean it up.

  1. It's correct for every test written so far. Making it general is the next tests' job.
  2. The simplest passing code is legitimate. Later tests and the refactor step replace it.
  3. JUnit runs tests. It has no opinion on how your production code looks.
  4. Step 4's table handles 4 with no special case, so it isn't required.

"Refactoring" means…

Behaviour stays the same, and that's what the green tests prove, while the design improves.

  1. New behaviour belongs to the red and green steps. A refactor adds none.
  2. Deleting failing tests hides bugs. Refactoring keeps every test, and keeps them green.
  3. That's a port. Refactoring is small structural steps, each checked by the existing tests.
  4. The design improves while the same tests stay green, which proves behaviour didn't change.

How do tests help when an AI writes the implementation?

Tests turn "looks plausible" into "passes the spec you wrote". You still read the code (L40), but now you have a precise check.

  1. A test is an executable spec: any implementation either passes it or doesn't.
  2. Tests don't change how fast code runs, or how fast it gets written.
  3. You still read the code (L40). Tests only check the cases they contain.
  4. Tests catch only the bugs their cases cover. Untested inputs can still be wrong.

Java. Step 3's green code meets two new tests. Each . is a pass and each F a failure. What does this print?

public class Triangulate {
    // Step 3's code: green for 1, 2, 3, 4 and 5
    static String toRoman(int number) {
        if (number == 4) return "IV";
        if (number == 5) return "V";
        return "I".repeat(number);
    }

    public static void main(String[] args) {
        int[] numbers = {1, 4, 5, 6, 9};
        String[] wanted = {"I", "IV", "V", "VI", "IX"};
        StringBuilder dots = new StringBuilder();
        for (int i = 0; i < numbers.length; i++) {
            dots.append(toRoman(numbers[i]).equals(wanted[i]) ? "." : "F");
        }
        System.out.println(dots);
    }
}

The code does exactly what the tests so far demanded: 4 and 5 are special cases, and everything else is a row of I's. So 6 gives IIIIII and 9 gives IIIIIIIII. Green proves only the cases you tested, which is why Step 4 adds 9 and 1994.

  1. Green covers only the tested inputs. For 6 and 9 the code falls through to "I".repeat(n).
  2. Nothing builds 6 from V and I. Only exactly 4 and 5 are special-cased.
  3. return ends the method at once, so 4 and 5 never reach the repeat line.
  4. 1, 4 and 5 match. 6 and 9 come out as rows of I's.

Wrap-up

Exit quiz, recall card, sources

~5 min

Why does assertEquals work on two separately built data class or record values?

assertEquals just calls equals, and data classes and records generate a content-based one (L7). JUnit itself never looks at fields.

  1. JUnit never looks at fields. It just calls equals.
  2. The compiler generates a content-based equals, and assertEquals calls it.
  3. Every constructor call makes a new object. Only object declarations are singletons.
  4. They're ordinary objects, and nothing is inlined. Equality still goes through equals.

Which input is most likely to expose an overflow bug?

Extremes break fixed-width arithmetic (L2). That's exactly how the average bug surfaced.

  1. Zero is a good edge for division and empty input, but adding it can't overflow.
  2. 1 is a typical value, far from the limits of an Int.
  3. -1 tests negatives, but it's nowhere near Int.MIN_VALUE.
  4. It's the largest Int, so adding anything positive to it wraps round.

In what order do the tests in a class run?

The output above shows tests running in neither written nor alphabetical order. Independent tests don't care.

  1. PriceTest's output listed the tests in a different order from the source file.
  2. Not alphabetical either: "formats cents…" ran before "can hide the cents".
  3. JUnit's default order is deterministic but deliberately unspecified, so each test must stand alone.
  4. JUnit doesn't time tests in advance or sort them by speed.
