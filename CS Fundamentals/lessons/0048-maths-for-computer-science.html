Part 1

Logic, sets and induction

~30 min

You already write logic every day: every if is a proposition, and every && is a logical AND. What you probably haven't done is reason about it the way a proof does. The primary source for this lesson, Mathematics for Computer Science (MIT's free textbook, called MCS below), explains why that matters to programmers: proofs "are used to certify that software and hardware will always behave correctly, something that no amount of testing can do" (MCS, Introduction). By the end of this part you'll have seen a claim pass forty tests and still be false.

Implication, and the contrapositive

"If p then q" is written p → q. MCS sums up its truth table in one sentence: "An implication is true exactly when the if-part is false or the then-part is true" (MCS §3.1). In code, that's !p || q. Two related statements get confused with it all the time:

  • The contrapositive, ¬q → ¬p, which "is logically equivalent to" the original (MCS §1.5.2). "If n is divisible by 4, n is even" says exactly the same as "if n is odd, n isn't divisible by 4".
  • The converse, q → p, which is a different claim. "If n is even, n is divisible by 4" is false: n = 6.

Programs can check every row of a truth table, because a boolean has only two values. Checking every case is a real proof, called a proof by exhaustion. The same program checks De Morgan's laws: ¬(a ∧ b) ≡ ¬a ∨ ¬b and ¬(a ∨ b) ≡ ¬a ∧ ¬b.

p      q      p->q   !q->!p  q->p
true   true   true   true   true
true   false  false  false  true
false  true   true   true   false
false  false  true   true   true
De Morgan holds for all inputs: true
all >= 70: true   any == 100: false
not all >= 90 == any < 90: true
empty.all { it > 1000 }: true
A ∪ B = [1, 2, 3, 4, 5]   A ∩ B = [3, 4]   A − B = [1, 2]
|A ∪ B| = |A| + |B| − |A ∩ B|: 5 = 4 + 3 − 2

Java prints the same lines; only its vacuous-truth line is labelled empty.allMatch(x > 1000). The p->q and !q->!p columns are identical, and the q->p column isn't. De Morgan is the law you use when you simplify if (!(user.isActive && user.isVerified)) into if (!user.isActive || !user.isVerified).

"For all" and "there exists"

"Every score is at least 70" is a statement for all elements (∀). "Some score is 100" is a statement that there exists one (∃). In code they're all and any (Java: allMatch, anyMatch). Negating one turns it into the other: "not every score is ≥ 90" means "some score is < 90", and the program checks exactly that.

Then there's the line that surprises people. all on an empty list is true. The Kotlin docs: "if the collection contains no elements, the function returns true because there are no elements in it that do not match the predicate" (all). The Java docs name it: "If the stream is empty, the quantification is said to be vacuously satisfied and is always true (regardless of P(x))" (Stream.allMatch). It's the right answer, and it's also a classic bug. L14's passesAll(pw, rules) = rules.all { it.check(pw) } accepts every password if someone passes an empty rule list.

Sets

A set is a collection with no duplicates and no order that matters (MCS §4.1). The three operations you'll use are union A ∪ B (in either), intersection A ∩ B (in both) and difference A − B (in A but not B). Kotlin's union, intersect and subtract each return a new set (union). Java's bulk methods change the set you call them on: retainAll "effectively modifies this set so that its value is the intersection of the two sets" (Set.retainAll). That's why Logic.java copies a before each one. The last output line is the counting rule called inclusion–exclusion (MCS §14.9): when you add the two sizes, the overlap gets counted twice, so you subtract it once.

Testing is not proving

Here are two claims about every n ≥ 0. Claim A: 1 + 2 + … + n = n(n+1)/2. Claim B, from MCS §1.1: n² + n + 41 is always prime. Test both:

Claim A holds for n = 1..100000: true
Claim B holds for n = 0..39, then fails: p(40) = 1681 = 41 * 41

Forty passing cases in a row, and then it's false. MCS draws the moral: "you can't check a claim about an infinite set by checking a finite set of its elements, no matter how large the finite set" (MCS §1.1). Claim A's 100,000 passes are evidence, but not yet proof. Induction turns them into one.

Induction

MCS states the principle like this: "Let P be a predicate on nonnegative integers. If P(0) is true, and P(n) IMPLIES P(n + 1) for all nonnegative integers, n, then P(m) is true for all nonnegative integers, m" (MCS §5.1, the Induction Principle). It's a chain of dominoes. Knock over the first one (the base case), show that each domino knocks over the next (the inductive step), and every domino falls. Here is Claim A proved (MCS Theorem 5.1.1):

Claim. For all n ≥ 0, 1 + 2 + … + n = n(n+1)/2.

Base case, n = 0. The empty sum is 0, and 0·1/2 = 0.

Inductive step. Assume it holds for n. Then 1 + … + n + (n+1) = n(n+1)/2 + (n+1) = (n+1)(n/2 + 1) = (n+1)(n+2)/2, which is the formula for n+1. ∎

Now look at a recursive function. The proof above and the code below have the same shape: the base case is the if (n == 0), and the inductive step is "assume the recursive call is right, then show this call is right". That's how you convince yourself any recursive function works, and L18 relies on it.

Strong induction lets the step assume P(0) through P(n), not just P(n) (MCS §5.2). factor needs it, because it recurses on d and n / d, which can be any smaller numbers, not just n − 1:

sumTo(10) = 55, formula = 55
factor(360) = [2, 2, 2, 3, 3, 5]
factor(97) = [97]
factor(1001) = [7, 11, 13]

Loop invariants: induction for loops

A loop is recursion in disguise, so it has its own version of the argument. An invariant is "a property that is preserved through a series of operations or steps" (MCS §5.4). To prove a loop correct with one, you show three things:

  1. It starts true. The invariant holds before the first pass.
  2. Each pass keeps it true. If it holds at the top of a pass, it holds at the top of the next one.
  3. When the loop stops, it gives the answer. The invariant plus the exit condition imply the result you wanted.

Steps 1 and 2 are the base case and inductive step again. Step 3 is the new part. You can also make the program check the invariant while it runs. In Kotlin that's check. In Java it's the assert statement, which is a different kind of tool:

On all-negative temperatures it returns a maximum that isn't even in the array. Kotlin's check catches the bug every time. The JLS: "If the assertion is disabled, execution of the assertion has no effect whatsoever" (JLS §14.10).

This invariant check rescans the array on every pass, which turns an O(n) loop into an O(n²) one (L16 makes that precise). What Kotlin does for you.
  • require, check and assert are ordinary standard-library functions with a lazy message lambda (L10, L14). Java's assert is a statement built into the language, and the always-on checks are hand-written if … throw.
  • all, any and none work on any collection directly. Java goes through .stream() first.
  • a union b, a intersect b and a subtract b are infix and return new read-only sets. Java's addAll/retainAll/removeAll mutate the receiver, so you copy first or lose your original set.
  • factor(d) + factor(n / d) concatenates two lists with +. Java makes a new ArrayList and calls addAll.
Exercise: Euclid's algorithm, with its invariant

From a blank file, in both languages. MCS §8.2 describes Euclid's gcd algorithm as a state machine: the state is a pair (x, y), and each step goes from (x, y) to (y, x mod y) until y is 0. Its invariant is "gcd(x, y) = gcd(a, b)".

  1. Write gcdSlow(a, b), which tries every candidate divisor from the larger number down. It's slow but obviously correct.
  2. Write gcd(a, b) with the Euclid loop. Check the invariant on every pass with gcdSlow, and count the steps.
  3. Write the three-step argument as a comment: why the invariant starts true, why each step keeps it, and why x is the answer when y hits 0.
  4. Run it on (1071, 462), (462, 1071), (17, 0) and (832040, 514229).
Solution 
gcd(1071, 462) = 21 in 3 steps
gcd(462, 1071) = 21 in 4 steps
gcd(17, 0) = 17 in 0 steps
gcd(832040, 514229) = 1 in 28 steps

The argument. It starts true, because (x, y) = (a, b). Each step keeps it, because any number that divides x and y also divides x mod y = x − qy, and the reverse holds too (MCS Lemma 8.2.1: "gcd(a, b) = gcd(b, rem(a, b))"). When y = 0, gcd(x, 0) = x, so x is the answer. It also stops quickly: MCS shows that x at least halves every two steps, so the algorithm "terminates after at most 1 + 2 log a transitions". For a = 832040 that bound is about 40 steps, and the real run took 28. (832040 and 514229 are consecutive Fibonacci numbers, which take many steps for their size.)

Part 2

Counting and probability

~25 min

How many passwords can an attacker try? How many keys will collide in a hash table? How likely is a duplicate among your random IDs? All three are counting questions, and they're the probability you need for L19 and for every "how likely is this to fail?" question later in the course.

The product rule, permutations and combinations

  • Product rule: if you make a sequence of independent choices, multiply the number of options for each (MCS Rule 14.2.1). A 4-digit PIN is 10 × 10 × 10 × 10.
  • Permutations count ordered picks. Gold, silver and bronze among 10 runners: 10 × 9 × 8 = 720.
  • Combinations count unordered picks. A team of 3 from 10 is 720 / 3! = 120, because each team was counted once for every order its 3 people could be in. MCS calls this the division rule (§14.4). The formula is C(n, k) = n! / (k! (n−k)!), read "n choose k".
  • Pigeonhole principle: "If there are more pigeons than holes they occupy, then at least two pigeons must be in the same hole" (MCS §14.8).

  • Counts explode, so L2's overflow comes back. 62¹² doesn't fit in a Long, and 21! doesn't either. Math.powExact, new in JDK 25, throws instead: it "Returns x raised to the power of n, throwing an exception if the result overflows a long" (Math.powExact). When you need the exact huge number, use BigInteger.
  • choose never computes a factorial. Its loop has an invariant: after step i, result = C(n, i+1). Each division is exact, because C(n, i) · (n − i) = C(n, i+1) · (i + 1). So C(60, 30) fits in a Long even though 60! has 82 digits. MCS counts poker hands the same way: "the number of 5-element subsets of a 52-element set, which is C(52, 5) = 2,598,960" (§14.7).
  • Hash collisions are guaranteed. There are about 4.3 billion Int values and infinitely many strings, so by the pigeonhole principle some strings must share a hash code. String.hashCode is "s[0]*31^(n-1) + s[1]*31^(n-2) + ... + s[n-1]" (String.hashCode), so "Aa" = 65·31 + 97 = 2112 and "BB" = 66·31 + 66 = 2112. Hash tables (L19) can't avoid collisions. They have to handle them.

Probability, and the birthday paradox

When every outcome is equally likely, the probability of an event is (outcomes in the event) / (all outcomes). Two rules do most of the work. The complement rule: P(at least one) = 1 − P(none). And for independent events, probabilities multiply (MCS §17.7). Put them together on a classic question from MCS §16.4: "There are 95 students in a class. What is the probability that some birthday is shared by two people?" Most people guess around a quarter. The real answer is more than 0.9999.

The working: with d possible values and n people, the product rule gives dn equally likely sequences, of which d(d−1)…(d−n+1) have no repeats. So P(no match) = (d/d) · ((d−1)/d) ⋯ ((d−n+1)/d), and P(match) = 1 minus that. MCS explains why programmers care: "birthday matching is a good model for collisions between items randomly inserted into a hash table" (§16.4).

  • Exact maths and simulation agree to within about 0.001 over 100,000 random rooms. Simulating like this is called the Monte Carlo method. It's how you check a formula you don't trust yet. Kotlin's Random(42) and Java's new Random(42) are different generators, so the simulated digits differ between the two columns, but both are seeded, so each language repeats its own numbers exactly.
  • 23 people give better-than-even odds. The intuition fails because you're counting pairs, and 23 people make C(23, 2) = 253 of them. MCS's rule of thumb: with d values and about √(2d) items, "the probability that two share a birthday is about 1 − 1/e ≈ 0.632" (§16.4).
  • Hash codes collide early. A perfectly random 32-bit hash still has a 50% chance of a collision by about 77,000 keys. That's tiny next to 4.3 billion.

Expected value, and why it adds up

The expected value of a random quantity is its average, weighting each possible value by its probability. One property makes it easy to calculate with: "the expected value of a sum of random variables is the sum of the expected values of the variables" (MCS §18.5, Theorem 18.5.1). This is called linearity of expectation, and it holds "for any random variables", independent or not. Each of the 253 pairs among 23 people matches with probability 1/365, so the expected number of matching pairs is 253/365 = 0.693. The pairs aren't independent (if A matches B and B matches C, then A matches C), and that doesn't matter. L19 uses the same calculation for "how many keys share a bucket?"

What Kotlin does for you.
  • acc * BigInteger.valueOf(…) / … works because the standard library adds operator functions to BigInteger: "Enables the use of the * operator for BigInteger instances" (times). Java spells it .multiply(…).divide(…).
  • "%,d".format(x) is an extension on String. Java calls the static String.format("%,d", x).
  • (1..n).fold(1L) { acc, k -> acc * k } is a factorial in one expression, with the Long chosen by the 1L start value.
  • repeat(trials) { … } replaces a counting for loop whose variable you never use.
  • kotlin.random.Random works on every Kotlin platform, not just the JVM. java.util.Random is the JVM's own.

Part 3

Logs, sums and modular arithmetic

~25 min

A logarithm counts halvings

log₂ n answers the question "how many times can I halve n before I reach 1?". That's the whole reason logs appear in algorithms. Binary search (L18) halves its range on every step, and a balanced tree (L20) halves the remaining keys at every level. You can count halvings exactly, without floating point, by looking at the bits:

n              halvings  31-leadingZeros  floor(log2)
1                     0                0            0
8                     3                3            3
1000                  9                9            9
1000000              19               19           19
1000000000           29               29           29
2147483647           30               30           30
ln(1000)/ln(10) = 2.9999999999999996
  • A billion items take 29 halvings. That's why an O(log n) algorithm barely notices the size of its input.
  • The highest 1-bit is the answer. numberOfLeadingZeros "Returns the number of zero bits preceding the highest-order ("leftmost") one-bit" (Integer). 31 minus that is the position of the highest 1-bit, which is floor(log₂ n), computed exactly with integer operations.
  • Floating-point logs can be slightly wrong. ln(1000)/ln(10) should be exactly 3. Take the floor of 2.9999999999999996 and you get 2: L2's 0.1 + 0.2 again. Java's Math has log and log10 but no log2, which tempts you into exactly this change of base. Kotlin has kotlin.math.log2 (log2).

Two sums you'll meet everywhere

The arithmetic series, 0 + 1 + … + (n−1) = n(n−1)/2, which you proved in Part 1. It's how many times the inner loop runs in for i … for j < i: about n²/2, so O(n²) (L16). The geometric series, 1 + 2 + 4 + … + 2k = 2k+1 − 1 (MCS §13.1 derives the general form). Each term is one more than the sum of all the terms before it. This sum is why a growable array that doubles its capacity is fast:

pairs i>j for n=1000: 499500   formula n(n-1)/2 = 499500
1+2+4+...+512 = 1023   formula 2^10 - 1 = 1023
n          doubling copies  per item   +10 copies    per item
1000                  1023      1.02         49600        49.6
10000                16383      1.64       4996000       499.6
100000              131071      1.31     499960000      4999.6
1000000            1048575      1.05   49999600000     49999.6

When a full array of capacity c grows, it copies c elements. With doubling, the copies are 1 + 2 + 4 + … up to less than n, which is a geometric series adding up to less than 2n. So the copying costs fewer than 2 per item no matter how big n gets, and the table shows between 1.02 and 1.64. With "+10" growth, the copies are 1 + 11 + 21 + …, an arithmetic series of about n²/20. That's about n/20 copies per item, and 50,000 per item at a million items. L16 calls the doubling result amortised O(1), and you'll build exactly this array there.

Modular arithmetic

a mod m is the remainder after dividing by m, which always lands in 0 … m−1. A clock is the classic picture: 10 days after a Wednesday is a Saturday, because 10 mod 7 = 3. MCS gives the rule that makes it useful: when you only need the remainder, "we can take remainders at every step so that the entire computation only involves numbers in the range [0..n)" (MCS §8.7). Adding or multiplying first and reducing later gives the same answer as reducing at every step.

On the JVM there's a trap, which you met in L2. % isn't mod for negative numbers. "The result of the remainder operation can be negative only if the dividend is negative" (JLS §15.17.3). Math.floorMod's result "has the same sign as the divisor y or is zero" (Math.floorMod), and so does Kotlin's mod: "The result is either zero or has the same sign as the divisor" (mod).

(2 - 10) % 7 = -1   (2 - 10).mod(7) = 6

  • Wednesday minus 10 days is Sunday (6), not "day −1".
  • Hash codes are often negative. hashCode() % 10 as an array index gives −9, which throws ArrayIndexOutOfBoundsException. Math.abs doesn't fix it, because one hash code, Integer.MIN_VALUE, has no positive twin (L2), so abs(h) % 10 is still −8. mod/floorMod is always safe. Part 4 shows the trick HashMap actually uses: and 15.
  • Modular powers in a few dozen steps. powMod looks at the exponent's bits. Each pass squares b and halves e, so 3^(10¹⁸) takes about 60 passes, where a naive loop would need 10¹⁸ multiplications. Reducing mod m at every step (the MCS rule above) keeps every product below m², about 10¹⁸, which fits in a Long. And BigInteger.modPow agrees: it "Returns a BigInteger whose value is (thisexponent mod m)" (BigInteger.modPow). This is the arithmetic inside RSA encryption (MCS §8.11), and the final proves this loop correct.
What Kotlin does for you.
  • x.mod(m) is a method on the number, available since Kotlin 1.5. Java calls the static Math.floorMod(x, m).
  • n.countLeadingZeroBits() reads as an English question about n. Java's equivalent is the static Integer.numberOfLeadingZeros(n).
  • kotlin.math.log2 exists. Java has no Math.log2, so Java code divides two logs and risks the 2.9999… trap.
  • copies(items) { it * 2 } passes a Kotlin function type (L14). Java declares the parameter as IntUnaryOperator and calls applyAsInt.

How many times does the inner body run in for (i in 0 until n) for (j in 0 until i) …?

0 + 1 + … + (n−1), the arithmetic series: 499,500 for n = 1000 in the output above. That's O(n²).

Why does a doubling array cost under 2 copies per added item?

1 + 2 + 4 + … stays below twice its last term, and the last copy is smaller than n, so all the copies together come to fewer than 2n.

Roughly how many squaring passes does powMod make for an exponent of 1018?

One pass per bit of the exponent: log₂ 10¹⁸ ≈ 59.8, so 60 passes.

  • Why n and (n - 1) works. Subtracting 1 flips the lowest 1-bit to 0 and every 0 below it to 1, leaving the higher bits alone. AND-ing with the original therefore clears exactly that lowest 1-bit. The result is 0 only if that was the only 1-bit, which is what being a power of two means. That's a complete proof, and the column of results agrees. In the same way, n and -n keeps only the lowest 1-bit, because −n is n.inv() + 1 in two's complement (L2).
  • Counting bits: countOneBits() / Integer.bitCount returns "the number of one-bits", which "is sometimes referred to as the population count" (Integer.bitCount).
  • When the table size is a power of two, h and (size - 1) equals h.mod(size). The low bits are the remainder when you divide by a power of two, and the result is never negative. The program checks every h from −1000 to 1000. That's why HashMap keeps its table size a power of two and finds a bucket with (n - 1) & hash (HashMap.java, implementation detail).
  • The catch: the mask throws away the high bits. Keys that differ only up there all land in bucket 0, as the eight keys above do. OpenJDK's comment says the same: "Because the table uses power-of-two masking, sets of hashes that vary only in bits above the current mask will always collide." Its fix is one line, (h = key.hashCode()) ^ (h >>> 16), which XORs the top 16 bits into the bottom 16. With that fix, the same eight keys spread over eight different buckets. You'll write this in L19.
Bridge to Android. Every colour in Android is a bit-packed Int. The Color docs call them "ARGB colors" and give the encoding as int color = (A & 0xff) << 24 | (R & 0xff) << 16 | (G & 0xff) << 8 | (B & 0xff); (Android: Color). The exercise below builds exactly that.
What Kotlin does for you.
  • Named infix operators (and, shl, ushr) are easier to read than &, << and >>>, and you can't confuse and with && the way & gets confused with it in Java.
  • There are no octal literals, so there's no leading-zero trap. Java's 010 == 8 compiles silently.
  • countOneBits(), takeHighestOneBit() and countLeadingZeroBits() are extension functions on Int, available since Kotlin 1.4. Java uses statics on Integer.
  • perms += Perm.WRITE works on any MutableCollection, including Java's EnumSet. Java calls add.
  • One thing Kotlin makes you do: 0xff0000ff is too big for an Int, so Kotlin types it as Long. "Kotlin infers Int if the value fits in the Int range. Otherwise, Kotlin infers Long" (Kotlin: Numbers). Write 0xff0000ff.toInt(). Java treats the same literal as a negative int.

Loops that prove themselves

1 · Integer square root. isqrt(n: Int): Int returns ⌊√n⌋ for n ≥ 0, and rejects negatives with IllegalArgumentException. Don't use floating point. Search with two bounds, lo and hi, under the invariant lo² ≤ n < hi², and do the arithmetic in Long so that hi * hi can't overflow. Start with lo = 0, and pick hi so the invariant holds for every Int. (Hint: 46341² = 2,147,488,281.) Check the invariant on every pass: with check in Kotlin, and with assert in Java.

Wrap-up

Exit quiz, recall card, sources

~5 min

Java: Integer a = 128, b = 128; System.out.println(a == b); (L5)

== compares references, and the Integer cache only covers −128 to 127, so these are two different boxes. Use equals.

Java: Math.abs(Integer.MIN_VALUE) % 10 (L2, Part 3)

abs(MIN_VALUE) stays negative, because there's no +2³¹ int, and % keeps the sign of the left operand. That's why a bucket index needs floorMod or a mask.

Kotlin: listOf<String>().any { it.isEmpty() } (L14, Part 1)

"There exists" needs at least one element that matches, and an empty list has none. It's the opposite of vacuous truth: on an empty list, all is true and any is false.

In Kotlin, which call checks an invariant in every build, production included? (L10, Part 1)

check is always on and throws IllegalStateException. assert needs -ea, and require is for arguments, not state.
