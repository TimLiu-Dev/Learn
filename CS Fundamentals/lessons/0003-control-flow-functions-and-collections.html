Int.MAX_VALUE + 1 prints…

Fixed-width integers wrap silently: the top bit flips, and the top bit is the negative one.

  1. 2,147,483,648 doesn't fit in an Int, whose largest value is 2,147,483,647. The result stays an Int, so it wraps.
  2. Infinity is a floating-point value. Integer arithmetic has no infinity; it wraps around instead.
  3. Adding 1 to the largest Int carries into the sign bit, giving the smallest Int.
  4. Neither language checks Int overflow by default. Java's Math.addExact throws only if you ask for it.

In Java, the safe way to check whether two strings have the same text is…

Java's == compares references. Kotlin's == calls equals for you.

  1. Java's == compares references, so two equal strings built separately can give false.
  2. equals compares the characters. If a might be null, Objects.equals(a, b) avoids an NPE.
  3. === is Kotlin's identity check. Java has no such operator, so this won't compile.
  4. String has no compare method. compareTo exists, but it orders strings and returns an int.

Kotlin: val x: Double = 1

Kotlin never converts implicitly, not even Int to Double. Write 1.0 or 1.toDouble().

  1. 1 is an Int literal, and Kotlin won't convert it to Double implicitly.
  2. Java would widen 1 to 1.0 here. Kotlin refuses: it has no implicit number conversions.
  3. A Double variable can't hold an Int, and this line never compiles anyway.
  4. Type mismatches are caught by the compiler, so the program never gets to run.

Control flow as expressions

~28 min

A statement does something, like printing or assigning. An expression produces a value. In Java, if and the classic switch are statements. In Kotlin, if and when are expressions, so you can assign their result directly. Kotlin has no ternary ? : operator, because if already does that job (Kotlin docs: Conditions and loops).

when vs switch

  • Kotlin when can match exact values ("SAT", "SUN" ->), ranges (in 80..<90) and types (is String, covered in L7). It can also have no subject at all: when { x > 0 -> … }. Used as an expression, it needs an else unless the compiler can prove every case is covered (Kotlin docs).
  • Java's modern switch with arrows -> can be used as an expression, has no fall-through, and can list several values per case. It arrived in JDK 14 (JEP 361; dev.java: Switch expressions). It can't match ranges, which is why grade uses an if/else chain.
  • Java's classic switch, with colons, falls through into the next case unless you write break. Forgetting it is a classic bug:
weekend
weekday

It ran straight on into the MON case. Prefer the arrow form, which can't fall through, and keep this in mind when you read older code.

Hint 1 of 3

A range matches with in: in 3..12 -> 5. For fizzBuzz, a when with no subject lets each branch be any true/false test, like i % 3 == 0 -> "Fizz".

Hint 2 of 3

when runs the first branch that matches, so order matters: 15 is a multiple of 3 too. For the line, loop for (i in 1..n) and put a space before every answer except the first.

Hint 3 of 3

After the three ranges, only negative ages and 65+ are left, so the last branch can be else -> if (age < 0) -1 else 6. Test i % 15 == 0 before the other two. 1..0 is an empty range, so fizzBuzzLine(0) needs no special case. Java's switch can't match ranges, so use an if/else chain there, like Flow.java's grade.

Final answer

Why it works. Each when branch is checked top to bottom, and the first match wins. That's why the ranges can simply follow each other, and why "FizzBuzz" must come first. Both functions return their text instead of printing it, so fizzBuzzLine can reuse fizzBuzz, and the checks can test each one.

Common mistake. Testing i % 3 == 0 first. Then 15 matches the Fizz branch and never reaches FizzBuzz, so fizzBuzz(15) returns "Fizz".

Which Kotlin line replaces Java's a > b ? a : b?

if is an expression in Kotlin. As an expression it needs its else (Kotlin docs).

  1. when needs braces and -> branches. This isn't valid syntax.
  2. ?: is Elvis, which supplies a default for null. It isn't a condition operator.

  4. Kotlin has no ternary ? : operator, so this doesn't compile.

What does FallThrough.java print for "SAT"?

With no break, a colon-style switch keeps running into the following cases.

  1. That needs a break after weekend. Without one, execution carries on into the next case.
  2. "SAT" jumps to its label, prints weekend, falls into MON, and stops at its break.
  3. Execution starts at the matching label, case "SAT", so weekend prints first.
  4. default runs only when nothing matches, or by falling into it. The break after weekday stops that.

for (i in 10 downTo 0 step 3) print("$i ") prints…

Start at 10 and subtract 3 while the value is still ≥ 0. The next one, −2, would be past the end.

  1. 1 is still ≥ 0, so it's included. The loop stops only when the next value would pass 0.
  2. A downTo range starts at its first number, 10, not at a multiple of 3.
  3. −2 is past the end. A range never goes beyond its bound, 0.
  4. 10, 7, 4 and 1 are all ≥ 0. The next step, −2, would pass the end.

When is else required in a Kotlin when expression?

An expression must always produce a value. If the compiler can't prove the branches are exhaustive, as with an Int subject, you need else. Sealed types and enums can be exhaustive without one (L7).

  1. An expression must produce a value, so the compiler needs either full coverage or an else.
  2. The subject's type isn't the rule. An Int subject needs else too, because its values can't all be listed.
  3. Kotlin never invents a branch. Without full coverage, the when expression doesn't compile.
  4. With true and false both covered, a Boolean when is exhaustive and needs no else.

Two ranges overlap. What does this print?

fun size(cm: Int): String = when (cm) {
    in 0..100 -> "small"
    in 50..150 -> "medium"
    else -> "large"
}

fun main() {
    println(size(75) + " " + size(100) + " " + size(120))
}

when tries its branches top to bottom and runs the first match. 75 and 100 are both in 0..100 (.. includes the end), so they never reach medium. Only 120 does.

  1. when doesn't pick the last or the "best" match. 75 matches the first branch and stops there.
  2. First match wins, and .. includes 100, so only 120 gets past the first branch.
  3. 0..100 includes its end, so 100 matches the first branch. 0..<100 would exclude it.
  4. Kotlin doesn't reject overlapping ranges. Branches may overlap, and their order decides.

What Kotlin does for you. One function with default values replaces Java's ladder of three overloads that delegate to each other. A Kotlin function with a block body and no declared return type returns…

"If a function has a block body and no explicit return type, the compiler infers its return type as Unit" (Kotlin docs).

  1. With a block body and no declared type, Kotlin infers Unit, a real type with one value.
  2. Nothing is for functions that never return, like one that always throws.
  3. void is Java's keyword. Kotlin's equivalent is Unit.
  4. Any is the supertype of all non-null types. A block body with no return type gives Unit, not Any.

Why prefer functions that return a value over ones that print?

A returned value can be checked by a test, passed to another function, or printed. Printed text is a dead end.

  1. Speed isn't the reason. The difference is what callers can do with the result.
  2. Kotlin allows println anywhere. logLine in this part does exactly that.
  3. The caller decides what happens next: check it in a test, pass it on, or print it.
  4. Memory isn't the issue: the same text exists either way. Testability is.

Null safety

~28 min

null means "no object here". In Java, any reference variable can hold null, and the compiler doesn't track which ones might. Calling a method on null throws a NullPointerException (NPE) at runtime, often far from where the null came from.

Kotlin moves the problem to compile time. String can never be null. String? can, and the compiler won't let you use a String? until you've dealt with the null case (Kotlin docs: Null safety).

Kotlin: val s: String? = null; println(s.length)

  1. It never gets to run. Kotlin rejects a plain . call on a String? at compile time.

  3. That's what s?.length would give. A plain . call doesn't compile.
  4. Nothing turns null into 0 unless you ask for it, with ?: 0.

s?.length is null, and Elvis then supplies 0.

  1. s?.length is null, so Elvis falls back to its right side, 0.
  2. s?.length on its own would be null. The ?: 0 replaces it.
  3. ?. skips the call when s is null, so nothing is dereferenced.

Which one can still throw a NullPointerException in Kotlin?

!! is an explicit opt-out of null safety. Treat every !! in your code as a question mark over that line.

  1. A safe call returns null instead of throwing when s is null.
  2. The safe call gives null, and Elvis turns it into 0. Nothing throws.
  3. let after ?. runs only when s isn't null, so it is never null.
  4. !! throws an NPE when s is null. It's an explicit opt-out of null safety.

Reading compiler errors

A compiler error is a precise message, not a judgement. Every one has the same anatomy: file : line : column, then what was expected versus what was found, often followed by the offending line with a ^ under the exact spot. Three rules:

  1. Start with the first error. Later errors are often side-effects of earlier ones.
  2. Read the message literally. "expected 'Int', actual 'String'" tells you the fix.
  3. Recompile after each fix. Some checks only run once earlier ones pass, so new errors can appear. That's progress, not regression.

Best type to hold a count of 5 GiB worth of bytes?

5 GiB is about 5.4 billion, which is beyond Int's roughly 2.1 billion, and an exact count should never be a float. (L2 callback.)

  1. Int stops at about 2.1 billion, and 5 GiB is about 5.4 billion bytes.
  2. Long goes up to about 9.2 × 1018 and counts exactly.
  3. Short stops at 32,767, which is far too small.
  4. A Float can't represent every whole number above 16,777,216, so a count this big gets rounded.

Which Java switch form can't fall through?

Arrow cases (case X ->) run exactly one branch (JEP 361).

  1. Colon cases fall through into the next one unless you write break.
  2. default is just another label. It doesn't stop fall-through.
  3. Arrow cases run exactly one branch, with no break needed.
  4. Strings fall through just like numbers in the colon form, as FallThrough.java showed.

  1. There's no automatic zero. Write ?: 0 or use getOrDefault for that.
  2. map[key] never throws. getValue(key) does, for a missing key.
  3. The result type is nullable, like Int?, because the key might be missing.
