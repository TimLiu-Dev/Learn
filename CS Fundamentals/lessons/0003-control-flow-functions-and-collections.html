Part 1

Control flow as expressions

~20 min

A statement does something, like printing or assigning. An expression produces a value. In Java, if and the classic switch are statements. In Kotlin, if and when are expressions, so you can assign their result directly. Kotlin has no ternary ? : operator, because if already does that job (Kotlin docs: Conditions and loops).

95 -> A
83 -> B
70 -> C
42 -> F

bigger: 7, SAT is a weekend

#1 = 83

when vs switch

  • Kotlin when can match exact values ("SAT", "SUN" ->), ranges (in 80..<90) and types (is String, covered in L7). It can also have no subject at all: when { x > 0 -> … }. Used as an expression, it needs an else unless the compiler can prove every case is covered (Kotlin docs).
  • Java's modern switch with arrows -> is an expression, has no fall-through, and can list several values per case. It arrived in JDK 14 (JEP 361; dev.java: Switch expressions). It can't match ranges, which is why grade uses an if/else chain.
  • Java's classic switch, with colons, falls through into the next case unless you write break. Forgetting it is a classic bug:
weekend
weekday

It ran straight on into the MON case. Prefer the arrow form, which can't fall through, and keep this in mind when you read older code.

Kotlin has no three-part for (init; cond; step). You loop over a range instead: .. includes the end, ..< excludes it, and downTo and step change the direction and stride (Kotlin docs: Ranges; dev.java: Control flow).

What Kotlin does for you. if and when return values, so you don't need a ternary operator or a temporary variable. when never falls through, and it can test ranges and types. Ranges like 0..<10 say what you mean with no counter variable to get wrong.

With no break, a colon-style switch keeps running into the following cases.

Start at 10 and subtract 3 while the value is still ≥ 0. The next one, −2, would be past the end.

When is else required in a Kotlin when expression?

An expression must always produce a value. If the compiler can't prove the branches are exhaustive, as with an Int subject, you need else. Sealed types and enums can be exhaustive without one (L7).

What Kotlin does for you. One function with default values replaces Java's ladder of three overloads that delegate to each other. The Kotlin docs say exactly this: "optional parameters reduce the need for multiple overloads" (Kotlin docs). Named arguments let you skip a middle parameter and make calls self-documenting, as in connect(timeoutMs = 500). Java must repeat "Hello" just to change the punctuation. One limit: named arguments don't work when calling Java methods. L9 covers @JvmOverloads, which makes your defaults usable from Java.

A design habit to start now: prefer functions that return a value over functions that print it. grade(score) returns a String, so you can test it, reuse it, and print it wherever you like. A function that only prints can do none of that. In L11 you'll write tests, and they need values to check.

Part 3

Null safety

~20 min

null means "no object here". In Java, any reference variable can hold null, and the compiler doesn't track which ones might. Calling a method on null throws a NullPointerException (NPE) at runtime, often far from where the null came from.

Kotlin moves the problem to compile time. String can never be null. String? can, and the compiler won't let you use a String? until you've dealt with the null case (Kotlin docs: Null safety).

Both programs end in an NPE, and that's the point to take away. In Kotlin you had to ask for it by typing !!. In Java the crash comes from a perfectly ordinary-looking line that the compiler accepted. Java's tools are discipline (check before you use), Objects.requireNonNull(x) to fail early, and Optional for return values. The JDK describes Optional as "primarily intended for use as a method return type where there is a clear need to represent 'no result'" (Optional docs). The e -> … inside .map is a lambda, which L14 covers properly.

Kotlin isn't null-proof. The docs list where NPEs still come from: !!, Java interop (values coming from Java code are "platform types", covered in L9), and a few initialization edge cases (Kotlin docs).

What Kotlin does for you. Kotlin makes nullability part of the type, so "can this be null?" is answered by the compiler, not by reading documentation and hoping. Smart casts remember your != null checks, and ?., ?: and let replace whole if blocks. Map lookups (contacts[name]) honestly return String?. Java's get returns null too, but its type doesn't tell you.

Collections, and reading compiler errors

~25 min

The big three

TypeHoldsOrder?Use when…
Listelements by position, duplicates allowedyes, by indexorder matters: a queue of tasks, lines of a file
Setunique elementsdepends on the implementation"have I seen this?": tags, visited items
Mapkey → value pairs, unique keysdepends on the implementationlooking things up by key: counts, settings, an index

Kotlin's default mutable implementations are ArrayList, LinkedHashSet and LinkedHashMap, and the last two preserve insertion order (Kotlin docs: Collections overview). In Java you choose explicitly: HashMap has no order guarantee, LinkedHashMap keeps insertion order, and TreeMap keeps its keys sorted. Note that Map.of(…) has an iteration order that is "unspecified and is subject to change" (Map docs), so never rely on it when printing.

Read-only vs mutable

Kotlin enforces read-only through the type: List simply has no mutating methods, while MutableList extends it with them. Java's List.of returns a list whose mutators "always cause UnsupportedOperationException to be thrown" (List docs), so you only find out when the line runs. One caveat for both: read-only isn't the same as immutable. A List view can wrap a list that someone else is still changing, and the elements themselves may be mutable (Kotlin docs). One more Java surprise: Set.of("apple", "pear", "apple") doesn't quietly drop the duplicate. It throws IllegalArgumentException: duplicate element: apple. Kotlin's setOf just drops it.

What Kotlin does for you. You can index with list[0] and map[key], and assign with map[key] = v, instead of get/set/put. "x" in list replaces contains, and for ((k, v) in map) destructures each entry, where Java spells out Map.Entry<String, Integer> e. Collections print readably out of the box. Read-only is checked when you compile, not discovered when the program runs.

Arrays, briefly. An array is a fixed-size block of elements: Kotlin arrayOf(…) / IntArray, Java int[]. You've already met one in main(String[] args). Prefer lists in everyday code. Arrays can't grow, and Java arrays print as gibberish like [I@1b6d3586 unless you use Arrays.toString. In L16 you'll build a growable list on top of an array yourself.

Reading compiler errors

A compiler error is a precise message, not a judgement. Every one has the same anatomy: file : line : column, then what was expected versus what was found, often followed by the offending line with a ^ under the exact spot. Three rules:

  1. Start with the first error. Later errors are often side-effects of earlier ones.
  2. Read the message literally. "expected 'Int', actual 'String'" tells you the fix.
  3. Recompile after each fix. Some checks only run once earlier ones pass, so new errors can appear. That's progress, not regression.
