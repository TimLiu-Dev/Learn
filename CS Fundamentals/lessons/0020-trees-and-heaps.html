Trees & Heaps

A hash map finds a key in O(1) but forgets every kind of order. A tree keeps its keys sorted and still finds one in O(log n), as long as it stays bushy. A heap gives up full sorting and keeps just enough order to hand you the smallest item, fast, every time.

Part 1

Binary search trees: build MyBST

~30 min

A linked list node has one "next" link. A binary tree node has two links, left and right, and either can be null. The vocabulary:

WordMeaningIn the tree below
rootthe one node with no parent; you hold a reference to it50
leafa node with no children20, 40, 60, 80
subtreea node plus everything below it, itself a tree30, 20, 40
depthhow many links from the root down to a node60 is at depth 2
heightnodes on the longest root-to-leaf path (this lesson: empty tree = 0)3

Height conventions differ. Sedgewick & Wayne count links, so a single node has height 0. This lesson counts nodes, so a single node has height 1 and "n sorted keys give height n" comes out exactly. Pick one and say which.

A binary search tree (BST) adds one rule. In Sedgewick & Wayne's words, it is "a binary tree where each node has a Comparable key (and an associated value) and satisfies the restriction that the key in any node is larger than the keys in all nodes in that node's left subtree and smaller than the keys in all nodes in that node's right subtree" (Algorithms §3.2, Binary Search Trees). Note the words all nodes: the rule covers the whole subtree, not just the two children. That detail returns as a bug in Part 2's exercise.

The payoff: to find a key, compare with the root and go left or right. Every comparison discards a whole subtree, like binary search (L18) without the array.

rec 60: true, rec 45: false
loop 60: 50 70 60 true
loop 45: 50 30 40 false

Both programs print the same thing. The search for 45 touched 3 of 7 nodes and stopped at a null link. Notice compareTo rather than <. It returns negative, zero or positive, and it's the only comparison a generic K : Comparable<K> will offer you in the final (L13).

Step through it. Each tab is a separate run. The insert tab shows why insert is "search, then hang a leaf on the null link where the search fell off":

Insert: the "return the new subtree" pattern

The recursive insert has one trick that makes everything else easy. The function returns the root of the subtree it was given, and the caller re-links it: node.left = insert(node.left, key). Most calls return the same node they got, so the link is rewritten with its own value. The call that reaches a null link returns a brand-new node, and the assignment hangs it in place. Delete uses the same pattern, so learn the shape now.

Delete: three cases

Find the node, then:

  1. Leaf. Return null to the parent. The link disappears.
  2. One child. Return that child to the parent, which promotes the whole subtree one level.
  3. Two children. Neither child can take the slot alone. Find the in-order successor, the smallest key in the right subtree: step right once, then go left until you can't. Copy its key (and value!) into this node, then delete the successor from the right subtree. The successor has no left child, so that second delete is always case 1 or 2. Sedgewick & Wayne credit this to Hibbard, 1962: "The replacement preserves order in the tree because there are no keys between x.key and the successor's key" (§3.2, Deletion).

Cases 1 and 2 collapse into two lines once you see that a leaf is just "a node whose only child is null": if there's no left child, return the right one, which may be null; if there's no right child, return the left one.

What Kotlin does for you.
  • Node? makes "this subtree might be empty" part of the type, so the compiler won't let you read node.key until you've handled null. In Java, forgetting the check is a NullPointerException at runtime.
  • ?: return turns a missing child into an early exit in one line: val left = node.left ?: return node.right is cases 1 and 2 of delete.
  • Default parameters give one Node(key, left = null, right = null) constructor. Java needs two overloads to build trees by hand.
  • when on compareTo's result reads like the three-way branch it is, and can be an expression whose value is the next node.

When the tree is a stick

Every operation walks one root-to-leaf path, so they all cost O(h), where h is the height. The height depends entirely on the insertion order. Insert keys in sorted order and each new key is bigger than everything so far, so it always goes right: you've built a linked list with extra steps. Here are the same 1..1000 keys inserted sorted and shuffled, with an iterative insert so the deep tree can't overflow the stack:

n=1000  sorted height=1000  shuffled height=27
n=10000  sorted: 49995000 comparisons, 76 ms   shuffled: 151003 comparisons, 0 ms
n=20000  sorted: 199990000 comparisons, 298 ms   shuffled: 335284 comparisons, 1 ms
n=40000  sorted: 799980000 comparisons, 1174 ms   shuffled: 755895 comparisons, 3 ms
n=1000  sorted height=1000  shuffled height=27
n=10000  sorted: 49995000 comparisons, 73 ms   shuffled: 151003 comparisons, 1 ms
n=20000  sorted: 199990000 comparisons, 280 ms   shuffled: 335284 comparisons, 2 ms
n=40000  sorted: 799980000 comparisons, 1113 ms   shuffled: 755895 comparisons, 3 ms

Read it like an L16 doubling experiment:

  • Sorted: the comparisons are exactly n(n−1)/2 (10,000 × 9,999 / 2 = 49,995,000), and each doubling of n multiplies the time by about 4 (76 → 298 → 1174 ms). That's O(n²) to build, because each insert is O(n).
  • Shuffled: about 15–19 comparisons per insert, growing by roughly one per doubling, which is the O(log n) signature. Sedgewick & Wayne prove that inserts into a BST built from random keys take "~ 2 ln N (about 1.39 lg N) compares on the average" (§3.2). For 1,000 keys a perfect tree would have height 10; random gives 27, which is fine. Sorted gives 1,000, which is not.
  • Both languages compare exactly the same number of times, because both shuffle with java.util.Random(42). Kotlin's own shuffled(Random(42)) uses a different generator and would give a different tree.
OperationCostBalancedWorst (sorted input)Why
contains / getO(h)O(log n)O(n)one path from the root
insert / putO(h)O(log n)O(n)search, then attach a leaf

The fix exists, and you already have it. A balanced tree rearranges itself on every insert and delete so the height stays O(log n) whatever the input order. java.util.TreeMap is "A Red-Black tree based NavigableMap implementation", and it "provides guaranteed log(n) time cost for the containsKey, get, put and remove operations" (TreeMap API). Sedgewick & Wayne show that "the height of a red-black BST with N nodes is no more than 2 lg N" (§3.3, Balanced Search Trees). Read that section once for the idea of rotations, but don't implement a red-black tree: in real code, use TreeMap/TreeSet. Your MyBST is for understanding.

Searching the 7-node tree above for 45. How many nodes does the search compare against?

You delete a node that has two children. Which key takes its place?

The in-order successor, the smallest key in the right subtree. Nothing lies between it and the deleted key, so order is preserved. (The largest key in the left subtree, the predecessor, also works.)

You insert 1, 2, 3, …, 1000 in order into an unbalanced BST. What is contains(1000)?

Sorted input makes every node a right child: height 1000, the measured value. The search walks all of it.

Why does insert return a Node instead of returning nothing?

node.left = insert(node.left, key): when node.left was null, the call returns the new node and the assignment attaches it. Delete returns the replacement subtree the same way.

In real code you need a sorted map with guaranteed O(log n) get. Use…

TreeMap is a red-black tree with guaranteed log(n) operations. An unbalanced BST can degrade to O(n), a sorted list has O(n) inserts, and a hash map isn't sorted.

Part 2

Traversals

~25 min

A traversal visits every node once. There are three depth-first orders, and they differ only in when the node itself is visited relative to its two subtrees. Then there's one breadth-first order:

pre   [50, 30, 20, 40, 70, 60, 80]
in    [20, 30, 40, 50, 60, 70, 80]
post  [20, 40, 30, 60, 80, 70, 50]
level [50, 30, 70, 20, 40, 60, 80]
OrderVisitsTypical use
pre-ordernode, left, rightcopying or saving a tree: re-inserting the keys in pre-order rebuilds the same shape
in-orderleft, node, righta BST's keys in sorted order; this is how TreeMap iterates
post-orderleft, right, nodeanything where children must finish first: freeing nodes, computing height or folder sizes
level-orderdepth 0, then 1, then 2…"closest first": the shallowest match, printing by level. It's BFS on a graph (L21)

The recursive versions use the call stack as their memory of "where do I go back to" (L4, L18). Level-order can't do that, because it jumps sideways across the tree, so it uses an explicit FIFO queue (L17).

Lazy in-order: a generator vs an iterator

Sometimes you want the keys in order but only need the first few. Kotlin's sequence { } builder (L15) lets the recursive in-order walk pause at every yield. yieldAll hands over a whole nested sequence (Kotlin docs: Sequences, from chunks). Java has no yield for iterators, so the paused recursion has to become an explicit stack inside an Iterator class: push the path down the left edge, pop a node, then push the left edge of its right subtree.

  visit 20
  visit 30
  visit 40
first key > 35: 40
stack version:  [20, 30, 40, 50, 60, 70, 80]
  visit 20
  visit 30
  visit 40
first key > 35: 40

Both stop after visiting 40: the other four nodes are never touched. The Kotlin file also shows the explicit-stack walk as a plain function, so you can see it's the same algorithm as the Java iterator.

The JDK's navigation methods

Because a tree keeps its keys in order, it can answer questions a hash map can't: "the closest key at or below x", "everything before y". These live on NavigableMap, which TreeMap implements. One Kotlin trap, which I hit while writing this lesson:

err/SortedNav.kt:4:20: error: unresolved reference 'floorKey' on receiver of type 'SortedMap<Int, String>'.
    println(trains.floorKey(400))           // a TreeMap method...

sortedMapOf is declared to return a SortedMap (Kotlin API: sortedMapOf). Delete the last line and the program prints java.util.TreeMap: the object really is a TreeMap. But the compiler only knows the declared type, and SortedMap doesn't have floorKey. That's L8's static type vs runtime type again. Create the TreeMap directly:

java.util.TreeMap

floorKey and ceilingKey return the closest key at or below / at or above, or null if there isn't one, which is the last line. headMap(k) is "strictly less than k"; tailMap(k) is "k and above" (NavigableMap API). Each lookup is O(log n), because it's one walk down the red-black tree. TreeSet has the same methods for plain keys: floor, ceiling, headSet.

Bridge. "Find the latest price at or before 10:42", "which time slot contains this timestamp", "the leaderboard entries between 900 and 1000 points": whenever an app needs a range or a nearest match over sorted keys, look for a TreeMap (or a database index, which is also a tree; see L35).
What Kotlin does for you.
  • sequence { yieldAll(…); yield(…) } turns the three-line recursive walk into a lazy iterator. Java needs an explicit-stack Iterator class with hasNext/next and a NoSuchElementException.
  • n.left?.let { queue.addLast(it) } enqueues a child only if it exists, in one line.
  • ArrayDeque is in the Kotlin standard library with addLast/removeFirst/removeLast, so the same names work as a queue and as a stack.
  • Kotlin calls TreeMap methods directly and adds trains[key] indexing. But the declared type still decides which methods you see.

Part 3

Heaps and priority queues

~25 min

A priority queue answers one question fast, over and over: "give me the smallest (most urgent) item". A sorted list does it in O(1) but pays O(n) per insert. A BST does both in O(log n), but only if balanced, and with two pointers per item. A binary heap does both in O(log n) guaranteed, with no pointers at all.

The idea is to keep less order. A min-heap promises just one thing: every parent ≤ its children. Siblings can be in any order, so it's not sorted, but the smallest item is always at the root. Sedgewick & Wayne define it for a max-heap: a tree is "heap-ordered if the key in each node is larger than (or equal to) the keys in that node's two children" (Algorithms §2.4, Priority Queues). A min-heap flips the comparison.

A tree stored in an array

A heap is also kept complete: every level is full except possibly the last, which fills left to right. A complete tree has no gaps, so it fits in an array level by level, and the links become arithmetic:

For the node at index i0-based (this lesson, PriorityQueue)1-based (Sedgewick & Wayne)
parent(i - 1) / 2k / 2
left child2 * i + 12k
right child2 * i + 22k + 1

Sedgewick & Wayne leave index 0 empty so the formulas are tidier: "the parent of the node in position k is in position k/2" (§2.4). With 0-based indexing you subtract one. Both are the same tree.

Two operations keep the heap rule intact:

  • add: put the new item at the end of the array, which keeps the tree complete. Then sift up: while it's smaller than its parent, swap them. Sedgewick & Wayne call this "swim".
  • poll: the answer is a[0]. Move the last item into the root, which keeps the tree complete but breaks the order. Then sift down: while it's bigger than its smaller child, swap with that child. Their name for it is "sink".

Each swap moves one level, and a complete tree of n items has about log₂ n levels. So both operations are O(log n), guaranteed, whatever the input order. A complete tree can't become a stick. peek just reads a[0]: O(1).

java.util.PriorityQueue

The JDK's class is "An unbounded priority queue based on a priority heap", and "The head of this queue is the least element with respect to the specified ordering". Its implementation note promises "O(log(n)) time for the enqueuing and dequeuing methods (offer, poll, remove() and add); linear time for the remove(Object) and contains(Object) methods; and constant time for the retrieval methods (peek, element, and size)" (PriorityQueue API). Kotlin has no priority queue of its own, so both languages use this class.

println(pq): [1, 2, 8, 5, 3, 9]
peek:        1
poll order:  1 2 3 5 8 9
max first:   9 8 5
longest:     banana cherry

The surprise is line 1. println(pq) is not sorted: it walks the backing array, which is the exact array the diagram above built. The docs warn that the iterator is "not guaranteed to traverse the elements of the priority queue in any particular order. If you need ordered traversal, consider using Arrays.sort(pq.toArray())". Only poll gives sorted order. A max-heap is a min-heap with the comparison reversed: Comparator.reverseOrder(), or any comparator you can build (L14).

Top-k: a heap that never grows past k

"The 3 highest scores out of 10 million." Sorting is O(n log n) and holds everything. Instead keep a min-heap of at most k items. Its root is the smallest of your current top k, which is exactly the one to evict when something better arrives. Each of the n items costs one O(log k) heap operation: O(n log k) time and O(k) memory. For k = 3, that's nearly linear.

Heapsort in one paragraph: add all n items to a heap, then poll n times. Each poll is O(log n), so it sorts in O(n log n) worst case. Sedgewick & Wayne show how to do it in place inside the input array (§2.4, Heapsort). It's rarely used directly, because merge sort and quicksort (L18) have better constant factors and cache behaviour, but the heap underneath is everywhere.

Bridge. Schedulers are priority queues: the next task to run is the one with the earliest time. The JDK's PriorityBlockingQueue "uses the same ordering rules as class PriorityQueue and supplies blocking retrieval operations" (API), so a worker thread can wait on it for the next job. You'll meet blocking queues in the concurrency phase. In L21, Dijkstra's shortest-path algorithm uses a priority queue to always expand the closest unvisited node next.
What Kotlin does for you.
  • On any Comparable, Kotlin's a < b compiles to a.compareTo(b) < 0: "All comparisons are translated into calls to compareTo" (Kotlin docs: comparison operations). The final's generic heap can write at(i) < at(parent), where Java has to spell out a[i].compareTo(a[p]) < 0.
  • compareByDescending { it.length }.thenBy { it } and compareValuesBy(…) build comparators without the Comparator.comparingInt(…).reversed().thenComparing(…) chain.
  • check(size > 0) { "heap is empty" } throws an IllegalStateException with a message in one line (L10). IntArray.copyOf(n) grows the array like Arrays.copyOf.
  • arrayOfNulls<Any?>(n) plus a per-element cast avoids Java's generic-array trap, which you'll hit in the final.

Why is heap add O(log n) even for sorted input, when a plain BST isn't?

New items always go in the next array slot, so the tree's shape never depends on the values. A complete tree has about log₂ n levels, and sift up crosses at most all of them.

You want the 10 largest of n numbers. Which heap, and how big?

The min-heap's root is the smallest of the current top 10, the one to evict. That's O(n log 10) time and O(10) memory.

Reference implementation: Kotlin

inOrderKeys uses a local function, walk, declared inside it, which can read and append to out without passing it along. Java has no local functions, hence its private helper. a[size] = null after a poll clears the slot so the heap doesn't keep a dead object reachable. That's a memory leak in the GC sense (L24).

Reference implementation: Java

The generic-array trap. L13 said to create a generic array with (T[]) new Object[n]. That works for a plain <T>. Here T extends Comparable<T>, and erasure replaces T with its bound, so the cast becomes a real cast to Comparable[], which an Object[] isn't. It compiles, then crashes at construction:

Exception in thread "main" java.lang.ClassCastException: class [Ljava.lang.Object; cannot be cast to class [Ljava.lang.Comparable; ([Ljava.lang.Object; and [Ljava.lang.Comparable; are in module java.base of loader 'bootstrap')
	at ObjectArrayHeap$Heap.<init>(ObjectArrayHeap.java:3)
	at ObjectArrayHeap.main(ObjectArrayHeap.java:9)

Hence (T[]) new Comparable[4] in MyMinHeap.java. Kotlin's arrayOfNulls<Any?> stores elements as Any? and casts each one on the way out, so it never hits this.

Exit quiz, recall card, sources

~5 min

You need "all orders placed between 10:00 and 11:00" many times a second. Which map? (L19 + L20)

Range queries need order: subMap/headMap/tailMap on a TreeMap are O(log n) to locate. A hash map would have to scan every key.

Java: class H<T extends Comparable<T>> { T[] a = (T[]) new Object[4]; }, then new H<Integer>() (L13)

It compiles with an unchecked warning, but T erases to Comparable, so the constructor runs a real cast of Object[] to Comparable[]: ClassCastException.

A Kotlin sequence { } in-order walk is asked for first { it > 35 } on the 7-node tree. How many nodes get visited? (L15)

20, 30, then 40 matches and the sequence stops pulling. Laziness means the rest of the walk never runs.
