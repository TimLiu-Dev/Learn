Part 1

Final by default vs open

~28 min

Inheritance lets a class (the subclass) start from everything another class (the superclass) has, then add to it or override parts of it. In Java, "excepting Object, which has no superclass, every class has one and only one direct superclass" (dev.java: Inheritance). The two languages start from opposite defaults:

Java used to require super(…) to be the very first statement. Since JDK 25 you may run statements before it, as long as they don't use the object under construction (JEP 513). Kotlin calls the superclass constructor in the class header, before any of the subclass's own initialization (Kotlin docs).

Why final by default?

A class that can be extended makes a promise: subclasses may rely on which of its methods call which. That's an internal detail you now can't change without breaking them (Part 4 shows exactly this). Joshua Bloch's rule is Effective Java Item 19, "Design and document for inheritance or else prohibit it" (Effective Java, 3rd ed.). Kotlin builds that advice into the language: extension is opt-in, so every open is a deliberate design decision.

What Kotlin does for you. Classes and members are closed unless you write open, so you never accidentally promise subclassers anything. override is a keyword the compiler requires, so the Java typo bug can't happen. Omit it and you get an error, misspell the name and there's nothing to override. Calling the superclass constructor happens right in the header (: Employee(name)). Java makes you remember final, @Override and super(…) yourself.

Hint 1 of 3

Kotlin's first error is on class Bike : Vehicle(2): "This type is final, so it cannot be extended." Every Kotlin class is closed unless you write one keyword in front of class.

Hint 2 of 3

Once Vehicle is open, Truck.describe() clashes with the superclass method. You need open on Vehicle.describe() and override on Truck.describe(). Leave honk() alone: members are final by default.

Hint 3 of 3

The truck's text is super.describe() + ", carrying $load kg". In Java, the bug is the misspelled descibe: it's a brand-new method, so nothing is overridden. Add @Override and the compiler points straight at it. Then mark honk() final.

Final answer

Why it works. Kotlin needed three keywords: open class, open fun describe and override fun describe. honk() needed nothing, because it's already final. Java needed the opposite: the class was already extendable, so the fixes were @Override, which turns the silent typo into a compile error, and final on honk().

Common mistake. Writing open fun honk() "to be safe". Every open is a promise to subclassers (Effective Java Item 19), so open only what you mean to.

Check

Kotlin rejects class Dog : Animal() when Animal is declared as plain class Animal. Why?

"this type is final, so it cannot be extended." Add open to allow subclasses (Kotlin docs).

  1. Interfaces are optional: any open class can be extended directly.
  2. The header syntax is fine. The error message says the type is final.
  3. Calling the superclass constructor in the header, Animal(), is exactly Kotlin's syntax.
  4. Without open, a Kotlin class can't have subclasses.

Without @Override, Java's misspelled sond()…

It's simply a different method, so nothing is overridden and calls to sound() still run the superclass version.

  1. A different name is a different method, so it compiles and overrides nothing.
  2. Only @Override asks the compiler to check. Without it, there's nothing to complain about.
  3. Dispatch matches methods by exact name and parameters, so sound() still runs Animal's version.
  4. Nothing fails at runtime. You just get the superclass behaviour, silently.

Kotlin's final override fun describe() means…

An override is open by default, and final closes it again for any further subclasses.

  1. Callers can still call describe(): final only limits subclasses.
  2. final has nothing to do with static. describe still runs per object.
  3. It overrides the parent's describe, and final stops further subclasses from overriding it.
  4. It runs this class's version. The parent's runs only if you call super.describe().

Stretch: a superclass calls an open method from its init block. What prints?

open class Base {
    init {
        println("Base sees " + describe())
    }

    open fun describe() = "base"
}

class Derived : Base() {
    val label = "derived"
    override fun describe() = "label=$label"
}

fun main() {
    Derived()
}

The call dispatches to Derived.describe(), but Base's initializer runs before Derived's fields are set, so label is still null, even though its type says it can't be. That's why Effective Java Item 19 says constructors must not call overridable methods. Kotlin warns you here ("Calling non-final function describe in constructor").

  1. Dynamic dispatch works even inside a constructor, so the override runs, not Base's version.
  2. label gets its value only after Base's init has finished.
  3. The override runs while label still holds the JVM default for references: null.
  4. An unset reference field is null, not an empty string, and string templates print it as null.
Part 2

Interfaces and abstract classes

~28 min

An interface is a contract: "anything of this type can do these things." A class can implement as many interfaces as it likes. Interface methods may also have bodies. Java calls these default methods, added in Java 8 "to add new functionality to the interfaces of your libraries" without breaking existing implementers (Java 8 enhancements). What an interface can't do is store state: "Unlike abstract classes, they cannot store state" (Kotlin docs: Interfaces).

circle with area 3.14
a 2.0x2.0 square
a 6.0x6.0 square

Circle uses the interface's default describe(), and Square overrides it. Both are Shapes and Scalables at once. Notice the return types: Square.scaled returns a Square even though the interface promises only a Shape. That's allowed, because a Square is a Shape.

An abstract class sits between an interface and a normal class. It can have fields, constructors and finished methods like a class, plus abstract members with no body, which every concrete subclass must supply. You can't create an instance of it directly.

[Ada: 495, Grace: 5000, Linus: 2000]
AbstractNew.kt:6:13: error: cannot create an instance of an abstract class.
AbstractNew.java:7: error: Account is abstract; cannot be instantiated

applyFee() is written once, in the base class, but it calls monthlyFee(), which each subclass answers differently. The shared state (owner, balance) lives in one place. An interface couldn't hold that state.

When in doubt, start with an interface.

Program to the interface

Declare variables and parameters with the interface type, and name the concrete class only where you create the object. Effective Java Item 64 is "Refer to objects by their interfaces". Your code then depends only on the contract, so you can swap the implementation freely:

pear apple pear
apple pear
What Kotlin does for you. Kotlin interfaces can declare properties (val name: String), and implementers satisfy them with override val name = "circle". Java writes a name() method instead. Interface functions with a body need no default keyword, and Kotlin compiles them to JVM default methods (Kotlin docs). In Java, every method implementing an interface must be marked public. In Kotlin, public is the default, so there's nothing to forget.

Final answer

Why it works. The interface says what every priced thing can do. The abstract class shares the code and state that products have in common. The subclasses fill in the one thing that varies. The gift card proves the point of programming to the interface: labels never mentions Product, so anything Priced fits.

Check

Which can hold instance state, meaning fields with values?

Interfaces "cannot store state" (Kotlin docs). Abstract classes can have fields and constructors.

  1. Interfaces can declare properties but can't hold their values: they have no backing fields.
  2. Abstract classes can have fields and constructors, just like ordinary classes.
  3. Interfaces can't store state, so the two aren't equal here.
  4. Abstract classes can hold fields. Only interfaces can't.

A single class can extend… and implement…

Single inheritance of classes, but any number of interfaces (dev.java).

  1. The JVM allows only single class inheritance, so a class extends at most one class.
  2. There's no limit of one interface: a class can implement as many as it needs.
  3. Extending many classes is multiple inheritance, which Java and Kotlin forbid.
  4. One superclass, and any number of interfaces.

Why declare val names: MutableList<String> = ArrayList(), rather than typing it as ArrayList?

Effective Java Item 64: refer to objects by their interfaces, so swapping the implementation touches one line.

  1. It's the same ArrayList object either way, so the speed doesn't change.
  2. It's still a MutableList: the declared type doesn't freeze anything.
  3. Only the MutableList contract is used, so swapping the implementation touches one line.
  4. Kotlin happily lets you declare a variable as ArrayList. Using the interface is a design choice.
Part 3

Polymorphism and dynamic dispatch

~28 min

Every variable has a static type, the type it's declared with, which the compiler checks. Every object has a runtime type, the class it was actually built from. They can differ: a Shape variable can point at a Circle. When you call an overridden method, the JVM looks at the object, not the variable, to decide which version runs. That's dynamic dispatch, and it's what makes polymorphism (one interface, many behaviours) work. The JLS puts it like this: "For instance methods, the class of the object referenced by the run-time value of o participates because a subclass may override a specific method already declared in a parent class" (JLS §15.5; see also dev.java: Polymorphism).

Two different mechanisms are at work, and they happen at different times:

Overriding (a.sound())Overloading (describe(a))
What it isa subclass replaces a superclass methodseveral functions share a name but have different parameter types
Decidedat runtime, by the object's classat compile time, by the arguments' static types
So a: Animal = Dog() givesthe Dog versionthe Animal version

The JLS describes compile-time step 2 as choosing "the most specific" applicable method from the argument expressions, and that choice is fixed into the bytecode (JLS §15.12.2). Only which override of that chosen method runs is looked up at runtime (JLS §15.12.4.4). Kotlin on the JVM follows the same rules.

When is overriding resolved, and when is overloading?

Overrides are dispatched on the object's runtime class, and overloads are fixed by the compiler.

  1. That's backwards: overloads are fixed early, and overrides wait for the object.
  2. An override can't be fixed at compile time, because the object's class isn't known until runtime.
  3. Overloads are chosen by the compiler from static types, before the program runs.
  4. Overrides use the object's runtime class. Overloads use compile-time static types.

  2. It's a design smell, not a performance symptom.
  3. Move each branch into its class's override, and dispatch replaces the chain.

Part 4

Composition over inheritance

~28 min

Inheritance couples a subclass to its superclass's implementation, not just its contract. Here's the famous demonstration from Effective Java Item 18, "Favor composition over inheritance": a set that counts how many elements were ever added.

added 3, counted 6

Three elements were added, but the count is 6. That's still true today on JDK 26, exactly as Bloch describes. HashSet's addAll works by calling add once per element, and since add is overridden, dynamic dispatch (Part 3!) sends each of those calls to our add, which counts again. Nothing in HashSet's contract says addAll uses add. It's an internal detail, and the subclass broke because it depended on it. This is the fragile base class problem, and it's exactly why Kotlin makes you opt in with open (Part 1).

The fix: has-a, not is-a

Instead of being a HashSet, have one: keep a set in a private field and forward the work to it. This is called composition, with forwarding. The inner set's addAll can't call your add, because it doesn't know you exist:

What Kotlin does for you. In Java, if your wrapper must itself be a Set, you write a forwarding method for every one of Set's methods by hand. Bloch's book does exactly that with a ForwardingSet class. Kotlin's MutableSet<E> by inner makes "the compiler … generate all the methods of Base that forward to b", and your overrides replace just the ones you care about (Kotlin docs: Delegation). That's CountingSet above: a real MutableSet, with no fragile coupling, in about ten lines. You'll use by properly in L15.

A notification system

~20 min

Step 1: refactor a misuse. Someone added "urgent" messages by subclassing every channel:

[email] to ada: URGENT: Server down
[sms] to ada: URGENT: Server down

Two subclasses, the same code twice, and a third channel means a third copy. Wanting "urgent and logged" would mean subclasses of subclasses. (In Kotlin, notice that the misuse needed open typed twice: the language made you sign up for it.)

Step 2: build the replacement, from a blank file in both languages, using the blank-file routine (examples, plan, code, check):

  1. An interface Notifier with send(to, message).
  2. An abstract ChannelNotifier(channel) that holds a sent counter (the shared state that justifies an abstract class) and a final send that increments it and prints [channel #n] to …: …. It also has one overridable step, format(message).
  3. EmailNotifier (no change), SmsNotifier (truncates past 20 characters to 17 plus ...), and PushNotifier (prefixes (!) ).
  4. Two wrappers that implement Notifier by holding another Notifier: LoggingNotifier(inner, log), which records "sending to …", and UrgentNotifier(inner), which prefixes URGENT: . They work with any channel, and with each other.
  5. Send "Your build finished successfully" to "ada" through this list, in one loop:
email,

LoggingNotifier(PushNotifier(), log),
UrgentNotifier(SmsNotifier()),
UrgentNotifier(LoggingNotifier(email, log))   // the SAME email object as the first entry

Kotlin: a == b for two different objects of a class that doesn't override equals.

The inherited equals from Any is identity, and == calls it (L5). Overriding equals is dynamic dispatch too.

  1. Only an equals override that compares fields would make two different objects equal.
  2. == is null-safe and calls equals, so nothing here throws.
  3. Any's equals compares identity, and these are two different objects.
  4. == compiles for any two objects of the same type.

Passing a Dog to train(a: Animal) copies…

Pass-by-value of the reference (L4). The parameter's static type is Animal, but its arrow still points to the Dog.

  1. The parameter gets a copy of the arrow, so both point to the same Dog.
  2. Objects are never copied when they're passed. Only references are.
  3. The fields stay in the one object on the heap.
  4. Something is copied: the reference value itself. That's pass-by-value.

A Kotlin companion object is closest to Java's…

Members that belong to the class rather than to an instance (L6).

  1. An inner class holds a reference to an outer instance. A companion belongs to the class itself.
  2. Default methods are interface methods with bodies. They're unrelated to companions.
  3. final fields can't be reassigned. That's about mutability, not about belonging to the class.
  4. Members that belong to the class itself, called as ClassName.member.
