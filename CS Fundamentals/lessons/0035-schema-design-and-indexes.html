Schema Design & Indexes

A schema decides which bugs your data can have; an index decides how fast you can ask questions about it. This lesson normalises a messy table step by step, then fills the library database with 200,000 loans and makes slow queries hundreds of times faster by reading what the database tells you it's doing.

Warm-up

Recall from L19, L20, L22 and L34

~10 min
From memory: no peeking
  1. Write a query that lists every author with their number of books, including authors with none. Which join, and why? (L34)
  2. A BST gets the keys 1, 2, 3, …, 1000 in order. Draw its shape. How many comparisons does a lookup of 1000 take? (L20)
  3. A hash map answers get(key) in O(1). Why can't it answer "every key between 40 and 50" quickly? (L19)

authors LEFT JOIN books. What happens to an author with no books? (L34)

A left join keeps every row from the left table and fills the right side's columns with NULL when nothing matches. An inner join would drop the author.

A fresh SQLite connection inserts a loan pointing at book 999, which doesn't exist. With default settings: (L34)

The SQLite docs: "Foreign key constraints are disabled by default (for backwards compatibility), so must be enabled separately for each database connection." Part 1 shows it from Kotlin and Java.

Keys 1..1000 inserted in sorted order into a plain (unbalanced) BST. Its height? (L20)

Each key becomes the right child of the previous one: a linked list in disguise. L20 measured exactly 1000. Balanced trees fix this; Part 2 shows the balanced tree databases actually use.

Why can't a hash index answer "all loans between two dates" efficiently? (L19)

A good hash function sends 2026-09-01 and 2026-09-02 to unrelated buckets, so there's no "next key" to walk to. A sorted structure keeps neighbours together, which is why databases default to B-trees.

Roughly how much slower is a random 4 KB SSD read than a main-memory reference? (L22)

Norvig's table: about 100 ns for memory, about 150,000 ns for a random SSD read: roughly 1,500×. That's why databases count page reads, and why a tree that needs 3 of them beats one that needs 18.

Schema design and normalisation

Entities, relationships, and the library schema

Design starts on paper. List the entities (things you store facts about) and the relationships between them, then count how many of each side can pair up: the cardinality.

The spreadsheet design, and why it rots

Now imagine someone skipped the design step and kept everything in one wide table, the way a spreadsheet would: one row per loan, with the member, the book and the author copied into every row.

It answers simple questions fine. The trouble starts when the data changes. Three classic anomalies, shown for real:

  • Update anomaly. The author's name lives in three rows. Fix one and the database now holds two names for the same person, born the same year. Nothing stopped it, because to the database these are just strings.
  • Insert anomaly. You can't record that the library knows about Ann Leckie until someone borrows her book: a row needs a loan date.
  • Delete anomaly. Hedy's only loan was the only place her email lived. Delete the loan and the member vanishes too.

Every anomaly has the same root: one fact stored in more than one place, or two unrelated facts forced into one row. Normalisation is the discipline of removing that, one rule at a time.

First normal form: one value per cell

The genres column holds a comma-separated list. Watch what that does to queries:

loan_id  book_title                 genres
-------  -------------------------  ----------------
2        Kindred                    SF,Time travel
5        Stories of Your Life       SF,Short stories
6        The Left Hand of Darkness  SF
8        Exhalation                 SF,Short stories
9        Frankenstein               Horror,Proto-SF
book_title            genres            n_genres
--------------------  ----------------  --------
A Wizard of Earthsea  Fantasy           1
Exhalation            SF,Short stories  2
Frankenstein          Horror,Proto-SF   2
Guards! Guards!       Fantasy,Comic     2

Frankenstein is tagged Proto-SF, not SF, but LIKE '%SF%' matches any substring, so it slips in. Counting genres takes string arithmetic. Renaming a genre means a replace() across every row. And you can't put a foreign key, an index, or a CHECK on one item inside a string.

The three normal forms in one sentence each. These are the standard definitions (as summarised by Wikipedia, which cites Codd's original papers; for a textbook treatment see Silberschatz, Korth & Sudarshan, Database System Concepts, 7th ed., ch. 7):

  • 1NF: "each field is atomic, containing a single value rather than a set of values or a nested table."
  • 2NF: it's in 1NF "and contains no partial dependencies": no non-key column depends on only part of a composite key (source).
  • 3NF: it's in 2NF and "every non-prime attribute … is non-transitively dependent on each candidate key": no column depends on the key only through another column (source).

The informal version people remember: every column depends on "the key, the whole key, and nothing but the key".

  1. 1NF splits the list with a recursive CTE (a query that feeds its own output back in until rest is empty). The table grows from 10 to 17 rows, and the repetition gets worse: every loan's member and book are now copied once per genre. 1NF alone doesn't remove duplication.
  2. 2NF. The key of loans_1nf is (loan_id, genre), but the member, book and dates depend on loan_id alone. That's a partial dependency, so those columns move to a table keyed by loan_id. The genre facts turn out to be about the book, not the loan.
  3. 3NF. loan → member_email → member_name and loan → book → author → born are transitive chains. Each link becomes its own table with its own key, which gives back exactly L34's four tables.

The EXCEPT query is the proof that nothing was lost: joining the normalised tables back reproduces the original rows exactly, a lossless decomposition. And the update anomaly is gone: renaming the author changes one row.

Keys, constraints and types

A schema is also the place to write down business rules, so the database enforces them for every program that ever touches the data, including one an AI wrote at 2 a.m.:

$ /usr/bin/sqlite3 library.db < library.sql
$ java --enable-native-access=ALL-UNNAMED -cp sqlite-jdbc-3.53.4.0.jar Constraints.java library.db
FK off (the default): OK, 1 row(s)
FK on: [SQLITE_CONSTRAINT_FOREIGNKEY] A foreign key constraint failed (FOREIGN KEY constraint failed)
UNIQUE: [SQLITE_CONSTRAINT_UNIQUE] A UNIQUE constraint failed (UNIQUE constraint failed: members.email)
CHECK: [SQLITE_CONSTRAINT_CHECK] A CHECK constraint failed (CHECK constraint failed: year BETWEEN 1400 AND 2100)
NOT NULL: [SQLITE_CONSTRAINT_NOTNULL] A NOT NULL constraint failed (NOT NULL constraint failed: books.price_cents)

Both languages print the same five lines. The first one is the trap: a brand-new connection happily stored a loan for a book that doesn't exist, because SQLite's foreign keys are off until each connection turns them on. The pragma docs add a second trap: "This pragma is a no-op within a transaction", so run it right after connecting. Other databases (PostgreSQL, H2) enforce foreign keys always.

  • Surrogate vs natural keys. members.email is a natural key: it's unique in the real world. But emails change, and every loan would have to change with it. So members gets a meaningless surrogate key (id) for references, and UNIQUE keeps the business rule "one member per email". In SQLite, "UNIQUE and PRIMARY KEY constraints are implemented by creating a unique index" (CREATE TABLE docs), which is the sqlite_autoindex_members_1 you'll meet in Part 2.
  • Money is integer cents (price_cents INTEGER), for the same reason as L2 and L32: 0.1 + 0.2 isn't 0.3 in floating point.
  • Dates are ISO-8601 text. "SQLite does not have a storage class set aside for storing dates and/or times" (datatypes); its date functions work on 'YYYY-MM-DD' strings, which also sort correctly as text. PostgreSQL and H2 have real DATE types: use them there.

When to break the rules on purpose

Normalised schemas make writes safe and cheap: each fact has one home. The price is joins on every read. A read-heavy report that runs a 5-table join thousands of times a minute may deserve a denormalised copy: a summary table, a materialised view, or a cache (L31's HTTP caching, and L41 at system scale). The trade-off is always the same: you now own keeping the copy in sync, and every anomaly from the top of this part can come back. Normalise first; denormalise only with a measurement in hand.

What Kotlin does for you.
  • Little that's database-specific: JDBC is the same API in both languages, and the SQL is identical.
  • Extension functions let you add the helper you wish JDBC had: Connection.tryUpdate(label, sql) reads like a method on the connection. Java needs a static helper with the connection as a parameter.
  • use { } closes statements and result sets (L10), and returns a value, so val n = createStatement().use { it.executeUpdate(sql) } is one expression. Java's try-with-resources is a statement, so you declare n inside it.
  • No checked SQLException: Kotlin's main needs no throws clause (L10).

Check

In loans_flat, fixing an author's name in only one of their rows is which anomaly?

The same fact (the author's name) is stored in several rows, so an update can leave them disagreeing. Normalised, it's stored once and updated once.

A genres column holds 'SF,Horror'. Which normal form does that break?

1NF requires atomic values: one value per cell. A list in a string can't be indexed, constrained, or matched exactly; LIKE '%SF%' also found Proto-SF.

loans_2nf stores member_email and member_name in every loan row. What's left to fix?

The key is loan_id; member_name depends on it only through member_email. That chain is a transitive dependency, which 3NF removes by giving members their own table.

Books and genres are many-to-many. How do you store that?

Neither side can hold the other's key once, so the pairs get their own table: book_genres(book_id, genre_id), with the pair as its primary key.

Which column definition stores a price of £10.99 safely?

Integer cents are exact, sum exactly and sort numerically. Floating point can't represent 10.99 exactly (L2), and a text price can't be summed or compared as a number.

Part 2

Indexes as B-trees

~35 min

A database big enough to be slow

Ten loans fit in a CPU cache; nothing is slow. To see indexes matter, the same schema gets 272,000 rows: 2,000 authors, 50,000 books, 20,000 members and 200,000 loans. There's no randomness; every value is arithmetic on the row number, so your database will be byte-for-byte the same as mine:

$ /usr/bin/sqlite3 big.db < genbig.sql      # about a quarter of a second
$ /usr/bin/sqlite3 -header -column big.db "SELECT (SELECT count(*) FROM loans) AS loans, ..."
authors  books  members  loans
-------  -----  -------  ------
2000     50000  20000    200000

A real bug I hit writing this: in SQLite, || binds tighter than %, so '+' || (i * 17) % 1000 || ' days' computes ('+' || i*17) % 1000, and the first run failed with "NOT NULL constraint failed: loans.loaned". Hence the extra parentheses. Every member ends up with exactly 10 loans, and 40,000 loans are still out.

Without an index, every query reads everything

Here's a small timing harness. It asks for one member's loans 200 times (a different member each time) and checks that each answer has 10 rows. Then it adds an index on loans(member_id) and asks 2,000 more times:

About 300× faster, in both languages, for an index that took 24 ms to build. Without it, SQLite reads all 200,000 loans to find 10: O(n). With it, the lookup is O(log n) plus the 10 rows.

What's --enable-native-access=ALL-UNNAMED? sqlite-jdbc loads SQLite's C library through JNI. Without the flag, JDK 26 prints four lines starting "WARNING: A restricted method in java.lang.System has been called" and ending "Restricted methods will be blocked in a future release unless native access is enabled". That's JEP 472, which prepares Java "for a future release that ensures integrity by default by uniformly restricting JNI". The flag says "yes, I meant to".

How an index is shaped

An index is a second copy of some columns, kept sorted, with a pointer back to each row. In SQLite's words, "an index is another table similar to the original … but with the content … stored in front of the rowid and with all rows in content order" (query planner docs). Sorted means binary-searchable (L18). But a sorted array can't absorb inserts cheaply (L16), so databases store it as a B-tree.

A B-tree is the balanced tree L20 promised. Instead of 2 children per node, each node is a page of disk (4,096 bytes here) holding hundreds of sorted keys and hundreds of child pointers. "The tree depth is equal at every position", and it grows logarithmically: "Real world indexes with millions of records have a tree depth of four or five" (Use The Index, Luke, The Search Tree). The leaf pages are chained left to right, "very much like a chain" (The Leaf Nodes), so a range query finds its start once and then walks sideways.

Why fan-out matters. Every level is one page read, and a page read from SSD is ~1,500× a memory access (L22). So the question isn't "how many comparisons", it's "how many pages".

balanced BST (L20)2⌈log₂ 200,000⌉ = 18
B-tree, ~375 keys per pagehundredslog₃₇₅ 200,000 ≈ 2.1 → 3

Every tree, the table included, is 3 levels deep for 200,000 rows. The member index's root has 2 children, each of those has about 265 children, and each leaf holds 375 entries. So a lookup is 3 page reads, where a BST would need 18 node visits scattered across memory.

Tables are B-trees too. SQLite's file format has two kinds: "'Table b-trees' use a 64-bit signed integer key and store all data in the leaves. 'Index b-trees' use arbitrary keys and store no data at all." So the loans table itself is a tree keyed by rowid: that's why SEARCH b USING INTEGER PRIMARY KEY (rowid=?) in a join is fast. An index entry is (member_id, rowid): find the entry in the index, then use the rowid to find the row in the table. (Index B-trees also keep some keys in interior pages, which is why the leaves above hold 199,470 entries, not 200,000.)

Composite indexes and the leftmost prefix

An index can cover several columns: CREATE INDEX idx_books_author_year ON books(author_id, year). It sorts by author_id first, and by year only among rows with the same author, "like the ordering of a telephone directory" (Use The Index, Luke, Concatenated Indexes). A phone book sorted by surname, then first name, finds "Smith, Ada" instantly and every Smith together. It's useless for "everyone called Ada":

So a composite index serves WHERE author_id = ? and WHERE author_id = ? AND year > ?, but not WHERE year > ? on its own: the leftmost prefix rule. Part 3 confirms it with EXPLAIN. A corollary: an index on (member_id, loaned) makes a separate index on member_id alone redundant.

Covering indexes

If every column a query needs is already in the index, SQLite never visits the table: a covering index. SELECT count(*) FROM loans WHERE member_id = 42 only needs the index; SELECT book_id … needs the table too, unless you add book_id to the index. The index-only scan chapter explains when that's worth it.

What indexes cost

Every index is another B-tree that every INSERT, UPDATE and DELETE has to keep sorted, and another few megabytes on disk. Measured:

insert 50k, 0 indexes:    31 ms
insert 50k, 3 indexes:    70 ms
file before: 9.9 MB, after 3 indexes on loans: 18.2 MB
insert 50k, 0 indexes:    29 ms
insert 50k, 3 indexes:    73 ms
file before: 9.9 MB, after 3 indexes on loans: 18.2 MB

(Kotlin first, then Java.) Three indexes made bulk inserts about 2.3–2.5× slower and nearly doubled the file. That's the trade: reads get faster, writes get slower, so index for the queries you actually run, not every column "just in case". The dbstat output above shows where the space went: the date index alone is 3.8 MB, because its keys are 10-character strings.

  1. A function on the column. The index is sorted by email, not by lower(email), so SQLite can only SCAN: every entry, O(n). It scans the index (smaller than the table), but it's still a scan. The fix is an index on the expression itself. Use The Index, Luke calls this case-insensitive search, and it's the most common way AI-written queries lose their index.
  2. LIKE. A prefix pattern ('m42%') is really a range, email >= 'm42' AND email < 'm43', but only when collations line up. SQLite's LIKE optimization rules: "if case_sensitive_like mode is enabled then the column must be indexed using the built-in BINARY collating sequence, or if case_sensitive_like mode is disabled then the column must be indexed using the built-in NOCASE collating sequence." The default LIKE is case-insensitive and our index is BINARY, so: scan. Turn on case_sensitive_like (or index email COLLATE NOCASE) and it becomes a SEARCH. A suffix pattern ('%42@…') can never use a sorted index: there's no "starting point".
  3. Types. SQLite applies the column's affinity to the literal, "If one operand has INTEGER, REAL or NUMERIC affinity and the other operand has TEXT … NUMERIC affinity is applied to the other operand" (datatypes), so member_id = '42' still searches. Wrapping the column in CAST is a function on the column again: scan. Other databases are stricter, and comparing a string column to a number can silently disable an index.
  4. OR across columns. One index can't serve member_id = 42 OR book_id = 7. With an index on each, SQLite runs both searches and merges them (MULTI-INDEX OR).

Hash indexes? Some databases offer them. In PostgreSQL, "Hash indexes store a 32-bit hash code derived from the value of the indexed column. Hence, such indexes can only handle simple equality comparisons" (index types): L19's O(1) lookup, with no ranges and no sorting. B-trees are the default for a reason.

Partial indexes. One more tool for the final: an index can cover only some rows. "A partial index is an index over a subset of the rows of a table" (partial indexes), e.g. CREATE INDEX … ON loans(loaned) WHERE returned IS NULL indexes only the 40,000 open loans.

What Kotlin does for you.
  • fun Connection.exec(sql: String) and Connection.longOf(sql) are one-line extension functions; in Java they're static helpers taking the connection as their first parameter (L9).

Check

An index on loans(member_id) changes WHERE member_id = 42 from…

Without an index, every row is checked. With a B-tree, the lookup descends a few levels (log n with a huge base), then reads the matches.

Why is the B-tree only 3 levels deep for 200,000 rows, when a balanced BST needs 18?

Fan-out. dbstat showed about 375 entries per leaf, so each level multiplies capacity by hundreds instead of 2.

With an index on books(author_id, year), which condition can't use it as a search?

The leftmost prefix rule: the index is sorted by author first, so years on their own are scattered across every leaf.

WHERE lower(email) = ? on a table with UNIQUE(email). What does SQLite do?

The index is sorted by email, not lower(email). The plan said SCAN members USING COVERING INDEX sqlite_autoindex_members_1: every entry, still O(n). An expression index fixes it.

Adding three indexes to the copy of loans did what to 50,000 inserts here?

31 ms became 70 ms: each insert now updates four B-trees instead of one. Indexes trade write speed and disk space for read speed.

Reading EXPLAIN

~25 min

Guessing whether a query uses an index is how slow code ships. Ask the database instead. In SQLite, prefix any statement with EXPLAIN QUERY PLAN (docs):

1. no index
QUERY PLAN
`--SCAN loans
2. with idx_loans_member
QUERY PLAN
`--SEARCH loans USING INDEX idx_loans_member (member_id=?)
3. only needs what the index holds
QUERY PLAN
`--SEARCH loans USING COVERING INDEX idx_loans_member (member_id=?)
4. one member, newest loans first
QUERY PLAN
|--SEARCH loans USING INDEX idx_loans_member (member_id=?)
`--USE TEMP B-TREE FOR ORDER BY
5. same query, composite index
QUERY PLAN
`--SEARCH loans USING COVERING INDEX idx_loans_member_loaned (member_id=?)
6. a join
QUERY PLAN
|--SEARCH l USING INDEX idx_loans_member (member_id=?)
`--SEARCH b USING INTEGER PRIMARY KEY (rowid=?)
You seeIt meansUsually
SCAN loansread every row of the tablebad on a big table, unless you want most rows
SEARCH … USING INDEX x (col=?)descend index x, then fetch matching rows by rowidgood
USING COVERING INDEXthe index alone answers it; the table is never readbest
USE TEMP B-TREE FOR ORDER BYresults are sorted after fetching; the docs say "Using an index is almost always much more efficient than performing a sort"fixable with a composite index
SCAN … USING COVERING INDEXread every entry of an indexstill O(n), just smaller

Joins read top to bottom. Plan 6 is a nested loop: the first line is the outer loop (search loans by member, 10 rows) and the second is the inner loop, run once per outer row (look up each book by its integer primary key). The planner picked that order because starting from the 10 matching loans is far cheaper than starting from 50,000 books.

A warning from the docs worth keeping: "The data returned by the EXPLAIN QUERY PLAN command is intended for interactive debugging only. The output format may change between SQLite releases." Read it, test with it, but don't parse it in production code.

The workflow: explain, index, explain again, time

Three realistic queries, three different endings.

1. A member's loans, newest first. Plans 4 and 5 above: idx_loans_member found the 10 rows but still needed a temporary B-tree to sort them. A composite (member_id, loaned) index stores each member's loans already in date order, so the sort disappears, and because id is the rowid, it's covering too.

2. An author's books in a year range.

author only
QUERY PLAN
`--SEARCH books USING INDEX idx_books_author_year (author_id=?)
author and year range
QUERY PLAN
`--SEARCH books USING INDEX idx_books_author_year (author_id=? AND year>? AND year<?)
year range only
QUERY PLAN
`--SCAN books

Exactly the leftmost-prefix rule from the widget: both columns are used when the author is fixed, and nothing helps a year range on its own.

3. Overdue loans (still out after 21 days, as of 2026-10-01). This one is a trap:

The index was used, and the query got slower: about 4 ms became 9 ms. 39,200 rows match, 20% of the table. Each one found through the index costs a separate lookup into the table B-tree, while the scan reads the table's pages once, in order. Use The Index, Luke has a whole section on this, slow indexes. Indexes win when they're selective: a few rows out of many. For "a fifth of the table", a scan is often the right plan. The final shows a better fix when the overdue set is small.

Plans from code, and in H2

The same check works through JDBC. EXPLAIN QUERY PLAN returns rows with a detail column. H2's EXPLAIN returns the query rewritten, with the access path in a comment (H2 commands):

SQLite, no index:   [SCAN books]
SQLite, with index: [SEARCH books USING INDEX idx_books_author_year (author_id=? AND year>?)]
H2, no index:
SELECT
    "TITLE"
FROM "PUBLIC"."BOOKS"
    /* PUBLIC.BOOKS.tableScan */
WHERE ("AUTHOR_ID" = 7)
    AND ("year" > 2000)
H2, with index:
SELECT
    "TITLE"
FROM "PUBLIC"."BOOKS"
    /* PUBLIC.IDX_BOOKS_AUTHOR_YEAR: AUTHOR_ID = 7
        AND "year" > 2000
     */
WHERE ("AUTHOR_ID" = 7)
    AND ("year" > 2000)

Both languages print the same thing. H2's tableScan is SQLite's SCAN; PUBLIC.IDX_BOOKS_AUTHOR_YEAR: AUTHOR_ID = 7 AND "year" > 2000 is SQLite's SEARCH … (author_id=? AND year>?). Same idea, different dialect.

Dialect honesty. Why is "year" quoted? The first version of Plans used the same CREATE TABLE as SQLite, and H2 refused it:

Exception in thread "main" org.h2.jdbc.JdbcSQLSyntaxErrorException: Syntax error in SQL statement "CREATE TABLE books(id INT PRIMARY KEY, title VARCHAR(100), author_id INT, [*]year INT)"; expected "identifier"; SQL statement:
CREATE TABLE books(id INT PRIMARY KEY, title VARCHAR(100), author_id INT, year INT) [42001-252]
	at org.h2.message.DbException.getJdbcSQLException(DbException.java:514)

YEAR is a reserved word in every SQL standard since SQL-92, and H2 enforces that. Its keyword list says keywords "can't be used as identifiers … unless they are quoted". SQLite is lenient and accepts it. H2 also offers SET NON_KEYWORDS, but its docs say "Use quoted identifiers instead of this setting if possible." Lesson: a schema that works in one database isn't automatically portable, and reserved words are the first thing to break.

When the planner guesses wrong

The planner chooses between indexes using statistics. ANALYZE "gathers statistics about tables and indices and stores the collected information in internal tables of the database where the query optimizer can access the information" (ANALYZE). It doesn't always help:

QUERY PLAN
`--SEARCH loans USING INDEX idx_loans_member (member_id>?)
QUERY PLAN
`--SEARCH loans USING INDEX idx_loans_member (member_id>?)
idx_loans_loaned|200000 200
idx_loans_member|200000 10
1200
Run Time: real 0.039 user 0.037221 sys 0.001693
1200
Run Time: real 0.001 user 0.000318 sys 0.000034
QUERY PLAN
`--SEARCH loans USING INDEX idx_loans_loaned (loaned>?)

Only 1,200 loans are after 2026-09-20, but nearly all 200,000 have member_id > 100. The planner picked the member index both before and after ANALYZE, and took 39 ms. Forcing the date index took 0.3 ms: over 100× faster. Why didn't the statistics help? sqlite_stat1 only records the average rows per key (200000 10: about 10 rows per member). It has no idea how dates are distributed, so a range is a guess. Histograms live in sqlite_stat4, which "is only created and is only used if SQLite is compiled with SQLITE_ENABLE_STAT4" (file format), and the macOS build isn't (PRAGMA compile_options doesn't list it).

The unary + in +member_id > 100 is a no-op that stops a term from using an index. SQLite documents it as a last resort: "Disqualifying WHERE clause terms this way is not recommended. This is a work-around." (optimizer overview). Don't reach for INDEXED BY either; the docs say it "is not intended for use in tuning the performance of a query" (INDEXED BY). The honest takeaway: the planner is right most of the time, wrong some of the time, and the only way to know is to measure.

Bridge. Android's Room declares indexes with @Index on an entity, and JPA has its own @Index annotation (L25: annotations read by a framework). Both generate exactly the CREATE INDEX statements from this lesson. In production, databases can log every query slower than a threshold (a slow-query log), and that log plus EXPLAIN is how real performance work starts.

What Kotlin does for you.
  • buildList { while (rs.next()) add(rs.getString("detail")) } builds a read-only list in one expression. Java declares a mutable ArrayList, fills it, and returns it.
  • String templates ("EXPLAIN QUERY PLAN $sql") replace concatenation, and \"year\" escapes work the same in both languages.
  • One function per database (sqlitePlan, h2Plan) with expression bodies: = conn.createStatement().use { … }. Java needs explicit returns inside try blocks.

Both print the same two lines. Where it lives: in a test (L11), against a test database built from your real schema and pinned to the SQLite version you ship. Check

A plan says SEARCH loans USING COVERING INDEX idx (member_id=?). What's skipped?

Covering means every needed column is in the index, so SQLite never follows the rowid into the table B-tree.

WHERE member_id = ? ORDER BY loaned shows USE TEMP B-TREE FOR ORDER BY. Which index removes the sort?

Equality on member_id first, then loaned in order within that member: the index hands rows over already sorted. Reversing the columns breaks the leftmost prefix.

An index made the 39,200-row overdue query slower. Why?

The index was used. But a fifth of the table matched, and each match meant a separate jump into the table B-tree, while a scan reads the table's pages once, in order. Indexes win when they're selective.

ANALYZE didn't fix the bad plan for loaned > X AND member_id > 100. Why?

sqlite_stat1 stores average rows per key, which can't describe a date range. Histograms need sqlite_stat4, which this SQLite build doesn't compile in.

According to the SQLite docs, INDEXED BY is meant for…

"The INDEXED BY clause is not intended for use in tuning the performance of a query." It makes a query fail if its index disappears: a regression check.

Kotlin and Java agree to within a few percent. Notes on the less obvious ones:

  • Q2 is the selectivity lesson. 6,000 rows match. A plain partial index on loaned alone only got 4.1 ms down to 3.1 ms, because each of the 6,000 rows still needed a table lookup. Adding member_id to the partial index took it to 0.55 ms. A full (returned, loaned, member_id) index was just as fast (0.52 ms) but took 1,519 pages against the partial index's 217: about 7× the disk, spent indexing 160,000 returned loans this query never wants. (SQLite's plan says USING INDEX rather than COVERING INDEX for the partial index, but the timing matches the covering version.)
  • Q5 still sorts (two temp B-trees). That's honest: counting per book and ranking by count can't come pre-sorted from any index. The win is reading the 6,200 index entries for January instead of 200,000 rows.
  • Q1's index also makes a plain loans(member_id) index redundant: leftmost prefix.

Wrap-up

Exit quiz, recall card, sources

~5 min

The loans table doubles from 200,000 to 400,000 rows. An indexed lookup by member_id gets… (L16)

O(log n) with a base in the hundreds: 400,000 keys still fit in 3 levels. Doubling n adds almost nothing, which is the whole point of the structure.

A B-tree page holds k sorted keys. Finding the right child inside one page costs… (L18)

The keys in a page are sorted, so binary search applies. The expensive part is the page read, which is why the number of levels matters more than the search inside each page.

GET /members?email=… from L32's API takes 800 µs. Where's the fix most likely? (L32)

Q4 in the final: the lookup scanned 20,000 members until it had an index matching the query's lower(email). Measure first, and the database is usually where the time goes.

A query concatenates user input into WHERE email = '…'. Adding an index on email fixes… (L33)

Indexes change how fast a query runs, never what it means. SQL injection is fixed by PreparedStatement and ? placeholders (L33, and L36 next).
