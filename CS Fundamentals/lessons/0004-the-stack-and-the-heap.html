Part 1

The call stack and frames

~28 min

While your program runs, the JVM keeps track of which function is running and who called it. It does this with the call stack, or just the stack. Every call creates a frame: a small block of memory holding that call's parameters and local variables, plus where to resume when it returns. The JVM spec puts it simply: "A new frame is created each time a method is invoked. A frame is destroyed when its method invocation completes" (JVM Spec §2.6).

Frames are stacked like plates. A call pushes a frame on top, and a return pops it off. Only the top frame is running, and when it finishes, control goes back to the one underneath. This "last in, first out" rule is why it's called a stack. Each thread gets its own private stack (JVM Spec §2.5.2), but threads wait until L26.

Step through it. Press Next ▶, or focus the box and use the ← → arrow keys. Watch frames appear and disappear, and switch between the Kotlin and Java listings with the tabs. The memory picture is the same for both.

A stack trace is a photo of the stack

When an exception escapes, the JVM prints the stack as it was at that moment, top frame first. That's why the first at … line is where the problem happened, and the lines below it are who called whom:

Exception in thread "main" java.lang.IllegalStateException: boom
	at TraceKt.c(Trace.kt:2)
	at TraceKt.b(Trace.kt:5)
	at TraceKt.a(Trace.kt:7)
	at TraceKt.main(Trace.kt:10)
	at TraceKt.main(Trace.kt)
Exception in thread "main" java.lang.IllegalStateException: boom
	at Trace.c(Trace.java:3)
	at Trace.b(Trace.java:6)
	at Trace.a(Trace.java:8)
	at Trace.main(Trace.java:11)

Read it bottom-up for the story ("main called a, which called b, which called c, which threw") and top-down to find the culprit. Notice TraceKt: the class Kotlin generated for you, as in L1. The extra last main line is the bridge Kotlin generates from the JVM's main(String[]) to your main(). L10 covers exceptions properly.

The stack is small, and it runs out

The stack is a fixed-size region. A function that calls itself forever keeps pushing frames until there's no room left. The spec says that when "the computation in a thread requires a larger Java Virtual Machine stack than is permitted, the Java Virtual Machine throws a StackOverflowError" (JVM Spec §2.5.2):

stack overflowed at depth 44509     ← Kotlin, on my machine
stack overflowed at depth 47477     ← Java, on my machine
stack overflowed at depth 440931    ← java -Xss8m Dive.java  (a bigger stack)

Your numbers will differ. They depend on the default stack size and how big each frame is. -Xss "sets the thread stack size" (java launcher docs), and that's the only reason the third run got deeper. Catching StackOverflowError here is just for the demo. In real code it means "fix the recursion", usually by adding the missing base case. Recursion gets a full lesson in L18.

Practice · A loop needs only one frame

sumTo(n) adds 1 + 2 + … + n. It's correct for small n, but every call pushes another frame, so a big n overflows the stack. A negative n never reaches the base case at all.

  • Rewrite sumTo with a loop, so it runs in a single frame. A negative or zero n gives 0.
  • Watch the size of the answer: sumTo(100_000) is about 5 billion.
// Correct for small n, but each call waits in its own frame for the next one to return.
fun sumTo(n: Int): Long =
    if (n == 0) 0 else n + sumTo(n - 1)

Hint 1 of 3

The recursion is the problem: sumTo(1_000_000) needs a million frames on the stack at once. A for loop does the same additions inside one frame.

Hint 2 of 3

Keep a running total in a local variable and add each i from 1 to n. For a negative n, the range 1..n is simply empty.

Hint 3 of 3

Start the total at 0L, not 0: an Int total silently wraps past 2,147,483,647 (L2). In Java, that's long total = 0; and for (int i = 1; i <= n; i++).

Final answer

Why it works. The recursive version keeps every unfinished call on the stack until the base case returns, so its depth grows with n. The loop never calls anything, so it uses one frame with two locals, whatever n is. The negative case is fixed for free: 1..n is empty, so the loop body never runs.

Common mistake. var total = 0. It infers Int, which overflows silently past about 2.1 billion, and converting to Long at the end is too late: the wrong number is already there.

Check

When square returns, its frame…

Returning destroys the frame along with its locals. The next call to square gets a brand-new frame.

  1. Frames never move to the heap. A frame lives on the stack and disappears when its call returns.
  2. Returning pops the top frame, and its parameters and locals go with it.
  3. Frames don't wait for main: each one is destroyed as soon as its own call completes.
  4. The caller keeps its own frame. Only the return value is handed back to it.

In Trace's stack trace, which frame is listed first?

A trace lists the stack top-down, so the frame that threw comes first.

  1. main is at the bottom of the stack, so it's listed last (Kotlin adds one bridge line below it).
  2. a was called straight from main, so it's near the bottom of the stack.
  3. b called c, so it's one frame lower: the second line, not the first.
  4. c was the top frame when the exception was thrown, so the trace starts there.

Recursion with no base case eventually fails with…

Every call pushes a frame and none ever pops, so the stack runs out of room.

  1. That's the heap running out of room for live objects, not the stack running out of frames.
  2. Nothing here is null. The recursion fails because frames pile up.
  3. Each call pushes a frame and none returns, until the fixed-size stack is full.
  4. That's for arithmetic errors, such as dividing an integer by zero.

Recursion with a local variable. What does this print?

fun countdown(n: Int) {
    if (n == 0) return
    val label = "n=$n"
    countdown(n - 1)
    print("$label ")
}

fun main() {
    countdown(3)
    println()
}

Each call prints only after its inner call has returned, so the deepest frame (n=1) prints first and the first call (n=3) prints last. Each frame keeps its own label, so no call overwrites another's.

  1. That order needs the print before the recursive call. Here each frame prints only after the deeper call returns.
  2. Each call has its own frame, so each has its own label. A deeper call can't overwrite it.
  3. The n == 0 call returns before it creates a label, so it prints nothing.
  4. Frames pop newest first: the n=1 frame finishes first, and the first call, n=3, finishes last.
Part 2

The heap and references

~33 min

Frames are short-lived and small. Objects (class instances, arrays, lists, strings) live somewhere else: the heap, a large area "shared among all Java Virtual Machine threads… from which memory for all class instances and arrays is allocated" (JVM Spec §2.5.3).

That gives you the single most useful mental model in this course:

A variable of a primitive type holds the value itself. A variable of an object type holds a reference: an arrow pointing to an object on the heap. Assigning, passing or storing that variable copies the arrow, never the object.

The spec describes this model, and it's the right way to reason about your code. Behind the scenes, the JIT compiler (L23) may optimise some short-lived objects away, but your program can't tell the difference.

x=1 y=99
a.count=99 b.count=99
a.count=99 c.count=5

Two different operations look almost identical in code, so learn to tell them apart on sight:

CodeWhat changesWho sees it
b.count = 99Mutates the object at the end of the arroweveryone with an arrow to that object
c = Counter(5)Re-points the variable to a different objectonly that one variable

null fits the picture too: it's a reference with no arrow. Calling a method through it has nowhere to go, which is exactly what a NullPointerException is (L3).

Objects outlive the frames that made them

11

fresh lived in makeCounter's frame and died with it, but the object is on the heap and was handed back by reference, so it lives on. An object stays alive as long as some reference can still reach it. Once nothing can, it's garbage. "Heap storage for objects is reclaimed by an automatic storage management system (known as a garbage collector); objects are never explicitly deallocated" (JVM Spec §2.5.3). L24 is all about the garbage collector.

The heap can run out too

If you keep objects reachable forever, for example by stuffing them into a list you never clear, the garbage collector can't free anything. Here's that deliberately, with the heap capped at 64 MB using -Xmx, which "specifies the maximum size… of the heap" (java launcher docs):

$ java -Xmx64m Hoard.java
holding 10 MB
...
holding 50 MB
Exception in thread "main" java.lang.OutOfMemoryError: Java heap space

Compare the two failures. StackOverflowError means too many frames, usually runaway recursion. OutOfMemoryError means too many live objects, usually something holding references it shouldn't.

What Kotlin does for you (and doesn't). Both languages share the JVM's memory model exactly, so stack, heap and references work identically. What Kotlin hides is the primitive/boxed split from L2: you write Int and the compiler picks a primitive slot in the frame or a boxed object on the heap. Also notice that Kotlin needs no new keyword. Counter(1) is a constructor call, but you still get a new heap object every time, just as with Java's new Counter(1).

counters.map { Counter(it.count) } builds a new list of new objects: map runs the block once per element and collects the results (blocks like this are lambdas, L14). In Java, loop over the list and add(new Counter(c.count)) to a new ArrayList<>().

Final answer

Why it works. map builds a new list, and its block creates a new Counter for every element, copying only the Int inside. Copying an Int copies the number, so nothing in the copy shares an object with the originals.

Common mistake. counters.toList() (Java: new ArrayList<>(counters)). It passes the "adding to the original list" check, because the list itself is new, but fails when an original counter changes: both lists hold arrows to the same objects. Check

After val a = Counter(1) and then val b = a, how many Counter objects exist?

Assignment copies the reference. Only a constructor call creates an object.

  1. Counter(1) is a constructor call, so at least one object exists.
  2. One constructor call makes one object. b = a copies only the arrow.
  3. val b = a creates nothing new. It's a second reference to the same object.
  4. Only constructor calls create objects, and there's just one here.

Which of these lives directly inside a stack frame?

A frame holds primitive locals and references. Everything an object holds lives on the heap.

  1. A primitive local sits directly in the frame, as the number itself.
  2. Objects live on the heap. The frame holds only a reference to it.
  3. A list and its elements are heap objects. The frame holds only a reference to the list.
  4. A String is an object, so its characters are on the heap.

makeCounter returned a reference, then its frame was popped. The object…

Reachability decides an object's lifetime, not the frame that created it.

  1. The JVM has no explicit delete. The garbage collector frees an object only once nothing can reach it.
  2. Objects never move into frames. main's frame now holds a reference to the same heap object.
  3. Returning copies the reference to the caller. Nothing sets it to null.
  4. kept still references it, so it stays alive however many frames pop.

A list keeps growing with objects that are all still reachable. You'll eventually get…

The heap is full of objects the garbage collector isn't allowed to free.

  1. Every object stays reachable, so the garbage collector can't free any, and the heap fills up.
  2. That's too many frames. Adding to a list in a loop doesn't make the stack any deeper.
  3. That signals a call made when an object is in the wrong state. Nothing here checks state.
  4. That's reading past the end of a list, not running out of memory.

Part 3

Always pass-by-value

~28 min

When you call f(x), the new frame's parameter is initialised with a copy of x's value. For a primitive that's a copy of the number. For an object that's a copy of the reference, the arrow. Java is always pass-by-value. It never passes "the variable itself". dev.java says it outright: the object reference "was passed in by value and cannot change" (dev.java: Passing reference data type arguments). Kotlin on the JVM works the same way.

Two consequences follow, and between them they explain a whole family of bugs:

  • A function can mutate an object you pass it, because its copy of the arrow points at the same object.
  • A function can't re-point your variable. Reassigning its parameter only moves its own copy.

after bump: 6
after replace: 6
n=5
after bump: 6

Step through the Java version. It's the clearer one here, because Java lets you reassign a parameter. Watch the arrows in bump and replace:

What Kotlin does for you. Kotlin parameters are read-only (L3), so reassigning a parameter, like Java's confusing c = new Counter(100), simply won't compile:

            return x.count;
        });
        check("topThree finds the three highest", List.of(9, 7, 5), () -> topThree(new ArrayList<>(List.of(5, 1, 9, 7, 3))));
        check("topThree leaves the caller's list alone", List.of(5, 1, 9, 7, 3), () -> {
            List<Integer> scores = new ArrayList<>(List.of(5, 1, 9, 7, 3));
            topThree(scores);
            return scores;
        });
        check("fewer than three scores is fine", List.of(8, 4), () -> topThree(new ArrayList<>(List.of(4, 8))));
    }

    interface Check { Object get() throws Exception; }

    static void check(String name, Object expected, Check actual) {
        try {
            Object got = actual.get();
            System.out.println(Objects.equals(expected, got) ? "PASS " + name : "FAIL " + name + ": expected <" + expected + "> but was <" + got + ">");
        } catch (Exception e) {
            System.out.println("FAIL " + name + ": threw " + e);
        }
    }
    // END CHECKS
}
Hint 1 of 3

swapCounts is the classic three-line swap with a temporary variable, applied to a.count and b.count. For topThree, ask: which object does scores point at?

Hint 2 of 3

scores is a copy of the caller's arrow, so sortDescending() reorders the caller's own list. Sort a copy instead: L3's sorted() returns a new list, and sortedDescending() does the same, highest first.

Hint 3 of 3

scores.sortedDescending().take(3). Then change the parameter to List<Int>: the compiler would now reject sortDescending(). In Java, sort new ArrayList<>(scores), and beware: subList returns a view of the list it came from, not a copy.

Final answer

Why it works. A parameter is a copy of the caller's arrow. That's exactly what makes swapCounts work: it changes the objects, which the caller shares. It's also why the old topThree broke the caller's list: sortDescending() sorted the one list both arrows point at. sortedDescending() sorts a new list instead. The tmp swap survives swapCounts(x, x), because it only ever writes values it saved first.

Common mistake. val sorted = scores, then sorting sorted. That copies the arrow, not the list, so the caller's list is reordered anyway. The arithmetic swap (a.count = a.count + b.count…) fails too: when a and b are the same object, it sets the count to 0.

Check

Java's swap(p, q) on two ints…

It swaps its own copies, and they vanish when the frame pops.

  1. swap gets copies of the two numbers, so only its own copies change places.
  2. It swaps its parameter copies, and they vanish when its frame pops.
  3. It compiles: Java lets you reassign parameters. Kotlin is the language that forbids it.
  4. Nothing fails. It runs normally and has no effect on the caller.

bump(counter) changes counter.count for the caller because…

It's a copied reference, not a reference to your variable. That's the precise difference from true pass-by-reference.

  1. Java passes everything by value. For an object, the value that's copied is the reference.
  2. bump returns nothing. The change happens through the shared object.
  3. The parameter's copy of the arrow leads to the caller's object, so changes to that object stick.
  4. Each call gets its own frame. The parameter and the caller's variable just point at one object.

Kotlin: fun f(n: Int) { n = 2 }

Kotlin parameters are vals: "'val' cannot be reassigned."

  1. Kotlin parameters are read-only, so assigning to n is rejected.
  2. Nothing gets to run: the compiler stops it first.
  3. Even in Java, reassigning a parameter changes only the function's copy, never the caller's variable.
  4. Parameters are vals, and the compiler reports "'val' cannot be reassigned."

Java. Mutate, re-point, mutate again. What does this print?

public class Tweak {
    static class Counter {
        int count;
        Counter(int count) { this.count = count; }
    }

    static void tweak(Counter c) {
        c.count = 2;
        c = new Counter(3);
        c.count = 4;
    }

    public static void main(String[] args) {
        Counter k = new Counter(1);
        tweak(k);
        System.out.println(k.count);
    }
}

c.count = 2 changes the caller's object through the copied arrow. Then c is re-pointed at a new object, so c.count = 4 changes only that one, and it's unreachable once the frame pops.

  1. Objects aren't copied when they're passed. c points at k's object, so the first line changes it.
  2. Only the first line reaches k's object. After re-pointing, c leads to a different one.
  3. Re-pointing c never changes k, and the new object was changed to 4 straight after anyway.
  4. That's pass-by-reference thinking. Re-pointing c moves only the parameter's copy of the arrow.

Stretch: Integer is an object type, so the parameter gets a copy of an arrow. What does this print?

public class Inc {
    static void inc(Integer i) {
        i++;
    }

    public static void main(String[] args) {
        Integer x = 5;
        inc(x);
        System.out.println(x);
    }
}

An Integer object can never change. i++ unboxes 5, adds 1, and boxes the result as a different Integer, then points the local i at it. That's a re-point, not a mutation, which is why a swap with Integer parameters can't work either.

  1. i++ re-points the parameter at a new Integer. The caller's x still points at 5.
  2. That would need i++ to change the object x points at, but Integer objects are immutable.
  3. ++ works on an Integer variable: Java unboxes it, adds 1 and boxes the result (L2).
  4. Nothing is null and nothing goes out of range, so it runs normally.

Exit quiz, recall card, sources

~5 min

Which one is not stored on the heap?

A local primitive lives in its frame. Arrays are objects too, even arrays of int.

  1. An ArrayList is an object, so it lives on the heap.
  2. Every Counter object lives on the heap, wherever its references are stored.
  3. A local primitive sits directly in its method's frame on the stack.
  4. Arrays are objects, even arrays of int, so they live on the heap.

java -Xss8m changes the size of…

-Xss is the stack size and -Xmx is the maximum heap.

  1. The heap is sized by -Xmx (maximum) and -Xms (initial).
  2. -Xss has nothing to do with strings. It sets how deep a thread's stack can grow.
  3. The code cache, where the JIT keeps compiled code, has its own flags.
  4. -Xss sets the thread stack size, so deeper chains of calls fit.

val m = mutableMapOf<String, Int>(). Can you add entries to m?

val fixes the arrow, not the object at the end of it. L5 is all about this.

  1. val stops m being reassigned. The map object itself is still mutable.
  2. m can't point anywhere else, but the MutableMap it points at accepts new entries.
  3. var would let you re-point m. Adding entries doesn't need that.
  4. A map from mutableMapOf accepts brand-new keys, not just updates.
