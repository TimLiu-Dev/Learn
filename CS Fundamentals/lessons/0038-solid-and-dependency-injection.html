Part 1

SOLID, on code you've already written

~35 min

SOLID is a mnemonic for five object-oriented design principles that Robert C. Martin collected around 2000, most famously in his paper "Design Principles and Design Patterns". Some are older: the open-closed principle is Bertrand Meyer's (Object-Oriented Software Construction, 1988), and the substitution principle is Barbara Liskov's. Treat them as heuristics: each names a kind of pain and a way out of it. None of them is a law, and every one of them can be over-applied. For each, you'll see the pain on course code, the fix, and when the fix isn't worth it.

LetterPrincipleOne line
SSingle responsibilityGather together what changes for the same reason; split what changes for different reasons.
OOpen-closedAdd new behaviour by adding code, not by editing code that works.
LLiskov substitutionA subtype must keep every promise its supertype makes.
IInterface segregationDon't make clients depend on methods they don't use.
DDependency inversionPolicy shouldn't depend on detail; both should depend on an abstraction.

S: single responsibility

Martin's own later wording is the clearest: "Gather together the things that change for the same reasons. Separate those things that change for different reasons." He adds: "This principle is about people" (The Single Responsibility Principle, 2014). A "responsibility" isn't "does one thing". It's "answers to one group of people who might ask for a change".

L32's books handler answers to four groups. The front-end team owns the JSON shape. The librarians own the rules (titles can't be blank, years must be plausible). You own the storage, and it's about to move to SQLite. The API designers own the routes. Here's a shrunken version, without the HTTP server, before and after:

POST /books   -> 201 {"id":1,"title":"Dune","year":1965}
POST /books   -> 400 title must not be blank
POST /books   -> 400 year must be 1450..2100
GET /books/1  -> 200 {"id":1,"title":"Dune","year":1965}
GET /books/7  -> 404

Both languages print exactly this, and there's no DIFFERENT marker on any line: the refactored handler answers every request the way the original did. Now each change request lands in one place. "Years before 1450 are fine for manuscripts" touches only BookRules. "Use book_title in the JSON" touches only BookJson. "Store books in SQLite" touches only BookStore.

When it's overkill. This split is worth it because the four parts really do change for different people at different times. Splitting a 20-line script into four classes "for SRP" gives you four shallow modules (L37) and more reading, not less. Wait until you can name the actors.

O: open-closed

Meyer's slogan: a module should be open for extension, but closed for modification. You add behaviour by adding code, and the code that already works stays untouched. L8's notifier was already built this way. Broadcaster depends on the Notifier interface, so a Slack channel added months later is a new class, and nothing else changes:

interface, three channels:
  email to ada: Your reserved book is ready
  sms to ada: Your reserved boo...
  slack #library: @ada Your reserved book is ready
sealed, two operations:
  email costs 0 cents
  sms (max 160 chars) costs 5 cents

The second half is the opposite trade-off, and you met it in L7. A sealed type makes adding a new operation easy: describe is one new function, and no class was edited. But adding a new case means editing every when/switch, and the compiler tells you exactly where:

OcpNewCase.kt:8:34: error: 'when' expression must be exhaustive. Add the 'is Slack' branch or an 'else' branch.
fun costCents(c: Channel): Int = when (c) {
                                 ^^^^
OcpNewCase.java:9: error: the switch expression does not cover all possible input values
        return switch (c) {
               ^
1 error

This tension has a name, the expression problem (Philip Wadler's term, from 1998). Classes behind an interface make new cases cheap and new operations expensive: every class needs the new method. Sealed types plus when flip it. Neither is "the OCP way". Ask which kind of change you expect more of. New payment providers? Use an interface. A fixed set of shapes, each needing many new calculations? A sealed type, with the Kotlin docs' promise that "a when expression, used with a sealed class, allows the Kotlin compiler to check exhaustively that all possible cases are covered" (Kotlin: Sealed classes).

L: Liskov substitution

Liskov and Wing's 1994 paper "A Behavioral Notion of Subtyping" (PDF) makes this precise. Paraphrased: anything you can prove about objects of a type should stay true for objects of any of its subtypes. In code terms, a function written against the supertype must keep working when you hand it a subtype. The compiler checks method names and types. It can't check promises.

You've already been bitten by this. In L5, List.of(…) returned a List you couldn't add to. Java's List interface promises add, but its docs allow an escape: add "Throws: UnsupportedOperationException - if the add operation is not supported by this list", and the List.of lists "are unmodifiable. Elements cannot be added, removed, or replaced" (List). Kotlin made a different design choice:

mutable list:   [sci-fi, new, unread]
cast loophole:  java.lang.UnsupportedOperationException
ArrayList:      [sci-fi, new, unread]
List12: java.lang.UnsupportedOperationException
UnmodifiableRandomAccessList: java.lang.UnsupportedOperationException

Java compiles both calls, because both lists are Lists, and they fail when they run. Kotlin splits the type in two: "A read-only interface that provides operations for accessing collection elements" and "A mutable interface that extends the corresponding read-only interface with write operations" (Kotlin: Collections overview). A List never promised add, so passing one where a MutableList is needed is a compile error:

err/LspReadOnly.kt:5:26: error: argument type mismatch: actual type is 'List<String>', but 'MutableList<String>' was expected.
fun main() = addDefaults(listOf("sci-fi"))
                         ^^^^^^^^^^^^^^^^

Kotlin isn't airtight, though. Kotlin's lists are Java's lists at run time, so the explicit cast as MutableList<String> compiled without a warning and failed at run time. Casts are you overruling the type system; that's on you.

The textbook case: a square is not a substitutable rectangle. In geometry, a square is a rectangle. In code, a mutable Rectangle promises that setting the width leaves the height alone, and a Square can't keep that promise. The best way to make a promise checkable is a test written once against the supertype, then run against every subtype:

(Java's RectangleTest is the same three lines as SquareTest, returning new Shapes.Rectangle(width, height).) Run in a Gradle project like L11's:

The fix isn't a cleverer Square. Either drop the inheritance (both implement a read-only Shape with an area), or make the shapes immutable, so there's no setter whose promise a square could break. This "contract test" pattern comes back in Part 3, where it keeps a fake honest.

I: interface segregation

The idea: no client should be forced to depend on methods it doesn't use. The pain shows up as soon as you write a test. Here, an overdue-reminder emailer needs one method from a seven-method library interface. Its fake still has to implement all seven:

before: [To Ada: please return Dune]
after:  [To Ada: please return Dune]

Same behaviour; very different cost. After the split, OverdueEmailer depends on OverdueReport alone. Its fake is one lambda, and a change to exportCsv can never force it to recompile or change. The real library class can still implement all three role interfaces at once. ISP is about what each client sees, not about splitting the implementation.

D: dependency inversion

Martin's two-part rule: high-level modules shouldn't depend on low-level modules, and both should depend on abstractions. The policy here (the lending rules: at most three open loans) is the thing the library actually cares about. SQLite is a detail. In the "before" code the arrow points from policy to detail, so the rules can't run without a database. Flip through the views:

before, SQLite     member 1: false  member 2: true
after,  SQLite     member 1: false  member 2: true
after,  in-memory  member 1: false  member 2: true

One rule, three wirings, identical answers. Member 1 has three open loans; member 2 has one (their second loan was returned). Notice who owns the interface: LoanStore has exactly the method the rules need, named in the rules' language, not a general-purpose "database" interface. That ownership is what "inversion" means.

Balance: when SOLID hurts

Each principle adds structure, and structure has a price. Ousterhout's warning about "classitis", lots of small classes and interfaces that each do little (A Philosophy of Software Design, ch. 4), is aimed squarely at SOLID taken too far. So is YAGNI: "Yagni originally is an acronym that stands for 'You Aren't Gonna Need It'", and Fowler's argument is that "while we may now think we need this presumptive feature, it's likely that we will be wrong" (Fowler: Yagni). An interface with exactly one implementation and no test fake is usually just indirection.

PrincipleSmell it fixesCost of overdoing it
SRPOne class edited for unrelated reasons; merge conflictsMany shallow classes; logic scattered
OCPEvery new variant means editing a big if/whenPlug-in points nobody ever plugs into
LSPSubclasses that throw "not supported" or need is checksRarely over-applied; mostly avoided by preferring composition (L8)
ISPFakes full of TODO(); recompiles for unrelated changesDozens of one-method interfaces to hunt through
DIPPolicy you can't run without a database, network or clockAn interface per class "just in case"
What Kotlin does for you.
  • Read-only vs mutable collection types. List doesn't promise add, so Java's UnsupportedOperationException substitution trap becomes a compile error.
  • fun interface turns a one-method role interface into something a test can fake with a lambda (L14). Java's @FunctionalInterface does the same for Java interfaces.
  • Classes are final by default (L8). You can't subclass a class whose author didn't plan for it with open, which avoids many substitution problems before they start.
  • Exhaustive when on sealed types: the compiler lists every place a new case must be handled. Java 21's pattern-matching switch does this too, as long as you leave out default.
  • object gives you stateless pieces like BookParser without Java's private constructor and static methods.

Part 2

Dependency injection by hand

~25 min

Dependency inversion says what to depend on: an abstraction. Dependency injection says how the concrete thing arrives: someone else creates it and hands it in. Fowler named the pattern in 2004, in an article written to cut through the "inversion of control" jargon of the frameworks of the day (Inversion of Control Containers and the Dependency Injection pattern). Spring and Hilt are this idea, automated. First, the idea without any framework.

The problem: a class that reaches out

Here's a lending service written the way AI assistants often write it. It opens its own database file and asks the operating system for today's date:

today, per the system clock: 2026-10-21
member 1 may borrow: true   (expected true)
the same check flips to false from 2026-10-25 on, with no code change

That "test" passed on the day I ran it. Run it on 25 October and it fails, with no code change: the loan from 10 October is then more than 14 days old. It also writes a real file in your temp folder, so two copies running at once share one database. Neither problem is visible in the class's constructor. LendingService() takes no arguments and looks self-contained. Its dependencies are hidden inside.

Constructor injection and the composition root

The fix is to ask for dependencies instead of fetching them. The service takes a LoanStore and a java.time.Clock. Clock exists for exactly this: "The primary purpose of this abstraction is to allow alternate clocks to be plugged in as and when required", and Clock.fixed "Obtains a clock that always returns the same instant… The main use case for this is in testing, where the fixed clock ensures tests are not dependent on the current clock" (Clock).

production wiring, today 2026-10-21: member 1 may borrow = true
test wiring, fixed 2026-10-30: member 1 may borrow = false
test wiring, fixed 2026-10-24: member 1 may borrow = true

main is the composition root: the one place that names concrete classes and connects them. It's at the edge of the program, and nothing inside the program calls it. The test lines show the payoff. The same LendingService answers questions about 24 and 30 October today, and will give the same answers next year. The 24th is the last day the loan isn't overdue; the 30th is well past it.

A Kotlin shortcut worth being suspicious of. clock: Clock = Clock.systemUTC() lets production code write LendingService(store). Java needs a second constructor for the same convenience. It's handy, but a default argument quietly brings a hidden dependency back: a test that forgets to pass a clock silently uses the real one. Many teams allow defaults only for genuinely harmless values, and make clocks, stores and network clients required.

Why constructor injection, not setters or fields

The other two styles assign the dependency after the object exists. Forget to, and you find out only when the code runs:

reminder at 2026-10-21T...
Exception in thread "main" kotlin.UninitializedPropertyAccessException: lateinit property clock has not been initialized
	at ReminderService.getClock(LateInject.kt:5)
	at ReminderService.stamp(LateInject.kt:7)
	at LateInjectKt.main(LateInject.kt:14)
reminder at 2026-10-21T...
Exception in thread "main" java.lang.NullPointerException: Cannot invoke "java.time.Clock.instant()" because "this.clock" is null
	at LateInject$ReminderService.stamp(LateInject.java:10)
	at LateInject.main(LateInject.java:18)

With constructor injection, a missing dependency is a compile error, and the field can be val/final. Spring's own documentation agrees: "The Spring team generally advocates constructor injection, as it lets you implement application components as immutable objects and ensures that required dependencies are not null" (Spring: Dependency Injection). Kotlin's primary constructor makes it nearly free: one line declares the parameter, the field and the assignment that Java spells out in three places.

What a container adds (and costs)

You built a container in L25. Here it is again:

A container automates the composition root. You register instances or recipes, and it works out the constructor calls. Real containers add auto-wiring (finding implementations by type), scopes (one instance per app, per request or per screen) and lifecycles (create, then close). The cost is the one L25 showed: wiring mistakes become run-time errors, and "where does this object come from?" has no answer you can click through.

Spring's ApplicationContext with @Autowired does this with reflection at startup. Android's Hilt sits on Dagger, which "is a fully static, compile-time dependency injection framework for Java, Kotlin, and Android" (dagger.dev), so wiring mistakes become compile errors. Google describes Hilt as "a dependency injection library for Android that reduces the boilerplate of doing manual dependency injection in your project" (Android: Hilt). Manual DI is the thing being automated, and it's worth doing by hand until the boilerplate hurts.

Service locator: the near miss

A service locator is a global registry that classes ask for their dependencies: Services.get(LoanStore::class). It also decouples you from concrete classes, but Fowler names the catch: "The key difference is that with a Service Locator every user of a service has a dependency to the locator." Dependencies stop showing in constructors, and tests have to remember to fill the registry. His conclusion is the real takeaway: "The choice between Service Locator and Dependency Injection is less important than the principle of separating service configuration from the use of services within an application" (Fowler).

What Kotlin does for you.
  • Primary constructors: class LendingService(private val loans: LoanStore, private val clock: Clock) is the parameter list, the fields and the assignments in one. Java repeats each name three times.
  • Default arguments replace Java's telescoping constructors. Use them carefully for dependencies (see above).
  • lateinit at least fails with a clear message (UninitializedPropertyAccessException naming the property), where Java gives a NullPointerException. Both fail at run time, which is why constructors win.
  • Named arguments make a composition root readable: LendingService(loans = store, clock = Clock.systemUTC()).

Part 3

Testing with fakes

~25 min

Once dependencies come in through the constructor, a test can pass in something that isn't the real thing. Gerard Meszaros's name for that something is a test double, and Fowler's summary of the five kinds is the standard vocabulary (Fowler: TestDouble):

KindFowler's definitionIn this lesson
Dummy"passed around but never actually used. Usually they are just used to fill parameter lists."A MemberStore handed to a test that never looks up a member
Fake"actually have working implementations, but usually take some shortcut which makes them not suitable for production (an InMemoryTestDatabase is a good example)."FakeLoanStore, MemoryKvStore
Stub"provide canned answers to calls made during the test"Clock.fixed(…); a lambda returning one overdue loan
Spy"stubs that also record some information based on how they were called"RecordingMailer, RecordingHttpPoster
Mock"pre-programmed with expectations which form a specification of the calls they are expected to receive"Usually made with a library (Mockito, MockK). Not used here; see below.

A fake for the network

The JDK's HttpClient is a big abstract class you'd rather not fake. So don't depend on it. Give the service a tiny interface it owns (DIP again), and have one real implementation wrap HttpClient:

real:  ok=true server got=[member=ada&cents=75]  (150 ms)
fake:  ok=true calls=[POST https://payments.example/payments member=ada&cents=75]  (16 µs)
fake 503: ok=false
real:  ok=true server got=[member=ada&cents=75]  (121 ms)
fake:  ok=true calls=[POST https://payments.example/payments member=ada&cents=75]  (56 µs)
fake 503: ok=false

Be careful with those numbers. The real call's 120–150 ms is mostly a one-off cost: creating the HttpClient and opening the first connection. A warmed-up localhost call is far cheaper. The bigger wins are elsewhere. The fake needs no server, can't be flaky, and can pretend to be a payment provider that's down (503), which is a failure you'd struggle to produce on demand with a real one.

Contract tests keep fakes honest

A fake is a second implementation of an interface, and any second implementation can drift from the first. The defence is Part 1's Rectangle trick: write the tests once against the interface, and run them against both the fake and the real thing. JUnit supports this directly: "Test methods and lifecycle methods may be declared locally within the current test class, inherited from superclasses, or inherited from interfaces" (JUnit User Guide). Here it is on a small key-value store:

(Java's KvStore interface, MemoryKvStore and MemoryKvStoreTest mirror the Kotlin ones line for line.) Every test runs twice, once per store. How long did each take? The honest reading: almost all of SqliteKvStoreTest's 233 ms is its first test (about 200 ms in every run), which pays for loading SQLite's native library. After that, a SQLite test took 1–5 ms against 0–1 ms for an in-memory fake (the Java project's numbers were within a few milliseconds of these). With a tiny local database, the speed difference is real but not dramatic. What makes the fake-based LendingServiceTest valuable is that its eight tests need no files, no schema and no cleanup, and that they'll give the same answer in any year. Against a real database server across a network, the speed gap would be much larger.

Mocks, and when to prefer fakes

Mocking libraries such as Mockito (Java) and MockK (Kotlin) create test doubles from an interface at run time and let you script and verify calls. They're useful at awkward boundaries. Overused, they produce tests that restate the implementation: "Mocks Aren't Stubs" calls this behaviour verification, and it means a refactoring that changes nothing visible can still break dozens of tests (Fowler: Mocks Aren't Stubs). Google's testing blog gives a practical alarm: "Some signs that you're overusing mocks are if you're mocking out more than one or two classes, or if one of your mocks specifies how more than one or two methods should behave" (Testing on the Toilet: Don't Overuse Mocks). A hand-written fake, checked by a contract test, tests what your code does rather than how.

Bridge: frameworks give you a way to swap a dependency in tests because they own the composition root. In Hilt, "To replace a binding, you need to replace the module that contains the binding with a test module" (Hilt testing). Spring Boot tests use @MockitoBean to "define a Mockito mock for a bean inside your ApplicationContext" (Spring Boot: Testing); older tutorials call it @MockBean. Same idea as your test wiring, one level up.

What Kotlin does for you.
  • Data classes give fakes and assertions equals for free (L7): assertEquals(listOf(loan), store.openForMember(1)) compares field by field. Java records do the same.
  • copy makes "the same loan, now returned" a one-liner in FakeLoanStore: loans[i].copy(returned = day). Java needs a hand-written withReturned.
  • Backtick test names (L11) read like the contract they check: `a returned loan no longer counts for its member`.
  • assertIs<LendResult.Lent>(result) also smart-casts result, so the next line can read result.loan with no cast. JUnit's assertInstanceOf returns the cast value instead.

Why did the service depend on a small HttpPoster interface instead of on HttpClient directly?

The service owns an interface with exactly the one method it needs (DIP). A real class adapts HttpClient to it, and a ten-line fake replaces it in tests.

Reference solution: the abstractions and the policy

Java also has one-line files for Member and Loan (records, with a withReturned helper on Loan) and for the sealed LendResult and ReturnResult, each a sealed interface with nested records. LendingService imports nothing from java.sql. That's the whole point, and you can check it with a search.

Reference solution: the SQLite details and the composition root

A trade-off to notice. In L36, lend checked availability and inserted the loan inside one transaction, so eight simultaneous lenders produced exactly one loan. Now the rule lives in the service and the store does one step per call, so two concurrent lenders could both pass the "book is free?" check (L27's check-then-act). The partial unique index still guarantees the database never holds two open loans for one book: the second insert fails with a constraint error instead of returning BookOnLoan. Keeping both the clean split and the transaction means giving the store an atomic operation, say tryAdd returning null on conflict, or passing a unit of work into the service. Design is choosing which of those costs you want.

Wrap-up

Exit quiz, recall card, sources

~5 min

Because OverdueReport is a Kotlin fun interface, a test's fake can be… (L14)

SAM conversion (L9, L14): a functional interface can be implemented by a lambda, so the whole fake is OverdueReport { listOf(…) }.

Why does LendingService return Blocked instead of throwing an exception? (L10)

L10's rule: exceptions for bugs and broken environments, return values for outcomes the caller must handle. A sealed type makes the caller handle every one.

With the "is the book free?" check outside any transaction, two simultaneous lenders can… (L27)

Check-then-act (L26, L27): both read "free", then both insert. The partial unique index rejects the second insert, so the data stays correct, but that caller gets an exception rather than BookOnLoan.

Which Kotlin parameter type lets a function promise not to add to the list it receives? (L3)

List is read-only: it has no add, so it makes no promise a subtype could break. Callers can pass a mutable list, and the function still can't change it through that reference.
