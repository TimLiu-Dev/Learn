Part 1

The command line

~15 min

Already comfortable here? Jump to the check. If you get 3 out of 3, skim this part and do only the exercise.

The shell is a program that reads a command you type, runs it, and prints the result. On your Mac it's zsh, inside the Terminal app. Both Git and the compilers are command-line tools, and IDEs run the same commands behind the scenes. That's why we start here (Missing Semester, lecture 1).

Where am I, and what's here?

The shell always has a working directory, the folder it's currently "in". Paths can be absolute, starting at / (the root of the disk), or relative to where you are now. Three shorthands come up constantly: ~ is your home folder, . is the current folder, and .. is its parent.

CommandWhat it does
pwdPrints the working directory
ls · ls -laLists the entries in a folder; -la adds hidden files and details
cd path · cd .. · cd ~Changes directory
mkdir -p a/bMakes folders, including any missing parents
cat filePrints a file's contents
echo textPrints text
man ls · ls --helpShows the manual for a command (press q to quit man)

Plumbing: redirects and pipes

Every program has an input and an output stream. > sends the output into a file and overwrites it. >> appends instead. |, the pipe, feeds one program's output into the next program's input. grep word keeps only the lines that contain word. Small programs chained together like this are the core idea of the Unix shell (Missing Semester).

Two habits that save hours: press Tab to auto-complete file names, and ↑ to bring back earlier commands.

Check

You're in /Users/tl/katas. You run cd .., then pwd. What's printed?

.. means "the parent folder". The parent of /Users/tl/katas is /Users/tl, and pwd always prints the resolved absolute path.

  1. That's two levels up. One cd .. moves up exactly one folder.
  2. The parent of /Users/tl/katas is /Users/tl, and that's now the working directory.
  3. / is the root of the disk. Getting there from katas takes three cd .. steps.
  4. pwd prints the resolved path. The shell turns .. into the real parent folder, not extra text.

What does ls | grep kt do?

ls prints one entry per line, and the pipe hands those lines to grep, which keeps only the matching ones. grep searches the text it receives, which here is the list of names, not the files' contents.

  1. That would be something like grep kt *, which reads files. Here grep only sees the names ls printed.
  2. Nothing is created. Only > or >> would write a file, and kt is just the pattern.
  3. grep drops the lines that don't match, so entries without kt disappear rather than staying unhighlighted.
  4. The pipe feeds ls's list of names to grep, which keeps only the lines containing kt.

You run echo hi > notes.txt twice. What's in notes.txt?

> overwrites, so the second run replaces the first. Use >> to append.

  1. Each > empties the file before writing, so only the last hi remains.
  2. Two lines would need >>, which appends. > overwrites.
  3. > empties the file and then writes the output into it, so hi is there.
  4. Overwriting a file you own is allowed, so the shell does it silently. That's why > deserves care.
Part 2

Compile and run by hand

~20 min

Kotlin and Java take the same route to running. A compiler turns your source file into bytecode, a compact instruction format stored in .class files. The JVM (Java Virtual Machine) then runs that bytecode. Because both languages compile to the same bytecode, Kotlin code can call Java code and the other way round. You'll lean on this in Android and Spring all the time.

Hello.ktKotlin source
→ kotlinc →
HelloKt.classbytecode
→
JVMruns it
Hello.javaJava source
→ javac →
Hello.classbytecode
→
JVMruns it

We'll open these .class files with javap and read the bytecode in L23.

Install the Kotlin compiler

You already have JDK 26, which provides javac and java. Kotlin's command-line compiler installs with Homebrew (Kotlin docs: command-line compiler):

$ brew update
$ brew install kotlin
$ kotlinc -version           # prints the Kotlin version

Hello, in both languages

In ~/katas/l01, create these two files with any plain-text editor. nano Hello.kt works in the terminal. Save with Ctrl-O, then Enter, and exit with Ctrl-X.

What Kotlin does for you. Java makes you write a class, mark the method public static, accept String[] args, and reach for System.out.println. Kotlin lets you write a top-level function and quietly does the rest. It generates a class named after the file, HelloKt, and turns main into a static method on it (Kotlin docs: package-level functions). Semicolons are optional too.

Run them: the explicit way, then the shortcut

# Java, step by step: compile, look, run
$ javac Hello.java
$ ls                         # Hello.class appeared
$ java Hello                 # run the CLASS (no .java, no .class)

# Java shortcut: compile in memory and run, one file only
$ java Hello.java

# Kotlin: compile into a self-contained jar, then run it
$ kotlinc Hello.kt -include-runtime -d hello.jar
$ java -jar hello.jar

The single-file shortcut java Hello.java has existed since JDK 11 (JEP 330). For Kotlin, -include-runtime bundles Kotlin's standard library into the jar so the plain JVM can run it, and -d names the output (Kotlin docs). Expect kotlinc to take a few seconds. That's the compiler starting up, not your code being slow.

Heads-up: modern Java can be shorter. Since JDK 25, a file can be just void main() { IO.println("Hello"); } (JEP 512), and your JDK 26 supports it. This course still writes the classic form, because that's what you'll read in real codebases, Android and Spring included.
Exercise: see what Kotlin generated
$ kotlinc Hello.kt -d out    # compile to a folder instead of a jar
$ ls out                     # find HelloKt.class, the class Kotlin wrote for you

Kotlin also writes a META-INF folder for its own bookkeeping, which you can ignore. The class name proves the point from the box above: you never wrote a class, but the JVM needs one, so Kotlin made one.

Check

What does javac Hello.java produce?

javac compiles each class to its own .class bytecode file. Jars are zip bundles of class files, made by a separate step.

  1. Jars are zip bundles of class files, made by a separate step such as jar. javac writes class files.
  2. .kt files are Kotlin source. A compiler reads source; it never writes source files.
  3. Each class in the file becomes its own .class file of bytecode, here Hello.class.
  4. .exe is native Windows code. javac produces bytecode for the JVM, not machine code.

Why does kotlinc need -include-runtime to make a jar you can run with java -jar?

Kotlin bytecode is ordinary JVM bytecode, but it calls into Kotlin's standard library (for things like listOf). The flag packs that library into the jar so it's self-contained (Kotlin docs).

  1. Kotlin bytecode is ordinary JVM bytecode, so the JVM runs it. What's missing is the library it calls.
  2. Kotlin code calls its standard library, so the jar must carry that library to run on a plain JVM.
  3. kotlinc compiles straight to bytecode. No Java source is ever generated.
  4. The flag only changes what goes into this one jar. Nothing is installed on your machine.

Kotlin and Java both compile to…

Same output format, same runtime. That shared target is why the two languages interoperate so smoothly.

  1. Both produce JVM bytecode, which runs on any OS that has a JVM. Native code would tie it to one platform.
  2. Kotlin has a separate JavaScript target, but kotlinc here makes JVM bytecode, and javac never makes JavaScript.
  3. Both are compiled before running. The JVM runs the compiled bytecode, never the source text.
  4. One shared format and runtime, which is why Kotlin and Java can call each other's code.

Warm-up: predict, don't run

Answer these from your head. You can confirm afterwards by putting the lines in a main. The Java versions use System.out.println and Integer.MAX_VALUE, and give the same results.

println(Int.MAX_VALUE + 1)

An Int is 32 bits, and adding past the maximum overflows, silently wrapping round to the minimum. There's no error. L2 explains why, using binary.

  1. 2147483648 doesn't fit in 32 bits. It would need a Long, but the result's type stays Int.
  2. Integer addition never checks for overflow. Only methods like Math.addExact throw ArithmeticException when it happens.
  3. The sum wraps past the maximum round to the minimum value, with no error.
  4. Infinity exists only for floating-point types like Double. Integer types have no such value.

println(7 / 2)

Both operands are integers, so this is integer division, and the fractional part is thrown away (truncated, not rounded). Write 7.0 / 2 to get 3.5.

  1. Two Ints give integer division, which drops the fractional part.
  2. You'd get 3.5 only if one operand were a Double, as in 7.0 / 2.
  3. Integer division truncates toward zero. It never rounds, so 3.5 becomes 3, not 4.
  4. The result is an Int, so it prints without a decimal point.

println(0.1 + 0.2 == 0.3)

0.1 and 0.2 can't be stored exactly in binary floating point, so their sum is 0.30000000000000004 (The Floating-Point Guide). L2 covers this properly.

  1. 0.1 and 0.2 are stored as close approximations, and their sum isn't the double nearest to 0.3.
  2. Comparing two Doubles with == is legal in both languages, so it compiles.
  3. == gives a Boolean, so only true or false can print. The sum itself isn't printed.
  4. The sum is 0.30000000000000004, which isn't the same double as 0.3.

Check: code predictions

Three whole programs, now that the tasks are done. Predict the output before you answer. These go into your results too.

What does this print?

fun main() {
    var n = 1
    var count = 0
    while (n <= 10) {
        count++
        n += 3
    }
    println("$count $n")
}

The loop tests n <= 10 before each pass. The test passes with n at 1, 4, 7 and 10, so the body runs 4 times. The fourth pass makes n 13, the next test fails, and n keeps the value that stopped the loop.

  1. That reads <= as <. When n is 10, 10 <= 10 is true, so there's a fourth pass.
  2. The count is right, but the fourth pass still adds 3. The loop stops only once n is 13.
  3. Four passes, at n = 1, 4, 7 and 10, and the last one leaves n at 13, which fails the test.
  4. At 13 the test fails before the body runs, so there's no fifth pass.

What does this Java program print?

public class Concat {
    public static void main(String[] args) {
        System.out.println(1 + 2 + "3" + 4 + 5);
    }
}

+ works from left to right. 1 + 2 adds two ints, giving 3. 3 + "3" has a String on one side, so it joins them into "33", and every later + joins text too: "334", then "3345" (JLS §15.18.1). Kotlin refuses 1 + "3" at compile time, and string templates avoid the puzzle altogether.

  1. 1 + 2 adds to 3 first. Once a String joins in, every later + joins text.
  2. That treats every + as joining text. The first + has two ints, so it adds them.
  3. That adds 4 + 5 on its own. But + groups left to right, so 4 is joined to "33" first.
  4. The quotes make "3" a String, not a number, and Java never turns it back into one for you.

This function is meant to test whether a number is odd. What prints?

fun isOdd(n: Int): Boolean = n % 2 == 1

fun main() {
    println("${isOdd(3)} ${isOdd(-3)} ${isOdd(4)}")
}

% is the remainder, and its sign follows the left operand: -3 % 2 is -1, not 1 (Kotlin docs: rem). So isOdd(-3) is false, which is a real bug. Java behaves the same way (JLS §15.17.3), and Java Puzzlers opens with this exact trap. The fix is n % 2 != 0.

  1. That assumes a remainder is never negative. In Kotlin and Java, -3 % 2 is -1, so the test fails for −3.
  2. isOdd returns the result of == 1, a Boolean, so only true or false can print. And −3's remainder is −1.
  3. Those are the right remainders, but isOdd compares each with 1 and returns a Boolean, so the words true or false print.
  4. 3 % 2 is 1, -3 % 2 is −1 and 4 % 2 is 0, so only the first equals 1.
Part 4

Git: save your work

~15 min

Git records snapshots (called commits) of a folder over time, so you can see what changed, when, and why, and go back if something breaks. The idea that makes everything else click is the three places a change can be (Pro Git §2.2):

Working directoryfiles on disk
→ git add →
Staging area"the next commit"
→ git commit →
Repositorypermanent history

The staging area lets you choose exactly what goes into a commit. Git stages a file as it is at the moment you run git add. If you edit it again afterwards, you have to add it again (Pro Git §2.2).

CommandWhat it does
git initTurns the current folder into a repository
git statusShows which files are untracked, modified or staged. Run it constantly.
git add file · git add .Stages one file, or everything under the current folder
git commit -m "msg"Records the staged snapshot with a message
git diffShows changes you haven't staged yet
git log --onelineShows the history, one line per commit

Check

You edit Main.kt, run git add Main.kt, edit it again, then run git commit. What does the commit contain?

Git stages a snapshot of the file at git add time, and that snapshot is what gets committed. The second edit stays unstaged until you add it again (Pro Git §2.2).

  1. A commit takes what's staged, not what's on disk. The second edit was never staged.
  2. One git commit makes one commit. The unstaged edit isn't recorded at all yet.
  3. git add stored a snapshot of the file at that moment, and the commit records exactly that snapshot.
  4. The staged snapshot is still there and gets committed. The later edit just waits, unstaged.

Which command shows the changes you haven't staged yet?

On its own, git diff compares your working directory with the staging area. Once everything is staged it shows nothing (Pro Git §2.2).

  1. git log lists past commits. It never looks at your current, uncommitted changes.
  2. With no arguments, it compares the files on disk with the staging area.
  3. git show displays an existing commit, the latest one by default, not your pending edits.
  4. git commit records what's staged. It doesn't display anything you haven't staged.

Why put *.class in .gitignore?

History should hold what you wrote. Anything a compiler can rebuild just adds noise and causes pointless conflicts.

  1. Git stores binary files, such as images, without trouble. The problem is that these files are generated.
  2. A class file holds only what your source already holds, compiled. It's ignored because it can be rebuilt.
  3. IntelliJ never deletes untracked files. Untracked only means Git isn't recording them.
  4. Anything the compiler can rebuild from source is noise in history and causes needless conflicts.

IntelliJ without autopilot, and a first Gradle project

~25 min

Out of energy? Do this part at the start of next session instead. You won't need IntelliJ or Gradle until L2's exercises get bigger, but read Study with these pages before you start L2.

Switch off AI completion

IntelliJ's full line completion uses a language model to suggest whole lines, which is exactly the habit you're trying to break. To turn it off, open Settings → Editor → General → Code Completion → Inline and clear "Enable inline completion using language models". To remove it completely, disable the Full Line Code Completion plugin under Settings → Plugins → Installed (IntelliJ docs). If you have the JetBrains AI Assistant plugin, its completion is a separate feature, so disable that plugin too.

Keep basic completion, the popup of names you get with Ctrl-Space. It only offers names that already exist, much like looking them up in the docs. The logic is still yours to write. AI completion writes the logic for you.

A first Gradle project

Typing kotlinc … -include-runtime by hand stops scaling once a project has many files, tests and libraries. Gradle is the build tool that Android and most Spring projects use to do that work. For now, just generate a project and run it:

$ mkdir ~/katas/gradle-hello && cd ~/katas/gradle-hello
$ gradle init --type kotlin-application --dsl kotlin --package katas --use-defaults
$ ./gradlew run              # first run downloads things; it can take a few minutes
Hello World!

The options come from the Gradle Build Init docs, and run is a task added by the application plugin. On the first run Gradle may also download a separate JDK for this project, because the generated build asks for a specific Java version (a toolchain). L25 explains that.

import java.util.Objects;

public class Practice {
    static String greeting(String name) {
        throw new UnsupportedOperationException("TODO: return \"Hello, NAME!\"");
    }

    // CHECKS
    public static void main(String[] args) {
        check("greets the katas folder", "Hello, katas!", () -> greeting("katas"));
        check("uses the name it is given", "Hello, Ada!", () -> greeting("Ada"));
        check("keeps a name with a space in one piece", "Hello, Grace Hopper!", () -> greeting("Grace Hopper"));
    }

    interface Check { Object get() throws Exception; }

    static void check(String name, Object expected, Check actual) {
        try {
            Object got = actual.get();
            System.out.println(Objects.equals(expected, got) ? "PASS " + name : "FAIL " + name + ": expected <" + expected + "> but was <" + got + ">");
        } catch (Exception e) {
            System.out.println("FAIL " + name + ": threw " + e);
        }
    }
    // END CHECKS
}
Hint 1 of 3

The first run fails with NotImplementedError: that's what TODO(…) throws. Replace the whole TODO(…) call with the text you want to return.

Hint 2 of 3

The text has three pieces: "Hello, ", then the name, then "!". The checks compare exactly, so watch the space after the comma.

Hint 3 of 3

In Kotlin, a string template does it in one go: "Hello, $name!". Java has no templates, so you join the pieces: return "Hello, " + name + "!";

Final answer

Why it works. The string template drops the value of name into the text, so one expression covers every name. The checks call greeting with three different names, which is how they know you didn't just type one answer.

Common mistake. Returning "Hello, katas!" because that's the example. The first check passes and the other two fail: checks test behaviour, not one example. A missing space or ! fails them all.

What is ./gradlew?

Because the wrapper is committed with the project, everyone who builds it, including your future self and CI servers, uses the same Gradle version (Gradle docs).

  1. It reads the version from gradle/wrapper/gradle-wrapper.properties, downloads that Gradle if needed, and runs it.
  2. It's a small shell script, with gradlew.bat beside it for Windows, so it runs on macOS too.
  3. gradle init generated it, not IntelliJ, and it works from any terminal.
  4. It runs any Gradle task, such as run, build or test. Testing is only one of them.

Exit quiz

Which compiles Hello.java and then runs it, the explicit two-step way?

javac takes a file (Hello.java), and java takes a class name (Hello).

  1. java Hello.java already compiles in memory and runs, and javac needs the file name, including .java.
  2. javac needs the .java file name, and java takes a class name, not a .class file.
  3. javac takes a file and writes Hello.class. Then java runs that class by name.
  4. kotlinc compiles Kotlin into bytecode, not Java files. Java source needs javac.

You've written and run a new kata. What's the right order to save it in Git?

Stage first, then record. git commit only records what's in the staging area.

  1. A commit records only what's staged. Commit first, and your new file isn't in it.
  2. git add stages a snapshot, and git commit records it in history.
  3. git init creates a repository, once. git log shows history. Neither saves your work.
  4. Both only show information. They're good checks before you commit, but nothing gets saved.

The fun main() in Hello.kt ends up inside which JVM class?

Top-level functions go into a class named after the file, plus Kt (Kotlin docs).

  1. Kotlin adds Kt to the file's name, which leaves Hello free for a class you write yourself.
  2. The generated class is named after the file, not after the function.
  3. Right suffix, wrong base: the name comes from the file, Hello.kt, not from main.
  4. Top-level functions in Hello.kt go into a generated class called HelloKt.
