TCP gives you a reliable, ordered stream of bytes. Why does a protocol on top of it need its own framing? (L30)

One write on one side can arrive as several reads on the other, or be merged with the next one. The receiver needs a rule for where a message ends. Today you'll see HTTP's three rules: a blank line ends the headers, then Content-Length, chunked encoding, or the server closing the connection ends the body.

  1. TCP retransmits lost segments, so the application never sees gaps. Reliability is what it does provide.
  2. TCP hands bytes to the reader in the order they were sent; any reordering in the network is undone first.
  3. A stream is only bytes: one write can arrive as several reads, or merge with the next, so HTTP marks its own ends.
  4. Writes of any size are allowed. TCP cuts them into segments for you, which is part of why boundaries vanish.

A URL says http://example.com/ with no port. Which TCP port does the client connect to? (L30)

For the http scheme, "TCP port 80 (the reserved port for WWW services) is the default", and for https it's 443 (RFC 9110 §4.2.1–4.2.2). 53 is DNS, which runs first to turn the name into an address.

  1. RFC 9110 makes 80 the default for http, so a URL without a port means port 80.
  2. 443 is the default for https. The scheme decides the port, and this one is plain http.
  3. 8080 is a popular port for development servers, but no scheme uses it as its default.
  4. 53 is DNS. A lookup does happen first, but only to find the address, not to carry HTTP.

A server gives every connection its own virtual thread. One client sends its request very slowly. What happens? (L28)

A blocked read unmounts the virtual thread, so its carrier is free for other connections (JEP 444). Today's raw-socket server uses exactly that pattern: Thread.ofVirtual().start { handle(socket) }.

  1. Each connection has its own thread, so a slow reader holds only its own thread, not anyone else's.
  2. A slow client is normal, not an error. Nothing in the server fails because a read takes a while.
  3. The accept loop runs on its own thread and keeps accepting; one waiting read doesn't stop it.
  4. The blocked read unmounts the virtual thread, which frees its carrier thread for other connections.

Which LinkedHashMap constructor setting turns it into the core of an LRU cache? (L19)

With accessOrder = true, every get moves the entry to the end, so the eldest entry is the least recently used one, and removeEldestEntry evicts it. Part 3 puts that map in front of HttpClient.

  1. Load factor only decides when the table resizes. It has nothing to do with ordering or eviction.
  2. Access order moves every entry you read to the end, so the eldest entry is the least recently used.
  3. Initial capacity is only a sizing hint. The map still keeps insertion order and never evicts anything.
  4. LinkedHashMap has no fair parameter. Fairness is a ReentrantLock setting (L26).

HTTP/1.1 is text you can type

RFC 9112 defines the format: "An HTTP/1.1 message consists of a start-line followed by a CRLF and a sequence of octets …: zero or more header field lines …, an empty line indicating the end of the header section, and an optional message body" (RFC 9112 §2.1). CRLF is \r\n. So a request is a few lines of text, a blank line, and maybe a body. Here is one typed by hand over a plain L30 socket:

status line : HTTP/1.1 200 OK
header      : Content-Type: text/html; charset=utf-8
header      : Transfer-Encoding: chunked
header      : Connection: close
header lines: 12
body line 1 : 241   <- chunk size in hex = 577 bytes
body line 2 : <!doctype html><html lang=en><head><meta...
bytes read  : 931
  • Host is required. "A client MUST send a Host header field … in all HTTP/1.1 request messages" (RFC 9112 §3.2). One IP address can serve thousands of sites, and Host says which one you mean.
  • Connection: close is why readAllBytes() returned. "HTTP/1.1 defaults to the use of persistent connections, allowing multiple requests and responses to be carried over a single connection" (RFC 9112 §9.3). Without the header, the server would keep the socket open for the next request, and a read-until-closed would hang.
  • The body starts with 241. That isn't HTML. It's a chunk size in hexadecimal, because the response says Transfer-Encoding: chunked: "a series of chunks, each with its own size indicator", where chunk-size = 1*HEXDIG (RFC 9112 §7.1). 0x241 is 577 bytes of HTML, then the next size line, and a size of 0 ends the body.

The same request from the shell, with nc from L30. One macOS detail: nc hangs up as soon as its input ends, before the reply arrives, so keep the input open for two seconds with sleep:

How a body ends: three rules

TCP has no message boundaries, so HTTP/1.1 spells out how the receiver knows the body is complete (RFC 9112 §6.3, simplified):

FramingHow it worksWhen you see it
Content-Length: 11"its decimal value defines the expected message body length in octets". Read exactly that many bytes.The size is known up front. Our server always does this.
Transfer-Encoding: chunkedSize line in hex, that many bytes, repeat; a 0 chunk ends it. If both headers are present, "the Transfer-Encoding overrides the Content-Length".The size isn't known yet: streamed or generated pages, like example.com above.
Connection closeFor a response with neither, the body is "the number of octets received prior to the server closing the connection".Old or lazy servers. A dropped connection looks the same as a finished body, so the RFC discourages it.

Responses to HEAD, and every 304 and 204, have no body at all, whatever the headers say (rule 1 of §6.3).

Methods: what the client wants

The method is the first word of the request line (RFC 9110 §9). Two properties matter more than the names:

  • Safe means "essentially read-only; i.e., the client does not request, and does not expect, any state change on the origin server". "The GET, HEAD, OPTIONS, and TRACE methods are defined to be safe" (§9.2.1). That's what lets crawlers and caches send them freely.
  • Idempotent means "the intended effect on the server of multiple identical requests with that method is the same as the effect for a single such request". "PUT, DELETE, and safe request methods are idempotent" (§9.2.2). A client may safely retry these after a dropped connection. POST is neither, which is why a browser warns before resubmitting a form.

Status codes: what happened

"The first digit of the status-code defines the class of response" (RFC 9110 §15): 1xx informational, 2xx successful, 3xx redirection, 4xx client error ("bad syntax or cannot be fulfilled"), 5xx server error ("failed to fulfill an apparently valid request"). The ones you'll meet every week:

Headers you'll read every day

"Field names are case-insensitive" (RFC 9110 §5.1): content-type and Content-Type are the same header, which is why our server lower-cases them before looking them up.

  • Request: Host; Accept (the formats I can read); User-Agent (who's asking); Authorization (credentials, L33); Content-Type and Content-Length when there's a body.
  • Response: Content-Type (how to interpret the bytes, including the charset from L2); Content-Length; Location (where to go, for 3xx and 201); and the caching headers in Part 3.
  • Cookies. HTTP is stateless, so state rides in headers: "Using the Set-Cookie header field, an HTTP server can pass name/value pairs and associated metadata (called cookies) to a user agent", which sends them back in a Cookie header on later requests (RFC 6265 §1, MDN: Cookies). Login sessions are usually a cookie.
  • CORS. "For security reasons, browsers restrict cross-origin HTTP requests initiated from scripts." Cross-Origin Resource Sharing is "an HTTP-header based mechanism that allows a server to indicate any origins … other than its own from which a browser should permit loading resources", sometimes after a "preflight" OPTIONS request (MDN: CORS). It's enforced by browsers, not servers: curl and HttpClient ignore it entirely.

HTTP/2 and HTTP/3

Line 6 says HTTP_2, and curl agrees:

$ curl -sI --http2 https://example.com | head -1
HTTP/2 200

HTTP/2 keeps the same methods, status codes and headers but changes the wire format. Messages become binary frames: "The basic protocol unit in HTTP/2 is a frame", and "multiplexing of requests is achieved by having each HTTP request/response exchange associated with its own stream", so "a blocked or stalled request or response does not prevent progress on other streams" (RFC 9113 §2). Many requests share one TCP connection instead of queuing. HTTP/3 (RFC 9114) "supports the same semantics over a new transport protocol", QUIC, which runs over UDP (L30). That avoids TCP's problem of one lost packet stalling every stream behind it.

Why did our local server get HTTP/1.1? HttpClient "will prefer HTTP/2" and, for a plain http:// URL, tries to upgrade the connection. I captured its first request with a throwaway listener:

GET / HTTP/1.1
Connection: Upgrade, HTTP2-Settings
Host: 127.0.0.1:49858
HTTP2-Settings: AAEAAEAAAAIAAAAAAAMAAAAAAAQBAAAAAAUAAEAAAAYABgAA
Upgrade: h2c
User-Agent: Java-http-client/26.0.1

Our server ignored the Upgrade header and answered in HTTP/1.1, which the client accepts: "If the upgrade fails, then the response will be handled using HTTP/1.1". This cleartext upgrade "was never widely deployed and is deprecated" by RFC 9113 (§3.1). In practice HTTP/2 means HTTPS.

Bridge. On Android, OkHttp and Retrofit play the role of HttpClient. Android throws NetworkOnMainThreadException "when an application attempts to perform a networking operation on its main thread", which is why you used L29's withContext(Dispatchers.IO). In Spring, a @RestController method is a handler like handle() here: the framework parses the request line and headers and writes the status, headers and body you return.

What Kotlin does for you.
  • Nothing extra for HTTP itself. Kotlin calls the same java.net.http and socket APIs, and the bytes on the wire are identical. Say so honestly when someone asks for "the Kotlin HTTP client": it's the JDK's, or a library like OkHttp or Ktor.
  • use { } closes sockets the way try-with-resources does, and socket.use { } works on any Closeable.
  • substringBefore(':') / substringAfter('?', "") replace Java's indexOf arithmetic in the parser, and destructuring val (method, target) = line.split(" ") names the parts of the request line.
  • when with conditions routes requests and returns the status code in one expression, where Java needed a mutable status variable assigned in every branch.
  • sendAsync(...).await() lets three requests run concurrently in code that reads top to bottom (L29), instead of a thenApply chain.
Exercise: a raw client that frames by Content-Length

With TinyServer serving, write rawGet(host, port, path) from a blank file. It returns a Response(status, reason, headers, body):

  1. Send a GET request line, a Host header and a blank line, and don't send Connection: close.
  2. Read the status line and split it into version, code and reason phrase.
  3. Read header lines into a case-insensitive map until the empty line.
  4. Read exactly Content-Length bytes for the body, or until the server closes if there's no length.

Call it for /, /hello?name=Ex, /old and /nope, and print each status, header count and body, plus the Location if there is one.

Reference solutions

/hello?name=Ex  200 OK                3 headers  body="hello, Ex"
/old            301 Moved Permanently 4 headers  body=(empty)  location=/new
/nope           404 Not Found         3 headers  body="no route for /nope"

Both languages print the same. Two details worth noticing. TreeMap(String.CASE_INSENSITIVE_ORDER) lets you look up "location" even though the server sent Location, as RFC 9110 §5.1 requires. And reading exactly Content-Length bytes is what makes persistent connections possible: you know the response is over without waiting for the socket to close, so the next request could reuse it. Hint 1 of 3

Ask "does this path exist?" before "is this method allowed?". If you check both at once, a wrong method on a real path drops through to 404, and the client never learns which methods would work.

Hint 2 of 3

For /notes/N, path.removePrefix("/notes/").toIntOrNull() gives the number, or null for /notes/abc (L3). titles.getOrNull(n - 1) gives the note, or null when there isn't one, including note 0.

Hint 3 of 3

The POST checks go in order: blank → 422, already in the list → 409, otherwise add it and answer Response(201, mapOf("Location" to "/notes/${titles.size}")). In Java, Map.of("Allow", "GET, POST") builds the header map.

Final answer

Why it works. Each status answers a different question. 404: there's nothing at this path. 405: there is, but not for this method, and Allow says what would work (RFC 9110 §15.5.6 requires it). 422: the request was well-formed, but the content makes no sense. 409: it clashes with what's already stored. 201: something new now exists, and Location says where.

Common mistake. Matching method and path together, as in method == "GET" && path == "/notes", with a 404 at the end. Every route works, but DELETE /notes says "not found" about a resource that plainly exists.

The header section ends with "an empty line" (RFC 9112 §2.1), the bare \r\n in the printed response. Then the body's own framing rule takes over.

  1. Requests carry any number of headers. A fixed count would cut some off, or wait for lines that never come.
  2. RFC 9112 ends the header section with an empty line: the bare \r\n in the printed response.
  3. The client keeps the socket open to read the response, so waiting for a close would hang both sides.
  4. Host is one header among many, and it can appear anywhere in the list, not only last.

A client's connection drops before the response arrives. Which requests may it retry automatically, by RFC 9110's definition?

"PUT, DELETE, and safe request methods are idempotent" (§9.2.2): sending them twice has the same intended effect as once. Retrying a POST could order the same pizza twice.

  1. POST and PATCH aren't idempotent: sending one twice may create or change something twice.
  2. GET is idempotent, but so are HEAD, OPTIONS, PUT and DELETE. Limiting retries to GET is overly cautious.
  3. These are exactly the methods RFC 9110 calls idempotent, so a repeat has the same intended effect as one.
  4. A body says nothing about idempotence: PUT has one and is idempotent, POST has one and isn't.

  2. A 3xx is a normal response, not an error, so send() returns it rather than throwing.
  3. The client hands back what the server sent: status 301, not an invented 200.
  4. With the NEVER policy you get the 301 itself, and you can read its Location header.

HTTPS and TLS at a high level

What TLS gives you, and what it doesn't

HTTPS is the same HTTP, sent inside a TLS connection on port 443. RFC 8446 lists what that channel provides (§1):

  • Authentication: "The server side of the channel is always authenticated; the client side is optionally authenticated." You know you're talking to the real example.com.
  • Confidentiality: "Data sent over the channel after establishment is only visible to the endpoints." The request line, headers, cookies and body are all hidden.
  • Integrity: "Data sent over the channel after establishment cannot be modified by attackers without detection."

What it doesn't hide: the IP addresses you're talking between (L30), "the length of the data it transmits" (same paragraph), and timing. The ClientHello that starts the handshake goes out before any keys exist, since "all handshake messages after the ServerHello are now encrypted" (§1.2), so the hostname the client names in it (SNI) is visible to the network. Someone watching sees that you visited example.com, but not which page or what you sent.

The handshake, in one picture

TLS has "a handshake protocol … that authenticates the communicating parties, negotiates cryptographic modes and parameters, and establishes shared keying material", followed by a record protocol that uses those keys. In outline:

  1. The client says hello: the TLS versions and cipher suites it supports, a key share, and the server name.
  2. The server picks a version and cipher, sends its key share, and both sides derive the same secret with an (EC)DHE key exchange. An eavesdropper who saw both key shares still can't compute it.
  3. The server sends its certificate chain and signs the handshake with the certificate's private key, proving it owns the certificate.
  4. From then on, HTTP travels encrypted with a fast symmetric cipher such as AES-GCM. L33 explains the difference between those two kinds of cryptography.

The first request to http://bank.example is sent unencrypted, and an attacker can answer it before any redirect to HTTPS happens.   2. The HTTP version is negotiated separately (ALPN), and trust checks don't affect it.
  3. Skipping the checks saves almost nothing. The handshake's cost is mostly the round trip and key exchange.
  4. Certificate checks are how you know who holds the other end. Without them, anyone can pose as the server.

The fastest request is the one you don't send. L22's latency ladder put a packet's round trip from the US to Europe at about 150 ms, while a lookup in a local map takes nanoseconds. RFC 9111 says "a cache stores cacheable responses to reduce the response time and network bandwidth consumption on future equivalent requests" (§1). It names two kinds:

  • A private cache "is dedicated to a single user; often, they are deployed as a component of a user agent": your browser's cache, or the one you'll write in a moment.
  • A shared cache "stores responses for reuse by more than one user": a company proxy, a CDN, or the proxy in today's final.

A stored response is fresh if it "can be reused without validation (checking with the origin server …)". Once it's stale, it can still be reused if validation shows it hasn't changed. The origin controls all of this with response headers.

Validators: "has it changed?"

When a stored response is stale, the cache doesn't have to download it again. It sends a conditional request (RFC 9111 §4.3, "validating" or "revalidating"), and if nothing changed the origin answers 304 Not Modified with no body:

  • ETag is "an opaque validator", such as a hash of the content or a version number, in quotes: ETag: "39fc27bb00f99a68" (RFC 9110 §8.8.3). The cache sends it back as If-None-Match, which is true when the current tag does not match. If the tag matches, the condition is false, and the answer is 304.
  • Last-Modified is a timestamp, sent back as If-Modified-Since: return the content only if it's "more recent than the date provided" (§13.1.3). It's coarser, with one-second resolution, and that's what the exercise builds.

Handle the two special values first: a missing header means the client has nothing, and * means "whatever you have". Everything else is a list: split(","), then trim() each tag.

Hint 2 of 3

Weak comparison ignores the W/ prefix on either side, so compare tag.removePrefix("W/") with etag.removePrefix("W/"). The quotes are part of the tag, so v7 without quotes is not "v7".

Hint 3 of 3

The 304 is "HTTP/1.1 304 Not Modified\r\nETag: $etag\r\nCache-Control: $cacheControl\r\n\r\n": the final \r\n is the blank line, and nothing follows it. For the 200, body.encodeToByteArray().size is the length. In Java, that's body.getBytes(StandardCharsets.UTF_8).length.

Final answer

Why it works. A cache that holds several versions sends all their tags, and one that stored a weak tag sends it back with W/. If any of them is current, the client already has the bytes, so the origin answers 304 with only the headers a 200 would have sent for caching: ETag and Cache-Control (RFC 9110 §15.4.5). A 304 ends at the blank line: it "cannot contain content".

Common mistake. ifNoneMatch == etag, which is what this part's EtagServer does. It works for a client that sends back exactly one strong tag, but answers 200 for a list, a W/ tag or *, so those clients download bytes they already have.

A response says Cache-Control: no-cache. What may a cache do with it?

"Does not prevent the storing of responses but instead prevents the reuse of responses without revalidation" (MDN). That's why /report showed REVALIDATED, not MISS. The directive that forbids storing is no-store.

  1. That's no-store. no-cache allows storing; it only forbids reuse without asking the origin.
  2. The cache may keep the response, but it must revalidate with the origin before every reuse.
  3. no-cache names no duration. Freshness comes from max-age or Expires.
  4. no-cache applies to every cache. The directive that only shared caches must obey is private.

The cache sends If-None-Match: "r-v1" and the origin replies 304. What does the cache send its client?

304 means "your copy is still good". The cache refreshes the stored entry's freshness from the 304's headers and serves its body as a normal 200, labelled REVALIDATED in our runs.

  1. The 304 has no body because the cache already has one. The client gets that stored body.
  2. The cache deals with the 304 itself. The client never has to talk to the origin.
  3. A 304 confirms the stored copy, so the cache updates its freshness and serves its body as a 200.
  4. A 304 isn't an error: it tells the cache that its stored copy is still valid.

A response says Cache-Control: private, max-age=60. Which cache may store it?

"A shared cache MUST NOT store the response", while "a private cache MAY store the response" (RFC 9111 §5.2.2.7). A CDN that ignored private would show one user's page to the next.

  1. private allows only a cache dedicated to one user, such as that user's browser.
  2. It's the reverse: private is the directive that forbids shared caches from storing it.
  3. private doesn't forbid storing; no-store does. A private cache may keep it for 60 seconds.
  4. A shared cache must not store it at all, so only the private cache keeps it for 60 seconds.

Beyond request/response: polling, SSE and WebSockets

When the server has news

Everything so far followed one rule: the client asks, the server answers. But a chat message arrives, a long job reaches 80%, a language model produces its next word, and the server has no way to start an HTTP exchange. RFC 6202 surveys how people bend HTTP into "bidirectional HTTP" (RFC 6202). Together with WebSockets, that gives four options:

TechniqueOn the wireCostPick it when
Short polling"A client sends regular requests to the server" (RFC 6202 §2.1): GET /messages?after=41 every few seconds, usually answered "nothing new".News waits up to one interval; most requests are wasted.Updates are rare and a delay is fine, like a build status checked every 30 s.

Server-Sent Events: a response that doesn't end

The format is defined in the HTML standard (WHATWG HTML: Server-sent events). "This event stream format's MIME type is text/event-stream", and "event streams in this format must always be encoded as UTF-8". The body is lines of field: value:

  • data: appends its value and a line feed to the event's data, so several data: lines make one multi-line message.
  • A blank line dispatches the event; event: names its type (the default is message); id: sets the last event id.
  • A line starting with a colon is a comment, which clients ignore. "The space after the colon is ignored if present": exactly one space.

This is how LLM APIs stream their answers. Anthropic's Messages API, for example, says that with "stream": true it will "incrementally stream the response using server-sent events (SSE)", sending events such as event: content_block_delta with a few characters of text in each data: line (Claude docs: Streaming messages). WebSockets: upgrade, then frames

"The WebSocket Protocol is designed to supersede existing bidirectional communication technologies that use HTTP as a transport layer" (RFC 6455 §1.1). It starts as an ordinary HTTP/1.1 request. This is the RFC's own example (§1.2):

Why the odd Accept value? "The server has to prove to the client that it received the client's WebSocket handshake, so that the server doesn't accept connections that are not WebSocket connections" (§1.3). It takes the key, appends the fixed GUID 258EAFA5-E914-47DA-95CA-C5AB0DC85B11, hashes that with SHA-1 and Base64-encodes the result. An ordinary HTTP server that happened to answer 101 couldn't produce it. It isn't a security check: anyone can compute it, and it only proves the server speaks WebSocket.   • The first line checks accept against the RFC's example before trusting it with a real client. Then the JDK client's real request: a random 16-byte key in Base64 and Sec-WebSocket-Version: 13. When I sent the key back unhashed instead, buildAsync(…).join() threw a CompletionException caused by java.net.http.WebSocketHandshakeException: the client really checks.
  • After the 101 it isn't HTTP any more. Each message is a frame (§5.2). In the first byte, 0x81, the top bit is FIN ("last fragment") and the low four bits are the opcode: %x1 "denotes a text frame" and %x8 "denotes a connection close". The second byte is a mask bit plus a 7-bit length; lengths of 126 and more need extra length bytes, which this demo doesn't handle.
  • The client's frames say 95, not 15: the mask bit is set. "A client MUST mask all frames that it sends to the server", and "a server MUST NOT mask any frames that it sends to the client" (§5.1). The server XORs the payload with the 4-byte masking key to read it, which is what the loop with % 4 does. The RFC says masking exists "to avoid confusing network intermediaries (such as intercepting proxies)", not to hide anything.
  • The JDK client. HttpClient.newWebSocketBuilder().buildAsync(uri, listener) opens the connection; your WebSocket.Listener gets onText(webSocket, message, last) calls. It's flow-controlled: a WebSocket "will invoke onText, onBinary, onPing, onPong or onClose methods on the associated listener … up to n more times" after request(n) (java.net.http.WebSocket), which is why onText calls request(1). sendClose "initiates an orderly closure": code 1000 is a normal close.
  • In real code the server side is a library, such as Spring's WebSocket support or Ktor, and the URL is wss://: the default for "wss" is port 443, WebSocket inside TLS (RFC 6455 §3). You wrote frames by hand once, so you know what those libraries do.

Which one?

  1. Does the client need to send often, in real time, on the same connection? Use a WebSocket.
  2. Does only the server push, as with notifications, progress or an LLM reply? Use SSE. It's plain HTTP, so caches, proxies, auth headers and HTTP/2 all just work, and the browser reconnects for you. The client can still send the occasional normal POST.
  3. Is streaming blocked, or the server too simple to hold connections? Long polling works anywhere HTTP does.
  4. Are updates rare and allowed to be late? Short polling is the least code and the easiest to cache.

Bridge. In Spring MVC a controller returns an SseEmitter, which "provides support for Server-Sent Events", then calls emitter.send(…) from another thread and complete() at the end. That's Sse's server loop, with the framing done for you (Spring: Asynchronous Requests). On Android, OkHttp has WebSockets built in: "Connect a web socket by passing a request to the newWebSocket() method along with a listener for server-sent messages" (Square: Web Sockets now shipping in OkHttp 3.5). It's the same handshake and frames as above. When the app is in the background, use FCM instead.

What Kotlin does for you.
  • Not much, honestly: both versions use the same HttpServer, HttpClient, WebSocket and socket classes, and the bytes on the wire are identical.
  • A local extension function, fun OutputStream.event(s: String) inside main, captures the flush flag, so the handler reads out.event(…). Java passes the flag to a static helper on every call.
  • resp.body().use { lines -> … } closes the line stream, like try-with-resources, and line.ifEmpty { "(blank line)" } replaces a ternary.
  • object : WebSocket.Listener { override fun onText(…) } is Java's anonymous class with less noise.

Hint 1 of 3

Keep three pieces of state outside the loop: the event type, a StringBuilder for the data, and the last id. Loop over stream.lines(), which already handles \n and \r\n. An empty line is the moment to emit an event, then reset the type and the data, but not the id.

Hint 2 of 3

For a field line, line.substringBefore(':') is the field name and line.substringAfter(':', "") the value (empty if there's no colon). Then removePrefix(" ") drops exactly one space. Don't use trim(): a second space is part of the data.

Hint 3 of 3

On data, append the value and a '\n'. On a blank line, emit only if (data.isNotEmpty()), using data.removeSuffix("\n").toString() and type.ifEmpty { "message" }. Whatever is still buffered when the loop ends is simply never emitted. In Java, stream.split("\\r?\\n", -1) gives the lines (the -1 keeps the trailing empty ones), and indexOf(':') does the splitting.

Final answer

Why it works. It's the WHATWG algorithm with the parts you need: each data: line adds the value plus a line feed, and dispatching removes the last line feed, so three data lines become YHOO\n+2\n10. The event type is reset after every dispatch, but the last event id isn't. That's what lets a reconnecting EventSource send Last-Event-ID, as in Ex4. Data that never sees its blank line isn't dispatched, so a dropped connection can't deliver half an event.

Common mistake. value.trim(). The spec removes one space after the colon, which is just formatting, so data: two spaces carries " two spaces". Trimming also eats trailing spaces: Sse's token "lo, " would arrive as "lo,", and a streamed answer would run its words together.

A chat UI shows an LLM's reply token by token; the browser sends nothing while it streams. Which fits best?

Only the server talks while the reply streams, so one SSE response carrying an event per token is the natural fit. It's what LLM APIs such as Anthropic's use. A WebSocket would work too, but it adds a second protocol for traffic that only goes one way.

  1. Polling every second makes tokens arrive in bursts up to a second late, and most requests come back empty.
  2. A full HTTP request and response per token adds headers and a round trip to every few characters.
  3. One long response, one event per token, pushed the moment each is ready: exactly what SSE is for.
  4. Script in a web page can't open raw TCP sockets; it uses APIs such as fetch, EventSource and WebSocket.

Why must a WebSocket server answer with Base64(SHA-1(key + GUID))?

RFC 6455 §1.3: the server proves "that it received the client's WebSocket handshake", so a server that doesn't understand WebSockets can't be tricked into accepting a connection. The JDK client rejected a wrong value with WebSocketHandshakeException.

  1. The hash is computed once and used for nothing else. Confidentiality comes from TLS, with wss://.
  2. Only a server that implements RFC 6455 combines the key with that fixed GUID, so the reply proves it.
  3. Anyone can compute the value from the key. Logging in is done with cookies or tokens, as for any HTTP request.
  4. It makes nothing smaller: it's an extra header, and compression is a separate extension.

Sse's server writes each event but never calls flush(). When do the client's lines arrive?

The JDK server buffers what you write. Without flush(), nothing leaves until closing the stream sends it, so in the noflush run every line arrived at about 970 ms.

  1. That needs a flush after each event. Without one, each write only fills the server's buffer.
  2. Closing the stream flushes it and ends the chunked body, so the client gets everything and finishes.
  3. No event is special. The comment and all four events sat in the buffer together.
  4. The buffered bytes go out when the stream closes, so every line arrives at the same moment.

Exit quiz, recall card, sources

~5 min

RawGet sends Connection: close and then calls readAllBytes(). Why is the header needed? (L22 + L31)

readAllBytes() reads until end of stream. HTTP/1.1 connections are persistent by default (RFC 9112 §9.3), so without the header the server keeps the socket open for another request, and the read waits. Ex1's fix is to frame by Content-Length instead.

  1. Reading a whole response is fine. The problem is knowing when the response has ended.
  2. Connection: close is optional. Without it, servers simply keep the connection open.
  3. The header only changes how long the connection lives, not the size of the body.
  4. readAllBytes() waits for the end of the stream, which comes only when the server closes the socket.

EtagServer calls setExecutor(Executors.newVirtualThreadPerTaskExecutor()). What changes? (L28 + L31)

Without an executor, every handler runs on the single thread start() created. With one, each request becomes a task, here a virtual thread, so a slow handler no longer holds up the rest, and shared state needs L27's care.

  1. That describes the default single thread, where requests wait their turn. The executor removes that.
  2. Each exchange becomes a task on its own virtual thread, so a slow handler no longer blocks the others.
  3. An executor only decides which threads run the handlers. This server still speaks HTTP/1.1.
  4. Executors run tasks; they don't cache anything. Caching is your own code, like EtagServer's ETags.

In Kotlin, you call client.send(...) with no try/catch and no @Throws. What does the compiler do? (L10 + L31)

Kotlin has no checked exceptions, so IOException and InterruptedException don't have to be declared. That's why the Kotlin handle() needed no catch. The network can still fail, so decide deliberately where to handle it.

  1. Kotlin has no checked exceptions, so nothing forces you to catch IOException.
  2. The compiler doesn't warn about uncaught exceptions, so remembering the network can fail is up to you.
  3. Kotlin treats every exception as unchecked, so the call compiles exactly as written.
  4. @Throws only adds a throws clause for Java callers. It's never required.

Why is a fresh cache HIT so much faster than a revalidation that returns 304? (L22 + L31)

A 304 saves the body but still costs a full network round trip, often tens of milliseconds. A fresh HIT is a map lookup measured in nanoseconds. L22's latency ladder is the reason max-age exists alongside ETags.

  1. A fresh hit is a local map lookup, while a 304 still waits for a full network round trip.
  2. A 304 has no body at all. It's smaller, yet still slower, because of the round trip.
  3. Stored copies aren't encrypted in this cache. TLS protects the network leg only.
  4. A HIT still returns headers. What it skips is the trip to the origin.
