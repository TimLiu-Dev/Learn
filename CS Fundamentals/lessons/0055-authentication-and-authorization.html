Authentication & Authorization

L33 stored passwords properly and left one thing hard-coded: who is asking. This lesson answers that question three ways (a session cookie, a signed token, and a login delegated to someone else with OAuth), then answers the second question every request raises: now that we know who you are, are you allowed to do this?

Part 1

Sessions, cookies and CSRF

~30 min

Two words, two questions. Authentication asks "who are you?" and authorization asks "are you allowed to do this?". HTTP remembers neither: every request arrives on its own (L32). The oldest fix is a cookie. The cookie draft, RFC 6265bis, says the Set-Cookie and Cookie headers let servers "maintain a stateful session over the mostly stateless HTTP protocol" (draft-ietf-httpbis-rfc6265bis-22, which will replace RFC 6265 and is now in the RFC Editor's queue).

A server-side session splits the job in two. The browser holds a long random session id and nothing else. The server holds a map from that id to the user. Step through it:

A session, end to end

The server below logs ana in with L33's PBKDF2 hash, hands out the cookie, recognises it on /me, and forgets it on logout. An in-program HttpClient plays the browser, sending the Cookie header by hand the way curl would.

wrong password              -> 401 invalid name or password  (45 ms)
unknown user                -> 401 invalid name or password  (45 ms)
unknown user, quick exit    -> 401 invalid name or password  (0 ms)
right password              -> 204
  Set-Cookie: __Host-sid=hLmkplMpjLqtE… Secure; HttpOnly; SameSite=Lax; Path=/; Max-Age=1800
GET /me with the cookie     -> 200 you are ana
GET /me without it          -> 401 please log in
GET /me with a guessed id   -> 401 please log in
POST /logout                -> 204, Set-Cookie: … Max-Age=0
GET /me with the old cookie -> 401 please log in
sessions left on the server: 0

The Java run printed the same lines, with a different random id. Four things to notice.

  1. The id is just a key. 32 bytes from SecureRandom is 256 bits, well above OWASP's floor: "Session identifiers must have at least 64 bits of entropy to prevent brute-force session guessing attacks" (Session Management Cheat Sheet). The guessed id got a 401 because nothing in the map matched it.
  2. Both failures look identical. Same status, same words, and the same time: a wrong password and an unknown user both took 45 ms, because an unknown name is still checked against a dummy hash. The /login-quick route returns early for unknown names and answered in under a millisecond, which tells anyone with a stopwatch which names exist. OWASP's Authentication Cheat Sheet shows the same two versions: the "quick exit" approach, and one that "will go through the same process no matter what the user or the password is, allowing the application to return in approximately the same response time." (These are single requests after three warm-up calls (L16), on my machine, an Apple M5 Max; yours will differ. The gap is 45 ms against 0, so one sample is enough to see it.)
  3. Logout happens on the server. After /logout the old cookie gets a 401 even though the client still sends it. The Max-Age=0 reply only asks the browser to delete its copy. OWASP: "deleting a cookie alone does not invalidate a stolen copy of the session ID."
  4. No cookie jar. HttpClient has none by default, so the program copies Set-Cookie into Cookie itself. A browser does this automatically, for every request to that host. That's convenient, and it's the root of CSRF below.

The cookie's attributes

The Set-Cookie line carries the session's security settings. Each one closes a specific hole:

AttributeWhat it doesHole it closes
HttpOnly"Forbids JavaScript from accessing the cookie" (MDN: Set-Cookie)an XSS bug reading the id (L33)
Securesent "only when a request is made with the https: scheme (except on localhost)" (MDN)the id travelling in plain HTTP
SameSite=Laxkept off cross-site requests, except top-level navigations with a safe methodmost CSRF, shown below
Path=/sent for every path on the hostnothing on its own: MDN says Path "is not intended as a security measure"

RFC 6265bis on the prefix: a __Host- cookie "will have been set with a Secure attribute, a Path attribute with a value of /, and no Domain attribute", which "hews as closely as a cookie can to treating the origin as a security boundary" (§4.1.3.2). OWASP calls it "Recommended for session IDs". Note that Max-Age only tells the browser when to drop the cookie. The real lifetime is enforced by the server, which is this part's exercise.

Session fixation: rotate the id at login

Stealing a session id is hard. A sneakier route is to give the victim an id the attacker already knows, wait for them to log in, and then use it. That only works if the server keeps the same id across login:

-- vulnerable: same id before and after login --
attacker gets an anonymous id and plants it in Ana's browser: Hu8lA_gj…
Ana logs in; her id is now Hu8lA_gj…
attacker, using the planted id: 200 you are ana
Ana, using her id:              200 you are ana
-- fixed: new id on login --
attacker gets an anonymous id and plants it in Ana's browser: UFT1VSWz…
Ana logs in; her id is now O3lB1l32…
attacker, using the planted id: 401 please log in
Ana, using her id:              200 you are ana

In the vulnerable version, logging in upgraded the anonymous session the browser already had, so the attacker's planted id became ana's login. The fix is two lines: delete the old id and issue a new one. OWASP: "The session ID must be renewed or regenerated by the web application after any privilege level change within the associated user session", and the most common case is "during the authentication process". (How an attacker plants an id in someone else's browser is a separate bug, such as a sibling subdomain setting cookies. The __Host- prefix blocks that route too.)

CSRF: the browser sends the cookie for you

Cross-site request forgery is the price of automatic cookies. OWASP's CSRF Prevention Cheat Sheet: "Since browser requests automatically include all cookies including session cookies, this attack works unless proper authorization is used". A page on another site can submit a form to your bank, and the browser attaches your bank cookie.

The demo needs two sites. Here's a detail worth checking for yourself: ports don't separate sites. The HTML standard defines a site as a scheme plus a host's registrable domain, or the whole host when it has none (an IP address, say), and says "the port and domain components are ignored" (HTML: Sites). Cookies ignore ports too: "Cookies do not provide isolation by port" (RFC 6265bis §8.5). So by the spec's definition, localhost:3000 and localhost:8080 are the same site and share cookies. But 127.0.0.1 and localhost are two different hosts, so they're two different sites. The demo uses that pair, and Chrome's own Sec-Fetch-Site header below confirms it.

The toy bank runs on http://127.0.0.1:<port>. The attacker's page runs on http://localhost:<port> and holds an invisible form that submits itself. The victim is a real headless Chrome with a fresh profile per case: it logs in at the bank, gets redirected to the attacker's page, and the page fires.

(no SameSite attribute)      -> 200 SENT 100 to mallory
    bank saw: cookie=yes Origin=http://localhost:54965 Sec-Fetch-Site=cross-site
SameSite=Lax                 -> 401 not logged in
    bank saw: cookie=no  Origin=http://localhost:54965 Sec-Fetch-Site=cross-site
SameSite=Strict              -> 401 not logged in
    bank saw: cookie=no  Origin=http://localhost:54965 Sec-Fetch-Site=cross-site
(none) + CSRF token check    -> 403 bad CSRF token
    bank saw: cookie=yes Origin=http://localhost:54965 Sec-Fetch-Site=cross-site
(none) + Origin check        -> 403 foreign Origin
    bank saw: cookie=yes Origin=http://localhost:54965 Sec-Fetch-Site=cross-site

The Java run printed the same five results; only the port numbers differ. Read the bank saw: lines as the server's view:

  • No SameSite attribute: the transfer went through. That's surprising at first, because Chrome treats a cookie without the attribute as Lax. But a default Lax has an exception. RFC 6265bis lets browsers apply "Lax-allowing-unsafe" enforcement to cookies that didn't set the attribute, limited to cookies "created recently", and notes that "Deployment experience has shown a cookie age of 2 minutes or less to be a reasonable limit" (§5.6.7.2). MDN: "cookies are also included in POST requests, as long as they were set no more than two minutes before the request was made." In this demo the attack lands seconds after login.
  • Lax and Strict: no cookie arrived, so the bank saw an anonymous request. A cross-site POST isn't a safe method, so even Lax withholds the cookie.
  • CSRF token: 403. The cookie arrived, but the form lacked the secret token the bank's own pages would include. The attacker's page can't read it from another site.
  • Origin check: 403. The browser stamped Origin: http://localhost:… on the request, and page scripts can't change it. The bank compared it with its own origin.

To check the two-minute window, the program has an aged mode: the attacker's page waits 125 seconds before answering, so the form fires when the cookie is older than two minutes:

$ java -cp csrf.jar:… CsrfKt aged
(none), cookie 125 s old     -> 401 not logged in
    bank saw: cookie=no  Origin=http://localhost:55112 Sec-Fetch-Site=cross-site

Same cookie, no attribute, and this time Chrome withheld it (the Java run agrees). So "no SameSite" is protected sometimes, depending on the browser and on timing. OWASP's advice follows: "Always set SameSite explicitly, and do not assume every user gets its protection", because "Chromium-based browsers treat cookies without a SameSite attribute as Lax, but Firefox and Safari do not".

The defences, and why there are several

  • Synchronizer token. The server stores a random token in the session and expects it back on every state-changing request, in a form field or a header. Tokens must be "Unique per user session", "Secret" and "Unpredictable", and "A CSRF token should not be transmitted in a cookie" (OWASP), since the whole problem is that cookies are sent automatically. The final sends it in an X-CSRF-Token header.
  • Origin check. Compare the Origin header with your own origin, matching all of it, so that example.org.attacker.com doesn't pass. OWASP: "Missing headers and Origin: null are not evidence of a same-origin request."
  • SameSite. OWASP calls it "useful as a defense-in-depth control but it does not replace a proper CSRF defense in most deployments." Its biggest gap: "If any state-changing operation in the application is reachable via a GET request, SameSite=Lax will not stop it." Never change state on GET (L32's safe methods).
  • Fetch Metadata. Look at the bank saw: lines again: Chrome also sent Sec-Fetch-Site: cross-site. OWASP calls this header "the primary signal for CSRF protection" and suggests: "By default, reject non-safe methods (POST / PUT / PATCH / DELETE) when Sec-Fetch-Site: cross-site."

One warning sits above all of these. OWASP: "Remember that Cross-Site Scripting (XSS) can defeat all CSRF mitigation techniques!" A script running on your own page can read the token and send a same-origin request. L33's HTML escaping comes first.

What Kotlin does for you.
  • Cookie parsing is one safe-call chain: getFirst("Cookie")?.split(";")?.map { it.trim() }?.firstOrNull { … }?.let { sessions[it] }. Java's sessionId needs a null check, a for loop and a substring.
  • return reply(ex, 401, …) replies and leaves in one statement, because reply returns Unit, which is a value (L3). Java writes { reply(ex, 401, …); return; }.
  • Named arguments document the call site: login(it, quickExit = true) against Java's bare login(ex, true).
  • listOf(Triple(…)) plus for ((name, attrs, check) in cases) destructures each case (L7). Java's Csrf uses a String[][] and indexes c[0], c[1], c[2].
  • The compiler refused old in sessions on a ConcurrentHashMap. That's Kotlin protecting you from a Java legacy method, and it caught a real security bug in this lesson.
  • What Kotlin does not do: @Volatile is Java's volatile under another name, and cookies, CSRF and timing are the same on both sides.

Check

A user clicks "Log out". What must the server do for the logout to mean anything?

A stolen copy of the cookie ignores Max-Age=0. Only removing the id on the server makes every copy worthless. OWASP: deleting the cookie alone "does not invalidate a stolen copy of the session ID".

Why must a server issue a new session id when someone logs in?

That's session fixation: the attacker plants an id they know before login, and if the server keeps it, their copy becomes the victim's login. The Fixation run shows the attacker getting 200 you are ana, then 401 once ids rotate.

Your API runs on localhost:8080 and a dev tool on localhost:3000. To cookies, the two are…

Different ports make different origins, but cookies ignore ports: "Cookies do not provide isolation by port" (RFC 6265bis §8.5), and the HTML standard's "same site" ignores the port too. So the dev tool can read and overwrite the API's cookies.

A cookie with no SameSite attribute was set 30 seconds ago. A cross-site form POSTs to its site in Chrome.

That's the demo's first row: 200 SENT 100 to mallory. Default-Lax cookies get "Lax-allowing-unsafe" treatment for about two minutes after they're set (RFC 6265bis §5.6.7.2). At 125 seconds the cookie stayed home. Set SameSite explicitly.

Where should a synchronizer CSRF token travel from the page back to the server?

A header or form field is something only your own page can fill in. A cookie is sent automatically, which is the very thing CSRF abuses, and a URL leaks into logs and history. OWASP: the token "must not be leaked in the server logs or in the URL".

Part 2

Tokens: JWTs and refresh tokens

~20 min

A session id means nothing without the server's map. A self-contained token carries the facts itself ("this is ana, an editor, until 14:28") with a signature so nobody can edit them. Any server holding the key can check it without asking a shared store, which suits L32's stateless requests and many copies of a service (L42). The standard format is the JSON Web Token: RFC 7519 calls it "a compact claims representation format", "always represented using the JWS Compact Serialization or the JWE Compact Serialization" (RFC 7519). The signed kind is three base64url parts joined by dots (RFC 7515 §7.1):

BASE64URL(header) . BASE64URL(payload) . BASE64URL(signature)

HS256 by hand

HS256 is L33's HMAC-SHA256 over the first two parts. The program first reproduces the worked example in RFC 7515 Appendix A.1 (the RFC's key, its exact signing input, its published signature), then makes a token of its own:

RFC 7515 A.1 signature: dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
matches the RFC: true
token: eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ…YXoZ7N2OXJWw
valid signature: true
anyone can read: sub="ana" role="editor"
role edited to admin, old signature kept: valid=false
  • It matches the RFC byte for byte (RFC 7515 A.1), so the HMAC, the base64url encoding and the "no padding" rule are all right. Java printed the same first two lines.
  • The key is 256 random bits. RFC 7518 §3.2: "A key of the same size as the hash output (for instance, 256 bits for "HS256") or larger MUST be used with this algorithm" (RFC 7518). A short human-chosen secret could be guessed offline from any one token.
  • Signed is not secret. Anyone can base64url-decode the payload and read role="editor", exactly like L33's Base64 "password". Never put secrets in a JWT payload.
  • Edits break the signature. Changing editor to admin and keeping the old signature fails the check, because the HMAC covers every byte of the first two parts.

A strict verifier

Checking the signature is necessary, not sufficient. Real JWT bugs come from verifiers that trust the token's own header, or skip the claims. RFC 8725, the JWT Best Current Practices, records two classic ones: the algorithm "can be changed to "none" by an attacker, and some libraries would trust this value", and an RSA token can be relabelled HS256 so that "some libraries would try to validate the signature using HMAC-SHA256 and using the RSA public key as the HMAC shared secret" (RFC 8725 §2.1). OWASP's JSON Web Token Cheat Sheet gives the defence: "Make sure that "alg":"none" is not accepted by your JWT parser", and "if possible, hardcode the accepted algorithms". The verifier below follows that, and a table of tokens it must reject is its test:

genuine token              -> Valid(subject=ana)
unsigned (alg none)        -> Rejected(reason=alg must be HS256)
other algorithm            -> Rejected(reason=alg must be HS256)
signed by another key      -> Rejected(reason=bad signature)
expired 10 min ago         -> Rejected(reason=expired)
expired 30 s ago (leeway)  -> Valid(subject=ana)
for another service        -> Rejected(reason=wrong audience)
from another issuer        -> Rejected(reason=wrong issuer)
genuine token              -> Valid[subject=ana]
unsigned (alg none)        -> Rejected[reason=alg must be HS256]
other algorithm            -> Rejected[reason=alg must be HS256]
signed by another key      -> Rejected[reason=bad signature]
expired 10 min ago         -> Rejected[reason=expired]
expired 30 s ago (leeway)  -> Valid[subject=ana]
for another service        -> Rejected[reason=wrong audience]
from another issuer        -> Rejected[reason=wrong issuer]

The rules, in the order the code applies them:

  1. The server picks the algorithm. The header's alg is only compared with the one we expect, never used to choose. RFC 8725 §3.1: libraries "MUST NOT use any other algorithms when performing cryptographic operations", and "each key MUST be used with exactly one algorithm". That one line rejects the unsigned token and the HS512 one.
  2. Signature before claims. Until the HMAC matches (in constant time, L33), the payload is untrusted text, so it isn't even parsed.
  3. exp is required, with a small allowance for clock skew. RFC 7519 §4.1.4: implementers "MAY provide for some small leeway, usually no more than a few minutes". That's why "expired 30 s ago" passes with a 60-second leeway and "10 min ago" doesn't. (Clock skew between machines is real, L32's time part.)
  4. iss and aud must be ours. RFC 8725 §3.9: "if the audience value is not present or not associated with the recipient, it MUST reject the JWT." Without that check, a token minted for billing-api by the same issuer would work here too.

In production you won't write this yourself; you'll configure a maintained library. What you take away is the checklist, because a library can still be configured to skip aud. Also look at the two right-hand columns: Kotlin's data classes print Valid(subject=ana), Java's records print Valid[subject=ana].

The catch: you can't take a JWT back

A session dies the moment the server deletes it. A signed token stays valid until exp, wherever copies of it went. OWASP: "if you use JWTs for user sessions, you will need a solution for managing session invalidation", and a deny list means "user sessions won't be completely stateless anymore". For a browser talking to its own server, a plain session (Part 1) is often the simpler answer.

Where tokens do fit (an app calling APIs, Part 3), the standard compromise is two tokens. A short-lived access token (minutes) goes with every API call, so a stolen one soon expires. A long-lived refresh token is sent only to the authorization server to get new access tokens, and it can be revoked there. RFC 9700, OAuth's security best practice, adds rotation: "the authorization server issues a new refresh token with every access token refresh response. The previous refresh token is invalidated", and if a stolen token is "used by both the attacker and the legitimate client, one of them will present an invalidated refresh token, which will inform the authorization server of the breach" (RFC 9700 §4.14.2).

app refreshes with rt1             -> ok, access(ana, 15 min), new refresh _I8FRp…
a stolen copy of rt1 is used       -> REUSE of a retired token: family 1 revoked
app refreshes with its rt2         -> family revoked: log in again
app sends a made-up token          -> unknown token
ana logs in again, new family      -> ok, access(ana, 15 min), new refresh dvAFDF…

Line 2 is the alarm. Someone presented rt1 after it had been used. The server can't tell whether that's the thief or the real app, so it does what the RFC says, "it will revoke the active refresh token", and the whole family dies. Line 3 shows the price: the real app is logged out too, and ana signs in again (line 5, a new family). Java printed the same, with different random token prefixes.

What Kotlin does for you.
  • sealed interface Verdict with data class cases is Java's sealed interface with records, nearly line for line (L7). The visible difference is toString: Valid(subject=ana) against Valid[subject=ana].
  • token.split(".") splits on a literal dot. Java's split takes a regex, where . matches any character, so Java must write split("\\.", -1). That's L33's split("$") bug in a new place, and in a verifier it would be a security bug.
  • runCatching { … }.getOrNull() turns "bad base64 or bad JSON" into null in one expression; Java needs a try/catch per call site.
  • Refresh.kt uses the standard library's Result<T> and fold. Java has no built-in Result, so Refresh.java declares its own sealed Outcome and takes it apart with a record-pattern switch (JEP 440, JEP 441), which is arguably clearer.
  • buildJsonObject { put("sub", "ana") } and Jackson's createObjectNode().put("sub", "ana") do the same job; @Synchronized is Java's synchronized modifier as an annotation.
Exercise: a token decoder for debugging

When an API rejects a token, the first question is "what does it actually say?". Build the tool you'd reach for, and keep in mind that decoding is not verifying.

  1. From a blank file, write decode(token, now). Require exactly three parts, and print the header JSON.
  2. Print each claim on its own line. For exp, iat and nbf, also print the time as an Instant (they're seconds since the epoch, RFC 7519's "NumericDate").
  3. Say how long until exp, or how long ago it passed, against the now you were given (an injected clock again).
  4. End with a line saying the signature was not checked.
  5. Run it on JwtDecode's sample token with now = 2026-09-21T14:30:00Z.

Check

A JWT's payload contains "role":"editor". Who can read that value?

The payload is base64url, an encoding with no key (L33). The signature stops edits, not reading. Jwt's output decoded it with no key at all.

Your verifier reads alg from the token's header and picks the algorithm to match. What's wrong?

The header is written by whoever made the token, so it can say none or name a different algorithm. RFC 8725 §3.1: the library must use only the algorithms the caller allows, and "each key MUST be used with exactly one algorithm".

A refresh token that was already used is presented again. What does a rotating server do?

Two parties hold copies, and the server can't tell which is the thief. RFC 9700 §4.14.2: it "will revoke the active refresh token", forcing a fresh login. Refresh's line 3 shows the legitimate app paying that price.

Kotlin: "a.b.c".split(".").size

Kotlin's split(String) treats the delimiter literally. Java's "a.b.c".split(".") uses the regex ., which matches every character, and after trailing empty strings are removed you get length 0. Hence split("\\.", -1) in the Java verifier.

Part 3

OAuth 2.0 and OpenID Connect

~20 min

"Sign in with…" buttons and "let this app read your photos" screens are OAuth 2.0. The problem it solves: photo-app wants to read ana's photos on another service, and ana must not give photo-app her password. RFC 6749 names four roles (§1.1):

RoleRFC 6749's wordsHere

PKCE: proving you started the flow

The code comes back through the browser, and on a phone through an app redirect, where it can leak. RFC 7636 describes the attack it was written for: "the attacker intercepts the authorization code returned from the authorization endpoint", and "Once the attacker has gained access to the authorization code, it can use it to obtain the access token" (RFC 7636). PKCE (Proof Key for Code Exchange) makes a copied code useless. The app invents a random verifier, sends only its hash, the challenge, at the start, and reveals the verifier when it redeems the code: code_challenge = BASE64URL-ENCODE(SHA256(ASCII(code_verifier))) (§4.2).

verifier:  dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
challenge: E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
both match Appendix B: true
a fresh verifier has 43 chars, all unreserved: true
its challenge: v_QRc3HlkakF3x6F12EZsPPZstDmPkC8tEl_xRW3-Kk

Both values match the test vector in RFC 7636 Appendix B, and Java agrees on all but the random last line. A fresh verifier is 43 characters, the minimum the RFC allows ("with a minimum length of 43 characters", §4.1). Look closely at that verifier: it's the same string as the JWS signature in Part 2. RFC 7636's example starts from the same 32 bytes that RFC 7515 lists as its example's HMAC output. RFC 9700 says when to use PKCE and which method: "Public clients MUST use PKCE", and "Currently, S256 is the only such method" that doesn't expose the verifier (§2.1.1).

All three parties on localhost

Three HttpServers on 127.0.0.1 play the authorization server, the client app and the photos API. The "browser" is an HttpClient that follows each redirect by hand, so every hop is printed. Tokens are Part 2's HS256 JWTs. After the happy path, the program tries five things that must fail:

OpenID Connect: who logged in

OAuth on its own grants access; it doesn't tell the app who the user is. OpenID Connect adds that on top. "The primary extension that OpenID Connect makes to OAuth 2.0 to enable End-Users to be Authenticated is the ID Token data structure", a JWT with "Claims about the Authentication of an End-User by an Authorization Server" (OIDC Core 1.0 §2). An OIDC request has to ask for it: "OpenID Connect requests MUST contain the openid scope value" (OIDC §3.1.2.1), which is why photo-app's request says scope=openid photos.read. (The simulated AS skips that check and always returns an id_token.) Keep the two tokens apart:

  • The ID token is for the client. Its aud is the client's id, and it answers "who just logged in?". Check 5 shows an API rejecting one.
  • The access token is for the API. Its aud is the API, and the client should treat it as opaque.
  • The nonce ties an ID token to one login attempt: it's "used to associate a Client session with an ID Token, and to mitigate replay attacks" (OIDC §2).

The implicit flow is out. Older single-page apps used response_type=token, which puts the access token straight into the redirect URL. RFC 9700 §2.1.2: "clients SHOULD NOT use the implicit grant (response type token) or other response types issuing access tokens in the authorization response", because such tokens are exposed to "access token leakage and access token replay". Use the code flow with PKCE everywhere, including in browser apps.

Honest limits of the simulation. To stay short, the API shares the AS's HMAC key. OWASP: "A different secret must be used for each (issuer, audience) pair", because any holder of a shared secret can mint tokens. Real authorization servers sign with a private key, and APIs verify with the public key: OIDC's default ID token algorithm is RS256. There's also no real login page or consent screen, and no TLS, which real OAuth always needs: RFC 7636's introduction takes it as given, "Because OAuth requires the use of TLS".

Bridge: on Android you don't build this by hand. Use Credential Manager for sign-in and passkeys, and AppAuth for the OAuth/OIDC code flow with PKCE. Knowing the steps lets you read their logs when a login fails.

Part 4

Authorization: roles, ownership, CORS

~20 min

Parts 1 to 3 answered "who are you?". Every request then asks a second question, and L33 showed what happens when nobody asks it: ben read ana's orders by editing a URL. OWASP's Authorization Cheat Sheet starts from three rules: least privilege, deny by default, and "Permission should be validated correctly on every request". It adds why the last one matters: "Remember an attacker only needs to find one way in."

401 or 403?

The status code says which question failed (RFC 9110 §15.5.2, §15.5.4):

  • 401 Unauthorized is about authentication, despite its name: the request "lacks valid authentication credentials for the target resource". The server "MUST send a WWW-Authenticate header field … containing at least one challenge". L33's toys skipped that header; Part 3's API sent Bearer error="invalid_token", and the final sends one too.
  • 403 Forbidden is about authorization: "the server understood the request but refuses to fulfill it." Logging in again won't help: "The client SHOULD NOT automatically repeat the request with the same credentials."
  • 404 stays allowed for hiding: "An origin server that wishes to "hide" the current existence of a forbidden target resource MAY instead respond with a status code of 404". L33's IDOR fix did that. The final uses 403, because its books are public anyway.

Roles and ownership in one decision function

Role-based access control (RBAC) gives permissions to roles and roles to users. It answers "may editors update books?", but not "may this editor update this book?". That needs a relationship check, and the cheat sheet recommends exactly that: "ABAC and ReBAC should typically be preferred for application development", where ReBAC means "allowing only the user who created a post to edit it". The program below combines both, in one function that every request must go through:

on ana's book   READ     CREATE   UPDATE   DELETE   PUBLISH  
anonymous       yes      -        -        -        -        
ben (reader)    yes      -        -        -        -        
ana (editor)    yes      yes      yes      yes      -        
cy (editor)     yes      yes      -        -        -        
root (admin)    yes      yes      yes      yes      -

Both languages print the same matrix. Three things it shows:

  • cy and ana have the same role and different rights. Both are editors; only ana owns the book. That row is L33's IDOR bug, fixed by book.owner == user.name.
  • Nobody can PUBLISH, not even the admin. No rule mentions it, so can falls through to false. When someone adds an action and forgets the rules, the result is a denial, never a hole. That's deny by default.
  • Reading is public, deliberately. The first line of can says so explicitly, rather than reading as public by accident.

CORS is not an authorization mechanism

Call an API from another origin's page with fetch and you'll meet CORS errors, and it's tempting to think CORS protects the API. It doesn't: it protects the response from the other page's script. MDN: CORS "allows a server to indicate any origins (domain, scheme, or port) other than its own from which a browser should permit loading resources" (MDN: CORS). The test below runs a real Chrome on a page at http://localhost:<port>, calling an API at http://127.0.0.1:<port>, and prints both sides: what the page's script got, and what the server actually received.

What the page's script got:

  2 GET  /shared            -> read 200 {"balance":1234}
  3 PUT  /items     (JSON)  -> blocked (TypeError)
  4 PUT  /items-ok  (JSON)  -> read 200 {"balance":1234}

The Java run printed the same, apart from the port. Match the two halves up:

  • 1 and 2: simple GETs. Both reached the server, and both got answers. The browser handed /shared's answer to the script, because that route sent Access-Control-Allow-Origin with the page's origin, and threw /private's away. The server did its work either way.
  • 3 and 4: PUT with JSON is preflighted. The browser first sent OPTIONS to ask permission. /items didn't grant it, so the real PUT was never sent. That's the one case where CORS stops a request from arriving.
  • 5: the dangerous one. A POST with text/plain is a "simple request": no preflight. The server received it and ran it (account deleted); only the response was blocked. MDN explains why: a <form> "can submit simple requests to any origin, so anyone writing a server must already be protecting against cross-site request forgery (CSRF)", and "the server still must opt-in using Access-Control-Allow-Origin to share the response with the script."

So CORS decides who may read; the server must still decide who may act, with sessions, CSRF defences and authorization checks. Two settings to get right: never reflect any Origin back as allowed, and with cookies, MDN says the server "must specify an origin in the value of the Access-Control-Allow-Origin header, instead of specifying the * wildcard."

Why WWW-Authenticate: Session realm="books"? RFC 9110 §15.5.2 says a 401 "MUST send a WWW-Authenticate header field (Section 11.6.1) containing at least one challenge". The schemes in IANA's HTTP Authentication Scheme Registry (Basic, Bearer, Digest and others) all describe credentials sent in the Authorization header, and none describes a session cookie. So the server names its own scheme, as the comment in guard says. It's unregistered (RFC 9110 §11.1 says new schemes "ought to be registered"), so treat it as a documented convention for this API, not a standard. What matters is that the header is present and tells a client how to get in: log in first: POST /login.

The session map is read and written by request handlers on virtual threads. Which map? (L27, L28)

Handlers run concurrently (L32's final gave each request a virtual thread), so a plain HashMap would race (L27). And remember Part 1's trap: on a ConcurrentHashMap, use containsKey, never Kotlin's in.

Any server holding the key can check a JWT access token without a shared session store. Which REST constraint does that serve? (L32)

Fielding (ch. 5.1.3): each request "must contain all of the information necessary to understand the request". The price is Part 2's: a token can't be taken back before exp.

Why does Auth take now: () -> Long instead of calling System.currentTimeMillis()? (L11, L32)

Test 10 moves the clock 16 minutes in one line and checks the idle timeout, with no sleeping. It's the same reason L32's time part passed a Clock in.

An authorization check throws an unexpected exception halfway through. How should the request end? (L10, L33)

Fail closed. The final's handle turns any exception into a 500 Problem Details response, so the action behind the check never runs, and the routes exercise refuses to start rather than run unguarded. L33's A10 callout showed the failing-open alternative.

Which cookie attribute keeps a session id off plain-HTTP connections? (L31)

Secure cookies go only over HTTPS (MDN makes an exception for localhost). HttpOnly is about JavaScript, not the network. L31's TLS is what makes the id unreadable on the wire.
