An extension on Shape and one on Circle, both called name(). You call it through val s: Shape = Circle(). Which runs?

Extensions are resolved statically, from the declared type (L9). Overriding is the only thing chosen at runtime.

  1. Extensions aren't virtual: the compiler picks by the declared type Shape, not the runtime Circle.
  2. The variable is declared as Shape, and extension calls are bound to that static type at compile time.
  3. Resolution never depends on class loading. The compiler decides it entirely from declared types.
  4. Extensions on different receiver types don't clash. For a Shape receiver, only the Shape one applies.

Why did Java callers need Kotlin's @Throws(IOException::class) in L9?

Without it, javac refused a catch (IOException e) it thought could never happen. Part 2 explains that compile-time check.

  1. Kotlin throws any exception freely. @Throws only adds a throws clause to the bytecode, for Java's sake.
  2. Checked exceptions are a compile-time rule only. At runtime the JVM lets any exception through.
  3. javac rejects a catch for a checked exception that nothing in the try declares, so the declaration had to exist.
  4. Every uncaught exception prints a trace. The annotation only changes the method signature javac sees.

In a stack trace, the first at … line is…

Traces list the stack top-down, so the frame that threw comes first (L4).

  1. The top frame is the one that was running when the exception was created, so it's listed first.
  2. The entry point, main, is at the bottom of the trace, not the top.
  3. The first frame is where the failure happened, not the line that ran before it.
  4. The top frame is often JDK code like Integer.parseInt. main usually comes last.
Part 1

Exceptions and stack traces

~38 min

An exception is an object that describes something going wrong. You throw it, and the JVM then searches for a handler, a catch block that accepts that type. It starts in the current frame and works outward through the call stack, popping each frame that doesn't handle it. That process is called unwinding. If no frame catches the exception, the thread ends and the JVM prints a stack trace (dev.java: What is an exception?).

parsePort: parsing "80x"
startServer: finally runs while unwinding
main caught: For input string: "80x"
main continues

When nobody catches it

Remove the try from main, and the exception unwinds every frame. The trace is that journey, printed top-down:

Exception in thread "main" java.lang.NumberFormatException: For input string: "80x"
	at java.base/java.lang.NumberFormatException.forInputString(NumberFormatException.java:67)
	at java.base/java.lang.Integer.parseInt(Integer.java:527)
	at java.base/java.lang.Integer.parseInt(Integer.java:624)
	at UncaughtKt.parsePort(Uncaught.kt:1)
	at UncaughtKt.startServer(Uncaught.kt:3)
	at UncaughtKt.main(Uncaught.kt:6)
	at UncaughtKt.main(Uncaught.kt)

How to read it:

  1. The first line gives the type and the message.
  2. The next lines are the stack, top-down. The java.base/… frames are JDK code. Skim down to the first frame in your code, here parsePort(Uncaught.kt:1). That's where to start looking.
  3. Read further down to see who called it.

Kotlin's toInt() calls Java's Integer.parseInt underneath, which is why both traces show the same JDK frames. The Java version is the same apart from the class names.

The exception family tree

Throwable                      "the superclass of all errors and exceptions"
├── Error                      serious problems an app "should not try to catch"
│   ├── StackOverflowError       (L4)
│   └── OutOfMemoryError         (L4)
└── Exception
    ├── IOException            ← checked (Part 2)
    └── RuntimeException       ← unchecked
        ├── IllegalArgumentException
        │   └── NumberFormatException
        ├── IllegalStateException
        ├── NullPointerException     (L3)
        ├── IndexOutOfBoundsException

The quotes come from the JDK docs for Throwable and Error. A catch block catches its type and every subtype, so catch (IllegalArgumentException e) also catches a NumberFormatException. That's why order matters: list the most specific types first.

          ^

Kotlin 2.4 compiles its version without any error or warning and prints something failed. The second catch is silently dead code. Kotlin won't catch this one for you, so put the specific types first yourself.

Chained causes: "Caused by:"

Low-level exceptions often don't make sense higher up: "For input string: 80x" means nothing to the code that was loading a config file. Good practice is to catch it, and throw a higher-level exception that keeps the original as its cause. Effective Java Item 73 calls this throwing exceptions "appropriate to the abstraction" (see also dev.java: Chained exceptions):

$ javac Chained.java && java Chained
Exception in thread "main" java.lang.IllegalStateException: could not load config 'app.conf'
	at Chained.loadConfig(Chained.java:9)
	at Chained.main(Chained.java:14)
Caused by: java.lang.NumberFormatException: For input string: "80x"
	at java.base/java.lang.NumberFormatException.forInputString(NumberFormatException.java:67)
	at java.base/java.lang.Integer.parseInt(Integer.java:527)
	at java.base/java.lang.Integer.parseInt(Integer.java:624)
	at Chained.parsePort(Chained.java:2)
	at Chained.loadConfig(Chained.java:6)

Read the top section for what failed, and the Caused by: section for why. The ... 1 more line means "the remaining frames are the same as the enclosing exception's". The JDK docs explain that these lines indicate "the remainder of the stack trace for this exception matches the indicated number of frames from the bottom of the stack trace of the exception that was caused by this exception" (Throwable.printStackTrace). The Kotlin run prints the same shape, ending in ... 2 more because of Kotlin's extra main bridge frame.

finally, and the one thing never to do in it

A finally block runs whether the try succeeded, threw, or returned. That's what made startServer's message print during unwinding. It exists for cleanup. But if the finally block itself completes abruptly, for example by returning, the spec says the original exception "is discarded and forgotten" (JLS §14.20.2):

-1
no one ever hears about the failure

Both languages compile this without complaint by default. javac only warns if you ask for lint warnings:

$ javac -Xlint:all FinallyReturn.java
FinallyReturn.java:7: warning: [finally] finally clause cannot complete normally

Never return or throw from finally.

Cleaning up resources: try-with-resources and use

Files, network connections and database connections must be closed even when something fails. Java's try-with-resources closes any AutoCloseable declared in its header, "in the reverse order from that in which they were initialized" (JLS §14.20.3). Kotlin has no special syntax for this. It uses an ordinary extension function, use, which "closes it down correctly whether an exception is thrown or not" (Kotlin API: use).

open A
open B
using A and B
close B
close A
open C
close C
caught: body failed
  suppressed: close C failed

The second block shows suppressed exceptions. The body threw, and then close() threw too. Only one exception can propagate, so the body's exception wins, and the close failure is attached to it rather than lost. Throwable.addSuppressed is "typically called (automatically and implicitly) by the try-with-resources statement" (Throwable docs), and Kotlin's use does the same. In an uncaught trace these show up as indented Suppressed: sections.

What Kotlin does for you. use is just a library function, not new syntax, and it works on anything AutoCloseable. Nesting use blocks gives the same reverse close order as Java's multi-resource header. The { a -> … } after use is a lambda, which L14 covers properly. One caution, where Kotlin does less than Java: the wrong-order catch above compiles silently in Kotlin.

Hint 1 of 3

Wrap the whole body in conn.use { … }. Whatever the lambda's last expression is becomes the value of use, and the connection is closed on the way out, whether the block returned or threw.

Hint 2 of 3

Inside use, read the line, then put only the parsing in a try. Catch NumberFormatException, not Exception: the dropped-connection check wants its IllegalStateException to pass through untouched.

Hint 3 of 3

In the catch, write throw ConfigException("bad port in ${conn.name}: '$text'", e). Passing e as the second argument is what puts the Caused by: section in the trace. In Java, the same shape is try (conn) { … } and throw new ConfigException(…, e), and readPort must declare throws ConfigException because it extends Exception.

Final answer

Why it works. use closes the connection on every path out of the block, just like try-with-resources. The narrow catch translates only the failure this level understands, a bad number, into ConfigException. It passes the original along as the cause, so nothing is lost (Effective Java Item 73). The dropped connection isn't a config problem, so it isn't caught at all.

Common mistake. Calling conn.close() at the end of the function. It runs only when parsing succeeds, so every bad line leaks a connection. Cleanup belongs in use or finally.

In Unwind, which line is never printed?

Once toInt/parseInt throws, the rest of parsePort is skipped and its frame is popped.

  1. main caught the exception, so execution carries on after its try/catch as normal.
  2. main's catch accepts NumberFormatException, so it stops the unwinding and prints this line.
  3. The line before it throws, so the rest of parsePort is skipped as its frame is popped.
  4. finally runs even while an exception passes through, which is exactly why this line prints.

Java rejects catching Exception before NumberFormatException. What does Kotlin 2.4 do with the same code?

The real compile produced no diagnostics. The second catch is just dead code.

  1. That's Java's behaviour. Kotlin 2.4 doesn't check catch order at all.
  2. No compiler reorders catch blocks. They're tried top to bottom, exactly as written.
  3. The real compile printed no warning at all, which is why you must check the order yourself.
  4. Kotlin accepts it silently, and the second catch becomes dead code that can never run.

The Caused by: section of a trace shows…

It's the cause passed to the constructor, as in IllegalStateException("…", e).

  1. The cause happened first. The outer exception was thrown afterwards, to wrap it.
  2. It's the exception passed as cause to the constructor, printed with its own frames.
  3. A trace never shows where an exception was caught, only the frames it was thrown through.
  4. An exception discarded by finally is lost completely. It appears nowhere in the trace.

Resources A then B are opened in one try-with-resources, or in nested use blocks. In what order are they closed?

They close in reverse order of opening (JLS §14.20.3), because B might depend on A.

  1. Resources close in reverse order of opening, so the last one opened is the first one closed.
  2. Closing in opening order could close A while B still depends on it.
  3. The closes run one after another on the same thread, in a defined order.
  4. Every resource that was opened gets closed, even if an earlier close() throws.

A return inside finally…

"…the throw of value V is discarded and forgotten" (JLS §14.20.2).

  1. Once finally returns, the pending exception is gone. Nothing rethrows it.
  2. Both compilers accept it. javac only warns with -Xlint, and Kotlin says nothing.
  3. The return ends the try statement abruptly, so the pending exception is discarded (JLS §14.20.2).
  4. finally always runs after the try block and any catch, never before.

One finally changes the variable being returned, the other returns its own value. What prints?

public class Finally {
    static int keep() {
        int x = 1;
        try {
            return x;
        } finally {
            x = 99;
        }
    }

    static int replace() {
        try {
            return 1;
        } finally {
            return 2;
        }
    }

    public static void main(String[] args) {
        System.out.println(keep() + " " + replace());
    }
}

return x evaluates x and saves the value 1 before finally runs, so setting x = 99 afterwards changes nothing. In replace(), the finally block's own return 2 ends the method abruptly and replaces the pending return, just as it discarded the exception in FinallyReturn (JLS §14.20.2).

  1. The pending return 1 doesn't survive: a return in finally overrides it.
  2. keep() returns the saved 1, and replace() returns the finally block's 2.
  3. The return value was saved before finally ran, so x = 99 can't reach it.
  4. Both halves are backwards: the saved value ignores x = 99, and the return in finally wins.

The body throws, and then both resources fail to close. What prints?

class Res(private val name: String) : AutoCloseable {
    override fun close() {
        print("close $name, ")
        throw IllegalStateException("close $name failed")
    }
}

fun main() {
    try {
        Res("A").use {
            Res("B").use {
                throw IllegalStateException("body failed")
            }
        }
    } catch (e: IllegalStateException) {
        println("caught ${e.message} (+${e.suppressed.size} suppressed)")
    }
}

The inner use closes B first. Its close failure is attached to the body's exception as suppressed, and the body's exception keeps travelling. The outer use then closes A and attaches that failure too. So the exception that reaches catch is the body's, carrying both close failures. Java's try-with-resources behaves the same way.

  1. Reverse close order, the body's exception wins, and each close failure is attached to it with addSuppressed.
  2. Nested use closes the innermost resource first, so B closes before A.
  3. That's what a hand-written finally that throws would do. use keeps the body's exception and suppresses close failures.
  4. A failing close() doesn't stop the outer use: A still closes, and the body's exception isn't lost.
Part 2

Checked vs unchecked

~33 min

Java splits exceptions into two kinds. Unchecked exceptions are RuntimeException, Error and their subclasses. Every other exception is checked (JLS §11.1.1). For checked exceptions, Java "requires that a program contains handlers": a method must either catch them or list them in its throws clause (JLS §11.2). Unchecked ones "do not need to be declared" (RuntimeException docs).

Checked.java:6: error: unreported exception IOException; must be caught or declared to be thrown
        return Files.readString(Path.of(name));   // readString declares: throws IOException
                               ^

The compiler gives you exactly two ways out: declare it with throws IOException, passing the decision to your caller, or catch it where you can actually do something useful:

using defaults, because: java.nio.file.NoSuchFileException: app.conf
Exception in thread "main" java.nio.file.NoSuchFileException: app.conf
	at java.base/sun.nio.fs.UnixException.translateToIOException(UnixException.java:92)
	…
	at java.base/java.nio.file.Files.readString(Files.java:3010)
	at CheckedKt.loadConfig(Checked.kt:5)
	at CheckedKt.main(Checked.kt:8)
	at CheckedKt.main(Checked.kt)

Kotlin compiled the very same JDK call without complaint, then crashed at runtime. The Kotlin docs: "Kotlin treats all exceptions as unchecked by default… you can catch exceptions, but you don't need to explicitly handle or declare them" (Kotlin docs: Exceptions). That's freedom, and also responsibility. Nothing reminds you that a file might be missing.

Which should you use? The Java tutorial's rule of thumb: "If a client can reasonably be expected to recover from an exception, make it a checked exception. If a client cannot do anything to recover from the exception, make it an unchecked exception" (dev.java: Unchecked exceptions, the controversy). Effective Java's exceptions chapter (Items 69–77) adds:

  • use exceptions only for exceptional conditions (Item 69)
  • use checked exceptions for recoverable conditions and runtime exceptions for programming errors (Item 70)
  • favour the standard exceptions (Item 72)
  • never ignore an exception with an empty catch (Item 77)

Custom exceptions

When callers need to react to a specific failure, and to read data about it, define your own exception class:

insufficient funds: short by 250 cents (shortBy=250)

Both classes extend Exception. In Java that makes it checked, so pay must declare throws InsufficientFundsException and every caller must deal with it. In Kotlin the same superclass means nothing extra. Put useful data in the exception (shortByCents) and in its message (Effective Java Item 75).

What Kotlin does for you.
  • try produces a value, so there's no "declare then assign in every branch".
  • ?: throw works because throw is an expression.
  • require, check and error replace three-line if … throw new … blocks, and their lazy message lambdas build the string only when the check fails.
  • No throws clauses anywhere.
What Java gives you that Kotlin doesn't: a compiler that won't let you forget a recoverable failure like a missing file.

Final answer

Why it works. The exception type is part of the message. IllegalArgumentException says "you called me wrong", IllegalStateException says "not now", and SeatTakenException says "this can happen, here's who has it", carrying the data a caller needs to offer another seat (Effective Java Items 72 and 75).   3. Both failures are IllegalArgumentExceptions, so the first catch handles both of them.
  4. That's how javac reacts. Kotlin 2.4 compiles the dead catch without an error or a warning.

sealed interface AgeResult {

    data class NotANumber(val text: String) : AgeResult
    data object Missing : AgeResult

fun readAge(row: String): AgeResult {

    return try {
        AgeResult.Ok(fields[2].trim().toInt())
    } catch (e: Exception) {

    }
}

import java.util.Objects;

public class Practice {
    sealed interface AgeResult permits Ok, NotANumber, Missing {}
    record Ok(int age) implements AgeResult {}
    record NotANumber(String text) implements AgeResult {}
    record Missing() implements AgeResult {}

    // A row looks like "name,age", e.g. "Ada,36".
    static AgeResult readAge(String row) {
        String[] fields = row.split(",");
        try {
            return new Ok(Integer.parseInt(fields[2].trim()));
        } catch (Exception e) {
            return new NotANumber(fields[fields.length - 1].trim());
        }
    }

    // CHECKS
    public static void main(String[] args) {
        check("a good row gives the age", new Ok(36), () -> readAge("Ada,36"));
        check("spaces around the fields are ignored", new Ok(41), () -> readAge(" Grace , 41 "));
        check("a non-number age keeps the text", new NotANumber("abc"), () -> readAge("Ada,abc"));
        check("a row with no age field is Missing, not NotANumber", new Missing(), () -> readAge("Ada"));
        check("a blank age is Missing", new Missing(), () -> readAge("Ada, "));

Final answer

Why it works. Every outcome a caller should handle is now a value of the sealed AgeResult, and each one is detected on purpose. A missing field is checked, and a bad number comes from toIntOrNull. Nothing is caught broadly, so if the code had another bug, such as a wrong index, it would crash in testing instead of hiding as bad data.

Common mistake. Fixing the index but keeping catch (e: Exception). "Ada" then throws IndexOutOfBoundsException, the broad catch swallows it, and a missing field is reported as NotANumber("Ada").

A programming error should fail fast and loudly, with require / IllegalArgumentException (Effective Java Item 70).

  1. null hides the bug: the caller carries on, and the failure surfaces later somewhere unrelated.
  2. Logging and continuing means running on with a value you already know is wrong.
  3. A caller's bug should fail fast where it happens, with require / IllegalArgumentException.
  4. A result type forces every caller to handle a case that only a bug can produce.

Absence is normal and needs no explanation: String? or Optional.

  1. Having no middle name is normal, not exceptional (Effective Java Item 69).
  2. Absence is ordinary and needs no reason, which is exactly what String? or Optional express.
  3. There's only one way to have no middle name, so a result type adds ceremony and nothing else.
  4. Ending the program over missing optional data would stop every user for a normal case.

A sign-up form must tell the user why each field was rejected. Best design?

Failure is expected and carries a reason, and the compiler makes sure each one is handled.

  1. Rejected input is expected on a form, and an exception stops at the first bad field.
  2. A bad field is a normal event, so the program must keep running and explain it.
  3. null says that something failed but not what, so the form can't tell the user.
  4. Each reason is its own case carrying data, and an exhaustive when makes every caller handle all of them.

Why did readAge with the broad catch return −1 for "Ada,36"?

Index 2 doesn't exist. catch (Exception) caught that bug and disguised it as bad input.

  1. fields[2] doesn't exist, and catch (Exception) turned that bug into a believable −1.
  2. "36" was never parsed at all: the code read index 2, which doesn't exist.
  3. toInt() throws on bad input, and toIntOrNull() returns null. Neither returns −1.
  4. "Ada,36" has a comma, so split gives two fields, at indexes 0 and 1.

Kotlin's runCatching catches…

The docs say it catches "any Throwable exception", which is broader than most code should be.

  1. It also catches checked exceptions and Errors: anything that is a Throwable.
  2. Kotlin has no declarations to go by. runCatching catches whatever the block throws.
  3. It logs nothing. It wraps the exception in a failed Result for you to inspect.
  4. It catches any Throwable, so even an Error such as OutOfMemoryError becomes a failed Result.

An unfinished branch meets runCatching, then a catch (e: Exception). What prints?

fun discount(code: String): Int = when (code) {
    "HALF" -> 50
    "NONE" -> 0
    else -> TODO("discount for $code")
}

fun main() {
    val safe = runCatching { discount("VIP") }.getOrDefault(0)
    println("runCatching gave $safe")
    try {
        discount("VIP")
    } catch (e: Exception) {
        println("the Exception branch ran")
    } catch (e: Throwable) {
        println("the Throwable branch ran")
    }
}

TODO() throws NotImplementedError, which is an Error, not an Exception. runCatching catches any Throwable, so it quietly hands back the default 0: unfinished code disguised as "no discount". catch (e: Exception) doesn't match it, so only the Throwable branch catches it.

  1. NotImplementedError extends Error, so catch (e: Exception) doesn't match it.
  2. runCatching catches every Throwable, Errors included, and returns a failed Result.
  3. TODO() has type Nothing, a subtype of every type, so it fits where an Int is expected.
  4. runCatching turns the Error into a failed Result, and afterwards only Throwable is broad enough to catch it.

Exit quiz, recall card, sources

~5 min

You add a new case to a sealed PortResult that's handled by a when with no else. What happens?

That's the point of exhaustive matching (L7): new failure reasons can't slip through unnoticed.

  1. A when without else must be exhaustive, so the gap is caught before anything runs.
  2. The check happens at compile time, so the code never runs with a branch missing.
  3. Every when that no longer covers all cases stops compiling, which points you at each one.
  4. This isn't a runtime concern. You handle the new case and recompile.

Runaway recursion throws StackOverflowError (L4). Should normal code catch it?

An Error "indicates serious problems that a reasonable application should not try to catch" (Error docs).

  1. A StackOverflowError signals a bug, usually a missing base case, so fix the code.
  2. Catching every Throwable hides bugs, including Errors the program can't sensibly recover from.
  3. The same input recurses the same way, so calling again just overflows again.
  4. finally catches nothing. It runs cleanup while the error keeps propagating.

Math.addExact(Int.MAX_VALUE, 1) (L2) throws…

It's an unchecked RuntimeException subclass, so no throws clause is needed in either language.

  1. No text is parsed here. NumberFormatException is for strings like "80x".
  2. addExact throws ArithmeticException on overflow instead of silently wrapping to a negative number.
  3. Overflow is an arithmetic problem, not an object in the wrong state.
  4. There's no recursion here, and a single addition can't overflow the stack.
