Part 1

Exceptions and stack traces

~30 min

An exception is an object that describes something going wrong. You throw it, and the JVM then searches for a handler, a catch block that accepts that type. It starts in the current frame and works outward through the call stack, popping each frame that doesn't handle it. That process is called unwinding. If no frame catches the exception, the thread ends and the JVM prints a stack trace (dev.java: What is an exception?).

parsePort: parsing "80x"
startServer: finally runs while unwinding
main caught: For input string: "80x"
main continues

Step through it. Watch the frames pop as the exception passes through them:

When nobody catches it

Remove the try from main, and the exception unwinds every frame. The trace is that journey, printed top-down:

Exception in thread "main" java.lang.NumberFormatException: For input string: "80x"
	at java.base/java.lang.NumberFormatException.forInputString(NumberFormatException.java:67)
	at java.base/java.lang.Integer.parseInt(Integer.java:527)
	at java.base/java.lang.Integer.parseInt(Integer.java:624)
	at UncaughtKt.parsePort(Uncaught.kt:1)
	at UncaughtKt.startServer(Uncaught.kt:3)
	at UncaughtKt.main(Uncaught.kt:6)
	at UncaughtKt.main(Uncaught.kt)

How to read it:

  1. The first line gives the type and the message.
  2. The next lines are the stack, top-down. The java.base/… frames are JDK code. Skim down to the first frame in your code, here parsePort(Uncaught.kt:1). That's where to start looking.
  3. Read further down to see who called it.

Kotlin's toInt() calls Java's Integer.parseInt underneath, which is why both traces show the same JDK frames. The Java version is the same apart from the class names.

The quotes come from the JDK docs for Throwable and Error. A catch block catches its type and every subtype, so catch (IllegalArgumentException e) also catches a NumberFormatException. That's why order matters: list the most specific types first.

CatchOrder.java:7: error: exception NumberFormatException has already been caught
        } catch (NumberFormatException e) {         // ...so this can never run
          ^

Kotlin 2.4 compiles its version without any error or warning and prints something failed. The second catch is silently dead code. Kotlin won't catch this one for you, so put the specific types first yourself.

Chained causes: "Caused by:"

Low-level exceptions often don't make sense higher up: "For input string: 80x" means nothing to the code that was loading a config file. Good practice is to catch it, and throw a higher-level exception that keeps the original as its cause. Effective Java Item 73 calls this throwing exceptions "appropriate to the abstraction" (see also dev.java: Chained exceptions):

$ javac Chained.java && java Chained
Exception in thread "main" java.lang.IllegalStateException: could not load config 'app.conf'
	at Chained.loadConfig(Chained.java:9)
	at Chained.main(Chained.java:14)
Caused by: java.lang.NumberFormatException: For input string: "80x"
	at java.base/java.lang.NumberFormatException.forInputString(NumberFormatException.java:67)
	at java.base/java.lang.Integer.parseInt(Integer.java:527)
	at java.base/java.lang.Integer.parseInt(Integer.java:624)
	at Chained.parsePort(Chained.java:2)
	at Chained.loadConfig(Chained.java:6)
	... 1 more

Read the top section for what failed, and the Caused by: section for why. The ... 1 more line means "the remaining frames are the same as the enclosing exception's". The JDK docs explain that these lines indicate "the remainder of the stack trace for this exception matches the indicated number of frames from the bottom of the stack trace of the exception that was caused by this exception" (Throwable.printStackTrace). The Kotlin run prints the same shape, ending in ... 2 more because of Kotlin's extra main bridge frame.

finally, and the one thing never to do in it

A finally block runs whether the try succeeded, threw, or returned. That's what made startServer's message print during unwinding. It exists for cleanup. But if the finally block itself completes abruptly, for example by returning, the spec says the original exception "is discarded and forgotten" (JLS §14.20.2):

-1
no one ever hears about the failure

Both languages compile this without complaint by default. javac only warns if you ask for lint warnings:

$ javac -Xlint:all FinallyReturn.java
FinallyReturn.java:7: warning: [finally] finally clause cannot complete normally

Never return or throw from finally.

Cleaning up resources: try-with-resources and use

Files, network connections and database connections must be closed even when something fails. Java's try-with-resources closes any AutoCloseable declared in its header, "in the reverse order from that in which they were initialized" (JLS §14.20.3). Kotlin has no special syntax for this. It uses an ordinary extension function, use, which "closes it down correctly whether an exception is thrown or not" (Kotlin API: use).

open A
open B
using A and B
close B
close A
open C
close C
caught: body failed
  suppressed: close C failed

The second block shows suppressed exceptions. The body threw, and then close() threw too. Only one exception can propagate, so the body's exception wins, and the close failure is attached to it rather than lost. Throwable.addSuppressed is "typically called (automatically and implicitly) by the try-with-resources statement" (Throwable docs), and Kotlin's use does the same. In an uncaught trace these show up as indented Suppressed: sections.

What Kotlin does for you. use is just a library function, not new syntax, and it works on anything AutoCloseable. Nesting use blocks gives the same reverse close order as Java's multi-resource header. The { a -> … } after use is a lambda, which L14 covers properly. One caution, where Kotlin does less than Java: the wrong-order catch above compiles silently in Kotlin.

Part 2

Checked vs unchecked

~25 min

Java splits exceptions into two kinds. Unchecked exceptions are RuntimeException, Error and their subclasses. Every other exception is checked (JLS §11.1.1). For checked exceptions, Java "requires that a program contains handlers": a method must either catch them or list them in its throws clause (JLS §11.2). Unchecked ones "do not need to be declared" (RuntimeException docs).

Checked.java:6: error: unreported exception IOException; must be caught or declared to be thrown
        return Files.readString(Path.of(name));   // readString declares: throws IOException
                               ^

The compiler gives you exactly two ways out: declare it with throws IOException, passing the decision to your caller, or catch it where you can actually do something useful:

using defaults, because: java.nio.file.NoSuchFileException: app.conf
Exception in thread "main" java.nio.file.NoSuchFileException: app.conf
	at java.base/sun.nio.fs.UnixException.translateToIOException(UnixException.java:92)
	…
	at java.base/java.nio.file.Files.readString(Files.java:3010)
	at CheckedKt.loadConfig(Checked.kt:5)
	at CheckedKt.main(Checked.kt:8)

Kotlin compiled the very same JDK call without complaint, then crashed at runtime. The Kotlin docs: "Kotlin treats all exceptions as unchecked by default… you can catch exceptions, but you don't need to explicitly handle or declare them" (Kotlin docs: Exceptions). That's freedom, and also responsibility. Nothing reminds you that a file might be missing.

Which should you use? The Java tutorial's rule of thumb: "If a client can reasonably be expected to recover from an exception, make it a checked exception. If a client cannot do anything to recover from the exception, make it an unchecked exception" (dev.java: Unchecked exceptions, the controversy). Effective Java's exceptions chapter (Items 69–77) adds:

  • use exceptions only for exceptional conditions (Item 69)
  • use checked exceptions for recoverable conditions and runtime exceptions for programming errors (Item 70)
  • favour the standard exceptions (Item 72)
  • never ignore an exception with an empty catch (Item 77)

  • In Kotlin, try produces a value: the last expression of the try block, or of whichever catch ran (Kotlin docs). In Java it's a statement, so you declare the variable first and assign it in each branch.
  • In Kotlin, throw is an expression whose type is Nothing, "a subtype of all other types" (Kotlin docs). That's why settings["port"] ?: throw … type-checks as a String.
  • A trap on the Java side: Objects.requireNonNull throws a NullPointerException, not an IllegalArgumentException. Choose it when null really is the problem.

Custom exceptions

When callers need to react to a specific failure, and to read data about it, define your own exception class:

insufficient funds: short by 250 cents (shortBy=250)

Both classes extend Exception. In Java that makes it checked, so pay must declare throws InsufficientFundsException and every caller must deal with it. In Kotlin the same superclass means nothing extra. Put useful data in the exception (shortByCents) and in its message (Effective Java Item 75).

What Kotlin does for you.
  • try produces a value, so there's no "declare then assign in every branch".
  • ?: throw works because throw is an expression.
  • require, check and error replace three-line if … throw new … blocks, and their lazy message lambdas build the string only when the check fails.
  • No throws clauses anywhere.
What Java gives you that Kotlin doesn't: a compiler that won't let you forget a recoverable failure like a missing file.

Part 3

Throw vs return null vs a result type

~25 min

"Parse a port number from user input" can fail. There are three honest ways to tell the caller about it, and each is right somewhere:

8080 -> 8080 | 8080 | port 8080
http -> threw: not a number: 'http' | null | 'http' is not a number
99999 -> threw: out of range: 99999 | null | 99999 is outside 1..65535
isSuccess=false, error=out of range: 99999, or default=80
8080 -> 8080 | 8080 | port 8080
http -> threw: not a number: 'http' | empty | 'http' is not a number
99999 -> threw: out of range: 99999 | empty | 99999 is outside 1..65535
DesignUse it when…KotlinJava
Throwfailure means a bug or a broken precondition, so the caller shouldn't have askedrequire, throwthrow new IllegalArgumentException(…)
Return null / empty"nothing there" is a normal answer and the reason doesn't matterInt?, toIntOrNull()Optional / OptionalInt
Return a sealed resultfailure is normal and the caller needs to know why, e.g. to show the usersealed interface + whensealed interface + records + switch

The third design is L7's PaymentResult idea applied to errors. The compiler forces every caller to handle every outcome, and adding a new failure reason breaks the build wherever it isn't handled. Kotlin's built-in runCatching wraps "value or exception" in a Result. It's convenient, but it catches "any Throwable", including Errors, so prefer your own sealed type when the failures are part of your domain.

Catching too broadly hides bugs

broad catch says age = -1
Exception in thread "main" java.lang.IndexOutOfBoundsException: Index 2 out of bounds for length 2
	at java.base/java.util.ArrayList.get(ArrayList.java:428)   (JDK frames trimmed)
	at BroadCatchKt.readAgeNarrow(BroadCatch.kt:11)
	at BroadCatchKt.main(BroadCatch.kt:19)
broad catch says age = -1
Exception in thread "main" java.lang.IndexOutOfBoundsException: Index: 2 Size: 2
	at java.base/java.util.ImmutableCollections$AbstractImmutableList.outOfBounds(…)
	at java.base/java.util.ImmutableCollections$List12.get(…)
	at BroadCatch.readAgeNarrow(BroadCatch.java:15)
	at BroadCatch.main(BroadCatch.java:24)

The broad catch (Exception) turned an off-by-one bug into a believable "invalid age". You'd ship it, and every user's age would read as −1. The narrow catch handles only the failure it was written for, so the bug crashes loudly in testing, with a trace pointing straight at it. Catch the narrowest type you can actually handle, and let everything else propagate.

What Kotlin does for you. toIntOrNull() plus ?: return makes the null design a two-liner, where Java needs a try/catch just to ask whether something is a number. Kotlin's when over a sealed result needs no else, and the branches smart-cast. Java 21's pattern switch now matches it, but needs separate record declarations. runCatching gives you a ready-made Result, but you have to remember how broadly it catches.

Final exercise

A config-line parser

~20 min

From a blank file, Kotlin then Java, using the examples, plan, code, check routine from L2:

Input (hard-code it as a multi-line string; reading real files is L22):

# server config
port=8080
timeout=abc
host=
garbage
retries = 3
  1. Read it line by line with a BufferedReader(StringReader(text)) inside use / try-with-resources. In Java, readLine() declares IOException, so decide where to deal with it.
  2. A low-level splitEntry(lineNo, line) throws a custom ConfigFormatException when there's no =.
  3. A boundary function parseLine turns every outcome into a sealed LineResult: Entry, BadValue (empty value, or a non-number for port/timeout/retries), Malformed (built from the caught exception's message), or Skipped (blank or #).
  4. Print one line per input line, then a summary.
line 1: skipped
line 2: port = 8080
line 3: timeout: 'abc' is not a whole number
line 4: host: value is empty
line 5: missing '=' in "garbage"
line 6: retries = 3
summary: 2 ok, 2 bad values, 1 malformed, 1 skipped

Why it's shaped this way: the exception lives at the low level, where "no =" really is exceptional for a splitting function. At the boundary it becomes a value, because for a config report, a bad line is expected data, not a crash. Note what is not caught: no catch (Exception) anywhere, so a genuine bug in this code would still surface. In Java, main declares throws IOException, because reading from a StringReader can't really fail and there's nothing useful to do here if it did. In Kotlin nobody asked.
