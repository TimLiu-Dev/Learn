Binary search finds an item among a million in about 20 steps. What does it require? (L18)

Each comparison throws away half of a sorted range, so it's O(log n). Hashing aims lower still, at O(1), and doesn't need sorting at all.

  1. A linked list can't jump to its middle in one step, so binary search needs an array, not a list.
  2. Each comparison discards half the range, and that only works when the items are in order.
  3. Binary search never hashes anything. It compares the target with the middle element.
  4. A balanced tree also gives O(log n) lookups, but binary search runs on a plain sorted array.

What's the cost of list.contains(x) on an unsorted ArrayList of n items? (L16)

It checks the elements one by one with equals. In the worst case that's all n of them. A hash table skips straight to the one place the item could be.

  1. O(1) needs a way to jump straight to the item, as hashing does. A list has to look.
  2. O(log n) needs sorted data to halve the range. Unsorted data can't be halved.
  3. That's the cost of sorting first. contains doesn't sort; it just scans.
  4. It may compare x with every element once, so the worst case is n comparisons.

A Java class overrides equals but not hashCode. You add two equal objects to a HashSet. What's its size? (L7)

Different identity hash codes send the two "equal" objects to different buckets, so the set never compares them. Part 3 shows exactly why.

  1. Their identity hashes almost certainly differ, so the set never calls equals and keeps both.
  2. A set spots a duplicate only when hashCode agrees first. equals alone is never reached.
  3. Both add calls succeed and nothing removes them, so the size can't be 0.
  4. Overriding only equals is legal Java. It's a bug the compiler can't see.

An ArrayList doubles its array when full. Why is add still "amortised O(1)"? (L16)

A copy of n elements happens only after about n cheap adds, so the average cost per add stays constant. Hash tables resize with the same trick.

  1. Copying n elements costs O(n). It's how rarely copies happen that keeps the average low.
  2. The copy happens inside add, on your thread. The JVM doesn't do it for you.
  3. A copy of n elements comes only after about n cheap adds, so each add pays a constant share.
  4. Elements are copied at every resize, so some are copied several times. The total stays under 2n.

Kotlin: val a = Point(1, 2); val b = Point(1, 2) (a data class). What does a === b give? (L5)

=== is identity: two separate objects. a == b is true, because the data class's equals compares values. A hash map needs value equality, not identity.

  1. That's a == b, which calls the data class's equals. === checks identity.
  2. Two constructor calls make two objects, so the identity check says false.
  3. Comparing references never throws: it only asks whether they point to the same object.
  4. === works on any two references of compatible types, so this compiles.
Part 1

Hashing and collisions

~33 min

An array gives you O(1) access, but only by a number: items[5]. A hash table extends that to any key. It turns the key into a number, uses the number as an array index, and stores the entry in that slot, called a bucket:

StepWhat happensExample
1 · hashkey.hashCode() turns the key into an Int"cat" → 98262
2 · indexsqueeze that number into 0 until capacity98262 mod 16 → 6
3 · bucketlook in that one bucket and compare keys with equalsbuckets[6]

If the hash spreads keys evenly, each bucket holds about one entry, and lookups cost O(1) on average no matter how big the table gets. Sedgewick and Wayne call this the uniform hashing assumption: "the hash function that we use uniformly distributes keys among the integer values between 0 and M−1" (Algorithms §3.4: Hash Tables).

Where hash codes come from

The JDK specifies String.hashCode exactly: "s[0]*31^(n-1) + s[1]*31^(n-2) + ... + s[n-1] using int arithmetic" (JDK docs: String.hashCode). So you can compute one by hand:

  • It's just arithmetic on the characters. 'c' is 99, 'a' is 97 and 't' is 116, so 99·31² + 97·31 + 116 = 98262.
  • Overflow is fine. Longer strings overflow Int and wrap around (L2), so "banana" gets a negative hash. That's legal, and it matters in a moment.
  • Different keys can share a hash. "Aa" and "BB" both give 2112. There are only about 4 billion Ints, and infinitely many strings.
  • Your own classes: Kotlin data classes and Java records generate hashCode from their fields (Kotlin docs: Data classes, JEP 395). In a plain Java class you write it yourself, usually with Objects.hash(x, y), which combines the fields' hashes "as if all the input values were placed into an array" and hashed with Arrays.hashCode (JDK docs: Objects.hash). The exact numbers differ, which is fine: they only need to be consistent with equals.

  • % keeps the sign of the left side. Kotlin's rem result "has the same sign as the dividend" (Kotlin API: rem), and Java's % behaves the same. A negative hash gives a negative index, and the program crashes.
  • Use floor modulus instead. Kotlin's mod result "has the same sign as the divisor" (Kotlin API: mod), and so does Java's Math.floorMod (JDK docs). With a positive capacity you always get 0 until capacity. Sedgewick's code does it a third way, masking off the sign bit: (key.hashCode() & 0x7fffffff) % M.
  • Powers of two allow a shortcut. When the capacity is 2ᵏ, h & (capacity − 1) keeps the low k bits, which is the same as floor mod but cheaper.
  • What HashMap really does (implementation detail, not a guarantee): its capacity is always a power of two, and before masking it mixes the high bits into the low ones with (h = key.hashCode()) ^ (h >>> 16). Otherwise "sets of hashes that vary only in bits above the current mask will always collide" (OpenJDK source: HashMap.hash). That's the spread line above.

Collisions are guaranteed, and sooner than you think

Two different keys landing in the same bucket is a collision. With more keys than buckets it's unavoidable: that's the pigeonhole principle. But it happens long before the table is full. With 23 people and 365 birthdays, there's already a 50% chance that two of them share one, which is the "birthday paradox" from Sedgewick's §3.4 exercises:

23 people, 365 days: shared birthday in 50.665% of trials
exact: 50.7%
1,000,000 buckets: first collision after ~1266 keys on average

Even a million buckets get their first collision after only about 1,266 random keys, close to the classic birthday-problem estimate √(πM/2) ≈ 1,253. Both programs print identical numbers because they share java.util.Random(42). So every hash table needs a plan for collisions, and there are two classic ones (Algorithms §3.4):

chaining:
  [2] [10, 18, 26]
  [3] [3, 11]
linear probing:
  put 10: home 2, landed in 2 after 1 probe(s)
  put 18: home 2, landed in 3 after 2 probe(s)
  put 3: home 3, landed in 4 after 2 probe(s)
  put 26: home 2, landed in 5 after 4 probe(s)
  put 11: home 3, landed in 6 after 4 probe(s)
  _ _ 10 18 3 26 11 _
  • Separate chaining: each bucket holds a linked list of every entry that hashed there (L17's nodes). A lookup walks one short chain. This is what HashMap uses, and what you'll build.
  • Open addressing / linear probing: one entry per slot. If the slot is taken, try the next one, wrapping around. There are no node objects, but neighbouring keys pile into clusters. Look at 3: it never collided with an equal hash, yet it was pushed out of its home slot by 18. Deleting is also tricky, since an empty hole would break later searches.

Load factor and resizing

The load factor is size / capacity: entries per bucket. With chaining, the average chain length is the load factor, so to keep lookups O(1) the table must grow as it fills. HashMap's docs: "When the number of entries in the hash table exceeds the product of the load factor and the current capacity, the hash table is rehashed… so that the hash table has approximately twice the number of buckets." The no-argument constructor uses "the default initial capacity (16) and the default load factor (0.75)", which "offers a good tradeoff between time and space costs" (JDK docs: HashMap). Every key must be rehashed, because its index depends on the capacity. That's an O(n) copy, but like L16's dynamic array it happens rarely enough to be amortised O(1).

Hint 1 of 3

Both functions walk the same probe path, so write it once: a private find(key) that returns the slot holding the key, or the first empty slot it meets. Start at key.hashCode().mod(capacity).

Hint 2 of 3

Step with i = (i + 1) % capacity, which wraps the last slot back to 0. Stop after capacity steps, or a full table makes get loop forever; return -1 then. put stores the key only if the slot was empty, and always writes the value.

Hint 3 of 3

put: val i = find(key); check(i >= 0) { "table is full" }, then fill the slot. get: if (i >= 0 && keys[i] == key) values[i] else null. In Java, the start is Math.floorMod(key.hashCode(), keys.length), and you throw the exception yourself.

Final answer

Why it works. A key is always stored on its own probe path, the run of slots from its home slot forward. So get can stop at the first empty slot: if the key were in the table, put would have placed it there or earlier. Counting steps bounds the walk when no slot is empty.

Common mistake. Starting at key.hashCode() % capacity. "banana" has a negative hash, so % gives −11 and the array access throws. Use mod (Math.floorMod) for the home slot.

Why must a hash table turn hashCode() into an index with floor mod rather than %?

"banana".hashCode() % 16 is −11, and indexing with it threw ArrayIndexOutOfBoundsException. Floor mod keeps the result in 0 until capacity.

  1. Speed isn't the issue: % is just as fast. The problem is the sign of its result.
  2. % doesn't round. Its result takes the sign of the left operand, so it can be negative.
  3. A negative hash makes % negative, an invalid index. Floor mod always lands in 0 until capacity.
  4. h % capacity is always smaller than the capacity in size. Only its sign can be wrong.

"Aa".hashCode() == "BB".hashCode()

Both are 2112: 65·31 + 97 = 66·31 + 66. Equal hashes for unequal keys are allowed, which is why buckets must still compare keys with equals.

  1. 65·31 + 97 and 66·31 + 66 both equal 2112, so the hash codes are the same.
  2. Unequal strings can share a hash code: there are far more strings than Ints.
  3. hashCode on a string never throws. It's plain arithmetic on the characters.
  4. Comparing two Ints with == is fine in both languages.

A default HashMap holds 12 entries. You add a 13th. What happens?

16 × 0.75 = 12. The 13th entry pushes the size past the threshold, so the table is rehashed to about twice the buckets (JDK docs).

  1. HashMap has no size limit. Passing the threshold triggers a resize, not an error.
  2. Dropping entries is what an LRU cache does on purpose. A plain HashMap keeps everything.
  3. 12 is the threshold (16 × 0.75), and the 13th entry crosses it, so the table changes.
  4. Size 13 exceeds 16 × 0.75 = 12, so the table rehashes into twice the buckets: 32.

In linear probing, what happens when a key's home slot is already taken?

That's the "probe". A linked list per bucket is separate chaining, the other strategy.

  1. Open addressing never drops keys. It keeps probing until it finds a free slot.
  2. Linear probing steps to the next slot, wrapping at the end, until it finds a free one.
  3. Resizing depends on the load factor, not on one collision. A taken slot just means: probe.
  4. A list per bucket is separate chaining. Probing stores one key per slot, with no lists.

Exercise: MyHashMap in five steps, from a blank file

Practice · Grow before you're full

IntSet is a linear-probing set of Ints. add and contains already work, and add calls resize() once more than half the slots are used. Write resize():

  • Double the number of slots.
  • Put every element into the new array at the slot it belongs in there. find takes the table as a parameter so you can use it for the new array.
  • size doesn't change: a resize moves elements, it doesn't add any.
// Linear probing for Ints, kept at most half full so probe runs stay short.
class IntSet {
    private var slots = arrayOfNulls<Int>(8)
    var size = 0
        private set
    val capacity: Int get() = slots.size

    fun contains(x: Int): Boolean = slots[find(slots, x)] == x

    fun add(x: Int): Boolean {
        val i = find(slots, x)
        if (slots[i] == x) return false
        slots[i] = x
        size++
        if (size > capacity / 2) resize()
        return true
    }

        TODO("double the slots and put every element where it belongs in the new array")

    // The slot holding x, or the first empty slot on its probe path.

        while (table[i] != null && table[i] != x) i = (i + 1) % table.size
        return i

Object.hashCode's contract says: "If two objects are equal according to the equals method, then calling the hashCode method on each of the two objects must produce the same integer result." Unequal objects may share a hash, but "producing distinct integer results for unequal objects may improve the performance of hash tables" (JDK docs: Object.hashCode).   • HashMap order is bucket order. The docs promise nothing: "This class makes no guarantees as to the order of the map; in particular, it does not guarantee that the order will remain constant over time." The demo proves the second half. Same six keys, but after a resize to 32 buckets and back down to six entries, the order changed. Never write code, or a test, that depends on it.
  • LinkedHashMap is a HashMap that also "maintains a doubly-linked list running through all of its entries", so iteration follows insertion order (JDK docs: LinkedHashMap). It's still O(1) per operation, with a little more memory per entry.
  • Kotlin's defaults are the ordered ones. "LinkedHashMap is the default implementation of MutableMap. It preserves the order in which you insert the entries", and likewise LinkedHashSet for sets (Kotlin docs: Collection types). The javaClass lines confirm it. Use hashMapOf() when you want a plain HashMap. That's why L3's word counter printed words in first-seen order in Kotlin.
  • TreeMap keeps keys sorted, at O(log n) per operation, because it's a balanced tree. That's L20.
  • HashSet "implements the Set interface, backed by a hash table (actually a HashMap instance)" (JDK docs: HashSet). In the OpenJDK source, every element is stored as a key with the same dummy value, PRESENT. Everything in Part 3 applies to sets too.
  • ConcurrentHashMap is the thread-safe one. HashMap's docs say that if several threads use one and any of them modifies it, it "must be synchronized externally". That's for the concurrency phase.

An LRU cache in ten lines

LinkedHashMap has a second mode. Pass accessOrder = true and it orders entries "in which its entries were last accessed, from least-recently accessed to most-recently (access-order). This kind of map is well-suited to building LRU caches." Then override removeEldestEntry, which put consults after every insert. The docs' own example is return size() > MAX_ENTRIES; (JDK docs: removeEldestEntry).

access order: [b, c, a]
cache: [c, a, d]

Reading a made it the most recent, so when d arrived, b was the eldest and got evicted. A least-recently-used (LRU) cache is the standard answer to "keep the hot data in memory, but bounded". You'll meet it again in L41, on latency and caching. The final wraps this in a proper class with tests.

What Kotlin does for you. mutableMapOf() already gives you insertion order, where Java makes you choose LinkedHashMap explicitly. object : LinkedHashMap<…>(…) { override fun … } is Kotlin's anonymous subclass, the equivalent of Java's new LinkedHashMap<>(…) { … }, and with an expression body the override fits on one line. getOrPut is computeIfAbsent with a friendlier name.

Hint 1 of 3

When you reach x, the number it needs is target - x. A map from value to index answers "have I already seen that number, and where?" in O(1).

Hint 2 of 3

Order matters inside the loop: look up the partner before you put x into the map. Otherwise [3, 4] with target 6 pairs the 3 with itself. For countPairs, the map holds counts, and each x adds as many pairs as there were earlier partners.

Hint 3 of 3

twoSum: indexOf[target - x]?.let { return it to j }, then indexOf[x] = j. countPairs: pairs += seen[target - x] ?: 0, then seen.merge(x, 1, Int::plus). In Java, seen.getOrDefault(target - x, 0) and seen.merge(x, 1, Integer::sum).

Final answer

Why it works. When the loop reaches index j, the map holds exactly the numbers before it. So every pair i < j is found once, at j, with one O(1) lookup. That's O(n) in total, where checking every pair is O(n²).

Common mistake. Putting x into the map before looking up its partner. When x is exactly half the target, it finds itself: [3, 4] with target 6 returns (0, 0) instead of null.

A test asserts that a HashMap's keys come out as [a, b, c]. What's wrong?

The docs guarantee no order, not even a stable one. It may pass today and fail after a resize or a JDK upgrade.

  1. Sorting the expected list doesn't help: HashMap order isn't sorted either.
  2. Strings are ideal keys: immutable, with a well-defined hashCode.
  3. assertEquals compares lists element by element, in order. That's what makes this fragile.
  4. Bucket order can change with the capacity or the JDK version. Never assert on it.

What makes a LinkedHashMap evict entries automatically?

accessOrder only changes the iteration order. Eviction happens when removeEldestEntry returns true after an insert.

  1. put asks removeEldestEntry after each insert, and returning true evicts the eldest.
  2. Access order only decides which entry is eldest. Nothing is removed without the override.
  3. The load factor controls resizing, which adds buckets. It never removes entries.
  4. LinkedHashMap has no trimToSize. That's an ArrayList method, and it frees capacity, not elements.

fun main() {

    println(m.keys)
}

Updating a key that's already there keeps its place: "encounter order is not affected if a key is re-inserted into the map" (JDK docs: LinkedHashMap). Removing a forgets it, so putting it back is a new insertion, at the end.

  1. c keeps first place despite the update, and a, removed and added again, goes to the end.
  2. That's sorted order, which you'd get from a TreeMap. This map follows insertion order.
  3. Updating c's value doesn't move it. Only a brand-new insertion goes to the end.
  4. After remove, a has no remembered position. Putting it back appends it.

Which assertion fits "remove on a missing key returns null"? (L11)

assertNull(m.remove("cat")). Use assertThrows only if your design throws for missing keys, like Kotlin's getValue.

  1. assertThrows expects an exception, but a missing key returns null here.
  2. assertTrue needs a Boolean, and remove returns a value or null.
  3. assertNull(m.remove("cat")) states exactly the expected result.
  4. assertSame checks two references for identity. Here there's one result to check.

Your Java MyHashMap creates its bucket array as (Entry<K, V>[]) new Entry[8]. Why the cast? (L13)

new Entry<K, V>[8] is illegal because of erasure, so you create a raw array and cast it. That's safe here because the array never leaves the class, which is why it's suppressed on the smallest scope.

  1. Erasure means the runtime can't create an array of Entry<K, V>, so you cast a raw one.
  2. Ordinary arrays such as new String[8] need no cast. Only generic element types do.
  3. A private nested class works fine as an array type. The type parameters are the problem.
  4. The capacity is right there, the literal 8. Size has nothing to do with the cast.

A chain in your map is a singly linked list. To remove a node from the middle you need… (L17)

You set prev.next = target.next. A singly linked node doesn't know its predecessor, so you track it while walking.

  1. A linked list has no indexes to jump to. You still walk to the node.
  2. Copying the chain is O(n) extra work and memory. Relinking one pointer is enough.
  3. The target already links to its next node. What's missing is the link into the target.
  4. Setting prev.next = target.next skips the target, so you need the node before it.

Kotlin: data class Tag(var name: String) is used as a HashSet element, then name changes. Then set.contains(tag)… (L7 + L19)

The generated hashCode now points to a different bucket, so the set looks in the wrong place. This is MutableKey again, in set form.

  1. True would need the set to find it, but it searches the bucket for the new hash.
  2. The element is still filed under its old hash, so the lookup misses and returns false.
  3. contains doesn't detect a changed element. It just fails to find it.
  4. A var in a data class is legal. The compiler can't know you'll mutate a set element.
