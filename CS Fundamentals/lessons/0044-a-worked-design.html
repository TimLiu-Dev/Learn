  2. Name the four golden signals, and say which one a p99 belongs to. (L43)
  3. A queue delivers "at least once". What must the consumer be, and why? (L42)

A circuit breaker's reset timeout has passed, and it lets one trial call through. Which state is it in? (L43)

Fowler: "a third state present - half open - meaning the circuit is ready to make a real call as trial to see if the problem is fixed" (CircuitBreaker). Success closes it again; failure re-opens it.

Token bucket: capacity 10, refill 1 per second. The client was idle for 30 s, then sends 15 requests at once. How many are allowed? (L43)

Tokens accumulate while idle but are capped at the capacity, so the burst can use at most 10. That cap is what makes a token bucket allow bursts without allowing floods.

With consistent hashing, you add a 5th node to 4. Roughly how many keys move? (L42)

Only the keys on the arcs the new node takes over move, about 1/5. With plain hash % N, changing N from 4 to 5 moves most keys. You'll lean on this when the shortener outgrows one database.

A hot key expires and 500 requests miss the cache at the same moment. The standard fix? (L41)

A stampede is many identical misses at once. Coalescing (one loader, everyone else waits for its result) turns 500 database queries into 1. A shortener's most popular link is exactly this kind of hot key.

Part 1

Requirements and estimates

~25 min

A URL shortener turns https://example.com/some/very/long/path?with=params into https://sho.rt/4xdNF0v, and redirects anyone who visits the short one. It sounds like a weekend project, which is why it's the classic first design problem: small enough to hold in your head, but it touches every Phase 12 idea.

How to approach a design question

The System Design Primer frames it as "an open-ended conversation. You are expected to lead it", in four steps (System Design Primer: How to approach a system design interview question):

  1. Outline use cases, constraints, and assumptions. Who uses it, how much data, how many requests per second, "What is the expected read to write ratio?"
  2. Create a high level design. "Sketch the main components and connections. Justify your ideas."
  3. Design core components. Its own example is a URL shortener: hashing, base62, collisions, schema.
  4. Scale the design. "Identify and address bottlenecks, given the constraints… Everything is a trade-off."

The same steps work for a real project at work, where "the interviewer" is your team. The order matters: numbers before boxes, because the numbers decide which boxes you need.

Requirements

Functional (what it does)Non-functional (how well)

Non-goals (things that could reasonably be goals, chosen not to be): user accounts and logins, editing a link after creation, custom domains, real-time analytics dashboards, link previews. Writing them down stops the design from quietly growing. The Google design-doc article puts it well: non-goals "aren't negated goals like 'The system shouldn't crash', but rather things that could reasonably be goals, but are explicitly chosen not to be goals" (Design Docs at Google).

Back-of-envelope estimates

Estimates aren't predictions. They're arithmetic on stated assumptions, so that a reviewer can argue with the assumption instead of the conclusion. The Primer's handy conversions: "2.5 million seconds per month" and "40 requests per second = 100 million requests per month" (Primer: Design Pastebin.com (or Bit.ly)). I wrote the arithmetic as a program, so you can change one assumption and watch everything move:

writes/s: avg 38.6, peak 115.7
reads/s:  avg 3.9 k, peak 11.6 k
links after 5 years: 6.0 G
link storage: 3.0 TB
raw click rows after 5 years: 600.0 G (x 50 B = 30.0 TB)
cache for hot links: 10.0 GB
redirect bandwidth: avg 1.9 MB/s, peak 5.8 MB/s
base62 chars needed for 6.0 G codes: 6 (62^6 = 56.8 G)

Both languages print identical lines. Read them as decisions:

  • Writes are trivial. 39 per second, 116 at peak. One SQLite file handles that (L36 batched 10,000 inserts in 18 ms).
  • Reads are the problem. 3,900 per second, about 11,600 at peak. Every redirect must be cheap, and every design choice below protects the read path.
  • 3 TB of links won't fit one machine comfortably forever. Sharding is a "later" decision, but the code design must not prevent it.
  • Raw clicks would be 600 billion rows (30 TB). That decides the analytics design: count clicks per link per day instead of storing each click.
  • The hot set fits in memory. 10 GB for the busiest 20% of a month's links. That's why a cache will work (Part 2 measures it).
  • Six base62 characters are enough to number every link for five years with a counter. We'll still choose seven random ones, for a security reason you'll see in Part 2.
  • Bandwidth is tiny. Redirects have no body; 6 MB/s at peak is nothing.

Latency budget: a redirect adds a round trip before the user sees anything, so every millisecond counts. Norvig's table (L22, L41): "send 2K bytes over 1Gbps network 20,000 nanosec", but "send packet US to Europe and back 150 milliseconds" (Teach Yourself Programming in Ten Years). Distance dominates, so a global service would put redirect servers near users. That's a non-goal for us, but it belongs in the doc as a known limit.

What Kotlin does for you.
  • when with conditions returns a value, so human() is one expression. Java needs an if/return ladder (or a switch with guards, which can't test ranges of doubles as directly).
  • String templates ("links after $years years") vs Java's + concatenation. Both compile to similar bytecode (L23).
  • const val at top level is a real compile-time constant without a class around it. Java needs static final inside a class.
  • The estimate itself is language-neutral. A design is about boxes and numbers, and Kotlin vs Java only matters once you write the boxes.
Exercise: re-estimate on paper, then check

A different product: 10 million new links a month, but each is clicked 1,000 times on average (a marketing tool). Keep 500 B per row, 5 years and the hot 20%. By hand, before running anything: writes/s, reads/s, storage, cache size and the shortest counter code. Then change the assumptions in Estimates and compare. Which number didn't change, and what does that tell you?

Worked answer
  • Writes: 107 / 2,592,000 ≈ 3.9/s.
  • Reads: 3.9 × 1,000 ≈ 3,860/s. The same as before: 10× fewer links, 10× more clicks each.
  • Storage: 107 × 60 months × 500 B = 300 GB. Fits one machine for years.
  • Cache: 0.2 × 107 × 500 B = 1 GB.
  • Codes: 6 × 108 links; 625 ≈ 916 million, so 5 characters.

The read rate didn't change, and the read rate is what drives the cache and the server count. So this product needs the same read path but a tenth of the storage plan: no sharding for years. Same shape, different bottleneck. That's why estimates come before boxes.

Check

100 million new links a month is roughly how many writes per second?

108 / 2.6 × 106 seconds ≈ 39. The Primer's rule of thumb: 40 requests per second ≈ 100 million a month.

Why does the design store clicks as one row per code per day, not one row per click?

3,900 clicks a second for five years is 600 billion rows, about 30 TB. Daily counts keep one small row per active link per day. The estimate made the decision.

Which of these is a non-goal, in the design-doc sense?

A non-goal could reasonably be a goal but is deliberately excluded. "Never crash" is a negated goal (everyone wants it), and the other two are requirements.

6 billion links over 5 years. What's the shortest base62 code a counter needs?

625 ≈ 916 million is too few; 626 ≈ 56.8 billion is enough. Estimates computes ⌈log62(6 × 109)⌉ = 6.

Reads outnumber writes 100 to 1. Where should the design spend its effort first?

99% of the traffic is redirects. Caching, replicas and the async click queue in Part 2 all exist to keep that path cheap.

2.1 · The API

RequestSuccessFailures (Problem Details, L32)
POST /api/links {"url", "alias"?, "ttlSeconds"?}201 + Location: /{code}400 invalid URL · 409 alias taken · 429 + Retry-After
GET /{code}302 + Location: <url>404 unknown · 410 expired
GET /api/links/{code}/stats200 {"code", "url", "clicks"}404 unknown

Two details carried over from L32. Create is not idempotent (POST never is), so a client that retries after a timeout could create two links. An Idempotency-Key header fixes that: the same key from the same client returns the same link. Expired is 410, not 404: RFC 9110 says 410 Gone means "access to the target resource is no longer available at the origin server and that this condition is likely to be permanent" (RFC 9110 §15.5.11). That's exactly an expired link.

2.2 · Which redirect status?

Four status codes redirect, and the choice has consequences (callback L31, RFC 9110 §15.4):

CodeMeaningCached by default?Keeps the method?
301 Moved Permanently"any future references to this resource ought to use one of the enclosed URIs"yes: "heuristically cacheable"may turn POST into GET
302 Found"the client ought to continue to use the target URI for future requests"nomay turn POST into GET
307 Temporary Redirectlike 302no"MUST NOT change the request method"
308 Permanent Redirectlike 301yeskeeps it

RFC 9110 lists the heuristically cacheable codes: "200, 203, 204, 206, 300, 301, 308, 404, 405, 410, 414, and 501" (§15.1). 302 isn't on the list, and RFC 9111 allows heuristic caching only for those codes (RFC 9111 §4.2.2). So:

  • 301 lets browsers remember the redirect and stop asking. That's less load, but the shortener never sees repeat clicks (analytics undercount), and an expired or removed link keeps "working" from caches.
  • 302 keeps every click visible and every expiry effective. It costs a request per click, which is the read load we already planned for.

Decision: 302, with no Cache-Control header. Redirects are GETs, so 307 would work too. 302 is the conventional choice for shorteners, and real shorteners differ here, which is why it goes in the design doc's "alternatives".

Everything matches except the last line, which is random on every run, as it should be. Now the trade-offs.

Counter. Short (6 characters for 5 years) and collision-free by construction. But look at [g8, g9, ga, gb, gc]: anyone holding one code can guess its neighbours and walk through every link ever created. If people shorten private documents (they do), that's the L33 IDOR bug at internet scale.

Hash and truncate. The same URL always gives the same code, which de-duplicates for free. But truncating to 7 base62 characters (3.5 × 1012 possible codes) brings back L19's birthday problem. The expected first collision is at about √(πN/2) inserts, not N. I measured it:

5 chars: space 916,132,832, birthday estimate 37,935, measured mean 40,870 over 20 trials
7 chars: space 3,521,614,606,208, birthday estimate 2,351,965, measured mean 1,835,574 over 5 trials
  each trial: 672,104, 3,133,710, 1,330,403, 1,702,602, 2,339,055
6.0 G links in 7 chars: P(any collision) = 1.000000, expected colliding pairs ≈ 5,111,292

Identical in both languages, because SHA-256 is deterministic. At 5 characters the 20-trial mean (40,870) sits near the estimate (37,935). At 7 characters a single trial swings from 672 thousand to 3.1 million. Single runs of a random process are noisy, which is why I ran five. Either way, the first collision arrives after a couple of million links, not trillions, and at our 6 billion links about 5 million pairs collide. Hashing still needs a collision check, which removes its main advantage.

Random + collision check. Unguessable, and no coordination between servers: any server can pick a code. The database's UNIQUE constraint is the collision check, and a clash means "pick again". With 6 billion of 3.5 trillion codes used, a new code clashes 6 × 109 / 3.5 × 1012 ≈ 0.17% of the time, so retries are rare.

Decision: random, 7 characters, retry on UNIQUE. At very large scale, companies also use Snowflake-style IDs: Twitter's 2010 design packs "time - 41 bits", "configured machine id - 10 bits" and "sequence number - 12 bits" into 64 bits, so that "machines generating ids should not have to coordinate with each other" (twitter-archive/snowflake). They're time-ordered and so guessable, though, which is the same problem as the counter.

2.4 · The data model

All three hot queries are a SEARCH, never a SCAN (L35). The UNIQUE on code creates the index the redirect uses (sqlite_autoindex_links_1), and doubles as the random-code collision check. The click upsert (ON CONFLICT … DO UPDATE) adds to a day's count instead of inserting a row; the two inserts of 5 and 3 became one row of 8. Expiry is checked on every read (an expired link answers 410 even if the purge hasn't run), and a nightly DELETE uses the partial index, which holds only links that can expire.

2.6 · The working mini version

One process that contains the boxes that matter for correctness: an HttpServer (L32) on virtual threads (L28), SQLite (L34–L36), the LRU cache with negative caching (L41), the click queue and batch writer (L42, L36), and a token bucket (L43). Read lookup carefully, because it's the whole read path in one expression. Cache first. On a miss, the database. Then remember the answer either way: a Found link, or Missing. Caching "there's no such code" is negative caching, and it stops a scraper hammering random codes from reaching the database every time. A test below proves it.

The other files: storage, click queue, cache, rate limiter, base62, model

A design note on ClickRecorder: my first version had a worker that took one click off the queue and then wrote a batch. A test calling flush() could run between those two steps and see the click missing. The fix was a periodic flusher that shares one lock with flush(), so a flush never overlaps an in-flight batch. Concurrency bugs hide in exactly these gaps (L26–L27).

  • The cache works on skewed traffic: a 95.7% hit rate, and database queries fall from about 10,000 to about 430. The 430 are each code's first visit, plus a few click-batch writes.
  • Even with no injected latency, the cache roughly halves p50. A SQLite query is fast, but opening a connection per call (as L36 did) isn't free. A connection pool would narrow this gap; the design doc should say so.

2.7 · Scaling and failure modes

PressureResponseTrade-off
3 TB, growingShard links by code with consistent hashing (L42). A redirect knows its code, so it knows its shard.Stats across all links need a fan-out query
Read peaksRead replicas; fall back to the primary on a missReplication lag for brand-new links
Global usersEdge/CDN caching of redirectsEdge hits never reach us: the analytics undercount
Database downCached redirects keep working; creates fail with 503Degraded, not dead: decide which matters more
One link goes viralIt's already hot in every cache; coalesce misses on expiry (L41)Per-key locks or single-flight loading
AbuseRate limits on create (and on redirects per IP)Legitimate bulk users need higher limits

Spam and phishing. A shortener hides where a link goes, which attackers love. Real services check new URLs against blocklists of known-bad domains, and can disable a code after reports, answering with a warning page instead of a redirect. It's out of scope for the mini version, but it belongs in the design doc's risks, because it decides whether email providers and browsers trust your domain at all.

Bridge. In Spring, the read path would be a @GetMapping("/{code}") with @Cacheable on the lookup (Spring cache abstraction), and a library such as Resilience4j for rate limits. On Android, an app that shows previews of shortened links would cache them with an image or HTTP cache. The design decisions are the ones you just made by hand.

What Kotlin does for you.
  • data object Missing is a singleton with a readable toString and correct equals. Java uses an enum (or an empty record) to get the same thing inside a sealed hierarchy.
  • Exhaustive when over the sealed Lookup, vs Java 21's pattern switch with case Found(Link link). Both make the compiler check that every case is handled (L7), and Java needs the newer syntax to get there.
  • Default arguments: ShortenerServer(store, port = 18044, verbose = true). The Java constructor takes six arguments every time, and a builder (L39) would be the fix.
  • explicitNulls = false on the Json instance drops null fields everywhere; Java annotates each record with @JsonInclude(NON_NULL).
  • use { } and withLock { } are library functions taking lambdas, where Java writes try-with-resources and lock()/try/finally by hand. The behaviour is the same.
Exercise: type it, then predict
  1. From a blank file, write encode(n: Long) and decode(code: String) for base62, plus a round-trip check over 0, 61, 62, 3843, 3844 and Long.MAX_VALUE. Then the Java version.
  2. Predict: you switch the redirect from 302 to 301 and click the same short link three times in one browser. What does /stats show, and why?
  3. Predict: in the full design, click counts live in a separate analytics database. It goes down for ten minutes. What happens to redirects, and to clicks?
Answers
  1. Compare with Base62.kt/Base62.java in the folded files above, and with CodeGen's output: 62 → 10, 3843 → ZZ, 3844 → 100, Long.MAX_VALUE → aZl8N0y58M7. The classic slips: forgetting the n == 0 case (the loop never runs, so you return ""), and forgetting reverse().
  2. Probably 1. A 301 is heuristically cacheable, so the browser may reuse it without asking, and the second and third clicks never reach the server. The exact behaviour is up to the browser, which is part of the problem: you lose control.
  3. Redirects keep working, because they only read links (from the links database and the cache) and enqueue clicks. In the mini version both tables share one SQLite file, so this only holds in the full design. The queue fills, and once it's full, record drops clicks and counts them in dropped. That's a deliberate choice, written into the design doc: analytics are allowed to lose data, and redirects are not allowed to wait. In the mini version the flusher's exception would end the background thread, so a production version needs retry with backoff (L43) and an alert on dropped.

Check

Why does the shortener answer with 302, not 301?

RFC 9110: "A 301 response is heuristically cacheable", and 302 isn't on that list. Cached redirects hide clicks and keep expired links alive.

Hash-and-truncate to 7 base62 characters. Roughly when does the first collision appear?

The birthday bound is √(πN/2) ≈ 2.35 million for N = 3.5 × 1012; five real trials averaged 1.8 million. Collisions arrive at around √N, not N (L19).

A cached redirect for a popular code, in the mini version. How many database queries does it cost?

The test "a cached redirect does not query the database" checks exactly this. The click goes into the queue, which writes in batches later.

The click queue is full. What does record do?

queue.offer returns false instead of blocking, and the code increments dropped. A redirect must never wait for analytics.

Sequential codes like g8, g9, ga leak what?

Guessable identifiers let anyone enumerate every link, including private ones: L33's IDOR at scale. Random codes from SecureRandom close that hole.

Writing a one-page design doc

The design doc for the shortener

Short links: design (one page)

Context. Teams share long URLs in chat, email and print. We want short, reliable links on our own domain, with basic click counts. Built on our standard stack: JVM services and SQLite now, with a managed SQL database at scale.

Goals. Create a short link; redirect fast (p99 under 10 ms server-side); optional alias and expiry; daily click counts. Non-goals. Accounts, editing links, custom domains, real-time analytics, previews.

Estimates. 100 M links/month, 100:1 reads. That gives 39 writes/s; 3.9 k reads/s average and 11.6 k at peak; 6 G links and 3 TB over 5 years; a 10 GB hot set; daily click counts instead of 30 TB of raw clicks.

Design. Stateless app servers behind a load balancer. POST /api/links → 201 + Location; GET /{code} → 302; GET /api/links/{code}/stats. Codes are 7 random base62 characters from SecureRandom; the UNIQUE index is the collision check (0.17% retries at 6 G links). Reads: in-process LRU (positive and negative entries), then a read replica, then the primary. Clicks: enqueued, batch-upserted into clicks_daily(code, day) every 200 ms. Expiry is checked on read (410) and purged nightly via a partial index. Creates are limited per client by a token bucket (429 + Retry-After). The prototype measured a 95.7% hit rate on skewed traffic, with queries down from 10,003 to 429.

Alternatives considered. Counter + base62: shorter (6 characters) but enumerable, so rejected. Hash and truncate: still collides after about 2 M links, so it needs the same check; rejected. 301 redirects: cheaper but hide clicks and outlive expiry; rejected. One row per click: 30 TB; rejected. Shared Redis cache: deferred until the hit rate per server drops.

Cross-cutting. Security: unguessable codes; URL validation (http/https only); rate limits; blocklist check on create (phase 2). Privacy: no IPs stored, counts only. Observability: the golden signals per endpoint, cache hit rate, queue depth and dropped clicks (L43).

Risks and open questions. Abuse could get the domain blocklisted. A single SQLite writer limits creates (fine at 116/s; revisit before 1 k/s). Idempotency keys live in memory, so move them to the database before running more than one server. Replica lag could 404 a new link without the primary fallback.

Rollout. The prototype's tests run in CI (L40). Next, a load test at peak rate, an internal beta, and a public launch behind a feature flag.

Notice what made it short: every sentence is a decision or a number, and the reasoning is a reference ("Part 2 measured…") rather than a re-explanation. Notice also what it admits. The idempotency map that lives in one process is fine for the prototype and wrong for three servers, and the doc says so instead of hiding it.

Reviewing a design doc

The L40 review mindset, applied one level up:

  1. Are the numbers there, with stated assumptions? "Fast" and "scalable" without a number are not requirements.
  2. Does every component trace back to a requirement or estimate? A box nobody can justify is cost without benefit.
  3. Are the alternatives real? A strawman alternative ("or we could do nothing") means the author didn't look.
  4. What happens when each dependency fails? Database, cache, queue, network.
  5. Where is the data, who can read it, and for how long? Privacy and retention.
  6. How will we know it's working? Metrics, alerts, a load test.
  7. What's the cheapest experiment that could prove it wrong? The mini version and its load test were exactly that.
What Kotlin does for you.

Nothing, at this level, and that's the point. A design doc should read the same whether the service is written in Kotlin, Java or Go. Language shows up only in the details the doc points to, such as sealed result types for "found / missing / expired" and data classes as API DTOs. If your design doc needs to mention suspend or record, it's probably too low-level.

Exercise: review a weak design doc

A teammate's design-doc excerpt for an image-upload service. List at least five problems, using the checklist above.

"The service will be fast and scalable. Users upload images, which we store in the database. We'll use Kafka, Redis, Elasticsearch and a CDN. Image IDs are auto-increment integers shown in the URL. Alternatives: none, this is the best approach. We'll add monitoring later."

Sample review
  1. No numbers. How many uploads per second, what average size, what read ratio? "Fast and scalable" isn't testable.
  2. Images in the database with no size estimate: blobs bloat the database, its backups and its replicas. Object storage, with metadata in the database, is the usual alternative. Ask for the estimate first.
  3. Components without reasons: Kafka, Redis and Elasticsearch, each a system to run and page someone for. What requirement needs each one?
  4. Auto-increment IDs in URLs make every image enumerable. If any image is private, that's an IDOR (L33).
  5. No alternatives means no trade-offs were weighed.
  6. No failure modes (what if the CDN or the database is down?), no privacy section (who can see an image, and what about photo metadata?), and "monitoring later" means the team can't tell whether the service works.

Reference solution: the pastebin

Compare with the Primer's own walkthrough afterwards (Design Pastebin.com). Its assumptions differ (1 KB pastes), and seeing where two careful designs diverge is instructive.

1 · Requirements. Paste text (≤ 64 KiB), get an unguessable link, read it back as plain text, optional expiry, anonymous. Non-goals: accounts, editing, syntax highlighting, search, real-time view counts.

2 · Estimates. 10 M new pastes/month, 10:1 reads, average paste 10 KB (code snippets and logs), 5 years:

  • Writes: 107 / 2.6 × 106 ≈ 3.9/s (12 peak); reads ≈ 39/s (116 peak). Tiny.
  • Storage: 107 × 60 × 10 KB = 6 TB of content. This is the real problem, not traffic.
  • Cache: hot 20% of a month = 2 × 106 × 10 KB = 20 GB.
  • Read bandwidth: 39 × 10 KB ≈ 390 KB/s average.
  • IDs: 8 random base62 characters = 2.2 × 1014 codes vs 6 × 108 pastes, so a clash on about 1 insert in 360,000.

3 · API. POST /api/pastes (body = text; header or field for TTL) → 201 + Location: /p/{id}; 413 if over the limit (RFC 9110 "Content Too Large"); 429 + Retry-After. GET /p/{id} → 200 text/plain; charset=utf-8, 404 or 410.

4 · Data model. pastes(id TEXT PRIMARY KEY, content TEXT, created_at, expires_at) plus a partial index on expires_at. At scale: metadata stays in SQL, and content moves to object storage keyed by id (deep dive 1).

5 · Diagram.

clients ─▶ rate limiter ─▶ LB ─▶ app ×N ─┬─▶ LRU cache (20 GB hot)
                                          ├─▶ SQL: metadata (id, expiry, blob key)
                                          └─▶ object store: content blobs
                       hourly purge job ──▶ deletes expired rows + blobs

6 · Deep dives.

  • Where content lives. In a SQL TEXT column (simple, transactional; fine for the prototype) vs object storage (cheap per GB, built for blobs, keeps the database small and its backups fast). Decision: SQL now, object storage once content passes about 100 GB. The PasteStore interface hides which one is in use.
  • IDs. A counter is enumerable, and pastes often hold secrets people shouldn't have pasted, so it's rejected. Hashing the content gives free de-duplication but reveals whether a given text was ever pasted, so it's rejected. Decision: 8 random base62 characters, retrying on the primary-key clash.
  • Expiry. Delete exactly at expiry (needs a scheduler per paste) vs check on read plus an hourly purge (simple; expired data lingers up to an hour but is never served). Decision: check on read, purge hourly.

7 · Failure modes. Database down: cached pastes still readable, creates fail with 503. A huge paste flood: the size limit plus per-client rate limits. Malware or credentials pasted: an abuse report and takedown path. Purge job dies: reads still return 410, so it's a disk-growth alert, not an outage.

8 · The one-page doc follows the shortener's template: context, goals and non-goals, the estimates above, the design, the three deep dives as "alternatives considered", cross-cutting concerns (privacy: content may contain secrets, so use unguessable IDs, no listing endpoint and expiry options), risks (6 TB storage cost, abuse), and rollout.

Wrap-up

Exit quiz, recall card, sources

~5 min

The click flusher writes 300 upserts. Why in one transaction instead of 300? (L36)

Every commit has to make the journal durable on disk, and that's the expensive part. L36 measured 10,000 inserts at 2,399 ms with autocommit vs 18 ms in one transaction.

A browser got a 301 for /docs yesterday. Today you change where /docs points. What happens on the next click? (L31)

301 is heuristically cacheable, so without explicit cache headers the browser may reuse yesterday's answer. That's why a shortener whose targets can change or expire uses 302.

Why does the birthday estimate grow with √N rather than N? (L19)

With k items there are k(k−1)/2 pairs, and any pair can match. The number of pairs grows with k², so a collision becomes likely once k² is around N, that is, when k is around √N.

The load test's injected 1 ms is a Thread.sleep on a virtual thread. What does the carrier thread do meanwhile? (L28)

A sleeping virtual thread unmounts, so its carrier picks up other virtual threads. That's why 32 concurrent clients plus a sleeping "database" didn't need 32 OS threads.
