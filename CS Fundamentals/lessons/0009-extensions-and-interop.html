Part 1

Extension functions

~25 min

You often want a helper that "belongs" to a class you can't change, like String, a library class, or a final class. Java's answer is a utility class full of static methods: StringUtils.initials(name). Kotlin lets you declare an extension function instead. You write the receiver type before the function name, and inside the body, this is the receiver. You then call it like a member: name.initials() (Kotlin docs: Extensions).

# two Kotlin files, compiled together
$ kotlinc StringUtils.kt ExtMain.kt -include-runtime -d ext.jar
$ java -cp ext.jar ExtMainKt
# two Java files
$ javac -d out StringUtils.java ExtMainJava.java
$ java -cp out ExtMainJava

Three kinds of extension appear above:

  • Extension function: fun String.initials().
  • Extension property: val String.lastChar. It must use a getter, because "initializers are not allowed for extension properties". An extension can't add a backing field to someone else's class (Kotlin docs).
  • Nullable receiver: fun String?.orDash(), callable on a null without ?.. Inside it, this may be null, so you must check.
What Kotlin does for you. The Java version needs a holder class, a private constructor so nobody instantiates it, and call sites that read inside-out: StringUtils.initials(name). Kotlin's extension reads left to right, name.initials(), and your IDE offers it in autocomplete on any String. That's why the Kotlin standard library is built largely from extensions: split, uppercase, toIntOrNull and friends.

Extensions are resolved statically

Here's the catch, and it's L8's overload puzzle in disguise. "Extension functions are dispatched statically, meaning the compiler determines which function to call based on the receiver type at compile time" (Kotlin docs). An extension isn't really part of the class, so it can't be overridden.

Circle / circle
Shape / circle

The same object gives Shape from the extension but circle from the member. The extension was picked using the variable's declared type (Shape), and the member using the object's real class. The Java version behaves identically, because Java's static overloads are chosen at compile time too. That's the strongest hint about what extensions really are.

Members win, and private stays private

If a class already has a member with the same signature, "the member function takes precedence" (Kotlin docs). The compiler warns you that your extension is dead code:

member

MemberWins.kt:5:13: warning: this extension is shadowed by a member: 'fun greet(): String' defined in 'Greeter'.

Extensions also get no special access. Declared outside the class, an extension "can't access the receiver's private or protected members" (Kotlin docs). So your L6 encapsulation is safe:

PrivateExt.kt:5:35: error: cannot access 'val pin: String': it is private in 'Account'.

What an extension compiles to

All three facts above have one explanation. An extension compiles to an ordinary static method, with the receiver as its first parameter, on the class Kotlin generates for the file. For StringUtils.kt that class is StringUtilsKt, the same "file name + Kt" rule as for main in L1 (Kotlin docs: package-level functions, "including extension functions"). Here's the proof, calling them from Java:

$ kotlinc StringUtils.kt -d out
$ javac -cp out:kotlin-stdlib.jar -d out CallExtFromJava.java
$ java -cp out:kotlin-stdlib.jar CallExtFromJava

Platform types: Java's nulls meet Kotlin's types

Kotlin's null safety (L3) needs to know whether a value can be null. A plain Java method doesn't say. So Kotlin gives its result a platform type, written String!, meaning "String or String?: you decide" (docs). You can't type String! yourself, but it shows up in compiler messages:

NullMisuse.kt:4:20: error: initializer type mismatch: expected 'Int', actual 'String!'.

You make the decision when you store the value:

  • Choose String? (val nick: String? = p.nickname), and null safety is back on: ?:, ?., smart casts.
  • Choose String, and "the compiler will emit an assertion upon assignment" (docs). Compare the two crashes above. Kotlin fails at the assignment with getNickname(...) must not be null, naming the culprit. Java fails later, wherever the value happens to be used. In real code that can be far away.

Annotations end the guessing

If the Java author annotates nullability, Kotlin sees real types instead of platform types. Kotlin understands several annotation families, including JetBrains', Android's and JSpecify's (docs). JSpecify is the newer cross-industry standard. Directory.findEmail is marked @Nullable, so it arrives as String?, and misuse is a compile error. JSpecify is "the only supported flavor that uses strict report level by default" (docs):

NullMisuse.kt:2:23: error: initializer type mismatch: expected 'String', actual 'String?'.
    val email: String = Directory.findEmail("ada")   // @Nullable into non-null
NullMisuse.kt:3:25: error: null cannot be a value of a non-null type 'String'.
    Directory.findEmail(null)                        // null into @NonNull

Compile with -Xjspecify-annotations=warn and the same mistakes become warnings:

NullWarn.kt:2:25: warning: Java type mismatch: inferred type is 'String?', but 'String' was expected.
NullWarn.kt:3:25: warning: Java type mismatch: inferred type is 'Nothing?', but 'String' was expected.

In a Gradle project, the JSpecify jar is one dependency line: implementation("org.jspecify:jspecify:1.0.0"). For the command line, download it from Maven Central.

What Kotlin does for you. Kotlin turns Java's getter/setter ceremony into property syntax, accepts lambdas wherever Java expects a single-method interface, and drops the checked-exception requirement. For nulls, it treats unannotated Java as "unknown" rather than pretending it's safe, puts a guard at the boundary when you claim non-null, and makes annotated APIs fully type-checked. A Java caller gets none of these checks: getNickname() is just a String that might be null.

Fix those two, with Greeter.Companion.create() and greet("Ada", "!"), and recompile. As in L3, javac then reports the next round of errors:

UsePlainRound2.java:9: error: exception IOException is never thrown in body of corresponding try statement
        } catch (IOException e) {                    // no @Throws

Java forbids catching a checked exception the callee doesn't declare. Without @Throws, Java code literally can't write a catch (IOException e) for that call, even though the exception really can happen.

In a real project you won't type these commands. A Gradle project using the Kotlin plugin compiles src/main/java and src/main/kotlin together, in either direction. The Kotlin docs say Kotlin and Java sources "can be stored in the same directory, or they can be placed in different directories" (docs). I checked it on a project generated the same way as L1's gradle-hello: a Java class in src/main/java and a Kotlin file calling it in src/main/kotlin built together. That's how Android and Spring codebases migrate from Java to Kotlin one file at a time.

What Kotlin makes you add, for Java's sake. This time Kotlin is the one being explicit. Java has no defaults, no companions and no top-level functions, so if Java code will call your Kotlin, you choose what Java sees: @JvmStatic, @JvmOverloads, @JvmField, @file:JvmName, @Throws. Kotlin callers never need any of them, which is why pure-Kotlin code rarely uses them.

Why add @Throws(IOException::class)?

Without the throws clause in the bytecode, javac rejects a catch (IOException e) around the call.
