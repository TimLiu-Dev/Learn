Overridden members use dynamic dispatch: the object's real class decides (L8).

  1. That's how overloads and extensions are chosen. An overridden member waits for the object's real class at runtime.
  2. Calling an overridden method through a supertype variable is exactly what polymorphism allows, so it compiles.
  3. Dynamic dispatch looks at the object, a Dog, when the call runs.
  4. An override replaces the method for that class. Animal's version runs only if Dog's calls super.sound().

Overloads like describe(Animal) and describe(Dog) are chosen by…

Overload resolution happens at compile time, using static types (L8). Keep this in mind: it comes back in Part 1.

  1. Overload resolution uses the declared (static) types of the arguments, fixed by the compiler.
  2. That's how overrides are chosen. Overloads are picked before the program runs, so the runtime class doesn't matter.
  3. Source order never matters. The compiler picks the most specific overload that fits the argument types.
  4. Neither overload replaces the other: both exist, because their parameter types differ.

Can you subclass a Kotlin class that isn't marked open?

Kotlin classes are final by default (L8). This is exactly why extensions are so useful: you can't subclass String, but you can add functions to it.

  1. Only classes marked open (or abstract) can be extended. A plain class is final.
  2. Without open, a Kotlin class is final, so the compiler rejects the subclass.
  3. It compiles to a final JVM class, so javac refuses to extend it too.
  4. override is for members, not classes. It can't make a final class extendable.
Part 1

Extension functions

~33 min

You often want a helper that "belongs" to a class you can't change, like String, a library class, or a final class. Java's answer is a utility class full of static methods: StringUtils.initials(name). Kotlin lets you declare an extension function instead. You write the receiver type before the function name, and inside the body, this is the receiver. You then call it like a member: name.initials() (Kotlin docs: Extensions).

$ java -cp ext.jar ExtMainKt

Three kinds of extension appear above:

  • Extension function: fun String.initials().
  • Extension property: val String.lastChar. It must use a getter, because "initializers are not allowed for extension properties". An extension can't add a backing field to someone else's class (Kotlin docs).
  • Nullable receiver: fun String?.orDash(), callable on a null without ?.. Inside it, this may be null, so you must check.
What Kotlin does for you. The Java version needs a holder class, a private constructor so nobody instantiates it, and call sites that read inside-out: StringUtils.initials(name). Kotlin's extension reads left to right, name.initials(), and your IDE offers it in autocomplete on any String. That's why the Kotlin standard library is built largely from extensions: split, uppercase, toIntOrNull and friends.

Extensions are resolved statically

Here's the catch, and it's L8's overload puzzle in disguise. "Extension functions are dispatched statically, meaning the compiler determines which function to call based on the receiver type at compile time" (Kotlin docs). An extension isn't really part of the class, so it can't be overridden.

Circle / circle
Shape / circle

The same object gives Shape from the extension but circle from the member. The extension was picked using the variable's declared type (Shape), and the member using the object's real class. The Java version behaves identically, because Java's static overloads are chosen at compile time too. That's the strongest hint about what extensions really are.

Members win, and private stays private

If a class already has a member with the same signature, "the member function takes precedence" (Kotlin docs). The compiler warns you that your extension is dead code:

MemberWins.kt:5:13: warning: this extension is shadowed by a member: 'fun greet(): String' defined in 'Greeter'.

Extensions also get no special access. Declared outside the class, an extension "can't access the receiver's private or protected members" (Kotlin docs). So your L6 encapsulation is safe:

What an extension compiles to

All three facts above have one explanation. An extension compiles to an ordinary static method, with the receiver as its first parameter, on the class Kotlin generates for the file. For StringUtils.kt that class is StringUtilsKt, the same "file name + Kt" rule as for main in L1 (Kotlin docs: package-level functions, "including extension functions"). Hint 1 of 3

Inside labels, it has the static type Item. Extensions are chosen at compile time from that static type, so Item.label() runs for every element, books included.

Hint 2 of 3

Only members get dynamic dispatch. Move label into Item as an open member, give Book an override, and delete both extensions. For bookCount, count the elements that pass an is Book check.

Hint 3 of 3

open fun label() = "item: $name" in Item, override fun label() = "book: $name by $author" in Book, and get() = count { it is Book }. Java's static label(Item) / label(Book) overloads fail the same way. Turn them into instance methods with @Override, and labels maps Item::label.

Final answer

Why it works. An extension is a static method chosen from the declared type, so it can never be overridden. A member with override is dispatched on the object's runtime class (L8), so a Book in a List<Item> runs Book.label(). bookCount stays an extension: you can't add members to List, and counting needs no dispatch. One extension with when (this) { is Book -> … } also passes, but every new subclass would mean editing it.

Common mistake. Making Item.label() a member but leaving Book's version as an extension. The member wins ("this extension is shadowed by a member"), so even a plain Book variable prints item: Dune.

From Java, the extension String.initials() declared in StringUtils.kt is called as…

A static method on the file class, with the receiver passed as the first argument.

  1. Java has no extension syntax. The method is static, so Java passes the receiver as an argument.
  2. StringUtils is the hand-written Java helper. Kotlin's class is named after the file, plus Kt.
  3. A static method on the file class StringUtilsKt, with the receiver as its first parameter.
  4. INSTANCE belongs to object declarations. Top-level functions are plain static methods, so no instance is needed.

Can an extension read the receiver's private properties?

It's compiled outside the class, so ordinary visibility rules apply.

  1. It compiles to a static method outside the class, so private and protected members stay hidden.
  2. It only looks like a member at the call site. It's declared, and compiled, outside the class.
  3. open is about overriding, not visibility. It never grants access to private members.
  4. A nullable receiver only lets you call it on null. Visibility rules don't change.

Stretch: extensions compile to static methods like these, and Java picks overloads at compile time. What prints?

public class Pick {
    // What fun Any?.show() and fun String?.show() compile to:
    static String show(Object o) { return "any"; }
    static String show(String s) { return "string"; }

    public static void main(String[] args) {
        Object o = "hi";
        String s = null;
        System.out.println(show(o) + " " + show(s) + " " + show(null));
    }
}

Each call uses the declared type: o is an Object, and s is a String, even though it holds null. The bare literal null fits both overloads, so Java picks the most specific one, String (JLS §15.12.2.5). Kotlin does the same for null.show() with extensions on Any? and String?.

  1. s is declared String, so show(s) picks the String overload even though its value is null.
  2. o holds a String at runtime, but overloads ignore runtime classes, and o is declared Object.
  3. The null literal fits both overloads, and Java picks the most specific one: String.
  4. Declared types decide the first two calls. For the bare null, the most specific overload wins.

Platform types: Java's nulls meet Kotlin's types

Kotlin's null safety (L3) needs to know whether a value can be null. A plain Java method doesn't say. So Kotlin gives its result a platform type, written String!, meaning "String or String?: you decide" (docs). You can't type String! yourself, but it shows up in compiler messages:

NullMisuse.kt:4:20: error: initializer type mismatch: expected 'Int', actual 'String!'.

You make the decision when you store the value:

  • Choose String? (val nick: String? = p.nickname), and null safety is back on: ?:, ?., smart casts.
  • Choose String, and "the compiler will emit an assertion upon assignment" (docs). Compare the two crashes above. Kotlin fails at the assignment with getNickname(...) must not be null, naming the culprit. Java fails later, wherever the value happens to be used. In real code that can be far away.

Annotations end the guessing

If the Java author annotates nullability, Kotlin sees real types instead of platform types. Kotlin understands several annotation families, including JetBrains', Android's and JSpecify's (docs). JSpecify is the newer cross-industry standard. Directory.findEmail is marked @Nullable, so it arrives as String?, and misuse is a compile error. JSpecify is "the only supported flavor that uses strict report level by default" (docs):

NullMisuse.kt:2:23: error: initializer type mismatch: expected 'String', actual 'String?'.
    val email: String = Directory.findEmail("ada")   // @Nullable into non-null
NullMisuse.kt:3:25: error: null cannot be a value of a non-null type 'String'.
    Directory.findEmail(null)                        // null into @NonNull

Compile with -Xjspecify-annotations=warn and the same mistakes become warnings:

NullWarn.kt:2:25: warning: Java type mismatch: inferred type is 'String?', but 'String' was expected.
NullWarn.kt:3:25: warning: Java type mismatch: inferred type is 'Nothing?', but 'String' was expected.

In a Gradle project, the JSpecify jar is one dependency line: implementation("org.jspecify:jspecify:1.0.0"). For the command line, download it from Maven Central.

Bridge to Spring. This is why upgrading Spring changes your Kotlin code. "As of Spring Framework 7, the Spring Framework codebase leverages JSpecify annotations to expose null-safe APIs", and "in Kotlin, JSpecify annotations are automatically translated to Kotlin's null safety" (Spring Framework reference: Null-safety). Spring Boot 4.0, Spring Data 4.0, Spring Security 7.0 and more of the Spring portfolio did the same, so a Spring API that can return null now arrives as T? instead of a platform type (Spring blog: Null-safe applications with Spring Boot 4).

What Kotlin does for you. Kotlin turns Java's getter/setter ceremony into property syntax, accepts lambdas wherever Java expects a single-method interface, and drops the checked-exception requirement. For nulls, it treats unannotated Java as "unknown" rather than pretending it's safe, puts a guard at the boundary when you claim non-null, and makes annotated APIs fully type-checked. A Java caller gets none of these checks: getNickname() is just a String that might be null.

The missing-port check fails with getProperty(...) must not be null. That's the assertion Kotlin adds when you store a platform type in a non-null String. Decide the other way: store it as String?.

Hint 2 of 3

With String?, chain ?.toIntOrNull() (L3) and finish with ?: 8080, so a missing value and a bad number both fall back. File(path).parent is also a platform type, and it really is null for a bare file name.

Hint 3 of 3

Final answer

Why it works. A platform type makes you choose. Choosing String? turns null safety back on, so ?. and ?: handle the missing value, and toIntOrNull() handles the bad number without an exception. File's getters read as properties: name, parent, and isAbsolute, which keeps its is name.

Common mistake. Keeping val raw: String = … and adding if (raw == null) on the next line. The assertion fires on the assignment, before your check runs, and the compiler warns that the condition is always false.

Check

Kotlin's p.isActive = true, on a Java Person, calls…

Boolean is-getters keep the getter's name as the property name, and assignment calls the matching setX.

  1. isActive() is the getter. Assigning to the property calls the setter.
  2. No such method exists. The Java setter is setActive, and Kotlin pairs it with isActive.
  3. Assigning to the property calls Java's matching setter, setActive.
  4. Kotlin never invents method names. Property syntax maps only to existing getX/isX/setX methods.

An unannotated Java getter returns null into val s: String = obj.thing. What happens?

A platform type lets it compile, and the generated assertion fails immediately: "getThing(...) must not be null".

  1. A platform type String! may be stored as String, so the compiler accepts it.
  2. Kotlin checks the value on assignment and throws NullPointerException naming getThing(...).
  3. A non-null variable can't hold null: the generated check throws before the value is stored.
  4. That's Java's later failure. Kotlin's check fails at the assignment, which points straight at the culprit.

A Java method is annotated with JSpecify's @Nullable. You assign its result to a non-null String…

JSpecify mismatches are errors by default. -Xjspecify-annotations=warn downgrades them to warnings.

  1. Nothing gets to run: the compiler rejects the code first.
  2. Annotated nullability is fully type-checked, so the null can't slip through.
  3. That's what -Xjspecify-annotations=warn gives. JSpecify's default level is strict.
  4. JSpecify is strict by default, so assigning String? to String is an error.

Kotlin calls a Java method declared throws IOException, with no try…

Kotlin has no checked exceptions. The exception still happens at runtime if nobody catches it (L10).

  1. Kotlin has no checked exceptions, so the call compiles without try or throws.
  2. That's javac's rule. Kotlin never forces you to catch an exception.
  3. Kotlin doesn't warn either. An uncaught exception simply propagates at runtime.
  4. @Throws is for Java callers of Kotlin code. Calling Java from Kotlin doesn't need it.

Final answer

Why it works. Each annotation changes only what the compiled class shows Java: a field instead of a getter, an extra add(String) overload, a throws clause, and a static method on Library. The two Kotlin checks passed before and after, because Kotlin callers never needed any of it.

Common mistake. Writing @Throws(Exception::class) "to be safe". Every Java caller must then catch or declare Exception, the broadest checked type. Declare exactly what the function can throw.

@JvmOverloads fun record(c: Double, note: String = "", rounded: Boolean = false). How many public record methods does Java see?

Why add @Throws(IOException::class)?

Without the throws clause in the bytecode, javac rejects a catch (IOException e) around the call.

  1. It puts a throws clause in the bytecode, so javac allows a catch (IOException e).
  2. Kotlin callers are never forced to catch anything, with or without the annotation.
  3. It's the opposite: Java now sees a checked exception, so its callers must catch or declare it.
  4. It only adds a throws clause to the signature. It has no effect on speed.

Which methods can Java call as static methods directly on Thermo? This lists them with reflection.

import java.lang.reflect.Modifier

class Thermo {
    companion object {
        @JvmStatic fun indoor() = "indoor"
        fun outdoor() = "outdoor"
    }
}

fun main() {
    // The static methods Java can call directly on Thermo
    val statics = Thermo::class.java.declaredMethods
        .filter { Modifier.isStatic(it.modifiers) }
        .map { it.name }
        .sorted()
    println(statics)
}

Companion functions are instance methods on the Companion object. @JvmStatic adds a real static indoor() to Thermo itself, and it stays callable through Companion too. outdoor exists only on the companion, so Java writes Thermo.Companion.outdoor().

  1. @JvmStatic does add a static method to the outer class, so indoor is listed.
  2. Backwards: outdoor has no annotation, so it lives only on Thermo.Companion.
  3. Only the @JvmStatic function gets a static method on Thermo. outdoor stays on the companion.
  4. A companion's functions aren't static by default. Without @JvmStatic, outdoor isn't on Thermo.

A Kotlin data class's generated equals compares…

Only properties in the primary constructor take part in the generated equals/hashCode/toString (L7; Kotlin docs: Data classes).

  1. Properties declared in the class body are left out of the generated equals.
  2. That's a plain class's equals. A data class compares property values.
  3. Only primary-constructor properties take part in equals, hashCode and toString.
  4. Every primary-constructor property is compared, not just the first.

When "ada".initials() runs, the static method receives the receiver as…

It's an ordinary argument, so it's passed by value as a copied reference (L4).

  1. Only the reference is copied. The method sees the same String object.
  2. The JVM passes values, never variables, so reassigning the parameter can't change the caller's variable.
  3. The method gets the existing object. Nothing new is created.
  4. The receiver is an ordinary first argument, and the JVM passes a copy of its reference.
