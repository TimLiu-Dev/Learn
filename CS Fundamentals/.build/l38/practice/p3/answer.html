Why it works. A fake is a second, real implementation of the interface, so it has to keep the same promises as the SQL one: a counter for ids (like an AUTOINCREMENT key), insertion order for the queue, and a fresh list from every queue call. The checks are written against the interface, so the same suite could run against the real store too: that's the contract test from Part 3.

Common mistake. Reservation(all.size + 1L, …). It passes every check that never cancels, and then hands out an id that's already taken. A close second: keeping a list per book and returning it directly. That's aliasing (L3), so a "snapshot" keeps growing behind the caller's back.
