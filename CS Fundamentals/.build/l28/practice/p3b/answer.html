Why it works. All three are now reductions: each worker builds a partial result for its own chunk, and the stream combines the partials in encounter order. Nothing is shared, so there is nothing to lock, and toList() puts chunk results back in source order. reduce(0L, …) is safe because 0 is the identity for +, so starting every chunk from it changes nothing.

Common mistake. Swapping the ArrayList for Collections.synchronizedList. The crash and the lost elements go away, but forEach still runs in whatever order the workers finish, so the squares come out shuffled, and every add now contends for one lock. The stream docs call the forEach-into-a-list version an "unnecessary use of side-effects".
