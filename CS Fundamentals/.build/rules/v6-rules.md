## 1. Explain every option of every quiz (`whyopts`)

After each quiz's `<p class="why">…</p>`, add one `<li>` per button, in button order:

```html
<ol class="whyopts"><li>…</li><li>…</li><li>…</li><li>…</li></ol>
```

`lesson.js` labels each item with ✓/✗ and the option text, so don't repeat the option.

- **Wrong options:** name the specific misconception, and say what's actually true. "This is wrong" alone is not allowed.
- **The correct option:** one sentence on why it holds. Don't just copy `.why`.
- Keep each item to about 25 words or fewer. Use plain words, and keep code in `<code>`. Make every statement accurate: you're teaching with it. If an option is a deliberately silly distractor, still say briefly why it fails.
- If the existing `.why` or question is wrong, unclear or gives the answer away, fix it.

## 2. Code quizzes ("what does this print?"): 3–4 new ones per lesson

- **Files:**
  - Put the snippet in `.build/lNN/cq/Name.kt`, `Name.java` or `Name.sql`, with its exact expected stdout in `Name.out`.
  - `pg_check.py` runs it and compares: Kotlin on the Playground (Java 17 APIs only), Java on the local JDK, SQL in sqlite3 printed as `a|b` rows.
  - A snippet must not throw or write to stderr. If the point is an exception, catch it and print something.
- **Mix of languages:** at least one Kotlin and one Java per lesson. Use SQL where the lesson is about SQL.
- **Markup** (see L8 `p1-4`, `p1-5`, `p3-4`, `p4-4`):

  ```html
  <div class="quiz" data-id="pN-K" data-group="Part N · …" data-answer="i">
    <div class="q"><p>Question</p>
  <!--CODE:lNN/cq/Name.kt--></div>
    <div class="opts">…4 buttons…</div><p class="why">…</p><ol class="whyopts">…</ol></div>
  ```

- **Placement:** in the matching part's `Check` section, after the existing quizzes, with new unique `data-id`s.
- **Test what the lesson taught.** Use the classic traps: aliasing, dispatch, `==` vs `===`, integer overflow, lazy vs eager, off-by-one, `finally` order, ordering under concurrency only when it's deterministic. A "Stretch:" question may go one step further, if its explanation teaches the step.
- **Options:**
  - Either all options are `<code>`, or all are plain text. Plain-text options have equal word counts; the 2-word pattern "Prints 3", "Compile error" and "Throws exception" fits well.
  - Vary the correct position: across a lesson's new quizzes, use at least three different positions.
  - Distractors must be the outputs a learner with a specific misconception would predict.
- **Running after answering:** `playground.js` unlocks Run on a Kotlin quiz snippet after the quiz is answered, once the manifest lists it. I re-run the manifest at the end, so you don't need to.

## 3. Runnable practice: one per teaching part (usually 3–4), not for the final exercise

**Folder** `.build/lNN/practice/pK/`, where K is the part's id: `p1`, `p2` … matching the template's part ids. Its files:

- `task.html`: first line is the title (plain text). The rest is HTML: what to do, in 2–5 short lines or bullets.
- `Starter.kt`: what the learner starts from.
  - It must compile and fail at least one test; `TODO("hint text")` bodies are ideal.
  - It may instead fail to compile on purpose, if the skill is reading a compiler error (L8 p1). The errors must then be in `Starter.kt` only.
- `Tests.kt`: JUnit 4, sent as a hidden file.
  - Use `import org.junit.Test` and `org.junit.Assert.*`.
  - Name tests with backticks so they read as sentences: ``@Test fun `a truck adds its load`()``.
  - Write 3–6 tests that check behaviour, including edge cases.
  - Give a message wherever a bare value would confuse.
  - Tests may define helper classes (L8 p3 defines a `Duck`).
- `Solution.kt`: the model answer, passing every test. Idiomatic, commented only where it teaches.
- `Starter.java` and `Solution.java`: `public class Practice` with static nested classes or methods.
  - The block between `// CHECKS` and `// END CHECKS` must be identical in both files. It holds `main` plus the `check(name, expected, () -> actual)` helper; copy it from L8.
  - The solution prints only `PASS` lines; the starter prints at least one `FAIL`, or throws.
  - Starters use `throw new UnsupportedOperationException("TODO: …")`.
- `hints.html`: 2–3 hints separated by lines containing only `---`. They are progressive: a nudge, then the approach, then nearly the answer. Hint 3 may mention the Java difference.
- `answer.html`: `<p><b>Why it works.</b> …</p>` plus `<p><b>Common mistake.</b> …</p>`.
- Optional, and wanted whenever `answer.html` names a mistake: `Mistake.kt` (or `Mistake.sql`), containing that mistake. `pg_check` proves the tests catch it.

**SQL practice** (L34–L36, L56 and anywhere SQL is the skill): the folder has `setup.sql` (schema and a few rows), `Starter.sql`, `Solution.sql`, optional `check.sql` (a query run after the learner's statements, for tasks that change data), `hints.html`, `answer.html` and optional `Mistake.sql`. The checker compares values, not column names. Row order matters only if the solution or check uses ORDER BY.

**Design:**

- **Fit.** Practise exactly the part's skill, sized for 5–10 minutes, in the learner's zone of proximal development.
- **No repeats.** Don't duplicate the part's IDE exercise; complement it. The IDE exercises and finals stay, because writing code by hand in IntelliJ is the real goal.
- **Interleaving.** At least one practice per lesson should also need a skill from an earlier lesson.
- **Playground limits:**
  - Single file, Java 17 APIs, kotlinx.coroutines and kotlinx.serialization available.
  - No file system, no stdin, 10 s limit, output cap.
  - Threads and sockets work. Keep concurrency tests deterministic: join, use latches, no sleeps for timing.
- **Where Kotlin can't express the skill** (pure shell, a design discussion), use the closest honest Kotlin exercise, e.g. reimplement a pipeline stage in Kotlin. Don't skip the practice.

**Placement:** `<!--PRACTICE:lNN/practice/pK-->` goes right after that part's `.exercise` block, before its `<h3>Check</h3>`. If a part has no exercise, put it before the Check.

## 4. Review the lesson (you are check #1 of 3)

Read the whole lesson as the learner will. Fix definite problems, keep the voice, and touch only what's needed:

- **Wrong facts, outdated APIs, or claims without a citation.**
  - Every example's printed output must still match its source. Re-run any source you change.
  - If a primary-source link might be dead, check it with `curl -sI`.
- **Quiz problems:** wrong `data-answer`, ambiguous questions, a giveaway in the wording, or word counts. The QA script checks counts; you check meaning.
- **Inconsistencies** with the glossary (`reference/glossary.html` if present) or with other lessons' terms. Also broken nav, a missing `.auto` box, or unclear steps.
- **Time estimates:** add ~8 minutes per practice to the part's `<span class="t">` and to the toc and `lesson-meta` totals.
- Anything you'd **add or remove** beyond your brief's extras: don't do it. List it in your report.

## 5. Finish

1. `pg_check.py .build/lNN` → `0 problem(s)`.
2. Rebuild.
3. Diff against your backup.
4. `qa.py --strict`: your lesson is `OK`.
5. Browser check: one practice end to end, plus no errors or horizontal scroll at 420px.

Don't edit NOTES.md, the roadmap or the shared assets (`assets/*.js`, `course.css`, `.build/bin/*`). If you think a shared file needs a change, say so in your report.
