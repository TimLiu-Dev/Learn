Clean Code & Refactoring

Code is read far more often than it's written. This lesson covers the habits that make it readable: good names, functions that do one thing (but not too little), and honest comments. Then comes the skill that matters most when you work with AI: changing the structure of code in small, named steps, with tests proving after each step that nothing broke.

Part 1

Naming, small functions, and when comments help

~25 min

Names are the first interface

A reader meets your names before your logic. The Kotlin coding conventions put it plainly: "The names should make it clear what the purpose of the entity is, so it's best to avoid using meaningless words (Manager, Wrapper) in names" (Kotlin: choose good names). Functions are verbs, classes are nouns, and a Boolean reads as a question: isEmpty, hasLoans. Google's Java guide agrees on the shape: method names "are typically verbs or verb phrases", constants are UPPER_SNAKE_CASE, and "special prefixes or suffixes are not used" (no mName, no s_name) (Google Java Style §5). Both languages use lowerCamelCase for functions and variables.

Here is L3's word counter as it often looks the first time, and the same code with names that carry meaning. Same behaviour, verified by the last line:

{the=3, cat=1, sat=1, on=1, mat=2, was=1, flat=1}
{the=3, cat=1, sat=1, on=1, mat=2, was=1, flat=1}
true
{the=3, cat=1, sat=1, on=1, mat=2, was=1, flat=1}
{the=3, cat=1, sat=1, on=1, mat=2, was=1, flat=1}
true

Look at the call sites. calc(text, true) tells you nothing: true what? That's a flag argument, a Boolean that switches the function into a different mode. Fowler lists it as a smell with its own fix, Remove Flag Argument. The languages fix it differently:

  • Kotlin can keep the parameter and name it at the call site: wordCounts(text, ignoreCase = true) reads like a sentence. The default value means most callers don't pass it at all.
  • Java has no named arguments, so the honest fix is two methods whose names say the mode: wordCountsIgnoringCase(text) and wordCounts(text). The flag survives only in a private helper.

Functions: one job, one level of abstraction

A good function does one thing, and its body works at one level: price should read as "subtotal, discounts, shipping", not mix that with index arithmetic. Two related smells:

  • Long parameter lists. Five parameters that always travel together are really one concept. Give it a name with a data class or record (Introduce Parameter Object, step 7 in Part 2).
  • Flag arguments, as above.

The counterweight: functions can be too small

"Keep functions small" is good advice taken too far surprisingly often. John Ousterhout, whose A Philosophy of Software Design is this phase's main source, argues that past a point "the amount of functionality hidden behind each interface drops, while the interfaces often become more complex". He calls such methods shallow, and warns that over-splitting causes entanglement: "if, in order to understand how one of them works internally, you also need to read the code of the other". He wrote that in a 2024–25 public debate with Robert Martin, the author of Clean Code, about exactly this point (APoSD vs Clean Code: method length). His book makes the same case in ch. 4, "Modules Should Be Deep".

Same logic both ways. Version A is nine tiny functions; version B is three that each hide a real decision:

2026-10-10  A: on time  B: on time
2026-10-06  A: 1 day late  B: 1 day late
2026-09-30  A: 7 days late  B: 7 days late
2026-10-10  A: on time  B: on time
2026-10-06  A: 1 day late  B: 1 day late
2026-09-30  A: 7 days late  B: 7 days late

To understand statusA you must open isLate, which sends you to isAfter and dueDate, which sends you to loanDays. isAfter adds nothing to LocalDate.isAfter at all. Version B's daysOverdue is worth a name: it hides the due-date rule and the "never negative" decision behind one line of doc comment. The test for a function is not its length. It's whether its name lets you stop reading.

Comments: say why, not what

Ousterhout devotes three chapters to comments: ch. 12 "Why Write Comments? The Four Excuses", ch. 13 "Comments Should Describe Things that Aren't Obvious from the Code", and ch. 15 "Write The Comments First". A comment like // add up above a loop that adds up repeats the code. A comment that says why (// SQLite has foreign keys off by default), or that documents an interface's contract, tells the reader something the code can't. The same debate has a long section on this: Martin treats most comments as a failure to express yourself in code, while Ousterhout treats interface comments as essential.

Interface comments look almost the same in both languages. Naming.kt above uses KDoc and Naming.java uses Javadoc. "Just like with Javadoc, KDoc comments start with /** and end with */", and both use block tags like @param and @return (KDoc syntax). The differences: KDoc uses Markdown and links with [text]; Javadoc uses HTML (<p>) and {@code …} / {@link …} (Javadoc spec).

The worst comment is one that lies. Code changes, comments don't get compiled, and nothing warns you:

Late fee for 4 days: $100
Late fee for 4 days: $100

Four days at 25¢ is $1.00. The caller believed "returns dollars". The fixes, best first: put the unit in the name (lateFeeCents), so the compiler-checked part carries the fact; or a dedicated type such as a Cents value class (Replace Primitive with Object); and only then a comment. You'll meet a lying comment again in the final.

Formatting

Consistency beats preference. Let the tool decide: IntelliJ's Reformat Code is ⌘⌥L on macOS (IntelliJ macOS keymap). Teams usually enforce it in the build with ktlint (Kotlin) or Spotless (both). L40 puts that in CI.

What Kotlin does for you.
  • Named and default arguments make a Boolean readable at the call site (ignoreCase = true) and let most callers omit it. Java needs extra overloads or extra methods.
  • KDoc is Markdown, so [text] links to a parameter or class, where Javadoc needs {@link #…} and HTML tags.
  • Destructuring in loops (for ((quantity, unitCents) in items)) names the parts of a pair right where you use them. Java reads item[0] and item[1], or declares two extra variables.
  • One expression body (fun f() = …) keeps genuinely small functions small without ceremony.

Part 2

Refactoring with tests as your safety net

~35 min

Martin Fowler's definition: refactoring "is a disciplined technique for restructuring an existing body of code, altering its internal structure without changing its external behavior. Its heart is a series of small behavior preserving transformations" (refactoring.com). Two words do the work: small and behavior preserving. Each transformation has a name and a recipe in his catalog, and every name used below links to it.

Smells: the reasons to start

Fowler and Kent Beck call the warning signs code smells (Refactoring, 2nd ed., ch. 3 "Bad Smells in Code"). The ones you'll see today:

First: characterisation tests

Before changing a line, pin down what the code does today, including the weird parts. Michael Feathers calls these characterisation tests (Working Effectively with Legacy Code). You don't ask "what should it do?" yet. You ask "what does it do?", write that down as an assertion, and run it until it's green. Refactoring vs rewriting

A rewrite throws the old code away and hopes the new code matches. A refactoring keeps the program working at every step, so you can stop after any step and ship. When a step goes red, you undo that step and try a smaller one; you've lost two minutes, not two days. Assistants are genuinely good at mechanical refactorings like renames, extractions and moving code. They're also good at "simplifications" that look equivalent and aren't. Here is one you could easily accept in review, applied to the Step 5 code: compute both percentages and apply them in one line. It's shorter. Run the tests:

What Kotlin does for you.
  • Default parameters turned percentOff(cents, percent, capCents = Int.MAX_VALUE) into one function. Java passed Integer.MAX_VALUE explicitly at each call, or would need an overload.
  • sumOf, filter, map made the Split Phase parsing two short lines (L14). Java used a stream, or kept the loop.
  • data object None is a singleton coupon with a readable toString. Java needed record NoCoupon(), which works but allocates per call.
  • Destructuring lambdas ({ (quantity, _) -> quantity > 0 }) name the pair's parts; _ says "not needed here". Java reads item[0].
  • Top-level private const val keeps the constants file-local without a class. Java needs private static final fields inside one.

Part 3

Deep modules and information hiding

~25 min

Ousterhout's central idea (APoSD ch. 4, "Modules Should Be Deep"): a module's interface is what callers must know, and its implementation is what they get for free. A deep module has a simple interface over a lot of functionality. His canonical example is Unix file I/O: a handful of calls (open, read, write, lseek, close) hide disks, caching, permissions and file systems, which you met in L22. A shallow module's interface is nearly as complicated as what it does.

The tool for depth is information hiding (ch. 5, "Information Hiding (and Leakage)"): each module keeps some design decision to itself. Two red flags from that chapter and ch. 7:

  • Temporal decomposition: structuring code by the order things happen ("first check, then reserve, then record"), so every caller must know the order.
  • Pass-through methods (ch. 7, "Different Layer, Different Abstraction"): methods that only forward to another layer, adding interface without adding depth.

A shallow loan desk

Here is a loan desk that exposes everything: its maps, its id counter, and four little checks callers must run in the right order. Two callers use it. The second, written months later, skips one step:

Ada's loan was silently overwritten. Nothing in the desk prevented it, because the rule "check before you record" lived in the callers. That's temporal decomposition, and it leaks: every new caller must rediscover the ritual. The reflection count makes the surface visible. Kotlin's 11 includes the generated getBooks/getNextId/setNextId accessors for those public properties, which is the Kotlin version of Java's 4 public fields.

The deep version

Move the ritual inside. Callers say what they want (lend) and get an answer that covers every case. The maps, the id scheme and the order of checks become private decisions you can change freely:

Five public methods instead of eleven, and the overwrite bug is now impossible rather than merely discouraged. The last test pins the interface itself, so a future change that widens it shows up as a red test. You've built this before: L36's LibraryRepository.lend hid the Connection, the transaction and the SQL behind one call. Depth isn't about size. It's about how much the caller doesn't have to know.

Define errors out of existence

Ch. 10 of APoSD has a provocative title, "Define Errors Out Of Existence". Every exception an interface can throw is something every caller must handle, so the best error is one the API design makes impossible. giveBack above has no "not on loan" error: returning a book that's already back just does nothing, so a double click can't crash anything. The tension with "small" and with SRP

Part 1 said "don't split too far" and this part says "hide a lot behind a small interface". Next lesson's Single Responsibility Principle says "one reason to change". They pull in different directions on purpose. The useful question each time is: does this split let a caller know less? If yes, it's a deeper design. If it only moves code around and adds names to learn, it's classitis (Ousterhout's word for it in ch. 4). L38 takes this up with SOLID.

What Kotlin does for you.
  • private by default where it matters: one keyword on private val books hides the field and the getter Kotlin would generate. In Java, a public field (or a getter you didn't mean to add) is the leak.
  • Sealed results (LendResult with data objects) let one method report every outcome without exceptions, and when makes callers handle them all. Java's enum works for simple cases; for results that carry data, it's a sealed interface plus records.
  • Error-free standard functions (take, getOrNull, getOrElse, firstOrNull, toIntOrNull) are built in. Java makes you write the bounds check yourself.
  • also (L15) let addBook return the new id and record it in one expression.

Final exercise

The late-fees kata

~25 min

Here is a late-fees calculator for L36's library, written in a hurry. It's the kind of code you'll inherit, and the kind an assistant will happily extend without cleaning up. Your job: refactor it into a deep LateFeePolicy module with a small interface, in at least six named steps, keeping the characterisation tests green after every step. Don't change behaviour, not even the weird parts.

The rules it implements (worked out by reading it; that's what you'd have to do too):

  • A loan is due 14 days after it was taken out. If that falls on a Sunday, it's due on Monday instead.
  • Per day late: DVDs 100¢, new books 50¢, everything else 25¢.
  • Still not returned? Add a 200¢ surcharge.
  • Premium members get 100¢ off each late loan, never below zero. Then each loan's fee is capped. (Check what the cap really is. The comment and the code disagree.)
  • A flag switches between a one-line total and a detailed report.

Wrap-up

Exit quiz, recall card, sources

~5 min

JDBC with autocommit on: a transfer runs two UPDATEs, and the program crashes between them. What's in the database? (L36)

With autocommit, each statement commits on its own. That's the L36 "half transfer" bug, and why lend used an explicit transaction.

Building SQL by concatenating user input into the string invites… (L33)

Use PreparedStatement with ? placeholders. A refactoring that "simplifies" a prepared statement back into string building is a behaviour change, and a dangerous one.

A Java class overrides equals but not hashCode, and you add two equal objects to a HashSet. What happens? (L7)

Equal objects land in different buckets, so the set keeps both. Records and data classes generate both methods together.

A refactoring step turns one characterisation test red. What's the safest next move? (L11)

The step changed behaviour. Undo it (that's why steps are small), then take a smaller step or find what the step broke.
