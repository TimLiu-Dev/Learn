Why it works. The memtable and the runs together are a stack of versions, newest on top. get stops at the first layer that knows the key, and a tombstone is knowledge too: "deleted". The merge applies the runs oldest first, so each key ends up with its newest version, which is what Part 3's heap merge does in one O(n log k) pass instead of a TreeMap's inserts. Only a merge of every run can drop tombstones, because nothing older is left for them to hide.

Common mistake. mem[key] ?: runs.firstNotNullOfOrNull { it[key] }. It reads well, but it treats a tombstone's null as "not here" and keeps searching, so a deleted key comes back from an older run. The other two: merging newest first, so older values overwrite newer ones, and mem.clear() in flush, which empties the run as well.
