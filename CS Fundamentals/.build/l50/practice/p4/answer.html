Why it works. Each successful deletion makes the list shorter, so the loop must end. It can only end when every single deletion was tried and passed, which is exactly the "can't delete anything" condition. On the window bug it turns [2, 1, 1, 1, 3, 1, 5, 2] into [1, 5] with target 5: the slow version finds the run [5], while the if shrinks the window once, to [5], and never measures it. It costs O(n²) calls to fails, nothing next to a debugging session. Property-testing libraries (QuickCheck, Kotest, jqwik) shrink counterexamples automatically, with smarter versions of this idea.

Common mistake. Always doing i++, even after a deletion. The element that slid into slot i is never tried, so (1..6) with "needs 2 and 5" shrinks only to [2, 4, 5].
