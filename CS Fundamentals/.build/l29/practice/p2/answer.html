Why it works. withContext(Dispatchers.IO) moves the blocking calls to the IO pool, which allows up to 64 threads, so every countRows can block at the same time and the fake's "everyone asked" latch opens. The UI thread is never blocked: while it waits, it is free to run other coroutines, such as the clicker. When the block finishes, the coroutine resumes on ui by itself. Java needs the executor passed in, and the caller must hop back to the UI thread itself (thenAcceptAsync(…, ui)).

Common mistake. withContext(Dispatchers.Default). It's off the UI thread, so it looks main-safe, but Default has one thread per core. With one table more than that, the last call can't start until another call finishes, so the blocked calls give up and return -1. That's thread-pool starvation, in miniature. Plain async with no withContext fails too: the children run on the UI thread and block it, one after another.
