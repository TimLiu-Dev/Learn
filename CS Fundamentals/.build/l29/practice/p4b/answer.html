Why it works. suspendCancellableCoroutine hands you the coroutine's Continuation, the object Part 1 found in javap. The callback calls resume on it, so the code after find(…) carries on, on the coroutine's own dispatcher, with the value or the exception. callbackFlow gives the listener a channel to trySend into, and awaitClose keeps the producer alive until the collector stops, then runs your cleanup.

Common mistake. Leaving out invokeOnCancellation. Every happy-path test still passes, but when the user leaves the screen and the coroutine is cancelled, the real request keeps running and its callback fires into nothing. On Android that's wasted battery and network, and a listener left registered can leak the whole screen. The suspendCancellableCoroutine docs show the unregister call as part of the pattern.
