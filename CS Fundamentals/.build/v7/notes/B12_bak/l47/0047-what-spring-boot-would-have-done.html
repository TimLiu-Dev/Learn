Shelf v1 gets PATCH /books/1. The path exists; the method doesn't. What comes back? (L45)

Match.WrongMethod carries the methods that do fit the path, and RFC 9110 says a 405 "MUST generate an Allow header field". You'll see Spring MVC do the same thing for you in Part 1.

  1. 404 means no route matched the path. Here the path matched; only the method is wrong.
  2. Match.WrongMethod becomes a 405, and RFC 9110 requires an Allow header listing the methods that fit.
  3. Nothing throws: the router recognises this case and answers it on purpose.
  4. Shelf never answers 200 to a request that no handler accepted.

How did your L25 CommandRouter find the methods to call? (L25)

It walked the handler's methods with reflection and kept the ones carrying @Command. Spring MVC finds @GetMapping methods the same way, at much larger scale.

  1. No build step or annotation processor generated a table; everything happened at runtime.
  2. Source files aren't available at runtime. Only the compiled classes are.
  3. It listed the handler's methods and kept the ones carrying @Command, all at runtime.
  4. No bytecode was changed: reflection reads annotations and invokes the methods as they are.

In L38's design, which code is allowed to name SqliteLoanStore? (L38)

Services depend on the LoanStore interface and receive an implementation through their constructor. Only the composition root (Shelf's Shelf class) says SqliteLoanStore(db). Spring's container takes over exactly that job.

  1. Services see only the LoanStore interface, which is why a test can hand them a fake.
  2. Tests build their own objects, and often use a fake store rather than the SQLite one.
  3. A store can't create itself: something must call its constructor and pass it a Db.
  4. One place names the concrete classes and wires them; everything else depends on interfaces.

Shelf's Kotlin Db.transaction rolls back when its block throws… (L45)

It catches Throwable, rolls back and rethrows. Shelf's Java version catches SQLException | RuntimeException. Hold on to both: Spring's default rule, in Part 2, is different from either.

  1. catch (e: Throwable) rolls back for exceptions and Errors alike, then rethrows.
  2. Kotlin has no checked exceptions, and the catch isn't limited to any kind of exception.
  3. The catch type is Throwable, far wider than SQLException.
  4. Commit runs only after the block returns normally. A throw skips straight to the rollback.

How annotation dispatch really works: build MiniSpring

"Spring finds your @GetMapping methods" can sound like magic until you write the mechanism. It takes four reflection calls, all from L25: list a class's methods, read an annotation, read parameter annotations, and invoke. Before you look at my version, here is the behaviour to aim for. The controller has two routes, two error handlers and no routing code at all; the dispatcher prints one line per request:

GET /books/7 -> 200 {"id":7,"title":"Dune"}
GET /books/99 -> 404 {"title":"Not Found","detail":"No book 99"}   (handled NoSuchElementException via notFound)
GET /books/abc -> 400 cannot convert path variable: For input string: "abc"
POST /books/7 -> 405 allowed=[GET]
GET /boom -> 500 {"title":"Internal Server Error"}   (handled IllegalAccessError via jvmError)
GET /authors -> 404 no handler

Both languages print exactly those six lines. Read the fifth one closely. /boom throws IllegalAccessError, which is an Error, not an Exception: the same kind of failure that gave L45's client silence, because Shelf's router catches only Exception. MiniSpring wraps the Error in a HandlerDispatchException, then walks the cause chain until an @OnError method matches. That is exactly what Spring does. Here is the code from DispatcherServlet.doDispatch in the Spring Framework 7.0.10 source:

catch (Exception ex) {
    dispatchException = ex;
}
catch (Throwable err) {
    // As of 4.3, we're processing Errors thrown from handler methods as well,
    // making them available for @ExceptionHandler methods and other scenarios.
    dispatchException = new ServletException("Handler dispatch failed: " + err, err);
}

And the matching rule, from the Spring docs' Exceptions page: an exception "may match against a top-level exception being propagated … or against a nested cause within a wrapper exception", and "As of 5.3, this can match at arbitrary cause levels". (Spring 5 used a NestedServletException wrapper; it was deprecated in 6.0 "in favor of standard ServletException nesting" and no longer exists in 7.0.) If nothing matches, Spring Boot's /error mapping produces a JSON 500 (Servlet Web Applications · Error Handling). So the gap L45 found in Shelf (an Error killed the response) is one Spring closes for you.

Composition root → the ApplicationContext

In Spring you don't write that class. You mark classes with @Service, @Repository or @RestController; component scanning finds them, and the container calls their constructors with the beans they ask for. The docs say plainly which style to prefer: "The Spring team generally advocates constructor injection, as it lets you implement application components as immutable objects and ensures that required dependencies are not null" (Dependency Injection). That is L38's advice, word for word. For classes you can't annotate, such as Shelf's own stores in the final exercise, you write @Bean methods in a @Configuration class. That is a composition root again, just one Spring calls for you.

What Kotlin does for you (and what it costs with Spring)
  • Kotlin annotation classes are kept at runtime by default (L25), so MiniSpring's annotations need no @Retention. Java's need @Retention(RUNTIME) or reflection never sees them.
  • Annotation arguments of class type are KClass (OnError(IllegalAccessError::class)); reflection hands you the Java class through .java.
  • A constructor parameter is a property and a dependency at once: class BookController(private val books: BookService) is constructor injection in one line. Java needs the field, the constructor and the assignment.
  • The cost: Kotlin classes are final by default, and Spring needs to subclass some of them to build proxies. Spring Boot's Kotlin docs: "Since Kotlin classes are final by default, you are likely to want to configure kotlin-spring plugin in order to automatically open Spring-annotated classes so that they can be proxied" (Kotlin Support). It's the same problem JMH had in L24. A project from start.spring.io adds kotlin("plugin.spring") for you.
Practice · A container with scopes and cycle checks

L25's container built every object afresh. Real ones don't. Write get(type) so that it builds a bean through its only constructor, resolving each parameter type with get again, and:

  • a SINGLETON is built once and then reused; a PROTOTYPE is built on every get;
  • a constructor cycle fails with IllegalStateException("Dependency cycle: A -> B -> A") instead of a StackOverflowError;
  • a failed get leaves the container usable.

implementationOf is done for you: it finds the registered class for an interface, or fails with "No bean of type …".

enum class Scope { SINGLETON, PROTOTYPE }

        scopes[type] = scope

Hint 1 of 3

Three steps, in this order: if singletons already holds impl, return it; if impl is already in creating, you've come back round a cycle; otherwise build it. type.cast(bean) turns the Any back into a T.

Hint 2 of 3

To build: impl.declaredConstructors.single(), then parameterTypes.map { get(it) }, then newInstance(*args.toTypedArray()). Add impl to creating before the recursive calls and remove it afterwards. Store the bean in singletons only for SINGLETON.

Hint 3 of 3

The cycle's path is creating.dropWhile { it != impl } + impl, joined with " -> " on simpleName. Remove from creating in a finally: a get that fails half-way must not leave Lonely marked "under construction". Java: getDeclaredConstructors()[0] and a for loop over getParameterTypes().

Final answer

Why it works. creating is the path of beans being built right now, so seeing impl on it again means the constructors form a loop. Spring reports the same situation as a BeanCurrentlyInCreationException at startup. The singleton map is what makes two Handlers share one Service, while PROTOTYPE skips it.

Common mistake. Removing impl from creating only on success. When Friend is missing, Lonely stays on the list, and the retry fails with a false "Dependency cycle: Lonely -> Lonely". Clean-up belongs in finally (L10).

MiniSpring's /boom handler throws IllegalAccessError. Which method handles it?

The dispatcher wraps the Error in an exception, then walks getCause(): the wrapper doesn't match any handler, its cause does. Spring's DispatcherServlet wraps in a ServletException for the same reason.

  1. That was Shelf v1's gap. MiniSpring wraps the Error, so the request still gets an answer.
  2. The fallback runs only when nothing in the cause chain matches a handler, and here something does.
  3. The wrapper matches no handler, so the walk reaches its cause, an IllegalAccessError, which jvmError declares.
  4. notFound handles NoSuchElementException, which appears nowhere in this cause chain.

In Spring MVC, GET /books/abc reaches a method with @PathVariable id: Long. The default response is…

The conversion fails with a TypeMismatchException, which DefaultHandlerExceptionResolver maps to 400. Shelf's L45 router answered 404 on purpose; in Spring you'd override the default to keep that.

  1. 404 was Shelf's deliberate choice. Spring's default for a failed conversion is different.
  2. TypeMismatchException maps to 400: the request itself is malformed.
  3. 405 means the method is wrong, but GET is mapped here.
  4. The resolver handles the failure, so it never becomes an unhandled 500.

Two templates match /books/featured. What does this print?

fun matches(template: String, path: String): Boolean {
    val t = template.split("/")
    val p = path.split("/")
    return t.size == p.size && t.zip(p).all { (a, b) -> a.startsWith("{") || a == b }
}

fun variables(template: String) = template.count { it == '{' }

fun main() {
    val routes = listOf("/books/{id}" to "byId", "/books/featured" to "featured")
    val path = "/books/featured"
    val first = routes.first { matches(it.first, path) }.second                        // Shelf's rule
    val ranked = routes.filter { matches(it.first, path) }.minBy { variables(it.first) }.second   // Spring's rule
    println("$first $ranked")
}

first stops at the first template that matches, and {id} matches any segment, including featured. Ranking by the fewest URI variables picks the literal /books/featured, which is Spring's rule. Shelf's router used the first.

  1. The ranked line ignores list order: it picks the template with the fewest variables, the literal one.
  2. The first-match line stops at /books/{id}, because {id} matches featured too.
  3. First match takes the earlier {id} route; ranking prefers zero variables to one.
  4. It's the other way round: list order favours byId, and ranking favours featured.

Final answer

Why it works. Lookup order is precedence: the environment overrides the properties file, which overrides the default, as in Spring's externalized configuration. Collecting problems instead of throwing at the first one gives the operator the whole list in one go; Spring Boot does the same for @Validated configuration properties: its startup failure report prints a Property, Value and Reason block for every constraint that failed. A value that can't be converted at all, such as 'abc' for an int, stops binding at that one field instead. (Both behaviours are read from Spring Boot's source, BindValidationFailureAnalyzer and Binder; the reference docs don't spell them out.)

Common mistake. Throwing at the first bad value. The message is right, but a file with two mistakes then takes two failed deploys to fix, and the test that sets both shelf.port and shelf.pool-size sees only one.

In TxProxy, the unannotated lendBoth(2, 3) calls the annotated lend twice. How many transactions open?

The calls go to this, the real object, so the proxy never sees them. Spring's docs: self-invocation "does not lead to an actual transaction at runtime even if the invoked method is marked with @Transactional".

  1. A transaction opens only for a call that goes through the proxy. These go straight to this.
  2. lendBoth isn't annotated, and its inner calls bypass the proxy, so nothing opens.
  3. One shared transaction needs @Transactional on lendBoth itself: that's Exercise 2.
  4. No call reached the transactional path at all, so nothing opened, let alone nested.

A Spring @Transactional method throws a checked IOException. By default, Spring…

"Checked exceptions that are thrown from a transactional method do not result in a rollback in the default configuration." Rollback rules (rollbackFor) change it.

  1. Rollback is the default only for RuntimeException and Error. IOException is checked.
  2. A transaction proxy never retries. Retrying is a separate decision (L43).
  3. By default a checked exception doesn't trigger rollback, so the work commits and the exception still reaches the caller.
  4. Spring doesn't swallow the exception: the caller still sees it.

  2. The container calls constructors with the beans they ask for.

  4. Indexes depend on your queries and your data. No framework can choose them (L35).

Through a JDK proxy, Kotlin's importLoan threw an undeclared IOException. The caller saw…

A proxy may only rethrow the checked exceptions the interface method declares. Kotlin declared none, so the JDK wrapped it. @Throws(IOException::class) on the interface method fixes it.

  1. Java's caller sees that. Kotlin's interface method declares no throws, so the proxy can't rethrow it as is.
  2. The JDK wraps any checked exception that the interface method doesn't declare.
  3. Method.invoke throws that inside the handler, but TxProxy unwraps it before rethrowing.
  4. That's Spring MVC's dispatcher wrapper. No servlet is involved in TxProxy.

public class SelfCall {
    interface Desk {
        void lendBoth();
        void lend();
    }

    static class RealDesk implements Desk {
        public void lendBoth() { lend(); lend(); }
        public void lend() { }
    }

    public static void main(String[] args) {
        int[] seen = {0};
        Desk real = new RealDesk();
        Desk desk = (Desk) Proxy.newProxyInstance(Desk.class.getClassLoader(), new Class<?>[] {Desk.class},
            (proxy, method, params) -> {
                seen[0]++;
                return method.invoke(real, params);
            });
        desk.lendBoth();
        desk.lend();
        System.out.println(seen[0]);
    }
}

The proxy sees only calls made on desk: lendBoth and the direct lend. Inside RealDesk.lendBoth, lend() means this.lend(), and this is the real object. It's TxProxy's self-invocation trap, counted.

  1. The lambda holds a reference to the same array, so its increments are visible in main (L5's aliasing).
  2. Two calls go through the proxy: lendBoth, and then the direct lend.
  3. The two inner lend() calls run on this, the real object, so the proxy never sees them.
  4. Changing an array element is allowed. Only the variable seen itself must be effectively final.

Spring's default rollback rule, applied to four failures. What does this print? (R = roll back, C = commit)

import java.io.IOException
import java.io.UncheckedIOException
import java.sql.SQLException

// Spring's default rule for @Transactional, as TxProxy copies it
fun rollsBack(t: Throwable) = t is RuntimeException || t is Error

fun main() {
    val failures = listOf(
        UncheckedIOException(IOException("disk full")),
        SQLException("database is locked"),
        AssertionError("bad state"),
        Exception("plain"),
    )
    println(failures.joinToString(" ") { if (rollsBack(it)) "R" else "C" })
}

The rule looks only at each object's runtime class. UncheckedIOException extends RuntimeException, whatever it wraps. SQLException and plain Exception are checked, so they commit. AssertionError is an Error.

  1. The wrapped IOException doesn't matter: UncheckedIOException itself is a RuntimeException.
  2. SQLException is checked, so the default commits, database error or not. Add rollbackFor to change that.
  3. Kotlin not declaring checked exceptions changes nothing: the rule tests each object's class at runtime.
  4. The runtime exception and the Error roll back; the two checked exceptions commit.

When you find a security bug

Sooner or later you'll notice one in someone else's system: change an id in a URL and see a stranger's data (L33's IDOR). What you do next matters more than how clever the find was. The usual answer is coordinated disclosure. The OWASP Vulnerability Disclosure Cheat Sheet describes it: "the initial report is made privately, but with the full details being published once a patch has been made available".

  1. Stop. Confirm it with one request, and don't explore further, download data or change anything. Seeing it isn't permission to use it (ACM 2.8).
  2. Find the private channel. Look for /.well-known/security.txt. RFC 9116 says web services "MUST place the 'security.txt' file under the '/.well-known/' path". Its Contact field "MUST always be present", and its Expires field "MUST always be present and MUST NOT appear more than once", so a stale file announces itself. No file? OWASP lists the fallbacks: a bug bounty programme, security@, the contact page, and failing all those, a national CERT.
  3. Report clearly. Include the steps to reproduce, the request and response, and the impact. OWASP: "Redact any personal data before reporting."
  4. Coordinate the timing. Agree when the details may be published, normally after a fix. Deadlines are common: Google's Project Zero, OWASP notes, "generally gives vendors 90 days". Never ask for payment as a condition of telling them; OWASP warns that "this may constitute extortion".
  5. On your own systems, be the good receiver. Publish a security.txt, answer reports quickly, fix, and credit the reporter. Shelf's could be five lines:
# https://shelf.example.com/.well-known/security.txt
Contact: mailto:security@shelf.example.com
Expires: 2027-11-01T00:00:00Z
Policy: https://shelf.example.com/security-policy
Preferred-Languages: en

RFC 9116 recommends an Expires "less than a year into the future", so renewing it becomes a yearly task, and a forgotten file goes visibly stale instead of quietly pointing at a dead mailbox.

Should this be built?

Say a product manager asks for a Shelf feature: "email every member's full reading history to all staff each week, so they can recommend books". It's easy to build. Ask the Code's questions first:

  • Who could be harmed, including people who aren't your users? "Avoiding harm begins with careful consideration of potential impacts on all those affected by decisions" (1.2). Reading history can reveal health, beliefs and politics, and an email to every member of staff can't be recalled once it's sent.
  • What's the least data that does the job? Staff need open loans, not lifetimes of history. Collect less, keep less and log less: that's L33's personal-data part, and 1.6's "Personal information gathered for a specific purpose should not be used for other purposes without the person's consent."
  • What happens when it leaks or is misused? Joining data you hold separately creates new risks: "the consequences of data aggregation and emergent properties of systems should be carefully analyzed" (1.2).
  • Is there a safer version? Usually there is: opt-in recommendations computed from the member's own loans, shown only to that member. And sometimes there isn't: "In cases where misuse or harm are predictable or unavoidable, the best option may be to not implement the system" (2.9).

Raise these questions in the design review (L44's design doc has room for them), not after launch. If leaders ignore a serious risk, the Code goes further: "it may be necessary to 'blow the whistle' to reduce potential harm". It also warns that "capricious or misguided reporting of risks can itself be harmful", so check your facts first (1.2).

In Java, Integer a = 1000, b = 1000; System.out.println(a == b); (L5)

== compares references, and the Integer cache only covers −128 to 127 (Integer.valueOf docs). Two boxes of 1000 are different objects; use equals.

  1. Only values from −128 to 127 come from the cache, so 1000 gives two separate objects.
  2. Two distinct Integer objects, and == compares references.
  3. Comparing two references is legal and safe: nothing is unboxed, so nothing can fail.
  4. == between two Integers compiles. It just compares identity.

Appending to the end of an ArrayList costs, amortised… (L16)

Most appends write into spare capacity; the occasional copy when the array grows is spread over all the appends that came before it.

  1. Growing the array by a factor makes the rare copies average out to constant work per append.
  2. Appending searches nothing and halves nothing, so there's no source of a log factor.
  3. O(n) is the cost of one occasional resize, not the average over all appends.
  4. No sorting happens when you append.

A class overrides equals but not hashCode. You add an object to a HashSet, then ask contains with an equal copy. It usually… (L19)

The copy has a different identity hash, so the set looks in the wrong bucket and never calls equals. Equal objects must have equal hash codes (Object.hashCode contract, L7).

  1. A missing hashCode is legal. The set just looks in the wrong bucket, with no error.
  2. Only by luck: equal copies almost always get different identity hashes.
  3. Overriding only equals compiles. The compiler doesn't check the contract.
  4. The lookup goes to the copy's bucket, finds nothing there, and never calls equals.

Two threads each run count++ a million times on a plain shared field. The final value is… (L26)

count++ is read, add, write. Two threads can read the same value and both write it back plus one, losing an update. Some runs may still land on 2,000,000; that proves nothing.

  1. That needs a lock or an atomic counter. count++ on its own isn't atomic.
  2. An update is lost whenever both threads read the same value before either writes.
  3. Most increments do land. Losing exactly one thread's work would be a coincidence.
  4. Updates can be lost but never invented, so the total can't exceed 2,000,000.

A worker loops while (!stop) on a plain field that the main thread sets to true. On HotSpot, the worker can… (L27)

With no happens-before edge, the JIT may hoist the read out of the loop; in L27 it hung on every run. volatile (or @Volatile) fixes it.

  1. A stale read raises no error. The thread just keeps seeing the old value.
  2. It compiles fine: the problem is the memory model, not the compiler.
  3. With no happens-before edge, the JIT may hoist the read, so the loop never sees true.
  4. Nothing guarantees the write is ever seen, let alone at once.

A composite index on loans(member_id, loaned) can serve which WHERE clause on its own? (L35)

A B-tree index is sorted by its leftmost column first, so it helps member_id = ? but not loaned alone. A function on a column, or a leading %, defeats an index.

  1. loaned is the second column, so without member_id the index's order doesn't help.
  2. member_id is the leftmost column, so the B-tree can seek straight to the matching rows.
  3. A function on a column hides it from a plain index. It needs an expression index.
  4. A leading % means the prefix is unknown, so the sorted order can't help.

With autocommit on, your code runs two UPDATEs and crashes between them. Afterwards… (L36)

Autocommit makes every statement its own transaction, so the first one is already committed. That's L36's half-finished transfer; Shelf's Db.transaction and Spring's @Transactional both exist to prevent it.

  1. Undoing both needs one transaction around them. Autocommit gave each its own.
  2. The first UPDATE ran and committed before the crash.
  3. Autocommit committed the first statement on its own, so it survives the crash.
  4. The database accepted the first update and never saw the second.

Which response header lets a client revalidate cheaply and get 304 Not Modified? (L31)

The client sends the tag back in If-None-Match; if it still matches, the server answers 304 with no body (RFC 9110, RFC 9111).

  1. Location points at a resource, after a 201 or in a redirect.
  2. Allow lists the methods a resource supports, as in a 405.
  3. Retry-After says when to try again, after a 429 or a 503.
  4. The client sends it back in If-None-Match, and a match gets a 304.

How should Shelf store a member's password? (L33)

A per-user salt defeats precomputed tables, and a deliberately slow, adaptive hash makes each guess expensive (OWASP Password Storage Cheat Sheet). Base64 is not even encryption.

  1. A per-user salt and a slow, tunable work factor make every single guess expensive.
  2. Base64 is an encoding that anyone can reverse (L33).
  3. SHA-256 is fast and unsalted, so guessing and lookup tables are cheap.
  4. Encryption is reversible: whoever steals the key gets every password.

Five hundred requests miss the same expired cache key at the same moment. The standard fix is… (L41)

One request loads the value and the others wait for its result; L41 took 50 database hits down to 1. Spring's @Cacheable(sync = true) is the same idea.

  1. Memory isn't the problem. Five hundred identical database loads are.
  2. A shorter TTL makes the key expire more often, so stampedes happen more often.
  3. One request loads the value, and the others wait for its result.
  4. More threads would send even more concurrent loads to the database.

Going from four nodes to five with consistent hashing, roughly how many keys move? (L42)

Only the keys the new node takes over move: about 1/N. Plain hash mod N moved 80% of them in L42.

  1. About four fifths move with hash mod N. The ring exists to avoid that.
  2. The new node takes over only its share of the ring, about 1/N of the keys.
  3. Only a full rehash moves every key. Consistent hashing moves the minimum.
  4. The new node has to take some keys, or it would serve nothing.

A circuit breaker's open timeout has passed, and it lets a single trial call through. Its state is… (L43)

From HALF_OPEN, a successful trial closes the breaker and a failure opens it again (Fowler's CircuitBreaker, L43).

  1. CLOSED lets every call through. The breaker returns there only after the trial succeeds.
  2. OPEN fails calls fast without trying them, and the timeout has just ended that state.
  3. There's no FAILED state: the three are closed, open and half-open.
  4. After the timeout, one trial call decides whether to close the breaker or reopen it.

A public Kotlin function with a non-null String parameter compiles to bytecode that… (L23)

kotlinc inserts Intrinsics.checkNotNullParameter, so a Java caller passing null fails at the boundary instead of deep inside your code. You saw it in javap in L23.

  1. Strings are immutable, so there's nothing to gain from a copy. The reference is passed.
  2. Kotlin's nullability isn't Optional: it's a compile-time type plus a runtime check at the boundary.
  3. Interning is a string-pool feature. kotlinc doesn't add it to parameters.
  4. Intrinsics.checkNotNullParameter makes a Java caller's null fail right at the call.

Which is the classic memory leak in a garbage-collected language? (L24)

Anything reachable from a static field is reachable from a GC root, so it is never collected. L24 took one to OutOfMemoryError and found it with a heap histogram.

  1. A bounded cache evicts old entries, so its memory stays capped.
  2. A static field is a GC root, so everything in the map stays reachable forever.
  3. A local list becomes unreachable when the method returns, so it's collected.
  4. An empty immutable set can never grow, so it can't leak.

A Java method takes List<? extends Number>. Inside it, you can… (L13)

"Producer extends": every element is some kind of Number, so reading is safe, but the compiler can't know which subtype the list holds, so adding is refused. Kotlin writes it List<out Number>.

  1. The list might be a List<Double>, so adding an arbitrary Number could corrupt it.
  2. Even an Integer might not belong: the list could hold Doubles.
  3. Whatever the real element type is, every element is a Number, so reading is safe.
  4. Removing is allowed: remove(Object) and clear() don't need the element type.

~5 min

A Java annotation declared without @Retention is, at runtime… (L25)

The default is RetentionPolicy.CLASS: recorded in the class file but not available through reflection. That's why MiniSpring's Java annotations say @Retention(RUNTIME).

  1. Only RetentionPolicy.RUNTIME makes an annotation visible to reflection.
  2. The default, CLASS, keeps it in the class file but hides it from reflection.
  3. That's SOURCE retention. The default keeps the annotation in the class file.
  4. Inheritance needs @Inherited, and it applies only to annotations on classes.

Why does the Spring team advocate constructor injection? (L38)

The docs: it "lets you implement application components as immutable objects and ensures that required dependencies are not null". L38 gave the same reasons for injecting by hand.

  1. Speed isn't the reason the docs give, and the injection style barely affects it.
  2. Constructor injection works hand in hand with interfaces: L38 used both together.
  3. Fields set once in the constructor can be final, and a required one can't be missing.
  4. Spring still uses reflection to call the constructor.

In Spring Boot 4.1, spring.threads.virtual.enabled is… (L28)

The docs say "To enable virtual threads, set the spring.threads.virtual.enabled property to true", and warn about pinned virtual threads (L28).

  1. You set the property to true to enable them. Nothing turns them on for you.
  2. It's a current property, documented on the SpringApplication page for Boot 4.1.
  3. Virtual threads arrived in Java 21. Java 8 has none.
  4. Virtual threads are opt-in: you set the property to true yourself.

Shelf v1's Kotlin router catches Exception. Spring's DispatcherServlet also catches… (L45)

Since Spring 4.3 it catches Throwable and wraps an Error in a ServletException, "making them available for @ExceptionHandler methods" (the comment in its source).

  1. Catching only RuntimeException would miss Errors, which is exactly Shelf's gap.
  2. Since 4.3 it catches Throwable and wraps an Error, so @ExceptionHandler methods can match it.
  3. IOException is one checked exception among many. The dispatcher catches far wider.
  4. The dispatcher knows nothing about JDBC: an SQLException is caught as an Exception.
