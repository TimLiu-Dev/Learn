When does the garbage collector consider an object collectable? (L24)

Reachability is the rule: an object stays alive while a chain of references leads to it from a GC root (a local variable in a live frame, a static field, and so on). Setting one reference to null only helps if it was the last path.

Part 1

Annotations

~25 min

The Java spec is blunt about it: "An annotation is a marker which associates information with a program element, but has no effect at run time" (JLS §9.7). An annotation is a label stuck on a class, method, field or parameter. Nothing happens until some tool reads the label. There are exactly three kinds of reader, and every annotation you'll ever meet is aimed at one of them:

Who reads itWhenExamples
The compilerwhile compiling@Override, @Deprecated, @Suppress, @JvmStatic, @JvmOverloads
An annotation processor (KSP, kapt, javac's processors)during the build, generating new source filesRoom's @Dao, Dagger's @Component, Moshi's @JsonClass
Your program, through reflectionat runtimeJUnit's @Test, Spring's @Autowired and @GetMapping, and today's @Command

Built-in annotations

@Deprecated is the one you'll meet most, and it shows the two languages' different styles. Kotlin's version carries a message, a machine-readable replacement (IntelliJ turns it into a one-click fix) and a level. Java's carries since and forRemoval:

  • My first Java draft put oldPrice and main in the same class, and javac printed no warning at all. The spec exempts uses where "the declaration where the use appears and the declaration of the … deprecated program element are both within the same outermost class" (JLS §9.6.4.6). That's why Prices is a separate class.
  • The [removal] warning appears with no -Xlint flag: the JLS says a compiler "must produce a removal warning" for terminally deprecated elements.

Raise Kotlin's level to ERROR and the same call no longer compiles. That's how library authors move users along: warning first, error in the next release, deletion after that.

Declaring your own

Java declares an annotation with @interface. Its elements look like methods and can have defaults. Kotlin uses annotation class, and the elements are constructor parameters. Both get two meta-annotations, which are annotations on annotations. @Target says what the annotation may be attached to. @Retention says how long it survives:

KotlinJavaKept until
SOURCESOURCEcompilation. Not in the .class file at all.
BINARYCLASSthe .class file, but invisible to reflection
RUNTIME ★ the defaultRUNTIMEruntime: reflection can read it

The defaults differ, and this trips people up. A Kotlin annotation with no @Retention is kept and visible "by default" (Kotlin docs: Annotations). A Java one with no @Retention "defaults to RetentionPolicy.CLASS" (Retention API docs), so reflection never sees it. Watch all three lifetimes at once:

save -> [@Timed(warnAbove=50, unit="ms")]
load -> [@Timed(warnAbove=100, unit="ms")]
save: unit=ms warnAbove=50

Both languages print exactly this. save carries three annotations, but reflection reports only @Timed. Where did the other two go? L23's javap -v answers it. Here is save() from the compiled Kotlin class; the Java class is identical apart from line numbers:

@Timed sits in a RuntimeVisibleAnnotations attribute. @Audited (BINARY/CLASS) is in the file but marked invisible: tools that read class files can see it, reflection can't. @Draft (SOURCE) is gone entirely. One more you've already met without knowing it: every class kotlinc writes carries a RuntimeVisibleAnnotations entry for @kotlin.Metadata. It "is present on any class file produced by the Kotlin compiler and is read by the compiler and reflection" (API docs). That's where Kotlin-only facts like properties and nullability survive compilation.

What an annotation's elements may hold is restricted: primitives, strings, class literals, enums, other annotations, and arrays of those. Kotlin adds that "annotation parameters cannot have nullable types, because the JVM does not support storing null as a value of an annotation attribute" (Kotlin docs).

Kotlin use-site targets

One Kotlin line, class User(val email: String), produces three JVM things: a constructor parameter, a private field, and a getEmail() getter (L6). So when you annotate email, which one gets the annotation? Kotlin lets you say exactly, with a use-site target: @field:, @get:, @set:, @param:, @property:, @file:, and since 2.4 @all: (Kotlin docs: use-site targets). The Java comparison is a record, whose components produce the same three things:

a: param=[] field=[field] getter=[]
b: param=[] field=[] getter=[get]
c: param=[param] field=[] getter=[]
d: param=[none] field=[none] getter=[]
e: param=[all] field=[all] getter=[all]
a: param=[component] field=[component] getter=[component]
  • Explicit targets (a, b, c) land exactly where you say.
  • No target (d): "the compiler chooses one or more" of them. The constructor parameter if applicable, then the property if applicable, then the field "if it's applicable and the property target isn't" (Kotlin docs). Tag can't target a Kotlin property, so d gets param and field. That's what a Java framework reading fields expects.
  • This rule is new. Before Kotlin 2.2, an annotation went to "only one of param, property, or field" (What's new in 2.2), usually just the parameter. The new defaults and @all: became Stable in Kotlin 2.4.0. Older Stack Overflow answers about "my @Email annotation is ignored" describe the old rule.
  • Java records do this automatically: a component annotation "is propagated to the declarations of members and constructors of the record class if their annotation interfaces are applicable" (JLS §8.10.1). That's why the Java side shows it in all three places.
  • @property: annotations are "not visible to Java" at all. Only Kotlin's own reflection sees them (Part 2).

Annotation processing: code that writes code

The middle reader in the first table runs during the build. An annotation processor sees your annotated declarations and generates new source files that get compiled with the rest. No reflection is needed at runtime, so it's fast and errors appear at compile time. Kotlin has two ways to run one:

kaptKSP
What it isRuns existing Java annotation processors on Kotlin by first generating Java stubs (Kotlin docs: kapt)Kotlin Symbol Processing: "a source code generation framework for Kotlin" (Kotlin docs: KSP)
StatusAndroid's docs: "Kapt is now in maintenance mode, and we recommend that you migrate from kapt to KSP" (Migrate to KSP)The current choice. Typical users named in its docs: Dagger, Moshi, Room
LimitsSlower: stub generation is an extra pass"can't examine expressions or statements, and they can't modify the source code"

You won't write a processor in this course. Just recognise the pattern: when an Android library says "add the KSP plugin", it's generating code from your annotations at build time.

What Kotlin does for you.
  • override and fun interface are keywords, so you can't forget them the way you can forget @Override.
  • Custom annotations default to RUNTIME, so they're readable by reflection with no extra line. A Java annotation without @Retention(RUNTIME) is silently invisible.
  • @Deprecated can carry a ReplaceWith that the IDE applies for you, and a level that escalates a warning to an error.
  • Annotation elements are ordinary constructor parameters with defaults, and arguments can be named: @Timed(warnAbove = 50).
  • The cost: one property is three JVM elements, so you sometimes have to say which one with @field: or @get:. Java records spread annotations to all three automatically.

Part 2

Reflection

~25 min

Reflection is code inspecting and using other code at runtime: listing a class's methods, calling one by name, reading its annotations, creating instances. dev.java: "Reflection is commonly used by programs which require the ability to examine or modify the runtime behavior of applications running in the Java virtual machine" (dev.java: The Reflection API). It's how a framework can call your methods without ever having been compiled against them.

Getting hold of a class

Everything starts from a class object. Java has Class<T>. Kotlin has its own KClass<T>, which knows Kotlin-only things like properties and nullability, plus a bridge to the Java one:

class Point | class Point
same KClass: true, same Class: true
bridge: true, true
names: Point Point
class Point
same Class: true
names: Point Point
record? true, super: class java.lang.Record

There's exactly one Class object per loaded class (per class loader, L23), so === is true however you got it. Class.forName("Point") is the interesting one: the name is just a string, so it could come from a config file. That's how plugin systems and JDBC drivers get loaded.

Inspecting, invoking, and breaking in

fields:  [balance]
methods: [audit, deposit]
balance=1250
balance=5
  • Sort what you list. The Class docs say the arrays from getMethods/getFields "are not sorted and are not in any particular order" (Class API docs). Never rely on declaration order.
  • A method is identified by name plus parameter types. getMethod("deposit", int.class), because overloads (L3) share a name. Kotlin's Int maps to the primitive through Int::class.javaPrimitiveType.
  • setAccessible(true) switches off access checks. The last line set a private field to 5, skipping deposit and every invariant you wrote in L6. Frameworks (JSON libraries, ORMs, DI containers) do this routinely. It's also why "private" in a reflective world means "please don't", not "can't".

Kotlin reflection needs an extra jar

Kotlin's richer API (memberProperties, declaredFunctions, findAnnotation, call) lives in a separate library. The docs explain that the runtime component is "a separate artifact, kotlin-reflect.jar. This allows applications without reflection features to exclude this artifact and reduce the size of the runtime classpath" (Kotlin docs: Reflection). In a fresh gradle init project (L1), it isn't there, and it fails in two different ways. Using the kotlin.reflect.full extensions doesn't even compile:

  1. Typos fail at runtime. "ad" compiles happily. You find out only when that line runs, which is the compile-time safety you gave up.
  2. Exceptions arrive wrapped. The divide-by-zero inside divide comes out as an InvocationTargetException whose cause is the real error. A catch (ArithmeticException) around invoke would not catch it. Your router will unwrap this.
  3. JDK internals are locked. Since JDK 17 it is "no longer … possible to relax the strong encapsulation of internal elements via a single command-line option" (JEP 403). Reflection works on your code and on libraries' public APIs, not on java.lang's private fields.
  4. It's slower. On my machine, about 6–7 ns per reflective call (boxing the arguments, checking them, dispatching) against well under 1 ns direct. Honestly, that "direct" number is too good to be real: the JIT (L23) has probably inlined and unrolled the loop. This is precisely the trap L24's JMH exists to avoid, so treat these numbers as "reflection costs a few nanoseconds", not as a benchmark. Since JDK 18, core reflection is built "on top of java.lang.invoke method handles" (JEP 416). Frameworks also scan once at startup and cache the Method objects, as your router will.
Bridge to Android and Spring. Android's R8 shrinker deletes and renames code it thinks is unused. Code that's only reached by reflection looks unused, so it needs keep rules; R8's full mode "might require additional keep rules to prevent necessary code from being stripped" (Android docs: R8). On the server, Spring scans your classes at startup. It finds @Autowired constructors and fields (annotation-based configuration) and @GetMapping methods (mapping requests), builds tables from them, and calls your methods when a request arrives. JUnit does the same with @Test, and even lets you build composed annotations out of its own (JUnit: Annotations). In the final you'll build the same idea in about 60 lines.
What Kotlin does for you.
  • X::class gives a KClass that understands properties, nullable types and default arguments. .java and .kotlin cross between the two worlds.
  • findAnnotation<T>() uses reified (L13): no Class token, no cast.
  • callBy honours default parameter values and named arguments. Java reflection must supply every argument positionally.
  • apply { isAccessible = true } configures the reflected member in one expression (L15).
  • The cost: the full API needs kotlin-reflect on the classpath, a 3.7 MB jar (kotlin-reflect-2.4.0.jar in this build) that you add yourself.

Why do frameworks scan for annotations once at startup and keep the Method objects?

Scanning and lookups are the slow part, and a mistake like a duplicate route or a bad signature should crash at startup, not on the first request. Your router's constructor does all its checks for exactly this reason.

The word before each dependency is its configuration. It decides when the library is on the classpath. Quoting Gradle: Dependency Configurations:

ConfigurationGradle's descriptionTypical use
implementation"required for both compilation and runtime"Guava, kotlin-reflect, your normal libraries
api"… and included in the published API" (java-library plugin only)a library whose public methods expose another library's types
compileOnly"needed only for compilation, not included in runtime"annotation-only jars the runtime provides or never needs
runtimeOnly"needed only at runtime, not included in the compile classpath"a logging backend or JDBC driver loaded by name
testImplementation"required for compiling and running tests"JUnit, kotlin-test

The api versus implementation distinction matters for libraries. api dependencies "will be transitively exposed to consumers … Dependencies found in the implementation configuration will, on the other hand, not be exposed to consumers, and therefore not leak into the consumers' compile classpath" (Java Library plugin). In an application, use implementation.

Fix 2: one "fat" jar

Gradle's docs note that it has no built-in way to create uber JARs. They point to the third-party Shadow plugin, or show a Jar task that unzips every runtime jar into yours (Gradle: Creating "uber" or "fat" JARs). I pasted their example and it failed:

Execution failed for task ':app:uberJar' (registered in build file 'app/build.gradle.kts').
> Entry META-INF/versions/9/module-info.class is a duplicate but no duplicate handling strategy has been set. Please refer to https://docs.gradle.org/9.7.1/dsl/org.gradle.api.tasks.Copy.html#org.gradle.api.tasks.Copy:duplicatesStrategy for details.

Six of the runtime jars (Guava, failureaccess, JSpecify, the Kotlin stdlib and two more) each contain META-INF/versions/9/module-info.class, and a zip can hold only one file per path. With the DuplicatesStrategy line added, it works:

// From Gradle's docs, "Creating uber or fat JARs": copy every runtime jar inside.
tasks.register<Jar>("uberJar") {
    archiveClassifier = "uber"
    duplicatesStrategy = DuplicatesStrategy.EXCLUDE   // keep the first copy of clashing files
    manifest { attributes("Main-Class" to "demo.AppKt") }
    from(sourceSets.main.get().output)
    dependsOn(configurations.runtimeClasspath)
    from({
        configurations.runtimeClasspath.get().filter { it.name.endsWith("jar") }.map { zipTree(it) }
    })
}
$ ./gradlew uberJar
$ ls -la app/build/libs | grep jar
-rw-r--r--@ 1 tl  wheel  4885088 Oct 20 05:04 app-uber.jar
-rw-r--r--@ 1 tl  wheel     1590 Oct 20 05:04 app.jar
$ java -jar app/build/libs/app-uber.jar Ada
Hello, Ada!
=============

1.6 KB of your code, 4.9 MB of everyone else's, 3,187 files. Fat jars are convenient to ship, but discarding duplicates is a blunt tool: if two libraries need different versions of a file with the same name, one of them silently loses. That's why Shadow exists, and why installDist is the calmer default.

Bridge to Android and Spring. An Android app is a Gradle build with the Android Gradle Plugin applied (Android docs: Configure your build). It adds tasks that compile to DEX (L23) and package an APK or bundle instead of a jar, but the files, configurations and dependency trees are the ones you just read. Spring Boot's Gradle plugin adds a bootJar task that creates "executable archives … that contain all of an application's dependencies and can then be run with java -jar" (Spring Boot: Packaging). It's a smarter fat jar: dependencies "should be placed in a nested BOOT-INF/lib directory", whole jars inside the jar, instead of being unzipped together (Spring Boot: Nested JARs). That avoids the duplicate problem you just hit.
What Kotlin (and the Kotlin DSL) do for you.
  • Build scripts are Kotlin, so libs.guava and tasks.jar { … } are type-checked, with autocompletion in IntelliJ.
  • kotlin("reflect") is shorthand for org.jetbrains.kotlin:kotlin-reflect with no version: the tree shows it resolved to kotlin-reflect -> 2.4.0, the plugin's version, so the two can't drift apart.
  • "A dependency on the standard library (stdlib) is added automatically", at "the same as the version of the Kotlin Gradle plugin" (Kotlin docs: Configure a Gradle project).
  • The cost: that stdlib must be on the runtime classpath, as the Intrinsics crash showed. A plain Java app with no dependencies runs from a bare jar with a Main-Class. A Kotlin app never does, unless it avoids the stdlib entirely like gradle init's Hello World. I checked: that one runs, because println is an inline function, and javap -c shows it compiled straight to java/io/PrintStream.println.

The tests run in a different order each time, which is fine, because each test is independent (L11). Notes on the design:

  • Kotlin's KFunction.call also wraps a handler's exception in InvocationTargetException, the same as Java's Method.invoke. That's why both routers catch it and report e.cause.
  • The signature check can only test for List, not List<String>, in Java: erasure (L13). Kotlin's fn.parameters.size == 2 counts the receiver as parameter 0.
  • Java's router calls setAccessible(true), because Greetings is package-private. Real frameworks do the same, which is why Part 2's encapsulation rules matter to them.
  • The container is constructor injection by type. "The Spring team generally advocates constructor injection, as it lets you implement application components as immutable objects and ensures that required dependencies are not null" (Spring docs: Dependency Injection). Real containers add scopes, interfaces, cycle detection (L21's topological sort!) and much more, but the core is these ten lines.

This is, in miniature, what Spring MVC and JUnit do. Spring scans for @GetMapping the way your router scans for @Command, builds a table from them, converts the request into arguments, calls your method reflectively and converts the result into a response. JUnit scans for @Test, "creates a new instance of each test class before executing each test method" (JUnit: Test Instance Lifecycle) and calls it, reporting exceptions instead of crashing. From now on, when a framework "magically" calls your code, you know the steps.

Wrap-up

Exit quiz, recall card, sources

~5 min

Your router stores commands in a HashMap<String, Method>. Average cost of looking up one command by name? (L19)

A hash table gives average O(1) get. That's why the router builds the map once at startup and never scans the methods again per call.

Kotlin: try { m.invoke(calc, 1, 0) } catch (e: ArithmeticException) { println("caught") }, where m is divide. What happens? (L10)

The ArithmeticException arrives wrapped in an InvocationTargetException, which the catch doesn't match, so it escapes and the program dies. I ran it to check: Exception in thread "main" java.lang.reflect.InvocationTargetException.

Why can't Java reflection tell whether a parameter is List<String> or List<Integer> through getParameterTypes()? (L13)

getParameterTypes() returns the erased class, List.class. Generic signatures are kept as metadata for getGenericParameterTypes(), but the runtime type of a list never knows its element type.

Which annotation lets kotlin-reflect recover Kotlin-only facts, like properties and nullability, from a .class file? (L23)

kotlinc writes @kotlin.Metadata as a runtime-visible annotation on every class. It "is read by the compiler and reflection".
