Match.WrongMethod carries the methods that do fit the path, and RFC 9110 says a 405 "MUST generate an Allow header field". You'll see Spring MVC do the same thing for you in Part 1.

In L38's design, which code is allowed to name SqliteLoanStore? (L38)

Router → @RestController

Here are two Shelf routes from L45, and the same two endpoints as a Spring MVC controller. The Shelf code is excerpted, line for line, from the tested L45 files; the Spring code follows the PersonController example in the Spring Framework docs' Mapping Requests page.

Line by line:

  • get("/books/{id}") { req -> … } becomes @GetMapping("/{id}") on a method. The Router you registered routes with becomes Spring's DispatcherServlet: Spring MVC "is designed around the front controller pattern where a central Servlet, the DispatcherServlet, provides a shared algorithm for request processing" (DispatcherServlet). @RestController marks "a controller whose every method inherits the type-level @ResponseBody annotation and, therefore, writes directly to the response body" (Declaration).
  • req.id(), which parsed the string and turned a bad id into a 404, becomes @PathVariable id: Long. Spring converts the string for you, and a failed conversion is a TypeMismatchException, which Spring answers with 400 (the DefaultHandlerExceptionResolver table). Shelf chose 404 on purpose in L45 ("/books/abc names no book"). Both are defensible; with Spring, 400 is the default you'd have to override.
  • The 404 for an unknown path and the 405 for a wrong method are built in: the same table maps NoResourceFoundException to 404 and HttpRequestMethodNotSupportedException to 405.
  • When two templates match one path (L45's Exercise 1), Spring ranks them: "A pattern is more specific if it has a lower count of URI variables" (Mapping Requests, Pattern Comparison). Shelf took the first match.

How annotation dispatch really works: build MiniSpring

"Spring finds your @GetMapping methods" can sound like magic until you write the mechanism. It takes four reflection calls, all from L25: list a class's methods, read an annotation, read parameter annotations, and invoke. Before you look at my version, here is the behaviour to aim for. The controller has two routes, two error handlers and no routing code at all; the dispatcher prints one line per request:

GET /books/7 -> 200 {"id":7,"title":"Dune"}
GET /books/99 -> 404 {"title":"Not Found","detail":"No book 99"}   (handled NoSuchElementException via notFound)
GET /books/abc -> 400 cannot convert path variable: For input string: "abc"
POST /books/7 -> 405 allowed=[GET]
GET /boom -> 500 {"title":"Internal Server Error"}   (handled IllegalAccessError via jvmError)
GET /authors -> 404 no handler

Both languages print exactly those six lines. Read the fifth one closely. /boom throws IllegalAccessError, which is an Error, not an Exception: the same kind of failure that gave L45's client silence, because Shelf's router catches only Exception. MiniSpring wraps the Error in a HandlerDispatchException, then walks the cause chain until an @OnError method matches. That is exactly what Spring does. Here is the code from DispatcherServlet.doDispatch in the Spring Framework 7.0.10 source:

catch (Exception ex) {
    dispatchException = ex;
}
catch (Throwable err) {
    // As of 4.3, we're processing Errors thrown from handler methods as well,
    // making them available for @ExceptionHandler methods and other scenarios.
    dispatchException = new ServletException("Handler dispatch failed: " + err, err);
}

And the matching rule, from the Spring docs' Exceptions page: an exception "may match against a top-level exception being propagated … or against a nested cause within a wrapper exception", and "As of 5.3, this can match at arbitrary cause levels". (Spring 5 used a NestedServletException wrapper; it was deprecated in 6.0 "in favor of standard ServletException nesting" and no longer exists in 7.0.) If nothing matches, Spring Boot's /error mapping produces a JSON 500 (Servlet Web Applications · Error Handling). So the gap L45 found in Shelf (an Error killed the response) is one Spring closes for you.

One real compiler error I hit on the way, in case you meet it: building the argument list as listOf(if (isLong) raw.toLong() else raw) and spreading it with *args.toTypedArray() fails in Kotlin 2.4:

ArgsInfer.kt:5:35: error: type argument for reified type parameter 'T' was inferred to the intersection of ['Comparable<*>' & 'Serializable']. Reification of an intersection type results in the common supertype being used. This may lead to subtle issues and an explicit type argument is encouraged.

The two branches are a Long and a String, so Kotlin infers their common supertypes, Comparable<*> & Serializable, and refuses to make an array of that. Declaring val args: List<Any> fixes it (L13: reified type parameters need one concrete type).

Problem Details → ProblemDetail

In L45 you wrote RFC 9457 bodies yourself. Spring has a class for them and a property that turns them on for its own errors. From the Spring docs' Error Responses page: "In Spring Boot, the spring.mvc.problemdetails.enabled property autoconfigures a ResponseEntityExceptionHandler that handles built-in exceptions with problem details", and "You can return ProblemDetail or ErrorResponse from any @ExceptionHandler … The status property of ProblemDetail determines the HTTP status."

@RestControllerAdvice is the Spring name for Shelf's catch blocks in Router.handle: one place that turns exceptions into responses for every controller.

Composition root → the ApplicationContext

In Spring you don't write that class. You mark classes with @Service, @Repository or @RestController; component scanning finds them, and the container calls their constructors with the beans they ask for. The docs say plainly which style to prefer: "The Spring team generally advocates constructor injection, as it lets you implement application components as immutable objects and ensures that required dependencies are not null" (Dependency Injection). That is L38's advice, word for word. For classes you can't annotate, such as Shelf's own stores in the final exercise, you write @Bean methods in a @Configuration class. That is a composition root again, just one Spring calls for you.

What Kotlin does for you (and what it costs with Spring)
  • Kotlin annotation classes are kept at runtime by default (L25), so MiniSpring's annotations need no @Retention. Java's need @Retention(RUNTIME) or reflection never sees them.
  • Annotation arguments of class type are KClass (OnError(IllegalAccessError::class)); reflection hands you the Java class through .java.
  • A constructor parameter is a property and a dependency at once: class BookController(private val books: BookService) is constructor injection in one line. Java needs the field, the constructor and the assignment.
  • The cost: Kotlin classes are final by default, and Spring needs to subclass some of them to build proxies. Spring Boot's Kotlin docs: "Since Kotlin classes are final by default, you are likely to want to configure kotlin-spring plugin in order to automatically open Spring-annotated classes so that they can be proxied" (Kotlin Support). It's the same problem JMH had in L24. A project from start.spring.io adds kotlin("plugin.spring") for you.

MiniSpring's /boom handler throws IllegalAccessError. Which method handles it?

The dispatcher wraps the Error in an exception, then walks getCause(): the wrapper doesn't match any handler, its cause does. Spring's DispatcherServlet wraps in a ServletException for the same reason.

In Spring MVC, GET /books/abc reaches a method with @PathVariable id: Long. The default response is…

The conversion fails with a TypeMismatchException, which DefaultHandlerExceptionResolver maps to 400. Shelf's L45 router answered 404 on purpose; in Spring you'd override the default to keep that.

Porting Shelf to Spring Boot, which part can you keep unchanged?

Services depend only on store interfaces, and stores only on JDBC (L38). Spring replaces the HTTP layer and the wiring around them; the final exercise reuses them as they are.

Data, cross-cutting concerns, and what stays yours

Stores → JdbcClient

Shelf's stores bind parameters, run SQL and map rows by hand with L36's helpers. Spring's JdbcClient (in Spring Framework since 6.1) is the same idea with less code, and Spring Boot auto-configures one: "Spring's JdbcClient is auto-configured based on the presence of a NamedParameterJdbcTemplate" (SQL Databases). It maps rows to "a record class, a custom constructor, bean properties, or plain fields" by name (JDBC Core Classes).

The SQL is unchanged: your join, your alias, your indexes (L35). Spring Data goes one step further and writes simple queries from method names; you'll meet it in mission A, along with the N+1 problem it can hide (L36).

Transactions → @Transactional, which is a proxy

Here is Shelf's transaction helper, then the Spring version:

How can one annotation start and commit a transaction? Spring doesn't hand you your own object. It hands you a proxy that implements the same interface, or subclasses your class, and wraps every call (Proxying Mechanisms: "Spring AOP uses either JDK dynamic proxies or CGLIB to create the proxy for a given target object"). You can build the JDK version in about 50 lines with java.lang.reflect.Proxy. TxProxy prints BEGIN, COMMIT and ROLLBACK where a real one would call your Db, and it copies Spring's default rollback rule from the docs. The @Transactional here is TxProxy's own annotation, not Spring's:

  COMMIT
desk.lend(13)

  ROLLBACK
  -> caller sees IllegalStateException: book 13 is on loan
desk.lendBoth(2, 3)

    insert loan for book 3
desk.importLoan(4)
  BEGIN
    insert loan for book 4
  COMMIT (checked IOException)
  -> caller sees UndeclaredThrowableException: null

  BEGIN

  COMMIT
desk.lend(13)

  COMMIT (checked IOException)

Four calls, three lessons about Spring:

  • lend(1) and lend(13): commit on success, roll back on a RuntimeException. This is your Db.transaction, moved into a proxy.
  • lendBoth(2, 3) got no transaction at all, although it calls the annotated lend twice. Inside lendBoth, lend(a) means this.lend(a), and this is the real object, not the proxy. Spring has exactly this trap. From Using @Transactional: "In proxy mode (which is the default), only external method calls coming in through the proxy are intercepted. This means that self-invocation (in effect, a method within the target object calling another method of the target object) does not lead to an actual transaction at runtime even if the invoked method is marked with @Transactional."
  • importLoan(4) committed, although it threw. Spring's default, from Rolling Back a Declarative Transaction: it rolls back "only in the case of runtime, unchecked exceptions. That is, when the thrown exception is an instance or subclass of RuntimeException. (Error instances also, by default, result in a rollback.)" And: "Checked exceptions that are thrown from a transactional method do not result in a rollback in the default configuration." Compare Shelf's Kotlin Db.transaction, which rolls back on any Throwable (warm-up question 4).

The last line differs between the languages, and it's a real Kotlin trap. In Java the caller sees the IOException. In Kotlin the caller sees UndeclaredThrowableException, because Kotlin doesn't declare checked exceptions (L10) and a JDK proxy may only rethrow what the interface method declares. The rule, from the InvocationHandler docs: "If a checked exception is thrown by this method that is not assignable to any of the exception types declared in the throws clause of the interface method, then an UndeclaredThrowableException containing the exception that was thrown by this method will be thrown by the method invocation on the proxy instance." The fix is L9's @Throws on the interface method:

$ diff TxProxy.kt TxProxyThrows.kt
9a10
>     @Throws(IOException::class)
$ kotlinc TxProxyThrows.kt -include-runtime -d t.jar && java -jar t.jar | tail -5

  BEGIN
    insert loan for book 4
  COMMIT (checked IOException)
  -> caller sees IOException: import file truncated

What Kotlin does for you (with proxies)
  • No checked exceptions means no throws clauses, so a JDK proxy over a Kotlin interface wraps a checked exception in UndeclaredThrowableException. Add @Throws where Java callers or proxies need the declaration (L9).
  • The project start.spring.io generates for Kotlin adds the compiler flag -Xannotation-default-target=param-property, the setting Spring Boot's Kotlin docs recommend, so an annotation on a constructor property lands where Spring looks for it (L25's use-site targets).
  • generateSequence(failure) { it.cause } turns the cause-chain walk into a lazy sequence (L15). Java writes the loop.

In TxProxy, the unannotated lendBoth(2, 3) calls the annotated lend twice. How many transactions open?

The calls go to this, the real object, so the proxy never sees them. Spring's docs: self-invocation "does not lead to an actual transaction at runtime even if the invoked method is marked with @Transactional".

A Spring @Transactional method throws a checked IOException. By default, Spring…

"Checked exceptions that are thrown from a transactional method do not result in a rollback in the default configuration." Rollback rules (rollbackFor) change it.

Which of these does Spring Boot leave entirely to you?

JSON, wiring and Problem Details are all automated. Which columns to index depends on your queries and data (L35); no framework can choose for you.

Through a JDK proxy, Kotlin's importLoan threw an undeclared IOException. The caller saw…

Final exam: retrieval practice across the whole course

Fifteen questions, deliberately mixed. Answer each from memory before you click. Each one names the lesson to revisit if you miss it.

In Java, Integer a = 1000, b = 1000; System.out.println(a == b); (L5)

== compares references, and the Integer cache only covers −128 to 127 (Integer.valueOf docs). Two boxes of 1000 are different objects; use equals.

Appending to the end of an ArrayList costs, amortised… (L16)

Most appends write into spare capacity; the occasional copy when the array grows is spread over all the appends that came before it.

A class overrides equals but not hashCode. You add an object to a HashSet, then ask contains with an equal copy. It usually… (L19)

The copy has a different identity hash, so the set looks in the wrong bucket and never calls equals. Equal objects must have equal hash codes (Object.hashCode contract, L7).

Two threads each run count++ a million times on a plain shared field. The final value is… (L26)

count++ is read, add, write. Two threads can read the same value and both write it back plus one, losing an update. Some runs may still land on 2,000,000; that proves nothing.

A worker loops while (!stop) on a plain field that the main thread sets to true. On HotSpot, the worker can… (L27)

With no happens-before edge, the JIT may hoist the read out of the loop; in L27 it hung on every run. volatile (or @Volatile) fixes it.

A composite index on loans(member_id, loaned) can serve which WHERE clause on its own? (L35)

A B-tree index is sorted by its leftmost column first, so it helps member_id = ? but not loaned alone. A function on a column, or a leading %, defeats an index.

With autocommit on, your code runs two UPDATEs and crashes between them. Afterwards… (L36)

Autocommit makes every statement its own transaction, so the first one is already committed. That's L36's half-finished transfer; Shelf's Db.transaction and Spring's @Transactional both exist to prevent it.

Which response header lets a client revalidate cheaply and get 304 Not Modified? (L31)

The client sends the tag back in If-None-Match; if it still matches, the server answers 304 with no body (RFC 9110, RFC 9111).

How should Shelf store a member's password? (L33)

A per-user salt defeats precomputed tables, and a deliberately slow, adaptive hash makes each guess expensive (OWASP Password Storage Cheat Sheet). Base64 is not even encryption.

Five hundred requests miss the same expired cache key at the same moment. The standard fix is… (L41)

One request loads the value and the others wait for its result; L41 took 50 database hits down to 1. Spring's @Cacheable(sync = true) is the same idea.

Going from four nodes to five with consistent hashing, roughly how many keys move? (L42)

Only the keys the new node takes over move: about 1/N. Plain hash mod N moved 80% of them in L42.

A circuit breaker's open timeout has passed, and it lets a single trial call through. Its state is… (L43)

From HALF_OPEN, a successful trial closes the breaker and a failure opens it again (Fowler's CircuitBreaker, L43).

A public Kotlin function with a non-null String parameter compiles to bytecode that… (L23)

kotlinc inserts Intrinsics.checkNotNullParameter, so a Java caller passing null fails at the boundary instead of deep inside your code. You saw it in javap in L23.

Which is the classic memory leak in a garbage-collected language? (L24)

Anything reachable from a static field is reachable from a GC root, so it is never collected. L24 took one to OutOfMemoryError and found it with a heap histogram.

A Java method takes List<? extends Number>. Inside it, you can… (L13)

"Producer extends": every element is some kind of Number, so reading is safe, but the compiler can't know which subtype the list holds, so adding is refused. Kotlin writes it List<out Number>.

Exit quiz, recall card, sources

~5 min

A Java annotation declared without @Retention is, at runtime… (L25)

The default is RetentionPolicy.CLASS: recorded in the class file but not available through reflection. That's why MiniSpring's Java annotations say @Retention(RUNTIME).

Why does the Spring team advocate constructor injection? (L38)

The docs: it "lets you implement application components as immutable objects and ensures that required dependencies are not null". L38 gave the same reasons for injecting by hand.

In Spring Boot 4.1, spring.threads.virtual.enabled is… (L28)

The docs say "To enable virtual threads, set the spring.threads.virtual.enabled property to true", and warn about pinned virtual threads (L28).

Shelf v1's Kotlin router catches Exception. Spring's DispatcherServlet also catches… (L45)

Since Spring 4.3 it catches Throwable and wraps an Error in a ServletException, "making them available for @ExceptionHandler methods" (the comment in its source).
