The Memory Model & Deadlock

L26 fixed lost updates. This lesson covers the two other ways shared state goes wrong: a thread that never sees another thread's write, and threads that wait for each other for ever. Then it covers the tools that avoid both: volatile, lock ordering, concurrent collections and immutable values.

Part 1

Visibility, volatile, happens-before

~30 min

L26 was about atomicity: two threads interleaving the steps of one update. This part is about visibility, a separate problem that surprises nearly everyone. Without synchronization, there is no guarantee that a thread ever sees a value another thread wrote, however long you wait. The program below has no count++ and only one writer. A worker spins until main sets a flag.

The worker is a daemon thread, so a stuck worker can't stop the JVM from exiting, and join(3000) gives up after three seconds. Never write a concurrency demo that can hang. Here are every run I did, each identical:

$ java StopFlag               # Java, 5 runs: all 5 printed this
main set stop = true
still running after 3 s: the worker never saw the write
$ java -jar StopFlag.jar      # Kotlin, 3 runs: all 3 printed this
main set stop = true
still running after 3 s: the worker never saw the write

main wrote true, and three seconds later the worker was still looping. Now switch off the JIT compiler with -Xint (interpreter only, L23) and run the same class:

$ java -Xint StopFlag
main set stop = true
worker saw stop after 381262217 spins

What happened. After a second of spinning, the loop is hot, and the JIT compiles it (L23). Nothing in the loop tells the compiler that another thread might change stop, so it's allowed to read the field once and keep using that value. In effect it turns while (!stop) spins++ into if (!stop) while (true) spins++. The interpreter happens to re-read memory every time, so the bug "disappears" under -Xint. That is the worst kind of bug: it depends on the JIT, the machine and the timing.

The hardware is allowed to do similar things. Cores keep values in private caches and buffer their writes (L22), and Apple's documentation says it directly: "A weak memory ordering model, like the one in Apple silicon, gives the processor more flexibility to reorder memory instructions and improve performance, but doesn't add implicit memory barriers" (Apple: Addressing architectural differences). The Java Memory Model exists so that you don't have to reason about any of this. You reason about one rule instead.

The fix: one keyword

main set stop = true
worker saw stop after 4111260979 spins

Every run stopped, in both languages. The two lines can print in either order, since the worker may report first. Kotlin has no volatile keyword. The @Volatile annotation "marks the backing field of the annotated var property as volatile, meaning that reads and writes to this field are atomic and writes are always made visible to other threads" (Kotlin API: Volatile). javap -v on the compiled Kotlin shows the same flag Java sets: flags: (0x004a) ACC_PRIVATE, ACC_STATIC, ACC_VOLATILE.

The rule: happens-before

The Java Language Specification defines when one thread's write is guaranteed to be visible to another thread's read. It calls the relation happens-before. The java.util.concurrent docs put it in one sentence: "The results of a write by one thread are guaranteed to be visible to a read by another thread only if the write operation happens-before the read operation" (Memory Consistency Properties). The JLS lists the basic edges (JLS §17.4.5):

  • Program order: "If x and y are actions of the same thread and x comes before y in program order, then hb(x, y)."
  • Locks: "An unlock on a monitor happens-before every subsequent lock on that monitor."
  • Volatile: "A write to a volatile field happens-before every subsequent read of that field."
  • Starting: "A call to start() on a thread happens-before any actions in the started thread."
  • Joining: "All actions in a thread happen-before any other thread successfully returns from a join() on that thread."
  • Transitivity: "If hb(x, y) and hb(y, z), then hb(x, z)."

Transitivity is the useful part. Everything a thread did before a volatile write, or before releasing a lock, becomes visible to the thread that later reads that variable or takes that lock. That's why volatile works as a "ready" flag that publishes other, non-volatile data written before it. And it's why L26's join() calls were enough to read the final count safely. java.util.concurrent adds more edges: "Actions in a thread prior to placing an object into any concurrent collection happen-before actions subsequent to the access or removal of that element from the collection in another thread", and similar rules for executors, futures and locks. Part 3 relies on these.

The JLS names the bug: "When a program contains two conflicting accesses that are not ordered by a happens-before relationship, it is said to contain a data race." StopFlag has a data race on stop, so the JVM never promised the worker would see the write.

volatile is not a lock

volatile gives visibility and ordering. It does not make a read-modify-write atomic. The package docs warn that volatile reads and writes "do not entail mutual exclusion locking". Four threads, one million count++ each, on a volatile field:

About three quarters of the increments are lost. Every thread sees the latest value, but two threads still read it, add one, and write the same number back. For counters, use L26's tools (AtomicInteger, LongAdder, a lock). Use volatile for a value that one thread writes and others read: a stop flag, a "ready" flag, a reference to a fresh immutable config.

Safe publication and final fields

Handing an object to another thread is called publishing it. Publish through a field with no happens-before edge and the reader may see the reference before it sees the fields the constructor wrote (Java Concurrency in Practice §3.5, "Safe publication"). There is one big exception. "A thread that can only see a reference to an object after that object has been completely initialized is guaranteed to see the correctly initialized values for that object's final fields" (JLS §17.5). An object whose fields are all final, and which doesn't leak this from its constructor, is safe however it's shared. That's the foundation of Part 3's best defence. Kotlin's val compiles to exactly such a field: javap shows private final java.util.List<java.lang.String> hosts;.

Lazy initialisation: double-checked locking

"Create it on first use" looks simple until eight threads ask at once. This program races four strategies. The 20 ms sleep inside the constructor deliberately widens the window so the race shows up every time. That's a standard trick for making a timing bug reproducible.

  • Racy check-then-act built eight "singletons", and each caller got its own.
  • Double-checked locking (DCL) skips the lock once the field is set. It is correct only because the field is volatile. Without it, "the writes that initialize the Helper object and the write to the helper field can be done or perceived out of order", so another thread can see a non-null reference to a half-built object. Under the Java 5 memory model, "the Double-Checked Locking idiom can be made to work by declaring the helper field to be volatile" (The "Double-Checked Locking is Broken" Declaration, signed by Bloch, Lea and others; JCiP §16.2). The broken version usually works in testing, which is exactly why it was so widespread.
  • The holder class is simpler. The JVM initialises Holder exactly once, on first use, under its own lock (L23's class initialisation). No volatile, no synchronized.
  • by lazy is DCL written for you. In the Kotlin standard library's source, SynchronizedLazyImpl has a @Volatile private var _value that it reads once without a lock and again inside synchronized(lock), the exact shape of the Java version (LazyJVM.kt; an implementation detail, not a guarantee).
  • lazy(PUBLICATION) ran the initializer eight times but handed everyone the same instance. That matches its documentation: the "initializer function can be called several times on concurrent access", "but only one computed value will be used" (LazyThreadSafetyMode). Use it when the initializer is cheap and has no side effects.
  • object: "The initialization of an object declaration is thread-safe and done on first access" (Kotlin docs). Under the hood it's the holder-class idiom: a static INSTANCE set in the class initializer.
What Kotlin does for you.
  • by lazy { } writes correct double-checked locking for you, volatile field included. In Java you type every line yourself and must remember the keyword.
  • object gives you a lazily created, thread-safe singleton in one word. Java needs the holder class or an enum.
  • val compiles to a final field, so a class of vals gets the JLS §17.5 publication guarantee automatically.
  • What Kotlin doesn't do: there's no volatile keyword, so you write @Volatile. And a plain var shared between threads has exactly the same visibility bug as Java.

Part 2

Deadlock: cause one, then prevent it

~30 min

Locks fix races. Take more than one lock, and you can build a program that stops for ever. Two transfers run at the same time, alice→bob and bob→alice. Each locks its "from" account, pauses, then locks its "to" account. The 50 ms pause again widens the window so the bug shows up every run.

Each thread holds one lock and waits for the other's. Neither can continue, so neither will ever let go. Nothing crashes and nothing is logged: the threads just stop. The program above ends cleanly only because of the watchdog. After two seconds, ThreadMXBean.findDeadlockedThreads() asks the JVM to look for cycles of threads waiting on each other's locks. The @4f023edb part is the lock object's identity hash. Step through how the cycle forms, then switch tabs to see why ordering prevents it:

The four conditions

OSTEP lists the four conditions that must all hold for a deadlock (OSTEP ch. 32, "Common Concurrency Problems"):

  • Mutual exclusion: "Threads claim exclusive control of resources that they require (e.g., a thread grabs a lock)."
  • Hold-and-wait: "Threads hold resources allocated to them (e.g., locks that they have already acquired) while waiting for additional resources."
  • No preemption: "Resources (e.g., locks) cannot be forcibly removed from threads that are holding them."
  • Circular wait: "There exists a circular chain of threads such that each thread holds one or more resources (e.g., locks) that are being requested by the next thread in the chain."

"If any of these four conditions are not met, deadlock cannot occur." Every prevention technique breaks one of them.

Fix 1: a global lock order (breaks circular wait)

"The most straightforward way to do that is to provide a total ordering on lock acquisition" (OSTEP). Accounts have ids, so always lock the lower id first, whichever direction the money moves (JCiP §10.1 calls the original bug a dynamic lock-order deadlock, because the order depends on the arguments).

2,000,000 opposite transfers in 30 ms
alice=1000000 bob=1000000 total=2000000

Two million transfers in opposite directions, no deadlock, and the money adds up. Both languages printed these lines. Java's first run also took 30 ms, its second 52 ms. When objects have no natural id, JCiP §10.1 suggests ordering by System.identityHashCode, with a tie-breaking lock for the rare equal hashes.

Fix 2: give up and retry (breaks hold-and-wait)

ReentrantLock.tryLock(timeout) waits only a limited time. If the second lock doesn't come, release the first one too, back off for a random moment, and start again:

total=2000 after 20,000 transfers, 18 retries      # Kotlin
total=2000 after 20,000 transfers, 25 retries      # Java, run 1
total=2000 after 20,000 transfers, 21 retries      # Java, run 2

A handful of attempts failed, let go and retried, and every transfer completed. The random back-off matters. Without it, two threads can fail, retry and collide again in lock-step for ever. OSTEP calls that livelock: "both systems are running through this code sequence over and over again (and thus it is not a deadlock), but progress is not being made". Its suggested fix is the one used above: "add a random delay before looping back". tryLock is more code than ordering, so prefer ordering when you can define one.

Fix 3: fewer locks

One lock can't form a cycle. A single lock around the whole bank is deadlock-free by construction. The cost is that unrelated transfers now wait for each other. The final exercise measures whether that cost matters here. Lock-free designs (L26's atomics) go further and hold no lock at all.

Two more liveness failures

  • Livelock: threads keep running and keep retrying, but none makes progress. You met it above.
  • Starvation: one thread rarely or never gets the lock (or the CPU) because others keep winning. L26's ReentrantLock(true) fairness option trades throughput to prevent this. JCiP §10.3 covers both.
What Kotlin does for you.
  • synchronized(lock) { … } is a standard-library inline function, not a keyword. It compiles to the same monitorenter/monitorexit pair as Java's block (L23), so the thread dump looks identical.
  • thread(isDaemon = true, name = "t1 alice->bob") { } creates, names, configures and starts a thread in one call. Java needs new Thread(…, name), setDaemon(true) and start().
  • lock.withLock { } wraps lock() … finally { unlock() } for you (used in the final). tryLock still needs the explicit try/finally in both languages.
  • Destructuring val (first, second) = if (…) from to to else to to from makes the ordering rule a single readable line.
Exercise: dining philosophers

Five philosophers sit at a round table with one fork between each pair. To eat, philosopher i needs fork i (left) and fork (i + 1) % 5 (right). From a blank file, start five threads that each eat 100,000 meals by taking left then right with synchronized. Add a two-second watchdog using findDeadlockedThreads(). Run it a few times. Then add an ordered mode that fixes it with the lock-ordering rule, without changing who needs which forks.

Reference solutions and real output 
$ java Philosophers            # 3 runs per language: all 6 deadlocked
DEADLOCK: 5 philosophers each hold one fork
$ java Philosophers ordered    # both languages
everyone ate 100000 meals

Everyone grabs their left fork, so all five are held and every philosopher waits for a right fork that their neighbour holds: a five-thread cycle. With ordering, philosophers 0–3 still take left then right, but philosopher 4 needs forks 4 and 0 and now takes fork 0 first. That one change means the arrows can no longer close into a loop.

Part 3

Thread-safe collections and immutability as a defence

~25 min

You rarely write synchronized around your own fields in real code. You reach for a collection that's already thread-safe, or you share data that can't change. Both have traps. "Thread-safe" describes each method, not the sequence of calls you make.

Synchronized wrappers: each call is atomic, your sequence isn't

Collections.synchronizedList wraps every method in a lock (JCiP §5.1). Eight threads each try to add 0…9,999 "if absent":

no client lock:   size 10143 (expected 10000)     # Kotlin
with client lock: size 10000 (expected 10000)
no client lock:   size 10225 (expected 10000)     # Java, 3 runs: 10225, 11031, 10250
with client lock: size 10000 (expected 10000)

contains is atomic and add is atomic, but two threads can both find "absent" before either adds: L26's check-then-act, again. The fix is client-side locking: hold the wrapper's own lock (the list object) around the whole sequence. The same applies to iteration, and the API docs say so in bold: "It is imperative that the user manually synchronize on the returned list when traversing it via Iterator, Spliterator or Stream … Failure to follow this advice may result in non-deterministic behavior" (Collections.synchronizedList).

ConcurrentHashMap: use the atomic methods

Four threads count the same words into one ConcurrentHashMap, first with "get, add one, put", then with merge:

get + put: {cat=940077, end=960540, mat=979162, on=994027, sat=925004, the=1290824}     # Kotlin
merge:     {cat=1000000, end=1000000, mat=1000000, on=1000000, sat=1000000, the=3000000}
get + put: {cat=958101, end=973288, mat=974895, on=988549, sat=958071, the=1549119}     # Java
merge:     {cat=1000000, end=1000000, mat=1000000, on=1000000, sat=1000000, the=3000000}

The map never corrupted itself and never threw: it's genuinely thread-safe. The program still lost more than half of the "the" counts, because get then put is two operations. merge is one: "The entire method invocation is performed atomically" (ConcurrentHashMap.merge). So are compute, computeIfAbsent and putIfAbsent. For hot counters, the class docs suggest LongAdder values: "freqs.computeIfAbsent(key, k -> new LongAdder()).increment();". Keep the function you pass short, because "some attempted update operations on this map by other threads may be blocked while computation is in progress".

A Kotlin trap: getOrPut on a concurrent map

Kotlin's getOrPut reads naturally, so it's tempting on a ConcurrentHashMap. Here eight threads ask for the same missing key at once:

getOrPut never overwrote an entry, and everyone got the same connection, but it opened eight and threw seven away. That's documented behaviour: on a ConcurrentMap it "guarantees not to put the value into the map if the key is already there, but the defaultValue function may be invoked even if the key is already in the map" (Kotlin API: getOrPut). The Java column shows the equivalent hand-written logic. computeIfAbsent invokes the function "exactly once per invocation of this method if the key is absent, else not at all", and other callers wait. Use computeIfAbsent when building the value is expensive or has side effects. (L21 showed the other edge: never modify the map from inside that function.)

Iterating while someone modifies

Concurrent collections use weakly consistent iterators: "they will never throw ConcurrentModificationException" and "are guaranteed to traverse elements as they existed upon construction exactly once, and may (but are not guaranteed to) reflect any modifications subsequent to construction" (package docs). For listener lists, which are read constantly and changed rarely, the classic choice is CopyOnWriteArrayList. Every write copies the array, and its "snapshot" iterator "is guaranteed not to throw ConcurrentModificationException" (CopyOnWriteArrayList). Here a one-shot listener unregisters itself in the middle of notification, which happens all the time in event buses (L24's listener leak was the opposite mistake):

CopyOnWriteArrayList:
  one-shot got saved, unregistering
  logger got saved
  listeners left: 1
ArrayList:
  one-shot got saved, unregistering
  listeners left: 1

Both languages printed exactly this. I expected the ArrayList to throw, and it didn't. It silently skipped the logger. Removing element 0 shrank the list to one element while the iterator's cursor was already at 1, so hasNext() said "done". Add a third listener (Listeners3.java) and the same code throws instead:

Exception in thread "main" java.util.ConcurrentModificationException
	at java.base/java.util.ArrayList$Itr.checkForComodification(ArrayList.java:1104)
	at java.base/java.util.ArrayList$Itr.next(ArrayList.java:1058)
	at Listeners3.fire(Listeners3.java:18)

The ArrayList docs warn about this: "Fail-fast iterators throw ConcurrentModificationException on a best-effort basis. Therefore, it would be wrong to write a program that depended on this exception for its correctness" (ArrayList). No exception doesn't mean no bug.

Handing work between threads: BlockingQueue

The producer-consumer pattern lets threads communicate without sharing mutable objects: one side puts jobs into a queue, the other takes them out (JCiP §5.3). An ArrayBlockingQueue is bounded. put blocks when it's full, which slows a fast producer down automatically, and take blocks when it's empty. To shut down, the producer sends a poison pill, a special value meaning "no more work", one per consumer:

consumer-1 took 960 jobs        # Kotlin
consumer-2 took 40 jobs
total 500500 (expected 500500)
consumer-2 took 463 jobs        # Java, run 1
consumer-1 took 537 jobs
total 500500 (expected 500500)
consumer-2 took 134 jobs        # Java, run 2
consumer-1 took 866 jobs
total 500500 (expected 500500)

The split between consumers is different every run, and that's fine. The total is always exact, and no job is processed twice. The happens-before rule for concurrent collections means each consumer sees a job exactly as the producer built it, with no extra locking.

The best defence: immutability

Every bug in this lesson and in L26 needs shared, mutable state. Remove either word and the bug can't exist. JCiP §3.4 makes immutable objects its strongest recommendation: an object whose state can't change after construction is thread-safe with no locking at all, and §17.5's final-field guarantee means it's even safe to publish carelessly. But "immutable" has to go all the way down (L5):

The first config's hosts is a val / record component, yet it changed, because it's a read-only view of a list someone else can still mutate (L5). If another thread were iterating it, you'd have a data race inside a "constant". The fix is a private copy at construction: List.copyOf in a Java compact constructor, which is also unmodifiable, or toList() in Kotlin, whose result is typed as read-only. Persistent collection libraries go further, but a copy is usually enough.

Thread confinement is the other way out: don't share at all. A local variable used by one thread needs no locking (L4: every thread has its own stack). ThreadLocal gives each thread its own copy of a field, but in thread pools the values outlive the task, which is L24's leak again (JCiP §3.3).

Bridge. Spring creates most beans once and shares them across every request thread. Its docs say: "Only one shared instance of a singleton bean is managed", and "as a rule, you should use the prototype scope for all stateful beans and the singleton scope for stateless beans" (Spring: Bean Scopes). A mutable field in a singleton service is this lesson's bug, running on hundreds of threads. On Android, UI state usually lives in a StateFlow holding an immutable data class, and MutableStateFlow.update { it.copy(…) } "updates the MutableStateFlow.value atomically" (kotlinx.coroutines API). It swaps one immutable value for another, never mutating in place. You'll use flows in L29.
What Kotlin does for you.
  • data class with val properties gives you final fields, equals/hashCode and copy(), the raw material for immutable values. Java records do the same.
  • Kotlin's List type has no add, so safe.hosts.add(…) doesn't even compile. Java's List has add, so Java needs List.copyOf to make the call fail at runtime.
  • But a Kotlin List is only a read-only view. The compiler won't stop someone holding the MutableList. Copy at the boundary.
  • Kotlin uses Java's concurrent collections directly. The Kotlin-specific risk is getOrPut, which looks atomic and isn't. Prefer computeIfAbsent/merge on shared maps.

Check

Eight threads run if (!list.contains(x)) list.add(x) on a Collections.synchronizedList. Can duplicates appear?

Each call is atomic on its own, but another thread can add between contains and add. Hold the list's lock around both.

Which line counts a word atomically in a shared ConcurrentHashMap<String, Int> named m?

merge is one atomic read-modify-write. The others read and then write in two separate calls.

Eight threads call chm.getOrPut("db") { open() } on a missing key at once. open() runs…

The real run opened 8. Only one value is kept, but "the defaultValue function may be invoked even if the key is already in the map". computeIfAbsent runs it once.

A listener removes itself while a plain two-element ArrayList of listeners is being iterated. What happened in my run?

The iterator's cursor passed the new size, so the loop ended early without throwing. Fail-fast is "best-effort", so silence isn't proof of correctness.

Why can an immutable object be shared between threads without any locking?

Races need a write. With no writes after construction, and final fields guaranteeing the constructor's values are visible, there's nothing to race on.

Reference solutions and real output

v1 deadlocked on every one of my runs, in both languages, after anywhere from 140 to 1,577 transfers. The frozen monitor count is a symptom worth recognising: a program that's still running but has stopped making progress. Look at the first Java run. The cycle is worker-1 ↔ worker-2, and worker-0 is reported too, because it's stuck waiting for a lock that worker-1 holds. A deadlock can freeze threads that aren't part of the cycle.

v2 and v3 always finished with the total at exactly 10,000. The first Java runs took 16 ms (v2) and 18 ms (v3), and repeats took 21–23 ms and 21–22 ms. The single global lock is just as fast here, because each transfer holds a lock for a few nanoseconds and there are only 4 threads. Fine-grained locking pays off when the work inside the lock is long or the thread count is high. Measure before you take on the extra deadlock risk.

Why only the flag needs volatile: the balances are only ever read and written while holding locks, and unlock→lock gives the happens-before edge. The running flag is read by the monitor without any lock, exactly like StopFlag, so it needs volatile to be guaranteed to see running = false. The final balances are read after join returns, which is its own happens-before edge. In the deadlock case the reader never gets that far.

Wrap-up

Exit quiz, recall card, sources

~5 min

L10 + L27: why does every lock() call get its unlock() in a finally block?

If the guarded code throws, a lock with no finally stays held for ever. Every later caller blocks, which looks just like a deadlock. synchronized and withLock release automatically.

L19 + L27: a key's hashCode changes after it's put in a ConcurrentHashMap. Does the map's thread safety help?

Thread safety protects the map's own structure, not your keys' contract. A mutated key sits in the wrong bucket in any hash map. Immutable keys avoid it.

L23 + L27: in bytecode, a synchronized (lock) { … } block or Kotlin's synchronized(lock) { } compiles to…

Both take the object's monitor, which is why jcmd Thread.print shows "waiting to lock monitor" for either language.

L24 + L27: a static ConcurrentHashMap cache is perfectly thread-safe but only ever grows. The remaining problem?

Thread safety isn't boundedness. A static root holding ever more entries is L24's leak. Bound it, for example with an LRU.
