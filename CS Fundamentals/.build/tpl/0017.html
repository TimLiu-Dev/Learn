Part 1

Singly linked lists

~30 min

An array list keeps its elements side by side in one block of memory, which is why get(i) is instant and inserting at the front means shifting everything. A linked list makes the opposite trade. Each element lives in its own little object, a node, and each node holds a reference to the next one. Sedgewick & Wayne define it recursively: "a linked list is a recursive data structure that is either empty (null) or a reference to a node having a generic item and a reference to a linked list" (Algorithms §1.3).

Why is the Java node static? A nested class declared without static is an inner class: every instance carries a hidden reference to an instance of the outer class (JLS §8.1.3). A node doesn't need its outer object, so that hidden field would just waste memory in every node and could keep the outer object alive longer than it should be. Effective Java Item 24: favour static member classes over non-static ones. Kotlin flips the default. A nested class is "static" unless you write inner, and "inner classes carry a reference to an object of an outer class" (Kotlin docs: Nested and inner classes).

What each operation costs

A singly linked list can only be walked forwards, from head. Everything follows from that:

OperationCostWhy
addFirst(x)O(1)new node points at the old head; move head
removeFirst()O(1)head = head.next
get(i)O(n)walk i steps from the head: there's no address arithmetic
contains(x)O(n)check nodes one by one
addLast(x), head onlyO(n)walk to the last node first
addLast(x), with a tail fieldO(1)jump straight to the last node
remove a node you holdO(n)you need the node before it, and only forward links exist

A tail reference makes addLast constant time, at the price of one more field to keep correct. Removing the last node is still O(n), because to update tail you need the node before it. Part 2 fixes that with backward links.

Reversing in place: three pointers

The classic interview problem: reverse a list without creating new nodes. You walk the list once, flipping each arrow to point backwards. The trick is keeping three references: prev (the reversed part so far), curr (the node being flipped) and next (the rest, saved before you destroy the only link to it).

Two bugs everyone writes once

Pointer code fails quietly: no exception, just a list that's suddenly shorter, or endless. Here are both classics, deliberately broken:

fixed: A -> X -> B -> C
buggy: A -> X -> X -> X -> X -> X -> ...
size=1 contents=[]
  • Overwriting a link too early. insertAfterBuggy replaced node.next before reading it, so B and C became unreachable, and fresh.next = node.next made X point at itself: a cycle. A plain while (cur != null) loop would never end, which is why show stops after 6. The rule: read the old link before you overwrite it. The fixed version does both in one expression: Node(value, node.next) reads node.next first.
  • A stale tail. Removing the only element left head == null but tail still pointing at the removed node. The next addLast hung B off that dead node, so size says 1 and the list is empty. Every method that can empty the list must clear tail. The final's tests check exactly this.

Kotlin's smart cast stops at mutable properties

Inside a list class, head is a var property, and that changes how null checks work:

err/SmartCast.kt:7:34: error: smart cast to 'Node<T (of class MyList<T>)>' is impossible, because 'head' is a mutable property that could be mutated concurrently.
        if (head != null) return head.value     // head is a var PROPERTY
                                 ^^^^

With a local variable, Kotlin remembers your null check and treats it as non-null afterwards: a smart cast. For a var property the docs say smart casts work "never, because the variable can be modified at any time by other code" (Kotlin docs: Smart cast prerequisites). Another thread, or a method you call, could set head to null between the check and the use. The fix is to read the property once, into a val or through ?.:

null
A A

That's why you'll see val h = head ?: throw … and val t = tail all through linked-list code in Kotlin. Java compiles if (head != null) return head.value; without complaint, and has exactly the same race; it just doesn't tell you.

What Kotlin does for you.
  • Nested classes are static by default, so a Node never drags a hidden outer reference along. Java needs the static keyword, and forgetting it is a silent memory cost.
  • Node<T>? spells out in the type that next may be null, and the compiler makes you handle it. In Java every reference may be null and only a NullPointerException tells you that you forgot.
  • The smart-cast error flags a real hazard: re-reading a mutable property after a null check. Java accepts the same code silently.
  • class Node<T>(val value: T, var next: Node<T>?) is the whole class: constructor, fields and accessors in one line, where Java needs four.

Reference solutions

removeValue walks with two references, prev and cur, so that when cur matches it can do prev.next = cur.next. Java uses Objects.equals because cur.value might be null; Kotlin's == is already null-safe. Objects.checkIndex is the JDK's ready-made bounds check (JDK docs).

Check

A singly linked list with only a head field holds n nodes. What does addLast cost?

Without a tail field you must walk all n nodes to find the last one. Keeping a tail reference makes it O(1).

In the three-pointer reversal, why must next = curr.next come before curr.next = prev?

curr.next is the only reference to the rest of the list. Overwrite it first and nodes 2…n are lost, the same bug as insertAfterBuggy.

Java: why declare the node as static class Node<T> inside the list?

A non-static (inner) class gets a hidden field pointing at the enclosing instance (JLS §8.1.3). A node doesn't need it (Effective Java Item 24). Kotlin's nested classes are static unless marked inner.

Kotlin, inside a class: var head: Node? = null, then if (head != null) return head.value

Smart casts never apply to var properties, which "can be modified at any time by other code". Copy into a local val, or use head?.value.

After head.next = head.next.next removes node B, what happens to B?

Nothing references B any more, so it's unreachable, and unreachable objects are what the garbage collector frees (L4; L24 goes deeper).

Part 2

Doubly linked lists and java.util.LinkedList

~20 min

Give each node a prev reference as well as next, and the list can be walked both ways. More importantly, a node now knows its own neighbours, so removing a node you already hold is O(1): no walking to find the one before it. The second trick is sentinel (dummy) nodes. A permanent empty node sits before the first element and another after the last, so every real node always has a prev and a next. No special cases for an empty list, the first node or the last node.

A B C D | backwards [D, C, B, A]
removed C, now [A, B, D] size=3
joined: A-B-D
A B C D | backwards [D, C, B, A]
removed C, now [A, B, D] size=3
  • One insertion routine. addFirst is "link before the first real node" and addLast is "link before the tail sentinel". Thanks to the sentinels, linkBefore never meets a null.
  • Order of updates. Wire the new node's own prev/next first, then point the neighbours at it. That's the "read before you overwrite" rule from Part 1 again.
  • Iterable. Implementing iterator() is what makes for (s in list) work. In Kotlin, for works with anything that has an iterator() function returning something with next() and hasNext(), and "the easiest way to create your own iterator for a class is to inherit from the Iterable<T> interface" (Kotlin docs: for loops). Java's enhanced for requires an array or "a subtype of the raw type Iterable" (JLS §14.14.2).
  • The Kotlin bonus. Once your class is an Iterable, the whole standard library works on it: toList(), joinToString, map, filter (L14). Java's Iterable gives you forEach and nothing more, which is why the Java version collects into a list by hand.

So should you use java.util.LinkedList?

The JDK class is exactly what you just built: a "doubly-linked list implementation of the List and Deque interfaces", where "operations that index into the list will traverse the list from the beginning or the end, whichever is closer" (JDK docs: LinkedList). Its source has the same Node class with item, next and prev fields (OpenJDK source; an implementation detail, not a guarantee). These are real numbers from my machine (an Apple M5 Max, JDK 26); yours will differ, so run it yourself. Read them for shape, not precision. This is a crude best-of-N timing with a JIT warm-up, and JMH, the proper benchmarking tool, comes with profiling in L24 (OpenJDK: JMH). Two lessons stand out anyway:

  • Indexing a linked list in a loop is quadratic. Each get(i) walks up to n/2 nodes, and a loop does it n times. Doubling n roughly quadruples the time (×4.1, ×4.1, ×4.2): that's O(n²) showing itself, exactly the L16 doubling test. The ArrayList column is too small to measure meaningfully; it even shrinks as the JIT finishes compiling. A for-each loop uses the iterator and avoids this, but code that writes for (i in list.indices) list[i] is common, and on a LinkedList it's a performance bug.
  • Even plain iteration is slower, and both lists do the same O(n) work. The array list's references sit next to each other in memory, while a linked list's nodes are separate objects wherever the heap put them, so each step chases a pointer to a new address. CPUs are built to read memory in sequence and are much slower at hopping around. That's cache locality, and L22 (the memory hierarchy) explains why it matters so much. On top of that, every element costs a whole extra node object.

So in real code, reach for ArrayList (Kotlin's mutableListOf()) as your default list, and for ArrayDeque when you need fast operations at both ends (Part 4). Linked nodes still matter enormously: they're how you build stacks, queues, LRU caches, hash-table buckets (L19) and trees (L20). It's the general-purpose LinkedList class that rarely wins.

Bridge to Android. On a phone the cache argument matters even more, because memory bandwidth and battery are tighter. Lists of items you show on screen live in array-backed lists, and adapters look items up by position, which would be O(n) per lookup on a linked list.
What Kotlin does for you. Implement Iterable<T> once, and for, toList(), joinToString, map and filter all work on your own class, because they're extension functions on Iterable. In Java, Iterable buys you the enhanced for and forEach, and everything else is a manual loop or a StreamSupport detour. The nullable types (Node<T>?) also tell you exactly which links can be missing. With sentinels, almost none can, and the !!s in Doubly.kt mark the spots where the code relies on that guarantee.

Check

What do sentinel nodes buy you in a doubly linked list?

Every real node always has non-null neighbours, so insert and remove never need "is this the first, the last, or the only node?" branches.

You hold a reference to a node in the middle of a doubly linked list. Removing it costs:

The node knows both neighbours, so two reference updates unlink it. In a singly linked list you'd first have to walk from the head to find the node before it.

Doubling n made the LinkedList get(i) loop about four times slower. What does that suggest?

(2n)² = 4n². Each of the n calls to get(i) walks O(n) nodes. A for-each loop over the same list is O(n).

Why is iterating a LinkedList slower than an ArrayList, even though both are O(n)?

An array's references sit side by side, which CPUs read quickly. Linked nodes live at unrelated addresses, so each step is a jump: poor cache locality (L22).

Part 3

Stacks

~20 min

A stack is a collection where the last thing in is the first thing out: LIFO. You can only touch the top. push puts an item on top, pop removes and returns it, and peek looks without removing. You already know the most important stack in computing: the call stack from L4, where each call pushes a frame and each return pops it. Undo in an editor is a stack too, and so is the Android back stack, where activities "are arranged in a stack… in the order in which each activity is opened" (Android docs: Tasks and the back stack).

Two ways to build one

Both give O(1) operations. The rule is to put the top wherever the structure is cheap to change:

  • On an array list: the top is the end. add and removeAt(size - 1) never shift anything. Pushing is amortised O(1), because of resizing (L16).
  • On a linked list: the top is the head. addFirst and removeFirst are O(1), always, with no resizing, but you pay a node object per item. You'll build this one in the final.
peek: delete word  size: 3
undo delete word
undo bold
undo type 'Hi'
pop: stack is empty

Putting the top at the front of an array list would make every push and pop O(n), because everything shifts. Same abstract stack, very different cost: choosing where the top goes is the whole design decision.

The classic stack program: balanced brackets

Is {[()]} balanced? ([)] isn't, even though it has one of each. The insight: a closing bracket must match the most recent unmatched opener, and "most recent" is exactly what a stack gives you. Push every opener; on every closer, pop and compare. Sedgewick & Wayne set this as an exercise (Parentheses.java in §1.3):

"{[()]}"       true
"f(a[0], {b})" true
"([)]"         false
"(("           false
"())"          false
""             true

Three ways to fail: a closer with nothing open (())), a closer that doesn't match the top (([)]), and openers left over at the end (((). Look at the Java comparison: !top.equals(pairs.get(c)). Both sides are boxed Character objects, and != would compare references. It happens to work for ASCII characters because of the boxing cache, the same trap as L5's Integer cache. Kotlin's != calls equals, so the trap doesn't exist.

Don't use java.util.Stack

Java has a class literally called Stack, from Java 1.0. It's a subclass of Vector, an old synchronised array list, so a "stack" inherits every list method:

true
[sneaky, a, b, c] get(1)=a
pop: c
[c, b, a] pop: c

You can insert at the bottom and read any position, which breaks the whole idea of a stack. This is L8's "favour composition over inheritance" lesson in the JDK itself (Effective Java Item 18). The API docs say so: "A more complete and consistent set of LIFO stack operations is provided by the Deque interface and its implementations, which should be used in preference to this class. For example: Deque<Integer> stack = new ArrayDeque<Integer>();" (JDK docs: Stack). Notice too that the two print in opposite orders: Stack lists bottom first, while ArrayDeque used as a stack lists top first, because push adds at the front of the deque (JDK docs: Deque).

Kotlin has its own ArrayDeque in the standard library, a "resizable-array implementation of the deque data structure" (Kotlin API: ArrayDeque). It's a different class from Java's, and it's what you get without an import:

kotlin.collections.ArrayDeque
[a, b, c] pop: c peek: b
[a, b, c, d] pop: d
[b, a] java.util.ArrayDeque

Kotlin's stack vocabulary is addLast / removeLast / last(), with the top at the end, like an array list. Java's Deque uses push / pop / peek, with the top at the front. Same idea, opposite ends: keep that in mind when you switch languages.

Bridge to Spring and Android. Every stack trace you read in L10 is the call stack printed top first. Spring's long traces through proxies and filters are just a very deep stack, read from the top down until you reach your own code.
What Kotlin does for you.
  • A modern ArrayDeque is available with no import, so there's no legacy Stack class to stumble into.
  • removeLastOrNull() and lastOrNull() turn "empty" into a null you can handle with ?:, as in open.removeLastOrNull() ?: return false. Java's poll() also returns null, but nothing in the type says so.
  • == and != compare values, so comparing boxed Chars just works. In Java, != on Character is a reference comparison that only happens to work for cached values.
  • when with several values per branch ('(', '[', '{' ->) reads like Java 14+'s arrow switch, with no fall-through and no break.

Check

A stack is built on an array list. Where should the top go?

Adding and removing at the end shifts nothing (amortised O(1)). At index 0, every push and pop would shift all elements: O(n).

What does the bracket checker return for "([)]"?

When ) arrives, the top of the stack is [, not (. Counting brackets isn't enough; their order matters, and that's what the stack tracks.

Why do the Java docs recommend ArrayDeque over java.util.Stack?

Stack extends Vector, so you can add(0, x) or get(i), which breaks LIFO. The docs point to Deque for "a more complete and consistent set of LIFO stack operations".

Evaluating the postfix 8 2 /, what is the first value popped when / arrives?

2 was pushed last, so it pops first, and it's the right operand: 8 / 2 = 4. Swap them and you'd compute 2 / 8 = 0.

Part 4

Queues and ArrayDeque

~20 min

A queue is the fair version: first in, first out (FIFO). Items join at the back (offer) and leave from the front (poll), like a line at a till. On a linked list with a tail pointer that's easy: addLast and removeFirst are both O(1). On a plain array list it isn't, because removing from the front shifts everything.

The circular buffer

The array-based fix is to stop shifting. Keep two indexes: head, where the next poll reads, and tail, where the next offer writes. Both only ever move forwards, and when one runs off the end of the array it wraps to slot 0 with % capacity. The array is used as if its end were glued to its start: a circular buffer (or ring buffer). The listing below shows only main; watch the array on the right:

A
B
items=[C, D, E, F, G, null, null, null] head=0 tail=5 size=5
C D E F G

Here is the class behind that demo. Read it with the visualiser open: every line maps to an arrow or a slot above.

  • Wrap-around is one expression: (tail + 1) % items.size. No if needed.
  • Full vs empty. In both states head == tail, so a separate size tells them apart.
  • Growing copies the elements in queue order, starting at head, so the new array is unwrapped. Copying the old array slot by slot would scramble the order. The cost is O(n) but rare, so offer is amortised O(1), the same argument as L16's array list.
  • Clearing the polled slot (items[head] = null) matters. Otherwise the array keeps a reference to an object the queue has already handed out, and the garbage collector can't reclaim it. Holding on to references you no longer need is how memory leaks happen in a garbage-collected language (L24).
  • Generic arrays are the L13 erasure problem again. Kotlin uses arrayOfNulls<Any?> and casts on the way out; Java uses (T[]) new Object[n] and suppresses the unchecked warning, with a comment saying why it's safe.
  • Two files in Java: with both files in one folder, java RingDemo.java finds MyQueue.java by itself on JDK 22+ (JEP 458: multi-file source-code programs). In Kotlin, compile both: kotlinc MyQueue.kt RingDemo.kt -include-runtime -d ring.jar.

java.util.ArrayDeque is a circular buffer like yours, and the docs are blunt about it: "This class is likely to be faster than Stack when used as a stack, and faster than LinkedList when used as a queue. Most ArrayDeque operations run in amortized constant time." Also: "Null elements are prohibited" (JDK docs: ArrayDeque). That's because poll uses null to mean "empty", so a stored null would be ambiguous. Kotlin's ArrayDeque<E> allows nulls if your element type is nullable, and uses explicit …OrNull functions for "maybe empty". A deque ("deck", a double-ended queue) supports both ends, so one class serves as your stack and your queue.

Bridge to Android and servers. Android's main thread runs a loop that takes messages off a queue one at a time: MessageQueue is the "low-level class holding the list of messages to be dispatched by a Looper" (Android docs). A slow message blocks every message behind it, which is why long work must leave the main thread (Phase 8). On a server, a thread pool keeps submitted tasks in a queue until a worker is free: in ThreadPoolExecutor, "any BlockingQueue may be used to transfer and hold submitted tasks" (JDK docs).
What Kotlin does for you. Kotlin's ArrayDeque has one clear vocabulary: addFirst/addLast, removeFirst/removeLast (which throw) and removeFirstOrNull/firstOrNull (which don't), where Java has add/offer/push, remove/poll/pop and element/peek spread across two interfaces. The OrNull name puts "might be empty" in the call itself, and the T? return type makes you handle it. Kotlin's deque also implements MutableList, so deque[2] works.

Why does the circular buffer keep a size field as well as head and tail?

When the buffer is full, tail has wrapped round to meet head, the same picture as empty. A count (or a deliberately wasted slot) tells them apart.

Wrap-up

Exit quiz, recall card, sources

~5 min

Infinite recursion ends with StackOverflowError. Which structure overflowed? (L4)

Each call pushes a frame onto the thread's call stack, and the stack has a fixed maximum size (-Xss). It's LIFO for the same reason as today's stacks: the most recent call returns first.

Which kotlin.test call checks that pop() on an empty MyStack throws? (L11)

assertFailsWith runs the lambda and passes only if it throws that exception type. Java's equivalent is assertThrows(NoSuchElementException.class, () -> stack.pop()).

Java: Character a = 'x', b = 'x'; then System.out.println(a == b); (L5)

ASCII characters (0–127) are cached, so both refer to the same boxed object. The comparison is still by reference, and outside the cache it fails, which is why Brackets.java uses equals.

MyStack has a MyLinkedList rather than extending one. Which principle is that? (L8)

Composition exposes only the stack operations. Inheriting, as java.util.Stack does from Vector, leaks every list method (Effective Java Item 18).

Kotlin: listOf(3, 4, 5).fold(0) { acc, x -> acc + x } (L14)

fold starts at 0 and adds each element: 0 + 3 + 4 + 5 = 12. Because your MyLinkedList is an Iterable, fold works on it too.
