Thread A writes x = 42, then calls queue.put(x). Thread B calls queue.take(). Is B guaranteed to see 42? (L27)

The java.util.concurrent docs promise that actions before putting an object into a concurrent collection happen-before actions after another thread removes it (Memory Consistency Properties). Executors make the same promise for submitting a task, which this lesson relies on.

  1. The queue's put/take pair already creates the happens-before edge, so volatile adds nothing here.
  2. The Java memory model gives this guarantee on every CPU. Correct code never relies on x86's stronger ordering.
  3. Everything A wrote before put is visible to B once take returns that element.
  4. True, nothing is copied, but visibility doesn't need a copy: the edge covers every write made before put.

Two threads each need locks A and B. Which rule prevents the classic deadlock? (L27)

Deadlock needs a cycle of waiting. If every thread takes A before B, no cycle can form.

  1. With one global order, no thread can hold B while waiting for A, so no waiting cycle can form.
  2. volatile is about seeing a field's latest value, not about who holds a lock. The threads still wait on each other.
  3. yield is only a hint to the scheduler. Each thread can still end up holding one lock and waiting forever.
  4. Priority changes scheduling, not lock ownership. A blocked high-priority thread waits just as long.

Java: future.get() fails because the task threw IllegalStateException. What does get() actually throw? (L10)

The task's exception is wrapped. You read the original with getCause(), the same "Caused by" chain you learned to read in L10. Part 1 shows it.

  1. The original is kept only as the cause. get() never throws it directly.
  2. get() wraps the failure in its own checked exception, not in a generic RuntimeException.
  3. InterruptedException means the waiting thread was interrupted, not that the task failed.
  4. get() throws ExecutionException, and getCause() returns the task's IllegalStateException.

Why can't a Runnable lambda call Thread.sleep(100) in Java without extra code? (L10, L14)

Thread.sleep throws the checked InterruptedException, and Runnable.run() declares none. You either catch it or use a Callable, whose call() is declared throws Exception. Kotlin has no checked exceptions, so its lambdas don't care.

  1. Lambdas call static methods all the time. The problem is the checked exception that sleep declares.
  2. run() has no throws clause, so InterruptedException must be caught inside the lambda.
  3. You may sleep in a lambda. You just have to handle InterruptedException, or use a Callable.
  4. A Runnable runs on whichever thread calls run(), such as any pool worker.

Thread pools and executors

A platform thread is an OS thread with its own stack, so creating thousands of them costs real time and memory (L26, L22). Creating one per task also means nothing limits how many run at once. A thread pool fixes both problems: a few long-lived worker threads take tasks from a queue, one after another. In Java the pool hides behind the ExecutorService interface. Inside the pool: ThreadPoolExecutor

The Executors factory methods are shortcuts for ThreadPoolExecutor, whose full constructor shows every decision a pool makes: corePoolSize, maximumPoolSize, keepAliveTime and its unit, the workQueue, a ThreadFactory and a RejectedExecutionHandler. The class docs describe three queuing strategies: a direct hand-off (SynchronousQueue), an unbounded queue, which "admits the possibility of unbounded work queue growth when commands continue to arrive on average faster than they can be processed", and a bounded queue, which "helps prevent resource exhaustion … but can be more difficult to tune and control" (ThreadPoolExecutor). A fixed pool's unbounded queue is why a flood of requests can quietly eat all your memory.

A task that waits 90 ms for every 10 ms of work (W/C = 9) on 18 cores at full use wants about 18 × 1 × 10 = 180 threads. Hold that number for Part 3.

Two laws behind the numbers: Amdahl and Little

Two short formulas tell you what more threads can buy, before you measure anything. The first is about one job split across cores. The second is about a steady stream of requests.

Amdahl's law. Gene Amdahl's three-page paper at the 1967 AFIPS Spring Joint Computer Conference, "Validity of the single processor approach to achieving large scale computing capabilities", argued in prose that the part of a job that must run on one processor limits the whole job, however many processors you add. Today the argument is written as a formula. If a fraction p of the 1-thread time can run in parallel on n cores, the best possible speed-up is:

speed-up = 1 / ((1 − p) + p / n)

The serial part, 1 − p, takes the same time whatever n is. Only p shrinks, so the speed-up can never pass 1 / (1 − p). With 10% serial (p = 0.9), 18 cores give at most 1 / (0.1 + 0.05) ≈ 6.7×, 64 cores give 1 / (0.1 + 0.014) ≈ 8.8×, and a million cores still give less than 10×.

Sizing got close to the core count because counting primes is almost all parallel: the only serial work is adding up 144 numbers. Its gap below 18× comes mostly from the slower cores, not from Amdahl. To see the law at work, Amdahl pretends the first 28 chunks can't be split, so they run alone on main before the pool starts the other 116:

The program measures p itself: about 10% of the 1-thread time is the serial part. The same prime counting that reached about 14× in Sizing now stops at 6×, just under Amdahl's limit. The limit is a ceiling, and real runs lose a little more to the slower cores and to uneven chunks. A 64-core server could add at most another 1.3× on top of 18 cores. If you want this job faster, shrink the serial part; more cores won't do it.

Little's law. For a stream of requests, the question is how many are in the system at once. John Little proved the answer in "A Proof for the Queuing Formula: L = λW" (Operations Research 9(3), 1961). For any stable system, averaged over a long run:

L = λ W

L is the average number of items inside the system, λ (lambda) is the average arrival rate, and W is the average time each item spends inside. The result doesn't depend on how arrivals or service times are distributed, which is why it applies almost everywhere. "Stable" means that, over the long run, items leave as fast as they arrive. Otherwise the queue grows without limit, like the unbounded queue above.

Read "inside" as "holding a thread", and L is the number of busy threads. A service gets 200 requests per second, and each request holds a thread for 50 ms. Then L = 200/s × 0.05 s = 10 threads busy on average. Add headroom for bursts, but a pool of 200 would sit mostly idle. Turned around, λ = L / W is the most work a fixed number of threads can finish per second. PoolBasics had 3 threads and 100 ms tasks, so at most 3 / 0.1 s = 30 tasks per second, and its 6 tasks needed 0.2 s. It measured 221 ms. The JCiP formula above is Little's law too. When the CPUs are the bottleneck, they finish Ncpu × Ucpu / C tasks per second, and each task holds its thread for W + C. Multiply the two and you get Ncpu × Ucpu × (1 + W/C).

The surprise is that tasks 5 and 6 start before 3 and 4. The order of decisions comes straight from the class docs: below the core size, create a thread (tasks 1, 2). Otherwise queue the task (3, 4). Check

Your program's main finishes, but the process never exits. The most likely cause?

Pool worker threads are non-daemon, so they keep the JVM alive. Virtual threads are daemon threads and don't (Thread docs). Use try-with-resources / use.

  1. A deadlock can hang a process too, but it needs threads waiting on each other's locks. An idle, unclosed pool is far more common.
  2. Its worker threads are non-daemon, so they keep the JVM alive while they wait for more work.
  3. Virtual threads are daemon threads, so they never keep the JVM alive. The JVM exits and abandons them.
  4. The garbage collector's threads are JVM internals, and they never stop the JVM from exiting.

You submit a task that throws, and never call get() on its future. What appears on the console?

submit stores the exception in the Future. With no get(), it's silently lost, as "boom in submit" was in LostException.

  1. A stack trace appears only with execute, where the exception reaches the worker's uncaught-exception handler.
  2. submit prints nothing, not even the message: the exception waits in the Future.
  3. Pools don't log failed tasks. ThreadPoolExecutor has no such warning.
  4. The exception is stored in the Future, and without get() nobody ever looks at it.

A pool has core 2, max 10 and an unbounded LinkedBlockingQueue. Under heavy load, how many threads will it create?

Extra threads are only created when the queue is full, and an unbounded queue is never full. The docs: "no more than corePoolSize threads will ever be created. (And the value of the maximumPoolSize therefore doesn't have any effect.)"

  1. Extra threads are created only when the queue is full, and an unbounded queue never fills.
  2. Reaching the max needs a full queue first, which an unbounded queue never is.
  3. There's no gradual growth: the pool grows past its core size only when the queue refuses a task.
  4. That's closer to newCachedThreadPool, whose SynchronousQueue hands each task straight to a thread.

Pure CPU work on a machine with 8 identical cores. Which pool size is the sensible starting point?

CPU-bound work wants about one thread per core (JCiP §8.2 says Ncpu + 1). More threads only take turns, as 72 vs 18 showed in Sizing.

  1. One thread uses one core and leaves seven idle, like the 1-thread row in Sizing.
  2. 64 threads on 8 cores just take turns. Like 72 threads in Sizing, they add switching, not speed.
  3. One thread per core keeps every core busy without needless switching.
  4. A cached pool starts a new thread whenever none is idle, so a burst of CPU tasks gets far more threads than cores.

10% of a job's single-thread time must run on one thread. On 64 cores, the best possible speed-up is about…

Amdahl: 1 / ((1 − 0.9) + 0.9 / 64) = 1 / 0.114 ≈ 8.8×. The serial tenth never shrinks, so even infinitely many cores stop at 10×.

  1. 64× needs a fully parallel job. The serial tenth still takes as long as it did on one thread.
  2. 0.9 × 64 scales the speed-up by the parallel share. Amdahl divides the time, not the speed-up.
  3. The serial 0.1 plus the parallel 0.9 / 64 is 0.114 of the time, and 1 / 0.114 ≈ 8.8.
  4. 10× is the limit with infinitely many cores. With 64, the parallel part still takes 0.014 of the time.

A service gets 200 requests per second, and each one holds a thread for 50 ms. How many threads are busy on average?

Little's law: L = λW = 200/s × 0.05 s = 10. A much bigger pool sits idle, unless W grows, for example when the database slows down.

  1. 200 ÷ 50 divides the rate by the time. Little's law multiplies them: L = λ × W.
  2. 200 is how many arrive per second, not how many are inside at once. Each request leaves after 50 ms.
  3. That's 200 × 50 with W left in milliseconds. Convert first: 50 ms is 0.05 s.
  4. 200 per second × 0.05 s each = 10 requests in flight at any moment, on average.

Core size 1, max 2, a queue that holds 1, and every task blocks until the gate opens. What does this print?

Task 1 gets the core thread. Task 2 waits in the queue. The full queue lets task 3 start a second thread, up to the max. Task 4 finds no free thread and no room, so it's rejected. It's Ex1 in miniature.

  1. Core thread, then queue, then an extra thread up to the max, then rejection: one task at each stage.
  2. ArrayBlockingQueue(1) is bounded: it holds one task, not three. Only newFixedThreadPool's queue is unbounded.
  3. With the queue full, the pool may still grow to its max of 2, so task 3 gets a new thread.
  4. A pool never exceeds maximumPoolSize, here 2. One thread per task is what a cached pool does.

Futures and CompletableFuture

Virtual threads

~34 min (+7 min optional)

The JCiP formula from Part 1 said a task that mostly waits wants hundreds of threads, and a server with 10,000 waiting connections would want 10,000. Platform threads are too expensive for that, which is why pools and async callbacks exist. Virtual threads, final since JDK 21 (JEP 444), change the trade-off. From the Thread docs: "Virtual threads are typically user-mode threads scheduled by the Java runtime rather than the operating system. Virtual threads will typically require few resources and a single Java virtual machine may support millions of virtual threads. Virtual threads are suitable for executing tasks that spend most of the time blocked, often waiting for I/O operations to complete. Virtual threads are not intended for long running CPU intensive operations."

The mechanism is the third tab of the diagram above. JEP 444: "The platform thread to which the scheduler assigns a virtual thread is called the virtual thread's carrier." When a virtual thread blocks, it unmounts: its stack frames move to the heap and the carrier is free to run another one. You write plain blocking code (Thread.sleep, a socket read), and the JDK does the juggling. The API is the same Thread class in both languages:

Rules for using virtual threads

  • Don't pool them. JEP 444 says it directly: "Do not pool virtual threads". They're cheap enough to create one per task and throw away. A pool exists to ration expensive threads, and these aren't expensive.
  • To limit access to something scarce, use a semaphore, "constructs specifically designed for that purpose, such as semaphores" (JEP 444). A database with 10 connections, 1,000 virtual threads:
1000 queries, at most 10 at once, 2345 ms
1000 queries, at most 10 at once, 2351 ms

1,000 queries of 20 ms through 10 permits is 100 rounds, about 2 s plus overhead. That's Little's law again: 10 permits ÷ 0.02 s = 500 queries per second. Waiting on acquire() parks the virtual thread, which costs no carrier.

  • Be careful with ThreadLocal. With a pool, a thread-local is one object per worker. With a virtual thread per task, it's one per task, possibly a million. The JDK itself "removed many uses of thread locals from the JDK's java.base module in preparation for virtual threads … in order to reduce memory footprint when running with millions of threads" (JEP 444). The replacement for passing context down a call chain is scoped values, final in JDK 25 (JEP 506), which offer "lower space and time costs, especially when used together with virtual threads".
  • CPU-bound work gains nothing, as shown above. Use a fixed pool sized to your cores, or Part 4's Fork/Join.

Work stealing is why uneven halves don't matter much. Each worker keeps its own queue of forked tasks. The ForkJoinTask docs say subtasks "should also not perform blocking I/O", because a blocked worker is a core nobody else in the JVM can use.

Measure with Amdahl. Part 1's law applies unchanged: the split and the final combine are serial, and so is anything before the stream starts. A parallel stream over 1,000 elements of cheap work finishes faster sequentially, because there's almost no p to speed up and the fork/join overhead is all cost. An AI-diff smell. A stray .parallelStream() is one of the commonest "optimisations" in generated code. In review, ask four questions. Is the work CPU-bound and large? Does the source split well? Is every lambda free of side effects and blocking I/O? Was it measured? A .parallelStream().forEach { list.add(…) } or a parallel stream that calls an HTTP API fails at least one of them.

Kotlin has no parallel Sequence. A Kotlin Sequence "performs all the processing steps one-by-one for every single element" (Kotlin docs: Sequences), on the calling thread, and there's no .parallel() to call on it. On the JVM, Kotlin code calls Java's list.parallelStream() directly, as Parallel.kt does. For parallel work that also waits, use coroutines on Dispatchers.Default (L29).

What Kotlin does for you.
  • Not much here: ForkJoinPool, RecursiveTask and parallel streams are the same Java classes in both languages, and both printed the same counts. Kotlin's own collection operations (map, filter, count) and sequences are always sequential.
  • One thing it does against you: a Kotlin lambda can modify a captured var, so var n = 0; list.parallelStream().forEach { n++ } compiles and races. Java refuses, because a local used in a lambda "must either be final or effectively final" (JLS §15.27.2), which is why AI-written Java reaches for int[] n = {0}. That compiles too, and races just the same.
  • (lo + hi) ushr 1 is Java's (lo + hi) >>> 1, L18's overflow-safe midpoint.

A pipeline does light work on each of 5,000,000 numbers. Which source made .parallel() pay off in Parallel?

An ArrayList splits by index in constant time, so every worker gets an even share at once. A linked list has to be walked to split, and iterate computes each element from the previous one. With light work, only the ArrayList got clearly faster.

  1. A linked list must be walked node by node to split it, and in Parallel it gained nothing with light work.
  2. Index-based splitting is O(1) and even, so the cores share the work from the start.
  3. Each iterate element depends on the previous one, so the source is inherently sequential.
  4. They were equal only with heavy work, where the work per element hides the splitting cost.

An AI change replaces ids.map { api.fetch(it) } (50 ids, each a 200 ms HTTP call) with ids.parallelStream().map { api.fetch(it) }.toList(). What's the main problem?

Parallel streams run on ForkJoinPool.commonPool(), shared by the whole JVM and sized to the cores. Blocking HTTP calls tie up those workers, so every other parallel stream waits. Waiting work belongs on virtual threads (Part 3) or coroutines (L29).

  1. map + toList() on a list keeps encounter order, even in parallel.
  2. Kotlin calls Java's parallelStream() directly, as Parallel.kt did.
  3. HTTP calls can overlap fine. The issue is which threads wait for them.
  4. Blocked common-pool workers are lost to every other parallel task in the JVM; this work wants virtual threads.

Java: a RecursiveTask that sums 1..20 and counts its leaves. What does this print?

The range [1, 21) has 20 numbers. It splits into 10 + 10, then four pieces of 5. Five is still more than 4, so each splits into 2 + 3: 8 leaves. Every number is added exactly once, so the total is 1 + … + 20 = 210, whichever threads ran the leaves.

  1. 20 / 4 = 5 assumes even chunks of 4, but halving 20 never produces a piece of exactly 4.
  2. The pieces of 5 are still above the threshold, so they split once more.
  3. 20 → 10 → 5 → 2 and 3: eight leaves, and every number is counted once.
  4. hi is exclusive, but it's 21, so 20 is included: the sum is 210.

  • 16 threads divide that by about 16: 125.8 / 16 ≈ 7.9 s, measured 8.1 s. The pool is the bottleneck, because 984 tasks are always waiting in its queue.

Exit quiz, recall card, sources

~5 min

L22 + L28: why can a JVM hold a million virtual threads but not a million platform threads?

Every platform thread is a real OS thread with a fixed native stack and kernel bookkeeping (L22). A virtual thread is a heap object whose stack is only as big as it needs to be.

  1. Virtual threads are ordinary heap objects, and the garbage collector manages them like any others.
  2. Platform threads do have stacks: fixed-size native ones, which is a big part of their cost.
  3. Each one needs a kernel thread and a native stack, while a virtual thread is a small heap object.
  4. Virtual threads run in parallel, one per carrier, and there's a carrier per core.

L16 + L28: a fixed pool of k threads runs n independent tasks of 1 s each (n much larger than k). The wall time grows like…

The tasks run in waves of k: 2,000 tasks / 200 threads = 10 s, and 10,000 / 200 = 50 s. Doubling n doubles the time.

  1. n tasks in waves of k take about n / k seconds.
  2. More threads make it faster, not slower, so k belongs in the denominator.
  3. Nothing halves the remaining work at each step. The time grows in proportion to n.
  4. A fixed pool can't run any number of tasks at once. Constant time would need a thread per task.

L24 + L28: which JFR event tells you a virtual thread blocked while stuck to its carrier?

"jdk.VirtualThreadPinned indicates that a virtual thread was parked while pinned" (JEP 444). On JDK 26 it also reports the reason, here SlowInit.<clinit>.

  1. jdk.ExecutionSample samples which methods are running, for CPU profiling (L24).
  2. jdk.GarbageCollection records collections and their pauses, not thread scheduling.
  3. jdk.ObjectAllocationSample samples allocations, for finding memory hot spots.
  4. It's recorded when a virtual thread parks while pinned, and on JDK 26 it includes the reason.

L26 + L28: 1,000 virtual threads each do count++ on a shared Int field. The final value is…

Virtual threads are still threads running in parallel on many carriers. count++ is still a read-modify-write race (L26), so use an atomic, a LongAdder or a lock.

  1. Virtual threads don't make count++ atomic, so updates can still be lost.
  2. count++ is read, add, write: two threads can read the same value, and one update is lost.
  3. Every increment writes something, so the field does change. Some updates are simply lost.
  4. A race can only lose increments, never invent them, so the result can't exceed 1000.
