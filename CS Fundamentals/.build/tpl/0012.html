Part 1

Debugger basics

~25 min

So far, when a program misbehaved, you've added printlns, re-run it, read the output, and repeated. A debugger does better. It pauses the running program at a line you choose, shows you every variable in every active call, and lets you advance one line at a time while you watch values change. You don't edit code, re-run, or guess. JetBrains' own summary of the workflow is: set breakpoints, run in debug mode, examine the suspended program, and step through it (IntelliJ: Debug code).

The debugger works identically for Kotlin and Java, because both run on the same JVM (L1) and IntelliJ debugs the bytecode.

Set up an L12 project

The debugger needs a project IntelliJ can build. Make one with Gradle, exactly as in L1, inside your katas repo:

$ mkdir ~/katas/l12 && cd ~/katas/l12
$ gradle init --type kotlin-application --dsl kotlin --package katas --use-defaults --project-name l12
$ mkdir -p app/src/main/java          # Java files go here, Kotlin files in app/src/main/kotlin

Open ~/katas/l12 in IntelliJ with File → Open…. Put each Kotlin file below directly in app/src/main/kotlin/ and each Java file in app/src/main/java/, without a package line. I checked that this project compiles all of this lesson's Kotlin and Java files side by side (L9 showed why mixing works).

Hands-on: a checkout that overcharges

Ten percent off a 2 × $10.00 item, plus 2 × $5.00 at full price, should cost 2800 cents. The program says 3000. Type it in, run it, and see the wrong total for yourself:

total: 3000 cents
Exercise: find it with the debugger, not by staring
  1. Put a breakpoint on the first line of main, then Debug.
  2. Press Step Into (F7) to enter lineTotal. Check Frames: there are now two frames. Step Over (F8) and watch gross appear in Variables.
  3. Step Into discountCents. Step Over one line. What's rate? What did you expect it to be?
  4. Press Step Out (⇧F8) to go back to lineTotal. What's discount?
  5. Fix the bug, re-run, and confirm total: 2800 cents. Then press Resume (⌘⌥R) to finish a debug session without stepping through everything.
What you'll see, and the fix

Inside discountCents, the Variables view shows priceCents = 2000, percent = 10 and then rate = 0. 10 / 100 is integer division, the L2 trap, so it truncates to 0 and the discount is always 0. Back in lineTotal after Step Out, discount = 0 and gross = 2000, so the line returns 2000 instead of 1800. The fix is to multiply before dividing:

total: 2800 cents

What Kotlin does for you (and what it doesn't). Nothing changes for debugging. Kotlin compiles to ordinary JVM bytecode with line numbers, so breakpoints, frames and stepping work exactly as they do in Java. You'll notice one Kotlin-specific detail: the frame for a top-level function shows up under the generated class, such as CheckoutKt (L1, L9). And the bug itself is language-neutral. Both languages truncate Int division silently.

Part 2

Debugger power tools

~20 min

Stepping is fine for ten lines. Real bugs hide on iteration 733 of a loop, or deep inside a library call. These tools take you straight there:

ToolHow (macOS)Use it when…
Conditional breakpointright-click the line → Add Conditional Breakpoint, then type a Boolean expressionthe bug only happens for certain values: "stop only when total < 0"
Exception breakpointRun → View Breakpoints (⌘⇧F8) → Add (⌘N, top-left of the dialog) → type the exception's namesomething throws and you want to stop at the moment it's thrown, with every variable still alive
Evaluate Expression⌥F8you want to try out code against the paused state: "what would sum.toDouble() / n give?"
Watchestype an expression at the top of the Variables tab → Add to Watchesyou want an expression recomputed at every step
Set Valueselect a variable → F2you want to test a hypothesis by changing a value mid-run

Sources: Breakpoints (conditional and exception breakpoints: "click Add… in the top-left corner of the dialog and enter the name of the exception", or "check Any Exception under Java Exceptions" to catch everything) and Examine suspended program (Evaluate Expression, watches "evaluated for each step", Set Value).

The debugger calls your toString(). Objects in the Variables tab are displayed using their toString() results; the setting is called "Enable toString() object view" (IntelliJ: Customize views). That's why a data class or record (L7) is so pleasant to debug: you see Cart(items=…, tier=GOLD) instead of Cart@1b6d3586. It also means the debugger runs your toString(), so keep it free of side effects. A toString() that changes state will change it every time you look.

Exercise: two bugs, two power tools
  1. Points: put a breakpoint on the total += earned line and make it conditional on total + earned < 0, which is true exactly when the next addition will wrap. Debug it. Which customer does it stop on? What are total and earned? Use Evaluate Expression (⌥F8) to compare total + earned with total.toLong() + earned (Java: (long) total + earned). Then fix it.

What you'll see, and the fixes

Points. The conditional breakpoint stops on customer = 733. At that moment earned = 5864000, and total is just below Int.MAX_VALUE. Evaluate shows total + earned as a large negative number, while the Long version gives 2152088000, which is larger than 2,147,483,647. It's the L2 overflow, found in seconds instead of by stepping 733 times. The fix is to use a Long for the total and make the multiplication itself Long:

total points: 4004000000

ParseAll. The exception breakpoint fires "when Throwable or one of its subclasses is thrown" (IntelliJ docs), here deep inside Integer.parseInt. That's the top frame, and it's JDK code. Click your main frame below it: index = 640 and line = "64l" (a lowercase L where a 1 should be). The fix is in the data, not the code. Or, if bad input is expected, parse with toIntOrNull() (L3) or catch the exception (L10).

Check

A bug only appears on iteration 733 of a loop. What's the best tool?

The condition is checked every time the line is hit, and the debugger only pauses when it's true.

An exception breakpoint for NumberFormatException pauses the program…

It stops at the throw, before the stack unwinds (L10), so every frame's variables are still there to inspect.

Evaluate Expression (⌥F8) lets you…

It runs an arbitrary expression against the paused program's current state (IntelliJ docs).

Why should toString() never have side effects?

Every time you look at the object in the Variables view, its toString() is called.

Part 3

Git branches

~15 min

In L1 every commit went onto one line of history. A branch lets you start a separate line, for a fix or an experiment, while main stays exactly as it was. The surprise is how little a branch is: "A branch in Git is simply a lightweight movable pointer to one of these commits." Git also keeps "a special pointer called HEAD… a pointer to the local branch you're currently on" (Pro Git §3.1). Making a branch copies no files. It writes a single pointer.

First: check your branch name

Run git branch --show-current in ~/katas. On this Mac's Git (2.50.1, Apple Git-155), a fresh git init already names the first branch main, but Pro Git notes that Git traditionally creates master by default (Pro Git §1.6). If yours says master, rename it and set the default for future repos:

$ git branch --show-current
master
$ git branch -m master main
$ git branch --show-current
main
$ git config --global init.defaultBranch main

While you're configuring things, pick the editor Git opens for merge messages, for example git config --global core.editor nano. Pro Git warns that an unconfigured editor can leave you "in a really confusing state" (Pro Git §1.6).

Part 4

Merging and conflicts

~20 min

git merge other brings other's commits into the branch you're on. There are two outcomes, and which one you get depends only on the shape of the history.

Fast-forward: nothing to combine

If your branch hasn't moved since other split off, Git "simply moves the pointer forward… this is called a 'fast-forward'" (Pro Git §3.2). No new commit is made:

$ git switch main
$ git merge greeting
Updating 55834c9..d5fc4cd
Fast-forward
 Hello.kt | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)

Three-way merge: a new commit with two parents

If both branches got new commits, Git combines the two branch tips and their common ancestor (a three-way merge) and records the result as a merge commit, which "is special in that it has more than one parent" (Pro Git §3.2). Here farewell changed Hello.kt while main added a README:

$ git switch -c farewell
# (edit Hello.kt: add println("Bye!") after the greeting)
$ git commit -am "Add farewell"
[farewell 5280d17] Add farewell
 1 file changed, 1 insertion(+)
$ git switch main
# (create README.md, then git add README.md)
$ git commit -m "Add README"
[main 5ca77b4] Add README
 1 file changed, 2 insertions(+)
 create mode 100644 README.md
$ git merge farewell                # Git opens your editor for the merge message: save and close
Merge made by the 'ort' strategy.
 Hello.kt | 1 +
 1 file changed, 1 insertion(+)
$ git log --oneline --graph --all
*   4e2c46f Merge branch 'farewell'
|\
| * 5280d17 Add farewell
* | 5ca77b4 Add README
|/
* d5fc4cd Friendlier greeting

Conflicts: when Git can't decide for you

If both branches changed the same lines, Git can't know which version you want, so it stops and asks. Here shout and main each rewrote the greeting line:

$ git merge shout
Auto-merging Hello.kt
CONFLICT (content): Merge conflict in Hello.kt
Automatic merge failed; fix conflicts and then commit the result.
$ cat Hello.kt
fun main() {
<<<<<<< HEAD
    println("Hello, merge conflicts!")
=======
    println("HELLO, BRANCHES!")
>>>>>>> shout
    println("Bye!")
}
$ git status

You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
	both modified:   Hello.kt

no changes added to commit (use "git add" and/or "git commit -a")

Read the conflict markers like this: between <<<<<<< HEAD and ======= is your side, the branch you're on. Between ======= and >>>>>>> shout is their side, the branch you're merging in (git-merge docs: how conflicts are presented). Notice that println("Bye!") merged cleanly. Only the overlapping line is in conflict.

What IntelliJ does for you. When a merge stops on conflicts, IntelliJ's Conflicts dialog offers Accept Yours, Accept Theirs or Merge…. The merge tool "consists of three panes": your read-only version on the left, theirs on the right, and "a fully-functional editor" in the middle showing the result (IntelliJ: Resolve Git conflicts). It's the same decision you just made in nano, shown side by side. Learn the markers first, because you'll meet them in terminals, code reviews and CI logs where there's no IDE.

Check

When is a merge a fast-forward?

If your branch hasn't diverged, Git just moves the pointer forward (Pro Git §3.2). Changing different files on both sides still needs a three-way merge commit.

In a conflict, what's between <<<<<<< HEAD and =======?

That part is your side, HEAD. The part after ======= is their side (git-merge docs).

After editing out the conflict markers, you…

"Staging the file marks it as resolved in Git." Then git commit or git merge --continue finishes the merge (Pro Git §3.2).

What does git branch -d do on a branch whose commits were never merged?

"The branch must be fully merged". -D forces it (git-branch docs).

(I've trimmed two index … lines from the git diff output, which are hashes that will differ for you anyway.) The new println("Empty list: …") line from main merged automatically. Only the return line conflicted, because both branches rewrote it.

The resolution takes the guard from HEAD (your side) and the fix from fix-average (their side). Neither side alone is right:

Average heart rate: 76.5 bpm
Empty list: 0.0 bpm

If you'd clicked Accept Theirs, you'd have lost the empty-list guard, and average(emptyList()) would print NaN, because 0.0 / 0 isn't a number (L2). If you'd clicked Accept Yours, the bug would come back. Resolving a conflict means understanding both changes.

~5 min

Does Kotlin force you to catch IOException the way Java does?

Kotlin has no checked exceptions (L10). @Throws exists only so Java callers can catch them (L9).

Which JUnit assertion checks that code throws an exception?

From L11. A test for the ParseAll bug could use assertThrows<NumberFormatException>.

Why did average(listOf(72, 75, 79, 80)) print 76.0?

306 / 4 on Ints is 76, and converting afterwards can't bring back the .5 (L2).
