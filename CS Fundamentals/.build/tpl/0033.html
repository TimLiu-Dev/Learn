Security Basics

The JDK ships hashing, encryption and signatures, and every one of them is easy to misuse. This lesson separates encoding from hashing from encryption, stores passwords the way OWASP says to, and then breaks and fixes three of the most common web bugs on toy servers that only ever listen on 127.0.0.1.

Part 1

Encoding vs hashing vs encryption

~30 min

Three words get mixed up constantly, including in code AI writes for you:

Reversible?Needs a key?Use it for
Encoding (Base64, hex, URL)yes, by anyonenofitting bytes into text formats
Hashing (SHA-256)nonofingerprints, integrity checks
Encryption (AES-GCM)yes, with the keyyeskeeping data secret

Encoding is not security

encoded: cGFzc3dvcmQxMjM=
decoded: password123

Base64 is a public, keyless transformation (Base64 docs). If you ever see a "secret" stored as Base64, it's stored in plaintext with extra steps. HTTP Basic auth sends user:password Base64-encoded (RFC 7617), which is only safe because TLS (L31) encrypts the whole request.

Cryptographic hashes

A cryptographic hash such as SHA-256 maps any input to a fixed 256-bit fingerprint. The MessageDigest docs call them "secure one-way hash functions that take arbitrary-sized data and output a fixed-length hash value". Three properties matter: you can't run it backwards, you can't find two inputs with the same output, and a tiny change in the input scrambles the whole output (the avalanche effect).

hello -> 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
hellp -> fdd7585e08c4e2afd71dcabdb4636c89d557a3f42db9e2040c8bbd1708aa4ce7
bits that differ: 131 of 256
"Aa".hashCode() = 2112, "BB".hashCode() = 2112

One letter changed, and 131 of 256 bits flipped: about half, which is what "looks random" means. Meanwhile L19's hashCode collides on two-letter strings. It's built to be fast for hash tables, and nobody claimed it resists attackers.

Try it live. Your browser has SHA-256 built in. Change one character and watch about half the hex digits change:

Try Aa and BB to see the String.hashCode collision next to two completely different SHA-256 values.

Integrity checks. Every jar this course downloaded from Maven Central was checked against its published hash. It's the same idea from the command line:

$ shasum -a 1 h2-2.5.252.jar
993ba74eafa574df15f4809f8082a12f67cad34b  h2-2.5.252.jar
$ cat h2-2.5.252.jar.sha1
993ba74eafa574df15f4809f8082a12f67cad34b

If one byte of the jar had been altered in transit, the hashes wouldn't match. (SHA-1 is broken for collision resistance, so prefer SHA-256 where you have the choice. Maven Central also requires PGP signatures, which prove who published a file, not just that it arrived intact.)

Symmetric encryption: AES-GCM

Encryption is reversible, but only with the key. Use an authenticated mode: OWASP's Cryptographic Storage Cheat Sheet says "Where available, authenticated modes should always be used", naming "GCM and CCM" as "first preference". GCM adds a tag that detects any tampering:

ciphertext+tag: 28 bytes
decrypted: meet at noon
tampered: AEADBadTagException: Tag mismatch

12 plaintext bytes became 28: the ciphertext plus a 16-byte (128-bit) tag. Flipping a single bit made decryption throw AEADBadTagException, "thrown when a Cipher operating in an AEAD mode (such as GCM/CCM) is unable to verify the supplied authentication tag". The IV (nonce) can be public, but it must never repeat under the same key. That's why it comes from SecureRandom.

Asymmetric crypto: signatures

Public-key crypto uses a key pair. Whoever holds the private key can sign; anyone with the public key can verify. (The reverse direction, encrypting to someone's public key, is how a key gets agreed safely.) The JDK has supported Ed25519 since JDK 15 (JEP 339):

signature: 64 bytes
original verifies: true
altered verifies:  false

Why TLS uses both (L31). Asymmetric crypto is slow but solves the "how do we share a key with a stranger" problem: the server proves its identity with a signature over its certificate, and the two sides agree a fresh key. Then fast symmetric encryption (AES-GCM or ChaCha20-Poly1305) protects the actual data (RFC 8446, TLS 1.3).

HMAC: a keyed fingerprint

A plain hash proves nothing about who made it: anyone can hash an edited message. An HMAC mixes in a secret key, so only key holders can produce a valid tag. That's how API request signing works, and how an HS256 JSON Web Token's signature is computed.

tag: b372f5ca7983000d…
genuine: true
edited:  false

Random numbers that attackers can't predict

Random(42) twice: -5025562857975149833, -5025562857975149833, same=true
token length: 43 chars

In L18 and L21 a seeded Random was a feature, because it made tests repeatable. For tokens it's fatal. The Random docs say it plainly: "Instances of java.util.Random are not cryptographically secure. Consider instead using SecureRandom". OWASP's cheat sheet lists Math.random(), java.util.Random and ThreadLocalRandom as unsafe, and SecureRandom and UUID.randomUUID() as safe.

Never roll your own crypto. OWASP's whole guidance on custom algorithms is two words: "Don't do this." Use the JDK's reviewed primitives, with their standard names (Java Security Standard Algorithm Names), and prefer a higher-level library when one fits.

What Kotlin does for you.
  • Not much here, honestly: the crypto APIs are the JDK's, and Kotlin calls them exactly as Java does. What changes is the noise around them.
  • No checked exceptions (L10), so NoSuchAlgorithmException and GeneralSecurityException don't force throws Exception onto every signature.
  • run { init(…); doFinal(…) } and apply { init(256) } (L15) configure a Cipher or KeyGenerator in one expression.
  • ByteArray(12).also { rng.nextBytes(it) } creates and fills an array in one line, where Java needs a temporary variable.
  • salt + pw.toByteArray() concatenates byte arrays with +. Java needs two System.arraycopy calls.

Check

A config file stores db.password=c2VjcmV0, which turns out to be Base64. How protected is the password?

Base64 has no key; Base64.getDecoder().decode gives back secret immediately. Encoding changes the format, never the secrecy.

You need to show a customer's saved address back to them later. Hash it or encrypt it?

You need the original back, and a hash can't be reversed. The OWASP Password Storage Cheat Sheet uses exactly this example: an address "is displayed in plaintext on the user's profile. Hashing their address would result in a garbled mess."

One ciphertext byte is altered, then Cipher.doFinal runs in AES/GCM/NoPadding decrypt mode.

GCM checks the authentication tag first and throws AEADBadTagException: Tag mismatch. You never receive tampered plaintext, which is the point of an authenticated mode.

Which tool proves a message came from someone holding a shared secret key?

Anyone can recompute a plain SHA-256 over an edited message. An HMAC needs the key, so a valid tag shows a key holder produced it.

Password-reset tokens generated with new Random(System.currentTimeMillis()). What's wrong?

An attacker who knows roughly when the token was made can try each millisecond as the seed and regenerate it. SecureRandom draws from the OS's cryptographic source instead.

Part 2

Storing passwords properly

~25 min

Assume your database will leak one day: a stolen backup, an injection bug, a misconfigured server. The question is what the attacker gets. OWASP's Password Storage Cheat Sheet starts from exactly that: passwords "must be protected from an attacker even if the application or database is compromised."

  • Plaintext: they get every password, and because people reuse passwords, access to your users' other accounts too.
  • Encrypted: they get every password as soon as they find the key, which usually sits on the same server. Passwords should be hashed, not encrypted.
  • Hashed with plain SHA-256: better, but not good enough. Two problems follow.

Problem 1: same password, same hash

unsalted SHA-256:
  ana 284fff3bd254b48c…
  ben 284fff3bd254b48c…
salted (random 16-byte salt per user):
  ana 45c60526776c47a5…
  ben 52be903134f63c25…

Without a salt, the attacker sees at a glance that ana and ben share a password, and can look the hash up in a precomputed table. A salt is random bytes stored next to each hash and mixed in before hashing. The salted lines differ even though the passwords match (and differ again every run: the Java run printed other values). The cheat sheet: salting "protects against an attacker's pre-computing hashes using rainbow tables", and makes it "impossible to determine whether two users have the same password without cracking the hashes".

Problem 2: SHA-256 is too fast

Salts stop precomputation, but the attacker can still just guess: hash "password1", "sunshine1", and so on, against each salt. The cheat sheet: "Fast hashing algorithms such as SHA‑256 are not suitable for password storage because they allow attackers to perform large numbers of guesses quickly." How fast? Measured on this machine:

SHA-256, one guess:   33 ns  (~30303030 guesses/s on one core)
PBKDF2 600k, one guess: 52 ms  (~18 guesses/s)
slowdown: ~1601770x   (sink 48000590)
SHA-256, one guess:   29 ns  (~34482758 guesses/s on one core)
PBKDF2 600k, one guess: 54 ms  (~18 guesses/s)
slowdown: ~1877073x   (sink 48000590)

On my machine, one core tries about 30 million SHA-256 guesses a second. A GPU rig does far more; the cheat sheet points out that "with high speed hardware (such as GPUs) and cloud services with many servers for rent, the cost to an attacker is relatively small". A deliberately slow hash cuts that to about 18 guesses a second per core, roughly a million-fold slowdown, while a real user logging in waits 50 ms once. (The sink variable keeps the JIT from deleting the work, L23's dead-code lesson.)

The fix: a slow, salted, adaptive hash

OWASP's summary, quoted directly:

  • "Use Argon2id with a minimum configuration of 19 MiB of memory, an iteration count of 2, and 1 degree of parallelism."
  • "For legacy systems using bcrypt, use a work factor of 10 or more and with a password limit of 72 bytes."
  • "If FIPS-140 compliance is required, use PBKDF2 with a work factor of 600,000 or more and set with an internal hash function of HMAC-SHA-256."

Argon2id is the first choice because it's memory-hard: each guess needs megabytes of RAM, which is what makes GPUs, with thousands of cores but little memory each, expensive to throw at it. But the JDK doesn't include Argon2id or bcrypt; you'd add a library such as Bouncy Castle. In Spring, Spring Security's PasswordEncoder wraps these for you (bridge only). PBKDF2 is built into the JDK (PBKDF2WithHmacSHA256 in the standard names), so that's what we'll write by hand, at OWASP's "PBKDF2-HMAC-SHA256: 600,000 iterations (recommended)":

stored: pbkdf2-sha256$600000$sRNv4xzCYXXut2fJJuriEw==$68…
one hash took 48 ms
right password: true
wrong password: false
same password again gives a new string: true
stored: pbkdf2-sha256$600000$kwZfdzA6J+GP9rf/EGy9HQ==$ua…
one hash took 47 ms
right password: true
wrong password: false
same password again gives a new string: true

Three design points:

  1. Store the parameters with the hash. algorithm$iterations$salt$hash means you can raise the cost later and still verify old hashes. The exercise uses that.
  2. Compare in constant time. A normal equals stops at the first differing byte, so a wrong guess that matches more leading bytes takes slightly longer. Measured over many requests, that timing difference can leak information. The OWASP Authentication Cheat Sheet asks for comparison that "Returns in constant time, to protect against timing attacks". MessageDigest.isEqual does that: "the calculation time depends only on the length of digesta. It does not depend on … the contents of digesta and digestb" (API docs).
  3. Never log passwords, not even failed ones, and rate-limit login attempts so online guessing is slow too.

CharArray vs String. PBEKeySpec takes a char[], and clearPassword() wipes its copy, because a String is immutable and can't be wiped. The old advice is to keep passwords in arrays and zero them after use. Treat it as a small extra, not a defence: the password already arrived as a String from the HTTP request, and the GC may have copied the array (L24). Hashing properly matters far more.

What Kotlin does for you.
  • val (alg, iter, salt, hash) = stored.split("$") destructures the stored string in one line (L7), where Java indexes p[0]…p[3].
  • Kotlin's split("$") splits on a literal string. Java's split takes a regex, where $ means "end of line", so Java must write split("\\$"). Forget the escape and Java silently returns one piece. A real bug class.
  • require(alg == "pbkdf2-sha256") { … } (L10) replaces an if … throw new IllegalArgumentException.
  • In a string template, "\$$ITERATIONS" prints a literal $ and then the value. Note the escape: a bare $ followed by a name would be interpolated.

Check

Why does every user get their own random salt?

Different salts mean different hashes for the same password, so precomputed tables are useless and shared passwords don't show. A salt doesn't make guessing slower; the slow hash does that.

According to OWASP, the minimum PBKDF2-HMAC-SHA256 iteration count is…

"PBKDF2-HMAC-SHA256: 600,000 iterations (recommended)". 72 is bcrypt's byte limit on password length, not a cost.

Why compare password hashes with MessageDigest.isEqual rather than contentEquals?

An early-exit comparison takes longer the more leading bytes match, which leaks information. isEqual's time depends only on the length.

Java: "pbkdf2$600000$c2FsdA==$aGFzaA==".split("$").length

Java's split takes a regex, and $ is the end-of-input anchor, a zero-width match at the very end. Nothing is split, so you get the whole string back: length 1. Kotlin's split("$") treats it literally and gives 4.

The OWASP Top 10: injection, XSS, access control

~35 min

The OWASP Top 10:2025 is "a standard awareness document for developers and web application security", ranking the most critical web risks from real test data. The 2025 list:

A01Broken Access Controlthis part (IDOR)
A02Security Misconfigurationverbose errors, below

A04Cryptographic FailuresParts 1 and 2

Broken access control stays at #1: "100% of the applications tested were found to have some form of broken access control" (A01). Injection fell to #5 but "had the greatest number of CVEs for any category", and it now includes cross-site scripting (A05).

SQL injection

Injection is "an application flaw that allows untrusted user input to be sent to an interpreter … and causes the interpreter to execute parts of that input as commands" (A05). Here's the classic version against an in-memory H2 database. JDBC gets a proper lesson in L36; for now you only need Statement vs PreparedStatement. (This toy stores plaintext passwords so the injection is easy to see. Part 2 already told you never to do that.)

$ java -cp h2-2.5.252.jar SqlLogin.java
  SQL: SELECT name FROM users WHERE name = 'ana' AND password = 'p4ss'
concat, right password:  true
  SQL: SELECT name FROM users WHERE name = 'ana' AND password = 'nope'
concat, wrong password:  false
  SQL: SELECT name FROM users WHERE name = 'ana' AND password = '' OR '1'='1'
concat, crafted input:   true
prepared, right password: true
prepared, crafted input:  false

Read the third SQL line. The input's first ' closed the string literal, and the rest became SQL: … AND password = '' OR '1'='1'. Because AND binds tighter than OR, the condition is true for every row, so the "login" succeeded with no password. Both languages print the same.

The fix is not to escape quotes by hand. OWASP's SQL Injection Prevention Cheat Sheet lists "Option 1: Use of Prepared Statements (with Parameterized Queries)" first, and marks escaping as "STRONGLY DISCOURAGED". With ? placeholders, the SQL text is fixed before any input arrives, and the database receives the input separately as a value. It can't become syntax, whatever characters it contains.

Command injection

The same mistake works against the shell (callback to L22's ProcessBuilder):

shell:   Hello, Ada | INJECTED
argList: Hello, Ada; echo INJECTED

sh -c hands the whole string to a shell, which treats ; as "and now run another command". The argument-list form starts echo directly with three arguments, so the input is one argument and the ; is just a character. OWASP's OS Command Injection Defense Cheat Sheet: "The primary defense is to avoid calling OS commands directly", and in Java, "use ProcessBuilder and the command must be separated from its arguments".

Cross-site scripting (XSS)

XSS is injection into HTML. If a page echoes user input unescaped, a <script> in that input runs in every visitor's browser, with access to the page and its cookies. A tiny guestbook on 127.0.0.1, fetched by an in-program HttpClient (L31) so you see the raw HTML a browser would receive:

/unsafe -> <p>Thanks for signing, <script>alert('hi')</script>!</p>
/safe -> <p>Thanks for signing, &lt;script&gt;alert(&#x27;hi&#x27;)&lt;/script&gt;!</p>

The unsafe response contains a working <script> element. The safe one contains text that a browser displays as <script>… and never runs. The escape function encodes exactly the five characters in OWASP's XSS Prevention Cheat Sheet table for HTML content: &→&amp;, <→&lt;, >→&gt;, "→&quot;, '→&#x27;. & must go first in a chain of replace calls, or you'd double-escape the others.

Two extra layers, neither a replacement for escaping:

  • Content-Security-Policy tells the browser which scripts may run. The /safe route sends default-src 'self', which blocks inline scripts: MDN says that with a default-src or script-src directive, "inline JavaScript will not be allowed to execute unless extra measures are taken". OWASP calls CSP "an additional layer of defense" and warns "it should not be your primary defense mechanism" (MDN: CSP).
  • HttpOnly cookies can't be read by JavaScript. MDN: it "Forbids JavaScript from accessing the cookie, for example, through the Document.cookie property", which "mitigates attacks against cross-site scripting" (MDN: Set-Cookie). Session cookies should always set it.

Kotlin's "…${name}…" templates and Java's "…" + name + "…" are both plain string concatenation: neither escapes anything. Real web apps rarely hand-build HTML strings for this reason. OWASP notes that modern frameworks help "by using templating, auto-escaping, and more", but warns that their escape hatches bring the bug straight back.

Broken access control (IDOR)

An insecure direct object reference is A01's textbook case: "Permitting viewing or editing someone else's account by providing its unique identifier". The server checks that you're logged in, but not that the record is yours:

ben reads his own (unsafe):  200 ["laptop"]
ben reads ana's   (unsafe):  200 ["book"]
ben reads ana's   (safe):    404 not found
ben reads his own (safe):    200 ["laptop"]
no token          (safe):    401 who are you?

Ben only had to change ben to ana in the URL. The fix is one line: the record's owner must equal the caller. OWASP's prevention advice: "Model access controls should enforce record ownership", and "Except for public resources, deny by default."

401, 403 or 404? (L31, RFC 9110 §15.5)

  • 401 Unauthorized means the request "lacks valid authentication credentials": we don't know who you are. (A real 401 also "MUST send a WWW-Authenticate header field"; these toys skip it.)
  • 403 Forbidden means "the server understood the request but refuses to fulfill it": we know who you are, and the answer is no.
  • 404 Not Found is allowed when the server "is not willing to disclose that one exists". That's why the safe route says 404 rather than 403: a 403 would confirm that ana's orders exist.
A real A10 bug, found while writing this lesson. The first Java version of Idor.java looked up the token with TOKENS.get(ex.getRequestHeaders().getFirst("X-Token")). With no header, that's get(null). TOKENS was a Map.of(…), and those maps "disallow null keys" (Map docs), so the lookup threw inside the handler. The server never sent a response; it just closed the connection, and the client saw: 
ben reads his own (safe):    200 ["laptop"]
Exception in thread "main" java.io.IOException: HTTP/1.1 header parser received no bytes
	at java.net.http/jdk.internal.net.http.HttpClientImpl.send(HttpClientImpl.java:1059)
	…
Caused by: java.io.EOFException: EOF reached while reading
The Kotlin version worked, because mapOf with several pairs returns a LinkedHashMap, which allows get(null). The fix is the explicit null check now in Idor.java. The lesson: an unexpected exception in a security check must still produce a clean deny, never a crash or, worse, an allow. That's "failing open", CWE-636 in A10:2025.

Four more, briefly

  • Secrets in code. An API key in source ends up in every clone and in git history forever: git log -p (L1, L12) shows deleted lines too, so removing it in a later commit doesn't help. Read secrets from environment variables or a secrets manager, and rotate any key that was ever committed. OWASP's Secrets Management Cheat Sheet describes secrets "hardcoded within the source code in plaintext" as the common problem.
  • Vulnerable dependencies (A03). Know what you ship: ./gradlew dependencies (L25) shows the full transitive tree. Scanners such as OWASP Dependency-Check match it against known vulnerabilities, and Gradle's dependency verification pins checksums, so a tampered jar fails the build: Part 1's integrity idea, automated.
  • Verbose errors (A02, A10). A stack trace in a response tells an attacker your libraries, versions and sometimes your SQL. OWASP's Error Handling Cheat Sheet says to respond without "any content … that would reveal implementation details", pointing to Problem Details (L32, RFC 9457). Log the detail server-side.
  • Logging and alerting (A09). Log logins, failures and access-control denials (who, what, when; never passwords or tokens), and alert on bursts. A breach nobody notices goes on for months (Logging Cheat Sheet).

Bridge: Spring Security exists to handle password encoding and access rules, and on Android, "Starting with Android 9 (API level 28), cleartext support is disabled by default", so plain http:// requests fail unless the app opts in (Network security configuration). These defaults exist because of the bugs above, and every one can be switched off or misused. Now you know what they protect against.

What Kotlin does for you.
  • use { } closes the Statement, ResultSet and Connection in the right order (L10), which matters on a server that runs for months. Java's try-with-resources does the same, but with more ceremony.
  • buildList { while (rs.next()) add(…) } collects JDBC results without a mutable temporary.
  • Early returns read naturally: tokens[…] ?: return reply(ex, 401, …) combines the lookup and the deny into one line.
  • What Kotlin does not do: escape anything. A string template is concatenation, so SQL, shell and HTML injection are exactly as easy in Kotlin as in Java.

Check

Why does a PreparedStatement stop SQL injection?

The SQL text is fixed with ? placeholders before any input exists. Values travel separately and are never parsed as SQL. OWASP marks manual escaping "STRONGLY DISCOURAGED".

Ben is logged in and requests /users/ana/orders. The fixed server should answer…

He's authenticated, so not 401. He's not the owner, so not 200. 403 would also be correct, but RFC 9110 lets 404 hide whether the resource exists at all, which is what the toy does.

Which character must your hand-written escape chain replace first?

Every other replacement inserts an &. Escape & afterwards and &lt; becomes &amp;lt;, which displays wrongly.

An API key was committed, then deleted in the next commit. What should you do?

History keeps it: git log -p shows the deleted line to anyone with a clone. Treat the key as leaked, revoke it, issue a new one, and load it from the environment.

Java: Map.of("tok-ana", "ana").get(null)

Map.of maps disallow nulls, and get(null) throws NullPointerException; jshell shows it coming from ImmutableCollections$Map1.get. A HashMap or Kotlin's mapOf with several pairs would return null.

Review and fix a notes service

Below is a small notes service: HttpServer plus H2, listening only on 127.0.0.1. It works, and it has six planted security flaws. This is a code review, the same job you'll do on AI-written diffs.

  1. Find all six flaws, using this checklist: How are passwords stored? How is SQL built? Is user data escaped before it goes into HTML? Does every read check who owns the record? What does an error response contain? Are there secrets in the source?
  2. Prove each one before fixing it, with a curl repro or a grep. A fix you never saw fail isn't proven (L11's red-green loop, applied to security).

Wrap-up

Exit quiz, recall card, sources

~5 min

A login handler catches every exception and returns true so users aren't locked out by bugs. What's this called? (L10 + L33)

Any exception, including one an attacker can trigger, now grants access. Security checks must fail closed. OWASP lists "Not Failing Securely ('Failing Open')", CWE-636, under A10:2025.

Two threads call new SecureRandom().nextBytes(…) at the same time. Is that safe? (L26)

Nothing is shared, so there's no race: thread confinement from L26/L27. (A shared SecureRandom is also documented as thread-safe, but separate instances sidestep the question.)

PBKDF2 at 600,000 iterations took about 50 ms per hash. Why is that acceptable on a login path? (L16)

A user pays 50 ms once per login, which they won't notice. An attacker pays it for every guess, which turns 30 million guesses a second into about 18. A constant cost per operation is fine; it's the attacker who multiplies it by n.

Which HTTP header stops JavaScript reading a session cookie? (Part 3)

MDN: HttpOnly "Forbids JavaScript from accessing the cookie". It limits what an XSS bug can steal; it doesn't fix the XSS.
