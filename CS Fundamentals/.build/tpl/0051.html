The Limits of Computation

Some problems need only a fixed handful of states. Some need a tape. Some can't be solved by any program at all, and some can probably only be solved slowly. This lesson finds each boundary by building something that runs into it: a regex engine that beats the JDK's, a Turing machine, a program that defeats every halting checker, and a SAT solver that colours graphs.

Part 1

Finite automata

~20 min

Start with the most limited computer imaginable: a machine with a fixed, finite set of states and no other memory. It reads its input one character at a time, and each character moves it from one state to the next. When the input ends, it answers yes if it's in an accepting state. Jeff Erickson's notes: "Finite-state machines are also known as deterministic finite-state automata, abbreviated DFAs. The word 'deterministic' means that the behavior of the machine is completely determined by the input string" (Erickson, Models of Computation: Finite-state automata). Russ Cox puts it the same way: it's a DFA "because in any state, each possible input letter leads to at most one new state" (Cox, "Regular Expression Matching Can Be Simple And Fast").

A DFA that knows if a binary number is divisible by 3

Read a binary number from the left. Each new bit b turns the value v into 2v + b. So you don't need the value at all, only its remainder mod 3: the remainder r becomes (2r + b) mod 3 (L48's modular arithmetic). Three remainders, three states. Erickson builds the same machine for multiples of 5 with "transition function: δ(q, a) = (2q + a) mod 5".

110 (6): R0 -> R1 -> R0 -> R0  accept=true
1001 (9): R0 -> R1 -> R2 -> R1 -> R0  accept=true
111 (7): R0 -> R1 -> R0 -> R1  accept=false
checked 131070 strings, 0 disagreements
1,000,000-bit number: dfa=false BigInteger=false

Both languages print the same thing. Two things to notice. The DFA agrees with real arithmetic on all 131,070 bit strings up to 16 bits long. And it judged a million-bit number using one variable: the memory doesn't grow with the input, which is the whole definition of "finite". The states carry no data, so an enum (L7) fits, and the compiler still checks that the when/switch covers every state.

Nondeterminism: being in several states at once

An NFA (nondeterministic finite automaton) relaxes one rule: a state may have several arrows for the same character, or none, and it may have ε-arrows that it can follow without reading anything. Think of it as guessing. The NFA accepts if some sequence of guesses ends in an accepting state.

Here's a language where guessing helps: "strings of as and bs whose third symbol from the end is a". The NFA waits in state 0, and on every a it may guess "this is the one" and move to state 1. Exactly two more symbols must follow. You can't run a guess on a real computer, so you track the set of states the guesses could have reached. With at most 32 states, an Int's bits make a fine set (L48):

babb: {0} -b-> {0} -a-> {0,1} -b-> {0,2} -b-> {0,3}  accept=true
abab: {0} -a-> {0,1} -b-> {0,2} -a-> {0,1,3} -b-> {0,2}  accept=false

 2           3           4

Any NFA can be turned into a DFA. Cox: "Any NFA can be converted into an equivalent DFA in which each DFA state corresponds to a list of NFA states." That's the subset construction, and dfaStatesNeeded runs it: a BFS (L21) over sets of NFA states. The table is the catch. The NFA grows by one state per step of k, while the DFA doubles: 4,096 states for k = 12. Nondeterminism adds no power (both recognise the same languages), but it can be exponentially more compact. That's why regex engines run NFAs directly, as Part 2 does, instead of converting them first.

Why no smaller DFA exists Optional deep dive

The table shows the subset construction makes 2k states, but could a cleverer DFA use fewer? No. Take any two different strings x and y of length k. They differ at some position p; say x has a there and y has b. Append any p − 1 characters z. Then xz has length k + p − 1, and its k-th symbol from the end is at position p: an a for xz, a b for yz. A DFA must accept one and reject the other, so it must be in different states after reading x and after reading y. There are 2k strings of length k, pairwise like this, so every DFA for the language needs at least 2k states. Erickson calls such a set of strings a fooling set: "A fooling set for a language L is a set F of strings such that every pair of strings in F has a distinguishing suffix."

What Kotlin does for you.
  • s.runningFold(Rem.R0) { q, c -> step(q, c) } returns every intermediate state: the whole trace in one expression. Java builds the trace by hand in a loop with a StringBuilder.
  • states and (1 shl q) spells out bitwise operations as infix functions. Java's states & (1 << q) is shorter, but its precedence trap (== binds tighter than &) forces the extra parentheses you see in KthFromLast.java.
  • s.toInt(2) parses binary. Java writes Integer.parseInt(s, 2). Kotlin's padStart(len, '0') replaces Java's String.format plus replace trick.
  • ArrayDeque needs no import in Kotlin. The when over an enum and Java's arrow switch are both checked for exhaustiveness.

Part 2

What a regex really is

~25 min

A regular expression is a compact way to write down an NFA. Ken Thompson's 1968 construction turns any regex into one, piece by piece. Cox: "The NFA for a regular expression is built up from partial NFAs for each subexpression, with a different construction for each operator." A literal is one arrow, e? is a choice between e and an ε-arrow that skips it, e* adds a loop back, and e1|e2 adds a choice between two branches. The result is small: "the number of states in the final NFA is at most equal to the length of the original regular expression".

Here's a?a?aa, drawn with ε-arrows. Watch the state set on input aa. Before reading anything it's already in {0, 1, 2}, because both a?s may be skipped:

Two ways to run the same NFA

  • Backtracking: follow one choice at a time, and when you get stuck, go back and try the other choice: L50's backtracking, applied to regex. Cox: "This backtracking approach has a simple recursive implementation but can read the input string many times before succeeding. If the string does not match, the machine must try all possible execution paths before giving up." With n choices that's up to 2n paths.
  • State sets (Thompson's simulation): exactly what KthFromLast did. Cox: "The efficiency comes from tracking the set of reachable states but not which paths were used to reach them. In an NFA with n nodes, there can only be n reachable states at any step, but there might be 2n paths through the NFA."

java.util.regex backtracks, and so does Kotlin's Regex on the JVM, which wraps a java.util.regex.Pattern (it even has toPattern(); Kotlin Regex). Cox: "Java uses a backtracking implementation too. In fact, the java.util.regex interface requires a backtracking implementation, because arbitrary Java code can be substituted into the matching path." Backtracking is what makes features like backreferences (\1) possible, and it has a price. Let's measure it:

(\w+\s?)*             n=16 no       0 ms  n=20 no       0 ms  n=24 no       0 ms  n=28 no       0 ms
(['"])(\w+\s?)*\1     n=16 no       7 ms  n=20 no      15 ms  n=24 no     244 ms  n=28 no    3928 ms
(\w+\s?){1,30}        n=16 no       0 ms  n=20 no      12 ms  n=24 no     207 ms  n=28 no    3314 ms
a?{n}a{n}             n=16 yes      2 ms  n=20 yes     15 ms  n=24 yes    287 ms  n=28 yes   4840 ms

That's Kotlin; Java's run gave the same pattern of numbers (3.0, 2.7 and 4.2 s at n = 28). Three of the four rows multiply by about 16 every time n grows by 4: that's 2n, the signature of trying every path. One extra letter doubles the time, so n = 40 would take hours.

  • Row 1 is the surprise. (\w+\s?)* on a run of letters is a textbook catastrophe: "abcd" can be split into words in 2n−1 ways. OWASP lists (a+)+$, ([a-zA-Z]+)*$ and friends as examples of an "Evil Regex", one that "can get stuck on crafted input" (OWASP: ReDoS). On JDK 26 it takes 0 ms. Why? The JDK's Pattern.java remembers positions where a greedy loop already failed: "Optimize the greedy Loop to prevent exponential backtracking, IF there is no group ref in this pattern" (OpenJDK source, Pattern.java). That code is in the JDK 9 release source and absent from JDK 8u's. It's an implementation detail, not a guarantee.
  • Row 2 adds a backreference to match the same quote at both ends, and the safety net switches off. The source says so: "Turn off the stop-exponential-backtracking optimization if there is a group ref in the pattern."
  • Row 3 bounds the repetition with {1,30}, and the memo didn't save it either (measured). Row 4 is Cox's pathological pattern a?ⁿaⁿ, which has no loop at all to memoise.

This isn't a lab curiosity. In July 2019 Cloudflare's network went down for 27 minutes: "The CPU exhaustion was caused by a single WAF rule that contained a poorly written regular expression that ended up creating excessive backtracking" (Cloudflare: outage of July 2, 2019).

At n = 28: well under a millisecond, against 4.2–4.8 seconds for the backtracker. Here the pattern grows with n too, so the cost is O(m × n) = O(n²): doubling n roughly quadruples the time (with the usual small-number noise, L16). Cox: "For a regular expression of length m run on text of length n, the Thompson NFA requires O(mn) time." Go's standard library chose this design, and promises it: "The regexp implementation provided by this package is guaranteed to run in time linear in the size of the input" (Go: package regexp).

Why doesn't everyone do this? Backreferences. A backreference such as \1 needs to remember what a group matched, which a finite set of states can't do. Cox: "no one knows how to implement regular expressions with backreferences efficiently, though no one can prove that it's impossible either. (Specifically, the problem is NP-complete…)". You'll meet NP-complete in Part 4.

Bridge to Spring and Android. Any regex you run on input you don't control (a request parameter, a JSON field, text typed into an Android form) is a possible denial-of-service. Keep validation patterns unambiguous, cap input length before matching, and treat a pattern with a backreference or a bounded repeat over a repeated group as a code-review red flag (L40).
What Kotlin does for you.
  • Raw strings: Regex("""(['"])(\w+\s?)*\1""") is the pattern exactly as you'd read it. Java needs "(['\"])(\\w+\\s?)*\\1", with every backslash doubled and the quote escaped (L2).
  • Regex.matches(input) is a whole-string match, the same as Java's matcher(input).matches(). Kotlin's containsMatchIn is Java's find().
  • measureTime { … } returns a Duration (L16). Java subtracts two System.nanoTime() readings.
  • Default arguments: nfa.add(CHAR, 'a', next) leaves o2 at -1. Java must pass all four arguments every time.
  • There's no engine difference to discover: on the JVM, both languages run the same java.util.regex code.
Exercise: defuse an evil regex

Row 2's pattern, (['"])(\w+\s?)*\1, accepts a quoted phrase: the same quote at both ends, words separated by single spaces. Write two replacements that accept exactly the same strings but don't backtrack exponentially:

  1. a possessive quantifier, *+, which never gives back what the loop matched (Pattern docs: "Possessive quantifiers");
  2. an unambiguous rewrite, where each input can be split into words in only one way.

Prove "the same strings" by comparing all three on every string up to length 7 over the alphabet a, space, ", ', !. Then time them on the evil input.

Solution 
all three agree on 97655 strings
(['"])(\w+\s?)*\1             n=20     11 ms  n=24    185 ms  n=28   3127 ms
(['"])(\w+\s?)*+\1            n=20      0 ms  n=24      0 ms  n=28      0 ms
(['"])(\w+(\s\w+)*\s?)?\1     n=20      0 ms  n=24      0 ms  n=28      0 ms

Java prints the same agreement count and the same shape (3.8 s for the evil one at n = 28). The possessive version is safe here because the loop can only ever consume word characters and spaces, and the thing that must come next is a quote, which the loop never took. Giving characters back could never help. The rewrite is safe for a different reason: after the first word, every \s must be followed by a new \w+, so there's only one way to split any input. Agreement on 97,655 strings isn't a proof, but it's strong evidence that costs one loop to get.

Why can't a state-set engine support backreferences like (a+)b\1?

A finite set of states can't store an arbitrary string to compare against later. Cox notes that matching with backreferences is NP-complete.

Part 3

Turing machines and the halting problem

~25 min

A DFA can't count. Try to recognise 0n1n (some zeros followed by the same number of ones) with k states. Feed it k + 1 prefixes 00, 01, …, 0k. By the pigeonhole principle (L48), two of them, 0i and 0j, end in the same state. From then on the DFA can't tell them apart, so it gives 0i1i (in the language) and 0j1i (not in it) the same verdict, and it's wrong about one. The exercise below turns that argument into code that fools any DFA you hand it.

Add a tape: the Turing machine

Alan Turing's 1936 paper "On Computable Numbers, with an Application to the Entscheidungsproblem" gave the machine one more thing. Erickson: "Turing described an abstract machine with a finite number of internal states that has access to 'memory' in the form of a tape." The machine reads the symbol under its head, then writes a symbol, moves one cell left or right, and changes state, all according to a finite table. That's it:

increment 1011: accept after 8 steps, tape=1100
increment 111: accept after 8 steps, tape=1000
increment 0: accept after 3 steps, tape=1
0^n1^n "": accept after 1 steps, tape=
0^n1^n "01": accept after 5 steps, tape=XY
0^n1^n "0011": accept after 13 steps, tape=XXYY
0^n1^n "000111": accept after 25 steps, tape=XXXYYY
0^n1^n "0010": reject after 8 steps
0^n1^n "011": reject after 4 steps
0^n1^n "10": reject after 0 steps
0^n1^n n=10: 221 steps
0^n1^n n=100: 20201 steps
0^n1^n n=1000: 2002001 steps
forever: still running after 1000000 steps
  • The tape fixes counting. The 0n1n machine crosses off one 0 (as X) and one matching 1 (as Y), walks back, and repeats. It needed 2n² + n + 1 steps: O(n²), slow but correct for every n. Exactly the same output in both languages.
  • This simple model is as powerful as Kotlin. Your Kotlin program simulates any Turing machine (you just wrote one), and a Turing machine can simulate any program you can write, given enough tape. The claim that nothing reasonable computes more is the Church–Turing thesis (Erickson's Turing machines notes tell the history). So "no Turing machine can do X" means "no program can do X".
  • Look at the last line. After a million steps, is forever stuck, or about to finish? Running a program can only ever tell you "it halted" or "not yet".

The halting problem

Erickson: "Turing's canonical example of an undecidable problem was the halting problem, which asks whether a given Turing machine halts when given a particular input string" (Erickson: Undecidability). Suppose someone hands you a decider: a function that, for every program, always answers, and answers correctly, whether it halts. Here's a program built to make it wrong. It asks the decider about itself, then does the opposite:

always says halts        says halts                               actually: still running after 10,000,000 steps
always says loops        says loops                               actually: halts
guesses from hashCode    says loops                               actually: halts
runs it for 1,000 steps  says never answers (StackOverflowError)  actually: can't even start: it asks d first
always says halts        says halts                               actually: still running after 10,000,000 steps
always says loops        says loops                               actually: halts
guesses from hashCode    says halts                               actually: still running after 10,000,000 steps
runs it for 1,000 steps  says never answers (StackOverflowError)  actually: can't even start: it asks d first

Kotlin on the left, Java on the right. The hashCode decider's verdict changes from run to run, because identity hash codes do, but it's wrong every time. The "smart" decider that simulates the program never answers at all: to simulate the contrarian, it must simulate itself simulating the contrarian, and so on until the stack runs out. A decider that doesn't answer has failed too.

The proof, for every possible decider. Let d be any decider that always answers, and let p = contrarian(d). If d says p halts, then p runs while (true) and never halts, so d is wrong. If d says p loops, then p returns at once and halts, so d is wrong again. Either way d is wrong about p, so no correct, always-answering decider exists. The four runs above aren't the proof; they're the proof applied to four particular deciders. Erickson calls Turing's argument "an avatar of the famous diagonalization argument that uncountable sets exist, published by Georg Cantor in 1891".

It isn't only contrived programs. Take this four-line loop: "halve n if it's even, otherwise make it 3n + 1, until n is 1". Nobody can prove it stops for every starting value: "At present the 3x+1 Conjecture remains unsolved" (Lagarias, "The 3x+1 problem: An annotated bibliography").

Rice's theorem: why your tools must guess

Erickson again: "In 1953, Henry Rice proved the following extremely powerful theorem, which essentially states that every interesting question about the language accepted by a Turing machine is undecidable." "Does this method ever return null?", "is this variable always initialised?", "is this code reachable?": a tool can't answer any question like that exactly for every program. So compilers and linters approximate, and they choose to be safe. Here's a correct program both compilers reject:

Definite.kt:4:12: error: variable 'x' must be initialized.
    return x
           ^
Definite.java:5: error: variable x might not have been initialized
        return x;
               ^
1 error

n == n is always true for an Int, so x is always assigned, but the checker doesn't evaluate values. The JLS states the rule directly: apart from &&, ||, ? : and constant expressions, "the values of expressions are not taken into account in the flow analysis" (JLS ch. 16, Definite Assignment). Rejecting a few correct programs is the price of never accepting an incorrect one. The same trade-off is behind every IntelliJ warning that says "might be null" when you know it can't be.

What Kotlin does for you.
  • sealed interface Outcome with nested data classes: three result shapes, each carrying its own data, in seven lines. Java needs a permits list and three records, and its switch binds each case with a type pattern, case Accepted a -> (JEP 441).
  • fun interface Program lets a lambda be a Program, like Java's @FunctionalInterface. contrarian uses an object : Program expression instead, because it needs this to mean "the program itself". Java's anonymous class works the same way.
  • tape[head] ?: BLANK turns a missing cell into a blank. Java writes tape.getOrDefault(head, BLANK).
  • RuntimeException(null, null, false, false) skips filling in a stack trace in both languages. Kotlin can call that protected constructor directly from a subclass's supertype call, just as Java's super(...) does.

A bigger DFA only pushes the failure further out: one more state than its counter can hold. Erickson's notes make this argument formal as fooling sets, and conclude that 0n1n is not a regular language. No regex without backreferences can match balanced parentheses for the same reason, which is why the final uses a recursive-descent parser, not a regex, to read regex syntax with nested parentheses.

Check

What does a Turing machine have that a DFA doesn't?

Unbounded memory it can read, write and move over. That's what lets it count the zeros in 0n1n.

A decider says contrarian(d) halts. What does contrarian(d) actually do?

It does the opposite of the verdict: told "halts", it runs while (true). So the decider is wrong, and that works against every decider.

Why can't you decide halting by running the program with a big step budget?

A program still running after a million steps might finish at a million and one. A budget can confirm halting but can never confirm looping.

Java: int x; if (n == n) x = 1; return x;

Definite assignment ignores values (JLS ch. 16), so the compiler can't see that n == n is always true: "variable x might not have been initialized". Rice's theorem is why such checkers must be conservative.

Part 4

P, NP and NP-completeness

~20 min

Part 3 was about what can be computed at all. This part is about what can be computed fast, meaning in polynomial time: O(nc) for some constant c. Erickson's definitions, from the chapter "NP-Hardness" (Erickson, Algorithms, ch. 12):

  • "P is the set of decision problems that can be solved in polynomial time. Intuitively, P is the set of problems that can be solved quickly."
  • "NP is the set of decision problems with the following property: If the answer is Yes, then there is a proof of this fact that can be checked in polynomial time."
  • "Every decision problem in P is also in NP." Whether P = NP is the open question. The Clay Mathematics Institute put it in one line: "If it is easy to check that a solution to a problem is correct, is it also easy to solve the problem?" It's one of their Millennium Prize Problems (Clay: P vs NP).

Checking vs finding: SAT

The classic NP problem is satisfiability (SAT). You're given a formula in conjunctive normal form, an AND of clauses where each clause is an OR of variables or their negations. Is there a true/false assignment that makes every clause true? Checking a proposed assignment means one pass over the formula. Finding one, as far as anyone knows, can take trying them all:

NP-complete: the hardest problems in NP

  • NP-hard: "A problem Π is NP-hard if a polynomial-time algorithm for Π would imply a polynomial-time algorithm for every problem in NP."
  • NP-complete: "a problem is NP-complete if it is both NP-hard and an element of NP … Informally, NP-complete problems are the hardest problems in NP." The first one was found by Stephen Cook and, independently, Leonid Levin: "The Cook-Levin Theorem. Circuit satisfiability is NP-hard." SAT is NP-complete too.
  • Reductions connect them. A reduction is a fast translation from instances of problem A into instances of problem B that preserves the yes/no answer, so a solver for B also solves A. Erickson's rule: "To prove that problem A is NP-hard, reduce a known NP-hard problem to A."

Here's a reduction you can run: graph 3-colouring → SAT. Variable x(v, c) means "vertex v gets colour c". Each vertex gets at least one colour, at most one colour, and neighbours never share one. The formula has 3V variables and 4V + 3E clauses: polynomial, so the translation itself is fast. The solver is L50's backtracking, pruning a branch as soon as a clause is all false:

wheel, 5-cycle rim   V= 6 E=10 -> 18 vars,  54 clauses: UNSAT, so no 3-colouring (223 nodes)
wheel, 6-cycle rim   V= 7 E=12 -> 21 vars,  64 clauses: SAT 0121212 proper=true (36 nodes)
Petersen graph       V=10 E=15 -> 30 vars,  85 clauses: SAT 0101210221 proper=true (51 nodes)

Why it's correct, both ways. If the graph has a proper 3-colouring, set x(v, c) true exactly when v has colour c; every clause is then true. If some assignment satisfies every clause, each vertex has exactly one true x(v, c), which gives a colouring, and the edge clauses make it proper. So the formula is satisfiable exactly when the graph is 3-colourable. Notice the direction: this uses SAT to solve colouring, which shows that SAT is at least as hard as colouring. Erickson's chapter goes the other way, translating 3SAT into colouring, to prove colouring NP-hard. Both are NP-complete, so each can be translated into the other. In practice that's why industrial SAT solvers are such useful tools: translate your problem into clauses and hand it over.

What to do when your problem is NP-hard

The travelling salesman problem "asks to find the shortest Hamiltonian cycle (or path) in a graph with weighted edges", and it's NP-hard (Erickson ch. 12). It's an optimisation problem, not a yes/no one, but it's at least as hard as the NP-complete question "is there a tour shorter than L?". NP-hard doesn't mean give up. It means pick a strategy:

  1. Small n: solve it exactly. The exact search prunes any partial tour already longer than the best found (branch and bound), so it visits far fewer than (n − 1)! tours. It still grows about 3–4× per extra city: 3.7 s at 15 cities, and it would take days at 25.
  2. Special structure: dynamic programming. Some NP-hard problems have a DP whose cost depends on the size of the numbers in the input. The exercise shows it for knapsack.
  3. Heuristics. Nearest neighbour handles 10,000 cities in half a second, and on these small cases it came within 0–37% of optimal. In general it comes with no guarantee.
  4. Hand it to a solver. Reduce to SAT (or another well-studied problem) and use a tool someone has spent decades tuning.

Exercise: knapsack, fast or hopeless

0/1 knapsack: given items with weights and values, choose a subset with total weight ≤ the capacity and maximum value. From a blank file, write a brute force over all 2n subsets (bit masks, L48) and the L21 DP over capacities, then compare them on 24 random items with capacity 500. Then answer: what happens to the DP if the same weights are written in milligrams instead of kilograms?

Solution 
n=24 cap=500  brute force=771 in 553 ms (2^24 = 16777216 subsets)
n=24 cap=500  dp=771 in 195 µs (12024 updates at most)
weights x 1,000,000: the dp needs up to 12000000024 updates and a 2000 MB array

The DP costs O(n × W), which looks polynomial, but W is a number, and writing it takes only log W digits (L48). Multiply every weight by a million and the input grows by a few characters while the DP grows a million-fold. Erickson: "Algorithms like this are said to run in pseudo-polynomial time, and any NP-hard problem with such an algorithm is called weakly NP-hard." Knapsack is NP-hard because subset sum, which Erickson's chapter proves NP-hard, is the special case where every value equals its weight. The downTo loop (high to low) is what keeps each item to one use; low to high would let an item be added again.

Check

What puts SAT in NP?

NP means a Yes answer has a proof that can be checked in polynomial time. For SAT the proof is the assignment, checked in one pass: 3 µs above.

You want to prove your new problem A is NP-hard. You should…

Erickson's rule: "reduce a known NP-hard problem to A". If A were easy, SAT would then be easy too. Reducing A to SAT only shows that A is no harder than SAT.

The colouring reduction for a graph with V vertices and E edges produces how many clauses?

Per vertex: 1 "at least one" + 3 "at most one" clauses. Per edge: 3, one per colour. Polynomial size is what makes it a valid reduction.

Knapsack's DP runs in O(n·W). Why doesn't that make knapsack polynomial?

Input size counts the digits of W, about log W, but the table has W columns: exponential in the number of digits. That's pseudo-polynomial.

Final exercise: a regex engine of your own

~25 min
Final: TinyRegex, test-first

Build TinyRegex(pattern).matches(input) in a fresh gradle init project per language. It supports literals, ., *, +, ?, |, parentheses and \ escapes, with whole-string matching like matches(). It must stay linear in the input on patterns that defeat backtracking. Three pieces, in order:

  1. Parser (recursive descent, L18): text → a sealed syntax tree (L7). Use one function per grammar rule: 
    alt    := concat ('|' concat)*
concat := repeat*
repeat := atom ('*' | '+' | '?')?
atom   := '(' alt ')' | '.' | '\' char | other char
    Reject malformed patterns ((ab, ab), *a, a**, a trailing \, and the unsupported [ ] { } ^ $) with IllegalArgumentException.
  2. Thompson's construction: tree → NFA. Each node becomes a fragment with one entry state and one ε-state whose exit is still unconnected. For example, e* is a split state that goes either into e or out, with e's exit wired back to the split.
  3. Simulation: Part 2's state sets, with an explicit stack for the ε-closure so that deeply nested stars can't overflow the call stack (L4).

Tests to write, in this order: a literal matches the whole input only → . matches one character → *, +, ? → | has the lowest precedence and parentheses group → the empty pattern and empty branches (a|) → escapes → malformed patterns are rejected → differential: 2,000 random patterns over a, b, . with operators, 25 random inputs each, compared with java.util.regex → the pathological patterns from Part 2 finish in under a second → ((a*)*)* on 50,000 as doesn't overflow.

./gradlew run then races your engine against the JDK's. My Kotlin run:

Precedence falls out of the grammar: alt calls concat, which calls repeat, so | binds loosest and * tightest. ab|cd parses as (ab)|(cd), and ab* as a(b*). A real bug, found by the differential test. My first Java draft wrote out1[b.end()] = add(SPLIT, …). All the hand-written tests passed, and then the random test crashed:

TinyRegexTest > agreesWithJavaUtilRegexOnThousandsOfRandomCases() FAILED
    java.lang.ArrayIndexOutOfBoundsException: Index -1 out of bounds for length 17
        at katas.TinyRegex.addWithClosure(TinyRegex.java:100)

The smallest trigger is abcdefgh: 8 letters make 16 states, so adding the MATCH state is exactly the call that grows the arrays from 16 to 32. Java evaluates an array assignment left to right. "First, the array reference subexpression of the left-hand operand array access expression is evaluated", then the index, and only then "the right-hand operand is evaluated" (JLS §15.26.1). So the store went into the old 16-slot array, which add had just replaced, and the new array's slot kept its -1, meaning "not connected". The fix is to call add first, then assign: the two-line form you see above. The Kotlin version can't hit this, because its out1 is an ArrayList whose object stays the same as it grows. Seven letters never crashed, and the hand-written tests only used short patterns.

Exit quiz, recall card, sources

~5 min

A doubling experiment shows each doubling of n multiplies the time by about 4. The algorithm is probably… (L16)

T(2n)/T(n) ≈ 2b for T(n) ≈ a·nb, and a ratio of 4 means b = 2. Exponential growth looks different: adding a constant to n multiplies the time, as in Part 2's ×16 per +4.

Why must a hash table with more keys than buckets have collisions? (L19, L48)

More pigeons than holes means some hole holds two. The same principle fooled every DFA in Part 3.

Merge sort's worst case is… (L18)

log n levels of halving, with O(n) merging work per level, whatever the input order. Sorting is firmly in P.

An IntelliJ inspection warns "might be null" about a value you know is never null. That's because… (Part 3)

By Rice's theorem, no tool can answer such questions exactly for every program, so tools approximate on the safe side and sometimes flag correct code.

Backtracking that lists every subset of 30 items examines about how many? (L50)

230 ≈ 1.07 × 109. That's the same wall the SAT brute force hit, and why exponential algorithms stop scaling somewhere in the 30s.
