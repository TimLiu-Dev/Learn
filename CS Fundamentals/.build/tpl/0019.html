Warm-up

Recall from L5, L7, L16 and L18

~10 min
From memory: no peeking
  1. Write contains(list, x) by hand for an unsorted list, and say its Big O. Then say what binary search needs before it can do better. (L16, L18)

Binary search finds an item among a million in about 20 steps. What does it require? (L18)

Each comparison throws away half of a sorted range, so it's O(log n). Hashing aims lower still, at O(1), and doesn't need sorting at all.

What's the cost of list.contains(x) on an unsorted ArrayList of n items? (L16)

It checks the elements one by one with equals. In the worst case that's all n of them. A hash table skips straight to the one place the item could be.

A Java class overrides equals but not hashCode. You add two equal objects to a HashSet. What's its size? (L7)

Different identity hash codes send the two "equal" objects to different buckets, so the set never compares them. Part 3 shows exactly why.

An ArrayList doubles its array when full. Why is add still "amortised O(1)"? (L16)

A copy of n elements happens only after about n cheap adds, so the average cost per add stays constant. Hash tables resize with the same trick.

Kotlin: val a = Point(1, 2); val b = Point(1, 2) (a data class). What does a === b give? (L5)

=== is identity: two separate objects. a == b is true, because the data class's equals compares values. A hash map needs value equality, not identity.

Part 1

Hashing and collisions

~25 min

An array gives you O(1) access, but only by a number: items[5]. A hash table extends that to any key. It turns the key into a number, uses the number as an array index, and stores the entry in that slot, called a bucket:

StepWhat happensExample
1 · hashkey.hashCode() turns the key into an Int"cat" → 98262
2 · indexsqueeze that number into 0 until capacity98262 mod 16 → 6
3 · bucketlook in that one bucket and compare keys with equalsbuckets[6]

If the hash spreads keys evenly, each bucket holds about one entry, and lookups cost O(1) on average no matter how big the table gets. Sedgewick and Wayne call this the uniform hashing assumption: "the hash function that we use uniformly distributes keys among the integer values between 0 and M−1" (Algorithms §3.4: Hash Tables).

Where hash codes come from

The JDK specifies String.hashCode exactly: "s[0]*31^(n-1) + s[1]*31^(n-2) + ... + s[n-1] using int arithmetic" (JDK docs: String.hashCode). So you can compute one by hand:

by hand: 98262  built-in: 98262
c*31^2 + a*31 + t = 98262
banana: -1396355227
Aa=2112 BB=2112
true
Point(1, 2): 33
by hand: 98262  built-in: 98262
c*31^2 + a*31 + t = 98262
banana: -1396355227
Aa=2112 BB=2112
true
Pixel(1, 2): 994
  • It's just arithmetic on the characters. 'c' is 99, 'a' is 97 and 't' is 116, so 99·31² + 97·31 + 116 = 98262.
  • Overflow is fine. Longer strings overflow Int and wrap around (L2), so "banana" gets a negative hash. That's legal, and it matters in a moment.
  • Different keys can share a hash. "Aa" and "BB" both give 2112. There are only about 4 billion Ints, and infinitely many strings.
  • Your own classes: Kotlin data classes and Java records generate hashCode from their fields (Kotlin docs: Data classes, JEP 395). In a plain Java class you write it yourself, usually with Objects.hash(x, y), which combines the fields' hashes "as if all the input values were placed into an array" and hashed with Arrays.hashCode (JDK docs: Objects.hash). The exact numbers differ, which is fine: they only need to be consistent with equals.

From hash code to index, and the negative trap

h          = -1396355227
h % 16     = -11

  • % keeps the sign of the left side. Kotlin's rem result "has the same sign as the dividend" (Kotlin API: rem), and Java's % behaves the same. A negative hash gives a negative index, and the program crashes.
  • Use floor modulus instead. Kotlin's mod result "has the same sign as the divisor" (Kotlin API: mod), and so does Java's Math.floorMod (JDK docs). With a positive capacity you always get 0 until capacity. Sedgewick's code does it a third way, masking off the sign bit: (key.hashCode() & 0x7fffffff) % M.
  • Powers of two allow a shortcut. When the capacity is 2ᵏ, h & (capacity − 1) keeps the low k bits, which is the same as floor mod but cheaper.
  • What HashMap really does (implementation detail, not a guarantee): its capacity is always a power of two, and before masking it mixes the high bits into the low ones with (h = key.hashCode()) ^ (h >>> 16). Otherwise "sets of hashes that vary only in bits above the current mask will always collide" (OpenJDK source: HashMap.hash). That's the spread line above.

Collisions are guaranteed, and sooner than you think

Two different keys landing in the same bucket is a collision. With more keys than buckets it's unavoidable: that's the pigeonhole principle. But it happens long before the table is full. With 23 people and 365 birthdays, there's already a 50% chance that two of them share one, which is the "birthday paradox" from Sedgewick's §3.4 exercises:

23 people, 365 days: shared birthday in 50.665% of trials
exact: 50.7%
1,000,000 buckets: first collision after ~1266 keys on average

Even a million buckets get their first collision after only about 1,266 random keys, close to the classic birthday-problem estimate √(πM/2) ≈ 1,253. Both programs print identical numbers because they share java.util.Random(42). So every hash table needs a plan for collisions, and there are two classic ones (Algorithms §3.4):

chaining:
  [2] [10, 18, 26]
  [3] [3, 11]
linear probing:
  put 10: home 2, landed in 2 after 1 probe(s)
  put 18: home 2, landed in 3 after 2 probe(s)
  put 3: home 3, landed in 4 after 2 probe(s)
  put 26: home 2, landed in 5 after 4 probe(s)
  put 11: home 3, landed in 6 after 4 probe(s)
  _ _ 10 18 3 26 11 _
  • Separate chaining: each bucket holds a linked list of every entry that hashed there (L17's nodes). A lookup walks one short chain. This is what HashMap uses, and what you'll build.
  • Open addressing / linear probing: one entry per slot. If the slot is taken, try the next one, wrapping around. There are no node objects, but neighbouring keys pile into clusters. Look at 3: it never collided with an equal hash, yet it was pushed out of its home slot by 18. Deleting is also tricky, since an empty hole would break later searches.

Load factor and resizing

The load factor is size / capacity: entries per bucket. With chaining, the average chain length is the load factor, so to keep lookups O(1) the table must grow as it fills. HashMap's docs: "When the number of entries in the hash table exceeds the product of the load factor and the current capacity, the hash table is rehashed… so that the hash table has approximately twice the number of buckets." The no-argument constructor uses "the default initial capacity (16) and the default load factor (0.75)", which "offers a good tradeoff between time and space costs" (JDK docs: HashMap). Every key must be rehashed, because its index depends on the capacity. That's an O(n) copy, but like L16's dynamic array it happens rarely enough to be amortised O(1).

Try it. This table works exactly like the MyHashMap you're about to build: Java's string hash, floor mod, new entries prepended to the chain, and doubling once the load factor passes 0.75. Press Next demo key seven times and watch the resize. Then tick constant hashCode, add five keys, and get the first one you added.

What Kotlin does for you.
  • data class writes hashCode (and equals) from the constructor properties. In a plain Java class you write Objects.hash(…) yourself, and records only cover immutable data.
  • Int.mod is a readable infix-style call: h.mod(16) vs Math.floorMod(h, 16). Both are floor modulus; both % operators are the dangerous one.
  • Kotlin has bitwise functions instead of symbols: and, xor and ushr for Java's &, ^ and >>>.
What's the same: both languages call the same String.hashCode on the JVM, and get the same numbers.

Check

Why must a hash table turn hashCode() into an index with floor mod rather than %?

"banana".hashCode() % 16 is −11, and indexing with it threw ArrayIndexOutOfBoundsException. Floor mod keeps the result in 0 until capacity.

"Aa".hashCode() == "BB".hashCode()

Both are 2112: 65·31 + 97 = 66·31 + 66. Equal hashes for unequal keys are allowed, which is why buckets must still compare keys with equals.

A default HashMap holds 12 entries. You add a 13th. What happens?

16 × 0.75 = 12. The 13th entry pushes the size past the threshold, so the table is rehashed to about twice the buckets (JDK docs).

In linear probing, what happens when a key's home slot is already taken?

That's the "probe". A linked list per bucket is separate chaining, the other strategy.

Build MyHashMap<K, V>

Time to build it yourself, with separate chaining. You already have every piece: L17's linked nodes for the chains, L16's growable array for the buckets, and L13's generics for K and V. Build it in the steps below, running a small main after each one. The reference solution is folded away at the end.

Exercise: MyHashMap in five steps, from a blank file
  1. The shape. A private Entry node holding key, a mutable value and next. An array of 8 buckets, each the head of a chain or null, plus a size. Java needs the L13 trick for a generic array: (Entry<K, V>[]) new Entry[8], with @SuppressWarnings("unchecked") on the smallest scope. Kotlin: arrayOfNulls<Entry<K, V>>(8).
  2. indexFor(key, capacity) using floor mod, and a private findEntry(key) that walks one chain comparing keys with equals (Kotlin ==).
  3. put(key, value). If the key exists, replace its value and return the old one. Otherwise prepend a new entry to the chain, which is O(1) with no walk to the tail, increment size and return null.
  4. get and containsKey, both one line on top of findEntry. In Kotlin, make them operator fun get/set so m["cat"] = 3 works.
  5. Resize. After an insert, if size > capacity * 0.75, allocate twice the buckets and move every entry to its new index. Reuse the nodes: just relink their next.

Then instrument it: add chainLengths(), put the keys key0 to key999, and print the capacity, the longest chain, and how many buckets have each chain length. Your main should print exactly this:

put six: size 6, capacity 8

Reference solutions

Both print identical output. The seventh put tips 7 > 8 × 0.75 = 6, so the table doubles to 16, matching what the widget showed. With 1000 keys in 2048 buckets the average chain is about 0.5 and the longest is 3: no lookup compares more than three keys. One honest note: the key0…key999 hashes are close together, which is exactly the kind of input HashMap's bit-spreading is for, so a real HashMap would spread them a little differently.

That worst case isn't theoretical. Part 3 triggers it on purpose. The real HashMap has a defence your version doesn't: when one bucket's chain reaches TREEIFY_THRESHOLD = 8 nodes (and the table has at least 64 buckets), it converts that chain into a red-black tree, the same structure as TreeMap (L20). That gives "worst-case O(log n) operations when keys either have distinct hashes or are orderable". Like the bit-spreading, this is an implementation detail from the OpenJDK source, not a promise in the API docs.

Check

Why does put prepend a new entry instead of appending it to the chain?

A singly linked list (L17) inserts at the head in O(1). put has already walked the chain to check for the key, but prepending keeps insertion simple. Real HashMap appends; either works.

During a resize, why can't you copy each chain to the same index in the bigger array?

The index is hash mod capacity. Change the capacity and most keys belong somewhere else; leave them in place and get would look in the wrong bucket.

Java: map.get("ghost") returns null on a HashMap<String, Integer>. What do you know?

HashMap allows null values, so only containsKey can tell the two apart (JDK docs).

What is the worst-case cost of get in your MyHashMap?

If every key lands in one bucket, get walks a chain of n entries. HashMap caps this at O(log n) for orderable keys by treeifying long chains.

Part 3

Why the equals/hashCode contract matters

~20 min

L7 stated the rule; now you know the machine it protects. Object.hashCode's contract says: "If two objects are equal according to the equals method, then calling the hashCode method on each of the two objects must produce the same integer result." It must also stay the same "provided no information used in equals comparisons on the object is modified." Unequal objects may share a hash, but "producing distinct integer results for unequal objects may improve the performance of hash tables" (JDK docs: Object.hashCode). Break each clause in turn and watch a map fail.

1 · equals without hashCode: the lookup goes to the wrong bucket

equal keys? true
price: null
fixed price: 45

Walk through it with your own findEntry. The stored key and the lookup key are equal, but each one inherited an identity-based hash, so indexFor sends the lookup to a different bucket. equals never even runs. (The real HashMap also stores each entry's hash and compares that first, so even a lucky same-bucket landing fails.) Effective Java Item 11: always override hashCode when you override equals.

2 · A key that changes after insertion: the entry is lost

before: 100
same object: null
old name: null
size 1, contents {Member(name=ada lovelace)=100}

The entry is still in the map, and it still prints, but it's filed under the bucket for "ada". Looking up the same object now hashes "ada lovelace" and goes to a different bucket. Looking up Member("ada") finds the right bucket, but equals fails. Nothing can reach that entry any more: it's a quiet memory leak. A data class with a var is the easy way to build this bug, because its generated hashCode reads the current field values.

Rule: use immutable keys. Kotlin data classes with only vals, Java records and Strings are ideal. One catch: a record holding a mutable List is only shallowly immutable (L7), so its hash still changes when the list does.

Bridge to Spring. A JPA entity whose hashCode uses a database id that's only assigned on save has exactly this bug: put it in a HashSet before saving and it gets lost afterwards. That's why persistence guides spend pages on entity equals/hashCode. The cause is the one you just saw.

3 · A legal but terrible hashCode: O(1) becomes O(n)

override fun hashCode() = 42 obeys the contract, since equal objects get equal hashes. It also puts every key in one bucket. Time it against your MyHashMap and the JDK's HashMap, with a doubling experiment (L16):

  • Good keys: under a millisecond at every size. That's O(1) per operation.
  • Constant hash, both maps: roughly ×4 each time n doubles. That's the signature of O(n²) total: n operations, each walking a chain of up to n keys.
  • Constant hash, but Comparable keys, in HashMap: fast again. Long chains were treeified, and with keys it can order, the tree search is O(log n). Without Comparable the tree can't use ordering, so it's no better than a list. Your map has no trees, so it's quadratic either way.

Measuring honestly: there are three warm-up rounds first, so the JIT compiler has optimised the code before the clock starts. Even so, single runs jitter by tens of percent. JMH (openjdk/jmh) is the professional tool, and it comes in L24. A doubling experiment is robust because it only looks at ratios.

What Kotlin does for you. A data class generates an equals and hashCode that always agree, from the same properties, and it regenerates both when you add a property. Java records do the same. In a plain Java class you keep two hand-written methods in sync by discipline alone, which is exactly how Isbn broke. What neither language can do is stop you writing var in a key class; that's still on you.

Which hashCode breaks the contract?

Two objects that are equal but differ in that ignored field would get different hashes. Constant hashes are legal, just slow.

You change a key's field (one used by hashCode) after putting it in a HashMap, then call get with the same object.

The new hash points to a different bucket, while the entry stays filed under the old one.

Constant-hash keys: doubling n multiplied the time by about 4. What does that tell you?

×4 per doubling means quadratic: n puts, each scanning a chain that grows with n.

Why stayed HashMap fast with constant-hash keys that were Comparable?

Chains of 8 or more become red-black trees, giving O(log n) search for keys it can order. That's an OpenJDK implementation detail.

The JDK's hash-based collections

~15 min

In real code you use the JDK's classes, never your own. But you now know what's inside them, and that changes how you choose between them.

HashMap:       [banana, apple, cherry, pear, kiwi, fig]
mutableMapOf:  [pear, apple, fig, kiwi, banana, cherry]
TreeMap:       [apple, banana, cherry, fig, kiwi, pear]
HashMap again: [cherry, kiwi, fig, apple, pear, banana]
java.util.LinkedHashMap
java.util.HashMap
java.util.LinkedHashSet
HashMap:       [banana, apple, cherry, pear, kiwi, fig]
LinkedHashMap: [pear, apple, fig, kiwi, banana, cherry]
TreeMap:       [apple, banana, cherry, fig, kiwi, pear]
HashMap again: [cherry, kiwi, fig, apple, pear, banana]
  • HashMap order is bucket order. The docs promise nothing: "This class makes no guarantees as to the order of the map; in particular, it does not guarantee that the order will remain constant over time." The demo proves the second half. Same six keys, but after a resize to 32 buckets and back down to six entries, the order changed. Never write code, or a test, that depends on it.
  • LinkedHashMap is a HashMap that also "maintains a doubly-linked list running through all of its entries", so iteration follows insertion order (JDK docs: LinkedHashMap). It's still O(1) per operation, with a little more memory per entry.
  • Kotlin's defaults are the ordered ones. "The default implementation of MutableMap – LinkedHashMap – preserves the order of elements insertion when iterating the map", and likewise LinkedHashSet for sets (Kotlin docs: Collections overview). The javaClass lines confirm it. Use hashMapOf() when you want a plain HashMap. That's why L3's word counter printed words in first-seen order in Kotlin.
  • TreeMap keeps keys sorted, at O(log n) per operation, because it's a balanced tree. That's L20.
  • HashSet "implements the Set interface, backed by a hash table (actually a HashMap instance)" (JDK docs: HashSet). In the OpenJDK source, every element is stored as a key with the same dummy value, PRESENT. Everything in Part 3 applies to sets too.
  • ConcurrentHashMap is the thread-safe one. HashMap's docs say that if several threads use one and any of them modifies it, it "must be synchronized externally". That's for the concurrency phase.

An LRU cache in ten lines

LinkedHashMap has a second mode. Pass accessOrder = true and it orders entries "in which its entries were last accessed, from least-recently accessed to most-recently (access-order). This kind of map is well-suited to building LRU caches." Then override removeEldestEntry, which put consults after every insert. The docs' own example is return size() > MAX_ENTRIES; (JDK docs: removeEldestEntry).

access order: [b, c, a]
cache: [c, a, d]

Reading a made it the most recent, so when d arrived, b was the eldest and got evicted. A least-recently-used (LRU) cache is the standard answer to "keep the hot data in memory, but bounded". You'll meet it again in L44–L45 on caching and system design. The final wraps this in a proper class with tests.

What Kotlin does for you. mutableMapOf() already gives you insertion order, where Java makes you choose LinkedHashMap explicitly. object : LinkedHashMap<…>(…) { override fun … } is Kotlin's anonymous subclass, the equivalent of Java's new LinkedHashMap<>(…) { … }, and with an expression body the override fits on one line. getOrPut is computeIfAbsent with a friendlier name.

Both are O(n · k log k) for n words of length k: one map operation per word, plus sorting its letters. Check

Kotlin: mutableMapOf<String, Int>().javaClass.name

Kotlin's default mutable map preserves insertion order. hashMapOf() gives a plain HashMap.

A test asserts that a HashMap's keys come out as [a, b, c]. What's wrong?

The docs guarantee no order, not even a stable one. It may pass today and fail after a resize or a JDK upgrade.

What makes a LinkedHashMap evict entries automatically?

accessOrder only changes the iteration order. Eviction happens when removeEldestEntry returns true after an insert.

Design notes. The Kotlin tests have no null-key test because MyHashMap<String?, Int> doesn't compile: the K : Any bound already rejects it. wordReport doesn't need a separate max loop with tie-breaking: it scans the keys in sorted order and only replaces best on a strictly greater count, so ties keep the alphabetically first word. LruCache wraps the LinkedHashMap rather than extending it, so callers can't reach putAll, entrySet and the rest and bypass the eviction rule. That's L8's composition argument in miniature. Finally, the JDK's LinkedHashMap is what you'd ship. MyHashMap exists to make you fluent, not to replace HashMap.

~5 min

Which assertion fits "remove on a missing key returns null"? (L11)

assertNull(m.remove("cat")). Use assertThrows only if your design throws for missing keys, like Kotlin's getValue.

Your Java MyHashMap creates its bucket array as (Entry<K, V>[]) new Entry[8]. Why the cast? (L13)

new Entry<K, V>[8] is illegal because of erasure, so you create a raw array and cast it. That's safe here because the array never leaves the class, which is why it's suppressed on the smallest scope.

A chain in your map is a singly linked list. To remove a node from the middle you need… (L17)

You set prev.next = target.next. A singly linked node doesn't know its predecessor, so you track it while walking.

Kotlin: data class Tag(var name: String) is used as a HashSet element, then name changes. Then set.contains(tag)… (L7 + L19)

The generated hashCode now points to a different bucket, so the set looks in the wrong place. This is MutableKey again, in set form.
