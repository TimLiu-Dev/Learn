How Languages Work

kotlinc and javac read text and produce bytecode, and the JVM runs that bytecode. In this lesson you build the same pipeline, small enough to hold in your head: a scanner, a parser, a tree-walking interpreter, a compiler to stack bytecode and the virtual machine that runs it. After this, a compiler error is just a parser telling you which token it expected.

Part 1

Scanning: text to tokens

~20 min

Every language implementation is a pipeline, and the first half is always the same. Robert Nystrom's Crafting Interpreters, this lesson's primary source, describes it: "The first step in any compiler or interpreter is scanning. The scanner takes in raw source code as a series of characters and groups it into a series of chunks we call tokens" (Scanning). The parser then turns tokens into a tree. After that the paths split: an interpreter runs the tree directly, and a compiler translates it into another form. "When you generate bytecode or machine code, you are compiling" (A Map of the Territory).

javac is built exactly like this. Its source code describes its two front-end stages in their own header comments. JavaTokenizer: "The lexical analyzer maps an input stream consisting of UTF-8 characters and unicode escape sequences into a token sequence." JavacParser: "The parser maps a token sequence into an abstract syntax tree" (JavaTokenizer.java, JavacParser.java, OpenJDK source).

The language: Calc

Calc is just big enough to need every stage: integers, variables, six operators and parentheses. A program is some let statements followed by one expression, whose value is the result.

let width = 12;   // a comment
let area = width * (width - 2);
area / 4          // the result: 30

A lexeme is "the smallest sequences that still represent something", and a lexeme bundled with what kind it is and where it came from is a token (Crafting Interpreters §4.2). Calc has numbers, names, the keyword let, and ten symbols: + - * / % ^ ( ) = ;. Each kind of token is a tiny regular expression: a number is [0-9]+ and a name is [a-zA-Z_][a-zA-Z_0-9]*. Nystrom points out that this is no coincidence: in most programming languages "the rules of that grammar are simple enough for the language to be classified a regular language. That's the same 'regular' as in regular expressions" (§4.3). So a scanner is a DFA (L51), written by hand as a loop.

Java's three small files: T.java, Token.java, CalcError.java

Kotlin put the token enum, the token class and the error type at the top of Lexer.kt. Java gives each public type its own file, and the source launcher finds a class by its file name:

Both languages print exactly this. Read it line by line:

  • Positions. Every token knows its line and column, so every later error can point at the source: '#' at 1:11. Real compilers spend a surprising amount of code on this.
  • The comment vanished. skipSpaceAndComments eats whitespace and // comments before each token, so the parser never sees them.
  • One character of lookahead. On /, the scanner must peek at the next character to decide between division and a comment. a//b\n/ c is a name, a comment, then a real slash.
  • Bad numbers fail early. 99999999999 doesn't fit in an Int, and the scanner says so with a position, instead of letting the parser crash later.

Maximal munch

The last line scanned letter as one name, not the keyword let followed by ter. The scanner keeps reading while the next character can still belong to the current token, and only then checks whether the word is a keyword. Nystrom: "When two lexical grammar rules can both match a chunk of code that the scanner is looking at, whichever one matches the most characters wins" (§4.7). Java's specification makes the same rule, with a famous consequence: "The longest possible translation is used at each step, even if the result does not ultimately make a correct program while another lexical translation would… The input characters a--b are tokenized as a, --, and b, which is not part of any grammatically correct program" (JLS §3.2). Both compilers really do this. With var a = 5 and b = 2, try println(a--b):

Part 2

Parsing: tokens to a tree

~30 min

Tokens are a flat list, but programs nest: (1 + 2) * 3 multiplies a sum. L51 proved that no finite automaton can track nesting to any depth, so the parser needs a stronger tool. Nystrom: "regular languages aren't powerful enough to handle expressions which can nest arbitrarily deeply. We need a bigger hammer, and that hammer is a context-free grammar (CFG)" (Crafting Interpreters §5.1). A grammar is a set of rules, each naming a piece of syntax and saying what it's made of. Here is all of Calc, in EBNF (* means "zero or more", ? "optional", | "or"):

program := ( "let" IDENT "=" expr ";" )* expr EOF
expr    := term ( ( "+" | "-" ) term )*
term    := unary ( ( "*" | "/" | "%" ) unary )*
unary   := "-" unary | power
power   := atom ( "^" unary )?
atom    := NUMBER | IDENT | "(" expr ")"

Precedence lives in the shape of the grammar

Nothing in those rules says "* binds tighter than +" in so many words, yet it does. expr is built from terms, and term from unarys, so a multiplication is always finished before the addition around it gets to see it. There's one rule per precedence level, lowest first. Nystrom: "Each rule here only matches expressions at its precedence level or higher" (§6.1). Parentheses get back in at the very bottom: atom can be a whole expr in brackets, which is the recursion a DFA can't do.

Associativity decides which operator wins among equals: is 8 - 3 - 2 equal to (8 - 3) - 2 or to 8 - (3 - 2)? Subtraction is left-associative, and ^ (power) is right-associative in maths: 2 ^ 3 ^ 2 means 2 ^ 9. The grammar encodes that too, as you'll see in the code.

Recursive descent: one function per rule

The technique is recursive descent, and it's what you'll find in real compilers. Nystrom: "Recursive descent is the simplest way to build a parser, and doesn't require using complex parser generator tools like Yacc, Bison or ANTLR… GCC, V8 (the JavaScript VM in Chrome), Roslyn (the C# compiler written in C#) and many other heavyweight production language implementations use recursive descent" (§6.2). javac too: "The parser is a hand-written recursive-descent parser that implements the grammar described in the Java Language Specification." The translation is mechanical:

GrammarCode
a token, like "("check it and consume it: expect(T.LPAREN, …)
a rule name, like termcall that rule's function: term()
|if or when/switch on the next token
*a while loop
?an if

The tree is a sealed type (L7): four kinds of expression node, each a data class in Kotlin and a record in Java.

Java's tree types: Expr.java and Program.java

The four node kinds are records nested inside the sealed interface, so they need no permits clause. JEP 409: when subclasses are declared in the same file, "the sealed class may omit the permits clause and the Java compiler will infer the permitted subclasses" (JEP 409).

Look at how the grammar became code:

  • expr and term are loops, not recursion. The textbook way to write a left-associative rule is expr := expr "+" term, but a recursive-descent function for that would call itself before consuming anything, forever. Nystrom calls such a rule "left-recursive" and notes that some parsing techniques "have trouble with left recursion" (§6.1). The loop builds the same left-leaning tree: each new Bin takes the tree so far as its left child.
  • power recurses on the right. After ^ it calls unary(), which can contain another ^, so the tree leans right: right-associative.
  • unary sits above power. So -2 ^ 2 means -(2 ^ 2), as in maths. That decision comes back to bite in the final.
  • Errors say what was expected. expect knows which token the grammar needs at that point, so the message practically writes itself. That's all a compiler's "';' expected" ever was.
1 + 2 * 3               (+ 1 (* 2 3))
(1 + 2) * 3             (* (+ 1 2) 3)
8 - 3 - 2               (- (- 8 3) 2)
2 ^ 3 ^ 2               (^ 2 (^ 3 2))
-2 ^ 2                  (neg (^ 2 2))
let x = 3; x * (x + 1)  let x = 3; (* x (+ x 1))

show prints the tree Lisp-style, with every operator before its operands, so the shape is visible: (+ 1 (* 2 3)) is a + node whose right child is a * node. 8 - 3 - 2 leans left and 2 ^ 3 ^ 2 leans right, as promised. Java prints the same, except that a record's toString uses square brackets: Bin[op=MINUS, left=Bin[… where Kotlin's data class writes Bin(op=MINUS, left=Bin(….

Why sealed types fit syntax trees so well

A compiler has a handful of node types and several operations on them: print, evaluate, compile, optimise. Nystrom draws this as a table with "rows" for types and "columns" for operations, and calls the tension between them the expression problem. Object-oriented style puts each row in a class, which "makes it easy to extend the table by adding new rows", while the functional style uses "pattern matching—sort of a type-based switch on steroids", which "makes it trivial to add new operations—simply define another function that pattern matches on all of the types" (§5.3.1). Calc gains operations all lesson (show, eval, compile, two exercises), so the functional grain fits. Kotlin's when and Java 21's pattern switch are that "switch on steroids". (The book's Java code gets the same effect with the Visitor pattern.) The compiler checks coverage: Kotlin "allows the Kotlin compiler to check exhaustively that all possible cases are covered" (Kotlin docs: Sealed classes), and in Java, when the cases cover every permitted subclass, "this switch block is exhaustive. As a result, no default label is needed" (JEP 441). Add a fifth node type and every function that needs a new branch fails to compile until it has one.

Every nested ( costs a chain of calls (atom → expr → term → unary → power → atom), so very deep nesting must eventually overflow the thread's stack (L4):

That's an observation about HotSpot on my machine, not a guarantee. No human writes 10,000 nested brackets, but generated code can, which is one reason some production parsers handle deep nesting without recursion.

Part 3

Interpreting: walking the tree

~15 min

With a tree, running the program is a recursive function. To evaluate a + node you need both operands' values first, so "you have to evaluate those first. That means working your way from the leaves up to the root—a post-order traversal" (Crafting Interpreters ch. 5). That's L20's post-order walk, with arithmetic where the println was. Variables need somewhere to live. "The bindings that associate variables to values need to be stored somewhere. Ever since the Lisp folks invented parentheses, this data structure has been called an environment. You can think of it like a map where the keys are variable names" (§8.3). For Calc, a HashMap (L19) is the whole environment.

1 + 2 * 3                       = 7
2 ^ 3 ^ 2                       = 512
-2 ^ 2                          = -4
let x = 3; x * (x + 1)          = 12
let x = 5; let x = x * x; x - 1 = 24
2147483647 + 1                  = -2147483648
7 / 2 + -7 % 2                  = 2
let a = 1; a + b                CalcError: undefined variable 'b' at 1:16
10 / (5 - 5)                    CalcError: division by zero at 1:4
2 ^ -1                          CalcError: negative exponent at 1:3

Identical output in both languages. Calc inherits the JVM's integer rules because arith uses Int, as you'd expect when your language runs on another language:

  • 2147483647 + 1 wraps to -2147483648. The JVM's iadd is specified that way: "The result is the 32 low-order bits of the true mathematical result… If overflow occurs, then the sign of the result may not be the same as the sign of the mathematical sum" (JVMS §6.5 iadd). L2 showed the same thing from the outside.
  • 7 / 2 + -7 % 2 is 3 + -1 = 2. Division truncates, and the remainder takes the sign of the dividend, as in L48.
  • let x = x * x reads the old x before rebinding it, because interpret evaluates the value before it updates the map.
  • Errors happen when evaluation reaches them, and carry the position of the token that caused them.

This style is called a tree-walking interpreter. Nystrom: "This implementation style is common for student projects and little languages, but is not widely used for general-purpose languages since it tends to be slow" (§2.2.2). Part 4 measures how slow.

Part 4

Compiling: bytecode and a virtual machine

~25 min

Why not just walk the tree? Nystrom's answer is memory: the tree's nodes "could be anywhere. Every step the tree-walker takes where it follows a reference to a child node may step outside the bounds of the cache" (L22's caches), whereas "to use the cache effectively, the way we represent code in memory should be dense and ordered like it's read." Bytecode is that representation: "Structurally, bytecode resembles machine code. It's a dense, linear sequence of binary instructions" (Crafting Interpreters §14.1.1). It sits between the two extremes: "a tree-walk interpreter is simple, portable, and slow. On the other, native code is complex and platform-specific but fast. Bytecode sits in the middle."

You've read bytecode already (L23), and Calc's will look familiar. Like the JVM, it's a stack machine: instructions take their inputs from an operand stack and push their results back. The JVM specification describes the format: "A Java Virtual Machine instruction consists of a one-byte opcode specifying the operation to be performed, followed by zero or more operands" (JVMS §2.11). Calc has eleven opcodes. Three of them take one operand: push 3, load 0 and store 0. The rest work purely on the stack. To keep things simple, opcodes and operands are Ints in an IntArray, not bytes.

The compiler: the same walk, emitting instead of computing

Compare expr below with Part 3's eval. Both visit the children, then the node. Where eval computes a value, expr emits the instruction that will compute it later. Three things happen at compile time that the interpreter did at run time:

  • Names become numbers. Each variable gets a slot in a locals array, as javac gives a slot 0 (L23's iload_0). The VM never sees a name or a HashMap.
  • The stack depth is worked out in advance. The compiler tracks how deep the stack gets and records the maximum, like the class file's max_stack: "the maximum depth of the operand stack of this method… at any point during execution of the method" (JVMS §4.7.3). The VM allocates exactly that much.
  • Positions are kept on the side. where remembers the source position of each instruction, so a division by zero at run time can still say at 1:4. The class file's LineNumberTable does the same job for your stack traces: it "may be used by debuggers to determine which part of the code array corresponds to a given line number in the original source file" (JVMS §4.7.12).
Java's Op.java and Chunk.java

The virtual machine: fetch, decode, execute

The JVM specification sketches its own interpreter in four lines: "Ignoring exceptions, the inner loop of a Java Virtual Machine interpreter is effectively do { atomically calculate pc and fetch opcode at pc; if (operands) fetch operands; execute the action for the opcode; } while (there is more to do);" (JVMS §2.11). It's the same loop your toy CPU ran in L52. Here it is for Calc:

stack=3, locals=1 [x]
  0: push 3
  2: store 0   // x
  4: load 0   // x
  6: load 0   // x
  8: push 1
 10: add
 11: mul
 12: return
result = 12, interpreter says 12
1 + (2 * (3 - 4))   maxStack=4
((1 + 2) * 3) - 4   maxStack=2

What Kotlin does for you.
  • object Op { const val PUSH = 0 … } makes compile-time constants, like Java's static final int. Both can be when/case labels, and both became a tableswitch.

Exercise: constant folding

The folded method above came out as bipush 6: javac computed 2 * 3 at compile time. The JLS calls such an expression a constant expression: "an expression denoting a value of primitive type or a String that does not complete abruptly and is composed using only" literals, operators and a few other pieces (JLS §15.29). Note the words "does not complete abruptly". Here's javac on return 1 / 0 + x;:

  static int g(int);

         1: iconst_0

         5: ireturn

1 / 0 would throw, so it isn't a constant expression, and javac leaves the division for run time. Check

What maxStack does Calc's compiler compute for 1 + (2 * (3 - 4))?

1, 2 and 3 wait on the stack while 4 is pushed: four values before the first sub. Bracketing to the left, ((1 + 2) * 3) - 4, never needs more than two.

Why does Calc's add instruction need no operand?

On a stack machine, earlier instructions have already pushed both inputs. add pops two values and pushes one, like the JVM's iadd.

javac compiles return 2 * 3 + x; into instructions that start with…

2 * 3 is a constant expression (JLS §15.29), so javac folds it to 6 at compile time. 1 / 0 isn't one, because it would complete abruptly, so javac leaves it alone.

The first is a bug in the test. For "(−2) to the power d", my generator printed -(2) ^ d. The second is a real semantic difference. In let a = (2 ^ -((7 ^ 4))); … -(c), the interpreter reached the negative exponent first and reported it. For the GRAMMAR row: write Calc's six rules from memory, on paper. Then extend the grammar with comparisons, < and == (giving 1 or 0), at a new lowest precedence level, non-associative so that 1 < 2 < 3 is a syntax error. Write down the tree your grammar gives 1 + 2 < 4, and which functions in the parser change.

Model answer for the GRAMMAR row 
program := ( "let" IDENT "=" compare ";" )* compare EOF
compare := expr ( ( "<" | "==" ) expr )?
expr    := term ( ( "+" | "-" ) term )*
...      (the rest unchanged; atom's brackets now contain a compare)

1 + 2 < 4 becomes (< (+ 1 2) 4). The ? instead of * is what makes it non-associative: after one comparison, a second < is left over, and expect(T.EOF, …) reports it. The scanner gains LESS and EQEQ, and needs one character of lookahead to tell = from ==, maximal munch again. The parser gains one function, and program and atom call compare() where they called expr(). Every exhaustive when over the operator type then fails to compile until it handles the two new operators, which is the sealed-type check from Part 2 doing its job.

Wrap-up

Exit quiz, recall card, sources

~5 min

Calc's scanner looks at each character a constant number of times. Its running time on n characters is… (L16)

One pass, at most one character of lookahead: linear. Calc's parser is linear too: it decides every step from the next token alone, so it never backtracks and consumes each token once.

About 10,000 nested parentheses crash the parser with… (L4, L18)

Each level adds several frames to the thread's stack, and the stack is far smaller than the heap. -Xss raises the limit (L18).

Why can't one regular expression check that Calc's parentheses balance? (L51)

Balanced brackets need a counter that can grow without limit, and a finite automaton has a fixed number of states. Calc uses regular rules for tokens and a context-free grammar for structure.

The interpreter's environment is a HashMap. Looking up a variable costs, on average… (L19)

Hash, then one bucket. But it's a large O(1): hashing a String and unboxing an Integer. The compiler replaced it with an array index, a much smaller O(1), and that's part of the 5.5× gap.

Your Calc VM runs inside the JVM. Who turns execute into real machine instructions? (L23)

Your VM is ordinary bytecode. HotSpot interprets it at first, then its JIT compiles the hot execute loop to machine code, so two interpreters are stacked on one CPU.
