The OS & the Memory Hierarchy

Your program is not alone on the machine. The operating system gives it the illusion of a private computer, the CPU's caches decide how fast its memory really is, and every file read is a request to the kernel. This lesson shows each one with real measurements.

Part 1

Processes, virtual memory, system calls

~30 min

An operating system's main job, in the words of the free textbook Operating Systems: Three Easy Pieces (OSTEP), is virtualization: "the OS takes a physical resource (such as the processor, or memory, or a disk) and transforms it into a more general, powerful, and easy-to-use virtual form of itself". To let programs use that virtual machine, "a typical OS, in fact, exports a few hundred system calls that are available to applications" (OSTEP ch. 2, Introduction). This part looks at the three illusions your JVM lives inside: its own CPU, its own memory, and a safe door into the kernel.

Processes and threads

A process "is a running program". The program on disk "is a lifeless thing", and the OS turns it into something running (OSTEP ch. 4, The Process). There are only a few CPU cores, yet hundreds of processes seem to run at once. The OS creates that illusion by time sharing: "by running one process, then stopping it and running another", it makes it look as if "many virtual CPUs exist when in fact there is only one physical CPU (or a few)".

A process can contain several threads. All threads of one process share its memory (the heap from L4), and each thread has its own stack. Java gives you the current process and lets you start new ones:

my pid:     9817
parent pid: 9787
command:    /Users/tl/Library/Java/JavaVirtualMachines/openjdk-26.0.1/Contents/Home/bin/java
6 threads: [Common-Cleaner, Finalizer, Notification Thread, Reference Handler, Signal Dispatcher, main]
child 9818 said 'hello from a child', exit 0
sh -c 'exit 3' gave exit 3
  • Every process has a number, its pid, and a parent: here, the shell that launched java. Both languages print the same thing, because Kotlin on the JVM calls the same ProcessHandle API.
  • Even "hello world" is multi-threaded. Before main runs, the JVM has already started helper threads. Thread.getAllStackTraces() returns stack traces "for all live platform threads" (Thread docs), meaning the threads that exist as Java Thread objects. Below, the OS will count far more.
  • ProcessBuilder starts a child process (ProcessBuilder). You read its output as a stream and wait for its exit code. By convention 0 means success and anything else means failure, which is how shell scripts and build tools know a step failed.

Each process gets its own address space

OSTEP calls the memory illusion the address space: "the running program's view of memory in the system". It holds the program's code, its stack ("to keep track of where it is in the function call chain") and its heap (OSTEP ch. 13, Address Spaces). For a JVM there's one stack per thread. The key fact sits in a box in that chapter, titled "Every Address You See Is Virtual": "any address you can see as a programmer of a user-level program is a virtual address".

The hardware and the OS translate virtual addresses into physical ones a page at a time. Memory is cut into fixed-size pages, and a per-process page table maps each virtual page to a physical one. (On this Mac a page is 16 KB: sysctl hw.pagesize prints 16384.) Looking up the page table on every memory access would be slow, so the CPU keeps a small cache of recent translations, the TLB or translation-lookaside buffer: "simply a hardware cache of popular virtual-to-physical address translations" (OSTEP ch. 19, TLBs).

That's why two processes can use the same address without clashing. I started two copies of the Hold program below at the same time and asked each one where its heap lives:

$ jcmd 26961 GC.heap_info | grep heap
garbage-first heap   total reserved 1048576K, committed 215040K, used 208060K [0x00000007c0000000, 0x0000000800000000)
$ jcmd 26963 GC.heap_info | grep heap
garbage-first heap   total reserved 1048576K, committed 215040K, used 208060K [0x00000007c0000000, 0x0000000800000000)

Two live processes, identical heap addresses 0x7c0000000–0x800000000, each holding its own 200 MB. Each page table maps those virtual pages to different physical RAM. One process can't even name another's memory, which is the protection that stops a crashing app from corrupting your editor.

System calls: the door into the kernel

Your code can't touch the disk, the network or another process directly. OSTEP explains the hardware rule: code in user mode "is restricted in what it can do", while the OS runs in kernel mode, where code "can do what it likes, including privileged operations such as issuing I/O requests" (OSTEP ch. 6, Limited Direct Execution). To cross the line, a program makes a system call. It looks like a normal function call, "but hidden inside that procedure call is the famous trap instruction", which jumps into the kernel and raises the privilege level, then returns when the work is done. Every file read, network send and new thread goes through one.

Tools can show you each system call a process makes. On Linux that's strace. macOS has dtruss, but its man page says "since this uses DTrace, only users with root privileges can run this", and recent macOS versions add further restrictions. I didn't run either one here. Instead, here's a safe, real measurement of what one system call costs:

array:                  0.22 ns per byte
RandomAccessFile.read(): 305 ns per byte
ratio: about 1391x  (checksum 126979520)
array:                  0.22 ns per byte
RandomAccessFile.read(): 309 ns per byte
ratio: about 1409x  (checksum 126979520)

The file is tiny and already in the OS's memory, so no disk is involved at all. The difference is pure overhead: entering the kernel, finding the file, copying one byte back. Why is each read() a system call? In OpenJDK, RandomAccessFile.read() is a native method that ends up in readSingle, which calls IO_Read(fd, &ret, 1): one OS read of one byte (io_util.c; an implementation detail, not a guarantee). About 1,400× slower per byte is why Part 3 is all about buffering. (The checksum is printed so the JIT can't throw away a loop whose result is never used.)

Bridge: an Android app is a Linux process too. "When an application component starts and the application doesn't have any other components running, the Android system starts a new Linux process for the application with a single thread of execution", the main thread (Android: Processes and threads). Android may kill that process to reclaim memory, which is why the platform cares so much about your app's RSS.

What Kotlin does for you.
  • Kotlin uses the very same JDK classes (ProcessHandle, ProcessBuilder, RandomAccessFile) with no wrappers needed.
  • stream.bufferedReader().use { it.readText() } reads a child's whole output and closes the reader in one line. Java needs a try-with-resources block, and before Process.inputReader() (JDK 17) it needed an InputStreamReader wrapper too.
  • No throws IOException, InterruptedException on main. Kotlin has no checked exceptions (L10), so waitFor() and start() just work, and you decide where to catch.
  • me.parent().map { it.pid() }.orElse(-1) works on Java's Optional with a lambda, and string templates replace the + chains.

Part 2

CPU caches and the memory hierarchy

~30 min

Big O counts steps as if every memory access cost the same. It doesn't. A CPU can do arithmetic far faster than main memory can deliver data, so chips put small, fast caches between the cores and RAM. The result is a memory hierarchy: registers, then the L1, L2 (and on many chips L3) caches, then RAM, then storage. Each level is bigger and slower than the one before. Peter Norvig's widely quoted table gives "approximate timing for various operations on a typical PC" (Norvig, Teach Yourself Programming in Ten Years). It's old (the disk rows are spinning disks, not SSDs) and every number is approximate, but the shape still holds. The purple rows are things I measured in this lesson.

Switch to the second tab. If an L1 cache hit took one second, a trip to main memory would take over three minutes, and reading a megabyte one system call at a time would take about 20 years. That last row isn't from a book. It's the unbuffered reader in today's final exercise.

This chip has two kinds of cores, each with its own caches: 128 KB of L1 data cache per core on the fastest ones, and a shared 16 MB L2. No L3 key exists here. (On Linux, try lscpu; on Windows, Task Manager's CPU page. I didn't run those.) The number that matters most today is hw.cachelinesize: 128. Memory doesn't move between RAM and the caches one byte at a time. It moves in cache lines, here 128 bytes, which is 32 ints. Read one int and its 31 neighbours come along for free.

Caches pay off because programs have locality. OSTEP: "with temporal locality, the idea is that an instruction or data item that has been recently accessed will likely be re-accessed soon", and "with spatial locality, the idea is that if a program accesses memory at address x, it will likely soon access memory near x. Imagine here streaming through an array" (OSTEP ch. 19). Code that walks memory in order gets most of its data for free. Code that jumps around pays for a miss on almost every access.

Row-major vs column-major

Here's a toy cache: 4 ints per line, room for 4 lines. Step through both orders and count the misses:

Row-major gets 16 misses out of 64 reads: one per line, and the next 3 reads are hits. Column-major touches 8 different lines per column, but the cache holds only 4, so every line is evicted before it's reused: 64 misses out of 64. Real caches are far bigger, but so are real arrays. Now on real hardware:

row-major:       3.7 ms  (sum 50331645)
column-major:   27.4 ms  (sum 50331645)
column-major is 7.4x slower
row-major:       3.8 ms  (sum 50331645)
column-major:   29.3 ms  (sum 50331645)
column-major is 7.7x slower

It's the same 16.7 million additions with the same result, and both are O(n²) in the grid side n. Yet one order is 7–8× slower. Each row is an IntArray of 4,096 ints (16 KB), so column-major lands on a different row, a different cache line and usually a different 16 KB page on every single step.

Arrays vs boxes vs linked lists

Now the experiment behind L17's timing. Same 5 million numbers, four containers:

IntArray                 1.1 ms    1.0x  (sum 12499997500000)
ArrayList<Int>           1.8 ms    1.6x  (sum 12499997500000)
ArrayList, shuffled     14.2 ms   12.4x  (sum 12499997500000)
LinkedList<Int>          8.0 ms    7.0x  (sum 12499997500000)
int[]                    1.1 ms    1.0x  (sum 12499997500000)
ArrayList<Integer>       2.1 ms    1.9x  (sum 12499997500000)
ArrayList, shuffled     10.6 ms    9.6x  (sum 12499997500000)
LinkedList<Integer>      7.3 ms    6.6x  (sum 12499997500000)
  • IntArray / int[] stores the numbers themselves, side by side: 32 per cache line.
  • ArrayList<Int> stores references to boxed Integer objects (L5, L13). Every element costs an extra hop. It's only about 2× slower here because the objects were allocated in order, so they happen to sit next to each other in the heap.
  • Shuffled holds the same objects and the same values, and gives the same sum and the same Big O. Only the visiting order changed, so each hop now lands somewhere unpredictable, and it's 10–12× slower. That is locality, isolated.
  • LinkedList hops twice per element, node then Integer, and each node carries extra pointers (L17). It's 7× slower than the array.

So "an array beats a linked list in practice" isn't folklore. Big O deliberately drops constant factors (L16), and memory access is where the hardware hides big ones. The JDK's everyday collections are array-based (ArrayList, ArrayDeque, HashMap's bucket table), and you should measure before you trust a Big O argument about speed.

Look at the last column. Up to step 16, an access costs under a nanosecond. At step 32 it jumps about 7×, to around 6 ns, and stays there. 32 ints × 4 bytes = 128 bytes, exactly hw.cachelinesize. From that step on, every access lands on a new cache line, so every access is a miss. Below it, several accesses share each line.

Be honest about what this table doesn't show. The total times don't follow a neat formula: step 16 is faster overall than step 32, even though both touch every cache line. Real CPUs prefetch lines they predict you'll need, and the JIT compiler can unroll simple loops and turn them into vector instructions (L23). I won't pretend to explain every number. The clear, repeatable signal is the jump at the cache-line size. Real hardware is messy, which is the best argument for measuring.

Coming in Phase 8: when two threads write to different variables that happen to share one cache line, the cores keep stealing the line from each other. That's called false sharing, and it can make correct concurrent code mysteriously slow.

Bridge: Android ships SparseArray for maps keyed by int. Its docs say it's "intended to be more memory-efficient than a HashMap, because it avoids auto-boxing keys and its data structure doesn't rely on an extra entry object for each mapping" (SparseArray). What Kotlin does for you (and what it hides).
  • IntArray(N) { it } creates and fills a primitive array in one expression. Java needs a separate loop.
  • Kotlin hides boxing, which is convenient and also a trap here. Array<Int>, List<Int> and ArrayList<Int> all store boxed Integers. Only IntArray stores raw ints. The docs: "If you use the Array class with primitive values, the compiler boxes these values into objects. To avoid boxing overhead, you can use dedicated primitive-type arrays" (Kotlin: Arrays). Java makes the difference visible in the type: int[] vs Integer.
  • for (x in boxed) unboxes automatically, as does Java's for (int x : boxed). Neither shows you the pointer hop.
  • Destructuring val (row, s1) = bestMs { … } returns two values via Pair, where the Java version packs them into a double[].

Part 3

Files and I/O

~30 min

A file is a sequence of bytes. Text only appears once you decode those bytes with a character encoding. Java's classic I/O library keeps the two worlds apart:

BytesCharacters (text)
ReadInputStream (FileInputStream, BufferedInputStream)Reader (BufferedReader, InputStreamReader)
WriteOutputStreamWriter (BufferedWriter)
BridgeInputStreamReader(stream, charset) decodes bytes into chars; OutputStreamWriter encodes

The classes are designed to wrap each other: a BufferedInputStream wraps a FileInputStream and adds a buffer. That's L8's decorator pattern, and dev.java's tutorial calls it exactly that (dev.java: Decorating I/O Streams).

  • Three different sizes for one string. 6 code points (L2): c a f é, a space and 😀. 7 Java chars, because 😀 needs two UTF-16 units. 10 bytes in UTF-8: c a f take 1 byte each, é takes 2 (c3 a9), and 😀 takes 4 (f0 9f 98 80). xxd, the standard hex-dump tool, shows the same bytes the program printed.
  • Decode with the wrong charset and you get mojibake. windows-1252 maps each byte to one character, so c3 a9 becomes Ã©. If you've ever seen Ã© on a web page, someone decoded UTF-8 as a one-byte charset. ISO-8859-1 does the same to é, and turns the emoji's bytes into invisible control characters.
  • UTF-8 is the default since JDK 18. JEP 400: "Specify UTF-8 as the default charset of the standard Java APIs. With this change, APIs that depend upon the default charset will behave consistently across all implementations, operating systems, locales, and configurations." Before that, the same program could write different bytes on Windows. java -XshowSettings:properties -version prints file.encoding = UTF-8 on this machine. Still, pass a charset explicitly whenever the bytes come from somewhere else.

  • Unbuffered: 8,388,608 bytes means 8,388,608 system calls, about 2.6 seconds.
  • Buffered: 60× faster with the same loop. "As bytes from the stream are read or skipped, the internal buffer is refilled as necessary from the contained input stream, many bytes at a time" (BufferedInputStream). OpenJDK's default buffer is 8,192 bytes (DEFAULT_BUFFER_SIZE, an implementation detail), so the kernel is called about 1,024 times instead of 8 million. Each read() is now just a method call that takes the next byte from an array.
  • readAllBytes: a few large reads straight into one array, close to memory speed. That's fine for files that fit comfortably in memory.

Close what you open

Every open file uses one entry in the process's table of file descriptors, the small numbers you saw from lsof. The table is limited. This program opens 300 streams and "forgets" to close them. On macOS and Linux, /dev/fd lists the current process's open descriptors:

Java refuses to compile it, which is L10's checked-exception rule in its most common setting: almost every file method declares throws IOException. Kotlin compiles it, and the missing file becomes a runtime NoSuchFileException, a subclass of IOException. Neither is wrong. Kotlin just trusts you to decide where to handle it, so do decide.

What Kotlin does for you.
  • path.readText(), writeText, useLines, readLines and dir / "notes.txt" read like English. Java spells each one as a static Files.xxx(path) call.
  • useLines and use close the file for you, even when an exception is thrown. With Java's Files.lines, forgetting the try block compiles fine and leaks a descriptor.
  • No throws IOException on every method, but the exceptions are still thrown. Handle them where it makes sense (L10).
  • file.deleteRecursively() deletes a whole tree in one call. Java walks the tree in reverse order and deletes the children first.
  • InputStream.copyTo(out) and Path.copyTo(target) already exist, so use them in real code instead of the exercise below.

Byte by byte makes two system calls per byte, a read and a write, so 4 MB takes 6 seconds. A 16-byte buffer divides the number of calls by 16 and is about 15× faster. An 8 KB buffer is about 3,000× faster. Past a few KB, the buffer size stops mattering much. The last read usually returns fewer bytes than the buffer holds, and read returns that count as n. Writing the whole buffer would append stale bytes from the previous read, and mismatch would catch it.

A log analyser

~25 min

Servers write access logs, one line per request, and you'll often need to answer questions like "which endpoints are busiest, and how slow are they at the 95th percentile?" Build the whole thing from a blank file, Kotlin first and then Java. Run it with -Xmx1g.

  1. Generate a log of 1,200,000 lines (about 50 MB) in a temp file, using java.util.Random(22) so the data is the same in both languages. Each line looks like 2026-10-20T00:00:01 GET /api/users 200 12ms. Use 8 paths; /health gets 3 picks in 10. Latency is a per-path base plus a random 0–29 ms, plus a random spike of up to 900 ms on 1 request in 12.
  2. Read it three ways and time each:
    • unbuffered FileInputStream.read(), but only the first 1 MB (count the newlines, then estimate how long the whole file would take)
    • a buffered readLine loop that builds a Map<String, MutableList<Int>> of latencies per path
    • a lazy pipeline, useLines / Files.lines + groupBy / groupingBy (L15), and check that it gives the same map
  3. Report the top 5 paths by request count (ties alphabetical) with their p95 latency. p95 by the nearest-rank method: sort the latencies, then take index ceil(0.95 × n) − 1 (L18).
  4. Print RSS at the start and the end, using ps -o rss= -p <pid> from Part 1. Delete the temp file at the end.

Explain the numbers (the MEASURE row):

  • Unbuffered: 1 MB took about 320 ms, which is about 300 ns per byte, Part 1's system-call cost again. The whole 50 MB would take about 16 s, more than 100× slower than the buffered readers.
  • Buffered vs pipeline: both are in the 130–200 ms range, because both read through an 8 KB buffer. Most of the remaining time goes on split and toInt, not on I/O. Whichever runs first also pays for the JIT warming up (L23), so don't read much into the gap between them.
  • p95 around 370–390 ms, while a typical request takes 10–60 ms. With spikes on 1 request in 12 (about 8%), more than 5% of requests are spikes, so the 95th percentile lands inside the spike range. That's why teams track p95 and p99 rather than averages: tail latency is what users notice.
  • RSS grew by about 300 MB for a 50 MB file. Not much of that is the results. Most latencies are below 128, so L5's Integer cache shares those boxes, and 1.2 million references are only a few MB. The rest is the heap growing to hold the temporary garbage both readers create: a String per line, plus a list of five pieces from split. In a variant run, with Runtime.getRuntime() prints added at the end, the heap had grown to 306 MB committed but only 75 MB used. After System.gc(), the committed heap shrank to 97 MB, yet RSS stayed at 362 MB. RSS tracks memory the process holds from the OS, not your live objects (L24 digs in). A real tool would stream the data with a fixed amount of memory per path, for example an IntArray histogram.
  • Java started at 118 MB, against 50 MB for Kotlin, because java LogAnalyzer.java compiles the source in-process first (JEP 330, as in the Part 1 exercise).

About 7×: same Big O, very different constants. Pointer chasing defeats spatial locality.

Without @Throws the bytecode declares no checked exception, and javac rejects a catch for an exception the method can't throw (L9).

Deep recursion hits StackOverflowError. Which part of the address space ran out? (L18)

Every thread gets its own fixed-size stack (-Xss, L4). vmmap showed one stack region per thread.

How should you test the analyser's p95 function? (L11)

Pure functions like p95(sorted) are easy to test with hand-made inputs, e.g. 20 values where you know the answer. Keep the I/O at the edges.
