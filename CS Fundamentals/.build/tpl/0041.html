Latency & Caching

Phase 11 shaped code inside one program. Phase 12 shapes systems made of many programs, and the first thing that changes is time: a database is a thousand times further away than a HashMap. This lesson puts real numbers on that, shows why the average hides the slow requests that users notice, and then builds the most common fix, a cache, including the three ways caches go wrong: stale data, stampedes and races.

In L40's AI-written diff, the books endpoint cached its result under the key "books". What went wrong? (L40)

The key ignored page and size, so every request after the first got the first answer. A cache key must include everything the answer depends on. Exercise 2 today builds a proper key.

A response has Cache-Control: max-age=2 and an ETag. Three seconds later the client wants it again. What happens? (L31)

After 2 seconds the copy is stale, so the client sends If-None-Match with the ETag. If nothing changed, the server answers 304 Not Modified with no body. TTL plus revalidation is today's whole topic, at the HTTP layer.

With accessOrder = true, which entry does LinkedHashMap's removeEldestEntry see as "eldest"? (L19)

Access order moves an entry to the end on every get, so the eldest is the least recently used: an LRU cache in three lines. Part 3 builds the same thing from a hash map and a linked list, and makes it thread-safe.

Eight threads call Kotlin's getOrPut on one ConcurrentHashMap for the same missing key. How many times can the lambda run? (L27)

getOrPut is check-then-act: several threads can miss at the same moment and each run the lambda. In L27 it ran 8 times. Today you'll meet the same bug at system scale, under its own name: a cache stampede.

Part 1

Latency numbers worth memorising

~25 min

In L22 you climbed the memory hierarchy inside one machine. Systems add rungs further down: another machine in the same building, then another continent. The System Design Primer's appendix reproduces the classic table, originally from Jeff Dean and Peter Norvig (System Design Primer: Latency numbers every programmer should know; Norvig's version is in Teach Yourself Programming in Ten Years). The numbers are approximate and dated: hardware has moved on, but the gaps between rungs have not.

OperationApprox. timeCompared with
L1 cache reference0.5 ns
Main memory reference100 ns200× L1
Send 1 KB over a 1 Gbps network10 µs
Read 4 KB randomly from SSD150 µs
Read 1 MB sequentially from memory250 µs
Round trip within the same datacenter500 µs
Read 1 MB sequentially from SSD1 ms4× memory
Read 1 MB sequentially over 1 Gbps10 ms40× memory
Send a packet California → Netherlands → California150 ms

Memorise four rules of thumb, all approximate: memory ≈ 100 ns, SSD read ≈ 100 µs, a round trip inside one datacenter ≈ 0.5 ms, a round trip across a continent or ocean ≈ 150 ms. The primer's own summary line puts it in requests: "2,000 round trips per second within a data center" but only "6-7 world-wide round trips per second". That last fact is why a server in one region feels slow on the other side of the world, no matter how fast its code is.

On my machine, on localhost. Read the ratios:

  • HashMap ≈ 5 ns. Faster than the 100 ns memory figure because 100,000 small entries mostly fit in the CPU caches (L22).
  • SQLite ≈ 2 µs: about 400× a map lookup. And this is the friendliest possible database: an in-process library reading a file the OS already holds in memory (the page cache). A database server adds a network round trip on top.
  • HTTP round trip ≈ 110 µs, on loopback. No network card, no cable: this is pure kernel and JVM overhead (L22's system calls). Real machines in one datacenter add about 0.5 ms more; across an ocean, 150 ms more.
  • Cold vs warm: over 1,000×. The first call loads and links classes; later calls run JIT-compiled code (L23). The cold number swings wildly between runs and languages (0.3 ms in Java, 7 ms in Kotlin here), which is why benchmarks warm up first (L24).

The sink line exists only so the JIT can't delete the loops as dead code (L23).

Percentiles: why the average lies

A service that's usually fast and occasionally slow is the normal case: a garbage collection, a cold cache, a lock, a retry. The average blends those together into a number no request actually took. Systems people describe latency with percentiles instead: p50 (the median, half of requests are faster), p95, p99 and so on. To find them, sort the measurements and index into the sorted array (L18). Here is a local service where exactly one request in 50 sleeps:

requests 10000, slow 2%
mean     0.70 ms
p50      0.13 ms
p95      0.24 ms
p99     30.20 ms
p99.9   30.39 ms
max     32.38 ms
pages with a call slower than p99: computed 9.6%, simulated 9.6%
requests 10000, slow 2%
mean     0.70 ms
p50      0.14 ms
p95      0.24 ms
p99     30.18 ms
p99.9   30.37 ms
max     32.96 ms
pages with a call slower than p99: computed 9.6%, simulated 9.6%

Three lessons in eight lines:

  1. The mean describes nobody. 0.70 ms is five times the typical request (0.13 ms) and 40 times faster than the slow ones (30 ms). No single request took 0.70 ms.
  2. p95 is fine, p99 is terrible. With 2% slow requests, the 95th percentile is still in the fast group and the 99th is in the slow group. Which percentile you watch decides which problem you can see.
  3. Timers lie a little too. The code asks for sleep(20), yet slow requests took about 30 ms in both languages. The OS doesn't wake a sleeping thread at the exact millisecond. Always measure; never assume.

Fan-out makes the tail everyone's problem. A real page often calls several services in parallel and must wait for the slowest. If each call is slower than its p99 one time in 100, a page that makes 10 calls hits at least one slow call with probability 1 − 0.9910 ≈ 9.6%. The simulation above drew 100,000 pages of 10 calls from the measured latencies and got the same 9.6%. Jeffrey Dean and Luiz André Barroso wrote the classic paper on this, The Tail at Scale (Communications of the ACM, 2013). Their abstract says "Temporary high latency episodes which are unimportant in moderate size systems may come to dominate overall service performance at large scale."

Why this matters for caching. A cache makes most requests fast, but every miss is still slow. You'll see this in the final: the cache drops the median from about 27 ms to 0.5 ms, while p95 and p99 stay near 30 ms because they're made of misses. Always report a cache's effect as percentiles, not just "average latency halved".

What Kotlin does for you.
  • DoubleArray(n) { … } fills an array of measurements in one expression. Java needs a loop writing into new double[n].
  • sortedArray(), average() and count { it > 10 } are built in. Java goes through Arrays.sort and Arrays.stream(...).
  • (1..pages).count { (1..10).any { … } } states the fan-out simulation directly. Java needs two loops and a flag.
  • use { } closes the response stream; Java uses try-with-resources (L10).
  • The latency itself is language-neutral: both run on the same JVM, so the numbers match.

Check

Roughly how long does a network round trip inside one datacenter take?

About 500 µs = 0.5 ms (the primer's table): 5,000 main-memory reads. 150 ms is the cross-ocean round trip.

In Tail, 2% of requests are slow. Why is p95 fast but p99 slow?

The slowest 2% occupy ranks 9,801–10,000 of the sorted 10,000. p95 is rank 9,500, still fast; p99 is rank 9,900, inside the slow group.

A page waits for 10 parallel calls, each slower than its p99 1% of the time. About how often is the page slow?

1 − 0.9910 ≈ 9.6%, and the simulation agreed. Fan-out turns a rare per-call event into a common per-page one (The Tail at Scale).

Why is the SQLite lookup here much faster than querying a database server would be?

SQLite is a library inside your process, reading a file the OS has cached. A database server is another process, usually on another machine: add at least a datacenter round trip (~0.5 ms) to every query.

Why does a benchmark run warm-up iterations before it starts timing?

The first calls include class loading and interpretation; the cold String.format was over 1,000× slower than the warm one. Steady-state numbers come after the JIT has compiled the hot code (L23, L24).

Part 2

Cache patterns, and why invalidation is hard

~35 min

A cache keeps a copy of data somewhere faster and closer than its source of truth. The System Design Primer puts the motivation plainly: "Caching improves page load times and can reduce the load on your servers and databases" (System Design Primer: Cache). You have already met caches at almost every level of this course:

WhereExampleLesson
CPUL1/L2/L3 caches in front of RAML22
Operating systemthe page cache: recently read file pages kept in RAM (why SQLite above was fast)L22
Inside your processa HashMap or LRU cache in the JVM heap: today's Part 3L19
Shared cache serverMemcached ("a high-performance, distributed memory object caching system"), Redis: one cache many app servers shareL42
CDNcopies of static files in data centres near usersL31
Browserthe HTTP cache, driven by Cache-Control and ETagL31

An in-process cache is fastest (no network) but each server has its own copy, and it vanishes on restart. A shared cache like Redis is one network hop away but consistent across servers. We can't run Redis here (and won't install it), so everything below is an in-process cache; the patterns are the same whichever kind you use.

Five ways to keep a cache and a database in step

The demo puts one tiny cache with a time-to-live (TTL) in front of a SQLite table that takes an extra 5 ms per query (an injected sleep, standing in for a database server). Each numbered section is one pattern.

no cache        reads 10, db reads 10, 76 ms
cache-aside     reads 10, hits 6, misses 4, db reads 4, 30 ms
  after write + invalidate, id 2 = Emma (2nd ed.)
read-through    reads 10, hits 6, misses 4, db reads 4, 30 ms
write-through   read after write: Middlemarch, db reads 0
no negative cache: 5 lookups of id 99 -> 5 db reads

  after write + invalidate, id 2 = Emma (2nd ed.)
read-through    reads 10, hits 6, misses 4, db reads 4, 28 ms
write-through   read after write: Middlemarch, db reads 0
no negative cache: 5 lookups of id 99 -> 5 db reads
negative cache:    5 lookups of id 99 -> 1 db read
  after insert, cache still says: not found
TTL 300 ms: stale for 345 ms, then saw 'Ulysses (annotated)'

The same ten reads (four distinct books) went from ten database queries to four. Here is what each pattern means:

  • Cache-aside (also called lazy loading). In the primer's words, "The application is responsible for reading and writing from storage. The cache does not interact with storage directly." On a read: check the cache; on a miss, load from the database and put it in the cache. On a write: update the database, then invalidate (delete) the cached copy, so the next read loads the fresh value. Deleting rather than updating is deliberate: you never risk writing a value computed from stale data. Memcached "is generally used in this manner".
  • Read-through. The same reads, but the loading logic lives inside the cache. The application asks only the cache, which calls a loader on a miss. It's the decorator idea from L39: ReadThrough wraps the database's find. Caffeine, the standard Java cache library, calls this a LoadingCache: "a Cache built with an attached CacheLoader" (Caffeine wiki: Population).
  • Write-through. Every write goes to the database and the cache together, so a read right after a write is a hit, and "Data in the cache is not stale". The cost: every write pays for both, and much written data may never be read.
  • Write-behind (write-back). Writes go to the cache immediately and reach the database later, in batches. Writes are fast; the risk is in the next demo.
  • Refresh-ahead. The cache reloads popular entries before they expire, so readers never wait for a miss. Caffeine's version: "The old value (if any) is still returned while the key is being refreshed" (Caffeine wiki: Refresh). The primer's warning: if you predict the wrong keys, you load data nobody asks for.

Look again at ReadThrough.get in Kotlin. It checks the entry, not the value, because a cached "not found" is stored as null. The tempting one-liner cache.get(id)?.value ?: load(id) would treat a cached null as a miss and reload every time: the same trap as getOrPut with null values in L39.

Negative caching

Looking up a book that doesn't exist hits the database every time, which is exactly what an attacker or a broken client does in a loop. Negative caching remembers "not found" too: 5 lookups, 1 query. The risk is in the next output line: when the book is added, the cache keeps saying "not found" until the entry expires. Give negative entries a short TTL, or invalidate them on insert.

TTL: how long you're willing to be wrong

The last line is the important one. Someone updated the database without telling the cache (another service, an admin, a script), and the cache served the old title for 345 ms: the 300 ms TTL plus up to 50 ms of polling. A TTL is a promise about staleness: "I might be wrong, but never for longer than this". Pick it per kind of data: a book's title can be stale for minutes; a bank balance can't be cached this way at all.

Write-behind: what a crash costs

Write-behind is the fastest way to write and the easiest way to lose data. The primer lists it as the first disadvantage: "There could be data loss if the cache goes down prior to its contents hitting the data store." This program sells stock through a write-behind cache that flushes every 500 ms, then cuts the power with Runtime.halt, which stops the JVM without running shutdown hooks:

$ java --enable-native-access=ALL-UNNAMED -cp sqlite-jdbc-3.53.4.0.jar WriteBehind.java write
  flushed 2 writes
cache says: {dune=5, emma=4, ulysses=6}, queued: 3
power cut!
$ echo $?
1
$ java --enable-native-access=ALL-UNNAMED -cp sqlite-jdbc-3.53.4.0.jar WriteBehind.java check
database says: {dune=7, emma=9, ulysses=10}

The Kotlin version prints the same lines. Five sales were acknowledged; the database has only the first two. Three sales are gone, and nothing anywhere records that they happened. Real write-behind systems reduce the risk with a durable queue (L42) or a replicated cache, but they never make it zero. Use write-behind only for data you can afford to lose or rebuild, such as view counters.

The race inside cache-aside

Cache-aside has a classic race, and it involves the "invalidate on write" rule itself. It needs this exact interleaving:

  1. A reader misses and reads the old value from the database.
  2. Before the reader puts it in the cache, a writer updates the database and invalidates the cache (which is empty anyway).
  3. The reader now puts the old value into the cache. It stays there until it expires.

Races are rare and timing-dependent (L26), so the demo forces this exact order with two latches:

plain cache-aside:  cache = Emma   database = Emma (2nd ed.)
versioned cache:    cache = Emma (2nd ed.)   database = Emma (2nd ed.)

Both languages print exactly this. Without the fix, the cache holds the old title with nothing to correct it but the TTL. The fix gives every row a version number that increases on each write; the writer puts the new versioned row into the cache, and merge keeps whichever row is newer, atomically (L27). The reader's late write of version 1 loses to version 2, whatever the order. Other real fixes: keep a short TTL so the damage is bounded, or use "leases", as described in Facebook's paper Scaling Memcache at Facebook (Nishtala et al., NSDI 2013).

Stampede: everyone misses at once

A popular key expires, and 50 requests arrive in the same millisecond. All 50 miss, and all 50 query the database for the same row: a cache stampede, or thundering herd. It's L27's check-then-act bug at system scale, and it hits right when the database is busiest. The fix is request coalescing: the first miss starts the load; everyone else waits for that same load.

plain      50 requests -> 50 database queries, 64 ms
coalesced  50 requests ->  1 database queries, 58 ms
plain      50 requests -> 50 database queries, 58 ms
coalesced  50 requests ->  1 database queries, 55 ms

I ran each version several times: always 50 queries without coalescing and exactly 1 with it. The wall time looks the same only because this fake database never gets overloaded; a real one serving 50 identical queries slows down for every other user too.

  • Java keeps a ConcurrentHashMap<Integer, CompletableFuture<String>> of loads in progress. putIfAbsent is atomic, so exactly one caller gets null back and does the load; the others join() the winner's future (L28). Why not computeIfAbsent(id, k -> slowDbFind(k))? Its docs warn: "Some attempted update operations on this map by other threads may be blocked while computation is in progress, so the computation should be short and simple" (API docs). A 50 ms database call is neither, so the map holds a future, which is created instantly.
  • Kotlin uses coroutines (L29): a Mutex guards a plain map of Deferred loads. Here getOrPut is safe, because the mutex makes the whole check-then-act atomic. The docs describe Mutex as "Mutual exclusion for coroutines" whose lock "happens-before every subsequent successful lock" (Mutex API docs), just like synchronized.
  • Both remove the in-flight entry when the load finishes, success or failure, and pass a failure on to every waiter, so one bad load doesn't wedge the key forever.

Which entry to throw away

A cache is smaller than the data behind it, so when it's full something must go. The three classic eviction policies are LRU (least recently used), LFU (least frequently used) and FIFO (oldest inserted). Real traffic is skewed: a few books get most of the requests. The simulation below uses a Zipf-like distribution, where the r-th most popular key is requested in proportion to 1/r, with a fixed seed:

Zipf only
  LRU  hit rate 57.7%
  LFU  hit rate 56.3%
  FIFO hit rate 52.2%
Zipf + a one-off scan of 500 cold keys every 1,000 requests
  LRU  hit rate 55.4%
  LFU  hit rate 60.1%
  FIFO hit rate 50.7%

Both languages print identical numbers (same seed, same java.util.Random). With a cache holding 10% of the keys, all three policies serve over half the requests, which is the power of skew. FIFO is worst: it evicts popular keys just because they're old. LRU wins on plain skewed traffic. But add occasional scans (a report or a crawler touching hundreds of keys once each) and LRU loses: every scanned key becomes "most recently used" and pushes hot keys out. LFU ignores one-off keys, so it wins there. Plain LFU has its own weakness, visible in the first result: a new key starts with a count of 1, so it's the first evicted even if it's about to become popular.

Production caches combine both ideas. Caffeine "uses the Window TinyLfu policy due to its high hit rate and low memory footprint": a small LRU window in front of a frequency-based main area (Caffeine wiki: Efficiency). Redis's LRU is approximate on purpose: it "samples a small number of keys at random and then evicts the ones with the longest time since last access" (Redis docs: Key eviction).

Check

In cache-aside, what should a write do with the cached copy of the row it changed?

Write the source of truth, then invalidate. The next read misses and loads the fresh row. Updating the cache instead risks storing a value computed from stale data.

Which pattern lost three acknowledged sales when the process halted?

Write-behind acknowledges writes once they're in the cache and flushes later. Anything still queued at a crash is gone: the database still said dune=7 after five sales.

With a 300 ms TTL, an update made directly in the database is visible through the cache after at most...

The cached entry lives at most 300 ms, so 300 ms is the worst-case staleness. The run showed 345 ms only because it polled every 50 ms.

Why does coalescing put a CompletableFuture in the map instead of calling computeIfAbsent(id, k -> slowDbFind(k))?

The docs say the computation "should be short and simple" because other updates to the map may block meanwhile. Creating a future is instant; the slow query runs outside the map.

Why did LFU beat LRU once scans of one-off keys were added?

Each scanned key becomes LRU's most recently used entry and pushes hot keys out. LFU ranks by count, and a key seen once can't displace a key seen hundreds of times.

Part 3

A thread-safe LRU cache from scratch

~25 min

In L19 an LRU cache took three lines of LinkedHashMap. Now build what's inside it, because the structure is a classic interview question and because you need to own it to add TTLs and thread safety:

  • A HashMap<K, Node> finds a key's node in O(1) (L19).
  • A doubly linked list of those nodes keeps them in recency order: most recently used next to the head sentinel, least recently used next to the tail sentinel. Moving a node to the front and dropping the last node are both O(1) pointer swaps (L17). The two sentinels mean no step ever has to special-case an empty list.
  • Each node also stores when it expires. The time comes from an injected Clock (L38), so tests can move time forward instantly.
  • One ReentrantLock guards the map and the list together, because every get writes (it moves a node). There's no such thing as a read-only LRU lookup (L26).

Set the project up as in L11 (gradle init), with org.xerial:sqlite-jdbc:3.53.4.0 added for the final. Write the tests first if you can.

Two details worth copying. An expired entry is removed the moment a read finds it, so it doesn't sit in the cache taking a slot. And put on an existing key updates in place instead of evicting someone to make room for a key that's already there.

The surprise is the 8-thread line: 8 times the work took about 26 times as long. Adding threads made total throughput worse, because one lock lets one thread in at a time and the rest queue up and hand the lock around (L26). That's why production caches don't use one lock:

  • Striping splits the cache into, say, 16 segments by key hash, each with its own lock and its own LRU list, so threads touching different segments don't wait for each other. The price: eviction is only "least recently used within a segment".
  • Caffeine goes further: reads record their access in a buffer and the reordering happens later, in batches, so a get almost never waits for a lock. Its wiki describes it as "a high performance Java caching library providing a near optimal hit rate" (Caffeine wiki). In real code, use Caffeine; write your own only to learn, as here.

Bridge. Spring's cache abstraction lets you put @Cacheable on a method: "the Spring Framework provides support for transparently adding caching to an existing Spring application" (Spring docs: Cache Abstraction), with Caffeine or Redis as the store behind it. That's the read-through decorator from Part 2, generated for you. On Android, image loaders keep exactly this two-level structure: Coil's ImageLoader "keeps a memory cache of recently decoded Bitmaps as well as a disk cache for any images loaded from the Internet" (Coil docs), and Glide "checks multiple layers of caches before starting a new request for an image" (Glide docs: Caching).

What Kotlin does for you.
  • lock.withLock { } is lock() + try/finally unlock() in one inline call. Java writes the try/finally by hand in every method, and forgetting unlock() on one path is a deadlock waiting to happen (L27).
  • Because withLock is inline, return null inside it returns from get itself (L14's non-local return).
  • K : Any forbids null keys at compile time. Java's HashMap accepts a null key, and the cache would quietly cache it.
  • data class Stats gives equals, so a test compares all three counters in one assertEquals. Java's record does the same.
  • Test names in backticks read as sentences in the Gradle report.

Check

Why does an LRU cache need a linked list as well as a hash map?

The map finds a node; the list keeps recency order. Moving a node to the front and removing the tail are constant-time pointer changes, which an array or tree can't match.

Why must get take the lock, even though it only "reads"?

A hit moves the node to the front: four pointer writes. Without the lock, two threads did that at once and the list broke, giving NullPointerExceptions and a cache 10× over capacity.

How does the TTL test check expiry without sleeping for 10 seconds?

The cache reads time from a Clock passed in (L38). The test passes a FakeClock and moves it forward 9 s, then 1 s more, instantly.

With one lock, 8 threads did 8× the work in about 26× the time. Why?

Every operation queues for the same lock, and handing it between cores costs extra. That's why real caches stripe their locks or, like Caffeine, buffer reads and reorder later.

Capacity 2: put a, put b, peek(a), put c. Which key is evicted?

peek doesn't change recency, so a is still the least recently used. A get(a) would have saved it and evicted b.

Wrap-up

Exit quiz, recall card, sources

~5 min

An LRU cache needs a doubly linked list. Why doubly linked, not singly? (L17)

Removing a node from the middle needs its predecessor. With a prev pointer you have it immediately; a singly linked list would have to walk from the head, which is O(n).

Your cache uses Book objects as keys. What must Book provide for lookups to work? (L7, L19)

Hash lookups use hashCode to find the bucket and equals to find the key. A data class or record generates both, which is why ids and records make good cache keys.

Which executor did the final's HttpServer use so that thousands of blocked requests stay cheap? (L28)

A virtual thread per request: waiting on the 20 ms database or on a coalesced future parks the virtual thread and frees its carrier. A single thread would serve one request at a time.

A PUT writes the book in a transaction, then invalidates the cache. When must the invalidation happen? (L36)

Invalidate too early and a concurrent read can reload the old, still-committed row into the cache. Invalidate after commit, so the next miss can only see the new value.
