Part 1

JSON and serialisation

~35 min

JSON (JavaScript Object Notation) is a text format with exactly six kinds of value: objects ({"key": value, …}, keys are always strings), arrays ([v1, v2]), strings (double quotes only, Unicode, with backslash escapes like \" and \n; L2), numbers, true/false, and null. That's the whole grammar (RFC 8259; json.org draws it as railroad diagrams). There are no comments, no trailing commas, no dates and no distinction between integers and decimals.

Serialisation turns an object into JSON text, and deserialisation turns text back into an object. The Kotlin docs define it as "converting data used by an application to a format that can be transferred over a network, or stored in a database or a file" (Kotlin docs: Serialization). The class you serialise is usually called a DTO (data transfer object): a data class or record that mirrors the JSON.

{"id":1,"title":"Dune","year":1965,"tags":["sci-fi","classic"],"subtitle":null}
Book(id=1, title=Dune, year=1965, tags=[sci-fi, classic], subtitle=null)
equal after round trip: true
{

    "title": "Dune",
    "year": 1965,
    "tags": [
        "sci-fi",
        "classic"

    "subtitle": null
}
{"id":1,"title":"Dune","year":1965,"tags":["sci-fi","classic"],"subtitle":null}

  "year" : 1965,
  "tags" : [ "sci-fi", "classic" ],

The compact JSON is byte-for-byte identical. Only the pretty-printing style differs. Property names come from the Kotlin property names and from the record component names, in declaration order. A Kotlin List<String> becomes a JSON array, and null becomes null.

Numbers: the 253 trap

JSON's grammar puts no limit on numbers, but RFC 8259 §6 warns that most software reads them as IEEE 754 doubles (L2), and only "integers … in the range [-(2**53)+1, (2**53)-1] are interoperable in the sense that implementations will agree exactly on their numeric values" (RFC 8259 §6). JavaScript reads every JSON number as a double. So a 64-bit id from a JVM backend can arrive in a browser slightly wrong:

Long:   9007199254740993
Double: 9007199254740992  re-encoded: {"id":9.007199254740992E15}
String: 9007199254740993
0.1 + 0.2 = 0.30000000000000004
10 + 20 cents = 30

Both languages print the same thing. Read as a double, the id quietly became a different id, and re-encoding it produced scientific notation that some clients won't even accept as an id. The defences:

  • Large ids: send them as strings ("id": "9007199254740993"). Many public APIs do.
  • Money: never a floating-point number (L2's 0.1 + 0.2). Send integer minor units ("priceCents": 1299) or a decimal string ("price": "12.99") that you parse into BigDecimal.

Defaults, nulls and missing keys

JSON has three different states for a field: present with a value, present as null, and absent. The two libraries map those states differently:

{"email":null,"theme":"dark"}
{"email":null,"theme":"dark","fontSize":14,"nickname":null}
{"theme":"dark"}
Settings(email=ada@example.com, theme=light, fontSize=14, nickname=null)
MissingFieldException: Field 'email' is required for type with serial name 'Settings', but it was missing at path: $
{"email":null,"theme":"dark","fontSize":14,"nickname":null}
{"theme":"dark","fontSize":14}
Settings[email=ada@example.com, theme=light, fontSize=14, nickname=null]
  • Kotlin: a property with a default is optional. "Properties with default values are optional during deserialization and can be skipped during serialization", and the default JSON configuration "skips encoding default values" (Kotlin docs: Customize serialization). encodeDefaults = true writes them anyway, and explicitNulls = false omits null values (JSON configuration).
  • The surprise: email: String? with no default is still required. Nullable means "may be null", not "may be absent". The last line proves it.
  • Java: a missing key just becomes null in the record (or 0/false for primitives), so defaults are your job. The compact constructor (L7) fills them in. That's why fontSize is an Integer here: an int can't tell you whether the key was there. Leaving out nulls is a mapper setting, Include.NON_NULL.

The plugin also taught us something while compiling the first draft of Defaults.kt. Writing Json { … }.encodeToString(s) inline produced "warning: redundant creation of Json format. Creating instances for each use can be slow." Build each configured Json once and reuse it, as the file now does. The same advice applies to Jackson's JsonMapper.

Data from the network is untrusted input (L10). Here is what each library does with a missing field, a wrong type, and a key the class doesn't have:

The defaults are opposites, and that matters when you switch languages:

Kotlin's docs: "By default, unknown keys … result in an error during deserialization" (JSON configuration). Jackson changed this in version 3. Its design notes list "FAIL_ON_UNKNOWN_PROPERTIES: default to false (TOP REQUEST by users)" (Jackson JSTEP-2), so Jackson 2 tutorials that show this error are now out of date. Ignoring unknown keys is usually what you want for a client: APIs add fields over time, and an old client shouldn't crash. On a server, strictness catches typos like "titel". Jackson's exceptions are unchecked in version 3 (JacksonException extends RuntimeException, checked with javap). In Jackson 2 they were checked IOExceptions, which L10 would have made you catch.

Dates: ISO-8601 strings

JSON has no date type, so the convention is an ISO-8601 string: "2026-10-20T09:30:00Z" for an instant, or "2026-11-03" for a date.

{"book":"Dune","at":"2026-10-20T09:30:00Z","due":"2026-11-03"}
Loan(book=Dune, at=2026-10-20T09:30:00Z, due=2026-11-03)
{"book":"Dune","at":"2026-10-20T09:30:00Z","due":"2026-11-03"}
Loan[book=Dune, at=2026-10-20T09:30:00Z, due=2026-11-03]
  • Kotlin's own kotlin.time.Instant (in the standard library since Kotlin 2.3; API docs) serialised as an ISO string with no extra code. java.time.LocalDate did not, so the file writes a tiny KSerializer: a descriptor saying "this is a string", plus serialize and deserialize. That's the general recipe for any type the library doesn't know.
  • Jackson 3 handles java.time out of the box. Its design notes record that the java-time module was merged into databind, and that WRITE_DATES_AS_TIMESTAMPS now defaults to false "to serialize as ISO-8601 String" (JSTEP-2). In Jackson 2 you needed an extra module, and dates came out as numbers by default.

Renamed fields and sealed hierarchies

JSON often uses snake_case names, and one endpoint may return several shapes of event. @SerialName and @JsonProperty rename a field. For a sealed hierarchy (L7), both libraries add a type discriminator property so the reader knows which subclass to build:

[{"type":"borrowed","book_id":7,"member":"ada"},{"type":"returned","book_id":7,"lateDays":2}]
ada borrowed #7
#7 back, 2 days late

Identical output from both. Kotlin's plugin saw that Event is sealed and found the subclasses itself, using "type" and each class's @SerialName as the discriminator (JSON configuration). Jackson needed the subtypes listed in @JsonSubTypes.

No DTO at all: the tree model

Sometimes you need two values from a big response and don't want to model the whole thing. Both libraries can parse into a generic tree:

city: Oslo
wind: 18
alerts: [yellow, orange]
missing: null
city: Oslo
wind: 18
alerts: [yellow, orange]
missing: true

Kotlin's JsonElement plays well with ?. (L3): an absent key is just null. Jackson's path() never returns null. It returns a "missing node", so a long chain can't throw a NullPointerException. Prefer DTOs for anything you'll keep. The tree model trades type safety for convenience, the same trade as raw types in L13.

Bridge: when a Spring controller method returns a record, Jackson turns it into the response body using exactly the mapping above. Spring Boot also supports Kotlin Serialization (Spring Boot: JSON). On Android, Retrofit is "a type-safe HTTP client … built on top of OkHttp" with "support for several serialization libraries" (Android: Connect to the network). Either way, the DTO rules in this part are the ones that bite.

What Kotlin does for you.
  • Compile-time serializers. The plugin generates the serializer (Book$$serializer), so there's no reflection at runtime, and an unserialisable property is a compile error, not an empty {}.
  • Nullability in the JSON contract. A non-null String property can't silently become null because a key was missing. Java records accept the null and the bug shows up later.
  • Defaults make fields optional with no extra code. Java needs a compact constructor with a null check per field, and boxed types to detect "missing".
  • decodeFromString<List<Event>> works because of reified. Java needs a TypeReference type token.
  • Sealed subclasses are discovered automatically. Jackson needs them listed by hand in @JsonSubTypes.

Part 2

REST: resources, verbs, idempotency

~20 min

REST (Representational State Transfer) is an architectural style that Roy Fielding described in chapter 5 of his dissertation (Fielding, ch. 5). In everyday use, a "REST API" or "RESTful API" means one that follows HTTP's own rules instead of inventing its own:

  • Resources are nouns with URIs. A collection is /books, one item is /books/42, and a sub-resource is /books/42/loans. The URI names a thing. Verbs like /getBook or /deleteBook?id=42 don't belong in it.
  • The HTTP method says what to do with the thing (L31): GET reads, POST creates inside a collection, PUT replaces, PATCH partly updates, DELETE removes.
  • The status code says how it went, and the body carries a representation of the resource: here, JSON.

Safe and idempotent methods

RFC 9110 gives each method two properties, and they're the most practical part of the whole spec:

  • Safe: "the client does not request, and does not expect, any state change on the origin server". "The GET, HEAD, OPTIONS, and TRACE methods are defined to be safe" (RFC 9110 §9.2.1).
  • Idempotent: "the intended effect on the server of multiple identical requests with that method is the same as the effect for a single such request". "PUT, DELETE, and safe request methods are idempotent" (§9.2.2).
  • POST is neither. PATCH "is neither safe nor idempotent", although a PATCH "can be issued in such a way as to be idempotent" (RFC 5789 §2).

Why care? Because networks fail. The RFC again: "Idempotent methods are distinguished because the request can be repeated automatically if a communication failure occurs before the client is able to read the server's response." Remember L28's fetches where 2% failed: a client library, or a proxy, may retry for you. Here is what a retry does to each kind of request when the server did the work but the reply was lost:

POST:
  attempt 1: connection reset before reply, retrying
  orders on the server: {1=Dune, 2=Dune}
PUT:
  attempt 1: connection reset before reply, retrying
  orders on the server: {42=Dune}
POST + key:
  attempt 1: connection reset before reply, retrying
  orders on the server: {1=Dune}
  • POST, retried: two orders. If that was a payment, the customer was charged twice.
  • PUT, retried: "make order 42 look like this", done twice, is the same as done once. Safe to retry.
  • POST with an idempotency key: the client invents a unique key per intended operation and sends it as a header. The server remembers key → result, here with L27's atomic computeIfAbsent, and a retry gets the original result back. It's a widespread industry pattern. An IETF draft tried to standardise an Idempotency-Key header, but it has expired without becoming an RFC (IETF datatracker).

  • PUT can also create. It "requests that the state of the target resource be created or replaced" (§9.3.4), so a PUT to a new id may answer 201. The final keeps it simple and answers 404, which is a legitimate choice when the server assigns the ids.
  • 400 or 422? 422 means "the syntax of the request content is correct, but it was unable to process the contained instructions" (§15.5.21), a good fit for validation failures. Plenty of APIs use 400 for everything the client got wrong. Pick one and document it. The final uses 400.

Statelessness and hypermedia

Fielding's stateless constraint: "each request from client to server must contain all of the information necessary to understand the request, and cannot take advantage of any stored context on the server" (ch. 5.1.3). Every request carries its own auth token and its own page number, so any server instance can answer it. That's what makes it easy to put ten copies of a service behind a load balancer (Phase 12).

Fielding also listed "hypermedia as the engine of application state" (HATEOAS) among REST's interface constraints (ch. 5.1.5): responses should contain links to what the client can do next, the way web pages do. Most JSON APIs only go part of the way. Martin Fowler's write-up of the Richardson Maturity Model grades this: Level 1 adds resources, Level 2 adds HTTP verbs, and Level 3 adds hypermedia controls (Fowler: Richardson Maturity Model). The final sits at level 2, plus one hypermedia touch: a next link in each page.

Not everything is REST. RPC APIs expose actions (POST /chargeCard) rather than resources. GraphQL sends one query to one endpoint and gets back exactly the fields it asked for. gRPC uses binary Protocol Buffers over HTTP/2 with generated clients. You'll meet all three. REST over JSON is the default for public HTTP APIs, and the one Spring and Android tooling are built around.

Bridge: Spring's annotated controllers map onto this table one to one. A class marked @RestController with a method annotated @GetMapping("/books/{id}") becomes the GET /books/42 row (Spring: Annotated Controllers). On Android, a Retrofit interface declares the same rows from the client side.

What Kotlin does for you.

Nothing new here, honestly: HTTP semantics are language-neutral, and both versions of Retry use the same JDK classes. Kotlin's conveniences are the usual ones: a to b pairs and destructuring for ((name, call) in scenarios) instead of Map.Entry; lambdas that return values without a Supplier wrapper; no UncheckedIOException dance, because IOException isn't checked (L10); and an exhaustive when over an enum, as in the exercise.

Notice that DELETE is idempotent but not safe: it changes state, but deleting twice leaves the same state as deleting once. The status code may differ on the retry (204 then 404, as the final's test checks), and that's allowed: idempotency is about the effect on the server, not the response.

Check

Which method is idempotent but not safe?

PUT changes state, so it isn't safe, but repeating it has the same effect (§9.2.2). GET is both. POST and PATCH are neither by default.

A client retries a plain POST after its reply was lost. The risk?

Retry ended with {1=Dune, 2=Dune}. Idempotency keys or PUT to a client-chosen id avoid it.

A DELETE succeeded and there's nothing to send back. Which status?

204 No Content. The final sends it with sendResponseHeaders(204, -1), where -1 means "no response body may be written".

What does REST's stateless constraint require?

Fielding: each request "must contain all of the information necessary to understand the request". The server can still store resources. What it mustn't keep is per-client conversation state.

According to RFC 5789, PATCH is…

"PATCH is neither safe nor idempotent", though a particular PATCH can be designed to be idempotent.

Part 3

API design

~20 min

An API is a user interface for programmers, and it's very hard to change once other people depend on it. A handful of conventions make one predictable:

  • Names: plural nouns for collections (/books, not /book or /bookList). Pick one JSON naming style, camelCase or snake_case, and never mix them. The final uses camelCase because both libraries produce it from Kotlin and Java names with no configuration.
  • Filtering and sorting go in the query string: /books?author=herbert&sort=year.
  • Pagination: never return an unbounded list. Offset paging (?limit=10&offset=20) is simple and lets you jump to a page, but items shift between pages if someone inserts while you're paging. Cursor paging (?after=opaqueToken) is stable under inserts but can't jump. Either way, give the client the next link rather than making it build URLs.
  • Versioning: a path prefix (/v1/books) is the most visible option; a header is the cleaner one. Add fields freely, since clients should ignore unknown ones (Part 1). Removing or renaming a field is a breaking change that needs a new version.
  • Validate at the boundary (L10): parse the input, check every rule, and report all the failures at once, so the client can fix everything in one round trip.
  • One error format everywhere. That's what RFC 9457 is for.

Problem Details (RFC 9457)

Status codes "cannot always convey enough information about errors to be helpful", so RFC 9457 defines a standard JSON error body, "problem details", with the media type application/problem+json (RFC 9457 §1, §3). Its members (§3.1):

MemberMeaning (quoted)
type"a URI reference … that identifies the problem type". When it's absent "its value is assumed to be about:blank"
title"a short, human-readable summary of the problem type". It "SHOULD NOT change from occurrence to occurrence"
statusthe HTTP status code. It's "only advisory", and generators "MUST use the same status code in the actual HTTP response"
detail"a human-readable explanation specific to this occurrence of the problem"
instance"a URI reference that identifies the specific occurrence of the problem"

You may add your own extension members (§3.2). The final adds errors, a list of every validation failure. For plain HTTP errors like 404 and 405, type is about:blank and title is the status phrase (§4.2.1).

Here's the design toolkit for the final as plain functions: a generic page envelope with a next link, a validator that collects every error, and a Problem body:

{"items":[{"id":1,"title":"Book 1","year":2001},{"id":2,"title":"Book 2","year":2002}],"limit":2,"offset":0,"total":5,"next":"/books?limit=2&offset=2"}
{"items":[{"id":5,"title":"Book 5","year":2005}],"limit":2,"offset":4,"total":5}
{"type":"https://example.com/problems/validation","title":"Invalid book","status":400,"detail":"2 field(s) failed validation","errors":["title must not be blank","year must be between 1450 and 2100"]}

Identical in both. The last page has no next member at all, because explicitNulls = false and @JsonInclude(NON_NULL) drop null members. That's how the client knows it has reached the end. The type URI is on example.com, a domain reserved for documentation. In a real API it would point to a page that explains the error, which the RFC encourages.

Optimistic concurrency, briefly. Two clients GET book 7, both edit it, both PUT: the second silently overwrites the first. That's L26's lost update again, across the network. L31's ETag fixes it: the client sends If-Match: "<etag it read>" with its PUT, and the server answers 412 Precondition Failed if the book has changed since. It's a good extension for your final once it works.

What Kotlin does for you.
  • Generics: a generic @Serializable data class Page<T> just works. The plugin generates a serializer that takes the element serializer as a parameter.
  • One switch for the whole format: explicitNulls = false on one Json instance. Jackson's equivalent is an annotation on each record, or a mapper-wide inclusion setting.
  • Less ceremony: buildList { … } builds the error list in place, in 1450..2100 replaces two comparisons, and drop/take replace stream().skip().limit().
  • Smart casts: sealed results like Invalid/PageParams in the exercise are checked exhaustively with when, and narrowed for you.

Check

Which Content-Type does RFC 9457 define for a JSON error body?

"Problem details" serialized as JSON use application/problem+json. The final's tests assert exactly that header on a 404.

A 405 Method Not Allowed response MUST include which header?

RFC 9110 §15.5.6: "The origin server MUST generate an Allow header field in a 405 response", listing the methods the resource does support.

Why report every validation error, rather than stopping at the first?

Stopping at the first error forces one round trip per mistake. The errors extension member lists them all.

What's the weakness of offset pagination (?offset=20)?

If a book is inserted before your offset while you page, everything moves along by one: you see one item twice, or skip one. Cursors avoid it. The offset style stays stateless either way.

A JSON API on the JDK's HttpServer

~25 min (more if you test-drive it)

Build a books API from a blank Gradle project, Kotlin first and then Java, with no web framework. The JDK ships an HTTP server in the jdk.httpserver module: "the JDK-specific HTTP server API", whose com.sun.net.httpserver package "defines a high-level API for building servers that support HTTP and HTTPS" (module docs). It's a supported, documented API, but deliberately minimal. Routing, JSON and error handling are up to you, and writing them is the point.

The API:

RequestResponse
GET /books?limit&offset200 page envelope; defaults 10/0; limit 1..100; next link; bad params → 400
POST /booksvalidates (title required and not blank; year required, 1450..2100) → 201 + Location + book
GET /books/{id}200 book, or 404
PUT /books/{id}validates → 200 book, or 404
DELETE /books/{id}204, or 404
anything else404; wrong method → 405 + Allow; malformed JSON → 400
  1. Every error body is RFC 9457 Problem Details, with Content-Type: application/problem+json. Validation failures add an errors list.
  2. Store books in a ConcurrentHashMap with an AtomicLong for ids (L27). Handlers run concurrently.
  3. Run each request on a virtual thread: server.setExecutor(Executors.newVirtualThreadPerTaskExecutor()) (L28). The docs: "All HTTP requests are handled in tasks given to the executor", and without one "a default implementation is used, which uses the thread which was created by the start() method", one thread for everyone (HttpServer.setExecutor).
  4. Bind to 127.0.0.1, accept port 0 so tests get a free port, and make main stop the server after N seconds. Never leave a server running.
  5. Serialise with kotlinx.serialization in Kotlin and Jackson 3 in Java.

Test-first, in this order (L11), each with java.net.http.HttpClient (L31) against the running server:

  1. POST returns 201, Location: /books/1, and the book.
  2. GET returns the book, and an unknown id gives a 404 problem with the right content type.
  3. Invalid input lists every error.
  4. Malformed JSON and wrong types give 400, not 500.
  5. The list pages with a next link, the last page has none, and limit=0 is a 400.
  6. PUT replaces; DELETE gives 204, then 404.
  7. PATCH on /books gives 405 with Allow: GET, POST.

Four things the JDK server makes you handle yourself, all from its docs:

  • createContext("/books", handler) matches by "the longest matching prefix of the request URI's path", compared "literally" (HttpServer). So /booksXYZ also reaches your handler. Check the first path segment.
  • sendResponseHeaders(code, length): a length > 0 is an exact byte count, 0 means chunked encoding, and -1 means "no response body may be written" (HttpExchange). Use -1 for 204, and measure the length in UTF-8 bytes, not characters (L2).
  • Set headers before sendResponseHeaders; afterwards they're already on the wire (L30).
  • HttpExchange implements AutoCloseable, and an exchange ends when its streams are closed, so wrap each one in use { } / try-with-resources (L10).

Wrap-up

Exit quiz, recall card, sources

~5 min

Why does the final store books in a ConcurrentHashMap? (L27)

With a virtual-thread executor, every request runs on its own thread at the same time. A plain HashMap under concurrent writes can lose entries or corrupt itself, as L26 showed.

Why does Jackson need new TypeReference<List<Event>>() {}? (L13)

Erasure leaves only List at runtime. The anonymous subclass's class file records the full type argument, so Jackson can read it back. RawList.java showed the crash without it.

Kotlin, books is a ConcurrentHashMap<Long, String>: println(1L in books) (L19)

Kotlin rejects it, because in would call the legacy contains(value), which checks values. Say containsKey.

With server.setExecutor(Executors.newVirtualThreadPerTaskExecutor()), each request gets… (L28)

One cheap virtual thread per task, which unmounts from its carrier while it blocks on I/O. Without setExecutor, the server would handle every request on the single thread created by start().
