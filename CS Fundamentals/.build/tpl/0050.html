Part 1

Two pointers and sliding windows

~25 min

Many slow programs have the same shape: for (i …) for (j …), where the inner loop starts again from scratch every time. That's O(n²) (L16). Two related patterns fix it when the input has the right structure. In both, two indices only ever move forward, so together they take at most 2n steps.

Two pointers: pair sum on a sorted array

Problem: in a sorted array, find two values that add up to a target. Sedgewick & Wayne's brute-force 2-sum "takes time proportional to N^2", and their faster version, which runs a binary search for each element, solves it "in time proportional to N log N time" (algs4 §1.4). If the array is already sorted, two pointers do it in O(n). Start one index at each end and move one of them inward on every step:

Why it's correct. This is an L48 loop invariant: if a pair exists, both of its indexes are between lo and hi. It's true at the start. Each step keeps it true. If a[lo] + a[hi] is too small, then a[lo] plus any remaining value is too small too, because a[hi] is the largest one left. So no pair can use a[lo], and discarding it is safe. The "too big" case is the mirror image. The loop ends when the pointers meet, after at most n − 1 steps.

Dedupe in place. The second function uses a slow pointer (where the next unique value goes) and a fast pointer (the value being examined). L16's uniqueFast needed a whole HashSet; on a sorted array, duplicates sit next to each other, so O(1) extra memory is enough. The "whole array" in the output shows that the tail past the new length still holds leftovers. Only the first 5 slots are meaningful, which is how in-place algorithms usually report their result.

Now the doubling test from L16, on the worst case for both: all values even, the target odd, so no pair is ever found:

That's the Kotlin run; Java's shows the same ratios. The brute force quadruples each time n doubles, as O(n²) should, and the two-pointer ratios sit near 2. The step counts are exact: n(n − 1)/2 against n − 1. Notice that the brute force does 3.2 billion steps in about 350 ms, roughly 9 steps per nanosecond. A loop this simple gets unrolled and vectorised by the JIT (L16 previewed it; L23 opens it up), but that only changes the constant. At n = 80,000 the two-pointer version would take about 0.04 ms, against 350.

Sliding windows

A sliding window is a contiguous range [left, right] that moves through the input. When the window moves, you update its summary (a sum, a count, a set of characters) for the one element entering and the one leaving, instead of recomputing it. Use one whenever a problem says contiguous (a substring, a run of days) together with longest, shortest, at most or every window of size k.

  • Fixed size k: add the element that enters on the right and subtract the one that leaves on the left. Each slide costs O(1), so the whole pass is O(n), not O(n·k).
  • Variable size: grow on the right; whenever the window breaks the rule, shrink it from the left until it's valid again. right moves n times and left only moves forward, so the total work is O(n) even though there's a loop inside a loop.

Both languages print the same thing. In longestUnique the window never actually shrinks one step at a time. lastSeen remembers where each character was last seen, so when a repeat arrives, left jumps straight past the earlier copy. The prev >= left check matters: a character last seen before the window (like the first a once left has passed it) is no repeat at all. The best 3-day total is 9 + 4 + 6 = 19.

The same doubling test, comparing the window with the obvious "restart from every position" version, on the worst case of a string where nothing ever repeats. Both versions track characters in a 65,536-slot array, one slot per Char value (L2), so we compare the algorithms rather than HashMap overhead:

Kotlin on the left, Java on the right. The restart version quadruples with every doubling, in both languages. The window stays under 0.1 ms at every size, which is below what this simple harness can measure reliably, so ignore its small wobbles (L16). Look at the absolute numbers, though. The same brute force took about 240 ms in Kotlin and 39 ms in Java. That isn't Kotlin being slower: both compile to the same simple loop of bytecode (check with javap -c), and when I compiled the Java file with javac and ran the class, it took 251 ms too. Only java WindowTiming.java, the source launcher, gave 39 ms, and I didn't track down which JIT decision differs. It's a real example of why L16 told you to trust ratios, not raw milliseconds, and why L24 reached for JMH.

Window maximum with a monotonic deque Optional deep dive

A harder window question: the maximum of every window of size k. A running sum can't do it, because when the maximum leaves the window you don't know the next largest. The trick is a deque of indexes whose values are kept decreasing from front to back, so the front is always the window's maximum:

  • Before pushing a[i], pop every smaller-or-equal value from the back. They leave the window before a[i] does and are no bigger, so they can never be a maximum again.
  • If the front index has slid out of the window, drop it.

There's a while loop inside the for, but every index is pushed exactly once and popped at most once, so the total work is O(n). That's the amortised argument from L16's doubling array, applied to a deque. The JDK docs say "Most ArrayDeque operations run in amortized constant time", and that the class "is likely to be faster than Stack when used as a stack, and faster than LinkedList when used as a queue" (ArrayDeque). The third tab of the widget above steps through it. The last line is a differential test: 10,000 random inputs checked against the obvious O(n·k) version. Part 4 turns that idea into a reusable tool.

What Kotlin does for you.
  • return lo to hi builds a Pair, and the result prints as (1, 5). Java has no standard pair type, so it returns an int[] and needs Arrays.toString to print it.
  • A when with no subject replaces an if/else if ladder, and every branch is an expression.
  • for ((right, c) in s.withIndex()) gives you the index and the character together. Java writes an index loop and calls s.charAt(right).
  • ArrayDeque is in the standard library with no import (L17), and its first()/last() read better than peekFirst()/peekLast(). They throw on an empty deque instead of returning null, which is why both versions check isNotEmpty() first.
  • require(k in 1..a.size) is one line; Java spells out the range check and the throw.

Exercise: shortest run with sum at least target

From a blank file, in both languages. Given an array of positive integers and a target, return the length of the shortest contiguous run whose sum is at least the target, or 0 if there is none. [2, 3, 1, 2, 4, 3] with target 7 gives 2 (the run [4, 3]). [1, 4, 4] with 4 gives 1. [1, 1, 1] with 11 gives 0. Reject non-positive numbers with IllegalArgumentException. Aim for O(n). Then answer: why does the window need every number to be positive?

Solution

The inner loop is a while, not an if: one new element on the right can make several shorter windows valid. Part 4 catches exactly that bug automatically. Why positive? Shrinking from the left has to lower the sum and growing on the right has to raise it. With negative numbers, dropping an element can raise the sum, so a window you gave up on could become valid again later, and the "left only moves forward" argument breaks.

16 is too big, and even the smallest partner (1) is too much for 15, so no pair can use 15. Move hi left. The trace above shows it.

Why is it safe to discard a[lo] when a[lo] + a[hi] is below the target?

a[hi] is the largest value still in range. If even that isn't enough, nothing is, so no pair uses a[lo] and the invariant survives.

Part 2

Backtracking

~25 min

Some problems really do ask for every combination: every subset, every ordering, every placement. Jeff Erickson defines the strategy: "A backtracking algorithm tries to construct a solution to a computational problem incrementally, one small piece at a time. Whenever the algorithm needs to decide between multiple alternatives to the next component of the solution, it recursively evaluates every alternative and then chooses the best one" (Algorithms, ch. 2: Backtracking). In code it's always the same three moves around a recursive call:

  1. Choose: add one piece to the partial solution.
  2. Explore: recurse to extend it.
  3. Un-choose: remove the piece again, so the partial solution is exactly as it was before the choice.

The partial solutions form a tree: the root is "nothing chosen", and each child adds one more choice. Erickson again: "The backtracking search for complete solutions is equivalent to a depth-first search of this tree." It's L21's DFS on a tree you never build, with L18's recursion keeping the path on the call stack.

Subsets and permutations

Both languages print the same thing. The counts are L48's product rule: each item is in or out, so there are 2n subsets. A permutation has n choices for the first slot, n − 1 for the next, and so on, so there are n!. Neither can be generated in less time than it takes to write the answers out. At 20 items, 1,048,576 subsets is fine; 20! orderings (2.4 × 1018) is not. Backtracking is only fast when it can skip most of the tree, which is the next section.

The classic bug. out += current.toList() stores a copy. Store current itself and you get this:

Six references to one list (L4), which the un-choose steps emptied by the end. val or final wouldn't have helped either: they protect the reference, not the list (L5).

Pruning: N-queens

Erickson calls the n-queens problem "the prototypical backtracking problem": place n queens on an n × n board so that "no two queens are in the same row, the same column, or the same diagonal". Put one queen per row and, for each row, try each column. The key move is pruning: if a square is already attacked, don't recurse at all. One whole subtree of the search disappears with each skipped square. Three boolean arrays make the attack check O(1). Along one diagonal, row + col is constant; along the other, row − col is (shifted by n so it's never negative).

  • The answers are right. Every count matches the On-Line Encyclopedia of Integer Sequences, entry A000170: "Number of ways of placing n nonattacking queens on an n X n board". The check would have thrown otherwise. Java's run prints the same counts with timings within a few percent.
  • Pruning is enormous. For n = 8, brute force checks all 88 = 16,777,216 complete boards. The pruned search visits 2,057 partial placements, about 8,000 times fewer.
  • It's still exponential. From n = 11 on, each extra queen multiplies the nodes, and the time, by about 5. Pruning shrinks the base of the exponent; it doesn't remove it. L51 asks whether that's avoidable in general.

Step through 4-queens. Hatched squares are attacked by a queen already placed. A green outline is a safe try, and a red ✕ is a pruned one. Press Play to watch the search go deep, hit a dead end, back up and try again. It finds both solutions in 79 steps.

Stopping early

Often you want the first solution, or the first few. A backtracking search that collects everything into a list can't stop. Kotlin's sequence { } builder can: it "Builds a Sequence lazily yielding values one by one. If the consuming code stops iterating the sequence before it's completed, the remainder of the computation will not run at all" (Kotlin API: sequence). Java has no equivalent, so the visitor returns false to mean "stop", and every level of the recursion passes it back up:

Both languages print the same thing. take(3) built 3 permutations out of 3,628,800. But the second search shows the catch: to reach the first permutation that starts with 10, the search had to build every permutation starting with 1 to 9 first, which is 9 × 9! = 3,265,920 of them, plus the one it wanted. A search order that tried 10 first, or pruned "first item isn't 10" at the root, would build one. Prune as early in the tree as you can.

What Kotlin does for you.
  • Local functions. "A local function can access local variables of outer functions (the closure)" (Kotlin docs: Local functions). So go() sees out, current and used directly. Java has no local functions, so every helper takes the shared state as parameters, or the state becomes fields, as in NoCopy.java.
  • The sequence builder turns a recursive search into a lazy stream with one yield. The local function is a suspend extension on SequenceScope so that it's allowed to call yield. In Java you either collect everything or thread a "stop" flag through every call.
  • current.toList() and Java's List.copyOf(current) both copy. Kotlin's += on a MutableList is add, so out += current compiles happily and stores the reference. That's the bug above, in either language.

Why does the N-queens search visit 2,057 nodes for n = 8 instead of checking 16,777,216 boards?

In which order does backtracking explore the tree of partial solutions?

Each recursive call goes one level deeper before trying the next sibling. Erickson: the search "is equivalent to a depth-first search of this tree".

Part 3

Tries

~20 min

A HashMap (L19) answers "is sea a word?" in O(1). It can't answer "which words start with se?" without looking at every key. A sorted TreeMap (L20) can, but every comparison along the way compares whole strings. A trie (from retrieval, usually pronounced "try") is built for string keys. Sedgewick & Wayne state its goal as "as fast as hashing, more flexible than binary search trees", and it "can efficiently support additional operations including prefix and wildcard matching" (algs4 §5.2 Tries).

The idea: one node per distinct prefix. The path from the root spells the prefix one character at a time, and a flag marks the nodes where a whole word ends. Words that share a prefix share those nodes.

  • Sharing. 7 distinct words with 27 letters need only 20 nodes: the root plus one per distinct prefix. sea, sells, she, shells and shore all share the s node.
  • "Is a word" vs "is a prefix". se is on a path, so hasPrefix is true, but it isn't a word end, so contains is false.
  • Cost. The algs4 trie's docs: put, contains and longest-prefix "take time proportional to the length of the key (in the worst case)" (TrieST.java). Finding a prefix doesn't depend on how many words are stored. Ours keeps children in a TreeMap, which "provides guaranteed log(n) time cost for the containsKey, get, put and remove operations" (TreeMap). Here n is a node's child count, at most 26 for lowercase letters, so each step is a small constant. The sorted children are also why withPrefix returns words in alphabetical order for free.
  • Arrays instead of maps. algs4's TrieST "uses a 256-way trie": every node holds an array of 256 links, one per extended-ASCII character. That makes each step a single array index, but most links are null. Its ternary search trie (TST) is the memory-friendly alternative.

A trie vs the alternatives, on a real book

Download Alice's Adventures in Wonderland from Project Gutenberg as plain text (UTF-8) and save it as data/alice.txt. Then compare three ways of answering prefix queries over every distinct word, split with L3's rule: a word is a run of letters, compared in lowercase.

Kotlin on the left, Java on the right. The two sink values differ because Kotlin's and Java's Random(50) shuffle the prefixes differently. The memory figures come from Runtime after a few System.gc() calls, so treat them as rough. Reading the results:

  • Scan the list: simplest, no extra memory, and about 7–9 µs per query. That's fine for 2,575 words, but it grows linearly with the dictionary.
  • Trie: 7,302 nodes for 15,727 letters, because shared prefixes are stored once. It answers about 5–8 times faster, and the cost of finding the prefix doesn't depend on the dictionary's size.
  • Prefix map: fastest by far, since each answer is precomputed and a lookup is one hash. But it stores every prefix as its own string (40,094 characters of keys) and lists every word once per prefix (15,727 slots). Each word of length L adds L keys and L list entries, and every insert or delete must update all of them.
  • A 256-way array trie on the same words would hold 7,302 × 256 = 1,869,312 links. At 4 or 8 bytes per reference, that's 7.5–15 MB of mostly null.

There's no single winner. That's the L21 lesson about choosing collections again: pick by the operations you need and how often you'll do them.

Where tries show up. Sedgewick & Wayne's motivating example is routing: an "IP routing table wants to forward to 128.112.136.12, instead forwards to 128.112 which is longest matching prefix that it knows about" (§5.2). That longest-prefix match is a walk down a trie that remembers the last word end it passed. Phone keyboards and IDE completion lists need the same "everything under this prefix" query as today's final.
What Kotlin does for you.
  • children[c] ?: return null walks one step or leaves the function, in one expression. Java needs a get, a separate null check and a return.
  • find(word)?.isWord == true handles the "not found" case in one line, because null == true is simply false.
  • var nodes = 1; private set is a property anyone can read but only the class can change. Java writes a private field plus a nodes() getter.
  • getOrPut(c) { nodes++; Node() } runs its block only when the key is missing, like Java's computeIfAbsent. The block's last expression is the value to store, so it can count first.
  • Both versions box each char into a Character map key. Kotlin hides the boxing; it doesn't avoid it (L5).
Exercise: count words by prefix in O(prefix length)

From a blank file, in both languages. Write a CountingTrie with insert(word), contains(word) and countPrefix(prefix), which returns how many inserted words start with prefix. countPrefix must not visit the words below the prefix, so it must cost O(prefix length) no matter how many words match. Inserting the same word twice counts it once. For "she sells sea shells by the sea shore": "" → 7, "s" → 5, "sh" → 3, "shel" → 1, "x" → 0. Hint: what could each node remember while you insert?

Solution

Each node stores pass, the number of words whose path goes through it. Insert adds 1 along the path, and the answer is the pass of the prefix's node. The contains check at the top stops a duplicate from being counted twice. This is the same move as L20's size-augmented tree: store a summary in each node at insert time, then read it in O(1) later.

Check

A trie holds to, tea and ten. How many nodes does it have, counting the root?

One node per distinct prefix: t, to, te, tea, ten. That's 5, plus the root makes 6. The three words have 8 letters, but t and te are shared.

Finding a prefix's node in a trie takes time that grows with…

One step per character of the prefix, whatever else is stored: "time proportional to the length of the key". Collecting the matches afterwards costs extra, in proportion to how many there are.

The prefix map answered queries about 15× faster than the trie. What did it cost?

7,301 separate key strings (40,094 characters) and every word repeated once per prefix. More memory, and every insert or delete touches L entries.

Your own judge: a stress tester

Without an online judge, how do you know a practice solution is right? Write the obviously correct slow version too, and compare the two on thousands of small random inputs. Generate small inputs first, so the first counterexample is short enough to debug by hand. It's the differential test from the window-maximum section, made generic with L13's generics and L14's function types:

The buggy version uses if where the window needs while, Part 1's exercise trap. It fails within a dozen trials. Kotlin found [1, 1, 4] with target 4: when the 4 arrives, the window shrinks once, to [1, 4], and stops, so it never reaches [4] on its own. The two languages report different counterexamples only because kotlin.random.Random(50) and java.util.Random(50) produce different streams. The fixed version survives 10,000 trials. That doesn't prove it's correct, but it's strong evidence, and it's how you'll check every practice problem below.

What Kotlin does for you.
  • gen: (Random, Int) -> T is a function type you can read at a glance. Java has to pick the right interface: BiFunction<Random, Integer, T>, with Integer boxed (L14).
  • want != got calls equals (L5); Java needs Objects.equals to be null-safe.
  • A caveat: a data class with an IntArray property compares the array by reference in its generated equals, and Java records do the same. Case is never compared here, only the Int results. If you need value equality on arrays, use List<Int> or compare with contentEquals / Arrays.equals.

Exercise: put L49's greedy rule on trial

From a blank file, in both languages. L49 proved that "earliest finish first" picks the most non-overlapping meetings. Test it, and two plausible-looking alternatives ("earliest start first", "shortest meeting first"), against a brute force that tries every subset of up to 7 meetings: the backtracking from Part 2, pruning picks that clash with one already chosen. "Find the longest stretch of a server log in which at most 2 distinct users appear."

"List every way to split catsanddog into dictionary words."

"Every way" means enumerating choices: choose a dictionary word as the next piece, recurse on the rest, un-choose. A trie of the dictionary makes the "which words start here?" check fast, so the two patterns combine.

"Friendships keep being added. After each one, answer: are Ana and Ben now connected through any chain of friends?"

Connectivity under added links is union-find's job (L49): union per friendship, then find(ana) == find(ben), each nearly O(1). Rerunning BFS after every new link would cost O(V + E) each time.

The spec. An Autocomplete class built on a trie whose word-end nodes carry a count:

  • add(word, times = 1) adds to a word's count. Words are stored in lowercase. Reject an empty word or a non-positive count with IllegalArgumentException.

Java also needs Suggestion.java, a one-line public record Suggestion(String word, int count) {}. The Kotlin data class sits at the top of Autocomplete.kt.

The ranking is two comparators. "Weakest first" orders by count ascending and, for equal counts, by word descending, so the min-heap's root is the suggestion to evict: the lowest count, and among equals, the word that sorts last. Reversing that one comparator gives the output order. Each match costs O(log k) on the heap, so a query is O(p + m log k) for a prefix of length p with m matches, plus the walk over the m words' nodes.

At most 2n deque operations in total, however they're spread across iterations. That's amortised analysis, as for L16's doubling array: some steps do a lot, but the total is bounded.
