TCP gives you a reliable, ordered stream of bytes. Why does a protocol on top of it need its own framing? (L30)

One write on one side can arrive as several reads on the other, or be merged with the next one. The receiver needs a rule for where a message ends. Today you'll see HTTP's three rules: a blank line ends the headers, then Content-Length, chunked encoding, or the server closing the connection ends the body.

A URL says http://example.com/ with no port. Which TCP port does the client connect to? (L30)

For the http scheme, "TCP port 80 (the reserved port for WWW services) is the default", and for https it's 443 (RFC 9110 §4.2.1–4.2.2). 53 is DNS, which runs first to turn the name into an address.

A server gives every connection its own virtual thread. One client sends its request very slowly. What happens? (L28)

A blocked read unmounts the virtual thread, so its carrier is free for other connections (JEP 444). Today's raw-socket server uses exactly that pattern: Thread.ofVirtual().start { handle(socket) }.

Which LinkedHashMap constructor setting turns it into the core of an LRU cache? (L19)

With accessOrder = true, every get moves the entry to the end, so the eldest entry is the least recently used one, and removeEldestEntry evicts it. Part 3 puts that map in front of HttpClient.

Part 1

Methods, status codes, headers; curl as a debugging tool

~35 min

HTTP/1.1 is text you can type

RFC 9112 defines the format: "An HTTP/1.1 message consists of a start-line followed by a CRLF and a sequence of octets …: zero or more header field lines …, an empty line indicating the end of the header section, and an optional message body" (RFC 9112 §2.1). CRLF is \r\n. So a request is a few lines of text, a blank line, and maybe a body. Here is one typed by hand over a plain L30 socket:

status line : HTTP/1.1 200 OK
header      : Content-Type: text/html; charset=utf-8
header      : Transfer-Encoding: chunked
header      : Connection: close
header lines: 12
body line 1 : 241   <- chunk size in hex = 577 bytes
body line 2 : <!doctype html><html lang=en><head><meta...
bytes read  : 931
  • Host is required. "A client MUST send a Host header field … in all HTTP/1.1 request messages" (RFC 9112 §3.2). One IP address can serve thousands of sites, and Host says which one you mean.
  • Connection: close is why readAllBytes() returned. "HTTP/1.1 defaults to the use of persistent connections, allowing multiple requests and responses to be carried over a single connection" (RFC 9112 §9.3). Without the header, the server would keep the socket open for the next request, and a read-until-closed would hang.
  • The body starts with 241. That isn't HTML. It's a chunk size in hexadecimal, because the response says Transfer-Encoding: chunked: "a series of chunks, each with its own size indicator", where chunk-size = 1*HEXDIG (RFC 9112 §7.1). 0x241 is 577 bytes of HTML, then the next size line, and a size of 0 ends the body.

The same request from the shell, with nc from L30. One macOS detail: nc hangs up as soon as its input ends, before the reply arrives, so keep the input open for two seconds with sleep:

$ (printf 'GET / HTTP/1.1\r\nHost: example.com\r\nConnection: close\r\n\r\n'; sleep 2) | nc example.com 80 | head -6
HTTP/1.1 200 OK
Date: Wed, 21 Oct 2026 02:27:20 GMT
Content-Type: text/html; charset=utf-8
Transfer-Encoding: chunked
Connection: close
Server: cloudflare

How a body ends: three rules

TCP has no message boundaries, so HTTP/1.1 spells out how the receiver knows the body is complete (RFC 9112 §6.3, simplified):

FramingHow it worksWhen you see it
Content-Length: 11"its decimal value defines the expected message body length in octets". Read exactly that many bytes.The size is known up front. Our server always does this.
Transfer-Encoding: chunkedSize line in hex, that many bytes, repeat; a 0 chunk ends it. If both headers are present, "the Transfer-Encoding overrides the Content-Length".The size isn't known yet: streamed or generated pages, like example.com above.
Connection closeFor a response with neither, the body is "the number of octets received prior to the server closing the connection".Old or lazy servers. A dropped connection looks the same as a finished body, so the RFC discourages it.

Responses to HEAD, and every 304 and 204, have no body at all, whatever the headers say (rule 1 of §6.3).

A server on raw sockets

Now the other side. This server parses the request line and headers, reads a body if Content-Length says there is one, and answers with a status line, headers, a blank line and the body. Each connection gets a virtual thread (L28). Run with no arguments, it also plays the client, sending raw requests and printing what came back:

Methods: what the client wants

The method is the first word of the request line (RFC 9110 §9). Two properties matter more than the names:

  • Safe means "essentially read-only; i.e., the client does not request, and does not expect, any state change on the origin server". "The GET, HEAD, OPTIONS, and TRACE methods are defined to be safe" (§9.2.1). That's what lets crawlers and caches send them freely.
  • Idempotent means "the intended effect on the server of multiple identical requests with that method is the same as the effect for a single such request". "PUT, DELETE, and safe request methods are idempotent" (§9.2.2). A client may safely retry these after a dropped connection. POST is neither, which is why a browser warns before resubmitting a form.
MethodMeaningSafeIdempotent
GETGive me the resourceyesyes
HEAD"identical to GET except that the server MUST NOT send content"yesyes
POSTProcess this body: create, submit, triggernono
PUTReplace the resource with this bodynoyes
PATCHApply a partial change (RFC 5789)nono*
DELETERemove the resourcenoyes
OPTIONSWhat can I do here? (also CORS preflight)yesyes

* RFC 5789: "PATCH is neither safe nor idempotent", though a particular PATCH can be designed to be idempotent. L32 uses these properties to design a REST API.

Status codes: what happened

"The first digit of the status-code defines the class of response" (RFC 9110 §15): 1xx informational, 2xx successful, 3xx redirection, 4xx client error ("bad syntax or cannot be fulfilled"), 5xx server error ("failed to fulfill an apparently valid request"). The ones you'll meet every week:

CodeMeaning
200 OK · 201 Created · 204 No ContentSuccess; 201 usually comes with a Location of the new resource; 204 has no body.
301 / 308 · 302 / 307Moved permanently · temporarily. 307 and 308 forbid changing the method; with 301 and 302, "for historical reasons, a user agent MAY change the request method from POST to GET" (§15.4.2).
304 Not ModifiedYour cached copy is still good: a conditional request whose condition "evaluated to false" (§15.4.5). Part 3 lives on this one.
400 Bad Request · 422 Unprocessable ContentMalformed request · well-formed but semantically invalid content (§15.5.21).
401 Unauthorized vs 403 Forbidden401: "lacks valid authentication credentials", so log in; it must come with WWW-Authenticate. 403: "understood the request but refuses to fulfill it", so logging in again won't help (§15.5.2, §15.5.4).
404 · 409 Conflict · 429 Too Many RequestsNot found · clashes with the current state, e.g. an edit conflict · rate-limited (L43 builds a rate limiter).
500 · 502 · 503 · 504Server bug · a gateway got a bad upstream reply · overloaded or down · a gateway timed out waiting upstream.

Headers you'll read every day

"Field names are case-insensitive" (RFC 9110 §5.1): content-type and Content-Type are the same header, which is why our server lower-cases them before looking them up.

  • Request: Host; Accept (the formats I can read); User-Agent (who's asking); Authorization (credentials, L33); Content-Type and Content-Length when there's a body.
  • Response: Content-Type (how to interpret the bytes, including the charset from L2); Content-Length; Location (where to go, for 3xx and 201); and the caching headers in Part 3.
  • Cookies. HTTP is stateless, so state rides in headers: "Using the Set-Cookie header field, an HTTP server can pass name/value pairs and associated metadata (called cookies) to a user agent", which sends them back in a Cookie header on later requests (RFC 6265 §1, MDN: Cookies). Login sessions are usually a cookie.
  • CORS. "For security reasons, browsers restrict cross-origin HTTP requests initiated from scripts." Cross-Origin Resource Sharing is "an HTTP-header based mechanism that allows a server to indicate any origins … other than its own from which a browser should permit loading resources", sometimes after a "preflight" OPTIONS request (MDN: CORS). It's enforced by browsers, not servers: curl and HttpClient ignore it entirely.

You won't write raw requests in real code. java.net.http.HttpClient, standard since JDK 11 (JEP 321), does it for both languages. Kotlin has no HTTP client of its own in the standard library; it uses the same one. Run this with TinyServer still serving:

HTTP/2 and HTTP/3

Line 6 says HTTP_2, and curl agrees:

$ curl -sI --http2 https://example.com | head -1
HTTP/2 200

HTTP/2 keeps the same methods, status codes and headers but changes the wire format. Messages become binary frames: "The basic protocol unit in HTTP/2 is a frame", and "multiplexing of requests is achieved by having each HTTP request/response exchange associated with its own stream", so "a blocked or stalled request or response does not prevent progress on other streams" (RFC 9113 §2). Many requests share one TCP connection instead of queuing. HTTP/3 (RFC 9114) "supports the same semantics over a new transport protocol", QUIC, which runs over UDP (L30). That avoids TCP's problem of one lost packet stalling every stream behind it.

Why did our local server get HTTP/1.1? HttpClient "will prefer HTTP/2" and, for a plain http:// URL, tries to upgrade the connection. I captured its first request with a throwaway listener:

GET / HTTP/1.1
Connection: Upgrade, HTTP2-Settings
Host: 127.0.0.1:49858
HTTP2-Settings: AAEAAEAAAAIAAAAAAAMAAAAAAAQBAAAAAAUAAEAAAAYABgAA
Upgrade: h2c
User-Agent: Java-http-client/26.0.1

Our server ignored the Upgrade header and answered in HTTP/1.1, which the client accepts: "If the upgrade fails, then the response will be handled using HTTP/1.1". This cleartext upgrade "was never widely deployed and is deprecated" by RFC 9113 (§3.1). In practice HTTP/2 means HTTPS.

Bridge. On Android, OkHttp and Retrofit play the role of HttpClient. Android throws NetworkOnMainThreadException "when an application attempts to perform a networking operation on its main thread", which is why you used L29's withContext(Dispatchers.IO). In Spring, a @RestController method is a handler like handle() here: the framework parses the request line and headers and writes the status, headers and body you return.

What Kotlin does for you.
  • Nothing extra for HTTP itself. Kotlin calls the same java.net.http and socket APIs, and the bytes on the wire are identical. Say so honestly when someone asks for "the Kotlin HTTP client": it's the JDK's, or a library like OkHttp or Ktor.
  • use { } closes sockets the way try-with-resources does, and socket.use { } works on any Closeable.
  • substringBefore(':') / substringAfter('?', "") replace Java's indexOf arithmetic in the parser, and destructuring val (method, target) = line.split(" ") names the parts of the request line.
  • when with conditions routes requests and returns the status code in one expression, where Java needed a mutable status variable assigned in every branch.
  • sendAsync(...).await() lets three requests run concurrently in code that reads top to bottom (L29), instead of a thenApply chain.
Exercise: a raw client that frames by Content-Length

With TinyServer serving, write rawGet(host, port, path) from a blank file. It returns a Response(status, reason, headers, body):

  1. Send a GET request line, a Host header and a blank line, and don't send Connection: close.
  2. Read the status line and split it into version, code and reason phrase.
  3. Read header lines into a case-insensitive map until the empty line.
  4. Read exactly Content-Length bytes for the body, or until the server closes if there's no length.

Call it for /, /hello?name=Ex, /old and /nope, and print each status, header count and body, plus the Location if there is one.

Reference solutions 
/               200 OK                3 headers  body="home"
/hello?name=Ex  200 OK                3 headers  body="hello, Ex"
/old            301 Moved Permanently 4 headers  body=(empty)  location=/new
/nope           404 Not Found         3 headers  body="no route for /nope"

Both languages print the same. Two details worth noticing. TreeMap(String.CASE_INSENSITIVE_ORDER) lets you look up "location" even though the server sent Location, as RFC 9110 §5.1 requires. And reading exactly Content-Length bytes is what makes persistent connections possible: you know the response is over without waiting for the socket to close, so the next request could reuse it. TinyServer happens to close anyway (Connection: close).

Check

TinyServer's readRequest stops reading headers at some point. How does it know where the headers end?

The header section ends with "an empty line" (RFC 9112 §2.1), the bare \r\n in the printed response. Then the body's own framing rule takes over.

A client's connection drops before the response arrives. Which requests may it retry automatically, by RFC 9110's definition?

"PUT, DELETE, and safe request methods are idempotent" (§9.2.2): sending them twice has the same intended effect as once. Retrying a POST could order the same pizza twice.

A default HttpClient sends GET /old, and the server answers 301 with Location: /new. What does send() return?

The default redirect policy is NEVER, so you get the 301 and its Location header, exactly as line "2 NEVER" printed. Use Redirect.NORMAL to follow it.

Logging in again keeps returning the same error on an admin page: the server knows who you are and still says no. Which status fits?

Part 2

HTTPS and TLS at a high level

~20 min

What TLS gives you, and what it doesn't

HTTPS is the same HTTP, sent inside a TLS connection on port 443. RFC 8446 lists what that channel provides (§1):

  • Authentication: "The server side of the channel is always authenticated; the client side is optionally authenticated." You know you're talking to the real example.com.
  • Confidentiality: "Data sent over the channel after establishment is only visible to the endpoints." The request line, headers, cookies and body are all hidden.
  • Integrity: "Data sent over the channel after establishment cannot be modified by attackers without detection."

What it doesn't hide: the IP addresses you're talking between (L30), "the length of the data it transmits" (same paragraph), and timing. The ClientHello that starts the handshake goes out before any keys exist, since "all handshake messages after the ServerHello are now encrypted" (§1.2), so the hostname the client names in it (SNI) is visible to the network. Someone watching sees that you visited example.com, but not which page or what you sent.

The handshake, in one picture

TLS has "a handshake protocol … that authenticates the communicating parties, negotiates cryptographic modes and parameters, and establishes shared keying material", followed by a record protocol that uses those keys. In outline:

  1. The client says hello: the TLS versions and cipher suites it supports, a key share, and the server name.
  2. The server picks a version and cipher, sends its key share, and both sides derive the same secret with an (EC)DHE key exchange. An eavesdropper who saw both key shares still can't compute it.
  3. The server sends its certificate chain and signs the handshake with the certificate's private key, proving it owns the certificate.
  4. From then on, HTTP travels encrypted with a fast symmetric cipher such as AES-GCM. L33 explains the difference between those two kinds of cryptography.

HttpClient to an https:// URL needed no setup at all. Verification is on by default, and that's how it should stay.

Never "trust all certificates". When a handshake fails, search results offer a TrustManager whose check methods are empty, or a HostnameVerifier that returns true. The connection is still encrypted, but you've thrown away authentication, so you're encrypting your data to whoever answered, including an attacker in the middle. Fix the real problem instead: an expired or misconfigured server certificate, a missing intermediate, or, for a company's internal CA, adding that one CA to a trust store.

HSTS: don't even try plain HTTP

The first request to http://bank.example is sent unencrypted, and an attacker can answer it before any redirect to HTTPS happens. HTTP Strict Transport Security is "a mechanism enabling web sites to declare themselves accessible only via secure connections", declared "via the Strict-Transport-Security HTTP response header field" (RFC 6797). After a browser has seen it once, it rewrites http:// to https:// itself for that site, for the max-age given (MDN: Strict-Transport-Security).

Bridge: Android goes further by default. "Starting with Android 9 (API level 28), cleartext support is disabled by default", so an app's plain http:// requests fail unless its Network Security Config opts in with cleartextTrafficPermitted="true" (Android: Network security configuration). A local development server is the usual reason to opt in, for one host only.

What Kotlin does for you.
  • Property syntax reads Java getters as properties: session.protocol, cert.notAfter and socket.session instead of getProtocol(), getNotAfter() and getSession() (L9's interop).
  • generateSequence(e as Throwable) { it.cause }.last() walks the cause chain (L10) in one expression, where Java needs a while loop and a mutable variable.
  • catch (e: SSLHandshakeException) is optional in Kotlin: it's a checked IOException in Java, but Kotlin has no checked exceptions (L10). The compiler won't remind you that the network can fail, so you have to remember.
  • The TLS itself is identical: same JDK, same cacerts, same cipher.

Check

You load https://example.com/account?id=42 on café Wi-Fi. What can the café's network not see?

The path /account?id=42, the headers, cookies and body are all inside the encrypted channel. Addresses, the SNI hostname in the ClientHello, and the length of the traffic are not hidden (RFC 8446 §1, §1.2).

What did HttpClient.send throw for https://expired.badssl.com/?

The TCP connection worked, but certificate validation failed during the handshake: (certificate_expired) PKIX path validation failed, caused by a CertificateExpiredException. No HTTP was ever sent.

A forum answer fixes a handshake error with a TrustManager that accepts every certificate. What does that throw away?

The traffic is still encrypted, but you no longer know who holds the other end. That's server authentication, the first property RFC 8446 lists. A man in the middle can present any certificate and read everything.

Part 3

HTTP caching: Cache-Control, ETag, freshness

~25 min

Why cache, and which caches

The fastest request is the one you don't send. L22's latency ladder put a packet's round trip from the US to Europe at about 150 ms, while a lookup in a local map takes nanoseconds. RFC 9111 says "a cache stores cacheable responses to reduce the response time and network bandwidth consumption on future equivalent requests" (§1). It names two kinds:

  • A private cache "is dedicated to a single user; often, they are deployed as a component of a user agent": your browser's cache, or the one you'll write in a moment.
  • A shared cache "stores responses for reuse by more than one user": a company proxy, a CDN, or the proxy in today's final.

A stored response is fresh if it "can be reused without validation (checking with the origin server …)". Once it's stale, it can still be reused if validation shows it hasn't changed. The origin controls all of this with response headers.

The directives that matter

Response headerWhat a cache must do (RFC 9111 §5.2.2)
Cache-Control: max-age=2Fresh for 2 seconds: "considered stale after its age is greater than the specified number of seconds". Expires: <date> is the older way to say the same.
s-maxage=60"For a shared cache", this overrides max-age: a CDN can keep it longer than browsers do.
no-cacheMay store it, but "MUST NOT be used to satisfy any other request without forwarding it for validation". MDN: it "does not prevent the storing of responses but instead prevents the reuse of responses without revalidation".
no-store"MUST NOT store any part of either the immediate request or the response". For truly sensitive data.
private"A shared cache MUST NOT store the response (i.e., the response is intended for a single user)". Your own browser still may.
must-revalidateOnce stale, never reuse without a successful validation, even when the origin is unreachable.
immutable"Will not be updated during their freshness lifetime", so don't revalidate even on reload (RFC 8246). Used for versioned files like app.3f2a1.js.
Vary: Accept-EncodingThe stored response only matches requests whose named headers match the original request (§4.1), e.g. gzip and plain copies stored separately.

With none of these, a cache "MAY assign a heuristic expiration time", often based on Last-Modified (§4.2.2). Being explicit is better.

Validators: "has it changed?"

When a stored response is stale, the cache doesn't have to download it again. It sends a conditional request (RFC 9111 §4.3, "validating" or "revalidating"), and if nothing changed the origin answers 304 Not Modified with no body:

  • ETag is "an opaque validator", such as a hash of the content or a version number, in quotes: ETag: "39fc27bb00f99a68" (RFC 9110 §8.8.3). The cache sends it back as If-None-Match, which is true when the current tag does not match. If the tag matches, the condition is false, and the answer is 304.
  • Last-Modified is a timestamp, sent back as If-Modified-Since: return the content only if it's "more recent than the date provided" (§13.1.3). It's coarser, with one-second resolution, and that's what the exercise builds.

Check

A response says Cache-Control: no-cache. What may a cache do with it?

"Does not prevent the storing of responses but instead prevents the reuse of responses without revalidation" (MDN). That's why /report showed REVALIDATED, not MISS. The directive that forbids storing is no-store.

The cache sends If-None-Match: "r-v1" and the origin replies 304. What does the cache send its client?

304 means "your copy is still good". The cache refreshes the stored entry's freshness from the 304's headers and serves its body as a normal 200, labelled REVALIDATED in our runs.

A response says Cache-Control: private, max-age=60. Which cache may store it?

"A shared cache MUST NOT store the response", while "a private cache MAY store the response" (RFC 9111 §5.2.2.7). A CDN that ignored private would show one user's page to the next.

A caching proxy

One program, three roles, all on 127.0.0.1 with ports chosen by the OS (port 0). Build it from a blank file, Kotlin first, then Java:

  1. Origin (an HttpServer on port A) serves:
    • /time: the current time, with Cache-Control: max-age=2;
    • /report: fixed text, with ETag: "r-v1" and Cache-Control: no-cache, and a 304 when If-None-Match matches;
    • /me: hello, Ada, with Cache-Control: private, max-age=60;
    • anything else: 404.
    It counts the requests it sees per path, and how many were 304s.
  2. Proxy (an HttpServer on port B) is a shared cache. It forwards misses with HttpClient, serves fresh entries itself, revalidates stale entries that have an ETag, never stores no-store or private responses, and adds X-Cache: HIT | MISS | REVALIDATED | MISS (not stored) to each response.
  3. Client runs the script /time ×3, wait 2.5 s, /time, /report ×3, /me ×2, /nope. It prints the status, X-Cache and body for each request, then the origin's counts.
  4. Both servers stop in a finally, and the program exits by itself.

Design notes.

  • Why /time was a MISS after 2.5 s, not REVALIDATED: it has no validator, so a stale entry can only be replaced. Give it an ETag and the proxy would revalidate instead, which the "max-age + ETag" tab of the diagram shows.
  • private is the shared-cache rule. The client cache in Part 3 could have kept /me; this proxy must not, because the next user to ask would get Ada's page. That's a real class of CDN incident.
  • Only 200s are stored. RFC 9111 §3 allows more, e.g. a 404 with explicit freshness. Keeping the rule narrow keeps the exercise small.
  • Why ConcurrentHashMap? These servers use the default executor, which runs every handler on the one thread start() created (setExecutor), so a plain map would work today. The moment you add setExecutor(newVirtualThreadPerTaskExecutor()), as EtagServer does, handlers run concurrently and L27's rules apply.
  • What a real proxy adds: an Age header, "the sender's estimate of the time since the response was generated or successfully validated" (RFC 9111 §5.1); Vary handling; size limits with LRU eviction (Part 3's map); and collapsing many simultaneous misses for the same URL into one origin request. L41 picks up that last one.
Wrap-up

Exit quiz, recall card, sources

~5 min

RawGet sends Connection: close and then calls readAllBytes(). Why is the header needed? (L22 + L31)

readAllBytes() reads until end of stream. HTTP/1.1 connections are persistent by default (RFC 9112 §9.3), so without the header the server keeps the socket open for another request, and the read waits. Ex1's fix is to frame by Content-Length instead.

EtagServer calls setExecutor(Executors.newVirtualThreadPerTaskExecutor()). What changes? (L28 + L31)

Without an executor, every handler runs on the single thread start() created. With one, each request becomes a task, here a virtual thread, so a slow handler no longer holds up the rest, and shared state needs L27's care.

In Kotlin, you call client.send(...) with no try/catch and no @Throws. What does the compiler do? (L10 + L31)

Kotlin has no checked exceptions, so IOException and InterruptedException don't have to be declared. That's why the Kotlin handle() needed no catch. The network can still fail, so decide deliberately where to handle it.

Why is a fresh cache HIT so much faster than a revalidation that returns 304? (L22 + L31)

A 304 saves the body but still costs a full network round trip, often tens of milliseconds. A fresh HIT is a map lookup measured in nanoseconds. L22's latency ladder is the reason max-age exists alongside ETags.
