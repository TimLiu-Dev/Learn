Thousands of requests miss the cache for one hot key at the same instant and all hit the database. What is that called? (L41)

A stampede, or thundering herd: every request sees the miss before any of them has refilled the cache. L41's fix was request coalescing, letting one caller load the value while the others wait for it. The same "many arrive at once" shape appears today with load balancers and queues.

A hash table doubles from 16 to 32 buckets, indexing with h & (n - 1). Roughly how many keys change bucket? (L19)

One more bit of the hash now counts, so each key either keeps its index or moves to index + 16: about half move. Inside one process that's a quick rehash. When the "buckets" are database servers holding terabytes, moving half the data is a disaster, and Part 2 measures something worse.

Why does an L30-style server give each connection its own virtual thread? (L30)

Each connection mostly waits on the network. With a thread per connection, a slow client blocks only its own thread, and virtual threads make that cheap (JEP 444). The load balancer you build today serves every request on its own virtual thread for the same reason.

How many connections can write to one SQLite database at the same moment? (L36)

SQLite allows one writer at a time; the others wait or get SQLITE_BUSY, as L36's concurrent lenders showed (SQLite: isolation). Bigger databases allow more, but every database has a limit on one machine. Replication and sharding in Part 2 are how systems get past it.

Part 1

Stateless servers and load balancers

~35 min

Scaling up vs scaling out

When one server can't keep up, you have two choices. Scaling up (vertical scaling) means a bigger machine: more cores, more memory. Scaling out (horizontal scaling) means more machines, each running a copy of the program, with something in front spreading the work. The System Design Primer puts the trade-off plainly: "Scaling out using commodity machines is more cost efficient and results in higher availability than scaling up a single server on more expensive hardware, called Vertical Scaling" (System Design Primer: horizontal scaling).

Scale upScale out
Howa bigger machinemore machines behind a load balancer
Code changesnoneservers must be stateless (below)
Limitthe biggest machine you can buythe shared parts: database, load balancer
One machine dieseverything is downthe others carry on

Scaling up is simpler and often right for a long time. You measure the difference between the two near the end of this part.

Why servers must be stateless

The same page of the Primer lists the price of scaling out: "Servers should be stateless: they should not contain any user-related data like sessions or profile pictures", and "Sessions can be stored in a centralized data store such as a database (SQL, NoSQL) or a persistent cache (Redis, Memcached)." Here is what goes wrong otherwise. Two servers, A and B, each keep logged-in sessions in their own memory, and the load balancer happens to send your second request to B:

-- stateful: sessions live in each server's memory
login    -> A: session 13963612
GET /me  -> B: 401 who are you? (B has no such session)
GET /me  -> A: 200 hello ada (from A)
-- stateless: a signed token, nothing remembered
login    -> A: token ada.cUwOwDHjKosyBHs2
GET /me  -> B: 200 hello ada (from B)
GET /me  -> A: 200 hello ada (from A)
forged   -> B: 401 bad signature
-- stateful: sessions live in each server's memory
login    -> A: session 09ff6ad2
GET /me  -> B: 401 who are you? (B has no such session)
GET /me  -> A: 200 hello ada (from A)
-- stateless: a signed token, nothing remembered
login    -> A: token ada.cUwOwDHjKosyBHs2
GET /me  -> B: 200 hello ada (from B)
GET /me  -> A: 200 hello ada (from A)
forged   -> B: 401 bad signature
  • Stateful: A created the session, so only A knows it. One request later you're "logged out", purely because of which server answered.
  • Stateless: the server signs the user name with an HMAC (L33) and hands the token to the client. Any server holding the same key can check it, and none of them remembers anything. The token is identical in both languages: same key, same HMAC, same bytes. A forged token fails the signature check. The comparison uses MessageDigest.isEqual, the constant-time compare from L33.
  • The key is configuration, not state. Every server starts with the same secret, the way they all start with the same code. What must not differ between servers is anything learned from requests.

Three ways out of the stateful trap, each with a cost:

Shared storesessions in a database or Redis that every server readsa network round trip per request; the store must scale too

The Primer lists the sticky option as a load-balancer feature: "Session persistence - Issue cookies and route a specific client's requests to same instance if the web apps do not keep track of sessions" (System Design Primer: load balancer).

A load balancer, by hand

"Load balancers distribute incoming client requests to computing resources such as application servers and databases. In each case, the load balancer returns the response from the computing resource to the appropriate client." The Primer adds that they are effective at "Preventing requests from going to unhealthy servers" and "Helping to eliminate a single point of failure". It lists the usual ways of choosing a server: "Random, Least loaded, Session/cookies, Round robin or weighted round robin, Layer 4, Layer 7". Step through what you're about to build (the numbers come from the real run further down):

First the backend. Each one runs as its own JVM process, started by the demo with ProcessBuilder (L22). Three servers inside one JVM would be simpler, but they'd share a heap and die together; separate processes can be killed one at a time, like real machines. The price is about half a second of JVM start-up each.

  • One thread per backend, on purpose. The HttpServer docs: "If this method is not called (before start()) or if it is called with a null Executor, then a default implementation is used, which uses the thread which was created by the start() method" (HttpServer.setExecutor). So each backend handles one request at a time, like a one-core machine. That makes the effects of load easy to see. The optional third argument gives it a pool instead, for the scale-up comparison.
  • /slow sleeps to imitate a slow backend; /work burns CPU with one PBKDF2 hash (L33); /health is what the load balancer polls.
  • startBackend launches the same program again as a child process and reads its first line, READY 51234, to learn the port the OS picked.

Now the load balancer. It's an HttpServer too, serving each request on a virtual thread and forwarding it with HttpClient (L31), a reverse proxy:

  • Round-robin takes the next healthy backend in turn; least-connections takes the one with the fewest requests in flight right now (active). Both are on nginx's list: "round-robin — requests to the application servers are distributed in a round-robin fashion, least-connected — next request is assigned to the server with the least number of active connections" (nginx: load balancing).
  • Active health checks: a virtual thread asks every backend for /health every 500 ms, with a 300 ms timeout, and flips healthy on a change.
  • Passive health checks and retry (off unless asked for): when a request fails, mark that backend down immediately and try another. nginx does the same: "If the response from a particular server fails with an error, nginx will mark this server as failed, and will try to avoid selecting this server for subsequent inbound requests for a while."
  • Only GET is retried. A request that failed might have reached the backend and done its work before the connection dropped. Sending a GET twice is harmless; sending a POST twice could create two books. That's L32's idempotency, and the final shows it.
  • Forwarding headers: everything except the per-connection ones (Host, Content-Length, Connection…), which each hop sets for itself. HttpClient refuses to set some of them anyway.

  • Least-connections finished four times sooner (about 1.07 s against 4.2 s). Round-robin gave slow b2 its full third, 20 requests, and b2 serves one at a time at 200 ms each: 20 × 200 ms is 4 s. Least-connections saw b2's requests piling up and sent it only 5.
  • The health checker marked a working server DOWN. b2 wasn't dead, just busy: its single thread was working through queued slow requests, so /health waited in line past the 300 ms timeout. Under round-robin it then flapped DOWN, UP, DOWN as the queue drained and refilled. That's a real failure mode, not a bug in the demo. An overloaded server fails its health check, the balancer pulls it out, and its load lands on the others, which may then overload in turn. L43 calls this a cascading failure. Real systems answer health checks on a separate thread or port, and require several failures in a row before pulling a server.
  • The kill: b2 died at about 690 ms, and its round-robin turns failed with 502 until the next health check, about 330 ms later: 3 failures out of 60. That window is the price of active checks alone.
  • With retry on, the first failure marked b2 down on the spot and the request was resent to b3: 60 of 60 succeeded.

Layer 4, layer 7, and before the balancer

Your balancer reads each HTTP request, so it's a layer 7 balancer (application layer, L30). The Primer: "Layer 7 load balancers terminate network traffic, reads the message, makes a load-balancing decision, then opens a connection to the selected server." A layer 4 balancer only looks at addresses and ports: "Generally, this involves the source, destination IP addresses, and ports in the header, but not the contents of the packet." Layer 4 is cheaper; layer 7 can route on paths, headers and cookies. In production these are nginx, HAProxy ("a free, very fast and reliable reverse-proxy offering high availability, load balancing, and proxying for TCP and HTTP-based applications"), or a cloud provider's load balancer. A single balancer is itself a single point of failure, so the Primer notes "it's common to set up multiple load balancers, either in active-passive or active-active mode."

Spreading starts even earlier, in DNS (L30): example.com returned two A records, and clients pick one, a crude form of balancing. Anycast goes further: "Anycast is the name given to the practice of making a Service Address available to a routing system at Anycast Nodes in two or more discrete locations" (RFC 4786). The same IP address is announced from many places, and internet routing delivers each client to a nearby one.

Bridge. When you deploy a Spring Boot service, the platform (Kubernetes, a cloud load balancer) does this part, and your job is to make the service stateless and give it a health endpoint. Spring Boot's Actuator provides /actuator/health for exactly that. On Android, the app is the client of all this: it talks to one hostname and never knows how many servers are behind it.

What Kotlin does for you.
  • when (strategy) over an enum is an expression, and up.minBy { it.active.get() } picks the least-loaded backend in one call. Java needs a stream with Comparator.comparingInt and orElseThrow().
  • pick(skip = null) ?: return reply(…) handles "no healthy backend" in the same line that picks one.
  • use { } closes the load balancer and the executor; Java writes try-with-resources. Default arguments (retryOnFailure = false, slowMs = 0) replace Java's extra constructor or overload.
  • No checked exceptions: Thread.sleep and client.send need no catch (InterruptedException e). The Java health loop has three catch blocks for the same logic.

Check

Server A keeps sessions in a HashMap. The load balancer sends your next request to B. What happens?

B has its own memory and has never seen your session, exactly as Sessions showed with a 401. Servers behind a balancer must be stateless: keep sessions in a shared store, or in a signed token the client carries.

In the demo, why did least-connections finish in about 1 s instead of 4 s?

Least-connections looks at requests in flight. b2's piled up while it slept 200 ms on each, so new requests went to b1 and b3: b2 got 5 instead of 20. Round-robin ignores load and sends b2 its full third.

A backend dies, and the balancer has active health checks but no retries. Which requests fail?

Until the next health check notices, the dead backend keeps getting its round-robin turns, and each one fails. In the demo that was 3 of 60 requests in a 330 ms window. After the check marks it DOWN, nothing more goes there.

Why may the load balancer retry a failed GET but not a failed POST?

The failed attempt may have reached the backend and done its work. Repeating a GET changes nothing; repeating a POST might create a second book. RFC 9110 calls GET idempotent and POST not (L32); safe retries of POST need an idempotency key, which L43 covers.

Part 2

Replication, read replicas, sharding

~30 min

Part 1's backends are easy to multiply because they keep nothing. The database keeps everything, so all the backends still share one. Two techniques spread a database over several machines. Replication keeps a full copy on each, which helps reads and survives a crash. Sharding gives each a slice, which helps writes and size. Designing Data-Intensive Applications gives each a chapter; read the replication and sharding (partitioning) chapters after this lesson.

Leader and follower

The Primer describes the classic set-up, using the older names master and slave: "The master serves reads and writes, replicating writes to one or more slaves, which serve only reads. Slaves can also replicate to additional slaves in a tree-like fashion. If the master goes offline, the system can continue to operate in read-only mode until a slave is promoted to a master or a new master is provisioned" (System Design Primer: replication). Today they're usually called leader and follower, or primary and replica. Managed databases replicate asynchronously by default. Amazon RDS: "When you make updates to the primary DB instance, Amazon RDS copies them asynchronously to the read replica" (Amazon RDS: read replicas).

Here it is with two SQLite files. Each write goes to the leader together with a row in a changes table (the replication log), in one transaction (L36). A replicator thread copies changes to the follower in order, each one 300 ms after it was written. That's an artificial delay standing in for the network and a busy replica.

Run with sqlite-jdbc on the classpath, as in L36. Java: java --enable-native-access=ALL-UNNAMED -cp sqlite-jdbc-3.53.4.0.jar Replication.java.

  • Read right after a write: the follower hasn't heard about Dune yet and answers "not found". 400 ms later it has. Nothing is broken: the follower is eventually consistent. Step through it in the Replication tab of the diagram above.
  • Read-your-writes: the writer remembers the version its write produced and asks for "at least version 2". The follower is only at 1, so the read goes to the leader. Once the follower catches up, reads go back to it. Other users don't get this guarantee unless they carry a version too; the final shows what they see.
  • Lag under load: after a burst of 20 writes the follower sat 20 versions behind for about 300 ms. The Primer warns that "The more read slaves, the more you have to replicate, which leads to greater replication lag."
  • Four connections, on purpose: a JDBC connection isn't meant for several threads at once, so writers, readers and the replicator each get their own. WAL mode lets a reader read while the replicator writes (SQLite: WAL).

Synchronous vs asynchronous. This replicator is asynchronous: the leader commits and answers without waiting for the follower. That's fast, but the Primer lists the risk: "There is a potential for loss of data if the master fails before any newly written data can be replicated to other nodes." A synchronous replica makes the leader wait until the follower has the change too: no loss, but every write is as slow as the slowest replica, and a dead replica blocks writes. Many systems compromise with one synchronous follower and the rest asynchronous. Failover, promoting a follower when the leader dies, is the hard part: deciding the leader really is dead and not just slow (Part 1's health-check false alarm again), and making sure the old leader can't come back and accept writes. "Additional logic is needed to promote a slave to a master," says the Primer. Real databases do this with consensus, which L43 introduces.

Sharding: splitting the data

Replicas copy everything, so every replica still receives every write. To spread writes, split the data. The Primer: "Sharding distributes data across different databases such that each database can only manage a subset of the data. Taking a users database as an example, as the number of users increases, more shards are added to the cluster" (System Design Primer: sharding). Two ways to choose a key's shard:

  • By range: users A–F on shard 1, G–M on shard 2, and so on. Range queries stay on one shard, but popular ranges get hot: every new order today lands on the "today" shard.
  • By hash: hash(key) mod N. Load spreads evenly, but neighbouring keys scatter, and changing N is painful. That pain is measurable:
hash mod N, 4 -> 5 nodes: 80,147 of 100,000 keys move (80%)
ring,   1 vnode(s) per node: load {n1=17431, n2=32435, n3=8682, n4=41452}
   add n5: 25,475 keys move (25%), all of them to n5: true
ring, 100 vnode(s) per node: load {n1=22391, n2=24129, n3=26412, n4=27068}
   add n5: 22,091 keys move (22%), all of them to n5: true

ring,   1 vnode(s) per node: load {n1=17431, n2=32435, n3=8682, n4=41452}

  • mod N moved 80% of the keys when one node was added. A key stays put only if its hash gives the same remainder for 4 and 5, which happens about one time in five. Real shards hold real data, so 80% means copying almost the whole database across the network.
  • Consistent hashing puts nodes and keys on the same ring of 64-bit positions, and each key belongs to the first node position clockwise from it. That's a TreeMap.ceilingEntry lookup (L20), wrapping round to firstEntry at the end. Adding n5 only takes over the stretches just before its own positions, so every moved key moved to n5, and none moved between old nodes. The idea comes from Karger and colleagues' 1997 paper "Consistent hashing and random trees". The Primer recommends it: "A sharding function based on consistent hashing can reduce the amount of transferred data."
  • Virtual nodes even out the load. With one position per node the slices are luck: n4 owned 41% and n3 only 9%. With 100 positions per node every node gets 22–27%, and adding a fifth moves 22%, close to the ideal fifth. Step through a small ring in the Hash ring tab above.
  • Hash quality matters: String.hashCode is fine for mod but clusters similar strings, so the ring uses the first 8 bytes of MD5. Here MD5 is a mixing function, not security (L33).

What sharding costs. The Primer's list: "Data distribution can become lopsided in a shard. For example, a set of power users on a shard could result in increased load to that shard compared to others", "Rebalancing adds additional complexity", and "Joining data from multiple shards is more complex." A single celebrity's account is a hot key that no hash function can spread, because all of its traffic has one key. A query across shards ("top 10 books by loans") must ask every shard and merge the answers. A transaction that touches two shards loses the simple single-database guarantees of L36 and needs a distributed commit protocol, which is slow and rare. So you choose the shard key to keep each user's or each tenant's data together.

Bridge. Managed databases such as Amazon RDS create read replicas with a click; your code decides which reads may go to them, which is today's read-your-writes problem. On Android, Room is a single local SQLite database ("an abstraction layer over SQLite"), with no replication at all. The phone's copy plus the server's copy is a replication problem, which offline-first sync has to solve.

  • groupingBy { it }.eachCount().toSortedMap() is a sorted histogram. Java writes new TreeMap<>(…groupingBy(n -> n, Collectors.counting())).
  • data class Written(val id: Long, val version: Long) returns two values with names; Java's record does the same since JDK 16 (L7).
  • (ring.ceilingEntry(h) ?: ring.firstEntry()).value is the whole wrap-around in one expression; Java needs a temporary and a null check.

You write to the leader, then immediately read the same row from an asynchronous replica. What might you see?

The replica applies changes after a delay, so for a moment it answers with what it had before, or "not found" for a new row, as Replication showed. Read-your-writes fixes it for the writer: carry the version and read the leader until the replica has it.

Sharding with hash mod N, going from 4 to 5 nodes. Roughly what fraction of keys moved?

80,147 of 100,000 in the real run. A key keeps its shard only when its remainder is the same for 4 and 5, about one key in five. That's why plain mod N is a bad sharding function for a cluster that grows.

With consistent hashing, adding node n5 moves keys only…

n5's positions take over the stretch of ring just before each of them, so the only keys that change owner are the ones n5 now owns. The run checked it: "all of them to n5: true".

Why give each node 100 virtual positions on the ring instead of 1?

One random position per node gives random slice sizes: 9% to 41% in the run. A hundred small slices per node average out to 22–27% each. Lookups are a little slower (a bigger TreeMap), keys still move, and one hot key is still one hot key.

Part 3

Message queues and asynchronous work

~25 min

Some work doesn't belong in the request at all: resizing an image, sending a welcome email, recomputing a report. The user shouldn't wait for it, and a burst of it shouldn't take the web servers down. The Primer's workflow: "An application publishes a job to the queue, then notifies the user of job status. A worker picks up the job from the queue, processes it, then signals the job is complete. The user is not blocked and the job is processed in the background" (System Design Primer: message queues). A queue also smooths load spikes: jobs wait instead of overwhelming anyone, and workers can be added without touching the producers.

A queue that survives crashes

The hard part is a worker dying halfway through a job. If the queue deleted each message when handing it out, that job would be lost. So real queues hand it out and keep it: "When you receive a message from an Amazon SQS queue, it remains in the queue but becomes temporarily invisible to other consumers… If you don't delete it before the timeout expires, the message becomes visible again in the queue and can be retrieved by another consumer" (Amazon SQS: visibility timeout). RabbitMQ does the same when the consumer's connection drops: "any delivery (message) that was not acked is automatically requeued" (RabbitMQ: consumer acknowledgements). Here's that design in about forty lines:

  • Three places a message can be: ready (waiting), inFlight (handed out, with a deadline), or deadLetters (given up on).
  • receive moves a message to in-flight and counts the attempt; ack removes it for good. A sweeper thread puts expired in-flight messages back, or into the dead letters after maxAttempts.
  • inFlight.remove(id, entry) removes only if the entry is still the one the sweeper saw, so a late ack and the sweeper can't both win (L27's compare-and-set idea).
  • Bounded: LinkedBlockingQueue(capacity) makes push block and offer refuse when full.

Which worker gets which job differs between the two runs (and between your runs): three threads race for messages. The outcomes are the same every time.

  • At-least-once delivery means duplicates. A worker crashed between sending email #2 and acking it. After the 300 ms visibility timeout #2 came back and another worker sent it again: 7 emails for 6 jobs. The queue can't tell "crashed before the work" from "crashed after", so it errs on the side of not losing jobs. SQS says it directly: "Design your applications to be idempotent (they should not be affected adversely when processing the same message more than once)" (Amazon SQS: at-least-once delivery).
  • The idempotent consumer records each job id it finishes and skips ids it has seen: 6 emails for 6 jobs, one redelivery skipped. Here the record is an in-memory set; in production it's a processed_ids table with a unique key (L35). There's still a gap between "email sent" and "id recorded": a crash exactly there would duplicate the email. You close it by writing the effect and the id in one transaction when the effect is a database write (L36), or by passing an idempotency key to the downstream service so it can de-duplicate (L32).
  • Poison messages go to the dead letters. "BAD" failed on every attempt. After 3 tries it moved to the dead-letter list instead of looping forever, and the good messages weren't held up. SQS: "The maxReceiveCount is the number of times a consumer can receive a message from a source queue before it is moved to a dead-letter queue" (Amazon SQS: dead-letter queues). Someone looks at the dead letters later.
  • Backpressure: with room for 5, push blocked whenever the queue was full, so pushing 20 jobs took about 750 ms, the consumer's pace (15 waits × 50 ms). offer refused all 20 extras straight away. The Primer explains why bounded queues are better: "Back pressure can help by limiting the queue size, thereby maintaining a high throughput rate and good response times for jobs already in the queue." It's L28's bounded executor queue again, at system scale.

Delivery guarantees, ordering, and logs

GuaranteeHowFailure looks like
At-most-onceack (delete) before doing the worka crash loses the job
At-least-onceack after doing the work (today's queue)a crash repeats the job
"Exactly-once"at-least-once + an idempotent consumerrepeats happen, but have no extra effect

"Exactly-once" delivery over an unreliable network isn't possible in general; what systems offer is exactly-once effect, built from the bottom two rows.

Ordering. With several workers, jobs finish in whatever order the workers manage, not the order they were pushed. In the run above, w1 sent #4–#6 before #2's retry. Often that's fine. When it isn't, say all updates to one user must apply in order, real systems keep order per key rather than globally. Kafka: "Events with the same event key (e.g., a customer or vehicle ID) are written to the same partition, and Kafka guarantees that any consumer of a given topic-partition will always read that partition's events in exactly the same order as they were written" (Apache Kafka: introduction). That's sharding again, applied to a queue.

Queues vs logs. SQS and RabbitMQ are queues: a message is deleted once acked, and each one goes to one consumer. Kafka is a log: messages are kept for days, and each consumer group remembers its own position, so several independent consumers can read the same stream, and a new one can replay history. DDIA's stream-processing chapter compares the two in depth.

Bridge. On Android, WorkManager is the phone's job queue: it "is intended for work that is required to run reliably even if the user navigates off a screen, the app exits, or the device restarts" (Android: WorkManager), and it retries with backoff, like today's queue. In Spring, @Async runs a method "in a task that has been submitted to a TaskExecutor" (Spring: @Async), which is an in-process queue that loses jobs on a crash. Spring Kafka's @KafkaListener and the SQS integrations are the durable kind.

What Kotlin does for you.
  • data class Message plus m.copy(attempts = m.attempts + 1) makes "the same message, one more attempt" one expression. Java's record has no copy, so you call the constructor with every field again.
  • ready.poll(…) ?: return null and q.receive(500) ?: break put the empty case on the same line.
  • Destructuring for ((id, entry) in inFlight) reads a map entry by its two parts; Java writes e.getKey() and e.getValue().
  • No checked InterruptedException: Java's worker lambdas each need a try just to call receive.

Check

A worker finishes a job but crashes before acking it. With a visibility timeout, what happens?

The message stays in flight until its deadline, then the queue makes it visible again and another worker gets it. That's at-least-once delivery: no job lost, but the job ran twice, which is why consumers must be idempotent.

What makes a consumer idempotent?

Idempotent means a repeat has no extra effect, like the demo's "skips #2: already done". Acking instantly would make delivery at-most-once and lose jobs on a crash; and no consumer can promise never to crash.

A message fails every single time it is processed. What should the queue eventually do?

After maxAttempts it goes to the dead-letter queue, where someone can inspect and fix it, while the healthy messages keep flowing. Retrying forever wastes workers; deleting it hides a bug.

The bounded queue is full. What does push() in JobQueue do?

LinkedBlockingQueue.put waits for space, so a fast producer is slowed to the consumers' pace: 20 pushes took about 750 ms. That's backpressure. offer is the non-blocking choice that says no instead.

Wrap-up

Exit quiz, recall card, sources

~5 min

The stateless servers compare token signatures with MessageDigest.isEqual, not equals. Why? (L33)

equals stops at the first different character, so an attacker can measure how long a guess took and learn the signature byte by byte. MessageDigest.isEqual takes the same time either way (L33).

Which TreeMap call finds the owner of a key's ring position h? (L20)

"Clockwise to the first node position" is the smallest key ≥ h: ceilingEntry, falling back to firstEntry() to wrap round. A balanced tree makes it O(log n) (L20). get(h) would almost never find an exact match.

Which executor rejection policy also pushes back on a producer that is too fast? (L28)

With CallerRunsPolicy a full pool makes the submitting thread run the task itself, so it can't submit more until it's done: backpressure, like push() blocking. AbortPolicy throws, more like offer() returning false; the discard policies silently lose work.

Several workers record finished job ids in one set at the same time. Which set is safe? (L27)

Only the concurrent set is built for writers on several threads; the others can lose entries or corrupt themselves (L26–L27). Today's queue and final use ConcurrentHashMap.newKeySet() for exactly this.
