Why it works. Tokens only grow, because the lock service hands out the next number on every grant. So a token smaller than one the store has already accepted can only come from a holder whose lease ran out while someone newer took over. The storage is the one place every write passes through, which is why the check lives there and not in the client: a paused client can't know it was paused. @Synchronized makes the check and the write one step, the same idea as the exercise's single conditional UPDATE (and L26's check-then-act race).

Common mistake. Rejecting equal tokens too (token <= seen). The current holder then can't write twice under one lease. Another one: keeping a single highest token for the whole store, so a job holding token 50 for one key blocks every other lock's lower tokens on unrelated keys.
