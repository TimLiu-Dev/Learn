Why it works. Every read and write of items happens under one lock, so there's no race and no visibility problem. await() atomically releases that lock and parks, which is why a waiting taker doesn't block the putter that will wake it. Two conditions mean a put wakes only takers and a take wakes only putters. The JDK's ArrayBlockingQueue is built the same way: one ReentrantLock with notEmpty and notFull.

Common mistake. if (items.isEmpty()) notEmpty.await(). When one put wakes two takers, the second one runs on without checking and calls removeFirst() on an empty deque. The Condition docs say it plainly: "a Condition should always be waited upon in a loop, testing the state predicate that is being waited for".
