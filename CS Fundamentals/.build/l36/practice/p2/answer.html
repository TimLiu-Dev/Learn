Why it works. Each successful write bumps the version, so any transaction that read the row earlier now holds a stale version. Its write matches zero rows, which is the signal to read again and retry. Nobody waits for a lock; a conflict just costs one retry, which is why optimistic locking suits rows that are rarely contended. It's L26's compare-and-set loop, with the version number standing in for the old value.

Common mistake. Checking the version but forgetting version = version + 1. The version never changes, so every check passes, and T2 overwrites T1's deposit exactly as the blind write did.
