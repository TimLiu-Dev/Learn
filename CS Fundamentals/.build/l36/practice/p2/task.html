Lost update, then optimistic locking

A tiny model of Part 2: runSchedule plays steps like "T1 read" and "T2 write" in a fixed order, so the interleaving is the same every run. With blind writes, the schedule T1 read, T2 read, T1 write, T2 write loses a deposit, just as READ COMMITTED did.

  • Implement updateIfVersion with the semantics of UPDATE … SET balance = ?, version = version + 1 WHERE id = 1 AND version = ?, returning the update count.
  • Implement writeIfUnchanged with it, and make runSchedule retry a failed write: read again, write again, at the end of the queue.
