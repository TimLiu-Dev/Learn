Part 1

Pipes and text tools

~30 min

The Unix shell rests on one idea, summed up by Doug McIlroy, "the inventor of Unix pipes": "Write programs that do one thing and do it well. Write programs to work together. Write programs to handle text streams, because that is a universal interface" (quoted in The Art of Unix Programming, Basics of the Unix Philosophy). A pipeline isn't one program running after another. MIT's Missing Semester puts it this way: "all three programs are being spawned and the shell is connecting the output of cat to the input of grep and the output of grep to the input of uniq" (Missing Semester: Command-line Environment). They are separate processes (L22), running at the same time.

Three streams, and where they go

Every process starts with three open file descriptors, the ones lsof showed you in L22: 0 is standard input, 1 standard output and 2 standard error. The shell decides where each one points before the program starts:

SyntaxMeaning
cmd > f · cmd >> fstdout (fd 1) into file f, overwriting or appending (L1)
cmd 2> fstderr (fd 2) into f
cmd > f 2>&1stdout into f, then stderr to wherever stdout now points
cmd < fstdin (fd 0) reads from f
a | ba's stdout becomes b's stdin. stderr is not piped.
/dev/nullA file that throws away whatever you write to it

Errors went to the terminal even when stdout was redirected or piped, which is the whole point of having two output streams: data goes down the pipe, complaints go to you. ls nosuch.log | wc -l counted 0 lines, because the error never entered the pipe. Order matters, as the Bash manual warns: "The order of redirections is significant", because ls > dirlist 2>&1 sends both streams to the file, while ls 2>&1 > dirlist "directs only the standard output to file dirlist" (Bash manual: Redirections).

cut, sort, uniq: the classic top-N

"Which paths get the most traffic?" is one pipeline. Step through it on a 12-line sample first; every output below is real:

Now the full million lines, plus a trap. uniq only merges lines that touch: the BSD manual warns that "Repeated lines in the input will not be detected if they are not adjacent, so it may be necessary to sort the files first" (uniq(1); macOS's man uniq says the same).

  • Without sort, /api/books appears twice and /health twice: a count for each run, not each path.
  • awk gets the same answer differently. n[$3]++ is an associative array, awk's built-in hash map (L19). Counting with a hash map is O(n); sort | uniq -c sorts a million lines first, which is O(n log n) (L18). On my machine that's 0.57 s against 0.84 s.
  • sort -rn: -n compares as numbers (otherwise 99868 sorts after 301266, character by character), -r reverses.

sed and awk: edit and compute

sed is a stream editor: it applies a command, usually s/pattern/replacement/, to every line. awk splits each line into fields $1, $2, … ($NF is the last) and runs a small program on them.

  • sed -E 's/ ([0-9]+)ms$/ \1/' captures the digits in a group and writes them back as \1, dropping the ms.
  • The -i trap. On macOS, -i always takes a backup extension: "If a zero-length extension is given, no backup will be saved" (sed(1), the BSD sed macOS uses). So sed -i 's/ms$//' small.log took the script as the extension and the file name as the script, and failed. On Linux, GNU sed's suffix is optional, -i[SUFFIX] (GNU sed manual), so plain sed -i 's/…//' file works there and sed -i '' doesn't. Scripts that must run on both usually avoid -i and write to a new file.
  • awk '$4 >= 500 { … }' is a pattern plus an action: run the action only on lines where the pattern is true. With no pattern, the action runs on every line.
  • The last awk keeps two hash maps, sums and counts, and prints averages in its END block, which runs once after the last line. That's a groupBy in one line of shell.

jq: grep for JSON

Logs and APIs increasingly speak JSON, and line tools can't see its structure. "jq is like sed for JSON data - you can use it to slice and filter and map and transform structured data with the same ease that sed, awk, grep and friends let you play with text" (jq). macOS ships it as /usr/bin/jq.

A jq program is a filter: .[0] picks the first element, .[] streams every element, | feeds one filter into the next, and select(…) keeps only the values for which the test is true. With -r, "if the filter's result is a string then it will be written directly to standard output rather than being formatted as a JSON string with quotes" (jq manual), which is what you want when the next stage is sort or awk. @tsv turns an array into one tab-separated line. In L32 you'll parse JSON inside a program; jq is the same idea at the prompt.

xargs: turn lines into arguments

Some commands, like rm, take file names as arguments, not on stdin. xargs reads lines and passes them as arguments. It splits on spaces, though, so a name with a space breaks in two:

The fix is to separate names with a byte that can't appear in them. find -print0 ends each name with "an ASCII NUL character (character code 0)" (find(1)), and xargs -0 expects "NUL (``\0'') characters as separators, instead of spaces and newlines" (xargs(1)). Part 2

Permissions, environment and PATH

~20 min

Nine bits per file

The first column of ls -l, like -rw-r--r--, is a file type (- file, d directory) followed by three groups of three letters: what the owner, the file's group and others may do. r is read, w write, x execute; - means no. That's 9 bits, so each group of three is one octal digit, the grouping you did in the warm-up (L48): r = 4, w = 2, x = 1. The BSD manual: "Modes may be absolute or symbolic. An absolute mode is an octal number constructed from the sum of one or more of the following values" (chmod(1)). Toggle some bits:

  • stat -f '%Sp %Lp %N' is BSD stat printing the symbolic mode, the octal mode and the name (stat(1)). On Linux it's stat -c '%A %a %n'.
  • Octal or symbolic. chmod 600 sets all nine bits at once. chmod g+r,o+r changes only the bits it names.
  • The umask decides the bits of every new file. Its "9 low-order access permission bits … are used by system calls, including open(2), mkdir(2), and mkfifo(2), to turn off corresponding bits requested in file mode" (umask(2)). touch asks for 666 and mkdir for 777; umask 022 turns off the two write bits, giving 644 and 755. In bits that's requested and umask.inv(), a mask from L48.

On a directory, the letters mean something different: r lets you list the names in it, and x lets you go in and use those names:

With r but no x, ls could read the name inside.txt but complained when it tried to look further, and both cat and cd were refused. A directory almost always needs x wherever it has r.

Permissions from Kotlin and Java

java.nio.file represents the nine bits as a set of PosixFilePermission values. Converting that set to the octal number stat prints is a mask exercise, and it shows a small difference between the languages: "Kotlin does not support octal literals" (Kotlin docs: Numbers), while Java's leading-zero octal, L48's trap, is finally the right tool.

Files.createFile got 644 from the umask, just like touch, and stat agrees with the program about the final 750.

Making a script runnable

To run a file as a command, it needs the x bit and a first line saying which program should run it: the shebang, #! followed by a path. #!/usr/bin/env bash asks env to find bash on your PATH. Java and Kotlin can do it too. Java's source launcher lets you put "a single-file program (such as a script or source code) … in any conveniently named executable file whose first line begins with #!" (JEP 330), and "A Kotlin script is a Kotlin source file (.kts) with top-level executable code" (Kotlin docs: Run scripts):

Without x, zsh refused with permission denied, while bash hello.sh worked anyway: it only needs to read the file. JEP 330 insists the Java file must not end in .java ("the use of the shebang mechanism to execute files that follow the standard naming convention for Java source files is not permitted"). The timings show the trade-off: bash starts in 3 ms, a Java script in about 0.2 s and a Kotlin script in about 0.7 s. Each JVM run starts a JVM, and Java's source launcher compiles the file in memory every time ("the effect is as if the source file is compiled into memory", JEP 330). Quick glue belongs in the shell; logic you'd want to test belongs in Kotlin or Java.

Environment variables

"Whenever a shell program calls another program it passes along a set of variables that are often referred to as environment variables" (Missing Semester). A shell variable is only copied into a child's environment once you export it, and a child can never change its parent's environment.

  • Not exported, not inherited. GREETING=hi alone set a shell variable that java couldn't see. After export it could.
  • GREETING=once java … sets the variable for that one command only. Afterwards the shell's own value is still empty.
  • Read-only inside the JVM. System.getenv() "Returns an unmodifiable string map view of the current system environment" (System docs). The Kotlin line compiled anyway, because Java's Map arrives as a platform type that Kotlin treats as possibly mutable (L9), and failed at run time.
  • A child gets a copy. ProcessBuilder.environment() "may be modified using ordinary Map operations. These modifications will be visible to subprocesses started via the start() method" (ProcessBuilder docs), and the parent's own value didn't change.

Bridge: configuration through environment variables is how servers are deployed. L46 reads SHELF_PORT and SHELF_DB with System.getenv. Spring Boot binds variables to its settings by a fixed rule: "Replace dots (.) with underscores (_). Remove any dashes (-). Convert to uppercase" (Spring Boot: Externalized Configuration), so server.port comes from SERVER_PORT.

PATH: how the shell finds a command

When you type java, the shell searches the directories in PATH, in order, and runs the first java it finds. "export PATH="$PATH:path/to/append"" is the pattern you'll see in install instructions (Missing Semester).

First match wins, so whoever controls an early PATH directory controls what java means. That's why you should never put ., the current directory, at the front of PATH: any folder you cd into could then replace ls. When a command behaves strangely, which tells you which file actually runs.

What Kotlin does for you (and one thing it doesn't).
  • No octal literals in Kotlin, so permissions are written as binary literals with underscores (0b110_100_000), which show the three groups directly, or parsed with "750".toInt(8). Java's 0750 is shorter but easy to misread (L48).
  • perms.sumOf { BIT.getValue(it) } and BIT.filterValues { mode and it != 0 }.keys replace Java's loops with |= and an EnumSet.
  • System.getenv("X") ?: "(not set)" handles the null that Java returns for a missing variable in one expression.
  • The trap: System.getenv()["X"] = "…" compiles in Kotlin, because a Java collection's mutability is unknown (a platform type, L9). Java's put fails the same way at run time; neither compiler stops you.

Part 3

Processes, signals and exit codes

~20 min

A signal is a tiny message the OS delivers to a process: "When a process receives a signal it stops its execution, deals with the signal and potentially changes the flow of execution based on the information that the signal delivered. For this reason, signals are software interrupts" (Missing Semester). kill sends them; despite its name, most signals ask rather than kill. The ones you'll meet, from the POSIX list (signal.h):

SignalPOSIX descriptionWho sends it
SIGINT"Terminal interrupt signal."Ctrl-C
SIGTERM"Termination signal."kill pid; container platforms stopping you
SIGKILL"Kill (cannot be caught or ignored)."kill -9 pid, the last resort
SIGHUP"Hangup."closing the terminal
SIGPIPE"Write on a pipe with no one to read it."the OS, when a reader like head exits early

Watch a JVM get the signal

This program registers a shutdown hook, a thread the JVM starts when it shuts down, then works for a while inside a try/finally:

  • Normal end: main finishes, its finally runs, then the hook. Exit 0.
  • & runs a command in the background so you get your prompt back; $! is its pid. In your own terminal, zsh also prints a job number and pid such as [1] 92715. pgrep -fl finds processes by command line, and ps shows that its parent (PPID) is the shell.
  • SIGTERM: the hook ran, but main: finally block never printed. The JVM begins its shutdown sequence "when some external event occurs, such as an interrupt or a signal is received from the operating system", and when it terminates, "finally clauses are not executed" and "resources opened with try-with-resources are not closed" (Runtime docs: Shutdown Sequence). Cleanup that must happen on SIGTERM belongs in a hook, not a finally.
  • SIGINT is what Ctrl-C sends to the program in the foreground. Here pkill -INT stands in for the key press, and the hook ran again.
  • SIGKILL: nothing at all after the pid line. SIGKILL "cannot be captured by the process and it will always terminate it immediately" (Missing Semester). Save kill -9 for processes that ignore SIGTERM.

Exit codes 143, 130, 137. "When a command terminates on a fatal signal whose number is N, Bash uses the value 128+N as the exit status" (Bash manual: Exit Status). Count along kill -l: INT is 2, KILL is 9, TERM is 15, so 130, 137 and 143. The JVM does the same arithmetic on purpose. Its signal handler calls Shutdown.exit(sig.getNumber() + 0200) (Terminator.java; an implementation detail, not a guarantee), and 0200 is octal for 128: L48's notation inside the JDK.

Why kill -INT can do nothing Optional deep dive

This time SIGINT was ignored: the program worked its full 3 seconds and exited 0. My capture shell had no terminal attached, so job control was off, and POSIX says that then "the commands in the list shall inherit from the shell a signal action of ignored (SIG_IGN) for the SIGINT and SIGQUIT signals" for anything started with & (POSIX Shell, 2.12 Signals and Error Handling). The JVM respects that: when asked to handle a shutdown signal that arrived already ignored, HotSpot's JVM_RegisterSignal returns early with if (PosixSignals::is_sig_ignored(sig)) return (void*)1; (jvm_posix.cpp; implementation detail). Scripts can hit the same thing, so the practical rule is: stop background jobs with SIGTERM, which no shell sets to ignored.

Exit codes: a program's one-number report

Every process ends with an exit status. "The convention is that zero means everything went well whereas nonzero means some issues were encountered" (Missing Semester). The shell keeps the last one in $?, and && and || branch on it: a && b runs b only if a succeeded, and a || b only if it failed. Part 4

SSH keys and safe scripts

~20 min

Your SSH key pair

SSH logs you into other machines, and it's also how you push to GitHub without a password. It authenticates with a key pair, L33's public-key cryptography: "The file ~/.ssh/authorized_keys lists the public keys that are permitted for logging in. … The client proves that it has access to the private key and the server checks that the corresponding public key is authorized to accept the account" (ssh(1)). Missing Semester's warning: "the private key (often ~/.ssh/id_rsa and more recently ~/.ssh/id_ed25519) is effectively your password, so treat it like so and never share its contents". This demo writes its keys into a demo/ folder, so your real ~/.ssh is never touched:

-t ed25519 picks the algorithm from L33, -C sets a comment, -f the file name, and -N "" an empty passphrase (fine for a demo; protect a real key with one). ssh-keygen already gave the private key mode 600 and the public key 644. The fingerprint is how you compare keys by eye. The other half of the trust works the other way round: the first time you connect to a server, ssh stores its host key, because "Host keys are stored in ~/.ssh/known_hosts", and "If a host's identification ever changes, ssh warns about this" (ssh(1)).

Inside the .pub line

A public key line is type base64-blob comment. The blob is a sequence of SSH strings, each "stored as a uint32 containing its length (number of bytes that follow)" followed by the bytes, where a uint32 is "Stored as four bytes in the order of decreasing significance (network byte order)" (RFC 4251 §5). For Ed25519 there are two: the name "ssh-ed25519" and "the 32-octet public key" (RFC 8709 §4). DataInputStream.readInt() reads exactly that big-endian length (L48's bytes):

51 bytes: a 4-byte length, the 11-byte name, another length and the 32-byte key. The SHA-256 of the blob, in Base64 without the trailing =, matches the fingerprint ssh-keygen -l printed, character for character.

Scripts that fail loudly

By default a shell script keeps going after a failure, treats a typo'd variable as empty, and reports only the last command of a pipeline: "The exit status of a pipeline is the exit status of the last command in the pipeline, unless the pipefail option is enabled" (Bash manual: Pipelines). Three options change that (The Set Builtin):

  • set -e: "Exit immediately if a pipeline … returns a non-zero status", with exceptions such as the test of an if and commands in a && or || list.
  • set -u: "Treat unset variables and parameters … as an error when performing parameter expansion."
  • set -o pipefail: the pipeline's status becomes "the value of the last (rightmost) command to exit with a non-zero status, or zero if all commands exit successfully".

Without set -e, the script carried on in the wrong directory, which is how a script ends up running rm somewhere it shouldn't. (bash 3.2 happens to exit with 127 for the unset variable; what matters is that it stopped.)

Quote every variable. The shell splits the results of unquoted expansions into words: it "scans the results of parameter expansion, command substitution, and arithmetic expansion that did not occur within double quotes for word splitting" (Bash manual: Word Splitting). For a script's arguments, use "$@": "When the expansion occurs within double quotes, and word splitting is performed, each parameter expands to a separate word. That is, "$@" is equivalent to "$1" "$2" …" (Special Parameters).

Look closely at the unquoted run: $f became two words, my and notes.txt, and because a notes.txt was left over from Part 2, ls happily listed the wrong file. With rm instead of ls, that's a deleted file you never named. (zsh doesn't split unquoted variables unless its SH_WORD_SPLIT option is set, which "Causes field splitting to be performed on unquoted parameter expansions" (zsh options); bash, and therefore your bash scripts, always do.)

Know your bash. macOS's /bin/bash is very old, and some features simply aren't there:

bash 3.2 rejected declare -A (associative arrays), then quietly treated count[x] as an ordinary indexed array where x counts as 0, so it printed 1 anyway. That kind of silent surprise is why Google's shell style guide says "If you are writing a script that is more than 100 lines long, or that uses non-straightforward control flow logic, you should rewrite it in a more structured language now" (Google Shell Style Guide). For you, that language is Kotlin or Java.

In bash, "If a sigspec is 0 or EXIT, action is executed when the shell exits" (Bash manual: trap). Without pipefail, a pipeline's status is its last command's, and true succeeded. With pipefail it was 1.

In a bash script, f="my notes.txt"; rm $f removes what?

Unquoted, $f is split into two words, so rm gets two arguments. rm "$f" removes the one file you meant.

Wrap-up

Exit quiz, recall card, sources

~5 min

The JVM exits with sig.getNumber() + 0200. For SIGTERM (15), that gives? (L48)

0200 is octal: 2 × 64 = 128. 128 + 15 = 143, the same number bash reports. Reading it as decimal 200 gives the trap answer 215.

ProcessBuilder("sh", "-c", "grep " + userInput + " log"): what's the danger? (L33)

Input like x; rm -rf ~ becomes shell syntax. Pass arguments as a list, as Pipe did, and no shell parses them.

sort | uniq -c on n lines costs? (L18)

The sort dominates: O(n log n). awk's hash map counts in O(n) on average (L19).

SIGTERM arrives while main is inside reader.use { … }. Is the reader closed? (L10)

When the JVM terminates, "resources opened with try-with-resources are not closed", and use is Kotlin's try-with-resources. Put shutdown work in a hook.

After ls > out.txt 2>&1, where do file descriptors 1 and 2 point? (L22)

> points fd 1 at the file, then 2>&1 copies fd 1's target into fd 2. Swap the order and stderr stays on the terminal.
