The bug is the gap between "is it cached?" and "store it". Another thread can pass the same check in that gap. One lock has to cover the whole get: the check, the loads++, the load and the store.

---

Kotlin: put @Synchronized on get, which locks this. values.getOrPut(key) { … } (L19) does the check-then-act for you; on its own it isn't thread-safe, but inside the lock it is. Reads of loads need the same lock: @Synchronized get on the property.

---

Locking only the check and only the store, but loading outside the lock, still fails: both threads see "not cached" before either stores. In Java: synchronized String get(String key) { return values.computeIfAbsent(key, k -> { loads++; return loader.apply(k); }); } and synchronized int loads().
