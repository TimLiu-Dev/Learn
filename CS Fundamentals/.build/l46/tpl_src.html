v1 opens a connection with transaction_mode=IMMEDIATE. What does IMMEDIATE change? (L36)

A deferred transaction takes SQLite's write lock at its first write, so two writers can both start and one fails halfway. IMMEDIATE takes it at BEGIN, so writers queue up front. Part 1 depends on exactly this.

50 requests miss the cache for the same key at the same moment. Request coalescing makes… (L41)

The first miss starts the load and registers a future; the other 49 wait on that future instead of starting their own. L41 measured 50 queries without it and 1 with it.

A token bucket has capacity 5 and refills 1 token per second. A client sends 8 requests at once. How many get through? (L43)

A full bucket holds 5 tokens, so a burst can spend 5; the other 3 get 429. You'll see exactly this shape in Part 3's curl session, with capacity 5: the 4th and 5th requests are refused.

Shelf gives HttpServer a virtual-thread-per-task executor. What does that mean for shared objects? (L28)

Every request runs on its own virtual thread, at the same time as the others. Anything they share (stores, caches, counters) must be thread-safe. v1 never tested that. Today you do.

Two different bugs, and the second is the dangerous one.

  • Race 1: right answer, wrong status. All 20 requests passed openForBook(bookId) == null before any of them inserted. The first insert won. Every later insert hit L36's partial unique index, which refused it. The data stayed correct, but most clients got 500 Internal Server Error instead of 409 Conflict: a bug report and an alert, for a perfectly normal situation.
  • Race 2: wrong data, and no error at all. All 10 requests counted the member's open loans as 0, all 10 passed the limit check, and all 10 inserted. Nothing in the schema says "at most 3 per member", so the database had no reason to object. This is the check-then-act race of L26, with a SQL table playing the shared variable. No test, log or alert notices it.

Step A: map the constraint violation (fixes Race 1 only)

The tempting fix: catch the unique-constraint error and turn it into BookOnLoan. sqlite-jdbc throws an SQLiteException whose resultCode says which constraint failed:

Race 1 is cured: one 201 and nineteen 409s, every round, and no errors in the log. Race 2 is untouched: still 10 loans. A fix that relies on an index can only protect rules that the index expresses.

Step B: make check-and-insert one atomic step

Both rules must be checked and the loan inserted without anyone else writing in between. That's what a transaction is for. Shelf's Db already opens transactions with IMMEDIATE, so BEGIN takes SQLite's single write lock; while you hold it, no other writer can run its checks (L36). The checks just have to move inside the transaction. They can't stay in the service, because the service calls the store three separate times, and each call is its own short transaction. So the store gets one new method that does all of it:

The memory fake gets the same method, marked @Synchronized / synchronized like all its others, so its check and add share one lock. Now the race demo again:

Both races are gone, and the error logs are empty. Notice the trade-off: the "max 3 open loans" rule now lives partly in SQL, passed in as maxOpen. The alternative is to let the service open a transaction around several store calls (a "unit of work"). That keeps rules in the service but leaks transactions into it. Spring's @Transactional is exactly that alternative, done for you: L47 shows it.

SQLite write contention, and a bug that hid it

IMMEDIATE makes writers queue for the lock. How long does a queued writer wait? SQLite's busy_timeout: its busy handler "sleeps for a specified amount of time when a table is locked … After at least "ms" milliseconds of sleeping, the handler returns 0 which causes sqlite3_step() to return SQLITE_BUSY" (sqlite3_busy_timeout). v2 sets it explicitly in the URL, so it's visible and configurable. To see why it matters, 200 writers add a book at the same instant:

With no timeout, a writer that finds the lock taken gives up at once, so only 5 of 200 succeeded. With 3 seconds of patience, all 200 queue and succeed, because each transaction holds the lock for well under a millisecond.

Getting that first line was harder than it looks. My first run of this demo crashed with a different error:

"cannot rollback - no transaction is active" is not the real problem. When SQLite refused the write lock at BEGIN, no transaction had started, so v1's catch block called rollback(), which threw its own exception, and that exception replaced the real SQLITE_BUSY. The old code hit this in 1 of my 3 runs, depending on where the lock was refused. It's the same lesson as L10's suppressed exceptions: keep the original, and attach the secondary one to it. v1's Db had this bug in both languages. v2's transaction fixes it; you'll see the fix in the Db listing just below.

Connection-per-request vs a pool

v1 opened a fresh SQLite connection for every store call: open the file, run PRAGMA foreign_keys, query, close. v2's Db can keep a fixed set of open connections in an ArrayBlockingQueue (L27). take() waits when all of them are in use, so the pool also caps how many requests touch the database at once.

Measured, with 64 virtual threads each doing 500 lookups (each size run twice, so the JIT is warm for the second pass):

A pool is about 6× faster here, and the size hardly matters past 4: with a file on a fast SSD, the cost being saved is opening the connection, not waiting for the disk. Production apps use a pool library such as HikariCP ("a 'zero-overhead' production ready JDBC connection pool"), which adds what this one lacks: timeouts on take, health checks, and replacing broken connections. Its wiki page About Pool Sizing explains why bigger pools are usually slower.

What Kotlin does for you.

Check

In v1, 20 members borrow one book at once. Why did most of them get 500 instead of 409?

Each request checked openForBook while the book was still free, then tried to insert. The partial unique index refused every insert after the first, and nothing mapped that exception to 409, so the router's catch-all made it a 500.

Why did step A (catching the constraint violation) not fix Race 2?

The database refuses only what its schema says. "At most one open loan per book" is an index; "at most three open loans per member" is a rule in code. Without an atomic check-and-insert, nothing stops the eleventh loan.

What makes step B's tryLend atomic?

The checks and the insert run inside one transaction that took SQLite's write lock at BEGIN. No other writer can run its checks until this one commits or rolls back.

The naive tryLend failed on SQLite but passed on the memory fake. Why?

MemoryLoanStore.tryLend is synchronized, so its check and add can't interleave. The naive change only broke the SQLite version, and only the contract run against SQLite exposed it. Keep running the contract against the real store.

v1's transaction called rollback() in its catch block. When BEGIN itself failed with SQLITE_BUSY, the program reported…

rollback() threw "cannot rollback - no transaction is active", and an exception thrown in a catch block replaces the one being handled. v2 keeps the real error and adds the rollback failure with addSuppressed (L10).

Part 2

Add your L41 cache and L43 rate limiter, and measure the difference

~30 min

The cache is a decorator

L39's Decorator pattern pays off here: a CachingBookStore is a BookStore, wraps another one, and nothing else in Shelf changes. Reads go through the cache. Writes go to the real store and then invalidate (L41's cache-aside). The cache itself is L41's LruCache, copied in with two additions: clear(), and getOrPut() for the rate limiter below.

Two decisions worth questioning. First, a write drops every cached page and count, because a new book can shift every page after it. That's crude but correct, and with 5% writes it costs little. Second, invalidation happens after the write, so a reader can briefly see the old value. L41's TTL bounds how long (30 seconds by default here). Shelf runs as one instance; with several instances behind a load balancer (L42), each would have its own cache, and a write on one wouldn't clear the others. That's when people reach for a shared cache such as Redis.

The rate limiter is a filter

The JDK's HttpServer has a built-in hook for code that runs around every request on a context: "A filter used to pre- and post-process incoming requests. Pre-processing occurs before the application's exchange handler is invoked, and post-processing occurs after the exchange handler returns" (Filter docs). A filter may "Terminate the chain of invocation, by not calling Filter.Chain.doFilter(HttpExchange)", in which case it "must use the HttpExchange to send back an appropriate response". That's exactly a rate limiter: a 429 never reaches the router. The bucket is L43's, unchanged.

Look closely at the buckets map. A plain ConcurrentHashMap<String, TokenBucket> would get one entry per client id forever, and since the client picks its own X-Client-Id, an attacker could fill your heap with made-up ids: L24's unbounded-cache leak. An LRU with a cap and a TTL bounds it. (A real deployment would use an authenticated identity, not a header anyone can set.) Router's private send moved to a shared top-level function, so the filter can answer with the same Problem Details format as the handlers.

Wiring it: the composition root and Config

Three details. Filters run in the order they're added, so the access log (Part 3) is outermost and sees even the requests the limiter refuses. decorateBooks is a seam for tests and load tools: they wrap the real store to count or slow down its calls, without touching any production class (L38). And v1's constructor still exists, so all 33 of L45's tests run unchanged against v2.

Measure it, honestly

A load test only means something if you can say what it measured. This one:

  • Runs the same v2 build twice: once with pool, cache and limiter switched off by Config ("before"), once with the defaults ("after"). That's not quite v1, but it changes one thing at a time.
  • Sends 16 polite clients with a 20 ms pause between requests: 85% GET /books/{id}, picked Zipf-style so a few books are popular (L41), 10% list pages, and 5% PUT. On top of that, one greedy client sends 1,000 GETs with no pause at all.
  • Wraps the real store in a SlowBookStore that adds 2 ms to every read and counts reads. Localhost SQLite answers in microseconds, which would make any cache look pointless; a real database across a network takes milliseconds (L41's latency table). The delay is injected, and the table says so.
  • Uses fixed seeds, so the same requests go out every run. (Kotlin's Random(seed) and Java's java.util.Random(seed) produce different sequences, so the two languages send the same mix, not the same requests.)

What the numbers show.

  • The median request got about 6× faster (3.5 → 0.6 ms), and the database did about 6× less work (about 4,350 → under 700 reads). 87–88% of book lookups were served from memory.
  • The tail barely moved. p95 is ~6 ms in both runs. The slowest requests are the ones the cache can't help: misses, and list pages refetched after a PUT cleared them. L41 found the same: a cache improves the typical request, not the worst one.

What they don't show. This is one machine, one run, localhost, and an injected delay; the shape is trustworthy, the exact milliseconds are not. The two runs share one JVM and "before" goes first, so its first half-second ran on a cold JIT (its p95 there was 86 ms): a fairer harness would warm up first, or alternate the order, as JMH does (L24). It says nothing about a cold cache after a restart, many server instances, or a database that slows down under load. And a load test only finds the problems its workload exercises. What Kotlin does for you.
  • In tests, class SpyBookStore(inner: BookStore) : BookStore by inner overrides one method and forwards the other five. Java's SpyBookStore and SlowBookStore forward all six by hand (L15's class delegation).
  • One generic load(key, cache, fetch) serves find, list and count, with !! where a list can't be null. Java does the same with Supplier<V>, plus an Optional wrapped and unwrapped around find.
  • context.filters += AccessLogFilter(…) uses Kotlin's += on a mutable list; Java writes context.getFilters().add(…).
  • config.copy(port = 0) comes free with a data class. Java's Config record needs hand-written "withers" like withPort(0) (L7).

Reference answer

The prediction. "Before" should slow down about 10× everywhere, since every request makes at least one database read. "After" should keep its median, because most requests never reach the database. Both parts held: p50 stayed at 0.7 ms.

The bug. getOrPut runs create() while holding the cache's lock. For the rate limiter, create() builds a token bucket in nanoseconds, so that's fine. For list pages, it's a 20 ms database read. Every other list request, including those for pages already in the cache, waits for the lock behind it. After each PUT clears the pages, the first few list requests queue up single-file. That's L27's rule: never hold a lock during I/O. At 2 ms the queue was short enough to hide.

The fix. Load outside the lock, coalescing concurrent misses per key with the same in-flight map that find already used. That's the generic load function in the CachingBookStore listings above. After the fix, at 20 ms (Kotlin, then Java):

p95 fell from 96 to 31 ms and p99 from 153 to 58 ms: now better than "before", as it should be. Throughput rose too (480 → about 600 requests/s), because the greedy client was no longer stuck behind the lock. The 2 ms table earlier on this page is the post-fix run; it's slightly better than my pre-fix 2 ms run, too.

Look again at the first table: the bug was there all along. At 2 ms, though, the "after" run still beat "before" at p50 and roughly tied at p95, so it looked fine. Measuring only the case you expect can't show you this; push one variable until something gives.

Check

Why does CachingBookStore implement BookStore?

A decorator has the same interface as what it wraps, so BookService can't tell a cached store from an uncached one. The composition root decides, from Config (L39).

A rate-limited request never reaches Router.handle. What stops it?

A Filter continues the chain only if it calls chain.doFilter(exchange). If it doesn't, the docs say it "must use the HttpExchange to send back an appropriate response". Here that's a 429 with Retry-After.

Why are the rate limiter's buckets kept in a bounded LRU and not a plain map?

One bucket per client id, and the client sends its own X-Client-Id. Without a bound, made-up ids would grow the map until the heap runs out: L24's leak. A capped LRU with a TTL forgets idle clients.

With the cache on, why did p95 hardly change at 2 ms?

p95 is the slow tail, and the slowest requests are the ones that still go to the database: first reads, and list pages refetched after a write. A cache moves the median far more than the tail.

Part 3

Structured logging, metrics, config, shutdown

~30 min

One JSON line per request, and the golden signals

A second filter, added first so it's outermost, does four jobs for every request. It takes the caller's X-Request-Id or makes one. It joins the caller's W3C trace (L43) or starts one. It times the request and records it in Metrics. And it writes one JSON log line, even for requests the limiter refused. Metrics keeps L43's four golden signals: traffic and errors (a counter per status code), latency (a histogram) and saturation (requests in flight, plus idle pool connections).

The router's 500 handler now logs JSON too, carrying the same request id. That's the point of request ids: one id ties the error to the access line, and to the client's bug report. /health now runs a real SELECT 1 and answers 503 if it fails, which is what a load balancer's health check needs (L42). /metrics renders the counters as plain text in the shape of Prometheus' format.

Configuration from the environment

"The twelve-factor app stores config in environment variables … Env vars are easy to change between deploys without changing any code; unlike config files, there is little chance of them being checked into the code repo accidentally" (The Twelve-Factor App: Config). That last part is L33's rule about secrets. Shelf has no secrets yet, but a database password would come in the same way. Every setting has a default, and 0 switches a feature off, which is how the load test made its "before" run.

Graceful shutdown

v1's close() called server.stop(0). The docs say what the number means: stop closes the listening socket, and "will then block until all current exchange handlers have completed or else when approximately delay seconds have elapsed (whichever happens sooner). Then, all open TCP connections are closed" (HttpServer.stop). With 0, "whichever happens sooner" is immediately. Here are three slow requests in flight (each read takes 0.8 s) when close() is called, with v1's stop(0) and then v2's stop(5):

The demo: ShutdownDemo.kt / ShutdownDemo.java

With stop(0), all three clients lost their connection, even though the handlers carried on working until the executor closed (that's why close() still took about 0.7 s). With stop(5), all three got their answer, close() returned as soon as they finished rather than after 5 seconds, and a new request was refused. In production, deploys and autoscaling stop servers constantly; without draining, every deploy fails some requests.

Tests for all of it

Two habits from earlier lessons are doing the heavy lifting. A MutableClock (L38) makes the rate-limit test instant and exact: no sleep(1000) waiting for a refill. And the log sink is just a function, so a test can collect lines into a list and assert on them. The one test that does sleep, for shutdown, only waits 100 ms to be sure its request is in flight.

What Kotlin does for you.
  • log: (String) -> Unit = ::println is a function-typed parameter with a default; tests pass logs::add. Java uses Consumer<String> and passes System.out::println explicitly (L14).
  • jsonLine("ts" to clock.instant(), …) takes pairs built with to, in order. Java builds a LinkedHashMap line by line. Using Map.of would scramble the key order, since its iteration order is unspecified; I started that way in App.java and changed it.
  • Config.fromEnv uses local functions (fun int(name, default)) and ?.let; Java uses a static helper and containsKey ternaries.
  • try { chain.doFilter(exchange) } finally { … } is the same in both. The access line is written even if a filter or handler throws.

Check

Why is the access-log filter added before the rate limiter?

Filters run in the order added, so the first one wraps everything after it. Outermost, the access log times and records every request, 429s included, which is exactly the traffic you want to see during an attack.

What does server.stop(5) do with three requests still running?

The docs: it closes the listening socket, then blocks "until all current exchange handlers have completed or else when approximately delay seconds have elapsed (whichever happens sooner)". The demo returned after about 0.6 s, as soon as the three finished.

Why read the port and database path from environment variables?

Twelve-Factor: "Env vars are easy to change between deploys without changing any code", and they're unlikely to be committed by accident. The same build runs on your laptop and on a server with different settings.

In the session, /metrics showed shelf_in_flight 1. Which request was that?

The filter increments the gauge before calling the handler and decrements it in finally. The /metrics handler renders while its own request is still in flight, so it counts itself.

Wrap-up

Exit quiz, recall card, sources

~5 min

Two request threads read Shelf's route list, which was filled before server.start(). Why do they see every route without locking? (L27)

JLS §17.4.5: a call to start() on a thread happens-before any action in the started thread. Everything written before server.start() (and the executor's task handoff after it) is visible to the request threads, as long as nobody writes it afterwards.

A map of rate-limit buckets keyed by a client-chosen id, never trimmed, is an example of… (L24)

Every entry stays reachable from the map, so the garbage collector can never free it, however stale. L24's leaks were all this shape: a long-lived collection that only grows.

A load balancer polls /health and gets 503. What should it do? (L42)

L42's health checks took failing backends out of rotation. Shelf's /health now answers 503 when its database check fails, so a load balancer can route around it.

Why must a database password never appear in Config's defaults? (L33)

Anything in code is in every clone and every commit forever, and L33 showed old secrets turning up with git log -p. Secrets come from the environment (or a secrets manager) at run time; defaults are only for harmless settings.
