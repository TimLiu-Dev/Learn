Why it works. The key names one intended operation, so the server can tell "the same request again" from "another request that looks the same". Replaying the stored response means the client sees the same 201 and the same id however many times it retries, and the order exists once. A real server keeps the keys in its database, expires them after a while, and has to handle two copies arriving at the same moment, which is where L27's computeIfAbsent in Retry comes in. This practice is single-threaded. The 422 follows the IETF draft: a key reused "with a different request payload" SHOULD get 422 Unprocessable Content.

Common mistake. Deduplicating by content: "is there already an order for Dune?" That blocks a member who genuinely orders Dune twice with two keys, and still creates an order for a reused key with a new item. Compare keys, not bodies.
