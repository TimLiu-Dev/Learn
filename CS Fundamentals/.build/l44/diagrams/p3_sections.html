Decisions as ADRs

A design doc is written once, before the build. Decisions keep coming for years after it, and the people who join later need to know why things are as they are. Michael Nygard's answer is the architecture decision record (ADR): one short file per decision, kept in the repository next to the code (Documenting Architecture Decisions, 2011). L58 teaches the format in depth; here you just use it. Each record has five parts, in Nygard's words:

  • Title: "short noun phrases".
  • Context: "the forces at play, including technological, political, social, and project local".
  • Decision: "our response to these forces".
  • Status: "proposed" or "accepted"; and "If a decision is reversed, we will keep the old one around, but mark it as superseded."
  • Consequences: "the resulting context, after applying the decision", good and bad.

The shortener's "alternatives considered" become three of them. Each fits in a screen; Nygard's limit is "one or two pages".

ADR-001 · Random 7-character short codes

Status: accepted. Context: Codes are public, and people shorten private documents. A counter gives 6-character codes but makes every link enumerable (L33's IDOR). Hashing and truncating collides after about 2 M links (measured in Part 2), so it needs a collision check anyway. Decision: 7 random base62 characters from SecureRandom; the UNIQUE index detects a clash, and we pick again. Consequences: unguessable codes, and no coordination between servers. One character longer than a counter. About 0.17% of creates retry at 6 G links. Codes aren't time-ordered, so "newest links" needs created_at.

ADR-002 · Redirect with 302, not 301

Status: accepted. Context: RFC 9110 makes 301 heuristically cacheable, so browsers may stop asking us. We count clicks and links can expire. Decision: answer 302 Found with no Cache-Control. Consequences: every click reaches us and expiry takes effect at once. We pay one request per click, which the read estimates already include. If load ever forces caching, this ADR is superseded by one that accepts undercounting.

ADR-003 · Count clicks per day, through a queue

Status: accepted. Context: one row per click is 600 G rows (30 TB) in five years, and writing on the redirect path would make redirects wait for analytics. Decision: the redirect enqueues the code; a batch writer upserts clicks_daily(code, day) every 200 ms in one transaction. A full queue drops clicks and counts the drops. Consequences: stats lag by up to a flush, and can lose clicks under overload or a crash; redirects never wait. No per-click data means no per-hour or per-country stats without a new ADR.

Notice what moved out of the design doc: the reasoning. The doc now says "ADR-002" in one line, and the record carries the argument, so it can be found, linked from code review, and superseded without editing the original doc.

Diagrams as text

A box diagram in a drawing tool goes stale the day after the review, because nobody can diff it. Diagrams written as text live in the repository, change in the same pull request as the code, and show up in git diff. Mermaid is the common choice, and GitHub renders Mermaid blocks in Markdown files (GitHub Docs: Creating diagrams). L58 teaches the notations (C4, sequence, state and ER diagrams); here are the two this doc needs. Paste either into a Markdown file inside a ```mermaid fence, or into the editor at mermaid.live, to see it drawn.
