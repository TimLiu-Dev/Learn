Trade-offs & Resilience

Once a system is several programs talking over a network, parts of it will be slow, broken or unreachable while the rest keeps running. This lesson is about living with that: what "consistent" can mean when the network splits, how timeouts, retries, circuit breakers and rate limits stop one failure from spreading, and how logs, metrics and traces tell you what actually happened.

Part 1

Consistency and the CAP theorem, in plain terms

~25 min

In L42 you copied data to replicas so you could survive a dead machine and spread reads. Copies raise a question that one database never had to answer: when a copy is behind, what may a reader see? A consistency model is the answer, a promise about which values reads can return. Three you'll meet constantly, from strongest to weakest:

ModelPlain-words promiseExample
Strong (linearizable)The system behaves as if there were one copy. Once a write finishes, every later read, anywhere, sees it.A bank balance; "is this username taken?"
Read-your-writesYou always see your own writes. Other people may briefly see older data.Your own profile edits (L42)
EventualIf writes stop, all copies converge on the same value eventually. Until then, reads can disagree.A like counter; DNS records (L30)

Stronger models are easier to program against and cost more: the replicas must talk to each other before answering, which adds latency and fails when they can't reach each other. Designing Data-Intensive Applications (2nd ed.) treats these properly in its chapter on consistency and consensus; this part gives you the working intuition.

CAP: what happens when the network splits

A network partition means some machines can't reach others: a cable, a switch, a misconfigured firewall, a cloud region that goes dark. The machines are fine; the link between them isn't. The CAP theorem (Brewer's conjecture, proved by Gilbert and Lynch in "Brewer's Conjecture and the Feasibility of Consistent, Available, Partition-Tolerant Web Services", 2002) says that during a partition, a replicated system must choose: refuse some requests to stay consistent (C), or answer every request and risk returning stale or conflicting data (A).

You'll often hear CAP as "pick 2 of 3". Brewer himself rejected that framing twelve years later: "The '2 of 3' formulation was always misleading because it tended to oversimplify the tensions among properties", and "CAP prohibits only a tiny part of the design space: perfect availability and consistency in the presence of partitions, which are rare" (Brewer, "CAP Twelve Years Later: How the 'Rules' Have Changed"). Martin Kleppmann goes further and argues that labelling whole databases "CP" or "AP" is meaningless, because the theorem's definitions are narrow and real systems fit neither bucket cleanly: "please stop talking about CP and AP, because they just don’t make any sense" ("Please stop calling databases CP or AP", 2015). The useful takeaway is narrower and more practical: decide, per piece of data, what you do while replicas can't talk.

Read it as two business decisions:

  • The balance chose consistency. During the partition, nobody could change it: both writes were refused. That's unavailable, but nobody spent money they didn't have. When the link comes back, there's nothing to reconcile.
  • The cart chose availability. Both sides kept accepting writes and the two replicas disagreed for a while. On heal, "last write wins" quietly threw away the lamp: the customer added it, and it vanished. LWW is simple and convergent, and it loses data whenever two writes happen concurrently. That's acceptable for some data (a "last seen" timestamp), and terrible for a cart. The exercise fixes it by keeping both versions.

Bridge: offline-first Android apps are AP systems. The phone keeps working without a network and syncs later. Android's own guide describes the same trade-off: "For mobile apps, a common approach is "last write wins."" (Build an offline-first app). Its conflict-resolution section is worth reading after this part.

PACELC: the trade-off you face every day Optional deep dive

Optional: skip to the exercise if you're short of time; no Check question or later lesson depends on PACELC.

Partitions are rare. Daniel Abadi pointed out that a replicated system faces a second trade-off all the time ("Consistency Tradeoffs in Modern Distributed Database System Design: CAP is Only Part of the Story", IEEE Computer, 2012). His summary is PACELC: if there's a Partition, choose Availability or Consistency; Else, choose Latency or Consistency. That "else" is L42's replication choice. Waiting for the follower to confirm every write (synchronous replication) keeps reads consistent and makes every write slower. Replying before the follower has the data (asynchronous replication) is fast, and that's why read-your-writes can break.

What Kotlin does for you.
  • Destructuring a triple. val (a, b, link) = cluster("CP") unpacks a Triple in one line. Java returns a Node[] and indexes it, or needs a record to carry three values.
  • Data class vs record. data class Versioned(…) and record Versioned(…) both give you equals/hashCode/toString (L7). Kotlin reads fields as v.ts, Java as v.ts().
  • lateinit var peer says "set right after construction" without making the type nullable. Java's field just starts as null and nothing stops you forgetting it (L6).
  • Pairs. key to v builds a Pair; Java uses Map.entry(key, v).
Exercise: keep both versions

Last write wins lost the lamp. From a blank file, build two cart replicas that never lose an item. Each write records the version it replaced (its parent). When a replica receives a version with the same parent as its own current version, the two writes were concurrent: neither saw the other. Instead of picking one, keep both and merge them (for a cart, the union of the items). Replay the scenario: sync [book], partition, add lamp on A and pen on B, heal. Both replicas must end with all three items.

Reference solution and real output

Both replicas hold the same set. This is a simplified version of what real systems do with version vectors (Amazon's 2007 Dynamo paper, "Dynamo: Amazon's Highly Available Key-value Store", used exactly this shopping-cart example). Merging only works when the data has a sensible merge: a union is fine for a cart, while two concurrent bank withdrawals can't be "merged".

What does the CAP theorem actually force you to choose between?

CAP only bites when replicas can't reach each other. Brewer called the "2 of 3" reading misleading; with no partition, you can have consistency and availability. The everyday trade-off is PACELC's "else": latency vs consistency.

In the AP cart demo, why did the lamp disappear after the link healed?

Both writes were accepted. On heal, B compared timestamps and kept only the newer version (t=6), dropping A's concurrent write (t=5): "B drops [book,lamp]".

Part 2

Timeouts, retries, circuit breakers; a rate limiter

~35 min

Timeouts everywhere

Every remote call can hang: the other side is overloaded, stuck in a GC pause (L24), or its packets are going nowhere. Java's HttpClient has no request timeout unless you set one. The HttpRequest.Builder.timeout docs say it plainly: "The effect of not setting a timeout is the same as setting an infinite Duration, i.e. block forever" (docs). Amazon's guidance is blunt too: "A best practice in Amazon is to set a timeout on any remote call, and generally on any call across processes even on the same box" (AWS Builders' Library: Timeouts, retries, and backoff with jitter).

Here's why it matters. A dependency has one hung endpoint (/slow sleeps 5 s, standing in for an overloaded service) and one healthy one (/fast). Our service handles requests on a pool of 8 threads (L28). Fifty requests need /slow; then one request needs /fast:

  1. No timeouts. All 8 threads block on /slow. The /fast request, which needs nothing broken, waits in the queue behind 42 doomed requests and never gets a thread. After 5.5 s only the first wave of 8 has finished; the other 42 would take about 30 s more. One slow dependency has made a healthy endpoint unavailable. That's how failures spread: the Google SRE book defines it, "A cascading failure is a failure that grows over time as a result of positive feedback" (Addressing Cascading Failures). Callers waiting on us now time out, their threads fill up, and so on up the chain.
  2. 300 ms timeouts. Each doomed call gives up quickly, so the pool drains: all 50 fail fast in about 2.1 s (7 waves of 8 × 300 ms), and /fast is answered after 1.8 s. That's still slow, because it queued behind the failures, but it's no longer stuck.
  3. A bulkhead. Give each dependency its own small pool, like a ship's watertight compartments. The slow pool is still stuck, but /fast runs on its own threads and answers in 4 ms. A bulkhead doesn't fix the broken part; it stops it sinking everything else.

Notice what the timeout didn't do: the dependency kept sleeping for its full 5 s per request, doing work nobody would read. The SRE book's answer is to propagate deadlines down the call chain, so servers can drop requests their caller has already given up on. You'll see this waste in a trace in the final.

Retries, with exponential backoff and jitter

Many failures are transient: a dropped connection, a server restarting, a brief overload. Retrying turns them into successes. Retries are also dangerous, because they add load exactly when a system is struggling. AWS's article puts it well: "Retries are “selfish.” In other words, when a client retries, it spends more of the server's time to get a higher chance of success." Three rules make retries safe:

  1. Only retry what's safe to repeat. A failed request may still have had its effect: "A timeout or failure doesn't necessarily mean that side effects haven't happened", and "APIs with side effects aren't safe to retry unless they provide idempotency" (AWS, same article). GET, PUT and DELETE are idempotent by definition (RFC 9110, L31); POST needs an idempotency key (L32).
  2. Back off exponentially. Wait longer after each failure (50 ms, 100, 200, …, up to a cap) so a struggling server gets breathing room.
  3. Add jitter. "Jitter adds some amount of randomness to the backoff to spread the retries around in time" (AWS). Google's SRE book agrees: "Always use randomized exponential backoff when scheduling retries."

The third rule is the one people skip. Marc Brooker's companion post "Exponential Backoff And Jitter" simulates it, and names the simplest variant Full Jitter: sleep a random time between 0 and the capped exponential backoff. (The post shows its formulas as images; this is the same algorithm in words.) Here's a similar simulation: 100 clients fail at t=0; the server is down until 1 s, then can serve 10 requests per 100 ms window, and anything beyond that also fails. No network, just arithmetic, so both languages print exactly the same:

Without jitter, every client sleeps the same amount, so all the retries land together: waves of 100 with silence in between. When the server recovers, each wave brings 100 clients for 10 slots, 90 fail together, and they all back off together again. The last client is served at 28.8 s, after 1,050 attempts. With full jitter the same clients spread out: 706 attempts, and everyone is served by 3.9 s. Randomness made the system both kinder to the server and faster for the clients. Step through it in the Retries: jitter tab below.

Also limit how much retrying a whole process does. The SRE book suggests "Limit retries per request" and "Consider having a server-wide retry budget. For example, only allow 60 retries per minute in a process, and if the retry budget is exceeded, don't retry; just fail the request." Otherwise one outage turns every request into three.

Circuit breakers

Retries help with brief blips. When a dependency is properly down, retrying every request just hammers it, and makes every caller wait for timeouts. Martin Fowler describes the fix: "You wrap a protected function call in a circuit breaker object, which monitors for failures. Once the failures reach a certain threshold, the circuit breaker trips, and all further calls to the circuit breaker return with an error, without the protected call being made at all." After a while it goes half open, "meaning the circuit is ready to make a real call as trial to see if the problem is fixed" (CircuitBreaker). Here it is by hand, with an injectable clock (L38) so the demo and tests can move time instantly:

Pricing is down from 300 ms to 1,500 ms. After three failures in a row the breaker opens and the next four requests fail instantly, without touching pricing. At 1,000 ms one trial call goes through, fails, and the breaker opens again; at 1,500 ms the trial succeeds and traffic resumes. Pricing saw 17 calls instead of 25, and callers got immediate answers instead of slow failures. The Java run prints the same lines.

Three details make it safe under concurrency (L26–L27): every state change happens inside synchronized; the protected call itself runs outside the lock, so a slow call doesn't block other threads; and trialInFlight lets exactly one request probe a half-open circuit. Production libraries add more. Resilience4j "uses a sliding window to store and aggregate the outcome of calls", and opens "when the failure rate is equal or greater than a configurable threshold". A failure rate is often a better trigger than consecutive failures, as the final shows. Spring users usually reach it through Spring Cloud CircuitBreaker.

Rate limiting: protect yourself from your callers

Timeouts and breakers protect you from slow dependencies. A rate limiter protects you from your callers: one buggy client in a retry loop, or one scraper, shouldn't use up capacity everyone else needs. Two classic algorithms:

  • Token bucket. A bucket holds up to capacity tokens and refills at a steady rate. Each request takes one token; with none left, it's rejected. That allows bursts up to the capacity, and the refill rate on average.
  • Sliding window log. Remember when each accepted request happened, and allow a new one only if fewer than limit happened in the last window. That's exact and simple, but it stores one timestamp per request.

Both allow 5 per second, but they treat the 500 ms burst differently. The token bucket had refilled 2.5 tokens, so it let 2 through. The sliding window still remembered the 5 requests from t=0 and refused all 3, then let 4 through at 1,000 ms when those 5 slid out of the window. Neither is wrong; they're different definitions of "5 per second". Token buckets are the common choice for APIs because they're O(1) memory per client and naturally allow small bursts. Step through the bucket in the Token bucket tab above.

Over HTTP, a rejected request gets 429. RFC 6585 §4: "The 429 status code indicates that the user has sent too many requests in a given amount of time ("rate limiting")", and the response "MAY include a Retry-After header indicating how long to wait before making a new request" (RFC 6585). Retry-After itself is defined in RFC 9110 §10.2.3, either as an HTTP date or as a number of seconds (RFC 9110). One bucket per client, in a ConcurrentHashMap (L27); a greedy client next to a polite one:

Alice fires about 35 requests a second. She gets 9 through in the first second (the burst of 5 plus one second of refill), then a steady 5 per second, and everything else is a 429 with Retry-After: 1. Bob asks politely, about 2.5 times a second, and never notices the limiter exists: his bucket is separate. The 429 counts differ slightly between the runs because they depend on timing; the shape doesn't. A well-behaved client reads Retry-After and waits that long, instead of retrying immediately.

Bridge: in production, rate limiting usually lives in an API gateway or load balancer in front of your services, and per-client buckets live in a shared store (often Redis) so every server instance enforces the same limit. A bucket in one JVM's memory, as here, only limits traffic to that one instance. Mobile clients throttle themselves too: Android's WorkManager runs background work with backoff instead of hammering a server.

What Kotlin does for you.
  • @Synchronized on a method is Java's synchronized keyword, and synchronized(this) { } is a stdlib function that works like Java's block (L26). The bytecode is the same.
  • SAM conversion for Java interfaces. InstantSource { Instant.ofEpochMilli(now.get()) } turns a lambda into the JDK's one-method interface, just like Java's () -> … (L14). The breaker never knows the clock is fake.
  • Ranges read like the problem. now.get() in 300 until 1500 vs Java's now.get() >= 300 && now.get() < 1500.
  • Expressions everywhere. val outcome = try { … } catch (…) { … } assigns from a try (L10). Java needs a variable declared first and assigned in each branch.
  • Named arguments. TokenBucket(capacity = 5.0, perSecond = 5.0, clock = clock) says which 5.0 is which. Java's new TokenBucket(5.0, 5.0, clock) doesn't.

In the cascade demo with no timeouts, why was the healthy /fast request never answered?

All 8 worker threads were waiting forever on /slow, so /fast sat in the queue. Timeouts free the threads; a bulkhead gives /fast threads of its own.

Why did full jitter finish faster and make fewer attempts than plain exponential backoff?

Without jitter, 100 clients retried at the same instants and fought over 10 slots; 90 failed together each time. Random sleeps spread the same clients across many windows, so far more of them succeeded on each try.

A circuit breaker is OPEN. What happens to the next call?

That's the whole point of OPEN: fail fast and give the dependency room. After the open period, one trial call (HALF_OPEN) decides whether to close or reopen.

Part 3

Observability: logs, metrics, traces

~25 min

With one program, you debug by reading its output or attaching a debugger (L12). With twenty programs, a user's "it's slow" could be any of them. Observability is being able to answer "what is the system doing, and why?" from the outside. It usually rests on three kinds of telemetry: logs (events), metrics (numbers over time) and traces (one request's path through every service).

What should you measure first? Google's SRE book: "The four golden signals of monitoring are latency, traffic, errors, and saturation. If you can only measure four metrics of your user-facing system, focus on these four" (Monitoring Distributed Systems). Latency is how long requests take, and the book warns to track failed requests' latency separately, since "a slow error is even worse than a fast error!" Traffic is demand, such as requests per second. Errors is the rate of failing requests. Saturation is "how "full" your service is"; it adds that "Latency increases are often a leading indicator of saturation".

Metrics: counters, gauges, histograms

A counter only goes up (requests served). A gauge goes up and down (requests in flight, queue length). A histogram counts observations into fixed buckets, so you can estimate percentiles without storing every value: this is how L41's p99 is computed in production. Here they are by hand, exposed as text in the shape of Prometheus' text format (# HELP/# TYPE lines, cumulative _bucket{le="…"} counts, _sum and _count):

Each bucket line is cumulative: 588 requests took ≤ 25 ms, 958 took ≤ 50 ms, and so on, up to all 1,000. To estimate p95, find the first bucket whose count reaches 950: that's ≤ 50 ms. The format requires exactly this property: "A histogram must have a bucket with {le="+Inf"}. Its value must be identical to the value of x_count." The estimate is only as good as the buckets. The 4% of slow requests sit somewhere between 250 and 1,000 ms, so p99 can only be reported as "≤ 1000 ms". The exercise measures how much that costs. In real code you'd use Micrometer (Spring Boot's metrics library), which "provides a simple facade over the instrumentation clients for the most popular observability systems".

Structured logs

A log line like Got price for 42 in 125ms is fine for a person reading one file, and terrible for a machine searching a billion lines from fifty services. Structured logs write one JSON object per line with consistent field names: level, service, message, duration, and the IDs that tie a line to a request. Then "show me every error from pricing slower than 100 ms in trace X" is a query, not a grep puzzle. The JDK has System.Logger and java.util.logging; most JVM projects use SLF4J with Logback or Log4j 2, which can emit JSON. The next demo writes its JSON by hand.

Traces: one request across three services

A trace follows one request through every service it touches. Each service records a span; OpenTelemetry's docs: "A span represents a unit of work or operation. Spans are the building blocks of Traces", and each span knows its parent (OpenTelemetry: Traces). The services pass the trace along in an HTTP header standardised by the W3C: "The traceparent HTTP header field identifies the incoming request in a tracing system. It has four fields: version, trace-id, parent-id, trace-flags" (W3C Trace Context, a W3C Recommendation). Its grammar is trace-id = 32HEXDIGLC ("16 bytes array identifier. All zeroes forbidden") and parent-id = 16HEXDIGLC. The spec's own example is traceparent: 00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01.

Pricing's parent_id is books' span_id, and books' parent_id is the gateway's; the gateway has no parent, because the client sent no traceparent, so it started the trace. Rebuilding the tree gives the waterfall, and self time (a span's duration minus its children's) points at the culprit. The gateway did almost nothing itself; books spent about 40 ms (its fake 10 ms database call plus opening its first connection to pricing); pricing spent all of its time itself. That's where to look. Step through it in the Trace waterfall tab above. In production, each service would send spans to a collector (the OpenTelemetry Collector, Jaeger, Zipkin…) instead of a shared queue, and the OpenTelemetry SDK would read and write traceparent for you.

Don't forget the JVM's own telemetry. JFR (L24) records GC pauses, lock contention and hot methods with almost no overhead, and jcmd can dump threads and heap from a live process. When a trace says "pricing spent 900 ms itself", JFR on the pricing JVM tells you which method.

Alert on symptoms; budget for errors

Which of all these numbers should wake someone at 3 a.m.? The SRE book separates what's broken (the symptom) from why (the cause): "it’s better to spend much more effort on catching symptoms than causes". Users feel "checkout is slow", not "a disk is 80% full". So page a human on the golden signals as users experience them, and use cause-level metrics to diagnose.

How bad is too bad? "An SLI is a service level indicator—a carefully defined quantitative measure of some aspect of the level of service that is provided", and "An SLO is a service level objective: a target value or range of values for a service level that is measured by an SLI" (Service Level Objectives). For example: 99.9% of price lookups succeed in under 300 ms, measured over 30 days. The remaining 0.1% is an error budget: "The error budget provides a clear, objective metric that determines how unreliable the service is allowed to be within a single quarter" (Embracing Risk). With budget left, ship features; once it's spent, slow down and fix reliability.

What Kotlin does for you.
  • Raw strings for JSON. """{"level":"INFO", …}""" needs no \" escapes. Java needs a backslash before every quote, or a text block.
  • Templates with expressions. ${parentId?.let { "\"$it\"" } ?: "null"} renders a JSON string or null in place. Java needs a ternary and string concatenation.
  • generateSequence walks up the parent chain to compute a span's depth in one expression (L15). Java uses a for loop with a stream lookup per step.
  • Receiver lambdas can shadow your names, as the count() callout shows. That's the price of buildString's convenience: inside it, name the receiver whenever a method could exist on both.

Which list is the SRE book's four golden signals?

"The four golden signals of monitoring are latency, traffic, errors, and saturation." CPU and disk are causes; the golden signals are what users feel, plus how full you are.

In a trace, how do you know which service caused a slow request?

The root span is always the longest, because it includes everyone else. Self time (duration minus children) shows where the time was actually spent: here, pricing.

A Kotlin buildString { } block calls count(), meaning the enclosing class's method. What gets called?

The builder is the closest receiver, so CharSequence.count() wins, silently. My histogram printed _count 536. Write this@Histogram.count().

Final exercise

A resilient gateway

~25 min

Put Part 2 and Part 3 together. Start from a blank Gradle project (as in L11), Kotlin first and then Java, and don't look at the parts above until you've rated yourself.

  1. A flaky pricing service on 127.0.0.1: GET /price/{id} returns a price, but 20% of calls return 500 and 5% sleep 2 s first. Use a seeded Random. Also script a 2-second outage (every call returns 503 between 4 s and 6 s after start) so the breaker has something to do.
  2. A gateway with GET /api/price/{id} that, in this order:
    1. rate limits per client (the X-Client header) with a token bucket of 10, refilling 10/s, answering 429 with Retry-After;
    2. calls pricing through a circuit breaker that opens after 5 consecutive failures, for 1 s;
    3. gives every call a 300 ms timeout;
    4. retries up to 2 more times with exponential backoff (50 ms base, 400 ms cap) and full jitter, for GETs only, and never when the circuit is open;
    5. falls back to the last good price for that id, marked "stale":true with an X-Fallback header, or answers 503 with Retry-After if it has never seen one.

What the runs show, in both languages:

  • No user saw an error. The 503 column is 0 in every second, including the scripted outage at 4–6 s. While pricing was down, requests were answered from the last good prices, marked stale, in 0–3 ms each. Whether a stale price is acceptable is a business decision; for a product page it usually is, at checkout it isn't.
  • The breaker opened before the outage, at about 2.5 s. Pricing fails 25% of the time (20% errors + 5% timeouts), and four clients share one breaker, so five failures in a row happen by chance within a couple of seconds. That's the weakness of a consecutive-failure trigger under a steady error rate, and the reason libraries like Resilience4j use a failure rate over a sliding window instead. Then it kept re-opening: each trial call during the outage failed, until the first trial after 6 s succeeded.
  • The greedy client was contained. Every 429 belongs to it; the polite clients stayed under 10 requests a second and were never limited. The greedy client's requests still count as traffic, which is why the request column is high.
  • The trace shows wasted work. Attempt 1 timed out after 302 ms, yet pricing went on working on it for 2,001 ms, long after the gateway had given up and retried successfully (attempt 2, 2 ms). Without the trace you'd never see those 1.7 s of pointless work. Deadline propagation, from the SRE book, is the fix.
  • The histogram's p95 (≤ 50 ms) is far below the per-second p95 in the slow seconds (around 320–340 ms, when timeouts and retries happened). An aggregate over the whole run hides bad seconds. That's why dashboards plot percentiles over short windows.

Production versions of these pieces: Resilience4j or Spring Cloud CircuitBreaker for breakers and retries; an API gateway, or Redis-backed buckets, for rate limits; Micrometer plus Prometheus for metrics; the OpenTelemetry SDK and Collector for traces and logs. Each is a well-tested version of a class you just wrote.

Wrap-up

Exit quiz, recall card, sources

~5 min

L26 + L43: why are tryAcquire and refill in the token bucket synchronized?

"Check tokens ≥ 1, then subtract" is check-then-act on shared state (L26). Without the lock, two request threads can both see 1.0 and both proceed. The 8-thread test proves exactly 100 grants for 100 tokens.

L31 + L43: which of these requests is safe to retry automatically after a timeout?

GET is safe and idempotent (RFC 9110). A timed-out POST may already have created the order or charged the card, so retrying it blindly can do it twice, unless the API supports an idempotency key (L32).

L38 + L43: why do the breaker and bucket take an InstantSource instead of calling Instant.now()?

Dependency injection of the clock (L38) lets a test jump 1,000 ms instantly with a fake. The tests run in milliseconds and give the same result every time.

L24 + L43: a trace shows the pricing span spent 900 ms of self time. What should you reach for next?

The trace tells you which service; a profiler tells you which code. JFR's execution samples (L24) find the hot method inside that 900 ms. The other three only hide the symptom.
