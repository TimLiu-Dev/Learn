Why did L44's URL shortener redirect with 302 instead of 301? (L44)

A 301 is cacheable by default, so a browser stops asking after the first visit and the click counter never sees the rest. 302 keeps every click coming back to the server (RFC 9110 §15.4).

  1. A 301 is cacheable by default, so repeat visits skip the server and its click counter.
  2. Both are one round trip. The difference is what the browser may cache, not speed.
  3. RFC 9110 still defines 301 Moved Permanently; it's the right answer for a move that never changes back.
  4. The Location header is visible either way. No redirect hides its target.

What is a composition root? (L38)

Everything else depends on interfaces and receives its dependencies through constructors; only the composition root says SqliteBookStore(db). Today that's the Shelf class.

  1. It's about wiring objects, not inheritance. Shelf's services extend nothing.
  2. It's a place in the code, not in the file system: in Shelf it's one class.
  3. Only Shelf names SqliteBookStore and friends; everything else receives interfaces through constructors.
  4. Tests build their own objects. A composition root is production wiring, not a test.

L36 put a partial unique index on loans(book_id) WHERE returned IS NULL. What does it do? (L36)

Only open loans are in the index, and it's unique on book_id, so a second open loan for the same book is a constraint violation, whatever the application code does. Shelf keeps it as its last line of defence.

  1. It can speed up open-loan lookups by book, but its real job is the uniqueness rule.
  2. Unique over rows WHERE returned IS NULL: one open loan per book, enforced by SQLite itself.
  3. Returned loans aren't in this index at all: its filter keeps only open ones.
  4. An index never changes what's written to the table. returned is stored as usual.

A POST /books that creates a book should answer with… (L32)

RFC 9110 §9.3.3: the origin server "SHOULD send a 201 (Created) response containing a Location header field that provides an identifier for the primary resource created". Shelf does exactly that.

  1. 200 works, but says nothing about a new resource. RFC 9110 recommends 201 for a creating POST.
  2. 204 sends no body, and no URL for the new book.
  3. 302 sends the client somewhere else. It doesn't report that something was created.
  4. 201 says a resource was created, and Location tells the client where it lives.

Three details carry over from earlier phases. The server binds to InetAddress.getLoopbackAddress(), so nothing outside this machine can reach it (L30). The router

HttpServer routes by context. Its docs: "the appropriate HttpContext (and handler) is located by finding the context whose path is the longest matching prefix of the request URI's path." Shelf registers a single context, "/", which is a prefix of every path, so every request reaches one handler: Router.handle. From there, routing is yours. A route is a method plus a path template such as /books/{id}. Matching a request has three outcomes, which is why Match is a sealed type:

  • Found: a template and the method both match. The router binds the {id}-style segments into a map and calls the handler.
  • WrongMethod: some template matches the path, but not for this method. That's a 405, and RFC 9110 §10.2.1 says "An origin server MUST generate an Allow header field in a 405 (Method Not Allowed) response", so the router collects the methods that would have worked.
  • NoRoute: nothing matches the path at all. That's a 404.
Java's Request and Response (Kotlin keeps them in Router.kt)

Read handle as the whole "framework" in twenty lines: match, run the handler, turn every failure into a Problem Details response, send. Handlers never write to the exchange themselves; they return a Response. That keeps them small, and it means status codes and headers are decided in exactly one place. Errors flow the other way: a handler that can't answer throws an ApiError (404, 409, 400…), and handle renders it. Anything unexpected becomes a 500 whose body says only "Something went wrong"; the details go to the log, never to the client (L33).

Part 2

JSON endpoints

~35 min

DTOs are not the domain

The domain classes (Book, Member, Loan) are plain data: no JSON annotations, no SQL. The http package has its own DTOs (data transfer objects), shaped like the JSON. Keeping them apart costs a few mapping functions, and buys three things you'll use today:

  • Input DTOs have nullable fields, even for required data, so a missing title becomes the message "title is required" instead of a parser exception. Validation happens here, at the boundary, and produces a clean command (NewBook) that the service can trust (L10: parse, don't trust).
  • Output DTOs choose the wire format. Loan.loaned is a LocalDate in the domain and an ISO-8601 string in the JSON (L32).
  • The API can change without touching the domain, and the reverse.

Errors as Problem Details

RFC 9457 defines "a 'problem detail' to carry machine-readable details of errors in HTTP response content" (RFC 9457). Shelf uses the about:blank type everywhere, which "indicates that the problem has no additional semantics beyond that of the HTTP status code", and the RFC adds that the title "SHOULD be the same as the recommended HTTP status phrase for that code". So a validation failure is titled Bad Request, and the specific messages go in an errors extension member. (My first version titled it "Invalid request"; rereading §4.2.1 made me fix it in both languages.)

Java's ApiError (Kotlin keeps it in Json.kt)

The two JSON libraries start from opposite defaults (you saw this in L32). kotlinx.serialization rejects unknown keys unless you set ignoreUnknownKeys, and by default "all null values are encoded into JSON output" unless you set explicitNulls = false (Kotlin docs: Customize the Json instance). Jackson 3 ignores unknown keys by default. Shelf configures both the same way: strict about unknown keys, and silent about nulls. That's why the two servers give byte-identical responses.

The handlers

Each handler does three things: read the request (path parameters, query, body), call one service method, and map the result to a response. There's no SQL here and no business rule. When the service returns a sealed result such as BookOnLoan, the handler chooses the status code.

JDBC with SQLite; unit vs integration tests

The schema and a tiny JDBC helper

The schema is L34's library (with authors in their own table, L35), plus L36's partial unique index. Db opens a fresh connection per operation, switches on foreign keys every time (they're off by default in SQLite, L34), and asks for transaction_mode=IMMEDIATE so concurrent writers queue instead of failing halfway (L36). Three helpers, query, update and insert, bind every value through a ? placeholder, so SQL injection (L33) can't happen here.

The rules

A known race, kept on purpose. lend checks openForBook and then calls add: two store calls, two transactions. Two requests for the same book at the same instant can both pass the check (L26's check-then-act, L38 flagged it). In v1 the partial unique index still refuses the second insert, so the data stays correct, but that request gets a 500 instead of a 409. L46 load-tests Shelf, reproduces this for real, and fixes it.

Three kinds of test

Martin Fowler's Test Pyramid: "you should have many more low-level UnitTests than high level BroadStackTests". Ham Vocke's longer Practical Test Pyramid puts it as "Write lots of small and fast unit tests. Write some more coarse-grained tests and very few high-level tests". Shelf has all three levels:

  • Unit tests run one class with fakes: RouterTest, BookServiceTest and LendingServiceTest (the real service, in-memory stores, a fixed clock).
  • Contract tests run one suite against both store implementations (L38), so the fakes the unit tests rely on can't drift away from SQLite. (This is the provider's own kind of contract: one interface, two implementations. Part 5 meets the other kind, written by the API's consumers.)
  • Integration tests start the whole app on port 0 (the OS picks a free port) with a temporary SQLite file, and talk to it over real HTTP with HttpClient (L31).

The bug only a contract test caught

The Java store's first book() mapper looked fine, and every unit test passed, because unit tests use the in-memory store. The contract test, running against SQLite, didn't:

getInt returns 0 for SQL NULL, and the ResultSet docs say wasNull() "Reports whether the last column read had a value of SQL NULL" (java.sql.ResultSet). Java evaluates constructor arguments left to right, so by the time wasNull() ran, the last column read was column 3, the author, which is never null. The fix reads the columns in order and asks wasNull() straight after getInt(4). The Kotlin version never had the bug, by luck of argument order: rs.getInt(4).takeUnless { rs.wasNull() } is the fourth argument, so wasNull runs right after getInt. Same contract, same test, both stores now green: this is what contract tests are for.

What Kotlin does for you.
  • inline fun <T> transaction(block: (Connection) -> T) takes a lambda, and since SQLException isn't checked in Kotlin, there's no wrapper type. Java defines a Work<T> interface whose method throws SQLException, and wraps failures in DbException (L10).
  • c.query(sql, id) { book(it) }: an extension function with a trailing lambda. Java's varargs must come last, so the row mapper goes in the middle: query(c, sql, mapper, id).
  • One file, SqliteStores.kt, holds three classes. Java needs one public class per file.
  • rs.getString(5)?.let(LocalDate::parse) handles a nullable column in one expression.
  • A nullable Book? return replaces Java's Optional<Book>.
  • @Synchronized on the fakes compiles to the same monitor as Java's synchronized methods (L26).

Coverage and property-based tests

~28 min

Shelf has 33 tests per language, all green. Two questions a green bar can't answer: which code did no test ever run, and which inputs did nobody think of? A coverage tool answers the first. A property-based test goes after the second. Both work with what you already have: a Gradle plugin, and a seeded Random.

What coverage measures

JaCoCo attaches an agent to the test JVM, records which bytecode instructions ran, and maps them back to source lines. Its docs define the two numbers you'll read most (JaCoCo: Coverage Counters):

  • Line coverage. "A source line is considered executed when at least one instruction that is assigned to this line has been executed."
  • Branch coverage. JaCoCo "calculates branch coverage for all if and switch statements": each way out of a decision counts. A line with a || b has four branches, two per condition. And "exception handling is not considered as branches", so a catch block only shows up in line coverage.

Gradle ships a jacoco plugin (Gradle docs: The JaCoCo Plugin). Add it to app/build.gradle.kts in either language. On first use, Gradle 9.7.1 downloaded JaCoCo 0.8.14 from Maven Central.

Run ./gradlew test jacocoTestReport, then open app/build/reports/jacoco/test/html/index.html. The CSV next to it has one row per class. Summed per package, for the Java capstone:

The Kotlin report has the same shape: 92.5% of lines and 78.7% of branches. The numbers differ a little because JaCoCo counts bytecode, and the two compilers produce different bytecode from similar source.

Read the red lines, not the percentage

The percentage is a summary. The useful part is the list of lines no test ran (red) or only partly ran (yellow). Here are three files from the Java HTML report:

What coverage does not prove

Coverage says that a line ran. It doesn't say a test checked what it did, and it doesn't say the inputs were the ones that matter. Here's a small demonstration, run with the same plugin in a separate project:

Both tests pass, and every line and every branch ran: 100% and 100%. The rule is still wrong. A member who holds 3 loans may borrow a fourth, because <= should be <. Branch coverage only asks that the comparison came out true once and false once, and 0 and 5 manage that without going near the boundary at 3. Shelf's real test, a member can hold at most three open loans, lends exactly three and checks that the fourth is refused, which is why it would catch this. Two more blind spots:

  • A test with no assertions covers the same lines as one with good assertions.
  • Code that's missing, such as a check nobody wrote, has no line to turn red.

Use coverage as a map of what you haven't tested, not as a score. A required percentage rewards tests that run code without checking it.

Property-based testing, by hand

An example test checks one input you chose. A property is a statement that must hold for every input, and a property-based test checks it on many generated ones. The idea comes from Koen Claessen and John Hughes's paper QuickCheck: A Lightweight Tool for Random Testing of Haskell Programs (ICFP 2000): "Properties are described as Haskell functions, and can be automatically tested on random input". You've used a cousin already: the differential tests in L49, L51 and L54 generated inputs and compared two implementations. A property needs no second implementation, only a rule that must always hold. And you don't need Haskell or a library. It has three parts:

  1. A generator. Random inputs from a Random with a fixed seed, so any failing run can be replayed exactly.
  2. A property. Shelf's lending rules must hold after any sequence of lends and returns: no member holds more than 3 open loans, and no book is on two open loans at once.
  3. A loop. 1,000 runs of 30 random operations each, against the real LendingService with the memory stores, checking the property after every operation. Unknown book and member ids are in the mix on purpose.

Shrinking. That counterexample is 29 steps long, and most of them are noise: the failure needs only four lends.   • steps += if (…) { … } else { … }: if is an expression, so each branch's last line is the step's description. Java adds to the list in each branch.
  • open.groupBy { it.memberId }.any { it.value.size > 3 } is one expression. Java needs Collectors.groupingBy(…, counting()) and a helper.
  • kotlin.test.fail returns Nothing, so the compiler knows the code after it can't run.

JaCoCo reports 100% line coverage for a class. What does that tell you?

A line counts as covered when at least one of its instructions ran during the tests. Nothing in the number says what was checked, or with which inputs. The demo had 100% and a bug.

  1. That's all it means: at least one instruction on each line ran during some test.

A new test calls validate() on several bodies but asserts nothing. What happens to coverage?

JaCoCo records what ran, not what was verified, so the new test raises the numbers without catching anything. That's why a coverage target on its own invites hollow tests.

  1. More code ran, so coverage can only stay the same or rise.
  2. JaCoCo looks at bytecode execution. It knows nothing about assertions.
  3. The lines ran, so they count as covered, but nothing checks the results.
  4. JUnit passes a test that doesn't throw. Assertions are optional, as far as it's concerned.

Why does LendingPropertyTest build its Random from a fixed seed?

  2. JUnit doesn't care where test inputs come from; unseeded randomness runs fine.
  3. Seeding costs the same as not seeding. Speed isn't the reason.
  4. Same seed, same inputs, same failure, so you can rerun and debug it.

  1. Shrinking works on inputs, not on files or reports.
  2. It searches for a smaller input that still fails, so you debug four lends, not 29 steps.
  3. The number of cases is a separate setting. Shrinking starts only after a failure.
  4. It never touches your test suite. It only works on one failing input.

  2. At 4 both say no: 4 <= 3 and 4 < 3 are both false, so they agree.
  3. 3 is the only value where <= and < give different answers.
  4. For 0–2, both comparisons are true, so those values agree and aren't failures.
Part 5

Evolving the API without breaking clients

~35 min

The day Shelf v1 ships, its API stops being yours alone. Say an Android app reads GET /books/{id}. Version 1.0 of that app is now installed on phones you don't control, and it keeps calling Shelf until each owner updates it. Android's own docs say that "some users enable background updates", but "other users might need to be reminded to install updates" (Android: in-app updates). So every old app version you ever shipped is a client you must keep working, for months or years. This part is about changing Shelf without breaking them.

Tolerant readers, strict input

Martin Fowler's Tolerant Reader (2011) starts from Postel's law, "be conservative in what you do, be liberal in what you accept from others", and recommends: "be as tolerant as possible when reading data from a service". For JSON, that means: read the fields you need and ignore the rest. Here's an app's v1.0 parser meeting three versions of the server: unchanged, with an isbn field added, and with author renamed to authors:

Three things to read off that output. A strict client breaks the moment the server adds a field, even though nothing it uses changed. A tolerant client shrugs off the addition. And no reader survives a rename: the field it needs is gone. Kotlin's non-null author made the failure loud; Java needed requireNonNull in the record, because without it Jackson would quietly have built a book whose author is null, and the app would have crashed later, somewhere else.

Now look at Shelf from the other side. Part 2 made Shelf strict about its input: an unknown key in a request body is a 400 (quiz p2-4). That's a trade-off, not a rule:

  • For strict input: a typo such as "yaer": 1965 is rejected, instead of silently saving a book with no year. Clients learn about their mistakes on the first request.
  • Against it: a newer client that sends a field the server doesn't know yet gets a 400. That happens during a rolling deploy, when old and new servers run side by side, and after a rollback to the previous server (L59). Many public APIs ignore unknown request fields for exactly this reason.

Shelf keeps strict input, and accepts the consequence: when a request gains a field, the server that understands it must be fully deployed before any client sends it. Responses go the other way. Clients must read them tolerantly, because the server will keep adding fields.

Changes that are safe, and changes that break

Google's API guidelines put the rule in one sentence: "Existing client code must not be broken by a service updating to a new minor or patch release" (AIP-180: Backwards compatibility). New components "may be added to existing APIs in the same major version"; but "Removing a component is a backwards incompatible change", and renaming is "semantically equivalent to" remove and add.

ChangeOld clientsSo…
Add a field to a responseTolerant readers ignore itSafe: just do it
Add an endpointNever call itSafe
Add an optional request field with a defaultDon't send it, get the old behaviourSafe, once every server understands it
Remove or rename a field, or change its typeFail to parse, or read nullBreaking
Make an optional request field requiredGet 400sBreaking
Change what a field meansParse fine, show wrong dataBreaking, and the worst kind

The last row deserves its own rule: never repurpose a field. If year started meaning "year of this edition" instead of "year first published", every old client would keep working and keep showing the wrong year, with no error anywhere. AIP-180 covers it too: APIs "must not change visible behavior or semantics in ways that are likely to break reasonable user code". Add editionYear instead, and leave year alone.

A new version (/v2/books, say) is for breaking changes only, and it's expensive: you now run, test and secure two APIs until the last old client is gone. Additive changes need no new version at all. That's the same idea as SemVer's major version (L25), applied to a network API.

Retiring an endpoint politely

Sometimes something really must go. HTTP has two headers for saying so in advance. RFC 9745's Deprecation header "allows a server to communicate to a client application that the resource in the context of the message will be or has been deprecated"; its value is a date, written as @ plus Unix seconds (RFC 9745, 2025). RFC 8594's Sunset header "indicates that a URI is likely to become unresponsive at a specified point in the future", as an ordinary HTTP-date (RFC 8594). RFC 9745 ties them together: the sunset "MUST NOT be earlier than" the deprecation, and "for historical reasons the Sunset HTTP header field uses a different data format for date".

Deprecation: @1798761600                    (2027-01-01T00:00:00Z)
Sunset: Sat, 01 Jan 2028 00:00:00 GMT
Link: <https://shelf.example.com/docs/changes#member-loans>; rel="deprecation"

Two things the headers don't do. They don't change behaviour: "The act of deprecation does not change any behavior of the resource" (RFC 9745 §5). And nobody is obliged to read them: RFC 9745 calls them "only a hint", and says clients "should always be implemented in ways that allow them to function without deprecation-related information". So before you switch an endpoint off, count who still calls it. L46's access log, one JSON line per request, answers that with one jq command. Exercise 5 retires a real Shelf endpoint this way.

Two kinds of "contract test"

Part 3's StoreContract is one kind: one test suite, run against every implementation of an interface you own, so the memory fake can't drift away from SQLite. It protects Shelf from itself. It says nothing about Shelf's clients.

The other kind is the consumer-driven contract test. The Pact project defines contract testing as "a technique for testing an integration point by checking each application in isolation to ensure the messages it sends or receives conform to a shared understanding that is documented in a 'contract'", and Pact itself as "a code-first consumer-driven contract testing tool" (Pact docs). The consumer (the app team) writes down what it actually reads. The provider (Shelf) runs those expectations in its own build. If a Shelf change would break the app, Shelf's build goes red, before anything ships.

Wrap-up

Exit quiz, recall card, sources

~5 min

Which executor does Shelf give its HttpServer? (L28)

One cheap virtual thread per request. A request blocked on SQLite parks its virtual thread and frees the carrier. Without setExecutor, HttpServer would handle requests on its own dispatcher thread, one at a time.

  1. One virtual thread per request, so a request blocked on SQLite parks cheaply.
  2. One thread would serve requests one at a time, like having no executor.
  3. A fixed pool caps concurrency at four; blocked requests would queue behind them.
  4. The common pool is meant for CPU-bound fork/join work, not blocking I/O.

The 500 handler logs the exception but sends only "Something went wrong". Why? (L33)

Error details reveal libraries, versions and sometimes SQL: the security-misconfiguration category of L33's OWASP list. Log them for yourself; send a generic problem to the client.

  1. Clients parse long JSON fine. The issue is what the details reveal.
  2. HttpServer sends whatever length you declare. It truncates nothing.
  3. Details reveal libraries, versions and SQL to whoever triggers the error.
  4. Logging is good practice, not a precondition for answering.

The contract test compares domain objects with assertEquals. What makes that work? (L7)

data class and record generate value-based equals and hashCode, so a book read back from SQLite equals the one you added, field by field.

  1. toString only shapes the failure message. It doesn't decide equality.
  2. data class and record compare field by field, so equal values are equal.
  3. Constructors don't affect equality, and these records have no no-arg constructor.
  4. java.io.Serializable is about byte streams. It doesn't define equality.

What does ./gradlew installDist produce? (L25)

The Application plugin's docs: "You can run gradle installDist to create an image of the application in build/install/projectName". That image has bin/app plus every jar in lib/; the session above ran bin/app.

  1. A fat jar needs a plugin such as Shadow. installDist keeps the jars separate.
  2. The Application plugin doesn't build container images.
  3. A native image needs GraalVM's own plugin. installDist runs on a normal JVM.
  4. build/install/app holds bin/app, a start script, and every jar in lib/.
