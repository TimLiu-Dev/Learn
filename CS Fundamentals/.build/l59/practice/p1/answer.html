Why it works. Validating before applying means an edited history stops the run while the database is still in a known state. Running the script and writing its history row in one transaction makes "applied" and "recorded" the same fact: you can never have a table without its row, or a row without its table. That's exactly what Migrator does with JDBC's commit and rollback.

Common mistake. Running the script first and recording it in a separate transaction afterwards. When the second statement of a script fails, the first one's table stays behind with no history row, and the next run trips over "table members already exists".
