Why it works. lowerBound halves lo..hi on every read, so 200,000 entries take 18 reads to find the start. The walk then reads one entry per match, plus one to see the key that ends it: 29 reads for member 42, against 200,000 for a scan. That's Part 2's B-tree in miniature: a short descent, then a sideways walk along sorted leaves. A real B-tree does the same with ~375 keys per page, so its descent is 3 page reads.

Common mistake. The textbook "find it" binary search, which returns as soon as it hits an equal key. It lands on some entry for member 42, usually not the first, so the walk misses the loans to its left. A linear search for the start gives correct rows but reads 100,000 entries on average: a scan wearing an index's clothes. The read-count checks catch that one.
