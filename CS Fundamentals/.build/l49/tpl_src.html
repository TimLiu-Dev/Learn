Part 1

Greedy choices and the exchange argument

~30 min

A greedy algorithm builds its answer one choice at a time. At each step it takes whichever option looks best right now, and it never goes back to reconsider. That makes greedy algorithms short and fast: usually a sort followed by one loop, so O(n log n). It also makes them easy to get wrong. In L21, "always take the biggest coin" made 6 from [1, 3, 4] as 4 + 1 + 1, three coins, when 3 + 3 needs only two.

A problem where some greedy rule works

Jeff Erickson's free textbook Algorithms opens its greedy chapter with class scheduling. Every class has a start and a finish time, two classes that overlap can't both be taken, and "you want to register for as many classes as possible" (Erickson, ch. 4 "Greedy Algorithms", Scheduling Classes). Meeting rooms, CPU time slots and conference talks are the same problem. Three greedy rules sound reasonable:

  • Earliest start: take the class that starts first, then the next one that fits, and so on.
  • Shortest first: short classes block less of the day, so take those first.
  • Earliest finish: Erickson's choice: "Intuitively, we'd like the first class to finish as early as possible, because that leaves us with the largest number of remaining classes."

Two small schedules already break two of them. Times are half-open, [start, end), so a class may start the minute another ends. (Erickson treats touching classes as clashing; the argument below works either way.)

In trap1, "earliest start" grabs long and blocks both short classes. In trap2, "shortest first" grabs short, which overlaps both of the others. Two counterexamples prove two rules wrong. But no number of passing examples proves a rule right, so let's first gather evidence. The program below runs each rule on both traps, then on 10,000 random schedules, comparing each answer with the true optimum found by brute force over all 28 subsets. Bit i of mask means "take class i", the subset trick from L48.

  • Earliest start fails a third of the time. Easy to catch.
  • Shortest first is optimal in 95.7% of random schedules. A test suite of a few hand-picked cases could easily pass it and ship a bug. Random testing found it, but only because the counterexamples weren't too rare.
  • Earliest finish is optimal in all 10,000. That's strong evidence, but it isn't proof: maybe the counterexample needs 9 classes. L48's lesson applies. Tests can show a bug exists; only an argument can show none does.

The exchange argument

Greedy algorithms are usually proved correct the same way. Erickson calls it an inductive exchange argument, and gives its general pattern:

  • "Assume that there is an optimal solution that is different from the greedy solution."
  • "Find the “first” difference between the two solutions."
  • "Argue that we can exchange the optimal choice for the greedy choice without making the solution worse (although the exchange might not make it better)."

"This argument implies by induction that some optimal solution contains the entire greedy solution, and therefore equals the greedy solution" (Erickson ch. 4, General Pattern). Here it is for earliest finish, in plain words:

  1. The key lemma. Let f be the class that finishes first. Take any best schedule. If it doesn't contain f, look at its first class g. Swap g out and f in. Because f finishes no later than g, it can't clash with anything that came after g. The new schedule has the same number of classes, so it's still best. Erickson: "At least one maximal conflict-free schedule includes the class that finishes first."
  2. The induction. So some best schedule starts with greedy's first choice. Remove f and every class it clashes with. What's left is a smaller scheduling problem, and greedy's next choice is exactly "the first to finish" in that smaller problem. The same lemma applies again, and again: L48's induction step.
  3. The finish. After k steps some best schedule agrees with all k greedy choices. Greedy only stops when no class fits, so that best schedule can't contain any more classes either. They have the same size.

Notice why the same swap fails for the other rules. In trap2, swapping in short for x doesn't work, because short ends later than x and clashes with y. The exchange only works if the greedy choice "leaves at least as much room" as whatever it replaces. That's the property to look for whenever you try a greedy rule.

Where greedy wins elsewhere. The same chapter proves Huffman's compression codes optimal with an exchange argument: "Every Huffman code is an optimal prefix-free binary code" (Erickson ch. 4, Huffman Codes). Huffman coding is half of DEFLATE, the format gzip uses (RFC 1952), which "compresses data using a combination of the LZ77 algorithm and Huffman coding" (RFC 1951). And the two algorithms in the rest of this lesson are greedy too. Dijkstra always settles the closest unsettled vertex. Kruskal always takes the lightest edge that doesn't close a cycle. Both are correct for the same reason: an exchange argument.

Solution

It's always optimal, and the proof is the mirror image of the one above. Run time backwards and "latest start" becomes "earliest finish". Then let l be the class that starts last. Check

A greedy rule passes 10,000 random tests against a brute-force answer. What have you shown?

"Shortest first" passed 95.7% of random schedules while being wrong. Random tests can find a counterexample but can't rule one out, because it might need a bigger input or a rare pattern. The exchange argument is what turns evidence into certainty.

Which greedy rule always schedules the most non-overlapping classes?

Earliest finish leaves the most room for everything after it, which is exactly what the swap in the proof needs. Earliest start and shortest first each fail on a three-class trap, and longest first fails on trap1 too: it grabs long. Erickson's end-of-chapter exercise lists nine plausible rules with the hint "Three of these algorithms are actually correct".

In an exchange argument, you swap the best schedule's choice for greedy's choice. The swap must…

Erickson: exchange "without making the solution worse (although the exchange might not make it better)". An equally good solution that agrees with greedy one step further is all the induction needs.

Sorting n classes by finish time, then one pass over them, costs…

The sort dominates (L18). The pass itself is O(n) if you only compare against the last class taken, which is enough for earliest-finish order: Erickson notes that "after the initial sort, the algorithm is a simple linear-time loop". Schedule checks against every chosen class instead, because its other rules don't produce time order. The brute force is the O(2ⁿ) one.

Part 2

Dijkstra, built for real

~35 min

L21 described Dijkstra's algorithm in one paragraph: BFS with the queue replaced by a priority queue ordered by distance so far. Today you write it. The graph is seven towns joined by two-way roads, each labelled with minutes of driving. The widget below draws it.

Relaxation

Every shortest-path algorithm is built on one move. Keep a best-known distance dist[v] for every vertex: 0 for the start, ∞ for the rest. Sedgewick & Wayne: "To relax an edge v->w means to test whether the best known way from s to w is to go from s to v, then take the edge from v to w, and, if so, update our data structures" (algs4 §4.4 Shortest Paths). If dist[v] + weight < dist[w], then w gets a new distance and a new parent, v.

Dijkstra decides the order of relaxations. It "repeatedly relaxes and adds to the tree a non-tree vertex with the lowest distTo[] value" (§4.4). In other words, it always settles the closest unsettled vertex next. That's the greedy choice. The priority queue from L20 is what makes "closest" cheap to find.

Both languages print exactly this. Look at what happened:

  • B's distance improved. From A, the direct road to B gives 4. But C was closer (2), so C was settled first, and C-B gave 2 + 1 = 3. The detour beats the direct road, and Dijkstra found it because it settles in order of distance.
  • Four "stale" polls. PriorityQueue can't lower an entry that's already inside it. Removing the old entry is no help either, since remove(Object) takes "linear time" (PriorityQueue). So the code just adds a second, shorter entry, and when the old one comes out later, it skips it. This is the lazy version of Dijkstra. Sedgewick & Wayne's DijkstraSP instead "uses IndexMinPQ.java for the priority queue", a heap that can lower a key in place. Same Big O, more code.
  • Ties broken by name. (10, D) and (10, E) tie. The JDK says that when "multiple elements are tied for least value, the head is one of those elements -- ties are broken arbitrarily". Adding the town name to the comparator makes every run, in both languages, print the same lines.
  • F-G didn't relax. When F was settled at 12, its road to G offered 12 + 3 = 15, which is worse than the 14 G already had through E. Not every edge improves something.

Step through it. Purple edges are each town's current parent: together they form the shortest-path tree. Dashed orange edges were just relaxed. The small purple numbers are dist. Dashed queue entries are stale: their town is already settled.

Why the greedy choice is safe

Claim: when a town is polled with the smallest distance in the queue, its distance is final. The invariant (L48) is "every settled town's distance is final", and this is the step that keeps it true. Suppose town x is polled with distance d, and some route from A to x were shorter than d. The route starts at A, inside the settled set, so at some point it leaves the set through an edge from a settled town y into an unsettled town u. By the invariant, y's distance is final, so relaxing y-u already gave u a queue entry no longer than the route up to u. Since d was the smallest entry in the queue, the route up to u is already at least d long. The rest of the route can only add to that, because no weight is negative. So the route costs at least d, which contradicts "shorter". (That's a sketch; the book proves it in full.) Sedgewick & Wayne's statement, §4.4: Dijkstra "solves the single-source shortest-paths problem in edge-weighted digraphs with nonnegative weights using extra space proportional to V and time proportional to E log V (in the worst case)".

Where E log V comes from. Each edge relaxation adds at most one entry, so the queue sees at most E adds and E polls, each O(log E). A simple graph has at most V² edges, so log E ≤ log V² = 2 log V (L48's log rules). O(E log E) is therefore O(E log V).

Measuring E log V Optional deep dive

Doubling the graph (L16's method) should a little more than double the time: 2 × log(2V) / log V is about 2.1 here. This version uses plain arrays for speed, and packs each queue entry (dist, vertex) into one Long, distance in the high 32 bits (L48's shifts and masks). Comparing two such longs compares the distances first.

The timing program

Kotlin on the left, Java on the right, best of 3 after a warm-up. The ratios come out at 2.4–3.0, higher than 2.1. It's the same story as L21's trees. Negative edges break it

The safety argument used "no weight is negative". Remove that and the greedy choice is no longer safe:

Dijkstra settles B at 2 because it's the closest, before it ever looks at C. Then C's edge to B, with weight −4, would give 5 − 4 = 1, but B is already final. Sedgewick & Wayne explain that if Dijkstra is written "so that a vertex cannot be enqueued more than once (e.g., using a marked[] array to mark those vertices that have been relaxed), then the algorithm is guaranteed to run in E log V time but it may yield incorrect results when there are edges with negative weights" (§4.4, Q&A). That's our settled set.

Bellman–Ford gives the right answer. It relaxes every edge, in any order, V−1 times, because a shortest path has at most V−1 edges. It isn't clever, but it doesn't depend on a greedy choice. It "solves the single-source shortest-paths problem from a given source s (or finds a negative cycle reachable from s) for any edge-weighted digraph with V vertices and E edges, in time proportional to E V" (§4.4). That's far slower than E log V, so you'd never use it on a road network. It's perfect as a test oracle, though: a slow, obviously correct answer to check the fast one against. The final uses it exactly that way.

Faster in practice: A*. Dijkstra spreads out in every direction. When you only want one target and can estimate how far away it is, such as straight-line distance on a map, A* adds that estimate to each queue priority, so the search leans toward the goal. Red Blob Games' interactive introduction puts the condition simply: "A* is guaranteed to find the shortest path if the heuristic is never larger than the true distance" (Introduction to A*).

Bridge: the internet runs Dijkstra. OSPF, the routing protocol inside most large networks, has every router build "the shortest-path tree using itself as the root", and "using the Dijkstra algorithm, a tree is formed from this subset of the link state database" (RFC 2328 §16.1). The packets your Android app or Spring service sends are steered by trees like the one in the widget.

  • compareBy<Entry>({ it.dist }, { it.town }) builds a two-key comparator from lambdas. Java chains Comparator.comparingInt(Entry::dist).thenComparing(Entry::town). Same comparator, different spelling.
  • dist[w] ?: Int.MAX_VALUE treats "no entry yet" as ∞. Java's getOrDefault(w, Integer.MAX_VALUE) does the same.

Part 3

Union-find and Kruskal

~30 min

A different question about the same towns: which roads should be paved so that every town is connected, for the fewest total minutes of paving? That's a minimum spanning tree (MST): "a spanning tree whose weight (the sum of the weights of its edges) is no larger than the weight of any other spanning tree" (algs4 §4.3 Minimum Spanning Trees). Cable networks, power grids and clustering all reduce to it.

Kruskal's algorithm is greedy: it "processes the edges in order of their weight values (smallest to largest), taking for the MST (coloring black) each edge that does not form a cycle with edges previously added, stopping after adding V-1 edges" (§4.3). The sort is easy. The hard part is asking "would this edge close a cycle?" fast, thousands of times, while the forest keeps growing. An edge closes a cycle exactly when its two ends are already connected. So the question becomes "are p and q connected?", with the answer changing as edges are added. That's the union-find problem.

Three union-finds

Sedgewick & Wayne's API has two operations: union(p, q) merges the components of p and q, and find(p) names p's component, so connected(p, q) is find(p) == find(q) (algs4 §1.5 Case Study: Union-Find). Every version below stores one int per site.

  • Quick-find "maintains the invariant that p and q are connected if and only if id[p] is equal to id[q]". find is one array read. union must relabel a whole component, so it scans the array: O(n).
  • Quick-union stores a forest instead: each site points to a parent, "following links until reaching a root, a site that has a link to itself". union just links one root under the other. But nothing stops the trees from growing tall.
  • Weighted quick-union "keep[s] track of the size of each tree and always connect[s] the smaller tree to the larger". Add path compression, where every node a find walks past is pointed straight at the root, and the trees stay almost flat.

Kotlin on the left, Java on the right. The heights are deterministic and identical. Timings are best of 3 after a warm-up, and a dash means "skipped, too slow".

  • Chain unions (0-1, 1-2, 2-3, …) turn plain quick-union into a linked list of height 65,535. Every find(0) walks all of it. Weighted quick-union always hangs the single new site under the big tree, so the height stays 1.
  • Equal merges are weighted quick-union's worst case: pairs, then pairs of pairs, and so on. The tree reaches height 16, which is exactly lg 65,536. The book's guarantee: "The depth of any node in a forest built by weighted quick-union for n sites is at most lg n" (§1.5). Why, using L48: a node only gets deeper when its tree is hung under a tree at least as big, so the size of its tree at least doubles each time. A size can double at most lg n times before it passes n.
  • Path compression then flattens everything to height 1 after one find per site. With both tricks, the cost per operation "is known to be bounded by a function known as the inverse Ackermann function and is less than 5 for any conceivable value of n that arises in practice" (§1.5, exercises).
  • The doubling table shows the difference. Quick-find's ratio is about 4: n unions at O(n) each is O(n²), so doubling n quadruples the time (L16). Plain quick-union is also quadratic on random input, and worse: 4–7× per doubling, because its trees grow tall. Weighted with compression doubles cleanly. At 80,000 sites it's about 3 ms against 2.4 seconds.

Kruskal, on the union-find

Both languages print exactly this. A-B and E-G both weigh 4; the stable sort keeps them in input order. Kruskal's cost is the sort, so it "computes the MST of any connected edge-weighted graph with E edges and V vertices using extra space proportional to E and time proportional to E log E (in the worst case)" (§4.3). The union-find part is nearly free. Step through it, watching the PARENT array and the sets merge:

Two different trees. Compare the MST with Part 2's shortest-path tree from A. The MST paves F-G (3) and leaves E-G (4) out, for 15 minutes in total. Dijkstra's tree uses E-G, because from A that's the faster way to G: 14 minutes against 15. The shortest-path tree's edges add up to 16. The MST minimises the total cost of connecting everyone. The shortest-path tree minimises each town's distance from A. They're different questions, and they can have different answers.

Why it's correct. The book's foundation is the cut property. Split the vertices into two groups, any way you like: "Given any cut in an edge-weighted graph (with all edge weights distinct), the crossing edge of minimum weight is in the MST of the graph" (§4.3). Its proof is an exchange argument, and you'll write it yourself in the final. Prim's algorithm uses the same property differently. It grows one tree from a start vertex, "always taking next (coloring black) the minimum-weight edge that connects a vertex on the tree to a vertex not yet on the tree", which makes it Dijkstra's close cousin. It uses a priority queue instead of a union-find.

What Kotlin does for you.
  • Kotlin classes are final unless marked open (L8). WeightedQU can only extend QuickUnion because it's declared open class, and parent must be protected to be visible there. Java classes are open by default, and its protected also opens the field to the whole package.
  • An interface method with a body, fun connected(...) = find(p) == find(q), needs no keyword in Kotlin. Java marks it default.
  • override is required in Kotlin, so a typo in find's signature is a compile error. Java's @Override is optional, but writing it gets you the same check.
  • IntArray(n) { it } fills 0, 1, 2, … in one expression. Java declares the array and then loops.
  • height() in Kotlin uses a local function, fun d(p: Int), declared inside another function. Java has no local functions, so the same logic sits inline in the loop.

Model answer: the proof

Let e = (u, v) be the edge Kruskal takes, with F already inside an MST T, and suppose T doesn't contain e.

  1. Adding e to T creates exactly one cycle, since a tree plus one edge has one cycle (§4.3: "Adding an edge that connects two vertices in a tree creates a unique cycle").
  2. e joins two different components of F, since otherwise Kruskal would have skipped it. So the cycle must cross from u's component to the rest through some other edge f, with f in T but not in F.
  3. f was still allowed when e was taken: its ends were in different components of F. If f had come before e in the sorted order, Kruskal would have taken it then, because components only merge over time, never split. So f comes after e, and weight(f) ≥ weight(e).
  4. Swap them: T − f + e is still a spanning tree, because removing f breaks the cycle again, and it weighs no more than T. So it's also an MST, and it contains F and e.
  5. By induction over Kruskal's steps (L48), the final forest is contained in an MST. It has V − 1 edges, so it is one.

Same shape as the scheduling proof: first difference, swap, no worse, induct.

  • The oracle test is the strongest one. It compares 250 answers against an algorithm with no greedy step at all, so it doesn't share Dijkstra's assumptions or its bugs.
  • Test names: Kotlin backtick names can't contain a dot on the JVM (the compiler says name contains illegal characters: .), so "1.51" became 1_51.
  • App.resource loads the files from the classpath, so ./gradlew run and the tests both find them in src/main/resources.
  • Route? vs Optional<Route>: Kotlin's nullable type is checked by the compiler. Java's Optional is a wrapper object, and orElseThrow() is the Java form of assertNotNull(...).

A stable sort is given several items with equal keys. Those items… (L18)

Stable means equal keys keep their relative order, as merge sort does (L18). Kruskal relied on it: A-B and E-G both weigh 4, and A-B was considered first in both languages because sortedBy and List.sort are both stable.

Kotlin's require(weights.none { it < 0 }) fails. What does it throw? (L10)

require checks arguments and throws IllegalArgumentException. check is the one that throws IllegalStateException, for a bad internal state. The final's negative-weight test expects the first.

Adding n elements to a dynamic array that doubles when full costs, in total… (L16, L48)

The copies add up to 1 + 2 + 4 + … + n < 2n, the geometric series from L48. So the total is O(n), and each add is amortised O(1).

Two different keys in a HashMap have the same hashCode. They… (L19)

That's a collision. Both entries live in the same bucket, and equals tells them apart on lookup. Overwriting happens only when equals says the keys are the same.
