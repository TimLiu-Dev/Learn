Production Android Flow & Concurrency

Writing callbackFlow + awaitClose, stateIn(WhileSubscribed(5_000)), cancelling stale work with flatMapLatest, and guarding shared async state with Mutex.withLock.

Warm-up: Rapid Recall

  1. Why must a coroutine catching broad Exception or using runCatching rethrow CancellationException?
    CheckStructured concurrency relies on CancellationException propagating upward cleanly; swallowing it keeps child jobs running after the scope or screen is destroyed.
  2. What is the difference between a cold Flow and a hot StateFlow?
    CheckCold Flow runs its producer block independently for each collector; hot StateFlow holds one current conflated .value shared across collectors.

The Concept: Four Essential Android Coroutine Patterns

1. Bridging Callback APIs Safely: callbackFlow + awaitClose

Calling emit() inside an external listener thread fails because emit is a suspending function. Use thread-safe trySend(...) inside callback lambdas.Android platform APIs (Location, ConnectivityManager, Firebase listeners, Biometrics) report results via register/unregister callbacks. Wrap them in a cold callbackFlow, emit updates with non-blocking trySend, and always unregister inside awaitClose { ... } so cancellation cleans up resources immediately:

import kotlinx.coroutines.* import kotlinx.coroutines.channels.awaitClose import kotlinx.coroutines.flow.* class FakeNetworkMonitor { var active = false private var cb: ((Boolean) -> Unit)? = null fun register(onChange: (Boolean) -> Unit) { active = true cb = onChange onChange(true) onChange(false) } fun unregister() { cb = null; active = false } } fun connectivityFlow(monitor: FakeNetworkMonitor): Flow<Boolean> = callbackFlow { monitor.register { isOnline -> trySend(isOnline) } awaitClose { monitor.unregister() } // Guaranteed cleanup when cancelled/completed! } fun main() = runBlocking { val monitor = FakeNetworkMonitor() val seen = connectivityFlow(monitor).take(2).toList() check(seen == listOf(true, false)) check(!monitor.active) { "Monitor leaked after collection ended!" } println("callbackFlow events=$seen, active=${monitor.active}") }

2. stateIn with SharingStarted.WhileSubscribed(5_000)

In an Android ViewModel, convert a cold repository stream to UI state via .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), initialValue):

  • Laziness trap: Unlike Eagerly, WhileSubscribed stays at initialValue until the first UI collector subscribes.
  • Why 5 seconds? When the user rotates the phone, the Activity unsubscribes and re-subscribes within milliseconds; the 5,000 ms grace window keeps the upstream database/network stream alive across rotation without restarting, then stops cleanly when the user leaves the app.

3. flatMapLatest / collectLatest vs Stale Races & Mutex.withLock

  • flatMapLatest (requires @OptIn(ExperimentalCoroutinesApi::class)): When a new search query arrives, the upstream previous flow is immediately cancelled—eliminating out-of-order network response bugs!
  • Mutex.withLock: JVM synchronized blocks a carrier thread and forbids calling suspend functions inside the lock. Use kotlinx.coroutines.sync.Mutex with mutex.withLock { ... } for async critical sections—remembering that Mutex is non-reentrant (never call a helper that tries to lock the same Mutex while already inside withLock).
import kotlinx.coroutines.* import kotlinx.coroutines.flow.* import kotlinx.coroutines.sync.Mutex import kotlinx.coroutines.sync.withLock @OptIn(ExperimentalCoroutinesApi::class) fun main() = runBlocking { val mutex = Mutex() var sharedCounter = 0 coroutineScope { repeat(50) { launch(Dispatchers.Default) { mutex.withLock { val cur = sharedCounter delay(1) // Allowed inside Mutex.withLock (impossible in synchronized!) sharedCounter = cur + 1 } } } } check(sharedCounter == 50) val latest = flowOf("ko", "kot", "kotlin") .flatMapLatest { q -> flowOf("Result($q)") } .toList() println("counter=$sharedCounter, flatMapLatest=$latest") }

Quick Check

1. What happens in Android if you define a callbackFlow that registers a callback listener and finishes the builder lambda without calling awaitClose { ... }?

awaitClose { ... } both suspends the callbackFlow coroutine so it stays open for incoming trySend events and runs deterministic cleanup on close or cancellation.

2. Why is SharingStarted.WhileSubscribed(5_000) the standard choice for Android ViewModel stateIn flows?

This gives you both zero wasted background work when users switch apps and zero redundant API reloads when rotating the screen.

3. Why should a repository caching an async auth token prefer Mutex.withLock over Java's synchronized block?

synchronized fails compilation around suspending calls and blocks threads while waiting; Mutex.withLock suspends cleanly.

Exercise 1 · Write from blank

Lifecycle-Safe Sensor Stream & Mutex Token Cache

Build two production Android building blocks tested deterministically in main:

  1. fun sensorStream(sensor: FakeSensor): Flow<Int> using callbackFlow that calls sensor.start { trySend(it) } and cleans up inside awaitClose { sensor.stop() }.
  2. class TokenCache(private val fetchToken: suspend () -> String) with a private Mutex() and nullable cachedToken: String? = null. Implement suspend fun getToken(): String using mutex.withLock (double-checked inside the lock so concurrent callers invoke fetchToken() only once!).
import kotlinx.coroutines.* import kotlinx.coroutines.channels.awaitClose import kotlinx.coroutines.flow.* import kotlinx.coroutines.sync.Mutex import kotlinx.coroutines.sync.withLock class FakeSensor { var running = false fun start(onValue: (Int) -> Unit) { running = true onValue(101) onValue(102) onValue(103) } fun stop() { running = false } } // Write sensorStream(sensor: FakeSensor) and TokenCache(fetchToken) here: fun main() = runBlocking { val sensor = FakeSensor() val readings = sensorStream(sensor).take(2).toList() check(readings == listOf(101, 102)) check(!sensor.running) { "awaitClose must call sensor.stop()!" } var networkCalls = 0 val cache = TokenCache { delay(20) networkCalls++ "tok_$networkCalls" } val tokens = coroutineScope { List(5) { async { cache.getToken() } }.awaitAll() } check(networkCalls == 1 && tokens.all { it == "tok_1" }) println("sensorStream=$readings stopped=${!sensor.running} networkCalls=$networkCalls") }
Hint 1: callbackFlow cleanupWrite callbackFlow { sensor.start { trySend(it) }; awaitClose { sensor.stop() } } so cancelling collection after take(2) triggers sensor.stop().
Hint 2: Mutex single-flight cacheInside getToken(), wrap both the null check and fetchToken() in mutex.withLock { cachedToken ?: fetchToken().also { cachedToken = it } }.
Exercise 2 · Refactor

Cancel Stale Searches with flatMapLatest & Fix WhileSubscribed State

Refactor this racy search coordinator so typing a new query cancels stale slow requests using flatMapLatest, and expose UI results via stateIn(..., SharingStarted.WhileSubscribed(5_000), "Idle").

@file:OptIn(kotlinx.coroutines.ExperimentalCoroutinesApi::class) import kotlinx.coroutines.* import kotlinx.coroutines.flow.* // Slow search query: earlier slow query "a" must be cancelled when "android" arrives! suspend fun runSearchQuery( q: String, onStarted: (String) -> Unit, onFinished: (String) -> Unit ): String { onStarted(q) if (q == "a") delay(150) else delay(10) val result = "Hits:$q" onFinished(result) return result } // REFACTOR: Use flatMapLatest so stale slow queries are cancelled instead of completing late! fun buildResultsFlow( queries: Flow<String>, onStarted: (String) -> Unit, onFinished: (String) -> Unit ): Flow<String> = flow { queries.collect { q -> emit(runSearchQuery(q, onStarted, onFinished)) } } fun main() = runBlocking { val completed = mutableListOf<String>() val aStarted = CompletableDeferred<Unit>() val queryTrigger = MutableSharedFlow<String>(extraBufferCapacity = 4) val scope = CoroutineScope(coroutineContext + SupervisorJob()) val uiState: StateFlow<String> = buildResultsFlow( queries = queryTrigger, onStarted = { if (it == "a") aStarted.complete(Unit) }, onFinished = { completed.add(it) } ).stateIn(scope, SharingStarted.WhileSubscribed(5_000), "Idle") // Verify WhileSubscribed starts lazily from initialValue "Idle" check(uiState.value == "Idle") val collected = mutableListOf<String>() val collector = launch { uiState.take(2).toList(collected) // Collects "Idle" then latest hit } queryTrigger.subscriptionCount.first { it > 0 } // Wait until WhileSubscribed upstream subscribes queryTrigger.emit("a") aStarted.await() // Deterministic hook proving slow query "a" is in-flight before cancellation queryTrigger.emit("android") // Must cancel slow "a"! collector.join() check(collected.last() == "Hits:android") { "Expected latest 'Hits:android' but got $collected (completed=$completed)" } check("Hits:a" !in completed) { "Stale query 'a' was NOT cancelled: $completed" } scope.cancel() println("Collected=$collected completed=$completed") }
HintMake buildResultsFlow a single-expression chain: queries.flatMapLatest { q -> flow { emit(runSearchQuery(q, onStarted, onFinished)) } }.
