Multi-Module Architecture, explicitApi() & Pure-Kotlin DI

Designing senior module boundaries with internal visibility, Kotlin's explicitApi() compiler mode, api vs implementation dependencies, and constructor/factory Dependency Injection.

Warm-up: Spaced Retrieval

  1. In Kotlin, what is the default visibility modifier if you omit one, and how does internal differ from Java's package-private?
    CheckKotlin defaults to public. internal makes a declaration visible anywhere inside the same compilation module (e.g. a Gradle subproject), but invisible to other Gradle modules—even if they share the same package name.
  2. What is the difference between implementation(libs.okhttp) and api(libs.okhttp) in a library module's build.gradle.kts?
    Checkimplementation hides the dependency's types from downstream modules' compile classpaths (faster incremental builds); api transitively exposes the dependency's types to consumers and is required only when those types appear in your module's public signatures.
  3. By default, is Kotlin's by lazy { ... } thread-safe when multiple threads access a singleton property simultaneously?
    CheckYes: by lazy defaults to LazyThreadSafetyMode.SYNCHRONIZED, using double-checked locking so the initializer runs exactly once.

The Concept: Senior Module Boundaries & Dependency Graphs

1. Enforcing Module Boundaries with internal & explicitApi()

Docs: Explicit API mode. Enable via kotlin { explicitApi() } in build.gradle.kts.In a single-module junior project, every class is public by default, so feature screens frequently reach directly into database entities or network DTOs. In a senior multi-module codebase (:app, :feature:feed, :core:domain, :core:data), you enforce strict architectural boundaries at compile time:

  • Public Interfaces, internal Implementations: Expose only the contract (public interface FeedRepository) and mark the implementation internal class DefaultFeedRepository : FeedRepository. Feature modules cannot instantiate or cast to DefaultFeedRepository.
  • Kotlin's explicitApi() Compiler Mode: When enabled in shared :core or KMP modules, the compiler rejects any declaration that relies on implicit defaults:
    1. Every public class, function, and property must declare an explicit visibility modifier (public, internal, protected, or private)—preventing accidental public leaks.
    2. Every public function and property must declare an explicit return type—preventing silent binary/source incompatibility when a single-expression body changes!
// Explicit API style: every public symbol carries 'public' AND an explicit return type! public data class UserProfile(public val id: String, public val tier: String) public interface ProfileRepository { public fun fetchProfile(id: String): UserProfile } // Hidden inside the compilation module: consumers can never couple to this class internal class NetworkProfileRepository(private val endpoint: String) : ProfileRepository { override fun fetchProfile(id: String): UserProfile = UserProfile(id = id, tier = "PRO@$endpoint") } public fun createProfileRepository(endpoint: String): ProfileRepository = NetworkProfileRepository(endpoint) fun main() { val repo: ProfileRepository = createProfileRepository("api.v2") println(repo.fetchProfile("u-99")) }

2. Pure-Kotlin Dependency Injection & Assisted Factories

Whether a 2027 project uses compile-time DI (Hilt, Dagger, or Kotlin Metro) or KMP-friendly pure-Kotlin DI, the underlying pattern is identical. Senior engineers never hide dependencies inside global object service locators—doing so makes unit tests share mutated global state. Instead, structure dependencies into a Composition Root Graph:

  • App-Scoped Singletons: Declared as val repo: Repo by lazy { ... } inside the graph so they initialize once on demand.
  • Parameterized / Screen-Scoped Dependencies (Assisted Injection): Use a fun interface factory (e.g. fun interface DetailViewModelFactory { fun create(itemId: String): DetailViewModel }) that combines graph singletons with runtime navigation arguments!
public interface AnalyticsTracker { public fun track(event: String) } internal class MemoryAnalyticsTracker : AnalyticsTracker { val events = mutableListOf<String>() override fun track(event: String) { events.add(event) } } public class CheckoutController( private val tracker: AnalyticsTracker, private val cartId: String ) { public fun submitOrder(): String { tracker.track("checkout:$cartId") return "Submitted $cartId" } } public fun interface CheckoutControllerFactory { public fun create(cartId: String): CheckoutController } // Pure-Kotlin Scoped DI Container (Composition Root) public class AppGraph { public val tracker: AnalyticsTracker by lazy { MemoryAnalyticsTracker() } public val checkoutFactory: CheckoutControllerFactory = CheckoutControllerFactory { cartId -> CheckoutController(tracker = tracker, cartId = cartId) } } fun main() { val graph = AppGraph() val c1 = graph.checkoutFactory.create("cart-101") val c2 = graph.checkoutFactory.create("cart-202") println(c1.submitOrder()) println(c2.submitOrder()) check((graph.tracker as MemoryAnalyticsTracker).events == listOf("checkout:cart-101", "checkout:cart-202")) println("Tracked events in shared singleton: ${(graph.tracker as MemoryAnalyticsTracker).events}") }

Quick Check

1. What two requirements does enabling kotlin { explicitApi() } in build.gradle.kts enforce on public API declarations?

explicitApi() prevents two classic library bugs: accidentally exposing an implementation class as public, and accidentally changing a public function's inferred return type.

2. In a multi-module project where :feature:profile depends on :core:data, when should :core:data declare a dependency using api(...) instead of implementation(...)?

Default to implementation(...) so implementation changes don't force downstream modules to recompile; use api(...) only when a dependency's types are part of your module's public contract.

3. Why is calling a global object NetworkClient singleton directly inside a ViewModel considered a senior architectural anti-pattern compared to constructor injection?

Global `object` state is fine for stateless pure constants or `data object` sealed states, but stateful I/O services should always be injected via an interface constructor parameter.

4. How does an Assisted Factory (fun interface DetailPresenterFactory { fun create(id: String): DetailPresenter }) solve mixing DI singletons with runtime screen arguments?

Assisted factories cleanly separate graph-managed dependencies (repositories, dispatchers) from caller-supplied runtime parameters (`itemId`, `cartId`).
