Section 10 · Coroutines & Flow · Lesson 10.5

Hot streams: StateFlow & SharedFlow

Broadcast state pipelines: atomic .update { } mutations, backing properties, conflation, and event broadcasts.

Warm-up: Rapid Recall

  1. What is the difference between a cold flow and a hot flow?
    CheckA cold flow runs its producer block on-demand per collector; a hot flow stays active in memory and broadcasts emissions independently of individual collectors.
  2. Why does StateFlow always require an initial value?
    CheckBecause it models current state: any new collector (and any reader of .value) must immediately receive a valid snapshot.

The Concept: StateFlow vs SharedFlow

1. StateFlow: Observable State with Conflation

  • Always holds a current snapshot accessible via .value.
  • Conflates rapid emissions and skips consecutive duplicates (compared with ==): slow collectors always receive the latest state without backpressure buildup.

2. Backing Properties & Atomic .update { }

Keep mutation private with MutableStateFlow and expose read-only StateFlow via .asStateFlow(). Crucially, when computing the next state from the current state, never write _state.value = _state.value.copy(...)—two concurrent coroutines can read the same stale snapshot and overwrite each other's changes! Always use _state.update { ... }, which runs an atomic compare-and-set (CAS) retry loop:

Racy Read-Modify-Write

// ❌ Lost updates under concurrency! _state.value = _state.value.copy( count = _state.value.count + 1 )

Atomic CAS Loop (.update)

// ✅ Thread-safe compare-and-set! _state.update { current -> current.copy(count = current.count + 1) }

3. SharedFlow: Multi-Subscriber Event Broadcasts

  • Does NOT hold a single permanent .value; configurable replay (default 0) and extraBufferCapacity.
  • Use when multiple subscribers must react to broadcast events (e.g. session invalidation, cache-busting triggers, live telemetry buses).

Quick Check

1. Why should a senior developer prefer _state.update { it.copy(items = it.items + item) } over _state.value = _state.value.copy(...)?

MutableStateFlow.update uses an internal compare-and-set spin loop. If another thread updates the state while your lambda is computing the copy, update safely re-runs your function on the fresh state instead of silently clobbering the concurrent write.

2. You emit "A", then "A" again into a MutableStateFlow("Init"). How many times does an active collector receive "A"?

StateFlow has equality-based conflation built in: assigning a new value that is structurally equal (==) to the current value is a no-op.

Practice: Hands-On Exercises

Exercise 1 · Write from blank

Atomic Download Queue Coordinator

Implement DownloadCoordinator to track concurrent file downloads safely:

  1. data class QueueState(val activeIds: Set<String> = emptySet(), val completedCount: Int = 0).
  2. Private _state = MutableStateFlow(QueueState()) exposed publicly as val state: StateFlow<QueueState> = _state.asStateFlow().
  3. Private _events = MutableSharedFlow<String>(extraBufferCapacity = 4) exposed publicly as val events: SharedFlow<String> = _events.asSharedFlow().
  4. fun startDownload(id: String): atomically adds id to activeIds using _state.update { ... }.
  5. fun completeDownload(id: String): if id in _state.value.activeIds, atomically removes id and increments completedCount via _state.update { ... }, then broadcasts "Done: $id" via _events.tryEmit(...).
import kotlinx.coroutines.* import kotlinx.coroutines.flow.* data class QueueState( val activeIds: Set<String> = emptySet(), val completedCount: Int = 0 ) class DownloadCoordinator { // 1. Declare private MutableStateFlow / MutableSharedFlow and public read-only views // 2. Implement startDownload(id: String) and completeDownload(id: String) using .update { } } fun main() = runBlocking { val coord = DownloadCoordinator() val alerts = mutableListOf<String>() val job = launch(start = CoroutineStart.UNDISPATCHED) { coord.events.collect { alerts.add(it) } } coord.startDownload("video.mp4") coord.startDownload("slides.pdf") check(coord.state.value == QueueState(setOf("video.mp4", "slides.pdf"), 0)) coord.completeDownload("video.mp4") yield() check(coord.state.value == QueueState(setOf("slides.pdf"), 1)) check(alerts == listOf("Done: video.mp4")) job.cancel() println("All checks passed! Final state: ${coord.state.value}") }
HintKotlin sets support clean immutable operators: current.copy(activeIds = current.activeIds + id) and current.copy(activeIds = current.activeIds - id, completedCount = current.completedCount + 1).
Exercise 2 · Refactor

Fix Leaked Mutable State & Non-Atomic Updates

AuthSession below leaks its MutableStateFlow publicly AND mutates .value with a racy read-modify-write. Encapsulate it behind session: StateFlow<Session> and refactor addPermission to use .update { }.

import kotlinx.coroutines.flow.* data class Session(val username: String = "Guest", val permissions: Set<String> = emptySet()) // REFACTOR THIS: Fix public MutableStateFlow leak and non-atomic .value update class AuthSession { val session = MutableStateFlow(Session()) fun login(user: String) { session.value = Session(username = user) } fun addPermission(perm: String) { session.value = session.value.copy(permissions = session.value.permissions + perm) } } fun main() { val auth = AuthSession() auth.login("Alice") auth.addPermission("ADMIN") check(auth.session.value == Session("Alice", setOf("ADMIN"))) println("Verified session: ${auth.session.value}") }
