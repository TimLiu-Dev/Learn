Warm-up: Rapid Recall

  1. Why does JPA Hibernate require a no-arg constructor on entity classes, and how does Kotlin supply it cleanly?
    CheckHibernate instantiates entities via reflection before hydrating fields; the kotlin-jpa (no-arg) compiler plugin synthesizes a bytecode-only zero-arg constructor so your Kotlin code stays clean.
  2. Why must you avoid data class on JPA @Entity classes with lazy relationships?
    CheckGenerated equals, hashCode, and toString touch every property—triggering N+1 lazy loads, circular StackOverflowErrors, and broken HashSet buckets when Hibernate assigns generated IDs.

The Concept: Production Kotlin on the Backend

Spring Boot and Kotlin shine together once you understand how Kotlin properties map to JVM bytecode:

// 1. DTO: data class + @field: validation targets + init invariants data class CreateUserDto( @field:NotBlank val email: String, @field:Min(18) val age: Int = 18 ) // 2. Spring Data Kotlin extension (no Java Optional!) + Elvis 404: fun getUserOrThrow(id: Long): UserResponse = userRepository.findByIdOrNull(id)?.toResponse() ?: throw ResponseStatusException(HttpStatus.NOT_FOUND, "User $id not found")
  • Annotation use-site targets: A constructor property val email: String compiles into a constructor parameter, a private backing field, and a getter. Prefix Jakarta Bean Validation annotations with @field: (e.g. @field:NotBlank) so Hibernate Validator inspects the field rather than ignoring a constructor parameter annotation.
  • Compiler plugins: Always enable kotlin-spring (all-open, allowing Spring CGLIB proxies to subclass @Service / @Transactional classes) and kotlin-jpa (no-arg).

Quick Check

1. What happens in Spring Boot if you omit the kotlin-spring (all-open) compiler plugin and annotate a regular Kotlin class OrderService with @Transactional?

Kotlin classes and methods are final by default. Spring AOP's CGLIB proxy mechanism subclasses beans at runtime to wrap @Transactional logic, throwing a startup error unless kotlin-spring opens them.

2. Why do Jakarta Bean Validation annotations on Kotlin DTO constructor properties usually require @field:NotBlank instead of bare @NotBlank?

When an annotation allows multiple targets (parameter, field, method), Kotlin prioritizes @param: on primary constructor properties. Prefixing @field: guarantees field-level Bean Validation runs.

3. Why does using a generated var id: Long? = null inside a data class JPA entity corrupt a HashSet<Customer>?

A data class computes hashCode() from its primary constructor properties. Mutating id after inserting into a HashSet changes its hash bucket, making the element unfindable in the set.

Practice: Hands-On Exercises

Exercise 1 · Write from blank

Spring DTOs, Preconditions & Service Mapping from Blank

Write the complete backend order creation slice from a blank file:

  1. data class CreateOrderRequest(val customerId: String, val amountCents: Long, val notes: String? = null) with an init block validating customerId.isNotBlank() and amountCents > 0 via require.
  2. data class OrderResponse(val id: String, val customerId: String, val amountCents: Long, val notes: String, val status: String).
  3. Extension function fun CreateOrderRequest.toResponse(orderId: String): OrderResponse that trims customerId, defaults blank/null notes to "NONE", and sets status = "CONFIRMED".
  4. Function fun createOrder(req: CreateOrderRequest): OrderResponse returning req.toResponse("ord-123").
// 1. Declare CreateOrderRequest (with init require checks) and OrderResponse // 2. Declare CreateOrderRequest.toResponse(orderId: String) and createOrder(req) fun main() { val req = CreateOrderRequest(" cust_99 ", 4500) val res = createOrder(req) check(res == OrderResponse("ord-123", "cust_99", 4500, "NONE", "CONFIRMED")) val invalidFailed = runCatching { CreateOrderRequest("", 100) }.isFailure val negativeFailed = runCatching { CreateOrderRequest("cust_1", -5) }.isFailure check(invalidFailed && negativeFailed) println("All Spring DTO & service checks passed: $res") }
HintTo turn both null and " " into "NONE", combine safe calls + trim() + takeIf + Elvis: notes?.trim()?.takeIf { it.isNotEmpty() } ?: "NONE".
Exercise 2 · Refactor

Java-Style Spring Service Refactor

Refactor this Java-style Spring service method—with verbose null/blank checks and imperative mutation—into concise idiomatic Kotlin using require and apply.

class UserEntity(var id: Long? = null, var email: String = "", var active: Boolean = true) // REFACTOR THIS SERVICE METHOD: fun updateEmail(entity: UserEntity, newEmail: String?): UserEntity { if (newEmail == null || newEmail.trim().isEmpty()) { throw IllegalArgumentException("Email cannot be blank") } entity.email = newEmail.trim().lowercase() return entity } fun main() { val user = UserEntity(1, "old@example.com") val updated = updateEmail(user, " New@Example.COM ") check(updated.email == "new@example.com") check(runCatching { updateEmail(user, " ") }.isFailure) println("Updated email: ${updated.email}") }
Hint!newEmail.isNullOrBlank() has a Kotlin compiler contract: once require(!newEmail.isNullOrBlank()) passes, newEmail is automatically smart-cast from String? to String!
