Idiomatic unit testing & fakes

Writing expressive tests with kotlin.test, backtick method names, failure assertions, and why senior teams favor Fakes over MockK.

Warm-up: Rapid Recall

  1. Why does mocking libraries like MockK or Mockito fail on Kotlin Multiplatform iOS/Native targets?
    CheckJVM mocking libraries rely on bytecode generation (CGLIB, ByteBuddy, or Java reflection proxies) which do not exist on Kotlin/Native iOS binaries. commonTest code must be testable with pure Kotlin Fakes.
  2. How does Kotlin allow spaces and readable punctuation in test method names?
    CheckBy enclosing function names in backticks: fun `returns 404 when user is not found`().

The Concept: Senior Testing Philosophy in Kotlin

1. Expressive Test Naming & kotlin.test Assertions

Kotlin test names can be written as natural English sentences using backticks. Use kotlin.test assertions which work across all platforms (JVM, Android, iOS, Wasm):

// Interactive Example: Test harness with idiomatic assertions class Cart(val items: MutableList<String> = mutableListOf()) { fun addItem(item: String) { require(item.isNotBlank()) { "Item name cannot be blank" } items.add(item) } } fun main() { val cart = Cart() cart.addItem("Espresso") // Assert state check(cart.items.size == 1) { "Expected 1 item, got ${cart.items.size}" } // Assert expected exception var failed = false try { cart.addItem(" ") } catch (e: IllegalArgumentException) { failed = true } check(failed) { "Expected IllegalArgumentException for blank item" } println("✅ All cart assertions passed cleanly!") }

2. Fakes vs Mocks: The Architectural Shift

In Java, developers heavily mocked interfaces using Mockito. In modern Kotlin, senior engineers strongly prefer Fakes (in-memory test doubles):

  • Mocks are brittle: They couple tests to internal implementation details (verify { repo.getUsers(any()) }), breaking whenever you refactor private helper methods.
  • Mocks struggle with Kotlin idioms: Mocking final classes, extension functions, inline functions, and coroutine scopes requires complex byte-buddy sub-plugins.
  • Fakes are reusable contracts: An InMemoryUserRepository : UserRepository behaves like the real database, runs at lightning speed, works 100% in KMP commonTest, and lets you test real behavior instead of verifying method calls.

Quick Check

1. Why do senior Kotlin teams recommend writing in-memory Fakes instead of using MockK for repository layers?

Fakes provide fast, deterministic, state-verifying doubles that survive internal refactorings and compile natively in multiplatform modules.

2. What is the idiomatic way to assert that a block of code throws a specific exception in kotlin.test?

assertFailsWith<T> { ... } from kotlin.test ensures the expected exception is thrown and returns the exception instance for message validation.

Exercise 1 · Write from blank

Testable In-Memory User Service with Fake

Implement a user registration test slice with a contract interface, an in-memory Fake, and self-verifying test cases:

  1. data class User(val id: String, val email: String, val active: Boolean = true).
  2. interface UserDao with fun insert(user: User), fun findById(id: String): User?, and fun findByEmail(email: String): User?.
  3. class FakeUserDao : UserDao using an internal mutableMapOf<String, User>().
  4. class UserService(private val dao: UserDao) with fun register(id: String, email: String): User that requires email.contains("@"), requires dao.findByEmail(email) == null (throws IllegalStateException("Email already taken")), and inserts the new user.
// 1. Declare User and UserDao interface // 2. Declare FakeUserDao : UserDao // 3. Declare UserService(private val dao: UserDao) fun main() { val fakeDao = FakeUserDao() val service = UserService(fakeDao) // Test 1: Successful registration val u1 = service.register("u1", "alice@example.com") check(u1.email == "alice@example.com") check(fakeDao.findById("u1") == u1) // Test 2: Duplicate email rejected val dupFailed = runCatching { service.register("u2", "alice@example.com") }.isFailure check(dupFailed) { "Should reject duplicate email" } // Test 3: Invalid email format rejected val invalidFailed = runCatching { service.register("u3", "invalid-email") }.isFailure check(invalidFailed) { "Should reject invalid email format" } println("✅ All UserService fake tests passed successfully!") }
Hint 1In FakeUserDao, maintain a private val users = mutableMapOf<String, User>(). findByEmail can use users.values.find { it.email == email }.
Hint 2In UserService.register, use require("@" in email) { "Invalid email" } and check(dao.findByEmail(email) == null) { "Email already taken" }.
Exercise 2 · Refactor

Replace Brittle Verification Mocks with Deterministic State Assertions

Refactor this test suite—which tightly couples assertions to mock execution order—into an idiomatic state-verifying test using a lightweight Fake discount calculator.

interface DiscountRule { fun calculateDiscount(amountCents: Long): Long } class FixedDiscountRule(private val discountCents: Long) : DiscountRule { override fun calculateDiscount(amountCents: Long): Long = minOf(amountCents, discountCents) } class CheckoutService(private val discountRule: DiscountRule) { fun calculateTotal(subtotalCents: Long): Long { require(subtotalCents >= 0) { "Subtotal cannot be negative" } val discount = discountRule.calculateDiscount(subtotalCents) return subtotalCents - discount } } // BRITTLE SPY TO REMOVE: class SpyDiscountRule(private val discountCents: Long) : DiscountRule { var invocations = 0 override fun calculateDiscount(amountCents: Long): Long { invocations++ return minOf(amountCents, discountCents) } } fun main() { // REFACTOR THIS: Replace SpyDiscountRule + interaction verification with FixedDiscountRule(500) // and assert real state/output behavior for: // 1) subtotal = 2000 -> total == 1500L // 2) subtotal = 300 (smaller than discount, capped at 0) -> total == 0L val spy = SpyDiscountRule(500) val checkout = CheckoutService(spy) val total = checkout.calculateTotal(2000) check(total == 1500L) { "Expected 1500, got $total" } check(spy.invocations == 1) { "Expected rule invocation once" } println("Ran brittle spy check: total=$total") }
HintA simple FixedDiscountRule(discountCents) implements DiscountRule in 3 lines and lets you test exact edge cases (e.g. subtotal < discount) with 100% determinism.
