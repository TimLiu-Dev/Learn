Section 6 · Review · Lesson 6.R

Mixed review: Scope functions

Interleaved mastery: choosing with surgical precision between let, apply, run, also, with, and takeIf.

Warm-up: Rapid Recall

  1. In val res = list.also { it.add(10) }, what is the type of res?
    CheckThe type of list (the context object itself).
  2. Why does view?.apply { visibility = GONE } not execute if view is null?
    CheckBecause the safe-call ?. short-circuits when the receiver is null.
  3. What happens when takeUnless { it.isEmpty() } is called on an empty string?
    CheckIt returns null because the predicate is true.

Quick Check

Which pair of scope functions return the context object itself (type T)?

Both apply and also return the context object (this in apply, it in also).

Practice: Hands-On Exercises

Exercise 1 · Write from blank

Transactional Order Processor

Build an order processing pipeline:

  1. Data class Order(val id: String, val amountCents: Int, var status: String = "PENDING")
  2. Function processOrder(order: Order?): Order?:
    • Filter out null or orders where amountCents <= 0 using takeIf.
    • Update status = "PROCESSED" using apply.
    • Log audit line "AUDIT: Order ${it.id} processed for ${it.amountCents}c" using also.
    • Return the processed order.
data class Order(val id: String, val amountCents: Int, var status: String = "PENDING") fun processOrder(order: Order?): Order? { // Chain takeIf, apply, and also return null } fun main() { val o1 = processOrder(Order("ord-1", 4500)) val o2 = processOrder(Order("ord-2", -500)) val o3 = processOrder(null) println("O1: $o1") println("O2: $o2") println("O3: $o3") }
Hint 1: Order validationValidate safely without throwing: order?.takeIf { it.amountCents > 0 } returns null when the order is missing or non-positive.
Hint 2: Configuration & loggingChain ?.apply { status = "PROCESSED" } to update status and ?.also { println("AUDIT: Order ${it.id} processed for ${it.amountCents}c") } to log before returning Order?.
Exercise 2 · Refactor

The Scope Overuse Special

The code below was generated by an LLM that tried to use every scope function at once. Refactor it into clean, simple, idiomatic Kotlin.

data class ServerConfig(var host: String = "", var port: Int = 0) // REFACTOR THIS OVER-SCOPED MESS: fun startServer(rawHost: String?, rawPort: Int?): ServerConfig { return ServerConfig().let { cfg -> rawHost?.let { h -> cfg.apply { this.host = h.trim().also { println("Host trimmed") } } } ?: run { cfg.host = "localhost" } rawPort?.let { p -> cfg.port = p } ?: run { cfg.port = 8080 } cfg.also { println("Server ready on ${it.host}:${it.port}") } } } fun main() { val c = startServer(" api.internal ", null) println("Final config: ${c.host}:${c.port}") }
Hint 1: Untangle gratuitous scope nestingReplace overuse of scope functions with plain local variables, default constructor parameters, or the Elvis operator.
Hint 2: Keep only purposeful scope callsUse also strictly for side effects like logging, leaving property assignments to standard constructor calls.
