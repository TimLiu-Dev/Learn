Null safety rests on promises in three places

Everything so far has been the compiler proving things: this value can't be null, this check still holds. This lesson covers the three places where the compiler takes your word for it instead. Each one exists for a real reason, and each one becomes a crash when the promise turns out to be false.

1. !!: “trust me, it isn't null”

Docs: Not-null assertion operator.x!! turns a T? into a T. If x really is null, it throws NullPointerException. The docs describe it as for cases where “you are confident that a value is not null … but the compiler cannot guarantee this.”

The problem is that it brings back exactly the crash null safety was designed to remove, and the crash carries no message. A stack trace pointing at !! doesn't tell you which assumption was wrong.

So when you're tempted to write !!, work down this list and stop at the first option that fits:

  1. Handle it: x?.foo(), or x ?: default. Ask yourself whether null is actually a normal case.
  2. Bail out: val y = x ?: return. Nothing to do without it? Then leave the function.
  3. Fail loudly, with a reason: if null really means a bug, crash with a message that explains which assumption broke.

API docs: requireNotNull, checkNotNull. See also precondition functions.For option 3, the standard library has functions that say what kind of bug it is:

fun main() { //sampleStart val sessionId: String? = null // 1. !!: NullPointerException, no message // val a = sessionId!! // 2. requireNotNull: a bad ARGUMENT was passed in → IllegalArgumentException // val b = requireNotNull(sessionId) { "sessionId must be passed in" } // 3. checkNotNull: the object is in a bad STATE → IllegalStateException // val c = checkNotNull(sessionId) { "Session not started yet" } // 4. Elvis + error(): same as 3, written inline val d = sessionId ?: error("Session not started yet") //sampleEnd }

Uncomment them one at a time and compare the error messages. Both …NotNull functions return the non-null value, and after the call the compiler also treats the original variable as non-null.

When is a bare !! acceptable? Rarely: in a quick test or prototype, or when an outside guarantee makes null genuinely impossible and a message would add nothing. In production code you review, treat every !! as a question that needs an answer.

2. lateinit: “it'll be set before anyone reads it”

Docs: Late-initialized properties and variables.Some properties can't be set in the constructor, but they're always set before use. On Android the classic case is a view binding created in onCreate. Others are dependencies injected by a framework and fields prepared in a test's setup method. Declaring these as Binding? would force ?. or !! on every single use, for a value that is never actually null when you use it.

lateinit lets you keep the honest, non-null type, and moves the check to the moment you read the property:

// Android (not runnable here): the standard view-binding pattern class WorkoutActivity : AppCompatActivity() { private lateinit var binding: ActivityWorkoutBinding override fun onCreate(savedInstanceState: Bundle?) { super.onCreate(savedInstanceState) binding = ActivityWorkoutBinding.inflate(layoutInflater) setContentView(binding.root) binding.title.text = "Tempo run" // no ?. or !! needed } }

If you break the promise, the crash at least names the culprit. You get an UninitializedPropertyAccessException that includes the property's name, not an anonymous NullPointerException:

class WorkoutTimer { lateinit var athlete: String fun start(name: String) { athlete = name } fun status(): String = if (this::athlete.isInitialized) "Timing $athlete" else "Not started" } fun main() { val timer = WorkoutTimer() println(timer.status()) timer.start("Ana") println(timer.status()) // println(WorkoutTimer().athlete) // uncomment: UninitializedPropertyAccessException }

The rules, all checked by the compiler:

  • var only. It gets assigned later, so it must be reassignable.
  • Non-null type only. lateinit var x: String? makes no sense: if it can be null, just start at null.
  • No primitive types (Int, Long, Double, Boolean, …). For those, use a nullable type or a sensible starting value.
  • Not in the primary constructor, and no custom getter or setter.

this::athlete.isInitialized lets you ask whether it has been set yet. If you find yourself asking that all over the place, the value is genuinely optional, and a nullable type was the honest choice.

For values you can compute on first use, instead of having them set from outside, there's by lazy, which works with val. That's lesson 8.1.

3. Platform types: “Java didn't say”

Docs: Java interop → Null-safety and platform types and notation.The Android SDK and many libraries are written in Java. In Java, any object can be null, and an unannotated method signature doesn't say whether it might return null. Kotlin has no way of knowing. Treating every Java value as nullable would bury your code in ?., and treating them all as non-null would be dishonest.

So Kotlin gives such values a platform type. The IDE and error messages show it as String!, which means “String or String?, you decide”. You can't write String! yourself. Null checks are relaxed for platform types, so if you guess wrong, you crash at runtime.

You can try this here. System.getProperty is an unannotated Java method from the JDK, and it returns null for an unknown key:

fun main() { //sampleStart val inferred = System.getProperty("workout.device") // platform type String! val safe: String? = System.getProperty("workout.device") // you chose nullable: always works println(inferred) println(safe ?: "unknown device") val trusting: String = System.getProperty("workout.device") // you chose non-null... println(trusting) // ...crashes at the line above //sampleEnd }

Notice that val trusting: String = … compiles fine. Kotlin inserts a check at the assignment, so the program fails right there with a NullPointerException, before the null can spread further. With the inferred platform type, by contrast, the failure only shows up later, wherever you first use the value as if it weren't null.

Nullability annotations remove the guesswork. When the Java code marks a method @Nullable or @NonNull (from JetBrains, JSpecify, Android's annotation packages and others), Kotlin sees a real String? or String, not a platform type. If you see ! in a tooltip, that API isn't annotated, and you're the one deciding.

The convention: decide at the boundary. “Any property … initialized with an expression of a platform type must declare its Kotlin type explicitly,” and so must public functions that return one. For local values it's optional.

From Kotlin coding conventions → Platform types

When in doubt, choose String? and handle the null. That keeps the compiler on your side for the rest of the code.

AI/Java-flavoured smells to spot
  • !! chains like user!!.profile!!.name!!, or !! straight after a null check
  • A nullable var plus !! on every use, when lateinit (or a local val) was meant
  • The opposite: lateinit on data that's genuinely optional, guarded by isInitialized everywhere
  • A property initialized from a Java/SDK call with no declared type, which silently keeps the T!

Quick check

1. sessionId is null. What does val id = checkNotNull(sessionId) { "No session" } do?

checkNotNull is for bad state (IllegalStateException). requireNotNull is for bad arguments (IllegalArgumentException). Only !! gives you the bare NPE.

2. Which declaration compiles?

lateinit needs a var, a non-null type, and a non-primitive type. Int fails the last rule, val the first, and String? the second.

3. A Java method String getDeviceName() has no annotations. What type does the IDE show for val name = sdk.getDeviceName()?

A platform type: “String or String?, you decide”. You can't write it yourself; you see it in tooltips and error messages.

4. You store that call's result in a class property. What do the conventions say?

Properties and public functions initialized from a platform type must declare the Kotlin type. Usually that means String?, unless you know it can't be null.
