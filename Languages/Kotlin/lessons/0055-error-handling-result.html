Error handling: Result, require & check

Preconditions, functional Result<T> vs typed domain errors, and why naive runCatching breaks coroutines.

Warm-up: Rapid Recall

  1. Does Kotlin have checked exceptions (throws clauses) in function signatures?
    CheckNo. All exceptions in Kotlin are unchecked. (@Throws is only an interop annotation for Java/Swift callers).
  2. What is the difference between require() and check()?
    Checkrequire validates caller arguments (throws IllegalArgumentException); check validates internal object state (throws IllegalStateException).

The Concept: Kotlin Error Architecture

1. Preconditions for Programming Bugs: require, check, error

Use stdlib precondition functions to fail fast when a caller violates an API contract or an object enters an impossible state:

fun setSpeed(kmh: Int) { require(kmh >= 0) { "Speed cannot be negative: $kmh" } // IllegalArgumentException check(engineIsRunning) { "Cannot set speed when engine is stopped" } // IllegalStateException }

2. Result<T> vs Sealed Domain Outcomes

  • Use Result<T> / runCatching at infrastructure boundaries where external parsing, I/O, or network calls throw exceptions you want to capture as values.
  • Use a sealed interface when modeling expected business outcomes (e.g. InsufficientFunds, AccountLocked) so callers get exhaustive compile-time when checks instead of inspecting untyped Throwables.
fun parsePort(raw: String): Result<Int> = runCatching { val port = raw.toInt() require(port in 1..65535) { "Port out of range: $port" } port } val activePort = parsePort("8080").getOrDefault(80)
Senior Production Warning · runCatching + Coroutines

runCatching catches Throwable—which includes CancellationException (and fatal JVM Errors)! If you wrap a suspend call inside runCatching { api.fetch() } and swallow the failure with .getOrNull() or .onFailure { log(it) }, your coroutine ignores cancellation and breaks structured concurrency. In suspending code, always rethrow cancellation:

inline fun <R> runSuspendCatching(block: () -> R): Result<R> = try { Result.success(block()) } catch (c: kotlin.coroutines.cancellation.CancellationException) { throw c // Never swallow coroutine cancellation! } catch (e: Exception) { Result.failure(e) }

Quick Check

1. Which precondition function is idiomatic when validating arguments passed into a public function?

require() throws IllegalArgumentException, signalling that the caller supplied an invalid parameter.

2. Why is runCatching { delay(500); fetchUser() }.getOrNull() dangerous inside a coroutine?

When delay(500) throws CancellationException to abort the cancelled coroutine, runCatching traps it inside Result.failure and .getOrNull() turns it into null, keeping the cancelled coroutine alive!
