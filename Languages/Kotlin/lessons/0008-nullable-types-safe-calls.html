Section 2 · Null safety · Lesson 2.1

Nullable types and ?.

“Might be missing” becomes part of the type, so the compiler catches null crashes before your users do.

The problem: a crash that waits until runtime

In many languages, any object reference can secretly be null. Call a method on it and the program crashes with a NullPointerException. On Android, that means the app closes on your user's phone. Nothing warned you while you were writing the code, because the type String didn't say whether a string was actually there.

Docs: Null safety → Nullable types and non-nullable types. The docs call null references “The Billion-Dollar Mistake”.Kotlin's fix is to put “might be missing” into the type itself:

  • String can never hold null. You can call anything on it, safely.
  • String? might hold null. The compiler won't let you use it as if it were definitely there.

These are two different types. Run this and read both errors: the crash has become a compile error.

fun main() { //sampleStart var nickname: String = "Kai" nickname = null // ❌ String can't hold null val bio: String? = null // ✅ String? can println(bio.length) // ❌ might be null, so .length isn't allowed directly //sampleEnd }

This moves the decision to the place where it belongs. Whoever declares the value says whether it can be absent, and whoever uses it is forced to deal with that.

Where nullable values come from

You'll mostly receive nullable values rather than create them: optional fields in an API response, a map lookup (settings["theme"] is String?, because the key might not exist), or conversions that can fail:

fun main() { //sampleStart val settings = mapOf("theme" to "dark") val units: String? = settings["units"] // key missing, so null val minutes: Int? = "45min".toIntOrNull() // not a number, so null println(units) println(minutes) //sampleEnd }

A guideline worth keeping: make something nullable only when “absent” is a real, meaningful state, like a user who hasn't set a nickname yet. Adding ? “just in case” pushes the null handling onto everyone who reads the value.

The safe call ?.

Docs: Null safety → Safe call operator.The commonest thing to do with a maybe-missing value is “use it if it's there, otherwise give up and stay null”. That is exactly what ?. means:

a?.b means: if a isn't null, evaluate a.b. If a is null, the whole expression is null, and nothing crashes.

So the result is always nullable. nickname?.length has type Int?, not Int, because “no nickname” has to come out somewhere.

Chains: one ?. per link that might be missing

Here's a user profile as it might arrive from an API. Not every user is in a workout, and not every workout has a coach:

class Coach(val name: String) class Workout(val title: String, val coach: Coach?) class Profile(val nickname: String?, val currentWorkout: Workout?) fun main() { //sampleStart val maya = Profile("Maya", Workout("Intervals", Coach("Ravi"))) val newUser = Profile(null, null) println(maya.currentWorkout?.coach?.name) // Ravi println(newUser.currentWorkout?.coach?.name) // null: stops at the first null println(newUser.nickname?.uppercase()) // works for function calls too //sampleEnd }

Read the chain left to right. The first link that turns out to be null stops it, and the whole chain evaluates to null. Notice that .title and .name would need no ?, because their types aren't nullable. You add ?. only after a value whose type ends in ?.

On the left of =

A safe call can also guard an assignment. If any link is null, the assignment is skipped, and the right-hand side isn't even evaluated:

class Session(var notes: String?) class Profile(val currentSession: Session?) fun loadNotes(): String { println("loadNotes() called") return "Felt strong" } fun main() { //sampleStart val resting = Profile(currentSession = null) resting.currentSession?.notes = loadNotes() // skipped: loadNotes() never runs val active = Profile(Session(notes = null)) active.currentSession?.notes = loadNotes() // runs and assigns println(active.currentSession?.notes) //sampleEnd }

AI/Java-flavoured smells to spot
  • if (x != null) x.length else null: that is exactly x?.length
  • Pyramids of if (a != null) { if (a.b != null) { … } } to reach one value
  • !! added wherever the compiler complained, which brings the crash back (lesson 2.4)
  • Every property declared String? = null “to be safe”, even though it's never actually absent

Quick check

1. nickname is a String?. What's the type of profile.nickname?.length?

length is an Int, but a safe call has to be able to produce null, so the result is Int?.

2. What happens with val name: String = null?

String and String? are different types. Only String? accepts null, and this is checked at compile time.

3. profile.currentWorkout?.notes = loadNotes() runs while currentWorkout is null. What about loadNotes()?

When a safe-call chain on the left side hits null, the whole assignment is skipped, including evaluating the right-hand side.

4. Given val nick: String? = "kai" and val city = "Oslo", which expression has the non-null type String?

city is a plain String, so calling on it gives a plain String. Any ?. makes the result nullable, and toIntOrNull() returns Int?.

Flatten the null-check pyramid

class Device(val name: String) class Session(var notes: String?, val device: Device?) class Athlete(val nickname: String?, val session: Session?) fun deviceLabel(athlete: Athlete?): String? { if (athlete != null) { if (athlete.session != null) { if (athlete.session.device != null) { return athlete.session.device.name.uppercase() } } } return null } fun saveNotes(athlete: Athlete?, text: String) { if (athlete != null && athlete.session != null) { athlete.session.notes = text } } fun main() { val full = Athlete("Kai", Session(null, Device("Treadmill T5"))) val noSession = Athlete(null, null) println(deviceLabel(full)) println(deviceLabel(noSession)) println(deviceLabel(null)) saveNotes(full, "Felt strong") saveNotes(noSession, "Ignored") println(full.session?.notes) }
