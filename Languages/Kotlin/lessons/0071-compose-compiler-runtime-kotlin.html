Compose Compiler & Kotlin Runtime Mental Model

How Kotlin immutability, closure capture, equality contracts, and flows drive Jetpack Compose stability, Strong Skipping, rememberUpdatedState, and snapshotFlow.

Warm-up: Spaced Retrieval

  1. Why does mutating an existing list inside a MutableStateFlow (e.g. _state.value.items.add(x)) fail to trigger a new emission?
    CheckStateFlow compares old and new values using structural equality (==). Mutating a list in place keeps the same reference and equal contents compared to itself, so StateFlow conflates the update and emits nothing.
  2. When should you use remember { derivedStateOf { ... } } in Jetpack Compose?
    CheckWhen an upstream state changes at high frequency (like scroll pixel offset) while the derived UI value changes rarely (like a boolean showJumpToTop).
  3. Why is kotlin.collections.List<T> considered read-only rather than strictly immutable?
    CheckList<T> is an interface without mutation methods, but the underlying runtime instance can still be a MutableList (such as ArrayList) mutated by another reference holder.

The Concept: Kotlin Mechanics Under the Compose Hood

1. Stability (@Immutable vs @Stable) & Strong Skipping Mode

In Kotlin 2.0+, the Compose Compiler lives directly inside the Kotlin repository and enables Strong Skipping Mode by default.To skip recomposing a @Composable function whose inputs haven't changed, the Compose compiler classifies every Kotlin parameter type as stable or unstable:

  • Stable types: Primitives, String, function types (lambdas), and classes where every property is a val of a stable type (or annotated with @Immutable / @Stable). Compose compares stable parameters using structural equality (old == new).
  • Unstable types: Any class with a var property (not backed by Compose State), or standard collection interfaces (List<T>, Set<T>, Map<K, V>) unless wrapped in kotlinx ImmutableList<T> or a class annotated @Immutable.
  • Strong Skipping Mode (Kotlin 2.0.20+): In classic Compose, a single unstable parameter forced the composable to never skip. With Strong Skipping enabled, Compose compares unstable parameters using referential instance equality (old === new)—skipping recomposition as long as the exact same reference is passed!
data class Article(val id: Int, val title: String) fun explainSkipBehavior( oldArg: Any, newArg: Any, isStableType: Boolean, strongSkipping: Boolean ): String = when { isStableType && oldArg == newArg -> "SKIP (structural == matched)" isStableType -> "RECOMPOSE (structural == changed)" strongSkipping && oldArg === newArg -> "SKIP (Strong Skipping === matched)" else -> "RECOMPOSE (unstable parameter)" } fun main() { val a1 = Article(1, "Kotlin 2.4") val a2 = Article(1, "Kotlin 2.4") // distinct instance, equal value println("Stable data class: ${explainSkipBehavior(a1, a2, isStableType = true, strongSkipping = true)}") val listRef = listOf("Compose", "KMP") println("Unstable List (same ref): ${explainSkipBehavior(listRef, listRef, isStableType = false, strongSkipping = true)}") println("Unstable List (new copy): ${explainSkipBehavior(listRef, listOf("Compose", "KMP"), isStableType = false, strongSkipping = true)}") }

2. Lambda Closure Capture & The rememberUpdatedState Trap

In Kotlin, a lambda captures variables from its enclosing lexical scope in a generated closure object. This creates one of the most common Senior Android interview bugs inside LaunchedEffect or DisposableEffect:

Suppose a composable receives onTimeout: () -> Unit and launches a one-time timer via LaunchedEffect(Unit) { delay(5_000); onTimeout() }. Because the key is Unit, the coroutine does not restart when the parent recomposes with a new onTimeout lambda—so after 5 seconds, the coroutine invokes the stale closure captured on the very first composition!

import kotlinx.coroutines.* // Models Compose's rememberUpdatedState<T> mutable holder box class UpdatedStateBox<T>(var value: T) fun main() = runBlocking { var latestUser = "Guest" val initialCallback: () -> String = { "Timeout for $latestUser (captured at start)" } // Fix: hold callback inside a state box updated on recomposition val callbackBox = UpdatedStateBox<() -> String>(initialCallback) val job = launch { delay(30) // BUG if calling initialCallback() directly; SAFE when reading callbackBox.value() println("Stale closure : ${initialCallback()}") println("UpdatedStateBox: ${callbackBox.value()}") } // Simulate recomposition 10ms later with new user and new callback lambda: delay(10) latestUser = "SeniorEngineer" callbackBox.value = { "Timeout for $latestUser (fresh callback)" } job.join() }

3. derivedStateOf vs snapshotFlow

  • derivedStateOf { ... }: Stays inside the synchronous Compose Snapshot world. Combines one or more Compose State<T> objects and only triggers recomposition when the derived result changes.
  • snapshotFlow { ... }: Bridges the Compose Snapshot world into a cold Kotlin Flow<T>. Use it inside LaunchedEffect when you need coroutine Flow operators (debounce, filter, flatMapLatest) or suspending side effects (analytics, pagination triggers) driven by Compose UI state. It automatically applies distinctUntilChanged().

Quick Check

1. Under Strong Skipping Mode in the Kotlin 2.0+ Compose Compiler, how does Compose decide whether to skip recomposition when a parameter's type is unstable (such as List<String>)?

Strong Skipping uses === for unstable parameters (fast and safe if you don't mutate in place) and == for stable parameters.

2. Why does LaunchedEffect(Unit) { delay(5000); onComplete() } risk a bug if the parent composable recomposes with a new onComplete lambda after 1 second?

Whenever a long-lived effect (LaunchedEffect(Unit) or callbackFlow) outlives individual recompositions, wrap captured callbacks in rememberUpdatedState.

3. When should you choose snapshotFlow { ... } over remember { derivedStateOf { ... } }?

Use derivedStateOf for synchronous UI state derivation in composition; use snapshotFlow when you need asynchronous Flow operators or coroutine side effects.

4. What contract do you promise the Compose compiler when you annotate a Kotlin class with @Immutable?

@Immutable is a stronger promise than @Stable: once constructed, no public property of the instance will ever return a different value.

Exercise 1 · Write from blank

Compose Stability Judge & Closure-Safe Effect Runner

Implement three pure-Kotlin components modeling how Compose handles stability, updated state capture, and distinct snapshot streams:

  1. class UpdatedStateHolder<T>(var current: T): a mutable box modeling rememberUpdatedState, with fun update(newValue: T).
  2. enum class SkipResult { SKIP_STRUCTURAL, SKIP_REFERENTIAL, RECOMPOSE } and fun evaluateRecomposition(prev: Any, next: Any, isStable: Boolean, strongSkipping: Boolean): SkipResult using a guarded or multi-condition when:
    • If isStable and prev == next → SkipResult.SKIP_STRUCTURAL
    • If isStable (and not equal) → SkipResult.RECOMPOSE
    • If !isStable and strongSkipping and prev === next → SkipResult.SKIP_REFERENTIAL
    • Otherwise → SkipResult.RECOMPOSE
  3. fun <T> simulatedSnapshotFlow(snapshots: List<T>): Flow<T> that emits the items of snapshots as a cold Flow while filtering out consecutive duplicates via distinctUntilChanged().
import kotlinx.coroutines.* import kotlinx.coroutines.flow.* // Write UpdatedStateHolder<T>, SkipResult, evaluateRecomposition, and simulatedSnapshotFlow above main: fun main() = runBlocking { val holder = UpdatedStateHolder { "Initial" } val deferred = async { delay(20) holder.current() } delay(5) holder.update { "Updated after recomposition" } check(deferred.await() == "Updated after recomposition") val listA = listOf("A", "B") val listB = listOf("A", "B") check(evaluateRecomposition("ok", "ok", isStable = true, strongSkipping = true) == SkipResult.SKIP_STRUCTURAL) check(evaluateRecomposition(listA, listA, isStable = false, strongSkipping = true) == SkipResult.SKIP_REFERENTIAL) check(evaluateRecomposition(listA, listB, isStable = false, strongSkipping = true) == SkipResult.RECOMPOSE) val scrollIndices = simulatedSnapshotFlow(listOf(0, 0, 1, 1, 1, 2, 2)).toList() check(scrollIndices == listOf(0, 1, 2)) println("All Compose runtime mental model checks passed: $scrollIndices") }

Exercise 2 · Refactor

Fix the In-Place State Mutation & Stale Effect Closure

This code suffers from two classic Android bugs:

  1. CartUiState uses a var and a MutableList<String> mutated in place—so StateFlow thinks the state never changed (old == new is true on the same mutated reference!) and drops emissions.
  2. AutoSaveWorker.start captures the initial onSave callback parameter directly instead of reading from its callbackHolder: StateBox<() -> String>.

Refactor CartUiState into a deeply read-only data class CartUiState(val items: List<String> = emptyList(), val checkedOut: Boolean = false) updated via _state.update { it.copy(...) }, and fix AutoSaveWorker so it invokes the latest callback in callbackHolder.value.
