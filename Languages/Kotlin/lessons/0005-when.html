when in depth

One construct that replaces switch and long if/else if ladders, and gives you back a value.

The problem when solves

Here's the kind of code that piles up in an Android screen: one value, many cases, each in its own else if:

var label = "" if (workoutType == "run" || workoutType == "jog") { label = "Cardio" } else if (workoutType == "squat") { label = "Strength" } else if (workoutType == "yoga") { label = "Mobility" } else { label = "Other" }

The variable name is repeated on every line, the || hides which values belong together, and label needs a throwaway starting value. All you really mean is a lookup table: this value → that result. when lets you write it as one:

fun main() { val workoutType = "jog" //sampleStart val label = when (workoutType) { "run", "jog" -> "Cardio" "squat" -> "Strength" "yoga" -> "Mobility" else -> "Other" } println(label) //sampleEnd }

Docs: Control flow → when expressions and statements: “compares the result against each branch in order until one branch condition is satisfied.”Three things to notice:

  • Commas group values that share a result: "run", "jog" ->.
  • Only the first matching branch runs. Branches are checked top to bottom, and there's no fall-through and no break.
  • It produces a value, so label is a val, assigned once.

What a branch can test

With a subject, which is the value in parentheses, each branch condition can be:

fun main() { val bpm = 128 val restingBpm = 60 //sampleStart val zone = when (bpm) { 0 -> "No signal" // a constant restingBpm -> "At rest" // any expression, compared with == in 1..<100 -> "Easy" // in a range in 100..<140 -> "Moderate" !in 0..220 -> "Sensor error" // NOT in a range else -> "Hard" } println(zone) //sampleEnd }

Ranges are where when really pays off. in 100..<140 says what bpm >= 100 && bpm < 140 says, with no chance of mixing up < and <=.

When is matches, Kotlin lets you use the value as that type inside the branch. That's called a smart cast, and it's lesson 2.3.You can also test a value's type with is:

fun main() { //sampleStart val reading: Any = "152 bpm" val text = when (reading) { is Int -> "Number: $reading" is String -> "Text of length ${reading.length}" else -> "Unknown" } println(text) //sampleEnd }

No subject: a cleaner if/else if

Leave out the parentheses and every branch becomes its own true/false condition. Use this when the conditions test different things:

fun main() { val minutes = 40 val missedDays = 3 //sampleStart val advice = when { missedDays >= 3 -> "Ease back in" minutes > 60 -> "Great endurance" minutes >= 30 -> "Solid session" else -> "Short but counts" } println(advice) //sampleEnd }

Docs: Coding conventions → if versus when.So when do you use when at all? The conventions say: “Prefer using if for binary conditions… Prefer using when if there are three or more options.”

Exhaustiveness: every case must be covered

When when produces a value, there has to be a value for every possible input, so the compiler makes you cover them all. Usually that means an else. A when with no subject always needs else, even when your conditions look complete:

fun main() { val bpm = 128 //sampleStart val effort = when { // ❌ compile error: 'when' expression must be exhaustive bpm < 100 -> "Easy" bpm >= 100 -> "Hard" } println(effort) //sampleEnd }

The compiler doesn't check your arithmetic. It just sees two conditions with no else. Replacing the last condition with else fixes it, and is clearer anyway.

Docs: Control flow → Expressions: no else needed for “a Boolean, enum class, sealed class, or one of their nullable counterparts.”The exception is a subject with a fixed set of values: a Boolean, an enum (4.4) or a sealed type (4.5). There, the compiler can check that you listed every case. You can drop else, and if someone later adds a new case, every when that misses it stops compiling. That safety net is a big reason Android code models UI state as sealed types.

Name the subject: when (val x = …)

When the subject comes from a function call you also need inside the branches, give it a name right inside when:

fun readBpm(): Int = 231 fun main() { //sampleStart val status = when (val bpm = readBpm()) { in 40..200 -> "OK" else -> "Ignoring reading of $bpm" } println(status) //sampleEnd }

The name bpm exists only inside that when. It can't leak into the rest of the function and get misused later.

Newer syntax · Kotlin 2.2+

Guard conditions add an extra if to a branch: is Workout.Run if (workout.km > 10) -> "Long run". They became stable in Kotlin 2.2.0 and work only in a when with a subject. You'll see them more once we reach sealed types. Check which Kotlin version your Android project uses before relying on them.

AI/Java-flavoured smells to spot
  • Three or more else ifs that test the same variable
  • var result = "", then assigned inside every branch, instead of val result = when …
  • x == "a" || x == "b" where a comma would do: "a", "b" ->
  • x >= 100 && x < 140 instead of in 100..<140
  • when (flag) { true -> …; false -> … } for a yes/no choice: use if

Quick check

1. A value matches the conditions of two different branches. What happens?

Branches are checked in order, and the first match wins. There's no fall-through, so put the more specific cases first.

2. bpm is an Int and isResting is a Boolean. Which val x = when … fails to compile?

With no subject, an else is required. The compiler doesn't reason about whether your conditions cover every number. A Boolean subject listing both true and false is exhaustive. (For a real yes/no choice, though, prefer if.)

3. In when (val bpm = readBpm()) { … }, where can you use bpm?

A subject declared this way only exists inside the when, in every branch. That keeps it from being misused later in the function.

4. A value has exactly two outcomes. What do the coding conventions prefer?

Use if for a yes/no choice and when for three or more options. (And when doesn't need a subject: it can stand alone with true/false conditions.)
