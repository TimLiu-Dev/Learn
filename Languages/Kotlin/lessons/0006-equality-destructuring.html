Equality and destructuring

== vs ===, and pulling a value apart into named pieces in one line.

Warm-up

Answer from memory first, then check.

  1. A when with no subject is used as a value. Which branch is mandatory? (1.5)
    Checkelse. The compiler doesn't reason about whether your true/false conditions cover everything.
  2. How do you put workout.minutes inside a string? Why doesn't "$workout.minutes" work? (1.2)
    Check"${workout.minutes}". Without braces, $ takes only the simple name workout, and .minutes is printed as plain text.
  3. What is the value of a try expression when its catch block runs? (1.4)
    CheckThe last expression in the catch block. finally runs, but doesn't change the value.

Two questions: same contents, or same object?

“Are these equal?” can mean two things. Do they hold the same data? Or are they literally the same object in memory? In app code you almost always mean the first. So Kotlin gives the common question the short operator:

  • == means structural equality: same contents. It calls equals() for you.
  • === means referential equality: same object. You'll rarely need it.
fun main() { //sampleStart val planned = listOf("Run", "Row") val completed = listOf("Run", "Row") val sameRef = planned println(planned == completed) // true: same contents println(planned === completed) // false: two different list objects println(planned === sameRef) // true: one object, two names //sampleEnd }

In Java, == on objects checks identity, and you must remember .equals() for contents. Comparing strings with == is a classic Java bug. Kotlin swapped them, so the obvious operator does the right thing.If you see a.equals(b) in Kotlin, it's almost always Java habit (or AI) leaking through. Write a == b.

== handles null for you

Docs: Equality → Structural equality: a == b is translated to a?.equals(b) ?: (b === null).Under the hood, a == b checks for null before calling equals. So comparing a nullable value never crashes:

fun main() { //sampleStart val lastWorkout: String? = null println(lastWorkout == "Run") // false, no crash println(lastWorkout == null) // true //sampleEnd }

(The ? in String? marks a value that may be null. That's Section 2. For now, just know == is always safe.)

What “same contents” means for your own classes

== calls equals(), so it's only as smart as that class's equals(). A plain class doesn't know which of its fields matter, so by default it compares identity. A data class generates a field-by-field equals() for you:

class Workout(val type: String) data class WorkoutRecord(val type: String) fun main() { //sampleStart println(Workout("Run") == Workout("Run")) // false println(WorkoutRecord("Run") == WorkoutRecord("Run")) // true //sampleEnd }

That one keyword is most of the reason data classes exist. Lesson 4.3 covers them properly.

Docs: Arrays → Compare arrays: “Don't use equality (==) … to compare the contents of arrays.”One trap: arrays (arrayOf, IntArray) compare identity with ==, unlike lists. Use a.contentEquals(b). In everyday Android code you'll mostly use lists, which compare contents.

Destructuring: one line, several names

Functions often produce two related values: minutes and seconds, a day and its total. Reaching into them with .first and .second makes the reader work out what each one is. Destructuring names each part as you unpack it:

fun splitDuration(totalSeconds: Int): Pair<Int, Int> = totalSeconds / 60 to totalSeconds % 60 fun main() { //sampleStart val (minutes, seconds) = splitDuration(1265) println("$minutes min $seconds s") //sampleEnd }

a to b creates a Pair(a, b). (to is an ordinary function written between its arguments, an infix function, covered in lesson 3.4.)

How it works: componentN()

Docs: Destructuring declarations.There's no magic here. val (minutes, seconds) = pair compiles to:

val minutes = pair.component1() val seconds = pair.component2()

Any type with component1(), component2(), … functions can be destructured. That includes Pair, Triple, map entries and every data class. It also means position decides, not names:

fun main() { //sampleStart val (minutes, type) = "Run" to 30 // compiles, but oops println(minutes) // prints Run //sampleEnd }

Experimental: Kotlin is adding name-based destructuring, which matches names instead of positions. It's behind a compiler flag and not ready for production code. Use positions for now.The compiler won't catch a swapped order when both parts happen to fit. Keep the order of your names the same as the order of the values.

Skipping, looping and lambdas

fun main() { //sampleStart val weeklyMinutes = mapOf("Mon" to 30, "Wed" to 45, "Sat" to 60) // _ skips a part you don't need val (_, wedMinutes) = "Wed" to 45 // Map entries destructure into key and value for ((day, minutes) in weeklyMinutes) { println("$day: $minutes min") } // In a lambda, parentheses destructure ONE parameter println(weeklyMinutes.map { (day, minutes) -> "$day=$minutes" }) println(wedMinutes) //sampleEnd }

The parentheses in the lambda matter. { (day, minutes) -> … } takes one parameter (a map entry) and splits it, while { day, minutes -> … } would mean two parameters. Lambdas get full treatment in Section 5.

The docs suggest data classes over Pair when values travel: “it's often better to have your data named properly.”Pair or a named type? A Pair is fine inside one function, or for a quick return value you destructure right away. When it crosses into other parts of your code (a repository result, a UI state), result.second says nothing about what it is. Use a data class with named properties instead (lesson 4.3).

AI/Java-flavoured smells to spot
  • a.equals(b) instead of a == b
  • === used to compare strings or other contents
  • for (entry in map) { val k = entry.key; val v = entry.value … }
  • result.first / result.second sprinkled through code, where destructuring would name them
  • Pair returned from functions far from where it's used, when a named data class would explain itself

Quick check

1. val a = listOf(1, 2) and val b = listOf(1, 2). What do a == b and a === b give?

== compares contents, and lists compare element by element. === asks whether they're the same object, and two listOf calls make two objects.

2. class Workout(val type: String) is not a data class. What does Workout("Run") == Workout("Run") give?

Every class has an equals(). A plain class's default compares identity, so two separate objects aren't equal. Add data and you get a field-by-field equals().

3. val (minutes, type) = "Run" to 30. What is minutes?

Destructuring goes by position (component1(), component2()), not by name. The first slot of the pair is "Run", so that's what minutes gets.

4. In a lambda, what does { (day, mins) -> … } declare?

Parentheses inside a lambda's parameter list destructure a single parameter, such as a map entry. Without them, { day, mins -> … } would declare two parameters.
