Section 1 · Foundations · Lesson 1.1

val, var and type inference

Immutable by default, and why the compiler can usually work out the type for you.

Warm-up

This is the first lesson, so there's nothing to review yet. Instead, answer these from memory before reading on. Guessing is fine: trying to recall first makes the explanation stick better.

  1. In one sentence, what is the difference between val and var?
    Checkval can be assigned once; var can be reassigned. That's all. It says nothing about whether the object can change.
  2. In val x = 5, what type is x, and who decided?
    CheckInt, worked out by the compiler from the right-hand side. It's still statically typed: x can never hold a String.

The problem val solves

When you read code, every variable that can be reassigned is something you have to keep tracking. Where could it change? In which branch? Inside that loop? A variable that is assigned exactly once can be understood from its declaration alone.

In Java, a value that can't be reassigned needs the extra keyword final, so most code skips it. Kotlin makes both choices the same length on purpose.Kotlin makes this choice explicit and free. val (value) and var (variable) are both three letters, so choosing the safe one costs you nothing. The official conventions are blunt about it:

“Always declare local variables and properties as val rather than var if they are not modified after initialization.”

From Kotlin coding conventions → Immutability

The habit: start with val, and switch to var only when the compiler tells you something gets reassigned. In practice, most of a well-written Kotlin file is val.

val fixes the name, not the object

A val always points at the same object, but that object can still change if it's mutable:

fun main() { //sampleStart val workouts = mutableListOf("Run") workouts.add("Row") // fine: same list, new contents // workouts = mutableListOf() // error: val cannot be reassigned println(workouts) //sampleEnd }

So val means read-only reference, not “deeply immutable”. Making the contents read-only too is a collections topic (lesson 7.1).

Assign later, but only once

Docs: Basic syntax → Variables. Without an initializer, the type must be written.A val doesn't have to be initialized on the line where it's declared. The compiler checks that every path assigns it exactly once:

fun main() { //sampleStart val heartRate = 172 val zone: String // no initializer, so the type is required if (heartRate > 160) { zone = "Peak" } else { zone = "Cardio" } println(zone) //sampleEnd }

This is already better than var zone = "" followed by reassignments. In lesson 1.4 you'll see an even better form, where if itself produces the value.

Type inference: the compiler reads the right-hand side

Kotlin is statically typed, like Java and Swift. But when the type is obvious from the value, you don't have to write it. The compiler works it out and fixes it for good:

val name = "Sam" // String val sets = 4 // Int val steps = 3_000_000_000 // Long: too big for Int val laps = 12L // Long: L suffix val distanceKm = 5.2 // Double: decimal literals default to Double val weightKg = 72.5f // Float: f suffix

Docs: Numbers → Type conversion: “Numeric types are not subtypes of one another.”One rule catches people out: Kotlin never converts between number types for you. An Int is not a Double, even when the value is 5:

fun main() { //sampleStart val pace: Double = 5 // ❌ compile error. Try 5.0, or 5.toDouble() println(pace) //sampleEnd }

Integer literals are flexible, though. val laps: Long = 12 compiles, because a bare whole number takes whatever integer type you declare, as long as it fits.

So when do you write the type?

  • No initializer: val zone: String. The compiler has nothing to infer from.
  • You want a different type than the literal gives: val total: Long = 0.
  • Public API and values from Java code: the conventions ask for explicit types on public functions and properties, so changing the implementation can't silently change the type (conventions for libraries). Values that come from Java APIs (much of the Android SDK) are covered in lesson 2.4.
  • Otherwise, leave it out. val name: String = "Sam" repeats what's already obvious.
AI/Java-flavoured smells to spot
  • var everywhere, even for values that are never reassigned
  • Repeated types: val count: Int = 0, var title: String = "Hi"
  • var x = "" (or null), then assigned in each branch, instead of one val

Quick check

1. val workouts = mutableListOf("Run") then workouts.add("Row"). What happens?

val stops you pointing workouts at a different list. It doesn't stop the list itself changing.

2. What type is inferred for val steps = 3_000_000_000?

Unsuffixed whole numbers are Int if they fit and Long if they don't. Three billion is bigger than Int.MAX_VALUE (about 2.1 billion).

3. Which line does not compile?

An integer literal can become Long, but never Double. There are no implicit number conversions. Write 5.0.

4. For a local variable, when is writing the type actually needed?

With no right-hand side there's nothing to infer from. You also write it when you want a different type than the literal gives, as in val total: Long = 0.
