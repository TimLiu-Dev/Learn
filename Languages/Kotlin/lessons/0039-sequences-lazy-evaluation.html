Section 7 · Collections & DSA · Lesson 7.6

Sequences & lazy evaluation

Avoid intermediate collection allocations, optimize big-O space complexity, and build infinite streams.

Warm-up: Rapid Recall

  1. In list.filter { ... }.map { ... }, how many intermediate lists are created?
    CheckTwo: one new list for the filter result, and another new list for the map result.
  2. What happens when you process a list of 1,000,000 objects with 4 chained collection operators?
    Check4 large temporary lists are allocated on the heap, causing significant garbage collection pressure.

The Concept: Eager Collections vs Lazy Sequences

1. Eager vs Lazy Processing Order

  • Collections (Eager): evaluate each step on the whole collection horizontally before moving to the next operator.
  • Sequences (Lazy): evaluate vertically item-by-item through the entire pipeline. Only elements that reach the terminal operation are computed!
val numbers = listOf(1, 2, 3, 4, 5, 6) // Eager: filters all 6, then maps all 3 evens, then takes 1st val eagerResult = numbers.filter { it % 2 == 0 }.map { it * 10 }.first() // Lazy: takes 1 (skips), takes 2 -> even -> maps to 20 -> first() matches! // 3, 4, 5, 6 are NEVER inspected or mapped! val lazyResult = numbers.asSequence() .filter { it % 2 == 0 } .map { it * 10 } .first()

2. Intermediate vs Terminal Operations

Sequence operations are categorized into:

  • Intermediate operations (stateless or stateful): map, filter, take, drop. They return a new Sequence and execute zero work until triggered.
  • Terminal operations: toList(), toSet(), first(), count(), sum(), forEach(). They trigger the pipeline computation.

3. Generating Infinite Sequences

Build on-demand sequences without pre-computing bounds:

// Infinite natural numbers generator: val naturalNumbers = generateSequence(1) { it + 1 } // Infinite Fibonacci: val fibonacci = generateSequence(0 to 1) { Pair(it.second, it.first + it.second) } .map { it.first } println(fibonacci.take(8).toList()) // [0, 1, 1, 2, 3, 5, 8, 13]

4. When NOT to Use Sequences

For small collections (< 100 items), the overhead of creating Sequence wrapper objects exceeds the intermediate list cost. Use standard collection operators for small lists; switch to asSequence() when:

  1. The collection is large (> 1,000 items) and has 2+ chained transformations.
  2. You use short-circuiting operators (first(), take(n)) on an unknown size.

Quick Check

Given (1..1_000_000).asSequence().filter { it % 2 == 0 }.map { it * 2 }.take(3).toList(), how many total numbers are processed by filter?

Because sequences are lazy and process item-by-item, checking 1 (odd), 2 (even #1), 3 (odd), 4 (even #2), 5 (odd), and 6 (even #3) fulfills take(3). Processing stops immediately after 6.

Exercise 2 · Refactor

Heavy Eager Pipeline Optimization

Refactor this eager list processing pipeline on 100,000 records to a lazy asSequence() with short-circuiting.

data class LogEntry(val id: Int, val level: String, val message: String) // REFACTOR THIS EAGER PIPELINE: fun findFirstErrorAlerts(logs: List<LogEntry>, limit: Int): List<String> { // Inefficient: filters all 100,000 entries into intermediate list, // then maps all errors into second list, then takes 3: return logs .filter { it.level == "ERROR" } .map { "[ALERT ${it.id}] ${it.message.uppercase()}" } .take(limit) } fun main() { val sampleLogs = (1..100_000).map { id -> LogEntry(id, if (id % 10 == 0) "ERROR" else "INFO", "Message payload $id") } val alerts = findFirstErrorAlerts(sampleLogs, 3) println(alerts) }
Hint 1: Lazy pipeline conversionAdd .asSequence() to the start of the collection pipeline.
Hint 2: Early terminationApply .take(3).toList(); lazy evaluation stops scanning lines as soon as 3 matching errors have been captured.
