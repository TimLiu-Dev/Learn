Value classes and type safety

Eliminating primitive obsession with @JvmInline value class—and knowing the exact rules for when the JVM still boxes them.

Warm-up

The Problem: Primitive Obsession

Consider this standard Android or backend API function:

fun assignCoach(coachId: String, athleteId: String) { ... } // Bug waiting to happen: parameters accidentally swapped! assignCoach(athleteId, coachId) // Compiles fine, corrupts database silently!

Wrapping them in normal classes (class CoachId(val id: String)) solves the type safety problem, but allocates an extra wrapper object on the heap every time an ID or metric is created.

The Solution: @JvmInline value class

Docs: Inline value classes. On the JVM, Kotlin mangles function names (e.g. assignCoach-xxxx) to avoid bytecode signature clashes when two value classes wrap the same underlying type.Kotlin solves this with value classes. At compile time, they are distinct types that prevent parameter swapping. At runtime, whenever possible, the compiler erases the wrapper and passes the underlying value directly:

@JvmInline value class CoachId(val value: String) @JvmInline value class AthleteId(val value: String) fun assignCoach(coachId: CoachId, athleteId: AthleteId) { ... } // assignCoach(athleteId, coachId) // ❌ COMPILE ERROR! Type mismatch: required CoachId, found AthleteId

Member functions, init checks, and interfaces

Value classes cannot have backing fields beyond their single val property, but they can declare init validation blocks, computed properties, functions, and implement interfaces:

@JvmInline value class Seconds(val value: Int) { init { require(value >= 0) { "Duration cannot be negative: $value" } } val toMinutes: Double get() = value / 60.0 }
Senior Caveat · When Value Classes STILL Box on the Heap

A value class is not unconditionally zero-allocation. Just like Int boxes to java.lang.Integer, the compiler must allocate a heap wrapper object whenever a value class is used as:

  • A nullable type (e.g. Seconds? wrapping a primitive Int must box so null is distinguishable from 0).
  • A generic type argument (e.g. List<Seconds>, Result<CoachId>, or calling fun <T> log(x: T)).
  • An interface or Any supertype (e.g. passing Seconds as an implemented Measurable interface or Any).

Quick check

1. Which declaration rule is strictly enforced by the compiler for every @JvmInline value class?

A value class wraps a single underlying runtime representation, so its primary constructor must contain exactly one val property.

2. Given @JvmInline value class Seconds(val raw: Int), which usage avoids heap boxing at runtime?

Direct non-null parameter and return positions inline to primitive int. Generics (List<Seconds>), nullable primitives (Seconds?), and Any upcasts all trigger boxing.
