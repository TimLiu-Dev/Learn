Sealed classes and sealed interfaces

Modeling robust Android UI states, algebraic data types, and compile-time exhaustiveness.

Warm-up

  1. In Kotlin 1.9+, why is MyEnum.entries preferred over MyEnum.values()?
    Checkentries returns a pre-cached immutable list with zero memory allocations, whereas values() allocates a new array on every call.
  2. If an enum has 4 entries, what happens if you write a when expression without an else branch handling all 4?
    CheckIt compiles cleanly. If a new entry is added later, the compiler immediately raises an error pointing directly to the unhandled case.

Enums vs Sealed Types: What problem do they solve?

Docs: Sealed classes. Direct subclasses must be in the same package and module.An enum is great when every case has the exact same structure (e.g. CARDIO, REST). But what if one state needs to hold a list of items, while an error state needs a message string, and a loading state needs no data at all?

In Java, developers often made an anemic class with 4 nullable fields (data, isLoading, errorMessage, hasError), leading to impossible states (e.g. isLoading = true AND errorMessage = "Failed" simultaneously).

A sealed hierarchy restricts inheritance to a known set of subclasses, where each subclass can have completely different properties:

sealed interface ScreenState { data object Loading : ScreenState data class Success(val workouts: List<String>) : ScreenState data class Error(val message: String) : ScreenState }

Exhaustive handling & Smart Casts

When evaluated in a when expression, the compiler knows all possible subclasses. In each branch, Kotlin automatically smart-casts to that specific subclass:

fun render(state: ScreenState): String = when (state) { ScreenState.Loading -> "Loading spinner..." is ScreenState.Success -> "Displaying ${state.workouts.size} workouts" // smart-cast! is ScreenState.Error -> "Error: ${state.message}" // smart-cast! }

sealed interface vs sealed class

  • Use sealed interface (preferred default): A class can implement multiple sealed interfaces, and interfaces have no constructor overhead.
  • Use sealed class: Only when subclasses must inherit shared state or constructor parameters from a common base class.

Quick check

Why is data object preferred over plain object for stateless sealed entries (like Loading)?

data object synthesizes a clean toString() output (e.g. Loading instead of ScreenState$Loading@1a2b3c), making logcat and debugging crystal clear.

Android UI State Model

  1. data object Loading : WorkoutUiState
  2. data class Ready(val workoutTitle: String, val distanceKm: Double) : WorkoutUiState

  • "Workout ready: <workoutTitle> (<distanceKm> km)" for Ready

Eliminate the Anemic Nullable State Antipattern

This class is a classic anti-pattern: multiple nullable fields representing mutually exclusive states. Refactor it into a sealed interface SyncResult with Success and Error subtypes.

// Antipattern: single class representing 3 incompatible states class ApiResponse( val isSuccess: Boolean, val items: List<String>?, val errorCode: Int?, val errorMessage: String? ) fun handleResponse(response: ApiResponse): String { if (response.isSuccess) { val count = response.items?.size ?: 0 return "Received $count workouts" } else { val code = response.errorCode ?: 500 val msg = response.errorMessage ?: "Unknown error" return "Error $code: $msg" } } fun main() { val r1 = ApiResponse(true, listOf("Run", "Swim"), null, null) val r2 = ApiResponse(false, null, 404, "Server not found") println(handleResponse(r1)) println(handleResponse(r2)) }
