Nullable types and ?. · 2.1

  • Nulls come from API fields, map[key] (returns V?), toIntOrNull(), Java APIs.
  • Put ?. only after values whose type ends in ?. The chain stops at the first null. On a non-null receiver you get an “Unnecessary safe call” warning.
  • Make something nullable only when “absent” is a real state.

Elvis ?: · 2.2

val name = profile?.nickname ?: profile?.email ?: "Athlete" // chain of fallbacks val goal = settings["weeklyGoal"]?.toIntOrNull() ?: 150 fun start(w: Workout?) { val workout = w ?: return // missing is normal → leave val coach = workout.coach ?: throw IllegalStateException("No coach") // missing is a bug }
  • Precedence trap: x ?: 0 + base means x ?: (0 + base). Use parentheses.
  • return and throw are expressions of type Nothing, which fits anywhere. That's why guards type-check.

Smart casts · 2.3

After x != null, x is T, !is T + return, ?: return, or on the right of &&/||, the compiler treats x as the narrower type. A when (x) { is T -> … } casts inside each branch. An as straight after an is check is redundant.

Is a smart cast possible on…
local valAlways
val propertyIf private, internal or in the same module, not open, no custom getter
local varIf not modified between check and use, and not captured by a lambda that modifies it
var propertyNever: it could change between check and use

Fix for “smart cast is impossible”: copy it into a local val (val w = current ?: return) or use ?.. Never use !!.

!!, lateinit and platform types · 2.4

Instead of !!, in this order

  1. Handle it: ?. / ?: with a sensible default
  2. Leave early: ?: return
  3. Fail with a message: requireNotNull(x) { "…" } for a bad argument (IllegalArgumentException); checkNotNull(x) { "…" } or ?: error("…") for a bad state (IllegalStateException). Both …NotNull functions return the value, and it's non-null afterwards.

lateinit var

private lateinit var binding: ActivityWorkoutBinding // Android: set in onCreate
  • var only, non-null type, not a primitive (Int, Double…), not in the primary constructor, no custom getter/setter.
  • Read before it's set → UninitializedPropertyAccessException, naming the property.
  • this::binding.isInitialized checks it. If you need that often, the property should probably be nullable.
  • A value that's computed once on first use: by lazy (lesson 8.1).

Platform types (T!)

  • Values from Java code with no nullability info. Kotlin can't know if they're null, so it relaxes the checks. You can't write T! yourself.
  • Nullability annotations (JetBrains, JSpecify, AndroidX) turn them into proper T? or T.
  • Storing one in a String makes Kotlin check at that line and throw there if it's null. That's better than crashing later, far from the cause.
  • Convention: a property or public function initialized from a platform value must declare its Kotlin type.
