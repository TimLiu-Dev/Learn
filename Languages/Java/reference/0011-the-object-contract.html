The Object Contract: equals(), hashCode() & toString() — Quick Reference

The Object Contract Reference.

The Object Contract Reference

Mathematical Invariant Formal Rule Practical Violation Risk
Reflexive x.equals(x) == true Violated if equals checks external mutable network state.
Symmetric x.equals(y) == y.equals(x) Violated when comparing superclass instances with subclass instances.
Transitive x.equals(y) && y.equals(z) ⇒ x.equals(z) Violated by mixing inheritance hierarchies with new value components.
Consistent Consecutive calls return identical result Violated when equals() relies on mutable fields.

Canonical Production Snippet: Compliant equals & hashCode

public final class AccountId {
    private final String value;

    public AccountId(String value) {
        this.value = Objects.requireNonNull(value);
    }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof AccountId other)) return false;
        return Objects.equals(this.value, other.value);
    }

    @Override
    public int hashCode() {
        return Objects.hashCode(value);
    }
}

Senior Production Pitfalls Checklist

  • Never Overload equals(): Always write equals(Object o). Writing equals(AccountId o) overloads rather than overrides, breaking hash sets!
  • Mutable Map Keys: Never use mutable classes as keys in HashMap or HashSet; mutating fields makes entries unfindable and leaks memory.
  • Always Use Records for Value Types: Java record classes automatically generate mathematically proven equals() and hashCode() implementations.
