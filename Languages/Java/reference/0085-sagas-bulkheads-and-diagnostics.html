Distributed Coordination, Virtual-Thread Bulkheads & JDK 25 Incident Triage

Quick production survival guide for Sagas, ShedLock, Rate Limiting, DB pool protection, and live JVM diagnostics.

1. Distributed Coordination & Triage Matrix

Canonical Production Snippet: Split TransactionTemplate + Bulkhead

@ConcurrencyLimit(40)
public OrderResult processCheckout(String orderId, long cents) {
    txTemplate.executeWithoutResult(s -> repo.insertPending(orderId, cents));
    try {
        String receipt = remoteGateway.charge(orderId, cents); // Zero DB connection held!
        txTemplate.executeWithoutResult(s -> repo.markConfirmed(orderId, receipt));
        return OrderResult.confirmed(orderId, receipt);
    } catch (RuntimeException ex) {
        txTemplate.executeWithoutResult(s -> repo.markCompensated(orderId));
        throw ex;
    }
}

Senior Production Pitfalls Checklist

  • Never Mix @Transactional with RestClient / ChatClient: Holding a JDBC connection during a 2-second HTTP call under Virtual Threads will exhaust HikariCP in milliseconds.
  • Compensating Actions Must Be Idempotent: If a Saga compensation step (refundPayment) is retried after a network timeout, it must use an idempotency key so the customer is never refunded twice.
  • Always Set -XX:+ExitOnOutOfMemoryError in Containers: A JVM after OutOfMemoryError can be left in an inconsistent state; let Kubernetes restart the pod cleanly after writing -XX:HeapDumpPath.
