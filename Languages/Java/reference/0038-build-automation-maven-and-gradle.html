Maven vs. Gradle Build & Dependency Quick Reference

Conflict resolution mechanics, diagnostic CLI commands, BOM alignment templates, and CI reproducibility rules.

1. Maven vs. Gradle Resolution & Diagnostic Matrix

Dimension Apache Maven (pom.xml) Gradle Kotlin DSL (build.gradle.kts)
Default Conflict Strategy Nearest-Wins (BFS): Shortest graph depth wins; ties broken by declaration order. Highest-Version-Wins: Highest semantic version across the graph wins.
BOM Import Syntax <dependencyManagement> with <type>pom</type><scope>import</scope> implementation(platform("group:bom:ver")) or enforcedPlatform(...)
Graph Tree Command mvn dependency:tree -Dverbose ./gradlew dependencies --configuration runtimeClasspath
Single Artifact Trace mvn dependency:tree -Dincludes=groupId:artifactId ./gradlew dependencyInsight --dependency artifactId
Downgrade Guardrail maven-enforcer-plugin → <requireUpperBoundDeps/> resolutionStrategy { failOnVersionConflict() } or strictly(...)
JDK 21 Pinning <maven.compiler.release>21</maven.compiler.release> + Toolchains java { toolchain { languageVersion = JavaLanguageVersion.of(21) } }

2. Canonical Maven POM Template (BOM + Upper-Bound Enforcer)

<project xmlns="http://maven.apache.org/POM/4.0.0">
  <modelVersion>4.0.0</modelVersion>
  <groupId>com.acme</groupId>
  <artifactId>ledger-service</artifactId>
  <version>1.0.0</version>

  <properties>
    <maven.compiler.release>21</maven.compiler.release>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
  </properties>

  <dependencyManagement>
    <dependencies>
      <dependency>
        <groupId>com.fasterxml.jackson</groupId>
        <artifactId>jackson-bom</artifactId>
        <version>2.17.2</version>
        <type>pom</type>
        <scope>import</scope>
      </dependency>
    </dependencies>
  </dependencyManagement>

  <build>
    <plugins>
      <plugin>
        <groupId>org.apache.maven.plugins</groupId>
        <artifactId>maven-enforcer-plugin</artifactId>
        <version>3.5.0</version>
        <executions>
          <execution>
            <id>enforce-upper-bounds</id>
            <goals><goal>enforce</goal></goals>
            <configuration>
              <rules>
                <requireUpperBoundDeps/>
                <requireJavaVersion><version>[21,)</version></requireJavaVersion>
              </rules>
            </configuration>
          </execution>
        </executions>
      </plugin>
    </plugins>
  </build>
</project>

3. Senior Production Pitfalls Checklist

  • Never fix a transitive NoSuchMethodError by reordering <dependency> blocks: Declaration-order tricks break silently on the next refactor; promote the version into <dependencyManagement> or import the official BOM.
  • Prefer --release 21 over -source 21 -target 21: Only --release (maven.compiler.release / Gradle toolchains) cross-checks bytecode against JDK 21's exact standard library API signatures (ct.sym).
  • Default to implementation instead of api in Gradle libraries: Reserve api strictly for types appearing in your module's public method signatures or return types.
  • Pin Wrapper SHA-256 checksums in VCS: Commit gradlew / mvnw and configure distributionSha256Sum in gradle-wrapper.properties to prevent supply-chain tampering and tool-version drift.
  • Ban SNAPSHOT dependencies on release branches: Use Maven Enforcer requireReleaseDeps or Gradle dependency locking so tagged builds remain 100% immutable.
