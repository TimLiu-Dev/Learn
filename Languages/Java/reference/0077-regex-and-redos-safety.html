Java Regular Expressions (Pattern/Matcher) & ReDoS Defense

Quick-lookup guide for Matcher.find() vs matches(), named capturing groups, quantifier modes, and ReDoS prevention.

Method / ConstructMeaningKey Rule
static final PatternCompiled regex machineImmutable & thread-safe; never call String.matches in hot paths.
matcher.matches()Full-string matchImplicit ^...$ boundaries across whole input.
matcher.find()Substring searchAdvances match cursor forward per match (results() streams them).
a++ / (?>a+)Possessive / atomic quantifierPrevents backtracking into matched characters — eliminates ReDoS!
(?<name>...)Named groupExtract clearly via matchResult.group("name").

Canonical Production Snippet: Precompiled ReDoS-Safe Extractor

public final class TraceHeaderParser {
    private static final Pattern HEADER = Pattern.compile(
        "^svc=(?<svc>[a-z0-9-]++)\\s+trace=(?<id>[a-f0-9]{16,32})$"
    );

    public static Optional<String> parseTraceId(String raw) {
        if (raw == null || raw.length() > 128) return Optional.empty();
        Matcher m = HEADER.matcher(raw);
        return m.matches() ? Optional.of(m.group("id")) : Optional.empty();
    }
}

Senior Production Pitfalls Checklist

  • Never Share Matcher Across Threads: Pattern is immutable and thread-safe; Matcher mutates internal cursor offsets and must be instantiated per call.
  • Eliminate Nested Quantifiers: Patterns like ([a-z]+)+ or (a|aa)+ trigger exponential O(2^N) ReDoS CPU lockups on non-matching input; use possessive quantifiers (++) and length caps.
  • matches() vs find(): Remember that Java's m.matches() requires matching the entire input string, whereas m.find() searches for substrings.
