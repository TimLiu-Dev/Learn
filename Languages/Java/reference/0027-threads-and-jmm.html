Threads, Happens-Before & The Java Memory Model (JMM) — Quick Reference

Java Memory Model (JMM) Quick Reference.

Java Memory Model (JMM) Quick Reference

Concept Guarantees Provided Limitations / Failure Modes
volatile field Visibility + prevents instruction reordering Does not guarantee atomicity for compound operations (count++).
synchronized / Locks Visibility + Mutual Exclusion (Atomicity) Higher overhead; potential for deadlock and thread contention.
AtomicInteger / CAS Lock-free atomicity via hardware CPU CAS High contention can cause CAS retry loops; use LongAdder instead.
final field Safe publication without synchronization Must not allow the this reference to escape the constructor.

Canonical Production Snippet: Safe State Publication

public class ConfigHolder {
    // volatile ensures reference publication happens-before any thread reads config fields
    private volatile Config currentConfig;

    public void updateConfig(Config newConfig) {
        this.currentConfig = Objects.requireNonNull(newConfig);
    }

    public Config getConfig() {
        return this.currentConfig;
    }
}

Senior Production Pitfalls Checklist

  • Volatile is Not Atomic: Never use volatile for flags or counters updated by multiple writers using read-modify-write expressions.
  • Constructor Reference Leak: Never register listeners or start threads inside constructors; the partially initialized object reference can escape before final fields are frozen.
  • L1 Cache Stale Reads: Without volatile, threads can read stale cached values indefinitely in tight loops.
