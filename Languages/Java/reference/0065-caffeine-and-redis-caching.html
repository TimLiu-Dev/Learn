Multi-Tier Caching: Caffeine (W-TinyLFU) & Redis Quick Reference

Failure-mode defenses, L1/L2 sizing parameters, and transactional eviction templates.

1. Cache Failure Modes & Architectural Mitigations

Hazard Trigger Condition Symptom Mandatory Production Mitigation
Cache Stampede (Dogpiling) Hot key expires under high concurrency Thousands of threads execute identical expensive SQL queries simultaneously Caffeine AsyncLoadingCache single-flight + refreshAfterWrite, or @Cacheable(sync = true)
Cache Penetration Requests for keys that exist in neither cache nor DB 100% cache bypass straight to PostgreSQL (often malicious ID enumeration) Cache negative sentinel ("__MISSING__") with 30s TTL, or guard entry with a Bloom Filter
Cache Avalanche Bulk-warmed keys share an identical fixed TTL or Redis node restarts Sudden cliff of misses overwhelms DB connection pool Randomized TTL jitter (baseTtl + random(0..120s)) + Resilience4j DB bulkhead
Pre-Commit Stale Populate Calling redis.delete(k) inside @Transactional before COMMIT Reader misses cache, reads old MVCC snapshot, writes stale row back for full TTL Publish domain event and evict inside @TransactionalEventListener(AFTER_COMMIT)

2. Canonical Typed RedisCacheManager Configuration (No JDK Serialization!)

@Configuration
@EnableCaching
public class RedisCacheConfig {

    @Bean
    public RedisCacheManager cacheManager(RedisConnectionFactory connectionFactory, ObjectMapper mapper) {
        var serializer = new GenericJackson2JsonRedisSerializer(mapper);
        RedisCacheConfiguration defaults = RedisCacheConfiguration.defaultCacheConfig()
            .entryTtl(Duration.ofMinutes(15))
            .disableCachingNullValues()
            .computePrefixWith(cacheName -> "app:v1:" + cacheName + ":")
            .serializeKeysWith(RedisSerializationContext.SerializationPair.fromSerializer(new StringRedisSerializer()))
            .serializeValuesWith(RedisSerializationContext.SerializationPair.fromSerializer(serializer));

        return RedisCacheManager.builder(connectionFactory)
            .cacheDefaults(defaults)
            .transactionAware() // Defers Redis PUT/EVICT operations until Spring transaction commits
            .build();
    }
}

3. Canonical Caffeine Weight-Bounded Builder

AsyncLoadingCache<String, byte[]> documentCache = Caffeine.newBuilder()
    .maximumWeight(64L * 1024 * 1024) // Hard 64 MiB heap ceiling
    .weigher((String key, byte[] bytes) -> key.length() * 2 + bytes.length + 64)
    .refreshAfterWrite(Duration.ofMinutes(1))
    .expireAfterWrite(Duration.ofMinutes(5))
    .recordStats()
    .buildAsync((key, executor) -> CompletableFuture.supplyAsync(() -> fetchBytes(key), executor));

4. Senior Production Pitfalls Checklist

  • Never leave JdkSerializationRedisSerializer enabled: It couples Redis state to private Java class internals, inflates network bandwidth, and breaks blue/green rollouts.
  • Never build an in-heap cache without maximumSize or maximumWeight: Time-only TTLs (expireAfterWrite) will still OOM the JVM under high key cardinality.
  • Remember refreshAfterWrite is lazy: Cold keys are not refreshed on a timer; pair refreshAfterWrite with a longer expireAfterWrite so abandoned keys actually get evicted.
  • Export CaffeineStatsCounter to Micrometer: Monitor cache.gets(result=hit/miss) and cache.evictions; a high eviction rate with low hit ratio signals an undersized window/main space.
  • Synchronize L1 invalidations across pods: When mutating mutable entities cached in L1 across multiple Kubernetes pods, keep L1 TTL tight (15–60s) or broadcast invalidation keys over Redis Pub/Sub / Kafka.
