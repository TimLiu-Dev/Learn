Database Concurrency: Isolation Levels, Optimistic/Pessimistic Locking, @Transactional Traps & Flyway

Master ACID transaction isolation levels, Optimistic vs Pessimistic locking strategies, and Flyway zero-downtime database migrations.

1. The ACID Isolation Levels & Concurrency Anomalies

In relational database systems (PostgreSQL, MySQL), concurrent transactions without proper isolation levels produce catastrophic data corruption anomalies:

  • Dirty Read: Transaction reads uncommitted modifications made by another transaction that later rolls back.
  • Non-Repeatable Read: Re-reading the same row within a transaction returns different column values because another transaction committed an update.
  • Phantom Read: Re-executing a range query (WHERE status = 'PENDING') returns newly inserted rows committed by another transaction.
  • Serialization Anomaly: The outcome of concurrent transactions cannot be reproduced by executing them in any serial order.
// ANTI-PATTERN: Blind update under Read Committed without locking
@Transactional
public void deductBalance(Long accountId, BigDecimal amount) {
    Account acc = accountRepository.findById(accountId).orElseThrow();
    // RACE CONDITION: Two threads read balance $100 simultaneously, both deduct $80!
    acc.setBalance(acc.getBalance().subtract(amount));
    accountRepository.save(acc); // Overwrites balance to $20 instead of failing overdraft!
}

2. Optimistic vs Pessimistic Locking in Spring Data JPA

Two primary concurrency control strategies prevent lost updates: 

// 1. OPTIMISTIC LOCKING: Uses @Version column (Hibernate verifies version at UPDATE)
@Entity
public class Account {
    @Id private Long id;
    private BigDecimal balance;
    @Version private Long version; // Incremented on each update; fails if changed
}
// Emits: UPDATE account SET balance=?, version=2 WHERE id=? AND version=1;
// If zero rows updated -> throws ObjectOptimisticLockingFailureException -> Retry loop!

// 2. PESSIMISTIC LOCKING: Acquires database row lock directly
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT a FROM Account a WHERE a.id = :id")
Optional<Account> findByIdWithLock(@Param("id") Long id);
// Emits: SELECT ... FOR UPDATE (blocks competing transactions until commit)
⚡ Optimistic vs Pessimistic Decision Rule
Use Optimistic Locking when contention is low to moderate (95% of web APIs) to maximize database throughput without holding long locks. Use Pessimistic Locking for ultra-high-contention resources (e.g. concert seat reservations or inventory decrement counters) where collision retry storms would overwhelm the CPU.

3. Zero-Downtime Database Migrations with Flyway

Never use spring.jpa.hibernate.ddl-auto=update in production. Flyway manages version-controlled, repeatable SQL migrations: 

# Migration naming conventions:
# V<Version>__<Description>.sql (Immutable versioned migration)
# R__<Description>.sql           (Repeatable migration executed when checksum changes)

src/main/resources/db/migration/
  ├── V1__create_account_table.sql
  ├── V2__add_version_column.sql
  └── R__create_account_views.sql
