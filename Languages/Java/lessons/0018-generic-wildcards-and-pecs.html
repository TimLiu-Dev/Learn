Generic Wildcards, Variance & The PECS Principle

Master Generic Wildcards, PECS (Producer Extends, Consumer Super), covariance, and contravariance.

1. The Invariance Rule of Java Generics

Unlike arrays (which are covariant), generic types in Java are strictly invariant: List<Integer> does NOT extend List<Number>, even though Integer extends Number: 

// ANTI-PATTERN: Invariance compilation failure
List<Integer> ints = List.of(1, 2, 3);
// List<Number> nums = ints; // COMPILATION ERROR: Incompatible types!
// If this were allowed, nums.add(Double.valueOf(3.14)) would corrupt the Integer list!

2. The PECS Principle: Producer Extends, Consumer Super

To make generic APIs flexible, Effective Java (Item 31) defines the PECS mnemonic:

  • Producer Extends (? extends T): If your parameter produces items for your method to read, use extends (Covariance). You can read T from it, but you CANNOT add items (except null).
  • Consumer Super (? super T): If your parameter consumes items for your method to write, use super (Contravariance). You can safely write T into it, but reading only returns Object.
// IDIOMATIC JAVA 21: Canonical PECS copy method (Collections.copy)
public static <T> void copy(List<? super T> dest, List<? extends T> src) {
    for (T item : src) { // src PRODUCES items of type T
        dest.add(item);   // dest CONSUMES items of type T
    }
}
⚡ The Wildcard Capture Helper Pattern
When a method accepts an unbounded wildcard List<?> and needs to manipulate elements by type (such as reversing in-place), use a private generic helper: <E> void helper(List<E> list) to capture the wildcard.

3. Under the Hood: Why You Cannot Add to ? extends T

A frequent interview trap is attempting to insert elements into an upper-bounded collection: 

List<? extends Number> list = new ArrayList<Integer>();
// list.add(Integer.valueOf(10)); // DOES NOT COMPILE!
// The compiler knows list holds SOME subtype of Number, but cannot prove whether
// it is actually List<Double>, List<Float>, or List<Integer>!
