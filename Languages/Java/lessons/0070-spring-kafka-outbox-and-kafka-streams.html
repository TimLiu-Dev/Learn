Spring Kafka Async CompletableFuture Publishing, Retry/DLT, Transactional Outbox & Kafka Streams

Master the Transactional Outbox Pattern, async KafkaTemplate publishing, and non-blocking retry topics.

1. The Dual-Write Problem & The Transactional Outbox Pattern

In microservices, writing to a database and publishing to Kafka in the same method suffers from the Dual-Write Problem: if the database commits but the network fails before Kafka publishes, data is permanently inconsistent. The Transactional Outbox Pattern resolves this without complex Two-Phase Commit (2PC): 

// IDIOMATIC JAVA 21: Transactional Outbox inside atomic DB boundary
@Transactional
public void processPayment(Payment payment) {
    paymentRepository.save(payment); // 1. Save business state
    // 2. Insert outbox record into relational DB in the EXACT same transaction!
    outboxRepository.save(new OutboxEvent("payments", payment.id(), toJson(payment)));
} // Both commit or rollback together! Asynchronous poller / Debezium publishes to Kafka.

2. Asynchronous KafkaTemplate Publishing with CompletableFuture

In Spring Kafka 3.x, KafkaTemplate.send() returns a standard CompletableFuture<SendResult<K, V>>. Senior systems attach non-blocking completion callbacks to record partition offsets or handle delivery failures: 

// UNDER THE HOOD: Non-blocking CompletableFuture callback
kafkaTemplate.send("orders", orderId, orderPayload)
    .whenComplete((result, ex) -> {
        if (ex != null) {
            log.error("Failed to deliver order {}: {}", orderId, ex.getMessage());
            alertingService.notifyFailure(orderId, ex);
        } else {
            RecordMetadata meta = result.getRecordMetadata();
            log.info("Delivered order {} to partition {} offset {}", orderId, meta.partition(), meta.offset());
        }
    });

3. Non-Blocking Retries & Dead Letter Topics (@RetryableTopic)

Blocking retries in consumers hold partition offsets, causing consumer lag spikes across all subsequent messages. Spring Kafka's @RetryableTopic implements non-blocking retries by forwarding failed messages across dedicated retry topics with progressive delays before sending to a Dead Letter Topic (DLT): 

// IDIOMATIC JAVA 21: Non-blocking progressive retry topics
@RetryableTopic(
    attempts = "4",
    backoff = @Backoff(delay = 1000, multiplier = 2.0),
    autoCreateTopics = "true"
)
@KafkaListener(topics = "incoming-payments")
public void handlePayment(PaymentEvent event) {
    paymentService.process(event); // If fails, moves to payments-retry-1000, then DLT!
}
