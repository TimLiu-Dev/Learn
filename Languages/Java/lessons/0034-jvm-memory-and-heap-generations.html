JVM Memory Layout, Object Headers, Compressed OOPs & Heap Generations

Master 64-bit object headers, Compressed OOPs, the 32GB cliff, and JVM memory regions.

1. The 64-Bit Object Header Architecture

Every object on the HotSpot heap carries an object header consisting of two 64-bit words (when uncompressed):

  • Mark Word (64 bits): Stores object identity hashcode, generational GC age (4 bits: max age 15), lock flags (biased, lightweight, heavyweight), and GC state.
  • Klass Pointer (32 or 64 bits): Points to the metadata definition of the object's class inside Metaspace.
// ANTI-PATTERN: Believing an empty object has 0 bytes overhead
class Empty {} // Overheads: Mark Word (8B) + Klass Word (4B compressed) + 4B padding = 16 BYTES!

2. Under the Hood: Compressed OOPs & The 32GB Cliff

On 64-bit architectures, pointers consume 8 bytes. With Compressed Ordinary Object Pointers (Compressed OOPs) enabled via -XX:+UseCompressedOops, the JVM stores 32-bit pointers by exploiting 8-byte object alignment. Shifting the 32-bit address 3 bits left yields a 35-bit addressing space: 

// UNDER THE HOOD: 3-bit bitwise shift addressing
// 32-bit pointer shifted 3 bits left: 2^32 * 8 bytes = 32 Gigabytes!
// PITFALL: Allocating a 33GB heap disables compressed OOPs!
// Pointers immediately inflate from 4 bytes to 8 bytes, wasting ~20-30% of your heap!
// A 31GB heap effectively provides MORE usable memory than a 33GB heap!

3. JVM Memory Regions: Heap vs Metaspace vs Off-Heap

HotSpot divides memory into structured native and garbage-collected regions: 

// IDIOMATIC JAVA 21: Production JVM memory layout
// [ Eden | Survivor S0 | Survivor S1 ] -> Young Generation (G1 / Parallel)
// [ Tenured / Old Gen                ] -> Long-lived objects promoted after surviving N cycles
// [ Metaspace (Native OS Memory)     ] -> Class definitions, method bytecode, constant pools
// [ Thread Stacks (Native OS Memory) ] -> 1MB per platform thread frame
// [ Direct ByteBuffers (Native Heap) ] -> Off-heap buffers allocated via allocateDirect()
