Structured Concurrency (StructuredTaskScope) & ScopedValue vs ThreadLocal

Master Project Loom Structured Concurrency (JEP 505 preview / JDK 21 JEP 453) to eliminate orphaned threads, and ScopedValue (finalized in Java 25 JEP 506) for zero-leak context propagation.

1. The Unstructured Concurrency Crisis: Orphaned Threads & Leaks

In traditional Java concurrency with ExecutorService or CompletableFuture, task lifecycles are unstructured. If a request handler spawns sub-tasks and one sub-task fails, the remaining sub-tasks continue running in the background as orphaned threads, consuming CPU, database connections, and memory: 

// ANTI-PATTERN: Unstructured concurrency leaking orphaned threads
public UserProfile getUserProfile(String userId) throws Exception {
    CompletableFuture<User> userFuture = CompletableFuture.supplyAsync(() -> fetchUser(userId));
    CompletableFuture<Orders> ordersFuture = CompletableFuture.supplyAsync(() -> fetchOrders(userId));

    // If fetchUser fails, fetchOrders keeps running unnoticed in background!
    return new UserProfile(userFuture.get(), ordersFuture.get());
}

2. Under the Hood: StructuredTaskScope (JDK 25 JEP 505 Preview — Requires --enable-preview)

Modern Java introduces Structured Concurrency via StructuredTaskScope (still a preview API requiring javac --enable-preview --release 25 and java --enable-preview). Subtasks are lexically bound to a syntactic block using try-with-resources. In Java 25 (JEP 505), scopes open via static factories like StructuredTaskScope.open(); if any subtask fails, siblings are cancelled automatically and scope.join() throws: 

// IDIOMATIC JAVA 25 (JEP 505 Preview): StructuredTaskScope.open() with automatic sibling cancellation
// Note: Legacy JDK 21-24 previews used new StructuredTaskScope.ShutdownOnFailure() + scope.throwIfFailed()
public UserProfile fetchUserProfile(String userId) throws Exception {
    try (var scope = StructuredTaskScope.open()) {
        Subtask<User> userSubtask = scope.fork(() -> fetchUser(userId));
        Subtask<Orders> ordersSubtask = scope.fork(() -> fetchOrders(userId));

        scope.join(); // Blocks until all finish or one fails; throws FailedException if any failed

        // Here, both subtasks are guaranteed completed successfully
        return new UserProfile(userSubtask.get(), ordersSubtask.get());
    } // Exiting block guarantees all spawned virtual threads have terminated!
}
⚡ Joiner Policies: First-Success vs All-Must-Succeed
Use StructuredTaskScope.open(Joiner.<T>anySuccessfulResultOrThrow()) (legacy JDK 21 preview: ShutdownOnSuccess<T>) for speculative fan-out (e.g. querying multiple replicas or redundant price quotes where the fastest result wins). The first subtask to succeed cancels all remaining siblings and scope.join() returns that winning result directly!

3. ScopedValue vs ThreadLocal (Finalized in Java 25 JEP 506)

When running millions of virtual threads, ThreadLocal causes severe overhead: every thread maintains its own mutable map, and failure to call remove() leaks memory. ScopedValue introduces immutable, bounded-lifetime context: 

// IDIOMATIC JAVA 25 (JEP 506): ScopedValue for zero-overhead, immutable context propagation
public class SecurityContextHolder {
    public static final ScopedValue<UserCredentials> CURRENT_USER = ScopedValue.newInstance();

    public void handleRequest(UserCredentials creds) {
        // Bound ONLY for the lexical scope of the runnable
        ScopedValue.where(CURRENT_USER, creds).run(() -> {
            processPayment(); // Reads CURRENT_USER.get() without thread-local map overhead!
        });
        // Out here, CURRENT_USER is automatically unmapped! No memory leaks!
    }
}
🔗 Android / Kotlin Bridge: coroutineScope vs StructuredTaskScope
Kotlin's coroutineScope { async { ... } } cancels sibling jobs on child failure and propagates CoroutineContext lexically — which maps directly to Java 25's StructuredTaskScope.open() (JEP 505) and finalized ScopedValue (JEP 506)!
