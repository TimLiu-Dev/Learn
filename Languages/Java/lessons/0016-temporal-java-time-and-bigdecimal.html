Production Date/Time (java.time) & Financial Math (BigDecimal)

Master modern date-time manipulation with JSR-310 (Instant, ZonedDateTime, Duration), DST transition edge cases, and high-precision financial arithmetic with BigDecimal.

1. The Production Hazards of Legacy Date/Time & Floating-Point Math

In enterprise financial and distributed backend systems, two bugs cause catastrophic production outages:

  • Legacy java.util.Date & SimpleDateFormat: Mutable and thread-unsafe. Concurrently calling format() corrupts timestamps silently across threads.
  • IEEE-754 double / float for Currency: Binary floating-point cannot accurately represent decimal fractions like 0.1 or 0.01. Operations like 1.0 - 0.9 yield 0.09999999999999998, introducing accounting drift and audit failures. 
// ANTI-PATTERN: Dangerous float math and legacy date usage
double price = 0.70;
double tax = 0.05;
double total = price + tax; // 0.7500000000000001 - accounting error!

// ANTI-PATTERN: Thread-unsafe date formatting in singleton service
public class LegacyReportService {
    private static final SimpleDateFormat SDF = new SimpleDateFormat("yyyy-MM-dd"); // RACE CONDITION!
}

2. Under the Hood: The java.time Mental Model (JSR-310)

Modern Java 25 provides immutable, thread-safe classes with clear temporal semantics: 

// Machine time: UTC nanosecond instant from Unix Epoch (1970-01-01T00:00:00Z)
Instant nowUtc = Instant.now();

// Human calendar time in specific geographic zone (handles DST transitions):
ZoneId tokyo = ZoneId.of("Asia/Tokyo");
ZoneId ny = ZoneId.of("America/New_York");
ZonedDateTime nyMeeting = ZonedDateTime.of(2026, 11, 7, 14, 30, 0, 0, ny);
ZonedDateTime tokyoTime = nyMeeting.withZoneSameInstant(tokyo);

// Wall-clock time WITHOUT time zone (NOT a point in timeline):
LocalDateTime wallClock = LocalDateTime.now(); // Dangerous to persist for audit logs!
⚠ The Daylight Saving Time (DST) Fall-Back Trap
In autumn when clocks "fall back" from 02:00 to 01:00, wall-clock time 01:30 repeats twice! ZonedDateTime handles this using ZoneOffsetTransition. Always persist database timestamps as UTC Instant (or TIMESTAMP WITH TIME ZONE) to ensure monotonically increasing event ordering across clusters.

3. Financial Arithmetic with BigDecimal

Always construct BigDecimal from a String or long (cents), never from double: 

// PRODUCTION TRAP:
BigDecimal bad = new BigDecimal(0.1); // Value is 0.10000000000000000555111512312578...
BigDecimal good = new BigDecimal("0.1"); // Exact decimal 0.1
BigDecimal preferred = BigDecimal.valueOf(10, 2); // Exact 0.10

// Division without scale and rounding mode throws ArithmeticException on non-terminating decimals!
// BigDecimal result = BigDecimal.ONE.divide(new BigDecimal("3")); // CRASH! Non-terminating decimal!
BigDecimal safeResult = BigDecimal.ONE.divide(new BigDecimal("3"), 4, RoundingMode.HALF_EVEN);
