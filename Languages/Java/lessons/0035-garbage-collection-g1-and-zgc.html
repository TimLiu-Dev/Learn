Garbage Collection Engineering: G1GC & Generational ZGC

Master G1 GC regions, humongous objects, and Java 21 Generational ZGC sub-millisecond pauses.

1. The Weak Generational Hypothesis

Decades of JVM telemetry confirm that the vast majority of allocated objects die shortly after creation (method parameters, temporary strings, DTOs). Modern garbage collectors exploit this by partitioning memory into generations, collecting young objects frequently with minimal overhead: 

// ANTI-PATTERN: Forcing Full GC passes via code
System.gc(); // DISASTER: Triggers stop-the-world Full GC; disable via -XX:+DisableExplicitGC!

2. Under the Hood: G1 GC Regions & Humongous Allocations

The Garbage-First (G1) Collector divides the heap into 2,048 contiguous regions ranging from 1MB to 32MB. Rather than collecting the entire heap, G1 dynamically prioritizes regions with the highest garbage ratio to meet the target pause deadline (-XX:MaxGCPauseMillis=200): 

// UNDER THE HOOD: G1 Humongous Object Allocation
// Any single object > 50% of the G1 region size is classified as "Humongous"
// Humongous objects bypass Eden and are allocated directly into contiguous Old Gen regions!
// Frequent humongous allocations cause severe heap fragmentation and premature Full GC!
// REMEDY: Increase region size via -XX:G1HeapRegionSize=16m or stream large payloads.

3. Generational ZGC: Sub-Millisecond Pauses at Terabyte Scale

In Java 21, Generational ZGC (JEP 439) delivers sub-millisecond maximum pause times across heaps from 8MB to 16 Terabytes. ZGC performs all phase transitions (marking, relocation, and pointer remapping) concurrently with application threads using colored pointers (metadata bits in the top 16 bits of 64-bit addresses) and load barriers: 

// IDIOMATIC JAVA 21: Enabling Generational ZGC
// java -XX:+UseZGC -XX:+ZGenerational -Xms16g -Xmx16g -jar service.jar
// Result: Stop-The-World pause times under 1 millisecond regardless of heap size!
