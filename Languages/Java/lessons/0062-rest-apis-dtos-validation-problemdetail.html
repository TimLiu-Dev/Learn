Production REST APIs, Bean Validation & RFC 9457 ProblemDetail

Master RFC 9457 ProblemDetail, Jakarta bean validation, and immutable DTO records.

1. The RFC 9457 ProblemDetail Standard

Historically, microservices invented inconsistent JSON error formats. In Spring Boot 4 and Spring Framework 7 (alongside standardized JSpecify @NullMarked / @Nullable nullness contracts across controller DTOs), error reporting standardizes on RFC 9457 Problem Details for HTTP APIs using org.springframework.http.ProblemDetail: 

// UNDER THE HOOD: Standardized RFC 9457 Error Response Body
{
  "type": "https://api.example.com/errors/not-found",
  "title": "Account Not Found",
  "status": 404,
  "detail": "Account ACT-999 was not found in the primary database",
  "instance": "/api/v1/accounts/ACT-999",
  "timestamp": 1700000000000
}
🔗 Android → Spring Boot 4 Bridge: Retrofit Client Interfaces vs. Spring @RestController
On Android, you write Retrofit interfaces (@GET("orders/{id}"), @Path("id"), @Body) to call a backend REST API. In Spring Boot 4.0, you are building the server side of that exact contract:
• Retrofit @GET("orders/{id}") → Spring @GetMapping("/orders/{id}") inside a @RestController
• Retrofit @Path("id") → Spring @PathVariable String id
• Retrofit @Query("limit") → Spring @RequestParam int limit
• Retrofit @Body → Spring @Valid @RequestBody CreateOrderRequest request (using immutable Java 25 record DTOs!).

2. Declarative Jakarta Validation with Immutable DTO Records

In modern Spring, request DTOs should always be Java records annotated with Jakarta Bean Validation. Annotating @Valid on @RequestBody instructs Spring to validate incoming payloads before invoking controller logic: 

// IDIOMATIC JAVA 25 + JACKSON 3: Validated Request DTO Record
// Note: Jackson 3 databind uses tools.jackson.*, while @JsonProperty stays in com.fasterxml.jackson.annotation!
import com.fasterxml.jackson.annotation.JsonProperty;
import jakarta.validation.constraints.*;

public record CreateAccountRequest(
    @JsonProperty("account_name")
    @NotBlank(message = "Account name is required")
    @Size(min = 3, max = 50)
    String name,

    @NotBlank(message = "Email is required")
    @Email(message = "Must be a valid email format")
    String email,

    @PositiveOrZero(message = "Initial deposit cannot be negative")
    long initialDepositCents
) {}

3. Global Exception Handling with @RestControllerAdvice

Instead of polluting controllers with try-catch blocks, centralized exception translation is handled by @RestControllerAdvice: 

// IDIOMATIC JAVA 25: Centralized Exception Translator
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(AccountNotFoundException.class)
    public ProblemDetail handleNotFound(AccountNotFoundException ex) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
        problem.setTitle("Account Not Found");
        problem.setProperty("errorCode", "ACC_404");
        return problem;
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ProblemDetail handleValidation(MethodArgumentNotValidException ex) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, "Validation failed");
        Map<String, String> errors = new LinkedHashMap<>();
        ex.getBindingResult().getFieldErrors().forEach(fe -> errors.putIfAbsent(fe.getField(), fe.getDefaultMessage()));
        problem.setProperty("fieldErrors", errors);
        return problem;
    }
}
