Primitive Data Types, Memory Layout & Arithmetic Hazards

JVM operand-stack slot widths, binary numeric promotion quirks, silent two's-complement wrap-around, and IEEE-754 floating-point failure modes.

1. The 8 Primitives & JVM Memory Density

Java partitions every value into either a primitive value or an object reference. Unlike boxed wrappers (Integer, Long, Double) which carry a 12-to-16-byte object header on the heap, incur pointer indirection, and create Garbage Collection pressure, primitives store raw binary values directly inside JVM stack-frame slots or inline inside object/array layouts:

Primitive Logical Bits JVM Stack Slots Heap Array Stride Exact Value Domain / Standard
boolean 1 bit 1 slot (32-bit int) 1 byte in boolean[] false (0) or true (1)
byte 8 bits 1 slot (sign-extended) 1 byte in byte[] -128 to 127
short 16 bits 1 slot (sign-extended) 2 bytes in short[] -32,768 to 32,767
char 16 bits 1 slot (zero-extended) 2 bytes in char[] 0 to 65,535 (unsigned UTF-16 code unit)
int 32 bits 1 slot 4 bytes in int[] -231 to 231 - 1 (~2.147 × 109)
float 32 bits 1 slot 4 bytes in float[] IEEE-754 binary32 (24-bit significand, ~7 decimal digits)
long 64 bits 2 slots (Category 2) 8 bytes in long[] -263 to 263 - 1 (~9.223 × 1018)
double 64 bits 2 slots (Category 2) 8 bytes in double[] IEEE-754 binary64 (53-bit significand, ~15–17 decimal digits)
⚠ Supplementary Unicode & char Surrogate Pairs
A 16-bit char is a single UTF-16 code unit, NOT a full Unicode character! Emojis and rare CJK ideographs above U+FFFF require two char surrogate units (32-bit code point). When processing arbitrary Unicode code points in Java 21, prefer int code points via String.codePoints() over raw charAt(i) indexing.

2. Production Traps: Premature Overflow, Midpoint Bugs & IEEE-754 Drift

Three subtle primitive bugs routinely cause outages in distributed rate limiters, binary searches, and billing services: 

// PRODUCTION HAZARDS: Compiles cleanly without warnings, fails catastrophically at scale!
public class ArithmeticTraps {
    public static void main(String[] args) {
        // TRAP 1: 32-bit int overflow BEFORE widening assignment to 64-bit long!
        int retentionDays = 30;
        long retentionMicros = retentionDays * 24 * 60 * 60 * 1_000_000;
        // All 5 operands are 32-bit ints! Product overflows 32 bits BEFORE widening to long!

        // TRAP 2: Signed midpoint overflow when searching large arrays (> 1.07 billion items)
        int low = 1_500_000_000, high = 1_800_000_000;
        int brokenMid = (low + high) / 2; // Evaluates to -497,483,648 -> ArrayIndexOutOfBoundsException!

        // TRAP 3: IEEE-754 binary64 decimal rounding + 53-bit integer precision ceiling
        double ledger = 0.1 + 0.2;        // 0.30000000000000004 (never exact for base-10 dimes/cents!)
        long snowflakeId = 9_007_199_254_740_993L; // 2^53 + 1
        long roundTripped = (long) (double) snowflakeId; // Silently corrupts to 9_007_199_254_740_992L!
    }
}

Notice Trap 1: Java evaluates expressions bottom-up according to operand types, completely ignoring the target variable type on the left-hand side of =! Because every literal in retentionDays * 24 * ... * 1_000_000 is a 32-bit int, multiplication silently wraps around in 32-bit two's complement, and only the mangled 32-bit result is sign-extended into long retentionMicros.

3. Under the Hood: Binary Numeric Promotion & Compound Casts

The JVM instruction set lacks arithmetic opcodes (`add`, `sub`, `mul`) for `byte`, `short`, or `char`. Instead, per JLS §5.6 (Binary Numeric Promotion), operands narrower than `int` are widened to 32-bit `int` on the operand stack before arithmetic executes: 

public class PromotionMechanics {
    public static void inspect() {
        byte a = 100;
        byte b = 40;

        // byte sum = a + b;
        // ^ COMPILE ERROR: incompatible types: possible lossy conversion from int to byte!
        // Bytecode pushes iload_0, iload_1, executes 32-bit 'iadd' -> result type is int (140).

        // SURPRISE: Compound assignment (+=) compiles cleanly by injecting an implicit cast!
        a += b;
        // JLS 15.26.2 defines 'E1 op= E2' as 'E1 = (T) ((E1) op (E2))'
        // Bytecode: iload_0 -> iload_1 -> iadd (140) -> i2b (-116!) -> istore_0
        // Silently truncates 140 into -116!
    }
}

Also beware of Integer.MIN_VALUE asymmetry: two's complement holds one extra negative value (`-2,147,483,648` vs `+2,147,483,647`). Consequently, `Math.abs(Integer.MIN_VALUE)` and `-Integer.MIN_VALUE` both evaluate to negative `-2,147,483,648`! Never write `Math.abs(key.hashCode()) % buckets` in a custom sharder—use `(key.hashCode() & 0x7fffffff) % buckets` or `Math.floorMod(key.hashCode(), buckets)`.

4. Idiomatic Java 21 Safe Numeric Engineering

In production backends, replace silent wrap-around and naive float comparisons with overflow-checked `Math.*Exact` intrinsics (which leverage CPU overflow flags via C2 intrinsics!), unsigned right-shifts, and `Double.compare`: 

// IDIOMATIC JAVA 21: Overflow-checked math, safe midpoints, and NaN-safe comparisons
public final class SafeNumericOps {
    private SafeNumericOps() {}

    public static long retentionToMicros(int days) {
        // Leading 24L forces 64-bit promotion across the entire chain; multiplyExact guards bounds
        return Math.multiplyExact((long) days, 24L * 60L * 60L * 1_000_000L);
    }

    public static int safeMidpoint(int low, int high) {
        // Unsigned right-shift treats the 33rd carry bit properly for non-negative indices
        return (low + high) >>> 1;
    }

    public static int safeShardIndex(int rawHash, int shardCount) {
        // Math.floorMod always returns [0, shardCount - 1], even for Integer.MIN_VALUE!
        return Math.floorMod(rawHash, shardCount);
    }

    public static boolean isMetricValidAndPositive(double metric) {
        // Double.isFinite rejects both NaN and +/-Infinity in a single bitmask check
        return Double.isFinite(metric) && Double.compare(metric, 0.0d) > 0;
    }
}
