The Object Contract: equals(), hashCode() & toString()

Master the equals() and hashCode() contract, mutable key memory leaks, and HashMap TreeBin collision treeification.

1. The Unbreakable Rule: The equals & hashCode Contract

In Java, the contract between equals() and hashCode() is the cornerstone of hash-based collections (HashMap, HashSet, ConcurrentHashMap):

  • Consistent Equality: If a.equals(b) == true, then a.hashCode() == b.hashCode() MUST ALWAYS be true.
  • Collision Tolerance: If a.hashCode() == b.hashCode(), a.equals(b) does NOT have to be true (hash collision).
// ANTI-PATTERN: Overriding equals() without overriding hashCode()
public class BrokenUser {
    private final String id;
    public BrokenUser(String id) { this.id = id; }
    @Override
    public boolean equals(Object o) {
        return (o instanceof BrokenUser other) && Objects.equals(this.id, other.id);
    }
    // BUG: Missing hashCode()! Uses System.identityHashCode (memory address)
}

Set<BrokenUser> set = new HashSet<>();
set.add(new BrokenUser("USR-1"));
boolean found = set.contains(new BrokenUser("USR-1")); // FALSE! Hash code mismatch!

2. The Mutable Key Disaster in Hash Collections

If an object is used as a key in a HashMap or HashSet and its fields are mutated after insertion, its computed hash bucket changes. The object becomes permanently lost inside the map: 

// PRODUCTION TRAP: Mutating keys after insertion
public class MutableKey {
    private int id;
    public MutableKey(int id) { this.id = id; }
    public void setId(int id) { this.id = id; }
    @Override public int hashCode() { return id; }
    @Override public boolean equals(Object o) { return (o instanceof MutableKey other) && this.id == other.id; }
}

Map<MutableKey, String> map = new HashMap<>();
MutableKey k = new MutableKey(1);
map.put(k, "SessionData");
k.setId(2); // MUTATION!
// map.get(k) is now NULL! HashMap searches bucket 2, but entry sits in bucket 1!
⚠ Memory Leak from Mutated Keys
In the code above, not only does map.get(k) return null, but map.remove(k) also fails! The entry cannot be deleted, causing a silent memory leak on the heap. Always use immutable types (like records, String, or UUID) as map keys.

3. Under the Hood: HashMap TreeBins & Hash Flooding (DoS)

Prior to Java 8, hash collisions caused buckets to degrade into O(N) linked lists, exposing servers to algorithmic complexity DoS attacks. In Java 8 through 21: 

// Under high collision, HashMap transforms linked bins into Red-Black TreeBins:
// TREEIFY_THRESHOLD = 8 (converts linked list to red-black tree: O(log N) search)
// UNTREEIFY_THRESHOLD = 6 (shrinks back to linked list during resizing)
