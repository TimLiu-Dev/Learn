Apache Spark on the JVM: Catalyst DAG, Java Dataset API, Shuffle Skew & Tungsten Off-Heap

Master Apache Spark Catalyst DAG optimizer, Project Tungsten off-heap memory, and data skew salting.

1. The Apache Spark JVM Architecture: Catalyst & Tungsten

Apache Spark executes distributed computations across clusters. Its core performance engines rely on two subsystems:

  • Catalyst Optimizer: Transforms DataFrame transformations into an optimized Directed Acyclic Graph (DAG) of logical and physical execution plans with predicate pushdown and projection pruning.
  • Project Tungsten: Bypasses JVM Garbage Collection by managing off-heap binary memory pages directly using native sun.misc.Unsafe, and compiling entire query stages into native machine code (Whole-Stage Code Generation).

2. The Data Skew Hazard & Salting Techniques

In distributed shuffle joins, Spark partitions data by hash of the join key: hash(key) % partitions. If 90% of records share the same key (e.g. null or high-volume merchant), a single executor receives 90% of the workload, freezing the job while other executors sit idle (Data Skew). Salting appends a random suffix to the key, spreading the skewed key across multiple worker partitions: 

// IDIOMATIC JAVA 21: Key Salting in Spark
Dataset<Row> saltedDf = df.withColumn(
    "salted_key",
    functions.concat(functions.col("user_id"), functions.lit("_"), functions.floor(functions.rand().multiply(10)))
);

3. Broadcast Hash Joins: Eliminating Network Shuffles

Joining two large datasets requires a Sort-Merge Join, which shuffles gigabytes of data across cluster network switches. When one table is small (<10MB default), marking it with functions.broadcast(dimDf) copies the small table to every executor, completely eliminating network shuffle overhead: 

// IDIOMATIC JAVA 21: Zero-shuffle Broadcast Hash Join
Dataset<Row> joined = largeOrders.join(
    functions.broadcast(smallCurrencies), // Broadcasts small table to all executors!
    "currency_code"
);
