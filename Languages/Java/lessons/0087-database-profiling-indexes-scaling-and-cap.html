SQL Profiling (EXPLAIN ANALYZE), Index Internals, Read Replicas, Sharding & CAP

Stop guessing inside Hibernate: read PostgreSQL execution plans, design left-prefix & partial B-Tree indexes, route @Transactional(readOnly = true) traffic to replicas safely, and choose between PostgreSQL, OpenSearch, and NoSQL using CAP/PACELC.

1. Reading EXPLAIN (ANALYZE, BUFFERS) & Why Queries Turn into Seq Scan

Even with OSIV=false and keyset pagination (Lesson 0063), a single unindexed JPA query scanning 20 million rows stalls PostgreSQL CPU and saturates HikariCP. Never guess index usage—run EXPLAIN (ANALYZE, BUFFERS) directly on the SQL emitted by Hibernate: 

-- ANTI-PATTERN: Non-sargable predicate + missing left-prefix column forces Seq Scan!
CREATE INDEX idx_orders_tenant_status_created ON orders (tenant_id, status, created_at DESC);

-- 1. Skips leading column tenant_id -> cannot seek B-Tree efficiently!
-- 2. LOWER(customer_email) wraps the column in a function -> bypasses B-Tree on customer_email!
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, total_cents FROM orders
WHERE status = 'PAID' AND LOWER(customer_email) = 'alice@acme.io'
ORDER BY created_at DESC LIMIT 20;
-- Plan output: Seq Scan on orders (actual time=0.04..412.80 rows=20 loops=1)
--              Buffers: shared hit=1200 read=48920  <-- 380 MB scanned for 20 rows!

In a composite B-Tree index (A, B, C), PostgreSQL sorts tuples lexicographically by A, then B, then C. Equality predicates must match from the leftmost prefix (A, then B), with at most one trailing range/sort column (C). For rare hot states like status = 'PENDING', a partial index shrinks index RAM by 95%: 

-- IDIOMATIC POSTGRESQL: Sargable left-prefix + partial index + covering INCLUDE
CREATE INDEX idx_orders_pending_tenant
    ON orders (tenant_id, created_at DESC)
    INCLUDE (total_cents)
    WHERE status = 'PENDING'; -- Tiny partial index!

-- Store normalized email (or index LOWER(customer_email) explicitly) so equality is sargable:
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, total_cents FROM orders
WHERE tenant_id = 'T-42' AND status = 'PENDING'
ORDER BY created_at DESC LIMIT 20;
-- Plan output: Index Only Scan using idx_orders_pending_tenant (actual time=0.03..0.09 rows=20)
--              Heap Fetches: 0   Buffers: shared hit=4

2. Scaling Relational DBs: Read Replicas, Partitioning vs. Sharding & CAP/PACELC

When a single PostgreSQL primary node saturates on read traffic or table size, senior engineers scale along three distinct steps before jumping to NoSQL:

Scaling MechanismHow It WorksFatal Production Trap
Read Replicas (AbstractRoutingDataSource)Routes @Transactional(readOnly = true) queries to streaming async replicas.Replication Lag (Read-Your-Own-Writes): User saves an order on Primary, redirects immediately, and Replica returns 404 50ms later!
Table Partitioning (Declarative)Splits one logical table (e.g., events_2027_01) by time or tenant inside one PostgreSQL instance.Queries missing the partition key scan every child partition (partition pruning fails).
Horizontal ShardingDistributes rows across independent database clusters by shard key (e.g., tenant_id).Cross-shard JOINs and distributed ACID transactions become slow or impossible; resharding is painful.
 
// IDIOMATIC SPRING: LazyConnectionDataSourceProxy + ReadOnly Replica Routing
// CRITICAL: Wrap routing DataSource in LazyConnectionDataSourceProxy so Spring evaluates
// TransactionSynchronizationManager.isCurrentTransactionReadOnly() BEFORE borrowing a JDBC connection!
public final class ReplicaRoutingDataSource extends AbstractRoutingDataSource {
    public enum Role { PRIMARY, REPLICA }

    @Override
    protected Object determineCurrentLookupKey() {
        boolean isReadOnly = TransactionSynchronizationManager.isCurrentTransactionReadOnly();
        boolean pinnedToPrimary = WritePinContext.isPinnedPrimary(); // e.g., post-mutation flag in same request!
        return (isReadOnly && !pinnedToPrimary) ? Role.REPLICA : Role.PRIMARY;
    }
}
⚡ CAP & PACELC + Polyglot Storage Decision Rule in 2027
Under a network partition (CAP), distributed stores choose CP (PostgreSQL synchronous commit, Kafka acks=all + min.insync.replicas) or AP (Redis async replicas, DynamoDB eventual reads). In normal operation without partitions (PACELC), they trade Latency vs. Consistency. Reach for Elasticsearch/OpenSearch for multi-field fuzzy full-text search & facets, Redis for sub-millisecond TTL/rate-limit counters, and keep source-of-truth business state in PostgreSQL (including JSONB and pgvector) until scale genuinely demands sharding or MongoDB.
