Deep Java 21 Pattern Matching & Algebraic Domain Modeling

Master Java 21 Record Patterns (JEP 440), exhaustive switch pattern matching (JEP 441), when guards, and modeling business domains so invalid states are unrepresentable at compile time.

1. The Naive Inheritance Anti-Pattern vs Algebraic Domain Modeling

In legacy Java, domain models frequently relied on mutable open class hierarchies with nullable fields or error-prone type casts (instanceof followed by an explicit downcast). This forced defensive null checks across every service layer.

Modern Java 21 introduces Algebraic Data Types (ADTs) via Sealed Interfaces (Sum types) and Records (Product types). By making illegal states unrepresentable, compiler exhaustiveness guarantees that every domain variation is handled: 

// ANTI-PATTERN: Mutable state with nullable fields allowing illegal combinations
public class LegacyPayment {
    public String type; // "CARD", "CRYPTO", "INVOICE"
    public String cardNumber; // null if CRYPTO
    public String cryptoAddress; // null if CARD
    public Long amountCents;
    public boolean isAuthorized; // Can be true even if cardNumber is null!
}

The idiomatic Java 21 LTS solution models this with sealed interfaces and records: 

// IDIOMATIC JAVA 21: Algebraic Data Type (Sum of Products)
public sealed interface PaymentMethod permits CreditCard, Crypto, BankWire {}

public record CreditCard(String panLast4, String expiry, String cardholder) implements PaymentMethod {}
public record Crypto(String walletAddress, String network) implements PaymentMethod {}
public record BankWire(String iban, String bic) implements PaymentMethod {}

2. Under the Hood: JEP 440 Record Patterns & Nested Deconstruction

Java 21 record patterns deconstruct record components directly in pattern matching without accessor boilerplate. The JVM matches types and binds variables simultaneously: 

public record Money(long cents, String currency) {}
public record Order(String id, PaymentMethod payment, Money total) {}

// Nested Record Pattern Matching with 'when' guards:
public String auditOrder(Order order) {
    return switch (order) {
        case Order(var id, CreditCard(var pan, var exp, var name), Money(var cents, "USD")) when cents > 100_000L ->
            "High-value domestic card payment: " + pan + " for $" + (cents / 100.0);

        case Order(var id, Crypto(var wallet, var network), Money(var cents, var curr)) ->
            "Crypto settlement on " + network + " for " + wallet;

        case Order(var id, BankWire(var iban, _), var total) ->
            "Pending wire verification for IBAN: " + iban;

        case Order(var id, CreditCard(var pan, _, _), var total) ->
            "Standard card order: " + id + " using " + pan;
    };
}
⚡ The Null Safety & Exhaustiveness Invariant
In modern switch expressions, if the selector expression evaluates to null, a NullPointerException is thrown before entering the switch—unless you explicitly define an arm: case null -> .... Furthermore, when switching over a sealed type, the compiler verifies that all permitted subtypes are covered. No default is required!

3. The Unnamed Pattern & Guard Sequencing

When you only care about specific fields during deconstruction, Java 21 allows using the unnamed pattern variable (_) to omit unused parameters, preventing variable pollution: 

// IDIOMATIC JAVA 21: Unnamed variables and guarded fall-through
public String summarize(PaymentMethod payment) {
    return switch (payment) {
        case CreditCard(var pan, _, _) -> "Card ending in " + pan;
        case Crypto(_, var net) -> "Crypto on " + net;
        case BankWire(var iban, _) -> "Wire to " + iban;
    };
}
