Heaps, Custom PriorityQueues & The Two-Heap Streaming Median Pattern

Master implicit array binary heaps, O(N) Floyd heapification vs O(N log K) bounded Top-K eviction, overflow-safe comparators, and O(1) streaming median invariants.

1. Inside java.util.PriorityQueue: Contiguous Array Binary Heaps

Unlike TreeSet or TreeMap—which allocate a separate 40-byte Red-Black tree node object per entry and chase pointers across fragmented heap memory—java.util.PriorityQueue<E> stores elements in a single contiguous Object[] queue array representing a complete binary min-heap. Because levels are packed left-to-right without gaps, no parent or child pointers are stored; tree navigation uses pure bit-shift index arithmetic:

  • Left child of index i: (i << 1) + 1
  • Right child of index i: (i << 1) + 2
  • Parent of index i: (i - 1) >>> 1
  • Min-heap invariant: Every parent satisfies cmp.compare(queue[parent], queue[child]) <= 0. Consequently, index 0 is guaranteed to hold the minimum element, while sibling and cousin ordering is intentionally left partial.
Operation / Constructor Time Complexity JVM & Algorithmic Mechanics
peek() O(1) Reads queue[0] directly (returns null if empty).
offer(e) / add(e) O(log N) Appends at queue[size] and runs siftUp along at most log2(N) ancestors; rejects null with NullPointerException.
poll() O(log N) Extracts queue[0], moves last element queue[size - 1] to root, and runs siftDown.
new PriorityQueue<>(Collection) O(N) Copies array in bulk and runs bottom-up Floyd heapify() from (size >>> 1) - 1 down to 0 (unless input is already a SortedSet or PriorityQueue).
remove(Object o) / contains(o) O(N) Senior Trap: Performs a linear indexOf(o) scan across queue[] before O(log N) sift repair!
for (E item : pq) O(N) Senior Trap: Iterates raw queue[] level-order array—NOT sorted priority order!

2. Production & Interview Traps: Subtraction Overflow, Full-Stream Heap Blowup & remove()

Three mistakes repeatedly sink senior candidates and cause production incidents when working with heaps in Java:

  1. Comparator Subtraction Overflow: Writing (a, b) -> b - a to build a max-heap silently overflows 32-bit signed integers whenever inputs span positive and negative values (for example, b = 2_000_000_000 and a = -1_000_000_000 produces negative -1_294_967_296, violating comparator transitivity and corrupting the heap).
  2. Unbounded Max-Heap for Top-K: Pushing all N stream elements into a max-heap to extract the top K wastes O(N) heap memory and O(N log N) insertions. When N = 50_000_000 telemetry events and K = 100, an unbounded heap triggers Old-Gen GC thrashing, whereas a bounded min-heap of capacity K + 1 uses O(K) memory and O(N log K) time.
  3. Linear pq.remove(obj) Inside Event Loops: Updating priorities by calling pq.remove(oldEntry) degrades a O(N log N) algorithm into O(N2). Prefer lazy deletion (pushing the updated entry and discarding stale entries on poll()) or an indexed heap.
import java.util.ArrayList;
import java.util.List;
import java.util.PriorityQueue;

public class BrokenHeapAntipatterns {

    // ANTI-PATTERN: Unbounded heap + overflowing comparator + unsorted iterator assumption
    public static List<Integer> brokenTopKLargest(int[] metrics, int k) {
        // BUG 1: (a, b) -> b - a overflows when b = Integer.MAX_VALUE and a = -10!
        PriorityQueue<Integer> maxHeap = new PriorityQueue<>((a, b) -> b - a);

        // BUG 2: Inserts all N items -> O(N) memory and O(N log N) time instead of O(K) and O(N log K)
        for (int m : metrics) {
            maxHeap.offer(m);
        }

        // BUG 3: Enhanced for-loop reads raw heap backing array, NOT sorted descending order!
        List<Integer> wrongResult = new ArrayList<>();
        for (int val : maxHeap) {
            if (wrongResult.size() == k) break;
            wrongResult.add(val);
        }
        return wrongResult;
    }
}
⚠ Why Top-K Largest Requires a Min-Heap (And Vice Versa)
To retain the K largest elements seen so far, you need O(1) access to the weakest member of your top-K club so you can evict it whenever a stronger candidate arrives. The weakest of the K largest elements is their minimum—so a min-heap of size K guards the gate! Conversely, retaining the K smallest elements requires a max-heap of size K.

3. Under the Hood: O(N) Bottom-Up Heapify vs O(N log N) Sequential Insertion

When all N elements are already in a Collection, passing that collection directly into new PriorityQueue<>(collection) runs Robert Floyd's bottom-up heapify() in O(N) linear time rather than O(N log N). Why? In a binary tree of N nodes, half the nodes (N / 2) are leaves of height 0 that require zero swaps, a quarter (N / 4) have height 1 and sift down at most 1 level, N / 8 sift down at most 2 levels, and only the single root sifts down log2(N) levels. Summing (N / 2h+1) * h over all heights h >= 0 converges strictly below 2N comparisons! 

// Simplified OpenJDK java.util.PriorityQueue Floyd heapify & siftDown mechanics
final class HeapMechanicsShowcase {

    static void heapify(int[] queue, int size) {
        // Start at the last non-leaf parent ((size >>> 1) - 1) and sift down to root 0.
        // Leaves [size >>> 1 .. size - 1] already satisfy the heap invariant trivially!
        for (int i = (size >>> 1) - 1; i >= 0; i--) {
            siftDown(i, queue[i], queue, size);
        }
    }

    static void siftDown(int k, int key, int[] queue, int size) {
        int half = size >>> 1; // Loop while node k has at least one child
        while (k < half) {
            int child = (k << 1) + 1; // Assume left child is smaller
            int smallestChildVal = queue[child];
            int right = child + 1;

            if (right < size && Integer.compare(smallestChildVal, queue[right]) > 0) {
                child = right;
                smallestChildVal = queue[right];
            }
            if (Integer.compare(key, smallestChildVal) <= 0) {
                break; // Heap order restored
            }
            queue[k] = smallestChildVal; // Pull smaller child up (no full 3-way swap per level!)
            k = child;
        }
        queue[k] = key; // Single final write at resting position
    }
}

Notice an important HotSpot micro-optimization in OpenJDK's siftDown: instead of performing three assignments (a full swap) at every tree level, it shifts winning children upward by one slot and writes key once at its final resting index, cutting array writes nearly in half.

4. Idiomatic Java 21: Bounded Top-K Frequent & Two-Heap Streaming Median

Now let us examine two canonical patterns that appear equally in Staff/Senior interviews and real-time telemetry services:

  1. Bounded Min-Heap for Top-K Frequent Items (O(N log K)): Aggregate frequencies in a HashMap<T, Integer> in O(N) using merge(item, 1, Integer::sum), then feed entries through a min-heap ordered by Comparator.comparingInt(Map.Entry::getValue), polling whenever heap.size() > k.
  2. The Two-Heap Pattern (MedianFinder — O(log N) insert, O(1) query): Partition a dynamic stream into two halves:
    • lowerHalf: a max-heap (Comparator.reverseOrder()) holding the smaller half of numbers, exposing the largest of the small numbers at its root.
    • upperHalf: a min-heap holding the larger half of numbers, exposing the smallest of the large numbers at its root.
    By routing every new value through lowerHalf into upperHalf, and rebalancing whenever lowerHalf.size() < upperHalf.size(), we guarantee two invariants simultaneously: (a) every value in lowerHalf is <= every value in upperHalf, and (b) lowerHalf.size() equals either upperHalf.size() (even total) or upperHalf.size() + 1 (odd total). 
import java.util.ArrayList;
import java.util.Collections;
import java.util.Comparator;
import java.util.HashMap;
import java.util.List;
import java.util.Map;
import java.util.PriorityQueue;

public final class StreamingHeapPatterns {

    // 1. Bounded O(N log K) Top-K Frequent Endpoints
    public static List<String> topKFrequentEndpoints(List<String> logs, int k) {
        if (k <= 0 || logs.isEmpty()) return List.of();

        Map<String, Integer> counts = new HashMap<>();
        for (String endpoint : logs) {
            counts.merge(endpoint, 1, Integer::sum);
        }

        // Min-heap of capacity k + 1: lowest frequency (or reverse lexicographical tie-breaker) evicted first
        PriorityQueue<Map.Entry<String, Integer>> minHeap = new PriorityQueue<>(
            k + 1,
            Comparator.<Map.Entry<String, Integer>>comparingInt(Map.Entry::getValue)
                .thenComparing(Map.Entry::getKey, Comparator.reverseOrder())
        );

        for (Map.Entry<String, Integer> entry : counts.entrySet()) {
            minHeap.offer(entry);
            if (minHeap.size() > k) {
                minHeap.poll(); // Evict weakest candidate in O(log K)
            }
        }

        List<String> topK = new ArrayList<>(minHeap.size());
        while (!minHeap.isEmpty()) {
            topK.add(minHeap.poll().getKey());
        }
        Collections.reverse(topK); // Highest frequency first
        return topK;
    }

    // 2. Two-Heap Streaming Median (O(log N) addNum, O(1) findMedian, overflow-safe)
    public static final class MedianFinder {
        private final PriorityQueue<Integer> lowerHalf = new PriorityQueue<>(Comparator.reverseOrder());
        private final PriorityQueue<Integer> upperHalf = new PriorityQueue<>();

        public void addNum(int num) {
            // Step 1: Offer to max-heap so it bubbles against smaller half's maximum
            lowerHalf.offer(num);
            // Step 2: Move max of lowerHalf to upperHalf to enforce lowerHalf.max <= upperHalf.min
            upperHalf.offer(lowerHalf.poll());
            // Step 3: Maintain size invariant: lowerHalf.size() == upperHalf.size() (+ 0 or 1)
            if (lowerHalf.size() < upperHalf.size()) {
                lowerHalf.offer(upperHalf.poll());
            }
        }

        public double findMedian() {
            if (lowerHalf.isEmpty()) {
                throw new IllegalStateException("Cannot compute median of an empty stream");
            }
            if (lowerHalf.size() > upperHalf.size()) {
                return lowerHalf.peek();
            }
            // Cast to double BEFORE adding so two values near Integer.MAX_VALUE never overflow int!
            return ((double) lowerHalf.peek() + upperHalf.peek()) / 2.0;
        }
    }
}
💡 Production Nuance: Exact Two-Heap Median vs Approximate Quantiles
The Two-Heap pattern computes the exact median of N items using O(N) memory—ideal for bounded sliding windows or interview problems up to 106 elements. For unbounded production latency metrics (p50, p95, p99 across billions of requests in Micrometer/Prometheus), storing every observation would exhaust the heap; production telemetry libraries instead use HDR Histogram or t-digest sketches in fixed O(1) memory.
