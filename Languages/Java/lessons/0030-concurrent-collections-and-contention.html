High-Contention Concurrency: ConcurrentHashMap, LongAdder, StampedLock & Semaphore

Master high-contention memory patterns with LongAdder, lock-free StampedLock optimistic reads, and ConcurrentHashMap bucket contention.

1. The CAS Contention Bottleneck: AtomicLong vs LongAdder

Under high concurrency (hundreds of threads recording metrics or counters simultaneously), AtomicLong.incrementAndGet() suffers from catastrophic CAS cache-line bouncing. Multiple CPU cores repeatedly invalidate their L1/L2 caches attempting to CAS the same single memory address, causing throughput to collapse. 

// ANTI-PATTERN: Heavy CAS contention under high thread concurrency
public class MetricsCollector {
    private final AtomicLong requestCounter = new AtomicLong(); // Collapses under 64+ cores!

    public void onRequest() {
        requestCounter.incrementAndGet(); // Bus lock / cache line invalidation storm
    }
}

The idiomatic Java solution for high-write scenarios is LongAdder (and DoubleAdder). It maintains a dynamically allocated array of cell counters padded to 64 bytes (using @jdk.internal.vm.annotation.Contended) to avoid false sharing. Each thread hashes to a separate cell, converging to near-linear scaling: 

// IDIOMATIC JAVA 21: Striped counter immune to single-cell contention
public class HighThroughputMetrics {
    private final LongAdder requestCounter = new LongAdder();

    public void onRequest() {
        requestCounter.increment(); // Distributes writes across independent cache-padded cells
    }

    public long snapshot() {
        return requestCounter.sum(); // Gathers sum across all cells
    }
}

2. Under the Hood: StampedLock Optimistic Reads

ReentrantReadWriteLock permits concurrent readers, but readers still incur CPU overhead by writing to an internal synchronization counter via CAS. StampedLock provides an optimistic read mode that acquires no locks and performs no memory writes: 

// IDIOMATIC JAVA 21: Optimistic read loop without lock acquisition
public class PointTracker {
    private double x, y;
    private final StampedLock lock = new StampedLock();

    public double distanceFromOrigin() {
        long stamp = lock.tryOptimisticRead(); // Non-blocking read stamp (no lock acquired)
        double currentX = x, currentY = y;
        if (!lock.validate(stamp)) { // Check if an intervening write occurred
            stamp = lock.readLock(); // Fallback to pessimistic read lock
            try {
                currentX = x;
                currentY = y;
            } finally {
                lock.unlockRead(stamp);
            }
        }
        return Math.hypot(currentX, currentY);
    }
}
⚠ StampedLock Re-entrancy & Thread-Interruption Warning
StampedLock is NOT re-entrant! A thread holding a write lock that attempts to acquire another write lock will self-deadlock. Furthermore, never call lockInterruptibly() on StampedLock if threads might be interrupted, as historical JVM bugs caused CPU spinning.

3. ConcurrentHashMap: The Recursive computeIfAbsent Trap

In Java 8 through 21, calling ConcurrentHashMap.computeIfAbsent() locks the individual hash bucket (bin) while computing the value. If the mapping function attempts to mutate or recursively compute another key in the same map, it can cause a silent deadlock or throw IllegalStateException: 

// PRODUCTION TRAP: Recursive computeIfAbsent deadlock
ConcurrentHashMap<String, String> cache = new ConcurrentHashMap<>();
cache.computeIfAbsent("keyA", kA -> {
    return cache.computeIfAbsent("keyB", kB -> "valB"); // DEADLOCK if keyA and keyB hash to same bucket!
});
