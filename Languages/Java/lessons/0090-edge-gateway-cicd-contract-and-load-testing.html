Edge Gateways (Nginx & Spring Cloud Gateway), 12-Factor Secrets, CI/CD, Contract & Load Testing

Bridge local Docker builds to production traffic: terminate TLS at Nginx or Spring Cloud Gateway, trust X-Forwarded-* headers safely, wire GitHub Actions + Testcontainers CI/CD, and gate releases with Contract + Load tests.

1. Reverse Proxies (Nginx), Spring Cloud Gateway & Trusted X-Forwarded-*

In production Kubernetes or cloud environments, Spring Boot services sit behind a reverse proxy (Nginx, Envoy, AWS ALB) and/or an API Gateway (Spring Cloud Gateway). If your app blindly reads HttpServletRequest.getScheme() or trusts arbitrary X-Forwarded-For headers from public clients, redirect URLs break (http:// instead of https://) and IP rate-limiters get bypassed by header spoofing! 

# 1. NGINX REVERSE PROXY: TLS termination + forwarding real scheme/host
location /api/ {
    proxy_pass http://order-service:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

# 2. SPRING BOOT 4 application.yaml: Honor X-Forwarded-* ONLY from trusted internal proxies!
server:
  forward-headers-strategy: framework
  tomcat:
    remoteip:
      internal-proxies: 10\.\d{1,3}\.\d{1,3}\.\d{1,3}|172\.1[6-9]\.\d{1,3}\.\d{1,3}

For cross-cutting API concerns across dozens of microservices (JWT edge validation, tenant routing, circuit breaking, edge rate-limiting), Spring Cloud Gateway provides declarative routes without duplicating filter logic inside every downstream service. 

# SPRING CLOUD GATEWAY ROUTE + TOKEN RELAY & REDIS RATE LIMITER (application.yml)
spring:
  cloud:
    gateway:
      routes:
        - id: orders-v1
          uri: http://order-service.internal:8080
          predicates: [ Path=/api/orders/** ]
          filters:
            - TokenRelay=
            - name: RequestRateLimiter
              args: { redis-rate-limiter.replenishRate: 50, redis-rate-limiter.burstCapacity: 100 }

2. Twelve-Factor Config, PII/GDPR Hygiene & GitHub Actions CI/CD

Never bake DB passwords, JWT signing keys, or API secrets into Git or Docker images. Follow the Twelve-Factor App rule: externalize configuration via environment variables / Kubernetes Secrets / Vault, and enforce PII/GDPR compliance (mask emails/cards in logs, support tenant deletion/export). Automate every build with a repeatable GitHub Actions pipeline: 

# IDIOMATIC GITHUB ACTIONS CI/CD: Java 25 + Gradle 9 + Testcontainers + Docker
name: ci-backend
on: [push, pull_request]
jobs:
  verify:
    runs-on: ubuntu-latest # Includes Docker daemon for Testcontainers!
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '25'
      - uses: gradle/actions/setup-gradle@v4
      - run: ./gradlew test integrationTest --no-daemon

3. Contract Testing & Load Testing Before Release

End-to-end staging suites are slow and brittle. Senior backend teams pair fast CI integration tests with two specialized safety nets:

  • Consumer-Driven Contract Testing (Pact / Spring Cloud Contract / OpenAPI Diff): Android and web consumers publish exact JSON expectations; the backend verifies every PR against those contracts in seconds without spinning up 15 services.
  • Load & Stress Testing (k6 / Gatling): Never measure only average latency—assert p95 / p99 tail latency, HikariCP connection wait time, and error rate under 2x expected peak load before shipping!
// IDIOMATIC k6 LOAD TEST: Assert p99 latency & error budget in CI/staging
import http from 'k6/http';
import { check } from 'k6';

export const options = {
  vus: 50,
  duration: '60s',
  thresholds: {
    http_req_failed: ['rate<0.01'],     // <1% errors allowed
    http_req_duration: ['p(99)<250'],   // 99th percentile < 250ms!
  },
};

export default function () {
  const res = http.get('https://staging.acme.io/api/v1/orders?limit=20');
  check(res, { 'status is 200': (r) => r.status === 200 });
}
