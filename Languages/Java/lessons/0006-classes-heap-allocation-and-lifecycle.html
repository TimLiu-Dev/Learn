Classes, Heap Allocation & Object Lifecycle

Master HotSpot object headers (Mark Word, Klass pointer), field & constructor initialization sequence, and static factory methods.

1. The Object Header: Mark Word & Klass Pointer

Every object allocated on the Java heap carries an Object Header consisting of:

  • Mark Word (8 bytes): Identity hash code, GC age bits (4 bits = max age 15 before Tenuring), locking state (biased, thin, fat monitor), and GC flags.
  • Klass Word (4 bytes with CompressedClassPointers): Points to the class metadata in Metaspace.
  • Array Length (4 bytes): Present only on array instances.
// ANTI-PATTERN: Massive memory bloat from wrapper object overhead
// Integer object: 8 bytes (mark) + 4 bytes (klass) + 4 bytes (int) = 16 bytes!
// Primitive int: exactly 4 bytes. Storing 10M Integers consumes 160MB vs 40MB!

2. Constructor Chaining & Object Initialization Order

Object initialization executes in a strict deterministic sequence:

  1. Static initializers and static fields of parent, then child.
  2. Instance field initializers and instance blocks of parent.
  3. Parent class constructor body.
  4. Instance field initializers and instance blocks of child.
  5. Child class constructor body.
// PRODUCTION TRAP: Calling overridable method in constructor
public class SuperClass {
    public SuperClass() {
        init(); // DANGEROUS! Child fields not yet initialized!
    }
    public void init() {}
}

public class SubClass extends SuperClass {
    private String name = "Default";
    @Override
    public void init() {
        System.out.println(name.toUpperCase()); // CRASH! 'name' is still null here!
    }
}
⚠ Never Call Overridable Methods in Constructors
When a superclass constructor invokes an overridden method, the child's implementation executes before the child's instance field initializers have run, leading to subtle NullPointerException crashes.

3. Idiomatic Java Classes: private final Fields, this Constructors & static Factories

Unlike Kotlin's primary constructor header (class Account(val id: String, var cents: Long)), a standard Java class declares its fields inside the class body, initializes them inside an explicit constructor having the exact class name (and no return type), and exposes named static factory methods when clarity beats overloaded constructors: 

// IDIOMATIC JAVA 25 CLASS: Explicit fields, constructor chaining & static factory
public final class LedgerAccount {
    private final String id;   // 'final' = assigned once in constructor (like Kotlin 'val')
    private long balanceCents; // mutable state encapsulated behind methods

    public LedgerAccount(String id, long openingCents) {
        this.id = (id == null || id.isBlank()) ? "UNASSIGNED" : id.trim();
        this.balanceCents = Math.max(0L, openingCents);
    }

    public static LedgerAccount openEmpty(String id) { // Named static factory (replaces companion object)
        return new LedgerAccount(id, 0L);
    }

    public String getId() { return id; }
    public long getBalanceCents() { return balanceCents; }
    public void deposit(long cents) { this.balanceCents += Math.max(0L, cents); }
}
// (Note: For pure immutable data carriers, Lesson 0012 introduces Java 'record's!)
🔗 Android / Kotlin Bridge: companion object & Inner this$0
Where Kotlin puts factory helpers in a companion object, Java uses static methods and fields directly on the class. Also remember Android's classic Handler/ViewHolder leak: a non-static nested class in Java holds an implicit this$0 pointer to its outer instance unless marked static class (unlike Kotlin nested classes, which are static by default unless marked inner).
