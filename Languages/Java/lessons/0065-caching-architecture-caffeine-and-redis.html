Multi-Tier Caching: Caffeine (W-TinyLFU), Redis, Stampede Protection & After-Commit Eviction

Architect high-hit-ratio L1/L2 caches in Java 25, defeat cache stampedes, penetration, and avalanches, and eliminate stale-read database race conditions.

1. The Naive @Cacheable Production Trap

Slapping @Cacheable("catalog") onto a Spring service backed by default RedisCacheManager looks effortless in staging and causes catastrophic outages under real traffic. Default Spring Redis configuration uses JdkSerializationRedisSerializer, which writes brittle Java bytecode streams tied to serialVersionUID, bloats payload sizes by 3–5x, and breaks rolling deployments whenever a DTO field changes.

Even worse, four subtle concurrency and distributed-systems hazards lurk inside naive cache-aside code: 

// ANTI-PATTERN: Four production outages waiting to happen in 25 lines
@Service
public class NaiveCatalogService {

    @Autowired private RedisTemplate<Object, Object> redisTemplate; // Trap 1: JDK binary serialization!
    @Autowired private ProductRepository repository;

    // Trap 2: No sync=true -> 5,000 virtual threads stampede PostgreSQL when a hot SKU expires!
    // Trap 3: Fixed TTL across bulk-warmed keys -> Cache Avalanche when all keys expire simultaneously!
    @Cacheable(value = "products", key = "#sku")
    public ProductDto getProduct(String sku) {
        return repository.findBySku(sku)
            .map(ProductDto::from)
            .orElse(null); // Trap 4: Returning null allows Cache Penetration on random/attack SKUs!
    }

    @Transactional
    public void updatePrice(String sku, BigDecimal newPrice) {
        repository.updatePriceBySku(sku, newPrice);
        // Trap 5: Evicting BEFORE the DB transaction commits!
        // A concurrent reader misses Redis, reads the OLD committed price from PostgreSQL,
        // and writes the stale price right back into Redis until TTL expiry!
        redisTemplate.delete("products::" + sku);
    }
}
⚠ The Pre-Commit Cache Eviction Race Condition

Under PostgreSQL's default READ COMMITTED isolation, uncommitted writes from Thread A are invisible to Thread B. If Thread A deletes the Redis key inside @Transactional before COMMIT finishes on the wire, Thread B suffers a cache miss, queries PostgreSQL (receiving the old row), and repopulates Redis with stale data that persists for the entire TTL.

2. Under the Hood: Caffeine W-TinyLFU & Multi-Tier L1/L2 Mechanics

Why is Caffeine the undisputed standard for in-heap Java caching over legacy ConcurrentHashMap + LRU wrappers or Guava Cache? Classic LRU suffers from scan pollution: a single batch reporting job scanning 100,000 cold keys flushes your hottest working set out of memory. Pure LFU suffers from the opposite flaw: an item that went viral yesterday accumulates 1,000,000 hits and squats in heap long after traffic moves on, plus maintaining exact per-key frequency heaps costs O(log N) under lock contention.

Caffeine implements Window-TinyLFU (W-TinyLFU) with lock-free striped ring buffers, achieving near-optimal hit ratios in O(1) time and 8 bytes of frequency state per capacity slot: 

// Caffeine W-TinyLFU Memory & Admission Pipeline:
//
// Incoming Read/Write --> [ Striped RingBuffer ] (lock-free CAS, avoids monitor contention)
//                                  |
//                      (Async drain on maintenance)
//                                  v
// +-----------------------+    Victim     +------------------------------+
// | 1% Window Cache (LRU) | ------------> | TinyLFU Admission Filter     |
// | Absorbs bursty scans! |               | 4-bit Count-Min Sketch       |
// +-----------------------+               | Periodically halves all      |
//                                         | counters (aging out old hot) |
//                                         +--------------+---------------+
//                                                        |
//                        Compare sketch(candidate) vs sketch(probationVictim)
//                                                        v
//                       +------------------------------------------------+
//                       | 99% Segmented LRU Main Space                   |
//                       |  - 20% Probationary Segment (new admissions)   |
//                       |  - 80% Protected Segment (promoted on 2nd hit) |
//                       +------------------------------------------------+

In high-throughput microservices, combining an L1 In-Heap Caffeine Cache with an L2 Distributed Redis Cache gives sub-microsecond hot-key reads without melting Redis network I/O on viral keys (like a flash-sale homepage banner):

Dimension L1: In-Heap (Caffeine) L2: Distributed (Redis) Defense Against Failure Modes
Read Latency ~50–150 ns (direct OOP reference) ~0.8–2.5 ms (TCP + JSON parse) Stampede (Hot Key Expiry): Coalesce concurrent misses with Caffeine AsyncLoadingCache single-flight or @Cacheable(sync = true); proactively reload via refreshAfterWrite.

3. Idiomatic Java 25 Production Solution: Single-Flight, Typed JSON & AFTER_COMMIT

To build a rock-solid two-tier cache in Spring Boot 4 and Java 25:

  • Use Caffeine.newBuilder().maximumSize(...).refreshAfterWrite(...).buildAsync(...) so concurrent Virtual Threads requesting the same missing key share a single in-flight CompletableFuture, while stale-while-revalidate background refreshes hide database latency on hot keys.
  • Use StringRedisTemplate with explicit Jackson JSON serialization, negative-cache sentinels, and randomized TTL jitter.
  • Emit an immutable Java 25 record domain event inside @Transactional and evict Redis + local Caffeine inside @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT) so eviction happens strictly after PostgreSQL commits the new row.
import tools.jackson.databind.json.JsonMapper;
import com.github.benmanes.caffeine.cache.AsyncLoadingCache;
import com.github.benmanes.caffeine.cache.Caffeine;
import java.math.BigDecimal;
import java.time.Duration;
import java.util.Optional;
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.Executor;
import java.util.concurrent.Executors;
import java.util.concurrent.ThreadLocalRandom;
import org.springframework.context.ApplicationEventPublisher;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.transaction.event.TransactionPhase;
import org.springframework.transaction.event.TransactionalEventListener;

public record ProductView(String sku, String title, BigDecimal price) {}
public record ProductUpdatedEvent(String sku) {}

@Service
public class ResilientCatalogCacheService {

    private static final String NEGATIVE_SENTINEL = "__MISSING__";
    private static final Duration REDIS_BASE_TTL = Duration.ofMinutes(15);
    private static final Duration NEGATIVE_TTL = Duration.ofSeconds(30);

    private final StringRedisTemplate redis;
    private final JsonMapper jsonMapper;
    private final ProductRepository repository;
    private final ApplicationEventPublisher events;
    private final AsyncLoadingCache<String, Optional<ProductView>> l1Cache;

    public ResilientCatalogCacheService(
            StringRedisTemplate redis,
            JsonMapper jsonMapper,
            ProductRepository repository,
            ApplicationEventPublisher events) {
        this.redis = redis;
        this.jsonMapper = jsonMapper;
        this.repository = repository;
        this.events = events;

        Executor vtExecutor = Executors.newVirtualThreadPerTaskExecutor();
        this.l1Cache = Caffeine.newBuilder()
            .maximumSize(10_000) // Hard heap bound via W-TinyLFU
            .refreshAfterWrite(Duration.ofSeconds(30)) // Async background refresh for hot keys
            .expireAfterWrite(Duration.ofMinutes(2))   // Hard staleness ceiling per pod
            .recordStats()                             // Expose hit/miss/eviction to Micrometer
            .executor(vtExecutor)
            .buildAsync((sku, executor) -> CompletableFuture.supplyAsync(() -> loadFromL2OrDb(sku), executor));
    }

    public Optional<ProductView> findBySku(String sku) {
        // Single-flight guarantee: 1,000 concurrent misses on the same SKU join ONE CompletableFuture!
        return l1Cache.get(sku).join();
    }

    private Optional<ProductView> loadFromL2OrDb(String sku) {
        String redisKey = "catalog:v1:sku:" + sku;
        String rawJson = redis.opsForValue().get(redisKey);

        if (NEGATIVE_SENTINEL.equals(rawJson)) {
            return Optional.empty(); // Defeats Cache Penetration without hitting PostgreSQL
        }
        if (rawJson != null) {
            return Optional.of(deserialize(rawJson));
        }

        Optional<ProductView> dbResult = repository.findBySku(sku).map(ProductView::fromEntity);
        if (dbResult.isPresent()) {
            long jitterSeconds = ThreadLocalRandom.current().nextLong(0, 120);
            redis.opsForValue().set(
                redisKey,
                serialize(dbResult.get()),
                REDIS_BASE_TTL.plusSeconds(jitterSeconds) // Defeats Cache Avalanche
            );
        } else {
            redis.opsForValue().set(redisKey, NEGATIVE_SENTINEL, NEGATIVE_TTL);
        }
        return dbResult;
    }

    @Transactional
    public void updatePrice(String sku, BigDecimal newPrice) {
        repository.updatePriceBySku(sku, newPrice);
        // Recorded in Spring transaction synchronization; does NOT fire if transaction rolls back!
        events.publishEvent(new ProductUpdatedEvent(sku));
    }

    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void onProductUpdated(ProductUpdatedEvent event) {
        redis.delete("catalog:v1:sku:" + event.sku());
        l1Cache.synchronous().invalidate(event.sku());
        redis.convertAndSend("catalog:invalidation", event.sku()); // Fan out L1 eviction to peer pods
    }

    private String serialize(ProductView view) { /* Jackson writeValueAsString */ return ""; }
    private ProductView deserialize(String json) { /* Jackson readValue */ return null; }
}
💡 Senior Operational Rule: Always Bound maximumSize or maximumWeight

Never configure an in-heap Caffeine cache using only expireAfterWrite! If an attacker or batch job requests 5,000,000 distinct keys inside a 5-minute TTL window, an unbounded heap cache triggers a fatal OutOfMemoryError: Java heap space before time-based expiration can reclaim entries.
