Collections Internals: HashMap Treeification, Load Factor & ArrayDeque

Master Collections Framework internals, CPU cache locality of ArrayList vs LinkedList, and ArrayDeque.

1. The Cache Locality Myth: ArrayList vs LinkedList

In legacy computer science courses, LinkedList is often taught as superior for insertions/deletions (O(1)). In production Java runtimes on modern hardware, ArrayList almost always outperforms LinkedList:

  • CPU Cache Locality: ArrayList stores contiguous memory in an array. When CPU cores fetch a cache line (64 bytes), adjacent elements are pre-fetched into L1/L2 cache.
  • Pointer Chasing & Node Overhead: LinkedList allocates a separate Node object per element (24 bytes overhead per node). Traversing it causes constant CPU cache misses!
// ANTI-PATTERN: Using LinkedList for queues or stacks
LinkedList<Order> list = new LinkedList<>(); // Heavy GC allocation pressure per node!

// IDIOMATIC JAVA 25: Contiguous ring-buffer ArrayDeque for Stack and Queue
ArrayDeque<Order> queue = new ArrayDeque<>(); // Zero node object allocation!
🔗 Kotlin → Java 25 Syntax Bridge: No [] Bracket Indexing on Java List or Map!
One of the biggest muscle-memory surprises when switching from Kotlin to Java is that Java Collections do not support [] bracket indexing (only raw arrays int[] / String[] use arr[i]). In Java:
• List: Kotlin list[i] → Java list.get(i); Kotlin list[i] = v → Java list.set(i, v); Kotlin list.size → Java list.size().
• Map: Kotlin map[k] → Java map.get(k) (or map.getOrDefault(k, def)); Kotlin map[k] = v → Java map.put(k, v).

2. Map<K, V> & Set<E>: Everyday Java 25 Idioms & HashMap Treeification

In backend services, HashMap, LinkedHashMap (insertion-ordered), and HashSet (backed by a HashMap) power O(1) indexing, deduplication, and grouping. Coming from Kotlin (map[k] = v, getOrPut), master the modern Java Map API: 

// IDIOMATIC JAVA 25 MAP & SET PATTERNS:
Map<String, Integer> counts = new HashMap<>();
counts.merge("ORD-1", 1, Integer::sum); // Atomic-style upsert: sets 1 if absent, else old + 1!
int hits = counts.getOrDefault("MISSING", 0);

Map<String, List<String>> byTenant = new HashMap<>();
// Kotlin map.getOrPut(tenant) { mutableListOf() }.add(id) -> Java computeIfAbsent:
byTenant.computeIfAbsent("acme", k -> new ArrayList<>()).add("ORD-99");

// Iterating entries cleanly (replaces Kotlin 'for ((k, v) in map)'):
for (var entry : counts.entrySet()) {
    System.out.println(entry.getKey() + "=" + entry.getValue());
}

Under the Hood of java.util.HashMap:

  • Power-of-Two Bucket Table & Hash Spreading: Capacity n is always a power of 2 (default 16). Key hashes xor upper and lower 16 bits ((h = key.hashCode()) ^ (h >>> 16)) so high-bit entropy participates in fast bitmask indexing (n - 1) & hash instead of slow CPU % division.
  • Load Factor (0.75f): When size > capacity * 0.75 (e.g., 12 entries in a 16-bucket table), HashMap doubles its array to 32. Pre-size maps of known count N via HashMap.newHashMap(N) (Java 19+/25, which divides by 0.75 automatically!).
  • Red-Black Treeification (Hash-DoS Defense): If 8+ keys collide into one bucket (TREEIFY_THRESHOLD = 8) and table capacity is at least MIN_TREEIFY_CAPACITY = 64, HashMap converts that bucket's O(N) linked list into a balanced O(log N) Red-Black TreeNode (degrading back at UNTREEIFY_THRESHOLD = 6).

3. ModCount & ConcurrentModificationException

Standard collections maintain a modCount field tracking structural modifications. Iterators check whether modCount changed during traversal: 

// PRODUCTION TRAP: Mutating collection during enhanced for-loop
List<String> names = new ArrayList<>(List.of("A", "B", "C"));
for (String name : names) {
    if (name.equals("B")) {
        names.remove(name); // CRASH! Throws ConcurrentModificationException!
    }
}

// IDIOMATIC JAVA 25: Using Collection.removeIf (single-pass O(N))
names.removeIf(name -> name.equals("B")); // Safe, optimal, fail-safe!
⚡ Collection.removeIf vs Iterator.remove
removeIf() performs removal in a single linear pass using bit shifting on ArrayList's backing array, avoiding repeated System.arraycopy calls incurred by multiple iterator.remove() invocations.

4. Modern Unmodifiable Collections: List.of, Set.of & Map.of vs Arrays.asList

Java 9+ introduced List.of(), Set.of(), and Map.of(): 

// List.of(): Truly immutable, space-efficient, rejects null elements immediately:
List<String> immutable = List.of("A", "B"); // immutable.add("C") throws UnsupportedOperationException!

// Arrays.asList(): Fixed-size view wrapping backing array (supports .set(i, val)):
List<String> fixed = Arrays.asList("A", "B"); // Allows mutation of existing elements!
