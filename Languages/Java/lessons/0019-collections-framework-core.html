Collections Internals: HashMap Treeification, Load Factor & ArrayDeque

Master Collections Framework internals, CPU cache locality of ArrayList vs LinkedList, and ArrayDeque.

1. The Cache Locality Myth: ArrayList vs LinkedList

In legacy computer science courses, LinkedList is often taught as superior for insertions/deletions (O(1)). In production Java runtimes on modern hardware, ArrayList almost always outperforms LinkedList:

  • CPU Cache Locality: ArrayList stores contiguous memory in an array. When CPU cores fetch a cache line (64 bytes), adjacent elements are pre-fetched into L1/L2 cache.
  • Pointer Chasing & Node Overhead: LinkedList allocates a separate Node object per element (24 bytes overhead per node). Traversing it causes constant CPU cache misses!
// ANTI-PATTERN: Using LinkedList for queues or stacks
LinkedList<Order> list = new LinkedList<>(); // Heavy GC allocation pressure per node!

// IDIOMATIC JAVA 21: Contiguous ring-buffer ArrayDeque for Stack and Queue
ArrayDeque<Order> queue = new ArrayDeque<>(); // Zero node object allocation!

2. ModCount & ConcurrentModificationException

Standard collections maintain a modCount field tracking structural modifications. Iterators check whether modCount changed during traversal: 

// PRODUCTION TRAP: Mutating collection during enhanced for-loop
List<String> names = new ArrayList<>(List.of("A", "B", "C"));
for (String name : names) {
    if (name.equals("B")) {
        names.remove(name); // CRASH! Throws ConcurrentModificationException!
    }
}

// IDIOMATIC JAVA 21: Using Collection.removeIf (single-pass O(N))
names.removeIf(name -> name.equals("B")); // Safe, optimal, fail-safe!
⚡ Collection.removeIf vs Iterator.remove
removeIf() performs removal in a single linear pass using bit shifting on ArrayList's backing array, avoiding repeated System.arraycopy calls incurred by multiple iterator.remove() invocations.

3. Modern Unmodifiable Collections: List.of vs Arrays.asList

Java 9+ introduced List.of(), Set.of(), and Map.of(): 

// List.of(): Truly immutable, space-efficient, rejects null elements immediately:
List<String> immutable = List.of("A", "B"); // immutable.add("C") throws UnsupportedOperationException!

// Arrays.asList(): Fixed-size view wrapping backing array (supports .set(i, val)):
List<String> fixed = Arrays.asList("A", "B"); // Allows mutation of existing elements!
