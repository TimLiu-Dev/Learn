Inter-Service HTTP: Spring RestClient, Resilience4j (Circuit Breakers, Retries) & Idempotency Keys

Master modern Spring 6 RestClient over Virtual Threads, Resilience4j CircuitBreaker fault tolerance, and atomic Idempotency Keys.

1. The Evolution from RestTemplate to RestClient (Spring 6 / Boot 3)

In Spring Framework 6 and Spring Boot 3, the legacy RestTemplate is in maintenance mode, and WebClient requires reactive Project Reactor dependencies. Spring 6 introduces RestClient: a modern, synchronous, fluent HTTP client designed specifically to run efficiently atop Java 21 Virtual Threads: 

// ANTI-PATTERN: Legacy RestTemplate with verbose exception handling
RestTemplate restTemplate = new RestTemplate();
ResponseEntity<OrderDto> resp = restTemplate.getForEntity("https://api.corp.com/orders/1", OrderDto.class);

// IDIOMATIC JAVA 21: Fluent, clean RestClient with HTTP status handling
RestClient restClient = RestClient.builder()
    .baseUrl("https://api.corp.com")
    .requestFactory(new JdkClientHttpRequestFactory()) // Uses Java 21 java.net.http.HttpClient
    .build();

OrderDto order = restClient.get()
    .uri("/orders/{id}", 1)
    .accept(MediaType.APPLICATION_JSON)
    .retrieve()
    .onStatus(HttpStatusCode::is4xxClientError, (req, res) -> {
        throw new OrderNotFoundException("Order not found: " + res.getStatusCode());
    })
    .body(OrderDto.class);

2. Fault Tolerance with Resilience4j: CircuitBreaker & Retries

Calling downstream third-party services synchronously can exhaust thread pools if the remote host experiences latency. Resilience4j provides circuit breaking with three states:

  • CLOSED: Normal operation. Calls pass through while failure rate is monitored in a sliding window.
  • OPEN: Failure rate exceeded threshold. Calls fail fast immediately without hitting downstream network.
  • HALF_OPEN: Trial period. A limited number of probe requests are permitted to test downstream recovery.
// IDIOMATIC JAVA 21: Resilience4j CircuitBreaker with Fallback
CircuitBreakerConfig config = CircuitBreakerConfig.custom()
    .failureRateThreshold(50.0f) // Open if >50% fail
    .waitDurationInOpenState(Duration.ofSeconds(10))
    .slidingWindowSize(20)
    .build();

CircuitBreaker breaker = CircuitBreaker.of("paymentService", config);
Supplier<PaymentResult> guardedCall = CircuitBreaker.decorateSupplier(breaker, () -> restClient.post()...);

3. Under the Hood: Distributed Idempotency Keys

Network requests can fail due to dropped TCP acknowledgments: the upstream server completed the charge, but the response was lost! Retrying blindly creates duplicate charges. A senior architecture enforces Idempotency Keys: 

// IDIOMATIC JAVA 21: Atomic Idempotency Check in Service Layer
public PaymentResponse processPayment(String idempotencyKey, PaymentRequest request) {
    // Atomic insert into Redis or DB with unique constraint:
    boolean isNewRequest = idempotencyStore.putIfAbsent(idempotencyKey, "IN_PROGRESS", Duration.ofMinutes(15));
    if (!isNewRequest) {
        // Return existing cached result or report in-flight status:
        return idempotencyStore.getExistingResponse(idempotencyKey);
    }

    PaymentResponse response = executePaymentGateway(request);
    idempotencyStore.saveFinalResponse(idempotencyKey, response);
    return response;
}
