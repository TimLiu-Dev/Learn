Software Architecture: Modular Monoliths (Spring Modulith), Hexagonal Boundaries & ArchUnit

Avoid premature microservice sprawl with Spring Modulith domain modules, decouple business rules from JPA/HTTP via Hexagonal Ports & Adapters, and enforce architecture automatically in CI using ArchUnit.

1. Package-by-Layer Sprawl vs. Package-by-Feature & Hexagonal Ports

In junior codebases, every class is dumped into three giant top-level buckets (controllers/, services/, repositories/) with everything marked public. Within six months, OrderService directly queries InventoryJpaRepository and mutates BillingEntity—turning the codebase into a distributed-transaction-resistant Big Ball of Mud. 

// ANTI-PATTERN: Cross-domain repository entanglement & leaked JPA entity in Domain
package com.acme.orders;

@Service
public class EntangledOrderService {
    // BUG 1: Directly reaches into another bounded context's database table!
    private final com.acme.inventory.internal.InventoryJpaRepository inventoryRepo;

    public OrderJpaEntity placeOrder(String sku) { // BUG 2: Leaks mutable JPA entity to web layer!
        inventoryRepo.decrementStockDirectly(sku);
        return new OrderJpaEntity(sku);
    }
}

Senior Java systems in 2027 combine two complementary patterns:

  • Hexagonal Architecture (Ports & Adapters): The core domain model contains pure Java 25 records, sealed interfaces, and domain services with zero imports from jakarta.persistence.*, org.springframework.web.*, or tools.jackson.*. Inbound adapters (REST controllers, Kafka listeners) call Inbound Ports (use-case interfaces), and the domain calls Outbound Ports (repository/gateway interfaces implemented by JPA or HTTP adapters).
  • Modular Monolith (Spring Modulith): Each top-level subpackage (com.acme.orders, com.acme.inventory, com.acme.billing) is a strict Application Module. Types inside com.acme.inventory.internal are invisible to other modules—verified at build time!

2. Under the Hood: Spring Modulith & `@ApplicationModuleListener`

When modules communicate inside a Modular Monolith, calling another module synchronously inside the same `@Transactional` block couples their failure blast radius. Spring Modulith solves this with its built-in Event Publication Registry: 

// IDIOMATIC SPRING MODULITH: Decoupled Domain Event + Transactional Event Publication Log
package com.acme.orders;

import org.springframework.context.ApplicationEventPublisher;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class OrderManagement {
    private final ApplicationEventPublisher events;

    public OrderManagement(ApplicationEventPublisher events) {
        this.events = events;
    }

    @Transactional
    public void completeOrder(String orderId, long amountCents) {
        // Spring Modulith automatically persists OrderCompletedEvent into EVENT_PUBLICATION table
        // inside the SAME local database transaction (built-in Outbox)!
        events.publishEvent(new OrderCompletedEvent(orderId, amountCents));
    }
}

// In com.acme.inventory.InventoryListener:
// @ApplicationModuleListener (= @Async + @Transactional(propagation = REQUIRES_NEW) + @TransactionalEventListener(AFTER_COMMIT))
// void on(OrderCompletedEvent event) { ... }

Notice what @ApplicationModuleListener gives you out of the box: (1) the event is recorded in an `event_publication` table inside the producer's DB transaction; (2) the listener runs asynchronously in a fresh transaction after commit; and (3) if the pod crashes mid-listener, Spring Modulith replays incomplete publications on startup—giving you microservice-grade isolation inside a single deployable JAR!

3. Automated Architecture Enforcement in JUnit: ApplicationModules & ArchUnit

Architectural diagrams on a wiki rot within weeks unless enforced by the CI test suite. Senior teams fail the build automatically whenever a developer imports an internal class or leaks a framework annotation into the pure domain layer: 

// IDIOMATIC JAVA 25: CI Architecture Gate with Spring Modulith & ArchUnit
import com.tngtech.archunit.core.importer.ClassFileImporter;
import com.tngtech.archunit.lang.syntax.ArchRuleDefinition;
import org.junit.jupiter.api.Test;
import org.springframework.modulith.core.ApplicationModules;

class ArchitectureVerificationTest {
    @Test
    void verifyModularBoundariesAndCyclicDependencies() {
        // Rejects cycles between modules and illegal imports of other modules' .internal packages!
        ApplicationModules.of(AcmeApplication.class).verify();
    }

    @Test
    void domainMustNotDependOnWebOrJpaFrameworks() {
        var classes = new ClassFileImporter().importPackages("com.acme");
        ArchRuleDefinition.noClasses()
                .that().resideInAPackage("..domain..")
                .should().dependOnClassesThat()
                .resideInAnyPackage("..web..", "..persistence..", "jakarta.persistence..", "org.springframework.web..")
                .check(classes);
    }
}
