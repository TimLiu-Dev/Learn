Packages, package-private, Inner-Class this$ Leaks & Flexible Constructors (JEP 513)

Master Java's four visibility levels, module imports (JEP 511), initialization order, Android-style inner-class memory leaks, method-chaining builders, and Java 25 pre-super() constructor validation.

1. Packages, Imports (JEP 511) & the Four Access Levels

Every non-trivial backend Java class lives in a reverse-domain package matching its directory structure (com/acme/orders/OrderService.java). While Java 25's Module Import Declarations (JEP 511) let you write import module java.base; to import every exported package in java.base in one line, explicit package boundaries still govern encapsulation:

⚠ Package-Private vs. Kotlin internal
Unlike Kotlin's internal (visible anywhere in the Maven/Gradle module), Java's omitted visibility is package-private: subpackages like com.acme.orders.internal cannot see package-private classes in com.acme.orders. Package-private is ideal for Spring Boot package-by-feature encapsulation so controllers stay public while repository adapters remain package-scoped.

2. Production Trap: Non-Static Inner Classes (this$0) & Rigid Old super()

Just like Android's classic Handler or AsyncTask memory leak, declaring a nested helper class in Java without static silently instructs javac to inject a synthetic final Outer this$0; pointer. Any long-lived background callback or cache holding that inner object pins the entire outer service instance (and all its buffers) in heap memory! 

// ANTI-PATTERN: Non-static inner class pins OuterCache + rigid pre-Java-25 constructor hack
public class SessionHost {
    private final byte[] heavyBuffer = new byte[10_000_000];

    // BUG 1: Missing 'static'! Holds hidden this$0 pointer keeping 10MB alive forever.
    class CleanupHook implements Runnable {
        @Override public void run() { System.out.println("cleanup"); }
    }
}

// PRE-JAVA 25 HACK: super() HAD to be statement #1, forcing ugly static validation wrappers!
class BasePort {
    final int port;
    BasePort(int port) { this.port = port; }
}
class LegacyServicePort extends BasePort {
    LegacyServicePort(int port) { super(validate(port)); }
    private static int validate(int port) {
        if (port < 1024) throw new IllegalArgumentException("Privileged port");
        return port;
    }
}

Furthermore, class initialization executes in deterministic order: (1) Superclass static fields/blocks → (2) Subclass static fields/blocks (once at class load) → (3) Superclass instance initializers/constructor → (4) Subclass instance initializers/constructor. And in Java 25 (JEP 513 Flexible Constructor Bodies), constructors can validate arguments, compute values, and initialize safe fields in a prologue cleanly before calling super(...): 

// IDIOMATIC JAVA 25: static nested class + JEP 513 pre-super() validation + Builder
import module java.base;

public final class HttpServerConfig {
    private final int port;
    private final boolean tls;

    private HttpServerConfig(Builder b) {
        this.port = b.port;
        this.tls = b.tls;
    }

    // static nested Builder: zero hidden this$0 outer reference!
    public static final class Builder {
        private int port = 8080;
        private boolean tls = true;

        public Builder port(int port) { this.port = port; return this; }
        public Builder tls(boolean tls) { this.tls = tls; return this; }
        public HttpServerConfig build() { return new HttpServerConfig(this); }
    }

    public static class ServicePort extends BasePort {
        public ServicePort(int port) {
            if (port < 1024 || port > 65535) { // JEP 513: prologue runs BEFORE super()!
                throw new IllegalArgumentException("Invalid port: " + port);
            }
            super(port);
        }
    }
}
