Closures, Capture Semantics & Defensive Error Handling

Escaping closures (@escaping), autoclosures (@autoclosure), typed throws (Swift 6), rethrows, and deterministic LIFO defer cleanup.

← Master Curriculum & Systems Legend • 📖 Swift Syntax Cheatsheet • 📚 Systems Glossary

🧠 The Senior Android Anchor: Systems Comparison

In Kotlin, all lambdas are objects on the JVM heap (unless inlined via inline fun). Exceptions are unchecked at runtime (no checked exceptions exist in Kotlin).

In Swift, closures are non-escaping by default: they cannot outlive the function call, allowing the compiler to allocate them on the stack with zero heap allocation! Only when marked @escaping do they escape to the heap. Furthermore, Swift error handling is compile-time checked with throws, Swift 6 typed throws throws(AppError), and deterministic defer blocks executed in LIFO order.

⚡ Low-Level Core: How Swift Works Under the Hood

1. Escaping vs Non-Escaping Closures

  • Non-Escaping (Default): Executed synchronously within the function. Guaranteed not to escape. Does not require [weak self] because retain cycles are impossible!
  • @escaping: Stored in a property or dispatched asynchronously. Escapes the current scope. Retains referenced objects; requires explicit capture list.
  • @autoclosure: Automatically wraps an expression argument into a zero-argument closure, delaying evaluation (used by assert and ??).

2. Swift 6 Typed Throws

enum NetworkError: Error, Equatable {
    case unauthenticated
    case rateLimited(retryAfter: Int)
}

// Swift 6 Typed Throws: caller knows exact concrete error type!
func executeRequest() throws(NetworkError) -> String {
    throw NetworkError.rateLimited(retryAfter: 30)
}

3. Deterministic defer Cleanup (LIFO Order)

A defer block executes whenever execution leaves the current scope (via return, throw, or break). Multiple defer blocks execute in Last-In First-Out (LIFO) stack order:

func processFile() {
    openFile()
    defer { closeFile() } // Executes LAST
    defer { flushBuffer() } // Executes FIRST upon exit
}
⚠️ Senior Failure Mode & Anti-Pattern:

Swallowing Errors with try?: Using try? indiscriminately converts any thrown error into nil, discarding critical debugging info, telemetry, and error categorization. Use do { try ... } catch { ... } or typed throws in production.

import Foundation

enum TransactionError: Error, Equatable {
    case insufficientFunds
    case accountLocked
}

final class BankVault {
    var balance: Double = 500.0
    var isLocked: Bool = false
    var auditLog: [String] = []

    func acquireLock() {
        isLocked = true
        auditLog.append("LOCK_ACQUIRED")
    }

    func releaseLock() {
        isLocked = false
        auditLog.append("LOCK_RELEASED")
    }

    func executeSecureTransaction(amount: Double) throws(TransactionError) -> Double {
        acquireLock()
        defer {
            releaseLock()
        }
        guard amount <= balance else {
            throw TransactionError.insufficientFunds
        }
        balance -= amount
        return balance
    }
}

func runTests() {
    print("🧪 Running Lesson 1.6 Verification Tests...")
    let vault = BankVault()
    do {
        let newBal = try vault.executeSecureTransaction(amount: 200.0)
        assert(newBal == 300.0)
        assert(vault.isLocked == false)
    } catch {
        fatalError()
    }
    vault.auditLog.removeAll()
    do {
        _ = try vault.executeSecureTransaction(amount: 999.0)
        fatalError()
    } catch TransactionError.insufficientFunds {
        assert(vault.isLocked == false)
        assert(vault.auditLog == ["LOCK_ACQUIRED", "LOCK_RELEASED"])
        print("  ✅ All tests passed!")
    } catch {
        fatalError()
    }
}
runTests()
Senior Engineering Walkthrough:

Swift 6 typed throws (throws(TransactionError)) enforces exhaustiveness at the callsite. The defer block guarantees that releaseLock() is executed as the stack unwinds, regardless of whether the function returns normally or throws an error.
