Automatic Reference Counting (ARC) & Memory Safety

Strong, Weak, Unowned references, closure capture lists [weak self], retain cycles, and autorelease pools.

← Master Curriculum & Systems Legend • 📖 Swift Syntax Cheatsheet • 📚 Systems Glossary

🧠 The Senior Android Anchor: Systems Comparison

In Android (ART), cyclical references between heap objects (e.g. Object A points to B, and B points to A) are collected harmlessly by the generational tracing garbage collector as long as the cluster is unreachable from a GC Root.

In iOS, memory is managed deterministically via Automatic Reference Counting (ARC). Each class instance tracks its retain count. When count reaches zero, it deallocates immediately. Retain cycles are never collected and cause silent, permanent memory leaks that eventually trigger Darwin Kernel Jetsam termination.

⚡ Low-Level Core: How Swift Works Under the Hood

1. The Three Reference Types

  • Strong (Default): Increments reference count by 1. Keeps object alive.
  • Weak: Does not increment count. Always optional (weak var delegate: Delegate?). Automatically zeroed to nil when target deallocates.
  • Unowned: Does not increment count. Assumes object never deallocates before the reference. Hazard: Accessing an unowned reference after target deallocates crashes immediately with EXC_BAD_ACCESS.

2. Closure Capture Lists

In Swift, closures capture variables by strong reference by default. Escaping closures stored on self create instant retain cycles unless broken with [weak self]:

class NetworkClient {
    var onResponse: (() -> Void)?

    func execute() {
        // ❌ Retain Cycle: self -> onResponse -> self
        // onResponse = { self.handleSuccess() }

        // ✅ Senior Solution: capture list
        onResponse = { [weak self] in
            guard let self else { return }
            self.handleSuccess()
        }
    }
    func handleSuccess() {}
}

3. Autorelease Pools in High-Throughput Loops

When interacting with Objective-C bridged APIs (e.g. UIImage, CoreGraphics), temporary objects are added to the current runloop autorelease pool. In tight loops (processing 10,000 images), memory balloons until the runloop drains. Wrapping iterations in autoreleasepool { ... } drains memory immediately on each loop cycle.

⚠️ Senior Failure Mode & Anti-Pattern:

Unowned Self in Asynchronous Callbacks: Using [unowned self] in network or timer callbacks assumes the view controller will still exist when the network returns. If the user dismisses the screen, the response callback fires on a deallocated instance, instantly crashing the app.

🔑 Reveal Final Reference Solution & Architecture Walkthrough 
import Foundation

final class WorkerSession {
    let id: String
    var completionHandler: (() -> Void)?
    static var deinitCount = 0

    init(id: String) {
        self.id = id
        self.completionHandler = { [weak self] in
            guard let self else { return }
            self.doWork()
        }
    }

    func doWork() {}

    deinit {
        WorkerSession.deinitCount += 1
    }
}

func runTests() {
    print("🧪 Running Lesson 1.3 Verification Tests...")
    WorkerSession.deinitCount = 0
    do {
        let session = WorkerSession(id: "sess_42")
        session.completionHandler?()
    }
    assert(WorkerSession.deinitCount == 1)
    print("  ✅ All tests passed!")
}
runTests()
Senior Engineering Walkthrough:

By adding [weak self], the closure captures a non-owning optional pointer to WorkerSession. When the outer variable goes out of scope, the session's strong reference count drops to 0 and deinit runs deterministically.
