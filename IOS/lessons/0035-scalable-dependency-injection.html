Scalable Dependency Injection Architecture

Protocol-based constructor injection, container factories, environment injection, and eliminating global singletons.

← Master Curriculum & Systems Legend • 📖 Architecture Cheatsheet • 📚 Systems Glossary

🧠 The Senior Android Anchor: Systems Comparison

In Android, dependency injection is almost always handled by Dagger 2 or Hilt (using compiler annotation processors) or Koin (service locator).

In iOS, commercial teams favor Protocol-Based Constructor Injection and Container Factories over heavy third-party DI reflection frameworks. Dependencies are passed explicitly via initializers, enabling hermetic unit test mocking with zero runtime reflection overhead.

⚡ Low-Level Core: How Swift Works Under the Hood

1. Protocol-Based Constructor Injection

protocol NetworkServiceProtocol: Sendable {
    func fetchMetrics() async throws -> [Metric]
}

final class DashboardViewModel {
    private let networkService: any NetworkServiceProtocol

    // Dependencies injected via constructor:
    init(networkService: any NetworkServiceProtocol) {
        self.networkService = networkService
    }
}

2. Container Factories

Centralize assembly in an AppContainer to avoid scattering concrete constructor calls across the codebase:

final class AppContainer {
    let networkService: any NetworkServiceProtocol
    let databaseService: any DatabaseServiceProtocol

    init(isTesting: Bool = false) {
        if isTesting {
            self.networkService = MockNetworkService()
            self.databaseService = MockDatabaseService()
        } else {
            self.networkService = LiveNetworkService()
            self.databaseService = LiveDatabaseService()
        }
    }
}
⚠️ Senior Failure Mode & Anti-Pattern:

Overusing Global Singletons (Service.shared): Scattering NetworkService.shared across classes couples code to concrete implementations, preventing parallel unit testing and introducing hidden global mutable state.

🔑 Reveal Final Reference Solution & Architecture Walkthrough 
import Foundation

protocol AuthService: Sendable {
    func authenticate() -> String
}

struct LiveAuthService: AuthService {
    func authenticate() -> String { "LIVE_AUTH_TOKEN" }
}

struct MockAuthService: AuthService {
    func authenticate() -> String { "MOCK_TEST_TOKEN" }
}

final class LoginViewModel {
    let authService: any AuthService
    init(authService: any AuthService) {
        self.authService = authService
    }
}

struct AppFactory {
    static func makeViewModel(isTest: Bool) -> LoginViewModel {
        let service: any AuthService = isTest ? MockAuthService() : LiveAuthService()
        return LoginViewModel(authService: service)
    }
}

func runTests() {
    print("🧪 Running Lesson 5.2 Verification Tests...")
    let testVM = AppFactory.makeViewModel(isTest: true)
    assert(testVM.authService.authenticate() == "MOCK_TEST_TOKEN")

    let liveVM = AppFactory.makeViewModel(isTest: false)
    assert(liveVM.authService.authenticate() == "LIVE_AUTH_TOKEN")
    print("  ✅ All tests passed!")
}
runTests()
Senior Engineering Walkthrough:

Constructor injection decouples the consumer (LoginViewModel) from the concrete service implementation. Centralizing instantiation in AppFactory enables swapping live services with test doubles effortlessly.
