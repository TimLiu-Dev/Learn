Swift 6 Strict Concurrency, Region-Based Isolation & Sendable

Compile-time data-race safety, Sendable protocols, non-Sendable transfer rules, and migrating legacy codebases.

← Master Curriculum & Systems Legend • 📖 Swift Concurrency Cheatsheet • 📚 Systems Glossary

🧠 The Senior Android Anchor: Systems Comparison

In Android (Kotlin), thread safety is enforced by convention. Mutable class references can be passed freely across Coroutine contexts (withContext(Dispatchers.Default)), risking data races unless developer manually applies synchronization primitives.

In Swift 6, data-race safety is enforced by the compiler at compile time. Types passed across actor or task boundaries must conform to Sendable. Swift 6 introduces Region-Based Isolation (SE-0414): non-Sendable values can cross concurrency boundaries as long as the compiler proves no other reference to that memory region exists!

⚡ Low-Level Core: How Swift Works Under the Hood

1. The Sendable Protocol

A marker protocol indicating values can be safely transferred across threads:

  • Value Types (structs, enums): Implicitly Sendable if all stored properties are Sendable.
  • Actors: Implicitly Sendable because access to mutable state is serialized.
  • Classes: Must be final, contain only immutable let Sendable properties, or use internal synchronization with @unchecked Sendable.

2. Region-Based Isolation (Swift 6 SE-0414)

In Swift 5, sending a non-Sendable class into a Task was an immediate error. In Swift 6, the compiler tracks the memory region of variables. If you create an object and pass it to a background Task, but never access it again in the caller, Swift 6 proves there is no concurrent overlap and allows the transfer safely!

⚠️ Senior Failure Mode & Anti-Pattern:

Overusing @unchecked Sendable to Silence Compiler Warnings: Slapping @unchecked Sendable on mutable classes tells the compiler "trust me, I synchronized this manually." If you don't actually implement thread synchronization (locks or serial queues), you reintroduce silent memory corruption.

import Foundation

final class SecurityToken: Sendable {
    let rawToken: String
    let expiresAtEpoch: Int

    init(rawToken: String, expiresAtEpoch: Int) {
        self.rawToken = rawToken
        self.expiresAtEpoch = expiresAtEpoch
    }
}

func transferToken(_ token: SecurityToken) async -> String {
    let task = Task {
        return "validated_\(token.rawToken)"
    }
    return await task.value
}

func runTests() async {
    print("🧪 Running Lesson 2.6 Verification Tests...")
    let token = SecurityToken(rawToken: "sec_token_999", expiresAtEpoch: 5000)
    let result = await transferToken(token)
    assert(result == "validated_sec_token_999")
    print("  ✅ All tests passed!")
}

await runTests()
Senior Engineering Walkthrough:

For a class to conform to Sendable, it must be final (preventing subclass state injection) and have immutable let stored properties that are themselves Sendable. This guarantees zero concurrent data races when passed across Tasks.
