From Room Entities to Relational Thinking, Types, Constraints & SQL Execution

In Android Room, it’s easy to treat SQLite as a passive box that saves Kotlin objects. Senior engineers flip that mental model upside down: your database is the unbreakable source of truth that protects data integrity even when app code, background workers, or API deploys have bugs.

Room Bridge 1. Stop Treating the Database Like a Dumb Persistence Bucket

As an Android developer using Room, you’re used to writing a Kotlin data class and letting annotation processing generate SQLite tables behind the scenes: 

@Entity(tableName = "wallets")
data class WalletEntity(
    @PrimaryKey(autoGenerate = true) val id: Long = 0,
    val ownerEmail: String,
    val balanceDollars: Double,   // DANGER in production!
    val currency: String
)
Why Room Habits Break in Production Backend Systems

In a mobile app, one process (your app) talks to one local SQLite file, so validating balance >= 0 in a Kotlin ViewModel feels “good enough.” In production backend systems, 10 microservices, cron jobs, admin scripts, and mobile API versions hit the same database simultaneously. If a rule isn’t enforced inside the database schema, corrupt data will eventually enter—and unlike a crashed request, corrupt data stays broken forever.

Junior / App-Centric Mindset

  • Store money as Double / REAL because Kotlin uses Double.
  • Leave foreign keys off “so deletes are easier.”
  • Validate uniqueness and non-negativity only in Kotlin if statements.
  • Fetch all rows in a DAO and filter/sum them in Kotlin .filter { }.sumOf { }.

Senior Database Engineer Mindset

  • Store money as integer minor units (balance_cents BIGINT/INTEGER) or fixed-point NUMERIC(19,4).
  • Enforce invariants at the DB boundary with STRICT, NOT NULL, UNIQUE, CHECK, and FOREIGN KEY.
  • Understand SQLite vs PostgreSQL type rules and logical SQL execution order.
  • Let the database engine filter, join, and aggregate near the disk.

Core Concept 2. Data Types, SQLite’s Dynamic Typing Trap & Money Precision

Most developers assume that if a column is declared INTEGER, the database rejects strings. Classic SQLite (and Room by default!) does NOT. It uses dynamic typing with type affinity: if you insert 'hello' into an INTEGER column, SQLite quietly stores a text string!

Starting in SQLite 3.37+, adding the STRICT keyword at the end of CREATE TABLE forces SQLite to enforce real column types (INT, INTEGER, REAL, TEXT, BLOB, ANY). PostgreSQL always enforces strict types by default.

The IEEE-754 Money Bug (Never Use REAL / FLOAT / Double for Money)

Binary floating-point types (REAL in SQLite, DOUBLE PRECISION in PostgreSQL, Double in Kotlin) cannot represent base-10 decimals like 0.1 or 0.2 exactly. Over thousands of ledger rows, rounding drift turns into missing cents and failed financial audits.

Senior Trap Floating-Point Drift vs Integer Minor Units

Type Mapping Cheat Sheet: Kotlin / Room → SQLite STRICT → PostgreSQL 17/18

Domain Concept SQLite STRICT Choice PostgreSQL Production Choice Why Senior Engineers Choose It
Money / Currency INTEGER (minor units, e.g., cents) BIGINT (cents) or NUMERIC(19,4) Exact base-10 / integer arithmetic; zero IEEE-754 drift.
Primary Key ID INTEGER PRIMARY KEY or TEXT (UUIDv7) BIGINT GENERATED ALWAYS AS IDENTITY or UUID (v7) Avoids 32-bit INT overflow (2.1B limit!) and preserves B-tree insert locality.
Timestamps TEXT (ISO-8601 UTC) or INTEGER (Unix ms) TIMESTAMPTZ (always with time zone!) PostgreSQL TIMESTAMP without TZ causes DST & timezone bugs; TIMESTAMPTZ stores UTC cleanly.
Booleans INTEGER CHECK (flag IN (0, 1)) BOOLEAN NOT NULL DEFAULT false SQLite STRICT lacks a native BOOL type; CHECK prevents storing 2 or -1.
Strings TEXT TEXT (or TEXT CHECK (length(x) <= 255)) In Postgres, VARCHAR(n) has no speed benefit over TEXT. Increasing n is metadata-only in PG 9.2+ but still takes a brief ACCESS EXCLUSIVE lock and fails if views depend on the column; shrinking n rewrites the table.
PostgreSQL vs SQLite STRICT Subtlety

In SQLite STRICT tables, only 6 type names are allowed: INT, INTEGER, REAL, TEXT, BLOB, ANY. Writing VARCHAR(100) or BOOLEAN on a STRICT SQLite table throws a syntax error, whereas in PostgreSQL you use TEXT, BOOLEAN, BIGINT, NUMERIC, and TIMESTAMPTZ.

Invariants 3. Constraints, Primary Keys & The Foreign Key Trap

Every constraint you declare is an automated unit test that runs on every INSERT and UPDATE at C/native speed:

  • NOT NULL: Eliminate surprise NULL states by default. Make every column NOT NULL unless absence has a concrete domain meaning.
  • UNIQUE: Prevents duplicate accounts, emails, or idempotency keys even under concurrent requests (app-level “check-then-insert” has a race condition!).
  • CHECK (...): Enforces domain rules directly on rows, e.g. CHECK (balance_cents >= 0) or CHECK (currency IN ('USD', 'EUR', 'GBP')).
  • FOREIGN KEY ... REFERENCES: Guarantees child rows can never point to non-existent parent rows (orphans).
Senior Trap #1: SQLite Disables Foreign Keys by Default on Every New Connection!

PostgreSQL, MySQL (InnoDB), and SQL Server always enforce foreign keys. SQLite does NOT unless the connection executes PRAGMA foreign_keys = ON;. Room turns this on automatically when you define @ForeignKey, which hides the trap until you touch raw SQLite CLI, scripts, or Python/Node drivers. Always turn it on explicitly!

Senior Trap #2: ON DELETE CASCADE on Financial or Audit Tables

Junior devs love ON DELETE CASCADE because deleting a user cleanly wipes everything. Senior engineers use ON DELETE RESTRICT (the default!) on orders, payments, and ledger entries so an accidental DELETE FROM users WHERE id = 42 fails loudly instead of silently erasing legal/accounting history. (Soft-delete or anonymize PII instead!)

Senior Trap #3: NULL Passes CHECK Constraints!

A CHECK (amount_cents > 0) constraint only rejects rows where the expression evaluates to FALSE. If amount_cents is nullable and you insert NULL, NULL > 0 evaluates to UNKNOWN, which passes! Always pair CHECK with NOT NULL unless absence is intentional, and use multi-column checks like CHECK (end_at > start_at) for range invariants.

SQL Mental Model 4. Logical Query Execution Order & The NULL 3VL Trap

You write SQL starting with SELECT, so it feels like SELECT runs first. It doesn’t. The database engine logically processes clauses in a strict pipeline:

STEP 1
FROM / JOIN
Build working row set
→
STEP 2
WHERE
Filter individual rows
→
STEP 3
GROUP BY
Collapse into buckets
→
STEP 4
HAVING
Filter grouped buckets
→
STEP 5
SELECT
Compute expressions & aliases
→
STEP 6
DISTINCT
Deduplicate output rows
→
STEP 7
ORDER BY
Sort final rows
→
STEP 8
LIMIT / OFFSET
Slice final result

This execution order explains three things that trip up developers constantly:

  1. Why WHERE SUM(total_cents) > 5000 fails: WHERE runs in Step 2, before GROUP BY (Step 3) has even created the aggregates! Aggregate filters belong in HAVING (Step 4).
  2. Why PostgreSQL rejects SELECT aliases in WHERE: Because SELECT runs in Step 5 (after WHERE), Postgres throws column "alias" does not exist if you use a SELECT alias inside WHERE. (Note: SQLite has a permissive non-standard quirk allowing scalar aliases in WHERE, so don’t rely on it if you write portable SQL!)
  3. Performance rule: Put non-aggregate row filters (like status = 'paid') in WHERE, never in HAVING, so the engine discards irrelevant rows before sorting/hashing for GROUP BY (and can use indexes!).

Three-Valued Logic (3VL): Why NULL != 'cancelled' Silently Drops Rows

In Kotlin, booleans are true or false. In SQL, NULL means “unknown”, so comparisons produce TRUE, FALSE, or UNKNOWN. WHERE only keeps rows where the predicate evaluates to TRUE—rows evaluating to UNKNOWN are silently dropped! Similarly, x NOT IN (1, 2, NULL) evaluates to UNKNOWN for every row and returns an empty result!

Portable Standard SQL / PostgreSQL Syntax for Null-Safe Inequality

In SQLite, IS NOT / IS acts as null-safe equality (and SQLite 3.39+ also supports standard IS DISTINCT FROM!). In PostgreSQL, write WHERE resolution IS DISTINCT FROM 'wont_fix' (or WHERE resolution IS NULL OR resolution <> 'wont_fix').

Summary 8. Lesson 1 Senior Engineering Checklist

  • Always opt into STRICT in SQLite 3.37+ (and rely on PostgreSQL’s native strict types).
  • Never store money in REAL / FLOAT / Double. Use integer minor units (cents) or NUMERIC.
  • Always execute PRAGMA foreign_keys = ON; on every raw SQLite connection.
  • Default to NOT NULL and ON DELETE RESTRICT on financial/audit relations.
  • Filter rows in WHERE, filter grouped buckets in HAVING, and never write col != 'x' without thinking about NULL.
