Under the Hood: Slotted Pages, Heap Files, B+Trees & LSM-Trees

Why does a database fly at 10,000 rows and suddenly fall off a latency cliff at 50 million rows? Because databases do not read or write individual rows—they move fixed-size 4KB/8KB pages between disk and RAM. Understanding physical page layout, clustered vs heap storage, and B+Tree vs LSM-Tree mechanics turns mysterious slowdowns into predictable engineering tradeoffs.

Room Bridge 1. Why autoGenerate = true vs Random UUID Behaves Dramatically Differently at 50M Rows

In Android Room, changing a primary key from a monotonically increasing Long to a random UUID string looks like a one-line Kotlin refactor: 

// Pattern A: Sequential 64-bit integer -> appends to the RIGHTMOST B+Tree leaf page
@Entity(tableName = "events")
data class EventInt(
    @PrimaryKey(autoGenerate = true) val id: Long = 0,
    val tenantId: Long,
    val payload: String
)

// Pattern B: Random UUIDv4 string -> scatters writes across EVERY leaf page in the tree!
@Entity(tableName = "events_uuid")
data class EventUuid(
    @PrimaryKey val id: String = UUID.randomUUID().toString(),
    val tenantId: Long,
    val payload: String
)
Why You Never Notice This in a Mobile Prototype

At 5,000 rows inside a mobile app, the entire SQLite file is ~1 MB and sits warm in RAM. Both patterns finish in <1 ms. At 50 million rows on a production server (100+ GB index), random UUIDv4 forces every INSERT to fetch a cold 8KB page from SSD, dirty it, split it at 50% fill, and flush it back—causing buffer pool thrashing, 2× storage bloat, and 5–10× write amplification.

Sequential Keys (BIGINT / UUIDv7)

  • Inserts land on the hot rightmost leaf page already pinned in RAM.
  • Pages stay tightly packed (~90–95% full) with minimal splits.
  • Recent time-range queries read contiguous pages sequentially.

Random Keys (UUIDv4 / MD5 Hash PK)

  • Inserts jump to random positions across the entire B+Tree.
  • Evicts hot pages from the buffer pool (cache hit ratio collapses).
  • Frequent mid-page splits leave pages ~50–68% full + bloat WAL volume.

Disk Layout 2. Slotted Disk Pages, Buffer Pool & PostgreSQL TOAST

Whether you use SQLite (4KB pages by default via PRAGMA page_size) or PostgreSQL (8KB pages), the storage engine manages files as arrays of fixed-size slotted pages: 

+-------------------------------------------------------------------------+
| Page Header (24B in PG: LSN, lower/upper offsets, checksum, flags)      |
+-------------------------------------------------------------------------+
| Slot / Line Pointer Array -> [ptr0][ptr1][ptr2] ... grows downward      |
|                                                                         |
|                      ~~~ Free Space (Hole) ~~~                          |
|                                                                         |
|              ... grows upward <- [Tuple 2][Tuple 1][Tuple 0]            |
+-------------------------------------------------------------------------+
  • Indirection via Line Pointers: External indexes never store raw byte offsets into a page. They store (page_id, slot_index) (called a ctid in PostgreSQL, e.g. (412, 7)). That lets the engine compact free space inside a page without updating every index!
  • Buffer Pool / Page Cache: Engines read pages into an in-memory buffer pool (PostgreSQL shared_buffers + OS page cache; SQLite PRAGMA cache_size). Queries run against pinned RAM pages; background writers flush dirty pages to disk.
  • Overflow Pages & TOAST: A single row cannot span across normal 8KB pages cleanly. In PostgreSQL, when a row exceeds ~2KB, TOAST (The Oversized-Attribute Storage Technique) compresses large TEXT/JSONB/BYTEA fields and moves chunks out-of-line into a separate pg_toast_* table, keeping the main heap pages dense so scans stay fast. SQLite similarly spills oversized cells into linked overflow pages.
PostgreSQL Parity: Inspecting Physical Tuple Addresses (ctid) & TOAST
-- In PostgreSQL, every heap row exposes its physical (page_number, slot_number):
SELECT ctid, id, length(payload) FROM events LIMIT 5;
-- Example output: (0,1) | (0,2) | (0,3) ... (1,1) on page 1!

-- PostgreSQL TOAST strategies per column (default: EXTENDED = compress + out-of-line):
ALTER TABLE events ALTER COLUMN payload SET STORAGE EXTERNAL; -- skip compression for pre-compressed blobs

Table Organization 3. Heap + Secondary B+Tree (PostgreSQL) vs Clustered B+Tree (SQLite rowid / WITHOUT ROWID)

How do engines connect a primary key to the actual row bytes? There are two dominant architectures:

Heap Table + Secondary B+Tree (PostgreSQL)

  • Table rows sit in an unordered Heap of 8KB pages.
  • Every index (including PRIMARY KEY!) is a separate B+Tree pointing to ctid (page, slot).
  • Secondary indexes are small and independent—no PK duplication inside them.
  • Reads via PK need index traversal + 1 heap page fetch (unless Index-Only Scan).

Clustered B+Tree (SQLite rowid, InnoDB, SQLite WITHOUT ROWID)

  • SQLite tables default to a B+Tree clustered on the 64-bit rowid (aliased by INTEGER PRIMARY KEY).
  • If you declare id TEXT PRIMARY KEY without WITHOUT ROWID, SQLite creates two structures: a hidden rowid B+Tree for the rows AND a separate unique index mapping id → rowid!
  • Adding WITHOUT ROWID eliminates that hidden lookup, storing the entire row inside the PK B+Tree.
Senior Trap: When WITHOUT ROWID Makes Things WORSE

WITHOUT ROWID shines on narrow key-value or composite-PK tables (e.g., (tenant_id, metric_id) with few/no secondary indexes), and is counterproductive on single INTEGER PRIMARY KEY tables (which already cluster directly on the 64-bit rowid!). Avoid WITHOUT ROWID on wide tables (>200 bytes/row) or tables with multiple secondary indexes: 1) Wide rows reduce B+Tree fanout (fewer keys per 4KB page → taller tree); 2) Every secondary index in a WITHOUT ROWID table must store the entire primary key (e.g., a 36-byte UUID) instead of a compact 1–8 byte rowid!

PostgreSQL Heap Optimization: HOT Updates, FILLFACTOR & B+Tree Fanout

1. Why B+Trees stay shallow: With ~300–500 keys per 8KB internal page, a 4-level B+Tree indexes 100M+ rows in just 3–4 page hops (and top levels stay pinned in the Buffer Pool).
2. Heap-Only Tuple (HOT) Updates: Because PostgreSQL tables are heaps, updating a last_seen_at column normally inserts a new row version AND updates every secondary index. If the updated column is unindexed and the same 8KB page has free space (tunable via WITH (fillfactor = 80)), Postgres performs a HOT update—chaining the new tuple inside the same page and updating zero secondary indexes!

Write Amplification 4. Random UUIDv4 Page Splits vs BIGINT & Time-Ordered UUIDv7

Suppose your Room app or microservice needs globally unique IDs generated on clients before hitting the database. If you generate random UUIDv4 (122 random bits), consecutive inserts land at completely unrelated places in the B+Tree:

  • Buffer Pool Misses: When the working set exceeds RAM, each random insert evicts a cached page to load a cold target leaf page.
  • Page Splits & Internal Fragmentation: Inserting into a full middle leaf splits it into two ~50% full pages and bubbles keys upward to parent nodes.
  • Secondary Index Bloat (Clustered PKs): A 36-byte string UUID (or 16-byte binary UUID) embedded as the PK pointer in 4 secondary indexes bloats all 4 indexes!

The 2027 Senior Standard: Use BIGINT GENERATED ALWAYS AS IDENTITY for internal server-generated IDs, or UUIDv7 (RFC 9562: 48-bit Unix millisecond timestamp prefix + random suffix) when clients/distributed workers must mint IDs offline! Because UUIDv7 sorts chronologically, inserts stay pinned to the rightmost B+Tree leaf pages just like BIGINT.

PostgreSQL 18 Parity: Native uuidv7() & uuid Binary Storage
-- PostgreSQL stores UUID as 16 raw bytes (not 36-char ASCII TEXT!)
-- PostgreSQL 18 adds built-in uuidv7()! (In PG 14-17, generate UUIDv7 in app code or pg_uuidv7)
CREATE TABLE ingest_events (
  id UUID PRIMARY KEY DEFAULT uuidv7(),
  tenant_id BIGINT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  payload JSONB NOT NULL
);

Engine Architectures 5. B+Tree vs LSM-Tree (RocksDB / Cassandra) & The RUM Conjecture

The RUM Conjecture states that no storage engine can simultaneously minimize Read overhead, Update (write) overhead, and Memory/Space overhead—optimizing two comes at the expense of the third.

Dimension B+Tree (PostgreSQL, SQLite, InnoDB) LSM-Tree (RocksDB, Cassandra, Pebble, CockroachDB)
Write Path Write WAL + locate leaf page + modify page in place (random I/O when flushing dirty pages). Write WAL + insert into in-memory MemTable; flush sequentially as immutable SSTables (L0 → L1 → L2).
Read Path Fast & predictable O(log N) tree descent (3–4 hops for 100M rows); zero level merging. Must check MemTable + multiple SSTable levels; mitigated by Bloom filters & block cache.
Deletes & Updates Marks tuple dead / overwrites slot in-place; reclaimed by VACUUM / page merge. Appends a tombstone record! Old versions linger until background compaction merges SSTables.
Best Workloads Mixed OLTP, point/range queries, predictable p99 read latency, relational joins. Write-heavy telemetry, time-series ingest, append-dominant KV stores, SSDs sensitive to random writes.

Summary 9. Lesson 5 Senior Engineering Checklist

  • Think in 4KB / 8KB pages, not individual rows: sequential locality keeps hot leaf pages in the buffer pool.
  • Use BIGINT identity or time-ordered UUIDv7 for primary keys—never random UUIDv4 on high-ingest tables.
  • In SQLite, use WITHOUT ROWID, STRICT for narrow KV / composite-PK lookup tables; keep INTEGER PRIMARY KEY (rowid) for wide tables or tables with secondary indexes.
  • In PostgreSQL, understand Heap + ctid + TOAST (>2KB out-of-line storage) so wide blobs don’t ruin sequential scan density.
  • Choose B+Trees for predictable OLTP reads/ranges and LSM-Trees (with Bloom filters & compaction) when sustained random write throughput dominates.
