Room Bridge 1. Moving Beyond @Embedded and @Relation

In Android Room, developers often model nested objects using @Embedded (flattening a Kotlin object into the parent table’s columns) or @Relation (a Kotlin POJO helper that silently executes two separate SELECT queries under the hood). 

// Android Room convenience — hides real relational boundaries:
data class OrderWithProducts(
    @Embedded val order: OrderEntity,
    @Relation(
        parentColumn = "id",
        entityColumn = "id",
        associateBy = Junction(OrderItemCrossRef::class)
    )
    val products: List<ProductEntity> // Where did qty & snapshot price go?!
)
Why Room CrossRef & @Embedded Shortcuts Break Down at Scale

Room’s Junction(OrderItemCrossRef::class) returns a plain List<ProductEntity>, stripping away the edge payload (how many units were bought, at what snapshot price, or what role a user holds in a workspace). Similarly, overusing @Embedded leads to bloated tables full of nullable columns for optional sub-entities instead of clean 1:1 tables.

1 : 1

True 1:1 Extension Table

Use a shared Primary Key (user_id INTEGER PRIMARY KEY REFERENCES users(id)) or a UNIQUE foreign key when splitting wide PII, credentials, or rarely accessed blobs from hot rows.

1 : N

Parent → Child FK

Always put the foreign key on the “N” (many) side (e.g., orders.customer_id), never a comma-separated list of order IDs on customers.

M : N

Junction Table + Payload

Join tables are first-class entities! Give enrollments or order_items a composite PK (a_id, b_id) (or surrogate PK + UNIQUE(a_id, b_id)) plus payload columns like role, qty, and created_at.

Core Concept 2. Normalization (1NF–BCNF), Keys & Polymorphic Anti-Patterns

Normalization isn’t academic busywork—it is the discipline of ensuring each fact lives in exactly one place so updates, inserts, and deletes can’t leave your database contradicting itself (update anomalies).

Normal Form Formal Rule (Plain English) Classic Violation Senior Fix
1NF Every cell holds one atomic value; no repeating column groups. tags TEXT storing "sql,ai,cloud" or columns phone1, phone2, phone3. Child table user_phones(user_id, phone) or validated JSONB array when schema-less.
2NF In 1NF + every non-key column depends on the entire composite PK (no partial dependency). enrollments(student_id, course_id, course_title) where course_title depends only on course_id. Keep course_title in courses(id, title); leave only relationship facts (role, grade) in enrollments.
3NF In 2NF + no non-key column depends on another non-key column (no transitive dependency). users(id, zip_code, city, state) where zip_code → city, state. Move zip_code → (city, state) to a postal_codes lookup table.
BCNF Every determinant (left side of a functional dependency) is a candidate key. mentorships(student_id, topic, mentor_id) where each mentor teaches only 1 topic (mentor_id → topic), yet PK is (student_id, topic). Decompose into mentors(mentor_id, topic) and student_mentors(student_id, mentor_id).

Surrogate vs Natural vs Composite Primary Keys

  • Surrogate PK (INTEGER PRIMARY KEY / Postgres BIGINT GENERATED ALWAYS AS IDENTITY or UUIDv7): Stable when business attributes (like email or SKU) change; small 8-byte FK footprint.
  • Natural PK (e.g., ISO country code 'US', currency code 'USD'): Great for small, immutable reference/lookup tables—saves joins when 'USD' is already readable!
  • Composite PK (PRIMARY KEY (student_id, course_id)): Ideal for pure M:N junction tables—automatically enforces uniqueness of the pair and clusters table rows by the leading key in SQLite WITHOUT ROWID (or orders the B-tree index entries by the leading key in PostgreSQL, where heap pages remain unordered).

Senior Trap: The Polymorphic Association Anti-Pattern (commentable_type + commentable_id)

ORMs like Rails/Django/Room-wrappers love tables with (id, body, target_type, target_id) where target_type is 'post' or 'video'. Never do this! A SQL FOREIGN KEY can only point to one table, so the database cannot verify target_id exists, cannot enforce ON DELETE RESTRICT, and silently accumulates orphan comments forever.

Use one of three real relational alternatives instead:

  1. Exclusive Arc (Most Pragmatic for 2–4 targets): Nullable FKs post_id REFERENCES posts(id) and video_id REFERENCES videos(id) with CHECK ((post_id IS NOT NULL) + (video_id IS NOT NULL) = 1) in SQLite (in PostgreSQL, booleans cannot be added directly, so write CHECK (num_nonnulls(post_id, video_id) = 1) or cast ::int).
  2. Supertype / Subtype Pattern (Best for 5+ targets): Create a parent commentable_entities(id) table that both posts and videos reference as their PK, and comments references commentable_entities(id).
  3. Separate Join Tables: post_comments and video_comments referencing comments(id).

Architecture 3. Intentional Denormalization: Immutable Snapshots vs Premature Caching

Junior developers denormalize out of laziness (“joins feel hard”). Senior engineers normalize first, and then denormalize only for two valid reasons:

  • Domain Immutability (Mandatory!): When a historical record must freeze the value at the time of an event. An order_items row must copy unit_price_cents and product_name at checkout—otherwise raising a catalog price next month retroactively falsifies last year’s tax invoices!
  • Measured Read Performance: Precomputed counters (e.g., post.comment_count) or summary tables added after profiling shows a join/aggregate bottleneck, maintained via transactions, triggers, or async CDC workers.

Hybrid Modeling 4. Semi-Structured Data: SQLite JSON & PostgreSQL JSONB + GIN

What if you sell laptops, t-shirts, and SaaS licenses in one products table? Adding 80 nullable columns (ram_gb, sleeve_length, seat_limit) is ugly, and an EAV (Entity-Attribute-Value) table (product_attributes(product_id, key, val)) turns simple queries into 6-way self-joins.

Hybrid Relational + JSONB gives you the best of both worlds: keep core relational fields (id, sku, price_cents, category_id) as strict typed columns with FKs, and store sparse, product-specific metadata in a validated JSON column.

PostgreSQL Parity: JSON vs JSONB + GIN Indexes

In PostgreSQL, almost never use JSON (which stores raw text and re-parses on every query). Always choose JSONB (binary parsed, whitespace stripped, duplicate keys removed, indexable): 

-- PostgreSQL 17/18 production pattern:
CREATE TABLE products (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  sku TEXT NOT NULL UNIQUE,
  price_cents BIGINT NOT NULL CHECK (price_cents > 0),
  attrs JSONB NOT NULL DEFAULT '{}'::jsonb
);

-- Fast containment queries (@>) with a GIN index (jsonb_path_ops is smaller & faster for @>):
CREATE INDEX idx_products_attrs_gin ON products USING GIN (attrs jsonb_path_ops);

SELECT sku, attrs->>'brand' AS brand
FROM products
WHERE attrs @> '{"tags": ["linux"]}'::jsonb
  AND (attrs#>>'{specs,ram_gb}')::int >= 16;
When NOT to Use JSONB

Never shove foreign keys, money amounts, user IDs, or columns that need FOREIGN KEY / frequent SUM() / tight CHECK constraints inside JSONB. JSONB has higher per-row storage overhead and lacks per-key column statistics in the query planner compared to real relational columns. Note also: in PostgreSQL 17+, SQL/JSON functions like JSON_TABLE and JSON_VALUE let you project nested JSON arrays cleanly into typed relational columns, and single-key equality lookups often prefer a lightweight B-tree expression index on ((attrs->>'brand')) over a heavier GIN index.

Senior Trap: Soft Deletes (deleted_at) + UNIQUE Constraints

Adding UNIQUE(email, deleted_at) to allow re-signup after soft deletion silently breaks: because NULL != NULL in standard SQL, two active users with (email='a@b.com', deleted_at=NULL) both pass! Fix active uniqueness with a partial unique index CREATE UNIQUE INDEX uq_users_active_email ON users(email) WHERE deleted_at IS NULL; (or use PostgreSQL 15+ UNIQUE NULLS NOT DISTINCT when you want at most one NULL row).

Summary 8. Lesson 2 Senior Engineering Checklist

  • Replace Room @Relation / CrossRef toys with real M:N junction tables carrying composite PKs and edge payload columns.
  • Normalize to BCNF by default: atomic values (1NF), full-key dependence (2NF), zero non-key transitive dependence (3NF/BCNF).
  • Never build polymorphic (entity_type, entity_id) tables without FKs; use Exclusive Arcs (CHECK sum = 1) or Supertype/Subtype tables.
  • Always snapshot volatile prices, names, and tax rates onto order_items / invoices at transaction time.
  • Use validated JSON (CHECK (json_valid(...))) / PostgreSQL JSONB + GIN only for truly sparse or evolving attributes—never for FKs or money.
