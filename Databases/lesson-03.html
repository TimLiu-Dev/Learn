Room Bridge 1. Replacing Nested DAO Loops & Kotlin .groupBy {}

In local Android Room, firing a DAO query inside a customers.map { ... } loop takes ~0.2ms per call on flash storage, so N+1 loops slip past code review. In a backend PostgreSQL cluster over a network, 1,000 sequential DAO calls burn seconds of latency, exhaust connection pools, and transfer megabytes of rows just to compute a top-3 list in Kotlin: 

// ANTI-PATTERN: N+1 round-trips + pulling entire table into JVM/Node memory
val customers = customerDao.getAll()
val topOrders = customers.flatMap { c ->
    orderDao.findByCustomer(c.id)
        .sortedByDescending { it.amountCents }
        .take(2)
}
Push Computation Near the Data

With Joins, WITH RECURSIVE, and Window Functions (ROW_NUMBER() OVER (...)), the database scans, partitions, ranks, and filters on indexed pages in C and returns only the final 20 rows over the wire in a single round-trip.

Join Algebra 2. INNER, LEFT, FULL OUTER, CROSS & The LEFT JOIN Trap

  • INNER JOIN: Keeps only rows where the join predicate matches on both sides.
  • LEFT JOIN: Keeps every row from the left table; unmatched right columns become NULL.
  • FULL OUTER JOIN: Keeps every row from both sides, padding unmatched left or right columns with NULL. Ideal for financial reconciliation (e.g., Stripe payouts vs internal ledger). (Supported in SQLite 3.39+ and PostgreSQL!)
  • CROSS JOIN: Cartesian product (every row in A paired with every row in B)—useful for generating calendar/tier matrices, dangerous by accident!
Senior Trap: Putting a Right-Table Filter in WHERE Destroys a LEFT JOIN!

If you write FROM customers c LEFT JOIN orders o ON o.customer_id = c.id WHERE o.status = 'paid', unmatched customers have o.status = NULL. Since NULL = 'paid' is UNKNOWN, WHERE drops all customers with zero orders—silently turning your LEFT JOIN into an INNER JOIN! Fix: Put right-table filters inside the ON clause (AND o.status = 'paid') when preserving left rows.

Anti-Joins & Lateral 3. EXISTS vs IN, NULL-Safe NOT EXISTS & LATERAL

To check whether a related row exists (semi-join) or does not exist (anti-join), you have two options: IN / NOT IN vs EXISTS / NOT EXISTS. Senior engineers strongly prefer EXISTS / NOT EXISTS for subqueries:

  • Short-circuiting: EXISTS stops scanning as soon as it finds 1 matching row (especially fast with an index on the FK).
  • NULL Safety: Remember Lesson 1? If a subquery inside NOT IN (SELECT col FROM ...) returns even one NULL, the entire NOT IN predicate becomes UNKNOWN and returns 0 rows. NOT EXISTS simply checks whether a row exists—NULL values in the other table never poison it!

PostgreSQL Parity: LATERAL Joins for Correlated Top-K Subqueries

Normally a subquery inside FROM cannot reference columns from earlier tables in the same FROM clause. PostgreSQL’s LATERAL keyword acts like a SQL “for-each” correlated subquery in FROM—perfect for fetching the latest order per customer using an index on (customer_id, created_at DESC): 

-- PostgreSQL 17/18 (use LEFT JOIN LATERAL ... ON true to keep customers with 0 orders!):
SELECT c.id, c.name, latest.id AS latest_order_id, latest.amount_cents
FROM customers c
LEFT JOIN LATERAL (
  SELECT o.id, o.amount_cents
  FROM orders o
  WHERE o.customer_id = c.id
  ORDER BY o.created_at DESC
  LIMIT 1
) AS latest ON true;

Note: SQLite does not have the LATERAL keyword—in SQLite, solve top-N-per-group cleanly using ROW_NUMBER() OVER (PARTITION BY ...) (covered in Section 5!).

Hierarchies 4. Traversing Trees & Org Charts with WITH RECURSIVE

Adjacency lists (categories(id, name, parent_id REFERENCES categories(id))) are simple to write, but a plain JOIN can only descend a fixed number of levels. WITH RECURSIVE traverses arbitrary depth in one query using two parts joined by UNION ALL:

  1. Anchor (Base) Member: Selects the root node(s), e.g., WHERE parent_id IS NULL, setting depth = 0.
  2. Recursive Member: Joins the CTE itself (tree) to child rows (c.parent_id = tree.id), incrementing depth + 1 until no more children match.

Cycle Prevention: SQLite vs PostgreSQL 14+ CYCLE Clause

If bad data introduces a cycle (A → B → A), UNION ALL loops infinitely unless guarded! Always add a max-depth cap (WHERE t.depth < 20) or track visited IDs in a path string. In PostgreSQL 14+, you can also append CYCLE id SET is_cycle USING path directly onto the recursive CTE.

Analytical SQL 5. Window Functions: Ranking, LAG/LEAD & Frame Clauses

GROUP BY collapses multiple rows into one summary row per bucket. Window functions (fn() OVER (...)) compute aggregates or rankings across a set of related rows without collapsing the individual rows! They execute conceptually during the SELECT phase (after HAVING, before DISTINCT and ORDER BY).

Ranking Functions on Tied Values (100, 100, 90)

  • ROW_NUMBER(): 1, 2, 3 (arbitrary tie-break unless ORDER BY is unique)
  • RANK(): 1, 1, 3 (leaves gaps after ties)
  • DENSE_RANK(): 1, 1, 2 (no gaps—best for “top 3 salary tiers”)

Row Navigation & Running Frames

  • LAG(col, 1, 0) OVER (...): Previous row’s value (great for day-over-day delta!)
  • LEAD(col, 1) OVER (...): Next row’s value (great for session duration!)
  • ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW: Strict row-by-row running total.
Senior Trap: Default RANGE Frame Merges Duplicate Timestamps!

When you write SUM(amount) OVER (ORDER BY tx_date) without an explicit frame, SQL defaults to RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. If two transactions occur on the same tx_date, RANGE treats them as peers and adds both amounts to both rows! Always write ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW (with a deterministic tie-breaker like ORDER BY tx_date, id) for ledger running balances.

Two Senior Traps: Join Cardinality Fanout & CTE Materialization

1. Join Fanout: Joining two independent 1:N child tables (e.g., orders + refunds) before SUM() multiplies rows (M × N) and silently inflates totals—pre-aggregate each child in a CTE (or LATERAL) before joining.
2. CTE Optimization Fence: Before PostgreSQL 12, CTEs always materialized into temp buffers; in PostgreSQL 12+ and SQLite 3.35+, non-recursive single-use CTEs are inlined by default unless you write WITH x AS MATERIALIZED (...).

Summary 9. Lesson 3 Senior Engineering Checklist

  • In a LEFT JOIN, put right-table conditions in the ON clause (not WHERE) unless you intentionally want to discard unmatched left rows.
  • Prefer NOT EXISTS over NOT IN (subquery) so a single NULL never wipes out your entire result set.
  • Use WITH RECURSIVE with a depth/cycle guard for arbitrary-depth trees and org charts.
  • Know when to use ROW_NUMBER (unique slot) vs RANK (gaps) vs DENSE_RANK (no gaps).
  • Always specify ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW with a deterministic tie-breaker for running totals.
