Replication, High Availability, Failover & Backups (RPO / RTO)

Hardware dies, AZs lose power, and engineers accidentally run DELETE FROM users; without a WHERE clause. Senior engineers design for failure upfront using RPO/RTO budgets, Read-Your-Own-Writes LSN routing, fenced Patroni failover, and Point-in-Time Recovery (PITR).

Room Bridge 1. Moving Beyond Single-Device Data Loss Risk to 99.99% Multi-AZ Systems

In Android Room, if a user drops their phone in a lake, local SQLite storage is gone (unless your server holds the authoritative copy). In backend engineering, your database IS that authoritative copy for millions of users—so a single SSD failure or AZ outage cannot lose committed payments or take checkout offline for hours.

Replication Is High Availability, NOT a Backup!

Junior engineers often assume: “We have 2 read replicas, so we don’t need backups.” Deadly mistake! If someone accidentally executes DROP TABLE invoices; or UPDATE users SET email = NULL; on the Primary, physical streaming replication dutifully replays that exact destruction onto every replica within milliseconds! Replication protects against hardware/AZ loss; PITR backups protect against human & software corruption.

Core Concept 2. RPO vs RTO & Synchronous vs Asynchronous Replication

RPO (Recovery Point Objective)

How much data loss (in time) can the business survive?
• RPO = 0: zero committed transactions lost (requires synchronous replication with synchronous_commit = on—standby WAL flushed to disk—or remote_apply for immediate visibility; avoid remote_write for RPO=0 since OS page cache isn’t fsync’d!).
• RPO = 5 min: up to 5 minutes of recent writes may vanish in a sudden primary crash (async WAL archiving).

RTO (Recovery Time Objective)

How long can the database be down before recovery completes?
• RTO < 30s: automated multi-AZ failover (Patroni + quorum).
• RTO = 2–4 hrs: restoring a 2 TB base backup + replaying WAL archives from S3.

Senior Trap: synchronous_standby_names = 's1' With Only 1 Standby

If you configure synchronous replication with only ONE standby (s1) and that standby reboots or loses network, your Primary hangs forever on every COMMIT waiting for an ACK that never arrives! Always pair synchronous commits with at least 2 standbys using quorum syntax: synchronous_standby_names = 'ANY 1 (standby_az2, standby_az3)'.

Scaling Reads 3. Physical vs Logical Replication & Read-Your-Own-Writes (RYOW)

  • Physical Streaming Replication: Ships raw WAL bytes block-for-block. Exact cluster clone, minimal CPU overhead, supports read-only hot_standby replicas—but both nodes must run the exact same PostgreSQL major version.
  • Logical Replication (Pub/Sub): Decodes WAL into table-level row changes (INSERT/UPDATE/DELETE). Supports selective tables, cross-region filters, and zero-downtime major version upgrades (e.g., PG 15 → PG 18)! Caveats: tables need a PK or REPLICA IDENTITY FULL for updates/deletes, and pre-PG 18 logical replication does not sync SEQUENCE values automatically—always verify/bump sequences before cutover.
Two Standby Outage Traps: Replication Slots & Replica Query Cancels

1. Orphaned Replication Slot: If a logical subscriber or dead replica disconnects, its replication slot pins WAL segments on the Primary until disk hits 100% and crashes the Primary! Always cap max_slot_wal_keep_size.
2. Read Replica Conflicts: Long analytics on a hot_standby replica conflict with Primary VACUUM; configure max_standby_streaming_delay / hot_standby_feedback (and note cloud differences: RDS Multi-AZ uses synchronous block storage vs Aurora’s 4-of-6 quorum storage vs self-hosted Patroni).

Solving Stale Reads on Replicas via LSN Watermarks

A user updates their shipping address on the Primary (advancing WAL to LSN 1050), then immediately refreshes /profile which routes to an async Read Replica still at LSN 1042. They see their old address and assume the save failed! Fix: Return the writer’s commit LSN (pg_current_wal_lsn()) in a short-lived cookie/Redis token; route subsequent reads from that user to a replica ONLY if replica.replay_lsn >= user.min_lsn, otherwise fall back to Primary.

Disaster Recovery 4. Automated Failover, Split-Brain Fencing & PITR

In multi-AZ PostgreSQL, Patroni coordinates leader election through a distributed consensus store (etcd or Consul). The Primary holds a time-bounded leader lease (TTL ~30s). If the Primary becomes network-partitioned:

  • A healthy standby in the majority partition wins the quorum vote in etcd and promotes to Primary.
  • Split-Brain Prevention (Fencing): The isolated old Primary immediately demotes itself to read-only (or is fenced via STONITH / watchdog / cloud API detach) the moment it cannot renew its etcd lease—guaranteeing two primaries NEVER accept divergent writes simultaneously!

Point-in-Time Recovery (PITR): Base Backup + Continuous WAL Replay

pg_dump creates a logical snapshot at one timestamp (great for dev/small DBs, bad for multi-TB clusters). For production, combine periodic physical pg_basebackup (or pgBackRest) snapshots with continuous WAL archiving to S3/GCS so you can replay transactions up to any exact second before an accidental DELETE.

Summary 8. Lesson 13 Senior Engineering Checklist

  • Define explicit RPO (acceptable data loss) and RTO (acceptable downtime) before choosing Async vs Sync Quorum replication.
  • Never deploy single-standby synchronous replication (1-of-1)—use quorum ANY 1 (s1, s2) so one replica reboot doesn’t halt all writes.
  • Fix read-replica stale reads with Read-Your-Own-Writes LSN watermarks (route to replica only when replay_lsn >= user.min_lsn).
  • Use physical replication for HA failover, logical replication for zero-downtime major PG version upgrades, and Patroni/etcd quorum + fencing to prevent split-brain.
  • An untested backup is not a backup: run automated PITR restore drills (basebackup + WAL archive) against staging regularly.
