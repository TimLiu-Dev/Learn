ACID, Isolation Levels & Real Concurrency Anomalies

Memorizing “Atomicity, Consistency, Isolation, Durability” won’t save a checkout API when two requests hit the same wallet at the exact same millisecond. Senior engineers understand how Snapshot Isolation, Lost Updates, Write Skew, and Serializable (SSI) actually behave under concurrent load.

Room Bridge 1. From Room’s Single-Writer withTransaction to Concurrent MVCC

In Android Room, you wrap multiple DAO calls in db.withTransaction { ... }. Under the hood, SQLite uses a single-writer file lock (even in WAL mode): only one write transaction can run at a time, while readers see a consistent snapshot. 

// Android Room: Only ONE write transaction runs at a time on the device!
database.withTransaction {
    val wallet = walletDao.getById(1)
    if (wallet.balanceCents >= 5000) {
        walletDao.updateBalance(1, wallet.balanceCents - 5000) // Safe ONLY because 1 writer!
    }
}
Why That Exact Kotlin Pattern Loses Money on PostgreSQL

On a backend database like PostgreSQL or MySQL, hundreds of concurrent write transactions execute simultaneously using Multi-Version Concurrency Control (MVCC). Under PostgreSQL’s default READ COMMITTED isolation, two pods executing that exact “read balance → compute in app → write new balance” pattern simultaneously will both read $100, both approve -$50, and both write $50. One withdrawal vanishes silently!

SQLite / Room Model

  • Single-writer lock serializes all mutations automatically.
  • BEGIN defaults to DEFERRED: upgrading a read snapshot to a write after another writer commits throws immediate SQLITE_BUSY (ignoring busy_timeout!). Always use BEGIN IMMEDIATE for write transactions.
  • Default isolation is always serializable across connections (unless PRAGMA read_uncommitted = ON in shared-cache mode).
  • App-level read-modify-write feels safe until you move to a server DB.

PostgreSQL MVCC Server Model

  • Multiple writers modify different (or even overlapping) rows concurrently.
  • Default isolation is READ COMMITTED (fresh snapshot per statement).
  • REPEATABLE READ uses Snapshot Isolation (stops Lost Updates, allows Write Skew!).
  • SERIALIZABLE uses SSI predicate locks and throws 40001 retries.

Core Concept 2. ACID Unpacked & Partial Rollbacks with SAVEPOINT

Each letter of ACID protects a different failure boundary:

  • Atomicity (“All or Nothing”): If step 2 of a 3-step transfer fails or crashes mid-flight, every earlier write leaves no durable effect (undone via rollback journal/undo in SQLite/InnoDB, or marked invisible via aborted xmin in PostgreSQL MVCC). Inside a running transaction, SAVEPOINT name lets you roll back a failed sub-operation (ROLLBACK TO SAVEPOINT name) without throwing away earlier valid work.
  • Consistency (“Invariants Hold”): Unlike the “C” in CAP, ACID Consistency is a contract shared by your schema (CHECK, UNIQUE, FOREIGN KEY) and your transaction logic (e.g., double-entry debits + credits always sum to 0).
  • Isolation (“Concurrent Safety”): Controls which intermediate or committed states concurrent transactions can observe.
  • Durability (“Committed Means Permanent”): Once COMMIT returns OK, the WAL record has been flushed with fsync() to persistent storage—not merely sitting in volatile OS page cache.

Senior Trap: SAVEPOINT Abuse & Subtransaction Overflow in PostgreSQL

In PostgreSQL, each SAVEPOINT allocates a subtransaction XID. Creating hundreds of savepoints per transaction (e.g., an ORM wrapping every loop iteration in SAVEPOINT) overflows Postgres’s 64-subtransaction cache per backend, causing massive SubtransSLRU lock contention and latency spikes under load. Use ON CONFLICT DO NOTHING for upsert batching instead of SAVEPOINT loops!

Concurrency Bugs 3. The 5 Real Concurrency Anomalies

To reason about isolation levels without guessing, know the exact 5 anomalies that happen when transactions interleave:

Anomaly Interleaving Pattern Real-World Impact
1. Dirty Read T1 updates row → T2 reads uncommitted value → T1 ROLLBACKs. T2 issues a shipping label or receipt for a payment that never committed.
2. Non-Repeatable Read T1 reads row id=1 (→ 100) → T2 updates id=1 to 50 & commits → T1 re-reads id=1 (→ 50). Financial report reads inconsistent numbers for the same account inside one request.
3. Phantom Read T1 runs WHERE status='open' (3 rows) → T2 inserts a new 'open' row & commits → T1 re-runs query (4 rows). End-of-day batch sum disagrees with row count queried 10ms earlier.
4. Lost Update T1 reads 100, T2 reads 100 → T1 sets 70 → T2 sets 80 (clobbers T1’s -30!). Inventory counts, wallet balances, and view counters silently lose increments/debits.
5. Write Skew T1 & T2 read overlapping predicate (≥ 2 doctors on call), then update disjoint rows (Dr. A off, Dr. B off). 0 doctors left on call, double-spend across checking+savings, or double room booking!

Lost Update: Why App-Side Read-Modify-Write Breaks Under READ COMMITTED

Even though PostgreSQL prevents dirty reads by default, READ COMMITTED takes a fresh snapshot for every SQL statement. If your API fetches balance = 10000 in statement 1, subtracts 3000 in application code, and sends SET balance_cents = 7000 in statement 2, any concurrent deposit between statement 1 and 2 gets erased.

Write Skew: The Subtle Snapshot Isolation Killer

Suppose a hospital invariant says: at least 1 doctor must remain on call per shift. Alice and Bob are both on call (count = 2). Under Snapshot Isolation (REPEATABLE READ in PostgreSQL), Alice’s transaction reads count = 2 and updates doctor = 'Alice' to on_call = 0. Simultaneously, Bob’s transaction reads the same snapshot (count = 2) and updates doctor = 'Bob' to on_call = 0. Because they modify different rows, Snapshot Isolation sees zero write-write conflict and commits both!

Isolation Matrix 4. SQL Isolation Levels & PostgreSQL Parity

PostgreSQL implements stricter guarantees than the SQL-92 minimum standard in two huge ways: (1) it never allows Dirty Reads (even at READ UNCOMMITTED), and (2) its REPEATABLE READ prevents Phantom Reads and Lost Updates via Snapshot Isolation—only leaving Write Skew possible unless you upgrade to SERIALIZABLE (SSI).

PostgreSQL Production Pattern: Handling 40001 serialization_failure & Outer-Boundary Retries

In PostgreSQL, both REPEATABLE READ (on same-row concurrent updates) and SERIALIZABLE (via Serializable Snapshot Isolation predicate tracking) protect invariants by aborting one conflicting transaction with SQLSTATE 40001. You MUST wrap REPEATABLE READ / SERIALIZABLE transactions in an idempotent application retry loop (3–5 attempts with jittered backoff)—and never trigger external HTTP calls or emails inside the transaction before COMMIT. (For long read-only analytics on a busy primary, BEGIN ISOLATION LEVEL SERIALIZABLE READ ONLY DEFERRABLE; waits once for a safe snapshot with zero 40001 aborts!) 

-- PostgreSQL: Strict isolation for double-spend / scheduling invariants
BEGIN ISOLATION LEVEL SERIALIZABLE;
  SELECT COUNT(*) FROM on_call_shifts
  WHERE shift_date = '2027-06-01' AND on_call = 1;
  -- If >= 2, update doctor_id = 1; if another txn concurrently removes doctor_id = 2,
  -- Postgres SSI detects the rw-antidependency cycle and aborts the 2nd committer with SQLSTATE 40001!
  UPDATE on_call_shifts SET on_call = 0
  WHERE shift_date = '2027-06-01' AND doctor_id = 1;
COMMIT;
Stopping Write Skew & Double-Booking Without Full SERIALIZABLE

1. Materializing a Lock Row: Under READ COMMITTED, create a parent row shifts(shift_date PRIMARY KEY, ...) and run SELECT 1 FROM shifts WHERE shift_date = '2027-06-01' FOR UPDATE; before checking and updating on_call_shifts.
2. Range Exclusion (EXCLUDE USING gist): For hotel/meeting-room double-bookings, PostgreSQL’s EXCLUDE USING gist (room_id WITH =, during WITH &&) prevents overlapping time ranges atomically at the index level even under READ COMMITTED. (Note also: MySQL InnoDB’s REPEATABLE READ uses next-key gap locks rather than PostgreSQL’s Snapshot Isolation.)

Summary 8. Lesson 9 Senior Engineering Checklist

  • Never compute a new balance in app code and send SET balance_cents = :computed under READ COMMITTED—use atomic relative SQL (SET balance_cents = balance_cents - :amt WHERE id = :id AND balance_cents >= :amt) or explicit locking/OCC.
  • Know that PostgreSQL REPEATABLE READ uses Snapshot Isolation: it blocks Lost Updates on the same row, but still allows Write Skew on disjoint rows.
  • Use SERIALIZABLE (SSI) or parent-row FOR UPDATE locking when invariants span multiple rows (doctor schedules, multi-account credit limits).
  • Always wrap REPEATABLE READ and SERIALIZABLE transactions in a bounded retry loop for SQLSTATE 40001.
  • Use SAVEPOINT sparingly for partial rollbacks; avoid putting SAVEPOINT inside per-row ingestion loops in PostgreSQL.
