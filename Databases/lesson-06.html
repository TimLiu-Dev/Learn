Indexing Mastery: Composite, Covering, Partial, Expression & JSON/GIN Indexes

Slapping a single-column index on every WHERE column is the fastest way to bloat writes and still miss query plans. Senior engineers design surgical composite, covering, partial, expression, and GIN indexes matched directly to access paths.

Room Bridge 1. Moving Beyond Single-Column @Index in Room

In Android Room, most developers only ever write single-column indexes (or skip them entirely): 

// Naive Room approach: 3 separate single-column indexes!
@Entity(
    tableName = "orders",
    indices = [
        Index(value = ["tenantId"]),
        Index(value = ["status"]),
        Index(value = ["createdAt"])
    ]
)
data class OrderEntity(...)
Why Three Single-Column Indexes Lose to One Surgical Composite Index

Each extra index must be updated on every INSERT, UPDATE, and DELETE (write amplification + extra buffer pool pressure). Worse, for WHERE tenant_id = 42 AND status = 'pending' ORDER BY created_at DESC, an index on just status has terrible selectivity (maybe 30% of rows are pending!), forcing thousands of useless row lookups. One composite index (tenant_id, status, created_at) narrows directly to tenant 42’s pending rows already sorted by created_at!

B-Tree Order 2. Leftmost Prefix, Equality-Before-Range & Selectivity

A B+Tree sorts entries lexicographically by (col_1, col_2, col_3)—just like a phone book sorted by (last_name, first_name):

  • Leftmost Prefix Rule: An index on (a, b, c) accelerates queries on (a), (a, b), and (a, b, c). It generally cannot efficiently seek on (b) or (c) alone!
  • Equality-Before-Range Rule: Put equality predicates (=, IN) FIRST, then the range or ORDER BY column (>, BETWEEN, ORDER BY) LAST. Once a range condition hits on col_1, col_2 is no longer contiguous!
  • Index Selectivity: Selectivity = distinct_values / total_rows. A boolean column (is_active, 2 values) has low selectivity; scanning 50% of a table through an index is slower than a sequential scan (random I/O vs sequential I/O), so the planner ignores it!

Zero Heap Fetch 3. Covering Indexes (USING COVERING INDEX & INCLUDE)

Normally, an index search is a two-step dance: walk the B+Tree to find matching row pointers (rowid / ctid), then jump to the main table pages to read the remaining SELECT columns. If every column needed by WHERE, ORDER BY, and SELECT already lives inside the index leaf, the engine performs an Index-Only Scan (USING COVERING INDEX in SQLite)!

PostgreSQL Parity: INCLUDE Payload Columns & The Visibility Map
-- PostgreSQL 11+ lets you append non-key payload columns with INCLUDE
-- so they sit in leaf pages without bloating internal B-Tree branch nodes:
CREATE INDEX idx_orders_cov
  ON orders (customer_id, status, created_at DESC)
  INCLUDE (total_cents);

-- Caveat: PostgreSQL's Index-Only Scan still checks the per-page Visibility Map (VM)!
-- If a table isn't VACUUMed recently so VM bits aren't set, PG falls back to heap fetches to check MVCC xmin/xmax!

Surgical Size 4. Partial Indexes & The Predicate Implication Rule

Suppose an outbox_jobs table holds 50 million historical 'completed' rows and only 4,000 'pending' rows. Indexing all 50M rows wastes gigabytes of RAM and slows down every insert/update. A partial index indexes only the hot slice: 

CREATE INDEX idx_outbox_pending ON outbox_jobs(created_at) WHERE status = 'pending';
Senior Trap: The Query WHERE Clause MUST Imply the Partial Index Predicate!

Both SQLite and PostgreSQL refuse to use a partial index unless the planner can mathematically prove your query’s WHERE clause implies the index’s WHERE clause. Writing SELECT * FROM outbox_jobs ORDER BY created_at LIMIT 10 will do a full SCAN! And for soft-delete partial indexes (WHERE deleted_at IS NULL), every active-row query must explicitly include AND deleted_at IS NULL to activate the index.

Expressions & Inverted Indexes 5. Expression Indexes, Generated Columns & PostgreSQL GIN

Wrapping an indexed column inside a function like WHERE LOWER(email) = 'ada@acme.io' destroys a normal index on email because the B+Tree is sorted by raw case-sensitive strings. You have two clean solutions:

  • Expression Index: Index the exact expression CREATE UNIQUE INDEX idx_users_lower_email ON users(LOWER(email)); (also works for json_extract(meta, '$.event_type') in SQLite!).
  • Generated Column: Declare email_norm TEXT GENERATED ALWAYS AS (LOWER(email)) STORED and index email_norm.
PostgreSQL Parity: GIN & GiST Indexes for JSONB and Full-Text Search (tsvector)

B+Trees index scalar values well, but cannot index arbitrary keys inside a nested JSONB document or individual stemmed words inside a paragraph. PostgreSQL solves this with GIN (Generalized Inverted Index)—mapping each token or JSON key-path to a posting list of matching ctids: 

-- 1. JSONB containment queries (@>) using compact jsonb_path_ops GIN index:
CREATE INDEX idx_events_meta_gin ON events USING GIN (metadata jsonb_path_ops);
SELECT id FROM events WHERE metadata @> '{"plan": "enterprise", "region": "us-east"}';

-- 2. Full-Text Search using generated tsvector + GIN (fast reads, higher write cost; use pending list / fastupdate):
ALTER TABLE docs ADD COLUMN fts_vec tsvector
  GENERATED ALWAYS AS (to_tsvector('english', coalesce(title,'') || ' ' || coalesce(body,''))) STORED;
CREATE INDEX idx_docs_fts ON docs USING GIN (fts_vec);
SELECT id, title FROM docs WHERE fts_vec @@ websearch_to_tsquery('english', 'btree compaction');

Four Index Maintenance Anti-Patterns Seniors Catch in Review
  • Redundant Leftmost Indexes: Keeping (tenant_id) when (tenant_id, created_at) already exists wastes RAM and doubles write amplification.
  • OR Across Columns: WHERE a = 1 OR b = 2 often defeats a composite B-tree; rewrite as UNION ALL (deduped) or rely on Postgres BitmapOr with two separate indexes.
  • Sort Direction Mismatch: Index (a ASC, b DESC) cannot satisfy ORDER BY a ASC, b ASC without a sort (unless both directions match or invert together).
  • Zombie Indexes: Audit pg_stat_user_indexes (idx_scan = 0) to drop unused indexes that burn write IOPS and block HOT updates.

Summary 9. Lesson 6 Senior Engineering Checklist

  • Order composite B-Tree columns by equality predicates first, range/sort column last.
  • Use covering indexes (INCLUDE in Postgres, trailing columns in SQLite) to achieve USING COVERING INDEX / Index-Only Scans.
  • Use partial indexes (WHERE status = 'pending' or WHERE deleted_at IS NULL) to shrink index RAM footprint, and verify queries explicitly imply the predicate.
  • Create expression indexes for LOWER(email) or JSON attribute paths rather than wrapping indexed columns unindexed.
  • In PostgreSQL, reach for GIN (especially jsonb_path_ops) for JSONB containment and tsvector full-text search, balancing read speed against write amplification.
