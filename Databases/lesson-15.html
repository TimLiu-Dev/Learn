Caching Patterns, Redis & Choosing Polyglot Storage Engines

Your fastest database query is the one that never hits disk—or never hits Postgres at all. Yet naive caching causes subtle stale-data races and catastrophic thundering-herd meltdowns when a hot key expires. And while PostgreSQL handles 85% of workloads brilliantly, senior engineers know exactly when specialized engines (Redis, DynamoDB, TimescaleDB, Graph) deliver 10x better latency or cost.

Room Bridge 1. From Android LruCache + DataStore to Distributed Redis

In Android apps, you keep an in-memory LruCache or Kotlin StateFlow in front of Room/Retrofit. Because only one user runs on one phone, invalidation is local.

Why Process-Local Caches Break in Stateless Backend Fleets

Behind a load balancer, 40 Kubernetes API pods handle requests for the same users. If Pod 1 updates a user’s subscription in PostgreSQL and clears its own local HashMap, Pods 2–40 still serve stale data! A shared in-memory store like Redis / Valkey gives all pods a single sub-millisecond cache, atomic counters, and distributed coordination primitives.

Core Concept 2. Cache-Aside, Write-Through & Write-Behind

Cache-Aside (Lazy Loading)

App checks Redis first. On miss, reads Postgres, writes to Redis with a TTL, and returns. On write: updates Postgres, then deletes (invalidates) the cache key. Most common & resilient pattern.

Write-Through

Every write updates both the cache and the backing DB synchronously before returning OK. Keeps cache warm and consistent, at the cost of higher write latency and caching rarely read rows.

Write-Behind (Write-Back)

App writes only to fast memory cache and acks immediately; a background worker flushes batches to DB later. Ultra-fast writes (e.g., view counters), but risks data loss if the cache node crashes before flush!

Senior Trap: The Cache-Aside Stale-Write Race (and Why You Always Set a TTL!)

1. Request A gets a cache miss, reads plan = 'free' from Postgres.
2. Request B updates Postgres to plan = 'pro' and deletes the cache key.
3. Request A finishes and writes its old plan = 'free' into Redis!
Defenses: Always attach a bounded TTL (e.g., 60–300s), prefer DEL over blind SET on writes, and for critical state include a monotonic version (or use CDC/Outbox invalidation).

Failure Modes 3. Cache Stampede (Thundering Herd) & Cache Penetration

Two failure modes turn a healthy cache into a database outage:

  • Cache Stampede (Thundering Herd): A celebrity profile or homepage key expires at 12:00:00. Within 50 ms, 5,000 concurrent requests get a cache miss and all fire the exact same heavy SQL query at PostgreSQL simultaneously.
  • Cache Penetration: Malicious or buggy clients request nonexistent IDs (GET /users/-1 or random UUIDs). Neither Redis nor Postgres has the row, so Redis never caches anything—and 100% of garbage traffic punches straight through to Postgres!

Stopping Stampedes

  • Request Coalescing (singleflight): Within each app process (or via distributed Redis lease SET lock:key 1 NX PX 2000), only 1 caller recomputes while others wait on the shared Future.
  • TTL Jitter: Add random jitter (base_ttl + rand(0, 60s)) so 100,000 warmed keys don’t expire at the exact same second.
  • Probabilistic Early Expiration (XFetch): Near TTL end, one lucky request refreshes asynchronously in the background before expiry.

Stopping Penetration & Eviction

  • Negative Caching: Cache __NULL__ with a short TTL (15–60s) when Postgres returns zero rows.
  • Bloom Filter: Check an in-memory/Redis Bloom filter of valid IDs before touching Postgres.
  • Eviction Policy: Configure Redis maxmemory-policy allkeys-lru or allkeys-lfu for caches, but noeviction when Redis also holds rate-limiters or queues!

Architecture 5. Polyglot Storage: When NOT to Force PostgreSQL

Rule #1 of pragmatic architecture: start with PostgreSQL until a specific workload outgrows its strengths. Adding a second database introduces another backup pipeline, failure mode, and consistency boundary. When you do hit a wall, pick the purpose-built engine:

Engine Category Top Examples When It Beats Plain Postgres Tradeoff / Anti-Pattern
Key-Value / Wide-Column DynamoDB, ScyllaDB, Cassandra Predictable <5ms lookups at millions of QPS with zero server ops; single-table access patterns. No ad-hoc JOINs or arbitrary aggregations; you must design PK/SK/GSI keys upfront.
Time-Series TimescaleDB (Postgres ext!), InfluxDB High-ingest IoT/telemetry metrics; 90%+ Gorilla/ZSTD compression; automated chunk retention & continuous rollups. Not meant for heavily updated transactional entities. (TimescaleDB lets you stay inside Postgres!)
Document Store MongoDB, Couchbase (vs Postgres JSONB) Rapidly evolving nested catalogs/CMS blobs needing built-in horizontal shard balancing. Lacks cross-document relational integrity guarantees; Postgres JSONB + GIN beats it for mixed relational+JSON apps.
Graph Database Neo4j, Amazon Neptune Deep multi-hop traversals (4–10+ hops: fraud rings, social shortest-path, supply-chain dependencies). Overkill for 1–3 hop hierarchies where PostgreSQL WITH RECURSIVE + indexes works cleanly.

Production Redis & DynamoDB Internals: Durability, Slots & GSIs
  • Redis Persistence & Sharding: RDB takes periodic point-in-time snapshots (fast restarts, minutes of data loss); AOF logs every write (appendfsync everysec = ≤1s loss). Redis Cluster shards keys across 16,384 hash slots using CRC16(key) % 16384 (use {hashtag} prefixes so multi-key commands land on one slot).
  • DynamoDB GSIs vs LSIs & Consistency: Local Secondary Indexes (LSIs) share the base partition key and support strongly consistent reads (10GB item-collection cap); Global Secondary Indexes (GSIs) replicate asynchronously to a new partition key and are always eventually consistent.

Summary 9. Lesson 15 Senior Engineering Checklist

  • Use Cache-Aside with explicit TTLs + jittered expiration to avoid synchronized thundering herds.
  • Protect Postgres from stampedes with singleflight/mutex leases, and from cache penetration with negative caching or Bloom filters.
  • Pick the right Redis primitive: ZSET for sliding-window rate limiters & leaderboards; Streams (not Pub/Sub) when consumers must survive restarts.
  • Model DynamoDB single-table keys (PK + SK) strictly around known access patterns—don’t expect ad-hoc joins.
  • Keep workloads in PostgreSQL (including JSONB and TimescaleDB) until measured QPS, retention, or graph-depth justifies another operational engine.
