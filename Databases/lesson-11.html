Room Bridge 1. Leaving Room’s Blocking Migration(1, 2) Behind

In Android Room, you write a Migration(1, 2) object that runs when the user launches the updated app. Only one binary version talks to that local SQLite file, and no web traffic hits it while ALTER TABLE executes. 

// Android Room: Only v2 app code runs after Migration(1, 2) finishes
val MIGRATION_1_2 = object : Migration(1, 2) {
    override fun migrate(db: SupportSQLiteDatabase) {
        db.execSQL("ALTER TABLE users RENAME COLUMN full_name TO display_name")
    }
}
Why RENAME COLUMN & Direct ALTER TABLE Break Rolling Production Deploys

During a rolling Kubernetes deploy, v1 pods and v2 pods run simultaneously against the exact same database for several minutes! If you run RENAME COLUMN full_name TO display_name before deploying v2, every running v1 pod immediately crashes with column "full_name" does not exist. Even worse, if your ALTER TABLE waits behind a single slow analytics query, PostgreSQL’s lock queue blocks all incoming SELECT traffic behind it!

Outage Mechanics 2. PostgreSQL Lock Queues & Mandatory lock_timeout

Every query in PostgreSQL acquires a table-level lock mode. Normal SELECT queries take ACCESS SHARE (compatible with reads/writes), while ALTER TABLE requests ACCESS EXCLUSIVE (incompatible with everything, including SELECT!).

Here is the trap: PostgreSQL grants locks in strict FIFO queue order to prevent writer starvation. If one 30-second reporting SELECT holds ACCESS SHARE, your 2-millisecond ALTER TABLE waits in the queue—and every new incoming checkout SELECT queues behind the waiting ALTER TABLE! Within 3 seconds, your connection pool saturates and the entire site goes down.

SET lock_timeout = '2s';

PostgreSQL Parity 3. CREATE INDEX CONCURRENTLY & Safe NOT NULL / CHECK

Index Builds Without Blocking Writes

Standard CREATE INDEX takes a SHARE lock (blocks all INSERT/UPDATE/DELETE for minutes). Always use CREATE INDEX CONCURRENTLY in production! Note: it cannot run inside an explicit BEGIN ... COMMIT transaction, and if it fails you must check pg_index.indisvalid and DROP INDEX CONCURRENTLY before retrying.

2-Step NOT NULL / CHECK Without Full Lock

Naive SET NOT NULL scans the whole table under ACCESS EXCLUSIVE. Instead: (1) ADD CONSTRAINT ... CHECK (col IS NOT NULL) NOT VALID; (instant metadata lock, enforces on new writes); (2) VALIDATE CONSTRAINT ...; (uses SHARE UPDATE EXCLUSIVE—does NOT block reads or writes!); (3) ALTER COLUMN col SET NOT NULL; (instant in PG 12+ because validated CHECK proves zero nulls!). 

-- PostgreSQL Safe 3-Step NOT NULL & Concurrent Index Pattern:
-- Step 1: Instant metadata lock (protects new writes immediately)
SET lock_timeout = '2s';
ALTER TABLE users ADD CONSTRAINT users_email_nn CHECK (email IS NOT NULL) NOT VALID;

-- Step 2: Online table scan (allows concurrent SELECT / INSERT / UPDATE / DELETE!)
ALTER TABLE users VALIDATE CONSTRAINT users_email_nn;

-- Step 3 (PG 12+): Instant metadata promotion, then drop redundant CHECK
ALTER TABLE users ALTER COLUMN email SET NOT NULL;
ALTER TABLE users DROP CONSTRAINT users_email_nn;

-- Non-blocking index build (MUST run outside BEGIN...COMMIT):
CREATE INDEX CONCURRENTLY idx_users_created_at ON users (created_at);
Good News Since PostgreSQL 11: ADD COLUMN ... DEFAULT & PG 18 NOT NULL NOT VALID

Since PostgreSQL 11+, adding a column with a non-volatile constant DEFAULT (like 'active', 0, or false) is an instant metadata-only operation (though you still need lock_timeout to enter the lock queue safely, while volatile defaults like DEFAULT random() still rewrite the table!). In PostgreSQL 18+, you can even run ALTER TABLE ... ADD CONSTRAINT ... NOT NULL ... NOT VALID directly without the temporary CHECK workaround. Also remember: in SQLite/Room, many schema changes require SQLite’s 12-step table rebuild (create new table → copy → drop old → rename).

Three More Zero-Downtime Hazards: INT → BIGINT, FKs, and DROP COLUMN
  • Changing INT to BIGINT PK: Direct ALTER COLUMN TYPE BIGINT rewrites the entire table under ACCESS EXCLUSIVE! Instead, use Expand-and-Contract (shadow id_v2 BIGINT column + backfill + swap or logical replication cutover).
  • Safe Foreign Keys: Use ALTER TABLE orders ADD CONSTRAINT fk_cust FOREIGN KEY (customer_id) REFERENCES customers(id) NOT VALID; followed by VALIDATE CONSTRAINT fk_cust;.
  • DROP COLUMN & SELECT *: Never run DROP COLUMN until zero running app pods use SELECT * or ORM entities mapping the old column; lint every PR with CI tools like squawk.

Zero-Downtime Pattern 4. Expand-and-Contract & Batched Backfills

Suppose you need to rename full_name → display_name (or split a column, or change a type) while v1 and v2 app servers coexist. You split the change into 4 safe deployments:

EXPAND
Add nullable display_name + dual-write trigger
→
PHASE 2
BACKFILL
Chunked keyset updates of historical rows
→
PHASE 3
SWITCH
Deploy v2 reading/writing new column; validate NOT NULL
→
PHASE 4
CONTRACT
Once v1 pods are gone, drop trigger & full_name

Why Bounded Batched Backfills Beat One Giant UPDATE

Running UPDATE orders SET new_col = old_col; on 100 million rows holds row locks for minutes, creates 100 million dead tuples (bloat!), saturates WAL replication bandwidth, and can stall autovacuum. Always backfill in bounded chunks (1,000–10,000 rows per transaction with short pauses): either via a keyset cursor loop (WHERE id > :last_id AND id <= :last_id + 5000, which never re-scans skipped rows!) or a partial-indexed NULL queue. Note also: in PostgreSQL, write dual-write triggers as BEFORE INSERT OR UPDATE mutating NEW.col := ... in-memory to avoid double MVCC row versions (in SQLite, AFTER triggers are used below because SQLite doesn’t support mutating NEW.* in BEFORE triggers).

Summary 8. Lesson 11 Senior Engineering Checklist

  • ALWAYS run DDL migrations with SET lock_timeout = '2s' + retry loop so a slow reader never causes an API-wide lock queue outage.
  • Always use CREATE INDEX CONCURRENTLY in production (outside a transaction block) and verify indisvalid = true.
  • Use the 2-step ADD CONSTRAINT ... CHECK (...) NOT VALID → VALIDATE CONSTRAINT pattern before SET NOT NULL.
  • Use Expand-and-Contract (4 phases: Expand + dual-write → Batched backfill → Switch reads → Contract) whenever v1 and v2 app servers overlap.
  • Chunk historical backfills in bounded keyset batches instead of updating millions of rows in one transaction.
