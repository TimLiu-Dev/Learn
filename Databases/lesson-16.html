OLTP vs OLAP, Columnar Engines (DuckDB/ClickHouse), Star Schemas & CDC

Your checkout API needs 2-millisecond point writes. Your CFO’s dashboard wants a 12-month revenue rollup across 200 million rows. Running both workloads on the same primary PostgreSQL instance is a classic recipe for buffer-pool eviction, IOPS starvation, and production outages. In 2027, senior engineers pair row-oriented OLTP with columnar OLAP engines (DuckDB, ClickHouse, Parquet) connected via Transactional Outbox + Change Data Capture (CDC).

Room Bridge 1. Why Running BI Dashboards on Your App Primary Causes Outages

In Android Room, aggregating 500 local expenses for a pie chart takes 1 ms on flash. On a production backend handling 5,000 TPS, a single analyst query scanning 80 GB of historical orders does three catastrophic things at once:

The 3-Way OLTP Meltdown from Ad-Hoc Analytics
  1. Buffer Pool Eviction: A sequential scan of 100M cold rows flushes hot user/session pages out of Postgres shared_buffers, causing sudden 10x latency spikes across every checkout API call.
  2. IOPS & CPU Saturation: Parallel hash joins and disk sorts consume 100% of EBS/NVMe bandwidth.
  3. MVCC Vacuum Pinning: Long-running analytical transactions pin old row versions (xmin horizon), blocking VACUUM from reclaiming dead tuples and causing rapid table bloat.

Storage Engines 2. Row-Oriented (OLTP) vs Columnar (OLAP: DuckDB / ClickHouse / Parquet)

Row-Oriented Storage (PostgreSQL, SQLite)

Stores all columns of Row 1 together on an 8 KB page, then Row 2, etc. Ideal for OLTP: inserting a complete order or fetching 1 customer row takes a single page read. Slow for OLAP: summing just 1 column (amount_cents) forces reading every wide text/JSON column on the page off disk!

Columnar Storage (DuckDB, ClickHouse, Parquet)

Stores all values of amount_cents contiguously, all values of country contiguously, etc. Ideal for OLAP: queries read only needed columns; identical types compress 5x–15x via Run-Length Encoding (RLE), Dictionary, and Delta encoding; Zone Maps (min/max per row group) skip 95% of chunks; and CPU SIMD vectorized execution scans millions of values per core per millisecond.

2027 Analytics Stack: DuckDB + Parquet vs ClickHouse
-- DuckDB queries S3 Parquet files directly with zero ETL server overhead (in-process OLAP!):
SELECT
  date_trunc('month', order_ts) AS month,
  country,
  SUM(amount_cents) / 100.0 AS revenue_usd
FROM read_parquet('s3://pulse-lake/orders/year=2027/*.parquet')
WHERE country IN ('US', 'CA')
GROUP BY 1, 2
ORDER BY 1, 3 DESC;

Dimensional Modeling 3. Star Schemas & Slowly Changing Dimensions (SCD Type 2)

Analytical warehouses reshape normalized OLTP tables into a Star Schema:

  • Fact Table (center): Narrow, append-only business events (fact_orders) holding numeric measures (amount_cents, qty) and foreign keys to dimensions.
  • Dimension Tables (rays): Descriptive context (dim_customer, dim_product, dim_date) optimized for fast filtering and grouping.

The SCD Type 2 Trap: Suppose Customer Maya was in tier 'free' in January (spending $50), then upgraded to 'enterprise' in March (spending $2,000). If you overwrite Maya’s row in place (SCD Type 1), your Q1 report suddenly claims a free-tier customer never bought anything and attributes January’s $50 to 'enterprise'! SCD Type 2 preserves historical truth by inserting a new version row with valid_from and valid_to (NULL for current) and joining facts on the order’s timestamp.

Data Pipelines 4. Transactional Outbox & Change Data Capture (Debezium)

How do OLTP mutations reach Kafka, ClickHouse, or Iceberg/Parquet without losing events or slowing down checkout?

Never Dual-Write to Postgres and Kafka in App Code!

If your API runs COMMIT on Postgres and then calls kafka.send(), a pod crash or network timeout between the two lines permanently loses the event. Conversely, sending to Kafka before COMMIT publishes phantom events for transactions that roll back!

  • Pattern 1 — Transactional Outbox: Write the business row (orders) and the event row (outbox_events) inside the exact same ACID transaction. A background relay (or Debezium) forwards outbox rows reliably.
  • Pattern 2 — WAL-Based CDC (Debezium): Debezium connects as a PostgreSQL logical replication consumer (pgoutput), tailing the Write-Ahead Log asynchronously with near-zero query overhead on OLTP tables and streaming INSERT/UPDATE/DELETE frames to Kafka → OLAP.
  • WAL Retention Trap: If Debezium goes down for days and its PostgreSQL replication slot stays open, Postgres cannot recycle WAL segments and will fill the primary disk until the DB crashes! Always configure max_slot_wal_keep_size + lag alerts.

2027 Lakehouse & Columnar Engines: Apache Iceberg, ClickHouse & Debezium Ops
  • Apache Iceberg / Delta Lake over Raw Parquet: Raw Parquet files on S3 lack transactions and safe schema evolution. Modern 2027 pipelines write Parquet inside an Apache Iceberg table format (ACID snapshot manifests, time travel, hidden partitioning, safe column renames) queried directly by DuckDB, Trino, or Spark.
  • ClickHouse MergeTree / ReplacingMergeTree: High-ingest OLAP stores sort data in immutable parts and merge asynchronously in the background; dedup happens during merges (use FINAL or argMax() when querying CDC feeds).
  • Debezium & Outbox Maintenance: Partition outbox_events by day/week so processed rows are dropped cleanly without VACUUM bloat, and note Debezium’s initial snapshot reads tables safely via incremental chunked watermarking.

Summary 8. Lesson 16 Senior Engineering Checklist

  • Keep heavy analytical scans off your OLTP primary (use columnar OLAP like DuckDB/Parquet or ClickHouse fed by CDC).
  • Never write SELECT * on columnar tables—projection pushdown only reads requested columns.
  • Use SCD Type 2 (valid_from / valid_to) for dimensions whose attributes change over time so historical facts stay accurate.
  • Eliminate dual-write race conditions with the Transactional Outbox or WAL-based CDC (Debezium).
  • Always set max_slot_wal_keep_size on PostgreSQL logical replication slots to prevent disk-full outages when CDC consumers pause.
