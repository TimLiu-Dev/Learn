Room Bridge 1. The Room @Insert(onConflict = REPLACE) Footgun

In Android Room, developers routinely annotate DAO methods with OnConflictStrategy.REPLACE thinking it performs an “upsert” (insert or update): 

// DANGER IN ROOM & SQLITE:
@Insert(onConflict = OnConflictStrategy.REPLACE)
suspend fun upsertProduct(product: ProductEntity)
Senior Trap: SQLite REPLACE Is Actually DELETE + INSERT!

Under the hood, Room’s REPLACE compiles to SQLite’s INSERT OR REPLACE. When a UNIQUE or PRIMARY KEY conflict occurs, SQLite deletes the existing row and inserts a brand-new row:

  • Child rows vanish or crash: If child tables reference it with ON DELETE CASCADE, all child rows are silently wiped! With ON DELETE RESTRICT, the write fails with FOREIGN KEY constraint failed!
  • IDs & defaults reset: Auto-incremented IDs change, and omitted columns like created_at get overwritten with defaults or NULL.
The Senior Fix: True SQL UPSERT (ON CONFLICT DO UPDATE)

Modern SQLite (3.24+) and PostgreSQL (9.5+) support true in-place upserts via INSERT ... ON CONFLICT (col) DO UPDATE SET .... It updates only the columns you specify on the existing row, preserves the primary key, keeps created_at intact, and never triggers ON DELETE actions.

Single-Pass Analytics 2. Conditional Aggregation (FILTER) & Multi-Level Rollups

Instead of running three separate queries for total orders, paid revenue, and refunded revenue, use the SQL-standard FILTER (WHERE ...) clause (supported in both SQLite 3.30+ and PostgreSQL 9.4+) to pivot metrics in a single scan:

  • COUNT(*) FILTER (WHERE status = 'paid') counts only rows matching the predicate.
  • COALESCE(SUM(amount_cents) FILTER (WHERE status = 'refunded'), 0) turns empty-bucket NULL sums into clean 0s!

Multi-Level Subtotals: PostgreSQL GROUPING SETS / ROLLUP vs SQLite Simulation

PostgreSQL Production Syntax: GROUPING SETS, ROLLUP & CUBE

PostgreSQL computes multi-level subtotals and grand totals in a single query using ROLLUP, CUBE, or explicit GROUPING SETS, plus GROUPING(col) (which returns 1 for a subtotal row vs 0 for a real NULL): 

-- PostgreSQL 17/18: Regional + Channel subtotals + Grand Total in one statement
SELECT
  COALESCE(region, 'ALL_REGIONS') AS region,
  COALESCE(channel, 'ALL_CHANNELS') AS channel,
  GROUPING(region) AS is_region_subtotal,
  SUM(amount_cents) AS revenue_cents
FROM channel_sales
GROUP BY ROLLUP (region, channel)
ORDER BY region NULLS LAST, channel NULLS LAST;

Set Algebra 3. UNION vs UNION ALL, INTERSECT & EXCEPT

  • UNION ALL: Concatenates two result sets verbatim (fast, zero sort/hash deduplication, preserves duplicates).
  • UNION: Concatenates and deduplicates every row across both sets (expensive sort/hash + silently drops duplicate amounts!).
  • INTERSECT: Returns rows present in both queries (deduplicated).
  • EXCEPT: Returns rows in the first query that do not appear in the second (ideal for finding missing events!).

Subtlety: Unlike WHERE NULL = NULL (which is UNKNOWN), SQL set operations (UNION, INTERSECT, EXCEPT) treat two NULL values in the same column position as equal!

Atomic Writes 4. Idempotent Upserts (ON CONFLICT) & RETURNING

In distributed systems, webhooks and mobile syncs get retried. Your database writes must be idempotent and race-free:

  • ON CONFLICT (col) DO NOTHING: Silently ignores duplicate idempotency keys / webhook IDs without failing the transaction.
  • ON CONFLICT (col) DO UPDATE SET ...: Updates the existing row in place. Use EXCLUDED.col to reference the incoming proposed values, and optionally add a WHERE guard (e.g., WHERE table.updated_at < EXCLUDED.updated_at) to ignore stale out-of-order messages!
  • RETURNING * (or specific columns): Returns inserted/updated values in the exact same atomic statement—supported in SQLite 3.35+ and PostgreSQL! No second SELECT round-trip or race condition.
Runnable Demo 4 INSERT OR REPLACE Footgun vs ON CONFLICT ... RETURNING
PostgreSQL 15–17 Parity: MERGE ... RETURNING, Partial Upserts & Batch Deadlocks
  • MERGE (PG 15+, MERGE ... RETURNING in PG 17): Great for batch ETL syncing (WHEN MATCHED THEN UPDATE / DELETE, WHEN NOT MATCHED THEN INSERT), whereas single-key OLTP writes should still prefer INSERT ... ON CONFLICT because MERGE is not immune to concurrent insert unique-violation races.
  • Partial Unique Index Targets: In Postgres, ON CONFLICT (email) WHERE deleted_at IS NULL DO UPDATE ... targets only active rows!
  • Multi-Row Upsert Deadlocks: When batch-upserting multiple rows in one statement, always sort the input rows by conflict key first so concurrent batches lock rows in identical order.
  • SQLite Quirk: INSERT OR REPLACE fires FOREIGN KEY actions when PRAGMA foreign_keys = ON, but skips ON DELETE triggers unless PRAGMA recursive_triggers = ON.

Summary 8. Lesson 4 Senior Engineering Checklist

  • Never use Room OnConflictStrategy.REPLACE / INSERT OR REPLACE on tables referenced by FKs or containing preserved columns like created_at.
  • Use COUNT(*) FILTER (WHERE ...) and COALESCE(SUM(...) FILTER (WHERE ...), 0) for single-scan conditional pivots.
  • Default to UNION ALL unless you explicitly need deduplication (where UNION also incurs sort/hash cost).
  • Use EXCEPT for clean set-difference reconciliation between external events and internal ledgers.
  • Combine ON CONFLICT (...) DO UPDATE SET ... (with EXCLUDED.*) + RETURNING for idempotent, race-free atomic writes.
