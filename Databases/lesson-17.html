Vector Databases, Embeddings, pgvector & Hybrid Search (2027 AI Stack)

In 2027, almost every production SaaS product ships AI search and Retrieval-Augmented Generation (RAG). Yet naive RAG pipelines fail in two classic ways: pure vector search misses exact SKUs/error codes, and HNSW post-filtering silently returns empty results for smaller tenants. In this lesson you’ll learn the exact math behind Cosine/L2/Inner Product, HNSW vs IVFFlat tradeoffs, and build real Hybrid Search + Reciprocal Rank Fusion (RRF) directly in SQL.

Room Bridge 1. Beyond Android LIKE '%query%'

In an Android Room DAO, searching support notes usually starts with WHERE body LIKE '%' || :query || '%' (or Room @Fts4). When a user types “card declined double charge”, LIKE fails completely if the policy doc says “payment authorization failure & duplicate settlement reversal”.

Why Postgres + pgvector Often Beats Standalone Vector DBs

Spinning up a separate vector database (Pinecone/Qdrant/Milvus) creates a synchronization problem: when a tenant deletes a confidential doc in PostgreSQL, stale embeddings can linger in the external vector store and leak into AI prompts! Keeping vector(1536) (or halfvec) right inside PostgreSQL + pgvector gives you ACID deletes, transactional chunk ingestion, and JOINs with tenant permissions in one engine.

Vector Math 2. Embeddings & Distance Metrics (Cosine, L2, Inner Product)

An embedding model turns text into a fixed-length array of floats (e.g., 1536 dimensions) where semantically similar meanings point in similar directions. Three similarity/distance metrics matter in SQL:

Metric Formula pgvector Operator When to Use
Cosine Similarity / Distance cos(θ) = (A · B) / (‖A‖ · ‖B‖), distance = 1 − cos(θ) <=> Default for text embeddings; compares vector angle regardless of magnitude.
L2 (Euclidean) Distance √Σ(ai − bi)² <-> When vector magnitude carries meaning (spatial, unnormalized embeddings).
Negative Inner Product −Σ(ai · bi) <#> Fastest when vectors are already L2-normalized (‖v‖ = 1), since cos(θ) = A · B!

Vector Indexing 3. Exact KNN vs ANN (HNSW vs IVFFlat)

Comparing a query vector against every single row (Exact KNN) guarantees 100% recall, but scanning 5 million 1536-D vectors takes seconds. Approximate Nearest Neighbor (ANN) indexes trade ~1–3% recall for sub-10 ms latency:

HNSW (Hierarchical Navigable Small World)

  • Multi-layer proximity graph (express highways at top layers, dense local links at bottom).
  • Pros: Best speed/recall tradeoff (~98%+ recall in <10 ms); works incrementally on empty tables!
  • Cons: High RAM footprint (must fit graph in memory!) & slower index builds (m, ef_construction).

IVFFlat (Inverted File Flat)

  • Partitions vectors into lists Voronoi clusters via k-means; queries probe nearest probes centroids.
  • Pros: Much smaller RAM & faster build time than HNSW.
  • Cons: Trap: Creating IVFFlat on an empty table builds useless centroids! Lower recall unless probes is tuned upward.
Production PostgreSQL + pgvector + tsvector Schema
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE rag_chunks (
  id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  tenant_id   UUID NOT NULL,
  doc_id      UUID NOT NULL,
  content     TEXT NOT NULL,
  tsv         TSVECTOR GENERATED ALWAYS AS (to_tsvector('english', content)) STORED,
  embedding   HALFVEC(1536) NOT NULL   -- halfvec cuts vector RAM & index size by 50%!
);

CREATE INDEX idx_rag_tsv  ON rag_chunks USING GIN (tsv);
CREATE INDEX idx_rag_hnsw ON rag_chunks USING hnsw (embedding halfvec_cosine_ops)
  WITH (m = 16, ef_construction = 64);

-- Tune search accuracy vs latency per session/transaction:
SET LOCAL hnsw.ef_search = 100;
SET LOCAL hnsw.iterative_scan = strict_order;  -- pgvector 0.8+: prevents post-filter starvation!

Senior Trap 4. The Metadata Pre-Filtering vs Post-Filtering Trap

Consider a multi-tenant RAG query: SELECT id, content FROM rag_chunks WHERE tenant_id = 't_small' ORDER BY embedding <=> $q LIMIT 5;

If Postgres navigates the global HNSW graph first (scanning the top ef_search = 40 global nearest neighbors) and applies WHERE tenant_id = 't_small' afterward (post-filtering), what happens if 't_small' owns only 0.2% of chunks? All 40 global candidates belong to huge tenants, so the post-filter throws them all away and returns 0 rows even though 't_small' has 500 valid documents!

  • Fix 1: Enable pgvector 0.8+ hnsw.iterative_scan = strict_order so the HNSW iterator keeps walking the graph until LIMIT 5 post-filtered rows are found.
  • Fix 2: Partition rag_chunks (or create partial HNSW indexes) by tenant_id for large tenants, or pre-filter with a B-tree/bitmap scan when a tenant has <5,000 chunks.

2027 Gold Standard 5. Hybrid Search + Reciprocal Rank Fusion (RRF)

Why does pure vector search still disappoint users on technical queries? If a user searches for ERR_PG_40001 or INV-2027-8841, dense embeddings blur specific alphanumeric identifiers into generic “error” or “invoice” vectors. Conversely, BM25 / tsvector nails exact tokens but misses synonyms.

Hybrid Search runs both lexical (keyword) search and vector similarity search, then merges the two incompatible score scales using Reciprocal Rank Fusion (RRF):

RRF Formula & Production pgvector Top-K Scaling Pattern

rrf_score(doc) = COALESCE(1.0 / (60 + lex_rank), 0.0) + COALESCE(1.0 / (60 + vec_rank), 0.0)
Because cosine similarity sits in [-1, 1] while BM25 scores are unbounded (note: native Postgres ts_rank lacks true corpus-wide IDF/length normalization unless paired with an extension like ParadeDB pg_search), converting both to ordinal ranks (1, 2, 3...) with k = 60 merges them cleanly.
Crucial Production Scale Rule: In the tiny 5-row SQLite demo below we rank all rows for clarity, but on 10M rows in PostgreSQL you MUST put ORDER BY ... LIMIT 50 inside each branch (so HNSW & GIN indexes execute instead of full-scanning!) and merge the two top-50 sets via FULL OUTER JOIN, optionally followed by a cross-encoder reranker (or binary quantization / DiskANN for tight RAM).

Summary 9. Lesson 17 Senior Engineering Checklist

  • Use Cosine (or negative Inner Product on unit-normalized vectors) for text embeddings.
  • Choose HNSW for high recall (>98%) and incremental inserts; size RAM carefully (consider halfvec). Never build IVFFlat on an empty table.
  • Prevent HNSW post-filtering empty results on selective tenant_id predicates via iterative scans, partitioning, or tenant-scoped pre-filtering.
  • Combine lexical search (tsvector/BM25) + vector similarity via Reciprocal Rank Fusion (RRF, k=60) so exact SKUs/error codes and semantic synonyms both surface.
  • Enforce UNIQUE(tenant_id, content_hash) and ON DELETE CASCADE on RAG chunk tables so deleted documents never haunt AI prompts.
