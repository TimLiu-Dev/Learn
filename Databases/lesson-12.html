Room Bridge 1. From 1 Local SQLite Connection to 500 Pods Hitting One Database

In Android Room, your app opens a single SQLite database file in-process (one connection pool of 1 writer + a few WAL readers). Network latency is 0ms, and you never worry about 5,000 concurrent devices holding TCP sockets open to your phone’s SQLite file.

Why “Open a Connection Per Request” Destroys Backend PostgreSQL

Unlike SQLite (an embedded C library inside your process), PostgreSQL uses a process-per-connection architecture: every TCP client connection forks a dedicated OS process (postgres backend) consuming ~5–10 MB of RAM, private work memory, and snapshot/lock bookkeeping. If 2,500 serverless Lambdas each open 2 connections, PostgreSQL spawns 5,000 OS processes (~35–50 GB RAM!), thrashing CPU caches and snapshot arrays until the Linux OOM killer terminates the primary!

Core Concept 2. PgBouncer Pooling Modes & Session-State Traps

PgBouncer (or RDS Proxy / Supavisor) sits between your 5,000 app sockets and PostgreSQL, multiplexing thousands of mostly-idle client connections onto a small pool of real PostgreSQL backend processes (e.g., default_pool_size = 25).

PgBouncer Mode When Server Conn Returns to Pool Multiplexing Power What Breaks / Caveats
session Only when client disconnects. Low (1:1 while client connected). Nothing breaks, but idle Lambda/pod pools still starve DB slots.
transaction (Recommended) Immediately on COMMIT / ROLLBACK! Huge (5,000 clients → 25 PG backends). Breaks session-pinned state: SET (use SET LOCAL), LISTEN/NOTIFY, CREATE TEMP TABLE, session advisory locks, and older named prepared statements (unless PgBouncer ≥ 1.21 max_prepared_statements > 0).
statement After every single SQL statement. Extreme. Multi-statement BEGIN ... COMMIT transactions are completely disallowed!

Math & Resilience 3. Pool Sizing (Little’s Law) & Essential Timeouts

Counterintuitively, increasing PostgreSQL’s pool size from 30 to 500 almost always makes throughput WORSE due to CPU context switching and spinlock/snapshot contention. By Little’s Law (L = λ × W), if an 8-vCPU NVMe database executes queries in W = 2ms on average, just L = 20 active connections have a theoretical ceiling of 20 / 0.002 = 10,000 QPS (target ~50–70% utilization in practice for queueing headroom and network RTT!).

The Classic cores × 2 + spindles Rule: Myth vs Reality

You’ll often hear the old formula pool_size = (CPU_cores × 2) + effective_spindle_count. That rule was written for one app process on spinning HDDs. On modern NVMe cloud SSDs (0 spindles, high IOPS) with 50 microservices pods, the real rule is: keep the total active connections across the entire cluster inside PgBouncer’s default_pool_size around 2–4 × DB_vCPUs (e.g., 16–32 for an 8-vCPU DB), while max_client_conn absorbs thousands of idle app sockets (or use RDS Proxy / Supavisor for serverless fleets).

The Essential Production Timeouts (Including PostgreSQL 17 transaction_timeout)

-- PostgreSQL: Bake defensive timeouts directly onto the app database role!
ALTER ROLE app_writer SET statement_timeout = '5s';
ALTER ROLE app_writer SET lock_timeout = '2s';
ALTER ROLE app_writer SET idle_in_transaction_session_timeout = '15s';
ALTER ROLE app_writer SET transaction_timeout = '30s'; -- PG 17+: caps total BEGIN..COMMIT time even across many fast queries!

-- App connection string: connect_timeout=3 & tcp_keepalives_idle=60 (plus pool maxLifetime < NAT timeout!)
-- SQLite / Room equivalent for local write contention:
-- PRAGMA journal_mode = WAL;
-- PRAGMA busy_timeout = 5000;

Security 4. Parameterized Queries & Allow-Listed Dynamic Sorting

Bind parameters ($1, $2 in PostgreSQL; ? in SQLite) separate SQL syntax from user-supplied data values, completely neutralizing classic SQL injection. Hidden traps: You cannot parameterize table names, column names, or sort directions (ORDER BY $1 sorts by a literal constant!). Map API ?sort=... keys through a strict server-side allow-list. Also: while ORDER BY CASE ... below is injection-safe in pure SQL, it blocks B-Tree index ordering on huge tables—in backend code, map an enum allow-list directly to pre-written static ORDER BY queries, use = ANY($1) for dynamic IN arrays, escape %/_ in LIKE patterns, and use format('%I', ident) / quote_ident() if dynamic identifiers are unavoidable.

Summary 8. Lesson 12 Senior Engineering Checklist

  • Put PgBouncer (or RDS Proxy) in transaction pooling mode in front of PostgreSQL whenever running pods/serverless fleets.
  • Never rely on session state (SET, CREATE TEMP TABLE, LISTEN, session advisory locks) through a transaction pooler.
  • Size the backend PostgreSQL pool near 2–4 × CPU cores using Little’s Law—never 500+ active Postgres processes.
  • Set connect_timeout, statement_timeout, lock_timeout, and idle_in_transaction_session_timeout on every app DB role (and PRAGMA busy_timeout on SQLite).
  • Use bind parameters for values and strict server-side allow-lists for dynamic column names and ORDER BY directions.
