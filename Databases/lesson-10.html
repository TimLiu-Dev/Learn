Room Bridge 1. Concurrency Without SQLITE_BUSY or Deadlock Cascades

In Android Room, if two background workers (say WorkManager + a foreground ViewModel) try to write simultaneously without WAL or busy_timeout, SQLite throws SQLiteDatabaseLockedException (SQLITE_BUSY). On PostgreSQL, you don’t get a whole-file lock error—instead, transactions acquire fine-grained row-level locks.

Why Fine-Grained Row Locks Create New Failure Modes

With fine-grained row locks, two transactions touching different rows never block each other. However, if Transaction A locks row 1 and then waits on row 2, while Transaction B locked row 2 and waits on row 1, they form a deadlock cycle. And if 40 workers run SELECT * FROM jobs WHERE status = 'queued' LIMIT 1 FOR UPDATE without SKIP LOCKED, 39 workers stall waiting on the exact same first row!

Core Concept 2. Pessimistic Row Locks vs Optimistic Concurrency (CAS)

You have two primary strategies to serialize edits to a specific row without full SERIALIZABLE isolation:

Pessimistic Locking (PostgreSQL)

  • SELECT ... FOR UPDATE: exclusive row lock until COMMIT/ROLLBACK.
  • SELECT ... FOR SHARE: shared lock; blocks writers, allows other readers with FOR SHARE.
  • NOWAIT: fail immediately with lock-not-available instead of blocking HTTP threads.
  • SKIP LOCKED: skip rows locked by other transactions (perfect for queues!).

Optimistic Concurrency Control (OCC / CAS)

  • No long-held DB lock during user think-time or external HTTP calls!
  • Store a monotonic version INTEGER column on the row.
  • Update with Compare-And-Swap: WHERE id = ? AND version = ?, incrementing version = version + 1.
  • If 0 rows modified → conflict! Reload & retry (or return HTTP 409 Conflict).
-- PostgreSQL Pessimistic Lock (when you MUST hold the row across multi-step SQL logic):
BEGIN;
  SELECT balance_cents FROM accounts WHERE id = 42 FOR UPDATE NOWAIT;
  -- App validates rules / computes fee while row 42 is locked
  UPDATE accounts SET balance_cents = balance_cents - 1500 WHERE id = 42;
COMMIT;

Senior Trap: Using OCC on Hot Contention Rows (Flash Sales)

OCC shines when conflicts are rare (editing profiles, tickets, documents). If 5,000 users try to buy the last 10 concert tickets on sku = 'VIP' simultaneously, OCC causes a 99.8% retry storm! On hot rows, use atomic SQL (WHERE stock >= 1), pessimistic FOR UPDATE, or sharded inventory buckets.

Deadlock Prevention 3. Deadlocks & Deterministic Lock Ordering

A deadlock occurs when two transactions hold locks the other needs and wait in a cycle:

  • Tx A (Transfer 1 → 2): locks account 1, then tries to lock account 2.
  • Tx B (Transfer 2 → 1): locks account 2, then tries to lock account 1.
  • PostgreSQL’s deadlock detector wakes up after deadlock_timeout (default 1s), aborts one victim with SQLSTATE 40P01, and lets the other proceed.

The Mathematical Cure: Deterministic Lock Ordering. If every transaction ALWAYS acquires locks in sorted primary-key order (MIN(from_id, to_id) first, MAX(from_id, to_id) second), a cycle in the Wait-For Graph is mathematically impossible!

PostgreSQL One-Liner to Lock Multiple Rows Safely

In PostgreSQL, SELECT id FROM accounts WHERE id IN ($1, $2) ORDER BY id ASC FOR UPDATE; acquires row locks in deterministic ascending ID order in a single round-trip! (Note: in SQLite, MIN(a, b) takes 2+ scalar arguments, whereas in PostgreSQL the 2-argument scalar function is called LEAST(a, b) / GREATEST(a, b).)

Production Patterns 4. SKIP LOCKED Queues, Idempotency Keys & Advisory Locks

Pattern A: PostgreSQL Job Queue with FOR UPDATE SKIP LOCKED

Need a reliable transactional job queue without deploying Kafka on day 1? PostgreSQL’s SKIP LOCKED lets 100 concurrent workers claim distinct jobs with zero blocking and zero duplicate execution: 

-- PostgreSQL Production Worker Claim (runs inside a single atomic CTE):
WITH next_job AS (
  SELECT id
  FROM jobs
  WHERE status = 'queued' AND run_at <= now()
  ORDER BY priority DESC, id ASC
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
UPDATE jobs
SET status = 'running', worker_id = $1, started_at = now(), attempts = attempts + 1
FROM next_job
WHERE jobs.id = next_job.id
RETURNING jobs.*;

Pattern C: PostgreSQL Advisory Locks

Need a distributed mutex across 20 backend pods without standing up ZooKeeper or Redis Redlock? PostgreSQL provides RAM-only Advisory Locks keyed by 64-bit integer: 

-- Transaction-scoped advisory lock (automatically released on COMMIT or ROLLBACK!):
BEGIN;
  SELECT pg_try_advisory_xact_lock(hashtext('nightly-billing-cron'));
  -- Returns true on the single winning pod, false immediately on the other 19 pods!
COMMIT;
Production Queue & Lock Hardening (Lease Recovery, FOR NO KEY UPDATE & Diagnostics)
  • Crashed-Worker Lease Reaper: If a worker holding a job crashes after marking status = 'running', that job stays stuck forever unless you stamp lease_expires_at = now() + interval '30 seconds' and run a reaper (or claim WHERE status = 'queued' OR (status = 'running' AND lease_expires_at < now())) up to max_attempts before moving to DEAD_LETTER.
  • Advisory Lock Collisions: hashtext() is 32-bit (~65k birthday collision risk); use two-argument pg_try_advisory_xact_lock(namespace_int, entity_id) or 64-bit hashtextextended(..., 0) for per-tenant/per-entity locks.
  • Parent/Child Lock Strength: Use FOR NO KEY UPDATE (instead of FOR UPDATE) when updating non-PK columns so child tables taking FOR KEY SHARE FK checks aren’t blocked, and always index FK columns! Inspect live production lock queues via SELECT pid, pg_blocking_pids(pid), wait_event FROM pg_stat_activity;.

Summary 8. Lesson 10 Senior Engineering Checklist

  • Use Optimistic Concurrency Control (version = version + 1 WHERE id = ? AND version = ?) for low-contention edits and user forms with think-time.
  • Eliminate deadlocks permanently by acquiring multi-row locks in deterministic sorted ID order (ORDER BY id ASC or LEAST(a,b)/GREATEST(a,b)).
  • Never build a DB worker queue with plain FOR UPDATE—always add SKIP LOCKED so workers never queue up behind each other.
  • Always store idempotency_keys in the same atomic transaction as financial/order mutations using ON CONFLICT DO NOTHING.
  • Prefer transaction-scoped advisory locks (pg_try_advisory_xact_lock) over session-scoped ones (especially behind PgBouncer!).
