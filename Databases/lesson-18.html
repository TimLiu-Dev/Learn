Database Security (RLS), Multi-Tenancy, Observability & Cloud FinOps

A single missing WHERE tenant_id = $1 in one API handler is a company-ending security breach. Senior engineers never rely on application code alone for tenant isolation—they enforce PostgreSQL Row-Level Security (RLS) inside the database engine, pair it with least-privilege roles, diagnose fleet-wide bottlenecks via pg_stat_statements, and eliminate wasteful IOPS and dead-index cloud spend.

Room Bridge 1. When One Missing WHERE Clause Leaks Every Customer

On Android, SQLite lives inside one user’s encrypted app sandbox; there is only one tenant per database file. In a multi-tenant B2B SaaS backend, 5,000 companies share the same PostgreSQL tables.

Defense in Depth Inside the Database Engine

Even with code reviews and unit tests, developers eventually forget AND tenant_id = ? in a new reporting endpoint or admin script. With Row-Level Security (RLS), PostgreSQL injects the tenant predicate automatically at the storage-plan boundary—turning a catastrophic cross-tenant data leak into an empty result set or permission error!

Architecture 2. Multi-Tenancy Models Compared

Model Isolation Schema Migrations Scale Ceiling & Best Use
Shared Table + tenant_id + RLS (Pool) Logical (enforced by RLS policy) Run once on 1 set of tables Scales to 100,000+ tenants. Default choice for modern B2B SaaS.
Schema-per-Tenant (Bridge) Separate namespace per tenant Must migrate N schemas sequentially Trap past ~500–1,000 schemas: pg_catalog bloat & slow ALTER TABLE deploys.
DB-per-Tenant (Silo) Physical DB / cluster isolation Orchestrated across N DBs Best for strict HIPAA/FedRAMP whale customers (hybrid: Pool for SMB, Silo for Enterprise).

Security & RLS 3. PostgreSQL Row-Level Security, PgBouncer Trap & PII Masking

In PostgreSQL, enabling RLS binds every SELECT, INSERT, UPDATE, and DELETE to an explicit policy evaluated against a transaction-local GUC variable (app.current_tenant_id).

Production PostgreSQL 17 RLS + Least-Privilege Role DDL
-- 1. Never let the app connect as table owner or superuser (they bypass RLS by default!)
CREATE ROLE app_runtime NOINHERIT LOGIN PASSWORD '...';
REVOKE ALL ON SCHEMA public FROM PUBLIC;
GRANT SELECT, INSERT, UPDATE ON invoices TO app_runtime;

-- 2. Enable AND FORCE RLS (so even table owners obey policies if tested)
ALTER TABLE invoices ENABLE ROW LEVEL SECURITY;
ALTER TABLE invoices FORCE ROW LEVEL SECURITY;

-- 3. Fail-closed InitPlan policy: wrapping in (SELECT ...) evaluates current_setting() ONCE per statement instead of per row!
--    USING filters existing rows (SELECT/UPDATE/DELETE); WITH CHECK validates new/modified rows (INSERT/UPDATE).
CREATE POLICY tenant_isolation ON invoices
  USING (tenant_id = (SELECT NULLIF(current_setting('app.current_tenant_id', true), '')::uuid))
  WITH CHECK (tenant_id = (SELECT NULLIF(current_setting('app.current_tenant_id', true), '')::uuid));

-- 4. Views on RLS tables: ALWAYS use security_invoker = true (PG 15+), or the view runs as the owner and bypasses RLS!
CREATE VIEW v_tenant_invoices WITH (security_invoker = true) AS
SELECT id, tenant_id, amount_cents FROM invoices;

-- 5. CRITICAL PgBouncer Transaction Pooling Rule: ALWAYS use SET LOCAL inside BEGIN ... COMMIT!
BEGIN;
  SET LOCAL app.current_tenant_id = '11111111-1111-1111-1111-111111111111';
  SELECT * FROM v_tenant_invoices; -- Safely sees ONLY tenant 1111...
COMMIT;
Three Fatal RLS & Transport Security Bugs
  • Bug #1 — BYPASSRLS / Table Owner: Superusers and roles with BYPASSRLS skip RLS silently; table owners also skip RLS unless FORCE ROW LEVEL SECURITY is enabled. Always test RLS as your actual app_runtime role!
  • Bug #2 — Views Without security_invoker = true: Standard PostgreSQL views run as the view owner (often a migration admin) and silently bypass RLS unless created WITH (security_invoker = true) (PG 15+).
  • Bug #3 — Session SET behind PgBouncer & Weak TLS: Plain SET app.current_tenant_id leaks tenant context across PgBouncer connections (always use SET LOCAL), and production connections should enforce sslmode=verify-full (or IAM auth) in pg_hba.conf.

Observability 4. Production Forensics: pg_stat_statements, Cache Hit Ratio & Locks

Never guess which query is burning your database CPU. Enable pg_stat_statements and watch four critical signals:

  • total_exec_time vs mean_exec_time: A slow 800 ms admin query run twice a day uses 1.6 s of CPU. A 4 ms missing-index query fired 500,000 times/hour burns 2,000 seconds of CPU (crashing your cluster!). Always rank by total_exec_time (% of total DB time) first.
  • Buffer Cache Hit Ratio: SUM(shared_blks_hit) / (SUM(shared_blks_hit) + SUM(shared_blks_read)). Healthy OLTP databases stay at > 99%. Dropping below 95% signals either working-set growth (upgrade RAM) or sequential scans evicting cache.
  • Dead Tuples & Bloat: Watch pg_stat_user_tables.n_dead_tup to catch stalled autovacuum or long-lived idle transactions pinning old MVCC snapshots.
  • Lock Waits: Query pg_locks + pg_blocking_pids(pid) to spot blocked DDL migrations or unindexed FK deletes.

Cloud FinOps 5. Right-Sizing IOPS, Dead Indexes & Archival Costs

Databases are frequently #1 or #2 on a SaaS startup’s AWS/GCP invoice. Four high-ROI FinOps levers require zero feature sacrifices:

Drop Unused & Duplicate Indexes

Check pg_stat_user_indexes WHERE idx_scan = 0 (excluding primary/unique constraints). Every unused 40 GB index wastes EBS storage, bloats snapshots, steals RAM cache, and blocks Postgres HOT updates whenever an update touches an indexed column (reclaim bloated tables online via pg_repack rather than locking with VACUUM FULL)!

Fix Missing Indexes Before Buying IOPS

Paying $3,000/mo for provisioned 30,000 IOPS because one query does sequential scans on a 200 GB table is classic waste. Adding one composite/partial index often drops IOPS 90% overnight.

Summary 9. Lesson 18 Senior Engineering Checklist

  • Enforce multi-tenant isolation in Postgres with ENABLE + FORCE ROW LEVEL SECURITY and a non-owner, non-BYPASSRLS runtime role.
  • Behind PgBouncer transaction pooling, always bind tenant context with SET LOCAL (never session-scoped SET).
  • Expose masked views to support/analytics roles so raw emails/SSNs never leave privileged schemas.
  • Triage performance via pg_stat_statements ordered by total_exec_time and monitor cache hit ratio (>99% OLTP target).
  • Audit unused non-unique indexes (idx_scan = 0) and cold-partition archival before upgrading cloud IOPS/storage tiers.
