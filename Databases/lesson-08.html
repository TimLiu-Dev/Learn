Phase 2 • Lesson 8 Durability & Concurrency Internals WAL, MVCC & VACUUM

Crash Recovery, WAL, MVCC Tuple Versioning & Vacuum Bloat

How can a database promise zero data loss when the power cord is yanked mid-transaction, while simultaneously letting thousands of readers query consistent snapshots without blocking writers? The answer lies in Write-Ahead Logging (WAL), MVCC tuple versioning, and disciplined VACUUM hygiene.

Room Bridge 1. Why Room Defaults to WAL Mode—and How Server PostgreSQL Differs

Starting in Android Pie (API 28), Room enables JournalMode.WRITE_AHEAD_LOGGING (PRAGMA journal_mode = WAL;) by default: 

Room.databaseBuilder(context, AppDatabase::class.java, "app.db")
    // Default in modern Room: WRITE_AHEAD_LOGGING
    // Allows background UI reads concurrently while a coroutine writes!
    .setJournalMode(RoomDatabase.JournalMode.WRITE_AHEAD_LOGGING)
    .build()
SQLite WAL vs PostgreSQL MVCC + WAL

In SQLite WAL mode, readers don’t block the writer and the writer doesn’t block readers—but there is still only ONE writer at a time across the whole database file! In PostgreSQL, WAL handles crash durability while MVCC (Multi-Version Concurrency Control) stores row versions right inside heap pages so hundreds of writers on different rows run concurrently without blocking readers or each other.

Durability 2. Write-Ahead Logging (WAL), fsync, Checkpoints & ARIES Recovery

Modifying scattered 8KB B+Tree pages directly on disk before returning COMMIT OK has two fatal flaws: random disk I/O is slow, and a power cut halfway through leaves torn/half-written pages.

  • The WAL Rule: Before any dirty data page is allowed to overwrite the main datafile, its log record (what changed + lsn Log Sequence Number) MUST be appended sequentially to the WAL and flushed via fsync().
  • Commit = Sequential WAL Flush: On COMMIT, the engine appends a COMMIT record and calls fsync() on the WAL file alone—dirty heap pages stay in RAM and flush lazily later!
  • Checkpoints: Periodically (or when WAL hits max_wal_size), a background checkpointer flushes dirty pages from RAM to the main datafile and advances the redo recovery starting point so old WAL segments can be recycled.
  • ARIES Crash Recovery (Redo + Undo): After a crash, the engine replays WAL forward from the last checkpoint (Redo) to bring pages back to the exact crash state, then rolls back any transaction that lacked a COMMIT record (Undo—note PostgreSQL doesn’t even need Undo because uncommitted MVCC tuples are simply invisible!).

SQLite Journaling 3. Rollback Journal (DELETE) vs WAL Mode

Rollback Journal (DELETE, legacy default)

  • Copies original pages into -journal, overwrites main .db in place, deletes journal on commit.
  • Writers block readers and readers block writers (2× I/O + lock contention).

SQLite WAL Mode (Room default)

  • Appends new page frames to -wal; main .db stays untouched until checkpoint.
  • Readers record an end-of-WAL mark and read concurrently with 1 writer!
  • Trap: A long-running open read transaction prevents checkpoints from resetting -wal, causing unbounded WAL file growth!

Concurrency 4. PostgreSQL MVCC: xmin, xmax & Snapshot Isolation

In PostgreSQL, UPDATE never overwrites a row in place. Every physical tuple header carries two transaction IDs:

  • xmin: The txid that inserted (created) this tuple version.
  • xmax: The txid that deleted or updated this tuple version (0 if untouched, or a row-locker XID/MultiXactId flagged by HEAP_XMAX_LOCK_ONLY when locked via SELECT ... FOR UPDATE).

When you run UPDATE wallets SET balance = 80 WHERE id = 1, PostgreSQL sets xmax = current_txid on the old tuple AND inserts a brand-new tuple with xmin = current_txid, xmax = 0! A real PostgreSQL snapshot records (xmin, xmax, xip[])—tracking which transactions were still in-flight (xip[]) at snapshot start so even if one commits a millisecond later, the older snapshot keeps ignoring it. Readers never block writers, and writers never block readers.

Bloat & Maintenance 5. Dead Tuples, HOT Updates, VACUUM vs VACUUM FULL & TXID Wraparound

Keeping old tuple versions enables lock-free MVCC—but once all active transactions move past an old tuple’s xmax, that tuple becomes a dead tuple wasting disk and buffer pool RAM.

  • HOT (Heap-Only Tuple) Updates: If an UPDATE does not change any indexed column AND the same 8KB heap page has free space (tuned via fillfactor = 80 on update-heavy tables), PostgreSQL avoids touching any secondary indexes by chaining the new tuple directly on the same page!
  • VACUUM (Standard / Autovacuum): Runs online without blocking reads or writes. Marks dead tuples reusable inside existing heap pages, updates the Visibility Map (enabling Index-Only Scans!), and freezes old xmins. Note: space is reused by future inserts, not returned to the OS unless trailing pages are empty.
  • VACUUM FULL (Senior Outage Trap!): Rewrites the entire table + all indexes to shrink the OS file—while holding an ACCESS EXCLUSIVE lock that blocks every SELECT, INSERT, and UPDATE for minutes/hours! Use pg_repack online instead (and REINDEX CONCURRENTLY for bloated indexes). Note: PostgreSQL 17 introduced a streaming TidStore removing the legacy 1GB maintenance_work_mem cap for dead-tuple tracking.
  • AUTOVACUUM Scale Factor Trap: Default autovacuum_vacuum_scale_factor = 0.2 (20%) means a 100M-row table accumulates 20 MILLION dead tuples before autovacuum even wakes up! Tune per-table autovacuum_vacuum_scale_factor = 0.01 (1%) or fixed thresholds on large tables.
  • TXID Wraparound: PostgreSQL transaction IDs are 32-bit (~4.2 billion, ~2.1B visible horizon). VACUUM FREEZE kicks in around autovacuum_freeze_max_age (200M default); if neglected as age(relfrozenxid) approaches 2 billion, PostgreSQL shuts down writes to prevent ancient rows from suddenly looking “in the future”!
Durability Parity: full_page_writes & synchronous_commit

OS disk blocks (4KB) are smaller than PostgreSQL 8KB pages, so a crash mid-write can leave a torn page. Keeping full_page_writes = on logs the full page image on the first change after each checkpoint so WAL recovery repairs torn pages cleanly. You can also tune durability vs latency per transaction with synchronous_commit (on = flush primary + standby WAL; local = flush primary only; off = async group commit risk up to ~wal_writer_delay).

PostgreSQL Parity: Monitoring Dead Tuples & Wraparound Risk
-- Inspect live vs dead tuples & transaction age in production PostgreSQL:
SELECT
  relname,
  n_live_tup,
  n_dead_tup,
  round(100.0 * n_dead_tup / NULLIF(n_live_tup + n_dead_tup, 0), 2) AS dead_pct,
  age(c.relfrozenxid) AS txid_age
FROM pg_stat_user_tables s
JOIN pg_class c ON c.oid = s.relid
ORDER BY n_dead_tup DESC LIMIT 10;

Summary 9. Lesson 8 Senior Engineering Checklist

  • WAL gives durability via sequential fsync() before commit acknowledgment and enables ARIES crash recovery.
  • In SQLite WAL mode, close read transactions promptly so readers don’t starve WAL checkpoints.
  • PostgreSQL MVCC never overwrites tuples in place: xmin/xmax let readers and writers run concurrently without blocking.
  • Never run VACUUM FULL in production traffic (ACCESS EXCLUSIVE lock); tune autovacuum_vacuum_scale_factor down on massive tables and use fillfactor to encourage HOT updates.
  • Monitor age(relfrozenxid) so VACUUM FREEZE prevents catastrophic TXID wraparound lockouts.
