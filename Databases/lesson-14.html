Partitioning, Horizontal Sharding & Distributed Consensus (NewSQL)

Vertical scaling carries a single PostgreSQL primary surprisingly far (64+ vCPUs, 512 GB RAM, NVMe RAID). Eventually, though, you hit hard physical walls: multi-terabyte B-trees no longer fit in RAM, VACUUM lags behind write velocity, or a single region’s write IOPS saturate. Senior engineers know the exact ladder: partition locally first, shard only when forced, and understand the distributed consistency taxes you pay when you cross node boundaries.

Room Bridge 1. Scaling Past a Single Database Machine

In Android Room, one device holds one user’s data in one SQLite file—a single table rarely exceeds a few hundred thousand rows. In a multi-tenant cloud backend, a single events or ledger_entries table can reach 10 billion rows (8 TB) on one machine.

The Scaling Escalation Ladder (Don’t Jump to Sharding on Day 1)

Every rung upward adds operational complexity and sacrifices some SQL ergonomics. Always exhaust cheaper rungs first: (1) Indexing & Query Tuning → (2) Vertical Scale + Read Replicas → (3) Declarative Table Partitioning (still 1 DB!) → (4) Horizontal Sharding / NewSQL.

Strategy Nodes Primary Bottleneck Solved Key Tradeoff / Limitation
Vertical Scaling 1 Primary (+ Read Replicas) CPU, RAM buffer pool, NVMe IOPS Hardware ceiling; single-writer lock & failover blast radius.
Declarative Partitioning 1 Primary (split into child tables) Index bloat, VACUUM duration, instant archival (DROP) Does not add more CPU/RAM/write throughput across machines.
Horizontal Sharding N Independent DB Nodes Write throughput & total storage beyond 1 machine No native cross-shard JOINs or ACID transactions; hot-shard skew; resharding pain.
NewSQL (Spanner / CockroachDB / TiDB) Distributed Raft/Paxos Cluster Horizontal write scale with distributed ACID SQL Higher write latency (network quorum RTT per commit); distributed deadlock/clock sync overhead.

Core Concept 2. Declarative Partitioning in PostgreSQL

Table partitioning splits one logical parent table into smaller physical child tables on the same PostgreSQL server. Your application still queries the parent table, while Postgres’s planner routes reads and writes to the matching child partition.

  • RANGE Partitioning: Most common for time-series, logs, and ledger events (e.g., 1 partition per month on created_at).
  • LIST Partitioning: Discrete values like region IN ('us-east', 'eu-west') or large enterprise tenants.
  • HASH Partitioning: Evenly spreads rows across N buckets (MODULUS 16) to keep individual B-trees shallow when no natural time range exists.

Why Partitioning Saves Production Systems: Pruning & Instant Archival

  1. Partition Pruning: When your query includes WHERE created_at >= '2027-02-01' AND created_at < '2027-03-01', the planner skips all other monthly B-trees completely.
  2. Zero-Bloat Archival: Deleting 100 million old rows with DELETE FROM events WHERE created_at < ... generates huge WAL spikes and dead-tuple bloat requiring days of VACUUM. With monthly partitions, you simply run ALTER TABLE events DETACH PARTITION events_2026_01 CONCURRENTLY; and DROP TABLE events_2026_01;—an instant filesystem unlink!
Production PostgreSQL 17 Declarative Partitioning DDL
CREATE TABLE audit_events (
  id          BIGINT GENERATED ALWAYS AS IDENTITY,
  tenant_id   UUID NOT NULL,
  created_at  TIMESTAMPTZ NOT NULL,
  event_type  TEXT NOT NULL,
  payload     JSONB NOT NULL,
  PRIMARY KEY (created_at, id)  -- Partition key MUST be part of any PK / UNIQUE constraint!
) PARTITION BY RANGE (created_at);

CREATE TABLE audit_events_2027_01 PARTITION OF audit_events
  FOR VALUES FROM ('2027-01-01 00:00:00+00') TO ('2027-02-01 00:00:00+00');

CREATE TABLE audit_events_2027_02 PARTITION OF audit_events
  FOR VALUES FROM ('2027-02-01 00:00:00+00') TO ('2027-03-01 00:00:00+00');

-- Instant archival with zero VACUUM bloat:
ALTER TABLE audit_events DETACH PARTITION audit_events_2027_01 CONCURRENTLY;
DROP TABLE audit_events_2027_01;
Senior Trap: Forgetting the Partition Key, DEFAULT Partitions & Automation

In PostgreSQL, a PRIMARY KEY or UNIQUE constraint on a partitioned table must include the partition key (Postgres enforces uniqueness per-partition B-tree, not globally across partitions). Also, if a query filters by id = 42 without created_at, Postgres scans all 60 monthly partitions! Automate monthly partition creation/retention with pg_partman, and beware of adding a DEFAULT partition: attaching a new future month forces Postgres to scan the entire DEFAULT partition under an ACCESS EXCLUSIVE lock to prove no overlapping rows live there!

Scale Architecture 3. Horizontal Sharding, Shard Keys & The Hot-Shard Problem

When one primary database can no longer absorb your write IOPS or total disk footprint, you move to horizontal sharding: splitting rows across multiple independent database instances (e.g., Shard 0..3, or Vitess/Citus).

Hash Sharding (hash(shard_key) % N)

  • Spreads writes uniformly across nodes, avoiding chronological write hotspots.
  • Range scans (WHERE tenant_id BETWEEN 10 AND 50) must scatter-gather across all shards.
  • Naive modulo % N makes adding a 5th shard painful unless you use consistent hashing / virtual shards.

Range Sharding (Key Ranges per Node)

  • Contiguous key ranges live together, making range scans fast on a single shard.
  • Classic failure: Sharding by created_at sends 100% of today’s live inserts to the newest shard while older shards sit idle!
  • Requires dynamic range splitting (how CockroachDB / TiKV rebalance 64 MB ranges).

The Hot-Shard (Celebrity) Problem & Cross-Shard Limitations

Suppose you shard a multi-tenant SaaS database by tenant_id. Everything balances nicely—until Enterprise MegaCorp (tenant_id = 999) signs up and generates 80% of all cluster traffic. That single tenant saturates Shard 3 while Shards 0, 1, and 2 sit at 8% CPU!

  • Mitigation 1 — Composite / Salted Shard Key: Route mega-tenants using (tenant_id, bucket) where bucket = event_id % 8, trading single-shard tenant queries for 8-way write spread.
  • Mitigation 2 — Dedicated Silo Shard: Isolate whale tenants onto dedicated shards (routing metadata table maps tenant_id → shard_dsn).
  • Cross-Shard Join Trap: You cannot efficiently JOIN a table on Shard 1 with a table on Shard 3. Co-locate related tables by the same shard key (e.g., orders and order_items both sharded by customer_id) and duplicate small lookup/reference tables onto every shard.

Distributed Systems 4. Distributed Transactions, CAP/PACELC, Raft & NewSQL

Two-Phase Commit (2PC) vs The Saga Pattern

Suppose a transfer debits Wallet A on Shard 1 and credits Wallet B on Shard 2:

  • Two-Phase Commit (2PC): A coordinator sends PREPARE to both shards; both acquire row locks and flush to WAL; if both vote YES, coordinator sends COMMIT. Why backend teams avoid 2PC across services: It holds locks across network round-trips, slashes throughput, and if the coordinator crashes between Phase 1 and Phase 2, participants remain blocked holding locks indefinitely!
  • Saga Pattern (Orchestration + Compensation): Break the workflow into local ACID transactions (T1 → T2 → T3). If T3 fails, execute semantic compensating transactions in reverse order (C2 → C1, e.g., REFUND_WALLET, RELEASE_HOLD). Every step and compensation must be idempotent.

CAP & PACELC Theorems

In distributed networks, partitions (dropped packets between Availability Zones) will happen, so you cannot ignore P. PACELC extends CAP to describe normal healthy operation too:

  • If Partition (P): Choose Availability (A) (serve potentially stale reads/divergent writes) or Consistency (C) (reject writes on the minority side).
  • Else (E — healthy network): Choose Latency (L) (acknowledge writes locally before replicas confirm) or Consistency (C) (wait for quorum replication RTT on every commit).
  • Examples: DynamoDB default reads / Cassandra (PA/EL); PostgreSQL Sync Replication / CockroachDB / Spanner (PC/EC).

Consensus (Raft) & NewSQL Architecture

How do CockroachDB, TiDB, and Google Spanner achieve horizontal write scale without losing ACID SQL?

  • Range Splitting + Raft Quorum: Data is divided into small contiguous ranges (e.g., 64 MB). Each range is replicated across N nodes (usually 3 or 5) as a Raft consensus group. A write commits only once a majority quorum (⌊N/2⌋ + 1) appends it to their WAL. With N = 3, quorum is 2 (tolerates 1 node loss); with N = 5, quorum is 3 (tolerates 2 node losses). (Note: for hash-sharded caches/KV clusters, consistent hashing with virtual nodes avoids rehashing 90%+ of keys when adding a shard.)
  • Global Ordering & Clocks: Spanner uses hardware GPS + atomic clocks (TrueTime) to bound clock uncertainty (ε < 7 ms) and guarantee strict serializability across continents. CockroachDB uses Hybrid Logical Clocks (HLC) over commodity NTP with commit-wait uncertainty restarts when clocks drift.

Summary 8. Lesson 14 Senior Engineering Checklist

  • Exhaust indexing, read replicas, and declarative partitioning before introducing multi-node sharding.
  • Include the partition key in PRIMARY KEY / UNIQUE constraints and query predicates to achieve partition pruning.
  • Archive old time-series/audit data via DETACH PARTITION CONCURRENTLY + DROP TABLE instead of massive DELETE + VACUUM.
  • Guard against hot-shard celebrity skew using salted keys or dedicated silo shards, and co-locate joined tables on the same shard key.
  • Use Sagas with idempotent reverse-order compensations rather than cross-service 2PC, and size Raft groups with odd counts (3 or 5).
