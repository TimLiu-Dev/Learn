Reading Query Plans: EXPLAIN ANALYZE, Join Algorithms & Tuning

Guessing why a query is slow wastes hours. Senior engineers read the query planner’s execution tree directly—spotting full scans, misestimated row counts, spilled hash joins, non-SARGable predicates, OFFSET cliffs, and N+1 round-trip storms.

Room Bridge 1. Eliminating Room N+1 Queries & Slow OFFSET Pagination

Two classic mobile/ORM patterns silently destroy backend APIs at scale: 

// Anti-Pattern 1: N+1 Queries in a Kotlin / Service Loop
val customers = customerDao.getTopCustomers()      // 1 query -> 200 rows
for (c in customers) {
    c.totalPaid = orderDao.sumPaidForCustomer(c.id) // +200 network round-trips!
}

// Anti-Pattern 2: Deep OFFSET Pagination
// Page 2,500 -> scans and discards 50,000 rows BEFORE returning 20!
@Query("SELECT * FROM feed ORDER BY created_at DESC, id DESC LIMIT 20 OFFSET :offset")
suspend fun getFeedPage(offset: Int): List<FeedItem>
Why Local Flash Hides Both Bugs

In Room on a phone, 200 local function calls take ~10 ms total. Over a microservice network hop (0.5–2 ms per query), 200 sequential queries add 400 ms of pure network wait and saturate connection pools! And OFFSET 50000 doesn’t jump to row 50,001—the engine still walks and throws away all 50,000 rows, getting linearly slower on every page.

Planner Anatomy 2. SQLite EXPLAIN QUERY PLAN vs PostgreSQL EXPLAIN (ANALYZE, BUFFERS)

In SQLite, EXPLAIN QUERY PLAN reveals how tables are accessed:

  • SCAN table: Full table scan (reads every row).
  • SEARCH table USING INDEX idx (...): B+Tree seek + table rowid lookup.
  • SEARCH table USING COVERING INDEX idx (...): Index-Only Scan (no table lookup!).
  • USE TEMP B-TREE FOR ORDER BY: Index order didn’t match ORDER BY, forcing an in-memory/temp sort.
PostgreSQL Parity: Reading EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, total_cents FROM orders WHERE customer_id = 42 AND status = 'paid';

-- Sample Output (read bottom-up / inner-to-outer!):
Index Scan using idx_orders_cust_status on orders  (cost=0.43..12.85 rows=8 width=12) (actual time=0.041..0.055 rows=9 loops=1)
  Index Cond: ((customer_id = 42) AND (status = 'paid'::text))
  Buffers: shared hit=5 read=1
Planning Time: 0.18 ms
Execution Time: 0.08 ms

What to check first: (1) EXPLAIN alone only estimates; EXPLAIN ANALYZE actually runs the query (wrap DML in BEGIN; EXPLAIN ANALYZE ...; ROLLBACK;!). (2) Compare estimated rows=8 vs actual rows=9—a 100× mismatch means stale statistics (run ANALYZE table;!). (3) Check Buffers: shared hit (RAM) vs read (disk/OS cache) vs temp read/written (disk spill!).

The 4 Scan Types in PostgreSQL

Seq Scan & Index Scan

Seq Scan reads heap pages sequentially (fastest when returning >15–20% of a table or tiny tables). Index Scan walks the B+Tree and fetches matching heap pages one by one.

Index-Only Scan & Bitmap Heap Scan

Index-Only Scan skips the heap when all columns are in the index and Visibility Map bits are set (check Heap Fetches: 0 in EXPLAIN ANALYZE—high Heap Fetches means AUTOVACUUM is lagging!). Bitmap Heap Scan collects matching ctids into a page bitmap first, sorts by physical page ID, then reads heap pages sequentially—great for medium selectivity or combining AND/OR indexes!

Join Execution 3. Nested Loop vs Hash Join vs Merge Join

PostgreSQL chooses among three join algorithms based on row estimates, indexes, sort order, and work_mem (SQLite primarily uses Nested Loop + automatic transient B-tree indexes, assisted by Bloom filters in SQLite 3.38+):

Algorithm How It Works When It Wins Watch Out For
Nested Loop For each outer row, probe the inner table (ideally via an index seek). Small outer result (e.g., 1–100 rows) + indexed inner join key. Lowest startup cost for LIMIT! Planner misestimates outer as 1 row when it’s 500,000 rows → O(N·M) catastrophe!
Hash Join Build an in-memory hash table on the smaller input’s join key, then stream the larger input probing the hash table. Large unsorted equi-joins (=) where no useful index exists. Exceeding work_mem spills hash batches to temp disk (Batches: 16, temp written).
Merge Join Zip two inputs already sorted by the join key in a single streaming pass. Very large tables already sorted via B+Tree index scans or tight memory budgets. Requires an explicit Sort step if inputs aren’t pre-sorted.

SARGability 4. SARGable Predicates: Don’t Blind Your Index

SARGable means Search ARGument-able: the predicate lets the engine seek directly into a B+Tree range. Wrapping an indexed column in a function, arithmetic, or leading wildcard forces a full scan!

Non-SARGable (Breaks B+Tree)

WHERE strftime('%Y', created_at) = '2026'
WHERE amount_cents + 500 >= 25000
WHERE COALESCE(status, 'open') = 'open'
WHERE email LIKE '%@acme.io'

SARGable (Uses B+Tree Seek)

WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'
WHERE amount_cents >= 24500
WHERE status = 'open' OR status IS NULL
WHERE domain = 'acme.io' -- extracted/indexed

Production Patterns 5. Keyset (Cursor) Pagination & Eliminating N+1 Queries

Instead of OFFSET 50000, pass the last row’s (created_at, id) tuple as a cursor and use a composite index (created_at DESC, id DESC). Keyset pagination runs in O(log N) at page 1 AND at page 100,000—and never skips or duplicates rows when new items arrive!

Reading Production EXPLAIN ANALYZE & Bridging Room @Relation
  • Tree Math (loops=N): PostgreSQL reports actual time per loop. A child Nested Loop index scan showing actual time=0.05..0.08 rows=2 loops=50000 actually took 0.08 × 50,000 = 4,000 ms! Watch Rows Removed by Filter and never executed too.
  • Correlated Columns & Skewed Tenants: If WHERE country = 'US' AND currency = 'USD' misestimates rows, run CREATE STATISTICS ... ON country, currency FROM orders; ANALYZE;. If a prepared plan gets stuck on a bad generic plan for a huge tenant, check plan_cache_mode.
  • Room @Relation Reality: Room avoids classic N+1 by running 2 batched IN (...) queries—which works locally until >999 parent IDs hit SQLite’s bind-parameter limit! On servers, replace N+1 loops with a single JOIN or batched query.

Summary 9. Lesson 7 Senior Engineering Checklist

  • Always run EXPLAIN (ANALYZE, BUFFERS) (Postgres) or EXPLAIN QUERY PLAN (SQLite) before guessing.
  • Watch for estimated vs actual row count gaps (run ANALYZE) and disk spills (temp written → tune work_mem or indexes).
  • Keep predicates SARGable: never wrap indexed columns in date formatting functions or arithmetic.
  • Replace OFFSET pagination with tuple keyset pagination WHERE (created_at, id) < (?, ?) backed by (created_at DESC, id DESC).
  • Eliminate N+1 loops using single-round-trip LEFT JOIN + GROUP BY (putting child filters in ON, not WHERE!).
