Why does combining Nagle's algorithm with Delayed ACKs cause artificial 200 ms latency spikes, and what socket flag fixes it?

Nagle holds small outgoing packets until prior data is ACKed, while Delayed ACK holds incoming ACKs up to 200 ms waiting for a reply. When an app sends two small writes back-to-back, neither side moves until the 200 ms timer fires. Fixed with socket.setTcpNoDelay(true).

The stream framing dilemma

In session 14, we saw that UDP is message-oriented (preserves packet boundaries). TCP is a continuous byte stream. It has zero concept of message boundaries!

If your client sends two messages:

out.write("Hello");
out.write("World");

TCP treats this as a single sequence of 10 bytes: H-e-l-l-o-W-o-r-l-d. Due to packet fragmentation, buffering, and Nagle coalescing, the server's read() call might return:

  • Case 1: "HelloWorld" (both messages packed into one packet).
  • Case 2: "Hel" followed by "loWorld" (split across two packet arrivals).
  • Case 3: "Hello" followed by "World" (two separate reads).

Because any of these cases can happen at any moment, the application protocol must invent its own framing to tell where one message ends and the next begins:

The Two Universal Framing Strategies
  1. Delimiter-Based Framing: Terminate each message with a special sentinel byte sequence. For example, SMTP, Redis (RESP), and HTTP headers use \r\n (CRLF). The receiver buffers incoming bytes until it sees the delimiter.
  2. Length-Prefix Framing: Prepend every message with a fixed-size number indicating how many payload bytes follow. For example, gRPC, Protobuf, and WebSocket frames prepend a length header; HTTP uses Content-Length: 42. The receiver reads the header, knows exactly how many bytes to expect, and loops until all bytes arrive.

Code: A multithreaded raw TCP server in Java

Save this as EchoServer.java. You can run it directly on modern Java (JDK 21+) with java EchoServer.java. It uses modern virtual threads to handle thousands of concurrent clients effortlessly:

import java.io.*;
import java.net.*;
import java.util.concurrent.*;

public class EchoServer {
    public static void main(String[] args) throws IOException {
        int port = 8080;
        try (var serverSocket = new ServerSocket(port)) {
            System.out.println("EchoServer listening on port " + port + "...");
            
            // Modern Java: One virtual thread per client connection!
            try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
                while (true) {
                    Socket clientSocket = serverSocket.accept();
                    clientSocket.setTcpNoDelay(true); // Disable Nagle!
                    executor.submit(() -> handleClient(clientSocket));
                }
            }
        }
    }

    private static void handleClient(Socket socket) {
        try (socket;
             var reader = new BufferedReader(new InputStreamReader(socket.getInputStream()));
             var writer = new PrintWriter(socket.getOutputStream(), true)) {
            
            System.out.println("New client connected: " + socket.getRemoteSocketAddress());
            String line;
            // Delimiter-based framing: reads until newline '\n'
            while ((line = reader.readLine()) != null) {
                if ("quit".equalsIgnoreCase(line.trim())) break;
                System.out.println("Received: " + line);
                writer.println("ECHO: " + line); // Echo back with newline delimiter
            }
        } catch (IOException e) {
            System.err.println("Client error: " + e.getMessage());
        }
    }
}

Free Recall Practice

From memory: why can't a TCP server assume that one write() call on the client equals one read() call on the server? Describe the two main framing solutions.

Key points to compare against:

  • Why writes don't equal reads: TCP is a continuous byte stream with no message boundaries. The OS kernel may buffer, coalesce (Nagle), or fragment bytes into segments based on MSS and window sizes. Multiple writes can arrive in one read, or one write can be split across multiple reads.
  • The two framing solutions: (1) Delimiter-based framing: append a unique delimiter (like \n or \r\n\r\n) to mark message boundaries; (2) Length-prefix framing: prepend a fixed-size header containing the byte length of the following payload (like Content-Length in HTTP or length prefixes in gRPC).
