Warm-up · from earlier sessions

Two minutes, from memory, before you read on:

What destination port and protocol does VXLAN use to encapsulate Ethernet frames over an IP network?

VXLAN encapsulates frames inside standard UDP datagrams on destination port 4789, adding 50 bytes of outer encapsulation overhead.

Kubernetes implements zero networking code

Kubernetes mandates the three golden rules of networking (Session 60), but the Kubernetes core codebase does not contain a single line of code that provisions IP addresses, configures bridges, or routes packets.CNCF Container Network Interface: CNI Specification v1.0.

Instead, Kubernetes defines an open specification called the Container Network Interface (CNI). When the kubelet creates a Pod, it simply executes an external CNI binary on the host (e.g. calico, flannel, or aws-cni) passing ADD, the network namespace path, and the container ID. The CNI plugin handles 100% of the network configuration.

The Great Divide: Overlay vs Native Routed CNI

When Pod A on Worker Node 1 transmits a packet to Pod B on Worker Node 2, CNI plugins choose between two fundamentally distinct architectural models:

Architectural PropertyOverlay CNI (Flannel / Calico VXLAN)Native Routed CNI (AWS VPC CNI / Calico BGP)
EncapsulationWraps Pod packets in VXLAN (UDP 4789) or IP-in-IPZero encapsulation (raw IP packet on wire)
Pod IP RoutabilityPod IPs are virtual overlay addresses; invisible to VPCPod IPs are real VPC subnet IPs
PerformanceSlight CPU overhead for encap/decap; MTU reduced by 50B100% line rate hardware speed; standard 1500 MTU
Infrastructure FitRuns on any cloud, on-prem, or bare metal out-of-the-boxRequires deep cloud integration or physical BGP switches
IP Exhaustion RiskZero risk: uses private overlay CIDRs (e.g. 10.244.0.0/16)High risk: large clusters burn hundreds of VPC subnet IPs

Deep Dive: AWS VPC CNI (Native Routing)

In Amazon EKS, the default plugin is the AWS VPC CNI:

  • The plugin talks directly to the AWS EC2 API, attaching multiple secondary Elastic Network Interfaces (ENIs) to each worker node.
  • It allocates secondary private IP addresses from your VPC subnet (e.g. 10.0.1.45) and assigns them directly to Pod eth0 interfaces!
  • Benefits: Pods can communicate directly with Amazon RDS databases, on-premise servers over Direct Connect, or external services without any NAT Gateway or double-hop routing! Furthermore, AWS Security Groups can be attached directly to individual Pods.
  • The Tradeoff: A cluster with 500 Pods consumes 500 private IP addresses from your VPC CIDR. If your subnet is only a /24, your cluster will fail to launch new Pods due to IP address exhaustion!

Deep Dive: Calico & Enterprise BGP Peering

In bare-metal data centers, Project Calico implements high-performance native routing without cloud APIs:Project Calico Documentation: Calico BGP Peering and Network Architecture.

  • Every Kubernetes worker node runs a lightweight BGP router daemon (BIRD).
  • The node peers with the data center Top-of-Rack (ToR) physical switches over BGP.
  • When a Pod is scheduled, the worker node advertises that Pod's IP (e.g. 192.168.10.5/32) directly to the physical data center routers!
  • Packets route natively across the physical enterprise network at 100 Gbps wire speed with zero encapsulation.

Hands-on: Inspecting CNI configuration on a node

On macOS, spin up a local single-node Kubernetes cluster with kind create cluster (via Docker/OrbStack), then shell into the Linux worker node container with docker exec -it kind-control-plane bash for steps 1–2.

  1. Inspect the CNI plugin configuration directory on a Kubernetes worker node: 
    $ ls -la /etc/cni/net.d/
    Look for configuration files like 10-calico.conflist, 10-flannel.conflist, or 10-aws.conflist.
  2. Read the JSON configuration of the active CNI plugin: 
    $ cat /etc/cni/net.d/*.conflist | head -n 25
    Observe the "cniVersion": "0.3.1", "type": "calico", and IPAM (IP Address Management) CIDR blocks.
  3. Inspect Pod IP addresses across nodes in a live Kubernetes cluster: 
    $ kubectl get pods -o wide
    Notice whether Pod IPs share the same subnet range as the worker node IPs (Native CNI) or live in a distinct 10.244.x.x range (Overlay CNI)!

Free Recall Practice

From memory: contrast the advantages and disadvantages of an Overlay CNI (Flannel/VXLAN) versus a Native Routed CNI (AWS VPC CNI).

Key points to compare against:

  • Overlay CNI: Wraps Pod packets in VXLAN/UDP or IP-in-IP tunnels. Advantage: Runs anywhere regardless of underlying network topology without burning host subnet IPs. Disadvantage: Incurs ~50 bytes of encapsulation overhead, requires MTU tuning, adds CPU latency, and hides Pod IPs from external firewalls.
  • Native Routed CNI: Assigns real underlying subnet IPs directly to Pod ENIs. Advantage: Runs at raw 100% line rate with zero encapsulation overhead, integrates directly with cloud Security Groups, and allows direct on-prem connectivity without NAT. Disadvantage: Rapidly exhausts VPC subnet IP address space in large clusters.

Code Implementation: Java & Kotlin

Java 25 
// CNI Host-Local IPAM Allocator in Java
import java.util.*;

public class CniIpam {
    public static Optional<String> allocate(String cidr, Set<String> used) {
        var base = cidr.substring(0, cidr.lastIndexOf('.') + 1);
        for (int i = 2; i <= 254; i++) {
            var ip = base + i;
            if (!used.contains(ip)) return Optional.of(ip);
        }
        return Optional.empty();
    }
}
Kotlin 
// CNI Host-Local IPAM Allocator in Kotlin
fun allocatePodIp(cidr: String, used: Set<String>): String? {
    val base = cidr.substringBeforeLast(".") + "."
    return (2..254).map { "$base$it" }.firstOrNull { it !in used }
}
