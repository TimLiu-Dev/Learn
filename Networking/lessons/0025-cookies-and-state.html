What is the difference between an idempotent method and a safe method in HTTP?

Safe methods (GET, HEAD) never modify server resource state. Idempotent methods (GET, PUT, DELETE) may modify state, but N identical executions yield the exact same server state as a single execution.

HTTP is stateless

By design, HTTP is a stateless protocol. The server processes each request in total isolation; it has no memory of what you requested two seconds ago.RFC 6265: HTTP State Management Mechanism.

Statelessness makes web servers exceptionally scalable: any server in a cluster of 1,000 backend instances can handle any incoming request. But users expect state: shopping carts, dashboards, and logged-in accounts. To bridge this gap, Netscape engineer Lou Montulli invented HTTP Cookies in 1994.

The cookie handshake

  1. The client sends credentials via POST /login.
  2. The server verifies credentials, creates a session, and instructs the browser via the Set-Cookie header: 
    HTTP/1.1 200 OK
Set-Cookie: session_id=x9f7a1; Path=/; Secure; HttpOnly; SameSite=Lax
  3. The browser stores the cookie in secure local storage.
  4. On every subsequent request to that domain, the browser automatically attaches: 
    GET /dashboard HTTP/1.1
Host: example.com
Cookie: session_id=x9f7a1

The 3 non-negotiable security flags

If you deploy cookies without these three attributes in production, your application is vulnerable to session hijacking and account takeover:

AttributeWhat it preventsHow it works
HttpOnlyCross-Site Scripting (XSS) Token TheftPrevents client-side JavaScript (e.g. document.cookie) from reading the cookie. If an attacker injects malicious JS into your page, they cannot steal the session token!
SecureMan-in-the-Middle (MITM) InterceptionInstructs the browser to transmit the cookie only over encrypted HTTPS connections. It is never leaked over plaintext HTTP.
SameSiteCross-Site Request Forgery (CSRF)Restricts when cookies are sent on cross-origin requests originating from third-party websites.

Understanding SameSite: Strict vs. Lax vs. None

  • SameSite=Strict: The cookie is never sent on cross-site requests. If a user clicks a link to your site from an external email or Google Search, they will arrive logged out!
  • SameSite=Lax (Modern Default): Safe compromise. The cookie is withheld on dangerous cross-site requests (e.g. cross-origin POST form submissions or image embeds), but is included when the user clicks a standard top-level link (GET navigation).
  • SameSite=None: The cookie is sent on all cross-origin requests (e.g. embedded third-party iframes). Requires the Secure attribute.

Session IDs vs. JSON Web Tokens (JWTs)

FeatureOpaque Session IDJSON Web Token (JWT)
StorageRandom string; state stored in server DB (Redis)Self-contained cryptographically signed JSON
VerificationServer queries database on every requestServer verifies signature via public/private key (0 DB queries)
RevocationInstant: delete entry from RedisDifficult: valid until expiration timestamp (exp)
ScaleRequires centralized session storeStateless: perfect for distributed microservices

Try it: saving cookies with curl

  1. Send a request and store returned cookies in a "cookie jar" file: 
    $ curl -c cookies.txt -I https://www.google.com
  2. Inspect the saved cookie jar file: 
    $ cat cookies.txt
    Look at the domain, path, expiry date, and secure flags.
  3. Re-send a request using the stored cookies: 
    $ curl -b cookies.txt -v https://www.google.com
    Notice the outgoing Cookie: header!

Free Recall Practice

From memory: explain the role of HttpOnly and SameSite cookie attributes. What is the primary operational drawback of stateless JWTs compared to server-side session IDs?

Key points to compare against:

  • HttpOnly: Blocks JavaScript from accessing document.cookie, preventing attackers from stealing session tokens via XSS script injection.
  • SameSite: Restricts automatic cookie attachment on cross-site requests, protecting against CSRF attacks.
  • JWT Drawback: Inability to perform immediate server-side revocation. If a user logs out or their token is compromised, the JWT remains cryptographically valid across all servers until its exp timestamp expires.
