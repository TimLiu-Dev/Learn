What are the two universal techniques for framing messages over a continuous TCP byte stream?

1. Delimiter-based framing: Terminate messages with a unique byte sequence (e.g. \r\n\r\n).
2. Length-prefix framing: Prepend a fixed-size header specifying payload byte count (e.g. Content-Length: 42).

The plaintext protocol that powers the web

Despite modern browsers and complex web frameworks, HTTP/1.1 at its core is pure human-readable ASCII text transmitted across a TCP socket.RFC 9112: HTTP/1.1 Specification.

An HTTP request is structured in three distinct sections:

  1. Request Line: Method, Request Target, and HTTP version, terminated by \r\n (Carriage Return + Line Feed).
  2. Headers: Case-insensitive key-value pairs (Name: Value\r\n).
  3. Empty Line: A standalone \r\n (CRLF) that signals to the server: "The headers are finished!"
  4. Optional Body: Raw payload bytes (JSON, form data, file uploads).

Why the Host header is mandatory

In HTTP/1.0, requests did not include a Host header. A request was simply: GET / HTTP/1.0.

This worked when every computer had its own public IP. But as the web exploded, companies needed a single web server with one IP address to host hundreds of distinct websites (virtual hosting). Without a Host header, the server has no idea which website the client is asking for! In HTTP/1.1, the Host header was made strictly mandatory. Any HTTP/1.1 request missing a Host header is immediately rejected with 400 Bad Request.

Keep-Alive: Reusing the TCP connection

In HTTP/1.0, the connection was closed after every single response. Loading a web page with 20 icons and stylesheets opened and closed 20 separate TCP connections, paying 20 full 3-way handshakes and resetting TCP's Slow Start window every time!

HTTP/1.1 introduced Persistent Connections (Connection: keep-alive, default in HTTP/1.1). After serving a response, the server keeps the underlying TCP socket open. The client sends subsequent requests down the same socket, eliminating handshake latency!

Chunked Transfer Encoding

Normally, a server includes Content-Length: 1048576 so the client knows how many bytes to read before expecting the next request. But what if the server is dynamically generating data from a slow database stream? The server doesn't know the total size yet!

HTTP/1.1 solves this with Chunked Transfer Encoding (Transfer-Encoding: chunked):

  • The server sends data in pieces. Each piece starts with its hexadecimal byte length, followed by \r\n and the chunk data.
  • The stream is terminated by a final chunk of size zero: 0\r\n\r\n!

Try it: speak HTTP by hand using Netcat

  1. Open Terminal and open a raw TCP connection to example.com on port 80: 
    $ nc example.com 80
  2. Immediately type this exact request and press Return twice: 
    GET / HTTP/1.1
Host: example.com
  3. Watch the raw response arrive in real time! Notice the Status Line (HTTP/1.1 200 OK), the response headers, the empty line, and the raw HTML body.
  4. Now inspect with curl's verbose mode: 
    $ curl -v -4 http://example.com
    Lines starting with > are what curl sent; lines starting with < are what the server returned.

Key points to compare against:

  • Four components: (1) Request Line (Method, Path, Version); (2) Header lines (Key: Value); (3) Empty Line (\r\n); (4) Optional Message Body.
  • Why Host was added: Virtual hosting. A single physical server with one IP address can host hundreds of different websites. Without the Host header, the server cannot know which virtual host the request belongs to.
