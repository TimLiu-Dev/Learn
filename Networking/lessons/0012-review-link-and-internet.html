You'll prove you can follow one packet from the moment your laptop joins a network to a server on another continent and back: every protocol, every lookup, every address that changes and every one that doesn't. And when a step fails, you'll know which tool to reach for.

Why a review session

Re-reading feels productive. Pulling facts out of your memory, with nothing to look at, is what actually makes them stick.

In one classic experiment, students who re-studied a text did better on a test five minutes later, but students who had instead tested themselves on it remembered substantially more two days and a week later. The packet journey

Here's the scenario. You open your laptop in a café, join its Wi-Fi for the first time, and fetch http://198.51.100.10/, a web server on another continent. To keep this to Parts 0–1, assume the laptop already knows the server's IP address (DNS is Part 3), and follow only the first packet of the request and its reply (TCP's handshake is Part 2).

Before you look at anything below: explain the whole journey from memory. Start with "the laptop has no address yet" and finish with the reply arriving. Name every protocol, every lookup, and every address that changes and every one that stays the same.

  1. Get configured (DHCP, session 8). With no address yet, the laptop broadcasts a Discover: source 0.0.0.0, destination 255.255.255.255, frame to ff:ff:ff:ff:ff:ff, UDP 68 → 67. Then Offer, Request, Ack. It now has an address, mask, default gateway and DNS server, on a lease.
  2. Same subnet? (session 6, session 9) AND the server's address with its own mask and compare networks. Different, so only the default route (0.0.0.0/0) matches: send via the gateway.
  3. Find the gateway's MAC (ARP, session 7). Broadcast "Who has <gateway IP>?", unicast reply, cache it. The router also caches the laptop's mapping from the request.
  4. Send (session 4, session 5). Frame to the router's MAC; inside, a packet from the laptop's private IP to the server's IP, TTL 64. Encapsulation: message → segment → packet → frame (session 2).
  5. The café router (NAT, session 10). Rewrites source IP and source port to its public address and a port it picks, records the mapping, decrements TTL, fixes checksums, and sends a new frame towards the ISP.
  6. Across the internet (session 9). Each router does a longest-prefix match, decrements TTL (at 0: drop and send ICMP Time Exceeded), and re-frames the packet: new MACs every hop, same IPs. Each hop adds processing, queuing, transmission and propagation delay (session 1).
  7. The reply. The server replies to the public address and port it saw. The café router looks up the reply's destination port in its translation table, rewrites the destination to the laptop's private IP and port, and frames it to the laptop's MAC, which it already knows.
  8. Over IPv6 instead (session 11): SLAAC from a Router Advertisement instead of DHCP, NDP instead of ARP, hop limit instead of TTL, and no NAT.

When something breaks: what's going on, and what do you run?

Each scenario is a real failure you'll meet. Work out which session's idea it's testing before you read the options.

A teammate's Mac is on Wi-Fi, but ifconfig en0 shows inet 169.254.81.3. They want to try a different DNS server. What do you do first?

  1. Point their DNS settings at 1.1.1.1 and retry
  2. Run traceroute -n to the website's IP address
  3. Capture with filter dhcp and look for Offers
  4. Check arp -a -n for the website's MAC
169.254 means the Mac self-assigned an address because no DHCP server answered. It has no gateway and no DNS server yet, so changing DNS can't help. A capture filtered on dhcp shows whether Discovers go out and anything answers. And no website's MAC ever appears in your ARP cache: you only ARP for your own subnet.

traceroute -n to your company's server prints replies up to hop 9, then * * * on every line until it gives up. Yet curl to the server works. What do you try next?

  1. Rerun it with -I to send ICMP probes
  2. Tell the server team their machine is down
  3. Rerun it with -m 128 for more hops
  4. Report heavy packet loss at hop ten upstream
curl works, so the server is up and the path is fine. Stars at the very end usually mean a firewall near the destination drops traceroute's UDP probes or their replies. Probing with ICMP Echo (-I) often gets through. A * means "no reply in time", not packet loss. And allowing more hops can't help: the probes already reach the server's network.

Your laptop is 192.168.50.23/24 on a guest Wi-Fi network. It reaches 1.1.1.1 fine, but not the printer at 192.168.1.40. Which command shows how your Mac tries to send to the printer?

  1. ping -c 3 1.1.1.1
  2. ipconfig getoption en0 router
  3. curl -4 -s https://icanhazip.com
  4. route -n get 192.168.1.40
The printer is in a different /24, so it isn't on your subnet. route -n get will show a gateway: line: your Mac hands the packet to the router rather than ARPing for the printer. Whether it gets any further is the router's decision, and a guest network may well be kept apart from the main one on purpose. Nothing on your laptop is broken.

Your Mac is 10.0.6.37/22. ping 10.0.5.200 prints sendto: Host is down. What does that tell you?

  1. Your default gateway dropped the ICMP packet
  2. No device answered ARP for that address
  3. The packet's TTL ran out in transit
  4. The target's firewall blocked the echo request
10.0.5.200 is inside 10.0.4.0/22 (10.0.4.0–10.0.7.255), so the Mac ARPs for it directly and the gateway isn't involved. "Host is down" is macOS saying several ARP requests got no reply; arp -a -n shows the entry as (incomplete). A host whose firewall drops pings still answers ARP, so you'd see timeouts, not this error.

You forwarded port 25565 on your home router, but friends still can't connect. The router's admin page shows its internet-side address as 100.72.14.9. What explains it?

  1. Ports above 1024 can never be forwarded
  2. The router's address is RFC 1918 private
  3. Your ISP puts you behind carrier-grade NAT
  4. Forwarded ports work only over IPv6 connections
100.72.14.9 is inside 100.64.0.0/10, the shared space for CGNAT (it is not RFC 1918). Your friends' traffic hits the ISP's NAT first, which has no mapping to your router. To confirm, compare that address with what curl -4 -s https://icanhazip.com reports: they'll differ.

On a hotel network, small requests work but uploads stall. ping -D -s 1472 1.1.1.1 gets no replies, while ping -D -s 1400 1.1.1.1 does. What have you learned?

  1. Some link on the path has MTU below 1,500
  2. The server rejects every ICMP echo request it gets
  3. Your packets' TTL runs out before they reach it
  4. Routers on the path are fragmenting the large packets
1,472 data bytes + 8 bytes of ICMP header + 20 bytes of IP header = 1,500 bytes; with 1,400 it's 1,428. With DF set, a router facing a smaller MTU must drop the packet rather than fragment it, so the path MTU is somewhere from 1,428 to 1,499 bytes. You just did path MTU discovery by hand. Fragmenting routers would have made the big ping succeed.

An online shop says its servers are in Tokyo, about 9,300 km from you in Amsterdam. ping to its site shows a minimum of 6 ms. What do you conclude?

  1. Your Wi-Fi bandwidth is unusually high today
  2. Fibre carries light faster than usually estimated
  3. Routers skipped queuing, so propagation got shorter
  4. A machine near Amsterdam answered the ping
Physics sets a floor: 2 × 9,300 km ÷ 200 km/ms ≈ 93 ms. Nothing beats that, and bandwidth and queuing don't change propagation. So whatever answered in 6 ms is at most about 600 km away (6 ms × 200 km/ms ÷ 2): a nearby copy of the site, such as a CDN server.

ifconfig en0 inet6 shows an fe80:: address but no global one. Which Wireshark display filter shows whether any router is advertising a prefix?

  1. icmpv6.type == 135
  2. icmpv6.type == 134
  3. arp.opcode == 1
  4. icmp.type == 11
Every interface makes a link-local address by itself. A global address needs SLAAC, and SLAAC needs a prefix from a Router Advertisement: ICMPv6 type 134. Type 135 is a Neighbor Solicitation (NDP's "who has"); ARP and ICMP Time Exceeded are IPv4.

Quick-fire, mixed

Your Mac's table has default via 10.0.4.1, 10.0.0.0/8 via a VPN tunnel, and 10.0.4.0/22 directly connected on Wi-Fi. What happens to a packet for 10.0.7.200?

  1. Sent straight into the VPN tunnel
  2. ARP for 10.0.7.200 directly on Wi-Fi
  3. ARP for the gateway at 10.0.4.1
  4. Dropped, because no route matches it
10.0.7.200 matches all three entries: /0, /8 and /22 (which runs 10.0.4.0–10.0.7.255). Longest-prefix match picks the /22, which is directly connected, so the Mac ARPs for the destination itself.

A Mac got a 2-hour DHCP lease with no T1 or T2 options, and its DHCP server has been unreachable ever since. When does it start broadcasting Requests to any server?

  1. After about 90 minutes
  2. After about 60 minutes
  3. After about 120 minutes
  4. After about 105 minutes
At T1 = 0.5 × 120 = 60 minutes it unicasts Requests to its own server (RENEWING), which gets no answer. At T2 = 0.875 × 120 = 105 minutes it starts broadcasting to any server (REBINDING). At 120 minutes the lease expires and it starts over with a Discover. Source: RFC 2131 §4.4.5; a REBINDING Request "MUST be broadcast" (§4.3.2).

What is the RFC 5952 canonical form of 2001:0db8:0000:0000:00a0:0000:0000:0001?

  1. 2001:db8:0:0:a0::1
  2. 2001:db8::a0::1
  3. 2001:db8::a0:0:0:1
  4. 2001:db8::a:0:0:1
Drop leading zeros (00a0 → a0, never trailing ones). Two zero runs of equal length: compress the first (RFC 5952 §4.2.3). :: may appear only once, or nobody could tell how many zeros each one stands for.

For an outgoing web request, which headers does a home NAT router read or rewrite?

  1. Link, network and transport headers
  2. Only the network-layer IP header
  3. Link and network headers only
  4. Every header, HTTP message included
Like every router, it builds a new frame (link) and decrements TTL (network). NAT also rewrites the source IP and the source port, which sits in the transport header, and fixes both checksums. It has no reason to read HTTP. That's why session 10 called NAT a layer violation.

Try it: one capture, four protocols

One Wireshark capture, filtered with every protocol from this part. Each step below makes a different one appear. Display filters can be combined with || (or).Protocol names: arp, dhcp, icmp, icmpv6 in the Wireshark display-filter reference. Commands are the ones you've used before; the work is in reading the results.

  1. Start a capture on Wi-Fi: en0 with the display filter arp || dhcp || icmp || icmpv6. Leave it running through every step.
  2. Renew your lease: System Settings → Network → Wi-Fi → Details… → TCP/IP → Renew DHCP Lease, then OK.
  3. Make your router discard a packet: ping -c 2 -m 1 1.1.1.1
  4. Using your address and mask, work out an address that's inside your subnet but not listed by arp -a -n, and ping -c 3 it. (If something answers, pick another.)
  5. Ping every IPv6 node on your link: ping6 -c 2 -I en0 ff02::1. Then stop the capture.

Then answer these. Bring your answers to chat rather than looking them up:

  • For each of the four protocols, what carries it: an EtherType, an IP protocol number, or a UDP port? Which layer does that put it in?
  • Which DHCP messages did the renewal produce, and were they broadcast or unicast? Which situation from session 8 does that match?
  • Who sent the Time Exceeded, and what Type and Code did it carry? Which hop of a traceroute would that be?
  • For your unused address: how did you make sure it was inside your subnet? How many ARP requests went out, what did ping print, and why did no reply ever come?
  • Pick one echo request to 1.1.1.1. Name its source and destination MAC and IP, and the device each one belongs to. Which of the four would be different on the same packet as it leaves your router towards your ISP, and why?
