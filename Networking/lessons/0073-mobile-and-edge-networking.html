Warm-up · from earlier sessions

Two minutes, from memory, before you read on:

Suppose an Android user walks out of their apartment while uploading a photo: their phone drops Wi-Fi (192.168.1.42) and activates cellular 5G (100.64.8.19). Why does an open HTTPS/2 over TCP socket freeze or reset, while HTTP/3 over QUIC can keep the upload alive?

A TCP connection is permanently bound to the 4-tuple (src_ip, src_port, dst_ip, dst_port). Changing the client source IP breaks the server's socket lookup, forcing a fresh TCP + TLS 1.3 handshake (plus retransmitting unacknowledged bytes). QUIC binds state to a 64-bit Connection ID inside the UDP/QUIC header rather than the source IP/port, so after validating the new path with PATH_CHALLENGE/PATH_RESPONSE, the same cryptographic session and streams continue seamlessly.

1 · Dual-Stack Pain & Happy Eyeballs v2 (RFC 8305)

Modern mobile networks frequently hand a device both an IPv6 address and an IPv4 address (dual-stack). If the client queries AAAA and A DNS records and tries every IPv6 address sequentially with a 30-second TCP connect timeout when IPv6 routing on a misconfigured café Wi-Fi is black-holed, the user stares at a spinning loader for half a minute before falling back to IPv4.

RFC 8305 (Happy Eyeballs v2) fixes this without flooding the network or starving IPv6:

  • DNS Racing: Issue AAAA and A queries asynchronously. If AAAA arrives first, start trying IPv6 right away; if A arrives first, wait briefly (~50 ms Resolution Delay) for AAAA so IPv6 still gets preference when healthy.
  • Staggered Connection Attempts: Sort candidate addresses interleaving address families (starting with IPv6). Start attempt #1, then wait a Connection Attempt Delay (recommended 250 ms, minimum 10 ms, maximum 2 s) before launching attempt #2 from the opposite family.
  • First Connected Wins: Whichever socket completes the TCP 3-way handshake first is handed to TLS/HTTP; all other pending sockets are immediately closed to avoid leaked file descriptors and battery drain.
Why 250 ms instead of launching all sockets at 0 ms? Racing every IP simultaneously doubles SYN packet bursts, stateful NAT table entries, and server accept-queue pressure at global scale. A 250 ms head start gives healthy IPv6 enough time to finish a local RTT (~20–80 ms) while bounding broken-IPv6 stalls to a fraction of a second.

2 · OkHttp Internals, Radio Wakeups & Background Limits

On Android, the cellular modem is one of the highest-power components on the board. Every unbundled network request forces the LTE/5G radio from RRC_IDLE to RRC_CONNECTED, keeping a power tail active for 5–15 seconds afterward.

  • Single Shared OkHttpClient: Instantiating a new OkHttpClient per request creates a new ConnectionPool and Dispatcher every time—bypassing HTTP/1.1 keep-alive, HTTP/2 stream multiplexing, and TLS session resumption. Always share one singleton client and derive variants via newBuilder() (which shares the underlying pool and thread pool).
  • DNS & Captive Portals: Hotel or airport Wi-Fi often intercepts HTTP (port 80) or spoofs DNS to redirect to a login page. Android's ConnectivityManager probes connectivitycheck.gstatic.com/generate_204 (expecting HTTP 204 with zero body) and marks the network NET_CAPABILITY_CAPTIVE_PORTAL until resolved.
  • IPv6 NAT64 / DNS64 (RFC 6146 / 6147): Many cellular carriers (like T-Mobile) operate IPv6-only RANs. When an app queries an IPv4-only domain, the carrier's DNS64 synthesizer embeds the IPv4 literal inside the well-known 64:ff9b::/96 prefix, and NAT64 translates packets at the carrier gateway. Gotcha: Hardcoded IPv4 literals ("192.0.2.10") in mobile code skip DNS64 entirely unless Android's CLAT (464XLAT) intervenes—always connect by hostname.

3 · QUIC Connection Migration vs Multipath

HTTP/3 runs over QUIC (UDP/443). Unlike TCP, a QUIC connection is identified by variable-length Connection IDs (CIDs) negotiated during the handshake. When the client switches interfaces:

  1. The client sends packets from its new source IP/port using an unused server-issued CID (to prevent linkability across networks by passive eavesdroppers!).
  2. The server detects the non-probing packet on a new 4-tuple and initiates Path Validation: it sends an encrypted PATH_CHALLENGE frame with 8 random bytes to the new address and waits for PATH_RESPONSE before committing high-rate congestion window growth (preventing off-path amplification attacks).
  3. Active HTTP/3 streams and in-flight RPCs continue without re-authenticating TLS. (Carrier middleboxes that block UDP/443 trigger a fast fallback to HTTP/2 over TCP/443.)

4 · Certificate Pinning: Why Leaf Pins Break Apps

Android apps sometimes use CertificatePinner (or network_security_config.xml) to defend against rogue device CAs or corporate MITM proxies. Pinning the exact leaf certificate SPKI hash is an infamous outage generator: the instant your CDN/TLS edge rotates its leaf cert (often every 60–90 days, or automatically via ACME/Let's Encrypt), every un-updated mobile binary bricks itself.

Safe Pinning Rules (if you must pin at all):
  • Pin intermediate/root CA SPKI hashes, never only the leaf certificate.
  • Always ship at least one offline backup pin generated from a different CA / keypair already pre-staged with your incident plan.
  • Include a configurable kill-switch or expiration date (Android <pin-set expiration="2027-06-01">), and prefer Certificate Transparency (CT) enforcement over rigid client pinning where feasible.
