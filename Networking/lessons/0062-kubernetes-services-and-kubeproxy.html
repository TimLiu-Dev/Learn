What is Destination NAT (DNAT), and how does it alter a packet header?

Destination NAT rewrites the destination IP address (and optionally destination port) in the packet header before routing, transparently redirecting traffic to an internal target server.

The Ephemeral Pod Dilemma

In Kubernetes, Pods are mortal. They crash, autoscale, and get rescheduled across nodes during deployments. When a Pod restarts, it receives a completely brand-new IP address.Kubernetes Documentation: Services, Load Balancing, and Networking.

If your frontend application hardcodes the IP address of the backend database Pod, the frontend collapses the moment the database Pod restarts. Kubernetes solves this by introducing the Service: a permanent, stable abstraction with a static virtual IP and DNS name that load-balances traffic across an elastic set of healthy Pod endpoints.

The Mystery: Why ClusterIP is a "Ghost IP"

If you create a Service, Kubernetes assigns it a ClusterIP (e.g. 10.96.0.150). But if you log into a worker node and run:

$ ping 10.96.0.150
PING 10.96.0.150 (10.96.0.150): 56 data bytes
Request timeout for icmp_seq 0...

It will never respond to a ping! If you run ip addr show or ifconfig, you will find that 10.96.0.150 does not exist on any physical or virtual network interface on any node in the cluster!

A ClusterIP is a ghost IP. There is no network card, no container, and no listening socket bound to that address. How, then, does curl http://10.96.0.150:80 reach your backend Pods? The answer is kube-proxy.

How kube-proxy Works: The iptables Engine

kube-proxy runs as a DaemonSet on every worker node in the cluster. It constantly watches the Kubernetes API server for Service and EndpointSlice changes, and programs the Linux kernel's Netfilter / iptables subsystem:

The Step-by-Step Packet Interception

  1. A container sends a SYN packet to destination 10.96.0.150:80.
  2. Before the packet exits the node, the Linux kernel passes it through the Netfilter NAT table.
  3. The packet matches the KUBE-SERVICES chain, which points to KUBE-SVC-XXX.
  4. Inside KUBE-SVC-XXX, iptables uses the statistic module to perform probabilistic load balancing:
    • 50% probability: jump to Endpoint 1 (KUBE-SEP-1) → execute DNAT rewriting the destination IP to 10.244.1.5:8080!
    • Remaining 50%: jump to Endpoint 2 (KUBE-SEP-2) → execute DNAT rewriting destination to 10.244.2.8:8080!
  5. By the time the packet leaves the network stack, the destination is no longer the ghost ClusterIP; it is the real IP of a living Pod!

The iptables Scaling Collapse vs IPVS

In small clusters, iptables works fine. But in large enterprise clusters, iptables hits a scaling wall:Kubernetes Enhancement Proposal (KEP): IPVS-Based In-Cluster Service Load Balancing.

  • iptables is a flat, sequential list of rules: evaluating a packet requires sequential O(N) traversal.
  • In a cluster with 5,000 Services and 40,000 Pods, the kernel must traverse over 100,000 sequential iptables rules for every single packet!
  • Furthermore, adding or deleting a single Pod requires rewriting the entire iptables ruleset, triggering kernel locks that spike node CPU to 100%.
  • The Solution: IPVS Mode: Modern clusters run kube-proxy in IPVS (IP Virtual Server) mode. IPVS uses in-kernel hash tables, providing O(1) constant-time lookups regardless of whether your cluster has 10 services or 100,000 services!

Hands-on: Inspecting iptables service chains and CoreDNS

On macOS with a local kind cluster (kind create cluster), run kubectl from your Mac terminal for step 1, and shell into the Linux node container (docker exec -it kind-control-plane bash) for steps 2–3 where Linux iptables and cluster DNS are reachable.

  1. View the active Kubernetes Services in your cluster: 
    $ kubectl get services
    Look for: NAME: kubernetes, TYPE: ClusterIP, CLUSTER-IP: 10.96.0.1, and PORT(S): 443/TCP.
  2. Inspect the low-level iptables NAT rules programmed by kube-proxy on a worker node: 
    $ sudo iptables -t nat -L KUBE-SERVICES -n -v | head -n 25
    Observe the matching chains targeting virtual ClusterIPs!
  3. Query internal CoreDNS to resolve a Service hostname: 
    $ dig +short @10.96.0.10 my-service.default.svc.cluster.local
    Verify that CoreDNS returns the virtual ClusterIP address!

Free Recall Practice

From memory: why does a Kubernetes ClusterIP not respond to ICMP ping? How does kube-proxy route traffic to backend Pods?

Key points to compare against:

  • Why ClusterIP cannot be pinged: A ClusterIP is a purely virtual "ghost IP." It does not exist on any physical or virtual network interface on any node; there is no ARP responder or ICMP echo reply stack attached to it.
  • How kube-proxy routes traffic: kube-proxy programs Netfilter/iptables rules in the node's Linux kernel. When a client sends a packet to the ClusterIP, the kernel intercepts it in the PREROUTING/OUTPUT chains, applies probabilistic DNAT to rewrite the destination to a living Pod IP from the EndpointSlice, and forwards the packet natively to that Pod.

Code Implementation: Java & Kotlin

Java 25 
// kube-proxy iptables Random DNAT selection in Java
import java.util.*;

public class KubeProxyDnat {
    public static String route(List<String> endpoints, double r) {
        if (endpoints.isEmpty()) return null;
        int idx = Math.min((int)(r * endpoints.size()), endpoints.size() - 1);
        return endpoints.get(idx);
    }
}
Kotlin 
// kube-proxy iptables Random DNAT selection in Kotlin
fun selectKubeEndpoint(endpoints: List<String>, r: Double): String? {
    if (endpoints.isEmpty()) return null
    val idx = (r * endpoints.size).toInt().coerceIn(0, endpoints.lastIndex)
    return endpoints[idx]
}
