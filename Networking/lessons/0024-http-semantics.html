Methods: Safe vs. idempotent

When building REST APIs and distributed systems, choosing the correct HTTP method is not an aesthetic choice—it dictates how browsers, proxies, and retry engines handle failures.RFC 9110 §9: Method Definitions.

MethodSafe?Idempotent?Semantic Purpose
GETYesYesRetrieve representation of a resource. No side effects.
HEADYesYesIdentical to GET, but returns headers only (no body).
POSTNoNoProcess data, create new child resource. Repeated calls create multiple entities!
PUTNoYesReplace the resource completely at target URL. N identical calls leave state identical.
PATCHNoNo (usually)Apply partial modifications to a resource.
DELETENoYesDelete target resource. Calling DELETE once or ten times leaves resource gone.
  • Safe: Calling the method does not alter server state. Browsers can prefetch safe requests (GET/HEAD) in the background.
  • Idempotent: Making N identical requests produces the exact same server side-effects as making 1 request (f(f(x)) = f(x)). If a network timeout occurs during a PUT or DELETE, a client can safely retry automatically. If a timeout occurs during a POST, retrying blindly might charge a customer's credit card twice! This is why browsers display: "Confirm Form Resubmission" on reload.

Status code families

The first digit of the 3-digit status code defines its category:

  • 1xx (Informational): Request received, continuing (e.g. 101 Switching Protocols during WebSocket upgrades).
  • 2xx (Successful): Action understood and accepted:
    • 200 OK: Standard success.
    • 201 Created: Resource created (includes Location header).
    • 204 No Content: Success, but deliberately returns zero body bytes (common for DELETE/PUT).
  • 3xx (Redirection): Client must take additional action:
    • 301 Moved Permanently: Browsers cache this redirect aggressively; search engines update SEO links.
    • 302 Found / 307 Temporary Redirect: Temporary redirect; do not cache permanently.
    • 304 Not Modified: Resource hasn't changed; use local cache!
  • 4xx (Client Error): The problem is on the caller's side:
    • 401 Unauthorized: Authentication failure (who are you?). Missing or invalid credentials.
    • 403 Forbidden: Authorization failure (identity is known, but permissions denied).
    • 404 Not Found: Resource does not exist.
    • 429 Too Many Requests: Rate limit exceeded.
  • 5xx (Server Error): The server failed:
    • 500 Internal Server Error: Uncaught exception or server crash.
    • 502 Bad Gateway: A reverse proxy (e.g. Nginx, ALB) received an invalid or reset response from the upstream application server.
    • 504 Gateway Timeout: The upstream application took too long to reply before the reverse proxy's timeout expired.

HTTP caching & conditional validation (ETags)

The fastest request is the one that never touches the network. HTTP caching is governed by Cache-Control:MDN Web Docs: Cache-Control.

  • Cache-Control: max-age=3600: Cache the response for 1 hour.
  • Cache-Control: no-cache: Misunderstood! It does not mean "don't cache". It means: "You may cache this, but you MUST revalidate with the server before using it."
  • Cache-Control: no-store: The true anti-cache directive. Never save to memory or disk (used for bank details and authentication tokens).

Conditional Requests with ETags: When serving a file, the server returns an ETag (entity tag, usually a hash of the content):

HTTP/1.1 200 OK
ETag: "686897696a7c"
Content-Length: 500000

When the client re-requests this asset later, it sends a conditional request:

GET /image.png HTTP/1.1
If-None-Match: "686897696a7c"

If the file hasn't changed, the server does not retransmit the 500 KB image. It returns a lightweight 304 Not Modified header with zero body bytes, saving massive latency and bandwidth!

Free Recall Practice

From memory: define the difference between safe and idempotent HTTP methods. Explain the difference between 401 Unauthorized and 403 Forbidden.

Key points to compare against:

  • Safe vs Idempotent: Safe methods (GET, HEAD) do not alter server state. Idempotent methods (GET, PUT, DELETE) can be executed N times with the exact same resulting server state as a single execution. POST is neither safe nor idempotent.
  • 401 vs 403: 401 Unauthorized means authentication failed (identity unknown or credentials missing). 403 Forbidden means authentication succeeded (identity is known), but the caller lacks permission to access the resource.
