Warm-up · from earlier sessions

Two minutes, from memory, before you read on:

Why does UDP have zero connection setup delay, and what does it trade away to achieve this?

UDP is connectionless: it sends data immediately in packet #1 (0-RTT). It trades away all reliability, ordering, retransmissions, and flow control—if a packet is lost, UDP does nothing.

The connection abstraction

Before two computers can exchange data reliably over TCP, they must establish a stateful agreement: a TCP connection.

There is no physical wire or circuit reserved between the machines. The "connection" exists purely as state in the operating system memory of the two endpoints: buffers, timers, sequence numbers, and window sizes. To the underlying internet routers, every TCP segment is just an ordinary, independent IP packet.

The TCP header

Unlike UDP's 8-byte header, TCP's header is minimum 20 bytes, and frequently up to 60 bytes with options:RFC 9293 §3.1: "Header Format".

The 1-bit control Flags drive the entire TCP state machine:

  • SYN (Synchronize): Initiates a connection and synchronizes Initial Sequence Numbers.
  • ACK (Acknowledgment): Indicates that the Acknowledgment Number field is valid.
  • FIN (Finish): Gracefully closes the connection from the sender's side.
  • RST (Reset): Abruptly aborts a connection (e.g., port closed or process crashed).

The 3-way handshake

To establish a connection, TCP uses a three-step exchange. Both hosts must pick a random Initial Sequence Number (ISN) and confirm the other side heard it:

Why 3 steps instead of 2? In an unreliable network, packets can be delayed and arrive minutes later. If connection setup took only 2 steps, a delayed old SYN packet wandering the internet could arrive at the server. The server would send a single reply and immediately allocate memory and open a connection, believing a client just connected, while the client has no idea! Three steps ensure that both sides actively verify mutual bidirectional reachability.

Connection teardown: The 4-way close

TCP connections are full-duplex: data can flow in both directions independently. Because of this, closing a connection requires each direction to close separately:

  1. Client sends FIN ("I have no more data to send").
  2. Server sends ACK ("Understood. I may still have data for you"). The client enters FIN_WAIT_2.
  3. When the server finishes its transmission, it sends its own FIN.
  4. Client sends final ACK and enters the infamous TIME_WAIT state.

The TIME_WAIT state and 2MSL

Why does the client not immediately destroy the socket after sending the final ACK? Why does it sit in TIME_WAIT for 1 to 2 minutes?

Why TIME_WAIT is Essential
  1. Ensuring the final ACK is received: If the client's final ACK is lost in transit, the server will time out and retransmit its FIN. If the client had already destroyed its socket, it would reply with RST (error), causing the server to report a broken connection instead of a clean exit!
  2. Draining "ghost packets" from the network: The Maximum Segment Lifetime (MSL) is the maximum time a packet can wander through routers before dying (default 60 seconds). Waiting 2 × MSL guarantees that all delayed duplicate packets from this connection have died, preventing old data from corrupting a brand-new connection that accidentally reuses the exact same 5-tuple.

Try it: capture a handshake in Wireshark

Let's capture a real TCP handshake and see the flags and sequence numbers on the wire.

  1. Open Wireshark and start capturing on Wi-Fi (en0).
  2. Set the display filter to: tcp.flags.syn == 1.
  3. In Terminal, fetch a page using plain HTTP: 
    $ curl -4 http://example.com
  4. Stop the capture. In Wireshark, you will see two packets: your outgoing SYN and the server's incoming SYN, ACK!
  5. Clear the filter, find the SYN packet, right-click it, and select Conversation Filter → TCP.
  6. Notice the sequence: 
    1. [SYN]            Seq=0
2. [SYN, ACK]       Seq=0 Ack=1
3. [ACK]            Seq=1 Ack=1
4. [PSH, ACK]       GET / HTTP/1.1 (Data begins!)
    Wireshark displays "Relative Sequence Numbers" starting at 0 by default for human readability. Right-click the Sequence Number field and uncheck "Relative Sequence Numbers" to view the true 32-bit random ISN!

Free Recall Practice

From memory: describe the three steps of the TCP handshake. Why does connection teardown require 4 steps instead of 3?

Key points to compare against:

  • Handshake: Step 1: Client sends SYN (seq = client_isn). Step 2: Server sends SYN + ACK (seq = server_isn, ack = client_isn + 1). Step 3: Client sends ACK (seq = client_isn + 1, ack = server_isn + 1).
  • Why 4 teardown steps: TCP is full-duplex. Each direction of data flow must be closed independently. A client sending FIN indicates it is done sending, but the server can acknowledge the FIN and continue transmitting data until it independently sends its own FIN.
