Two minutes, from memory, before you read on:

Suppose you write a Python loop that pushes bgp neighbor 10.0.0.2 sequentially to 200 switches via SSH, taking 8 seconds per switch—and if run twice, it blindly appends duplicate ACL lines. Why do Senior NetDevOps engineers build around idempotent diffs and thread-pooled runners like Nornir instead?

Sequential loops across 200 devices take ~27 minutes and stall on the first unreachable box. Nornir executes Python tasks concurrently across a worker thread pool in ~10 seconds cleanly, while NAPALM computes compare_config() against live state—producing an empty diff (no-op) if the device already matches desired state (idempotency)!

2 · Idempotency & Check-Diff-Commit Workflow

An automation task is idempotent if running it once or 50 times yields the exact same desired network state with zero side effects on runs 2..50. Follow the mandatory 5-step safety loop:

  1. Render desired config from YAML/NetBox Source of Truth + Jinja2 templates.
  2. Stage & Diff (compare_config()) without changing production yet.
  3. Assert Blast Radius: Abort automatically if a change would touch >N BGP sessions or wipe out management routes!
  4. Commit / Replace atomically (with rollback timer where supported).
  5. Post-Validate: Verify BGP Established counts, interface CRC errors, and reachability assertions.

// Checking idempotency: normalized desired config vs live config diff
fun computeConfigDiff(liveLines: Set<String>, desiredLines: Set<String>): Pair<List<String>, List<String>> {
    val toAdd = desiredLines.filter { it !in liveLines }.sorted()
    val toRemove = liveLines.filter { it !in desiredLines }.sorted()
    return toAdd to toRemove // empty pairs == completely idempotent no-op!
}
