1 · Explain it from memory

Write in full sentences, as if to a teammate. Only then reveal the key points and compare.

Explain the difference between latency and bandwidth. Give one symptom of a latency problem and one of a bandwidth problem, and the kind of fix each needs.

Latency is how long one bit takes to get there (ms). Bandwidth is how many bits per second a link can carry. Latency symptom: many small, sequential requests are slow even though the data is tiny (e.g. a chatty API to a distant server). Fix: fewer round trips (batching, parallelism) or move closer (CDN, nearby region). Bandwidth symptom: large transfers are slow while small requests feel fine. Fix: a bigger link, less data (compression), or removing a bottleneck. Throughput is what you actually achieve, capped by the slowest link on the path.

Name the five layers of the Internet model, top to bottom. For each: its job, the name of its unit of data, and the kind of address it uses (if any).

Application: what the program means (HTTP, DNS); a message; names like example.com but no address of its own.
Transport: process to process; a segment (TCP) or datagram (UDP); port.
Network: host to host across many networks; a packet; IP address.
Link: one hop to the next device on the same network; a frame; MAC address.
Physical: bits as signals on a wire or radio; no address.
OSI adds presentation and session between application and transport (7 layers); RFC 1122 merges link and physical (4 layers).

Code Example: Network Bottleneck Classifier in Java & Kotlin

Senior engineers quickly categorize performance incidents as Latency-Bound (too many round trips or excessive distance) or Bandwidth-Bound (link serialization saturation) using quantitative thresholds:

public class BottleneckClassifier {
    public static final double FIBER_SPEED_KM_PER_MS = 200.0;

    public static String classifyBottleneck(long payloadBytes, long linkBps, double distanceKm) {
        double transMs = ((double) payloadBytes * 8.0 * 1000.0) / (double) linkBps;
        double propMs = distanceKm / FIBER_SPEED_KM_PER_MS;

        if (transMs > 2.0 * propMs) {
            return "BANDWIDTH_BOUND";
        } else if (propMs > 2.0 * transMs) {
            return "LATENCY_BOUND";
        } else {
            return "BALANCED";
        }
    }

    public static void main(String[] args) {
        System.out.println("500B API across 6000km: " + classifyBottleneck(500, 100_000_000L, 6000.0));
        System.out.println("50MB video across 100km: " + classifyBottleneck(50_000_000L, 10_000_000L, 100.0));
        System.out.println("250KB over 100Mbps across 4000km: " + classifyBottleneck(250_000L, 100_000_000L, 4000.0));
    }
}
object BottleneckClassifier {
    const val FIBER_SPEED_KM_PER_MS = 200.0

    fun classifyBottleneck(payloadBytes: Long, linkBps: Long, distanceKm: Double): String {
        val transMs = (payloadBytes * 8.0 * 1000.0) / linkBps
        val propMs = distanceKm / FIBER_SPEED_KM_PER_MS

        return when {
            transMs > 2.0 * propMs -> "BANDWIDTH_BOUND"
            propMs > 2.0 * transMs -> "LATENCY_BOUND"
            else -> "BALANCED"
        }
    }
}

fun main() {
    println("500B API across 6000km: ${BottleneckClassifier.classifyBottleneck(500, 100_000_000L, 6000.0)}")
    println("50MB video across 100km: ${BottleneckClassifier.classifyBottleneck(50_000_000L, 10_000_000L, 100.0)}")
}

Transmission: 3,000,000 bytes × 8 = 24,000,000 bits; ÷ 50,000,000 bits/s = 0.48 s. Propagation: 2,000 km ÷ 200 km/ms = 10 ms one-way. For big transfers, bandwidth usually dominates. 60 ms forgets the ×8; 20 ms is the round trip, not the one-way delay.

For the page in the previous question, which change would cut its load time the most?

      
    
        
  1. Upgrade the server's network link

    3.

The time goes on round trips, which is latency. Bandwidth and compression shrink transmission delay, tiny for small API responses. A faster database doesn't touch propagation. Fewer round trips is the fix: batch the calls, run them in parallel, or move the server closer.

4 · Say it like an interview

  

    
A colleague says: "Our users in Singapore see 3-second page loads. The servers are in Oregon. Let's buy a 10 Gbps uplink." Write what you'd say back, with numbers and a better proposal.

    

      
The winning response:

      
    
        
  • Physics first: Singapore to Oregon is ~12,800 km. At 200 km/ms in fiber, one-way propagation delay is ≥ 64 ms, so minimum RTT is ≥ 128 ms. If the page makes 15 serial API or asset round-trips, that's 15 × 128 ms ≈ 2 seconds spent purely on the speed of light!
    • 
        
  • Why 10 Gbps fails: Upgrading bandwidth cuts transmission delay (L/R), which is already tiny (< 1 ms) for web requests. It does nothing to reduce propagation delay (d/s).
    • 
        
  • A better architecture: (1) Deploy an edge CDN (CloudFront / Cloudflare) to terminate TLS and cache static assets in Singapore; (2) Batch API calls or use HTTP/2 multiplexing so multiple requests share a single RTT; (3) Deploy a regional API/database read replica in AWS ap-southeast-1 (Singapore).
