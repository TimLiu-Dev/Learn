Your win today

You'll be able to look at a slow or broken network interaction and say, with numbers, which delay dominates and which layer is involved. That's the first move in every debugging session in this course.

Why a review session?

Re-reading a lesson feels productive but builds little. Pulling an answer out of memory is what makes it last, even when retrieval is hard. Especially when it's hard.The "testing effect": Roediger & Karpicke (2006) found that students who practised recall remembered far more a week later than students who re-read, even though the re-readers felt more confident. So: no scrolling back to sessions 1 and 2 until you've committed to an answer. A wrong answer you then correct sticks better than a right answer you copied.

Questions are deliberately mixed, delay next to layers, so you have to work out which idea applies before you can use it.

1 · Explain it from memory

Write in full sentences, as if to a teammate. Only then reveal the key points and compare.

Explain the difference between latency and bandwidth. Give one symptom of a latency problem and one of a bandwidth problem, and the kind of fix each needs.

Latency is how long one bit takes to get there (ms). Bandwidth is how many bits per second a link can carry. Latency symptom: many small, sequential requests are slow even though the data is tiny (e.g. a chatty API to a distant server). Fix: fewer round trips (batching, parallelism) or move closer (CDN, nearby region). Bandwidth symptom: large transfers are slow while small requests feel fine. Fix: a bigger link, less data (compression), or removing a bottleneck. Throughput is what you actually achieve, capped by the slowest link on the path.

Name the five layers of the Internet model, top to bottom. For each: its job, the name of its unit of data, and the kind of address it uses (if any).

Application: what the program means (HTTP, DNS); a message; names like example.com but no address of its own.
Transport: process to process; a segment (TCP) or datagram (UDP); port.
Network: host to host across many networks; a packet; IP address.
Link: one hop to the next device on the same network; a frame; MAC address.
Physical: bits as signals on a wire or radio; no address.
OSI adds presentation and session between application and transport (7 layers); RFC 1122 merges link and physical (4 layers).

2 · Mixed practice

Paper and pencil allowed, calculator allowed, scrolling up not allowed. Keep these two facts in your head: fibre carries a signal about 200 km per ms, and there are 8 bits in a byte.

A 3 MB image crosses a single 50 Mbps link that is 2,000 km long. Which delay dominates, and roughly how big is it?

  1. Propagation, about 10 ms
  2. Transmission, about 60 ms
  3. Propagation, about 20 ms
  4. Transmission, about 480 ms
Transmission: 3,000,000 bytes × 8 = 24,000,000 bits; ÷ 50,000,000 bits/s = 0.48 s. Propagation: 2,000 km ÷ 200 km/ms = 10 ms one-way. For big transfers, bandwidth usually dominates. 60 ms forgets the ×8; 20 ms is the round trip, not the one-way delay.

Which layer's header carries the number 443 that tells the server's machine which program should receive the data?

  1. Application
  2. Transport
  3. Network
  4. Link
Ports identify processes, and they live in the transport header (TCP or UDP). The network layer only gets the data to the right host.

Your servers are 8,000 km from your users. Loading one page makes 10 API calls one after another, each a single round trip. What's the physics floor on the page's network time?

  1. 80 ms
  2. 400 ms
  3. 800 ms
  4. 1,600 ms
One RTT ≥ 2 × 8,000 ÷ 200 = 80 ms. Ten sequential round trips ≥ 800 ms, before any server work at all. 400 ms counts only one direction per call.

For the page in the previous question, which change would cut its load time the most?

  1. Upgrade the server's network link
  2. Batch calls into one request
  3. Compress every response with gzip
  4. Use a faster database server
The time goes on round trips, which is latency. Bandwidth and compression shrink transmission delay, tiny for small API responses. A faster database doesn't touch propagation. Fewer round trips is the fix: batch the calls, run them in parallel, or move the server closer.

An Ethernet switch decides which port to send a frame out of. Which layer's header does it read?

  1. Application
  2. Transport
  3. Network
  4. Link
Switches work up to layer 2, the link layer, and read MAC addresses. Routers go one layer higher and read the IP header. Hosts implement all five layers.

A link's bandwidth is doubled. A tiny 100-byte request to a server 5,000 km away gets…

  1. barely faster at all
  2. about twice as fast
  3. about four times faster
  4. slower than it was
For a tiny packet, transmission delay is already microseconds; propagation (≈ 25 ms one-way here) dominates and doesn't care about bandwidth. Doubling bandwidth halves a number that was already near zero.

Your Mac sends an HTTP request. As the bits leave the Wi-Fi card, which header comes first, on the outside?

  1. The TCP header
  2. The HTTP header
  3. The Ethernet header
  4. The IP header
Encapsulation wraps from the top down: HTTP inside TCP inside IP inside the link-layer frame. The frame header is outermost, and the receiver strips it first.

Under packet switching, what happens when packets reach a router faster than its outgoing link can send them?

  1. they queue, then get dropped
  2. the router reserves more capacity
  3. the sender pauses its transmission
  4. the link sends them faster
The router buffers them in a queue (queuing delay). When the queue is full, new arrivals are dropped (packet loss). The network layer doesn't recover them; that's a job for a layer above (TCP, session 16).

3 · Back to the tools

One short capture that joins sessions 1 and 2, and sets up session 5.

  1. Open Wireshark, start capturing on Wi-Fi (en0), and type icmp into the display-filter bar.
  2. In Terminal: ping -c 3 1.1.1.1. Stop the capture.
  3. Click one of the captured packets and expand the packet-details pane, just as you did with your HTTP capture in session 2.
  4. Compare its list of headers with your HTTP request's list.
  • Which layer from your HTTP capture is missing from the ping packet, and what sits in its place?
  • Given what's missing, what does that tell you about whether ping can show you that a particular program on the server is up? Bring a hypothesis; session 5 confirms it.
  • Compare the RTTs ping reports with the gap between the request and reply timestamps in Wireshark. Do they agree?
