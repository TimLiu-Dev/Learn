In traditional enterprise routing with OSPF, where does route calculation occur?

Route calculation is fully distributed: every individual router runs Dijkstra's algorithm inside its own local CPU to compute its own routing table.

The Crisis of Traditional Network Management

In traditional networking, every box is an autonomous silo. If you deploy 500 switches, you must log into 500 individual command lines, configure 500 independent OSPF processes, and pray their distributed interactions never trigger a micro-loop.Nick McKeown et al., "OpenFlow: Enabling Innovation in Campus Networks" (ACM SIGCOMM CCR 2008).

In 2008, researchers at Stanford University asked a radical question: why do we build switches like 1970s mainframes, where the operating system and the hardware are welded together in an expensive proprietary box? Why not separate the brain from the forwarding hardware, just like modern computers separate software from CPUs? This became Software-Defined Networking (SDN).

The Three Planes of Networking

To understand SDN, you must separate a network device into three planes:

  • 1. Data Plane (Forwarding Plane): The "muscles." High-speed ASIC hardware switches whose only job is to match arriving packet headers against memory tables and forward, rewrite, or drop packets at nanosecond speeds.
  • 2. Control Plane: The "brain." The logic that determines where packets should go: running routing algorithms, building forwarding tables, and reacting to link failures. In SDN, the control plane is stripped out of individual physical switches and moved into a centralized software controller.
  • 3. Management Plane: The human/API interface used to configure devices (CLI, SSH, SNMP, Terraform).

How SDN Forwarding Works: Flow Tables

In traditional switches, MAC forwarding (CAM) and IP routing (TCAM) are isolated hardware silos. In SDN, all forwarding is generalized into unified Flow Tables:

Flow Entry = [ Match Fields ] → [ Instructions / Actions ] + [ Counters ]

  • Match Fields: Any arbitrary combination of Ingress Port, Source/Dest MAC, VLAN, EtherType, Source/Dest IP, and TCP/UDP ports.
  • Actions: Forward out Port X, Drop, Push/Pop 802.1Q or VXLAN tag, Decrement TTL, Rewrite IP/MAC header, or Send to Controller.
  • Counters: Packets matched, bytes matched, duration active.

Why Hyperscalers Built Everything on SDN

In 2012, Google revealed B4, its private global backbone connecting data centers across continents.S. Jain et al., "B4: Experience with a Globally-Deployed Software Defined WAN" (ACM SIGCOMM 2013).

Using standard distributed BGP, links were limited to ~30% capacity to leave headroom for failures. By replacing distributed BGP with a centralized SDN controller that has real-time visibility into application traffic priorities and link utilization, Google drove fiber link utilization to nearly 100%—saving hundreds of millions of dollars in undersea fiber costs. Every major cloud provider (AWS Nitro, Azure Andromeda, Google Andromeda) is fundamentally an SDN engine.

Hands-on: Inspecting Open vSwitch (OVS) flow tables

Because Open vSwitch runs inside the Linux kernel, launch a quick privileged Ubuntu container on macOS (Docker Desktop, OrbStack, or Lima) first: docker run --rm -it --privileged ubuntu bash -c "apt-get update && apt-get install -y openvswitch-switch && service openvswitch-switch start && ovs-vsctl add-br br0 && bash".

  1. View the flow table entries on an Open vSwitch (OVS) software bridge: 
    $ ovs-ofctl dump-flows br0
    Look for: cookie=0x0, duration=42s, table=0, n_packets=120, priority=100,ip,nw_dst=10.0.0.5 actions=output:2.
  2. Inject a manual SDN flow rule to redirect traffic matching TCP port 80: 
    $ ovs-ofctl add-flow br0 "priority=500,tcp,tp_dst=80,actions=mod_nw_dst:192.168.1.10,output:3"
    Notice how an SDN rule can rewrite IP headers and redirect ports without requiring a separate NAT device!
  3. Inspect the port status and OpenFlow version of the SDN bridge: 
    $ ovs-ofctl show br0
    Verify connected ports and supported OpenFlow capabilities (OF1.3, OF1.5).

Free Recall Practice

From memory: explain the difference between the Control Plane and the Data Plane. Why is this separation revolutionary for cloud networks?

Key points to compare against:

  • Control vs Data Plane: The Control Plane makes policy decisions and computes paths; the Data Plane forwards packets based on hardware match-action tables. In traditional networking, both are locked inside the same physical switch.
  • Why separation is revolutionary: Decoupling them allows network brains to run in scalable, centralized software on server clusters. Cloud orchestrators can program global network policies programmatically via APIs, eliminate vendor lock-in with cheap "white-box" switches, and adapt traffic flows in real time.

Code Implementation: Java & Kotlin

Java 25 
// OpenFlow Pipeline Simulation in Modern Java
import java.util.*;

public class OpenFlowSwitch {
    public record FlowEntry(int priority, String matchIp, int matchPort, String action) {}

    public static String processPacket(String dstIp, int dstPort, List<FlowEntry> flowTable) {
        return flowTable.stream()
            .filter(r -> (r.matchIp().equals("*") || r.matchIp().equals(dstIp)) &&
                         (r.matchPort() == 0 || r.matchPort() == dstPort))
            .max(Comparator.comparingInt(FlowEntry::priority))
            .map(FlowEntry::action)
            .orElse("DROP");
    }

    public static void main(String[] args) {
        var table = List.of(
            new FlowEntry(10, "*", 0, "CONTROLLER"),
            new FlowEntry(100, "10.0.0.1", 80, "FORWARD:2")
        );
        System.out.println("Action: " + processPacket("10.0.0.1", 80, table)); // FORWARD:2
    }
}
Kotlin 
// OpenFlow Pipeline Simulation in Kotlin
data class FlowEntry(val priority: Int, val matchIp: String, val matchPort: Int, val action: String)

class OpenFlowSwitch {
    fun processPacket(dstIp: String, dstPort: Int, table: List<FlowEntry>): String {
        return table.filter { (it.matchIp == "*" || it.matchIp == dstIp) &&
                              (it.matchPort == 0 || it.matchPort == dstPort) }
            .maxByOrNull { it.priority }
            ?.action ?: "DROP"
    }
}

fun main() {
    val table = listOf(
        FlowEntry(10, "*", 0, "CONTROLLER"),
        FlowEntry(100, "10.0.0.1", 80, "FORWARD:2")
    )
    val action = OpenFlowSwitch().processPacket("10.0.0.1", 80, table)
    println("Action: $action")
}
