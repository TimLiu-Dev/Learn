The 5-Phase Diagnostic Hierarchy

The Socket Error Rosetta Stone

When an application fails to connect, the OS kernel returns a specific POSIX error code. Each error pinpoints an exact failure mode:

Operating System ErrorNetwork PhenomenonDefinitive Root Cause
Connection refused
(ECONNREFUSED)		 The target host sent an immediate TCP RST packet back. The network path is 100% fine! The packet reached the target machine, but no application is listening on that port (the process crashed), or a local host firewall (iptables) rejected the port.
Connection timed out
(ETIMEDOUT)		 Client transmitted TCP SYNs repeatedly with exponential backoff; zero response was received. Packets were silently dropped along the path! A cloud Security Group, hardware firewall, or ISP routing black hole is discarding the packet without sending any ICMP error.
Connection reset by peer
(ECONNRESET)		 An active, established connection was abruptly aborted by a TCP RST mid-session. The remote application process crashed, an intermediate stateful firewall timed out the idle connection, or an upstream WAF/DPI middlebox terminated the socket.
No route to host
(EHOSTUNREACH)		 An intermediate router returned an ICMP Destination Unreachable (Type 3). Routing table error. An intermediate router has no matching route to the destination IP or the destination subnet is administratively down.

The 5-Minute Terminal Triage Runbook

  1. Step 1: Test IP connectivity directly (Bypass DNS!): 
    $ ping -c 3 8.8.8.8
    If this succeeds, your local link, IP address, default gateway, and internet NAT are working! If this fails, ping your local gateway (192.168.1.1); if you can't ping your gateway, check arp -a and cable status.
  2. Step 2: Test DNS resolution: 
    $ dig +short api.example.com
    If pinging 8.8.8.8 worked in Step 1 but dig returns nothing, your local DNS resolver is broken.
  3. Step 3: Test TCP socket reachability with netcat: 
    $ nc -zv -w 3 api.example.com 443
    Look at the result:
    • Connection to api.example.com 443 port [tcp/https] succeeded! → L4 is healthy! Problem is at Layer 7.
    • Connection refused → App is down on remote server.
    • Operation timed out → Firewall / Security Group is dropping packets!
  4. Step 4: Test TLS handshake integrity: 
    $ openssl s_client -connect api.example.com:443 -servername api.example.com
    Verify: Verify return code: 0 (ok). Look for certificate expiration, self-signed root errors, or SNI mismatches.
  5. Step 5: Inspect HTTP status codes: 
    $ curl -Iv https://api.example.com/healthz
    • 502 Bad Gateway: The reverse proxy (Nginx/ALB) reached the backend, but the backend application crashed or returned an invalid HTTP response.
    • 504 Gateway Timeout: The reverse proxy reached the backend, but the backend took too long to answer and timed out.

Hands-on: Reproducing socket errors in the terminal

  1. Trigger a real Connection refused error by querying a port with no listening service: 
    $ nc -zv 127.0.0.1 59999
    Notice the immediate, instantaneous rejection (TCP RST emitted by your own kernel!).
  2. Trigger a Connection timed out error by attempting to connect to a blackholed/firewalled IP: 
    $ nc -zv -w 2 192.0.2.1 443
    Notice the 2-second hang as SYN packets disappear into the void with zero response.
  3. Diagnose latency spikes and intermediate packet loss using mtr or traceroute: 
    $ traceroute -m 10 1.1.1.1
    Identify the exact hop where latency jumps or asterisks (* * *) appear.

Free Recall Practice

From memory: explain the exact difference between "Connection refused" and "Connection timed out." What does each tell you about the state of the network?

Key points to compare against:

  • Connection refused (ECONNREFUSED): Proves the network path is fully functional. The client's TCP SYN reached the destination server, but the destination OS kernel sent back an immediate TCP RST because no application is bound to that port (or a host firewall rejected it).
  • Connection timed out (ETIMEDOUT): The network path is blocked. The client sent TCP SYNs but received zero response. A firewall (like an AWS Security Group), packet filter, or dead router dropped the packet silently without emitting an ICMP error or TCP RST.

Code Implementation: Java & Kotlin

Java 25 
// Network Diagnostic Triage Classifier in Java
public class NetworkTriage {
    public static String classify(boolean dns, boolean ping, boolean tcp, boolean tls, int http) {
        if (!dns) return "L3_DNS_FAILURE";
        if (!ping && !tcp) return "L3_HOST_UNREACHABLE";
        if (!tcp) return "L4_PORT_CLOSED_OR_FIREWALL";
        if (!tls) return "L6_TLS_CERT_OR_CIPHER_FAILURE";
        return switch (http) {
            case 200 -> "HEALTHY";
            case 502 -> "L7_BAD_GATEWAY";
            case 504 -> "L7_UPSTREAM_TIMEOUT";
            default -> "UNKNOWN";
        };
    }
}
Kotlin 
// Network Diagnostic Triage Classifier in Kotlin
fun classifyTriage(dns: Boolean, ping: Boolean, tcp: Boolean, tls: Boolean, http: Int): String = when {
    !dns -> "L3_DNS_FAILURE"
    !ping && !tcp -> "L3_HOST_UNREACHABLE"
    !tcp -> "L4_PORT_CLOSED_OR_FIREWALL"
    !tls -> "L6_TLS_CERT_OR_CIPHER_FAILURE"
    http == 200 -> "HEALTHY"
    http == 502 -> "L7_BAD_GATEWAY"
    http == 504 -> "L7_UPSTREAM_TIMEOUT"
    else -> "UNKNOWN"
}
