2 · How Containerlab Actually Works Under the Hood

There is no magic in Containerlab—it automates the exact Session 0075 primitives you just learned:

  1. Reads topology.clab.yml (nodes + endpoints list).
  2. Starts each router as a container (e.g., quay.io/frrouting/frr or ghcr.io/nokia/srlinux) connected to a management bridge for SSH/NETCONF/gNMI access.
  3. For every edge like ["r1:eth1", "r2:eth1"], calls Linux Netlink to create a veth pair and moves each end into the respective router's network namespace.
  4. Mounts startup config files (e.g., daemons, frr.conf) and records topology state in clab-<name>/topology-data.json.
macOS Apple Silicon Tip: Run Containerlab inside a Linux VM (OrbStack or Lima/Colima with Docker) using native ARM64 images like quay.io/frrouting/frr:10.3.1. Avoid x86 QEMU-emulated router VMs on M-series Macs when FRR or SR Linux containers already run natively at full speed!

3 · Anatomy of a Minimal FRRouting Lab Topology

FRRouting (FRR) is an open-source routing suite used in Cumulus Linux, SONiC, container routers, and hypervisors. It runs separate daemons (zebra for kernel FIB sync, ospfd, bgpd, bfdd) behind one Cisco-like unified CLI shell: vtysh.

Previewing a Containerlab + FRR Topology

  1. Verify Docker/OrbStack is available on your Mac: docker info --format '{{.Architecture}} {{.OSType}}'.
  2. Review how vtysh connects to FRR daemons inside a running FRR container: docker exec -it clab-lab-r1 vtysh -c 'show ip route'.
  3. Observe how Containerlab captures packets directly from a virtual router link without modifying router configs: ip netns exec clab-lab-r1 tcpdump -i eth1 -nn.

Declarative 2-Router BGP/OSPF Containerlab Manifest

Java 25 
# topology.clab.yml — version-controlled multi-router lab
name: neteng-bgp-lab
topology:
  nodes:
    r1:
      kind: linux
      image: quay.io/frrouting/frr:10.3.1
      binds:
        - configs/daemons:/etc/frr/daemons
        - configs/r1.conf:/etc/frr/frr.conf
    r2:
      kind: linux
      image: quay.io/frrouting/frr:10.3.1
      binds:
        - configs/daemons:/etc/frr/daemons
        - configs/r2.conf:/etc/frr/frr.conf
  links:
    - endpoints: ["r1:eth1", "r2:eth1"]

Why is Containerlab strongly preferred over legacy GUI-only labs when building CI/CD verification pipelines for network automation?

      
    
        
  1. Containerlab replaces BGP and OSPF completely with proprietary Docker swarm gossip.
    2. 
        
  2. Containerlab forces every virtual router to use the exact same shared routing table.
    3. 
        
  3. Topologies are plain YAML files wired rapidly via kernel veth pairs, enabling headless Git/CI runs.
    4. 
        
  4. It eliminates the need for any Linux kernel networking primitives or TCP/IP stacks.
    5. 
      

      
Infrastructure-as-code topology YAML + fast containers turns network testing into repeatable software CI.

    

    

      
Inside FRRouting (FRR), you configure OSPF and BGP. Which daemon is responsible for resolving administrative distance between them and programming winning routes into the Linux kernel?

      
    
        
  1. zebra, which acts as the central RIB manager programming the kernel FIB via Netlink.
    2. 
        
  2. vtysh, which stays resident in memory as the kernel forwarding plane driver.
    3. 
        
  3. tcpdump, which inspects interface ARP tables to install Layer-3 ECMP routes.
    4. 
        
  4. systemd-networkd, which disables ospfd whenever static routes are added.
    5. 
      

      
FRR separates protocol daemons (ospfd, bgpd) from zebra (kernel RIB/FIB programmer).

    

    

      
When choosing between Containerlab and EVE-NG on a team, when does EVE-NG still make clear practical sense?

      
    
        
  1. When you need ultra-fast ephemeral 10-second automated tests on every Git pull request.
    2. 
        
  2. When running exclusively ARM64-native Linux containers directly on a laptop with zero hypervisor.
    3. 
        
  3. Whenever you only want to write Java socket applications with no router images.
    4. 
        
  4. When emulating legacy monolithic VM appliances (like IOSv, CSR1000v, or vMX) lacking container images.
    5. 
      

      
Match the tool to the NOS packaging: Containerlab for container-native NOS/FRR and CI; EVE-NG for heavy VM-only appliances.
