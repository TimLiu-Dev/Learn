In standard operating systems, what happens if two processes try to bind to TCP port 80 on the same IP address simultaneously?

The operating system kernel rejects the second bind request with an EADDRINUSE ("Address already in use") socket error.

Why Docker's original port-mapping model broke

When Docker gained popularity in 2013, it relied on a host-NAT port-mapping model: every container lived on an internal bridge and mapped ports to the host VM (e.g. docker run -p 8080:80).Kubernetes Documentation: Cluster Networking.

In a large cluster with thousands of microservices, this port-mapping model collapsed: developers had to track port allocations to prevent collisions, applications could not see their own real IPs, and every packet traversed layers of heavy Linux NAT. Kubernetes was designed to fix this from first principles.

The Kubernetes Network Model: The Three Golden Rules

To eliminate port-management chaos, the designers of Kubernetes established three fundamental, non-negotiable networking laws:

  1. Every Pod gets its own real IP address (the IP-per-Pod model).
  2. All Pods can communicate with all other Pods across all nodes in the cluster without NAT.
  3. The IP that a Pod sees as its own IP is the exact same IP that every other Pod and Node sees it as.

Why IP-per-Pod is a Superpower

  • Every Pod acts like a distinct physical virtual machine on a flat network.
  • Two separate Pods running on the exact same worker node can both bind to TCP port 80 with zero conflicts!
  • Containers within the same Pod share the exact same network namespace: they communicate over 127.0.0.1 (localhost) at memory speed and share the Pod's port space (e.g. an app container listens on 8080 while an Envoy sidecar proxy listens on 15001).

Under the Hood: Linux Network Plumbing

How does the Linux kernel provide isolated networking to lightweight containers without launching full virtual machines?

1. Linux Network Namespaces (`netns`)

The Linux kernel allows the operating system to create isolated network stacks called network namespaces. A network namespace has its own private loopback interface (lo), its own network devices (eth0), its own routing table, and its own firewall rules.

2. Virtual Ethernet Pairs (`veth`)

To connect an isolated Pod namespace to the outside world, the kernel creates a veth (Virtual Ethernet) pair. A veth pair acts like a virtual bidirectional patch cable with two ends:

  • End 1 is inserted into the Pod's network namespace and renamed to eth0 (holding IP 10.244.1.5).
  • End 2 stays in the host's root network namespace (named something like veth7a1b2c) and attaches to a virtual Linux bridge or router.
  • Any packet sent into eth0 inside the Pod pops out of veth7a1b2c on the host node instantly!

Hands-on: Building a container network from scratch

Network namespaces (ip netns) and veth pairs are Linux kernel primitives. On macOS, open an interactive Linux shell first via Docker/OrbStack/Lima: docker run --rm -it --privileged ubuntu bash -c "apt-get update && apt-get install -y iproute2 iputils-ping && bash" (inside the container, omit sudo).

  1. Create two isolated Linux network namespaces (simulating two Pods): 
    $ sudo ip netns add pod-red
$ sudo ip netns add pod-blue
    Verify with ip netns list.
  2. Create a virtual Ethernet (veth) cable: 
    $ sudo ip link add veth-red type veth peer name veth-blue
    Plug each end into the respective namespace: 
    $ sudo ip link set veth-red netns pod-red
$ sudo ip link set veth-blue netns pod-blue
  3. Configure IP addresses and ping across the virtual wire: 
    $ sudo ip netns exec pod-red ip addr add 10.0.0.1/24 dev veth-red
$ sudo ip netns exec pod-red ip link set veth-red up
$ sudo ip netns exec pod-blue ip addr add 10.0.0.2/24 dev veth-blue
$ sudo ip netns exec pod-blue ip link set veth-blue up
$ sudo ip netns exec pod-red ping -c 3 10.0.0.2
    Observe that packets traverse isolated namespaces with 0.05 ms latency without touching physical hardware!
