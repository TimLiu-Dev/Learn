Warm-up · from earlier sessions

Two minutes, from memory, before you read on. Retrieving what you learned in session 1 is what makes it stick.

Name the four kinds of delay a packet pays at every hop. Which one grows with packet size, and which one grows with distance?

Processing, queuing, transmission, propagation. Transmission = L ÷ R grows with packet size (and shrinks with bandwidth). Propagation = d ÷ s grows with distance and ignores packet size and bandwidth. Queuing varies with load; when a queue fills, packets are dropped.

A server is 3,000 km away. What is the lowest round-trip time physics allows over fibre, and why can't a faster internet plan beat it?

Light in fibre travels about 2 × 10⁸ m/s, roughly 200 km per ms. One way: 3,000 ÷ 200 = 15 ms; round trip ≥ 30 ms. A bigger plan raises bandwidth, which cuts transmission delay, not propagation delay.

Why layers matter to you

When something breaks, the most useful first question is: which layer is broken?

"Could not resolve host", "Connection refused", "No route to host" and "Wi-Fi has no internet" are four different failures at four different layers. Each one has its own tools and its own fixes. Engineers who can place an error on the right layer debug in minutes. Engineers who can't, guess. Session 43 turns this into a full debugging method.

Layers are also one of the most common interview topics. "Walk me through the OSI model" and "what's the difference between an L4 and an L7 load balancer?" both come straight out of this lesson.

Layers are abstraction, applied to networks

You already know this idea from programming. When your Java code calls socket.getOutputStream().write(bytes), it asks for one service: deliver these bytes, in order, to that program on that machine. It has no idea whether the bytes travel over Wi-Fi, Ethernet or 5G, and it doesn't need to.

Networks are built as a stack of layers. Each layer offers a service to the layer above it and uses only the service of the layer below.Services and layering: Systems Approach §1.3.1; Kurose & Ross §1.5.1. The rules a layer follows when it talks to the same layer on another machine are its protocol: HTTP, TCP, IP and Ethernet are all protocols. The payoff is separation of concerns. Swap Wi-Fi for an Ethernet cable and only the bottom layers change. Your browser, written by people who never saw your router, keeps working.

The cost is overhead: every layer adds its own bookkeeping bytes to every packet. You'll measure that overhead yourself in a few minutes.

  • The OSI model was the ISO standards body's design for a complete protocol suite. Systems Approach §1.3.4. The Internet has no dedicated layers for its extra two, session and presentation. Applications and their libraries do those jobs (such as encoding data) themselves.
  • RFC 1122, the IETF's own description of what an Internet host must implement, uses four layers. It calls the network layer the "Internet layer", and lumps everything below IP, hardware included, into one "link layer".RFC 1122 §1.1.3. It says its application layer "combines the functions of the top two layers — Presentation and Application — of the OSI reference model"; textbooks usually fold session in too. The RFC also calls routers "gateways", an older name you'll still see.

Why "L4" and "L7" use OSI numbers. Layers 1 to 4 line up in both the OSI and Internet models, so "L2 switch", "L3 router" and "L4 load balancer" mean the same thing either way. Above that, the numbers diverge: the application layer is layer 5 in the Internet model but layer 7 in OSI. The industry kept OSI's numbering, so "L7" always means the application layer. An L4 load balancer sees only IP addresses and ports. An L7 load balancer reads the HTTP request itself, so it can route by URL path, header or cookie. AWS's docs say exactly this: their Network Load Balancer works "at the fourth layer" and their Application Load Balancer at "the seventh layer of the OSI model".AWS docs: Network Load Balancer, Application Load Balancer. Load balancers in depth: session 38.

Interview tip: if you're asked to "explain the OSI model", name all seven layers, then say that the real Internet runs on the five-layer stack and where session and presentation went. That second sentence is what shows understanding.

Encapsulation: envelopes inside envelopes

When your Mac sends an HTTP request, the request travels down the stack. Each layer treats everything handed down from above as an opaque payload and puts its own header in front. This is encapsulation.Systems Approach §1.3.2; Kurose & Ross §1.5.2.

The unit of data has a different name at each layer: an application message; a TCP segment (UDP's is a datagram); a network-layer packet; a link-layer frame.Kurose & Ross call the network-layer unit a "datagram". This course says packet throughout, and keeps "datagram" for UDP. At the receiver it runs in reverse. Each layer reads its own header, strips it, and passes the payload up. How does it know which protocol above should get the payload? Each header contains a field naming what's inside it, like a label on an envelope saying which department it's for.Peterson & Davie call this field a demultiplexing key. Systems Approach §1.3.3.

Not every device opens every envelope. Hosts (your Mac, the server) implement all five layers. A router implements layers 1–3: it reads the IP header to choose where to send the packet next and never needs your TCP or HTTP headers.Kurose & Ross §1.5.2: hosts implement all five layers, routers layers 1–3, link-layer switches layers 1–2. Home routers that do NAT are an exception you'll meet in session 10. A switch implements layers 1–2 and forwards on MAC addresses alone.

Code Example: Modeling Encapsulation Overhead in Java and Kotlin

Every layer adds fixed overhead. When sending tiny payloads (like a 1-byte SSH keystroke or a 40-byte ACK), headers consume up to 98% of wire capacity. In Java and Kotlin, engineers calculate goodput (useful payload ÷ wire size) to decide when to batch writes:

public class PacketEncapsulation {
    // Fixed header/trailer sizes in bytes
    public static final int ETHERNET_HEADER = 14;  // 6B Dst MAC + 6B Src MAC + 2B EtherType
    public static final int ETHERNET_TRAILER = 4;  // 4B Frame Check Sequence (FCS) CRC32
    public static final int IPV4_HEADER = 20;      // Standard IPv4 without options
    public static final int TCP_HEADER = 20;       // Standard TCP without options
    public static final int UDP_HEADER = 8;        // 2B SrcPort + 2B DstPort + 2B Len + 2B Checksum

    public static int calcTotalFrameLength(int payloadBytes, String transportProto) {
        int transportHeader = "UDP".equalsIgnoreCase(transportProto) ? UDP_HEADER : TCP_HEADER;
        return ETHERNET_HEADER + IPV4_HEADER + transportHeader + payloadBytes + ETHERNET_TRAILER;
    }

    public static double calcGoodputPercentage(int payloadBytes, String transportProto) {
        int total = calcTotalFrameLength(payloadBytes, transportProto);
        return ((double) payloadBytes / (double) total) * 100.0;
    }

    public static void main(String[] args) {
        int synFrame = calcTotalFrameLength(0, "TCP");
        int httpFrame = calcTotalFrameLength(1442, "TCP");
        double sshGoodput = calcGoodputPercentage(1, "TCP");
        double bulkGoodput = calcGoodputPercentage(1442, "TCP");

        System.out.printf("TCP SYN frame size: %d bytes (0 payload)%n", synFrame);
        System.out.printf("Full HTTP frame size: %d bytes%n", httpFrame);
        System.out.printf("1-byte keystroke goodput: %.2f%%%n", sshGoodput);
        System.out.printf("1442-byte bulk transfer goodput: %.2f%%%n", bulkGoodput);
    }
}
object PacketEncapsulation {
    const val ETHERNET_HEADER = 14
    const val ETHERNET_TRAILER = 4
    const val IPV4_HEADER = 20
    const val TCP_HEADER = 20
    const val UDP_HEADER = 8

    fun calcTotalFrameLength(payloadBytes: Int, transportProto: String): Int {
        val transportHeader = if (transportProto.equals("UDP", ignoreCase = true)) UDP_HEADER else TCP_HEADER
        return ETHERNET_HEADER + IPV4_HEADER + transportHeader + payloadBytes + ETHERNET_TRAILER
    }

    fun calcGoodputPercentage(payloadBytes: Int, transportProto: String): Double {
        val total = calcTotalFrameLength(payloadBytes, transportProto)
        return (payloadBytes.toDouble() / total) * 100.0
    }
}

fun main() {
    val synFrame = PacketEncapsulation.calcTotalFrameLength(0, "TCP")
    val httpFrame = PacketEncapsulation.calcTotalFrameLength(1442, "TCP")
    val sshGoodput = PacketEncapsulation.calcGoodputPercentage(1, "TCP")
    val bulkGoodput = PacketEncapsulation.calcGoodputPercentage(1442, "TCP")

    println("TCP SYN frame size: $synFrame bytes (0 payload)")
    println("Full HTTP frame size: $httpFrame bytes")
    println("1-byte keystroke goodput: ${"%.2f".format(sshGoodput)}%")
    println("1442-byte bulk transfer goodput: ${"%.2f".format(bulkGoodput)}%")
}
