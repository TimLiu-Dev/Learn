Reverse Proxies, Request Smuggling &amp; Graceful Draining

How Nginx, Envoy, and API Gateways terminate TLS, rewrite hop-by-hop headers, stop CL.TE request smuggling, enforce rate limits, and drain connections cleanly on SIGTERM.

Warm-up · from earlier sessions

Two minutes, from memory, before you read on:

Your API server sits behind an ALB/Nginx reverse proxy. During a rolling deploy you stop the old backend container and see a spike of 502 Bad Gateway errors even though Kubernetes already marked the pod Terminating. Why did in-flight or queued requests still hit the dead container?

Two simultaneous race windows occur: (1) iptables/conntrack/Envoy endpoint removal is asynchronous with the pod receiving SIGTERM, so new TCP SYNs or pooled keep-alive requests still arrive for 1–5 seconds after SIGTERM; and (2) killing the HTTP listener immediately drops active in-flight requests mid-response. Returning 503 on /healthz, keeping the listener open briefly with Connection: close, and waiting for active requests to finish eliminates 502s.

1 · What a Reverse Proxy Actually Changes on the Wire

Clients speak to the edge proxy (Nginx, Envoy, Cloudflare, AWS ALB) over TCP+TLS; the proxy maintains a separate pool of backend TCP connections to your application servers. Because backend sockets show the proxy's private IP as remoteAddr, the proxy injects forwarding metadata:

  • X-Forwarded-For: <client-ip>, <proxy1-ip> — Security trap: Never blindly trust the leftmost entry if clients can spoof X-Forwarded-For directly! Count backwards by your known number of trusted proxies (rightmost minus N), or parse Forwarded (RFC 7239).
  • X-Forwarded-Proto: https and X-Forwarded-Host — Essential so your app generates https:// redirects and validates OAuth callback URLs rather than seeing plain backend HTTP.
  • Hop-by-hop header stripping (RFC 9110 §7.6.1): Proxies must strip Connection, Keep-Alive, Proxy-Authenticate, TE, Transfer-Encoding, and Upgrade (unless explicitly proxying WebSockets) so upstream framing doesn't corrupt downstream parsing.

2 · HTTP Request Smuggling (CL.TE & TE.CL)

In HTTP/1.1, message body length can be specified either by Content-Length (bytes) or Transfer-Encoding: chunked. If a front-end proxy trusts Content-Length while the backend honors Transfer-Encoding (a CL.TE desynchronization), an attacker's extra bytes inside one body spill into the backend's keep-alive buffer and get prepended as a hijacked prefix to the next victim user's request on that pooled connection.

Defenses Required on Modern Proxies & Apps:
  • Reject any HTTP/1.1 request containing both Content-Length and Transfer-Encoding (RFC 9112 §6.3 requires 400 Bad Request and closing the connection) or duplicate conflicting Content-Length headers.
  • Upgrade proxy-to-origin links to HTTP/2 (binary length-prefixed DATA frames eliminate ambiguous chunked vs CL text parsing — except beware improper H2-to-H1 downgrade proxies).

3 · Rate Limiting & Load Shedding Algorithms

Edge proxies protect backends with L7 rate limiting (returning 429 Too Many Requests + Retry-After):

  • Fixed Window Counter: Simple (Redis INCR per minute), but allows 2× burst spike at window boundaries (e.g., 100 requests at 00:59 + 100 requests at 01:00 = 200 in 2 seconds).
  • Token Bucket (Burst-friendly): Tokens refill at steady rate r up to capacity B. Allows legitimate short bursts (loading a dashboard) while capping sustained rate.
  • Sliding Window Log / Weighted Counter: Smooths boundary spikes at slightly higher memory/state cost.

4 · Zero-Downtime Graceful Draining Lifecycle

Never treat SIGTERM as "exit immediately". Follow this 4-step drain state machine (which you will implement directly in Capstone 1 / Session 0069):

  1. Enter Draining State: Flip an atomic draining = true flag immediately upon receiving SIGTERM.
  2. Fail Readiness Probe: Make GET /healthz (or /readyz) immediately return 503 Service Unavailable while keeping /livez (if separate) returning 200 so the orchestrator removes the pod from Service/ALB endpoints without force-killing it early.
  3. Stop Keep-Alive Reuse & Wait for Drain Window: Wait a short preStop propagation delay (~2–5 s) so load balancers stop sending new requests, add Connection: close on responses, stop accepting new connections cleanly, and wait until inFlight.sum() == 0 (bounded by a hard deadline before force-exit).

Hands-On Inspection (macOS Terminal)

  1. Use two netcat/Java terminals or curl -v against a local server to observe how Connection: keep-alive vs Connection: close changes socket reuse after response bytes finish.
  2. Test readiness vs liveness probes visually with curl -i http://localhost:8080/healthz before and after signaling kill -TERM <pid> during a slow request.
  3. Inspect request headers echoed by https://httpbin.org/headers (or a local Java echo server) to verify whether your edge proxy/VPN injected X-Forwarded-For or Via.

// 1. Safe right-to-left X-Forwarded-For extraction (trustedProxyCount = hops you control)
public static String realClientIp(String xff, String remoteAddr, int trustedProxyCount) {
    if (xff == null || xff.isBlank() || trustedProxyCount <= 0) return remoteAddr;
    String[] parts = xff.split(",");
    int clientIdx = parts.length - trustedProxyCount;
    if (clientIdx < 0) return parts[0].trim(); // fewer hops than expected
    return parts[clientIdx].trim();
}

// 2. Graceful shutdown hook (Java JVM / Raw ServerSocket)
Runtime.getRuntime().addShutdownHook(new Thread(() -> {
    draining.set(true);               // /healthz immediately returns 503
    try { Thread.sleep(2000); } catch (InterruptedException ignored) {} // LB propagation
    try { serverSocket.close(); } catch (IOException ignored) {}
    long deadline = System.nanoTime() + Duration.ofSeconds(15).toNanos();
    while (inFlight.sum() > 0 && System.nanoTime() < deadline) {
        try { Thread.sleep(25); } catch (InterruptedException ignored) {}
    }
}));
