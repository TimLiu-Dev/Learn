Warm-up · from earlier sessions

Two minutes, from memory, before you read on:

Why does writing a regex parser for show interfaces CLI output over SSH inevitably break in production across vendor OS upgrades—and why does pushing line-by-line SSH config risk leaving a router half-configured if the SSH link drops mid-change?

CLI text is designed for human eyes, not machines: minor firmware column changes break regex parsers, and CLI commands apply imperatively line-by-line without transactional rollback. Model-driven protocols (NETCONF / RESTCONF / gNMI) validate typed YANG schemas upfront, support atomic candidate-to-running commits, and auto-rollback via confirmed-commit timers if management connectivity drops!

1 · YANG & OpenConfig: Typed Schemas for Networks

Before configuring a network device programmatically, you agree on a data contract. In NetDevOps, YAML and JSON hold human-authored intent ("Source of Truth"), while YANG (RFC 7950) defines the strict schema (types, ranges, defaults, keys, read-only state vs read-write config trees).

  • Vendor Native vs OpenConfig: Cisco IOS-XE YANG models differ from Juniper/Arista models. OpenConfig defines vendor-neutral YANG paths (e.g., /interfaces/interface[name=eth1]/config/mtu) supported across Arista EOS, Juniper Junos, Cisco IOS-XR, and Nokia SR Linux.

2 · NETCONF vs RESTCONF vs gNMI

ProtocolTransport / PortEncodingKiller Capability
NETCONF (RFC 6241)SSH (default TCP 830)XMLMulti-datastore (running, candidate, startup), explicit <lock>, atomic <commit>, deadman confirmed-commit auto-rollback!
RESTCONF (RFC 8040)HTTPS (TCP 443)JSON or XMLSimple HTTP GET / PATCH / PUT / DELETE targeting YANG resource paths; easy for web developers & Postman/curl
gNMIHTTP/2 + gRPCProtobuf / JSON_IETFUnified Get, Set, and high-frequency streaming Subscribe telemetry over one binary gRPC channel
Why confirmed-commit saves careers: In NETCONF, you push an ACL or BGP change to candidate and run <commit><confirmed/><confirm-timeout>120</confirm-timeout></commit>. If the ACL accidentally locked out your own management SSH/NETCONF IP, the router automatically rolls back to the exact previous running config 120 seconds later when no second confirming <commit/> arrives!

Why does YANG matter even if your automation pipeline already stores network intent in clean YAML files?

      
    
        
  1. YAML refuses to store IP addresses unless compiled into XML first by NETCONF.
    2. 
        
  2. YANG acts as the formal type-checked schema defining valid ranges, leaf types, and RPC paths.
    3. 
        
  3. YANG compresses Ethernet frames at Layer 1 to double optical fiber throughput.
    4. 
        
  4. YAML cannot be read by Python scripts without an external RADIUS authentication server.
    5. 
      

      
YANG is to network device state what OpenAPI/Protobuf schemas are to software microservices.

    

    

      
You push a management-VRF firewall edit to a remote core router across the WAN using NETCONF confirmed-commit (timeout 180s), and immediately lose SSH/NETCONF access to the router. What happens next?

      
    
        
  1. The router reboots into factory ROMMON defaults after three failed SSH TCP SYN retries.
    2. 
        
  2. NETCONF retries the commit over UDP port 161 SNMP traps until an operator intervenes.
    3. 
        
  3. After 180 seconds without a confirming commit, the router rolls back to pre-change running.
    4. 
        
  4. RESTCONF immediately deletes the BGP neighbor table to prevent traffic leaks.
    5. 
      

      
Always use commit-confirmed whenever touching remote ACLs, management VRFs, or routing policies.
