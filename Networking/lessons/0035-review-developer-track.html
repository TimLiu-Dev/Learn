Trace the architectural evolution across HTTP/1.1, HTTP/2, and HTTP/3: transport layer protocol, message framing, concurrency/multiplexing mechanism, and vulnerability to Head-of-Line (HoL) blocking.

  • HTTP/1.1: Runs over TCP. Uses plain-text framing delimited by \r\n\r\n and Content-Length/chunked markers. One request-response transaction per connection at a time (sequential). Suffers from severe application-layer HoL blocking (forcing browsers to open 6 parallel TCP connections per host).
  • HTTP/2: Runs over TCP. Introduces binary framing layer splitting messages into discrete frames (HEADERS, DATA) tagged with Stream IDs over a single TCP connection. Solves application HoL blocking via interleaved multiplexing, but remains vulnerable to transport-layer HoL blocking: a single dropped TCP segment stalls all multiplexed streams in the OS buffer.
  • HTTP/3: Replaces TCP with QUIC over UDP. Implements binary framing natively inside QUIC. Independent, lightweight streams operate with independent byte accounting: a dropped UDP datagram only stalls the specific stream that lost data, while all other concurrent streams deliver data to the application with zero interruption. Supports 0-RTT/1-RTT handshakes and connection migration across IP changes.

How does modern HTTPS establish both cryptographic trust and data confidentiality? Detail the roles of the X.509 certificate authority chain, SNI, ECDHE key exchange, and Perfect Forward Secrecy (PFS).

  • Trust & Authentication: The server presents an X.509 certificate containing its public key and domain identity. The client cryptographically verifies digital signatures up an unbroken chain of trust: Leaf → Intermediate CA → Root CA stored in the client's local OS/browser trust store.
  • Server Name Indication (SNI): Transmitted in the ClientHello plaintext so multi-tenant reverse proxies know which virtual host certificate to present before TLS encryption begins.
  • Confidentiality via ECDHE: Both client and server generate ephemeral Elliptic-Curve Diffie-Hellman keypairs, exchange public coordinates, and compute an identical shared symmetric secret without ever transmitting the secret over the wire.
  • Perfect Forward Secrecy (PFS): Because ephemeral ECDH keys are immediately discarded from memory after session derivation, an attacker who records encrypted traffic and steals the server's long-term private key 10 years later still cannot decrypt historical captured sessions.

Compare Server-Sent Events (SSE), WebSockets, and WebRTC: transport protocol, directional flow, statefulness, and ideal production use case.

  • Server-Sent Events (SSE): Standard HTTP persistent connection (text/event-stream). Unidirectional (server → client). Stateless/lightweight, native browser auto-reconnect, traverses corporate HTTP firewalls trivially. Ideal for LLM token streaming, live stock ticker feeds, and dashboards.
  • WebSockets: Initiated via HTTP 101 Switching Protocols upgrade, then transitions to a stateful, framing-based full-duplex TCP socket. Bidirectional with minimal per-message frame overhead (2–14 bytes). Ideal for interactive multiplayer games, live collaborative document editing (Figma), and chat applications.
  • WebRTC: Peer-to-peer UDP media pipeline utilizing ICE, STUN, and TURN for NAT traversal, encrypted via SRTP/DTLS. Bidirectional real-time audio, video, and low-latency datagrams. Ideal for video conferencing (Zoom/Meet), voice chat, and peer-to-peer file transfer.

3 · The Staff Engineer Architecture Gauntlet

  

    
Staff System Design Scenario: "You are the lead architect for an e-commerce platform processing 150,000 checkout transactions per second. Outline the end-to-end network architecture from mobile app to backend microservices: protocols, encryption, timeouts, connection management, and resilience strategies."

    

      
The Staff Engineer's Blueprint:

      
    
        
  • Edge / Ingress (Mobile App → Cloud CDN / Anycast API Gateway):
          
      
            
    • Protocol: HTTP/3 (QUIC over UDP) with fallback to HTTP/2 over TLS 1.3. QUIC eliminates connection drops during mobile cell/Wi-Fi handover via Connection IDs and achieves 0-RTT/1-RTT handshakes.
      • 
            
    • Security: TLS 1.3 exclusively with ECDHE (PFS), modern cipher suites (AES-GCM / ChaCha20-Poly1305), OCSP Stapling, and strict HSTS preloading.
      • 
            
    • Authentication: Short-lived JWTs (5 min) signed via asymmetric Ed25519; session refresh tokens stored in HttpOnly; Secure; SameSite=Strict cookies.
      • 
          
    
        
    • 
        
  • Internal Microservices (API Gateway → Order Service → Payment Service):
          
      
            
    • Protocol: gRPC over HTTP/2 with Protocol Buffers serialization. High-density binary packing, strongly typed schemas, and bidirectional streaming.
      • 
            
    • Transport Security: Mutual TLS (mTLS) with internal service mesh certificates rotated automatically every 24 hours.
      • 
          
    
        
    • 
        
  • Resilience & Connection Management:
          
      
            
    • Connection Pooling: Warm persistent HTTP/2 and gRPC channel pools. Keep-Alive pings configured every 30 seconds to prevent silent middlebox NAT dropouts. Pool sized based on Little's Law (N = RPS × Latency).
      • 
            
    • Timeouts: Aggressive differentiated timeouts: Connect timeout 150 ms; Read timeout 800 ms; overall request budget propagated via HTTP/gRPC deadline propagation headers.
      • 
            
    • Retry Policy: Retries strictly restricted to idempotent operations (GET, PUT, or POST with client-generated Idempotency-Key header). Exponential backoff with Full Random Jitter (t = random(0, 2attempt × 50 ms)). Max 2 retries.
      • 
            
    • Circuit Breaker: Local sliding-window circuit breakers (e.g., trip to Open when 50% of requests fail over 5 seconds). Fail fast immediately with fallback cached responses or clean customer error codes without swamping downstream databases.
