HTTP/3 & QUIC: Why HTTP moved to UDP

Zero-RTT handshakes, Connection IDs that survive IP roaming, and eliminating transport Head-of-Line blocking

Why does a dropped packet in HTTP/2 stall all other multiplexed requests across the connection?

Because HTTP/2 runs over TCP. TCP abstracts data as a single, contiguous byte stream. If one packet is lost, the operating system kernel refuses to deliver subsequent received bytes to user space until the lost packet is retransmitted (transport Head-of-Line blocking).

The HTTP/2 paradox on mobile networks

When HTTP/2 was deployed, engineers discovered an alarming paradox: on lossy mobile networks (1–2% packet loss), HTTP/2 was frequently slower than HTTP/1.1!

Why? In HTTP/1.1, browsers opened 6 separate TCP connections. If a packet dropped on connection #1, only that connection paused; the other 5 connections kept downloading at full speed. In HTTP/2, all traffic is consolidated into a single TCP connection. A single packet drop halted all 50 multiplexed resources simultaneously!

TCP's rigid kernel-level byte stream was holding the web hostage. To fix this, engineers at Google took a radical step: bypass TCP entirely.

What is QUIC?

QUIC (RFC 9000) is a modern transport protocol that runs on top of UDP datagrams.RFC 9000: QUIC: A UDP-Based Multiplexed and Secure Transport (IETF Standard, 2021).

By running over UDP in user-space, QUIC achieved what TCP could never do:

1. Independent Stream Multiplexing (No HoL Blocking)

In QUIC, streams are first-class transport citizens. Each stream has its own independent sequence numbering and packet loss recovery. If a packet carrying Stream 1 is lost, the receiver delivers Streams 2, 3, and 4 to the application instantly! Only Stream 1 waits for retransmission.

2. Integrated 1-RTT & 0-RTT Handshake

In classic TCP + TLS 1.3, establishing a secure connection costs 2 full RTTs (1 RTT for TCP, plus 1 RTT for TLS). QUIC merges transport connection and cryptographic key exchange into 1 single RTT. On repeat visits, QUIC supports 0-RTT, allowing the browser to encrypt and transmit HTTP GET requests in the very first packet!

3. Connection Migration (Surviving Wi-Fi → 5G Handoffs)

In TCP, connections are strictly bound to the 5-tuple. When you walk out of your house and your phone switches from Wi-Fi to cellular, your IP address changes. The 5-tuple breaks, all TCP sockets die, and streams fail.

QUIC replaces the 5-tuple identity with a random 64-bit Connection ID (CID). When your phone switches to 5G, it sends packets carrying the same Connection ID from its new IP address. The server seamlessly continues streaming without dropping the connection!

Try it: testing HTTP/3 with curl

  1. Test HTTP/3 connectivity against Cloudflare using curl: 
    $ curl --http3 -I https://cloudflare.com
    macOS default curl may require Homebrew's HTTP/3 build: brew install curl. If unsupported, inspect HTTP/3 directly in Chrome DevTools under the Protocol column (h3).
  2. Look at the response status: HTTP/3 200!
  3. Inspect the Alt-Svc header on any major website: 
    $ curl -I https://www.google.com | grep -i alt-svc
    Notice: alt-svc: h3=":443"; ma=2592000. This tells the browser: "On your next visit, upgrade to HTTP/3 over UDP port 443!"

Key points to compare against:

  • 1. No Transport Head-of-Line Blocking: Streams are independent at the transport layer; packet loss on one stream does not pause other streams.
  • 2. Fast Handshake Latency: Combines transport and TLS 1.3 key exchange into 1 single RTT (or 0-RTT on repeat connections).
  • 3. Connection Migration: Connections are bound to a Connection ID rather than the 5-tuple, allowing uninterrupted streaming when client IP addresses change (e.g. switching between Wi-Fi and 5G).
