What is a Virtual Private Cloud (VPC)?

When you launch a virtual server in Amazon Web Services, Google Cloud, or Microsoft Azure, you are executing code on multi-tenant server hardware shared with thousands of global corporations.AWS Well-Architected Framework: Reliability Pillar — Rel 3: Plan your network topology.

A Virtual Private Cloud (VPC) is a logically isolated virtual network dedicated to your cloud account. Under the hood, the cloud provider's SDN overlay software (such as AWS Nitro) wraps all virtual machine frames in encapsulated overlay packets (Geneve or VXLAN), ensuring that your packets can never be seen or accessed by any other tenant sharing the same physical motherboard or switch.

Designing a Non-Overlapping CIDR Block

When provisioning a VPC, your first architectural decision is defining its primary IPv4 CIDR block from RFC 1918 private address space (typically a /16 providing 65,536 IPs, such as 10.0.0.0/16):

The Fatal Overlap Mistake: Never build your primary production VPC using 192.168.0.0/16, 10.0.0.0/16 (the AWS default), or any subnet used by your corporate office LAN. If two VPCs share identical IP ranges, they can never be connected via VPC Peering, Transit Gateway, or IPsec VPN! Overlapping CIDRs require painful, expensive NAT proxies or total IP renumbering during corporate acquisitions.

Regions, Availability Zones, and Subnet Boundaries

Cloud infrastructure is built on two geographic tiers:

  • Region: A geographic area (e.g. us-east-1 in Northern Virginia or eu-west-1 in Dublin). A VPC spans an entire Region.
  • Availability Zone (AZ): An isolated physical data center (or cluster of data centers) within a Region, separated by 10 to 50 km with redundant high-speed, sub-millisecond fiber connections. AZs have independent power, cooling, and flood plains.
  • The Subnet Rule: In AWS, a subnet exists in exactly one Availability Zone. It can never span across multiple AZs! High availability requires deploying redundant pairs of subnets across at least two distinct AZs (e.g. us-east-1a and us-east-1b).

The Multi-Tier Subnet Pattern

Production enterprise VPCs isolate workloads into three distinct security tiers:

  • Tier 1: Public Subnets (DMZ): Route table points 0.0.0.0/0 to an Internet Gateway (IGW). Contains only public load balancers (ALBs) and NAT Gateways. Application servers should never sit here!
  • Tier 2: Private App Subnets: Contains backend microservices, Kubernetes worker nodes, and container tasks. Route table points 0.0.0.0/0 to an internal NAT Gateway so servers can pull outbound updates, but no inbound Internet traffic can touch them.
  • Tier 3: Isolated Database Subnets: Contains relational databases (Amazon RDS / Aurora) and Redis caches. Route table has zero egress route to the Internet (no IGW, no NAT Gateway). Data cannot leak to the outside world!

The 5 Invisible Reserved Cloud IPs

In standard on-premise networking, every subnet reserves 2 addresses: network (.0) and broadcast (.255). In AWS VPCs, 5 IP addresses are strictly reserved in every subnet and cannot be assigned to hosts:

IP Offset (in 10.0.0.0/24)Assigned Cloud RoleOperational Function
10.0.0.0Network AddressStandard binary base network identifier.
10.0.0.1VPC Default GatewayInternal virtual router IP for default route next-hop.
10.0.0.2Amazon Route 53 DNSVirtual DNS resolver IP (VPC Base + 2).
10.0.0.3AWS Future UseReserved by AWS infrastructure.
10.0.0.255Network BroadcastBroadcast address (AWS drops L2 broadcast, but reserves it).

Therefore, a /24 subnet provides 256 − 5 = 251 usable IPs. A tiny /28 subnet (16 IPs) yields only 16 − 5 = 11 usable IP addresses!

Hands-on: Inspecting VPC subnets and Route 53 DNS

  1. Query your local DHCP lease or cloud instance metadata to identify the VPC DNS resolver: 
    $ cat /etc/resolv.conf
    Notice on AWS EC2 instances, nameserver is set to 10.x.x.2 (the VPC Base + 2 address!).
  2. List subnets and available IP counts using AWS CLI (or local cloud emulator): 
    $ aws ec2 describe-subnets --query "Subnets[*].[SubnetId,CidrBlock,AvailableIpAddressCount,AvailabilityZone]" --output table
    Verify that a fresh /24 subnet displays exactly 251 available IPs!
  3. Test resolution against the internal cloud metadata service: 
    $ curl -s http://169.254.169.254/latest/meta-data/network/interfaces/macs/
    Notice that the cloud hypervisor uses link-local address 169.254.169.254 (RFC 3927) to provide instance identity metadata.

Free Recall Practice

From memory: why does AWS reserve 5 IP addresses in every subnet, and what does each reserved offset represent? Why is CIDR overlap dangerous?

Key points to compare against:

  • The 5 reserved offsets: Offset .0 (Network address), .1 (VPC Router/Default Gateway), .2 (VPC Amazon DNS Resolver), .3 (AWS Future Use), and .255 (Broadcast address). Only total size minus 5 addresses are available to hosts.
  • Why CIDR overlap is dangerous: If two VPCs or an on-premise datacenter share identical IP ranges, standard IP routing cannot route between them because routing tables cannot disambiguate destination addresses. This prevents VPC peering, Transit Gateway attachment, and direct IPsec VPN connectivity.

Code Implementation: Java & Kotlin

Java 25 
// AWS VPC Subnet IP Calculator in Modern Java
public class VpcCalculator {
    public static int awsUsableIps(int prefix) {
        if (prefix < 16 || prefix > 28) return 0; // AWS VPC constraints
        return (1 << (32 - prefix)) - 5; // AWS reserves .0, .1, .2, .3, .255
    }

    public static void main(String[] args) {
        System.out.printf("/24 has %d usable hosts in AWS (256 - 5)%n", awsUsableIps(24)); // 251
        System.out.printf("/28 has %d usable hosts in AWS (16 - 5)%n", awsUsableIps(28));  // 11
    }
}
Kotlin 
// AWS VPC Subnet IP Calculator in Kotlin
fun awsUsableIps(prefix: Int): Int =
    if (prefix in 16..28) (1 shl (32 - prefix)) - 5 else 0

fun main() {
    println("/24 usable: ${awsUsableIps(24)}") // 251
    println("/28 usable: ${awsUsableIps(28)}") // 11
}
