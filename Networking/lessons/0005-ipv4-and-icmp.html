Warm-up · from earlier sessions

Two minutes, from memory, before you read on. Both prompts come from session 1 and session 2.

A packet arrives at a router whose outgoing queue is already full. What happens to it? Does the network itself do anything to recover it?

The packet is dropped: that's packet loss. The network does nothing to fix it. Recovering lost data is TCP's job at the transport layer (session 16). Before the queue fills, packets just wait, which shows up as queuing delay.

An HTTP request travels down the stack. Name the unit of data at each layer from application to link, and say what each layer does to the unit it's handed.

Application: message. Transport: TCP segment (or UDP datagram). Network: packet. Link: frame. Each layer puts its own header in front of what it was handed and passes the result down: encapsulation.

Why this matters

"Request timeout", "Time to live exceeded", "Destination unreachable", "Message too long": these are the network layer talking to you.

They come from IP and its error-reporting partner, ICMP. If you know the IPv4 header, you can read them as precise diagnoses instead of noise. Interviewers like this layer too: "what does TTL do?", "how does ping work?" and "how does traceroute work?" are common warm-up questions. And IPv4's 32-bit address is the reason NAT (session 10) and IPv6 (session 11) exist at all.

IPv4 addresses

An IPv4 address is 32 bits."Addresses are fixed length of four octets (32 bits)." RFC 791 §2.3. We write it in dotted decimal: four bytes, each as a decimal number from 0 to 255, separated by dots, like 192.0.2.10.192.0.2.0/24 is reserved for documentation, like the MAC example in session 4: RFC 5737. 32 bits gives 2³², about 4.3 billion addresses. That's fewer than the number of devices online today. The central free pool of IPv4 addresses ran out in February 2011.NRO, 3 February 2011: "the free pool of available IPv4 addresses is now fully depleted." Keep that shortage in mind. It explains a lot of Part 1.

What IP promises: almost nothing

IP's service is best effort and connectionless. Each packet is handled on its own, with no setup beforehand. The network tries to deliver it, but there are no acknowledgements, no retransmissions, no ordering and no flow control. A packet can be lost, duplicated, delayed or arrive out of order, and IP won't tell anyone."The internet protocol does not provide a reliable communication facility. There are no acknowledgments either end-to-end or hop-by-hop." RFC 791 §1.4. Also Systems Approach §3.3.2. That's the dropped packet from your warm-up. Keeping IP this simple is what lets it run over any kind of link. Reliability is added at the edges, by TCP (Part 2).

The IPv4 header

Every IPv4 packet starts with this header. It's drawn the way the RFC draws it: 32 bits per row, so each row is 4 bytes.The header and every field: RFC 791 §3.1. Walkthrough: Systems Approach §3.3.2, "Packet Format"; Kurose & Ross §4.3.1.

FieldBitsWhat it's for
Version4Always 4 here. (IPv6 has its own header: session 11.)
IHL4Header length in 4-byte words. 5 means 20 bytes, no options.
DSCP · ECN8Originally "type of service". Now a priority marking plus a congestion signal. Usually 0.DSCP: RFC 2474 §3; ECN: RFC 3168 §5.
Total length16Header + data, in bytes. At most 65,535.
Identification, Flags, Fragment offset16, 3, 13Fragmentation bookkeeping (below). The flags are a reserved bit, DF (don't fragment) and MF (more fragments).
TTL8Hop limit. Every router subtracts 1.
Protocol8What's inside: 1 ICMP, 6 TCP, 17 UDPIANA Protocol Numbers registry.
Header checksum16Covers the header only. Recomputed at every hop, because TTL changes.
Source, Destination32 eachWho sent it and where it's ultimately going

Notice the Protocol field does for IP what EtherType did for the Ethernet frame in session 4: it tells the receiver whom to hand the payload to.

TTL: why packets don't circle forever

If routers are misconfigured into a loop, a packet could bounce between them forever, wasting capacity. The TTL (time to live) field prevents that. The sender sets a starting value. Every router that forwards the packet must subtract at least 1. A router that brings TTL to 0 must throw the packet away and send an ICMP Time Exceeded message back to the source.RFC 1812 §5.3.1. It was meant to count seconds, which is where the name comes from; in practice it's a hop count (RFC 791 §3.1). So TTL is really a hop limit. It's also a tool: send a packet with TTL 1 and the first router will tell you who it is. Send TTL 2 and the second one will. That's exactly how traceroute works (session 9).

ICMP: the network layer's error messages

IP can't report problems by itself, so it has a companion: ICMP (Internet Control Message Protocol). ICMP messages travel inside IP packets with Protocol = 1, but ICMP is considered part of IP, not a layer above it."ICMP, uses the basic support of IP as if it were a higher level protocol, however, ICMP is actually an integral part of IP." RFC 792, Introduction. Each message starts with a type and a code. Four types cover almost everything you'll see:

TypeNameSent when
8Echo requestping asks "are you there?"
0Echo replyThe target answers
11Time exceededA router dropped a packet whose TTL hit 0 (code 0)
3Destination unreachableNo way to deliver. Code 4 means "fragmentation needed and DF set".

An ICMP error carries a copy of the offending packet's IP header plus its first 8 bytes of data."Internet Header + 64 bits of Original Data Datagram": RFC 792, Destination Unreachable and Time Exceeded messages. That's how your Mac matches an error to the packet that caused it. You'll see that copy in Wireshark in a minute.

Too big: MTU, DF and fragmentation

Session 4's Ethernet frame carries at most 1,500 bytes, its MTU. What if a packet is bigger than the next link's MTU? An IPv4 router may chop it into fragments. Each fragment is a packet with its own IP header, the same Identification, and a Fragment offset saying where its data belongs, counted in 8-byte units. Every fragment except the last has MF set. Only the final destination reassembles them.Worked example with real numbers: Systems Approach §3.3.2, "Fragmentation and Reassembly". Offsets in 8-byte units: RFC 791 §3.1.

Fragmentation is best avoided: lose one fragment and the whole packet is lost.RFC 8900, "IP Fragmentation Considered Fragile" (BCP 230). So senders can set DF (don't fragment). A router that would have to fragment a DF packet drops it instead and returns ICMP type 3, code 4. The sender then knows to send smaller packets. This is called path MTU discovery.RFC 1191, Path MTU Discovery.

Try it: read, expire and squeeze a packet

You'll use three options of macOS ping: -m sets the TTL, -D sets the DF bit, and -s sets the number of data bytes (default 56).man ping: "-m ttl: Set the IP Time To Live for outgoing packets"; "-D: Set the Don't Fragment bit"; "-s packetsize: … The default is 56, which translates into 64 ICMP data bytes when combined with the 8 bytes of ICMP header data." Linux ping uses different letters. When a router answers instead of the target, ping also prints the header of your packet that the router quoted back:

PING 1.1.1.1 (1.1.1.1): 56 data bytes
xx bytes from xx.xx.xx.xx: Time to live exceeded
Vr HL TOS  Len   ID Flg  off TTL Pro  cks      Src      Dst
 4  5  00 xxxx xxxx   x xxxx  xx  xx xxxx xx.xx.xx.xx  xx.xx.xx.xx

Request timeout for icmp_seq 0

That row is the IPv4 header, field by field. Some columns, like Len, are printed in raw byte order, so take exact numbers from Wireshark.

  1. Check the TTL your Mac starts every packet with: sysctl net.inet.ip.ttl.man ping: without -m, "the kernel uses the value of the net.inet.ip.ttl MIB variable."
  2. In Wireshark, start a capture on Wi-Fi: en0 and set the display filter to icmp.Field names: dfref: IPv4 and dfref: ICMP. In Terminal run ping -c 3 1.1.1.1. Each reply line shows ttl=xx: the TTL the reply had left when it reached you.
  3. Click an Echo (ping) request. Expand Internet Protocol Version 4 and find every field from the diagram. Click each one and watch its bytes light up below. Then expand Internet Control Message Protocol and note its Type and Code.
  4. Expire a packet on purpose: ping -c 2 -m 1 1.1.1.1. In Wireshark, click the Time-to-live exceeded message and expand its ICMP part all the way down.
  5. Repeat with -m 2, -m 3 and so on, until 1.1.1.1 itself replies. Note who answers at each step. You're doing traceroute by hand.
  6. Squeeze: run ping -c 2 -D -s 1400 1.1.1.1, then raise -s in small steps until it fails. Find the largest size that still gets replies. In Wireshark, use the filter ip.flags.df == 1 to confirm DF is set.
  7. Now without DF: ping -c 1 -s 3000 1.1.1.1. Fragments that don't contain the ICMP header won't match icmp, so use the filter ip.addr == 1.1.1.1. For each packet of your request, note Total Length, Identification, MF and Fragment offset.

Then answer these. Bring your answers to chat rather than looking them up:

  • In your echo request: what are IHL, Total Length and Protocol? Account for every byte of Total Length using ping's "56 data bytes" and the header sizes you know.
  • In step 4, which address sent the Time Exceeded message? Inside it is a second IPv4 header. Whose packet is that, and what TTL does it show?
  • What was the smallest -m that reached 1.1.1.1? Replies arrive with ttl=xx: if 1.1.1.1 started them at 64, how many routers did they cross? If the two numbers differ, suggest two reasons why.
  • Take the largest -s that worked with -D, add the ICMP and IP header sizes, and say where you've seen that total before. One byte more: what error did you get, and was it produced by your Mac or by a router?
  • How many IP packets carried your 3,000-byte ping? Show how their offsets (× 8) and lengths fit together.

Check yourself

Answer from memory first. Scroll up only after you've committed to an answer.

An IPv4 header's Protocol field is 6. What does the packet carry?

  1. ICMP
  2. UDP
  3. TCP
  4. IPv6
1 is ICMP, 6 is TCP, 17 is UDP. The Protocol field plays the same role as the EtherType in a frame.

A router receives a packet with TTL 1 that it would need to forward. What does it do?

  1. forwards it on with TTL zero
  2. resets TTL to 64 and forwards
  3. drops it silently, sends no message
  4. discards it, sends ICMP Time Exceeded
Forwarding would take TTL to 0, so the router must discard the packet and send ICMP Time Exceeded (type 11, code 0) to the source. traceroute relies on exactly this.

How long is an IPv4 header with no options?

  1. 20 bytes
  2. 40 bytes
  3. 14 bytes
  4. 8 bytes
Five 32-bit rows: 20 bytes, so IHL = 5. 14 bytes is the Ethernet header, 8 the ICMP header, and 40 the IPv6 header (session 11).

A router's queue is full and it drops your packet. What does IP itself do about it?

  1. retransmits it after a timeout
  2. it does nothing at all
  3. asks the sender to resend
  4. reroutes it via another path
IP is best effort: no acknowledgements, no retransmissions. If the data matters, a higher layer such as TCP notices the gap and resends.

A 4,000-byte packet with DF set reaches a link whose MTU is 1,500. What happens?

  1. router drops it, returns Destination Unreachable
  2. router fragments it into three pieces
  3. router truncates it to 1,500 bytes
  4. router queues it until MTU grows
DF forbids fragmentation, so the router drops it and sends ICMP type 3, code 4 ("fragmentation needed and DF set"). The sender can then try smaller packets: path MTU discovery.

Besides TTL, which IPv4 header field must an ordinary router change at every hop?

  1. the source address
  2. the identification field
  3. the header checksum
  4. the protocol number
The checksum covers the header, and the header just changed (TTL went down by 1), so the checksum is recomputed at every hop. Addresses stay the same unless a NAT rewrites them (session 10).
Primary source

RFC 791, the Internet Protocol specification, §3.1 "Internet Header Format". Free and the definitive source: the field-by-field description of the header you just read in Wireshark, in about 15 minutes. Skip the Options details.

Going deeper: RFC 792, ICMP, short and readable; Systems Approach §3.3.2, including a fragmentation example with real numbers; Kurose & Ross §4.3.1 and §5.6 (with free lecture videos). For a one-page summary, see the addressing reference sheet and the tools reference sheet.
