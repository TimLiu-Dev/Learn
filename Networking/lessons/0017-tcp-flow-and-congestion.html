Warm-up · from earlier sessions

Two minutes, from memory, before you read on:

Do TCP sequence numbers count packets or bytes? What does an Acknowledgment Number of 5001 mean?

TCP sequence numbers count bytes in the data stream, not packets. An ACK of 5001 confirms receipt of all bytes up to 5000 and tells the sender it is waiting for byte 5001.

Two completely different problems

Students and junior engineers frequently confuse Flow Control and Congestion Control. They protect two completely different entities from being overwhelmed:

MechanismWho is being protected?The ThreatControlling Variable
Flow ControlThe Receiver (your laptop or server)The sender transmits bytes faster than the receiving application reads them out of the OS buffer.rwnd (Receive Window), advertised in the TCP header.
Congestion ControlThe Network Core (routers and switches)Senders inject more packets into the internet than intermediate router links can forward.cwnd (Congestion Window), calculated internally by sender.

The sender must respect both limits simultaneously. The maximum volume of unacknowledged data allowed in transit is:

Max Bytes in Flight = min(rwnd, cwnd)

1 · Flow control: The sliding window

When an application receives bytes from the network, the operating system kernel places them in a memory buffer. If your Java code is slow at processing them, the buffer fills up.

To prevent buffer overflow, every TCP segment carries a 16-bit Receive Window (rwnd) field. The receiver continuously informs the sender: "I have 64 KB of free buffer space left." As the buffer fills, the receiver shrinks rwnd. If the buffer is completely full, the receiver advertises rwnd = 0 (a Zero Window). The sender must immediately halt transmission until the receiver reads data and advertises a window update!

The Window Scale Option: A 16-bit field can only advertise up to 216 − 1 = 65,535 bytes (64 KB). On modern gigabit fiber links, a 64 KB buffer is far too small. RFC 7323 defines the Window Scale option negotiated during the 3-way handshake, multiplying the window by up to 214, allowing windows up to 1 Gigabyte!RFC 7323: TCP Extensions for High Performance (Window Scale and Timestamps).

The Bandwidth-Delay Product (BDP)

To achieve 100% throughput on a network link, your TCP window must be large enough to keep the physical pipe completely filled while waiting for the first ACK to return.

Formula: Bandwidth-Delay Product (BDP)

BDP = Link Bandwidth (bits/sec) × Round-Trip Time (sec)

Divide by 8 to convert to bytes. If your TCP window size is smaller than the BDP, the sender is forced to stop transmitting and wait for ACKs, wasting available bandwidth!

Example: Suppose you have a 1 Gbps link connecting New York to London (RTT ≈ 80 ms = 0.08 s):

  • BDP = 1,000,000,000 bits/s × 0.08 s = 80,000,000 bits = 10 Megabytes.
  • If your operating system capped the TCP window at the unscaled 64 KB limit, your maximum achievable throughput would be: 64 KB ÷ 0.08 s ≈ 800 KB/s = 6.4 Mbps—wasting 99.4% of your 1 Gbps fiber!

2 · Congestion control: Protecting the internet

Intermediate routers do not have infinite memory. If senders inject packets faster than a router's outgoing link can transmit them, the router's queue fills and drops packets. If senders blindly retransmit dropped packets, the entire internet collapses into congestion collapse.

To prevent this, the sender maintains an internal Congestion Window (cwnd).

The Classic Algorithm: TCP Reno / Cubic (Loss-based AIMD)

Traditional TCP algorithms treat packet loss as the signal of network congestion, operating in phases:

  • Slow Start: Starts small (typically 10 segments). For every ACK received, cwnd increases by 1 MSS—effectively doubling cwnd every RTT (exponential growth) until it reaches ssthresh (slow start threshold).
  • Congestion Avoidance: Above ssthresh, exponential growth stops. The window grows conservatively by adding 1 MSS per RTT (linear growth).
  • Loss Recovery (AIMD): When 3 duplicate ACKs arrive, TCP cuts cwnd in half (Multiplicative Decrease) and resumes linear growth (Additive Increase). This creates TCP's characteristic "sawtooth" throughput curve.

The modern revolution: Google BBR

In 2016, Google engineers recognized a fatal flaw in Reno and Cubic: loss-based congestion control is fundamentally broken on modern networks.Cardwell et al. (ACM Queue, 2016): "BBR: Congestion-Based Congestion Control". BBR is deployed across YouTube and Google Cloud.

Because modern routers have huge memory buffers, loss only occurs when the buffer completely overflows (bufferbloat). By the time Reno detects loss, packets have been sitting in bloated queues for hundreds of milliseconds, driving latency sky-high. Conversely, on Wi-Fi links, random radio interference causes harmless packet drops, tricking Cubic into slashing throughput in half when the network wasn't congested at all!

BBR (Bottleneck Bandwidth and RTT) does not wait for packet loss. Instead, it builds a continuous mathematical model of the connection: 1. It tracks the minimum observed RTT over the link. 2. It measures the maximum bottleneck bandwidth. 3. It paces transmission to keep intermediate router queues completely empty, maximizing throughput while keeping latency at the speed-of-light floor!

Free Recall Practice

From memory: what is the fundamental difference between Flow Control and Congestion Control? Why does Google BBR outperform classic loss-based TCP Cubic?

Key points to compare against:

  • Flow Control vs Congestion Control: Flow Control (rwnd) protects the receiver's local memory buffer from being overwhelmed by a fast sender. Congestion Control (cwnd) protects intermediate network routers from buffer overflow. Max data in flight is min(rwnd, cwnd).
  • Why Google BBR wins: Classic Cubic waits for packet loss to slow down, allowing oversized router buffers to fill up with latency spikes (bufferbloat). BBR models actual bottleneck bandwidth and min-RTT directly, pacing packets to keep router buffers completely empty while maintaining full throughput.
