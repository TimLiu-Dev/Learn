"Who has this address?" How your Mac finds its neighbours

ARP: from IP address to MAC address

~25 minutesTools: arp, Wireshark★ interview
Your win today

You'll explain how your Mac learns the MAC address behind an IP address on its subnet, then catch it happening: one ARP request and its reply, live in Wireshark.

Warm-up · from earlier sessions

What does a switch do with a frame addressed to ff:ff:ff:ff:ff:ff, or to a MAC address it hasn't learned yet? And which Ethernet header field tells the receiver what kind of data the frame carries?

It floods the frame out of every port except the one it arrived on. A switch learns MAC → port from the source addresses of frames it sees. The EtherType field names the payload: 0x0800 IPv4, 0x86DD IPv6, 0x0806 ARP. (Session 4)

What exactly does ping send and get back, and how does the receiving host know that an IPv4 packet carries ICMP rather than TCP or UDP?

An ICMP echo request; the target answers with an ICMP echo reply. The IPv4 header's protocol field says what's inside: 1 = ICMP, 6 = TCP, 17 = UDP. (Session 5)

Why this matters

Last session ended with your Mac deciding "this destination is on my subnet, deliver it directly". But directly how?

To put a packet on Wi-Fi or Ethernet, your Mac must wrap it in a frame, and a frame needs a destination MAC address (session 4). All your Mac has is an IP address. Something has to translate. That something is ARP, and it runs before almost every conversation your machine starts, including the first hop of every web request. That's why it belongs in any good answer to "what happens when you type a URL?". It's also behind real debugging puzzles: the first ping to a host that's slower than the rest, Host is down errors for a machine on your own network, and an attack (ARP spoofing, session 34) that works because ARP believes whatever it hears.

The question and the answer

The Address Resolution Protocol (ARP) maps an IPv4 address to the MAC address of the interface that owns it, on the local link only.RFC 826 (1982), still the definition. Overview: Systems Approach §3.3.6; Kurose & Ross §6.4.1. It has exactly two messages:

  • An ARP request is broadcast: the frame goes to ff:ff:ff:ff:ff:ff, so every device on the link receives it. In words: "Who has 10.1.2.7? Tell 10.1.2.3." It carries the sender's own IP and MAC address, plus the target IP. The target MAC field isn't filled in with anything meaningful, because that's the unknown.
  • An ARP reply comes only from the device that owns the target IP, and it's unicast straight back to the asker: "10.1.2.7 is at 02:00:00:00:00:07." Everyone else ignores the request.Request = opcode 1, reply = opcode 2. The owner swaps the sender and target fields and sends the reply "to the (new) target hardware address", i.e. the asker: RFC 826, "Packet Reception".

ARP messages ride directly inside link-layer frames with EtherType 0x0806, not inside IP packets. ARP is glue between the network layer and the link layer.

The cache

Broadcasting before every packet would be wasteful, so each host keeps an ARP cache (ARP table) of recent answers. Entries time out, typically after 15–20 minutes, in case a device's address changes.Systems Approach §3.3.6 says "on the order of every 15 minutes"; macOS's man 4 arp says "normally 20 minutes after validated". One shortcut: when the printer receives a request aimed at it, it stores the asker's IP → MAC pair from that request before replying, betting that it's about to talk back.

If nobody answers, your Mac keeps asking a few times and then gives up for a short while. Programs then get an error. On macOS, ping shows it as sendto: Host is down, which really means "ARP got no answer".man 4 arp: after several unanswered requests the host "is considered to be down for a short period (normally 20 seconds)", and sends fail with EHOSTDOWN.

Only for your own subnet

A broadcast frame never leaves its link: routers don't forward them. So ARP can only resolve addresses on your own subnet. For a destination elsewhere, session 6's same-subnet test says "use the gateway", so your Mac ARPs for the gateway's IP. It then sends the frame to the gateway's MAC, with the far-away destination still in the IP header.Sending off the subnet via the router's interface: Kurose & Ross §6.4.1. "Either to the ultimate destination or to a router": Systems Approach §3.3.6. This is session 4's "MAC addresses change at every hop, IP addresses don't", seen from the sender's side.

Two loose ends

ARP trusts everyone. There's no authentication. A host updates its cache from any ARP message about an address it already knows, and "the new hardware address supersedes the old one".RFC 826, "Packet Reception". Any device on your Wi-Fi can claim to be your gateway. That's ARP spoofing, and session 34 comes back to it.

IPv6 doesn't use ARP. It does the same job with Neighbor Discovery (NDP), built on ICMPv6 and multicast instead of broadcast.RFC 4861, Neighbor Discovery for IPv6. Session 11 covers it.

Try it: catch an ARP exchange

arp -a prints your cache; add -n to skip slow name lookups. Each line looks like this. (incomplete) means a request went out and nobody has answered yet:

? (xx.xx.xx.xx) at xx:xx:xx:xx:xx:xx on en0 ifscope [ethernet]
? (xx.xx.xx.xx) at (incomplete) on en0 ifscope [ethernet]

To see ARP on the wire you need a fresh lookup: an IP on your subnet that isn't in the cache yet. The easiest is another device of yours. On a phone, its IP is in the Wi-Fi network's details in Settings.

  1. List your cache: arp -a -n. Find your gateway (route -n get default | grep gateway) in the list.
  2. In Wireshark, start a capture on Wi-Fi (en0) and type the display filter arp.
  3. Pick an on-subnet IP that's not in your cache (check with arp -a -n; use session 6's test to confirm it's on your subnet). Then: ping -c 3 that address.
    Optional, needs your password: to redo the experiment with an address that's already cached, delete its entry first with sudo arp -d xx.xx.xx.xx (see man arp, flag -d). Your Mac relearns it on the next packet.
  4. In Wireshark, find the request (Info: Who has xx.xx.xx.xx? Tell xx.xx.xx.xx) and its reply (xx.xx.xx.xx is at xx:xx:xx:xx:xx:xx). To hide other devices' chatter, narrow the filter: arp.dst.proto_ipv4 == xx.xx.xx.xx || arp.src.proto_ipv4 == xx.xx.xx.xx.
  5. Click each packet. In the details pane, compare the Ethernet II destination with the Address Resolution Protocol fields: Opcode, Sender MAC/IP, Target MAC/IP.
  6. Run arp -a -n again to see the new entry. arp -l -a -n adds an Expire column.
  7. Now ping -c 3 1.1.1.1 with the capture still running, then arp -a -n once more.

Wireshark may also show ARP traffic you didn't cause, sometimes labelled ARP Probe or ARP Announcement: devices checking that nobody else is using their address.RFC 5227, IPv4 Address Conflict Detection. Wireshark's ARP fields: display filter reference.

Then answer these. Bring your answers to chat rather than looking them up:

  • In your request, what was the Ethernet destination MAC, and what was in the ARP Target MAC address field? In the reply, who was the Ethernet destination? Explain each value.
  • Predict first, then check: after pinging 1.1.1.1, did 1.1.1.1 appear in arp -a? Why or why not? Which cache entry did your Mac actually use to send those pings, and how can you tell?
  • Did your capture show ARP between other devices? Which kinds of message from other devices could you see, which couldn't you, and why?

Check yourself

Answer from memory first. Scroll up only after you've committed to an answer.

An ARP request is sent in a frame addressed to which destination MAC?

  1. the target's address
  2. the all-zeros address
  3. the broadcast address
  4. the gateway's address
The asker doesn't know the target's MAC (that's the question), so it broadcasts to ff:ff:ff:ff:ff:ff and everyone on the link receives it.

Your Mac (10.1.2.3/24) sends its first packet to a server at 203.0.113.10. Whose MAC address does it ARP for?

  1. The default gateway's address
  2. The remote server's address
  3. The local switch's address
  4. The DNS resolver's address
203.0.113.10 is off the subnet, so the packet goes via the gateway. The Mac ARPs for the gateway's IP and addresses the frame to the gateway's MAC. The server's IP stays in the IP header. The switch has no address of its own in this exchange.

Why can the ARP reply be unicast when the request had to be broadcast?

  1. Broadcasts are faster than unicast frames
  2. Switches refuse to forward unicast requests
  3. Replies must stay hidden from attackers
  4. The request includes the sender's MAC
The request carries the asker's own IP and MAC, so the owner knows exactly where to send the reply (and caches that mapping too).

How does a host check that an ARP reply is genuine?

  1. It verifies a digital signature
  2. It doesn't; ARP trusts replies
  3. The router confirms each reply
  4. It checks the frame's checksum
ARP has no authentication; a newer mapping simply replaces the old one. The frame check sequence only detects transmission errors, not lies. This is what ARP spoofing exploits.

Which EtherType value marks a frame that carries an ARP message?

  1. 0x0800
  2. 0x86DD
  3. 0x0806
  4. 0x0101
0x0806 is ARP. 0x0800 is IPv4 and 0x86DD is IPv6. ARP sits directly in the frame, not inside an IP packet.

You ping an address on your own subnet that no device is using. What does Wireshark (filter arp) show?

  1. Repeated ARP requests, no reply
  2. One ARP reply from router
  3. An ICMP echo reply anyway
  4. Nothing at all is sent
Your Mac can't send the ICMP packet without a MAC, so it keeps asking "Who has …?" and nobody answers. arp -a shows the entry as (incomplete), and ping eventually reports Host is down.
