Why does QUIC (HTTP/3) avoid transport-layer Head-of-Line blocking?

QUIC runs on UDP and implements stream multiplexing at the transport layer. Each stream maintains its own independent sequence numbers and loss recovery, so packet loss on one stream does not pause other streams.

Beyond request-response

Server-Sent Events (SSE): The developer's secret weapon

Many developers reach for WebSockets when all they need is Server-Sent Events (SSE). SSE is a native browser API (EventSource) that streams text from server to client over standard HTTP.

  • The client sends an ordinary HTTP request with: Accept: text/event-stream.
  • The server replies with: Content-Type: text/event-stream and keeps the connection open indefinitely.
  • Whenever an event occurs, the server flushes lines formatted as: 
    event: message
data: {"token": "Hello"}

event: message
data: {"token": "world"}
  • Why SSE is superior to WebSockets for AI and dashboards: SSE runs over standard HTTP (works natively with HTTP/2 multiplexing, load balancers, and corporate firewalls) and includes automatic reconnection and event IDs out of the box!

WebSockets: True bidirectional TCP

When you need true full-duplex communication (client and server transmitting simultaneously with sub-millisecond overhead), WebSockets are the industry standard.

Free Recall Practice

From memory: compare Server-Sent Events (SSE) and WebSockets. When should an engineer choose SSE over WebSockets?

Key points to compare against:

  • SSE: Unidirectional (server → client). Runs over standard HTTP using text/event-stream. Supported natively by HTTP/2, firewalls, and reverse proxies; features automatic reconnection. Best for streaming LLM tokens, dashboards, and live notifications.
  • WebSockets: Full-duplex bidirectional. Starts with an HTTP 101 Upgrade, then transitions to binary framing over raw TCP. Best for collaborative tools (Figma), multiplayer gaming, and high-frequency two-way messaging.
