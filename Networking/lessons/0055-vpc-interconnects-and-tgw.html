Warm-up · from earlier sessions

Two minutes, from memory, before you read on:

How many point-to-point connections are required to fully mesh N nodes?

A full mesh requires N(N − 1) / 2 connections. For 10 VPCs, that requires 45 connections; for 50 VPCs, it requires 1,225 separate peerings!

From one VPC to enterprise multi-account clouds

A startup begins with a single VPC containing a few subnets. An enterprise, however, operates hundreds of AWS accounts and VPCs separated by security boundaries: Production, Staging, Development, Shared Services, and Payment Processing.AWS Documentation: VPC Peering and AWS Transit Gateway.

How do workloads in Production securely query shared authentication servers in Shared Services without exposing traffic to the public Internet? Cloud networking provides two primary interconnect architectures: VPC Peering and AWS Transit Gateway (TGW).

Option 1: VPC Peering (Direct Point-to-Point)

A VPC Peering connection is a 1-to-1 direct virtual link between two VPCs:

  • Traffic routes directly across the AWS private SDN underlay; it never touches the public Internet.
  • Zero single point of failure: there is no physical gateway appliance to saturate or fail.
  • Zero hourly gateway fees: you only pay standard cross-AZ or cross-region data transfer rates.

The Non-Transitive Peering Rule

VPC Peering has one rigid, non-negotiable architectural rule: Edge-to-edge routing is non-transitive!

If VPC A is peered with VPC B, and VPC B is peered with VPC C, packets from VPC A cannot pass through VPC B to reach VPC C. AWS drops the packets at the hypervisor level. To allow VPC A and VPC C to talk, you must create a direct, dedicated peering connection between A and C.

As an organization expands to 50 VPCs, creating a full mesh requires 1,225 separate peering links and thousands of route table modifications—an operational nightmare.

Option 2: AWS Transit Gateway (TGW)

To eliminate full-mesh peering sprawl, AWS released the Transit Gateway (TGW): a cloud-scale regional virtual router operating as a high-speed hub-and-spoke network fabric:

Key Capabilities of Transit Gateway

  • Transitive Routing: Unlike VPC Peering, TGW is a real Layer 3 router. Workloads in Prod VPC route through the TGW to reach Shared Services or on-premise servers effortlessly.
  • Scale: A single Transit Gateway supports up to 5,000 VPC attachments and scales up to 50 Gbps of burst throughput per VPC connection using AWS Hyperplane SDN technology.
  • Multiple TGW Route Tables (Network Segmentation): You can create multiple independent route tables inside a single TGW. For example, attach Prod VPCs to a "Prod Route Table" and Dev VPCs to a "Dev Route Table" with zero route propagation between them, guaranteeing that Dev can never communicate with Prod!
  • Centralized Inspection (Security VPC): Directs all East-West (VPC-to-VPC) or North-South (Internet-bound) traffic through a centralized inspection VPC containing Next-Gen Firewalls (Palo Alto, Fortinet, AWS Network Firewall) before forwarding packets to their final destination.

Hands-on: Inspecting Transit Gateway attachments and routes

  1. View Transit Gateway attachments across your accounts: 
    $ aws ec2 describe-transit-gateway-vpc-attachments --output table
    Look for: TransitGatewayAttachmentId, VpcId, and associated SubnetIds.
  2. Inspect the routes installed in a specific TGW Route Table: 
    $ aws ec2 search-transit-gateway-routes --transit-gateway-route-table-id tgw-rtb-0123456789abcdef0 --filters "Name=state,Values=active"
    Notice the DestinationCidrBlock: 10.100.0.0/16 mapped to ResourceId: vpc-xxx.
  3. Verify VPC subnet route pointing to the Transit Gateway: 
    $ aws ec2 describe-route-tables --filters "Name=association.subnet-id,Values=subnet-01234"
    Verify that routes destined for other enterprise VPCs target GatewayId: tgw-xxx!

Free Recall Practice

From memory: why does the non-transitive nature of VPC Peering create operational complexity at enterprise scale, and how does Transit Gateway solve this?

Key points to compare against:

  • Non-transitive peering complexity: Because VPC Peering forbids transitive routing, each VPC must establish direct point-to-point peerings with every other VPC it needs to contact. Connecting N VPCs requires N(N − 1) / 2 peering links, leading to route table bloat, administrative overhead, and unmanageable mesh complexity.
  • Transit Gateway solution: TGW acts as a central Layer 3 cloud router. Every VPC connects via a single attachment to the TGW hub. TGW natively supports transitive routing, enabling any VPC to communicate with any other VPC (or on-premise network) according to centralized TGW route table policies.

// AWS Transit Gateway Routing Simulator in Java
import java.util.*;

public class TgwRouter {
    public record TgwRoute(String cidr, String attachment) {}

    public static String route(String ip, List<TgwRoute> routes) {
        long addr = ipToLong(ip);
        TgwRoute best = null;
        int maxLen = -1;
        for (var r : routes) {
            var parts = r.cidr().split("/");
            long net = ipToLong(parts[0]);
            int len = Integer.parseInt(parts[1]);
            long mask = len == 0 ? 0L : (0xFFFFFFFFL << (32 - len)) & 0xFFFFFFFFL;
            if ((addr & mask) == (net & mask) && len > maxLen) {
                maxLen = len;
                best = r;
            }
        }
        return best != null ? best.attachment() : "BLACKHOLE";
    }

    private static long ipToLong(String ip) {
        long r = 0;
        for (var p : ip.split("\\.")) r = (r << 8) | Long.parseLong(p);
        return r;
    }
}

// AWS Transit Gateway Routing Simulator in Kotlin
data class TgwRoute(val cidr: String, val attachment: String)

fun routeTgw(ip: String, routes: List<TgwRoute>): String {
    val addr = ip.split(".").fold(0L) { acc, s -> (acc shl 8) or s.toLong() }
    return routes.map { r ->
        val (cidrIp, lenStr) = r.cidr.split("/")
        val len = lenStr.toInt()
        val mask = if (len == 0) 0L else (0xFFFFFFFFL shl (32 - len)) and 0xFFFFFFFFL
        val net = cidrIp.split(".").fold(0L) { acc, s -> (acc shl 8) or s.toLong() }
        Triple(r, len, (addr and mask) == (net and mask))
    }.filter { it.third }
     .maxByOrNull { it.second }
     ?.first?.attachment ?: "BLACKHOLE"
}
