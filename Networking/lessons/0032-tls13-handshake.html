What is the difference between an Intermediate CA and a Root CA? Where does the Root CA reside?

Intermediate CAs sign public website certificates on behalf of the Root CA, keeping the Root private key offline in a vault. The Root CA is self-signed and pre-installed directly inside the operating system or browser's trusted Root Store.

The TLS 1.3 revolution

Defined in RFC 8446 in 2018, TLS 1.3 was the most ambitious overhaul in the history of internet cryptography.RFC 8446: The Transport Layer Security (TLS) Protocol Version 1.3.

In older versions (TLS 1.0, 1.1, 1.2), establishing an encrypted session required two full round trips (2 RTTs). Furthermore, TLS 1.2 allowed hundreds of complex, obsolete, and insecure cipher suites (static RSA key exchanges, RC4, CBC-mode ciphers vulnerable to POODLE and BEAST attacks).

TLS 1.3 transformed security by applying two radical principles:

  1. Speed: Slashed to 1 RTT: The handshake latency was cut from 2 RTTs down to 1 single RTT (or 0-RTT on repeat visits).
  2. Mandatory Forward Secrecy: Static RSA key exchange was completely abolished. Every connection must use Ephemeral Diffie-Hellman (ECDHE). Only five modern, authenticated AEAD cipher suites (such as TLS_AES_256_GCM_SHA384 and TLS_CHACHA20_POLY1305_SHA256) are permitted.
  3. Maximum Privacy: Everything past the initial ServerHello is encrypted! Even the server's X.509 certificate and extensions are completely shielded from network eavesdroppers.

The 1-RTT handshake in action

  1. ClientHello: The client sends its supported ciphers, the domain it wants (SNI), and proactively sends its Key Share (its Diffie-Hellman public key) in the very first packet!
  2. ServerHello: The server chooses the cipher and sends its own Key Share. Both sides now calculate the shared symmetric secret!
  3. Encrypted Transmission: The server immediately switches to symmetric encryption, sending its Certificate and digital signature verification encrypted, concluding with Finished.
  4. The client sends its own Finished verification and immediately streams encrypted HTTP payload data!

Server Name Indication (SNI)

In session 23, we saw that HTTP/1.1 uses the Host header to host multiple domains on one IP. But in HTTPS, the HTTP headers are encrypted inside TLS! How does the web server know which SSL certificate to present before encryption is established?

To solve this, the client includes the Server Name Indication (SNI) extension inside the plaintext ClientHello.RFC 6066 §3: Server Name Indication. This informs the server: "I am connecting to api.example.com" so it loads the correct certificate.

Decrypting HTTPS in Wireshark: SSLKEYLOGFILE

Because TLS 1.3 uses ephemeral keys (PFS), simply knowing the server's private key is no longer enough to decrypt a packet capture! To debug HTTPS, operating systems support the SSLKEYLOGFILE standard.Wireshark Wiki: TLS Decryption. Supported natively by Chrome, Firefox, and curl.

Try it: decrypting your own HTTPS traffic

  1. Open Terminal and set the SSL keylog environment variable, running curl: 
    $ SSLKEYLOGFILE=~/Desktop/tls_keys.log curl https://example.com
  2. Inspect the generated keylog file: 
    $ head -n 5 ~/Desktop/tls_keys.log
    You will see lines starting with CLIENT_TRAFFIC_SECRET_0 and hex secrets.
  3. In Wireshark: go to Settings → Protocols → TLS → (Pre)-Master-Secret log filename, and browse to tls_keys.log.
  4. Capture or open your trace: Wireshark will automatically decrypt the TLS session, lighting up the plain HTTP request and response tabs!

Free Recall Practice

From memory: how does TLS 1.3 reduce handshake latency from 2 RTTs to 1 RTT? What is the function of SNI?

Key points to compare against:

  • 1-RTT Reduction: In TLS 1.3, the client speculates on the server's elliptic curve and sends its Diffie-Hellman public key share directly in the initial ClientHello. The server replies with its own key share in ServerHello, allowing symmetric encryption to begin immediately after 1 round trip.
  • SNI: Server Name Indication is an extension in the plaintext ClientHello that names the requested hostname, enabling virtual hosting servers to select and present the correct TLS certificate before encryption begins.
