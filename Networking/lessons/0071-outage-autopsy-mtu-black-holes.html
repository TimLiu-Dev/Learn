Outage Autopsy: MTU Black Holes & Silent TCP Freezes

The anatomy of the most perplexing network failure in systems engineering: why ping and DNS work perfectly, small API calls fly, yet large TLS handshakes and file transfers hang forever.

~25 minutesTools: ping -D -s, PMTUD, MSS Clamping⚡ outage autopsy★ interview
Your win today

You'll diagnose silent TCP freezes caused by tunnel encapsulation overhead and dropped ICMP Type 3 Code 4 packets, binary-search exact Path MTU on macOS using ping -D -s, and apply the three production fixes (ICMP firewall policy, TCP MSS clamping, and PLPMTUD).

The Symptom: The "Almost Working" Network

You deploy a new service across a VPN, cloud VPC, or SD-WAN tunnel. The junior engineer tests the connection and reports complete success: ping api.service.internal returns sub-millisecond replies with zero packet loss, curl http://api.service.internal/health returns 200 OK in 4 ms, and DNS resolves instantly.

Ten minutes later, production deploys. Customer reports flood in immediately: users can log in, but viewing order histories hangs indefinitely; SSH sessions connect and allow typing pwd, but executing ls -la or cat config.json freezes the terminal; TLS connections hang during the initial handshake without ever reaching application code.

This is the classic signature of an MTU Black Hole. It is one of the most widespread, time-consuming diagnostic traps in computer networking.

The Mechanics: Path MTU Discovery (PMTUD)

Standard Ethernet has a Maximum Transmission Unit (MTU) of 1,500 bytes. A standard TCP/IPv4 segment consumes 20 bytes of IP header and 20 bytes of TCP header, leaving a Maximum Segment Size (MSS) of 1,460 bytes.

To avoid the performance degradation of router IP fragmentation (which burdens router CPUs and causes entire packets to be discarded if a single fragment is lost), modern operating systems set the Don't Fragment (DF=1) bit in the IPv4 header of all outgoing TCP packets.

When packets traverse encapsulation tunnels (such as IPsec, WireGuard, GRE, PPPoE, or AWS VPC Geneve/VXLAN overlay networks), tunnel headers are prepended to the packet. This shrinks the effective payload MTU of the intermediate link from 1500 bytes down to 1420 or 1360 bytes.

Why Small Packets Work While Large Packets Freeze

The deceptive nature of an MTU Black Hole arises because TCP handshakes and basic health checks consist of tiny packets:

  • TCP 3-Way Handshake: SYN, SYN-ACK, and ACK packets contain only protocol headers and options (~40 to 64 bytes). They pass through the 1420-byte tunnel without issue.
  • HTTP Health Checks: GET /health is ~100 bytes; the response {"status":"UP"} is ~150 bytes. Both easily fit inside any intermediate MTU.
  • ICMP Ping: Default ping sends 56 or 64 bytes of payload. It easily traverses the link.
  • Large Payloads & TLS Handshakes: When the server transmits a TLS certificate chain (often 3,000 to 5,000 bytes) or returns a JSON API response larger than 1,420 bytes, TCP segments the data into full 1,500-byte frames with DF=1. The tunnel router cannot transmit them across the 1420-byte link, drops them, and generates an ICMP packet. When the firewall drops that ICMP notification, the connection enters an infinite silent retransmission loop.

Hands-On: Terminal Reproduction & Diagnosis

You can identify the exact Path MTU to any remote host using ping by setting the Don't Fragment bit and testing payload sizes.

  1. Test with a standard 1,500-byte packet on macOS (1,472 bytes ICMP payload + 8 bytes ICMP header + 20 bytes IPv4 header = 1,500 bytes): 
    $ ping -D -c 3 -s 1472 1.1.1.1
# (Linux equivalent: ping -M do -c 3 -s 1472 1.1.1.1)
    If the path supports a full 1,500-byte MTU, pings succeed. Now test 1 byte larger (-s 1473) and observe your kernel reject it immediately with ping: sendto: Message too long!
  2. If a VPN or tunnel hangs silently without response at 1472, binary-search downward until replies succeed: 
    $ ping -D -c 3 -s 1392 1.1.1.1   # 1392 + 28 = 1420 bytes (WireGuard / IPsec MTU)
    Add 28 bytes (IPv4 + ICMP headers) to the largest working -s value to find your exact Path MTU.
  3. Check your active macOS interface MTUs (compare physical en0 against any active utun* VPN interfaces): 
    $ ifconfig | grep -E '^[a-z0-9]+:|mtu'
# (On a Linux container/VM, you can also run: tracepath example.com)

Three Production Solutions

Solution 1: Fix the Firewall (Permit PMTUD ICMP)

The cleanest fix according to RFC 1191 and RFC 4821 is to stop dropping necessary ICMP control packets. Update security groups and firewalls to permit:

  • IPv4: ICMP Type 3, Code 4 (Destination Unreachable: Fragmentation Needed and DF Set).
  • IPv6: ICMPv6 Type 2 (Packet Too Big). Note that IPv6 routers never fragment packets; Path MTU Discovery is mandatory in IPv6. Blocking ICMPv6 Type 2 breaks IPv6 traffic completely!

Solution 2: TCP MSS Clamping on Routers

When you do not control external firewalls or intermediate networks, border routers can perform TCP MSS Clamping. The router inspects all passing TCP SYN packets, checks the advertised MSS option, and rewrites it to match the tunnel path:

# Linux iptables MSS Clamping:
iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu

# Or explicitly clamp to 1360 (for 1400 MTU):
iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --set-mss 1360

# Cisco IOS:
interface Tunnel0
 ip tcp adjust-mss 1360

Because both endpoints now believe the maximum segment size is 1,360 bytes, neither host ever transmits a packet larger than 1,400 bytes, completely bypassing the MTU bottleneck!

Solution 3: OS-Level Black Hole Detection (PLPMTUD)

RFC 4821 defines Packetization Layer Path MTU Discovery (PLPMTUD). The Linux kernel can automatically detect MTU black holes when TCP experiences repeated retransmissions, dynamically shrinking its segment size without relying on ICMP:

# Enable TCP MTU Probing in Linux sysctl:
sudo sysctl -w net.ipv4.tcp_mtu_probing=1

Code Implementation: Java & Kotlin

Java 25 
// PMTUD Black Hole & MSS Clamp in Java
public class PmtudEngine {
    public static boolean detectBlackHole(int size, int mtu, boolean df, boolean icmpBlocked) {
        return size > mtu && df && icmpBlocked;
    }

    public static int clampMss(int mtu) {
        return mtu - 40; // 20 bytes IP + 20 bytes TCP
    }
}

Why is blocking ICMPv6 Type 2 (Packet Too Big) even more destructive in IPv6 networks than in IPv4?

      
    
        
  1. IPv6 routers do not perform packet fragmentation; PMTUD is the sole mechanism to adapt packet size
    2. 
        
  2. IPv6 switches automatically disable port duplex when ICMP is dropped
    3. 
        
  3. IPv6 addresses cannot be translated without ICMP type 2 translation tables

    5. 
      

      
In IPv6, intermediate routers are strictly forbidden from fragmenting packets; senders must perform PMTUD, making ICMPv6 Packet Too Big indispensable.
