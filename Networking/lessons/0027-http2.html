HTTP/2: Binary framing, multiplexing, and HPACK

Solving application-level head-of-line blocking, single-socket efficiency, and header compression

Warm-up · from earlier sessions

Two minutes, from memory, before you read on:

What limitation existed in HTTP/1.1 persistent connections when fetching 50 images from a server?

HTTP/1.1 persistent connections operate strictly in FIFO (First-In, First-Out) order per TCP socket. If request #1 stalls, all subsequent requests must wait behind it (Application-level Head-of-Line blocking).

Why HTTP/1.1 hit a wall

Between 1999 and 2015, the web shifted from static HTML documents to complex web applications requiring hundreds of resources (JavaScript bundles, CSS stylesheets, images, API calls).RFC 9113: HTTP/2 (superceding RFC 7540). Developed from Google's SPDY protocol.

HTTP/1.1 struggled under this load because of two severe bottlenecks:

  1. Application Head-of-Line (HoL) Blocking: Even with Keep-Alive, HTTP/1.1 cannot interleave responses. If a large image is requested first, a tiny 200-byte JSON response must wait until the entire image is transmitted! To hack around this, browsers opened 6 parallel TCP connections per domain, and engineers split assets across multiple domains (Domain Sharding: cdn1.site.com, cdn2.site.com).
  2. Redundant Header Bloat: Every single HTTP/1.1 request retransmits identical headers (User-Agent, Accept, Cookies), often burning 1 to 2 KB of uncompressed ASCII text per request.

The core innovations of HTTP/2

HTTP/2 preserved 100% of HTTP's application semantics (methods, headers, status codes, URIs remain identical), but radically changed how bytes travel across the wire:

1. The Binary Framing Layer

Instead of parsing newline-delimited ASCII strings, HTTP/2 parses structured binary frames:

  • HEADERS frame: Carries request/response headers.
  • DATA frame: Carries payload body chunks.
  • SETTINGS frame: Negotiates configuration parameters.
  • RST_STREAM frame: Cancels a specific stream without closing the underlying TCP socket!

2. Streams and Multiplexing

Every frame carries a 31-bit Stream ID. Client-initiated streams use odd numbers (1, 3, 5...); server-initiated streams use even numbers. The client can initiate 100 requests concurrently down a single socket. Responses arrive interleaved and are cleanly reassembled by Stream ID, completely eliminating application Head-of-Line blocking!

3. HPACK Header Compression (RFC 7541)

HTTP/2 uses a purpose-built header compression algorithm called HPACK:RFC 7541: HPACK - Header Compression for HTTP/2.

  • Static Table: Pre-defines 61 common headers indexed by integer (e.g. index 2 = GET /, index 7 = :scheme: https).
  • Dynamic Table: As client and server exchange custom headers (like authorization tokens), both sides record them in a shared stateful dictionary. Subsequent requests send only a 1-byte integer reference instead of a 1,000-byte string!

Try it: comparing HTTP/1.1 vs HTTP/2 with curl

  1. Fetch Google using HTTP/1.1: 
    $ curl -I --http1.1 https://www.google.com
    Notice the Status Line: HTTP/1.1 200 OK.
  2. Fetch Google using HTTP/2: 
    $ curl -I --http2 https://www.google.com
    Notice the Status Line: HTTP/2 200!
  3. Run verbose mode to see the ALPN (Application-Layer Protocol Negotiation) during TLS: 
    $ curl -v --http2 https://www.google.com
    Look for: ALPN: server accepted h2.

Free Recall Practice

From memory: explain how HTTP/2 multiplexing works. Why did HTTP/2 render domain sharding obsolete?

Key points to compare against:

  • How Multiplexing works: HTTP/2 splits requests and responses into binary frames tagged with a Stream ID. Frames from multiple concurrent requests are interleaved over a single TCP socket and reassembled at the receiver, preventing slow requests from blocking subsequent ones.
  • Why Domain Sharding died: Domain sharding was a hack to circumvent the browser's 6-connection-per-domain limit in HTTP/1.1. In HTTP/2, all requests share a single optimized TCP connection; opening multiple connections hurts performance by restarting TCP slow start and splitting HPACK compression tables.
