Why the internet doesn't know your laptop's address

Private addresses and network address translation

~25 minutesTools: ipconfig, curl, dig, traceroute★ interview
Your win today

You'll explain why websites see a different IP address from the one your laptop has, how replies still find their way back to the right device, and you'll work out how many layers of NAT sit between your laptop and the internet.

Warm-up · from earlier sessions

Which address does each layer use (application, transport, network, link)? Which layers does a router implement?

Application: none of its own. Transport: port. Network: IP address. Link: MAC address. Hosts implement all five layers; routers go up to the network layer; switches up to the link layer. (Session 2.) Keep the router fact in mind: NAT bends it.

How many bits is an IPv4 address, roughly how many addresses is that, and what problem did that create?

32 bits, so 2³² ≈ 4.3 billion addresses. That's fewer than the devices that want to be online, so the supply ran out (IPv4 exhaustion). (Session 5.) Today's session is the workaround that kept IPv4 alive.

Why this matters

You start a server on your laptop, it works on localhost, and your phone on Wi-Fi can reach it too. Switch the phone to mobile data and it can't connect at all.

NAT is the reason. It's also why webhook providers can't call a server running on your laptop, why video calls and multiplayer games need extra machinery to connect two people directly, and why your server logs may show hundreds of users arriving from a single IP address, which makes rate-limiting by IP risky. Interviewers ask about NAT because the honest answer to "how does the reply get back to my laptop?" tests whether you understand addresses and ports.

Private addresses

IPv4 has too few addresses for every device to get its own. So RFC 1918 set aside three blocks of private addresses that anyone can use inside their own network:RFC 1918 §3. ISPs are expected to filter routes to these blocks out of the public internet.

BlockRangeTypical use
10.0.0.0/810.0.0.0 – 10.255.255.255companies, cloud VPCs
172.16.0.0/12172.16.0.0 – 172.31.255.255companies, Docker
192.168.0.0/16192.168.0.0 – 192.168.255.255home routers

Millions of homes reuse the same 192.168.1.x addresses. That works only because packets with private addresses are never routed across the public internet. Note the /12: 172.32.0.1 is not private. Use your session 6 subnet maths.

So how does a laptop at 192.168.1.20 load a web page? Its home router has one public address from the ISP, and it shares that one address among every device in the house.

How NAT works: rewrite on the way out, look up on the way in

A NAT (network address translator) router sits between the private network and the public one. Home routers use the port-based variant, NAPT (network address and port translation), and everyday "NAT" almost always means NAPT.RFC 3022 §2.2 defines NAPT as mapping (private IP, port) pairs onto one public address with different ports. Also Kurose & Ross §4.3.3.

  1. Outbound. When a packet leaves the LAN, the router replaces its private source IP with the public IP, and its source port with a port it picks. It records the pair in its translation table.
  2. Inbound. When a reply arrives at the public IP, the router looks up the reply's destination port in the table, rewrites the destination back to the private IP and port, and forwards the packet onto the LAN.

The destination of an outgoing packet is never touched. The server just sees a connection from the router's public address and replies to it.

Why rewrite the port, not just the IP? Because the port is the only thing that tells replies apart. If your phone also connects from port 51000, the router gives it a different outside port, and the reply's destination port says which device it's for. Ports are 16-bit, so one public IP can carry tens of thousands of simultaneous connections.

Notice what the router just did. In session 2, routers only went up to the network layer. A NAT router reads and rewrites transport-layer ports, and it has to fix the TCP/UDP checksums too.Header rewriting and checksum adjustment: RFC 3022 §4.1–4.2. That layer violation is the source of most of NAT's side effects.

What NAT breaks

Unsolicited inbound traffic. A table entry exists only because someone inside sent something first, and idle entries expire after a few minutes.A UDP mapping must last at least 2 minutes; 5+ minutes is recommended: RFC 4787 §4.3 (REQ-5). A connection that starts outside matches no entry, so the router has nowhere to send it and drops it. That's your phone-on-mobile-data problem. The fix at home is port forwarding: a permanent entry you configure by hand, such as "public port 8080 → 192.168.1.20:8080".RFC 3022 §2.2: inbound sessions work only through ports "statically mapped" to an inside host.

NAT is not a firewall. Unsolicited packets get dropped because there's no mapping, not because anything checked them. Rewriting address bits gives no security by itself. The real protection is the stateful filtering that routers usually run alongside NAT, which you'll meet properly in session 36.RFC 4864 §2.2: "The act of translating address bits within the header does not provide security in itself." §4.2: "IPv4 NAT was not developed as a security mechanism."

Peer-to-peer. When two people behind NATs want a direct connection (video calls, games), neither one can accept unsolicited traffic. Apps use STUN to ask an outside server "what public IP and port do you see me as?", then try to "punch holes" by having both sides send at once. When that fails, a TURN server relays everything, which is reliable but slower.STUN: RFC 8489. TURN: RFC 8656. Hole punching and relaying ("most reliable, but least efficient"): RFC 5128 §3. You only need the names for now.

NAT on top of NAT

Many ISPs can no longer give every customer a public IPv4 address. Instead they run their own big NAT, called carrier-grade NAT (CGNAT), and give your router an address from 100.64.0.0/10, the shared address space reserved for exactly this.RFC 6598: 100.64.0.0/10 numbers the links between CGN devices and customer routers, and must not cross ISP boundaries. Your packets are translated twice: once by your router, once by the ISP. Port forwarding on your own router can't help then, because the ISP's NAT has no entry pointing at you.

Double NAT also happens at home, for example an ISP modem-router with your own Wi-Fi router plugged in behind it. Each NAT puts its "inside" addresses one hop further from the internet.

How to tell from your laptop. Compare three things: your LAN address, the public address a website sees, and your router's WAN address (shown on its admin page). Then look at the first few hops of a traceroute (session 9) and classify each address: RFC 1918 private, 100.64.0.0/10 shared, or public. Each NAT shows up as a boundary between address types.

Try it: find your NATs

Output formats look like this (your values will differ):

$ ipconfig getifaddr en0
xxx.xxx.xxx.xxx
$ traceroute -n -m 5 -q 1 1.1.1.1
traceroute to 1.1.1.1 (1.1.1.1), 5 hops max, 40 byte packets
 1  xxx.xxx.xxx.xxx  x.xxx ms
 2  xxx.xxx.xxx.xxx  x.xxx ms
 …
  1. Your laptop's LAN address: ipconfig getifaddr en0
  2. The address the internet sees, from two independent services: curl -4 -s https://icanhazip.com and dig +short myip.opendns.com @resolver1.opendns.com. (-4 forces IPv4; IPv6 is next session.)
  3. Your router's LAN address, as in session 1: route -n get default | grep gateway
  4. If you can, open that address in a browser, log in to the router's admin page and find its WAN or Internet IP address. Look only. Don't change any settings. If you can't log in, skip this step.
  5. The first five hops toward the internet: traceroute -n -m 5 -q 1 1.1.1.1. (-n skips name lookups, -q 1 sends one probe per hop.) Label each hop: private, shared (100.64.0.0/10) or public.

Then answer these. Bring your answers to chat rather than looking them up:

  • Which RFC 1918 block is your LAN address in? How does it compare with what icanhazip and OpenDNS reported, and do those two agree with each other?
  • If you saw your router's WAN address: is it the same as the address icanhazip saw? If not, what kind of address is it, and what does that tell you?
  • In your traceroute, how many hops pass before the first public address? Are you behind CGNAT, double NAT, both, or neither? Say which evidence settles it.
  • Could a friend on another network connect to a server on your laptop's port 8080 right now? What would need to change, and is that change possible given your answer above?

Check yourself

Answer from memory first. Scroll up only after you've committed to an answer.

Which of these is an RFC 1918 private address?

  1. 172.32.4.1
  2. 192.169.0.5
  3. 10.200.3.4
  4. 100.64.0.9
10.0.0.0/8 covers every 10.x.x.x address. 172.16.0.0/12 stops at 172.31.255.255, 192.168.0.0/16 doesn't include 192.169, and 100.64.0.9 is in the CGNAT shared space (RFC 6598), not RFC 1918.

A reply arrives at the router's public IP. How does NAPT know which inside host it's for?

  1. By broadcasting the reply to everyone
  2. By the reply's destination port number
  3. By the reply's source MAC address
  4. By the reply's IP header checksum
Every inside host shares one public IP, so the destination port is the only thing that tells replies apart. The router looks it up in its translation table. MAC addresses change at every hop, so the server's MAC never reaches your router.

From another network, a friend tries to open a TCP connection to your router's public IP, port 8080. Nothing is forwarded. What happens?

  1. Delivered to every LAN host
  2. Forwarded to the default gateway
  3. Delivered to the DHCP server
  4. The router silently drops it
Translation entries are created by outbound traffic. An inbound connection with no entry and no port-forwarding rule has nowhere to go, so the router drops it (or answers it itself).

Your ISP uses CGNAT. Why doesn't adding a port-forwarding rule on your home router let friends reach your game server?

  1. The ISP's NAT also needs a mapping
  2. Port forwarding only works with IPv6 addresses
  3. Your router cannot run a DHCP server
  4. Game servers must use well-known port numbers
Inbound traffic first hits the ISP's carrier-grade NAT, which has no entry pointing at your router, so it never reaches your rule. You'd need the ISP's cooperation, IPv6, or a relay or tunnel.

Which statement about NAT and security is accurate?

  1. NAT encrypts traffic between LAN and internet
  2. NAT replaces the need for any firewall
  3. NAT blocks via missing state, not translation
  4. NAT hides which websites your hosts visit
Unsolicited packets are dropped only because no mapping exists. Rewriting addresses protects nothing by itself (RFC 4864 §2.2). Real protection comes from deliberate stateful filtering, and NAT encrypts nothing.

Two laptops on your LAN both connect to the same server from source port 51000. Why must NAPT rewrite the source port, not only the IP?

  1. Ports below 1024 need special privileges
  2. The server rejects duplicate source ports
  3. Routers cannot forward packets without ports
  4. Otherwise both mappings would look identical
With only the IP rewritten, both connections would appear as 203.0.113.7:51000 → server:443, and the router couldn't tell whose reply was whose. A distinct outside port per connection keeps the mappings unique.
Primary source

RFC 3022, "Traditional IP Network Address Translator", §2 (Overview). Short and readable, and it's the document that defines NAPT. Read §2.2 with today's diagram beside it, then skim §6 to see what its authors already knew NAT would break.

Going deeper: Kurose & Ross §4.3.3; RFC 4787 (how real NATs map and filter, the background to STUN); RFC 6598 (CGNAT's address block). Summary tables: Addressing and LAN protocols reference sheets.
