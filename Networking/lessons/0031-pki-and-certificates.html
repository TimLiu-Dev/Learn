Why does modern network security use hybrid cryptography rather than pure asymmetric encryption?

Asymmetric encryption is thousands of times slower than symmetric ciphers. Hybrid cryptography uses asymmetric Diffie-Hellman key exchange only during the handshake to agree on a secret, then immediately switches to hardware-accelerated symmetric ciphers (AES-GCM) for wire-speed bulk encryption.

The Man-in-the-Middle (MITM) trap

In session 30, we saw that Diffie-Hellman allows you to securely negotiate an encrypted channel with a remote server. But there is a fatal catch: Diffie-Hellman cannot tell you who is on the other end of the wire.

If an attacker at a coffee shop intercepts your Wi-Fi, they can perform a Diffie-Hellman handshake with you (impersonating the server) and a separate Diffie-Hellman handshake with the real server. You are now encrypted—directly to the hacker! To prevent this, you need a mechanism to cryptographically authenticate identity: Public Key Infrastructure (PKI).RFC 5280: Internet X.509 Public Key Infrastructure Certificate and CRL Profile.

Digital signatures: The math of identity

Asymmetric keypairs have an inverted capability: authentication.

  1. The signer takes a message and computes its SHA-256 cryptographic hash.
  2. The signer encrypts the hash using their Private Key. This encrypted hash is a Digital Signature.
  3. Anyone in the world possessing the signer's Public Key can decrypt the signature and compare it with the message hash. If they match, it proves with mathematical certainty that:
    • The message was not modified by a single bit (Integrity).
    • The message was produced by the unique owner of that private key (Authenticity).

What is an X.509 certificate?

An X.509 Certificate is an electronic identity card binding a domain name to a public key, signed by a trusted third party called a Certificate Authority (CA).

The chain of trust

  1. Leaf (End-Entity) Certificate: Issued to a specific domain (e.g. google.com). Contains the server's public key and Subject Alternative Names (SANs).
  2. Intermediate CA: Root CAs never sign website certificates directly—doing so would risk catastrophic compromise. Instead, the Root CA signs an Intermediate CA, and the Root CA private key is locked inside an air-gapped hardware vault. The Intermediate CA signs the public website certificates.
  3. Root Certificate Authority (Trust Anchor): Who signs the root certificate? The Root CA signs itself! It is a self-signed certificate. Why does your computer trust it? Because Apple, Microsoft, Google, and Mozilla maintain audited Root Trust Stores embedded directly into operating systems and browsers.

Certificate revocation: CRL vs. OCSP Stapling

What happens if a server's private key is stolen before the certificate expires?

  • CRL (Certificate Revocation List): CAs published lists of revoked serial numbers. Browsers had to download massive multi-megabyte files, which was slow and unscalable.
  • OCSP (Online Certificate Status Protocol): The browser queries the CA's server in real time: "Is certificate #42 still valid?" Downside: Adds latency and leaks user browsing history to CAs!
  • OCSP Stapling (RFC 6066): The modern standard. The web server queries the CA periodically, gets a cryptographically signed, timestamped validity proof, and "staples" it directly to the TLS handshake! The browser gets proof of validity with zero extra latency and complete privacy.

Try it: walk a real certificate chain with OpenSSL

  1. Connect to Google's HTTPS port and dump the certificate chain: 
    $ openssl s_client -connect google.com:443 -showcerts
  2. Scroll to the top of the output and look at the Certificate chain: 
    Certificate chain
 0 s:CN = *.google.com
   i:C = US, O = Google Trust Services, CN = WR2
 1 s:C = US, O = Google Trust Services, CN = WR2
   i:C = US, O = Google Trust Services LLC, CN = GTS Root R1
  3. Notice how certificate 0 (Leaf) was issued by certificate 1 (Intermediate), which was issued by Root R1!

Free Recall Practice

From memory: explain how a browser verifies that a website certificate is authentic. What is OCSP Stapling?

Key points to compare against:

  • Verification: The browser uses the Intermediate CA's public key to verify the Leaf certificate's digital signature. It then uses the Root CA's public key to verify the Intermediate CA's signature. Finally, it confirms that the Root CA is pre-installed in the operating system's trusted root store.
  • OCSP Stapling: The web server queries the CA periodically for a signed revocation check and "staples" this proof into the TLS handshake, eliminating the need for client browsers to contact the CA.
