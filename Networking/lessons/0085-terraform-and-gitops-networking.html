Warm-up · from earlier sessions

Two minutes, from memory, before you read on:

A cloud engineer changes one line in a Terraform aws_vpc resource—the primary cidr_block—and merges blindly without reading terraform plan. Why can Terraform's plan turn a 1-line edit into a catastrophic total VPC deletion and rebuild?

Cloud APIs don't allow mutating a VPC's primary CIDR block in place. Terraform marks that attribute as ForceNew (-/+ destroy and then create replacement), which attempts to tear down subnets, NAT Gateways, ENIs, and live production workloads before recreating the VPC from scratch!

1 · Why Terraform Complements Ansible (State vs Stateless Push)

  • Terraform (Lifecycle IaC): Tracks a dependency graph + Remote State File (encrypted S3 + DynamoDB/state locking). Knows what used to exist so deleting a Security Group rule block in HCL actually deletes it in AWS/GCP/Azure!
  • Cloud Networking Modularity: Break VPCs, Transit Gateway attachments, firewall policies, and DNS zones into separate Blast-Radius state workspaces—never put your entire global TGW backbone + dev app buckets into one giant state file!
  • Remote State Locking: Prevents two engineers running terraform apply simultaneously and corrupting route tables mid-flight.

2 · Reading terraform plan Like a Senior NetEng

Before approving any networking Pull Request, check every plan symbol explicitly:

Plan SymbolMeaningNetEng Red-Flag Check
~ update in-placeMutates attribute without recreationSafe for adding SG descriptions/rules; check route precedence changes
+ createProvisions brand new resourceVerify IP CIDRs don't overlap hybrid VPN/Direct Connect!
-/+ destroy & replaceForceNew! Drops live traffic while rebuildingProtect critical IGW/TGW/VPCs with lifecycle { prevent_destroy = true }!
- destroyDeletes resource permanentlyNever allow unintended TGW attachment or NAT GW Elastic IP drops!

3 · Network CI Verification: Batfish & pyATS

Software teams run unit tests on PRs; Senior NetEng teams run static data-plane verification in CI:

  • Batfish (Pre-Change Static Analysis): Ingests vendor router configs offline, mathematically builds the exact FIB, BGP RIB, and ACL model, and answers CI assertions like "Does prod-db stay unreachable from dmz-web across all ECMP links?" or "Are any BGP sessions misconfigured?" before a single packet touches hardware!
  • Cisco pyATS / Genie (Post-Change Snapshot Diff): Captures structured live snapshots (interfaces, OSPF/BGP states, routing tables) before & after maintenance and fails the pipeline on any unintended dropped peer!

Hands-On GitOps Workflow Check

  1. Review a standard PR GitOps pipeline: Branch PR triggers terraform fmt -check → terraform validate → terraform plan posted as PR comment → Senior NetEng reviews zero unexpected -/+ destroys → Merge triggers terraform apply.
  2. Always protect core NAT Gateway Elastic IPs, Transit Gateways, and production VPCs with lifecycle { prevent_destroy = true } so Terraform refuses to execute accidental replacement plans.

// Model checking CIDR overlap before accepting a new Cloud Spoke VPC into a Transit Gateway
data class SpokeCidr(val name: String, val startIp: Long, val endIp: Long)
fun overlapsExisting(candidate: SpokeCidr, existing: List<SpokeCidr>): String? =
    existing.firstOrNull { candidate.startIp <= it.endIp && it.startIp <= candidate.endIp }?.name

Why should core Transit Gateways and production VPCs sit in separate Terraform state files from developer application buckets?

      
    
        
  1. Terraform restricts each state file to strictly 10 total cloud IP addresses.
    2. 
        
  2. Sharing a state file turns private RFC 1918 CIDRs into public internet BGP announcements.
    3. 
        
  3. Isolating state limits blast radius, speeds up plan execution, and enforces strict RBAC approval.
    4. 
        
  4. Cloud providers forbid Terraform from querying VPC attributes across multiple files.
    5. 
      

      
Blast-radius isolation + separate approval permissions prevent app deploys from touching core routing state.

    

    

      
What does Batfish let a Network Engineering team verify BEFORE pushing updated router configurations to production?

      
    
        
  1. Actual real-time optical RX light power dBm on physical QSFP28 fiber transceivers.
    2. 
        
  2. Mathematical reachability, BGP policy outcomes, and ACL isolation invariants across the modeled topology.
    3. 
        
  3. Automated TLS leaf-certificate issuance with public ACME certificate authorities.
    4. 
        
  4. Physical RJ-45 copper cable length limits beyond 100 meters.
    5. 
      

      
Batfish provides pre-deployment network unit testing; pyATS validates live post-deployment operational state.

    

    

      
Why is enabling remote state locking (e.g., S3 lockfile / DynamoDB) critical for a team running Terraform on shared network infrastructure?

      
    
        
  1. It prevents concurrent terraform applies from racing and corrupting shared routing state.
    2. 
        
  2. It encrypts BGP AS numbers using post-quantum key encapsulation on physical routers.
    3. 
        
  3. It disables DNS TTL caching globally across public internet recursive resolvers.
    4. 
        
  4. It converts Terraform HCL automatically into Containerlab Linux bridges.
    5. 
      

      
Remote state + locking guarantees serialized, conflict-free infrastructure updates across teams and CI runners.
