Warm-up · from earlier sessions

Two minutes, from memory, before you read on:

What controls flow control versus congestion control, and how is the maximum data in flight calculated?

Flow Control is governed by rwnd (advertised by the receiver to protect its memory buffer). Congestion Control is governed by cwnd (calculated by the sender to protect intermediate routers). Maximum data in flight is min(rwnd, cwnd).

The small packet problem (Tinygrams)

Every standard TCP segment carries a 20-byte IP header plus a 20-byte TCP header—40 bytes of overhead minimum.

In the early days of Telnet and terminal sessions, users typed one character at a time. A user typing a single key generated a 1-byte payload wrapped in 40 bytes of headers: 97.5% protocol overhead! If thousands of users did this across early ARPANET links, networks clogged with millions of tiny 41-byte packets (known as tinygrams).RFC 896: "Congestion Control in IP/TCP Internetworks" by John Nagle (1984).

Nagle's algorithm: The solution to tinygrams

In 1984, engineer John Nagle proposed an elegant solution:

Nagle's Rule: If an application writes data smaller than a full packet (MSS ≈ 1,460 bytes):

  • If there is no unacknowledged data in flight, send the packet immediately.
  • If there is unacknowledged data in flight, do NOT send! Hold the bytes in a local buffer until either:
    1. An ACK arrives for the previous data, OR
    2. Enough new data accumulates to fill a full MSS packet.

Nagle's algorithm automatically coalesces tiny writes into efficient, full-sized packets without requiring application developers to manually buffer keystrokes. It was so effective that it was built into every OS kernel in the world and enabled by default.

Delayed ACKs: The second optimization

A few years later, RFC 1122 introduced another optimization: Delayed ACKs.RFC 1122 §4.2.3.2: Delayed Acknowledgments.

Sending a standalone 40-byte TCP segment purely to say "ACK" wastes bandwidth. RFC 1122 stated: when a packet arrives, the receiver should wait up to 200 milliseconds (or until a second packet arrives) before sending the ACK. The hope is that the server's application will generate a response, allowing the ACK to be "piggybacked" for free onto the outgoing data packet!

The disaster: When Nagle meets Delayed ACKs

Independently, both algorithms are brilliant. Together, they create a catastrophic deadlock:

Consider an application that writes an HTTP request in two consecutive calls: write(headers) followed by write(body):

  1. The client sends the headers (small packet #1).
  2. The client immediately calls write(body). But because packet #1 is unacknowledged, Nagle buffers the body!
  3. The server receives the headers. It needs the body to respond, so it has no response to send. Because only one packet arrived, Delayed ACK pauses for 200 ms before sending an acknowledgment.
  4. DEADLOCK: The client is waiting for the server's ACK. The server is waiting for the client's body. Neither side moves until the receiver's 200 ms timer forcibly fires!

The solution: TCP_NODELAY

To kill this deadlock, every high-performance web framework, database driver, and reverse proxy (Nginx, Netty, Redis, gRPC, Node.js) explicitly sets the socket option TCP_NODELAY:

// Java / Kotlin: Disable Nagle's algorithm!
socket.setTcpNoDelay(true);

Setting TCP_NODELAY = true disables Nagle's algorithm completely. Packets are transmitted into the network the instant your application calls write(), dropping latency from 200 ms to sub-millisecond.

Head-of-Line (HoL) blocking: TCP's fatal flaw

Even with TCP_NODELAY enabled, TCP has one insurmountable architectural limitation: it enforces a strictly linear byte stream.

In modern web browsers, HTTP/2 multiplexes 50 different images, scripts, and API requests across a single shared TCP connection. But to TCP, those 50 streams look like one single unbroken sequence of bytes. If a single packet carrying part of Image #1 is dropped by Wi-Fi interference:

  • The receiving OS kernel halts delivery to the browser.
  • Images #2 through #50 are already sitting in memory, perfectly intact, but the OS refuses to deliver them because byte order must be strictly preserved!
  • Everything freezes until the missing packet for Image #1 is retransmitted.

This is Transport-Layer Head-of-Line Blocking. It cannot be fixed within TCP. Eliminating this problem required the industry to build QUIC and HTTP/3 on top of UDP (session 28)!

Free Recall Practice

From memory: explain the collision between Nagle's algorithm and Delayed ACKs. What is Head-of-Line blocking, and why can't TCP fix it?

Key points to compare against:

  • Nagle + Delayed ACK: Nagle holds small outgoing writes if prior data is unacknowledged. Delayed ACK holds incoming acknowledgments up to 200 ms unless a second packet or response arrives. When an app sends two small consecutive writes (like HTTP headers and body), Nagle waits for the ACK while the receiver waits for the next packet, creating an artificial 200 ms stall. Fixed with TCP_NODELAY.
  • Head-of-Line Blocking: TCP guarantees an ordered byte stream. If a single packet is dropped, all subsequent packets must wait in OS memory buffers and cannot be delivered to user-space applications until the lost bytes are retransmitted—even if those subsequent packets belong to completely independent HTTP/2 streams.
