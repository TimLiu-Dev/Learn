Explain the multi-tier VPC subnet pattern (Public, Private App, Isolated DB) and why AWS reserves 5 IP addresses in every subnet.

Key points to compare against:

  • Multi-tier pattern: Public subnets route `0.0.0.0/0` directly to an Internet Gateway (IGW) and host public load balancers and NAT Gateways. Private App subnets route `0.0.0.0/0` to a NAT Gateway, allowing outbound updates while blocking unsolicited inbound connections. Isolated DB subnets have zero egress route to the Internet, ensuring database data cannot leak outside the VPC.
  • The 5 reserved IPs: AWS reserves the first 4 IPs and the last IP in every subnet: offset .0 (Network address), .1 (VPC Router/Default Gateway), .2 (VPC Amazon Route 53 DNS), .3 (AWS future use), and .255 (Broadcast address). Usable host IPs equal total subnet capacity minus 5.

Why does VPC Peering become unmanageable as an enterprise scales to 50 VPCs, and how does AWS Transit Gateway solve this? What is AWS PrivateLink?

Key points to compare against:

  • VPC Peering scaling limits: VPC Peering is non-transitive; traffic cannot hop through an intermediate VPC. Connecting N VPCs requires an N(N − 1) / 2 full mesh (1,225 connections for 50 VPCs), resulting in unmanageable route table bloat. Transit Gateway operates as a centralized hub-and-spoke Layer 3 cloud router supporting up to 5,000 VPCs with native transitive routing and isolated routing domains.
  • AWS PrivateLink: Deploys a private IP Elastic Network Interface (ENI) directly into your private subnet to consume AWS services or third-party SaaS (Snowflake, Datadog) over AWS's private fabric. It bypasses NAT Gateways and functions seamlessly even when VPC CIDRs overlap.

Why is a Kubernetes ClusterIP called a "ghost IP"? How does eBPF (Cilium) eliminate kube-proxy and accelerate pod networking?

Key points to compare against:

  • The Ghost IP mystery: A ClusterIP does not exist on any physical or virtual network interface on any node in the cluster; it cannot respond to an ICMP ping. kube-proxy programs in-kernel Netfilter/iptables rules to intercept packets targeting the virtual IP and rewrite them via Destination NAT (DNAT) to a healthy Pod IP.
  • eBPF / Cilium acceleration: Cilium replaces O(N) sequential iptables rules with O(1) in-kernel eBPF hash tables, eliminating CPU locks in large clusters. Furthermore, Cilium uses socket-level short-circuiting (`sock_ops`) to pass data directly between local Pod socket buffers, bypassing veth pairs and the TCP/IP stack entirely.

Diagnose these three complex cloud production incidents like a Staff Infrastructure Engineer:


  

    
Scenario A: The Silent Outbound Blackout (The Ephemeral Port Trap)

    
Incident: Following a SOC2 security audit, an infrastructure engineer locked down the subnet Network ACL (NACL) on a private microservices subnet. The engineer configured Inbound Rule 100: Allow TCP 443 from 0.0.0.0/0 and Outbound Rule 100: Allow TCP 443 to 0.0.0.0/0. Immediately, all backend instances lost the ability to call external third-party payment APIs, query GitHub, or run apt update.

    
Root Cause Analysis: Outbound requests sent to external servers on destination port 443 originate from dynamic client ephemeral ports (32768–60999 or 1024–65535). Because Network ACLs are 100% stateless, the return packets arrive with the ephemeral port as the destination. The NACL inbound table lacked an allow rule for ephemeral ports, silently dropping all return packets.

    
Architectural Remediation: Add an explicit Inbound Rule to the subnet NACL: Allow TCP 1024–65535 from 0.0.0.0/0.

  


  

    
Scenario B: The \$40,000 Runaway NAT Gateway Bill

    
Incident: A machine learning platform runs hundreds of distributed training jobs across an Amazon EKS cluster in a private VPC. At the end of the month, the cloud bill contains a shocking \$42,500 line item for "AWS Managed NAT Gateway - Data Processed."

    
Root Cause Analysis: Worker nodes in the private subnets were streaming 100 Terabytes of training datasets and model checkpoints from an Amazon S3 bucket. Because the private subnet route tables only contained a default route (0.0.0.0/0 -> nat-gateway), all S3 traffic was routed through the Managed NAT Gateway at $0.045 per Gigabyte!

    
Architectural Remediation: Provision a Gateway VPC Endpoint for Amazon S3 and attach it to the private subnet route tables. Gateway Endpoints for S3 are 100% free and inject a prefix-list route that steers S3 traffic directly over the internal AWS fabric, instantly eliminating the entire NAT processing fee.

  


  

    
Scenario C: The 100% CPU iptables Freeze in Kubernetes

    
Incident: An enterprise e-commerce Kubernetes cluster scales to 4,000 microservices and 35,000 Pods ahead of Black Friday. During a rolling deployment, cluster nodes begin reporting NotReady. Worker node CPU utilization spikes to 100%, and application inter-pod latency jumps from 2 ms to 1,500 ms.

    
Root Cause Analysis: The cluster was running default kube-proxy in iptables mode. With 4,000 services, the Linux kernel was evaluating over 80,000 sequential iptables rules per packet (O(N) traversal). Frequent pod churn during the deployment forced kube-proxy to repeatedly acquire global kernel table locks to rewrite the ruleset, causing CPU thrashing and packet queue drops.

    
Architectural Remediation: (1) In the short term, migrate kube-proxy from iptables mode to IPVS mode, which uses in-kernel hash tables (O(1) lookup time). (2) In the long term, migrate the cluster CNI to Cilium (eBPF), completely removing kube-proxy and iptables from the data path and leveraging socket-level short-circuiting.
