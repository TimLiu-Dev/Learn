The fallacies of distributed computing

In 1994, Sun Microsystems engineer L. Peter Deutsch outlined the Fallacies of Distributed Computing: false assumptions made by developers writing network software.Deutsch, Gosling et al.: "The Fallacies of Distributed Computing Explained".

The top three fallacies that take down production systems:

  1. "The network is reliable." (Routers reboot, Wi-Fi drops, cables are cut).
  2. "Latency is zero." (Physics imposes an inescapable speed-of-light tax).
  3. "Bandwidth is infinite." (Buffers fill, queues drop packets).

The two timeouts you must always configure

Default HTTP clients in many languages (including early Java and Python) have **no timeouts** by default. If a remote server hangs, your application threads freeze indefinitely, accumulating until your entire web server runs out of memory and crashes!

Timeout NameWhat it measuresRecommended ValueWhat fails if unset
Connect TimeoutTime to complete the TCP 3-way handshake and TLS setup.1 to 2 secondsIf an upstream server is partitioned or dropped into a black hole, client threads hang for minutes waiting for kernel SYN retries!
Read (Socket) TimeoutMaximum time allowed between incoming data bytes once connected.3 to 5 secondsIf a downstream database query hangs or locks, client threads freeze forever waiting for response bytes.

Connection pooling

Establishing a fresh TCP connection plus TLS 1.3 handshake burns multiple round trips and CPU cryptography cycles. A Connection Pool (such as OkHttp, Apache HttpClient, or HikariCP) keeps a warm pool of established, pre-authenticated sockets ready for instant reuse.

  • Sizing the Pool: Sized to handle concurrent request bursts without creating thousands of idle connections.
  • Evicting Stale Connections: Firewalls and NAT gateways silently drop idle connections after a timeout without sending a FIN packet. Client pools must periodically validate sockets with TCP keep-alives or maximum idle time limits to prevent writing to "dead" sockets.

Retries & the thundering herd problem

When an API call fails with a network glitch, the natural impulse is to retry. But naive immediate retries are lethal.

If an overloaded database hiccups for two seconds, causing 5,000 client queries to fail, and all 5,000 clients retry immediately at the exact same millisecond, they deliver a coordinated sledgehammer that obliterates the database just as it begins to recover! This is the Thundering Herd Problem (Retry Storm).

The Fix: Exponential Backoff with Jitter:

  • Exponential Backoff: Double the wait time on each attempt: t, 2t, 4t, 8t…
  • Full Jitter: Add random noise: sleep = random(0, backoff). This completely breaks up the synchronization of retrying clients!AWS Architecture Blog: Exponential Backoff And Jitter by Marc Brooker.

The circuit breaker pattern

When an upstream service is completely dead, repeatedly retrying burns client threads and server resources. The Circuit Breaker (popularized by Netflix Hystrix and Resilience4j) operates in three states:Michael Nygard: Release It! Design and Deploy Production-Ready Software (O'Reilly).

StateBehaviorTransition
Closed (Normal)Requests flow through to the network normally.If error rate exceeds threshold (e.g. 50% failures over 10s), trips Open!
Open (Failing Fast)All calls fail immediately in memory without touching the network! Returns fallback data instantly.After a sleep window (e.g. 30 seconds), transitions to Half-Open.
Half-Open (Trial)Allows a small sample of trial requests through to the server.If trials succeed, resets to Closed. If trials fail, trips back to Open.

From memory: explain the difference between Connect Timeout and Socket Read Timeout. What is a Circuit Breaker and why is it vital in microservice architectures?

Key points to compare against:

  • Connect vs Read Timeout: Connect Timeout bounds the time required to complete the TCP 3-way handshake and TLS setup (protects against network partitioning / routing drops). Read (Socket) Timeout bounds the time waiting for response bytes once connected (protects against hanging server processes).
  • Circuit Breaker: A stability pattern that monitors failure rates. When errors exceed a threshold, it trips to an "Open" state, failing subsequent calls fast in local memory without attempting network calls. This shields failing dependencies from overload and prevents client thread pool exhaustion.
