How your Mac gets an address before it has one

DHCP: four messages, one lease, and a tell-tale 169.254

~25 minutesTools: ipconfig, Wireshark★ interview
Your win today

You'll watch your Mac ask the network for its configuration, name each DHCP message you capture and what it carries, and read the lease your Mac is living on right now.

Warm-up · from earlier sessions

What is the Ethernet broadcast address, and what does a switch do with a frame sent to it?

ff:ff:ff:ff:ff:ff. A switch floods it out of every port except the one it arrived on, so every device on the LAN receives it. (Session 4.) DHCP depends on exactly this.

Your Mac wants to send a packet to some IP address. How does it decide whether to deliver it directly or hand it to the gateway?

It ANDs the destination with its own subnet mask and compares the result with its own network address. Same network: deliver directly. Different: send it to the default gateway. (Session 6.) So it needs to know its own address, its mask, and the gateway first.

Why this matters

"Connected to Wi-Fi, but nothing works" is a complaint every engineer hears, and DHCP is one of the first things to check.

Before your laptop can send a single useful packet, it needs four facts: its own IP address, the subnet mask, the default gateway, and a DNS server. Without the mask and gateway it can't make the decision from the warm-up; without DNS, it can't turn names into addresses. Nobody types these in anymore. Laptops, phones and cloud VMs get them automatically, usually from DHCP. "What happens when you join a network?" is the first chapter of the classic interview question about typing a URL. And once you can read a lease, one glance at an address like 169.254.x.x tells you where to start debugging.

Talking without an address

The Dynamic Host Configuration Protocol (DHCP) hands out those four facts. A DHCP server (on a home network, built into your router) owns a pool of addresses; a DHCP client (your Mac) borrows one.Why manual configuration doesn't scale, and the pool model: Systems Approach §3.3.7; Kurose & Ross §4.3 ("Obtaining a Host Address").

There's a chicken-and-egg problem: how do you send a packet when you have no IP address and don't know the server's? You shout. The client sends a UDP datagram from source IP 0.0.0.0 ("I have no address") to 255.255.255.255 (everyone on this network), inside a frame to ff:ff:ff:ff:ff:ff. Clients send to UDP port 67 (the server port) from port 68 (the client port).Ports 67/68, source address 0, and the broadcast rules: RFC 2131 §4.1. Because routers don't forward broadcasts, this only reaches the local network. Larger networks put a relay agent on each subnet that passes DHCP messages to a central server.

Discover, Offer, Request, Ack

A client joining a network for the first time exchanges four messages. Memorise the order; the acronym DORA helps.The full exchange and its timeline figure: RFC 2131 §3.1.

  • Discover: the client broadcasts "is there a DHCP server?"
  • Offer: each server that hears it may offer an address (in a field called yiaddr, "your IP address") plus configuration.
  • Request: the client picks one offer and asks for it. This is broadcast too, so any other server that made an offer learns it was declined.
  • Ack: the chosen server commits and confirms. Only now may the client use the address. (A server that can't honour the request sends a Nak instead, and the client starts over.)

Before using the address, the client should check nobody else already has it, for example by ARPing for it (session 7).RFC 2131 §3.1, step 5. If someone answers, the client sends a Decline and starts over.

What the Ack carries

The configuration rides in options: numbered, tagged fields after the fixed header.Option codes are defined in RFC 2132. The names in the first column are how macOS's ipconfig prints them. The ones that matter today:

Leases, and why you rarely see all four

Addresses are lent, not given. A lease lasts the number of seconds in lease_time; a client that disappears without saying goodbye eventually frees its address for someone else. Two timers manage renewal:States and default timers: RFC 2131 §4.4.5. Servers may send their own T1/T2 (options 58 and 59), and the RFC recommends adding some random "fuzz" so clients don't all renew at once.

  • At T1 (default: half the lease), the client enters the RENEWING state and unicasts a Request straight to the server that gave it the address. Usually an Ack comes back and the clock restarts.
  • If that fails, at T2 (default: 87.5% of the lease) it enters REBINDING and broadcasts the Request to any server.
  • If the lease expires anyway, the client must stop using the address and start again from Discover.

A client that remembers an address from before (after waking from sleep, or rejoining a network) also skips ahead. It starts in the INIT-REBOOT state and broadcasts a Request asking for its old address. The server replies Ack ("still yours") or Nak ("not on this network").RFC 2131 §3.2 and §4.4.2. So in a real capture you'll often see only Request and Ack. You can tell which state sent a Request by three fields (RFC 2131 §4.3.2):

Request sent in…ciaddr (client IP field)Option 50, Requested IPSent to

The first two look alike; the giveaway is whether a Discover and Offer came just before. (A Selecting Request also names the chosen server in option 54; an INIT-REBOOT Request must not.)

The 169.254 clue

What if nobody answers? macOS gives up and assigns itself a link-local address in 169.254.0.0/16, often labelled "self-assigned".The 169.254/16 range and how hosts pick an address in it: RFC 3927. macOS's behaviour: man ipconfig, "It may also allocate and assign a link-local IP address if DHCP fails." It can reach other devices on the same link, but there's no gateway and no DNS, so nothing beyond the LAN works. If you see a 169.254 address, stop suspecting DNS or the remote server: the problem is between the machine and the DHCP server (Wi-Fi association, the cable, the router's DHCP service, or a full address pool).

Try it: read your lease, then watch a renewal

ipconfig getpacket en0 prints the last DHCP message your Mac accepted from the server. Its format looks like this (values replaced with xx):

op = BOOTREPLY
…
ciaddr = xx.xx.xx.xx
yiaddr = xx.xx.xx.xx
siaddr = xx.xx.xx.xx
giaddr = xx.xx.xx.xx
chaddr = xx:xx:xx:xx:xx:xx
…
options:
dhcp_message_type (uint8): ACK 0x5
server_identifier (ip): xx.xx.xx.xx
lease_time (uint32): 0x…
renewal_t1_time_value (uint32): 0x…
…
router (ip_mult): {xx.xx.xx.xx}
domain_name_server (ip_mult): {xx.xx.xx.xx}
end (none):

Times are printed in hex. Convert one in the shell with echo $((0x…)), pasting the hex value in place of 0x…. (The header still says BOOTREPLY: DHCP was built on an older protocol called BOOTP and reuses its packet format.)

  1. Read your current lease: ipconfig getpacket en0. Convert lease_time, renewal_t1_time_value and rebinding_t2_time_value to seconds, then to hours.
  2. For a quick look at single options in decimal, try ipconfig getoption en0 lease_time, ipconfig getoption en0 subnet_mask and ipconfig getoption en0 router.
  3. Open Wireshark, start capturing on Wi-Fi (en0), and type dhcp in the display filter bar.The filter is dhcp in Wireshark 3.0 and later; older guides use bootp, which no longer works. Wireshark display filter reference: DHCP.
  4. Renew your lease: Apple menu → System Settings → Network → Wi-Fi → Details… → TCP/IP → Renew DHCP Lease, then OK.Path from Apple's Mac User Guide: Renew your IP address from the DHCP server. The Terminal equivalent is sudo ipconfig set en0 DHCP; man ipconfig notes it creates a temporary service that lasts only until the next network configuration change. Your connection may blip for a second.
  5. Stop the capture once you see packets. Change the filter to dhcp || arp to see what your Mac did right after.
  6. Click each DHCP packet and expand Dynamic Host Configuration Protocol. Find the message type option, Client IP address (ciaddr), Your (client) IP address (yiaddr), and any Requested IP Address option. Also note the IP and UDP headers above it.
  7. Optional: to see all four messages, capture while joining a network your Mac has never used, such as a phone's hotspot.

Then answer these. Bring your answers to chat rather than looking them up:

  • Which DHCP message types did you capture, and in what order? If you didn't get a Discover and Offer, use the ciaddr / option 50 / destination table above: which state was your Mac in when it sent its Request?
  • For each message, what were the source and destination IP addresses and UDP ports? Which of them are broadcasts, and why must they be?
  • Your lease's T1 and T2 as fractions of the lease time: does your router use the RFC defaults (0.5 and 0.875), or something else?
  • Did any ARP packets from your Mac appear right after the Ack? Which address were they about, and why would a freshly configured host send them?

Check yourself

Answer from memory first. Scroll up only after you've committed to an answer.

A client's first DHCP message has source IP 0.0.0.0 and destination 255.255.255.255. Why?

  1. routers block unicast until the client logs in
  2. it lacks an address and cannot locate servers
  3. broadcast is always faster than unicast on Wi-Fi
  4. DHCP servers listen only on the broadcast address
With no address of its own, the client uses 0.0.0.0 as its source; not knowing where any server is, it broadcasts to everyone on the local network. Servers also receive unicast: that's how renewals reach them.

Which transport and ports does DHCP use?

  1. TCP, server 67, client 68
  2. UDP, server 68, client 67
  3. TCP, server 53, client 53
  4. UDP, server 67, client 68
UDP: a client with no address can't hold a TCP connection, and every DHCP exchange is a single request and reply anyway. Servers listen on 67, clients on 68. Port 53 is DNS.

A laptop joins a network it has never used before. In what order are the DHCP messages sent?

  1. Discover, Offer, Request, Ack
  2. Request, Offer, Discover, Ack
  3. Discover, Request, Offer, Ack
  4. Offer, Discover, Ack, Request
DORA. The client discovers servers, a server offers an address, the client requests that offer, and the server acknowledges it.

A friend's Mac shows Wi-Fi connected, but ifconfig en0 shows inet 169.254.37.12. What is the most likely cause?

  1. the DNS server is not responding
  2. the website they want is down
  3. no DHCP server answered the Mac
  4. the default gateway's ARP entry expired
169.254.0.0/16 is the self-assigned link-local range a host falls back to when DHCP gets no answer. With no gateway or DNS configured, DNS and remote websites never even get a chance to fail.

A server grants an 8-hour lease and sends no T1 option. When does the client first try to renew?

  1. after 2 hours
  2. after 4 hours
  3. after 7 hours
  4. after 8 hours
T1 defaults to half the lease: 4 hours, a unicast Request to the same server. 7 hours is T2 (87.5%), when it starts broadcasting to any server; 8 hours is expiry.

You rejoin your home Wi-Fi and capture only a Request and an Ack. Why no Discover or Offer?

  1. Wi-Fi captures never show any broadcast frames
  2. home routers skip both steps for speed
  3. Discover and Offer travel over TCP instead
  4. the Mac requested its previous address again
A client that remembers its previous address starts in INIT-REBOOT and broadcasts a Request for it directly. The server only has to confirm with an Ack (or refuse with a Nak).
