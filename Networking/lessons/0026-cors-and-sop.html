How do HttpOnly and SameSite cookie attributes protect web applications?

HttpOnly prevents client-side JavaScript from reading cookies (mitigating XSS token theft). SameSite controls whether cookies are attached on cross-site requests (mitigating CSRF forgery).

The Same-Origin Policy (SOP)

The foundation of all browser security is the Same-Origin Policy (SOP). An Origin is strictly defined by three components:MDN: Same-Origin Policy and RFC 6454 (The Web Origin Concept).

Origin = Protocol (Scheme) + Host (Domain) + Port

If any one of these three parts differs, two URLs have different origins:

Comparing against: https://example.com:443OutcomeReason
https://example.com/account/settingsSame OriginSame scheme, host, and port. Path does not matter.
http://example.comCross-OriginDifferent scheme (HTTP vs HTTPS).
https://api.example.comCross-OriginDifferent host (subdomain differs).
https://example.com:8080Cross-OriginDifferent port (8080 vs 443).

Why does SOP exist? Imagine you are logged into your bank at https://mybank.com. In another browser tab, you visit a malicious site at https://evil.com. Without the Same-Origin Policy, JavaScript on evil.com could run:

fetch('https://mybank.com/api/transfers', { method: 'GET' })
  .then(res => res.json())
  .then(data => sendToHacker(data));

Because browsers automatically attach stored cookies, the bank server would authenticate the request! The Same-Origin Policy strictly forbids JavaScript running on evil.com from reading responses returned by mybank.com.

What is CORS?

Cross-Origin Resource Sharing (CORS) is the mechanism that allows a server to explicitly relax SOP and declare: "I give permission for scripts running on https://myfrontend.com to read my API responses."W3C / WHATWG Fetch Standard: CORS.

The #1 Fact to Know About CORS

CORS is enforced exclusively by the BROWSER. The server is not blocking your request!

When a CORS error occurs, your server actually received the request, executed the database query, and returned a 200 OK! It is your local browser that intercepts the response, checks for CORS headers, and hides the data from JavaScript. This is why curl, Postman, and backend servers never experience CORS errors.

Simple vs. preflighted requests

Browsers divide cross-origin requests into two categories:

1. Simple Requests (No Preflight)

If a request uses standard methods (GET, POST, HEAD) with default headers and simple content types (e.g. application/x-www-form-urlencoded), the browser sends it immediately. The server replies with:

Access-Control-Allow-Origin: https://myfrontend.com

2. Preflighted Requests (The OPTIONS Call)

If a request sends JSON (Content-Type: application/json), uses non-standard methods (PUT, DELETE), or includes custom headers (e.g. Authorization: Bearer token), the browser considers it potentially hazardous. It sends a preflight OPTIONS request first:

From memory: why does curl never fail with a CORS error? What three components define an Origin?

Key points to compare against:

  • Why curl never fails with CORS: CORS and the Same-Origin Policy are client-side security policies enforced exclusively by web browsers. The server executes requests normally. Command-line tools like curl and backend servers have no browser sandbox, so they never enforce or block on CORS headers.
  • Origin components: Protocol/Scheme (e.g. https), Host/Domain (e.g. example.com), and Port number (e.g. 443).
