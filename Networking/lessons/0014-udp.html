The philosophy of minimalism

The User Datagram Protocol (UDP), defined in RFC 768 in 1980, is the thinnest possible transport protocol. Its entire specification fits on less than three pages.RFC 768: "This protocol provides a procedure for application programs to send messages to other programs with a minimum of protocol mechanism."

UDP does only two things beyond raw IP:

  1. Process multiplexing: It adds Source Port and Destination Port so data reaches the right program.
  2. Bit error detection: It adds an optional 16-bit checksum covering the header and data.

Everything else is stripped away. There is no connection setup, no 3-way handshake, no acknowledgments, no sequence numbers, no retransmissions, and no congestion control. You fire a packet into the network; whether it arrives in 10 ms, arrives duplicated, arrives out of order, or gets dropped by an overloaded router is completely up to chance.

The 8-byte UDP header

Because it offers no bookkeeping, UDP's header is tiny: exactly 8 bytes (64 bits). Compare this to TCP's header, which starts at 20 bytes and frequently spans 32 to 60 bytes with options!

Message-oriented vs. Stream-oriented

A critical architectural difference between UDP and TCP is how they treat application boundaries:

  • UDP is Message-Oriented (Datagrams): If your program writes 500 bytes into a UDP socket, the receiver gets a discrete packet containing exactly those 500 bytes on a single read() call. Message boundaries are strictly preserved by the protocol.
  • TCP is Stream-Oriented (Continuous Bytes): TCP sees data as an unbroken river of bytes. If you write 500 bytes twice, the receiver might read 1,000 bytes in one chunk, or 200 bytes across five chunks. You have to invent your own framing protocol (session 19).

Why would anyone choose an "unreliable" protocol?

Why do Discord, Zoom, DNS, and modern HTTP/3 choose UDP? Because in networking, reliability costs latency.

The Three Dominant Use Cases for UDP
  1. Real-Time Audio, Video, and Gaming: In a live phone call, if an audio packet containing 20 milliseconds of speech is dropped, waiting 150 ms for TCP to detect the loss and retransmit it is useless—by the time the retransmitted packet arrives, the conversation has moved on. Playing stale audio causes jarring lag. It is far better to drop the frame and let the human brain interpolate the silence!
  2. Simple Request-Response Transactions: When looking up an IP address via DNS, the query fits in one packet and the answer fits in one packet. Opening a full TCP connection requires a 3-way handshake (1 full RTT) before sending the question. UDP sends the question immediately in packet #1 (0-RTT). If no answer arrives in 1 second, the client simply asks again.
  3. Custom User-Space Protocols (QUIC / HTTP/3): Operating system kernels update slowly. By running on top of UDP datagrams, modern protocols like Google's QUIC implement custom encryption, packet recovery, and multiplexing entirely in application space, eliminating Head-of-Line blocking (session 28).

Try it: speaking UDP with Netcat and Java

Let's spin up a UDP listener and send datagrams directly using Terminal tools.

  1. Open two Terminal windows side by side.
  2. In Terminal 1, start a UDP listener on port 9099: 
    $ nc -u -l 9099
    -u specifies UDP mode; -l puts Netcat in listening mode.
  3. In Terminal 2, send datagrams to that port: 
    $ nc -u 127.0.0.1 9099
  4. Type "Hello UDP" in Terminal 2 and press Return. Notice it appears instantly in Terminal 1!
  5. Now, kill Terminal 1 with Ctrl+C. Notice that Terminal 2 does not notice when the server dies (no TCP FIN packet arrives!). When you type one more line, your Mac's kernel sees no listener on port 9099 and replies with an ICMP Port Unreachable message—which a "connected" UDP tool like nc -u surfaces on the subsequent write, whereas an unconnected DatagramSocket.send() in Java silently drops into the void forever!

UDP in Code: Single-file Java Datagram

In modern Java (JDK 21+), sending a UDP packet takes only four lines using DatagramSocket:

import java.net.*;

public class UdpSend {
    public static void main(String[] args) throws Exception {
        try (var socket = new DatagramSocket()) {
            byte[] data = "Ping from Java".getBytes();
            var packet = new DatagramPacket(data, data.length, 
                InetAddress.getByName("127.0.0.1"), 9099);
            socket.send(packet);
            System.out.println("Datagram sent!");
        }
    }
}

Free Recall Practice

From memory: state the four fields of the UDP header. Why does live voice/video streaming prefer UDP over TCP?

Key points to compare against:

  • The four UDP header fields: Source Port (16 bits), Destination Port (16 bits), Length (16 bits), and Checksum (16 bits). Total = 8 bytes.
  • Why real-time streaming prefers UDP: TCP guarantees delivery by pausing the stream and retransmitting lost packets. In live video/audio, delayed packets are useless—a 200 ms retransmission causes noticeable audio stutter or video freeze. UDP skips retransmissions, maintaining low latency and real-time responsiveness.
