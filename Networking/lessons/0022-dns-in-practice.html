What is the difference between a recursive resolver and an authoritative nameserver?

A recursive resolver (e.g. 1.1.1.1) traverses the global DNS tree on behalf of clients and caches results. An authoritative nameserver (e.g. Route 53) holds the official, configured DNS records for a domain.

The core record types

Every entry in a DNS database is stored as a Resource Record (RR). The six records every developer and system engineer meets weekly are:RFC 1035 §3.2.2: TYPE values for Resource Records.

The zone apex trap (Why CNAME can't sit on the root)

A classic production blunder is attempting to add a CNAME record to a naked root domain (the zone apex, such as example.com rather than www.example.com).

The RFC 1912 Rule

RFC 1912 §2.4: "If a CNAME record is present at a node, no other data should be present."

A zone apex (example.com) must have an SOA record and NS records to exist. Because a CNAME forbids any other record on the same name, placing a CNAME on the apex destroys the zone and breaks email (MX) and DNS resolution!

The Modern Fix: Cloud providers (Cloudflare, AWS Route 53) invented non-standard virtual records: ALIAS or ANAME. To the user it behaves like a CNAME, but the nameserver internally resolves the target IP and serves it as an ordinary A record to clients!

Time-to-Live (TTL) & the migration dilemma

Every DNS record carries a TTL (Time-to-Live), expressed in seconds. It tells resolvers: "You may safely cache this answer for N seconds before asking me again."

  • Long TTL (e.g. 86400s = 24 hours): Maximizes browser caching, minimizes query latency, and shields your authoritative nameservers from millions of queries. Downside: If you change your server's IP address, users with cached records will continue hitting the old (or dead) server for up to 24 hours!
  • Short TTL (e.g. 60s): Allows rapid IP failover and zero-downtime database migrations. Downside: Clients must resolve DNS more frequently, adding 20–80 ms of latency before cold requests.

Best Practice for IP Migration: One week before a migration, lower your TTL from 24 hours to 300 seconds (5 minutes). Once all global caches have absorbed the short TTL, switch the IP. After confirming stability, raise the TTL back to 24 hours.

Try it: query records and flush cache with dig

  1. Query the IPv4 address (A record) of Google: 
    $ dig google.com A +noall +answer
    +noall +answer strips verbose DNS boilerplate, showing only the answers and their TTL countdown.
  2. Query the IPv6 address (AAAA record) of Google: 
    $ dig google.com AAAA +noall +answer
  3. Query the TXT records of GitHub to see domain verification tokens: 
    $ dig github.com TXT +noall +answer
  4. Flush your local macOS DNS cache if you suspect stale records: 
    $ sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder

Free Recall Practice

From memory: explain why a standard CNAME record cannot be placed at the apex of a domain (e.g. example.com). How do cloud providers solve this?

Key points to compare against:

  • Why CNAME cannot sit at apex: RFC 1912 mandates that if a CNAME exists for a name, no other record types can exist for that same name. But a zone apex requires SOA and NS records to function. Placing a CNAME on the apex would eliminate the SOA/NS records, invalidating the zone.
  • The Cloud Fix: Cloud DNS providers created virtual ALIAS or ANAME records. The user enters an alias, but the provider's authoritative nameserver queries the alias internally and emits a standard synthetic A record to the public internet.
