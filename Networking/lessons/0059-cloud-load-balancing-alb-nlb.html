What does a reverse proxy do when handling client connections?

A reverse proxy terminates the client's TCP/TLS connection on its own front interface, inspects the request, and opens a separate backend TCP connection to forward the request to an internal server.

Distributing load at cloud scale

A single web server can only handle a few thousand concurrent requests before memory and CPU limits are reached. To scale to millions of users, applications deploy fleets of stateless servers behind a load balancer.AWS Elastic Load Balancing Documentation: What is Elastic Load Balancing?

In modern cloud architectures, load balancers split into two primary paradigms: Layer 7 (Application Load Balancers) and Layer 4 (Network Load Balancers).

Deep Dive: Application Load Balancer (ALB)

An ALB is a full Layer 7 reverse proxy. Because it terminates the client connection and buffers the HTTP request, it can execute rich routing decisions:

  • Path-Based Routing: Send requests matching /api/* to a Go microservice target group, and requests matching /static/* to an S3 bucket or Node.js cluster.
  • Host-Based Routing: Route orders.company.com and billing.company.com to completely separate backend container fleets sharing a single ALB.
  • The Client IP Caveat: Because the ALB initiates a new TCP connection from its own private IP to the backend instance, the backend's TCP stack sees the ALB's private IP as the source! To preserve client identity, the ALB injects the X-Forwarded-For: <client-ip> and X-Forwarded-Proto: https headers.

Deep Dive: Network Load Balancer (NLB)

An NLB operates at Layer 4, forwarding raw packets using AWS Hyperplane (the same distributed SDN engine that powers NAT Gateways and PrivateLink):

  • Extreme Performance: Scales to handle massive traffic spikes (like Super Bowl streaming or flash sales) instantly without pre-warming.
  • Static IP Whitelisting: Unlike an ALB (which provides only a DNS CNAME that resolves to rotating IPs), an NLB provides a guaranteed static Elastic IP for each Availability Zone. This is mandatory when corporate B2B clients require firewall IP whitelisting.
  • Native Client IP Preservation: For target groups registered by instance ID, the NLB does not rewrite the source IP header; packets arrive at the backend server carrying the real external client IP address!

Health Checks & Connection Draining

A load balancer is only as reliable as its Target Health Checks:

  • The load balancer periodically polls a health endpoint on each backend instance (e.g. GET /healthz every 10 seconds).
  • If an instance returns three consecutive 500 errors or fails to answer within the timeout, the load balancer marks it Unhealthy and immediately ceases routing new traffic to it.
  • Connection Draining (Deregistration Delay): When an instance is terminated or deployed during a rolling update, the load balancer stops sending new requests but allows existing, in-flight connections up to 300 seconds to complete gracefully before severing the socket.

Hands-on: Inspecting load balancer target health

  1. View target health status for an Application Load Balancer target group: 
    $ aws elbv2 describe-target-health --target-group-arn arn:aws:elasticloadbalancing:...
    Look for: Target: {Id: i-01234, Port: 8080} and TargetHealth: {State: healthy}.
  2. Inspect the DNS resolution of an Application Load Balancer: 
    $ dig +short my-alb-123456789.us-east-1.elb.amazonaws.com
    Notice that the ALB resolves to multiple rotating IP addresses (one per active AZ)!
  3. Verify client IP forwarding headers using curl: 
    $ curl -H "X-Forwarded-For: 203.0.113.195" http://httpbin.org/headers
    Observe how backend applications parse proxy headers to log authentic client identities.

Free Recall Practice

From memory: explain the architectural difference between an ALB and an NLB. When would you choose an NLB over an ALB?

Key points to compare against:

  • ALB vs NLB architecture: An Application Load Balancer is a Layer 7 reverse proxy that terminates client TCP connections and parses HTTP headers, cookies, and paths. A Network Load Balancer operates at Layer 4, streaming raw TCP/UDP packets through hardware at line rate with sub-millisecond latency.
  • When to choose an NLB: Choose an NLB when applications require: (1) static Elastic IP addresses for client firewall whitelisting, (2) extreme throughput of millions of requests per second with ultra-low latency, (3) non-HTTP protocols (raw TCP, gaming UDP, MQTT), or (4) native client IP preservation at Layer 3.

// Cloud ALB vs NLB Routing in Java
import java.util.*;

public class LoadBalancerSimulator {
    public record AlbRule(String host, String prefix, String target) {}

    public static String routeAlb(String host, String path, List<AlbRule> rules) {
        return rules.stream()
            .filter(r -> (r.host().equals("*") || r.host().equalsIgnoreCase(host)) && path.startsWith(r.prefix()))
            .map(AlbRule::target)
            .findFirst()
            .orElse("tg-default");
    }

    public static int routeNlb(String sIp, int sPort, String dIp, int dPort, String proto, int targets) {
        return Math.floorMod(Objects.hash(sIp, sPort, dIp, dPort, proto), targets);
    }
}
Kotlin 
// Cloud ALB vs NLB Routing in Kotlin
import java.util.Objects

data class AlbRule(val host: String, val prefix: String, val target: String)

fun routeAlb(host: String, path: String, rules: List<AlbRule>): String =
    rules.firstOrNull { (it.host == "*" || it.host.equals(host, true)) && path.startsWith(it.prefix) }
        ?.target ?: "tg-default"

fun routeNlb(sIp: String, sPort: Int, dIp: String, dPort: Int, proto: String, targets: Int): Int =
    Math.floorMod(Objects.hash(sIp, sPort, dIp, dPort, proto), targets)
