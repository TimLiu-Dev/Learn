Real-Time Backends, Queues & Background Workers (SSE, WebSockets & BullMQ)

An in-memory WebSocket Map and a fire-and-forget async email call work fine on one laptop—and break loudly the day you scale to two Kubernetes pods. 01 · Mental Model Bridge (Spring Boot Bridge)

From Spring WebSocket, @Async & RabbitMQ to Redis Pub/Sub, SSE & BullMQ

If you come from Spring Boot, you already know that scaling real-time sockets or background work past a single JVM instance requires externalizing state. Spring's @EnableWebSocketMessageBroker replaces the in-memory simple broker with an external STOMP relay (RabbitMQ/ActiveMQ), SseEmitter streams server events over HTTP, and @Async plus RabbitMQ/Kafka offload slow side effects off Tomcat request threads.

From first principles, the exact same physics govern Node.js—with two runtime twists. First, each Node pod has its own isolated V8 heap, so an in-memory Map<roomId, Set<WebSocket>> only sees clients connected to that pod; Redis Pub/Sub bridges pods in real time (fire-and-forget), while BullMQ persists background jobs in Redis Sorted Sets, Lists, and Streams so zero emails, exports, or AI tasks vanish on pod restart. Second, because Node's HTTP loop is single-threaded, you must never buffer entire exports or block requests on external APIs: enqueue fast, return 202 Accepted, and verify inbound webhooks on raw bytes in constant time.

06 · Production Verification & Next Steps

Real-Time & Worker Production Checklist + Teacher Follow-Up

  • Multi-Pod Socket Audit: Verify zero global in-memory rooms are assumed authoritative across replicas; use Redis Pub/Sub (separate pub and sub clients) with tenant-scoped channel names like tenant:{id}:room:{room}, and enable sticky sessions only if using Socket.IO HTTP long-polling fallback.
  • SSE Proxy & Resume Check: Inspect live SSE responses in DevTools → Network → EventStream: verify Content-Type: text/event-stream, X-Accel-Buffering: no, periodic : keepalive comments (<30s), and id: fields paired with Last-Event-ID catch-up.
  • BullMQ Worker Resilience: Run workers in dedicated processes/deployments with bounded concurrency, exponential backoff + jitter, explicit removeOnComplete/removeOnFail retention caps, alerts on failed/DLQ growth, and SIGTERM graceful worker.close().
  • Webhook Security & Idempotency: Preserve the raw request bytes before JSON parsing, check timestamp freshness (e.g., ±300s) + constant-time HMAC-SHA256 verification, persist event.id atomically (Redis SET NX EX or DB unique constraint), and return 200 OK on duplicates.
