01 · Mental Model Bridge (First Principles + Android Transfer)

Android WorkManager + Room Offline Sync → Web Workers & Service Workers

First, establish a foundational rule on the Web: Service Workers and Dedicated Web Workers are completely different primitives even though both run off the main UI thread. A Dedicated Web Worker is an in-memory background compute thread tied to a single tab (like Dispatchers.Default or a HandlerThread)—it exists to keep heavy JSON parsing, filtering, or crypto from blocking the 60fps UI loop. A Service Worker is a programmable, event-driven network proxy shared across all tabs of an origin; it lives independently of any single tab, survives page reloads, and intercepts every fetch() request before it hits the network. Neither worker type can touch the DOM directly; all communication happens via asynchronous message passing (postMessage).

Just as Android separates app installation (AndroidManifest.xml), local persistence (Room SQLite), offline background delivery (WorkManager), and network caching (OkHttp interceptors), a production Progressive Web App (PWA) composes four distinct browser APIs over HTTPS.

06 · Real-World Verification & Next Steps

Chrome DevTools PWA Audit Checklist + Teacher Follow-Up

  • Application → Manifest: Verify zero manifest errors, valid start_url, display: "standalone", and maskable + standard PNG icons (192x192 and 512x512).
  • Application → Service Workers: Confirm your SW is activated and is running. Test toggling Offline and reloading, and inspect Update on reload vs the real-world waiting state.
  • Application → Cache Storage & IndexedDB: Verify hashed bundles reside in versioned caches (cleaned up during activate), HTML uses Network-First, and offline mutations sit in IndexedDB with idempotencyKey fields.
  • Performance Tab (Long Tasks): Record heavy filtering or parsing; confirm CPU-bound work runs on a Dedicated Worker thread (leaving the Main track free of >50ms Long Tasks).
