01 · Mental Model Bridge (Android Bridge)

From Jetpack Compose & Android Views to React Fiber & Hooks

In imperative Android Views (findViewById + textView.setText(...)), you manually mutate UI objects step-by-step and must remember every inverse transition. Both Jetpack Compose and React replace imperative mutation with declarative UI: your component is a pure function of state (UI = f(state)), and the runtime computes the minimal diff between renders. The critical difference is how each runtime stores state and schedules work on a single-threaded browser DOM.

Concept Android / Jetpack Compose Equivalent React Internal Mechanism Key React Pitfall
Declarative Description @Composable emits UI tree nodes into the Composer Slot Table JSX compiles to jsx(type, props, key) returning plain immutable JS objects (React Elements) Calling external mutations or impure Math.random() in render breaks StrictMode & concurrent restarts.
Diffing & Tree Memory Compose Slot Table + positional groups + key(...) Fiber Tree (current & workInProgress linked nodes) reconciled by type + key Using array index as key on dynamic lists causes React to reuse the wrong Fiber and scramble row state.
Component Local State remember { mutableStateOf(...) } stored in positional Slot Table useState nodes stored in a singly-linked list on fiber.memoizedState (call-order cursor) Calling a hook inside if or a loop shifts cursor positions and silently pairs state to the wrong hook.
State Updates & Snapshots Compose SnapshotState invalidates scopes & batches per frame setState enqueues an update and schedules a re-render; current render keeps its closure snapshot Calling setCount(count + 1) twice adds 1 total; use functional updater c => c + 1.
Side Effects & Cleanup LaunchedEffect(key) & DisposableEffect(key) { onDispose { ... } } useEffect(fn, deps) runs asynchronously after DOM commit + paint; cleanup runs before re-run & unmount Omitting dependencies creates stale closures; computing derived state in an effect causes redundant renders.
Skipping Work / Memoization Strong Skipping Mode + Compose Compiler stability inference useMemo / useCallback / React.memo (or React Compiler auto-memoization) Over-memoizing primitives wastes memory; unstable inline object/function props defeat React.memo without compiler.
First-Principles Check (Pure Render Rule): A React component function is called during the Render phase—which React may pause, replay, or run twice in <StrictMode>. Never mutate props, never push into module-level arrays, and never start network requests or timers directly in the component body. Keep rendering pure; put side effects in event handlers or useEffect.

06 · Production Verification & Next Steps

React DevTools & Production Audit Checklist + Teacher Follow-Up

  • StrictMode Double-Invocation Audit: Wrap your app root in <React.StrictMode> during development. If a component duplicates list items or leaks timers when React double-invokes renders and effects, you caught an impure render or missing useEffect cleanup before production.
  • React DevTools Profiler ("Why did this render?"): Record an interaction in the Profiler tab, enable Record why each component rendered, and check whether re-renders are driven by genuine state changes or unstable inline props / derived state stored in unnecessary useEffect calls.
  • List Keys & Derived State Review: Grep for key={index} or key={i} on any list that supports sorting, filtering, insertion, or item deletion—and audit every useEffect that just calls setState on props/state (compute it inline during render instead!).
Primary Source Recommendation: Study React Docs: Render and Commit and React Docs: You Might Not Need an Effect to cement the three-step lifecycle (Trigger → Render → Commit) and eliminate redundant effect synchronization.
