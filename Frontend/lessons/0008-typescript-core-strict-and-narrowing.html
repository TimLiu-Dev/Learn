01 · Mental Model Bridge (Android → TypeScript)

Kotlin Sealed Classes & Smart Casts vs. TypeScript's Erased Type Layer

In Kotlin/JVM, types live in bytecode: a ClassCastException triggers at runtime if data violates its declared type, and two classes with identical fields are incompatible unless they share a nominal supertype. TypeScript flips both assumptions. First, TypeScript compiles to plain JavaScript by erasing every type annotation: zero runtime overhead, zero runtime checks. Second, TypeScript uses structural typing: if an object has the required shape, it satisfies the interface—no implements clause needed.

First Principles Rule — The Compile-Time / Runtime Split: Inside your TypeScript modules, the compiler proves soundness across functions you control. At I/O boundaries (fetch().json(), localStorage, URL query params, postMessage), TypeScript knows nothing about the bytes arriving at runtime. Only runtime validation (e.g., Zod or custom type guards) bridges untrusted unknown data into trusted domain types.
Concept Kotlin / Android Mental Model TypeScript Mechanism Senior Trap to Avoid
Type Identity Nominal: UserId("1") != OrderId("1") even if both wrap String. Structural: { id: string } matches any object with id: string; use branded types for distinct IDs. Assuming two type aliases with identical fields cannot be accidentally swapped.
Top & Bottom Types Any? (must check before use) and Nothing (never returns / impossible). unknown (safe top type), any (disables type checking!), and never (empty bottom type). Using any or JSON.parse() without annotating unknown lets bugs bypass strict mode.
State Modeling sealed interface UiState + exhaustive when (state) expression. Discriminated Union (shared literal tag like status: "loading" | "error") + switch + never check. Modeling state with optional flags ({ loading?: boolean; data?: T; error?: string }) allows impossible states.
Smart Casts & Guards if (x is Success) smart-casts; Kotlin contracts teach the compiler custom checks. Control-flow narrowing (typeof, in, instanceof), Type Predicates (x is T), and asserts x is T. TypeScript does not verify the body of x is T is truthful—a buggy predicate silently lies to callers.
Indexing & Optionals Map[key] returns V?; list.getOrNull(i) avoids IndexOutOfBoundsException. By default arr[0] is typed as T (unsafe!); noUncheckedIndexedAccess: true makes it T | undefined. Leaving noUncheckedIndexedAccess off hides undefined crashes in dictionary lookups and array reads.
Deserialization kotlinx.serialization / Moshi enforces field types on JVM at parse time. res.json() returns Promise<any>; as User is a compile-time cast with zero runtime validation. Using as MyDto on API responses—malformed backend fields slip through until deep UI code crashes.

06 · Production Verification & Next Steps

Strict TypeScript Audit Checklist + Teacher Follow-Up

  • TSConfig Baseline: Verify strict: true, noUncheckedIndexedAccess: true, exactOptionalPropertyTypes: true, isolatedModules: true, and moduleResolution: "bundler" (for Vite/Next) or "nodenext" (for Node ESM) are enabled in tsconfig.json.
  • Zero Silent any Leaks: Search your codebase for as assertions on fetch()/JSON.parse() results and replace them with runtime schema validators (Zod/Valibot) or explicit type predicates.
  • Exhaustive Unions: Replace boolean flag bags (isLoading + isError + data) with discriminated unions and a shared assertNever(x: never): never helper in every switch default branch.
Local Compiler Companion (tsc --noEmit): Because browsers execute JavaScript rather than TypeScript types, complement the runtime labs above by running a quick local drill with npx tsc --noEmit --strict --noUncheckedIndexedAccess --exactOptionalPropertyTypes (or the official TypeScript Playground). Deliberately trigger and fix TS2322 (excess/incompatible property), TS7053 (unsafe index access), and TS2345 (unknown argument without narrowing) so reading real compiler diagnostics becomes muscle memory.
