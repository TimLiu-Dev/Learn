API Auth, Security & Validation: JWT/PKCE Sessions, argon2, Zod & Rate Limiting

In Spring Boot, SecurityFilterChain, @Valid, and JPA repositories give you opinionated guardrails out of the box. In Node.js, those layers are explicit code you compose yourself—meaning a missing tenant filter, weak hash, permissive CORS reflection, or unvalidated redirect URL turns directly into a breach. In this lesson, you will build every defense from first principles.

01 · Mental Model Bridge (Spring Boot Bridge)

From Spring Security FilterChain + @Valid to Explicit Node.js Pipelines

Every production API must answer five questions on every request in strict order: (1) Is this origin & transport allowed? (CORS & TLS/Helmet headers), (2) Is this caller flooding us? (Rate Limiting), (3) Is the payload structurally safe? (Zod DTO parsing & unknown-key stripping), (4) Who is the caller? (Authentication via session cookie, JWT, or OAuth2 + PKCE), and (5) Can this caller touch this exact tenant's resource? (Authorization: RBAC + IDOR/BOLA isolation).

06 · Production Verification & Next Steps

Pre-Deploy Security Audit Checklist + Teacher Follow-Up

  • Fail-Fast Env & Strict DTOs: Validate process.env with Zod at boot (crash immediately if JWT_SECRET is short or missing) and parse every route's body/query/params with strict schemas that strip unknown properties.
  • Cookies, CORS & Helmet: Inspect Set-Cookie in DevTools → Application (confirm HttpOnly; Secure; SameSite=Lax or Strict), verify Vary: Origin on CORS responses, and verify Helmet headers (X-Content-Type-Options: nosniff, Strict-Transport-Security, CSP).
  • IDOR & SSRF Regression Tests: Write automated integration tests proving User A in Tenant 1 receives 403/404 on Tenant 2's resource IDs, and outbound webhook fetchers reject 127.0.0.1, 10.0.0.0/8, and 169.254.169.254 even after DNS resolution.
