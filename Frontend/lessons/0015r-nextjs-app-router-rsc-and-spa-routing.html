01 · Mental Model Bridge & First Principles

Android Navigation Component → Web Rendering & App Router

In Android, your screens live inside an installed APK and only JSON crosses the network. On the Web, every first visit pays a code + data waterfall—so modern React frameworks split work between the server and the browser. Before diving into Next.js internals, ground yourself in the four foundational rendering models and how Android / Spring Boot concepts map directly to Next.js and TanStack Router.

CSR (Client-Side Rendering)

Server sends a near-empty HTML shell plus a JS bundle. The browser downloads JS, runs React, fetches JSON APIs, and paints. Great for behind-login dashboards; weak for cold SEO and slow mobile networks.

SSR & Streaming SSR

Server renders React into HTML per request so users see content fast. Classic SSR waits for all data before sending bytes; Streaming SSR sends the shell immediately and streams <Suspense> chunks as slow queries resolve.

SSG & ISR

SSG pre-renders HTML at next build and serves it from a CDN at edge speed. ISR (Incremental Static Regeneration) serves cached static pages while revalidating stale pages in the background by time or tag.

RSC vs Client Components

React Server Components (RSC) run only on the server, read databases directly, and ship 0 KB of component JS. Add 'use client' only at interactive leaves (state, effects, DOM events).

06 · Production Verification & Next Steps

App Router & Deployment Verification Checklist

  • RSC Payload & Client Bundle Audit: Run next build and inspect route output sizes (First Load JS). Verify heavy libraries (markdown parsers, date formatters, SDKs) stay inside Server Components and only thin interactive leaves carry 'use client'.
  • Cache & Streaming Headers Check: In Chrome DevTools → Network, inspect the document response for X-Nextjs-Cache: HIT | STALE | MISS (or Cache-Control) and verify Streaming SSR flushes the shell chunk immediately before slow <Suspense> data resolves.
  • Server Action Security Check: Confirm every 'use server' function validates the authenticated session, authorizes resource ownership, and validates inputs (e.g., with Zod) before mutating data or calling revalidateTag().
  • Docker vs Vercel Parity: When self-hosting via Docker, enable output: 'standalone' in next.config, configure a shared cache handler (e.g., Redis) if running multiple replicas so revalidateTag propagates across containers, and wire OpenTelemetry in instrumentation.ts.
