Lesson 0009: LLM & Event Gateways: Server-Sent Events (SSE) & Backpressure

In 2027 cloud architectures, Go microservices frequently serve as high-concurrency API gateways for AI inference, real-time market feeds, and distributed event streams. Serving streaming tokens via Server-Sent Events (SSE) requires precise mastery of HTTP response flushing (http.Flusher), client disconnect propagation, and TCP window backpressure.

⚙️ Senior Architecture Principle: The Flusher Contract

By default, Go's net/http buffers outbound response writes in 4KB chunks before flushing to the TCP socket. For real-time streaming (such as LLM tokens or financial quotes), buffering completely destroys the user experience. You must cast http.ResponseWriter to http.Flusher and explicitly flush after each event frame.

1. Anatomy of the Server-Sent Events Protocol

SSE is an ultra-lightweight, unidirectional text-based protocol over standard HTTP/1.1 or HTTP/2: 

HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive
X-Accel-Buffering: no

data: {"token": "The", "index": 0}

data: {"token": " Go", "index": 1}

data: [DONE]

2. Immediate Upstream Cancellation on Client Disconnect

If a user closes their browser tab or mobile app, the Go HTTP server closes r.Context().Done(). Your gateway must listen to this signal and abort the upstream LLM inference call immediately:

sse_gateway_loop.go Select Loop with Client Cancellation 
for {
    select {
    case <-r.Context().Done():
        // Client aborted! Abort upstream inference immediately to save GPU dollars
        return
    case token, ok := <-tokenStream:
        if !ok {
            fmt.Fprintf(w, "data: [DONE]\n\n")
            flusher.Flush()
            return
        }
        fmt.Fprintf(w, "data: %s\n\n", token)
        flusher.Flush()
    }
}

3. Hands-On Practice: Building an SSE Token Stream Handler

Implement an HTTP handler that streams tokens as Server-Sent Events:

  • Task 1: Set standard SSE headers (Content-Type: text/event-stream, Cache-Control: no-cache, Connection: keep-alive).
  • Task 2: Cast w to http.Flusher. Stream tokens from the channel, formatting each as data: <token>\n\n and flushing immediately. Abort if r.Context().Done() fires.

Canonical Reference Solution

package sse

import (
    "fmt"
    "net/http"
)

func StreamHandler(w http.ResponseWriter, r *http.Request, tokenStream <-chan string) {
    flusher, ok := w.(http.Flusher)
    if !ok {
        http.Error(w, "Streaming unsupported", http.StatusInternalServerError)
        return
    }

    w.Header().Set("Content-Type", "text/event-stream")
    w.Header().Set("Cache-Control", "no-cache")
    w.Header().Set("Connection", "keep-alive")
    w.WriteHeader(http.StatusOK)
    flusher.Flush()

    ctx := r.Context()
    for {
        select {
        case <-ctx.Done():
            return // Client disconnected
        case token, ok := <-tokenStream:
            if !ok {
                fmt.Fprintf(w, "data: [DONE]\n\n")
                flusher.Flush()
                return
            }
            fmt.Fprintf(w, "data: %s\n\n", token)
            flusher.Flush()
        }
    }
}

4. Architectural Knowledge Check (Senior Level)

Question 1 of 2 • http.Flusher Role
Why must a streaming HTTP SSE gateway verify that http.ResponseWriter implements http.Flusher?
Without flushing the buffer every event is delayed until request completion
The operating system kernel drops uncompressed network frames after ten seconds
The garbage collector purges active response sockets during concurrent mark sweeps
Without flushing the runtime compiler converts streaming payloads into static memory
A (CORRECT): Standard Go HTTP handlers buffer output in internal chunk buffers (typically 4KB). Without invoking flusher.Flush() after writing an SSE frame, events sit queued in memory until the buffer fills or the entire request finishes, defeating the purpose of real-time streaming.
B (INCORRECT): The OS kernel manages TCP buffers via window sizes; it does not drop uncompressed frames due to timeouts.
C (INCORRECT): Active network connections are referenced root descriptors, never purged by GC cycles.
D (INCORRECT): The compiler has no awareness of runtime HTTP buffer management.
Question 2 of 2 • Client Disconnect Handling
How should an SSE gateway handle client disconnection during an active token stream?
Monitor request context cancellation and immediately terminate upstream inference streaming pipelines
Continue streaming tokens until the completion payload is fully generated internally
Trigger a runtime panic to restart the HTTP server connection pool
Store undelivered tokens in global memory buffers for later client retrieval
A (CORRECT): When a client disconnects, r.Context().Done() is closed. The gateway must catch this and immediately terminate upstream processing (such as LLM generation or database queries) to free GPU/CPU compute and prevent server waste.
B (INCORRECT): Continuing to process tokens for a disconnected client wastes valuable GPU and compute resources.
C (INCORRECT): Panicking on client disconnect is an extreme anti-pattern that crashes the handler and destabilizes the server.
D (INCORRECT): Storing discarded tokens in memory for SSE leads to rapid memory leaks.
