0000-3. Errors, defer & Modern Go Generics

Kotlin gives you exceptions, sealed class Result, and .use {} blocks. Go makes every failure path an ordinary return value (T, error) so edge cases cannot unwind invisibly across network boundaries, while defer guarantees resource cleanup in LIFO order.

📱 Android / Kotlin Bridge: Errors as Values, Not Exceptions

In cloud Go codebases, reserve panic strictly for unrecoverable startup/invariant bugs—never normal request failures like missing database rows or rate limits. Wrap causes with fmt.Errorf("...: %w", err), inspect sentinels with errors.Is, and extract typed errors with Go 1.26's generic errors.AsType[*MyErr](err).

1. Wrapping, errors.Is & Go 1.26 errors.AsType

Formatting with %v destroys the underlying error chain; formatting with %w preserves it so upstream handlers can still match sentinels (errors.Is(err, ErrRecordNotFound)) or unwrap structured metadata across multiple layers.

Previously, extracting a custom struct error required declaring a target variable and passing its pointer to errors.As(err, &target)—an API easy to misuse if you forgot the pointer level. Since Go 1.26, errors.AsType validates types at compile time with zero variable boilerplate:

error_astypes.go (Go 1.26+) 
// Wrap while adding operational context
return fmt.Errorf("fetch %s %s: %w", entity, id, ErrRecordNotFound)

// Unwrap typed error safely in Go 1.26+
if rl, ok := errors.AsType[*RateLimitError](err); ok {
    return rl.RetryAfter, true
}

2. Deterministic Cleanup with defer & Prudent Generics

Deferred calls push onto a per-frame stack and run in LIFO order when the enclosing function returns (even on panics). Arguments passed to a deferred call evaluate immediately when defer executes—never defer closing files inside an unbounded loop unless wrapped in a helper function.

For algorithms across ordered types (int, float64, string), Go's standard cmp.Ordered constraint enables zero-boxing generics without losing compile-time type safety.

func WrapNotFound(entity string, id string) error {
	return fmt.Errorf("%s %s: %w", entity, id, ErrRecordNotFound)
}

func ExtractRetryAfter(err error) (time.Duration, bool) {
	if rl, ok := errors.AsType[*RateLimitError](err); ok {
		return rl.RetryAfter, true
	}
	return 0, false
}

func MaxSlice[T cmp.Ordered](items []T) (T, bool) {
	if len(items) == 0 {
		var zero T
		return zero, false
	}
	best := items[0]
	for _, item := range items[1:] {
		if item > best {
			best = item
		}
	}
	return best, true
}

4. Knowledge Verification Quizzes

Quiz 1 of 2 • defer Execution Semantics
When you place defer db.Close(start) inside an inner if block of a handler function, when do arguments evaluate and when does cleanup run?
A Both argument evaluation and Close execute immediately when control leaves the inner if block.
B Both argument evaluation and Close happen when the function returns, executing in FIFO order.
C Arguments evaluate when the function returns, while Close executes asynchronously on a cleanup goroutine.
D Arguments evaluate at the defer statement, while Close executes LIFO when the enclosing function returns.
Option A (Incorrect): defer is scoped to the enclosing function, not an if or for block.
Option B (Incorrect): Deferred calls run in LIFO (last-in, first-out) stack order, not FIFO, and capture argument values early.
Option C (Incorrect): Deferred calls run synchronously on the returning goroutine, not a background goroutine.
Option D (Correct): Argument expressions evaluate immediately when defer runs; the deferred function executes LIFO on function exit.
Quiz 2 of 2 • Modern Error Inspection
You wrap a pointer error *RateLimitError twice using fmt.Errorf("...: %w", err). How should Go 1.26+ callers inspect it?
A Compare directly with err == &RateLimitError{} since Go unwraps %w chains automatically during equality checks.
B Call errors.AsType[*RateLimitError](err) to walk wrapped causes cleanly and obtain a typed pointer directly.
C Use a direct type assertion err.(*RateLimitError) because %w compiles away wrapper structs.
D Check strings.Contains(err.Error(), "RateLimitError") because reflection unwrapping breaks after multiple wraps.
Option A (Incorrect): == checks pointer/value identity on the outermost wrapper only and never walks wrapped errors.
Option B (Correct): Go 1.26's generic errors.AsType[*RateLimitError](err) walks the full unwrap tree type-safely in one call.
Option C (Incorrect): A bare type assertion checks only the outer wrapper error and fails on wrapped chains.
Option D (Incorrect): Substring matching on Error() is brittle across message edits; unwrap trees handle arbitrarily deep %w chains.
