Lesson 0006: Clean Architecture, Interface Segregation, & Dependency Injection

Engineers coming from Java or C# often import excessive OOP patterns into Go: 50-method interfaces, factory classes, and heavy reflection frameworks. In Go, interfaces are implicitly satisfied and structural. In this lesson, we master idiomatic Go Clean Architecture (Ports & Adapters), the Interface Segregation Principle, and compile-time dependency injection without magic reflection.

⚙️ The Golden Rule of Go Interfaces

"Accept interfaces, return structs."
• Functions should accept the smallest possible interface required to do their job (often 1 or 2 methods).
• Constructors should return concrete types (*Service, *Store), not interfaces.
• Interfaces belong to the consumer, not the producer. The package implementing the database does not define the interface; the business service calling the database defines what it needs.

1. The Production Cloud Service Layout

cmd/
  server/
    main.go         // Wires dependencies, handles OS signals, initiates graceful drain
internal/
  domain/           // Pure enterprise entities, business rules, zero external dependencies
    account.go
  service/          // Application use cases; defines Consumer Interfaces (Ports)
    transfer.go     // type AccountRepository interface { ... }
  postgres/         // Infrastructure Adapter: satisfies AccountRepository
    store.go
  transport/
    grpc/           // Transport Adapter: gRPC / ConnectRPC server
    http/           // Transport Adapter: HTTP handlers / SSE gateways

2. Interface Segregation: Defining Consumer Ports

Avoid monolithic interfaces. If your transfer service only needs to fetch an account balance and persist an entry, define only those two methods:

internal/service/transfer.go Tightly-Scoped Consumer Port 
package service

import (
    "context"
    "errors"
)

var ErrInsufficientFunds = errors.New("insufficient balance for transfer")

// Store abstracts persistence behind a transactional UnitOfWork boundary.
// Never split debit and credit across separate non-transactional repo calls (TOCTOU risk).
type AccountStore interface {
    WithinTx(ctx context.Context, fn func(tx AccountTx) error) error
}

type AccountTx interface {
    GetBalanceForUpdate(ctx context.Context, accountID string) (int64, error)
    UpdateBalance(ctx context.Context, accountID string, delta int64) error
}

type TransferService struct {
    store AccountStore
}

func NewTransferService(store AccountStore) *TransferService {
    return &TransferService{store: store}
}

func (s *TransferService) Transfer(ctx context.Context, fromID, toID string, amount int64) error {
    return s.store.WithinTx(ctx, func(tx AccountTx) error {
        bal, err := tx.GetBalanceForUpdate(ctx, fromID)
        if err != nil {
            return err
        }
        if bal < amount {
            return ErrInsufficientFunds
        }
        if err := tx.UpdateBalance(ctx, fromID, -amount); err != nil {
            return err
        }
        return tx.UpdateBalance(ctx, toID, amount)
    })
}

3. Hands-On Practice: Building a Clean Service with In-Memory Mock Port

Implement a decoupled OrderProcessor that relies on a consumer-defined interface PaymentGateway.

  • Task 1: Define the PaymentGateway interface with method Charge(ctx context.Context, orderID string, amountCents int64) error.
  • Task 2: Implement OrderProcessor.ProcessOrder to validate that amount is positive and delegate charging to the gateway.
🛠️ Interactive Lab: Interface Segregation & Mock Injection
Target: Decoupled Port
Complete the code below so OrderProcessor validates inputs and delegates via its consumer-owned PaymentGateway port. Verify syntax here, then run the Go race test suite in labs/.

Canonical Reference Solution

package orders

import (
    "context"
    "errors"
)

var (
    ErrInvalidAmount = errors.New("amount must be greater than zero")
)

// PaymentGateway is the consumer port
type PaymentGateway interface {
    Charge(ctx context.Context, orderID string, amountCents int64) error
}

type OrderProcessor struct {
    gateway PaymentGateway
}

func NewOrderProcessor(gateway PaymentGateway) *OrderProcessor {
    return &OrderProcessor{gateway: gateway}
}

func (p *OrderProcessor) ProcessOrder(ctx context.Context, orderID string, amountCents int64) error {
    if amountCents <= 0 {
        return ErrInvalidAmount
    }
    return p.gateway.Charge(ctx, orderID, amountCents)
}

4. Architectural Knowledge Check (Senior Level)

Question 1 of 2 • Interface Segregation
In idiomatic Go architecture, where should interfaces be defined according to the Interface Segregation Principle?
A Interfaces belong inside the producer package beside the concrete struct
B Interfaces belong inside a shared global types package across services
C Interfaces belong inside the consumer package calling only needed methods
D Interfaces belong inside the storage adapter beside database schema queries
A (INCORRECT): Defining interfaces beside concrete producers is a Java/C# holdover that causes interface pollution and import cycles.
B (INCORRECT): A central shared interface package tightly couples unrelated modules into bloated change fan-out.
C (CORRECT): Go satisfies interfaces implicitly, so each consumer package can declare the exact slim interface port it calls without coupling to adapters.
D (INCORRECT): Storage layers act as concrete adapters implementing business ports rather than prescribing consumer contracts.
Question 2 of 2 • Interface Pollution Prevention
Why does returning a concrete struct pointer rather than an interface value prevent interface pollution?
A Callers can independently declare minimal consumer interfaces without locking into producer abstractions
B The compiler always bypasses CPU instruction caching whenever methods use concrete structs
C The garbage collector skips tracing pointer fields inside returned structs during scans
D Returning concrete structs permits unrestricted raw pointer arithmetic without unsafe package imports
A (CORRECT): Returning concrete pointers lets every caller define its own slim interface covering only the methods it uses without locking downstream callers into an artificial producer interface.
B (INCORRECT): Although direct calls avoid itable lookup indirection, clean decoupling stems from Go's implicit satisfaction model rather than cache bypass.
C (INCORRECT): The GC traces heap pointers accurately whether held via concrete pointers or interface values.
D (INCORRECT): Go disallows pointer arithmetic outside unsafe.Pointer regardless of function return types.
