Lesson 0006: Clean Architecture, Interface Segregation, & Dependency Injection

Engineers coming from Java or C# often import excessive OOP patterns into Go: 50-method interfaces, factory classes, and heavy reflection frameworks. In Go, interfaces are implicitly satisfied and structural. In this lesson, we master idiomatic Go Clean Architecture (Ports & Adapters), the Interface Segregation Principle, and compile-time dependency injection without magic reflection.

⚙️ The Golden Rule of Go Interfaces

"Accept interfaces, return structs."
• Functions should accept the smallest possible interface required to do their job (often 1 or 2 methods).
• Constructors should return concrete types (*Service, *Store), not interfaces.
• Interfaces belong to the consumer, not the producer. The package implementing the database does not define the interface; the business service calling the database defines what it needs.

1. The Production Cloud Service Layout

cmd/
  server/
    main.go         // Wires dependencies, handles OS signals, initiates graceful drain
internal/
  domain/           // Pure enterprise entities, business rules, zero external dependencies
    account.go
  service/          // Application use cases; defines Consumer Interfaces (Ports)
    transfer.go     // type AccountRepository interface { ... }
  postgres/         // Infrastructure Adapter: satisfies AccountRepository
    store.go
  transport/
    grpc/           // Transport Adapter: gRPC / ConnectRPC server
    http/           // Transport Adapter: HTTP handlers / SSE gateways

2. Interface Segregation: Defining Consumer Ports

Avoid monolithic interfaces. If your transfer service only needs to fetch an account balance and persist an entry, define only those two methods:

internal/service/transfer.go Tightly-Scoped Consumer Port 
package service

import (
    "context"
    "errors"
)

var ErrInsufficientFunds = errors.New("insufficient balance for transfer")

// AccountRepository is defined here by the consumer, requiring ONLY the methods it uses.
type AccountRepository interface {
    GetBalance(ctx context.Context, accountID string) (int64, error)
    UpdateBalance(ctx context.Context, accountID string, delta int64) error
}

type TransferService struct {
    repo AccountRepository
}

func NewTransferService(repo AccountRepository) *TransferService {
    return &TransferService{repo: repo}
}

func (s *TransferService) Transfer(ctx context.Context, fromID, toID string, amount int64) error {
    bal, err := s.repo.GetBalance(ctx, fromID)
    if err != nil {
        return err
    }
    if bal < amount {
        return ErrInsufficientFunds
    }
    if err := s.repo.UpdateBalance(ctx, fromID, -amount); err != nil {
        return err
    }
    return s.repo.UpdateBalance(ctx, toID, amount)
}

3. Hands-On Practice: Building a Clean Service with In-Memory Mock Port

Implement a decoupled OrderProcessor that relies on a consumer-defined interface PaymentGateway.

  • Task 2: Implement OrderProcessor.ProcessOrder to validate that amount is positive and delegate charging to the gateway.

Canonical Reference Solution

package orders

import (
    "context"
    "errors"
)

var (
    ErrInvalidAmount = errors.New("amount must be greater than zero")
)

// PaymentGateway is the consumer port
type PaymentGateway interface {
    Charge(ctx context.Context, orderID string, amountCents int64) error
}

type OrderProcessor struct {
    gateway PaymentGateway
}

func NewOrderProcessor(gateway PaymentGateway) *OrderProcessor {
    return &OrderProcessor{gateway: gateway}
}

func (p *OrderProcessor) ProcessOrder(ctx context.Context, orderID string, amountCents int64) error {
    if amountCents <= 0 {
        return ErrInvalidAmount
    }
    return p.gateway.Charge(ctx, orderID, amountCents)
}

4. Architectural Knowledge Check (Senior Level)

Question 1 of 2 • Interface Segregation
In idiomatic Go architecture, where should interfaces be defined according to the Interface Segregation Principle?
Interfaces belong in the client consumer package that calls required methods
Interfaces belong in the producer package alongside the concrete implementation struct
Interfaces belong in a dedicated global shared interface package across repositories
Interfaces belong in the database repository package alongside table migration schemas
A (CORRECT): In Go, interfaces are satisfied implicitly without an implements keyword. The consumer package should define the minimal interface it requires (Ports). This avoids interface pollution and prevents tight coupling to implementation details.
B (INCORRECT): Defining interfaces in the producer package is a Java/C# holdover that creates interface pollution and circular dependency problems.
C (INCORRECT): Shared global interface packages create monolithic dependencies where changing one interface forces rebuilding the entire ecosystem.
D (INCORRECT): The database layer is an infrastructure adapter, not the entity that defines business interface ports.
Question 2 of 2 • Interface Pollution Prevention
Why does returning a concrete struct pointer rather than an interface pointer prevent interface pollution?
Consumers can independently define small interfaces matching their specific requirements without lock-in
The compiler automatically generates faster assembly instructions when structs bypass method virtual table lookup
The garbage collector avoids scanning pointers stored in concrete struct memory during concurrent sweep
Concrete struct pointers allow direct memory address arithmetic without invoking runtime reflection package calls
A (CORRECT): Returning concrete structs allows caller packages the freedom to declare their own custom single-method or multi-method interfaces matching exactly what they use. It also avoids prematurely restricting struct methods behind an artificially narrow producer interface.
B (INCORRECT): While direct struct calls avoid interface dynamic dispatch (itable lookup), interface pollution is primarily a design cohesion concern rather than micro-optimization.
C (INCORRECT): The GC sweeps heap pointers regardless of whether they were returned as concrete structs or interfaces.
D (INCORRECT): Go does not permit raw pointer arithmetic without unsafe.Pointer, independent of return type conventions.
