Lesson 0010: Enterprise Structured Logging (log/slog), Dynamic Levels, & PII Redaction

Third-party logging libraries (Logrus, Zap, Zerolog) fragmented the Go ecosystem for years. In Go 1.21, the Go team standardized structured, high-performance logging via log/slog. In this lesson, we build production-grade logging infrastructure: dynamic level switching via HTTP without restarting pods (slog.LevelVar), custom handler middleware, and automatic Personally Identifiable Information (PII) redaction.

⚙️ Senior Production Practice: The Zero-Allocation Attr Pattern

Instead of loose key-value pairs (slog.Info("msg", "key", val)) which box parameters into any, senior engineers use strongly-typed attributes:
• slog.Int64("user_id", id)
• slog.String("trace_id", traceID)
• slog.Duration("latency", d)
This allows slog.Handler to format records without triggering heap allocations.

1. Dynamic Runtime Log Level Switching with slog.LevelVar

In production Kubernetes clusters, running at DEBUG level generates terabytes of noisy logs and overwhelms ingest pipelines. But when an outage occurs, you need debug logs immediately without redeploying containers:

dynamic_logging.go Live Runtime Adjustment via HTTP 
package main

import (
    "log/slog"
    "net/http"
    "os"
)

var programLevel = new(slog.LevelVar) // Defaults to INFO

func initLogger() {
    h := slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{
        Level: programLevel,
    })
    slog.SetDefault(slog.New(h))
}

// HTTP Admin endpoint to flip level live:
// curl -X POST http://localhost:8081/admin/log-level?level=DEBUG
func handleSetLogLevel(w http.ResponseWriter, r *http.Request) {
    lvl := r.URL.Query().Get("level")
    switch lvl {
    case "DEBUG":
        programLevel.Set(slog.LevelDebug)
    case "INFO":
        programLevel.Set(slog.LevelInfo)
    case "WARN":
        programLevel.Set(slog.LevelWarn)
    }
    w.Write([]byte("Log level updated: " + programLevel.Level().String()))
}

2. Redacting Sensitive Fields with slog.ReplaceAttr

Accidentally logging authorization tokens, passwords, or credit card numbers violates GDPR, PCI-DSS, and SOC2 compliance:

redaction_handler.go Scrubbing Sensitive Keys 
func RedactSensitiveAttrs(groups []string, a slog.Attr) slog.Attr {
    switch a.Key {
    case "password", "token", "authorization", "secret", "cvv":
        return slog.String(a.Key, "[REDACTED]")
    }
    return a
}

func NewRedactingLogger() *slog.Logger {
    opts := &slog.HandlerOptions{
        ReplaceAttr: RedactSensitiveAttrs,
    }
    return slog.New(slog.NewJSONHandler(os.Stdout, opts))
}

package logging

import (
    "log/slog"
    "strings"
)

func RedactAttr(groups []string, a slog.Attr) slog.Attr {
    keyLower := strings.ToLower(a.Key)
    switch keyLower {
    case "authorization", "password", "secret_token", "api_key", "token":
        return slog.String(a.Key, "[REDACTED]")
    }
    return a
}

4. Architectural Knowledge Check (Senior Level)

Question 1 of 2 • Dynamic Log Levels
Why is slog.LevelVar preferred over static log levels in cloud microservices?
LevelVar permits changing log verbosity dynamically without restarting running container pods
LevelVar completely disables all log record heap allocations across garbage collection sweeps
LevelVar automatically encrypts sensitive audit logs using hardware AES processor instruction sets
LevelVar compresses JSON log payloads to prevent disk storage exhaustion in production
A (CORRECT): slog.LevelVar is an atomic thread-safe level container. It allows operations teams to expose an internal admin endpoint or listen to config updates to switch from INFO to DEBUG mode in real time during an incident without restarting or redeploying the pod.
B (INCORRECT): LevelVar manages log filtering level checks; it does not eliminate GC allocations.
C (INCORRECT): Encryption is handled at transport or disk storage, not inside LevelVar.
D (INCORRECT): Payload compression is performed by log shippers (Fluentbit, Vector), not by the Go logger level variable.
Question 2 of 2 • Production PII Security
How should sensitive customer PII like authorization tokens be protected in production slog output?
Implement a custom slog.Handler that scrubs sensitive keys during Record evaluation
Rely on production cloud log aggregators to filter unencrypted customer credential attributes
Convert string authentication tokens into raw integer memory addresses before writing logs
Disable all structured log outputs across production Kubernetes clusters to ensure security
A (CORRECT): Defense-in-depth requires redacting sensitive data at the source before writing to stdout. Using slog.HandlerOptions.ReplaceAttr or custom handler wrappers guarantees sensitive keys like password or authorization are replaced with [REDACTED] before leaving the process.
B (INCORRECT): Relying on downstream collectors risks leaking credentials into container stdout, local node logs, and SIEM staging queues.
C (INCORRECT): Memory addresses are useless for logging and do not properly redact credentials.
D (INCORRECT): Disabling logs destroys operational observability during outages.
