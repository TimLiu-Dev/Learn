Lesson 0004: Channel Internals, CSP Concurrency, & iter.Seq (Range-Over-Func)

Go's concurrency philosophy is rooted in Hoare's Communicating Sequential Processes (CSP): "Do not communicate by sharing memory; instead, share memory by communicating." But in production cloud services, channels are often misused, leading to memory leaks and lock contention. In this lesson, we dissect channel internals (hchan, sudog, waitq), production CSP patterns, and why Go 1.22+ iter.Seq (range-over-func) replaces channels for sequential streaming.

⚙️ Senior Architectural Truth: Channels are not "Magic"

Under the hood, a Go channel is a heap-allocated runtime.hchan struct protected by a standard lock mutex with two bidirectional wait queues (recvq and sendq) storing parked goroutines (sudog). Channels are ideal for coordination, signaling, and passing ownership across goroutines. But for streaming data within a single goroutine, channels create unnecessary heap allocations and lock contention.

2. Modern Go: When to Use iter.Seq (Range-Over-Func) Instead of Channels

In legacy Go, if you wanted to yield elements lazily, you spawned a background goroutine feeding an unbuffered channel:

legacy_channel_leak.go vs modern_iter.go Zero-Allocation Streaming 
// LEGACY (Anti-Pattern): Spawns goroutine, allocates hchan, risks goroutine leak if loop breaks!
func LegacyStream(items []string) <-chan string {
    ch := make(chan string)
    go func() {
        defer close(ch)
        for _, it := range items {
            ch <- it // If consumer breaks early, this goroutine leaks forever!
        }
    }()
    return ch
}

// 2027 STANDARD: iter.Seq (Zero allocation, synchronous, impossible to leak)
import "iter"

func ModernStream(items []string) iter.Seq[string] {
    return func(yield func(string) bool) {
        for _, it := range items {
            if !yield(it) {
                return // Consumer executed 'break', clean instant exit!
            }
        }
    }
}

// Usage:
for item := range ModernStream(records) {
    if item == "stop" { break } // Clean, zero leak!
}

Canonical Reference Solution

package pipeline

import "sync"

// FanOutProcess distributes jobs across workerCount workers and streams results
func FanOutProcess(jobs <-chan int, workerCount int, transform func(int) int) <-chan int {
    out := make(chan int)
    var wg sync.WaitGroup

    // Spawn workers
    for i := 0; i < workerCount; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for job := range jobs {
                out <- transform(job)
            }
        }()
    }

    // Closer goroutine: closes out when all workers complete
    go func() {
        wg.Wait()
        close(out)
    }()

    return out
}

4. Architectural Knowledge Check (Senior Level)

Question 1 of 2 • Channel Panic Mechanics
Why does closing a nil channel or sending to a closed channel cause an immediate runtime panic?
The channel memory specification explicitly mandates panic to catch logic bugs
The operating system kernel raises invalid memory segmentation fault during send
The garbage collector immediately sweeps active wait queues causing memory faults
The scheduler detects deadlock and terminates background process with fatal signal
A (CORRECT): In Go, sending to a closed channel or closing a nil channel indicates a fundamental architectural defect in ownership coordination (the sender should own channel closing). The language designers chose an immediate explicit panic to prevent silent state corruption or zombie execution.
B (INCORRECT): Channels are purely user-space runtime structures managed by Go runtime code, not kernel hardware segmentation faults.
C (INCORRECT): Active channels and parked sudog queues remain reachable root objects and are never swept prematurely by the GC.
D (INCORRECT): Deadlock detection terminates when all goroutines sleep; sending to a closed channel panics immediately within the executing goroutine.
Question 2 of 2 • 2027 Iterators vs Channels
When should a senior Go architect prefer Go 1.22 range-over-func iterators over channels?
For sequential internal collections to eliminate channel synchronization and allocation overhead
For cross goroutine pipelines where asynchronous worker queues demand backpressure buffering mechanisms
For distributed network sockets where multiplexed select statements require non blocking cancellation
For operating system signal handlers where interrupt routines must safely terminate processes
A (CORRECT): iter.Seq provides completely zero-allocation, synchronous lazy iteration. Using channels within single goroutine loops incurs unnecessary hchan heap allocations, mutex acquisitions, and risks permanent goroutine leaks if consumers break early.
B (INCORRECT): For concurrent cross-goroutine communication with asynchronous buffers, channels remain the idiomatic CSP solution.
C (INCORRECT): Network socket select multiplexing requires channel select primitives, not synchronous iterators.
D (INCORRECT): OS signal notifications in Go utilize signal.Notify(chan os.Signal), requiring channel semantics.
