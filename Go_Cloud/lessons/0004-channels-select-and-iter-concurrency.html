Lesson 0004: Channel Internals, CSP Concurrency, & iter.Seq (Range-Over-Func)

Go's concurrency philosophy is rooted in Hoare's Communicating Sequential Processes (CSP): "Do not communicate by sharing memory; instead, share memory by communicating." But in production cloud services, channels are often misused, leading to memory leaks and lock contention. In this lesson, we dissect channel internals (hchan, sudog, waitq), production CSP patterns, and why Go 1.22+ iter.Seq (range-over-func) replaces channels for sequential streaming.

⚙️ Senior Architectural Truth: Channels are not "Magic"

Under the hood, a Go channel is a heap-allocated runtime.hchan struct protected by a standard lock mutex with two bidirectional wait queues (recvq and sendq) storing parked goroutines (sudog). Channels are ideal for coordination, signaling, and passing ownership across goroutines. But for streaming data within a single goroutine, channels create unnecessary heap allocations and lock contention.

2. Modern Go: When to Use iter.Seq (Range-Over-Func) Instead of Channels

In legacy Go, if you wanted to yield elements lazily, you spawned a background goroutine feeding an unbuffered channel:

legacy_channel_leak.go vs modern_iter.go Zero-Allocation Streaming 
// LEGACY (Anti-Pattern): Spawns goroutine, allocates hchan, risks goroutine leak if loop breaks!
func LegacyStream(items []string) <-chan string {
    ch := make(chan string)
    go func() {
        defer close(ch)
        for _, it := range items {
            ch <- it // If consumer breaks early, this goroutine leaks forever!
        }
    }()
    return ch
}

// 2027 STANDARD: iter.Seq (Zero allocation, synchronous, impossible to leak)
import "iter"

func ModernStream(items []string) iter.Seq[string] {
    return func(yield func(string) bool) {
        for _, it := range items {
            if !yield(it) {
                return // Consumer executed 'break', clean instant exit!
            }
        }
    }
}

// Usage:
for item := range ModernStream(records) {
    if item == "stop" { break } // Clean, zero leak!
}

Canonical Reference Solution

package pipeline

import (
    "context"
    "sync"
)

func FanOutProcess(ctx context.Context, jobs <-chan int, workerCount int, transform func(int) int) <-chan int {
    out := make(chan int)
    var wg sync.WaitGroup

    for range workerCount {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for {
                select {
                case <-ctx.Done():
                    return
                case job, ok := <-jobs:
                    if !ok {
                        return
                    }
                    select {
                    case out <- transform(job):
                    case <-ctx.Done():
                        return
                    }
                }
            }
        }()
    }

    go func() {
        wg.Wait()
        close(out)
    }()

    return out
}

4. Architectural Knowledge Check (Senior Level)

Question 1 of 2 • Channel Panic Mechanics
Why does closing a nil channel or sending to a closed channel cause an immediate runtime panic?
A The channel specification mandates panics to catch broken ownership coordination bugs
B The operating system kernel delivers an invalid memory segmentation fault signal
C The garbage collector eagerly sweeps active wait queues during concurrent sends
D The runtime scheduler traps permanent deadlocks and aborts worker threads immediately
A (CORRECT): Sending on a closed channel or closing a nil channel signals broken producer ownership coordination, so Go fails fast with a panic rather than corrupting state silently.
B (INCORRECT): Channels are managed in user space by the Go runtime rather than kernel hardware segmentation faults.
C (INCORRECT): Active channels and queued waiters stay reachable GC roots and are never collected prematurely.
D (INCORRECT): Deadlock detection occurs when all goroutines are parked, whereas send-on-closed panics synchronously in the caller goroutine.
Question 2 of 2 • 2027 Iterators vs Channels
When should a senior Go architect prefer Go 1.23+ range-over-func iterators (iter.Seq) over channels?
A For concurrent worker pipelines requiring bounded queues and backpressure buffering controls
B For network socket fan-in loops needing multiplexed select cancellation across peers
C For sequential lazy streaming to eliminate channel locking and goroutine leak risks
D For operating system signal delivery requiring asynchronous interrupt wakeups via runtime
A (INCORRECT): Multi-goroutine asynchronous pipelines with backpressure require channels.
B (INCORRECT): Multiplexed non-blocking select awaits operate on channels, not synchronous push iterators.
C (CORRECT): Stabilized in Go 1.23, iter.Seq yields items lazily on the caller's stack with zero hchan locks or leaked producer goroutines when a loop exits early with break.
D (INCORRECT): OS signals subscribe via signal.Notify onto buffered channels.
