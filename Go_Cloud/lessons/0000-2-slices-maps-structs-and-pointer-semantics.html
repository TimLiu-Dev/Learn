0000-2. Slices, Maps, Structs & Pointer Semantics

In Kotlin, every class instance or MutableList is passed as an object reference on the heap. In Go, everything passes by value—including structs, pointers, and slice headers. Mastering what gets copied prevents silent data corruption bugs.

📱 Android / Kotlin Bridge: Why Passing a Slice Isn't Passing a List

A Kotlin MutableList holds one shared list object reference: calling list.add(x) from a callee changes the caller's size. In Go, a slice value is a 3-word header (ptr, len, cap) passed by value. Appending updates a new header (requiring s = append(s, x)), yet two slices sharing spare capacity share the same backing array!

1. The Three-Index Full Slice Expression

Suppose a parent slice has length 2 and capacity 8 (backing := make([]int, 2, 8)). If branch A executes append(backing, 30) and branch B also executes append(backing, 99), both writes fit inside index 2 of the same backing array—branch B silently corrupts branch A's element!

To force Go to allocate an isolated backing array on append, clamp capacity equal to length with the full slice expression base[:len(base):len(base)] (or explicitly copy into a fresh slice).

slice_isolation.go 
// Safe: clamp cap to len before appending extra elements
isolated := base[:len(base):len(base)]
return append(isolated, extra...)

2. Nil Maps, Comma-Ok Idiom & Pointer Receivers

Unlike a zero-value slice (which lets you append safely), writing to a nil map panics at runtime, whereas reading a nil map safely returns the zero value. Because a missing key and a stored key mapped to 0 both return 0, always read maps with Go's two-value v, ok := m[k] lookup when presence matters.

Similarly, methods define either value receivers (c Counter) (operating on a copy) or pointer receivers (c *Counter) (mutating the caller's struct in place). Mutating methods and large structs use pointer receivers consistently.

func AppendIsolated(base []int, extra ...int) []int {
	clamped := base[:len(base):len(base)]
	return append(clamped, extra...)
}

func LookupPort(ports map[string]int, service string) (int, bool) {
	port, ok := ports[service]
	return port, ok
}

func (c *Counter) Inc() {
	c.n++
}

4. Knowledge Verification Quizzes

Quiz 1 of 2 • Slice Capacity Aliasing
A slice s has len(s) == 2 and cap(s) == 8. How do you derive a slice whose subsequent append never overwrites spare backing slots visible through s?
A Re-slice using s[:len(s)] so Go copies elements onto the stack immediately.
B Pass &s to functions because pointer arguments prevent shared array indexing.
C Clamp capacity with s[:len(s):len(s)] so any append allocates fresh backing storage.
D Call append directly on s because Go enforces immutable copy-on-write slices.
Option A (Incorrect): Two-index slicing s[:len(s)] retains the parent's capacity (8), leaving spare slots shared.
Option B (Incorrect): Taking &s exposes the same slice header rather than cloning the backing array.
Option C (Correct): The third index sets cap == len, forcing the runtime to allocate a brand-new backing array on append.
Option D (Incorrect): Go slices are NOT copy-on-write; append mutates spare capacity whenever len < cap.
Quiz 2 of 2 • Map Semantics
What happens when reading key "disabled" from a nil map var m map[string]int versus a map containing {"disabled": 0}?
A Single-value read returns 0 for both, whereas comma-ok distinguishes false from true.
B Reading from a nil map panics immediately with a nil-pointer assignment panic.
C Single-value read returns nil from an uninitialized map and 0 from a populated map.
D Comma-ok returns true for nil maps because zero-value keys exist implicitly.
Option A (Correct): Both reads yield zero (0) safely, so v, ok := m[k] is needed to tell absent (false) from explicit zero (true).
Option B (Incorrect): Writing to a nil map panics, but reading a nil map is completely safe in Go.
Option C (Incorrect): An int value in Go cannot be nil; its zero value is always 0.
Option D (Incorrect): Missing keys and keys in a nil map always yield ok == false.
