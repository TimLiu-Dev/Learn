0000-6. Linux cgroups, Type-Safe SQL (sqlc) & Redis Foundations

Android gives every app one private SQLite DB inside an OS-managed sandbox. Cloud Go services run inside Linux containers across dozens of replicas sharing PostgreSQL and Redis under strict kernel CPU and memory limits.

📱 Android / Kotlin Bridge: Room → sqlc, Local Memory → Redis, Sandbox → cgroups

Instead of Room annotations or reflection ORMs, senior Go engineers write explicit SQL checked at compile time by sqlc alongside versioned migrations. Instead of an in-process singleton cache that diverges across pods, shared rate-limits and ephemeral reads live in Redis. And Kubernetes container limits map directly onto Linux cgroups v2 files.

1. How Kubernetes Limits Map to Linux cgroups v2

When Kubernetes sets limits.cpu: "500m" on a container, the Linux kernel writes 50000 100000 into /sys/fs/cgroup/cpu.max (50,000µs quota every 100,000µs period = 0.5 vCPU). If quota reads max, CPU is unconstrained. Go 1.25+ natively reads this cgroup limit to pace GOMAXPROCS automatically, whereas Go 1.24 and earlier required third-party automaxprocs to prevent CFS bandwidth throttling.

2. Parameterized SQL (sqlc + pgx) vs Reflection ORMs

Never build SQL strings with fmt.Sprintf—besides inviting SQL injection vulnerabilities, dynamic strings defeat PostgreSQL prepared statement plan caching. Tools like sqlc parse raw .sql queries (with positional placeholders like $1) against your schema migrations and generate zero-reflection, strongly typed Go methods backed by pgx or database/sql.

sqlc_and_cgroup_example.go 
// Safe parameterized query (never concatenate user inputs!)
const getAccountSQL = `SELECT id, balance FROM accounts WHERE id = $1`

row, err := q.db.QueryRowContext(ctx, getAccountSQL, accountID)

// Redis rule of thumb: add randomized jitter to cache TTLs (prevents thundering herd stamps)
// when dozens of pods expire the same hot key simultaneously.

func (q *Queries) GetAccountByID(ctx context.Context, id int64) (AccountRow, error) {
	return q.db.QueryRowContext(ctx, "SELECT id, balance FROM accounts WHERE id = $1", id)
}

func ParseCgroupMaxCores(cpuMax string) (float64, error) {
	fields := strings.Fields(cpuMax)
	if len(fields) != 2 {
		return 0, errors.New("invalid cpu.max format")
	}
	if fields[0] == "max" {
		return 0, nil
	}
	quota, err := strconv.ParseFloat(fields[0], 64)
	if err != nil {
		return 0, err
	}
	period, err := strconv.ParseFloat(fields[1], 64)
	if err != nil || period <= 0 {
		return 0, errors.New("invalid cgroup cpu period")
	}
	return quota / period, nil
}

4. Knowledge Verification Quizzes

Quiz 1 of 2 • Data Access Layer Architecture
Why do senior Go cloud teams prefer generated parameterized queries (sqlc) over string formatting or reflection-heavy ORMs on hot paths?
A Because sqlc bypasses PostgreSQL TCP transactions by executing queries directly inside goroutines.
B Because PostgreSQL rejects any query that is not statically code-generated during compilation.
C Because bound parameters prevent SQL injection while compile-time generation eliminates runtime reflection overhead.
D Because ORMs cannot issue concurrent SQL queries safely across multiple Kubernetes replica pods.
Option A (Incorrect): Generated Go code still communicates normally with PostgreSQL over network connections.
Option B (Incorrect): PostgreSQL executes arbitrary SQL; compile-time checking is enforced by sqlc prior to build.
Option C (Correct): Parameterized $1 queries neutralize injection and preserve query plans, while generated wrappers scan rows without reflection.
Option D (Incorrect): ORMs can execute concurrent queries across pods, though often with extra allocations and hidden SQL queries.
Quiz 2 of 2 • Linux Container Internals
Inside a Kubernetes pod, /sys/fs/cgroup/cpu.max reads 50000 100000 on a 16-core host. What does this signify?
A The pod owns 50% of all 16 host cores, yielding 8 full dedicated vCPUs continuously.
B The pod is throttled to 0.5 vCPU average quota every 100ms scheduling period.
C The Linux OOMKiller will deliver Exit Code 137 when heap size surpasses 500MiB.
D The kernel limits the container to 500 OS processes regardless of thread activity.
Option A (Incorrect): 50000 / 100000 = 0.5 core total across all threads combined, not half of 16 host cores.
Option B (Correct): cgroups v2 cpu.max expresses <quota_us> <period_us>; exceeding 50ms of CPU time in a 100ms window throttles the pod.
Option C (Incorrect): OOMKills are governed by memory.max, whereas cpu.max throttles CPU scheduling rather than killing the process.
Option D (Incorrect): Process counts are governed by pids.max, not cpu.max.
