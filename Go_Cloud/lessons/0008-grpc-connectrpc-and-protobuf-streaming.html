Lesson 0008: High-Throughput gRPC, ConnectRPC, & Streaming Interceptors

For internal service-to-service communication, binary serialization (Protocol Buffers) over HTTP/2 multiplexed streams leaves JSON REST APIs in the dust. However, classical grpc-go carries heavy idiosyncrasies and requires proxy sidecars (like Envoy) to communicate with web clients. In this lesson, we examine modern ConnectRPC, protobuf binary wire framing, and streaming interceptors for zero-overhead telemetry.

⚙️ Senior Architecture Shift: Why ConnectRPC Won in Cloud

ConnectRPC (by Buf) is 100% wire-compatible with standard gRPC, but runs on standard Go net/http.Handler. It natively supports three protocols simultaneously on the same port:
• gRPC over HTTP/2 (for low-latency Go-to-Go service mesh)
• gRPC-Web (for browser clients without Envoy proxies)
• Connect Protocol over HTTP/1.1 or HTTP/3 (JSON or Protobuf) (for curl, REST clients, and edge CDNs)

1. Protocol Buffers: Varints & Field Tags

JSON transmits field names repeatedly on every single request (e.g. {"transaction_id": "tx_99", "amount_cents": 5000}), burning network bandwidth and CPU cycles on text parsing. Protobuf encodes field tags as (Field Number << 3 | Wire Type) followed by base-128 varints (with explicit ZigZag encoding used specifically for signed sint32/sint64 fields):

  • Wire Type 0: Varint (int32, int64, uint32, sint32, bool, enums)
  • Wire Type 2: Length-delimited (string, bytes, embedded messages)
  • Wire Type 1/5: 64-bit / 32-bit fixed numbers

2. Production Interceptors: Telemetry & Auth Pipeline

Interceptors wrap RPC execution with cross-cutting concerns (authentication, OpenTelemetry tracing, panic recovery) in a clean middleware onion model:

interceptor.go Production Unary Interceptor 
package interceptors

import (
    "context"
    "log/slog"
    "time"
    "google.golang.org/grpc"
)

func LoggingInterceptor() grpc.UnaryServerInterceptor {
    return func(
        ctx context.Context,
        req any,
        info *grpc.UnaryServerInfo,
        handler grpc.UnaryHandler,
    ) (any, error) {
        start := time.Now()
        resp, err := handler(ctx, req)
        duration := time.Since(start)

        slog.Info("gRPC Call Completed",
            "method", info.FullMethod,
            "duration_ms", duration.Milliseconds(),
            "has_error", err != nil,
        )
        return resp, err
    }
}

3. Hands-On Practice: ConnectRPC HTTP-Native Rate-Limiting Middleware

Because ConnectRPC exposes standard Go net/http.Handler endpoints, cross-cutting interceptors work directly via composable HTTP middleware returning Connect-compatible status codes over HTTP/1.1, HTTP/2, and HTTP/3:

  • Task 1: Check limiter.Allow(r.URL.Path); when denied, respond with HTTP 429 Too Many Requests, Content-Type: application/json, and body {"code":"resource_exhausted","message":"rate limit exceeded"}.
  • Task 2: Otherwise, delegate the request cleanly to next.ServeHTTP(w, r).

Canonical Reference Solution

package interceptors

import "net/http"

type Limiter interface {
    Allow(procedure string) bool
}

func RateLimitingMiddleware(limiter Limiter, next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        if !limiter.Allow(r.URL.Path) {
            w.Header().Set("Content-Type", "application/json")
            w.WriteHeader(http.StatusTooManyRequests)
            _, _ = w.Write([]byte(`{"code":"resource_exhausted","message":"rate limit exceeded"}`))
            return
        }
        next.ServeHTTP(w, r)
    })
}

4. Architectural Knowledge Check (Senior Level)

Question 1 of 2 • ConnectRPC vs Legacy grpc-go
Why does ConnectRPC provide superior cloud compatibility compared to traditional grpc-go in web environments?
A ConnectRPC natively speaks HTTP/1.1 and JSON without requiring Envoy translation proxies
B ConnectRPC bypasses OS network sockets by routing raw kernel packet rings directly
C ConnectRPC strips TLS encryption layers to minimize cloud network packet serialization cost
D ConnectRPC replaces compact Protobuf schemas with flexible text-based XML payload envelopes
A (CORRECT): Classic gRPC browsers require HTTP/2 trailers via Envoy gRPC-Web proxies; ConnectRPC works directly over standard Go net/http using HTTP/1.1, HTTP/2, HTTP/3, JSON, or Protobuf.
B (INCORRECT): ConnectRPC operates in user space on top of standard Go net/http sockets.
C (INCORRECT): ConnectRPC uses standard HTTPS/TLS 1.3 transport security seamlessly.
D (INCORRECT): ConnectRPC supports both compact binary Protobuf and standard JSON, never XML.
Question 2 of 2 • gRPC Interceptor Role
What is the primary role of a unary interceptor or RPC middleware in cloud microservice architectures?
A Compressing Go heap allocations to skip concurrent garbage collector pause cycles
B Mapping incoming TCP socket reads directly onto Linux OS thread priority queues
C Wrapping handlers with cross-cutting auth, telemetry tracing, and rate limiting
D Verifying relational database foreign-key constraints before executing SQL writes
A (INCORRECT): Reducing heap churn comes from escape analysis and sync.Pool buffers, not interceptor middleware.
B (INCORRECT): Socket scheduling and epoll events live inside the OS kernel and Go runtime netpoller.
C (CORRECT): Unary interceptors and HTTP middleware enforce shared operational logic—auth, OpenTelemetry spans, logging, and rate limits—cleanly around handlers.
D (INCORRECT): Relational integrity belongs to PostgreSQL constraints and data-access repositories.
