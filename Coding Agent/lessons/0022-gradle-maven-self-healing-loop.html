The Gradle & Maven Self-Healing Loop: JVM Diagnostics & Stack Traces

In interpreted Python environments, running tests means executing scripts directly with pytest. In enterprise JVM ecosystems, however, running ./gradlew test initiates a staged build lifecycle: dependency resolution, code generation, compilation, and bytecode execution. In this lesson, you will teach your agent to parse complex Gradle build outputs, sharply distinguish compilation errors from assertion failures, and filter deep JVM stack traces.

Primary Source & Architecture Reference

"Automated Program Repair in the Era of Large Pre-trained Language Models" — Chunqiu Steven Xia, Yuxiang Wei, Lingming Zhang (University of Illinois Urbana-Champaign, ICSE 2023).

Read preprint on arXiv (ICSE 2023, DOI: 10.1109/ICSE48619.2023.00129) → • Core Insight: LLM repair agents fail catastrophically when presented with unparsed raw build logs. Pre-classifying compilation diagnostics versus runtime assertion traces yields a 2.8x higher repair success rate in multi-stage compiled languages.

1. The Two Fundamental JVM Failure Modes

When an autonomous coding agent executes ./gradlew test in a sandbox container, the build can fail in two fundamentally different phases:

Gradle Test Execution Pipeline Failure Mode Decision Branch
PHASE 1

Compilation Phase

Tasks: :compileKotlin, :compileJava. Fails due to syntax errors, missing imports, or type mismatches. Tests never ran!

PHASE 2

Bytecode Assembly

Tasks: :processResources, :classes. Packages compiled .class files and manages classpath assets.

PHASE 3

Test Runner Execution

Task: :test. JUnit/TestNG executes compiled bytecode. Fails with AssertionFailedError or unhandled exceptions.

PHASE 4

Diagnosis Routing

Agent routes compilation errors to syntax/type repair prompt; routes assertion errors to behavioral logic repair prompt.

Why this distinction is vital: If an agent mistakes a compiler error (e: Auth.kt: Unresolved reference: token) for a failing test, it will hallucinate changes to test mock assertions rather than importing the missing symbol in production code!

2. Filtering JVM Stack Trace Noise vs. Signal

A typical Gradle test failure produces over 200 lines of JVM stack trace output. Over 90% of those lines belong to Gradle worker dispatchers, JUnit platform runners, and Java reflection internals: 

// ❌ RAW GRADLE LOG (CONTEXT-POLLUTING NOISE):
com.aegis.AuthServiceTest > testExpiredToken() FAILED
    org.opentest4j.AssertionFailedError: expected: <false> but was: <true>
        at org.junit.jupiter.api.AssertionUtils.fail(AssertionUtils.java:55)
        at org.junit.jupiter.api.AssertTrue.assertTrue(AssertTrue.java:40)
        at com.aegis.AuthServiceTest.testExpiredToken(AuthServiceTest.kt:42)   <-- REAL SIGNAL!
        at java.base/jdk.internal.reflect.NativeMethodAccessorImpl.invoke0(Native Method)
        at java.base/jdk.internal.reflect.NativeMethodAccessorImpl.invoke(NativeMethodAccessorImpl.java:77)
        at org.gradle.api.internal.tasks.testing.junitplatform.JUnitPlatformTestClassProcessor.processTestClass(...)
        at org.gradle.internal.dispatch.ReflectionDispatch.dispatch(ReflectionDispatch.java:36)
        ... [150 MORE LINES OF GRADLE DAEMON REFLECTION FRAMES] ...

A production-grade agent must extract the signal: the exact test method that failed, the assertion comparison, and the single stack frame pointing to the project package (com.aegis.AuthServiceTest.testExpiredToken(AuthServiceTest.kt:42)), dropping all framework reflection junk.

3. Hands-On Interactive Code Practice

Your Challenge: Implement parse_gradle_test_output() below. It analyzes raw Gradle build logs and returns a structured diagnostic envelope:

  • status: "COMPILATION_ERROR", "TEST_FAILURE", or "BUILD_SUCCESS".
  • failed_tasks: List of failed Gradle task paths (e.g., [":compileKotlin"]).
  • compilation_errors: List of compiler diagnostics with file, line, column, and message.
  • failed_tests: List of failed tests capturing test_class, test_method, error_message, and filtered_stack (frames containing project_package_prefix).
