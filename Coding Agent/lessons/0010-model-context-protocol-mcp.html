Model Context Protocol (MCP): Universal Client-Server Tool Architecture

Before late 2024, integrating an AI coding agent with databases, git providers, and internal enterprise APIs required writing bespoke connectors for every single agent harness. Anthropic's open-source Model Context Protocol (MCP) transformed an O(N × M) fragmentation trap into an O(N + M) composable ecosystem. Learn how MCP leverages JSON-RPC 2.0 to standardize Tools, Resources, and Prompts across STDIO and SSE transports.

Primary Source & Architecture Reference

"Model Context Protocol Specification" — Anthropic (Released November 2024 as an open open-source specification).

Official MCP Documentation → • Core Insight: By decoupling host environments (IDEs, CLI tools, Claude Desktop) from tool providers (PostgreSQL, GitHub, local filesystems) via a standard JSON-RPC 2.0 state machine, any tool server instantly works with any MCP-compliant agent.

1. The Fragmentation Crisis: O(N × M) vs. O(N + M)

Consider four agent hosts (Claude Desktop, Cursor, Custom Agent CLI, Antigravity) and five data integrations (Git, PostgreSQL, Slack, AWS, JIRA). Without a universal protocol, developers were forced to build 20 distinct integration adapters.

Architectural Protocol Transition Standardized Interoperability
BEFORE MCP

Proprietary Fragmentation

Every IDE/agent framework defines its own function calling format. Developers re-implement the same Postgres tool 5 times with subtle schema bugs.

WITH MCP

Universal Decoupling

Write an MCP Postgres Server once. Any MCP client host discovers its schemas, runs queries, and streams results over a standard wire protocol.

SECURITY

Process Boundaries

MCP servers run in isolated processes communicating over standard I/O (STDIO) or HTTP Server-Sent Events (SSE), enforcing strict privilege separation.

2. The Three Core MCP Primitives

MCP organizes all context sharing and capabilities into three distinct protocol primitives:

MCP Core Primitives Capability Specification
PRIMITIVE 1

Tools (Executable)

Model-callable functions with side effects (e.g. execute_sql_query, run_git_checkout). Exposes JSON Schema for inputs.

PRIMITIVE 2

Resources (Read-Only)

Passive data context (e.g. postgres://db/schema, file:///logs/today.txt). Client can read or subscribe to real-time updates.

PRIMITIVE 3

Prompts (Workflows)

Pre-packaged prompt templates defined by the server (e.g. "Review Security Audit", "Summarize Git Diff") parameterized with user inputs.

3. The MCP Wire Protocol: JSON-RPC 2.0 In Action

Communication between the MCP Host and Server follows the strict JSON-RPC 2.0 specification. The lifecycle begins with an initialize handshake: 

// 1. Client sends initialize request:
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2024-11-05",
    "capabilities": {},
    "clientInfo": { "name": "AegisAgent", "version": "1.0.0" }
  }
}

// 2. Server replies with supported primitives and version:
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocolVersion": "2024-11-05",
    "capabilities": {
      "tools": { "listChanged": true },
      "resources": {}
    },
    "serverInfo": { "name": "local-git-server", "version": "0.1.0" }
  }
}

After initialization, the agent queries available tools using tools/list and invokes specific functions via tools/call: 

// 3. Client invokes tool:
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "git_diff",
    "arguments": { "staged": true }
  }
}

// 4. Server returns text or embedded binary payload:
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "content": [
      {
        "type": "text",
        "text": "diff --git a/auth.py b/auth.py\n..."
      }
    ],
    "isError": false
  }
}

4. Hands-On Interactive Code Practice

Your Challenge: Implement an in-memory MCPServerHandler that processes incoming JSON-RPC 2.0 requests.

  • Handle method == "initialize": return protocolVersion: "2024-11-05" and server capabilities.
  • Handle method == "tools/list": return registered tool metadata and JSON schemas.
  • Handle method == "tools/call": find tool by name, execute it with params["arguments"], and format content into [{"type": "text", "text": str(output)}].
  • If a method is unknown, return standard JSON-RPC 2.0 error code -32601 ("Method not found").
  • If a called tool does not exist, return an error with code -32602 ("Unknown tool").
