The Self-Healing Test Repair Loop: Localizing Faults via Traceback Parsing

What separates an autonomous AI software engineer from a naive chatbot is the ability to run automated tests, observe failures, pinpoint the exact source code fault, and iteratively repair the defect until the test suite turns green. Discover how to build a closed-loop self-healing state machine powered by targeted pytest traceback parsing.

Primary Source & Architecture Reference

"Self-Debugging: Decoding-Time Self-Correction of Language Models for Code Generation" — Xinyun Chen, Maxwell Lin, Nathanael Schärli, Denny Zhou (Google DeepMind, ICML 2023).

Read paper on arXiv → • Core Insight: Passing targeted, parsed error messages and localized stack frames back to the language model achieves 2x–3x higher repair accuracy than naive re-prompting or dumping unparsed terminal stdout logs into the prompt.

1. The Self-Healing State Machine

An autonomous repair loop is a closed cybernetic feedback cycle that executes deterministically without human intervention:

Self-Healing State Machine Iterative Convergence Protocol
STEP 1

Apply Patch Candidate

Agent generates and writes surgical patch using Search/Replace blocks to the target file.

STEP 2

Execute Test Suite

Runs sandboxed pytest runner. Captures return code, stdout, and stderr.

STEP 3

Parse & Localize Fault

If return code != 0, extract the exact file, line number, and assertion mismatch from the traceback.

STEP 4

Window Slice & Iterate

Read a localized ±15 line window around the fault line and re-prompt the agent with targeted context.

2. The Raw Terminal Dump Failure Mode

In many naive agent implementations, when pytest fails, the system dumps the entire 2,000-line terminal output into the next prompt. This triggers three critical failures:

  • Attention Dilution: In long logs, the actual failing assertion is buried under warnings, deprecations, and module import traces.
  • Context Window Blowout: Repeated failed attempts cause the context window to expand rapidly, pushing out initial task instructions and system prompts.
  • Test File Tampering: If the model is not strictly instructed, it will frequently attempt to "fix" the bug by modifying or deleting the test assertions so the test artificially passes!

3. Anatomy of a Pytest Traceback Frame

Pytest formats test failures with explicit demarcations. Consider this representative output: 

============================= FAILURES =============================
____________________________ test_calculate_tax ____________________________

    def test_calculate_tax():
>       assert calculate_tax(100.0, "CA") == 8.25
E       AssertionError: assert 7.5 == 8.25
E         -7.5
E         +8.25

tests/test_tax.py:18: AssertionError
====================== 1 failed, 14 passed in 0.22s ======================

A high-performance parser extracts four structured fields:

  1. Target File: tests/test_tax.py (or the underlying source module)
  2. Line Number: 18
  3. Exception Type: AssertionError
  4. Failure Detail: assert 7.5 == 8.25

4. Hands-On Interactive Code Practice

Your Challenge: Implement parse_pytest_traceback(). It accepts raw pytest terminal stdout and returns a structured dictionary:

  • If tests passed cleanly (e.g. passed in ... with no FAILURES or ERRORS), return {"status": "PASSED"}.
  • If a failure occurred, extract:
    • status: "FAILED"
    • failing_file: relative path of the failing file
    • line_number: integer line number of the failure
    • exception_type: string (e.g. "AssertionError", "KeyError")
    • failure_message: the actual assertion or exception message (e.g. "assert 7.5 == 8.25")
