Production RAG: Chunking, HNSW Vector Indexing & Cross-Encoder Reranking

Dumping PDFs or architecture docs into a naive cosine similarity script fails quickly in production. Senior AI Engineers build multi-stage RAG pipelines: structure-preserving chunking with overlap, HNSW approximate nearest-neighbor indexes (e.g., pgvector / Qdrant), Cross-Encoder rerankers, and systematic Ragas retrieval metrics.

1. Chunking & HNSW Vector Search Tradeoffs

Embedding models output fixed-size vectors via bi-encoders (query and document encoded separately so documents can be pre-indexed). To scale beyond brute-force O(N) scans, vector stores like Qdrant and PostgreSQL pgvector build HNSW (Hierarchical Navigable Small World) multi-layer proximity graphs delivering ~O(log N) search:

  • m: Bidirectional links per node (higher m improves recall and RAM footprint).
  • ef_construct: Build-time search beam width (higher gives cleaner graph connectivity).
  • hnsw_ef: Query-time beam width (tunable per request to balance p99 latency vs. recall).

2. Bi-Encoder + Cross-Encoder Reranking & RAG Evals

Why can't we use Cross-Encoders everywhere? A Cross-Encoder feeds [query, doc] jointly through full Transformer self-attention—impossible across 10M documents, yet blazingly fast on the top 20–50 candidates returned by HNSW! Finally, frameworks like Ragas evaluate two distinct failure modes separately: Context Recall / Precision (did the retriever find the answer?) vs. Faithfulness (did the LLM stick strictly to retrieved facts without hallucinating?).
