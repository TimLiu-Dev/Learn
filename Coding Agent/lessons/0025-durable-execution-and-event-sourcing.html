Module 9: 2027 Frontier Est. 25 Mins Production Durability

Durable Agent Execution: Event Sourcing, Checkpointing & Resumability

Real-world coding agents tackle long-horizon tasks lasting 30 minutes to several hours across hundreds of tool invocations. If an API rate limit hits, a container restarts, or a human takes hours to approve a diff, an in-memory loop crashes and loses everything. Here, we build Durable Agent Execution using immutable event sourcing and periodic state snapshots.

Primary Source & Architecture Reference

"Temporal: Durable Execution Systems Architecture & Replay Mechanics" — Maxim Fateev et al. (Temporal Technologies) & Martin Kleppmann, Designing Data-Intensive Applications (Event Sourcing & Stream Processing).

Temporal System Architecture Reference → • Core Insight: In durable execution, code execution history is stored as an immutable sequence of events. When a crash or pause occurs, the agent's memory and state machine are deterministically reconstructed by replaying the event stream without re-invoking external tools or burning duplicate LLM tokens.

1. The Fragility of In-Memory Agent Loops

Junior agent implementations maintain state as a mutable Python list: history = [{"role": "user", ...}]. Consider what happens during a real production run:

  • Pod Eviction / OOM / Spot Termination: The worker host is preempted at step 42. The entire history is lost.
  • Asynchronous Human Approval Gates: An agent requests permission to run git push --force. The reviewer is offline for 4 hours. Holding a live server process open in memory leaks file descriptors and blocks worker threads.
  • API Rate Limiting & 429 Backoff: Claude or OpenAI enforces an 8-minute cooldown. In-memory state risks socket timeouts and disconnection.
Event Sourcing vs. Mutable In-Memory State Deterministic Recovery Protocol 
[MUTABLE IN-MEMORY LOOP] (Vulnerable to total state loss):
Process RAM: [Step 1, Step 2, Step 3, Step 4] ──X (Crash / Pod Restart) ──> ALL LOST

[EVENT-SOURCED DURABLE ARCHITECTURE] (2027 Production Standard):
Append-Only Event Stream (WAL / SQLite / Kafka):
Seq 1: SESSION_STARTED  ──> {goal: "Fix Issue #402"}
Seq 2: TOOL_CALLED      ──> {tool: "read_file", path: "jwt.py"}
Seq 3: TOOL_OBSERVED    ──> {cached_stdout: "def verify(): ..."}
Seq 4: STATE_SNAPSHOT   ──> {active_files: ["jwt.py"], tokens_used: 1420} (COMPACTION)
Seq 5: PATCH_PROPOSED   ──> {diff: "+ return token.valid"}
             ─── CRASH OR TIMEOUT OCCURS ───
Recovery: Load Snapshot Seq 4 + Replay Seq 5 ──> ZERO-LOSS RESUME IN 2ms!

2. Handling Non-Determinism During Replay

The foundational law of durable replay: Tool outputs and LLM tokens must be recorded as immutable event payloads during execution, not re-evaluated during replay.

If your agent calls time.time(), queries a database, or runs git diff during step 3, that exact observation must be recorded in event TOOL_OBSERVED. During replay after a restart, the execution engine intercepts the call and serves the recorded event payload instantly, guaranteeing 100% deterministic reconstruction without burning LLM API costs!
