Tree-sitter for Kotlin & Java ASTs: Precision Polyglot Code Extraction

Enterprise engineering systems are rarely pure Python. Over 60% of enterprise backends and Android mobile stacks rely on Kotlin and Java. In this specialization lesson, you will teach your agent runtime to parse Kotlin and Java syntax trees using Tree-sitter: navigating companion objects, data classes, extension functions, Java interfaces, and package dependency graphs with sub-millisecond precision.

Primary Source & Architecture Reference

"Tree-sitter: An Incremental Parsing System for Programming Tools" — Max Brunsfeld (GitHub, 2018) & "Kotlin Grammar Specification" (JetBrains).

Tree-sitter Official Documentation → • Core Insight: Concrete Syntax Trees (CSTs) preserve exact source tokens, whitespace, and syntactic anomalies even when source code is partially broken or mid-edit, allowing agents to accurately index symbols without waiting for heavyweight JVM compiler passes.

1. Why Simple Regex Breaks on Kotlin & Java

In Python, functions start with def foo():. In Kotlin and Java, syntax is vastly richer and more polymorphic:

  • Kotlin Extension Functions: fun User.toDto(format: Format = Format.JSON): UserDto — The function name is preceded by a receiver type, which itself might be parameterized with generics: fun <T> List<T>.customFilter(...): List<T>.
  • Companion Objects: Static members and factory methods in Kotlin are declared inside companion object { ... } blocks rather than with a static keyword.
  • Data Classes & Primary Constructors: data class Account(val id: UUID, var balance: BigDecimal) — Properties and parameters are declared directly on the class signature line without an explicit body block.
  • Java Generic Interfaces: public interface Repository<T, ID extends Serializable> extends CrudOps<T> — Nested angle brackets and bound types cause regex pattern matching to collapse into catastrophic backtracking.

2. Tree-sitter S-Expression Query Mechanics

Tree-sitter provides a Lisp-like pattern matching language (S-expressions) to query syntax trees: 

;; Query 1: Extract all Kotlin class names and primary constructor parameters
(class_declaration
  (simple_identifier) @class.name
  (primary_constructor)? @class.constructor)

;; Query 2: Extract Kotlin extension functions with receiver type
(function_declaration
  (user_type (simple_identifier) @receiver.type)
  (simple_identifier) @function.name
  (function_value_parameters) @function.params)

;; Query 3: Extract companion objects
(companion_object
  (class_body) @companion.body)

By querying syntax nodes instead of matching raw strings, your agent remains completely immune to line breaks, varied whitespace indentation, or nested generic brackets.

3. Hands-On Interactive Code Practice

Your Challenge: Implement parse_kotlin_declarations() below. It parses a Kotlin source file string and extracts structured metadata:

  • package: The package identifier string (e.g. com.aegis.security).
  • imports: List of imported package identifiers.
  • classes: List of dicts with name and kind (e.g., "data class", "class", "interface").
  • companion_objects: List of parent class names containing companion objects.
  • functions: Standard top-level or member functions with name, parameters, and return_type.
  • extension_functions: Extension functions capturing receiver, name, parameters, and return_type.
