TRACK 01 • BARE-METAL C & MEMORY PHYSICS

The Silicon-to-Software Bridge:
Memory Maps, MMIO, Pointer Physics & Register Bitmasking

Every line of software you have ever run on an Android device ultimately boils down to electric potential on physical address bus lines. In this foundational benchmark lesson, we strip away the JVM, the Android Framework, and the Linux kernel to understand how a CPU physically talks to silicon peripherals through pointers, bit manipulation, and memory-mapped hardware registers.

Mental Model Shift: Android JVM/Linux vs Bare-Metal Embedded

In Android App Development, an object reference like val user = User() points to a virtual memory address managed by ART (Android Runtime) and the Linux MMU. You never think about physical RAM chips, page faults are handled silently, and when memory is exhausted, the Garbage Collector kicks in or the OS triggers lowmemorykiller.

In Bare-Metal Systems, there is no MMU, no OS, no garbage collector, and no virtual memory. A pointer like (uint32_t*)0x40004400 is literally wired to the address decoder of a hardware UART or CAN controller. Writing to that address does not store data in RAM—it directly switches physical transistors on an on-chip peripheral.

1. The Physical Memory Map & MMIO Architecture

In modern 32-bit microcontroller architectures (such as ARM Cortex-M0/M3/M4/M7 and RISC-V RV32I), the CPU has a flat 4 Gigabyte (232 bytes) address space ranging from 0x00000000 to 0xFFFFFFFF.

This address space is partitioned into dedicated physical regions defined by the chip architects. This paradigm is known as Memory-Mapped I/O (MMIO).

Connected via I-Code (Instruction) and D-Code (Data) AHB bus. CPU executes instructions directly out of Flash via an on-chip instruction prefetch cache (ART Accelerator). The first 4 bytes hold the Initial Stack Pointer value; the next 4 bytes hold the Reset Handler address!

Because peripherals reside in the standard memory map, we interact with silicon hardware using ordinary C pointer dereferences. There are no special "hardware I/O" instructions like in x86 in/out; a simple pointer store *reg = val; triggers an AHB/APB bus transaction that toggles physical pins.

2. Pointer Physics & The `volatile` Qualifier

One of the most catastrophic bugs in systems engineering occurs when an engineer treats an MMIO register like a normal C variable. Consider this standard polling loop in C:

uart_poll_bug.c — Dangerous Compiler Optimization Hazard 
// Address of the UART Status Register (UART_SR)
uint32_t* uart_status_reg = (uint32_t*)0x40004400;

// Wait until the Transmit Data Register Empty (TXE) bit 7 is set by hardware
while ((*uart_status_reg & (1U << 7)) == 0) {
    // Spin wait...
}

If you compile this with standard release optimization (-O2 or -O3), your device will lock up forever in an infinite loop! Why?

From the compiler's perspective, nobody inside the while loop body modifies *uart_status_reg. The C optimizing compiler assumes the memory contents are unchanged, loads *uart_status_reg into CPU register r0 once before the loop, and rewrites the assembly as:

ARM Cortex-M Disassembly (Optimized without volatile) 
    LDR   r1, =0x40004400    ; Load address of UART_SR
    LDR   r0, [r1]           ; Load value ONCE into r0
    TST   r0, #128           ; Test bit 7
.L_loop:
    BEQ   .L_loop            ; IF zero, branch to .L_loop (INFINITE TRAP!)

The CPU never touches the physical bus again! It checks register r0 repeatedly while the real hardware changes state on the bus undetected.

The Fix: The `volatile` Keyword

The volatile qualifier instructs the compiler: "This memory location can change value outside the control of the program (by hardware or an ISR). Every read and write MUST emit a real bus transaction. NEVER optimize it away or cache it in a CPU register."

Correct Hardware Register Definition 
// Correct: Pointer to VOLATILE memory
volatile uint32_t* uart_status_reg = (volatile uint32_t*)0x40004400;

// Emits an LDR instruction on EVERY single iteration of the while loop
while ((*uart_status_reg & (1U << 7)) == 0) {
    // Hardware updates the register, and the loop safely exits when TXE becomes 1
}
Declaration Meaning in Systems Programming Common Use Case
volatile uint32_t* reg Mutable pointer to a hardware register whose content can change spontaneously. Read/Write peripheral control register (CR).
const volatile uint32_t* reg Read-only pointer to hardware-mutated register (software cannot write, hardware updates). Hardware Status Registers (SR), Pin Input Registers (IDR).
volatile uint32_t* const reg Fixed address pointer to a hardware register (address is constant, content is volatile). Standard industry CMSIS register definitions.

3. Bitwise Manipulation Mechanics (Register Bitmasking)

Hardware control registers are 32-bit bitfields where each individual bit or group of bits controls an exact hardware feature (clock prescaler, parity check, baud rate, interrupt enable).

You must know the four fundamental bitwise operations by muscle memory:

Bitwise Register Operations in C 
/* 1. SET A BIT (Without disturbing other bits) - Use Bitwise OR */
*UART_CR1 |= (1U << 13);    // Sets Bit 13 (UART Enable - UE) to 1

/* 2. CLEAR A BIT (Without disturbing other bits) - Use Bitwise AND with NOT */
*UART_CR1 &= ~(1U << 12);   // Clears Bit 12 (Word length - M) to 0

/* 3. TOGGLE A BIT - Use Bitwise XOR */
*GPIO_ODR ^= (1U << 5);     // Flips State of Pin 5 (e.g. LED Blink)

/* 4. READ-MODIFY-WRITE A MULTI-BIT FIELD (e.g., 3-bit Baud Divisor in bits [8:6]) */
uint32_t mask = (0x7U << 6); // 0b111 shifted to bits 6, 7, 8
uint32_t value = (0x5U << 6);// Desired setting (5 = 0b101)

// Step A: Clear existing bits; Step B: Write new value
*UART_CR1 = (*UART_CR1 & ~mask) | value;
⚠️ Critical Rule: The Read-Modify-Write (RMW) Hazard
When you execute *reg |= (1 << 5);, the CPU executes 3 separate assembly instructions: LDR (read from bus), ORR (modify in ALU), and STR (write back to bus). If an Interrupt (ISR) triggers between the LDR and STR and alters other bits in that same register, its modifications will be silently overwritten! In Lesson 03, we will study ARM Bit-Banding and Atomic Clear/Set registers (BSRR) that prevent this race condition.

4. Professional Register Architecture: Struct Mapping

In production systems (ARM CMSIS, Linux drivers, and Zephyr), engineers do not write individual pointer macros for every register offset. Instead, they model contiguous peripheral register blocks using C Structures:

uart_driver.h — Industry Standard Struct Mapping 
typedef struct {
    volatile uint32_t SR;     // Offset 0x00: Status Register
    volatile uint32_t DR;     // Offset 0x04: Data Register
    volatile uint32_t BRR;    // Offset 0x08: Baud Rate Register
    volatile uint32_t CR1;    // Offset 0x0C: Control Register 1
    volatile uint32_t CR2;    // Offset 0x10: Control Register 2
    volatile uint32_t CR3;    // Offset 0x14: Control Register 3
} UART_TypeDef;

// Cast base hardware address to the struct pointer
#define UART1_BASE   (0x40011000UL)
#define UART1        ((UART_TypeDef*)UART1_BASE)

// Clean, readable hardware access:
void uart_send_byte(uint8_t data) {
    // Wait until TXE (Transmit Empty) bit 7 is set in Status Register
    while ((UART1->SR & (1U << 7)) == 0);
    
    // Write byte to Data Register
    UART1->DR = data;
}

This compiles down to a single base register indexed instruction STR r0, [r1, #4]! Because each member is uint32_t (4 bytes), their alignment perfectly matches the silicon hardware register map offsets 0x00, 0x04, 0x08, 0x0C....

Hardware Register Map Specifications:

  • Control Register 1 (CR1):
    • Bit 13: UE (UART Enable) → Must be set to 1.
    • Bit 3: TE (Transmitter Enable) → Must be set to 1.
    • Bit 2: RE (Receiver Enable) → Must be set to 1.
    • Bit 10: PCE (Parity Control Enable) → Must be cleared to 0 (Disabled).
  • Baud Rate Register (BRR):
    • Must be assigned the exact clock divisor value: 0x1D4C (for 115200 Baud @ 80MHz).
  • Preserve Other Bits: When setting bits in CR1, ensure existing configuration bits are not wiped out!
uart_driver_exercise.c
💡 Progressive Guidance Hints:
Hint 1: Remember to write to struct pointer fields using arrow syntax: uart->CR1 and uart->BRR.
Hint 2: To set multiple bits at once without overwriting existing settings: uart->CR1 |= ( (1U << UART_CR1_UE_BIT) | (1U << UART_CR1_TE_BIT) | (1U << UART_CR1_RE_BIT) );
Hint 3: To clear Bit 10: uart->CR1 &= ~(1U << UART_CR1_PCE_BIT);
✅ Reference Production Solution:
void configure_uart(UART_Regs* uart, uint32_t baud_divisor) {
    // 1. Assign baud divisor to Baud Rate Register
    uart->BRR = baud_divisor;

    // 2. Set UE (Bit 13), TE (Bit 3), and RE (Bit 2) without clobbering other flags
    uart->CR1 |= ( (1U << UART_CR1_UE_BIT) | 
                   (1U << UART_CR1_TE_BIT) | 
                   (1U << UART_CR1_RE_BIT) );

    // 3. Clear Parity Control Enable PCE (Bit 10)
    uart->CR1 &= ~(1U << UART_CR1_PCE_BIT);
}

Senior Systems Note: In automotive standards (like AUTOSAR / MISRA-C), note the explicit use of 1U (unsigned literal). Omitting the U can cause undefined behavior on 32-bit signed shift overflows!

6. Systems Architecture Quizzes

Test your low-level systems mental model with these senior-level interview questions. Click an answer to reveal immediate analysis and explanations for why every option is right or wrong.

Question 1 • Compiler Optimization & Memory
An engineer discovers that their bare-metal program hangs inside an interrupt polling loop when compiled with -O2, but works fine with -O0. What is the fundamental cause?
A. Optimization causes a stack overflow because local variables are stored in the MSP register.
B. The flag or MMIO pointer was not declared volatile; the compiler hoisted the memory load outside the loop into a CPU register.
C. The CPU's instruction cache is disabled, causing memory alignment traps on 32-bit bus lines.
D. The C compiler stripped out the while loop because empty loops are undefined behavior in C99.
✓ Correct! (Option B)
Without the volatile keyword, the optimizing compiler treats memory as static within the loop scope. It reads the hardware status register once into a general-purpose CPU register (like r0) and checks only that register repeatedly in a tight loop. Because the physical bus is never re-read, changes made by hardware or an ISR are never detected.
Analysis of Distractors:
• Option A is wrong: Optimizations actually reduce stack frame usage by keeping variables in registers.
• Option C is wrong: Disabling instruction caches slows down execution, but does not cause memory alignment traps.
• Option D is wrong: A loop polling memory is not an empty loop; the compiler doesn't delete it, it just optimizes the load.
Question 2 • Pointer Arithmetic Physics
Given a 32-bit microcontroller where uint32_t* ptr = (uint32_t*)0x20000004;, what physical address in hex does the expression ptr + 3 evaluate to?
A. 0x20000007
B. 0x2000000C
C. 0x20000010
D. 0x20000014
✓ Correct! (Option C: 0x20000010)
In C pointer arithmetic, adding an integer n scales by the size of the referenced type: new_address = base + (n * sizeof(*ptr)).
Here sizeof(uint32_t) == 4 bytes.
Therefore: 0x20000004 + (3 * 4) = 0x20000004 + 12 (0x0C in hex) = 0x20000010.
Analysis of Distractors:
• Option A (0x20000007) is wrong: This is the classic beginner mistake of adding 3 raw bytes (as if ptr were a uint8_t*).
• Option B (0x2000000C) is wrong: This is 0x20000000 + 12, forgetting the initial base offset of +4.
• Option D (0x20000014) is wrong: This represents ptr + 4.
Question 3 • Memory Alignment & Struct Layout
On an ARM Cortex-M or 32-bit RISC-V processor with 4-byte natural alignment, what is the value of sizeof(DeviceTelemetry)? 
typedef struct {
    uint8_t  sensor_id;   // 1 byte
    uint32_t timestamp;   // 4 bytes
    uint16_t voltage_mv;  // 2 bytes
} DeviceTelemetry;
A. 7 bytes (1 + 4 + 2, exactly the sum of its fields)
B. 12 bytes (due to padding for natural alignment boundaries)
C. 8 bytes (padded to nearest even power of 2)
D. 16 bytes (padded to 64-bit cache line boundary)
✓ Correct! (Option B: 12 bytes)
Let's trace the memory layout byte by byte:
• Byte 0: sensor_id (1 byte).
• Bytes 1, 2, 3: 3 Padding bytes, because uint32_t timestamp requires a 4-byte aligned address (multiple of 4)!
• Bytes 4, 5, 6, 7: timestamp (4 bytes).
• Bytes 8, 9: voltage_mv (2 bytes).
• Bytes 10, 11: 2 Trailing padding bytes, so that array elements of this struct remain properly aligned to the largest member (4 bytes).
Total: 1 + 3 + 4 + 2 + 2 = 12 bytes!
Analysis of Distractors:
• Option A is wrong: That would only be true if explicitly declared with __attribute__((packed)), which causes severe performance degradation or alignment faults on older ARMs.
• Option C and D are wrong: The compiler pads based on the largest alignment requirement (4 bytes), not arbitrary 8 or 16-byte blocks.
