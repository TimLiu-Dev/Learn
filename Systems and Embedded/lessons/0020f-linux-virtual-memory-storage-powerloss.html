Track 04: Non-AOSP Linux Systems • Lesson 0020f

Linux Virtual Memory, Flash Storage
& Power-Loss Atomic Persistence

Embedded Linux devices lose power without warning and run without swap partitions. Senior Linux engineers must understand MMU page tables, page faults, mmap, OOM Killer behavior, read-only SquashFS + OverlayFS, and atomic crash-safe file writes.

Mental Model Shift: Android SharedPreferences vs Embedded Linux Power-Cut Reality

In Android apps, you call DataStore or Room on battery-backed devices with orderly shutdowns.

On headless Embedded Linux, a user yanking the 12 V plug mid-write() leaves half-written files or zeroed configs in page cache unless you write to a temp file, call fsync() on the file, atomically rename(), and fsync() the parent directory!

1. MMU Virtual Memory, Page Cache & OOM Killer

  • Virtual-to-Physical Translation: The ARM/x86 MMU translates 4 KB virtual pages via hardware page tables cached in the TLB. Accessing an unmapped page faults into the kernel: minor faults map existing RAM; major faults read from eMMC/flash.
  • Page Cache & Dirty Pages: Linux buffers file writes in RAM first. Without fsync(), data can sit unsaved for seconds—lost instantly on power cut.
  • No-Swap OOM Prevention: Embedded systems disable swap to avoid destroying eMMC/NAND flash wear cycles. Enforce MemoryMax= in systemd / cgroups v2 so a leaking helper cannot trigger the kernel OOM Killer on critical telemetry daemons.

2. Flash Storage & Atomic Crash-Safe Writes

Production gateways keep the root filesystem immutable (read-only SquashFS + dm-verity, or OverlayFS) and isolate mutable device state on a dedicated partition using the POSIX atomic update pattern:

atomic_persist.c (Power-Loss Safe Config Commit) 
int atomic_write_config(const char *tmp_path, const char *final_path,
                        const void *buf, size_t len, int dir_fd) {
    int fd = open(tmp_path, O_WRONLY | O_CREAT | O_TRUNC, 0600);
    if (fd < 0) return -1;
    if (write(fd, buf, len) != (ssize_t)len || fsync(fd) < 0) {
        close(fd);
        return -1;
    }
    close(fd);
    if (rename(tmp_path, final_path) < 0) return -1;
    return fsync(dir_fd); // Persist directory entry so rename survives power loss
}

int commit_state_atomically(int tmp_fd, const char *tmp_path, const char *final_path, int dir_fd) {
    if (fsync(tmp_fd) < 0) {
        close(tmp_fd);
        return -1;
    }

Knowledge Check

Question 1 • Crash-Safe Storage
Why must an embedded Linux daemon call fsync() on the temporary file before calling rename()?
Renaming files automatically disables MMU virtual address translation hardware globally
Without fsync the renamed target may contain zeroed unwritten blocks
The Linux kernel deletes SquashFS partitions whenever rename runs directly
POSIX requires fsync before rename or compilation fails immediately
✓ Correct! (Option B: Prevent empty/corrupt file after power loss)
If the directory entry updates before the temp file's data pages flush from RAM to eMMC, a sudden power cut leaves the new filename pointing to zeroed or stale blocks.
Analysis of Distractors:
• Options A, C, D: rename() neither disables the MMU nor fails to compile without fsync().
Question 2 • Virtual Memory & OOM
Why do production embedded Linux gateways disable swap partitions and configure cgroups v2 memory limits?
Prevent flash wearout and isolate leaks away from critical daemons
Allow every user application direct unguarded physical register access permanently
Force kernel interrupts to execute inside slower user space threads
Replace standard POSIX file descriptors with dynamic JVM garbage collectors
✓ Correct! (Option A: Protect flash lifespan and contain leaks)
Swapping destroys eMMC/NAND flash endurance and causes huge latency spikes. cgroups v2 (MemoryMax=) ensures a leaky service is killed cleanly without starving safety-critical processes.
Analysis of Distractors:
• Options B, C, D: Unrelated to physical register access, kernel IRQs, or JVM GC.
