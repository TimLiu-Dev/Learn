C++ Foundations for Android Devs:
Value Semantics, References, Namespaces & Casts

In Kotlin, every class instance lives on the heap and variables hold garbage-collected references. C++ defaults to value semantics: objects live directly on the stack or inline inside structs, and assigning copies the bytes unless you explicitly borrow by reference (&). Master these mechanics before touching C++20 templates and AIDL HALs.

Mental Model Shift: Kotlin Object References vs C++ Values & Lvalue References

In Kotlin, passing sensor: SensorConfig passes a reference to a single heap object (or a primitive copy); mutating a var field inside a function mutates the caller's instance.

In C++, passing SensorConfig cfg copies the entire struct by value! To inspect without copying or mutating, pass const SensorConfig& cfg; to mutate a caller variable without nullable pointer syntax, pass SensorConfig& cfg.

1. References (T& / const T&) vs Pointers (T*)

Both C pointers and C++ references pass an address in machine registers under the hood, but C++ references enforce strict compile-time contracts:

  • A reference cannot be null and cannot be reseated: It must be bound to a valid object at initialization and stays bound to that object for its lifetime.
  • Use T* only when nullable or optional (or hardware MMIO addresses): Use const T& for read-only borrowing of structs (> 16 bytes), and T& for intentional out-parameters/mutation. Pass small scalars (uint32_t, bool, std::span) directly by value!
  • Lifetime Trap: Never return a const T& or T& to a local stack variable—the frame pops on return, leaving a dangling reference (Undefined Behavior).

2. Namespaces, enum class, auto & Structured Bindings

cpp_basics.cpp (Modern C++17/20 Idioms Seen in AOSP HALs) 
#include <cstdint>
#include <utility>

// Nested C++17 namespace syntax (matches AOSP AIDL packages in Lesson 0023!)
namespace automotive::power {

enum class RailState : uint8_t { Off = 0, Standby = 1, Active = 2 };

struct Sample {
    uint16_t raw_adc;
    uint8_t  channel;
};

// Function overloading + const reference parameter (zero copy, read-only)
std::pair<bool, int32_t> convert_mv(const Sample& s, int32_t scale_uv) noexcept {
    if (s.channel > 7U) return {false, 0};
    int32_t mv = static_cast<int32_t>((static_cast<int64_t>(s.raw_adc) * scale_uv) / 1000);
    return {true, mv};
}

void poll() noexcept {
    Sample imu{1250U, 2U};
    // Structured binding (C++17): cleanly unpacks pairs/structs
    auto [ok, mv] = convert_mv(imu, 800);
    if (ok && mv > 0) {
        RailState st = RailState::Active; // Scoped: won't pollute global names!
        (void)st;
    }
}

} // namespace automotive::power

3. The 4 C++ Named Casts (Ban C-Style (type)x Casts!)

A C-style cast (int*)ptr silently tries combinations of const_cast, static_cast, and reinterpret_cast, hiding dangerous bugs from code review. Systems C++ uses explicit named casts:

  • static_cast<T>(x): Compile-time checked conversions between numeric types (e.g., uint16_t to int32_t) or up/down a known non-virtual hierarchy (used heavily in Lesson 0016 CRTP).
  • reinterpret_cast<T>(x): Low-level bit/address reinterpretation (e.g., mapping MMIO uintptr_t integers into volatile uint32_t* in Lesson 0013). Dangerous if violating strict aliasing on normal memory objects!
  • const_cast<T>(x): Strips or adds const/volatile (used almost exclusively when calling legacy C APIs that forgot const; mutating a genuinely const object is UB).
  • dynamic_cast<T>(x): Runtime type-checked downcast using RTTI—fails to compile under embedded -fno-rtti and avoided in latency-critical AOSP HALs.

Knowledge Check

Question 1 • Mastery Verification
Why should a C++ firmware function accept a read-only 64-byte configuration struct as const Config& cfg instead of by value Config cfg?
Value parameters automatically trigger garbage collection sweeps across stack frames
Const references avoid copying bytes while blocking caller mutation safely
Struct parameters cannot pass into C++ functions without explicit references
References place all local arguments inside permanent flash memory sections
✓ Correct! (Option B: Zero-copy non-null read-only borrow)
Passing by value copies all 64 bytes onto the callee's stack/registers. Passing const Config& passes only a single address while guaranteeing at compile time that the callee cannot mutate it and the caller cannot pass null.
Analysis of Distractors:
• Option A: C++ has no garbage collector.
• Option C: Structs can be passed by value in both C and C++; it just copies them.
• Option D: A reference parameter itself simply passes an address; it does not move objects to Flash.
Question 2 • Mastery Verification
Which C++ cast explicitly forbids runtime RTTI overhead and fails to compile when you attempt an unrelated pointer-to-integer conversion?
dynamic_cast checks runtime polymorphic type tables inside every call site
reinterpret_cast forces compilers to bypass all address type safety rules
static_cast performs compile-time checked conversions with zero runtime overhead
const_cast validates polymorphism across disconnected C++ hardware interfaces dynamically
✓ Correct! (Option C: static_cast)
static_cast handles well-defined compile-time conversions (numeric widening/narrowing, CRTP base-to-derived casts) with zero runtime metadata and rejects unrelated pointer/integer reinterpretations (which require reinterpret_cast).
Analysis of Distractors:
• Option A: dynamic_cast relies on RTTI metadata and fails to compile under embedded -fno-rtti.
• Option B: reinterpret_cast is specifically for unsafe bit/address reinterpretation (such as MMIO addresses).
• Option D: const_cast only adds/removes const or volatile qualifiers.
