Track 04: Embedded Linux & Kernel • Lesson 0020

Kernel Concurrency & Top/Bottom Halves:
Spinlocks, Waitqueues & Threaded IRQs

In the Linux kernel, long-running operations inside an interrupt handler cause high latency across all CPU cores. In this lesson, we master top/bottom-half interrupt architectures (Threaded IRQs), compare kernel spinlocks with mutexes, and coordinate asynchronous hardware transfers using waitqueues and DMA.

Mental Model Shift: Coroutine Dispatchers vs Linux Kernel Threaded IRQs

In Android app development, background tasks run on coroutine dispatchers or worker threads.

In the Linux kernel, hardware interrupts must be split: The Top Half (hard ISR) acknowledges the silicon interrupt within microseconds and returns IRQ_WAKE_THREAD. The Linux kernel scheduler then wakes the Bottom Half (Threaded IRQ), running as a real kernel process where sleeping, mutexes, and DMA copies are 100% legal!

1. Top Halves vs Bottom Halves (Threaded IRQs)

Modern Linux drivers use request_threaded_irq():

threaded_irq.c (Modern Linux Driver Interrupt Model) 
// TOP HALF: Runs in atomic hard IRQ context (cannot sleep, cannot allocate heap)
static irqreturn_t hard_irq_handler(int irq, void* dev_id) {
    if (hardware_interrupt_pending()) {
        clear_hardware_irq_flag();
        return IRQ_WAKE_THREAD; // Wake up bottom half thread!
    }
    return IRQ_NONE;
}

// BOTTOM HALF: Runs in dedicated kernel thread context (kthread)
static irqreturn_t threaded_irq_handler(int irq, void* dev_id) {
    // Process large data packets, acquire mutexes, and wake up user processes!
    wake_up_interruptible(&driver_wait_queue);
    return IRQ_HANDLED;
}

2. Kernel Concurrency: Spinlocks vs Mutexes

  • Spinlocks (spin_lock / spin_unlock): Busy-wait (polls in a tight loop) with preemption disabled. Safe to use in interrupt context. Must be held for tiny durations (microseconds).
  • Mutexes (mutex_lock / mutex_unlock): Sleepable lock. If the lock is held, the thread is put to sleep and another task executes. Strictly illegal in interrupt context!

3. Check Your Understanding

Question 1 • Kernel Spinlock Mechanics
Why are spinlocks permitted inside hard interrupt contexts where mutexes are forbidden?
Spinlocks poll continuously without putting threads to sleep
Spinlocks compress executable machine instructions inside flash memory
Mutexes disable all nested vectored interrupt controllers permanently
Spinlocks automatically allocate variables inside dynamic system heap
✓ Correct! (Option A: Polls without putting threads to sleep)
Spinlocks do not sleep; they busy-wait with local CPU interrupts disabled, making them safe for atomic interrupt context where sleeping is fatal.
Analysis of Distractors:
• Option B, C, D: Irrelevant to flash compression, disabling NVIC, or heap allocations.
Question 2 • Threaded IRQ Bottom Half Execution
What capability is uniquely available in a Linux threaded IRQ bottom half?
Direct execution from internal silicon boot mask rom
Ability to sleep and acquire sleepable kernel mutexes
Elimination of all physical bus termination pullup resistors
Automatic acceleration of processor clock frequency during run
✓ Correct! (Option B: Ability to sleep and acquire mutexes)
Because the bottom half runs in kernel thread context (kthread), it is scheduled like any normal process and is free to acquire mutexes, sleep, and allocate memory.
Analysis of Distractors:
• Option A, C, D: Unrelated to boot ROM, pullup resistors, or CPU clocks.
