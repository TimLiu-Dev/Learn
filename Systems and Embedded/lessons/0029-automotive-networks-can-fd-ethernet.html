Automotive In-Vehicle Networks:
CAN-FD, 29-Bit Extended IDs, DBC Parsing & SOME/IP

A modern vehicle is a distributed computing cluster of 70 to 150 Electronic Control Units (ECUs) communicating over specialized in-vehicle buses. In this lesson, you will master the physical and data link layers of CAN 2.0B, CAN-FD, bitwise DBC decoding, and high-speed Automotive Ethernet (SOME/IP) that stream real-time telemetry into Android Automotive OS.

Mental Model Shift: Mobile TCP/IP REST vs Automotive In-Vehicle CAN-FD

In Android mobile apps, you communicate over TCP/IP using JSON payloads and HTTP REST APIs. Endpoints have IP addresses, messages can arrive with jitter, and dropped packets are retransmitted minutes later.

On a CAN Bus, there are no IP addresses and no destination headers! Every message is broadcast across a twisted copper wire pair (CAN-H and CAN-L). Collision arbitration is resolved at the physical layer bit-by-bit: lower ID values win physical wire dominance. Telemetry is transmitted cyclically (e.g. speed every 10 ms, battery temperature every 100 ms) encoded in raw bit fields defined by a CAN database (.DBC) file.

1. CAN Physical Layer & Arbitration Physics

CAN uses differential signaling across two wires terminated with 120Ω resistors at each end:

  • CAN_H (CAN High) and CAN_L (CAN Low).
  • Dominant Bit (Logical 0): CAN_H is driven to 3.5V, CAN_L is pulled to 1.5V (Differential voltage = 2.0V). A dominant bit physically overrides any recessive bit!
  • Recessive Bit (Logical 1): Both wires float at 2.5V (Differential voltage = 0V).
CAN Bus Collision ArbitrationPhysical Layer
Node A (ID 0x120: 001 0010 0000) ───┐
                                      ├───► Physical Wire: 001 000... (Node B wins!)
Node B (ID 0x105: 001 0000 0101) ───┘
                       ▲
                       │ At bit 6, Node B drives Dominant (0),
                       │ Node A drives Recessive (1), senses 0 on bus,
                       │ and immediately backs off without corrupting data!

Because lower numerical IDs have more leading zeros (dominant bits), critical safety messages (e.g., Brake Control 0x020) always take precedence over convenience messages (e.g., Climate Temperature 0x450).

2. CAN 2.0 vs CAN-FD (Flexible Data-Rate)

Classic CAN 2.0 was limited to 1 Mbps and 8 bytes of payload per frame. As vehicles introduced advanced ADAS, digital cockpits, and OTA updates, 8 bytes became a massive bottleneck.

Feature Classic CAN 2.0B Modern CAN-FD (ISO 11898-1:2015)
Max Data Rate 1 Mbps (Nominal across whole frame) 5 to 8 Mbps (Data phase accelerated)
Max Payload per Frame 8 bytes 64 bytes
Arbitration ID Length 11-bit (Standard) or 29-bit (Extended) 11-bit (Standard) or 29-bit (Extended)
CRC Robustness 15-bit CRC 17-bit / 21-bit CRC with stuffing bit count

3. CAN Database (.DBC) File Decoding

CAN payloads are raw binary bytes. ECUs use a CAN Database (.dbc) file that acts as the vehicle's telemetry dictionary. Let's inspect a DBC message definition:

vehicle_telemetry.dbcDBC Specification
BO_ 512 VEHICLE_SPEED_REPORT: 8 BRAKE_ECU
 SG_ SPEED_KMH : 0|16@1+ (0.01,0) [0|300] "km/h" AAOS_HEADUNIT
 SG_ WHEEL_SLIP : 16|1@1+ (1,0) [0|1] "" AAOS_HEADUNIT
 SG_ BRAKE_PEDAL_PRESSURE : 24|8@1+ (0.5,0) [0|100] "%" AAOS_HEADUNIT

DBC signal syntax: SG_ Name : StartBit|BitLength@EndiannessSign (Scale,Offset) [Min|Max] "Unit" Receiver.

To compute physical speed:

\[ \text{Physical Speed (km/h)} = (\text{Raw Unpacked Value} \times \text{Scale}) + \text{Offset} \]

If raw bits 0–15 read 0x251C (9500 decimal):

\[ \text{Speed} = (9500 \times 0.01) + 0 = 95.00 \text{ km/h} \]

4. Automotive Ethernet & SOME/IP

For camera feeds, radar sensor fusion, and digital cockpit infotainment, even CAN-FD is too slow. Modern automotive architectures adopt 100BASE-T1 (100 Mbps) and 1000BASE-T1 (1 Gbps) Automotive Ethernet over single unshielded twisted pair (UTP).

On top of UDP/IP, the automotive standard SOME/IP (Scalable service-Oriented MiddlewarE over IP) provides request/response remote procedure calls and publish/subscribe notification streams between the AAOS Head Unit and vehicle domain controllers.

Interactive Systems Workbench: Real-Time CAN Signal Decoder

Implement the C signal unpacking logic for VEHICLE_SPEED_REPORT. The speed signal starts at bit 0, length 16 bits, little-endian, scale = 0.01, offset = 0.0. Given raw CAN payload {0x1C, 0x25, ...}, extract the raw 16-bit unsigned integer and compute the physical float speed.

can_decoder.cValidation Workbench
Hint: Little-endian means byte 0 is the least significant byte (LSB) and byte 1 is the most significant byte (MSB): payload[0] | (payload[1] << 8). Multiply the result by 0.01f.
Reference Solution: 
float decode_vehicle_speed(const uint8_t *payload) {
    uint16_t raw_speed = (uint16_t)payload[0] | ((uint16_t)payload[1] << 8);
    return (float)raw_speed * 0.01f;
}

1. Why does a lower numerical arbitration ID guarantee transmission priority on a shared CAN bus?
Dominant zero bits physically overwrite recessive one bits during physical bus arbitration.
The central vehicle gateway router assigns prioritized time slots based on configuration.
Higher frequency clock oscillators allow earlier packet dispatch over the copper wires.
Software drivers execute preemptive thread interrupts across all connected vehicle nodes.
2. What primary architectural improvement does CAN-FD provide compared to classic CAN 2.0B protocols?
It replaces differential physical wiring pairs with optical fiber communication links completely.
It supports sixty four byte payloads with accelerated data phase transmission.
It routes automotive control packets through external wireless cell towers for validation.
It removes hardware cyclic redundancy checking headers to maximize microcontroller processing speed.
