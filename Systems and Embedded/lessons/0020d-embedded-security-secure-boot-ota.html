Track 04: Non-AOSP Linux Systems • Lesson 0020d

Embedded Linux Security Chain:
Verified Boot, dm-verity, TPM 2.0 & A/B Partitions

Physical devices sit in untrusted environments—parking lots, factories, and homes—where attackers can pull SD cards or probe flash chips. Learn how Senior Systems Engineers establish a hardware-rooted chain of trust from ROM fuses up to a read-only dm-verity rootfs.

Mental Model Shift: Android Verified Boot (AVB) vs Pure Linux Root-of-Trust

In Android, Google's AVB (vbmeta) and Keystore already wire up verified boot and hardware-backed keys for you.

On non-AOSP Embedded Linux, you build that chain: fuse an RSA/ECDSA public key hash into SoC OTP eFuses, verify U-Boot FIT images (kernel + DTB), mount an immutable SquashFS rootfs protected block-by-block with dm-verity, and seal device TLS private keys inside a TPM 2.0 or Secure Element.

1. The Silicon-to-RootFS Chain of Trust

Verified Boot ChainHardware Root of Trust
1. Immutable SoC Mask ROM
   └─► hashes & verifies U-Boot SPL signature against OTP eFuse public key hash
2. Signed U-Boot + FIT Image (Flattened Image Tree)
   └─► verifies Kernel + Device Tree + Initramfs RSA-4096/ECDSA signatures
3. Initramfs mounts Read-Only RootFS via dm-verity
   └─► verifies Merkle tree hash of every 4KB block on-the-fly before execution
4. TPM 2.0 / HSM Unsealing
   └─► releases LUKS /data encryption key & mTLS device identity ONLY if PCR boot hashes match

2. A/B Partition Layout for Zero-Brick Field Devices

Mutable ext4 root filesystems corrupt on sudden power loss. Production Linux gateways separate immutable OS slots (rootfs_a / rootfs_b) from a persistent writable /data partition for logs, configs, and offline telemetry buffers.

Interactive Practice: U-Boot FIT Signature & Slot Selection Policy

Implement select_verified_boot_slot() in C: enforce that a slot is bootable only when its cryptographic signature is valid (sig_ok == true) AND its retry counter (tries_left > 0) is non-zero; fall back from Slot B to Slot A, or return -1 (halt to recovery) if neither passes.

💡 Progressive Guidance Hints:
Hint 1: Write a helper bool valid(BootSlot s) { return s.sig_ok && s.tries_left > 0; }.
Hint 2: Check the preferred slot first; if invalid, check the other slot; if both fail, return -1.
✅ Reference Production Solution:
static bool slot_valid(BootSlot s) {
    return s.sig_ok && s.tries_left > 0;
}

int select_verified_boot_slot(BootSlot a, BootSlot b, int preferred_slot) {
    if (preferred_slot == 1) {
        if (slot_valid(b)) return 1;
        if (slot_valid(a)) return 0;
    } else {
        if (slot_valid(a)) return 0;
        if (slot_valid(b)) return 1;
    }
    return -1;
}

Knowledge Check

Question 1 • Mastery Verification
What protection does Linux dm-verity provide beyond checking a kernel signature once at boot?
Continuously verifies Merkle block hashes detecting offline rootfs flash tampering immediately
Encrypts MQTT telemetry packets using symmetric AES keys during socket writes
Compiles BitBake packages dynamically on the device whenever user binaries crash
Guarantees zero priority inversion inside real time microcontroller interrupt service routines
✓ Correct! (Option A: Per-block Merkle integrity verification)
Even if an attacker pulls the eMMC chip and flips a single byte inside /usr/bin/sshd, dm-verity catches the Merkle hash mismatch on read and returns an I/O error before execution.
Analysis of Distractors:
• Option B, C, D: dm-verity is purely block-level filesystem integrity checking.
Question 2 • Mastery Verification
Why are device TLS private keys stored inside a hardware TPM 2.0 or Secure Element rather than plain files in /etc/certs/?
Linux ext4 filesystems refuse storing PEM text files exceeding two kilobytes
Hardware modules double wireless cellular throughput by skipping elliptic curve signatures
Private keys never leave silicon preventing cloning after physical flash extraction
TPM chips automatically install kernel device drivers during early bootloader startup
✓ Correct! (Option C: Non-exportable hardware key storage)
The TPM signs TLS challenges internally; an attacker who dumps the raw flash chip still cannot extract or clone the device's private identity key.
Analysis of Distractors:
• Option A, B, D: The goal is physical key extraction resistance, not file size or throughput.
