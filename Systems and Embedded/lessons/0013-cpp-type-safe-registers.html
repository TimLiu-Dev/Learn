Zero-Cost Abstractions:
Type-Safe Register Modeling in C++20

In pure C, hardware registers are manipulated with untyped macros and raw bit shifting, where passing the wrong address or shifting a signed integer goes completely undetected by the compiler. In this lesson, we harness Modern C++20 templates and constexpr to catch hardware bugs at compile-time with verified zero runtime overhead.

Mental Model Shift: Kotlin Generics vs C++ Compile-Time Templates

In Kotlin/Java, generics use type erasure: List<User> is compiled into List<Object>, incurring object boxing and runtime casting.

In Modern C++, templates are monomorphized at compile time. A template like Register<0x40011000, uint32_t> evaluates completely during compilation. The emitted assembly is identical to—or more optimized than—raw C pointer dereferences!

1. The Problem with C Register Macros

In C, we commonly write:

Unsafe C Macro Register Definition 
#define UART_CR1 (*(volatile uint32_t*)0x4001100C)
#define SPI_CR1  (*(volatile uint32_t*)0x40013000)

// BUG: Accidentally writing SPI settings into UART register compiles with NO warnings!
UART_CR1 = SPI_CR1_DFF_16BIT;

2. Type-Safe C++20 Register Modeling

We can model registers with distinct C++ types, C++20 concept constraints (catching accidental signed types like int at compile time), and compile-time constants:

Register.hpp (Zero-Overhead C++20 Template) 
#include <cstdint>
#include <type_traits>

template <typename T>
concept RegisterWord = std::is_unsigned_v<T> &&
    (sizeof(T) == 1 || sizeof(T) == 2 || sizeof(T) == 4);

template <uintptr_t Address, RegisterWord T = uint32_t>
struct Register {
    static constexpr uintptr_t addr = Address;

    static void write(T value) noexcept {
        *reinterpret_cast<volatile T*>(addr) = value;
    }

    static T read() noexcept {
        return *reinterpret_cast<const volatile T*>(addr);
    }

    template <T BitMask>
    static void set() noexcept {
        *reinterpret_cast<volatile T*>(addr) |= BitMask;
    }

    template <T BitMask>
    static void clear() noexcept {
        *reinterpret_cast<volatile T*>(addr) &= ~BitMask;
    }
};

// Strongly-typed peripheral register tags
using Uart1_CR1 = Register<0x4001100C>;

// Usage in application:
Uart1_CR1::set<(1U << 13) | (1U << 3)>(); // Emits a single STR instruction!

3. Check Your Understanding

Question 1 • Zero-Cost Abstraction Principles
What is the formal definition of a "zero-cost abstraction" in C++ systems programming?
Features you do not use incur zero runtime overhead
Compiler strips all assembly instructions from final binary output
Firmware executes with zero microamps of electrical battery current
Memory management unit performs automatic garbage collection at runtime
✓ Correct! (Option A: What you don't use you don't pay for)
Bjarne Stroustrup's rule: What you don't use, you don't pay for. And what you do use, you couldn't hand-write in assembly any better!
Analysis of Distractors:
• Option B, C, D: It does not eliminate code, consume zero power, or introduce GC.
Question 2 • Compile-Time Evaluation
What guarantee does the Modern C++ keyword constexpr provide when applied to functions?
Allocates variables exclusively inside the dynamic system heap
Evaluates functions at compile time for constant inputs
Forces compiler to disable all instruction cache lines
Generates interrupt service routines inside vector table entries
✓ Correct! (Option B: Enables evaluation at compile time)
constexpr allows calculations to happen entirely during compilation, replacing complex runtime bit-shift logic with a single immediate numeric constant in the machine code.
Analysis of Distractors:
• Option A, C, D: Unrelated to heap, caches, or vector tables.
