Track 06: Systems Rust & AOSP • Lesson 0028

Modern AIDL HAL in Rust for AOSP:
Zero-Vulnerability Hardware Services

Google introduced Rust into the Android Open Source Project (AOSP) starting in Android 12, and by Android 14/15/16, the majority of new native system daemons and Hardware Abstraction Layer (HAL) services are authored in Rust. In this lesson, you will build a production AIDL HAL in Rust, configure Android.bp, and expose hardware capabilities to Android system services with zero memory corruption risk.

Mental Model Shift: C++ BnInterface vs Rust binder::Interface

In C++ (from Lesson 0023), writing a HAL requires inheriting from BnInterface<ITelemetry>, managing android::sp<T> reference pointers, configuring virtual method tables, and manually ensuring thread safety across Binder worker threads.

In Rust AIDL, the aidl_interface generator produces safe Rust traits. You implement the generated trait on a standard Rust struct wrapped in a thread-safe Sync + Send container. Thread safety across Binder transaction worker threads is guaranteed at compile time by the Rust compiler.

1. The AIDL Interface Definition

Let's define a hardware telemetry interface in AIDL for an automotive telemetry unit:

hardware/interfaces/telemetry/aidl/android/hardware/telemetry/ITelemetry.aidlAIDL
package android.hardware.telemetry;

@VintfStability
interface ITelemetry {
    int getVehicleSpeed();
    float getBatteryTemperature();
    void setWarningBeacon(in boolean active);
}

2. Configuring Android.bp for Rust Backend

In modern AOSP, adding the rust: { enabled: true } flag to aidl_interface instructs Soong to generate Rust bindings in addition to C++ and Java:

hardware/interfaces/telemetry/aidl/Android.bpSoong Build Blueprint
aidl_interface {
    name: "android.hardware.telemetry",
    vendor_available: true,
    srcs: ["android/hardware/telemetry/*.aidl"],
    stability: "vintf",
    backend: {
        cpp: { enabled: false },
        java: { enabled: true },
        ndk: { enabled: true },
        rust: {
            enabled: true,
        },
    },
}

rust_binary {
    name: "android.hardware.telemetry-service.rust",
    relative_install_path: "hw",
    init_rc: ["android.hardware.telemetry-service.rust.rc"],
    vintf_fragments: ["android.hardware.telemetry-service.rust.xml"],
    vendor: true,
    srcs: ["src/main.rs"],
    rustlibs: [
        "android.hardware.telemetry-V1-rust",

3. Implementing the HAL Service in Rust

The generated crate android_hardware_telemetry::aidl::android::hardware::telemetry::ITelemetry defines the trait our struct must implement:

src/main.rsRust AIDL Service
use android_hardware_telemetry::aidl::android::hardware::telemetry::ITelemetry::{
    BnTelemetry, ITelemetry,
};
use binder::{BinderFeatures, Interface, ProcessState, Result as BinderResult};
use std::sync::atomic::{AtomicBool, AtomicI32, Ordering};

struct TelemetryService {
    speed_kmh: AtomicI32,
    warning_active: AtomicBool,
}

impl Interface for TelemetryService {}

impl ITelemetry for TelemetryService {
    fn getVehicleSpeed(&self) -> BinderResult<i32> {
        let speed = self.speed_kmh.load(Ordering::Relaxed);
        Ok(speed)
    }

    fn getBatteryTemperature(&self) -> BinderResult<f32> {
        Ok(42.5) // Sample temperature in Celsius
    }

    fn setWarningBeacon(&self, active: bool) -> BinderResult<()> {
        self.warning_active.store(active, Ordering::SeqCst);
        log::info!("Beacon state updated to: {}", active);
        Ok(())
    }
}

fn main() {
    // Initialize logging
    logger::init(
        logger::Config::default().with_tag_on_device("TelemetryHal"),
    );

    // Create the service instance wrapped in generated Binder stub
    let service = TelemetryService {
        speed_kmh: AtomicI32::new(65),
        warning_active: AtomicBool::new(false),
    };
    let service_binder = BnTelemetry::new_binder(service, BinderFeatures::default());

    // Register with Service Manager
    let service_name = format!("{}/default", TelemetryService::get_descriptor());
    binder::add_service(&service_name, service_binder.as_binder())
        .expect("Failed to register Telemetry AIDL HAL with ServiceManager");

    log::info!("Rust Telemetry AIDL HAL registered successfully.");

    // Join the Binder worker thread pool
    ProcessState::join_thread_pool();
}

Notice how simple this is compared to C++: no manual memory management, no raw pointer casting, and zero possibility of use-after-free vulnerabilities!

1. Which configuration enables automated generation of native Rust bindings inside an AOSP aidl_interface definition?
Enabling the rust boolean flag inside the backend configuration block
Invoking an external shell script inside vendor init launch rules
Writing standard C headers and converting them using bindgen tools
Exporting environment variables before initiating Soong build commands on hosts
✓ Correct! (Option A: backend: { rust: { enabled: true } })
In Android.bp, setting backend: { rust: { enabled: true } } instructs the Soong AIDL compiler to emit strongly-typed Rust traits (like BnTelemetry / ITelemetry).
Analysis of Distractors:
• Option B: init.rc starts daemons at boot, not build-time codegen.
• Option C: Soong generates native Rust bindings directly from .aidl specs without manual bindgen.
• Option D: Environment flags do not enable per-interface AIDL backends.
Question 2 • Mastery Verification
2. What call must a native Rust AIDL daemon execute after registering its service with ServiceManager?
It must restart Zygote daemons to reload active framework components
It must join the Binder thread pool to handle requests
It must fork child workers to flush disk log buffers
It must allocate shared memory segments for SurfaceFlinger compositor buffers
✓ Correct! (Option B: ProcessState::join_thread_pool())
After calling binder::add_service(), the daemon executes ProcessState::join_thread_pool() so the process blocks waiting for incoming Binder IPC transactions instead of exiting main() immediately.
Analysis of Distractors:
• Option A: Vendor HALs never restart Zygote during normal startup.
• Option C: Binder dispatch uses thread pools, not per-log forks.
• Option D: SurfaceFlinger manages graphics buffers independently.
