AOSP 17 Vendor AIDL HAL (C++ & Rust) & Compose UI

Complete the Mid-Level Gate vertical slice on AOSP 17 Cuttlefish: ingest verified telemetry packets from your Raspberry Pi 4 socket/driver, enforce VINTF & SELinux isolation, expose vendor.dev.hardware.fitnesstelemetry side-by-side in C++ & Rust, and feed a 60 FPS Jetpack Compose dashboard.

Mental Model Shift: Raw Byte Stream to Reactive Framework State

In device driver programming, data exists as untyped byte buffers in kernel memory. If a user space app interprets byte offsets incorrectly, data corrupts without compiler warnings.

In AOSP 17 Systems Architecture, your C++ and Rust IFitnessTelemetry vendor AIDL HAL acts as the authoritative type-safe bridge: it reads the binary stream from your Raspberry Pi 4 telemetry daemon (/dev/telemetry_sensor + ESP32-S3 UART), validates CRC-16 checksums, maps raw fields into typed TelemetrySnapshot parcels, and fires AIDL callbacks to Jetpack Compose at 60 FPS!

1. Side-by-Side Rust & C++ Vendor AIDL HAL (IFitnessTelemetry)

In AOSP 17 Cuttlefish, your vendor HAL daemon runs in its isolated SELinux domain, reads verified 16-byte frames from your Phase 5A Raspberry Pi 4 socket, and dispatches updates over /dev/binder. Below is the Rust binder service (paired with your side-by-side C++ libbinder_ndk implementation from Lesson 0023):

vendor/hal/fitnesstelemetry/src/main.rsRust AIDL Service (AOSP 17)
use vendor_dev_hardware_fitnesstelemetry::aidl::vendor::dev::hardware::fitnesstelemetry::{
    IFitnessTelemetry::{BnFitnessTelemetry, IFitnessTelemetry},
    ITelemetryCallback::ITelemetryCallback,
    TelemetrySnapshot::TelemetrySnapshot,
};
use binder::{BinderFeatures, Interface, ProcessState, Result as BinderResult, Strong};
use std::io::Read;
use std::net::TcpStream;
use std::sync::{Arc, Mutex};
use std::thread;

const PI4_TELEM_ADDR: &str = "10.0.2.2:9100"; // Host-forwarded Pi 4 Phase 5A daemon socket
const PACKET_SIZE: usize = 16;
const SYNC_BYTE_0: u8 = 0xAA;
const SYNC_BYTE_1: u8 = 0x55;

struct FitnessTelemetryService {
    callbacks: Arc<Mutex<Vec<Strong<dyn ITelemetryCallback>>>>,
}

impl Interface for FitnessTelemetryService {}
impl IFitnessTelemetry for FitnessTelemetryService {
    fn registerCallback(&self, callback: &Strong<dyn ITelemetryCallback>) -> BinderResult<()> {
        let mut list = self.callbacks.lock().unwrap();
        list.push(callback.clone());
        Ok(())
    }
}

fn start_pi4_socket_reader(callbacks: Arc<Mutex<Vec<Strong<dyn ITelemetryCallback>>>>) {
    thread::spawn(move || {
        let mut stream = TcpStream::connect(PI4_TELEM_ADDR)
            .expect("Failed to reach Phase 5A Pi 4 telemetry daemon");
        let mut buffer = [0u8; PACKET_SIZE];

        loop {
            if stream.read_exact(&mut buffer).is_ok() {
                if buffer[0] != SYNC_BYTE_0 || buffer[1] != SYNC_BYTE_1 {
                    continue;
                }
                let expected_crc = ((buffer[14] as u16) << 8) | (buffer[15] as u16);
                if expected_crc != compute_crc16(&buffer[0..14]) {
                    log::warn!("CRC mismatch! Corrupted telemetry frame dropped.");
                    continue;
                }
                let raw_speed = ((buffer[4] as u16) << 8) | (buffer[5] as u16);
                let snap = TelemetrySnapshot {
                    speedKmh: (raw_speed as f32) / 100.0,
                    busVoltageMv: (((buffer[6] as i32) << 8) | (buffer[7] as i32)),
                    tempCelsius: buffer[9] as i32,
                };
                // Snapshot listeners cleanly, drop Mutex BEFORE Binder IPC to prevent deadlock!
                let active = { callbacks.lock().unwrap().clone() };
                for cb in active.iter() {
                    let _ = cb.onTelemetryUpdate(&snap);
                }
            }
        }
    });
}

2. Jetpack Compose Hardware Telemetry Dashboard (AOSP 17)

A privileged Kotlin Jetpack Compose system app (or framework SystemService client) collects telemetry snapshots from IFitnessTelemetry via Binder and renders smooth 60 FPS gauges:

TelemetryDashboard.ktJetpack Compose (AOSP 17 System App)
@Composable
fun TelemetryDashboard(viewModel: TelemetryViewModel = viewModel()) {
    val speedKmh by viewModel.speedKmh.collectAsStateWithLifecycle()
    val animatedSpeed by animateFloatAsState(
        targetValue = speedKmh,
        animationSpec = spring(stiffness = Spring.StiffnessLow),
        label = "consoleSpeedGauge"
    )

    Box(modifier = Modifier.fillMaxSize().background(Color(0xFF0F172A)), contentAlignment = Alignment.Center) {
        Canvas(modifier = Modifier.size(300.dp)) {
            drawArc(
                color = Color.DarkGray,
                startAngle = 135f,
                sweepAngle = 270f,
                useCenter = false,
                style = Stroke(width = 24.dp.toPx(), cap = StrokeCap.Round)
            )
            val sweep = (animatedSpeed.coerceIn(0f, 240f) / 240f) * 270f
            drawArc(
                brush = Brush.sweepGradient(listOf(Color(0xFF06B6D4), Color(0xFF10B981))),
                startAngle = 135f,
                sweepAngle = sweep,
                useCenter = false,
                style = Stroke(width = 24.dp.toPx(), cap = StrokeCap.Round)
            )
        }

        Column(horizontalAlignment = Alignment.CenterHorizontally) {
            Text(text = "${speedKmh.toInt()}", fontSize = 64.sp, fontWeight = FontWeight.Black, color = Color.White)
            Text(text = "KM / H • LIVE BENCH", fontSize = 14.sp, color = Color(0xFF94A3B8), fontWeight = FontWeight.Bold)
        }
    }
}

Interactive Systems Workbench: Rust VHAL Frame Parser & Dispatcher

Implement the Rust packet verification routine: verify that the packet starts with sync bytes [0xAA, 0x55], unpack the big-endian speed_scaled u16, divide by 100.0, and return the speed as f32. If framing is invalid, return -1.0.

Hint: Check if packet.len() < 6 || packet[0] != 0xAA || packet[1] != 0x55 { return None; }, then let raw = u16::from_be_bytes([packet[4], packet[5]]); and return Some(raw as f32 / 100.0).
Reference Solution: 
pub fn parse_vhal_speed_packet(packet: &[u8]) -> Option<f32> {
    if packet.len() < 6 || packet[0] != 0xAA || packet[1] != 0x55 {
        return None;
    }
    let speed_scaled = u16::from_be_bytes([packet[4], packet[5]]);
    Some((speed_scaled as f32) / 100.0)
}

1. What operational action should the Rust VHAL daemon take if an incoming SPI packet fails CRC-16 verification?
It logs a warning and discards corrupted packets protecting speedometer data
It triggers an immediate Android system reboot across all active processes
It overwrites local flash partitions with zero bytes preventing future reads
It forwards corrupted speeds directly onto dashboard gauges without checksum checks
✓ Correct! (Option A: Drop corrupted frames & warn)
When CRC-16 fails (line noise or torn DMA read), dropping the corrupted packet prevents glitching driver-visible gauges to bogus speeds while recording a diagnostic warning.
Analysis of Distractors:
• Option B: Rebooting the cockpit over one noisy SPI frame would violate availability.
• Option C: Corrupting flash breaks the device.
• Option D: Propagating invalid telemetry violates automotive data integrity.

It redraws view hierarchies synchronously inside dedicated Linux kernel interrupt threads
It interpolates discrete speed states smoothly using hardware accelerated spring animations
