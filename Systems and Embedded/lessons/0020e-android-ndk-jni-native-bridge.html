Android NDK & JNI Bridge:
Zero-Copy Native C/C++/Rust Libraries in Kotlin Apps

You already know Kotlin and Jetpack Compose—now bridge that skill into native systems code. Master how the Android NDK compiles C/C++/Rust .so libraries, how JNI crosses the ART-to-native boundary safely, and how DirectByteBuffer achieves zero-copy telemetry ingestion in Android apps.

Mental Model Shift: ART Garbage-Collected Heap vs Unmanaged Native .so Memory

In pure Kotlin, the ART garbage collector freely moves objects around in memory to compact the heap. Native C/C++/Rust code cannot hold raw pointers to movable JVM objects!

The Java Native Interface (JNI) solves this via pinned handles (jobject local/global refs) and off-heap ByteBuffer.allocateDirect() regions—letting your Kotlin UI share high-speed binary buffers with C++ or Rust without per-frame allocations.

1. Bridging Kotlin external fun to Native C / Rust

native_decoder.c (Zero-Copy DirectByteBuffer JNI Entrypoint) 
#include <jni.h>
#include <stdint.h>

JNIEXPORT jint JNICALL
Java_com_acme_cockpit_NativeBridge_decodeFrameDirect(
        JNIEnv *env, jobject thiz, jobject direct_buf, jint len) {
    (void)thiz;
    const uint8_t *raw = (*env)->GetDirectBufferAddress(env, direct_buf);
    jlong cap = (*env)->GetDirectBufferCapacity(env, direct_buf);

    if (!raw || len < 4 || len > cap) return -1;
    return (jint)(((uint16_t)raw[2] << 8) | raw[3]);
}

2. Four Production JNI Pitfalls

  • Local Reference Table Overflow: Loops creating jstring/jbyteArray without DeleteLocalRef() crash ART (512-ref limit on older threads).
  • Cross-Thread JNIEnv* Bug: JNIEnv* is thread-local! Cache JavaVM* in JNI_OnLoad and call AttachCurrentThread() on native worker threads.
  • C++ Exceptions Crossing JNI: Uncaught C++ exceptions abort the JVM immediately; catch or use -fno-exceptions and throw a Java exception cleanly via ThrowNew.
  • NDK vs Platform AIDL HAL: Unprivileged apps use NDK/JNI for codecs, DSP, or Rust crypto; privileged hardware access goes through AOSP AIDL HALs (Lessons 0021–0028).

int32_t decode_direct_speed(const JNIEnv *env, jobject buf, int32_t len) {
    const uint8_t *ptr = (*env)->GetDirectBufferAddress(env, buf);
    jlong cap = (*env)->GetDirectBufferCapacity(env, buf);
    if (!ptr || len < 2 || len > cap) return -1;
    return (int32_t)(((uint16_t)ptr[0] << 8) | ptr[1]);
}

Knowledge Check

Question 1 • Mastery Verification
Why is caching a JNIEnv* pointer from the Android UI thread and using it inside a native C++ worker thread undefined behavior?
JNIEnv pointers are strictly thread local requiring AttachCurrentThread on native threads
Worker threads in Android lack permission to execute compiled machine code
JNI automatically serializes every native function call through Binder kernel locks
Native worker threads automatically switch CPU endianness inside Android runtime environments
✓ Correct! (Option A: Thread-local JNIEnv)
JNIEnv* contains thread-specific local reference tables and exception slots. Cache JavaVM* globally in JNI_OnLoad() and attach each native thread before calling into Java/Kotlin.
Analysis of Distractors:
• Option B, C, D: Native threads run freely and do not use Binder or change endianness; the constraint is purely JNI thread attachment.
Question 2 • Mastery Verification
When should an engineer build an AOSP AIDL HAL instead of an app-bundled Android NDK .so library?
Whenever computing pure math filters inside ordinary Play Store mobile games
Whenever exposing privileged kernel hardware nodes across isolated system services safely
Whenever linking standard Jetpack Compose animations inside an application view model
Whenever rendering simple offline JSON layouts inside standard consumer screen widgets
✓ Correct! (Option B: Privileged hardware isolation via AIDL HAL)
Unprivileged Android apps cannot open /dev/cockpit_bridge directly under SELinux. AIDL HALs isolate vendor hardware access behind Binder IPC and VINTF stability.
Analysis of Distractors:
• Option A, C, D: In-process math/DSP fits NDK/JNI, while UI belongs in Kotlin/Compose.
