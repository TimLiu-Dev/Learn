Pointers, Object Lifetimes, Array Decay & Null-Terminated C Strings

Pointers are the backbone of C. Master address-of (&), dereference (*), void* byte buffers, the const read-right-to-left rule, stack frame dangling pointers, array-to-pointer decay, and bounds-safe C string handling with snprintf and memcpy.

Mental Model Shift: Kotlin References vs Raw Addresses & Null-Terminated Bytes

In Kotlin, variables hold opaque managed object references guarded by null-safety and the GC, and String tracks its own exact length.

In C, a pointer is simply a raw integer memory address. There is no garbage collector—returning the address of a local stack variable creates an instant dangling pointer bug—and a "C string" is just contiguous bytes terminated by a zero byte ('\0'). Always pass explicit buffer capacities!

1. Pointer Mechanics, void* & The const Reading Rule

pointers_and_const.c 
uint32_t count = 42U;
uint32_t *ptr = &count; // & takes the address of count; * declares a pointer
*ptr = 100U;            // * dereferences ptr, writing 100U into count's RAM slot

// void* holds an untyped generic address (cannot dereference without casting)
void *dma_src = &count;

// Read pointer declarations RIGHT-TO-LEFT around the '*':
const uint8_t *rx_view;        // Pointer to constant uint8_t (can move ptr, cannot edit *rx_view)
uint8_t * const tx_reg = ...;  // Constant pointer to mutable uint8_t (pin fixed to one address!)

// Output parameters use pointers so functions can write back to caller memory:
void split_u16(uint16_t v, uint8_t *hi, uint8_t *lo) {
    if (hi == NULL || lo == NULL) return;
    *hi = (uint8_t)(v >> 8);
    *lo = (uint8_t)(v & 0xFFU);
}

2. Lifetimes & Array-to-Pointer Decay

Inside the scope where an array is declared, sizeof(arr) returns total byte size. The moment you pass that array into a helper function, it decays into a pointer to element 0—the length is erased! Always pass (uint8_t *buf, size_t len) as a pair:

lifetimes_and_decay.c 
// DANGER: Stack-use-after-return! Stack frame vanishes when function exits!
uint32_t *dangling_bug(void) {
    uint32_t local_adc = 512U;
    return &local_adc; // UNDEFINED BEHAVIOR: caller dereferences reclaimed stack!
}

// TRAP: sizeof(pkt) inside this parameter list is sizeof(uint8_t*) == 4 or 8!
void process_packet(const uint8_t pkt[], size_t pkt_len) {
    // Use pkt_len explicitly; never compute sizeof(pkt) inside helper functions!
    for (size_t i = 0; i < pkt_len; i++) {
        uint8_t byte_i = *(pkt + i); // Equivalent to pkt[i], scaled by sizeof(uint8_t)
        (void)byte_i;
    }
}

3. Null-Terminated C Strings vs Kotlin String

In C, char msg[] = "OK"; allocates 3 bytes: 'O', 'K', '\0'. Forgetting space for the trailing '\0' or using unbounded functions (strcpy, sprintf) causes classic buffer overflows. Always use bounded functions like snprintf and strnlen:

bounded_strings.c 
#include <stdio.h>
#include <string.h>

char log_line[16];
// UNSAFE: sprintf(log_line, "ECU_%s", long_str); -> overwrites adjacent SRAM!
// SAFE: snprintf guarantees null-termination and never writes past sizeof(log_line)
int needed = snprintf(log_line, sizeof(log_line), "RPM=%u", 4500U);
if (needed < 0 || (size_t)needed >= sizeof(log_line)) {
    // Handle truncation explicitly!
}

Reference Solution: 
int format_can_tag(char *out, size_t cap, uint32_t node_id) {
    if (out == NULL || cap == 0) return 0;
    int n = snprintf(out, cap, "CAN_%u", node_id);
    if (n < 0 || (size_t)n >= cap) return 0;
    return 1;
}

Knowledge Check

Question 1 • Mastery Verification
Why does passing uint8_t buf[64] to a function make sizeof(buf) shrink to 4 or 8 inside that function?
Array parameters decay implicitly into pointers losing array extent
Stack frames automatically compress trailing zero bytes upon entry
Linker strips unused array elements during final binary emission
Hardware MMU pages limit single function arguments to words
✓ Correct! (Option A: Array-to-pointer decay)
In C function parameter lists, uint8_t buf[64] is syntactic sugar for uint8_t *buf. Calling sizeof(buf) inside the callee returns the size of a pointer (4 bytes on ARM32, 8 bytes on ARM64), never 64!
Analysis of Distractors:
• Option B: Stack frames do not compress byte arrays.
• Option C: Linker dead-code stripping does not shrink sizeof.
• Option D: MMU paging governs memory protection, not C parameter decay rules.
Question 2 • Mastery Verification
Why is returning &local_temp from a C function fatal undefined behavior?
Heap allocator freezes local variables inside read only flash
Returning stack addresses creates dangling pointers once frames unwind
Local variables reside inside CPU registers lacking physical addresses
Global BSS zeroing clears local pointers after function returns
✓ Correct! (Option B: Dangling stack frame pointer)
Non-static local variables live on the stack frame and their lifetime ends at return. The next function call or interrupt overwrites that stack memory silently!
Analysis of Distractors:
• Option A: Local variables live on the stack, not Flash.
• Option C: Taking &local_temp forces the compiler to spill it to a stack address, which still expires on return.
• Option D: .bss zeroing only runs once during startup before main().
