Track 02: Real-Time Operating Systems • Lesson 0009

RTOS Kernel Internals:
Schedulers, Context Switching & Task Control Blocks

A bare-metal superloop (`while(1)`) cannot guarantee microsecond deadlines when juggling multiple sensors, wireless telemetry, and motor control. In this lesson, we enter the world of Real-Time Operating Systems (RTOS), exploring how microkernels multiplex a single CPU core across deterministic concurrent tasks.

Mental Model Shift: Linux/Android Scheduler vs Hard Real-Time RTOS

The Linux kernel inside Android uses CFS (Completely Fair Scheduler). Its goal is fairness and maximum throughput. If a thread is delayed by 15 milliseconds due to background garbage collection, the user might see a dropped UI frame, but no disaster occurs.

In a Hard Real-Time RTOS (like FreeRTOS or Zephyr), fairness is irrelevant. If the airbag controller task or automotive motor control loop misses its 1-millisecond deadline, the system has fatally failed. An RTOS is strictly priority-preemptive: the highest-priority ready task ALWAYS runs immediately.

1. The Task Control Block (TCB) & Task Stacks

In an RTOS, every task is an infinite loop that believes it owns the CPU. Each task is allocated its own private stack in SRAM:

Task Control Block (TCB) Anatomy in C 
typedef struct tskTaskControlBlock {
    volatile uint32_t* pxTopOfStack;   // Must be the first element in the TCB!
    uint32_t           uxPriority;     // Task priority (0 = lowest/idle, 31 = highest)
    uint32_t*          pxStack;        // Base of task's allocated private stack
    char               pcTaskName[16]; // Debug string name
} TCB_t;

2. The Context Switch: Under the Hood

How does the CPU switch from Task A to Task B?

  1. Trigger: The periodic SysTick timer (typically 1 kHz / 1 ms) fires or a high-priority task unblocks. It asserts the ARM PendSV (Pended Service Call) exception.
  2. Hardware Stacking: The ARM core automatically pushes 8 CPU registers (r0-r3, r12, LR, PC, xPSR) onto Task A's stack.
  3. Software Stacking: The PendSV_Handler assembly pushes the remaining registers (r4-r11) onto Task A's stack, then saves the Stack Pointer into Task A's TCB.
  4. Task Switch: The scheduler selects Task B's TCB and loads its stack pointer into the CPU's PSP (Process Stack Pointer).
  5. Unstacking: PendSV_Handler pops Task B's registers. Task B resumes execution exactly where it left off!

✅ Reference Production Solution:
MockTask* rtos_select_next_task(MockTask tasks[], int task_count) {
    MockTask* best_task = NULL;
    int highest_prio = -1;
    for (int i = 0; i < task_count; i++) {
        if (tasks[i].is_ready && tasks[i].priority > highest_prio) {
            highest_prio = tasks[i].priority;
            best_task = &tasks[i];
        }
    }
    return best_task;
}

3. Check Your Understanding

Question 1 • RTOS Context Switching
Which ARM Cortex-M hardware exception is designated for executing RTOS context switches?
The pended service call pendsv exception
The non maskable interrupt nmi exception
The memory management fault memmanage exception
The reset handler power on exception
✓ Correct! (Option A: PendSV exception)
PendSV is configured at the lowest possible interrupt priority. This guarantees that context switches occur only when all urgent hardware peripheral ISRs have completely finished, preventing context switch jitter.
Analysis of Distractors:
• Option B: NMI is reserved for fatal hardware faults (e.g. brownout).
• Option C: MemManage triggers on MPU access violations.
• Option D: Reset handler runs once at boot.
Question 2 • Preemptive Schedulers
What happens when a high-priority task unblocks while a low-priority task is executing?
Low task finishes entire timeslice before yielding
High task preempts low task running immediately
Scheduler terminates low task clearing its stack
Operating system crashes triggering hard fault trap
✓ Correct! (Option B: High task preempts low task running immediately)
In a preemptive RTOS, the instant a higher-priority task unblocks (e.g. from a timer or semaphore), the kernel triggers an immediate context switch to meet real-time deadlines.
Analysis of Distractors:
• Option A: Describes non-preemptive / cooperative scheduling.
• Option C & D: Preemption is a standard operation; tasks are preserved and no faults occur.
