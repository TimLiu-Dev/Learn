Track 05: AOSP Internals & AIDL HALs • Lesson 0023

Modern AIDL HAL Development:
Project Treble & C++ Hardware Abstraction

Before Project Treble, updating Android required rebuilding the entire vendor Board Support Package. In this lesson, we master modern AIDL Hardware Abstraction Layers (HALs), learning how Google transitioned from deprecated HIDL to standardized AIDL across C++, NDK, and Rust backends.

Mental Model Shift: In-Process SDK vs Binderized AIDL HAL

In early Android (versions 1 to 7), hardware HALs were in-process shared libraries (.so) loaded via dlopen() directly into system_server. A single bug or null-pointer in a vendor driver crashed the entire phone!

In modern Android (13/14/15/16), all HALs are Binderized AIDL services running in isolated vendor processes. They communicate across process boundaries using vndservicemanager. If a vendor HAL crashes, the Android system server stays alive and automatically restarts the daemon!

1. The 3 Steps to Authoring an AIDL HAL

Step 1: Define the Interface (IVehicleSensor.aidl)

hardware/interfaces/vehiclesensor/aidl/IVehicleSensor.aidl 
package android.hardware.vehiclesensor;

@VintfStability
interface IVehicleSensor {
    int getSpeedKmh();
    float getBatteryTemperature();
    void setWarningLed(boolean active);
}

Step 2: Implement the C++ Backend

VehicleSensor.cpp (Native HAL Service) 
#include "VehicleSensor.h"
#include <fcntl.h>
#include <unistd.h>

namespace aidl::android::hardware::vehiclesensor {

::ndk::ScopedAStatus VehicleSensor::getSpeedKmh(int32_t* _aidl_return) {
    // Read from kernel character device created in Track 04!
    int fd = open("/dev/telem_bridge", O_RDONLY);
    int32_t speed = 0;
    read(fd, &speed, sizeof(speed));
    close(fd);

    *_aidl_return = speed;
    return ::ndk::ScopedAStatus::ok(); // Success status
}

} // namespace

Step 3: Register with vndservicemanager in service.cpp

Vendor services register with vndservicemanager (the vendor-specific Binder registry) rather than the framework servicemanager:

main.cpp (Daemon Entry Point) 
int main() {
    ABinderProcess_setThreadPoolMaxThreadCount(4);
    auto service = ndk::SharedRefBase::make<VehicleSensor>();
    const std::string instance = std::string(VehicleSensor::descriptor) + "/default";
    
    // Register with vendor Binder namespace
    AServiceManager_addService(service->asBinder().get(), instance.c_str());
    ABinderProcess_joinThreadPool();
    return 0;
}

3. Check Your Understanding

Question 1 • AIDL vs Deprecated HIDL
Why did Android replace HIDL with AIDL HALs starting in Android 13?
Unifies interface definitions across framework ndk and rust
Doubles the maximum physical clock frequency of bus
Eliminates requirement for physical pullup bus termination resistors
Forces nested vectored interrupt controllers into low sleep
✓ Correct! (Option A: Unifies interface definitions across languages)
HIDL required a separate compiler and supported only C++. AIDL now serves as a single unified interface definition language across Java, C++, NDK, and Rust!
Analysis of Distractors:
• Option B, C, D: Unrelated to bus clock frequencies, pullup resistors, or NVIC sleep.
Question 2 • Vendor Service Manager Routing
Which service registry manages Hardware Abstraction Layer daemon bindings?
The standard android application package package manager
The vendor specific vndservicemanager daemon binder registry
The uboot secondary program loader bootloader utility
The nested vectored interrupt controller hardware core
✓ Correct! (Option B: The vndservicemanager daemon)
vndservicemanager manages the /dev/vndbinder device namespace, strictly isolating hardware vendor services from user application access.
Analysis of Distractors:
• Option A: PackageManager manages app APKs.
• Option C & D: U-Boot and NVIC are bootloader and ARM core components.
