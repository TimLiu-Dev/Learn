Track 05: AOSP Internals & AIDL HALs • Lesson 0024

SELinux, SEPolicy & VINTF:
Hardening Android Daemons & Preventing AVC Denials

In Android, even if your native hardware daemon runs as root (UID 0), the Linux kernel will block it from accessing your /dev hardware node unless permitted by SELinux. In this lesson, we master SEPolicy rules, resolve avc: denied crashes, and define Vendor Interface (VINTF) compatibility manifests.

Mental Model Shift: Android App Runtime Permissions vs SELinux MAC

In Android app development, permissions are user-facing prompts (e.g. Manifest.permission.CAMERA) evaluated at the Java framework layer.

In systems engineering, SELinux (Security-Enhanced Linux) is Mandatory Access Control (MAC) enforced directly inside the Linux kernel. Every process has a domain, and every file or socket has a type. If an explicit rule does not permit the interaction, the kernel blocks the system call and emits an avc: denied audit log!

1. The Anatomy of an SEPolicy Rule (.te File)

Every rule in an SELinux policy file follows the structure:

allow <source_domain> <target_type> : <class> { <permissions> };

telem_daemon.te (Vendor Hardware Policy) 
# Define domain for our hardware daemon
type vendor_telem_daemon, domain;
type vendor_telem_daemon_exec, exec_type, vendor_file_type, file_type;

# Associate daemon with HAL domain
init_daemon_domain(vendor_telem_daemon)

# Permit daemon to read/write the kernel character device node
allow vendor_telem_daemon telem_device:chr_file { open read write ioctl };

# Permit daemon to register with vndservicemanager
vndbinder_use(vendor_telem_daemon)

2. Diagnosing avc: denied Crashes

When a driver fails to open in Android, check Logcat/dmesg for audit denials:

Kernel Audit Log (dmesg) 
type=1400 audit(1700000000.123:45): avc: denied { read } for comm="telem_daemon" 
name="telem_bridge" dev="tmpfs" ino=123 scontext=u:r:vendor_telem_daemon:s0 
tcontext=u:object_r:device:s0 tclass=chr_file permissive=0

This log explicitly states: process domain vendor_telem_daemon attempted operation read on target class chr_file, but was denied!

3. VINTF Manifests (manifest.xml)

To ensure compatibility across Treble partitions, the vendor partition declares all supported AIDL interfaces in its VINTF manifest:

vendor/etc/vintf/manifest.xml 
<hal format="aidl">
    <name>android.hardware.vehiclesensor</name>
    <version>1</version>
    <interface>
        <name>IVehicleSensor</name>
        <instance>default</instance>
    </interface>
</hal>

3. Check Your Understanding

Question 1 • SELinux Enforcement vs Root Privilege
What happens when a process running as root UID 0 violates SELinux policy?
Kernel denies access emitting an avc denied audit
Root permissions bypass all mandatory access policy checks
Microcontroller stack pointer automatically grows upward into flash
Operating system scheduler immediately elevates task active priority
✓ Correct! (Option A: Kernel denies access emitting an avc denied audit)
Unlike traditional UNIX permissions where root bypasses checks, SELinux is Mandatory Access Control (MAC). If an explicit allow rule does not exist, the kernel denies root access immediately!
Analysis of Distractors:
• Option B: Root does NOT bypass SELinux in Enforcing mode.
• Option C & D: Unrelated to stack pointer direction or RTOS priorities.
Question 2 • VINTF Compatibility Manifests
What is the primary architectural purpose of Android VINTF compatibility manifests?
Compresses dalvik executable bytecode inside application package archives
Verifies interface compatibility between system and vendor partitions
Eliminates requirement for physical pullup bus termination resistors
Doubles the maximum physical clock frequency of bus
✓ Correct! (Option B: Verifies compatibility between partitions)
VINTF (Vendor Interface) manifests verify that the System partition's framework requirements exactly match the Vendor partition's published HAL interfaces during Over-The-Air (OTA) updates.
Analysis of Distractors:
• Option A, C, D: Unrelated to bytecode, pullups, or clock frequencies.
