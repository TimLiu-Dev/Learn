Atomics & Lock-Free Concurrency:
The Single-Producer Single-Consumer Ring Buffer

In hard real-time systems, Interrupt Service Routines (ISRs) cannot acquire mutexes because an ISR can never block or sleep. In this lesson, we study C++ memory models (relaxed, acquire, release) and build a zero-lock, zero-overhead Single-Producer Single-Consumer (SPSC) ring buffer.

Mental Model Shift: Mutexes vs Lock-Free Atomics

In high-level applications, sharing a list between threads typically uses a Mutex or synchronized block.

In embedded firmware, calling mutex.lock() inside an interrupt causes an immediate crash or deadlock. Lock-free data structures use atomic CPU memory instructions (like ARM LDREX/STREX and DMB memory barriers) to pass streaming sensor telemetry from an ISR to a processing thread with zero locks.

1. The C++ Memory Ordering Models

Modern out-of-order CPUs and optimizing compilers reorder memory reads and writes to maximize pipeline efficiency. C++ std::atomic provides explicit ordering flags:

  • std::memory_order_relaxed: Guarantees atomic read/write, but allows the compiler and CPU to reorder operations before or after it.
  • std::memory_order_release: A store operation. Guarantees that all prior memory writes (like filling a telemetry buffer) are physically committed to memory before this atomic flag is written.
  • std::memory_order_acquire: A load operation. Guarantees that all subsequent memory reads see the data written prior to the matching release store.
  • std::memory_order_seq_cst: Sequential consistency. The strictest (and slowest) full memory barrier.

2. Lock-Free SPSC Ring Buffer Architecture

LockFreeRingBuffer.hpp (Zero-Lock Thread-Safe SPSC) 
#include <atomic>
#include <array>

template <typename T, size_t Capacity>
class SPSCQueue {
public:
    bool push(const T& item) noexcept {
        const size_t current_head = m_head.load(std::memory_order_relaxed);
        const size_t current_tail = m_tail.load(std::memory_order_acquire);

        // Check if buffer is full: (head + 1) % Capacity == tail
        if (((current_head + 1) % Capacity) == current_tail) {
            return false; // Queue full!
        }

        m_buffer[current_head] = item; // Store item

        // Publish head update with release semantics: ensures item data is committed!
        m_head.store((current_head + 1) % Capacity, std::memory_order_release);
        return true;
    }

    bool pop(T& item) noexcept {
        const size_t current_tail = m_tail.load(std::memory_order_relaxed);
        const size_t current_head = m_head.load(std::memory_order_acquire);

        if (current_head == current_tail) {
            return false; // Queue empty!
        }

        item = m_buffer[current_tail]; // Read item

        // Publish tail update with release semantics
        m_tail.store((current_tail + 1) % Capacity, std::memory_order_release);
        return true;
    }

private:
    std::array<T, Capacity> m_buffer{};
    // alignas(64) puts producer & consumer indices on separate cache lines to stop false sharing on SMP cores
    alignas(64) std::atomic<size_t> m_head{0};
    alignas(64) std::atomic<size_t> m_tail{0};
};

Embedded Performance Tip: On small microcontrollers without a hardware divider (e.g., Cortex-M0), pick a power-of-two Capacity and replace % Capacity with bitwise masking & (Capacity - 1), and enforce static_assert((Capacity & (Capacity - 1)) == 0) at compile time.

3. Check Your Understanding

Question 1 • ISR Synchronization Restrictions
Why is taking a standard RTOS mutex strictly illegal inside an Interrupt Service Routine?
Interrupt service routines cannot block or yield execution
Mutex locks consume excessive electrical current during transitions
Compiler strips atomic instructions from all interrupt handlers
Hardware floating point unit enters low power sleep
✓ Correct! (Option A: ISRs cannot block or yield)
If an ISR attempts to take a locked mutex, it cannot sleep or wait for another thread to release it. Attempting to block in an ISR hangs the CPU or triggers an immediate kernel panic.
Analysis of Distractors:
• Option B, C, D: Irrelevant to electrical current, stripping atomics, or the FPU.
Question 2 • Memory Order Acquire/Release
What guarantee does storing an atomic index with memory_order_release provide?
Allocates variables exclusively inside the dynamic system heap
Prior memory writes are visible before atomic store
Disables nested vectored interrupt controller dynamic priority grouping
Generates machine code instructions for flash block erase
✓ Correct! (Option B: Prior memory writes are visible)
Release semantics prevent the compiler and CPU from reordering writes across the barrier. The payload data written into the buffer is guaranteed to be physically visible before the index is updated.
Analysis of Distractors:
• Option A, C, D: Unrelated to heap, NVIC, or flash erases.
