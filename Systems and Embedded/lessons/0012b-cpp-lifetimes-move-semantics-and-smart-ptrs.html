Ownership Without GC:
Rule of Zero/Five, Move Semantics & Smart Pointers

Kotlin lets you allocate freely and wait for the garbage collector. In systems C++, every byte and every kernel file descriptor must have one crystal-clear owner. Learn how destructors, move semantics (std::move), and smart pointers (std::unique_ptr, std::shared_ptr) automate cleanup deterministically.

Mental Model Shift: Kotlin Shared Garbage Collection vs C++ Ownership Hierarchy

In Android apps, five components can hold references to one object and the runtime frees it later on a GC thread.

In Modern C++, prioritize ownership from cheapest to heaviest: (1) Stack value / RAII (bare-metal MCUs), (2) std::unique_ptr (zero-overhead exclusive owner on Linux/AOSP), and (3) std::shared_ptr (atomic reference counting—used sparingly because refcount increments are atomic instructions). Never write raw new/delete in application code!

1. Rule of Zero vs Rule of Five & Move Semantics (&&)

When a class directly owns a raw resource (file descriptor, DMA channel, raw pointer), the compiler's default copy constructor duplicates the handle—causing a catastrophic double-free / double-close when both destructors run:

  • Rule of Zero (Default Goal): Compose classes from RAII members (std::unique_ptr, std::array, nested guards) so you write zero custom destructors, copy ops, or move ops.
  • Rule of Five (Resource Owners): If you must write a custom destructor (~FdGuard()), explicitly declare or = delete the other four: copy constructor, copy assignment, move constructor (T(T&&)), and move assignment (T& operator=(T&&)).
  • std::move(x): Casts x to an rvalue reference (T&&), permitting the destination to steal ownership (zero allocation, just swapping a handle and setting the source handle to -1/nullptr).
move_only_fd.cpp (Deterministic Linux Device Guard — Rule of Five) 
#include <unistd.h>
#include <utility>

class DeviceFd {
public:
    explicit DeviceFd(int fd = -1) noexcept : fd_(fd) {}
    ~DeviceFd() noexcept { reset(); }

    // Non-copyable: prevents double-closing the same kernel descriptor
    DeviceFd(const DeviceFd&) = delete;
    DeviceFd& operator=(const DeviceFd&) = delete;

    // Move-only: transfers ownership in O(1) without touching kernel
    DeviceFd(DeviceFd&& other) noexcept : fd_(std::exchange(other.fd_, -1)) {}
    DeviceFd& operator=(DeviceFd&& other) noexcept {
        if (this != &other) {
            reset();
            fd_ = std::exchange(other.fd_, -1);
        }
        return *this;
    }

    int get() const noexcept { return fd_; }
    void reset(int new_fd = -1) noexcept {
        if (fd_ >= 0) ::close(fd_);
        fd_ = new_fd;
    }
private:
    int fd_;
};

Question 1 • Mastery Verification
What memory bug happens if a class closes a Linux file descriptor inside its destructor without deleting copy operations?
Compiler automatically disables optimization passes across all compilation units
Copying duplicates the descriptor leading to double close bugs
Garbage collector stalls execution while scanning dynamic descriptor tables
Destructors execute on background kernel threads only after process exit
✓ Correct! (Option B: Shallow copy causes double close)
The default copy constructor copies the integer descriptor bit-for-bit. When both objects leave scope, both destructors call close(fd) on the same handle—potentially closing another thread's newly opened descriptor!
Analysis of Distractors:
• Option A: Compilers still optimize normally; the bug is silent semantic corruption.
• Option C & D: C++ destructors run synchronously on the current stack thread with no GC.
Question 2 • Mastery Verification
How does std::unique_ptr<FILE, FileCloser> compare in runtime overhead to std::shared_ptr<FILE> on embedded Linux?
Unique pointer omits heap control blocks and atomic counters completely
Shared pointers eliminate heap allocation using stack only frames
Unique pointers force mutex locks around every pointer dereference operation
Both smart pointers execute background sweep threads at fixed intervals
✓ Correct! (Option A: Zero control-block or atomic overhead)
With a stateless empty deleter struct (FileCloser), sizeof(std::unique_ptr<T, D>) equals a single raw pointer and performs zero heap allocations or atomic refcount increments.
Analysis of Distractors:
• Option B: std::shared_ptr requires a heap control block storing strong/weak atomic counts.
• Option C: Dereferencing std::unique_ptr compiles to a direct pointer load with no locks.
• Option D: Destruction is immediate and deterministic when the owner goes out of scope.
