Track 03: Modern Embedded C++ • Lesson 0012c

No-Exceptions C++:
std::optional/expected, Lambdas & C++20 Concepts

Embedded firmware and Android HALs compile with -fno-exceptions, which means throw is unavailable. Learn what replaces Kotlin try/catch, how C++ lambdas avoid hidden heap allocations, and how C++20 concepts constrain templates cleanly without legacy SFINAE hacks.

Mental Model Shift: Kotlin Exceptions / Result<T> vs Return-Value Errors

In Kotlin apps, failures throw exceptions caught far up the stack. In embedded firmware, unwinding tables bloat Flash and make worst-case interrupt latency unpredictable.

Systems C++ uses explicit value errors marked [[nodiscard]]: std::optional<T> (value or nothing), C++23 std::expected<T, Err> (value or typed error, equivalent to Kotlin Result/Rust Result), and Android Binder's ::ndk::ScopedAStatus.

1. Error Handling Under -fno-exceptions

error_values.cpp (Compile-Time Enforced Return Status) 
#include <cstdint>
#include <optional>

enum class CanErr : uint8_t { Timeout = 1, BusOff = 2 };

// [[nodiscard]] forces compiler warning/error if caller ignores failure!
[[nodiscard]] std::optional<uint32_t> calc_baud_div(uint32_t clk_hz, uint32_t baud) noexcept {
    if (baud == 0U || baud > clk_hz) {
        return std::nullopt;
    }
    return clk_hz / baud;
}

// In C++23 (or embedded backports like tl::expected), return value OR typed error:
// std::expected<uint32_t, CanErr> read_frame() noexcept;

2. Lambdas & Why Embedded Bans Arbitrary std::function

  • Capture-less lambdas [](uint8_t b) { ... }: Convert implicitly to raw C function pointers (void (*)(uint8_t)) with zero heap allocation or state.
  • Capturing lambdas [&ctx](uint8_t b) { ... }: Each lambda has a unique compiler-generated stack closure type; accept it via a template parameter template <typename Fn> to get full inlining!
  • The std::function Trap: Storing large capturing lambdas in std::function<void()> triggers hidden new heap allocations and virtual indirection—avoid inside ISRs or RTOS real-time loops.

3. Templates, if constexpr & C++20 concepts

Old C++11/14 libraries used cryptic SFINAE (std::enable_if) that produced unreadable compiler errors. C++20 concepts express constraints directly:

concepts_baud.cpp (Readable Compile-Time Constraints) 
#include <concepts>
#include <cstdint>

template <std::unsigned_integral RegT>
constexpr RegT set_bits(RegT current, RegT mask) noexcept {
    if constexpr (sizeof(RegT) == 1) {
        return static_cast<RegT>(current | (mask & 0xFFU));
    } else {
        return static_cast<RegT>(current | mask);
    }
}

prescaler_concept.cpp
💡 Progressive Guidance Hints:
Hint 1: Check if (target_hz == 0) return std::nullopt; first to prevent hardware divide-by-zero traps.
Hint 2: Compute return static_cast<T>(clk_hz / target_hz); cleanly without implicit signed conversions.
✅ Reference Production Solution:
template <typename T>
    requires std::unsigned_integral<T>
[[nodiscard]] constexpr std::optional<T> compute_prescaler(T clk_hz, T target_hz) noexcept {
    if (target_hz == 0) return std::nullopt;
    return static_cast<T>(clk_hz / target_hz);
}

Question 1 • Mastery Verification
What does adding [[nodiscard]] onto an embedded C++ driver function returning an error status enforce?
Forces return status values into non volatile EEPROM sectors automatically
Emits a compiler diagnostic whenever callers ignore the returned error value
Enables stack unwinding runtime exceptions inside interrupt service routine handlers
Strips template bounds checks completely during release builds with zero warnings
✓ Correct! (Option B: Compile-time checked return usage)
Under -fno-exceptions, functions signal errors by returning status values (bool, std::optional, std::expected, ScopedAStatus). [[nodiscard]] ensures callers cannot silently drop failure states.
Analysis of Distractors:
• Option A: [[nodiscard]] is purely a compile-time attribute; nothing is written to EEPROM.
• Option C: It has nothing to do with C++ exceptions.
• Option D: It adds warnings rather than stripping checks.
Question 2 • Mastery Verification
Why should real-time C++ callbacks accept a templated callable Fn or stateless function pointer rather than std::function?
Templated callables automatically enable runtime polymorphism across dynamic vtables
Stateless lambdas allocate dedicated heap blocks inside small caches
Function pointers trigger automatic garbage collection between periodic loops
Type-erased wrappers risk dynamic heap allocation and block inlining
✓ Correct! (Option D: Avoids heap allocation & preserves inlining)
std::function performs type erasure that dynamically allocates heap memory when captured state exceeds its small buffer, and calls through an indirect pointer that blocks compiler inlining.
Analysis of Distractors:
• Option A: Templates use static (compile-time) polymorphism, not vtables.
• Option B: Stateless lambdas convert straight to raw function pointers with zero allocation.
• Option C: C++ has no garbage collector.
