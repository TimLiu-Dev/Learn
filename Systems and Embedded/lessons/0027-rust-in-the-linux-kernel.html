Rust in the Linux Kernel:
Safe Abstractions, Kernel Crates & Char Drivers

Linux kernel development has been conducted in C since Linus Torvalds released version 0.01 in 1991. Starting with Linux 6.1 and expanding rapidly in Linux 6.6+ (and Android Common Kernels 6.1/6.6), Rust became the second official language in the Linux kernel. Writing device drivers in Rust eliminates entire classes of kernel vulnerabilities—including use-after-free, double frees, and data races.

Mental Model Shift: C Kernel Unwinding vs Rust Kernel RAII

In classic C kernel drivers (as seen in Lesson 0019), resource allocation requires manual tracking and complex error unwinding via labels: goto err_free_mem; goto err_unregister;. Forgetting a single step leaks kernel memory or leaves dangling hardware hooks.

In Rust for Linux, resource management is automated through RAII and the Drop trait. Kernel mutexes, memory buffers, and device registrations automatically clean up when their wrapper structs go out of scope. Error handling uses standard Rust Result<T, Error> with the ? operator, converting to negative Linux errno values (e.g. -EINVAL, -ENOMEM).

1. The Rust for Linux Architecture

Rust does not replace the C kernel; rather, it sits as a safe abstraction layer on top of existing C kernel subsystems.

Rust for Linux LayeringArchitecture
┌────────────────────────────────────────────────────────┐
│     Your Safe Driver (e.g., rust_sample_misc.rs)       │  Safe Rust
├────────────────────────────────────────────────────────┤
│     kernel crate (safe abstractions: chrdev, sync)     │  Safe API Wrappers
├────────────────────────────────────────────────────────┤
│     bindings crate (bindgen generated FFI headers)     │  Unsafe FFI
├────────────────────────────────────────────────────────┤
│     Linux Kernel C Core (mm, vfs, sched, drivers)      │  Raw C
└────────────────────────────────────────────────────────┘

The kernel crate provides idiomatic Rust equivalents of kernel APIs. Instead of raw struct mutex, you use kernel::sync::Mutex<T>, where the data is physically locked inside the mutex wrapper—making it impossible to access shared state without holding the lock!

2. A Complete Rust Kernel Module

Every Rust kernel module uses the module! macro instead of C's module_init() and module_exit(). Let's inspect a minimal loadable kernel module:

drivers/misc/rust_telemetry.rsRust Kernel Code
use kernel::prelude::*;

module! {
    type: RustTelemetryModule,
    name: "rust_telemetry",
    author: "Systems Engineer",
    description: "Automotive sensor telemetry driver in safe Rust",
    license: "GPL",
}

struct RustTelemetryModule {
    message: String,
}

impl kernel::Module for RustTelemetryModule {
    fn init(_module: &'static ThisModule) -> Result<Self> {
        pr_info!("Rust telemetry driver initialized successfully!\n");
        Ok(RustTelemetryModule {
            message: String::from("CAN-Gateway-Active"),
        })
    }
}

impl Drop for RustTelemetryModule {
    fn drop(&mut self) {
        pr_info!("Rust telemetry driver unloaded and cleaned up.\n");
    }
}

Notice how drop(&mut self) replaces module_exit(). When rmmod rust_telemetry is called, the kernel safely tears down the struct, freeing any allocated buffers automatically.

3. Safe Concurrency with `kernel::sync::Mutex`

In C, a programmer writes: 

mutex_lock(&dev->lock);
dev->speed_kmh = new_speed;
mutex_unlock(&dev->lock);

If an early return statement occurs before mutex_unlock, the kernel deadlocks permanently. In Rust:

Safe LockingRust Kernel Code
struct DeviceState {
    speed_kmh: u32,
    fault_code: u16,
}

struct DriverData {
    state: kernel::sync::Mutex<DeviceState>,
}

fn update_speed(data: &DriverData, new_speed: u32) {
    let mut guard = data.state.lock();
    guard.speed_kmh = new_speed;
    // Mutex automatically unlocks right here when guard drops!
}

The data cannot be touched without lock(), and early returns or errors cannot cause a deadlock because the guard's Drop implementation unlocks the hardware mutex automatically.
