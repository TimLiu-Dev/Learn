Interrupts, NVIC & Low-Level Concurrency

Polling hardware in a while-loop wastes 99% of CPU clock cycles. In this lesson, we study hardware interrupts, the ARM Nested Vectored Interrupt Controller (NVIC), interrupt latency, priority preemption, and how to write race-condition-free code without an operating system.

Mental Model Shift: Coroutines/Dispatchers vs Hardware ISRs

In Android/Kotlin, concurrency is cooperative: viewModelScope.launch(Dispatchers.IO) suspends functions politely and yields thread execution.

In hardware systems, an Interrupt Service Routine (ISR) is brutally preemptive. When an electrical pin changes state, the CPU hardware suspends whatever instruction it was executing within 12 clock cycles, pushes registers onto the stack, and executes the interrupt handler immediately.

1. The Nested Vectored Interrupt Controller (NVIC)

ARM Cortex-M cores include an on-chip hardware interrupt controller called the NVIC:

  • Vectored: The CPU automatically fetches the ISR function address directly from the vector table—no software lookup needed.
  • Nested: A higher-priority interrupt can preempt (interrupt) a currently running lower-priority ISR.
  • Tail-Chaining: If another interrupt is pending when an ISR finishes, the CPU skips restoring and re-saving registers, switching to the new ISR in just 6 clock cycles!

2. Concurrency Hazards: The Read-Modify-Write Race

Consider sharing a counter between an interrupt handler and the main loop:

race_condition.c (Silent Data Corruption) 
volatile uint32_t packet_count = 0;

// Triggered by hardware every time a CAN packet arrives
void CAN_RX_IRQHandler(void) {
    packet_count++;  // In assembly: LDR, ADD, STR
}

void process_packets(void) {
    if (packet_count > 0) {
        packet_count--;  // HAZARD! An interrupt arriving here causes corrupted counts!
    }
}

Because packet_count-- expands into three assembly instructions (LDR, SUBS, STR), if the interrupt fires between LDR and STR, the interrupt's increment is completely wiped out!

The Fix: Critical Sections

To protect shared state, disable interrupts temporarily during non-atomic modifications:

Atomic Critical Section Pattern 
uint32_t primask = __get_PRIMASK(); // Save current interrupt enable state
__disable_irq();                    // Disable interrupts (atomic critical section)

if (packet_count > 0) {
    packet_count--;                 // Safe from interrupt preemption!
}

__set_PRIMASK(primask);             // Restore previous interrupt state

3. Check Your Understanding

Question 1 • Tail-Chaining Optimization
What is the primary benefit provided by ARM NVIC hardware tail-chaining?
Doubles the maximum clock frequency of execution
Reduces latency between consecutive pending interrupt handlers
Enables automatic memory allocation inside dynamic heap
Prevents unaligned memory access usage fault traps
✓ Correct! (Option B: Reduces latency between handlers)
Tail-chaining avoids the overhead of unstacking 8 registers and immediately restacking them when a second interrupt is already pending, cutting transition time to only 6 clock cycles!
Analysis of Distractors:
• Option A: Does not alter CPU clock frequency.
• Option C & D: Unrelated to heap memory or unaligned traps.
Question 2 • Atomic Operations
Why does the single C line counter++ fail to execute atomically on 32-bit ARM?
Compiler disables optimization flags on global variables
Operation compiles into three separate load store instructions
Hardware floating point unit intercepts integer calculations
Interrupt controllers cannot read values from SRAM
✓ Correct! (Option B: Three separate load store instructions)
ARM is a RISC load-store architecture. counter++ emits LDR (read from SRAM into register), ADDS (increment in ALU), and STR (store back to SRAM). An interrupt can preempt between any of these steps!
Analysis of Distractors:
• Option A: Optimizations don't change load-store architecture.
• Option C: FPU does not execute integer increments.
• Option D: Interrupts have full access to SRAM.
