Systems engineers choose containers differently on a 64 KB Cortex-M vs a 16 GB Qualcomm Cockpit SoC. Mental Model Shift: Android Gradle Dependencies vs Dual-Target CMake + Host Tests

In Android apps, you run JVM unit tests on your laptop against Gradle dependencies, while device tests run only on the phone/emulator.

Senior embedded C++ teams separate pure protocol/control logic from silicon registers via interfaces (or CRTP in Lesson 0016), compile it with CMake into an ARM firmware image and a native macOS/Linux GoogleTest binary with -fsanitize=address,undefined!

1. Container Rules: Bare-Metal MCU vs Embedded Linux / AOSP

  • std::array<T, N> & std::span<T>: Zero dynamic allocation; fixed stack/static footprint—mandatory defaults on microcontrollers and hard real-time threads.
  • std::string_view (C++17): Non-owning (const char*, size_t) view with zero heap copies (watch out: never outlive the underlying std::string buffer, and note it is not guaranteed null-terminated!).
  • std::vector::reserve(N) (Embedded Linux / AOSP): Contiguous cache-friendly memory; pre-reserving avoids mid-loop reallocations in Android C++ HAL daemons (Lesson 0023). Avoid pointer-chasing std::list on hot paths!
  • Header-Only Templates vs .cpp Units: Templates (like Lesson 0013's Register) must live in .hpp headers so every translation unit can instantiate them at compile time, whereas non-template methods belong in .cpp files to avoid duplicate symbols.

2. Name Mangling & The extern "C" Bridge

Because C++ supports overloading and namespaces, the compiler mangles function names (e.g., void foo(int) becomes _Z3fooi in ELF symbol tables). Assembly startup tables and C RTOS kernels expect unmangled C symbol names like USART1_IRQHandler!

irq_bridge.hpp / irq_bridge.cpp (Calling C++ From Assembly / C) 
#ifdef __cplusplus
extern "C" {
#endif

// Unmangled C ABI symbol visible to vector_table.s and C RTOS code:
void USART1_IRQHandler(void);

#ifdef __cplusplus
}
#endif

// Inside irq_bridge.cpp: dispatch cleanly to your C++ namespace!
extern "C" void USART1_IRQHandler(void) {
    automotive::uart::on_rx_interrupt();
}

Question 1 • Mastery Verification
Why does omitting extern "C" on an ARM Cortex-M interrupt handler inside a .cpp file break firmware builds at link time?
Assembly startup files require C++ compilers to enable runtime exception tables
C++ name mangling hides the exact symbol expected by the vector table
Compilers refuse putting C++ functions inside non volatile executable flash memory
Linker scripts strip all non templated functions unless marked volatile
✓ Correct! (Option B: C++ mangles symbol names)
The startup vector table references weak C symbol names (such as CAN1_RX_IRQHandler). A mangled C++ symbol fails to override the weak default handler, leaving interrupts routing to an infinite dummy loop!
Analysis of Distractors:
• Option A: Startup vector tables have nothing to do with exception tables.
• Option C & D: C++ functions live in Flash .text cleanly once linkage matches.
Question 2 • Mastery Verification
What critical lifetime bug occurs when a function returns a std::string_view pointing to a local std::string created inside that function?
Returning a string view secretly forces heap deep copies across callers
String views automatically reject read only text literals during template instantiation
Destroying the local string leaves a dangling non owning character pointer
Local destructors delay releasing dynamic memory until background sweepers terminate execution
✓ Correct! (Option C: Dangling non-owning view)
std::string_view does not own memory or extend lifetimes. When the local std::string is destroyed at function return, the returned view points to freed memory (caught immediately by AddressSanitizer in CMake host tests!).
Analysis of Distractors:
• Option A: std::string_view never allocates or copies characters.
• Option B: String literals have static storage duration and are the safest possible backing for std::string_view.
• Option D: Destruction is synchronous and immediate on return.
