Edge Wire Serialization:
Protobuf (nanopb / prost), CBOR & Schema Evolution

Sending verbose JSON strings over cellular LTE-M or satellite links wastes battery, RAM, and bandwidth—and breaks silently when firmware versions skew across a fleet. Master zero-heap Protobuf (nanopb on MCUs, prost in Rust, Go structs) and CBOR.

Mental Model Shift: Android Moshi/Gson JSON vs Binary Schema Contracts

In Android apps, JSON over HTTPS with reflection-based parsers works because phones have gigabytes of RAM and broadband Wi-Fi.

On an MCU or Edge Gateway, reflection does not exist and malloc is forbidden. A .proto schema compiles ahead-of-time into fixed C structs (nanopb), zero-copy Rust structs (prost), and Go structs—shrinking a 140-byte JSON payload to 18 binary bytes with backward-compatible field tags!

1. One .proto Contract Across C, Rust, and Go

telemetry.proto (Shared Edge-to-Cloud Schema) 
syntax = "proto3";
package telemetry.v1;

message VehicleTelemetry {
  uint32 seq = 1;           // Varint tag 1
  uint32 speed_cm_s = 2;    // Fixed-point avoids float mismatch
  uint32 rpm = 3;
  int32 battery_temp_c = 4; // Sint32/int32 ZigZag or varint
  uint64 timestamp_ms = 5;
}

Knowledge Check

Question 1 • Mastery Verification
Why do Protobuf fields use numeric tags (= 1, = 2) instead of transmitting ASCII field names like JSON?
Numeric tags minimize payload bytes while preserving forward and backward schema compatibility
Embedded C compilers prohibit string literals inside header files across firmware modules
MQTT brokers reject TCP connections whenever payloads contain valid UTF-8 ASCII characters
Numeric tags encrypt binary telemetry automatically without needing hardware TLS certificates anywhere
✓ Correct! (Option A: Compact wire tags + safe schema evolution)
A field tag takes 1 byte on the wire, and older cloud consumers or firmware skip unknown tags safely without breaking existing fields.
Analysis of Distractors:
• Option B, C, D: Protobuf provides compact encoding and schema evolution, not encryption or MQTT constraints.
Question 2 • Mastery Verification
Why is nanopb preferred over standard Google C++ libprotobuf on Cortex-M microcontrollers?
Standard C++ protobuf strictly requires an active Java Virtual Machine process
Standard C++ protobuf only compiles properly on Windows desktop host workstations
nanopb encodes fixed stack buffers with zero heap and tiny flash
nanopb bypasses UART and SPI peripherals writing directly to cloud databases
✓ Correct! (Option C: Zero-heap, tiny ROM/RAM footprint)
Standard libprotobuf relies heavily on dynamic allocation, reflection tables, and RTTI (~hundreds of KB), whereas nanopb runs in ~5 KB ROM with zero malloc().
Analysis of Distractors:
• Option A, B, D: It's strictly about MCU flash/RAM constraints and deterministic no-heap execution.
