TrustZone-M (TF-M), MCUboot BLE DFU
& ESP32-S3 Virtual eFuses

Isolate cryptographic device identities inside the nRF54L15-DK's Arm Cortex-M33 Secure Processing Environment (TF-M), ship signed/anti-rollback BLE DFU packages from your Android phone, export west spdx SBOMs, and mirror Secure Boot v2 safely on your ESP32-S3 using virtual eFuses.

Critical Safety Rule: NEVER Burn Real eFuses on Your Only ESP32-S3

Silicon OTP eFuses on the ESP32-S3 are physically irreversible—burning Secure Boot / Flash Encryption keys permanently locks out unsigned flashing or bricks the board if a key is lost.

During lab exercises, enable CONFIG_EFUSE_VIRTUAL=y (and CONFIG_EFUSE_VIRTUAL_KEEP_IN_FLASH=y) so ESP-IDF emulates Secure Boot v2 & flash encryption without touching real hardware fuses.

1. Cortex-M33 TrustZone & Trusted Firmware-M (TF-M)

  • Secure (SPE) vs Non-Secure (NSPE): Hardware SAU/IDAU partitions Flash, SRAM, and peripherals. Private keys live exclusively inside SPE Internal Trusted Storage (ITS)—even a compromised Zephyr Bluetooth task in NSPE cannot read the raw key bytes!
  • PSA Crypto Calls Across the NSC Gate: Non-secure firmware passes a psa_key_id_t handle across a Non-Secure Callable (NSC) veneer into TF-M, calling psa_sign_message() so SPE signs telemetry payloads and returns only the ECDSA signature.

2. Signed A/B BLE DFU + west spdx SBOM

nRF54L15-DK MCUboot + TF-M + Android DFU Verification Flow 
1. west build -b nrf54l15dk/nrf54l15/cpuapp/ns --sysbuild
   -> Compiles MCUboot + TF-M (SPE) + Zephyr App (NSPE), signs Slot A/B with ECDSA-P256.
2. west spdx -d build  -> Generates SPDX 2.2 Software Bill of Materials for supply-chain audit.
3. Android Phone (nRF Connect Device Manager Kotlin app) pushes over MCUmgr/SMP BLE:
   - Corrupted payload   -> MCUboot SHA-256/ECDSA check fails -> rejected before swap!
   - Downgraded sec_ver  -> Anti-rollback check fails -> rejected!
   - Valid image w/o confirm -> Watchdog/reboot reverts back to known-good Slot A!

Interactive Practice: Non-Secure PSA Crypto Call Guard

Inside a TF-M Secure partition service, validate a pointer buffer passed from the Non-Secure world before signing: reject msg == NULL, msg_len == 0, or out_sig_size < 64U (ECDSA-P256 signature), and require psa_ns_range_ok == true (representing SAU/IDAU non-secure memory verification so NS cannot trick SPE into reading Secure RAM).

Hint 1: Check if (msg == NULL || msg_len == 0U || out_sig_size < 64U) return -1;.
Hint 2: Check if (!psa_ns_range_ok) return -2; to stop NS code from pointing SPE at Secure secrets.
✅ Reference Production Solution:
int tfm_validate_ns_sign_request(const uint8_t *msg, size_t msg_len,
                                 size_t out_sig_size, bool psa_ns_range_ok) {
    if (msg == NULL || msg_len == 0U || out_sig_size < 64U) return -1;
    if (!psa_ns_range_ok) return -2;
    return 0;
}

Question 1 • TrustZone-M Key Isolation
When running Zephyr BLE in the Non-Secure Processing Environment (NSPE) alongside TF-M on your nRF54L15-DK, what happens if a buffer overflow compromises the BLE stack?
Attacker dumps private keys directly from Internal Trusted Storage
Hardware SAU blocks Non-Secure reads into Secure key memory
MCUboot automatically burns permanent eFuses during the next reset
PSA Crypto shifts all private keys into external PSRAM
✓ Correct! (Option B: Hardware SAU/IDAU enforces isolation)
Any Non-Secure memory read into Secure Flash/RAM triggers a hardware SecureFault! The attacker can at most ask TF-M to sign data via the constrained PSA API, never extract the private key bytes.
Analysis of Distractors:
• Options A, C, D: ITS sits in Secure Flash protected by SAU/MPC, MCUboot never burns eFuses on faults, and nRF54L15 keeps keys inside Secure NVM.
Question 2 • ESP32-S3 Secure Boot Lab Safety
Why should you enable CONFIG_EFUSE_VIRTUAL when practicing Secure Boot v2 and flash encryption on your ESP32-S3 devkit?
Virtual eFuses double the dual-core CPU clock frequency
Real eFuses only work over Bluetooth Low Energy
Real eFuses burn permanently and risk locking boards
Virtual eFuses disable PSRAM pins thirty-five through thirty-seven
✓ Correct! (Option C: Real silicon eFuses are one-time programmable)
Once real eFuse bits blow, they cannot be cleared; losing the signing key or misconfiguring flash encryption modes permanently locks your single devkit.
Analysis of Distractors:
• Options A, B, D: Virtual eFuses don't change CPU clock, real eFuses are burned via UART/esptool, and PSRAM pin wiring is unrelated.
