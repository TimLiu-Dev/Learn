Fail-Safe A/B OTA Updates:
MCUboot, RAUC & Automatic Watchdog Rollback

Bricking 10,000 fielded devices with a bad firmware push can bankrupt a hardware company. Master cryptographically signed A/B updates across MCUs (MCUboot), Embedded Linux (RAUC / Mender), and Android (update_engine)—including trial-boot self-tests and anti-rollback counters.

Mental Model Shift: App Store APK Replacement vs Dual-Slot Atomic Rollback

On Android phones, Google Play updates an app while the OS keeps running underneath; if the app crashes, you just ship a patch.

In Embedded OTA, you are replacing the bootloader, kernel, or firmware itself. Power can vanish mid-flash, or the new image may kernel-panic before starting the network! Dual Slot A / Slot B partitioning + hardware watchdogs ensure the device automatically boots back to the previous known-good slot without human intervention.

1. The Universal A/B Trial-Boot State Machine

OTA LifecycleMCUboot / RAUC / update_engine
1. Running on Slot A (confirmed = true, version = 1.4.0)
2. Agent downloads v1.5.0 bundle -> verifies Ed25519/ECDSA signature + anti-rollback (1.5.0 >= min_sec_ver)
3. Agent writes v1.5.0 into inactive Slot B (zero impact if power fails mid-download!)
4. Agent marks Slot B = "TEST / PENDING" with boot_attempts = 3, then reboots
5. Bootloader arms Hardware Watchdog (30s) and boots Slot B
   ├─► Self-Check PASS (CAN + MQTT broker reachable): App calls mark_slot_confirmed()
   └─► Self-Check FAIL / Crash / Watchdog Reset (after 3 tries): Bootloader reverts to Slot A!

bool accept_ota_manifest(uint32_t new_sec_ver, uint32_t min_sec_ver, bool sig_valid) {

Question 1 • Mastery Verification
In a newly flashed Slot B trial boot, what must succeed before the OS marks Slot B as permanently confirmed?
The inactive Slot A partition must first be completely zeroed out
Core application health checks and cloud connectivity must pass cleanly first
A human technician must physically press a recovery button on board
The MCUboot bootloader disables the hardware watchdog permanently across future boots
✓ Correct! (Option B: End-to-end health + connectivity self-test)
If an update boots the kernel but breaks the Ethernet/MQTT daemon, confirming prematurely would strand the device unable to receive a fix! Confirm only after proving the OTA agent itself can still reach the cloud.
Analysis of Distractors:
• Option A, C, D: Keeping Slot A intact and keeping the watchdog active is the heart of autonomous rollback.
Question 2 • Mastery Verification
What security threat does an eFuse/OTP hardware monotonic anti-rollback counter prevent?
Prevents DMA controllers from reading uncached RAM buffers across peripheral buses
Prevents MQTT subscribers from decoding valid Protobuf messages during normal operation
Prevents Linux threads from sleeping inside non blocking epoll wait loops
Prevents attackers from flashing older legitimately signed images with known CVEs
✓ Correct! (Option D: Downgrade attack protection)
Even though an old v1.0 firmware carries a valid vendor signature, bumping the hardware monotonic security counter after patching a CVE ensures the bootloader refuses v1.0 forever.
Analysis of Distractors:
• Option A, B, C: Anti-rollback protects strictly against re-flashing old vulnerable signed binaries.
