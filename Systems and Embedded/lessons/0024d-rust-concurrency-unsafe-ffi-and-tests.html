Fearless Concurrency & FFI:
Send/Sync, Smart Pointers, unsafe & Cargo Tests

Systems Rust never executes in isolation: bare-metal drivers write hardware MMIO pointers, Linux drivers wrap C kernel structs, and AOSP Binder HALs dispatch concurrent RPCs across threads. Master Arc<Mutex<T>>, Send/Sync, the exact boundaries of unsafe FFI, and Cargo #[test] suites.

Mental Model Shift: Runtime Locks vs Compile-Time Send & Sync

In Java/Kotlin or C++, passing a non-thread-safe object into a background thread pool compiles cleanly and crashes weeks later in production under race load.

In Rust, types implement marker traits Send (safe to move across thread boundaries) and Sync (safe to share &T concurrently from multiple threads). Because AOSP's Binder pool invokes your HAL from worker threads simultaneously, your service struct must be Send + Sync—using Atomic* or Mutex<T> instead of plain unprotected fields!

1. Smart Pointers & Data-Inside-The-Lock (Mutex<T>)

  • Box<T>: Unique heap allocation (analogous to C++ std::unique_ptr<T>; unused on heapless MCUs, common on Linux/AOSP).
  • Rc<T> vs Arc<T>: Reference-counted shared ownership (like C++ shared_ptr). Rc<T> is non-atomic (!Send — single-thread only). Arc<T> uses atomic counts (thread-safe).
  • Mutex<T> / RwLock<T> / mpsc::channel: Unlike C/Kotlin where mutexes sit beside fields, Rust's Mutex<T> physically wraps T. You literally cannot read or write T without locking first! Always drop the returned guard before making blocking IPC calls.

2. The 5 Rules of unsafe, #[repr(C)] FFI & Safe Abstractions

An unsafe { ... } block does not turn off the borrow checker; it unlocks strictly five operations where the programmer must verify safety invariants (documented with // SAFETY: comments) and wrap them behind a safe public API:

  1. Dereferencing a raw pointer (*const T / *mut T).
  2. Calling an unsafe fn or C FFI function (extern "C").
  3. Accessing or modifying a mutable static variable.
  4. Implementing an unsafe trait (e.g., manual Send/Sync on FFI wrappers).
  5. Reading fields of a bare C union.
ffi_bridge.rs (#[repr(C)] ABI Alignment + Safe Wrapper + Unit Test) 
#[repr(C)] // Guarantee C struct field layout (Rust default layout can reorder!)
pub struct RawCanMsg {
    pub can_id: u32,
    pub dlc: u8,
    pub data: [u8; 8],
}

pub fn decode_c_frame(ptr: *const RawCanMsg) -> Option<u32> {
    if ptr.is_null() {
        return None;
    }
    // SAFETY: Null pointer already checked above; caller guarantees ptr points
    // to a valid, aligned, immutable RawCanMsg for the duration of this call.
    let msg: &RawCanMsg = unsafe { &*ptr };
    Some(msg.can_id)
}

#[cfg(test)]
mod tests {
    use super::*;
    #[test]
    fn null_pointer_returns_none() {
        assert_eq!(decode_c_frame(core::ptr::null()), None);
    }
}

Knowledge Check

Question 1 • Mastery Verification
Why does Rust reject sharing an Rc<RefCell<State>> across an AOSP Binder thread pool while accepting Arc<Mutex<State>>?
Non atomic reference counts lack Sync and Send trait guarantees
Reference counted pointers cannot live inside heap allocations safely anywhere
Binder frameworks forbid mutex synchronization across concurrent vendor kernel services
Interior mutability automatically allocates garbage collection threads on every write
✓ Correct! (Option A: Missing Send + Sync guarantees)
Rc updates its refcount with non-atomic increments and RefCell performs non-atomic borrow checking, so neither implements Send or Sync. Arc<Mutex<T>> provides atomic refcounts and mutual exclusion, allowing safe multi-thread sharing.
Analysis of Distractors:
• Option B: Both Rc and Arc allocate on the heap.
• Option C: Binder threads specifically require synchronization primitives like Mutex or atomics.
• Option D: Rust never creates GC threads.
Question 2 • Mastery Verification
Why must a Rust struct passed across an extern "C" FFI boundary be annotated with #[repr(C)]?
Annotation injects automatic null checks before every foreign function invocation
Annotation enables exception unwinding across Linux kernel C driver boundaries
Default Rust representation may reorder fields breaking C binary compatibility
Annotation strips borrow checker validation inside safe code modules completely
✓ Correct! (Option C: Preserves C ABI field order & alignment)
By default (#[repr(Rust)]), rustc has no stable ABI and can freely reorder fields to minimize struct padding. Marking a struct #[repr(C)] forces exact C compiler field ordering and alignment rules.
Analysis of Distractors:
• Option A, B, D: #[repr(C)] strictly controls memory layout, not runtime checks, unwinding, or borrow rules.
