Memory Anatomy:
Stack, Heap, Data, BSS & Flash Text

In high-level applications, variables are abstract names in code. In embedded systems, every variable occupies physical silicon either in non-volatile Flash or volatile SRAM. Understanding memory segments is essential to avoid stack overflows, memory leaks, and RAM starvation.

Mental Model Shift: JVM Garbage Collector vs Bare-Metal SRAM

In Kotlin/Android, when you create an object or list, ART allocates memory on the JVM heap and the Garbage Collector automatically cleans it up. You rarely know or care what physical memory address it occupies.

On an ARM microcontroller with only 64 KB of total RAM, there is no garbage collector. The Stack grows downward toward the Heap. If they collide, memory corruption is silent and catastrophic.

FLASH (ROM)       ──> ┌───────────────────────────┐
                      │    .rodata (Constants)    │
                      ├───────────────────────────┤
                      │    .text (Code/Vectors)   │
                      └───────────────────────────┘

The 5 Segments Explained

  • .text (Flash / ROM): Contains compiled machine instructions and the interrupt vector table. Read-only and non-volatile (persists through power cycles).
  • .rodata (Flash / ROM): Contains read-only constants, such as string literals ("Booting...") and lookup tables (const uint32_t sin_table[256]).
  • .data (Flash $\rightarrow$ SRAM): Stores initialized global and static variables (e.g. uint32_t baud = 115200;). Initial values are stored in Flash and copied to SRAM during boot.
  • .bss (SRAM): Stores uninitialized global and static variables (e.g. uint8_t buffer[1024];). It consumes 0 bytes in Flash; startup code zeroes this region in RAM before main() is called.
  • The Stack & Heap (SRAM):
    • Stack: Fast LIFO memory managed by the CPU Stack Pointer (SP). Allocates local function variables, return addresses, and saved registers. Grows downward.
    • Heap: Dynamically allocated memory via malloc()/free(). In safety-critical automotive systems (ISO 26262), dynamic heap allocation is strictly forbidden due to non-deterministic fragmentation!

2. Check Your Understanding

Question 1 • Flash Storage Optimization
Why does declaring a 100 KB uninitialized global array allocate zero bytes in Flash storage?
Array data gets compressed by compiler optimizations
Uninitialized global symbols live inside bss segment
Microcontroller stack pointer automatically grows upward instead
Memory management unit performs demand page loading
✓ Correct! (Option B: Lives inside bss segment)
The .bss segment stores uninitialized globals. The binary ELF file stores only the total size needed, not 100 KB of zeroes. At startup, the boot code uses a tiny loop to clear that RAM range to zero.
Analysis of Distractors:
• Option A: Flash does not use runtime compression.
• Option C: Stack is for local variables, not global arrays.
• Option D: Bare-metal MCUs have no MMU or demand paging.
Question 2 • Embedded Safety Practices
Why do automotive ISO 26262 safety standards strictly prohibit dynamic heap allocation?
Heap memory accesses draw excessive battery power
Compiler disables optimization flags on dynamic structures
Non-deterministic fragmentation causes unpredictable runtime allocation failures
Interrupt controllers cannot access dynamic heap memory
✓ Correct! (Option C: Non-deterministic fragmentation)
Repeated malloc() and free() leads to heap fragmentation. Even if 10 KB of free memory exists, it may be scattered in tiny disjoint blocks, causing an allocation to fail while braking or steering!
Analysis of Distractors:
• Option A: Heap memory draws the same power as stack memory.
• Option B: Optimizations apply equally to dynamic data.
• Option D: Interrupts can access any SRAM address.
