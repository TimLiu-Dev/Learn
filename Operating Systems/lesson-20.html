01 // MENTAL MODEL & INTERACTIVE SIMULATOR

Eliminating Kernel UAF & Data Races Without a Garbage Collector

1. Why Kernel Rust Differs From Userland Rust

No Panics on OOM (Fallible Allocation): Userland Vec::push aborts on OOM; in EL1 kernel space, an OOM panic crashes the entire phone! Kernel Rust uses custom fallible APIs (KBox::new(..., GFP_KERNEL)?, Arc::new(..., GFP_KERNEL)?, Result<T, Error> mapping cleanly to -ENOMEM / -EINVAL).

Data-Carrying Locks (SpinLock<T> / Mutex<T>): In C, a comment says `/* protected by proc->lock */`—nothing stops a developer from touching `proc->nodes` unlocked. In Rust-for-Linux, the lock owns `T`; you can only access `T` through a RAII guard (`let guard = lock.lock();`) whose lifetime prevents leaking `&mut T` after unlock!

2. Pin<KBox<T>>, UserSlice & FFI // SAFETY:

Why Pin Is Mandatory in Kernels: Linux embeds intrusive struct list_head and rb_node pointers inside structs (`binder_node`, `work_struct`). If Rust moved a struct in memory by value, every linked-list pointer would dangle! Pin<KBox<T>> + pin-init guarantees the struct never moves once initialized in place.

UserSliceReader / UserSliceWriter: Wraps raw user pointers so safe Rust kernel drivers can never dereference an EL0 pointer directly; every read/write goes through copy_from_user / copy_to_user and checks Result.

02 // RUST-FOR-LINUX CODE REALITY

Fallible Arc, Data-Owning Mutex<T> & Safe UserSlice

Rust-for-Linux: Safe Locking + User-Copy Driver Pattern 
use kernel::prelude::*;
use kernel::sync::{Arc, Mutex};
use kernel::uaccess::UserSliceReader;

struct SharedState { count: u64 }

fn handle_ioctl(state: &Arc<Mutex<SharedState>>, mut reader: UserSliceReader) -> Result<u64> {
    // 1. Safe copy_from_user (overflow + fault checked, returns EFAULT on bad ptr)
    let delta: u64 = reader.read()?;
    // 2. Compile-time enforced lock: cannot touch `count` without holding MutexGuard!
    let mut guard = state.lock();
    guard.count = guard.count.checked_add(delta).ok_or(EINVAL)?;
    Ok(guard.count)
    // 3. `guard` drops automatically on every return/error path (zero lock leaks!)
}
FFI Boundary Contract (// SAFETY: Invariants) 
// Safe Rust wrapper around C kernel struct `struct task_struct *`
pub struct TaskRef { ptr: NonNull<bindings::task_struct> }

impl Clone for TaskRef {
    fn clone(&self) -> Self {
        // SAFETY: `self.ptr` is guaranteed valid & refcounted while `TaskRef` exists.
        unsafe { bindings::get_task_struct(self.ptr.as_ptr()); }
        Self { ptr: self.ptr }
    }
}
impl Drop for TaskRef {
    fn drop(&mut self) {
        // SAFETY: Matches `get_task_struct` refcount invariant on drop.
        unsafe { bindings::put_task_struct(self.ptr.as_ptr()); }
    }
}

03 // ANDROID INTERNALS BRIDGE

Why Android Rewrote Binder, crosvm & pvmfw in Rust

C Binder CVEs vs. Upstream Rust Binder

Historically, drivers/android/binder.c was one of Android's top sources of privilege-escalation CVEs—complex concurrent lifecycles between binder_proc, binder_node, binder_ref, and death notifications caused subtle Use-After-Free races. Android's upstream Rust Binder uses Arc<Node>, Mutex<Inner>, and Pin intrusive lists so dangling references fail compilation rather than shipping as root exploits.

Android's Full Rust Systems Stack (2025–2027)

Beyond the kernel, modern AOSP uses Rust across critical security boundaries: crosvm (the AVF VirtIO VMM from Lesson 14), pvmfw (bare-metal Protected VM firmware running before Microdroid boots), KeyMint, DNS-over-HTTP3 in Netd, and native Rust AIDL services. Knowing both C and Rust FFI invariants is a major 2027 Senior Systems differentiator.

Implement Kernel Rust Ownership & Lock Verifier (simulateRustLockAndArc)

Catch unlocked access, double-lock deadlock, and Use-After-Free across ops (just like rustc does!).

Not Run
Specification: Simulate an Arc<Mutex<T>> with initial strongCount = 1 and lockOwner = null over ops (each { op, thread }):
• "CLONE_ARC": if strongCount === 0 reject { ok: false, error: "UAF_CLONE" }; else strongCount++.
• "DROP_ARC": if strongCount === 0 reject { ok: false, error: "DOUBLE_FREE" }; else strongCount--.
• "LOCK": if strongCount === 0 reject "UAF_ACCESS"; if lockOwner === thread reject "SELF_DEADLOCK"; if lockOwner !== null reject "CONTENDED"; else lockOwner = thread.
• "MUTATE": if strongCount === 0 reject "UAF_ACCESS"; if lockOwner !== thread reject "COMPILE_ERR_UNLOCKED_ACCESS".
• "UNLOCK": if lockOwner !== thread reject "UNLOCK_NOT_OWNER"; else lockOwner = null.
• Return { ok: true, strongCount, freed: strongCount === 0, lockOwner } if all ops succeed.
