P-States (DVFS), C-States (cpuidle), Suspend & Thermal Budgets

1. Active Power (P-States) vs. Idle Power (C-States)

DVFS & schedutil (P-States): Because dynamic power scales quadratically with voltage ($P = C V^2 f$), running a Big core at 3.2GHz burns dramatically more energy than running at 1.4GHz. schedutil is hooked directly into EEVDF's PELT utilization + uclamp bounds so frequency changes in <1ms without polling delays.

cpuidle (C-States): When a core's runqueue is empty, the idle task enters a C-state: shallow C1 (WFI) (clock-gated, <2μs wakeup, keeps L1/L2 cache) vs. deep C3/Power-Collapse (cuts core rail voltage to 0V, ~500μs wakeup + cache flush). Entering deep sleep for a 50μs timer wastes more energy than it saves!

2. System Suspend (s2idle), Wakelocks & Thermal IPA

wakeup_source Refcounting: When screen turns off, Android's suspend daemon writes mem to /sys/power/state. The kernel freezes user tasks (cgroup v2 freezer) and enters s2idle—unless any active wakeup_source (kernel driver or userspace /sys/power/wake_lock) has count > 0, or an IRQ/EPOLLWAKEUP fires.

Thermal Throttling (IPA): When skin/junction temperature approaches trip_point (e.g. 85°C SoC / 43°C skin), Linux's Intelligent Power Allocation (IPA) PID controller computes a milliWatt power budget and caps cooling devices (Big → Mid → GPU OPPs).

  __pm_stay_awake(m->ws);        // Blocks system suspend immediately

// Userspace daemon registers event with EPOLLWAKEUP:
struct epoll_event ev = {

03 // ANDROID INTERNALS BRIDGE

PowerManager.WakeLock, App Standby/Freezer & Thermal Mitigation

How Android Maps App WakeLocks to Kernel Suspend

Calling wakeLock.acquire() in Kotlin makes a Binder call into PowerManagerService, which holds a named kernel wakelock via /sys/power/wake_lock (backed by Linux wakeup_source). If an app forgets release(), the SoC enters shallow idle (`WFI`) instead of s2idle, draining battery overnight. Android's Doze and cgroup v2 Freezer counter this by freezing cached apps and deferring alarms.

ADPF & Android Thermal HAL Throttling

When a camera or 120fps game heats the device, Android's Thermal HAL monitors kernel /sys/class/thermal/thermal_zone* sensors and notifies apps via PowerManager.OnThermalStatusChangedListener and ADPF PerformanceHintManager so renderers scale down resolution before the kernel hard-caps Big/GPU OPPs and causes uneven frame pacing.

LAB 1 OF 3 // CPUIDLE C-STATE GOVERNOR

Implement Break-Even C-State Selector (selectIdleState)

Pick the deepest power-saving C-state without breaking PM QoS latency or break-even residency.

Not Run
Specification: Given states (array of { name, exitLatencyUs, targetResidencyUs, powerMw }), predictedIdleUs, and qosMaxLatencyUs:
• Filter to states where exitLatencyUs <= qosMaxLatencyUs AND predictedIdleUs >= targetResidencyUs.
• Choose the qualifying state with the lowest powerMw (tie-break by deepest / largest targetResidencyUs).
• If none qualifies (e.g. QoS=0), return null (polling / no idle).
LAB 2 OF 3 // WAKEUP_SOURCE & S2IDLE ARBITER

Implement Linux Suspend Arbiter (suspendArbiter)

Enforce wakeup-count race prevention and track active wakelock blockers.

Not Run
Specification: Given sources (array of { name, active: bool, expireMs: number|null }), nowMs, savedWakeupCount, and currentWakeupCount:
• First expire any source whose expireMs !== null && expireMs <= nowMs (treat as inactive).
• Collect names (sorted) of still-active wakeup sources into blockers.
• If blockers.length > 0, return { enterS2idle: false, reason: "ACTIVE_WAKELOCK", blockers }.
• Else if currentWakeupCount !== savedWakeupCount, return { enterS2idle: false, reason: "WAKEUP_RACE_DETECTED", blockers: [] }.
• Otherwise return { enterS2idle: true, reason: "SUSPEND_OK", blockers: [] }.
LAB 3 OF 3 // THERMAL IPA OPP CAPPING

Implement Thermal Power-Budget Allocator (allocateThermalBudget)

Cap Big/Mid/Little + GPU OPP levels to stay within a thermal milliwatt envelope.

Not Run
Specification: Given clusters (array of { name, opps: [{ mhz, mw }, ...] } sorted ascending by mhz, where index 0 is the minimum OPP) and budgetMw:
• Start every cluster at its highest OPP (index opps.length - 1).
• While total mw across all clusters exceeds budgetMw, step down by 1 OPP the cluster (with current index > 0) that saves the most mw in one step (tie-break by highest current mw, then lexicographically by name).
• Stop if total mw <= budgetMw or all clusters are at OPP index 0. Return { withinBudget: totalMw <= budgetMw, totalMw, chosen: { [name]: mhz } }.
