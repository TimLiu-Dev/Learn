Lesson 17: Hardware Interrupts, GICv3, SoftIRQs, Workqueues & Timers

An operating system does not only react to user SVC #0 syscalls—hardware devices and timers interrupt the CPU asynchronously via ARM64 GICv3 and the ARM Generic Timer. Senior kernel engineers know exactly what runs in atomic top-half IRQ context versus deferred softirq, threaded IRQ, and workqueue contexts—and how tickless NO_HZ + hrtimer keep phones asleep without missing deadlines.

01 // MENTAL MODEL & INTERACTIVE SIMULATOR

Top-Half Hard IRQs, Bottom-Half Deferral & Tickless Timers

1. ARM64 GICv3 Routing & Execution Context

Three Interrupt Classes: SGI (0–15, Inter-Processor Interrupts for TLB shootdowns/resched), PPI (16–31, per-core private interrupts like the ARM Generic Timer), and SPI (32–1019, shared peripherals like UFS, touchscreen, NIC).

Acknowledge → Handle → EOI: When GICv3 asserts IRQ, the core traps to VBAR_EL1 + 0x280 (EL1h) or 0x480 (EL0), reads ICC_IAR1_EL1 to acknowledge the active INTID (raising running priority so lower-priority IRQs wait), masks/acks the device, and writes ICC_EOIR1_EL1 to drop priority.

2. Top-Half vs. Bottom-Half & Why Sleep Panics

Hard IRQ (Top Half): Runs with local interrupts disabled and no process context (`current` is whatever task happened to be interrupted!). Calling mutex_lock(), msleep(), or kmalloc(GFP_KERNEL) causes BUG: scheduling while atomic.

Deferral Hierarchy: Use softirq (per-CPU atomic vector: NET_RX, TIMER, RCU; still cannot sleep!), Threaded IRQs (request_threaded_irq → dedicated RT kernel thread `irq/NN-dev` that can sleep on I2C/SPI buses), or workqueue (cmwq worker kthread pool for sleepable non-RT work). Legacy tasklet is deprecated in Linux 6.x.

High-Resolution Timers (`hrtimer`) & Tickless `NO_HZ`: Classic Unix woke every CPU 100–1000 times/sec (`HZ` tick) even when idle. Modern Linux (`CONFIG_NO_HZ_IDLE`) inspects the per-CPU hrtimer red-black tree before entering WFI, programs the ARM Generic Timer comparator (`CNTP_CVAL_EL0`) for the earliest next deadline, and goes completely silent—saving massive mobile battery.

02 // C, LINUX 6.x & ARM64 HARDWARE

Threaded IRQ Drivers, ARM Generic Timer & AegisOS-64 Vector Slot

Linux Kernel Driver: Top-Half + Threaded Bottom-Half 
// Top half: runs in atomic hard-IRQ context (NO sleeping!)
static irqreturn_t touch_hardirq(int irq, void *dev_id) {
  struct touch_dev *t = dev_id;
  t->irq_ts_ns = ktime_get_ns();      // O(1) timestamp
  disable_irq_nosync(irq);            // Mask level IRQ until thread finishes
  return IRQ_WAKE_THREAD;             // Wake irq/48-touch kernel thread
}

// Bottom half: runs in SCHED_FIFO RT thread context (CAN sleep on I2C!)
static irqreturn_t touch_thread_fn(int irq, void *dev_id) {
  struct touch_dev *t = dev_id;
  u8 buf[32];
  i2c_master_recv(t->client, buf, sizeof(buf)); // Sleeps via mutex/DMA!
  input_report_abs(t->input, ABS_MT_POSITION_X, parse_x(buf));
  input_sync(t->input);
  enable_irq(irq);
  return IRQ_HANDLED;
}

03 // ANDROID INTERNALS BRIDGE

VSYNC Delivery, Touch Latency & Wiring Timer Preemption in AegisOS-64

Touchscreen & Display VSYNC in Android

When your finger taps a Pixel screen, the touch controller pulls an SPI interrupt line high → GICv3 routes it to a CPU → touch_hardirq records the timestamp and wakes the threaded IRQ (irq/NN-fts_ts) → reads coordinates over I2C/SPI → wakes InputReader via epoll → dispatches to your app's Looper. Similarly, display hardware fires VSYNC IRQs that drive Choreographer and SurfaceFlinger.

Real-World Failure: SoftIRQ Starvation & IRQ Affinity

If heavy Wi-Fi/5G packet floods pin NET_RX_SOFTIRQ onto Core 0 alongside touchscreen IRQs, your UI feels laggy even at 20% total CPU! Android vendor kernels pin noisy modem/storage IRQs away from UI-critical cores via /proc/irq/<n>/smp_affinity and run critical threaded IRQs at real-time SCHED_FIFO priority.

Catch BUG: scheduling while atomic before routing work to softirq, threaded IRQ, or workqueue.

Not Run
Specification: Given req = { mode, maySleep, urgent, execNow }:
• If req.execNow is true and req.maySleep is true in mode === "HARDIRQ" or mode === "SOFTIRQ", return { ok: false, error: "BUG_SLEEP_IN_ATOMIC" }.
• If !req.execNow: route to "THREADED_IRQ" if req.maySleep && req.urgent; to "WORKQUEUE" if req.maySleep && !req.urgent; or to "SOFTIRQ" if !req.maySleep. Return { ok: true, target }.
